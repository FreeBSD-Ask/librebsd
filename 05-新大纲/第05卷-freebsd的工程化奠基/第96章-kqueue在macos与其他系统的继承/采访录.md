## 第 96 章 不同时期人员的采访录

> 本子节为第 39 章“kqueue 事件通知革命”的配套采访录，覆盖 2000 年 kqueue 诞生时期 1 位关键人员的公开论文。所有来源均经联网核实；考据过程另见 `原材料/研究/考据记录/`。

### kqueue 创生者的技术论文（2000 时期当事人）

#### 采访 1：Jonathan Lemon

**字段 1 采访元数据**

- 受访者：Jonathan Lemon，FreeBSD 核心贡献者、kqueue 与 kevent 机制作者
- 采访者：自述，无采访者（技术论文）
- 采访时间：2000-07（USENIX 2000 年度技术会议宣读）
- 采访形式：会议论文（技术设计陈述）
- 原始来源：Jonathan Lemon, “Kqueue: A generic and scalable event notification facility”, USENIX 2000 Annual Technical Conference, FREENIX Track。论文 PDF **<https://people.freebsd.org/~jlemon/papers/kqueue.pdf>**；作者页面 ** <https://people.freebsd.org/~jlemon/>**
- 存档信息：经联网检索确认论文 URL 真实存在（访问日期 2026-07-24），作者邮箱 <jlemon@freebsd.org> 经 FreeBSD 手册页 kqueue(2) AUTHORS 段交叉验证

**字段 2 采访摘要**

Lemon 在 kqueue 论文中陈述 FreeBSD kqueue/kevent 机制的设计目标：提供通用且可扩展的事件通知设施，克服传统 select/poll 在扩展性与功能上的局限。论文涵盖 kqueue 的 API 设计（kqueue() 创建、kevent() 注册与获取事件）、支持的事件类型（socket、vnode、timer、signal、process 等），以及与 Linux /dev/poll 的对照。kqueue 首次出现于 FreeBSD 4.1-RELEASE。

**字段 3 考据脚注**

本则论文 URL **<https://people.freebsd.org/~jlemon/papers/kqueue.pdf>** 经联网检索（WebSearch“Jonathan Lemon kqueue FreeBSD paper”）确认真实存在（访问日期 2026-07-24），多个技术博客与 C10K Problem 译文引用该 URL。作者页面 **<https://people.freebsd.org/~jlemon/>** 经检索确认可访问。Lemon 作为 kqueue 作者的身份，经 FreeBSD 手册页 **kqueue(2)** 的 AUTHORS 段（"The kqueue() system and this manual page were written by Jonathan Lemon <jlemon@freebsd.org>"）交叉验证，手册页同时记载 kqueue 首次出现于 FreeBSD 4.1。自利偏差审查：kqueue 论文为技术设计陈述，自利偏差风险较低；但其对 kqueue 优于 select/poll 的判断须与 Linux epoll 路径（几乎同期独立发展）对照，不得以 BSD 阵营视角径采 kqueue 优越论。完整考据过程见 [20260724_jonathan-lemon-kqueue-paper.md](../../../原材料/研究/考据记录/20260724_jonathan-lemon-kqueue-paper.md)。

**字段 4 与本章节内容的关联**

- 为子节 39.1（kqueue 的设计与动机）提供 kqueue 机制设计目标的当事人一手陈述
- 为子节 39.3（kqueue 在 FreeBSD 4.1 的引入）提供首次发布版本的论文佐证
- 为子节 39.7（kqueue 与 epoll 的比较）提供 kqueue 设计期与 /dev/poll 的对照基准

**字段 5 史观映射**

- 总纲 2 “历史是形式主义化的非存在”——据第 2 章原文 “本书所写皆是当下主体的重构”，Lemon 2000 年的 kqueue 论文虽为技术设计陈述，但仍是 2000 年当下主体对 select/poll 在高并发场景瓶颈的重组与形式主义化。其论文中 “kqueue 克服传统 select/poll 在扩展性与功能上的局限” 的判断，是 Lemon 在 2000 年这一当下赋予既有事件通知机制的形式主义化叙事。
- 总纲 3 “不存在进步，只有权力再分配”——据第 3 章原文 “技术演进不是从低级到高级的进步，而是形式主义的诡异曲线”，kqueue 从 select/poll 到通用事件通知设施的改造，不可被读为 “事件通知技术进步”，而是 select/poll 时代的同步阻塞权力被重新分配给 kqueue 时代的异步事件驱动权力。Lemon 的设计陈述本身即参与这一权力再分配。
- 总纲 5 “没有必然性，只有偶然性”——据第 5 章原文 “每一个关键人物、每一次 fork、每一个技术决定，都是不可替代的偶然”，kqueue 与 epoll 几乎同期独立发展，印证技术演化的偶然性而非必然性。Lemon 作为 kqueue 唯一作者的不可替代性，与 epoll 作者的不可替代性，构成 BSD 与 Linux 在事件通知路径上的偶然分化——不可被读为 “BSD 必然发明 kqueue” 或 “Linux 必然发明 epoll” 的目的论。
- 总纲 9 “经验优先”——据第 9 章原文 “优先呈现质朴的事实与当事人的直接经验，而非套用复杂框架”，kqueue 从 select/poll 在高并发场景的实际瓶颈经验中生发，而非从异步 I/O 理论推演。Lemon 论文中支持的事件类型（socket、vnode、timer、signal、process 等）的列举，体现从实际应用场景出发的工程取向。但 “经验优先” 不否定异步 I/O 理论的作用——kqueue 的 API 设计（kqueue() 创建、kevent() 注册与获取事件）仍借助既有事件通知理论框架。
- 总纲 10 “动手者创造历史”——据第 14 章 14.2 节 “真正的问题不在于技术发展的程度，而在于是否动手”，Lemon 作为 kqueue 唯一作者在内核一线的亲手实现，体现事件通知革命的动手形态。但 14.1 节 “决定世界的并非某个阶级，也不是什么经济” 提示：不可将 Lemon 的 “唯一作者” 身份简化为 “独立英雄” 的阶级叙事——其动手形态是与 FreeBSD 手册页 kqueue(2) AUTHORS 段的交叉验证中确认的，“动手者” 的认定本身依赖社区形式主义化的记录机制。
- 总纲 22 “知识注定过时”——据第 22 章原文 “今天书写的技术史，可能在出版之日就已过时。技术债务是历史遗产”，select/poll 被 kqueue 取代，印证具体事件通知机制随高并发演进而过时。但据第 22 章原文 “数字档案既是机遇也是威胁”，kqueue 作为历史遗产既为后续事件通知设计（如 Linux signalfd、Windows IOCP）提供参照，又作为技术债务制约 FreeBSD 事件通知路径的进一步演化。
