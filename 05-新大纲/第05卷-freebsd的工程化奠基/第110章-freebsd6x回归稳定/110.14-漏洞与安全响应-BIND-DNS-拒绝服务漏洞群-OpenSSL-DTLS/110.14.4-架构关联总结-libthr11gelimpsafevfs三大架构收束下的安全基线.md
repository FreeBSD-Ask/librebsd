# 110.14.4 架构关联总结——libthr 1:1/GELI/MPSAFE VFS 三大架构收束下的安全基线稳定

  **要点**：6.x 版本周期共 29 条 commit（7 CVE + 22 security fix），月均约 1.07 条/月，显著低于 5.x 的 3.64 条/月（80 条/22 个月）——这一降幅不能简单解读为 “6.x 更安全”，而是反映三重结构因素：其一，5.x 时期 SMPng/GEOM/MAC 三大新架构的安全基线已在 80 条 commit 中建立，6.x 受益于先发投入；其二，6.x 时期 libthr 1:1 取代 KSE M: N 线程模型，消除了 M: N 模型在内核线程调度路径上的复杂竞态面，线程相关安全修复需求随之下降；其三，6.x 时期 GELI 取代 GBDE 作为推荐磁盘加密方案，Colin Percival 提交的 gbde key file 修复 `a5e9d3ad0cdaaa2eb16b52cefe47a865c619bf84` 是 GBDE 维护期的尾声产物，GELI 的更严谨密钥派生模型（PBKDF2 + HMAC-SHA512）降低了后续密钥处理漏洞的暴露面。MPSAFE VFS 收束方面，John Baldwin 在 7.x 时期 `7f307a7ee8bd205f347128834017f3667adcde0b`（2009-03-10，MPSAFE sysctl 标记）的工作可追溯至 6.x 后期的 VFS Giant 锁退出路线，6.x 时期 VFS 路径的安全修复（如 devfs jail revert）需在 MPSAFE 化的语境下理解——devfs 自动挂载被撤销部分原因是 MPSAFE 化尚未完成的过渡期对竞态的容忍度更低。整体看，6.x 的安全响应节奏标志着 FreeBSD 从 5.x 架构转型期的 “高强度安全基线建设” 过渡到 “稳定维护期” 的工程节奏
  
**史料**：freebsd.duckdb freebsd-src 仓库 6.x 版本周期 commit 统计（29 条 security-related commit / 27 个月）；5.x 版本周期 commit 统计（80 条 / 22 个月，月均 3.64）；commit `a5e9d3ad0cdaaa2eb16b52cefe47a865c619bf84`（gbde key file，2006-02-14）；commit `7f307a7ee8bd205f347128834017f3667adcde0b`（7.x MPSAFE sysctl，2009-03-10，用于架构关联对照） ［A］
  
**史观**：总纲第 5 条——没有必然性，只有偶然性：5.x 架构转型的安全代价在 6.x 兑现为稳定红利；总纲第 3 条——不存在进步，只有权力再分配〔映射存疑，待主理人审定〕：libthr/GELI/MPSAFE VFS 三大架构收束的工程投入通过降低安全响应频率得到部分回报；总纲第 13 条——法律与道德是利益分配〔映射存疑，待主理人审定〕：稳定期的安全响应成本分摊不能作为 “安全质量” 的直接指标，需结合架构变化语境
  
**辨析**：5.x 与 6.x 的 commit 月均对比（3.64 vs 1.07）须谨慎解读——5.x 的 80 条中部分为 4.x MFC 回溯（约 30 条），扣除后 5.x 本身新增约 50 条（月均 2.27 条/月），仍高于 6.x 的 1.07，但差距收窄；6.x 的 22 条 security fix commit 中有 7 条为 Bruce A. Mah 的文档维护类 commit（非代码修复），扣除后 6.x 代码级安全修复约 15 条/27 个月 ≈ 0.56 条/月，与 5.x 扣除文档后的 1.91 条/月（约 42 条/22 个月）对比更合理；6.x 时期 OpenBSM 1.0 alpha 10 的 MFC 是 TrustedBSD 审计子系统从研究项目转向生产可用的关键节点，但 alpha 阶段的稳定性需对照 OpenBSM 1.0 正式版（2007-04-28）发布时间核验；GELI 在 6.x 时期作为新引入磁盘加密方案，其本身的安全响应记录（无 CVE）可能与采用率较低有关，需对照 6.x 时期 GELI 部署统计核验
