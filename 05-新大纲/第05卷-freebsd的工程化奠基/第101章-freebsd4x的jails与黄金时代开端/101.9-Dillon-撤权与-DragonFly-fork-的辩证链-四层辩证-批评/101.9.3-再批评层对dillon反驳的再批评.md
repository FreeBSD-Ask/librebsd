# 101.9.3 再批评层：对 Dillon 反驳的再批评

  **要点**：对 Dillon 反驳的再批评指出，DragonFly 的 LWKT 路线后续也面临重大挑战，Dillon 的“无锁”理想并非全然成功。其一，DragonFly 原定的内核级集群（single system image clustering）目标在 2007 年前后被放弃，官方历史页面承认“This original design direction, although no longer the primary goal of the DragonFly project, has influenced many of the design decisions”；其二，DragonFly 的 HAMMER 文件系统开发耗时远超预期（2008 年才随 2.0 发布），原定的集群基础设施未能实现；其三，FreeBSD 的 SMPng 路线虽在 5.x 付出性能倒退代价，但在 6.x/7.x 逐步成熟，7.1（2008-12-31）ULE 成为默认后 SMP 性能显著提升，证明细粒度锁路线在长期是可行的。再批评者认为，Dillon 对 5.x“too heavily mutexed”的批评在 2003 年有其道理，但 5.x 后续的演化证明 Core Team 的路线选择在长期是正确的
  
**史料**：DragonFly BSD 官方历史页面（dragonflybsd.org/history/，关于集群目标放弃的表述）；DragonFly BSD 2.0 Release Notes（2008，HAMMER 文件系统首次发布）；FreeBSD 7.1-RELEASE Release Notes（ULE 成为默认）；freebsd.duckdb freebsd-src 仓库 tags 表 release/7.1.0 的 tagger_date = 2008-12-31T22:57:14Z〔存疑：经 duckdb 实测该时刻 tag 的 tagger 为 Ken Smith，cvs2svn 名下 release/7.1.0 为 2008-12-19T21:12:36Z，标记者与时间错配待回源核正〕［A］
  
**史观**：总纲第 22 条——知识注定过时，Dillon 2003 年的判断在 2008 年后的 FreeBSD 演化中部分过时；总纲第 2 条——历史是形式主义化的非存在，“路线正确”本身是回溯性建构
  
**辨析**：考据过程留痕——【查证来源】DragonFly BSD 官方历史页面（<https://www.dragonflybsd.org/history/>）经 WebFetch 一手核验，明确记载"This original design direction, although no longer the primary goal of the DragonFly project, has influenced many of the design decisions”，原文以“no longer the primary goal”措辞承认集群目标已放弃，但未给出具体放弃年份；DragonFly BSD 2.0 Release Notes（2008）经核验记载 HAMMER 文件系统首次随 2.0 发布；FreeBSD 7.1-RELEASE Release Notes 与 freebsd.duckdb freebsd-src 仓库 tags 表 release/7.1.0 的 tagger_date = 2008-12-31T22:57:14Z（tagger = cvs2svn〔存疑：实测该时刻 tagger 为 Ken Smith，cvs2svn 名下 release/7.1.0 为 2008-12-19T21:12:36Z，错配待核正〕，target_commit_hash 经 SQL 查询一手核验）互证，ULE 调度器在 7.1 成为默认；“2007 年前后”为概数，须对照 DragonFly 邮件列表（users@与 <kernel@dragonflybsd.org>）核实集群目标被明确放弃的决议时间；【交叉验证方法】DragonFly 官方历史页面（二手但官方）、DragonFly 2.0 Release Notes（一手发布文档）、FreeBSD 7.1-RELEASE Release Notes（一手发布文档）、freebsd.duckdb freebsd-src tags 表 release/7.1.0 tagger_date（代码级证据）四方互证——HAMMER 2008 发布与 release/7.1.0 2008-12-31 tag 时序一致，二者在 2008 年时点同步验证 Core Team SMPng 路线“长期成熟”判断成立；【0 信任原则·“长期正确”的回溯性建构】称 Core Team 路线“长期正确”本身是一种回溯性建构，5.x 在 2003-2005 年的性能倒退是当时用户承受的真实代价，不得以 7.x 的成熟反推 5.x 路线“必然正确”——史家须区分“路线在长期被验证可行”与“路线从一开始即正确”两种判断，前者为事实陈述，后者为回溯性建构；DragonFly 的 HAMMER 文件系统虽开发耗时（2003 fork 至 2008 发布历时约 5 年）但最终成功，不得以其开发周期长即否定 LWKT 路线；【存疑判定依据】DragonFly 集群目标被明确放弃的具体年份未在官方历史页面给出，“2007 年前后”为概数，须对照 DragonFly 邮件列表存档核验；“5.x 性能倒退”在 Phoronix 与 freebsd-performance 邮件列表中的具体基准测试数据未在 Dillon 公告中引用，需后续补验具体测试场景与硬件配置；称“Core Team 路线长期正确”这一判断须以 5.x-7.x 完整 release cycle 的性能数据为据，当前仅以 7.1 ULE 默认为节点证据，存疑保留待 6.x-7.x 详细性能基准测试数据补验
