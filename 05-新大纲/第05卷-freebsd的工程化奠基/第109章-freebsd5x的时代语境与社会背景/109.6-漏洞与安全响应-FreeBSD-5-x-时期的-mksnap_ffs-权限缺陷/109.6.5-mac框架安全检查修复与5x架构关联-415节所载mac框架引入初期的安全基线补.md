# 109.6.5 MAC 框架安全检查修复与 5.x 架构关联——41.5 节所载 MAC 框架引入初期的安全基线补强

  **要点**：FreeBSD 5.0 引入的 MAC 框架（41.5 节〔存疑：旧 41 章节号，现行结构无对应节，重挂待考〕所载 Robert Watson 主导）在 5.x 版本周期内即发现安全检查覆盖不完整问题——2005-05-18 Christian S.J. Peron 提交 MAC check_vnode_mmap 入口点修复（commit `4818dd318bb3f760971f76b1e88c85ec2062d52a`，将 MAC check_vnode_mmap 入口点从 MAP_SHARED 专属扩展至所有 mmap 调用，使入口点覆盖 MAP_PRIVATE 等其他映射类型）；该修复直接关联 5.0 引入 MAC 框架时的设计缺陷——初始实现仅对 MAP_SHARED 映射执行 MAC 策略检查，遗漏 MAP_PRIVATE 映射，使 MAC 策略无法对私有内存映射强制执行访问控制；这一修复发生在 5.x 版本周期末段（2005-05-18，距 5.5-RELEASE 2006.5 约 1 年），反映 MAC 框架引入后安全基线需经实际部署才能完善；同期 2005-03-14 Bruce A. Mah 提交 jail(8) chflags_allowed 与 **ipfw(8)** debug 相关 commit（commit `f667ed26071cc2097d9e39883a4024dfdaf78de3`），反映 MAC/Jails/ipfw 三类安全机制的协同改进
  
**史料**：freebsd.duckdb freebsd-src 仓库 commits 表（4818dd318bb3f760971f76b1e88c85ec2062d52a、f667ed26071cc2097d9e39883a4024dfdaf78de3）；mac(4) 手册页；Watson BSDCon 2001 MAC 演讲 ［A］
  
**史观**：专题语（不设总纲条号）——形式主义膨胀与抽象克制：MAC 框架作为 5.0 引入的抽象层，其安全检查入口点的覆盖完整性需经实际部署验证——这是抽象层引入初期的典型工程代价；专题语（不设总纲条号）——软件工程：MAC 框架的安全基线建立不是一次性完成，而是随实际部署发现缺口逐步补强
  
**辨析**：MAC check_vnode_mmap 修复无 CAN/CVE 编号，但 commit message 明确说明修复目的（"Move MAC check_vnode_mmap entry point out from being exclusive to MAP_SHARED"），按 0 信任原则可采信；【架构关联】MAC 框架作为 5.0 引入的核心安全架构（41.5 节〔存疑：旧 41 章节号，现行结构无对应节，重挂待考〕），其安全检查入口点的覆盖完整性直接影响 MAC 策略模块（如 mac_biba/mac_mls/mac_seeotheruids）的强制能力——check_vnode_mmap 入口点遗漏 MAP_PRIVATE 使策略模块无法对私有映射强制执行机密性/完整性策略，是 MAC 框架引入初期的结构性缺陷；【GEOM 关联】5.x 版本周期内 GEOM 框架（41.3/109.2.1 节〔存疑：41.3 系旧 41 章节号，重挂待考〕所载）本身未发现直接安全漏洞，但 GEOM class 链（如 geli 加密 class）的安全性依赖上层 MAC 框架的访问控制——MAC check_vnode_mmap 修复间接强化了 GEOM 加密设备的访问控制覆盖；【commit 量比较公平性】5.x 版本周期内 MAC 框架相关 security fix commit 仅 1-2 条，反映 MAC 框架引入初期部署范围有限，安全基线完善需更长周期
