# 099.1.6 MidnightBSD起于Holt2004年的构想定位桌面BSD系统以易用与安全

- MidnightBSD 起于 Holt 2004 年的构想，定位桌面 BSD 系统，以易用与安全为核心诉求；他判定其他 BSD 项目对普通用户不够友好。桌面环境选择 GNUstep 而非 KDE 或 GNOME：PC-BSD 与 DesktopBSD 已占据 KDE 路线，GNOME 被众多 Linux 发行版采用而不合其差异化意图，且 Mac 社区存在 Objective-C 动量可资借助；其论证援引 NeXTSTEP 与 Mac OS X 的 BSD 痕迹与共享代码——Cocoa 即 NeXTSTEP、OpenStep 原始库的增强版本，GNUstep 则在库层面克隆 OpenStep，故 GNUstep 配 BSD 是历史的自然搭配。（BSDTalk EP126，[55.96-190.24]，L1）
- mports 是项目差异化重点：Holt 批评 FreeBSD ports 中相当一部分无法正确构建可复用的包，项目首要目标是让所有 port 都能打包，以 pkg_add、pkg_delete 式工具像 Linux 发行版那样消费二进制包，并完全重写包工具、提供命令行与图形两种界面、进而兼作系统更新之用。开发者 Chris Reinhardt 已完成初始脚本与 makefile 改动，正开发 ports 构建集群测试工具，包工具库与命令行界面随后，图形界面与系统偏好工具由 Holt 之妻以 GNUstep 编写。（BSDTalk EP126，[197.80-310.78]，L1）
- 基线与发布策略：当时仅发 i386，AMD64 随下一版本，Sparc64 仅为开发兴趣、PowerPC 无近期计划；项目继续基于 FreeBSD 6 系列，仅个别特性自 7 回移，Holt 强调“我们不是发行版，而是从 FreeBSD 项目分出的分支”；安装仍用 FreeBSD 的 sysinstall，基于 GNUstep 的 live CD 图形安装器（后端库加可选命令行界面）在开发中；镜像站点包括项目自有 FTP、ISD、东密歇根大学与 allbsd.org。1.0 设有自我约束门槛：普通用户放入光盘即得完整桌面环境并能图形化管理系统的程度未达，即不发布 1.0，以 Ubuntu 的开箱即用为参照；1.0 前至少五个发布，0.2 前完成包工具与新安装器，0.3 增加偏好工具，其余视社区反馈自适应。（BSDTalk EP126，[313.06-601.54]，L1）
- Holt 自陈开发以来最大障碍是获得社区接受：项目必须使用大量 GPL 许可的工具；操作系统偏好根深蒂固，Linux 仍然流行，许多开发者不愿看到又一个 BSD 出现；向上游提交补丁的成败因项目而异，Perl 项目是第一个接受其上游补丁的项目。安全方面，项目计划提供按服务开关、易于配置的防火墙面板（以 Mac OS X 防火墙控制面板为参照），并做用户态与内核的透明安全增强，针对 X11 的历史安全问题；明确不走 OpenBSD 那种妨碍用户的极端路线；ProPolice 曾进入代码树但因线程库问题撤出，未来可能恢复或转向 GCC 4.2；项目设安全官员专责研究。（BSDTalk EP126，[749.70-869.04]，L1）
- 受访者入坑经历：1990 年代末在 Western Digital 的分包商处支持一套专跑 FreeBSD 的硬盘物流系统，除物理盘故障外从未出现问题，其设计被其评价为优雅；此后试用 Linux 因不满 Red Hat 包管理而 FreeBSD ports 从未让他出问题，遂固定使用 FreeBSD 至今。（BSDTalk EP10，[127.86-189.50]，L1）
- 部署概况：加州 Fullerton 学区推行一对一笔记本计划，每名学生配一台底层运行 Darwin 的 Apple iBook，FreeBSD 承担控制全部 iBook 的后台服务器角色；BSD 只作服务器用途、不部署桌面（避免 KDE 等员工培训成本），完全占据服务器机房与各站点计算机；加州教育经费长期紧张，主要靠捐赠设备，BSD 装在捐赠旧硬件上整合入网，形成有钱买 Apple、没钱装 FreeBSD 的弹性组合，两者互操作良好。（BSDTalk EP10，[190.32-261.62]，L1）
- 可管理性与灾备设计：技术部门仅四人，以 OpenLDAP 集中管理全部学生笔记本的权限与账户，且刻意保持 Apple GUI 工具可直接管理 Intel 硬件上的 LDAP，使日常管理无需专家在场；针对管理层被公交撞了网络怎么办的追问，受访者以 sysinstall（其 man 页自认不应再存在）开设安装培训课，并为每台机器编制三环活页夹（配置文件与已装包清单），保证文字资料足以重建系统。（BSDTalk EP10，[283.38-405.98]，L1）
- 运维可靠性与旧硬件性能：以无 GUI 的 cvsup 经 cron 定期更新，除非重大安全问题不强制升级；一台 FreeBSD 4.0 机器在仓库执行简单任务已连续运行数年而无需到场维护；跨版本升级不难，3.x 手册已不再推荐 buildworld 而有二进制升级建议，最坏情况重装并迁移配置文件即可。BSD 可跑低配硬件是其关键优势：一台 Pentium 3 为 1200 台笔记本提供名字服务并承担 7 个 VLAN 的 DHCP，处理器利用率从未低于四成仍稳定运转；FreeBSD 的 PowerPC 支持规模有限，NetBSD 对 PowerPC 的支持成熟得多，学区借此复活大量退役 PowerPC Mac 与 Intel 捐赠机并用。（BSDTalk EP10，[406.58-660.80]，L1）
- Apple 对比与安全管控：若资金充裕，前端设备仍会保持 FreeBSD，阵列存储会选 Apple 因其界面简单；Apple 整机溢价换来后端与笔记本皆不受病毒蠕虫侵扰，省下的运维开支转投学生教育软件。对学术环境是否对网络抱敌意的问题，受访者称学生总体守规矩，曾抓到安装包嗅探程序者，但 OpenLDAP 目录结构将 Apple 笔记本锁定为只能启动事先授权的应用，下载程序即使在其用户空间内也无法获得执行许可。全套服务均构建于 FreeBSD：对外 VPN（可携带分支办公室，用 Stunnel）、RADIUS 认证、Squid 加 SquidGuard、学生行为监控的 LDAP 认证、面向业务办公室的 Samba 文件共享与面向 Apple 客户端的 Netatalk。（BSDTalk EP10，[503.50-701.10]，L1）
- Moore 自述 PBI 起于个人经验：大学时代在 Linux 桌面上加装仓库外应用屡因 RPM 依赖问题破坏系统，通宵修复而家人打印机停摆，遂立意做一个消除依赖之狱的桌面开源系统——应用自包含于单目录、自行安装、以删除目录即完成卸载，务求父母祖辈无需技术支持即可使用；PBI 正是他创办 PC-BSD 的立基概念。（BSDTalk EP141，[104.66-150.42]，L1）
- 他坦承早期 PBI 体系病在人工打包：志愿者做完一版 Firefox 便消失半年，期间 ports 三度更新而无人重打包；流程繁琐（数小时编译加数小时复原半年前的构建手法），换人重打包则结果时好时坏、回归频发，用户苦于 PBI 版本间不一致，由此判断自动化是唯一出路。（BSDTalk EP141，[153.42-205.16]，L1）
- PBI 4 的核心是构建服务器自动化：以数个纯文本模块配置声明待建端口、桌面图标、MIME 注册与安装脚本（查旧版、警示 Java 依赖等），在 chroot 环境内执行 make world 与编译，并将产物重排为自包含目录结构；模块经 subversion 上传后，每当 port 更新即按同一配置自动重建 PBI，号称可减少回归；构建器全以 shell 写就、可在未装 PC-BSD 的原生 FreeBSD 上运行，夜间构建的状态、报错与完整日志公开于 32/64 位两个 pbibuild 站点。（BSDTalk EP141，[413.58-490.44]，L1）
- 面向使用者的扩展包括：安装目录可自选（默认 /Programs，凡可写挂载点乃至 NFS 皆可）、命令行安装与卸载、安装前可将 PBI 提取到家目录检视且提取物附带生成用配置文件供开发者改后重打包测试、亦可把多应用并装一包（如 Apache、MySQL、PHP 加内容管理系统的 LAMP 式组合）。 [存疑脚注] 原转写作“Juml”不可辨，2026-09-29 重转明确为 Joomla（BSDTalk EP141，[238.0-408.8]，L1）[订正：原 [248.94-405.28]，2026-09-29 SenseAudio 重转核对]
- 规划中的 PC-BSD 1.5 将首度提供 64 位原生构建与 64 位 PBI，并以新托盘应用替换笨重的旧系统更新器：后台静默下载系统更新，同时监视已装 PBI 的过期状态并即时自动更新，令应用维护对使用者近乎无感。（BSDTalk EP141，[553.3-613.3]，L1）[订正：原 [551.68-591.00]，2026-09-29 SenseAudio 重转核对]
- Cornell 的多系统履历与 OpenSolaris 评价：2002 年自 Linux 入 Unix 之门，Solaris 9 曾免费下载（付 20 美元媒体费）但驱动支持贫弱而搁置，至 Solaris 10 渐趋稳定方回归 OpenSolaris；FreeBSD 使用更久，另试过至少 20 个 Linux 发行版、三大 BSD、DragonFly、Mac 与桌下的 SGI Irix 工作站。OpenSolaris 包管理仍是 SVR4 体系、无 ports 对应物、包可得性不及 FreeBSD，开发模式仍偏整体式，GNOME（JDS）以 tar 包加升级脚本发行被他评为主旧；Sun 营销与专利相关的许可证对部分开发者有诱惑，但 Linux 用户基数更大、开发更稳，他不认为 OpenSolaris 会威胁 Linux 或 BSD。（BSDTalk EP146，[152.16-403.44]，L1）
- NVIDIA 驱动的平台差异：Solaris 与 OpenSolaris 因 NVIDIA 与 Sun 的协议随系统附带驱动（其 Quadro FX 1500 开箱即用），FreeBSD i386 则须经 ports 或厂商文件手动安装，性能上 OpenSolaris 与 FreeBSD 相当、略逊于开发主力所在的 Linux；OpenSolaris X11 团队移植的 DRI 仅覆盖驱动全开的 Intel 卡，NVIDIA 走自有 DRI 与 GLX 实现；FreeBSD 7 对他的桌面拦路虎是 AMD64 平台缺 NVIDIA 驱动——他引 2006 年 FreeBSD 邮件档案中 NVIDIA 团队来信：系统缺少若干内核接口，致其无法对 FreeBSD 驱动执行质量管控，原称 FreeBSD 7 应予解决但此后再无音讯。 [存疑脚注] 转写作 curl interfaces，据语境应为 kernel interfaces（内核接口），待以原始邮件核证（BSDTalk EP146，[488.12-593.14]，L1）
- 编解码与专有依赖的桌面张力：MP3、MPEG 等专利编解码非自由，部分发行商付费授权却受 GPL 链接要求牵制，须手动取用或启用（如 GStreamer 前端）；VirtualBox 有与 VMware 竞争之势但当时无 64 位支持；他自认非纯粹主义者（采访需要时会用 Skype），最盼望的专有软件是 Adobe Flash、VMware Workstation/Server 与 Skype；Java 侧 FreeBSD Foundation 提供略旧的 Sun Java 版本、OpenJDK 则是获得新版之路；Gnash 兼容性尚不足生产使用；Skype 即便在 OpenSolaris 也依赖其专有中转服务器，SIP 路线则需软电话与企业级 SIP 支撑而显凌乱；Solaris 发行版自带 Flash 且 Mozilla Firefox 可用（FreeBSD 仅限 Opera），用户基数是厂商是否开放支持的关键变量。（BSDTalk EP146，[603.84-817.64]，L1）
- 流行度辩证与统计困难：BSD 没有 Linux Counter 一类可比统计（后者还混入服务器与高校实验室工作站），只能依赖 web 统计，OpenSolaris 数字只能听 Sun 的而营销另有说辞不可尽信；流行度仅在指望厂商递交专有软件时才重要，若不依赖厂商之“礼”，开发者是两人还是千人并不影响开发延续；开源替代品如 Gnash 已尽力但未达标，而 Adobe 专有 Flash 持续变异、如 Wine 对付 Windows 二进制般是移动目标；专有依赖在换平台时暴露无遗——开源系统几乎能跑任何古怪硬件，SGI 已掐死 Irix 平台，开源软件却仍能在其上编译，NetBSD 反倒在 2001 年的“新”板卡上犯难。（BSDTalk EP146，[843.12-1000.80]，L1）
- 协议标准化的先例与反事实：Will 感慨开源与其追赶专有规格不如自提灵活而流行的替代规格，然而这系于流行度，而流行度是“恶”的；他举 SMTP 先例——各厂商专有邮件系统互不兼容，最终人人臣服于处处可用的协议；Cornell 则给出反事实：1981 年 BSD TCP/IP 因自由（无 GPL 式负担）而被普遍采纳，若当年 BSD TCP/IP 栈是 GPL，将无人采纳，互联网也不会如此互联；两人随即征集开源设定标准的例子，Cornell 举 Evince（遍及 BSD 与类 Unix、新增表单编辑）、Adobe 开放 PDF 规格之举，并评 ODF 进展有限。（BSDTalk EP146，[1050.44-1182.26]，L1）
- FreeBSD 核心团队成员 M. Warner Losh 自述 2007 年以来推动嵌入式 FreeBSD 议程并从事 MIPS 移植，2010 年出任 iXsystems 自由软件开发总监后主持 FreeNAS 8 重构：目标是从单一 NAS 设备转向可跨 FreeBSD 版本移植、可扩展至打印与媒体服务等用途的平台，并以 Alpha 快照形式向社区公开测试。（BSDTalk EP197，[62.72-117.12]，L1）
- FreeNAS 8 的工程基座由旧版沿用 m0n0wall 的 crunched binary 方案整体切换为 NanoBSD：该框架作为 FreeBSD 源树内的打包脚本随主线同步，天然继承全部架构与驱动支持，以约半 GB 镜像面向 CF 卡介质，并通过双分区交替写入实现更新失败即回滚；配置层则改为以 SQLite 数据库统一建模主机、接口、磁盘与卷，开机时由 Shell 与 Python 脚本生成配置文件，Django 提供 MVC 式 Web 界面，数据模式带版本化转换层以延续旧版免手工合并的升级体验。 [存疑脚注] 转写将 NanoBSD 作者记作 Paul Hennigkamp，按 FreeBSD 通行史料应为 Poul-Henning Kamp，属转写音误（BSDTalk EP197，[293.88-1041.86]，L1）
- Losh 从工程角度论证 ZFS 的必要性：磁盘容量增长快于错误率下降使完整性校验与自动纠错成为刚需，ZFS 的去重、压缩、池动态扩容与数据冗余构成对低端商用 NAS 盒的差异化优势；其成熟度随各版本导入 FreeBSD 持续改善，且已有公司围绕 FreeBSD 加 ZFS 开展开发，即便 Oracle 不再发布新代码，ZFS 在 FreeBSD 生态中也足以独立维持演化。（BSDTalk EP197，[1544.10-1681.78]，L1）
- 分叉缘由与时机：DragonFly 自 FreeBSD 4.8 或 4.9 分叉，时机极佳——恰在 FreeBSD 为 5.x 及以后进行重大改造之前取得极稳定基座；分叉主因是 FreeBSD 为从单处理器架构迈向真 SMP 采取了他不认同的重型机制，特别是以 mutex 锁定内核各部分以摆脱 giant lock 的方式，未必错误但他认为过重，这促使他考虑分叉建树。（BSDTalk EP22，[244.72-298.60]，L1）
- 透明集群愿景：终极目标是内核级透明的集群架构——进程可在机器间迁移，机群运作如单一系统映像；愿景是把互联网广域环境的算力联合起来，从 SETI@home 式原始形态进阶到将家庭机器的 CPU、存储与网络资源安全地分配给互联网上的集群，供望远镜项目、公钥猎获、天气预报等需超算或本地大集群的任务使用。维护场景要求双机集群中把一台机的全部进程迁出后可安全关机换件，这不是冗余（冗余更难）。前提是数据一致性：把文件当数据库用的复杂程序需要与 SMP 模型相当的缓存一致性，这是进程迁移的门槛；此构想不同于任何现有操作系统，但概念不新——今日以 NFS 导出文件系统是粗糙等价物。安全约束：广域多贡献者集群存在安全问题，最适用途是结果可被更安全机器独立验证的批处理。架构取舍：仅支持 Intel/AMD 32 位，64 位虽为其所好但暂缓——开发者与时间有限必须排定优先级，跨架构移植会把内核核心焊死、妨碍大改，须先把核心朝目标做扎实。（BSDTalk EP22，[111.52-628.28]，L1）
