# 152.1.7 FreeBSD合入由JonathanTLooney提交的TCPblackboxr

- FreeBSD 合入由 Jonathan T. Looney 提交的 TCP black box recorder，可将 TCP 连接事件写入环形缓冲区，记录元数据、可选 TCP 头与套接字信息，并支持以 log id 关联多条连接；在 Netflix 级 100Gbps 流量下无法用 tcpdump 全量抓包，该机制可按错误触发或抽样比例记录连接过程。（BSD Now EP240，[2763.9-3030.7]，L2）
- OpenBSD 在技术邮件列表宣布 map_stack：近二十年前开始的 W^X（可写与可执行互斥）工作新增软件权限位，栈内存须以 map_stack 标志映射，系统调用时校验栈指针寄存器，指向非栈内存即终止进程；该机制由 Theo de Raadt 与 Stefan Kempf 完成，已覆盖 i386、amd64 与 mips64。（BSD Now EP240，[1282.9-1501.8]，L2）
- FreeBSD 合入多项 ZFS 上游特性：dnode 缓存从 ARC 的 1/64 提至 1/32 以减少间接块解压、ARC 统计采用扇出计数器聚合、引入池级 zpool checkpoint 作为可回滚的整池快照，并修复压缩 ARC 关闭时 arc loan 计数器错误导致断言崩溃的问题。（BSD Now EP240，[0.0-1282.9]，L2）
- 一篇博客用 Clang AddressSanitizer 定位并修复 ZXCVBN-C 密码强度库中多处堆与栈越界，说明该工具以约两倍减速为代价，能在测试阶段检出越界访问、use-after-free、double free 等内存错误，并可结合 LLDB 回溯内存分配历史。（BSD Now EP240，[1933.4-2529.0]，L2）
- 节目解读 OpenBSD 的 pledge 机制：程序在完成启动阶段所需的特权操作后调用 pledge 承诺此后仅使用特定资源，违约即由内核以 SIGABRT 终止；execpromises 可为子进程单独设定承诺集，error 标志使违约返回错误而非杀死进程。（BSD Now EP236，[0.0-463.3]，L2）
- 一篇博客通过把 ArcPiece 漏洞示例从 FreeBSD 8 i386 移植到 FreeBSD 11.1 amd64，说明 32 位平台经栈传递 syscall 参数、64 位平台经寄存器与 struct syscall_args 传递的差异，并指出 Linux 32 位用寄存器而非栈。（BSD Now EP236，[509.4-857.8]，L2）
- FreeBSD 源代码库越过 330000 次提交，第 330001 次提交是 Patrick Kelsey 在 Limelight Networks 赞助下完成的 TCP Fast Open 客户端实现，其服务端若干年前为 Verisign 的 DNS over TCP 需求而写，可缩短高频连接的三次握手延迟。（BSD Now EP236，[4559.8-4701.3]，L2）
- 博客讲解 cd 命令：cd 是 shell 内建命令，由标准 Unix 的 chdir 函数发起 chdir 系统调用，内核执行并校验目录权限；/usr/bin/cd 是供无内建实现的 shell 使用的脚本包装，实际 shell 不会去执行它。（BSD Now EP236，[3430.9-3872.6]，L2）

- 新闻综述报道 LibreSSL 2.3.1：基于 OpenBSD 5.9 开发分支的第二个快照，目标 2016 年 3 月前后为 2.3.x 系列冻结稳定 API；内部切换 64 位 time_t，主持人回引 Theo de Raadt 三年前 EuroBSDCon Malta 主题演讲，强调嵌入式设备装机后可二十年不换机、2038 年问题必须现在修复；本期并删除了引入即因运算符笔误从未编译成功的弱 DES 密钥检查死代码——OpenSSL 选择修复保留，LibreSSL 选择整体移除，两条维护路线就此分野；另及 FreeBSD 的 netcat 源自 OpenBSD 分叉。 [存疑脚注] 该死代码的引入年份转写在 2004 与 2014 间游移，函数名亦有语音失真，须对照 OpenSSL/LibreSSL 版本库提交记录核验（BSD Now EP115，[3509.45-3719.03]，L2）
- Hiren Panchasara 在专访中说明 TCP 改进是集体工程：freebsd-transport 邮件列表与每周四电话会议统筹，先在 wiki 清点 RFC 支持清单，再以小步评审引入 RFC 6675 SACK 丢包恢复与 RFC 6937 比例降速，并借 Phabricator 推进输出/输入段处理可运行时加载的模块化改造；他直言 FreeBSD 栈“以稳定著称因而对改动有阻力”（2070.00-2083.87），乱序包场景下重复 ACK 阈值 3 只是承自旧 RFC 的任意值，Linux 会按重排度动态调整；拥塞控制方向他关注 Swinburne 大学 CAIA 的延迟梯度类算法，指出无线时代丢包不再必然意味拥塞；其首次 IETF 之行的主要收获是“我们仍然不知道互联网是如何工作的”（2909.81-2922.05）——中间盒经年不更新、新 TCP 选项常被丢弃，标准化只能靠猜测与隐私约束下的数据收集。（BSD Now EP115，[2025.91-3015.59]，L1）
- 多路径 TCP 是叠加在标准 TCP 之上的协议扩展，让多宿主主机把多个网络接口聚合进同一条 TCP 连接，由内核在应用无感知的情况下跨接口调度数据；一条多路径连接由若干在线路上仍表现为普通 TCP 的子流构成，握手期生成的令牌用于把新增地址关联回既有连接，调度可按最低 RTT 或可用拥塞窗口选择路径，而两端协商失败或选项在中途消失时自动回退为普通 TCP；有状态防火墙把新增子流当作独立连接处理可能丢弃流量，中间盒兼容仍是未决问题。（BSD Now EP106，[1594.62-1658.38]，L1）
- 在 FreeBSD current 之上创建的 BSD router project 优化分支对路由转发代码做了改造，基准测试显示转发性能随网卡队列数增加近线性提升（1 到 2 队列提升约 88%，4 队列约 270%），尤其在该项目传统上因竞争而性能回落的临界点——队列数追平 CPU 数——新补丁使性能得以维持在峰值附近；配套仓库公开基准数据、测试工具与 ministat 统计显著性分析，可由第三方在不同硬件上复现。（BSD Now EP106，[480.86-695.16]，L2）
- IPsec 是作用于 IP 层的安全协议族，最常见用途是建立加密 VPN 隧道；它需要预先配置安全关联，适合端点已知、由网络管理员维护的企业组网，而端点数增长时隧道连接数按 n 乘 n 减一除二快速膨胀；相比之下 SSL 运行于 TCP 之上、依托信任网与证书可与陌生方建立加密，更适合客户端对服务器的 web 业务，两者是场景分工而非替代关系。（BSDTalk EP121，[52.44-307.08]，L1）
- IPsec 与 IPv6 的标准化在九十年代中期并行交织，IPsec 被视为 IPv6 的组成要求；KAME 项目在实现 IPv6 协议栈的同时实现了 IPsec，包含仅做认证的 AH、认证并加密且最常被使用的 ESP，以及严格说并非安全协议却被纳入规范集的 IPComp 压缩协议；这套代码于九十年代中期随 KAME 投放一并进入 FreeBSD 与其他各 BSD。（BSDTalk EP121，[84.76-207.84]，L1）
- 被称为 Fast IPsec 的实现并非 KAME 路线，其代码源自 OpenBSD，由 Sam Leffler 移植到 FreeBSD；OpenBSD 实现的关键动机是 KAME 代码不支持硬件加密卸载，而 Hifn 等厂商的加速芯片是构建商用 VPN 集中器的刚需，Fast IPsec 提供了使用这类高速加密芯片的框架。（BSDTalk EP121，[310.28-379.6]，L1）
- FreeBSD 从 KAME IPsec 栈转向原 Fast IPsec 的两大主因：其一是 KAME 项目已经结束，代码不再有原作者维护；其二是 KAME 代码从未为 SMP 内核多线程化，而 FreeBSD 7 已进入代码冻结，内核中的任何组件都必须 SMP 安全；他本人承担了使该实现支持 IPv6 及修复改进的工作，硬件加速虽对嵌入式与边缘设备很重要但并非换栈主因。（BSDTalk EP121，[413.66-504.4]，L1）
- KAME 的遗产仍留在 FreeBSD 中，其 IPsec 代码已不在 FreeBSD，但 IPv6 代码仍源自 KAME，且不再有 KAME 代码投放；一位原 KAME 开发者新获 FreeBSD 提交权限与他共同推进该代码，另有协作者负责用户态工具的正确性与大量测试；验证手段采用 WIDE 项目姊妹组织构建的 TAHI 一致性测试，要求新 IPsec 代码通过与 KAME 相同的测试集。 [存疑脚注] 转写将两位协作者人名音译失真，具体身份须与 FreeBSD 提交记录交叉核对。（BSDTalk EP121，[390.34-569.74]，L1） [订正：原 IPsec 代码血统来自 KAME 但不再有 KAME 代码投放，2026-09-29 SenseAudio 重转核对]
- 加密加速器的驱动一部分开源一部分闭源，招致社区惯常批评者对二进制 blob 的抱怨；他解释 FreeBSD 对二进制 blob 的容忍度本就高于 OpenBSD，且此类设备的交互模型是经通信通道向硬件传递加密描述符而非在内核内运行闭源代码，与闭源网卡驱动的情形在数据模型上并不相同。（BSDTalk EP121，[658.94-719.18]，L1）
- 核心团队成员回顾 7.x 系列的市场反馈：SMP 扩展性改进兑现为大规模性能提升，用户得以在高速多核服务器上完成服务器整合，把原本需要多台机器的负载并入一机，同时降低空间与能耗开销；大量基于 6.x 的企业与设备厂商正加速向 7.x 迁移，实际升级远不如其担忧的那样痛苦；7.2 定位为 7.x 线的精炼版本。（BSDTalk EP173，[309.9-364.8]，L1）
- 对于 8.0，受访成员一致指认虚拟网络栈（VNET/vimage）为最大变更：每个 jail 获得独立网卡配置、独立路由与自己的网络栈实例，互不影响，使 web 托管与机器整合场景受益；jail 框架由此完成从纯文件系统级、到获得网络支持、再到真正网络栈支持的逻辑升级，并与整机虚拟化到轻量虚拟服务器的连续谱系相衔接，8.0 开箱即用。 [存疑脚注] 转写将 FreeBSD 7 与 FreeBSD 4 误转为 3BSD7 与 3BSD4，此处按上下文订正（BSDTalk EP173，[383.5-470.7]，L1）
- 关于 IPv6，受访者给出关键的历史定性：KAME 团队当年向多个操作系统交付 IPv6 参考实现，对 FreeBSD 而言属于外部贡献，项目此后逐步取得该代码的所有权，使其与自有网络栈收敛、消除残余的巨型锁，并确立“凡改动 IPv4 必须同步改动 IPv6 并说明”的开发准则；IPv6 多播（MLD 与选择源多播）重新实现而非沿袭 IPv4 的后补设计，服务 IPTV 类应用；部署上日本与亚洲、欧洲部分地区已可取得原生 IPv6 服务而北美多为隧道，美国国防部要求采购支持 IPv6，Apple 的 Mac OS X 亦使用 FreeBSD 派生代码完成部分设备的 IPv6 配置。 [存疑脚注] 转写将 KAME 误作 Kami、将 cvsup6 服务器名讹化为 cvsub 等表述，引用时以原始音频核对（BSDTalk EP173，[1934.8-2165.3]，L1）
- 核心团队描述与 PC-BSD 的协作关系：PC-BSD 团队连续数年参加 FreeBSD 开发者峰会并演示其新版集成 jail 的图形化创建与管理功能；团队与上游合作改进桌面硬件支持，其中长期阻碍 64 位平台 Nvidia 驱动所需的虚拟内存特性由 John Baldwin 补齐，预期 FreeBSD 8.0 与 7.3 将支持 64 位 Nvidia；PC-BSD 背后由 iXsystems 推动，核心团队正吸纳其成员深入社区、增进对发布过程的了解，并期待其最终实现与 FreeBSD 发布同步。 [存疑脚注] 转写将 PC-BSD 讹作 PCVSD、PCBSC 等，将 iXsystems 误转为 IAC systems，将 Kris Moore 仅记作 Chris，正名以通行拼法为准（BSDTalk EP173，[1311.4-1460.4]，L1）
- 关于 pfSense，核心团队将其定位为面向防火墙场景的嵌入式 FreeBSD 衍生发行版，配以 web 管理界面；该产品直接集成 8.x 的虚拟接入点支持，使单块无线网卡可承载多个 SSID 与属性各异的网络，并吸纳了在 FreeBSD 社区搁置已久的 NAT-T 补丁；其大规模部署为这些代码提供了额外的实战检验，反馈回流使代码回归 base 树时更成熟，pfSense 团队亦因此受邀参加开发者峰会，带来与既有 PR 渠道不同的用户需求清单。（BSDTalk EP173，[1460.4-1553.9]，L1）
