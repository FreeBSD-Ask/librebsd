- Capsicum 部分他自述：内核部分已趋可用，重心转向 casper 守护进程，用以在无全局命名空间访问权的沙盒内以能力方式提供域名解析等受控服务；架构上曾试验 casper 作为独立进程，因资源限制、CPU 集与路由表等上下文无法经 UNIX 域套接字安全转发而判定不可取，转向由主进程派生并继承全部限制的方案。生态上他提及 Google 赞助 Linux 移植、OpenBSD 亦在考察相近设计。 [存疑脚注] OpenBSD 相关设计的转写含混（does live design），所指方案待核。（BSD Now EP62，[1282.25-1490.00]，L1）
- PEFS是FreeBSD的内核级堆叠加密文件系统，与在文件系统之下按块加密的GELI不同，PEFS位于文件系统之上，在数据写入底层文件系统之前对文件与目录加密。（BSD Now EP29，[4149.72-4230.32]，L1）
- PEFS可运行于ZFS之上，因此能配合ZFS send与receive复制加密数据，这是其相对块级加密在快照复制场景下的重要便利。（BSD Now EP29，[4197.60-4209.68]，L1）
- PEFS附带PAM模块，可在用户登录时把密钥加入文件系统并透明加密其主目录；出于安全考虑，该模块只加载密钥而不自动挂载文件系统。（BSD Now EP29，[3425.58-3494.70]，L1）
- PEFS使用AES-NI，并计划纳入近期的AES-NI性能改进；其未采用opencrypto框架，因为该框架最初面向网络栈的异步加解密任务，不适合文件系统即时读写的同步需求。（BSD Now EP29，[3508.38-3593.26]，L1）
- PEFS的安全审计于2014年2月启动、计划2月底完成，由iXsystems的Matt Olander出资进行；作者认为审计是推动PEFS进入FreeBSD主干的重要里程碑。（BSD Now EP29，[3597.82-4274.90]，L1） [订正：原 [3597.82-3653.42]，2026-09-30 SenseAudio 重转核对]
- PEFS的目标是进入FreeBSD主干，作者曾希望赶在FreeBSD 10分支前完成但因时间不足未成，当时亦无确定时间表。（BSD Now EP29，[3836.14-3899.58]，L1）
- PC-BSD的Life Preserver备份方案以PEFS为基础，对数据加密后进行快照复制与裸机恢复，使远程端即使无法信任也不暴露明文数据。（BSD Now EP29，[4033.52-4058.32]，L1）
- 教程演示在 FreeBSD 与 OpenBSD 上执行全盘加密安装；FreeBSD 侧以脚本化方式处理 GELI 与 ZFS 根文件系统，OpenBSD 侧则结合加密根分区与引导加载器。（BSD Now EP16，[4289.6-4418.6]，L2）
- 新闻讨论 FreeBSD Ports 将引入季度稳定分支（2014Q1），快照维护三个月，期间仅接受安全修复、构建与运行时修复及基础设施变更。（BSD Now EP16，[4690.7-4766.9]，L2）
- PackageNG 社区讨论类似 pkgsrc acceptable licenses 的许可证过滤，使用户可按许可证决定是否允许安装软件包，并考虑提供查看已装包许可证的命令。（BSD Now EP16，[4496.2-4585.9]，L2）
- Poul-Henning Kamp 自述其在 1990 年代初于丹麦公司使用 Unix 工作，386BSD 由 Bill Jolitz 将伯克利内核移植到标准 PC 硬件后开始接触；FreeBSD 项目从 386BSD 的生长中形成，他因时区原因未参与发起，但在项目启动约六小时内加入并自始参与。（BSD Now EP7，[765.12-827.62]，L1）
- Jails 的起源据 Poul-Henning Kamp 口述：chroot 最初是伯克利为构建 release 而作，他将其打磨并添加特性后未用于发布；后因南卡罗来纳州一位托管商希望在同一服务器运行多个 Apache 与 MySQL 版本而提出资助开发，约定一年后提交入 FreeBSD，最终他与 Robert Watson 合写论文《Confining the Omnipotent Root》并在 Maastricht 的 2000 年会议上发表。（BSD Now EP7，[968.64-1077.26]，L1）
- Poul-Henning Kamp 将 jail 描述为单向镜：主机管理员可以站在 jail 之外向内观察而不被 jail 内进程察觉，这一特性被安全研究者用于蜜罐，也被用于 CDN 计费系统等场景；jail 后续又获得虚拟网络栈，使单一内核可启动多个隔离环境。（BSD Now EP7，[1095.10-1257.20]，L1）
- MD5 crypt 诞生于 FreeBSD 2.0 时期：因美国加密出口管制，FreeBSD 无法随发行版附带基于 DES 的标准密码扰码器，secure 发行版改从南非分发；Poul-Henning Kamp 用一个下午写出 MD5 crypt 并以 $1$ 前缀预留算法升级机制，该代码后来广泛扩散至 Cisco 设备、glibc、Flash、JavaScript 与 COBOL 实现，他估计一度保护约五成互联网的完整性。（BSD Now EP7，[1481.56-1750.10]，L1）
- Poul-Henning Kamp 在 DARPA 合同背景下开发 GEOM 可插拔磁盘 I/O 框架，并实现面向全分区加密的 GBDE；GELI 则由 Pawel 编写，二者共同构成 FreeBSD 磁盘加密层。他亦以吃自己的狗粮形容其笔记本自 1992 年起运行 FreeBSD 且分区以 GBDE 加密。（BSD Now EP7，[1756.80-1900.42]，L1）
- Varnish 项目的首度公开：Kamp 描述其正在开发的以 BSD 许可发布的服务器端 web 缓存守护进程，动机是内容管理系统自数据库逐件拼装文章与广告而极度缓慢、用户被迫前置 Apache 或 Squid 抑或购置天价专有盒子；目标是把开源缓存做到极致速度；它不专属于 FreeBSD、可在任何像样的类 Unix 平台运行，FreeBSD 只是竞争的底层平台之一；计划当年夏天招募早期测试者与开发者，概念已在 BSDCan 引起注意，命名取为代码上清漆之意。（BSDTalk EP48，[824.82-919.62]，L1）
- 投身 FreeBSD 的动因源自商业 Unix 的欧洲支持黑洞：美国 Unix 厂商不理解欧洲夏令时制度差异、操作系统时戳出错；自欧洲报障须经厂商本地办事处转往总部，常落入市场部这一仅有的电话号码处，三个月后回称无法复现；作为生产系统负责人的挫败感凝成我能做得更好的信念；FreeBSD 至 2006 年已大体做到开箱即用，其一台机器已连续运行 500 天——可靠性与可预期性正是他所要求的操作系统品质。（BSDTalk EP48，[220.68-326.52]，L1）
- TTY 子系统的 SMP 化与 FreeBSD SMP 总体评价：TTY 代码勾连控制台与会话管理、属难啃的遗留代码，策略是先把锁做对以允许多 CPU 并入；因 SSH 与控制台已取代 VT 终端阵列、TTY 流量剧减，昔日为优化后端口争用而写的复杂代码可大幅简化；总体上 SMP 工作进展极好——BSDCan 公布的数据令人满意，Kris Kennaway 的文件系统扩展性数字尤为惊艳，网络栈虽未完成但在多数关键基准上已胜过 4.x 分支；比预期多花五年缘于网络泡沫的干扰，而当初选择的总体哲学已被证明正确。（BSDTalk EP48，[330.40-529.32]，L1）
- 发布工程观与嵌入式构建谱系：Kamp 曾主理 FreeBSD 2.x 系列与若干 3BSD 发布的发布工程并自称留有情感包袱，长年运行 current 的他视发布为特性沿途滴入的渐进过程而非节点事件；九十年代他为单软盘安装 FreeBSD 而奋战，但 ACPI 一项即占约一兆字节、软盘目标已不可行，PicoBSD 因此淡出视野；其替代谱系为意大利 Frisbee 项目——自光盘运行起家、渐成通用镜像构建工具，未来 nanoBSD 将改由 Frisbee 平台构建；然而四兆闪存加两兆内存的 SoC 级低端仍是空缺，需要按需拣选 bin 目录下少数程序（如接入点或防火墙所需）的构建方式——此缺口正是 BSDCan 上的用户反馈所揭示。（BSDTalk EP48，[689.16-757.76]，L1）
- 丹麦社区与会议出席哲学：丹麦 BSD 用户组以社交为本体——夏夜篝火烧烤、冬日入酒吧小酌、偶尔举办带演讲的聚会；EuroBSDCon 2007 已定于 2007 年 9 月 14 至 15 日在哥本哈根举行、筹备刚启而 Kamp 名字已上待办清单三处；他计划出席每届 EuroBSDCon 与每年渥太华的 BSDCan，理由是资深开发者须借开发者峰会与其他开发者沟通、并直接倾听用户将 FreeBSD 用于何处以校准项目方向——当年 BSDCan 上嵌入式议题的突然升温即被视为这样的方向信号。（BSDTalk EP48，[1057.58-1197.22]，L1）
- gjournal 是块级日志而非文件系统日志：它运行于文件系统层之下，仅需文件系统极少量特化代码即可提供日志能力，且不区分数据与元数据而两者皆记录；因此即便启用 gjournal，FreeBSD 在严格意义上仍属无日志文件系统的主流操作系统，引用时不应将 gjournal 记作 UFS 自身的日志功能。（BSDTalk EP52，[117.82-190.9]，L1）
- 作者说明同时记录数据与元数据的设计动机：仅记元数据存在已知竞态，两者皆记使日志设计更干净，并带来崩溃后镜像设备保持一致、无需重新同步等附带收益；gjournal 还可用于绕开 GBDE 的非可靠性问题。（BSDTalk EP52，[168.42-230.5]，L1）
- 在 soft updates 之下唯一已知的不一致是资源泄漏，后台 fsck 的作用即回收丢失资源；gjournal 使后台 fsck 不再必要。对删除但仍被进程打开的文件，inode 无文件名引用却仍占盘，原方案将其移入 .deleted 目录以便挂载时整体清除，发布补丁后收到反对意见，作者正改写为依赖更快速 fsck 仅回收泄漏 inode 与块的方案。（BSDTalk EP52，[239.98-405.54]，L1）
- GELI 是 GEOM 上的磁盘加密层，与 GBDE 同层但实现路径不同；作者刚提交的数据认证代码使其能够校验数据本身，据其所知此前没有磁盘加密框架认证数据，这对断电场景下防止新数据与旧哈希错配、保证崩溃一致性至关重要。（BSDTalk EP52，[517.02-648.12]，L1）
- 不可变与只可追加文件标志可上溯至 1980 年代 CSRG 的真实安全困境：当时具有登录权限的协作者凭证外流、木马式代码混入代码库，促使开发组将 setuid-root 二进制标记为不可变、将日志文件标记为只可追加；据 McKusick 回忆，攻入者既无法替换关键程序，也无法抹去记录其操作与来源的日志，多数人就此放弃并不再返回，他还追述了循线索追踪一名荷兰入侵者至其住所、由荷兰合作者上门探访后入侵骤然停止的轶事。（YouTube EPE04LxKiu79I，[786.67-941.12]，L1）[订正：原"木马代码险些混入代码库"→"木马式代码混入代码库"（转写为 sometimes they were like even committing stuff into the repository…because they were more or less Trojan horses，系既成混入而非未遂），内容复核]
- jails 为一组进程提供带独立根环境与独立 IP 的受限执行世界：本质上是不可逃逸的 chroot，每个 jail 获得自己的虚拟网络栈与成对虚拟接口，从内部视角自认为独占整机；jail 内 root 可管理本 jail 的进程、文件与端口绑定，却无法看见或向 jail 外进程发信号、无法变更内核变量、无法挂卸文件系统、无法关闭物理网卡或重启系统；随着 ZFS 委派与虚拟网络栈的引入，jail 可行事项持续扩充，其资源占用远低于完整虚拟机，单台服务器可承载数以百计乃至千计的实例。（YouTube EPE04LxKiu79I，[1259.79-1550.19]，L1）[订正："其资源占用远低于完整虚拟机，单台服务器可承载数以百计乃至千计的实例"不在所引区间内，该述出自演讲开头 jails 引入段 [431.8-510.1]（转写为 the footprint…the amount of memory they consume…is far far less than a full-on virtual machine…you're not going to run hundreds or thousands of full-on virtual machines on a single box whereas you can do that with jails），内容复核]
- 随机数体系由 Mark Murray 在 FreeBSD 5.3（2004 年）引入的 /dev/random 奠定：因中断时序、键盘节奏等熵源采集缓慢且总量稀少，系统以真实熵为种子驱动 Yarrow 密码学伪随机数发生器持续输出，并在新熵到达时重置密钥；Yarrow 由熵采集框架、熵累加器、重置密钥机制与生成机制四部分组成，刻意复用经公开文献充分检验的密码学原语而非自行设计；硬件熵源历经 VIA 专用芯片直通输出（早期嵌入式 CPU 跑 Yarrow 需占约两成算力）、Intel RdRand 直通（FreeBSD 9.2 起）到维基解密等事件后改为与其它熵源一并经 Yarrow 混合（FreeBSD 11 引入并回移植至 10.0 及以后）且可被管理员关闭的演进；McKusick 并指出 Fortuna 将以自动化的熵源估计取代 Yarrow 的固定算法，而开机与装机时最需要强随机数却熵源最少的矛盾在其看来仍无良解。 [存疑脚注] Intel RdRand 是否实际被掺假设施并无公开确证，演讲所述属防御性信任决策；Fortuna 替换在演讲时点仍是讨论中的方案而非树内现实。（YouTube EPE04LxKiu79I，[1554.43-2381.76]，L1）[订正：原"维基解密与斯诺登事件"→"维基解密等事件"（转写仅作 all of this stuff coming out with Wikileaks and so on，未提斯诺登），内容复核]
- 访问控制列表的标准史在当事人口中是一部标准政治史：POSIX 1003.1e 草案完成约九成时，委员会内反对者刻意拖延六个月令其越过十八个月的制定期限而死亡，各厂商只得自行补齐剩余一成，造成互不兼容的 ACL 实现，Windows 更另立一套；ACL 早在 1990 年代前中期即已存在，却因各系统实现各异而长期无人使用；此后厂商群体补完 POSIX 草案，另一路与 Windows 兼容的语义进入 NFSv4 规范；FreeBSD 在 UFS 上以挂载选项择一启用，两种语义共用同一套 getfacl 与 setfacl 工具，McKusick 建议新部署采用可跨 UFS、ZFS 与 NFS 且与 Windows 互通的 NFSv4 语义。（YouTube EPE04LxKiu79I，[2677.83-2905.76]，L1）
- 审计以问责与入侵检测为目标，围绕 OpenBSM 建立记录体系，须能回答谁在何时对谁做了什么；McKusick 以美国零售商 Target 数据泄露后数周乃至数月才被发觉、四千万客户信息外流六周的事故说明无人查看的审计日志形同虚设，而 FreeBSD 每夜对全系统 setuid 程序清单做差分、只报告二十四小时内新增或变动条目的做法，被视为让报告短到有人真会去看的实践范例；auditd 守护进程负责筛收与分发审计记录，可应对以填满磁盘来压制审计的攻击手法，记录详尽程度被比作强化版 ktrace，数据亦可外送异地保存；他并透露 FreeBSD 基础设施在约一年半前遭入侵后全面重建，二十年未更新的组件被替换。（YouTube EPE04LxKiu79I，[3413.23-3868.19]，L1）
- capsicum 被演讲者称为 FreeBSD 最新加入的安全机制，由 Robert Watson 与剑桥大学计算机实验室团队设计，大量实现工作出自此前将 ZFS 移植入 FreeBSD 的开发者 pav（Pawel Jakub Dawidek）；其思路是把不受信任的大型库从特权程序中拆出、置于能力模式的子进程中运行，仅凭主进程授予的文件描述符与能力行事——cap_enter 之后的进程如入不可逆的 chroot，无法打开绝对路径、无法访问全局名字空间、无法外联网络或落盘藏匿数据，描述符权利可细分至读、写、定位、监听等单项；名字服务器与 tcpdump 等组件已被沙箱化或在推进中，将大库整体置入能力模块只需付出边界穿越的小代价，即可对未经审计的第三方代码获得实质信心；答问中 McKusick 强调 capsicum 能力与 root 特权列表虽形似而目标迥异：前者隔离不可信组件，后者把 root 权限更精细地授予可信主体。（YouTube EPE04LxKiu79I，[3871.39-4365.60]，L1）
