# 193.6.3 pkgsrcCon2007为第四届于4月27日至29日在巴塞罗那的加泰罗尼亚理工

- pkgsrcCon 2007 为第四届，于 4 月 27 日至 29 日在巴塞罗那的加泰罗尼亚理工大学举行；该会四年前始于维也纳，首届仓促筹办却意外成功，此后固定于四月末五月初在欧洲开发者所在城市巡游，会议本身免费（free as in beer）仅需提前注册，旅费自理。（BSDTalk EP100，[230.64-304.04]，L1）
- 会议运作全凭志愿者，不提供住宿交通协助，选址刻意选旅行成本低的城市以保持参会门槛最低；组织者预期规模数十人，若增至约五十人连集体晚宴都会难以安排，显示其为小规模熟人式技术聚会的定位。（BSDTalk EP100，[409.24-488.08]，L1）
- Sedlacik 阐明会议的社交功能：把名字对应到面孔以提升日后邮件与讨论的沟通效率，让开发者偶尔从用户视角审视系统；并明确欢迎 FreeBSD、OpenBSD 乃至 OpenSolaris 与 Linux 开发者分享经验，往届已有 FreeBSD ports 开发者与会，跨阵营互鉴被列为会议目标。（BSDTalk EP100，[126.92-284.2]，L1）
- 其个人路径完全由动手实践铺就：约 2000 年为替代手头打包方案而在同事的旧工作站上接触 NetBSD 并喜欢 pkgsrc；为加密会议软件 SILC 创建其首批 pkgsrc 包；继而在 Solaris 平台使用 pkgsrc 并做通用缺陷修复，2002 年因持续提交缺陷报告与补丁被开发者接纳转正。（BSDTalk EP100，[504.36-591.88]，L1）
- 其现职揭示 pkgsrc 制度化运作的两翼：release engineering 负责维护稳定分支，安全团队负责修复已知漏洞并逐一通知维护者更新包，加之个人维护数十个包；2008 年会址柏林仅为暂定，取决于本地开发者能否落实场地。（BSDTalk EP100，[591.88-646.2]，L1）
- Cort 高中时代因读 Tanenbaum 的操作系统教科书初识 Minix，曾在 486 时代的 DOS 分区安装早期版本；2010 年经 Google Summer of Code 为 Minix 实现 Unix 域套接字，次年再度参与开发 Minix 上的 pkgsrc 并上游化补丁，在推动变更进入 pkgsrc 上游的过程中受邀成为 NetBSD 开发者，此后同时贡献两个项目。（BSDTalk EP232，[69.00-128.03]，L1）
- Minix 是 POSIX 兼容的微内核操作系统：驱动、文件系统等一切系统服务皆为用户态独立进程，小内核仅负责消息传递并在进程间强制安全隔离，声卡驱动无法触碰网卡、网卡驱动无法写盘；驱动崩溃可即时重启实现自愈，live update 特性可在运行中替换系统级进程；系统服务仅能访问特定硬件资源、须向内核请求许可、多数不以 root 运行。（BSDTalk EP232，[191.74-334.61]，L1）
- 微内核的代价与收益：各服务独立进程天然适合向多核多处理器分布；但用户态消息传递带来约一成到一成五的性能损失，当事人判断这是依负载而定的权衡，对不能宕机的嵌入式与任务关键系统而言，稳定性与安全性足以抵偿性能代价。（BSDTalk EP232，[345.22-398.94]，L1）
- Minix 自约四五年前开始导入 NetBSD 用户态，决策动因是让 Minix 开发者专注微内核设计与服务器架构的独特性；用户态需久经测试、可移植、缺陷清理充分的代码，而用户选择 Minix 的理由应是架构与可靠性而非个别工具；目前共享约八十个 NetBSD 工具及 C 库、构建系统、引导器、口令格式与 pkgsrc。（BSDTalk EP232，[399.59-459.09]，L1）
- ARM 移植推进约一年半，以 BeagleBoard XM、BeagleBone 与 BeagleBone Black 为参考实现；2013 年夏当事人在 Summer of Code 中开发 I2C、电源管理芯片、实时时钟与 GPIO 驱动并移植帧缓冲驱动；板卡文档环境良好，ARM 芯片手册逾四千页，TI Starterware 以 BSD 许可提供全外设示例代码，唯 BeagleBone Black 的 HDMI framer 缺文档。（BSDTalk EP232，[519.97-654.23]，L1）
- 生态现状：Minix 安装器与 OpenBSD 安装器体验相近，pkgsrc 前端提供二进制包，约三千个包可在 Minix 构建运行；TCP/IP 栈正被替换以支持 IPv6，仅上古版本 X 可编译运行；当事人认为当前最重要的待办是作业控制与 X11 移植。（BSDTalk EP232，[721.44-891.33]，L1）
- 受访者 Mitchell Smith 为视障系统管理员，约自 2001 年起使用 OpenBSD 与 NetBSD，此前自 1996 年起使用 Linux；其主要为托管公司与小型企业管理约 70 台 NetBSD 与 Linux 服务器，涵盖 Web、邮件、防火墙与文件服务器，构成 2006 年前后 BSD 在中小型商用运维场景中的一线使用样本。（BSDTalk EP63，[85.36-119.46]，L1）
- 主持人开场介绍受访者已为命令行开发屏幕阅读器并在 NetBSD 与 OpenBSD 上测试且取得进展；受访者本人在访谈中则聚焦于将 Linux 侧成熟无障碍组件移植到 NetBSD 的策略。（BSDTalk EP63，[38.92-62.64]，L2）
- 受访者论证命令行界面天然更利于屏幕阅读器用户：文本输出可被直接朗读，而图形环境需解读对话框、按钮、下拉菜单等视觉构件；其 DOS 屏幕阅读器使用经历佐证熟悉命令行后操作速度反高于图形界面加屏幕阅读器的组合。（BSDTalk EP63，[505.82-534.74]，L1）
- 屏幕阅读生态方面，GNOME 的 Orca 配合卡内基梅隆大学开发的 Festival 语音合成及其精简版 F-Lite，在 NetBSD 上已有相当程度的可用性；但受访者观察到视障用户更普遍的实践仍是 Windows 平台的 JAWS 或 Window-Eyes 商业屏幕阅读器叠加 SSH 终端远程管理 BSD 服务器。（BSDTalk EP63，[209.82-289.58]，L1）
- 受访者自述正在将 Linux 下的 BrailleTTY（内核模块与应用的组合）移植到 NetBSD，刻意目标为用户态实现：既避免改动运行中的稳定服务器内核，也便于直接部署；并指出串口控制台是 SSH 启动前乃至 BIOS 层面的最佳访问手段。（BSDTalk EP63，[297.52-370.4]，L1）
- 迁移与包管理经验：受访者因 Linux 2.6 系列早期内核频繁更新而转向可“安装后不再操心”的 OpenBSD，其后因虚拟化相关支持采用 NetBSD；包管理上其赞赏 Debian 的 apt 易用性，但指出二进制包限制自定义编译选项，而 pkgsrc 便于自行构建软件包并借助 CFEngine 等自动化工具批量下发。（BSDTalk EP63，[921.74-980.12]，L1）
- 运维方法论：受访者力主以 CFEngine、Puppet 等配置管理工具实现自动化，理由是减少人为差错、便于系统复制、留有审计轨迹并压缩管理时间；同类服务器共享基础镜像加客户端微调的模式，与 UNIX 传统上以配置文件为中心的管理方式互为表里。（BSDTalk EP63，[720.82-788.76]，L1）
- 受访者 Johnny Lam 回溯 pkgsrc 的起源：它于 1997 年前后从 FreeBSD ports 的早期版本分叉而来；当时 Solaris 与 Linux 阵营已有各自的包管理方案，而 BSD 系统尚无成熟的软件安装与管理机制，FreeBSD ports 与 pkgsrc 几乎同时处于初创期。分叉之初 pkgsrc 只是 NetBSD 开发者的自用工具，此后逐渐演化为跨操作系统的软件管理系统。（BSDTalk EP83，[105.12-157.22]，L1）
- 受访者将 pkgsrc 的构成概括为两个层面：其一是针对第三方软件的补丁与修改集合，使同一软件得以在多个操作系统上构建，其中长期保留着面向 Solaris、Linux 及各家 BSD 的适配补丁；其二是运行时的软件管理系统，负责跟踪已安装软件包之间的依赖关系，使管理员得以安全删除或更新软件而不影响系统其余部分。该系统同时支持源码编译安装与从 NetBSD FTP 服务器获取预编译二进制包两种模式。（BSDTalk EP83，[161.52-252.72]，L1）
- 关于可移植性与运维实践：pkgsrc 在 NetBSD 全部硬件架构间保持行为一致，并横向延伸至 FreeBSD、Linux 等其他平台；受访者身为纽约多家小公司的全职系统管理员，以 pkgsrc 逐台管理各公司混杂的 NetBSD、FreeBSD 与 Linux 服务器，并把 pkgsrc 视作一个“平台”——在缺乏集中推送软件条件的小规模分散环境中提供统一的管理视图。他还因日常维护大量 FreeBSD 机器而亲自参与 pkgsrc 的 FreeBSD 平台支持。（BSDTalk EP83，[350.08-392.22]，L1）
- 受访者坦言 pkgsrc 以 shell、awk、sed 与大量 make 规则实现，对 make 作为用户界面的过度依赖是项目弱点，FreeBSD ports 亦存在同样问题；非 NetBSD 平台须经 bootstrap 过程安装 NetBSD 版本的 make 方可使用。他同时承认项目规模（当时包数约 6000 至 8000，仍落后于 FreeBSD ports）已令维护吃紧，社区正在寻求更好的项目管理方式。（BSDTalk EP83，[395.06-466.72]，L1）
- 受访者透露 DragonFly BSD 于访谈前约一年决定采用 pkgsrc 作为主要包管理系统；其直接契机之一是 DragonFly 开发者 Joerg Sonnenberger 因兴趣成为 pkgsrc 开发者并与受访者密切协作，pkgsrc 侧的开发投入事实上压过了 DragonFly 原有的包管理团队，促成整体切换。（BSDTalk EP83，[263.4-299.44]，L1）

**史观**：

- 总纲10 动手者创造历史：Sedlacik 自述“处理我缺陷报告的人终于受够了我而邀请我成为开发者”，其身份由持续的实际修补工作而非学历或任命换来，是动手者以贡献换取历史位置的一手例证。（BSDTalk EP100，[578.68-591.88]，L1）
- 总纲8 本体论上各方平等：pkgsrcCon 把 NetBSD、FreeBSD、OpenBSD 乃至 OpenSolaris 与 Linux 阵营的开发者聚于同一屋檐下交流打包与工程经验，各分支在此平等互鉴而非论资排辈，构成分离阵营之间的聚合节点。（BSDTalk EP100，[268.88-284.2]，L1）
- 总纲10 动手者创造历史：Cort 的全部历史叙述由具体动手构成——写驱动、修内核、上游化补丁、更新 man 页——从 Summer of Code 学生到 NetBSD 开发者的身份亦由代码贡献换取；微内核的优劣判断同样出自写驱动者亲手停掉崩溃驱动、修复重编译再启动的一手体验，而非 Tanenbaum 与 Torvalds 式的理论论战。（BSDTalk EP232，[282.47-307.48]，L1）
- 总纲5 没有必然性，只有偶然性：当事人将微内核与宏内核的经典教条之争化为具体负载下的情境权衡：性能损失约一成到一成五，是否可接受取决于系统能否宕机、跑的是什么负载；不存在普遍更优的内核形态，架构选择的正当性由偶然的使用场景决定。（BSDTalk EP232，[376.42-398.94]，L1）
- 总纲9 经验优先：受访者对操作系统的全部判断均出自自身一线运维经验而非厂商话语：稳定性以“安装后不必再管”为标准，包管理以能否自定义构建为标准，界面以屏幕阅读器实际朗读效果为标准；这种以动手者经验为检验尺度的立场，正是基础设施工具史应当优先采信的经验优先路径。（BSDTalk EP63，[657.82-716.82]，L1）
- 总纲10 动手者创造历史：本期受访的视障管理员属于技术史上最不被书写的一类人群：约 70 台服务器的托管业务依赖其个人工作流维系，其自动化、审计与可及性实践是互联网基础设施得以运转的微观机制；记录此类默默做事者的口述，即为动手者创造历史命题在无障碍与运维交叠领域提供了具体载体。（BSDTalk EP63，[103.8-119.46]，L1）
- 总纲5 没有必然性，只有偶然性：受访者进入 NetBSD 社区的路径充满偶然：大学时期在实验室使用 Solaris 工作站，返家后仅有 Macintosh LC Ⅲ（约 16MHz、32MB 内存）可用，彼时 Linux 内核刚至 1.0 且尚无 Macintosh 移植；他经 Gopher 检索先试用 Tenon 的 MacMint（Mint OS 的 Macintosh 应用化移植），因功能受限转而发现支持 Mac 68k 的 NetBSD 移植并自此定居于此。技术归属由设备条件与检索路径等偶然条件促成，而非理性选型的必然结果。（BSDTalk EP83，[565.1-657.16]，L1）

**辨析**：
