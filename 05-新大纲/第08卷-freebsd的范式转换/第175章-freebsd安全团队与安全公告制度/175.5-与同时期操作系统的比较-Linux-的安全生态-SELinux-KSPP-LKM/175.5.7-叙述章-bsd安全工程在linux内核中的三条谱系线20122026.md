# 175.5.7 叙述章——BSD 安全工程在 Linux 内核中的三条谱系线（2012–2026）

2012 年 1 月 FreeBSD 9.0 发布，同期合入的对象能力框架 Capsicum 从剑桥大学 David Chisnall 与 Robert Watson 的合作项目中走出实验室，成为此后十四年 Linux 内核讨论中最常被引用的 BSD 安全设计参照物，Paulo Bonzini 在 2014 年 linux-api 邮件列表提出 "Adding FreeBSD Capsicum security framework" RFC v2 时直接把该框架作为整体移植对象，Eric Biederman 反驳 Capsicum 与 POSIX.1e 能力不同必须每处 fget/fdget/user_path_at 都加能力标注、约 100 处修改点，Bonizni 则把方案改造成按 file descriptor 而非 struct file 关联 seccomp-bpf 过滤器，把 FreeBSD 的能力模型翻译成 eBPF 语义；这条线最终没有以完整移植落地，却在 2014 年 6 月 David Drysdale 提交的 O_BENEATH 补丁中被显式承认出身——"was originally implemented as part of the internals of the Capsicum security framework, which is available in FreeBSD 10.x"，Kees Cook 2016 年补充 "Capsicum is a security framework that has been present in FreeBSD since version 9.0 (Jan 2012)" 并解释能力模式下 /proc 不可访问才导致 fexecve3 无法工作、execveat 因此是"实现 Capsicum 所需的一小部分"，Andy Lutomirski 在 v4 系列继续援引此说明，Christoph Hellwig 与 David Drysdale 各自补证这一动机链，Capsicum 的完整移植失败但语义碎片经 Drysdale 之手进入 openat 与 execve 两条接口线

第二条线从 Landlock 展开，Mickaël Salaün 2016 年 8 月提交 LSM RFC v2 时把目标写作 "to allow any process, including unprivileged ones, to create powerful security sandboxes comparable to the Seatbelt/XNU Sandbox or the OpenBSD Pledge"，此后 v3、v4、v8、v12、v14、v15、v19、v20、v21、v22、v23、v24、v25、v26、v30、v31、v32、v33 每一次重投都在 cover letter 里保留 "Landlock also takes inspiration from other OS sandbox mechanisms: XNU Sandbox, FreeBSD Capsicum or OpenBSD Pledge/Unveil" 一句，Salaün 与 Pavel Machek 在 v2/v3 讨论中反复回到"非特权进程自沙箱化"这一目标，Kees Cook 与 Alexei Starovoitov 把 seccomp 扩展为 eBPF 视为 Capsicum 指针追踪的等价路径，Landlock 十五轮补丁在 2020 年 9 月合入 Linux 内核主线，此线把 FreeBSD 9.0 的能力框架与 OpenBSD pledge(2)/unveil(2) 共同折算为 Linux LSM 的一个可堆叠模块，是 BSD 派系沙箱概念在 Linux 中最彻底的一次内化

第三条线由 MAP_STACK 引出，2019 年 11 月 Jann Horn 在 clone3 文档评审中转述 "on OpenBSD, they do use MAP_STACK now AFAIK" 与 "they periodically check whether the userspace stack pointer points into a MAP_STACK region, and if not, they kill the process"，Theodore Ts'o 由此发问 Linux 是否应照做即使只在系统调用入口检查成本也低，Kees Cook 明确反对只此一处不足以防 ROP、认为取得系统调用能力后即可把 ROP 栈搬到合法栈上，但承认 MAP_STACK 仍具"你的进程行为异常"的声明与强制价值；2023 年 4 月 20 日 Andrew Morton 在 MAP_STACK 到 VM_STACK 映射讨论中引 mmap(2) 手册明言 "MAP_STACK exists (and has an effect) on some of the BSDs"，2024 年 5 月 14 日 Linus Torvalds 在 buffered IO 的 LSF/MM/BPF TOPIC 讨论中重复此语并承认 BSD 家族系统行为差异是显式事实，2024 年 2 月 Theo de Raadt 在 mseal 线程中点明机制差异 "In OpenBSD, sigaltstack() forces MAP_STACK onto the specified (pre-allocated) region, because on kernel-entry we require the sp register to point to a MAP_STACK region"，随即补一句 "Linux does not have MAP_STACK enforcement (yet)"，Jeff Xu 引 Theo 视角说明 sigaltstack 可能构成 mseal 绕过路径，Waiman Long 提议把 MAP_STACK 映射为 VM_STACK 防止栈 VMA 与非栈匿名 VMA 合并、指出 glibc 用 MAP_STACK 而 Linux 完全忽略该标志触发 SELinux 禁止可执行栈的检查失败并造成随机 SEGV，2024 年 10 月 Pedro Falcato 评 mseal 时写 "I think this version of mseal() is OpenBSD's mimmutable()"，2026 年 6 月 Li Chen 在进程孵化模板 RFC 中横向调研三家并记 "FreeBSD has P_INEXEC, OpenBSD has PS_INEXEC"、Linux 至今无等价标志，这条线证明 OpenBSD 的 MAP_STACK 强制语义在 Linux 侧被反复作为设计基准、兼容性提示与待补齐项

同期还有若干散点级证据：Alexsa Sarai 2019 年 10 月提交 openat2 系列明言该系列复活 Al Viro 的 AT_NO_JUMPS、其语义源自 David Drysdale 的 O_BENEATH，"RESOLVE_BENEATH 的语义建模于 FreeBSD 的 O_BENEATH"，Ameer Hamza 提交 O_EMPTY_PATH 时说明"it is very similar to the FreeBSD O_EMPTY_PATH flag"、动机是避免为 samba 容器授予 /proc 访问权限；David Miller 在 GTSM 线程称 "This is already implemented the same way in BSD kernels"、在随机临时端口讨论中称 OpenBSD 已实现的随机化"we could easily implement as well"、并以 "The existing LSM hooks do not break BSD socket behavior" 守护 BSD 套接字兼容性契约，Yoshifuji 论证 IPv6 扩展头默认禁止时称 "FreeBSD does this in the same way"，Hallyn 在网络命名空间争论中反问 "we can all use the network part of the bsdjail lsm"，Eric Dumazet 在 GTSM 补丁中说明该机制的实现方式在 BSD 内核中早已存在同样实现，David S. Miller 在 XDP 示例讨论中评 bzero 用法时笑称 "It looks like you write OpenBSD security code"、并指出只有 BSD 派系用 bzero

反向判例与遗留同时存在，2022 年 7 月 Linus Torvalds 批评 "the traditionally horribly broken BSD model of do SCSI ioctl's using read/write calls was a complete disaster"，Jeff Layton 2025 年提交 Linux fsdevel 补丁由 Christian Brauner 合入 vfs-7.0.misc 分支理由是即便该接口需要特权也隐患众多、已有 eBPF 等更佳替代、原文"begin the deprecation of legacy BSD process accounting"，Peter Anvin 反对 CONFIG_STRICT_DEVMEM 做成运行时开关并援引 BSD securelevel 单向提权的思路作为对照、说明即便照搬该设计也需重新论证其合理性、"kind of like the BSD securelevel idea"，David Mosberger 与 Arnd Bergmann 在 BSD accounting format 跨架构测试串中贴出 s390、ia64 上 uname -a 输出与 struct acct 各 ac_ 字段偏移的三版本对照表，Doug Gilbert 在 SG_IO 命令白名单 CVE-2011-4127 争论中说明 ddpt 工具已移植到 FreeBSD 和 Win32、把 FreeBSD 列为该工具链的跨平台移植目标之一，Theodore Ts'o 在 SG_IO 白名单 CVE-2012-4542 的漫长往返中提到有 CD 刻录工具开发者想在 BSD、Solaris 与 Windows 虚拟机内测试、与既有诉求一致，unix.7 手册 CVE-1999-1402 记录连接 UNIX domain socket 需读/写权限但 Solaris 2.x、SunOS 4.x 与 4.4 之前的 BSD-based 系统会忽略这些访问权限、可移植程序不应据此做安全判断，2006 年 Alexey Dobriyan 的 inode 瘦身补丁则给出这条谱系最早的删除节点"[BSD security levels are deleted in -mm, assuming this below]"与 "The only user of i_security, f_security, s_security fields is SELinux, so ifdef them with CONFIG_SECURITY_SELINUX"、同期 Crispin Cowan 在 AppArmor FAQ 争论中列出 TRON、Janus、LIDS、Systrace、BSD Jail、EROS、PSOS、KeyOS、AS400 等非标签式约束方案、Stephen Smalley 反驳传统意义的 confinement 指信息流控制、AppArmor 并不提供、2010 年 7 月 David P. Quigley 在 NFSD MAC Labeling 补丁中要求 "if we have an SELinux box with an MLS policy and a FreeBSD box with their MLS MAC module" 互通、2010 年 10 月 26 日 James Morris 在 IMA 补丁争论中以 BSD secure levels 已被移除为例反驳 Al Viro 对 security/ 子树的贬斥

合观而言，BSD 安全工程在 Linux 内核中留下三条清晰谱系：一条是自 FreeBSD 9.0 起经 Capsicum 到 execveat 与 openat2 的能力语义流、Bonizni 与 Drysdale 是两条主要桥梁、语义落地但完整框架被放弃；一条是自 OpenBSD Pledge 与 Landlock 到 2020 年合入主线的非特权沙箱流、Salaün 把 pledge(2) 的减法哲学翻译成 Linux LSM 的可堆叠加法语义；一条是自 OpenBSD MAP_STACK 强制语义到 mseal 与进程孵化标志位的强制语义流、Horn、Ts'o、Morton、Linus、de Raadt、Falcato、Li Chen 各自在不同年份反复援引 BSD 侧行为作为设计基准或待补齐项；同时反向判例与遗留并存，acct(2) 与 fs_pin、SG_IO 与 SCSI ioctl、UNIX socket 权限与 CVE-1999-1402、BSD secure levels 与 STRICT_DEVMEM 各自以不同形式留在 Linux 内核治理视野中，BSD 派系安全工程因此在 Linux 中同时是设计基准、反面教材、兼容性契约与待删遗留、四种角色共存于同一内核谱系
