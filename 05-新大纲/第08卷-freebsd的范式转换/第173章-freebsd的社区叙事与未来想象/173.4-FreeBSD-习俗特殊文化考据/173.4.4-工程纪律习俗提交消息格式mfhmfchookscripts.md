# 173.4.4 工程纪律习俗：提交消息格式、MFH、MFC、hook scripts

**要点**：FreeBSD 提交消息须遵循结构化字段（Reviewed by 评审者、Approved by 批准者 mentoring 期必需、Obtained from 外部来源代码、Sponsored by 赞助方、Differential Revision Phabricator 评审编号、MFC after 合并至 STABLE 等待时间），《Committer's Guide》第 9 节 “Commit Log Messages” 自 1999 年文档建立即规范；FreeBSD ports 季度分支机制（YYYYQn 命名，如 2024Q3、2025Q2）建立后即形成 MFH（Merge From Head）提交消息约定，季度分支命名自 2014 年起标准化；FreeBSD MFC（Merge From Current）传统自 4.x 时代确立，从 -CURRENT（main）合并至 -STABLE 分支，通常需经 MFC after 等待期（如 2 周）以观察回归；FreeBSD 从 Subversion 迁移至 Git（2020-2021）后强化 Git hook 文化，Committer's Guide 第 5.2.2 节说明 repo.freebsd.org 的 commit hook 检查 “Commit” 字段与 committer 的 FreeBSD.org 信息一致性；工程纪律习俗将 “可追溯性” “分支稳定性” “政策代码化” 三种工程取向制度化

**史料**：FreeBSD Committer's Guide 第 9 节 “Commit Log Messages”（<https://docs.freebsd.org/en/articles/committers-guide/#commit-log-message>）；FreeBSD Committer's Guide 第 16 节 “Phabricator”（<https://docs.freebsd.org/en/articles/committers-guide/#phabricator>）；FreeBSD Committer's Guide 第 7 节 “Setup, Conventions, and Traditions”（<https://docs.freebsd.org/en/articles/committers-guide/#conventions>，含分支与 MFC 约定）；FreeBSD Committer's Guide 第 5.2.2 节 “Getting Started for Developers”（<https://docs.freebsd.org/en/articles/committers-guide/#git-primer>，"The commit hook in repo.freebsd.org checks the ‘Commit’ field matches the committer's information in FreeBSD.org "）；FreeBSD Ports 季度分支（<https://cgit.freebsd.org/ports/tree?h=2024Q3>，访问 2026-07-27）；DragonFly BSD DPorts 引用（<https://www.dragonflybsd.org/docs/howtos/DPortsUsage/>，访问 2026-07-27，" DPorts last release is based on FreeBSD ports branch 2024Q3 "）；FreeBSD Release Engineering（<https://docs.freebsd.org/en/articles/freebsd-releng/>，Copyright © 2002-2022 The FreeBSD Documentation Project，第 3 节 “ Release Engineering Terminology ” 定义 “ code slush ”、“ code freeze ” 等术语）；freefall.FreeBSD.org 上 **/usr/local/bin/gen-gitconfig.sh** 脚本 ［A］

**史观**：总纲第 9 条——经验优先，FreeBSD 提交消息格式的结构化字段是工程实践中积累的经验沉淀，每个字段都对应明确的工程责任与历史可追溯性，而非预先设计的理论框架；总纲第 17 条——证明世界先于解释和改造世界，MFC after 等待期与 ports 季度分支的工程实践是 “先证明工程稳定性，再合并至稳定分支” 的具体显现；总纲第 13 条——法律与道德是利益分配，“Obtained from” 字段为 BSD 跨项目代码引用独有，将代码来源合规性转化为提交消息中的利益分配显性化；总纲第 7 条——理论必须自反，本子节作为 FreeBSD 工程纪律习俗的考据叙事，自身亦嵌入 “结构化纪律即工程效率” 的前理解，须自觉呈现这一前理解；总纲第 22 条——知识注定过时，FreeBSD 从 Subversion 迁移至 Git（2020-2021）后部分提交消息字段调整，工程纪律习俗随版本控制系统演进而变迁

**辨析**：考据过程留痕——【查证来源】Committer's Guide 第 9 节 “Commit Log Messages” 经 docs.freebsd.org 一手核验，确认结构化字段清单；Phabricator 评审文化经第 16 节核验，2024 年 FreeBSD 迁移至 Bugzilla + Git 工作流后部分调整须以最新文档核验；FreeBSD Ports 季度分支经 cgit.freebsd.org/ports/tree?h = 2024Q3 一手核验；DragonFly BSD DPorts 基于 FreeBSD ports 季度分支经 dragonflybsd.org/docs/howtos/DPortsUsage/ 一手核验；commit hook 检查机制经 Committer‘s Guide 第 5.2.2 节一手核验；【交叉验证方法】提交消息字段须以 Committer’s Guide 与实际 commit log 互证；季度分支机制须以 ports 季度分支 cgit 页面与 <portmgr@FreeBSD.org> 维护记录互证；MFC 须以 Release Engineering 文档与 <re@FreeBSD.org> 维护记录互证；【0 信任原则·季度分支命名标准化时点】“季度分支命名 YYYYQn 格式自 2014 年起标准化” 的考据须以 cgit.freebsd.org/ports/log/ 历史 commit 核验，本考据暂以二手转述为依据；【0 信任原则·Phabricator 迁移影响】2024 年 FreeBSD 迁移至 Bugzilla + Git 工作流后，“Differential Revision” 字段的具体调整须以最新 Committer's Guide 与实际 commit 互证；【0 信任原则·gen-gitconfig.sh 脚本位置】freefall.FreeBSD.org 上 **/usr/local/bin/gen-gitconfig.sh** 脚本的具体功能与权限配置须以集群管理员文档补全；【与同类 UNIX/BSD 习俗对比】Linux 内核提交消息有 “Signed-off-by” 传统（Linus Torvalds 引入，源自 DCO Developer Certificate of Origin）；FreeBSD 的 “Obtained from” 字段为 BSD 跨项目代码引用独有；NetBSD 有 pullup request 机制（向稳定分支拉取修复），2025 AGM 报告显示 releng 团队 “Processed hundreds of pullup requests”；OpenBSD ports 无季度分支机制，采用 -stable 与 -current 双分支；所有大型开源项目均使用 Git hook；FreeBSD 特色是 hook 强制 committer 信息与 Kerberos 账号绑定，集成 OpenPGP 密钥认证；【自反性声明】本子节作为 FreeBSD 工程纪律习俗的考据叙事，自身嵌入 “结构化纪律即工程效率” 的前理解，实际工程纪律的代价（提交开销、流程复杂度）须以多源交叉验证逼近史实
