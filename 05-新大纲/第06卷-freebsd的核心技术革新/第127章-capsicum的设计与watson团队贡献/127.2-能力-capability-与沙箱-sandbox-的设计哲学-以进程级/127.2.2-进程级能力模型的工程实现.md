# 127.2.2 进程级能力模型的工程实现

**要点**：Capsicum 在 FreeBSD 内核中的工程实现包括以下核心组件：(1) **capsicum(4)** 内核框架——在 GENERIC 内核中默认编译（options CAPABILITIES 和 options CAPABILITY_MODE，FreeBSD 9.0 即已加入）；(2) **cap_enter(2)** 系统调用——设置进程的 P_CAPMODE 标志，该标志一旦设置不可清除（单向门），子进程自动继承；(3) 能力文件描述符——在普通文件描述符上附加 cap_rights 权限集合（如 CAP_READ、CAP_WRITE、CAP_SEEK、CAP_MMAP、CAP_IOCTL 等），通过 **cap_rights_limit(2)**、**cap_ioctls_limit(2)**、**cap_fcntls_limit(2)** 系统调用逐步收缩权限；(4) **libcapsicum(3)** 用户态库——提供高层 API 简化沙箱创建（**cap_init(3)**、**cap_service_open(3)**、**cap_wrap(3)** 等），封装 fork+fd passing+cap_enter 的标准流程；(5) **cap_new(3)**——将普通文件描述符包装为能力文件描述符并设置初始权限；(6) casperd 守护进程（**casper(3)**/**casperd(8)**）——为沙箱内进程提供受限系统服务（DNS 解析、随机数、文件打开对话框等），避免进程因需要系统服务而持有过多全局权限

**史料**：FreeBSD 9.0-RELEASE Release Notes（CAPABILITIES/CAPABILITY_MODE 选项记录，commit r219129）；FreeBSD 源码 src/sys/kern/kern_cap.c、src/sys/kern/descrip.c（Capsicum 内核实现）；FreeBSD 源码 src/lib/libcapsicum/（libcapsicum 库）；FreeBSD 源码 src/libexec/casper/（casperd 守护进程）；**capsicum(4)**、**cap_enter(2)**、**cap_rights_limit(2)**、**cap_ioctls_limit(2)**、**libcapsicum(3)**、**casper(3)** 手册页 ［A］

**史观**：总纲第 22 条——开源运动：Capsicum 的工程实现采用了“默认编译但不默认启用应用沙箱”的集成策略——FreeBSD 9.0 将 Capsicum 框架加入 GENERIC 内核但不附带任何 Capsicum 化的应用程序（LWN 2012 报道明确记载"9.0 release only contains the kernel changes required for Capsicum but doesn't ship any applications that use the facility"），从 9.1/10.x 开始逐步将基本系统工具 capsicum 化（tcpdump、dhclient、kdump、killall、hostctl 等）；这一渐进策略是 FreeBSD 工程文化的典型特征

**辨析**：casperd 的引入版本经 **freebsd.duckdb** `commits` 表与 `commit_files` 表交叉验证已确认：casperd 首次合入 FreeBSD-CURRENT 的 commit 为 `42a859525652decb08bba47ffaceb769d394175e`（Pawel Jakub Dawidek，2013-12-02T08:21:28Z，subject: "Please welcome casperd daemon. It (and its services) will be responsible for giving access to functionality that is not available in capability mode sandbox. The functionality can be precisely restricted."）；该 commit 引入了 `libexec/casper/` 目录及 dns、grp、pwd、random、sysctl 等服务模块；同日 Dawidek 补加 `lib/libcasper/` 目录（commit `05af64096c3cad1331108f5be2f4662555653de3`，2013-12-02T10:18:25Z，subject: “Forgot to ‘svn add’ lib/libcasper/ directory.”）；由于此合入发生在 FreeBSD 10.0-RELEASE（2014-01-20）发布前约 7 周，casperd 作为独立守护进程随 FreeBSD 10.0 首次正式发布；2013-12-19 commit `f01f7446472b47340fbaddd4d582fa4006df3842`（Dawidek，subject: "Make the world a bit more secure place (hopefully) and turn the casperd on by default."）将 casperd 默认启用；2016-02-25 commit `c501d73c7e2d5c843583084b84bd3e6f68a0047e`（Mariusz Zaborski）将 casperd 从独立守护进程架构重构为 libcasper 库架构（cap_init(3) 时 Casper 从原进程 fork 而非连接外部 daemon），同时移除 libcapsicum 库——因此 “casperd 作为独立守护进程” 的存在时期为 FreeBSD 10.0（2014-01）至 11.0（2016-10）之间；FreeBSD 基本系统中 capsicum 化工具的完整清单随版本演进变化，**tcpdump(1)** 是最常被引用的案例——仅需约两行代码即可在 BPF 设置完成后进入能力模式，但 DNS 解析需要 casper 的 DNS 服务支持；最初 tcpdump Capsicum 改造因 glibc/libc 解析器需要访问 **/etc/resolv.conf** 和网络命名空间导致功能受限，后通过 casper 的 libcasper_dns 服务解决
