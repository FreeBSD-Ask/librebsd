## 112.12.1 Torvalds 对 ZFS 的全面否定

**要点**：林纳斯·托瓦兹于 2020 年 1 月 6 日在 Real World Tech 论坛（realworldtech.com）讨论中回应用户关于 Linux 内核变更破坏 ZFS 兼容性的抱怨时，发表了对 ZFS 的强硬批评，原话为 "Don‘t use ZFS. It’s that simple. It was always more of a buzzword than anything else, I feel, and the licensing issues just make it a non-starter for me"；该帖被广泛报道但常被断章取义——Torvalds 的核心论点包括：（1）ZFS 的许可证问题使其无法合入 Linux 主干；（2）他个人对 ZFS 的技术价值持怀疑态度（称其更多是 “buzzword”）；（3）Linux 内核不会为 ZFS 等 out-of-tree 模块保持稳定 API/ABI；Torvalds 先前在 2016 年 ZFsonLinux 进入 Ubuntu 话题中也表示过 “我不是律师，但 ZFS 许可证问题很严重” 的立场，但 2020 年 1 月的发言更为强硬

**史观**：总纲第 6 条——技术路线分化：Torvalds 对 ZFS 的批评不仅是技术评价，更是 Linux 社区治理哲学的体现——Linux 坚持 “only upstream code matters”，out-of-tree 模块不被官方支持，而 ZFS 由于 CDDL 许可永远无法进入 upstream；这一立场与 BSD 社区对待 ZFS 的欢迎态度形成鲜明对比

**辨析**：Torvalds 言论需还原到具体语境：（1）他是在回应 “内核变更破坏了 ZFS” 的抱怨——他的核心论点是 “内核不为 out-of-tree 模块保证兼容性”，ZFS 只是例子之一；（2）“buzzword” 评价是个人技术判断，不是社区共识；（3）Torvalds 并未说 ZFS 技术上不好，而是说许可问题使其在 Linux 上 “non-starter”；Greg Kroah-Hartman（Linux 稳定版维护者）曾更明确表示 “使用 ZFS 的人需要自己承担风险，因为 Linux 内核社区不会维护 ZFS 代码”

## 112.12.2 Linux 内核模块接口政策分析

**要点**：Linux 内核长期政策是不维护稳定的内核内部 API/ABI——内核模块必须随内核版本更新，out-of-tree 模块（即不在 Linux 内核源码树中的模块）由其作者自行维护，内核开发者不为 out-of-tree 模块破坏兼容性负责；这一政策的官方表述参见 Linux 内核文档 Documentation/process/stable-api-nonsense.rst（由 Greg Kroah-Hartman 撰写）；ZFS on Linux（ZoL）/OpenZFS 作为 out-of-tree 模块，始终面临内核 API 变更导致的编译失败风险——每次 Linux 内核大版本更新都可能需要 OpenZFS 开发者适配；Linux 内核的 GPL-only 符号（EXPORT_SYMBOL_GPL）机制进一步限制了非 GPL 模块可用的内核功能

**史料**：Linux 内核源码 Documentation/process/stable-api-nonsense.rst；Linux 内核源码 MODULE_LICENSE 宏定义与 EXPORT_SYMBOL_GPL 机制；LKML 历史讨论 ［A］
    FreeBSD 社区论文：[FP-2024-003] Benchmarking Performance Overhead of DTrace on FreeBSD and eBPF on Linux（Mateusz Piotrowski，2024）<https://papers.freebsd.org/2024/asiabsdcon/piotrowski-benchmarking-performance-overhead-of-dtrace-on-freebsd-and-ebpf-on-linux/>
    FreeBSD 社区论文：[FP-2019-067] Migrating a Big Data Cluster from Linux to FreeBSD（Benedict Reuschling，2019）<https://papers.freebsd.org/2019/fosdem/reuschling-big_data_cluster/>

**史观**：总纲第 22 条——开源运动：Linux 的 “no stable in-kernel API” 政策是开源治理模式的体现——内核社区认为维护稳定 API 会阻碍技术进步，out-of-tree 模块应该进入 upstream；但 ZFS 因 CDDL 许可无法进入 upstream，这形成了一个结构性困境

**辨析**：Torvalds 2020 年言论的真正触发点是有用户抱怨内核变更破坏了 ZFS——Torvalds 的回应核心是 “我们不为 out-of-tree 模块保证任何东西”，这是他长期一贯的立场，并非针对 ZFS 个人恩怨；相比之下，FreeBSD 内核也不承诺 KPI（Kernel Programming Interface）绝对稳定，但 FreeBSD 将 ZFS 纳入 base system 后，ZFS 由 FreeBSD committer 维护，与内核同步更新，不存在 out-of-tree 问题

## 112.12.3 ZFS 批评话语的权力结构辨析

**要点**：ZFS 相关批评话语存在多重权力结构：（1）Linux 内核领袖（Torvalds、Kroah-Hartman）从 “upstream 优先” 立场否定 out-of-tree ZFS；（2）FSF 从 “自由软件纯洁性” 立场批评 CDDL 与 GPL 不兼容（2005 年 12 月声明）；（3）部分 Linux 发行版（如 Red Hat）从企业支持角度选择不支持 ZFS（转而支持 Btrfs/Stratis）；（4）部分性能批评者认为 ZFS 内存需求过高、不适合小内存系统；这些批评背后不仅有技术判断，更有生态竞争（Linux 自有 CoW 文件系统 Btrfs 与 ZFS 存在功能重叠）、许可哲学分歧（copyleft vs permissive/file-level copyleft）、社区治理模式差异（upstream 集中式 vs 跨平台分散式）等多重因素；FreeBSD 社区对这些批评的回应主要是实际行动——持续改进 ZFS 集成、证明其在生产环境中的稳定性

**史料**：FSF 2005 年 12 月 CDDL 不兼容声明；Torvalds 2016/2020 年关于 ZFS 的发言；Red Hat 关于 RHEL 不支持 ZFS 的官方声明；Btrfs 项目文档［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］ 〔L3 官方文档；L4 事后叙述〕

**史观**：总纲第 3 条——形式主义膨胀：ZFS 的争议不仅是技术优劣之争，更是 “什么构成合法开源” 这一形式化问题的具体化——CDDL 是否 “真正自由”、out-of-tree 模块是否 “一等公民”，这些问题都由许可证条款、社区规则等形式化结构决定

**辨析**：需区分不同批评的性质：Torvalds 的批评主要是治理立场（不为 out-of-tree 破坏内核负责）和个人技术判断；FSF 的批评是自由软件意识形态立场（CDDL 与 GPL 不兼容使其无法成为 GPL 生态的一部分）；Red Hat 的不支持是商业和法律风险规避决策；不应将这些不同性质的批评混为一谈

## 112.12.4 Torvalds 言论的一手史料考证

**要点**：关于 Torvalds 2020 年 1 月 6 日 RealWorldTech 帖子的一手史料考证：（1）原帖位置：论坛主题讨论 “Spectre/Meltdown Fixes” 下的回复，讨论中一名用户抱怨内核 API 变更导致 ZFS 等 out-of-tree 模块无法工作，Torvalds 在该 thread 中回复；（2）精确时间：2020 年 1 月 6 日（UTC 时间）；（3）精确引语："Don‘t use ZFS.
