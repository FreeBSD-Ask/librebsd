# 121.2 GEOM 模块化存储框架——Poul-Henning Kamp（波尔-亨宁·坎普） 设计的块设备变换栈（FreeBSD 5.0）

## 121.2.1 phk 的 GEOM 设计哲学与 class 体系

**要点**：GEOM 由 Poul-Henning Kamp（phk）设计，在 DARPA/SPAWAR 合同 N66001-01-C-8035（“CBOSS”）资助下作为 DARPA CHATS 研究项目的一部分开发，随 FreeBSD 5.0（2003 年 1 月）正式引入；GEOM 是一个模块化的块设备变换框架，设计灵感部分来自 Netgraph（网络栈模块化框架）但面向存储，核心抽象为 provider（提供者，即输出块设备）、consumer（消费者，即使用下层 provider 的 GEOM 模块）、geom（模块实例）三者构成的有向无环图；用户可通过堆叠 GEOM class 实现复杂存储拓扑，例如先对两个磁盘做 **gmirror(8)** 镜像，再在镜像设备上做 **geli(8)** 加密，最后在加密设备上创建 UFS 文件系统；GEOM 名称源自 “disk geometry”，象征其对磁盘几何结构的掌控

**史料**：phk 2004 BSDCan “GEOM tutorial” 幻灯片（phk.freebsd.dk/pubs/bsdcan-04.slides.geomtut.pdf）；FreeBSD Handbook “GEOM: Modular Disk Transformation Framework” 章节；FreeBSD 5.0-RELEASE Release Notes GEOM 章节；GEOM(4) 手册页；phk 在 freebsd-arch@ 邮件列表 2002 年的 GEOM 设计提案 ［A］

**史观**：边缘者贡献：GEOM 是 phk 一个人对着 FreeBSD 旧存储层发呆时的产物——在 GEOM 之前，FreeBSD 的存储变换（ccd、vinum、磁盘加密）各自独立实现，没有统一框架；phk 作为 FreeBSD 最具个人风格的核心开发者，用一个统一框架取代了所有零散实现，这种 “个人洞察重塑系统架构” 的模式在 BSD 历史上反复出现

**辨析**：GEOM 不是 “FreeBSD 的 LVM” 或 “FreeBSD 的 Device Mapper”——LVM/Device Mapper 主要面向逻辑卷管理，而 GEOM 是更通用的块设备变换框架，RAID、加密、分区、标签、压缩、挂载验证等都是其模块；GEOM 设计受 DARPA 资助这一事实常被忽略——这说明 BSD 的很多基础架构改进并非纯粹业余爱好，也有政府安全研究项目的资金支持；与 Netgraph 类似但有一个关键差异：GEOM 保证 I/O 请求按顺序完成，不支持乱序完成（Netgraph 网络包可乱序），这是存储栈与网络栈的本质区别

**文献**：Kamp, P.-H. (2004). *GEOM Tutorial*. BSDCan 2004 Slides, phk.freebsd.dk/pubs/bsdcan-04.slides.geomtut.pdf; Rhodes, T. *GEOM: Modular Disk Transformation Framework*. FreeBSD Handbook; FreeBSD Project. **GEOM(4)**, **geom(8)** Manual Pages; Kamp, P.-H. (2002). *GEOM Architecture Proposal*. freebsd-arch@ Mailing List Archives. ［A］

## 121.2.2 核心 GEOM 模块的功能与引入时间线

**要点**：GEOM 标准模块可分为几类：RAID 类包括 **gmirror(8)**（RAID1 镜像，FreeBSD 5.x 引入）、**gstripe(8)**（RAID0 条带）、**graid3(8)**（RAID3 专用奇偶校验）、**gconcat(8)**（JBOD 磁盘串联）、**graid(8)**（BIOS/固件软 RAID 支持）；加密类包括 **gbde(8)**（phk 设计的 GBDE，FreeBSD 5.0 引入，四道加密屏障）、**geli(8)**（Pawel Dawidek 设计，FreeBSD 6.0 引入，支持 HMAC 认证加密，推荐使用）、**gshsec(8)**（共享密钥加密）；分区与标签类包括 **gpart(8)**（GPT/MBR/APM/VTOC8/BSD disklabel 分区，FreeBSD 7.x 引入，替代老的 fdisk/bsdlabel）、**glabel(8)**（文件系统标签与 UFS ID 标签）；工具与调试类包括 **gnop(8)**（透明透传，用于调试和测试）、**gzero(8)**（零设备，写丢弃读返回零）、**geom_nop(4)** 等；虚拟设备类包括 **md(4)**/**mdconfig(8)**（内存盘与 vnode 盘，FreeBSD 5.0 前已存在但通过 GEOM 重构）、**ggate(8)**（用户态 GEOM 网关，允许用户态程序导出块设备）、**geom_virstor(8)**（虚拟大小超限，即精简置备）、**geom_mountver(8)**（挂载验证，防止脏设备挂载）、**geom_multipath(8)**（多路径 I/O）

## 121.2.3 GBDE 与 GELI：两种磁盘加密方案的对比

**要点**：GBDE（GEOM Based Disk Encryption）由 phk 本人设计，随 FreeBSD 5.0 引入，采用四道加密屏障设计：每扇区使用不同密钥、主密钥用用户口令加密、密钥材料分散存储于磁盘各处、使用 MD5 作为关键派生函数；GELI 由 Paweł Jakub Dawidek 设计，随 FreeBSD 6.0（2005 年 11 月）正式引入，设计目标是成为比 GBDE 更实用、更标准的加密方案：支持 FreeBSD 内核加密框架（可硬件加速）、支持 AES/Blowfish/Triple DES/Camellia 算法、支持 HMAC-MD5/SHA1/SHA256/RIPEMD160 数据认证与完整性校验、支持每扇区初始向量（IV）多种模式、支持最多两个密钥（用户密钥 + 公司密钥）、支持一次性密钥挂载、口令通过 PKCS#5 PBKDF2 强化；GELI 还支持数据认证（authentication），可检测到密文被篡改，这是 GBDE 不具备的功能；FreeBSD 社区推荐使用 GELI 而非 GBDE，尽管 GBDE 仍随系统发布。GBDE 与 GELI 关键维度对比见下表。

| 维度 | **gbde(8)** | **geli(8)** |
| --- | --- | --- |
| 设计者 | Poul-Henning Kamp（phk） | Paweł Jakub Dawidek |
| FreeBSD 引入版本 | FreeBSD 5.0（2003.01） | FreeBSD 6.0（2005.11） |
| 设计哲学 | 四道加密屏障（每扇区不同密钥、主密钥口令加密、密钥材料分散存储、MD5 KDF） | 工业界标准方案（兼容 OpenSSL/libcrypto、PKCS#5 PBKDF2） |
| 支持算法 | 较少 | AES、Blowfish、Triple DES、Camellia |
| 密钥派生函数 | MD5 | PKCS#5 PBKDF2 |
| 数据认证（防篡改） | 不支持 | 支持（HMAC-MD5/SHA1/SHA256/RIPEMD160） |
| 硬件加速 | 不支持 | 通过 **opencrypto(9)** 框架支持 |
| 多密钥支持 | 不支持 | 支持最多两个密钥（用户密钥 + 公司密钥） |
| 一次性密钥挂载 | 不支持 | 支持 |
| 内核加密框架集成 | 不集成 | 集成 |
| 社区推荐 | 不推荐（仍随系统发布） | 推荐 |
| 设计目标 | 密钥泄露时也难以解密特定扇区 | 标准化、易用性、完整性认证 |

**史料**：**gbde(8)** 与 **geli(8)** 手册页；Dawidek 2005-2006 年 freebsd-current@ 邮件列表 geli 设计讨论；Dawidek 2006 年 6 月提交的 “data authentication for geli” commit；FreeBSD Handbook “Encrypting Disk Partitions” 章节 ［A］

**史观**：总纲第 6 条——技术路线分化：GBDE 与 GELI 的分化是 FreeBSD 内部 “phk 个人设计 vs 社区标准方案” 分化的缩影——phk 设计的 GBDE 有独特的安全哲学但使用复杂度高，Dawidek 设计的 GELI 更符合工业界标准（兼容 OpenSSL/libcrypto、支持标准算法和认证模式）；最终社区选择了更务实的 GELI，这说明即使在 FreeBSD 这样个人风格鲜明的项目中，标准化和易用性仍会胜出

**辨析**：一个常见误解是 “GELI 比 GBDE 更安全”——两者安全模型不同，不能简单说谁更安全：GBDE 的设计目标是在密钥泄露时也难以解密特定扇区（四道屏障），但不提供完整性保护；GELI 提供完整性认证（防篡改），但密钥派生更标准；另一个误解是 “GELI 随 FreeBSD 5.0 引入”——实际上 Dawidek 在 FreeBSD 6.0 周期才完成 geli 的开发和集成，FreeBSD 5.x 使用 GBDE 作为唯一的 GEOM 加密方案

**文献**：FreeBSD Project. **geli(8)**, **gbde(8)** Manual Pages; Dawidek, P. J. (2005). *GELI Design*. freebsd-current@ Mailing List Archives; Green, L. *Encrypting Disk Partitions*. FreeBSD Handbook; FreeBSD Project. *Data authentication for geli(8) Commit* (2006-06-08). svn.freebsd.org. ［A］

## 121.2.4 GEOM 架构的史料辨析与设计权衡

**要点**：GEOM 引入 FreeBSD 的精确时间为 FreeBSD 5.0（2003 年 1 月），但开发工作从 2001-2002 年即已开始，在 FreeBSD 5.0-CURRENT 分支中逐步替换旧存储层；GEOM 与 Linux Device Mapper（2002 年 Red Hat 主导开发，随 Linux 2.6 引入）是同时代产物，但设计哲学存在关键差异：GEOM 是纯内核态框架，用户态工具（**geom(8)** 命令）仅用于配置，所有 I/O 路径在内核完成；Device Mapper 同样是内核态，但用户态配置工具（dmsetup、LVM2、cryptsetup 等）生态更丰富；GEOM 的拓扑发现是自动的，模块堆叠通过 provider/consumer 关系自动构成有向无环图；Device Mapper 的 target 类型由用户态明确指定；GEOM 模块开发相对简单但功能受限，Device Mapper target 开发更复杂但灵活性更高；截至 2025 年，GEOM 仍是 FreeBSD 唯一的块设备变换框架，Linux 的 Device Mapper 与 MD（软 RAID）、Bcache、Btrfs 内置 RAID 等并存形成更复杂生态

**史料**：phk 2004 BSDCan GEOM 教程与 Linux Device Mapper 文档对比；FreeBSD src/sys/geom/ 与 Linux drivers/md/ 源码结构对比；Lucas 2018《FreeBSD Mastery: Storage Essentials》；Linux kernel documentation Device Mapper 章节 ［A］

**史观**：总纲第 3 条——形式主义膨胀：GEOM 的 provider/consumer 拓扑模型是形式主义在存储架构中的体现——它将所有存储变换统一为 “输入块设备 → 变换 → 输出块设备” 的纯函数模型，不允许副作用（如网络包那样的乱序），这种形式化使得自动拓扑管理、自动发现、自动配置成为可能，但也限制了某些需要灵活 I/O 排序的功能

**辨析**：需纠正一个关于 GEOM 设计来源的说法：“GEOM 是 Netgraph 移植到存储”——phk 本人多次表示 GEOM 受 Netgraph 启发，但存储与网络有本质差异：存储 I/O 必须按请求顺序完成（生物序等价性），网络包可乱序、复制、丢弃，因此 GEOM 的实现与 Netgraph 完全独立；GEOM 是否 “未完成”——**geom_sched(8)**（I/O 调度器）模块长期处于实验状态，从未正式完善，这是因为现代 SSD 和 NVMe 设备的 I/O 调度主要由设备自身固件完成，内核 I/O 调度的价值下降，这不是 GEOM 架构的缺陷而是存储硬件演进的结果

**辨析**：

- 转写对 G-Union 的机制描述基于播客口述，其与 GEOM 层的准确语义及合并时间需与 FreeBSD 源码与提交记录核对。 [考据脚注] G-Union 的引入版本与实现细节需查 FreeBSD 源码树与 commit 记录。（BSD Now EP461，[466.18-543.7]，L4）
- 主持人在访谈中提出的生态缺口：PC-BSD 使用 GRUB 引导，而 GRUB 无法自动加载模块依赖，只能在 grub.cfg 中预先逐一列全，且彼时缺乏可直接列出某模块依赖树的用户态工具——KLDXRef 虽可能有读取 linker.hints 的模式但状态不明；这一问答从使用者视角映照出自动加载工程尚未覆盖引导链的现实。（BSD Now EP109，[928.86-948.60]，L2）
- GEOM 在内存耗尽时的回退机制构成一个由改进放大旧缺陷的案例：既有实现以分配失败计数触发退避，将系统长期压制在每秒 10 次 IOPS；Alexander Motin 的 direct dispatch 改进使并发下发的 I/O 从个位数跃升至数千，失败分配随之放大，病态退避更易触发；Losh 的权宜修复是将病态行为上限抬至每秒 1000 次 IOPS 并改为以失败是否持续为节流条件，而根本方案是预分配 I/O 事务全栈所需内存（编译期静态数组或受限的 UMA 储备池），否则当换出页所需的内存本身无法分配时理论上可构成经典死锁——其 Netflix 服务器有 256 GB 内存故罕见触发。（BSD Now EP109，[1739.60-1993.68]，L1）
- 对比文的定位被主持人辨析为方法论示范：作者声称只列事实、不替读者下结论；主持人补充逐项解读的必要性——FreeBSD 默认关闭项看似更多，但其中不少与具体硬件或使用场景无关（如 SPARC64 相关项），LibreSSL 虽不在 base 却可经 ports 安装，ASLR 等缺口由 HardenedBSD 推进，提醒读者警惕把默认差异直接读成安全优劣。（BSD Now EP68，[899.75-972.29]，L2）
- 多数开发者在 macOS 虚拟机里跑 FreeBSD、不吃自家狗粮的说法被现场辨析为以偏概全：回答者称因人而异，会议上密集出现的 MacBook 多是随身笔记本而非主力开发机，内核开发者用虚拟机是为了崩溃不伤及工作环境，且 pkg 二进制包与 PC-BSD 月度快照正在改变桌面化程度；此说仅有与会者个体见闻支撑，宜存疑对待。 [存疑脚注] 开发者主力系统构成仅有节目参与者个体见闻支撑，无统计来源；转写专名多处失真（如 Henning Brauer 作 Brower、Kirk McKusick 作 McCuse/McKenzie、Poul-Henning Kamp 作 Paul Henning Kamp），语义尚可辨识。（BSD Now EP68，[4993.72-5073.89]，L4）
