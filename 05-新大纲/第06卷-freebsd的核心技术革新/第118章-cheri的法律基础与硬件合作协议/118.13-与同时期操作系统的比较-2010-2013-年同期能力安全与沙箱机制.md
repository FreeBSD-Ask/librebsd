# 118.13 与同时期操作系统的比较：2010-2013 年同期能力安全与沙箱机制——Linux seccomp、SELinux、OpenBSD systrace、Windows AppContainer、macOS Sandbox——Capsicum/CHERI 的能力安全定位

## 118.13.1 Linux seccomp / seccomp-bpf（2012）

**要点**：Linux 的 seccomp（secure computing，2005 引入，仅允许少数系统调用）于 2012 年由 Will Drewry 扩展为 seccomp-bpf，允许基于 BPF 过滤器灵活限制进程的系统调用；Google Chromium 选择自行实现 seccomp-bpf 沙箱（而非采用 Capsicum），成为 Linux 沙箱的事实标准。Capsicum 的 capability 模型与 seccomp-bpf 的 “系统调用过滤” 代表沙箱的两种范式。

**辨析**：Capsicum 与 seccomp 并非互斥——Capsicum 提供 capability 抽象、seccomp 提供调用过滤，二者可叠加；“Chromium 放弃 Capsicum-linux” 是工程与生态选择，非技术优劣判定。

## 118.13.2 SELinux 与 Linux LSM 框架（2003-2010s）

**要点**：SELinux（NSA 2000 年 12 月发布，2003 进入主线）基于 Linux Security Module（LSM）框架提供强制访问控制（MAC），与 FreeBSD MAC 框架目标相似但实现不同；SELinux 的 “标签化 MAC” 在 Linux 服务器安全中占主导，Capsicum 则提供不同于 MAC 的细粒度 capability 沙箱。

**史料**：SELinux 设计文档（NSA）；Linux LSM 框架论文（WireX/Immunix, 2002）［B］

**史观**：总纲第 13 条——法律与道德是利益分配：许可证即法律层面的利益分配，SELinux 以 GPL 许可、Capsicum 以 BSD 许可，二者不同的许可证使其在不同生态中扩散；FreeBSD MAC 框架（含 Capsicum 挂钩）与 SELinux 形成 BSD/GPL 两端的 MAC 对照。

**辨析**：FreeBSD MAC 与 SELinux 功能重叠但哲学不同——MAC 关注 “主体-客体” 标签强制，Capsicum 关注 “能力句柄” 最小授权；将二者简单类比会忽略范式差异。

**文献**：Smalley S et al. Implementing SELinux as a Linux Security Module [EB/OL]. 2002. ［B］

## 118.13.3 OpenBSD systrace 与 pledge/unveil（2002/2016）

**要点**：OpenBSD 早期提供 systrace（2002，系统调用策略）作为沙箱工具，2016 年随 OpenBSD 5.9 推出 pledge(2)（限制系统调用集）与 2018 年 unveil(2)（限制文件系统视图），形成轻量级 “默认安全” 沙箱；其演进与 Capsicum 的 capability 思路有共鸣但实现更轻量，且为 OpenBSD 原生、BSD 许可。

**史料**：OpenBSD systrace/pledge/unveil 手册页与公告（2002/2016/2018）［A］

**史观**：总纲第 8 条——本体论上各方平等：OpenBSD 与 FreeBSD 同期探索沙箱，pledge/unveil 与 Capsicum 体现 BSD 家族各分支在 “最小权限” 上的并行创新，且均 BSD 许可可互鉴。

**辨析**：pledge/unveil 比 Capsicum 更轻量、更易部署，但缺乏跨进程 capability 传递的通用抽象；二者适应不同场景而非竞争。

**文献**：OpenBSD. pledge(2)/unveil(2) Manual [Z]. 2016-2018. ［A］

## 118.13.4 Windows AppContainer（2012）

**要点**：Microsoft 在 Windows 8（2012）引入 AppContainer，为 Modern 应用提供沙箱隔离（低完整性级别、受限 token、网络/文件能力显式授予）；其 “能力显式授予” 理念与 Capsicum 的最小权限方向一致，但基于 Windows 的 token/ACL 体系而非 UNIX capability。

**史料**：Microsoft Windows 8 AppContainer 文档（2012）［A］

**史观**：总纲第 8 条——本体论上各方平等：AppContainer 的 “能力令牌” 与 Capsicum 的 “能力句柄” 趋同但实现迥异，闭源与开源沙箱的工程路径平等对照、不分高下。

**辨析**：AppContainer 与 Capsicum 目标相似（最小权限沙箱）但无法跨生态共享代码；二者证明 “能力沙箱” 是 2010 年代操作系统的普遍方向。

**文献**：Microsoft. Windows 8 AppContainer [Z]. 2012.［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

## 118.13.5 macOS Sandbox：从 Seatbelt 到 App Sandbox（2007/2011）

**要点**：Apple 在 Mac OS X 10.5 Leopard（2007）引入基于 TrustedBSD MAC 框架的 Sandbox（内核设施俗称 Seatbelt），通过声明式 profile 限制进程资源访问；2011 年 OS X 10.7 Lion 进一步引入面向 App Store 应用的 App Sandbox；其底层 MAC 框架借鉴 FreeBSD/TrustedBSD 的 MAC 思想，是 BSD 安全技术经 Darwin 间接影响商业桌面的案例。

**史料**：Apple macOS Sandbox 指南（2011）［A］；TrustedBSD MAC 框架论文 ［B］
    FreeBSD 社区论文：[FP-2020-009] Oblivious Sandboxing with Capsicum and EBPF（Ryan Stone，2020）<https://papers.freebsd.org/2020/bsdcan/stone-oblivious_sandboxing_capsicum_ebpf/>
    FreeBSD 社区论文：[FP-2019-082] CheriABI: Enforcing Valid Pointer Provenance and Minimizing Pointer Privilege in the POSIX C Run-time Environment（Brooks Davis，2019）<https://papers.freebsd.org/2019/davis-asplos-cheriabi/>
    FreeBSD 社区论文：[FP-2016-003] Capsicum and Casper - a fairy tale about solving security problems（Mariusz Zaborski，2016）<https://papers.freebsd.org/2016/asiabsdcon/oshogbo-capsicum_and_casper/>
    FreeBSD 社区论文：[FP-2003-008] The TrustedBSD MAC Framework: Extensible Kernel Access Control for FreeBSD 5.0（Robert N. M. Watson，2003）<https://papers.freebsd.org/2003/rwatson-mac_framework/>

**史观**：总纲第 4 条——分离聚合是永恒规律：macOS Sandbox 的 MAC 基础源自 TrustedBSD（BSD 衍生），TrustedBSD 的 MAC 技术自 BSD 母体分离后又在 Apple 生态聚合回流，体现 BSD 安全技术经 Darwin 间接影响商业桌面。

**辨析**：macOS Sandbox 基于 MAC profile 而非 Capsicum capability，二者范式不同；但其 BSD 血统说明 BSD 安全研究对主流桌面 OS 的实际影响。

**文献**：Apple. App Sandbox Design Guide [Z]. 2011；TrustedBSD Project. MAC Framework [EB/OL]. ［B］
