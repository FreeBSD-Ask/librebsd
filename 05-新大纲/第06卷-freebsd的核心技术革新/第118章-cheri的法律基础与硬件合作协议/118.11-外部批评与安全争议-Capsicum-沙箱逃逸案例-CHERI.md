# 118.11 外部批评与安全争议——Capsicum 沙箱逃逸案例、CHERI 侧信道攻击与性能开销批评、应用改造门槛争议

## 118.11.1 Capsicum 沙箱模型的局限性与逃逸案例

**要点**：Capsicum 作为 OS 级沙箱机制并非无懈可击，其已知局限性包括：(1) 应用改造门槛高——Capsicum 要求应用显式重构以使用能力模型，大量遗留 UNIX 应用依赖全局命名空间访问，改造工作量大；(2) 内核攻击面仍然存在——Capsicum 不限制系统调用本身，仅限制对全局命名空间的访问和文件描述符权限，内核漏洞仍可能被利用进行沙箱逃逸；(3) casperd 作为特权代理本身成为高价值攻击目标——如果 casperd 被攻破，其代理的所有沙箱服务可能受影响；(4) IPC 通道攻击——沙箱进程之间通过 Unix domain socket 传递文件描述符的 IPC 机制本身可能成为攻击面；FreeBSD 安全公告中与 Capsicum 相关的 CVE 数量较少，主要因为 Capsicum 作为沙箱机制本身不直接引入漏洞，但应用程序使用 Capsicum API 时可能出现错误（如权限收缩不完整、能力泄漏）

**史观**：总纲第 7 条——理论必须自反：对 Capsicum 的批评反映了安全工程中的 “没有银弹” 原则——没有任何单一安全机制能提供完美防御，Capsicum 解决了 ambient authority 问题，但不解决内核漏洞、侧信道、逻辑缺陷等其他安全问题；这与 OpenBSD pledge/unveil 开发者的观点一致——pledge 的作者 Ted Unangst 多次强调 pledge 不是安全边界而是攻击面缩减工具，被攻破仍可能发生

**辨析**：需区分 “Capsicum 本身的漏洞” 和 “使用 Capsicum 的应用程序的漏洞”——前者属于 Capsicum 内核实现错误，后者属于应用开发者对能力模型理解不足导致的权限配置错误；截至 2025 年，公开记录中 Capsicum 内核框架本身的严重漏洞较少，但这可能也与 Capsicum 部署规模有限有关（相比 seccomp-bpf 在 Chrome/Android 中的大规模部署，Capsicum 的攻击面研究较少）；原大纲未提及 Capsicum 的局限性，已补充

## 118.11.2 CHERI 硬件安全的批评与争议

**要点**：CHERI 作为硬件能力架构面临多方面的批评和争议：(1) 性能开销争议——早期 256 位能力设计有显著性能开销（约 20-50%），CHERI Concentrate（128 位压缩）将典型开销降至个位数百分比，但仍存在内存带宽增加（能力指针是普通指针 2 倍大小）、缓存压力增大等问题；(2) 侧信道攻击风险——CHERI 不直接防御侧信道攻击（如 Spectre/Meltdown 类推测执行攻击、缓存时序攻击），硬件强制的边界检查可能引入新的侧信道泄露模式；(3) 编程模型争议——纯能力 CheriABI 需要重新编译所有软件，对现有 C/C++ 代码虽然修改量极小（0.026%），但与内联汇编、指针整型转换、自定义内存分配器等特定模式存在兼容性问题；(4) 生态采用门槛——需要新的硬件、编译器、操作系统、工具链全栈支持，迁移成本巨大；学术批评方面，2020 年代有论文演示 CHERI 指针压缩方案可能存在被绕过的理论可能性，以及 CHERI 在特定微架构实现上的侧信道漏洞

    FreeBSD 社区论文：[FP-2019-055] Fuzzing the kernel（Andrew Turner，2019）<https://papers.freebsd.org/2019/eurobsdcon/turner-fuzzing_the_kernel/>

**史观**：总纲第 5 条——没有必然性，只有偶然性：对 CHERI 的批评延续了 1980 年代以来对能力架构的长期争议——1980 年代 Intel iAPX 432 商业失败的原因之一即被认为性能开销过大；CHERI 团队通过 128 位压缩、微架构优化和软件兼容性努力试图解决这些历史问题，但是否能最终被市场接受仍未可知；安全与性能的权衡是计算机架构中永恒的矛盾，CHERI 代表了向安全一侧的倾斜

**辨析**：CHERI 性能开销数据需精确引用来源——Watson et al. 2024 IEEE Security & Privacy 论文给出的典型开销为：128 位 CHERI Concentrate 在 SPECint 基准上约 2-10% 性能损失（具体取决于工作负载），内存带宽开销约 30-60%（因指针大小翻倍），但通过压缩和微架构优化可部分缓解；“CHERI 可被侧信道绕过” 是对 CHERI 能力边界的准确描述——CHERI 解决内存安全问题，不解决所有安全问题；将 CHERI 宣传为 “不可攻破” 是错误的，CHERI 团队官方文档从未如此声称

## 118.11.3 应用改造门槛与生态采纳争议

**要点**：Capsicum 和 CHERI 共同面临的核心批评是应用/生态采纳门槛：(1) Capsicum 要求应用开发者显式重构代码——需要识别所有系统资源访问点、预先传递文件描述符、进入能力模式、为需要全局访问的操作设计 casper 服务；这一改造对简单工具（如 tcpdump）仅需数十行代码，但对复杂应用（如 Web 浏览器、数据库）需要大规模架构重构；(2) CHERI 需要全栈改造——CPU 硬件、编译器（LLVM/Clang 扩展）、操作系统内核（CheriBSD）、系统库、应用程序、甚至调试工具（gdb/kgdb）都需要 CHERI 感知支持；(3) 跨平台支持问题——Capsicum 主要在 FreeBSD 上原生可用，capsicum-linux 为实验性，其他平台无原生支持，开发者难以编写跨平台 Capsicum 化应用；CHERI 需要特定硬件，在 CHERI 硬件普及前只有研究人员和早期采用者能使用；(4) 与 Rust 等内存安全语言的竞争——Rust 通过软件层面（编译器类型系统）提供内存安全保证，不需要新硬件，且生态快速成熟，被部分开发者视为比 CHERI 更实用的内存安全路径

**史料**：CloudABI 项目弃用声明（2020-03）——Ed Schouten 明确将生态采纳困难列为 CloudABI 失败原因之一；WASI 设计文档——从 CloudABI/Capsicum 经验中学习如何降低采用门槛；各 Capsicum 化应用的改造工作量记录（tcpdump、dhclient 等）；CHERI 团队关于软件移植工作量的论文（0.026% 源代码修改）；Rust 安全研究与 CHERI 的对比分析 ［A］

**史观**：总纲第 10 条——动手者创造历史：应用改造门槛争议揭示了安全机制成功的关键要素不只是技术优越性，还包括开发者心智模型、生态系统支持、平台市场份额等非技术因素；Capsicum 和 CHERI 均由学术团队主导，技术设计严谨，但在开发者体验和生态推广方面面临挑战；WASI 的成功（继承 Capsicum 思想但运行在 WebAssembly 抽象层之上）说明：通过更高层的抽象降低采用门槛可能是能力模型走向主流的路径

**辨析**：“Rust vs CHERI” 是技术社区常见的二元对立叙事，但实际上二者解决不同层面问题且可互补——Rust 防止新编写的 unsafe Rust 之外的代码出现内存安全问题，但无法保护遗留 C/C++ 代码（数百万亿行现有代码无法被重写）；CHERI 可保护遗留 C/C++ 二进制（通过重新编译）且不需要重写代码；二者可组合使用（Rust 编译到 CHERI 目标提供双重保护）；CloudABI 的弃用不能简单视为 Capsicum 的失败——CloudABI 的纯能力 POSIX ABI 思想在 WASI 中获得了新生

(2021). CHERI Software Porting Effort Analysis. Capabilities Ltd Report; Rust Security Working Group. Memory Safety Documentation. rust-lang.org. ［B］
