# 122.1.5 收购与关闭事件的史料交叉验证

**要点**：Oracle 收购 Sun 及 OpenSolaris 关闭的关键日期交叉验证：Oracle 宣布收购 Sun：2009 年 4 月 20 日（Oracle/Sun 新闻稿、SEC filing 均确认）；欧盟反垄断审查通过：2010 年 1 月 21 日；收购完成：2010 年 1 月 27 日（SEC filing 确认）；illumos 项目启动：2010 年 8 月 3 日（Garrett D'Amore 邮件确认）；OpenSolaris Governing Board 解散：2010 年 8 月（OGB 会议纪要）；Oracle 内部备忘录泄露：2010 年 8 月 13 日（多个来源存档）；Oracle Solaris 11 发布：2011 年 11 月（首个完全闭源开发的 Solaris 版本）；需注意：OpenSolaris 从未被 Oracle “正式关闭”，而是通过停止更新开源代码仓库、解散治理委员会、撤回对社区版的支持等方式被 “实质终止”

**史料**：Oracle 2009-04-20 新闻稿（oracle.com）；Oracle 2010-01-27 收购完成新闻稿；SEC filing（sec.gov Archives）；illumos launch 邮件（2010-08-03，lists.illumos.org）；2010 年 8 月 Oracle 内部备忘录（存档于互联网档案馆）；LWN.net 2010-08-16 报道 ［A］

**史观**：总纲第 3 条——形式主义膨胀：Oracle 没有 “宣布关闭 OpenSolaris” 这一仪式化事件，而是通过一系列行政和技术操作使开源开发事实上无法继续——这提醒历史学家警惕 “官方叙事” 的完整性，历史的断裂往往发生在没有正式声明的灰色地带

**辨析**：部分中文资料称 Oracle 于 2010 年 3 月或 4 月关闭 OpenSolaris，此为不准确——OpenSolaris 代码仓库在 2010 年上半年仍有更新，真正的转折点是 2010 年 8 月的内部备忘录泄露和 illumos fork；Garrett D'Amore 发起 illumos 时仍在 Nexenta Systems 工作，Nexenta 是基于 OpenSolaris 的存储发行版（NexentaStor），illumos 的诞生有明确的商业动机——Nexenta 需要一个活跃的上游来维护其产品基础

**要点**：

- 该期复述一篇长文对 Oracle 杀死 Sun 的盘点：Oracle 收购 Java 后两度起诉 Google 索赔 80 亿美元均失败；Java EE 转由独立基金会运作；MySQL 安全修复官僚化导致用户流向 MariaDB；Hudson CI 处置失当催生 Jenkins；OpenOffice 社区转向 LibreOffice。（BSD Now EP212，[4636.04-4793.28]，L2）
- 尽管 Scott McNealy 曾认为 Solaris 必须开放才能赢得市场，Oracle 接手后先高调宣传又将其闭源；裁员使 Solaris 支持前景不明，Sun 的云计划被取消后又重新需要自建云。（BSD Now EP212，[4713.76-4785.84]，L2）
- James Nixon 在 iXsystems 负责 FreeNAS 的界面布局与社区倡导工作并充当 Django 模板问题的兜底支持；John Hixson 当时正打磨 FreeNAS API，Nixon 计划在 API 完成后编写第一个官方插件并发布逐步教程，以自身示范带动社区代码贡献；插件形态预计与 PC-BSD 的 PBI 模块类似，只要对接 API 即可用 Django 或任何语言编写。（BSDTalk EP210，[294.50-436.70]，L1）
- LISA 2011 展台演示的 TrueNAS 运行于小型 NAS 设备，含 ZFS v28 与 ZFS 复制功能，而社区版 FreeNAS 当时停留在 ZFS v15；iXsystems 将 TrueNAS 所需的特定 ZFS 特性回移植进 FreeBSD 8 系列，计划随 FreeBSD 9 发布回流公共侧；FreeNAS 下一主版本确定基于 FreeBSD 9，并与 PC-BSD 的发布节奏保持对齐。（BSDTalk EP210，[59.48-89.72]，L1）
- iXsystems 接管 FreeNAS 的缘由：原开发者 Olivier 因个人精力转向 Linux 曾考虑把项目迁往 Linux 平台，其副手近年承担主要维护工作，但 FreeNAS 7 所基于的 m0n0wall 框架难以添加新功能；iXsystems 内部使用 FreeNAS 已五年，为给社区保留 BSD 路线的 NAS 方案而接管项目并获得 Olivier 同意，随后重写 FreeNAS.org 并建立新论坛。（BSDTalk EP210，[983.02-1054.28]，L1）
- PC-BSD 9 isotope 版本自 beta1 起可一路升级而无需光盘重装；系统更新工具主动提示 RC 与 PBI 更新；新 PBI 系统改为差分下载，不再出现一百六十兆级的 Firefox 更新包；新控制面板与 meta package 机制支持 GNOME、KDE、LXDE、XFCE4 四大桌面（Fluxbox、TWM、Awesome 等可用但未官方支持），标志 PC-BSD 由 KDE 中心转向桌面中立；iXsystems 办公室桌面大量自用 PC-BSD，以 KDE 的 Dolphin 文件管理器访问 FreeNAS 共享。（BSDTalk EP210，[443.06-623.22]，L1）
- 社区生态方面，iXsystems 聘用 Dru Lavigne 统管 PC-BSD 与 FreeNAS 等项目的社区管理；论坛与 IRC 中社区保持活跃且敢于发声，有若干核心社区成员充当公司与社区之间的纽带；社区最期待 mini-DLNA 与 Transmission 等多媒体与下载插件回归，而插件系统在 FreeNAS 8.0 发布时尚未就绪；受访者预期社区会把 NAS 延伸为媒体中心，并愿意指导新人参与代码。（BSDTalk EP210，[623.22-787.18]，L1）
- ZFS 被视为 BSD NAS 的杀手特性：CDDL 许可证使 ZFS 在 BSD 侧的整合远比 Linux 侧容易，Linux 侧移植当时性能不切实际，受访者以 2004 年模拟 Dreamcast 每秒一帧作比；Oracle 收购 Sun 之后，公开 ZFS 预计止步于 v28，Oracle 内部后续版本不会开源，BSD 社区将自行延续开发；iXsystems 已实现盘故障通知、盘位指示灯等特性，并在自研 ZFS daemon。（BSDTalk EP210，[1054.28-1175.64]，L1）
- 用户侧证据显示 FreeNAS 在教育等预算受限场景被广泛推荐：主持人在缅因州 K-12 学区环境中观察到，学生统一配发苹果笔记本打破单一微软生态后，无法依赖 Windows 文件服务器的完全集成，FreeNAS 因此常被列为替代方案；TrueNAS 初装存在困惑，iXsystems 自 Cisco 招募 Garrett Cooper 专职客户支持，规划中的设置向导界面即针对初装门槛。（BSDTalk EP210，[916.74-965.42]，L1）
- 《FreeBSD Mastery: ZFS》的成书史：Allan Jude 早有意写 ZFS 专著但受困于“空白页”起步难，2015 年初在 Michael Lucas 动笔同类题材后主动提出合著，两人认定各有所长达成协议；全书主要面向 FreeBSD 10.1 时期的 OpenZFS，写作中途发现篇幅过大，将非核心主题拆出为第二本《Advanced ZFS》，最终仍超出目标篇幅；出乎意料的是审校与打磨耗时超过初稿写作。（BSDTalk EP256，[149.94-316.62]，L1）
- 书籍覆盖范围的技术决策：只收录 FreeBSD 上可用的 OpenZFS 特性，明确排除 Oracle 专有扩展；OpenZFS 在 illumos、Linux 及存储设备等平台间特性基本对等，故书的大部分内容平台无关，仅 gpart 与 GEOM 标签等建议属 FreeBSD 特定；因无闭源 Solaris 代码访问权且 Oracle 随机变更特性与版本号，书中不以 Oracle ZFS 为目标。（BSDTalk EP256，[317.02-393.44]，L1）
- ZFS 文档生态的消亡与补位：Solaris 时代文档质量虽高，但 sun.com 链接现重定向至 Oracle 首页而非文档新址，OpenSolaris 网站整体下线致大量资料只能零散检索；旧调优指南中大量 ZFS 建议对 FreeBSD 不适用或因 ZFS 演进而失效，许多旧 sysctl 已被全新子系统替代；受访者本人 2013 年在赴 BSDCan 的火车上写成 FreeBSD Handbook ZFS 章雏形，经 doc sprint 学会 DocBook，2014 年获文档 commit bit，正是社区文档补位的缩影。（BSDTalk EP256，[403.54-528.24]，L1）
- OpenZFS 特性管线与工具生态：Delphix 完成并开源的特性集成进 illumos 后“不到一周即进入 FreeBSD”；受访者最期待 resumable send——其跨洲复制 500 GB 级数据集的场景中中断可续传，但引入的 cookie 机制改变复制方式且与递归复制不兼容；快照管理工具至少五六个且各有缺陷（其 Ruby 工具依赖 .zfs 隐藏目录，在双挂载点场景致旧快照不回收）；他偶然接手 FreeBSD 9.1 后停更的 zfs-replicate 脚本并使自己的 GitHub 成为上游；Adam Leventhal 的写节流 DTrace 脚本因 Clang 内联函数致 DTrace 边界不可见而在 FreeBSD 失效，受访者提交了修复。（BSDTalk EP256，[533.58-816.50]，L1）
- 付费书与免费 Handbook 的内容分配：两种文体风格迥异——书口语化并含两位作者互相调侃、面向具体情境应用，Handbook 则是操作步骤式；受访者时间有限故优先投入书；FreeBSD Journal 允许作者保留版权，因此他可以计划把自己欠缺覆盖的 IPFW 文章内容（不可直接复制）日后充实进 Handbook 的 IPFW 章节，兼顾社区贡献与书的商业价值。（BSDTalk EP256，[817.24-939.18]，L1）

- 评述 Oracle 处置 Sun 技术资产的博客长文（含 Sun 技术逐项清单）；BSDCan 2017 会议视频（YouTube）。（BSD Now EP212，[4636.04-4793.28]，L2）

- PC-BSD 9 isotope 自 beta1 的连续升级使用史、PBI 差分更新机制与多桌面 meta package 的一线使用者口述，可与 PC-BSD 官方发布记录交叉核对。（BSDTalk EP210，[443.06-556.34]，L1）
- 该期指认的一手材料：Adam Leventhal 在 Delphix 博客发布的 ZFS 写节流（write throttle）说明与 DTrace 脚本集（其中一个脚本经受访者提交修复以适配 FreeBSD 的 Clang 编译）；sun.com 至 Oracle 的重定向现状与 OpenSolaris 网站下线事实，作为 ZFS 文献散逸的直接证据；旧 Solaris 调优指南中关于 ZFS 的失效建议。（BSDTalk EP256，[433.68-458.86]，L2）

**史观**：

- 总纲3 不存在进步，只有权力再分配：Oracle 收购 Sun 后技术资产被关闭、捐赠或流失，并非技术进步叙事，而是企业权力与利益重新分配的结果。（BSD Now EP212，[4636.04-4785.84]，L2）
- 总纲5 没有必然性，只有偶然性：Solaris 由开放转闭源、Jenkins 与 LibreOffice 的诞生均源于具体决策与事件，而非必然的技术演进。（BSD Now EP212，[4713.76-4793.28]，L2）
- 总纲4 分离聚合是永恒规律：FreeNAS 7 的单体功能集在 8 代被拆解为模块化插件架构，社区期待的多媒体与下载功能又将经由插件重新聚合回产品，呈现功能集先分离后聚合的循环。（BSDTalk EP210，[159.72-223.08]，L1）
- 总纲5 没有必然性，只有偶然性：FreeNAS 的 BSD 路线险些随原开发者个人精力转向而中断，其延续系于 iXsystems 恰好自用五年并愿意接手这一偶然组合，说明项目命运并非由技术优劣必然决定，而取决于具体的人和时机。（BSDTalk EP210，[983.02-1045.96]，L1）
- 总纲13 法律与道德是利益分配：CDDL 与 GPL 的许可证差异实际决定了 ZFS 在 BSD 与 Linux 两侧截然不同的生存境遇，许可证文本成为技术生态地理分布的直接塑造力量，体现法律形式对技术世界的分配作用。（BSDTalk EP210，[1058.76-1066.36]，L1）
- 总纲10 动手者创造历史：Nixon 以亲手编写第一个插件并发布逐步博客来带动社区参与，iXsystems 工程师逐项实现盘位指示灯与 ZFS daemon 等特性，产品演进由动手者的具体劳作而非路线图宣告推进。（BSDTalk EP210，[727.30-787.18]，L1）
- 总纲22 知识注定过时：Solaris 调优指南的 ZFS 建议大量失效、旧 sysctl 被全新子系统取代、权威文档链接成批腐烂——技术知识的过时不是意外事故而是常态，一代人的操作经验会随子系统更替而整体失效，唯有持续重写的社区文档能延缓这一过程。（BSDTalk EP256，[458.86-485.28]，L1）

**辨析**：

- dedup 约每 TB 两 GB 内存的说法为受访者即兴估计，与 ZFS 官方建议值须另行核对；Oracle 后 ZFS 止步 v28 与 ZFS daemon 细节为受访者预判与半保密表述，后者不可据此段展开引用；Linux 侧 ZFS 性能类比系修辞而非实测；转写讹误：Drew LeVine 应为 Dru Lavigne，John Hickson 应为 John Hixson，monowall 应为 m0n0wall，Trunaz 应为 TrueNAS，ADO release 疑为 8.0 release。 [存疑脚注] 内存估算与 ZFS 封顶判断均系单方口述或预判；ZFS daemon 相关内容受访者明示不便展开，须以 iXsystems 后续公开材料核实。（BSDTalk EP210，[275.50-283.90]，L4）
- 书对 Oracle ZFS 的覆盖为有意排除而非疏漏，源于闭源访问缺失，此局限为受访者自述；转写中将某 OpenZFS 存储设备名记为“Accenta”，疑为 Nexenta 之讹误，引用时须核对原始音频。 [存疑脚注] “Accenta”系转写疑误，疑为 Nexenta；Oracle ZFS 排除决策为单方陈述。（BSDTalk EP256，[370.32-376.50]，L4）
