# 124.2.5 要点ZFS贡献者记录中的几个关键辨析点1JeffBonwick杰夫邦威克是ZFS

**要点**：ZFS 贡献者记录中的几个关键辨析点：（1）Jeff Bonwick（杰夫·邦威克） 是 ZFS 的发明者和架构师，但他在 2010 年 Oracle 收购 Sun 后离开 Oracle，此后较少参与 OpenZFS 开发，当前 OpenZFS 开发由 Matt Ahrens 等人主导——不应将 ZFS 完全等同于 Bonwick 的个人项目；（2）Pawel Dawidek 虽然是 FreeBSD ZFS 移植的核心，但 2010 年代中期后他的工作重心转向其他 FreeBSD 子系统，FreeBSD ZFS 维护后续由 Martin Matuska、Andriy Gapon 等人接手；（3）Brian Behlendorf 不是 Apache Web 服务器的 Brian Behlendorf（同名同姓的两个不同开发者——Apache 的 Brian Behlendorf 是开源软件的早期先驱，ZoL 的 Brian Behlendorf 是 LLNL 的工程师，这一混淆在中文资料中很常见）；（4）许多 ZFS 贡献者来自商业公司（Delphix、iXsystems、LLNL、Joyent），他们的工作是公司雇佣劳动的一部分，不是 “业余志愿者贡献”；（5）illumos 社区在 2010-2020 年间是 OpenZFS 的事实上游，所有平台（包括 FreeBSD 和 ZoL）都从 illumos 同步代码，直到 OpenZFS 2.0 实现统一代码库后这一模式才改变

**史料**：OpenZFS GitHub commit 统计（github.com/openzfs/zfs/graphs/contributors）；FreeBSD SVN commit log；illumos commit log；LinkedIn/公司博客确认各贡献者身份 ［A］

**史观**：总纲第 10 条——边缘者贡献：开源项目的贡献者历史往往被简化为少数 “明星开发者”（Bonwick、Dawidek、Behlendorf），但 ZFS 的真正存续依赖于数十名持续维护者和数百名代码贡献者的日常工作；这些 “边缘者” 的工作是 ZFS 20 年后仍然活跃的基础

**辨析**：两个 Brian Behlendorf 的混淆问题：这是中文技术社区中广泛传播的一个错误——Apache 的 Brian Behlendorf（生于 1973 年，Apache Group 创始人之一，Mozilla 董事会成员）与 ZFS on Linux 的 Brian Behlendorf（LLNL 的 HPC 存储工程师）是完全不同的两个人；此错误在多个中文博客/教程中出现，须在正文中明确纠正；FreeBSD ZFS 主干导入 commit 经 freebsd.duckdb `commits` 表验证为 `f0a75d274af375d15b97b830966b99a02b7db911`（author = committer = Pawel Jakub Dawidek，<pjd@FreeBSD.org>，author_date = committer_date = 2007-04-06T01:09:06Z，message_subject = “Please welcome ZFS - The last word in file systems.”），原大纲引用的 r177621 等 SVN revision 号在 2020 年 FreeBSD SVN-to-Git 迁移后已不再作为主引用，Git commit hash 为当前权威追溯依据；该 commit 同时是 sys/cddl/contrib/opensolaris/ 目录下 ZFS 源文件首次引入 commit；0 信任原则提示：commit_hash 经迁移重算，但 author/committer 字段一致且与 Dawidek BSDCan 2007 演讲时间吻合，可信度高

**要点**：

- Klara Systems 详解 OpenZFS 2.1 的 dRAID（distributed RAID）：在 RAID-Z 语义上重排数据块使访问均匀铺满全部盘，配合预分配的分布式热备实现快速换盘；其顺序 resilver 仅沿 parity 布局重建目标盘，随后自动触发 healing resilver 补全校验，把传统 scrub 式全池校验拆分为两阶段以适应大容量盘时代；OpenZFS wiki 的 90 盘 16TB 组测试显示换盘时间由约 29 小时缩短至 15 小时余，且单/双/三奇偶校验皆不放大耗时。（BSD Now EP393，[463.28-869.34]，L2）
- 主持人重读 27 年前 Adrian Cockcroft 的 Sun Performance and Tuning：SunOS 4 目录名查找缓存（DNLC）只缓存 14 字符以内文件名、le0 网卡与 SCSI 接口共享 DMA 导致重负载网络拖慢磁盘吞吐等细节，折射 90 年代系统调优的现实约束；书中 VM stat/SAR 的多因素组合测量（六因素四水平即 4096 组合）提醒读者性能实验的组合爆炸与读数陷阱。（BSD Now EP393，[89.12-426.96]，L2）
- Signal 在伊朗遭封锁后给出代理方案，其官方 Docker 镜像内里只是 nginx 配置；社区据此给出 FreeBSD + nginx + acme.sh（Let's Encrypt/ZeroSSL）的等价部署教程，并默认关闭访问日志以避免记录经代理的通信内容。（BSD Now EP393，[1065.54-1311.46]，L2）
- 从 macOS 迁移者的 PDF 需求牵引出 OpenBSD ports 中的 Xournal/Xournalpp（触笔与手指标注、签名、导出只读 PDF）与 OCRmyPDF（对扫描件识别后生成可复制文本），讨论指出这类工具并非 OpenBSD 独有，映射桌面 Unix 在文档工作流上的补课过程。（BSD Now EP393，[1311.46-1662.86]，L2）
- Fabricator 平台的“现在就该做”清单以 Facebook 教训立论：ID 从 2 的 33 次方起跳以杜绝标识符与业务数值混淆（PHP array_slice 重排索引导致渲染错人的案例）、只存有效 UTF-8 以避免文件名跨系统漂移（Bacula 备份还原场景反例）、勿以黑名单构建安全系统（Facebook 的 CSS 黑名单制造了无尽的安全漏洞）、生产环境 SQL 语法错误应当高声报警以充当 SQL 注入的高信号探测器。（BSD Now EP393，[1672.1-1939.58]，L2）
- 反馈环节：Dan Langille 当场实测证明 ZFS 快照彼此独立、可任意删除旧快照而不影响新快照（快照是文件系统时点照片而非增量差分，仅回滚受限于更新快照）；另有听众询问 bhyve 中直通设备与物理盘并存的失败案例，以及多操作系统共享同一 ZFS 池引导的可行性，主持人以 bootfs 参数唯一性与加载器对加密池（GELI）的支持边界作答。（BSD Now EP393，[2438.92-2922.44]，L1）
- Delphix 作为 2015 年前后 ZFS 商业开发中心确立了一条自成一体的流水线：内部代码评审、跑 ZFS 测试套件与 Ztest 压力测试、先在自有生产服务器运行数月再交付客户，发布后一至两个月内 upstream 到 illumos；FreeBSD 侧由 Xin Li 约一周拉取一次 illumos 提交，形成 illumos 为源、FreeBSD 为近下游的分层结构（Matt Ahrens 与 Alex Reece 自述，ts 1431.88-1526.92）。（BSD Now EP77，[1431.88-1526.92]，L1）
- OpenZFS common repo 在 2015 年陷入有共识无动力的停滞：Matt Ahrens 判断“创建这个 common repo 本身并不解决任何问题，它只是让今后解决问题更容易”（ts 1618.08-1631.02），FreeBSD 因拉取成本低而需求有限，Linux 侧已分叉到对终态有不同设想，故 Delphix 转而把精力放在替其他贡献者测试并送入 illumos（ts 1529.26-1746.66）。（BSD Now EP77，[1529.26-1746.66]，L1）
- BIND 去 base 化呈现一条完整的成本收益逻辑：Allan Jude 估算 BIND 占 FreeBSD 过去十五年安全公告的四分之一以上，移入 ports（FreeBSD 10.0 起）换取当天级更新；OpenBSD 5.7 移除 BIND 后由 NSD 承担权威解析、Unbound 承担缓存解析的双守护进程分工，而“每台服务器都自带递归 DNS”的历史假设随单机时代终结而失效（主持人转述，ts 596.16-773.00）。（BSD Now EP77，[596.16-773.00]，L2）
- Paetzel 口述约 100TB 双机容灾池的连环故障：客户在升级存储软件但保留版本 28 池未升级的前提下扩展池，主单元加柜后即刻 kernel panic 且 spacemap 全毁；切换至备份机后，备份机在完全相同的补丁与内核下复现同型 panic——spacemap 亦损。团队以只读导入抢救数据（只读模式不依赖 spacemap，因其仅用于写路径），周五起反向复制，最终自圣何塞驱车六小时运送约 100TB 硬盘至洛杉矶重建新池并恢复服务；事后以实验法确认诱因：池版本与内核模块版本不一致时向池添加 vdev 存在风险，iXsystems 已在其软件中禁用该操作并与 OpenZFS 上游讨论归因。 [存疑脚注] 故事细节（卡车救援、日期序列）仅本访谈单源；转写将 Kris Moore 记作 Chris Moore，iXsystems 已由新转写正确转写。（BSD Now EP45，[267.00-648.68]，L1）[订正：原 转写将 iXsystems 记为 IAC/IAX Systems、Kris Moore 记为 Chris Martin/Moore，2026-09-30 SenseAudio 重转核对]
- 第二则战例：版本 28 池无异步删除，含约四十亿个 1K 文件的数据集在十余盘 RAIDZ 上删除时耗尽 I/O 且无法中止，重启后导入进程仍继续删除约四周方才放行；救援方法是自行实现按更早事务组导入。由此引出 feature flags 单向升级之弊——Paetzel 当面询问 Ahrens 能否提供兼容 FreeBSD 9.2 的版本 5000 池，并确认可逐项禁用特性或以 zpool create 指定版本号迂回。 [存疑脚注] 四周时长与四十亿文件数均为口述约数；转写记 BSDCan 为 HBSDCon。（BSD Now EP45，[696.68-858.72]，L1）[订正：原 转写记 BSDCan 为 HBS decon，2026-09-30 SenseAudio 重转核对]
- 第三则战例与对策：同型号 512n 与 512e 盘因总块数非 8 的倍数而相差 7 个逻辑块，两盘条带成池即错配（FreeNAS 以交换分区缓冲幸免于难）；FreeNAS 的回应是在 zpool create 中强制 ashift=12（不经 GNOP 而直接改写，GELI 仅用于 swap 与加密），head 随后新增最小 ashift 的 sysctl；另有厂商 RMA 不保证回件同型号的长期风险。Paetzel 亦说明 zpool status 报告 512/4K 非最优布局后逐盘替换是唯一修复路径。 [存疑脚注] 转写将 GELI 记为 jelly、GNOP 记作 G knob/genop；ashift 强制的实现细节待与 FreeNAS 提交记录核对。（BSD Now EP45，[912.20-1179.72]，L1）[订正：原 转写将 GELI 记为 jelly、GNOP 保留，2026-09-30 SenseAudio 重转核对]
- 工程进展自述：FreeNAS 9.3 安装器 GRUB 化以支持 USB/无光驱机型，因 Xen 等管理器上内存测试中断禁用致启动迟缓（约每秒一字节）而回退 ISO、GRUB 镜像单列；两百盘池导入自四十余秒降至 11 秒，新 MPS 驱动并行扫描使两分钟探测缩至 15 秒，以满足故障切换时间窗；主力开发仍驻 FreeBSD 9（在线更新、NFSv4），FreeBSD 10 的 direct I/O 在全 SSD 配置下性能约为 9 系两三倍、目标二十五万 IOPS（对照 Motley? 无——引用 Alexander 以 dd 在十六盘 SSD 达百万 IOPS 的非 ZFS 对照）；ctld 自 10 回移至 9 作实验性内核 iSCSI target 并通过 Windows 2012 集群验证（istgt 未通过）。 [存疑脚注] 百万 IOPS 对照者转写记为 Alexander、具体所指待核；导入时间基准（40+）单位存疑。（BSD Now EP45，[1186.40-1779.10]，L1）
- Ahrens 口述 ZFS 起源：Jeff Bonwick 早于项目一年多即受命为 Solaris 打造下一代文件系统，配有十余名多为 UFS 出身的人手却因迟迟无设计而难以推进，遂向管理层承认原路不通；2001 年他与刚毕业的 Ahrens 以两人小组在雷达之下重启 ZFS，白板推演设计。分工上 Bonwick 深谙 Solaris 内核与大公司政治，负责在需要低调时维持项目隐匿、在有所成果时对外推广，Ahrens 则以新人之姿不设设计成见，二人自认缺一不可。 [存疑脚注] 转写将 Jeff Bonwick 记作 Jeff Bondwick、将 skunkworks 记作 SoundQuirks，均按语境校正。（BSDTalk EP227，[121.88-315.90]，L1）
- 早期时间线：2001 年夏提出基本设计，并以 Ahrens 在校期间所写的文件系统 interposer 层实现用户态原型，约五六个月后的 2001 年万圣节前后跑通，万圣节自此成为 ZFS 的标志性节点；随后引入有 UFS 经验的 Mark Maybee 等人负责 ZPL 层，即实现属主、文件大小、权限、目录与符号链接等真实文件系统语义的部分，约一年后的 2002 年万圣节前后得到可随 Solaris 运行常规工具的内核级完整文件系统。 [存疑脚注] 转写作 Mark Mabee 与 Marcus Schellenbaum，按语境疑为 Sun 的 UFS/ZFS 工程师 Mark Maybee 与 Mark Shellenbaum，须以原始音频与 Sun 时期人员记录复核。（BSDTalk EP227，[392.72-502.08]，L1）
- 开源与信任曲线：2005 年万圣节前后 ZFS 源码随 OpenSolaris 发布，彼时团队约十余名工程师、累计投入近 100 工程年；发布虽引起热望，但用户对把数据托付给新文件系统持保留态度，历经新品亮相、进入 Solaris 10 成受支持产品、客户测试数月乃至一年后进入生产的缓慢爬坡；近两三年 ZFS 经 OpenZFS 运动可用于 FreeBSD、Linux 与 macOS，用户与以其为业的企业数量激增。（BSDTalk EP227，[518.66-610.58]，L1）
- 可移植性源于设计阶段的模块化分层而非移植意图——ZFS 当年深嵌 Solaris：最上层的 ZPL/POSIX 层因须对接各平台 VFS 而差异最大，中部大块代码高度可移植，最底层的磁盘接口既小又易于移植，这种清晰分层同时解释了 ZFS 后来的跨平台扩散能力。（BSDTalk EP227，[724.44-794.26]，L1）
- OpenZFS 伞状项目在 2013 年访谈时点刚刚起步、尚无正式管理结构，目标是把 Illumos/Solaris 衍生、FreeBSD 与 Linux 各平台实现收拢一伞，让各平台的创新彼此可得、避免在每处重复修同一 bug。现状是 Illumos 为上游仓库、改动流向 Linux 与 FreeBSD，但 FreeBSD 开发者向 Illumos 回馈改动因对方社区更小、缺乏便捷的开发测试环境而困难；第一步即降低向 Illumos 集成改动的门槛，Ahrens 正与 FreeBSD 社区的 ZFS 负责人协作推进。 [存疑脚注] 转写将 FreeBSD 侧协作人记作 Powell，按语境疑为曾主持 ZFS 移植 FreeBSD 的 Pawel Dawidek，待原音频复核。（BSDTalk EP227，[858.58-998.08]，L1）
- 对重写问题的回应：ZFS 基础扎实、极易修改与增强，去重即开发晚期干净加入且代码集中于单层，故无需推倒重来，并以 UFS 约三十年的寿命为期许。但若今日重新设计，将面向未来十年以 Flash 为主的硬件：Flash 随机读能力强，或使常开去重变得可行——去重如今依赖巨型哈希表在每次写块时查询，磁盘介质上代价高昂，SSD 化后可望大幅缓解。（BSDTalk EP227，[1115.24-1409.52]，L1）

**史料**：
