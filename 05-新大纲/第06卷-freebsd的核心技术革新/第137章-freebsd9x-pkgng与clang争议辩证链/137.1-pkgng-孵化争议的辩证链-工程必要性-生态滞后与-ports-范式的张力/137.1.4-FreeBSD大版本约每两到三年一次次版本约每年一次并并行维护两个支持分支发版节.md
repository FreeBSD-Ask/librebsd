# 137.1.4 FreeBSD大版本约每两到三年一次次版本约每年一次并并行维护两个支持分支发版节

- FreeBSD 大版本约每两到三年一次、次版本约每年一次并并行维护两个支持分支，发版节奏的最大瓶颈不在技术而在安全团队负担：维护中的旧版本越多，补丁构建与支援矩阵越大，历史上甚至出现 9.1 因长支持周期而晚于 9.2 终止支持的倒挂乱象。以 11 起启用的新支持模型依托 ABI 兼容承诺，令 11.1 发布数周后即终止 11.0 支持，以此压缩旧版本数量、换取更快的安全更新与更密的发版；9.3 之后不再有 9.4，改以分支末期汇总发布延长迁移窗口。讲述者还援引 9.1 时期 NFS 内存泄漏的亲历痛感：修复早已入库却不存在含修复的可下载版本，自行编译即意味着脱离 freebsd-update 支援体系。“我们目前不做更多 FreeBSD 发布的最大原因，基本就是安全团队不得不一直支援的版本更多了”（5312.08-5319.42）。（BSD Now EP86，[4447.40-4701.78]，L1）
- OpenBSD 严守每年五月与十一月各一次的发布节律，不区分大小版本，安全与重大缺陷修复回移至最近版本后即止，仅支援上一版，形成约三个月开发加三个月冻结的双窗口节奏。其收益是新代码最迟约两个月内即可抵达用户、安全团队得以保持精简，代价是对需要长期支持的企业不友好，且冻结期对 SMP 等大型改造构成节律性拖累；评论者认为 CVS 缺乏开发者侧分支的合并能力放大了这一结构性紧张，开发者遂以补丁集流转工作，形成与其余分支不同的协作形态。（BSD Now EP86，[4736.32-4886.76]，L2）
- M:Tier 的核心业务是为一家业务遍及一百五十余国、IT 部门规模超越其所在国任何本土集成商的蓝筹客户，在从边缘防火墙与路由器、FTP、Kerberos、LDAP、DNS、NTP、VPN 等服务到普通员工工作站的全栈上部署自管理 OpenBSD，公司内部约九成系统为 OpenBSD；选型动机受保密协议所限只能概括为法律与安全两条。为应对当地普遍缺乏 Unix 与 BSD 经验、多来自 Windows 背景的用户，方案以 PXE 安装服务器加一键引导实现全基础设施的自动分区、装包与配置，并围绕 GNOME 桌面补齐 Windows 用户预期（U 盘自动挂载、无线漫游图形工具），GNOME 3 所需 KMS 支持由公司出资赞助。 [存疑脚注] 嘉宾姓名转写作 Anton Jakuto（通行拼法为 Antoine Jacoutot），公司名转写存在 m-tier、m-chair、mtr 等变体，均按上下文校准为 M:Tier。（BSD Now EP86，[1200.02-1495.06]，L1）
- 针对 OpenBSD stable 分支不提供二进制安全更新、需自行重制版本或手工打补丁的现状，BinPatchNG 以一组 makefile 将 base 系统安全修复构建为可用包管理器安装的补丁包并支持回滚，OpenUp 则负责扫描仓库、自动安装缺失补丁并更新全部软件包；该工具链由 Gerardo Santana 首创，后经前 OpenBSD 开发者接手更名并搁置，M:Tier 维护至今。其外围效应是社区对 stable 的关注度上升，开发者开始更多向 stable 回移包级修复——“如今我们可以看到大量提交进入 stable，这在以前是不存在的”（2231.90-2236.62）。 [存疑脚注] BinPatchNG 的接手者姓名转写作 Felix Rolager，拼写待核。（BSD Now EP86，[1953.22-2244.60]，L1）
- Bryan Drewery（转写误作 Brian Drury）自述入圈路径：2003 年前后经 IRC 结识经营 shell 服务的 FreeBSD 4.11 用户而入坑，2012 年因不满包安装状态找到 pkgng 项目并协同 Baptiste Daroussin，从提交补丁到获 ports 提交权，再到以包框架贡献者身份进入 Port Manager 团队并新获 source 提交权——包体系维护者由工具建设者自然生长而成。（BSD Now EP46，[1963.44-2018.28]，L1）
- FreeBSD 官方包构建集群的一手运维细节：四台号称 beefy 的机器各配 32 核与 96—100GB 内存，每周二 UTC 凌晨一点对 ports 树拍快照并按各发布版与 head 构建 x86 包集，全量需三至五天；另有八套每日测试系统覆盖非 root 构建、打包测试与 QA，quarterly 季度分支自 head 切出并回灌安全修复，属仍在试验中的稳定化机制。（BSD Now EP46，[2439.92-2628.96]，L1）
- iodine DNS 隧道演示的实操要点构成其技术史价值：服务端以特权分离用户与 chroot 运行但密码将以明文见于进程列表，且 iodined 须独占一个 IP 承担 DNS 应答而无法与既有域名服务共存；客户端探测可用查询类型并按 DNS 包尺寸协商 MTU，建隧道后经压缩 SSH 登录验证，并可与 stunnel、SSH 链式跳板教程组合成受限网络下的成套突围方案。（BSD Now EP46，[5978.10-6327.42]，L1）
- FreeBSD 发行工程团队在代码冻结后审批所有针对该分支的变更，目标是在已知良好状态上修复既有问题而非引入新特性，以降低升级回归风险。（BSD Now EP2，[2347.62-2437.94]，L1）
- Glen Barber 加入 FreeBSD 基金会后获得专职时间协调发布流程，并兼管集群管理团队与项目资源维护，使发布节奏不再完全依赖志愿者的时间。（BSD Now EP2，[4398.47-4558.76]，L1）
- FreeBSD 10-CURRENT 自 2013 年 9 月起不再默认构建 GCC，基本系统改以 Clang 为默认编译器；需要 GCC 的场景改由 ports 提供现代版本。（BSD Now EP2，[543.86-622.62]，L2）
- LDNS 与 Unbound 正被移植入 FreeBSD 基本系统，计划在 10.0 前移除 BIND；主持人预期此举可减少约三分之一的安全公告负担。（BSD Now EP2，[4075.30-4225.94]，L1）
- Poudriere 以 jail 隔离并发构建二进制包，可在一台机器上按 FreeBSD 版本与架构分 jail 编译，并以增量重建与摘要签名支撑自有 pkg 仓库分发。（BSD Now EP2，[865.40-904.68]，L2）
- 该期头条报道 OpenBSD 已实现 64 位 time_t，以避免 2038 年 32 位时间戳溢出；该改动使 32 位平台也能跨越 Y2038 时间曲线。（BSD Now EP2，[71.70-150.60]，L2）
- Allan Jude 自述两档节目的生产机制：TechSnap 开播 134 周以来每周四一期从未间断，定位为面向系统管理员的安全新闻拆解加听众问答；BSD Now 则专攻 FreeBSD、NetBSD、OpenBSD，每周三东部时间下午两点直播，由 TJ 撰写几乎全部节目笔记与教程、PC-BSD 的 Kris Moore 主持；他起初认为 BSD 内容不足以支撑每周一档，深入参与会议与文档写作后才改观。（BSDTalk EP235，[272.10-378.10]，L1）
- Scale Engine 的 CDN 分布于 10 国 30 个数据中心（仅荷兰即 4 个），以 GDNSD 做全局服务器负载均衡——该软件原是 Logitech 开发者为地理分布驱动下载而写，用 GeoIP 数据库按解析请求来源改写结果，并辅以外部健康监控插件：经 SNMP 轮询网卡利用率、超过七成即视为不可用而改指次近节点；由于 DNS TTL 加上部分 ISP 无视 TTL 长时间缓存，无法确保新用户立即离开故障节点，故只向每台服务器推送六至七成链路容量——直播流一旦发生争用是全体观看者体验崩坏，而 HTTP 下载争用只是各自变慢。（BSDTalk EP235，[451.72-619.30]，L1）
- 运维与部署体系：全球机房一律租用服务器而非托管，以换取 30 天合约与厂商换件；经 VPN 加 IPMI 带外管理，可在汉密尔顿的桌面上给阿姆斯特丹的服务器挂载 ISO 重装系统；部署链为 FreeBSD 9.2 原版安装、自有 pkg 仓库（以定制编译选项预编译 Nginx 与 Varnish）、bootstrap pkg 后交 Puppet 签名引导，从 Puppet 启动到投产约七八分钟；PC-BSD 的 ISO 与 pkgng 仓库以 ZFS 复制预置到边缘，而 pkgng 仓库要求 repo 清单与密码学签名的 SHA-256 摘要文件同全部包文件保持整体一致、绝不许新旧混合状态，故用 rsync 延迟更新选项先写入临时目录再原子改名就位，每 15 分钟复制一次。（BSDTalk EP235，[691.80-978.18]，L1）
- Puppet 链路的性能改造：视频流所依赖的大型 Java 应用打包成 jail 由 Puppet 分发、EzJail 部署；经 Puppet 的 Ruby 代码直接分发 500MB 文件效率极低，其解法是教会 Nginx 信任 Puppet 的证书颁发机构，仅允许持 Puppet CA 所签客户端证书的已激活节点从安全文件库直接经 Nginx 拉取，安全模型不变而性能大幅提升；这些 Puppet 与 Nginx 优化曾于 2013 年春在 BSDCan 演讲披露。（BSDTalk EP235，[980.90-1046.78]，L1）
- 包管理迁移的量化对比：当年各边缘节点启动时自行从 ports 编译全部所需软件约需 45 分钟，切换 pkgng 后缩短至七分钟且一半耗在 EzJail；Poudriere 取代旧 Tinderbox，实测每 CPU 开一个 jail、单作业串行反而快于跨机并发分派，一台 24 核 96GB 内存的机器在 tmpfs 中编译全量约 24000 个 port（含 24 种语言的 LibreOffice 与四个 Firefox 版本）约 14 小时；他以 Poudriere 生成新包集再以 pkg2ng 转换旧机，通过手工改写包 origin 化解 Perl 5.10 到 5.14 与 PHP 5.3、5.4 并存的依赖冲突，迁移之顺利出乎意料。（BSDTalk EP235，[1069.80-1268.36]，L1）
- 升级 FreeBSD 9.2 的主要动机是 ZFS v5000：LZ4 压缩与存储池接近满载时的性能改进，对存有四组共 50 至 60TB 视频数据的阵列尤为关键；新版命令行全面支持干跑预演——删除快照前可预估将释放的空间，增量 zfs send 前可预估传输量，他据此脚本化出进度条，得以预知一次发送的体量与完成时间。（BSDTalk EP235，[1443.66-1538.90]，L1）
- Daroussin 自述重写动机：学生时代在笔记本上编译 ports 尚可当作乐趣，成为真正使用者后只求装上即用、升级不必等待两天；而在旧体系下想安装特定版本的 Apache，须先上网站查有无对应二进制包，再赌其构建正确、未过时且无安全漏洞。（BSDTalk EP239，[133.06-195.90]，L1）
- 为何不修 pkg_install：许多人尝试过，但该工具并非为如此长的服役期设计，代码注释即可证明其年代已逾二十年；OpenBSD 早年即认清其缺陷并整体重写——当时 ports 树规模尚小、重写代价低，NetBSD 仍在旧代码上不断增补却无法根治，FreeBSD 则选择不作为，以补丁和 ports 树中的大量变通手法迁就，最终得到一个用 C 写成却近乎 shellcode、处处错误执行、内存泄漏、随时可能损坏且完全不可维护的工具。（BSDTalk EP239，[195.90-291.66]，L1）
- 旧工作流的实际体验：pkg_add -r 装包之后只能祈祷依赖齐全、系统不被毁掉一半；两周后想升级 Apache 时，唯一安全的二进制升级路径是全部删除、清理 /usr/local 中残留的大量遗留、再全部重装；Portmaster 与 Portupgrade 虽提供二进制途径，但其底层依赖 pkg_install，因此注定同样做不好。（BSDTalk EP239，[296.46-359.52]，L1）
- pkg 的新范式：安装最新 Firefox 只需一条命令，包引擎自动计算全部依赖、确认可得性并按正确顺序预演安装，用户确认后才抓取、校验一致性与隐藏冲突，若有问题则什么都不会被安装；pkg upgrade 依据本地数据库与远程仓库推断升级顺序与冲突处理，把系统升至最新；此后用户即可卸载 Portmaster 与 Portupgrade，纯二进制用户甚至不再需要 ports 树、不必在主机上编译。（BSDTalk EP239，[362.86-442.16]，L1）
- pkgng 的架构定位：它不是又一个前端而是新的二进制包管理系统，覆盖安装、删除与信息查询——包使用的许可证、构建时选项、文件与包的双向归属查询皆可完成；同时它是一个高层 C 库，命令行的 pkg 只是作者写出的一个前端，刻意让他人可基于该库为 GNOME、KDE 或 PackageKit 等编写图形前端；演进计划上下一版本预计次月底发布，并教授用户编写插件以自行扩展。（BSDTalk EP239，[446.06-499.36]，L1）
