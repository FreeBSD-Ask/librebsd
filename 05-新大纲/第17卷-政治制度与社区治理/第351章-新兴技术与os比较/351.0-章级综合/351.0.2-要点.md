# 351.0.2 要点

- NetBSD 项目各团队面临的批评——Core Team 封闭性比 FreeBSD 更甚，Core Team 成员长期稳定，新人进入极难，决策几乎完全在内部达成，社区参与度低；pkgsrc 管理僵化，pkgsrc 核心团队对新包提交与现有包更新的审查严格且缓慢，贡献者常因格式问题而非技术问题被拒，打击积极性；安全团队响应迟缓，NetBSD 安全公告（NetBSD Security Advisories）数量少于 FreeBSD 与 OpenBSD，部分漏洞长期未修复，被批评为“安全优先级低”［存疑脚注：批评性统计断言，须以 NetBSD 安全公告存档核验］；文档团队人手不足，NetBSD 指南（NetBSD Guide）更新滞后，多语言翻译几乎停滞；基础设施团队资源有限，邮件列表、CVS/SVN 仓库、Bugzilla 等服务常出现中断，镜像站覆盖不足
- OpenBSD 项目各团队面临的批评——Theo de Raadt（西奥·德·若特） 个人主导整个项目，技术决策、人事任免、资金分配均由 Theo 最终决定，缺乏制度化的集体决策机制，“仁慈的独裁者”模式比 Linux 的 Linus 模式更集中；开发团队排外，外部贡献者提交的补丁常被公开斥责，Theo 的批评风格以直接、尖锐著称，部分贡献者因无法忍受而离开，社区被批评为“有毒”；文档团队风格傲慢，OpenBSD 手册页（man pages）虽以质量高著称，但 FAQ 与新手文档对初学者不友好，常以“读手册”回应简单问题，RTFM 文化比 FreeBSD 更甚；安全团队的“安全至上”理念被批评为走极端，为了安全牺牲过多功能性与性能，导致 OpenBSD 适用场景受限；翻译团队几乎不存在，多语言支持极差，非英语用户难以参与
- DragonFly BSD 项目因规模远小于 FreeBSD、NetBSD、OpenBSD，面临独特的团队批评——核心团队规模极小，长期由 Matt Dillon 主导，核心开发者数量不足十人，公交因子（bus factor）极低［存疑脚注：核心团队规模统计断言，须以项目 committer 名册核验］，一旦核心成员离开项目可能难以为继；团队结构单一，缺乏正式的分工体系，Core Team、安全团队、文档团队等职能边界模糊，往往由同一批人身兼数职；社区互动不足，DragonFly BSD 用户与开发者基数小，邮件列表流量低，论坛与 IRC 活跃度不高，新用户难以获得及时帮助；文档团队力量薄弱，DragonFly BSD 手册与 Wiki 内容相对简略，新手指南不完善，上手难度高于 FreeBSD；Ports/DragonFly dports 团队人手不足，dports（DragonFly Ports）基于 FreeBSD Ports，但维护者少，更新滞后，软件包数量远少于 FreeBSD
- 三大 BSD 各团队批评的史料辨析须基于——各项目官方邮件列表存档（一手）；各项目官方团队页面与公开报告（一手）；外部开发者与研究者的评论与论文（二手）；跨项目比较研究（二手，但有助于把握全局）；用户文章关于三大 BSD 团队批评的论述须按 0 信任原则考据；须警惕“以偏概全”——个别案例不能代表整个团队，个别团队的问题不能代表整个项目；须注意比较的公平性——项目规模不同，团队面临的资源约束不同，不宜用同一标准衡量
- 反批评者认为，NetBSD Core Team 的“保守”保证了跨平台移植的稳定性——NetBSD 支持 50 余种硬件平台，保守的变更管理是跨平台兼容性的必要保障；OpenBSD 的 de Raadt“个人主导”模式虽强硬但保证了安全审计的一致性——OpenBSD 的安全声誉与 de Raadt 的强力领导密切相关，一次安全审计若由委员会主导可能无法达到同样的严格程度；DragonFly BSD 的 Dillon“单人主导”模式在小规模项目中具有效率优势——小团队不需要复杂的治理结构，单人决策减少了协调成本；各项目的治理模式是在其特定历史条件下形成的适应性选择——用统一的治理标准评判不同规模、不同目标的项目是不恰当的
