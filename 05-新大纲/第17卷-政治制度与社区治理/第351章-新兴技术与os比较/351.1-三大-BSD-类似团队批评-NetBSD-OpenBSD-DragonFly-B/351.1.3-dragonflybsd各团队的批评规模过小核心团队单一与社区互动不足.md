# 351.1.3 DragonFly BSD 各团队的批评：规模过小、核心团队单一与社区互动不足

  **要点**：DragonFly BSD 项目因规模远小于 FreeBSD、NetBSD、OpenBSD，面临独特的团队批评——核心团队规模极小，长期由 Matt Dillon 主导，核心开发者数量不足十人，公交因子（bus factor）极低，一旦核心成员离开项目可能难以为继；团队结构单一，缺乏正式的分工体系，Core Team、安全团队、文档团队等职能边界模糊，往往由同一批人身兼数职；社区互动不足，DragonFly BSD 用户与开发者基数小，邮件列表流量低，论坛与 IRC 活跃度不高，新用户难以获得及时帮助；文档团队力量薄弱，DragonFly BSD 手册与 Wiki 内容相对简略，新手指南不完善，上手难度高于 FreeBSD；Ports/DragonFly dports 团队人手不足，dports（DragonFly Ports）基于 FreeBSD Ports，但维护者少，更新滞后，软件包数量远少于 FreeBSD
  **史料**：DragonFly BSD 开发者名单与 commit 统计；dragonfly-kernel、dragonfly-users 邮件列表存档；dports 提交记录；DragonFly BSD Wiki 与手册页内容统计；用户对 DragonFly BSD 社区的反馈 ［A］
  **史观**：总纲第 8 条——本体论上各方平等，小规模社区的生存困境是 BSD 谱系内部分化的结果；总纲第 4 条——分离聚合是永恒规律，DragonFly BSD 作为 BSD 谱系的“小众分支”，其存在本身就是分离聚合循环的体现
  **辨析**：“规模过小”是 DragonFly BSD 的选择（坚持技术方向而非追求规模）还是无奈结果须区分；核心团队单一与 Matt Dillon 个人能力的关系——Dillon 作为主要设计者与实现者，其高度参与是项目优势还是风险须辩证看待；社区互动不足与用户基数小互为因果，不宜简单归因于团队态度
  **文献**：DragonFly BSD 开发者页面；邮件列表存档；dports 统计；Wiki 与手册；用户反馈 ［A］
