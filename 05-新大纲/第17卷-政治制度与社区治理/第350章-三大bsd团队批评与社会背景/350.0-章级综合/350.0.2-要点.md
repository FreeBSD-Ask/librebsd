# 350.0.2 要点

- FreeBSD Core Team 作为项目最高治理机构，长期面临以下批评——决策过程不透明，多数讨论在闭门会议或受限的 freebsd-core 邮件列表中进行，普通 committer 与公众难以知晓决策背景；代表性不足，Core Team 成员地理分布集中于北美与欧洲，亚洲、南美、非洲代表性薄弱；选举制度的“小圈子循环”问题，候选人多为现任 Core Team 成员提名或背书，新人难以进入；任期无限制导致部分成员长期任职，形成“老男孩俱乐部”（old boys' club）氛围；2020 年行为准则引入前后 Core Team 内部派系化加剧，部分决策被指服务于派系利益而非项目整体利益；参见相关章节 Core Team 选举制度部分与外部批评部分
- FreeBSD 安全团队（Security Officer Team，由 Security Officer 及其副手组成）长期面临以下批评——安全漏洞披露流程迟缓，部分高危漏洞从发现到公告间隔数周甚至数月，与 OpenBSD 的快速响应形成对比；安全公告（FreeBSD Security Advisories）信息不完整，部分公告对漏洞影响范围、利用条件、修复方案的描述过于简略，系统管理员难以评估风险；漏洞响应优先级存在争议，核心组件（如内核、网络栈）的漏洞响应较快，但 Ports 系统中第三方软件的漏洞响应迟缓，大量 Port 漏洞长期未修复；安全团队成员数量不足，长期由少数志愿者承担高强度工作，导致响应能力受限；参见相关章节安全团队部分与 FreeBSD 安全模型部分
- FreeBSD Ports 管理团队（Port Management Team，简称 portmgr）长期面临以下批评——Ports 树更新滞后于上游版本，部分热门软件（如 Node.js、Python、Rust 工具链）的 Port 更新晚于上游数周甚至数月；Port 质量参差不齐，部分 Port 长期无人维护，存在编译失败、功能缺失、安全漏洞等问题；维护者流失严重，大量 Port 处于“orphan”（无维护者）状态，新维护者招募困难；portmgr 对 Port 提交的审查标准不一致，部分提交快速通过，部分提交长期积压；Ports 系统架构陈旧，仍基于 Makefile 与 patches 的传统模式，与现代软件包管理系统（如 dpkg、rpm、Nix）相比缺乏原子升级、回滚等功能；参见相关章节 FreeBSD Ports 部分与社区发展史部分
- FreeBSD 文档工程团队（Documentation Engineering Team，简称 doceng）长期面临以下批评——FreeBSD Handbook 更新停滞，部分章节内容停留在 FreeBSD 12.x/13.x 时代，新特性（如 OpenZFS 2.x 新功能、boot  loader 改进）未及时文档化；多语言翻译项目近乎荒废，中文、日文、俄文、德文、西班牙文等翻译版本严重滞后于英文原版，部分语言的翻译停留在 FreeBSD 7.x/8.x 时代；文档工具链过于复杂，基于 DocBook + Hugo + Git 的构建流程门槛高，新贡献者难以参与；文档与代码的同步机制缺失，代码变更后文档往往不更新，导致文档与实际功能脱节；参见相关章节 FreeBSD 文档项目的事实搁置部分与文档贡献者相关内容部分
- FreeBSD 集群管理团队（Cluster Administration Team，简称 clusteradm）负责运维 FreeBSD 项目的基础设施（包括 git 仓库、邮件列表、Bugzilla、CI 系统、镜像站、www 站点等），长期面临以下批评——基础设施不稳定，邮件列表、Bugzilla、CI 系统等服务中断频发，影响开发效率；服务中断后的通报不及时、不透明，用户往往通过社交媒体才得知服务故障，官方公告滞后数小时甚至数天；基础设施升级计划缺乏公开讨论，部分升级（如 SVN 转 Git、Bugzilla 迁移）过程中出现意外宕机；镜像站管理不善，部分镜像同步延迟高、部分地区镜像覆盖不足；集群管理团队成员数量少，长期由少数志愿者承担运维工作，响应能力受限
