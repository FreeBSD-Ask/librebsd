# 404.4.4 32.3 【Linux社区】Maintainer's Guide 与维护者峰会初拟议程（12 例）

**要点（判定表逐字）**：Theodore Ts'o 发布 Maintainer's Summit 初拟议程（回归追踪、炮轰维护者、Android 内核、Linus 喜恶等），附录列候选议题与出席者名单（含 Linus、Greg KH、Leemhuis 等）；Rafael Wysocki 表示此议程与全部维护者切身相关，特别点名欲参与回归追踪、缺陷报告闭环、驱动版本、跨区开发与 ABI 特性门等议题；Jiri Kosina 就 11:30 与 12:00 空档投票，首选缺陷报告闭环（因各大发行版将有代表在场）与 ABI 特性门两项；Takashi Iwai 主张将缺陷报告与回归追踪两场合并（实务上紧密相联），并投票将跨内核区开发、ABI 特性门填入空档；James Bottomley 追加三议题——git 树脚本对齐（可否由 kernel.org 统管通知）、trivial 补丁政策（OpenStack 已生厌）、优雅 rebase 之界定（尤其为 stable 干净回退）；Josh Poimboeuf 倡议编纂 Maintainer's Guide，将分支管理、合并冲突、rebase、pull、跨树改动等口耳相传的 tribal knowledge 成文，助新维护者并凝聚共识；Jonathan Corbet 呼应 Maintainer's Guide 之议，透露他处亦在酝酿，并提议以“如何避免 pull request 被骂”为起点（此处理已有相当共识且易错）；Josh Poimboeuf 赞同 Corbet，戏称既能就数百万行代码达成共识、想必也能就小流程文档达成一致，并问是否需设维护者专用邮件列表；James Bottomley 论接受 pull request 即表达信任关系、其形成机制记载不详，Linus 之要求虽见于 git-request-pull 但各树不一，被骂缘由从合并窗口外太多补丁到历史不净皆有；Josh Poimboeuf 回 Bottomley，称其每句所言皆宜成文，单句即可扩为段落或章节纳入指南；Linus Walleij 举 Documentation/driver-model/design-patterns.txt 与 Rusty Russell 的 API 设计宣言为例，坦言难辨共识（如 include 逆圣诞树、u8 之争），并赞 Documentation/process 中 management-style.rst；Mark Brown 就 git 树脚本对齐忆及往昔讨论，担忧脚本单一化（monoculture）会放大问题且各工作流差异本就造成麻烦
