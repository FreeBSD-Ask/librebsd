## 301.5.1 Apache 软件基金会 1999 年成立

  **要点**：Apache 软件基金会（ASF）于 1999 年 3 月成立，前身是 1995 年的 Apache Group（Brian Behlendorf（布莱恩·贝伦多夫）、Cliff Skolnick 等维护 NCSA HTTPd 衍生的 Apache 服务器）；ASF 组织模式借鉴 BSD 精英评审模式（committer、PMC、member 三层）；ASF 是除 FSF 与 OSI 外最具影响力的开源组织
  **史料**：ASF 1999 年成立公告、Apache Group 历史、Behlendorf 访谈 ［B］
  **史观**：BSD 与 UNIX 谱系的连续性，Apache 继承 BSD 开源传统
  **辨析**：ASF 是否真借鉴 BSD 模式，需查早期组织文档

## 301.5.3 Apache 对 BSD 开源传统的继承与演进

  **要点**：Apache 对 BSD 开源传统的继承：(1) 宽松许可证哲学；(2) 精英评审模式（committer/PMC/member）；(3) 基金会治理（轻治理）；Apache 对传统的发展：(1) 加入专利授权；(2) 项目孵化器（Incubator）；(3) 项目独立治理（每个顶级项目独立 PMC）；Apache 模式成为现代开源基金会的主流范式

## 301.5.4 Apache 项目生态与 BSD 系统的交织

  **要点**：Apache 项目生态与 BSD 系统的交织：(1) Apache HTTP Server 长期是 FreeBSD 默认 Web 服务器；(2) Yahoo! 早期 FreeBSD + Apache 是典型组合；(3) FreeBSD Ports 中 Apache 项目占重要位置；(4) Apache 项目大量在 BSD 系统上开发与测试
  **史料**：FreeBSD Ports、Apache 邮件；freebsd.duckdb freebsd-ports 仓库 1997 年起即有 Apache 相关 commit：1997-08-16 Andreas Klemm commit `f48f4dcfd107`（"libRSAglue.a is needed to build apache-ssl port. Added it to the post-install target in ports Makefile. Updated PLIST"）证明 1997 年 8 月 FreeBSD ports 已含 apache-ssl 端口；1997-08-25 Andrey A. Chernov commit `c9a02a1c285c`（"Do not replace Apache md5 with FreeBSD one, it cause support problems and gains almost nothing"）与 `7ec41b024f2d`（同主题 PR 4380）反映早期 Apache 与 FreeBSD 集成的工程问题——FreeBSD 开发者曾尝试用 FreeBSD md5 替换 Apache md5 但被驳回，反映 Apache 在 FreeBSD ports 中的独立性 ［A］
  **史观**：边缘者的作用，BSD 系统作为 Apache 开发平台
  **辨析**：freebsd.duckdb freebsd-ports 仓库 1997 年的 Apache commit 显示二者交织的起始时间早于 Apache 软件基金会 1999 年成立，证明 FreeBSD ports 是 Apache HTTP Server 早期分发与维护的重要平台之一；交织是双向但不对称的——FreeBSD ports 为 Apache 提供分发渠道与平台适配修复，Apache 项目本身则未特别针对 FreeBSD 优化；0 信任原则适用说明：commit message 中的 “PR 4380” 为 FreeBSD GNATS 问题跟踪系统编号，须与 GNATS 数据库交叉验证；1997 年的 commit 经历 CVS-to-SVN（2008）与 SVN-to-Git（2020）两次迁移，commit_hash 已重算，但 committer_date 与 author 信息应保持一致

**要点**：

- Covalent 的商业模式：八年来支持 Apache 软件基金会技术（Apache Web Server、Tomcat、Axis 网络服务框架，并新近支持 Geronimo），将免费获取的软件引入内部 QA 与测试实验室制成认证构建与安装器，向企业出售支持计划——技术支持、可检索知识库、保证缺陷修复的服务等级协议，以及传统开源世界不提供的产品赔偿（针对专利与版权侵权的 indemnification）；其可行的关键在于所支持的每个项目内部均有本公司代码提交者。（BSDTalk EP34，[114.82-244.0]，L1）
- Covalent 的工程实践：全部代码直接取自 ASF 分支、不维护自有版本控制分支；工程师对所支持项目拥有直接提交权，白天工作与夜间激情合一，此前在 Sun 或 IBM 时开源只是副业；发布纪律上宁等稳定——当前分发 Tomcat 5.5.9 而 ASF 最新为 5.5.16，因其判定后者尚不稳定、一级缺陷未清；选择支持对象的诀窍是选企业必需、正在使用且稳健成熟的技术，过早介入不成熟项目会令支持生意亏本。（BSDTalk EP34，[927.58-1136.54]，L1）
- 应用服务器格局与开源 Java：JBoss 极为成功且 Covalent 与之保持伙伴关系；Apache Geronimo 于 2006 年 1 月获 J2EE 认证，为可增删模块的轻量容器，与 JBoss 的分野核心在许可证——对 ISV 与惧怕改动 JBoss 代码的企业而言 Apache 许可几乎是不二之选；IBM、BEA、Oracle、Novell 均已嵌入 Apache 技术，若这些技术采用 GPL 它们将转而自行重写；Java 运行时许可须向 Sun、HP、IBM 分别获取，ASF 内孵化中的 Harmony 项目（以 Apache 类许可发布全套 JDK 与运行时）一旦认证完成，Geronimo 与 JBoss 都可能采纳。（BSDTalk EP34，[639.34-927.58]，L1）
- BSD 企业需求下滑的供给侧证词：Covalent 曾支持 BSD 平台，如今发布仅覆盖 Windows、IBM AIX、Solaris、HP-UX 与各发行版 Linux 六类平台（32 与 64 位），BSD 因需求下降而退出产品线，仅剩个别客户由其代为构建；当事人推测主因是 Linux 在财富千强级别大型商业企业中迅速崛起，而这恰是 Covalent 客户基所在；若有大客户重新采用，公司有能力随时恢复 BSD 支持。 [存疑脚注] 当事人对 BSD 需求下滑原因仅为推测性归因（Linux 在其客户群崛起），非系统市场研究结论（BSDTalk EP34，[1232.76-1300.72]，L1）

**史料**：

- 主持人开场转述的 2006 年 4 月 BSD 社区动态：FreeBSD 与 NetBSD 发布首季度报告；OpenBSD 获得 Mozilla Foundation 与 GoDaddy 各一万美元的捐赠，捐赠随 BSDCan 2006（5 月 12 至 13 日于加拿大举行）临近而受到关注；此与同期其他访谈提及的 Mozilla 万元捐赠互证。（BSDTalk EP34，[39.8-80.98]，L2）

**史观**：

- 总纲3 不存在进步，只有权力再分配：当事人观察开源商业价值的迁移：过去客户选择开源主要为价格（Web 服务器还有经证明的稳定性与安全性），而近两年驱动因素转为创新——开源项目产出专有厂商尚未提供的尖端技术，企业对开源的期待已超越商品化的旧技术，并愿意为创新付费获取支持；ASF 自身从两三年前仅三四个主力项目扩张到约三十个可用项目加三四十个孵化项目，Covalent 参与其中四个孵化项目，开源生态正从成本替代品转为创新来源地。（BSDTalk EP34，[1145.26-1368.28]，L1）

**辨析**：

- 宽松许可证的回馈压力自述：Apache 与 BSD 系许可允许对软件做任何改动并以商业许可再授权，这既是其慷慨之美，也带来双重诱惑——外部软件商将 Apache 项目加值写成专有附加组件转售，公司内部亦有“加一点专有功能即可多收支持费”的声音；Covalent 约在访谈前两年半做出有意识决定，早期曾以 Apache 相关专有附加组件盈利，此后一切构建全部回馈相应项目；当事人承认 BSD 或 Apache 许可并不确保增强回到社区。（BSDTalk EP34，[368.54-458.8]，L1）
- 当事人对 GPL 的两面评价：先替 GPL 辩护——GPL 与 LGPL 确保项目不分叉、防止公司拿软件改动牟利而不回馈社区，这正是其原则；随后指出其负面——SAP、Oracle 等 ISV 因修改须交回社区且无法以商业许可授权自建产品而回避嵌入任何 GPL 代码（只保证产品与 Linux、JBoss 等并存运行），财富千强中非软件企业则担心工程师改动源码后在现行 GPL 下是否构成衍生作品并不清晰，GPLv3 有望对此作出更清楚的界定。（BSDTalk EP34，[480.28-636.34]，L1）
