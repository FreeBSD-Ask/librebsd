# 222.2.6 要点7x周期OpenBSD对CPU与GPU硬件漏洞的响应体现快速跟进不等待上游的

**要点**：7.x 周期 OpenBSD 对 CPU 与 GPU 硬件漏洞的响应体现 “快速跟进—不等待上游” 的工程态度——**2024 年 3 月 17 日** guenther 提交 `6651c3e51fb0` 使用 VERW 指令缓解 RFDS（Register File Data Sampling）漏洞，针对 Intel Atom CPU；**2023 年 11 月 30 日** jsg 提交 `995354c8e016` 修复 drm/i915 潜在 Spectre 漏洞；**2025 年 8 月 29 日** jsg 提交 `09cdb8b5b4d2` 修复 drm/amd display NULL 指针解引用；**2026 年 6 月 10 日** jsg 提交 `a7f980a291d7` 修复 drm/amdkfd 整数溢出；**2026 年 6 月 23 日** kettenis 提交 `be56f357d439` 修复 CVE-2025-10263（TLB invalidation 需执行两次）——这是 7.x 周期少数有 CVE 编号的硬件相关漏洞；此外 **2023 年 10 月 8 日** deraadt 提交 `649efdcfafb1` 调整 release 节奏（"move release a earlier. when we wait for security fixes from one piece of software, another one will..."），反映 OpenBSD 将发布周期与安全修复节奏挂钩的工程决策

**史观**：总纲第 7 条——硬件与软件辩证：7.x 周期 OpenBSD 硬件安全响应的特征与 6.x 周期 “集中爆发期” 根本不同——6.x 周期 Spectre/Meltdown/MDS 三大 CPU 漏洞族集中爆发，OpenBSD 通过预防性禁用超线程与一系列软件缓解回应；7.x 周期 CPU 漏洞进入 “长尾跟进期”，RFDS（CVE-2023-28646）与 TLB invalidation（CVE-2025-10263）是 6.x 周期集中爆发后的延续性发现，OpenBSD 的响应节奏从 “应急缓解” 转为 “成熟跟进”；7.x 周期新出现的 drm/i915、drm/amd、drm/amdkfd GPU 驱动漏洞反映 OpenBSD 从 Linux 内核移植 drm 子系统后的持续维护负担——这些漏洞多数有 Linux 内核对应修复，jsg 的 commit 是将 Linux 修复回溯至 OpenBSD drm 移植版本，反映 “硬件驱动代码的跨项目维护” 是 7.x 周期的新工程问题；deraadt 调整 release 节奏（“等待某一软件安全修复时另一软件会出现新问题”）反映 OpenBSD 将 6 个月固定发布周期与安全修复节奏挂钩——这一工程决策在 6.x 周期未见明显记录，是 7.x 周期 OpenBSD 安全治理成熟化的新现象

**辨析**：**须精确说明 RFDS 漏洞的技术背景**：RFDS（Register File Data Sampling）是 Intel Atom 系列处理器的侧信道漏洞，CVE 编号为 CVE-2023-28646 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］，guenther 使用 VERW 指令（Verify User Write）作为缓解——VERW 会刷新缓冲区，防止攻击者通过寄存器文件采样获取敏感数据；**与 Linux/FreeBSD 对比的辨析**：Linux 内核对 RFDS 的缓解同样使用 VERW，但 OpenBSD 实现独立（不引用 Linux commit），FreeBSD 14.x 周期是否有对应 RFDS 缓解 commit 须以 freebsd-src 仓库搜索为准 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］；**drm 漏洞的性质**：drm（Direct Rendering Manager）漏洞位于 GPU 驱动层，jsg 的 drm/i915、drm/amd、drm/amdkfd 修复是 OpenBSD 从 Linux 内核移植 drm 子系统后的持续维护——这些漏洞多数有 Linux 内核对应修复，jsg 的 commit 是将 Linux 修复回溯至 OpenBSD drm 移植版本；**release 节奏调整的辨析**：deraadt 的 `649efdcfafb1` commit 表明 OpenBSD 将发布周期与安全修复节奏挂钩——“当我们等待某一软件的安全修复时，另一软件会出现新问题”，这一哲学解释了 OpenBSD 6 个月固定发布周期的合理性（不因单一组件延迟而阻塞整体发布）
