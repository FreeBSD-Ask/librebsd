# 220.2.6 libexpat/perl 等第三方库治理——“跟随上游—批量回溯”工作流的早期形态

**要点**：6.x 周期 libexpat 与 perl 是两大第三方库 CVE 来源——libexpat 由 bluhm 通过“Update libexpat to version X”形式的批量 vendor import 修复，**2017 年 6 月 30 日** bluhm commit `2feb5d2a36a7` 一次性修复 CVE-2012-0876、CVE-2012-6702、CVE-2015-1283、CVE-2015-2716、CVE-2016-0718、CVE-2017-9233 等 9 个 CVE（升级至 libexpat 2.2.1），**2019 年 6 月 29 日** bluhm commit `04da35325a0b` 修复 CVE-2018-20843（升级至 2.2.7），**2019 年 9 月 10 日** bluhm commit `94f813b1ac19` 修复 CVE-2019-15903 堆溢出，**2019 年 9 月 25 日** bluhm commit `28ce31191121` 升级至 2.2.8；perl 由 afresh1 修复，**2017 年 9 月 22 日** afresh1 commit `bc7b845e7aa7` 修复 CVE-2017-12837 与 CVE-2017-12883（正则表达式缓冲区过读与堆溢出），**2018 年 4 月 14 日** afresh1 commit `24ada909ab1e` 修复 CVE-2018-6797、CVE-2018-6798、CVE-2018-6913（堆溢出），**2018 年 6 月 19 日** afresh1 commit `26f75d2d572a` 修复 CVE-2018-12015（Archive:: Tar 目录遍历），**2018 年 11 月 29 日** afresh1 commit `b3b446fd892e` 修复 CVE-2018-18311/18312/18313/18314 四个溢出；bluhm 与 afresh1 的“批量 vendor import”工作流是 7.x 周期 libexpat 治理模式的早期形态——不逐个 CVE 修复，而是同步上游版本一次性清理积压

**史料**：**openbsd.duckdb** `commits` 表 openbsd-src 仓库 6.x 周期 libexpat 与 perl 相关 CVE commit 查询：

  ```sql
  SELECT commit_hash, author_date, author_name, message_subject
  FROM commits
  WHERE repo_name='openbsd-src'
    AND author_date>=‘2016-09-01’
    AND author_date<‘2019-10-01’
    AND (message_subject LIKE ‘%libexpat%’ OR message_subject LIKE ‘%expat%’
         OR (message_subject LIKE ‘%perl%’
             AND (message_body LIKE '%CVE-%' OR message_subject LIKE '%CVE-%')))
  ORDER BY author_date ASC
  ```

  ；bluhm 的 libexpat 2.2.1 升级 commit `2feb5d2a36a7`（一次修复 9 个 CVE）；afresh1 的 perl CVE 修复 commit 序列（`bc7b845e7aa7`、`24ada909ab1e`、`26f75d2d572a`、`b3b446fd892e`）；6.4 errata 024_expat.patch（CVE-2019-15903 libexpat 2.2.6 堆溢出修复）；6.9 errata 026/029/031_expat.patch（libexpat 批量 CVE 修复） ［A］

**史观**：专题语（不设总纲条号）——安全工程的演进（原挂总纲第 17 条系伪名目，删条号）：libexpat 与 perl 的“批量 vendor import”工作流反映 OpenBSD 对第三方库安全债务的治理哲学——以“跟随上游版本而非逐个 patch 回溯”为预设，将第三方库的 CVE 清算效率最大化；bluhm 的 libexpat 2.2.1 升级一次修复 9 个 CVE 是这一工作流的典型样本——其中 CVE-2012-0876 与 CVE-2012-6702 是 2012 年的 CVE，积压 5 年才通过版本升级一次性清理；这一模式在 7.x 周期延续并成熟，bluhm 在 7.x 周期继续以“Update libexpat to version X”模板化 commit 维护 libexpat

**辨析**：**须精确说明 libexpat 在 OpenBSD base 中的角色**：libexpat 是 XML 解析库，被 OpenBSD base 中多个组件依赖，但 libexpat 本身是上游独立项目（由 Google 维护）；OpenBSD 不 fork libexpat（与 LibreSSL 不同），而是直接 vendor import 上游版本——这代表 OpenBSD 对第三方库的两种不同治理策略：LibreSSL 是“独立 fork”（自主维护），libexpat 是“跟随上游”（vendor import）；**bluhm 一次修复 9 个 CVE 的辨析**：`2feb5d2a36a7`（2017-06-30）的 commit subject 为"Update libexpat to version 2.2.1 which has some security fixes"，message body 列出 CVE-2017-9233 等 CVE——9 个 CVE 中部分是 2012 年与 2015 年的旧 CVE，通过版本升级一次性清理，反映 OpenBSD 对第三方库 CVE 积压的“周期性清算”而非“即时修复”策略；**与 FreeBSD Heimdal 清理对比**：FreeBSD 14.x 周期 Heimdal CVE 集中清理（2024-02-14/15 两天 6 个 CVE，积压 7 年）与 OpenBSD 6.x 周期 libexpat 批量升级（2017-06-30 一次 9 个 CVE，积压 5 年）在工程模式上同构——均为“积压后集中清算”
