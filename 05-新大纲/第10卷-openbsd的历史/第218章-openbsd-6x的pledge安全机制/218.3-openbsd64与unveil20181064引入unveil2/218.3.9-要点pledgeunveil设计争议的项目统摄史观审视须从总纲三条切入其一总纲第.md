# 218.3.9 要点pledgeunveil设计争议的项目统摄史观审视须从总纲三条切入其一总纲第

**要点**：pledge/unveil 设计争议的项目统摄史观审视须从总纲三条切入——其一，总纲第 13 条“法律与道德是利益分配”映射：pledge/unveil 的“简洁正确性”叙事不仅是技术论证也是 OpenBSD 项目身份建构的政治产物，社区对 pledge 的辩护中混合了技术判断（粗粒度降低配置错误）与道德判断（“正确使用简单机制优于错误使用复杂机制”），后者本质是将 OpenBSD 工程哲学包装为道德优越，这一包装在社区治理中转化为对批评者的边缘化（misc@ 邮件列表中 pledge 批评者常被斥为“未理解 OpenBSD 哲学”），印证“社区治理亦是形式主义的政治产物”；其二，总纲第 19 条“解释学循环是历史认识的根本条件”映射：pledge/unveil 与 seccomp 的优劣评估受前理解差异制约——OpenBSD 阵营以“简洁即正确”为前理解，Linux 阵营以“细粒度即安全”为前理解，二者难以通约；同时，权力与知识在历史书写中共谋——pledge/unveil 的设计被 OpenBSD 官方文档与 de Raadt 公开声明塑造为“安全机制的正确方向”，而 seccomp-bpf 的复杂性被叙述为“Linux 的工程包袱”，这一叙述本身是 OpenBSD 阵营的权力行使，什么被记录为“正确设计”、什么被记录为“复杂包袱”，本身就是权力与知识的共谋；其三，总纲第 21 条“革命与改革是历史方法论的分歧”映射：pledge 是改革式路径——基于现有系统调用接口新增 `pledge()` 与 `unveil()` 两个调用，不改变内核架构，渐进式扩展覆盖范围（自 5.9 起逐 release 增加 base system 工具的 pledge 覆盖），seccomp-bpf 是革命式路径——引入 BPF 虚拟机作为内核内过滤器，改变了系统调用入口的执行模型，landlock 是另一改革式路径——基于现有路径解析机制新增安全模块；OpenBSD 选择 pledge 这一改革式路径与其在 LibreSSL、vmm 等子系统上的改革式选择一致，印证“BSD 靠改革”的方法论连续性，但改革的困难远高于革命——pledge 须逐个工具适配，覆盖范围扩展缓慢，而 seccomp-bpf 一经引入即可全局适用，“破山中贼易，破心中贼难”在 pledge 语境下体现为：技术机制（山中贼）易建，但让所有应用自觉采用（心中贼）难

**史料**：项目史观总纲第 13、19、21 条原文（原材料/哲学/项目统摄史观/第 25 章.md）；de Raadt 在 misc@ 关于 pledge 设计哲学与对批评者回应的发言（<https://marc.info/?laccopenbsd-misc>）；OpenBSD **pledge(2)** 手册页 HISTORY 段（记录 pledge 自 5.9 起的覆盖扩展）；Linux seccomp-bpf 设计文档与 landlock 设计文档；openbsd.duckdb openbsd-src 仓库 pledge 覆盖扩展 commit（usr.bin/ 路径下逐工具增加 `pledge()` 调用的 commit） ［A］

**史观**：总纲第 13 条——法律与道德是利益分配：pledge/unveil 的“简洁正确性”叙事是 OpenBSD 项目身份建构的政治产物，社区对批评者的边缘化是社区治理的政治行使；总纲第 19 条——解释学循环：pledge/unveil 与 seccomp 的优劣评估受前理解差异制约，权力与知识在“何为正确安全设计”的历史书写中共谋；总纲第 21 条——革命与改革是历史方法论的分歧：pledge 是改革式路径（新增系统调用、渐进扩展覆盖），seccomp-bpf 是革命式路径（引入 BPF 虚拟机改变执行模型），OpenBSD 选择改革式路径与其在 LibreSSL、vmm 等子系统上的选择一致，印证“BSD 靠改革”的方法论连续性

**辨析**：哲学审视的合理性须以三个层面交叉验证——【0 信任原则·道德包装论证的辨析】“pledge 辩护混合技术判断与道德判断”论证须对照 misc@ 邮件列表原文核实——若辩护文本仅含技术论证（如“粗粒度降低配置错误率”），不得人为添加道德判断成分，须以具体文本为据；【0 信任原则·权力-知识共谋的可证伪性】“pledge 被塑造为正确方向、seccomp 被叙述为包袱”论证须对照 OpenBSD 官方文档与第三方独立评估的差异——若第三方独立评估同样肯定 pledge 的工程价值，则“权力共谋”论证须重新审视；【0 信任原则·改革与革命路径的辨析】“pledge 是改革、seccomp 是革命”分类须对照二者的实际工程变更——pledge 新增了 `pledge()` 与 `unveil()` 两个系统调用并引入 `kern_pledge` 与 `kern_unveil` 内核子系统，这一变更幅度并非纯粹“改革”（亦包含新子系统的引入），seccomp-bpf 引入 BPF 虚机但 BPF 自 Linux 2.6.25（2008）已存在，seccomp-bpf 是对既有 BPF 的复用而非全新引入，故“革命 vs 改革”的二分须谨慎；【多源交叉验证不可靠性规则】多个 OpenBSD 阵营对 pledge 哲学优越性的论证在多处一致，但这一一致性可能源于社区共同立场而非独立验证，须以第三方独立安全研究交叉验证
