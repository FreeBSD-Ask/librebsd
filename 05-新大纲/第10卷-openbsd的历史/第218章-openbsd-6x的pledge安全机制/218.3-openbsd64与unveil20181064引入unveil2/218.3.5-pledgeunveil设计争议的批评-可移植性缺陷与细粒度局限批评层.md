# 218.3.5 pledge/unveil 设计争议的批评——可移植性缺陷与细粒度局限（批评层）

**要点**：对 pledge/unveil 机制设计局限的批评集中于四点——其一，pledge 与 unveil 仅限 OpenBSD，无法移植至 Linux 或 FreeBSD，跨平台应用若欲使用须为 OpenBSD 单独维护一份代码分支，采用门槛过高，与 seccomp 自 Linux 2.6.12（2005）后普遍可用、Capsicum 自 FreeBSD 9.0（2012）后随系统发布的跨发行版可达性形成对照；其二，pledge 采用粗粒度类别（如 `stdio`、`rpath`、`wpath`、`inet`），无法对单一系统调用进行过滤，更无法基于系统调用参数过滤，而 seccomp-bpf 可针对单系统调用及其参数进行细粒度过滤，Capsicum 可对单个文件描述符授予细粒度能力，pledge 在过滤精度上明显落后；其三，pledge 与 unveil 均为自愿模型（voluntary model），须由程序员显式调用 `pledge()` 或 `unveil()` 方能生效，对未调用这两个接口的代码无任何防护作用，攻击者注入的代码可径直绕过 pledge 限制，而 seccomp 可由系统管理员通过 `PR_SET_SECCOMP` 全局强制启用，不受应用自愿与否约束；其四，unveil 一旦调用 `unveil(path, NULL)` 即锁定后续 unveil 调用为无效，这一“锁定即不可逆”设计在需要动态揭示路径的场景下缺乏灵活性，与 Linux landlock 可动态调整路径限制的设计形成对照

**史料**：Linux seccomp 文档（<https://www.kernel.org/doc/html/latest/userspace-api/seccomp_filter.html>）；FreeBSD Capsicum 文档（<https://www.freebsd.org/cgi/man.cgi?query=capsicum>）；OpenBSD **pledge(2)** 手册页（<https://man.openbsd.org/pledge.2>）与 **unveil(2)** 手册页（<https://man.openbsd.org/unveil.2>）；Linux landlock 文档（<https://docs.kernel.org/userspace-api/landlock.html>）；pledge 可移植性批评的公开讨论（<https://marc.info/?laccopenbsd-misc>） ［A］

**史观**：商业与社区的张力：pledge/unveil 的可移植性缺陷使该机制的实际受益者局限于 OpenBSD 用户，外部性（跨平台应用的额外适配成本）由整个生态承担而非 OpenBSD 独自承担；总纲第 19 条——解释学循环：pledge/unveil 评估受前理解差异制约——OpenBSD 阵营以“简洁即正确”为前理解，批评者以“细粒度即安全”为前理解，二者难以通约

**辨析**：批评的合理性在不同叙事中评估不一——部分视为有效工程批评，部分视为对 OpenBSD 简洁哲学的误读；需对照 pledge/unveil 手册页与 seccomp-bpf、Capsicum 设计文档三方核实；【0 信任原则·可移植性的量化】“跨平台应用须单独维护一份代码分支”论证须提供具体案例（如哪个开源项目在 OpenBSD 上单独维护 pledge 调用分支），否则易沦为总体性指控；【0 信任原则·细粒度局限的解读】pledge 的粗粒度类别可能是有意设计而非缺陷——粗粒度减少了配置错误的概率，seccomp-bpf 的细粒度本身带来过滤器编写复杂度高、易出错的副作用，二者须对照区分；【0 信任原则·自愿模型的辨析】“自愿模型无防护”批评须对照 pledge 的“fail-closed”语义——pledge 一旦调用即不可放宽，攻击者注入的代码无法通过再次调用 `pledge()` 放宽限制，故“自愿”仅指调用前无防护而非调用后可绕过；【多源交叉验证不可靠性规则】多个 Linux 阵营对 pledge 的批评在多处一致，但这一一致性可能源于 Linux 社区对 seccomp 的共同立场而非独立验证
