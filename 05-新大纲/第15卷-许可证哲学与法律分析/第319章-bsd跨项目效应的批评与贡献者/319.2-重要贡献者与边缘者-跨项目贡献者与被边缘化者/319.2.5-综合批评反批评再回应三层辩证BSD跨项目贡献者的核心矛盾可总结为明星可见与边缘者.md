# 319.2.5 综合批评反批评再回应三层辩证BSD跨项目贡献者的核心矛盾可总结为明星可见与边缘者

- **要点**：综合批评-反批评-再回应三层辩证，BSD 跨项目贡献者的核心矛盾可总结为“明星可见与边缘者被遗忘的辩证统一”——即 BSD 跨项目叙事中项目创始人（PHK、McKusick、Watson、Hubbard 等）因技术产出可见度高而被铭记，协助者（Berg、Nordby、DES）、连接者（Grönvall、Mewburn）、早期推动者因协调角色可见度低而被遗忘，此“明星效应”部分源于贡献性质差异（技术产出 vs 协调角色），部分源于叙事偏差。此矛盾不可“调和”——因技术产出的可见度天然高于协调角色，若要求同等可见度则忽视贡献性质差异——但可“分离聚合”——因考据程序（如 bsd_commits.duckdb 量化分析、官方历史交叉验证、邮件列表存档）可使部分被遗忘的贡献者重新归位，此“重新归位”是“明星可见”与“边缘者被遗忘”的聚合点。合图层的核心判断为：BSD 跨项目贡献者是“明星与边缘者的集合”而非“仅明星的贡献”——PHK 主持 Varnish 但 Berg 发起、Nordby 连接、DES 提出构想；Watson 主持 Capsicum 但 Moore、Sewell、Davis 等共同参与；McKusick 参与 POSIX 但 CSRG 时代的 BSD 团队共同塑造——明星与边缘者的贡献是同一项目的两面，二者各有其形式主义化的具体显现。此判断对应项目史观总纲第十章“边缘者贡献”——边缘者非“被动的受害者”而是“主动的贡献者”，考据程序使其贡献被重新发现，此“重新发现”即“边缘者归位”的具体显现。
- **史料**：Varnish Software 官方历史（Berg 发起、Nordby 连接、DES 构想、PHK 执行）；OpenSSH 官方历史（Grönvall 的 OSSH 为 fork 源头）；openbsd.duckdb 查询 L7.2.1（衍生项目贡献者回馈前 10 位，使部分“看不见的贡献者”可见）；NetBSD rc.d(8) 手册页与 Mewburn USENIX 2001 论文（Mewburn 为 rc.d 设计者）；libarchive 官网（Kientzle 创建、Matuska 接手维护）；FreeBSD Darwin CREDITS 文件（2003-2020 年间超过 200 名外部贡献者）。
- **史观**：总纲第 10 条（边缘者贡献）与总纲第 6 条（主体性与和解）。BSD 跨项目贡献者的核心即“明星可见与边缘者被遗忘的辩证统一”——明星因技术产出可见度高而被铭记，边缘者因协调角色可见度低而被遗忘，二者是同一项目的两面。项目史观总纲第十章“边缘者贡献”在此显现：边缘者非“被动的受害者”而是“主动的贡献者”，考据程序使其贡献被重新发现。
- **辨析**：考据过程留痕——【查证来源】Varnish Software 官方历史（Berg 发起、Nordby 连接、DES 构想、PHK 执行）经 varnish-software.com/varnish-history/ 一手核验；OpenSSH 官方历史（Grönvall 的 OSSH 为 fork 源头）经 openssh.org/history.html 一手核验；bsd_commits.duckdb 查询 L7.2.1（衍生项目贡献者回馈前 10 位，使部分“看不见的贡献者”可见）经 SQL 查询一手核验；NetBSD rc.d(8) 手册页与 Mewburn USENIX 2001 论文（Mewburn 为 rc.d 设计者）经 NetBSD 官方手册页与 USENIX ATC 2001 论文集双向核验；libarchive 官网（Kientzle 创建、Matuska 接手维护）经 libarchive.github.io 一手核验；FreeBSD Darwin CREDITS 文件（2003-2020 年间超过 200 名外部贡献者）经 FreeBSD 源代码仓库 CREDITS 文件核验；【交叉验证方法】Varnish Software 官方历史（项目官方记录）与 PHK/Berg/DES 三人独立自述交叉印证“明星与边缘者的角色分工是同一项目的两面”的判断；bsd_commits.duckdb L7.2.1 量化数据（衍生项目贡献者回馈前 10 位使“看不见的贡献者”可见）与 libarchive 官网采用列表（Kientzle 创建、Matuska 接手维护）交叉印证“考据程序可使部分被遗忘的贡献者重新归位”的事实层面成立；OpenSSH 官方历史（Grönvall 的 OSSH 为 fork 源头）与 NetBSD rc.d(8) 手册页（Mewburn 为 rc.d 设计者）双向印证“考据程序本身是对边缘者的重新归位”的判断；FreeBSD Darwin CREDITS 文件（2003-2020 年间超过 200 名外部贡献者）与 bsd_commits.duckdb L7.2.1 量化数据交叉印证“BSD 社区已有部分公开致谢机制”的判断；【存疑判定依据】合图层的核心判断存在两种可能的反对意见——第一种为“BSD 社区应主动公开所有贡献者以消除明星效应”，此意见在伦理层面成立（公开致谢是对贡献者的尊重）但在实践层面较难实现（部分贡献者因隐私政策无法核实完整贡献范围，且协调角色的可见度天然低于技术产出），故采信“伦理层面反对意见成立，实践层面须开发分级致谢机制”的判断；第二种为“考据程序的修复能力有限”，此意见在史料保存层面成立（部分边缘者若无史料保存则无法重新归位）但在已有史料层面不成立（Grönvall、Berg、Nordby、DES、Mewburn 均经考据重新归位），故采信“史料保存层面反对意见成立，已有史料层面反对意见不成立”的判断；0 信任原则提示：bsd_commits.duckdb L7.2.1 查询基于 author_email 字段统计，同一人使用不同邮箱会导致统计分散；查询仅覆盖 7 个衍生仓库，不含 OpenZFS/OpenSSH/LibreSSL 等独立项目的贡献者；FreeBSD Darwin CREDITS 文件的“200+ 外部贡献者”为 2003-2020 年间的累计统计，未区分长期贡献者与一次性贡献者；合图层非终结性判断，若未来 BSD 社区引入分级致谢机制或 bsd_commits.duckdb 扩展覆盖范围，合图判断须重新审视；本节合图的呈现不偏袒任何一方，明星贡献者与边缘贡献者在本体论上地位相等，史家不得以“明星可见度高”为由否定边缘者的主体性呈现，亦不得以“边缘者被遗忘”为由否定明星贡献者的技术产出

**要点**：

- 移植工程缘起：Christoph Egger 经一家以 OpenBSD 为基础出售安全产品的慕尼黑公司 Gainware 接触 OpenBSD，寻找学位论文题目时由公司选定“把 OpenBSD 移植到 Xen”；其于 2005 年 12 月从 Xen 2 起步，2006 年 XenSource 经由 Google Summer of Code 把“OpenBSD 移植到 Xen3”立项，因其已有 OpenBSD 跑在 Xen 2 上的基础而顺势承接，至受访时已在 Xen 3 上完整可用——身份是 Xen 客户机（Xen guest）而非宿主。（BSDTalk EP69，[83.32-248.96]，L1）
- Xen 技术原理：Xen 是 XenSource 开发的 hypervisor，把大型机虚拟化技术带到 PC，使多个操作系统同时高速并行；所有系统都运行在 Xen 之上，Xen 掌管硬件与 CPU，其中特权最高的 domain zero（xenhost）负责管理其余客户机。Xen 不模拟整机（那是 VMware 的全虚拟化，客户机看到的是伪造的通用硬件），而采用半虚拟化——客户机操作系统自知运行于虚拟环境并直视真实硬件，开销约 2%-3%；借助 AMD Pacifica 与 Intel VT 硬件虚拟化还可运行未经修改的客户机。版本演进上，Xen 2 仅支持 i386 且要求 i686 级 CPU，Xen 3 已扩展至 IA64、Itanium、AMD64 并在开发 PowerPC 支持，加入 ACPI 电源管理与客户机 SMP；迁移分停机迁移与动态迁移（后者 TCP 网络连接不中断），并支持运行时增删 CPU 与增减内存——前提是客户机操作系统支持相应热插拔，否则结果未定义。（BSDTalk EP69，[159.36-505.38]，L1）
- OpenBSD 客户机功能与回馈主线：其移植提供网络、块设备 I/O（磁盘与 CD-ROM）、时钟、FPU、控制台五类基础驱动，使其普通可用；自加的特别功能是网络与块设备在运行时动态挂载与卸载。工作自 OpenBSD current（彼时即 4.0）起步并持续跟进 current；移植过程暴露的缺陷已修复并被接受——其一在 TCP 栈、其一在 UVM 内存管理，均已进入 OpenBSD 3.9，后续补丁将进入 current；此举也被视为 OpenBSD 社区借 Xen 移植清理内核缺陷的集体努力，目标是进入 OpenBSD current 并希望 4.1 收录 OpenBSD/Xen；现时代码经其 GSoC 导师与其他 OpenBSD 开发者试用，进展在专门邮件列表上讨论；使用状态为家中自用与部分开发者测试，尚无生产环境用户。（BSDTalk EP69，[505.38-897.16]，L1）
- 跨项目关系与许可证立场：受访者先找 NetBSD 后经公司转入 OpenBSD，评价两者代码干净、文档优良、运行稳定且极为相似——既已互移植彼此的缺陷修复，本可更紧密合作；许可证方面，其认为 BSD 许可证不强制公司开源，是优点还是缺点取决于立场，个人对 GPL 与 BSD 均接受、认为差别不大，只有在公司语境讨论是否开放源码时才真正相关；其时已供职 AMD，公司重心在市占更大的 Linux，但研究部门仍用 BSD 以求更宽的观察面，且多位同事使用并定期阅读 BSD 动态；桌面并跑 OpenBSD、NetBSD（SPARC 与 i386）与 Solaris、Mac OS X，除 Mac 外几乎全命令行，编辑器用 VI。（BSDTalk EP69，[624.8-815.22]，L1）

**史料**：

- 本期提及的一手材料：Gainware 基于 OpenBSD 的安全产品线、XenSource 提交 Google Summer of Code 2006 的“OpenBSD 移植到 Xen3”项目、讨论 OpenBSD/Xen 进展的专门邮件列表、已进入 OpenBSD 3.9 的 TCP 栈与 UVM 缺陷修复补丁，以及 Xen 2 到 Xen 3 的版本演进本身。（BSDTalk EP69，[210.68-248.96]，L1）

**史观**：

- 总纲8 本体论上各方平等：受访者把 NetBSD 与 OpenBSD 并置为同等洁净、同源相似的两个系统，合作不足被表述为待兑现的潜力而非优劣取舍；对 GPL 与 BSD 两种许可证亦持中立接受的态度，认为差别只在商业语境中方才显现——这种对 BSD 各分支与各许可传统一视同仁的姿态，是各分支本体论平等的具体发声。（BSDTalk EP69，[645.1-706.18]，L1）

**辨析**：

- 本期标题作 Xen on OpenBSD，实际内容是把 OpenBSD 移植为 Xen 客户机，主持人中途亦自行更正为 porting OpenBSD to Xen，引用时须防方向误读；转写失真包括 Zen/Xenia/OpenBST/OpenVC 均应为 Xen/OpenBSD，XenFORCE 应为 XenSource，Ethereum 应为 Itanium，TTP IcStick 应为 TCP 栈，flat BSD 疑为 NetBSD 而“2%-3% 开销”等数字为当事人口径未经独立基准验证。 [存疑脚注] 标题与内容方向相反易误引；flat BSD 的确切所指与性能数字均待音频及基准材料核实（BSDTalk EP69，[159.36-166.12]，L5）
