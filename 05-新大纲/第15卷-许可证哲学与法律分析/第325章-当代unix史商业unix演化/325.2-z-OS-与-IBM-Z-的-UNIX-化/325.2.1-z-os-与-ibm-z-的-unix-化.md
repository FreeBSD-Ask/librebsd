# 325.2.1 z-OS-与-IBM-Z-的-UNIX-化

#### 要点

MVS/ESA（Multiple Virtual Storage/Enterprise Systems Architecture，1988 年发布）演化为 OS/390（1995 年 3 月发布，引入 OpenEdition MVS 与 UNIX System Services 雏形），2001 年 12 月 OS/390 改名 z/OS（与 z/Architecture 64 位架构同步发布）；z/OS UNIX System Services（USS）是 z/OS 内置的 UNIX 兼容环境，实现 POSIX.1-2001 与 Single UNIX Specification V3（UNIX 03）认证（z/OS 1.7 于 2006 年通过 UNIX 03 认证，是首个通过 UNIX 03 认证的大型机操作系统）。
z/OS 演化：z/OS 1.0（2001）、1.7（2005，UNIX 03 认证）、1.9（2007）、1.10（2008）、1.11（2009）、1.12（2010）、1.13（2011）、2.1（2013，引入 zEDC 压缩）、2.2（2015，引入 z/OSMF REST API）、2.3（2017，引入 z/OS Container Platform 雏形）、2.4（2019，引入 z/OS V2R4 与 z15 同步）、2.5（2021，引入 z/OS XCF HTTPS、z/OS MF 2.5）、3.1（2023，引入 z16 与 AI 加速支持）。
IBM Z 硬件演化：System/360（1964）、S/370（1970）、S/370-XA（1981，31 位地址空间）、ESA/370（1988）、S/390（1990，ES/9000）、z/Architecture（2000，64 位地址空间，z900）、z9（2005）、z10（2008）、z196（2010，5.2GHz 高频）、zEC12（2012）、z13（2015，首个支持 Hadoop 的大型机）、z14（2017，pervasive encryption 全盘加密）、z15（2019，数据隐私护照）、z16（2022，集成 AI 加速器 Telum）。
Linux on z Systems（Linux on Z，1999 年 Linus Torvalds 与 IBM 合作将 Linux 内核移植到 S/390）演化为 IBM Z 与 LinuxONE（LinuxONE 是专为 Linux 工作负载设计的 IBM Z 变体，运行 Linux 而非 z/OS）；2026 年 7 月 27 日现状：z/OS 3.1 运行于 z16 服务器（z16 DT1、z16 A02/A01），Linux on Z 主流运行 RHEL、SUSE、Ubuntu 三大发行版，IBM Z 与 LinuxONE 在银行业核心系统、政府数据中心、大型企业 ERP/SAP HANA 部署中持续主导。
z/OS 与 BSD/UNIX 的关系：z/OS USS 提供完整 POSIX API（含 fork、exec、socket、pthread），使 BSD/UNIX 软件可在 z/OS 上编译运行（需源码级修改）；FreeBSD、NetBSD、OpenBSD 均未移植至 z/Architecture，但 Debian GNU/Linux on Z 与 openSUSE on Z 提供完整开源 UNIX 生态；OpenJDK、Python、Go、Rust 等开源运行时均官方支持 Linux on Z。

#### 史观

本子节史观映射覆盖以下 5 条相关总纲，皆已回溯到 29 章原文核验：

**总纲 4（分离聚合是永恒规律）**——据原文第 4 章 4.1 节：

> “分离聚合是世界发展的规律。分久必合，合久必分，具有必然性。”

z/OS 与 UNIX 的关系典型呈现分离聚合——MVS/ESA 早期完全独立于 UNIX（专有大型机操作系统），OS/390 引入 OpenEdition MVS（部分聚合 UNIX 兼容性），z/OS USS 实现 UNIX 03 认证（深度聚合），同期 Linux on Z 在 IBM Z 上独立运行（与 z/OS 分离但共享硬件）——这一系列分离聚合并非线性进步，而是 IBM 在不同历史阶段对大型机生态的主体性选择。

**总纲 3（不存在进步，只有权力再分配）**——据原文第 3 章 3.2 节：

> “所谓进步只不过是权力再分配，把演讲台上的人割一茬，换他来一个样。”

IBM 在 1999 年支持 Linux 移植至 S/390，并非 “IBM 拥抱开源 Linux” 的技术进步，而是商业资本的权力再分配——IBM 试图通过 Linux on Z 防止客户从大型机迁移至分布式 x86 集群，将客户 Linux 工作负载的资源从 x86 服务器重新分配至 IBM Z 大型机。所谓 “IBM 开源战略” 的叙事，掩盖了 IBM 真正的动机（保护大型机业务）。

**总纲 5（没有必然性，只有偶然性）**——据原文第 5 章 5.2 节：

> “将英雄人物的出现必然化是一种机械的错误，没有认识到偶然性和自由的意义。”

IBM 在 1999 年决定支持 Linux on S/390，依赖多重偶然——若 Linus Torvalds 未在 1999 年 Linux World 大会上与 IBM 工程师会面，若 IBM 董事会未在 2000 年批准 10 亿美元 Linux 投资，Linux on Z 可能根本不会发生。所谓 “IBM 必然支持 Linux” 的叙事是史家的事后重构。

**总纲 10（动手者创造历史）**——据原文第 14 章 14.1-14.2 节：

> “这个世界不是靠什么精英也不是靠什么人民更不是靠什么其他人运转的，而是我们这些老实人，才让世界运转了起来。”

IBM Boeblingen（德国）与 Poughkeepsie（美国）研发中心的工程师亲自实现 z/OS USS 的 POSIX API 兼容层；Linus Torvalds 与 IBM 工程师 Martin Schwidefsky、Heiko Carstens 等亲自实现 Linux 内核 s390 架构移植；IBM z16 工程师亲自设计 Telum AI 加速器——这些是动手者的实践，而非 “IBM 决定” 等高管决策的产物。

**总纲 2（历史是形式主义化的非存在）**——据原文第 2 章 2.5 节：

> “谁试图诠释历史，谁就在篡改历史。”

所谓 “z/OS 与 IBM Z 的 UNIX 化（1994-2026）” 的判定本身即形式主义化的非存在——若以银行业核心系统演化为主线，若以 IBM Z 硬件演化为主线，若以 Linux on Z 演化为主线，“z/OS 史” 会呈现完全不同的脉络。本子节选取 “z/OS UNIX 化+Linux on Z” 为主线，但这一选取本身须以自反性声明显化。

**自反性声明**：本子节选取 “MVS/ESA → OS/390 → z/OS + Linux on Z” 为 z/OS 谱系演化主线，但这一选取本身即形式主义化的非存在。若以银行业核心系统演化为主线，若以 IBM Z 硬件演化为主线，若以 z/OS MF REST API 演化为主线，“z/OS 史” 会呈现完全不同的脉络。本子节承认主轴选取本身是史家的形式主义化决策，欢迎被更自反的释读所超越。

#### 辨析

**z/OS UNIX 03 认证辨析**：部分二手资料称 “z/OS 是 UNIX 系统”，但严格法律意义上 z/OS 通过 UNIX 03 认证的是 z/OS 1.7+（2006 年起），且认证基于 z/OS USS 的 POSIX API 兼容性，而非 z/OS 内核结构（z/OS 内核为 MVS 继承，与 SVR4 或 BSD 内核结构无关）。本子节采用 “z/OS 通过 UNIX 03 认证（基于 USS 的 POSIX API 兼容性）” 的限定性表述。

**Linux on S/390 移植辨析**：部分二手资料称 “Linus Torvalds 亲自移植 Linux 至 S/390”，但 Linus 主要提供内核架构指导，实际移植工作由 IBM Boeblingen 工程师 Martin Schwidefsky、Heiko Carstens 等完成；Linux 2.4.0（2001 年 1 月）正式包含 s390 架构支持。本子节采用 “Linus Torvalds 与 IBM 工程师合作，IBM Boeblingen 工程师实现 s390 移植” 的限定性表述。

**z16 与 AI 加速辨析**：IBM z16（2022）集成 Telum AI 加速器，专为深度学习推理设计（不适用于训练）；部分二手资料称 “z16 可运行大型 AI 模型”，但 z16 AI 加速器主要适用于小型推理工作负载（如欺诈检测、推荐系统），无法运行大型语言模型（LLM）训练。本子节采用 “z16 集成 Telum AI 加速器，适用于深度学习推理（不适用于训练）” 的限定性表述。

**LinuxONE 与 IBM Z 关系辨析**：LinuxONE 是 IBM Z 的变体，专为 Linux 工作负载设计（不运行 z/OS）；LinuxONE 与 IBM Z 共享硬件（z15、z16），但 LinuxONE 通常为 Linux 工作负载优化（如 Ubuntu、SUSE、RHEL 预装）。本子节采用 “LinuxONE 是 IBM Z 的 Linux 优化变体” 的限定性表述。
