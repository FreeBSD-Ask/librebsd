- 〔USENIX Security（推测）〕后半场覆盖 Spectre 家族、防御评估与内核测量。Spectre 不利用故障而利用数据/控制流预测，命名为 Spectre-PHT（模式历史表，原 Spectre V1）、Spectre-BTB、Spectre-RSB、Spectre-STL（存储到加载转发）等，并演示预测器在超线程与进程间共享时的跨地址空间与异位（out-of-place）场景：利用 PHT 索引的地址子集/哈希找到映射同一项的相同地址（congruent address）即可在不同地址空间训练预测器；防御分为三类（降低隐蔽信道准确性、检测后中止推测、确保秘密数据不可达），在 Intel/ARM/AMD 上实测部分防御有效、部分无效，序列化（serialization）防御带来 62%–75% 的性能损失，主张组合多种防御；对 Linux kernel 5.0 中开发者已加 fence 位置的分析给出 prefetch、compare、index、execute 四类 Spectre gadget 的出现情况（index gadget 未发现实例）；PoC 已发布到 GitHub 并欢迎 pull request，Q&A 讨论了 gadget 搜索停留在 C 源码层面、指针算术可能造成低估。（YouTube EPibqC4nbs23Y，[583-1164]，L1）
- 〔USENIX Security（推测）〕时任卡内基梅隆大学的 Manuel Egele（合作者 Maverick Woo、Peter Chapman、David Brumley）提出 blanket execution：对程序二进制与组件中函数做动态相似性测试。以 GNU coreutils 的 ls 中 strcmp name/cmp name 为例说明 GCC -O0 与 -O3 编译差异（内联、常量传播、无寄存器溢出）使最先进的静态相似性分析失效，因此不追求严格等价而是行为相似；核心思想是在固定且可复现的执行环境中执行函数 f 并记录副作用（内存访问、系统调用等）作为特征，从函数第一条未执行指令反复重执行以达成全指令覆盖；针对随机环境下全局变量与结构体指针依赖未满足的问题，用按需映射到所有地址的 dummy 内存页保证所有读写成功且一致，从而支持特征向量间的可比性，相似度定义为各特征集归一化加权的 Jaccard 指数之和。（YouTube EPsRv17moG_k4，[10-797]，L1）
- 〔USENIX Security（推测）〕后半场为数据集、实现、评估与二进制搜索引擎。基于 coreutils 95 个二进制，用 GCC、Intel ICC、LLVM Clang 三种编译器在 O0–O3 优化级别编译出 1140 个二进制、约 20 万个函数（以调试符号匹配函数名作 ground truth 后剥离），共 7 类特征（栈/堆读写、系统调用、经 PLT 的库调用、RAX 返回值），用 WEKA 机器学习工具包的 SMO 实现学习权重；实现工具 BLAX 基于 Intel Pin，1100 万个执行环境设置下共 1700 万次 blanket execution run、约 57 CPU 天（各 run 完全独立、可高度并行，比较单个大型二进制如 ls 仅需 30 CPU 分钟）；与业界标准 Synopsys BinDiff 对比：语法差异大（O0 对 O3，66 项优化差异）时平均胜出约 2 倍、大型二进制最高 3.5 倍以上，语法差异小时 BinDiff 略优；并构建二进制搜索引擎（约 3 万函数索引语料、单次搜索平均不到 1 秒），64% 的查询正确函数排名第一、前十（首页）命中率 77%、前两页约 80%；Q&A 涉及 Java 等语言的适用性（技术上不限于二进制，前提是可识别函数）、混淆代码需先脱壳、随机执行环境的生成限制，以及 du 工具同一函数六个相同实现、-r 逆序比较需要能暴露参数交换差异的环境等假阳/阴性讨论。（YouTube EPsRv17moG_k4，[798-1594]，L1）
- 〔会议不详〕Simply Block 开发者布道师 Chris 以 Fortran（1957 年诞生、2023 年仍有新版本发布）与 iSCSI 老化的年代梗开场，介绍自己曾任职 Ubisoft、Hazelcast、Instana，创办过 Cleverbit，并推荐基于 Postgres 的 Timescale。随后讲 NVMe 术语的过载问题：NVMe 既指接口连接器/端口规范，也指协议族——700 页的基础规范及约 15 个衍生规范（NVMe Express、boot、管理接口、含 RDMA 与 TCP 的传输接口等）；NVMe over Fabric 是把 NVMe 命令集隧道到不同传输层的规范，已指定 InfiniBand、Fibre Channel、TCP、RDMA/RoCE 及 PCIe，重点讨论 NVMe over TCP；并回顾从 SMD、Shugart、RL01/MFM、SCSI（1985）、IDE、SATA/AHCI、SAS 到 NVMe Express（2011）的存储接口演进史，质疑在闪存时代仍用为机械盘设计的 iSCSI（约 2000 年）的理由。（YouTube EPzCdyAdQtW5s，[16-995]，L1）
- 〔会议不详〕后半场演示与论证。Linux 客户端属内核 NVMe 栈，nvme connect 指定 TCP 传输、IP、端口与设备名即可远程挂载（支持 discovery 发现服务，lsblk 中看不出是远程设备，兼容性好；AWS Linux 2 因内核配置缺失暂不支持 NVMe over TCP，vanilla Amazon Linux 2020 正常）；性能上引 BlockBridge 基准：与 iSCSI 相比读/写 IOPS 近乎翻倍、延迟减半、每包开销少约 25%，随机写性能与 RDMA、Fibre Channel 处于同一区间，且避免 iSCSI→NVMe 的非一一对应命令转换、默认内建 multipath 故障切换，推荐弃用 iSCSI；适用场景包括数据库、虚拟化与容器化远程块存储，Proxmox 已支持、TrueNAS Scale 内核层面可用（UI 未暴露）、VMware、NetApp、Portworx、Micron、Lightbits 等厂商均有实现；最后介绍 SimpleBlock 的云原生存储编排：面向 Postgres/MySQL 等数据库工作负载的 Kubernetes CSI 驱动（快照、克隆、动态供给）、支持本地 NVMe/EBS/S3 分层的写时复制分布式逻辑卷管理器（自嘲为"分布式 ZFS"），以及把块存储层 WAL 存到 S3 实现跨可用区的时间点恢复（PITR）。（YouTube EPzCdyAdQtW5s，[996-1991]，L1）
- 〔USENIX Security（推测）〕FixReverter：基于真实 CVE 修复的现实主义 bug 注入框架。主讲人 Zenong Zhang（与 Michael Hicks、Shiyi Wei 等合作）介绍 FixReverter，目标是给 fuzz 测试提供更真实的基准。现有方案各有不足：FuzzBench 式代码覆盖率与 fuzzer 性能关联弱、崩溃去重启发式不健全且不精确、LAVA 等注入基准被批评不真实易过拟合、Magma 式真实程序基准手工注入成本高。团队由此提出好基准的四目标（真实程序、真实 bug、清晰去重、防过拟合），从 800 个 CVE 修复中归纳 bug 修复模式，经 syntax matcher、semantic matcher、bug injector 与 live bug filter 四组件将修复代码回退为注入 bug。（YouTube EP8n0GVJGvF7w，[7.8-371.5]，L1）
- 〔USENIX Security（推测）〕FixReverter 的模式定义与 fuzz 评测结果。三类模式为 conditional-abort、conditional-execute 与 conditional-assign，模式以上下文无关文法定义并沿程序源码解析追踪关键变量；注入 bug 标记 trigger/reached 状态，经失败输入与触发 bug 组合的 triage 分为 individual cause 与 combination cause。在 10 个真实程序上注入近 8000 bug 生成 RevBugBench 并集成 FuzzBench，5 个 fuzzer 各 24 小时超时 3 次试验识别出 200+ individual causes，其中 AFL++ 表现最佳；90% 的 individual causes 仅被一个 fuzzer 发现，说明注入 bug 对 fuzzer 有真实难度，基准已开源。（YouTube EP8n0GVJGvF7w，[371.5-735.1]，L1）
- 〔OSDI（推测）〕QOS：量子操作系统。主讲人 Emmanouil Giortamis（慕尼黑工业大学，导师 Pramod Bhatotia）指出量子架构目前以 ad hoc 方式管理、缺乏操作系统支持，而 Kubernetes 等经典云 OS 因量子计算机与经典计算的根本差异并不适用。以 MaxCut 量子应用说明电路、QPU 非确定性与物理映射约束后，实测四大挑战：大电路保真度骤降近 99%、小电路仅约 42% 的 QPU 利用率、同型号 IBM QPU 之间及其随时间的保真度空间时间异质性、以及保真度与资源效率之间约 60 倍的负载不均衡。（YouTube EPAJB5aGrYTf0，[17.6-456.4]，L1）
- 〔OSDI（推测）〕QOS 的编译器、多道程序与调度器设计及评估。编译器以 IR 分析转换流水线组合互补优化、按热点消除效率贪心排序以提升保真度；多道程序器以兼容性评分（有效利用率加 crosstalk 量化）与 buffer zone 隔离缓解串扰噪声；调度器做多目标优化，可理性地用 3% 保真度换取 4 倍更低等待时间。基于 Qiskit SDK 在真实 IBM QPU 上的评估：保真度较 CutQC 基线提升 2.5 倍、较 Qiskit 提升逾 400 倍，同利用率下比裸跑电路高近 10 倍、比基线多道程序高 15%，代码已开源。（YouTube EPAJB5aGrYTf0，[456.4-902.4]，L1）
- 〔SREcon（推测）〕从航空检查单到安全性能：安全应成为技术工程的一部分。安全顾问公司创始人 John Benninghoff 以祖父 60 年飞行员生涯始终坚持检查单、《The Checklist Manifesto》与 MIT STPA 研讨会为引，引入 Eric Hollnagel 的 Safety-II 思想：不能以事件不发生定义成功，而应右移整体性能并关注正面结果，使安全从成本变为投资。以三份 2019 年研究论证安全与软件交付/可靠性性能高度相关：DORA 报告显示可靠性、性能与安全指标同向变动；Veracode 状态报告显示每日扫描团队以天级修复漏洞、比低频扫描快几个数量级；Gene Kim 与 Stephen Magill 的软件供应链研究显示常更新全部依赖的项目更安全。（YouTube EPAjJdB2ZMxe0，[16.6-748.0]，L1）
- 〔SREcon（推测）〕SRE 与安全的能力重叠及安全等级目标（Security Level Objectives）。2024 年一项 meta 分析显示最有效的安全控制是攻击面管理（配置与资产清单）和补丁节奏，本质都是 SRE 维护工作；作者进而主张不应设独立的漏洞管理团队。可观测性上 SIEM 市场约半数产品由通用可观测性工具加安全特性扩展而来；事件响应方面 Monte Carlo 模拟显示安全事件低频高损（对数正态长尾，损失中位数约为停机事件的 10 倍），两团队在事件处置与测试（关注 unhappy path）上互补。他提出 Security Level Objectives：预先设定可接受风险等级，低于阈值即把资源从功能转向安全，指标可用攻击面、补丁节奏、每端点漏洞率、孤儿账号比例与登录失败率等前瞻度量。（YouTube EPAjJdB2ZMxe0，[749.4-1913.2]，L1）
- 〔会议不详〕VFP-IO：面向可编程性与可移植性的 FPGA I/O 加速框架。主讲人 Harsha（慕尼黑工业大学，与 Jian、Atushi 及导师 Pramod Bhatotia 合作）指出 CPU 中心应用难以发挥高速 SSD/NIC 性能，云厂商转向 Azure Boost、Google Titanium 等智能 I/O 设备，但现有 FPGA shell（如 Coyote）直接暴露底层 I/O 接口且无 I/O 虚拟化，带来可编程性差、用户逻辑不可移植、多用户逻辑间无性能隔离三大挑战。VFP-IO 的虚拟 I/O 模块把物理端口抽象为虚拟 I/O 端口并支持运行时切换设备，shell 内 I/O 调度器按预配置策略拦截调度用户逻辑的 I/O 请求，主机侧 VFP 库可动态改写用户逻辑与目标设备间的 I/O 路径并配置调度策略。（YouTube EPEpt7PULQF50，[16.2-585.0]，L1）
- 〔会议不详〕VFP-IO 的移植性、性能隔离与评估。VFP 库以软件方式按需重配置 I/O 路径免去重编译重上传，I/O 设备以文件形式经 API 表示；调度器为每设备读写路径成对配置，支持 round-robin 与优先级策略，性能关键应用可切换为高优先级优先执行。在两台各配 Xilinx Alveo U280、以 100GbE 互联的 x86 服务器上以 Coyote 为基线：本地内存与 RDMA 场景虚拟 I/O 抽象平均开销仅 0.5% 与 1.1%；I/O 路径切换经软件驱动、下一时钟周期生效，较部分重配置（平均约 25000 微秒）快近 20000 倍；优先级调度使高优先级应用较 round-robin 快近 2 倍，代码开源。（YouTube EPEpt7PULQF50，[585.0-1158.9]，L1）
- 〔会议不详〕容器监控的黑暗艺术：经典排障工具为何在容器中失灵。Sysdig 软件工程师、开源排障工具 Sysdig 核心开发者 Gianluca 现场演示 WordPress+MySQL+Nginx 的 Docker Compose 三层应用（含 docker-gen 自动再生成 Nginx 配置），指出容器的隔离与轻量使监控多了一层屏障。经典工具不适配容器：top 需借 cgroups 才能定位进程所属容器、看不到容器内 PID 命名空间；netstat 在宿主机看不到跨容器的 MySQL 3306 连接；docker exec 进容器又因镜像轻量没有工具；nsenter 虽可跨命名空间执行 netstat 但手工步骤多不宜生产。Sysdig 以内核模块抓取全部系统调用、号称系统级 tcpdump，天然支持容器与 Kubernetes 过滤。（YouTube EPM6Z7b54iC_k，[10.4-1113.4]，L1）

- 〔会议不详〕InfluxDB：数据中心监控为何需要时间序列数据库。InfluxData 工程师以量化例子说明监控数据规模（2000 台服务器、每台每 10 秒 200 项指标、一年即 2.5 万亿条记录）不适合 SQL，且写入负载高、删除与写入同频。InfluxDB 用 Go 编写、无外部依赖、编译为单一可执行文件、完全开源（约两年半 8300 次提交、172 位贡献者），提供 SQL 风格查询语言与 HTTP API。数据模型自上而下为 measurement、tag、series 与 point；measurement 名与 tag 建索引而 field value 不建（仅按时间快速定位 shard），索引驻留内存以加速写入路由，作者提醒在最小内存主机上高频写入会耗尽内存；retention policy（最短 1 小时）以 shard 文件为单位在后台高效删除过期数据。（YouTube EPNRo4gpIyKCY，[11.4-1354.7]，L1）
