- 〔会议不详〕CTFS：用硬件内存翻译取代文件索引的持久内存文件系统。报告人 Robin 介绍与多伦多大学同事的合作工作：持久内存低延迟使存储瓶颈从 I/O 转向索引，EXT4-DAX 仍以块设备方式依赖软件索引，其微基准显示索引占 append 负载运行时间约 45%、顺序写约 43%、随机读写也超过 20%，SplitFS、HashFS 等既有优化仍未摆脱软件索引。CTFS 的核心观察是 PM 本质上仍是内存、可被 MMU 直接寻址：将所有文件与目录在虚拟地址空间连续分配，inode 只存起始虚拟地址，每次文件访问退化为软件中的简单偏移计算，物理数据位置由 CPU 内 MMU 进一步翻译；翻译由存于 PM、与 Linux 页表同构的持久页表管理，缺页时复制到 DRAM，物理页按需分配。内核部分仅向用户态提供内存抽象，文件系统功能以用户态库实现。（YouTube EPLwADcNapMWY，[8-430]，L1）
- 〔会议不详〕分层文件布局、pswap 系统调用与性能评估。借鉴 buddy 分配器，将虚拟地址空间划分为自 L0（4KB 页）起逐级 8 倍的分区层级，L6 分区起始地址按 1GB 对齐，每分区至多一个文件，浪费的只是虚拟地址、物理 PM 页因按需分页并不浪费；分区头含状态图与可用级别元数据，虚拟地址空间顶部保留两个最高层分区分别放元数据与文件数据。针对文件增长越界引入新系统调用 pswap，原子交换两段等长连续虚拟页映射，并利用多级页表的指针粒度（如 PUD 指针对应 1GB）把交换 128MB 化简为交换 64 对 PMD 指针而非 3.2 万页，512 页时已比 memcpy 快数百倍，还可配合 staging 分区加速原子写。评测显示 append 负载较 EXT4-DAX 提速 6.7 倍、较 SplitFS 2.1 倍，YCSB 上 sync 模式平均较对比 PM 文件系统提升 164%、较 EXT4-DAX 提升 188%；代价是元数据操作全在用户态、防护较弱，团队用 Intel MPK 防内存错误但无法防有意攻击，计划将元数据处理迁入内核。（YouTube EPLwADcNapMWY，[430-849]，L1）
- 〔SREcon〕Netflix Open Connect 的 SLI/SLO 基础与三类流媒体 QoE 指标。主讲人 Tiara Ortiz 是 Netflix 的 staff CDN 可靠性工程师，介绍 Open Connect 为 Netflix 自有 CDN：100% 流媒体码流由其承载，服务 2.3 亿以上会员、覆盖 175+ 国家，部署超过 1.8 万台 OCA 于互联网交换点与 ISP 机房；并讲解播放链路——客户端请求播放清单（playback manifest），云上播放应用服务借助内部引流服务 Coda 选出最佳 OCA 并生成 URL，Coda 依赖各 OCA 定期回报可用性、文件与 BGP 通告的缓存控制服务（CCS）。她引用 Google SRE 图书定义 SLI/SLO，并给出三类 QoE 指标：起播延迟（play delay，消费洞察团队研究显示延迟越高评分越差）、网络卡顿（network rebuffer）频率，以及播放期相对码率；三者在设备端自适应流媒体引擎（ASE）中彼此牵制，如同必须二选一的权衡。（YouTube EPLwvA6L1zizg，[15-665]，L1）
- 〔SREcon〕由易到难定义 QoE SLO 阈值并落到告警行动。方法分层：第一层凭直觉设阈值（如 15 秒起播上限，实现低成本但不适合敏感应用）；第二层把时序数据画成箱线图，用下四分位减 1.5 倍 IQR 设统计离群阈值（归一化码率约 87.5%），同时警惕 Simpson 悖论、按设备分组建 SLO，并用历史事故回验阈值能否捕获回归；第三层做调查——现场举手实验加 CDF 显示多数听众在 2-3 次 rebuffer 即放弃，但 SREcon 听众对卡顿格外敏感会带偏样本，故扩展到 Netflix 云游戏的 in-app 问卷，把 SLI 与问卷得分关联、甚至用 LLM 挖掘指标与用户抱怨的相关性；更强的手段是 A/B 测试，在生产环境以对照组/实验组观察 QoE 与收入变化。行动上：按阈值主动发现某客户端约 1 月 10 日的归一化码率骤降并通知 ISP（ISP 往往不知道自己退化），配合覆盖 61 个国家与地区的 ISP speed index 榜单，用黄金时段平均码率排名驱动 ISP 主动治理拥塞。（YouTube EPLwvA6L1zizg，[665-1313]，L1）
- 〔会议不详〕PMR 思路：用 procfs 与 cgroups 找出加载过期库的运行进程并无重启修复。主讲人是 systemd committer、Drupal 安全团队核心贡献者与 Fedora server 工作组成员，供职于一家运营数百万容器、约占互联网千分之一页面浏览量的大型云服务商；面对 Heartbleed、Shellshock 等 OpenSSL/Bash 漏洞，发行版推荐的装完即重启对 packed 基础设施代价高昂（服务可能中断数分钟到一小时），Debian/Ubuntu 更新后自动重启主守护进程的机制对这三类漏洞一个也覆盖不到，且对每个容器跑一个 nginx 实例这类多实例部署完全无效。其方法：遍历 procfs 的 maps，找被标记为 deleted 的映射（包更新后库文件被换出但旧副本仍在内存中），再用 cgroups 把这些 PID 映射回 systemd 单元（每个 systemd 服务启动于一个 cgroup，内核维护 PID 到 cgroup 的映射），即可自动重启对应服务；并以 OpenSSH 为例演示，用 rpm -qf 与 changelog 中 grep CVE 判断换出的更新是否为安全更新。（YouTube EPLySsjPAGx64，[10-1030]，L1）
- 〔会议不详〕PMR 工具实现、现场演示与问答交锋。工具名为 PMR（process maps restarter），pip 安装、须 root 运行，支持 dry-run、INI 白名单/黑名单规则与按命令行聚合，重启的服务依赖由 systemd 单元文件处理从而接近事务式滚动重启；在 Rackspace 的 Fedora 20 实例上 yum upgrade 后演示，发现 sshd 加载含 libcrypto（OpenSSL）在内的一批过期库、cron 过期 libaudit，无法映射回服务的进程（如 crond -n）标红且不会自动处置。问答中 MIT Lincoln Laboratory 的 Patrick Cabel 问及依赖映射，主讲人解释进程映射可隐式递归捕获 PyOpenSSL→OpenSSL 这类链式依赖；对 dpkg 依赖元数据+触发器的质疑，回应是多实例 nginx 与 mod_php 动态加载等场景元数据不完整；并透露曾与 Lennart Poettering 讨论集成进 systemd，但 Debian 不愿放在该层、且静态链接与 /opt 自带库等盲区使其不敢宣称完备，整体约为 99% 方案；Heartbleed 爆发时他们正是用该方法不重启机器地重启了约 10 万个进程。（YouTube EPLySsjPAGx64，[1030-2052]，L1）
- 〔USENIX Security〕Ret2Dir：physmap 地址别名瓦解 return-to-user 防御。主讲人 Vasilis Kemerlis 来自哥伦比亚大学（合作者 Michalis Polychronakis 与 Angelos Keromytis），回顾内核 exploit 最流行的 return-to-user 攻击及其防御谱系：PAX 补丁集的 KERNEXEC/UDEREF、两年前发表于 USENIX 的 KGuard（编译器方案、跨平台跨 OS）、Intel SMEP/SMAP 与 ARM PXN。核心观察是 64 位 Linux 内核空间有 64TB 的 physmap 区域直接映射全部物理内存（kmalloc、slab 等内核分配器均构建其上，具备免改页表、低 TLB 压力、虚物连续、页帧核算简单等优点）；当物理页同时被映射到用户地址时产生跨安全域的地址别名，攻击者可在用户态写好载荷，再经 procfs 的 /proc/pid/pagemap 接口读出用户地址对应的页帧号，乘页大小加 physmap 起始地址（该起始地址在同架构各实例间固定、不受 KASLR 影响）即得内核空间同义地址，用它改写内核代码/数据指针即可绕过全部 return-to-user 防御。（YouTube EPLyVVPU54WY4，[10-540]，L1）
- 〔USENIX Security〕physmap 喷射、真实 exploit 验证与 XPFo 防御及问答。若 pagemap 接口被禁用，攻击仍可概率性进行：physmap spraying 在用户态反复复制载荷污染 physmap，实验中成功率可高达 0.95。评估取 8 个公开 Linux exploit 加一个自造漏洞，先验证均被开启的全部 return-to-user 防御阻断，改写为 ret2dir 后全部绕过。防御方案 XPFo 在 buddy 分配器上加薄管理层，强制互斥页帧所有权（XPF）：页帧只能归属内核或用户空间，除非内核显式请求零拷贝共享；用户态分配时找到并解除 physmap 同义映射、回收时恢复，保留直接映射的全部优点，Phoronix 微/宏基准开销为 0.80%–2.91%。问答指出页缓存仍是未覆盖的注入路径；CFI 等内核代码完整性检查可挡住该攻击但主流系统尚未具备；Windows 与 Solaris（SPARC 与 x86-64）也存在直接映射全内存的区域——这是一条设计模式而非单一操作系统的选择。（YouTube EPLyVVPU54WY4，[540-1070]，L1）

- 〔SREcon（推测）〕停机预算（downtime budget）：错误预算在 HPC 的迁移与社区挑战。错误预算的精确实现不适配 HPC——千分之 0.01 的配额对一万个作业不足一个，且作业失败并无用处——但他们把追踪思路迁移为停机预算：每季度 3 次 DST×10 小时=30 小时计划停机，约占集群可用时间的 1.4%，与 80% 的良好利用率相称。用 Python 脚本连 MySQL 统计库、JSON 输出、Plotly 绘图（仍为概念验证），以恒定燃烧率为基线叠加各集群曲线：有集群因高速网络故障过夜停机烧穿整季预算（约 -13 小时），也有集群整季只用了 3 小时，9 月 9 日设施计划停电更让几乎所有系统转负。用途包括向资助方汇报（science stackometer、需要更多或更少时间）、与设施部门协商计划停电与水冷改造、为夏季雷击预留约 2 小时、审批专属用户时间请求，以及给管理员留出修复技术债的灭火时间；同时明确非目标：不搞数字抠门、不鼓励为指标而指标。最后提出社区挑战：识别各自环境的独特之处，把经验教给不同环境的人而非布道式转化；问答还讨论了向 DOE 上报利用率、朝九晚五运维的预算损耗、集群同构采购与每年约一轮的更新换代。（YouTube EPM2SBUePEyz8，[730-1696]，L1）
- 〔会议不详〕KleptoCache：以时间驱逐防御缓存攻击的动机与设计。这是与 Christian Listler、Dominic Funke、Gregor Leander、Pierre Meyer、Niels Pohl、Lukas Davi、Tim Güneysu 合作的论文：两年前同一会议上提出的 Prime+Prune 攻击是针对随机化缓存架构的通用攻击，攻击者先填满缓存、借受害者访问驱逐自己的地址来收集部分同余地址、构造广义驱逐集，实施类似 Prime+Probe 的攻击——随机化缓存让攻击更难但威胁仍在。KleptoCache 的目标是阻止观察者观察缓存冲突同时保持效率：组合缓存随机化（防止平凡构造驱逐集）与缓存衰减（cache decay），每个缓存行带 TTL——名称取自水漏 clepsydra；TTL 保住最近访问的数据、淘汰久未访问、大概率不再使用的数据，使缓存中始终存在空行可用。（YouTube EPM4vfZM7CPn8，[8-370]，L1）
- 〔会议不详〕TTL 动态调度、电容电路实现与安全/性能评估。三类事件的处理：miss 时随机化函数选出候选行、替换策略优先填入无效行而不驱逐任何数据，并把 TTL 设为区间内随机值使攻击者无法预测驻留时长；hit 时同样重置随机 TTL，让高频访问常驻；TTL 到期则脏行立即写回并失效。理想情况希望每组合候选行都含空行，但硬件上难以廉价监测，改为按全局冲突率动态调度 TTL：冲突发生时加快所有 TTL 过期，无冲突时放慢以最大化性能；为避免每个 cache set 维护计数器（每周期更新太贵），与电气工程系合作设计电容电路——以电容存 TTL 电荷、初始值与全局放电速率以电流施加，可叠在 SRAM 单元上不占面积。安全性上，Prime+Probe 需先填满缓存，必然引发冲突、加速 TTL 过期，攻击者即使填满候选行也无法区分自己观察到的 miss 是冲突还是 TTL 自然过期。Gem5 评测中无法构造驱逐集，冲突驱逐减少 90% 以上，miss 率仅升约 5-10%，整体性能开销在 -0.37% 到 +5.25% 之间。（YouTube EPM4vfZM7CPn8，[370-731]，L1）
