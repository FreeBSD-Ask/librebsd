# 321.4.223 〔USENIXSecurity23推测〕关键洞察是环回接口地址固定网卡接口与环回

- 〔USENIX Security '23（推测）〕关键洞察是环回接口地址固定：网卡接口与环回接口共享算法状态，而环回目的地 IP 恒定，故用于端口计算的计数器索引只取决于密钥 k2，与所在网络无关。〔07:49〕攻击要害因此变成"to collect hash collisions of the G hash function"〔07:58〕（正解 for loopback traffic）：收集一组使用同一计数器的环回目的地对，这些对在网络上独立、只依赖 k2。〔08:13〕收集足量此类配对后，配对集合本身即构成仅基于该密钥的设备 ID，其生命周期等于密钥生命周期——在 Linux 上即直到重启。〔08:32〕难点在于如何远程发现这些冲突：既无法从 JavaScript 读到源端口，也无法访问内核中的算法状态，唯一能观察的是发往攻击者服务器的源端口。〔08:51〕解法是间接找环回冲突——若两个不同环回目的地都与同一攻击者目的地冲突，即可推知二者互相冲突；而判定某攻击者目的地与某任意目的地是否冲突的主原语，是让设备按特定顺序建立三次 TCP 连接：先连攻击者目的地、再连待测任意目的地、最后再连攻击者目的地。〔09:51〕这样有两个 SYN 到达攻击者控制的追踪服务器、中间那个通常不可见；服务器计算两个源端口之差，"if they both share the same counter in the soft spot calculation, then the the delta would be two, because the counter was incremented twice"〔10:21〕（正解 source port calculation），否则 delta 为 1，"because they they use different contexts"〔10:27〕。〔10:49〕攻击分两阶段：先收集 T 个能唯一覆盖整张表所有单元的攻击者目的地（只知道映射存在、不知具体映射），再枚举环回目的地、为每个找到匹配的攻击者目的地，并据此推断环回目的地之间的冲突，直到收集够多冲突为止。〔11:18〕实现上追踪脚本用 JavaScript、追踪服务器用 Go，实验证明攻击在真实互联网上可行：测了 Chrome 与 Firefox 两大浏览器，跨站点、浏览器与网络均得到一致指纹，浏览器隐私模式下私有标签页与普通窗口的指纹也一致。〔12:00〕停留时间——攻击成功所需用户在页面上停留的时长——在 Chrome 上约十秒，取决于到攻击者服务器的 RTT；Firefox 上更久；Android 侧因研究当时无设备实现该算法，遂手工打了三星 Galaxy S21 的内核补丁来测试，Chrome 移动版停留时间约二十秒。〔12:54〕披露流程：2022 年 2 月告知 Linux 内核安全团队，获得 CVE 指派，与其协作打补丁，三个月后补丁合入内核。〔13:10〕结论是 RFC 6566 标准化的该算法易遭设备追踪，讲者认为这项研究说明用户隐私会以不明显的方式被侵蚀。（YouTube EPYWc-uXrTl3s，[433-822]，L1）
- 〔NSDI '17（推测）〕讲者 Anran Wang（华盛顿大学，与 Vikram Iyer、Wasim Taha 合作，师承 Shyam Gollakota 与 Josh Smith）以两幅愿景开场。〔00:29〕其一是"kinetic cities"：街头海报与招牌原本只显示乐队演出、促销广告或公益提示，愿景是让人走过时能与之交互——从海报里听到乐队的音乐。〔01:05〕其二是智能织物：衣物可集成交互设备与健康传感器，设想一件能监测心率与呼吸的衬衫。〔01:32〕两者共同的核心挑战是无线电不合适：海报用 Wi-Fi 或蓝牙持续放音乐，功耗之大让纽扣电池撑不满十二小时；智能织物另有难题——电池也必须是柔性的，而市面上的柔性电池连普通蓝牙或 Wi-Fi 无线电都带不动。〔02:09〕替代方案是反向散射（backscatter）通信，其三要素是产生信号的射频源、可反向散射的海报集，以及能解码散射信号的接收端。〔02:31〕三项约束逐层收窄：信号必须随处可见（Wi-Fi、蓝牙、电视、调频皆候选），又必须在室外可用（排除 Wi-Fi 与蓝牙），接收端还必须是手机与汽车已自带的（排除电视），于是"what we need to do is to backscatter the FM radio signals"〔03:11〕。〔03:18〕论文由此提出"FM backscatter"，"which enables wireless communications using reflecting ambient FM radio signals in outdoor environments"，散射信号可在智能手机乃至汽车上解码。〔03:41〕思路是先在频谱中找出最强调频信号（例：94.9 FM），再找最近的空闲频段（例：95.3），用反向散射把环境信号搬移到该空闲段。〔04:21〕总结一句：把自己数据叠加在既有 FM 信号之上。〔04:34〕三项贡献：首次证明环境调频广播信号可用于反向散射通信；由此让日常物体可与手机、汽车通信，功耗低至"twelve microwatts"〔04:42〕，与柔性电池兼容；并造出首个能与手机和汽车通信的智能海报与智能衬衫原型。〔05:07〕随后请 Vikram 上台演示，展示三部件系统：一台模拟室外发射塔的 FM 发射器（会场内调频覆盖不佳）、背面用铜箔胶带集成天线且与海报纸张同样扁平柔韧的海报，以及充当 FM 接收端的普通智能手机〔05:55〕；台上先播原台新闻节目，再调到相邻的 101.1 频道即可听到来自海报的音乐〔06:43〕。〔07:03〕（YouTube EPYXWcxLbTX9Y，[10-423]，L1）
- 〔NSDI '17（推测）〕演示后分两问展开：环境调频信号到底有多强〔07:07〕，以及怎样把自己的信息编码到这些信号上〔07:14〕。〔07:29〕第一项靠实地勘测回答：把西雅图全城划分成网格、逐格驱车测调频信号强度，覆盖市中心高楼密集区与郊外起伏丘陵等复杂地形。〔08:16〕结果为热力图与 CDF："the median FM signal power is actually about minus thirty five dBm"〔08:16〕，最低约 −55 dBm，且全城覆盖相当稳定。〔08:44〕作参照，所测环境调频实际上比典型 Wi-Fi（常为 −60 dBm 甚至更弱）强得多。〔09:13〕第二项从收发信机原理切入：正常 FM 发射的信号中 ω 项对应发射频率（如 94.9 FM），s_FM 是编码其中的声音信号，而接收端输出只给出听到的音频。〔10:11〕反向散射通过切换与天线相连的开关改变反射能量；用信号 B 控制该开关时，数学效果是把自己的信号与原 FM 信号相乘。〔10:50〕麻烦在于这一切发生在射频域的无线电信号上，而接收端只解出音频，于是核心挑战是把射频域的运算转成可被听见的音频。〔11:15〕解法其实很简单："we create a backscatter transmission with the exact same structure as a normal FM radio transmission"〔11:29〕——结构与正常 FM 信号完全相同，只是编码自己的声音信号 sb。〔11:52〕据此利用两个指数相乘的性质，得到的是两个音频信号的相加：整个叠加结果相当于又一个调频电台，接收端解出的正是原台与自己所散射音乐之和。〔12:32〕由此把射频域乘法转化为音频域加法。〔12:43〕两项改进：一是借调频的立体声模式降低从原台听到的背景声；二是把数字数据编码进所发音频流——"we use FSK modulation at frequencies between eight and twelve kilohertz"〔13:09〕，因该频段高于背景 FM 里的人声，故数据传输相当可靠。〔13:27〕两项技术实测可用距离都到十二英尺。〔13:45〕原型用树莓派与 FPGA 等现货零件拼装，尺寸偏大；但反向散射允许把整套系统做成小于平方毫米的定制芯片，仿真显示功耗低于十二微瓦。〔14:40〕两个概念验证应用：其一证明海报不仅可与智能手机通信，也可与汽车内置 FM 接收器通信，视频现场演示；另注车载 FM 接收器与其天线远优于手机内置，与汽车联测时可用距离提升到约六十英尺〔15:25〕。其二把用导电纤维缝进织物的天线做成一件可穿的衬衫，讲者当场穿着展示纤维排布形成的天线图案，该原型可传数据至"one point six kilobits per second"〔16:16〕，且边走边跑仍然可用。〔16:43〕收尾：这是首个在室外用环境调频信号工作的反向散射系统演示；课题组多年来的一系列工作再度证明反向散射的能力，希望研究界继续探索，直到反向散射在速率、频谱效率与距离上能与传统无线电竞争。〔17:22〕问答中 Rick Farrow 确认其机理是调制接地通路、改变与天线相连的阻抗从而产生 FM 系统信号；讲者补充系统里真正耗电的只有那枚开关与其控制逻辑。另有人问能否反过来把发射器装进汽车、组车对车网络：讲者答信道选择是变量、尚未充分测试移动收发端，但车内空间对装大天线不敏感，市面上已有很小、可插车的 FM 发射器。（YouTube EPYXWcxLbTX9Y，[423-1160]，L1）
- 〔掩码实现验证学术会议报告（推测）〕CoCo 试图验证针对物理侧信道攻击的对策，把软件与硬件一起纳入验证。发言人 Barbara Giger 描述攻击模型：设备持有秘密资产如“for example, a cryptographic key”〔00:33〕，设备可以是“a government ID, a passport, a SIM card”，也可以是运行加密软件、处理密钥的微处理器，攻击者能够“manipulate and observe certain properties of the device”〔00:57〕，例如监控 CPU 执行算法时的功耗；而功耗同时取决于“which instructions are executed”以及被处理的数据〔01:15〕，因此对策必须打断这一依赖，办法是把敏感值拆成多份随机共享量、只在这些共享量上运算〔01:51〕，使功耗依赖随机数而非敏感值本身。既有验证手段非硬件即软件：ReBecca 只做硬件验证，而面向软件的技术则“completely excluded the hardware”〔03:14〕，默认最终执行软件的 CPU 不会出问题，但这一假设在实践中并不成立。CoCo 要在特定软件与特定硬件上验证“the execution of the software on the hardware is secure”〔03:46〕，分两步走：先在电路网络级检测泄漏，再定位是哪段硬件引起的、并对写软件者不易察觉的问题加以修复。硬件之所以会破坏掩码，是因为被探测的导线在一个时钟周期内会同时经历 transition 与 glitch〔04:49〕，而 glitch 源于组合逻辑中的传播延迟差异，比如不同线长、不同门延迟；以寄存器文件为例，先读 X2 再读 X3 时，多路选择器与最终读出端口之间会出现从一个共享量到另一个共享量的跳变，于是设计中实际存在泄漏〔05:43〕，写数据与读地址也可能 glitch，后者在写软件时更难避免。（YouTube EPYaG6NDkFN70，[8-355]，L1）
- 〔掩码实现验证学术会议报告（推测）〕验证流程是：先在硬件上仿真软件执行，然后做注解，即告诉验证器哪些寄存器与内存位置存放共享量，再送入验证过程，结果要么判定执行安全，要么指出“the leak is in this cycle at this gate”〔06:36〕。该技术受 Rebecca 启发并扩展为可对“software on hardware”跨多个周期验证〔06:58〕，还可进一步做 codesign：只要能拿到网表，原则上适用于任意处理器。案例研究采用 RISC-V Ibex 内核——一个只有两级流水线的 32 位小内核，却具备寄存器文件、ALU 等常见微处理器部件〔07:22〕；在 Ibex 上运行掩码软件后，CoCo 在寄存器文件、ALU、数据存储器与 load/store 单元都找出了泄漏〔07:50〕。对策分硬件修复与软件约束两类：寄存器文件的加固是把易 glitch 的读地址信号换成来自寄存器的地址信号，读地址被编码成一热向量存入寄存器〔08:29〕，其输出不含组合逻辑产生的 glitch，再用该位门控寄存器输出，读取 X1 时就真的只读到 X1；相应软件规则是不连续读取这些寄存器，否则又会从一个寄存器跳到另一个〔09:20〕。评估方面，面积开销（不含 SRAM）约百分之十〔09:38〕；测试集聚焦 S-box 与掩码乘法器这类构造最难也最易泄漏的部分，能发现刻意写错的 DOM gate 实现并报告“the leaking cycle twelve”〔10:12〕，AES S-box 则“verified 1900 cycles in five hours”〔10:31〕，并做了更高阶测试如掩码三阶乘法器〔10:37〕。作者以“close the hardware-software gap”〔10:48〕收尾：既有工具只关注掩码软件而不管硬件，CoCo 则同时验证软件与硬件。（YouTube EPYaG6NDkFN70，[355-702]，L1）
- 〔Node.js 生态会议报告（推测）〕Node.js 的事件循环在同步阻塞面前几乎就是一次自拒绝服务。发言人自我介绍为“part of the Node.js Technical Steering Committee”与 OpenJS 基金会董事会成员，过去八年半一直做 Node 的大规模构建与部署〔00:17〕。事件循环本应很好用，直到它出问题为止：JavaScript 同步执行、Node 基于一大袋 C 与 C++，他说“Reality Node.js is just a big wrapper for a big bag of C and C plus plus code”〔02:15〕；HTTP 请求进来先做一段同步处理，再发起异步 IO，等事件回来继续。他算了一笔账：两段各 10 毫秒的同步处理，总响应 30 毫秒，但决定容量的是同步阻塞的 20 毫秒——服务器被阻塞 20 毫秒意味着每秒最多做 50 个请求〔03:30〕，而且这还是最好情况。现实中服务端渲染 React 应用渲染一大张列表要占 50 到 100 毫秒同步时间〔04:25〕，所以他称这本质是一次大规模 DoS 攻击，大多数 Node 应用并无防护〔05:00〕。若多个请求同时到达，第一个很快得到响应、最后一个被拖得很久〔06:07〕；延迟一旦超过一两秒，用户开始刷新页面、微服务按既有约定自动重试，于是风暴把系统彻底压垮〔07:10〕。他讲起一次做顾问的经历：客户声称无法复现，他在一个只有 10 兆的受限 Wi-Fi 上就把对方 staging 集群打挂了〔08:10〕。负载低于阈值时响应时间稳定，一旦越过阈值延迟线性增长而且“forever and ever”〔08:44〕，当响应一个请求要 10 秒时服务实际吞吐为零。自动扩容反应太慢，等它起效通常已离故障过去一分钟〔10:19〕，因此更该靠 CDN 与 Cloudflare、Akamai、Fastly 一类工具挡流量；而 Node 有个奇特性质，CPU 跑到 100% 时可能仍有容量，因为垃圾回收等活儿在别的线程里〔11:05〕。这类情形多半不是攻击而是黑色星期五〔11:35〕。症结在于我们不知道系统状态，只看 CPU 就太晚了〔12:56〕。他 2016 年写过极简库 loopbench：记下 now、再安排一秒后触发、比较实际漂移与预期，漂移超过阈值即可打开熔断〔13:26〕，但它跑在 timer 阶段，若事件循环卡在 poll 里处理事件就可能永远到不了 timer〔14:22〕。（YouTube EPYaTi4rOvas0，[16-904]，L1）
