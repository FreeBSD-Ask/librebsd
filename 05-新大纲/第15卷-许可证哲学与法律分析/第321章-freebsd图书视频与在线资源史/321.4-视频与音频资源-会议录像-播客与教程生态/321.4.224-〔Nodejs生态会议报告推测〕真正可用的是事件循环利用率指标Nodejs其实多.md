- 〔Node.js 生态会议报告（推测）〕真正可用的是事件循环利用率指标。Node.js 其实多线程，每个线程有自己的事件循环；一位朋友写出了事件循环的线性化模型并提供监控 API——“the event loop utilization”，他说明这是 NodeSource 团队的工作〔15:22〕。该 API 给出 0 到 1 之间的一个数，表示自上次检查以来事件循环被占用了多少、又在等多久〔15:54〕，于是能在饱和之前就感知自己接近最大容量，主动限流并把它当作反馈给负载均衡器的健康检查〔16:49〕。他几年前写了框架 Fastify，并做了一个插件：利用率超过 98% 时开始返回 503〔17:21〕〔17:42〕，健康检查路由也会自动改为返回错误，让负载均衡器在基础设施层摘除节点〔18:15〕。理由很直接——“we'll never be able to respond to that in time”〔19:01〕，不如不接、把活儿推回给负载均衡器。他现场演示：一个只有单路由的 Fastify 服务，异步 sleep 模拟数据库查询，再用同步 sleep 把进程冻结 10 秒〔20:21〕。10 个并发约每秒 39 个请求〔21:47〕；50 个并发、1 秒超时则约一半超时〔22:35〕；再跑久一点实际吞吐是“flat zero”，服务器完全无响应〔22:48〕，而这正是市面上每个 SSR React 系统的形态〔23:09〕。挂上插件（最大事件循环延迟 200 毫秒、最大利用率 80%）后仍有个别超时，但大量请求被 503 挡回，从而吸收了流量〔23:28〕〔24:08〕；只要请求被接受，就会被排队并把进程一直占着、故障迟迟无法解除〔24:31〕。更好的做法是流量整形与缓存降级：服务很忙时直接返回缓存值〔24:52〕，他给某个知名 SSR React 方案提过 PR——Node 忙就别做服务端渲染、返回空 HTML〔25:19〕；演示结果是熔断跳闸那一下的几次超时之后，服务器持续返回 200〔26:10〕。另两点：用 Piscina 把复杂运算（如 AWS 签名所需的哈希）委托给线程池，避免阻塞事件循环〔26:48〕；以及打破“never cross the streams”的去重思路，5 个相同请求只发一次，并可把结果缓存在 Redis 或内存、配合 TTL 与 stale 参数〔28:03〕。最后说这些都是 Platformatic 的内置能力〔29:03〕。（YouTube EPYaTi4rOvas0，[904-1793]，L1）
- 〔强化学习系统学术会议报告（推测）〕发言人来自密歇根大学，做的是大模型强化学习训练基础设施的效率工作，系统叫 RiO Boost，思路是收割云上的抢占式实例以降低训练成本〔00:18〕。他先回顾 RL 流程：它是个三阶段循环，rollout 阶段模型根据 prompt 随机生成回答，生成的 token 传给训练引擎，与奖励一起算出损失并更新权重，更新后的权重再同步回 rollout 引擎，如此反复〔00:51〕。他在数学推理任务上做 profiling，发现瓶颈在 rollout 侧——“Over seventy percent of our time is spent on generating tokens autoregressively”〔01:46〕；多堆 GPU 能压缩墙钟时间，但也意味着更高成本，于是真正要回答的问题是：有没有办法既压低 rollout 成本又提高其吞吐〔02:07〕。对比两者特性，训练是有状态的，要存模型权重、梯度、优化器状态与全部激活值，通常被切分到多台机器并经高速网络互联；rollout 则近乎无状态，单个实例即可服务推理，某实例被抢占或故障时可在其他存活实例上继续；但对训练而言，丢一片优化器状态就意味着从上一个 checkpoint 重来〔02:27〕。结论因此清晰：训练必须用预留的、紧耦合的 GPU 实例以换取稳定性与更高网络带宽，rollout 则可借助抢占式、碎片化的实例降成本，云上此类实例最多可便宜九成〔03:20〕。他的初步测试显示，随着抢占式实例数逐步增加，相对吞吐越来越高而每 token 成本反而下降，因为他把正确的硬件配给了匹配的工作负载特性〔03:46〕。落地需考虑两个现实因素：其一，spot 实例低价来自不稳定的可用性，随时可能被抢占，实例不足时 rollout 吞吐很低，进而阻塞训练；其二，工作负载随时间变化，随模型推理能力增强 rollout 越来越占主导〔04:12〕。所以目标不是简单拼凑两类资源，而是设计一个弹性系统来桥接动态的工作负载与资源〔04:51〕。现有架构都不理想：co-located 把 rollout 与训练放同一批机器，但训练跑在抢占式实例上风险太大；disaggregated 虽能把两者独立放在抢占式与预留实例上，却对传统 on-policy 训练造成 gap 与 bubble、降低利用率；近期 off-policy 解耦方案在有足够抢占式实例时能摊薄气泡，但可用性一降就把 rollout 时间拉长、在训练侧预留实例上留下气泡〔05:10〕。于是他提出混合架构：按可用性自适应地把工作负载卸载到抢占式实例，不足时仍留一小部分 rollout 任务在预留实例上、后接训练任务，使两类机器都被利用并能适配不同可用性水平〔06:14〕。系统由抢占式池（含 rollout worker）与预留池（含可在 rollout 与训练间切换的多角色 worker）组成，每个 worker 配一个 transfer agent 专职搬运模型权重，使权重更新不影响计算进度，另有一个叫 rollout manager 的专用 API 服务器，在 token 级别监控所有响应并协调 rollout 与训练节点间的工作负载〔06:45〕。三个核心挑战是：抢占随时可能发生，须以最小浪费处理；如何乐观地收割不断变化的实例可用性；以及运行时持续平衡各 rollout worker 负载，因为响应长度事先不可知〔07:24〕。（YouTube EPYbh1WWBkHvc，[18-453]，L1）
- 〔强化学习系统学术会议报告（推测）〕第一个挑战：抢占可能发生在序列生成中途。某实例用 prompt 生成三个 token 后就被抢占，常规做法会丢掉全部进度；但 rollout manager 以 token 级别收集全部响应进度，于是能把原 prompt 与已生成 token 拼成新 prompt、在另一台机器上继续生成，对进度近乎零浪费；自回归生成受内存瓶颈限制、计算本身未被充分利用，这一请求迁移机制也让系统对可用性变化更有弹性〔08:12〕。第二个挑战对应部分响应卸载：若因 spot 实例不足而把一部分 rollout 请求卸载到 spot，起初没问题，但一旦预留实例上出现超长序列，它会阻塞后续所有进度、在预留侧造成巨大气泡，进而拖慢整个训练，使预留侧与抢占侧双双低效〔09:08〕。他们的做法是不对这种会导致尾延迟的超长序列继续生成，而是设一个时间窗，到点就把该序列迁到抢占侧继续，让预留侧切回训练模式、按微批继续，rollout 的响应持续流向预留机器，只需为最后一个微批付出延迟；节省十分显著，且该时间窗会随 rollout 与训练实例的可用性被动态调整〔09:50〕〔10:22〕〔10:26〕。第三个挑战是运行时负载均衡：分配前无法预测响应长度，即使初始每个实例分到的请求数相同，负载也会随时间偏离，因此 rollout manager 持续盯住 rollout 过程中的待处理请求，把请求从繁忙实例迁到空闲实例，以最小化落后者带来的尾延迟〔10:47〕。评估使用了真实 spot 实例轨迹的三个代表性片段，覆盖不同级别的抢占率与可用性；不只对比 co-located 与 disaggregated 架构，还用上了 GPU 更少、网络带宽更低的真实碎片化实例；对 spot 成本的估计刻意保守，只按每小时节省七成五而非九成计算〔11:30〕〔12:12〕。结果上，吞吐几乎与可用实例数成正比，说明弹性收割效率很高、几乎零开销；在可用性良好但抢占频繁的片段 A，吞吐依然稳定，因为抢占处理几乎零浪费；即便可用实例数骤降，一旦实例回升也能快速恢复，因为预留与 spot 之间的动态平衡保证两类机器始终被充分使用〔12:37〕。与多个基线相比，它成本效率始终最好，较解耦基线节省高达 49%；作者又加了一个把预留实例数翻倍的基线，其性能反而下降，因为 co-located 架构在交换模型状态时通信开销很高，而这里 rollout 与训练已解耦，token 交换很轻、效率随规模线性扩展〔13:20〕。最后他把系统定位为对既有 RL 系统的一个增益：云上抢占式实例可用时就收割它们，即便最差情况下 spot 可用性走低也仍保持基线系统性能，做到“zero hurt to your original architecture or infrastructure”，终极目标是让 RL 更可负担〔14:06〕。（YouTube EPYbh1WWBkHvc，[453-888]，L1）
