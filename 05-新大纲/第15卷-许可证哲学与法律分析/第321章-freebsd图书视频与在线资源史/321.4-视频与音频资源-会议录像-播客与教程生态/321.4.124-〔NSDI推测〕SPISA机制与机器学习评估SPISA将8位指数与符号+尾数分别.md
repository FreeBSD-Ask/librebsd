# 321.4.124 〔NSDI推测〕SPISA机制与机器学习评估SPISA将8位指数与符号+尾数分别

- 〔NSDI（推测）〕S-PISA 机制与机器学习评估。S-PISA 将 8 位指数与符号+尾数分别存入不同流水级的内存（后者按二进制补码编码以便加减），聚合时仅执行提取、对齐与加减，把临时指数与尾数保留在流水线内直至端主机再做重归一化与组装；并复用 TCAM 的 LPM 路由表按掩码匹配模拟前导零计数，生成保证隐含 1 正确位置的移位动作表。在 Intel Tofino 上以 P4 实现后发现 VLIW 指令槽饱和，提出双操作数移位指令；针对端主机昂贵的字节序转换提出交换机电路级重排的硬件增强，开销可忽略且远便宜于标准浮点单元。以分布式机器学习训练评估：FP32/FP16 下 S-PISA 精度曲线与标准曲线高度重叠，相对定点量化的 SwitchML，端主机 8 核时快 35%、2 核时超 40%，并降低端主机资源消耗。（YouTube EPJTAupxdwKkY，[480-969]，L1）
- 〔会议不详〕Relief：以页级旁路延长 NAND 闪存寿命。讲者对闪存块持续编程并监测每页误码率，发现各页退化速度差异巨大，而实践中最弱页失效即被闪存控制器将整块标记为坏块，浪费其余仍可写的页。为此提出 relief 状态：编程时跳过弱页继续下一页；基于两颗不同厂商 NAND 芯片以 25%、50%、70% relief 率实测耐久度随 relief 率相应延长；结合 MLC 中 LSB/MSB 页对的结构，仅编程 LSB、旁路 MSB 的 half relief 相当于 SLC 模式，写速度比 MSB 编程快 3-4 倍，以容量换性能，由此形成旁路两页的 full relief 与仅旁路 MSB 的 half relief 两类。热数据聚集形成的热块写频繁、占比小，是 relief 机制的完美候选，配合磨损均衡最终每块都会获得 relief 机会。（YouTube EPJUuyoYnh4ck，[9-751]，L1）
- 〔会议不详〕响应式/主动策略与混合 FTL 集成评估。响应式策略在页错误率越过中间阈值时判定弱页并予以旁路（首被标记页用激进的 full relief、后段用更高效的 half relief），需每页 2 比特状态、每块最多 32 字节记录、最坏每次编程附加一次读（约 10% 写开销）；主动（proactive）策略利用页号与耐久度强相关的先验数据，用离线构建的查找表推测 relief 周期数并对齐其余页，仅需每块 16 位计数器与 1-2KB 可压缩查找表。将两种策略集成到混合 FTL（Rose 与 Kombu，页级缓冲+块级数据映射，relief 应用于热分区）上仿真金融应用、MSR Cambridge 追踪及自采家用服务器追踪等基准：芯片二平均寿命延长 44%（Kombu）到 48%（Rose）、多数超 50%，得益于 half relief 的 SLC 模式执行时间总体持平甚至更低；芯片一因架构干扰小提升有限（+6%/+3%），Q&A 讨论了块级映射 FTL 下该思路不适用与数据保持时间至多 2% 的轻微退化。（YouTube EPJUuyoYnh4ck，[751-1501]，L1）
- 〔CoNEXT（推测）〕TCP 在可重构数据中心网络（RCDN）中失效。主讲人 Christopher Cannell（CMU，与 UC San Diego 合作，主要由 Matt Mukerjee 完成）定义 RCDN：在传统 Clos/Fat Tree 分组网络上叠加 8-10 倍带宽的临时可重构电路网络（60GHz 无线、光路交换或自由空间光），且近年电路重构时延降低 10 倍使电路更短更频繁、利于更动态的工作负载。基于自建模拟器的实验（16 条长流、10Gbps 分组网 + 80Gbps 电路网）显示没有任何 TCP 变体取得超过约 55% 的电路利用率：180 微秒的电路仅有几个 RTT，不足以让 TCP 把发送速率提高 8 倍，而该网络的带宽波动比 TCP 设计假设频繁且剧烈一个数量级，破坏了网络稳定性的隐含假设，需要 TCP 反应速度的数量级转变。（YouTube EPJX-1KpLVgbA，[6-647]，L1）
- 〔CoNEXT（推测）〕动态缓冲区调整与 RETCP。第一项技术在网络侧：电路激活前透明放大 ToR 交换机队列，给 TCP 增长拥塞窗口的空间，实验显示提前 1800 微秒重 sizing 达到延迟-利用率权衡最优点的 90% 利用率，但尾延迟仍有 2 倍增长。第二项技术 RETCP 让发送端 TCP 栈显式响应电路状态：复用 ECN echo 位标记 ACK（分组网标 0、电路网标 1），发送端检测 0→1 状态转移后按系数 alpha 乘性增减拥塞窗口（一次性状态转移而非重复触发）；仅需 200 微秒预缓冲即达 93% 利用率、尾延迟仅增 1.2 倍，比纯动态缓冲少一个数量级的预缓冲。Q&A 讨论了与一个 RTT 即收敛的速率型拥塞控制方案的对比，以及电路切换期间的包乱序问题（模拟器在重构期间同时禁用两个网络以抑制乱序）。（YouTube EPJX-1KpLVgbA，[647-1294]，L1）
- 〔会议不详〕边缘 SoC 集群上的高密度移动云游戏。讲者（北京邮电大学 BUPT，与导师 Shangguang、Mengwei 合作）指出移动云游戏把游戏置于云端推流给端用户，可提供即时访问、高兼容性与更低硬件成本；传统方案在 Intel/ARM CPU 上做移动环境模拟并配服务器级 GPU，存在模拟性能损失、需游戏再工程与游戏可用性受限三大问题。而把多个移动处理器聚成 SoC 集群（高通骁龙 865）可提供与用户手机一致的移动环境且部署简单（一游戏一 SoC）；主要缺陷是游戏部署密度低：专用部署每 SoC 一个实例，预剖析的共置方案下 5 款游戏中 4 款每 SoC 只能承载 1 个游戏会话，多共置一个会话即浪费 50% 以上 CPU 与 25% GPU 资源，GPU 容量成为部署密度瓶颈，而先前云游戏系统拆分近端/远端后远端 GPU 负载几乎不降。（YouTube EPJX7yKeX7SmE，[16-457]，L1）
- 〔会议不详〕SFG 系统的设计与评估。SFG 采用两个技术：渲染管线前的游戏分区（类似计算机图形学的 sort-first rendering，用抽象矩形表示目标渲染区域并支持运行时调整，平均降低 GPU 负载 15%，使单个 SoC 无法支撑的游戏能跑在两个 SoC 上）与 NPU 增强的分区协调（假设游戏以原生分辨率渲染帧，GPU 资源不足时先渲染低分辨率帧，再由量化 EDSR 模型经 TensorFlow Lite 在空闲的 SoC NPU 上超分到原生分辨率）。系统实现为 Unity 插件并用 WebRTC 传输游戏状态与渲染结果，在 16 颗骁龙 865 的集群上：16 个 SoC 支持多达 13 个游戏，会话数较专用部署提升 4.5 倍、较先前共置方法提升 1.5 倍，FPS 仅有一款游戏从 54 降至 52，近 16% 的会话涉及帧超分；代码已开源。（YouTube EPJX7yKeX7SmE，[457-923]，L1）

- 〔USENIX ATC〕(推测)折磨数据库：模拟电源故障下的 ACID 测试。主讲人 Mai Zheng（俄亥俄州立大学，与 HP Labs 合作）开场即亮出结论：模拟电源故障下无一数据库全部通过测试。他们定义"干净终止（clean termination）"故障模型——故障后飞行中块无效、此前块持久且无损坏，并通过 iSCSI 层将被测数据库解耦、不修改内核以保高保真。三阶段框架为 worker 施加精心设计的负载、record and replay 在 SCSI 命令之下按最小原子块传输重放模拟故障点、checker 检查 ACID 违规；元数据行加时间戳的负载设计让原子性与顺序性检查变容易，多层 tracer 还关联时间戳、SCSI 命令号、文件与系统调用以提供上下文。（YouTube EPJemgH9dC744，[9.7-779.1]，L1）
- 〔USENIX ATC〕(推测)模式驱动的故障注入与根因诊断。基于早期轨迹总结出五种故障点模式（如 mmap 模式：内存映射文件在两次更新之间可被内核线程或文件系统非预期写入），故障注入策略按模式匹配打分排序、直接注入最易出错的高危点，取代穷举测试。8 个数据库（4 开源 4 商业）无一幸存，最常见为持久性（durability）违规，LMDB（转写听作 Lightning DB）仅极小比例故障即可触发但仍被模式法有效捕获；Tokyo Cabinet 案例揭示数据库开发者与 OS 实现者间关于 fsync 语义假设的鸿沟（失败原子 fsync 可解），模式法将所需测试点减少 19 倍以上、某库测试时间从两个多月缩到 3 天内。Q&A 中 Phil Bernstein（微软研究院）等就默认配置与隔离性检查提问。（YouTube EPJemgH9dC744，[781.6-1545.1]，L1）

- 〔SREcon〕(推测)四十年后配置依旧糟糕：把配置当 API 设计。Varnish 会把配置翻译成 C 编译为共享对象再执行，现代做法用 Lua/Python/Go text template，但 YAML 加 Go template 仍不理解结构与空白；所谓 configuration as code 的配置往往没有测试、用无类型语言写成。作者主张以 API 设计视角审视配置（适用 Hyrum's Law）：识别配置从简单值向复杂结构演化的时刻、设计匹配问题域的真实 API、在简单与复杂变体之间强制封装、弃用文本模板改用结构化生成，并建立覆盖全部选项空间的测试环境；同期 Jos Visser 与 Matt Proud 亦撰文讨论同一问题，可见这是热点话题。（YouTube EPJeoiLzlxiBI，[657.6-1256.0]，L1）
- 〔会议不详〕一毫秒的代价：延迟放大与排队论。ScyllaDB 开发者布道师 Avishai Shalom（Twitter @nukemberg）演示各阶段合计 16ms 的系统延迟被放大到 740ms。排队论速成：观测延迟等于排队等待加服务时间，队头阻塞会让一个 P99 拖慢队列中所有任务并恶化下一级甚至 P95；M/M/1 仿真显示队列几乎非空即满，Kingman 公式表明等待时间与变异系数的平方成正比，利用率逼近 100% 时延迟非线性飙升。磁盘、CPU、线程池、负载均衡器、连接池、锁、套接字等一切共享资源都是队列；相同服务台下单排队列吞吐更高延迟更低（如超市收银），且永远不要使用无界队列。（YouTube EPJgrcaK0WQCQ，[13.3-891.7]，L1）
- 〔会议不详〕对抗延迟放大的工程手段。超时值往往武断（如 HikariCP 获取连接最小超时 250ms 已不合时宜、memcache 场景等 100ms 不合理），应按分位数或直方图实测并动态化，timeout budget 沿请求上下文传递剩余预算以便提前中止或放宽等待；并行派发、投机执行、harvest and yield、投机重试（Cassandra/Scylla 驱动采用，需幂等 API）可显著降尾延迟。容量管理按 Little's law 限并发、封顶队列长度、自底向上传播 back pressure 到边缘做 load shedding，并按延迟特征拆分服务降方差、警惕无抢占运行时与 GC 拖尾；结论是栈底 1ms 可在 P99 放大为 10-50ms，必须主动对抗延迟放大。（YouTube EPJgrcaK0WQCQ，[860.2-1801.3]，L1）
