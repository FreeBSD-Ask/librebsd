- 〔USENIX ATC 2015（推测）〕主讲人 Jinglei Ren（转写音写为 Jing Lei）介绍与 Chieh-Jan Mike Liang（音写 Mike Thomas）、Yongwei Wu 合作、面向智能手机存储软件的“以内存为中心”设计，〔00:14〕"memory centric design of smartphone storage software"。切入点是用 Twitter 的 I/O 追踪说明几乎每行都是一次 fsync，而 fsync 昂贵，因为它要求把脏数据写回闪存〔00:49〕"it requires dirty data to be written back to flash"；既有研究表明这类行为同时损害能效与应用响应性，根因不在个别程序员，而在 "the fundamental design and assumptions about smartphone storage software"〔01:24〕。传统设计以文件系统为枢纽，写入先落 DRAM，回写靠 Android Linux 上约五秒的全局 flush 或显式 fsync，数据库又靠 fsync 保一致性，关键假设是数据只有落到闪存才算可靠〔02:46〕"reliable only when data has reached the flash media"；这使程序员陷入两难：旧存储沿用桌面与服务器二十余年、从未考虑能效与响应，反之把一切都 malloc 进 DRAM 会让操作系统内存管理变成噩梦、重启即丢。MobiFS 保持传统架构与接口、应用无需修改，只在文件系统内部加入新机制与新策略，核心差别是〔04:44〕"regard DRAM as a long-lived store instead of a cache"——写入一到 DRAM 即视为可靠，无论来自普通写还是 fsync；闪存退化为备份层，只在兼顾能效与响应的时机做检查点。可靠性有三条支撑：手机有电池供电内存（电池备份内存在服务器世界被视为可靠）；软件本身足够可靠——问卷中仅六成受访者能想起近几个月的操作系统崩溃〔06:26〕；应用因联网而健壮——Google Play 前六十二款应用中五十四款能容忍本地数据丢失，Pinterest 把资料存在服务器、Snapchat 三十天内重新登录消息仍可同步〔07:09〕。一致性方面把事务引入原有操作系统页缓存：对一组文件的写开启事务、写入不得覆盖前序事务的一致状态故采用 compare and write、事务关闭前新写入可合并，不同应用事务彼此独立以便做应用级优化。资源上援引 Windows XP 配 2GB 便“飞起”、如今多数手机同为 2GB 且活跃应用只有一两个，断言手机有富余内存可用作内存存储。系统名为 MobiFS，复用操作系统页缓存，每页由写日志（red log）中的一条记录引用，连续记录构成事务〔10:34〕；另一组洞察指出写能耗约为读能耗十五倍、而写入次数差异的影响在 1.5% 以内，故只需盯住写能耗、把落盘数据量压到最小〔11:58〕。（YouTube EPZM0S4tSCiZo，[10-751]，L1）
- 〔USENIX ATC 2015（推测）〕策略框架与实测结果。作者以 staleness（已写入内存却尚未检查点的量）为横轴、可合并比例 E 为纵轴做量化研究，不同应用的 E 曲线形状各异，反映 staleness 与能效之间的权衡〔12:44〕；原则是在没有充分理由时尽量降低 staleness，从而在曲线上取峰值——越过该点 E 下跌而 staleness 继续增长〔13:51〕。算法用连续写入的检测窗口，新写入到来时窗口滑动一步并把新的 E 比值喂给增量式线性回归，斜率低于阈值即建议做检查点；但算法只“建议”、只是让数据进入可检查点状态，真正何时落盘由响应性导向策略决定〔14:48〕。后者依据是必须有弹性时机，否则闪存活动会与用户交互冲突，最佳时机是设备空闲——例如用户正在阅读屏幕内容〔15:29〕；据此提出基于间隔预测的策略，把事务塞进相邻两次用户操作之间的 interval，并用状态机区分长间隔与短间隔两种模式（如刷信息流时先跳过数条再看一条）〔16:11〕。实现基于 Android 4.1，复用 ext4 与 btrfs 的闪存管理组件，实验结合追踪、基准与真实应用。结果：与 ext4 相比 MobiFS 平均减少闪存数据量 53%，逼近“完全不检查点”的理想线〔17:52〕；真机取三款同步频率不同的应用，整机能耗平均下降约 35.8%〔18:40〕；真实运行中文件系统 I/O 吞吐提升 18.8 倍，数据库基准事务吞吐提升 11.2 倍，脚本测量的平均用户操作延迟下降 51.6%〔19:36〕。对比工作：把耐久性与一致性耦合在其他领域已有先例，本工作贡献在智能手机场景及其自适应权衡；另一支以能效为目标的文献牺牲性能，而本工作两者兼得〔20:24〕。答疑中说明突然断电等同回到历史某时刻的数据状态，因为维护写日志且每个事务原子，一致性保证是“点时刻”的〔21:04〕；云同步时本地数据最坏落后约一分钟；关于用 I/O 去重或压缩减少闪存写入，答复是与计算开销的权衡，计算本身也耗能，故刻意采用简单线性回归而非多目标模型〔23:07〕；对不适用的应用（如密码管理器）目前按分区隔离，未来或向开发者与用户开放开关〔24:02〕。（YouTube EPZM0S4tSCiZo，[751-1485]，L1）
- 〔SREcon（转写明示）〕来自 SoundCloud 的 Vilda 讲“生产负载下的迁移”，〔00:05〕"migrations under production load. How to change your database without disrupting service"，并给出“行为不变、只变架构”的迁移定义〔01:43〕"a change in architecture without a change in behavior"——不是 alter table 式的表迁移，也不点评该用哪种数据库。她提出含一个“前置隐藏阶段”的四阶段法：先 justify 迁移，因为这类项目经常被低估，起步理由要比你以为的更硬〔02:30〕；随后 set up the writing，再 compare，通过在进程内比对结果或搭外部系统比对来确认数据正确性；接着 optimize 或 productionize，以你能承受的步速放量（有时一步到 100%、有时非常谨慎），直到延迟等目标达成；最后是最长的等待阶段，等到你信任新系统、能清理旧系统为止，期间会冒出度量、分析、文档、习惯、捷径与旧 hack 等意外〔03:54〕。第一个案例是 feed 迁移：系统从上游拉引用存进 Cassandra 并对外提供搜索结果，产品需求只是把某个 feed 换到新数据集〔05:16〕，起初“改用全新写路径、由轮询改为事件驱动”只是附带小事〔05:40〕。团队顺势想清理陈旧数据（数据模型不支持从 Cassandra 删除，删除只能回上游再问一遍），并想借机升级自托管集群的硬件。新集群接上新写路径后进入比对阶段；读路径无代码改动、数据模型完全相同，只需验数据，但因数据集不同无法直接比对，于是另起一个连新库的应用、再用外部程序同时查两边。此阶段严重超期——原定一两个月却拖得更久：先是奇怪的硬件退化逼得整集群重建（物理机、耗时），又发现上游投递有问题需重投全部，回填本身也有毛病，白白浪费大量时间〔07:56〕。最终比对正确后才发现，这根本不是数据集替换而是 Kafka 集成、是一次改写路径的迁移，直到此刻才意识到；而且数据本已在新旧两套里重复存在，除硬件升级外清陈旧数据的工作全属浪费〔09:01〕。回看若重来不会做迁移：只改写路径、数据库不动，硬件问题另案处理〔09:31〕。由于异步系统可容忍少量停机，切换当日即完成、优化阶段仅一两天；随后为确认可回滚等了两周、无异常再删旧代码与旧机器〔10:52〕。（YouTube EPZMxakAXB-nE，[5-714]，L1）
- 〔SREcon（转写明示）〕第二个案例是“数据库迁移”：一个明知很大、却非做不可的项目，起步于一年前、事后看推进得出乎意料地顺利〔11:54〕。服务是关键路径，每秒数万次请求、每次在数据库内放大一个数量级；它从 Kafka 队列消费 rule sets、存进 MySQL，再针对 SoundCloud 曲目给出判定〔12:21〕。两个问题：MySQL 逼近可支持的 QPS 上限（技术与组织原因混合——SoundCloud 基本不做分片 MySQL），且 MySQL 写太慢，批量更新时队列堆积导致新版本无法按时发布〔13:15〕；更根本的是数据模型不适合关系库、更适合键值库。迁移动因是技术与产品双重问题，但对 Cassandra 在该模型下的延迟是否有余量并不确定，仍先动手碰运气。新 Cassandra 集群独立消费同一 Kafka 队列，故两边写入起初互不关联——彼时一致并不重要〔14:36〕。要开始比对就必须把两边写入合并到同一组件、同时写，否则 Cassandra 更快会跑在前面，数据对不上、比对无意义〔15:00〕。读路径仍走 MySQL 立即返回，同时在后台读 Cassandra、比对结果并打点，马上查出若干写入错误；随后发现部分曲目在 Cassandra 缺 rule sets 而 MySQL 有，部分是曲目已被删，部分源于上游出错，还有一批是 MySQL 库比上游与 Kafka 集成更早、从未进过 Kafka 的历史数据〔16:10〕。判定修复上游超出范围，遂改为直接读 MySQL 数据、按 Cassandra 模型转换后直接写入（早先坚持走正常投递通道以验证其完备性，此处不再重要）；回填后再测达到 100% 正确，唯一例外是约六百万条中的 12 条，逐条排查都是 MySQL 与 Cassandra 写速差造成的竞态——请求与更新并发、Cassandra 刚写完而 MySQL 还在写〔17:24〕。恢复独立写入后，把读路径改为按百分比灰度标志在 Cassandra 与 MySQL 间切换（初始 0、全走 MySQL），谨慎放量：先撞到问题再迭代，尤其担心延迟；最终发现所有问题都在自家客户端代码而非 Cassandra，顺带摸清了命名混乱的 Cassandra 重试策略；结论是读延迟略升、写明显更快不再积压，附带效应是错误数还略降〔19:24〕。等待阶段须先能在无备份时信任新系统（值班工程师更熟 Cassandra 运维、补齐告警与备份工具、从两次宕机中学习），再等到能移除旧系统；Cassandra 已连续四到六个月 100% 承载，但 MySQL 仍因大量分析与业务依赖而保留、主要当分析工具用〔21:07〕。总结：迁移项目千差万别、难以预测却遵循共同模式——把理由想得比实际更硬、准备好变化，建写入，比对到所需正确度（未必 100%），优化到能吃下生产流量，然后等与清理，多久就多久〔22:27〕。（YouTube EPZMxakAXB-nE，[714-1424]，L1）
- 〔USENIX Security 2024（推测）〕介绍 OPTICKS——一套优化的密钥透明（key transparency）系统，主题是端到端加密通信系统中的密钥分发与校验，重点在端到端消息而非会议，〔00:08〕"Opticks, which is an optimized key transparency system"。端到端消息的意义是 Bob 发消息给 Alice 时在其设备上加密、在 Alice 设备上解密，服务提供商不应能解密阅读；尽管底下是复杂的棘轮协议，启动前都必须先拿到对方最新公钥〔00:38〕，而密钥会在重装应用或换机时改变；现行所有部署中服务提供商（如 Zoom 或 Meta）同时维护密钥目录并代用户分发公钥，于是无需额外校验它就能发起不可察觉的中间人攻击：自造密钥对，把假公钥当作 Alice 的告诉 Bob、同理告诉 Alice，随后解密、阅读并重新加密转发，全程无人察觉〔01:50〕。传统校验手段是 QR 码扫描（设备互置互扫）或安全串之类变体，可用性差、实践中使用率低；因此密钥透明试图自动化这一流程，让用户不必手动校验、由客户端在后台验证拿到的密钥彼此一致〔02:50〕。该领域已有近十年历史，首次部署是 Keybase 2014 年（面向 PGP 密钥分发而非加密消息，隐私要求略有不同），此后产业与学术界成果众多，IETF 也有工作组在标准化透明协议〔03:12〕。OPTICKS 的贡献有三：目前最简洁的密钥透明系统——简单、高效、易理解〔03:42〕；提供 OPTICKS 扩展，支持以往部署未涉及的特性，如缓存与账号下线〔04:12〕；以及一种分体架构，实现更可扩展、且可推广到其他设计（另一位作者 Kim 会深入讲）。系统概览：服务提供商仍维护密钥目录并做分发，但额外周期性地把对目录的签名承诺发布出来，且要求系统内所有方看到同一份承诺〔04:23〕；Bob 查询 Alice 公钥时同时得到密码学证明，其应用后台据此校验该密钥与已发布的目录承诺一致；Alice 也监控自身密钥历史、以同样方式验证与最新承诺一致；承诺发布在哪里（区块链属于很重的一种方案；第三方如 Amazon 则是 Meta WhatsApp 所用）留作开放问题〔05:09〕。核心密码构件是“只追加目录承诺”（append-only directory commitment, ADC）：论文中有有序零知识集合、历史字典等多层抽象，讲解时简化为目录即一组“标签-值”对，标签构成集合——此处标签是“用户名+版本号”，值是加密用公钥〔06:10〕。承诺是对整个密钥目录的简洁承诺、服务方可计算；关键性质是其后能不交互、且私有地证明某个带版本号的元素属于或不属于该目录，证明不得泄露集合的其他信息〔06:30〕；“只追加”意味着目录中不删除，并额外要求：给定两个承诺 C1、C2，服务方能生成“追加证明”，证明其中一个底层目录是另一个的子集。实现上仅用简单的密码积木——Merkle 哈希树与可验证随机函数〔07:26〕。（YouTube EPZN8uA0P_IT0，[8-451]，L1）
