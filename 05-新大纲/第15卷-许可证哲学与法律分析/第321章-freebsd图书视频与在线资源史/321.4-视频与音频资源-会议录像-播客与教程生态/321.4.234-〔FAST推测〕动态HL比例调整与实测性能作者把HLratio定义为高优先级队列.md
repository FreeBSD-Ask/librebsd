# 321.4.234 〔FAST推测〕动态HL比例调整与实测性能作者把HLratio定义为高优先级队列

- 〔FAST（推测）〕动态 HL 比例调整与实测性能。作者把 HL ratio 定义为高优先级队列与低优先级队列的权重之比，它代表 I/O 尺寸固定时快慢队列能产生的理想最大速度差：比例太小则节流能力不足、无法满足公平，比例太大又会推高 I/O 尾延迟（节流惩罚超出必要），故必须随流组合与 I/O 尺寸动态设定。实现上 D2FQ 周期性采集各流虚拟时间与 I/O 使用统计，用阈值 TW 检测不公平，一旦某流虚拟时间越过 TW 就计算虚拟时间最大与最小两条流的增量之比 Δvt_max/Δvt_mean 乘到旧 HL ratio 上再加大 1，以保证最慢流能追上最快流；公平已满足时则反向下调，此时用虚拟减速（只用高优先级队列时的估计带宽除以实际带宽）取所有活跃流的最大值作为新的 HL ratio。系统实现于 Linux 内核，实验使用支持 NVMe WRR 的三星 SSD，与 BFQ 及 MQFQ 对比，负载为 FIO 合成负载与 YCSB+RocksDB 真实负载：四流权重 8:6:4:2 时三家都能公平分配带宽，但只有 D2FQ 与 MQFQ 用满设备带宽，且 D2FQ 的 CPU 占用比 MQFQ 低 45%；动态 HL ratio 在流数与权重动态变化时比静态 3 更公平、比静态 128 尾延迟更低；未饱和场景下单线程 8 KB 随机读、深度 1 到 16 时延迟、带宽与 CPU 表现接近无调度（None），并可与异步 I/O 堆栈组合成 LLG Queue 方案，在 I/O 延迟、带宽与 CPU 占用上均占优。（YouTube EPZEPlvDOsfWw，[319-767]，L1）
- 〔USENIX ATC（推测）〕Violet：面向按字节寻址的用户态存储栈。来自 Argonne 的 Doug Santi 介绍，主机侧 I/O 层正在出现：许多应用把主机闪存放上 PCI 总线、绕过网络跳数来持久化状态，SAP HANA 一类内存数据库更把整个工作集放进 DRAM，用途也从企业关键分析扩展到 OLAP、OLTP、DSS、ERP；但 DRAM 易失仍需持久层，HANA 的持久层本质是只写工作负载，只是仍做逻辑事务日志，数据结构上却仍在用数十年沉淀下来的表与列，等于只因为 DRAM 快而快（作者甚至认为它差不多就是把 MonetDB 跑在 RAM 盘上）。他把问题归结为字节世界被强行折进面向块的机械世界：应用按计算便利选择内存数据结构（比如 STL 的 std::map），持久化时又得用迭代器把它摊平成数组写出、读回再逐条插回，既慢又是腐败来源，因为物理映射被甩给了应用。于是需要一层与数据结构选择解耦的字节导向持久层：Violet 把程序里的匿名堆/BSS 命名为文件（named heap），无缝复制其更新并自动保持一致，提供字节导向的快照与数据管理。架构由若干带本地盘的数据海绵（data sponges）与一个 master controller 组成，应用连入 Violet 用户态库、向 master 申请文件并由其组装复制组，数据路径经用户态直连复制组、完全绕过内核，仅控制路径仍走内核。（YouTube EPZH9Ja5GflP4，[9-466]，L1）
- 〔USENIX ATC（推测）〕TSX 指令插桩、Fibonacci 数组与实测开销。Violet 的接口建立在两条趋势的汇合上：C++ 标准化进程正在把事务变成语言级关键字（IBM、Intel、HP、Oracle 等推动），而 Intel TSX 的受限事务内存提供了硬件执行机制，编译器很快会用到 TSX；团队改造 Clang++ 识别新的 transaction 关键字，并用一个汇编前处理器插桩，以兼容任意编译器甚至任意语言。以向链表插入节点为例，transaction 块内保证原子性、一致性与隔离性但不保证持久性，volatile new 用来接管堆分配（因为库负责内存一致性），编译后发出 xbegin 与 xend 指令，并在所有内存赋值后调用 add_to_write_set 检查被赋值地址是否落在受管堆内，若是则把该内存位置的更新跨网络传播并持久化；但 TSX 事务内不能发系统调用、连操作系统抢占都会导致事务中止，因此在 xend 之后更新已对所有线程可见却尚未落网，存在非零 RPO，只能保证持久镜像一致（库内维护单调递增序列号与一致性点），而当 NVM 或 SCM 到位时该窗口不再重要。数据海绵端用 Fibonacci 数组把海量 8 字节级随机小更新（如链表指针）聚合成按地址排序的 patch 流（含地址、长度与数据），先在 NVM 中累积再分块写盘，相邻两级被占满即归并（按内存序已排序，归并平凡），因每级是前两级之和而文件高度为 log 1.618；同一地址取最低层条目即最新版本，据此可低成本做 Fibonacci 快照，新条目是全新信息而非写时复制。实测插桩开销极小（判断地址是否落在范围内只是几次整数比较且所需数据通常在 CPU 缓存中）；同步两阶段提交在以太网上不可行，因为以太网往返约 250 微秒而事务只有约 100 纳秒；Fibonacci 数组稳定跑到约 60 MB/s，而朴素文件方式（读整页、改字节、写回）低于 1 MB/s，且增加数据海绵数量、扩大复制组可显著缩短恢复时间。（YouTube EPZH9Ja5GflP4，[488-1094]，L1）
- 〔OSDI（推测）〕用基于图的 oracle 构造检测数据库引擎的事务性缺陷。来自 ETH Zurich 的 Zuming Jiang 以银行转账为例说明事务的意义：给 Mary 转 100 美元需要两条 UPDATE，若先扣减成功而加钱失败，这 100 美元就凭空消失；用 START TRANSACTION 与 COMMIT 把语句分组可保证整体成功或整体失败，杜绝部分成功。事务除金融外还广泛用于医疗、航空与社交媒体，而并发控制（如多版本并发控制或两阶段锁）实现复杂、极易出错，因此崩溃类缺陷容易检测（并发发送事务、引擎崩溃即缺陷），正确性缺陷却因没有崩溃这样的信号而很难发现。对简单事务还能推断期望结果再与实际结果比对，但一旦事务变复杂就失效——例如 UPDATE 中带子查询、子查询内用聚合函数 MIN 又带谓词，无法预测哪些行会被处理，因而无法推断该语句的期望结果。关键思路是不直接推断期望结果，而是在保持语义的前提下重排事务内部的语句，用重排后的用例产出结果作为 oracle；示例中左侧事务改了 table 1 的两行而重排后只改一行，即为缺陷（且是 MySQL 中的真实 bug），该方法在 MySQL、MariaDB、TiDB 三款流行 DBMS 上共发现 50 多个缺陷。（YouTube EPZJ54e28dIK0，[16-396]，L1）
- 〔OSDI（推测）〕TxCheck 的实现流程与实验结果。工具先随机生成若干事务送入被测 DBMS、取得执行结果，再结合生成用例做分析并产出重排用例；重排用例保证与原用例结果相同，送回 DBMS 再跑一遍，两次结果不一致即判定为缺陷。关键在分析与重排：先从用例抽取论文提出的语句依赖图（有向图，描述一条语句的结果是否依赖另一条语句的执行），对它做拓扑排序得到语句序列，再按该序列生成重排用例，最后比对两次执行结果。方法开源为 TxCheck，用于测试 MySQL、MariaDB、TiDB 三款 DBMS，共发现 56 个缺陷，其中 30 个与事务执行相关、19 个由该 oracle 发现。作者总结：数据库事务的正确性缺陷因缺乏 oracle 而难找，事务越复杂越难，因此提出语义不变地重排事务内语句这一通用思路，以重排用例作为 oracle 校验原始用例是否产出期望结果，并已开源实现。（YouTube EPZJ54e28dIK0，[396-620]，L1）
- 〔HotCloud（推测）〕Jobber：自动化云中的跨租户信任。来自 University of Colorado Boulder 的 Andy Saylor（导师为 Eric Keller 与 Dirk Grunwald）从如何让数据中心更高效、更安全、更可管理出发指出：云使用快速增长，而研究称数据中心全部流量中有 10% 到 40% 是跨租户流量（如广告网络与托管在同一机柜的网站、CDN 与 ISP 之间），但既有数据中心研究几乎都在做隔离、把所有流量当不可信处理，缺乏任何机制来识别同机柜、可信的合作方，于是可信内部流量也被送过防火墙与入侵检测，既浪费计算资源又极易出错。既有做法（业务方对签一堆法律文件、人工配置防火墙放行特定主机、搭建 VPN 隧道）充满静态手工配置，而安全失效多源于管理员配错；云中虚拟机频繁生灭，静态手工配置更加不成立。Jobber 因此提出一套网络安全架构（有原型但架构本身可换实现），由三件组件拼成：其一用信任网络自动判定可信流量，具体采用 Introduction Based Routing（IBR）——是否信任某人取决于你对中介的信任，中介若引荐了坏对象、双方结束信任时会把反馈回传给中介、降低其今后获得信任连接的能力，形成只敢善意引荐的经济激励；其二用网络传感器数据自动得出租户信誉，自建框架从 syslog、IDS 等多源采集（类似 Nagios 的通用接口），经采样限流与管理员定义的好坏行为分类后按租户聚合出信誉分并暴露查询接口；其三用可编程路由（SDN 与 OpenFlow、MPLS、GRE、EC2 VPC 等 API）把流量实际引导到可信或不可信路径，原型基于 Floodlight 控制器与 Mininet 仿真。（YouTube EPZJCJ3L6E4hc，[9-845]，L1）
- 〔HotCloud（推测）〕三种架构、当前进度与开销分析。Jobber 给出三套架构：第一套适合今天就能部署的遗留数据中心但需要主机感知——Jobber client 跑在每台虚拟机里，识别到入站连接后联系本机 Jobber server 查询对端租户信誉、必要时经 IBR 握手，可信后由虚拟机自建隧道或放开防火墙端口；第二套仍面向遗留环境但去掉主机改造，由 Jobber server 主动查询安全中间设备发现流并完成握手，租户仅通过 VPC 之类的路由表 API 把自己的流量改指过去，虚拟机对此无感知；第三套面向未来数据中心，把 Jobber 作为数据中心级 SDN 控制器上的一个应用，由交换机基础设施识别跨租户流并在相关租户间协商（多租户时经 IBR 引荐），借数据中心的集中视图降低 IBR 信任路径搜索的计算难度，同时坚持是否信任仍由各租户自行决定、信誉不下沉到数据中心。团队强调这仍是早期工作：架构设计已完成、各设计中的底层技术已有概念原型，正在做最终 SDN 架构的完整系统与遗留架构的部分原型，尚未做到可测性能的水平，也需再做可用性评估；对手模型上允许被信任的服务遭入侵后动态切断信任连接，最终架构的可信计算基必须包含云服务商与租户自己的 Jobber server；由于 SDN 的开销主要发生在流建立之初，一旦信任路径建成并更新好路由表，之后基本不再额外增加开销。（YouTube EPZJCJ3L6E4hc，[884-1678]，L1）
- 〔SREcon（推测）〕把根因定位从找证据退一步到缩小排查范围。来自百度智能运维团队的 Yu Chen 介绍，最初目标是输出导致服务故障的程序与数据变更，但因缺乏把现象与更新关联的证据而做不到，于是把目标降为把排查范围收敛到根因所属的模块——这已足够让值班工程师选择止损动作、让开发工程师去研读该模块，并宣称该算法能把诊断时间降低 80%、且只需极少量人工配置。他与值班工程师访谈后梳理出人工流程：先由前端模块 PV 大量丢失感知故障，再取整个服务的调用图，从前端模块 A 开始逐层下探其直接依赖模块、检查少量指标，若判定异常就把嫌疑下移，直到不能再下移为止（示例中 G 无直接依赖即被标为根因，若 G 正常则 E 成为根因）。一个直接的优化是做一个显示调用图并自动用颜色标注异常模块的工具：灰色表示按历史数据期望的响应时间，彩色表示期望与当前的差值，绿色代表变快、偏黄代表变慢、超阈值则标红，而各模块阈值不同、颜色本身就给出了建议，工程师往往直接看直方图而不再用调用图；但该半自动方案有三处局限——调用图需随系统演进手工同步（老系统中间件五花八门、无法靠挖掘中间件日志得到）、golden metrics 必须手工维护因为新故障类型常需要新指标、以及同一产品在多个数据中心内各需看一份调用图。（YouTube EPZJnq0NaYBIM，[10-442]，L1）
- 〔SREcon（推测）〕基于核密度估计与 DBSCAN 的自动指标筛查算法。目标是去掉对 golden metrics 的硬依赖、算法要能适配性质各异的指标并给出可解释的定量推荐。算法从实例级指标出发：对指标做异常度量、按所属实例聚合异常分得到测量向量，在模块内且同一数据中心内聚类，最后对结果排序。异常度量聚焦突变（突增或突降），因为多数故障会在某些指标上表现为突变、工程师也容易看懂，只需比较故障前后数据：取故障前 60 分钟窗口与故障后 5 分钟窗口（后窗更短是因为其长度会计入故障持续时间，5 分钟是经验上的平衡点），把问题形式化为已知 xi 来自某未知分布时观测到 yj 的条件概率，并定义上溢概率（随机变量大于 yj）与下溢概率（小于 yj）来区分突增与突降；用核密度估计把每个 xi 展开为一个均值为该值、标准差为整体标准差若干倍的核分布再取平均，一般用高斯核，计数类指标（每秒收发包数）用泊松核、取值被限制在 0 到 1 的指标（CPU 利用率或空闲率）用 Beta 核；假设各 yj 独立，取单点概率的几何平均（对数域下退化为算术平均，也消除了不同采集周期导致的点数差异），异常分即负对数概率，从而跨指标、跨实例可比。聚类推荐 DBSCAN，因为它不需要预先指定簇数还能自动剪掉脏数据，产物是每个摘要（digest）含一批异常实例与相关异常指标集合；排序只看实例占比、异常指标数量与异常程度三个因子，输出四列表格（模块名、占比、实例列表、指标列表），示例中 G 因覆盖 30% 实例居首且指标显示其过载，排在第二的 E 因直接依赖 G 而响应变慢、需要建立更多连接。用 70 个历史案例（根因都能反映在 Linux 标准性能指标上）评估：60 例把根因诊断排到第一，Top-1 准确率超过 80%；人工诊断耗时从 6 分钟到 2 小时以上、平均 35 分钟，而算法执行时间小于 6 分钟。（YouTube EPZJnq0NaYBIM，[442-1078]，L1）
