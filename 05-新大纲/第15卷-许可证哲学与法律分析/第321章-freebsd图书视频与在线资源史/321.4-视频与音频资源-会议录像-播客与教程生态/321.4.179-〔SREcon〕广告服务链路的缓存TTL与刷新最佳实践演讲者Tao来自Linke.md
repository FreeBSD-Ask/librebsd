- 〔SREcon〕广告服务链路的缓存 TTL 与刷新最佳实践。演讲者 Tao 来自 LinkedIn 广告服务基础设施团队，分享一套已在生产环境验证的缓存策略；缓存无处不在——CPU 缓存通过降低访存回退率提升运行速度、浏览器缓存避免重复下载内容、Redis 与 Memcached 等远端缓存加速应用（他也开玩笑提了《反恐精英》里那张叫 Cache 的地图，但本篇只谈传统缓存实现），传统 read-through 结构就是在服务与数据库之间加一层缓存（本地或远端）以降低 QPS、改善时延并提升可扩展性与用户体验，典型实现是建一个缓存（多数是 LRU）、设固定 TTL（如 5 分钟）、读取时先查缓存、miss 则回源 DB 并回填，据他说约九成缓存都这么写，但在某些角落场景会把系统打得很难看——他复盘自家广告跟踪系统：每个用户点击事件都要对照广告主设置做校验、这些设置存在 DB 并被本地缓存，某天 DB 崩溃，5 分钟后缓存开始过期、系统取不到设置、跟踪事件处理停摆，10 分钟后 SRE 才发现并切流到其他数据中心，而这 10 分钟里仍有大量事件堆积。由此得出核心洞察：大多数系统对数据陈旧的容忍度远大于 TTL 设定（他们希望 5 分钟内刷新，但最多可容忍 30 分钟陈旧），因此引入软 TTL 与硬 TTL——软 TTL 到期系统尝试刷新数据但条目在硬 TTL 前仍留在缓存中，两者间隔提供足够的缓解缓冲，再叠加异步缓存刷新（首个读取发生后数据稍后落缓存，缓存自身启动守护线程在软 TTL 后周期性刷新，硬 TTL 到期才删除），使读者总能从本地缓存取到新鲜数据，从而既不等待 DB 调用、对热数据也不再出现 miss、同时提升数据新鲜度；此外 TTL 不必是静态值，可按数据变更频率动态调整（频繁变更用短 TTL、罕见更新用长 TTL，可从 DB 回源回调中作为反馈学习），对定时任务（如每分钟跑一次）产生的固定间隔访问其缓存项会同时过期并触发对 DB 的首次流量冲击、难以扩展且易压垮 DB，可用高低水位加随机延迟把 DB QPS 抹平，对真正需要新鲜度的缓存可建通知管道让系统直接感知 DB 变更并推送更新后的新值到缓存、或简单地只删掉 key 让应用回源，若更新 QPS 很高则需在中间加过滤器以降低管道开销。（YouTube EPTDoEYzVuxwo，[14-547]，L1）
- 〔SREcon〕缓存回源、预热与内存效率的工程经验。回源侧他复盘一次真实生产事故：广告跟踪系统为提升排序速度缓存了大量数据、其中一些热特征几乎被所有请求使用，某天这些缓存特征几乎同时过期，全部请求回源导致 DB 过载、响应极慢，回源超时又无法回填缓存，随后更多条目过期、更多请求回源，最终把 DB 彻底打崩，由此总结三条教训：一是对回源成本做去重，不要为同一 key 并发发起多个回源、只发一个请求并把其余相同 key 的请求置为等待直到拿到 DB 反馈再唤醒；二是在独立缓存线程中跑 DB 回源，主请求激进超时先返回以及时服务用户、DB 稍后响应再回填供后续同 key 请求直接命中（若追求极快读取也可只读缓存不等回源，代价是预热期性能差但稳定后整体时延低）；三是缓存部分结果、空结果与错误状态——批量 get 要接受 DB 的部分结果并缓存、DB 中不存在则缓存空占位以减少回源量、回源抛错也缓存其错误状态并把错误当空处理以避免压垮已有问题的 DB，同时给错误状态设更短 TTL 使 DB 一恢复系统立刻回到正常。预热侧：重启服务（尤其每日发版清空内存缓存）、迁移到新主机、以及新代码带来的缓存 schema 变更都会导致无缓存与显著降级，因此关闭时把缓存持久化到本地磁盘、重启时加载，但务必记得先做 TTL 校验（主机宕机几天后磁盘缓存可能极旧、会让系统进入完全不可预期的状态），若预热代价很高（一两小时才能完全预热）可周期性 flush 以防范被 SIGKILL 之类的意外崩溃；跨主机部署没有本地数据时可建“缓存系统”从对等节点拷贝缓存文件（同集群主机多服务相同流量、缓存内容高度重合），或在能接受额外开销时直接用共享远端缓存；schema 演进建议用向后兼容的新 schema 以复用旧缓存项，代价是新代码有 bug 会污染数据且回滚代码也修不好，因此建议保留强制 bootstrap 的能力即清掉整个缓存并让节点从 DB 重载。内存效率侧：优先内存友好的数据结构——Java 原始类型通常只占 4 字节而对装箱对象占 16 字节约差 4 倍，建议把整数列表改成原始类型数组、小 Java 类拍平成扁平结构，其中一个数据结构从 7 GB 降到 700 MB（约 10 倍），去重与移除冗余对象（例如把空列表指向 Collections utils 中的不可变空集合），对 JSON 这类含大量冗余字符串（memberId、scores 等）的格式用符号表把字符串映射成整数并在 JSON 中存整数引用、在 LinkedIn REST API 系统中省约 4 倍空间；远端缓存里内存通常不是问题（加机器即可）而 RPC 成为新瓶颈、主要贡献者并非网络而是 schema 的序列化/反序列化，因此要选高效 schema——特定 schema（Protocol Buffers、Avro）通常快于 JSON、MessagePack 这类通用 schema，最后给出分片：数据集持续增长时单机再也装不下全部热数据，若延迟约束严格到无法访问 Redis、Memcached 等远端缓存，就把集群切成多个 shard、每个 shard 负责内容的一个子集（原先每个节点都要负责 C1–C4、分片后各只负责一半）从而可横向扩展，例如引入 4 个 shard 使单机缓存规模降到 25%。（YouTube EPTDoEYzVuxwo，[549-1546]，L1）
- 〔USENIX Security〕Themis：区分合法与非法 MoAS 以加速路由起源劫持检测。清华大学博士生兰程沁（Chengqin Lan）介绍 Themis 系统；论文指出起源劫持是最常见的 BGP 劫持类型、通常由配置错误或恶意攻击引发，分精确前缀起源劫持（劫持者宣告与受害者相同的前缀并重定向正常路由）与子前缀起源劫持（宣告受害者的一个子前缀、因 BGP 中更具体的前缀优先而可污染整个互联网），此类劫持往往持续时间不长但会造成严重的路由与安全问题如流量中断和经济损失——仅去年 BGPmon 就检测到 775 起主要 BGP 路由劫持事件、引发大规模网络中断。既有防御机制分两类：主动预防通常用密码学为某前缀的所有合法起源 AS 预先授权，但只有全部 AS 都部署才真正有效、这路还很长，因此许多网络更依赖被动检测，即由遍布全球的 BGP 监控点观察 BGP 更新并在发现劫持时告警，以 Argus 为代表的最新系统结合控制面分析与数据平面探测——先在控制面基于历史 BGP 数据检出所有 MoAS 冲突（MoAS 是 BGP 中的一个特殊现象，指多个 AS 同时起源同一个地址块），然后对每个 MoAS 冲突做两路探测并结合数据平面可达性信息识别起源劫持。问题在于绝大多数 MoAS 冲突其实是合法的（多由企业合作、IP 地址转移或 DDoS 防护导致），而现有 BGP 劫持检测机制无法凭控制面信息有效区分合法 MoAS 与起源劫持，因此仍需数据平面探测甚至人工核验；由于现实里合法 MoAS 远比起源劫持常见，海量合法冲突会消耗相当多的探测与核验资源，显著增加验证成本与延迟。（YouTube EPTERIK_0X6ng，[8-325]，L1）
- 〔USENIX Security〕MoAS 特征刻画、机器学习分类器与 Themis 系统设计。论文做法是先识别合法 MoAS 的潜在成因与真实劫持的行为特征、再训练机器学习分类器区分二者，最终提出 Themis 系统以节省验证成本与时延；Ground truth 数据集包含起源劫持与合法 MoAS 两类：劫持样本取自 BGPmon 并用四种过滤器人工核验，合法 MoAS 冲突取自 IRR 但只保留同样出现在 BGP 中的记录以避免配置错误，据此识别出六项主导特征：一是前缀类型（虽然目标是区分劫持与合法 MoAS，但精确前缀合法 MoAS 与子前缀合法 MoAS 在若干特征上差异显著），二是 AS 排名差（合法 MoAS 的整体排名差远小于其他三类 MoAS，且 80% 的精确合法 MoAS 冲突排名差为零），三是业务关系比例（受排名差结果启发假设合法 MoAS 中的 AS 间必然存在潜在业务关系，度量不同业务关系占比后发现合法 MoAS 与起源劫持在 P2C 比例与组织关系上有清晰区分），四是地理关系（考虑邻接、同国、同 RIR 三种，结果多数合法 MoAS 冲突发生在同一国家或同一 RIR 内），五是宣告活跃度（部分劫持者在劫持前长期不出现在全球路由表中，而合法 AS 通常在日常 BGP 更新中近乎连续地宣告前缀），六是受害规模与 RIR 分布（一个劫持者可能同时攻击数百个受害者而合法 AS 通常只出现在有限的 MoAS 冲突中，并计算受害者 RIR 分布的 Gini 系数、观察起源劫持的 Gini 系数高于合法 MoAS）。据此选出能很好刻画这六类特征的 26 个特征训练分类器，在 ground truth 上的 out-of-bag 准确率为 95.49%，实践中部署该分类器可在召回 99.2% 的前提下显著降低既有控制面分析的误报；Themis 把 MoAS 分类器与既有检测系统结合并从 RPKI 与 IRR 收集更多信息以构建更完整更准确的 prefix ownership 数据库——收到实时 BGP 更新时监控先检查更新中的前缀与起源 AS 是否与本地 prefix ownership 数据库一致，出现 MoAS 冲突时先用分类器划分为潜在劫持与合法冲突，之后只需对潜在劫持做数据平面探测以识别真实起源劫持（探测可沿用既有系统的数据平面识别方法），评测显示引入 MoAS 分类器后 Themis 大幅加速起源劫持检测且准确率与 Argus 几乎相当。（YouTube EPTERIK_0X6ng，[325-616]，L1）
- 〔USENIX Security 2023（推测）〕Vectravisor：让未修改的程序直接在 GPU 上并行运行。主讲人 Sam 是普林斯顿大学即将进入第六年的博士生，与 UBC（不列颠哥伦比亚大学）的 Muhammad Shahrad 及导师 Mike Freedman 合作完成。他指出到 2023 年 GPU 编程仍要在 DSL、自写编译器与 CUDA/OpenCL 等低级框架之间艰难取舍，因而在 DSL 或编译器这条路之外提出向量化整程序翻译：把单线程程序编译为 WebAssembly 中间表示、再编译成 OpenCL C 以兼容多家 GPU 厂商，然后在 GPU 上并发运行大量副本自动获得并行度，从而无需改写程序、并与 CPU 代码保持同等正确性。系统为每个 VM 的整个地址空间做内存交织，把相邻字节放到相邻位置，只要有跨 VM 访问局部性就能隐式完成内存合并，并借助 WebAssembly 的栈机语义把栈上的值直接装入 GPU 远大的寄存器文件。（YouTube EPTElCneM9UxQ，[16-665]，L1）
- 〔USENIX Security 2023（推测）〕用 CPS 与蹦床补齐递归、间接调用与抢占。由于 OpenCL C 明确禁止递归与间接函数调用，作者采用 CPS with trampolines 重写控制流，把这三类缺失能力统一化为循环迭代，从而使在任意位置抢占并进出 GPU 成为可能；主机侧用只暴露 WebAssembly 系统接口、不含任何代码与数据的微型 VM 执行系统调用，借 Wasm 的能力安全模型隔离各 VM 之间交互，并用重叠 I/O 让下一批 VM 的请求在上一批仍在 GPU 运行时入队。评测从 GitHub 与 crates.io 拉取百万级下载的开源仓库，包括 PDF 处理与改写为 Go 的 strings-go（需在 GPU 上跑完整垃圾回收），在显存 16 至 24 GB 的卡上可并发数千个各占 3 至 4 MB 的 VM；多数基准吞吐超过带 AVX-512 的 4 vCPU 计算优化型实例，在最贴近手写优化的 Gaussian Blur（BlurBMP）基准上，按每美元吞吐首次追平并略微超过手写 CUDA 版本。（YouTube EPTElCneM9UxQ，[702-1496]，L1）
- 〔ACM CoNEXT 2020（推测）〕P4RTC：把 P4 语言带到运行时完备（RTC）架构芯片。主讲人 Haojun 介绍这项来自华为公司与南京大学的经验论文。P4 是用于定义自定义包处理逻辑并编译到 Tofino 等可编程数据面的高层网络编程语言，但现有管道型架构存在两项挑战：可编程性受限（各级可用周期与处理单元层数有限、依赖会额外占用处理单元层，程序最大逻辑长度受限；且跨处理单元层无法访问同一存储器，导致选最小计数器等逻辑难以实现），以及下一代 Tofino 芯片停摆，短期内看不到新的 Tbps 级 P4 可编程交换机。P4RTC 因此以新架构模型并行执行、存储器在所有处理单元间共享，引入前台管道处理报文、后台管道以无限循环运行入口与出口控制块并可自行构造报文，并加入 foreach、continue、break、sleep、return 等控制流扩展与片上/片外、内容寻址（精确匹配、LPM）/线性寻址（计数器、寄存器）表类型扩展，允许报文在数据平面直接操作表项。（YouTube EPTGw9M5zYpXc，[16-472]，L1）
- 〔ACM CoNEXT 2020（推测）〕表部署优化、性能验证与逐流计量落地。编译阶段需在满足存储池资源约束的前提下放置表项，作者以表分片（把表拆成多片分散到多个存储池，容纳单池放不下的大表并均衡过载表）与表复制（复制读密集表以均衡负载，但会给数据写请求带来额外开销）两种策略为基础，用整数线性规划以最小化最大存储池负载为目标自动求解；由于表被众多处理器共享，热点表所在存储池常成瓶颈，且流量由 TCP 主导转向 RDMA 主导会带来显著性能退化，故采用画像指导优化按实时负载重新部署表项，并用基于 ESL 方法的性能模型在部署前完成代码画像、流量生成、周期近似仿真与指标输出的验证。系统已在华为 NetEngine 8000 F81C 路由器上原型化（1.2 Tbps RTC 芯片、8 GB HBM），其逐流精确计量系统支持多达五千万并发流、输出流量不到输入流量的 0.5%，且因可在数据平面直接插入精确匹配表项而不再像 Tofino 上那样触发哈希冲突驱逐。（YouTube EPTGw9M5zYpXc，[489-902]，L1）
- 〔USENIX Security（推测）〕VoltPwn：纯软件方式攻击 SGX 加密 enclaves 的完整性。主讲人 Tommaso Frassetto 来自德国达姆施塔特工业大学，并与加州大学尔湾分校研究者合作。现代处理器为延长电池寿命、防止过热而把电压与频率控制交给操作系统，这为恶意内核留下攻击面，而该攻击不需要任何硬件改装、物理访问，也不依赖侧信道泄漏；相比三年前在 USENIX Security 上演示于 ARM 上的 Clockwork，x86 只能选择 Intel 预定义且经充分测试的电压频率组合、所有核共享同一电压频率使攻击脚本自身也会受影响、多数接口未文档化、还有机器检查架构（MCA）会纠正运行期错误，因此难度大得多。攻击者先用公开 MSR 选定 P-State，再借助社区称之 OC mailbox 的未文档化寄存器写入负电压偏移，使处理器欠压运行。（YouTube EPTH709b_NJBU，[7-341]，L1）
