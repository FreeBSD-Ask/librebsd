# 321.4.55 〔会议不详〕FastACS架构跨集群复制与实验评估系统由实时提取器生成消息流并分

- 〔会议不详〕FastACS 架构、跨集群复制与实验评估。系统由实时提取器生成消息流并分片（shard，片内全序），跨集群复制采用以带宽代价为权重、带最大深度与扇出约束的 Prim 最小生成树（copy tree，典型深度约 4 节点），沿途设 readers/writers 与调度器（支持 orphaned 模式与经文件锁的 overtake，调度器不可用时流不中断）；存储分两层——L2 为 Google 2003 年开发的分布式文件系统 Colossus（只追加、RPC 读写、层次目录兼作发现），L1 为基于 RDMA 的易失分布式键值存储 ClickMap（写走 RPC、读走 RDMA、一致哈希、R=3 副本，最小化复制 Colossus 特性），上载数据缓存（4 KB 分块、按最久未修改淘汰、文件路径+分块序号唯一定位）与元数据缓存（文件长度与 best-effort 文件锁），缓存缺失时回退 Colossus。评估：实验一扩至约 8000 消费者无 Colossus 回退、投递延迟 500 ms（系统仅新增 100 ms）、支撑 70 Gbps；实验二（480 Mbps 写入、缓存层横向扩展）在叶子集群扩至 2 万消费者、消费者带宽达 1.8 Tbps，哈希取模变更期间出现短暂回退后稳定；消融实验移除缓存层后 Colossus 因网络拥塞大量不可用错误；系统约 2.5 万行代码，生产 p99 延迟 730 ms、缓存有效性 99.9% 并以此提供 SLO。（YouTube EP5QVWLXBHw4A，[259.0-934.3]，L1）
- 〔会议不详〕基于结构相似性的错误规格推断与 bug 检测（ESSS）。主讲人针对静态分析检测错误检查 bug 的三类问题——错误检查（如 OpenSSL 中函数返回值与 0 比较而 0 也是可能返回值）、缺失检查（如 libxml2 中第二个 if 检查因 ret val 赋值缺失而无效）与经隐式/显式类型转换的错误传播 bug——梳理错误建模的两类方法：按惯例（null、ret val、goto error 等关键字）与按规格（函数及其错误返回值列表，如 malloc 返回 0、open 返回 -1），并对比 EASy（人工规格，先给领域知识再扩展）与 APEX、Ares、ESSS（自动推断）。ESSS 的核心论断是所有错误处理代码彼此之间比其周边代码更相似：从 LLVM 位码出发，把代码段简化为控制流摘要后做相似性匹配（如长度为 2 的子序列匹配），把最佳匹配标记为错误处理块，从而推断函数的错误返回值；对找不到相似代码的孤立检查，再用关联分析——若其中出现频繁出现在错误处理代码中的典型函数（如 erase、malloc）则判定该代码与错误处理相关；整个流程迭代至不动点后检测规格违规。（YouTube EP5eIrd7bHy9I，[7.8-362.6]，L1）
- 〔会议不详〕ESSS 在 7 个开源项目上的评估与对比 EASy 的可扩展性。在 OpenSSL、OpenSSH、PHP 解释器、Zlib、libpng、FreeType、libwebp 七个项目上运行，报告以 OpenSSL 与 PHP（最大代码库）最多，缺失检查类 bug 占多数；人工核查 827 个报告，541 个为真阳性，并向 3 个项目提交 46 个最严重 bug 的补丁且全部被上游接受（OpenSSL 16 个、OpenSSH 1 个、PHP 29 个含一个 CVE）。误报分析：OpenSSL 误报率最高，源于其“先参数校验调用、后正式工作调用”的双重调用编码模式导致第二次调用被误标为缺失检查；PHP 次之，Zlib 再次，其余项目低于 25%。与 EASy 对比：EASy 分析 OpenSSL 约 3 分钟、20 GB 内存，但在 128 GB 机器上分析 PHP 仍内存溢出；ESSS 时间与内存低一个数量级，可完整分析 PHP，且 4 个项目亚秒级完成，适合未来集成进 IDE 插件为程序员提供即时反馈，工具与 artifact 均已开源并完成评估。（YouTube EP5eIrd7bHy9I，[363.9-621.3]，L1）
- 〔会议不详〕FlexCore：可编程交换机的运行时可编程性（架构与部分重编译）。主讲人指出 P4 交换机仅编译时可编程，重编译并重刷流水线会造成停机与丢包，需流量 join/unjoin 与精细调度，因此改动只能低频且由运维驱动；为快速部署新网络功能（实时防御攻击、即时网络优化、租户级网络扩展）需要零停机、零丢包、强一致的运行时可编程性。FlexCore 是支持活动程序升级的全栈生态：交换机硬件采用增强的解聚合 RMT（D-RMT）架构，计算与内存解耦，内存组织为跨 mesh 互联处理器共享的分片集中式内存组并做负载均衡以减少访问冲突，多个微动作处理器以 run-to-completion 方式并行处理报文；部分重编译基于指针间接机制，核心数据结构为由 P4 程序生成的程序描述表（PDTab，每项记录 match-action 表的键、键类型、指向表项的内存指针及指向下一表的 next-table 指针），运行时原子切换指针即可在不刷新整条流水线的情况下插入或切换表；重配置原语涵盖 match-action 表、控制流分支与解析器，均由硬件保证原子性（报文只经变更前或变更后的程序处理）。（YouTube EP5m7B7wiyRaI，[12.7-495.0]，L1）
- 〔会议不详〕FlexEdge 版本控制、多级一致性与多步事务及评估。程序级升级涉及多个离散改动，多次调用原子原语可能暴露导致未定义行为的中间状态，FlexCore 设计基于全局版本号的 FlexEdge（版本控制机制，版本号为 0 时报文走旧 P4 程序、置 1 则全体报文同时切换到新版本）实现单事务升级；但单事务需同时准备全部差异、瞬时开销可能超过交换机 headroom 而失败（如先释放被删表 D 的资源再插入表 E 则可成功），故引入多步事务与多级一致性：最强的程序一致性（单事务完成全部更新、开销最高）、居中的元素一致性、最弱的执行一致性（逐 pass 完成且保证报文只经旧 pass 或新 pass）。实现于 NVIDIA Spectrum-2 芯片（12.8 Tbps）与基于 BMv2、支持全部重配置原语与三级一致性的软件模拟器；加速多播案例研究显示：运行时把单播程序换成多播可显著改善作业完成时间，遥测确认重配置全程零丢包，移除多播节省 29 秒流水线延迟；愿景论文发表于 HotNets（转写音校正），终极目标是端到端（主机网络栈、智能网卡与所有交换机）的运行时可编程网络。（YouTube EP5m7B7wiyRaI，[498.0-936.4]，L1）
- 〔NSDI（推测）〕神威·太湖之光 I/O 转发架构与 FFM 的问题。来自清华大学与无锡超算中心的主讲人（与山东大学、卡塔尔计算研究院、埃默里大学合作）介绍部署在世界第三大超级计算机上的 I/O 资源分配优化：神威·太湖之光拥有 40 个机柜、4 万余计算节点（1000 万余核），客户端运行基于 GlusterFS 的轻量用户态文件系统、后端为 288 个 Lustre 存储节点（每节点为 OSS，节点对接 read 六阵列上的 OST，共 10 PB），中间 240 个转发节点经两条分离的高速 InfiniBand 互联连接计算与存储域，现有 FFM（固定转发映射）按 512 个计算节点（即 2 个 supernode）对应 1 个转发节点静态映射，仅消耗 80 个可用转发节点。问题在于：FFM 无视应用 I/O 行为差异（WRF 一写一、AWP N 写一、其余 N 写 N 等模式各异，且分别偏带宽、IOPS 或元数据），I/O 干扰显著——共享模式下 AWP 慢 4%、LAMMPS 慢 24%、神图引擎 I/O 时间增至三倍，且大作业只要一个转发节点被“讨厌邻居”共享即全作业受损；还存在 fail-slow 节点（第 8、34 号转发节点仅有约 10% 的正常性能）且用户无从察觉。（YouTube EP5yJoJm387cE，[10.6-693.5]，L1）
- 〔NSDI（推测）〕DFRA 动态转发资源分配、干扰研究与部署效果。DFRA（Dynamic Forwarding Resource Allocation）的核心思想是仅在必要时升级作业的转发节点分配：对高 I/O 需求作业按“执行 I/O 的计算节点数×单节点峰值带宽÷单转发节点带宽”计算并升级分配，对干扰邻居则不改数量而给予独占转发节点实现隔离（以“旅馆分房”作类比）；判断依据来自端到端监控系统 Beacon（姊妹论文 End-to-end I/O Monitoring on a Leading Supercomputer，主讲人称刚在本届 NSDI 报告）。干扰研究（8 个典型应用两两并行、512:1 共享转发节点）发现 N 写一模式不仅慢还极具破坏性（可拖慢邻居至百倍，原因是海量请求压垮转发节点请求队列与线程池）、元数据密集型作业因元数据请求优先级更高而成为“欺凌者”，干扰根因归结为 N 写一模式、元数据重负载与高带宽负载；DFRA 在 Slurm 调度器内以 C 与 Python 实现，按作业重映射、因转发节点充裕而不执行降级。自去年 2 月起部分部署于生产系统（用户经作业提交参数 opt-in，未来转 opt-out）：18 个月历史数据显示约 14% 的作业符合升级条件却消耗 80% 的核时，DFRA 下最高 I/O 慢化因子降至 1.1，重映射仅需几秒，平均每作业节省执行时间 6 分钟以上、8 个月估计节省 2 亿核时；历史数据还显示约 90% 的大型应用 I/O 行为从不改变。（YouTube EP5yJoJm387cE，[693.6-1753.8]，L1）
- 〔会议不详〕OctoSketch：多核软件网络监控的动机与整 sketch 合并设计的瓶颈。主讲人（与 University of Maryland 的 Pei Qin 与 Liu 教授合作，转写音校正）指出虚拟化趋势下大量网络管理应用在 Open vSwitch 等软件平台内监控流量，摩尔定律放缓与高带宽链路普及使单核已无法饱和带宽，应用需多核处理数百 Gbps 流量；负载均衡（识别 heavy hitters 并重分布大流）、入侵检测（识别 super spreaders）等应用需要跨核聚合流量统计，而每核维护全精度统计代价过高，需采用 count-min sketch（配合堆存储重流）等 sketch 算法以小内存、有界误差换取高吞吐。现有两条路线均有缺陷：按键把键固定到核会因流量偏斜导致核间负载失衡，且键定义（如按源 IP）与网卡五元组分发方式不匹配时常无法固定；整 sketch 合并（多个 worker 各自维护 sketch 并定期发给聚合器以 sum/max 等合并）则因计数器呈重尾分布（以 count-min sketch 识别 heavy hitter 为例，评估中 80% 以上计数器不变、部分变化超过 1000）而浪费大量计算与通信，导致关键计数器更新延迟、查询结果陈旧，且每核维护含 flow key 存储的完整 sketch 实例本身即是先验研究确认的性能瓶颈。（YouTube EP65chjQ7QwK4，[15.8-411.8]，L1）
- 〔会议不详〕OctoSketch 三个设计要点与评估。一是连续变化通知机制：每个 worker 只向聚合器推送变化足够大的计数器（按 sketch 类型定义“足够变化”以保持通用性），把大 sketch 合并摊销为逐计数器通知，并给出解析证明其保持与流量不分片的理想场景相同的渐近误差界，任意查询时刻都可给出有界误差的全核聚合结果，已应用于 6 类任务 9 种代表性 sketch；二是按报文到达率在 worker 与聚合器间动态分配资源：统一阈值控制推送（变化超过阈值即推入共享队列），聚合器周期性测量队列长度调整阈值（队列短则降低阈值以提高在线精度），也支持按精度目标计算发送率下界、释放多余计算资源等策略；三是重构 sketch、把 flow key 存储从 worker 中移除、只留聚合器维护，worker 仅发送潜在重流键。评估覆盖三种平台（如 DPDK）与负载均衡、键值缓存两个用例：heavy hitter 估计误差因连续变化机制而接近理想场景，整 sketch 合并则随合并周期波动；6 个 worker 时吞吐比整 sketch 合并高约 2000 万包/秒、每 worker CPU 占用低约 20%；整体较先前整 sketch 合并误差低约 15.6 倍、吞吐最高提升 4.5 倍，无 flow key 存储的 sketch 开销低于 10%；源码已发布在 GitHub（转写音校正）。（YouTube EP65chjQ7QwK4，[412.4-836.4]，L1）
- 〔会议不详〕ScaleDB：异步更新范围索引的可串行化内存数据库（问题与关键观察）。主讲人指出内存数据库历经十年研究的瓶颈已从存储转向多核 CPU 争用，而范围索引尤其难扩展——一篇 SIGMOD 2018 论文对比六种最佳范围索引设计后结论是无一扩展良好，根源在于层次化数据结构在争用下天然受限，但支持有序快速扫描又离不开范围索引。以 B+ 树上两事务分别插入键 15 和 35 为例，节点自旋锁可沿满内部节点向上蔓延到根；但结合数据库使用场景（主范围索引支持点查询与有序扫描、二级索引支持分析查询）可见：真正导致扩展性差的是当前架构下两事务在提交时同步更新所有范围索引，而若数据库保证可串行化，两条记录以任意顺序插入都不违反该保证——这种非必要争用被命名为机制争用（mechanism contention），其核心思想是把系统向客户端提供的保证与其实现机制分离。配套的写至范围扫描延迟实验（对 OLTP 基准套件中 TPC-C、AuctionMark、SEATS 三个写强度与扫描比例各异的基准插桩测量）证明：对范围查询而言读到刚写入的记录是例外而非规则（点查询则低延迟常见）。（YouTube EP6ETh2WfbpMU，[15.7-381.2]，L1）
- 〔会议不详〕ScaleDB 两大新机制（indexlet 与 ACC）及对 Cicada 的评估。其一是 indexlet：基于哈希的临时数据结构，以表主键为键、每表恰有一个，事务提交时同步记录全部增改删，通过限制每个 indexlet 持有的写入量免除 rehash，并按线程合并纪元（merge epoch）在纪元末把写入批量原子刷入范围索引，从而避免机制争用；其二是为该架构新设计的异步并发控制协议 ACC（基于乐观并发控制）：点查询先查 indexlet 再查范围索引，范围查询直接走范围索引，幻读（phantom）问题由 phantomlet（幻读检测 indexlet，每个主/二级范围索引各一）解决——提交时向受影响范围索引的 phantomlet 插入幻读指示符（以索引节点内存地址与当前版本号拼接为键、计数器为值），验证事务据此检查并中止。评估在 36 核 Intel 机器（每线程绑核）上对比 SIGMOD 2017 的 Cicada（TPC-C 低争用配置，仓库数=线程数）：ScaleDB（仅共享索引配置）相对单核 goodput 扩展 22.3 倍，而 Cicada 共享索引配置因范围索引机制争用（体现为索引版本验证失败导致的大量事务中止）仅扩展 6.4 倍（分区配置 20 倍），ScaleDB 吞吐高 1.8 倍；其整体中止率在 TPC-C 上随线程数保持很低，仅做多次范围扫描的 delivery 与 stock level 事务有非可忽略中止率且趋于稳定；代码即将发布。（YouTube EP6ETh2WfbpMU，[408.7-928.4]，L1）
