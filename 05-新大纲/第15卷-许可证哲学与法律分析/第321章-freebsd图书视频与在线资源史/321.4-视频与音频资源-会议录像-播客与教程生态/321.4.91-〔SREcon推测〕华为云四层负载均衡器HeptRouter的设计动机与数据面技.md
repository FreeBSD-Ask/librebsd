# 321.4.91 〔SREcon推测〕华为云四层负载均衡器HeptRouter的设计动机与数据面技

- 〔SREcon（推测）〕华为云四层负载均衡器 HeptRouter 的设计动机与数据面技术选型。主讲人 James 来自华为云可靠性实验室，合作者来自华为爱尔兰研究中心（去年曾分享七层数据面系统 Orion，已开源），华为云拥有 33 个以上公有 region 且以每年约 20% 增长，并建立覆盖设计、验证测试、变更管理与数据运维的 deterministic operation（terminus operation）框架。因 Nginx、Envoy 等七层 LB 对节点故障不具弹性、会打乱 TCP 连接，需在 L7 之前部署 L4，基于 anycast（多服务器共享同一 IP 经 BGP 通告）与 ECMP（按五元组哈希选路），采用一致性哈希做负载均衡、连接跟踪保住已建立连接，并只处理 ingress 流量、响应经默认网关直接返回（DSR）以简化 L4——第一条经验是 L4/L7 协同设计可降低整体成本并提升可靠性。数据面目标为接近线速（每核每秒超 1000 万包、纳秒级包处理）、高可扩展、高可靠与面向未来，Linux 内核栈因上下文切换与 skbuff 分配难以满足，在 XDP（eBPF 内核态、编程模型受限、需每网卡挂载难以支持多网卡）与 DPDK（用户态全接管网卡、原生多网卡与 huge page 但需独占网卡与 CPU 核、轮询模式空载仍占满 CPU）之间选择 DPDK。（YouTube EP0melA289C2E，[18-1098]，L1）
- 〔SREcon（推测）〕自愈隔离、去中心化控制面、爆炸半径与可观测性五条经验。用户态内核旁路是双刃剑：可开发特性丰富的超低延迟部署但限制硬件与内核能力的复用。自愈与隔离应为一等设计原则：数据面节点内控制器收集指标与 BGP speaker 健康检查，隔离节点时不回撤 BGP 而是在 AS path 前置 AS 号，借路径长度路由避开故障节点，即使误判其余节点仍能正常收流。控制面选择去中心化 P2P 变体以最小化外部依赖并抵抗网络分区：每节点持有全量数据、以 gossip 协议达成最终一致、版本号处理冲突、双向 gRPC 全互联形成强一致的 island，island 间弱连接上分区仍可工作；华为爱尔兰形式化验证团队严格验证系统规范并发现穷尽单元与集成测试未捕获的 bond 构建重试数不可预测 bug。运维卓越上，cell 架构配合 shuffle sharding（10 节点每分片随机取 2 个共 45 个虚拟分片，单分片故障影响仅 1/45）将爆炸半径降低约十分之一；可观测性以 CUJ（critical user journey）为顶层框架，经 tracing 与 span 指标转换精确定位 DPDK 难以监控的数据面延迟与正确性，最终总结六条经验。（YouTube EP0melA289C2E，[1099-2016]，L1）
- 〔SREcon（推测）〕Kubernetes 落地的前两个陷阱：容器化改造与资源规划。主讲人 King 是 Zappi（通过消费者测试帮助品牌做广告与创新决策）的基础设施工程师，团队三人在 AWS 上用 Kops 自管集群运行 Kubernetes 生产环境已四年，认为 Kops 生成的状态文件与 Terraform 配置均可版本化为源码，暂无更换必要。第一陷阱是容器化：应用 Docker 化带来陡峭学习曲线，CI/CD 管线需围绕镜像缓存重构（曾有一个 6GB 镜像拖慢构建与部署），需解决构建期 SSH 私钥与 API token 等密钥传递（社区常用多阶段构建避免密钥分层进入镜像），运行时需处理信号（Nginx 与 Resque 的优雅终止依赖 SIGQUIT，需用 stop signal 调整）、日志落点、指标采集与资源 requests 设置，并适配自动扩缩容、Pod 驱逐、卷绑定及 inter-pod affinity、taints/tolerations 等非确定性调度，基础设施侧还需权衡每应用一个负载均衡器还是 ingress、DNS、SSL 终止与 CDN/WAF 集成。第二陷阱是资源规划：调度 bin packing 是尽力而为，三个简化例子说明每节点必然浪费核心与内存（如 3 核 3GB 工作负载配 5 核 5GB 节点每节点浪费 2 核 2GB），按 requests 调度但可用至 limits 导致紧密打包节点无余量；非 Pod 组件（sshd、kubelet、容器运行时）常被忽视，需理解 kube-reserved、system-reserved、驱逐阈值与 allocatable 四类节点资源；CPU 节流由内核 CFS quota 实现，部分旧内核存在配额用尽前提前节流的 bug，可调高 limit、完全移除 CPU limit 或禁用/调小 CFS quota period。（YouTube EP0tnIS0Bgjy8，[8-1035.8]，L1）
- 〔SREcon（推测）〕Kubernetes 的成本、运维学习曲线与安全工具链陷阱。成本方面：生产就绪集群空载即需支付控制面费用（托管集群按小时计费、自管集群付节点与 EBS 资源），高可用至少 3 个 master 且通常跨 3 个 AZ 造成高额数据传输费，节点上 Fluentd、Prometheus node exporter、Calico/Weave/Flannel 等 DaemonSet 代理开销累加，还需 Prometheus 与 Elasticsearch 等日志与指标栈支撑；Kubernetes 无原生成本归属方案，需考虑 GPU、数据传输、共享卷、托管数据库与 on-demand/reserved/spot 混合计价，另有开源项目尝试基于原生 Kubernetes 概念做实时成本分摊。运维认知负载高：核心组件加 auto scaling、metrics、networking/DNS、Ingress 等大量 add-on 几乎不可能全掌握。工具与安全方面：Kubernetes 默认不安全，建议启用 RBAC（默认全拒绝、可细到资源与动作粒度）、静态加密、审计日志、禁用控制面公网访问与 kubelet 只读端口及匿名认证、禁止默认 service account token 自动挂载，并用 Network Policies（Pod 默认接受任意来源流量）与 Pod Security Policies（禁止特权容器与提权、限制 hostPath 与 root）加固；但传统安全工具在容器世界纷纷失效：网络漏洞扫描器面对随机端口与漂移节点失效、SSH PAM 双因素随 exec 命令消失（容器内失去用户身份）、容器短生命周期令取证困难、商用 IDS/IPS 按节点计费且需运行代理成本高昂，团队转向可自管的开源工具。结论：Kubernetes 对小团队可能过度，建议先容器化并采用 ECS 等更简单编排，安全决策应尽早而非事后，核心仍是平衡可靠性、风险与成本。（YouTube EP0tnIS0Bgjy8，[1040-2188]，L1）
- 〔会议不详〕高速 SSD 时代 I/O 完成机制的三难困境。主讲人为 UCI 博士、现就职于三星的 Dongju，介绍论文工作 DeepPath：SSD 已进入十几微秒时代，十到十五微秒量级下每一微秒软件开销都不再是噪音，而大量栈的默认 I/O 完成机制仍是基于中断的。中断是固定税负（提交/完成处理、上下文切换、缓存污染、电源状态切换）且不随设备变快而缩小，还会拖慢从完成到下一次提交的路径；在 Optane 设备上经典轮询较中断提升约 28% IOPS、TLC 上约 7%，收益因隐式开销消除而放大。但纯轮询烧满 CPU 核，CPU 争用下崩溃（单核 100% CPU 且不随线程扩展，而中断在 4 线程下用约 60% CPU 获得约 4-5 倍吞吐）；混合轮询先睡后醒再轮询，问题归结为选对睡眠时长：睡少浪费 CPU、睡多直接加延迟。现有基于 epoch 统计的混合轮询每 100 毫秒更新估计并取均值一半作安全边际，但既不及时（须等下个 epoch）也不准确（观测到的总 I/O 时间混入自身超睡与调度延迟，无法区分 SSD 变慢与醒得太晚），形成越睡越久的正反馈失效模式，且即便估计完美仍付定时器与睡眠唤醒、上下文切换、缓存污染与工作集重载开销。（YouTube EP137jn53rM1s，[18-340]，L1）
- 〔会议不详〕DeepPath：按 I/O 二值信号跟踪（PAS）与每核四态状态机动态切换。PAS 是新的 I/O 延迟跟踪机制：每次 I/O 后通过检查完成队列回答一个二值问题（队列仍 pending 即睡早了、已完成即睡晚了），得到干净的每 I/O 二值信号且不受超睡时长干扰；用仅 2 bit 记忆的微型反馈环处理四种情形（同向则同向加速调整、跨界则反向小步修正），无 epoch、无显式延迟测量，快速收敛到下包络并在延迟漂移时立即反应，而 epoch 方法按设计滞后、需多个 epoch 恢复。重 CPU 争用下 PAS 把所有唤醒记为超睡、持续压低睡眠直至趋零退化为带定时器开销的忙轮询（timer failure），这反而成为核心过载的强信号；DeepPath 据此以每核四态状态机（经典轮询、PAS normal、PAS overloaded、中断）按 timer failure 与队列深度安全切换——队列深度为 1 时上探经典轮询（限时窗口后回 PAS 复查），timer failure 宣告核心过载后由队列深度决定转向中断或恢复轮询，切换鲁棒不振荡。实现为块层内自包含小补丁、每核状态、无专用轮询线程，面向同步轮询路径，应用（FIO、经系统调用的 RocksDB）无需大改代码；在 20 核机器、含 Z-SSD 与商用 TLC 的 12 块 SSD 上评测：微基准中 PAS 较 Linux 混合轮询降低约 21 个百分点 CPU 占用且保持相近 I/O 性能，RocksDB 数据库负载下较中断提升 9%/7%/5% 吞吐，12 块 SSD 中 11 块领先、最后一块差距在数个百分点内，无需逐设备调优。（YouTube EP137jn53rM1s，[337-804]，L1）
- 〔HotStorage〕超低延迟 SSD 的能耗特征研究动机与测量方法。路易斯维尔大学的 Brian Harris 介绍对 Optane SSD 能耗特征及超低延迟存储对系统能效影响的研究：超低延迟（ULL）指约 10 微秒数据访问延迟的新一代存储，代表设备有三星 Z-SSD、东芝 XL-Flash 与 Intel Optane（基于 Intel 与 Micron 的 3D XPoint 相变存储技术），Optane 是当前最有前景、最普及且性价比最好的 ULL SSD。研究首要动机是节能，而现有 Optane 研究主要关注性能而非能效，涉及功耗者也只测单设备或 CPU 利用率而非整机功耗，3D XPoint 的功耗特性基本未知，且超低延迟设备对系统软件施压的影响无人研究。团队选取 HDD、两块闪存 SSD 与一块 Optane 四块价格相近（约两三百美元）的设备，代表磁、闪存与 3D XPoint 三代技术与 SATA、NVMe 两种接口，在一台 1U 戴尔企业服务器上用内嵌存储、经 USB 读出的串接式电力计量表测量（消除测量开销），FIO 以宽范围请求尺寸与队列深度的异步直通 I/O 推满设备。观察到 HDD 因盘片持续旋转空闲功耗高，闪存缓解了该问题，但 Optane 等高性能设备可能因高性能控制器设计、3D XPoint 内部物理与缺乏 APST（自主电源状态转换）支持而失去这一改善；新设备延迟更低、活跃功耗更高，且读写能耗不对称随代际更明显，其中 Optane 上 1KB 请求正是去年 HotStorage 论文《Towards an Unwritten Contract of Intel Optane SSD》指出应避免的微小请求。（YouTube EP18jCFlpHPf4，[9-355.9]，L1）
- 〔HotStorage〕能耗比例性、每焦耳性能与能效最佳实践及未来方向。能耗比例性指能耗与工作量成正比（理想机器空闲零功耗、满载峰值功耗），宽动态功耗范围是其关键特征：将系统功耗归一化后，HDD 功耗平坦完全不比例，闪存 SSD 更比例，Optane 最比例——功耗范围跨越超过峰值系统功耗的一半，最适合节能数据中心。超低延迟对系统软件施压：I/O 深度增大使中断率升至每秒约 60 万次；Optane 写在每秒 40 万次中断时占用约 300% 系统 CPU，而读在每秒 60 万次中断时仅约 100%，闪存 NVMe 亦有类似失衡，但功耗与 CPU 利用率不成正比（读的峰值功耗略高于写）。采用 Zadok 式能效指标 bytes per joule 与 IOPS per joule：大请求比小请求更高效（额外数据的传输能耗远小于请求本身的管理开销与系统软件压力），Optane 因完成更快而效率更高，1KB 微小请求低效，且 Optane 因内部并行度有限在 I/O 深度增大超过饱和点后能效不再提升，而闪存 NVMe 内部并行度更丰富、功耗增加对应持续提升的 I/O 性能。未来方向：为能效重新思考系统软件（轮询或混合轮询 vs 中断、io_uring 与 SPDK 等内核旁路新 I/O 接口、块多队列与 NVMe 接口的简化机制、I/O 调度算法），解释写用更多 CPU 但更少中断的读写不对称，评估存储子系统能耗是否被低估或忽视。（YouTube EP18jCFlpHPf4，[355.9-838]，L1）
- 〔会议不详〕RoboDB 的动机：消除复制键值存储中的冗余 compaction。主讲人 Haoyu 指出 Moore's law 已死、CPU 常成为系统瓶颈，LSM 树的后台 compaction（含 memtable flush）因需对输入文件全部键值对归并排序而高度吃 CPU，实验中最多占总 CPU 时间的 72%。在 R 副本复制设置（1 个 primary、R-1 个 secondary）中，写请求先达 primary 再转发各副本持久化，各实例写同样数据导致本质完全相同的 compaction 在主副本与 secondary 处重复发生。方案是只让 primary 做 compaction，将新 SST 文件经网络共享给 secondary 并在其上应用、删除对应输入，使整个复制组只做一次 compaction；由于集群中每台服务器通常同时有 primary 与 secondary，secondary 节省的 CPU 可供其上的 primary 使用。挑战有二：共享 SST 带来较重网络流量（可假设网络低利用率环境用网络换 CPU），以及文件落地本身经 open/write/close 引入重文件系统元数据开销。NVMe-oF（Non-Volatile Memory Express over Fabric，经 RDMA 或 TCP 传输、允许主机像本地文件系统一样挂载远端 NVMe 盘）的 target offloading 可在商用网卡上让 secondary CPU 完全旁路，但 NVMe-oF 工作于块层，会同时旁路 secondary 的文件系统：RocksDB 等 POSIX 接口使用者看不到传来的 SST 文件（报 no such file or directory），secondary 偶然创建的日志文件还可能覆写未分配的数据块。RoboDB 用 SST 文件预分配解决：利用 LSM 树中文件池最大数量与尺寸静态的性质在系统启动前预建 SST 池使两端文件系统都能看到文件，用位图记录槽位占用，primary 选取空闲槽位后以 Direct I/O 覆盖写确保数据落盘并触发 NVMe-oF 传输，再通知 secondary 该槽位文件已被共享。（YouTube EP1Sjf79QyvrM，[17-669]，L1）
