# 321.4.174 〔FAST〕LSU的副作用与数据一致性处理以及完整评估LSU的松同步带来两个副作

- 〔FAST〕LSU 的副作用与数据一致性处理，以及完整评估。LSU 的松同步带来两个副作用：一是 victim 选择次优（别的线程更新了 VPC 但本 DGC 看不到，导致 GC 写放大，评估中可忽略）；二是假阳性的 GC 读——DGC 读到 VPB 中某位为 1 就去读该页，但另一线程已把该位清掉、页变 stale，若照常写出会破坏数据一致性；解决办法是用 node 数据（inode 或 dnode）核对，若 node 内的 LBA 与 GC 读到的 LBA 不一致就判定该页 stale 并跳过写，且这步由 F2FS 已有的 node-level lock 保护，因此不引入额外锁开销。评估环境为 Intel Xeon + 160GB DRAM + Samsung 983 SSD，基线为内核 F2FS、纯 LFS 模式的 F2FS-L、最先进的可扩展 LFS MEX 与并行 GC 方案 PGC，ScaleLFS 在 F2FS 的 LFS 模式上做原型实现。micro benchmark 用 4KB 随机写：30GB 小分区（用以最小化 SSD 级 GC 的干扰）写入 120GB 时，执行时间最多快 7 倍，下发到 SSD 的写带宽最多高 19.6 倍；写满整盘 10.3TB 随机写时比 F2FS 少 37 分钟，而 F2FS-L 与 PGC 在 LFS 与 SSD 两级 GC 都启动后持续写带宽只有 11MB/s，ScaleLFS 则无明显退化。macro benchmark 用 Filebench 的三种写密集合成负载，吞吐最多提升 83.1%（低于 micro benchmark 是因为大量文件删除使 GC 不那么频繁，以及应用线程间竞争）；真实应用用 MySQL + YCSB（预置 650 万条记录、约占 70% 容量），写密集的 workload A 执行时间最多减少 70.4%，读密集的 workload B 减少 27.3%。（YouTube EPSmGh-HPySz0，[487-959]，L1）
- 〔BSDCan（推测）〕Jonas Amoson 报告将 NetSurf 浏览器移植到 Plan 9 的工作。NetSurf 是一个小而简单的浏览器，主体用 C89 编写，混有少量 C99 特性和 GCC 扩展，GPLv2 开源并自带渲染引擎，最初主要面向 RISC OS，也支持 Amiga、Atari ST、Haiku、BeOS，并可编译到 Linux 与 Windows；本 Plan 9 移植并非 NetSurf 仓库的官方一部分，它支持 HTML5 与相当多的 CSS、JavaScript，但远非完整支持。与 Firefox、Chrome 相比，NetSurf 功能更少、体积更小、在旧硬件上更快；与 Plan 9 自带的 Abaco、Mothra 相比则庞大得多、Web 技术支持也更多，用 asd 调试它时不得不大幅调大符号表 hash 尺寸以压低二进制的加载时间，使它远超 Plan 9 默认提供的其他二进制。此外 NetSurf 的开发独立于 Plan 9 进行，因此移植侧始终需要持续跟进上游特性与更新。（YouTube EPSn1_afvWohs，[20-291]，L1）
- 〔BSDCan（推测）〕Plan 9 移植的源码构成、前端取舍与三类移植挑战。上游源码由 core NetSurf 与一批各自拥有独立 git 仓库的支持库组成，Plan 9 移植同样各库独立成库：libcss 处理级联样式、libhub 是 HTML 解析库、libwebcs 做字符串缓存，浏览器自带 GIF 与 BMP 处理并把 svg-tiny 内置进来，另有 libnsfb 帧缓冲驱动（内含 widget、GUI 组件与字体处理，平台只需把图像复制到屏幕并分发事件）与自带日志库；内容分 content handler 与 content fetcher，上游取网内容用 libcurl。最初用 frame buffer 前端完成移植，但该前端已在新版 NetSurf 中废弃，被 Philippe Mechet 开发的原生前端取代——后者功能更多、支持 plumbing，大部分功能通过鼠标二键与三键的上下文菜单触达，运行在 APE 环境中，在网络场景（二进制跑在 cpu 服务器上、显示在终端上）快得多，因为它不必复制帧缓冲版那样的大块图像。移植挑战分三类：编译器差异（kenC 与 GCC 及各自标准不同）、POSIX 差异、构建系统（选择 Plan 9 原生 mk 文件而非上游的 GNU make）。具体包括：VLA 因 GCC 在栈上分配而改为 malloc 堆分配、可变参宏的 GCC 写法要换成 Plan 9 的 __VA_ARGS__ 形式、语句表达式改成 static inline 函数（该修改已回馈上游，上游现按环境探测二选一）、位域不能在静态初始化器中使用故换成整数或 char、空数组与零长数组的 C99 与 GCC 语法差异、APE 缺少 POSIX 函数（pread、pwrite 以桩形式调用 Plan 9 底层实现），以及 libwebfs 抓取器与上游 libcurl 做法差别很大。（YouTube EPSn1_afvWohs，[291-1184]，L1）
- 〔SREcon（推测）〕Sean Porter 以时间线梳理监控工具的演进。他是 Sensu 的作者兼 CTO（转写多处把 Sensu 音写为 SenseAudio、SenseU、Censys），现任职 Heavy Water Operations，有从小型快速创业公司到财富百强的基础设施自动化与监控经验。起点是 1983 年的 ping：走 ICMP 发 echo 包、能拿到少量遥测数据，但各实现输出格式不一、本身没有调度；而 ICMP 如今被 QoS 与普遍忽略所削弱，在高度临时的环境中尤难定位目标。1988 年的 SNMP 是首个被广泛采用的 agent-based 监控系统：设备侧跑 agent、管理端经网络通信，用 UDP 封装 octet-string、time-tick、integer，其 trap 非请求消息是早期的 push 机制；但它要分层管理才能规模化、要在各处打通 UDP 洞，安全糟糕——V1/V2c 只用明文社区字符串（V3 才有加密与认证，却仍是无状态协议，多数人还停在 V2c）。1999 年被他称为开源监控的黄金年：RRDtool 是环形数据库、采样间隔在创建时固定且不可改、除时间戳与数值外缺乏上下文，但简单高效、几乎每种语言都有绑定，并可用平均、最小、最大做聚合；OpenNMS 汇聚 ICMP、SNMP、TCP、syslog，可经 email、XMPP、SMS、自定义脚本、Jira 工单通知，用 Java 消息总线异步处理大量数据并以 Postgres 存状态；NetSaint 因商标问题改名 Nagios（1999 年把结尾的 1 翻掉），以主机与服务为中心，其 NRPE 远程插件执行器允许在目标机上跑插件采集 CPU、内存与服务健康。Nagios 的插件规范最有价值：只靠标准输出加退出码（0 正常、1 警告、2 严重、3 未知或自定义，可用到 255），任何语言任何脚本都能写，标准输出还可为结构化数据、JSON、YAML 或 perf data；缺点是静态配置须预先定义所有主机与服务，自动伸缩组难以适配。（YouTube EPSncq4gjl8-0，[20-1110]，L1）
- 〔SREcon（推测）〕2008 年之后的工具与 Sensu 的设计及未来方向。Graphite 由 Orbitz 于 2006 年创建、2008 年才公开，用点分层级指标名、数值与 epoch 时间戳的标准行协议（另支持 pickle），API 函数可回答“哪个磁盘利用率最高”、求导数之类问题，render API 能直接出图嵌入 Slack 或 IRC，Holt-Winters 指数平滑可做容量规划与异常判断；statsd 出自 Flickr（Perl），后被 Etsy 用 Node.js 重写，走 UDP 收 counter 与 timer、自动计算百分位与 min/max/avg 并按周期 flush 到 Graphite 或 OpenTSDB；不过预测与异常检测不宜作为唤醒人的告警引擎，更适合配合复杂事件处理（CEP）在时间窗内关联多数据源。2011 年他因在波士顿邮件归档与电子取证公司 Sonian 的经历（横跨四个云、四人运维团队、实例数从早晨四百到晚上两千）决定自研 Sensu，用两个 Sensu 实例替掉了三十台 Nagios 机器；Sensu 以 MIT 协议发布、已有约三百名贡献者，刻意不解决时序数据库与告警调度问题，只做数据收集与事件处理，因此被称作“监控路由器”；其管道为执行 check 后经 filter 与 mutator 转交给一个或多个 handler（pipe、TCP、UDP、set 分组），各 handler 可自带 filter 与 mutator（如 PagerDuty 每三十分钟、Slack 做去重），后端用 Redis 存当前状态、RabbitMQ 做传输并提供轮询、SSL、ACL 与免负载均衡的高可用；配置为 JSON，可从目录 glob 载入并深合并，还支持把修复 playbook 等自定义属性带进事件数据用于通知；它与配置管理、基础设施即代码工作流结合，把监控当作 CI 的反馈回路；客户端装上后自动发送首个 keepalive 注册进 registry，从而基于 subscription 实现服务发现，而资源发现（如 NFS 挂载）交给插件。生态侧还有 Reimann 与 InfluxDB 的 TICK Stack，UI 短板是 Uchiwa、公司计划招专职 UI/UX 人员；Sensu 2.0 计划改用 Go 与分布式共识配置，并把 RBAC、ACL、传输都收进单一二进制。（YouTube EPSncq4gjl8-0，[1110-2227]，L1）
- 〔USENIX Security（推测）〕CryptoWare 的 Mohamed El-Sabaawi 介绍 FirmScope：自动检测 Android 预装应用中提权漏洞的系统，合作者包括 CryptoWare 的 Ryan Johnson、Andrew Stavridis 与俄亥俄州立大学的 Chao Shen、Qingshun Zhu、Xijia Ding、Chunsheng Ling。Android 自底向上是 Linux 内核、ART 运行时与框架、再上是应用；应用默认被内核强制沙箱化：独立进程、私有 /data 存储、安全 RPC 通信，访问操作系统与外设受权限模型保护。应用分用户应用与系统应用：用户应用通常来自市场、权限低，敏感权限需用户显式授予；系统应用预装、持久、通常无法卸载（部分可禁用），权限更多且常被系统自动授予，因为它们承担电话、包管理等服务。预装应用来源多元：AOSP 与 Google 应用之外，还有固件签名厂商、芯片制造商、关联公司与运营商推送的应用；以 2019 年末的典型设备为例，平均 164 个预装应用对 30 个用户应用，攻击面很大。以几乎每台设备都有的包安装器为例，系统显示它不请求任何权限，但导出包信息可见其请求 22 项权限，其中不少是第三方应用拿不到的敏感权限，且全部已被系统自动授予。正常访问控制应保证认证、授权与审计，而 Android 4 到 9 中存在数千个提权漏洞实例，主要成因是预装应用的访问控制不当。实际案例 Lovely Fonts（另有多个别名）由用户可见应用与后台应用两部分组成，敏感功能全在后台，该后台服务存在多个本地与远程命令及代码注入漏洞，任何设备内或网络上的行为体都可在这一高权限进程上下文中执行任意命令与代码，相当于一条 C2 通道；该问题出现在十家以上厂商的四十余台设备上，影响百万级用户。（YouTube EPSnmc_BR0w6E，[8-380]，L1）
- 〔USENIX Security（推测）〕FirmScope 的实现、挑战与规模结论。流程分预处理与静态分析两阶段：预处理解包固件镜像、提取并规范化应用、反汇编并翻译为自研中间语言；静态分析阶段构建过程间控制流与数据流图，再由分析规则引导分析去检测特定漏洞类。预处理的主要挑战是 Android 镜像缺乏标准格式（格式多样、构建与优化配置及目录结构各异），且 Dalvik 字节码约有近两百条指令且相当复杂；解法是实现多套启发式尽量解出固件内容，并用自研中间语言替代直接操作 Java 字节码，以抽象掉与分析无关的内部细节。静态分析阶段的挑战是流经字段、回调与生命周期的数据（Android 常见），以及分析保证与运行时的平衡——要覆盖数十万应用，FirmScope 必须既准确又高效；解法是改造 Defuse 分析以覆盖字段读写、开发多个图 gadget 把尽可能多的信息编码进控制流与数据流图，使污点分析退化为可并行、可高效执行的路径查找，构造期无法保证的敏感度则对图上发现的路径做后处理校验。规则覆盖命令与代码注入、静默安装、设备录音等提权类别，多数是标准源-汇污点规则，部分为调用分析导出 API 的自定义插件。结果：扫描 2017 个 Android 镜像（Android 4 到 9）、约一百家厂商、共 33.1 万预装应用，77% 的镜像至少含一个漏洞，累计 3000 多个漏洞、850 个唯一漏洞，41% 的 ROM 至少含一个命令注入漏洞，约三分之一漏洞可导向某种代码执行；仅对 Android 7、8、9 的三百七十余项做披露，已获厂商确认两百余项，部分已修复；92% 的弱点由厂商引入，其添加代码的安全姿态宽松，且越接近 AOSP（定制越少）的设备弱点越少。开销为平均每应用约 7 分钟（中位 53 秒）、每镜像约 81 分钟（中位 51 分钟），准确率与 CPU、内存开销均显著优于既有方案。（YouTube EPSnmc_BR0w6E，[380-760]，L1）
- 〔会议不详〕讲者以自建的“自举式 Kubernetes 部署”demo 引出不可变基础设施议题。他有多年云基础设施自动化经验：主持 Digital Rebar 开放基础设施项目、联合主持 Kubernetes 的 Cluster Ops SIG，曾任 OpenStack 理事并写过早期 OpenStack 安装器 Crowbar。团队曾为 KubeCon 做过一个 demo：摆上机架、开机、灯闪几下，用内存 boot 镜像（如 Container Linux）自装 Docker、选出 leader、用 kubeadm 完成开源安装并 join 所有节点，全自动拉起一个 Kubernetes 集群，耗时五到十分钟。但这类 wiring 即使底层是内存不变引导也极难维护，Docker 或 kubeadm 一改就断。根因是“变更”本身：配置即修改系统，无论用 Chef、Puppet、Ansible、Salt、CFEngine 还是 Rundeck，都是在现场逐台构建，形成依赖图，环境间差异就会出问题，还必须在事后以 root 身份配置；OpenStack 社区的自升级同样难，装完即进入不确定状态导致升级与补丁失败。答案不是不打补丁（世界变化太快，不可行），而是“既不变系统又要改变系统”的不可变基础设施，即预配置或预部署配置的系统——像 Docker 构建那样把配置做进镜像再拉取使用。核心是“配置左移”：把通常发生在生产环境的动作（安全扫描、漏洞分析、认证）前移到受控、可重复的构建流水线，这也让回滚成为可能；配合 create-destroy 模式（像 Netflix 那样超配压测后销毁表现差的机器）替代逐台打补丁。打补丁的跑步机效应会让系统状态越来越不可知，而用同一个脚本在同样机器上反复执行却不产生奇怪结果几乎没人做到，因此需要放弃长期持有机器并持续打补丁的习惯。（YouTube EPSomEsVvolz8，[10-1130]，L1）
