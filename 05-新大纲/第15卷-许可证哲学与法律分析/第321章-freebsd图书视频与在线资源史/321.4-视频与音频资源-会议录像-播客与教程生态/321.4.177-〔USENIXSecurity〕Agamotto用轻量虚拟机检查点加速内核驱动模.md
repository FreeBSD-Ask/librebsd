# 321.4.177 〔USENIXSecurity〕Agamotto用轻量虚拟机检查点加速内核驱动模

- 〔USENIX Security〕Agamotto：用轻量虚拟机检查点加速内核驱动模糊测试。加州大学河滨分校（UCR）博士生 Song（与 UCR、TU Berlin、KAIST 合作）指出 2020 年驱动依然脆弱（不久前刚有 GPU 显示驱动的漏洞被公开），其运行在内核上下文、与其他内核组件无特权隔离，除系统调用攻击面外还暴露 PCI、USB 等外设攻击面，而驱动实现是状态机式、跨越多个状态的一条用例执行往往需要数秒，且驱动被赋予低优先级、频繁被更重要的内核任务打断；更糟的是浅层 bug——fuzzer 一旦撞到 bug 就会破坏系统状态、通常需要重启恢复且一次可达几十秒，于是反复撞同一个浅层 bug 而难以触达深层 bug。既有工具普遍只在程序启动时创建单一快照以支持“干净状态”重放，但快照技术自身开销不小、捕获内核组件更贵，VM 仿真与未优化的全量快照又很慢，因此不少项目干脆不用快照；论文改用动态检查点：初始化后创建根检查点，再按策略在测试用例执行过程中（驱动初始化之后建 A、驱动启动之后建 B）创建二级检查点，当新用例与旧用例共享前缀时直接从 B 恢复以跳过重复执行，遇到崩溃也可按下一条输入的前缀从本次模糊运行中任意可用检查点回滚，从而无干扰地高效 fuzz 深层路径。（YouTube EPSwo6jSkjviA，[8-313]，L1）
- 〔USENIX Security〕增量检查点、恢复优化与检查点管理策略。检查点以增量方式存入一棵检查点树：根节点保存完整系统快照，其余节点只存相对父节点创建后被弄脏的页；恢复采用自底向上算法，先计算待恢复节点 D 与目标节点 C 相对其公共祖先的脏页集合，只恢复这个“确实需要恢复”的页集合并保证每页只恢复一次，开销与脏页数而非全部页数成正比，实践中恢复最多快 8.9 倍。管理策略要抑制过量创建与内存压力：因模糊器更可能生成匹配较短前缀的用例故按递增间隔创建检查点，并在每个用例的首次变异处暂停创建（模糊运行中多数变异不带来新覆盖），内存不足时按驱逐策略淘汰；实现与评测方面，Agamotto 基于较新版本的 QEMU 与 Linux KVM，用 Syzkaller 做 USB 模糊、自研 PCI 模糊器，32 个并行实例、每实例 12 GB 检查点池，覆盖 Linux 上 8 个 USB 与 4 个 PCI 驱动，且刻意不改动所用模糊器的算法以避免把策略过拟合到某一算法的用例序列，结果是与无快照对照在反复撞到已知 bug 的前两个驱动上吞吐大幅领先、并在其后一个驱动上发现 Syzkaller 未发现的新 bug（Syzkaller 卡在已知 bug 上几乎无法推进），与单快照对照则显示深层动态检查点在所有实验中稳定提升吞吐——结论是“最先进模糊算法在短时间内就会反复产出相似用例”正是加速模糊测试的又一维度，未来可把用例序列与检查点创建/驱逐策略联合优化。（YouTube EPSwo6jSkjviA，[313-727]，L1）
- 〔TRIOS〕云上瞬态瓶颈对 n 层 Web 应用端到端性能的影响研究。演讲者为乔治亚理工的 Qingyang Wang（当年刚以助理教授身份加入路易斯安那州立大学 LSU，与富士通东京研究所等工业界伙伴合作），论文以 Gartner 2010 年“典型数据中心服务器平均利用率仅 18%”为背景，指出 SLA 敏感应用在低利用率下会出现幅度达三个数量级（10 ms 到 10 s）的响应时间波动，根源是存活时间只有几十毫秒的“极短瓶颈”；实测一套四层 Web 应用（Apache 作 Web 服务器、Tomcat 作应用服务器、C-JDBC 作数据库层负载均衡、MySQL 作数据库，采用仿 Slashdot 论坛的 RoboWork 基准、每用户平均 7 秒思考时间、双四核 CPU 与 16 GB 内存的机器，负载取 CPU 密集型）：在 9000 用户负载下瓶颈服务器平均 CPU 利用率仅约 61%、平均响应时间约 80 ms 且吞吐尚未到顶，但超过 2% 的请求耗时超过 2 秒、响应时间直方图呈明显双峰分布，平均值完全无法代表真实性能，测量借助富士通定制路由器盒的被动消息打时标基础设施精确记录每条请求在各层边界的到达/离开时间与排队数。论文给出三种不同层次的成因（系统软件层的 Java 垃圾回收、应用层的虚拟机整合、处理器架构层的 CPU 动态电压频率调节），第一类成因为 Java 垃圾回收：Tomcat 使用 JDK 1.4.5 的 stop-the-world 回收器，每次回收占满 100% CPU 达 50–100 ms 形成极短 CPU 打满，随即 Tomcat 与上游 Apache 的排队请求同时冲高，由于每台 Apache 的并发上限＝线程数＋内核 TCP backlog＝278，队列满后新请求被丢弃并触发 TCP 重传、客户端至少退避 3 秒才重发，连仅由 Apache 处理、根本不经过 Tomcat 的静态图片请求也被卷入排队，作者把这种被放大的排队传播称为“回推波”（pushback wave），其传播可在 100 ms 内完成，而把 Tomcat 的 JDK 从 1.5 升到 1.6/1.7 即可消除此类瓶颈。（YouTube EPSxojLwnR6R4，[10-830]，L1）
- 〔TRIOS〕虚拟机整合与 CPU DVFS 造成的第二类、第三类极短瓶颈。第二类成因为虚拟机整合：为提升硬件利用率业界用装箱算法把多个低利用率服务器整合到同一物理机共享硬件，论文对比 System Original（四层结构、14000 用户）与 System Bursty（1-1-1 配置、400 个相关用户即 Slashdot 效应、峰值请求速率远高于均值），把 System Original 的 Tomcat2（CPU 约 74%）与 System Bursty 的 MySQL（约 10%）整合到同一物理机共享 CPU 核心，实测 System Bursty 的请求速率峰与 System Original 的短时吞吐骤降、Tomcat2 的极短 CPU 打满高度吻合（Bursty 侧的突发 CPU 需求造成共享资源短缺，使 Original 侧感知到 100% CPU 利用率），经回推波放大后 Tomcat 与 Apache 队列堆积，Apache 队列峰同时对应系统响应时间峰与大量超长请求的出现、队列打满后丢包并触发 TCP 重传，而 System Original 的平均响应时间只有约 90 ms、长尾被平均值完全掩盖；第三类成因是 CPU DVFS：其本意是按实时负载调整频率与电压以兼顾性能与省电，但 Web 应用的突发长度常常接近 DVFS 控制周期、二者失步导致调整延迟从而产生极短瓶颈，机理与前两类相同（作者因时间限制未展开细节），结论认为极短瓶颈在真实系统中非常普遍，其破坏力来自系统内复杂资源依赖引发的回推波把排队效应从瓶颈层放大到上游层并最终导致丢包与 TCP 重传，问答中作者表示除按因对症（升级 JDK、把“吵闹邻居”虚拟机迁移到别的物理机）外尚无通用方案、正在探索打断回推波的方法，诊断方面也没有通用手段只能尽可能用细粒度监控采集更多数据。（YouTube EPSxojLwnR6R4，[968-1778]，L1）
- 〔USENIX LISA〕裸金属上的基础设施即代码（IaC）。RackN 的 CEO 兼联合创始人 Rob Hirschfeld 在 LISA 2021 开场就给出“能把 IaC 用到裸金属上吗？当然可以，那就给裸金属也来点 IaC”的定调（这是其 2020 年 SREcon PXE 引导主题演讲的续篇，本篇上移到构建“持久且高效”的自动化层）；他认为裸金属更难的根源在于没有 API 可以重新接线（设备是什么样就得接受什么样）、必要复杂性无法靠抽象掩盖（必须知道枚举了几块盘、哪块 NIC 接到哪个端口）、要同时驾驭 DHCP、TFTP、HTTP 等至少 5 个常常 10 个服务接口，以及他所谓“花生酱配巧克力”的供应（系统外搭基础设施）与配置（系统内配安全凭据、盘分区、网络映射、VLAN、装应用）必须协同完成而不是各建一套好工具。向管理层争取预算要用“风险降低”的话术：更透明可审计从而降低合规风险、更可重复从而降低交付风险、更可协作从而降低人员风险（降低 bus factor），而 IaC 归根到底是“协作故事”，他把 IaC 拆成六个方面：自动化与源码（运维工具应假定并要求你用 Git，版本化、可提取可打标签，kickstart/preseed/cloud-init 都入库但绝不允许把凭据写进这些文件而是运行时注入）、不可变性（“少触摸多呵护”，用镜像部署取代就地配置、替换而非打补丁，“reset/repave 而非 patch”，并把固件更新纳入流程）、当前状态（调节器模式，但任何被设计成单一真源的东西都不可信，工具间必须容忍漂移，自动化在状态不匹配时必须停下来而不是硬闯，采用 check-verify-act-confirm）、期望状态（声明式优于逐步命令，但要保证收敛过程可透明解释，且裸金属往往需要多次重启才能真正到达目标状态、工作流必须跨越完全不同的系统上下文例如从一个操作系统换到第三个操作系统）、协作复用与基础设施流水线。（YouTube EPT0FObTCWNwc，[8-989]，L1）
- 〔USENIX LISA〕协作复用、必要复杂性与 Digital Rebar 流水线演示。他强调自动化必须能被他人复用：就近文档化、拆成可复用模块、跨行业共享，并且系统必须明确声明变量及其类型与取值边界（把 string 当 boolean/int 用会彻底破坏复用）；固件打补丁、PXE 引导这类“不产生差异化价值又跨厂商不一致”的事不要自己写、直接复用别人的代码（复用会带来你现在看不到的复杂度，但硬件与系统终究会演进，自己写无助于公共利益）。裸金属工程要点是物理控制不能指望云或容器 API 直接够用、抽象要“够用即止”（以 Hibernate 为处理所有 SQL 异常而过度封装语言、而 Rails ActiveRecord 只做简单的事且复杂处直接写 SQL 作为类比），并维护 quirk 文件绕开硬件固有缺陷、按异构设计而非假设齐整（即使只买一家供应商，型号、固件与硬盘枚举方式也会变，Redfish 虽因协作在改进但各厂商实现仍各异）；运维层面不可变操作是低垂果实（更快、更有韧性、更安全），要“以重置而非供应”思考并杜绝一次性自动化，最关键的是基础设施流水线——它迫使所有其他行为就位，供应与配置交替构成循环而非线性分层，系统间以事件流与可观测性协作而不是各自持有私有状态，Digital Rebar 的教训是越少假设前置知识、越依赖过程中发现的知识，模块就越强大越可复用，现场演示中三台虚拟机跑“通用工作流”：先走 sledgehammer 发现阶段（RAID/BIOS 配置、磁盘擦除、校验），再按 profile（Ubuntu 20.04.2、CentOS 8.3）完成跨多次重启的安装，全程可订阅事件流、查看作业日志，代码全部在 Git 中且为未改动的标准模块、后续改进会发布回目录供整个生态受益；收尾建议是：把基础设施接进既有 CI/CD 流水线、先让能进版本库的部分进版本库并走评审与 Pull Request、避免定制以换取复用与模块化为规模扩展铺路、盘点并打通状态孤岛、遗留系统是可用的软件应改造而非烧毁（本场为 LISA 2021 赞助内容，RackN 官网 rackn.com、作者 Twitter 为 ziacal）。（YouTube EPT0FObTCWNwc，[990-2351]，L1）
- 〔USENIX Security〕VRASED：面向远程证明的可验证软硬件协同设计。报告人（未自报姓名，论文中含 Jin Soo Duk 等合作者）声明这并非新的生物识别方案，而是围绕“设计、实现并形式化验证一套面向传感器与执行器等低端 IoT 设备的远程证明架构”；这类设备（如德州仪器 MSP430、Arduino 平台常用的 AVR ATmega32）程序与数据内存只有几 KB、单核几 MHz、通信接口简单、通常裸机运行因而无法依赖操作系统的任何安全保证，跑一次签名计算往往要数秒并占满整个 RAM，因此在这类设备上预防恶意软件既困难又昂贵，只能退而求其次：检测感染后采取带外措施把设备恢复到安全状态，而检测手段即远程证明——一个由可信且更强大的验证方与可能已被攻陷的证明方执行的挑战-响应协议，证明方对挑战与内存计算 HMAC 类完整性函数、验证方据此比对期望内存值，且必须考虑被保护方软件状态处于完全对抗控制之下（凡未被安全硬件保护的内存都可能在被攻陷）。论文对三类既有方案作比较：依赖安全协处理器或 TPM 的硬件方案（他们查到的最便宜 TPM 本身约是待保护 MCU 价格的十倍）、仅软件方案（需要一跳、恒定延迟等强假设，不符合经互联网通信的 IoT 现实），从而选择“密码运算尽量下沉到软件、硬件只保留最小必要保证”的混合远程证明作为最佳契合；形式化验证的必要性在于所有现有远程证明架构都没有形式验证、也不是从可推理正确性与安全性的数学模型出发系统设计，因而必须从抽象重新设计，而混合软硬件协同设计里硬件一旦做错就只能扔掉设备（纯软件还能打补丁）。（YouTube EPT4XpkIPAKas，[11-402]，L1）
