- 〔APSys（推测）〕阿里巴巴 Ceres：将网络功能链组合进 P4 可编程边缘网关。主讲人 Jiaqi（阿里巴巴）介绍边缘云在数千个边缘站点部署可编程交换机，承载 CDN、云游戏、DNS 与 Web 缓存等网络功能，最大 P4 程序达 16000 行、248 张表、占满全部四条流水线；以 NAT 为例，单个简单 NAT 在 VM 互访、入向 SNAT、出向三种路径下拆成三条网络功能链，链间最少 10 张表相互依赖、最多 26 张，而朴素的复制合并方案会带来 3-5 倍内存开销、远超 ASIC 资源。开发者因此难以开发、调试和维护，根本原因是业务抽象与 ASIC+CPU 硬件之间存在三大鸿沟：多条链需手工合并进单一流水线、recirculation 等复杂特性在 P4 中一次写完、程序需手工划分部署到 ASIC 与 CPU。（YouTube EPJGmHQ3R76xc，[16-466]，L1）
- 〔APSys（推测）〕Ceres 以网络功能链为抽象自动合成 P4 程序。Ceres 接收 NF 链定义与边缘网关拓扑/流量元数据两项输入，自动生成最小化内存开销的流量识别表来标记每个包、提出对齐硬件约束且满足吞吐目标的流水线候选（错误排序会使 SNAT 入向流量因 recirculation 遭受 4 倍吞吐下降）并给出把最少网络功能划到 CPU 的划分方案；真实程序中 10 条链按序合并即产生 127 个环，Ceres 数分钟完成流水线化与划分方案，而最有经验的开发者需数周，开发效率提升三个数量级。（YouTube EPJGmHQ3R76xc，[466-932]，L1）
- 〔会议不详〕Solaris：可扩展且健壮的块存储。主讲人 Yang Wang（得克萨斯大学）提出目标：无论服务器发生什么客户端永远读不到损坏数据，且故障数低于阈值时保证数据持久性与可用性；现有可扩展存储（GFS、Bigtable、HDFS、HBase、Windows Azure 等）只容忍崩溃故障加简单校验和，无法应对内存损坏、CPU 错误与软件缺陷，而 BFT 等强防护技术与可扩展架构不契合。Solaris 基于键值存储架构（计算节点如 Bigtable 的 tablet server、HBase 的 region server，本身无持久存储）发现三大问题：写操作无顺序保证使 barrier 语义（对日志文件系统与数据库至关重要）可被违反、计算节点单点损坏可污染所有存储节点副本、损坏发生时客户端无从验证。针对 barrier 语义提出 pipeline commit 协议：提交阶段等上一事务 leader 通知后串行执行以保证事务间顺序，准备阶段仍并行以继承现有架构的扩展性与并行性。（YouTube EPJHAQsstni9k，[9-676]，L1）
- 〔会议不详〕Solaris 的主动存储与评估。Active storage 将安全性与活性分离：f+1 副本对所有存储节点更新达成一致即可保证安全，计算节点故障时整体替换新节点并要求其就存储节点当前状态达成共识、不成就再次替换；由于计算节点可 colocate 到存储节点本机，垃圾回收的全部网络传输被消除，带宽受限场景下 Solaris 反超 HBase 74%，网络消耗较 HBase 降低约 50%。在约 100 台 Amazon EC2 机器上以 9 台与 108 台服务器对比 HBase：顺序写吞吐几乎不随规模变化，随机写慢约 28% 但开销不随系统规模增长，即扩展性与 HBase 相当；Q&A 讨论了多写者模型（端到端校验的可扩展方案尚无完美解，可在因果一致性与单点串行化间权衡）与相关故障下的恢复表现。（YouTube EPJHAQsstni9k，[676-1351]，L1）
- 〔OSDI（推测）〕CacheLib：Facebook 的统一缓存引擎。主讲人 Ben Berg（Facebook CacheLib 团队，与 CMU 并行数据实验室合作）指出 Facebook 存在数百个缓存用例（CDN、键值、社交图、存储缓存），历史上各用专用实现，导致冗余代码、狭窄特性集，并成为新缓存思想在数百个实现中落地的障碍。四大系统呈现扩散的热点分布（社交图实测 50-20 而非 80-20 规则、存储 40-20、CDN 60-20），对象高度偏小（Memcached 每对象 56 字节、MemC3 40 字节 DRAM 开销，1TB 满载百字节对象需数百 GB DRAM），加上每两周代码更新重启的漫长 warmup，共同要求大容量、低每对象开销与生产稳定性。（YouTube EPJIM08lWPvNs，[7-550]，L1）
- 〔OSDI（推测）〕CacheLib 的设计与生产经验。CacheLib 提供统一线程安全 API（find/allocate 返回零拷贝的 item handle 智能指针），采用 DRAM+Flash 混合缓存：DRAM 链式哈希表每对象仅 31 字节开销，Flash 划分为小对象缓存（小于 2KB，直接哈希到 4K 页、每对象不足 1 字节）与大对象缓存（百万级对象、近似内存索引 10.5 字节），配合 admission policy 降低 Flash 写放大，并实现 warm restart、负缓存与原生结构化数组/哈希表。对比 Facebook Lookaside 生产数据，其命中率与 Memcached 相当而吞吐大幅领先，并优于 Nginx 与 Apache Traffic Server 的 Flash 缓存实现；CacheLib 成为优化聚合点（CDN 团队的大对象缓存改进惠及多个用例），用 Flash 缓存与可定制组件摊薄成本曲线，使 Facebook 缓存容量与缓存数量双增长，现支撑数十个缓存系统。（YouTube EPJIM08lWPvNs，[550-1100]，L1）
- 〔USENIX Security（推测）〕GitHub CI workflow 的安全性刻画。主讲人 Iggy Beck（与 NC State、普渡大学合作）认为 CI/CD 属于软件开发供应链，需与最终软件同等的安全管理，并定义了 CI/CD 流水线四项安全属性：准入控制（仅授权者可增改 workflow）、执行控制（仅授权者可配置触发器）、代码控制（控制 workflow 中运行的代码）与机密访问（仅直接访问的 step 可读机密）。对比 Travis CI、CircleCI、Jenkins、GitLab 发现 GitHub Actions 默认给代码写权限且所有 step 以管理员权限运行，组合起来放大了整体安全风险；第三方 action 可变（mutable）——插件作者无需修改 yaml 配置即可改变流水线行为，且所有 step 读取 /home/runner/_work 目录即可间接访问全部机密。（YouTube EPJIaFfMmXpXg，[7-358]，L1）
- 〔USENIX Security（推测）〕GitHub Actions 大规模测量：开发者不遵循安全指南。从 JS archive 收集仓库名并爬取 workflow 存入 MongoDB 的测量显示：仅 0.2% 的 workflow 自定义默认权限且其中仅 62% 设为只读；发现至少 11000 个无版本唯一 action（含版本达 19000 个），仅 2.9% 来自认证创作者；仅 0.1% 的引用使用 commit hash（GitHub 官方建议），且团队以 POC 演示即便 commit hash 引用也可改变 action 行为。约 50% 仓库向 4000 个 action（仅 8% 认证）传递机密、超 5000 个插件可间接访问机密；用 git vuln finder 分析出至少 500 个仓库依赖较高严重性漏洞的 action，作者已通知并获部分修复，结论是平台应提供安全的默认设置而非信任用户自行安全使用。（YouTube EPJIaFfMmXpXg，[358-716]，L1）
- 〔会议不详〕Kellum：以控制流完整性守护 serverless 应用。主讲人与普林斯顿 Liang Wang、微软 Sudan Bagat 及导师 Mike Swift 合作，研究无服务器计算安全：假设基础设施（自动扩缩、函数运行时等）可信，但至少一个函数存在可致远程代码执行的漏洞。以含 deposit 与 add user 方法的银行应用为例，函数调用序列构成路径（path）；两种攻击分别是攻陷 read balance 后把用户余额外泄到攻击者控制的外部服务器，与攻陷 validate user 后绕过 validate transaction 直接提交非法交易改写余额。核心洞察是传统单体 Web 应用中的控制流劫持在 serverless 中已可于网络层观测（依据函数间传递的消息即可推断控制流），而信息流控制与 Web 应用防火墙等先前工作均未考虑路径中函数的顺序。（YouTube EPJPIp162vcsU，[8-383]，L1）
- 〔会议不详〕Kellum 的设计与评估。Kellum 基于全部执行路径应合法的思想，为应用构建应用控制流图（函数调用顺序，边以目的函数 URL 标注）与函数控制流图（函数执行期间发出的消息顺序）作为预期画像，运行时增强函数运行时，基于 Google 用户态容器运行时 gVisor 拦截网络系统调用并检查载荷，由全局控制器维护当前执行位置以判定出边是否放行。评估显示两类攻击场景均被拦截（外泄消息与绕过 validate transaction 的调用因不在应用控制流图中而被拒绝），基于 Valve 信息流控制基准的性能开销较 Trappist 等相关框架更低，图生成技术假阳性率也较低，工件已公开。（YouTube EPJPIp162vcsU，[383-765]，L1）
- 〔SREcon（推测）〕监控反模式与精准度量。主讲人 Brian（Facebook 生产工程师，负责构建供各团队调试与告警的监控工具系统）批判三类看似合理实则有害的反模式：高基数告警（百台机器对同一问题产生百条通知，使人只见树木不见森林）、每次事故后针对具体根因不断累积的反应式告警（数月数年后充斥误报与来历不明的告警）以及 on-call wiki 一行命令造成的工具疲劳（实为接口差、目的不明的最差工具）。以 Scribe 的 ptail 为例说明精准度量：与其用 backlog 与 write rate 两条曲线加日志排查数小时，不如新增一条“ptail 是否在等待写标准输出”的 0/1 指标，把 15 分钟的图表解读缩短为 3 秒，也便于构建自动化。对需要人工处理的告警用信号（是否误报）、可行动性（收到后能否立刻行动）与相关性（是否与既有告警重叠）三准则治理后，Scribe 消除了 97% 的告警、收敛到每层栈约一条，相关性如同熵，告警越少每条信息量越大。（YouTube EPJPtvkaRIc-o，[11-787]，L1）
- 〔SREcon（推测）〕仪表盘即调试器。Brian 认为仪表盘不是被动工具而是持续附加的调试器：基于开源的 Cubism 密度图技术（把垂直高度转为密度，指标超出正常范围时反复滚动使图变暗，一张图可可视化约二十个指标），从 total view 逐层下钻两步即可定位问题；把所有指标无组织堆上网页，如同把字典塞进列表每次全量扫描。Q&A 中补充：Scribe 早期信噪比差到无需分析即可直接丢弃，其他团队则在 on-call 报告中细致跟踪信噪比；应度量系统间边界以捕获最多问题（如在数据可视化平台 Scuba 的前五大数据集上设告警以预测下游问题）；事故后应复查全部指标找出最佳预测指标，并区分机器处理与人工处理的告警，Facebook 用 Fbar 做自动处置（外部可用 Nagios event handlers）。（YouTube EPJPtvkaRIc-o，[787-1574]，L1）
- 〔NSDI（推测）〕FPISA：在可编程交换机上解锁内联浮点运算。UIUC、Caltech、微软研究院、NUDT 与 Intel 合作的工作指出最流行的可编程交换机范式 PISA（协议独立交换机架构）不支持浮点数据格式，而分布式机器学习梯度交换、数据库查询与拥塞控制带宽估计等应用都亟需浮点运算。报告剖析了 16 位半精度浮点的符号位、偏置指数与尾数结构，说明对齐尾数、重归一化等步骤使浮点加法器硬件极其复杂、无法单周期完成，而 PISA 每级每数据仅一次操作、每包一次内存访问，难以塞进单一流水级；带专用算术单元的交换机不灵活、FPGA 交换机性能存疑，因此 PISA 仍是性能与灵活性平衡的理想平台，该工作提出 S-PISA 机制以在商用 PISA 交换机上原生支持浮点。（YouTube EPJTAupxdwKkY，[12-480]，L1）
