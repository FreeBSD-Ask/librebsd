- 〔USENIX OSDI（推测）〕主讲人 Guanzhou（据论文匹配为威斯康星大学麦迪逊分校 Guanzhou Hu）介绍 Bodega：一种配备新式 lease 机制的共识协议，实现共识集群中任意位置、任意时间的线性化本地读。问题背景是广域共识中线性化与客户端地理亲和天然矛盾：写必须经 leader 与多数派 quorum 承担广域延迟，而读不改变状态，能否只由最近副本服务？协议目标为容错、线性化、读局部性、可配置性、最小写干扰五项。相关工作方面，Multi-Paxos、Viewstamped Replication、Raft 等多数派协议与 EPaxos、PQR 等 leaderless 协议都无法在指定副本提供纯本地读，需要 lease 补充：leader leases 只允许 leader 本地读、lease 承诺与 leader 身份耦合，quorum leases 允许任意 follower 本地读却在有并发写时 lease 不断被暂停、写干扰严重。核心观察是 lease 参与者要与 lease 保护的对象解耦，由此提出集群元数据 roster（映射 key 到可本地读的 responder 节点集合）与在共识关键路径之外运行的 roster leases。（YouTube EPJOR6P1FMkUA，[19-700]，L1）
- 〔USENIX OSDI（推测）〕Roster leases 的三条不变量、Bodega 协议设计与评估。不变量保证每个 ballot 唯一映射一个 roster、活跃 grant 对双方 ballot 一致，从而持多数派 grant 的节点可本地确认集群唯一稳定 roster；协议中 responder 持多数派 grant 即本地化读，leader 提交写需多数派 accept 加上该 key 全部 responder 的 accept，lease 续约以逻辑消息 piggyback 在共识心跳上并可多跳路由，读未确认提交时锚定到最新写日志项乐观等待 commit 通知，初始 grant 携带 safety threshold 解决新加入 responder 的日志追赶，故障经 lease 过期后换新 roster，主动 roster 变更平均两个消息往返完成，并有已模型检查的 TLA+ 规约与线性化简证。实现为数千行 async Rust 的协议无关测试床 Somersault KV（ASR 亦写 Somerset），在 CloudLab 5 节点跨地域、10% 写/90% 读、128B payload 的负载下，Bodega 在全部 responder 节点保持优异读延迟，YCSB（Zipfian 0.99 偏斜）A/B 工作负载下与允许过期读的 etcd、ZooKeeper 相当甚至更好。（YouTube EPJOR6P1FMkUA，[707-1388]，L1）
- 〔USENIX NSDI（推测）〕主讲人 Zijun（ASR 音写，据论文匹配为上海交通大学 IPADS 实验室的 Zixuan Wang）报告 ODRP：可编程 RDMA 支持的按需远程分页。动机是 K-means、图处理、数据库、Memcached 等内存密集应用的需求随时间波动，数据中心按峰值超额配置导致平均利用率低下，RDMA 分解内存架构把 CPU 与内存拆成 compute nodes 与 memory nodes 两个网络连接的资源池。细粒度内存管理依赖 RNIC 内存注册，频繁分配/释放请求与耗时的注册过程成为系统瓶颈（尤其内存节点 CPU 算力有限），而 FastSwap 等静态方案运行期几乎无分配却内部碎片严重，现有方案无法同时做到高性能、高内存利用率与低内存节点 CPU 占用。ODRP 借助较少被探索的 RNIC offloading（wait verb 实现事件触发的 worker 交叉触发，并把 RDMA read/write 等基本 worker request 链接起来表达复杂逻辑，示例用 CAS 链实现相等比较函数），把内存管理与访问逻辑卸载到内存节点 RNIC；系统按 swap 架构划分 4KB 页、维护 ring buffer 空闲页队列与每计算节点 translation table，swap 请求经 RDMA send 触发内存节点 NIC 执行预编程链完成地址翻译、按需分配与访问。（YouTube EPJmTefD5YJJo，[15-471]，L1）
- 〔USENIX NSDI（推测）〕ODRP 面临的效率与功能两大挑战及评估结果。效率上更复杂的逻辑意味着更长的 worker request 链与更多 PCIe 往返，提出 compute node-assisted 原则：安全共享 translation table 基址让计算节点直接给出表项地址，并利用其对自身 swap 空间映射状态的完全认知免去复杂的缺页检测逻辑。功能上 RDMA 缺少取模支持且 RNIC 字节序与主机不匹配，分别以 masked fetch-and-add 掩码高位实现环形队列回绕、用 scatter-gather IO 一次读 8 个 entry 完成 endian swap。评估在 8 个计算节点加 1 个共享内存节点（单核模拟弱算力）、100Gbps ConnectX-5 上对比 one-sided static、one-sided dynamic 与 two-sided 基线：K-means、Memcached、PageRank 真实负载下页面级分配带来至多 12 倍内存利用率提升、性能开销至多 14.2%，扩展性测试（每节点 4 个 quicksort 任务）开销至多 14.6%、比 one-sided dynamic 快 2.92 倍；结论是 ODRP 为首个利用 RDMA offloading 同时达成理想内存利用率、零内存节点 CPU 占用与高性能的系统。（YouTube EPJmTefD5YJJo，[473-818]，L1）
- 〔会议不详〕主讲人 Wenqing Jia（中国科学院计算技术研究所，现就职百度）介绍 C2FS：面向远程存储、主机与服务器协同的高性能文件系统。NVMe over Fabrics 把远程 SSD 暴露为本地块设备，实测 4KB 随机读写显示本地文件系统软件栈约占一半延迟、远程 SSD 软件开销占比更高，其中 NVMe over RDMA 驱动占 36%（内核处理 RDMA 中断带来高延迟）；扩展性上 ext4 与 F2FS 并发更新共享 10GB 文件时远程访问吞吐下降 63%、并发扩展再降约 30%，inode 级锁串行化并发读写，日志机制的跨网数据移动超过两倍。C2FS 设计为内核文件系统处理元数据、用户态库用轮询请求队列在用户态完成数据路径、target request handler 负责权限检查与并发控制；权限检查通过块粒度 I/O 反向权限表卸载到目标端：块分为 free/metadata/data 三类、各带 owner ID，每文件一条带读写权限 flag 的请求队列，按"操作类型匹配权限 flag、请求块 owner 匹配队列 owner"两条规则拦截非法地址访问。（YouTube EPOVnYj_s3RHo，[18-460]，L1）
- 〔会议不详〕C2FS 的并发控制卸载、文件原子 I/O 与评估。并发控制卸载让发起端并行发送所有请求、由目标端串行化保证正确性：发起端创建由相邻无冲突请求构成的请求组，并用低开销的合并组策略把可并行执行的组合并（示例中除 W3 外全部并入 G1），既省网络等待时间又提升并发与硬件利用。文件原子 I/O 卸载到目标端，提供原子 API、由 handler 维护事务元数据并后台执行 checkpoint，采用事务感知的延迟提交策略批量 MMIO 与 DMA 写。评估使用两台双路 Intel 服务器、ConnectX-5 RDMA 网卡与 Optane SSD，以 FIO 与 Phixmark（音写）工作负载对比 ext4（音写 S4）、F2FS 与 UFS：单线程读写消除内核软件开销、延迟至多降 50%，多线程高争用共享文件场景下卸载访问控制并合并无冲突请求组显著提升扩展性。结论是 C2FS 把数据面整体置于用户态、权限检查从内核控制面分离，向远端服务器卸载权限检查、并发控制与故障原子 I/O 三项任务；报告人现在从事百度 Elastic File System——面向 AI 负载、容量与性能双弹性伸缩的高性能分布式文件存储。（YouTube EPOVnYj_s3RHo，[462-835]，L1）
- 〔USENIX NSDI（推测）〕报告人（据论文匹配为 ETH Zurich 的 Magnifier 团队，仿真与设备实验均在 ETH Zurich 完成）讨论大型 ISP 网络中流量从何处进出（ingress/egress）这一难题：Deutsche Telekom 报告的中转容量已达 30 Tbps，仅看控制平面路由数据不够，故障或收敛期间数据面可能偏离控制面信息，而定位入口点更需要数据面洞察。现有两类监控手段各有缺陷：包采样（sFlow、NetFlow）理论上覆盖广但实际偏重 long hitter 大流、同一流可能不再被采样到；包镜像精确但匹配规则的全量克隆成本极高；对某大型 ISP 采样数据的实测显示缓存与聚合平均带来约 30 秒延迟，镜像则几乎即时反馈。Magnifier 的核心思路是结合两者取长补短：推理步基于采样观测（采样率 1/1000 或 1/4000）寻找用尽量少子网覆盖尽量多 IP 的方案，建立 IP 空间与 ingress/egress 的唯一映射，此推断可能出错，需再用镜像数据验证。（YouTube EPQvgGE4mRF-E，[14-460]，L1）
- 〔USENIX NSDI（推测）〕Magnifier 的验证机制、工程挑战与评估结果。验证步把镜像规则部署在推断不期望看到该流量的入口/出口点上：无镜像流量即支持推断且精度极高，一旦出现偏差立即触发；错误推断还可反馈给下一轮推理逐步提升覆盖。挑战包括镜像规则占用与 ACL 等关键特性争用的设备内存、大规模增删规则慢、单一控制器反应迟缓；对策是让运营者优先级排序、预部署规则后批量激活、在网络边界部署 sub-controllers 快速响应，也可用设备自带的镜像限速，且理论上一个包就足以证伪推断。评估结合仿真与 ETH Zurich 的 Cisco 真实设备（单台至多 500 条镜像规则、采样率 1/4000），用 traceroute 流量提供完整 ground truth，random/static/permuted 三种 IP→ingress 指派策略下，仿真中 random 已覆盖约 15% 数据包、static 与 permuted 最高达 77%，实验与仿真模式一致且全程镜像流量不超过 1.5%；相关工作包括 FlowVoyager（音写 Emberflow，仅基于采样观测）与面向数据中心的 PingMesh。结论指出网络随时间变化覆盖率不会持续单调提升，未来可预留 IP 空间逐步扫描。（YouTube EPQvgGE4mRF-E，[462-925]，L1）
- 〔USENIX SOUPS（推测）〕主讲人 Nikhil Patnaik（布里斯托大学博士生，研究提升安全 API 可用性的编程抽象）报告与 Joseph Hallett、Awais Rashid 合作的《Usability Smells: An Analysis of Developer Struggle with Crypto Libraries》（据论文匹配发表于 SOUPS 2019）。研究从 code smell（违反设计原则、影响质量的代码结构，如 Fowler 的 shotgun surgery）引出 usability smell：开发者在加密库编程接口上挣扎的信号。基于 Green & Smith 针对密码 API 的十条可用性原则（abstract 为 golden rule，十条均以正面表述），研究回答两个问题：开发者使用加密库时遇到哪些问题、十条原则被违反时有哪些迹象；团队对 2491 条 Stack Overflow 问题做主题分析，覆盖 OpenSSL、libsodium 与 NACL、Bouncy Castle、SJCL 与 CryptoJS、PyCrypto 七个库（OpenSSL 问题最多，属低层 API，libsodium 则以高度抽象自称可用），归纳出 16 条可用性问题并归入 7 大主题。（YouTube EPTy7NIKZMK98，[10-590]，L1）
- 〔USENIX SOUPS（推测）〕可用性问题的具体表现、四大 usability smells 与 Q&A。问题示例包括 missing documentation、"what's gone wrong here"（答案通常是改正后的同款代码）、appropriateness（该选哪个库或函数）、缺乏密码学基础知识（分不清 CA 签发的可信证书与自签证书）、borrowed mental models（把 OpenSSL 心智模型照搬到 PyCrypto）、compatibility issues（用 OpenSSL 加密、另一工具解密）与 build issues（OpenSSL 问题中 18% 属构建问题）；七主题涵盖 usage issues、system issues、not knowing what to do、not knowing if it can do so、missing information、programming is hard 与 issues across time and space。由此得到 need a super sleuth、confusion reigns、needs postmortem、doesn't play well with others 四个 usability smells，前三个被 Green & Smith 原则较好覆盖，最后一个（含构建、兼容与性能问题，性能问题未被十条原则覆盖）覆盖不佳。结论是 Green & Smith 原则基本正确、不应忽视构建问题、"下次用加密库时闻一闻（have a sniff）"；Q&A 讨论了 rot13 加密示例"正确答案是别做"、GitHub issues 与 Stack Overflow 问题类型差异、各库文档质量差异与 passing the buck 现象，静态分析与 usability smells 的关联留作博士后续工作。（YouTube EPTy7NIKZMK98，[593-1345]，L1）

- 〔NSDI（推测）〕午后第一场：报告人介绍 SlimFly 低直径拓扑的首次大规模实际部署。互连是超算与数据中心的关键成本项，其功耗可占数据中心总功耗最多一半、占整体成本约三分之一；SlimFly（2014 年提出）通过有限域代数构造出任意端点对至多两跳、直径为 2 的拓扑，由两个结构相同子图加全连接二部图组成，从而减少线缆与交换机并降低时延与功耗；实际部署为五个机架，把两个子图成对混排进同一机架以缩短线缆、避免长光纤，并按"机架内一致布线、机架间互联、机架内全连接"三步完成施工。（YouTube EPcKe0GfiTxMA，[16-580]，L1）
- 〔NSDI（推测）〕低直径拓扑上的路由实践与系统评估。以太网侧依赖多路径（ECMP 等）与 2020 年 Fat Paths 论文"三条不相交路径足以缓解流冲突"的结论，但 SlimFly 等低直径拓扑几乎只有单条最短路径，需要使用长一跳的"近最短路径"；在 InfiniBand 中借助 service level 构造虚拟链路，显式选择重叠最小的路径层，比以太网随机采样边的方式所需层数更少；评估以同硬件非阻塞两级 fat tree 为基线（SlimFly 用 DFS-SP 路由、线性放置），micro-benchmark 显示 8-16 节点以下 fat tree 因叶子交换机下 16 节点零跳通信在小消息场景略占优，而 all-to-all 高拥塞场景与深度学习代理负载（GPT-3 前反向传播）下换放置策略的 SlimFly 显著反超。（YouTube EPcKe0GfiTxMA，[644-1149]，L1）
