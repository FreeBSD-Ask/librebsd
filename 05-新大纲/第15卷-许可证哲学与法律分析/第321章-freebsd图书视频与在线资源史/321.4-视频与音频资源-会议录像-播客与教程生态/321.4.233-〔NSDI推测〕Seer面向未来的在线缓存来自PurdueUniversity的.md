# 321.4.233 〔NSDI推测〕Seer面向未来的在线缓存来自PurdueUniversity的

- 〔NSDI（推测）〕Seer：面向未来的在线缓存。来自 Purdue University 的 Jason Lei 指出，网络与分布式系统中的状态密集型组件（负载均衡、NAT、防火墙、接收端 TCP 处理、边缘缓存等）需要维护 300 到 600 MB 乃至数 GB 的状态，而 100 Gbps 线速下每个包处理器只有约 100 纳秒的处理窗口，DRAM 的访问延迟跟不上数百 Gbps 甚至 Tbps 的线速，因此这些应用必须依赖高效缓存。他对比五种传统缓存启发式与最优离线算法 Belady，发现每一种都明显落后、性能普遍差 2 到 3 倍；根因是 Belady 掌握全部过去与未来访问，而基于机器学习的替代方案易误判、精度高度依赖历史训练数据、对访问模式的突变脆弱。其关键洞察是：状态应用的访问索引本就由入向报文的报文字段（如五元组经哈希）携带，且只需 16 到 20 位；报文在网络中排队等待转发的延迟可被利用，把状态索引信息提前送往相关缓存；并且只让直连邻居发出通知才能给出未来状态访问时间的精确估计，因为跨多跳预测到达时间几乎不可能、报文还可能被丢弃。（YouTube EPZ7eJpXIJiGM，[16-479]，L1）
- 〔NSDI（推测）〕Seer 的三部分设计与评估结果。系统由低开销的未来状态访问通知协议、面向未来的缓存管理器与快速硬件实现组成。通知协议在以太网物理层强制的 96 bit 包间间隙（interpacket gap）上传输状态索引与未来到达时间，带宽开销为零；平时走 IPG，仅当同一时间收到大量通知时按可配置阈值 m 机会性地把控制包批量发出，从而兼得通知及时性、无批量延迟与低带宽开销。缓存管理器按预测访问时间把各输入端口的通知队列合成一条逻辑有序队列做预取（单次预取约 1+log(端口数)+缓存集大小 个时钟周期），淘汰策略则把缓存分为已知与未知未来访问时间两组、优先淘汰未知对象以模仿 Belady，单次淘汰约缓存集大小个时钟周期，故零知识的最坏情况等价于所配备份启发式、全知的最好情况等价于 Belady；FPGA 实现改造以太网 PCS 子层以读写 IPG 位。评估用 C 语言包级仿真器与双层 fat-tree 全平分带宽拓扑，incast 流量下较 Belady 仅差 7 到 20 个百分点并优于 LRU 20 到 100%，最坏 permutation 流量下不劣于 LRU，真实 Web 搜索负载下缓存未命中率较传统启发式降低 60 到 180%、流完成时间较 LRU 缩短 25 到 75%。（YouTube EPZ7eJpXIJiGM，[486-1045]，L1）
- 〔SREcon（推测）〕Project Osiris：主动缩小自己的数据中心。Allegro 的 Jakub Łalak 介绍，这家欧洲本土最大电商平台有 2100 万活跃买家、16.3 万商家、每天超过 5 亿条 offer，由 4400 多名技术团队成员维护 3000 多个微服务，日均 150 次以上部署与 8000 多次配置变更，几乎没有宕机余地；几年前一次数据中心消防喷淋事故把 CFO 提出的我们真的需要多个数据中心吗变成现实问题，于是启动 Project Osiris，以损失 N 个数据中心中的 1 个时平台照常运行为假设做混沌工程实验，而非随意搞破坏。执行前必须走完一套像任务发射序列一样的组织级检查清单，逐项勾完才能开始，最后一步是把实验摘要分享给干系人以完成持续改进闭环；同时逐次压缩被排除在实验之外的服务名单，在一张谁都看不清的依赖图中理清如何导航，并在避开 Black Friday、圣诞季、营销大促与关键软件发布的条件下，挑选低流量但仍有代表性的窗口。此外自 2023 年起不再提前数月指定要关停的机房，而是随机挑选数据中心并减少预告时间，以真正检验随时应对故障的 readiness。（YouTube EPZ9tnNTTz6GM，[88-490]，L1）
- 〔SREcon（推测）〕从剧本式手册到真正拉闸断电：Osiris 的演进与代价。实验手册近乎电影剧本，逐步规定关停哪些服务、按什么顺序、如何引流，每步都有指定负责人与精确到分钟的时间框，并配有对称的恢复计划：先引流、优雅关停服务，再运行模拟用户浏览检索下单的性能压测，最后按序恢复、验证数据复制与健康检查；自研的集中式监控服务充当单一事实来源，可按各国市场维度统一查看功能健康度并处理事件与宕机上报。团队把非预期故障称为蝎子，视其为最好的老师——每一次失败都暴露未知弱点：项目从 2022 年的求存活（首次实验直接把 Cassandra 集群搞挂导致 Allegro 停机，第二次因应用集群资源耗尽使自动扩缩容失效，第三次才成功）演进到 2023 年把纳入范围从半个数据中心扩到 90% 以上、引入问题管理与性能压测，再到 2024 年既经历过最漫长混乱的夜晚，也首次请持证电工真正关掉若干机柜，并在下半年把测试扩展到 Datadog 等第三方供应商集成。副作用还包括长 uptime 服务器数量下降、待打补丁内核被清理，但代价是在生产环境测试有时会真造成影响，需要就成本做艰难解释。（YouTube EPZ9tnNTTz6GM，[491-1279]，L1）
- 〔USENIX Security（推测）〕Midas：对 Linux 内核 TOCTTOU 缺陷的系统性防护。来自 EPFL HexaFive 实验室的研究者介绍，TOCTTOU 属于 double fetch 缺陷：内核为校验先读取一次用户态传入的参数，校验通过后又在稍晚处读取一次并使用，而数据位于用户态内存、两次读取之间可被改写，于是第二次读到非法值并形成可利用的内核缺陷。这类缺陷不限于 Linux 内核，还见于内核模块、seccomp 等系统调用封装，以及 KVM 等 Hypervisor 与 TrustZone 等可信执行环境，Linux 内核相关 CVE 曾导致整机沦陷或重大信息泄露。利用门槛极低：攻击者只需两个用户态线程，一个用合法参数发起如 sigaction 的系统调用，另一个在两次读取之间把配置结构体中的变量 x 改为非法值，即可制造越界访问与任意内存泄露。因此作者的思路不是遍历内核逐个修补，而是把内核代码隐含的假设——两次读取应返回同一值——真正落实下来，让攻击者无法在内存中制造可见的数值变化。（YouTube EPZAvPu99FAkQ，[7-236]，L1）
- 〔USENIX Security（推测）〕Midas 的机制、实现代价与评估。系统只复用 Linux 已有机制而不重写内核：借助受 supervisor memory access protection 保护的取数函数（如 copy_from_user，XNU 与 FreeBSD 有同类接口）显式获知每一次用户态读取，并利用页表把页临时设为只读，从而在系统调用生命周期内保证对同一用户态对象的每次读取返回同一值。首次触碰时创建黄金快照并置页为只读，此时仍只有一份副本；并发写合法但会触发缺页，经修改后的缺页处理程序完成页的复制与映射，新副本对用户态可见而快照受保护，系统调用结束时丢弃快照，等价于为用户态页实现了一套多版本系统；每页用状态机区分受保护与否、唯一或多副本四种状态，额外成本只在并发写发生时产生。实现上只看了两个函数、新增约 1000 行代码、修改 26 行，平均开销约 3.4%，在 NASA Parallel Benchmarks、ForRun 测试集与 Apache Nginx 上测得；机制同时抵御来自另一内核线程的 confused deputy 攻击，制品评估获得全部三个徽章。（YouTube EPZAvPu99FAkQ，[236-569]，L1）
- 〔USENIX Security（推测）〕MAZE：面向自动化堆风水（heap feng shui）的布局操控。来自中国科学院的 Wang Yan 介绍，漏洞数量快速增长使团队必须快速评估可利用性以排定修复优先级，为此需要自动漏洞利用生成；而堆上漏洞只能在特定堆布局下被利用——例如堆溢出需要让可被利用的对象紧挨被溢出的对象，才能控制其中敏感指针。MAZE 只解决内存布局操控这一子问题：输入是 PoC 与期望布局，输出是把对象摆到目标位置后的布局。以 UAF 漏洞为例，delete switch 不清空指针，期望布局就是把可控对象放到已释放对象上，从而控制其中敏感指针并制造任意写原语；工具先从程序中分析并提取堆布局原语（此处为 function dispatcher 中的 create router、create switch、delete switch 等代码片段），再用污点分析与符号执行刻画原语语义，例如 create router 原语含三次 malloc 且每块尺寸均为 160。（YouTube EPZCW4Vrjkrcg，[7-247]，L1）
- 〔USENIX Security（推测）〕MAZE 的 dig-and-fill 装配算法与评估结果。装配原语的核心难点是原语噪声（原语内部不希望出现的分配与释放）带来的大量副作用，使既有方案耗时很长且成功率很低；MAZE 把布局操控重新表述为把目标对象 o 放到目标地址 p，若放不上只可能是两种情形——dig 情形即分配 o 时 p 被其他对象占据，需加入能释放合适尺寸对象的原语来挖空，fill 情形即 p 空闲但 o 仍落到别的空档中，需加入能分配对象的原语来填平。据此可判断原语应插入何处、即装配顺序，再以标准操作（仅含一次分配或释放、尺寸等于目标对象 o）作为度量单位，把 PoC 的目标距离与各原语的增量距离列为方程求解，得到需要哪些原语及数量（示例中为 1 个 create router 与 2 个 delete switch）。评估方面，在 23 个 CTF 程序上为 5 个劫持控制流、为 1 个泄露敏感信息、为 10 个产出可利用布局、另 5 个失败；在 PHP、Python、Perl 解释器上比既有方案快得多且全部产出期望布局；噪声数量不影响成功率、原语数量有影响但成功率仍高于 87%，并可通过方程组支持多对象位置约束的复杂布局。（YouTube EPZCW4Vrjkrcg，[247-672]，L1）
- 〔USENIX Security（推测）〕Beauty and the Burst：加密视频流的远程识别。演讲者（现场被听众称为 Roy）指出，流媒体流量对精准营销与流量刻画有分析价值，而 Netflix 及随后 Pornhub 等相继全面启用 HTTPS，问题便变成加密之后攻击者还能学到什么。在流量分析攻击场景下，攻击者看不到视频包内容，但能观测包方向、大小与时间等元数据：一个流会话表现为先缓冲、随后每几秒一个突发；他追溯突发的来源——MPEG-DASH 把视频切成数秒一个的 segment 文件，客户端在缓冲区跌破阈值时取一个 segment，而 segment 为数百 KB 到数 MB，故取段即突发。叠加可变码率编码（用 iguana 被蛇追逐的片段现场演示，画面越静止所需字节越少），内容泄漏到码率曲线、码率曲线再泄漏到段大小与突发大小，于是 YouTube 下载的 3500 个视频中约 20% 具备唯一可识别的指纹，且该指纹因服务端存储方式不变而稳定一致。攻击方在自有网络回放视频收集元数据，用深度神经网络训练检测器（每部片用若干以 0.25 秒为粒度采样的上行、下行与总字节时间序列表示）；Netflix 数据集为 100 部片、每部 100 个一分钟会话的 100 类分类，YouTube 为 18 类分类加一个含 3500 个会话的未知类检测问题，两者准确率均约 99%，YouTube 零误报、Netflix 误报率 0.0005。（YouTube EPZCjB127w5BI，[10-809]，L1）
- 〔USENIX Security（推测）〕更弱的攻击者与可行的缓解空间。第二个对手模型是只在受害者内网获得立足点的弱攻击者：用户在客厅向智能电视观看 Armageddon，手机上刷 Facebook 信息流，右侧一个恶意 Web 广告与电视处在完全不同的设备、隔离的浏览器进程与浏览器沙箱内，能力弱于其他进程，但两者共享家庭路由器到公网这条带宽受限链路。攻击站点向其客户端代码连续发送足够大且足够频繁的报文，在这条链路上制造拥塞，广告端只需计时自己收报文的延迟——每当突发进入观看端就出现一次延迟尖峰，把所有尖峰按时间累加得到的序列与实际突发大小高度相关；仅用该特征训练的分类器准确率接近在链路侧直接观测的水平，只是需要稍长的录制时间。该场景既是跨设备攻击，也可退化为同设备不同标签页的跨站攻击。缓解只能改动两个事实之一：改恒定码率代价过高（可变码率本是为快画面分配字节），改取段粒度会牺牲自适应性，随机化段大小会让用户遭遇两个小突发连排带来的播放卡顿，而把缓冲开大就越来越像下载而非流式播放，作者认为业界目前不会朝这个方向走。（YouTube EPZCjB127w5BI，[810-1212]，L1）
- 〔FAST（推测）〕D2FQ：构建在 NVMe WRR 之上的低 CPU 开销公平排队。来自 Sungkyunkwan University 的 Jiwon Ju（与同事 Kyusun Minu 及导师 Jin Gu 合作）指出，现代高性能 SSD 可达每秒百万级 IOPS，带宽与容量的增长使单台设备上承载多租户 I/O 成为可能，公平共享 SSD 带宽以满足各应用 SLA 因而重要；但块层的公平共享 I/O 调度器会带来显著 CPU 开销，而现代 SSD 已把瓶颈从 I/O 转向 CPU，故把调度卸载到设备是节省 CPU 周期的诱人方向。标准 NVMe 协议提供了名为 WRR（weighted round robin queue arbitration）的固件侧调度特性，但它只有 I/O 处理频率这一个可调参数、不考虑请求大小、且仅支持三个优先级类，故无法直接实现公平排队。D2FQ 因此在 NVMe WRR 之上实现低开销公平排队：沿用 CFQ 的虚拟时间思路拉平各活跃流的虚拟时间，但应用一旦提交 I/O 就直通设备、只在块层做最少操作；调度器维护全局虚拟时间 GVT（各活跃流虚拟时间的最小值），把 WRR 的三个优先级类抽象为快、中、慢三种处理速度，虚拟时间落后的流强制使用快队列追赶，领先的流改用慢或中队列让路，从而不必在块层执行 straggling。落地需解决三件事：如何从 NVMe WRR 获得足够大的处理速度差、哪些流应被限速、以及如何可扩展地管理 GVT。（YouTube EPZEPlvDOsfWw，[16-319]，L1）
