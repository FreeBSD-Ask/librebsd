# 321.4.29 〔USENIXATC推测〕WearDrive面向可穿戴设备的快速节能内存存储主讲

- 〔USENIX ATC（推测）〕WearDrive：面向可穿戴设备的快速节能内存存储。主讲人 Jian Huang（微软研究院实习期间与 Anirudh Badam、Ranveer Chandra、Ed Nightingale 等合作）指出可穿戴设备电池仅 100-500 mAh 且沿用手机的软硬件栈、能耗压力更甚，故应把可穿戴负载卸载到手机。实测表明能耗大户是存储软件栈而非 flash 器件（最高达 110 倍），原因是 flash 慢、runtime 开销与数据加密；因此提出用电池不可拆卸的 DRAM 作存储（BB-DRAM），以固件中位图在崩溃、低电量与死锁（watchdog 定时器）时定位并回刷页面保证持久性。混合网络方面，实测经 Wi-Fi Direct 写手机内存比本地 flash 更省电，并利用与 Wi-Fi Direct 共享射频信道的低功耗 BLE 连接质量预测 Wi-Fi Direct 以决定切换。系统以 key-value store 构建分布式内存存储：可穿戴侧 wear cache、手机侧 wear KV。（YouTube EPRAJivKu4Y7I，[9.9-668.8]，L1）
- 〔USENIX ATC（推测）〕WearDrive 的实现与评估。应用可经 register_sensors 等 API 注册传感器或回调，短时数据分析在可穿戴本地跑、长时分析移交手机；基于 Android 实现，含 BB RAM 管理器与混合网络管理器。在仿真可穿戴（双核 1.2 GHz、512 MB、BLE+Wi-Fi Direct，用 Monsoon 功耗仪测量）上对比 wearable-only 与扩展后的 Android Wear SDK：写性能提升至 9 倍、功耗降 4 倍；传感器应用整体较 wearable-only 省 1.5 倍、较 Wear SDK 省 3 倍电；通知场景较 Wear SDK+BLE 省 3 倍电；k-means 计算卸载后可穿戴电池消耗从 27-30% 降至不足 1%，整体延长设备续航 3 倍。配套发布首个可穿戴系统基准 WearBench，覆盖扩展显示、传感器与音视频负载。（YouTube EPRAJivKu4Y7I，[668.8-1330.3]，L1）
- 〔USENIX Security（推测）〕CURE：可定制、有韧性的 enclave 安全架构背景与问题。主讲人梳理 enclave 架构：由最高特权级的可信组件（或微码）把内存、核与缓存分给受硬件安全机制保护的隔离隔间，与可能被攻陷的 OS 完全隔离。现有架构面临三大挑战：缓存与控制流侧信道防御未被业界方案涵盖、缺少对外设的安全绑定（MMIO 保护与防恶意 DMA）、以及“一刀切”无法按服务需求裁剪。用户态 enclave（如 Sanctum、SGX 及其扩展）可复用 OS 功能、TCB 小、易开发，但不能运行特权代码、上下文切换有净化开销且控制流侧信道防护难；内核态 enclave（如 TrustZone、Sanctuary、Keystone）能跑驱动、免切换、更易防控制流侧信道，但每个 enclave 需复制 runtime，资源与启动开销更大。（YouTube EPRYOlTnsDj_4，[8.6-374.2]，L1）
- 〔USENIX Security（推测）〕CURE 的 RISC-V 原型设计。CURE 在 RISC-V Rocket 芯片上实现，支持多类 enclave（用户态如 enclave A、内核态如 B，乃至裸金属运行），安全监视器运行于机器态、负责远程证明等安全关键任务。共享 L2 缓存采用 way-biased 划分为 enclave 专有缓存路；系统总线上新增 filter engine，扩展 TileLink 协议引入 enclave ID，在仲裁器/解码器中为每个 enclave 配置一段允许访问的连续内存区间实现访问控制，越界访问触发中断交由安全监视器处理。原型 OS 用 Linux，安全监视器足够小以便验证，架构为 VM enclave 与抗侧信道缓存架构留出扩展空间。（YouTube EPRYOlTnsDj_4，[374.2-739.8]，L1）
- 〔会议不详〕Orion：Google 的软件定义网络控制平面。Google 的 Chip Killian 介绍在第一代 Onix 基础上从零重建的第二代 SDN 控制面 Orion：负责配置、管理与数据中心网（Jupiter）、园区网及 B4 私有广域网的实时控制，已生产运行逾四年。其核心是微服务架构加发布订阅网络信息库（NIB），双周发布已交付 30 余项重要能力，支持规模提升 16 倍、Jupiter/B4 可用性分别提升 50 倍与 100 倍、收敛时间改善 40 倍。系统按“意图—真实状态持续调和”的分层微控制器设计，以最小干扰方式调和意图与底层状态；NIB 保存意图与状态序列供回放排障。能力调和协议（capability reconciliation protocol）让微控制器以抽象能力表达所需与所提供的状态，可从全网地面真值完整重建控制器状态而不丢流量，把各类失效归约为普通重启或状态重建两类。（YouTube EPW_tSOj6hDKU，[17.3-369.7]，L1）
- 〔会议不详〕Orion 的失效处理策略与爆炸半径教训。集中控制器下，交换机与控制器断连比数据面故障更常见，多数情况下什么都不做反而是对的；小规模失效采取悲观 fail-closed 快速绕行，疑似大范围相关失效则转乐观 fail-static 冻结流配置以避免成环、保留最后已知良好状态。以 2019 年真实事故警示爆炸半径对齐：把大地理范围的 Orion 作业划入同一虚拟作业管理分组，恰逢设施维护事件导致整组控制器下线，规模超出网络容错设计，并暴露 BGP fail-static 实现缺口导致路由被撤销、造成用户可见故障——即便数据面转发本身仍静态运行。结论是虚拟作业分组等管理维度也必须纳入爆炸半径考量。（YouTube EPW_tSOj6hDKU，[369.7-730.7]，L1）
- 〔会议不详〕Seth：持久内存上的可扩展、高效且可预测哈希。香港中文大学的 Chao Wang 介绍字节可寻址持久内存填补内存与存储之间的鸿沟，首款产品 Intel Optane 于 2019 年上市，但读延迟为 DRAM 的 2-3 倍、带宽仅 1/6-1/3。现有 PM 哈希分两类：level 系（Level Hashing、C-Level Hashing）用两级结构在扩容时仅重散列约 1/3 键值项、开销低但平均吞吐不高；扩展哈希系（CCEH、DASH）按段分裂并做缓存行对齐设计、平均吞吐高但实时吞吐因段分裂开销剧烈波动。实测揭示两者在效率与可预测性之间两难，且并发控制的过多 PM 写限制可扩展性，Seth 借 level segment 结构与低开销分裂兼顾可扩展性、效率与可预测性。（YouTube EPWfeYJ9i_h1g，[15.8-407.8]，L1）
- 〔会议不详〕Seth 的级段结构、无解引用重散列与半无锁并发。Seth 以 level segment 把 1.5 个物理段组成逻辑两级结构，结合 EH 系缓存行感知与 level 系低成本扩容：one-third split 分裂级段时只重散列低层桶中 1/3 键值项；dereference-free rehashing 预存 16 位哈希位（随 KV 指针存放并在后台更新），消除重散列时指针解引用造成的 PM 随机写；并发控制采用 semi-lock-free——插入、查询、更新、删除等高频操作无锁，分裂等低频关键操作加锁。在 Optane App Direct 模式实测平均吞吐至少 2 倍于现有设计且最坏情况吞吐最佳；消融实验显示 semi-lock-free 提升峰值吞吐约 17%（PM 写减少约 60%），one-third split 提升 70% 最小吞吐（重散列时间减半），dereference-free rehashing 再提升约 50%。（YouTube EPWfeYJ9i_h1g，[407.8-805.6]，L1）
- 〔会议不详〕SMAC：软件定义的多接入边缘计算（MEC）SLO 感知资源管理（上半场：测量与根因）。主讲人为 UT Austin 的 Xiao（转写音），合作者为其导师 Dave Kim，提出 SMAC（SLO 感知的全解耦框架）。团队在 Dallas、Nanjing、Seoul 三城三国的本地 5G 网络上测量商用 MEC，发现约 75% 的请求违反 SLO、尾延迟高达约 1 秒；根因之一是 5G 无线资源竞争（无边缘侧计算竞争时南京仍有约半数请求超 SLO，上行时延随数据大小波动剧烈），之二是边缘服务器 GPU/CPU 计算竞争（竞争从 0% 提到 40% 后 SLO 未达率大增），共同根因是现有 MEC 架构不感知 SLO 截止期，调度只顾公平性与利用率。（YouTube EPgUBY_7_3HXg，[19-538]，L1）
- 〔会议不详〕SMAC 设计与评估（下半场）。SMAC 让 RAN 与边缘各自独立估计请求截止期并加速临近截止期请求：RAN 利用 5G 标准控制信号（如缓存状态上报 BSR 从 0 变大）推断请求起始时间；边缘以稳定下行作锚点，用小探针/ACK 周期交换形成平行四边形来估计非对称网络时延，并用请求生命周期事件（到达、处理开始、结束）的中位数估计处理时间。实现在 SD-RAN（转写作 SR-Run）5G 协议栈与 Intel CPU 加 NVIDIA L4 GPU 边缘服务器上，对比商用默认及 TUTI、ARMA 等协调式 SOTA 基线：SLO 达成率 90%-96%，尾延迟降低约 100 倍，且几乎无需应用改动、无 RAN-边缘协调。（YouTube EPgUBY_7_3HXg，[538-1066]，L1）
- 〔会议不详〕提升分层内存系统性能（上半场：软件与硬件分层管理对比）。主讲人为悉尼大学的 Baptiste Lepers，合作者 Willy van Ophem。传统方案由软件守护进程监控内存访问、判定热冷页并按 4KB 页粒度在各层间迁移；现代硬件方案则把 DRAM 当作 L4 缓存，由 CPU 按 64 字节缓存行粒度透明管理（未命中 DRAM 再取慢速层并回填缓存）。但 DRAM 缓存存在冲突问题：极少量页面即可映射到同一缓存位置（生日悖论），逐出引发昂贵的写回，而现有 Linux 完全不感知机器可能配有超大 DRAM 缓存。（YouTube EPieVMY70bLdo，[16-465]，L1）
- 〔会议不详〕Johnny Cash 系统设计与评估（下半场）。核心思想是减少 DRAM 缓存冲突：静态策略在页分配时最小化页间重叠（保证前 N 页互不冲突、第 N+1 页恰与一页冲突），动态策略由守护进程迁移映射冲突的两个热页。在持久内存机器上、按原 HeMem（两年前发表于 SOSP）论文的工作负载评估，系统在几乎所有 HPC、数据库等应用上同时优于 Linux 与 HeMem；微基准中仅靠静态分配策略即达 RAM 速度的 85%（Linux 仅 60%）；HeMem 严重依赖的热页检测启发式被证明脆弱、线程少时检测不到热页，小对象场景下 64 字节粒度的硬件缓存也远优于页粒度迁移；局限是流式（streaming）负载不重用数据、缓存反而只增加时延。（YouTube EPieVMY70bLdo，[465-920]，L1）
- 〔会议不详〕面向嵌入式应用的半托管（semi-hosting）快速模糊测试（上半场：动机与架构）。演讲者与合作者来自 Northeastern University 与 Florida International University。嵌入式 MCU 软硬件多样、缺乏 MMU 等硬件原语且受实时/电池运行约束，发现漏洞困难；现有 rehosting 方案把固件搬移到工作站仿真执行，受保真度、可观测性与兼容性限制。该工作提出新架构：执行与分析直接在 MCU 上进行，工作站只提供变异输入（半托管范式，业界曾用于质量测试但未用于安全）；MCU 内一个核跑监控器/模糊器、另一核跑目标，支持桌面级插桩与开发早期集成，并通过特殊内存偏移组织（含只读区）实现了无 MMU 的 ASan，还动态构建覆盖率位图、只传几个字节即可在工作站端重建执行覆盖。（YouTube EPpw8lx2IFtX0，[8-391]，L1）
- 〔会议不详〕SHIV（转写作 Shiv）实现与评估（下半场）。原型支持 ARMv7（转写作 Arm B7/Arm BA）与 Xtensa 架构，固件基于 FreeRTOS 加内核扩展，插桩用 GNU ARM 工具链（含为 ASan 偏移定制的 GCC），并实现支持 AFL++ 等现代变异引擎的通用串行代理。评估显示兼容 12 种流行嵌入式架构（仅遗留的 AVR 架构有问题）；保真度优于所有基于仿真的方案、仅与同样直接用硬件模糊的方案相当；因 FreeRTOS 轻量上下文切换，MCU 上的模糊甚至快于桌面原生 AFL，且比基于仿真的方案快约 100 倍；找到 5 个无假阳性的新漏洞（含 AWS 开发、影响大量设备的 FreeRTOS 内核漏洞）。（YouTube EPpw8lx2IFtX0，[391-771]，L1）
- 〔会议不详〕理解并发现并行文件系统中的崩溃一致性缺陷（上半场：动机与测量）。主讲人（转写作 Jun Han Sun）与 Chen Wang、Zhang Huang、Marc Snir 等合作完成。并行文件系统是超算的存储骨干，近期报告显示 41% 的并行文件系统每月或每周发生故障，单日故障损失可超 10 万美元、可达 100 万美元，恢复耗时可超一周；HPC I/O 栈（并行文件系统条带化 + POSIX 兼容 + HDF5 等并行 I/O 库）远比传统 I/O 栈复杂。团队研究 BeeGFS（转写作 BGFS）与 OrangeFS 两个系统、7 种从 POSIX I/O 到 HDF5 I/O 库的工作负载，共发现 34 个漏洞（EXT4 仅 5 个，Btrfs 与 OrangeFS 分别 15 与 19 个），后果包括数据丢失、拒绝服务与数据集不可访问；并援引 TACC 2016 年报告的 Lustre 元数据不一致事件。（YouTube EPqw1TjMjlxwQ，[8-368]，L1）
- 〔会议不详〕跨节点持久化重排序缺陷与 PFS-Check 框架（下半场）。以原子替换重命名（ARVR，转写）工作负载在 BeeGFS（2 存储节点 + 1 元数据节点）上为例：元数据节点的 rename 先于存储节点的 append/unlink 被持久化这类跨节点持久化重排序会导致崩溃后新旧内容都读不到的数据丢失，且 Btrfs 提供的 fsck 无法修复其中一类。作者提出通用框架 PFS-Check（转写亦作 PFS tag/Fastjson 等），含五大组件：多级 I/O 日志（联合追踪服务端与客户端 I/O 调用及网络报文）、基于轨迹排列的崩溃状态模拟（含剪枝以避免频繁重启）、工作负载特定一致性测试、依据崩溃一致性模型的合法状态重放、以及据此区分缺陷归于文件系统还是上层 I/O 库的缺陷分类，注重自动化与效率，未来将提供完整实现。（YouTube EPqw1TjMjlxwQ，[368-726]，L1）
- 〔会议不详〕防御推测执行中的缓存侧信道（上半场：背景与设计考量）。主讲人为东南大学博士生 Xiao Yichen（转写）。Spectre 攻击利用推测执行错误预测访问机密数据并改变缓存等微架构状态，通过逐出-重载-计时三阶段建立侧信道（flush 基与冲突基两类），而串行化指令、不可见推测等既有防御因性能与硬件资源开销大、缺乏真实硬件原型而不实用。作者指出降低防御开销需权衡保护范围与保护时长：实验显示攻击中缓存未命中率显著高于正常程序，故将造成 cache miss 的推测性 load 识别为不安全载荷（转写作 muscle）纳入保护，并依据控制流预测、访存次序预测与值预测等推测窗口的起止条件确定保护与解除保护时机、及时解除对正确推测的保护。（YouTube EPr0oZCGlhyyk，[8-355]，L1）
- 〔会议不详〕Speculative LFB 设计与评估（下半场）。方案基于存储全部已派发指令信息的重排序缓冲区设计多 bank 负载缓冲（LB）掩码位图跟踪推测状态（LB 行与掩码位一一对应，行内所有 bank 指令都不在推测窗口时该位清零），并在行填充缓冲（LFB，与 MSHR 协作暂存 miss 取回的缓存行）中引入安全检查：取回数据不得直接回填缓存，须等对应掩码位为零；推测验证正确后可直接从 LFB 回填而几乎不增加时延，攻击者因而探测不到访问时间差。方案在 RISC-V 协仿真环境与 Gem5 x86 乱序模型中实现，基于 FPGA 平台为三种方案构建硬件原型，对比 SS-CRV 与 CT（转写）竞争方案并使用 SPEC 2017 基准集：性能开销约 1.85%、FPGA 硬件资源开销仅约 0.6%（LUT 0.77%、触发器 0.31%），Gem5 仿真中约 3.20%。（YouTube EPr0oZCGlhyyk，[355-697]，L1）
