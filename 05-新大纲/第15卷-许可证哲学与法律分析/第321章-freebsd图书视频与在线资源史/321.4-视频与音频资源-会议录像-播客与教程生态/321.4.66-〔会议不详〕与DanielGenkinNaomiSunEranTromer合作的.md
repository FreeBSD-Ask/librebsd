- 〔会议不详〕成均馆大学的 정식 최 介绍 LibNVMMIO（转写中亦作 LibNVMeIO/libnvmio 等）：Reconstructing Software Paths with Fail-Atomic Memory Mapped Interface。存储时延已低于软件开销，目标是削减 NVMM 系统的软件 I/O 开销：库在提供 DAX mmap 的任意文件系统上做用户级 I/O，透明截获请求转为 mmap I/O 加日志，fsync 时原子写回原文件；数据操作在用户态、元数据路由给内核。论证日志优于写时复制（COW 页粒度写放大、大页与 TSX 每复制页停顿加剧开销；redo 日志可字节粒度差分记录并把 checkpoint 移出关键路径）；提出混合日志，按每文件读写计数器在 fsync 时于 redo/undo 间切换以各取所长；并论证通用文件 I/O 无需事务隔离、集中式日志优于分散式，用 per-block 日志（4KB-2MB 可变块、每块一把 RW 锁）加细粒度锁实现可扩展的集中式日志，索引用固定深度四级基数树（支持 256TB 文件）配 skip pointer 降低小文件搜索开销。（YouTube EPAHJgvcac9yc，[7.9-648.7]，L1）
- 〔会议不详〕后半场讲基于 epoch 的提交与检查点及评测。写线程写日志即返回，fsync 只递增全局 epoch 号；小于当前全局 epoch 的日志即视为已提交，由后台线程池异步 checkpoint，写遭遇未 checkpoint 的已提交日志时同步补做。在 NVDIMM-N 与 Intel Optane 上对比 ext4-DAX、PMFS、Nova（内核）与 SplitFS（用户态）：FIO 各访问模式（顺序/随机读写）吞吐全面领先，最高 2.2 倍；随机写多线程时私有文件配置下与 Nova 同样可扩展，共享文件配置下仅 LibNVMMIO 保持可扩展（Nova 用 per-inode 整文件锁）；混合日志在 60/40 读写比例处切换达到两种日志的最优；SQLite 评测中事务原子性由 LibNVMMIO 保证、无需 WAL，比 SplitFS（POSIX 模式仍需执行 SQLite I/O）约高 5%，整体较其他文件系统最高约 2 倍吞吐、13 倍可扩展性，源码将开源。（YouTube EPAHJgvcac9yc，[656.3-1302.8]，L1）
- 〔会议不详〕讲者（与导师 Aditya 及 UT Austin、Cornell、Purdue 的合作者）论述微服务性能鲁棒性。微服务延迟目标严苛而性能变异因素潜伏：请求率增 20% 使尾延迟尖峰 1.7 倍（开源微服务迹数分钟内即有 3 倍波动），共置后台作业因 CPU 争用致 5.3 倍尖峰，共享服务成瓶颈，且这些因素难以从端到端测量观测；state-of-the-art 的 bandit 控制器 AutoThrottle 因只能依赖 SLO 违例信号，跟不上潜伏因素演化，调整时已太迟。提出性能鲁棒性证书 PERC：计算环境扰动范围内最坏尾延迟作为控制器优化的界；据此构建 Galileo 框架，先用解析性能推理模型计算 PERC 再训练控制器使用该界；模型基于排队论，把请求的每一跳抽象为 M/M/1-PS 队列网络，端到端延迟近似为 gamma 分布，跨多个微服务基准仅 4-19% 误差，且只需现有端到端测量即可标定。（YouTube EPAKaAgYRf7PU，[18.2-456.4]，L1）
- 〔会议不详〕后半场讲 PERC 求解、shield 与评测。扰动球 delta-E 定义为任一队列处理/到达率最多 delta 倍变化，最坏情形是所有队列处理率更低、到达率更高；Galileo 用梯度估计在运行时获得各队列 μ/λ 变化与端到端参数 alpha/beta 的关系，并以压缩感知技术大幅减少采样数；为学习型控制器加鲁棒性奖励之外再构建 shield 校验动作，非鲁棒动作沿梯度修正为安全动作并给予大负惩罚以避免级联影响。评测实现于 AutoThrottle（bandit CPU autoscaler）与 Topfull（RL 准入控制器）：250 小时开源基准加压表明 PERC 在小扰动下给出很好的最坏尾延迟上界；Galileo 过载缩放器在 hotel reservation 基准上 SLO 违例仅 0.05%（无 shield 也已大幅减少，shield 再兜底），代价是峰值 CPU 分配高约 20%；成果开源，PERC 抽象被认为可推广到微服务之外。（YouTube EPAKaAgYRf7PU，[462.8-905.1]，L1）
- 〔会议不详〕成均馆大学的 Jiyeon Jung 探讨用 NVMe 原子写单元（AWUPF，转写作 AWPF，多数 SSD 提供 4KB）把优化支持从日志移到 SSD 侧。SSD 经 FTL 以 out-of-place 方式写入并原生保证映射单元级原子性，而文件系统/数据库仍靠 journaling/WAL 双写防部分更新，开销显著；既有事务性 SSD 方案都要改 SSD 固件，而 AWUPF 已是原生能力，事务落在一个页内即可直接借用。案例选 log-structured RAID（追加写、RAID 元数据每次写都需更新），目标系统为三星开源的 Poseidon OS：崩溃时若元数据更新未完成会引用过期位置造成不一致，其元数据靠 journaling 恢复，但启用后随机写性能劣化最高 25 倍（checkpoint 期间随机写触碰多个元数据页）。在 Poseidon OS 中 1 个 M page 等于 8 个 AWUPF，可借原子直写减少覆写：仅更新 1 个 M page 的写直接落盘，不再等 checkpoint。（YouTube EPAPSHDebxJmE，[16.1-558.7]，L1）
- 〔会议不详〕后半场处理直写与日志并存的一致性问题并给出评测。内存中 base map 必须在 commit 完成后才能更新，否则直写会把未提交事务的元数据提前写入 SSD，崩溃后出现部分更新；写 C 覆盖写 A 位置时，恢复若按 commit log 回滚会丢失最新写。方案是为每个 M page 引入版本号，每次目录写/commit 递增，恢复时比较 commit log 版本与 M page 当前版本，仅当 log 版本更新才回滚。在 Poseidon OS（SPDK reactor 划分元数据与用户数据 reactor）实现：随机写下标准法性能不随元数据 reactor 增加，本方案扩展 3.3 倍；1MB 请求下平均优于标准 20%；FIO 随机写最高 3.6 倍提升（顺序写与 direct 方案相当）；应用评测中 FileBench fileserver 型小随机写最高 14%、SQLite 小同步随机写最高 73% 提升；结论是 AWUPF 可用于把主机侧热数据一致性管理下放到 SSD。（YouTube EPAPSHDebxJmE，[568.5-1104.1]，L1）
- 〔会议不详〕讲者（与 Cornell、Yale 大学合作者共同完成）介绍遗忘式数据访问（oblivious data access）与分布式容错系统 ShardStack（转写中亦作 Shotstack/short stack）。加密只保护内容，攻击者仍能观察访问分布并与先验分布关联（示例中最热门对象直接暴露为密钥 a），故需让输出分布独立于输入分布；ORAM 类方案带宽开销 O(log n) 且面向主动敌手，Pancake 带宽仅常数 3 倍、面向诚实但好奇敌手，但两者都用集中式有状态 proxy：故障后新 proxy 缺状态，读请求要么按版本取全部副本而泄露分布（两个副本同属密钥 a）、要么取全部键的副本而带宽爆炸并长期停机。ShardStack 的目标性质：fail-stop 故障模型下任意时刻有界故障仍保持遗忘保证、保持可用，并使吞吐随物理服务器数线性扩展。（YouTube EPAQMenh1x1EA，[12.7-410.0]，L1）
- 〔会议不详〕后半场讲设计原则、容错与评测。ShardStack 分三层：查询生成层按所有键生成查询（每台 proxy 独立生成，输出分布整体均匀，避免按子集分区导致的跨分区非均匀）、状态层按键分区（同一键状态落在单分区，免去昂贵跨分区同步）、执行层按副本分区（副本本就是随机对象，部分访问消失不泄露分布）；请求由客户端随机路由到第一层、按键路由到第二层、按副本路由到第三层。容错上第三层故障直接重路由到健康节点，第一、二层用足副本因子的 chain replication，组件跨链打包后仅需 F+1 台物理机抗 F 个故障；并提出允许参数 f 界定的任意失败、只要求输出分布独立于输入分布的新安全模型。端到端实现已开源、无需改键值存储，在 EC2 上以 Redis 为 KV、YCSB-A/C 为负载评测：吞吐随物理服务器数线性扩展（一台即达集中式 proxy 吞吐，两台翻倍、三台三倍）。（YouTube EPAQMenh1x1EA，[410.3-838.8]，L1）
- 〔会议不详〕讲者（与约翰斯·霍普金斯大学的 Sepehr Abdous 及 Gurbani 博士合作）研究主机网络栈对流量突发性的影响。突发性关系到缓冲区调参、时延与丢包：2-to-1 incast、40 Gbps 仿真中，4 倍突发的工作负载带来 10 倍的交换机缓冲利用率尾与 10 倍 RTT 尾；自相似流（Hurst 估计 0.6）在各时间尺度保持突发，跨尺度变平滑的流（0.4）则相反，强自相似流在 50KB-2MB 缓冲设置下排队时延增长更快更大。经典结论称突发尺度由重尾流大小决定、与协议栈无关，讲者决定重审：主机栈叠加了短队列、拥塞控制、pacing/policing/shaping 与 NIC offloading，还有异步的进程调度、内存与电源管理。据此提出高分辨率流量测量框架 Valinor：测量探针置于主机栈（eBPF 挂在软件包调度器处捕捉出口流量）与网络交换机（可编程数据面），辅以离线分析。（YouTube EPARbUtqhnM8Y，[12.7-463.8]，L1）
- 〔会议不详〕后半场讲 Valinor 实现与三项发现。eBPF 数据面在包被 queuing discipline 调度发出时触发，过滤目标流、采集发送时间戳与聚合统计，per-CPU 环形缓冲记录存入 Linux 虚拟文件系统，控制面用流水线多线程设计分离轮询与存储线程；网内侧用 match-action table 过滤、镜像包头加时间戳后 recirculate 转发给采集机。以 Hurst 指数衡量自相似：TCP Cubic 因丢包为拥塞信号呈现 on-off 缓冲占用（0.6），DCTCP 为 0.5，维持平稳占用的 BBR 为 0.4；开启 segmentation offloading 后 FIFO/FQ 的突发都变长并趋同（多队列 NIC 下亦然），说明栈下层完全压过软件整形，TCP pacing 形同虚设；进程调度方面，CFS 与计算密集任务共置时网络应用吞吐出现 on-off 周期，Hurst 从 0.5 升至 0.7，而转投实时 FIFO 调度类又不适合负载共置。结论：现有反突发措施被证明无效，建议把措施进一步下推栈并做面向突发性的栈函数协同设计，源码已开放。（YouTube EPARbUtqhnM8Y，[464.8-914.4]，L1）
