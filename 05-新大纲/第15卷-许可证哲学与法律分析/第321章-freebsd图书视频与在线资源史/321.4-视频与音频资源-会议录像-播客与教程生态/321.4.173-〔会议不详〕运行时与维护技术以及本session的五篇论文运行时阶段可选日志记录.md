- 〔会议不详〕运行时与维护技术，以及本 session 的五篇论文。运行时阶段可选日志（记录状态与相关操作，便于复现 bug、定位根因并发现优化点）、动态检查（按 bug 模式分析执行、遇险即终止以防攻击，但有额外开销且同样只针对特定模式）与运行时失效预防（掩盖或绕过死锁、内存破坏、性能退化、资源泄漏等错误）；维护阶段则强调补丁昂贵、需补丁管理工具帮助理解影响、自动化打补丁以降低测试与部署人力、以及不停机的 on-the-fly patching。她随后预告本 session 五篇论文：Columbia University 的 ThisAI 面向分布式协议做数据驱动的自动不变式综合，用协议模拟轨迹快速否掉错误候选、把求解器查询降到数千量级，并按有界大小以巧妙顺序遍历候选；MIT、Boston College 与 MPI 的 Go Journal 验证并发崩溃安全的日志文件系统，需把崩溃行为与崩溃安全正确性数学化并做模块化证明，还用它构建了简化版已验证的 NFSv3 内核；来自 India 与 UC San Diego 的 Storm 把数据依赖的安全策略写成带精化类型的 ORM 模型，用类型检查器在静态期验证，策略集中在一个源文件声明；UCLA、Michigan、Harvard 与 Princeton 的 Holocrux 做自动化 JavaScript 并行化，服务端用 warp 依赖跟踪找并行机会、客户端把任务调度到 JavaScript 引擎里的 web workers，在 LTE 网络下约 20% 加速；USC、HKUST 与 ETH 的 Ceres 用静态与动态混合分析找出冗余 sanity checker 以降低开销（AddressSanitizer 的平均开销可高达 33%）。（YouTube EPSdQqTRR4u9I，[558-1054]，L1）
- 〔SREcon〕SRE 的水晶球：用排队论与通用可扩展性定律预测系统性能。主讲人 Aravind Sampathkumar 是 Booking.com 的 SRE，背景为高性能计算集群与存储系统的性能工程；他致谢 Universal Scalability Law 的作者 Neil J. Gunther（他曾花四天参加其工作坊）、工具维护者 Stefan Muller 与同事 Phil Larson，并援引导师“任何系统都是一条瓶颈链”的观点：把某个瓶颈修好，只是揭示下一个瓶颈。他主张 SLO 是反应式的（只回答“我们现在是不是坏了、是不是慢了”），而排队论能让人回答“流量涨 X% 时 SLO 会被违反多少、在这个地方加资源是帮还是害”，即从救火转向预防。他给出排队论术语基线（到达过程与到达率 λ、队列纪律如 FIFO/LIFO、服务时间、队列长度、等待时间、滞留或响应时间＝等待＋服务、利用率），指出队列无处不在（负载均衡器、连接池、Jira 看板）且本质非线性——翻倍实例不等于翻倍容量，方差（到达方差与服务时间方差）才是关键；再把 Google SRE 的金色信号映射到排队论：latency 是 service+wait、utilization 驱动 wait、变异系数是领先指标、traffic 即到达率、errors 常是系统过载的症状、saturation 即高利用率。最后他用 Little's law（L = λR，像热力学定律那样必然成立）演示“餐巾纸数学”：某 API 端点超时告警时，180 rps × 50ms 服务时间 ÷ 4 个 server（server 可以是物理机、VM、Kubernetes pod、进程或线程）得利用率 2.25，超过 1 意味着队列会无限增长；扩到 8 个 pod 仍是 1.125（不够），扩到 10 个 pod 是 0.9，而刻意不为 1 是因为必须给方差留余量。（YouTube EPSdxeGBS7290，[18-1165]，L1）
- 〔SREcon〕USL 作为诊断工具，两个演示实验与实用建议。他把可扩展性形式化定义后引入 USL：X(N) = γN / (1 + α(N−1) + β(N−1)(N−2))，其中 γ 是单服务器理想吞吐，α 是随 N 线性增长的竞争惩罚（等锁、等共享 map），β 是随 N² 二次增长的一致性或串扰惩罚（USL 假设在飞的请求之间一对一协调）；β 哪怕很小也会造成严重惩罚乃至吞吐回退，他举了“旧版 MySQL 从 4 核升到 8 核性能反而下降”的传闻为证。实验用一个单文件 Rust 程序暴露 /work、/contention、/coherence、/summary 四个端点各打一种惩罚（work 是位运算的 CPU 密集负载，contention 加锁等待，coherence 按在飞请求数做 N×(N−1) 的二次惩罚），用 wrk 加压并在 Colab notebook 里用 Stefan 写的 R 包拟合与画图：软件可扩展性方面把资源限制在 32 个 CPU 核上，纯计算负载 α=β=0、γ=15 呈线性；竞争端点 α≈0.097（可解释为约 9% 的时间在串行工作）；一致性端点 α=0 而 β 显著。硬件可扩展性方面用两台 EC2（一台跑服务、一台跑 wrk），以 taskset 绑核按 Amdahl 定律逐步加核，同样得到高 α 或高 β 的曲线，从而在挑 EC2 实例前就知道自己的上限。他还用 predict 函数外推到 192 核找出峰值与拐点，强调 USL 是诊断工具而非预言机，并列出局限（噪声数据、10 个微服务组成的分布式系统难以建模、异步事件驱动模型、一对一协调假设未必成立、限流器与依赖在阈值处切换算法、noisy neighbors）与实用建议：garbage in garbage out、外推不要超过 2 倍、真正要的是“期望延迟下的吞吐”、用队列思考问题、优先共享资源池而非每服务一队列、用缓存与代码路径优化攻击方差、按大小 bin packing 分流轻重请求、对重尾服务时间考虑优先级队列或 size-based routing。（YouTube EPSdxeGBS7290，[1177-2245]，L1）
- 〔会议不详〕不费力也能成功的语言设计：Brian Kernighan 在诺丁汉大学的讲座。Brian Kernighan 当场感谢诺丁汉大学计算机系授予的荣誉教授称号。他从自己在普林斯顿的一个学生室友（学地质学）手工翻找火山喷发数据讲起，谈到“如果流落荒岛只能带一个编译器”，答案是 C——但他自己写 C 版本花了 20 分钟到半小时，还踩了 fgets 参数顺序、返回 EOF 还是 null、scanf 要写 %lf 而不是 %f 以及“史上最烂设计的函数” strtok 等坑，程序也不健壮；转而用 awk 只需两秒、首次即正确、什么也弄不坏。他由此强调记法（notation）差别巨大，语言设计大多是在为特定任务想合适的记法，并且程序员效率往往比机器效率更重要（不过他也确认 Google 不用 OCaml 跑搜索引擎）。接着他借《创世纪》第 11 章巴别塔、1560 年代 Peter Bruegel the Elder 的画作与 1961 年 1 月 CACM 封面上罗列的编程语言（那是 Maurice Wilkes 跑通首台存储程序计算机 EDSAC 之后约 13 年），梳理语言年代史：40 年代直接写机器码（EDVAC 最初就是这样）、50 年代汇编、60 年代高级语言把表达提升到接近人的思维方式（Fortran 面向工程、COBOL 面向业务、BASIC 面向教学）、70 年代 C 让编译器、装载器、编辑器等核心系统部件能用高级语言写、之后面向对象与强类型。关于教训，他总结：只要有用就一定会被滥用（awk 本意是一两行的小程序，他却见过 2 万行的 awk 程序）；机器生成的输入比人工输入更严苛也更糟（Bjarne Stroustrup 在 Bell Labs 写的第一个 C++ 编译器生成 20–40 层括号嵌套、名字高度相似的 C，把 C 编译器搞挂）；语言还要在“修错与新增功能”和“保持稳定”之间平衡（Swift 一直在变）；并引 Tony Hoare 的名言“不要把未经验证自己的想法放进语言”，最后用 99 bottles of beer（有 1500 多种语言版本）收尾。（YouTube EPSg4U4r_AgJU，[1-1810]，L1）
- 〔会议不详〕AMPL 案例、语言失败的共性，以及给语言设计者的建议。他以自己深度参与的线性规划建模语言 AMPL 为例：它的前身是生成巨型系数矩阵的 matrix generator 与一个“让 Fortran 都显得优雅”的糟糕语言 GAMS；语言由 Bob Fourer（Northwestern 工业工程与管理科学系教授，1984 年 sabbatical 到 Bell Labs）、Dave Gay 与他共同设计，Kernighan 用 C++ 做了第一个实现（那是他的第一个 C++ 程序）。他以 diet problem 演示 sets、parameters 与 indexing 的声明式写法（食物×营养素的二维数组、成本、约束），以及配套的稀疏矩阵（工业线性规划模型常见 1 千到 1 万行列、密度低于 1%）、数据描述语言与类 git 的命令语言；最优解是 46⅔ 包 macaroni and cheese（Sainsbury's 与 Tesco 都不卖），而整数规划虽是 NP-complete，却只需在模型里加一个 integer 关键字。他还给出语言失败的共性：应用领域消失（troff 相关工具）、工程不佳、太大太复杂（英国的 ALGOL 68、美国的 PL/1）、Perl 6 来得太晚以至于 Perl “永远错过了那条船”、C++ 太大太复杂但靠庞大的嵌入式基数撑住；他推测 Swift 可能在 5 到 10 年内终结 Objective C，而 Rust、Go、Dart 的前途未知，并指出很少有语言彻底消失、更多是“failed to thrive”。他引 Alan Perlis 的名言“你总能写出烂代码”，最后建议想做语言的人从领域特定语言入手，不要造下一个 C++。（YouTube EPSg4U4r_AgJU，[1829-3594]，L1）
- 〔SREcon〕用统计技术自动检测云游戏的阻断性问题。主讲人自报姓名 Ian Eidel，来自 Netflix 自研 CDN Open Connect 的 CDN Reliability 团队，负责点播、直播与云游戏在交付可靠性、可扩展性与体验质量上的责任，并以云游戏 Oxenfree 作演示：用户在手机（当作手柄）与电视（当作显示器）之间，由游戏服务器渲染帧再以类直播方式推回。他指出云游戏的独特难题是常规指标会骗人：延迟、码率、丢包全绿，用户却可能体验极差，因为游戏本身可能坏了——黑屏、错误面板或循环播放的内容都可能带着漂亮的码率与帧率被投递。而他们最热门的游戏上线后连续三周对部分用户与国家处于损坏状态，唯一线索是一行日志 NGP profile response type name unknown。迟迟未发觉有两个原因：损坏没有强信号（是读用户反馈、注意到加载投诉上升才发现的），以及这行日志是“大海捞针”（在当期全量日志图中只是底部一条小橙色线，纵轴底部就是 0），而且总日志量与故障无关、连这个都无法告警。他把解法定为“把可能损坏会话的用户行为与会话日志关联起来”，在 gameplay time、问卷评分、自由文本反馈、码率、点击率这些候选指标里，最终选 playtime 少于 2 分钟作为含噪真标签。日志侧他给出流水线的前两步：selection & filtering（只保留含 exception、error、warning 的程序输出，并排除几条已知无害的高量日志）与 preprocessing（多数错误日志取堆栈首行即可，再用正则把数字、IP、URL 以及 [num] 形式的任务 ID 抹平，把百万级唯一日志压到几百条）。（YouTube EPSg7RjuMlcGI，[16-446]，L1）
- 〔SREcon〕向量化与聚类、precision/recall/F1，以及落地效果。他把日志文本转成能表示语义的 embedding（用 transformers 技术，即 ChatGPT 之类模型依赖的底层技术，靠 sentence-transformers 与一个免费模型、几行代码即可），再用 DBSCAN 把无法用预处理合并的日志聚成一批——例如“error locale with code and then country code not found”下面有几十个条目、国家码各不相同（看到印尼的国家码 “in” 就没法用正则抹掉），却可聚成一簇；最终把 30 天内 2000 万+ 唯一日志压成 135 条加 26 个日志簇。他借用分类模型的 precision、recall 与 F1 衡量某日志与“会话疑似损坏”的相关性：把“会话含某日志”当预测标签、“播放少于 2 分钟”当真标签，与问题相关的日志得到 83% precision、67% recall、F1 0.74，而无问题的日志只有 10%、20%、0.13。回到当初那起事故，按 F1 重排后，触发问题的日志从淹没在高量无害错误日志中一跃到榜首，按 precision 看则有超过 80% 带该日志的用户在 2 分钟内退出。该流程现已在所有游戏与所有平台上每小时运行，抓到了多个必须开事故的真实问题；未来工作包括更快告警、用 time-to-abort 指标捕获游戏中途（如某个关卡或交互之后）才发生的故障、以及与发行商合作改善测试以获得更干净的信号。三点带走：新领域会带来看似无解的难题、统计方法能让高量难题变得可行，而且统计工具现成可用（幻灯片上的东西都是几行代码加免费模型与库）。（YouTube EPSg7RjuMlcGI，[447-874]，L1）
- 〔FAST〕ScaleLFS：面向消费级 SSD 的可扩展垃圾回收日志结构文件系统。主讲人 Jin Yonghao 是首尔大学（Seoul National University）的博士生，介绍 ScaleLFS——一种带可扩展垃圾回收、面向商用 SSD 的日志结构文件系统（LFS）。LFS 以追加写、顺序 LBA 的方式优化写性能，被覆盖的旧页被标记为 invalid；当 stale 页累积导致空闲空间不足时触发垃圾回收（GC），GC 选取一段连续 LBA 作为 victim segment、把其中有效页迁移到空闲空间。问题是 GC 单线程，成为瓶颈：GC 触发后应用带宽最多掉 68 倍，而直接增加 GC 线程并没有改善性能，因为现有 GC 流程里的锁竞争随线程数上升。他分析 F2FS（一种广泛使用的日志结构文件系统）得到四个扩展性障碍：共享资源（GC 的 destination segment 与 page cache 被多线程共享，产生同步开销，应为每个 GC 线程配专用资源）、victim 选择过度竞争（选择过程被独占保护，应允许并发选择）、元数据同步过严（段元数据由单个 mutex 保护，所有线程都要等待，应支持并发更新）、数据保护粒度粗（GC 线程与 I/O 线程在文件级争抢，应降到页级）。对应地提出三大组件：DGC（专用 GC：每线程数据缓冲与专用写流，避免昂贵的 page cache 开销并支持免锁的顺序 LBA 管理）、SVM（可扩展 victim 管理：并发 victim 选择 CVS 用 dirty-segment 与 victim-segment 两张原子位图加原子 test-and-set 解决选择同一段的竞争、松同步更新 LSU 用原子位图管 VPB、原子整数管 VPC）、SVP（可扩展 victim 保护：每文件并发哈希表加 CAS，访问前插入 file offset、访问后删除，逻辑删除由首个发现者物理清理，并按 file offset 把请求分散到多个 bucket 以降低竞争）。（YouTube EPSmGh-HPySz0，[16-486]，L1）
