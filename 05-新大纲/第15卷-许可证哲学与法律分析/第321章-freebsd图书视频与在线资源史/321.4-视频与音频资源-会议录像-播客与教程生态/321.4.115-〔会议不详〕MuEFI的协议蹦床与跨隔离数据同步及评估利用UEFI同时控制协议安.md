- 〔会议不详〕MuEFI 的协议蹦床与跨隔离数据同步及评估。利用 UEFI 同时控制协议安装与查询的时机，为每个协议函数动态生成并注入机器码 trampoline（硬编码协议 GUID 与函数指针偏移），无需修改原二进制即可拦截并重定向控制流；数据面利用 UEFI 单线程执行、协议参数带 in/out 注解、规范定义 200 余个标准协议的特点自动化数据传输，离线剖析协议头建立 protocol/function/type 三表，并用 parameter pairing 启发式（如 buffer 与 buffer size 配对）推断指针含义，在 edk2 MdePkg 上仅不到 2.5% 的字段无法自动分析。原型实现于 x86 的 QEMU/KVM 与 ARM 的树莓派 4，UEFI 核心改动不足 100 行；六个常用模块全部沙箱化仅带来 1.9% 固件启动开销，fat 驱动与磁盘 I/O 驱动沙箱化平均运行时开销不足 1%（开销主要来自数据同步）。（YouTube EPHxyeVTuy9BE，[436.3-862.0]，L1）
- 〔会议不详〕ASAP：基于自适应预取（pre-paging）的快速应用切换。首尔国立大学 Samson（与成均馆大学及 Google 合作）指出移动设备内存受成本、功耗与面积限制而长期高压，用户每天切换应用超过 100 次；Android 在内存压力下用 zram 压缩匿名页、直接丢弃文件页并借助 low memory killer，导致切换时需解压或按需读盘而延迟显著上升，重launch则更慢，因此应避免 low memory killer 触发的重启。实测 8 个流行应用发现高压下切换时间平均增至无压力时的 4 倍，且切换期 CPU 与磁盘带宽利用率仅约 34% 与 15%——根因是按需取页把压缩与磁盘 I/O 拖到缺页时才做。为此提出 ASAP：应用无关、不改应用代码，由 switch footprint estimator（SFE）决定预取什么、pre-paging manager 决定如何预取。（YouTube EPHy9GW2d3Sos，[9.1-429.4]，L1）
- 〔会议不详〕ASAP 的设计与真机评估。SFE 记录每次切换按需取页的 fault buffer，生成每应用的候选表与预取目标表：匹配即提升、过时即淘汰；因约 75% 的文件页在 10 次切换中 9-10 次被访问而匿名页仅 44%，文件页采用离线剖析生成的静态候选表、匿名页采用运行时更新的动态候选表。pre-paging manager 在切换开始时派生多个预取线程，以批处理方式取页（匿名页 16 页一批、同一文件目标页一批）以降低锁争用，并以 sched idle 优先级机会性使用 CPU 避免与应用线程争抢。集成进 Android 后在 Google Pixel 4 与 Pixel 3a 上评估：切换延迟最高降低 33.3%、平均 22.2%（总结给出最高 35.7%），CPU 利用率最佳提升 35%、平均 18%，文件页预取因静态访问模式精度更高、匿名页因动态更新召回更好。（YouTube EPHy9GW2d3Sos，[437.9-877.2]，L1）

- 〔会议不详〕用 OpenID 标准为电子投票生成资格证明。来自法国南锡研究团队（Nancy）的 Anselm 讲解电子投票须在恶意投票服务器存在的前提下同时保证选票隐私与结果完整性（常见做法是选民加密选票并发布到公开的 append-only 公告板），而 ballot stuffing 攻击让恶意服务器伪造选票混入公告板、旁观者无法分辨：许多现实系统选择忽略此问题，另一些系统（如爱沙尼亚基于电子身份证）用选民签名密钥给选票签名，但在缺乏公钥基础设施时需要额外架设发钥实体，且签名方案未来被攻破时公告板上的签名可能泄露隐私。研究者注意到广泛部署的 OpenID Connect 授权协议（relying party 发 challenge、ID provider 返回签名的 ID token），其 ID token 中的 nonce 本用于确保令牌为本会话新生成，遂提出把 nonce 与选民选票绑定的思路。（YouTube EPI28OLG7WlSI，[8.1-318.6]，L1）
- 〔会议不详〕协议设计（OpenID for eligibility）与零知识证明实现。为把“何时验证签名”的决定权交还选民：选民先对选票做承诺、以承诺值作为 OpenID 流程的 nonce，核对 token 确实对应自己的选票与身份后才揭示承诺，并检查发往 ID 提供方的请求防止投票服务器作梗；为不暴露谁投了票，最终用零知识证明替换明文 ID token——证明投票服务器知道某 ID 使签名有效。该陈述虽理论可行，但 OpenID 规范强制 SHA-256（无法换成 Poseidon 等 ZK 友好哈希）且语句中哈希众多，朴素实现的证明时间不可用；团队用 snark 框架优化电路至每张图像仅一次 SHA-256，选用 Plonky2 框架并保持电路设计通用，基准显示协议可支撑百万级选民的大规模选举（证明由投票服务器并行生成）。PoC 基于开源 Belenios 投票系统并随 artifact 公开，安全证明用 ProVerif 完成机器可查验证。（YouTube EPI28OLG7WlSI，[326.0-616.1]，L1）
- 〔USENIX WOOT（推测）〕TCP 反射/放大攻击的实践测量。主讲人（该工作完成于波鸿鲁尔大学，现转往萨尔大学）介绍这是对其今年 2 月在圣迭戈 NDSS 报告的 UDP 放大 DoS 论文（DNS 开放解析器、NTP 可达千倍放大，今年 2 月出现最大 400 Gbps 攻击）的续作：理论上 TCP 三次握手保证 SYN 最多换回一个 SYN-ACK、无放大可言，但实测发现三类滥用：服务器在未收到 ACK 时反复重传 SYN-ACK（Linux 默认即 6 次）、不少 FTP/Telnet 服务器为省一个 RTT 在握手未完成前就推送欢迎 banner 数据、以及对关闭端口持续回发成千上万个 RST 的坏 TCP 栈实现。团队对整个 IPv4 地址空间逐主机发送单个 SYN 扫描，筛选放大因子不低于 20 的主机并做攻击类型与放大器分类。（YouTube EPI3r5gMgzSqM，[9.8-459.9]，L1）
- 〔USENIX WOOT（推测）〕测量结果、受害方主动防御与设备指纹。扫描发现数百万台可滥用系统：FTP 约 300 万台放大器（平均放大 22 倍），SIP 设备的激进 SYN-ACK 重传可达 1600 倍（超过已知 UDP 攻击），RST 放大器平均放大数万倍且发送频率极高（60 秒内单台可回发上千包）；指纹分析显示设备类型多样，自研 TCP 栈的 ZyXEL（转写音译 Syxel）路由器问题突出——虽已通知厂商但修复遥遥无期，Q&A 还提到 nmap 扫描即可令其崩溃。受害方可主动防御：对 SYN 洪水回发一个 RST 段即可让约 99.9% 的流量停止；对 RST 风暴可发送 ICMP 端口不可达消息予以终止。工作与 Marc Kührer、Thomas Hupperich、Thorsten Holz（转写音译）合作完成，次日团队还将在 USENIX 主会报告另一论文。（YouTube EPI3r5gMgzSqM，[461.6-927.2]，L1）
- 〔USENIX ATC（推测）〕Flash：面向跨机构联邦学习（cross-silo federated learning）的硬件加速架构。主讲人 Junxuan（来自 iSING Lab，转写音译为 Icing Lab，与 Cluster 方合作）先厘清概念：与 Google 提出的跨设备联邦学习不同，跨机构场景下高质量数据分散在各公司机构、受 GDPR 等法规限制无法集中训练，中间结果须用密码学技术而非加噪保护，分为横向（同特征空间、类分布式训练）与纵向（同样本不同特征，如医院与实验室协作）两类，典型密码技术为 Paillier 加法同态加密与基于 RSA 盲签名的隐私集合求交（PSI，用于实体对齐）。团队分析大量开源跨机构联邦学习框架后归纳出 9 种常用密码学操作（Paillier 加密、密文加法、密文-明文乘法、密文直方图、RSA 加密、RSA 盲化等），细粒度评估显示 RSA PSI 部分操作带来 10 倍以上、纵向逻辑回归梯度计算约 47 倍的性能退化，且不同应用、同一应用的不同阶段所用操作各异。（YouTube EPI5V3r-8sY-Y，[12.8-487.3]，L1）
- 〔USENIX ATC（推测）〕Flash 的“乐高积木”式架构与评估。GPU 加速尝试失败：GPU 面向小整数的数据并行，而这些操作需要大整数流水线并行、片上共享内存装不下大整数导致流水线频繁停顿，遂自研硬件。关键观察是 9 种操作都构建在模乘与模幂两个公共算子上、性能也由其决定；Flash 把大部分硬件资源做成两个高性能引擎（先算法级优化降低复杂度并以乘法替代模运算，FPGA 原型含 300 个引擎，片上内存缓存大整数），由片上控制器按密码学公式在引擎槽间动态调度数据流拼装操作，软件层提供类 NumPy 接口。原型基于 Xilinx FPGA 并接入开源框架 FedML（约 3 万行 Verilog，改动已并入社区），另用 Synopsys 工具评估 ASIC：9 种密码学操作相对 CPU 最高加速 40 倍、相对 GPU 3.4 倍；端到端任务（纵向逻辑回归、secure boosting、LSTM、ResNet、VGG 等）相对 CPU 最高 6.8 倍、GPU 2 倍；12nm ASIC 预计比 FPGA 再提速 20 倍以上。（YouTube EPI5V3r-8sY-Y，[488.1-1045.7]，L1）
- 〔USENIX Security（推测）〕Philipp Koppe（波鸿鲁尔大学，Ruhr University Bochum）介绍 x86 处理器微码逆向工程。x86 指令集因变长指令、改变行为与长度的多前缀及大量扩展而复杂易错——1994 年 Intel Pentium FDIV 浮点除法 bug、Coffee Lake/Skylake 超线程 bug、AMD Phenom TLB bug、Ryzen FMA3 bug 均靠微码补丁修复；CPU 以硬件解码器加软件式微码引擎（vector decoder）将 x86 指令解码为 micro-ops，微码 ROM 存出厂持久微码、微码 RAM 存非持久更新，match/breakpoint 寄存器可在微码 ROM 中放置钩子。研究问题为更新机制细节、微码编码与含义分析、能否加载自编微程序及其安全影响；实验针对 AMD K8/K10（2013 年前），微码更新通常由 BIOS/OS 在启动早期应用，内核态也可手动加载——将更新装入 RAM 并把虚拟地址写入特定 MSR，复位即丢失；更新文件由含校验和的头部、match 寄存器与按 triad（三操作加序列字）组织的微码构成，无强密码保护。（YouTube EPI6dQfnb3y0I，[10.3-721.7]，L1）
- 〔USENIX Security（推测）〕后半：逆向方法、成果与微码木马。团队以自写最小 OS 的 AMD 节点加树莓派构建自动化测试框架，通过 breakpoint 寄存器逐地址 hook 微码 ROM 并执行指令观察崩溃，生成热图（heatmap）定位指令在微码 ROM 中的实现位置；因不知编码先暴力喂随机 micro-ops，找到“立即数加 EAX”微操作作突破口；同时开盖分层 AMD K8 裸片、用 OCR 读出 ROM 位流作并行验证。最终为 62 条指令生成热图、逆向 29 个微操作编码与 12 个操作数、确定 64 个操作位中 53 位的含义，并实现可反汇编现有更新中 40% 微操作的反汇编器；从头实现 11 个微程序，包括 JavaScript 可触发的远程微码后门与引入时序侧信道、故障攻击的密码学微码木马。现场演示木马比较 EAX 与暂存微码寄存器 T1D 中的 magic 常数后为 x86 程序计数器加偏移，错位跳入 JIT 代码执行 payload，在浏览器内无内存破坏即可任意代码执行，11 个微程序已以汇编与二进制形式发布 GitHub。Q&A 讨论现代处理器微码签名验证绕过（尚未深入，列为未来工作）与木马检测：微码跳转与额外指令引入的时序开销可测但检测复杂。（YouTube EPI6dQfnb3y0I，[768.1-1513.1]，L1）
