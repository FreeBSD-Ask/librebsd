# 321.4.171 〔会议不详推测系统会议〕Mage让安全计算获得近乎零成本的虚拟内存主讲人为加州大

- 〔会议不详（推测 系统会议）〕Mage：让安全计算获得近乎零成本的虚拟内存。主讲人为加州大学伯克利分校博士生 Sam Kumar，与教授 Kular 及 Popa 合作。他以安全多方计算（SMPC）为实例，说明 Alice 与 Bob 可在不向对方泄露各自秘密数据的前提下计算任意函数 F，典型应用是密码复用检测，以及多家银行联合排查可疑交易、多家医院因法规限制无法共享患者数据但希望跨机构研究健康模式；现实中内存开销成为瓶颈，因为密文远大于明文——乱码电路类方案把输入与中间结果放大到明文的一百二十八倍，前人经验上称 SMPC 只能扩展到几千条输入记录，因为内存耗尽后操作系统的换页极慢，而换页慢源于两点：依赖 LRU、NRU、LFU 等启发式且没有单一启发式对所有负载都好，以及经典换页是被动式的、只有缺页才取页，预取本身也依赖启发式。Mage 的关键观察是安全计算程序具有 obliviousness oblivious 性：程序发出的访存序列与输入数据无关，为达到这点须把分支替换为类似多路选择器的逻辑；这一要求本身内生于隐私保证——若程序不 oblivious，运行方就能通过观察访存推断对方输入。由于所有 oblivious 程序在某种意义上完全可预测，Mage 可预先计算访存模式并据此定制内存管理：密码复用检测可用排序归并连接求解但那样不 oblivious，惯用做法是用 bitonic sort 等 oblivious 算法合并两个已排序列表，其访存呈蝴蝶形；传统换页会因此表现更差，而 Mage 不受影响，实测在 bitonic sort 合并负载上比依赖 OS 换页的方案快 4 到 5 倍，且两方都受益，因为生成 garbled gates 的第一方做的计算与第二方类似。（YouTube EPSJo36EweWyo，[10-531]，L1）
- 〔会议不详（推测 系统会议）〕Mage 的 planner、评测结果与未来方向。给定程序与目标机器属性，Mage 的 planner 输出一份内存管理计划，概念上由描述计算的字节码与一份描述何时在内存与存储之间搬数据的日程表组成，运行时由解释器据此执行；为区别于 OS 换页，他把这份计划称为内存程序（memory program）、规划过程称为 memory programming。核心是两个想法：一是应用 Belady 最优换页算法（驱逐下次使用最远的页），经典换页无法直接用因为不知道未来访问，而这里未来已知；二是 Belady 仍然被动，故再用未来访问知识做预取，Belady 负责优化存储带宽、预取负责掩盖存储延迟，两者结合后开销所剩无几。planner 分三阶段：先在规划用的虚拟地址空间内放置变量与中间结果并输出描述访存模式的字节码；再把字节码变换为装入可用内存的形式并按需换出到存储，Belady 需两遍（反向分析页的使用位置、再正向施加算法）；最后用预取确定何时发起内存与存储之间的传输以得到换页日程，并与字节码合并成内存程序。系统尚存的挑战包括如何应付访存模式的规模、如何从 DSL 提取访存模式、如何把预取整合进 Belady、如何并行化与分布式化，以及如何扩展到新的安全计算协议。实现为 C++ 版本，支持乱码电路与另一种安全计算方案 ZKSK，以用户态程序运行、不修改操作系统。评测设三种配置：unbounded（内存足够装下全部计算，视为耗时下界）、mage、OS（依赖 OS 换页，视为上界），在 Microsoft Azure 上跑一组代表大型 SMPC 应用内核的负载；结果显示 Mage 相对 unbounded 的额外开销很小，七个负载在 unbounded 的十分之九以内完成，相对 OS 配置始终更优、其中七个至少快四倍，而 L Join 与 R Sum 两个基准上 Mage 比 OS 配置快一个数量级。密码复用检测应用并行到每方四台机器、两方分别跑在两家不同云商并跨广域网通信，成功扩展到每方一亿条用户密码记录，且在给定时间预算下 Mage 可处理比 OS 换页大三倍的问题规模。收尾他指出 oblivious 应用不限于安全计算：为硬件飞地编写的应用常以 oblivious 方式抵御侧信道，某些明文应用（如神经网络推理）天然 oblivious，因此 Mage 的技术也可能惠及这些场景。（YouTube EPSJo36EweWyo，[531-905]，L1）
- 〔会议不详（推测 系统会议）〕StreamBus：把网络当作语义感知存储总线以按需运行未修改的应用。主讲人为清华大学的 Jim，与 NUS 及中南大学合作。他先指出现有交付模式是 all-or-nothing 的全量下载，即使只用很小一部分也要下完几十 MB 乃至 GB，导致两个问题：用户推迟或跳过更新从而使漏洞长期残留，以及应用体积持续增大造成漫长下载安装、对短期使用场景（如出差者需要一张交通应用）尤其不友好；两者同源于应用必须完整安装后才能使用。他主张 5G 与 Wi-Fi 6 使网络带宽可比肩本地存储，因此可把网络当存储总线实现免安装按需执行，但现有方案各有硬伤：Google Instant Apps 这类框架绑定方案需要侵入式改造应用；Web 与小程序方案牺牲性能与原生能力；NFS 等网络文件系统虽在 OS 层支持远程执行，却是为高吞吐与顺序访问设计而非为应用执行设计，对不可预测的控制流跳转这类访问模式效率低下，即现有方案无法同时平衡透明性、效率与兼容性。核心思想是语义虚拟存储总线：不把存储当被动的数据块，而是让它感知应用执行，捕获当前运行线程等执行上下文，据此让语义感知预取器预测未来块访问序列、提前取回代码块并按需流式提供，即执行感知流式传输。两个根本挑战是延迟鸿沟（处理器微秒级需求对无线网络毫秒级访问，形成 100 到 1000 倍不匹配使 CPU 停顿）与上下文鸿沟（存储系统本质无状态、把代码块当独立请求，而应用执行是有状态且线程相关的，Linux 默认 readahead 之类通用预取策略无法有效预测）。StreamBus 位于应用与远程存储之间，使远程块看起来像本地执行感知流；工作流为应用触发缺页后请求被拦截送往 runtime，快路径立即取回所请求的块，慢路径同时启动、按预测在后台抓取块，两者都存入页缓存供后续使用，这种双模式传输用重叠按需取数与后台预取来掩盖网络延迟。（YouTube EPSOFDEfGOMi8，[10-435]，L1）
- 〔会议不详（推测 系统会议）〕StreamBus 的马尔可夫链预测模型、双模式传输与评测。预测采用马尔可夫链模型：它捕捉下一状态依赖当前状态的转移，与“下一个代码块常取决于当前块”的执行特性吻合，且轻量——只依赖当前状态、不需长历史或复杂模型。建模流程是先从同一应用的不同线程采集块访问序列并合并以捕获整体执行模式，再统计相邻块之间的转移构造下一状态频率的计数哈希表，最后归一化为概率形成马尔可夫转移模型；预测时给定应用与起始块先定位可执行文件及其马尔可夫模型，再依据当前状态迭代预测下一块直到达到预定义预测长度，毫秒级即可生成数百个未来块，开销远低于 DNN 之类复杂模型。双模式机制具体为：应用访问缺页进入快路径；快路径向服务器请求所需块；服务器返回元数据指示多少块走快路径、多少走慢路径；客户端据此激活慢路径做后台抓取；服务器经快路径返回所需块供立即执行、同时挂起块经慢路径在后台流式传输；所需块到达后主内核线程恢复执行。评测在 1 Gbps 网络下覆盖桌面与移动设备，并把 StreamBus 集成进 Android 框架使未修改的 Android 应用直接从远程存储运行，对手是本地存储与 NFS。微基准中缓存命中率较本地存储与 NFS 高约 40%，在 Shortcut 与 Android Studio 这类访问模式更复杂的应用上更明显；桌面端在冷启动条件下甚至优于高性能本地存储，每页延迟较 NVMe SSD 降低 15% 到 40%；移动端在 Wi-Fi 下延迟约为本地存储的 17% 到 27%，超出部分主要来自碎片化文件布局中小文件过多导致元数据增大、预测失效。端到端在桌面与 NFS 都跳过下载与安装阶段、移动端因 Android 系统限制仍需轻量安装，启动开销较本地存储降低 20% 到 55%，桌面接近 NVMe 性能、移动端通常保持在 40% 以内，例外是桌面 Shortcut 与移动 WPS 因碎片化布局与可预测性差而下滑；应用交付总时长桌面较原生流程减少 45% 到 78%，移动端也在 36% 以上。鲁棒性实验注入 2 到 100 毫秒往返延迟并叠加丢包与抖动模拟广域网，端到端延迟在约 2 毫秒的近距离延迟下接近或低于本地安装基线，约 10 毫秒的跨城延迟下多数应用仍低于该阈值，说明执行感知预取能有效掩盖网络延迟。他最后认为这有望支撑零安装应用与边缘云执行。（YouTube EPSOFDEfGOMi8，[435-949]，L1）
- 〔USENIX ATC〕HECo：首个端到端的全同态加密编译器。主讲人自称 Alex，本工作完成于其在 ETH 的博士期间、现在 Intel Labs，与导师 Anwar 及同事 Patrick、Nero 合作。他先回顾 FHE 的意义：数据在传输与静态时的加密已被广泛采用，但为处理数据必须先解除保护，而 MPC、ZKP 与 FHE 等高级密码技术能让数据在计算期间也保持加密，从而显著扩展真正端到端安全的适用范围。他否定“FHE 太不实用”的旧判断：十年来从做单次比特乘法要三十分钟到如今的几十毫秒，MNIST 推理从 2016 年的几分钟降到几百秒以内，ResNet 推理可做到几秒，并已有真实部署，如微软 Edge 的密码监控服务与韩国的 COVID 接触追踪应用；之所以用得不广，是因为开发与部署 FHE 应用极其困难，那两个部署都需要专职密码学家与研发工程师团队。原因是安全计算与业务逻辑深度交织、把函数翻译成安全计算的方式极大影响性能与功能；FHE 表达能力有限，本质上不能在零知识计算中分支，实践中大体限于二元或算术电路，没有除法与原生比较；基于 learning with errors 的现代方案会累积噪声、须用昂贵的密文维护操作仔细管理；许多方案引入昂贵的同态运算以换取把数千个值批量打包进单个密文的 SIMD 并行能力，但数据移动被严格限制。工具研究几乎与实用 FHE 同步展开，从最初只做单运算、再到 FPGA 库需开发者手工做噪声管理，直到 2019 年微软的 EVA 工具才首次能抽象并优化这些；但现有工具普遍仍假设输入是电路级表示、没有整体考虑开发流程。HECo 提出首个端到端 FHE 开发架构：由于应用横跨众多领域、各自范式与表达方式不同，直接下沉到电路会丢失大量信息，因此新增一层 schema 无关的高层抽象以支持高层优化；同时不再只面向软件实现，而是直接面向底层硬件含未来专用加速器，为此要把部分底层数学移入编译器，从而能在密码层面做新优化或按特定硬件后端调度。实现上基于 MLIR 编译框架：以 schema 无关的 FHE 高层操作结合标准 MLIR 的控制流等构件构成高层程序表示，优化后下沉到传统 FHE 电路表示，进而可对接微软 SEAL 等现有实现，或经更低层中间表示直达各硬件后端。（YouTube EPSP3C6gLWIS4，[10-390]，L1）
- 〔USENIX ATC〕HECo 的 SIMD 批处理优化、评测与后续方向。他聚焦高层 IR，提出针对这种能力强但数据移动受限的 SIMD 式并行的优化：不能置换，也不能 scatter-gather（其他向量化范式里很常见），只有对密文的循环旋转。他以图像处理应用为例说明为何传统向量化不适用：对每个像素迭代 3x3 卷积核时，展开并向量化内层循环需要数据移动而非减少运算数，反而引入昂贵的同态旋转操作使代价上升。进一步观察若干次迭代中底层密文与被不同迭代触及的槽位会发现槽位并不对齐，无法直接施加 SIMD 操作，而对齐所需的旋转让代价维持同样的高。出路是转变视角：聚焦单次迭代的运算（九个像素各乘一个权重）同时留意其他迭代的槽位变化；由于各迭代中卷积核像素的相对偏移相似，只要挑选得当便形成一种模式，可被精心旋转以同时处理全部迭代，于是得到只需九次旋转而非九乘 n 方次旋转的 FHE 程序（前提是密文足够大以容纳整张图像）。论文把这一思路推广并自动化、应用于多种负载；受时间所限他用少量评测展示 HECo 相对不考虑批处理的基线取得数量级加速，且选较小子问题规模以便与合成式工具 Porcupine 生成的最优解对比——结论是基本追平最优解，却只需几秒而非合成方法的分钟到小时。结论部分他把 HECo 定位为第一个端到端 FHE 工具链架构，并证明它使高效 FHE 对非专家可及，工具开源，论文可在 arXiv（转写 archive）与 USENIX 网站获取，感谢工件评审团队帮拿到三枚徽章。他还提到正牵头一个汇集 FHE 开发各主要参与方的工作组，目标是基于 HECo 与其他 MLIR 后续工作标准化一组 MLIR 式抽象与交换格式，让人能独立选择输入语言、算法优化与硬件后端；展望社区尚未真正攻克的有限表达力问题，需要让开发者表达应用应如何翻译到这个受限环境，而不必先理解其背后的密码学原因。（YouTube EPSP3C6gLWIS4，[390-703]，L1）
- 〔SREcon〕Y2K 与那些令人失望的灾难：风险削减与危害缓解。主讲人（转写未给姓名）自述做过二十年技术写作、英语专业出身，现供职于做 feature flagging 服务的 LaunchDarkly，曾在 Microsoft 参与 BitLocker 项目，并教初中性教育课；她以一 位 Des Moines 系统管理员朋友在 1999 年 12 月 31 日与老板拿饭碗打赌的 Y2K 亲历故事开场：当时业界真的以为世界会完蛋——Time 杂志以末日为封面，大型机上的 OS/390 不仅要改日期，还得冒险重启，因为硬件“一直跑着”与“重新开机”是两回事，而最终“没人记得你阻止了一场危机”。她由此把工程对策分为风险削减（risk reduction，如疫苗、ABS 防抱死、铁路道口闸门、把 OpenAPI 文档与 API 代码一起 code review、用状态机与流程图思考失败路径），并强调取舍必须基于数据而非直觉：BitLocker 让“烧掉机器、保住数据”取代了过去的“救机器”，正如“开车去机场比坐飞机更危险”所揭示的那样。（YouTube EPSWfsLwiDWzg，[6-1250]，L1）
