- 〔FAST '24（推测）〕上层还有三项附加优化。〔11:01〕第一是服务器端回写：vanilla Lustre 服务器默认写通，现允许服务器在一定阈值内改回写——后端为 LDXFS 时实测"under sixty four K it's more beneficial to use buffered I O"，默认阈值即定在 64 KB；第二是"cross file batching for buffered writes"〔11:31〕（正解 cross batching）：vanilla 把脏页批成一个大块 bulk RPC 以提升网络与磁盘效率，但若填充不足会拉长刷盘、对海量小于 1 MB 的小文件尤其不利，故把多个文件的脏页一起批；第三是"delayed allocation"〔12:07〕，服务端延后分配块以便合并小而分散的请求再一次性写下更大连续段，主要服务对单一共享文件做跨步（stride）I/O 的场景并减少碎片。〔12:43〕一致性方面，一个节点尚有未刷入页缓存的缓冲数据、另一节点以 direct I/O 写同一区域可能重叠，但分布式锁管理器可挡住此类冲突，非对齐 direct I/O 同理，整体不影响 Lustre 的强一致保证。〔13:18〕所有特性与多数阈值都可经 lctl 开关或调参，交付物中附全部配置项。〔14:13〕评测用三套文件系统、服务器均为 NVMe 后端、最多 32 个客户端节点：Btrfs 有缓冲与依赖 Linux 内核机制可切 direct 两种缓存模式（后者只有一个阈值，若 Auto I/O 只有单阈值则直接可比）；OrangeFS 该版本不接页缓存、客户端全同步，提供旧式 AIO 缓冲异步与写通两种服务端模式。〔15:20〕首个用例是单进程流式 I/O：Auto I/O 在小 I/O 段用缓冲、锁竞争为零时不切换，越过阈值后自动改 direct，读写两侧一致，作为健全性检查。〔15:54〕I/O500 十节点挑战的 md-test 产生大量极小文件，因低于小阈值而恒用缓冲；vanilla、服务器端回写与 cross batching 因撞上 VFS 加锁瓶颈而收益相近，改用四个挂载点（可把不同进程绑到不同挂载点）后开始见效，delayed allocation 因仍是单目录而无影响；读侧因没有同类锁竞争而各点更贴近。〔17:10〕IOR-Heart 产生非对齐跨步 I/O 且 I/O 尺寸落在决策窗口内、写向单一共享文件；另需说明 Btrfs 与 OrangeFS 不支持在线分层、此处回退到缓冲分层。〔17:42〕Lustre 的 direct I/O 可代客户端持锁从而减少锁抖动——缓冲式下有三百万五千次锁回调，切 direct 后消失，加上延迟分配取得最佳写入性能；读侧因无锁竞争仍全部留在缓冲模式。〔18:31〕真实负载用计算流体力学的 Nek5000，512 个进程各在每作业步写约六百 MB 文件、交替计算与 I/O，十分钟共产生约六百 GB，I/O 尺寸分布横跨小阈值以下、大阈值以上与窗口中间；cross batching 因一次只写一个文件无益，delayed allocation 收益有限，而 Auto I/O 与服务器端回写逐步改善——"over 130,000 I/O requests that would otherwise fall into default buffered mode were chosen to use direct I/O"〔19:25〕。〔19:41〕结论收束：透明地把缓冲与 direct 结合在文件系统内、保持强一致，关键技术是客户端 Auto I/O 与服务器端回写。〔20:07〕产品化方面，非对齐 direct I/O 支持已并入 Lustre 2.16（严格可选，仍需 O_DIRECT 标志），依赖 I/O 尺寸切换的基础 Auto I/O 计划进入 2.16 及以后版本，交付物附 issue 追踪链接；未来工作包括更广的硬件、集群与应用工作负载性能分析以实现运行时阈值自调整，以及让服务器端算法也考虑可用内存等服务器状态。（YouTube EPYPpTPQURy-U，[660-1303]，L1）
- 〔USENIX Security '15（推测）〕讲者开场申明，要用软件定义网络与网络功能虚拟化等新网络技术改进当下的 DDoS 防御实践，并介绍与卡内基梅隆、伊利诺伊同事共建的平台 Bohatei 的设计，实现代码亦已公开。〔00:37〕背景是 DDoS 代价高昂："which is both uh monetarily cost with with the cost of tens of thousands of dollars an hour"，还伴随声誉损失，且几周前 FBI 刚警告 DDoS 勒索诈骗上升。〔00:58〕三条恶化趋势：攻击数量增加（"thirty percent of botnets attack more than fifty targets a month"）、攻击量增大（"attacks of hundreds of gigabits per second are becoming the new norm"）、攻击类型多样化（NTP 攻击等新类型与 tsunami、syn floods 等新变体）。〔01:41〕而当下防御手段是专买专有硬件清洗设备——"we buy these appliances that are quite expensive"且能力与容量固定、只能放在固定位置。〔02:02〕三大局限：其一功能固定，"if I buy a blue box, it is only good for"〔02:09〕蓝色类型攻击，遇到橙色或红色攻击就只能依赖厂商；其二容量固定，多数时候要麼浪费防御资源要麼攻击成功；其三成本高，故通常只买少数几台放在固定位置，流量不得不偏离最优路径绕行，带来额外时延并需靠易错的路由技巧强行施加。〔03:42〕愿景是灵活而有弹性的防御：对攻击类型灵活（蓝橙红皆备）、对攻击位置灵活（三个入口 A B C 中按需部署）、对攻击量弹性（按比例伸缩）。〔04:43〕于是介绍 Bohatei——"a practical ISP scale system"、"It uses SDN and NFV"，且"can actually react to attacks of five hundred gigabits per second in one minute"〔05:00〕。〔05:15〕先补两门背景课：SDN 的动机是传统分布式路由协议施加转发行为"very complex and error-prone"，大厂转用逻辑集中控制器编程交换机；NFV 的动机是传统防火墙、入侵检测等专有硬件"very inflexible, very narrow, they have very narrow APIs, and they are expensive"，改在通用硬件上按需起虚拟机、靠起新 VM 伸缩。〔07:03〕两者对 DDoS 的价值是：NFV 降成本、以软件换硬件而更快迭代、可弹性扩容；SDN 则能按策略把流量导成期望的虚拟机序列。〔08:05〕平台设想是 ISP 把 DDoS 防御作为服务卖给客户，配一套防御策略，用 SDN 与 NFV 把可疑流量送进数据中心并按策略穿越虚拟机序列。〔08:35〕落到三阶段工作流：策略层先靠预测机制预判攻击场景（因任何真实系统都有非零滞后），资源管理模块据此决定 VM 数量、类型、位置与路由策略，网络编排机制则配置全网交换机使之生效。〔10:02〕威胁模型是通用且动态的：攻击者可挑任一或多个客户，最大攻击量有固定预算但不确定，在目标、类型、体量、入网口四个维度上自由且自适应地切换。〔10:51〕三个挑战随之而来：预测须抗欺骗、资源管理须够快、SDN 不能天真使用。〔11:44〕资源管理先把防御库与可用计算、网络资源连同攻击预测交给决策，若建模成全局优化虽正确最优但"even for decent sized ISPs it takes hours to solve. This is not practical"〔12:09〕；解法是先以数据中心粗粒度信息决定从各入网口送多少流量到哪个数据中心，再由各数据中心并行本地解 VM 分配，贪心加并行走"fast greedy algorithms and Parallelism"〔12:47〕。（YouTube EPYRTyz8zRKm4，[10-780]，L1）
- 〔USENIX Security '15（推测）〕第二个问题是网络编排如何可扩展。〔13:09〕天真用 SDN 的症结在于按流编程：策略说绿包给 VM2、红包给 VM3，而 SDN 交换机每遇一条未见过的新流都要上报控制器学习转发规则。〔13:22〕DDoS 场景下这本身成了漏洞——"all an attacker needs to do is to craft traffic that involves a lot of distinct flows"，控制通道被压垮、有限的交换机规则空间也被迅速耗尽。〔14:12〕解法是"proactive tag based steering"：控制器在任何流量到来前先配置各虚拟机的打标行为（良性置 1、可疑置 2），再据这些标签值配置交换机；交换机只需查表决定下一跳。〔14:47〕两点收益：建立过程是主动的、控制面与数据面之间无实时交互；且交换机规则数与下一跳虚拟机数成正比而非与流数成正比，"The combination of these two ideas of proactiveness and per VM tagging makes the orchestration scalable"〔15:01〕。〔15:19〕第三个问题是攻击预测——"any real system has non-zero lag"，天真用历史外推（前三个周期都是 syn flood 就猜下一个也是、体量取均值）会被聪明对手用完全不同的类型与体量破掉，"any simple prediction can be gained"〔16:31〕（正解 gamed）。〔16:34〕先定义 regret 衡量相对事后最优静态策略的差距作为评测基线，再借"follow the perturbed leader"框架设计在线自适应算法：只用过去数据不够，还须掺入随机噪声分量，使攻击者无法确定性地打垮系统。〔17:32〕三块拼起来：用在线自适应算法由历史数据预测攻击场景，喂给分层且快速的资源管理（兼用防御策略决定 VM 数量、位置、类型与路由策略），最后由可扩展的标签式编排起 VM Snort、IP tables、Bro 等开源工具，控制面与数据面之间用 OpenFlow 加上自研"flow tags"接口以支撑前述可扩展性；全部跑在 KVM 上，在校园里十三节点集群评测，物理网络扛不住的大攻击以仿真补足。〔20:40〕评测回答三问。〔21:11〕响应速度：分层资源管理"just takes a few milliseconds as opposed to hours"〔21:11〕，最优性损失"less than one percent"；端到端各攻击类型都在第十秒发起，Bohatei"can restore the throughput of legitimate traffic in about a minute"〔22:00〕。〔22:02〕可扩展性：与逐流规则的天真 SDN 相比，按虚拟机打标"cuts the number of forwarding rules uh by three to four orders of magnitude"〔22:26〕，主动建立相对反应式建立也把规则下发时间压小三到四个数量级。〔22:41〕抗动态对抗：在不同对抗者模型（如 Rand Ingress 每期随机换入网口但不换类型）下对比两种朴素预测与本算法，"Bohate's online adaptation algorithm - 〔USENIX Security '23（推测）〕讲者 Moshe（耶路撒冷希伯来大学）开场点题：本研究全部围绕用户在浏览网页时如何被追踪展开。终极目标是跨网站、跨网络、跨浏览器与隐私模式识别同一用户，用途既有害（实时定向营销、监控）也有益（欺诈检测、各类防护），中间地带亦存。〔00:52〕典型入口是常以 JavaScript 编写的追踪脚本，在用户浏览器上执行追踪逻辑并最终取得一个可用于识别用户的设备 ID。〔01:11〕本工作分析的是设备生成的 TCP 源端口，由于源端口无法经标准 JavaScript API 直接读取，需借追踪服务器检查；攻击总流程是追踪脚本发起一系列 TCP 连接，部分到达追踪服务器、部分不会，这由追踪逻辑决定，服务器则检查收到的 SYN、提取源端口并喂给状态机，最终吐出一个设备 ID。〔02:20〕提取出的设备 ID 基于内核数据，在 Linux 上多达 128 位，跨网站、网络、浏览器、隐私模式乃至 Linux 容器持久；但攻击依赖能看到设备生成的源端口，故无法追踪 Tor 用户，也无法追踪经带端口重写策略 NAT 路由上网的用户。〔03:06〕机制铺垫：TCP 连接由四元组标识（源 IP、源端口、目的 IP、目的端口），客户端只指定后两项，源端口由操作系统的源端口选择算法按源 IP、目的 IP、目的端口与内部状态算出。〔03:40〕源端口有两条要求：安全上应不可预测以抵御盲 TCP 攻击与数据注入攻击；功能上应很少复用，否则会引起连接建立延迟或失败。〔04:17〕RFC 6566 定义了五种端口选择算法，各有取舍，本攻击针对其中之一——"the double hash post selection algorithm"〔04:24〕（正解 double hash post-selection），自 Linux 内核 5.12 起实现。〔04:35〕算法状态是一张长度为 t 的 32 位整数表，随机初始化，可视作计数器数组；另有开机时随机初始化的两个密钥 K1 与 K2，以及用它们作密钥的两个散列函数 f 与 g。〔05:04〕给定三元组，先用 g 与 k2 散列出表的索引选定一个计数器；再用 f、K1 与三元组算出 32 位伪随机偏移量，这正是不可预测性的来源；然后取表中计数值加偏移、做模运算保证落在合法端口区间；最后把计数器加一。〔06:15〕该算法在不可预测性与低复用率之间取得合理折中，却不提供用户隐私，讲者识别出三个可叠加成严重问题的隐患：其一状态被共享——跨网络接口、网络协议（IPv4 与 IPv6）与网络命名空间共享；其二表长度偏小——RFC 建议长度为 10，而 Linux 用 256，"which is small enough"〔07:02〕，使两个互不相干的连接可能用到同一计数器；其三状态确定性变化——计数器永远只加一。〔07:13〕于是讲者转向把三者合成一项强大的设备追踪技术。（YouTube EPYWc-uXrTl3s，[8-433]，L1）
