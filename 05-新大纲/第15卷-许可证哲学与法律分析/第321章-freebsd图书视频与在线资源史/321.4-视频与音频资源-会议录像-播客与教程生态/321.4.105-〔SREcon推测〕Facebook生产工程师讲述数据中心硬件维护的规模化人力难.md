- 〔FAST（推测）〕Technion 与 Western Digital Research 合作论文 ZNSwap 研究 SSD 上的 swap 性能异常。随机写内存填充 swap 设备时，利用率仅 20% 带宽就掉到一半以下，根因是 SSD 与操作系统之间的知识鸿沟：SSD 不知哪些 swap 数据已被主机作废，垃圾回收做了无谓拷贝推高写放大；现有 Trim 过粗且受主机与设备命令处理速率限制，且 GC 影响整盘、破坏 cgroup 间的性能隔离（只写的 cgroup 拖垮只读 cgroup）。（YouTube EPG_WVGSeBcjY，[13-525]，L1）
- 〔FAST（推测）〕ZNSwap 借助 ZNS（zoned namespace）把 GC 收归主机侧并按介质特性重设计交换子系统。核心组件包括 zone append 写路径、策略管理器（决定目标 zone 并调度主机侧 ZNGC）、zone 分配器与 IO 管理器，ZNGC 利用 SSD 每页元数据区存的反向映射（VMA 指针与索引）在一次 IO 内取回数据并完成页表更新。在 Ubuntu 20.04、内核 5.12、512GB 内存的实验中，50% 利用率下吞吐为传统 SSD 的 2 倍、写放大减半，ZNGC 单核开销仅 0.3%（最高 15%，低于细粒度 Trim 的 32%）；跑 Memcached（Facebook CTC 负载）时 10% 利用率下 p99 延迟低 10 倍，隔离机制还能把 GC 带宽记账到引发 GC 的 cgroup。（YouTube EPG_WVGSeBcjY，[525-1176]，L1）

- 〔EuroBSDCon（推测）〕两套软件部署系统（AFS 感知与不感知）的对比与重构经验。AFS 不感知系统按 SDLC 同步发布约 300 个包（每个 6+ 版本），大卷可变且多包混居，需小心避免不一致的 release；AFS 感知系统作为战略选择支持多 SDLC，38.4 万个活跃包发布到 10 万+ 主机，每个包版本独占不可变卷、路径永不改变。因 OpenAFS 与旧 Auristor 客户端要求同卷两次 release 间隔 10 分钟且需三副本容灾，重构采用每包版本独立卷加 path volume 挂载点，进而用 AuristorFS 的 MagicMount 把 AFS 当对象存储（/afs/.at mount 形式）彻底消除 path volume 与 release 顺序问题，结果 50% 的包交付 1 分钟内完成（此前约 3 分钟）、90% 在 4 分钟内（此前 13 分钟），MagicMount 还暴露出 ../../ 路径查找反模式导致访问量暴涨 500%（转写至此截断）。（YouTube EPGa4M3xZNQoE，[597-1194]，L1）
- 〔会议不详〕主讲人 Sophia 介绍 Smart Cookie——一种对抗大规模 SYN 洪水攻击的分工式 split proxy 防御。2024 年 SYN 洪水仍是第二大 DDoS 手段；纯软件的 SYN cookie 把内存开销换成 CPU 密码学计算，反而成为新的攻击向量；纯硬件方案（可编程交换机代理）则因 header 翻译需维护每流状态而耗尽交换机内存（Jockey 规避内存却让所有良性流付出性能代价），且用 CRC 校验而非真密码学哈希生成 cookie，可被自适应攻击者用哈希碰撞绕过。（YouTube EPGbV1LZhpY8o，[9-394]，L1）

- 〔USENIX ATC（推测）〕Google 团队（Caroline Tice 等）讲述在 GCC 与 LLVM 中落地前向边控制流完整性（CFI）的实践。前向边（间接函数调用）攻击防御历来不如栈防御成熟有效，近期成功攻击多属此类；团队在 GCC 4.9 实现了 vtable verification（VTV，保证虚调用的 vtable 指针属于对象静态类的正确集合），在 LLVM 实现了间接函数调用检查器 IFCC（强制所有间接调用经由只读 jump table，新版还加入指针检查），并在 LLVM 的 UBSan 中提供帮助程序员找错的 IFSan 工具。两套机制对编译对象零限制，支持增量编译与动态库加载，已应用于 1500 万行 C++、5 万余源文件的 Chromium；VTV 为满足精确类层次信息采用编译期收集加运行时 libvtv 库合并（含动态库）的两段式设计，IFCC 则把函数地址改写为 jump table 项并用指针位掩码（表大小填充到 2^n）限制跳转目标。（YouTube EPGcTyaHANB2g，[10-539]，L1）
- 〔USENIX ATC（推测）〕安全性与性能评估及软件工程经验。安全性用 USENIX Security 提出的 AIR 指标改造出的 FARE（forward-edge AIR）度量：在 Chromium 上 VTV 达 95.2%、IFCC 达 99.8%（未覆盖部分多为静态链接 C 库中的间接调用）；运行时开销 0.6%-9.1%，多数情形 2%-5%。经验教训：CFI 与编译器深度集成可借后续优化 pass 提升性能，但必须审计编译器最终输出以防优化抵消安全代码；增量编译的信息不完整会导致假阳性（误判攻击而中止程序），IFCC 靠链接期优化器拿到全程序信息、VTV 靠运行时库解决；动态库与第三方插件造成混合验证代码，只能让程序员介入（IFCC 允许豁免指定函数，VTV 允许覆写默认失败函数做白名单与二次低精度验证）；Q&A 中回答了与 VirtualProtect 类敏感函数的关系，并表示把 Chrome 默认启用是最终目标。（YouTube EPGcTyaHANB2g，[546-1223]，L1）

- 〔会议不详〕CAM 的空间安全由可扩展分配器与编译器优化共同提供。借鉴 tcmalloc 用 span 保存基址与大小元数据、运行时计算指针边界；检查插在指针运算处而非解引用处（覆盖类型转换与指针计算两类指令），类型优化利用转换点的检查免除结构体内部索引的检查，合并优化让同一基址派生的多个指针共享一次边界获取。真实世界漏洞（NGS 基准）全部被检测并阻止，堆溢出亦全部拦截；SPEC CPU 2017 上几何平均开销 21%，优于 ASan、ESan 与 Memcheck，消融实验证明各优化均显著降低开销；系统基于 TCMalloc 与 LLVM 12 实现。（YouTube EPGg9OoYPJHas，[211-565]，L1）
- 〔会议不详〕主讲人 Radhika 提出 RC3 拥塞控制：用“最差服务质量”的低优先级突发流量缩短流完成时间（FCT）。拥塞控制有两个相互冲突的目标——填满管道获取高吞吐与不伤害其他流，传统方案用单一 slow start 机制同时追求两者，导致慢启动阶段浪费大量容量；RC3 用优先级解耦二者：正常 TCP 以高优先级照常爬坡，同时用低优先级（DSCP 字段）发送大量额外数据包填满网络空闲容量，随高优先级流量增长被自然节流。示例中 7 包小流从 3 个 RTT 缩短到 1 个 RTT；理论模型显示收益随流大小对数增长、随时延带宽积增大而提升，因而更适合大 RTT 的广域网。（YouTube EPGg_2SHpMRAo，[10-378]，L1）
- 〔会议不详〕RC3 的设计与评估细节。端主机并行运行两个控制循环：基本未改的 TCP 循环与从发送缓冲区尾部反向发送低优先级包的 RLP 循环，两股流量在接收端汇聚即提前完成；递归式多优先级（每级指数扩容，8 级可容纳 TB 级流）实现最大最小公平。ns3 仿真显示按流平均 FCT 降低 44%、按字节平均降低 74%，优于增大初始拥塞窗口（10 或 50，会伤及短流）与 RCP 显式速率协商方案。Linux 实现仅约 100 行额外代码、只改基础 TCP 文件，与 CUBIC/BBR 等任意拥塞控制算法兼容；配合 TSO/LRO 可把乱序低优先级包带来的每包处理开销降低近 50%。部署挑战包括部分部署（20% 路由器不支持优先级仍有收益）、中间盒与无线环境，未来 100 Gbps 数据中心预计平均可降 45%，仿真代码已开源在 GitHub。（YouTube EPGg_2SHpMRAo，[379-994]，L1）
- 〔SOSP（推测）〕香港大学 Songlin Huang（与导师 Shuo Chen 合作）介绍 Neutrino：通过可编程探针实现细粒度 GPU kernel 剖析。现有剖析工具要么内核侵入（拿不到设备内部数据）、要么硬件依赖（只能周期采样 PMU 计数器、不灵活）；Neutrino 的三个目标是细粒度（可计算被忽视的调度开销，torch.zeros 一行代码即含 20% 调度开销）、通用性（同时覆盖时间与值剖析）、可编程性（用 Python DSL 定制探针）。挑战在于 GPU kernel 对操作系统原子（没有 eBPF/ptrace 之类主机侧挂点）、缺乏可编程定时器中断、生态复杂；设计上选择 parallel assembly 作为探测层（生态最高公共层）、驱动作为运行时层（最低公共层），提出 eBPF 风格的探针模型（少量代码片段+checkpoint 指令匹配+结构化 map），直接把探针注入原始执行流，借助 SMT 线程顺序执行与独立寄存器组实现时间与资源隔离。（YouTube EPGh1joy8fXww，[18-445]，L1）
- 〔SOSP（推测）〕Neutrino 的实现与洞察。元数据以张量式布局按线程分 map，线程/块索引可推导而非存储且天然无锁；实现为命令行工具，hook driver 借助 ELF 同签名构造经 LD_PRELOAD 注入，probe engine 按探针定义改写 GPU 汇编，DSL 编译器以 Python 为前端、eBPF 风格 IR 为中间表示以复用成熟 eBPF 工具链。提出 DMAT 可视化（以物理时间为对齐锚点、颜色表示密度），对比 FlashAttention v1 与 memory-efficient attention 可见前者对 query 张量的访问被节省；小探针开销约 1.04%，某些情形甚至加速执行。案例研究发现共享 SM 配置的块有约 50% 的尾部效应（此前未知），进一步剖析发现每块先慢后快、跳变点恰与同 SM 上一块终止时刻对齐，揭示了 GPU 指令分发中隐含的 FIFO 式优先级调度；工具以 Python 包发布，支持 CUDA 与 AMD ROCm，兼容 JAX、PyTorch 及 Hugging Face 生态。（YouTube EPGh1joy8fXww，[445-911]，L1）
