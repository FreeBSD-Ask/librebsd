# 321.4.202 〔SOSP推测〕控制面／数据面分离的硬件支撑与量化收益他指出关键在于硬件IO虚拟

- 〔SOSP（推测）〕控制面／数据面分离的硬件支撑与量化收益。他指出关键在于硬件 I/O 虚拟化：SR-IOV 让网卡在 PCI 总线上创建各自拥有寄存器集、描述符队列与中断的虚拟副本；IOMMU 把设备访问限定在应用自己的页表上；Intel X520 的报文过滤器能按 IP 与端口把流量直接导向用户态虚拟网卡实例，RAID 卡则以逻辑盘表示应用被授权访问的盘区，网卡内置的速率限制与分组调度器则按管理员策略执行 I/O 调度。于是保护、多路复用与 I/O 调度三项下沉硬件，API 与全部 I/O 处理上移到应用内以库形式链接，形成零拷贝 I/O 栈，内核只留下全局命名、访问控制与资源限额三项且仅在配置阶段被低频调用；Redis 把对象名注册进内核 VFS，其他进程（如 Emacs）打开该配置文件的普通 open 系统调用会被内核通过 POSIX 兼容的间接 IPC 转发回 Redis。他把存储数据面的 API 换成持久化数据结构后，把 Redis 自身日志实现替换为自研实现（约 109 行改动、API 完全一致）：内存 GET 时延从 9 微秒降至 4 微秒（较 Linux 降 65%），持久化 SET 从 Linux ext4 上的 163 微秒降至 31 微秒（降 81%），吞吐分别为 GET 1.75 倍、SET 9 倍；Memcached 在单核即提升 1.8 倍并线性扩展至 4 核撞上网卡线速时的 3.1 倍，UDP echo 单核从 1 倍基准做到零拷贝接口的 3.4 倍、接近理论上限 3.6 倍。（YouTube EPWG3b2hE4i6U，[843-1671]，L1）
- 〔USENIX ATC（推测）〕面向备份存储的高性能细粒度去重框架。报告人自称 Xiang Zhou（音写存疑，论文作者或为 Xiang Zou）先对比两条数据缩减路线：LZ 系列与 deflate 一类通用压缩只在有限搜索范围内消除字符串级冗余、压缩比受限；去重面向超大文件，把数据流切成 chunk 并全局删除相同者，但粗粒度牺牲了压缩比；指纹去重除移除完全相同的 chunk 外，还通过对相似 chunk 做 delta 差分消除冗余，从而同时获得全局与流级的压缩能力。作者进一步指出去重引入三类局部性劣化：red path 中 base chunk 因用户修改而散布，且连续重复 chunk 常被合并压缩、使任何 chunk 的读取都必须以大单位进行，个别场景为取一个 base chunk 要读整个 container；restore 时同时存在 backup 直接引用 chunk、delta chunk 间接引用 base chunk 两类依赖关系，加剧碎片化；以及因 delta 与 base 的依赖，同一 container 会被反复访问。（YouTube EPWIO3Fn9zoaA，[13-476]，L1）
- 〔USENIX ATC（推测）〕MeGA 的三项技术与评测。选择性 delta 编码把若干 chunk 合成一个段并统计每个 container 在段内作为 base 的次数，低于阈值的视为 base 稀疏 container 并跳过其上 base 的编码，从而避免低效读取、加速去重工作流；delta-friendly 数据布局综合两类引用关系定义某个备份的必要 chunk，按 chunk 生命周期分类组织数据，使任意备份的 restore 所需 chunk 紧凑分布且无未使用 chunk 混入；always-forward-reference 遍历保证 delta chunk 总在其 base 之前出现，配合把已解码 chunk 预写到待恢复流（或改写入更小的缓存），显著避免反复访问 container。评测覆盖三类帧级与两类 chunk 级去重方案、四类备份数据集（网站快照、开源代码项目、虚拟机镜像与合成数据），MeGA 的备份速度最高达 greedy 的 34 倍、恢复速度最高达 105 倍，同时保留了细粒度去重的压缩比优势，选择性编码带来的压缩比损失除合成数据外都有限。（YouTube EPWIO3Fn9zoaA，[525-1041]，L1）
- 〔会议不详〕软件包处理的资源争用其实可预测。报告人未报名称，先说明可编程网络的诉求与软态方案的优势：把全部包处理放在商用服务器上带来熟悉的编程环境与 PC 生态的规模经济，但网络运营商讨厌它的性能不可预测，根因是同一盒子内多个处理流共享缓存、内存控制器与总线而发生难以预测的争用；已有研究只在所有包都经历同一种处理（如纯 IP 转发或某种加密）的受限设置下做到了高性能，而作者要的是一个支持多类应用与多类客户、且高性能可预测的系统。作者在商用 Intel Xeon（双路 Westmere、每路六核共享 L3、内存控制器与互连总线）上基于 Linux 与 SMP Click 搭建系统，配置规则是一核一应用以减少强制缓存缺失、NUMA 感知地分配内存，从而把系统划分为两个争用域；五个真实应用（带真实规模路由表的 IP 转发、NetFlow 式监控、冗余消除、小防火墙、VPN 加密）加一个可调 CPU 运算量与随机读数的合成应用，实测监控应用与五个冗余消除竞争者同跑时吞吐下降 27%、与五个防火墙竞争者同跑时下降 10%，并证明主导争用因素是缓存而非内存控制器——监控应用同时争两者时下降近 40%，只争缓存 32%，只争内存控制器仅 6%。（YouTube EPWIQNTJoJxo0，[6-886]，L1）
- 〔会议不详〕以缓存引用速率做简单而准确的预测。作者用一张图走查预测过程：把各竞争应用单独运行时的每秒缓存引用数测出并求和（示例为一亿次），在目标应用的下降曲线上取对应竖线的值即为预测值。可能造成偏差的假设有两个：一是假设真实竞争者与产生同样引用率的合成竞争者影响相同（由第一条观察支持），二是假设竞争者仍按单独运行时的速率工作；由于敏感应用的下降曲线在越过某点后增长缓慢，第二个假设引入的误差很小——实测各场景误差均小于 3%，最大偏差出现在以 IP 或监控为竞争者的场景，因为这两个应用对争用敏感、实际引用率会下降，从而造成高估。作者进一步解释两条观察为何对任意现代系统成立：竞争者访问的内存总量远超缓存容量，使缓存访问近似均匀（任何有意义的包处理应用都要访问数 MB 数据，而每核只有约两三 MB 共享缓存，且缓存再大会增加访问时延）；以及竞争引用增加时首先驱逐本应用数据、随后也驱逐竞争者自己的数据，这一机制可用简单的概率分析说明。结论是仅用简单技术就能构建性能可预测、且支持多类应用与多类客户的包处理平台，复杂作业放置在该语境下并不值得投入。（YouTube EPWIQNTJoJxo0，[931-1290]，L1）
- 〔会议不详〕用一个 TCP 互补机制解决数据中心的多项 TCP 顽疾。清华大学的 Peng Cheng 以厨房切菜需要多元工具、却总记不清工具位置的比喻说明现有 TCP 修复手段难以组合，然后逐问题拆解：TCP incast 方面 DCTCP 与 STCP 难以支撑 mapreduce 场景的大规模 sender，作者实验发现即使把 RTO 调小仍存在吞吐悬崖，原因是集中式丢包引发大量超时，因此避免超时是关键；TCP outcast 方面高丢包率下多瓶颈流吞吐显著偏低、与互联网上的结论一致，低丢包率下则不出现该现象，二者主因同样是超时；乱序方面固定阈值区分乱序与丢失会造成大量问题，数据中心的多冗余链路让多路径技术变得重要，而人们不敢做包级调度正是怕乱序；长查询完成时间方面约 12% 的实验流受影响、单个流可被拖到十五分钟，根因是重传时延中的检测时延。据此他提出 CP（cut payload）三步机制：交换机缓冲溢出时丢弃新包载荷、只转发首部，额外缓冲需求极小；接收端冻结该类包后取出起始序列号与包长，仿照 SACK 生成 PACK 选项、用块的左右边界标示缺失信息并保持与传统 SACK 兼容，随即立即发送以缩短检测时延；发送端解析 PACK 后检查接收状态，已收则忽略、未收则直接触发快重传与快恢复。作者把它实现在 NetFPGA 卡上，资源占用增加不到 2%、引入的额外时延约 56 纳秒，并公开了源码。（YouTube EPWJ5a9JWQdYA，[9-760]，L1）
- 〔会议不详〕CP 的评测与现场讨论。评测显示：在大量 sender 下 CP 能达到高吞吐并满足 mapreduce 需求；公平性方面低丢包率下可消除 TCP outcast、接近理论值，高丢包率下只能缓解而无法达到理论值（结果受所选拥塞控制机制影响）；乱序问题被解决并达到理论值；查询完成时间在第 99 百分位上约下降 40%，而在十倍流量场景下效果反而更好，因为拥塞与丢包越多 CP 的收益越大。作者强调 CP 是与 DCTCP 等 TCP 协议兼容的互补机制、已开源（论文还讨论了 ECN 标记等本次演讲未展开的部分）；问答中听众追问 PACK 是否必需、交换机缓冲是否按包而非按字节组织（作者称其实现中仅需约 2 KB 额外缓冲）、CP 流与纯 TCP 流混合是否会造成不公平（作者承认未做混合实验、也不能确定），以及由交换机直接回送包头作为反馈的方案对比（作者认为那更接近 QCN、并非 TCP 语义，且会引入更多不公平）。（YouTube EPWJ5a9JWQdYA，[782-1560]，L1）
- 〔USENIX LISA（推测）〕ntopng：第二代 Web 化实时流量分析器。报告人未报名称（ntop 团队），先回顾 1998 年诞生的 ntop——它当时已相当超前：Web 化、无需特殊操作系统或 X11 图形库，结构是抓包、分析器与 Web GUI 三层并用 C 编写；如今它已过时，于是团队决定彻底重写。重写动机是当下网络侧工具多聚焦告警、设备管理与用户，而真正分析流量的工具太少；ntopng 全部改用 C++，Web GUI 采用 HTML5 并通过 AJAX/JSON 拉取数据、界面逻辑写在 Lua 中，从而在引擎与展示之间形成清晰 API；引擎以网络设备为最小单元并支持多设备并行采集，官方宣称在现代服务器上单机单 CPU 即可处理 10 Gbps 的平均尺寸流量。引擎内 flow（同源同目的 IP、源目端口与协议相同）与 host 两级抽象全部常驻内存，因此带生命周期管理：不活跃的 host 与已结束的 flow 会被移出内存存入 Redis 缓存，采集恢复时不必从零开始统计。（YouTube EPWJfFXdBOPao，[9-318]，L1）
- 〔USENIX LISA（推测）〕ntopng 的开放扩展与工程化。作者强调流量分析不能只看协议、端口与 IP，于是为摆脱需签 NDA、收费昂贵的商业 DPI 库，团队自研开源深度包检测库以提取 URL、DNS 等元数据，并支持协议随时扩充与按国家（如意大利）定制扩展，还能在 Web 界面标注流量是安全还是不安全；ntopng 可作为采集器接收 sFlow 与 NetFlow，但改用 JSON 而非旧式 NetFlow 格式以便对接 Elasticsearch 等现代 NoSQL 或云端；结合 Linux 内核模块 cSD 可把流量关联到具体进程及其内存、I/O 与 CPU 占用，同时支持 Docker 与 OpenStack 部署。作者还宣布正与合作方推进双网口、即插即用的廉价设备与众筹计划，软件以 GPL3 许可发布、可从 ntop.org 获取并运行在 ARM、Intel、Mac 与 Windows 上；问答中他说明 JSON 是模块化设计的一部分、可组成层级化的 ntop 上报结构，而 NetFlow 到 JSON 的转换由另一个开源探针 nprobe 完成。（YouTube EPWJfFXdBOPao，[320-625]，L1）
- 〔USENIX HotEdge（推测）〕边缘计算硬件加速器的低成本选型框架 HARE。Vanderbilt 大学的 Xingyu Zhou（合著者 Robert Canady、Shunxing Bao，导师 Aniruddha Gokhale，均隶属 DOC-VU 组；转写中的 Robert Kennedy、Chunxing Bao、Andy Gong 系音写漂移）先说明为何边缘需要加速：算力负担上升、来自多种传感器的异构数据（尤其多路图像与视频）以及功耗与体积等物理约束；加速路径从更强的 CPU、GPU 到过去三十年的 FPGA、再到专用 ASIC。作者指出既有评测与基准选择研究要么只关注单一设备类型、要么下沉到电路设计层，导致加速器的适用性仍不清楚；于是以时延、功耗与商用成本三项最实用的指标，把加速策略拆成两问——选什么设备跑什么任务，以及放在拓扑何处、部署多久，并在满足时延约束的前提下最小化硬件成本与长期电费之和，选取 ResNet-50 分类与 Tiny YOLO 车辆检测两类深度学习任务建模。（YouTube EPWOm1e1Jl3vk，[7-342]，L1）
- 〔USENIX HotEdge（推测）〕HARE 的评估流程与结论。工作流先在真实设备上跑通并测量时延与功耗轨迹、再把轨迹代入系统级成本评估，从而把评估从单设备扩展到整体系统；作者以云—雾—边缘三层拓扑建模（底层 edge 节点直连摄像头传感器），设定四组摄像头、每组至少两台处理正确才满足可靠性目标的约束，用 WiFi 量级带宽近似 edge 到 fog、fog 到 cloud 的推理时延，按二十四个月的部署周期估算不同硬件在两项任务上的总成本。结论是通用 CPU 综合最不经济且性能最差、长期部署中功耗是决定性因素、FPGA 与嵌入式 GPU 潜力最大，但 FPGA 使用门槛很高、专用器件虽然即插即用却算力有限；作者承认这只是初步工作，目前只考虑单一设备类型与单一任务、假设理想调度与设备并行，未考虑设备间与通信干扰。（YouTube EPWOm1e1Jl3vk，[351-690]，L1）
- 〔会议不详〕面向智能手机体验的宿主 SSD 映射表统一管理。首尔国立大学的 Yuna Kim 指出智能手机最核心的性能指标是用户体验，而任何毫秒级的用户感知时延差异都会显著影响体验；存储 I/O 是启动、切换或加载应用时的主要贡献者之一，其中逻辑到物理（L2P）地址转换尤为关键——NAND 闪存每次请求都必须查映射表，设备侧 SRAM 未命中时多一次 Flash 读取使时延翻倍，作者实测最坏情况下 L2P 缓存未命中占整个用户感知时延约三分之一。随着存储容量增长，映射表按约 0.1% 容量增长（1 TB 设备约需 1 GB），而设备侧 SRAM 因成本约束仅约 512 KB 到 1 MB，未命中概率随之升高；Host Performance Booster（HPB）借宿主 DRAM 扩展 L2P 缓存以消除额外 Flash 读取，但现有以存储为中心、对体验盲目（UX-oblivious）的管理带来两类缺陷：HPB 与设备 SRAM 均未命中的 critical miss 依然存在，且 HPB 占用宿主内存会引发内存压力并触发 Android LMKD 杀死用户应用。作者分析发现现有 HPB 只按引用计数超过预设阈值（例如被引用超过五次）的条目做缓存，这一策略与前台、后台应用优先级无关。（YouTube EPWUh3AaSdKcQ，[14-599]，L1）
