# 321.4.193 〔USENIXATC推测〕DUA让数据中心资源对FPGA通用可访问主讲人RenX

- 〔USENIX ATC（推测）〕DUA：让数据中心资源对 FPGA 通用可访问。主讲人 Ren Xu（来自 Microsoft，原文亦转写为 Ran Xu）指出 FPGA 已广泛部署于 Microsoft、Amazon 等主流云服务商，用于加速计算、网络与存储，而这些应用需要访问不同类型的资源——CPU、内存、其他 FPGA、GPU 与 SSD；以 Microsoft 数据中心中用于加速 AI 应用的一块 FPGA 板为例，板载 DDR4 面向内存密集应用、PCIe Gen3 端口访问宿主机 CPU 与主存及其他设备、QSFP 端口连接数据中心网络，由于通信逻辑高度可复用，FPGA 厂商通常按物理接口各提供逐代变化的 IP 核，数据中心运营方再在数据链路层之上实现 DCP 等传输协议；但对比互联网的全栈架构，最关键的一层缺失，导致 FPGA 无法直接访问数据中心的所有资源。现有架构存在四类问题：一是接口复杂——不同栈的接口差异明显，而硬件描述语言每一行开发成本至少是软件语言的十倍、开发与验证及性能调优常需数周，因而难开发也难跨平台移植；二是命名空间割裂——DRAM、SSD、GPU 等只出现在宿主机本地命名空间中、远端 FPGA 难以使用，例如 FPGA 加速的大规模大数据分析要靠 CPU 协调数据传输从而限制性能收益；三是缺乏通用复用——共享同一通信栈的 FPGA 应用实际是在栈的电路里被复用的、程序员需自行实现复用/解复用器，且物理接口层面没有通用复用方案，导致不改底层栈就无法同时访问本机 DRAM 与 SSD；四是安全问题——FPGA 经 PCIe 挂载可经 DMA 直接访问 CPU 主存从而控制服务器，外部攻击者也可注入恶意消息攻击 FPGA 应用。（YouTube EPVRTGjhG-bE4，[10.6-360.2]，L1）
- 〔USENIX ATC（推测）〕DUA 的设计、架构与评测。示例中应用一要向远端服务器 FPGA 上的应用二发消息，DUA 发现本地 FPGA 板没有以太网口便经 PCIe 转发给同服务器的另一块 FPGA、再由以太网送达 FPGA3 与最终应用，由此可见 DUA 是数据中心中让 FPGA 访问所有资源的 IP 层——它以路由器的身份连接各栈与应用、构建抽象覆盖网络，复用现有通信栈与既有寻址路由设计因而简单易部署，四个关键特性是任意应用可直接访问数据中心内任意资源且无需代理应用、路由完全绕过 CPU 因而时延极低、为异构端点提供统一的类 BSD socket 接口以降低 FPGA 应用与通信栈的开发成本、为应用与通信栈提供通道复用使程序员无需再关心复用器实现，以及抵御外部恶意流量的 DDoS 防护并保护宿主机乃至整个数据中心网络免受异常应用与栈的影响。架构上因 FPGA 不适合实现复杂控制逻辑而把数据面与控制面分离：数据面作为路由器存在于所有 FPGA 中，控制面主逻辑放在 CPU 侧（FPGA 控制代理只监控与更新本地状态）、每台服务器由一个 CPU 控制代理负责本机控制，并借分层地址格式（服务器 IP 为第一级、由 CPU 控制代理管理第二级本地地址）与“各自只算本地路由、跨服务器由双方 CPU 控制代理结合数据中心路由得出端到端路径”的设计完全避免全局同步；数据面含 overlay 与 underlay 两部分——overlay 以统一接口连接所有应用与栈并提供路由、路由表缓存于数据面使数据传输完全绕过 CPU 以避免查表争用、每个连接器只缓存自己活跃连接因而表总规模很小、并作为栈转换器在既有接口之间转换以达到线速与近零开销，underlay 则解决物理接口复用并提供安全检查。评测把两块没有以太网口的 FPGA 分置于两台服务器、由 DUA 经 PCIe 借道带以太网口的 FPGA 建立端到端连接，整次往返经 4 次 PCIe、2 次以太网、4 次 DUA，DUA 仅增加不足 200 纳秒时延（不足总时延的 5%）、每次转发不足 50 纳秒，典型四端口实现只占用约 10% 的 FPGA 逻辑资源、预计在下一代 FPGA 上可再降两到三倍；应用上把 Deep Crossing（面向 Web 规模应用与数据集的深度神经网络、关键指标是时延）从单板扩展到双板使并行度翻倍、只多写 26 行 OpenCL 代码调用 DUA 接口即把延迟降低约 50%，正则在应用网关与 IDS 中被广泛用于匹配编译加速、原本需 CPU 在 FPGA 间搬数据、借助 DUA 仅需改几十行代码即可直接传输、时延再减半、吞吐最高提升 3 倍，团队表示将很快开源该项目。（YouTube EPVRTGjhG-bE4，[360.4-919.3]，L1）
- 〔IMC（推测）〕DNS 查询失败的大规模测量研究。主讲人来自中科院计算技术研究所，本工作与导师李振宇教授（同为中科院计算所）及伦敦玛丽女王大学 Gareth Tyson 教授合作；DNS 对互联网级分布式系统至关重要、几乎所有联网应用都依赖它，2016 年 DNS 运营商 Dyn 的基础设施遭受大规模 DDoS 攻击时，Netflix、Visa 等热门域名的查询开始失败、即便服务本身在线也无法访问，因此研究专门关注由 DNS 基础设施（而非域名拼写错误等 NXDOMAIN 情形）引起的失败。数据集来自三家中国 ISP 的深包检测（DPI）设备对递归解析器返回给终端用户的响应做被动日志采集，共 14 个样本（2018 年 2 月每隔一天采集、每样本为三家 ISP 全部 DPI 设备的 10 分钟日志，合计约 31 亿条），每条含匿名化终端用户 IP、BGP 前缀、ASN、递归解析器 IP、查询类型、全部资源记录、秒级时间戳，以及解析器与终端原始 IP 是否共享 /24 前缀的指示位（用于识别 ISP 解析器），CNAME 类响应会跟踪重定向到最终记录，且终端用户与递归解析器地址中均未出现 IPv6。由于数据集不含响应码、无法直接区分无错误与 NXDOMAIN，团队采用启发式过滤——先检查请求域名是否含有效应答（如 A 查询的响应中至少有一条 qname 的 A 记录），只抽取占比 99.5% 的四类最常见查询，再剔除在整个数据集中从未成功过的域名，最终保留约 28 亿条日志。（YouTube EPVT0EOhu6YQc，[9.6-633.4]，L1）
- 〔IMC（推测）〕失败模式、公共解析器差异与恶意新 gTLD 域名。结果显示 A 查询占绝大多数且成功率最高、其他查询类型更低，出乎意料地有接近三分之二的 AAAA 查询失败；按域名看（过滤请求数少于 100 的域名），约 7% 的域名 A 查询成功率低于 50%，而 AAAA 查询约有 60% 的域名从未成功解析，提示 DNS 对 IPv6 的支持存在基础设施性限制；失败高度集中于少数域名（按失败率取前 5 万名域名并用 Webroot BrightCloud API 分类，11 个类别中 8 个的失败有超过 80% 归因于前三个二级域名、多数为前一个），代理、色情、弹窗类域名失败尤其集中。按解析器统计成功率（剔除服务查询数少于 100 者）：多数解析器处理 A 查询成功率很高、约一半几乎无失败，但 60% 的解析器处理 AAAA 查询的成功率不到 20%、约 20% 从未成功解析过 AAAA 查询，可能在观测期内尚不具备 IPv6 能力；对若干热门中国公共解析器以及 Google DNS、OpenDNS（用官网公布的 IP 识别并与 ISP 解析器对比）发现，Google DNS 虽在中国知名度不高却是使用量最大的公共 DNS，而腾讯的 DNSPod 几乎全部成功、OpenDNS 仅 86.3%，差异原因之一是被查询模式不同（为每个解析器构造以其处理过的域名与查询量组成的向量并计算余弦相似度，结果显示各解析器之间相似度出乎意料地低，其中由多家中国运营商提供的 114 DNS 与属于阿里的 Ali DNS 最不像其他解析器——Ali DNS 处理大量 taobao.com 与 alipay.com 请求），另一原因是基础设施差异（比较同一域名在不同解析器上的成功率差值得出：由 114 DNS 与 ISP 解析器解析的域名更易失败，而 DNSPod 与奇虎 360 的 360 DNS 成功率更高）。顶级域方面，新通用顶级域（new gTLD）与国际化域名（IDN）成功率明显更低（如 .lol 仅约 20%、而 .com 约 83%）；进一步考察成功解析的 A 记录查询的托管网络段发现多数域名映射到相对较少的网段前缀，而若干激增点表明存在承载大量 new gTLD 域名或 IDN 的 /24 子网（由大型托管商造成）且这些头部 AS 的解析成功率极低，最极端情形是一个 AS 上有 19.5 万个域名对应 20.1 万次查询全部映射为 NXDOMAIN（这些域名在 2019 年 9 月 26 日仍可解析）且查询数接近完整域名数，说明这些域名生命周期极短、变化频繁；借 VirusTotal 与奇虎 360 两份黑名单核验（任一黑名单判定即标为恶意，因规模所限只检查二级域名）发现相当比例的新 gTLD 域名属恶意，其影响分布显示除托管在第三个子网的恶意二级域名足迹遍及几十个网络外，其余只影响一两个网络。由此提出两类可构建系统：一是主动测量系统，用于判断哪些解析器支持 AAAA 查询、按不同解析器测量域名成功率以帮助用户选择、并从本地化角度比较（统计各解析器在本地可服务时把用户引向本 AS 服务器的比例，该比例在解析器间差异显著），对内容发布方评估 IPv6 CDN 服务、ISP 估算 IPv6 流量与终端用户选择解析器均有价值；二是恶意 new gTLD 域名检测系统——由于恶意 new gTLD 的二级域名往往很短（传统顶级域下恶意域名通常较长，因为注册短域名对攻击者成本太高，而注册短 new gTLD 名称很容易），仅靠域名名特征不易检测，建议改用 DNS 查询频率、单个二级域名的完整域名数量、解析到的 IP 地址及其对应 ASN 等特征；主要贡献则是在约 30 亿条查询日志上证实失败查询确实普遍、失败高度集中于少数域名，尽管 IPv6 近年被大力推广但绝大多数查询仍是 A 记录且 AAAA 仅约三分之一成功、IPv6 远未就绪，终端用户也应关注不同解析器在查询失败与映射准确性上的差异。（YouTube EPVT0EOhu6YQc，[633.6-1206.1]，L1）
- 〔USENIX Security（推测）〕Shroud：用私有虚拟磁盘向数据中心服务方隐藏访问模式。这项工作与 Brian Parno、James Mickens、Mariana Raykova、Josh Shavit 合作，主讲人自述是 Microsoft 员工但强调该工作“离实践还很远”、性能尚不足以部署到 Bing Maps 或 Facebook、Flickr、Twitter 之类场景；动机是让用户访问数据中心数据时不向服务提供方泄露私有信息——无论出于对 Microsoft 或 Google 的不信任，还是担心被黑客入侵、员工被收买或监守自盗、乃至政府依传票索取公民私有数据。加密并不充分：戴维加密邮件后仍必须明文给出收件人地址以便投递，服务方由此得知谁在通信及通信时间，已有研究显示即便邮件加密、查询加密，仍可推断出多达 80% 的实际邮件内容，社交网络能学出好友关系、微博与博客站点能学出你属于哪些社区与兴趣、地图与推荐服务能学出你此刻的大致位置。Shroud 要隐藏的全部是这类访问模式信息，手段是一块私有虚拟磁盘——不仅隐藏块内容、也隐藏块的地址：戴维把加密邮件追加到保拉收件箱所用的 85 号块末尾、保拉取信时取 85 号块，由于 85 这个编号对攻击者不可见，两次访问根本无法关联；该方案假设一个很强但有限的攻击者（控制所有存储、能看到全部流量，却无法破解密码学、也无法窥视或篡改某些可信硬件），而满足此需求的 ORAM 极其缓慢——数据中心级负载（17 级缩放下约 300 亿张地图切片、数十亿条推文与数十亿张照片）下单个地图切片平均需两分钟、每万次请求要一个半小时、每千万次请求整个数据中心基本要离线一周去搬数据，且置换数据要消耗大量 WAN 带宽、用户还须持续跟踪当前置换，故 Shroud 借鉴文献把置换与密钥移入位于数据中心内、可防篡改防窥视的可信协处理器（可用 TPM 加安全执行基础设施，也可用防篡改智能卡、防篡改 FPGA 或整机防篡改的硬件安全模块等独立组件），让它在高带宽低延迟的数据中心网络上与服务器执行 ORAM，用户只需经安全通道向它提交请求。（YouTube EPVTZckIp1yzY，[9.7-773.5]，L1）
