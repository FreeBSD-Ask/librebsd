# 321.4.36 〔会议不详〕Gekko对虚拟化云内IO争用无感的存储系统主讲人JiayongCo

- 〔会议不详〕Gekko：对虚拟化云内 I/O 争用无感的存储系统。主讲人 Jiayong（Cornell University，与 Microsoft Research 的 Mahesh Balakrishnan、Google 的 Tudor Marian 及导师 Hakim Weatherspoon 合作）指出物理磁盘虚拟化很差：4 盘 RAID0 上并发 VM 顺序写使吞吐跌破一半，任一 VM 发随机 I/O 即把整体吞吐打到底；I/O 调度与负载放置都有局限，日志结构文件系统虽把多路写合成单流，但垃圾回收是其阿喀琉斯之踵（RAID0+log 上 GC 一触发应用吞吐掉到 1/10 以下）；设计原理是与其多盘在争用下互相寻道不如单盘顺序访问——链式日志（chain logging）逐盘顺序写日志、把 log tail 与 body 分离（取壁虎断尾逃生之意），GC 读写与写请求落在不同磁盘，tail 盘用 RAM+廉价 MLC flash 分层缓存挡住读请求，body 内再放小 flash 缓解读-读争用。（YouTube EP4v_2uyoQbDM，[9.7-853.7]，L1）
- 〔会议不详〕Gekko 实现与评估。实现上内存维护逻辑到物理映射（每项仅 4 字节，支持 8TB 存储约需 8GB RAM），flash 上保存严格顺序写入的物理到逻辑逆映射以持久化并利于闪存寿命；提供内核块设备与用户态模拟器两种实现，硬件为 600GB 10K RPM SATA 盘加 Intel MLC flash；评估显示 GC 场景下聚合吞吐约为 log+RAID0 的 3 倍、应用吞吐约 4 倍，MSR Cambridge/MS Enterprise 混合负载达 2-3 倍吞吐，7 盘 log+RAID0 仍不及 2 盘 Gekko（纯 RAID0 在随机负载下仅约 10MB/s），tail cache 读命中率至少 86%，加 2GB RAM 可使 SSD 寿命延长 2-8 倍；问答涉及 RAID5/6 小写问题、SSD 与加 RAM 的成本平衡、GC 碎片化，GC 读与写/GC 读争用仍属未来工作。（YouTube EP4v_2uyoQbDM，[854.7-1618.7]，L1）
- 〔会议不详〕RBFuse：安全使用不可信 U 盘的文件系统。主讲人 Ke（University of Pennsylvania，与上海交通大学的 Zhihao、Kemal 及导师 Sebastian 合作）指出 U 盘生态的默认信任原则：内核无法认证设备可信、设备可绕过内核经 DMA 访问内存、驱动易有缺陷且设备可伪装（如 rubber ducky），既有包过滤（Seng、USB Filter）、设备认证（ProveUSB）、沙箱方案分别败于动态载荷、需新硬件/改内核与漏报；提出 RBFuse 不经主机 USB 栈访问 U 盘：把主控内存空间重映射给虚拟机、把 flash 上的文件系统暴露为可挂载 VFS——VM 内跑 VFS server，主机侧 FUSE 式 VFS client（用户态守护进程+少量内核驱动）串行下发 getattr/mkdir 等请求；挑战包括元数据请求过多（读 1000 个文件要 3000 次 getattr）、读写分块，恶意盘与诚实盘并存时可窃取数据、篡改传输或以恶意响应崩溃主机，解析器不慎即被内存错误利用。（YouTube EP4yMei35HDI0，[9.6-387.8]，L1）
- 〔会议不详〕RBFuse 优化、评估与展望。优化包括初始化时预取并缓存全部文件元数据使 getattr 本地完成、读请求利用空间局部性预取整个文件与同目录小文件、写请求合并与批处理（延迟执行并按 U 盘剩余容量投机应答）；可选硬件适配器基于 BigBang Blackboard 开发板，对诚实盘的读写内容做类 TLS 端到端加密以防恶意盘窃听；解析器/序列化器由形式化验证的工具自动生成（转写 Arrow Parc）以规避内存错误；评估在 Ubuntu 16.04 主机/VM 上：单个 500MB 文件 RBFuse 写仅 2% 开销、读约 70%，加适配器后 3-10 倍开销；1000 个 16KB 小文件 RBFuse 为 2-4 倍开销，加适配器写反而超过基线、读约 8.8 倍；用 CrashMonkey 对 ext4 与 VFAT 做跨崩溃一致性测试，ext4 全部通过，VFAT 上创建空文件后 fsync 不落盘（与 Hydra 的观点一致）；未来工作为对恶意文件系统响应做服务端模糊测试与对 VFS 接口做形式化验证。（YouTube EP4yMei35HDI0，[389.5-945.6]，L1）
- 〔SREcon（推测）〕生产环境如何正确升级内核。主讲人 Ignat（Cloudflare Linux 工程师）列举不升级内核的代价：bug 不修复——5.15 分支 116 个每周 bug fix 版本中超半数含 100+ 个提交、约 20% 超 200 个、另有含 500 个修复的大版本；免费性能丢失——从 5.4 升 5.10 的 A/B 实验白得每台服务器约 4.5GB 内存节省（受益于 Meta 在内核内存管理上的改进）；变更增量随延迟加速累积（515.16 到 515.32 约 2196 个提交，延迟两倍风险约 2.48 倍）；安全上 90% 的 bug fix 版本至少修一个 CVE，Cloudflare 因 PCI DSS 合规要求高危补丁一个月内上线（Equifax 未及时修补 Apache 的前车之鉴）；并批判橡皮图章式审阅变更日志、把 CVE 是否可利用的问题问错对象（应问全职钻研利用链的攻击者，而非只想准点下班的 Linux 工程师）以及为一个月 soak 而放大风险等反模式。（YouTube EP4zrcHnavdfA，[8.1-993.0]，L1）
- 〔SREcon（推测）〕内核版本与发布机制去魅及升级建议。内核部署因必须重启反而天然更安全：逐台排空流量、下线、重启、跑验收测试再回池，出问题可在第三台时按大红停止按钮，且重启流程复杂使坏代码无法像普通应用那样几分钟内蔓延全网（Cloudflare 曾有此教训）；版本号并非语义化版本——最右位只含 bug 与安全修复（从 stable 分支 cherry-pick，约每周三发布），主线每 9-10 周出一个 stable（2 周 merge window 加约 7 周修复期），最左位数字无意义（Linus 的手指玩笑）；LTS 版本支持至少两年；建议：不为内核单设变更流程、每周无争议地应用 bug fix 升级、以指标驱动金丝雀并压缩 soak 时间、评估不过来可留在长期分支但应提早试新、按业务负载理解并测试所用内核子系统、用自动化消除运维对内核升级的人为偏见。（YouTube EP4zrcHnavdfA，[994.1-2029.3]，L1）
- 〔SREcon（推测）〕NIHS 与 PagerDuty 的 dark debt 故事。PagerDuty 工程师先厘清术语：not invented here syndrome（维基百科定义为坚信自研更优、更安全、更快而重复造轮子）、dark debt（新术语，类比暗物质——创建时不可识别、以复杂系统故障的形式显现，与可通过重构偿还的技术债不同）；案例 Work Queue：2011 年 10 月约 20 人的 PagerDuty 决定自研分布式公平分区队列与任务调度器，底层用 Apache Cassandra，需求包括跨区域乃至跨云厂商故障的高可用、持久性、弹性伸缩、可像关系数据库一样查询、schema 灵活、可备份重建，以及跨多数据中心/多厂商加密公网上的同步复制（分布式系统的危险操作）；当年 Kafka 刚开源不成熟不适用，也考虑过 Apache Storm 变体与事件驱动框架，最终基于熟悉的 JVM 生态选型 Cassandra，2012 年上线的 v1 快速而好用。（YouTube EP52T4Y_LtD2g，[5.7-888.4]，L1）
- 〔SREcon（推测）〕Work Queue 的功能膨胀、衰亡与教训。队列陆续加上 host-based partitioning、fair partitioning（队列的队列）、基于时间的分桶等特性，内部服务出现寒武纪爆炸式采用，一个本应只做好一件事的软件变成五六件事都做不好的组件；同期 Kafka 社区成熟、SQS/Cloud Pub/Sub/Kinesis 稳定可用，而 Cassandra 0.8 到 1.12 后 API 迅速变化使 Work Queue 兼容性断裂、Thrift RPC 亦失宠，dark debt 以重大故障形式显现（postmortem 中反复出现 Cassandra）；教训：dark debt 是复杂性的产物，自研本身不等于 dark debt，但专用软件向其他领域扩散往往意味着 NIHS，而 NIHS 是 dark debt 的强烈信号，应对之法是主动评估既有自研方案、无强用例不造轮子、复杂与简洁之间永远选简洁；尾声：Work Queue 于 2016 年停止内部支持、2017 年起用户几乎清零，并以 Edsger Dijkstra 的名言“简洁是伟大的美德，但需要努力才能实现，而且复杂更好卖”作结。（YouTube EP52T4Y_LtD2g，[890.5-1702.9]，L1）
- 〔会议不详〕Smart Dedup：面向资源受限设备的去重优化。主讲人 Ruiyu Jin（Arizona State University Viso Lab，与同学 Qi Ruiyang、导师 Ming Zhao 教授合作）针对边缘/IoT 设备数据密集负载与受限存储（I/O 性能、容量、 endurance 受限），收集分析长达 6 个月的智能手机 I/O 追踪：日 I/O 量最高 16GB、日写量 2.8GB，整体重复率最高 47%；重复来源因设备而异（有的资源文件最多、有的临时文件最多），且 80% 以上的重复来自非整文件重复，故需跨文件与应用的系统级去重；设计包括内存前缀树指纹库（指纹按 12 位前缀成组索引以省内存）与共享索引的磁盘级指纹库、按组淘汰降低 I/O 开销、inline 与 out-of-line 混合去重（写路径立即消除重复写、后台彻底清重）、页缓存索引（PBN 到页的映射）避免重复读，以及按 CPU/磁盘利用率、剩余电量和负载重复度自适应调节去重速率。（YouTube EP54FoKCmclwg，[10.3-654.9]，L1）
- 〔会议不详〕Smart Dedup 评估与问答。原型实现于 ext4 与 F2FS，平台为 Nexus 5X 手机与 Raspberry Pi 3，对比块级去重方案 DMDedup（支持灵活元数据后端）与面向受限 FTL 层的 CFTL：25% 重复度时写加速 17%，FIO 混合负载下 CPU 开销仅 3.3%（对比 ext4 的 Mix1）、比 F2FS 省电 49%，全程只用 3.5MB 内存；真实追踪回放达最高 51% 写加速与 70% 写减少；自适应去重以 8% 重复率损失换来 14% 功耗下降；问答中说明：存储节省低于重复率是因这些写入以对已有数据的更新为主；多对一的 LBA 到 PBA 映射下文件系统分配启发式与 F2FS GC 仍在 LBA 层照常工作；自适应限速与基于连续块数的去重机制之间存在局部性权衡，非手机平台资源更多时预期表现更好。（YouTube EP54FoKCmclwg，[656.1-1180.7]，L1）
- 〔会议不详〕Alea BFT：简单而高性能的异步拜占庭容错协议。主讲人 Diogo（工作于里斯本 IST 与 INESC）回顾状态机复制与 BFT 历史：Lamport 在八十年代初提出并解决、Castro 与 Liskov 的 PBFT 是首个实用解，加密货币兴起（Bitcoin、Ethereum）驱动了可扩展 BFT 研究，代表有 Algorand、HotStuff、QBFT；面对 FLP 不可能定理，多数协议用部分同步加超时保活性（超时太小不断触发无法推进、太大易被单点崩溃拖垮性能），替代路线是随机化异步协议（Ben-Or 与 Bracha 传统，后有 Honey Badger 与 Dumbo 家族）；作者主张简洁是现实采用的关键（QBFT 虽未全面胜出仍被 Hyperledger Besu、Protocol Labs、Quorum 等采用），Alea BFT 从经典部分同步协议借回“每请求指定 leader”这一洞见：leader 轮转提议、副本只需按是否接受投票，广播与裁决两组件并行、以 N 个本地队列衔接。（YouTube EP54cDdLn2_ME，[16.1-471.4]，L1）
- 〔会议不详〕Alea BFT 细节、部署与性能。广播组件用可验证一致广播（validity、consistency、verifiability 三性质，verifiability 使正确副本可构造证明让未交付者交付），裁决用异步二值裁决（其 validity 保证拜占庭节点无法单独阻止推进，输出 1 时至少一个正确副本持有该交易并可靠恢复机制传播），广播与恢复对副本数线性、每轮裁决二次方、最坏 σ 轮，总复杂度 σ·n²；实现从 Java 研究原型到集成进 Mere 框架（Filecoin 子网的新共识层）、SSV Network 与 Obol 的分布式验证器技术（PoS 下质押与罚没（slashing）对单节点风险大、催生中心化，分布式验证器靠 SMR 保证多节点行为一致以免被罚没）；基准测试：对 Honey Badger 与 Dumbo 吞吐相当、延迟大幅下降（改用更简单的二值裁决并做优化），分布式验证器场景吞吐优于基线 QBFT，Mere 场景对 ISS+PBFT 在副本崩溃（150 秒处）时无需等超时、优雅降级。（YouTube EP54cDdLn2_ME，[471.4-906.1]，L1）
- 〔SREcon〕LinkedIn Traffic Shift：规模化避免灾难。SREcon 2017 上 LinkedIn production SRE 团队的 Michael 与 Anil 介绍其基础设施演进：2003 年上线、2010 年前单机房托管、2010 年建首个无备份数据中心、随后 active-passive、2013 年双活、2014 年三活、其后为 APAC 增长建第四个国际数据中心；至 2017 年为 3 个国内加 1 个国际共 4 个数据中心 active-active、全球 13 个 PoP、上千个 API 端点，服务 200 个国家的 4.67 亿成员；traffic shift 是应对服务降级、基础设施故障、人为误配置（推错配置打挂全站）乃至机房火灾的魔法药丸——把线上流量从故障机房整体迁走而用户几乎无感；机制上 ATS（开源的 Apache Traffic Server）读取加密签名的 LIDC cookie 决定转发，cookie 失效则询问 sticky routing 服务；该服务以 Hadoop 作业按成员地理位置与机房容量做分配（近似 key-value 存储：用户 ID 到主/备数据中心），每个机房划成 100 个在线/离线桶，实现低延迟、按需存数据与对机房 QPS 的精确容量控制。（YouTube EP55L1OO5Ka6k，[10.1-885.2]，L1）
- 〔SREcon〕Traffic Shift 架构、负载测试与经验。架构为前端 Web 应用加后端 worker 进程，以 Couchbase 作持久存储、经 Salt Stack 与机房通信，与 sticky routing 协同把机房或桶置为离线即可把流量重定向到健康机房（灾备场景：关掉 US East 与 APAC 后 100% 流量由两个机房承载）；load test 是计划性压测——每周 3 次在高峰时段执行，工具内置自动引擎监听告警并自动再平衡以避免灾难，负载测试期间服务问题享最高优先级 SLA；收益包括精确的容量规划、用生产流量验证服务容量与性能、发现仅在高压下浮现的性能 bug，以及对灾备的信心，去年上线的 kill switch 能在 10 分钟内排空 fabric 与 PoP 流量；要点是假设灾难必然发生、把灾备端到端自动化（由易错的 Python 脚本演进）、随微服务增长持续验证；问答补充：sticky routing 只管外部入站流量、跨机房数据同步要求实时（失步即视为事故）、决策由 ATS 插件在边缘做出而 API 跑在数据中心、各机房桶容量并不等价。（YouTube EP55L1OO5Ka6k，[885.4-1739.7]，L1）
