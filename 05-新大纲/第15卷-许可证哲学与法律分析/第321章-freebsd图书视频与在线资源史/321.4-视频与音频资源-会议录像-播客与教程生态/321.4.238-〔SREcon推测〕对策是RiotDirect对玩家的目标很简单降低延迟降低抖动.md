# 321.4.238 〔SREcon推测〕对策是RiotDirect对玩家的目标很简单降低延迟降低抖动

- 〔SREcon（推测）〕对策是 Riot Direct：对玩家的目标很简单——降低延迟、降低抖动、降低丢包、缓解 DDoS〔17:00〕；DDoS 因极其机密不讲、丢包也略过，因为耗时难可视化且大量丢包发生在更靠近客户的末端（用户掉的是无线链路）〔17:24〕。基本思路是自建骨干网。第一步问“我们的服务器放对地方了吗”——这问题问得有点晚：北美所有游戏服务器原本都在俄勒冈，简单分析立刻表明这不适合服务整片大陆、遂全部迁往芝加哥；EUS 是全球最大的单一分片、原本在法兰克福也不够优〔18:35〕。流量路由优化最先动手：去烦 ISP、说你在我网上有大量客户、请他们改善体验，但多数 ISP 基本不听；另一条路是自己建骨干，因为你终于有筹码、能以平等待遇对话而非乞求网络之神〔19:33〕。建骨干的实操是打电话、找人、做分析、买光纤、买硬件、招网络工程师，从空白开始然后又做一遍、再扩组织——因为这真的很难、还会不断算出惊人成本〔20:29〕。几年间从俄勒冈与法兰克福各自为政、只经转运营商互连，变成全网连通、甚至开通到 Amazon 的 Direct Connect〔21:42〕。成果：图中圆点大小代表玩家数、每个圆大致对应一个 AS 号、绿为低于六十毫秒、红为一百五十毫秒以上；EUS 从阿姆斯特丹迁移与骨干建成前对比今日欧洲、宏观明显改善而南欧尤甚，但阿姆斯特丹旁约五十英里处仍有红点〔22:41〕。另一张图看低于六十毫秒的活跃账号占比、注意纵轴尺度：从零到一百中的七到八个百分点、是多年的上升〔24:12〕。EUNE 红区更多：土耳其较差、波兰红区多且玩家基数巨大、怨言很多，改善幅度不如美国戏剧化但足以证明建骨干非面子工程〔25:03〕。与西班牙 Telefónica、大型 ISP dtac 及德国电信建立直连后，德国电信体验本就好、但此前看均值不看方差、如今个体方差被压进窄得多的区间〔26:01〕。Telefónica 更耐人寻味：开启直连那一刻延迟曲线反而先升——直连暴露出对方内部路由并不优化、需协作给 traceroute 等把路径修正，之后回落到平均改善约十毫秒；这也是付费 peering、要在对端点存在连接、并非无结算 peering〔27:11〕。所有数据来自游戏服务器从真实玩家采集的实际对局体验、而非人工 ping 或 traceroute；与爱尔兰 UPC 母公司 Liberty Global 直连后他家 ping 与办公室只差约五毫秒，按 AS 号单独看则 UPC 最好、BTR 偶尔更优、Digiweb 有明显低效〔28:51〕。未来一是更多 peering 与更细的路由优化——欧洲已有两名 Riot Direct 员工、一名网络工程师与一名分析师、后者正是发现波兰问题的人、因而在波兰建了迷你 PoP；二是创新，先做厂商无关配置（抽象掉专有实现、换 Juniper 或 Cisco 都同样配）、再走向全代码化以真正掌控网络并寻找更好的设备与数据洞见；丢包仍未跟上半步、暗示其在某一侧 AS 内部而非两 AS 之间；第二款游戏很快就来、希望避免重蹈覆辙，甚至对内讨论是否向无力投入的初创游戏公司开放〔30:35〕。收尾是办公室的 PC bang 照片、也欢迎外部来参观〔32:52〕。（YouTube EPZQhQLPqhSUo，[1020-2032]，L1）
- 〔NSDI（转写明示）〕加州伯克利的 Kate Yang 报告与导师 Sylvia Ratnasamy 及 Ryan Rasti、Gan Chen、Scott Shenker 合作、理解数据分析框架性能的工作〔00:10〕。驱动力有二：巨额资本开支推动更省资源、终端用户在等响应推动更快〔00:22〕。框架形态：数十到数十万节点的集群上、数据集切成片存于不同机器，作业拆成任务——各任务做同一计算但作用于不同输入、Spark、Hadoop、Dryad 大体如此；更常见的是先有任务生成中间数据落盘、再由第二阶段任务把数据经网络 shuffle 重组〔00:57〕。既有优化分三类：优化网络（从交换机报文缓冲到减少应用发送的数据量）、优化磁盘（减少寻道、直至用内存缓存避开磁盘）、以及 straggler（少数任务明显更慢）——既往工作难以找出拖尾成因、更多靠缓解：发现任务慢就换台机器重跑〔01:45〕。这些工作展示了应用某项优化的可观完成时间提升，却缺“什么对端到端性能最重要”的认识；浮现的是被普遍接受的真言：网络与磁盘 I/O 是瓶颈、拖尾成因未知〔03:04〕。本工作检验这些真言，两项贡献：新方法论“阻塞时间分析”（blocked time analysis）刻画瓶颈；以及用三个负载验证真言〔03:42〕。三条结论：网络优化对端到端完成时间几乎无关、最多带来 2% 缩减；瓶颈通常是 CPU 而非磁盘 I/O；许多拖尾成因可识别并修复〔03:58〕。作者声明：不主张适用于每个分析负载、也不主张随框架演进长期成立〔04:31〕。方法上“作业瓶颈是什么”没有简单答案：任务内部线程众多、有的读数据、有的计算、有的在磁盘与内存间搬数据，任一时刻不同任务可能卡在各自不同资源上、同一任务也会随时间而变，故通常无单一答案，转而刻画每种资源的重要性——以网络为例问“若网络无限快、作业能快多少”〔05:17〕。两步：其一加入插桩测量任务阻塞在网上的时间（Spark 广泛使用流水线：计算某条记录时后台在读更多记录；作者聚焦计算线程、任务一开始就因缺记录而被阻塞）〔06:14〕；据此可平凡推算“从未因网络阻塞”时的完成时间——把橙色阻塞时间全减掉，但这是乐观上限、因为消除网络后可能改卡在磁盘上而更慢〔07:47〕。第二步用仿真看完成时间如何变化：三任务两槽的作业里只把每槽阻塞时间减掉并不正确、因为没考虑调度器——网络时间消除后任务一完成得远快、任务二会跑到另一个槽〔08:36〕。负载：既有大规模追踪插桩不足、故改用可自跑可插桩的负载——Spark 上的 TPC-DS、big data benchmark、Databricks 的一个生产负载；每个负载跑两版、一版输入输出存内存一版存磁盘〔09:19〕。结果：消除全部网络阻塞时间的中位收益为 2%、第九十五百分位为 10%、跨全部负载中位至多 2%〔10:46〕；同样口径消除磁盘阻塞时间——磁盘比网络更重要一些、但收益仍远低于真言暗示、中位至多 19%〔11:29〕；分布源于同一负载内不同作业受影响程度不同〔11:51〕。（YouTube EPZU4v248AKOY，[9-761]，L1）
- 〔NSDI（转写明示）〕CPU 无法做阻塞时间分析——难判断任务何时阻塞在 CPU（操作系统后台可能在做 I/O），故改用利用率指标：各负载 CPU 利用远高于磁盘与网络、多数作业卡在 CPU。仿真显示这些负载上缓解拖尾的收益至多 5% 到 10%〔12:41〕；更值得注意的是借助插桩他们能理解大多数拖尾成因、可修根本原因，且修拖尾往往同时改善其他任务——例如负载中的配置问题导致拖尾、修掉后所有任务变快、完成时间提升两倍〔13:07〕。既然是 NSDI、作者聚焦网络这一部分〔13:46〕。最初的假设是“我们测的负载是否异常不耗网络”，但既有追踪插桩不足、遂改用“每 CPU 秒传输多少数据”衡量：自家负载对比 Facebook 在数千台 Hadoop 集群上的追踪，后者每 CPU 秒发的数据反而更少；微软与谷歌的追踪只有作业级聚合信息、但平均传输量与作者持平——均不支持该假设〔14:14〕。于是得到两个可量化原因：其一指标不完整、其二把 CPU 时间与网络时间混为一谈。简单 MapReduce 作业中网络用于 shuffle 与复制输出两处，只看一处并不现实：作者看 shuffle 与输出相对输入的比例，最佳情形下 shuffle 数据仅为输入的约三分之一、输出更少；只看 shuffle 会忽略处理大得多的输入所花的时间，而用“全部输入都被 shuffle”（比值 ≥1）的负载也不现实，这是大量以 Hadoop 举例自称吞吐密集工作的通病；对三家公司的追踪画同一指标结论相似〔15:53〕。混同问题：sort 与用 GraphX 跑的 PageRank 虽被认为极耗网络，但优化网络带来的完成时间缩减非常低，因为“发数据过网络”实含两步——先把 Java 对象序列化成字节流、再真正发出；GraphX 类工作宣称减少网络数据量带来显著提升，其实是同时减少了发送与序列化时间、后者是 CPU 时间〔17:15〕。网络何时才真正重要：唯一的例外是求解最小二乘拟合的机器学习负载、每任务调用编译好的原生库做矩阵乘法、优化网络的潜在缩减约 75%，且需多因素同时具备——计算高度优化（跳出 JVM 调原生库）、序列化时间极低（数据本就以 double 数组存放）、发送量很大〔18:13〕。局限：三个负载均为业界标准并用更大规模生产追踪核对；集群偏小但 20 台扩到 60 台结论不变；只做了 Spark、但用 Hadoop 与谷歌、微软框架的追踪核对、并在相同负载上插桩评测 Hadoop 得到同样结论〔19:30〕。最终结论是“性能可理解性应成为一等关切”——缺少足够插桩就运行这些框架有代价；其全部插桩已进入 Apache Spark、追踪也在项目网站公开。答疑：Alex Noren（UCSD）由论文 CDF 看出压缩与不压缩序列化约两倍差距、认为改善方向应是运行时与语言灵活性而非网络与磁盘——作者认同，并称 Spark 社区最新重大举措（Databricks 博客）正是基于他们的工作降低序列化开销〔21:10〕。另有提问者报告 join 在十吉比特与一吉比特网络间有 50% 到 70% 的改善，作者答很多 join 因 Spark SQL 用广播 join 并不用网络；又被问背景流量与拥塞、作者答本工作只聚焦分析负载用网程度〔24:21〕。（YouTube EPZU4v248AKOY，[761-1526]，L1）
- 〔Facebook Web Foundation 主题演讲（会议不详）〕主讲人 2010 年加入 Facebook，此前与 Luis von Ahn 共同创办 reCAPTCHA——注册账号或买门票时输入的扭曲字母；他在 Web Foundation 团队任技术负责人，该团队介于各基础设施团队之间、负责 Facebook 面向用户产品的整体可靠性与性能〔00:04〕。工作分两块：大量主动性工作，与各基础设施团队合作帮他们构建可靠有韧性的服务并建立好的监控；另一块是真出事时的调试——有时问题没有根因、但确实影响整体性能、他们就调试并与正确的团队协同修复，也承担底层系统问题并把深度系统经验在内部扩散〔00:20〕。今天讲三件事：以“让它更快失败”为核心的可靠性想法；调查问题的方法；以及事故管理与事后学习〔01:16〕。以汽车碰撞引入：车以六十英里时速行驶时动能必须有去处；大型分布式系统失败时故障必须由系统某部分吸收；汽车有“溃缩区”吸收碰撞能量以保护乘客，所以他喜欢把自己做的事想成给基础设施建溃缩区〔01:37〕。经验之一是排队常是慢的诱因或放大器：服务通常有一池工作线程、无队列时最多只能阻塞 N 个人（N 为线程数），有队列就有无限条等待执行的请求列表、从而把无限程度的慢传播到整个系统〔02:10〕。排队分好坏：好的排队短暂、应对突发负载且处理速度大于请求到达速度、通过缓冲临时问题提升可靠性；坏的排队永远在排、代表系统从根本上坏掉，它带来延迟却不提升吞吐与可靠性、只是让系统对所有人都更慢〔02:42〕。已实现的机制之一是与 Thrift（他们用于服务器间通信的 RPC 框架）一起开源的排队延迟控制，关键洞察是受控队列最终总会清空〔03:46〕。"control delay" 的逻辑很简单：若过去十到十五秒内队列曾完全排空就什么都不做；若过去十秒内没能消费完所有请求、就把请求可停留的时间设成极小超时、约十到三十毫秒〔04:12〕，结果是好队列不受影响、坏队列被迅速识别并限制其能造成的延迟〔04:27〕。第二个同样开源的机制叫 adaptive FIFO：FIFO 总服务等待最久、已承受最多延迟的请求，而排队延迟达三十秒时用户早已放弃、转去别的网页或另一个 App，于是你在服务一个用户永远看不到响应的请求；adaptive LIFO 的想法是优先服务用户更可能看到响应的请求——常态下仍是 FIFO、一旦队列占用升到不典型水平就切到 LIFO，随后 control delay 把其余请求超时掉〔05:00〕。这套组合让服务更主动地告诉调用方“我这边排队很多、我要拒绝你的请求”、从而让用户整体响应继续推进〔05:58〕。另一条理念是不只修服务端问题、也让客户端不信任服务端会出于善意行事：把并发控制的哲学内置到很多服务里——服务资源有限即同一时刻能处理的请求数，不希望某个服务把全部资源垄断在反复联系一个不工作的下游上，故给任何给定服务的并发数设上限〔06:25〕。（YouTube EPZWYaFXM4wQ8，[4-409]，L1）
