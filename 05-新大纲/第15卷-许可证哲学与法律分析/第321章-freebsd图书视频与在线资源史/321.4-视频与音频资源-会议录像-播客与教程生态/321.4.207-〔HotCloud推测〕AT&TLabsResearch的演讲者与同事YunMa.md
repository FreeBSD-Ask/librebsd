# 321.4.207 〔HotCloud推测〕AT&TLabsResearch的演讲者与同事YunMa

- 〔HotCloud（推测）〕AT&T Labs Research 的演讲者（与同事 Yun Mao 合作）报告 Inception Cloud："Today I'll present our research Inception Cloud where we build a nested cloud architecture"〔00:10〕。起点的批评很直接：IaaS 云上 "you cannot do many things for example VM live migration"〔00:23〕，原因并非不会做——KVM、Xen 早已成熟——而是 "they do not allow us to migrate VMs simply because there is a conflict of interest"〔00:43〕：实时迁移需要共享存储与二层网络，比云商提供的三层网络更贵，于是用不上的负载也得为迁移能力付费。同类受限场景还包括自定义 Dom0 防火墙规则做入侵检测、复制虚拟机做高可用、高负载下批量起虚拟机〔01:50〕；更根本的是 "you do not control the hypervisors of underlying physical machines"〔02:12〕，它们由云商掌控且不愿向普通用户开放。研究者想自建大规模跨数据中心云也不行，那属于 Amazon、Microsoft、Rackspace 的体量与现金流游戏〔03:02〕。于是转向：既然云上已有近乎无限的 VM 资源，何不把它们当物理机用〔04:10〕——在别人的云里再跑一层云，即 "virtualized environment within virtualized environment"〔04:22〕，命名取自电影《盗梦空间》里 "downward is the only way forward" 这句台词〔05:20〕。好处清单包括完全掌控的 hypervisor 自由度、免掉制冷供电布线机架与坏件更换这些物理琐事〔06:44〕，还能跨公私云与多个提供商广域部署〔07:18〕，核心收益是 "entire control of your cloud with even less operation overhead"〔07:38〕。三个应用场景：为每个网站各跑一个 Web 托管云并按其负载特征开关 hypervisor 特性〔08:01〕；在公私云上并行跑多个持续集成云做完整网络特性测试，测完 "simply throw away your Inception Cloud by simply destroy the underlying VMs"〔09:10〕；以及跨三个云的虚拟桌面云，坐飞机从东海岸飞到西海岸参会时虚拟机自动迁移以获得更低时延〔09:26〕。他明确这些场景在现有 IaaS 上 "none of above scenarios is achievable"〔10:03〕。实现选型是 OpenStack 做云管理软件，目标是 "run stock OpenStack platform without any modifications to its source code"〔10:57〕，hypervisor 用开启嵌套虚拟化的 KVM〔11:19〕，并自定义网络组件：RVM（从云商拿到的普通 VM，带一个 eth0）与 IVM（跑在 RVM 内的嵌套 VM）之间自建二层网络，理由是 "layer two is easier to configure and manage than layer three"〔12:00〕，且二层才使得实时迁移可行〔12:09〕。（YouTube EPX7c6Ypx00vQ，[10-749]，L1）
- 〔HotCloud（推测）〕后半段进入网络设计与实现。设计对底层云商无关〔12:29〕：RVM 自带的 eth0 用作管理接口，在其上叠加由 Open vSwitch 与 VXLAN（转写误作 GXTN）构成的虚拟二层网络；eth1 是 IVM 之间的私有网络，ovb1 桥是所有 RVM 上 eth1 的全局逻辑桥〔13:13〕；eth2 提供 IVM 的公网访问；这三套网络彼此隔离，IP 泄露在设计上被排除且对 IVM 完全透明〔14:24〕。跨数据中心只需增设网关 RVM 拉隧道〔14:52〕。单台 RVM 内特意做了两座桥——Open vSwitch 的 ovb1 与 Linux 的 br1：前两条理由是设计上的（OpenStack 用 Linux 桥、与 ovs 网段不兼容，而目标是跑原生 OpenStack 不改代码），第三条是技术上的，"Open vSwitch does not well support iptables or ebtables firewall rules"〔16:12〕。公网访问更难，因为 OpenStack 的 floating IP 靠 NAT，做法是通过操作 DNAT/SNAT 等规则把一台 RVM 的公网 IP 转发到另一台 RVM 内的 IVM，效果上就像该公网 IP 挂在远端 IVM 上〔16:50〕；由此 "Each RVM can host many IVMs with any number of floating IPs"〔17:36〕，且可在不打断既有流量的前提下迁移 IVM〔17:44〕。另一个亮点是 "this design even supports recursively nested inception cloud"〔17:54〕——云套云套云，只要物理机吃得下。原型可部署 OpenStack 计算、存储、网络核心组件，用 Chef 自动化部署，"we can launch an inception cloud in about twenty minutes"〔18:46〕。后续方向三条：性能上现有文献报告 CPU 与内存开销在 5% 到 10%、可接受，但网络与存储有显著退化、正在查 I/O 瓶颈〔19:19〕；把二层网络做成可规模化——目标是每个数据中心承载约一万台 IVM，用 SDN 控制面接管 ARP、DHCP 广播、迁移与安全组这些传统二层不可规模化的问题〔19:53〕；以及用 Inception Cloud 反过来给 OpenStack 做持续集成〔20:23〕。问答三点：VXLAN 中多播与广播目前 "implemented as multiple unicast"、不可规模化，故要走 SDN 控制面〔22:08〕；5% 到 10% 开销数字引自 Turtles 等文献而非自测，且 "we didn't do any customization to KVM"〔23:02〕；跨云部署方面 Rackspace 默认开启嵌套虚拟化，Amazon 默认 Xen 不支持，但可用 Xen Blanket（一篇 EuroSys 论文）开启〔23:53〕。（YouTube EPX7c6Ypx00vQ，[749-1496]，L1）
- 〔USENIX Security（推测）〕Ruoyang Guo 报告 GridSE——"towards practical secure geographically searchable encryption"，即前缀对称可搜索加密〔00:08〕——与 Stevens Institute of Technology AISec Lab 的 Jia Li、Shucheng Yu 合作。现实场景是依赖敏感数据提供地理搜索的应用（Yelp、Instagram、Facebook 一类），"These G S apps usually need to collect personal information from users"〔00:47〕，包括实时位置；数据通常托管在云商，客户端直接推送明文风险很高，理想状态是地理数据 "better to be encrypted and can be faster searched"〔01:14〕。真正的约束来自生态兼容：现有 GIS 应用深度扎根于 DGGS（离散全球网格系统）——把二维乃至高维空间数据编码成字符串的体系，变体包括 Geohash、Google S2 与 Uber H3〔01:23〕。演讲给出直观例子：游客问新泽西最佳去处，"New Jersey will be encoded to D R five R"，而返回的自由女神像编码为 DR5R7〔01:53〕，所以 "this is in essence a a prefix search problem"〔02:20〕，安全地理搜索因此需要安全前缀搜索。工程难点有四：接近零延迟的即时响应、与主流 DGGS 兼容、支持前缀的加密搜索，以及支持插入删除的动态更新且不漏隐私〔02:38〕——前向隐私要求新加入数据无法与历史查询关联，后向隐私要求查询无法与已删除数据关联〔03:08〕。既有工作的不足是：动态 SSE 多面向整词而非前缀，安全子串搜索则在效率、更新成本、安全与误报率之间折衷，直接拿现有密码原语拼 SGS 方案 "very difficult"〔03:31〕。核心设计是新密码原语 SP²E，用于判定 "whether a keyword contains the prefix"〔04:01〕：服务器把待检索字符串（如 DR5R7）按字符映射到分层结构中的加密哈希函数、用伪随机值掩蔽后 XOR 得到密文；客户端持有前缀（DR5R）生成 token，同样按字符映射并以新鲜伪随机值掩蔽，但 "we need to introduce some definiteness"〔04:31〕——把 token 中的一部分伪随机值替换为源密文相同位置的那一部分，于是 "just by a single xor operation between the token and the cipher, we will find the zero bits will expose in the specific positions"〔05:20〕，靠这些固定位置上的零位即可识别带相同前缀的关键词。（YouTube EPX7mknw8Z6tU，[8-333]，L1）
- 〔USENIX Security（推测）〕后半段把 SP²E 扩展成动态方案并给出实测。防更新泄露的做法是加密三元组（keyword、file ID、增删操作），并按字典式映射组织：关键词放键区、用 SP²E 加密以便前缀检索，相同关键词的三元组以列表形式放值区〔05:33〕。仅隐藏更新计数器不足以做到前向与后向隐私——那只会产生相同密文；GridSE 靠 "only an extra single parameter, the dictionary sequence of address, I mean the sequence of key"〔06:26〕达成该标准，把键序信息并入三元组加密，使 "the server cannot distinguish"〔06:56〕插入与删除。除扩展原语外还提供通用框架，把动态 SSE 转换为动态前缀 SSE，只需遵守两条规则：保持 GridSE 的基础设定与客户端服务器之间的密钥存储及处理流程，以及沿用字典结构（键上前缀搜索、值上其他 SSE 方法）〔07:00〕。实验基于处理后的全球位置数据集，取得 "sixty thousand distinct users within California"〔07:53〕；数据库规模从一千到一百万、结果集从十到一万，检索范围从一百公里量级到一平方米量级，并覆盖 Geohash、Google S2、Uber H3，删除实验随机删掉匹配前缀结果的 10%〔08:15〕。性能结论：一百万文件、结果集一百时，含描述的搜索只需 20 毫秒〔09:00〕；删除比例对性能影响很小，百万库、万级结果下搜索时间无明显变化；通信成本随结果集线性增长但与数据库规模无关〔09:20〕；更新对规模极不敏感，单次更新 2 微秒、8 字节〔09:50〕。与 SOTA 相比，搜索时间有 "one hundred fifty to ... five thousand times speedup"、通信成本省九成〔10:18〕；与明文搜索相比仅多约 1.4 倍通信成本与 0.9 量级的额外开销，因此在给定地理区域内 SP²E 成本近似常数、可扩展性良好〔10:48〕。（YouTube EPX7mknw8Z6tU，[333-668]，L1）
- 〔USENIX Vault〕我先把话说在前头：接下来三场演讲全是 SMB 相关。讲者 Jeremy Allison 供职于 Google 的开源项目办公室，并特意声明“no Google lawyers have seen these slides”〔00:05〕——这是一场 Samba 演讲，不是 Google 演讲；他在 FOSDEM 做过同一场报告，弟弟专程赶到布鲁塞尔旁听，坐他旁边的两位观众在讨论“what's new in Samba”〔00:58〕，于是他说真正的题目不该是 Samba 有什么新东西，而是“the question should be why Samba”——这帮人还在不在。Samba 同时是文件服务器、打印服务器、Active Directory 服务器和认证服务器，内部分三层：SMB1/2/3 协议解析层、NTFS 仿真层，以及他投入最多时间的 VFS 虚拟文件系统层；微软的文档已把协议讲清楚，所以难的不是解析协议，而是“actually making POSIX and Unixes behave like Windows”〔02:44〕。第一优先事项是“die SMB one”〔04:41〕：SMB1 时代一切基于路径名，代码与 SMB2 纠缠得极丑，他与 Microsoft 的 Ned Pyle 长期合作拆它；靠把默认配置里的一行 yes 改成 no，开箱的 Samba 已不再启用 SMB1〔06:19〕，而“whenever I finish removing the SMB1 code, that's when I'm going to call it Samba five”；Susie 与 Sernet 等厂商正推进测试套件现代化，把测试迁到 SMB2 之上。第二战场是 VFS：这套 API 上世纪 90 年代建模于当时的 POSIX，而现代 Linux 用 openat 与 at 系列调用、支持基于文件描述符的相对路径且对符号链接安全，加之多线程与凭证代理，Linux 有 per-thread credentials 而 FreeBSD 没有（FreeBSD 下会退化为同步执行），glibc 又不暴露所需接口，于是他干脆自己写了带 per-thread credentials 的 setresuid，在 32 位与 64 位 Linux 上测试通过〔10:20〕。新 VFS 用句柄与 file struct 指针取代文件描述符、向 NTFS 语义靠拢并把可插拔模块上移让 OEM 获得更好性能，GPL 边界也拟清晰划定〔11:47〕。异步化靠回调把读写路径拆成 send 与 receive 对，底层是 Volker 维护约七年、至今仍偶尔冒出竞态的线程池；性能上他宣布自己退出了自研加密库业务改投 GnuTLS，加密传输快了三倍，内部数据库重做以应对 Windows 客户端在顶级共享目录上批量挂 change notify 的病理场景，iouring 模块也已落地，在内存文件系统上读到约 20% 提升〔15:19〕。（YouTube EPX7zBoee3ok8，[5-994]，L1）
- 〔USENIX Vault〕持久句柄、RPC 解耦、SMB over QUIC 与项目治理。持久句柄意味着集群可以停很久再重启、客户端带着句柄回来仍要被兑现持久性承诺，代价高昂且尚未完成，他预计要到 Samba 4.x（x 大于 12）才有；CTDB 已接进持续测试环境，目标是从 Samba 中解耦，因为大量 OEM 自有分布式文件系统和集群管理器，不想用 Samba 的那套〔17:24〕。加密方面他坦言当初自写加密是个坏主意，后来 Red Hat 的人去找 GnuTLS 维护者补齐 Samba 需要的能力，终于能删掉一大块代码并支持现代 Intel 处理器的硬件加密〔19:04〕。Samba 分裂又合流的历史留下了两套 RPC 服务端与客户端实现，GitLab 上有补丁要收敛成一套；还需要完全异步的 RPC 调用与 witness service，让客户端在服务端下线时把连接迁走；RPC 服务也在被拆成库供第三方 SMB 服务器直接调用 Samba，免得自己重写 NDR 与 DCE/RPC 那套丑东西〔21:55〕。试验性工作是 Steve 的 Google QUIC 实验性服务端与客户端：很多 ISP 封 445 端口但 443 畅通，让 SMB 走上 QUIC 与 HTTPS 通道才真正可行，团队曾在 SNIA 大会上用 Mac、Windows、Samba 客户端与 GNOME 文件浏览器全部连到同一云文件服务器验证；但把加密进来的连接转交给 Samba 服务器还缺端口分派机制，C QUIC 库选择也不明朗，Cloudflare 有带 C API 的 Rust 库而 Google 的库是 C++〔22:27〕。Active Directory 已做到 300000 用户、有 prefault 模型、智能卡认证与 JSON 审计日志，一些欧洲政府用得多，但缺 web 服务那部分——现代 AD 依赖 SOAP，“I I hate web technologies”，新西兰公司 Catalyst 承担了大部分 AD 工作〔26:15〕。项目治理上已迁移到 GitLab 做补丁集成与持续集成测试，任何 drive-by 提交都能跑完整测试套，master 仓库仍在 samba.org 并向 GitLab 镜像，仍要求至少两名团队工程师审阅；与 OSS-Fuzz 的集成已找出了躺在稳定代码十年以上的安全问题〔29:09〕。生态侧 Ronnie Sahlberg 的 libSMB2 只有 100 到 140KB、依赖极少、支持加密连接与零拷贝，Linux 内核态的 SMB2 服务器实现也在跑 Samba 的测试套件——虽然在他看来把集群化做进内核相当难，但用户态 SMB 客户端确实无处不在〔29:44〕。（YouTube EPX7zBoee3ok8，[994-1978]，L1）
