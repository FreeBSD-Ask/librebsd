# 321.4.195 〔SREcon〕JupyterHub与Kubeflow的运行机制逐项对比与经验教

- 〔SREcon〕JupyterHub 与 Kubeflow 的运行机制、逐项对比与经验教训（下半场）。Capital One 最初用 JupyterHub 供给 notebook——它自称是面向公司、课堂与研究实验室的多用户版 notebook、是带内置认证的后端 notebook 供给器与流量路由器，用户从单机走向更大工作负载或需要 GPU 支持时自建场景通常首选它，他们在 1.0 发布前采用、起初稳定且满足全部用例，但在大环境中维护难度足够高、等到规模铺开时已因可用性问题与无法达成平台 SLA 与 SLO 而打算更换（并顺带调侃“我们已经履行了在 SREcon 演讲的合同义务”）；其运行原理是 hub 创建一个代理（一个 pod）默认把所有请求转发给 hub，hub 负责日志并按需拉起单用户 notebook 服务器（在 Kubernetes 中表现为 pod 与 volume）、再配置代理把 URL 前缀转发给单用户服务器使用户拿到可用 URL，背后数据库通常放在 EBS 卷上的 PVC 上并直接挂到系统而非托管数据库，这在正常运行时效果很好但 EBS 卷在可用区与集群节点之间迁移本就可能引发问题，另外两个体验亮点是 notebook 服务器起来之前状态日志就已经 WebSocket 实时流式送到 UI、以及底层 hub 配置是纯 Python 易读且易于在内部扩展自定义选项。Alex 介绍 Kubeflow 是 Kubernetes 上的机器学习工具集、以统一平台与接口把原本零散且各自高度聚焦特定问题域的工具整合起来以弥补生命周期中切换工具时的不一致体验，Kubeflow 用 Kubernetes operator 实现 notebook 供给——operator 由一个或多个自定义资源定义（提供新数据模型、扩展 Kubernetes API）加一个响应自定义资源创建的控制器应用组成，控制循环即协调循环、把“自定义资源加循环内逻辑”共同定义的期望状态与集群上真实部署的实际状态比较并消除差异、故称 reconciliation loop；Kubeflow Notebook operator 用一个名为 Notebook 的新模型扩展 Kubernetes API，当用户（通常经 Kubeflow UI、也可直接调用 Kubernetes API）创建该自定义资源时协调循环被触发、调用 API 并创建 StatefulSet、Service 与 Istio Virtual Service 三个资源（前两者是原生对象、后者本身也是 CRD）共同运行并对外提供 notebook 服务器、整个过程几乎瞬间完成而普通数据科学家对其实现细节无感；Kubeflow 历史上曾用 JupyterHub 供给 notebook、后来切换（理由记录在一个 issue 里），两人都在用、各有优劣，本场只是对比而非贬低任何一方。逐项看：数据存储上 JupyterHub 不依赖 etcd 作为唯一事实来源、其中心 hub 组件自持数据库（即前述 EBS 卷），按维护者说法“hub 本身是单点故障，必须拥有它与之通信的数据库”，其他 hub 实例可能没在运行或没连同一个数据库就会出错误与状态不一致、因此很难让两个 hub 实例互为故障转移、hub 崩溃或被驱逐时服务会中断数分钟，而 Kubeflow Notebook operator 是 Kubernetes 原生的、唯一数据存储是 Kubernetes 数据库（几乎都是 etcd，即使用 Raft 算法取得一致性与高可用的分布式可靠键值存储）、Kubernetes API 高可用且通常应有多个副本并行接收请求并访问 etcd；认证上 JupyterHub 只解决 notebook 供给一个问题因而只提供面向这一问题的认证（可扩展性令人印象深刻但用途单一），而 Kubeflow 解决 notebook 供给、工作流编排、超参调优等许多问题、借 Istio 提供高度可扩展可拆解的认证并同时利用 Kubernetes RBAC；代理上 JupyterHub 默认的 configurable HTTP proxy（简称 CHP）是单点故障、只能向上扩展不能横向扩展，且 CHP 挂掉后恢复耗时较长、因为 hub 需要重建 CHP 默认存在内存中的路由表（除非指定 Redis 等外部存储后端），JupyterHub 后来确实发布了基于流量的代理显著改善高可用、但那已是 Kubeflow 完成向 notebook operator 迁移很久之后；UI 上 JupyterHub 朴素但极可扩展（用 Python 就能控制 notebook 配置表单、且不必修改底层镜像即可部署因为 hub 可在运行时动态加载代码，这是他们希望更多产品都能具备的开发体验），而 Kubeflow Notebook UI 功能极其丰富且打磨到位、默认把更多控制交给最终用户（可供给多个持久卷声明、指定存储类别与容量、容忍度、亲和性，以及 pod defaults 这一 Kubeflow Notebook 特有机制、借助动态准入控制与变更 webhook 侧装额外功能），要在 JupyterHub 中复刻这些功能需要巨大投入；反过来 JupyterHub 也有辩护——正如该 issue 中一位维护者所说其目标用例是“单机 5 到 50 个用户”、若干设计决策优先考虑用户态可安装性可维护性与简洁而可扩展性被明确划在范围之外，且它面向多种后端、各有专用 spawner（Docker spawner、Pseudo spawner、Batch spawner、Yarn spawner、SSH spawner 以及全程讨论的 Kube spawner），若要在本地高性能计算环境下供给 notebook、JupyterHub 可能反而比 Kubeflow Notebook 更合适——但在 Kubernetes 上则完全是另一回事。经验教训是：后端无关性可能付出代价（JupyterHub 极其灵活、能在 Kubernetes 集群上承载可观的 notebook 量，但他们在压测中用 Kubeflow 加 Kubernetes 能承受的并发 notebook 供给数要多得多、某些情况下高出约 10 倍且未发生控制器崩溃，故若明确要在 Kubernetes 上供给 notebook 他们的推荐是 Kubeflow）、解决生态问题时你需要模块化可拆解可共享可独立扩展的组件（随着系统规模增长、自包含方案可能与更偏生态的做法不兼容，这正是经典的单体 vs 微服务讨论）、在 Kubernetes 中该权衡同样存在而构建在分布式优先的架构上可扩展性与韧性自然涌现使高可用更易达成、要警惕沉没成本（Kubeflow 作出了切换的果断决策在他们看来是正确的、而他们自己也必须做同样的决定，有时发现问题无法用补丁解决时必须对技术债采取更大的措施）、架构上没有完美选择只有“逐步不那么糟”的选择（连 Unix 小工具这种被奉为不言自明的好实践也并非处处完美），两种 notebook 供给器都在演进、他们的判断也在演进，也许未来会出现同时超越两者的方案，工程师能做的只有依据当下所掌握的信息做出当下最好的决定。（YouTube EPVWOhiNaZinQ，[431.1-1119.9]，L1）
- 〔系统会议（推测）〕IntoOS：面向多线程间歇计算（intermittent computing）的持久嵌入式操作系统与语言支持。主讲人 Yilun Wu 为 Stony Brook University 博士生，师从 Professor Dongyong Li。间歇计算依赖环境能量采集与电容供电，因采能速率远低于耗电速率而频繁断电崩溃，寄存器与 SRAM 状态全部丢失；近十年已有大量支持单线程间歇执行的系统，却没有可运行的嵌入式 OS。既有 RTOS（如亚马逊支持的 Zephyr、完全用 Rust 实现的 Talk）本身并非崩溃安全，而 Ratchet、micro-continuation 只能依赖 NVM 因而缓慢低效，multitasking composition 需要巨大手工改造且不随代码规模扩展。IntoOS 分三层：应用层支持多线程，OS 层提供队列、事件、信号量、软件定时器等原语，硬件层同时利用易失与非易失存储，以事务保证非易失对象一致性，并用名为 replay-and-bypass 的新恢复方法实现崩溃一致性与快速恢复。以采集传感器数据做模式识别的单线程示例说明：内核维护事务与系统调用两张 replay table 记录已完成事务的返回值，崩溃恢复时已完成事务直接 bypass 并用记录值重建 volatile 指针，未完成事务回滚后重执行，最终精确回到故障点，从而在重建 volatile 状态的同时避免冗余执行。（YouTube EPVWTL4nCy2IA，[16-599]，L1）
- 〔系统会议（推测）〕多线程调度状态恢复的语言化执行与评测。多核场景带来三项额外挑战：内核维护更新极频繁的就绪队列与等待队列，IntoOS 为效率改用 row-forward（而非事务）的崩溃一致性方案；线程之间通过队列、信号量等共享对象交互，由内核级事务保证这些内核对象的崩溃一致性，恢复时先修复被中断的内核事务再恢复用户线程，防止用户线程观察到部分内核状态；任务有优先级差异，原则是优先恢复最高优先级的就绪任务，其余任务延后到被调度时再惰性恢复。因为若一次性回滚全部未完成事务，很可能在做任何有意义的工作之前就先耗尽电量，这就是 just-in-time recovery 的由来。安全性借助 Rust 类型系统落地：持久对象被包裹成 PBox 一类特殊类型，禁止把裸引用返回事务之外，事务内只能通过携带 journal handle 的 mut 方法取得引用，从而强制持久对象只能在事务内被解引用与修改，违规写法直接编译失败。评测基于自建的 7 个多线程微基准与实时数据处理基准 Rite Bench，测试床为带 FRAM 加 SRAM 的 MSP430 与带混合存储的 Apollo four plus 开发板，以 Ratchet 为基线。在 1-10 毫秒周期性断电注入下，重执行是开销主体，而 undo 日志与 bypass 的恢复开销很小，总体相对基线取得 1.3-2 倍的几何平均开销下降，使 IntoOS 成为首个崩溃安全、支持基于优先级的抢占式多线程的嵌入式 OS。（YouTube EPVWTL4nCy2IA，[606-1051]，L1）
- 〔安全会议（推测）〕用 CPU 缓存侧信道突破 Android 应用沙箱。主讲人自称 Devin，称该工作是与其前博士生和博士后合作完成的。Android 上每个应用运行在各自沙箱内，Uber 与 Lyft 这类竞争应用互相无法获取对方信息，作者要质疑的正是这一机制是否抗侧信道攻击。此前工作已关注 ARM CPU 缓存侧信道，但大多针对各进程共享的组件——Android runtime、共享原生库等：一旦检测到某个共享库被加载或某个方法被调用，无法判断究竟来自哪个应用，这是既有工作的关键局限。作者转而盯住应用层组件：若能定位到特定应用自身的代码，就能精确识别是哪个应用在做什么，从而对噪声鲁棒。核心杠杆是 2020 年被发现的 DICAC（动态跨应用组件共享）机制——应用可用少量代码加载设备上任意目标应用的上下文，包括其代码与共享库，Play 商店上不少知名应用都在使用它；由此攻击者可在自己的内存映射中看到目标应用库已被加载。整个攻击因此分为静态分析目标应用定位关键方法、加载其代码、再做侧信道探测三阶段，而探测本身用 flush-and-reload，工程细节包括把攻击者应用固定（pin）到 little core 以提高精度、用新方法确定缓存命中与未命中的判定阈值，以及引入 output voting 机制在同一方法内扫描多个目标以提升判定精度。（YouTube EPVYqTtb_yic4，[8-534]，L1）
- 〔安全会议（推测）〕路由重建与按键动力学实验及负责任的公开披露。论文报告了两台较老设备的结果，后续在更多最新设备与最新 Android 版本上测试，发现大部分最新设备仍可复现。第一个实验针对导航应用 Organic Maps：先静态分析找出目标应用中的关键方法（如每次播放左转或右转语音时调用的方法、界面视图更新时调用的方法），再用侧信道监测它们；实验显示可检测到这些方法的执行时刻，即每一次转向点，还能识别导航结束（车辆到达目的地），并利用车辆静止时视图不再变化这一点判断车辆是否在移动，从而恢复整个行程路线。第二个实验针对 Briar 应用做按键动力学推断，通过定位并监测每次按键触发的方法得到每个按键时刻，还可区分单词结束与消息发送完成，配合这些时序信息即可还原被输入的实际文本。相比既有工作，攻击无需任何权限、对噪声鲁棒，论文还测出可同时监测的目标数量；团队与 Google 协作完成负责任披露，Google 评估其严重程度为中等，团队获 250 美元奖励，Google 表示正在着手修复。（YouTube EPVYqTtb_yic4，[535-857]，L1）
- 〔系统会议（推测）〕Midas：为应用托管的软状态收割空闲内存。主讲人 Yifan 称这是与 UCLA 和 MIT 合作者的联合工作。软状态指能提升性能但可以随时丢弃的数据，典型如缓存与记忆化结果：应用先查软状态存储，未命中时按需重建并回填，以内存换取更高的性能，因此是收割空闲内存的理想用途。但开发者自己很难管好它——一位构建图片密集 UI 应用的开发者面临的问题就是二选一：把可能的软状态全部缓存在内存里，性能确实变好，但内存耗尽后进程会被内核 OOM 杀掉；改为把缓存静态限制在很小的规模，又无法吃满空闲内存，白白留下性能。Linux 的 page cache 能自适应伸缩，却只能缓存磁盘块，装不下应用需要的软状态。于是作者提出一种新的虚拟内存抽象：软内存（soft memory）给用户应用呈现出无限缓存空间的假象，应用可无顾虑地存入全部数据，内核在内存压力下快速 unmap 部分页面来应对，而被驱逐的软状态会被自动重建，底层可用内存的变化对应用完全透明。接口上开发者先创建软内存池，池返回的软指针用起来类似 C++ 的智能指针，可在初始化时注册一个 reconstructor 函数：对象已存在就直通访问，不存在则由软指针自动调用重建器，把新算出的值写回软内存并更新指针，使下一次访问直接命中。底层用与内核协作的应用集成式运行时：借鉴日志结构分配器（log structured allocator）把软内存组织成段的列表，跟踪每个对象的访问频率与活性，用 evacuator 持续压缩分段、把热、冷、死对象隔离开，使热对象聚集在小片内存区域内；内存压力到来时内核先向用户态运行时发消息要求返还内存，运行时按先空闲段、再冷段的顺序释放，并同步更新被驱逐对象的软指针以便日后重建。极端压力下运行时可能来不及或不被信任，Midas 让内核直接 unmap 软内存页，作者称之为内核强制回收（kernel enforced reclamation）。（YouTube EPV_cEoA5wF_E，[16-595]，L1）
