- 〔会议不详〕Reef：面向零知识正则证明的系统。主讲人 Eli Margolus 介绍私有正则匹配（用公开正则匹配私有文档），并以非对称口令认证密钥交换 aPAKE 为动机：服务器用正则表达“强口令”概念，用户以零知识证明自己的口令匹配该正则而无需向服务器泄露口令。朴素做法把正则转成 NFA、将 delta 函数写成级联 if 语句，存在三类瓶颈：lookahead/lookbehind 在 NFA 中的状态爆炸、for 循环需在电路中按字符展开、以及约束规模为文档大小×字母表×自动机规模；Reef 分别用跳跃交替有限自动机（skipping alternating finite automata, SAFA）、递归证明系统与查找论证（lookup argument）化解，把乘积项移入对数内，可扩展到大文档、大字母表与大自动机。（YouTube EP9RZr9LOUXVc，[8.3-368.1]，L1）
- 〔会议不详〕Reef 的组件细节、应用与评测。Reef 用两类查找论证替代级联 if：私有文档承诺表（把字符绑定到文档索引）与 SAFA 转移表（起始状态-字符-结束状态），并支持文档投影与公私混合表等可独立受益的优化；递归证明系统对单次 delta 调用生成证明并逐字符迭代，使电路规模只由单次 delta 决定、验证者只需检查最后一步。应用涵盖个性化医疗基因检测（大文档大自动机小字母表）、基于 ODoH 的安全浏览兼顾网络管理员恶意站点管控、以及记者源邮件脱敏后公众仍可用 DKIM 验证真实性；评测显示 Reef 在 8GB 内存笔记本上即可编译全部应用电路（基线在 764GB 内存服务器上仍编不过），证明时间最多快五个数量级，相比 zk regex、zk email 等现有系统约束更少且额外支持 lookarounds。（YouTube EP9RZr9LOUXVc，[398.7-779.6]，L1）
- 〔SREcon〕Parca 持续性能剖析的动机与 eBPF 数据采集。主讲人 Matthias Loibl（Polar Signals 高级软件工程师，长期维护 Parca、Thanos、Prometheus 等项目）指出 pprof 采样剖析开销很低但只是手动快照，难以抓到 OOM kill 前一刻的现场，因而需要常开、可“时间旅行”的持续剖析来定位生产问题与发布回退。Parca 起源于 Conprof、架构仿照 Prometheus（复用其服务发现与标签、可抓取 HTTP 端点、存对象存储、附 Web UI），Parca agent 基于 eBPF 以约 19 次/秒观察栈并写入 eBPF map、每 10 秒读取一次以保持低开销，借助 DWARF、Go PC 行表与 build ID 做符号化，编译型语言只上传带地址的栈从而节省带宽，内核与解释型语言则就近在 agent 符号化。（YouTube EP9U2nDA_fjYA，[15.5-1083.2]，L1）
- 〔SREcon〕Parca 的语言支持、存储与可视化及社区近况。Parca 实现了对 Python 与 Ruby 的零插桩剖析（回溯并符号化解释器内部抽象栈），支持 pprof 标签与 trace ID 关联以便从剖析跳转追踪系统；出于 SRE 安全考虑采用静态链接二进制、CO-RE 编译的 eBPF 程序、可复现构建并签名容器。存储上从 fork Prometheus TSDB 转为自研 FrostDB（Go 编写的可嵌入列式数据库，基于 Apache Arrow 与 Parquet，标签为一等公民），配 Prometheus 风格查询语言，可把一小时内剖析聚合合并为单张火焰图，并支持部署前后对比；可视化含函数名字母序折叠的火焰图/冰柱图与逐行源码视图。Polar Signals 云正式 GA，Parca 保持中立治理并每两周举办 office hours 欢迎贡献。（YouTube EP9U2nDA_fjYA，[1083.2-2156.4]，L1）
- 〔SOSP（推测）〕阿里巴巴大规模生产集群调度：从单主架构到 Omega 共享状态。本工作来自阿里巴巴：单集群达十万台机器、每日执行数十亿任务（87% 的任务在 10 秒内完成），原单主调度器被海量 worker 心跳与任务量压垮，需在调度效率（延迟）、调度质量（资源偏好满足）、公平与优先级、资源利用率四个相互冲突的目标间权衡，且要求对现有代码库改动最小、升级对内部用户与云客户透明。调研后选用 Omega 共享状态架构（多调度器各自维护集群状态本地副本，可按作业类型运行不同策略并实现全局公平策略），但生产环境中网络通信压力大、调度算法依赖的状态大，无法在每次分配任务时全量同步，本地状态陈旧导致冲突与重调度增多；数学解析难以处理递归重调度，团队转向轻量级仿真，以 N 个调度器、S 个槽位、任务提交率 R、同步间隔 G、槽位质量 B 等参数刻画冲突开销。（YouTube EP9UImX0fKHlw，[9-427.4]，L1）
- 〔SOSP（推测）〕Parsync 分区同步与自适应调度策略。仿真发现提交率、槽位质量与同步间隔是冲突主因，且调度延迟随同步间隔不成比例增长（间隔末端状态陈旧引发递归重调度）；据此提出 Parsync：把 master 状态划分为不少于调度器数的分区，各调度器按轮转方式同步不同分区，以更细粒度、更高频率换取新鲜状态，diff-sync 策略优于各调度器同步相同分区的 same-sync。调度上提出 quality-first（按平均槽位质量选分区、再按槽位分数加权采样）、latency-first（优先选新鲜分区）与自适应混合策略，仿真与真实负载的高保真实验显示自适应策略能紧跟各种情形下的最优者；最终把生产集群调度能力提升到十万台机器上每秒四万任务，降低冲突、保持用户透明与向后兼容。（YouTube EP9UImX0fKHlw，[427.7-846.3]，L1）
- 〔USENIX Security（推测）〕ODGen：面向 Node.js 漏洞挖掘的对象依赖图。主讲人 Song Li（约翰霍普金斯大学）指出 npm 自 2010 年引入后已达约 130 万个包，漏洞近乎指数增长、约 30% 为严重级别，涵盖 OS 命令注入、任意代码执行、内部属性篡改与原型污染等；而代码属性图（AST+控制流+数据流）缺失原型链等动态特性，难以覆盖内部属性篡改与原型污染这两类需要建模引用、对象与作用域的漏洞。ODGen 在代码属性图基础上新增变量节点（对应一个引用）与对象节点（对应一个对象），并引入对象定义边、对象级数据流边、AST 对象查找边与属性边四类新边，逐语句构造并贯穿原型链（如 new 实例与构造函数间的原型链连接），形成新的程序表示。（YouTube EP9WBCWm-Cydk，[7.8-314.5]，L1）
- 〔USENIX Security（推测）〕ODGen 的漏洞查询与零日挖掘结果。检测内部属性篡改时查询赋值 AST 节点、验证左侧属性可被攻击者控制且属内部属性（在原型链上的对象）、污染对象随后被使用；原型污染、注入类与不当文件访问等也以图查询表达。工具 ODGen 由对象依赖图表示与查询、JavaScript 解析器与抽象解释三部分组成、完全开源，共报告 2964 个漏洞，按热度核查 Top 264 包得到 182 个确认、70 个 CVE 标识；零日按应用层、间接包级与直接包级三种威胁模型分析，假阴性率约 26%，过半数包代码覆盖率超 80%、90% 的包 30 秒内分析完成，工件评估获 available、functional、reproduced 三枚徽章。（YouTube EP9WBCWm-Cydk，[314.5-636.8]，L1）
- 〔SREcon〕Chubby 锁服务二十年的诞生与用例堆积。主讲人 Salim Virji（2018 年起任 Google Chubby 的 SRE 技术负责人三年）与 Mox（2022 年离开 Google 加入 Snowflake）回顾：Chubby 最初为 GFS（谷歌集群文件系统）的主节点选举而建，由 Mike Burrows 设计，提供类 Unix 键空间的文件 API（lock/unlock、少量数据读写）与 watch 通知机制，以 5 副本 Paxos 保证正确性与强一致读，锁为建议性质。上线一两年内即堆积了配置推送（写文件触发回调同步发布配置）、服务发现（免 DNS TTL，与 Borg 共同演化）与公司级 ACL 等用例，而早期 --gfs_user 字符串任意可传、ACL 信息又存于 Chubby 自身形成潜在循环依赖，为后续问题埋下伏笔；涌现模式包括 5 个专用副本的“宠物”化（当数十组五机实例存在时成为灾难）、复杂性与可靠性相悖、watch 带来的海量读流量引发级联故障而需加读代理。（YouTube EP9XZPfzjyi8A，[15.8-1046.9]，L1）
- 〔SREcon〕Chubby 二十年的四条教训与反思。教训一：单一共享基础设施存在公地悲剧，需可问责与隔离——最初靠“Chubby SRE Gooning Tool”棒球棍式人工约束，后基于底层认证授权体系实现按方法按客户端限流；教训二：好的 API 设计无价，文件 API 造就快速采纳，也印证 Hyrum's law（一切可观察行为都会被依赖，见 hiramslaw.com）；教训三：先发劣势——为避免循环依赖把定制代码烙进核心，导致无法采用 gRPC 新特性与分布式追踪，历经数年密集重构才补上；教训四：迭代有价值但也可能失败——读缓存与直写代理成功，而要求客户端双写的并行 Chubby 部署因引入延迟、SRE toil 加倍，约一年后下线，应果断移除。收尾讨论“Chubby 是文件系统吗”：不管为何而建，只要允许用户存取字节，你就在运营存储系统；建议多租户系统的配额与可观测性从第一天内建（遥测数据曾导出到 BigQuery 做事后分析），并逐步把锁定/配置推送/服务发现拆成独立 API、各自可切换后端实现。（YouTube EP9XZPfzjyi8A，[1046.9-2096.4]，L1）
- 〔NDSS（推测）〕Stalloris：RPKI 降级攻击。主讲人 Donika Mirdita（合作者含 Tomas Havacek、Filip Jaitner、Haya Shulman、Michael Weidner）介绍 RPKI 以 ROA（网络前缀与被授权源 AS 号）保护 BGP 路由，发布点中的 manifest 是入口、有效期常仅数小时至数天；RP（relying party）定期查询各发布点、验证 ROA 后下发路由器，无效路由被丢弃，但“未找到”的路由仍被放行。攻击者注册合法发布点后即可预测各 RP 的查询时间与间隔，通过触发 DNS 名字服务器限速或压垮发布点本身阻止 RP 在刷新间隔内更新，等 manifest 过期后整个发布点不再被处理，ROA 在路由表中从 valid 变为 not found，实现 RPKI 降级、前缀重新可被劫持；优化版攻击利用 RP 5 分钟至 2.9 小时的内建超时，通过重新委托构造数百上千节点的子发布点树，把停滞时间放大为树的规模×单点超时。（YouTube EP9XfOr3e3ABQ，[8.9-342.7]，L1）
- 〔NDSS（推测）〕RPKI 脆弱性成因与攻击可行性测量。成因有三：25 个测试发布点对应的名字服务器中 21 个存在可被利用的限速（其中 2 个限速低至每秒 3-4 个响应）、RP 按稳定可观测的间隔刷新缓存且超 70% 的互联网 manifest 有效期不足 48 小时、发布点可无限制地重复委托资源构造停滞树。实验遵循负责任做法：在实验室进行、停滞仓库不对外可达、限速探测与 DNS 运营者协商且单次不超过 6 秒；几乎所有 RP 都沿用源码默认刷新间隔，攻击可用现成开源软件实例化。计算得优化版攻击平均每秒约 4800 包、最坏约 10 万包即可阻止连接，属现实可行的攻击能力；结论是 RPKI 即便客户端实现正确仍易受降级攻击，限速与停滞的攻击门槛低、代价小、影响不成比例地大，且仅靠 RP 管理员人工查日志才能发现。（YouTube EP9XfOr3e3ABQ，[348.3-681.7]，L1）
- 〔会议不详〕基于 M3 的分布式能力系统设计。主讲人 Matthias Hille（与 Niels Asmussen、Pramod Bhatotia、Hermann Härtig 合作）提出把能力（指向资源的指针加访问权限，含能力树、委托与撤销）在分布式系统全局强制执行，并按范围、实施方式与可扩展性调研 seL4/Fiasco（范围限于缓存一致性域、经 MMU 实施）、M3（硬件软件协同设计、经 DTU 与片上网络）与 Barrelfish（可扩展到 32 核）等系统后，选择 M3 作为基础。M3 在专用特权核上运行一个内核，远程配置应用核的 DTU 使其只能访问有权限的资源，系统调用经消息传递完成；本系统扩展为多内核分区设计，各内核管理本分区应用核与能力，跨分区关系用“分布式数据查找”解决，能力 ID 作为 fat pointer 标识所属分区。并发展示并发撤销/委托的竞态：撤销被误判完成而资源仍被第三分区进程持有，或撤销与委托交错产生无父的“孤儿”能力带来安全风险，解法是双向握手（先预留能力 ID 再确认连接）并对撤销采用分布式 mark-and-sweep 算法。（YouTube EP9_vR8anr6d8，[10.2-580.2]，L1）
- 〔会议不详〕能力系统评估与问答。在 Gem5 仿真（640 个乱序核）中回放 Linux 录制的应用轨迹（SimpleScalar 中实现全部系统调用），OS 服务为使用能力系统的内存文件系统：按文件区段授予内存能力、越界续授、关闭即撤销；选取 tar/untar、find、SQLite、LevelDB 与 Postmark 等应用，512 个应用实例并行时 Postmark 达每秒 34.8 万次能力操作。11% 的核用于 OS 时并行效率达 72-78%，Nginx 压测下 32 内核/32 服务配置几乎线性扩展。问答环节 John Criswell（罗切斯特大学）追问委托与撤销来源（文件系统以类似 Unix 文件描述符的方式授予内存能力），另有听众建议与 Paxos/Raft 状态机复制类比，作者认为能力管理并无选主排序需求，且系统中不广播能力副本、始终知晓能力位置是可扩展的关键。（YouTube EP9_vR8anr6d8，[580.2-1199]，L1）
