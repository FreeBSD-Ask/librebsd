- 〔USENIX Security '19〕Chrome 安全团队的 Charlie Rice 报告 site isolation 已全量上线于 Windows、Mac、Linux 与 Chrome OS：初衷是为渲染引擎漏洞提供第二道防线、使跨站数据不再泄漏给攻击者，意外收获是它也成为抵御 Spectre 等瞬态执行攻击的关键措施〔00:11〕。动机可上溯到十年前浏览器多进程化：把浏览器进程拆成特权进程与沙箱化的渲染进程、把大部分攻击面放进后者，使攻击者即便已知浏览器漏洞也难于逃逸去装恶意软件或访问本地资源〔01:29〕。但攻击者网站仍能把受害者数据带入同一渲染进程——加载跨站 iframe 或弹出窗即可〔01:56〕。于是要对付两类新型攻击者：renderer exploit 攻击者知道浏览器漏洞、可在渲染进程内执行任意代码并向浏览器进程发送伪造 IPC，企图读取用户在别处的账号〔02:29〕；另一类随 Spectre 出现，JavaScript 或 WebAssembly 即可在渲染进程内对 CPU 状态做侧信道、读出跨站 iframe 中的内存〔02:57〕。后者性质不同：力量更弱，不能执行任意代码、不能伪造 IPC，却完全不依赖浏览器漏洞——即便实现完全正确也能成功，故同源策略必须两头都防〔03:12〕。架构含两大要点：为单一站点原则配置专属渲染进程，进程内所有文档与 worker（含 iframe）都受限于该站点；以及过滤流入进程的信息、尤其来自网络的数据〔03:57〕。最大的工程是 out-of-process iframes：把现成渲染引擎（此处为 WebKit）并行跑多份用于多标签页还算温和，而 iframe 出进程意味着要把整个渲染引擎改造为按 frame 粒度工作——绘制需跨进程合成、要确定输入事件该发给谁、要为别的进程里的 frame 建表示以便发消息，而页内搜索这类原先假定同页同进程的功能一下子成了分布式系统，部分结果可能慢回、乱序甚至不回，还不得泄漏给其他进程〔04:43〕。这构成绝大部分工作量，也是为让 site isolation 成为可能而更新的四十多万行代码的主体〔05:48〕。另一类挑战是数据过滤：cross-origin read blocking 必须放行任意站点的图片、JavaScript 与 CSS，却不让攻击者以图片名义把别站的机密 HTML 拽进渲染进程〔06:05〕。只按 content type 会误伤被标成 text/html 的合法 JS，而现成嗅探也不行——以 HTML 注释开头的内容对 JS 引擎同样合法，所以必须自写嗅探逻辑确认确为 HTML、XML 或 JSON 再拦截〔06:53〕（YouTube EPYvVwrcaxxbQ，[11-433]，L1）
- 〔USENIX Security '19〕对不能向浏览器进程说谎的内存披露型攻击者，专属进程加过滤已足够；但 renderer exploit 还能发恶意 IPC 索取超出其权限的数据，于是浏览器进程记录每个进程被锁定于哪个站点，发现越权索取即终止该渲染进程，作为第二道防线〔07:33〕。实践意义有据可查：二〇一四至二〇一八年间 Chrome 共有九十四例 universal cross-site scripting 之类的高危漏洞，平均每年约二十例〔08:29〕。网站开发者从此被透明升级——cookie 与保存密码的认证、受 CORB 保护的机密数据、postMessage 的源与目标源校验、防点击劫持的 X-Frame-Options 与 CSP frame-ancestors、以及对存储与权限的使用，即便渲染进程已沦陷也由浏览器进程强制〔09:15〕。对照瞬态执行攻击的其他路线：浏览器最初从平台移除高精度定时器，把 performance.now 做得更粗并拿掉共享数组缓冲区等隐式定时器，但极粗的定时器被放大后仍可完成攻击、带宽仅略降，同时伤害了确实需要精密定时器与 WebAssembly 线程的开发者，故不作为长期缓解〔09:53〕；其后厂商转向编译器与运行时缓解，指望 JIT 输出不出该攻击所需的代码模式，同样收效不佳——诸如依赖 store-to-load forwarding 的 Spectre variant four 极难以此方式缓解，V8 团队的论文 Spectre is here to stay 从更深层面说明此路不通〔10:39〕。于是只剩把数据置于攻击者够不到的地方，这正是 site isolation 的思路，它对能留在进程之外的数据有效抵御同进程变体；而微架构数据采样一类跨进程乃至针对内核的变体仍需与操作系统和硬件缓解配合，由于操作系统与硬件看不到浏览器内部的站点抽象，两类缓解必须并存〔11:18〕。局限方面：site 定义为 scheme 加注册域名（如 https://google.com），比同源策略的 origin 粗，因 document.domain 允许在站点内运行时改 origin；该特性若能弃用最好，同时提供站点级 opt-in 的 origin 级隔离〔12:02〕。CORB 尚未覆盖的数据类型上，提供 opt-in 的 cross-origin resource policy 响应头并扩展到 PDF、zip 等格式，但长远更寄望于默认 same-site cookie 等生态级改变〔12:49〕。工程化同样关键：未启用时用户九十九分位已有三十五个渲染进程，朴素实现会推到约八十，靠同站进程复用等优化压回五十三；渲染进程更多却更小、生命周期更短、碎片更少，总内存开销在低分位仅百分之十三、高分位百分之九〔14:35〕；配合导航与输入事件延迟优化，甚至因并行度提升了主框架响应〔15:46〕。结论是：为渲染引擎漏洞准备的这道防线同样成为抵御瞬态执行攻击的最好路径，且该平台尚未上线 Android 与移动端〔16:05〕；问答中说明 CORB 检查发生在沙箱外的特权网络服务进程中、先审视响应头与内容再放行〔17:28〕，性能收益主要来自跨站 iframe（多为广告）不再拖累主页以及预留空闲渲染进程以减少跨进程导航延迟〔18:12〕，跨站 iframe 数量亦有上限以防 DDoS〔19:22〕（YouTube EPYvVwrcaxxbQ，[433-1168]，L1）
- 〔NSDI '25〕北京大学 Nai Qianzheng 介绍 MeshTest：随着云应用愈发松耦合、微服务各自实现并维护 RPC 通信逻辑给开发者带来沉重负担，service mesh 因此接管服务间 RPC 通信，开发者只需在 mesh 上定义网络功能；mesh 提供流量管理、认证、安全与可观测性，其中流量管理是根本，因为它决定请求被送往何处以及如何重写〔00:15〕。功能丰富必然带来复杂度：mesh 的输入是通信配置，包含数十种 CRD 与百万级选项，输出则是应对任意网络请求的抽象网络行为，代码库因此极其庞大——Envoy 逾一千个组件、超三十万行代码，而复杂度总是伴随缺陷〔02:00〕。演讲者展示由其工作发现的 Envoy 真实 bug：当两个 service entry 主机相同而端口不同时，其中一个 entry 不生效、最终导致服务不可用，根因是 EDS 的规则合并实现错误，既有测试并未覆盖这种规则合并情形，报告后开发者已修复〔02:35〕。重要原因是测试不足：现有测试大多是单元测试（Envoy 逾一万条），端到端测试极少；对比之下 Elasticsearch 与 Lucene 两个最著名的检索系统分别只有一百六十条与三十条端到端测试〔03:15〕，而前述 bug 用端到端测试很容易覆盖、单元测试却很难命中，因为它源于功能之间的交互。因此测试必须分两步：先生成各种 service mesh 配置，再检查 mesh 是否正确实现了该配置〔03:57〕。第一个挑战是构造输入配置必须端到端有效——资源需彼此配合、从源服务一路连接到目标服务形成一条 entry 到 exit 的服务流路径，且要通过每个功能自身的校验规则〔04:22〕；符号执行会在选项上爆炸，模糊测试又难以组合成服务流路径并通过校验〔05:27〕。第二个挑战是正确性检查：mesh 输出是抽象网络行为、无法直接核对，只能核对单个请求是否被正确处理，而要覆盖整体正确性需要处理任意请求，于是必须挑选一个有限、全面且具代表性的请求集，为每个代表性请求推断正确行为，同时检查器必须自动、因为它要检查大量输入〔05:42〕（YouTube EPYxtEqGGMfxI，[15-362]，L1）
- 〔NSDI '25〕MeshTest 是一个 service mesh 系统的自动端到端测试器，输入为资源定义、资源连接定义与 CRD 解释器，自动产出测试结果；它由端到端配置生成器与自动 oracle 检查器组成，两者既可在 MeshTest 中协同，也可单独被其他工具集成〔06:23〕。四个阶段依次推进。第一阶段从服务流入手，这是端到端输入配置的关键——服务流刻画请求如何在资源间移交并最终路由到目标；作者用一个领域专属的服务流骨架模型表达高层布局，包括测试使用哪些资源、如何连接以构成服务流，并显式揭示资源间交互如优先级竞争与请求移交；生成思路是交互之处最易出问题，故从资源交互的种子出发向两端延展到 entry 与 exit，组合出覆盖全部资源交互的完整服务流〔07:16〕。第二阶段把骨架转成完整配置：先用连接器字段落实骨架指定的服务交互（最直接的做法是让资源 A 的字段 A 与资源 B 的字段 B 取同值），再用基于约束的模糊测试扩展配置、确保不破坏任何校验〔08:22〕。第三阶段构建 oracle：用控制流图精确建模服务在 mesh 中的行为，并纳入优先级竞争、默认规则等配置中并未明写却真实生效的低层细节，图中每条路径即一个代表性请求；为使图自动构建，作者利用 mesh 流量管理内在的三阶段架构，先为每类资源写一个小解释器，再通过解决优先级选择与补入默认规则把各子 CFG 连接起来——写解释器约需两人周人力，此后便全自动，已为 Envoy 与 Linkerd 建好解释器并提供 API〔09:35〕。第四阶段据 CFG 生成真实请求：在 CFG 上做远程执行、每条路径对应唯一请求，借助测试服务器识别请求归属哪条路径以及经 mesh 处理后应为如何，再由测试驱动程序核对每个请求的落点与内容并与求解器算出的期望比对，同时检查系统是否 panic 或报错〔10:25〕。整个流程从高度抽象的服务流骨架到配置、再到具体 CFG、最终到真实服务请求逐级细化，用不同粒度建模既避免生成阶段爆炸又保证 oracle 阶段准确〔11:05〕。对 Envoy 与 Linkerd 两个最广泛使用的系统测试共发现二十三个新 bug，十九个被确认、十个被修复〔11:37〕；生成器每秒产生两千五百份配置，oracle 平均以二十九个不同请求检查每个输入，且保证成对资源交互百分之百覆盖，无需改动被测代码库、只有 mesh 规范变化时才需更新〔11:59〕。文中另一个真实 bug 是请求 foo-api 返回 not found，只在两个资源主机相同、规则不同且优先级较高者带 delegation 规则时出现，既有测试未捕获主要因为资源间关系颇为刁钻〔12:39〕（YouTube EPYxtEqGGMfxI，[362-819]，L1）
- 〔USENIX Security '14〕Nikolaos Karapanos 提出：TLS 客户端认证协议（尤以 TLS Channel ID 为代表）无法单独有效阻止 TLS 中间人攻击，必须为浏览器通信引入 invariance（不变性）——一个弱于认证却更易达成的性质〔00:09〕。动机是服务器认证本身就有问题：攻击者可通过攻陷证书颁发机构或窃取服务器私钥来冒充服务器，即便什么都不发生，用户也常会点过警告继续〔00:25〕。假设攻击者成功向用户冒充了合法服务器，那么只要他在网络上位置得当，就能拦下连接实施 TLS man in the middle：用户发往合法服务器的 HTTP 请求被截获、其中密码或 cookie 等凭据被窃取，随后攻击者以另一条 TLS 连接向服务器冒充该用户、进入并控制其在线账号；这既可用于监视用户，NSA 等政府机构也被怀疑用此类攻击实施大规模监控〔01:05〕。本工作聚焦较新的 TLS Channel ID 提案：它已被 Google Chrome 与 Google 服务器实验性支持，而由 Google、微软、Visa、MasterCard、PayPal 等组成的非营利组织 FIDO Alliance 发布的规范也把 Channel ID 式认证视为抗中间人方案〔02:12〕。防 TLS 中间人有两条路：其一从终端入手、最好一开始就阻止服务器冒充，即修复有缺陷的证书机构信任模型，代表方案有证书固定与 certificate transparency、convergence 等〔04:02〕；其二阻止用户冒充——即便攻击者仍能冒充服务器，也无法滥用凭据完成攻击，Channel ID 及其上的客户端认证协议走的正是此路〔04:37〕。Channel ID 是浏览器首次连接某域名时临时生成的密钥对中的公钥（可视为一张自签证书），私钥永不出浏览器；握手时浏览器发送该 Channel ID 并用签名证明持有对应私钥，此后该 TLS 连接即由这个 Channel ID 标识，同一浏览器对同一站点重连复用同一 ID、不同浏览器各不同，服务器据此区分客户端〔05:06〕。用法分两阶段：用户首次登录时，FIDO、FIDO U2F 等二次认证协议借 Channel ID 抗中间人；首次登录之后服务器下发一个与该浏览器 Channel ID 绑定的 cookie，即 channel bound cookie，只有在本应的那条 TLS 通道上出示才被接受〔06:52〕。于是攻击者即使用旧手法偷到 cookie 也无法拿来冒充用户——它必须在一个 Channel ID 不同的连接上出示，服务器察觉不匹配即拒收，攻击失败〔08:07〕（YouTube EPZ-mNblnhmXE，[9-509]，L1）
