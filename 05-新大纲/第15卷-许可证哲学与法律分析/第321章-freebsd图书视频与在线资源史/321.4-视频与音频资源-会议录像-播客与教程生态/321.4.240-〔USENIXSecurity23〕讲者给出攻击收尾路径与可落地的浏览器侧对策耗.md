# 321.4.240 〔USENIXSecurity23〕讲者给出攻击收尾路径与可落地的浏览器侧对策耗

- 〔USENIX Security '23〕讲者给出攻击收尾路径与可落地的浏览器侧对策。耗尽 UDP 端口池本身只是拒绝服务，为升级为缓存投毒，攻击者"we release one socket back to the operating system"〔05:53〕并"leak it via WebSocket to the attacker's poisoner"〔06:07〕，从而预知受害者将使用的 DNS 查询端口；随后预置带伪造事务 ID 的 DNS 响应在途，同时让受害者浏览器发起 XHR 触发同域 DNS 查询，事务 ID 匹配后受害者即把恶意条目写入缓存，此后访问 bank.com 一律被引向攻击者服务器。缓解方面，全局端口上限只能治 DoS、多浏览器并发时未必够用，且全局上限本身可被反向用来攻击浏览器，而 fork bomb 问题"currently not mitigated"〔07:08〕；作者为 Chromium 实现了概念验证补丁，核心是"limit the number of processes or sites that can be created per tab"〔07:35〕——为每个标签维护本地限额 L，新建进程即扣减，命中上限即停止渲染并提示离开或留下，选留下仅按固定增量 delta L 放宽，允许攻击者多嵌若干 iframe 却恢复不了攻击能力，同时其余标签照常工作、新标签获得独立限额。以 L 与 delta L 均取 30 实测，"those prevent the fork bomb, prevent denial of service on the browser"〔10:10〕，并对 Tranco 前一千站点回归验证结果"none of the websites triggered our dialogue"〔10:24〕；产物经 Zenodo 与机构 GitLab 镜像发布，演示视频挂在 Chromium 缺陷追踪器。（YouTube EPZYoyh5R4Dn8，[345-681]，L1）
- 〔OSDI '14〕研究者提出 Haven，目标是在完全不可信的云环境中以商用量产硬件安全执行未经修改的应用程序。讲者指出云上与自持机器的根本差别：网络之外还必须"assume that there's malware running in the cloud"〔00:50〕，能攻陷云厂商平台者可直接摆弄你的虚拟机——一周前 Amazon 正因 Xen 权限缺陷重开全部 EC2 节点。云上可信计算基"the trusted computing base of the cloud is enormous"〔01:46〕，涵盖宿主机全部特权软件、管理栈、有管理或物理访问权限的员工乃至执法机构；症结在于层级化安全模型使底层任一层次都能观察或改写上层数据，数据一旦解密进内存用于计算即暴露。既有方案各有短板：HSM 昂贵且只支持少量密码 API；微型可信虚拟化层需要允许触碰客数据的管控接口、对物理攻击无防护，且必须回答"how do you know that some machine somewhere in the cloud is actually running the small secure hypervisor"〔03:52〕——远程证明只做到"not preventing the wrong software from running, but making it possible to detect when the wrong software runs"〔04:24〕，随即把问题推回到信任云厂商自报的期望哈希。因此讲者借安全托管机柜的类比（供应商只供电、冷却与网络，拿不到机内数据）提出"we've termed this property shielded execution"〔06:06〕，即"the stuff you care about is inside the sandbox"式的反向沙箱〔06:10〕；同时承认应用"an application isn't an island"〔09:41〕，系统调用是 Iago 攻击的完美通道，故不逐条校验而是"we admit all of the pieces of the OS that the application directly depends upon"进可信基〔10:41〕。（YouTube EPZatjao5peXo，[10-748]，L1）
- 〔OSDI '14〕讲者随后展开 Haven 的构造并交代性能与遗留威胁。Haven 在宿主内构造一个 PICA 进程作为隔离的用户态地址空间，其中建 enclave 并加载未修改的应用二进制；应用依赖的 Win32 API 由既有库 OS Drawbridge 提供，而 Drawbridge 所需的少量核心原语由新组件 shield module 在一条极窄不可信接口上实现，"The untrusted interface consists of about twenty calls"〔12:51〕，并贯彻策略与机制分离：访客掌管虚拟资源策略（地址布局、线程与调度），宿主保留物理资源策略。shield module 自建内存分配器与 region manager，由它决定虚拟地址并请求宿主在指定地址按指定权限放置页面，再经硬件机制核验；自建私有文件系统为加密且完整性保护的 VHD 上的 FAT；自实现调度器"much like scheduler activations"〔14:11〕以避免信任宿主处理互斥与时序交错；对异常与 CPUID 等指令做处理与模拟，并对所有不可信输入做健全性检查，发现异常即按拒绝服务处置直接 panic。规模约"about twenty-three thousand lines of code"〔15:04〕，其中过半是 FAT 实现。作者据此发现 SGX 四处不足：动态内存分配与保护需新指令、部分异常无法上报 enclave、读时间戳计数器等指令难以模拟，以及 x86 线程局部存储的老问题，并称新版规范已修复。因"we don't have access to a real SGX implementation"〔16:49〕，性能只能建模——每次进出 enclave 刷 TLB、SGX 指令可变延迟、加密内存拖慢整机 DRAM——在最悲观参数下 Apache 与 SQL Server 相对普通虚拟机慢三分之一到三分之二〔17:41〕。遗留威胁以持久存储回滚为最，另有信任宿主授时，未来还想上挂起恢复与加密网络通信；讲者以"why would you trust the cloud when you don't have to"〔19:00〕作结。（YouTube EPZatjao5peXo，[748-1486]，L1）
- 〔USENIX Security '24〕研究者 Jimmy Liu 报告首个围绕漏洞管理全生命周期评估 ChatGPT 能力的大规模实证研究。大型语言模型已被广泛用于问答、数据增强与教育，由于编程语言与自然语言高度相似，研究者倾向用 ChatGPT 做代码相关分析，既有工作也显示它能处理 AST 生成等基础任务；但"they mostly focus on several specific tasks rather than the entire lifecycle of vulnerability management"〔00:53〕，而漏洞管理实为从问题发现、确认、修复到补丁提交的完整链路，各阶段要求对代码语法、程序语义与相关文档有深入全面的理解，因此 ChatGPT 能否在整个过程中直接协助维护者尚不明确。研究从三个视角切入：是否达到主流方法同等水平、提示工程方法如何影响表现、以及每个任务的未来改进方向。方法上作者"compared ChatGPT's performance to eleven SOTA approaches on six vulnerability management tasks"〔02:29〕，覆盖缺陷报告摘要、安全缺陷报告识别、严重性评估、漏洞修复、补丁正确性评估与稳定补丁分类，复用各任务现有数据集与评价指标、手工设计提示模板（含可注入领域专家知识的 expertise 提示与去掉专家知识的通用模板）。首个任务缺陷报告摘要上"ChatGPT can get outstanding performance"〔04:25〕，用户研究显示真实场景中正确性与可读性更佳，因其与大型模型擅长的传统 NLP 任务高度同构。第二个安全缺陷识别上，配合高级提示与模型"ChatGPT outperformed two baselines"〔04:59〕，但"cannot obtain capability on par with"专用方法 DKU〔05:16〕；单示例提示会让它把含有示例中无关词的报告误判为安全相关，"such as tab and open"〔05:21〕，更严重的是存在概念幻觉，"it thinks memory leak and null pointer dereference are not security related"〔05:54〕，而在 expertise 提示中直接补充这些属于安全缺陷后取得最佳表现。（YouTube EPZeIgqpc_rII，[8-367]，L1）
- 〔USENIX Security '24〕研究继续覆盖剩余四类任务并总结共性结论。严重性评估要求把函数描述映射到 CVSS 指标，表现略逊于主流方法但高级提示提升明显；作者转而让 ChatGPT 从样例中自总结任务知识，这种 self-heuristic 提示"improves ChatGPT's performance significantly"〔07:35〕，以自启发方式提升自身在困难任务上的表现是值得探索的方向。漏洞修复任务中"ChatGPT can fix ten out of twelve vulnerabilities"〔07:53〕，而基于程序分析与其它大模型的方法分别修复十处与八处；失败主因是提供的漏洞相关上下文不足，作者建议结合更先进的程序切片来供给针对性上下文。补丁正确性评估上，配合高级提示与模型可与主流方法相当；注意到三个数据集中两个仅含代码、CodeQuadrant 仅含补丁描述，因此作者提出 code+description 提示使其接近 CoT，随后加做 code-only 提示发现多数评分更好，说明"providing patch descriptions even makes a negative effect"〔10:00〕——人工分析表明同时给代码与描述时它会去比对改动是否契合描述而非判定补丁正确性，由此得出"more information is not always better"〔10:18〕。稳定补丁分类上略逊主流，零样本与单示例提示下"ChatGPT tends to report all patches as stable ones"〔10:44〕，根因是不理解何为稳定补丁，在 expertise 提示中补入定义后显著改善。总结称这是首个大规模评估，"we compare ChatGPT with eleven SOTA approaches on six vulnerability management tasks"〔11:18〕，结论是若干任务上能力优异并揭示瓶颈，全部提示模板与代码随论文链接开放。（YouTube EPZeIgqpc_rII，[367-726]，L1）
- 〔NSDI '22〕数据中心之外的容器供给远比其应有速度更慢，而云上的先进优化非但帮不上反而使问题更糟，根因在于不适合边缘环境的设计决策。多伦多大学 Mickey Gabel 报告开源容器加速器 Starlight——"an open-source container accelerator that decouples the structure of containers from how we provision them"〔01:14〕——使云内与边缘的新建 worker 与更新都更快、几乎无开销且向后兼容。容器以分层镜像栈描述其文件系统，天然便于复制并叠加配置层来打包与部署；部署加速对容器即服务（Amazon ECS、Azure Container Instances）、FaaS 弹性扩容、缩短安全与软件更新窗口以及应对边缘用户移动性都至关重要。但边缘自身带来高时延低带宽链路、通常缺乏本地注册表或缓存、节点被激进复用与需频繁重配置等约束。作者取三个流行容器在 100 Mbps 广域链路上把往返时延自 0 逐步推到约 300 ms 的地理分布典型上限，结果显示"provisioning time can triple as we move from the cloud to the edge"〔05:16〕，而且增长快于纯下载时间；云上行之有效的按需取文件方案 EStarGZ 在边缘同样扩展性差，时延超过约 150 ms 后甚至"can be even slower than the containerd baseline"〔06:20〕。两个设计病根随之浮出：pull-based 部署中 worker 只索取本地缺失的压缩层，多条 HTTP 请求在注册表并发上限下排队——"The result of these multiple requests is queuing"〔07:01〕——按需逐文件取件方案进一步放大请求数；分层结构又把每文件元数据嵌进各压缩层，早启动必须为每一层额外请求元数据增加往返，且元数据任何小改都要把整个文件复制到上层，例如升级 Node.js 要下载 39 MB 镜像而"Only 3.7 megabytes of files are actually new"〔08:24〕，因此只改 worker 或只改注册表都不够，必须重做整条部署流水线。（YouTube EPZfIJz-zSXJU，[15-564]，L1）
- 〔NSDI '22〕作者由此提出 Starlight，一套以文件为粒度、push-based 的新供给协议及其实现。核心产物是 update delta bundle：只含 worker 尚缺文件内容并带齐早挂载所需全部元数据的供给包，其设计由四项决策驱动——协议 push-based，"the worker makes a single request to the cloud"〔09:30〕，由云侧负责送达其所需一切；只发送 worker 需要的内容，故初始请求须声明其已有文件内容；"we send all metadata for all files across all layers before any of the actual payload"〔09:43〕；以及"works at file granularity instead of container images that work at layer granularity"〔09:54〕从而可为包去重。云端据此算出版本一至版本二的差异并生成包：包头给出版本二的合并展平文件系统目录表，逐文件列出名称、内容哈希、属性等挂载所需元数据与源层指针，内容未变仅元数据变化的文件只带更新后的元数据出现，内容新增者则在包体中给出压缩偏移。实现建立在 containerd 之上，云侧 proxy 中介 Starlight worker 与任意标准注册表，查询目录数据库后"the proxy computes this delta bundle individually on demand for each file"〔12:39〕，而非为每种可能更新预生成膨胀的包；worker 侧以 StarlightFS 替代 overlayFS，得以在文件内容尚未下载完就启动容器并规避阻塞。评估选取二十一个流行容器，用 Linux traffic control 控带宽与时延做受控实验并在横跨三大洲的真实广域网验证：Starlight 在全部时延区间均为最快，"Starlight is the fastest provisioning approach"〔14:56〕，即便云内亚毫秒时延亦然；因 push-based，时延升高时其供给时间只随带宽时延积变化，不像 containerd 与 EStarGZ 那样急剧恶化；借早启动它甚至比下载完所需数据本身还快，更新场景提速"four to five times faster"〔16:23〕。YCSB 两百万次操作、读写各半的负载下（内存与磁盘数据库各测），Starlight worker 启动更早、完成更快且峰值性能与基线持平；作者亦指出未来可在在线收集访问轨迹、预测文件访问顺序乃至多容器联合优化等方向继续优化，代码已开源。（YouTube EPZfIJz-zSXJU，[564-1113]，L1）
- 〔USENIX Security '24〕Signal Messenger 工程师 Ralf 与 Kartik、Franciscus、Charlie 报告对 Signal 后量子密钥协议 PQXDH 的形式化验证工作，其主旨是"the story ... really isn't so much about our protocol PQXDH. it's about formal verification and how it can speed development and clarify security of real world protocols like the Signal Protocol"〔00:28〕。背景上，Signal 协议已十年，由 Moxie Marlinspike 与 Trevor Perrin 设计，由 X3DH 握手建立会话、再由 double ratchet 持续密钥协商，给出前向保密、后陷密安全、双向认证与可否认性等保证，现保护全球数十亿用户通信，但实践中依赖 Curve25519，显然不是后量子安全的。作者的初始目标相当克制——"we wanted to provide harvest now decrypt later protection for our users without taking away any of those Diffie Hellman based security guarantees"〔02:31〕——即防止今天被录制的流量将来被量子计算机解密。PQXDH"really a very small addition to X three DH"〔02:58〕：在若干次 Diffie-Hellman 之外增加一个后量子安全 KEM 公钥用于封装共享秘密，与各 DH 共享秘密拼接后送入 KDF 得到会话密钥 SK；密钥来自"untrusted key distribution server"〔04:00〕，SPK 与 PQ KEM 公钥由身份密钥签名，KEM 实践中用 Kyber 第三轮、其他密钥用 Curve25519，初始消息为带关联数据（身份密钥与公钥编码的拼接）的 AEAD 密文。作者把初版规范与实现交外部评审，用"ProVerif and CryptoVerif"〔06:27〕双工具推进：前者在符号模型下几乎全自动、此前已用于 Signal 与 TLS 1.3，后者在计算模型下给出机器检查的 game hopping 证明且经后量子扩展具备"post quantum sound"性质〔07:05〕；模型含任意数量通信方、带外身份密钥校验、不可信分发服务器与单条加密消息，威胁模型允许身份密钥随时泄露、量子对手可算离散对数、KEM 安全性未来可能崩塌，整个流程是设计者、实现者与证明工程师之间快速交互的过程。（YouTube EPZg9WJlQnXoc，[8-436]，L1）
