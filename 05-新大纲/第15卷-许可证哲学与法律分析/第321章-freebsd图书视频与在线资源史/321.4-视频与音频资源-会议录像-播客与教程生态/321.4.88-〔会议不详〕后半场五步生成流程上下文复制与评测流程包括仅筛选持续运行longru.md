- 〔USENIX ATC（推测）〕与导师 Amit 及 Microsoft Research 合作伙伴（Shadi、Sebastian）共建的无服务器（serverless）编排系统 Unum 报告。报告指出 serverless 原生构建大型应用的困难（聚合等有状态模式难以实现、at-least-once 执行语义带来端到端正确性与成本问题、非确定性函数导致输出分歧），而现有编排器方案要么是用户在 VM/容器中自部署的编排器（牺牲免运维与细粒度按量计费），要么是提供商托管的编排器如 Amazon Step Functions（昂贵且受限、难以做应用特定的数据存储选择与性能优化）；该工作反其道行之，在应用层不加任何基础设施服务地解决编排问题：Unum 构建于基本 serverless 抽象之上、无需新服务或 API 变更，与 Step Functions 支持同样的高层编程接口并保证 exactly-once 语义、支持有状态模式，且更可编程、更便宜、多数场景性能更好，应用可在 AWS 与 Google Cloud 间零代码迁移；编译期把应用转成中间表示（IR），将转移边指派给尾节点。（YouTube EPFdLxvGEcjxM，[12.7-517.1]，L1）
- 〔USENIX ATC（推测）〕后半场：运行时执行、有状态模式、exactly-once 的实现与评测。运行时库包裹用户代码透明执行 IR 编排指令；聚合等 fan-in 模式让每个尾函数完成后把结果写入数据存储并检查完成情况，Unum 用 set 数据结构做协调，把每节点 N-1 次读降为 1 次，并依赖数据存储强一致性避免两个分支互等死锁；exactly-once 通过对节点唯一命名的检查点实现——并发重复执行的结果被丢弃，崩溃重试读取既有检查点甚至直接跳过用户代码；实现基于 AWS Lambda+DynamoDB 与 Google Cloud Functions+Firebase 的运行时库及把 Step Functions 编译为 Unum IR 的前端工具链；评测显示单转移时延在各数据尺寸下均快于 Step Functions，512 个并行分支下端到端时延低逾 4 倍（Step Functions 从约 20 分支起限流，而 Unum 可扩展到 Lambda 允许的约千级并发），真实应用快至 2 倍、成本省至 9 倍；Step Functions 应用的主要成本是编排服务本身，而 Unum 的主要成本在数据存储，换用更便宜的数据存储（如 Cosmos DB）或底层服务改进即可自动受益。（YouTube EPFdLxvGEcjxM，[555.3-1066.1]，L1）
