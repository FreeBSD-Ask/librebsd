# 321.4.77 〔FAST〕DeepSketch去重后数据压缩中参考搜索的问题与核心思路ETHZ

- 〔FAST〕DeepSketch：去重后数据压缩中参考搜索的问题与核心思路。ETH Zurich 高级研究员兼讲师 Jisang Park 指出，去重后增量压缩按去重、增量压缩、无损压缩的顺序可最大化数据缩减比，但现有 super-feature 数据草图技术参考搜索精度有限，在通用 PC 负载上只提供穷举搜索约 60% 的数据缩减比，核心问题是高假阴性率——对不算高度相似但仍能受益于增量压缩的块生成不同的 sketch。解决思路是 learning-to-hash：训练深度神经网络、用最后一隐层生成二值哈希作为块 sketch，以 DNN 生成器替换 super-feature 生成器，使两块增量压缩收益越高 sketch 越相似。（YouTube EPC_yfI9GJH5Q，[13.2-441.2]，L1）
- 〔FAST〕DeepSketch 的 DNN 训练设计与评估。针对目标数据缺乏语义信息、维度极高导致训练集多样性不足的问题，采用先对无标注数据聚类、再以聚类结果做监督学习的训练方式：提出动态 k-means（DK 聚类）解决 k 值未知与层次聚类开销大的矛盾，并对簇的非均匀分布做重采样；随后按 greedy hash 方法的两步迁移学习训练出仅含 3 个卷积层与 2 个全连接层的轻量 sketch 生成器。在 11 个工作负载上，DeepSketch 相对最先进的 super-feature 技术 Finesse 大幅提升数据缩减比，对未参与训练的 Stack Overflow 负载同样有效，两者结合可互补，但与最优仍有差距且对写带宽引入非平凡开销。（YouTube EPC_yfI9GJH5Q，[454.1-875.8]，L1）
- 〔USENIX ATC〕gg：把日常任务外包到数千核云函数的框架与动机。讲者用具体例子说明外包需求：单核笔记本编译 Google Chrome 需 16 小时、运行 libvpx 单元测试需 1.5 小时、渲染《怪兽大学》单帧需 29 小时，而这类任务偶发、暖集群昂贵（EC2 上一万核约 400 美元/小时）。方案一是以内容哈希命名的轻量容器 thunk（包含可执行文件哈希、参数、环境与输入输出清单）管理软件依赖，方案二是用哈希把 thunk 链接成 GG 中间表示（GGIR）把整个作业一次下发，避免笔记本与云之间多余往返；冷集群启动太慢，而 AWS Lambda 等无服务平台可在数秒内提供一万个 worker。（YouTube EPCc_MVldSijA，[14.6-608.5]，L1）

- 〔SREcon〕把 SRE 模型引入传统企业的前提与组织设计（SREcon Düsseldorf 场次）。讲者（兼具 Google、Stripe、Dropbox 等公司经验）强调执行管理层 buy-in 是前提，SLO 是客户满意度与市场竞争的代理指标而非 IT 团队考核，需业务、产品与交付方共同担责，否则 SLO 永远可被妥协。建议优先内部培养 SRE（用少量职能负责人与资深工程师做种子、可培训新毕业生而非设门槛），SRE 是“造工具让全公司都能跑运维”的力量倍增器而非接管运维：服务责任最终在服务所有者，Dropbox 的 on-call 由 SRE 与产品开发分担；Stripe 把 SRE 用作 foundation 团队的“销售工程师”，用 Carrot 工具与全员生产就绪评审提升韧性，推广共享 on-call 可借助按小时分页热力图展示运维工作量。（YouTube EPCg877bv_xig，[5.7-1460.2]，L1）
- 〔SREcon〕以代理（proxy）为核心的遗留系统整合策略与量化风险。针对无法纳入同构云原生基础设施的遗留系统，建议用代理把观测能力带回既有体系：日志代理把非结构化日志经 protobuf 与模式匹配转为结构化日志、监控代理抓取旧 SNMP 数据与新监控并行运行避免割接阵痛、YouTube 曾用代理衔接旧数据中心与 Borg 并需保持配额配置同步（否则圣诞节会超出代理配额堆积流量）、Vitess 代理实现 MySQL 水平分片、Envoy 是最全面的开源代理范例。在强监管行业，SRE 的不可变构建产物、CI/CD、可观测性与量化风险矩阵（用年化停机分钟而非高中低分级，参考 Matt Brown 在 SREcon Americas 的报告）反而受监管者欢迎；最后推荐《Accelerate》（Jez Humble、Gene Kim、Nicole Forsgren）论证同行高上下文实时评审胜过外部变更控制板，并以 ratchet 惯例只对新增/被触碰代码应用新 lint 规则。（YouTube EPCg877bv_xig，[1549.5-2906.3]，L1）
- 〔USENIX Security〕用分层硬件模型验证商品化多处理器 KVM 虚拟机监控器。哥伦比亚大学 Xuewei Li 指出虚拟化依赖的 hypervisor 日益复杂、漏洞可让攻击者获得全部托管 VM 数据，而 seL4、CertiKOS 等既有形式化验证工作依赖过于简化的硬件模型（如无 TLB），其证明在真实多处理器服务器硬件上可能不成立。方案是分层硬件模型：为依赖 TLB 等低层特性的软件层匹配含完整特性的详细机器模型，为不依赖低层特性的高层匹配简化抽象模型（只要能证明两种模型下软件等价）；SeKVM 在先前工作基础上借助 ARM 虚拟化扩展把 KVM 重构为小的 KCore 与大量 hypervisor 服务 Kserve，只需推理 KCore 即可验证整个 KVM，并用“unmap 页表后未正确 flush TLB 会破坏 VM 间隔离”的例子说明正确 TLB 管理至关重要。（YouTube EPCh-7bGbJ6SI，[8.5-317.8]，L1）
- 〔USENIX Security〕页观察者（page observer）建模与验证、性能结果。引入 page observer 表示所有可能经 TLB 或页表观察某物理页的主体（VM 或 Kserve）集合，证明 KVM 中可更新页表的层保证经 TLB 可观察的页与页表一致（TLB 未及时 flush 时经 TLB 可观察页会成为页表超集，据此可检测错误管理），再把含 TLB 与多级页表的详细模型精化（refine）为高层可用的扁平映射抽象模型。最终用 Coq 验证 KCore 全部实现的功能正确性（约 3.8K 行 C 与汇编代码、模块化为 34 层）以及 SeKVM 对 VM 机密性与完整性的保护在多处理器服务器硬件上成立；性能上相对未修改 KVM 开销适中，而建模无标记 TLB、频繁 flush 的验证实现会带来显著 VM 性能损失。（YouTube EPCh-7bGbJ6SI，[318.3-646.7]，L1）
- 〔USENIX ATC〕DBE：加密前去重的新范式与 DEBE 系统设计动机。香港中文大学的 Zuoru Yang（与 Jingwei Li、Patrick P. C. Lee 合作）论证现有“加密后去重”（DAE）范式的三大局限：逐块派生密钥带来高密钥管理开销、密文高熵不可压缩（客户端先压缩会泄露压缩后块长）、密钥服务器成为单点攻击面且确定性加密易受频率分析。转向先在明文块上去重、仅对非重复块加密的 DBE 范式：非重复块可用内容无关密钥按传统对称加密处理、去重后可再压缩、且无需密钥服务器。系统基于 Intel SGX 屏蔽执行（enclave，EPC 容量有限且 Ecall/Ocall 有上下文切换开销）实现，利用备份负载中块频率高度倾斜（VM 数据集中最频繁的 5% 块贡献约 97% 重复块）的洞察提出 frequency-based deduplication，把去重分为 enclave 内小索引与 enclave 外全索引两个阶段。（YouTube EPCjNnpYxXCHc，[12.7-606.4]，L1）
- 〔USENIX ATC〕DEBE 的频率去重实现与评估。enclave 用计数草图近似跟踪块频率（把密码学哈希指纹直接分片映射到计数器、取最小值估计，几乎无额外开销），以小顶堆加哈希表实现 O(k) 空间的 top-k 索引做第一阶段去重，第二阶段用查询密钥确定性加密指纹后经 OCall 查询 enclave 外全索引，最后压缩非重复块并用长期数据密钥加密存储。在 5 个真实备份数据集（源代码、文档、图像、文件系统与 VM 快照）上，DBE 上传性能优于各 DAE 方案（重复数据上传相对基线最高约 30 倍加速，FSL 快照上传最高约 277 MB/s 对 CE 的 179 MB/s），密钥元数据较 DAE 节省约 93%，以 KLD 度量的频率泄露比最先进的 TED 最多降低 87%（TED 需额外存储约 50% 数据）。（YouTube EPCjNnpYxXCHc，[607.1-1192.9]，L1）

- 〔SREcon〕Jet.com 从单区域到多区域的历程与架构选择。Jet.com/Walmart Labs 云平台组 tech lead Andrew Duch 介绍 2015 年 8 月上线不到一个月即遭遇重大宕机，叠加黑五临近使多区域成为业务刚需，理由是容忍区域性故障、更快 MTTR（当时缺乏好的链路追踪）与支持计划内维护。架构上只复制事件溯源（event sourcing）的事实源数据 event store，在次区域本地投影重建 Redis 缓存、Elasticsearch 索引与 Kafka 消息；第一年以自研异步链式复制加 active-passive 撑过首个假日，但因次区域无真实流量、健康度未知，20–30 分钟的 failover 常踩坑，进而走向双区域接真实流量的 active-active 无状态模型，并让 SLO 驱动多区域投资决策。（YouTube EPCm4H-eiYx8I，[10.5-515.2]，L1）
- 〔SREcon〕三数据中心比二便宜、持续演练与故障切换自动化。两区域互备需各自保留 100% 冗余容量，三区域只需各扩到 50% 峰值负载即可容忍单区域故障（更多区域收益递减），Jet 因此选择三区域。团队每周甚至每日做流量 failover、每月做存储层灾备演练（超一个月不演练系统就会漂移），并主动切断区域间复制链路以暴露“依赖只存在单区域”的隐患，借 postmortem 与 SLA 问责倒逼团队补齐依赖或实现优雅降级。最终以状态机式工具全自动化 failover——每个系统迁移时检查数据中心全局状态，避免双写主与数据发散，并主张把故障切换内建到平台层。（YouTube EPCm4H-eiYx8I，[516.1-1030.0]，L1）
- 〔LISA〕3 Myths and 3 Challenges：以 Alvin Toffler 三次浪潮批判系统管理的工业化思维。CFEngine 的 Mark Burgess 主张系统管理仍停留在用工业 brute-force 方法“拆了重装”的黑暗时代（早期 LISA 论文与今天一样都是“一天装 N 台机器还有空割草”），需要破除三个迷思：一是串行顺序控制——流水线文化让人忽视随机顺序、并行与 Monte Carlo 等优化，XML 书目顺序即文化印记强加的例子；二是确定性与回滚——热力学时间之箭说明“undo 不等于回到过去”，回滚一词被数据库理论滥用，只适用于高度隔离的绝热小世界，应学 747 而非火箭做可中途改道的变更；三是层级结构——层级只是关系网络的生成树且不唯一，树每个节点都是单点故障，鸭嘴兽与 C++ friend 的例子说明强行二分类会破坏模型，CFEngine 转而用可重叠的集合。（YouTube EPCp3ZiPW6w7c，[28.0-1362.2]，L1）
- 〔LISA〕三大挑战：复杂性与规模、商业、知识管理。第一是复杂性与规模——先观察系统现状、从演化稳定的结构出发允许涌现结构，而非强推 one size fits all（技术应让支持多样性变得廉价）；第二是认识商业在 IT 社会中的角色——商业发明了 iPhone 与平板、驱动互联网从 DARPA 技术走向千家万户，需要支持机会主义与商业目标的敏捷工具，把火箭式高风险大变更变成可复用、可改道的 747，甚至把基础设施藏进墙里做到自愈；第三是本十年的知识管理——从信息中提炼“意义”（少量信息比大量噪音更有意义），个人技能因专业化而不可替代，连 CFEngine 的银行客户也不得不走向联邦化。问答中讨论冯·诺依曼架构的串行性、Erlang actor 模型以私有状态减少内存锁，并引用 Conway 定律：组织被其底层通信系统所约束。（YouTube EPCp3ZiPW6w7c，[1404.2-2737.3]，L1）
