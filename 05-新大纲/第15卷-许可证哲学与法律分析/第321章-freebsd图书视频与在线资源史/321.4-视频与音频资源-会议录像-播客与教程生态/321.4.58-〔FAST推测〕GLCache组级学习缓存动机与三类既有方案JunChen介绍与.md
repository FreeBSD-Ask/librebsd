# 321.4.58 〔FAST推测〕GLCache组级学习缓存动机与三类既有方案JunChen介绍与

- 〔FAST（推测）〕GL-Cache：组级学习缓存（动机与三类既有方案）。Jun Chen 介绍（与 Yale 的 Zhiming Shen、Yao Yue 及导师合作）：缓存普遍部署于各系统栈，效率（命中率）与吞吐是两大指标；学习缓存分三类——simple expert 型（转写作 Nika）需维护两套元数据且有 delayed reward 问题（要等被逐对象再次被请求才能知道对错）；learning from distribution（LHD，Least Hit Density）特征数受限（更多特征需指数级状态空间）且每次驱逐需大量采样；object-level（LRB，40+ 特征）每次驱逐需采样与推理，比 LRU 慢 100 倍以上。GL-Cache 按组组织对象、在组级跟踪特征并训练模型预测，计算与存储开销被组内对象摊薄；多数负载服从 Zipf 分布、对象请求极少，而组（数十至上百对象）信息更多、更易学习。（YouTube EP8VMJjdYqX84，[13.5-472.0]，L1）
- 〔FAST（推测）〕GL-Cache 的设计与评估。按插入时间分组（相似时间插入的对象在频率与欧氏距离上更相似，简单通用，可利用日志结构存储的低碎片高吞吐与 flash 友好特性）；设计新的组效用函数——组效用为组内对象 1/(T·S) 之和（T 为下次请求时间、S 为对象大小），组大小为 1 时退化为 Belady 行为；7 个特征（3 个上下文特征：写速率、缺失率、请求率，如每日备份时三者同升）配合梯度提升树回归，用模型对组排序后做 merge-based eviction（保留少量对象、驱逐其余，保持新组对象相似）。基于 CloudPhysics/MSR/Wikipedia 三类 trace 评估（micro 实现与基于 CacheLib 的原型，各有效率与吞吐两种模式）：相比 LRU 等基线命中率显著更高、吞吐显著更高，组大小可在吞吐-效率谱上调节，兼顾效率与性能；已开源。（YouTube EP8VMJjdYqX84，[472.3-955.5]，L1）
- 〔USENIX ATC（推测）〕TGS：容器云深度学习负载的透明 GPU 共享（动机与背景）。北京大学一年级博士生 Bingyang Wu（合作者 Zili Zhang、Xuanzhe Liu、Xin Jin，及 Johns Hopkins 的 Zhihao Bai）指出生产 GPU 集群利用率低：微软研究显示均值仅 52%，阿里集群中位数不超过 10%，根因是 GPU 被静态独占分配给单个容器。应用层方案对用户不透明、需大改框架（NNI 为单个 TensorFlow 版本加 4000 行代码、PyTorch 加 2000 行）；NVIDIA MPS 只隔离计算资源、内存不可超分且无故障隔离（合并多进程 CUDA 上下文，单进程故障可使其他进程挂起）；NVIDIA MIG 依赖高端 GPU 硬件、每实例仅 7 种固定配置、不能动态重配置且不支持内存超分订阅。（YouTube EP8VQHwNwX-BU，[14.3-422.1]，L1）
- 〔USENIX ATC（推测）〕TGS 的设计与评估。TGS 工作在容器之下的 OS 层、对用户完全透明，核心是容器与 GPU 之间的轻量间接层：自适应速率控制基于 kernel 到达速率（利用 DL 训练的迭代特性）以 AIMD 调节机会作业出队速率，用尽剩余算力而不显著影响生产作业；透明统一内存以 CUDA unified memory 为间接层，只分配虚拟内存、实际使用时触发 page fault 才换入 GPU 内存，GPU 满时优先保留生产作业的块、必要时驱逐机会作业块到主机内存。原型约 3000 行代码并集成 Docker，在 2×A100 服务器与 V100 AWS 实例上用 Microsoft 真实 trace 与 7 个模型混合负载评估（与 AntMan、MPS、Mix、Exclusive、Co-execution 对比）：机会作业平均归一化 JCT 较 exclusive 降低 52%，生产作业较 co-execution 降低 21%，性能与 AntMan 相当且对作业透明，内存超分场景下机会作业吞吐较 MPS 提升最高 15 倍。（YouTube EP8VQHwNwX-BU，[422.2-859.7]，L1）
- 〔会议不详〕Swarm：性能感知排序增强网络故障缓解。数据中心故障频繁，约 16% 的事故损失超过 100 万美元，云厂商依赖缓解系统在事故发生后几分钟内部署到位。现有方法（运维 playbook 统计每台上行链路数、更新的工作统计路径数）用简单静态指标换取可扩展性，但完全忽略网络上下文（对丢包多少不同的链路一视同仁），在生产环境与构造示例中性能惩罚达 18% 甚至更高。Swarm 接收候选缓解动作列表、按预期性能排序后部署最优项，综合考虑流量性质、故障性质与运维关心的性能目标；三大挑战是快速量化性能（模拟器需精确建模每个包/流/故障而过慢，但排序只需相对比较、可容忍误差从而大胆近似网络行为）、捕获未来流量不确定性、以及方法的通用性与表达力。（YouTube EP8W5tX96THGQ，[16.0-474.1]，L1）
- 〔会议不详〕Swarm 的技术与评估。按流大小拆分长/短流，分别为长流吞吐估计器与短流 FCT 估计器；长流估计以 epoch 近似（假设流到达于 epoch 开头、epoch 内状态稳定，epoch 大小为精度-可扩展性权衡的超参数），结合传输模型把流分为 loss-limited 与 capacity-limited 两类（先假设无限容量估计 loss-limited 速率，再输入资源分配算法求最大公平速率）。用过去流量的分布生成多样本、快速估计性能并聚合为复合分布以刻画每个动作的不确定性，按目标分布并排比较取更鲁棒者；支持任意可表达为流级指标分布函数的单目标、优先级列表与加权组合，覆盖比先前工作更广的故障与缓解。评估中优先级列表目标下基线最高面临 80-120% 性能惩罚，而 Swarm 最高优先级惩罚至多 0.1%、其余低于 5%；约 1.6 万服务器的数据中心不到 4 分钟可产出缓解。（YouTube EP8W5tX96THGQ，[475.5-958.6]，L1）
- 〔SREcon（推测）〕大规模基因组云平台的性能与可靠性管理（背景与发现）。报告人 Haotong（与芝加哥大学 Robert Grossman 教授合作，工作多在 Center for Translational Data Science 完成）介绍：Genomic Data Commons（GDC）每周/月处理数百万核时的癌症数据并公开，公开数据 3.7 PB（含内部共 7.2 PB，单样本 10 到 100+ GB）；其 G-PAS 流水线自动化系统建立在裸金属节点与 OpenStack KVM 虚拟机上，以 CWL tools 为执行引擎，流水线为有向图任务（使用 SAMtools、BWA 等工具），作业性能只在同一 pipeline、实验策略与 project 内可比（用执行时间除以输入大小的 processing rate 度量）。变异特征提取流水线的 CDF 显示裸金属节点性能稳定（近乎垂直），VM 作业更差且呈长尾；VarScan2 实验定义了 fresh VM 与 aging VM，Sysbench 文件 I/O 基准发现 aging VM 上 utilization raw 与 derived 出现差距（VM 内丢失时间片），VM 的 system usage 仅 27% 而 host 上接近整体利用率，说明 hypervisor 高强度活动。（YouTube EP8Wz1WyOCBvo，[8.1-502.3]，L1）
- 〔SREcon（推测）〕VM 老化变慢的根因与缓解。修改内核记录 read 操作五个步骤（查页缓存、同步读、发起异步读、等待异步读完成、从内核空间拷贝到用户空间）的耗时，发现大部分时间花在 copy page（纯内存操作）且随进程数显著增长；极高 system CPU usage 与内存变慢主要由 Extended Page Table（EPT，二级地址转换）violation 触发的昂贵 VM exit 造成。连续 10 天以上运行 DNA 比对任务（每任务 6 CPU）显示 VM 运行越久 EPT violations 越多、执行时间越长，并定义"后续 EPT violation 地址距离"新指标表征内存碎片（距离越大越碎片化）。检测采用 host 级 EPT violation 监控（基于距离分布，第 3 天出现明显差异）与 vCPU efficiency（VM/host 记录时间片之比，重负载 40 CPU 场景明显而轻负载 8 CPU 不敏感）；缓解上内存碎片整理可提升性能、降低 EPT violations 但无法回到初始状态，AWS 与 Google Cloud 专用宿主机上作业性能远更一致但成本更高。（YouTube EP8Wz1WyOCBvo，[503.8-887.3]，L1）
- 〔NSDI〕云游戏自适应渲染优化系统 Stimpack（转写亦作 SteamPack/Steampunk/Synpex）。主讲人 Jin Heo（Georgia Tech）指出云游戏受 FPS、画质与低延迟制约而部署在边缘，集中式云高扩展但高延迟、边缘机资源有限，现有服务靠限时限流维持 QoS；其核心洞见是服务器端高渲染质量在用户网络差、有损压缩时投入回报递减，GPU 开销并不总能转化为用户感知质量，Stimpack 据此以 playability、video quality、system utility 三支柱量化资源效率，由集成于各游戏实例的插件与运行时在多用户共享单 GPU 时协调分配渲染质量，把回收资源让给真正能看到画质提升的用户。（YouTube EP8X6HiUVWxII，[18-455]，L1）
- 〔NSDI〕Stimpack 评估：动态网络下的实际收益与结论。测试床用两个 Unreal Engine 游戏（中等负载卡通风与高负载写实风），最多 6 用户、渐进/突发到达、静态与动态网络；相对所有实例最高渲染质量的朴素基线，重载游戏中基线只能以可玩 FPS 服务 3 个用户而 Stimpack 服务 6 个用户并维持 30 FPS；盲测 A/B 用户研究中多数场景胜过 highest-only、lowest-only 与不考虑用户侧质量转化的先前工作，并在真实 4G/LTE 带宽 trace 下展现动态优先级（200 秒附近用户一网络变好、用户二变差时渲染质量随之对调），单 GPU 用户容量提升至 2 倍且保持高 QoE。（YouTube EP8X6HiUVWxII，[471-927]，L1）
- 〔USENIX Security〕面向二进制-only 模糊测试的编译器级插桩 ZAFL（转写亦作 Zafle/Zafro/Zaphod）。主讲人 Stefan Nagy（Virginia Tech 博士生，导师 Matthew Hicks，并与 UVA 的 Anh Nguyen-Tuong、Jason Hiser、Jack Davidson 合作）指出二进制-only 软件因语义不透明导致模糊测试插桩开销高、增强变换得不偿失；提出以编译器视角审视插桩的四大考量（代码插入、调用方式、寄存器使用、可扩展性），论证静态重写优于动态翻译、内联优于 trampoline、需 liveness 感知寄存器优化，据此把 ZAFL 设计为静态插入、内联、liveness 感知的插桩平台，改造自 Ziper 二进制重写项目，支持 x86-64 ELF 与 Windows PE32+ 二进制。（YouTube EP8Z-5aTpk_l0，[8-390]，L1）
- 〔USENIX Security〕ZAFL 实现与评估。其低层 API 为语义不透明的二进制世界带来语义丰富性，实现 5 个基于 LLVM 的模糊测试增强变换（降低插桩点开销的性能类与细化 interesting 行为粒度的反馈类）；对 8 个开源与 5 个闭源二进制、每项 5 次 24 小时试验，相对静态重写的 AFL Dyninst 与动态翻译的 AFL QEMU 分别多暴露 26% 与 131% 独立分诊崩溃；插桩开销 27%-32% 接近编译器级 24%，远低于 AFL Dyninst 的 88% 与 AFL QEMU 的 256%；对商业工具 IDA 的堆越读 2.5 小时内暴露（最近对手超 23 小时），指令恢复率最高、控制流图覆盖精度接近 100%，并确认在 33 个开源与 23 个闭源二进制上可扩展。（YouTube EP8Z-5aTpk_l0，[393-781]，L1）
- 〔USENIX Security〕npm 生态安全威胁实证研究（Small World with High Risks）。主讲人 Markus Zimmermann（TU Darmstadt，与 Cristian-Alexandru Staicu、Michael Pradel 及 r2c 的 Cam Tenny 合作）基于 2010 年 11 月至 2018 年 4 月、67 万包、500 万版本、约 20 万维护者与 609 条安全通告的数据，定义 package reach 与 maintainer reach 等度量：平均安装一个包会隐式信任 79 个第三方包和 39 位维护者，是最令人意外的攻击面；npm 开放发布、几乎无审查、GitHub 与 npm 产物不比对，加上锁依赖实践需手动升级才能获得安全补丁，放大了恶意包、账号接管与维护者合谋等威胁。（YouTube EP8_2SdHrBUt4，[11-630]，L1）
- 〔USENIX Security〕结果、缓解与问答。最流行包可影响超十万其他包，维护者影响同样呈幂律；维护者合谋仅需约 100 个最流行维护者即可触达约 50% 的有依赖包；安全通告长期积压（Liang Gong 目录遍历大规模披露、typo squatting 永无补丁、包无人维护），高达 40% 的包依赖含至少一个公开已知漏洞的代码。缓解上建议向开发者展示依赖风险度量、用 npm audit 告警已知漏洞，并评估代码审查策略：审查被依赖最广的约 1500 个包可将隐式信任降低 10 倍，但需审查超 20 万行代码；问答环节（Naval Postgraduate School、Rice、UC Berkeley 听众）讨论 2016 年 left-pad 事件后传递依赖回落与对 Python/Ruby 生态的可推广性。（YouTube EP8_2SdHrBUt4，[633-1268]，L1）
- 〔USENIX Security〕Linux 固件 rehost 的两个缺失能力与 FICD 技术（Pandawan，转写亦作 Panda One/Pandemonium）。主讲人（波士顿大学 Ioannis Angelakopoulos 等）指出 IoT 固件 rehost 此前不能把用户态与内核态作为整体单元分析——先前的 FirmSolo（USENIX 2023）侧重内核模块、定制内核缺少用户态所需功能，例如不启用 MTD 字符设备选项导致 flush_to_fs 死循环；也缺乏基于模拟能力的客观比较手段，wall-clock time 因各框架（如 FirmAE 与 FirmSolo）系统设计差异而失真。为此提出固件初始化完成检测技术 FICD：用计时器（每执行新任务刷新一次）判定固件不再执行新任务的初始化完成点，作为概念上跨 rehost 框架一致的比较锚点。（YouTube EP8avZXHb1rpI，[8-394]，L1）
- 〔USENIX Security〕Pandawan 框架与评估。框架由内核增强组件（用 FirmSolo 生成定制内核，再以 Oracle 机制增补 IoT 固件常用配置项，同时过滤会改变内核模块所用数据结构布局的选项如 config ipmr，避免内核模块崩溃）与基于 PyPanda 的固件 rehost 与分析组件组成，内置 FICD 等插件；分析上用 syscall-to-kmod tracer 追踪访问已加载 IoT 内核模块的系统调用，仿 Moonshine 转换为种子后用 TriforceAFL 模糊测试。对约 1500 张固件镜像（多数来自 FirmSolo 数据集、50 张来自 Greenhouse 的较新内核）评估，Pandawan 在执行的用户态程序数、加载的内核模块数及用户态/内核态基本块覆盖率上超越 FirmAE、FirmSolo 等；为 500 张固件生成种子，TriforceAFL 触发 16 个 bug（6 个未知），涉及 12 个内核模块（8 个专有），已报告厂商。（YouTube EP8avZXHb1rpI，[400-792]，L1）
- 〔SREcon〕Bing.com 生产环境剖析（BPerf）的动机与事故案例。主讲人 Mukul Sabharwal（Microsoft Bing 前端团队）介绍 C#/ASP.NET MVC 前端栈部署于 Windows Server 2016、经 Azure CDN 承接所有 Bing 流量，每日多次全量发布、约百个提交、大量 A/B 实验导致没有规范负载；剖析生产是把不寻常代码区域定位并隔离出来而不扰动被剖析对象，高层工具（RPS、时延等聚合指标与降级手段）不可替代但只能识别与缓解，无法给出根因。以一起凌晨 3 点事故为例：无 feature flag 的查询触发多控制变量的非显然死循环，只能靠五六个开发者人工二分日志定位代码，再单独构建 standalone app 复现调试，说明剖析与检查局部变量能力本可大幅缩短事故时间。（YouTube EP8dBhT8WJhYA，[10-753]，L1）
