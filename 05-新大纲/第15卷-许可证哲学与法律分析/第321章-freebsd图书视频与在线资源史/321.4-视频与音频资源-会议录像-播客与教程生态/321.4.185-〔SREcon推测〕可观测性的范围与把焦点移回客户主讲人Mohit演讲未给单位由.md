# 321.4.185 〔SREcon推测〕可观测性的范围与把焦点移回客户主讲人Mohit演讲未给单位由

- 〔SREcon（推测）〕可观测性的范围与"把焦点移回客户"。主讲人 Mohit（演讲未给单位；由内容推断其团队运营 Bing 类产品），以"给各位唱首可观测性安眠曲"开场：他引 Google Trends 说 observability 自 2004 年以来先有一波高峰、随后回落、如今又回升，而近期回升多来自工程与其他学科的可观测性概念而非我们系统中的可观测性，把它与 monitoring 一起搜索时曲线形态完全不同、这个词大约 2016 年才进入行业话语，算是相当新。他不愿挑起名词之争，只界定这 45 分钟里的含义：可观测性是超集，包含监控（含告警）、调试、测试、洞察等等，并以哈勃望远镜类比——它的职责不只是寻找冲向地球毁灭人类的彗星，更要解释宇宙中存在什么现象；双关地说是"get a good understanding of the problem space"。他的第一个假设是关于可观测性如何被度量：无论度量客户行为还是相关指标，总是透过我们自己所维护系统这副透镜，且观测者与被观测者构成一种关系；他反问难道每个工程团队都会说"确保系统 uptime 很好，客户做什么与我无关"吗？这正是客服与工程脱节、工程师完全不接触真实客户的经典配方，因此提议不要只盯应用栈，而要把焦点移向客户本身。随后他放了三分钟 Monty Python 短片（Stephen Fry 与 Hugh Laurie 的 Blef）——Marjorie 在 Stratton Brook 从 Thunderbolt 上摔下被 Cottrell 抬进客厅、医生 Cavendish 正在客厅给她检查，而时钟不会因为有人摔下马就变成首相，"Marjorie 摔得很重"这句事实被听成了"时钟摔了"；结论是听到与听见不同，这句格言并非网图而是妻子贴在冰箱上的贴纸。回到工程：应用指标是我们最舒服的区，而其中最痴迷的两个数字是可用性的 nines 数与 p75、p95 分位数，正因此它们离用户很远。可用性方面，大家都在某种形式上度量可用性——5xx 错误乃至微服务内部的成功与失败，但这只是倒置冰山的水面部分：还有更多人根本连不上你的服务而你不知道，服务可能假设用户有高速网络，而你的用户可能只是该产品可及市场的很小一部分（对搜索这类服务而言，所有能上网的人都应能搜索）。他给出的第一个工具是网络错误记录（Network Error Logging，W3C 草案规范），让浏览器就你的端点可用性发送旁路遥测，相当于电话的占线提示音（dial tone）式检查：过去 12–14 个月使用后他们对客户连接遇到的问题获得全新认识——此前完全不知道有人在某些网络下经常遇到 DNS 解析问题、或在某些端点遇到 TCP 连接问题，如今对客户附近网络空间有了更合适的理解；该特性当前即可启用，在全部 Chromium 系浏览器可用。速度方面，人们总盯高分位数，但 p75 只关注最慢的 25%、却默认其余 75% 体验良好；有时性能看起来快恰恰是因为图片加载不出来、体验次优，对速度的单一执念反而造成糟糕体验，所以可观测性应看整条分布而非单一分位数。易用性曾是软件开发的支柱之一（靠研究来做），但在每天多次发布的在线服务时代既无法这样做、也无法把易用性压成单一数字。例子是有人在 Reddit 抱怨看到奇怪的紫色广告——显然不是实验，也不是站点挂掉，开发者几乎无法复现；"如果我们能看到用户看到的画面会怎样？"这一手法成了改变游戏规则：匿名化易用性数据支撑会话回放，可以看到用户四处移动鼠标、看不清明面上发生了什么、最后挣扎着滚到页面底部点链接，从而识别出这类特定行为；再用结构化数据检索"展示的广告背景色是否不是默认色"等条件，并注意到例子里的绿盾图标进而定位根因——是客户端某个脚本在破坏客户体验，而且不止能复现、还能量化影响面。这套工具叫 Clarity，代码在 GitHub，把会话回放、结构化数据与行为分析合为一体，作者自称其为"打了类固醇的 RUM"。（YouTube EPUg4xiz8QPgU，[5.1-832.9]，L1）
- 〔SREcon（推测）〕用户更近的两层：反馈与倾听之旅。反馈层用看医生类比：医生先读血检报告（指标），再让你抬抬膝盖脚踝（易用性度量），最后才会问"你今天感觉如何"——后者才是客户反馈，因为我们终究是人，人处理的是感受与情绪。反面案例是他亲历的"你的鸡肉 tikka masala 要多辣、1 到 10 打几分"式提问：一是被 10 分锚定，二是把反馈与某个人的考核绑定，若真不满意便不可能诚实作答；问人"你在 1 到 5 内给我打分"根本说不通。更好做法是给与他此刻所看内容相关的结构化选项，在时机点上询问（选项随所在页面变化，用高亮面板针对具体事物收反馈）；一流系统还会从用户写的文字里抽取情感——人们会用标点与特定词汇表达状态，至少先拿到原文再自行量化，以保留原始数据，作者说他们最初用的是斯坦福的 CoreNLP 库并大加改造。好的反馈系统应具备：上下文感知、可及（不藏在四层汉堡菜单之下）、主动（检测到有人反复按 F5 或在两页面间来回就走上去问"看起来你遇到了麻烦，能告诉我们发生了什么吗"）、能做情感抽取、而且可执行——无法据此行动的反馈没有用，只要遥测管线与分析到位就能把反馈转化为可理解的指标。再往外是内部人员计划（insider program）：目标应是与客户建立联系而非消耗客户，人不只是数据点、工程师也不是照指令行事的地下室机器人，线上服务天然带一丝非人化——服务挂掉时没人想到背后有人运维、客户点了错的按钮时也被斥为愚蠢。内部人员计划不是 dogfooding（dogfooding 指你既生产又消费自家产品，但作为订阅服务的工程师你免费用、从没见过支付页面、不知道催缴邮件怎么运作），而是让真正活跃的消费者在功能上线前参与；实验能告诉你收入数字在涨，却给不出满意度，且你可能用了自家产品却根本不是目标客户。最后是倾听之旅（listening tour，即"与客户零距离"）：作者问在座有多少人想亲眼看自己服务跑在的数据中心、被海量基础设施震撼——几乎人人如此，但很少人同样投入去了解用户在哪儿、日常做什么。用户其实就在我们周围，这正是矛盾所在：他们近在咫尺却又远在天边。做法是让工程师当面见客户，体会是相互的：接触极端负反馈会锤炼品格、也会建立一种社会极需的容忍度；一位总统候选人在辩论中说 Bing 没人用，这足以点燃怒火，但去见真人后你会发现服务确有人在用，还有人为了被邀请而驱车 150 英里前来。与粉丝交流还帮你看见自己做得好的地方——让你惊喜的是让人非常满意的多不是那些隆重发布的大功能，而是小事；面聊得到的反馈无与伦比，很多实验无法告诉你。收束时他点明为何选这个受众与这场会：在座各位运行着遥测平台、是数据汇集的地方，既是最懂自己系统、最了解上线后现场的人，也是唯一有从用户电脑穿全栈直到数据中心的三万英尺视野的人，所以把可观测性与客户对齐属于本职工作而非额外负担。他的五步计划是从指标到可用性再到易用性、反馈、客户参与，提醒这不是全有或全无——总得从某处开始，并且要与客户建立长期联系，才能带来产品与服务的长期收益。答疑中他强调我们区分的不是重要或不重要的客户，而是客户与机器人：某些服务流量中相当部分是机器人，工程师的职责是用系统识别出被误当机器人的真人并给予正常体验；对真人客户按设计不做差异化，因为我们的产品是零成本切换，座右铭是绝不落下任何一个用户，而收入是长期博弈、与这件事正交。追问 Lynx 这类无 JavaScript 支持的纯文本浏览器是否也在乎时，他说在乎，但也承认在约 48 kbps 这类低速网络上表现并不好——在不用重 JS 库的前提下为这些人渲染正确体验是他们与所有想扩张的人都面临的问题，努力在做，但这正是金钱是零和博弈时商业考量与客户考量相互拉扯之处：心是好的，可优先级最终凌驾一切。（YouTube EPUg4xiz8QPgU，[834.6-1782.6]，L1）
- 〔会议不详〕Sage：为 LinkedIn 流处理应用做自动资源定容的反馈控制器。主讲人 Raymond 来自 LinkedIn，与本批同事 Bharat、Sam 合作。流处理应用处理形如流的输入数据，例如 LinkedIn 上有职位发布的流与候选人技能流，需要实时或近实时地把岗位与候选人匹配、算出最容易找到工作的技能；对应系统包括 Apache Flink、Storm、Samza、Heron、Spark Streaming，其他例子还有发邮件、摘要与通知的应用、监控服务间调用的应用、实时分析与下钻 A/B 测试的应用。LinkedIn 上运行着上千个这类应用、覆盖不同逻辑类别，处理速率达每秒数百万消息、即每秒数百 GB 数据。LinkedIn 以平台形式提供流处理：给用户（通常是应用开发者与数据科学家）提供 SDK 与 API 写业务逻辑，容量供给、运维问题、应用安全等由平台承担，同时要求可扩展性、效率、容错与性能等标准特性。问题在于用户仍要自己定容：内存、CPU、线程数、堆与原生内存的分配、是否为应用启用专用硬件，这些定容与调优决策对用户很难做，结果要么大幅过度供给造成浪费——他们的经验是一半以上用户过度供给至少 50%，一篇 Google 的近期论文在类似主题上有相同发现——要么供给不足，导致应用内存耗尽、卡住、失败、经常性能不佳并引发运维问题。理想中需要一个控制器，输入包括应用的时延与吞吐目标、输入负载、应用内部信息（如服务依赖）、网络时延与环境状况等，输出为应用的参数与规模。既有工作分两类：一类假设应用是由 map、join、filter 等有据可查算子构成的 DAG、各阶段性能与资源特征可预测，然后调各阶段并行度以优化吞吐、时延、资源利用率与调优本身耗时；另一类对输入负载或单消息服务时间做假设，再用算法方式调并行度。作者拿真实生产应用检验这些假设，发现大量应用依赖远程服务处理输入（blob 或键值存储、负责内容控制与通知用户的 web 服务），应用服务时间因此直接依赖这些服务的时延、失败率与网络时延，而这与既有假设不同——它不遵循任何特定分布，可能是长尾或多峰；这类应用的吞吐还依赖远程服务吞吐，且输入负载本身随时变化、到达率也不遵循任何分布。（YouTube EPUi7XcOGSUsY，[7.8-440.3]，L1）
- 〔会议不详〕Sage：按优先级序列化的反馈式策略栈与生产实测。应用远不止算子 DAG：有的加载 DL4J、TensorFlow 这类外部重资源框架，有的用 UDF，有的用 RocksDB 之类本地持久化状态存储且可能把状态复制到远端，有的还调整处理语义（如启用乱序处理、定制数据消费行为），作者用热图度量了生产应用所用功能的重叠度，从而判断"按功能标签聚类"式模型不足以用于定容；应用还存在资源使用相关性——CPU 供给不足会拉长服务时间、进而增加输入缓冲、从而推高内存使用并使吞吐下降；在 Samza、Flink 这类 Java 系统上内存不足会引发频繁 GC、导致时延上升、CPU 飙高、吞吐下降，这一点既有工作几乎忽略。跨应用看差异极大：单消息平均服务时间可少至 10 微秒、多达 10 秒以上；输入流数量可少至一两条、多达数千条；本地状态可少至几 KB、多达 TB，因此控制器不能依赖任何特定实现假设或阈值，也不能假设负载与到达率分布。作者据此提出需求：给出虽非最优但能约束过度供给同时始终避免供给不足（及其后果）的尺寸，允许并便于服务方人工覆盖与解释决策，从当前规模出发走到目标尺寸的轨迹不应加剧供给不足问题，还要最小化到位时间、能扩展到大量应用、容错且资源高效。实现上作者在两种极端间取中间路径：黑盒试错法（对应用施加决策再撤销或重做，类似 Azure 虚拟机规模集与 AWS EC2 的规则式自动扩缩）简单、可解释、能得到正确尺寸，但不了解应用内部（如 CPU 与内存使用是耦合的），且已被证明会出现振荡——控制器永不收敛或收敛极慢，生产上不可取；另一种是为每个资源参数建立对各应用的影响模型并把定容形式化为优化问题，可最小化到位时间，但缺乏可解释性与运行时修改行为的能力（如应对应用依赖的远程服务故障、网络时延上升）。Sage 是反馈式控制系统，把资源定容策略组织为按优先级排列的策略，每条策略只负责单个资源，只有当所有更高优先级策略都不再给出调整动作时才轮到它；为提高生产可理解性，Sage 把作用于同一应用的策略序列化执行，即逐个资源串行改变尺寸。优先级排序带来两点关键收益：无论应用类型、所用功能或其他自由度如何，各资源尺寸的确定顺序都是确定的；策略易于可编程——某策略可以假定其更高优先级策略所管资源已经无需调整，例如负责并行度（线程数或进程数）的策略可以假定当前应用不存在内存或 CPU 瓶颈，从而大幅降低编写与调优策略的难度。作者为 Samza、Flink 这类连续算子系统定制了该优先级顺序，其他系统类型可能需要调整策略与顺序。示例中应用跟不上输入负载时可能受内存、CPU 或并行度瓶颈所限：由于 Flink、Samza 的输入缓冲有界（其他系统可能按可用内存动态决定），只要先调内存就能保证应用稳定不失败运行，之后再由后续策略处理因 CPU 瓶颈造成的高服务时间与因并行度不足造成的低吞吐；同理调并行度的策略可测量应用的积压增长率并与应用所用远程服务的指标关联，据此向上扩并行度（缩容部分见论文）。Sage 本身也实现为一个流处理应用（它处理来自其他应用的输入流），约 6000 行代码，已在数百个生产应用上启用；生产上从启动到定容到位平均约 30 分钟，而定出的尺寸比人工调优的最优尺寸大约 14%；30 分钟之所以偏长，主要是生产上刻意控制各策略的响应性；缩容则对每个资源（如 CPU 与内存）施加一次单独的缩容动作。结论是资源定容对任何服务的性能、可用性与可运维性都至关重要，对流处理应用尤其如此（它们持续运行在变化负载下），而今日生产应用远超出传统 DAG 视角，资源供给意味着在资源利用率、性能、成本与可运维性之间做出复杂权衡，Sage 这套针对生产应用定制的规则式系统负责处理这些权衡。（YouTube EPUi7XcOGSUsY，[444.4-805.0]，L1）
