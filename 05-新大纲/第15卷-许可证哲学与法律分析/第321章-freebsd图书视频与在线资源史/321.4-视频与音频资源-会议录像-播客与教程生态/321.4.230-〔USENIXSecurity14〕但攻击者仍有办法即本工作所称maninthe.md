- 〔USENIX Security '14〕但攻击者仍有办法，即本工作所称 man in the middle scripting in the browser〔08:52〕：浏览器打开到 example.com 的连接被攻击者拦截，而攻击者不能再新建一条到 example.com 的连接，于是他改以一段自己起源的恶意 JavaScript 作为 HTTP 载荷直接回给浏览器、随即关闭这条被拦截的连接；而浏览器起初认定自己在连 example.com，故脚本运行于目标服务器的 web origin 之内、可读取该域任一文档并发出任意请求〔09:08〕。关键在于此后浏览器为 example.com 发起的下一个请求会被迫建立新连接、而攻击者这次并不拦截，因此这些请求携带那个与 Channel ID 绑定的 cookie、走正确通道、全部被正常认证；攻击者的脚本则在后台持续运行、能访问用户可做任何的事、甚至自行发起恶意请求——攻击者实际上把自己从网络转移进了浏览器〔10:24〕。作者指出这一盲点为众多提案共有：TLS Channel ID 及其上层协议 FidoNotes、FIDO U2F、传统 TLS 客户端认证、乃至二〇〇六年的 TLS Session-Aware Authentication 均受影响，原因都是只关注客户端认证而忽视服务器认证〔11:00〕。结论是服务器认证无法被忽略；但只要已部署基于 Channel ID 的客户端认证方案从而阻止凭据被窃用，只需再要求 invariance 这一更弱性质即可抵御此类攻击〔12:06〕。论证是：Channel ID 已堵死常规中间人、剩下 MITMSIB，而要成功必须让浏览器在同一次会话内连到两个不同实体——一条连接被拦截以投递恶意载荷、另一条被引导到合法服务器供脚本读取账号信息〔12:35〕。据此要求浏览器不得在同一会话内与两个不同实体通信：若首条连接未被拦截则后续都不得被拦截；若首条被拦截则后续必须全部被拦截；出现一条直通而另一条被拦这类不一致即为 invariance violation，浏览器据此中止通信、终止攻击〔13:19〕。与认证的区别在于：认证不允许攻击者拦截任何连接，invariance 允许拦截但要求全都被拦，因而不需预先建立的信任、更易达成〔14:56〕。实现是首次建立 TLS 连接后、浏览器与服务器以两个随机值（浏览器选 RB、服务器选 RS）即时生成挑战应答对并各自本地保存；后续每次连接由浏览器索要 RB 的应答、服务器查表回送、浏览器校验一致性——两端为同一实体则成功、若任一被拦截则失败并被检测出；服务器还需一并保存浏览器 Channel ID 与应答以防中继攻击〔15:58〕。论文另给出把服务器状态安全下放到客户端的更繁复协议，并讨论跨源通信、资源缓存等真实场景处理〔17:24〕。若应用只用弱客户端认证（口令与 cookie）就必须确保服务器认证真正有效（固定、证书透明等）；若用强客户端认证则只需 invariance，二者结合即作者方案 SISCA（转写漂移为 Cisca 或 Cisco）〔17:56〕。最后强调：web 服务器可以把代码推给客户机并要求其执行任意代码，这一点在设计面向 web 的协议时必须纳入考量，Channel ID 正因忽略它而失守〔18:46〕。Google 的 Juan Lan 问是否只需要求跨连接公钥不变即可、作者确认仅在服务器换用多证书或私钥被窃时才需协议改动〔21:38〕（YouTube EPZ-mNblnhmXE，[509-1385]，L1）
- 〔USENIX ATC '22〕上海交通大学青年教师金宇报告 EPK：Intel Memory Protection Keys 只能提供十六个内存域，无法承载现实中的轻量级隔离需求；EPK 通过把 MPK 与用于快速 EPT 切换的 VMFUNC 组合，在不改硬件的前提下把内存域数量扩展而开销很低〔00:13〕。背景是 MPK（又称 Intel PKU）：自二〇一九年起在桌面与服务器 CPU 中可用的进程内内存隔离硬件特性，它复用页表项中此前未用的四位作为四位保护键（即域 ID），把一个进程的虚拟地址空间划成十六个内存域，每页专属于其中一个域；新增三十二位寄存器 PKRU 以每域两比特的方式规定这十六个域的只读、读写或禁止访问权限，该寄存器每核独立，使同进程内并发线程可对各域持不同权限；更新它的是非特权指令 WRPKRU，可直接在用户态执行且仅需约二十八周期〔00:34〕。常见用法模型是：进程把不同保护键绑定到不同域、把数据分散到各域，线程在访问某域数据前后取用或释放该域权限以降低被漏洞波及的概率，这个取放权限的动作称为域切换〔02:11〕。但十六个域严重制约可用性：典型服务器应用并发服务远多于十六个客户、本应把各客户私有数据放进隔离域以防敏感数据泄漏；持久内存数据受意外或恶意访问的威胁日益受关注，更多域能缩短数据暴露时间；应用与系统软件需要隔离的组件也常多于十六个，热门应用动辄引用数十个第三方库〔03:09〕。根源是每个域必须独占一个保护键而硬件只支持十六个。一个候选方案是资源时分复用——让不同域在不同时间共用同一保护键，先把保护键从旧域驱逐再分给新域；若想把 PK1 复用到域十七就得先清空所有打了 PK1 的 PTE，域内存大时改 PTE 代价高昂、还要额外刷 TLB〔04:55〕。另一个直观方案是把页表项中更多位用作域 ID（例如十位可给一千零二十四个域），但在商用机上不可行、还可能与即将到来的五级页表不兼容，且权限也无法用一个超过两千位的 PKRU 表达〔05:40〕。EPK 的三个设计目标是支持可扩展的内存域数量、无需硬件修改、性能开销低且能支撑可扩展的域大小〔06:23〕。关键观察是：MPK 的性能优势来自特权态下配置域与非特权态下切换域的解耦，而另一硬件特性 VMFUNC（供快速 EPT 切换）具有相同模式——宿主机态配置 EPT、访客态切换 EPT，故可把两者结合〔06:50〕（YouTube EPZ0TiHWZKlJw，[13-438]，L1）
- 〔USENIX ATC '22〕VMFUNC 的背景是：Intel 硬件虚拟化用 EPT 做内存虚拟化，虚拟机内部页表把访客虚拟地址映射到访客物理地址、EPT 再把访客物理地址映射到宿主物理地址，由 hypervisor 统一管理；VMFUNC 是让访客虚拟机直接加载新 EPT 的硬件指令，可选 EPT 只能取自 hypervisor 预先配置、最多五百一十二项的列表，而 MPK 在虚拟机内同样可用，因此 EPK 直接组合二者〔07:47〕。应用需运行于虚拟机内、系统为该 VM 建立多份 EPT；应用把虚拟地址空间切成内存域，每个域含离散的内存页，域 ID 由一个保护键加一个 EPT 索引组成的扩展保护键标识，每个 EPT 可容纳该应用的十五个域（同一 EPT 索引、不同保护键）。同一保护键可被不同 EPT 中的域并发使用——例如域一、域十六、域三十一都用 PK1，只是分别落在 EPT 0、1、2 中；同一 EPT 内的域靠不同保护键隔离，不同 EPT 之间则靠每个域的映射只存在于其自身那一份 EPT 来保证；全局代码与数据打 PK0 并映射到所有 EPT、构成特殊的域零，这也是每份 EPT 只能提供十五而非十六个域的原因〔09:42〕。EPK 完整保留原有使用模型：用户态库提供接口，alloc_domains 取回多个域 ID 并优先返回位于同一 EPT 的域、因为同 EPT 内的域切换更快；domain_map 在域内分配虚拟页，domain_begin 与 domain_end 负责切换——同 EPT 内只需执行 WRPKRU，跨 EPT 需额外一条 VMFUNC〔10:48〕。两项实现挑战是：如何让 VM 在带差异的多份 EPT 上无缝运行、以及 hypervisor 并不掌握域映射信息时如何区分因按需分页产生的非法 EPT 违例与因错误访问产生的违例；此外 MPK 允许单线程同时访问多个域，多份 EPT 并存时如何支持这种灵活性〔12:12〕。在 Dell PowerEdge 服务器上的评测里，除原生进程外还对比了一个 EPT 一个域的 VMFUNC 方案与采用时分复用的先例工作 libmpk（为公平起见在宿主 OS 上运行）〔12:41〕。三个案例：nginx 上把不同客户端的 SSL 会话密钥放进不同域，用 ab 生成三百客户端各发五个请求即共三百个域，EPK 相对原生约百分之五开销、优于另外两者（VMFUNC 方案约百分之十二，libmpk 因改页表与刷 TLB 约百分之十八）〔13:52〕；NVM 保护场景中把域数固定为三十二、通过给每张哈希表加桶与键值对放大域大小，libmpk 的开销随域变大而上升、而 EPK 与 VMFUNC 方案的开销与域大小无关〔14:31〕；微内核场景中，较新的 IPC 设计 On the Bridge 借助 MPK 把系统服务器拉进内核地址空间、用 WRPKRU 做 IPC 因而极快，但受十六域上限限制只能加速有限数量的系统服务器，而 EPK 派生的 HyBridge 让系统服务器仍留在用户态、各占一个私有内存域互不可见，相关服务器放同一 EPT 后多数跨服务器 IPC 只需 WRPKRU、应用到服务器才需 VMFUNC〔15:30〕。在自家微内核 ChCore 上 HyBridge 优于分别基于 MPK 与 VMFUNC 的 UnderBridge 与 SkyBridge；在 Google 的 Zircon 上跑负载时比原生最高快九倍、比 SkyBridge 快约百分之六十六〔17:57〕。作者总结 EPK 是首次尝试把 MPK 与硬件虚拟化结合以获得可扩展且高效的进程内内存隔离〔18:35〕（YouTube EPZ0TiHWZKlJw，[438-1139]，L1）
- 〔OSDI '20〕微软研究院印度所研究员 Kaushik Rajan 报告 Resin：现代大数据查询优化器会在同一查询中反复处理相同数据、产生大量冗余交换阶段，Resin 把 map-reduce 推理前置到逻辑阶段、用两个泛化算子把子查询融合进更少阶段以消除冗余 I/O〔00:08〕。背景是大数据查询编译：SQL 查询经基于数据库优化器的编译产出 map 与 reduce 阶段的 DAG，各阶段以多任务并行处理各自分区，阶段末通过 exchange（shuffle）把数据重新分区以便下一阶段继续数据并行〔00:51〕。在大数据场景下 exchange 是最贵的算子——它要求把数据先落盘再由网络全对全传输，而且每次 exchange 都会引入一个新阶段，因此阶段越少越好〔01:36〕。然而分析标准基准 TPC-DS 发现，一百零四个查询里有四十个被 Spark 优化器生成了多余阶段；其中二十五个平均把百分之五十的时间耗在那些重复处理同一数据的冗余阶段上，更有十六个查询在冗余阶段上花掉超过一半时间〔02:03〕。结论是现行编译器缺少合适的原语：今天的优化器只在 SQL 空间里做纯逻辑重写、对引入多少个阶段毫无知觉，阶段的产生只发生在物理规划时加 exchange 的那一刻〔03:24〕。于是 Resin 改变优化器、让 map-reduce 推理从一开始就进行，目标是产出阶段数尽可能少的计划：它在逻辑阶段就引入一个泛化 map 算子与一个泛化 reduce 算子，再加一批新规则、尽可能把多个算子塞进这两个泛化算子〔03:45〕。效果上，在最冗余的那二十五条查询上 Resin 节省约百分之二十的 I/O，而累计节省的 CPU 时间更高达约百分之二十五——因为消除冗余 I/O 同时减少了序列化、压缩这类由 I/O 派生的计算〔04:42〕。ResinMap 是把每行输入经自定义函数产生多行输出的泛化 map 算子；典型例子是对同一张表（演讲中以 iot logs 为例）各做一次不同过滤与不同列选择后再 UNION ALL，标准计划会重复扫描该表，而 Resin 只需一次扫描加一个带两个 context 的 ResinMap，每个 context 对应 UNION ALL 对每行可能产出的两个输出，代码生成后即为取每行、施加相应过滤、两个条件都满足则产出两行〔05:57〕。它能力相当强：任何仅由 select、project、union 构成的单表查询都能被它用单一阶段实现〔08:07〕。ResinReduce 则是泛化 reduce 算子，按键聚合同键的全部行、每键产出一行；例如同表两次做不同过滤与不同聚合、两侧按同一列分组再 join，标准计划要多个阶段，Resin 只要一个 mapper 加一个 reducer 两阶段——reducer 按两侧共享的分组键（示例中为 ID 列）分组、依各 context 对不同子集施加不同聚合，聚合完已有足够信息用一次 filter 即可模拟掉那个 join〔08:24〕（YouTube EPZ0Xm83hgQZw，[8-572]，L1）
- 〔OSDI '20〕多表查询上的阶段融合演示：一条九个阶段的查询经 Resin 融合为四阶段——先把同样穿越表 signals 的 S1 与 S2 融成 S10，再把 S3 与 S4 融成 S11，随后 S5 与 S6 可融，最后 S7、S8、S9 融为一阶段〔10:42〕。具体机理是：为 S1 与 S2 引入的 ResinMap 承担两侧全部计算、融合后其输出包含两侧任一所需的全部行；融合的一个副产品是需要额外标记以区分融合输出的左半与右半，本例即过滤条件 F1 与 F2；由于这些残余 mapper 与来自 S10 的融合部分运行在同一阶段，Resin 会把本次融合得到的残余过滤做交并运算〔11:54〕。把这些融合阶段代回计划后继续向上融合：S5 与 S6 的两个 join 恰好作用于同一组列，可融成先做 join、稍后再施加过滤的一阶段，而紧随其后的过滤保证即便 join 产出行数超过 S5 或 S6 所需、被进一步 shuffle 的也只有二者真正需要的行〔13:22〕。最终 S7、S8、S9 正是 ResinReduce 模式：同一张表上走两条不同路径做两种不同聚合再把结果 join 起来〔14:18〕。论文还给出这两个算子的参数、语义与实现，说明如何融合所有 Spark SQL 算子并明确各自可融合的条件；尤其证明融合后 shuffle 的行数保证不多于融合前、且平均少得多——这条要求是融合总是带来收益的关键〔15:00〕。实现上是扩展 Spark 的 Catalyst 优化器：加入 ResinMap 与 ResinReduce 的逻辑算子与物理算子，并引入一批新规则，其中融合规则单趟遍历整棵树完成一切可能的融合；随后做 union 与 join 消除——若融合后某子查询的多个消费者确实会再次 join 或 union，则在特定条件下可整个消掉；否则插入 exchange 并保证有两个父节点消费其结果〔15:56〕。评测在 1 TB 与 10 TB 两个规模因子、两种集群上进行，并对阶段较多的四十条查询逐一细评；对照基线本身已做基本 I/O 优化：谓词与投影下推到存储层（数据为 Parquet、可在存储层直接剪列剪行），且当两个 exchange 点交换的数据完全相同时会丢掉其中一个〔16:05〕。结果显示，在 1 TB 下对这二十五条中高影响查询平均加速约 1.4 倍、个别查询高达 6 倍；更重要的是 Resin 在不额外消耗内存的前提下消除 I/O——融合虽增加了每个算子处理的数据量，但幅度不足以推高系统整体内存需求〔18:12〕（YouTube EPZ0Xm83hgQZw，[572-1135]，L1）
