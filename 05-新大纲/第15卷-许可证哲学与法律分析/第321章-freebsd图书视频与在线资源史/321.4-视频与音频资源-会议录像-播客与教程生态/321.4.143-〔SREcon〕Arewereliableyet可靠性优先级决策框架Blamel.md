- 〔SREcon〕可靠性仪表盘与业务对齐。完成指标定义、目标设定与差距评估（目标 25% 以内为绿、25-50% 为黄、超 50% 为红，刻度可按组织定制）后汇总为精简的可靠性仪表盘，可按团队或服务等维度下钻；未知状态（如尚未追踪的 error budget 消耗）以灰色显式标注，以促成跨组织对话、培育承认不完美的透明文化。仪表盘让从工程 IC 到销售 VP 共享同一视图，建立工程师与其他部门的信任与对齐，且流程只规定 what 并直接输入季度 OKR（如 MTTD 提升 25%）。挖掘业务需求靠跨部门对话：所问问题直接对应各部门激励与目标，用业务语言（保护客户信任、最小化 SLA 赔付风险、支持收入增长与续约增购）证明投资更易获批，例如 SRE 负责人请销售负责人用因可靠性问题流失的订单佐证重构项目的必要性；最后演示同一框架适配 Series A 初创公司（重速度、产品反馈与客户关系）的需求。（YouTube EPO255Tk0XiDw，[906.1-1726.4]，L1）
- 〔会议不详〕从数据估计漏洞可利用性（前半）。讲者与亚利桑那州立大学的 Tiffany Bao 等及马里兰大学的 Tudor Dumitraș 合作，指出近十年漏洞检测研究论文与披露漏洞数量同步增长，而可利用性判定手段仍不足：手工或自动 exploit 生成、在野检测只能提供存在性的确证证据，CVSS temporal、微软可利用性指数、Red Hat 等启发式评估指标精度不佳（以阈值以上全预测真的简单预测器测得大量误报）。论文提出 expected exploitability 概念——随时间近似可利用性的期望值，并以三个案例说明挑战：2018 年 Internet Explorer 远程代码执行漏洞（披露后技术文章促成 exploit 开发）、2019 年 Cisco 路由器漏洞（后续 POC 代码被发现在在野 exploit 中，须从 POC 代码与自然语言描述提取特征）、EternalBlue（NotPetya 与 WannaCry 背后，exploit 早于公开披露存在 5 年，涉及 ground truth 标签噪声）。（YouTube EPO2kp2_S9l_U，[7.7-349.8]，L1）
- 〔会议不详〕时变可利用性、POC 特征与标签噪声缓解（后半）。基于逾 20 年的漏洞数据集、约 30 万件公开收集的 artifact 与多来源 exploit 证据，实证 exploit 发布与 artifact 发布高度相关，据此构建部署后持续估计可利用性的监督学习系统，较静态指标与基于手工特征的 EPSS 等数据驱动基线取得大幅性能提升。POC 与功能 exploit 的共同点在于都须触发漏洞：POC 代码复杂度反映 exploit 复杂度、其描述揭示利用所需步骤，团队用程序分析加 NLP 构建特征抽取系统并证明这些特征与先前工作互补。标签噪声方面，exploit 可能私有留存或延迟公开带来 class 依赖噪声，个体来源偏差（如 Symantec 无 Linux 产品致 Linux exploit 缺失）带来 feature 依赖噪声，对至少含四个特征的各标签来源做统计独立性检验证实两类噪声并存；嵌入训练阶段的 FFC 损失函数利用噪声分布先验与噪声概率、降低可疑标签实例的犯错惩罚，可成功纠正两类噪声造成的性能下降，成果已部署为提供工具与 API 的在线平台。（YouTube EPO2kp2_S9l_U，[390.5-784.8]，L1）
- 〔USENIX Security（推测）〕首个基于 TCP 的反射放大攻击（前半）。马里兰大学的 Kevin Bock 介绍放大因子为可引出响应大小除以请求大小，经典 DNS、NTP、Memcached 放大攻击几乎都限于 UDP，而 TCP 因三次握手使伪装受害者的攻击者拿不到完成握手所需信息，历来被认为免疫。本工作的洞察是现代网络已更复杂、中间盒本身可充当放大器：防火墙、IDS/IPS 及国家级审查基础设施预期丢包（见无握手的形式良好请求时只能放行），阻断时又以伪造源地址注入 RST 或大阻断页，等于消解了传统 TCP 反射攻击的握手难题。方法学用专为抗审查设计的遗传模糊测试工具 Geneva（修改适应度函数以奖励从中间盒引出大放大因子）在 Censored Planet 识别的全球审查中间盒上训练 184 次，随后 35 次全 IPv4 互联网扫描，共发现 5 种可触发响应的包序列（如携带被禁内容 HTTP 请求的 SYN 包、无握手的直接请求、SYN 后在 PUSH 或 PUSH ACK 上发送真实请求），并负责任地知会了多国 CERT、防护服务商与相关厂商。（YouTube EPO4Vs_g--5d4，[7.8-359.3]，L1）
- 〔USENIX Security（推测）〕测量结果与无限放大（后半）。分析 Censored Planet 数据选出触发最多中间盒的五个域名（色情、赌博、社交媒体、文件分享与性健康），各中间盒因缺陷与配置而响应不同。全 IPv4 扫描显示数十万 IP 具有危险的高放大因子、另有数亿 IP 充当弱放大器（长尾多为国家级审查器背后数百万地址）；理想攻击者视图下超过 30 万 IP 的放大倍率大于 100 倍，超过 DNS、NTP、Memcached 的 UDP 放大基准，表明 TCP 放大至少与 UDP 同样强大。曲线头部的 mega amplifiers 达 10^6 至 10^8 的因子实为录制停止时机的低估，部分 IP 无限发送流量即无限放大：机制一是 victim-sustained loops（受害者的 RST 反而重新触发审查中间盒再发阻断页，无限循环并冲击上下行链路），二是路由环路——攻击包每绕环一次就重复触发中间盒，有限环路随 TTL 提高带来 240-250 倍的放大提升，并在中国及俄罗斯多个 ISP 发现穿越审查基础设施的无限路由环路；代码与网站见 censorship.ai。（YouTube EPO4Vs_g--5d4，[372.0-724.8]，L1）
- 〔会议不详〕UW-Madison 博士生 Shankar 介绍其与导师 Michael Swift、Nam Sung Kim 合作的 Bolt 系统，目标是将 Linux 处理器重配置（hotplug）提速约 20 倍。变更活跃处理器集合可带来节能（core parking、Moonshot 等拆解式服务器）、应对负载峰值与功耗约束等收益；而 Linux hotplug 最初只是移除故障核的可靠性机制，未把速度当目标，一次重配置需数十至数百毫秒，远慢于硬件睡眠状态切换的 10-100 微秒量级。其三大局限在于：同步（每条通知的全部回调都在关键路径执行）、悲观（完全清空并重新初始化软件结构）与串行（整个过程持全局锁，同一时刻只允许一次重配置，离线/在线各发 down_prepare、dying、dead 等大量消息，系统中约有 50 个内核子系统订阅回调）。（YouTube EPO5gBGJbjPps，[9.8-485.1]，L1）
- 〔会议不详〕Bolt 的设计与评估：把 50 个 hotplug 订阅回调中约 30 个判定为非关键操作并移出关键路径。非关键操作通过延迟清理、复用线程与软件结构（sysfs 等系统信息改为在文件打开时检查 CPU 是否在线）以及用其他锁机制替换 RCU 等手段消除主要开销；新增的批量接口以聚合与并行执行支持多核同时重配置，避免热插拔延迟随核数线性增长。在 x86 与 ARM big.LITTLE 平台上，离线与在线重配置获得约 15-20 倍加速；问答中作者估计 75% 以上的延迟源自 Linux 自身设计，并坦言与 crossover proxy、Barrelfish 等已能接近 10 微秒（含软件开销）的方案相比仍有长路要走。（YouTube EPO5gBGJbjPps，[692.6-1246.6]，L1）
- 〔SREcon（推测）〕华为爱尔兰研究中心软件工程师分享近三年与 SRE 团队保障华为云可靠性的经验，主题是大规模分布式系统的爆炸半径削减。援引 Charles Perrow 在《Normal Accidents》中的论断指出系统复杂性使故障不可避免，故障源头可归为黑天鹅、盲点与权衡三类；建议把爆炸半径削减纳入系统设计并作为可靠性度量之一，并在爆炸半径与弹性/成本之间权衡（单租户隔离模式难以维护、全多租户共享资源池则爆炸半径过大，无黄金法则）。重点介绍单元化（cell-based）架构：把大集群拆成数百个自包含的最小扩缩单元（扩容即加单元），由 cell router 层分发流量，无状态层最易实施，数据同步的复杂性可卸载给 Google Spanner、DynamoDB、Cosmos DB 等提供跨可用区同步能力的专用数据库。（YouTube EPO6RV6U2Pj2k，[20.6-417.4]，L1）
- 〔SREcon（推测）〕单元化架构的代价与时间维度的爆炸半径治理。拆成上百个小单元会带来基础设施成本（100GB 缓存无法均分为每单元 1GB，实际需 5GB 以上）、系统容量与运维成本，解法是 everything as code 加自动化部署与配置。时间维度上，均值 MTTR 不如最大恢复时间（maximum time to recover）有意义，可按故障类型选用自愈（虚拟机故障、基础设施健康状态触发的自动/主动迁移）与跨区域切换策略；演讲者结合其构建多层 DNS 全局负载均衡（L4/L7 全栈方案）的经验，指出 DNS TTL 及部分 ISP 不遵守 TTL 的问题，认为 BGP/anycast 更可靠但伴随 BGP flapping 复杂性，并提及 lamp post exposure 新概念以及基于形式化规约、模型检查与 SMT 求解器的可靠性形式化验证方向。（YouTube EPO6RV6U2Pj2k，[613.0-922.5]，L1）
- 〔会议不详〕哈佛大学博士生 Warren 介绍新一代审计系统 OmniLog。审计日志是网络攻击取证分析的基础，但现代攻击者已能攻陷内核，使审计系统在攻陷后不可信、驻留本机的日志可被删除或篡改；依赖受保护存储（经网络栈或 USB 异步写入外部设备）的既往方案会因异步批量化在内核内存中留下易被篡改的日志记录，而这恰恰是攻击者攻陷内核前最后执行的一批安全事件。团队分析了 GitHub 上 164 个概念验证漏洞利用来检验规则集的事件覆盖：表现最好的学术规则集覆盖率仅 15.4%，多数规则集对不少漏洞连一条事件都不记录，而这些漏洞共调用 146 个不同系统调用，因此只有记录全部系统调用才能保证事件覆盖。（YouTube EPODXEubaSeFY，[8.4-298.5]，L1）
- 〔会议不详〕OmniLog 的设计与实现：构建受保护环境实现同步日志保护，并端到端重设计日志流水线。auditd 配置为记录全部系统调用时开销已高得惊人（这还是异步日志的情形）；OmniLog 借助 x86 的 VMX/SMM 与 ARM 的 EL3 等 CPU 特性隔离内存区域与磁盘，系统调用执行前把日志同步复制进受保护内存缓冲区、再异步写入受保护磁盘，并由高特权环境处理日志保护、持久化与电源管理以保证关机前日志落盘。流水线优化把最长约 1KB 的 ASCII 日志改为压缩二进制格式（平均 64 字节，生成延迟从约 12000 周期降至约 3000 周期），配合每核内存分区消除核间争用、每核双缓冲与后台线程缓解写盘停顿；ARM 与 x86 原型在全系统调用规则集下几何平均开销分别仅 3.2% 与 3.6%。（YouTube EPODXEubaSeFY，[299.1-612.2]，L1）
- 〔USENIX Security（推测）〕MIT 的 Alexandra（与 Matt、Henry、Vinod 及 Google 的 Sarah 合作）讲解简单快速的单服务器隐私信息检索（PIR）。现代 PIR 的通信量已可随数据库规模只按多对数增长，但服务器端计算受下界约束——服务器每次查询必须触碰数据库每个位置、做近乎全库线性扫描；以服务器吞吐量（GB 每核秒）为指标，其两个新方案 Simple PIR 与 Double PIR 达到约 10 GB/核秒，比先前工作快约一个数量级（ProtoPIR 为基于类似想法的同期独立工作，且大吞吐以通信开销为代价）。核心技术是把 Kushilevitz-Ostrovsky 1997 年的矩阵式单服务器 PIR 与带预处理的快速线性同态加密组合：加密由固定随机大矩阵 A 与消息相关小向量 B 组成，D·A 可一次性预计算（因 A 维度大，占 99.9% 以上的计算量），每条消息只剩每条目一次 32 位乘加的 D·B。（YouTube EPODdWD_gvbN8，[20.3-354.6]，L1）
- 〔USENIX Security（推测）〕Simple PIR 的参数、评估与部署展望。基于学习误差（LWE）假设，n 字节数据库的一次性 hint 约 4000·√n 字节，之后每次查询仅需 8√n 字节，服务器对数据库每字节恰做一次 32 位乘加、无隐藏常数；开源实现约 1600 行代码、不依赖外部库，在 AWS C5n 裸金属实例单线程、1GB 数据库上达到 10 GB/核秒，距机器内存带宽仅 20%，吞吐与最快的双服务器 Xor PIR 相当但不依赖任何信任假设、仅靠密码学困难假设；对不超过 1 字节的短记录可把 hint 缩到与数据库规模无关的恒定 16MB。展望包括进一步压缩通信、用 Double PIR 隐私审计网页证书、创业公司 Bliss 用 Double PIR 做密码泄露私密检查，以及当年秋季 SOSP 上用 Simple PIR 构建隐私网页搜索的新工作。（YouTube EPODdWD_gvbN8，[388.8-697.9]，L1）
- 〔USENIX ATC〕韩国汉阳大学的 Won Gun 介绍新型协作日志模式 WardIO（转写中亦作 Word I/O、war mode），与 Nam Sung Kim、Yoo Ji-won、Bum Sung Nam 合作完成。SQLite 作为 Android/iOS/Tizen 的内嵌数据库与 ext4 文件系统交互时存在“日志之日志”异常：在应用中输入两个字符（hi），经 SQLite 与 ext4 双重日志最终给存储带来 40KB 写放大，一次插入操作需 5 次写调用与 4 次 fsync。通过重建 ext4 分析分配型/非分配型写、buffered I/O 与直写（Direct I/O）的 I/O 行为，发现非分配型 Direct I/O 不伴随文件系统日志，这是消除该异常的关键；但把 Direct I/O 用作 SQLite 日志模式要解决三大问题：提交时避免 SQLite 元数据更新、让 I/O 大小与扇区/块设备对齐、以及让 Direct I/O 写更高效且对闪存友好。（YouTube EPODf7TfvgHJM，[10.9-642.65]，L1）
