# 316.4.5 IgorSysoev口述nginx起源与设计取向2002年春夏之交以业余爱好启动

- Igor Sysoev 口述 nginx 起源与设计取向：2002 年春夏之交以业余爱好启动，目标是可靠、易配置、能承载上千连接并服务静态文件与反向代理的服务器；他最得意的在线升级功能由同事提议、本人实现，此前仅个别 IRC 服务具备类似能力；FreeBSD 是其长期的工作与家用首选平台，nginx 依赖 sendfile、accept filter、kqueue 等 FreeBSD 特性，并以更高效的内核接口把瓶颈从 Web 服务器推回内核网络、磁盘与 VM 子系统。（BSD Now EP124，[1657.60-2172.66]，L1）
- Theo 的 pledge 状态公告称 5.9 将禁用 paths 参数，理由是无暇复查内核代码是否无 bug，拟用下个六个月开发周期重新评估该接口并复审代码树；基础树 652 个 ELF 二进制中 451 个已用 pledge、约 154 个未来可纳入；Chromium 的渲染与 GPU 进程已启用 pledge，但因 Mesa 解析 /etc/drirc 与 ~/.drirc 暂需 rpath，团队目标是移除 rpath 以防恶意插件读取 SSH 密钥；同期 Firefox 走 W^X、Chrome 走 pledge，形成互补格局。（BSD Now EP124，[1181.84-1354.90]，L2）
- Gleb Smirnoff 在上年度 FreeBSD Storage Summit 的幻灯梳理 sendfile 谱系：FreeBSD 1.0 时代 FTPD 只能在用户态反复读写；该系统调用约 1997 年首现于 HP-UX 11.00，1998 年由 FreeBSD 3.0 与 Linux 2.2 跟进；Netflix 主导的异步化让调用发起后即返回、完成时由内核通知，单机吞吐自 25 Gbit/s 提升至 35 Gbit/s，另有可做 TLS 加密并利用卸载卡的版本已在 AsiaBSDCon 报告；遗留难题是 sendfile 的内核缓冲与 ZFS ARC 可能双重缓存同一文件，社区设想把 ARC 独立成模块乃至供 UFS 使用。（BSD Now EP124，[2852.20-3119.24]，L2）

- Adam Dunkels 自述其为瑞典计算机科学研究所（SICS）网络研究员，专攻内存仅数百字节量级的超小型网络化嵌入式设备；其主导的 Contiki 2.0 于 2007 年春发布，三大新特性为 ELF 格式动态加载模块（取代此前的预链接自定义格式，允许同一网络混布多版本内核）、protothreads 轻量线程与 RIME 低功耗协议栈。（BSDTalk EP107，[59.55-90.31, 640.47-791.38]，L1）
- Contiki 的差异化定位在于运行时动态加载与卸载程序：Dunkels 指出通用操作系统自 1960 年代即支持动态装载，但嵌入式领域默认将软件写入 ROM 后不可更改，而远程传感器（如投放入波罗的海后整个冬季不可触及的水质监测节点）必须支持运行中重编程，这一现实需求塑造了整个系统架构。（BSDTalk EP107，[199.19-263.0, 126.23-157.48]，L1）
- protothreads 以每线程仅 2 字节状态存储替代完整线程约 200 字节的栈预分配，在保留类线程线性编程模型的同时消除内存开销；uIP 栈以约 5K 编译代码、200 字节至 2K 可配置 RAM 的足迹实现 2001 年时最小的 RFC 兼容 IP 栈，RIME 则针对无线电收发能耗远高于 CPU 指令执行的现实，以头部压缩与非 TCP 原语（本地广播、网络泛洪、二进制数据分发）适应低功耗射频链路。（BSDTalk EP107，[717.01-768.37, 329.55-349.55, 366.91-459.60]，L1）
- Josh Berkus 自述其任 PostgreSQL 核心团队七人小组成员，该团队决定 PostgreSQL 的版本发布时机；Sun Microsystems 决定支持 PostgreSQL 项目并在 Solaris 平台销售支持服务后聘请其为 PostgreSQL 战略负责人。其此前履历包括 OpenOffice.org 项目负责人（为加入 PostgreSQL 核心团队而辞任）、Software in the Public Interest 董事会成员与 O'Reilly 开源大会委员会成员。（BSDTalk EP110，[49.23-95.41, 742.27-801.59]，L1）
- 关于项目接续史的当事人叙述：PostgreSQL 前身 Postgres 于 1986 年在伯克利加州大学启动，作为大学项目运行十年后校方 CS 系失去兴趣；此时校友与互联网社区中的职业使用者已将其投入生产，伯克利决定放手时，包括一位 FreeBSD 操作系统主要贡献者 Marc Fournier 在内的开发者群体将其改造为真正的开源项目并上线 CVS——1995 年开始、1996 年完成，社区遂以 1996 年 7 月 8 日为开源项目诞生日；十周年时在多伦多举办逾百人开发者峰会。 [存疑脚注] 转写作“Mark Fournier”，按 FreeBSD 核心团队与 PostgreSQL 基础设施史应为 Marc G. - Berkus 的技术栈迁移史完整呈现了 1990 年代小企业咨询市场从专有软件向开源的转换动因：其自立门户服务小企业与非营利客户后，发现专有技术许可费与 MSDN 订阅侵蚀利润，而微软于 1997 至 1998 年停止补贴转向盈利，SQL Server 起步价从约 700 美元跃至 3000 美元；同时 SQL Server 加 COM+ 方案每两三周随机故障，迫使其每两周上门维护；MySQL 当时仍是共享软件且其 2.x 版不支持表连接，无法满足其 SQL 专家标准；转投 PostgreSQL 后，社区对其 SQL 合规性质疑的开放接纳与 MSDN 论坛的封禁文化形成鲜明对照，首周即融入项目——社区文化本身成为技术选型的决定因素。（BSDTalk EP110，[529.11-741.71]，L1）
- Berkus 对数据库生态的定位划分：PostgreSQL 居高端，面向需支撑海量连接、TB 级数据与长事务、以替换 Oracle、DB2、SQL Server 2005 为目标的场景；Derby 与 Sleepy Cat（即 Berkeley DB）一类居嵌入式端；MySQL 居中，规模与扩展性占优但不及 PostgreSQL，对用户数据库知识要求也更低。PostgreSQL 的比较优势包括 BSD 许可证允许与专有软硬件捆绑（其最流行的分发方式之一）、活跃企业用户转化为社区成员从而获得对软件未来的归属感与控制感、独立安全评级（Database Hackers Handbook 中高于 Oracle 与 DB2）、提交即持久的可靠性保证，以及源自对象关系设计的可编程数据库对象——PostGIS 借此成为全球第二大 GIS 数据库系统（仅次于 NavTeq），基因组学领域亦出现以专用数据类型扩展 PostgreSQL 的项目。 [存疑脚注] 基因组项目名转写作“BlastGres”，确切名称待核；NavTeq 为转写原貌，当作 Navteq（BSDTalk EP110，[802.59-1047.13, 884.21-927.73]，L1）
- Fossil 的定位是为其自身与 SQLite 的配置管理而设计的分布式软件配置管理系统，不属三大主流之列：它把分布式 bug 跟踪与 wiki 与版本控制纳入同一包，离线时可看 bug、加评论、改代码、改 wiki，联网后自动同步；单文件无依赖二进制适配公司统一配置笔记本的场景；内置 web 界面随 fossil ui 一键启动本地服务器并拉起浏览器，克隆 Fossil 项目本身即可在本地得到连同全部历史的完整官方网站。（BSDTalk EP194，[406.12-714.12]，L1）
- 存储设计上，Fossil 仓库被定义为无序的 artifact 袋，每个 artifact 有简单而明确界定的文件格式，设计目标是让尚未出生的人也能使用、阅读与扩展这一长期格式；现行实现把 artifact 以 delta 与 zlib 压缩存入 SQLite，但此属实现细节，他人可重写为兼容实现；SQLite 九年的 CVS 历史（三百余兆）导入后仅约三十兆，同步协议高效到可在拨号网络使用。（BSDTalk EP194，[807.48-930.76]，L1）
- Fossil 强制以整个项目连同全部分支为同步单位，被当事人视为特性而非限制：他要迫使项目成员始终共享全部工作，保留所有未成功的丑陋分支与反复犹豫；其原始动机是高可靠软件需要默认完整、可审计且不可伪造的开发史，以此对照 Git 用户热衷的 rebase——把长串修订压缩成干净提交，本质是把历史改写得比实际更整洁。（BSDTalk EP194，[1005.32-1146.12]，L1）
- 权限模型兼取两端：克隆不包含用户安全数据库，全局状态即全部 artifact，而各仓库可设本地权限；Fossil 自托管的三个主仓库只允许已签署版权转让者推送，任何人可克隆并本地随意提交，但无密码不得推回中央；已有第三方克隆 SQLite 仓库加入自定义修改对外分发，当事人称此为分叉友好并视之为开源本义。（BSDTalk EP194，[1156.60-1282.80]，L1）
- YUI 库源于约一年半前 Yahoo 内部的平台化倡议：将分散的前端开发整合为平台工程，集中代码库以鼓励复用与一致性、在各产品组间标准化；作为发布激励，Yahoo 公开原始源码与完整 API 文档，并分享应对各浏览器开发怪癖的经验，供撞过同样墙壁的开发者复用。（BSDTalk EP33，[69.44-147.94]，L1）

- lighttpd 定位为极快、极轻量的 Web 服务器，目标是在低资源占用下维持大量并行连接，面向大量短连接的 Web 2.0 应用；与 Apache（在不使用事件 MPM 时每连接占一进程或线程）不同，lighttpd 为完全事件驱动的单进程单线程架构，无线程也无 fork，基于非阻塞 I/O——等待中的连接只是进程内的一个文件描述符加少量内存；仅受单进程文件描述符数限制且可调，可同时维持一万至两万连接；Keep-Alive 场景下等待连接近乎零成本，这对 AJAX 类低延迟小请求尤为关键。（BSDTalk EP61，[179.02-344.98]，L1）
- 项目起源：最初是 Boa、Mathopd、thttpd、Zeus 一类擅长静态内容的小型 Web 服务器（当年常被用作 Apache 的静态卸载前端），但自始即带 FastCGI 与 PHP 支持、sendfile 等系统级优化和 kqueue 等事件接口，迅速长成全功能服务器；作者自述直接动因是读到 Dan Kegel 论 C10K 问题（单机万级并行连接）的论文，想以此做概念验证，结果一做即快。（BSDTalk EP61，[88.68-146.44]，L1）
- 事件接口分层决定扩展性：select 与 poll 在所有平台可用（macOS 的 poll 为 select 模拟）但先天受限——select 默认上限 1024 连接、poll 每次返回全部描述符须线性扫描，连接越多系统调用开销越大；kqueue（BSD）、epoll（Linux）、dev-poll（Solaris）只返回发生变更的描述符，使服务器可按事件量而非连接量扩展，接近线性；lighttpd 维护多个事件处理器以适配各平台。（BSDTalk EP61，[539.84-733.94]，L1）
- 安全设计上，lighttpd 从不使用 C 字符串库函数，一切字符串操作先行长度检查、先确认内存再写入，以自有字符串函数集消除缓冲区溢出这一 C 语言服务器的主要攻击面；长度可知同时带来速度（便于追加与复用）；开发中以 Valgrind 与 KCacheGrind 检查性能与内存；重大漏洞约半年前与一年半前各一次，均与 Windows、macOS 默认大小写不敏感的文件系统有关——改变大小写即可绕过安全模式检查，Windows 从非其推荐的生产环境，macOS 则因 Web 服务器部署更多而受影响更实；对外提供 mod_secdownload 限时哈希 URL（10-30 秒有效，防深链盗链）与 X-Sendfile 式头部卸载：后端完成 LDAP、数据库、Kerberos 或 NTLM 等认证后交由服务器以 sendfile 零拷贝发送，兼顾认证安全与传输效率。（BSDTalk EP61，[1237.72-1657.12]，L1）
- 1.5 版本重写核心组件：Rails 社区改用 Mongrel（Ruby 小型 HTTP 服务器）以 HTTP 与前置服务器对话，暴露了现役 lighttpd HTTP 代理模块的最大短板——不处理故障转移，后端宕机时连接直接报错、由客户端重试其他后端；新版 mod_proxy_core 整合 FastCGI、SCGI、HTTP 协议，向后端提供 keep-alive 与 HTTP/1.1，内置轮询与哈希两种负载均衡、故障转移，并向后端提供 sendfile 支持；哈希均衡按 URL 分区，使同一页面的请求恒达同一后端，从而大幅提升后端缓存利用率。（BSDTalk EP61，[733.94-941.52]，L1）
