# 328.2.10 借语义的第二次回流：BSD 从网络共享模式、信号表、fork 继承语义三处重新进入 Linux（2024–2026）

BSD 与 Linux 之间"借语义"的路径不止一条，也不止发生在 2010 年前后：到 2024 与 2025 年，NFS 与 SMB 共享模式的互操作讨论、信号表容量扩展的补丁集、fcntl UAPI 的 32 位常量补齐，把 BSD 血统以三种不同姿势再次带回 Linux 内核主线的接口讨论场，把"借语义"从"内核内部对齐"扩展到"跨协议、跨层、跨进程边界"的三向渗透

**网络共享模式的互操作讨论首先把 BSD 文件锁标志抬到 Linux 接口层面**：一份针对 NFS 与 SMB 共享模式冲突的补丁提案把 open 时锁标志作为跨协议仲裁手段，援引 GNU libc 文档列出 `O_EXLOCK` 与 `O_SHLOCK` 两类 BSD 风格标志；Jeff Layton 的回应一句 "Nice. I wasn't aware of those BSD flags." 表面上是维护者的知识补漏，实质上是 BSD 文件系统锁词汇被正式引入 Linux 共享模式接口设计的记录，NFS 与 SMB 在 POSIX 语义之外的第三套锁模型被允许在 glibc 头部以 BSD 命名出现

**信号表容量扩展的争论紧接着把 BSD 信号语义摆到 Linux 信号表取舍的对象上**：Walt Drummond 提交把信号数量上限从 64 扩至 1024 的补丁集，理由是与 glibc 与 musl 的既有上限一致；Eric W. Biederman 强烈反对扩张，在转述补丁条目时把添加 BSD 信号列为测试项，原文 "Add BSD SIGINFO (and VSTATUS) as a test."，并借机梳理 SIGPWR 默认语义的旧争，把 BSD 信号在 Linux 信号表中的取舍显形为一次公开的对账，BSD 信号在 Linux 信号体系里既不是缺省也不是例外，而是一个被反复点名、需要被单独测试的兼容分支

**glibc 头文件的 32 位常量补齐则把 BSD 语义直接写入内核 UAPI 的注释文字**：Jeff Layton 向 glibc 提交 fcntl-linux.h 补丁，新增 `F_OFD_GETLK32` 等 32 位常量，作者建议常设 64 与 32 两套宏并按编译模式重定向；所改注释即内核 UAPI 对 F_OFD 锁的语义说明，把该语义与 BSD flock 锁在 fork 后的可继承性对照，原文 "inherited across fork or clone with CLONE_FILES like BSD (flock) locks"，BSD 血统在此不再只是"曾经借用"的接口，而成为解释 Linux 内核 UAPI 语义时不可省略的对照坐标

从 NFS 与 SMB 的 O_EXLOCK / O_SHLOCK 到 Linux 信号表的 SIGINFO / VSTATUS 再到 glibc fcntl-linux.h 里 flock 与 BSD 的可继承性对照，BSD 血统在此从许可证层与 ABI 层的旧战场，转成跨协议、跨层、跨进程边界的新一轮接口语义回流；GPL 传染性与 BSD 宽松条款作为 1997 年以来两派许可证哲学的主脉，在此之外多了一条更细、更慢、也更难察觉的支线，即接口语义、命名与对照关系的持续引用，这条支线不需要判决或和解来裁决，只需要补丁提交者在下一次接口设计时是否愿意在注释里写下 "BSD" 这三个字母
