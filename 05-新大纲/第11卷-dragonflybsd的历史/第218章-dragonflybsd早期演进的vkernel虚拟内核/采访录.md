- 受访者：Matthew Dillon，时任 DragonFly BSD 项目创始人兼单一决策核心

**字段 2 采访摘要**

Dillon 在 23 年间（2003-2026）以“设计 + 实现 + 提交”三步一体方式推进 DragonFly 所有重大架构决策，dragonfly.duckdb 显示核心子系统首引 commit 均由其一人提交：LWKT（`8ad65e080342`，2003-06-20T02:09:59Z）、HAMMER（`8750964d1997`，2007-10-10T19:37:25Z）、HAMMER2（`703720e4d599`，2012-02-26）、vkernel（`39619464950a`，2006-10-22）。DragonFly 无 Core Team 选举机制、无 Foundation 法律实体（dragonflybsd.org/foundation/ 页面 404）、无公开 bylaws，Dillon 作为创始人对技术路线拥有最终裁定权。dragonfly.duckdb contributors 表显示 Dillon 合并 10666 条 commit，与第二名 Wildner（10846 条）体量相当，但在核心子系统设计决策上唯一独立。23 年间 DragonFly 无公开重大技术路线分歧事件（对比 FreeBSD 5.x SMPng 争议、NetBSD 2007 Core Team 解散事件）。

- 总纲 10“动手者创造历史”——项目史观总纲第 14 章 14.2 节原文“真正推动 BSD 的是‘Get your hands dirty’（动手去做）的人，而非旁观者”“真正的问题不在于技术发展的程度，而在于是否动手”。Dillon 单一决策模式直接塑造 DragonFly 技术路径——LWKT 的消息传递架构、HAMMER 的写时复制设计、vkernel 的用户态虚拟化均出自 Dillon 个人设计，与 FreeBSD Core Team 集体审议后推进 GEOM/ZFS/bhyve 的路径截然不同。须区分项目统摄史观主张与项目统摄史观批评的对象：项目统摄史观批评的是“旁观评论者”以理论框架替代动手实践，而主张历史由动手做事的老实人创造——Dillon“设计 + 实现 + 提交”三步一体的工程实践，是对“动手者”定位的工程化呈现。
- 总纲 17“证明世界先于解释和改造世界”——项目史观总纲第 25 章原文“问题不在于解释世界和改造世界，而在于证明世界”。Dillon“设计 + 实现 + 提交”三步一体的工程实践反映“证明世界”的工程认识论——核心子系统设计文档散见 commit message 与邮件列表发言，无系统性 RFC/PEP 公开审议流程，是以可运行代码“证明世界”，而非以理论先行解释。须注意项目统摄史观批评的对象是“解释与改造的二分”这一形式主义框架本身，而非简单的“实践先于理论”。
- 总纲 5“没有必然性，只有偶然性”——项目史观总纲第 25 章原文“每一个关键人物、每一次 fork、每一个技术决定，都是不可替代的偶然”。Dillon 个人精力与健康状况直接影响项目存续——dragonfly.duckdb 显示 2018-2020 年间 Dillon commit 频率显著下降，同期项目整体 commit 量同步下降，反映 Dillon 个人节奏与项目节奏的高度耦合。须区分项目统摄史观主张与项目统摄史观批评的对象：项目统摄史观批评的是“将项目存续归结为必然规律”的目的论叙事，而主张偶然性是历史的根本结构——Dillon 个人状况作为偶然因素，塑造 DragonFly 项目的存续节奏。

**要点**：

- Dillon 阐明 DragonFly 1.8 最具分量的特性是 vkernel：以普通进程形态运行于真实 DragonFly 内核之上的完整 DragonFly 内核，思路近似 User Mode Linux，但与 Xen 支持多客户系统不同，它只支持 DragonFly 自身的嵌套运行。（BSDTalk EP98，[51.8-65.72]，L1）
- vkernel 的实现仅依赖三项新增的通用机制——信号邮箱（signal mailboxes）、可经 mmap 映射的虚拟页表、以及受用户完全控制的 VM 空间管理；Dillon 明确建议其他 BSD 项目审视并采纳这些机制，而非完全依赖 QEMU/VMware 做内核虚拟化。（BSDTalk EP98，[1202.34-1302.26]，L1）
- 1.8 版本以底层工程为主：缓存一致性管理部分并入内核、命名空间拓扑重构并重写 nullFS 以支持 jail/chroot 场景下的只读挂载、文件系统 API 为 SysLink 协议预作清理、并引入 GCC 4.1 形成以环境变量切换多编译器的体系（基础编译器仍为 3.4），为项目第二阶段的集群目标铺垫。（BSDTalk EP98，[469.1-583.34]，L1）
- Dillon 宣告项目进入下半场：SMP 基础设施基本就绪，第二阶段主线是集群、SysLink 链路协议与新文件系统；他预计 2.0 不会在生产环境携带新特性，2.1 才是真正落地新文件系统的版本，并直言不愿使用 1.10 这类字符串排序混乱的版本号。（BSDTalk EP98，[706.12-743.92]，L1）
- 关于自 FreeBSD 分化后的代码互通，Dillon 给出分层评估：应用层走 pkgsrc 相当省力，缺陷修复在两树之间双向取用几乎无痛，但整块驱动替换（如移植 FreeBSD 新 ATA 驱动）因 DragonFly 驱动基础设施已显著分叉而代价高昂。（BSDTalk EP98，[605.18-674.7]，L1）

**史料**：

- 本期可核验的一手材料包括：DragonFly 1.8 中为 vkernel 新增的系统调用与代码实现（信号邮箱、虚拟页表 mmap、VM 空间管理三要素）、Dillon 在项目网站发布的开发日志与博客中关于文件系统选型的讨论，以及 release 与 head 分支的维护实践。（BSDTalk EP98，[452.74-1259.5]，L1）

**史观**：

- 总纲10 动手者创造历史：Dillon 自述其工作风格是不深读研究论文，而是提取各家文件系统的可取思想后从头自行实现；这种以动手者个体工程创造替代文献路径的姿态，正是动手者创造历史的一手例证。（BSDTalk EP98，[927.96-944.12]，L1）
- 总纲9 经验优先：vkernel 的立项动机出自直接的工程经验：内核开发中“测试—修改—再测试”的循环在 QEMU/VMware 上过慢，vkernel 将启动压缩到五秒左右并支持在真实内核上以 GDB 实时调试，说明这一技术决策由开发体验而非理论论证驱动。（BSDTalk EP98，[79.0-104.28]，L1）

**辨析**：

- Dillon 估计移植 ZFS 的耗时与按同类原则自建新文件系统相当，并断言 ZFS 本质是海量存储而非集群文件系统；此判断出自其个人经验而非公开测算，且他自认不深读研究文献，采用时应存疑待验。 [存疑脚注] ZFS 移植成本与自建相当的估计系 Dillon 个人经验判断，未见公开量化依据；转写存在乱序与重复标记，时间戳经重排后理解（BSDTalk EP98，[756.0-777.98]，L4）
