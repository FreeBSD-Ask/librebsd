# 240.7.3 传统 mutex 与 BGL（Big Giant Lock）→ DragonFly token 机制（2005-2007）

**要点**：FreeBSD 4.x 继承自传统 BSD 的 BGL（Big Giant Lock，亦称 MP lock）在 DragonFly fork 初期仍大量保留，1.0 公告将 “移除 BGL” 列为下一阶段目标；DragonFly 1.10（**2007.8.6** 发布）引入 token 机制——LWKT 框架下的轻量级同步原语，让线程在持有时可被抢占，避免 mutex 的死锁与优先级反转问题；token 由 Dillon 设计，是 DragonFly 区别于其他 BSD 的关键同步机制，1.10 之后 BGL 在 DragonFly 中逐步被 token 替代；同期 FreeBSD 5.x/6.x 继续推进 SMPng 细粒度锁，与 DragonFly token 路径根本分化；DragonFly 官方 history 页面记载：
    > the token, lends itself directly to ease of maintenance and understandability of the kernel
    token 与 mutex 的关键差异对照如下：
    | 维度 | FreeBSD mutex | DragonFly token |
    |---|---|---|
    | 持有时可抢占 | 否 | 是 |
    | 同步原语类型 | 自旋锁/睡眠锁 | LWKT 框架下轻量级同步原语 |
    | 死锁风险 | 较高 | 较低（持有时可被抢占） |
    | 优先级反转风险 | 较高 | 较低 |
    | 多核扩展性 | 适配现有代码 | 适配重新设计 |
    | 学习曲线 | 较平缓 | 较陡 |
**史料**：DragonFly 1.10 release notes；Dillon 的 token 设计文档；DragonFly 源码 `sys/sys/lwkt_token.h`；DragonFly 官方 history 页面 ［A］

**史观**：总纲第 17 条——软件工程：token 机制是软件工程中 “避免锁竞争” 哲学的极致实现，体现 DragonFly 形式主义化的工程路径；总纲第 3 条——形式主义膨胀：token 是 Dillon 将 “轻量级同步” 哲学固化为代码结构的形式主义化实践

**辨析**：1.10 的精确发布日期在不同来源中存在差异——日文 wdic 记载 **2007.8.6**，本卷 50.4.1 节沿用 ~~2007.11~~ 的说法，需以 DragonFly 官方 release notes 为准；token 与 mutex 的性能对比缺乏权威基准——需对照同硬件同负载核验；BGL 的移除是渐进过程而非 1.10 一次性完成，需对照 commit log 考据具体移除时间
