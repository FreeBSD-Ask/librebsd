# 255.2.1 无独立 VSA 公告系列的安全响应机制


**要点**：DragonFly BSD 采用 Matt Dillon 单一决策核心的治理模式，Dillon 作为 founder 对技术路线拥有最终裁定权；dragonfly.duckdb dragonfly-src 仓库统计显示 Dillon（合并 <dillon@dragonflybsd.org>、<dillon@apollo.backplane.com>、<dillon@backplane.com> 等邮箱）共提交 10666 条 commit（首条 2003-06-17T02:57:24Z，末条 2026-06-10T11:36:47-07:00），与第二名 Sascha Wildner（10846 条，2004-12-17 至 2026-05-21）体量相当——但在 LWKT、HAMMER、HAMMER2 等核心子系统设计中 Dillon 是唯一决策者；早期 tagger 角色（v2.x 系列 2008-2009）由 Simon Schubert 担任，2012 年起由 Justin C. Sherrill（贾斯廷·C·谢里尔） 担任（v3.0.0 至 v6.4.2），2022 年 12 月 v6.4.0 由 Antonio Huete Jimenez（安东尼奥·韦特·希门尼斯） 担任 tagger——tagger 角色更替表明 release engineer 职能由多人分担，但架构决策始终归 Dillon

**史观**：组织结构塑造技术路径：Dillon 单一决策核心模式直接塑造 DragonFly 技术路径——LWKT 的消息传递架构、HAMMER 的写时复制设计、vkernel 的用户态虚拟化均出自 Dillon 个人设计，与 FreeBSD Core Team 集体审议后推进 GEOM/ZFS/bhyve 的路径截然不同；Dillon 在 FreeBSD Core Team 中曾属边缘者（2003 年因争议失去提交权限触发 fork），在 DragonFly 中转为绝对中心——第 14 章边缘者贡献的具体显现

**辨析**：Dillon 治理模式的“独裁”性质在不同叙事中存在评价分歧，Linux 社区以“bus factor 极低”批评之，DragonFly 社区以“工程效率高”辩护之——两种评价各有所据，DragonFly 持续运行 23 年（2003-2026）是事实，但同期 commit 频率从 2005 年峰值 4194 条降至 2024 年谷值 277 条再回升至 2026 年 916 条也是事实；DragonFlyBSD Foundation 的成立年份在部分叙事中记为 2007 年 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］——dragonflybsd.org/foundation/ 页面截至 2026-07-22 返回 404，无法从官方来源核实注册年份与章程文本，须以美国国税局 501(c)(3) 公开数据库或州务卿注册记录核验

**文献**：dragonfly.duckdb dragonfly-src 仓库 contributors 表；dragonfly.duckdb dragonfly-src 仓库 tags 表；DragonFly BSD mailing lists [EB/OL]. <https://www.dragonflybsd.org/mailinglists/> ［A］

**要点**：DragonFly BSD 项目不设独立的 Vulnerability Security Announcement（VSA）公告系列，与 FreeBSD（FreeBSD-SA 系列）、OpenBSD（errata 公告系列配合 **signify(1)** 签名与 **syspatch(8)** 二进制更新）、NetBSD（NetBSD-SA 系列）形成鲜明对比。据 2026-07-23 公告考据（详见 `原材料/研究/考据记录/20260723_announcements-dragonfly.md`），检索 DragonFly BSD 官方网站未发现名为 VSA、Security Advisory、DragonFly-SA、DF-SA 的独立安全公告页面，**dragonflybsd.org/docs/developer/Security/** 返回 404 Not Found。DragonFly BSD 的安全修复机制为：直接向源码仓库提交修复 commit，由用户通过 `git pull` 跟踪 release 分支并重新编译 `world` 与 `kernel` 获取修复；第三方软件漏洞通过 DPorts（基于 FreeBSD ports）更新。各版本 release 页面提供 errata 子页面（如 **dragonflybsd.org/release64/errata6_4.shtml**、**dragonflybsd.org/release20/errata2_0.shtml**）记录该版本发布后回溯的 bug 修复，但 errata 不等同于独立的安全公告系列

**史料**：DragonFly BSD 官方网站（dragonflybsd.org，截至 2026-07-23 无独立 SA/VSA 公告页面）；**dragonflybsd.org/docs/developer/Security/** 返回 404 Not Found；各版本 errata 子页面（**dragonflybsd.org/release64/errata6_4.shtml**、**dragonflybsd.org/release20/errata2_0.shtml**）；FreeBSD Security Advisories 官方存档（freebsd.org/security/advisories/）；OpenBSD errata patches 存档（openbsd.org/errata.html）；NetBSD Security Advisories 存档（netbsd.org/security/advisories/）；`原材料/研究/考据记录/20260723_announcements-dragonfly.md`（VSA 系列不存在的考据结论，VSA 公告总数 0 条） ［A］

**史观**：社区治理：DragonFly 无独立 VSA 系列是 Dillon 个人主导治理模式在安全响应维度的具体显现——Dillon 个人能力替代形式化流程，在 2003-2015 年间 Dillon 主导代码贡献的背景下尚可运转，但 2024 年后 Dillon 代码贡献量持续下降（2024 = 22、2025 = 38、2026 = 19 条 commit），无形式化安全公告流程意味着无接续机制，这一风险在 6.x 周期凸显；与 FreeBSD（14.x 周期 80 个 PGP 签名 SA）、OpenBSD（errata patches 配合 **signify(1)** 签名）的安全响应制度化形成对比

**辨析**：无 VSA 系统不等于无安全响应——DragonFly 通过 commit message 与 kernel@/commits@ 邮件列表通知用户安全修复，regreSSHion（CVE-2024-6387）3 天内响应即为案例；但无 VSA 系统意味着用户难以系统跟踪安全修复状态，须自行监控 dragonfly-src 仓库 commit log 或订阅 commits@ 邮件列表；errata 子页面虽记录 bug 修复，但 errata 为 per-release 的回溯性记录，非独立的安全公告系列，不等同于 FreeBSD-SA 或 OpenBSD errata 的制度化签发流程；【0 信任原则·errata 页面未逐一核查】各版本 errata 子页面因 WebFetch 超时未能逐一抓取核查，不影响 VSA 不存在的结论。具体争议点：①版本号误载——regreSSHion CVE-2024-6387 在 DragonFly 中的响应 commit 须以 CVE 编号在 dragonfly-src commit message 中检索核验，dragonfly.duckdb 显示 2024 年 commit 仅 277 条，须逐条检索 commit_message 含 “CVE-2024-6387” 或 “regreSSHion” 关键词核验；②日期差异——“3 天内响应”的具体起算日期（CVE 公布日 2024-07-01 vs DragonFly commit 日）须经 NVD CVE 详情页与 dragonfly-src commits 表 author_date 交叉核验；③人物归属分歧——DragonFly 安全响应由 Dillon 个人主导还是 commits@ 邮件列表集体决策，dragonfly.duckdb 不记录决策过程，须以邮件列表存档为准 [存疑脚注：regreSSHion CVE-2024-6387 在 DragonFly 中的具体响应 commit hash 与 author_date 须经 dragonfly.duckdb commits 表 commit_message 字段检索核验，“3 天内响应”的起算日期须经 NVD CVE 详情页与 dragonfly-src commits 表 author_date 交叉核验，本轮考据未联网核验]。0 信任原则应用维度：author 字段可伪造（安全响应 commit 作者归属须与 committer 字段交叉验证，Dillon 双邮箱 <dillon@dragonflybsd.org> 与 <dillon@apollo.backplane.com> 须合并统计）、tagger_date 与实际发布日期可能偏差（errata 子页面更新日期与 commit 实际提交日期可能不一致，须以 dragonfly.duckdb commits 表 author_date 为准）、关键词匹配局限（安全 commit 可能以 CVE 编号或具体漏洞名（如 “regreSSHion” “OpenSSL”）为关键词而未提及 “security”，须以 commit_message 字段细分检索核验）。考据留痕至 `03-原始史料库/06-考据记录/20260730_jianyi缺口补全考据.md` 8aw 节
