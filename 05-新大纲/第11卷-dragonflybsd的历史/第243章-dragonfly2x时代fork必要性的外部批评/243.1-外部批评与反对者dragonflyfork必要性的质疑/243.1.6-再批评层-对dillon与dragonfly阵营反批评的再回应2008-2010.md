# 243.1.6 再批评层——对 Dillon 与 DragonFly 阵营反批评的再回应（2008-2010）

**要点**：批评方对 Dillon 与 DragonFly 阵营前述五层反批评的再回应聚焦三个维度，承认 fork 路线在 2.x 时代的工程可行性的同时指出其未能兑现 2003 年的工程承诺与主体性建立代价。其一，LWKT 路径工程可行性的再质疑——dragonfly.duckdb dragonfly-src 仓库 contributors 表显示 2.x 时代 bus factor 仍极低（2008 年 top10 占 91.56%、2009 年 top10 占 86.93%），LWKT 与 token 机制学习曲线陡峭，业界未见主流采纳；Dillon 本人在 DragonFly 官方 history 页面承认“logical continuation of the FreeBSD 4.x series”表述“has long since become obsolete”，反映 fork 后期定位从“FreeBSD 4.x 延续者”向“与 Linux 竞争者”漂移（"From a performance perspective DragonFly's only real competitor these days is Linux"），这一漂移本身印证批评方对 fork 定位模糊性的质疑——若 fork 初始定位的“4.x 延续”在 2.x 时代即被放弃，则 fork 必要性的初始论证亦随之松动。其二，小社区可持续性的再质疑——dragonfly.duckdb dragonfly-src 仓库 contributors 表显示 2.x 时代贡献者数 2008 年 36 位、2009 年 36 位，看似较 1.x 时代（2003 年 10 位）扩大，但相对 FreeBSD 8.x 同期数百 committer 群体仍属少数派；dragonfly.duckdb 显示 DragonFly 2024 年 commit 量仅 277 条，反映 2.x 时代社区规模短暂扩大后持续萎缩的长期趋势；与 OpenBSD fork 后建立安全细分市场（pledge/unveil/LibreSSL）形成对照，DragonFly 在 2.x 时代未建立明确细分市场，LWKT/HAMMER/vkernel 创新未获业界主流采纳。其三，HAMMER 自研文件系统必要性的再质疑——dragonfly.duckdb dragonfly-src 仓库 `sys/vfs/hammer*` 路径 commit 显示 2008 年 1,213 条（工程爆发）、2009 年 282 条（维护期），commit 量在 HAMMER 1.0 默认切换后即大幅回落，反映 HAMMER 1.0 的工程投入集中在发布前一年而非持续维护；Dillon 2008-07-02 HAMMER update 邮件原文“There are currently no known bugs!”属当事人自辩，须以独立第三方测试核验——DragonFly 2.2（2009-04-26）release notes 方称“HAMMER is now considered production-capable”，意味着 2.0（2008-07-20）发布时 HAMMER 尚未达生产级，至 2.2 方达生产级的 9 个月间用户承受了稳定性风险；FreeBSD 8.x 同期 ZFS 路径已成熟（OpenSolaris 2005 年开源 ZFS、FreeBSD 7.0 引入 ZFS、8.x 完善 ZFS 集成），OpenBSD FFS 保守路径稳定，DragonFly 自研 HAMMER 增加维护负担的同时未获业界采纳

**史料**：DragonFly 官方 history 页面（**dragonflybsd.org/history/**，“this description has long since become obsolete”自否弃声明、"From a performance perspective DragonFly's only real competitor these days is Linux"后期定位漂移表述）；dragonfly.duckdb dragonfly-src 仓库 contributors 表（2.x 时代 bus factor：2008 年 top10 占 91.56%、2009 年 top10 占 86.93%、2008 年 36 位贡献者、2009 年 36 位贡献者、2024 年 commit 量 277 条）；dragonfly.duckdb dragonfly-src 仓库 commits 表（HAMMER 路径 `sys/vfs/hammer*` 2008 年 1,213 条、2009 年 282 条）；Dillon 2008-07-02 HAMMER update 邮件原文（lists.dragonflybsd.org/pipermail/kernel/2008-July/316683.html，"Stabilization and testing work continues. There are currently no known bugs!“）；Dillon 2008-07-18”2.0 BRANCH FREEZE"邮件（lists.dragonflybsd.org/pipermail/kernel/2008-July/316748.html，“The release will be officially announced on Sunday!”）；DragonFly 2.2 release notes（**dragonflybsd.org/release22/**，“HAMMER is now considered production-capable”）；FreeBSD 7.0/8.0 release notes ZFS 集成部分；OpenBSD 4.4-4.8 FFS 文档 ［A］

**史观**：总纲第 5 条——没有必然性，只有偶然性：再批评须警惕“fork 必然失败”的目的论叙事——DragonFly 社区规模萎缩是多种偶然因素（细分市场未建立、LWKT 未获主流采纳、Dillon 个人精力分配）的叠加，而非 fork 决策本身的必然结果；总纲第 8 条——本体论上各方平等：再批评不等于否定，LWKT 路径与 SMPng 路径在本体论上地位相等，前者未获主流采纳不等于后者“正确”；软件工程：HAMMER 自研文件系统的工程投入集中爆发（2008 年 1,213 条 commit）与发布后回落（2009 年 282 条 commit）反映“先设计 → 工程爆发 → 维护期”的工程节奏，但 HAMMER 在 2.0 发布时尚未达生产级（2.2 方达生产级）的 9 个月窗口期是工程节奏过快的代价

**辨析**：考据过程留痕——【查证来源】DragonFly 官方 history 页面经 **dragonflybsd.org/history/** 一手核验，“this description has long since become obsolete”与"From a performance perspective DragonFly's only real competitor these days is Linux"表述确为官方页面自述，但 0 信任原则提示：history 页面是动态的，可能存在事后修订，2003-2010 年原始页面内容须以互联网档案馆存档交叉验证；Dillon 2008-07-02 HAMMER update 邮件经 lists.dragonflybsd.org/pipermail/kernel/2008-July/316683.html 一手核验，“There are currently no known bugs!”表述确为 Dillon 原文，但属当事人自辩，HAMMER 1.0 的实际稳定性须以独立第三方测试核验，不得仅凭 Dillon 单方面陈述采信；【关键考据发现·2.0 发布日期考据】Dillon 2008-07-18“2.0 BRANCH FREEZE”邮件原文“The release will be officially announced on Sunday!”，2008-07-18 为周五，下周日为 2008-07-20，与 DragonFly 官方 release20 页面记载“2.0.0 20-July-2008 RELEASE CD”吻合——故 DragonFly 2.0 正式发布日期为 **2008-07-20**（周日），前述反批评层与默认切换叙事中所使用的 **2008.7.20** 比官方记载晚 1 天，可能源于 PDT（美国太平洋夏令时，UTC-7）至 UTC 跨日转换差异或媒体首发报道时差，本节采用官方记载的 2008-07-20；【交叉验证方法】2.x 时代 bus factor 数据（2008 年 top10 占 91.56%）以 dragonfly.duckdb dragonfly-src 仓库 contributors 表统计，与 1.x 时代（2003 年 top10 占 100.00%）对照反映社区规模扩大但集中度仍高，但 bus factor 仅反映 commit 量集中度，不直接等同于项目可持续性；HAMMER 路径 commit 量从 2008 年 1,213 条回落至 2009 年 282 条，反映工程节奏变化，但 commit 量不等于质量——2009 年 282 条 commit 含功能完善与 bug 修复，并非全部用于核心功能；【0 信任原则·Dillon 自述考据】Dillon 2008-07-02“no known bugs”声明属发布前的当事人自辩，2.2 release notes 方称“production-capable”反映 2.0 发布时 HAMMER 尚未达生产级，9 个月窗口期的实际稳定性风险须以 DragonFly 邮件列表用户反馈与 commit log 中 bug 修复 commit 核验；【HAMMER 必要性批评的史观界限】HAMMER 自研文件系统必要性的批评须严格区分“工程负担”与“本体论错误”——HAMMER 增加维护负担是经验事实，但 HAMMER 作为 Dillon 主体性呈现的本体论地位不受经验负担影响；【与 OpenBSD 比较的史观界限】OpenBSD 建立安全细分市场与 DragonFly 未建立明确细分市场的比较须严格区分——两者 fork 动机不同（人际冲突 vs 技术分歧），细分市场的建立与 fork 动机无直接因果，不得以 OpenBSD 的成功反推 DragonFly 的失败；【社区可持续性判断的界限】2024 年 commit 量 277 条反映开发活跃度下降，但不等于项目“失败”——DragonFly 至今仍持续发布版本，可持续性挑战与项目失败是两个不同判断，史家不得以 commit 量下降即推论“fork 失败”；【LWKT 性能对比的史料局限】LWKT 与 SMPng 的性能对比缺乏权威第三方基准，“DragonFly 未能持续保持性能优势”的判断须以同硬件同负载基准测试核验，本节不臆造具体性能数字
