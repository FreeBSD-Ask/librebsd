**要点**：

- 自2008年7月上一次访谈后DragonFly发布2.2与2.4两版（时为2.4.1、2.5为开发分支）：HAMMER在2.2即被视为生产可用，2.4起提供64位与32位的批量包源构建，发行节奏整体后移两月以避开圣诞假期档；当事人预期2.6将成为其最稳定的一版。（BSDTalk EP184，[97.44-109.48]，L1）
- DevFS作为Summer of Code项目自零实现（非移植）并稳定后进入2.4：设备节点以独立文件系统动态创建销毁，取代其他文件系统中长期存在的设备节点shim；配合串行号探测，可用dev/serno路径访问设备，2.4安装器默认以串行号写入fstab，硬盘在AHCI与传统IDE接位间移动而系统无感，设备访问路径得以清淤优化。（BSDTalk EP184，[273.96-361.20]，L1）
- AHCI作为新式ATA芯片组标准带来原生命令队列与更优的设备派发模型；Dillon在2.4前后亲自实现AHCI驱动：先借第三方primitive驱动完成芯片组探测的初始引导，继而几乎推倒重写为面向DragonFly的从零实现，支持运行中热插拔（自认此前唯Linux驱动做得好），唯因手头芯片组rev所限未实现port multiplier原生命令队列。（BSDTalk EP184，[438.56-556.56]，L1）
- HAMMER演进至版本4：目录布局在v2重构后re-blocking使目录访问性能大增；快照管理由文件系统内软链接改为元数据存储（镜像端与源端策略不一致问题所致）；undo FIFO完全自包含后sync免于更新卷头，恢复时改为探测定位，性能显著改善；规划中的媒体redo FIFO意在让数据库fsync只同步日志（以MySQL逐事务fsync场景为动机）；卷删除功能靠“新分配避开该卷再加reblock搬移数据”轻量实现，根卷删除待做。（BSDTalk EP184，[844.02-1013.34]，L1）
- NFS客户端被Dillon作为“低垂果实”约一周重写：废除逐RPC线程模型，收敛为读写各一内核线程并全异步化RPC机制，线上在途RPC可达四五十个且无上限、按入队顺序序列化，大文件线性读不再停顿；挂载默认由UDP改TCP（UDP逐RPC超时不计服务器排队延迟导致完美网络下的假超时重试）；他明确NFS不属于集群工作，集群将采用事务能力远超NFSv4的自研协议。（BSDTalk EP184，[1128.14-1287.82]，L1）
- 单镜像集群OS的一年里程碑自认无实质推进，HAMMER性能被视为前提，undo/redo FIFO被定位为未来quorum同步的必要条件，2010年目标是启动主线集群协议；其应用愿景是以DragonFly加Samba的 appliance 替换现有Windows Server 2003同步队列存储（链路中断即队列塞满出错），本人异地备份已切换为HAMMER带宽受限镜像流加快照，经由共享Linux主机上的QEMU模拟运行。（BSDTalk EP184，[1287.82-1467.58]，L1）
- Dillon 综述迟了两三周发布的 DragonFly 2.8：集成大部分 Linux 模拟层、提供带条带化与加密的 DM 存储管理器、恢复 GUI USB 安装镜像，并伴随大量底层稳定性工作。（BSDTalk EP202，[47.32-95.60]，L1）
- 并发架构进展：巨型 MP 锁在代码层面基本移除（发布版默认仍启用以求稳定）；内核拆分为承接系统调用的前端与处理中断、设备调度的后端，后端几乎全部达到 MP 安全——网络栈、全部网络驱动、NATA 磁盘驱动、直至用户态缓存情形的整条 IO 路径与 HAMMER 均不触碰大锁；前端改用 token 锁协作，其中约半数仍保留回落大锁的保险机制；移除大锁后用户报告 Xorg 桌面等负载不再被单线程路径阻塞，性能显著改善。（BSDTalk EP202，[456.50-589.08]，L1）
- NFS 客户端重构为完全异步：RPC 不再依赖其他 BSD 中的 NFSIOD 机制（连内核线程形式也不存在），改为每条 NFS 套接字分配一对专用内核线程分别负责收发，预读默认大幅上调至十六至六十四；该实现自 2.6 起性能表现极佳，高预读引入的个别停滞边角案例在 2.8 中已修复至仅剩其一。（BSDTalk EP202，[589.08-670.24]，L1）
- HAMMER 两条线：其一，GSoC 去重项目接近入库（仍标实验性），按 B 树内建 CRC 收集匹配、经数据块实际一致性校验后合并引用，测试中在两块 TB 级盘获得可观去重比，但须让 reblocker 感知去重结果，否则无条件重整会撤销全部去重成果；其二，因一位用户盘面出现坏扇区且未做备份的求助，Dillon 放弃尝试两年未果的 HAMMER fsck（判定过于复杂不可行），改用一两天内写成的灾难恢复工具——对坏盘线性扫描识别 B 树节点、抽取文件与目录项并在目标盘动态重建文件系统，该用户借此恢复了九成九的数据。 [存疑脚注] 转写将 dedup 误作 D-Doop、去重比例数字（3 至 4 与 5 比 1 之间）含混，具体数值须回查原音频或发布说明（BSDTalk EP202，[124.88-807.80]，L1）
- 存储与加密配套：swapcache 自 2.6 稳定运行，2.8 树内经 VM 调整进一步优化并在发布后修复高负载下 pageout 守护进程迟滞引发的停滞，一块约百二十美元的 40GB Intel SSD 即可让单 HDD 加单 SSD 承载生产服务器并显著省本；内核开放加密框架经三人小组 MP 化改造后，软件加密由多核仅用单核的每秒三四十 MB 提升至一百五十 MB 以上，加密选项正在集成进安装器；标准磁盘安装采用七百 MB UFS 引导分区加整盘 HAMMER 的两分结构，使 HAMMER 分区可整盘加密并支持复杂根挂载；集群单一镜像系统长期目标仍在，但先行推进 multi-master 集群文件系统与缓存一致性，SSI 本身暂缓。（BSDTalk EP202，[248.22-498.28]，L1）
- Justin Sherrill 的主要项目工作是维护 DragonFly BSD Digest，每日从邮件列表中选摘要点；HAMMER 是 Matt Dillon 打造的历史保留、即时检查、可无限快照的文件系统，用户可按磁盘空间余量随时回溯历史版本文件，受访者称其为救命文件；HAMMER 1 采用 master-slave 复制，可在同一机器或跨机乃至跨互联网指定从盘并按带宽同步，主盘损毁时可将从盘提升为主，单主多从且各从盘可保留不同时长的历史，例如用大慢盘存放长期历史。（BSDTalk EP212，[54.16-349.12]，L1）
- HAMMER 1 已功能完备并经数年使用与修复锤炼；Sherrill 本人在重要数据上启用全部特性，开启去重后回收了约 20% 的磁盘空间；去重提供实时与隔夜两种模式，他使用隔夜模式即可满足需求，实时去重被比作快速复制——在大量数据复制过程中即时去重；HAMMER 内存要求很低，256MB 内存即可运行（需关闭吃内存的隔夜 reblocking），与作为对比基准的 ZFS 形成鲜明反差。（BSDTalk EP212，[447.16-638.52]，L1）
- HAMMER 与 ZFS 的主要差距在工具集成而非核心能力：ZFS 将磁盘管理与 RAID 等工具内建、具有所想即所得的便利，HAMMER 则采用主从复制而非 RAID，期望软件 RAID 的用户应转向硬件 RAID 卡；因此更好的硬件 RAID 卡驱动支持被视为 DragonFly 成败的关键因素，Sascha Wildner 近期引入 Areca 卡支持且该公司亲自测试了驱动，被受访者视为项目获得业界承认的时刻。（BSDTalk EP212，[641.47-760.04]，L1）
- HAMMER 2 在访谈前数日刚进入代码树，处于极早期，Matt Dillon 称六个月内无可玩内容、年底方能完成；其 multi-master 设计是 DragonFly 早期集群目标的当代回归——最初目标是整个操作系统的集群，而多核处理器的普及使单机多核已能满足算力需求，集群理想遂转向存储层；HAMMER 2 将继承 HAMMER 1 全部特性，新增更精细的去重（可只对部分文件系统执行）与配额支持，并已有技术性 release notes 发布。（BSDTalk EP212，[207.66-447.16]，L1）
- 架构与产品想象方面，DragonFly 支持 i386 与 x86_64；Sherrill 口头上一直鼓吹 ARM（尤其即将到来的 ARMv8）但自认缺乏执行技能、项目内亦无人推动，且新架构移植本身极为困难；他设想基于 ARM 的小型 NAS 设备运行 HAMMER、在亲属家放置第二台作受信备份并经 SSH 同步文件系统，认为这是一个亟待出现的 FreeNAS 的 HAMMER 等价物——相较每月三十美元电费的台式机，小 ARM 盒更容易被家庭接受。（BSDTalk EP212，[830.22-927.22]，L1）
- 社区观察：DragonFly 开发者总数保持静态，有人离开也会回归；受访者担忧编写操作系统已不像十年前那样吸引人，潜在贡献者转向 Android、iOS 应用开发；非 Windows 系统的开发日益由公司赞助，他即兴估计 Linux 内核约八成贡献来自公司付费开发者；开源从业余者人人贡献转向受益公司付费贡献，他不以此为大恶——认为水涨众船高——但怀旧 2002 年前后一个 tarball 即可开搞的朴素网页与个人痴迷式文档传统，对比如今要么商业抛光、要么近乎不存在的生态，并自承此判断并不科学。（BSDTalk EP212，[1018.30-1251.22]，L1）
- 治理与基础设施实态：DragonFly 完全由志愿者运作且没有法人实体，Sherrill 长期想创建 DragonFly 非营利组织以获得可签约、可持有版权的法律实体；代码版权栏写 DragonFly BSD Project 但技术上并不存在该实体，受访者自承非律师、不知此问题多严重；基础设施是一堆地下室——主站是 Matt Dillon 家中的数台机器，pkgsrc 批量构建依赖志愿者捐赠的机器空间，无商业实体托管；版本控制已由 CVS 转 Git 且相当成功，pkgsrc 的 CVS 到 Git 转换正在进行；Sherrill 自愿出任 3.0 发布经理，尚余七个阻塞 bug，nightly build 与候选版已可下载；项目连续四年参与 Google Summer of Code 并拟再次参加。（BSDTalk EP212，[1251.22-1595.34]，L1）
