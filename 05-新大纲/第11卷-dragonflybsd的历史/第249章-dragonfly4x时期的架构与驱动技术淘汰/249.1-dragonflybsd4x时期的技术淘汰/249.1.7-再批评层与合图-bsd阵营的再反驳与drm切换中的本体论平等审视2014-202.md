# 249.1.7 再批评层与合图——BSD 阵营的再反驳与 DRM 切换中的本体论平等审视（2014-2020）

**要点**：BSD 阵营对 DragonFly 阵营的三层回应提出再反驳，并在合图阶段以项目史观总纲第 6 条与第 8 条为框架达成辩证综合。再反驳其一，“硬件支持不等于代码血缘”——BSD 阵营承认 Linux DRM 的硬件支持覆盖率确实高于 FreeBSD DRM，但指出 FreeBSD 通过 linuxkpi 兼容层同样支持现代 GPU，问题不在于“是否支持”而在于“以何种方式支持”，DragonFly 选择直接 Linux DRM 移植而非 linuxkpi 兼容层，是路线选择而非硬件支持的必然。再反驳其二，“维护负担的双向性”——dragonfly.duckdb 显示 Tigeot 一人 9 年 1346 条 commit 的 DRM 移植工作量不可谓不大，BSD 阵营指出“维护负担转移”并非真正减轻，而是从“BSD 内部协作维护”转移为“单人跟随 Linux 上游维护”，后者在 Tigeot 停止贡献后将面临无人接续的风险——dragonfly.duckdb 显示 Tigeot 末次 commit 为 2020-12-19，此后 DragonFly 的 DRM 维护进入低活跃期。再反驳其三，“多元展开的边界”——BSD 阵营承认 BSD 许可证允许不同路线，但指出“多元展开”不等于“放弃协作”，BSD 家族在 GPU 驱动上的代码共享本就有限，DragonFly 的 Linux DRM 移植进一步减少了潜在的代码共享空间。合图阶段，以项目史观总纲第 6 条“和解优于斗争”与第 8 条“本体论上各方平等”为框架：DragonFly 的 DRM 切换既非“背叛”亦非“必然”，而是在 2014 年的资源约束与硬件支持现实下的偶然工程选择；FreeBSD DRM 的独立适配与 Linux DRM 的直接移植在本体论上平等，二者各有代价与收益；BSD 家族的多样性不应被“代码血缘”的规范预设所束缚，而应在尊重各项目工程现实的基础上寻求和解——这种和解不是要求 DragonFly 回退到 FreeBSD DRM，而是要求 BSD 阵营理解 DragonFly 的工程约束，同时要求 DragonFly 阵营承认 BSD 协作传统的价值
