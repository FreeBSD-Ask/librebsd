# 257.2.1 fork 起因、HAMMER ZFS 替代、HAMMER2 高可用与单开发者项目传言

**要点**：DragonFly BSD 在 BSD 生态中长期伴随四类典型传言——(1) “DragonFly BSD fork FreeBSD 是因为 Matt Dillon 与核心团队冲突”（真伪混杂：2003-07-16 Dillon 在 freebsd-current 邮件列表发布的 fork 公告明确陈述技术动机为“5.x 锁粒度过重、SMPng 路线不可取”，未提及“核心团队冲突”，freebsd.duckdb 显示 Dillon 在 freebsd-src 末次 commit 为 2003-01-28，dragonfly-src 首 commit 为 2003-06-17，间隔约 4.5 个月，时间窗口与“撤权后转而筹备 fork”叙述吻合，但 FreeBSD Core Team 关于撤权的正式公告原文未在 lists.freebsd.org 公开归档中检索到，将 fork 主因简化为“与核心团队冲突”掩盖了技术路线分歧的根本性质）；(2) “DragonFly BSD HAMMER 文件系统是 ZFS 的替代”（史实失实：2008-06-21 Dillon 发布的 HAMMER 设计文档第 1 节明确陈述“我的目标是让 HAMMER 成为 BSD 系统的下一代文件系统”，参照系是 Linux 已有的文件系统（如 ext3、ext4、XFS、JFS），而非 ZFS，整份设计文档约 15.4 KB 通篇未提及“ZFS”字样，DragonFly 官方 HAMMER 页面亦无“ZFS 替代”陈述，传言基于特征相似性的投射谬误）；(3) “DragonFly BSD HAMMER2 支持高可用”（史实失实：DragonFly 官方 HAMMER2 页面“Future and TBD Features”段落明确写道“亦有为 multi-master、master-slave 及其他复制与镜像机制预留的字段，但尚未实现，包括投票与愈合机制”，multi-master、master-slave、复制、镜像、投票、愈合等高可用关键机制均处于“预留字段、尚未实现”状态，传言混淆了“设计中预留字段”与“已实现功能”两个层次）；(4) “DragonFly BSD 是单开发者项目”（史实失实：DragonFly BSD GitHub 仓库主页显示 44,910 commits、123 branches、131 tags、616 stars、140 forks，2026 年 7 月已有 liweitianux、lileding、dreamfall 等非 Dillon 提交者活跃提交，2003-10 起 commits 邮件列表归档已记录 David Rhodus 等非 Dillon 提交者，项目自早期即为多开发者协作，长期核心贡献者含 Sascha Wildner（萨沙·维尔德纳）、François Tigeot、Tomohiro Kusumi 等）

**史料**：Matthew Dillon（马修·狄龙） 2003-07-16 fork 公告（**<https://lists.freebsd.org/pipermail/freebsd-current/2003-July/006889.html>**，标题拼写“Annoucning”为原始拼写）；DragonFly BSD 官方历史页面（**<https://www.dragonflybsd.org/history/>**，页面底部标注“Last edited Thu Jan 17 13:32:06 2019”）；dragonfly.duckdb dragonfly-src 仓库首 commit `984263bcb83a`，author_date `2003-06-17T02:57:24Z`，message_subject“Initial import from FreeBSD RELENG_4”；freebsd.duckdb 显示 Dillon 在 freebsd-src 末次 commit 为 `2003-01-28T18:44:40Z`；HAMMER 设计文档 PDF（**<https://www.dragonflybsd.org/hammer/hammer.pdf>**，2008-06-21，互联网档案馆存档 2022-10-09）；DragonFly 官方 HAMMER 页面（**<https://www.dragonflybsd.org/hammer/>**，“Future and TBD Features”段落，页面底部标注“Last edited Tue Jan 17 10:43:58 2023”）；DragonFly BSD GitHub 仓库主页（**<https://github.com/DragonFlyBSD/DragonFlyBSD>**，显示 44,910 commits、123 branches、131 tags、616 stars、140 forks）；DragonFly BSD commits 邮件列表归档（**<https://www.dragonflybsd.org/mailarchive/commits/2003-10/index.html>**，可见早期非 Dillon 提交者如 David Rhodus）；HAMMER2 设计文档 v1（2012-02-08，**<https://gitweb.dragonflybsd.org/dragonfly.git/blob/05af5bd1aeaf8bf30d36fc65103097415b943700:/sys/vfs/hammer2/DESIGN>**）；HAMMER2 设计文档 v6（2018-12-08，**<https://gitweb.dragonflybsd.org/dragonfly.git/blob/57614c517203403e7fe4a34c370c7151ba52c539:/sys/vfs/hammer2/DESIGN>**）；Linux 伊甸园转载驱动之家报道（2008-07-22，**<http://www.linuxeden.com/html/news/20080722/59687.html>**）；腾讯新闻《FreeBSD 大败局》（2022-02-24，**<https://view.inews.qq.com/a/20220224A03J2D00>**） ［A］〔L2 即时通讯记录/L3 官方文档与公告/L5 二手研究〕

**史观**：总纲第 9 条——经验优先，Dillon fork 公告陈述的技术动机（“5.x 锁粒度过重”）是 SMPng 路线在工程实践中的经验沉淀，而非预先设计的政治姿态；总纲第 19 条——解释学循环是历史认识的根本条件，“fork 因核心团队冲突”传言须在 Dillon 自述（fork 公告）与第三方转述（Linux 伊甸园、腾讯新闻）之间往复印证，Dillon 自述存在“为 fork 决策辩护”的自利倾向须对照 FreeBSD SMPng 设计文档与第三方性能评估加以辨析；总纲第 15 条——文化即形式主义，“HAMMER 是 ZFS 替代”传言将 HAMMER 与 ZFS 的特征相似性（快照、COW、校验和）形式主义归因为“竞争/替代”关系，忽略了 Dillon 在设计文档中明确的“下一代 BSD 文件系统”定位；总纲第 7 条——理论必须自反，本子节作为 DragonFly BSD 传言考据叙事，自身亦嵌入“多开发者协作即善”的前理解，须自觉呈现这一前理解；总纲第 23 条——一切历史写作都是基于哲学设定的历史小说，“Dillon 是独裁型创始人”等社区叙事是史家基于有限公开史料的形式主义建构

**辨析**：考据过程留痕——【查证来源】Dillon 2003-07-16 fork 公告经 lists.freebsd.org/pipermail/freebsd-current/2003-July/006889.html 一手核验，公告标题拼写“Annoucning”为原始拼写，公告本身仅陈述技术动机未提及“核心团队冲突”；DragonFly 官方历史页面经 dragonflybsd.org/history/ 一手核验“forked from FreeBSD 4.8 in June of 2003, by Matthew Dillon”；dragonfly.duckdb dragonfly-src 首 commit `984263bcb83a` 经本地数据库查询核验；HAMMER 设计文档经 dragonflybsd.org/hammer/hammer.pdf 一手核验，第 1 节明确陈述“我的目标是让 HAMMER 成为 BSD 系统的下一代文件系统”，通篇未提及“ZFS”；HAMMER2 官方页面经 dragonflybsd.org/hammer/ 一手核验“Future and TBD Features”段落明确陈述 multi-master 等高可用机制“尚未实现”；DragonFly GitHub 仓库主页经 github.com/DragonFlyBSD/DragonFlyBSD 一手核验 44,910 commits 与多开发者提交活动；【交叉验证方法】fork 起因须以 Dillon fork 公告（Dillon 自述）、DragonFly 官方历史页面（项目自述）、dragonfly.duckdb commit 元数据（代码仓库）三源互证；HAMMER 设计目标须以 HAMMER 设计文档（Dillon 自述）与 DragonFly 官方 HAMMER 页面（项目自述）互证；HAMMER2 高可用状态须以官方 HAMMER2 页面“Future and TBD Features”段落与 HAMMER2 设计文档 v6 互证；“单开发者项目”须以 GitHub 提交活动页与 commits 邮件列表归档互证；【0 信任原则·FreeBSD Core Team 撤权公告】FreeBSD Core Team 关于 Dillon 撤权的正式公告原文未在 lists.freebsd.org/pipermail/freebsd-hackers/2003/ 与 lists.freebsd.org/pipermail/freebsd-announce/2003/ 归档中检索到，freebsd.duckdb 仅提供间接时间线证据（freebsd-src 末次 commit 2003-01-28 至 dragonfly-src 首 commit 2003-06-17 的 4.5 个月间隔），不构成撤权决定本身的直接证据，撤权决定的具体日期、公告 URL、Core Team 投票记录均待后续考据补充；【0 信任原则·Dillon 自述自利偏差】Dillon fork 公告存在“为 fork 决策辩护”的自利倾向，其对 5.x 锁模型的批评在工程层面有据可查但须对照 FreeBSD SMPng 设计文档（John Baldwin（约翰·鲍德温）, 2002, “SMPng Design”）与第三方性能评估加以辨析；【0 信任原则·HAMMER 与 ZFS 算法渊源】HAMMER 与 ZFS 是否存在“平行创新”或“启发关系”，须经源码级比较（sys/vfs/hammer/ 与 OpenZFS 源码的算法对比）方能定论，本次考据仅就“ZFS 替代”传言定位进行考证，不涉及 HAMMER 与 ZFS 的源码级算法渊源；【0 信任原则·HAMMER2 私有分支原型】HAMMER2 是否在私有分支或实验分支中存在 multi-master 原型实现，本次考据未覆盖 DragonFly BSD 私有分支与实验分支源码，须以 DragonFly 邮件列表与 HAMMER2 邮件列表的近期讨论为补充证据；【0 信任原则·“单开发者”措辞模糊性】“单开发者项目”存在定义歧义：若定义为“仅有 Dillon 一人贡献代码”则明显失实（GitHub 显示 44,910 commits 来自多人）；若定义为“Dillon 是项目主要决策者与核心贡献者”则部分属实，但这是“BDFL 治理模式”而非“单开发者项目”；【自反性声明】本子节作为 DragonFly BSD 传言考据叙事，自身嵌入“多开发者协作即善”与“技术分歧优于人际冲突”的前理解，实际 DragonFly BSD 治理的工程代价与 fork 事件的多因性须以多源交叉验证逼近史实
