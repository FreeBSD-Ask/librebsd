# 041.6.3 要点三个争议焦点使Kerberosv4在BSD中长期作为可选组件而非默认启用44

**要点**：三个争议焦点使 Kerberos v4 在 BSD 中长期作为可选组件而非默认启用——4.4BSD（**1994**）与 4.4BSD-Lite（**1994**）保留 Kerberos v4 作为可选组件，FreeBSD 1.0-3.x（**1993-2000**）与 NetBSD 早期版本继承 BSD 单文件 `/etc/passwd` 格式与 `~/.rhosts` 信任链作为默认远程认证机制，Kerberos 仅作为可选组件存在；BSD 实际的远程认证主流是 **1995 年** Tatu Ylönen 发布的 **ssh(1)**（SSH 1.0），**ssh(1)** 基于公钥加密与对称加密混合体制，无须 KDC 集中式基础设施，部署门槛远低于 Kerberos，且不受 US Export Control 对 DES 的出口管制（SSH 1.0 使用 RSA 与 IDEA 等算法，后续 OpenSSH 使用 Blowfish、AES 等），快速取代 `~/.rhosts` 信任链成为 BSD 与 Linux 的远程认证主流；MIT Kerberos v5 与 RFC 1510（**1993 年 9 月** 由 Kohl & Neuman 发布的“The Kerberos Network Authentication Service (V5)”）标准化后，Kerberos v5 逐步解决 v4 的部分争议（如 KDC 部署简化、加密算法可插拔），但 BSD 社区已选择 **ssh(1)** 作为远程认证主流，Kerberos 直至 FreeBSD 5.x（**2003 年**）才作为默认可选组件；Kerberos 在 BSD 中的长期边缘化反映了 BSD 社区对认证基础设施的审慎态度——优先选择部署门槛低的 **ssh(1)** 而非安全性理论更强但部署复杂的 Kerberos

| 认证机制 | 引入年份 | 部署门槛 | BSD 中的地位 | 主要优势 |
| ------ | ------ | ------ | ---------- | ------ |
| `~/.rhosts` 信任链 | 4.1BSD（1981） | 极低（无 KDC） | 1995 年前的默认机制 | 部署简单 |
| Kerberos v4 | 1988（MIT）/ 1990（Reno 集成） | 高（需 KDC） | 4.4BSD 起可选组件 | 集中式票据认证，安全性理论强 |
| Kerberos v5（RFC 1510） | 1993.9 | 中（简化部署） | FreeBSD 5.x（2003）起默认可选 | 部分解决 v4 争议 |
| **ssh(1)**（SSH 1.0） | 1995 | 低（无 KDC） | 1990 年代末取代 `~/.rhosts` | 公钥加密，部署门槛远低于 Kerberos |
| OpenSSH | 1999 起 | 低 | OpenBSD 主导，BSD/Linux 主流 | 无 DES 出口管制问题（Blowfish/AES 等） |

(1995) SSH 1.0 发布记录与 RFC 系列文档；Kohl, J. & Neuman, C. **史观**：第 9 条——经验优先——BSD 社区选择 **ssh(1)** 而非 Kerberos 是实践驱动而非理论先行，**ssh(1)** 的部署门槛优势在工程实践中压倒 Kerberos 的安全理论优势；第 2 条——历史是形式主义化的非存在——Kerberos 的“集中式 KDC 票据认证”形式逻辑在 **ssh(1)** 的“分布式公钥认证”形式逻辑竞争下边缘化，两种形式主义的竞争以部署门槛为裁决标准

**辨析**：Kerberos 在 BSD 中“长期边缘化”须区分“完全弃用”与“作为可选组件保留”——Kerberos 在 BSD 中持续作为可选组件保留至现代（FreeBSD 当代版本仍支持 Kerberos v5），但从未成为默认远程认证机制，须区分“可选保留”与“主流采纳”；**ssh(1)** 取代 `~/.rhosts` 信任链的时间须区分“SSH 1.0 发布（1995）”与“SSH 广泛采纳（1990 年代末至 2000 年代初）”——SSH 1.0 发布后仍需数年才广泛取代 `~/.rhosts`，须避免将“发布”等同于“取代”；FreeBSD 5.x（2003）将 Kerberos v5 作为默认可选组件须区分“默认可选”与“默认启用”——FreeBSD 5.x 提供 Kerberos v5 作为安装时可选组件但非默认启用，须区分“可选组件”与“默认启用”；Kerberos v5 与 RFC 1510“解决 v4 部分争议”须谨慎判断——v5 确实简化了 KDC 部署与加密算法可插拔，但 KDC 集中式基础设施的根本复杂性仍存在，须区分“部分解决”与“完全解决”
