# 303.8.4 要点企业贡献的量化需通过committer邮箱域名统计但邮箱域名可能不反映实际雇

**要点**：企业贡献的量化需通过 committer 邮箱域名统计，但邮箱域名可能不反映实际雇主（如个人邮箱）。资料数据库.duckdb 查询 C-45/C-46/C-47 显示：materials 表 `commit_hash` 字段填充率仅 2.70%（385/14,273），`archive_url` 字段填充率 0.00%，`tag_tagger_date` 字段填充率 0.00%，反映企业贡献的 commit 级溯源在史料数据库层面存在系统性数据缺口；跨数据库关联分析 C-50 显示：materials 表 commit_hash 与 bsd_commits.duckdb commits 表 commit_hash 的 JOIN 命中率为 98.4375%（378/384），即在已填充 commit_hash 的 384 条史料中，98.44% 可在 bsd_commits.duckdb 中定位到对应 commit，但鉴于 materials 表整体 commit_hash 填充率仅 2.70%，此高命中率仅覆盖极小比例史料，企业贡献的全量 commit 级溯源仍不可行。

**史料**：**FreeBSD** git log 中的 Author 邮箱、committer 列表 ［A］；资料数据库.duckdb 查询 C-45/C-46/C-47 显示：materials 表共 14,273 条史料中，`commit_hash` 字段填充率 2.70%（385/14,273），`archive_url` 字段填充率 0.00%（数据缺口），`tag_tagger_date` 字段填充率 0.00%（数据缺口）；跨数据库关联分析 C-50 显示：materials 表 commit_hash 与 freebsd.duckdb commits 表 commit_hash 的 JOIN 命中率 98.4375%（378/384，精确匹配 + 短哈希前缀匹配）

**史观**：commit 记录作为企业贡献的量化史料；统计结论印证：C-45/C-46/C-47/C-50 揭示企业贡献量化在史料数据库层面的双重局限——一是 materials 表 commit_hash 填充率仅 2.70% 使绝大多数史料无法 commit 级溯源，二是 archive_url 填充率 0.00% 使互联网档案馆存档完全缺位，三是即便在已填充 commit_hash 的 384 条史料中 JOIN 命中率高达 98.44%，但高命中率仅覆盖 2.70% 史料，企业贡献的全量量化仍受数据缺口制约

**辨析**：邮箱域名统计可能遗漏或误归，需多源核实；0 信任原则局限标注：C-45/C-46/C-47 反映的是资料数据库.duckdb materials 表的字段填充率，materials 表为本书编纂者手动录入，commit_hash 填充率 2.70% 受限于编纂者对 commit 哈希的手动核对工作量，不代表 BSD 社区企业贡献的实际规模；C-50 的 JOIN 命中率 98.4375% 仅基于 384 条已填充 commit_hash 的史料，样本量小，统计显著性有限，不可外推至全部 14,273 条史料；archive_url 填充率 0.00% 为字段设计后未填充的数据缺口，非企业贡献信息缺失；统计显著 ≠ 实际显著，JOIN 命中率高不等于企业贡献溯源完整

**要点**：

- Julian Elischer 一手自述其 BSD 起点：1990 年入职 TRW，在基于 VME 总线 68030 的图像处理服务器群上运行 BSD 4.3；公司为降级到 x86 工作站而采用 Mach 系统——即 CMU 将其微内核研究成果嫁接 BSD 4.3 之上、保留原文件系统与网络栈的产物；x86 与 68030 的大小端差异令他迅速领教网络栈中字节序转换函数存在的理由。因 Mach 无 SCSI 支持，他为 Mach 编写了 SCSI 子系统，随后将其移植入 386BSD，该代码成为 FreeBSD SCSI 子系统的基础，后由 Justin Gibbs 等人重写；他声称其残留文件与署名至今仍存于 FreeBSD、NetBSD 与 OpenBSD 之中。（BSDTalk EP165，[508.86-588.84]，L1）
- 386BSD patchkit 时期的协作形态由当事人还原：Bill Jolitz 与 Lynn Jolitz 因家庭危机淡出后，开发者群体自行维护官方补丁集，无版本控制工具，参与者复制源码树制作 diff 汇入补丁集；Julian 在 TRW 金融系统的外部网络上架设服务器，向所有愿意工作的人开放账号。1993 年他返澳期间 Jordan Hubbard 等人分叉出 FreeBSD，他将其定性为组织性争论而非技术争论；NetBSD 更早分叉、性质偏技术，诉求是获得 CVS 树与更好的支持结构。Jolitz 夫妇最终因家庭变故（他提及 Bill 父亲去世等）彻底退出，FreeBSD 从此自立。（BSDTalk EP165，[359.28-477.40]，L1）
- Whistle Communications（1996 至 1999）是其总结的“以 BSD 解决问题、开发成果回流 FreeBSD”模式的典型：小企业一体机被当事人称为盒装 IT 部门，公司被 IBM 收购后产品线遭整体关停，当事人形容为花费约 1.2 亿美元买下再关掉的怪异决策；该时期回流 FreeBSD 的成果包括以合同委托 McKusick 移植的 soft updates、Divert Sockets、NetGraph 子系统与 AppleTalk 栈。对“BSD 许可证纵容企业只取不予”的担忧，他以跨公司经验给出系统性反驳：回馈即由社区维护、代码保鲜，NetGraph 首次提交仅约 12 个模块、如今 50 至 60 个模块大多出自他人之手，回馈即省钱；竞争对手若已自行实现同类功能，将己方代码回馈入主线会抬高对手门槛，拖延三年则可能错失窗口——对手正解决同一问题，谁先回馈谁的定义成为事实标准，故总有理由尽快回馈。（BSDTalk EP165，[884.96-1081.76]，L1）
- TRW 分部管理层强推 COTS（商用现货）路线的教训由当事人痛陈：以改用 Windows NT 与 Sun 服务器、把工程师从百人裁至五十人为诱饵的论证，被其斥为似是而非——采用 COTS 即接受所有公司共有的 COTS 局限，公司从能做出差异化产品的 vendor 沦为 me-too vendor。此前自研系统曾以 15.5K 巨型帧穿过作局部总线用的以太网、专用驱动将包直接写入内存缓冲馈入磁盘、几乎无 CPU 干预，一台 68030 即可打满六七条以太网；自造成本 1.5 万美元售 7 万美元，而改用 Sun 方案后需三倍硬件，24 万美元的 Sun 设备以 18 万美元亏本竞标。管理层的省钱承诺从未兑现。（BSDTalk EP165，[1223.02-1367.42]，L1）
- IronPort（2005 年加入，后被 Cisco 收购）延续同一人群与同一模式：设备为 Dell 硬件，其 AsyncOS 即标准 FreeBSD 加一层异步事件驱动、协作式线程的 Python 运行时；内部沿用 Whistle 时代的引导块实现双 root 分区、下载写入备用分区失败即回退的升级机制，当事人认为其在该功能上仍优于现行 FreeBSD 引导块。因所有改动回流主线，公司升级路径顺畅：4.8、6.1、6.3、再到等待中的 7.1，自研补丁先入 current 再回稳定分支，抵达新分支时补丁已在其中；反例是 Nokia 因对 FreeBSD 魔改过深而长期困守 2.0，待需 SMP 升级至 6.0 时付出巨大代价。（BSDTalk EP165，[1497.22-1710.10]，L1）
- Cisco 收购后的组织生态由当事人描述：IronPort 并入安全技术业务单元 STBU，原 IronPort 首席执行官接管 STBU，被当事人形容为一场宫廷政变，STBU 现近乎 IronPort 的放大版。收购消息令 Linux 工程师担心被迫转 BSD、BSD 工程师担心被迫转 Linux，管理层回答均为否定；BSD 在 Cisco 内部渐获尊重。当事人还透露 Cisco 内部曾有项目考虑采用 BSD，被 Linux 派以政治手段阻止，理由包括采用 BSD 会“验证 Juniper 选择 BSD 的正确性”；Cisco 设有开源监督流程，要求报告所用开源组件并核验许可证，其对 Cisco 大量采用 Linux 的 GPL 合规持保留态度。（BSDTalk EP165，[1790.74-1888.62]，L1）
- Losh 给出 FreeBSD 分支模型的理想设定：主线持续开发，理论上每 18 个月出一个大版本，分支活跃约 24 个月、3 年后终止，任意时刻通常只保有一条活跃分支。但现实明显偏离：大版本间隔不均、发布工程师推进有快有慢，分支因用户仍在使用而远超预期寿命——1999 年创建的 RELENG_3 分支到演讲时（2008）每年仍有约一次提交，而 4.x 与 6.x 分支的提交斜率远大于 5.x，商业跟踪者必须直面这种不对称的分支长尾。[订正：时间戳原 [264.479-452.28]→[227.2-466.5]，“主线持续开发”出自 227.2-233.8 与 252.6-256.1、末句“跟踪者直面不对称长尾”出自 452.3-466.5，原不在区间内，按字幕源重锚]（YouTube EPVaZ9Ef04bJg，[227.2-466.5]，L1）
- 升级 FreeBSD 版本的现实动因被归纳为：新硬件支持（即便自研板卡，元器件终将停产，几轮小改后必须升级到下一代技术并跟进新以太网驱动）、新特性（单处理器产品向 SMP 与线程演进）、上游 bug 修复，以及与开发者社区保持联系本身。升级中的典型摩擦是合并冲突——公司修过的 bug 上游他人也修过——以及接口环境变迁（串口设备改名、硬连线串口转向 USB 串口）。演讲以多家公司经历合成的反例说明：导入某版本后闭门自用、完全无视社区，产品成功后被迫升级时即演变为一次代价高昂的大型移植工程。[订正：原“跟进新总线与以太网驱动”→“升级到下一代技术并跟进新以太网驱动”，内容复核]（YouTube EPVaZ9Ef04bJg，[523.08-722.64]，L1）
- 演讲给出商业跟踪 FreeBSD 的四种策略谱系：其一“拿了就忘”，简单但累积技术债且享受不到上游持续演化，是反面经历之源；其二“拿了再升级”，适合改动极少或直接以标准系统做设备的用户；其三跟踪 stable 分支——Losh 在 Timing Solutions 的八年实践中交付了 20-25 个基于 3.x 至 6.x 的产品，做法是将 stable 分支按主线导入公司 CVS 的独立目录（TSC 4/5/6），维持少量本地修改，借源码管理工具的差异比对生成补丁集推送上游，SCM 同时充当“机构记忆”，且可自主决定跳过糟糕的 4.8 发布或仅拉取关键修复；其四镜像 FreeBSD 开发流程，自建 current 并自行决定建 stable 分支的时机。（YouTube EPVaZ9Ef04bJg，[785.68-1361.52]，L1）
- 跟踪 stable 分支的收益在于持续获得官方修复、小增量补丁集易于合入上游，且回流补丁经社区更多双眼审查后质量常高于公司内部程序员单独所能；其代价是多分支间修改不自动传播、stable 修复因“先进 current”的上游流程而难以合入，以及官方大版本时机不可预测。自建 current 模式（被 Cisco 收购、大量使用 FreeBSD 的某公司）则换来合并极简、同行评审快速回流、发布时机自主（后期转用 Perforce），但自有分支的测试广度不及官方 stable，还需说服管理层接受“两份工作”的表象，且社区面对其私有分支常以“该 bug 三个月前已修复”式的回应难以施援。[存疑脚注] 该公司未具名，其实践细节无法据本演讲核验。 [存疑脚注] 被 Cisco 收购的公司未具名，自建 current 实践为单一来源口述。（YouTube EPVaZ9Ef04bJg，[1388.2-1931.88]，L1） [订正：原 [1601.2-1931.88]→[1388.2-1931.88]，stable 分支收益与代价一节（官方修复、小增量补丁集、多双眼审查、多分支不自动传播、先进 current、大版本不可预测）出自 1388.2-1590.2 原不在区间内，内容复核]
