# 081.7.6 被疏远贡献者的再批评——对反批评的再回应（再回应层）

  **要点**：对 OpenBSD 阵营反批评的再回应集中于三点——其一，“个人选择” 叙事忽视了结构性压力，贡献者在持续被拒绝或被 de Raadt 公开羞辱（如 “this is stupid” 式回复）后 “选择” 离开，实为被结构性排斥而非自由选择；其二，“补丁质量问题” 论证忽视了质量标准的主观性——de Raadt 的审美偏好（如 KNF 代码风格、API 简洁性要求）常以 “质量” 名义行使，部分被拒绝补丁在技术正确性上无缺陷但不符合 de Raadt 的设计哲学；其三，被疏远贡献者叙事的 “放大” 指控本身可能是 OpenBSD 阵营对批评的回避——“外部观察者放大” 的指控忽视了被疏远贡献者本人自述的存在，将批评者定性为 “外部” 本身就是排斥性话语
  
**史料**：被疏远贡献者关于结构性压力的自述、OpenBSD 邮件列表中补丁被拒绝的具体案例与时序（含 de Raadt 的回复原文）、社区治理研究中关于结构性排斥的文献、OpenBSD KNF 代码风格文档
  
**史观**：解释学循环：被疏远贡献者叙事的评估受前理解差异制约——OpenBSD 阵营以 “个人选择” 为前理解，批评者以 “结构性排斥” 为前理解，二者难以通约；文化即形式主义：de Raadt 的言辞文化（“this is stupid” 等）在形式主义化过程中被固化为排斥机制
  
**辨析**：考据过程留痕——【查证来源】被疏远贡献者结构性排斥论证的关键证据基于 OpenBSD misc@、tech@ 邮件列表原始存档（marc.info 与 OpenBSD 官方邮件列表归档）中补丁被拒绝的具体时序与 de Raadt 的回复原文；OpenBSD KNF 代码风格文档（style.styles(9) 手册页）为质量标准主观性论证的对照基础；openbsd.duckdb openbsd-src 仓库 contributors 表（403 名贡献者）为贡献者基数证据；OpenBSD security.html 经 <https://www.openbsd.org/security.html> 一手核验，页面明确记载 "Our security auditing team typically has between six and twelve members"，确认代码审计团队规模为 6-12 人，远小于 403 名贡献者基数——核心决策圈与贡献者基数的差距是结构性排斥的量化证据；【交叉验证方法】被疏远贡献者自述（当事人叙事）与邮件列表原始记录（技术记录）与 commit message 中 “ok” 行（审核者署名）三方互证，区分 “补丁被拒绝” 与 “补丁被推迟” 两种情形——前者是结构性排斥的强证据，后者可能仅反映审核流程延迟；“结构性排斥” 论证须提供可证伪的证据（如补丁被拒绝的具体时序、de Raadt 的具体回复原文、贡献者离开的时序与拒绝时序的关联），否则易沦为不可证伪的总体性指控；“质量标准主观性” 论证须列举具体被拒绝补丁案例（如补丁内容、拒绝理由、技术评估），不得以 “可能存在” 模糊表述；【存疑判定依据】将批评者定性为 “外部观察者” 本身是排斥性话语，须辨析批评者是否为前 OpenBSD 贡献者——若是前贡献者，则 “外部” 定性不成立，OpenBSD 阵营的 “外部放大” 指控本身可能是回避批评的形式主义话语；0 信任原则提示：被疏远贡献者自述存在自利偏差与记忆偏差风险，当事人可能在离开后重构 “被排斥” 叙事以合理化个人选择；多源交叉验证不可靠性规则提示：多个被疏远贡献者在 “排斥感” 叙述上的一致性可能源于共同立场而非独立验证，史家须辨析其是否为对同一文化氛围的独立观察；OpenBSD KNF 代码风格本身是工程标准而非纯审美偏好——C 代码格式化、命名约定、错误处理风格等 KNF 规范有客观工程基础，“质量主观性” 论证须区分 “审美偏好” 与 “工程标准” 两类拒绝理由，不得将所有 KNF 相关拒绝归为审美偏好
  
**文献**：被疏远贡献者自述；OpenBSD 邮件列表存档（misc@、tech@ 中补丁被拒绝案例）；OpenBSD KNF 代码风格文档；社区治理研究文献 ［A］
