# 075.6.3 NetBSD 1.x 安全响应的架构关联——securelevel、MI/MD 与 pullup 模型

  **要点**：NetBSD 1.x 时期的安全响应能力受三项架构因素约束——其一，securelevel 内核安全等级机制经 NetBSD 1.0 rebase 至 4.4BSD-Lite 引入（27.14.3 所述），但 securelevel 限制 root 能力而无法阻止网络服务远程漏洞（BIND、telnetd、DHCP）与本地权限提升（mmap、procfs），故 securelevel 引入并未显著降低 NetBSD 1.x 的漏洞面；其二，MI/MD 分层架构使安全修复须在多平台验证后方可 pullup 至稳定分支，1996-1997 年 pullup commit 的作者多为 rat（pullup 操作执行者）而非原始漏洞发现者，反映 NetBSD 安全响应的工程分层——原始修复在 -current 分支由漏洞发现者提交，pullup 至 1.x 稳定分支由 releng 团队（rat、he 等）执行；其三，pullup 安全响应模型在 1998 年 SA 制度建立后保留，SA 公告与 pullup commit 并行——SA 公告向用户披露漏洞信息与补丁获取方式，pullup commit 在源码层面执行回溯，二者构成 NetBSD 安全响应的双轨制；NetBSD 1.x 时期 50 条 security fix commit 中，2000 年 2 月 he 的 procfs 修复修正版与 2000 年 3 月 he 的 ip_input.c 编译器 bug 安全漏洞修复（commit_hash `8c06dd0b055e31625eb646eb1f393905ef3dbddd`，"work around a compiler bug that causes a security vulnerability"）反映安全漏洞的诱因多样性——procfs 为代码逻辑缺陷，ip_input.c 为编译器 bug 引入的安全漏洞
  
**史料**：netbsd.duckdb `commits` 表（netbsd-src, 1993-04-01 至 2000-12-01, 50 条 security fix commit）；4.4BSD SMM: 16《On the Security of UNIX》securelevel 描述；NetBSD 1.0 Release Notes（4.4BSD-Lite rebase）；NetBSD pullup 机制文档 ［A］
  
**史观**：MI/MD 分层是 NetBSD 工程传统，但这一形式在安全响应场景中转化为内容约束——多平台验证延迟安全修复 pullup 速度；多平台移植优先策略的安全代价是 pullup 延迟，这一代价在 1998-2000 年 SA 制度建立后通过 SA 公告 + pullup commit 双轨制部分缓解
  
**辨析**：securelevel 在 NetBSD 1.x 安全响应中的实际作用须精确界定——securelevel 限制 root 修改不可变文件（**chflags(2)** schg 标志）、访问 `/dev/mem` 与原始磁盘、修改系统时间，但无法阻止网络服务远程漏洞利用与本地用户利用用户空间工具漏洞提权，故 securelevel 引入是 NetBSD 安全基线升级的必要条件而非充分条件；MI/MD 架构对安全响应速度的影响须量化评估——1996-1997 年 pullup commit 的时间延迟（从 -current 原始修复到 1.x 稳定分支 pullup）因缺乏 -current 分支原始 commit 时间戳而无法精确计算 据一手文献印证消解^doubt-resolved-301：pullup 延迟时间须对照 netbsd-src CVS 历史中 -current 分支原始 commit 与 1.x 分支 pullup commit 的时间差核实 ］；2000-03-02 he 的 ip_input.c 编译器 bug 安全漏洞（commit_hash `8c06dd0b055e31625eb646eb1f393905ef3dbddd`）须区分“编译器 bug 引入的安全漏洞”与“源代码逻辑缺陷”——前者属于工具链缺陷，后者属于代码设计缺陷，二者的修复路径不同（编译器 bug 须通过 workaround 或编译器升级修复，源代码缺陷须通过代码修改修复）；【0 信任原则·pullup 延迟评估】pullup commit 的 author_date 反映 pullup 操作时间而非原始修复时间，安全响应速度评估须以 -current 分支原始修复时间为基准
