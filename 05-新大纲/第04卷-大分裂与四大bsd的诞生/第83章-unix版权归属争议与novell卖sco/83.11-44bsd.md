# 83.11 4.4BSD-Lite 取代 386BSD 成为 FreeBSD 与 NetBSD 直接安全基线（1994-1995）

## 83.11.1 4.4BSD-Lite 作为 FreeBSD 2.0 与 NetBSD 1.0 共同新安全基线

  **要点**：**1994 年 6 月** 4.4BSD-Lite 发布后，FreeBSD 2.0（**1994 年 11 月 22 日** 网络发布）与 NetBSD 1.0（**1994 年 10 月 26 日** release tag）均 rebase 至 4.4BSD-Lite，4.4BSD-Lite 取代 386BSD 成为 FreeBSD 与 NetBSD 的共同直接安全基线；FreeBSD 1.x（**1993-1995**）与 NetBSD 0.8/0.9（**1993**）先前直接基于 386BSD 0.1（**1992-07**）+ patch kit，其安全基线为 4.3BSD-Reno 安全机制在 80386 平台的移植——root/超级用户二元特权模型、文件权限 rwx、setuid/setgid、DES **crypt(3)** 密码散列、单文件 `/etc/passwd`、4.3BSD 网络栈远程漏洞面；4.4BSD-Lite rebase 后这一 386BSD 安全基线被 4.4BSD-Lite 的安全机制取代，386BSD 作为 FreeBSD 与 NetBSD 直接安全基线的历史地位在 **1994 年下半年** 终结；OpenBSD 1.0（**1995 年 10 月 18 日** fork）经 NetBSD 1.0 间接继承 4.4BSD-Lite 新基线，386BSD 作为 OpenBSD 直接基线的地位更早在 **1994 年 10 月** NetBSD 1.0 rebase 时即被取代。4.4BSD-Lite 取代 386BSD 作为安全基线时间线如下：

| 时间 | 事件 | 安全基线变化 |
| -- | -- | ---------- |
| **1992.7** | 386BSD 0.1 发布 | 386BSD 成为 FreeBSD/NetBSD 直接基线 |
| **1993.4** | NetBSD 0.8 发布 | 基于 386BSD 0.1 + patch kit |
| **1993.11** | FreeBSD 1.0 发布 | 基于 386BSD 0.1 + patch kit |
| **1994.6** | 4.4BSD-Lite 发布 | 法律洁净版本出现 |
| **1994.10.26** | NetBSD 1.0 发布 | rebase 至 4.4BSD-Lite |
| **1994.11.22** | FreeBSD 2.0 发布 | rebase 至 4.4BSD-Lite |
| **1995.10.18** | OpenBSD fork | 经 NetBSD 1.0 间接继承 4.4BSD-Lite |

## 83.11.2 securelevel 等 4.4BSD 新安全机制经 4.4BSD-Lite 传递给三大 BSD

  **要点**：4.4BSD-Lite 引入的 securelevel 内核安全等级机制经 rebase 路径直接传递给 FreeBSD 2.0 与 NetBSD 1.0，并经 NetBSD 1.0 → OpenBSD 1.0 fork 间接传递给 OpenBSD——level 0 不安全模式（insecure mode）、level 1 安全模式（secure mode，禁止 `/dev/mem` 访问、原始磁盘写入、强制 **chflags(2)** 不可变标志）、level 2 高安全模式（highly secure mode，进一步限制系统时间修改），securelevel 一旦提升至非零级即不可降级须重启方能恢复至 level 0；securelevel 是 4.4BSD-Lite 时期 CSRG 最后定型的安全机制，是 FreeBSD 后世 `kern.securelevel` sysctl、NetBSD `kern.securelevel`、OpenBSD **securelevel(7)** 的直接祖先；386BSD 0.1 时期未引入的 securelevel、chroot 安全沙箱用途（4.4BSD-Lite 时期仍为构建隔离用途，详见 `3bsd-vax-security.md`）、shadow password（System V 才有 `/etc/shadow`，BSD 延续单 `/etc/passwd` 直至 FreeBSD 4.x 才弥合〔存疑：shadow 口令（master.passwd）引入 FreeBSD 的通行记载早于 4.x，此说无来源支撑，待 FreeBSD 源码史核验〕）等机制经 4.4BSD-Lite rebase 方能进入 FreeBSD 与 NetBSD 主线；FFS soft updates 的完整机制由 McKusick 在 CSRG 解散后研发（1990 年代末至 2000 年），非 4.4BSD-Lite 安全机制定型的组成部分，但 4.4BSD-Lite 时期 FFS 元数据一致性问题已被 CSRG 识别为待解工程难题
  
**史料**：4.4BSD SMM: 16《On the Security of UNIX》securelevel 初始描述、4.4BSD PSD: 5《Berkeley Software Architecture Manual (4.4 Edition)》securelevel 相关系统调用接口（如 `securelevel` sysctl 与 **chflags(2)** 不可变标志）、McKusick et al. 1996 设计与实现一书第 9 章；McKusick M K. Soft Updates: A Technique for Eliminating Most Synchronous Writes in the Fast Filesystem. **史观**：〔订正注：原作自撰标签“密码学与信息安全”未挂条号，去号留论旨〕securelevel 是 CSRG 最后定型的安全机制，是 BSD 后世安全等级机制的直接祖先；总纲第 3 条——不存在进步，只有权力再分配（存疑）〔订正注：原作伪标签族名目“终结中的延续”未挂条号，按族例改挂〕：4.4BSD-Lite 的安全机制经三大 fork 持续演化，是 CSRG 解散后 BSD 安全基因延续的关键载体
  
**辨析**：securelevel 在 4.4BSD-Lite 中为概念雏形，其完整机制在后世 BSD 中持续演化——FreeBSD 演化为 `kern.securelevel` sysctl，NetBSD 演化为 `kern.securelevel`，OpenBSD 演化为 **securelevel(7)** 手册页并进一步加固；FFS soft updates 与 4.4BSD-Lite 的关系须严格区分——FFS 在 4.4BSD-Lite 时期存在已知一致性难题（元数据依赖顺序、同步写开销），是 soft updates 研发的史源背景，但 soft updates 完整机制在 CSRG 解散后由 McKusick 研发并集成至 FreeBSD 4.x（约 1999-2000 年），非 4.4BSD-Lite 安全机制定型的组成部分；【0 信任原则·存疑处理】FFS soft updates 任务清单提示与考据结果存在差异，本节采用考据结果，对存疑项保留 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］ 标注，避免为消除存疑而强行采信低质量来源或臆造证据

## 83.11.3 386BSD 直接基线地位被 4.4BSD-Lite 取代的法律与技术双重动因

  **要点**：386BSD 作为 FreeBSD 与 NetBSD 直接安全基线的地位被 4.4BSD-Lite 取代，是法律与技术双重动因共同作用的结果——法律动因为 USL v. BSDi 诉讼和解协议（**1994 年 1 月** Novell 与 UC Berkeley 达成和解，要求 Net/2 中删除 3 个 System V 共享内存/信号量相关文件、约 70 个文件添加 USL 版权声明，Novell 承诺不起诉基于 4.4BSD-Lite 的组织或个人），386BSD 基于 4.3BSD-Reno/Net-2 含争议代码的法律地位模糊，FreeBSD 1.x 与 NetBSD 0.8/0.9 经 386BSD 间接继承这一法律风险，须通过 rebase 至 4.4BSD-Lite 消除；技术动因为 4.4BSD-Lite 引入 securelevel 等 4.4BSD 新机制，386BSD 0.1 基线（4.3BSD-Reno 安全机制在 80386 平台的移植）未引入这些机制，rebase 至 4.4BSD-Lite 后 FreeBSD 2.0 与 NetBSD 1.0 方能继承 securelevel、4.4BSD SMM: 16 安全文档、4.3BSD-Tahoe/Reno 时期补丁纪律等新机制；法律与技术双重动因共同决定 386BSD 直接基线地位被 4.4BSD-Lite 取代的历史必然性，这一取代是 FreeBSD 赓续 CSRG 未竟事业的关键节点——FreeBSD 与 NetBSD 通过 rebase 至 4.4BSD-Lite 重新接入 CSRG 主线代码演化，CSRG **1995 年** 解散后 BSD 主线代码演化权完全转移至三大 fork 项目
  
**史料**：USL v. BSDi 和解协议 1994.1（含要求删除的具体文件清单与代码清理范围）、4.4BSD-Lite Release Notes 1994.6（说明与 4.4BSD 完整版的差异、删除的文件、新增的安全机制）、FreeBSD 2.0 Release Announcement 1994.11.22、NetBSD 1.0 Release Announcement 1994.10.26、McKusick M K. Twenty Years of Berkeley Unix [M]//Open Sources, 1999（当事人一手记载）；bsd_commits.duckdb 数据库证据——bsd_commits.duckdb 查询 L3.6.1 显示：1994 年（USL 诉讼和解年、4.4BSD-Lite 发布年）含 license/copyright/patent/BSD 关键词的 commit 为 3,005 commits/62 位贡献者，1995 年（4.4BSD-Lite2 发布年、CSRG 解散年）升至 4,055 commits/95 位贡献者，反映 USL 诉讼和解后 BSD 阵营对许可证与版权议题的关注度提升，4.4BSD-Lite 的法律洁净催生了大量与许可证相关的代码提交 ［A］
  
**史观**：总纲第 13 条——法律与道德是利益分配（存疑）〔订正注：原作自撰标签“法律结构”未挂条号，按论旨近第 13 条补挂〕：法律结构（USL v. BSDi 和解协议）直接塑造技术路径（386BSD → 4.4BSD-Lite rebase），是 FreeBSD 赓续 CSRG 未竟事业的关键法律节点；〔订正注：原作自撰标签“许可证”未挂条号——“许可证（作总纲主题）”在伪标签族清单，去号留论旨〕4.4BSD-Lite 完全自由许可证是三大 fork 重建的法律基础，许可证模式决定 BSD 代码的演化路径
  
**辨析**：386BSD 直接基线地位被 4.4BSD-Lite 取代的法律与技术动因须区分——法律动因（USL 诉讼和解要求消除争议代码）是直接驱动，技术动因（securelevel 等 4.4BSD 新机制引入）是 rebase 后的附带收益，二者非对立而是互补；【0 信任原则·关键词匹配可能误报】L3.6.1 的关键词匹配基于 message_subject LIKE ‘%license%’ OR ’%copyright%’ OR ‘%patent%’ OR ’%BSD%’，可能将包含 “BSD” 一词但与许可证无关的 commit 误报为许可证相关 commit，1994-1995 年的 commit 量级须结合手动抽样核实关键词匹配精度；【0 信任原则·commit 量不等于质量】L3.6.1 的 license/copyright 关键词 commit 量增长反映开发者对许可证议题的关注度但不等于许可证清理工作的实际完成度；USL 诉讼和解协议要求删除的具体文件清单须查协议原文，本节不臆造具体文件数，仅引用 McKusick 1999 当事人一手记载（3 个文件被完全删除、约 70 个文件添加 USL 版权声明）
