# 286.1.5 NetBSD引入NVMe支持取OpenBSD代码而非FreeBSD实现后者系In

- NetBSD 引入 NVMe 支持取 OpenBSD 代码而非 FreeBSD 实现，后者系 Intel 直接贡献；主持人归因于 OpenBSD 本为 NetBSD 的 fork、设备模型与内核更接近故移植 diff 更小，并以同一 NVMe 设备在传统盘模拟接口下五六百兆与 NVMe 模式读 3800 兆、写 1700 兆每秒的性能差，及协议允许 64 路并发而其中一路保留给管理用途的队列细节佐证技术跃迁。 [存疑脚注]移植路径归因为主持人单源推断（原话以 I imagine 引导），未见 NetBSD 移植者自述佐证；性能数字为主持人借测试集群设备的一手自述（BSD Now EP141，[3600.8-3640.4]，L4）[订正：原 [3607.47-3631.34] 并 65536/63 并发表述，2026-09-30 SenseAudio 重转核对]
- 旧基线之辩是本期最有张力的技术判断：SmallWall 坚守 FreeBSD 8.4，主张 “Old is good”（1380.53-1383.13）——基线更久经测试，因 Shellshock 与 Heartbleed 均未波及（无 shell、无受影响特性），但 8.4 安全支持数月内终止，向 FreeBSD 10 迁移牵动大量代码；且历史上 monoWall 曾因 FreeBSD 6 网络性能不济而自 4 直接跳 8——稳定与前沿的取舍并非单向进步，而是按自身负载场景的权衡。（BSD Now EP97，[1374.01-1478.79]，L1）
- 转写为双音轨交错且时间戳乱序，ASR 讹误密集（Chris Moore=Kris Moore、Alan Duke=Allan Jude、Ipsak/Ipsac/IPset=IPsec、q-cube=kqueue、beehive=bhyve）；Gurney 所述 kqueue 锁定项目由其当时公司 Encircle 资助一节仅单源；录制日期 2014 年 10 月 29 日由转写开场白自证，与 EP62 前后衔接一致；上述专名与公司名均须以 shownotes 与 Gurney 网站复核。 [存疑脚注] Encircle 公司名、Camille 拼写、AUX 记法均待核。（BSD Now EP61，[1805.72-1845.76]，L4）
- 当事人关于FreeBSD PF在FreeBSD 10之后将作为独立分支继续发展、并将在部分方面持续优于OpenBSD PF的判断，属于基于当时开发状态与预期测试的推断，需以日后两个PF实现的实际走向复核。 [存疑脚注] 此为2014年当事人基于当时FreeBSD 10 SMP可扩展性预期的前瞻判断，是否兑现需对照后续FreeBSD PF与OpenBSD PF的分叉事实。（BSD Now EP25，[1400.92-1442.64]，L4）
- 存疑点集中在 DHCP 技术路线：主持人称“OpenBSD 最新 DHCP 服务器”并提及新近引入、基于其防火墙同步机制的补丁（103.8-124.68），此表述与 2008 年前后 OpenBSD 的实际状态存在时间线张力，转写内核实无门。另转写专名多误：Dyna Bollack 应为 Linux Live CD Dyne:bolic，Socrus、Socrist、Socrace 均为 Soekris 之误转；“dhcpd 版本三”应指 ISC DHCP 3.x 的同步能力。本转写文件内 segment 顺序错乱，按时间戳复原后首尾完整、无受损旗标，可整体采信。 [存疑脚注] “OpenBSD 新近引入的 DHCP 同步补丁能否进入 4.4”仅为主持人口头转述，且其与 2008 年 OpenBSD 树中运行 ISC dhcpd 的实际状况是否相符无法在转写内核实，须以 OpenBSD 源码树提交记录与 4.4 发行公告交叉验证后方可引用。（BSDTalk EP157，[103.8-129.96]，L4）
- 该期转写质量整体可用但人名与术语讹化严重：转写中的 Rob Lutzon 按其自述研究领域（安全与高性能网络）应为 Robert Watson，Philip Papps 应为 Philip Paeps，George Neville-Nail 应为 George Neville-Neil，Rui Paolo 应为 Rui Paulo，Stacy Son 应为 Stacey Son；PCVSD、PCBSC、PCBs 均为 PC-BSD，STTP、SETCP、SCP 均为 SCTP，Zendom U 为 Xen DomU，frivici、frivBSD、FribiSD、FreeBC 均为 FreeBSD。引用该期观点时须先以原始音频核对正名。 [存疑脚注] 人名正名系依据研究领域与上下文所作推断，未经原始音频逐字核对前不得直接引用（BSDTalk EP173，[74.4-1185.9]，L4）
- 社区以 Vyatta 限制 ARP 表条目数等厂商先例类推 pfSense 将走向功能阉割与闭源，这一担忧的依据是对其他项目轨迹的观察而非本项目的事实；Buechler 的否认属当事人立场陈述，不足以独立定谳——许可证收紧与商标执行同商业利益的张力，须与次年 pfSense 生态的分叉动向及后续许可证实践相互印证后方可评判。 [考据脚注] 闭源化担忧为社区推断、当事人否认，两者均为立场表达；pfSense 生态后续分叉须另行考据（BSDTalk EP242，[938.90-978.70]，L2）
- 受访者将 FreeNAS 跨版本升级故障归因于自身未细读升级说明而非软件缺陷，此为当事人单方自我归因，且转写文件分段顺序错乱（时间戳非单调），具体升级版本与故障细节无法在本访谈内独立验证。 [存疑脚注] 升级故障的自我归因系单方陈述，缺少版本号与故障记录佐证；转写分段顺序错乱但不损内容完整性。（BSDTalk EP254，[500.28-533.44]，L4）
- 安装器生态的分岔与惋惜：当事人与 PC-BSD 开发者邮件交流并赞赏其成果——外观精致、发行版优秀，也认同简易安装是引导用户接触操作系统的好方式；但惋惜 PC-BSD 的图形安装未与 BSD installer 结合：BSD installer 的前端系统 DFUI 独立于用户输入、可动态生成表单，同一后端既可驱动 DragonFly BSD 或 pfSense 的网页安装，也可输出 CGI 或 curses 前端，另有尚待打磨的 Qt 前端；两个项目本可共用一个安装器、只需重写 Qt 前端。（BSDTalk EP39，[588.0-676.64]，L1）
- 桌面使用的坦白与 X 的短板：当事人自认会因此挨批——桌面用 Microsoft 产品与 OS X，虽尝试过 Linux 与 FreeBSD 上的 GNOME、KDE、XFCE 且评价不恶，但因职业须支持 Apple 与 Microsoft 产品，桌面停留在 XP 与 OS X 更省事；服务器、防火墙与路由器则全部用 FreeBSD；BSD 桌面的具体短板：三显示器在 X 下难以各按理想原生分辨率配置，为此耗费的时间不如写代码，而 X 剪贴板行为不合标准——关闭应用即丢失剪贴板数据，与 Windows、OS X 乃至 OS 9 的惯例相悖。（BSDTalk EP39，[678.44-772.88]，L1）
