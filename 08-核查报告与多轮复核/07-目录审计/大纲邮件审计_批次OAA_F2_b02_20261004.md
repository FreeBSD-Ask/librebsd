## 五、事件与教训（供后续批次沿用）

1. **base64 附件解码坑（pk311538）**：初版解码脚本从 `Content-Transfer-Encoding: BASE64` 头行开始取段，导致头文字母（`Content`、`Transfer`、`Encoding`）被当成 base64 字母表消耗、每个字节全部错位，解码出乱码。**必须先越过分隔头的空行**（`\r\n\r\n` 与 `\n\n` 取较早者），再按 `[^A-Za-z0-9+/]` 清洗并截断到 4 的倍数。修好后 `debug.diff` 14,721 B 解出，实测 `DPRINT_MASK=9`、`DPRINT_WARN/INFO/DATA=5/5/5`、`DEBUG_WARN/INFO/DATA=3/3/3`、`DEBUGLIST=4`、`DPRINTLIST=3`、`sys/debug.h=4`、`sysctl=18`、`debug.c=5` → **B 级留档，判定件不改**。
2. **我曾把宿主从 `git show HEAD:` 整文件恢复**，之后 apply 干跑报“已落过 2,787 / 退化 2,743”，看起来像数据丢失。`git log -- <宿主>` 证明波10、波11+12、波13 **早已提交落地**，恢复只是把已提交的行拉回原位，apply 干跑的“已落过”是在对已就位行做幂等比对——**没有任何东西被回滚**，本轮真正新增的只有 778 行。教训：apply 的“退化”计数是**定位策略统计**，不是内容损失；判据只能是差分门禁。
3. **`git status` 幽灵 ` M `**：宿主显示已修改，但 `git hash-object` == `git rev-parse HEAD:` == `9e7ea4f2144…`。UNC stat 缓存假象，非真实差异。**不得据此判定工作区脏。**
4. **UNC 上 `ls`／`find` 假阴**：目录明明有文件却返回空（SMB）。**一律用 Python `os.listdir`／`os.stat` 按精确路径**。
5. **UNC 上禁内联 `python -c` 跑长脚本与 heredoc 写 UNC 路径**：反复 `FileNotFoundError` 指向明明存在的目录；同一代码存成 `.py` 文件即正常。本轮所有校验与修复脚本均落盘为 `script/_db_row_mining/_tmp/_f2_*.py`。
6. **校验脚本自身造假象的三例**：①G4 首版口径错（见 §四）；②`_f2_review_bodies.py` 首版跨全部分片搜人名，导致“Bill Studenmund”平凡命中数十片——必须改为**仅同片内**搜索；③`_f2_triage_152.py` 漏 `.fetchall()` 把 connection 当迭代器。
7. **判读件 `新摘要句` 可能是 list**：原 apply 对 list 做 `' '.join`，把写手误写进列表的字数元素当成文本拼进大纲（实证 pk229579 块体尾部被写入“定论。 50”）。已改为**拒绝落地**并记异常。
