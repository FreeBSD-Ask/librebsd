## 二、复核发现

1. **G3 汉字数口径的真实门槛是 `C < 30` 判 FAIL、`C == 30` 判 PASS**：`oaa_verify` 源码判定为硬不等式。本批自建校验一度按 `31` 自设线过严，p003 中 4 行 C=30 曾被误判不合格——按源码为准不返修。`--len-flex` 只放宽**上限**（CJK>80 或总长>200 仅打印备案、不判 FAIL），**下限不放宽**。计字口径为 `body = 摘要行.split('引用时按')[0].rstrip('。')`，收尾句号不计入。

2. **🔴 登记序曾漏掉整条 `a` 波（7 件 / 306 key），已补回并复核影响面**：终态合并初版序为 `s → sup_q → b`，未含 `a` 波。`a` 波与 `b` 波几乎不相交（a 306 key、b 245 key、交集仅 10），`a` 波未搬入 `suppb`、自成一段（`shards/suppa`）。但影响面有限：**`a` 波 306 个 key 全部已由 `s` 波登记为 fix 类**（fix-format 283／fix-text 19／remap 4，无 fix-db、无存疑），故不存在“keep 静默翻成 fix”的漏账。补回后登记序 157 → **164** 件，合并判定分布回到 `fix-format 2,746／remap 107`（补回前误为 2,742／111）。

3. **🔴 波次次序陷阱：`b` 必须排在 `a` 之后，按 apply 提交先后而非文件名字母序**：`a002` 对 4 条判 `remap`（目标宿主 11.12），而更晚的 `b008/b009/b010`（段五 `d4b7b1c62`）把同 4 条改判 `fix-format` **并已实写宿主**。首版修复曾把 `a` 放在 `b` 之后，导致这 4 条在台账里被记成 `remap`（批次标记 `f4b09_a002`）——台账记录与磁盘终态背离，已纠正为 `fix-format`（批次标记 `f4b09_b008/b009/b010`）。其 `remap` 方向不丢失：由 remap 台账的“原判 remap”列承接移交。全量复核 **490 个多波覆盖 key 判定全部一致**，唯此 4 条例外。

4. **🔴 6 块磁盘变更归属他会话，非本批引入——用 git 反证而非猜测**：终态对账发现 11.3 有 6 块被改写，但其判读判定为 keep（4）／fix-db（2），且**其摘要文本与所有 176 件判读件的 `新摘要句` 均不匹配**（无一件是宿主实态来源）。逐块查 git 历史定位：`bd0aba260`“112 X7/X8/X9 三路交叉复核落卷”插在 `8438376a9` 与 `6382a53be` 之间，**并发 112 线在同一宿主上独立重写了这 6 条摘要**（内容更具体，如 pk 114853 补出“Aegis 上限约 1500”、pk 119590 补出“属于编程语言层面的问题而非 Unix 自身问题”）。基线有效性已验：`.bak-f4b09a` 字节数 **3,305,878 与 `git show 0916595a5^:` 完全一致**，故差异真实存在。
   **由此得出精确闭合**：3,879（磁盘实变更）− 6（他会话）＝ **3,873**，恰等于 fix-format 2,746 ＋ fix-text 1,127 ＝ **3,873**。**本批实际改写块数与 fix 类判定数一字不差**，keep／fix-db／remap 三类的块一行未动。

5. **挂账台账曾因字数重判而缩水，已复原完整移交清单**：113 条原判 remap／fix-db 的块为过字数门禁被改判 fix-format／fix-text（仅为摘要达标，位置与等级判断未变），其原判线索只存活在判读件 `问题` 字段与 `shards/supp4` 的 `_原判` 字段里。若按当前判定机械计数，台账会从 187／169 缩到 107／136，移交即不完整。`_f4b09_final_merge.py` 的 emit 逻辑已改为“当前判定 **或** `_原判` 字段前缀”双条件收录：**fix-db 136（原判 33）→ 169**、**remap 107（原判 80）→ 187**、存疑 0。
