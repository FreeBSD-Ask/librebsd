| DB | 绝对重复（同列表同 msg_hash） | 处理 |

> openbsd 重复根因：misc 分块入库时，同一邮件两次入库的 message_id 生成规则不同（一次用 list_name `openbsd-bugs`，一次用 list_id `11`），绕过 `(list_id, message_id)` UNIQUE 约束，但 msg_hash 相同。已按 `GROUP BY msg_hash, list_id` 保留最小 id 删除。

> 跨列表重复（freebsd 18,091 / usenet 11,369 等）为 cross-posting 正常现象（同一邮件发多个列表），**不删除**。

## 二、优化策略（按优先级）

### P0 — 数据正确性（已完成 ✅）
- [x] openbsd 3,833 条绝对重复删除
- [x] NULL year 全库归零（此前已完成）

### P1 — 查询性能（本轮已执行 ANALYZE，建议补 msg_hash 索引）
1. **ANALYZE 重建统计信息**（已执行）— 6 库 sqlite_stat1 从 0 恢复，查询优化器可获得准确的索引选择性。
2. **添加 msg_hash 索引** — `msg_hash` 是去重/完整性验证的核心字段（100% 填充），当前无索引，全表扫描成本高。建议：
   ```sql
   CREATE INDEX idx_messages_hash ON messages(msg_hash);
   ```
   用途：跨库重复检测、按内容哈希查重、完整性校验。

### P2 — 存储优化（需评估后执行）
3. **VACUUM 收缩** — `auto_vacuum=0`（NONE），删除 3,833 条后 openbsd 有碎片；freebsd 有 16 页 freelist。VACUUM 可回收空间但会锁库+重写全文件（freebsd 8.9G 耗时较长），建议择机执行。
4. **body_html 冗余列** — 6 库 body_html 几乎全空（仅 freebsd 472 条非空），该列长期无用，可考虑 DROP 节省表空间（需先确认无依赖）。

### P3 — 结构一致性（不紧急，建议记录待办）
5. **元数据表不一致** — other-bsd 缺 `schema_meta` 表；usenet 缺 `ingest_log` + `schema_meta` 表。建议补建以统一 6 库结构。
6. **journal_mode** — 当前 `delete`（默认）。批量写入场景可临时切 `WAL` 提升并发，单机只读考据场景收益有限，可不改。
