## 第一部分：总体设计

### 1.1 三层架构

```
① 本体层（图谱是什么）
   entity（6 基类 + 18 细分 subtype）× entity_relation（24 受控关系）
   落库位置：historical_claims.db（v0.1 已有表，v0.2 补分类学与时间窗列）

② 规则层（什么组合是历史不可能的）
   consistency_rule 登记表（T1-T5 时间类 / N1-N6 叙事类，共 11 条，编号稳定）
   每条规则带 severity（block/warn/info）与 SQL 实现文本

③ 审计层（检查结果留痕与门禁）
   consistency_check 结果表（run_id 快照制）+ v_unresolved_conflict 门禁视图
```

### 1.2 设计立场（与全书哲学一致）

1. **一致性检查是诚实性工具，不是真相裁决器**（P43）：规则命中 = "此处存在需要解释的张力"，不等于"某一方是错的"。N2（多起源）、N6（动机矛盾）允许**并存标注**作为合法处置——多面性本身可以是一致性检查的终点。
2. **未知不判违规**：时间窗为 NULL 的实体不触发 T 类违例，而是进入 `v_temporal_gap` 补考清单。BSD 史大量早期日期本就存疑（02 报告 §2.3 已点名日期脏区），强制判定会制造伪精确。
3. **规则编号稳定**：T1-T5/N1-N6 编号一经发布不再复用它义，审计报告、争议簿、章节评分均可引用（07/09/17 号文档已有先例）。

## 第二部分：实体本体（18 类 → 6 基类）

### 2.1 映射表（entity_type_class，DDL 已预置 20 行）

任务书 Phase 31 列 18 类实体。为保持 v0.1 表结构零改动，采用"**6 基类列 + subtype 细分表**"方案：`entity.entity_type` 取 6 基类（person/org/project/technology/event/place），细分写入 `entity.attrs` JSON 的 `subtype` 键，取值受 `entity_type_class` 表约束。

| 任务书实体类 | subtype | 基类 | 说明 |
| ------------ | ------- | ---- | ---- |
| 人物 | person | person | 迁移自 person_records/person_bio_research |
| 机构 | org | org | 通用机构 |
| 大学 | university | org | UC Berkeley、MIT、哈佛（P42：学术机构在 BSD 史中是一等行动者） |
| 公司 | company | org | AT&T/USL、BSDi、Apple、Juniper 等 |
| 项目 | project | project | FreeBSD/OpenBSD/NetBSD/DragonFly 及 CSRG、386BSD 等历史项目 |
| 发行版 | distribution | project | GhostBSD/OPNsense/pfSense/TrueNAS 等衍生发行（区别于主干项目） |
| 版本 | version | technology | 4.4BSD-Lite、FreeBSD 2.0；attrs 记 parent 项目。**版本与项目分立**是关键决策：N2 起源争议与 T1 时序检查都以版本为粒度（fork 发生在版本之间，不是"项目"之间） |
| 代码 | code | technology | 模块/文件级对象（如 TCP/IP 实现、Jolitz 移植代码），07 影响分类类型 1 的载体 |
| 技术 | technology | technology | 通用技术概念（虚拟内存、kqueue） |
| 标准 | standard | technology | POSIX/SUS/RFC——07 §类型 3 警示"标准化倒灌"，标准必须独立建模 |
| 论文 | paper | technology | 作为**被引用的知识对象**；其史料载体另在 raw_source(namespace='ref')，二者经 cross_ref 关联 |
| 书籍 | book | technology | 同上（如 McKusick《The Design and Implementation》各版） |
| 许可证 | license | technology | BSD 4-clause/3-clause/MIT/GPL——P41/07 类型 8 要求落到文本与决策 |
| 会议 | conference | event | BSDCan/EuroBSDCon/AsiaBSDCon，discussed 关系的舞台 |
| 法律事件 | legal_event | event | USL v. BSDi、SCO 诉讼、和解——T3/N4 的核心对象 |
| 资金 | funding | event | DARPA 合同、基金会资助——建模为"事件"而非"机构属性"，因为资助是**有时间窗的关系事实**（07 DARPA 链的实体基础） |
| 硬件 | hardware | technology | 物质文化史料（03-原始史料库/09 硬件史料对应）：VAX、Sun-3 |
| 社区 | community | org | 无注册实体的虚拟组织（"FreeBSD 社区"），P42 警示不得等同共识 |
| 地点 | place | place | 伯克利、贝尔实验室所在地 |

**为什么不是 18 个基类**：SQLite CHECK 枚举 18 值会让 entity_type 的每个消费方（视图、审计脚本、下游文档）都背负 18 分支逻辑；6 基类 + 受控细分表把分类学的演化限制在一张表里（新增"播客""基金会年报"类实体只需 INSERT 一行）。

### 2.2 实体生命窗（v0.2 新增列）

```
entity.time_start / entity.time_end   -- ISO 8601，允许年份粒度
```

各基类的语义约定：人=生/卒（在世则 time_end NULL）；机构/公司=成立/解散；项目=发起/终止；版本=发布/停止支持；许可证=发布/废止；法律事件=立案/结案。

**填充来源**：person_bio_research（生卒已结构化）→ timeline_events 抽取 → 仓库库 earliest commit 日期（代码实体的 time_start 下界）→ 人工。**时间窗是 T 类规则的比较基准，其证据等级本身受措辞门禁约束**——一个来自回忆录的生年（L4）与来自户籍记录的生年（L3）在冲突时按 P41 仲裁。

## 第三部分：关系本体（24 受控关系）

### 3.1 任务书 20 关系全覆盖 + 4 补充

`entity_relation_type` 预置 24 行：任务书 Phase 31 的 20 个关系（created/worked_on/employed_by/funded/forked/derived_from/copied/ported/rewritten/influenced/adopted/rejected/licensed_under/acquired/merged/split/published/discussed/criticized/remembered_as）**零缺失**（自测 task20_rel_missing=[]），另补 4 个图谱必需关系：member_of（人→组织）、participated_in（人/机构→事件）、located_in（→地点）、successor_of（后继关系，与 forked 区分：fork 是分裂性分离，successor 是承接性延续）。

### 3.2 两个治理标志位

| 标志 | 含义 | 治理效果 |
| ---- | ---- | -------- |
| `requires_temporal_order=1`（14 个关系：created/funded/forked/derived_from/copied/ported/rewritten/influenced/adopted/rejected/licensed_under/acquired/merged/split/participated_in/successor_of） | 时序敏感 | 进入 T1 检查；缺时间窗进 v_temporal_gap 补考清单 |
| `requires_evidence=1`（除 located_in 外全部） | 关系须有证据 | 无 evidence_id 的挂接进 v_relation_unsupported |

### 3.3 influenced 关系的特殊纪律（与 07 号文档联动）

`influenced` **禁止裸挂**：任何 influenced 边必须回指一条 `claim_type='INFLUENCE_CLAIM'` 的主张（经 claim_relation 或 attrs JSON 的 claim_ref），由主张的 evidence_level 决定措辞门禁（07 §2.3：L1 级相关性主张不得产生"影响"边）。这把"影响"从图谱的**断言**降格为**主张的可查结果**——图谱不直接说历史，只呈现已审计的关系。

### 3.4 方向约定（全系统统一，周知各下游）

`entity_relation.from_entity = 来源端 / 发起端`，`to_entity = 结果端 / 承受端`。例：`(386BSD) --forked--> (FreeBSD)`、`(DARPA funding) --funded--> (CSRG)`、`(Bill Joy) --created--> (vi)**方向写反即 T1 误报源**（自测中已用正反两例验证 T1 SQL 对方向的敏感性）。

## 第四部分：时间一致性检查（T1-T5）

> 目标：禁止"历史不可能的组合"。所有 T 规则对 NULL 时间窗**不判违例、转补考**（v_temporal_gap）。

### T1 时序可行性（block）

**定义**：`requires_temporal_order=1` 的关系中，结果端 `time_start` 不得早于来源端 `time_start`。
**典型违例**：FreeBSD 作为来源 fork 出 386BSD（1993→1992 倒置）；某许可证被用于早于其发布的版本。
**SQL（已入 consistency_rule.sql_impl，自测验证正反例）**：

```sql
SELECT er.* FROM entity_relation er
JOIN entity_relation_type rt ON rt.relation_code = er.relation_type
JOIN entity fe ON fe.entity_id = er.from_entity
JOIN entity te ON te.entity_id = er.to_entity
WHERE rt.requires_temporal_order = 1
  AND fe.time_start IS NOT NULL AND te.time_start IS NOT NULL
  AND te.time_start < fe.time_start;
```

**边界**：日期粒度不一致时（年 vs 月），先按精度对齐到粗粒度再比较；同年内先后不可判的记为 `warn` 降级处置。

### T2 参与时存在性（block）

**定义**：participated_in / employed_by / member_of / created 关系中，关系时间窗必须落在主体的 [time_start, time_end] 内（time_end NULL 视为存续）。
**典型违例**："某人 1975 年参与 CSRG"而其 1977 年才入学；"某公司 1990 年资助 BSDi"而该公司 1995 年成立。
**判定伪 SQL**：

```sql
-- 关系时间 r_time 取 er.time_start；主体时间窗取 from_entity（人/机构端）
SELECT er.* FROM entity_relation er
JOIN entity a ON a.entity_id = er.from_entity
WHERE er.relation_type IN ('participated_in','employed_by','member_of','created')
  AND er.time_start IS NOT NULL AND a.time_start IS NOT NULL
  AND er.time_start < a.time_start
  OR (a.time_end IS NOT NULL AND er.time_start > a.time_end);
```

**与 02 盘点的衔接**：仓库库 contributors 表可自动生成 worked_on 候选，其时间窗 = 该贡献者首末 commit 日期（commit author_date 须先过脏区裁剪），T2 自动覆盖"提交时间落在人物生卒窗外"类异常（对应盘点发现的 1973 年 freebsd-ports 提交、2085 年 linux 日期）。

### T3 许可证先行（block）

**定义**：licensed_under(X, L) 的时间不得早于许可证实体 L 的 time_start。
**典型违例**："某代码 1988 年以 BSD 3-clause 发布"而 3-clause 是 1999 年从 4-clause 简化而来——这正是 N4（许可证双重定义）的时间维度。
**判定**：复用 T1 SQL，过滤 `er.relation_type='licensed_under'` 且结果端基类='technology'、subtype='license'。

### T4 术语时代性（warn）

**定义**：叙事单元/证据中使用的术语不得早于该术语的**首次见诸记载时间**（terminology_index 登记的 first_attested 字段，09 术语史接口）。
**典型违例**：在 1979 年的叙事中使用"开源"（open source 一词 1998 年才定型）、在 1985 年语境用"fork"的贬义社区用法。
**判定流程**：FTS 检索叙事单元文本 → 命中术语表 → 比较单元所述时间与 first_attested。severity=warn 因术语的**概念先行、名称后出**现象普遍（P28"时间是一种形式主义"：概念史与词汇史不同步是常态），命中后默认处置是"改用时代语汇或加说明"，不是删改史实。

### T5 引用时代性（warn）

**定义**：叙事单元引用的史料，其 source_date 不得晚于该单元所述事件的 time_end 上限（禁止用事后追述冒充当时记录）。
**衔接 P41**：第四层史料（回忆/访谈）用于重建"当时情景"时自动触发本规则提示，要求搭配第一、二层史料（对应 P41"引用第四、五层须带保留语气并配低层佐证"）。
**判定伪 SQL**：

```sql
SELECT nc.unit_id, nc.target_id FROM narrative_citation nc
JOIN narrative_unit nu ON nu.unit_id = nc.unit_id
JOIN evidence ev ON nc.target_type='evidence' AND ev.evidence_id = nc.target_id
JOIN raw_source rs ON rs.source_id = ev.source_id
JOIN entity e ON e.entity_id = (单元所述事件实体，经 claim_entity 解析)
WHERE rs.source_date IS NOT NULL AND e.time_end IS NOT NULL
  AND rs.source_date > e.time_end;
```

## 第五部分：叙事一致性检查（N1-N6）

> N 类检查跨"实体-主张-章节"三个层面，命中后的合法处置包括**并存标注**（P10 本体平等、P43 多面性）——不是所有矛盾都要消灭。

### N1 身份唯一性（block）

同一人物实体在不同叙事单元中的身份描述矛盾（"BSDi 创始人" vs "从未参与 BSDi"）；或两个实体撞名而未裁决。
**机制**：`v_entity_alias_conflict` 视图自动扫描 canonical_name 撞名（自测已建）；身份描述冲突经 claim_relation('contradicts') 在同一 entity 上检出。处置：合并实体（merged_into）或分立并注记。

### N2 起源唯一性（block，可降级为并存标注）

同一技术/项目的 ORIGIN_CLAIM / FIRST_APPEARANCE 主张多于一条且互不支持。
**典型**：inetd 的移植归属、jiffies 类机制的多起源。处置三选一：裁决（一方 superseded）、并存标注（claim_relation='related' + controversy 登记）、降为 UNVERIFIED。**07 类型 3 的"标准化倒灌"误用是本规则的高发区**：POSIX 接口相似 ≠ 同源。

### N3 日期唯一性（block）

同一事件在不同层出现两个互斥日期（timeline_events.event_date vs 章节叙述 vs 仓库 commit 日期）。
**容差规则**：精度不同取粗粒度兼容判定（'1993' 与 '1993-06' 不冲突；'1993-06' 与 '1993-11' 冲突）。仲裁序：metadata_interfaces.timeline_records（全书锚点）> 低 source_layer 史料 > 高 source_layer（P41 矛盾仲裁规则）。
**存量**：doubts_standalone 的 date 类（334 条）+ 年代类（33 条）迁移为 N3 的初始 run。

### N4 许可证定义一致性（block）

同一许可证在不同章节的条款叙述矛盾（经典场景：BSD 广告条款的存废时间线、"GPL 传染性"表述在各卷口径不一）。
**机制**：license 实体的 attrs 中维护**权威条款快照**（versioned），章节叙述引用快照版本号；版本号不一致即命中。对应 07 类型 8"许可证影响必须落到文本"。

### N5 判断一致性（block）

同一 claim 在不同章节的采信状态/措辞档位矛盾（第 3 卷写"确立了继承"，第 9 卷写"仅表面相似"）。
**机制**：claim 是全库单点（claim_id 唯一），narrative_citation 只能引用不能复述状态；检查 = 扫描同一 claim_id 被引用的各 narrative_unit 文本中的措辞档位是否越过 claim.wording_gate。**这是 09 争议簿"跨卷一致义务"的自动化执行**。

### N6 动机一致性（block）

对同一主体的 MOTIVATION 主张互斥（"Theo 分叉出于安全理念" vs "出于人际冲突"）而未登记争议。
**处置**：互斥动机**必须**进 controversy（controversy_position 各挂一方），允许并存呈现——但"各卷各采一说而不标注"是硬违规。对应 09 记忆史系统：动机叙述天然含记忆重构成分（第四层），N6 命中时默认要求补充当时文本佐证。

## 第六部分：审计流程与门禁

### 6.1 运行模型

```
每次审计 = 一个 run_id（'AUDIT-YYYYMMDD-nn'）
  1. 执行 T1-T5（SQL 可全自动）→ 命中写入 consistency_check（severity 按规则表）
  2. 执行 N1-N6（半自动：SQL 初筛 + 人工确认）→ 同上
  3. 生成 run 报告：block 数 / warn 数 / 新增 vs 复现 vs 已解决
  4. 门禁：v_unresolved_conflict 中 severity='block' 且 resolution IS NULL 的目标，
     禁止进入书稿定稿流水线（Task #20 审稿模式与 Task #22 验收映射消费此视图）
```

### 6.2 处置词表（consistency_check.resolution）

`已修正`（改正数据/文本）/ `并存标注`（登记争议或 coexists_with，P43 合法终点）/ `已裁决`（争议簿出暂定判断）/ `转补考`（时间窗缺失等，挂 Task #9 问题树）。**处置必须留人留时**（resolved_by/resolved_at）。

### 6.3 与既有审计资产的整合

- doubts_standalone 1,987 条 → 迁移为 consistency_check 的 **run 'AUDIT-LEGACY-20260801'**（历史存量），其中已解决 1,966 条带 resolution 迁移，未决 10 条 + 不可解 11 条保持未处置状态进入门禁视野；
- 08-核查报告的多轮复核记录（Markdown）作为 consistency_check.detail 的引用源（经 cross_ref），不重复录入。
