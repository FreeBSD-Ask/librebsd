# 第一部分 因果链 schema

## 1.1 设计立场：证据审计状态，而非本体论断言

本 schema 的首要设计决策是一个哲学定位，直接来自总纲 25（P35）："历史解释不得声称具有逻辑必然性；因果归因只能作为建构呈现。" 由此：

1. **箭头不表示"世界中的因果实在"，而表示"一条被提出、正在被审计的因果主张"。** `causal_arrow.status` 记录的是该主张当前的**证据审计状态**，不是历史本体。这一点与 P43（三重形式主义化：不存在待还原的真相，只有多面性的呈现）一致。
2. **"因果成立"（CAUSALITY_ESTABLISHED）在本书语境中的含义是：机制已被至少一条 L4 级证据（作者/开发者明确陈述）或等价的证据组合支撑，且时间一致性、替代解释、反证均已排查并留痕。** 它不等于"历史必然如此"——总纲 5（P15）禁止一切"必然/注定/不可避免"表述，因此 `status = CAUSALITY_ESTABLISHED` 的箭头在书稿出口处仍须译为弱表述（见 1.3 的措辞映射）。
3. **状态是单调可降的**：新证据到达时，任何箭头可被降级直至 REFUTED。REFUTED 箭头不物理删除——被推翻的因果主张同样是历史编纂的一部分（对应 P34 断裂美学：裂缝是诚实的形式）。
4. **链级状态由箭头状态聚合推出，不手工赋值**：一条链只要有一个箭头非 ESTABLISHED，整条链就不许在书稿中写成完整因果句。聚合规则写成视图（附录 B），防止人工误标。

## 1.2 形式模型：链、节点、箭头

```
causal_chain（因果链）
   │
   ├── causal_node（节点：历史事件/状态） × N
   │        按 seq_no 全序排列；节点是"事件或状态"，不是解释
   │
   └── causal_arrow（箭头：相邻节点间的机制主张） × (N-1)
            每个箭头挂接：机制描述、证据集、反证集、替代解释、
            时间一致性约束、反事实检查记录、状态审计历史
```

**节点（causal_node）**

- 节点是**历史事件**（有明确时点：如"1969-1975 DARPA 对网络研究的资助立项"）或**持续状态**（有起止窗：如"Berkeley 具备网络技术研究能力"）。二者用 `node_kind` 区分（`EVENT` / `STATE`）。
- 每个节点必须可指向主张库/时间线中的既有对象（`object_ref`），把"这个节点是什么"的定义权交给主张数据库（Task #10），本库只引用、不复述，避免事实性描述双写发散。节点允许带一个**描述性快照**（`node_summary`，≤150 字），但明确标注 `summary_is_authoritative = 0`（快照仅供阅读，权威定义在 object_ref 指向处）。
- 节点本身**不携带因果含义**。"DARPA 资助"只是节点；"DARPA 资助 → 产生了网络研究需求"是箭头。任务书第九阶段的核心禁令——"禁止“A发生，B发生，于是A导致B”"——在 schema 层面被实现为：**两个相邻节点之间若没有 causal_arrow 记录，系统视其为零因果**；书稿生成器只允许沿 causal_arrow 输出因果句。

**箭头（causal_arrow）**

- 箭头连接链内**相邻**节点（`from_seq` = `to_seq` - 1）。跨越多节点的长程因果必须拆成多段箭头逐段举证——这正是 DARPA 示例链拆成 5 段的原因。若研究者认为 A 直接导致 D，正确做法不是画长箭头，而是声明候选中间节点并逐段填充；填不出的段标 `INSUFFICIENT_EVIDENCE`。
- 箭头必须声明**机制**（`mechanism`：因如何产生果的过程描述）与**机制类型**（`mechanism_type`：资源传导/制度传导/人员传导/代码传导/需求传导/观念传导——六类与任务书"中介载体：代码/人员/文档/组织"衔接，另加需求与观念两类以覆盖 DARPA 链的前两段）。机制描述为空时，状态最高只能到 `MECHANISM_PROPOSED`（规则 R2，见 1.3）。
- 每个箭头挂接（全部为独立关联表，不塞 JSON 黑盒）：
  - **证据集**（`causal_arrow_evidence`，`role = supporting`）：引用证据 ID + 证据等级快照 L1–L5；
  - **反证集**（同表，`role = contradicting`）：反证同样必须挂证据 ID——"没有反证"与"找了没找到反证"是两回事，后者必须留检索记录（`search_log_ref` 字段，指向核查留痕）；
  - **替代解释**（`causal_arrow_alternative`）：每条替代解释是一个独立文本 + 其证据挂接位 + 处置状态（未评估/已排除/并存）。**未列任何替代解释的箭头，状态封顶 `MECHANISM_PROPOSED`**（规则 R3）——这是把"排除竞争假说"变成强制动作，而非美德；
  - **时间一致性约束**（`causal_arrow_temporal`）：因节点的终止时间必须早于（或在明确声明的共窗情形下不晚于）果节点的起始时间。违反即触发红旗（规则 R4）。时间数据缺失本身是状态：`verified = NULL` 表示"未核验"，与"核验通过"严格区分。

**链（causal_chain）**

- 链级字段含：名称、一句话论题（`thesis`：这条链试图审计的因果判断原文）、来源章节（`origin_chapter_ref`：链由哪一章的写作/复核需求触发）、链级反事实字段（见第四部分）、`hindsight_risk`（后见之明风险标记）。
- 链之间可交叉引用（`chain_cross_ref`）：同一历史事件常是多条链的公共节点（如"TCP/IP 实现"既在 DARPA→BSD 链上，也在 BSD→互联网扩散链上）。公共节点通过 `object_ref` 对齐到同一主张对象实现"节点复用"，跨库语义由主张库保证。

## 1.3 箭头状态枚举与升降级规则

**五个状态**（任务书第九阶段规定的五值枚举，语义按审计口径定义）：

| 状态 | 含义（审计口径） | 书稿出口允许措辞 |
| ---- | ---------------- | ---------------- |
| `CAUSALITY_ESTABLISHED` | 机制已陈述或强推断 + 证据≥L4（或≥2 条独立 L3）+ 时间一致性核验通过 + 至少列出并处置了 1 条替代解释 + 反证检索留痕 | "从记录来看，A 通过 m 机制为 B 提供了条件"；仍禁用"必然/注定" |
| `CORRELATION_ONLY` | 仅有 A、B 同时/相继发生的证据，无传导机制证据 | 只能写"A 与 B 相伴出现/相继发生"；禁止任何因果句式 |
| `MECHANISM_PROPOSED` | 机制已被提出（编纂者或文献中的假说），但直接证据 < L4，或替代解释未处置 | "有假说认为 A 通过 m 作用于 B，现有证据等级为 LX" |
| `INSUFFICIENT_EVIDENCE` | 连相关性证据都不足，或节点本身时间窗未定 | 书稿中必须写为信息黑洞（P34：明确标注而非推测填充） |
| `REFUTED` | 存在被采信的反证，或时间一致性被证伪，或机制被证明不成立 | "曾有“A 导致 B”的说法，现已证伪/被反证推翻"（可写成破除型段落） |

**状态机规则**（写入 schema 为 CHECK 约束 + 视图校验，见附录 B）：

- **R1（时间优先）**：`status IN ('CAUSALITY_ESTABLISHED','CORRELATION_ONLY')` 要求 `causal_arrow_temporal.verified = 1`。因先于果是最低门槛——连时间顺序都没核验的箭头不许谈因果或相关。
- **R2（机制优先）**：`mechanism IS NULL OR mechanism = ''` 时，status 封顶 `CORRELATION_ONLY`。没有机制就没有高于相关的状态。
- **R3（替代解释优先）**：`status = 'CAUSALITY_ESTABLISHED'` 要求该箭头至少存在 1 条 `disposition != '未评估'` 的替代解释记录。
- **R4（证据等级门禁）**：`CAUSALITY_ESTABLISHED` 要求支撑证据中至少 1 条 `evidence_level IN ('L4','L5')`，或 ≥2 条来源独立的 `L3`（独立性判定：不同当事人、不同史料层级、不同载体，三者至少居其二）；`CORRELATION_ONLY` 允许 L1 起步。
- **R5（反证优先）**：存在 `role='contradicting'` 且未被处置（`disposition IS NULL`）的反证时，status 自动封顶 `MECHANISM_PROPOSED` 并置 `dispute_flag = 1`。

**升降级路径**：

```
INSUFFICIENT_EVIDENCE ⇄ CORRELATION_ONLY ⇄ MECHANISM_PROPOSED → CAUSALITY_ESTABLISHED
任何状态 ──(采信反证/时间证伪)──> REFUTED
REFUTED ──(仅当新证据推翻原反证，且经复核留痕)──> 回到 CORRELATION_ONLY 重新审计
```

每次状态变化写入 `causal_arrow_status_log`（谁、何时、依据哪些证据 ID、从什么状态变到什么状态）——这是"持续证明而非完成解释"（P30 考据留痕）在因果层的实现。

**与 P15 偶然性的衔接**：`CAUSALITY_ESTABLISHED` 的箭头仍必须可回答"如果因没有发生"（第四部分）。因果成立 ≠ 必然发生——箭头成立后反而**强制**触发反事实检查，以标注偶然条件。这是本 schema 与一般因果建模（追求"确定因果"）的根本差异：本书要的是"确定的审计 + 自觉的偶然"。

## 1.4 SQLite DDL（设计文本，不执行）

> 说明：以下为设计文本，本次重构**不建库、不执行**。命名与约束风格对齐既有库盘点（02 号文档）中的惯例：TEXT 主键、`created_at/updated_at`、`schema_meta/update_log`。
> **落库裁决（已定，2026-08-12）**：本表组**独立成库 `causal_graph.db`**——由洗澄明拍板（`06-史学数据库schema设计.md` §8.2）。理由：因果链是高频迭代的**审计过程库**，主张库是主数据性质，分离便于独立备份与回滚；本表组自带 schema_meta/update_log，天然成库。与主张库的耦合点全部是 TEXT 引用位，无 SQL 级 FK 依赖，建库时以 cross_ref 登记互指。
> **跨库编码约定（已定，06 §8.2 / §4.1）**：
> ① `evidence_id` 一律使用主张库 evidence 表主键命名空间 **`EV-<六位序号>`**；
> ② `causal_chain.origin_claim_ids` 与 `causal_node.object_ref` 引用主张库 claim 表主键 **`CL-<卷>-<序号>`**（一般主张）或 **`IC-<卷>-<序号>`**（影响主张，与 CL- 同表共存）；
> ③ **双轨编码警示**：`source_layer`（P41 史料五层级，**1 = 代码产物最强**）与 `evidence_level`（L1–L5，**L5 最强**）方向**相反**——填表与审计时严禁混用（主张库 schema_meta 已登记此约定，06 号验收清单第 5 条将抽查）。

```sql
-- ============================================================
-- 因果链 schema v0.1（设计文本 · 不执行）
-- 依据：用户任务书第九、十六阶段；01-编纂原则清单 P14/P15/P35/P41
-- ============================================================
PRAGMA foreign_keys = ON;

-- ---------- 元信息（对齐全仓三件套惯例） ----------
CREATE TABLE IF NOT EXISTS schema_meta (
    key        TEXT PRIMARY KEY,          -- 如 'schema_version','created_by','scope'
    value      TEXT NOT NULL
);
CREATE TABLE IF NOT EXISTS update_log (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    op          TEXT NOT NULL,            -- 'ddl_draft' / 'review' / ...
    detail      TEXT,
    operator    TEXT,
    created_at  TEXT NOT NULL DEFAULT (datetime('now'))
);

-- ---------- 因果链 ----------
CREATE TABLE IF NOT EXISTS causal_chain (
    chain_id            TEXT PRIMARY KEY,             -- 规范：CC-<卷>-<序号>，如 CC-05-001
    chain_name          TEXT NOT NULL,                -- 如 "DARPA 资助 → BSD 网络能力链"
    thesis              TEXT NOT NULL,                -- 被审计的因果判断原文（一句话）
    origin_chapter_ref  TEXT,                         -- 触发本链的章节引用（卷/章/节）
    origin_claim_ids    TEXT,                         -- JSON 数组：主张库 claim_id（CL-<卷>-<序号> / IC-<卷>-<序号>，06 §4.1）
    chain_scope         TEXT,                         -- '技术'|'组织'|'法律'|'商业'|'文化'|'跨域'（对应五维，问题4）
    cf_required         INTEGER NOT NULL DEFAULT 1,   -- 是否属于须强制反事实检查的重要判断（见 4.4）
    cf_notes            TEXT,                         -- 反事实检查记录，结构见 4.3（JSON）
    hindsight_risk      TEXT NOT NULL DEFAULT 'unchecked'
                        CHECK (hindsight_risk IN
                          ('unchecked','low','medium','high','flagged')),
                        -- flagged = 已检出后见之明倒灌，未完成整改（问题7）
    status              TEXT NOT NULL DEFAULT 'draft'
                        CHECK (status IN ('draft','active','superseded','archived')),
    created_by          TEXT,
    reviewed_by         TEXT,
    created_at          TEXT NOT NULL DEFAULT (datetime('now')),
    updated_at          TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX IF NOT EXISTS idx_chain_status  ON causal_chain(status);
CREATE INDEX IF NOT EXISTS idx_chain_hindsig ON causal_chain(hindsight_risk);

-- ---------- 因果节点（事件/状态） ----------
CREATE TABLE IF NOT EXISTS causal_node (
    node_id      TEXT PRIMARY KEY,        -- 规范：ND-<链序号>-<两位序号>
    chain_id     TEXT NOT NULL REFERENCES causal_chain(chain_id) ON DELETE CASCADE,
    seq_no       INTEGER NOT NULL,        -- 链内全序：1,2,3,...
    node_kind    TEXT NOT NULL CHECK (node_kind IN ('EVENT','STATE')),
    title        TEXT NOT NULL,           -- ≤40 字事件/状态名
    node_summary TEXT,                    -- 描述性快照 ≤150 字，非权威
    summary_is_authoritative INTEGER NOT NULL DEFAULT 0,
    object_ref   TEXT,                    -- 指向主张库/时间线对象的引用串（跨库引用位）
    time_start   TEXT,                    -- ISO 8601；允许 '1969'/'1969-06'/'1969-06/1975-09'
    time_end     TEXT,                    -- EVENT 可与 time_start 相同；STATE 应有起止窗
    time_precision TEXT CHECK (time_precision IN ('year','month','day','range','unknown')),
    created_at   TEXT NOT NULL DEFAULT (datetime('now')),
    updated_at   TEXT NOT NULL DEFAULT (datetime('now')),
    UNIQUE (chain_id, seq_no)
);
CREATE INDEX IF NOT EXISTS idx_node_chain ON causal_node(chain_id, seq_no);
CREATE INDEX IF NOT EXISTS idx_node_obj   ON causal_node(object_ref);

-- ---------- 因果箭头 ----------
CREATE TABLE IF NOT EXISTS causal_arrow (
    arrow_id        TEXT PRIMARY KEY,     -- 规范：AR-<链序号>-<序号>（连接 seq n → n+1）
    chain_id        TEXT NOT NULL REFERENCES causal_chain(chain_id) ON DELETE CASCADE,
    from_seq        INTEGER NOT NULL,
    to_seq          INTEGER NOT NULL,
    mechanism       TEXT,                 -- 机制描述：因如何产生果；可为空（触发 R2）
    mechanism_type  TEXT CHECK (mechanism_type IN
                    ('resource','institutional','personnel','code',
                     'demand','idea','other','unknown')),
    status          TEXT NOT NULL DEFAULT 'INSUFFICIENT_EVIDENCE'
                    CHECK (status IN ('CAUSALITY_ESTABLISHED','CORRELATION_ONLY',
                                      'MECHANISM_PROPOSED','INSUFFICIENT_EVIDENCE','REFUTED')),
    dispute_flag    INTEGER NOT NULL DEFAULT 0,   -- 存在未处置反证时置 1（R5）
    assessed_by     TEXT,
    assessed_at     TEXT,
    created_at      TEXT NOT NULL DEFAULT (datetime('now')),
    updated_at      TEXT NOT NULL DEFAULT (datetime('now')),
    UNIQUE (chain_id, from_seq, to_seq),
    CHECK (to_seq = from_seq + 1),        -- 只允许相邻节点箭头；长程因果必须拆段
    FOREIGN KEY (chain_id, from_seq) REFERENCES causal_node(chain_id, seq_no),
    FOREIGN KEY (chain_id, to_seq)   REFERENCES causal_node(chain_id, seq_no)
);
CREATE INDEX IF NOT EXISTS idx_arrow_status ON causal_arrow(status);

-- ---------- 箭头证据挂接（支撑/反证共用一表，role 区分） ----------
CREATE TABLE IF NOT EXISTS causal_arrow_evidence (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,

                                          -- 等级快照：以主张库/证据等级表为权威，此处冗余存快照便于审计

    disposition_note TEXT,
    search_log_ref  TEXT,                 -- 反证检索留痕引用（"找了没找到"的记录）
    created_at      TEXT NOT NULL DEFAULT (datetime('now')),

);
CREATE INDEX IF NOT EXISTS idx_ae_arrow ON causal_arrow_evidence(arrow_id, role);
CREATE INDEX IF NOT EXISTS idx_ae_evid  ON causal_arrow_evidence(evidence_id);

-- ---------- 替代解释 ----------

    id            INTEGER PRIMARY KEY AUTOINCREMENT,

    assessed_at   TEXT,
    created_at    TEXT NOT NULL DEFAULT (datetime('now')),

-- ---------- 时间一致性 ----------

    verified_at   TEXT,
```

## 1.5 模板示范：DARPA 链的填表示例

> 定位重申：以下示范展示**如何填表**，不是对 DARPA→Unix 网络化因果的历史结论。节点时间为通行说法的占位，实际入库前须按史料五层级核验。

**链**：`CC-01-001`，名称"DARPA 资助 → Unix 网络化链（任务书示例）"，`thesis` = "DARPA 资助最终促成了 Unix 的网络化能力"，`cf_required = 1`（属重要判断），`hindsight_risk` 初值 `unchecked`。

| seq | node_id | 节点（kind） | 时间窗（占位） |
| --- | ------- | ------------ | -------------- |
| 1 | ND-01-01 | DARPA 对网络研究的资助立项（EVENT） | 1969 起 |
| 2 | ND-01-02 | 受资助机构形成研究资源与网络研究需求（STATE） | 1970s |
| 3 | ND-01-03 | Berkeley 开展网络技术研究（STATE） | 1975 起 |
| 4 | ND-01-04 | TCP/IP 在 BSD 中实现（EVENT） | 1977–1983 |
| 5 | ND-01-05 | BSD 具备网络能力（STATE） | 1983 起 |
| 6 | ND-01-06 | Unix 世界网络化（STATE） | 1980s |

**箭头填表要点**（以 AR-01-02“Berkeley 网络研究 → TCP/IP 实现”为例）：

- `mechanism`：CSRG 研究人员承接 DARPA 合同，将 ARPANET 协议栈实现进 BSD（合同与人员是传导体）；`mechanism_type = 'resource' + 'personnel'`（主值取 resource，personnel 在机制描述中注明）。
- 支撑证据：合同文件（L3/L4 级官方文档）、当事人陈述（L4）——`evidence_id` 采用 `EV-<六位序号>` 命名空间（06 §8.2），本示范以 `EV-000000` 系列占位。
- 替代解释（至少一条，满足 R3）："TCP/IP 进入 BSD 是 Internet 协议竞争胜出后的被动移植，而非 Berkeley 主动研究的结果"——`disposition` 初值 `未评估`，评估前该箭头封顶 MECHANISM_PROPOSED。
- 时间一致性：ND-01-03 起始（1975）早于 ND-01-04 起始（1977），`verified = 1`。
- 反事实钩子：链级 `cf_notes` 中必须回答"若无 DARPA 合同，Berkeley 是否仍会实现网络栈"（见第四部分示例）。

**链级状态的自动推出**（视图 `v_chain_readiness`，附录 B）：本示范链 5 个箭头中只要有一个处于 `未评估替代解释` 或 `INSUFFICIENT_EVIDENCE`，整链 `readiness ≠ 'narratable'`，书稿生成器拒绝输出完整因果句。

# 第二部分 影响十二分类体系

## 2.0 总则：原子主张、多类并存、等级门禁

任务书第十阶段规定："禁止笼统说“BSD 影响了 X”，必须拆分为 12 类。" 本体系把它落实为三条硬规则：

1. **原子化**：一条"影响主张"（impact_claim）只能断言**一种**影响类型的一段关系（来源 → 去向）。任何笼统主张（"BSD 影响了 macOS"）在入库时被分解为多条原子主张，或标记为 `UNDECOMPOSED` 并禁止进入书稿。分解动作本身留痕（`parent_claim_id`）。
2. **多类并存**：同一对"来源→去向"可以同时挂多条不同类型的原子主张（事实上重大关系几乎总是多类的）。"可多类"不是允许一条主张选多个类型，而是允许多条主张并存——每条独立举证、独立定级。
3. **等级门禁**：每条原子主张携带证据等级 L1–L5（任务书第二十九阶段），**等级决定允许措辞**（2.3 门禁表）。L1 主张可以入库（作为研究线索），但措辞门禁禁止其以任何继承/影响句式出现在书稿中。

**与因果链的关系**：影响主张是因果链箭头的"候选池"与"已决池"——一段影响主张被采信后，可作为某条因果箭头的支撑证据（`evidence_id` 互指）；反过来，因果链审计中被推翻的箭头，其对应影响主张同步降级。两套表通过 `linked_arrow_id` / `evidence_id` 双向挂接。

**与分离聚合（P14）的关系**：十二分类中的每一类，都可能是"分离中的聚合"的具体载体——分支分离后，代码共享（类 1/2/3）、人员流动（类 9）、文档沿袭（类 10）就是聚合的发生机制。审计影响主张时，`direction` 字段必须允许双向（FreeBSD→OpenBSD 与 OpenBSD→FreeBSD 都是合法主张），防止把聚合写成单向。

## 2.1 十二类影响逐类定义

> 每类给出：**定义 / 判定所需证据 / 典型误用 / 与邻类的边界**。定义中的"来源"指影响的发出方，"去向"指接收方。

### 类型 1：source-code inheritance（源代码继承）

- **定义**：去向系统中存在**逐字或近似逐字**来源于来源系统的代码文件/函数/代码段，且该来源关系可被代码考古证实。这是唯一以"代码物质本身"为对象的影响类型。
- **判定所需证据**：commit/vendor branch/cherry-pick 记录；文件级谱系（同名文件+相同版权头+可追溯的复制事件）；代码 diff 与同源性分析（如 `SCCS/CVS log`、`cvs import` 记录）；许可证声明中保留的原版权文本。理想等级：L5（直接代码来源证据，如 4.4BSD-Lite 源码进入 NetBSD/FreeBSD 初始代码树的 commit 记录）。
- **典型误用**：(a) 把"两个系统各自独立实现了同一功能"（如都有 `ls` 命令）当作代码继承——共同祖先（Unix）导致相似 ≠ 两者之间的继承；(b) 把"重写后功能等价"说成代码继承（重写属于类型 2）；(c) 把共享的第三方代码（如来自 AT&T 的原始 Unix 代码）记作 BSD 之间的相互继承。
- **边界**：与类型 2（technical）的分界是**有无逐字代码存留**——代码被重写、只保留算法，降为类型 2；与类型 3（API）的分界是**对象是代码还是接口签名**——只保留函数名与语义、实现全部替换，属类型 3。

### 类型 2：technical inheritance（技术方案继承）

- **定义**：去向系统采用了来源系统的**具体技术方案**——算法、协议实现方式、数据结构设计、子系统工作机制——但**不要求**逐字代码存留。关键词是"方案的沿袭可被证实"。
- **判定所需证据**：实现之间的强技术对应（同名结构体/同构算法/相同边界处理）+ 至少一条传承路径证据（文档记载、开发者陈述、时间上的先后与接触可能性）。理想等级：L3 以上（技术文档明确说明"本实现参照 X"）。
- **典型误用**：(a) 仅凭"技术对应"而无传承路径证据——这是 L2，只能写"存在技术对应"，不能写"继承"；(b) 把**趋同演化**（面对相同约束的独立解法）当作继承：如多个内核都有类似的缓冲区缓存设计，可能纯属面对相同问题的独立解；(c) 把"共同祖先遗产"当作两者之间的继承（见 3.2 对 POSIX 的处理）。
- **边界**：与类型 1 比，本类不要求逐字代码；与类型 4（architectural）比，本类对象是**具体方案**（一个算法、一个协议栈的实现方式），而架构类对象是**组件划分与组织方式**；与类型 5（design）比，本类必须落到可指认的技术实体，"哲学/原则"层面的归 type 5。

### 类型 3：API inheritance（接口继承）

- **定义**：去向系统保留了来源系统的**编程接口、命令行接口或 ABI**——系统调用集合与语义、库函数签名、ioctl 编号、命令行语法与标志、man 手册结构等。
- **判定所需证据**：接口签名与语义的对应表；man page 的谱系（大量 BSD man page 直接沿用于后代系统，这是 L5 级证据的富矿）；ABI 兼容努力或兼容层（如 Linux 的 BSD 兼容层、macOS 的 POSIX/BSD 系统调用表）；头文件谱系。
- **典型误用**：(a) **标准化倒灌**：某 API 若经由 POSIX/SUS 等标准固化，则后代系统"实现 POSIX"不能自动记为"继承 BSD"——必须追问标准条文的来源史（BSD 实践进入标准，与后代实现标准，是两段独立主张）；(b) 把接口名称的历史巧合当继承；(c) 只证接口相似、未证语义沿袭（同名不同义）。
- **边界**：与类型 1 的分界见上（有无逐字实现）；与类型 2 的分界：接口是**契约**，技术方案是**实现**——"兼容 BSD socket API 但实现全部自研"= 类型 3 成立、类型 2 不成立。

### 类型 4：architectural influence（架构影响）

- **定义**：去向系统的**组件划分、层次结构、子系统组织方式**受到了来源系统的影响——如内核/用户空间边界的划法、设备驱动框架的组织、网络栈的分层方式。
- **判定所需证据**：设计文档中对架构选择的说明与引用；架构同构 + 设计者接触证据（参与过来源系统的人的陈述，L4）；早期架构讨论记录（邮件/RFC）。
- **典型误用**：(a) **功能必然性陷阱**：一切操作系统都需要进程管理、文件系统、网络栈——"都有这些组件"不构成架构影响；架构影响必须指向**划分方式的可选择特征**（为什么这样切分而不是那样）；(b) 把时代通行的架构模式归因于某一个来源。
- **边界**：与类型 2 比，架构是"组件如何组织"，技术方案是"某个组件内部如何做"；与类型 5（design）比，架构可画成框图、可指认组件，设计哲学则表现为原则与取舍偏好。

### 类型 5：design influence(设计影响)

- **定义**：去向系统的设计原则、工程惯例、风格规范受到来源系统影响——如"一切皆文件"的取舍、配置文件的组织惯例、工具组合哲学、"小而锐利"的模块化偏好。
- **判定所需证据**：设计者明确援引来源系统的陈述（L4）；早期文档中的设计理由（design rationale）段落；惯例的谱系（同一惯例在来源系统出现的时间早于去向系统 + 传播路径）。
- **典型误用**：(a) **共同来源陷阱**（本体系最高频错误）：Linux 与 BSD 都体现 Unix 设计哲学，不能据此互认影响——须先证明该哲学要素是经由哪条路径从 Unix/贝尔实验室分别到达两者，还是两者各自独立总结；(b) 把事后总结出的"设计哲学"倒灌为当时的设计动机（P15/问题 7：'简洁'是事后总结，不是当时动机——设计影响主张必须锚定当时的文本，不得用后人总结的哲学作为证据）。
- **边界**：与类型 6（organizational）比，设计影响落在**技术制品**上，组织影响落在**人的协作结构**上；与类型 7（cultural）比，设计影响可通过技术决策指认，文化影响表现为符号、仪式、话语。

### 类型 6：organizational influence（组织影响）

- **定义**：去向项目的**治理结构、组织形式、发布流程、维护制度**借鉴了来源项目——如 core team 制、committer 权限模型、发布工程流程、基金会形态。
- **判定所需证据**：治理文件的谱系（章程、handbook 的参照关系）；组织创立者的陈述（L4）；制度要素的时序与接触证据。
- **典型误用**：(a) **独立起源陷阱**：多个项目独立演化出相似治理（核心小组+外围贡献者）是常见现象，相似不等于借鉴；(b) 把人员流动本身当组织影响——某人加入是载体（类型 9），他是否实际移植了组织模式须另行证明。
- **边界**：与类型 9（personnel）的关系：人员是组织影响的**常见载体**，但主张必须分开立条——"某人从 A 到 B"（类型 9，易证）与"B 的治理因此仿 A"（类型 6，难证）是两条主张，禁止合并。

### 类型 7：cultural influence（文化影响）

- **定义**：去向社区的**符号、仪式、话语、身份认同、社区惯例**来源于来源社区——如恶魔吉祥物（Beastie/daemon 谱系）、术语（port、hack 的特定用法）、发布命名传统、社区幽默。
- **判定所需证据**：符号的谱系记录（图像源文件、首次使用记录、衍生记录）；社区文档与仪式的沿袭证据；当事人的指认（L4）。
- **典型误用**：(a) 把**泛黑客文化共有元素**（如"RTFM"、愚人节玩笑传统）记作某一 BSD 分支的独特影响；(b) 浪漫化表述（P26/总纲 15 禁止）——文化影响条目必须具体到"哪个符号/惯例、何时、由谁、经何种重复传播"，不得写"BSD 社区的精神感染了 X"；(c) 把文化相似当作影响，忽略独立起源与第三方共同来源。
- **边界**：与类型 5（design）比：惯例若直接约束技术决策（如"新工具必须配 man page"在工程流程中被执行）可同时构成两类，须分立两条主张分别举证。

### 类型 8：licensing influence（许可证影响）

- **定义**：去向项目/产品的**许可证选择、许可证文本、合规实践**受到来源影响——BSD 许可证文本的沿用与变体、宽松许可传统的传播、许可证兼容性决策。
- **判定所需证据**：许可证文本 diff 与谱系；许可证选择过程的记录（邮件讨论、法律备忘录）；当事人/法务的陈述（L4）。
- **典型误用**：(a) **理念化还原**（总纲 13 明令禁止）：不得把许可证史写成"自由理念的冲突/感召"——许可证影响主张必须落到**文本、决策记录与利益流向**，不落到理念叙事；(b) 把"采用了宽松许可证"自动记作"受 BSD 影响"——MIT/X11/Apache 各有谱系，须分别溯源；(c) 把许可证的**商业后果**（闭源采用）写成本类——那是类型 11。
- **边界**：本类只管"许可证本身"的传播与选择；因许可证宽松而诱发的商业采用、代码分叉行为，分别归类型 11、类型 1。

### 类型 9：personnel transfer（人员转移）

- **定义**：**人**从来源社区/机构流动到去向项目/机构，构成影响的载体。本类主张只断言"流动发生 + 流动者携带了来源系统的经验"，是十二类中唯一以"人"为直接对象的类型。
- **判定所需证据**：任职/参与记录（雇佣记录、commit author 历史、邮件列表参与史、简历与自述）；流动时序（先参与来源，后参与去向）。理想等级：L4/L5（人事记录+本人 commit 历史）。
- **典型误用**：(a) **载体内容混淆**：只证明了"此人从 A 到 B"，就断言"B 因此获得了 A 的代码/技术/组织"——流动是载体，携带了什么内容必须另立对应类型的主张分别举证；(b) 把"此人当时用过 A"当作转移——须证明在 B 的工作实际动用了 A 的经验；(c) 神化个体（P20 禁止天才叙事）——人员转移条目写具体行动，不写"天才带去了火种"。
- **边界**：本类与其余所有类型正交：人是载体，代码/技术/组织/文化是内容。一条完整的"人员传导影响"在本体系中永远是 ≥2 条主张（一条类型 9 + ≥1 条内容类型）。

### 类型 10：academic influence（学术影响）

- **定义**：来源系统经由**论文、教材、课程、学术引用、学位论文**影响去向系统的设计者或技术选择。
- **判定所需证据**：引用记录（去向系统的文档/论文/设计笔记引用了关于来源系统的学术文献）；课程与教材谱系（如 CSRG 技术报告、BSD 相关论文的阅读史）；设计者的学术背景记录。
- **典型误用**：(a) 把"引用了一篇 Unix 书"当作"受 BSD 影响"——须核验被引对象是否确为 BSD 特有内容（大量 Unix 文献与 BSD 无专属关系）；(b) 把时代通行的学术常识归因于单一来源；(c) 以回忆性访谈（第四层史料）中的"我读过 X"单独定案——须配当时文本佐证（P41）。
- **边界**：与类型 5（design）的分界在**证据形态**：同一设计原则的传承，若证据是学术引用链归本类，若证据是工程文档与代码惯例归类型 5。

### 类型 11：commercial influence（商业影响）

- **定义**：来源系统影响了去向方的**商业产品、商业策略、市场行为**——商业公司对 BSD 的采用、基于 BSD 的产品线、围绕 BSD 的商业模式。
- **判定所需证据**：公司记录（产品文档、采购/许可合同、财报与公告）；商业决策过程记录；当事人陈述。
- **典型误用**：(a) **技术优秀论倒灌**（§3.1.5/P24 禁止）：不得把商业采用写成"BSD 技术优秀的结果"——商业影响条目只记录**采用事实、利益流向、决策记录**，不评价技术优劣因果；(b) 把商业公司**事后**的品牌叙事（"我们的产品源自 BSD"的营销话术）当作当时证据——营销材料属第四、五层史料，须降级对待；(c) 混淆"采用 BSD 代码"（类型 1）与"采用 BSD 作为商业基础"（本类）——前者要代码证据，后者要商业记录，常常只有一者成立。
- **边界**：与类型 1 的分界：商业产品可能只用 BSD 的名字/血统营销而无代码继承；与类型 8 的分界：选择 BSD 许可证是类型 8，因许可证宽松而得以闭源获利是类型 11。

### 类型 12：indirect influence（间接影响）

- **定义**：影响不直接发生于来源→去向之间，而经由**明确的中介环节**（来源→中介→去向），或来源塑造了去向得以出现的环境条件。
- **判定所需证据**：间接影响主张**必须分解为多段直接影响主张**（每段属于类型 1–11 之一）并逐段举证；若任何一段无法举证，整条间接主张降级为 `INSUFFICIENT_EVIDENCE`。
- **典型误用**：(a) **垃圾筐陷阱**（本类型最大风险）：把无法直接证明的影响塞进"间接影响"以规避举证——本体系明令禁止：类型 12 不是弱证据的收容所，而是"多段强证据的组合"；(b) 无限拉长中介链（"BSD 影响了互联网，互联网影响了 X，所以 BSD 影响了 X"）——中介超过两段时必须单独立项审查每段的实质传导；(c) 把"时间上在先"当作"间接影响"。
- **边界**：与其余十一类的关系是**组合关系而非并列实质**——类型 12 的每条记录必须引用 ≥2 条类型 1–11 的原子主张作为其段（`segment_claim_ids`）。不满足此结构约束的类型 12 记录视为无效。

## 2.2 影响主张记录模板

> 以下为单条"影响主张"的著录模板（书稿编纂与核查用人类可读形态）；落库 DDL 见 2.4。带 ★ 的字段为必填。

```
【影响主张记录】 claim_id: IC-<卷>-<序号>
★ 主张文本     ：一句话原子主张，格式 "<来源> 经由 <中介载体> 在 <类型> 上影响了 <去向>"
                 （禁止笼统形式："BSD 影响了 X"）
★ 影响类型     ：十二类之一（一条记录只许一类；多类 = 多条记录）
★ 来源（source）：发出方，指向主张库对象（项目/分支/机构/个人/文档）
★ 去向（target）：接收方，同上
★ 时间窗       ：来源具备该影响要素的时间窗 + 去向接收的时间窗；
                 约束：来源时间窗起点必须早于去向接收起点（违反即红旗）
★ 中介载体     ：代码 / 人员 / 文档 / 组织（任务书规定四选一；可多选但须逐一指明）
★ 证据等级     ：L5 直接代码来源证据 / L4 作者开发者明确陈述 / L3 技术文档论文明确说明 /
                 L2 强技术对应但缺直接证明 / L1 仅历史相关性相似性
★ 证据 ID 列表 ：引用主张库/史料库的证据对象（每条附史料层级 1-5 快照，P41）
  反证 ID 列表 ：无则填"已检索，未见反证（附检索记录引用）"——不许留空
  替代解释     ：与来源无关的竞争性说明（共同祖先/趋同/第三方来源），至少评估一条
  关联因果箭头 ：linked_arrow_id（若本主张服务于某条因果链箭头）
  状态         ：proposed / supported / contested / refuted
  措辞核查     ：本条主张在书稿中允许使用的措辞档位（见 2.3 门禁表）
  登记/复核    ：created_by / reviewed_by / 时间戳
```

## 2.3 证据等级与允许措辞门禁表

任务书第二十九阶段五级证据，与本体系措辞门禁的绑定（**L1 不得写成"X 继承了 BSD"是硬禁令**）：

| 等级 | 证据性质 | 允许的措辞档位 | 禁止措辞 |
| ---- | -------- | -------------- | -------- |
| L5 直接代码来源证据 | commit/vendor 记录、代码谱系、版权头链 | "X 中包含来自 BSD 的代码（文件 F，commit C）"；可写**继承** | 不得扩大到代码之外的类型（类型 5/6/7 另证） |
| L4 作者开发者明确陈述 | 当事人的邮件、访谈、自述（注意第四层史料性：须尽量配当时文本，P41） | "据 X 本人陈述……"；可写**影响**，须带归源限定 | 不得写"必然""注定" |
| L3 技术文档论文明确说明 | 官方文档、设计文档、论文中的明确记载 | "文档 D 记载……"；可写**影响** | 同上 |
| L2 强技术对应但缺直接证明 | 实现高度同构但无传承路径证据 | **只许**"存在强技术对应，传承路径待证" | 禁止"继承/影响/源自/借鉴" |
| L1 仅历史相关性相似性 | 时序相伴、表面相似、共同祖先遗产 | **只许**"A 与 B 在时间上相伴/表面相似/共享共同祖先" | **禁止一切**"继承/影响/源自/借鉴/抄自"；书稿中只能以相关性句式或存疑脚注出现 |

**升级路径**：L1/L2 主张是合法的研究线索（入库、列入研究问题清单），其存在本身不构成书稿违规；违规只发生于**措辞越档**。审计视图（附录 B）按等级扫描措辞越档。

## 2.4 影响主张落库 DDL

> **整合裁决（已定，06 §4.1，2026-08-12）**：以下 `impact_claim` 表**不再单独建表**——影响主张改以主张库 claim 表的 `claim_type='INFLUENCE_CLAIM'` + `impact_subtype`（十二分类枚举）落同一张 claim 表，IC- 前缀与 CL- 同表共存。理由：claim_id 命名空间统一；claim_evidence/claim_entity/claim_period/claim_relation 四张关系表免建第二套；措辞门禁与审计视图一次覆盖。字段 1:1 映射（impact_type→impact_subtype、source_ref/target_ref→claim_entity 的 source/object 角色、carriers→attrs JSON、linked_arrow_id/parent_claim_id/segment_claim_ids 同名保留或 JSON）见 06 §4.1。本节 DDL **保留为过渡设计文本**，其字段定义与措辞门禁规则继续有效；causal_arrow 侧的 `linked_arrow_id` 引用方向不变（claim → 箭头）。

```sql
-- ============================================================
-- 影响主张 schema v0.1（设计文本 · 不执行；已按 06 §4.1 整合入主张库 claim 表）
-- 依据：用户任务书第十、二十九阶段
-- ============================================================

CREATE TABLE IF NOT EXISTS impact_claim (
    claim_id        TEXT PRIMARY KEY,      -- 规范：IC-<卷>-<序号>
    claim_text      TEXT NOT NULL,         -- 原子主张文本（禁笼统式）
    impact_type     TEXT NOT NULL CHECK (impact_type IN (
                        'source_code','technical','api','architectural','design',
                        'organizational','cultural','licensing','personnel',
                        'academic','commercial','indirect')),
    source_ref      TEXT NOT NULL,         -- 来源：指向主张库对象
    target_ref      TEXT NOT NULL,         -- 去向：指向主张库对象
    time_window_src TEXT,                  -- 来源侧时间窗（ISO 区间）
    time_window_tgt TEXT,                  -- 去向侧时间窗
    carriers        TEXT NOT NULL,         -- JSON 数组：["code","personnel","document","organization"]
    evidence_level  TEXT NOT NULL CHECK (evidence_level IN ('L1','L2','L3','L4','L5')),
    status          TEXT NOT NULL DEFAULT 'proposed'
                    CHECK (status IN ('proposed','supported','contested','refuted')),
    linked_arrow_id TEXT REFERENCES causal_arrow(arrow_id),   -- 服务于哪条因果箭头（可空）
    parent_claim_id TEXT REFERENCES impact_claim(claim_id),   -- 分解溯源：笼统主张的分解留痕
    segment_claim_ids TEXT,                -- 仅 indirect 类用：JSON 数组，引用 ≥2 条类型 1-11 主张
    wording_gate    TEXT,                  -- 措辞档位快照（与 evidence_level 联动，2.3）
    created_by      TEXT,
    reviewed_by     TEXT,
    created_at      TEXT NOT NULL DEFAULT (datetime('now')),
    updated_at      TEXT NOT NULL DEFAULT (datetime('now')),
    -- 结构约束：indirect 必须给 segment_claim_ids；其余类型不允许给
    CHECK ( (impact_type = 'indirect' AND segment_claim_ids IS NOT NULL)
         OR (impact_type <> 'indirect') )
);
CREATE INDEX IF NOT EXISTS idx_ic_type   ON impact_claim(impact_type);
CREATE INDEX IF NOT EXISTS idx_ic_level  ON impact_claim(evidence_level);
CREATE INDEX IF NOT EXISTS idx_ic_src    ON impact_claim(source_ref);
CREATE INDEX IF NOT EXISTS idx_ic_tgt    ON impact_claim(target_ref);

-- 影响主张的证据挂接（复用因果箭头的证据挂接模式）
CREATE TABLE IF NOT EXISTS impact_claim_evidence (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    claim_id       TEXT NOT NULL REFERENCES impact_claim(claim_id) ON DELETE CASCADE,
    role           TEXT NOT NULL CHECK (role IN ('supporting','contradicting')),
    evidence_id    TEXT NOT NULL,
    evidence_level TEXT CHECK (evidence_level IN ('L1','L2','L3','L4','L5')),
    source_layer   INTEGER CHECK (source_layer BETWEEN 1 AND 5),
    citation_detail TEXT,
    disposition    TEXT,                  -- 反证处置，同因果箭头
    search_log_ref TEXT,
    created_at     TEXT NOT NULL DEFAULT (datetime('now')),
    UNIQUE (claim_id, role, evidence_id)
);

-- 影响主张的替代解释（共同祖先/趋同/第三方来源）
CREATE TABLE IF NOT EXISTS impact_claim_alternative (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    claim_id      TEXT NOT NULL REFERENCES impact_claim(claim_id) ON DELETE CASCADE,
    alternative   TEXT NOT NULL,          -- 如 "共同祖先 Unix 所致，非两者间影响"
    evidence_ids  TEXT,
    disposition   TEXT NOT NULL DEFAULT '未评估'
                  CHECK (disposition IN ('未评估','已排除','并存','升格为主解释')),
    disposition_note TEXT,
    created_at    TEXT NOT NULL DEFAULT (datetime('now'))
);

-- 时间一致性（影响方向的时间约束：来源须早于去向接收）
CREATE TABLE IF NOT EXISTS impact_claim_temporal (
    claim_id      TEXT PRIMARY KEY REFERENCES impact_claim(claim_id) ON DELETE CASCADE,
    constraint_txt TEXT NOT NULL,
    verified      INTEGER,               -- NULL=未核验；0=违反；1=通过
    violation_note TEXT
);
```

# 第三部分 双示范链拆解模板

## 3.0 使用说明：这是研究问题清单，不是答案

任务书第十一阶段要求：BSD→macOS 不能只写"macOS 基于 BSD"，BSD→Linux 不能因"都用 Unix/POSIX 思想"就自动认定影响，必须分别研究具体机制。本部分给出两条示范链按十二分类展开的**研究问题清单**：

1. **只列问题，不给答案。** 本次重构不撰写正文；每个问题标注"应产出的证据形态"，供后续研究与史料建设排期。
2. **每个问题可转化为一条或多条影响主张**（第二部分模板）或因果链箭头（第一部分）。问题编号即为未来主张的占位符（如 `Q-MAC-01`）。
3. **中介者优先。** 两条链都不是二元直达关系：BSD→macOS 之间存在 Mach、NeXTSTEP、Darwin 三个中介环节；BSD→Linux 之间存在 Unix 共同祖先、MINIX、POSIX 标准等共因/中介。按任务书要求，问题清单**首先按中介环节组织**，再按十二类展开。
4. **陷阱标注**：凡容易产出 L1 答案、或流行说法会直接污染的问题，标 ⚠ 并注明陷阱类型（共同祖先陷阱 / 标准化倒灌 / 功能必然性 / 营销话术 / 事后回忆）。

## 3.1 BSD→macOS：按十二类逐类研究问题

> 任务书点名的分解维度：BSD 代码、Mach、NeXTSTEP、Darwin、与 FreeBSD/NetBSD/OpenBSD 等分支的具体技术关系、用户空间、网络栈、工具链、许可证、人员、组织关系。以下 12 组问题全覆盖这些维度。

### 3.1.1 源代码继承（类型 1）

- **Q-MAC-01**：Darwin/macOS 中现存多少可追溯至 4.4BSD/4.4BSD-Lite 的逐字代码？文件清单、版权头链、进入 Darwin 代码树的 commit/同步记录在哪里？（应产出：代码谱系报告，L5 级）
- **Q-MAC-02**：Apple 从 FreeBSD/NetBSD/OpenBSD 各自取用过哪些代码？三个分支的取用是否可区分（各自的版权头与同步记录）？（应产出：按分支分列的取用清单，L5/L4 级）⚠ 营销话术陷阱：Apple 官方声明中的"based on BSD"不得代替逐文件证据。
- **Q-MAC-03**：BSD 代码进入的路径是直接取用，还是经由 NeXTSTEP 阶段累积？NeXT 时期的 BSD 代码存留记录是什么？（应产出：NeXT/OPENSTEP 发行版的代码谱系）
- **Q-MAC-04**：被取用的 BSD 代码在后续版本中是否被逐段替换或重写？现存 BSD 来源代码的占比变化曲线如何？（应产出：跨版本 diff 审计；⚠ 注意区分"仍在树上"与"已被重写"）

### 3.1.2 技术方案继承（类型 2）

- **Q-MAC-05**：macOS/Darwin 的 TCP/IP 网络栈与 4.4BSD 网络栈的技术对应关系如何？哪些子系统（socket 实现、路由、防火墙机制）保留了 BSD 方案，哪些已替换？（应产出：子系统级对照表 + 传承路径证据，目标 L3+）
- **Q-MAC-06**：BSD 内核方案（进程模型、VFS 层、设备驱动模型）在 XNU 内核的 BSD 层中保留了哪些？与 Mach 层的分工边界如何形成？（⚠ 功能必然性陷阱：只问"可选择的划分方式"，不问"是否都有内核"）
- **Q-MAC-07**：工具链（编译器、链接器、调试器、构建系统）中哪些 BSD 方案被保留？从 BSD make 到后续构建体系的谱系是什么？

### 3.1.3 接口继承（类型 3）

- **Q-MAC-08**：macOS 系统调用表中 BSD 来源的系统调用集合与语义沿袭情况？（应产出：系统调用谱系表，L5 级可行）
- **Q-MAC-09**：用户空间命令行工具的 BSD 血统：哪些工具是 BSD 版本的直接沿用（含 man page 谱系），哪些被 GNU 版本替代后又部分回摆？（⚠ 标准化倒灌：属 POSIX 标准要求的接口不得自动记为 BSD 继承，须查标准条文来源史）
- **Q-MAC-10**：man page 的 BSD 谱系覆盖率是多少？版权头中的 BSD 归属记录？（man page 属第一层史料，是 L5 级证据富矿）

### 3.1.4 架构影响（类型 4）

- **Q-MAC-11**：XNU 的"Mach 微内核 + BSD 层"混合架构是如何形成的？BSD 层承担了哪些职责，该职责划分的设计记录在哪里？（中介环节：Mach 源自 CMU，其 BSD 关系须单独成链审计）
- **Q-MAC-12**：NeXTSTEP 的架构决策（显示服务、对象框架、内核选择）中，哪些决策记录显示了对 BSD 方案的取舍？
- **Q-MAC-13**：从 NeXTSTEP/OPENSTEP 到 Rhapsody 到 Mac OS X 到 macOS 的架构变迁中，BSD 成分的架构地位如何变化（边缘兼容层 → 用户空间基座）？每次变化的决策记录？

### 3.1.5 设计影响（类型 5）

- **Q-MAC-14**：Darwin 用户空间的设计惯例（目录结构、配置文件组织、工具组合方式）与 BSD 惯例的对应与偏离？（⚠ 共同来源陷阱：须区分"BSD 独有惯例"与"Unix 通行惯例"）
- **Q-MAC-15**：macOS 的 Unix 认证与 POSIX 符合性努力中，BSD 设计实践的角色是什么？（⚠ 标准化倒灌）

# 第四部分 反事实检查接口

## 4.1 定位：总纲 5 与第十六阶段的制度化

本部分把三处上游规定焊接成一个可执行的字段系统：

1. **总纲 5（P15）**："标注'假如条件 A 不成立，事件会如何发展'——不是为了证明'必然'，而是为了揭示'偶然'"；研究必须**枚举关键节点的偶然条件**。
2. **P37 映射表**："偶然性 → 反事实呈现 → 在关键节点标注'假如不'的条件"——反事实是七组官方叙事策略之一，不是可选项。
3. **任务书第十六阶段**：对重要历史判断**自动提出**四个问题——"如果 A 没有发生，B 是否仍可能发生 / 是否存在替代路径 / 是否存在多个共同原因 / 当时的人是否知道未来结果"。

设计决策：**反事实检查不做成一张游离的备注表，而是因果链 schema 的强制组件**——每条链有链级 `cf_notes` 与 `hindsight_risk`（DDL 见 1.4），另有逐问题登记表 `causal_counterfactual`（DDL 见 4.7）。"自动提出"的含义是：只要一条链被标记 `cf_required = 1`，系统即视四个问题为**待回答义务**，未回答状态会以视图红旗形式出现在审计面板（附录 B），而不是等人记得去填。

**反事实检查在本书中的认识论边界**（必须写死，防止工具被反向使用）：反事实回答**永远不得**被用来升级为必然性结论（"看，没有 A 就没有 B，所以 A 必然导致 B"违反总纲 5 与 T2 事件层禁令）；它的合法产出只有两种——**偶然性标注**（书稿出口的偶然性脚注）与**降格建议**（发现替代路径/共同原因后，建议把箭头降级）。

## 4.2 四个自动提问的形式化

| 问题代号 | 任务书原文 | 形式化 | 合法产出 |
| -------- | ---------- | ------ | -------- |
| Q1 `without_a` | "如果 A 没有发生，B 是否仍可能发生" | 对链上每条 ESTABLISHED/CORRELATION 箭头：去除 from 节点后，to 节点是否有其他已知前件支撑？ | 偶然条件清单；若发现其他支撑 → 该箭头只是**充分条件之一**，书稿措辞必须写"之一" |
| Q2 `alternative_paths` | "是否存在替代路径" | 枚举 from→to 之间不经过本箭头机制的已知路径（人物、机构、技术替代方案） | 每条替代路径作为候选箭头登记或作为替代解释挂接（第二部分替代解释表） |
| Q3 `common_causes` | "是否存在多个共同原因" | 检查 from 与 to 是否共享上游原因 C（C→A 且 C→B），即混杂结构 | 发现共因 → 箭头降格建议（混杂未排除前最高 CORRELATION_ONLY）；共因本身登记为新的因果链候选 |
| Q4 `contemporary_awareness` | "当时的人是否知道未来结果" | 逐节点核验：该节点时间窗内的当事人文本中是否出现对后续节点的预期？ | hindsight_risk 评级依据；**只允许第一、二层史料**（当时文本）作为"当时知道/不知道"的证据（规则 R9） |

**Q4 的特殊地位**：它是"后见之明倒灌"检测器（问题 7：成功/简洁/新纪元/远见卓识等十类概念不得倒灌）。一条链若大量依赖"当时的人就知道这很重要"的叙事，而该判断只能从第四五层事后史料中找到，则该链 `hindsight_risk` 必须升为 `high` 乃至 `flagged`。

## 4.3 字段挂接：counterfactual_notes 与 hindsight_risk

**链级字段**（已在 1.4 DDL 中定义，此处给出 `cf_notes` 的 JSON 结构约定）：

```json
{
  "cf_required": true,
  "questions": [
    {
      "qid": "Q1_without_a",
      "target_arrow_id": "AR-01-02",
      "answer": "若 CSRG 未获 DARPA 合同，Berkeley 仍可能经由 …… 路径接触网络研究，但时序与深度存疑",
      "answer_status": "documented",
      "evidence_ids": ["EV-000000"],
      "permitted_source_layers": [1, 2]
    },
    { "qid": "Q2_alternative_paths", "...": "..." },
    { "qid": "Q3_common_causes", "...": "..." },
    { "qid": "Q4_contemporary_awareness", "...": "..." }
  ],
  "contingent_conditions": [
    "DARPA 恰好选择资助网络互联而非其他方向",
    "Berkeley 恰好具备承接合同的人员结构"
  ],
  "downgrade_suggestions": [
    { "arrow_id": "AR-01-02", "from_status": "CAUSALITY_ESTABLISHED",
      "to_status": "MECHANISM_PROPOSED", "reason": "发现替代路径未排除" }
  ],
  "hindsight_sources_excluded": ["事后回忆录 X（第四层，不得用于 Q4 判定）"]
}
```

要点：

- `contingent_conditions` 是 P15"枚举关键节点的偶然条件"的直接落库位——每条链的偶然条件清单最终从这里生成书稿的偶然性脚注（4.6）。
- `downgrade_suggestions` 是**建议**而非自动执行：反事实检查发现问题后提出降级建议，实际降级须走 1.3 的状态变更流程并留 `status_log` 痕迹（防止反事实检查被滥用为随意降级工具）。
- `permitted_source_layers`：Q4 的判定证据被 schema 约定限制在第一、二层（规则 R9）。

**`hindsight_risk` 五级**（已在 DDL）：`unchecked`（未检）/ `low`（未发现倒灌）/ `medium`（存在事后史料参与但非关键证据）/ `high`（关键证据依赖事后叙述）/ `flagged`（已确认倒灌，整改中）。评级规则：链内任一箭头的关键证据为第四五层且无低层佐证 → 至少 `medium`；链的 thesis 本身使用了问题 7 十类倒灌概念之一 → 直接 `high` 起步并进入整改队列。

## 4.4 触发规则：何时必须做反事实检查

`cf_required = 1` 的自动判定标准（满足任一即触发）：

1. **叙事枢纽**：链被任何卷/章的"核心叙事线"引用（`origin_chapter_ref` 指向章概述的核心叙事线字段）；
2. **强状态箭头**：链内出现任一 `CAUSALITY_ESTABLISHED` 箭头——**因果越被采信，越必须揭示其偶然**（这是本体系的核心对称性：证据强度与反事实义务成正比）；
3. **遗产/影响句**：链支撑书稿五段式第 5 段"遗产"段或任何影响主张（第二部分的 linked_arrow_id 关联）；
4. **关键节点所在链**：链内节点被标记为章级"关键节点"（标准 4 要求每章 2 个以上关键节点有偶然性脚注——脚注必须有字段支撑，不能凭空写）。

不满足任何一条的链可暂免（`cf_required = 0`），但一旦后续满足即自动进入义务队列（视图监控，附录 B）。

## 4.5 与箭头状态的交互规则（审计规则 R6–R9）

接续 1.3 的 R1–R5：

- **R6（反事实先于叙事）**：`cf_required = 1` 的链，若四个问题中任一 `answer_status = 'unasked'`，链级 `readiness ≠ 'narratable'`——书稿生成器不得引用该链输出因果句或遗产段。反事实检查不是写完之后的点缀，而是叙事许可的前置条件。
- **R7（倒灌一票否决）**：`hindsight_risk = 'flagged'` 的链，其全部箭头在书稿中冻结引用（数据库状态不变，但出口禁写），直至整改完成、复核留痕后解除。整改动作 = 用第一、二层史料重证关键证据，或把依赖事后叙述的主张降级。
- **R8（共因降格）**：Q3 发现未排除的共同原因时，相关箭头强制封顶 `CORRELATION_ONLY`，直到共因被作为替代解释处置（`disposition != '未评估'`）。这是把"混杂排除"从统计直觉翻译成本 schema 的硬约束。
- **R9（当时性证据限定）**：Q4（contemporary_awareness）的证据 `source_layer` 必须 ∈ {1, 2}；违反即该回答无效（`answer_status` 回退 `unasked`）。事后史料可以用来**提出问题**（"某某后来回忆说当时大家就知道……"），不可以用来**回答**"当时的人是否知道"。

## 4.6 书稿出口：偶然性脚注的字段支撑

P48 规定五段式第 6 段"偶然性反事实"（可选）与标准 4（≥2 个偶然性脚注/章）。本 schema 与书稿出口的映射：

| 书稿装置 | 字段来源 | 生成规则 |
| -------- | -------- | -------- |
| 偶然性脚注（"假如条件 A 不成立……"） | `cf_notes.contingent_conditions` + Q1/Q2 回答 | 每个关键节点取该节点所在箭头的偶然条件，按脚注模板生成；脚注必须可回溯到具体 chain_id/question 记录 |
| "遗产"段的非必然化表述 | `cf_notes` + 链级状态视图 | 遗产段禁止"注定影响深远"句式；生成器仅允许引用 `readiness = narratable` 且反事实完整的链 |
| 争议并置（反证成立的箭头） | `status = REFUTED` 的箭头 + 状态日志 | REFUTED 箭头生成"曾有……说法，现被……反证推翻"的破除型段落（P34：裂缝保留） |
| 后见之明警示 | `hindsight_risk ∈ {high, flagged}` | 相关章节审核警告区（章末合法结构成分）列出倒灌风险点 |

**示范（DARPA 链的偶然性脚注出口样例，模板演示非结论）**：
> 〔偶然性注〕若 DARPA 当年未将资助方向定为网络互联（条件：1970 年代初 ARPA 研究主题尚有多种可能，见 cf_notes.Q1），Berkeley 的网络研究时序或将不同——本链第 2、3 段箭头所依据的合同记录并不能排除这一替代路径。

## 4.7 反事实检查 DDL（第一部分 DDL 的扩展）

```sql
-- ============================================================
-- 反事实检查 schema v0.1（设计文本 · 不执行；causal_graph 扩展表）
-- 依据：用户任务书第十六阶段；01-编纂原则清单 P15/P37/P48；问题 7
-- ============================================================

CREATE TABLE IF NOT EXISTS causal_counterfactual (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    chain_id       TEXT NOT NULL REFERENCES causal_chain(chain_id) ON DELETE CASCADE,
    arrow_id       TEXT REFERENCES causal_arrow(arrow_id) ON DELETE CASCADE,
                   -- NULL = 链级问题；非 NULL = 针对特定箭头的问题
                   -- （注：SQLite UNIQUE 视 NULL 为互异，链级多题靠 question_kind 区分）
    question_kind  TEXT NOT NULL CHECK (question_kind IN
                   ('without_a','alternative_paths','common_causes','contemporary_awareness')),
    question_text  TEXT NOT NULL,          -- 实例化后的问题文本（含具体节点名）
    answer         TEXT,
    answer_status  TEXT NOT NULL DEFAULT 'unasked'
                   CHECK (answer_status IN ('unasked','in_progress','documented','unanswerable')),
                   -- unanswerable = 已尽力检索、确无史料可答（信息黑洞，P34：标注而非填充）
    evidence_ids   TEXT,                   -- JSON 数组；Q4 限定第一二层史料（R9，由视图校验）
    contingent_conditions TEXT,            -- JSON 数组：本问题揭示的偶然条件
    downgrade_suggestion TEXT,             -- JSON：{arrow_id, from_status, to_status, reason}（建议，非执行）
    reviewed_by    TEXT,
    reviewed_at    TEXT,
    created_at     TEXT NOT NULL DEFAULT (datetime('now')),
    updated_at     TEXT NOT NULL DEFAULT (datetime('now')),
    UNIQUE (chain_id, arrow_id, question_kind)
);
CREATE INDEX IF NOT EXISTS idx_cc_chain  ON causal_counterfactual(chain_id);
CREATE INDEX IF NOT EXISTS idx_cc_status ON causal_counterfactual(answer_status);
```

# 附录 B 审计查询示例（SQL 视图）

> 设计文本，与 DDL 同属未执行状态。

```sql
-- B1：链级叙事许可（readiness）——任一箭头非 ESTABLISHED 或有未处置反证，
--     或反事实未完整（cf_required=1 且存在 unasked），即不可叙事
CREATE VIEW IF NOT EXISTS v_chain_readiness AS
SELECT c.chain_id,
       c.chain_name,
       c.hindsight_risk,
       CASE WHEN NOT EXISTS (SELECT 1 FROM causal_arrow a
                              WHERE a.chain_id = c.chain_id
                                AND a.status <> 'CAUSALITY_ESTABLISHED')
                 AND NOT EXISTS (SELECT 1 FROM causal_arrow a2
                                  JOIN causal_arrow_evidence e ON e.arrow_id = a2.arrow_id
                                  WHERE a2.chain_id = c.chain_id
                                    AND e.role = 'contradicting' AND e.disposition IS NULL)
                 AND (c.cf_required = 0
                      OR NOT EXISTS (SELECT 1 FROM causal_counterfactual cc
                                     WHERE cc.chain_id = c.chain_id
                                       AND cc.answer_status = 'unasked'))
            THEN 'narratable' ELSE 'blocked' END AS readiness
FROM causal_chain c;

-- B2：措辞门禁违规扫描——L1/L2 影响主张若进入 supported 状态即为红旗
CREATE VIEW IF NOT EXISTS v_wording_gate_violation AS
SELECT claim_id, claim_text, evidence_level, status
FROM impact_claim
WHERE evidence_level IN ('L1','L2') AND status IN ('supported');

-- B3：时间一致性红旗——未核验或违反的箭头/主张
CREATE VIEW IF NOT EXISTS v_temporal_flags AS
SELECT 'arrow' AS kind, a.arrow_id AS id, t.verified
FROM causal_arrow_temporal t JOIN causal_arrow a ON a.arrow_id = t.arrow_id
WHERE t.verified IS NULL OR t.verified = 0
UNION ALL
SELECT 'claim', ic.claim_id, it.verified
FROM impact_claim_temporal it JOIN impact_claim ic ON ic.claim_id = it.claim_id
WHERE it.verified IS NULL OR it.verified = 0;

-- B4：反事实义务欠账——cf_required=1 但有问题未问/未答的链
CREATE VIEW IF NOT EXISTS v_cf_overdue AS
SELECT c.chain_id, c.chain_name,
       COUNT(cc.id) FILTER (WHERE cc.answer_status IN ('unasked','in_progress')) AS open_questions
FROM causal_chain c
LEFT JOIN causal_counterfactual cc ON cc.chain_id = c.chain_id
WHERE c.cf_required = 1
GROUP BY c.chain_id, c.chain_name
HAVING open_questions > 0;

-- B5：indirect 类主张结构完整性——段引用不足 2 条即无效（由 CHECK 之外再审计引用真实性）
CREATE VIEW IF NOT EXISTS v_indirect_integrity AS
SELECT claim_id, segment_claim_ids
FROM impact_claim
WHERE impact_type = 'indirect'
  AND (segment_claim_ids IS NULL OR segment_claim_ids = '' OR segment_claim_ids = '[]');
```
