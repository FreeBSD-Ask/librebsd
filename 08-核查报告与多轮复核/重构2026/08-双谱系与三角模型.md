## 0. 设计总纲：为什么需要"双谱系 + 三角"

### 0.1 原则锚定

〔原文〕总纲 8 编纂指令："不预设任何 BSD 分支的优越地位。"＋"不使用'主流/支流''正统/旁支'等隐含等级制的表述"（标准 5）。
〔原文〕§3.1.7/§1.1b："同一源代码树（4.4BSD-Lite）在 1993 年后分叉为四个独立分支……呈现'分离→独立发展→部分聚合→再分离'的循环结构。"
〔推断〕据此，谱系系统的第一设计约束是：**分叉树不携带"正统/分支"的等级语义**——它是分离聚合循环的结构呈现，不是"谁是嫡传"的判定工具。

### 0.2 为什么"项目谱系"与"技术谱系"必须分离

〔原文〕总纲 22："真正使项目得以成立的，不是代码，而是外围的形式主义的东西……BSD 代码会过时，但 BSD 社区的实践方式不会完全过时。"＋总纲 8 域扩展"文档与代码本体平等"。
〔推断〕项目谱系（以代码树/组织为单位）与技术谱系（以具体技术为单位）是两个不同的历史对象：同一项技术（如 pf）可以在项目谱系中"从 OpenBSD 分离"又在技术谱系中"聚合进 FreeBSD/NetBSD"。**只用项目谱系会丢失聚合，只用技术谱系会丢失组织权力**——故须双系统并行。这也正是《约束矩阵》§3 P0"聚合侧专章"的数据基础。

### 0.3 三角模型解决什么

〔原文〕总纲 10："真正推动历史的是'动手去做'的人……区别不在于'谁做了'而在于'谁被形式主义包装遮蔽了'。"＋§3.1.2："人物不神化——不将个体叙述为'天才'。"
〔推断〕人物-机构-技术三角的功能是：**把"谁做了什么"落到可核查的边上，并为人物动机强制标注证据等级**——防止把推测动机写成事实（禁天才叙事、禁动机倒灌）。

## 1. 系统一：Project Genealogy（项目谱系）

### 1.1 schema

| 字段 | 说明 |
| ---- | ---- |
| `project_id` | 项目标识 |
| `name` | 项目名（标注术语历史含义，接 Task #14 系统二） |
| `parent_id` | 分离来源（fork 自哪个项目；无则为根） |
| `fork_date` | 分叉时间（标注偶然条件，接 Task #14 系统四） |
| `fork_agent` | 分叉行动者（接三角模型） |
| `phase` | 循环相位：分离期/独立发展期/聚合期（标准 11） |
| `code_flow` | 代码流向记录（cherry-pick/vendor import/共享） |
| `org_structure` | 权力结构（Core Team/BDFL/Foundation） |
| `license` | 许可证（接总纲 13 利益分配） |
| `sources` | 史料依据（L1 commit/L2 邮件/L3 公告） |
| `equality_note` | 固定字段：本项目与其他分支本体平等（总纲 8），不标"主流/支流" |

### 1.2 示例填充：UNIX→BSD→386BSD→四大 BSD

```
Multics（根外参照）
  └─[退出/失败]→ UNIX (1969, 贝尔实验室)
        ├─[学术授权]→ Berkeley BSD (1BSD 1977 → 4.4BSD-Lite 1994)
        │      ├─ 386BSD (1992, Jolitz 夫妇)
        │      │      ├─[分离 1993]→ FreeBSD
        │      │      ├─[分离 1993]→ NetBSD
        │      │      │      └─[分离 1995]→ OpenBSD（de Raadt 被逐后）
        │      │      └─（DragonFly BSD 后自 FreeBSD 分离 2003）
        │      └─[商业衍生]→ Darwin/macOS（Apple）
        └─[其他谱系]→ illumos/Solaris 支（第 15 卷）
```

**聚合边（循环的另一相位）**：OpenBSD pf → FreeBSD/NetBSD；4.4BSD-Lite → 各分支共同基线；macOS↔FreeBSD 双向流动。
〔推断〕示例中每一条分离边须挂 fork_date + fork_agent + 偶然条件；每一条聚合边须挂 code_flow 记录。这正是"分离聚合循环"（总纲 4）的数据化。

### 1.3 操作规则

1. **无等级语义**：`parent_id` 仅表示"分离来源"，不表示"正统性"；禁止在谱系渲染中使用"主干/分支"的粗细差异暗示等级。
2. **相位标注**：每个项目记录其当前循环相位；全书谱系图须同时呈现分离边与聚合边。
3. **fork 须配反事实**：每个 fork 节点关联 Task #14 系统四的一条反事实记录（"若条件不成立则……"）。

## 2. 系统二：Technology Genealogy（技术谱系）

### 2.1 schema

| 字段 | 说明 |
| ---- | ---- |
| `tech_id` | 技术标识 |
| `name` | 技术名（标注英文原文，标准 10） |
| `origin_project` | 起源项目 |
| `origin_date` | 起源时间 |
| `designers` | 设计者（接三角模型，动机须标证据等级） |
| `lineage` | 技术自身的演化链（版本/重写/替代） |
| `cross_project_flow` | 跨项目流动记录（被哪些项目采用/移植） |
| `successor` | 后继/替代技术（若有） |
| `practice_note` | 该技术承载的"实践方式"（总纲 22：行动方式长存） |
| `sources` | 史料依据（L1 代码优先） |

### 2.2 任务指定技术的谱系示例（简表）

| 技术 | 起源 | 跨项目流动要点 |
| ---- | ---- | -------------- |
| TCP/IP | 4.2BSD（DARPA） | 成为参考实现，外溢至几乎全部 OS |
| socket API | 4.2BSD | 成为事实标准接口 |
| FFS/UFS | 4.2BSD | 各 BSD 沿用；ZFS/HAMMER 为后继 |
| VM | BSD 演化 | 各分支独立演化 |
| jails | FreeBSD 4.x | → 影响容器概念（macOS/其他） |
| pf | OpenBSD | → 移植入 FreeBSD/NetBSD（聚合边典型） |
| rc/init | BSD | 与 systemd 构成方法论对照（总纲 21） |
| ports/包管理 | FreeBSD ports / NetBSD pkgsrc | 双谱系并行，对称呈现 |
| 安全机制 | OpenBSD 审计文化 | pledge/unveil 等 |

### 2.3 操作规则

1. **技术谱系独立于项目谱系**：同一技术在不同项目中的实现分列，不因某项目"主流"而以其版本为准。
2. **跨项目流动即聚合**：`cross_project_flow` 是聚合边的技术层记录，须标注来源与去向项目。
3. **实践方式字段**：每项技术须尝试填写 `practice_note`（它承载了什么行动方式）；若无可填，标注"待考"而非留空。

## 3. 系统三：人物-机构-技术三角模型

### 3.1 节点与边

**节点类型**：Person / Organization / Project / Technology。
**边类型**：

- Person → Organization（隶属/创立）
- Person → Project（贡献/维护/fork）
- Person → Technology（设计/实现）
- Organization → Project（资助/治理）
- Project → Technology（承载）
- **Person ↔ Person**（协作/师承/分歧）
- **Organization ↔ Organization**（资助/合作/分裂）

### 3.2 边的 schema（含动机证据等级）

| 字段 | 说明 |
| ---- | ---- |
| `edge_id` | 边标识 |
| `from_node` / `to_node` | 两端节点 |
| `edge_type` | 边类型（上述之一） |
| `action` | 具体行动（"提交了什么补丁/回复了哪些问题"，标准 12 要求具体行动而非空洞贡献） |
| `date` | 行动时间 |
| `motive_evidence_level` | **人物动机证据等级**（见 3.3） |
| `sources` | 史料依据 |

### 3.3 动机证据等级（任务指定五级）

| 等级 | 含义 | 允许的表述 |
| ---- | ---- | ---------- |
| DIRECT_STATEMENT | 当事人直接陈述（邮件/采访自述） | "据其本人邮件称……" |
| CONTEMPORARY_DOCUMENT | 同期文献可证 | "同期记录显示……" |
| STRONG_INFERENCE | 强推断（多源一致） | "编纂者基于多源推断……" |
| WEAK_INFERENCE | 弱推断（单源/间接） | "编纂者弱推断，证据有限……" |
| SPECULATION | 推测 | 须标注"推测，无直接证据"，原则上不入正文 |

〔原文锚定〕此五级是 lishidagang.md §1.2.1 五层级史料在"人物动机"对象上的具体化，也是标准 1"人物生平须经至少两次独立核验"的动机版本。
〔推断〕SPECULATION 级动机禁止写入正文（只可入"辨析"字段作存疑），以防止天才叙事与动机倒灌。

### 3.4 操作规则

1. **动手者优先**：三角模型的节点须包含非核心贡献者（标准 12），不得只建 Core Team 节点。
2. **不神化**：Person 节点禁止"天才/英雄"属性字段；人物贡献以 `action` 具体行动描述。
3. **动机必标等级**：任何涉及"为何 fork/为何离开/为何坚持"的叙述，须挂 `motive_evidence_level`；无等级标注的动机陈述视为违规。
4. **分歧边对称**：Person↔Person / Org↔Org 的分歧边（如 de Raadt 被逐）须按标准 5 对称呈现双方立场。

## 4. 三系统的协同与下游接口

```
Project Genealogy（项目谱系）
    ├─ fork 节点 → Task #14 反事实系统（偶然条件）
    ├─ 聚合边 → 约束矩阵 P0"聚合侧专章"数据基础
    └─ license 字段 → 总纲 13 利益分配分析

Technology Genealogy（技术谱系）
    ├─ cross_project_flow → 聚合边的技术层记录
    └─ practice_note → 总纲 22 实践方式史

三角模型
    ├─ Person→Technology 边 → 技术谱系 designers 字段
    ├─ Person→Project 边 → 项目谱系 fork_agent 字段
    └─ motive_evidence_level → 标准 1/标准 12 核查
```

**→ Task #11（因果链）**：三角模型的边是因果链的载体。
**→ Task #19（知识图谱）**：三系统的节点/边 schema 可直接作为知识图谱的图模型。
**→ Task #10（史料分层）**：所有 `sources` 字段使用 L1-L5 编码。
