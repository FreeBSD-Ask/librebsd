# 02-数据库盘点与史料字段差距分析

> **项目**：《给我自由——一部 BSD 史》编纂系统二次重构 · 数据库层"史料考古"盘点
> **执行人**：数据工程师 · 洗澄明（实证研究团）
> **盘点日期**：2026-08-11
> **铁律**：本次盘点为**只读**操作——所有 SQLite 连接均以 `mode=ro`（失败回退 `immutable=1`）打开，未执行任何 INSERT/UPDATE/DELETE/CREATE/VACUUM；未修改任何数据库文件（盘点前后文件大小与 mtime 已核验一致）。
> **方法**：sqlite3 `PRAGMA`（journal_mode / integrity_check / table_info / foreign_key_list / index_list）+ `sqlite_master` 全量导出 + 每表 `COUNT(*)` 与前 3 行样本。探针脚本与原始 JSON 结果存档于 `qa_tmp/_ro_db_probe*.py` 与 `qa_tmp/_db_probe*_result.json`。
> **基线引用**：references_fulltext.db 与 资料数据库.db 的五维审计结论直接引用今日已完成的 `script/_audit_20260811_fulltext/FULL_AUDIT_REPORT.md`（DB A：references 4,163 条，author 缺 29.4%、year 缺 20.7%、chapter_match 覆盖 73%；DB B：materials 24,129 + references 17,355，title 填充率修复后 94.6%），本报告不重复审计，仅做字段差距对照。

### 1.5 七个文件夹级数据库的共性 schema（三件套）

七个文件夹级库（sacred/original/research_notes/fact_checks/review/cross/meta）共享同一套由 `build_folder_databases.py` 生成的基础 schema（schema_version 1.4）：

```sql
files(id PK, file_path UNIQUE, filename, folder_path, file_extension, file_size,
      sha256, content_hash, line_count, char_count, encoding, line_ending,
      mtime, ingested_at, title, summary, frontmatter, status DEFAULT 'active',
      duplicate_of_id FK→files, duplicate_type, duplicate_of_db, duplicate_of_global_file_id)
blocks(id PK, file_id FK→files CASCADE, block_index, block_type, block_level,
       block_content, block_line_start/end, block_char_offset_start/end,
       heading_anchor, block_metadata, UNIQUE(file_id, block_index))
cross_references(id PK, source_file_id FK→files CASCADE, source_block_id FK→blocks SET NULL,
      reference_type, reference_text, target_path, target_db, target_record_id,
      target_anchor, resolution_status DEFAULT 'pending', reference_context, resolved_at)
update_log(id PK, file_id FK→files SET NULL, operation, field_changed, old_value,
      new_value, timestamp, operated_by, notes)
schema_meta(key PK, value)
```

**设计要点**：① 以"文件夹=库"切分，文件级 sha256/content_hash 支持去重；② `duplicate_of_*` 四字段为跨库去重预留，但**实测 7 库中全部为 NULL**（仅 research_notes 有 3 条库内 merged）；③ `cross_references.target_db/target_record_id` 为跨库引用预留，实测填充率极低（见 4.1）；④ blocks 配 FTS5 全文检索（blocks_fts）+ ai/au/ad 触发器；⑤ **没有任何史料学语义字段**（source_type/author/date/reliability 等均不存在于基础 schema）。

**史料价值判定**：commits 是**机器可读的一手史料**（author_date 即事件时间、commit_hash 即不可篡改凭证）。但注意：① 多处日期异常（见上表），疑为 CVS/SVN 转换或时区解析错误；② `bsd_commits.db`（多份大纲文档引用的"主要史源"）**在本族中不存在**，推测为这些分库的前身/合并名（1.16）；③ 仓库库与资料数据库.materials 之间仅靠 commit_hash 可打通，而 materials.commit_hash 填充率仅 4.6%。

### 2.3 数据质量警示（影响字段可用性）

1. **日期异常**：linux 仓库 commits 存在 2085 年日期（repos 表 latest 字段亦见 2085）、freebsd-ports 含 1973 年提交（早于项目诞生）、openbsd 邮件含 1960 年消息——一手档案层 source_date 须先做异常值隔离（|z| 无法用于日期，建议用项目生命周期窗口硬裁剪），否则 timeline_events 时间轴会被污染。
2. **同名异构表**：`references` 在 资料数据库（素材级，17,355）与 references_fulltext（书目级，4,163）中同名不同义（schema_meta 已有警示语），字段对照时必须显式加库名前缀，未来合并建"史料主数据表"时须改名。
3. **软删除未清**：fact_checks（41/41 deleted）、original_sources（601/604 deleted）、cross_indexes（51/54 deleted）的 files 表几乎全为墓碑记录，真实内容已迁往 资料数据库/Markdown；盘点口径上这些库的"有效数据"≈0，但 blocks/cross_references 残留行仍会干扰 COUNT 统计。

## 第三部分：史料层与知识层隔离的现状评估（五层模型）

### 3.1 目标五层模型 vs 现状映射

| 层级 | 定义 | 现状承载 | 隔离状态 |
| ---- | ---- | -------- | -------- |
| L1 Raw Source（原始史料） | 未经加工的原件：邮件、提交、公告、档案扫描件 | **充实**。6 邮件库（2,539,801 条 messages，含 body/raw_headers/archive_url）+ 11 仓库库（7,223,589 条 commits + commit_files）+ sacred_sources（53 文件/3,182 块，OCR 原文）+ 官方 SA/Errata（713+条） | 🟢 实体存在且规模完整 |
| L2 Extracted Evidence（抽取证据） | 从原件抽取的、带出处的结构化证据片段 | **部分建成**。references_fulltext.key_facts（8,354，带 source_quote+source_block_id+confidence）、timeline_events（42,307，带原文引句）、people/technologies_mentioned；资料库.materials（24,129 条素材级著录，带 trust_basis） | 🟡 已有抽取流水线产物，但仅覆盖书目层（4,163 篇文献），对 254 万封邮件与 722 万次提交**零抽取** |
| L3 Historical Claim（历史主张） | 对历史事实的可争辩断言（"X 于 Y 年发生在 Z"），可被证据支撑或反驳 | **不存在**。全仓无 claims 表、无主张 ID、无支撑/反驳关系 | 🔴 完全缺失 |
| L4 Historical Interpretation（历史解释） | 对主张的因果/意义阐释（"X 之所以发生，是因为…"），允许多解释并存 | **不存在**。解释性内容散落在考据 Markdown（kaoju_records 570 条为考据过程而非解释实体）、章节提纲与复核报告的自然语言段落中 | 🔴 完全缺失 |
| L5 Narrative Draft（叙事草稿） | 最终成书文本，引用 L3/L4，可回溯到 L1 | **部分存在**。chapter_metadata 348 章提纲（status 全部 `outline`，正文未落库）、卷册大纲 Markdown（05-卷册大纲）、sacred 的"叙事参照"合并记录 | 🟡 有提纲骨架，无正文层；且现有章节直接引用 L1 素材（vol/ch/sec 挂钩），**跳过了 L2-L4** |

### 3.2 总体判定

**五层隔离未实现。当前体系是"两层半"结构：**

```
现状：  L1 原始史料 ────────────(vol/ch/sec 直挂)────────────→ L5 章节提纲
             │
             └→ L2 抽取证据（仅书目一支，与 L1 半连通：key_facts.source_block_id 只指向 sacred 库块）

目标：  L1 → L2 → L3 主张 → L4 解释 → L5 叙事（每层只引用下一层，禁止跨层直引）
```

具体证据：

1. **L1→L5 跨层直挂是主流路径**：资料库.materials 通过 vol/ch/sec 三级字段直接钩到 348 章（样本逐条验证，如素材 #1 "ARPA IPTO 1963 年度报告"→卷1章1节1.1.1）。素材未经证据抽取与主张化，直接服务章节写作——这意味着**写作层消费的仍是"原料"而非"经审判的证据"**，事实核查只能事后在成文上做（现有 fact_checks/多轮复核即此模式，且 fact_checks.db 已成空壳，41/41 deleted）。
2. **L2 只有"文献抽取"一条腿**：知识抽取流水线（key_facts/timeline_events/mentioned 系列）只跑了 references_fulltext 的 4,163 篇文献。占比最大的一手档案（邮件+提交 ≈ 976 万条记录）没有任何证据抽取层——邮件里的一句话要成为证据，目前只能靠人工摘录进考据 Markdown。
3. **L2→L1 回溯链半断**：key_facts.source_block_id 设计指向 blocks 主键，但 blocks 表分属 8 个三件套库且各自独立编号，跨库时 block_id 无法定位（cross_db_references.csv 全仓仅 13 条跨库引用、其中 7 条指向不存在的 bsd_commits 库，即为此断链的实证）。
4. **L3/L4 空白的连锁后果**：无主张实体 → doubts_standalone 的 1,987 条存疑"无物可疑"（只能挂在素材 doubt_flag 上）→ 争议图谱（review_reports 中 9 个文件）只能用散文表达 → relevant_claims 字段（20 字段之一）无处安放 → Anti-Bias 审查（Task #13）与关键命题审判（Task #18）缺审判对象。

### 3.3 与既有设计文档的对照

- 现行 schema 的设计意图（见各库 db_meta/schema_meta）停留在"**文献管理 + 全文检索**"范式（FTS5、章节挂钩、考据记录），而非"**史料批判 + 主张管理**"范式。
- 五层模型并非推翻现有资产：L1 完好可复用；L2 的 key_facts 系列表结构（source_quote/source_block_id/confidence 三件套）质量很高，**建议直接升格为全仓统一的 Evidence 表原型**，把抽取对象从"书目"扩展到"素材+邮件+提交"；L5 的 chapter_metadata 348 章骨架可保留为叙事层主键。
- 真正需要从零新建的是 L3（claims）与 L4（interpretations）两张主表及其关系表——即 Task #10"历史主张数据库 schema"的核心交付物。

### 4.1 数据库间打通状态（FK / ID 体系）

| 跨库 FK | SQLite 跨文件 FK 本不可行；项目设计的替代方案是 cross_references 的 target_db/target_record_id/target_anchor 三字段 | 🔴 全仓 6 个三件套库合计仅 **11 条**填了 target_db（全是 sacred 库自指 sacred_sources），cross_db_references.csv 汇总仅 **13 条**且 **7 条指向不存在的 bsd_commits 库**（悬空引用） |

### 4.2 重复 / 冗余 / 孤儿数据风险

1. **物理冗余约 7.4 GB**：6 份 .tmp_fix 副本（资料库/全文库修复过程遗留，约 1.2 GB）+ 5 份多阶段备份（约 5.9 GB）+_tmp_sacred_staging.db（发散 staging，69 文件、schema 停在 1.3）。均为重构前清理候选，但**必须先由人工确认修复已收敛**（只读盘点不动手）。
2. **同名异构表**：`references`（素材级 17,355 vs 书目级 4,163）、`blocks`（8 库各自独立编号）、`files`（同）。任何跨库 JOIN 或视图封装都必须先消歧，否则合并即数据事故。
3. **墓碑库**：fact_checks.db（41/41 deleted，无 blocks 表，cross_references.source_block_id 悬空指向不存在的表）、original_sources.db（601/604 deleted，实体内容已迁资料库）、cross_indexes.db（51/54 deleted）。三库合计有效数据趋近于零，但登记簿仍列名在案——**登记簿与现实严重脱节（11 库在册，18 个实体未登记）**，重构第一步应重建 folder_db_registry。
4. **孤儿数据**：sacred_sources 45/53 文件 status=orphaned（OCR 原文与目录失联）；文献库 3 条 merged 记录与 6 条 deleted 残留；doubts 中 11 条 unresolvable 未回挂任何素材。
5. **日期脏区**：linux 库 2085 年、freebsd-ports 1973 年、openbsd 邮件 1960 年等超窗日期，进入时间轴前必须裁剪（见 2.3）。

### 4.3 面向"历史主张数据库 / 知识图谱"的结构性缺口（Top 3）

**缺口一：主张层（L3）与解释层（L4）整体不存在——知识图谱没有"边"的落点。**
现有实体（人 1,141 / 术语 237 / 技术 7,185 / 事件 42,307 / 章节 348）都是"点"，而历史学知识图谱的核心是"主张-证据-解释"关系边。没有 claims 表，则：支撑/反驳关系、证据等级、多源互证、争议裁决全部无处建模。Task #10 的 DDL 必须一次建齐 claims、claim_evidence、interpretations、claim_interpretation 四张主表，并预留与现有 5 类实体（person/org/tech/event/place）的桥接键。

**缺口二：全局 ID 与跨库引用体系从未启用——图谱无法连边。**
global_file_id、duplicate_of_*、target_db/target_record_id 三组预留字段全部空置，cross_db_references 13 条中过半悬空。建议重构时先建"史料主数据表"（materials 主档，统一 source_id 命名空间：`mat:` / `mail:` / `commit:` / `ref:` 前缀 + 库内主键），所有跨库边一律经主数据表中转；cross_references 的三字段契约保留但必须回填校验脚本（target 不存在即拒收）。

**缺口三：一手档案层（976 万条邮件+提交）与编纂体系零接触——史料的主体在体系之外。**
6 邮件库 + 11 仓库库合计约 34 GB、占数据总量八成以上，但没有任何史料学元数据（20 字段中 author/source_date 之外全缺），未登记进 registry，与 348 章无挂钩。它们是 BSD 史最大的一手史料富矿，当前却只能被"仓库统计"（org_contributions/codev_network）消费，不能被"史实考据"消费。建议为邮件/提交建立轻量级 evidence 抽取视图（不必全量，按"章节需求清单"拉取），挂到统一 Evidence 表（复用 key_facts 的 source_quote+confidence 结构）。

### 4.4 其他观察与建议
