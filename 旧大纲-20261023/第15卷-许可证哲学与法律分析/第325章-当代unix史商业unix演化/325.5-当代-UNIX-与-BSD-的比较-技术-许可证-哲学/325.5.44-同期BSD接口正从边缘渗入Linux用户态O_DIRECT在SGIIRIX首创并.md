同期 BSD 接口正从边缘渗入 Linux 用户态。O_DIRECT 在 SGI IRIX 首创并带对齐查询接口，"FreeBSD 4.x introduced a flag of same name, but without alignment restrictions"，Linux 于 2.4.10 采纳却保留对齐限制，Kerrisk 因此在 open(2) 中重写谱系段而非直接删除 IRIX 引文；getpass(3) 是 SUSv2 标为 LEGACY、POSIX 完全剔除的老函数，BSD 侧已有 readpassphrase(3) 而 glibc 没有，Colomar 因此主张 Linux 手册页保留该函数——"it's still the most portable way to get a password"，git(1) 至今使用之；ffs(3) 按 POSIX 定义于 <strings.h>，FreeBSD 与 NetBSD 遵此，Ruohonen 观察到项目存在"an implicit trend towards trying to limit the documentation to Linux only"，并称这是"good direction"，仅维护 Linux 一项已足够繁重

1995 年前后 2.11BSD 出现 sysctl.3 页面却标注 1993 年，Robinson 判定其为 4.4BSD 因 USL v. BSDI 诉讼和解而分出 Lite 与 Encumbered 版本时的反向移植，SCCS 标记"@(#)sysctl.3 8.1.1 (2.11BSD GTE) 1/13/95"与 1995 年一致，故"带 sysctl 的 2.11BSD 比 4.3BSD 更晚"，Linux man-pages 项目"not attempt to track the provenance or timeline of 2.11BSD features"；同一时期的 4.2BSD 手册页把 mkdir(2) 与 fast file system 一并引入，Robinson 首反应是"that's impossible"，第二反应是"that must be the point at which Unix dropped the 14-character filename limit"，Kirk McKusick 的 O'Reilly Open Sources 自述予以证实

2008 年 David Miller 提交 ec98c6b 系列从 SPARC 内核移除 SunOS 与 Solaris 二进制仿真支持，Linus Torvalds 明确表达惋惜——"we are losing binary compatibility with SunOS and Solaris which is a real loss of functionality"——理由是 Solaris 与 SunOS 为 SPARC 平台事实标准；同期 openprom 驱动 compat_ioctl 表项注释写"only accepts SunOS and Solaris implementations, since the NetBSD version embeds a pointer in the arg parameter"，把 BSD 二进制兼容层的实际边界以代码形式固化；SPARC 平台 errno 编号亦不跨版本一致，Andi Kleen 直言"the original design of errno was for compatibility with the native Unix on that platform"，SPARC 上该原生系统即 SunOS 与 Solaris；SunOS 4.1.x 与 Solaris 2.x 的 VTOC 分区表差异迫使 Linux 同时兼容两套标签格式，Mark Fortescue 警告 sparc 开发者"don't read Solaris code, ever"，"the only safe way is a clean room"，并以"reference the BSD sparc32 port and drivers"作为合法替代路径

2011 至 2022 年间 close-on-fork 提案反复把 BSD 作为 POSIX 共识的锚点：Karstens 援引 LWN 评论区称该特性已在 AIX、BSD 与 MacOS 上定义；Al Viro 直接翻阅三家 BSD 内核源码反驳——"I checked FreeBSD, NetBSD and OpenBSD sources, and it is not present in any of them"——把它斥为"urban legend"，并强调 POSIX 的权威"always comes from the consensus of the existing Unices"；这一回合说明 BSD 家族本身在特性上并非铁板一块，把"the BSDs"当作单一实体来援引 POSIX 论据的做法经不起源码核对

命名与语义细节最能暴露 Linux 与 BSD 的错位。字节序宏跨系统统一尝试以失败告终：Langstraat 自评"I clearly didn't hit the right notes to interest anybody in adopting a standard"，OpenBSD 坚持 <sys/endian.h> 的 betoh64 命名，Drepper 选择 FreeBSD 主导的 be64toh，Kerrisk 遂改写手册页措辞为"the BSDs contain similar but not wholly identical functions in header file <sys/endian.h>"；aligned_alloc(3) 的 C17 合规性各家不一致——"OpenBSD conforms to C11+DR460, but not C17"，"FreeBSD seems to conform to C17, but it claims to conform to C11"；Colomar 向 WG14 提交 alx-0097r1 要求恢复 memory.h，追溯"the APIs have been in <memory.h> since 1986 in 4.3BSD, and in System V they go back further to 1983"，认为 C89 把 mem* 并入 string.h 是"a huge mistake"，提案抄送 BSD 维护者 Keith Bostic

2024 年 4 月 Collin Funk 在 glibc 提交 ee33752b 中批量标注"GNU and BSD extensions that were adopted by POSIX.1-2024"——MAP_ANON/MAP_ANONYMOUS、reallocarray、_Fork、WCOREDUMP、SIGWINCH、secure_getenv、gettext 家族等条目转正，把 BSD 一系在四十年里散落的扩展集中写回主流 C 标准，标志 BSD 与 Linux 的技术分岔开始被 ISO/IEC 与 Austin Group 反向收编；同期 Colomar 在 putenv(3) 里把表述改为"The 4.3BSD-Reno version, like glibc 2.0, uses a copy"，因"4.3BSD-Reno is a single release and hence a single version"，硬版本标注取代了模糊的"the BSD"提法；2019 年 Matthew Wilcox 在 mincore 溯源中发现"FreeBSD claims to have a manpage from SunOS 4.1.3 with mincore"，进一步证明 BSD 派生工具在 Linux 用户态的兼容实现持续承担技术支撑功能
