- 〔会议不详〕KVCache-Cache：LLM 服务中键值缓存管理子系统的负载驱动优化（Zhang Dingyan/IPADS，上海交通大学，与阿里巴巴通义实验室合作）。前缀相同的请求共享 KV cache，缓存命中可跳过大算力预计算、节省宝贵 GPU 周期，对时延与整体吞吐都有益。KV cache 系统有两个子目标：高命中率与低缓存成本（后者受限于 KV cache 必须放在 GPU HBM、DRAM、NVM 或 RDMA 可达远端内存等昂贵高速介质上）。命中时间局部性因三因素而异：多轮对话自然共享前轮前缀而各轮继续概率不同、多模态请求（纯文本/图像与声学理解）复用模式不同、人类与 agent 请求的执行节奏迥异；工作负载无关的 LRU/LFU/FIFO 策略在有限容量下最多多 24% 未命中，而 Mooncake 式用全集群 DRAM 做缓存会因 KV cache 复用的短暂性浪费多达 40% 的 DRAM。作者主张两步走的负载驱动方法：先刻画不同 LLM 工作负载的 KV cache 复用模式，再据此提出负载感知的系统设计。（YouTube EPA6PuiR-BMis，[18.1-502.1]，L1）
- 〔会议不详〕阿里巴巴一周匿名 trace 的洞见与系统设计：既有开源 trace 均缺请求类型（人类/agent、纯文本/多模态）、轮数、时间戳或 KV cache 块哈希等关键信息，作者自采 trace 并开源。三条洞见：按类型与轮次定义的负载其复用时间分布可区分、单轮请求也贡献大量命中；给定时段负载复用概率近似指数分布且跨小时、跨天平稳，可由历史画像推导当前策略；多数 KV cache 复用是短暂的（trace A 中 90% 的 KV cache 十分钟后不再被复用，trace B 中仅 0.3 秒），且寿命按小时可预测。据此提出负载感知淘汰策略（按负载拟合指数分布、用缓存内驻留时间估计未来复用概率、只在画像确定的 live 短时间窗内估计以兼顾短暂复用）与 KV cache 空间估计器，在真实 trace 上将 vLLM 的 KV cache 命中率提升 1-24%，端到端排队 TTFT 最多降低 42%。（YouTube EPA6PuiR-BMis，[502.1-969.1]，L1）
- 〔会议不详〕Collaborative ZK-SNARK：支持分布式秘密的零知识证明（讲者 Alex，Stanford，研究方向为密码学与形式化方法）。传统零知识证明只适用于单方持有的秘密；当秘密分布多方（如多家银行要在非公开的全局交易图中证明存在某类路径）或为分摊高昂的证明生成而把数据秘密分享给服务器群时，常规 ZK-SNARK 不再适用。该原语把单个证明者替换为多个证明者（各有公共数据与一段秘密见证），通过交互协议产生仍可非交互验证的证明；安全性质 t-零知识要求控制至多 t 个证明者的敌手除见证集体有效外学不到任何信息，并以模拟式定义形式化（敌手视图仅由被腐化见证、公共数据与有效性位可模拟）。构造采用标准预处理划分：谓词编译为 R1CS，编码器把分布式见证转为秘密分享的 R1CS 见证（此场景中编码器本身为多方协议）。（YouTube EPA6gjVn_Gkf4，[8.5-366.4]，L1）
- 〔会议不详〕构造技术与评估：直接在 SNARK 证明器上运行通用 MPC 可能比原计算慢一百万倍，作者定制 MPC 使 MPC 与 SNARK 的开销相加而非相乘（约一两千倍）。关键技术之一是椭圆曲线运算不秘密分享坐标（坐标公式非线性、MPC 处理低效），而是直接秘密分享曲线点，使椭圆曲线加法成为本地计算；该技巧此前已证明适用于 SPDZ，作者观察到同样适用于两年前 Crypto 上提出的 GSC MPC。基于 Groth16、3Gbps 数据中心链路的评估显示：约束数足够大时两方 1-零知识协作证明仅比单证明者基线慢 2 倍，三方 2-零知识相同；若零知识阈值低到可假设诚实多数则用 GSC 协议几乎无开销，而通常安全 MPC 比本地计算慢一百到一万倍。还给出把现有 ZK-SNARK 证明器近自动地提升为交互协议的技术、更大规模与更差网络下的评估，以及两方加性秘密分享下通信量至少随 R1CS 约束数线性的条件性复杂度下界（部分构造达到该下界）。（YouTube EPA6gjVn_Gkf4，[368.2-736.4]，L1）
- 〔NSDI（推测）〕AccelTCP：面向更好扩展性与性能的硬件辅助 TCP 栈（Yang Yun，KAIST，合作者 Seongwon Ahn 与导师 Kyoungsoo Park）。网络带宽增速持续快于 CPU，TCP 本身是协议栈中最昂贵的部分：蜂窝网络中 80% 的流小于 1KB，短连接为主时基于 MTCP 的 KV store 有 60% CPU 周期耗在连接管理；L7 代理在 100G 链路上需约 48 个核只做负载中继，连接拼接（connection splicing）也仍有 DMA 与 TCP 重组开销。全栈 TOE 因连接状态受 NIC 资源限制、难以演进（如拥塞控制算法）而失败；AccelTCP 采用网卡栈与主机栈协作的双栈架构，把 TCP 功能分为需灵活策略的中央操作（留在主机）与机械性、变化少的外围操作（卸载到网卡）。双栈面临 TCB 同步与网卡资源受限（如 Azure 网卡仅 8MB SRAM、整体搬移 TCP 预计下降 80% 性能）两大挑战：AccelTCP 在连接建立/拆除与拼接各阶段强制单一所有权以减少同步、同步消息可搭载在数据包上（单次消息事务仅需两次 DMA），连接建立用今日智能网卡硬件优化的密码哈希 cookie 做无状态化，并只为各操作卸载最小 TCB（可多处理 25 倍连接）。（YouTube EPA8fdQY_fgak，[5.4-611.3]，L1）
- 〔NSDI（推测）〕实现与评估：连接拆除与泄漏需跟踪超时，但数百个 NIC 核不保证流到核的亲和性，且高连接率下定时器布防/撤防是写密集、锁争用严重的操作；AccelTCP 提出定时器位图轮（timer bitmap wheel，按超时值排序的位图环、每位按流 ID 索引），置位完全无锁、多核可并行注册，超时到达时可由数百 NIC 核并行扫描触发事件。实现上 NIC 栈基于内核旁路网卡由 P4 管线（报文解析）加 C 代码（状态操作）组成、主机栈扩展 MTCP：64 字节消息微基准比 MTCP 吞吐高 3 倍、与 MTCP 持久连接性能相当（开发者无需再为性能坚持长连接，连接池与空闲超时复杂度交由网卡处理）；Facebook USR 工作负载吞吐稳定提升 2.3 倍且 CPU 占用更低；HAProxy 真实 Web 负载下比 MTCP 八核配置好 11 倍以上，说明代理长期受限于 DMA 开销与负载重组逻辑。问答讨论了 netfilter/iptables/eBPF 钩子可在 P4 管线中处理、长流收益递减，以及卸载后仍待优化的主机栈数据投递路径。（YouTube EPA8fdQY_fgak，[611.3-1249.7]，L1）

- 〔会议不详〕克里特大学（University of Crete）博士生 George 介绍 GPU 有状态包处理框架 GASPP（转写中亦作 Gasp/GUSP 等，属 FORTH 研究所工作）。包处理天然可按包并行、适合多核 GPU，但现有 GPU 入侵检测/路由/代理实现为单体独立应用，需手写大量 CPU 侧代码处理批处理、PCIe 数据搬运；GASPP 抽象出包解码、TCP 流跟踪与流重组等常见操作并提供简洁接口。关键设计之一是主机到 GPU 的传输：NIC 与 GPU 共享缓冲对大包最优，但小包在固定 slot 中占用稀疏导致吞吐低，故采用选择性方案——共享缓冲占用稀疏时先在独立缓冲中背靠背紧凑拷贝再传 GPU。框架模块化，每个模块是一个以包为输入的 GPU 函数；由于 warp 内执行相同指令，不同大小/协议/模块的混包会造成严重线程分歧，用 GPU radix sort 按长度与模块分组后再动态分配到同一 warp。（YouTube EPAEaqaOkR220，[9.8-560.2]，L1）
- 〔会议不详〕后半场讲 TCP 连接状态维护与评测。GASPP 在 GPU 设备内存维护连接表（存 TCP 序号与状态），关键洞见是包 A、B 连续当且仅当 B 的序号等于 A 的序号加其长度，从而对每个包按 seq 与 seq+len 各做一次哈希即可并行确定同连接包的先后并更新连接表，还能处理乱序与序号空洞。评测环境为 2 NUMA 节点、2 高端 GPU、4 个 10GbE 口外加 40 Gbps 流量发生器：大包时 GPU 传输完全隐藏、达 40 Gbps 线速，但延迟比 CPU 实现高约 4 个数量级（8K 批），1K 批可降到半毫秒以下；应用全部写成单个 GPU kernel、无 CPU 侧代码，GPU 较 CPU 实现快 3.6 倍（轻负载）至 36 倍（重负载），多应用并发时靠调度再获约 2 倍加速。Q&A（Comcast、IBM Research）涉及未与 SSLshader/PacketShader 对比、DPDK 轮询占满 CPU 而 GASPP 释放 CPU、对比实现未用 AVX/SIMD 等问题。（YouTube EPAEaqaOkR220，[563.6-1136.4]，L1）
