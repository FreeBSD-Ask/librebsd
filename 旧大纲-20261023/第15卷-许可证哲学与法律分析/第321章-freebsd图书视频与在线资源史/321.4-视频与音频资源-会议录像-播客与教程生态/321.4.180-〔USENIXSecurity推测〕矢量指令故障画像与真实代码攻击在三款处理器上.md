# 321.4.180 〔USENIXSecurity推测〕矢量指令故障画像与真实代码攻击在三款处理器上

- 〔USENIX Security（推测）〕矢量指令故障画像与真实代码攻击。在三款处理器上每核分析一千次故障，故障在矢量寄存器内的位置分布因核而异，部分核几乎集中在单一位置，攻击者可据此挑选最有效的核；易错模式是矢量 xor 或 add 之后紧跟把结果写回内存，该写法在加密代码中大量出现。攻击时把受害者 enclave 放在一个核、攻击脚本放在另一个核，把系统与其他进程全部挪到攻击核以减少对受害者的干扰，并在受害者核的同物理核逻辑伙伴上运行最佳压测程序（压内存、两次矢量左移、再弹出内存）以加大争用。用 Intel 官方为 enclave 设计的 OpenSSL 计算 32 位字符串的 HMAC-SHA256，在部分核上平均成功率 96%、最高 99%，另一核平均仅 20%；作者于 2019 年 8 月负责任披露，Intel 同年 12 月发布可关闭 OC mailbox 访问的 BIOS 补丁与把该标志状态纳入 SGX 证明报告的微码更新，同主题并行工作为 Plundervolt。（YouTube EPTH709b_NJBU，[343-620]，L1）
- 〔NSDI 2023（推测）〕DCM：用声明式编程简化集群管理器。主讲人 Lalit Suresh 来自 VMware Research。数据中心里无论跑虚拟机、容器还是 Serverless，都要靠层层策略代码完成资源分配与基础设施配置，而这类代码背后的算法问题本身很难——以 Kubernetes 调度器为例，它要在约三十种可配置的硬软约束下为 Pod 选择节点，属于带约束的多维装箱等 NP 难问题。作者调研商业与开源系统后发现普遍靠手写的临时启发式链式求解，代价是工程投入大、为求速度牺牲决策质量（搜索空间覆盖不足甚至漏掉可行解）、引发运维摩擦且难以扩展。DCM 的做法是把集群状态维护在 SQL 数据库里，用 SQL 书写约束，再由编译器生成替代启发式的代码：拉取最新状态、高效编码成优化问题、交给现成约束求解器求解并把结果接回调用方，整个流水线可在毫秒级完成。（YouTube EPTJ8GuGREmRE，[8-538]，L1）
- 〔NSDI 2023（推测）〕面向约束求解器的代码生成与三项落地验证。编程上把外键列标记为变量列即声明其为待赋值的决策变量、取值域来自外键邻居列，硬约束写成视图加谓词、软约束写成视图加待最大化表达式，例如把每节点空闲容量建成变量视图后最大化其最小值以打散 Pod，也可在不同时间尺度上实例化多个模型（快速增量放置、必要时抢占腾挪、每日全局再均衡）。编译器主力后端生成与 Google OR-Tools CP-SAT 对接的 Java 代码，关键是尽量不引入多余变量与约束、优先使用求解器有专门传播器与算法的全局约束——在 50 个任务分配给 1000 名工人的基准上，逐字翻译需约 25 秒，逐步启用重写规则后降到约 85 毫秒。作者在 500 节点集群上结合 Azure 公开追踪负载并配置跨 Pod 反亲和，DCM 调度器在推荐的反亲和最佳实践下把 P95 端到端 Pod 拉起时延压缩一半，整体上最高比基线快两倍，同时新增策略只需多加几行 SQL。（YouTube EPTJ8GuGREmRE，[539-1090]，L1）
- 〔USENIX ATC 2022（推测）〕Luna：为云存储从零设计的用户态 TCP。主讲人 Shoma 来自阿里云，分享过去五年在阿里云存储落地用户态 TCP Luna 的经验。阿里云存储遵循存算分离，计算集群与存储集群经前端网络互联，前端网络需兼容各地边缘集群的不同驱动与网卡、支持海量连接并跨地理远距可用区组网，而 2017 年受产品发布计划所限又没有多年时间大规模研发新协议。内核 TCP 可靠且兼容性好，但模拟数据中心常见 RPC 的基准测试显示其时延与吞吐都远不及云存储产品的 SLA，根源是中断开销大、多次内存拷贝、上下文切换、锁与跨核竞争；RDMA 因老机型不支持、单机海量连接也会降低其性能而不适用，既有用户态 TCP 又存在跨调用通信、难以与内核 TCP 应用同机共存与硬件兼容性问题，因此团队选择自研。（YouTube EPTK1vEDOopX4，[16-653]，L1）
- 〔USENIX ATC 2022（推测）〕三种模型设计、生产收益与演进路线。Luna 采用 LibOS 加运行时完备（run-to-completion）形态，让网络协议栈与应用逻辑同线程执行以消除上下文切换与跨调用通信，内置批处理 R2C 与内联 R2C 两种线程模型（前者便于快速迁移 epoll 应用，后者把每个报文处理到底、时延最优，但需换编程模型），配合零拷贝的用户态内存池 zbuf 与把复杂控制面留给内核、经 SR-IOV 或流量导向并配合 netlink 同步 ARP 与路由表的流量模型，使使用 Luna 与内核 TCP 的应用可在同机无干扰共存。相对 Linux 内核协议栈，Luna 把尾时延降低 70%、吞吐提升 3.5 倍，并优于 mTCP 与 vCP；生产中弹性块存储吞吐提升 50% 而时延持平、表格存储端到端时延下降 50% 至 68%。架构上不同于 Google Nap 的微内核方案以换取云存储定制的极致性能，并在 2020 年因 TCP 与软件的固有限制转向新传输协议 SOLA。（YouTube EPTK1vEDOopX4，[661-1111]，L1）
- 〔USENIX FAST 2022（推测）〕Cognitive SSD：把检索加速器放进 SSD 做非结构化数据检索。主讲人 Qinglin 来自清华大学，代中科院与清华大学合作团队汇报。非结构化数据据 Intel 与 IBM 报告已占数据中心存储容量的 80%，会带来密集检索请求，而传统检索系统在软件与硬件两侧都有短板：Linux 面向机械硬盘设计的 I/O 栈给检索系统带来沉重负担，数据又必须跨越低速 I/O 接口、主存与缓存才能到达计算单元。作者把深度哈希与图搜索整合为 DLGX 加速器并嵌入 SSD，用近数据处理绕过片内 DRAM 与常规内存层级、直接从 NAND 读取参数，对外通过 NVMe 协议提供配置命令与哈希任务命令，配套 DLGX 编译器把深度学习模型转为指令并生成图参数，固件侧由配置器、DLGX 任务调度器与 I/O 任务调度器分工处理请求。（YouTube EPTRgcO15Mh6k，[10-412]，L1）
- 〔USENIX FAST 2022（推测）〕NAND 友好的图布局与能效评测。DLGX 把闪存控制器直接暴露给加速器，使卷积层带宽需求由闪存带宽满足，全连接层只使用 PE 阵列的一列以平衡带宽，并按 DLGX 使用的通道数切分参数、配合闪存厂商的进阶命令来最大化并行度；图搜索阶段离先用 DLGX 生成哈希码构建有向 kNN 图，在线按邻接元的邻接元很可能仍是邻接元的思路检索，并把顶点与邻居对齐到页首、以冗余换更少的闪存访问以缓解按页读取造成的带宽浪费。样机基于 OpenSSD 平台（Xilinx FPGA、1 GB DRAM、8 通道 NAND，加速器与闪存控制器实现在 FPGA 上、固件运行在 ARM 上），以基于内容的图像检索为负载对比四个基线：深度哈希与图搜索两单元均优于 CPU，深度哈希单元功耗低于 GPU；系统级平均时延比 CPU 方案低 69.9%、能效为 GPU 方案的 2.4 倍，占集群功耗仅 14.08%，并据此提出无主机（host-free）集群形态。（YouTube EPTRgcO15Mh6k，[413-928]，L1）
- 〔ACM SIGMOD 2020（推测）〕ChunkGraph：面向外部内存的块式图表示。主讲人 Wei Xu（徐伟中）来自浙江大学。真实图数据已达 TB 级，内存内系统与分布式系统开销高昂，单机加大容量存储设备更具成本优势；基于子图迭代的核外系统虽能把多个随机 I/O 合并为顺序 I/O，但每次访问都要加载整个子图导致 I/O 效率低、子图间同步引入额外计算开销，用户还必须自行管理 I/O；基于页缓存的通用系统虽支持细粒度访问、稀疏访问效率更好，却存在页粒度与顶点访问不匹配（Yahoo 等数据集过半顶点只有一两个邻居）以及记录跨页割裂问题。ChunkGraph 据此按度把顶点分为三类：极小度顶点直接存进索引省去存储与寻址开销，中度顶点存进块避免割裂，超级顶点用巨页技术降低页表项与 TLB 开销。（YouTube EPTSQC6QlRUR4，[15-269]，L1）
- 〔ACM SIGMOD 2020（推测）〕顶点重排组合、差分块访问与评测结论。在基本页与巨页之间建立分层结构并按度分层设缓冲，始终优先使用更小的块以提升 I/O 效率；块布局优化依据拓扑信息重排顶点以改善 BFS 等算法在迭代间的局部性，再用互补顶点在线填充重排后产生的块内碎片；针对自底向上扫描全部顶点以寻找活跃顶点的访问模式（遍历顺序与重排顺序不同而引发随机访问），维护重排序号到原始编号的键值映射以按实际顺序访问。系统基于 Ligra 的 graph interface（vertex map 与 edge map）实现，引擎管理内存与磁盘间 I/O 且对用户完全透明。在双路 24 核、108 GB DRAM 服务器上用六张图对比 BlazeGraph 与 LigraMap，ChunkGraph 在 BFS、SSSP、BC 等稀疏访问算法上查询更快、I/O 开销更低，计算开销与 LigraMap 相当而显著低于 BlazeGraph，避开了额外的序列化开销。（YouTube EPTSQC6QlRUR4，[270-533]，L1）
- 〔NSDI 2014（推测）〕V-Shaper：用极少数整形器模拟大量整形器。主讲人 Srikanth 来自微软研究院（MSR），与同事 Peter、Ishai 及当年暑期实习生 Gautam 合作。数据中心里的带宽划分、延迟优先等网络分配功能已成为性能与成本瓶颈，现有方案要么要求新交换机新网卡做更强的包处理，要么在每台主机用软件实现并像 TCP 一样从丢包反推可用带宽、逻辑复杂且新增服务器或虚拟机就会失效。作者主张只用商品交换机已有的整形器（权重公平队列、优先队列或限速器，即内存管理加调度逻辑）：带宽划分映射为权重公平队列、更好的延迟映射为优先队列。核心难题是需要上百租户、上千虚拟机、上万流的成百上千类流量，而交换机可用的整形器通常只有 8 至 16 个；等待更高级别设备还会因验证成本与周期使成本上升。（YouTube EPTVxLC3hzOhY，[9-476]，L1）
- 〔NSDI 2014（推测）〕自适应映射算法、可实施性与仿真结果。V-Shaper 用 TCAM 规则把多类流量多对一映射到少数整形器，并借这些规则免费获得每类流量的需求估计，再周期性调整映射，以输出画像之间的误差（如带宽的均方根误差、满足截止期限概率之差）衡量好坏。对严格优先访问，把需求建模为随机变量并计算每个队列成为临界队列的概率，让临界概率高或需求波动大的队列独占整形器，并给出类似错排的闭式表达式；对加权公平分配，把归一化失败率以下的欠载类整体合并为一组不损失分配，把需求与权重比相近者归组、避免竞争力相差悬殊者互相抢占，并证明最优划分性质后给出动态规划解与更省时的贪心近似。实测在 Bing 机房运行 MapReduce 的 ToR 上行链路上仅用 8 个权重公平队列即把整形误差控制在约 3%；在 Arista 7048S 交换机上以 EOS 命令行脚本验证，常见适配与插表操作只需几毫秒，因而可约每 50 毫秒调整一次。（YouTube EPTVxLC3hzOhY，[479-1108]，L1）
- 〔会议不详〕Shopify 自建本地 Kubernetes 集群的动机与取舍。主讲人 Danny 来自 Shopify。Kubernetes 作为开源容器管理平台提供便捷部署、弹性伸缩与硬件多路复用，还自带服务发现层与配置管理；概念上 node 是一台物理或虚拟服务器、pod 是一组一起部署的容器、service 可理解为对匹配 Pod 做轮询负载均衡的 DNS 名、ingress 负责把互联网请求引入集群内的服务。Shopify 既有自研容器系统只能承载单体大应用、按整台主机扩容无硬件多路复用且不开源不便分享，因而考虑 Kubernetes，但也要面对 Rails 长时任务（如数据库迁移）与滚动部署互相冲突、按主机与进程数做舱壁隔离等弹性策略需重新校准，以及运维聊天机器人 Spy 需要穿透集群访问 Redis 与 Memcache 等额外负担。最终基于不想浪费两个数据中心即将报废的硬件、避免引入跨云往返时延、防火墙内服务间可明文通信带来的安全与隐私优势，以及对商户 PII 与用户数据的信任考量，决定自建集群。（YouTube EPTXGinzAa9ME，[10-525]，L1）
- 〔会议不详〕主控高可用、流量接入、持久存储与最终放弃自建。主控组件（调度器、IP 分配、API 服务器）一旦丢失集群就会冻结、无法扩缩容与部署，而用 Chef 重建需 15 至 20 分钟、赶不上高峰期每 10 分钟一次的发布与可能二十分钟内结束的闪购，于是同时运行多组无状态主控并利用内置的领导选举机制，把配置里的 DNS 名解析到由 ECMP 组支撑的虚拟 IP 实现 anycast，故障切换降到秒级，前提是必须确认主控真正能服务 API 请求才让它接流量；etcd 需保举多数派（三、五、七）且建议直接跑在主控节点上而非作为 Pod 部署，规模化时可改用 SRV 记录替代手工填列的对端地址列表。流量接入方面 Nginx 每次部署重载会丢失轮询状态造成部分 Pod 流量十倍于基线而其余饥饿，于是改用每个 Pod 独立可路由 IP、由负载均衡层直接查 Kubernetes API 获取 Pod IP 并路由过去，恢复原有负载均衡算法；持久存储则需在 K8s 可随时调度驱逐 Pod 的规则下使用持久卷或自购存储设备，并与节点可随时整体下线的可抛弃理念相权衡。最终结论是所谓成功的失败：确实跑起了生产流量，但主、客户端组件与插件版本组合升级痛苦且缺少可参考组合、团队还被迫成为分布式文件系统等非核心能力专家，因而转向公有云。（YouTube EPTXGinzAa9ME，[530-1106]，L1）
- 〔VLDB 2023（推测）〕Alluxio Local Cache：企业级 PB 级 OLAP 的数据缓存层。主讲人 Hope Wang（自称 Yi Wang）是 Alluxio 开发者布道师并负责开源社区，与 Ziyue（子月）共同呈现这篇 Alluxio 开源团队与 Uber 数据平台团队协作的论文。Uber 的查询系统由开源分布式 SQL 引擎 Presto 驱动、存储为 Apache Hadoop HDFS 并向高密度机械硬盘迁移，生产追踪显示负载极度读密集、访问高度倾斜（只有极少数块被极频繁访问）、数据节点 I/O 带宽跟不上硬盘容量形成节流，且 Parquet 与 ORC 列存格式为读效率优化而产生大量碎片化小读。据此提出设计要求：应用无关（同时服务 SQL 查询引擎与 HDFS 数据节点）、最小化与应用的 socket 通信、内存占用小但单节点可缓存数 TB、同时支持随机与顺序访问；架构上以准入控制器优先处理高频访问文件，缓存管理器在命中时直接返回所请求页、未命中时回源，淘汰策略含 FIFO、随机、LRU 及基于时间的策略，并用 page store 把文件级操作下沉为页级。（YouTube EPTXMkhyX8V8Q，[16-553]，L1）
