# 321.4.83 〔会议不详〕TriCache支持核外outofcore高性能处理的用户透明块缓存

- 〔会议不详〕TriCache：支持核外（out-of-core）高性能处理的用户透明块缓存。主讲人冯冠宇来自清华大学；NVMe SSD 阵列随 PCIe 4/5 与 U.2 而大幅提速（2U 服务器可挂 16 盘达 50TB 容量、50GB/s 带宽、千万 IOPS），但仍受块级 I/O、高延迟与写寿命限制；OS 页缓存易用但核外性能差（TLB shootdown、上下文切换、全局锁与 I/O 栈开销），用户态缓存与 SPDK 高效却要求基于缓存 API 重写程序并手工管理块边界；TriCache 的目标是像页缓存一样免改代码，分别以编译期插桩解决改写、多级缓存解决软件地址翻译、消息传递委托与无锁结构保证可扩展性以吃满 SSD 阵列。（YouTube EPEB6uu2Z7Epo，[0-454]，L1）
- 〔会议不详〕TriCache 的三级缓存设计与评估。基于 LLVM IR 在 load/store 前插入 get_raw_pointer 运行时调用，把虚拟内存空间放入非规范地址区、用最高位快速识别，重编译库直接支持、未重编译库用 library hooking 与 trap 处理兜底；三级包含式缓存为线程/纤程级直接映射的 direct SATC、private SATC 与全功能 shared cache，用引用计数保证包含性以避免昂贵的软件广播；shared cache 按分区组织为单线程服务器、消息传递委托处理缓存管理与元数据，客户端自行执行数据操作；评估覆盖图处理（Ligra 对比 Ligra swapping 与 FlashGraph）、KV 存储、大数据分析与图数据库，WCC 下缓存版内存内比页缓存慢约 3 倍但比 FlashGraph 快约 4 倍，核外场景比页缓存快数个数量级，SATC 命中约 15 周期（近 NUMA 本地 L3），承担绝大多数访存。（YouTube EPEB6uu2Z7Epo，[454-909]，L1）
- 〔会议不详〕Cider：面向高性能存储盘的存内（in-storage）计算伴生系统。主讲人 Zane 与 UCLA 的 Tom He、Jason Kong 合作；存储盘带宽约每两年翻倍而主机互连扩展不佳，形成阻碍先进存储发挥的数据搬运墙，存内计算（如把 SQL 查询的过滤下推到盘内）可缓解，但现有工作在硬件层（ARM 算力不足以饱和盘内带宽、ASIC 制造后不可编程）、系统运行时层（缺保护与虚拟化）与编程层（缺有效抽象、需大量改主机代码）各有局限；Cider 选用兼顾性能与灵活性的 FPGA 作为存内计算单元，构建独立控制平面实施权限检查与资源调度，并提供类 POSIX 的文件抽象。（YouTube EPEBbG-JOCBTY，[0-524]，L1）
- 〔会议不详〕Cider 的控制平面、虚拟文件与评估。盘内 FPGA 芯片经重编程承接计算逻辑（LBA 由固件翻译为 PBA），因纯数据平面缺保护，改为 compute-only 盘程序、由可信 Cider 运行时作集中代理在主机侧做文件权限检查；虚拟化靠部分重配置把 FPGA 均分为三片并集中收回 offload 权限，再在 FPGA 内实现硬件调度器（主机侧 PCIe 往返 1 微秒太慢），采用类 deficit round robin 的公平策略；用户注册虚拟文件（如特征选择程序产出的 post file 直接喂给 SVM）；PCIe FPGA 盘（64GB、5 微秒访问延迟、16GB/s 顺序带宽、PCIe Gen3 x8、XFS 主机文件系统）上各应用只需数十行主机代码与数百行设备代码、开发 2-9 人日，对比先前工作数千行代码与逾一人月；对四核 ARM Cortex A72 平均 12 倍（CNN 达 58 倍）并饱和盘带宽，性价比 2.5-149 倍、平均 31 倍（Xilinx Artix-7 37 美元对 A72 95 美元）。（YouTube EPEBbG-JOCBTY，[524-1049]，L1）
- 〔SREcon（推测）〕用可信平台模块（TPM）保护系统完整性。主讲人 Dmitry Potapov 是 Facebook 生产工程师，以演示贯穿全场：容器（运行 DHCP 服务器与软件 TPM 模拟器）加 QEMU Linux 虚拟机经 tap 设备互联；用 EDK2 编写约 700 行 C 的恶意 DXE 驱动（编译后约 16KB、支持 DHCPv4/v6、已在真机验证），扫描分区找到 flag.txt 后经 DHCP 取址并把密件发往容器内 Python HTTP 服务器；规模化运维下 Secure Boot 并非万能——签名校验失败常意味着主机根本无法开机且原因未必与安全有关，特权者还可在少数主机上禁用 Secure Boot 并伪造检查结果——进而引出 measured boot：逐级度量启动链并扩展哈希、信任攻击面极小的信任根（Intel 平台为 TXT/Boot Guard）、PCR 只能扩展不可直写且可由厂商证书链签名导出，支撑远程证明（remote attestation）与封装（sealing）。（YouTube EPEGUzB9-C1Go，[0-804]，L1）
- 〔SREcon（推测）〕密件封装与解封演示。理想流程为远程证明确认已知良好状态、用仅在该状态可用的密钥送入密件并按策略本地加密封装；因良好系统状态数量庞大，采用 policyAuthorize——任何由指定密钥签名的策略均可满足；演示生成 RSA 策略签名密钥并载入 TPM、创建授权策略，用厂商认证的 endorsement key 封装密件（该密钥由 endorsement 层级种子确定性派生，可保留在非易失内存）并取得含启动计数的 quote，再构造匹配已知良好状态的 PCR 策略并用签名密钥签署，解封时校验签名、满足两策略、重新派生 endorsement key 载入密件后成功 unseal；改用被攻陷固件开机后 PCR 不匹配、策略无法满足、解封失败。（YouTube EPEGUzB9-C1Go，[804-1609]，L1）
- 〔USENIX Security〕电子邮件发件人伪造攻击与 SPF/DKIM/DMARC 发件人认证机制研究。主讲人 Jianjun Chen（时任加州大学博士后，师从 Vern Paxson），合作者还有 F5 的 Jian Jiang；现场演示了对 Gmail 的实际伪造：邮件显示由 security@facebook.com 发出并通过其 mailed-by/signed-by 签名验证。讲解邮件 From 头（写信人）与不可见的 SMTP 信封 HELO/MAIL FROM（传输者）两类标识，并梳理 SPF 按 DNS 中授权 IP 列表认证、DKIM 按公钥签名认证、DMARC 做标识对齐且只要求两者之一通过（否则按策略如拒收处置）的认证流程。（YouTube EPEMThz0vwgSw，[8.7-350.3]，L1）
- 〔USENIX Security〕提出 18 种绕过邮件发件人认证的攻击，核心思想是利用邮件处理链中至少六个组件（由不同开发者或不同公司实现）之间的解析不一致。例如攻击者在 DKIM 签名的 D 标签中放入含换行/空字符的域，DKIM 组件与 DNS 组件对签名域解析不一致，使攻击者用自己的公钥通过验证；还可利用双 From 头、From 头周围空白、Sender/Resent-From 回退显示、路由段与多种编码等 From 头复杂语法制造歧义，使接收服务器认证的标识与邮件客户端展示给用户的标识不同。实测 10 个邮件服务与 19 个邮件客户端共发现 43 种可利用组合（黑盒测试仅是问题子集），建议实现遵循 strict-in-what-you-accept、在规范层面简化消息语法、客户端显式展示认证结果，终端用户辅以 PGP 端到端验证，测试用例工具已发布于 GitHub。（YouTube EPEMThz0vwgSw，[407.0-763.0]，L1）

- 〔OSDI〕从 WiscKey 到 Bourbon：把学习型索引（learned indexes）集成进日志结构合并树（LSM-tree）。主讲人 Yifan Dai（威斯康星大学麦迪逊分校博士生），并有 Microsoft 的 Brian 参与；学习型索引用机器学习（如线性回归模型 0.5x-50）把键映射到位置以获得常数级查找与常数级内存开销，但插入会改变数据分布、迫使重训或降低精度，而 LSM-tree 把数据组织为不可变 SSTable、写入期间不原地更新，天然契合学习型索引。在介绍 LevelDB 内存表与分层 SSTable 压缩机制的基础上，研究 SSTable 生命周期（level 0 平均约 10 秒、level 4 约一小时，各层均有因连续压缩产生的短于一秒的表）得出学习准则：优先学习低层表、学习前设置等待以避开极短命表、不忽视可能服务更多查找的高层表、按负载与数据动态感知；索引模型采用贪心分段线性回归（误差界设为 8，训练一遍 O(n)，推理在段间二分对数级），Bourbon 构建在采用键值分离优化 LevelDB 的生产级系统 Wisckey 之上。（YouTube EPEUxEx5hwLXk，[8.9-504.5]，L1）
- 〔OSDI〕Bourbon 的运行时学习决策与评测：含写入的负载会产生新 SSTable，总是学习前景时延最好但后台学习开销高，为此设计代价-收益分析器，按同层历史表的查找次数、基线路径与模型路径耗时估计收益、按表大小估计学习成本，仅在预估收益大于成本时学习；在 10% 写负载下学习量与 always-learn 策略相当，50% 写负载下仅学习其约 10% 却保持接近的前景时延，总 CPU 开销最低。评测显示相对基线 Wisckey 只读与读重负载提升 1.23-1.78 倍、写重负载约 1.1 倍且对写无开销；在合成数据集上线性数据增益最高、分段增多时增益下降，Amazon 评论与 OpenStreetMap 纽约真实数据集约 1% 段比例下增益约 1.6 倍；YCSB 各核工作负载 C 超 1.6 倍、B/D 约 1.35 倍、A/F 约 1.1 倍、E 约 1.2 倍；数据驻留 Opal SSD 时只读仍提升超 1.3 倍，结论是 Bourbon 把学习型索引集成进生产级 LSM 系统并在多种负载下获益，同时提出机器学习如何改变系统机制的更广泛问题。（YouTube EPEUxEx5hwLXk，[622.4-1131.4]，L1）

- 〔WOOT〕FUZZVPN：系统性发现 OpenVPN 漏洞。主讲人 Anqi（美国东北大学三年级博士生），与导师 Cristina Nita-Rotaru 等合作；OpenVPN 是基于 TLS 定制的最流行 VPN 协议之一（NordVPN、ProtonVPN 均采用），支持 TCP/UDP 与 tun/tap 设备、尚未被 IETF 标准化（RFC 仍为草案），仅 8 年前有针对早期 2.4 版本的技术报告；现有变异式（AFLite）、生成式（Peach）与代理式模糊测试工具难以适配其会话级加密与不清晰的协议模型，WireGuard 有大量形式化验证而 OpenVPN 没有。工作构建了 UDP/TCP 两种模式下握手协议的详细消息序列图（MSC，被动学习包结构、主动学习交互语义），实现工具 FUZZVPN，发现 2 个拒绝服务、17 个配置输入处理不当、服务器过早发送数据、性能下降与 ACK 包相关等多类新攻击。（YouTube EPEXrhPMkOsoE，[10.5-520.9]，L1）

- 〔Vault〕SMB3 Linux/POSIX 协议扩展的设计与实现进展（主讲人 Jeremy Allison，Samba 团队/Google，Steve French 同台）。回顾 SMB1 Unix 扩展：由 Samba 独家实现、POSIX 语义优于 NFS，但协议设计系按需塞入的有机演化（"要是能加个功能就酷了"是最危险的协议设计宣言），允许客户端创建服务器端符号链接是其自认的重大安全设计失误，不过它率先实现传输层加密并促成了 SMB3 随后采纳。SMB3 Unix 扩展遵循彻底最小化：能复用 SMB3 既有能力（加密、ACL 等）就不发明新东西，仅扩展必需的小块区域（对比 Apple 采用 magic create context 切换魔法模式的复杂做法），在 negotiate 阶段发送含 GUID 的 POSIX create context，使客户端能区分服务器"不支持 POSIX"与按策略（如导出 FAT32 U 盘共享）拒绝 POSIX 语义。（YouTube EPEZOD6qzuqSE，[12.3-369.1]，L1）
