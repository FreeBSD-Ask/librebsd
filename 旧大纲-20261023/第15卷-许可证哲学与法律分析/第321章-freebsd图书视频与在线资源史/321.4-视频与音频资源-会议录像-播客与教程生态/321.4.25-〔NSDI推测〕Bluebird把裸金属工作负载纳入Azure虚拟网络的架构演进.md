- 〔会议不详〕Macaron：面向微秒级应用的RDMA成员服务。主讲人Antoine Murat（与EPFL及华为的合作者共同完成）指出etcd、ZooKeeper等成员服务无法工作在微秒尺度，高频交易等应用在故障或重配置时遭遇巨大延迟尖峰；Macaron能在15微秒内检测故障、10微秒更新成员、25微秒作废旧成员，对故障整体反应仅50微秒；其把故障分类处理——进程崩溃借助内核崩溃通知、内核挂死借助经RDMA暴露的心跳计数器（即使CPU不工作也能读取且不受网络异步性影响）、整机失联才使用可调超时，拜占庭故障不在范围之内。（YouTube EP3_U9VD8RVcM，[13-500]，L1）

- 〔会议不详〕M3X：让固定功能加速器自主运行并兼顾快速路径通信。德累斯顿工业大学与Barkhausen研究所的Niels Asmussen（与Hermann Härtig等合作）指出加速器通常需CPU代为访问文件系统、网络栈等OS服务，导致高CPU负载并抵消能效优势，而M3式绕过内核的快速路径通信又与上下文切换难以结合；基于硬件-操作系统协同设计M3（以Gem5仿真评估、不依赖缓存一致性），系统以每个计算单元旁的DTU提供统一接口、内核运行于内核tile，借助通用文件协议（一切皆文件）与外接在加速器上的加速器支持模块（ASM）实现对输入输出文件的直接访问。（YouTube EP3b-TiJqe54I，[10-593]，L1）
- 〔会议不详〕M3X的上下文切换、数据通路收益与Q&A。内核与用户tile上的辅助组件用通用上下文切换协议（只做保存/恢复），DTU记录运行活动与通信目标，ID不匹配时报告错误并回退为经内核的慢路径投递；以图像处理加速链为例，自主方式让加速器直接读写文件、OS不再搬运数据，OS造成的CPU负载降低30倍，而PCIe连接下辅助方式单条链即近90% CPU负载；共享1-4条加速链时1毫秒时间片开销1-2%、更长片低于1%。Q&A涉及接收端基于信用的流控、支持前后回溯访问的请求处理加速器（缓存式访问）以及Barkhausen研究所正以硬件实现DTU并向逻辑厂商提供设计。（YouTube EP3b-TiJqe54I，[594-1187]，L1）
- 〔会议不详〕原子DDL缺陷（ADB）的系统研究：207个真实缺陷剖析。作者因签证缺席，由清华大学的博士后Fuqin Ma代讲：原子DDL要求数据定义语句全成全败，MySQL 8等引入后因多组件协同实现复杂仍易出错（如ALTER TABLE回滚不当致列数与期望不符）；团队从MySQL、MariaDB与PostgreSQL收集207个真实缺陷报告，发现44%表现为错误结果、32%为恢复后数据不一致、24%为系统不可用，根因依次为不完整回滚（32%）、同步不当（22%）、并发控制实现错误（18%）与错误处理不当（22%），约93%由多语句操作同一元数据元素的元数据冲突点触发，并归纳出错误结果、系统不可用与恢复后不一致三类测试预言。（YouTube EP3bQD7giOKLM，[17-496]，L1）
- 〔会议不详〕DDLumos工具设计与评估。工具由元数据冲突引导的DDL合成测试用例生成器与基于图的元数据一致性分析器组成：先初始化元数据表并随生成更新冲突点，交替生成DDL与其他语句、构造元数据图并按语句序列控制并发压力下发，再以图推导的期望元数据与执行后的实际库状态比对判定缺陷；在6个DBMS（含PostgreSQL、MySQL、MariaDB）上发现73个真实缺陷（20个可用性、31个错误结果、22个恢复后不一致），全部获确认、14个已修复；与CycleLancer、CycleSmith、Squirrel、TxCheck对比的48小时实验显示其覆盖更多相关分支，36个独特缺陷大多为其他工具未覆盖。（YouTube EP3bQD7giOKLM，[497-912]，L1）
- 〔会议不详〕EnigmaMap：面向安全飞地的外部存储遗忘映射。主讲人Afonso（与Sicheng Gao、Yilun Xu合作）以Signal私人联系人发现为动机：数据库放进SGX飞地后访问模式仍会泄露查询内容，需要访问模式不泄露信息的遗忘算法——Signal最初的批量线性扫描需500台服务器，改用遗忘算法后仅6台；EnigmaMap是SGX飞地内的遗忘键值映射，提供查询隐私与数据库隐私。微基准显示OCALL比EWB页换出略高效但比飞地内换页贵46-60倍，据此团队采用把飞地内存视作大缓存的外部存储模型（按页读写），较此前遗忘映射快10-100倍。（YouTube EP3c8ocTudulM，[8-378]，L1）

- 〔USENIX ATC（推测）〕ListDB：写前日志与持久化跳表联合的增量检查点。UNIST博士生Wonbae Kim指出LSM树在写密集负载下因后台flush慢于前台写而出现写停顿（write stall），PM仅索引慢于DRAM索引，DRAM+PM混合索引恢复代价又高；ListDB以三项设计应对——索引统一日志（把日志项转为schemaless元素加快flush）、拉链压实（原地归并降低写放大）与NUMA感知编织跳表（减少远程NUMA访问），写吞吐比Intel的PMem-RocksDB高25倍；日志项预留跳表指针空间，memtable刷盘时仅写指针即成跳表，指针按批持久化并推进WAL边界，从而实现异步增量检查点。（YouTube EP3cDztgVGFgQ，[12-436]，L1）

- 〔会议不详〕主讲人（Akamai，署名邮箱按通行拼写校正为 nygren@akamai.com，ASR 音写为 niger）讲述多年来在其网络中实施 IPv6 的经验。背景是 IPv4 地址枯竭：IANA 与 APNIC 已耗尽，按 Jeff Huston 的数据 RIPE 约 2012 年、ARIN 约 2013 年耗尽并可能提前进入紧缩模式，短缺已开始显现为更多 NAT 与 IP 地址二手市场涨价，而替代方案 NAT444 会带来多层 NAT 与 STUN 依赖。核心论断是 IPv4 与 IPv6 是两个互不直接兼容的互联网、仅靠双栈机器衔接；网站是否走 IPv6 由 DNS 的 A 与 AAAA（quad-A）记录结合客户端行为决定，CNAME 链不可拆分 A 与 AAAA，DNS 查询所用协议与所问记录类型相互独立。当时仅约 0.3% 客户端 prefer IPv6，6to4/Teredo 流量近乎归零，Happy Eyeballs 草案实现五花八门（引 Emile Aben 的 Hampering Eyeballs 与 Geoff Huston 的后续文章），法国 Free 用 6rd、挪威渗透率高，日本 KDDI 受监管制约导致发 quad-A 反而损害性能，broken peering 与残缺实现使部分网络 IPv6 完全不通。（YouTube EP0OdYdFiByKc，[5-1267]，L1）
