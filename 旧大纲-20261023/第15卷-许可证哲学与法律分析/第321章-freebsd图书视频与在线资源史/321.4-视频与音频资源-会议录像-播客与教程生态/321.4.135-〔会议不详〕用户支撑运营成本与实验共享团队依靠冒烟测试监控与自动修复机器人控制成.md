- 〔会议不详〕用户支撑、运营成本与实验共享。团队依靠冒烟测试、监控与自动修复机器人控制成本，每周仅约 13 个 help desk 工单，并将可分配资源能力回馈为 OpenStack 顶级组件 Blazar；用户来自 168 个机构，累计 275 篇论文，使用量呈学期季节性波动但总体增长、租约开始趋于饱和。在共享维度上，将 Jupyter hub 集成进测试床以打包复杂多节点实验并实现可复现，与 CERN 开发的 Zenodo 集成发布数字产物并获取 DOI 使实验可引用，还发布 Chameleon Box 供学术界或工业界自建同类测试床；结语强调"实验测试床永远不会完工"，必须持续追逐研究前沿。（YouTube EPL_gOvsVoq-4，[738-1507]，L1）
- 〔SREcon〕BPF：Linux 的下一个超级能力（跟踪篇）。主讲人 Sasha Goldshtein（以色列咨询公司 CTO），讲解以 BPF 虚拟机与 BCC（BPF Compiler Collection）前端为核心的动态跟踪：C 代码编译进内核执行，Python/Lua 在用户态做聚合与展示。BPF 程序具有安全性保证（程序大小受限、无回跳，不会崩溃或挂起内核），内核 4.1 起可挂 kprobes/uprobes、4.7 起支持静态 tracepoint，数据结构扩展出哈希表、直方图、栈跟踪聚合；BCC 内置 biolatency、filetop、cachestat、stackcount 等成套工具，Brendan Gregg 的 BCC 工具图覆盖文件系统、调度器等各子系统。（YouTube EPL_sVgheLNT0，[30-1130]，L1）
- 〔SREcon〕argdist/trace 通用工具、自写工具与部署。argdist 可对任意函数参数做分布统计，trace 可在 kprobe/uprobe/内核 tracepoint 上插一行命令插桩（示例包括 bash 的 readline、Node.js HTTP 请求、OpenJDK 线程启停），现场演示用 BCC 的 tracepoint 模块统计 sched:sched_switch 进程切换计数并用 attach 接口挂 kmalloc 统计分配；工具由编译进内核的 C 部分与用户态 Python/Lua 驱动两部分组成。部署仅需较新内核（探针 4.1、多数工具 4.4、栈跟踪 4.6 起）加 Python 与 libbcc，Lua 工具则只需静态链接的 bcc-lua；答疑指出跟踪基本需要 root、BPF 程序的记账能力尚缺，作者曾用 BCC 内存泄漏跟踪工具（对比 Valgrind 无需重编译）解决过 C++ 泄漏。（YouTube EPL_sVgheLNT0，[1130-2248]，L1）
- 〔FAST（推测）〕MatrixKV：用 NVM 矩阵容器降低 LSM 树 KV 存储的写停顿与写放大。主讲人 Ting Yao（华中科技大学），与 PingCAP、UT Arlington、Temple 大学合作。对 RocksDB 随机写 80GB 数据集的测量发现：吞吐周期性跌至近零的写停顿根因是 L0→L1 compaction 因 L0 SSTable 相互重叠、来回选取而演变为近乎全对全的合并（平均约 3.1GB）；而写放大随 LSM 层数线性增长（WA=AF×N）。现有最先进方案 NoveLSM（ASPLOS 2018，将大型可变内存表放入 NVM）虽提升约 1.7 倍随机写吞吐，却显著膨胀未排序的 L0、使 compaction 数据达 15GB，不足以同时解决两个挑战。（YouTube EPLabTka3h1ek，[7-621]，L1）
- 〔FAST（推测）〕MatrixKV 设计与评估。在 DRAM 与 SSD 间加入 NVM 层，四项设计策略：矩阵容器（receiver 按行表逐行存放刷下的 memtable、填满后逻辑转为 compactor）存储并管理未排序的 L0；列压缩（column compaction）按 L1 的连续键范围逐列合并、每次仅处理少量数据；SSD 上采用"扁平化 LSM 树"增大 L0/L1 以减少层数 N；跨行提示搜索（cross-row hint search）用前向指针保证大 L0 下的读效率。在 8GB Optane DC PMM 平台上，4KB 值随机写吞吐较 RocksDB-L0-NVM 提升 3.6 倍，99 分位尾延迟较 SSD 版 RocksDB 低 27 倍，单次合并仅 33MB（对照组 3.1GB）共 467 次列压缩，写放大降低 3.43 倍。（YouTube EPLabTka3h1ek，[622-1233]，L1）
- 〔USENIX Security（推测）〕AIFORE：基于自动输入格式逆向工程的智能模糊测试。以 readelf 解析 ELF 为例归纳三条观察：不可分字段的各字节总在同一基本块内被解析、不同类型字段呈现不同处理模式、输入结构变体会使程序分派不同解析代码。方案含三个模块：字段边界分析（先做指令级与字节级污点分析，再合并到基本块级映射，最后用最小聚类切分不可分字段）；字段类型分类（用 CNN 结合 IR 指令、格式串与 memcpy/strcopy/malloc 等库调用三类特征，将字段分为六种语义类型）；以及模糊测试期间的功耗调度。（YouTube EPLc9mH8LMF8g，[8-330]，L1）
- 〔USENIX Security（推测）〕功耗调度、实现与评估。只对触及新基本块、更可能属于未见格式变体的"有价值"种子做格式提取，并按字段类型的自定义 mutator 将功耗重新分配给变异不充分的格式变体；实现上构建基于 libdft 的污点分析引擎（支持 64 位程序与字节级污点）、以 angr 做静态分析后端、用 Keras 实现机器学习组件、写脚本从 010 Editor 导出模板结果，模糊测试框架基于 AFL。评估显示字段边界准确率与编译优化级别无关、最终分类准确率超 85%，格式识别准确率与解析耗时均优于 tf-parser、Parser/AFL 等方案；与 6 个 fuzzer 每目标 24 小时×5 次对比，多数情况覆盖最优，共发现 34 个 bug（其中 20 个其他 fuzzer 未覆盖），消融实验证明边界、类型与功耗调度三模块均有显著贡献。（YouTube EPLc9mH8LMF8g，[330-706]，L1）
- 〔会议不详〕Hyperscan：面向现代 CPU 的快速多模式正则匹配。Intel 方主讲人（答疑中被称 Xuyang）：正则匹配是第 7 层 DPI 应用的核心但性能缓慢；现行"预过滤"最佳实践手工从正则中挑取字符串关键字，易被频繁匹配而触发昂贵正则回溯，且识别机需从头再扫输入造成重复串匹配浪费 CPU，复杂正则又常退化为慢速 NFA。方案为基于分解的匹配：把正则原子地分解为字符串组件与 FA 组件，必须按原始顺序全部匹配才算命中，从而避免重复匹配且可把 FA 组件做小后转成快速 DFA；多正则场景可分解后对同一输入并行匹配全部正则，单串与多正则匹配分别提速 3.2 倍与 13.5 倍，Snort 实测约 9 倍。（YouTube EPLe67mP-jIa8，[10-722]，L1）
- 〔会议不详〕SIMD 加速、评估与系统演化。用图结构分析（NFA 图上的主导路径、主导区域与最大流-最小割网络流三种分析）自动分解正则，自动关键字使正则调用次数最多降低 700 倍。算法层用 SIMD 指令加速：多串匹配把经典 Shift-Or 扩展为多模式近似匹配、128 位移位掩码分 8 个桶并预移位打断数据依赖提高 IPC，FA 匹配采用每状态仅 1 bit 的位级 NFA 与 SIMD 并行位运算。在 Intel Xeon 上对 Snort/Suricata 规则评估：随机流量单串匹配最高 3.2 倍、真实流量 2.5 倍，正则匹配较最优方案 1.8–6.9 倍；集成进 Snort 后吞吐从约 100Mbps 提升到 1Gbps（超 8 倍），数万条规则编译时间小于 1 秒；答疑回顾该长跑项目从预过滤到图优化的十余年演化与 Hyperscan 已被 40 余个商业产品、37 个开源项目采用。（YouTube EPLe67mP-jIa8，[722-1443]，L1）
- 〔会议不详〕云中的优先级 I/O 调度（PBS）。主讲人 Philip Blagoevich（HGST Research）：分布式文件系统被多个延迟要求不同的应用共享时，文件系统层设置的 I/O 优先级在硬盘设备内部调度中失效（设备只追求最大带宽、不感知宿主调度），导致高优先级实时请求高延迟甚至饥饿；很多用户被迫把队列深度限制为 1，代价是吞吐损失近一半（相对 QD32）。方案 PBS 基于 SATA ICC-NCQ（Isocronous Command Completion）的高优先级命令把分布式文件系统的 I/O 优先级直通设备，盘内固件将优先命令放入单独 FIFO 队列处理；实现横跨用户态与内核：PBS JNI→PBS CDB→扩展 SGIO 接口→内核模块→FIS 数据结构（优先级最终落在 FIS 的 byte 13），并绕过页缓存、用 mincore 判断数据是否已在 DRAM 以决定是否走标准读。（YouTube EPLk8O3MvZiOU，[9-866]，L1）
- 〔会议不详〕评估、软件栈改造与展望。4 节点（每节点 24GB DRAM、4 块 HDD，本地 ext4+CFQ）上运行 YCSB（HBase/Hadoop 之上）并与 MapReduce wordcount（50GB 数据集）、rowcounter 竞争：PBS 高优先级命令的平均与 95 分位延迟均显著优于 Linux 调度器，且 YCSB 线程数越多差距越大。为此改造了几乎整个软件栈：Hadoop 的 DFSInputStream/BlockReader/BlockSender 通过扩展 read 调用与环境变量传递优先级，HBase 客户端经扩展 RPC 把优先级传给 region server。未来方向包括低优先级命令的饥饿问题、ICC-NCQ deadline 命令与自动优先级分配；答疑说明目前仅支持 SATA（SAS 因规范中优先级字段不明确未实现），且依赖说服固件厂商定制的 ICC-NCQ 实现。（YouTube EPLk8O3MvZiOU，[866-1716]，L1）
- 〔会议不详〕Parquet 列式格式速览。主讲人 Nitish（Parsable 创始人）：Parquet 是开源列式二进制格式，凭借列存设计支持快速过滤与高效压缩（因此不能用文本编辑器直接打开）；其逻辑表示简单，格式按行组（row group）组织，把数十万行的各列物理上连续存放在一起，这正是压缩高效的来源。（YouTube EPLnBSu2fiv-M，[18-73]，L1）
- 〔会议不详〕Parquet 为何适合日志、追踪与指标。随着世界转向半结构化日志与追踪，这些信号中已存在一定结构：例如所有状态词可存入同一列并利用字典编码压缩，其实际用例中仅用 Parquet 格式即可压缩约 90%；对指标而言基数（cardinality）是最大挑战，但指标事件写入 Parquet 后只是某列中的一个字段，列式方案天然带来更好的压缩，且使用者无需再关心基数问题。（YouTube EPLnBSu2fiv-M，[73-136]，L1）
- 〔会议不详〕不精确分支历史引发的侧信道攻击。主讲人 Yu Hui Zhu（圣安娜高等研究学院，Scuola Superiore Sant'Anna），系统分析现代分支预测单元（BPU）的资源共享与争用，识别出可操纵分支历史缓冲（BHB）的新机制。针对 Spectre-BHI 之后的 BHB 清洗与特权切换隔离等缓解，以 Arm Cortex-A72 的 bias-free 分支预测为突破口：分支状态表（BST）默认把分支归类为偏向分支，直到 BST 捕获不同结果；攻击者用蹦床片段的地址别名让 bx_evict 运行时逐出 bx_prime 的 BST 表项，迫使非偏向分支被重新归类为偏向分支，BPU 据此混淆两条执行流并错误预测分支目标，实验显示间接分支总能触发逐出、条件分支仅在 taken 时触发，据此构造 BiasScope 侧信道（监测分支是否 taken）与 Spectre-BSC（操纵 BST 表项劫持预测）两类攻击。（YouTube EPLpw64_YRyMg，[10-390]，L1）
- 〔会议不详〕Spectre-BHS 攻击族与 Chimera eBPF 漏洞利用。级联投机执行中未确认的分支结果也被写入 BHP，单个 Spectre V1 误预测可级联污染后续分支预测；BTB/BHT 逐出与仅记录 taken 分支的路径历史寄存器（PHR）之间的混淆，使"分支因逐出被遗忘"与"分支存在但未 taken"不可区分，构成 Spectre-BHS 攻击族，所有被测处理器均表现出该行为（但 AMD/Intel 对内核态间接分支预测有限制）。再利用 indirect BTB 无预测时的 PC 回退预测机制绕过 eBPF 验证器：在互斥基本块之间插入 BHB shuffle 分支并在攻击时令其成为投机窗口内唯一 taken 的分支，迫使后续指令走 PC 回退预测、从而对 gadget 单独训练，即 Chimera 攻击；除 Cortex-A72 外所有被测处理器均实现数据泄漏，Cortex-A76 泄漏率最高。（YouTube EPLpw64_YRyMg，[390-768]，L1）
- 〔USENIX Security（推测）〕PAX：面向 Linux 内核的权限检查静态分析框架与 Q-IR 间接调用解析。报告人自我介绍为来自 Ocean Tech 的 Tong（导师为 Dong Li 与 Chang Huijun 博士），指出 Linux 有 DAC、38 项 capabilities 与 LSM（约 190 个安全钩子）三种权限控制模型，但检查点以 ad hoc 方式加入，存在缺失检查、不一致与冗余检查问题，例如经 procfs 的 comm 写入需过 security_file_permission 检查，而经 prctl 直接调用 set_task_comm 可绕过该检查。为枚举用户可达路径需先构建过程间控制流图（ICFG），而 Linux 4.18.5 有约 11.5 万个间接调用点：基于函数签名的类型法不精确（write 与 read 签名相同会连错边），SVF 等高级指针分析在 1600 万行内核上不可扩展，拆分内核又会破坏健全性。为此提出 Q-IR：利用内核良定义接口（如 file_operations）分两步解析间接调用，静态与动态地收集函数指针所有可能目标，可解决约 90% 的间接调用，精度优于类型法、可扩展性优于 SVF。（YouTube EPLqGYzE5BVSs，[10-550]，L1）
- 〔USENIX Security（推测）〕特权函数识别、评估结果与问答。在 ICFG 上以用户可达为前提，用权限检查函数调用点支配（dominate）另一调用点的性质识别其保护的特权函数，再反向分析到系统调用入口，若路径上无权限检查调用即报警；实现基于 LLVM 并用 WLLVM 生成单一 .bc 文件，在默认配置（约 240 万行）与全配置（约 1600 万行）两种内核上评估。PAX/Q-IR 检出 21 个 bug（类型法同为 21 个、SVF 法仅 6 个，因后者 ICFG 不健全），且告警数量远少于类型法，共发现 36 个权限检查 bug 并产出可供开发者使用的权限检查函数与特权函数清单。提问环节中 John Criswell（罗切斯特大学）问及调用图分析是否利用内核全局结构初始化后只读的特性，Mohamed Talabi（UC Irvine）问函数指针多候选时如何选择。（YouTube EPLqGYzE5BVSs，[550-1186]，L1）
- 〔FAST（推测）〕微服务能否推动工作负载感知的存储管理复兴：动机与研究分解。报告人 Pranav Pandhari 介绍这是 Emory University 与 IBM Research 的合作工作，关注微服务架构下采用远程分布式存储基础设施、每个微服务自管卷时的存储影响（优于对象存储，且不把微服务绑死在存有其数据的本地计算节点上）。研究分两部分：工作负载刻画，对比单体应用与微服务化应用的存储负载，假设因微服务只做简单任务、基于访问模式的负载指标在微服务侧更稳定；以及自动调优组件，按使用卷的容器负载自动调优存储卷，因为微服务不仅自管卷还可被动态供给。（YouTube EPLv0EXqIPAus，[8-181]，L1）
- 〔FAST（推测）〕以 IO 缓存为案例的卷配置实验与 Kubernetes 原型设计。应用采用 Docker 容器与 Kubernetes 编排，计算节点上的 IO 缓存可带来低延迟本地内存访问并减少对存储服务的网络请求，缓存按持久卷分配、大小由微服务负载决定。用 ARC 与 LRU 在真实客户数据库部署的两个虚拟机负载上对比共享与隔离缓存，共享缓存命中率大幅落后于均分的隔离缓存；进一步评测不同缓存划分比例，发现按负载定制比例优于均分，说明需要良好的负载分析机制来用好计算节点上有限的缓存。最后给出工作负载感知存储配置与调度的初始设计：collector 按持久卷收集指标，recommender 生成卷配置建议，Kubernetes 部署微服务时读取建议配置存储，调度器据此判断节点是否有足够内存放置 IO 缓存。（YouTube EPLv0EXqIPAus，[181-352]，L1）
