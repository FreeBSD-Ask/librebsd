# 321.4.33 〔NSDI推测〕互联网拥塞控制异构化呼唤性能隔离新目标演讲者指出当下最流行的Cu

- 〔NSDI（推测）〕互联网拥塞控制异构化呼唤“性能隔离”新目标。演讲者指出当下最流行的 Cubic 与 BBR 同瓶颈竞争时极不公平（2019 年研究显示单条 BBR 流可与多达 16 条 Cubic 流竞争仍固定占 35–40% 链路容量），SIGCOMM 2024 社区讨论与 IETF 因此重审现代部署性标准；其此前测量研究发现不同网站、不同区域甚至同一网站的不同资产使用不同算法（Twitch 视频用 BBR、静态资源用 Cubic；Amazon 在俄亥俄用 BBR、在印度用 Cubic），根因是各算法对吞吐-时延权衡取向不同（Cubic 灌缓冲换吞吐、Vegas 压时延），故论文主张以“近似性能隔离”为现代互联网目标，让各流不受竞争对象影响地维持期望的权衡点。（YouTube EP41NN8Wlckos，[18-510]，L1）
- 〔NSDI（推测）〕Santa：P4 交换机上的“善恶名单”多队列 AQM。由于互联网流太多而队列太少，Santa 通过周期性“洗牌”实现近似隔离：新流随机入队后观察其 sojourn time（驻留时间）作为带宽占用的代理，抢带宽的“淘气”流上调至吞吐型队列、让带宽的“乖”流下调至时延敏感队列，控制面每轮决策、数据面（P4）维护队列指派与带宽跟踪，另设专属 mice 队列照顾过短流，各队列带宽与所辖流数成比例；实验显示 9 条长流（Cubic/BBR/Vegas 各 3 条、每 5 秒洗牌）经 Santa 后操作点位移极小，单队列退化为 FIFO、队列足够多时收敛到公平排队，P4 实现已开源。（YouTube EP41NN8Wlckos，[510-939]，L1）
- 〔会议不详〕把“自治”延伸到客户端：100MB 应用的共性研究。演讲者（NSDI 论文 Embassies 团队）从 XKCD 漫画切入：Web 服务器因厂商掌控全栈并自负修补（如 Heartbleed 由 Flickr 自行修复），用户端无需为此操心，而 Embassies 用 pico process 把整套软件栈（含 TCP/HTTP 栈与图形库）以 IP 通信隔离地发往客户端，使客户端几乎没有可被攻破的公共软件；但随之而来的是应用从数百 KB JavaScript 膨胀到中位数约 200MB 且失去可信缓冲缓存。对 100 个交互式桌面应用的调研显示共性充足：缓存 6 个应用后装第 7 个仅需约 40MB，聚焦快速启动所需的 startup set 后单应用中位数仅 64MB，应用间差异可压至 MB 量级、其余后台流式传输。（YouTube EP44_PhrGtEL4，[10-531]，L1）
- 〔会议不详〕无 fork/exec、不信任内核下的数百毫秒启动。启动流程为：运行中的应用经 DNSSEC 之类机制解析目标后取回签名 boot block，内核 instantiate 仅验签并创建进程，boot block 把镜像 hash 发给不可信缓存进程，用 Merkle tree 配方命中共性块、其余自源站或 P2P 邻机获取，再以 IPv6 jumbo frame 单包经内存重映射送回应用并验 hash；应用镜像打包成带 Merkle tree 配方的 Zarr 式文件，按重尾分布（“大象与老鼠”文件）把小文件灌入大文件尾部空隙以减少填充浪费，并用依赖内核密钥的 VMAC 把 100MB 验证从约 400 CPU 毫秒降一个数量级；WebKit 与 GIMP 等应用热启动（缓存全命中）增量不超过约 100 毫秒、warm 情形也在数百毫秒内，证明“百 MB 应用即点即用”可行。（YouTube EP44_PhrGtEL4，[531-1132]，L1）
- 〔NSDI〕可编程交换机上 sketch 集合的跨 sketch 组合优化。主讲人 Sun（与 CMU、波士顿大学、微软研究院合作）指出网络测量需要 top-k 流、SYN flood 与端口扫描检测、熵估计等多样任务，固定功能交换机上的 NetFlow 采样精度低、开销高且不灵活；在可编程交换机上运行 sketch 集合（ensemble）时，其 NSDI 前作 SketchLib（转写音 Sketch Clip）只优化单个 sketch 实例、硬件资源随实例数线性增长，无法同时满足通用性、低资源与高精度三要求；本文提出跨 sketch 优化思路，设计五个优化构件加自动代码生成模块，使一个 ensemble 可并发运行多达 18 个 sketch 实例并节省至多 45% 硬件资源。（YouTube EP46lyJglnyBg，[13-497]，L1）
- 〔NSDI〕构件细节、策略搜索与 Tofino 评测。优化构件包括：同一 flow key 定义的实例间复用 hash 结果（hash 单元从 6 个降到 3 个，不损精度）、不同 flow key 时用 XOR 组合生成哈希（3 降到 2）、以及跨实例共享计数器数组（行数 9→4、SRAM 块 25→13，单个任务分到更多内存精度反升）；策略搜索空间巨大，利用各优化只作用于不同工作流步骤（哈希计算、计数器更新、重 key 存储）的独立性做搜索空间分解，逐组求最优再拼接即得全局最优；在 Tofino 交换机上用 CAIDA packet trace 评测 10 种 sketch 算法组成的 4 个 ensemble，优化后更多原本不可行的 ensemble 变为可行且精度保持或提升。（YouTube EP46lyJglnyBg，[497-1019]，L1）
- 〔USENIX Security 2021〕安全群组消息中的跨群组效应与事后妥协安全（PCS）。主讲人（转写音 Conrad Kobrook）与 Cas Cremers、Britta Hale 合作分析两种群组消息范式——以一对一连接构成群组与群组状态各自独立——在 PCS（受攻陷方能够自愈的协议性质）下的表现；通过 Alice（CEO）手机在机场被攻陷的机密性场景演示：其下一条全员消息附带的更新在一对一范式下连带治愈了 A–B 子群，而独立群组范式下 A–B 群组密钥依旧泄露，Bob 后续的密约消息在两种范式下安全性截然不同，论文据此用更多场景揭示两种范式的 PCS 弱点与差异。（YouTube EP489YHv_QkUk，[9-300]，L1）
- 〔USENIX Security 2021〕签名密钥治愈的设计空间与 PCS-Sig。Britta Hale 部分梳理签名密钥更新选项：按群组治愈需逐一排查群组、更新任一密钥即全量更新会泄露群组活动信息且不保护未来新建群组、周期轮换仍不解决新群组问题；最优组合是全局签名密钥加每群组本地密钥、并以周期性对称机密性密钥更新配合；据此定义事后妥协安全签名（PCS-Sig）安全实验，刻画被动敌手阶段下密钥更新之后的伪造不可行性，并给出“新密钥对以旧密钥签名加标签”的示例构造，在 PCS-Sig 下实例化与证明。（YouTube EP489YHv_QkUk，[300-631]，L1）
- 〔会议不详〕Flightplan：数据平面解聚（data plane disaggregation）新范式。宾夕法尼亚大学的 Nick Sultana 代表团队介绍，当前“一个数据平面程序映射到一个设备”的范式使软件定义网络重新被硬件束缚，只能使用单台设备的资源而非网络整体资源；解聚范式把数据平面程序视作资源感知的虚拟数据平面，分析资源需求后拆分为子程序并映射到异构硬件（其测试台三类硬件在吞吐、成本、功耗上画像各异），同时需应对分布式系统的一致性、间歇性故障与调试问题；Flightplan 系统是该问题的候选解，通过让流量绕道经过可渐进推进计算的各数据平面来执行解聚后的程序，且不改变语言或硬件以利推广。（YouTube EP4921HaO1tew，[17-419]，L1）
- 〔会议不详〕Flightplan 的抽象、规划算法与评测。系统名取自符号 AI 的规划（planning）思想：P4 源码中以段注解（segment annotation）标出可切分的“接缝”，资源依赖由 Flightplan 代码分析器自动抽取为规则并喂给规划器，硬件能力也以规则形式刻画以捕捉异构性，另有在数据平面在线做故障检测与处理的轻量类 OS 运行时；经测试台实验与仿真评估，激活程序的不同部分可缓解故障并提升性能，不同规划方案的对比显示即便使用传统旧硬件也能从解聚中获益，多程序多运行时并存的仿真（论文图 7、9、10）与浏览器在线 demo 正在筹备。（YouTube EP4921HaO1tew，[350-694]，L1）
- 〔会议不详〕解耦存储之上的查询引擎设计：Snowflake 生产负载洞察。主讲人（转写未记名，来自 Snowflake 团队）指出 shared-nothing 架构因计算与持久存储紧耦合，导致硬件-负载失配（如为 50 盘 20 CPU 的负载需配 25 台 VM、浪费约 80 CPU）与弹性差；Snowflake 采用 virtual warehouse 抽象，把用户数据放在 S3 等远程存储，并用与计算同置的 ephemeral storage（DRAM→本地 SSD→再溢出到 S3 三级）交换延迟敏感的中间数据；基于 14 天约 7000 万条生产查询的分析显示中间数据量与 CPU 消耗、持久读取量相关性弱、难以预先判断。（YouTube EP4CYNxisz3d0，[5-605]，L1）
- 〔会议不详〕仓库弹性、按秒计费冲击与资源共享方向。Snowflake 用预热 VM 池加 lazy consistent hashing 实现扩缩容：扩容新增节点后，等真正读取被重映射文件的任务到达时直接从 S3 读取并回填该新节点缓存，避免大量缓存重洗；生产数据显示约 20% 仓库使用弹性、最大缩放可达 100x，但弹性粒度显著粗于负载变化，系统级 CPU/内存/网络利用率仍有很大提升空间；云厂商转向按秒计费使预热池日益不经济，故只剩资源共享模型一条路，其可统计复用需求提升利用率，但带来共享缓存（缓存条目无预知寿命不可抢占）与跨租户干扰等隔离挑战，需要租户私有地址空间等机制；7000 万查询统计的数据集已开源。（YouTube EP4CYNxisz3d0，[620-1190]，L1）
- 〔SREcon〕（推测）Doorman：全球分布式客户端限流的动机与设计。主讲人 Jos Visser（Google，马萨诸塞剑桥）讲述 YouTube 播放计数批处理向 MySQL 发出的 insert 超过其承载导致频繁告警的问题，催生让客户端自协调限流的 Doorman；系统可对 MySQL 分片、RPC/Bigtable tablet server 等有限容量的共享资源按可插拔公平算法（fair share 为 O(n^2)、proportional share 为 O(n)）发放容量租约，客户端库覆盖 Python、C++、Go（Java、Lisp 在计划中），经 gRPC 与 Go 写成的 Doorman 服务端通信，并借观察调用方 wait 操作模式推断客户端期望容量，估计误差约 5%。（YouTube EP4Ipwgcdu-sQ，[9-1841]，L1）
- 〔SREcon〕（推测）Doorman 服务器树、无状态容错与开源。为全球部署，Doorman 采用根/洲/集群级服务器树做容量收敛，新客户端申请大容量时从地球另一侧偷取闲置容量，三节点树约 30 秒即可重新平衡；每个节点由三台以上服务器经 etcd 选主（主发现通常两跳）、不做状态复制也不落盘，主失效后通过 learning mode 在租约期（典型 5 分钟，刷新间隔 5 秒）内向客户端回放其既有容量重建状态；safe capacity 防止全网宕机时流量全停，实验图显示容量分配贴合需求并能在总需求超过 1000 QPS 时精确封顶，代码已开源并提供 Doorman shell，由 Google 悉尼等三地三人维护。（YouTube EP4Ipwgcdu-sQ，[957-1921]，L1）
- 〔NSDI〕Pequod：原生支持物化视图的分布式应用缓存。主讲人（哈佛与 MIT 合作成果）以 Twitter 时间线（读频率约为新帖的 100 倍）论证应用缓存应内建物化视图：key-value 缓存快但更新维护复杂、数据库物化视图简单却难担海量读写的双重负载；Pequod 通过把列塞进键的 cache join（支持 get/put/有序 range scan 及安装物化视图的 join 操作）在缓存中实现部分且动态物化，并用 eager（新帖自动复制进时间线）与 lazy（新订阅下次查询时更新）两类增量维护，还可作为 write-around 缓存窥探数据库写来更新基表。（YouTube EP4Ks0P4SnPnY，[10-799]，L1）
- 〔NSDI〕Pequod 评估、扩展性与问答。对比实验中 Pequod 做到不差于 Redis/Memcached 且因 cache join 用单 RPC 处理新帖而略胜，去掉 cache join 的版本反而低于 Redis；在 Amazon EC2 上两阶段部署把 compute server 从 12 台扩到 48 台带来 3 倍吞吐提升（理想 4 倍），开销来自 base/compute 服务器间的数据复制与订阅元数据管理；Q&A 讨论了冷缓存延迟尖峰、整段淘汰策略与最终一致（真实 Twitter 新推文一般 1 秒内触达）；相关工作包括 Xu 等在 SQL Server 实现的动态物化、用边缘节点吸读的 DBProxy，以及加入物化视图的分布式键值存储 Peanuts。（YouTube EP4Ks0P4SnPnY，[800-1524]，L1）
- 〔会议不详〕mRPC：把 RPC 实现为托管系统服务。主讲人 Jingrong（与 Yongji 合作的多机构联合工作）指出 RPC 占 Google 数据中心 95% 以上应用流量，而传统库内 RPC 实现难以满足可观测性、策略执行与在线升级（打补丁需重编译重启应用）等可管理性需求；sidecar 代理在 L4 截获流量使每次 RPC 的编解码步骤增至三倍，评估中 Envoy 加 gRPC 使 P99 尾延迟升至 2.8 倍、吞吐近乎减半；mRPC 将精简的 shim 库经共享内存队列连接常驻系统内、被所有应用共享的 mRPC 系统服务，在 L7 完成策略处理后再做一次 marshaling，兼顾可管理性与性能。（YouTube EP4L1l-djnDNw，[13-408]，L1）
- 〔会议不详〕mRPC 的实现挑战与评估。Yongji 介绍两大挑战：动态绑定——不可信应用只传 RPC schema，由服务端 schema generator 生成 marshaling 模块、应用侧仅生成发送描述符的前端桩；共享内存管理——消息放共享堆、经 RPC 描述符传递，在执行访问控制等内容型策略前用 copy-on-write 把消息复制到私有堆，防止应用篡改绕过策略。框架用 Rust 实现约 3.2 万行：TCP 大 RPC 吞吐较 gRPC+proxy 提速 3.1 倍，RDMA 小消息时延较 eRPC 方案提速 1.7 倍，访问控制策略开销仅约 6%，微服务基准 DeathStarBench 端到端时延降低 2.5 倍。（YouTube EP4L1l-djnDNw，[408-888]，L1）
- 〔FAST〕（推测）DPES：跨层动态编程-擦除缩放延长 NAND 闪存寿命。主讲人 Jiyoung Jung（首尔国立大学，与 Sanghyun Han、Sungjin Lee 及导师 Jihong Kim（转写作 Jiyoung Kim）合作）用 Flashman（转写作 Freshman）漫画讲解：NAND 容量每两年翻倍，但近年 endurance 大幅下降，企业级存储的总写入量与寿命未如预期增长，成为可持续增长的瓶颈；擦除操作中高擦除电压是单元损伤主因，改用低擦除电压和慢速擦除可减少单元损伤，据此提出擦除电压缩放与擦除时间缩放，并定义有效磨损（effective wear）指标——3000 次 P/E 循环下默认配置累计磨损为 3000，最小电压加慢速擦除可降至 1200，寿命可提升逾两倍。（YouTube EP4LAoHgdbieE，[10-790]，L1）
- 〔FAST〕（推测）DPS 感知 FTL 与实验评估。设备侧被改造为支持多擦除电压、写模式（0-4 共五档）与擦除速度模式，DPS 感知 FTL（OreEPTL）依据缓冲利用率及含垃圾回收拷贝/擦除时间的有效利用率动态选择写模式与擦除模式，浅擦块编程需更细粒度控制，必要时用惰性擦除（lazy erase）短时低压补擦；六条企业级 trace 上平均寿命提升 69% 而写吞吐下降不足 2.2%，惰性擦除每千次擦除不足一次；擦除时间缩放最多再增 18% 寿命、吞吐代价约 2.1%。Q&A 讨论了隧道氧化层损伤物理、相邻单元耦合对窄阈值分布的制约及随写模式动态维护读阈值。（YouTube EP4LAoHgdbieE，[790-1767]，L1）
