# 321.4.153 〔SREcon〕Jetcom的分布式追踪实践后半团队改用极简wire规范与Ope

- 〔SREcon〕Jet.com 的分布式追踪实践（后半）。团队改用极简 wire 规范（与 OpenTelemetry 同名的 trace ID、operation name、库自动计算的 tags），把元数据以事件而非 HTTP 头承载避免业务敏感信息入头与全局可变状态，并利用 F# computation expressions（单子语法糖）在每次 bind 自动计算追踪数据（reader monad 模式）使开发者只改一处、无需换类型签名；同时为 Kafka、内部事件流、内部项目与复制系统、Azure HTTP 数据库提供多载体支持，DevOps 的 Go、数据组的 Scala、Nginx Lua 用户则把遥测事件写本地文件，由守护进程转发 Kafka。项目 X-Ray 以 Filebeat 复制日志到 Kafka，索引进微软 Cosmos DB 并借 change feed 构建投影服务，每 5 分钟把拓扑快照推给 Splunk 供窗口化告警，另有按 trace ID/商户查询的 API 与迭代三版的仪表盘；作者认为未来追踪应"对开发者更少可见、更开箱即用"，schematization（schema 是节点间的边）将成关键，Jet 会把项目开源。问答讨论了 operation 字符串的命名空间冲突，回应是短期靠 service name union 去重，长期靠 type provider 或 Avro schema 等约定。（YouTube EPQ407GWi-_0U，[1095-2036]，L1）
- 〔SREcon〕为什么分布式系统如此之难（前半）。主讲人 Denise Yu（多伦多 Pivotal Cloud Foundry 软件工程师，以科技涂鸦闻名，正与 Steve Smith 合著儿童版《A to Z of Continuous Delivery》）从单体数据库时代的客户端/服务器架构讲起：IT 从成本中心变为业务差异化能力后，数据驱动分析、机器学习与数据量/速度的增长推动了纵向扩展、云计算（AWS/Azure/GCP 与 vSphere）和水平扩展，带来可扩展性（分片）、可用性（副本）与延迟三种诉求。现代分布式系统以 shared nothing 架构为主，加上不可靠网络上的消息传递与部分失败，使推理异常困难；作者引用 Martin Kleppmann《Designing Data-Intensive Applications》与 Sun Microsystems 的八大分布式谬误（网络可靠、延迟为零、带宽无限、网络安全等），并把认识论（基础主义与融贯主义）和拜占庭将军问题引入"何为可信"的讨论。随后进入 CAP 定理：C 实为线性一致性（linearizability）这一极窄定义，要求近乎即时且全局的复制（受光纤速度上界约束），最终一致不算数；A 亦非二元，网络延迟使人难以区分节点无响应还是慢，只能设超时（新系统缺历史数据时如掷骰子，Cassandra 可自学）。（YouTube EPQ4p-2WIS0nQ，[11-839]，L1）
- 〔SREcon〕分区容错之必然与"人比机器更难达成共识"（后半）。CAP 定理 2000 年由 Eric Brewer 在 PODC 大会主题演讲提出，分区容错 P 无法被设计"愿走"——Google 集群第一年会经历 5 次机架故障、3 次路由器故障与 8 次网络维护，另有鲨鱼啃咬海缆（2015 年后已因凯夫拉包裹而缓解）、多租户 VM 突发互扰、stop-the-world GC、人为剪断光纤等成因；分区发生时只能二选一：各侧继续读写（牺牲线性一致性）或停止服务（牺牲可用性）。缓解手段包括 leader-follower 模式的人工 failover 与 Raft 等共识算法（Raft 得名于"一堆日志"而非缩写），但更难的是让人达成共识：系统远超个人脑容量，需靠事故分析等"信息丰富的代理物"在无指责、以学习为目的的环境中校准心智模型。以三哩岛事故与挑战者号 O 形环（设计区间 40-90 华氏度、发射当日仅 28 度、异常多年来被容忍）说明"偏差正常化"（normalization of deviance，并致谢 Foon Turing 的原始分析），最后呼吁为包括人性因素在内的整个系统做设计，依靠共情这一比 Raft 更强的超能力。（YouTube EPQ4p-2WIS0nQ，[848-1705]，L1）
- 〔SREcon〕度量一年中的事故：从单次复盘到跨事故分析。主讲人 Vanessa（Inova 弹性（resiliency）团队技术经理、Resilience in Software Foundation 董事，十年事故全生命周期工作与多家组织教练经验）指出事故总数、行动项数、持续时长等裸数字因缺乏上下文而毫无助益，主张在"从事故中学习"（learning from incidents）基础上演进为跨事故分析（cross-incident analysis），以模式识别支撑更大举措并帮助团队与公司达成目标。她对比 ITIL 式问题管理、五个为什么与"根因是人为失误、别再犯"式复盘的局限——制造虚假安全感甚至有害；转向 blame-aware、以学习为中心的叙事式复盘（收集 Slack/PR/工单数据、建时间线、多人协作复盘、按领导层/技术团队分别输出收获），才能挖出"老收购团队权限缺失拖慢项目并导致倦怠"这类深层收获。规模化的困难在于：叙事时间线从 Slack 到 Jira 拷贝粘贴极耗时、工程师缺乏访谈与定性数据分析技能、叙事报告不可查询，且小毛刺与年度最大流量日前一天弄坏依赖服务的事故难以互相比较。（YouTube EPQ69WND8YHag，[16-800]，L1）
- 〔SREcon〕Inova 的跨事故分析实践与"给数字以上下文"。Inova 建 4 人专职团队，对所有重大及敏感（法律/安全影响）事故做 blame-aware 学习复盘，行动项仅在会议末尾限时讨论并要求被指派者认可，另引入"建议 vs 承诺"区分跨事故反复出现的改进；季度复盘刻意嵌入季度规划使建议落地，工程、运营、市场、法务与合规都买账——她最推荐的单一改动就是邀请更多部门的人参会。报告工件在 Jira 混合定量字段（告警/解决/确认时点、触发原因）与叙事字段，形成"metrics with context"；分析上她戏称"蔬菜加肉酱"法：先看受影响最多的客户旅程，再下钻成因（不稳定供应商、重构关键旅程、feature flag 供应商与流程等），某年端分析发现大量 SLO 与告警类行动项后设立季度专项建 SLO。反模式包括"行动项工厂"（修复永不被优先、侵蚀信任）与把 MTTR/MTTX 等均值当目标导致刷数字（引 Courtney 的分析），建议从小处着手（一个小团队、一个季度、先提升复盘质量）、把数据当方向性信号并持续争取盟友而非与 CTO 开战。（YouTube EPQ69WND8YHag，[799-2223]，L1）
- 〔会议不详〕LightShield：兼顾虚拟机级隔离与容器性能的用户态微内核。主讲人 Casey Monacall（得克萨斯大学阿灵顿分校二年级博士生，合作者含空军研究实验室的 Nathan Doherty、Marcus Pendleton 与该校 Hui Lu 博士）从微内核与宏内核的教科书对比切入（宏内核性能好但代码库难维护，微内核可如 seL4 般形式化验证却更难开发），指出微服务容器部署虽轻量但共享宿主内核，暴露 400 余个系统调用的宽攻击面，恶意容器可利用内核漏洞越狱；现行"容器入 VM"（如 KVM 沙箱）方案隔离强，却因每容器整套客户 OS 带来高 CPU、大内存与 I/O 延迟，本质是以效率换安全。LightShield 的核心思想是新的用户态微内核架构：把客户内核解耦为一组用户态微内核服务（网络、文件系统等），应用进程经快速 IPC 与之交互，与宿主内核之间仅剩几十个系统调用的薄接口，主要内核功能全部留在用户态，性能敏感任务可经 DPDK 等库直接访问设备，服务可独立开发、扩展与替换。（YouTube EPQ6goGLQ762o，[18-519]，L1）
- 〔会议不详〕不可委派系统调用、内核旁路与实现评估。针对必须与应用同地址空间执行、无法转交用户态服务的系统调用（mmap 与 fork、clone、exit 等），LightShield 在不修改 Linux 的前提下用 ptrace 陷获并监控这些"不可委派系统调用"，由核心微内核服务做健全性检查与校验后放行，构成纵深防御；网络等高性能场景采用部分内核旁路，以 TAP 虚拟设备配合 DPDK 使用户态网络栈保留低内核参与度又能多容器共享物理网卡；对遗留应用用 LD preload 注入 libsyscall intercept 库，经内联钩取与二进制重写拦截系统调用并经共享内存缓冲 IPC 重定向到用户态微内核服务。实现上以 F-stack（DPDK 之上）做用户态网络栈并改其主循环监听 IPC 队列、内存映射文件支撑模拟 x2 风格存储栈的用户态文件系统，用户到宿主系统调用接口缩减到 22 个、核心服务约 7000 行代码；在第四代 Intel Xeon + 96GB DDR5 测试机上与 Docker、Firecracker、gVisor 对比，getpid/read 系统调用延迟、FIO、UDP/TCP 与 YCSB(Redis) 基准总体与基线相当，普遍快于基于虚拟机的方案（TCP 因缺 GRO 等特性稍弱，UDP 优势明显）。（YouTube EPQ6goGLQ762o，[533-1053]，L1）
- 〔会议不详〕利用风险画像早期发现被野外利用的漏洞。主讲人 Robbie 报告论文《From Patching Delays to Infection Symptoms: Using Risk Profiles for an Early Discovery of Vulnerabilities Exploited in the Wild》（与密歇根大学 Chaojie Zhao、Mingyan Liu，哈佛大学 Yang Liu，UIC 的 Polly 及墨尔本大学 Tudor Dimitrescu 合作）：补丁安装延迟（据估计漏洞利用代码出现时中位数仅 14% 易感主机已打补丁，WannaCry、NotPetya、Equifax 事件的底层漏洞早已发布补丁）为攻击者留下机会窗口，而已被利用的漏洞只是少数，若能检测/预测被利用状态即可优先部署补丁；现有工作要么只用内在 CVE 属性（预测力弱），要么爬社交媒体（提前量仅数天且依赖人工）。方法把漏洞类比为病毒 strains、风险行为类比为易感亚群、感染症状类比垃圾邮件：以 ISP 为边界聚合特征，比较症状相似性与风险行为相似性（patching 信号）之间相似性是否传递来获得统计证据，用社区检测（community detection）量化两者关联。数据为五个垃圾邮件黑名单（症状）、Semantics Mine 数据集 7 个应用（5 款浏览器、Adobe Reader 与 Flash Player）的补丁数据加 NVD CVE（风险信号），真值含 56 个已被野外利用与 300 个未被利用的漏洞。（YouTube EPQDNr8Ty0HwU，[10-694]，L1）
- 〔会议不详〕社区特征、随机森林与提前 25 天的检测。在漏洞披露后 10 天窗口内计算 ISP 间成对相似度构成加权图，仅对症状做一次社区检测，用症状社区结构上风险信号的簇内/簇间（intra/inter-cluster）相似度之差作为"community 特征"输入有监督分类器，与原始/直接特征（省略社区检测、预测力更弱）及 CVE 内在属性（描述 token、CVSS 评分）组合训练随机森林（五折交叉验证、20 次平均）。最优组合达到 90% 真阳率 @ 10% 假阳率、96% AUC（社区+内在特征即 95% AUC，社区特征单独 76%，内在特征与实测数据互补）；而利用报告的中位时间达 35 天、80% 超过 10 天，等效于比现有检测提前约 25 天，把窗口移到披露日还可发现疑似 0-day：Adobe Acrobat Reader 一例被正确识别，Flash Player 一例虽数月后才被报告被利用、系统在披露当日已见利用迹象。局限在于垃圾邮件并非完美的感染代理（非感染性租用服务器也会发 spam）且聚合会平均化信号；问答讨论了优先修复被利用漏洞是否会让其他漏洞被遗忘（作者承认需实际部署才能确定）与基于严重度/易利用性的先验优先级（对应 CVSS 等内在属性，单独预测力不强）。（YouTube EPQDNr8Ty0HwU，[695-1379]，L1）
- 〔SREcon（推测）〕运营就绪清单与强制功能（forcing functions）。主讲人（十年 SRE，长期供职早期初创企业，公司 7 个产品正迁往新云平台而 SRE 人数被工程师约 100:1 碾压）分享提升可靠性姿态的三个章节。第一章"缺乏想象力的清单"：众包整理的运维能力清单不过是一张电子表格，按控制面/数据面等支柱组织（能否在事故中即时访问调度器、服务网格、密钥、队列，本地开发，可观测性，on-call 轮换，每周运维评审等），并按产品生命周期维度切分为 pre-availability 与 post-availability（含常被遗忘的 EOL 阶段），以产品转向 GA 为锚点对客户团队做运营就绪评估，立即修的当场修复。她援引工地安全标语的研究（标语保存状况与数量影响遵从度）说明：清单太长或过时会失效；这些清单/评估是组织心理学意义上的强制功能，能在组织快速扩张、老人离开时维持实践惯性，也是良好的反馈回路与用户共情练习，但代价高昂——算下来绕组织一圈并完成全部服务认证需要约 24 个月，且口头达成的共识在人走之后往往不落地。（YouTube EPQIZg1wZ26Xs，[19-927]，L1）
- 〔SREcon（推测）〕持续检查、可靠性数据平台与可靠性评审。第二章为持续检查：先做 MVP——各仓库以流水线提交 YAML 元数据（服务可见性/负责人/描述、runbook 与仪表盘等运维工件，以及 GDPR 等安全/GRC 数据）到 meta repo，在静态站点上渲染检查结果，虽只覆盖 70-80 项清单中的 5 项但验证了自动认证可行，问题在于纯信任式元数据、元数据过时与只能看到 VCS 内数据；随后加倍投入构建可靠性数据平台：以检查（含修复指引、联系人及 informational/advisory/critical 严重级）为核心，采集器覆盖 VCS、GitHub、PagerDuty、可观测性、事故管理平台与调度器，采用轮询为主（约 80% 用例）、事件驱动为辅的模式，另有把结果外推到其他系统的分发器，多数据源引入了归属（attribution）难题，到 2023-24 年已自动完成 70% 的就绪评估。意外收获是 GRC 与安全团队成为大用户和贡献者、以及跨产品的"组合运营者"人设涌现。第三章是成功带来的问题：深度可靠性评审分架构（可扩展性、韧性、依赖、多区域）、平台采用与运维姿态、事故三大支柱，由 SRE 主导投入、团队需先提供架构图与业务上下文，痛点是"永远别说人家的孩子丑"带来的对抗性观感与结果难追踪。核心收获：抽象优于认证（一次采纳永久受益）、技术栈终将异构、要尊重运营者有限而宝贵的注意力，并坦承这一切由团队与客户共同建成、本人长期与冒名顶替综合征共处。（YouTube EPQIZg1wZ26Xs，[928-2070]，L1）
- 〔USENIX Security（推测）〕Delphi：卷积神经网络的安全推理系统。主讲人 Pratik（与 Ryan、Akshay、Wenting 及 Raluca Ada Popa 合著）指出客户端侧推理会明文暴露模型权重、服务端侧推理会明文看到用户数据，而安全推理要求双方只学到预测结果 m(x)、互不泄露其他信息。现有方案从全同态加密（FHE）到两方计算方案 Gazelle 仍远离原生执行性能：Gazelle 对线性层用线性同态加密（LHE）、对 ReLU 等非线性层用混淆电路，每次推理需 600 MB 通信、耗时 82 秒，对延迟敏感应用不可接受。（YouTube EPQMWBEFc3RK4，[8.0-380.9]，L1）
