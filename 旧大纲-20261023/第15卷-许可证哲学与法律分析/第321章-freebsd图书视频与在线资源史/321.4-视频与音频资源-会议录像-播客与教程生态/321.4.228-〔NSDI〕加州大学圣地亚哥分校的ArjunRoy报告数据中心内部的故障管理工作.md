# 321.4.228 〔NSDI〕加州大学圣地亚哥分校的ArjunRoy报告数据中心内部的故障管理工作

- 〔NSDI〕加州大学圣地亚哥分校的 Arjun Roy 报告数据中心内部的故障管理，工作在 UCSD 与导师 Alex Norton 合作完成，并在 Facebook 生产数据中心做了验证〔00:10〕。动机来自 2012 年他在 Facebook 实习的项目：查看采集于网络末端主机上的 TCP 指标〔00:40〕。他谈到当时与一位 Facebook 工程师的对话，对方说每隔一段时间会看到 TCP 重传，如果能把导致重传的是哪条链路找出来会更好〔00:59〕。困难在于大型数据中心网络里流量可能经过很多路径，你并不一定知道痛点在哪，而且组件数量庞大、故障率非零，看到的丢包也可能是网络故障所致〔00:59〕。理论上端点能感知故障并发出有针对性的告警，但实践中存在一类重要故障被称为 partial faults（也有人称 gray faults）：链路上的故障可能只影响经过该链路的流量子集、且只在间歇时间段发生，这既干扰“故障是否正在发生”的检测，也干扰定位故障在何处〔01:33〕。论文目标是：若发生 partial fault，能否快速把范围收窄到具体哪条链路〔02:03〕。gray fault 有多种成因——脏污的光纤连接器、TCAM 位错误或配置错误，甚至把光纤拉得太紧也可能诱发〔02:03〕。已有大量数据中心故障管理的前作都要应对规模问题，而今天的论点是：对某一类数据中心，规模本身反而能帮同时检测与定位故障〔02:58〕。他指出数据中心在负载均衡上投入了大量工程，并引用早前刻画 Facebook 数据中心流量的结果：从单台缓存服务器按目的地分组的流量分布几乎垂直，说明流量在网内极为均匀；抬到整个集群按机架对机相看，绝大多数流量集中在 web server 与 cache server 之间的两条带状区间，且同样没有明显热点〔02:58〕。设想是这种高度均衡的流量能简化故障处理：无错误时每路径表现应当相似，有错误则应出现明显劣于常模的离群路径，于是只要知道网内所有流量的网络路径，就能把流量表现与路径关联起来以发现故障〔03:52〕。实现上先解决路径信息：在 Fabric 拓扑里机架顶交换机只有一个、可免费得知，拓扑分为四个 aggregation 与 core 交换机平面，所以知道流量经过哪个 core 交换机基本等价于知道完整路径；方案是在每个 pod 的 aggregation 交换机上安装规则，按流量经过的 core downlink 标记报文〔05:02〕。但直接按路径比较流量表现会组合爆炸——单主机到某目的机架就有约一万条路径，而且这样比较也无法给出定位〔05:32〕。所幸在这种流量模式下，ECMP 路由不仅让每链路流量分布均匀，也让每链路字节数分布均匀，因此可以直接比较链路：他定义 equivalence set，即数据中心内承载名义相似负载、无故障时表现相似的链路集合〔05:56〕。这带来两个好处：比较次数从上万降到几百；按定义它能把故障钉在具体位置上〔06:26〕。他举例说明在 Facebook 拓扑里 equivalence set 的形态：单个 TOR 到 pod aggregation 层的四条上行链路在无错误时性能分布几乎相同〔07:05〕。指标方面，网内多数流量是 TCP，主机本就为拥塞控制跟踪若干指标——包括受丢包影响的拥塞窗口与重传、以及网络内延迟带来的往返时间，网络 I/O 系统调用在某些情况下也是流量丢失的良好预测器〔07:05〕。他接着说明 equivalence set 如何让这些指标可用：把指标按链路分组成分布后，只有链路故障才会在各链路之间造成分布差异〔08:05〕。他演示了在 aggregation 交换机到 TOR 的四条链路上注入故障的实验：在目标主机上用 iptables 规则随机丢掉一条链路上两百分之一的报文，结果显示三条正常链路的指标分布几乎相同，而故障链路成为明显离群点〔08:29〕；图中以箱线图呈现拥塞窗口在每条链路上的全流量分布，三条无故障链路几乎退化，故障链路的分布既在形状也在位置上发生偏移〔08:49〕。他在 web server 上重复同一实验，虽然各服务器的分布形状与位置不同，故障链路的离群性质依然清晰，这对拥塞窗口与 TCP 重传都成立〔09:49〕。为验证对真实故障也有效，他们在不注入故障的情况下监控流量经过 pod aggregation 交换机，选 30 台生产 web server 主机为样本，把连接 aggregation 交换机与 core 层的四条线卡作为 equivalence set，因每条线卡承载相同数量链路故构成有效比较〔10:18〕。1 月 25 日某条线卡发生软件故障：该线卡软件负责它与 core 层对等体之间的 BGP 路由，软件挂死后 BGP 路由超时、经该线卡的大部分生产流量被迁走〔10:41〕；几分钟后 Facebook 的生产监控因该线卡不响应 ping 而将其标记为故障，而他们的方案在软件挂死发生后约 30 秒就捕捉到了〔10:41〕。他展示的是故障发生 30 秒后的拥塞窗口均值曲线：其余三条线卡曲线彼此贴近，故障线卡的曲线在大量流量迁出后明显变化〔11:29〕。他特别强调：这不是“抓到故障”，而是抓到了故障的后果〔11:45〕。分类上他把问题表述为：集合中某条链路的重传率是否高于其他链路？这与“两条分布均值是否相等、或其中一条更大”是同类问题〔12:23〕。一元 t 检验可以回答，于是每台主机可独立判断某链路是否故障；但仅靠它会带来误报，而在有数万条链路的网络里误报无法承受〔12:58〕。他们的做法是再做一次离群分析：不问某链路是否被某主机标记，而问“是否所有链路被标记的速率相近、还是某子集被显著更高地标记”〔13:38〕。卡方检验可回答之，p 值接近 1 表示各链路被标记速率相近，接近 0 则表示存在某子集被显著更高地标记〔14:00〕。于是集中式分类器如此运作：汇总所有主机基于 t 检验的信息，再由运行卡方检验的控制器判定该链路是否整体故障，判定阈值取 p 值 0.05〔14:09〕。（YouTube EPYrlmxW8euNo，[10-878]，L1）
- 〔NSDI〕在数据中心内部的评估面临现实约束：虽然工作在真实数据中心环境，但它不是生产监控系统、只是原型，可观测面很小，仅仪器化了约一百台主机，因此未捕获任何真实故障〔14:57〕。评估方式是主动注入故障：构造多种故障场景考察系统能否应对，包括极小故障（极低丢包率）、并发故障、遮蔽故障（较大故障掩盖较小故障）与关联故障（硬件故障同时影响邻近多条链路），细节放在论文中，今天只讲极小故障〔15:33〕。拓扑是一个网络 pod、三机架生产 web server 主机、一台安装了故障注入交换机的设备，以从 pod aggregation 到 core 层的一批上行链路作为 equivalence set，并在其中挑一条链路注入不同强度的部分故障〔15:50〕。他报告了逐主机 t 检验在不同丢包率下的效果：从 2% 一直降到 0.05%，结果显示丢包率不低于 0.5% 时接近百分之百的主机能稳定检出；一旦低于 0.5%，每个 10 秒窗口内成功标记该链路的主机比例线性下降〔16:28〕。为缓解低丢包率下的困难，他们利用故障很可能在随后若干 10 秒窗口内持续存在这一事实，把多个窗口的分类结果在时间上聚合，让控制器运行更久以积累置信度〔17:21〕。于是存在一个权衡：对故障的敏感度与多久能得出结论之间的权衡。他给出控制器运行时长对卡方 p 值的曲线——横轴从 10 秒到 3 分钟，纵轴为 p 值，0.05 处有虚线判定线，低于该线即成功捕获〔18:09〕。在无故障情形下无论取哪种间隔，控制器都稳定输出接近 1.0，说明不会产生误报〔18:32〕。对 0.25% 丢包率的链路故障，10 秒间隔下第 95 百分位仍高于阈值、约百分之五的情形漏报，而 20 秒间隔可稳定捕获；对 0.2%，10 秒间隔已不足、20 秒则足够〔18:32〕〔18:56〕。随丢包率降到 0.15% 与 0.1%，分布进一步右移，即故障越轻微控制器需运行越久；即便在 0.1%（每千包丢一包）这么低的情况下，用两分钟间隔也有超过一半时间能检出〔19:09〕。他总结：当数据中心拓扑与流量具备某种均衡性时，可以在在线、轻量、与应用无关的前提下，把“是哪条链路出问题”定位到具体链路，而无需任何额外探测流量〔19:33〕。Q&A 中他补充：2012 年的实习往事已成往事〔20:29〕；针对 ECMP 本身不均衡可能误导运维者的质疑，他们曾在 UCSD 私有 k=6 fabric 上人为造成 ECMP 不均衡，系统会标记出那条平均表现开始变差的链路，但跨层级的不均衡传播更难处理、他们并未测试〔21:19〕；关于 fault 的定义他区分两类——一类是链路仍报告 up、仍在转发，但偶尔有部分流量丢失，成因可能是脏污连接器或配置错误；另一类是延迟问题而非丢包，例如配置错误引起的排队延迟〔23:15〕〔23:38〕。关于部署难点，最难的是获得所有流量的路径信息〔24:54〕；理想情况下希望交换机能在包头某几个比特上写入任意值，而 DSCP 只有 8 个比特且已有其他用途，IPv6 flow label 能提供 20 个比特、足以扩展到全网，论文也给出该能力缺失时获取路径信息的替代方法，代价是无法处理短流量〔25:26〕。被问及故障注入是否影响生产流量时，他说明注入只在被仪器化的主机上用 iptables 完成、范围仅限受测主机，而非在核心内制造故障〔26:25〕；至于如何排除观测只是巧合，做法是在一段时间内注入故障、再撤除，观察主机上报的“链路正常/异常”是否与注入时间窗严格对应〔28:35〕。（YouTube EPYrlmxW8euNo，[878-1747]，L1）
- 〔USENIX Security '19〕EnTrust 的出发点是：现行操作系统采用的 first use authorization 只在该传感器首次被使用时索取许可，挡不住应用之间合谋、借各自已有权限共同侵犯用户隐私；EnTrust 转而跟踪输入事件在协作程序之间的委托，把委托图交由用户显式授权，以此监管传感器访问〔00:10〕。演讲者 Giuseppe 来自宾夕法尼亚州立大学，联合英国 Alan Turing Institute、德国慕尼黑大学与语义研究实验室，工作由 Army Research Lab 资助〔00:24〕。抽象本身很熟悉：用户说出 take a selfie，语音助手转而依赖相机应用完成操作，相机应用再索取相机权限以取帧〔00:48〕；而应用可以 collude、语音助手也会打开新攻击面〔01:34〕。三类攻击依次为：camera app 实为木马，借 GPS 与麦克风权限记录自拍位置与短音频并外泄个人信息〔02:02〕；confused deputy，不可信语音助手诱导截屏服务在用户查看 secure notes 等敏感信息时截屏〔02:30〕；man in the middle，用户借助手存入支票，请求被 camera app 截获送往攻击者控制的远程服务器〔02:54〕，现场演示中 banking app 尚在用时相机应用里已出现同一张支票照片〔04:10〕。既有缓解各有硬伤：把输入事件与特定 UI 绑定（前后台、UI 上下文）并未建模输入事件委托〔04:36〕；按调用方下调被调用方权限会毁掉协作抽象〔05:20〕；去中心化信息流控制解决的是数据如何共享、而非如何访问传感器这一正交问题〔05:41〕；机器学习建模用户决策又以用户先拿到足够信息为前提〔06:03〕。假设为信任安全构建的操作系统、强制访问控制使用户态程序不能直接访问传感器、程序经沙箱隔离、提供双向 trusted paths；威胁为可从未知来源安装程序并在首次使用时授权、程序间可经 IPC 通信〔06:43〕，作者明确聚焦监管程序如何访问传感器、程序间数据共享与收集不在范围内〔07:23〕。机制上把输入事件建模为元组 E——生成上下文、接收该事件的源传感器（如触摸屏）、目标程序与时间戳——再模型化事件如何经 intent 委托给程序 Pj、Pj 又生成对目标传感器 D 的访问请求，结果即一张 delegation graph〔08:45〕。并发带来歧义：多个输入事件同时指向 pi 而它只发出一条 intent，该关联哪一个；多个 intent 指向 Pj 之后才发起操作请求，路径同样难定。作者观察到 events are consumed faster than they are produced，遂为每个程序排队并按序投递事件，即可判定哪个输入事件产生了该请求；若某 intent 并非由用户输入事件引起则直接丢弃，因为对特定输入而言它是无效委托路径〔09:59〕（YouTube EPYvUm3qUGepM，[10-616]，L1）
- 〔USENIX Security '19〕委托图生成并锁定委托路径后，EnTrust 用自然语言向用户呈现操作、传感器与执行该操作的应用标识，询问允许还是拒绝〔11:29〕，于是前述支票攻击在演示中被一个提示框拦下〔11:46〕。原型实现于 Android 并在真机上测试，围绕四个研究问题验证：其一，招募九名受试者发放预装七款应用与五个语音助手的设备试用七天，衡量新增授权带来的用户开销〔12:09〕；其二，用 Android compatibility test suite 对从 Google 商店精选的一千款应用验证向后兼容，并特意加入对延迟极敏感的增强现实游戏应用〔12:46〕；其三，用微基准测量构图、缓存、执行与歧义消解的开销以及内存占用〔13:22〕；其四，用实验室研究检验有效性——共招募六十名受试者分四组，两组跑常规 Android 的首次使用授权、两组跑 EnTrust，各组又分未预告与已预告〔13:56〕。中间人场景是请用户登录移动银行后让 Google Assistant 存入空白支票：基础相机应用注册了 deposit bank check 这一 intent，故在后台运行并拍下支票，再伪造 intent 去启动真正响应 deposit check 的移动银行应用，收集的数据送往攻击者的远程服务〔15:29〕。结果上，首次使用授权下仅百分之四十七的用户被提示授权——因为他们此前为其他用途误授了相机权限；EnTrust 则百分之百提示〔16:33〕。未预告组中攻击成功率由首次使用授权的百分之六十七降到 EnTrust 的百分之七〔17:32〕；已预告组从百分之五十三降到零〔18:06〕。总结为相对首次使用授权取得百分之四十七到六十七的改善〔18:25〕，未发现可辨别的卡顿、崩溃或响应问题，也不需要修改任何应用〔18:39〕；得益于预授权委托路径缓存，每个程序的显式授权不超过四次〔18:59〕，相对原生 Android 仅约百分之一的时间开销，每个程序约五点五千字节缓存〔19:14〕。问答中有人问是否考察过 Android 10 beta 对后台传感器访问的限制，演讲者承认没做、原型基于 Android 7〔19:54〕（YouTube EPYvUm3qUGepM，[616-1194]，L1）
