# 321.4.183 〔会议不详〕评测压缩比与压缩耗时同时逼近真实数据端到端收益明确评测以压缩比压缩因

- 〔会议不详〕评测：压缩比与压缩耗时同时逼近真实数据，端到端收益明确。评测以压缩比（压缩因子）与压缩耗时为目标指标，覆盖多种真实数据集以检验普适性；目标压缩器为基于位级重复查找或熵编码的无损失压缩器 zlib 与 LZ4（已被许多存储系统集成），并额外在 bzip2、LZMA 等不同族压缩器上测试泛化能力（结果略松但仍可接受）。结果显示重复长度分布与逐块熵的 CDF 都与真实数据高度吻合，因而不仅能模仿平均压缩比，还能复现数据集内部的压缩性异质性；一项新颖发现是压缩耗时同样可被近似模仿——尽管 LZ4 极快、对变化敏感，多数数据类型上其压缩耗时仍贴近真实值。端到端实验中 ZFS 写 1 GB 文件时面对原始数据与 SynGen 合成数据的吞吐表现一致，即便对 Calgary corpus 中使 gzip 表现极差的 DNA 测序文件这类极端数据也成立，而 FIO 式合成数据因过于易压缩会显著高估 ZFS 写吞吐；把 SynGen 作为数据生成层接入现有基准（音作 Ling Bench、Impressions）跑基于 ZFS + SSD 的数据库写负载时，随机数据与全零两种基线明显失真，而以 Calgary 文本及其合成副本作为 insert payload 得到的写入延迟曲线几乎重合。作者计划把模仿扩展到数据重复（去重）并与压缩联合。答疑中说明初始实现生成吞吐为文本类数据可达约 60 MB/s 每核、jpeg/mp3 等媒体类数据仅约 5 MB/s 每核，瓶颈是 Java 标准 Random 需频繁生成约 3.2 万个短随机片段，可通过复用随机数据改善；扫描阶段虽未尝试对飞行中数据做在线画像（设想是画像一次、生成多次），但所采指标简单，对采样输入流做实时表征并非不可行。（YouTube EPUSjpKn5g1eA，[768.6-1535.1]，L1）
- 〔会议不详〕OptimusCloud：云上键值数据库的参数与虚拟机规格联合在线调优。主讲人 Ashraf Makhou，工作由 Purdue University、Microsoft、Adobe Research、Google Research 合作完成并获得 NIH 资助，目标是让云托管键值集群在动态负载下同时达到成本与性能效率，做法是同时调优两组参数：键值存储自身暴露的参数（缓存大小、读写线程数、压实方法及其吞吐）与云 VM 规格类型（核数、可用内存、节点网络带宽）。作者指出两点挑战：一是两组参数组合空间巨大（Cassandra 有 25 多个性能调优旋钮，EC2 有 133 种实例类型与规格且相差五倍），二是两者存在依赖（如 Cassandra 缓存大小受 VM 可用内存限制），必须联合优化才能得到全局最优。他们用一台 Cassandra 服务器、三份工作负载之一的 30 分钟 trace，在六种 EC2 VM 规格上各用网格搜索选出 300 个数据库配置做基准，发现相对默认配置吞吐最多可提升 74%，且每种 VM 规格的最佳配置都不同。系统分四组件：离线训练的负载预测器依据历史 trace 给出前瞻窗口内负载形态；离线训练的性能预测模型以集群应用配置（复制因子、一致性级别、数据放置）与 VM 规格预测单服务器性能每美元；在线的集群性能预测器汇总各服务器预测值与集群信息给出总 ops/s；优化器在用户预算、最低 ops/s 与云厂商成本模型约束下选出云配置与键值配置。动态负载下旧配置往往不再最优，而重新配置通常要求重启服务器、带来停机与性能劣化，频繁重配会使集群整体性能严重退化，于是问题变成：能否只重配部分节点就达到全局最优并最小化停机？部分重配意味着异构配置，其收益在四节点 Cassandra 跑 MGnify REST 工作负载（读写阶段交替）的示例中显现：全 c4.large 写性能最好但 RAM 小导致读性能最差；把其中两个节点改为 RAM 更大的 r4.xlarge 后写略降而读提升 9 倍，改更多节点则读写双双变差，故最佳策略是按阶段只把两个服务器改成 r4.xlarge。（YouTube EPUV0d5rlN8w0，[8.4-650.9]，L1）
- 〔会议不详〕完整集（complete sets）把异构配置的搜索空间压到可解。异构化本身又带来搜索空间爆炸：20 节点、15 种可选配置时同构只有 15 种选择，异构等价于把 20 个相同球分到 15 个盒子中、共 1.3×10⁹ 种、不可建模优化。作者定义完整集为数据记录之并集至少覆盖全部数据库记录的最小节点子集；请求经各键值存储既有的快速副本选择机制（如 Cassandra 的 dynamic snitch、Elasticsearch 的自适应副本选择）服务，请求时延由最慢副本决定，故同一完整集内必须升级到更快配置集群性能才会改善，于是 OptimusCloud 保持同一完整集内配置同构、允许不同完整集配置不同；任一集群的完整集数量上界不超过复制因子（证明见论文），而复制因子实践上很低（3 或 5），重配数量等于一致性级别的完整集即可保证所有请求都由优化后节点服务，从而使上例搜索空间从 1.3×10⁹ 降到 680 种、可建模可优化。三个负载分别是：真实工作流 trace 的宏基因组分析门户 MGnify（无日周期与周周期、变化剧烈，前瞻难超 5 分钟）、公交追踪移动应用真实 trace（日与周周期强，前瞻可达一两小时）、以及模拟的批处理数据分析作业（作业时长与资源分配可长时间预测）。性能预测精度以 R² 与 RMSE 对比基线：按 VM 规格分别建模并用 SVD 推断未见配置的孤立模型不如 Optimus 的数值化表示（以核数、内存、带宽描述而非类别变量），后者靠跨 VM 规格的迁移学习取得最佳精度。四个基线是全局同构静态配置、NSDI 2017 的 CherryPick（贝叶斯优化找代表性阶段的异构配置，反应式）、USENIX ATC 2018 的 Selector（SVD 选同构配置，反应式）与作者 SoCC 2019 的 Sophia（遗传算法加性能建模、仅键值参数）。三项应用中 OptimusCloud 均取得最佳每美元吞吐且不牺牲 p99 尾延迟，相对同构静态配置最高提升 86%，相对 CherryPick、Selector 分别为 173% 与 130%，相对 Sophia 为 212%。鲁棒性实验向两个预测器分别注入均匀分布合成噪声，其相对同构静态配置的收益随噪声上升而下降，且对吞吐预测误差更敏感（曲线更陡）：因为偏离性能预测器给出的最优配置会显著降性能，而负载预测误差只使重配提前或延后、仍能从实际与预测负载的重叠区间获益。（YouTube EPUV0d5rlN8w0，[680.7-1280.3]，L1）
- 〔会议不详〕DSR：解耦的软件定义路由器重构云接入侧。主讲人 Xiao Liang Wang，合作者含 Shao Hua、Yuan Wei、Yan Bo、Sheng Li 与 Zhao 教授，并致谢腾讯网络平台团队。腾讯云在全球 27 个区域拥有 54 个可用区，客户把服务（以 VPC 形态）部署到云上，如何有效互联客户基础设施与云日益关键；典型接入需求有三类——私网连接（客户本地数据中心与云接入点直连，要求高带宽、可靠、安全）、面向全球终端用户的云上计算存储服务（要求网关支持海量转发表并优化路由路径）、以及企业分支经互联网低成本访问云上资源的 IPsec VPN 加 WAN 优化（即 SD-WAN 服务）。云网关是接入侧核心组件，过去主要依赖商用路由器，但随客户增长暴露三大挑战：转发表规模（私网连接网关需为大量租户维护上万条规则，互联网服务可达千万级转发表）、新网络特性需快速上线（客户或云自身要求，如自定义协议）、容量需随流量快速增长而弹性扩展。商用路由器的处理器能力、路由表规模与带宽通常按固定比例配置、无法独立扩展，且软硬件厂商锁定使一次小改动也可能耗时数月。作者先回顾典型商用路由器的三部分（运行 BGP/OSPF 的处理器即控制面、负责高速互联的交换网、转发面受限的线卡），再提出 DSR 解耦设计：线卡功能拆为接入面（各类接口、二层转发，用小型商用交换机即可，因其无需灵活性）与转发面（面向大规模转发表的三层包处理，以软件转发模块获得高特性速度与可扩展性）；处理器功能拆为负责协议与路由管理的路由面、负责存路由并生成并下发 FIB 与 ARP 表的控制面，同样以软件实现。各面各自部署在独立服务器集群上，无单服务器故障会导致整个系统崩溃，且各面可独立设计、维护与扩展（因资源需求不同），软件可编程性带来新特性部署与异构网络服务的灵活互通。（YouTube EPUWJxpPYYFcU，[16.9-337.7]，L1）
- 〔会议不详〕DSR 的扩展性、可靠性与接入场景落地。架构上，边缘接入模块是简单商用交换机用于连接外部路由器；转发模块负责高性能包处理，经 VXLAN 隧道与接入模块通信、经租户自定义 GRE 隧道与 VPC 通信；路由模块负责与外部路由器建会话交换路由信息；编排器作为全局控制器从管理系统收集流量调度需求，控制模块作为本地控制器把编排器配置下发到本地 DSR。扩展性上，互联采用 Clos 网络、服务器与接入交换机与核心交换机之间跑 BGP，每台服务器双上联到两台接入交换机；各面各有扩展方式，例如转发面不再对集群暴露单一虚拟 IP，而是引入租户共享的多虚拟 IP 结构，避免每台服务器承载所有 VPC 的完整路由表（另有 IPAM 表优化，见论文），从而每层网络都可水平扩展并由不同团队运维。可靠性上，服务器、链路或交换机单点故障不影响整体；整个控制系统失效时数据面凭最后一份良好转发表继续处理，整个路由系统失效时控制系统停止同步规则而数据面仍能正常转发；此外在 PIR 设备与路由模块间存在多条路径，需把 BFD 报文分片到多条路径以保证有足够 BFD 报文上报远端健康状态，由此向客户提供不停转发与不停路由能力。场景落地方面：私网连接上 DSR 与客户路由器直接建立 BGP 会话、底层再部署 IPsec 隧道，两套路由信息都同步给 VPC，VPC 通常优先选私网连接路径、失败后可快速切到 VPN 通道；面向全球终端用户的出向流量，DSR 能为用户流量选最佳出口而非依赖 BGP 路由，从而同时应对海量路由表与各类流量工程需求；安全防护上可用 DIP 到防火墙 VNI 元组、SIP 到防火墙 VNI 元组的灵活规则把入向与出向流量引向同一防火墙服务；入向 DDoS 是难点，因 DDoS 突发短促且流量巨大，作者希望在接入交换机而非转发面就重定向攻击流量，这需要让仅工作在二层的接入交换机按三层路由表转发——被留作论文中的 quiz。运维上作者以转发面为例说明三级探测（集群级、服务器级、核心级）以快速发现并处理故障，并把丢包、CRC 错误等统计与事件实时上报控制面，未来将增强网络可见性与监控、建设覆盖 overlay 等各层的全局端到端网络质量检测分析系统；总结为这套解耦软件定义路由器架构为不同客户提供了高度可扩展、灵活且高效的云接入服务。（YouTube EPUWJxpPYYFcU，[387.1-718.8]，L1）
- 〔会议不详〕Mutanex：用静态特征做可扩展的自动恶意软件聚类。主讲人未自报姓名，导师为密歇根大学教授 Kang Shin，合作来自 Symantec Research Labs（音作 Sandeep 与 Kent）。背景是恶意软件激增：一份报告显示 2012 年新增样本约 250 万个，相当于每天超过 7000 个新变体；Zeus、SpyEye 等自动化生成工具与多态混淆进一步放大变体数量。杀软厂商从各渠道每天收到数千至数万个样本，分析师须人工分析并产出签名下发终端，而既有研究显示从样本发布到被检出的平均时间窗约 54 天（答疑中补充约 15% 样本长时间多达 180 天仍未被检出），自动分析因此成为关键。Mutanex 的动机来自 G Data 报告：2012 年下半年超过 120 万个新变体只对应不到 2500 个新家族，多数新样本只是少量家族的轻微变体；把相似变体聚成家族既能把有限人力集中在代表性强、新颖的样本上，又能据其与已有家族的关联为新样本直接定标签，并把既有检测与缓解手段推广到同家族新变体。系统目标是对一批恶意软件预处理、以机器指令形式提取静态特征并高效聚类，需解决三难：多数样本用混淆与加壳躲避检测，如何高效提取属于原始程序的特征；如何表示特征以便相似度比较；如何让聚类算法跟上样本增速。作者把运行时加壳作为预处理重点——估计超过 80% 样本被加壳：加壳程序把原始可执行文件压缩或加密成看似随机数据、后接解壳代码并把入口指向解壳器，运行时先解密到内存再跳回原恶意代码，把恶意代码伪装成无害数据。已有专用解壳工具通常只针对一两个壳，且需重建 PE 头、导入表与指针使程序可执行，而 Mutanex 不要求可执行性、只需恶意代码可被检查，故利用"解壳器必然先写内存再执行"的性质：把样本载入内存并把所有页标为可执行但不可写，解壳器写入原代码时触发写异常，将该页标脏并改为可写但不可执行后继续；待其跳转到新生成代码时因缺执行权限触发执行异常，Mutanex 截获该异常、转储包含原始恶意代码的内存镜像，在其上补一个 dummy PE 头并把入口设为异常地址，再交反汇编器生成指令序列。特征表示上，既有工作用助记符序列（move、push、pop）会把语义过度泛化——例如表中多条指令助记符同为 move，语义却差别很大（写入调试寄存器意味着关键调试操作或检查调试状态，与写入通用寄存器不应等价），会造成不同代码片段的虚假相似，故 Mutanex 改用 x86 opcode 作为更准确的语义刻画，并对 opcode 序列做标准 n-gram 分析转换为定长特征向量（各元素为特定 n-gram 出现次数），使程序间相似度直接化为特征空间中的距离。（YouTube EPUXUU3owyFJA，[9.7-919.3]，L1）
