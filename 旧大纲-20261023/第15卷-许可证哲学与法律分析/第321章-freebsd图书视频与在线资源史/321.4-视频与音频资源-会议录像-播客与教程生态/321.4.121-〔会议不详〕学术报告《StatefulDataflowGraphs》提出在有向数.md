- 〔SREcon〕(推测) Google Traffic Interconnect SRE 团队负责人 Andrew Medworth（负责 Cloud Interconnect、Cloud VPN、Cloud Router、Cloud NAT 等）演讲《Fencing》，指出领导者选举（leader election）是并发互斥锁的粗粒度分布式版本，其锁保证本质上是基于时间的：由于没有完全可靠的故障检测器，超时可能误判存活任务，而 GC 停顿、调度与虚拟内存等都会使代码在失去锁后仍继续执行；他借 Martin Kleppmann《Designing Data-Intensive Applications》的例子说明陈旧写入风险，主张用 fencing token（如 Chubby 的 sequencer，单调递增让存储层拒绝 N+1 后跟 N 的旧写）把过时领导者挡在系统之外，并强调选举获胜对权力交接应是必要且充分的。（YouTube EPJ-Vg5FRehEc，[87-866]，L1）
- 〔SREcon〕(推测) 随后复盘 2019 年 3 月 Cloud Router 事故（影响 8 小时 34 分钟）：VRC 只在 TCP 连接断开时才重新查询 VRM 领导者这一 fencing 缺陷，叠加 VRM 初始化与领导权处理同线程的 bug，导致多次快速领导权切换后多任务并发初始化、批量去编程（deprogramming）数千客户路由，复杂超时机制又使初始化无法完成。总结后提出负载均衡后置、scope 对齐（Chubby 单 cell 与 Spanner 区域级对比）、金丝雀分析等运维挑战，并推荐把状态交给 ACID 数据库、动态分片（Google 内部 Slicer）与细粒度锁等替代方案；结论是领导者选举过于低层，若没有可靠故障检测与硬实时保证又要快速自动故障转移，就必须设计 fencing 策略。（YouTube EPJ-Vg5FRehEc，[921-1725]，L1）
- 〔会议不详〕演讲者介绍分布式追踪基础：在数万微服务、每秒百万级请求的架构下，指标与日志难以回答请求从哪来、在哪一段丢失或卡住，分布式追踪通过 trace ID、span（含时长、自定义标签等上下文）串联全链路，聚合后可视化瓶颈。当前基于 Dapper 的实现（Zipkin、Jaeger）默认随机采样约 1-5%，原因是全量采集带来 CPU 与存储成本；问题在于异常 trace 大概率落入未采集的 95%，且 5% 也未必命中故障请求，而 head-based 采样在 trace 开始时就做出丢弃决定，固定高采样率又抬高计算与存储开销。（YouTube EPJ0YaWwQl33w，[8-483]，L1）
- 〔会议不详〕演讲者提出的方案是自适应采样器：不再单一 tail-based，而结合 head 与 tail 采样，对刚上线的新服务全量采集一段时间再逐步收紧；采样依据从 trace 中提取特征向量（操作路径、服务名、span 主机名、状态码等），用空间分布/密度聚类把 trace 分成带权簇，权重是特征出现次数的反函数——例如已采到 200 个 200 OK 后，未出现过的非 200 状态码会获得更高权重，从而在固定存储预算下优先保存有价值的 trace。整体架构为微服务生成 span、聚合、trace 聚类、自适应采样引擎按反函数权重决定是否落存。（YouTube EPJ0YaWwQl33w，[483-778]，L1）
