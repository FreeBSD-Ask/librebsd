# 321.4.205 〔USENIXSecurity推测〕框架实现接口建模与实测结果工作流分两步先建模

- 〔USENIX Security（推测）〕框架实现、接口建模与实测结果。工作流分两步：先建模接口让固件能在仿真器中运行，再把现有 fuzzer 原样接入、经数据寄存器喂入输入并保存崩溃用例。寄存器按功能分为四类并分别处理，中断按固定频率触发；通过监控内存映射外设区域访问与中断控制器，自动识别并分类待建模接口，该抽象模型每种 MCU 架构只需做一次。在 70 个样本固件（覆盖 UART 等 8 类外设、3 种 MCU、3 个操作系统）上 79 个用例通过，寄存器分类准确率 76% 至 92% 且跨外设表现相当，说明机制协议无关；在 10 份真实固件（无人机、机器人等设备）上分类准确率达 100%，基本块覆盖最高 70%，相较不仿真外设的原生仿真器覆盖率最高提升 30 倍，并发现 7 个此前未知、可远程利用的漏洞，且全部在真机上复现以排除建模机制引入的假阳性。框架命名为 PIM，代码与测试固件已发布于 GitHub。（YouTube EPWwTRuvO_P5I，[343-632]，L1）
- 〔LSFS（推测）〕Linux LPFC 驱动的性能补丁集与瓶颈定位。ECD（原 Emulex，现属 Broadcom）的 James Smart 介绍已上游化的 v12.2.0 补丁集，动因是新 ASIC 把性能提到上代 2 至 3 倍，而软件已触及上限。LPFC 驱动支持两代 SLI 接口：老接口是几乎无扩展性的单体顺序引擎（8 Gb 及更早的适配器仍在大量出货），新接口面向高 CPU 数、已出三代 ASIC，具备数十个并行处理引擎、数千队列资源、每 CPU 的命令/完成队列与最多千个中断向量；初代芯片超百万 IOPS，次代约 150 万至 200 万 IOPS 且延迟 25 至 30 微秒，最新的 64 Gb 产品支持 500 万+ IOPS、延迟低于 10 微秒。基准显示 Gen7 单口仅约 150 万 IOPS、NVMe 单口不足 200 万，存在明显软件瓶颈；他们把驱动改为直通回送以剥离驱动与硬件路径做二分，发现 NVMe 能线性扩展到 96 CPU 且跨 NUMA 抖动很小，而 SCSI 一过 socket 边界就掉；随后又清掉每次完成都要抢的端口级锁（带来 15% 提升）等低垂果实。（YouTube EPX-txPAfclrY，[12-700]，L1）
- 〔LSFS（推测）〕三大改造、最终成绩与遇到的内核问题。一是全面 CPU 亲和化，为每个 CPU 建立命令/完成队列对并把中断、完成队列、工作队列都尽量留在本 CPU，资源不足时借鉴 irq affinity 的均衡算法按 socket 再按 CPU 分配，让缺资源的 CPU 与搭子 CPU 共享并优先在 socket 内争用；二是对无法按 CPU 分配的 exchange 资源（每次 I/O 都要用、SCSI 与 NVMe 共用，万级资源摊到上百 CPU 只剩十来个）引入“本地私有队列作快路径 + 共享区作溢出”，本地耗尽时逐个到其他 CPU 的共享队列偷取且优先 socket 内；三是改造中断处理，把硬 ISR 简化为给对应 CPU 派线程，完成队列处理下移到延迟中断线程并每轮自旋 1 至 1.5 毫秒，兼得轮询收益与低负载时的默认延迟。最终 SCSI 单口从 150 万升到 375 万 IOPS、双口从 200 万升到 450 万，NVMe 从不足 200 万升到 520 万（双口 530 万，硬件调优后聚合约 700 万），整体提升约 2 倍与 2.5 倍，FIO 测得单 I/O 延迟约 10.5 微秒。过程中还暴露两类内核问题：某内核宣称支持中断亲和 API 却未实现内部逻辑，把 100 个 CPU 的 150 个向量全压到 CPU0 导致软锁死，只能在驱动里加限流兜底；另在旧内核上 SCSI 一旦超过配置的队列深度，IOPS 会从 400 万骤降到 10 万，根因是 I/O 重试逻辑陷入不暂停的忙循环占满 CPU，NVMe 因深度按控制器而非 namespace 统计更难触发。（YouTube EPX-txPAfclrY，[700-1438]，L1）
- 〔OSDI '26（据频道标题标注）〕密歇根大学博士生 Jonah 介绍 TimeLock Drive：传统凭据式安全失效时，把“时间”当作数据完整性的最后防线。勒索软件日益暴利、专挑医院等脆弱群体且常成功摧毁备份；作者称“only about twelve percent of attacks leverage traditional software exploits, the vast majority target humans”〔00:48〕，主路径是钓鱼、窃密、社会工程与误配置，而获得人类权限却易受幻觉与数据投毒的 AI agent 是新隐患，故提出“using time as a last line of defense for integrity”〔01:17〕。做法是在存储设备读写接口上新增一条 time lock 命令，使数据“immutable for a duration of time”〔01:34〕：锁定期间对该地址的一切覆写失败，期满才放行；其价值在于“forces attackers to wait”——如同内嵌时钟的银行金库，时间成为攻击者必须支付、且大幅提高被抓概率的成本，可用于勒索防御、防篡改日志与萨班斯-奥克斯利、OSHA 病历等留存合规。既有方案把时间留存塞进版本化系统、TCB 庞大且已被证明可绕过检查提前删数据；本文首次构建“totally separate isolated time lock interface outside of the host and versioning system”〔03:05〕，信任边界排除整个宿主（用户、文件系统、数据库、版本化系统），只信任一个小 TCB 的微控制器检查器与未改动的存储设备，且版本化系统此后仍可自由优化而不影响 TCB。由此提出三问：如何用带时间锁的盘构建安全版本化、如何保持高性能、如何攻击后恢复。最难处是所有已知版本化系统最终都要覆写元数据，作者以追加只写日志记录映射表与时间锁状态的全部更新（写尾指针所指地址即完成追加、扫描重建映射）解决覆写问题，并指出时间锁元数据描述的是物理块状态、其日志又存放在物理块中，故“is self protecting”〔07:04〕。（YouTube EPX1RaXPrcfBg，[17-442]，L1）
- 〔OSDI '26（据频道标题标注）〕接着谈性能与恢复。纯日志结构的代价是“if I want to know the time lock state of a block, I need to scan N blocks on the disk”〔08:04〕，而每次普通写都要先查该块锁定状态；把锁定元数据缓存到检查器上又放不下，因为需要“two gigabytes of cache for every terabyte of storage”〔08:20〕。解法是让资源充足的宿主缓存全部时间锁元数据，并给每条元数据加新鲜度计数器与加密哈希，使检查器总能发现宿主可能造成的完整性或新鲜度破坏，检查器自身内存从 2 GB 降到“just one megabyte to store the freshness counters”〔09:10〕；宿主每次写随块提交元数据、计数器与哈希，由检查器校验后才判定该写是否违反锁定状态。恢复方面：若时间锁时长长于入侵检测时延，则数据保证未被破坏、可回滚到入侵前；针对攻击者伪造新数据或版本元数据扰乱恢复的问题，检查器记录每次锁定操作的“time of lock”〔10:26〕，该时间戳不可伪造，据此忽略入侵时刻之后创建的一切数据与版本元数据即可回到洁净状态。评估：检查器逻辑用 Dafny（转写作 Daphne）约四百行并转译为 Rust 编译为可运行程序，另有自定义驱动负责版本化与时间锁元数据管理及时间锁接口；形式化证明确认实现正确遵循论文的时间锁逻辑，作者认为易被验证正说明 TCB 小且逻辑简单；在虚拟机上发起多次勒索攻击并“recover with a hundred percent success rate”〔12:09〕；锁定与版本化合计在机械硬盘上延迟与吞吐开销低于 0.5%，SSD 平均亦低于 0.5%；把缓存改回检查器的对照实验因时间局部性很差而必然缺失，开销从乐观的约 5% 一路升到“all the way up to four hundred percent”〔13:10〕。结语称确有超越凭据的安全需求，希望本工作成为不依赖身份概念的安全保证之趋势的一部分，制品已在线公开。（YouTube EPX1RaXPrcfBg，[442-874]，L1）
- 〔USENIX ATC '23（据频道标题标注）〕蚂蚁集团 Juming Ma 与同事 Yancheng 介绍 SecretFlow-SPU：兼顾性能与易用性的隐私保护机器学习框架，Ma 讲前半、Yancheng 讲后半。背景是机器学习已渗透计算机视觉、自然语言处理乃至药物发现，而数据越关键越敏感——“biometric and financial data are very personal and requires strict protection”〔01:42〕，各国以欧盟 GDPR 等法规严格限制个人数据的收集、存储与处理。问题随之而来：既想处理数据又要保护它，靠什么？密码学的答案是安全多方计算，“allows multiple parties to jointly evaluate a function without revealing any information except the final result”〔02:46〕：以三方求工资和为例，各人把工资拆成三个随机数、分掉两个、自留一个，再把自留值与收到的两份求和并共享中间结果，即可得到总和而不暴露个人工资；MPC 由此支持隐私保护机器学习，多方可联合训练而不暴露各自训练集，模型服务器也能在服务请求时同时保住用户输入与自有模型。难点在于“MPC and MML exist in two distinct worlds with different focuses and priorities”〔05:44〕：一方关心底层密码协议，一方关心张量算子等高层积木。既有框架分两类：第一类是通用 MPC 编译器“such as MP-SPDZ”〔06:33〕，把密码原语封装成定制 ML API（可用其算子与优化器在加密数据上训练图像分类网络），但“not be compatible with existing machine learning frameworks”〔06:59〕，需要 GPT-2 推理这类复杂程序时“they have to write them from scratch”〔08:37〕；第二类如 TF-Encrypted、CrypTen 模仿 TensorFlow/PyTorch 接口而用密码实现，可用户必须改用 CrypTen 张量、把 PyTorch 算子换成 CrypTen 算子、把模型整体迁移，它终究是另一套框架而非 PyTorch 的替代品，且“normally is designed to mimic only one machine learning framework”〔10:53〕。于是主流框架尤其遗留程序能否被高效地以隐私保护方式运行，成了越来越重要的问题。（YouTube EPX20APC8c9pQ，[17-689]，L1）
- 〔USENIX ATC '23（据频道标题标注）〕Yancheng 介绍实现。SPU 含一个编译器，把模型“converting ML models into its own bytecodes”〔11:39〕，字节码交由采用特定 MPC 协议的高性能运行时执行。为不投入巨量工程即可接入多个主流框架，前端选择业界广泛采用的统一路径 XLA（转写作 XOA）作为输入：编译器以 XLA HLO 及各输入的可见性信息为起点，先在整图上做可见性推断，再转成自有隐私保护 HLO IR，待 IR 中可见性就绪后执行一批 MPC 专属优化；执行器设计以性能与可扩展为先，“supporting for multiple protocols while achieving a high performance execution”〔14:05〕。三个设计目标是易用性、可扩展性（同时支持多个 ML 前端与多个 MPC 协议）与高性能。以 GPT-2 推理为例：明文版基于 JAX、模型由 Hugging Face 预训练提供，用户实例化模型与分词器、把输入分词成 JAX 数组、再以贪心搜索迭代生成；SPU 版文本生成部分完全不变，只在 run 部分多几行——先在 P1 上以恒等函数把公开数组转成私有数据（内容永不离开 P1，调用方只拿到“a meta array with only input data type and shape information”〔17:24〕），再在 P2 上加载模型参数，随后 SPU 即时编译文本生成函数并按所选 MPC 协议运行，P1 与 P2 先生成秘密份额发给对应 SPU 节点，最后仅把结果还原给各方同意的选中一方。后端借鉴操作系统的硬件抽象层思想，指令经 HAL 层动态分派到相应 MPC API，协议开发者只需实现一小撮基本指令，用户改配置即可切换协议。两个编译器优化：重排乘法顺序，使 secret/public/public 的两次秘密截断降为一次，省下网络通信；对 max pooling，把首次 reduce_window 改写成同时返回 one-hot 索引向量供反向 scatter 复用，避开昂贵的比较通信。运行时再加向量化（逐元素算子捆成可多核分布的张量算子）与流式化（切小分块、通信与计算重叠以隐藏网络时延）。与 TF-Encrypted、MPyC、CrypTen 对比，SPU 在几乎所有设置下性能最好且精度可比，某设置下“four point one times faster than MPS and two point three times faster than TFE”〔22:15〕。（YouTube EPX20APC8c9pQ，[689-766]，L1）
- 〔USENIX Security '23（据频道标题标注）〕演讲者 John 与合作者 Ming Tian、Xue Li、Chao Chen、Nock Daniel、Yu Wang 提出 BunnyHop：把 Intel 处理器的指令预取器变成一条新侧信道；他先说两个趣闻——论文叫 Bunny Hop、发布于中国兔年，而他本人也属兔。动机是处理器快而访存慢，指令必须先自内存取回，“it will bring instructions ahead of the time to the processor”〔01:36〕再存入缓存，因为从缓存取指令远快于内存；而预取器“only checks the virtual addresses”〔01:19〕，根本不知道自己在预取什么。遇条件分支时预取器不知此处有分支、可能沿不会执行的路径预取而损害性能，于是它依赖分支预测器——后者“store the execution histories of all the branches and predict an outcome of a branch”〔02:27〕：预取器每取一条指令便问此处有无分支，预测器查历史给出可能目标，若历史显示该分支此前被取，就把目标地址及其后指令取回缓存。关键在于这些结构跨进程共享，“we can ask the instruction prefetcher to check an address for us”〔03:31〕：攻击者构造一条与受害进程某条件跳转同址的 NOP，执行时预取器同样去问预测器并拿到目标地址，该目标地址随即被取回驻留缓存，攻击者再做一次缓存攻击即可判断其是否存在——缓存攻击成熟、易用且可靠。论文核心观察是“we can translate the branch predictor state into cache state with the help of instruction prefetcher”〔05:08〕：把分支预测器（作者喻为兔子）原本不可观测的状态，借预取器换算成攻击者可见的缓存状态。（YouTube EPX2aNW6H75Bw，[8-351]，L1）
