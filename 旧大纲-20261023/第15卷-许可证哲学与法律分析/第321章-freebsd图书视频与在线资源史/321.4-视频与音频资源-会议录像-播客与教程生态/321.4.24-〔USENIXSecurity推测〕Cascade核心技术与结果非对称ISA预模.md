# 321.4.24 〔USENIXSecurity推测〕Cascade核心技术与结果非对称ISA预模

- 〔USENIX Security（推测）〕Cascade 核心技术与结果：非对称 ISA 预模拟与 bug 发现。先把保守程序交给 Spike ISA 模拟器取得分支操作数等关键值，再将复杂数据流缠绕进全程受控的控制流，程序复杂且有效；以指令不终止（non-termination）为 bug 信号，在 6 个不同复杂度的 RISC-V CPU 上发现 37 个新 bug（含 29 个新 CVE），并复现 VexRiscv 软核在推测时保留 FPU 资源不释放导致的挂起；黑盒吞吐增益同时带来显著覆盖率提升，项目已通过 artifact 评估并被社区广泛采用。（YouTube EP2c-xe-hei10，[393.8-766.7]，L1）
- 〔会议不详〕Origin-sensitive CFI：面向控制流完整性的新上下文敏感性。主讲人（与 Wenchen Liu、Abu Naser 及导师 Ji Wang、Ji Yang，Florida State University 合作）说明 CFI 策略不够强时控制流图上仍有攻击面，其 EuroS&P 2019 的先前工作虽用因果敏感性降低平均等价类大小，但最大等价类仍然很大。以 SPEC 471.omnetpp 基准为动机示例：对构造对象列表的迭代间接调用，路径/因果敏感性无法区分，而把对象创建处（构造函数调用点）与使用处相连即可精确定位目标；对 C 风格函数指针取最近赋值操作为 origin，以控制开销。（YouTube EP2dMDjvRsvUs，[10.6-552.7]，L1）
- 〔会议不详〕OSCFI 系统实现与评估。CFG 生成搭车（piggyback）在 SUPA 静态指针分析（FSE 2016，artifact 铂金级）之上，但其对成员函数指针返回空集且预算不足，作者强调静态指针分析仍需大量改进；复用 Intel MPX bounds 表的上下界单元存储 origin 与 origin context 保证代码指针完整性，并经 label-as-value 把 LLVM IR 映射回汇编以支持 ASLR。评估显示过滤失败用例后平均最大等价类缩减约 60%，运行时开销 7.1%（无 TSX）/7.6%（用 TSX）；问答环节 Rochester 的 John Criswell 就等价类指标与目标危险度提出改进建议。（YouTube EP2dMDjvRsvUs，[553.9-1194.5]，L1）
- 〔会议不详〕Automata SLH：将推测加载加固（Speculative Load Hardening）推向新高度。主讲人 John（合作者含 George Chen、Peter、Yuhao）介绍 LLVM 中实现的 SLH 通过在条件分支后条件更新推测状态掩码、并把误预测下所有内存访问投毒为 -1 来缓解 Spectre V1；而 2021 年的研究表明控制流转移同样可泄漏，strong SLH 理论上可缓解但未入 LLVM。借密码学的常数时间模型把泄漏归为内存、控制流转移与变时指令三类，SLH 只防第一类、strong SLH 防前两类，由此引出核心问题：变时指令在推测执行下是否真的泄漏。（YouTube EP2rfOdEVvBkI，[8.5-367.6]，L1）
- 〔会议不详〕变时指令泄漏分析与 Automata SLH 方案及结果。平方根+乘法的浮点操作对在误预测触发推测后，其执行时间差会落在推测窗口（如 200 周期）内而观测不到，但攻击者可通过观察一条秘密无关的独立内存访问是否推测执行来推断快/慢值，证明变时指令确实泄漏；Automata SLH 进一步把浮点值掩码为 -1 使泄漏只取决于处理器调度，SPEC2017 上整数基准较 SLH 慢约 13.5%、浮点开销约 44%，仍远快于完全禁止推测；另实现了泄漏 gadget 搜索工具并完成形式化验证。（YouTube EP2rfOdEVvBkI，[374.5-725.9]，L1）
- 〔会议不详〕G-Serve：处理不精确请求信息的 SLO 感知 LLM 服务系统。主讲人 Wei（合著者 Zhiyu 因技术问题未能共同报告；与 UIUC、Cisco 与 Google 研究者合作）基于覆盖 500 余人、六家学术与业界机构的用户研究指出 LLM 的 SLO 需求高度异质，并将请求分为延迟敏感（TTFB+TBT 按逐 token 计）、期限敏感（TTLT）与复合/agentic（DAG 关键路径端到端延迟）三类。现有延迟优化调度器（如 chunk prefill）对 78%-91% 的请求漏掉 SLO，即使喂给 oracle 精确长度信息漏发率仍超 50%，说明策略比预测更重要，由此提出按 SLO 分配刚好带宽、在线细化的 just-in-time 调度。（YouTube EP2wSboHoW2H4，[19.4-403.8]，L1）
- 〔会议不详〕G-Serve 三组件、G-Max 调度与评估。请求分析器用分位数回归森林（QRF）按请求自适应确定分位区间并随生成在线细化长度预测，用模式图加 K-medoids 聚类压缩、匹配历史 DAG 以应对依赖不确定性；G-Max 在每个时间帧重估每请求满足 SLO 的最小带宽并按估计吞吐/生成时间优先级与同长批处理滑动窗口调度，作者证明完整信息下最大化吞吐本身已是 NP-hard，并提供对离线最优调度器的竞争比保证。16 张 NVIDIA A100、4 个稠密与 MoE 模型的评估显示长期在线部署保持稳定吞吐，与 oracle 变体差距仅 3%-9%，资源节省最高 80%。（YouTube EP2wSboHoW2H4，[404.4-817.5]，L1）
- 〔会议不详〕HugeScope：解决虚拟化下的 hot bloat 问题。主讲人陈东立（Chen Dongli，Peking University）介绍两级页表遍历在基页配置下需 24 次内存访问，大页可降至 15 次并提升 TLB 覆盖，但当大页内访问偏斜到少数基页时，共享的 access/dirty 位使 hypervisor 误判整个大页为热页，导致分层内存管理误迁冷基页、页共享的 split-cold 策略退化为 keep-huge。现有方案各有短板：缺页跟踪引发 VM exit、采样滞后、Intel PEBS 缓冲缺乏虚拟化支持，而拆分并监控所有大页的 VMM 开销不可接受，由此提出只拆并页表而非页面本身。（YouTube EP30Y5-sBz1Wo，[16.2-483.5]，L1）
- 〔会议不详〕HugeScope 设计与评估：两阶段页跟踪与稳定接口钩子。基于两条洞察——嵌套页表建立后很少被 hypervisor 访问/修改，且 hypervisor 的修改仅限 Linux KVM 中 11 处多年稳定的接口——粗阶段周期性扫描并刷新嵌套页表项的 access/dirty 位，细阶段对热大页拆分嵌套页表按基页粒度跟踪后再合并，绕过所有元数据更新，并在稳定接口前加钩子合并页表以恢复一致性；另定义页偏斜比与热压力决定拆/并顺序并提供模块化接口。实验以本地 DRAM 为快内存、Intel Optane 为慢内存，跟踪开销低且精度接近基页配置，在 Redis/MongoDB 上优于 VTMEM 的大页与基页两种配置，页共享场景也兼顾性能与内存节省。（YouTube EP30Y5-sBz1Wo，[485.9-1004.0]，L1）
- 〔OSDI/ATC〕联合主旨演讲：现代计算机上的操作系统是“凝固”出来的，不是设计出来的。主讲人（ETH Zurich，Barrelfish 与 Enzian 项目相关）开场感谢 OSDI 与 ATC 同时邀请做主旨报告，并指出本届 OSDI 31 篇论文中仅约 6% 属操作系统设计与实现、近四分之一为机器学习，该方向甚至没有独立 session；以“安全复用硬件资源”的 OS 功能性定义回望现代 SoC 会发现，真正行使操作系统职能的是散布各处理器的运行时执行体、实时内核与微内核的集合，Linux 只是其中一个小组件。由此引出两个现实问题：Qualcomm 无线基带固件漏洞可欺骗 Linux 编程系统 MMU 获得整机访问（cross-SoC 攻击），以及电源管理策略实际运行在芯片另一组核上使 Linux 无从协商。（YouTube EP36myc8wQhLo，[7.2-2059.6]，L1）
- 〔OSDI/ATC〕主旨演讲后半：两条技术建议与问答。建议一是动手为整个 SoC 编写操作系统（NXP 手册长达 8981 页，“复杂度是我们的业务”），建议二是研究者应当自己造计算机——其 Enzian 平台一侧是 CPU、一侧是大型 FPGA，板级管理控制器运行 OpenBMC、在主 CPU 复位前执行数十万行代码，表明现代服务器与 SoC 一样复杂异构。随后的问答回应了入门门槛问题（称 FreeBSD、seL4 更易读，应协作分工而非一人造 OS）、“把 SoC 当分布式系统”的说法、能否访问 SoC 内隐藏处理器（NXP 有文档、Cavium/Marvell 配合）、Jeff Mogul 问 HotOS 是否 OS 论文的出路，以及向用户态搬迁是否属于同一问题等。（YouTube EP36myc8wQhLo，[2059.6-3970.1]，L1）
- 〔会议不详〕NICA：FPGA 智能 NIC 上的内联应用加速软硬件框架。主讲人 Hagai Aran（与 Lior Zino、Moran Tork、Gabi Malka 及导师 Mark Silberstein 合作）指出微软自 2015 年起在每台 Azure 服务器部署 SmartNIC，但这类网卡还可用于应用级内联加速——如把 KV 存储缓存放在网卡上直接服务缓存命中，或对 CoAP 请求（Samsung ARTIK Cloud 等 IoT 服务器所用）做密码学过滤以抵御 DoS。为此提出 iKernel 抽象在进程中代表 FPGA 上的加速功能单元（AFU），支持 POSIX sockets、绕过主机协议栈的 custom ring 与 RPC 配置接口，与 memcached 集成仅 107 行代码。（YouTube EP3AKoueaHfMc，[10.1-363.3]，L1）
- 〔会议不详〕NICA 虚拟化设计与评估。计算虚拟化比较 FPGA 静态空间共享、部分重配置的粗粒度时分（上下文切换太长不适合网络应用）与 AFU 内硬件上下文切换的细粒度时分（可到包粒度），I/O 虚拟化在每个接口按 VM 打标隔离并加加权包调度器实现性能隔离，部署模型主张云厂商自研可信 AFU 供用户市场选择而非客户自带设计的 FPGA-as-a-Service。在 40GbE Mellanox Innova Flex（Xilinx FPGA + Mellanox ASIC，类似 Microsoft Catapult）上以 VMA 用户态网络栈为基线评估 memcached：Zipf 99 下过滤获 4 倍、加 custom ring 共 9 倍提升，多 VM 线性扩展，60% 命中率时虚拟化下延迟 2.1 微秒与裸机持平；问答讨论了 FPGA 与主机同一 socket 回包的 TCP 一致性问题。（YouTube EP3AKoueaHfMc，[388.2-1043.7]，L1）
- 〔会议不详〕RIKER：从简单构建脚本获得既正确又快的增量构建。主讲人借 Star Trek Picard 复制器的比喻说明 Make 的问题：简单 Makefile 每次全量构建、复杂目标拆分又易漏依赖产生链接错误，构建系统需要在“正确（不漏依赖）”与“快（只做必要工作）”之间取舍。RIKER 让用户只写一条原构建命令的 Rikerfile，运行时用 ptrace、seccomp BPF 与注入库跟踪全部系统调用并转为自创语言 TraceIR，以解决构建依赖图无法刻画的三类问题：中间状态（temp.s）的顺序、collect2 反馈环，以及“文件不存在”的反依赖。（YouTube EP3DctR_Axd-c，[12.7-736.9]，L1）
- 〔会议不详〕RIKER 构建算法与评估。算法是“始终运行完整构建”：用已记录的 TraceIR 模拟未变化命令并把缓存产物按时序暂存，仅直接执行检测到变化的命令（CC1、AS、LD 等），迭代到无新变化即完成。14 个程序的全量构建中位开销 8.8%（Autoconf/coreutils 最差，LLVM 仅 4%），no-op 构建中位仅多 162 毫秒（LLVM 最差 11.3 秒对 Make 4.8 秒，因为 Riker 连反依赖、编译器二进制、系统头文件与配置脚本都检查）；增量构建以真实代码仓库演进驱动，Redis 100 次提交节省 26 分钟（Make 为 29 分钟），5 个项目 500 次提交达到 Make 4.16 小时节省的 94% 且无需手工增量规则，工具可在 riker.sh 获取。（YouTube EP3DctR_Axd-c，[739.1-1390.8]，L1）
- 〔会议不详〕若VPN支持遗留认证机制会出什么问题：IKEv1公钥加密（PKE）认证中的Bleichenbacher填充预言攻击。主讲人（与波鸿鲁尔大学的Jörg Schwenk及奥波莱大学的Adam Czubak等合作）介绍IKEv1六消息握手与四种认证方式，指出RFC 2409规定PKE认证的RSA加密须按PKCS#1格式编码，这一古老填充正是Bleichenbacher攻击目标；攻击者以中间人方式把一个响应者加密的nonce转发给另一响应者当填充预言，并让首个响应者保持等待，约数千次探测后即可恢复nonce并冒充响应者、破坏认证。Cisco、华为以及Clavister、Zyxel的实现均存在此类预言，该模式虽未进开源实现但配置上的疏漏同样可被利用。（YouTube EP3NT5TTZSY-A，[15-770]，L1）
- 〔会议不详〕以Cisco IOS为案例的实际利用、密钥重用与IKEv2签名攻击。主讲人在从eBay购得的Cisco ASR 1001-X路由器上验证：填充有效返回消息四、无效则延迟一秒返回消息二，恰好构成单比特预言；受60秒握手时限与约850次每秒RSA运算限制，模拟显示约四分之一的攻击可成功，且未发现任何实现了PKE/rPKE的设备不存在Bleichenbacher预言，相关CVE已发布补丁；报告还讨论跨套件、跨版本、跨协议密钥重用（如华为把RSA密钥兼作SSH主机密钥）及对IKEv2签名的Bleichenbacher攻击（模拟成功率约22%）；Q&A中Agile Bits的Jeffrey Goldberg等就前两消息异常延迟与TLS/IKE密钥重用展开讨论。（YouTube EP3NT5TTZSY-A，[776-1553]，L1）
- 〔会议不详〕云系统大规模日志压缩：LogZip在生产日志上失效的实证研究。清华大学的Wei Junyu介绍与拉夫堡大学、中国地质大学及阿里巴巴集团的合作工作：阿里云每天产生约1PB日志、为满足合规需保存6个月（约180PB），而基于解析器的LogZip在18类共1.76TB生产日志中有13类压缩比劣于通用LZMA，单台服务器压缩1PB需200多天；其失效源于Python库慢、每模板变量数受限以及未针对数值变量设计，团队据此设计并实现了LogReducer。（YouTube EP3V45WpSmUnM，[15-263]，L1）
- 〔会议不详〕LogReducer的三项数值变量压缩技术与评估结果。团队采用时间戳差分编码、相关性识别（如顺序写时当前offset等于前序offset加length）与弹性编码（超过50%的整数可压至极短表示），并以C++重写解析路径、辅以剪枝解析树、阈值调优与批处理等工程优化，较LogZip平均取得2.2倍压缩比与18.4倍速度提升；在1.76TB生产日志上压至34.25GB，压缩比较LZMA高至4.8倍、速度较LogZip高约两个数量级，代码与日志样本已开源。（YouTube EP3V45WpSmUnM，[295-701]，L1）
- 〔USENIX Security（推测）〕RLBox：沙箱化Firefox第三方媒体库的细粒度隔离框架。主讲人Shravan指出浏览器信任libjpeg、libtheora、libopus等数十个第三方媒体库，任一库的漏洞都可能危及整个浏览器，而渲染器隔离与站点隔离并不足够（Alexa Top500站点中93%跨源加载以JPEG为主的媒体）；即便把libjpeg放进进程内SFI沙箱（NaCl或WebAssembly），Firefox代码不加清洗地信任其数据仍可借memcpy等写gadget攻破渲染器，因此需要taint标记加强制验证的细粒度方案。（YouTube EP3VuZQXbPP9I，[8-330]，L1）
- 〔USENIX Security（推测）〕RLBox的使用流程、评估与生产落地。RLBox作为C++库抽象底层隔离机制（进程隔离或SFI）并仲裁应用与沙箱间的通信，把沙箱传出数据标记为tainted，经编译错误驱动的循环完成沙箱内存分配、自动边界检查与copy_and_verify清洗；在Firefox中移植6个库时每个仅需数天、编写2到51个各2-4行的简单验证器，页加载时间与峰值内存开销极小；该框架已用WebAssembly集成进生产Firefox（Linux与Mac用户当前就在使用），Windows支持与更多库的沙箱化在推进中。（YouTube EP3VuZQXbPP9I，[332-662]，L1）
