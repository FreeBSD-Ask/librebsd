- 〔NSDI（推测）〕控制律、网内遥测与评估：incast、公平性与可重构网络。PowerTCP 的控制律是基于功率的乘性增/乘性减加加性增，并以指数加权移动平均更新窗口；功率优先用网内遥测测量（交换机向包中附加元数据、接收端回显、发送端计算），并给出仅需 RTT 与 RTT 梯度的时延近似版本。在超订阅 fat tree 的 RDMA 评估中，PowerTCP 快速缓解 incast、收敛到近零队列且不丢吞吐，TIMELY 队列长且吞吐骤降、HPCC 略好但仍远逊、Homa 不丢吞吐但队列显著更长；公平性实验（4 条流每毫秒到达）中 PowerTCP 公平且稳定，Homa 因 SRPT 调度而不公平，时延近似版稍欠稳定。web search 真实负载下短流 99.9 分位 FCT 较 HPCC 改善最多 33%，但时延近似版长流 FCT 变差，PowerTCP 则长短流兼优；在可重构数据中心网络中，PowerTCP 快速填满高带宽电路、利用率约 85% 且保持低时延，优于 HPCC（低时延低吞吐）与 NSDI 2020 的专用方案（转写记作 ReTCP，高吞吐高时延）。（YouTube EP5K7p3jiDeR8，[490.0-973.5]，L1）

- 〔USENIX LISA（推测）〕为什么需要 Desired State Configuration：从 PowerShell 的诞生讲起。主讲人 Jeffrey Snover（PowerShell 之父，开场提及刚获 Unix 社区的 LISA 奖）认为"为什么不用 Salt/Chef/Ansible/Puppet/CFEngine"是错误提问，正确的问题是当年为什么发明 PowerShell：Unix 是文档导向的操作系统，一切皆文件，awk/grep/sed 就是管理工具（文件编辑还自带事务语义），而 Windows 是 API 导向的操作系统，这些 Unix 式工具在 WMI、Active Directory、注册表面前全部失效，IIS 能被管理的"虚假希望"让很多工具止步不前。他讲述了 1999 年加入微软后推行 CLI/Shell 的文化阻力与最终胜利，Services for Unix 免费发布却未能解决问题；团队以 POSIX shell 语义为基础、借鉴 Perl、按需发明，写下 Monad Manifesto，核心是把 Unix 组合模型（A|B|C）解构后重释到 API 世界：对象管道取代文本管道、消除祈祷式正则解析，直接对 API 返回的对象做处理。DSC 由此被定义为工具无关、分布式、异构的配置管理平台：以 DMTF 标准 MOF 文档描述期望状态，Make-It-So 代理调用 C/C++/PowerShell 编写的命令式 provider，支持 push（WS-Man 协议）与 pull（REST API）两种模式，显式分离配置的结构要素与环境要素以在 dev/test/生产/灾备间最大化复用。（YouTube EP5LN0SrMJBNo，[9.8-1410.0]，L1）

- 〔会议不详〕可编程流水线上有状态网络函数的状态一致性难题。主讲人 Yong Feng（清华大学）介绍面向高级有状态包处理的工作：有状态 NF（负载均衡、DDoS 缓解、流量整形、有状态防火墙等）的处理依赖同流历史包，基于扩展有限状态机抽象可分为状态查找、状态计算、状态更新三阶段；复杂 NF 需要"广义状态回写"——读状态与写状态之间夹多次表查找与计算，而计算可能超过一个硬件时钟周期，造成读后写（RAW）冒险：如 P1 在第一级读到状态 C=2，第二级计算后变为 4，若同流的 P2 在写回前读取则读到陈旧状态。流水线架构要靠 recirculate 原语写回、缺乏快速更新路径且同流包须在流水线外等待，多核架构则要等状态更新同步，二者都把高性能执行退化为顺序/串行执行；在 switch（流量达 60% 吞吐）与 NIC（28% 吞吐）场景的仿真显示，所需流水线较长时两种架构都出现丢包，同流包阻塞（P4-P6）与队头阻塞（P7-P9）共同压低吞吐、放大时延。（YouTube EP5LjRyzniLoc，[16.3-410.0]，L1）
- 〔会议不详〕Rapid 架构：可写状态表、推测执行与 FPGA/ASIC 评估。论文提出新抽象、新执行模式与新架构：其一，状态可写表（stateful writable table）抽象采用"本地读、远端写"，避免低效的 recirculate 且比任意位置读写更省硬件，本地流表兼作全局状态表扩大可访问范围；其二，观察到大多数复杂 NF 状态更新率低（并非每个包都改流状态），传统方案以 100% 概率阻塞保一致性，而推测执行预测包不改状态即并行送入流水线，发现读到旧状态的包（如 P4）再送回重读最新状态，非阻塞处理可省 2 个硬件周期；其三，在典型 match-action 单元基础上设计 Rapid 架构，在流水线一侧加 side ring 支持快速状态回写与一致性，用时间戳调度机制保证一致与有序，并提供多级一致性支持（如 sketch 类应用可放宽）。FPGA 原型与 PISA、Banzai、FlowBlaze 综合对比中 Rapid 占用更少 LUT/触发器/BRAM 且功能更强，ASIC 面积与功耗相对基线至多 5% 开销（远小于 FlowBlaze）；三种 trace 下吞吐较阻塞执行提升 2-3 倍、时延降低 1-2 倍，最后增强 P4 语言方便编写状态函数。（YouTube EP5LjRyzniLoc，[410.0-858.5]，L1）
- 〔会议不详〕访问模式泄漏与遗忘性验证的困境。主讲人 Zhang Song 介绍 OblivCheck（与 Griffin、Rishabh、Lalitha、Kushagra 合作）：加密能保护传输与磁盘数据、Intel SGX 等硬件飞地能加密内存中的数据，但访问模式（内存/网络地址、消息大小）仍会泄漏敏感信息——例如医院查询流感返回结果大、查询罕见癌症返回结果小，结合疾病频率即可推断 Bob 患癌；防止泄漏需要遗忘性（obliviousness），即访问模式与敏感数据内容独立。遗忘算法（如 Opaque 利用不可观察空间中的快速排序减少 sorting network 使用）又慢又复杂，设计者与用户只能手工撰写和阅读证明。现有自动检查手段失效：taint 分析沿执行传播污点、发现基于私有值的分支条件即拒绝，会把实际遗忘的 oblivious filter 代码（每轮向输出缓冲恰好追加一个元素、发送前加密）误判为不遗忘；符号执行在分支处分裂路径，随输入长度指数增长，遭遇路径爆炸（path explosion）。（YouTube EP5PZSDfjlYU0，[8.8-296.0]，L1）
- 〔会议不详〕OblivCheck 的核心技术与收益。三个核心思想：让用户通过 API 声明哪些访问可观察/不可观察（如用 OblivCheck 版 send 记录地址与长度的访问轨迹）；利用遗忘算法的领域知识做乐观状态合并——不可观察空间中的实际值攻击者无法区分，可用无约束符号变量（记作 *，如 s0）过近似替换，使两条路径的输出完全一致从而彻底合并，状态数保持线性而非指数增长，该变换基于过近似因而是可靠的（sound）；但过近似会引入假阳性（如扩展的 filter 代码中符号值被推断为"既非 0 也非 1"导致误报不遗忘），故提出迭代状态反合并（iterative state unmerging）：先全合并验证，不通过时按记录的符号变量引入位置逐步展开为具体值重跑。评估显示 taint 分析对全部测试算法几乎全误拒（仅一个正确），OblivCheck 能准确分类，性能较符号执行提升 200 至 15000 倍，且因目标程序"近乎遗忘"、首轮大多状态已合并，重跑的额外开销在实际中可容忍。（YouTube EP5PZSDfjlYU0，[296.0-727.7]，L1）

- 〔会议不详〕四步提取管线与结果：BiLSTM 分类 + 整数规划修复。方法含四步：离线用大量不同尺寸形状的网络（含随机堆叠层、组合式拼接的程序化架构）生成信号数据库以覆盖相邻层间的电磁交互；提取时从目标 GPU 或其电源线采集轨迹，滑窗送入训练好的 BiLSTM 循环网络，把单次扫描直接转为类别标签（即层）并借助前述层间同步的"计算 unraveling"同时得到拓扑序列；再利用相邻层上下文加电压与时序特征估计层参数（卷积核大小、图像输出通道维度、全连接神经元数等），离线可任意采样使参数估计精度相当好；但一个错误参数即导致层间输入输出不匹配的非法网络，因此最后把超参数规格化为整数规划问题、用 IBM CPLEX 求解器做联合优化验证与清理，使方法对未来网络设计更具韧性。结果：用 GTX 1080 单卡信号建库，用同型号"孪生"GPU 的信号仍能成功提取；多卡混合训练时即便从未见过目标卡也能靠相似卡保持威胁，含目标卡则更好；提取出的模型与原模型效果相当（保真度高），可作代理攻击；最终准确恢复了数百层的网络。（YouTube EP5PaT2XPljcM，[330.0-683.4]，L1）
