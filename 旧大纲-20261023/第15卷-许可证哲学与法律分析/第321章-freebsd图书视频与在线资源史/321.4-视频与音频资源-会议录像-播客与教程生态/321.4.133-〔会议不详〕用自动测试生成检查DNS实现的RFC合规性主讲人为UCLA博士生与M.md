- 〔会议不详〕用自动测试生成检查 DNS 实现的 RFC 合规性。主讲人为 UCLA 博士生（与 Microsoft 的 Ryan Beckett 及导师 Todd Millstein、George Varghese 合作）：DNS 是互联网的粘合剂且爆炸半径大——Slack 重大故障源于 Amazon Route 53 处理 DNSSEC 通配符的细微 bug；DNS 本质是复杂字符串重写系统，复杂性来自无确定性与复杂记录类型（DNAME 部分重写、CNAME 完全重写、通配符及约 60 种其他记录、约 30 个 RFC）；工具自动生成的 zone file+query 测试可让广泛使用的 BIND 崩溃（断言失败），条件包括 DNAME 记录重写到父域、查询类型被拒、foo.attack.com 在查询名中重复至少两次且以 com 结尾；攻击者可向权威服务器上传该 zone file 远程触发拒绝服务，BIND 为此发布高 CVSS 评分的 CVE，影响 Ubuntu、NetApp、Infoblox、Red Hat 的维护版本；模糊测试无法生成 zone file、符号执行受路径爆炸限制，现有工具因此不生成 zone file，无法发现 RFC 违规。（YouTube EPLIK7p2I4ZlI，[12.7-529.7]，L1）

- 〔会议不详〕从 toy 例子到真实 gadget 的利用与端到端攻击。Linux 内核大量使用把多变量打包进单个 struct 并传指针的模式，翻转嵌套结构体指针可一次性危及多个变量，堆喷伪造 struct 即可控制局部变量与执行流；端到端攻击四步为内存模板（memory templating）、内存按摩（memory massaging）、堆喷（heap spray）填充伪造 struct、最后调用含 gadget 的受害函数翻转指针；用扩展自 Spectre gadget 搜索的 Smatch 工具在最新内核中找到 192 个读 gadget 与 28 个写 gadget（smatch 有误报/漏报，仅作粗估）；对 pipe.c 中某 gadget 完成端到端攻击，以 82.6 bits/s 的速率转储内核内存，说明需要从根源解决 Rowhammer 的整体防御，而非只保护 PTE 与 sudo。（YouTube EPLJAFHBMqaB8，[344.8-680.8]，L1）
- 〔会议不详〕Zeta：大规模云中可扩展且鲁棒的东西向（east-west）通信框架。主讲人 Zhongyi 来自 Johns Hopkins University，一作 Chenyu Zhang 来自中国科学技术大学（合作方含 Futurewei、University at Buffalo）：数据中心可达 10 万台服务器、百万 VM，实例频繁启停，网络虚拟化需兼顾可扩展性、鲁棒性与建立通信的低延迟；预编程模型在启动 VM 时预装所有规则、部署延迟长且扩展性差，on-demand 模型首包送控制器编程、首包延迟极高且依赖控制面，gateway 模型只装指向网关的默认规则并卸载大象流到直连路径，但网关故障迁移慢、突发流量易过载；Zeta 分为管理层、网关集群层与主机侧转发层三层，用网关集群与虚拟交换机上的 group table 做负载均衡，网关节点用主动 XDP 转发并以 eBPF map 存储转发规则与实时流信息。（YouTube EPLK6uKNgGXlo，[12.7-442.9]，L1）
- 〔会议不详〕Zeta 的多 IP 迁移与评测。网关集群随故障与伸缩动态变化，逐台修改虚拟交换机 group table 开销大，Zeta 给每个网关逻辑分配多个虚拟 IP，故障时集群控制器重映射虚拟 IP 并由其余节点发送 RARP 包更新交换机 MAC 表，无需改动虚拟交换机规则；管理层做簇内负载调整（multi-IP planner）与簇间均衡（VPC-集群映射建模为 ILP 问题、用舍入算法求解）。测试床在 3 台裸金属服务器上部署 45 个 KVM 网关、另用 20 台裸金属服务器作计算节点：纯转发单核超 1.8 M packets/s，加检测与卸载在 eBPF map 2000 项时仍约 1.7 M packets/s；突发视频流量（2.4-100 Mbps）下实现低平均负载与更好均衡；多 IP 迁移使网关故障、过载、卸载与扩容下的恢复延迟比 gateway 模型（GW zone）低十倍以上。（YouTube EPLK6uKNgGXlo，[455.2-878.0]，L1）
- 〔会议不详〕Facebook 生产工程师 Patrick Shuff 以假设一台服务器服务全部 Facebook 的方式逐层构建负载均衡基础设施。规模数据：月活 17.9 亿、日均需终止约 11.18 亿条 TCP 连接（按每设备一条的保守估计）、10.9 亿来自移动端（需兼顾 2G/3G 等低速网络）、84.9% 用户在北美之外；流量分为动态请求（新闻 feed、点赞等改变状态者）与静态请求（照片、视频，易缓存），团队核心指标为以 Tbps 计的 egress 周曲线与昼夜周期（峰值约每日上午 9-10 点，太平洋时间）；L7 用 ProxyGen 终止 TCP/SSL 并代理到 HHVM 服务器，L4 用开源内核模块 IPVS 按四元组一致哈希，L3 用路由器 ECMP，构成前端集群（数十 L4、数百 L7、上万 HHVM），再扩展为多集群数据中心（Luleå 瑞典、建设中爱尔兰），所有负载均衡器都跑在同构 x86 服务器上、由类 Kubernetes/Docker 的调度系统分配，宕机即重新调度。（YouTube EPLLBT70yexZo，[10.4-1352.0]，L1）
- 〔会议不详〕TCP 连接保持、DSR 与就近终结、DNS 负载均衡。所有 L4 使用同一一致哈希且后端池相同，L4 故障时请求仍被哈希到同一 L7；L4 内核本地状态表记住连接去向，L7（ProxyGen）恢复后也不破坏 TCP 连接；L7 用 DSR（direct server return）直接回包，L4 用 IP-in-IP 封装转发请求，公网 VIP 监听在 L7 的 loopback 接口，网络拓扑全为三层路由；2011 年流量团队研究发现首尔到俄勒冈单请求约需 600 ms（跨洋 RTT 约 75 ms，TCP+SSL 握手占 3 个往返），在东京成田设 POP（约 15 ms）后降至 240 ms、提升超 50%，POP 内是与数据中心相同的负载均衡栈、仅无 HHVM，预建 HTTPS 连接回源；DNS 侧由 Sonar 按约每 4 万张头像一次的采样测量网络距离，Cartographer（后由 Python 重写为 C++）实时生成世界映射并每 1-2 分钟经 torrent 分发到数千台 tiny DNS 服务器，兼顾网络邻近、容量、健康与 geo 回退。（YouTube EPLLBT70yexZo，[1357.5-2696.4]，L1）

- 〔OSDI〕Scalene 的低开销实现与 AI 优化建议。它采用采样式分析，但 Python 解释器劫持信号并只在 opcode 边界投递，导致原生代码执行期间采样失效（cProfile 正因此漏掉原生代码耗时）；Scalene 每次采样同时记录虚拟时间，把超出采样间隔的延迟归因给在跑的 C 代码，从而区分 Python 与原生时间并达到行粒度。内存侧以阈值采样（增量跨过约 1 MB 才采样）替代 memory_profiler 对每次 malloc/free 发系统调用的做法（后者让 5 秒程序跑到 20 分钟），精度更高且几乎零开销。项目开源后被 Semantic Scholar 用于把成本降低 92%；论文完成后团队又让 Scalene 成为首个集成大语言模型的分析器，填入 OpenAI API key 即可对区域（爆炸图标）或单行（闪电图标）给出运行更快的优化建议。（YouTube EPLLxhCPWfBhg，[434-883]，L1）

- 〔USENIX Security〕USENIX Security '20 论文 Pixel: Multi-signatures for Consensus。主讲人 Gregory Neven（与 Manu Drijvers、Sergei Gorbunov、Hoeteck Wee 合作）说明区块链共识中每轮成千上万节点对区块签名、签名需上链保持可验证性，多重签名可用一个与单签名同尺寸、同验证代价的聚合签名替换。但还存在事后腐化（posterior corruption，又称长程攻击）：即便当前仅 1/3 节点腐化，历史上收集到的旧密钥仍可在其曾构成分叉多数的时点制造分叉，外部验证者无法分辨两个版本的历史；网络演化使更多密钥集合成为阿喀琉斯之踵，委员会签名与密钥买卖还会加剧该问题。前向安全签名（公钥不变、私钥按时段更新、历史时段不可伪造）正是解药，Pixel 即前向安全多重签名方案。（YouTube EPLOMmvynGGHY，[8-310]，L1）
- 〔USENIX Security〕Pixel 的设计与性能。Pixel 基于双线性映射，密钥结构可视为 Boneh-Boyen-Goh（2005）方案的层级密钥，技术源头可溯至 Canetti-Halevi-Katz（2003）与 Gentry-Halevi；聚合签名只需逐分量相乘，用聚合公钥以 3 次 pairing 验证。在随机预言机模型下（假设安全擦除与双线性 Diffie-Hellman 困难性）证明安全；BLS12-381 曲线上 1500 签名者、约 40 亿时段时公钥 48 字节、签名 144 字节，签名 3 ms、聚合 7 ms、验证不到 7 ms，无需可信设置并提供 rogue-key 防护，还可在两个群间切换以权衡密钥/签名尺寸与计算量。集成进 Algorand 替换其 Bellare-Neven 式树形前向安全 ED25519 签名后，区块验证时间节省约 33%、签名尺寸节省约 40%。（YouTube EPLOMmvynGGHY，[310-644]，L1）
- 〔USENIX Vault〕Vault '20 演讲 The Two New I/O Controllers and BFQ。主讲人 Paolo Valente（摩德纳大学，BFQ I/O 调度器维护者）介绍 Linux cgroup 新落的 io.latency（按目标时延节流分组）与 io.cost（按权重并反比于 I/O 成本分配带宽份额）两个控制器，其目标与 BFQ 相同但缺文档说明何时该用谁。其对比实验显示：SSD 上目标分组吞吐比 io.cost 高最多 47 倍、BFQ 总吞吐最高 3 倍，且失效跨 ext4、Btrfs 与多块盘普遍出现；传统主流控制方案会浪费最多 90% 的盘速，BFQ 能在控制 I/O 的同时把浪费降到几乎为零。他聚焦 io.cost（io.latency 的超集）展示两类失败：顺序读目标吃光带宽而随机读干扰者近乎饿死（总吞吐接近无控制），以及顺序读对顺序读/写时 io.cost 过度节流拖慢一切。（YouTube EPLQVuFHKDdj8，[5-795]，L1）
- 〔USENIX Vault〕io.cost 失效根因：非线性时变的驱动与失准的反馈回路。通过打补丁追踪内部，讲者指出驱动传输函数（请求下发与完成时间的映射）因多通道、流水、条带、重排、read-ahead、GC 与磨损等而复杂非线性、随时间与负载漂移；io.cost 却用仅依赖 I/O 类型的线性模型（基价+斜率）估计成本来度量服务，节流本身又改变 I/O 模式导致服务误估，其动态调权反馈回路同样失效。vrate 按不精确的 busy level（surplus/滞后分组数加请求时延对比静态阈值）调节，如同调节非线性、时变延迟的淋浴水温：busy level 一有毛刺 vrate 骤降，盘远未饱和仍被认为过忙而难以恢复，35 秒的测试大部分时间吞吐极低。Q&A 中说明 BFQ 成功正因不依赖这些参数：只按时间段内传输扇区数按权重分配，用户可静态慢调权重。（YouTube EPLQVuFHKDdj8，[795-1603]，L1）
