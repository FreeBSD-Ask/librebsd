# 321.4.192 〔会议不详〕Symphony为LLM推理服务提供低延迟内存层与计算内存分离主讲人

- 〔会议不详〕Symphony：为 LLM 推理服务提供低延迟内存层与计算内存分离。主讲人自述名为 Sarab，工作主要在 UT Austin 完成并与 Wisconsin–Madison 合作；LLM 应用是有状态的——聊天机器人中用户在拿到结果后追加信息再发下一次请求、多智能体软件工程工作流（程序经理、开发、测试三个 agent 的闭环）每次迭代都要访问上一轮状态，这个状态就是与先前查询关联的 KV 缓存（生成分词所需的内部表示），单个用户可产生数十 GB（以相对较小的 Llama 2 70B 为例约 20GB/用户），而各次请求间隔可能任意长。现有方案把状态卸载到主机内存、请求到来时再读回，既把计算与内存耦合（想扩内存就得扩昂贵的 GPU 节点），又让负载变得“粘”——请求必须送往状态驻留的节点，实测某实例上的最大未决请求数常达中位数的 5 倍，进而拖慢时延、抬高高尾延迟；而把 KV 缓存卸载到网络又会带来显著高延迟，而 LLM 应用因直接面向用户而极延迟敏感。Symphony 据此提供一层极低延迟的计算内存分离层，关键洞察是工作流中存在可用于预取的“提示”（聊天场景下用户开始在输入框打字、多智能体场景下 agent 回传结果时顺带丢下提示）以赶在请求到达前预取 KV 缓存并隐藏加载延迟；由于提示不可靠（至多是高概率估计）、无序且缺乏资源粒度，它采用与推理引擎深度集成的合作内存调度——掌握在途请求的内存需求、按优先级优先缓存早层 KV 使计算得以继续、同时重叠加载其余部分。（YouTube EPVLffR2xpRpo，[18.2-439.1]，L1）
- 〔会议不详〕Symphony 的系统架构与评测结果。系统引入两个组件：Symphony 调度器作为顶层调度器负责负载均衡与请求路由、并向节点管理器下发提示（含 KV 缓存位置以及是否需从远端存储获取），Symphony 节点管理器承担重活、与框架调度器集成并从 GPU 显存、主机内存、磁盘到对象存储跨层管理内存；由于推理引擎一旦缺内存生成就会停顿，它还把 KV 缓存复制到更低存储层级，以便放心清除高层缓存而不造成停顿。评测中聊天场景用 ShareGPT 真实提示、以人类阅读与打字速度生成提示，智能体场景采用 MetaGPT 软件工程工作流，三节点测试床含 A100 GPU、100Gb/s 互联、756GB 内存与 4TB 磁盘，基线为 vLLM、Intercept、Lumnix 及 Lumnix 加 Intercept 的更强组合。相较 Lumnix 加 Intercept，首 token 时延改进 5 倍以上（Lumnix 是反应式、须在负载失衡发生后才响应，而 Symphony 是主动式的），在用户数提高 4 倍时仍能维持相近的输出 token 时延与延迟分布，智能体服务相对 vLLM 约 2.8 倍加速；即使人为构造每个真实提示配两个伪造提示的最坏情况，最大延迟增幅仅约 36% 且仍大幅领先全部基线，结论是它支持状态卸载、相比基线可服务 4 倍用户且不影响精度、GPU 与内存资源可按工作负载特征独立扩展，并已开源。（YouTube EPVLffR2xpRpo，[444.9-848.8]，L1）
- 〔会议不详〕TaintCheck：用页面保护与标签指针检测堆缓冲区溢出。主讲人 Amogh 与 Ravindra Suri、Michael Ferdman、Dongyan Li 合作；C/C++ 广泛高效却无内存安全，越界写连续多年位列 CWE 最危险软件弱点（原文提及 2021 与 2022 年的排名），sudo 中的堆溢出可致提权，越界读又可造成 Heartbleed 式信息泄露。既有方案各有代价：Electric Fence 与页堆靠守护页、无需查任何元数据且越界即段错误，但内存开销高且保护缓冲区所需的系统调用频繁；softBound 依赖影子内存区而有元数据查找与比较开销；先前指针标签方案虽因元数据存于指针高位而查找快，却需要更大的标签从而压缩地址空间。TaintCheck 把两者结合：为原始对象额外分配一个内容无关紧要的“尾对象”（影子对象）并让其末端对齐到守护页，把到尾对象的距离存入指针高位标签位，程序中的任何解引用都在插桩下于尾对象上重复执行（下指针位取对象、高位标签位加偏移即直达尾对象），于是对原始对象的越界访问会命中守护页并触发可捕获的页错误。（YouTube EPVMzjInjFS3w，[16.6-263.7]，L1）
- 〔会议不详〕TaintCheck 的实现机制与评测。实现分两大组件：分配器按尾对象要求设置守护页、找出到尾对象的距离并给指针打标签，编译器插桩负责复制内存解引用并保证标签位不泄漏给外部未插桩库（跨出插桩边界的指针必须清洗标签），插桩通过 LLVM 链接时优化 pass 完成，包括复制解引用、调用点掩码、safe alloc 与 delta pointer 优化（去掉静态已知安全的访问检查）、以及把尾指针计算提升出循环（因标签在整个程序中恒定，只需持有一个指向对象、一个指向尾对象的指针做同样的指针运算）；关键技巧是共享尾对象——malloc 为每种对象大小维护空闲链表、一组块中最后一块作为该组的尾对象并让其末端对齐守护页，因此对任一原始对象的 load/store 都会在同一个尾对象上执行同一内存访问，而 16 位标签最多表示 64KB，更大对象回退为自身即尾对象（标签为 0、守护页直接对齐分配），因程序视角无法区分标签是否为零故两类保护用同一套插桩处理。评测采用四个服务器应用（Apache 与 Nginx 以 256 请求/秒并变化负载大小，Memcached 与 Redis 采用 50% 读写比并变化值大小）与 SPEC CPU 2006、2017：安全上 SPEC 2017 的 gcc 版本暴露出一处对已分配区域外 4 字节的非法读（可通过程序内越界检查修复）；性能上服务器场景尾部延迟开销低于 4%、比 AddressSanitizer 快约 3 倍，在 SPEC 2006 上优于 Delta Pointer（后者需为每次指针运算更新标签，在某些程序中开销较大），SPEC 2017 开销约 33%。（YouTube EPVMzjInjFS3w，[282.2-864.9]，L1）
- 〔USENIX Security（推测）〕Decaf：一个自动裁剪现成 UEFI 固件的可定制平台。主讲人 Jake Christensen（合作者含 Private Machines 的 Ram Taglang、Radu Ciontea 与布加勒斯特理工大学的 Mugur Anghele）指出固件位于微码之下的极低层、特权极高却几乎完全闭源，其供应链从 EDK2 开源参考实现出发、由 American Megatrends 加入特定芯片组所需模块、再交付给 Dell、HP 等主板厂最终为单个产品生成镜像，过程中模块只增不减导致镜像臃肿，代码质量也令人怀疑，跨厂商跨型号大量复用带来可轻易复制的攻击面（Kovacs 与 Kalmbach 2015 年发现大量在用主板因单个模块被复用而受影响），而他观察到高达约 70% 的模块其实是多余的。Decaf 是可在真实主板上调试现成 UEFI 固件的完全可定制平台：无需源码、直接作用于镜像、可用字节面积自动移除最多约 70% 的内容，功能可按需定制（例如保留启动操作系统并运行应用的能力而移除 VGA、USB 等特性），已在某云假设器的“计算即服务”环境中运行约三年、失败次数不高于原生镜像。裁剪的价值在于直接移除尚未知晓的潜在漏洞而无需先做漏洞分析；被移除的代码并非未使用或不可达——它常在做启动期间根本不会用到、且操作系统自带驱动的硬件初始化，因此裁剪会实实在在缩短启动时间，这也说明这些代码本来是活跃且可被利用的。（YouTube EPVQisvKY9Q-k，[27.5-449.6]，L1）
- 〔USENIX Security（推测）〕UEFI 机制、平台流程、依赖发现与实测结果。UEFI 把平台初始化分为四个阶段：SEC（安全）、PEI（预 EFI 初始化）、DXE（驱动执行环境）与 BDS（启动设备选择服务）；基本构件是模块（EFI 镜像切出模块、每个模块通常含一个 PE32 可执行文件），模块之间通过 EFI 协议通信——在最长也最关键的 DXE 阶段驱动被初始化并安装协议，其他模块凭 UID 查找到协议指针后调用以访问底层硬件（如 TCP、HTTP 协议），这正是后文裁剪所依赖的依赖关系。平台本身用 Luigi 调度任务与管理依赖，固件裁剪引擎基于 UEFI Tool（所用 Intel Galileo 固件示例来自 UEFI Tool 作者 Michael Lach，其中可见典型复制粘贴错误：取回一个值与常量比较，随后取回另一个值却仍拿第一个值去比较），镜像经 IPMI 控制器刷入主板并启动，若属依赖发现镜像则收集数据经网络发回外部服务器、若属验证镜像则采集验证输出并与首个运行的基线（原生镜像）比较以决定接受或拒绝该候选镜像；裁剪流水线先逐个尝试移除每个模块，再把通过的模块两两合并（两者都通过则尝试移除其总和、否则取较大的一组）直至得到一个候选解，随后随机逐个再尝试加入模块直到不能再移除。随后由 Mughal 讲解依赖发现：UEFI 模块像普通操作系统中的进程一样互相通信、依赖会随运行时条件（可用哪些模块、存在哪些资源）变化，而模块移除顺序对裁剪至关重要（依赖多的模块多半裁剪失败、无依赖者多半成功），团队因此劫持 EFI 协议 API、覆写函数指针以记录全部模块交互，再把这些信息喂给裁剪算法用于赋权；验证在 Docker 容器中完成且测试套件可由终端用户配置——用 dmidecode 检查平台硬件能力、lspci 检查 PCIe 总线、/proc/acpi 检查电源管理，并采用 ChipSec 扫描已知固件漏洞与平台配置错误，但明确不指望改善 ChipSec 结果（Spectre、Meltdown 这类高层漏洞无法靠删代码修复），转而确保不移除可能重新暴露已修复漏洞的安全特性。结果方面，在 Spark Micro 与 Titan 主板上启动时间最多缩短约 24%；通过移除 USB、网络栈等硬件能力可防御经由这些设备的攻击（如 2014 年 Black Hat 提出的 BadUSB——插入恶意 U 盘可接管操作系统乃至刷写固件），移除 micro 主板上的 USB 支持即删去 6 个模块并让操作系统感知不到物理 USB 端口存在；净模块减少比例在 9% 到接近 70% 之间，高质量 ROP gadget 移除比例在 11% 到 62% 之间（只统计满足前置条件、具有栈副作用等特征的高价值 gadget），团队提供“激进裁剪”与更温和、保留网络启动等功能的“数据中心裁剪”两种策略。（YouTube EPVQisvKY9Q-k，[464.9-739.7]，L1）
- 〔会议不详〕Facebook 瞬态发布订阅（ephemeral pub/sub）系统的重新架构动机。主讲人 Jeff 是 Facebook 实时基础设施团队的技术负责人；该系统支撑实时点赞、正在输入提示与评论的即时呈现，量级为每分钟数百万发布者、数十亿订阅，核心契约是设备订阅任意字符串主题并提供回调、发布发生时回调携带发布方载荷被触发、设备可随时取消订阅，且订阅生命周期绑定连接（设备断开即全部退订，这就是“瞬态”的含义）。2016 年团队定下两个目标：把“够用”量化成可对外承诺的可靠性等级（是五个九、三个九还是只有一个九），以及支撑十亿订阅者同订一个主题；旧架构的流转是订阅请求进网关后被打包为带网关 IP 与端口的“burrito”送进订阅存储，发布则由路由层拉取该主题的全部订阅、做完产品逻辑后仅向网关下达投递指令。他承认最大的错误是以为图中那些“箭头”（网络）是问题的唯一来源、以为把客户端各类指标的构成关系组合起来就能算出“四个九”，而现实体感像“两个九”——“数学很难”：回到最顶层重新定义可靠性（实际完成量 / 本应完成量）后发现送达数与发布数分别可由网关与路由层算出，唯一难以计算的分母——订阅者数量——恰在订阅存储里，暴露出该单分片服务虽有反熵模型却会在日志流中留下什么样的洞、而这些洞会让订阅错失本可实现的完整价值；十亿目标同样不可行，因单条订阅约 1KB、一次发布就要吃掉约 1TB 网络带宽，而事件期间每秒可能有数千次发布，若只达成 1% 连“一个九”都到不了。（YouTube EPVR-vcvfM4wA，[10.1-528.6]，L1）
- 〔会议不详〕新架构：把订阅存储压进网关并新增 Endpoint Store。重构的核心是重新分配三个角色的职责：路由层基本保留原样，但把订阅存储直接“搬”到网关上——网关收到订阅后即在内存中落地并向新服务 Endpoint Store 发一个小“叮”（tickle）表示自己对某主题感兴趣，完成映射即视为订阅成功；订阅存储是“主题到订阅”的映射，Endpoint Store 则是“主题到网关主机集合”的映射，后者特征迥异且复制更便宜，因此做了 3 副本，发布时路由层从三个副本拉取端点流（副本一致说明系统健康、不一致既是问题信号也是修复机会）并边发现新网关主机边转发，路由层几乎只做取与转发，全部工作在本机网关内完成（对本机所有订阅者扇出、产品逻辑与限流），带来更精细的产品控制与很高的敏捷性——加一个新限流器约两小时即可上线，因为无需在整个系统中新增契约。由此两大目标重新变得可验证：由于分母与分子都在同一主机内存内，可靠性在假设主机健康、无 bug（bug 恰是他们最大的问题来源）时可完整计算，也因此快得离谱；但引入新服务意味着必须重新定义可靠性，最终被简化为“路径可靠性”（路由层与网关通信的完好程度），并用网关端点间的反熵模型加以验证。十亿订阅也不再可怕——对过度配置的集群一个简单负载均衡器即可吃掉全部流量、网关自行拉起并把订阅存入内存，Endpoint Store 只需承载“主机数量”这一量级温和的负载，而且完全可测（先验证 Endpoint Store 能否承受相应数量的主机订阅、再验证网关能否在内存中容纳全部订阅），团队由此从“热门话题一出现就被叫醒”变成几乎无感；个人教训是遇到问题要跳出来回到顶层重新审视产品体验、以及定高目标并认清自身极限（极限会给你“令人窒息的现实视图”），代价是要承受“真有十亿人订阅同一主题而撑不住”的风险，问答中还澄清该方案并不使用 IP 多播、更像从传统数据库转向 MapReduce 的努力，而架构本身只需几周就能敲定，真正耗时的是迁移所有使用方。（YouTube EPVR-vcvfM4wA，[530.1-1050.8]，L1）
