- 〔SREcon〕Shopify 的服务化基础设施：从表格定义的基础设施到 owner、度量与自动化。主讲人未自报姓名（开场先纠正了介绍词里写错的公司名与微服务措辞），讲述团队为何要系统性追踪 service infrastructure——即应用层之外一切让它跑起来的东西：本地开发环境自动化、CI、部署自动化、遥测、自动缺陷跟踪与日志留存；这些工作单独看并不复杂，但乘上服务数量就令人发指：生产系统从六年前的约 10 个涨到约 250 个、平均每周新增一个，开发者从 30 人涨到近 900 人，每日发布次数从 2011 年的约 3 次涨到约 250 次，他真正担心的是增长速率而非体量本身。团队观察到的反模式是 spreadsheet-defined infrastructure：每次要跨全部或某类系统做改动，都得先在表格里手工搜集上下文，例如找出即将使用不再受支持的 Rails 版本的应用、弄清源码在哪、跑在哪里、谁在维护、是否重要到值得升级还是干脆关停，这套工作被反复重做；于是项目定了三个目标：定义 owner、可度量、以及作为构建自动化的平台。owner 目标最花时间，因为 Shopify 的信条是 act like an owner（做决定时问自己：如果你是完全投入这家公司未来的所有者，你会怎么做），但 900 名开发者都这样时会退化成旁观者效应，典型困境是故障发生时不知道找谁、以及要给长期项目做投资决策；最终做法极简——在每个 GitHub 仓库的元数据文件里记录 owner（个人或小队，视服务重要程度而定），归属变更就提 PR、走评审、留痕，全公司生产系统都已加上这一字段。（YouTube EPReLOxVDxr_E，[9-635]，L1）
- 〔SREcon〕四层服务模型、团队记分卡与自动修复机器人。度量目标要求回答我们是在变好还是变坏、时间该花在哪里、以及正确的投入量是多少——就像不能所有系统都要满九个 9，必须先决定每个系统值得投入多少；做法是把 Splunk、Bugsnag、PagerDuty、剧本、Git 仓库等一切生命周期相关系统关联到具体服务，第一个有用的产物就是每个系统一页的仪表盘（谁负责、代码在哪、公网端点、可直接起手的 Splunk 查询入口），随后按重要性把系统分为四层：最低层只要求有 owner、能处理安全缺陷、挂了有人最终把它拉起来，往上一层要求不止一个 owner（避免巴士因子）、开发部署自动化与 CI、至少要有可用性监控（不必页到人），再上一层要有值班轮转与告警、用 statsd 指标支撑实时视图、压测与无停机滚动部署，最高层要求明确 SLO、使用断路器与舱壁等弹性模式、并能容忍单个数据中心故障。基于分层可以为个人、小队乃至管理者生成记分卡：看得到名下所有系统的质量分与最关键的基建缺口（顺带一提，他们发现 LinkedIn 的报告里搭了几乎一样的东西，而榜首那条恰好是个 staging server、缺项不算严重）。自动化则体现在：机器人对着未通过检查的服务自动开 GitHub issue 并在问题消失后自动关闭（实测中系统迁到另一个集群后公网端点变化，Pingdom 还在监控旧 URL 的重定向，机器人自动报出）、拦截 Redis Labs 等第三方用邮件报警的邮件机器人并判断可执行后路由给当前 owner、以及直接调用 Pingdom 与 PagerDuty 的 API 一键补上可用性监控与值班排班。三条可迁移的结论：ownership 是光谱，要在集体所有与官僚式所有之间找到属于自己公司的平衡点；把基础设施投入当作权衡来显式决定而非无休止加码；以及当每周都在新增服务时人工配置注定不可持续，必须把自动化推到能处理接下来 300 个新系统（让机器人自动开常规升级与跨集群配置变更 PR），并把新系统上线频率当成长期约束。（YouTube EPReLOxVDxr_E，[637-1257]，L1）
- 〔USENIX Security（推测）〕NetWarden：在保持性能的前提下缓解网络隐蔽信道。Rice University 的 Jiarong Xing（与同校 Qiao Kang、Ang Chen 合作，谈末自述正在找 2021 年暑期实习）用一个例子开场：存着机密文件（转写音作 a bomb logic code）的服务器被恶意软件渗透，把秘密直接放进负载会被检查 payload 的防火墙拦住，于是改用 TCP 包头字段编码秘密——防火墙只查负载就放行了，这叫存储型隐蔽信道（storage channel）；再比如用大间隔编码 1、小间隔编码 0，叫时间型隐蔽信道（timing channel），本文两者都要缓解。隐蔽信道是难题：协议字段不确定（TCP 初始序列号本来就接近随机，改与不改无法区分）、包事件也不确定（时序既可能是攻击者控制，也可能只是网络抖动），检测因此困难；而缓解必须逐包执行，数据中心流量已到 terabit 每秒量级，软件逐包处理效率极低，加随机延迟又会加重数据中心里那些延迟敏感流的实际时延——正是这两个原因使已有防御（例如给每个包的序列号加统一偏移、或先用统计方法检测时间信道再加随机延迟）都只跑在软件里、在实际数据中心得不到部署。NetWarden 用可编程交换机（P4 等高级语言可编程、以线速运行）站在被保护服务器与用户中间当 TCP 代理，实时检测并缓解隐蔽信道而不损害 TCP 性能；四个关键特性是同时缓解存储与时间两类信道、每端口 100 Gbps 吞吐、性能损失不超过 1%、以及完全对主机透明。（YouTube EPRePMfuVtFPM，[8-372]，L1）
- 〔USENIX Security（推测）〕软硬件协同设计、ACK 加速器与实测对比。交换机天然为转发设计、编程模型受限，NetWarden 因此提出 hardware-software co-design 原则：数据面是可编程 ASIC，能改包头、维护逐流状态、提供纳秒级时间戳并以线速运行，但内存极少、只能做有限算术；控制面是通用 CPU，内存充裕、能做复杂运算却只能跑到软件速度，因此逐包操作与恒定状态放数据面、批处理与增长型状态放控制面，并尽量减少两者之间的跨面交互——RTT 测量、逐流状态维护、IP 头改写落在数据面，包检测与统计检验落在控制面。第二个挑战是保住连接性能：TCP 里服务器先发一批、收到 ACK 再发两倍，任何额外延迟都会拉长 RTT，同一时间窗能发出的数据就变少；解决办法是造一个 RTT 没有变的错觉，NetWarden 为此设计两个性能加速器——ACK 加速器（转写音作 Aqubuster/AggBoost，讲者只展开这一个）动态测量服务器与用户之间的真实 RTT，假装自己是接收方、在若无防御本该到达的时刻提前向服务器发伪造 ACK，服务器于是继续发下一批，数据先缓存在 NetWarden 再转给用户，若这段链路丢包就由 NetWarden 直接从缓存重传（服务器已认为该数据被确认过）；另一个是 receive window 加速器，通过放大接收窗口让每个 RTT 发更多数据。评估假设攻击者要通过隐蔽信道外泄 RSA 密钥，基线为无防御与朴素防御（不加性能加速器）：无防御时 IPD 幅度到 800 微秒解码率可达 100%，朴素防御与 NetWarden 都降到接近随机猜测；性能上无防御时发送速率稳定在 15 Mbps，朴素防御有 25% 损失，NetWarden 只有约 1% 偏差，且在不同网络条件、TCP 变体与应用上结论一致。（YouTube EPRePMfuVtFPM，[375-744]，L1）
- 〔NSDI（推测）〕Curator：企业集群的自治存储系统。主讲人未自报姓名（转写中提到导师在华盛顿大学，工作是 Nutanix 五年多的工程），称 Curator 是已部署在数千集群、数千客户中的运维系统的一部分，并说明企业越来越依赖集群存储：要么买专用存储节点（SAN），要么像 Nutanix 那样把计算与存储合在通用节点上，同时要求自动复制与恢复以应对故障、SSD 与硬盘无缝整合、面向虚拟机负载的快照与垃圾回收，以及压缩、去重、纠删等省空间变换。细看会发现这些工作大多可以在后台完成，从而让 I/O 路径保持尽可能简单，Curator 正是为这些后台任务提供的框架与系统支持，面临三大挑战：需要可扩展且能随存储量伸缩的框架来承载各类后台任务（借大数据分析的思路）、后台任务与前台 I/O 之间要有恰当的协同（靠共同设计）、以及集群之间乃至单个集群随时间的异质性（留给后续部分）。架构上以 Paxos 保证复制与一致的分布式键值库（基于深度改造的 Apache Cassandra）保存全部元数据，前台 I/O 服务与后台存储管理服务通过它协作；数据以 extent 为单位组织成 extent group 落到物理设备以提升整体写吞吐，extent ID map（extent ID 到 extent group ID）与 extent group ID map（extent group ID 到副本物理位置与状态）两张表构成多级重定向，这让跨文件的数据共享更简单、也最小化元数据更新——例如把数据从 SSD 挪到硬盘只需改后者。（YouTube EPRhoJRzQ-HiQ，[10-465]，L1）
- 〔NSDI（推测）〕MapReduce 式后台任务、前台协同与用强化学习取代阈值策略。Curator 用 MapReduce 处理这套全局分布的元数据以做高效的扫描与联表，从而获得系统级视野：以 tiering 为例（把冷数据从 SSD 挪到硬盘或云），extent group ID map 存修改时间、另有 extent group ID access map 存访问时间，而某个 extent group 冷不冷在四节点集群里要跨 A 节点的修改时间与 D 节点的访问时间判断，已不是本地决策，于是 map 阶段各 curator 进程扫描自己负责的 Cassandra 元数据环分片、以 extent group ID 为 key 发出修改时间或访问时间，reduce 阶段按 ID 汇聚成三元组后在本节点排序识别冷数据（例如 ID 120 的元组落到 curator C）；同一框架还实现磁盘故障后的副本重建、同层内磁盘均衡、容错与垃圾回收等任务。第二个挑战靠共同设计解决：存储服务向 I/O 服务暴露扩展的低层 API（不只是 extent group 的读写，还包括迁移某个 extent 到另一个 extent group、压缩某个 extent group 等），存储服务只操作元数据并给出提示，是否执行由 I/O 服务决定，并发变更可以让某条建议失去意义而被丢弃；任务分批限流以减少对前台的干扰，元数据读写经精心设计使存储管理服务总看到一致版本但允许陈旧，并用 compare-and-swap 而非加锁。评估取自约 50 个真实集群、两个半月的数据：95% 的集群欠复制数据不超过 0.1%、90% 的集群垃圾数据不超过 2%，说明恢复与垃圾回收任务确实在起作用；tiering 用阈值维持目标 SSD 占用率（Nutanix 默认 75%，一半集群正处该点），既想留足热数据又留出吸收新写的空间。由于集群间在资源（存储密集或计算密集节点）与负载（Hadoop、Spark 这类大数据应用或 SQL Server 这类服务，以及混合体）上差异很大、单个集群内负载还会随时间漂移，阈值式启发式常常次优，因此近期工作（尚未上生产）改用强化学习替代阈值策略。（YouTube EPRhoJRzQ-HiQ，[465-890]，L1）
- 〔USENIX Security（推测）〕Downfall：利用推测数据汇聚的攻击。主讲人未自报姓名，先讲 AVX2 扩展约十五年前引入的 gather 指令，用于加速对零散内存的访问，可按数据类型与向量宽度选择、也能通过 Intel intrinsics 直接调用，数据库、密码学、科学计算、视频编码与 AI 推理等重数据处理场景广泛在用。gather 接收查找表、索引与掩码向量寄存器，硬件为提速做了几件对本文很关键的事：索引命中同一 cache line 时复用而不重复请求内存、单条指令最多 16 个内存操作可以被中断并保留部分执行结果以便续跑、以及把已可用的数据推测性转发给下一条指令——本质上就是分配硬件缓冲并推测性写入数据。作者据此回顾教训：2018 年 Meltdown 从 L1 数据缓存泄露，Intel 声称第九代 Coffee Lake 已修，随后研究者（含作者本人）证明该缓解仍可从 CPU 内各类微架构缓冲泄露；Intel 又声称第十代硬件终于修好（部署中部分出货并未正确启用缓解），到 2022 年年中业界普遍以为问题永远解决。这些攻击的共同点是有保持共享用户数据的 CPU 缓冲，攻击者触发异常或微码检查后数据就从这些缓冲泄露——Meltdown 取自 L1 数据缓存，随后有攻击取自 store buffer、ZombieLoad 取自 line fill buffer、另有取自 load buffer 的，而本讲讲的是位于中间的那个：向量寄存器堆（vector register file）。（YouTube EPRiKas-0Vbk8，[8-493]，L1）
- 〔USENIX Security（推测）〕攻击原语、泄露规模与真实密钥窃取。攻击极其简单：受害者线程在 CPU 上做向量运算把数据填进寄存器堆；攻击者先用大量 cache flush 与 cache miss（或触发缺页等其他手段）把 CPU 送进推测态，然后只需执行一条 gather——不需要任何故障或特殊操作——再把 gather 的输出编码进缓存并扫描缓存，最后两步与原始 Meltdown 及 MDS 攻击一致；作者的 PoC 用 8 个 CPU 线程作为用户随机窥探字符串，另一位用户打印密码后能看到更多字符串冒出来。他写了一个小工具自动抽取 LLVM 汇编测试用例里的所有内存操作、按已知数据模式逐个执行并同时在同核跑 gather 采样，发现所有从内存加载的 SIMD 指令都会泄露，包括为加密加速而设计的 AES-NI 与 SHA-NI，也包括负责快速拷贝数据的 rep mov 以及若干以 SIMD 方式微编码执行的寄存器上下文恢复指令。泄露规模方面，把向量指令的 32 字节全部编码进缓存后，在第十一代 Core 上单次最多可泄露 22 字节、多数为 17 至 22 字节，而先前的 MDS 攻击每次只有 3 到 4 字节；再配合不同数据模式与 cache line、32 与 64 bit 编码与输出重排，可以取出 4 字节与 8 字节的连续段，且每次执行 gather 都能用 Vperm 瞄准寄存器不同位置，最终可取空整个 SIMD 寄存器。基于 AES 会把主密钥扩展成一组轮密钥、加密每个块时反复把轮密钥载入寄存器堆，因此泄露频率高于其他数据这一观察，攻击者每次泄露 8 字节连续块，保留频率高且分布均匀的块，拼成轮密钥候选再逐一比对即可还原主密钥；现场演示里受害者虚拟机跑 openssl 命令行十秒、攻击方采样前 8 字节与后 8 字节再暴力比对，成功取回原始密钥，AES-128 的攻击复杂度为 8 bit。作者结论是单个硬件缺陷足以击穿 OS、VMM、SGX 等各类安全边界，影响范围达数十亿台笔记本、台式机与服务器；Intel 的缓解措施是微码更新，把 gather 改回不再推测性转发数据，对关键路径上使用 gather 的工作负载开销最高可达 50%。（YouTube EPRiKas-0Vbk8，[494-1009]，L1）
