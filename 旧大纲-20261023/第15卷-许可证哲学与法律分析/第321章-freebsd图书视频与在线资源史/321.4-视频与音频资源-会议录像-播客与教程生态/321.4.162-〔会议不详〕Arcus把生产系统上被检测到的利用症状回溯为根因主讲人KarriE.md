- 〔会议不详〕Arcus：把生产系统上被检测到的利用症状回溯为根因。主讲人 Karri Egmann（转写音，佐治亚理工学院）与合作者指出，示例中 while 循环不检查缓冲区大小导致溢出、改写回调函数指针跳向 exec，CFI 与基于异常检测的 IDS/IPS 只能在这类症状处报警，而开发者修补需要的是根因（未检查大小的循环本身），真实评估中症状与根因平均相距约 11,000 个基本块；生产系统可用数据有限：崩溃转储可能被溢出破坏、系统日志无内部信息、记录具体输入有隐私与可复现性问题，且开发者倾向于忽视不理解的漏洞；Arcus（Analyzing Root Cause using Symbolic Execution，转写音漂作 simbex）的核心思想是用 what-if 问题测试特定输入对安全违例可满足性的影响，实现缓冲区溢出、释放后使用等漏洞类专属测试，运行时对被标记程序回放控制流轨迹、以符号分析重建中间符号状态，命中测试即生成含根因位置与初步补丁的报告。（YouTube EPNQvGv_Xob1Y，[7.8-292.2]，L1）
- 〔会议不详〕借助硬件控制流追踪规避状态爆炸与真实世界评估。现代 Intel/AMD CPU 具备健壮的追踪设施（尤其 Intel Processor Trace），能以约 7% 开销记录用户进程完整控制流，Arcus 直接在二进制上分析、无需源码或调试符号；以 2018 年一个 CVE（长命令行参数致栈溢出）为例，追踪告知该次执行恰把循环迭代 312 次，从而绕开符号执行的状态爆炸，函数末尾返回指针被输入符号改写并满足栈上控制流劫持测试；what-if（不破坏该指针会怎样）对比两状态发现约束矛盾——特定输入偏移处有无闭括号——据此在输入该校验闭括号即可修复；对 20 个真实 Linux 程序的 27 个利用全部成功定位根因，与官方补丁完全一致，并在分析已知漏洞过程中发现 4 个新的零日漏洞（严重到促成 3 个 CVE 并被开发者据 Arcus 报告修补），源码与评估数据集完全开源。（YouTube EPNQvGv_Xob1Y，[292.8-601.8]，L1）
- 〔SREcon（推测）〕监控数据的信号分类：先做对数学再谈异常检测。主讲人为 Circonus（转写音漂作 Sirona）CEO，称监控 SaaS 必须比所有客户加起来更可用，采集数据从交换机端口字节数、PDU 功耗、CPU idle 到 Twitter 情绪，既需离线建模（数月趋势回归预测）也需每秒百万/十亿量级的在线判定（那台机器坏了）；第一难是信号分类：不应直接测速率（如 CPU idle 百分比、包每秒），漏掉一个窗口便无从知晓其中发生了什么，而应测累计量再做离散正导数（rise over run），以避开重置假象；磁盘使用量则既是 gauge（容量规划）又可求导看填充速度，单信号可归入两类，静态阈值（超过 14 就告警）既费领域知识又随时间失效；Circonus 从信号提取单调性、周期、互联网流量双峰驼峰（camel pattern）等特征，用大量用户的实际使用行为投票训练贝叶斯/最大熵分类器为新信号归类——被问是机器学习吗，答曰那是数学。（YouTube EPNThyvGkU6xY，[9.7-1376.2]，L1）
- 〔SREcon（推测）〕噪声信号下的均值变化检测、lurching windows 与直方图化运维数据。滑动窗口均值内存开销过高（每秒万级采样需记住数千万个值），指数加权均值（EWMA）只需两个数却无法对历史数据重放告知用户上周本应何时报警，Circonus 用 lurching windows 折中：当日用 EWM 计算、再保留三天的每日一个数，当前日计算极廉价且效果很好；告警即对均值变化做正规的假设检验（转写音漂作 Q-sum/Q-sun 的方法，另评估非参数、比较所有可能均值的 Tukey 检验），但多数数据并非正态分布——CDN 首字节延迟呈三峰 gamma 分布（对应宽带、移动等三类用户群）——此时标准差毫无意义；Circonus 进一步采集每台机器每块盘每 IOPS 的微秒级延迟直方图（单直方图 2200 万样本、SSD 半机架每小时可达十亿数据点），以约 2.5% 误差压缩为压缩直方图传输，对提取出的模态流可应用统计模型，在数据库负载未变而单盘负载感知变化时，可比 SMART 提前约 18 小时预测磁盘故障，还能事后估计任意分位数，并把“99.5 分位小于 5ms”与“5ms 内覆盖多大比例流量”两个非线性指标一起看；Q&A 谈数学家用 SciPy（作者偏好 R）、两位有效数字的十进制分桶与约 4.8 万桶/直方图、以及减去已知基线值再测变化的技巧。（YouTube EPNThyvGkU6xY，[1382.2-2762.2]，L1）
- 〔USENIX HotEdge '20〕让边缘容器更轻。主讲人（转写中未自报姓名）围绕视觉分析、扩展现实（XR）、自动驾驶等新兴边缘应用发问：要让工作负载真正跑在边缘究竟需要哪些技术。其识别出三类阻碍云原生容器技术直接移植到边缘的问题：边缘计算能力稀缺，边缘服务器资源极为有限，是多数边缘问题的根因；应用镜像膨胀，应用依赖 TensorFlow 等重型运行时与硬件加速器，含 CUDA 支持的 TensorFlow 或 PyTorch 镜像会超过数 GB，使其无法按需部署；启动响应过慢，在典型 Xeon 平台上容器管理器启动需约 2 秒，导入 tensorflow 包还需约 2 秒。此外容器检查点恢复（checkpoint/restore）天然加剧内存与磁盘压力、且无法解决镜像膨胀，而单一长驻单体容器虽缓解资源压力却要求开发者改用新接口、放弃了容器化的既有收益，作者因此要在“不用容器”与“单体容器”之间寻找折中。（YouTube EPRSaLDPAlEv8，[8-332]，L1）
- 〔USENIX HotEdge '20〕共享后端与 Pocket。作者提出“共享后端”（shared backend）概念：把重型运行时栈剥离为一个长驻边缘服务，使其启动时间不再出现在应用启动的关键路径上，应用仍按容器部署以保留打包与分发的好处，多个应用实例共享同一后端运行时以降低资源压力。该方案被原型化为轻量系统 Pocket，把容器化应用拆成服务容器与应用容器两部分，提出由服务容器、应用容器及其通信构成的 Pocket 编程模型，并要求实现工作负载隔离、高性能 IPC、以及完全并发与运行时动态资源伸缩三项设计要素；当前实现为提升资源效率而部分妥协了这种非典型隔离理念，但仍保证命名空间隔离等基本语义。评测以 YOLOv3 的 TensorFlow 实现为基准测量从建模到查询返回的端到端延迟：单体容器方案资源占用随实例数线性陡增，Pocket 增长速度约慢 50%（源于已预热 warmed up 的服务实体），且因缓存反而取得更低平均推理延迟与更小镜像体积；不同通信机制的对比进一步表明必须保持轻量通信运行时。（YouTube EPRSaLDPAlEv8，[338-657]，L1）
- 〔USENIX Security '14〕Dual_EC 在 TLS 实现中的实际可利用性。主讲人自报 Steven Checkoway（通行拼写应为 Stephen Checkoway），报告其与来自五所高校的大量合作者关于 Dual_EC 与 TLS 实现的联合研究。Dual_EC_DRBG 是由 NSA 设计、随后经 ANSI、ISO、NIST 标准化的伪随机数生成器，标准发布后不久微软研究者 Shumow 与 Ferguson 即证明其中存在潜在后门；在 Edward Snowden 揭露 Project Bullrun、路透社报道 NSA 向 RSA 支付一千万美元使 Dual_EC 成为其 TLS 库默认 PRNG 之后，作者转而追问“若假设 TLS 中存在后门，它是否可利用、利用难度多大”——并明确本工作既不给出后门存在的概率，也不试图恢复后门密钥。他由此梳理 PRNG 的状态保密模型、椭圆曲线标量乘与 Dual_EC 的状态推进（32 字节状态经固定点 P 更新、再乘固定点 Q 取 x 坐标输出低 30 字节），说明 Shumow–Ferguson 后门攻击需要三个条件：持有秘密整数 d、看到至少 28 字节的 R1 输出、以及 R2 的某个公开函数用于校验猜测；随后在 Bouncy Castle（转写作 share）Java 库中演示恢复 Diffie–Hellman 私钥 x，用 x 计算 xP 与服务端公钥比对即告成功。（YouTube EPRT0u99-Jm0g，[10-529]，L1）
- 〔USENIX Security '14〕攻击后果与实证验证。恢复状态之后的影响更为严重：该库随后用同一生成器为 DSA 或 ECDSA 签名生成 nonce，攻击者拿到 nonce 与签名即可反推签名私钥，因此只要看到一条 TLS 连接，主动攻击者就能完全冒充服务器。作者随后给出实证方法：自行构造与 P 存在已知关系的 Q'，替换实现 Dual_EC 的常见 TLS 库——RSA BSAFE、Bouncy Castle for Java、Bouncy Castle for C/C++，以及 Microsoft SChannel 与 OpenSSL FIPS（后者实际是坏的、需一行修复）——中的 Q 及其为效率而预存的倍点表，对 BSAFE 与 SChannel 需做相当规模的逆向工程，再用 tcpdump 抓取流量运行攻击以恢复 TLS master secret。实测各实现的可选设计（随机数生成顺序、session ID 是否随机、30 字节块剩下 2 字节的缓存策略、是否把额外输入哈希进状态、2006 与 2007 两个标准版本）对攻击耗时影响巨大：有些可在笔记本上数秒完成，有些则需在小型集群上做相当规模的计算才能解开会话。结论是：后门 PRNG 能否被利用取决于 PRNG 设计、协议设计与实现选择三件事，而 NSA 恰在这三件事上都有插手（设计 Dual_EC、联合起草 TLS 扩展、付钱让 RSA 将其设为默认）。现场演示中他用 Wine 运行 Bouncy Castle C/C++ 服务端、用 OpenSSL 建连，解密耗时约 3.5 秒。（YouTube EPRT0u99-Jm0g，[572-1055]，L1）
- 〔USENIX Security '24〕揭示自动漏洞检测中机器学习的极限。Niklas Riese 与 Marcel Böhme 报告论文《Uncovering the Limits of Machine Learning for Automatic Vulnerability Detection》，作者来自德国马克斯·普朗克安全与隐私研究所（Max Planck Institute for Security and Privacy），并获 CASED（转写作 Kasa）资助。他们质疑大型语言模型在漏洞检测上“表现良好”是否名副其实：CodeXGLUE 基准基于 Defects4J 数据集，任务是对 C 函数分类判断是否含安全漏洞，UniXcoder（转写作 Unixcoder）等模型在该基准上取得接近 70% 的准确率；由于数据集类别平衡，这意味着十次判断里约七次正确。该基准所用数据集（主讲人称其为 Devign，转写作 Devine）由可能含漏洞也可能不含的 C 函数构成，例如参数 num_splits 为 0 时触发除零导致可被利用的崩溃。为探究高分是否另有解释，作者实现了一组共 11 种语义保持变换（semantic preserving transformations），例如增删注释、增删不可执行代码、把一个函数拆成两个、重命名变量或函数名等标识符、重排无关语句等，它们只改变代码外观而不改变语义与漏洞属性。（YouTube EPRVSKLyTXRCM，[8-406]，L1）
- 〔USENIX Security '24〕数据增强无法外推，VulPatchPairs 逼近随机猜测。作者先在标准评测设置下微调大模型并复现基准上六个最佳模型的成绩，再对测试集副本施加变换：准确率大幅下降，说明这些模型其实是在过度拟合语义保持变换引入的代码表层特征——只有当训练数据以与测试数据完全相同的方式变换时才能恢复性能，而训练集与测试集采用不同变换子集时结果与首轮几乎一致，即所得的鲁棒性并不能推广到新的变换。第二个实验引入新数据集 VulPatchPairs：从开源仓库提取漏洞函数及其被开发者修补后的版本组成配对，这些配对在外观上可能差异极小却在语义上截然不同；同一批六个模型在完全类别平衡的该数据集上得分接近甚至低于随机猜测的 50%。结论是：大语言模型擅长模式匹配，在测试数据与训练数据高度相似时表现良好，但漏洞检测恰恰要区分外观近乎相同、含义完全不同的一对函数，因此它们在真实漏洞检测中并不真正成功。（YouTube EPRVSKLyTXRCM，[416-618]，L1）
- 〔USENIX FAST '24〕让二十年老系统也能吃上 SSD：ONTAP 的读路径。Bharadwaj（NetApp 工程师，转写中仅出现这一个名字）介绍由 NetApp 多位工程师完成、已随产品售出多年的论文《I/O in a Flash》。约十年前闪存进入数据中心，业界普遍推倒重建以匹配 SSD 的设备特性与经济性；而当时已约二十岁的 ONTAP 是为 HDD 带宽而优化的老系统，其软件架构引入的延迟对 HDD 可接受、相对 SSD 的设备延迟却过大，ONTAP 能否做好 SSD 存储平台因而受到质疑。作者指出 ONTAP 的既有基础其实很强：它自诞生起就是日志式文件系统，在 NVRAM 中累积小块随机写再成批顺序落盘（利于 SSD 磨损管理），并已有压缩与去重等存储效率技术，只是当年作为批处理后台作业执行。此后他们把分配与擦除块大小对齐以对抗 SSD 常见的 log-on-log 问题、把存储效率技术改为在线执行以消除后台作业带来的写放大、引入 sub-block compaction 处理块内碎片并小幅调整调度器；但这些多已另行发表，本讲聚焦“房间里的大象”——读性能。他先给出从存储驱动、RAID 层到 WAFL（转写作 waffle，即 1992 年起沿用的 Write Anywhere File Layout）与协议栈的分层结构：各层拥有独立的数据结构与线程池、通过消息传递通信。（YouTube EPRVs1JjYQAkU，[16-443]，L1）
- 〔USENIX FAST '24〕层层剥离消息传递，把读路径压到微秒级。作者逐层拆解读路径：网络读请求经协议处理器解包后发给 WAFL，若数据不在内存则查元数据得块号、交给 RAID 由拓扑知识换算为磁盘 ID 与 LBA 映射并下发存储线程；返回时再经 read-done 消息做校验和与纠错、标记缓冲区有效并重跑 WAFL 读消息。这种“挂起并重启”（suspend and restart）编程模型虽易推理、可避免死锁，但消息处理器可能多次执行、带来 CPU 开销。优化依次是：把有效性从文件缓冲区下移到 page header（MP 安全、任意上下文可访问）、引入第三种 IO buffer（与文件缓冲共享页引用但不受 WAFL affinity 约束）从而消除 read-done 消息、让 RAID 直接调用 WAFL 函数填写响应向量、再把拓扑缓存改为在拓扑稳定时可被 RAID 之外访问，使 WAFL 查到映射后直接与存储线程对话、存储线程只做校验不做纠错并直接回包给客户端。NVMe 成为常态、延迟进入数十微秒量级后，作者又新增两个数据结构——存放文件偏移到块号映射（并保持对缓冲区缓存中间接块的引用及修改位图）的 storage location cache，以及存放卷在线状态、权限与 inode 大小等门禁信息的 hierarchical attributes cache，从而写出可完全绕过 WAFL 域读路径的 slim read handler；该路径运行在协议线程上下文中，因协议线程池可按带宽动态伸缩，突破了 WAFL 每卷 affinity 数量（例如每卷 8 个）对单卷负载并行度的限制。作者强调所有快路径都不违反 ONTAP 跨协议承诺的最强一致性保证（读己之写、并发读写下读操作要么看到写前要么看到写后、绝不混杂），并把经验总结为：把多数情形代码抽到精简高效路径、同时保留处理异常与错误的遗留路径，挂起重启模型让乐观尝试失败后能干净回退，对 IO 路径做外科手术式的增量优化保留了既有全部功能，比从零重建达成功能对等更划算。（YouTube EPRVs1JjYQAkU，[443-1298]，L1）
