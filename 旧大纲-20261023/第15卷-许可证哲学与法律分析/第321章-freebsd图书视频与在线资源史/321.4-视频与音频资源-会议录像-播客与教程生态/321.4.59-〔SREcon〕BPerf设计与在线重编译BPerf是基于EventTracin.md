# 321.4.59 〔SREcon〕BPerf设计与在线重编译BPerf是基于EventTracin

- 〔SREcon〕BPerf 设计与在线重编译。BPerf 是基于 Event Tracing for Windows（对应 Linux/BSD 的 perf/DTrace）的常开 CPU 采样剖析器：把默认采样率降低一个数量级至每 10ms、每次暂停全线程仅约 100μs，p95-p99 延迟几乎不受影响；周期性内存采样（每 5 分钟采 30 秒，托管内存每 100KB 分配采样一次调用栈）、磁盘/网络 I/O 记录，并标注 .NET 的 GC、异常（含被吞掉的异常）与 JIT 事件供 SRE 或自动化工具排除干扰请求；数据中心级聚合可见单机看不出的开销（如 fleet 中 2% CPU 用于 UTF-16 到 UTF-8 转换），并对 JIT 地址做规范化；最激进的低层能力是运行中重编译方法、注解局部变量/参数、在线加 try/catch 以直接缓解现场事故，并计划对热点方法做在线优化。（YouTube EP8dBhT8WJhYA，[753-1550]，L1）
- 〔NSDI〕CDN 边缘的服务器不可用与写负载不均衡问题（C2DN 背景）。主讲人 Juncheng Yang（与 UMass、Akamai、UW、Microsoft Research 合作）基于 Akamai 2000 多个集群一个月的 trace，发现服务器不可用出现在超过 45% 的五分钟观测中（典型边缘规模的集群超 30%），远多于传统数据中心；CDN 按域名等 bucket 粒度做一致性哈希路由，单台服务器不可用会使其上全部缓存对象失效并引发 miss ratio 尖峰，损害体验甚至违反 SLA；复制方案把尖峰从 200% 以上降到约 30% 却无法消除，还使平均 miss ratio 相对上升约 30%，根源在于缓存写入高度不均衡——10 台服务器集群中最大写服务器比最小者多写 2.5 倍，导致副本提前被淘汰、SSD 磨损速度不一而推高维护成本。（YouTube EP8g7XE98kmVk，[13-452]，L1）
- 〔NSDI〕C2DN（Coded CDN）设计与评估。引入纠删码提供容错：3 数据块+1 奇偶块仅 33% 存储开销，远低于容忍同等故障所需的 200% 三路复制，可缓存更多对象降低 miss ratio；但朴素使用会因各块被不同时间淘汰而失去容错且有每请求跨机取块的运行时开销，因此第二个技术 parity rebalance 利用奇偶块放置灵活性，把奇偶块分配建模为最大流问题（用交换解法算法求解）实现接近完美的写负载均衡，使各服务器淘汰速率与 SSD 磨损一致。在 Apache Traffic Server 上实现并重放 Akamai 真实 trace、用户/CDN 集群/源站分布 3 个 AWS 区域评估：不可用发生时 miss 曲线几乎与 x 轴重合（无尖峰），常态 miss ratio 显著下降，首字节与下载时延无可感知变化，CPU/磁盘用量仅略增。（YouTube EP8g7XE98kmVk，[455-904]，L1）
- 〔OSDI〕亚稳态失效（metastable failure）在野研究的问题定义与调查。主讲人 Lexiang Huang（Penn State，与 UNH、Twitter 合作）以重试风暴示例定义亚稳态失效：触发器（如备份任务干扰使容量从 1000 降到 600 rps）移除后系统仍因维持效应持续过载；AWS 过去十年 15 起重大宕机中 4 起源于此，业界以 persistent congestion、retry storm、death spiral 等各种名称与临时手段应对。团队梳理 600 多份公开事故报告识别出 21 起亚稳态失效（AWS、Microsoft Azure、Google 到 Elastic Cloud、Apache Cassandra 等），宕机时长 1.5 小时到 3 天以上、多为 4-10 小时；Spotify 为排查重试风暴在错误路径加日志反而抬高单请求成本、加剧失效。统计上约一半触发源于工程师失误、约三分之一为负载尖峰、45% 事故含多重触发，重试导致的负载放大是最常见的维持效应（超 50%），另有昂贵错误处理、锁争用、ZooKeeper 等协调服务选主抖动引起的性能退化；恢复手段以直接与间接 load shedding 为主（含重启清队、关闭机器学习特性换性能）。（YouTube EP8iMlUcmyHAc，[13-458]，L1）
- 〔OSDI〕2x2 分类模型、GC 亚稳态实例与教训。模型将触发分为负载尖峰与容量下降两类、放大机制分为负载放大与容量退化放大两类，组合出四类基本场景（多重触发与多重机制是其叠加）；本讲聚焦最初在 Twitter 发现、并在受控环境复现的负载尖峰触发+容量退化放大象限：高队列长度导致 GC 周期中活跃对象更多、内存压力更高而 GC 时长变长，GC 停顿又拖慢处理使队列继续堆积形成正反馈，即使激进 load shedding 降载 30% GC 行为仍居高不下。实验发现脆弱性有程度之分：系统负载越高、触发亚稳态所需触发越小（效率与脆弱性权衡），同等负载与触发下增大最大堆即可避免亚稳态。教训包括尽快检测并响应触发器、设计时消除级联效应（不能消除则尽量缩小维持效应、兼顾慢路径）、通过负载测试理解系统脆弱程度并调优相关配置；陷入亚稳态后需先修复全部触发器，再以准入控制、优雅降级、增容或降低最大重试次数打破维持效应；团队开源了三个亚稳态失效示例供研究。（YouTube EP8iMlUcmyHAc，[460-921]，L1）
- 〔USENIX Security〕eBPF 验证器瓶颈与硬件辅助隔离环境 HIVE 的动机与总体设计。主讲人 Patrick（Peihua Zhang）梳理 eBPF 执行环境（11 个寄存器、map、helper、栈）与验证器机制，把其全部安全检查归纳为 20 条安全属性并对应到内核完整性、机密性与可用性三目标；指出验证已构成 eBPF 瓶颈：正确性困境（不安全程序通过验证，验证器贡献了过去十年 eBPF 相关 CVE 的大头）与能力困境（安全但复杂程序因状态探索被拒绝）。核心洞见是把 BPF 程序视为一类内核态应用、借鉴用户态进程隔离：利用 AArch64 非特权 load/store 指令提供基于 EL 的内存隔离、为 BPF 数据设立独立地址空间消除内核层信息泄漏、以异常回滚机制保可用性（开场所称平台以 AArch64 为准，转写中 RISC-V 为音译漂移）。（YouTube EP8jhFEv_wK0A，[8-335]，L1）
- 〔USENIX Security〕HIVE 细节设计与评估。针对 BPF 程序与内核紧耦合的挑战（元数据嵌入 BPF 对象、需合法访问内核对象特定字段），以切换 BPF 栈指针把 BPF 栈与内核栈分区、分离其他对象元数据并映射进非特权 BPF 空间；JIT 阶段把访存指令变换为非特权形式，并用权限差异隔离用户空间与 BPF 空间；非特权 load 将 Spectre 转化为 Meltdown 型攻击，由 CSv3 硬件补丁阻止权限错误下投机加载数据形成地址而无须额外开销；对指向特权页内核对象的包含型指针，则用 ARM pointer authentication 保证指针完整性与类型安全。评估分三部分：对安全属性构造的攻击均被缓解；加载 100 多个 BPF 程序并运行 Nginx、Redis 实测吞吐下降小于 5%；把 10 个内核模块编译为 eBPF 程序（皆因无界循环或分支过多被验证器拒绝）后在 HIVE 中全部成功运行，验证了能力困境的解决。（YouTube EP8jhFEv_wK0A，[340-682]，L1）
- 〔USENIX Security〕基于计时侧信道的 Linux 内核堆利用技术 Pspray 的问题分析。主讲人 Yoochan Lee 分析 Linux slab 分配器两个机制如何导致堆利用不可靠：对象分配经由 CPU 随页（cpu slab）进行且会中途切换，UAF 利用要求漏洞对象被释放后目标对象落到同一地址，一旦利用过程中 cpu slab 切到别的 slab 目标对象便落错位置；freelist randomization 则随机化分配顺序，攻击者不知目标 slab 已分配多少目标对象，堆溢出利用难以保证漏洞对象与目标对象相邻。核心发现是内核按堆状态实现多条分配路径，其中经 buddy allocator 创建新 slab 的慢路径明显更慢，通过测量分配耗时即可推断内核堆的分配状态。（YouTube EP8kHBIQiSjBQ，[8-357]，L1）
- 〔USENIX Security〕Pspray 应用、评估与缓解。利用计时侧信道检测到新 slab 创建后，先分配 m-1 个 spray 对象填满该 slab 并将其转入 full list，把它锁定为利用专用 slab：UAF 场景中 cpu slab 不再中途切换、目标对象可落到同一地址；堆溢出场景中先放 m-1 个目标对象、预留最后位置给漏洞对象使二者必然相邻（仅当漏洞对象恰在 slab 末位的例外情形失效，概率极低）。评估 6 个 UAF 漏洞，基线普通释放+目标分配约 70% 成功率，应用 Pspray 后升至约 100%；4 个堆溢出场景基线约 30%，应用后大幅提升。并提出缓解：新增慢路径把新 slab 先放入 cpu partial page 延迟使用，使新 slab 的使用时机不可预测，从而掩盖侧信道；作者认为此类逻辑流同样存在于其他内核代码，因为开发者普遍未把计时侧信道纳入考虑。（YouTube EP8kHBIQiSjBQ，[358-767]，L1）
- 〔NSDI〕无状态高速负载均衡器 CHEETAH（转写亦作 Chita/shita/Gita）的核心思想。主讲人 Tom Barbette 指出负载均衡器四大需求——每连接一致性 PCC、均匀负载、高效、可动态增删服务器——今日方案无法同时满足：ECMP 等哈希方案高效但增删服务器必断连接，记住每连接状态的有状态方案均匀且动态却因大表低效且耗尽资源；CHEETAH 换一种方式回答“这条连接由哪台服务器处理”：把负载均衡决策存入连接包头的 cookie（嵌入 TCP timestamp 高位，不破坏 RTT 计算与序号回绕保护，亦可置于 QUIC connection ID 或 IPv6 地址低位），让 cookie 随每个数据包返回，从而支持任意可实现的负载均衡逻辑（round robin、最少负载、新增服务器优先等），且负载均衡器失效时状态随包返回、天然高弹性；再以服务器 ID 与四元组哈希的 XOR 混淆 cookie 防止攻击者定向打单台服务器，并提供修改版 Linux 内核在服务器侧做 cookie 校正以支持直接服务器返回。（YouTube EP8knKKir5IXM，[5-455]，L1）
- 〔NSDI〕CHEETAH 两版实现与评估。无状态版为全功能软件实现，4 核支持 100G 网络，另在 P4 Tofino 原型上可达数十 Tbps（因 NDA 未公开）并以 P4-16 重写开源；包处理比 DPDK 布谷鸟哈希表实现的有状态负载均衡器快 5 倍、与最优哈希方案相当，即以无状态分类的价格获得有状态分类的全部优势，尾延迟较哈希降低一半。状态ful 版在 cookie 中编码流表索引，直接索引状态表实现常数时间查找，并用空索引栈实现常数时间插入与删除，使整个方案可在硬件数据平面完成（P4 原需经控制平面插入而成为瓶颈）。负载均匀性实验显示哈希带来 20-30% 服务器负载方差（与 Google Maglev 报告的约 30% over-provision 一致），round robin 可将方差降至近零、99 分位流完成时间降低 2-3 倍；双峰负载下轮询失效，power-of-two choices 与按负载自动调权的 weighted round robin 再把尾延迟降低 2 倍；论文还讨论多级有状态负载均衡扩展时仍需无状态层分发、增删有状态均衡器仍会断连（这也是 Google Maglev、Microsoft Ananta 即使有状态仍用哈希的原因），并建议将 cookie 机制标准化，实现、数据集与实验开源在 GitHub。（YouTube EP8knKKir5IXM，[456-1115]，L1）
- 〔会议不详〕当系统变大、负载变重时往往变得难以预测，主讲人 Baron Schwartz（个人网站 xaprb.com，VividCortex 创始人）讲授如何建立负载与扩展性的心智模型。他借用 Jens Rasmussen 的安全边界模型刻画系统运行域（operating domain）：经济失败、不可接受负载与安全三条边界，真实边界不可知，只能画出人为的政策线（如 CPU 90% 告警、银行透支保护、超额预配），并引用 Richard Cook 的《How Complex Systems Fail》说明系统永远运行在部分降级模式、靠人的适应性维持。他把负载定义为区间内所有驻留时间之和除以区间长度所得的平均并发（average concurrency），并论证利用率（utilization）不适合作为负载度量：利用率上限为 1，而负载可趋无穷，系统过载时利用率无从反映。（YouTube EP8omPFYif3J8，[31-1119]，L1）
- 〔会议不详〕后半场讲解通用扩展性定律（Universal Scalability Law）：吞吐量是并发的函数，Amdahl 定律引入不可并行化分量 sigma 使曲线渐近封顶，而并发协调开销（作者称为 crosstalk，参数 kappa，最坏为 n(n-1) 对交互、即 O(n^2)）造成收益递减甚至负扩展（retrograde scalability）。他强调无需直接测量 sigma 与 kappa，只需采集吞吐量与并发数据点（如 MySQL threads_running、Apache server status 的活跃 worker，或用 Little 定律由时延求和折算平均并发），再用 Excel 或 Python 做回归拟合参数即可；并举 PayPal 比较高并发 Java 与单线程 Node.js 的基准测试为例，散点图边缘发散即说明系统已进入降级区。问答中他补充队列长度属于总并发的一部分、load average 本质也是队列长度，且 USL 同样适用于团队协作（如 Brooks 定律与 Adrian Colyer 的相关博客）。（YouTube EP8omPFYif3J8，[1346-2251]，L1）
- 〔FAST〕（推测）主讲人 Yuvraj Patel 提出对抗性同步（adversarial synchronization）这一新问题：攻击者可人为膨胀共享数据结构，导致重锁争用、性能骤降甚至拒绝服务，波及参与系统的多个受害者租户。他演示对 Linux 内核 inode cache 的真实攻击：挂载可自选 inode 编号的 FUSE 文件系统，通过精心构造的碰撞逐位破译出 superblock 指针，再向单一 hash bucket 灌入大量条目；受害容器中运行 Exim 邮件服务器的实验显示，攻击启动后数秒内吞吐即下降达 12 倍。攻击分为同步攻击（膨胀数据结构的同时持续参与抢锁）与构陷攻击（framing attack）两类。（YouTube EP8tpmKadVT68，[9-429]，L1）
- 〔FAST〕（推测）后半场介绍缓解框架 ThraThra（Strata）：随机探测锁等待时间检测攻击，按用户记录内核对象分配并在对象上打租户标记以定位攻击者，通过限时禁止攻击者继续分配对象阻止数据结构扩张，并对 cache 类结构逐条驱逐攻击者条目、对非 cache 类结构动态创建仅供攻击者访问的影子数据结构实现隔离恢复。评估显示原生 Linux 下 Exim 吞吐掉 12 倍，而 Strata 能快速检测并缓解攻击、性能影响极小，可同时应对多个攻击；攻击脚本与源码均已开源。（YouTube EP8tpmKadVT68，[504-853]，L1）
- 〔会议不详〕主讲人（与普林斯顿合作者及导师 Vincent Liu 教授团队）介绍 OpWave——利用网络中未被使用的带宽做网内协调的框架。他指出时钟同步、故障检测、拥塞通知、网内遥测等非用户流量常被配置为高优先级并直接挤占网络容量，迫使协议在协调保真度与带宽开销之间取舍；而实测与已有研究均表明亚微秒级包间间隙（interpacket gaps）在用户流量中普遍存在。OpWave 提出 weave stream 抽象：以可携带自定义信息的空闲（idle）包填充用户包之间的间隙，并保证 R1 可预测性（任意两包间隔有界，100GbE 链路、1500 字节 MTU 下约 120 纳秒）与 R2 不影响用户流量吞吐、丢包率与交换机功耗。（YouTube EP8u1qV37GFUA，[15-336]，L1）
