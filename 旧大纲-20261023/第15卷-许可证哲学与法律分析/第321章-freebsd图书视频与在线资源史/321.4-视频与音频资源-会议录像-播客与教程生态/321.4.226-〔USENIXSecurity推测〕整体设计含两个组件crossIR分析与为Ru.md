- 〔USENIX Security（推测）〕整体设计含两个组件：cross-IR 分析与为 RustSan 访问校验模型改造后的影子内存〔05:56〕。分析从 Rust 专有的 MIR 开始，因为 Rust 语义如 unsafe 在 MIR 阶段才被消耗；他们在 MIR 层做分析，并把结果作为指令元数据传播到 LLVM IR〔06:10〕。MIR 分析把对变量产生变更的 MIR 语句认定为 unsafe object 的出生地，然后把提炼出的信息通过给对应 LLVM 指令打标签传到 LLVM 阶段，从而把两种 IR 无缝衔接起来〔06:21〕。带着 MIR 传来的元数据，LLVM 分析做数据流分析以识别全部 unsafe object 分配，再用基于先进工具 SBP 的指针分析找出可能访问 unsafe object 的 false safe 点，其余站点判为安全，随后再次遍历数据流图以找出与 false safe 点相连的全部 overlapping object〔06:49〕〔07:21〕。带着站点与对象的安全信息，LLVM 编译器 pass 在对象分配点及其访问点上做插桩〔07:31〕。原始 ASan 中影子内存的颜色检查是二值的，RustSan 则按对象安全级别把对象染成三级颜色——safe 对象为红色、overlapping 对象为粉色，因此 RustSan 扩展了 ASan 的影子内存实现以反映 Rust 的安全模型〔07:45〕；对象按安全染色后，访问点也按其安全性插桩，安全点因此从不必要的消毒器检查中解脱出来，运行时性能显著提升〔08:00〕〔08:21〕。采用带颜色的检查后，false safe 点可以访问 overlapping 与 unsafe 对象但不能访问 safe 对象，而 unsafe 点只能访问 unsafe 对象、不能访问其他类型对象〔08:30〕〔08:40〕。评估部分，他们收集全部 Rust 内存安全 CVE 并用 RustSan 复现以展示检测能力，另从 crates.io 收集 20 个真实应用，用 ASan 与 RustSan 分别构建其基准〔08:50〕。在 33 个流行站点上，RustSan 平均把 93.8% 的代码判为安全，意味着它在绝大多数内存访问点上去掉了检查〔09:24〕。检测能力方面，他们从漏洞库调查全部 Rust CVE 并挑出可用 ASan 复现的那些，再用 RustSan 做检测测试：即便移除了 94% 的检查，RustSan 仍成功检测到 ASan 能检测到的所有 CVE，其中 66% 被作为 false safe 点检出，体现了跨层分析的有效性与准确性〔09:41〕〔10:01〕。这些案例正是“错误生于 unsafe、却显形于 Rust 完全安全部分”的内存错误〔10:08〕。性能方面，在流行 Rust crate 上 RustSan 平均带来约 62% 的提速，但各 crate 差异明显，因为收益来自减少影子内存检查的命中次数——若某测试执行期间高频遇到如今被免除检查的安全点，提升就很大，反之若执行点多为 unsafe 或 false safe，提升有限；例如 UUID 与 Adler 提升显著，VectiQ 则几无提升〔10:30〕。图中红线代表相对 ASan 的运行时影子检查命中次数下降幅度，与性能提升高度相关，验证了 RustSan 设计的有效性〔11:19〕。（YouTube EPYldjPs9Y1eM，[355-712]，L1）
- 〔USENIX ATC（推测）〕Google 的 Xiao Hongli 介绍 Thunderbolt：面向吞吐量优化、服务质量感知的规模化功耗封顶。先从动机说起：数据中心很贵，2019 年行业投入超过两千亿美元，因此在每个数据中心里塞进尽可能多的容量非常划算〔00:09〕。功耗超订阅是有效手段——功耗常常是数据中心的限制资源，但整个集群的聚合功耗很少接近理论最大值，因为许多机器的功耗不太可能同时到达峰值，所以可以在名义供电能力之上部署更多机器〔00:28〕。然而功耗尖峰虽罕见也并非不可能，因此需要一个保护系统以避免罕见尖峰过载供电设备；功耗封顶就是这样一种保护系统，它通过节流数据中心内运行的任务来削峰，但又必须在任务的服务等级目标之内做到〔01:16〕。他接着说明为何必须区分任务的服务质量：大致有两类任务，吞吐量导向类只需在数小时量级完成，例如网页索引与日志处理，它们可以接受性能节流但不能被中断，因为中断会浪费已做工作、可能违反吞吐量 SLO〔01:45〕；延迟敏感类需在毫秒到秒量级响应请求，例如 Web 前端与搜索服务，它们无法接受性能节流，否则会失去响应性〔02:11〕。问题在于他的数据中心里两类任务被放在同一批机器上，因为集群调度器把优先级与服务质量分配给任务而非机器，这提高了机器利用率却也带来挑战，因此目标是做一个任务级服务质量感知的封顶系统，温和地节流吞吐量导向任务、豁免延迟敏感任务〔02:47〕。现有工业方案无法满足：要么任务级感知但动作具破坏性，要么节流温和却导致过粗的质量区分〔03:21〕。Thunderbolt 同时达成四个目标：在性能退化最小的前提下保障功耗安全、任务级服务质量区分、硬件平台无关，以及容忍功耗遥测不可用〔03:45〕，并称它已在 Google 数据中心规模化部署多年，让日志处理集群得以实现此前不可能的 9% 到 25% 超订阅〔04:11〕。架构含两个子系统：功耗信号可用时的反应式封顶主子系统，以及功耗信号不可用时的主动式封顶切换子系统〔04:29〕。反应式路径是：中间 watcher 模块从数据中心电表读取功耗读数并交给 power notifier 模块，同时在功耗历史存储里存一份副本；power notifier 把读数与来自功耗拓扑数据的上限比较，用待展开的 load shaping 策略做出节流决策，再交给 machine manager 模块并发地把节流 RPC 发给分布式节点控制器，最终由 load controller 用稍后介绍的 CPU 带宽控制机制排序并节流任务〔04:56〕。主动式路径在功耗信号不可用时启动：risk assessor 模块从存储读取功耗历史、评估功耗达到上限的风险并把结果交给 power notifier 做决策，其后流程与反应式相同，只是节点控制器改用另一机制 CPU jailing 来节流任务〔05:55〕。（YouTube EPYmZ7ELFPDRs，[9-360]，L1）

- 〔USENIX Security（推测）〕Brian Wickman 报告用快速前向分配防御释放后使用（UAF）攻击，并用原型分配器 FFMalloc 说明“一次性分配”这个长期被弃用的想法其实是个合理的 UAF 解法〔00:09〕。先讲问题：UAF 是常见内存安全错误，即错误地访问程序先前已释放的内存；若该内存被重分配时能被攻击者控制的值填充，正常程序执行就可被劫持，这样的指针 p 称为悬垂指针〔00:29〕。示例里 p 在被 free 后仍被解引用，后果取决于分配器行为〔00:43〕；虽然简单示例中 bug 很明显，真实代码里很难发现——free 可能离 use 很远，甚至没有显式 free，而是悄悄藏在 realloc 调用里〔01:00〕。攻击演示：在先前片段上再加一次 malloc 与一次从网络连接的读入，因为 p 与 q 尺寸相同，多数分配器会把 p 释放的槽位重新分给 q，于是指向攻击者可控数据的 q 也使 p 可控；如果最后一个 if 语句守护的是安全敏感代码，攻击者就能按需进入或绕过〔01:19〕。已有对策包括指针失效器（试图找到并中和悬垂指针）、定制编译器（加运行时检查确认指针仍有效）与保险分配器（对已释放槽位随机延迟复用），但都没被广泛接受——大多带来不可接受的 CPU 开销，或保证不够强、不足以在实际生产工作负载中部署、只适合调试工具〔01:53〕〔02:03〕。最简单也最明显的对策是一次性分配原则：程序生命周期内，任何先前释放的虚拟地址区间都不应被用于新分配〔02:37〕。它无法消除应用里的 bug，但使攻击者无法利用〔02:44〕：分配器不再把 q 分配到与 p 相同的地址，程序仍在错误地解引用 p，但结果不再受攻击者控制；若 p 的虚拟内存区域仍有效，其内容未被改动，程序就像 free 从未发生一样继续执行，反之若该区域已被解除映射，则触发故障、程序终止〔03:03〕。尽管如此，这个显然的解法长期未被认真对待，批评也同样显而易见：频繁的缓慢内存映射系统调用会吃掉 CPU、碎片化的地址空间会浪费内存、而小指针宽度会很快用尽所有可用地址〔03:31〕。但有了 64 位巨大的地址空间，作者认为该重新评估这个简单有效的技术，并证明 CPU 与内存开销可以通过仔细的系统设计加以控制〔03:52〕。第一次实现 Forward-Continuous Malloc 用简单的 bump pointer 方案：每次新分配都比先前任何分配都高，新页面按需映射、页内全部分配释放后页面再解除映射〔04:08〕；结果如预期遭遇不可接受的 CPU 与内存开销——小而长寿的分配阻止了本来空闲的页面被释放，还有严重的内存碎片；这些小长寿分配在虚拟内存空间里形成孤岛并被内核的 VMA 结构跟踪，默认应用最多只能用 6.4 万个 VMA，耗尽后甚至无法再映射或解除映射地址空间〔04:22〕〔04:47〕。为此他们加入按批解除映射：必须先释放最少连续若干个页面才真正释放，这显著降低了 CPU 开销并缓解了 VMA 耗尽问题〔04:58〕。第二次尝试 Forward-Binning Allocator 只从若干固定尺寸中分配（即 BBO allocator），通过把相同尺寸的小而长寿分配同置于同一批页面上降低了 VMA 压力，但分配必须向上取整到下一个固定尺寸 bin，又引入过度分配造成的额外内存压力〔05:24〕；最终方案把 FCMalloc 与 FBMalloc 的思想合并进同一个分配器：大分配用 bump pointer 以避免过度分配的浪费并保留按批页面管理，小分配从固定尺寸 bin 中分配，从而让小分配聚在一起、不拖住 bump pointer 区的页面释放〔05:57〕。（YouTube EPYmvSM31HtqU，[8-357]，L1）
