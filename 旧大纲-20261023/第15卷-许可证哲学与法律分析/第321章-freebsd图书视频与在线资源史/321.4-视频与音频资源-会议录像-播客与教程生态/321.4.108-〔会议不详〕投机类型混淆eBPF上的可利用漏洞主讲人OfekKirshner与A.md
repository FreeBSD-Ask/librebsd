- 〔会议不详〕投机类型混淆：eBPF 上的可利用漏洞。主讲人 Ofek Kirshner（与 Adam Morrison 合作）研究野外存在的投机执行类型混淆漏洞；在回顾 Spectre V1 边界检查绕过与 Linux 的 array_index_nospec 手动缓解后，把投机类型混淆定义为错误推测使受害者以错误类型的变量值执行并泄露内存内容，此前只在面向对象多态代码中被假设；在 Linux eBPF 子系统中演示攻击：验证器静态分析时不考虑投机执行，会接受含类型混淆 gadget 的程序（寄存器 r0 指向 eBPF 数组项、r6 指向栈、r9 为攻击者可控标量，两个互斥分支经合法执行枚举被判定安全），若两条分支被同时预测为 taken，投机执行会解引用 r9 泄露任意内核内存。（YouTube EPGxv6LcabKrg，[7.9-357.5]，L1）
- 〔会议不详〕编译器引入的混淆、Spectre V2 缓解放松与结论。由于两分支互斥无法原地训练，作者在用户态构造结构相似但分支不互斥的影子 gadget，使其分支地址映射到与 eBPF 代码相同的分支预测单元表项做异地训练，以非特权进程每秒 6.5KB 的速率读取任意内核内存；二进制级分析发现 GCC 可能把无害代码（如互斥 if 块间移动攻击者可控值 x 到 rsi 寄存器）优化成投机类型混淆 gadget，多见于接收可选不可信用户指针的 syscall；针对用直接条件分支替代间接分支来廉价替代 retpoline 的 Spectre V2 缓解提案，作者在 Linux 内核接口多态/数据继承实现中发现数千处两个实现把内核指针与用户可控标量重叠在同一偏移的模式（其中数百个用作数组索引），人工分析当前因投机窗口或取值限制不可利用，但良性代码变更即可使其可利用，结论是大规模采用基于条件分支的缓解将使内核安全岌岌可危，投机缓解难以靠程序员人工推理。（YouTube EPGxv6LcabKrg，[357.5-715]，L1）
- 〔FAST（推测）〕文件系统配置依赖的分类学研究。主讲人为文件系统研究者（与导师 Mai Zheng 及同事合作，论文题为分析文件系统配置依赖 for fun and profit）；文件系统生态由 mke2fs、mount、e4defrag、e2fsck、resize2fs 等四阶段工具构成，配置组合可引发隐蔽 bug：Windows 上 checkdisk 参数组合损坏 NTFS 文件系统、mke2fs 启用 sparse_super2 后再用 resize2fs 扩容导致元数据损坏；状态爆炸（ext4 超过 85 个配置参数）与默认测试套件参数覆盖率不足 50% 使组合测试不可行，现有研究只覆盖拼写错误等浅约束；团队对 78 个 bug 补丁的关键词检索、随机抽样与人工检查归纳出四项发现，核心是配置依赖分三类：self（组件内参数满足自身约束）、cross-parameter（同组件两参数互斥，如 resize inode 与 meta_bg）、cross-component（跨组件，如 mke2fs 的 inline data 与 mount 的 dax 不能同时启用否则数据损坏），100% 案例涉及 self 依赖、96.2% 涉及跨组件依赖，且多数案例无需配置特定工作负载即可触发。（YouTube EPGygCZSnT-_8，[13.6-554.8]，L1）
- 〔FAST（推测）〕ConD 框架与在 ext4/XFS 上的评估。ConD 由 core 与 plugins 组成：污点分析器（过程内、过程间且上下文敏感）借共享 superblock 元数据结构（如 inode size 存于 superblock 第 27 字段）连接 mke2fs 与 ext4 等组件，依赖引导的状态生成器按深度 3 建树并分遵循/违反依赖两种策略生成有效与无效状态；六个插件覆盖 man page 规约检查、错误配置处理检查、集成两个开源原型（RFGK 与 GT Hydra 模糊测试）以及 xfstest、e2fsprogs 回归测试套件；评估从 ext4 与 XFS 自动提取 154 个唯一依赖（误报 8.4%），发现 e4defrag 在启用 bigalloc 的文件系统上运行会损坏镜像（源码有注释但无文档与防护）、man page 中 17 处未文档化或错误的依赖，rfsck 集成触发两种新症状（不可挂载镜像与无效文件内容）；与 Facebook Hydra 对比，10 个 mke2fs 参数下 ConD 只生成 30 个状态而 Hydra 生成 5.6 万个且含大量重复与无效状态；未来工作包括扩展到其他文件系统与数据库、集成 Facebook Hydra 与 CI/CD。（YouTube EPGygCZSnT-_8，[554.8-1109.5]，L1）
- 〔会议不详〕Mulberry：带修改开源组件中的可传播漏洞代码检测问题。主讲人 Seungwoo Noh 来自韩国高丽大学（Korea University），与 Han Ji-hong、Eunjin Choi、Heejoo Lee 合作；开源软件复用成为趋势但无管理复用会传播漏洞，而漏洞代码在传播时几乎总带语法修改：一是 OSS 内部更新（Lua 团队在 5.2.3 修复了一个 DDoS 漏洞，而 Redis 复用了旧得多的 Lua 5.1，多个版本迭代使两份含同一漏洞的函数语法迥异），二是开发者复用时的外部修改；现有方法因此失效：ReDeBug 以补丁附近三行删除/新增代码为签名（传播代码不含这 7 行签名则漏检），BoDDy 以整个漏洞函数为签名（语法差异大则漏检），由此提出 Mulberry 用函数比对与核心行提取精确发现各种语法的可传播代码。（YouTube EPGyjTgR497Qs，[7.8-327.5]，L1）
- 〔会议不详〕Mulberry 机制与评估结果。Mulberry 先把最早漏洞函数与公开披露函数做函数比对（collation），提取 essential（补丁删除且两版本皆有的行）、dependent（与 essential 有控制/数据依赖，判断漏洞触发环境是否一并传播）与 control-flow（两版本皆有的控制语句，应对开发者加条件语句消毒的修复）三类核心行生成漏洞签名，再对补丁新增行类似地生成补丁签名；目标函数需同时满足包含全部漏洞签名行、不含任何补丁签名行、与最早或公开漏洞函数的 Jaccard 相似度（阈值 0.5）足够高才判定为可传播代码；在 NVD 的 4000 余个 CVE 补丁与 10 个流行目标程序上发现 434 个可传播漏洞代码，精确率与召回率均达 96%，比 ReDeBug、BoDDy 分别多发现 2.5 倍与 5.8 倍，且 91% 的发现与公开漏洞函数语法不同，验证了带语法修改传播的普遍性。（YouTube EPGyjTgR497Qs，[327.5-655.1]，L1）
- 〔会议不详〕Carver：Azure 上的高效可扩展云准入控制。主讲人 Sultan 介绍 Carver（转写中亦被读作 Kerberos）——由 Microsoft Research、Microsoft Azure 与 Penn State 合作并已在 Azure 现网部署的准入控制系统；供应链短缺与需求激增使精确计量云资源空前重要，而 Azure 数百万机器、超 1000 种 VM 类型（从 1 核 2GB 到 448 核 24TB）、过半可用区支持 900 多种 VM 类型、部分区域多达 40 种硬件类型，碎片化与容量预留使能否接受新请求远比 total 减 allocated 复杂，还须尊重跨拓扑放置约束；供需随时间波动（短期 VM 请求尖峰、长期宏观经济影响），系统须满足每分钟超 12 万请求、平均时延 5-10ms，1% 的资源效率提升即相当于每年节省超 1 亿美元；核心思想是对预留资源做晚绑定（late binding），在领取时而非准入时绑定具体硬件，从而获得高装箱效率、准确记账、灵活装箱、快速准入，并能把未领取预留复用为 spot VM 以最大化 ROI。（YouTube EPGzJJ9IQIe3U，[15.8-452]，L1）
- 〔会议不详〕allocable VM 记账、CRA/LAA 算法与实证结果。晚绑定的风险示例：两机集群总容量 200、未领取预留 120，若预留由 6 个 20 的小 VM 组成则准入 50 请求后仍可领取，若由 2 个 60 的大 VM 组成则客户领取失败构成 SLA 违约，说明准入必须考虑预留形状；Carver 的 allocable VM 记账技术把 CPU、内存、磁盘等多维需求转换为单一计数，跟踪每种 VM 类型还能放入多少额外 VM；快组件 CRA（转换比率算法）用内存中放置快照按 VM 类型独立计数并扣减预留换算，每分钟运行实现快速可扩展准入，但保守舍入造成碎片浪费；慢组件 LAA（线性调整算法）用请求生成器做分配仿真并送 ML 平台校准 CRA 参数，每 30 分钟运行保证准确记账；仿真显示资源效率显著优于分区与立即绑定的 placeholder 方案，一个月生产数据达到四个 9 的稳定可用性，且 AV 计数计算随机器数增长扩展良好、不给分配引入新开销。（YouTube EPGzJJ9IQIe3U，[452-903.8]，L1）
- 〔会议不详〕Android root exploit 检测的动机与关键观察。主讲人 Boru Chen（转写作 Chuyin Chen）来自 UC Riverside；Android 高度碎片化定制（厂商、芯片、运营商都改代码库），近三个月 Android 安全公告中超 100 个可致提权的 CVE（大多在驱动与 AOSP，且不含三星/华为私有漏洞与闭源驱动组件）；root exploit 被恶意软件滥用（可获得 root 后持久化、键盘记录、广告注入并配合混淆/反调试难检测，曾有一个伪装 Pokemon Go 指南的应用下载超 50 万次存活数月），且因设备驱动差异与内核内存布局不同，exploit 需大量定制变体；目标是做类似 Google Bouncer 的云端应用筛查系统（只针对已知漏洞，零日不在范围内）；关键观察有二：一键 root 应用封装了专业 exploit（单个应用即提取出 167 个 exploit 二进制、59 个家族，号称支持超 10 万种机型），且 exploit 被大量复制复用，因此可从中学习各 exploit 的设备环境与程序前置条件。（YouTube EPGzbN-d8q2V4，[11.3-815.5]，L1）
- 〔会议不详〕Root Explorer 的设计与评估。系统分离线学习（从一键 root 应用提取 exploit 二进制并去混淆，静态抽取编码数据与控制依赖及程序前置条件的行为图——root exploit 必经系统调用与 OS 交互，故该表示适用）与在线测试（分析环境按目标机型仿真，经基于 IDA Pro 的符号执行引擎推导系统调用应返回的值，例如让 readline 返回 20 个无约束字符加 kernel code 子串以驱动 exploit 走到成功点；内核模块做 syscall 钩子、用户态后台服务决定每次调用返回并匹配行为图，全图匹配即标记为恶意）；实验用 Android 模拟器（灌入真实通话记录、短信、IMEI 与 build.prop 抗指纹）配合 UI 自动化（Monkey）每应用跑 10 分钟；评估显示 VirusTotal 对混淆编译的 exploit 漏检一半而 Root Explorer 无论编译方式都 100% 检出，Godless 恶意软件在 5 台仿真设备上触发不同 exploit，灰色样本中从第三方市场 2000 个新上传应用检出含 PingPong root 的 Wi-Fi 分析应用，并发现一个仅响应 boot complete 事件、针对 Samsung S3 专属驱动漏洞的手电筒恶意应用，结果经 VirusTotal 与杀毒厂商确认。（YouTube EPGzbN-d8q2V4，[815.5-1631]，L1）
- 〔SREcon（推测）〕Pinterest 采用基于 Google“meaningful availability”论文的 user uptime（用户在线率）度量。主讲人 Anika Mukherjee 是 Pinterest 的 SRE（此前做 iOS 开发与 Python API 性能），指出原先的 success rate 是按请求数计数的指标，会偏向高活跃用户、把仅供基础设施使用的请求（日志、实验事件）也计入，且无法反映持久性错误与用户在切换表面前的无效等待时长。user uptime 把用户事件视为系统探针：用户有成功体验即视为 up、直到失败体验转为 down，对每个用户建时间线再求平均，从而平等对待每个用户（示例中 3 次请求 2 次成功、SR 约 67%，而在线率仅约 25%）。（YouTube EPH0_eFfgmx5c，[13-776]，L1）
- 〔SREcon（推测）〕MVP 落地与后续路线：以服务端 Flask REST API 为起点，按产品三级关键性对端点做分类编码，仅统计关键端点的用户事件。事件以五字段负载（user ID、session ID、endpoint、成功布尔值、时间戳）写入专用 Kafka 主题，由 Flink 作业（Pinterest 流处理平台 Xenon）按 user ID 分窗、会话结束后排序评估上线/离线时长，汇入 OpenTSDB，实时指标有约 5-10 分钟延迟。报告还讨论移动端崩溃日志延迟、React 页面级 error boundary、第三方 CDN/DNS/GSLB 故障归因等难题：客户端故障造成的停机约为服务端的 3-4 倍（服务端平均每天约 10 天用户停机当量），月度可用性报告仍需人工修正；后续计划包括事件分级指南、SRE 与产品的关键性契约、广告/未登录体验覆盖，以及“多慢算失败”的性能阈值探索。（YouTube EPH0_eFfgmx5c，[777-1553]，L1）
- 〔NSDI（推测）〕NanoPU 是面向数据中心的纳秒级网络栈，主讲人 Steven Ibáñez（与斯坦福、普渡同事合作）。大数据服务的大量扇出 RPC 与细粒度计算（缓存驻留工作集、微秒级消息处理）要求同时压低中位与尾 RPC 延迟及软件开销；对比现有方案：内核旁路数据面 OS 受同步开销限制、调度粒度粗，eRPC 有 850ns 中位线到线延迟但牺牲尾延迟，RDMA 提供远程内存而非远程计算，Nebula 用集成 NIC 负载均衡但仍不够彻底。NanoPU 采用集成 NIC（类似 Nebula）与 Tonic 式硬件可编程传输，关键差异是新增直达每核寄存器文件的快速路径，消息不经主存层级直接交付核上应用；fast path 线到线延迟仅 69ns 且低负载下几乎零方差，每核每秒可处理近 1.2 亿请求。（YouTube EPH1si_4rB9Tg，[8-457]，L1）
- 〔NSDI（推测）〕核心设计与评估细节。受 1989 年 J-machine 等 HPC 系统启发，将两个通用寄存器改造为 net RX/net TX 网络队列，并为每线程设置独立收发队列以防跨线程串读；每核硬件线程调度器监控到达消息优先级并触发中断，由最小操作系统 nanokernel 执行线程切换。原型基于开源 RISC-V Rocket Core 的四核 NPU、200Gb/s 网卡，用 FireSim 在 AWS FPGA 上做周期精确仿真（FPGA 90MHz 模拟 3.2GHz 目标时钟）；对比集成 NIC iSNIC（约 100ns、1600 万请求/秒/核）与 eRPC（850ns、约 1000 万），寄存器文件接口把线到线延迟再降约 30%、小消息吞吐数量级提升；硬件调度器在低负载下把尾延迟降 4-6 倍并多支撑约 20% 负载；键值存储 Mica 仅改 36 行代码即达 592ns 的 99% 尾延迟（约为传统实现一半、多撑约 50% 负载）；用软件实现单边 RDMA 操作比 RDMA 网卡低约 65% 延迟，另评估了 Raft 共识、链复制等应用。（YouTube EPH1si_4rB9Tg，[457-905]，L1）
- 〔会议不详〕面向提交（commit）测试的关键代码引导定向模糊测试，主讲人 Yi Xiang。OSS-fuzz 中近五分之四的 bug 是由新提交引入的回归 bug，修复旧 bug 时也可能引入新 bug，因此应优先 fuzz 提交修改的代码；作者分析了 GitHub/GitLab 上部分项目的近期已关闭 issue，人工鉴定 30 个真实 bug 的引入提交，观察到两个特征：bug 崩溃点常不同于提交改动点，且引入提交常涉及多个改动点。现有定向模糊测试（基于距离的 AFLGo、基于可达性的 Beacon）在提交场景下把目标设为改动点、只求尽快到达而忽略彻底测试受影响代码，目标数增多时定向性退化甚至沦为覆盖率导向，面向多目标的 FishFuzz 又以 sanitizer 标记位置为目标、忽视改动点之间的关联。（YouTube EPH2YkFa-4nY4，[8-313]，L1）
