# 321.4.209 〔OSDI〕Sanitizer的高运行时代价阻碍了生产环境采用SANRAZOR用

- 〔OSDI〕Sanitizer 的高运行时代价阻碍了生产环境采用，SANRAZOR 用混合式冗余分析把它降下来。讲者 Jiang Zhang 是南加州大学博士生，这项工作是他此前在苏黎世联邦理工实习期间完成的，题目是“Reducing redundant sanitizer checks in C and C++ programs”〔00:08〕。C/C++ 不安全，有缓冲区溢出、use-after-free 与未定义行为等漏洞，为此设计的 AddressSanitizer 与 UndefinedBehaviorSanitizer 在实践中运行时代价很高；他给的数据是在 SPEC 基准上 AddressSanitizer 开销可达 74%、UndefinedBehaviorSanitizer 可达 160%〔01:35〕。既有工作分两类：一类用 sanitizer 专属的静态分析只移除语义上冗余的检查，另一类用基于成本的启发式只移除代价高的检查；他探索一个新设计点，提出通用框架 SANRAZOR（转写音写为 Sam Rider），通过检查冗余分析有效移除可能冗余的检查〔02:14〕。框架是混合式：先在 profiling 阶段基于程序测试套收集每个检查的覆盖统计作为动态模式，再提取检查的静态数据依赖作为静态模式，最后分析两者相似度来定位并移除被判定可能冗余的检查。具体地，它在 LLVM IR 中识别用户定义检查与 sanitizer 检查——“Sam Rider starts by identifying both user defined and sanitizer checks”〔03:19〕——每个检查都表示成一条比较指令后跟一条控制流转移指令；然后为每个检查插桩记录覆盖，选取合适负载运行并统计 BR 语句执行次数以及取真取假分支的次数，动态模式定义为总覆盖次数、取真分支覆盖类型与取假分支覆盖类型的三元组〔03:18〕。静态模式用深度优先搜索追溯每个 icmp 语句操作数的数据流，构建树结构；再定义 L0、L1、L2 三种校准方案分别用原始叶节点集合、去掉常量但保留比较常量、或去掉全部常量来规范，静态模式即规范化的叶节点集合即值依赖集〔05:29〕。（YouTube EPXEoTlvim7bw，[8-424]，L1）
- 〔OSDI〕SPEC 上的开销下降、CPU 周期节省与 CVE 检测能力保持。冗余分析先比较每对检查的动态模式，若覆盖模式相同则视为动态冗余，再比较静态模式，若值依赖集相同则视为冗余；两者都相同即判为可能冗余的一对。它只处理 sanitizer 检查而不处理用户检查，因为 sanitizer 检查可能与用户检查或其他 sanitizer 检查重复；判定后把冗余检查的控制流条件置为假使告警分支永不执行，再由 LLVM 的死代码消除移除冗余代码，框架集成进 LLVM 并提供 Clang 包装器供直接使用〔07:27〕。成本评估用 SPEC CPU 2006 基准做案例研究：AddressSanitizer 的运行时代价从 74% 降到 28% 到 62% 的区间，UndefinedBehaviorSanitizer 从 160% 降到 37% 到 124%，取决于采用哪种方案，其中 L2 方案最优——AddressSanitizer 仅 28%、UndefinedBehaviorSanitizer 仅 37%〔08:47〕；检查数量上最多可消除 30% 的 AddressSanitizer 检查与 39% 的 UndefinedBehaviorSanitizer 检查，分别节省 41% 与 77% 的 CPU 周期〔10:01〕。漏洞检测能力研究从 10 个常用程序中选取 38 个 CVE，SANRAZOR 至少能检测到 33 个；与基于成本移除检查、可配置任意开销预算的 ASAP 相比，在相同预算即相同 sanitizer 成本水平下 SANRAZOR 的漏洞检测结果显著更好，原因在于只移除高成本检查会忽视语法冗余这一重要观察〔10:36〕。它典型的应用场景是生产中无法承受全部 sanitizer 检查的软件，工具可以剔除那些对发现唯一问题价值最低的检查；因为它与其他 sanitizer 工具基本正交，可与 ASAP 结合把运行 sanitizer 的生产开销压到只有 7%，同时保留安全收益与漏洞检测能力〔12:40〕。结论是他提出了一个新颖实用的 sanitizer 检查削减工具，用混合方法移除可能冗余的检查，在有效降低 sanitizer 开销的同时保持高漏洞检测能力，工件已开源到 GitHub〔13:10〕。（YouTube EPXEoTlvim7bw，[424-833]，L1）
- 〔OSDI〕分层内存能不能既准确又轻量？Nomad 用事务性页面迁移与非独占分层来回答。这是德州大学与英特尔实验室的联合工作，讲者开场报题“Nomad, non-exclusive memory tiering via transactional page migration”〔00:15〕。随着 HBM、基于 CXL 的内存、持久内存与存储级内存等新设备出现，未来的内存层次将由速度、容量、成本、可扩展性与持久性各异、但都由 CPU 以普通 load/store 字节寻址的多种设备组成，层间性能差距在不断缩小。现代 Linux 通过 NUMA 接口管理新内存设备：性能层是 DDR4/DDR5 连到 CPU 的 DRAM，单位 GB 价格高、性能好、容量有限；容量层看起来像没有 CPU 的内存节点，单位 GB 便宜、性能较低、容量大得多〔01:01〕。传统上操作系统用包含式缓存管理 DRAM 与磁盘之间的数据，因为两者性能相差数个数量级且磁盘不能被 CPU 直接访问，所以更快一层的命中率至上；而分层内存的差距小得多，Linux 改用独占分层——某个页面只驻留在一个层，靠页面迁移把热数据移到性能层、冷数据移到容量层，虽最大化内存利用率却带来很高的迁移代价。为说明问题，他们评估了 Linux 中最先进的内存分层方案 Transparent Page Placement（同样是独占分层）：用 Zipfian 访问模式的合成负载，工作集本可放进性能层却初始放在容量层，结果显示 TPP 最终确实把所有热数据移到快速层并比不迁移取得高 30% 的带宽，但迁移过程中的开销高得难以接受，导致带宽损失达 16 倍〔03:19〕。（YouTube EPXH2NSkVja_4，[15-460]，L1）
- 〔OSDI〕事务性迁移、双队列提升与页面影子机制，以及三套测试平台的实测结论。Nomad 的思路是“The key idea of transactional migration is to keep pages accessible during migration and treat the migration process as a transaction”〔06:58〕：在页面可被用户访问时机会性地把内容复制到快速层，若被复制的页面期间没有被更新就提交迁移，否则回滚并稍后重试。事务分几步走：先保存 PTE 中原始脏位并清除它，若在迁移期间脏位被置位就回滚，并下发覆盖曾访问该页的两个核心的 TLB shootdown 以保证后续写入被记录进 PTE，此时页面仍可访问且仍映射到慢层源位置；随后复制页面内容到目标快速内存；复制完成后从页表解映射并发第二次 TLB shootdown，页面在重新映射前处于不可访问状态；最后检查脏位，干净就重新映射到快速内存的目标位置并提交，被置位就回滚、重新映射回慢层并恢复原始脏位。相比 Linux 的页面迁移，TPM 显著缩短了页面不可访问的时间窗。代价上它仍依赖频繁页面故障——把页面从慢层提升到快速层最多需要每页 15 次故障；与只提升活跃 LRU 列表上页面的 TPP 不同，Nomad 对任何被访问到的页面都恰好用一个故障把它排入提升候选队列，之后每次其他页面故障时扫描队列中页面的 PTE 判定热度，再提升到迁移待处理队列，由内核线程 kpromote 异步执行事务性迁移〔08:48〕。这个双队列设计保证慢层页面不必反复故障，初始故障之后用户可以在做决策期间自由访问该页。页面影子让性能层中一部分页面在容量层保留副本，只有从慢层提升上来的页面才有影子副本，这在内存压力下对最小化迁移开销至关重要，因为这让降级变成高效操作而不必在冷热之间来回交换；提升之后 Nomad 建立键值存储把 DRAM 中的主页面映射到 CXL 或 PMEM 上的影子副本，关键难点是跟踪主页面是否被更新以便让相应影子页失效，因此把所有带影子副本的性能层页面设为只读，并用 PTE 中的影子读位记录主页面原始读写权限，主页面被更新时触发写保护故障处理影子失效，丢弃副本后从软件影子读写位恢复原始权限〔10:11〕。评估在三套测试平台上进行：DRAM 加 Intel Optane 持久内存、Intel FPGA 上的 3D XPoint 原型、配预上市 Micron 3D XPoint 的 AMD 系统，对比 TPP 与 Memtis；微基准同时设置驻留大小与工作集大小两种内存足迹，并分别度量迁移进行中与迁移稳定两种状态。三点结论：Nomad 比 TPP 更有效也更高效，在几乎所有任务上于活跃迁移或抖动期间一致且显著优于 TPP；采样式的 Memtis 无法有效捕获全部热页面，当快速内存能容纳热数据时性能次优，但因迁移次数少得多反而在抖动中获得较高性能；Nomad 对只读负载更有效，对写密集负载迁移回滚较多。延迟对比显示采样方法虽然在抖动时吞吐不错但延迟次优，说明其页面迁移并不有效〔13:14〕。总结说 Nomad 具备事务页面迁移、页面影子与非独占分层三个特征，比 Linux 中最先进的方案显著高效，但也指出高内存压力下何时启用或禁用页面迁移的合适策略仍需进一步研究。（YouTube EPXH2NSkVja_4，[460-900]，L1）
- 〔USENIX ATC〕我们重新从第一性原理审视共识：特殊角色、最大网络延迟 Δ 与随机化都不是共识的内在要求。报告人 Rongji 展示与 Xiangzhe、Xiaofeng、Lei、Guangtao、Shengming 的联合工作《Towards Avoiding Unnecessary Fallback in Byzantine Consensus》〔00:19〕。大多数部分同步协议如 PBFT 与 Tendermint 基于领导者，分两部分：正常情况由单一领导者协调其他节点复制其提案，以及当新视图选出新领导者时的视图切换；部分同步协议依赖预先定义的最大网络延迟 Δ 来触发领导者替换，而此期间无法提供任何服务，如果网络同步假设不成立还可能陷入连续视图切换从而放弃活性〔00:52〕。异步协议没有同步假设也不预选领导者，要求每个节点每轮提出一个提案并参与多阶段消息交换，再用掷币帮助正确节点收敛，代价是更多通信轮数与更高延迟；新近的 DAG 协议则用掷币选出一个有效块并按 DAG 中的边提交之前的块。核心观察是“leader election timer and random coin are all located on the critical execution path, dragging down the system performance”〔02:04〕，因此他受两种快速路径协议的启发，专注一套应用快速路径的框架：正确节点仅凭消息交换就尝试达成一致，从而跳过昂贵的超时事件或随机掷币，只有快速路径失败时才诉诸回退机制。为简化讨论他只考虑一次完成共识问题：多值共识要求每个提议者 i 提出 bi，经过若干阶段消息交换后正确节点最终决定单个提案或提案子集，每个提案最终要么提交输出 1 要么中止输出 0〔02:54〕。例 1 展示快速路径生效：每个节点广播自己的提案，在最多 f 个节点故障下，收到 n-f 个提案后节点 i 就每个提案投票——方式是通知其他节点它收到的全部提案；收到 n-f 个这样的通知后，节点选择至少获得 f+1 票的提案作为最终决定候选；提案分成一值、零值与双值三类，前两类统称单值，若观察到本轮所有提案都是单值就可以直接通过快速路径提交单值提案并中止零值提案〔03:19〕。例 2 展示快速路径失败：三个提案是一值但某个提案是双值，导致节点 0 与节点 1 把它视为候选而另外两个节点认为它已被中止，因此需要回退〔04:57〕。（YouTube EPXNS-KH4WbVg，[19-533]，L1）
