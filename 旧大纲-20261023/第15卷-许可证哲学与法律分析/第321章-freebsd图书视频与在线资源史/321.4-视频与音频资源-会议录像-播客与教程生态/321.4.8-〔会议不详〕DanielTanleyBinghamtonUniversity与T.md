- 〔会议不详〕Daniel Tanley（Binghamton University，与 TOBB University of Economics and Technology 合作）介绍 composable cachelets（CC）——一种保护 enclave 抵抗缓存侧信道攻击（如 Prime+Probe）的缓存分区架构。讲者指出 TEE（如 Intel SGX）未考虑微架构副作用，现有分区方案要么由 OS 强制执行（与 TEE 信任模型不兼容）、要么纯硬件按 cache way 粗粒度修改替换逻辑；CC 将 L3 缓存划分为二维区域 cachelet 并可串联为非连续的 virtual partition，通过每核虚拟分区表（VPT）地址重映射与 cachelet 空闲链表（CFL）等轻量硬件机制强制分区边界，并利用 TEE 既有硬件状态保存机制保存 VPT 内容。（YouTube EP05iwE8I93ks，[7.8-421.1]，L1）
- 〔会议不详〕评估方面，讲者在 Gem5 模拟器上实现该地址方案（16 路 8MB L3）：密码学基准在 256KB 分区/单路配置下最大降速 8.4%（big quake）而多数应用开销可忽略，SPEC2017 在最小 512KB 分区下平均损失 6% 且随分区扩大显著下降；非 enclave 程序在 cachelet 占据一半缓存时平均 IPC 仅降 2.7%；McPAT 估算 CFL、VPT 及附加 tag bits 的面积/功耗开销均小于 1%。论文还包含基于缓存操作语义模型的形式化安全评估，可扩展用于评估其他分区方案。（YouTube EP05iwE8I93ks，[421.1-663.7]，L1）
- 〔会议不详〕讲者（与 Cas Cremers 等合作）报告对使用认证加密（AEAD）协议的自动化分析。讲者以三个真实攻击引入：Facebook message franking（2018 年 Krebs Adal 发现用户举报消息与服务器所见不一致）、SFrame 群组音视频加密协议（2021 年组成员可冒充他人）、UBHSM 密钥存储设备（2012 年 Kindermann 与 Steven 泄露密钥），指出这些攻击均源于对 AEAD 的误用；且 AEAD 定义众多互相竞争、协议设计者难以知晓保证，计算模型与符号模型两类传统分析对这类细微攻击要么不扩展、要么原语过粗，既往发现多为人工。（YouTube EP05k2RcaOfjo，[8.4-302.6]，L1）
- 〔会议不详〕方法上，讲者收集全部 AEAD 定义与已知攻击、补证定义间缺失关系，归纳出碰撞、nonce 误用等三大理论类别，构建可任意组合的符号模型变体并集成进 Tamarin prover，提出 targeted（按实际 AEAD 实例选攻击者模型）与 preemptive（穷举全部 AEAD 威胁模型）两种分析路径：前者在数秒内细化 UBHSM、SFrame、Facebook message franking 的攻击；后者对 GPG、WhatsApp 群消息、Scuttlebutt、WebPush API 建模，判定对 WhatsApp 群消息的攻击可行并报告厂商，WebPush 作者已确认，Scuttlebutt 未回复；全部模型组合的完整分析耗时不到两小时。（YouTube EP05k2RcaOfjo，[302.6-668.3]，L1）
- 〔SREcon〕SoundCloud 讲者 Björn 分享其“seeking sustainable SRE”历程：曾任 Google SRE，五年前加入 SoundCloud（约一亿用户、约百名工程师、服务多于工程师），发现仅按 SRE 圣经照搬 Google 实践并不奏效——正如借鉴 Netflix 文化与规模不匹配一样，SRE 中只有“基本定律”普遍适用而实现细节因规模与文化而异。讲者以错误预算为例阐述三个前提：监控（引 Mikey Dickerson 服务可靠性层级，监控为一切之基）、管理支持、核弹选项（收回寻呼机）。（YouTube EP0CoC5sOUm28，[5.7-900.0]，L1）
- 〔SREcon〕SoundCloud 是 anything goes 文化、生产工程团队不替开发者带 pager，故无法以收回寻呼机作核弹选项；解决方案最终是“让每个人至少兼职做 SRE”（true DevOps）：开发者自带 pager、自建自运营，借自主性与短反馈回路实现自我调节；讲者引用 Ben Treynor 一句定义并提出 true DevOps 定义（不再有独立 Dev/Ops 团队），强调只有遵守 SRE 基本定律（自动化、on-call 规模与工作生活平衡、可行动的告警与 runbook、不超过 50% ops 工作等）才能在小规模多服务约束下成功。如今 SoundCloud 采用软错误预算：站点级可用性目标折算为月度错误预算并展示在墙屏，足以约束发布节奏；问答环节补充该团队运营 Kubernetes 与 Prometheus（源于其自研监控）并作为升级支持点。（YouTube EP0CoC5sOUm28，[900.0-1749.7]，L1）
- 〔SREcon（推断）〕Facebook 生产工程师 Manirudh（Rackstorm 团队）讲述硬件退役（hardware decommissioning）自动化的故事：Facebook 有 14 个地理区域、数以万计服务器批量到期，旧流程依赖电子表格、剧本与部落知识，服务迁移环节最复杂——进度无人统一跟踪、靠私聊与哀求推进、由 on-call 手工执行脚本，既慢（以月计）又易错（未排空即断电、误复用已排空机器等事故）。团队先建 UI 供项目经理核验并批量发起迁移，随后构建 migration handler 框架与任务状态机：自动化失败时经内部工单系统降级派单给服务 on-call，可重试或手工完成后再标记，借“自动接入即生效”的平滑设计快速推广服务上钩。（YouTube EP-2E7vIunJ28，[5.8-542.4]，L1）
- 〔SREcon（推断）〕后续扩展包括替换容量下单自动化、资产标签工作流，以及讲者戏称“胶水厂/机器屠夫”的反 provision 系统，并复盘两次事故：缓存服务迁移 handler 的排空逻辑缺陷把在用机器送去清除（第一次 sev）；第二次 sev 因 on-call 未细读工单、排空未完成即标记完成而被屠夫系统清机。教训是引入人工环节必须让其知晓后果：新增“returned”硬件状态、禁止调度器在其上运行服务、迁移结束强制断言。该框架进而支持增/减容量、新硬件测试、灾备、裸机到虚拟机迁移与数据中心资源均衡等场景，服务迁移自动化已在生产运行一年以上，人工参与和错误大幅减少。（YouTube EP-2E7vIunJ28，[542.4-1158.1]，L1）
- 〔研讨会（边缘/容器方向，具体不详）〕讲者（与 UIUC、阿里巴巴、UC Berkeley 合作者）提出 dependency scheduling 以加速容器启动：启动需拉取镜像、解压并部署，边缘/serverless 短任务场景下开销占比过高。微基准显示（对 5 万余镜像、Docker 运行时）平均镜像拉取延迟约 20 秒，是启动时延主导项。第一版设计 image match 由主节点跟踪已安装镜像的节点并优先调度，但镜像名可变导致失配且二值决策太粗。（YouTube EP-2SiZ1hQRM4，[7.7-388.7]，L1）
- 〔研讨会（边缘/容器方向，具体不详）〕第二版 layer match 以镜像层为依赖单位做内容寻址匹配（trace 显示层跨镜像共享普遍、多版本共享公共层），选择匹配层总字节数最大的节点；在 Kubernetes 上仅需在 API server/调度器/节点代理加层跟踪与解析模块，总计几百行代码即可部署。实验显示 image match 与 layer match 分别将平均启动时延降低 1.4 倍与 2.3 倍（约降为原来的 71% 与 43%），并节省镜像磁盘与解压 CPU 开销；讲者亦讨论开放问题：按启动时延对工作负载分类、与 bin packing/负载均衡等策略的干扰、对 API server 的开销等。（YouTube EP-2SiZ1hQRM4，[273.6-664.5]，L1）
- 〔会议不详（形式化方法方向）〕题为“Protocol Verifiers of the World Unite”的报告介绍新工具 Sapic+（作者 Vincent Cheval、Charlie Jacomme、Steve Kremer 与 Robert Künnemann，兼有 ProVerif 与 Tamarin 两派专家）：为解决协议形式化验证中选型困难（trace 属性 vs 不可区分性属性、GUI、AC 算子、假攻击等考量）与需多工具并用的问题，Sapic+ 提供统一输入语言（applied pi calculus 变体）可翻译到 Tamarin、ProVerif 与 DeepSec 三大后端，已证明正确桥接三者语义差异；并改进语法降低建模出错率、引入 path compression 等优化（合并语义可合并的规则，如编译器内联）。（YouTube EP-GObyDlAzXM，[9.0-354.2]，L1）
- 〔会议不详（形式化方法方向）〕案例研究回答三个问题：翻译模型性能如何（ProVerif 若终止通常快于 Tamarin，两者分析时间均可接受，案例含 KEMTLS、SSH 嵌套端口转发、Privacy Pass、Needham-Schroeder-Lowe）；能否与手写模型竞争（将 Tamarin 最大的模型之一的 5G 模型经 Sapic+ 双向翻译后 ProVerif 性能相当且翻译模型反而更快，归功于 path compression；SSH 对照模型验证也更快）；工作流是否改善（开发期用 ProVerif 秒级运行、定稿用 Tamarin 更精确的 Diffie-Hellman 理论、ProVerif 无法自证的公理可在 Tamarin 中证明后于 ProVerif 使用，DeepSec 兜底不可区分性（indistinguishability）属性（决策过程，总是终止））。源码在 Tamarin 开发分支，提供 Docker 镜像一键运行。（YouTube EP-GObyDlAzXM，[354.2-749.0]，L1）
- 〔会议不详〕Microsoft Research 的 Yuheng Stefanovich 分析云规模存储的独特挑战与颠覆机会：云端三大存储技术（闪存、HDD、磁带）皆发明于云之前，按数据温度分层售卖 SLA；预计 2025 年每年将产生约 175 ZB 数据，云厂商只会采购单位成本指数下降的存储。以创新 S 曲线为定性工具判断：闪存正接近成熟（3D 层数线性扩展、每 cell 层数收益边际递减、特征尺寸缩小根本性损害耐久），HDD 已成熟（密度停滞十余年、IOPS/TB 随密度下降造成每盘 stranded capacity），磁带市场萎缩（六家制造商仅剩 Fujifilm 与 Sony）。（YouTube EP-HT2CFz3wSk，[8.1-341.8]，L1）
- 〔会议不详〕面向云原生（cloud-first）新存储的设计原则：层虚拟化（客户购买 SLA 而非具体介质）可用于 bootstrap 新技术（冷存储中 silica 或 DNA 与磁带并置，甚至开设新层）；应完全分解（full disaggregation）以独立扩展 I/O 速率与介质、按工作负载 right-size 计算（机架级已试验并出货，称 5% 改进在数百数据中心即值数百万美元）；拥抱形态自由、不模拟既有硬件接口（告诫磁带库机械设计利用率低下）；共同设计硬件软件以优化尾延迟（99 分位 provisioning）；并强调可持续性与多学科团队（Project Silica 汇聚物理、化学、光学、电子、机械、设计与计算机科学家）。结论：避免 drop-in 替换式仿真，应自材料层起 clean-slate 协同设计。（YouTube EP-HT2CFz3wSk，[298.2-844.1]，L1）
- 〔会议不详〕Fraunhofer SIT 博士后 Guendalina Pata 报告经 W3C EME 标准对 Widevine 的形式化安全分析（博士期间与导师合作）：OTT 平台（Netflix、Prime Video、Disney Plus）面临特殊攻击者模型——付费合法用户拥有完整设备控制权，目标是盗版再分发或无限期观看，故依赖 DRM（Microsoft PlayReady、Apple FairPlay、Google Widevine）。EME（Encrypted Media Extension）作为 HTML5 API 扩展标准化各 DRM 系统的通用接口，定义许可获取与许可续期两个工作流，但对 DRM 消息仅作不透明 blob 透传；讲者指出标准中的安全考量只面向用户隐私而非媒体保护，故为媒体消费定义了新的安全目标（解密密钥机密性、许可原样且新鲜送达、到期时间强制）。（YouTube EP-LU2okgnQKg，[8.2-447.8]，L1）
- 〔会议不详〕验证使用 Tamarin prover（适合含计数器与长生命周期密钥的有状态协议），通过 Widevine 测试许可服务器加自研插桩库拦截并篡改 EME hook 调用与部分系统调用做逆向，将消息中的签名、哈希等语义回填为 Tamarin 规则；因 Tamarin 基于事件序而无时间概念，以全局时钟 trick 建模等待许可过期的攻击者。分析发现会话密钥被加密但从未签名，且在验证许可响应完整性之前已处理并派生密钥，由此导出 Widevine EME 密钥派生攻击：攻击者可伪造许可续期响应无限延长观看。修复建议利用 EME 既有的 set server certificate 接口在 DRM 与服务器间建立强密码绑定并强制先验证后使用；已负责任披露（Widevine 团队未回复，EME 方讨论补丁并将跟进），工件与 PoC 在 GitHub 开放。（YouTube EP-LU2okgnQKg，[396.2-852.9]，L1）
- 〔会议不详〕讲者 Ruoyu 介绍 Mooncake 论文“Trading More Storage for Less Computation——KV cache 为中心的 LLM 聊天服务架构”：Mooncake 由月之暗面（Moonshot AI，转写多次误作 Qwen）与清华大学 KVCache.AI 团队联合研发，是 Kimi 的在线服务平台，承载 80% 以上流量、较旧系统成本减半；Transformer 推理分 prefill（计算密集、128K 输入首 token 需 5 秒以上）与 decode（带宽密集、需满足每秒 10 token 阅读速度）两阶段，指标为 TTFT 与 TBT。前缀缓存可跨请求复用，Kimi 线上负载约 50% token 可复用，但单节点约 300 万 token 缓存下命中率骤降，故应以更多存储换更少计算；KV cache 每个 token 膨胀数千倍（Llama3 70B 百万 token 上下文达 320GB，转写“three hundred. 120GB”），需要大容量存储、低时延高带宽传输与缓存感知调度。（YouTube EP-Lpx9QuCEsw，[16.3-405.3]，L1）
- 〔会议不详〕Mooncake 采用 prefill/decode 分离（P&D）双节点池架构，底层 Mooncake Store 在推理节点 VRAM/DRAM/SSD 上建全局缓存池，用前缀哈希对象存储（每块 16-512 token，附带前缀哈希键去重），容量满时 LRU 淘汰；传输引擎支持 GPU Direct RDMA、TCP、NVMe over Fabric，针对多 RDMA 网卡优化，无需像 NCCL 构建进程组以支持弹性伸缩，上层以零拷贝接口兼容 vLLM 与 Megatron。按线上请求分布构造会话/agent/合成三个约 10K token 均长 trace 评估：三个基线系统因混批干扰时延违约，Mooncake 有效请求容量（goodput）最高提升 498%，GPU 计算节省 29%-61%；vLLM 集成分两阶段，传输引擎部分已合入。（YouTube EP-Lpx9QuCEsw，[405.3-1025.7]，L1）
- 〔会议不详〕上海交通大学 Yicheng Gu 介绍 Gevoken（转写亦作 G-Vulkan）——面向 Vulkan 光线追踪渲染的可扩展 GPU 池化：光栅化低成本而光线追踪真实（利用光路可逆性自相机发射多射线），2018 年 RT Core 使实时化成为可能，但时延仍高（官方示例画最简三角形两者相差 6.7 倍，NVIDIA 官方混合应用差 1.5 倍）；降采样/超分等优化产生假图改变颜色，多 GPU 方面 AFR 不优化时延，光栅化的 sort first/sort last 在光追下更宜按屏切分。选择 Vulkan 因其由 Khronos 推出、低层细粒度控制、性能优于 OpenGL 且开源跨平台。挑战归三类：生态能力（应用需改代码才能多 GPU）、GPU 内（五阶段帧管线跨 CPU/GPU 相互等待、云渲染可省 present 阶段）、GPU 间（主 GPU 不参与拷贝、慢 GPU 拖累整帧）。（YouTube EP-PNOug51HRg，[16.2-507.3]，L1）
