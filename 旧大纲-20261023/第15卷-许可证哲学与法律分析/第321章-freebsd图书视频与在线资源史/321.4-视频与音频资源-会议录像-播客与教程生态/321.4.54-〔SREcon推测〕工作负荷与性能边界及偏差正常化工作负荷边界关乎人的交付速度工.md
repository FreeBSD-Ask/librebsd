- 〔SREcon（推测）〕工作负荷与性能边界及偏差正常化。工作负荷边界关乎人的交付速度、工作管理与士气，外部力量包括 GDPR 合规与 COVID；性能边界对一线最弱、最难看见，系统复杂化使职责去中心化，需要局部的纵深防御。引用 Diane Vaughan《The Challenger Launch Decision》中的偏差正常化（normalization of deviance）：靠重启、忽略 CPU 温度或网卡抖动等生命体征只会制造虚假安全感；提出用混沌工程（Linux traffic control 加延迟、负载迁移、synthetic testing）测量所认为的正常与实际误差边界的偏差，关闭反馈回路，避免把 MTTR 等指标跨团队平均成虚荣指标，并重视裁员对士气与投入度的影响。（YouTube EP1MB2YFiNQ-4，[717.5-1853.8]，L1）

- 〔SREcon〕Task Control：让分片服务在调度器上安全运维。主讲人 Laurie（Facebook 生产工程师，Web Foundation 团队，曾用调度器 Tupperware 跑 Elasticsearch 集群）讲解分片、实例、副本、任务（Facebook 对 pod/container 的称呼，带编号）等术语：分片是服务对某子集数据的响应能力，分片副本可独立于任务健康状态变不健康，按分片拆解错误率比平均值更能反映真相（1/3 实例故障的 33% 平均错误率实为一个分片 100% 故障）。调度器靠健康检查与抢占迁移任务处理主机故障，但磁盘数据不随任务走，服务需在副本重建（慢且耗资源）、坐等临时故障恢复与云盘（如 AWS EBS）之间取舍；Kubernetes Deployment 只按数量摘除、看不见单分片健康，Operator 方式则给控制权。（YouTube EP1OIGm3665E4，[5.8-1140.0]，L1）
- 〔SREcon〕Facebook 的 task control 协议与两个框架。task control 让服务对调度器请求只回答现在做或稍后做（不能拒绝），用 Thrift 调用实现并保持控制流自上而下、运维接口统一；配合 shard manager 框架（可动态把分片迁到别处再安全重启任务）与 shard task control（向服务索要任务-分片映射、副本健康与约束后模拟判断，可并行更新大幅提速，从 Elasticsearch 推广到多个服务）。这是危险的权力权衡：弄错一侧会堵住排空与维护，弄错另一侧会摘垮自家服务，且不能讨论 allocation、不能附加维护、不支持自定义停止信号，呼吁开源界把分片感知做进 Kubernetes 基础原语；问答强调失败关闭（failing closed）、记录允许操作的原因日志、协议要依赖最少，并用独立 rebalancer 保持调度器简单。（YouTube EP1OIGm3665E4，[1140.0-2682.8]，L1）
- 〔会议不详〕云端网络的隐藏限制：AWS EC2 网络带宽与包速率。演讲者（Emnify 工程师，其自研移动核心网部署在 AWS 上 7 个 breakout 区域）讲解 15 Gbps 实例无论 jumbo frame（默认 MTU 9001）都封顶，而未文档化的包速率（PPS）上限仅按 1500 字节包算足 15 Gbps（如 1.25M pps），IoT 用例平均包 150-200 字节时双向网络函数实际只得到约 750 Mbps。2021 年引入的 allowance exceeded 计数器需经 ENA 网卡驱动 ethtool 读取（不在 CloudWatch），Prometheus node exporter 的 ethtool collector 默认关闭，突发型实例带宽是按积分、best effort 的共享资源。案例：S3 每 5 分钟上传 9 MB 文件在 26 ms 内完成约 2.7 Gbps 微突发即触发计数器，AWS 支持也无解——限制实现粒度接近微秒，计数器表示排队未必丢包。（YouTube EP2AehFxKlUgQ，[18.4-1095.2]，L1）
- 〔会议不详〕分片包限制与 conntrack 连接跟踪实践。经隧道封装的分片包不享受 Nitro 硬件加速且入向封顶 1024 pps（与 link-local 查询是不同桶），可用 TCP MSS clamping、正确设置隧道 MTU、让 transit gateway 代为分片或新的 ENA fragment bypass 绕过；第二部分讲连接跟踪表：安全组靠它实现有状态，表满时新连接、DNS 甚至 SSM/SSH 登录都可能失败且无官方数字，实测 C5 系列表容量随实例大小翻倍、第六代加 12%、第七代网络增强型加 33%（c8 同限）。全放行入站 80 端口加全出站流量可禁用连接跟踪（NAT 网关等自动跟踪流量除外，transit gateway 与 gateway load balancer 已不再受限、文档历史可查），也可调低 idle timer（默认 5 天）或用 Geneve 封装控制流基数；Ubuntu 24.04 LTS 不含所需新 ENA 驱动需自行编译，团队还因使用 DPDK 从内核移除网卡接口而在审计的 Prowler 报告中遇到趣事。（YouTube EP2AehFxKlUgQ，[1095.4-2196.3]，L1）
- 〔会议不详〕iQ：数据中心网络边缘的可预测带宽分区。主讲人（与 Stanford 和 Windows Azure 团队合作）指出共享云中 Memcached p99 延迟全天波动高达 200 ms，网络拥塞是确定的性能干扰源，而 TCP 按流数分配带宽、加权公平队列在数万租户与数万台交换机规模不可行。在 Azure 的测量研究显示拥塞主要发生在网络边缘：最热集群中核心每丢 1 包边缘丢 1000 多包，17 个集群中 16 个核心几乎零丢包；iQ 据此在边缘（hypervisor 或 NIC）为每个 VM 建拥塞检测器，按带宽保证比例划分虚拟链路，用高速拥塞控制算法 RCP 发送显式速率反馈包（每 10 KB 抽样一个发送者、接收端无 per-source 状态），完全分布式地分配带宽。（YouTube EP2ngxLiGTt9k，[9.7-680.8]，L1）
- 〔会议不详〕iQ 的实现与评测。RCP 在 n 条长流竞争单瓶颈时毫秒级收敛（TCP 需数百毫秒），轻微核心拥塞靠 ECN 通知边缘减速，100 ms 收不到反馈则像 TCP 一样乘性降速；实现为 Linux 内核模块（开源）与 Windows 过滤驱动，作为 queuing discipline 不侵入应用、TCP 与 UDP 均可用；把全局 token bucket 拆成每 CPU 队列（类似 sloppy counter）摊销锁开销，5 Gbps 下比分层令牌桶 HTB 高效 33%（HTB 在 9 Gbps 无法线速工作），中位延迟降低一半。16 台机器宏评测中 Memcached（14.4 万次 set 请求/秒（均分于 4 台 Memcached 服务器，每台约 3.6 万）、6 KB 对象）与对抗性 UDP 租户共存，开启 iQ 后性能接近裸金属集群。（YouTube EP2ngxLiGTt9k，[738.5-1505.4]，L1）
- 〔EuroSys（推测）〕内核 Bug 的撤销式规避（Bailouts）：Undo Workarounds for Kernel Bugs。来自 UC Irvine 的主讲人 Seyed Mohammadsadegh Zadeh Lajevardi（转写音校正）与 UC Riverside、Atlassian 研究者合作，指出内核 bug 可导致系统崩溃、挂起甚至可利用的数据损坏，而现有方案——禁用有缺陷代码组件（如 USENIX Security 2016 论文 Talos 部署的代码禁用）或编写不完整的快速补丁（dirty patching）——或损失系统功能、限制 fuzzing 覆盖，或需大量人工。核心论断是复用内核已有的错误处理代码：当系统调用半途触发 bug 时撤销其全部副作用、把系统恢复到预期状态而非重启；实现上在被测函数（如 Pixel 3 GPU 驱动函数）尾部加入 bailout 语句并置于恒假条件中，配合条件 goto 跳转与跟踪状态改变语句执行的参数掩码（pair mask），使 bailout 对控制流敏感。（YouTube EP4QwMMCjAll8，[8.2-351.9]，L1）
- 〔EuroSys（推测）〕Bailout 运行时流程、Hekaton 自动生成与实验评估。运行时异常处理器置位 bailout 标志后经条件跳转进入 bailout，按掩码位对已执行的状态改变语句递归清理父函数；静态分析工具 Hekaton 依据内核错误处理代码的常见模式（如 if 条件中整数与零比较）与经人工核查验证的函数对数据库自动生成 bailout，并从六个导致不完整的因素量化构建置信度分数（实验中置信度高于 50 的 bailout 均为完整回滚），平均仅需人工补 2-3 条语句。在 113 个 bug（Android 内核未知真实 bug 与 CVE、30 个当时未修补的 Linux 内核 bug、74 个注入 bug）上评估：几乎全部场景可缓解漏洞并在所有实验中优于 Talos，性能开销可忽略，还能缓解 fuzzing 的重复重启、提升代码覆盖率与发现 bug 速度；局限包括不适用于已处于清理路径（如 free 函数）的 bug、需人工核查函数对数据库、依赖内核 sanitizer 先行捕获 bug。（YouTube EP4QwMMCjAll8，[360.8-715.5]，L1）
- 〔会议不详〕Cinderella：语言级 JavaScript 沙箱的自动化测试（沙箱研究部分）。主讲人 Abdulrahman 介绍 JavaScript 沙箱通过限制第三方代码对全局对象和内建函数的访问、并经 endowment 共享引用来提供轻量隔离，广泛应用于智能合约、IoT、恶意软件分析与云端应用，但此类沙箱缺乏自动化测试方法与测试协议。其研究将隔离技术分为 runtime-based 与 language-based 两类（后者可同时用于客户端与服务端），并归纳语言级沙箱的安全目标：防止沙箱外读写、限制特权操作调用、防止阻塞主程序循环（如 DDoS 或算法复杂度攻击）、防止宿主进程崩溃；还发现逃逸漏洞的共同模式是攻击者经原型链（prototype chain）访问外部引用（foreign references），从而打通沙箱与宿主间的隧道并调用强力 API。（YouTube EP4VZ-sXkw7To，[10.1-332.1]，L1）
- 〔会议不详〕Cinderella 工具设计与评估：动态分析、测试预言与 9 个 CVE。Cinderella 是首个针对语言级 JS 沙箱的自动化测试方法，以任意合法 JavaScript 种子代码为输入，插桩注入测试预言（oracle）并按条件生成变体，在沙箱上运行以探测外部引用，可集成进沙箱开发流程以获得更健壮的隔离；插桩覆盖全局对象与全局变量、函数调用与函数入口等分析点，预言检查包括读写违规标志（安全目标一）、强力 API 调用（安全目标二）与硬崩溃检测。评估选取 3 个 Node.js 版本与 ECMAScript 测试用例（test262）、V8 测试用例两个种子语料库，分别带与不带变体生成器运行，结果表明安全错误数量随 Node 版本变化（新语言特性未被沙箱覆盖）、更强隔离（如冻结全局对象的 secure ECMAScript 沙箱）威胁少于 self-eval；共报告 9 个 CVE，例如 realms-shim 经改写 prepared stack trace 触发原型污染实现沙箱逃逸，维护者确认为设计缺陷并弃用该包，源码发布于 GitHub。（YouTube EP4VZ-sXkw7To，[333.4-714.2]，L1）
- 〔会议不详〕基于指针认证的时序内存安全（PTL）方案设计。主讲人 Reza 指出 C/C++ 中时序内存损坏（temporal memory corruption）常见且易被攻击，现有最先进方案依赖海量元数据追踪对象、指针及其生命周期，内存开销高且元数据自身未受保护（需假设空间安全或依赖边界检查器）。其方案在堆上运行时检测时序损坏：利用 Arm 架构的 PAC（pointer authentication code）扩展作用于数据指针——为每个对象在内存中内联生成 64 位随机 ID（置于对象之前），以对象基址和 ID 为输入经 PACIA 指令生成签名存入指针未用位，从而绑定指针与对象；编译期在 LLVM 位码的分配（malloc）、解引用（load/store）与释放（free）位置插桩，运行时用 PACIA/AUTIA 指令生成与认证签名，认证失败即判定为悬空指针或对象 ID 遭时序损坏篡改。（YouTube EP52lBhBXDSGk，[8.7-257.7]，L1）
- 〔会议不详〕向后搜索、冗余检查消除与开销评估。针对指针指向对象中部（如指针运算后）的情形提出 backward search：向上逐级搜索可认证该指针的对象 ID，并把对象对齐到 16 字节以加速查找；同时做过程内的冗余检查消除优化（最适合单线程应用），在指针传入不可追踪的过程外函数（如 quantum add hash）之前移除重复认证、返回后重新启用。因研究时无支持 PAC 指令的硬件，先在 FVP 模拟器上测试，模拟器健壮性不足后又因 iPhone 需越狱而采用 PAC 的软件实现在 Raspberry Pi 上评估 SPEC2006 的 9 个基准：运行时几何平均开销 26%（软件实现所致，预期真实硬件与真实指令下更低），backward search 开销很低、切实可行，内存开销约 2%（指针元数据存于指针未用位）；结论是重新利用 Arm PAC 提供时序内存安全，并在不依赖边界检查器或空间安全假设的前提下保证对象与指针元数据完整性。（YouTube EP52lBhBXDSGk，[260.0-579.2]，L1）
- 〔会议不详〕超大规模有序消息投递（FastACS）问题与三项解法。来自 Google Ads 基础设施团队的主讲人给出目标：消息按生产顺序精确投递（全序）且至少一次，消费者分布在全球数十个集群（每集群数万消费者、全球合计数十万），单集群读取流量达 Tbps 量级并要求亚秒级端到端延迟。传统 Kafka 架构（生产者追加消息文件、broker 本地存储、消费者读字节反序列化）受存储介质限制：SATA SSD 带宽约 4.84 GBps；Google Cloud 实验（3 个 broker、8 vCPU、32 GB 内存、NVMe SSD、240 Mbps 生产速率）最多支撑 56 个消费者、峰值约 14 Gbps 后吞吐骤降。为此实现三项解法：把消息分为冷热两级、将最近的热消息保留在内存中（存储介质仅作回退）以绕过存储限制；把消息文件切分为小块分散到 N 个 broker、由消费者取块组装以绕过网卡（如 10 GBps）传输限制；再用 RDMA 让消费者直接取块以避免横向扩容的处理成本，有效聚合集群中多块网卡的能力。（YouTube EP5QVWLXBHw4A，[17.7-246.7]，L1）
