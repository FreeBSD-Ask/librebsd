- 〔FAST（推测）〕CacheTAG（转写音变 CacheSec/cashback）：Google 数据中心 Colossus 通用闪存缓存（以索引服务器形式工作、完全去中心化、按哈希切分键空间，任一单点故障不影响其他缓存服务器）的准入优化，服务于 Bigtable、Spanner、BigQuery、F1 等主流服务，主要目标是降低总体磁盘读（延迟通常改善但不保证）。主讲人 Chuwei Yang 阐述闪存引入的考量：写放大（非顺序驱逐如 LRU 导致碎片化，改用 1GB 容器 FIFO 队列的近似 LRU 驱逐，尾部容器回收后重插队首，聚合行为接近真 LRU）；写耐久（多数数据仅被访问一次、本不可缓存，曾用 LARC（Lazy Adaptive Replacement Cache）在第二次访问时才准入以减少闪存写）；以及 LARC 永远错过首次命中、对低频访问数据不友好（此前只能人工监控并逐工作负载关闭）；还有 Colossus HDD 服务器内存 buffer cache 的干扰——高闪存命中率可能伴随高磁盘读而毫无收益。（YouTube EPH3LSFHB-UkA，[13-489]，L1）
- 〔FAST（推测）〕级联模型与优化落地：把流量按类别划分（Bigtable/Spanner 中为 locality group 或 column family），每类可配置不同激进度的准入策略（admit on miss、admit on second miss 即 LARC、admit on write、never），并允许分数策略（同一类别内按块比例混用策略）；以缓存驻留时间 T 对到达间隔分类，结合 buffer cache 模拟器估计磁盘读、闪存写与缓存用量，形成以磁盘读加写字节为目标、缓存容量为约束的分数背包问题，用贪心算法高效求解。生产部署共 127 个缓存驻留时间（15 分钟至 16 天、6% 步长），完全去中心化、每 5 分钟运行全量优化，用 ghost 缓存记录最后访问时间，仅占单个索引服务器一小部分资源。一周生产对比实验显示 CacheTAG 相比 LARC 降低总体成本 6.5%；命中率最高但结果最差的 admit-on-miss 策略印证了 buffer cache 的反作用；系统淘汰了人工监控与手调规则，成为后续空间预取等优化的基础。（YouTube EPH3LSFHB-UkA，[489-971]，L1）
- 〔会议不详〕CAFault（转写音变亦作 CAFoT/C4FT）是清华大学 Yuan Liangcheng 提出的配置感知故障注入测试框架，通过生成大量故障相关（fault-dependent）配置来增强现有故障注入技术在实用分布式系统上的能力。系统配置中与故障处理逻辑密切相关的配置项会显著影响故障注入测试结果，但现有工具多在固定默认配置下测试而漏掉大量 bug；联合配置输入与故障注入输入（何时、何处、多久注入）的组合空间极其庞大，带来两大挑战：自动分析故障输入与配置项之间的隐藏依赖以缩小配置空间，以及针对给定配置智能探索故障注入输入空间。CAFault 包含两个过程：通过观察不同故障+配置组合下动态覆盖率是否变化来构建故障依赖（FD）模型（高质量配置进入下一步），并用二分搜索式最小化算法缩小真正触发差异的最小配置子集；以及以故障容错机制代码覆盖率为反馈的故障处理引导模糊测试，替代只增整体代码覆盖率的传统策略（如 CrashFuzz）。（YouTube EPH426tP_3I0U，[19-563]，L1）
- 〔会议不详〕实现与评估：用静态分析扫描源码识别并标记异常处理代码块作为故障容错逻辑反馈；在 Hadoop File System、ZooKeeper、MySQL Cluster、IPFS 四个来自不同组织、不同语言的系统上实现，体现跨平台与语言无关性；框架由配置生成器、故障注入器与交互适配器三部分组成。评估共发现 16 个新的错误处理 bug；把 FD 模型集成进现有工具（CrashFuzz+、Cronus+ 等）后能发现这些工具遗漏的额外 bug；覆盖率在约 8 小时的模型构建期落后，随后快速反超并持续领先；消融实验中禁用 FD 模型随机生成配置的版本 48 小时仅发现 16 个中的 7 个。未来工作包括用 AST 静态分析构造初始 FD 模型再由动态分析细化，以及设计负载不均衡、一致性等更多 oracle。（YouTube EPH426tP_3I0U，[563-1116]，L1）
- 〔FSE（推测）〕TLS-Anvil（转写音变 TLS Analyzer/TLS Envelope）：基于组合测试的 TLS 库黑盒评估测试套件。TLS 除 20 年间发布的四版主协议 RFC 外，众多其他 RFC 引入新密码套件并附带强制性实现要求，如 TLS 1.2 RFC 要求接收方校验 CBC 模式填充并以 bad_record_mac 告警指示填充错误以防 padding oracle 攻击，且该要求在任何协商参数下都必须满足；此前研究（Mergard et al.，音变）表明参数交互（密码套件、密钥交换、签名等）可能使要求在不同参数组合下被违反（如切换椭圆曲线套件后改发 internal error 告警）。穷举参数组合会组合爆炸，故采用 T-way 组合测试：故障通常只源于少数参数交互，如 3 参数各 2 值的 12 个 T-pair 仅需 4 个测试输入即可覆盖。测试套件含 408 个基于 13 个 TLS RFC 的测试模板、最多 14 个参数（含记录分片等非密码参数）。（YouTube EPH5g-QdcVC7A，[11-312]，L1）
- 〔FSE（推测）〕执行流程与评估：先对被测库做特性提取以选择适用模板与参数值，再用约束过滤非法组合（如 RSA 密钥交换须配 RSA 证书），交给亚琛大学开发的组合测试框架 Coffee4J 求 T-way 覆盖所需测试输入，反复建立 TLS 会话并自动评估，全流程自动化且低误报。对 13 个 TLS 库的客户端与服务端按强度 1-3 评估：mbedTLS 执行时间最长约 67 小时、约 18 万次会话，s2n 最短约 6 小时。共发现 239 个 RFC 违规，按影响分组：立即可利用漏洞、密码计算错误（如 LibreSSL 用错密钥解密的 key confusion bug）、互操作性问题（如 wolfSSL 无法解析某些小记录）、告警码不符等；3 个可利用漏洞分别是 MatrixSSL 客户端的 padding oracle（SHA-256 HMAC 套件下无效填充触发段错误直接关闭连接）、MatrixSSL 的畸形消息长度字段 DoS（CPU 飙升不终止），以及 wolfSSL 的服务端认证绕过（TLS 1.3 空证书消息，评估期间被独立报告）。作者建议把组合 RFC 测试集成进发布流水线，并将方法推广到 QUIC 等新协议；源码见 GitHub 与 tls-envelope.com（音变）。（YouTube EPH5g-QdcVC7A，[312-616]，L1）
- 〔会议不详〕2DFS 是为容器分发大文件（尤其分布式机器学习模型分片）设计的二维文件系统与分发框架，主讲人 Giovanni。动机：分割神经网络后可将模型分片部署多机做分布式推理并独立扩缩、快速适应边缘资源变化；Docker 也在推动用 OCI 制品（Docker Models）分发模型，开发者熟悉容器。但容器并非为承载大文件而设计、镜像打包内容远超原始设计。贡献有三：新层类型 2dfs layer 承载模型、驱动等与代码依赖无关的大文件；专用构建器 2DFS build（沿用 Docker build 习惯，用 JSON 描述符在文件源/目标原语上追加行、列坐标）；扩展注册表高效分发。文件组织进自包含、不重叠、独立的分配单元（allotment），以稀疏矩阵的行列表示，因而可并行构建、独立缓存与独立分发，且完全 OCI 兼容、无需改动任何容器运行时。（YouTube EPH9PncfSTXzY，[18-583]，L1）
- 〔会议不详〕分发与评估：在 OCI distribution spec 注册表上扩展新层类型与层扁平化能力，引入语义标签（如 --1.0.2）让注册表按行列范围选择拉取的分配单元，扁平化后附着在传统层之上返回完全合规的 OCI 镜像。评估：14 个模型按 18-82 个分片构建，2DFS 构建平均快 56 倍（峰值 120 倍），且构建时间不随分片数增长——一次构建即含全部分片，而 Docker 需按分片组合预建大量镜像；模型更新/重训场景平均缓存效率高 25 倍，Docker 最坏情形（底层缓存失效）下达 75 倍；代价是注册表每次请求都需扁平化，约 20ms 开销及少量 CPU/内存开销（相对秒级下载可接受）。分布式实验用 10 个边缘节点经 gRPC 分发最多 10 分片的 MobileNet：分片越多端到端延迟越高但吞吐提升，且 2DFS 只需构建一次、放置由运行时调度决定。（YouTube EPH9PncfSTXzY，[583-1155]，L1）
- 〔FAST（推测）〕XFuse（转写音变 XFS/X views）是阿里巴巴推出的与 FUSE 后向兼容的用户空间文件系统基础设施，主讲人 Qwen（Alibaba Group）。用户空间文件系统降低对 OS 的依赖、提升开发效率与迭代速度，但历来受性能与 RAS（可靠性、可用性、可服务性）拖累，且无法走标准内核接口时应用与构建需改动；XFuse 面向使用高速存储设备、生产环境有严格 SLA 的文件系统。改进包括：观察到高速设备上数据就绪快于内核事件等待/通知的微秒级开销，在等待事件前加入双向忙等初始期（NVMe 上端到端延迟可低至 3-4 微秒）；自适应事件等待（adaptive event wait）按预测动态开关忙等；引入多条请求 pending 队列并把 pending/processing 队列组成 channel、由文件系统 handler 选 channel，降低 daemon 线程间的内核锁竞争；以及在线升级方案——扩展 libfuse 支持在线升级工作流与状态迁移、由监控服务协调两个文件系统 daemon，应用升级时仅经历约 2 秒 I/O 冻结，已服务生产负载。（YouTube EPHAP3mazx3dE，[8-373]，L1）
- 〔FAST（推测）〕参数化分析与系统级评估：用基于 FUSE 低层 API、可模拟不同存储设备时序特征的 TimingFS 探测各方面收益并预测可达性能。自适应加权方案对 PMEM 与 SSD 类存储均有效，SSD 类慢存储下 I/O 延迟对忙等周期不敏感、且忙等优于纯事件等待，重载下收益更明显（忙等时 daemon 有时能立刻取到 pending 请求）；线程放置上，PMem 类存储负载适中时把应用与 daemon 线程放不同 CPU 可充分享受忙等降延迟，SSD 类（忙等无效）则放同一 CPU 更好（本地 CPU 的内核事件通知略快）；channel 选择以均匀分布请求最优，应避免把请求切到空闲 channel 使忙等失效，而计算廉价的 PID 策略（线程号 mod channel 数）反复测试表现良好。系统级用 Filebench 比较：PMEM 类 RAM disk 与 SSD 类快速磁盘上 XFuse 均显著优于 FUSE，慢速磁盘受存储而非用户空间计算瓶颈；File create 工作负载下 XFuse 也胜出但幅度更小，归因于 StackFS 与 ext4 的可扩展性限制。（YouTube EPHAP3mazx3dE，[373-738]，L1）
- 〔PDSW（推测）〕大规模 HPC 生产系统上 I/O 密集型文件的访问、重用与共享特征分析，基于 NERSC 的 Cori 超算（scratch 子系统为基于 Lustre 的共享并行存储：248 个 OSS/OST、InfiniBand 存储网络），分析约 4 个月、8400 万条日志、5200 万个文件、9000 个应用、600 余用户、约 13 PB I/O 传输。主讲人（转写未报姓名）使用 Darshan 三层监控（Slurm 作业日志应用级、I/O 请求级、Lustre 文件系统级含 OST 数量与条带宽度），并明确结论受 NERSC 策略与 Cori 负载影响、不外推到其他系统。筛选出四个月至少产生 100GB 数据且被访问至少 2 次的 I/O 密集型文件后仍有 8 PB、40 余万作业；分类发现读写文件占 71%、只写文件占 7%、只读文件占 22%；超过 80% 的 run 只执行读或只执行写，与传统单体 HPC 工作负载（同一次执行内读写交替）显著背离，反映向多应用相互依赖的科学工作流转变，可据此组织应用避免 I/O 竞争。（YouTube EPHBasfUuFBaU，[5-782]，L1）

- 〔会议不详〕TClock（转写亦作 TC locks/TCP lock，音变）是一种“移交临界区而非共享数据”的锁设计，为共享数据提供局部性。锁仍是最广泛使用的同步原语，Linux 内核锁 API 调用数在 2002、2012、2022 持续增长（从粗粒度走向细粒度加锁）；传统锁下临界区在竞争线程间顺序执行，共享数据随锁在核间移动、拉长临界区执行时间，按 Amdahl 定律损害性能，微基准（每线程枚举目录文件、竞争目录锁）显示吞吐随核数下降，NUMA 感知的 CNA 锁亦然。委托式锁（服务器-客户端模型，客户端把临界区封装为函数、传函数指针给服务器核执行）能保住数据局部性，但要求修改应用，对拥有数千把锁的 Linux 内核不现实。TClock 目标是透明委托：保留 lock/unlock API、用委托式设计最小化共享数据移动，需回答三个关键问题——如何捕获线程上下文、在何处捕获（lock/unlock API 边界即临界区）、等待者是否会在服务器执行其请求期间修改上下文导致损坏。（YouTube EPHENss0nFwBI，[16-437]，L1）
