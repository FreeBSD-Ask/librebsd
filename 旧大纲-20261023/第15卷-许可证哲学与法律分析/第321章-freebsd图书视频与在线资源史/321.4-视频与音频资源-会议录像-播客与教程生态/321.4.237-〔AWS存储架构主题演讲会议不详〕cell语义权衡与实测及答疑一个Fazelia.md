- 〔AWS 存储架构主题演讲（会议不详）〕cell 语义、权衡与实测及答疑。一个 Fazelia cell 是一台单一的状态复制机、含一个卷或一小组卷的配置——前述复制数据、分区映射与各类元数据，让客户端与服务器以完全一致的参与者身份加入这套高效简化的复制协议〔10:53〕。系统提供键值存储 API、组内提供严格可序列化事务、比实际所需更强；经验是宁可给出本地能给的最强语义、让使用者以最直白的方式调用、避开微妙保证带来的常见缺陷〔11:29〕。部署上在创建时与后台持续用数值优化压小半径、但并非一味最小化：只求最小、把一切塞进同一台机器，会付出巨量可用性与持久性代价〔12:07〕。权衡是：半径越小、分区风险越低（小圆越难被切开）、爆炸半径越小；圆做大则能在电源、网络、机架位置等维度获得更多内部冗余以提升可用性，也获得更多二分带宽——两组服务器间能搬多少带宽、直接决定复制存储的持久性（控制重新复制的速度）、还增加放置选择〔12:40〕。做法是取运行网络团队的拓扑与建数据中心团队的供电拓扑、经数值优化器给出兼顾可用性与爆炸半径的最优布局〔13:27〕。并非处处强一致：客户端发现该找哪个 cell 走最终一致发现缓存、监控用最终一致流水线、cell 修复走使用最终一致数据的元控制面，并做了形式化工作证明最终一致不破坏协议正确性；经验是最终一致又易又便宜但很微妙、能用则用〔14:37〕。爆炸半径还覆盖过载（大系统更易整体同时过载、故切分降半径）、软件缺陷（无论测试与发布多努力仍会发生、故以能清晰推断“最多触及多少卷”的方式滚动发布）、以及运维问题（仍是云事件重大成因、可用运维设计压低任何坏工具或坏手法的半径）〔15:34〕。作者归结为把谦卑造进系统：把自己当永不出错的傲慢架构师不可达、把谦卑设计进去才能去想东西何时坏、怎么坏、以及如何让它以最小的方式坏〔16:15〕。一张图看客户端到配置服务的错误率、绿线是部署前后对照：错误率极尖刺、多因故障时打向配置服务的流量本身尖刺、以过载为主，Fazelia 的水平扩展有助于规避〔16:46〕。答疑：Limelight Networks 的 Mike Settcoff 问 cell 之间是否还有复制、整 cell 坏掉卷是否丢失——答称 cell 有七个副本、有时间修复，但整 cell 坏掉该卷即丢失、因无法再推断其上数据的正确性与一致性；幸而 cell 持久性凭后台修复与七副本高于块存储设计值、故极罕见〔18:06〕；微软的提问者问单卷跨数百 cell 如何保一致——cell 即其所含数据的权威、复制总自 cell 向外、熵减以 cell 为权威副本〔18:42〕；Nutanix 的 Chinmay 问 cell 多大才够快——不足 1MB〔19:31〕；优化在整数据中心、约三十兆瓦尺度上跑、努力“把毛梳顺”使每个个体尽量互不相连；其中在线部分是有趣子问题、论文未涉及〔20:12〕。（YouTube EPZO9AxJTlgsU，[620-1247]，L1）
- 〔USENIX ATC 2013（推测）〕普渡大学的 Rohan Gandhi（转写音写为 Ron Gandhi）介绍与 Di Xie（音写 Dishya）、Y Charlie Hu 合作、面向异构集群的 MapReduce 性能改进系统 Pikachu，〔00:09〕。云上大量 Web 服务跑在数十万台节点上、普遍面临异构性：同样的工作放在两台节点上耗时不同。成因包括多代硬件并存（CPU、网卡、磁盘各异）、部分节点带 GPU 或 SSD 等加速硬件、甚至本应同性能的虚拟机之间差异也可达六成，以及服务同时使用多种容量不同的节点类型〔00:25〕。MapReduce 分 map 与 reduce 两阶段、reduce 再分 shuffle、sort 与用户自定义 reduce 函数；reduce 不必等全部 map 完成即可启动、故 map 与 reduce 并发执行，某节点可能同时跑 map、shuffle 与 sort，直到全部数据被接收、搬运并排序后用户 reducer 才跑，所有节点所有阶段结束作业才算完成〔02:08〕。为考察异构影响，作者把执行切为四阶段：map only、map shuffle（此处 shuffle 兼指 sort）、shuffle only 与 user reducer。在本地两快五慢（按 CPU 快慢贴标签）的集群上测各阶段耗时：第一阶段不到 5%、说明 reducer 起得相当早；下一阶段约占 40% 却仍在两类节点上几乎同时结束，差别在于快节点执行的 map 任务数是慢节点的 15 倍〔04:12〕。后果在 shuffle only 阶段显现：快节点因处理了更多 map 任务、本地数据更多，需从其他节点收的数据几乎少七成、执行时间明显短于慢节点；user reducer 阶段有同样现象〔04:58〕。改跑另一应用（六百八十个 mapper 的 word count）并调整配置后，发现快节点并非在所有情况下都更快——取决于槽位数量、槽里跑什么、任务是什么、可用资源为何，所以节点会不会更快、快多少并不总可预测〔05:18〕。由此提出问题：作业不会在所有节点同时结束、中间有明显空隙，能否弥合以缩短作业时间、省下钱？本文聚焦 reducer，因为 mapper 已被 Hadoop 调度大致均衡、而 reducer 没有。根因是 Hadoop 给所有 reducer 分配等量数据而处理速度不同；Pikachu 的做法是动态调节负载、让节点获得与其处理速度成比例的数据，把快慢节点的数据量之比记作分区比例 p，且 p 在运行期计算、不需任何先验任务或节点信息〔06:35〕。三个挑战是：何时算 p、如何算 p、以及怎么用 p 重平衡数据。分析 p 的精度随四阶段变化：p 是 reducer 中处理时间之比，reducer 开始后可精度、随其推进改善，而 reducer 之前精度很差——等待越久精度越高，但与重 shuffle 代价权衡：调整数据实为调整分区，把一个分区从某 reducer 移到另一个可能要搬已 shuffle 过的数据、产生罚分，可能反超过等到准确 p 的收益〔07:44〕。先前工作 Tarazu（去年 SOSP）用 map 任务进度为 reducer 估算、罚分为零但 p 精度不高；作者选择更勇敢一点，让 reducer 真正跑一段时间再算 p、接受一定罚分，这是第一项贡献。（YouTube EPZOwiwx1UF2I，[9-529]，L1）
- 〔USENIX ATC 2013（推测）〕p 的估法、重平衡机制、评测与答疑。第二项挑战是如何算分区比例：它是快慢节点上进度速率之比。把 map 与 reduce 的进度速率随时间画出并让 reducer 先跑一段时间，Hadoop 对每个任务都上报进度速率、本例中该比值为二，直接用之；但再测四阶段耗时仍有空隙，说明单靠 Hadoop 的进度分不足以算 p〔09:22〕。为查原因，作者监控随时间完成的任务数：蓝线是截至某时刻完成的 map 任务数，红绿两线分别是慢、快节点上已完成 shuffle 的 map 任务输出数。红线基本贴着蓝线走、说明快节点上的 reducer 能跟上 map 任务完成的速度，慢节点跟不上；同时监控 CPU 使用率发现快节点既然能跟上 map 生成速度就不需要它能获得的全部 CPU，而 Hadoop 的进度分本身就偏低估、因为它并非时刻都有活干〔10:26〕。故计算 p 时把 CPU 使用情况连同 Hadoop 上报的进度分一起考虑。第三部分是数据如何重 shuffle：Hadoop 中所有 reducer 拿等量数据，Pikachu 使用虚拟桶（virtual bins）——先给所有 reducer 均分，等一段时间后算出 p，再据此把一个桶从某 reducer 移到另一个〔11:21〕；三个挑战全部在运行期解决。评测先看快慢节点进度是否一致：绿线与红线同步推进、正是期望结果〔11:46〕；与 Tarazu 对比 Pikachu 弥合空隙更好、也更接近最优分区比例；重 shuffle 罚分在本应用中不显著、低于 5%〔12:30〕。加速比方面，本地集群上 Tarazu 相对 Hadoop 至多提升约 20%，Pikachu 相对 Hadoop 接近 40%；与“所有节点同时结束作业”的理论最优加速比相比差别不大，Pikachu 达到最优的 92% 到 98%〔13:01〕。在 AWS 的十六节点 EC2 集群上（四十慢节点、二十快节点）与 Tarazu、Hadoop 对比，相对 Hadoop 最多 40% 加速〔13:25〕。总结：Pikachu 按节点处理速度调节数据量，全部在运行期完成、运行期测量、计入资源占用，并用虚拟桶调节数据量。答疑：一位提问者问把配置反过来（快慢节点对调）是否仍有类似加速——答称即使只有一台慢机也可用、但收益会小一些，因为 reducer 本就在快节点上跑；微软研究院的提问者指出重 shuffle 罚分来自“数据先从 map 机器经网络到 reducer、再从 reducer 本地磁盘读”，建议改为先在 map 机器写盘、再网络读给正确的 reducer 以彻底避免重 shuffle，作者承认这可能有帮助但不确定〔15:48〕；NetApp 的 Michael Condit 问只区分一快一慢两类是否可推广到任意多种速度——答称标签只按 CPU 划分，可命名为 type one、type two…type N，对每种类型跑同样算法即可〔16:45〕。（YouTube EPZOwiwx1UF2I，[529-1038]，L1）
