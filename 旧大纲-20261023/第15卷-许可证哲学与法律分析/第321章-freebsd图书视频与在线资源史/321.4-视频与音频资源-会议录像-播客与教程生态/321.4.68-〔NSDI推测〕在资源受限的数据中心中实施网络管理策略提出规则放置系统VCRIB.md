# 321.4.68 〔NSDI推测〕在资源受限的数据中心中实施网络管理策略提出规则放置系统VCRIB

- 〔NSDI（推测）〕在资源受限的数据中心中实施网络管理策略，提出规则放置系统 V-CRIB（Virtual Cloud Rule Information Base，转写中亦作 V-CRIP）。主讲人介绍规则是对流字段上范围集合的动作（如 deny、accept、入队做 QoS），交换机与网卡的规则容量受高功耗 TCAM 限制、软件交换机占用 CPU，VLAN-per-service 与逐 VM 对策略在十万台服务器的数据中心会需要数百万条规则，因此规则位置形成资源占用与带宽占用之间的权衡。报告阐述卸载规则的挑战：必须保持重叠规则的语义、尊重异构的内存与 CPU 约束、最小化卸载带来的流量开销并应对流量/规则变化与 VM 迁移等动态性；为此提出 V-CRIB 抽象层与带复制的分区（partitioning with replication）方案避免规则膨胀，并按源 IP 维度创建分区，指出分区分配等价于 NP-hard 的广义分配问题，采用先生成可行放置再优化流量开销的两步法。（YouTube EPAtooRyxaPEo，[9.7-565.1]，L1）
- 〔NSDI（推测）〕后半场介绍 V-CRIB 的放置与精化算法及评估结果。提出 first-fit decreasing similarity 算法求解类似带重叠对象的装箱问题，并证明其为最优下界的 2-近似；精化阶段对比 overhead greedy 与 benefit greedy 算法，后者借助设备流行度因子避免局部最优，且两步法使频繁动态（流量变化、多数 VM 迁移）只需重跑精化算法。评估在 1000 台服务器 fat-tree 网络上用 ClassBench 流生成器生成 20 万条流，源放置最多需 5K 规则时 V-CRIB 能在 4K 容量的服务器上找到可行解，并在随机 IP 分配这一对抗情形下靠相似分区合并成功放置；结论为更小且更相似的分区更易找到可行解。问答环节讨论了限制规则变更数量的约束与规则数量爆炸的成因（逐对通信 VM 的策略与 SDN 新服务）。（YouTube EPAtooRyxaPEo，[567.9-1315.4]，L1）
- 〔会议不详〕主讲人 Jason Yu（新加坡国立大学博士生，与 NUS 及 ETH 同事合作）介绍面向可信执行环境（TEE）的新内存隔离模型 ElastiK（转写中亦作 Elastiklak/ElastiCave/ElastiCube）。以 Intel SGX 的空间隔离为例说明其数据共享表达力受限：互不信任的应用只能经公共内存通信，需两次额外拷贝与一对加解密，基准显示空间隔离执行共享密集应用可比原生 Linux 慢两个数量级。据此提出时间隔离（temporal isolation）让不同 enclave 在不同时间访问同一内存区域，并阐述两大难题：共享者无法控制数据后续访问方式，故引入所有者设定的 max permissions；恶意所有者可在共享内存布置恶意代码诱导代码注入，故再引入接收方可动态请求硬件修改的 effective permissions，且后者始终被前者约束。（YouTube EPAu15SuNUYCU，[8.5-422.2]，L1）
- 〔会议不详〕后半场介绍同步机制、原型实现与评估。针对互不信任方并发读写造成的 TOCTOU 竞态，ElastiK 在读/写/执行权限位旁增加 lock bit，持有该位即获得独占访问。原型基于 RISC-V 的 Rocket Core 在 M 模式实现安全监视器，通过 ElastiK 指令创建内存区域并设置权限，再由监视器按当前运行软件的 effective permissions 配置 RISC-V PMP 项；评估在 FPGA 模拟器 FireSim 上以 Keystone 实现的空间隔离为基线，共享密集微基准显示 ElastiK 稳定领先约两个数量级、性能接近原生执行。报告总结设计的三个必要元素（max permissions、effective permissions、lock bit），并称原型已开源。（YouTube EPAu15SuNUYCU，[424.8-838.1]，L1）
- 〔会议不详〕提出通过冗余请求降低云存储服务尾延迟的中间件 Coslo（Cost-effective tail latency Optimizer，转写中亦作 CalSlow/CostLo）。基于为期一周、从 120 个 PlanetLab 节点（转写中亦作 planum/planlam 节点）到最近 S3 与 Azure 数据中心的测量：get 请求第 99 百分位延迟比中位数至少高 70 毫秒、put 至少高 200 毫秒、相对膨胀至少 2 倍；包含 50 个对象的网页下载实验显示中位下载时间比理想情形翻倍、p99 恶化 20 倍。由于尾延迟由孤立的延迟尖峰主导、事后反应效果不佳，方案主张主动为请求附加冗余请求取最早响应，并指出朴素冗余的缺陷（可能命中同一慢副本、多份数据外传成本高），提出在数据中心内显式建立多副本、跨数据中心乃至跨云（S3+Azure）发冗余请求等手段。（YouTube EPAuozKia-MLI，[9.9-648.3]，L1）
- 〔会议不详〕后半场介绍 Coslo 架构与评估。Coslo 作为客户端与存储服务之间的中间件，由中央配置选择器综合应用 SLO、云定价、工作负载与云存储测量等输入，在无界的冗余配置空间中挑选满足目标且代价最小的配置。重点讲解延迟估计难题：独立采样会因并发请求高度相关而严重低估 p99 延迟，Coslo 显式建模依赖来源（同副本、同网络路径）后估计结果几乎吻合实测。评估在 AWS 上以 120 个 PlanetLab 节点为客户端、一周 Wikipedia 工作负载计算成本：设置 50/40/30 毫秒 SLO 时均有超过 80% 节点达标，且对比单数据中心单副本、加中继 VM、多数据中心等受限配置，证明必须组合全部冗余形式才能兼顾 SLO 与成本。问答讨论了与 TCP 拥塞退避的差异（利用路径多样性）及云服务商底层变化时的在线适配。（YouTube EPAuozKia-MLI，[657.5-1384.9]，L1）
- 〔USENIX Security（推测）〕主讲人 Jinoh Kang（佐治亚理工学院，与佐治亚大学合作）介绍反模糊测试技术 Fuzzification（转写中亦作 forgification/pacification）。动机是攻击者同样用模糊测试挖掘漏洞：有团队 50 天发现 50 个漏洞、Google 的 OSS-Fuzz（转写作 closed fuzzing）两年发现约九千个 bug，故要让模糊测试只对持有普通编译二进制的测试者有效，攻击者只能拿到加固二进制从而更少发现 bug。威胁模型假设攻击者无源码、知道该技术并试图将其失效；报告比较并排除打包/混淆、注入不可利用 bug、模糊器检测与模拟器检测等候选方案，随后给出前两个组件：在最少执行边上注入随机生成代码（带控制流与数据流依赖）以拖慢现代模糊器的 speed bump，以及借鉴 ROP 构造输入敏感路径与反馈位饱和分支以干扰覆盖管理的 branch trap。（YouTube EPAwH_ABHw9ms，[10.9-491.2]，L1）
- 〔USENIX Security（推测）〕后半场介绍第三个组件 anti-hybrid 与评估。将显式数据流改写为隐式数据流使动态污点分析失效，并把分支条件改用哈希运算制造路径爆炸以拖垮符号执行；工作流先对二进制采样收集 profile，再按用户指定的开销预算迭代注入组件。评估显示已发现路径覆盖率降低 71%，binutils（转写作 B utility）上崩溃减少 97%、LAVA-M 数据集减少 67%，开销为 binutils 体积 +62%、CPU 约 4%，分层应用体积 +5%、CPU 不足 1%；作者强调该方案是尽力而为、与其他防御技术互补。问答中 Dan（Google）追问罕见路径上的产物反而有助于攻击者、TU Berlin 的 Dominic 询问能否逆向移除保护，作者回应目标是显著延缓逆向与分析时间。（YouTube EPAwH_ABHw9ms，[493.0-1021.8]，L1）
- 〔会议不详〕主讲人 Chen Yu Song（与中国科学院合作，主要作者因故未能到场）介绍查找内核引用计数 bug 的工作。C 语言内核缺少垃圾回收与智能指针等机制，引用计数由开发者手动增减，漏加会形成悬空指针导致 use-after-free，漏减会导致内存泄漏；现有两条建模路线各有缺陷：基于路径一致性的两篇内核工作没有追踪引用计数与存活引用数一致这一根本不变量，会漏报且无法处理只发生在单条路径上的 bug，追踪该不变量的 HUGI（转写作 HuGi）又仅适用于 Python。报告进而指出两大挑战：精确检测需要路径敏感分析，在庞大内核上难以扩展；以及内核的内部引用/弱引用等惯例（如缓存指针不计数、对象析构时自动清理）会打破强不变量、产生误报。（YouTube EPAxPU07s2wE8，[7.7-467.8]，L1）
- 〔会议不详〕后半场介绍方法与结果。方法采用强 bug oracle（引用计数变化必须与引用变化一致），并把对象生命周期收缩为创建、使用、逃逸、释放四个局部场景以提升可扩展性；工作流先用静态分析识别被计数对象及增减计数的包装函数并划定分析范围，再做无约束符号执行进行路径敏感、基于摘要的分析，最后用启发式过滤疑似误报。在 Linux 4.14 内核上实现，符号执行约 200 小时内完成，共发现 82 个新 bug，其中 31 个在报告时已被修复、52 个为新问题。结论称该工具同时保证精确性与可扩展性，并通过内置内核引用计数惯例显著降低误报。（YouTube EPAxPU07s2wE8，[480.7-683.6]，L1）
- 〔会议不详〕提出面向物联网与边缘计算等资源受限环境的轻量级密码方案 CisPro（ciphertext and signature propagation，转写中亦作 CS Prop/C-S probe），合作者包括 Aroua、Abdulrahman、Silas 与 Nile。Thales、SonicWall、Kaspersky、Nokia 等报告显示 IoT 已成黑客主要目标，而 DNS、TLS、HTTPS 等互联网规模协议的传统加密算法对低功耗设备过于昂贵，只留下性能、安全或开发者三方受损的糟糕选择；作者在三代 Raspberry Pi 上实测 TLS 握手开销，CisPro 比椭圆曲线快约 2.7 倍。报告分析现有轻量级密码提案仍需昂贵运算、易受攻击或需要可信且有状态的中间节点（如代理/网关），故提出传播算法：上游能力较强的机器改造经认证消息或密文，使下游弱设备能高效验证或解密，且该机器无需可信或有状态。（YouTube EPAyIGZrLzkjs，[8.5-411.7]，L1）
- 〔会议不详〕后半场以 Alice（受限终端）、Patty（无需可信的传播者）、Bob（DNS/Web 源服务器）三方模型讲解方案与评估。签名传播中 Patty 收到 Bob 的原始签名后计算传播签名发给 Alice 验证，避免现实部署中 Patty 完全验签后转发明文、末段链路不设防而遭 DNS 缓存投毒的问题；密文传播方向相反，Alice 部分加密、Patty 完成加密、Bob 用私钥解密，从而在中间节点被攻破时保住机密性与完整性。方案基于 RSA 实例化并在 DNSSEC（签名）与 TLS（密文）上评估：在所有受测设备上时延与能耗均优于传统实现，并另做微控制器测量研究（Arduino MKR WiFi 1010），CisPro 作为原语在全部场景胜过传统 RSA 公钥操作；未来工作为优化私钥操作。（YouTube EPAyIGZrLzkjs，[412.6-829.5]，L1）
- 〔会议不详〕主讲人 Samuel Lee（KAIST）介绍 FPGA 深度学习加速器 TensorPrism（转写中亦作 Tensor Pyramid/TensorRT 等）。FPGA 硬件加速虽是加速深度学习的可行路线之一，但传统方案存在主机与加速器之间的数据搬运开销：数据需从 SSD 经 I/O 控制器、北桥到主机内存，再复制到运行 DNN 计算的用户进程，最后再复制到加速器显存。TensorPrism 用非易失参数（non-volatile parameters，转写作 non-bolitai/non volatility of the parent）替代常规范式，把 DNN 数据直接存储在加速器内的参数存储中，使加速器可直接从 VRAM 访问数据。（YouTube EPAzVGcDXkqf8，[8.4-164.2]，L1）
- 〔会议不详〕后半场给出评估对比。以 MLP（多层感知机）为负载，比较 CPU-X（单核通用处理器加线程）、DNN-X（DNN 加速逻辑加 DRAM）与 TensorPrism（DNN 加速逻辑加参数存储）：以 CPU-X 的执行周期为基准，DNN-X 平均降低 580 倍，TensorPrism 平均提升 1350 倍；剖析显示 DNN-X 的数据搬运开销占总执行周期的 60%，而 TensorPrism 显著削减了该开销。能耗方面 DNN-X 比 CPU-X 低 99%，TensorPrism 再比 DNN-X 低 61%。结论称集成外设的 FPGA 加速器在执行周期与能效上均优于基于 DRAM 的加速器，收益来自数据搬运开销的降低。（YouTube EPAzVGcDXkqf8，[166.1-317.6]，L1）
- 〔NSDI（推测）〕介绍 Tonic，一个在网卡上以可编程硬件实现传输协议的架构。传输层由连接管理与数据传输（数据缓冲区与传输逻辑）组成，传输逻辑即可靠交付与拥塞控制两类算法，相关创新不断（含 RDMA over Ethernet），因此可编程性至关重要；但线速升至 100 Gbps 后 CPU 周期开销难以承受，卸载连接管理、数据传输或整体卸载又会把算法固化为 NIC 厂商的实现。报告指出在高速硬件中实现传输逻辑的两大约束：有状态处理使流水线各阶段、各分段间的状态一致性难以保证（时序约束），以及 NIC 上高速内存仅几 MB、每流只剩几 Kbit 状态（内存约束）。（YouTube EPB9USJ5TagCo，[5.4-448.9]，L1）
- 〔NSDI（推测）〕后半场讲 Tonic 的设计方法与评估。通过考察多种传输协议归纳公共模式实现为可复用固定功能硬件模块，首次尝试（单一状态内存加可编程流水线）因内存过宽、并发访问过多不达时序而失败；Tonic 随后将处理解耦为 segment selection（可靠交付）与 credit management（拥塞控制）两个引擎，每个分段仅需 active/retransmitted/lost 几个比特的状态，用户只需用两个可编程模块指定分段如何判丢失（基于 ACK/超时信号），下一分段生成、事件并发冲突与状态合并均由 Tonic 处理。评估实现六个基准协议（TCP 变体、接收方驱动、硬件特化算法）只需不超过 200 行 Verilog，而 Tonic 自身可复用模块约 8000 行，全部在 100 MHz 满足 100 Gbps 下 128 字节包的时序，窗口可至 256 分段、并发流达 2048，代码已在 GitHub 开源；问答对比了与微软 TCP Chimney 的差异（Tonic 聚焦可编程性、协议无关）。（YouTube EPB9USJ5TagCo，[462.6-1136.5]，L1）
- 〔会议不详〕主讲人 Lily（厦门大学）介绍检测 DBMS 逻辑缺陷的变异测试工作（Worst-Case Variance Metrics-Aware Metamorphic Testing for Detecting Logical Bugs in DBMS，工具转写中亦作 VoskScope/Voscof）。2023 年 1 月 11 日一个 DBMS 正确性 bug 导致 9700 余架次航班延误、1300 余架次取消；逻辑 bug 不崩溃系统、仅对给定查询返回错误结果集，属于软件测试中的测试 oracle 问题。报告梳理三类现有技术及局限：差分测试受 SQL 方言差异制约（如 MySQL 的 IS NOT 后只能跟 true/false/null）；oracle 引导合成（如 PQS 以随机枢轴行验证）只考虑单行且难以覆盖复杂语句路径；等价类变异测试（如 NoRec 比较带/不带 WHERE 优化的查询）会因共享同一有 bug 的表达式而漏检深缺陷，基于集合包含的语义近似（转写作 Pinalo）又难以处理聚合函数、窗口函数与连接等破坏集合包含的特性。（YouTube EPBBCLtIx59lc，[18.8-505.0]，L1）
