- 〔会议不详〕数据、经验与走出困境的建议。行业侧数据同样失衡：她引用基于真实在招职位的 CyberSeek（NIST/DHS 通过 NICCS 支持）与 2019 年的 71.6 万在职安全从业者/31.4 万空缺，Evans Data 2020 全球开发者人口研究给出约 2450 万开发者（约占全球劳动力 3.1%）。她借《侏罗纪公园》Ian Malcolm 关于"不劳而获的科学力量"的台词批评"买个产品/服务就能解决"的推销逻辑，并以 25 年经验分享：联邦政府反而因系统临近生命末期与 18F（源自总统创新学者与 USDS，OMB 与白宫科技政策办公室联合）把敏捷/DevOps 带入项目立项而更易现代化，尽管有承包商的 Wormtongue 式抵制。她把上一场演讲的四个问题模型应用于 DevSecOps：会计师问题（职业商品化）、海豹/摇滚明星问题（证书军备竞赛稀释人才市场）、宇航员问题（特定工具/平台的深度专才易被技术迭代淘汰）、消防员问题（好心救火者终因压力或厌倦离场）；建议包括差距分析、文档化可重复过程的成熟度模型、以短期/合同"枪手"专家补位但做好文档交接、领导层明确期望，并接受并非一切工作都适合共享责任模型（如同不能让虎笼清洁工兼任兽医），强调可持续与稳定比追逐下一个时尚更重要。（YouTube EP5RkduV_cezs，[783.0-1640.5]，L1）
- 〔会议不详〕十亿级向量查询为何卡在 GPU 显存。主讲人 Zili Zhang（北京大学，与 Fangyue Gao、Xuanzhe Liu 等合作）介绍向量查询：用机器学习把文本/图像/音频相似度映射到高维向量空间，做成对距离评估找 top-k 近邻，应用于信息检索、人脸识别、推荐，尤其是 RAG——作为 ChatGPT 等 LLM 的持久长期记忆（GPT-4 上下文约 32k token），先向量查询定位可能含答案的文档再喂给 LLM，数据库规模到十亿/万亿级时向量查询成为关键瓶颈。主流近似检索分两类：IVF 倒排索引用 k-means 聚类、只搜最近簇，省内存但同精度计算更多；图索引把向量连成多级图，内存可高达数倍。GPU 天然适合向量距离的并行计算，但 Deep1B 数据集约 750GB 而 H100 只有 80GB 显存，多卡又浪费计算资源（近似搜索只需小部分数据参与），因此选 IVF 并用宿主内存扩展 GPU 显存（逐簇换入换出或 CUDA Unified Memory），面临三大挑战：批内冗余传输（显存只容 3 簇时 C1-C3 被换出又换回）、GPU SM 利用率不足（簇大小不均导致长尾 kernel、单组计算填不满 SM）以及传输与计算流水线方案设计（枚举所有方案是指数复杂度，无法运行时求解）。（YouTube EP5SwqLBxv9qY，[16.4-558.0]，L1）
- 〔会议不详〕Rami 系统设计：贪心重排 + 动态规划分组的近最优流水线。三项技术：基于代价的查询计划重构（refitting），把批内计划转为按簇优先的簇基计划，访问到某簇立即执行其全部相关查询、每簇至多传输一次以消除冗余传输，并优先计算仍驻留显存的簇进一步减少传输；计算优化上，先在离线建 IVF 索引时做簇均衡（拆大簇）使各 block 同时完成、消除 GPU 时间维度闲置，再用动态核填充（kernel padding）在检测到空闲 SM 时自动拆分计算搬运过去，达成 100% 空间利用率，同 SM 多 block 还能提高占用率；流水线设计上提出两个最优算法——贪心重排把传输时间为零的簇与计算时间最长的簇前移以最大化重叠（论文给出最优性证明），动态规划则基于含流水线同步开销的递推公式求最优簇分组。系统以约 1.2 万行 C++/CUDA 实现（首个 GPU 显存之外的向量查询系统），在 AWS A100 上用 Deep1B 十亿向量评估（V100/T4 做消融）：接近理论下界、显著优于逐块顺序传输与 CUDA Unified Memory（CUM）基线，比 64 vCPU 的 IVF-CPU 方案快数十倍且性价比更高，对算法优化正交、可被现有向量数据库集成。（YouTube EP5SwqLBxv9qY，[558.0-908.8]，L1）
- 〔CRYPTO（推测）〕iMessage 加密协议的教科书式破解。主讲人（约翰斯·霍普金斯团队，转写中提及合作者 Matt——Matthew Green）针对 2011 年推出、部署约 10 亿台设备、峰值每秒约 20 万条消息的 Apple iMessage 提出新型选择性密文攻击：仅凭 Apple iOS 安全白皮书的一段描述即可断定协议在密码学意义上被击穿——加密 iMessage 由接收方公钥下的 RSA 密文（1288 位）包裹对称密钥、消息用无认证的 AES-CTR 加密、外加发送方 ECDSA 签名；既非认证加密也无 HMAC，且存在身份误绑定（identity misbinding）攻击：截获 Alice 发给 Bob 的消息后可剥掉其签名、换上自己的名字与签名转发，而一旦剥掉签名密文即完全可篡改（malleable），无法满足 IND-CCA 安全定义。现实中"解密 oracle"会以报错、时序、副作用缺失等侧信道形式间接存在（Stack Overflow 上的 padding oracle 案例、format oracle），但 AES-CTR 是流密码、无 padding，padding oracle 类攻击全部失效，必须发明新的 format oracle；团队在 Quarkslab 部分逆向基础上用 Python 解析原始消息，恢复出格式：gzip 压缩的二进制 plist（为省推送网络带宽甚至把部分消息塞进 1288 位 RSA-OAEP 密文的剩余空间，OAEP 本身不可篡改）；苹果为防身份误绑定在密文内嵌发送方 ID 作反制，但该 ID 位于 CTR 可翻转区域，消息足够长时直接翻位即把反制化为乌有。（YouTube EP5VSD5nzOwcY，[10.0-860.0]，L1）
- 〔CRYPTO（推测）〕gzip oracle 与实战攻击、修复部署。gzip 由 deflate 压缩流加 CRC32 校验构成，而 CRC 线性（CRC(a⊕b)=CRC(a)⊕CRC(b)）故可修正校验和：不知道消息内容与原 CRC，也能通过异或翻转向量的 CRC 得到合法变异消息的 CRC，使其解压校验通过。deflate 的静态 Huffman 编码意味着翻转一位解压后改变的可能是别的符号——这恰好构成 format oracle：猜测字符、翻转密文位、以 CRC 校验结果验证猜测并迭代恢复整个消息（区别于观察消息大小变化的压缩 oracle，这是选择密文攻击且仅适用于带 Huffman 编码的 gzip）。远程观察利用大附件上传 iCloud 的机制：畸形密文使手机不解密下载附件，超时未见下载请求即失败，从而获得远程错误 oracle；屏蔽 iCloud 响应或把下载 URL 篡改到攻击者服务器（i8cloud.com，为概念验证注册）可全程静默。大消息触发动态 Huffman 表是攻击最难、最昂贵的部分，需在已知明文上重建变长符号边界。实测用 2^18 次查询（ naive 版因等待上限 1 秒需约 73 小时、回溯优化后约 35 小时）从真实系统恢复附件密钥 232/256 位（可暴力穷举余下）；写模拟器跑了约 1 万次模拟攻击，34% 恢复除 40 位外全部、23% 恢复除 24 位外全部。修复方面，升级到 Signal/Axolotl 类前向安全协议或认证加密（AES-GCM/OCB/HMAC）会破坏十亿设备的向后兼容；实际部署的是"RSA 密文黑名单"——RSA 密文不可变，同一 RSA 密文出现两个不同 AES 密文版本即说明攻击，直接丢弃，耗时约 4 个月、30 名工程师，覆盖 iOS 9.3 与 OS X。Q&A 中 Kenny Paterson（Royal Holloway）指出严格说需要的是 signcryption 方案、明文中包含身份正是防身份误绑定的标准反制，波鸿鲁尔大学的提问者则问及 RSA 上的 Manger 攻击与 OAEP 向 PKCS#1.5 的兼容性。（YouTube EP5VSD5nzOwcY，[860.0-1712.8]，L1）
- 〔USENIX Security（推测）〕Hot Pixels：物理、微架构之外的混合侧信道与频率-功耗-温度权衡。主讲人 Adithi Tanuja（合作者来自 Georgia Tech、密歇根大学与波鸿鲁尔大学）介绍论文"Hot Pixels: Frequency, Power, and Temperature Attacks on GPUs and ARM SoCs"：侧信道攻击从物理侧信道（功耗、EM 辐射，需示波器/EMI 探头，因利用固有物理属性而难缓解、跨微架构与代际有效）演进到微架构侧信道（经软件可见 API 泄漏、无需物理接近可远程），第三类混合侧信道借 OS 提供的内部传感器 API 测量物理属性，兼得远程可发起与难缓解。核心发现是 CPU/GPU 为遵守功耗与热限实施 DVFS，形成频率-功耗-温度三方权衡：M1 MacBook Air 上数据 0/1 两个无限循环的温度恒定，但频率与功耗差异显著并泄漏数据；多花 300 美元买风扇的 M1 MacBook Pro 因散热充足被最高 3.2GHz 钳制，转而经温度与功耗泄漏——器件要么热约束（不泄漏温度信息但经频率/功耗泄漏）要么频率约束（频率恒定但经温度/功耗泄漏），且泄漏遍布桌面、笔记本、手机与 GPU，可由无特权本地用户乃至 Chrome、Safari 浏览器发起。（YouTube EP5V_pgnXCP6g，[8.6-405.0]，L1）
- 〔USENIX Security（推测）〕像素窃取、历史嗅探与网站指纹攻击。GPU 渲染白像素显著慢于黑像素，时延与 GPU 频率成正比；攻击借助可叠加的 SVG 滤镜（feGaussianBlur 模糊、feColorMatrix 饱和度等，可施加于任意 DOM 元素）跨安全边界计算像素：attacker.com 内嵌 victim.com 的 iframe，隔离单像素并经 CSS 放大至全屏，再叠 SVG 滤镜压到 GPU 降频，依据滤镜耗时把目标像素分类为黑/白。该像素窃取攻击在 M1/M2 MacBook Air、Pixel 6 Pro、OnePlus 10 Pro 及 NVIDIA/AMD 独立 GPU 上平均 10-20 秒窃取一个像素、准确率约 60-80%。Safari 不向 iframe 提供 cookie（只显示通用的"欢迎新用户"）挡住了像素窃取，但已访问链接的着色差异仍可被同样的时序攻击分类：attacker.com 嵌入多个链接后逐个像素窃取判访与否，在 M1/M2 MacBook Air 与 iPhone 12/13 上平均 200-250 秒恢复一个链接、准确率 90-100%。最后一项网站指纹攻击利用 macOS 无特权用户即可读取 GPU 频率与功耗的 API（重大安全问题），google.com、amazon.com、nytimes.com 的频率/功耗轨迹各不相同且可指纹化：100 个网站的概念验证达到 27% 命中率（基线 1%）。（YouTube EP5V_pgnXCP6g，[405.0-799.9]，L1）
- 〔SREcon（推测）〕Meta 生产工程师 Yoshinori（MySQL 团队技术负责人，早年为 MySQL 顾问、Oracle DBA）谈在线数据库 SRE 的可靠性、性能与一致性共同挑战。他指出绝大多数数据库采用单主多副本架构、因一致性难题多主难以运维，Meta 按用户 ID 哈希分片（sharding/replica set）并跨多可用区做地理复制，但为控制成本保持主实例轻量、副本数量有限（美西到美东约 50-70ms、EMEA 超 100ms 延迟需应用容忍）；存储结构上对比 B-tree 与 LSM（RocksDB、HBase），Meta 最大社交图数据库 UDB 基于 MySQL+RocksDB 的 LSM 结构且前置缓存服务 Tao 挡住多数读请求，使空间受限场景下 LSM 得以良好运转；单主架构下主实例是单点故障，死主提升（dead primary promotion）的最大风险是脑裂导致成功写入丢失且几乎无法修复，因此主流方案是 Raft/Paxos 共识（MySQL Group Replication、Spanner、MongoDB 等），Meta 也正在 MySQL 中实现 Raft。（YouTube EP1DrLUEfE5Jw，[10.1-1483.6]，L1）
- 〔SREcon（推测）〕级联故障转移与过载治理：频繁 failover 会使副本数不断减少直至丧失冗余，Meta 用 primary capable instance（7 个副本中保留 3-4 个可升主）兜底，并以 admin 端口区分过载与真故障避免误切换；崩溃安全复制借助全局唯一事务状态 GTID，让宕机恢复的实例直接从新主追平、几秒几分钟恢复而非整库重建（1TB 实例重建需 1-2 小时）。过载多由坏查询触发——应用重试一条一小时的查询逐渐吃满全部 CPU 核心，可用 SHOW PROCESSLIST、EXPLAIN（新版还能对运行中查询看执行计划）排查，并靠查询内注释定位责任团队直接 ping on-call；正确性方面建议开启数据块/复制日志校验和，RocksDB 新引入 key-value checksums 检测内存位翻转后校验和仍有效的情况，并自研全库扫描的正确性检查工具，曾借此定位主副本数据漂移的位翻转根因、从主库重灌副本。（YouTube EP1DrLUEfE5Jw，[1484.0-2955.2]，L1）
- 〔会议不详〕Gabriel Ryan 报告论文《Fine-grained Data Flow Tracking with Proximal Gradients》，聚焦数据流分析——对所有可能输入概括数据如何在程序中流动。动态污点分析（DTA）用布尔标签近似数据流、标记源在执行中按传播规则动态扩散，广泛应用于漏洞利用检测、灰盒模糊测试、恶意软件分析与信息泄露识别；但布尔标签无法表达全部程序行为，导致过污点（over-taint）等传播错误（如 x-k 与 x-x1 相消后 x2 仍被标记），污点系统设计者只能在更健全（sound，传播更多、易过污点）与更精确（传播受限、易漏流）的规则间取舍，位级跟踪仅对位掩码等特定操作减少错误且增加开销。（YouTube EP5WG2NDeO8TM，[8.8-309.8]，L1）
- 〔会议不详〕核心思路是用梯度（gradient，机器学习中常用的数据流量度，可经链式法则跨操作复合）替换污点标签、用梯度链式法则替换污点传播规则，天然规避许多错误：在 x 被抵消的例子中梯度逐项相消归零，正确判定 x 到 x2 无数据流，区别于 Oakland 上发表的 Neotame 与 NDSS 2019 的 TaintInduce。针对位运算等不可微操作提出近端梯度（proximal gradient）近似：沿单一方向采样函数、选取引起最大输出变化的样本插值出近似梯度；实现为 LLVM sanitizer pass“gradient sanitizer（GRSan）”，在七个开源文件解析器上与 libdft、Dataflow Sanitizer（DFSan）对比，F1 全部更高，相比最优 DTA 框架 DFSan 平均提升 20%、最高提升 33%，代码已公开发布。（YouTube EP5WG2NDeO8TM，[327.3-624.8]，L1）
- 〔Percona Live（推测）〕Yoshinori Matsunobu（Facebook 生产数据库工程师，前 MySQL 顾问）讲述 Facebook 从传统 MySQL InnoDB 迁移到自研存储引擎 MyRocks 的缘起。Facebook 是全球最大 MySQL 用户之一，社交图谱存于大规模分片、PB 级的 InnoDB，前置巨大记录缓存 Tao，查询处理约 1ms 且高度自动化运维、纯闪存存储；在闪存上 InnoDB 暴露三大问题——修改单字节也要写整页 16KB 再加 doublewrite 翻倍的高写放大、随机插入导致的 B-tree 页碎片（常见浪费 50% 以上空间）、以及压缩页按 8KB 对齐致至多省一半空间，故团队研究 LSM 架构（源自 Google LevelDB 的 RocksDB，Netflix 等也在用），并以可插拔存储引擎方式将 RocksDB 集成进 MySQL，即开源的 MyRocks（myrocks.io），MariaDB 与 Percona 均提供支持。（YouTube EP5X2bSHPWUqg，[5.7-1481.2]，L1）
