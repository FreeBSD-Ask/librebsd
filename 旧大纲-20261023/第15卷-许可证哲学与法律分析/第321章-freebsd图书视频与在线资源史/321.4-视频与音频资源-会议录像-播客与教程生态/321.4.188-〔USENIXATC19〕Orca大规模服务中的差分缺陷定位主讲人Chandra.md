- 〔USENIX ATC '19〕Orca：大规模服务中的差分缺陷定位。主讲人 Chandra Maddila（微软研究院印度所 Applied Sciences Group，常驻 Redmond；合著者 Ankit、Rahul、Aditya 同属 MSR）介绍这项曾获 OSDI 2018 最佳论文的工作。他先梳理典型 DevOps 生命周期（开发、构建与测试、发布、部署后）与事故处理流程：服务出现异常行为时上报事故，值班工程师或 SRE 认领后翻大量日志、逐个询问各组件负责人以定位根因，再通过回滚变更或修复缺陷来缓解，整个过程随机、人工，耗时数小时乃至数天；Orca 属于微软 Sankey 项目（用 AI、ML 与信息检索技术改善开发生命周期各阶段），面向部署后阶段，只需两个输入——症状文本（告警名、异常信息或日志内容）与症状出现的构建号，输出按嫌疑度排序的提交或 PR 列表。三条关键观察构成前提：症状与代码变更之间存在强文本相似性（例如日志里的 operation not supported for type mail id 与把 get_mail_session 改为新增必填入参的提交互相印证）；文本相似性往往出现在同时发生的一组变更而非单个提交，因此需要判断哪一处真正引入缺陷；且问题显现的构建未必是引入问题的构建，加之微软采用环形部署（同一 VP 下属一个环、全公司一个环、全球外部客户一个环）伴随持续的反向与正向集成，构建图并非线性，同一环内的多个构建互为祖先或兄弟。（YouTube EPUwDhsaAc7pg，[10-461]，L1）
- 〔USENIX ATC '19〕Orca 的检索流水线、评分与实证效果。对症状文本做分词、词干化与词形还原，并用 TF-IDF 衡量 token 的重要稀有程度（Microsoft、Outlook 之类常现词信息量低，compose mail 这类具体短语才有指示性）；再用构建图找出兄弟、父、祖父等候选构建集合，把每个构建拆开得到提交、被修改的目录与文件，并对变更前后版本各建抽象语法树以定位被改动的节点，共同构成检索空间。相关性分数把 token 的 IDF 权重与匹配位置权重相乘（函数名与类名的权重高于文件名与目录名，且权重可动态调整），据此对提交与 PR 排序，并接入微软事故管理系统，在事故卡片底部直接列出建议优先查看的根因提交与 PR。评估在 74 个已知根因的真实线上事故上进行：仅用语法树差分可命中 43 例，加入构建图后提升到 52 例，命中率约 73%，平均互惠排名 0.44 意味着命中时根因通常排在第二到第三位（若排到第九、第十位则要先翻遍十几个 PR），平均恢复时间缩短约三倍，已部署到两项大规模云服务。问答中主讲人解释了未命中的两类主因：某些模块的探针要在根因出现一百到一百五十个构建后才报警，而工具为控制误报最多只回溯二三十个构建；以及症状文本过于笼统（例如 Kerberos 认证失败的顶层只报 page is not loading），并坦言为端到端机器学习模型整理训练数据极其困难、需要工程师与事故管理流程的文化转变。（YouTube EPUwDhsaAc7pg，[461-1091]，L1）
- 〔LISA15〕把 Puppet 用到网络设备上。Puppet Labs 的 Scott Garman（Release Engineering，嵌入式 Linux 与发行版背景，常驻波特兰总部）与 Rick Sherman（前网络设备厂商，负责扩充平台覆盖）联手介绍这一方向。Puppet 是声明式的配置管理与应用编排工具：定义期望的终态而非过程脚本，节点默认每三十分钟上报 facts（平台识别信息），服务器编译出 catalog（期望状态），节点据此幂等地应用变更并回报，供生成变更报告；模块可在 Forge（forge.puppetlabs.com）复用，已逾三千七百个，另有 Enterprise 版解决大规模部署下的节点分类等问题，学习资源包括 learn.puppetlabs.com、学习虚拟机、自学课程与讲师培训与认证。网络侧的独特困难在于设备异构、厂商专有 CLI 在同一厂商不同机型之间都不一致、单机配置动辄数百到数千行，且即使配置到位也不保证达成期望状态（常与不受控的第三方互联），厂商新功能发布又需 18 到 24 个月；演讲举例某次第三方 BGP 配置失误使 Amazon Web Services 的路由被抽走超过半小时、影响达数百万美元。支持进度包括：Arista EOS（自 EOS 4.13 起，兼容 PE 3.7.2 及以后）同时提供 Arista 自写模块与 NetDev Standard Lib；Cisco Nexus 9K 与 3K 系列（九月发布，兼容 PE 2015.2 及开源 4.0 起，puppetlabs/cisco 模块本周刚加 BGP），5K/6K/7K 预计 2016 年第一季度；基于 Debian 的 Cumulus Linux 2.2 及 x86 白盒交换机，可用标准 Linux 模块配置 NTP 等；F5 Big-IP 通过 Puppet Device 代理 REST API、无需在设备上装 agent；华为 CloudEngine 12800 搭配华为操作系统 6.0，agent 出厂预装。类型方面 NetDev 覆盖 NTP、syslog、基础接口、AAA、SNMP，厂商类型包括 BGP、MLAG、VXLAN，另有 eos_command 与 cisco_command_config 这类“拐杖”直接下发任意 CLI，但幂等性不保证。（YouTube EPV-8TaxP3LPg，[10-1400]，L1）
- 〔LISA15〕代码示例、跨厂商标准与社区问答。三位讲师分别给出同一件事的 Puppet 写法：Arista 上声明 EOS 角色、确保 agent 安装运行后配置 NTP 源接口与服务器；Cisco Nexus 由于当时尚无 NetDev 类型而用 command_config 直接下发 CLI 列表；Cumulus 上则复用与 Linux 服务器相同的标准 NTP 模块；随后是 Arista、Cisco、Cumulus 三家 VLAN 干道配置（同一 Ethernet 48 接口设为 trunk、传入 VLAN 区间与静态 VLAN、设置 native VLAN）的对照，差异主要在语法与厂商自定义类型。落地建议是先在实验室从小处起步（syslog 或 NTP 这类出问题不影响业务的服务），再逐步推进到网络端口等高级功能。关于标准化，演讲介绍 IETF 已通过的 Netconf（XML 承载、缺乏格式护栏，提供 get/set/lock/unlock 配置 RPC 与对应 CLI show 命令的操作型 RPC，历史上走 SSH、如今正转向 HTTPS 的 RESTCONF）、Netconf 的数据建模语言 YANG（人类可读、内容仍属厂商专有但可扩展可继承），以及 IEEE、IETF、CableLabs 与 Google、AT&T、Apple 推动的跨厂商 OpenConfig 模型；Puppet Labs 计划让 NetDev Standard Lib 向 IETF 等标准靠拢（例如按 IETF 的 BGP 定义组织类型），但明确担心把 YANG 模型机械翻译成 Puppet 类型会产出难以使用的“意大利面”，因此希望听取用户反馈。问答涉及 Dell Force10 自编译 agent 未获 Puppet Labs 认证、缺少配置 diff 沙箱（只能靠 no-op 或直接在虚拟机上验证）、老款 Cisco IOS 无法安装 agent 只能走 Puppet Device、Juniper EX 系列因 GCC 版本问题卡在无法升级到 4.0、agent 作为常驻守护进程每三十分钟唤醒一次，以及为何选择等厂商配合而非全量采用 Puppet Device 快速扩张。（YouTube EPV-8TaxP3LPg，[1400-2342]，L1）
- 〔USENIX ATC '25〕LogCrisp：让大规模压缩日志也能做聚合分析。主讲人 Gu Hao（清华大学，代表同事 Junyu Wei 报告，清华大学与阿里巴巴集团合作）说明背景：据亚马逊云与阿里云的披露，日志存储已成为最热门的服务之一，阿里云日志规模可达每天 PB 级且需保留至少 180 天，工程界因此拼命压缩日志，但在压缩后日志上做聚合分析仍是开放挑战。当前最先进的模式化日志压缩先解析出语句模板与变量（时间戳、文件路径、块号等），再为每类变量抽取模式，把变量重排成若干细粒度存储单元独立压缩与解压，压缩单元与映射文件、静态内容共同构成压缩文件；查询时用映射文件与静态内容过滤、只解压少数单元，阿里云生产上即采用这一方案。两个根本挑战随之而来：一是日志被切分成块后存在全局模式（从全量日志块的样本抽取后统一套用）与局部模式（逐块抽取并压缩）两种方案，聚合必须依赖全局描述，但全局描述缺少局部精度、影响模式过滤效率（例如全局模式 BLK 适用于所有块，但在某些块里第一个变量其实是常量，用局部模式本可免解压）；二是压缩会产生大量仅含数字的 N 单元，把它们编成整数向量有利于聚合（例如先按 BLK3 过滤、再筛长度大于 40、最后求最大长度），但日志本质是文本、仍需支持全文查询，因此如何在数值化单元上执行前缀查询成为难题。（YouTube EPV0iGMapywFc，[18-246]，L1）
- 〔USENIX ATC '25〕LogCrisp 的两阶段模式抽取、SIMD 前缀查询与评估。针对全局与局部的取舍，提出两阶段模式抽取：把模式拆成 sketch 与 spec 两部分，sketch 全局抽取以提供聚合所需的全局描述，spec 局部抽取负责过滤，二者共同参与过滤，并保证过滤能力等价于纯局部模式。针对第二个挑战，用 SIMD 在 N 单元上执行查询，最难的是向量化前缀查询：作者观察到前缀查询等价于判断编码后的数字是否落在某个区间（比较区间）内，而比较区间逐数字不同、难以向量化确定；但通过移位很容易确定每个数字对应的以 2 为底的区间（挤压区间），并证明每个挤压区间至多包含一个比较区间，由此构造一张对照表，用右移几次使数字变为零来判断挤压区间，再用向量化 blending 把对应比较区间载入 SIMD 寄存器（无对应区间则载入空区间），直到所有编码数字归零后得到每个数字的比较区间，最后执行向量化区间查询。系统 LogCrisp 先对全量日志块的样本抽取全局 sketch，再为每个日志块抽取 spec 与全部单元并整体打成 zip，内部包含日志、局部 spec、单元、映射与静态内容，N 单元按整数向量编码。评估在 Linux 服务器上取两个开源数据集与一个阿里云真实生产数据集，并额外跑 6 TB 规模数据，与全局式的 CLP 和局部式的 LogGraph 对比：分析时延在所有数据集上都最低（约为 CLP 的十五分之一、LogGraph 的四分之一）；摄取速度在开源日志上最多快两倍、生产日志上快三倍且与全局方法相当；压缩率分别为最优者的 89% 与 97%；引入向量化查询后前缀查询时延较直接在字符串编码数据上查询最多低 1.5 倍。（YouTube EPV0iGMapywFc，[246-551]，L1）
- 〔USENIX Security '23〕AURC：交叉校验文档、调用与调用方以发现代码与文档错误。中国科学院大学的 Hu Peiwei 从现代软件日益复杂、越来越多依赖开源库谈起：开源库构成金字塔底座、支撑顶层的实用软件，一旦底层带病就会波及上层，例如 Log4Shell 影响的下游产品超过一千八百个，因此检测开源库中的代码缺陷十分重要。已有缺陷检测普遍依赖三条不可靠假设——文档是正确的且相关 API 都写进了文档；从代码库抽取大量 API 用法后以多数投票判定哪种用法正确；正确用法一定存在于相似上下文中。作者类比有经验的工程师面对陌生 API 时会做的三件事：读文档、看该 API 的源码、看现有代码如何调用它，对应 API 调用中的三类对象，称为 API 用法参考（AUR）：document、call 与 caller。AURC 分别从三者抽取信息并交叉校验，而不是像前人只用其中一到两种，再执行正确性推断，决定应该修改哪一方以恢复一致性；整体流程为从 document、call、caller 分别抽取信息，交叉校验后进行正确性推断。（YouTube EPV3meIQaZcd4，[8-230]，L1）
- 〔USENIX Security '23〕AURC 的返回检查建模、分析优化与实证。当前版本聚焦错误的返回检查：先从调用侧抽取返回取值，例如某 API 的返回包含 -1 与另一个被调 API（BN_bnm_add）的结果，借助调用图拓扑排序可确保被调 API 的返回值已被预测并可用，于是取并集得到 -1 与大于 0；文档侧得到同样结论，二者一致；但调用方第三个案例把正、负返回当成同一执行状态，与文档和调用侧冲突，此时按第一条规则（文档与调用方一致而调用侧不一致，则修调用侧代码，因为错误源于使用者）修复。为应对两个分析成本问题——调用链很长、以及返回语句位于执行路径尾部导致前向分析开销大——采用调用图拓扑排序把过程间问题转为过程内问题，并提出上下文敏感的向后回溯预测，通过迭代查找到达定义而非从首行开始分析。文档侧同样有两个障碍：文档可能含与返回值无关的句子、也可能用自然语言而非数字或区间描述返回值，因此用 BERT 分类器剔除无关句子，再用映射表把自然语言还原成对应的区间或数值。基于对大量补丁的分析提出四条正确性推断规则，例如调用侧与调用方一致而文档不一致时，代码可正常运行，最安全的做法是更新文档。原型在十个代码库上找出五百多个代码缺陷与两百多个文档缺陷，误报率 12.1%、漏报率 9.1%；分类器的平均准确率与召回率分别为 95.5% 与 94.3%；向后分析可省掉 88% 的代码分析量，拓扑排序加 API 替换可省掉 99.94% 的路径；逾两百个代码补丁与一百个文档补丁已被维护者合入，作者凭借 AURC 在 OpenSSL 的八百名贡献者中排进前二十五，并得到维护者的积极反馈。（YouTube EPV3meIQaZcd4，[230-638]，L1）
- 〔USENIX ATC '24〕Camel：不依赖非易失存储的纯软件间歇计算。弗吉尼亚理工的博士后 Harrison Williams（合作者 Simon Maud 现就职于 Amazon，导师 Matthew Hicks）指出，移动与物联网设备规模预计到 2030 年超过 250 亿台，绝大多数是资源受限的小型传感节点，广泛用于工业物联网、可穿戴与植入式医疗器械、智慧城市环境监测等场景，在这些规模下电池供电在经济设计与生态上都不成立。免电池系统以能量收集电路加超级电容工作：充电到使能电压（示例 3.3 V）后上电，耗尽到关闭电压（1.8 V）完成一小段任务，基本模式是短脉冲加长时间充电，基本挑战是在断续电源下维持长任务；通用做法是断电前把易失状态写入持久存储、下次上电恢复后继续执行。但物联网节点上最常见的非易失存储是闪存，写功耗高且耐久仅一万到十万次，间歇计算的写频率会把系统寿命压到数周至数月，远达不到期望的数十年，因此研究者转向 FRAM、MRAM、RRAM 等新型存储——写不比 SRAM 慢多少、无实际耐久限制，却几乎没有商用供货。作者先前的 Total Recall 利用 SRAM 数据保持电压远低于微控制器最低工作电压这一特性（约 400 mV 仍可完全保持数据、1.8 V 系统才停摆）配合大容量电容把供电维持数小时到数天，把检查点从整块拷贝简化为对全部 SRAM 求校验和；但感知-计算-发射类应用的外设操作不可跨断电拆分（如无线电发射必须在一个电源周期内完成），研究界因此采用按任务边界插入检查点、断电自动回滚并重执行的任务式编程模型（还省掉了片上能量监测这一显著功耗项），而任务式模型需要一个真正持久存储中的已知良好状态，这与基于 SRAM 校验和的做法直接冲突——任务里第一条指令就会改动刚算完校验和的内存，使检查点立即失效。（YouTube EPV7FCBspvkSg，[17-474]，L1）
