- 〔会议不详〕PopStar：低泄漏的轻量级阈值报告（heavy hitters）系统，与华盛顿大学的 Sarah、Stefano 合作。任务是在损坏服务器（可与某些客户端合谋）面前统计超过阈值 tau 次的报告值（如崩溃事件）而不泄露个体报告；通用 MPC 太慢，故定制轻量协议并容忍可控泄漏，引入第二个非合谋服务器。对比两个现有系统：Poplar 用对称双服务器、恢复时泄露 heavy hitter 前缀；Star 的第二服务器无状态免交互、计算更轻但易被恶意报告打掉目标值，且泄露完整匿名直方图易受频率分析攻击——PopStar 取两者之长，服务器计算约为 Star 的 7 倍但仍远轻于 Poplar。（YouTube EPD6nBy37dPHc，[8-378]，L1）
- 〔会议不详〕PopStar 协议与原型评估。在 Star 的 OPRF 与 tau 次多项式报告之上为输入的每个前缀关联多项式，隐藏计数低于阈值的 tag 子群以大幅降低泄漏；朴素的逐位前缀版本会被 2L 次自适应查询逐位攻破，故改用 oblivious double-PRF（多项式绑定到由 x 派生的伪随机值 y）阻断攻击。泄漏恰为前缀树中大小不超过阈值的粉色终端节点；原型用半诚实混淆电路+恶意 OT 实现 OPRF，客户端报告 1.5 KB，百万报告服务端聚合约 2 分钟（Poplar 约需 2 小时，Star 快约 7 倍但泄漏更大），论文另含抗恶意报告的 robust 变体与启发式差分隐私机制。（YouTube EPD6nBy37dPHc，[378-737]，L1）
- 〔USENIX ATC（推测）〕EROFS：面向资源稀缺设备的压缩友好只读文件系统。主讲人为上海交通大学 IPADS 的 Mingkai Dong（转写 Ming Kai Dong），合作者包括其导师陈海波（转写 Hai Bochen）等。SquashFS 用于 Android 系统资源会卡顿甚至重启，其固定尺寸输入压缩带来读放大（读一个字节要解压整块、块不对齐进一步放大 I/O）与解压时大量缓冲区导致的内存压力；EROFS 改用固定尺寸输出压缩，配合隐式 I/O（复用 VFS/专用页缓存页）、vmap 解压与每 CPU 四页 buffer 解压等多种方案减少读放大、内存拷贝与分配。（YouTube EPD9R4TRjUOic，[10-466]，L1）
- 〔USENIX ATC（推测）〕EROFS 评估、部署与 Q&A。在 HiKey 开发板与高/低端手机上用 FIO 对比 SquashFS（多种 chunk 尺寸）、Btrfs、EXT4、F2FS：读放大较 SquashFS 降逾 80%，解压内存降逾 90%，低端/高端手机应用启动时间平均降 3.2%/10.9%；已部署于华为 EMUI 9.1 并上游进入 Linux 内核主线，在数千万部手机上节省系统资源 30% 以上存储。Q&A 承认功耗未实测（预计因减少 I/O 与内存分配不会更差），指出空间节省低于约 24% 时顺序读会劣于 EXT4（可部分文件不压缩缓解），低压缩比与加密文件在真实部署中也留作不压缩。（YouTube EPD9R4TRjUOic，[467-1024]，L1）
- 〔会议不详〕OpenOptics：光数据中心网络的开放研究与开发框架。主讲人 Federico 代第一作者 Yiming（因签证限制未能到场，现为框架主要贡献者与维护者）宣读。光交换（电路交换、物理层无队列）能以低成本高带宽应对电交换机 Moore 定理失效与 AI 流量激增，但现有方案是封闭生态：RotorNet 研发周期近十年，Google Jupiter 选择慢速光开关配专用拓扑/流量工程栈，Microsoft 则以超快光开关构建全盲交换结构，各研究缺乏统一评估平台。OpenOptics 将软件与光硬件解耦，支持物理测试床、NS-3 仿真与 Mininet 模拟三种后端，可插拔式实现与对比不同光架构。（YouTube EPDJ33HHI8xnw，[17-472]，L1）
- 〔会议不详〕OpenOptics 核心抽象与评估。核心的 time flow table 在 SDN 流表上增加到达/离开 timeslice 维度以表达“包可在中间节点等待直连电路”，每端口实现按 timeslice 分队列的 time-based backpressure 调度，避免发错电路与队头阻塞；提供 Python 路由/拓扑/遥测 API，约 10 行代码即可部署。测试床用 4 块 Intel Tofino 2 交换机模拟微秒级光开关、MEMS 光开关跑毫秒级架构，在 Memcached 与 Gloo（转写 Glu）ring reduce 上做跨架构对比，与 RotorNet 论文趋势一致以验证保真度，并展示 VLB 路由的乱序包会严重破坏 TCP 吞吐（需专用传输层）；框架完全开源并提供逐 timeslice 拓扑可视化仪表盘。（YouTube EPDJ33HHI8xnw，[475-934]，L1）
- 〔FAST〕CloudScape：首个大规模真实云架构数据集研究。主讲人为威斯康星大学麦迪逊分校博士生（转写音 Sam Bhoj，师从 Andrea 与 Remzi Arpaci-Dusseau），与 UW-Madison 和 NetApp 合作。从 AWS“This is My Architecture”视频播放列表出发，用迭代编码（iterative coding，多人独立编码再达成共识指南、后增 3 名编码员并验证）把近 400 个架构、380 家公司近 5 年的真实架构转成图数据集：节点为 AWS 服务与实体，边区分承载数据/触发类交互并带序列号，每个架构还捕获完成一个工作单元的 workflow（如 Snapchat 发图的存储与通知路径）。（YouTube EPDPmY7bR4W0w，[16-490]，L1）
- 〔FAST〕CloudScape 存储层四项发现。存储层最多用到 14 种存储服务，90% 架构使用专门存储服务、过半用 2 种以上（多样化异构）；S3 最流行（占 68%，为第二名的两倍），其后为 DynamoDB 与 RDS，分布式文件系统在 Web 部署中反而罕见；S3 数据重要性不均（日志可容忍不可用而配置文件不可用会卡死集群，S3 却一视同仁）、DynamoDB 常存指向 S3 对象的精简元数据，提示存储层紧耦合；与存储交互最多的是 serverless——Lambda 用于 65% 架构、约 20% 架构仅用 Lambda 一种计算服务，凸显捕获真实 serverless 存储负载的必要。数据集公开并提供交互式 Web 探索器。（YouTube EPDPmY7bR4W0w，[492-980]，L1）
- 〔会议不详〕HTM-FS：首个基于硬件事务内存（HTM）的持久内存文件系统，来自上海交通大学 IPADS（主讲人转写音 GFE）。文件系统需同时保证每请求顺序一致性与崩溃后 all-or-nothing 语义；PM 可用 load/store 指令以近 DRAM 速度访问，但写持久化所需的 cache line flush 指令会中止 Intel RTM；第二代 Optane PM 与新 Xeon 平台的 EADR（增强异步 DRAM 刷新）把 CPU cache 纳入持久域、保证“全局可见即持久”，为 RTM+PM 组合提供可能。但 RTM 读写集有限、文件系统调用路径嘈杂，直接包裹整个操作易致容量/冲突中止。（YouTube EPDRHydH0Nn2M，[8-454]，L1）
- 〔会议不详〕HOP 机制与 HTM-FS 评估。HOP（Hardware Assisted Optimistic Persistence）把文件系统操作按读/不可见写/可见写分类，将单个操作拆成多个小事务只包裹可见写（类似 transaction chopping），不可见写可低成本回滚、关键写由 sequence count 保护；设计崩溃后可回收的原子内存分配器（每线程 free/allocated list）防泄漏，目录用哈希分桶 sequence count 提升并发，rename 靠检查根到当前路径全部 sequence count 避免成环。基于用户态文件系统 ZoFS（转写 ZeroFS/ZFS）实现，FXMark 与 TPCC on SQLite、LevelDB 显示其性能与弱崩溃一致性的最先进文件系统相当甚至更好，“几乎免费”获得强崩溃一致性。（YouTube EPDRHydH0Nn2M，[455-908]，L1）
- 〔NSDI〕主讲人介绍 FlowBlaze——把有限状态机引入 match-action 抽象并在 NetFPGA 上实现的有状态包处理框架。讲者指出 NIC 正被 FPGA 增强、网络函数可装入网卡，但用硬件描述语言加综合流程编程 FPGA 对网络专家太困难，而 match-action 表（表大但只能经控制面写、寄存器可从数据面读写却容量小）难以描述有状态函数；FlowBlaze 在流水线中引入每流状态机（前置 flow context 表存流状态、转移表置于原 match-action 单元并加反馈回路），用 stash 缓冲加惰性搬移解决 Cuckoo 哈希插入时间可变的问题（插入时间可随负载因子放大 300 倍、在流水线中形成气泡），并以按流加锁而非全局锁消除反馈回路的竞态、避免锁整条流水线带来的性能损失。（YouTube EPDXqoiLLWL2Y，[10.7-741.7]，L1）
- 〔NSDI〕评估与结论。团队实现了约 10 个用例（NAT、防火墙、流量策略器、含序列号检查的完整 TCP 连接跟踪、key-value 存储等），全部由同一硬件单元承载；与优化过的 DPDK 网络函数执行器对比，无状态函数单 CPU 核即可达到相近性能，而引入状态处理后软件因额外查找与写回需要 3 个 CPU 核才能匹配 FlowBlaze 的线速；在 NetFPGA 原型 40 Gbps 线速最坏流量与真实流量轨迹测试下，细粒度五元组流定义时丢包率低于 1%、粗粒度约 2%（比全局锁方案好最多 10 倍），stash 在五元组定义最坏情况仅需 8 项，项目硬件与软件实现均已开源并可在 poster session 交流。（YouTube EPDXqoiLLWL2Y，[741.7-1525.4]，L1）
- 〔USENIX ATC（推测）〕论文 SelfTune: Tuning Cluster Managers（讲者为前微软研究院合作者）报告。大型云的集群管理器（Kubernetes、Azure、Google Borg、Facebook Twine、微软 Exchange Online workload manager）依赖数百个配置参数，通常凭领域专家加有限实验设置，且全局静态配置会在时间与空间两个维度产生次优（如 Kubernetes 用户反馈周末负载适应过快导致低估次日负载）；作者提出 SelfTune 框架，将调优建模为 RL 问题并搭载集群管理器天然的"测量健康—调整状态"迭代循环，仅通过 predict 与 set_reward 两个 API 集成、几乎零工程开销，隐式上下文（implicit context）支持按机器、集群或应用级粒度调参，学习引擎采用基于近期工作的连续 bandit 算法而非需手工特征与假设多的贝叶斯优化/传统 RL。（YouTube EPDfU2yx1XW8A，[12.7-506.2]，L1）
- 〔USENIX ATC（推测）〕三套场景评估。Kubernetes 上用 DeathStar 基准模拟约 30 个微服务的社交网络应用、以 p95 尾延迟为 reward 调约 100 个实数与离散参数，8 个样本即达到贝叶斯优化与 epsilon-greedy 需 30-40 个样本的效果且迭代成本更低；Exchange Online workload manager 生产环境部署数月，以吞吐（grant ratio）为 reward 时吞吐提升至少 25%（部分场景超 100%）且资源利用率无回退，以资源利用率（HUP）为 reward 时提升 1-3% 且吞吐同时提升 15-20%；Azure Functions 上对 prewarm/keep-alive 参数做应用级调优，以网格搜索的 Pareto 最优解为起点，在冷启动率无显著增加的情况下内存浪费降低 10-12%。（YouTube EPDfU2yx1XW8A，[506.2-1012.5]，L1）
- 〔SREcon（推测）〕负责 Google Compute Engine 与 Persistent Disk 可靠性的 SRE Michelle Brush 的演讲，主题是 LLM 时代 SRE 工作如何变化。她从代码中的"This should never happen"注释切入，指出每行代码都可能承重（load bearing）并携带编写时的假设、设计/上线/代码评审只是时点性检查；以 Jevons 悖论预测编程变便宜后世界会建造更多系统、反而增加对高技能工程师的需求，以 Bainbridge《The Ironies of Automation》说明自动化掉大部分工作后剩下的人类工作反而更难（监控自动化、修复其失败、技能衰减），并用"知识的诅咒"模型刻画 LLM 本质上"无意识胜任"（unconsciously competent）——知道很多但解释不了为什么，幻觉则是其"无意识不胜能"状态在无源材料时自行填补空白。（YouTube EPDqpcVQIs3G8，[17.6-1278.2]，L1）
- 〔SREcon（推测）〕应对之道。引用 Richard Cook《How Complex Systems Fail》与 4+1 视图说明系统越复杂越呈涌现行为，主张把通用缓解（generic mitigation：重启、回滚、驱逐硬件/热迁移等）当作系统需求并随每次变更持续验证（如 Compute Engine 持续注册、隐藏并删除集群的自动化，以及对 AI/ML 用 evals 持续测试）；用 agent 组成"小部队"按反模式提问并修复（缺失的错误重试、无 backoff/jitter 的重试、过时的 playbook、并发与资源管理问题），不再执着根因而转向持续补救风险，最终实现"不必管理 bug 积压"的愿景；引用 Mark Schwartz《The Art of Business Value》重构优先级（一小时能修好并验证的低优 bug 也是风险，Google 有"I told you so"徽章），把工作组织为一系列实验并保留可选性，用架构适应度函数（architectural fitness function，如 SLO）守护系统级不变量。（YouTube EPDqpcVQIs3G8，[1278.2-2556.4]，L1）
- 〔FAST（推测）〕报告 clustered fault tolerant write acceleration 在虚拟化环境中的实践实现。VM 密度上升使虚拟化数据中心面临 I/O 瓶颈，买更好硬件是破坏性且临时的方案，host-side flash 回写（write-back）缓存比 write-through（只缓存读）加速更明显（Microsoft Jet stress 与 FIO 混合负载验证）；但回写加速面临三大挑战——VM 迁移后失去对前主机 flash 上脏数据的访问、写密集 VM 会写满 flash 而 SAN 上是旧数据不能直写（否则数据损坏）、flash 故障导致脏写丢失；系统 FVP 通过让每个主机访问彼此的 host-side flash、迁移后新主机把 miss 的读重定向到前主机并逐步重建缓存足迹实现无缝 VM 迁移，并用流控（flow control）在确认写回 VM 时注入递增人为延迟，让 destager 有时间把脏写批量（批内不重叠、轮询调度）落盘到 SAN，最坏降至 SAN 速度但 VM 无需 stall。（YouTube EPE19ENyFyg08，[9.8-818.4]，L1）
- 〔FAST（推测）〕容错与评估。FVP 引入 write back with peers 策略把 VM 写复制到对端主机 flash，配合由虚拟机文件系统仲裁的 on-disk 锁（内容为 checkpoint 序列号加 VM UUID 加加速策略）协调恢复：flash 故障走 online replay（对端接管锁并把复制写落盘），主机故障走 offline replay，最多可容忍 P 个 flash 故障且恢复完全分布式、checkpoint 定期持久化以加速级联故障；实验显示迁移后读取延迟更快回到 flash 延迟、flow control 在约 80 秒写满后触发、peering 因单 NIC 支持不足使吞吐下降但即便两个 peer 仍优于 write-through，实现容错与加速双赢；提问环节 Saurabh Kadkol 与 Nimble Storage 的 Umesh 就迁移场景与回写缓存收益本质提问，讲者答以 VM 写的突发性使 flash 吸收突发的网络延迟远低于 SAN 延迟。（YouTube EPE19ENyFyg08，[818.4-1636.7]，L1）
