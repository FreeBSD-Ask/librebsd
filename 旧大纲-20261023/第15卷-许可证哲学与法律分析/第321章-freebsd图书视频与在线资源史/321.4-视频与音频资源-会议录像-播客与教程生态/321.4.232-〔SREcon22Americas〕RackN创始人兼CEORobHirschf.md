- 〔SREcon22 Americas〕新系统于是明确按几千台而非一百万台来设计、第一版数据库干脆就是一个文件系统，因为它是 first-in 平台——在什么都没有的数据中心先落地、任何先决条件哪怕只是数据库这类简单依赖都会被嫌弃〔16:32〕。V3 的两大结构性转折是：把 TFTP、DHCP、HTTP、API 与数据存储全部收敛进同一个 Go 后端，因为服务收敛在单体内反而更利于扩展；以及让 CLI 本身成为 agent：开机后把任务拉进本机执行、回传结果再领下一个，服务器只负责算出任务清单、后端不再是瓶颈〔16:51〕。与此同时他们主动放弃有向无环图：确有跨组件同步的场合、但用更线性的工作流把协调点交给后端等待即可，让服务器替所有人预先算完反而有害；于是从服务器承担全部逻辑转向在客户端承担，并从最少的逻辑起步、逐步加回——这要求保持敏捷与极度克制不过度工程，用 CTO 的话说就是我们停止预测、停止猜〔18:57〕。下一个顿悟是一次银行客户的会议室试点：一套三万台机器的 HPC 系统、三个区域每区一万台、每周只有两小时窗口做重装机，实际一次跑两千五百台要三小时、还有百分之二十的失败率〔20:38〕。运维团队很肯定地给出了操作步骤、可他们并不知道自己装机流程里到底发生了什么——原以为一天就能完成的试点变成了一次考古挖掘：客户要集成十套系统、他们只知道自己中的三套；团队当场一边挖一边写集成、最终靠全部十套集成与正确时序才交付成功〔21:44〕。他由此确立原则：绝不告诉客户他们做错了、也绝不要求他们弃掉某个系统，并且我们永远不认为客户在运维上是错的〔22:28〕。此后最大的架构改动是重写后端：组件数升到千级后他们又落回 Chef 时代的锁问题——每次写入都锁在一类对象上、因此把文件系统重写为支持分布式锁与更细粒度加锁的形态；这也意味着要投入大量自有知识产权、无法再以开源继续，最终只有支撑到万台规模的部分变成自有 IP、其余仍开源；他直言这是正确选择〔24:16〕。真正让规模越线的是客户跑赢他们自己的一次周五下午告警：某全球分布式银行客户不愿接受联邦控制面模型、坚持把一切都塞进一个中心数据库〔27:22〕。周五下午三点他们做 HA 故障切换测试——幸好只是测试——系统没能重新上线；复制日志后在自家环境重现、发现该环境需要两小时才能上线；根因并非存不下该站点积累的一千零多万条 job log、而是加载这些日志的启动时间。他们花了三到四个月优化加载路径、增加不锁数据库的修剪策略，最终发现真正的问题不是实体数量、而是冷启动的加载时间——靠改进修剪算法让无用 job 不再滞留并提醒客户修剪、而非靠分库与多线程这类花招，就把该客户推过了一万台〔30:04〕。结课教训是：保护 API 与 CLI 兼容性（五年前版本的命令今天仍可用）；暴露而非用重试掩盖运维缺陷——重试很贵且会掩盖本应修复的问题；以及把不可变性当作超能力、让各站点可被验证地一致或在已知方式上不同〔32:02〕（YouTube EPZ5RMtxKprzY，[925-2042]，L1）
- 〔USENIX ATC '15〕伊利诺伊大学与 IBM Research 的联合工作 Pyro 提出：时空数据的存储与查询不宜靠给 GIS 加全局索引、也不宜靠在大数据系统之上加翻译层，而应让存储系统内部真正理解时空数据、聚合并优化 I/O、并借副本放置策略缓解动态热点〔00:09〕。面向的应用是特殊而重要的一类负载：海量带地理标签的事件被实时产生与存储——推特、Instagram 照片、出租车位置；查询则是在给定地理区域与时间范围内索取事件数据、称为几何查询，例如用户想知道最近发布在自己城市的推文、广告商想知道过去一周到某商场的手机用户〔00:23〕。三个挑战是：如何高效存储与检索时空数据；可扩展性——数据随时间海量累积、必须扩展到大量服务器；以及如何应对动态工作负载热点——时空负载天然带热点，例如独立日烟花结束后数万人同时打车、或早高峰人人查询去市中心最不堵的路径〔01:12〕。已有方案分两类：一类让 GIS 可缩放——用全局索引把空间切成子空间、各子空间由一个 GIS 处理，但 GIS 虽极高效、可扩展性通常不行〔02:01〕；另一类让大数据存储系统理解时空数据与查询——在应用与底层系统之间加翻译层把二者翻译成底层能懂的形态，虽继承了底层系统的可扩展性、翻译层本身却拖累性能〔02:35〕。Pyro 因此是专门面向时空数据与查询的完整方案，三个贡献是内部理解并优化时空数据、聚合优化 I/O 操作、以及管理数据副本以缓解动态热点；它构建在 HBase 之上〔03:11〕。HBase 背景：语义上是带行、列、单元版本的分布式数据库，系统视角则是分布式键值存储、每个键指向一个带版本的单元；表被水平切成多个 region 分布在不同服务器、每个 region 按列族分成多个 store、每个 store 内有 memstore、达到预设阈值后刷盘形成 store file；它通常与 HDFS 共置、NameNode 负责命名空间与文件元信息、DataNode 存实际数据块、客户端暴露 DFS API〔03:42〕。Pyro 增加三个组件：几何翻译器（把时空信息编码成一维行键、并把几何查询翻译成一组范围扫描）、多扫描优化器（聚合优化这些范围扫描的 I/O）、以及基于组的副本放置策略（动态负载变化时改善数据局部性）〔04:59〕。几何翻译器用四叉树递归把空间切成瓦片、再用不同编码算法编码：strip 编码最简单、把 y 追加在 x 之后、类似逐行扫描；Z-order 编码交错 x 与 y 的二进制位作为瓦片索引；Moore 编码（与 Hilbert 编码）在高维数据降维时保留更多数据连续性——二维空间中每个瓦片有四个邻居、Moore 编码保证任一分辨率下任一瓦片的四个邻居中有两个降维后仍是邻居，例如第二行第二列的 3 号瓦片有 0、2、4、十二号四个邻居、其中 2 与 4 在一维中仍与它相邻〔05:38〕。翻译查询时把同一棵四叉树施加到查询上：最高层把空间分为四个象限、只要某象限与查询相交就继续下钻、直到不相交或该象限被完全覆盖，所得瓦片即对应一组范围扫描并交给多扫描优化器〔06:50〕（YouTube EPZ6h0HXzPl-E，[9-441]，L1）
- 〔USENIX ATC '15〕多扫描优化器针对的是作者命名为读放大的现象（沿用写放大的说法）：几何查询翻译出的一组范围扫描会迫使底层系统读更多数据、或反复遍历同一结构〔07:52〕。三种子情形：一是读面积放大——瓦片边界未必与查询边界对齐、同一瓦片内键值对在最粗分辨率上共享同一空间键，要满足请求就得取走整片瓦片的数据〔08:12〕；二是读容量放大——数据被序列化为默认六十四千字节一个的 HBlock、瓦片内键值对边界未必对齐 HBlock 边界，最坏情况取一个瓦片要额外多取两个 HBlock〔09:16〕；三是冗余读——每个 HBlock 内键值对排成一条链、取某个键值对必须每次从头遍历，范围扫描被分别处理时就会重复遍历同一条链〔09:48〕。显然的对策是用更小瓦片与更小 HBlock、代价是查询被翻译成更多更小的范围扫描即更多更小的 I/O 操作、反而伤害性能〔10:29〕。多扫描优化器因此允许更小瓦片与更小 HBlock、并把惩罚通过一起调度 I/O 来抵消：一个含十六个 HBlock 的文件里若只有若干被请求块，一端是逐块单独读、另一端是整文件一次定位读；算法以定位读延迟曲线为输入，例如某机械硬盘在定位读尺寸一百千字节以下时延迟几乎不变、读一个六十四千字节块约九毫秒而读十三个这样的块约二十毫秒，于是干脆对三到十五块发一次定位读；一般情形用作者称的自适应聚合法（动态规划）求解并给出保证调度器最优性的转移函数〔11:04〕。第三组件是基于组的副本放置策略：每个 HBase region 负责一段行键对应空间的一块子区域，而时空应用在很小的区域内制造热点、足以压垮承载该 region 的服务器〔12:37〕。三张热力图——二〇一三年除夕、十小时后、同年七月四日烟花夜的曼哈顿出租车接送点——分布差别明显，说明时空应用确实制造热点且会在很短时间内剧烈变化〔13:03〕。默认 HBase 里 region 过大可分裂成多个子 region 分散到多台物理服务器从而可扩展、但只有负载变化不大时才成立；一旦负载变化分裂反而有害：HDFS 中一个副本放在写节点、另两个被随机散布在全集群，写节点因此是唯一本地持有该 region 全部数据的节点，分裂搬走数据后子 region 便失去数据局部性〔13:56〕。Pyro 的做法是把副本组织成组——同组副本放同一物理服务器、不同组尽力放不同服务器〔14:56〕；示例中一个文件用预分裂键切成四片、每块复制三次，先建含全部键的 group 0、再建含下半键的 group 1、然后建各含四分之一键的 group 2 与 3；最初 region 放在承载 group 0 的服务器上并在组内本地读，此后每次分裂都让子区跟随对应组迁移、四个子区最终分别跟随 group 0、3、1、2、全部享有空间局部性〔15:02〕。组之所以非对称排列是刻意贴合 HFile 格式：文件信息、数据索引、元索引等关键信息位于文件末尾，丢一块元信息块会让整个文件不可用、而丢一块数据块不影响其他部分，故文件末尾放更多组、文件开头放较少组〔16:34〕。评测用纽约地区二〇一〇至二〇一三年七亿条出租车行程的开放数据集、在八十台服务器集群上运行一个 DFS NameNode、三十个 DFS DataNode、一个 HBase Master、三个 ZooKeeper 节点与三十个与 DataNode 共置的 HRegionServer〔18:50〕。对照基线是在应用与 HBase 之间加翻译层、并用 Z-order 编码（转写作 MDHBase）；第一组实验只测基于组的副本放置策略，为公平起见只提交范围扫描而非几何查询、从而关闭几何翻译器与多扫描优化器、两边都用 Z-order，在第两百四十秒手动分裂 region 后基线响应时间略升而 Pyro 从约一百二十毫秒降到约五十五毫秒〔19:41〕；第二组测整体延迟与吞吐：提交一百米乘一百米的矩形几何查询、Pyro 四种配置为 Pyro-M（Moore 编码）、Pyro-Z（Z-order）及分别关闭聚合算法的 Pyro-M-A3 与 Pyro-Z-A3；负载较轻时基线约五百五十毫秒、Pyro-M 降到略高于一百毫秒即约五倍改善；吞吐以八百毫秒为有效响应上限时、基线约每秒两百个几何查询、Pyro-M 提升到约每秒一千个〔20:47〕（YouTube EPZ6h0HXzPl-E，[441-1367]，L1）
