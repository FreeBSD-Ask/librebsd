- 〔HotStorage（推测）〕SSD 老化状态难以到达且缺乏老化工具。主讲人 Zhang Zhe（转写音）指出 SSD 磨损导致的误码率恶化性能，研究磨损需在早期阶段进行，但达到真实磨损态困难、目前没有现成 SSD 老化工具；预处理仅用于准备稳态而非人工老化，直接实盘老化到三年 H 态须先运行三年负载，资源与时间成本极高。其方案是基于机器学习的 SSD 老化框架，通过负载采样生成具有代表性的未来磨损状态；难点在于推理须相对仿真时间足够快且准确，需正确建模内部活动、磨损、误码率之间的正反馈环，为此按块增量构建轻量级回归模型。（YouTube EPFqRzRDK6kIc，[8.7-160.0]，L1）
- 〔HotStorage（推测）〕三阶段生成流程与对比评估。生成过程分三阶段：先对负载样本做实际仿真以观测 SSD 内部活动并收集信息，再用数据构建轻量回归模型预测未来状态，最后把生成的状态回馈仿真继续运行并重复直至达到目标老化程度。在 FTL Sim 配置的 256GB SSD 上运行三种真实负载，与两篇机器学习加速仿真工作 DVS 与 CML 对比：其配置下仿真加速 33%，预测分布紧贴全仿真基线，而 DVS 与 CML 明显偏离；未来工作包括提升 ML 结果可解释性并把框架集成到 Amber 与 FEMU 等更多平台。（YouTube EPFqRzRDK6kIc，[160.0-305.4]，L1）
- 〔SREcon（推测）〕SLX：为加速事故恢复扩展 SLO 框架。主讲人 Chen 与同事 Xuan 均为蚂蚁集团基础设施 SRE，管理 60 余个 Kubernetes 集群及 DNS、网关、Pub/Sub 等服务；事故恢复难在事故定义含糊（客户端报错而本方无告警）、循环依赖导致无法回滚、以及在度量/日志/看板中迷失。跨团队排查（如 Kubernetes 大量 Pod 创建失败涉及 API server、调度器与校验 webhook）带来巨大认知负担，且团队 50 余组件、每组件 5 个关键接口、3 类基础 SLO 与多环境组合使 SLO 数量爆炸，故提出 SLX：新增服务等级因子 SLF（算术上贡献 SLO 计算，可因子化定位最大贡献者）与服务等级依赖 SLD（间接影响 SLO 的信号，通常是下游 SLO），把 SLX 组织为依赖图，用异常检测沿图遍历定位异常因子并聚合出可能根因。（YouTube EPFsy7589uASs，[12.7-717.8]，L1）
- 〔SREcon（推测）〕SLX 的定义、自动化与异常检测实践。核心组件是 SLI：SLO 是带约束的 SLI，复杂 SLI 由两个以上简单 SLI 经聚合器组合（如成功率为错误数与总数两个简单 SLI 之比），支持任意时间窗评估，并可在其上声明 30 天 Pod 创建成功率 SLO 与错误预算耗尽触发告警。自动化上用 Kubernetes operator 模式与 YAML+Git 版本控制，采用两阶段 GitOps（面向初级用户的简化仓库经 CI/CD 渲染为完整 SLX 并提 PR，SLX 仓库再经 Argo CD 同步进集群），控制器生成 Prometheus 记录/告警规则与 Grafana 看板，告警事件推送 AI 系统做异常分析；演进分 L0（无自动化）、L1（辅助定位）到 L2+（自愈）。异常检测实践强调数据质量（Prometheus 空区间需补默认值）、防范维度灾难、算法须简单可解释（如为何用三倍而非四倍标准差）；要点是 SLO 非银弹、规模化靠自动化与标准化、用户体验优先。（YouTube EPFsy7589uASs，[717.8-1820.8]，L1）

- 〔FAST〕硬件辅助单索引 HTAP 存储的动机与现有设计局限。香港中文大学末年博士生 Ke Chenghuang（转写音）介绍 HTAP 需同时服务 OLTP 小随机更新与 OLAP 大规模列扫描，二者对存储格式偏好相反（行存利于更新、列存利于扫描），且实时分析要求数据即时新鲜。现有多索引 HTAP 两类设计各有短板：多索引多存储分离 OLTP/OLAP 引擎、依赖跨域数据迁移，资源消耗大且数据新鲜度差；多索引单存储在主列存上建行式 delta 层，OLAP 需同时访问列存与 delta 层，超内存数据集下性能严重退化。作者转向内置透明压缩的 SSD（计算存储盘 CSD）：其低成本压缩不侵入数据服务关键路径，虚拟化逻辑存储空间支持稀疏数据管理，为重思 HTAP 设计带来机会。（YouTube EPFul9vD6_0TY，[15.9-443.0]，L1）
- 〔FAST〕基于 CSD 的洞察、系统设计与评估。三个洞察：CSD 将写放大与页大小解耦，可把整块单体日志化为每页清除日志（purge logs），不必再靠小页保证 OLTP 最优；列数据按列稀疏管理避免紧密对齐 4KB 块导致的读放大；多版本记录随页分配提供并发能力并简化垃圾回收。据此提出 HSS（硬件辅助单索引存储），组件含混合缓冲池、小全局日志与带每页日志的混合页格式，并设计 major/minor compaction 深化 SSD 队列深度以高带宽摄取更新、混合缓冲池以验证法隔离 OLTP/OLAP 性能。在量产 ScaleFlux CSD（转写 Skyflax）上评估：OLTP 性能可比 MySQL 与 PostgreSQL，OLAP 可比 Parquet 列存基线，对比代表性 HTAP 系统 TiDB 能提供更稳定的即时数据新鲜度且性能相当，并因透明压缩不额外占用物理空间。（YouTube EPFul9vD6_0TY，[443.0-871.6]，L1）

- 〔SREcon（推测）〕利用率与尾延迟的权衡：排队论模拟。主讲人是 Google 悉尼的 SRE（从事 Cloud Datastore/Firestore，此前做内部存储系统），不用公式而用数值模拟理解 p99 尾延迟：用户观察到的延迟=排队时间+服务时间，而高利用率（少买机器省钱）与低尾延迟（体验好）天然矛盾。M/M/1（指数服务时间、均值 5ms）模拟显示：即便完全不排队，p99 服务时间已达 22ms，叠加排队后 p99 观察延迟为 44ms（不等于两个 p99 之和）；即使把算法写成恒定 5ms 服务时间，队列仍会带来 21.5ms 的 p99——显著的尾延迟来自排队效应。他给出可复刻的三步法（记录到达间隔、测/估服务时间、采样跑模拟器，讲义附 Python notebook），并展示利用率从 30% 提到 95% 时分布被急剧拉长、排队效应随利用率超线性增长，60% 以上就对用户很难受。（YouTube EP-cZFyfW9JWk，[6.3-838.9]，L1）
- 〔SREcon（推测）〕多核并行收拢尾延迟与数据驱动的利用率对话。把处理器数从 1 加倍到 16 的模拟表明并行度能显著收拢尾延迟：k=4 时可在 80% 利用率下运行，k=16 时 95% 也没问题；但保护共享数据结构的互斥锁会把队列平移到锁前，并非万能（另引 Amdahl 定律与通用可扩展性定律）。结论部分给出理想对话示范：Joe 拿出到达间隔分布图并以 65% 利用率为省钱目标，Jane 则建议重写核心数据结构为无锁、改用 16 vCPU 大节点并以 80% 利用率运行。三大要点：未测量就别假设排队效应为零、排队效应随利用率超线性增长、提高并行度需要配套的软件工程。（YouTube EP-cZFyfW9JWk，[838.9-1657.3]，L1）
- 〔会议不详〕RPRC：分布式协议实现的运行时精化检查。主讲人 Jing（论文报告）指出分布式协议即便有形式化证明，翻译成实现代码仍会引入 bug：他们调查 ZooKeeper、etcd、Redis Raft 等生产系统，均存在协议实现 bug，导致数据不一致与陈旧读。现有手段要么生成经验证的实现（不适用于已有系统），要么运行时用分布式快照检查安全属性（检查器远程取状态通信开销大、节点崩溃时无法继续检查），而其项目 Ellsberg（RPRC）改为本地检查：每个节点上与系统进程同跑一个检查器实例，不与任何其他节点通信，监控消息轨迹并与协议规约比对，不一致即告警。检查方法是用轨迹中的 in 消息重放执行、验证每条 out 消息是否为协议所允许，面临多线程并发与轨迹持续增长两大挑战。（YouTube EP-dQB2VN1kLc，[16.0-475.7]，L1）
