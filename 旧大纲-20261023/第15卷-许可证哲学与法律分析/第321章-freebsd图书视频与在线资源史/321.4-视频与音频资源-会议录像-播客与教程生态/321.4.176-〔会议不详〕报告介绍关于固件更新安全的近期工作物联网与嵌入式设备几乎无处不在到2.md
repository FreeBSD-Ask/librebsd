- 〔会议不详〕报告介绍关于固件更新安全的近期工作。物联网与嵌入式设备几乎无处不在，到 2025 年嵌入式设备市场规模预计接近一千二百亿美元；固件与软件更新对这些设备至关重要，可修 bug、增强功能、提升安全，但也可能带来风险并在真实世界造成重大损害。两个标志性事件：2020 年披露的 SolarWinds 大规模软件供应链攻击波及美国政府及三万余家公私组织，包括 Microsoft 与 Intel；2024 年 7 月 CrowdStrike 为其传感器软件发布了错误更新，导致约八百五十万台 Windows 系统崩溃，如今被视为 IT 史上最大规模的宕机事件。两起事故同源于一个关键问题：缺乏可靠、安全的更新机制，使恶意或有缺陷的更新得以攻陷庞大网络。类似问题同样威胁摄像头、网络设备、IoT 网关等各类设备；OWASP IoT 项目把缺乏安全更新机制（尤其是设备上缺少固件校验）列入 IoT 前五大安全问题。研究回答两个问题：固件更新机制中有哪些脆弱模式？以及如何有效识别其中的漏洞？为回答前者，收集并分析了约四百份 CVE 报告，基于抽象固件更新模型建立系统化模型；为回答后者，提出新的漏洞检测框架，并用一万两千个固件镜像验证。典型固件更新流程含四阶段：生成、下发、校验、安装。生成阶段由开发者创建固件镜像并分发给服务器及供应链，弱访问控制会导致供应链被攻陷（如 SolarWinds）；下发阶段经 HTTP、蓝牙等接口或协议把镜像送到设备，可能涉及设备用户或维护者，不可靠信道或恶意用户可引入被篡改的固件；校验阶段最关键，用签名、摘要、版本与 USID 检查固件的真实性、完整性、新鲜度与兼容性，缺失或执行不当会导致装上非预期的固件，CVE 分析显示多种最常见漏洞正发生在此阶段；安装阶段仅做简单安全检查后安装并重启，若校验不严，被攻陷的固件就能成功安装。（YouTube EPSrgcOrHbehw，[8-350]，L1）
- 〔会议不详〕CheckUp 框架的设计、实现与评估。分析发现漏洞可出现在更新的任何阶段，但健壮的正式校验机制能缓解来自其他阶段的大部分漏洞，因此研究聚焦校验阶段。CheckUp 的目标是检测固件更新机制中对真实性、完整性、新鲜度与兼容性的缺失或不当校验；核心思路是抽取固件更新过程的程序执行路径，再识别其中的校验步骤链以供进一步检查。设计中有三个主要挑战与对应解法：一是更新相关程序形式多样、难以恢复执行路径，做法是用图表示各类更新相关程序的控制流与跨进程通信，并用后向程序切片从设备重启点回溯到更新触发或固件下发，得到完整的更新执行过程；二是从执行路径上的大量函数中难以识别非正式校验步骤，做法是结合语法、结构与数据流语义特征评估函数相似度来识别校验步骤，通过匹配路径上缺失或不当的步骤定位漏洞并发出告警；三是静态分析会引入假阳性、必须验证，做法是为每个待测固件生成并应用补丁以绕过前置依赖、从而隔离并测试疑似脆弱的校验步骤，再对该打过补丁的固件做仿真，用被操纵的更新固件产出 PoC 证明漏洞存在。数据与结果：收集了 TP-Link、ASUS、Netgear 等多家物联网厂商的 15.7 万固件镜像，数据集开源在 GitHub 供社区复用；在一万两千个固件镜像上运行 CheckUp，告警主要来自各类网络设备与摄像头固件，最常见的问题是脆弱的完整性校验，例如使用 CRC、MD5 等弱算法；其他常见问题包括缺失校验步骤、使用对称数字签名，以及在新鲜度与兼容性校验中频繁使用文件名等未受保护数据来校验版本或设备 ID，改个文件名即可绕过。在 150 个固件镜像上验证告警，真阳率 86%、假阳率 5.3%，并促成了 25 个 CVE 与 1 个 PSV 的获得。总结：研究用 CVE 报告系统化了固件更新流水线的安全风险，CheckUp 通过解析更新路径与检查校验流程有效识别固件更新漏洞，评估结果带来 25 个 CVE ID 与 1 个 PSV ID。（YouTube EPSrgcOrHbehw，[350-700]，L1）
- 〔会议不详〕上海交通大学的 Mo Chixue 报告与 Intel 公司合作的工作：用混合浅页表提升 GPU 虚拟化性能。GPU 如今广泛用于 2D、3D 图形计算、硬件视频编解码与高性能计算，机器学习、分子动力学模拟、媒体转码等计算密集负载正迁入云端，形成 GPU 云新计算范式（如 Amazon EC2 实例），因此高效 GPU 虚拟化方案至关重要。去年 GTC 上 Intel 提出 G-Virt：基于 mediated passthrough 的 Intel GPU 全虚拟化方案，功能完整、性能高、可扩展性好；本报告提出基于 G-Virt 优化的 G-Heavy：实现一种新的 relaxed shadow page table，并配合自适应混合页表影子策略，性能最高为 QEMU 的 13 倍、达到原生性能的 85%。评测基准方面，2D、3D 图形负载用 3DMark 与 PassMark，GPU 负载用 Rodinia 与 Parboil，但作为 GPU 云关键负载的硬件媒体转码没有现成基准，于是自研 G-Media：基于 Intel Media SDK（提供硬件加速 API）封装编码与解码函数，用例按指定线程数与媒体参数运行，结束给出平均 fps 反映转码性能。结果显示，多数用例 G-Virt 与原生性能相近，但线程数越过某阈值后性能下降最多达 93%，这是一个严重的性能问题，被命名为 massive update issue。剖析该问题：对两组用例（每组两个无该问题、一个有该问题）用 Xen trace 记录所有 VM exit 及其原因，画 VM exit 占比直方图可见 EPT violation 占比从约 21% 升到 80%；进一步剖析显示 80% 以上的 EPT violation 由 PT update 引起；对单个出问题用例做十秒窗口统计，有的页表被更新多达 7500 次，散点图表明更新集中在少数“热”页表上，且在短时间（二十微秒）内更新持续作用于同一页表；机制原因是 VM 频繁交换显存页时会大规模修改页表项，造成密集更新，从而使 trap-and-emulation 忙转，开销最高可达 95%。（YouTube EPSuOKaALocAQ，[10-475]，L1）
- 〔会议不详〕relaxed shadow page table、四种自适应混合影子策略与评估结论。G-Virt 把虚拟化施加到 GPU 页表上以实现资源分区与用户空间隔离：shadow page table 为两级结构的全局共享页表，512 个页目录项各指向含 1024 个页表项的页表，全部映射 2 GiB 显存空间；它用 trap-and-emulation 维持一致性——写保护页表，客户页表被修改即触发 page fault 陷入 G-Virt 并更新 shadow page table，这种严格一致的称为 strict shadow page table。为解决 massive update issue，G-Heavy 提出新的 relaxed shadow page table 并与 strict 混合。灵感来自 GPU 编程模型：CPU 与 GPU 通过 ring buffer 加 head、tail 两个寄存器传递命令，CPU 从 tail 到 head 生产命令，GPU 从 head 到 tail 取命令，只有在 CPU 更新 tail 寄存器后 GPU 才会取命令。因此可解除客户页表的写保护，massive update 期间不再陷入与模拟；等 GPU 开始取命令时，由 G-Heavy 重建 shadow page table 以保证一致。重建分四步：更新前为客户页表拍照得到完全副本；解除写保护让客户 VM 大规模修改，快照保持不变；重建时比较当前页表与快照找出改动部分；最后更新 shadow page table 的对应部分使其重新与客户页表一致。混合策略共四种：full relaxed（所有页表都切到 relaxed）、static partial relaxed（挑选 50、100、200、300 个热页表转 relaxed）、dynamic partial relaxed（初始为 strict，页表一旦被修改即切到 relaxed）、dynamic segmented partial relaxed（重建后把页表切回 strict，是动态方案的优化版）。评估在 Intel 第四代 CPU 上完成：full relaxed 显著提升有 massive update 的用例、却使无该问题的用例性能变差；static partial 中放松的页表越多，无该问题用例越差，而有该问题的用例 static 200 表现更好，说明页表覆盖度影响性能；dynamic segmented partial 对无该问题用例表现良好，有该问题的用例可达 G-Virt 的 13 倍、原生性能的 85%，优于 dynamic partial，因此 G-Heavy 最终采用 dynamic segmented partial policy 作为自适应混合页表影子策略。2D、3D 性能在 Linux 与 Windows 上多数与 G-Virt 相当或略好，差距可接受；源码已开源。问答中讨论安全性：解除写保护确实让 VM 可任意修改页表、访问任意内存，重建时会检查修改是否安全，但修改发生到检查之间存在间隙，这恰是性能收益的来源，过于严格则性能变差，属于必须取舍的代价；而该可写页表由软件翻译使用，并非被硬件直接使用。（YouTube EPSuOKaALocAQ，[475-949]，L1）
- 〔会议不详〕CISPA 的 Martin Otto 报告论文《Why Even Mallory Still Loves Android: Revisiting TLS Insecurity in Android Applications》，与 Nicolas Huaman、Sabrina Anft、Jasminia Chang、Michael Backes、Sascha Fahl 合作。Android 应用自定义 TLS 使其易受中间人攻击的研究由来已久；为应对这一状态，新对策被引入，本工作评估其效率与影响：一是网络安全配置 NSC，二是让发起中间人攻击更难的安全默认值，三是 Google Play 拦截包含脆弱证书校验代码的应用。NSC 允许不写代码实现自定义网络行为：允许或禁止明文流量、配置信任锚、实现 pinning。规模调研收集约一百三十万个应用，其中 99212 个使用 NSC，可分析其中 96400 个；采用率统计显示其上升与 Android 9 的强制生效相关，因为该版本默认关闭明文流量。分析 NSC 使用的特性集合也解释了它为何被采用——第一大用途恰恰是重新允许明文流量；对明文流量还做了受影响域名的深入分析。自定义信任锚配置方面发现，超过 8600 个应用重新启用了用户安装 CA 的信任，这削弱了 Android 7 引入的防中间人安全默认值；此外还统计了信任锚分布并分析了自定义信任 CA。使用 pinning 增强安全的应用数量很少，但仍对证书 pin、备用 pin 与 pin 探索做了深入分析。另一个重要发现是参数配置错误会让 NSC 实际不生效，以及所谓含糊的 pinning 配置——在 NSC 里声明了 pinning，却因周边其他设置而在运行时不起作用；根因归于复制粘贴代码示例、文档有限与工具支持不足（工具不会告知开发者其 NSC 配置实际无效）。（YouTube EPSuZEXCIja5E，[8-286]，L1）
- 〔会议不详〕Google Play 保障机制的评估与整体结论。评估 Google Play 保障机制的有效性时，团队构建了多种不安全的自定义 TLS 实现并试图以违反平台政策的方式发布，结果只有两个用例被拒：一个是只在 error handler 中捕获 proceed 的 WebView 客户端，另一个是 acra 库的不安全版本（很可能被上游上报因而被拒），结论是 Play 对危险实现的检测能力有限，目前只拦得住平凡情形。NSC 的影响不分应用人气高低：不仅是冷门应用，百万级甚至亿级用户的应用也在用；对允许 HTTP 的应用做人工分析，发现窃听威胁——明文 HTTP 中确有登录数据与凭证等敏感信息。就生态整体的 TLS 代码安全状态，团队复现了 2012 年关于 TLS 灾难性现状的研究并得到同样结果：约三分之一被分析应用含不安全 TLS 代码，与 2012 年工作及 Play 保障研究的结果一致。结论是：自定义仍然有害；新的安全默认值整体提升了安全、缩小了中间人攻击面；但 NSC 主要被用来削弱这些安全默认值。NSC 很少被用于增强安全（pinning 仅见 663 例）；保障机制仍不足以强制执行任何策略来避免常见的不安全证书校验陷阱；自定义也容易出错，即使开发者意图是增强应用安全，也可能适得其反——源于理解不足、复制粘贴与工具支持有限。建议改进代码与工具文档，并加强对 Web 应用的保障措施。（YouTube EPSuZEXCIja5E，[286-572]，L1）
- 〔USENIX ATC〕数据中心的高精度延迟型拥塞反馈。KAIST 的 Changyong Lee（与 KAIST 的 Changjong Park、Soo Min、Dongsoo Han 及 Intel Labs 的 Kun Zhang 合作）指出拥塞控制的性能从根本上取决于拥塞反馈的质量，而 ECN 与 DCTCP 只能给出“队列是否越过阈值”的粗粒度信息（靠窗口内被标记包比例估拥塞概率）、定制网内反馈又难部署，因此重提 TCP Vegas 一系的延迟反馈；数据中心瓶颈链路通常达 10 Gbps（广域网往往只有 100 Mbps 甚至更低）、1 个 MTU 包的传输延迟仅约 1.2 µs，而背靠背两台机器、完全没有拥塞时内核测得的 RTT 仍从 20 µs 漂到 700 µs（相当于约 600 个包的失真），误差源包括端到端协议栈抖动（内核打时标含包输入/输出 I/O、协议栈处理与中断处理）与 I/O 批处理造成的突发时间戳。对策是用 SoftNIC（Intel 基于 DPDK 的包处理平台）做驱动级打时标、Mellanox ConnectX-3 网卡硬件打时标，接收端同样打时标以便从四个时间戳中剥离内核延迟，打时标前按链路速率对包做 pacing，并对网卡在 DMA 完成后才打时标的问题按传输延迟校准，最终把 RTT 标准差从内核的约 80 µs 降到纯软件的约 2 µs、硬件的约 500 ns。（YouTube EPSukd0N5ffc8，[11-860]，L1）
- 〔USENIX ATC〕DX 拥塞控制算法与实测评估。以排队延迟（当前 RTT 减去无拥塞基线 RTT）作为拥塞信号：用一台发送方以 1 Gbps 打满链路制造基线、另一台每 25 ms 发 ping 引入拥塞，测得的排队延迟与交换机真实队列长度逐点吻合（增量为 1 个 MTU 即 12 µs）；论文提出的 DX 目标是在最大化利用链路的同时把排队延迟降到最小，采用 AIMD 规则——AI 部分每 RTT 增加 1 个包、MD 部分按排队延迟成比例减窗，并引入归一化参数 v 计算“刚好打满链路又不排队”的窗口，靠“其他发送方窗口与自身相同”这一简化假设仅凭链路容量、RTT 与当前窗口即可求解。实现上打时标模块放在 SoftNIC，DX 在内核 TCP ACK 函数里只增加约 200 行代码并用 TCP option 头携带时间戳；测试床中 1 G 时仅用纯软打时标即可把中位排队延迟降到 DCTCP 的约 1/5.3，10 G 再加硬件打时标后比 DCTCP 快约 1.5 倍；NS-2 上以三层 fat-tree 与生产数据中心负载仿真，0–10 KB 小流的 p99 流完成时间好约 6 倍、平均快约 2.6 倍，而大于 10 MB 的大流因偶发利用率下降略慢于 DCTCP。（YouTube EPSukd0N5ffc8，[860-1535]，L1）
