# 321.4.160 〔会议不详〕检测控制程序中对输入绝对相对时序的依赖所引发的缺陷主讲人UIUC导师

- 〔会议不详〕检测控制程序中对输入绝对/相对时序的依赖所引发的缺陷。主讲人（UIUC 导师 Matt Caesar 指导，与 MSR 的 Rutul Mahajan、Madan Musuvathi 合作）以家庭自动化与软件定义网络为对象：集中控制器上的事件驱动脚本管理锁、灯、转发规则等，若规则配置错误（灯在错误时间开关、路由黑洞）会造成安全或财产风险；无时间概念的模型检查不足，因为事件域大（光照温度等环境因素组合爆炸）且时间连续、粒度难定。方案是用符号执行把输入空间划为等价类，每类只试一次转移，再借实时系统验证中的时间自动机理论：给状态机加实值时钟，用时钟约束把时间划成有限等价区域，以 delay 转移显式推进时钟、转移时复位时钟。（YouTube EPN1TTMP-X1ZU，[10.1-685.9]，L1）
- 〔会议不详〕工具 Delorean 用 C# 实现，含针对 ISY 与 Elk 两种家庭自动化语言的翻译器，把时间操作改写为虚拟时钟后用 MSR 的 Pex 符号执行提取时钟约束、环境因素与独立控制环，再做时间自动机模型检查输出违例路径。三项优化：按“时钟人格”（对全部时钟约束等价的取值）记忆化并直接预测后继状态（免序列化/反序列化）；合并虚拟时钟（动作+睡眠序列、日落类时刻表可用单时钟加程序变量模拟）；用污点跟踪切分独立控制环。在 10 个真实家庭脚本（至多 50 设备、90 条规则）上发现 4 个缺陷（3 个与时序相关），探索速度可快于实时；SDN 应用上与无时间模型检查器 NICE 对比，时序依赖越重的应用代码覆盖提升越大。（YouTube EPN1TTMP-X1ZU，[687.1-1373.5]，L1）
- 〔会议不详〕用计算缓存扩展 Open vSwitch 的包分类。来自 Technion 的 Alon Rashelbach（与 Ori Rottenstreich、Mark Silberstein 合作）展示 OVS 在 1K 至 50 万条规则下吞吐从数 Mpps 跌至数 Kpps：megaflow 缓存与 upcall 机制都是瓶颈。方案是用神经网络逐包分类替换数据路径分类——基于团队 SIGCOMM 2020 的 NeuMatch（RQ-RMI 架构：大量小型浅层网络，单核推理约 40 纳秒，50 万条规则无吞吐退化），可获最高 12 倍加速；但 NeuMatch 训练慢（10 万条/秒更新率的应用下需 5-20 分钟），慢三个数量级，无法直接集成进数据路径。（YouTube EPN6hub91dAsI，[12.7-421.2]，L1）
- 〔会议不详〕提出 NeuMatch-Up：三项正交改进——范围分桶（每桶 48 个范围即训练提速 7 倍且查询性能不变）、高效 SIMD 实现（替代 TensorFlow+C，几何均值 20 倍）与优化采样，合计训练快三个数量级。两个集成设计进入 OVS-DPDK 数据路径：作为附加缓存层匹配 megaflow（改动小但仍保留 upcall，1K 规则下仅 1.6-1.7 倍）；或完全替换数据路径机制、直接对 OpenFlow 规则分类并消灭 upcall（50 万规则下最高 160 倍、1K 规则下最高 7 倍，随核数线性扩展直至 10G NIC 饱和）。评测用 ClassBench 规则集与带时序局部性的 CAIDA 流量、限最大 1% 丢包；可部署于商用 CPU，后续方向为 P4 与硬件加速。（YouTube EPN6hub91dAsI，[421.4-847.7]，L1）
- 〔会议不详〕Zip 解析器之间的语义鸿沟：同一个 zip 文件在不同解析器下解出不同内容。清华大学的 Yu Fan Yao 展示差分解析工具 ZipDiff：每轮对语料中 zip 文件施加步级与批级变异后喂给所有被测解析器，以输出哈希对比发现不一致并用 UCB 算法平衡探索与利用、引导后续变异。对 19 种语言编写的 50 个常见 zip 解析器（含 WinRAR、7-Zip、libzip）评测：1225 对解析器中仅 4 对一致——不一致是常态而非例外；且判定标准严格（一方报错仍算一致，仅双方都成功解出同一部分而内容不同才算不一致）。归纳出三类共 14 种解析歧义：冗余元数据（文件名/大小多处记录）、路径处理差异（规范化方式）、zip 基本结构分歧（如中央目录位置）。（YouTube EPN9Q6f_H0j80，[10.9-351.2]，L1）
- 〔会议不详〕语义鸿沟的真实利用与披露。场景一：绕过 10 家邮件服务商的杀毒网关（如 Gmail 的“scanned by Gmail”）——网关只能扫压缩包内内容、无法接触宿主机解压结果；场景二：办公文档内容欺骗，docx/java 包/扩展包本质都是 zip——同一文档骗过查重器却在导师的 Word 里显示抄袭内容，还可在 LibreOffice 中伪造数字签名（校验器验原文、渲染器显篡改文）；场景三：Spring Boot 嵌套 JAR 用 Java 内建签名校验器加自研 ZIP 读取器，可构造绕过签名校验的恶意嵌套 JAR；场景四：利用 zip 歧义伪造 VS Code 扩展包身份（上传时 marketplace 看到攻击者命名空间、客户端装出被覆盖的合法扩展名）。已负责任披露，获 Google、Coremail、Zoho 赏金并产生多个 CVE；结论是“别再宽容地接受输入”，应强制严格格式校验。（YouTube EPN9Q6f_H0j80，[352.0-706.2]，L1）
- 〔会议不详〕SGX-Log：在宿主应用与 enclave 之间建立双向信任。浙江大学的 Yuan Chen（与佛罗里达州立大学、香港城市大学合作）指出 SGX 假设 enclave 可信、宿主不可信，但在第三方 enclave 等场景中二者实则互不信任，该假设引出“enclave-宿主不对称”：控制流不对称（enclave 可跳到宿主任意位置，宿主只能经少数入口进入）与数据访问不对称（enclave 可直读宿主内存，宿主因硬件隔离读不到 enclave）。SGX-Log 的对策：利用 Intel SDM 中“enclave 内整个执行被视为单条指令”的特性，进入前开启单步模式、退出时触发单步异常以校验跳转目标；数据面用 Intel MPK 内存保护键，为 enclave 与宿主分别分配键 E/H，参数缓冲区挂 E 键，进出 enclave 时摘除/恢复 H 权限，把 enclave 对宿主内存的访问限制在参数缓冲区。（YouTube EPNAAHm8e_8d0，[8.0-312.6]，L1）
- 〔会议不详〕加固与评测：挑战一是阻止 enclave 内更新 PKRU 寄存器——封堵 XRSTOR（关闭 XSAVE 特性掩码对应位）并以静态+动态二进制检查拦截 WRPKRU（静态在 enclave 创建时检查明文代码，动态由 W^X 权限违例触发、靠 enclave 内嵌代码完成检查）；挑战二是防止 enclave 操纵宿主栈指针，用基于密钥的宿主栈完整性检查。原型基于 Intel SGX SDK for Linux、在同时支持 SGX 与 MPK 的平台评测：宏基准显示进出 enclave 的 ocall 延迟开销较高，但 enclave 内外执行零开销；机器学习推理服务、数据库操作与 HTTP Web 服务器三个微基准场景即使高频 ocall 也保持高效。结论：对宿主的盲目信任引入 enclave-宿主不对称，SGX-Log 能有效约束不可信 enclave。（YouTube EPNAAHm8e_8d0，[313.2-627.8]，L1）
- 〔会议不详〕二进制代码中私有（proprietary）密码学原语的自动识别与分类。主讲人 Jos Wetzels（与 Carla Maier 等合作）指出私有密码学在嵌入式系统中长期存在，且常受 NDA 或禁令约束，阻碍安全评估、认证与采购。理想方案需满足三条件：能识别未知算法（属于已知类别但细节未知的变体）、在真实二进制上高效、不依赖固件仿真或动态插桩；而既有工作——专用密码 API/库/常量签名、位运算指令比例启发式、深度学习、污点+熵的数据流分析、直至 DFG 图同构（Ullmann 子图同构，最强基线但无法系统处理数据依赖分支，如流密码由长度参数驱动的循环）——均不满足。其观察是绝大多数私有密码仍属既有原语类别（Feistel 网络、SPN、LFSR 等），故构建覆盖整个分类学类别的结构签名，把 DFG 同构与符号执行结合，配套定义结构属性的 DSL，并提供免费开源实现。（YouTube EPNAN8oERHjV4，[8.3-399.9]，L1）
- 〔会议不详〕流水线与评测：给定函数入口增量构建 DFG（按操作数类型定节点），经操作化简、公共子表达式消除、内存访问操作数替换与结合性合并归一化为规范形；对欠定条件用“路径预言机”——首次相遇取真假两路，其后复放导致重访的决策直至第 N 次再取反路，从而得到 0 次与 N 次迭代的 DFG（N=4 足够）；剪除无返回值/调用/非栈存储的叶子节点至不动点后，用 Ullmann 子图同构比对签名（既有算法特定签名如 AES、MD5，也有 Feistel、LFSR 等通用签名）。在 Ryzen 3600 上对既有工作测试集全部正确识别且无需代码片段选择启发式；OpenWRT 与公开私有密码实现用通用签名识别出几乎全部原语；真实 PLC/ECU 固件中除一处因依赖隐式数据流而失败的用例外全部识别。（YouTube EPNAN8oERHjV4，[400.5-775.1]，L1）
- 〔会议不详〕自动发现由 CPU 异常引发的信息泄漏。阿姆斯特丹自由大学的 Emanuele Vannacci（与 Microsoft Azure Research 合作）在 4 颗 CPU 上测试 13 种异常变体，确认并佐证了既有发现、找到新泄漏并获得一个 CVE，同时给出异常泄漏的首批形式化描述。框架基于契约式安全推测：测试用例生成器产出随机程序与输入，分别在真实 CPU 与契约的可执行模型上运行并比对轨迹，CPU 泄漏超出契约允许即构成违例。测试异常的难点在于需要一致的确定性环境（在模型与 CPU 上对齐地触发异常）、掌控执行流以回收轨迹，以及把微架构行为形式化为契约。共跑 124 次、每次 24 小时（或直到违例）的 fuzzing 战役，聚焦同步异常（内存错误、计算错误、代码型错误），契约族从最严格的无暂态执行，逐步放宽到乱序执行、值推测（float 异常值/零注入等变体）与“暂态值依赖架构状态”。（YouTube EPNAiED1mxVNs，[8.3-333.9]，L1）
- 〔会议不详〕评测发现部分异常是串行化事件、不开启推测，并复现了既有报告的值推测（L1 缓存与各微架构缓冲区转发）。关键新泄漏是影响 AMD Zen+ 的 divider state sampling：除零异常后 RDX 中并非模型假设的零，逐条假设检验（为零、依赖故障指令源操作数、MDS 式架构状态任意值）后发现泄漏内容取决于更早那条除法指令的操作数，破坏机密性；违例报告显示契约轨迹一致而地址轨迹不同，说明模型低估了泄漏。相应讨论已在 Linux 社区展开、补丁已合入。（YouTube EPNAiED1mxVNs，[335.0-669.3]，L1）
- 〔NSDI（推测）〕数据中心拥塞控制算法 Poseidon（与 Google 合作）。来自 Rice 的主讲人（音 Wei Tao）提出好 CC 的三要求：高效（高利用率、低延迟、快收敛）、最大流量（多跳拥塞等角落场景下更稳健）、可落地（低开销、支持增量部署）。既有 CC 的三个盲区：对路径上每一跳拥塞都反应导致多跳场景无法达到最大公平——受害流跨两条饱和链路，Google 生产算法 Swift、以及 HPCC、DCTCP 的吞吐都远低于理论公平份额；流在到达公平份额前就被迫降速、靠 MD/AI 反复拉锯才收敛；AI/MD 使用同一调节步长，无法兼顾快速收敛与稳定（小流窗口已为 1 时每步 AI 使速率翻倍、引发剧烈震荡）。根因在于把拥塞信号当二进制，而带内遥测可提供定量信号、只对瓶颈跳反应。（YouTube EPNBGJo9axB8w，[12.7-414.7]，L1）
- 〔NSDI（推测）〕Poseidon 设计与结果：每包固定 2 字节携带最大单跳延迟 MPD、沿转发路径收集并经 ACK 反馈，开销极低；用速率自适应目标函数 MPT（随流速率单调递减）把公平性与 AIMD 解耦——同链路上的快慢流观察到相同延迟却因目标不同而一个增一个减；更新函数为无 AI 项的自适应 MIMD，按目标与延迟之差定更新比例，并用“更公平三角区”给出单跳公平性证明（适用一类函数而非单一函数），在多跳场景中因目标函数单调递减、最大延迟总出现在瓶颈跳，故只对瓶颈拥塞反应、论文证明可达最大公平。实现上仅需 2 行 P4 代码即可提供 INT 信号；评测：收敛快 12 倍、收敛后稳定吞吐提升 24 倍（更新比例恒为 1.0、速率线笔直）、命中理论公平份额，且支持增量部署（支持 INT 的交换机越多性能越好）；算法已在 ns-3 上开源。（YouTube EPNBGJo9axB8w，[417.1-837.2]，L1）
- 〔SREcon（推测）〕Intercom 生产 SSH 访问管理的动机与旧方案痛点，以及 SSH 证书基础。主讲人 Niall Sheridan 来自 Intercom（都柏林）生产系统团队、此前任 Google SRE 约十年，援引 NIST 2015 年报告指出多数组织连拥有多少 SSH 密钥、谁持有副本都不清楚，密钥长期累积、无轮换且被 GitHub 搜索一抓一大把；Intercom 旧方案把 authorized_keys 烘焙进不可变镜像、以员工 GitHub 资料为事实来源，靠重建镜像分发，规模变大后难以为继，改用持续同步工具后仍缺私钥保障，撤销耗时分钟到小时且无 SLO；随后介绍 OpenSSH 约七年前加入的 SSH 证书（非 X.509）：只需向实例分发 CA 公钥，证书可内嵌有效期、principals、来源地址与端口转发限制，服务器端以 TrustedUserCAKeys 与 authorized_principals 文件启用，Intercom 预置约五个 CA 公钥以便换钥不必全基础设施同步。（YouTube EPNCEQj27A3XA，[10.4-818.9]，L1）
- 〔SREcon（推测）〕Cashier 证书授权中心的落地、运维问答与路线图。采用证书后密钥管理归一为唯一一个由管理员掌控的签名密钥；Intercom 构建经 Google OAuth 认证的 CA“Cashier”，用户在终端发起、浏览器登录 Google 后换取令牌，客户端在内存中生成 SSH 密钥对交 CA 签发证书，仅存于 SSH agent、不落盘，证书有效期 20 小时，配合短有效期与 CRL 撤销，把漫游密钥从数百降到约 30 个且日志可见何人何时用何钥；Q&A 披露 CRL 每 4-5 分钟加抖动刷新、CA 运行在独立 AWS 账户的小型 EC2 上并从 KMS 加载私钥（作者家里用树莓派也能跑），路线图包括新机器自动签发主机证书与快速撤销整个 CA，撤销后现靠重启堡垒机杀会话。（YouTube EPNCEQj27A3XA，[826.9-1448.7]，L1）
