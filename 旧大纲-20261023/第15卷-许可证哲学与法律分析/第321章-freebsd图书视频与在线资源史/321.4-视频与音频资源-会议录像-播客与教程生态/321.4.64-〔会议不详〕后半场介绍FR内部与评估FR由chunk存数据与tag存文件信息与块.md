# 321.4.64 〔会议不详〕后半场介绍FR内部与评估FR由chunk存数据与tag存文件信息与块

- 〔会议不详〕后半场介绍 FR 内部与评估：FR 由 chunk（存数据）与 tag（存文件信息与块状态）连续组合而成，tag 的主键 key 与状态标志（valid/new 位）构成两路结构便于更新操作；静态分配虽有冲突风险但商用 PM 容量足以容纳应用工作集，并以 stride（文件块错位摆放减少侵入）与周期性后台冲刷（清理后无冲突惩罚）两项技术减少冲突，一致性协议同样全程采用静态机制。评估以 ext4+FR（FRX，X 为冲刷周期值）对比 ext4、DMWC、DAX 与 NOVA，Filebench 与 RocksDB YCSB 在 SATA SSD 后备下显示 fsync 密集负载中 FR 显著快于 ext4 与 DMWC、接近 NOVA；针对标准负载无法反映真实动态性的问题，用 FIO 生成 21 个文件共 154GB 数据集构造动态工作负载（FIO6/FIO12，总 I/O 575GB），FR 提供超过 9 倍聚合吞吐、比 ext4 快 3 倍以上，且同时保证保序语义。（YouTube EP9owL-fc_Mbs，[357-896]，L1）
- 〔会议不详〕主讲人报告 IRHash——基于 LLVM IR 的通用编译缓存（合作者 Johannes Christian 与 Daniel，音），围绕编译等待的浪费讨论编译缓存的最优抽象层。ccache 对翻译单元源码哈希、增量构建提速约 10%，但对格式与空白敏感、未使用代码的改动也触发重编译且基本只支持 C/C++；同事在 USENIX ATC'17 提出的 CHash 哈希 AST 更精确（提速 16%）但实现复杂且 C 专用。以 Clang 编译 OpenSSL 的单翻译单元约 70ms 耗时分解（解析成 AST 约 31ms、优化昂贵）为依据，团队选择在 IR 生成后建缓存：IR 足够早可跳过优化阶段、足够接近最终结果故精度高，且对格式、未用代码与语法糖不敏感，多种语言前端共享 LLVM IR 意味着 C、C++、Fortran、Haskell、Rust、Swift 等语言可免费获得支持。（YouTube EP9r72Pu0AVMU，[18-487]，L1）
- 〔会议不详〕后半场介绍 IRHash 的实现与评估：以不足 600 行的 LLVM pass 实现（约 200 行为缓存逻辑），自顶向下哈希 IR 的函数、基本块、指令与操作数并对复杂类型递归哈希，在 120 万个翻译单元上验证正确性。对 16 个开源项目、4 种语言（C 如 Linux、OpenSSH、SQLite、PostgreSQL、Python 等，C++ 如 Boost、Asio、Clang 等，Fortran 的 LAPACK 与 Haskell 的 ShellCheck）各取 100 个 commit 模拟变更，在 12 核 i7（32GB 内存、关闭睿频防热降频）上评估耗时一周余。结果：IRHash 相对无缓存减少 12-53% 编译时间，相对 ccache 再省 5-30% 且总是更快；以目标文件哈希为真值时精度接近 100%（与 CHash 接近），哈希开销稳定低于 1%、比 CHash 低约两个数量级，得益于 IR 数据结构线性化、无 AST 交叉链接；工件已公开可复现。（YouTube EP9r72Pu0AVMU，[487-937]，L1）
- 〔会议不详〕特伦托大学博士生 Michele Gisafi（音）报告 PISTIS——面向低端嵌入式系统的可信计算架构（与 Mahmoud Ammar（音）、Marco Roveri、Bruno Crispo 合作）。远程证明等安全服务通常依赖可信执行环境，而遗留或廉价设备没有 MPU/MMU 也无法承受硬件改造，落在硬件方案与软件方案之间的安全鸿沟中；PISTIS 以纯软件 TEE 填补该缺口，提供中断、DMA 与可信应用（含安全代码更新与远程证明）支持，威胁模型为不可信方编程的 MCU 遭受网络攻击（DoS 不在范围内），其核心是策略化的内存隔离原语，把恶意代码与 TEE 及其应用隔离以保证远程证明不受干扰，流程分划分内存区域、按段部署与运行时强制访问控制策略三步。（YouTube EP9srZgv2drHs，[24-391]，L1）
- 〔会议不详〕后半场讲解纯软件强制机制与评估：通过插桩与虚拟化保证应用二进制中每条指令符合访问控制策略，自定义工具链把不安全指令（如调用寄存器 R10 中的地址）替换为安全替代——先将 R10 存入安全寄存器再经虚函数调用交由 PISTIS 运行时检查；部署前先做二进制验证以抵御绕过插桩的更强攻击者，运行时虚调用内再做安全检查，机制同样覆盖 DMA 与中断操作。在 TI MSP430 微控制器上以 13 个嵌入式应用（含 TI 官方基准）评估内存占用、运行时开销与部署时间三项指标，开销虽高但对嵌入式场景（大量时间用于传感与高延迟网络收发）可接受，且借助优化二进制格式把部署时间开销降低 73%，代码已开源在 GitHub。（YouTube EP9srZgv2drHs，[396-722]，L1）
- 〔会议不详〕把代码隔离成本纳入云端计算与请求调度（Meghna Gupta，University of Utah）：百吉比特网络与 RDMA 等内核旁路技术让云上 VM 能以微秒级往返延迟每秒处理百万级请求，Spectre、Meltdown、L1TF 之外 WebAssembly、eBPF 等轻量隔离方案快速演进，无服务器编程模型又把应用推向细粒度分解，三者叠加要求彻底重思云端调度。作者主张以函数粒度显式计入数据移动与代码隔离成本来放置和隔离计算，并随微秒级负载变化自适应调整。存储与计算分离虽解决资源搁浅，却引入 RPC、内存拷贝、传输与序列化开销，而密集存放数千租户数据又使在存储服务上托管计算受限，短函数的隔离与调度开销会累积，形成云厂商映射租户到存储方式上的核心张力；实现隔离成本感知调度需要应用画像、隔离方案成本与行为漂移检测等细粒度可见性，作者在自研存储服务器原型上展示了这一效应。（YouTube EP9t8h47G5G24，[9.0-483.0]，L1）
- 〔会议不详〕后半场给出设计证据与仿真：存储服务器原型显示只访问单条记录的函数在存储服务器外用一次 get RPC 计算最快，访问两条以上记录的函数在服务器上运行反而更快，可用本地数据访问量与完成工作量之比做自适应函数放置。隔离方案上，VM 每整核独占配 SR-IOV 硬件队列支持每秒百万请求但共享 CPU 代价高，轻量语言运行时适合短函数；以三种硬件隔离方案成本校准的仿真显示进程/页表切换始终拖累吞吐，EPT 切换在数千租户时最优，MPK 在数十到数百租户时成本最低，故应按租户数量与请求率混用方案。其新 serverless 平台设计采用 DPDK 风格低开销负载均衡器（每秒数千万次函数调用、数十微秒内路由并感知租户数据位置）、CPU 核间工作窃取，并用 RDMA 写以至少每毫秒一次的频率把函数执行信息推送给负载均衡器；开放问题包括 serverless 编程模型演化、多种隔离方案放大的攻击面（如经验证的 eBPF JIT 能否用于隔离短函数）与效率节省如何传递给租户。（YouTube EP9t8h47G5G24，[484.9-992.3]，L1）
- 〔会议不详〕AutoRL：基于多目标强化学习的星地融合网络自适应拥塞控制（Xu Li，上海交通大学）。固定偏好只能在特定网络中表现好：低时延权重在短肥管道网络因饱和缓冲对总奖励惩罚低而丢包率高，高时延权重在长时延卫星链路对时延波动过敏、收敛慢（示例中两种模型分别约 25 秒与 15 秒才收敛）。AutoRL 不求单一偏好的最优结果，而由多目标（MOL）智能体逼近整个帕累托最优前沿、为所有可能偏好生成最优策略，偏好自适应模型以状态序列识别环境并自动设定偏好，从而兼顾时延敏感（在线会议）与吞吐敏感（文件同步）等多样化应用。建模上用相对值刻画异构网络状态、按观测 RTT 自适应调整监测区间长度、把延迟动作现象纳入状态（状态含网络统计历史与动作），奖励为吞吐与负 RTT 组成的向量；训练采用异步优势执行者-评论者（A3C）框架，并对非光滑损失采用同伦优化（构造光滑辅助损失再渐变转移）。（YouTube EP9ypIcsVMCek，[8.6-372.9]，L1）
- 〔会议不详〕偏好自适应模型训练与评估：缓冲饱和时智能体只能观察到同样差的奖励、易在探索阶段陷入收敛态（草堆寻针问题），作者提出早停技巧——训练初期缩短步长并随回合序号线性增长。偏好模型训练用专家策略（尽快把场景转至可用带宽）与 KL 散度衡量策略相似性，为每个训练环境挑选最合适偏好构造数据集并做监督学习。在 Pasea 与 Beholder 两个网络仿真平台对比 CUBIC、Vegas、PCC、BBR2 等：输入不同偏好可得一系列帕累托最优结果，卫星网络中丢包率比可比吞吐的基线低约 79% 与 86%；在每 5 秒于 2-10 Mbps 均匀变化的链路上平均吞吐最高，时延比可比吞吐方法缩短约 25%/97%/75%；面对超出训练范围（0-5%）的 8% 随机丢包仍达约 88% 链路利用率；Dumbbell 公平性实验表明总能找到合适偏好使两条流共享链路时吞吐相当。（YouTube EP9ypIcsVMCek，[373.5-775.4]，L1）
- 〔会议不详〕Marvin：通过运行时与操作系统协同设计改进移动内存管理（University of Washington 与 Microsoft Research 合作，讲者为 UW 研究生）。Android/iOS 给每个应用固定内存预算、内存耗尽即整杀应用，即使工作集远小于足迹也如此，重启应用耗时且开发者被迫压缩内存占用；传统交换对 Java 类托管语言不适：GC 追指针会把换出页换回、工作集估计被干扰、页粒度无法区分页内冷热对象；Android 开启 Linux swap 后内存压力下分配 500MB 接近 8 秒，远超可接受延迟。Marvin 与 Android Java 运行时协同设计重新引入交换，三大特性是提前把未用内存检查点落盘（ahead-of-time swap）加速分配、以对象而非页粒度做工作集估计与交换、以及可视为 PLDI 2005 bookmarking GC 改造版的 swap-aware GC；底层机制为 stubs（Java 堆内小伪对象间接层）、共享内存回收表（reclamation table，存对象位置、大小与锁定元数据位）与对象访问插桩（解释器与 ARM64 编译器成对修改，透明执行恢复、更新工作集等动作）。（YouTube EPA0ANld6It9c，[8.9-518.5]，L1）
- 〔会议不详〕机制实现与评估：对象头脏位支持后台检查点、按轮次以短/长期访问元数据（移位寄存器借助 GC 堆遍历更新）跟踪对象级工作集、swap-aware GC 直接从 stub 读取引用而无需换回底层对象。实现在修改版 ART 运行时上完成，默认把前台应用对象留在内存以免 UI 线程发生交换。在 Pixel XL（Android 7.1.1 及其修改版）上评估：Marvin 可同时运行约两倍于原版 Android 的活跃应用（开启 Linux swap 的 Android 应用会因交换抖动冻结甚至崩溃）；回收 500MB 只需约 100 毫秒，远快于内存压力下近 8 秒的分配；PCMark for Android 中测 Java 代码的基准得分与原版相差 15% 以内。相关工作 Acclaim、SmartSwap、A2S、MARS 均在内核层交换，Marvin 则在运行时层完成交换；源代码已在 GitHub 开源。（YouTube EPA0ANld6It9c，[522.4-1068.7]，L1）
- 〔会议不详〕FineMM：细粒度分离内存管理中打破分配开销与内存浪费的两难（Xiao Yang Wang，中国科学技术大学）。RDMA 远程内存分配需在内存节点 CPU 上做内存区注册（注册 1GB MR 可超过 100 毫秒），RPC 式分配又受限于内存节点算力：按需注册吞吐仅为预注册内存区的 20%，即使无需运行时注册也在 32 客户端后吞吐饱和。粗粒度（MB-GB 级）分配省开销但内存浪费大，DM KV store 中 4KB 粒度的碎片远少于 2MB 与 1GB 粒度。设计一：预注册整个远端内存为全局内存区，用 RDMA 内存窗口以每微秒一个的速率生成细粒度 RKey 实现用户间隔离，并由每核 worker 的可信分配服务代用户做单边分配以保护分配元数据不被用户直接访问。（YouTube EPA33Z60-31cg，[17.5-555.0]，L1）
- 〔会议不详〕单边 RDMA 两层位图与崩溃一致性及评估：section/span/chunk 两层位图（每 span 含 32 个连续 chunk 及 32 位空闲图、span 用 2 位状态含争用态）让 FineMM 至多两次 RDMA 请求即可搜索并分配最多 500 个 chunk（对比 2MB 大分配按逐条比较交换约需 500 次）。内存节点上由计算节点经单边 RDMA 写入 redo 日志跟踪 chunk 归属，另加 32 位临时日志区分瞬态与已提交状态、强制在下一次分配前刷入持久日志，并以时间戳检测过期条目，保证计算节点故障后可回收未用内存。在 16 计算节点、至多 6 内存节点的云实验室集群评估：4KB 到 2MB 各分配粒度上均优于现有方案，分配时延最多降低 90%、仅引入 10-20 微秒额外外部时延；集成到 DM KV store 使带宽提升最多 100% 且内存成本降约 40%；集成到基于 Fasa swap 的 DM swap 系统后内存利用率提升至约 70%、作业吞吐增约 8%。（YouTube EPA33Z60-31cg，[556.0-1109.5]，L1）
- 〔会议不详〕MongoDB 查询加密（QE）的独立安全分析（Tianxin，ETH Zurich 应用密码组）。QE 于 2022 年 6 月推出，是首个在广泛部署数据库中可用的可搜索加密技术，MongoDB 宣称敏感数据在传输、静态、内存、日志与备份中均安全；作为第五大数据库厂商（超 43,000 家商业客户），其安全声明影响深远。作者通过逆向公开代码库厘清内部机制：QE 维护新的加密搜索索引 ESC，字典键为域值 PRF 输出拼接文档计数器、值域为加密的文档计数器，文档检索用 PRF 于计数器实现等值搜索；为避免索引随插入线性膨胀，引入压缩（compaction）过程，压缩后每个可搜索域只保留最大计数器、其余计数可由其恢复。（YouTube EPA3Kw3qhN3OI，[8.4-376.4]，L1）
- 〔会议不详〕从 oplog 泄漏到查询重建：插入时递增计数器使同一域值的检索 PRF 输出各不相同，提供快照安全性；但 QE 的 29 个处理器中 24 个用原生 MongoDB 库处理器实现，与缓存、日志、备份等系统组件交互，oplog（复制集保持同步的写操作日志）中记录了与查询操作相关的信息。按事务 ID 分组日志事务可判断哪些加密文档共享同一域值，对应频率与相关性泄漏；作者基于 Grubbs 等针对关系数据库的攻击技术改进，用 2012 年美国社区调查个体级微观数据作辅助信息恢复 2013 年数据，虽 oplog 比查询日志更噪仍获较高恢复率。oplog 位于服务器文件系统上、快照攻击者易得，且 MongoDB 建议搜索索引超 1GB 即运行压缩（实验中约 65 万条文档即达阈值）；结论是可搜索加密不能视为独立实体，需考虑与其他系统组件的交互，且设计者与实现者间存在沟通鸿沟。（YouTube EPA3Kw3qhN3OI，[377.2-761.1]，L1）
