# 321.4.190 〔会议不详〕四个来源与各自可用的缓解手段他把变异来源归纳为虚拟机多租户CPU存储

- 〔会议不详〕四个来源与各自可用的缓解手段。他把变异来源归纳为虚拟机多租户、CPU、存储、网络连通性四类，并强调虚拟机多租户是最大元凶之一：同一物理主机上的多个虚拟机不只是共享空间，而是在主动争抢资源；AWS 会为实现公平设置限额（他比喻成交叉路口的红绿灯），管理开销不落在客户 CPU 上而是卸载到 Nitro 层，但这些限额的实际阈值与缓解办法通常找不到文档。Nathi 接着给了逐类方案：CPU 突发限额可通过选没有该限额的实例或更大实例规避，连接跟踪限额可改用 untracked 连接（有取舍），DNS 查询限额可以自己缓存，实例带宽配置可把带宽从块存储调向网络；真正无法强制限额的只能是共享资源——同 CPU socket 的多租户共享 L3 缓存、同一 SSD 设备共享 SSD 缓存、共享内存与 CPU 之间的总线、共享热与功耗管理（x86 上一个租户制造热负荷会让整个 socket 降频），以及 hypervisor 的 steal time，而 AWS 约十年前推出的 Nitro hypervisor 把大量工作推向硬件、大幅压低 steal time，官方博客显示多种 HPC 负载在有无 hypervisor 时差异小于 1%。存储侧，托管块存储看起来像本地 NVMe 其实是走网络的块设备：路径可能更长或更拥塞，不同卷类型有不同性能剖面，后端系统的维护事件会表现成性能尖峰；AWS 侧用 SRD 多路径连接存储绕开拥塞路径，也建议尽量用本地 SSD（代价是易失）、选到整块盘的实例规格以避开小实例共享 SSD 缓存，并监控 IOPS 与吞吐限额，Percona 对 EBS 卷类型的测试还显示不同卷的变异差异明显。AWS 自身体量下发现不同供应商的 SSD 控制器在尾延迟上剖面差异很大，于是自研 SSD 控制器降低所有 SSD 的尾延迟，新实例的 Nitro SSD 控制器则“免费”降低变异；网络侧两台实例可能走完全不同的路径、多可用区部署还会增加跳数且默认放置是隐式的，缓解手段包括用 placement group 请求同一网络 spine，以及“latency hunting”——多开几台实例挑延迟最低的那台。（YouTube EPVBXmxaMdBvI，[479-1218]，L1）
- 〔会议不详〕自动并行化 shell 脚本：Pash。报告者团队介绍由 Linux 基金会支持的开源项目 Pash，一个把 shell 脚本自动并行化的 shell-to-shell 编译器：把脚本翻译成自己的数据流模型抽象、对数据流图做并行变换，再转回 shell 脚本，因此能跑在任何 shell（如 bash）之上。他先用《Hadoop 实战》里的练习脚本说明 shell 的战斗力：抓取某国家机构的温度数据索引、下载归档、gunzip 解压、清洗数据，再排序取首行算出 2015–2019 年美国最高气温——前四步是预处理，最后两行替代了书中那个 150 行 Java 的 MapReduce 程序。但多数 shell 脚本是顺序的，并行化需要大量手工（加 -P 之类标志、上 GNU parallel 或干脆重写）；在 82 GB 的五年气象数据上，bash 跑预处理约 33 分钟、处理约 10 分钟，Pash 把预处理加速约 2 倍、处理约 12 倍、合计约 2.52 倍——Hadoop 之类的框架只关心后半段，而 Pash 连预处理也能并行。命令是任意二进制的黑盒，所以 Pash 引入一套命令规格框架把调用与数据流节点对应起来（注解既能把命令变成节点，也能转回命令以生成数据流 shell 脚本），并给出一个 order-aware 的数据流模型，其变换已被形式化并证明正确。（YouTube EPVBrclDqRqMI，[12-532]，L1）
- 〔会议不详〕静态路线为何失败，以及 Pash JIT 与评测。Pash 原先走静态路线（那是跟几位编程语言研究者讨论后的选择，“PL 研究者都说该做静态分析”），但 shell 极度动态：脚本行为依赖当前目录、环境变量、未展开的字符串与文件系统状态，一个 ls 就能生成整个目录的文件字符串；静态并行化只能二选一——要么保守、一遇动态信息就放弃，要么不健全地假设变量全程不变，而后者并不成立。于是 Pash JIT 把并行化推迟到尽可能晚的时刻，在求值与并行化之间不断切换，把 shell 状态、变量、目录、文件等关键信息一并交给编译器，既正确又更快；JIT 引擎本身其实只是一个 shell 脚本，先保存 shell 状态、进入 Pash 状态、向并行化服务器请求编译该片段，然后恢复状态并执行并行版（失败则执行原版），整个过程对 shell 完全透明，用户那个 shell 根本不知道自己拿到的不是原脚本。原先 Pash 是一个被你调用的编译器、产出并行脚本，现在改成常驻的有状态编译服务器，省掉初始化、把状态留在内存里以降低延迟——这在紧循环里至关重要，小脚本连毫秒都算数；它还提供并行化原脚本里并不并行的独立片段（如分别接触不同文件的迭代）、以及按历史执行时长为同一循环后续执行配置并行宽度的画像引导优化。正确性用 POSIX shell 测试套件来量：套件有 1000 条断言、400 个测试、约 29000 行代码，他们花了一年才把 Pash 调到能应付并通过；在 408 个测试上 bash 通过 376、失败 32，Pash 通过 374、失败 34，两者只在 2 个测试上分歧，且都是双方都报错、只是退出状态不同，作为对照 dash、ksh、mksh 相对 bash 的分歧是两位数；性能在 4 个套件加 11 个独立脚本共 82 个脚本上，静态版处理不了整个 NLP 套件等大量脚本，Pash JIT 平均加速 5.8 倍、静态版 2.9 倍。收尾时他说 shell 依旧易错难学（自己每次写脚本还是先 Google），唯一例外是当天上午那篇 ATC 2022 最佳论文修掉了这个问题，同时 shell 也缺乏对分布式集群等现代部署的支持，所以 Pash JIT 更像一种使能器——换掉编译服务器里的分析逻辑就能造出 shell 监控器、全分布式 shell 或增量执行 shell。（YouTube EPVBrclDqRqMI，[532-1011]，L1）
- 〔会议不详〕把内存标签、认证加密与纠错合一：Voodoo。报告者介绍 Voodoo——一个把内存标签（memory tagging）、认证加密与错误纠正经由 MAGIC 模式统一起来的方案。现状是每种机制都要单独付开销：内存加密有加密引擎开销，Arm MTE 的内存标签约占 3% 内存，DDR4 上的 SECDED ECC 约占 12.5% 内存；单看都不算糟，但把安全块一个个叠加上去开销会累加，最终可能为整片 DRAM 付费却只能用不到四分之三。Voodoo 的方案是复用已有的 MAGIC 模式做底座——MAGIC 已能同时提供认证加密与纠错：每个消息块先加密写入 DRAM，同时乘以秘密乘子 h 的幂，把各乘积求和，再连同受认证的数据 D 一起加密得到认证标签 T。读出时用 syndrome 定位故障：若第 j 块出错，syndrome 等于该块错误乘以 h 的 j 次方，而秘密乘子的选取使错误乘积的 Hamming 重量满足特定约束，从而能由 syndrome 与错误位置标识符的重量定位故障块，并可把单块内的可纠错比特阈值 t 调成想要的强度。（YouTube EPVD5cNVRnMGc，[8-407]，L1）
- 〔会议不详〕为什么不能直接把内存标签塞进认证数据。若天真地把受认证数据 D 换成内存标签 MT，读出后 syndrome 里剩下的就是标签差 et，而标签若完全无约束，et 可取任意值，于是标签不匹配可能被误判为“可纠错错误”，方案会去修正一个密文块、结果改写出错误数据；反过来想读标签（用空标签访问），一旦某块确有错误，读回的就是编码标签混入错误项且无法识别。解决之道是三种标签编码：其一是 check pattern 编码，由于标签通常很小、没必要占满 64 位或 128 位消息块，于是把标签高位固定为某一恒定图案（全零、全一或任意数字皆可），使标签差的高位恒为零从而大概率判定为标签不匹配，代价是极少数本可纠错错误会被误判，此时中止纠错并报告标签不匹配；其二是 bounded Hamming 编码，把标签编码成差值 Hamming 重量始终低于纠错阈值，即可在标签不匹配与可纠错错误之间唯一区分、做到完全确定性、无别名，代价是标签空间更小。论文共给出三种编码并做案例研究，报告者说明最强编码在 64 位块下可给出至多 15 个标签位、128 位块下至多 36 个标签位；随后用蒙特卡洛仿真（基于现代 DDR4 的比特错误分布建模）验证：把 t 调到阈值 19 附近时约 99% 的模拟错误可被纠正，超过后出现不同错误位置标识符之间的别名而急转直下；多块随机分布场景下约 99% 可被识别为多块错误，别名最坏出现在阈值约 27 处。（YouTube EPVD5cNVRnMGc，[407-829]，L1）
- 〔USENIX FAST（推测）〕不写文法也能做结构化输入的模糊测试：Cremoa。报告者 Moritz（开场自我介绍“我是 Moritz，不是 Tim”）介绍 Cremoa，一个在模糊测试过程中自行学习输入结构、从而施加大规模变异的方法。他先梳理路线：盲测只能盯着种子附近的少数点打转；覆盖引导式模糊测试通过插桩获得反馈，保留带来新覆盖的输入、丢弃覆盖相同的输入，但其变异全是小规模操作——按位置翻转字节、给某字节加常数、替换字符、重复、拼接两个输入——只对短小输入有效。对解释器、编译器这类结构严苛的程序，语法人工编写既费时又依赖领域专家，于是需要一种不需语法的替代；Cremoa 的做法是“泛化”：把已有输入切分成若干 token 块（如按空白、按词法），逐块试探删除后是否仍能维持同样的新覆盖，若删除后覆盖不变说明该位置是自由的、被记为 gap，最后把相邻 gap 合并，于是 print 'aaaa' 泛化成 print '<gap>'、另一例泛化成 <gap> if <gap> then <gap>。这样搜索空间里就只剩一批带缺口的“岛”，岛与岛之间间隔极大，小规模变异根本跨不过去，而借助这些带缺口的模板就能施加大规模变异跳过去。（YouTube EPVF9YcAnzMPI，[10-695]，L1）
- 〔USENIX FAST（推测）〕三类大规模变异、评测、局限与问答。具体用的是三类变异：一是把模板插入另一个模板的某个 gap 里（输入扩张，受启发于 C 语言中分号分隔的语句可任意拼接这一事实）；二是递归替换，把模板递归塞进自身 gap 以指数级扩展嵌套深度、最多 64 步，是最有威力的一类；三是字符串替换，直接对关键字做同义或形近替换、不需要泛化模板。结论是：对结构化输入的小规模变异普遍无效，大规模变异能显著扩展搜索空间；Cremoa 在多数目标上优于 grammar-based fuzzer，因为不需要人写文法，但在语法表达力的上限上仍不如人工文法，报告者坦承存在 grammar-based 方法占优的情形；他还强调 Cremoa 的价值在于把原本只有专职安全研究者能做的事变得可自动化、可被更多人使用，真实世界影响方面共发现了 11 个 CVE。问答环节补充了实现细节：词法切分的 token 长度采用 2 的幂、从 256 一路减半到 1；关键字替换依赖对二进制的静态字符串扫描以提取关键字，且评测时所有 fuzzer 都拿到同一个字典以保证公平。局限方面，像 XML 的开闭标签这类需要同时修改多处才能成立的变异目前未被处理，团队计划用启发式补充；至于能否泛化到真正的文法合成，报告者表示对不同依赖类型尚无成熟答案。（YouTube EPVF9YcAnzMPI，[695-1246]，L1）
- 〔会议不详〕超越 typosquatting：包混淆的深入考察。沃塞斯特理工学院、堪萨斯大学与卡尔加里大学的合作报告开场指出，包混淆（package confusion）是 typosquatting 之外的更大威胁，既有研究多停留在对包名的词法/拼写改动分析，而真实攻击面远不止于此；他们把研究分三部分：收集并分类历史攻击数据、构建混淆检测器、在真实生态上做评测。历史数据来自安全公司文章与安全公告，共收集 1200 余个不同包，覆盖 NPM、PyPI 与 RubyGems 三大生态，并识别出 7 起以上一次性投放 10 个以上包的大型活动，分析以规模最大的 NPM 为主；通过对包名做主题分析并经过多轮迭代，他们提炼出 13 类混淆类别。检测侧由于包名里的 token 往往不带语义分隔符（mllearnlib 拆不开成 learn 与 lib），他们基于 NPM 包名语料自行实现了一套无分隔符的 tokenization 作为检测前置；真实案例包括把 learnlib、mllearn 混同为 mllearnlib 这类前后缀增补（prefix/suffix augmentation），也有把恶意行为藏在依赖里而不是包里本身的案例。（YouTube EPVFqUy-ROK2g，[8-347]，L1）
- 〔会议不详〕四个研究问题的实证结果。RQ1 是 NPM 生态里存在多少潜在包混淆：沿用他们前作 TypoGuard 的流行度阈值，把周下载量更高的包当作已建立的原始包、把试图混淆它的包当作待查包，从而把分析空间从约 1.7 的平方级别的 NPM 包对压缩到 170 万个待查包对照 2.4 万个已建立包，检出 36 万以上对可混淆包、其中约 3000 对同时命中多个类别。RQ2 关注被检出的混淆对实际有多“容易让人踩中”：他们让 64 名学生开发者对混淆对打分，13 类中有 3 类的“非常混淆”比例超过 10%、被 70% 以上的人认为至少有混淆可能，说明这些类别的检测器具有实际可用性；另有 2 类被评为混淆的比例低于 25%，他们推测与样本不平衡或检测器过度泛化有关。RQ3 是安全影响：他们没有逐个包做人工审计，而是用漏洞数据库作为恶意包的下界估计，结果显示被检出包被判为恶意的概率是控制组的三倍。RQ4 方面，他们按已有分类标注恶意行为并新增 crypto theft、downloader、confusion 三类，许多包因已从生态下架而无法核实；结论是包混淆是可信威胁，13 类分类提供了 typosquatting 之外的新维度，部分检测器可直接用作告警机制、其余需要进一步打磨。（YouTube EPVFqUy-ROK2g，[347-683]，L1）
