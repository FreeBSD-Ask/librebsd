- 〔HotCloud〕系统架构、初步结果与局限。架构上：用户书写明文 Pig 脚本，经变换器分析生成数据流图并抽取表达式树（追踪列与表达式的血缘），在数据流图层面把列与函数替换为对应的加密版本，生成的密文脚本连同 UDF（如 ENC_sum）提交到云中的 Pig 服务器执行，加密服务维护明文与密文文件/列的映射（实现为一组 XML 文件）。当部分同态方案能力不匹配（如加法结果无法与 OPE 加密的常量比较）时对中间结果重加密到目标形态。在 Apache PigMix 2（约 17 个脚本）于 EC2 上的初步结果显示多数脚本密文计算开销约 2 倍，个别（L9/L10）约 3 倍。局限包括不支持迭代、仅支持内置 UDF、访问模式仍会泄露（攻击者可知 filter/join 存在）；相关工作有 CryptDB；未来工作包括表达式重写降低重加密成本、采样启发式选择执行路径与字段级保密设置。问答确认 HElib 的 FHE 单次密文乘法耗时毫秒级、当前重加密需把数据送回可信端。（YouTube EP7p17skkCtnA，[662-1640]，L1）
- 〔会议不详〕新加坡国立大学的 Michael Wu 讲解全异步 DAG BFT 协议 Lemon Shark 与“提前终局”（early finality）。Lemon Shark 与 DAG-Rider、Tusk、Bullshark 同属利用有向无环图结构的异步拜占庭原子广播协议，但挑战了“必须等待 leader 提交才有安全结果”的传统范式，能在 leader 选举前就给出安全已终局结果，延迟最多降低 65%。其关键洞察是：在提交前确定区块的最终结果只需两件事——知道该区块终将提交，并在所有将并发提交的冲突区块中识别哪些会排在其前；为此 Lemon Shark 引入固定的因果历史排序（广度优先逆序）与键空间分区（key space partitioning，每轮每分片仅允许单一节点建块），并把事务分为 alpha（分片内）、beta（跨分片读、单分片写）、gamma（可串行化多分片）三类。（YouTube EP7q5DC93eeJE，[18.1-429.2]，L1）
- 〔会议不详〕后半场讲解单分片 alpha 事务的提前终局条件与实验结果。对某分片第一个未提交的绿色区块，只需检查“持久性”（persistence，后续轮 2f+1 个区块中至少一个有路径指向它，即 f+1 个后续区块有路径即可保证），即可在 r+2 轮早于最早官方提交（r+4 轮）安全交付结果；其他区块则通过链式递归引用形成绿色区块链，迫使未来 leader 必须在其因果历史中包含该链的 Proper prefix。评测在 fork Bullshark 异步仓库实现、以 Bullshark 为基线：单分片场景延迟较 Bullshark 低 65%，高跨分片活动下仍保持至少 25% 改进；模拟崩溃故障下因提前终局条件不依赖 leader 选举仍能持续产出早结果，最大可容忍故障下单分片约 25%、重跨分片流量约 14% 的延迟改进。（YouTube EP7q5DC93eeJE，[445.0-880.3]，L1）

- 〔USENIX Security（推测）〕后半场剖析社会工程与商业间谍软件 FinSpy。一封假冒半岛电视台记者 Melissa Chan、附件名为 JPG 的邮件实际使用 Unicode 右至左覆盖（RTLO）技巧伪装 GPJ.BATR.EXE 可执行文件，内存转储中发现 FinSpy 字符串，确认为 FinFisher 公司面向政府销售的端点间谍软件；作者感染机器观察 C2 流量，发现其自研弱加密（重复读取系统时钟生成弱密钥、明文尾部泄露），识别出麦克风/Skype 录音、取证窃密、屏幕摄像头监控、键盘记录等模块。进一步用 ZMap、Shodan 与网络测绘数据做全球扫描，借助服务器返回“hello steffi”、UTC/GMT 头错误及伪造 Apache 等指纹，以及“伪装成 Google 页面却泄露真实中继 IP”（搜索 my IP address 暴露 relay→master 两级架构）的缺陷，在巴林、土库曼斯坦等多国定位 FinFisher 服务器，并对竞争对手 Hacking Team 的 HTS 间谍软件做了同样分析；后续研究转向活动人士易受攻击性与包注入（packet injection）等新威胁。（YouTube EP7qHwmCGArYU，[505.2-1112.6]，L1）
- 〔SREcon（推测）〕Meta 的 Linux 内核内存管理工程师、systemd 维护者 Chris Down 讲解程序员与系统管理员对内存的常见误解。以 malloc 一 MB 的 C 程序为例指出 malloc 与真实物理内存分配毫无关系：libc 只通过 brk/mmap 扩大虚拟地址空间，直到 CPU 触发缺页（page fault）才分配物理页框，且对进程完全透明；free 也只是发给分配器（而非操作系统）的信号——free 后 RSS 可能不变（如 tcmalloc 放回 free list）、可能部分下降（glibc/jemalloc）甚至反而上升（free 本身触达新页）。他还演示 DRAM 并不擅长随机访问：行列遍历二维数组性能差 50 倍的根源是 RAS/CAS/precharge 的行激活开销，其次是 cache line 与 TLB 局部性，SIMD/预取的贡献常被高估。（YouTube EP7rAOnbjRmIE，[16.0-1196.0]，L1）
- 〔SREcon（推测）〕后半场聚焦可回收（reclaimable）的误解、cgroup v2 与 swap、PSI 与 senpai。page cache/buffer 虽标为 reclaimable 却不意味着“随时可立即释放”，许多工作负载离不开缓存，因此 RSS 是“垃圾指标”——Facebook 曾有团队自认每机内存占用 100-150 MB，实际测得约 2 GB；cgroup v2 的 memory.max 把所有类型内存一起限额，但层层加限会造出没人说得清的资源分配，而 memory.low/min 通过接入内核 reclaim 提供保护、更具 work-conserving，已成为 Meta 内部主要的内存保护手段；他还为 swap 正名（swap 提供匿名页后备存储、使内存压力渐进爬升，而非“应急内存”），并介绍基于 PSI 的 senpai 工具——施加恰好足够的内存压力挤出冷页，动态测出应用真实所需工作集（如约 340 MB），是 Meta 负载堆叠（workload stacking）的关键组件。（YouTube EP7rAOnbjRmIE，[1226.9-2407.7]，L1）
- 〔FAST（推测）〕清华大学的 Julie（尤佳琳/报告人）介绍 StreamCache——面向快速存储设备上文件扫描（file scanning）负载重新设计页缓存。内核 buffered I/O 借助页缓存的透明缓冲、数据聚合、对齐与预取被科学计算/AI 训练等数据密集应用广泛使用，但在下一代 NVMe SSD 上暴露两个问题：以 XFS 聚合 8 块 PCIe 3.0 SSD、FIO 4 MB I/O 测得缓冲读随带宽提升不足 35%、缓冲写几乎无提升（direct I/O 反而扩展更好）；脏页积累触发后台回写后软件开销占比增大，与前台缓冲写争抢，造成约 32% 性能退化。perf 剖析给出三点结论：页分配占 CPU 时间 24%-36% 为主要开销；页缓存索引 xarray 同时维护脏状态导致插页与改脏状态都要排他锁、锁竞争激烈；用户/内核间数据拷贝不可避免故本工作不优化。（YouTube EP7sjyqiMjmZk，[16.0-603.8]，L1）
- 〔FAST（推测）〕后半场讲解 StreamCache 三项关键技术：轻量级流追踪模块把脏状态从页索引解耦到独立的流追踪树（STT）并以流描述符维护，顺序负载下借助 per-file 流指针实现“流命中”避免搜索，每次 I/O 只需一次排他锁；基于流的页回收用全局流/脏流双链表驱动后台回收线程按流粒度回写，fsync 用 per-file 回写计数器替代细粒度标签，回写路径上 xarray 不再存脏状态从而把写-写竞争变为可 RCU 无锁处理的读-写竞争；两层内存管理以 per-core 内存池加 per-file 缓存消除页分裂、缩小锁竞争并移出页清零关键路径。评测将 8 块 Intel Optane NVMe SSD 聚合成 RAID 0 模拟下一代设备，与原始页缓存及改编自 USENIX ATC 2020 论文 FastMap 的 fastmap 缓存对比：在 LLNL 激光等离子体模拟的 PF3D checkpoint 内核上把 checkpoint 带宽提升 26%-62%，FIO 合成负载下不同 I/O 尺寸/文件大小/进程数均一致获益，消融实验证明各技术均有效。（YouTube EP7sjyqiMjmZk，[680.0-1205.9]，L1）
- 〔会议不详〕伯明翰的讲者介绍一个以形式化建模距离界定（distance bounding）攻击为目标的验证框架，强调十三年前多做验证论文本可减少如今大量漏洞。以伯明翰家门口的中继盗窃案（窃贼把设备伸进门缝、把车钥匙信号中继给车）说明任何无源认证系统当前都无法用密码学阻止中继攻击；又以欧洲广泛使用的非接触式 EMV 银行卡为例剖析协议（读卡器发 nonce、卡用次数与银行密钥生成会话密钥并做 MAC/签名），指出其除一个必须真实中继的随机数外几乎全部步骤可缓存或乱序完成，且智能卡加密时间波动大于中继耗时，作者的两台手机 PoC 实验成功完成中继；Mastercard 引入无加密的快速 nonce 交换命令以精确计时检测中继，NXP 也在专利文档中披露了带时间阈值的类似协议（但要求签署 NDA）。（YouTube EP7suRRw21mDo，[11.0-507.2]，L1）
- 〔会议不详〕后半场给出符号框架（applied pi calculus 为基础的小型建模语言，带 start/stop timer 与位置方括号）与正确性定义的整序结果。语义只需一条规则“计时器运行时不能从远程位置接收输出”即可精确刻画这些卡片行为、无需精确时间建模，从而可自动化；文献中五种正确性定义（mafia fraud 中继攻击、distance fraud、distance hijacking、terrorist fraud 及其带协助变体）被统一写为可检验的等式，并证明 mafia fraud 严格弱于 terrorist fraud、后者又弱于 assisted distance fraud，distance fraud 弱于 distance hijacking，两大类之间不可比；加入启发式后还得到两个新性质 relay hijacking 与 uncompromised distance bounding，并给出按威胁模型选择正确性质的图谱（远程攻击者查 distance hijacking、硬件可信时查 relay hijacking、EMV/车钥匙场景查 uncompromised distance bounding）。工具化后分析了多种支付协议并发现新攻击：NXP 协议若使用共享密钥则存在在错误时机插入身份的攻击，必须每设备唯一密钥。问答环节讨论了模拟域中继下纳秒级时界假设的局限。（YouTube EP7suRRw21mDo，[522.7-1399.9]，L1）
- 〔NSDI（推测）〕Jin Huang（合作者 KK Ramakrishnan 来自 Rutgers、导师 Timothy Wood 来自 George Washington University）介绍 NetVM——在商用平台用虚拟化实现高性能（目标 10 Gbps 线速）且灵活的网络。动因是专用硬件盒子贵、难升级扩展，而 PacketShader（SIGCOMM 2010，GPU 加速）、netmap（USENIX ATC 2012）与 Intel DPDK 虽在商用服务器上实现了高性能，数据中心却部署在虚拟化平台，overlay 模型（NIC→主机 OS→虚拟交换机→虚拟 NIC→客户 OS→应用再原路返回）开销巨大；结合 NFV 趋势（防火墙、负载均衡、CDN、深度包检测、WAN 加速等依次串行处理报文），虚拟化平台可动态部署、并行处理功能链，但需克服高速 VM 间通信等挑战。为此 NetVM 对 KVM 与 DPDK 做了一系列改造：虚拟化高速报文投递、面向网络数据的内存共享框架、hypervisor 级交换与高速 VM 间通信、安全域；并分析“hypervisor 层部署 DPDK”与“VM 内 pass-through 部署 DPDK”两种架构各自在灵活性与 VM 间交换、线速支持上的不足。（YouTube EP7tyIcmKRCuA，[9.8-514.6]，L1）
- 〔NSDI（推测）〕后半场讲解 NetVM 的设计与评测。报文 DMA 到 hypervisor 与虚拟机共享的 huge page 后永不移动，仅传递报文描述符并经 ring buffer 通知，VM 中的应用轮询共享内存处理，可链式转发、改头外发或丢弃（只读时可并行处理）；通过 core 与 queue 对齐消除锁与 NUMA 乒乓（跨 socket 读包会反复失效缓存），经模拟 PCI 设备线性映射共享内存并预计算偏移实现一次映射，按安全域隔离可信/不可信 VM 组；实现含 NetVM manager、DPDK 组件、模拟 PCI 设备与用户态便捷库四部分。评测在双路 Nehalem（Intel Xeon 8 核）上：NetVM 转发率随输入线性增长，Click 版本约 6 Gbps 后丢包、SR-IOV 约 5 Gbps 后下降；VM 链式场景性能随链长下降（受限于分配给 VM 的核数），60% 链式 + 40% 进出的现实场景下五个 VM 链仍接近 10 Gbps；基于队列大小的负载均衡优于 SR-IOV 的静态 L2 转发。问答讨论了 socket 编程模型差异（可用 KNI/用户态协议栈如 mTCP）与代码修改范围（只改 KVM 用户态部分、加 PCI 设备，未动内核模块）。（YouTube EP7tyIcmKRCuA，[514.6-1485.3]，L1）
- 〔FAST（推测）〕北京航空航天大学的 Junbin 介绍 SpanFS——面向快速存储设备的可扩展文件系统。从多核 CPU 到内存到闪存 SSD 的硬件均提供高度并行，但现有文件系统扩展性差成为瓶颈：RAM 盘上用 sysbench 对 128 个文件并发同步写的微基准显示，XFS/Btrfs/ZFS 无论日志式还是写时复制式都呈近乎水平线，而理想文件系统（每实例独立分区）接近线性。作者以日志文件系统的 JBD2 为例剖析集中式日志设计的两大问题：为保证事务顺序，日志提交与 checkpoint 在设备上串行化、牺牲 SSD 并行性；原子计数器、集中式日志缓冲/检查点链表与等待队列等共享结构在高频访问下产生严重锁竞争，lockstat 显示读写锁等待时间占总执行时间显著比例；且可伸缩锁（如 RCU）适合读多写少而 JBD2 写多，per-core 等待队列只能消除部分瓶颈——因此需要新的文件系统结构而非并行编程技巧。（YouTube EP7yDk2uEO_g8，[9.9-407.3]，L1）
