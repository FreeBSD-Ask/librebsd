- 〔USENIX Security（推测）〕RTAG：跨主机的可精细化攻击调查。Georgia Tech 的 Yang Ji（转写音作 Yan Yanji）报告说，涉及多主机的攻击越来越多：2015 年某台湾银行遭 ATM 窃资攻击涉及多主机横向移动，企业内威胁也用持久化与横向移动渗透金融机构，Black Hat 2017 上 NCC Group 提出的 GitPoison 还通过 Git 客户端与服务端链路把数据从客户端经服务端导出到攻击者。调查目标是准确性、效率与多主机支持，但要先回答究竟泄露了文件 A 还是文件 B、文件 A 是怎样一步步泄露的、这是什么样的攻击；在对等网络场景还要排除未参与攻击的主机，于是产生一个核心疑问：是否必须把这些跨主机的复杂数据依赖串行起来，还是可以并行分析再聚合结果。作者总结了三个挑战：动态污点分析能给出精确数据流，但一类在程序运行时直接做污点分析的做法开销高达十倍到三十倍，另一类可精细化攻击调查用记录回放把昂贵的插桩与运行时解耦、录制开销很低再在回放时做分析（代表工作是 RAIN 一类），两者都能兼顾效率、细粒度与准确性；剩余两个挑战是需要严格满足录制时的数据依赖以保证回放可并行而不串行化，以及并行带来的时间与内存成本仍需优化。（YouTube EPRitiriTdtlA，[10-651]，L1）
- 〔USENIX Security（推测）〕全局标签压缩为局部标签、跨主机传播与实测结果。用 GitPoison 的 SSH key 外泄作为贯穿例子：攻击者借 git tag 命令把 SSH key 从客户端经 scp 送到服务端，服务端 hook 从临时对象文件读出并打成归档文件，目标是搞清 SSH key 如何从客户端一路走到服务端的归档文件。若用能跨主机唯一识别的全局标签（含主机 MAC 地址、inode/dev/gen 信息与偏移、版本信息，共 2088 bit），成本显然过高；RTAG 的做法是先分析系统调用序列再分配最优标签——比如某进程 read 出 6 字节写入对象文件，只需要 3 bit 就能区分这些数据的来源，于是本地标签随每个 diff 任务的符号数量按对数增长，而其他系统的标签随符号数指数增长，内存成本也只是其他系统的一小部分。实现由四部分组成：标签关联负责跟踪跨主机的数据传输，标签分配为每个 diff 任务计算所需的最小标签大小，标签切换技术为每个 diff 任务分配本地符号化标签（在 read、write、send、receive 等 I/O 系统调用处把标签从全局作用域切到局部作用域，做完污点分析再切回并更新全局标签映射），标签叠加把各 diff 的结果按经典 provenance graph 合并出最终结论。跨主机传播上，TCP 保持数据顺序故用基于计数器的方案（收发两侧 send 与 read 次数不一致、要在同一 socket 会话内逐流跟踪），UDP 可能丢包故采用标签植入——在内核 socket 处理栈里于校验和计算之前植入、接收端在校验之前读取；结果显示文件 A 由两个临时文件 B 与 C 拼接而成，并可回溯到原始文件 E 即 SSH key。系统跑在 Ubuntu 12.04（32 与 64 位）上，用 libDFT 做数据传播、Neo4j 做图可达性分析、PostgreSQL 存储标签；评估涵盖 GitPoison、Firefox 客户端配 Apache 服务的两种 SQL 注入、CSRF、XSS 以及 6 主机 Napster 式对等文件共享场景，能准确恢复跨主机的完整数据流，并行化最多把分析时间减少 90%，SPEC CPU 2006 上平均运行时开销低于 5%，内存成本比 Taint 与 B-checker 低 50% 到 99%（两者在 Firefox 与 Apache 场景直接跑不完），对网络带宽影响小于 0.5%、RTT 小于 0.05%；问答中作者承认当前威胁模型假设攻击者无法攻陷内核，攻击者篡改在途报文剥离标签暂不覆盖，可用哈希校验补上。（YouTube EPRitiriTdtlA，[652-1305]，L1）
- 〔SREcon（推测）〕Netflix 如何应对流量尖峰（上半）：需求侧的流量调度。Netflix 平台团队的 Joey（转写作 Joseph，自称是分布式系统发烧友）先给规模背景：产品被全球用户全天候使用、设备类型数以千计且能力差异巨大；控制面跑在四个 AWS 区域上负责登录、拿播放 URL 与个性化，视频数据则由全球数据面 Open Connect（一个很 Fancy 的 CDN）承载，PoP 遍布全球。主负载指标是每秒流启动数（stream starts per second），区域峰谷可差一个数量级、周期近似 24 小时，us-west-2 因亚洲起床与美国就寝重叠而呈双正弦；当大量流量在区域间移动就会造成显著负载位移，而他们每周做一次区域疏散演练——几分钟内把整个区域流量搬走再拉回，这实际上等于两次尖峰。尖峰来源还包括标题上线带来的关联观看（如 Stranger Things 与 Squid Game，且常是全球性）与设备驱动的重试风暴：出错后设备协议与人类都在猛按重试，这也是 Netflix 最大的尖峰来源之一；更麻烦的是服务为分层架构、调用图很乱，必须预判尖峰在分布式调用图上如何传导。流量调度靠 CDN 与边缘代理 Zuul、加上全活的 Cassandra 数据库与可复制缓存 EVCache 这四项技术把用户放到任意区域，放置决策本质是在延迟与可用性之间取舍，为迎接尖峰 Netflix 整体偏向可用性：跑在 Open Connect 上的自研权威 DNS 提供约 100 个流量控制点，可以约百份之一的粒度把 api.netflix.com 重定向到某个区域（例如把用户从 us-east-2 引开），据此可做均衡或倾斜整形、也可在尖峰过后按实际形态重新整形——DNS TTL 收敛仍需数分钟，其间要靠路由层兜底，即 Zuul 的优先式负载丢弃：客户端每次请求都带优先级（立刻播放是编号低的高优先、上报过去三十秒的日志是编号高的低优先），Zuul 先丢低优先保住高优先；若某区域只有一个或两个服务被打垮，就把请求降优先级后发往其他三个区域——降优先级正是为了避免级联故障引发全球性中断。（YouTube EPRivD2EK5QFk，[16-1319]，L1）
- 〔SREcon（推测）〕Netflix 如何应对流量尖峰（下半）：算力的供给、恢复速度与弹性技术。供给侧的核心概念是不再谈 CPU 百分比，而谈成功缓冲与失败缓冲：系统能承受而不违反延迟 SLO、不报错的额外负载就是成功缓冲，超出部分必须丢弃；缓冲与业务价值相关，可通过自动伸缩或预测式伸缩在恢复常数内恢复（有状态服务更慢），所以快速恢复的服务需要的缓冲更少、可以跑得更高；对直播与播放路径这类关键服务要多给缓冲，对个性化这类非关键服务少给，负载隔离本质是业务决策。云的现实之一：容量并非无限，慢伸缩的有状态服务几乎全部预留并常驻（低谷期拿来跑编码），快伸缩的无状态服务跟随波动，还要按运行时长与价格在预留、按需与 spot 之间取舍；现实之二：算力供给随机型与时段波动（黑色星期五前后更难拿到容量），新机型往往池子更浅，采用新机型必须谨慎；现实之三：不同服务器差异显著，Netflix 用容量建模库量化差异（例如 m7a.4xlarge 有 16 个物理核而 m6id.4xlarge 只有 8 个），核心越多越能跑热而不进入性能曲线的弯折点，因此 tier 0 常取 2 倍缓冲、tier 1 取 1.5 倍缓冲，同一服务部署到 m7a.xlarge 与 m7a.8xlarge 时的运行 CPU 利用率差异很大。当预测出错就得靠自动伸缩兜底：Netflix 是 EC2 自动伸缩的大用户、数万服务器组常驻伸缩，策略是在成功缓冲起点做 target tracking、在失败缓冲起点做 hammering（步骤式扩容，注入比按利用率算出的更多容量），但自动伸缩本身有延迟——拆成发现、控制面启动硬件、内核与 systemd 与应用启动、流量收敛几部分，Netflix 曾以为瓶颈在 VM 启动，实测 VM 很快、控制面不是问题，真正的大头是检测（原配置要花好几分钟才知道有尖峰）与长尾应用启动（某个 tier 0 应用启动要 15 分钟），以及 systemd 启动约一分钟和 30 秒轮询的服务发现把流量导过来；对应优化包括用 EC2 高分辨率指标、把 ASG 冷却时间自适应到真实启动延迟、按 RPS 做 hammer（因为 CPU 利用率对 10 倍、100 倍、1000 倍尖峰都只显示 100%，RPS 才能区分量级）、以及并发启动 systemd unit 去除关键阻塞路径，最终把 tier 0 服务面对 10 倍尖峰的恢复时间从 8 到 15 分钟降到 3 到 4 分钟。弹性技术还包括优先式负载丢弃的完整梯度（先弃低优先、最后弃全部以避免拥塞崩溃）、I/O 密集服务按后端延迟做丢弃、重试与指数退避、把无界工作切成可限流的增量工作（数据网关负责分块与幂等）、以及缓存优先与 Holocron 快照（把媒体元数据快照推到 S3、由无状态服务读快照，从而不把尖峰打到底层数据库）；团队用完整测试金字塔（单元、属性、模糊、负载测试）持续验证，并会在演练时把整个区域的流量重定向以观察缓冲耗尽点。（YouTube EPRivD2EK5QFk，[1321-2603]，L1）
- 〔SREcon（推测）〕混沌驱动开发：把测试驱动前移进分布式系统的设计阶段。Bloomberg 韧性工程团队负责人 Tucker Varner（转写作 Tucker Vento，同属可靠性工程 guild）与公有云工程团队的 Dishan Amarnath 合作报告；Bloomberg 有 7000 多名软件工程师、维护着世界最大的私有网络之一，每天处理 3000 亿条行情 tick、每秒超过 1500 万条，客户拿这些数据做他们自己认为很重要的事，所以必须给到正确的数据与正确的时间。他们把混沌工程从救火式的生产响应前移为主动探测，认为它缩短了通往韧性系统的路径、让团队在自己的时间尺度内预演事故，而且往往实验还没跑、光是规划就已经学到东西；内部混沌工具与监控告警深度集成，触发预期的告警常常就是测试拿到绿灯的唯一方式。由此把韧性期望像单元测试一样固化下来，进而借用 TDD：作者承认 TDD 有效性研究结论互相矛盾，但学者们一致认可两点——先写测试能提升对程序的理解（而大家显然无法为系统维持准确的心智模型），以及 TDD 的效果取决于测试本身的准确与有用；混沌实验正是真实故障的准确复现，不像单元测试那样容易看着像测了其实没测。价值主张也相同：多花一点开发时间、省下大量 QA 与上生产的时间，而复杂度越高 QA 成本越贵，把期望左移后韧性就成了系统的一个特性而非事后补丁。（YouTube EPRkuA17ce7pU，[7-543]，L1）
- 〔SREcon（推测）〕日志聚合架构上的实战发现与检查清单。Dishan 报告把混沌实验用于公有云上的日志聚合架构：工作负载产生日志、由 Kubernetes 集群里的日志处理 pod 处理并落到中心存储桶，主备集群之间靠健康检查与告警触发故障转移逻辑切换流量；他先用问对问题的方式做实验清单，直接发现架构缺项——中心存储桶是全局单一汇集点却没有指标与告警、日志处理器自己打出的日志没地方存（集群挂了谁知道）、以及值班人是否有权限查看，进而给主备与中心桶补齐冗余与 HA 配置，也就是说在跑任何实验之前架构就已经补齐了告警、日志与监控。他们试图给故障转移逻辑写单元测试——按文档构造 mock 事件验证逻辑——但用混沌实验注入真实的节点与 pod 故障让健康检查失败、告警触发后，故障转移逻辑并没有按预期工作，说明 mock 事件仍有用，真正的力量在于对着真实故障做开发。后续实验又挖出更多问题：单节点挂掉时并不该立刻故障转移，Kubernetes 会自己拉起新节点或迁移 pod、服务其实还活着，于是得以把故障转移阈值调对；日志文件名用处理时间戳，一旦注入 NTP 故障或遇上夏令时切换，时间偏移导致文件被覆盖，于是在文件名里加随机因子；他们一直依赖公有云的默认配置，功能测试时都好用，可一旦引入应用或 API 故障，默认值就不再满足需求，只得回读文档调整；开源日志处理器自带的重试与内存缓冲让故障发现最迟延后 3 到 4 分钟，公有云侧也有 3 到 4 分钟告警延迟，这些限制无法消除但可以用来设计工作流与变更管理流程。Tucker 收尾强调混沌工程同时验证了第三方与开源组件的失效模式、把延迟发现的成本前移，并把前期工作变成生产 game day 所需的准备；他们整理出一份新系统设计检查清单，主张韧性压力测试应当成为设计验收的一部分、第一天就开始混沌、多弄坏点东西并从中学习。（YouTube EPRkuA17ce7pU，[543-1053]，L1）
- 〔NSDI（推测）〕Meta 全网部署 DCTCP 的经验（上半）：动机、收益与上线目标。Meta 主机网络团队（转写未自报姓名）报告把 DCTCP 推到 Meta 数据中心整个机群的过程与一个有意思的问题；DCTCP 是成熟、被充分研究且在别的生产网络被验证有效的拥塞控制算法，其超能力在于 ECN 信号——在交换机队列上配置 ECN 阈值，达到阈值就打 CE 位，发送方据此感知网络拥塞程度并反应，Linux 内核现成提供多种改拥塞控制的接口，因此可以直接实验。Meta 运营 20 多个数据中心，硬件配置各不相同，单个数据中心内有成千上万服务跑在共享服务器池上，服务调度有时会把延迟敏感与吞吐敏感服务放到同一机架、而这些机架缓冲又很浅，DCTCP 正好能通过调节交换机缓冲使用来帮忙；他们在小型实验中的结论曾发在 2018 年 LPC 的报告里。全网上线后的收益：网络侧重传率下降约 75%，以一个延迟敏感服务为例 P90 与 P99 延迟下降 38%；反实验关掉整个区域的 DCTCP 后重传显著上升、吞吐下降。上线目标有四条：只改短 RTT 连接、必须在第一个 SYN 发出前就判定 RTT（因为 ECN 是在那里协商的）；一次改动要覆盖整个区域（不想让 ECN 与基于丢包的拥塞控制共存于同一队列，而队列还另有用途、没有专用队列可用）；最小化复杂度与依赖（数千服务都要能工作、配置不依赖网络变更、不要求服务重启）；以及 fail-open 与 fail-fast 的设计，避免调参失败把网络搞挂。实现上排除了给每个服务发 setsockopt 库、内核级默认（无法只挑子集连接）与路由表方案（可用但不想为每次改 CCA 动路由表），最终选 eBPF：为不同 cgroup 版本写了两版程序，后来淘汰一版只剩单一 CCA 选择器。（YouTube EPRlVJ38HWZEc，[16-442]，L1）
