# 321.4.113 〔会议不详〕Swiss的两阶段算法与评测第一阶段breadth广撒网寻找协议的小

- 〔会议不详〕Swiss 的两阶段算法与评测。第一阶段 breadth 广撒网寻找协议的小型不变式，第二阶段 finisher 以待证安全条件为引导寻找完成证明的最后一个大不变式。搜索空间优化包括对称性去重（1 千万亿候选降到 2 千亿）、反例引导合成（以不归纳的谓词缩小后续搜索，finisher 场景降到 155 个）、以及过滤被已找到不变式逻辑蕴含的候选（breadth 场景从 8.2 亿降到约 2 千）；结果显示反例引导合成在有安全条件引导时更有效，这正是两阶段设计的价值所在。在含 6 个 Paxos 变体的 27 个协议上，Swiss 解决 18 个，包括 Paxos、Flexible Paxos，以及在给出搜索空间引导（告知对哪些变量量化）后的 Multi-Paxos；与 i4 相比解决了更多需要存在量词的基准（但 i4 在可解基准上更快），与 separators 相比能扩展到其无法处理的 Paxos 与 Flexible Paxos。结论是各方法优势互补、存在组合改进空间，作者对该领域前景乐观。（YouTube EPHlkFOk9Mo5Y，[334-652]，L1）
- 〔FAST〕HARDFS：以选择性轻量版本化加固 HDFS 抵御静默失效。讲者 Tan 与 Vijay Chidambaram 等合作（导师为 Remzi、Andrea Arpaci-Dusseau 与 Haryadi Gunawi），指出 fail-stop 故障已有成熟的崩溃恢复手段，而系统不崩溃却行为错误的 fail-silent 故障（内存损坏、软件 bug 在生产环境显现）难以应对，复制状态机与 N-version 编程又因资源与工程开销过高而少有部署；其 SLEEVE 层（转写漂移为 sleep/slip layer）在每个节点旁挂一个极简的第二实现，仅拦截外部 I/O（磁盘访问与网络消息）观察输入输出，把坏行为尽早转为崩溃（"早崩溃胜过说谎"），再利用现有崩溃恢复机制从可信来源重载状态。为控制工程量与内存开销，SLEEVE 只保护易出错（频繁变更）与未受保护的子状态（如文件层级、file-to-block 映射），用 counting Bloom filter 编码状态，对非布尔校验引入 ask-and-check 技术，选择性检查只需数行代码即可实现。（YouTube EPHlm9K29n5pM，[10-920]，L1）
- 〔FAST〕HARDFS 的恢复机制、评估与问答。恢复分为 crash-and-reboot 的 full recovery 与 micro recovery：后者利用两个版本对比精确定位损坏状态并仅修复损坏部分（借 checkpoint 文件等可信来源做多数投票判定哪个版本损坏，修复 SLEEVE 侧则从空 Bloom filter 起步随验证逐条加入正确事实），失败时回退到全重启；随机位翻转注入实验显示静默失效数量降低约 10 倍（崩溃次数约为基线两倍，属以可用性换数据正确性的有意取舍），Bloom filter 仅带来约 2.6% 内存开销，百万文件的 NameNode 全重启需数小时（主要耗时在等待并处理 worker 的块报告）而 micro recovery 秒级完成，并复现 5 个可致数据丢失的真实 HDFS bug 全部防住；问答讨论了 Bloom filter 中事实的编码方式（依赖待检属性如全路径名、文件标志）、counting Bloom filter 的删除语义、误报导致的不必要恢复与崩溃循环处置（连续重启超限即整体停机待人工介入），以及假阳性在错误检测意义上等同于假阴性的边界情形。（YouTube EPHlm9K29n5pM，[925-1852]，L1）
- 〔会议不详〕DPP：面向数据型攻击的可扩展数据与指针优先级防护。讲者指出随着 CFI 等防御成熟、控制流劫持攻击变得不可靠，不违反程序正常控制流的数据型攻击日益增多且现有防御不实用——全量数据完整性检查因程序中数据对象与指针数量巨大而开销过高；其数据指针优先级（DPP）框架基于"应用中并非所有对象与指针同样脆弱或敏感"的观察，从外部输入源识别数据并污点传播构建 tainted data flow graph，在其上以规则启发式筛选敏感数据对象与指针，再交给现有防御保护，设计目标是通用、可适配且可与现有防御集成。规则通过把利用策略拆解为更小组件推导（兼具跨利用通用与预判未来利用的潜力），共 7 条：谓词中使用且可能改变程序行为的数据、靠近数据缓冲区循环中使用的指针、进入已脆弱函数且被强制转换类型的数据对象、越界访问对象，以及以非受限条件分配的数据指针等。（YouTube EPHndV2DrCDyI，[8-355]，L1）
- 〔会议不详〕DPP 的实现与评估。每条规则实现为 LLVM IR 分析 pass（需别名分析、循环分析与 LLVM 数据布局信息），在开源静态值流工具 SVF 之上补齐了数组索引污点应传播到数组本体等缺失依赖；评估中 ASan+DPP 在仅插桩优先级对象的前提下，对来自 Linux Flaw 项目与 NIST Juliet 测试套件的内存错误的检出能力与默认 ASan 相当，从应用提取的 16 个脆弱数据对象全部排在优先级列表前 5%；SPEC CPU2017 整数基准上性能提升约 1.6 倍、相对 AddressSanitizer 降低约 70% 运行时开销；讲者同时说明原型基于 ASan 尚非在线防御、部分规则只考虑了紧随缓冲区的数据指针、需要更广的基准等局限，源码已公开。（YouTube EPHndV2DrCDyI，[355-710]，L1）
- 〔OSDI〕PeeR：为 eBPF 运行时引入可调度性。MIT 博士生 Jeremy（Carin）指出 eBPF 自 2014 年以来已从执行时间均匀的简单程序演化为可在内核实现完整应用（如整个键值存储）的复杂程序，但中断驱动、run-to-completion 的执行模型始终未变，由此产生两大问题：应用内竞争——长 scan 请求不可抢占、阻塞后续 get 造成队头阻塞（用户态本可抢占长请求）；应用间竞争——同核共存作业的场景下 eBPF 程序对调度器不可见、其时间片还被记账到正运行的用户态任务上，导致共存作业被完全饿死。PeeR（可抢占 eBPF 执行运行时）保持正常请求的中断快速路径不变，把运行过长的 eBPF 程序挂起并将其上下文保存到 continuation buffer，随后在调度器可控的 PeeR kthread 上恢复执行直至完成，由此统一中断路径与恢复路径的 CPU 时间记账，让 eBPF 程序像普通进程一样被调度、记账与隔离。（YouTube EPHr-XkgwJrJk，[18-500]，L1）
- 〔OSDI〕PeeR 的安全抢占机制与评估。安全抢占点选在 helper 函数调用处——它们本质上是执行中的安全点（不得在持锁等不安全上下文使用），PeeR 为每个 helper 加仅约两个周期的轻量预算检查，由调度器在需要抢占时填充；跨挂起恢复时 eBPF 栈内指针悬垂（use-after-free）问题，借助 eBPF 验证期生成的 helper 调用点指针类型清单（栈、map 或包数据），生成映射数组并在运行时恢复前统一改写指向新位置；Redis 实验中在 99.5% get 加 0.5% scan 的负载下，用户态 Redis 约 100 万请求/秒即饱和，eBPF 版本尾延迟显著高于理想线，PeeR 则将 get 的 p99 延迟降低 19 倍且吞吐与 eBPF 持平（成功消除队头阻塞），共存实验中 eBPF Redis 使同核作业被完全饿死，PeeR 可让作业随时间推移获得应得的 CPU 份额。（YouTube EPHr-XkgwJrJk，[500-965]，L1）
- 〔会议不详〕CRISP：同态加密与零知识证明兼顾隐私与完整性的数据卸载。EPFL 的 Silvan Chatel 与 Apostolos Pyrgelis、Jean-Pierre Hubaux 等合作，针对用户从数据源获取经认证的个人数据再共享给服务提供方的标准模型（智能电表、位置活动追踪、基因组数据分析等场景），要求隐私（服务方仅获知交付服务所需结果）、完整性（防止用户篡改数据源签发数据作弊）、通信与精度开销可接受，且能依赖已广泛部署的软硬件直接使用；方案以 CKKS 近似同态加密（Cheon 等提出的最先进方案）在密文上执行近似多项式计算，用 Bootle 承诺方案实现范围证明确保加密噪声在界内，并以 MPC-in-the-head 的零知识电路证明（采用 ZKB++ 实用实现）保证密文确由数据源签名数据正确加密而来。（YouTube EPHr30UGSr1vg，[9-330]，L1）
- 〔会议不详〕CRISP 的五阶段流程与证明体积优化。流程为收集、传输、验证、计算与数据释放：传输阶段用户生成密文并以自定义电路同时校验 SHA256 哈希（布尔电路）、加密噪声范数与加密正确性（含算术/布尔电路间的转换块），验证与计算由服务方执行同态求值，释放阶段以两轮交互协议（双方互做承诺并揭示校验）防止结果调包；智能电表打包一个月数据约需 650 MB 证明、位置追踪最多约 1.6 GB，但三项优化可显著缩减——前端零知识证明改用预处理模型协议（约减 25%）、数据源改为对满容量数据批签名（约减 50%）、随机抽样完整性检查（可减 60% 以上），组合后证明体积降至数十到数百 MB 量级，且证明验证一次后可在服务方方便时复用任意数据点、无额外开销，未来工作包括恶意服务方与进一步缩减证明。（YouTube EPHr30UGSr1vg，[330-667]，L1）
- 〔CSET〕UBCIS：容器镜像扫描终极基准。BlackBerry 安全研究组的 Shay Berkovich 等的短篇先行工作指出，公共基础镜像人人可得、漏洞随镜像复制扩散，需要扫描器提供已知第三方漏洞的可见性（但扫描器不发现新漏洞、后门或恶意容器），而不同扫描器对同一镜像给出互不相同的结果、无一覆盖全集且均有误报；扫描器架构含组件检测（查询包管理器或二进制分析）、漏洞匹配（组合商业与开源漏洞情报源）与报告（对情报源解析与结果判定的歧义）三阶段，报告歧义是最大问题来源；团队在 Fedora、Ubuntu、Debian、Alpine、CentOS 五个流行发行版上运行多个扫描器、合并去重并逐条对照情报源人工判定，在稳定性与流行度之间权衡后选定 Debian 10.2、Ubuntu 18.10、Alpine 3.9.4 等镜像，受工作量与 Fedora 支持缺失所限最终完成 Debian 98 条、Ubuntu 72 条、Alpine 10 条人工判定基准。（YouTube EPHr8M5_KNMqQ，[8-370]，L1）
- 〔CSET〕UBCIS 的判定分类、双模式与实用建议。漏洞除真阳（新披露未修复、被标不重要的长期挂起项）与假阳（backport 补丁未检出如 Alpine busybox、SELinux 等非功能包/内核包、ARM 与 x86 架构不匹配）外，还存在大量难判定项：untriaged（维护者未分诊）、依赖构建参数与使用模式的环境相关项、注释无明确安全影响、版本分歧（如 GCC 某漏洞 NVIDIA 称已修至 8.8.0 而 Debian 仍报 8.4 受影响）、维护者争议等；团队主张这类判定本质上是环境相关的，故基准采用 relaxed 与 paranoid 两种模式（分别将难判项记为假阳或真阳），用精确率、召回率与 F 值衡量扫描器；给出建议：先评估风险容忍度、确认所用基础镜像受扫描器支持，再按基准表选择扫描器；没有任何镜像零漏洞（零报漏洞反而提示配置问题或不受支持）、CI/CD 管道组合多扫描器是好事（需先决定并集或交集合并、交集并不可取）、镜像仓库扫描底层仍是同样的扫描器，基准已开源并提供 super scan 与 score 两种模式。（YouTube EPHr8M5_KNMqQ，[370-747]，L1）
- 〔Percona Live（推测）〕Azure 三地域 MySQL 架构实践。Pythian 的 OSDB 首席顾问 Gabriel（常驻布宜诺斯艾利斯）分享客户案例：应用需部署在三个 Azure 地域（地理就近访问 Traffic Manager 按就近与 endpoint monitor 故障转移分发请求）、全部数据需在每个地域可用、沿用 MySQL、以读为主的交互式负载且要求高韧性；多主 Galera/wsrep（准同步）方案因每笔事务需在另两节点认证、对跨区链路延迟极敏感且无跨区延迟 SLA 而被放弃，半同步也无实质改善（仍需跨区一跳并等待从库读取 binlog），且任何方案都无法消除不一致读，最终采用单主异步复制；读走本地从库、写走中央 master，代理层置于中间层（独立于数据库实例失败、可缓存查询），产品上因 MaxScale 2.0 改为 BSL 许可而转投 ProxySQL，配置读写分离 hostgroup、按权重实现读故障转移、以注释加正则规则实现 read-after-write 强一致路由到主库及 TTL 查询缓存；拓扑管理选用 MHA（当时未评估 GitHub 的 Orchestrator），fencing 采用 Azure API 关机与从 ProxySQL 移除服务器双重策略，任一成功方可安全切换，master 固定选在延迟最低的 West Europe。（YouTube EPHrHP2Ot1S50，[10-1155]，L1）
- 〔Percona Live（推测）〕架构局限与问答环节。讲者总结局限：代理层无高可用（代理失败则该地域由 Traffic Manager 摘除直至重建，社区有 ProxySQL 配 keepalived 的方案但未实施）、三分之二地域的写需跨区一跳、ProxySQL 会监控 read_only 参数且未置 read_only 的实例将被视作 master 接收写入（务必在配置文件中启用以防重启后失效）、fencing 可能阻塞 failover（MHA 更新 ProxySQL 配置或关闭实例耗时过长时需等待）、MHA manager 需在 failover 后于幸存地域重启；问答回应了 ProxySQL 1.4 集群（配置跨实例复制）当时仍处 beta 未普遍可用所以未采用，并说明可通过在 SQL 中加注释标记强一致请求、再以正则规则将其路由到主库解决 read-after-write 问题。（YouTube EPHrHP2Ot1S50，[1155-1294]，L1）
- 〔USENIX Security〕Posthammer：基于浏览器并以推迟刷新命令增强的 Rowhammer 攻击。ETH Zurich 计算机安全组的 Finn（de Ridder）与 Patrick Jattke、Kaveh Razavi 展示其测试床 28 款内存芯片中 17 款可被浏览器内 Rowhammer 攻破（平均约 15 分钟、成功率约 40%），攻击者在受害者访问网页的同时于后台锤击，最终在 JavaScript 进程内获得读写原语；三项洞察：其一利用内存控制器周期性刷新之外标准允许的推迟刷新（postponed refresh）制造缓解失活窗口，攻击者可自由锤击大幅提升攻击效力；其二非均匀模式（不同 aggressor 锤击频率不同）比均匀模式更有效，因缓解只能选择性压制部分 aggressor；其三浏览器内没有 clflush 指令、须用 eviction set 触达 DRAM，团队引入 lane（极小化 eviction set）并以交替 aggressor 的车道链构造既快又非均匀的访问模式，可得到 50%/25% 等不同锤击占比组合。（YouTube EPHrQYklFtUl4，[11-480]，L1）
- 〔USENIX Security〕Posthammer 的模板模式与十步利用流程。仅两种模式即可绕过所有缓解、无需针对特定 DRAM：以重复多次的双 aggressor 均匀车道为主体，再加若干并非真锤击、旨在干扰缓解的额外车道连接成单条指针链，配合刷新推迟即对多数芯片奏效；利用以类型翻转为核心——位翻转使 JavaScript 对象的数组引用与浮点数互转，先以分配器耗尽获得连续内存构建一个 eviction set（再以此派生更多），锤击中用轻微变体并不断交换 eviction set，找到两个精确位翻转（0→1 与 1→0）后以前作 SoftHammer 轻锤避免非目标位翻转；随后释放锤击数组并立即分配目标数组承接位翻转（该步成功率约 80%），重触发两次翻转后即伪造出数据指针可控的假数组，获得 JavaScript 进程全地址空间读写原语，攻击不依赖大页，artifact 已开源可自行复现。（YouTube EPHrQYklFtUl4，[480-905]，L1）
