- 〔SREcon〕SRE 二十年：开篇主题演讲。自称"对普及 SRE 负最大责任"（指 SRE 图书，能在商业书店货架上买到）的主讲人做二十年回顾，并明确这是个人视角（"公关部就是我自己"），把演讲献给上月去世的继母 Helen Gray。他重点抨击"Google 平滑、无坚不摧、绝不出错，SRE 因此继承这些机器般特质"的主流叙事：Google 自己也是创业公司（"创业像吃玻璃"），早期只有一份 cluster.py——用 Python 列出哪台机器跑哪种软件，被工程师不断 fork 到接近每人一份；babysitter 以"运行时能改列表就不必 fork 脚本"这一惊人洞见取而代之，随后 Work Queue 与 Borg 逐步接管集群调度——彼时 SRE 组织尚不存在，但 SRE 思维已在：关心生产的人被允许在生产中做工程，就会发生魔法，SRE 源于"在明天的糟糕事情发生前把稍微不那么糟糕的东西放上去"的工程循环。会上还指出 SRE 团队已遍布娱乐、外卖、教育、零售、政府、自动驾驶等行业，并进入中小企业，SRE 图书虽可免费在线阅读却仍在畅销。（YouTube EPPxPNxh8DPo0，[16-819]，L1）
- 〔SREcon〕二十年的亮点与低光：知识扩散、时代封面与未竟之业。亮点：SRE 知识已渗入普通工程乃至商业意识，向通用工程师解释 SLO 等术语的频率明显下降，Gartner、Forrester 纷纷撰文（如 Gartner 称 2027 年 75% 的企业将采用 SRE 实践，可商榷但这句话本身证明 SRE 革新了这场对话）；SRE 团队二十年来完成大量工程，其贡献对 Google 两个内部非常成功、外部被引数百次的系统至关重要；Mikey Dickerson 修复美国医保系统登上《时代》封面，Susan Fowler 的 Uber 备忘录助推 MeToo 运动——修复破损系统与组织复盘本就是 SRE 的一部分；"toil 与倦怠完全可预防"这一 cursed knowledge 单独就值得 SRE 的存在。低光：初级职业管道缺失（甚至有组织建议 SRE 只应面向高级岗）、SRE 项目落地失败罕见组织级复盘、缺少对 SRE 工作价值的定量模型（最紧迫问题）、零利率时代"增长不再可靠就不投资可靠性"等说法需要反击、以及"运维低人一等"的持久偏见。结语：把软件技术与系统思维应用于运维领域，这个"激进想法"在二十年后依然激进。（YouTube EPPxPNxh8DPo0，[819-1637]，L1）
- 〔会议不详〕从文件系统日志的实现与配置看 journaling of journal 问题。罗切斯特大学的 Kai Shen（与 Stan Park——毕业后任职 HP Labs——及 Meng Zhu 合作）从另一视角审视上一场报告的"日志套日志"问题：SQLite 等轻量数据库与 Kyoto Cabinet 等 KV 存储以 redo/undo 日志保证自身故障原子 I/O，又依赖文件系统日志保护文件系统结构与元数据，同一故障原子保护功能在应用层与 OS 层重复实现，违反端到端论证；实验显示给 SQLite 加 ext4 日志最多使事务完成时间慢 73%。其核心论断是这些额外成本并非本质，而主要源于日志实现或配置不足的伪影，用极简单的调整即可大幅缓解：方法一是减少事务提交关键路径上的设备写——理论上 full data journaling 可以单次连续写同时记录事务数据与元数据、checkpoint 异步进行，但 ext4 fsync 实现会把早前 fsync 的延迟 checkpoint 不必要地纳入后续 fsync 的关键路径，修复后即可解决；方法二是针对 ext4 页粒度日志记录导致的写膨胀（一次含 9 个小写的事务竟产生 11 个 4KB 日志页共 44KB，写量放大逾 10 倍、加剧闪存磨损），引入自适应日志（2005 年 Wisconsin 提出）——但逐事务设置模式会在故障恢复时错误重排事务间的覆盖写（T1 的数据写因仅元数据入日志的 T2 重放而成为最终状态），故改为按文件粒度设置日志模式、并在文件打开时（无未落盘脏数据）切换以消除切换成本。（YouTube EPPxYABn1eg4Y，[10-610]，L1）
- 〔会议不详〕按文件自适应日志的应用、评测与替代路线。应用到 SQLite：顺序写且几乎无元数据变更的 WAL 在 ordered journaling 下本就是单次顺序 I/O、无需膨胀为 full data journaling，而提交后常被删除/截断的 undo 回滚日志涉及大量元数据变更、更适合 data journaling。同时指出近年 journaling of journal 研究多瞄准 Android 手机负载，但其网络往返时延（几十毫秒级）远超本地 eMMC 写入（约 1 毫秒），I/O 优化意义有限，故面向服务器与客户端的通用 I/O 密集负载。评测：在 Intel 311 SSD 上相比无日志，ext4 ordered journaling 慢至 19%、data journaling 慢至 58%，增强实现几乎零开销且常更快（合并多次设备写）；Nexus 7 平板（运行 Ubuntu Linux）上为 20% 与 73%，增强实现开销很小。结论重申对自带数据保护的应用加文件系统日志本质上代价很小；结尾提出替代路线——让 OS 暴露故障原子 I/O API（如团队此前报告的增强 POSIX msync 文件原子语义的工作），把数据保护集中到 OS 一处更高效，但需要 OS API 与编程改动，Q&A 中 Ted Ts'o 指出数据库对文件系统行为的悲观假设、Peter Desnoyers 问及 Android 跌落/断电等 fail-stop 之外失效模型时的适用性。（YouTube EPPxYABn1eg4Y，[610-1224]，L1）
- 〔会议不详〕增量可更新的蜜码库（honey vault）与更新安全问题。主讲人程海波（Haibo Cheng，北京大学）指出密码管理器以主口令加密口令库并存于在线服务同步，攻击者窃取密文后可对人可记忆的主口令发起猜解，传统加密对错误猜解返回随机垃圾使攻击者可一次性解出全部网站口令。最先进的 honeypot 方案依赖同态加密（homomorphic encryption，ASR 音写为 homing encryption）生成诱饵，但当用户新增或修改一条口令时，现有方案会为每个诱饵生成独立的新版本，攻击者可据新旧版本相似性区分真实口令，且旧密文常作为备份留存，威胁是现实的而非纯理论的。本工作提出通用构造与蜜字（honeyword）增量更新机制，并实例化能生成更逼真诱饵的构造。（YouTube EPPzv3AGkjaq8，[8-297]，L1）
- 〔会议不详〕条件编码器、增量更新机制与最优区分策略。构造假定用户逐个生成口令，使总体概率为各口令条件概率之积，只需估计给定若干旧口令时新口令的条件概率，据此提出条件编码器（conditional encoder，经 Cheng 等人的变换模块实现逐口令编码）。配合前缀保持加密（prefix-keeping encryption），新增口令只需把新口令比特串追加到库比特串，删除仅作标记不改密文，修改则追加并更新口令索引；条件编码器保证旧字节串是新串的前缀、加密方案保证旧密文是新密文的前缀，使拿到两个版本的攻击者退化为只拿到旧密文，从而达成更新安全。作者另提出单相似口令模型与马尔可夫模型分别刻画口令复用与全新生成，并形式化分析最优区分策略（按条件概率对候选排序），实验显示现有最优攻击对本方案区分准确率不超过 58%（接近完美方案的 50%），攻击在线代价提升 2.8 到 7.5 倍，机制也可推广到其他同态加密应用。（YouTube EPPzv3AGkjaq8，[309-586]，L1）
- 〔会议不详〕端到端加密消息中的密钥认证问题与 SOAP 协议。主讲人（第一作者，导师为 David，演示对象为同事 Christoph）指出 Signal 类应用中经 SMS 一次性口令认证手机号后即可向密钥服务器上传公钥，消息安全依赖 SMS 未被截获且服务器返回真实公钥；安全码（safety number）QR 码扫描验证虽提供强保证，却要求物理邻近，且攻击者事后把恶意公钥关联到联系人账号即可让既有验证轻易失效。作者提出 SOAP：用户向对端分享自己在 Microsoft、GitLab 等第三方账号上的 OpenID Connect 令牌，使对端完成"社会认证"（social authentication，此前仅被非正式研究、术语由前人提出），可确信同一人控制消息账号与第三方账号，即便不认识这些账号也可在日后作为二次因子重新认证。论文五项贡献包括把社会认证形式化为 trace 性质、给出自动化且支持多身份提供者的 SOAP 设计、并证明其安全性。（YouTube EPQ1p2iRec954，[8-352]，L1）
- 〔会议不详〕OpenID Connect 令牌分享的形式化与 Tamarin 证明。SOAP 用 OpenID Connect（驱动大量"用 Google/Apple 登录"按钮的协议）自动认证，难点是 OIDC 通道通常未认证，攻击者可用短链诱导用户点击而代替其触发请求，且 OIDC 在消息应用中被组合到其他协议使用；作者在 Tamarin prover 模型中还考虑了消息密钥服务器、蜂窝运营商与任意多次协议运行。在六条假设（账号凭据不泄露、TLS 密钥安全、消息应用与浏览器未攻破，最非常规的是 HTTP 重定向必须保密，换来的好处是不假设用户行为安全、允许用户点击一切链接）下证明了安全保证：攻击者除攻破 SMS 或密钥服务器外还须攻破每个关联账号，使其处境严格变难。未来工作包括更多支持 OIDC 的提供者（社交网络普遍不支持）、协议标准化与非安全消息场景、后台全自动运行，以及与 transparency log 等机制组合的安全分析。（YouTube EPQ1p2iRec954，[364-695]，L1）
- 〔会议不详〕云上副本数据服务的冗余复制问题与主增量（Main-Delta）架构。主讲人 Hemant（滑铁卢大学，与 SAP Labs Waterloo 的 Jeffrey Pang 合作）指出为本地部署设计的应用自带应用层复制以提供容错与高可用，上云后与云存储内置的复制叠加，造成冗余副本与额外存储开销而无额外收益；去掉应用层复制会引入单点故障，让各副本共享云端单一数据又使云存储 I/O 进入读写关键路径并在 Cassandra 这类 shared-nothing 系统中形成争用点。作者提出将主增量（main-delta，ASR 音写为 main database）架构引入副本应用：delta 存于各副本节点本地（内存或本地盘），main 存于云端存储并作为全部副本节点共享的单一应用层副本，delta 通常比 main 小一个数量级，因此只复制 delta，通过控制缓冲管理与刷盘即可纳入现有应用且兼容整个复制策略谱系。（YouTube EPQ2-QB9UpjIE，[8-442]，L1）
- 〔会议不详〕面向不同复制策略的 delta 合并与 AWS 评估。作者把复制策略分为单主（如 Kafka）、单主多读（如 MongoDB）与多节点读写/多数派（如 Cassandra）三类并给出两端做法：Kafka 以内存缓冲为 delta、盘上数据为 main，只合并主节点的 delta，主节点故障由新主接手合并职责；Cassandra 把 memtable 视为 delta、sstable 视为 main，各节点把 delta 刷到共享云存储后借助 Cassandra compaction 作业合并，仅在短时间内存在 delta 冗余且不改变刷盘语义、只改 compaction。AWS（EBS 与 EFS）上用系统自带性能工具做实验：复制因子为 3 时 MD-Kafka 设计上即省 3 倍存储且写吞吐与原版几乎相同，EFS 上因主增量架构批合存储 I/O 快约 2 倍；Cassandra 有约 2.8 倍存储节省（deltas 短期冗余），只读/只写/混合负载吞吐与原版相当。（YouTube EPQ2-QB9UpjIE，[445-849]，L1）
- 〔会议不详〕Garter：可调安全内存分配器。主讲人 Sam Silvestro（与同学 Hongyu Liu、Tianyi Liu、俄亥俄州立大学 Lin 博士及导师 Tongping Liu 合作）回顾缓冲区越读（如 OpenSSL Heartbleed）、use-after-free、堆溢出、double free 等漏洞后指出默认 Linux 分配器在对象前存放元数据、用双向 freelist 且无随机化、对 double/invalid free 处理不佳，攻击者可操纵 freelist 指针控制分配函数。现有安全分配器 OpenBSD、DieHarder、FreeGuard 均为 bibop（big bag of pages）风格并分离元数据，但要么熵低（FreeGuard 恒 2 位）要么熵不稳（OpenBSD 2-10 位、DieHarder log N 位且随 size class 增大骤降），且 OpenBSD 平均 31%、DieHarder 平均 74%（最坏 9 倍）的开销过高。Garter 追求可靠（跨 size class、输入、执行阶段与应用的稳定熵，可指定熵下限）且可调（按性能预算调整安全级别）：每线程为每个 size class 维护分配/释放缓冲对，释放缓冲为环形缓冲实现常数时间释放，分配缓冲容量取 2^(e+1) 并保持不低于半满、分 8 区整体检测并辅以前向游走，避免过度随机检测与频繁重填。（YouTube EPQ26_z5oKTVA，[12-649]，L1）
- 〔会议不详〕堆超额供应、随机守卫页与评估及问答。Garter 的分配缓冲在低于半满触发填充时随机选中 1/8 个新对象跳过不用实现可调堆超额供应（overprovisioning），把随机选择次数降为朴素方法的 1/8；另有每 bag 末尾的静态守卫页与默认 10% 的可调随机守卫页（无物理内存支撑、不增内存足迹），命中即段错误，可防堆溢出与堆喷射。在含 Parsec 多线程套件与 8 个真实应用的 21 个程序上（归一化到 glibc）Garter 平均开销小于 3%，快于 DieHarder 与 OpenBSD、与 FreeGuard（约 2%）基本持平但安全保证更强，原因是避免了中心锁（除全局 free cache）且释放为单次试验常数时间；默认 9 位熵下实测平均 9.9 位且跨 size class 稳定，安全特性覆盖最全（元数据完全分离、free 时 canary 检查、可检测全部 double/invalid free）。问答讨论了可调参数给开发者带来的认知负担与可用性、熵与 Windows 10 堆随机化等确定性防御的相对性、碎片化未测，以及作者尚未实际尝试绕过 Garter。（YouTube EPQ26_z5oKTVA，[654-1341]，L1）
- 〔SREcon〕Jet.com 的分布式追踪实践（前半）。主讲人 Gina（Jet.com 电商网站高级平台工程师，ASR 音写为 Maiynee，团队每两周发布全公司共用的基础库）介绍 Jet 以事件溯源（event sourcing）为事实来源、用微软 F#（OCaml 近亲、运行于 .NET）开发、托管 Azure 且多区域一键故障切换，tier 2/3 服务大量异步写总线，使跨系统因果归因困难（例如"展示某商户失败的全部库存更新"这类含 join/group by 的复杂查询）。商户工具经 RPC 更新 SKU 后经 Kafka 再到 Elasticsearch，静态架构图难以定位故障（Kafka 集群坏了商户 API 团队并不知道），而现有生态工具偏重 RPC 时序可视化，无法满足异步事件溯源场景，Jet 于是自建 F# 追踪平台（100% OpenTelemetry 兼容）。V1 的教训包括一开始就把追踪强行 bake 进平台（sprint 里塞不下这么多工作）、同时服务开发者端到端 SLA 与业务方拓扑图两种不同前后端需求导致贪多嚼不烂、没有找到愿意追踪的内部赞助者、以及 wire 规范过于复杂（correlation ID、payload schema URI、P/M tags 等字段让开发者无所适从且无人读文档）。（YouTube EPQ407GWi-_0U，[11-1095]，L1）
