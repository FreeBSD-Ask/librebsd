- 〔SREcon〕危害缓解与 fizzle factors。她主张坏事情总会发生，所以要像她教初中性教育课那样“让失败不那么致命”：墨西哥城 1985 年 8.2 级地震（约万人死亡）与 2017 年 7.9 级地震的差别是建筑规范；Grenfell Tower 约 82 人遇难（外覆层形成烟囱效应、燃烧还释放氰化物，且全楼只有一部中央疏散楼梯并被旧冰箱堵住），而外覆层几乎一样、高度两倍多的迪拜 Torch Tower 因四个角落加中央共四部疏散楼梯、火灾报警器正常响而无人死亡；芝加哥靠严苛的喷淋规范把高层建筑层间蔓延风险压到 2%。她进一步区分 fail safe 与 fail secure 的取舍（核反应堆失去控制即插入控制棒、SawStop 毁掉锯片保住手指、Halon 数据中心是“值得拿人命去算”的算计），指出失败几乎总是 oversight、要找能让你说出“你为什么要这么做”的测试者，kill switch 应当小而多而不是一个总开关；并用 Minneapolis 35W 大桥塌落（gusset plate 只有设计厚度的一半、桥龄 60 年、加铺混凝土与除冰系统增重、施工振动叠加）说明灾难源于多因素叠加而非单一根因，最后列出避免级联失效的 fizzle factors（微服务与松耦合、容错消息、数据复制、canary 发布、kill switch 与熔断器与泄压阀、自动恢复、负载压力与宕机测试）以及四句总结：expect failure、make systems less rigid、plan for disaster、degrade gracefully。（YouTube EPSWfsLwiDWzg，[1253-2414]，L1）
- 〔OSDI〕容错且具事务性的有状态 serverless 工作流。主讲人自报姓名 Haoran，与 Aditya、Peter 及导师 Sebastian、Vincent 合作，介绍系统 Beldi：serverless（FaaS）把服务器维护交给云厂商，AWS Lambda、Google Cloud Functions、Azure Functions 配上 DynamoDB、Bigtable、Cosmos DB 已成主流，但 worker 之间没有协调且随时会挂，云厂商只要求开发者写幂等函数——他的午餐登记计数示例说明，客户端在云端超时后并不知道程序崩在写之前还是写之后、能否重试，这对有状态应用代价太大。Beldi 作为 worker 与存储系统之间的 shim 层，暴露读写数据库、一个函数调用另一个函数、跨多个 serverless 函数定义事务三个 API；每个 lambda 维护 progress/use/log 三张表，用 instance ID 注册并由周期性 progress lambda 重启未完成实例，思路源自 OSDI'16 的 Olive。读操作没有外部可见副作用、可安全重读；写操作则必须连同日志原子提交，否则崩溃在写与记日志之间会重复写入、破坏 exactly-once。由于跨表事务既昂贵又并非所有数据库都支持，Beldi 借鉴 OLAP 领域的一种机制（讲者口述为 Dao）把日志条目与数据同存在同一行——在用户表上加一列 recent writes，用一次请求同时更新数据并插入日志。最后他列出三个技术挑战：单行空间有限、必须积极回收与数据同存的日志；每个 lambda 联邦化、各自拥有 progress lambda 与垃圾回收器；以及跨 lambda 的原子性需要一套事务协议（本讲只覆盖前两项，事务细节留待论文）。（YouTube EPSZVeAVyR0Lo，[8-552]，L1）
- 〔OSDI〕跨函数 exactly-once 与性能评估。由于各 lambda 的 progress lambda 与垃圾回收器相互独立，lambda 1 超时后用同一 instance ID 重试调用 lambda 2 时，lambda 2 的日志可能已被其自己的 GC 清掉，于是写入被重复执行、破坏 exactly-once；Beldi 因此引入 callback 机制，让 callee 在标记完成前把返回值搬回调用方的 log 表，使双方可各自独立回收。评估在 AWS Lambda（每实例 1GB 内存）上进行：micro benchmark 取 key 1B、value 16B、链表长 20 行，读写、条件写与调用的开销来自链表扫描、日志与 callback，整体比 baseline 贵约 2–4 倍；真实负载移植 DeathStarBench 的 movie review、travel reservation、social media 三个应用，travel reservation 含 10 个服务与 reserve hotel/reserve flight 的跨服务事务，在约 700 rps 处饱和（主要瓶颈是 AWS Lambda 单账号 1000 并发上限），median 与 p99 响应时间约为 baseline 的 2 倍，在可测的最高负载下 Beldi 能达到与 baseline 相同的吞吐、但 median 响应时间约为 baseline 的 3.3 倍（baseline 既不支持事务也不容错）。结论还提到支持跨多账本协作式分布式事务的协议、高效 GC，代码在 GitHub 上开源。（YouTube EPSZVeAVyR0Lo，[562-1083]，L1）
- 〔USENIX Security〕TLB;DR：用 TLB 失同步逆向工程增强 TLB 攻击。讲者（转写未给姓名）介绍 TLB 的动机与 Intel 拓扑：CPU 支持虚拟内存，多级页表使一次 page walk 需多次访存，故用 TLB 缓存已完成翻译；Intel 上有专用的 DTLB（数据加载）与 ITLB（取指），仅当 L1 未命中才查数据与取指共用的 L2 STLB；TLB 是集合并行结构，被同核的兄弟超线程进程共享，可通过时序采样（TLB hit 快于 page walk）泄露信息，前作 TLBleaks（Grasset 等）已逆向出部分 Intel TLB 属性。核心方法是 TLB desynchronization：利用 TLB 非一致、页表修改需显式失效的特性，故意让 TLB 中的 A→X1 与页表中的 A→X2 不一致，并让两处存放易区分内容（1,2,3 与 3,2,1），从而可靠区分 TLB 命中与失效；据此考察 inclusion 策略、insertion 策略、set 大小、哈希函数与替换策略，发现 Intel 上有三种替换策略：LRU（Ivy Bridge 的 ITLB）、tree-PLRU（所有被测 DTLB 与较老微架构的 STLB），以及新微架构 STLB 上的新策略 MRU+1——12-way 分三组、组内各为 3-PLRU，根节点记住最近使用组并 +1 决定 victim 组。（YouTube EPS_A4fBKE1iE，[8-340]，L1）
- 〔USENIX Security〕优化逐出模式带来的攻击收益。TLB 类攻击往往只需从某集中逐出一个特定条目（如 TLBleaks 采样时要逐出被监控进程的条目），以往朴素做法是把整组 12 个 way 全部刷满；掌握替换策略后可构造最优逐出序列，用 3 次 hit 加 1 次 miss 即可让目标条目成为 victim，替代原来所需的 12 次 miss。结果是：DTLB 上的 TLBleaks 采样快 20%，L2 STLB 的泄露从不可行变为可行（采样快 2 倍、接近 DTLB 上朴素逐出的水平），同时从 DTLB 与 STLB 联合泄露的变体采样率高 5 倍；对依赖 page walk 副作用的间接攻击也有收益，PT Hammer 的 hammer 时间缩短 12%，ASLR on the Line 破解 ASLR 所需时间少 20%。讲者还提到论文里另有一个用于记录地址空间的未文档化 cache，因时间所限未展开。（YouTube EPS_A4fBKE1iE，[341-657]，L1）
- 〔HotCloud〕分离与应用：分离式数据中心上让应用与操作系统协同。主讲人自报姓名 Sebastian，与 Mihir、Sid 合作。他先讲分离式数据中心（disaggregated data center，DDC）的动机：传统机架把 CPU、内存、存储、GPU 与高速网卡都塞在同一块主板，DDC 则把这些资源经高速网络拆开——存储与 GPU/TPU 的分离已相当常见，而本工作更进一步把内存也分离出去，服务器只保留少量本地内存（既跑操作系统、又作应用状态缓存），大部分内存放在独立的 memory blade 上。DDC 的运维收益是硬件可独立替换与扩容、故障可局部发生、便于满足“3 个 CPU + 117GB RAM + 2 个 GPU”这类奇特配置。已有操作系统 LEGOS 能以标准 POSIX 接口跑未改动的应用，但作者引用本团队发表于 VLDB 的测量研究指出，未改动的生产应用会损失一个数量级以上性能，因为即便有本地缓存，多数 load/store 仍落到远程内存；他用两个应用互传数据的例子说明数据被反复搬到同一处。他因此主张应用应当为这类硬件改造，前提是操作系统暴露足够的信息与能力，并提议三个原语：memory grant（授予方让出部分内存页的控制权，由 memory node 重配页权限并通知接收方 OS，几乎不搬数据、只传受控的小消息，且像 Rust 的移动语义那样约定授予方永不再访问，从而避免跨网络做缓存一致性）、memory steal（由接收方发起窃取）、failure informer 或 spies（内存节点崩溃时通知相关进程）。（YouTube EPS_o4SxYRWgw，[8-602]，L1）
- 〔HotCloud〕steal 与 spies 的语义约束，以及应用改造示例。memory steal 与 grant 类似但由接收方发起：App Two 请求从 App One 偷页，memory node 完成权限变更后通知 App One 页已消失，因此 App One 可能正干着活就丢了一半内存，这要求应用能接受这类操作；关键约束是被偷走的内存必须内部一致，否则接收方进程会崩，这与非易失内存系统里的崩溃一致性保证相似、可借用事务等技术，且 steal 只用于同一应用内部的进程协作而非互不相干的应用相互竞争——错误的 steal 相当于多线程程序里一个线程踩踏另一个线程的地址空间。failure informer（spies）则让内存节点崩溃时主动告知正在访问它的进程“我快挂了”。应用方面：MapReduce/Naiad 一类数据流与图处理系统可用 grant 以“传引用”方式在 worker 间传数据、用 steal 让新 worker 接走较慢 worker 的未完成任务以处理 straggler；Memcached 这类 scale-out 系统可让新实例 steal 热点对象；Paxos 可用 spies 在内存节点或 CPU 失效时更快触发 reconfiguration，并通过 steal 旧副本内存而非从别的副本下载整份快照来加速追赶。最后他总结：不建议在 DDC 上跑未改动的应用，但只要应用愿意适配、并由操作系统提供更多信息与控制，这些系统在这种环境下仍有竞争力。（YouTube EPS_o4SxYRWgw，[603-977]，L1）
- 〔FAST〕滑动回溯窗口辅助的数据块重写以改进去重与恢复性能。主讲人自报姓名 Zhi Chao（自称来自明尼苏达大学），研究与中国海洋大学（Ocean University）、华南理工大学的合作者共同完成，导师为 David Liu。他回顾备份去重与恢复的基本流程：字节流按 CDC 或定长算法切块，用 SHA1、MD5 等哈希得到 chunk ID，新块写入容器以利用 HDD 的顺序读写，并由 recipe（配方）记录未来恢复所需的块序列；恢复时靠缓存命中避免 4–8MB 容器的昂贵读 I/O，但当 recipe 引用的块散落在多个旧容器中时，每个块都要触发一次容器读，读到的无关数据对未来的恢复毫无帮助、缓存完全失效。重写（rewrite）虽能以空间换恢复性能，却面临去重率与恢复性能的取舍、去重阶段信息受限、去重与恢复难以解耦三个难题。他分析 HP Labs 发表于 FAST'13 的 Capping 方案——把字节流切成约 20MB（5 个容器、约 5000 块）的段，按被引用次数降序排列并设 clipping level，使整段恢复最多只需 3 个旧容器读加若干本段生成的容器，即对容器读次数给出上界——并指出其三点局限：固定的 clipping level、固定的切分边界、忽略缓存中已有块，据此先提出 FCRS，用引用计数阈值替代排名切点，并按用户给出的去重率上限与容器读上限两个 bound 在每段内动态调节阈值，把盈余累积到后续段以获得更大调整空间。（YouTube EPSay55dyAwx0，[11-867]，L1）
- 〔FAST〕LBW 设计与评估。为同时解决固定切分与缓存问题，他们提出滑动回溯窗口（LBW）方案：让窗口每次只前移一个块、等于在每个位置都切一刀，使每个块都拥有前后同等分量的信息来做重写决策；决策未必当场能定的块进 candidate cache 暂存，用大小与窗口相同的 recipe cache 记录窗口内仍引用旧容器的块，一旦决定移出窗口即最终落定；他们还引入“缓存有效范围”——结合 FA 等恢复缓存算法估算写入多少块后仍会命中缓存，从而避免为已被缓存覆盖的块白白重写。评估实现了 8 种去重-恢复组合（无重写的 normal、Capping、FCRS、LBW，配 HP 的 FA 与他们去年提出的 ALIKE 两种恢复引擎），用 File and Storage Lab 的 6 条 trace 做模拟：normal 去重率可达约 15 但加速比（speed factor，即一次容器读平均恢复多少原始数据）仅约 1；Capping 在约 1.2 的去重率（重写了 80% 以上的块）下加速比约 3.7，而 LBW 在同样激进的设置下仍保持约 4 的去重率、省下约 75% 空间；在高去重率（约 14）的保守设置下 Capping 加速比约 21.27，LBW 高约 30%；无论配 FA 还是 ALIKE、在全部 6 条 trace 上 LBW 都是最好的。Q&A 中他说明实验是 trace 驱动的模拟，以容器读次数而非绝对 I/O 时间作为度量以排除平台依赖，因为 EMC、Veritas 等企业常用 4–8MB 甚至更大的容器，读时间远大于寻道时间。（YouTube EPSay55dyAwx0，[868-1706]，L1）
- 〔会议不详〕正确性专题预告：软件正确性的验证、测试、运行时与维护技术。讲者自报姓名 Chen Chen，与 Le Fan 共同报告。她先说明“正确性”在没有完整规范时难以定义，但错误输出、崩溃、资源泄漏与内存破坏显然不正确，并给出问题规模：Microsoft 应用在内部测试期约 10–20 个 bug/千行代码、发布后约减半，Linux 内核每个版本上万补丁，Apache 每周约 15 个补丁，而 bug 会造成服务中断、安全漏洞乃至医疗危机。随后她按四个阶段梳理技术谱系：开发期的静态检查（用编译器替代人工 code review 扫描空指针解引用、复制粘贴后改名错误、并发访问相关性等已知反模式，通常只需线性扫描因而可扩展、且定位明确，但只覆盖已知模式、且因缺运行时信息而存在误报）与形式化验证（模型检查分显式遍历，如检查 C 程序的 CMC，与符号式，如检查 C/C++ 的 CBMC，把行为表示为关于符号的布尔表达式交给求解器判定可满足性，但状态数随规模指数爆炸；以及定理证明式，如 seL4 内核与 FSCQ 文件系统先以数学定义程序行为与正确性规格、再交给 Coq 判定，代价是巨大手工投入、证明体积数倍于程序、程序行为与数学语句之间还需人来填补 gap），再到测试期（符号执行用路径条件与约束求解得到 x=11、y=12 这类具体输入，对大系统太贵；fuzzing 以反馈循环随机变异输入替代昂贵的代码分析，成本低、实现简单，但依赖随机性、缺乏推理，结构化与领域特定数据的变异难）。（YouTube EPSdQqTRR4u9I，[9-556]，L1）
