- 〔SREcon（推测）〕无发布分支的全自动发布流水线与监控门控。主讲人供职于公司基础设施团队（monitoring team，运维数千台监控服务器），介绍 continuous deployment：每次提交后最多两周内即上线到全球数百台完全自治的机器，采用 Debian 风格的 unstable/testing/stable 安装仓库（明确非版本控制分支）；隔离的 test cluster 以约 15 分钟周期跑合成负载，canary fleet 承接真实生产流量子集，并以 KPI（QPS、查询准确率、每输入工作负载内存占用、磁盘利用率、CPU 负载）对照容量规划上限作为晋升门控；曾因 upstart 的 fork 跟踪缺陷推出坏二进制，此后把"重启后正确二进制仍在运行"加入生产监控与测试集群规则。（YouTube EP-KL_L-MW8XA，[9.7-1076.4]，L1）

- 〔会议不详〕基于精确函数配对（precise function pairing，转写音作 preset）检测无序错误处理（disordered error handling）缺陷。主讲人 Qiu Shiwu（与 Aditya、Navid、Stephen、Kangjie 合作）指出错误相关代码由 cleanup 操作与错误处理两部分组成，此前工作多聚焦错误处理本身、基于函数名/NLP/模式挖掘的启发式配对查准率与查全率不佳且难以处理自定义函数；cleanup 调用缺失、冗余或顺序错误会造成 missing release、double free、double unlock、use-after-free 等缺陷，团队将这类缺陷统一定义为 disordered error handling bugs，并提出函数配对（leader/follower，如 Linux 内核的 kmalloc/kfree）是正确清理的关键。（YouTube EP-NyBgEqHQFw，[8.5-397.6]，L1）
- 〔会议不详〕error handling stack 与 error handling delta 推导函数对及评估。主讲人提出把一次执行路径上的函数组织成 error handling stack，对相邻两个栈做差（只考虑成功执行的函数、忽略出错点）得到 error handling delta，而 delta 恰为函数对（如 alloc1/free1、alloc2/free2），据此对比大量相邻栈批量收集函数对；再基于函数对检测释放顺序颠倒等 disordered 案例（栈式结构要求 free2 先于 free1），并通过依赖推理排除无害案例、检查不可行约束排除不可行路径。工具分析了三个常用系统级程序和库，识别出数千个函数对与数百个无序错误处理缺陷，查准率与查全率均较好。（YouTube EP-NyBgEqHQFw，[378.1-726.1]，L1）
- 〔会议不详〕SPADe：信号感知的 DAG 调度与动态供给。主讲人 Adam Lechowicz（转写音作 Lequitz，UMass Amherst 博士生，师从 Mohammad Hajiesmaili，转写音作 Hajjami Ali，与 Berkeley、MIT、Caltech 合作者共同完成）指出 ChatGPT 后数据中心算力激增、欧盟立法与电网并网约束都要求数据中心按小时级外部条件调整——需要"灵活性"，碳强度信号（加州电网午间光伏低谷为例）随时间剧烈变化；论文聚焦 Spark 等框架产生的 DAG 结构批处理作业的信号感知执行问题，核心洞察是 DAG 作业下调度与信号感知供给紧密耦合、需要一体化方法：利用 Decima/Graphene 等现有调度器的打分分布导出 relative importance 指标，并借鉴 online knapsack 的指数阈值函数设计快速过滤器，决定任务当前执行还是推迟并关停机器。（YouTube EP-Ov1bsM0E5o，[18.5-469.8]，L1）
- 〔会议不详〕SPADe 理论界、消融实验与评估。系统以信号感知参数 γ 控制激进度：γ→0 时不增加 makespan、匹配信号无关调度，γ→1 时保证最小活跃资源并给出最坏 stretch factor 上界，中间区间有实例相关界；消融实验 SAP（在信号无关 DAG 调度器外层套信号感知供给封装）证明解耦两个控制模块次优——同等节省下 SPADe 性能损失更小，因为它避免对关键路径任务施加信号感知。评估基于 Apache Spark、100 节点 Kubernetes 测试床与 Spark 调度仿真环境，信号用碳强度与 Google 集群功耗 trace，负载用 Spark TPC-H 与阿里云生产 DAG，基线为 Decima、Graphene 及其 SAP 适配版；结果显示 SPADe 碳足迹节省最佳，且节省幅度随电网可再生能源占比带来的信号波动而变化。（YouTube EP-Ov1bsM0E5o，[469.8-917.0]，L1）
- 〔SREcon（推测）〕Slack 入口负载均衡从 HAProxy 迁移 Envoy 的翻车复盘（上）。主讲人 Radha（Slack 资深工程师，负责 ingress 负载均衡、TLS 与服务网络）介绍团队 2019 年启动迁移、"两年零十五天"后正式完成，并复盘迁移中的 oops 时刻：其一，Envoy retry_on 配置把 connect-failure 误写为 connect_failure，而当时 Envoy 对未知值静默忽略、envoy validate mode 校验通过导致漏检，连接失败重试缺失；该行为在 Envoy 1.11.0 修复后，团队同步修正配置、测试并在配置生成库中显式枚举合法值、遇未知值报错。其二，客户约 25% 请求收到 404：客户端在 HTTP Host 头中附带了默认 SSL 端口（HTTP 规范允许），而 Envoy 仅按主机名匹配路由（HAProxy 时代无主机路由、全量转发），团队先回滚再改为同时匹配 host 与 host:port。（YouTube EP-hA7pYGR2N4，[9.3-361.3]，L1）
- 〔SREcon（推测）〕翻车复盘（下）与迁移经验。文件流量 5xx 升高的根因是 HAProxy 配置了连接失败重试 3 次而 Envoy 为 0 次，补齐重试即恢复正常；最棘手的问题是所有 Slack 客户端每个 API 请求额外增加 12% 延迟，指标全局无区域细分、无错误信息可查，开启 Envoy 层追踪后定位到耗时发生在请求处理开始之前（TLS 阶段），最终发现 TLS session ticket keys 未在所有 Envoy 间同步轮换，客户端带着未知票据回退完整握手，确保同步轮换后延迟恢复。经验总结：先对等后增强（parity first，复制整个 HAProxy 配置并逐特性建 ticket、文档与 ticket 均需同行评审）、保持回滚方案快速简单（DNS 切换加 Terraform 流水线仅需几分钟）、迁移前向业务沟通风险与回滚计划；超过 95% 配置变更用 curl 测试，并以 envoy validate mode 与综合测试守护无效配置。（YouTube EP-hA7pYGR2N4，[361.3-765.5]，L1）
- 〔USENIX Security〕Return of Bleichenbacher's Oracle Threat（ROBOT）。主讲人（研究由 Hanno 对多台主机的初步扫描发现 Facebook 服务器异常而启动，与 Hanno、Craig 合作）回顾 1998 年 Bleichenbacher 对 TLS RSA 密钥交换中 RSA PKCS#1 v1.5 填充的自适应选择密文攻击（亦称百万消息攻击）：服务器以可区分的告警响应充当预言机，攻击者逐步解密 premaster secret；规范层面的对策是永远返回相同告警。团队发现 Facebook 服务器对无效 ClientKeyExchange 会依据消息内容响应 illegal_parameter 或 bad_record_mac 两种告警，进一步用 Bleichenbacher 攻击以 Facebook 私钥签名了一条带其姓名首字母的消息（网页提供校验脚本，经证书透明度日志验证）；随后 Craig 发现省略 ChangeCipherSpec/Finished 消息时服务器以 TCP RST 与超时区分消息有效性，构成新旁路并再次实施攻击，两次均获 Facebook 漏洞赏金。（YouTube EP037D7YZCpSM，[10.7-736.5]，L1）
- 〔USENIX Security〕全网扫描、责任披露与建议。团队扫描约一百万重要主机中的子集，发现 2.8% 存在漏洞，且 PayPal、Apple、eBay、Cisco 等高知名度站点大多中招；不同实现呈现 TCP 复位/超时与 illegal_parameter、bad_record_mac、handshake_failure、internal error 等告警的多种组合，甚至出现"无效消息发两条告警"这类伪对策。责任披露困难：有厂商回复"我们用军用级加密所以安全"，Cisco ASA 设备（转写音作 ACA）仅支持 TLS RSA 且以停止支持多年拒修，F5 五台服务器竟有五种不同漏洞响应；团队向 SSL Labs、testssl.sh、TLS Fuzzer 等测试工具开发者提供扫描脚本，SSL Labs 自 12 月起上线 Bleichenbacher oracle 检测。建议禁用 TLS 1.3 中已移除的 TLS RSA 密码套件，改用椭圆曲线或 RSA-OAEP（转写音作 RSA OPE）；Q&A 讨论了开发工具缺失是厂商不修的主因、TLS 实现指纹识别可绕过网站管理员直接找厂商，以及 Facebook 签名仅为叶证书消息、不能签发子证书。（YouTube EP037D7YZCpSM，[736.5-1445.5]，L1）
- 〔USENIX Security〕AuthenCall：电话呼叫的高效身份与内容认证。主讲人 Brad Reaves（转写音作 Brad Reeves，北卡罗来纳州立大学助理教授，与佛罗里达大学的 Logan Blue、Hadi Abdullah、Luis Vargas、Patrick Traynor、Tom Shrimpton 合作）以美国大选期间 DNC 遭攻击时 FBI 多次来电被 IT 人员当作恶作剧、每月数十亿 robocall、IRS 诈骗与 swatting（谎报枪击诱发出警）为例，指出电话网络安全的根因是身份只被断言（asserted）而非证明（attested）：信令协议在网关处改变、无保证的共享数据路径、呼叫音频在传输中被合法修改。方案 AuthenCall 不改造核心网，而是经辅助数据信道端到端密码学认证呼叫双方与内容：证书签发协议由 CA 回叫用户并经双音多频（touch tones）发送第二个 nonce 完成质询，全程软件自动化、证书有效期可短至一至两周；呼叫协议由中央服务器协调双方，向呼叫方告知对方是否为 AuthenCall 用户以防"接听后否认"的社会工程攻击，且消息不包含对方是否可用/在线等信息。（YouTube EP06AHMYwPdDY，[10.7-857.1]，L1）
- 〔USENIX Security〕AuthenCall 性能、音频鲁棒摘要与问答。系统仅给呼叫建立增加 1 到 1.5 秒（发生在振铃期间；常规电话信令本需 5-7 秒），针对带外认证引入的竞态（攻击者经电话网络并发呼叫使客户端无法区分），需把语音与数据信道绑定以保证活跃性与内容完整性；采用信号处理中的 robust digest 技术，用 RSH 把 1 秒音频压缩为 512 位摘要（30ms 窗口取 LPC 系数、密钥化伪随机选块做 DCT 取前 8 系数比较，重复 64 次）。实验显示正常网络传输前后摘要位错约 10-20%，而替换一秒音频位错约 50%，两类可分：逐秒认证可检出 90% 攻击、误报率 0.5%（约每 3 分钟一次），放宽到 5 秒窗口（每 5 秒中 3 秒命中）可检出 99% 内容篡改攻击、典型用户约六年一次误报。Q&A 中 Ian Goldberg（滑铁卢大学）问及 CA 如何防止冒充 FBI 签发证书（依赖 CA 标准最佳实践与授权代表文件、首次签发非全自动）、CA 回叫号码的作用、认证与信令并发进行因而用户接听时间不影响协议，以及与 Signal/Telegram 等 P2P VoIP 认证系统的区别。（YouTube EP06AHMYwPdDY，[857.1-1710.4]，L1）
- 〔USENIX Security〕WPA2 形式化分析：从 KRACK 到计数器破解的裂痕。主讲人 Niklas Medinger（转写音作 Meininghaus，与 Benjamin Kiesl、Cas Cremers（转写音作 Krebers）合作）在 USENIX 会议开场报告中讲解 WPA2 四次握手（ANonce/SNonce、replay counter、PTK 与 GTK）：2017 年 Vanhoef 与 Piessens 的 KRACK 攻击利用四次握手消息重传，诱使客户端重装 PTK 并把 nonce 复位为 0，在认证加密方案中 nonce 重用导致密钥泄露、后续流量可被解密。（YouTube EP0A-wIt2lsvY，[9.0-350.3]，L1）
- 〔USENIX Security〕Tamarin 形式化建模与证明结果。WPA2 的 sleep bit 与 WNM sleep mode（转写音作 WM sleep mode）等省电机制会与握手交互，直觉不可信，团队用 Tamarin prover 对标准中的七个状态机（四次握手、组密钥握手等）建模，并精化密码学规则以忠实刻画 nonce 重用导致的密钥泄露，估计耗时约 12 人月、大半花在阅读三千页标准上；借助大量引理（部分需在 Tamarin 图形界面中手工证明）证明了 PTK 与 GTK 的安全性及四次握手的认证性。分析覆盖了既有形式化工作未涉及的密钥泄露与省电机制等交互，推论是打过两次补丁的 WPA2 在 PTK 上不存在 KRACK 攻击，WPA2 由此加入 TLS、5G 等已形式化验证协议行列；模型已通过 USENIX artifact evaluation 并在 GitHub 开源。（YouTube EP0A-wIt2lsvY，[350.3-691.3]，L1）
- 〔NSDI（推测）〕NanoPipeline：缓解复杂数据平面应用的 CPU 前端瓶颈。主讲人 Yi Han（合作者来自西安交通大学，转写音作 Xiangjiang University 的 Xianzhou Tong 等）指出防火墙、软件路由器、负载均衡等演进出的复杂数据平面应用（CDPA）吞吐受限，剖析发现其 IPC 显著低于基于 Click 的简单应用，top-down 微架构分析显示最大瓶颈在 CPU 前端（平均 45.1%）；根因是逐包完整处理的经典模式使长处理路径远超 i-cache 容量、造成持续 thrashing，而代码布局聚合与死代码删除/编译器提示两类既有方法在长路径下均无效。团队的核心洞察是重定义执行路径：让前一个包在处理完成前挂起，i-cache 中留下的指令可被后续包复用，恢复时剩余指令仍能命中缓存；据此构建 NanoPipeline——离线分析器注入 scheduling sites 把代码划分为不超过 i-cache 容量的阶段，运行时调度器保存上下文并在包间切换，以流水线方式调度且不修改原生代码语义。（YouTube EP0DQdjUw-Tdg，[18.5-509.1]，L1）
- 〔NSDI（推测）〕语义一致性与调度效率两大挑战及评估。乱序控制流会破坏变量值：团队把变量分为 per-packet（非指针函数参数、栈变量，各有私有栈保存恢复）与 cross-packet（全局变量）两类，在 LLVM IR 层用数据流分析标出读写引用并构建 commitment window，未落入任何窗口的 CFG 边才允许放置 scheduling sites，从而严格保持原程序语义；针对 CDPA 代码比 i-cache 大一两个数量级、单包命中调度点上百次而抵消收益的问题，采用 profile-guided 划分（采集真实 trace 中各块的 cache line 消耗与端到端时间、识别最频繁路径），大幅减少所需调度点。评估显示 NanoPipeline 为代表性 CDPA 带来 17%-30% 吞吐提升；与按流重排包以优化 D-cache 的 Reframer 对比说明优化应对准真实瓶颈，布局优化几乎无益甚至更差；优化后 i-cache misses 大幅下降、retired 周期占比与 IPC 上升。（YouTube EP0DQdjUw-Tdg，[511.4-1009.0]，L1）
