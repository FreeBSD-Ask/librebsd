- 〔会议不详〕HPB Valve 的两项体验中心技术。由于后台应用运行时间更长、引用更多，HPB 缓存的其实是次要的后台条目，前台应用在启动初期因此遭遇大量 critical miss，形成优先级反转；另一根因是内存压力无感知的固定计时回收（例如二十秒未引用即逐出），系统内存紧张时 HPB 并不会释放内存，只能由 LMKD 杀应用——作者在示例中展示了内存压力持续数秒时 LMKD 连杀应用、而 HPB 只在压力消失后才逐出无效条目的过程。据此作者提出 HPB Valve，由五个关键模块组成：Android 平台上两个监控模块采集应用级信息与内存压力状态并上报给内核中的 HPB manager，设备驱动层另有三个模块以体验为中心管理 HPB 内存——前台区应用优先的缓存策略在用户最近最常使用的前台应用启动时预取其重要 L2P 条目以消除启动初期的 critical miss，动态大小调整则在 LMKD 选定受害应用之前先逐出低优先级条目。结论部分说明它对所有应用都把用户感知时延做到与理想情况几乎一致，总被杀应用数下降 25%、并阻止了约 70% 的高优先级应用被 LMKD 杀掉，未来工作是把该思路扩展到设备侧 SRAM 的 L2P 缓存。（YouTube EPWUh3AaSdKcQ，[602-1191]，L1）
- 〔NSDI〕把现成服务二进制原地升级为容错服务。报告人（MSR 的 Tardigrade 作者，开场致谢 Li Dang（音写存疑），转写中未自报姓名）以 FDS 元数据服务的单点故障切入：单台服务器一旦失败整个集群即不可用，作者团队写道当然该补上 Paxos 选主，但研究者总有别的事、甚至转去别的公司，很多服务也就这样留着一处已知缺陷；把既有服务改成容错有两条路——重写成确定性状态机做状态机复制，或调用可靠后端持久化状态，二者都费时、易错且需要大量调试，因此他的主张是直接拿二进制来改造。他回顾了异步虚拟机复制（Remus，七年前在 NSDI 发表）：主备两侧同跑一份虚拟机，增量同步状态并用输出缓冲阻塞尚未确认持久的输出以保证一致性；代价是客户端时延，同一 LAN 上 ping 的 p50 约 43 ms、p99.9 约 88 ms，随着病毒扫描与索引进程加入可升到 276 ms，而一旦启动 Windows Update 或 dedup 之类后台进程，时延可达数秒。于是他提出 LVMR（lightweight VM replication），以 Bascule 这类轻量虚拟机为边界、在库操作系统与宿主之间插入检查点层，原型名为 Tardigrade；为保证在不可靠故障检测器下的一致性切换他选用 vertical Paxos，并列出 LVM API 需要的四项能力——细粒度跟踪脏页以做增量、能静默并抓取所有线程状态、能通过重放 API 调用在备机重建宿主状态、且调用需确定或可再生；由于 Bascule 不支持暂停并检查其他线程，作者改用逐线程注入异常并注册处理器来抓取线程快照，对长时间同步调用则向 wait/select 等待列表插入一个额外事件描述符，让等待在需要检查点时返回。（YouTube EPWVKlhlG_Vdk，[10-895]，L1）
- 〔NSDI〕检查点的具体解法与实测时延。对 stream open 这类无法打断的长耗时同步调用，作者采用预检查点——在调用真正开始之前就抢占式保存线程状态；对 create semaphore 返回文件描述符这类非确定性，用间接表把句柄虚拟化，让 guest 只看到虚句柄并在备机上翻译成宿主实际给出的值。作者还指出网络 API 只暴露套接字而把 TCP 会话状态留在宿主操作系统里，检查点层无法捕获或再生，失败切换后只能把它暴露为连接断开——这是他给 API 设计者的一条教训：把宿主状态推给 guest 之外会直接损害可复制性。实测方面，同一 ping 场景下基线时延仅约 12 ms，外部进程几乎不再影响结果，仅由服务自身脏页引发的检查点时延为 9 到 15 ms；当服务的脏页速率超过约一半网络带宽时，客户端时延才会超过 100 ms。作者据此给出四条结论：无需改动源码即可让既有二进制变成容错服务；正确做法是复制轻量虚拟机而非整机；LVM API 设计者必须考虑可检查点性；以及 LVMR 并不适合所有服务，它面向的是能容忍少量额外时延、负载适中且脏页速率远低于网络带宽的服务。（YouTube EPWVKlhlG_Vdk，[904-1790]，L1）
- 〔会议不详〕通过直接变异生成器程序来构造结构化模糊输入。报告人未报名称，先用 unzip 配 zip 文件讲清典型模糊测试：以覆盖率为反馈信号，因为未覆盖的代码找不到 bug；但遇到魔数、CRC 校验、加密或签名等硬约束就会失败，翻位无法修复一个已失效的签名。应对手段有污点跟踪——找出输入中影响某条比较指令的位并集中变异；以及符号执行——把当前程序状态形式化后求解出合法输入，但在密码学哈希或加密面前无能为力。作者由此观察到两种方法都在从目标程序中提取领域知识，于是反过来利用程序里已经存在的领域知识：把模糊引擎换成第二个程序即生成器（对 unzip 而言就是 zip），让它产出完全合法的输入，再对生成器程序本身注入故障——在参与输入到输出转换的 load 与 store 指令上施加位掩码，从而在生成过程中引入变异、得到一份被合法变异过的输出文件。（YouTube EPWWWvWVS9ZHc，[8-335]，L1）
- 〔会议不详〕FastStructure 与 AFL++ 的组合、评测与结论。作者同样用覆盖率反馈判断对生成器的变异是否值得保留；因为故障可以注入在加密或签名发生之前，他还能生成仍通过加密、甚至仍然有效签名的输入。代价是同时运行两个程序、吞吐比只跑一个程序低，所以原型 FastStructure 负责生成高质量种子、再交给 AFL++ 做常规位翻转以进一步扩展覆盖。评测覆盖十个程序对、包含不同的障碍类型（如不设校验的 opt dumb、以及用 RSA 密钥而常规模糊器难以穿透的 OpenSSL gensrl 与 rsautl）；对 png2png（随 libpng 提供、PNG 自带 CRC 因而难以用现成工具生成合法样本）它优于包括由符号执行驱动的 Z3C3 在内的对手，而且与 AFL++ 覆盖的基本块集合并不重叠、二者组合后协同显著；对 7-Zip 压缩加密模式同样优于相关工作，而 SimpCC 因无法编译目标程序直接缺席。作者据此总结：借用生成器程序里现成的领域知识、直接变异生成器，可以在不依赖重量级程序分析的前提下生成复杂模糊输入，其能力上限只由生成器本身决定。（YouTube EPWWWvWVS9ZHc，[338-660]，L1）
- 〔会议不详〕用故障注入剖析 OpenStack 的容错缺口。IBM Research 与密歇根大学的合作研究由发言人代讲（第一作者为密歇根博士生 Xiaowen Zhu，本人未能到场）；作者先是亲历一次安装：数天翻日志终于让 OpenStack 跑通并能创建虚拟机，挂上基准测试过夜后回来集群整体陷入坏状态，由此决定研究这一层新软件。他说明云管理栈的地位（IBM SmartCloud 与 Amazon EC2 之外，私有机密场景仍需要自有云）并界定容错能力——系统在故障下仍保持正确功能，故障类型只取服务崩溃、短时无响应与网络分区三类简单情形，目标版本是 Essex。方法是改造 OpenStack 日志框架以跟踪外部请求，在干净环境中重放请求生成执行图（节点是 identity、image、compute 等服务组件，边是 REST 调用、AMQP RPC 或 SQL 访问），沿图在预定位置注入故障，再用两个信号判定故障是否真的暴露为问题：一是系统返回给用户的输出，二是内部状态规范（例如某虚拟机在运行时其网络必须已注册）。首批结论之一是 OpenStack 开箱并无高可用与自动故障切换，数据库等单点遍布全系统。（YouTube EPWYhkV9JRhe4，[9-768]，L1）
- 〔会议不详〕具体缺陷、结论与现场讨论。作者列出的问题包括：超时机制不完整——compute 服务只要能联系上 image 服务就假定其健康，若分区恰好发生在 image 服务回复前，请求会无限期等待；跨层协调失序——OpenStack 自有包装层与底层 QPID 客户端库反复互相重试，下层报连接损坏、上层说再试一次，二者如此空转永远无法完成请求；底层 select 在套接字已关闭时返回错误而非有效描述符，库层却仍按可读处理；以及缺少周期性清理——过期镜像长期堆积直到磁盘塞满，调度器崩溃后虚拟机会永久卡在 BUILD 状态且重启后不检查挂起操作。作者据此认为若要用 OpenStack、CloudStack、Eucalyptus 这类软件，容错能力必须内置，并希望以工具与渐进迁移的方式从现状过渡到容错架构；问答中他说明只增加日志的开销约 1% 到 2%，而故障重放因给每次 RPC 加锁步开销巨大、只能离线跑，另有听众借 Tom DeMarco 讲述的 Tektronix 数字示波器“工程师没意识到 bug 是被允许的”轶事，追问如何把责任上推到上游设计而非事后打补丁。（YouTube EPWYhkV9JRhe4，[773-1527]，L1）
