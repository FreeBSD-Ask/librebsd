- 〔会议不详〕binlog 订阅、Kafka 分发与嵌入式缓存注入的实现与效果。由于变更无单一代码入口、update where 语句的受影响行不可知，而触发器会拖慢峰值超百万次/分钟的事务，团队转而消费 MySQL binlog 流（以全局事务 ID 保证至少一次送达），自建 binlog 服务并行处理、按表过滤路由，经 Kafka 反向分发至前端，并以约一天的 Kafka 事务窗口叠加 MySQL 复制作基线；在前端服务内嵌 Kafka 消费者将变更直接注入缓存、跳过 DB 与缓存读取，从而可增大乃至移除 TTL；效果上变更到达全球数千台机器平均仅 2-3 秒（原为分钟级），关闭该特性时更新次数仅增约 10% 但机器负载激增 30%，binlog 服务宕机期间前端数据库查询量显著上升。（YouTube EP2ZVo7SVWQac，[820.8-1658.6]，L1）
- 〔会议不详〕通过架构接口（UMONITOR/UMWAIT）构建微架构侧信道。讲者（与 Taesang Kim、Daniel Weber、Michael Schwarz 合作）指出传统侧信道依赖高精度计时器且测量本身会破坏内部状态产生盲区（blind spot），提出改用 Intel 自 Tremont/Alder Lake 起提供的非特权指令对 UMONITOR/UMWAIT 作为架构化接口；实验证实唤醒基于物理缓存行的缓存一致性状态（写别名地址无差异、行内任意偏移写均触发），且未文档化的瞬时写（transient write）也会唤醒 CPU，据此构建带 carry flag 反馈的瞬时写监控（transient write monitor）原语，re-monitor 阶段约 175 cycles、盲区率每轮低于 0.2%。（YouTube EP2X4TYi-e9kk，[8.3-375.4]，L1）
- 〔会议不详〕由该原语扩展出定时与中断监控原语并给出三个案例研究。利用 OS 定义超时（Linux 默认 100000 cycles）特性，攻击者以双逻辑处理器加 nop/mfence 串行化填充区分事件快慢（缓存命中与缺失给出不同 carry flag），并把原语的误报转化为中断监控原语（统计 retired UMWAIT 次数），指出 AMD（MONITORX/MWAITX）与 ARM（WFI）也有类似非特权指令；案例包括结合 gadget 的 Spectre 泄漏（速率可达 200 kbit/s）、与 Flush+Reload/Prime+Probe 同样确定性的缓存攻击基准，以及在 Intel/AMD/ARM 设备上对 top 100 网站约 70% 准确率的网站指纹攻击，代码已在 GitHub 开源。（YouTube EP2X4TYi-e9kk，[349.3-661.4]，L1）
- 〔OSDI（推测）〕分布式系统静默语义违约（silent semantic violation）实证研究。讲者以 exactly-once 消息交付、n 副本持久化、watch 回调等语义承诺引入问题：系统正常运行却无显式错误信号地破坏语义，后果灾难性且用户被表面正常行为误导；团队对 9 个代表性分布式系统的 issue tracker 抽样 700+ 用户报告故障，确认 268 起静默违约并深入分析 109 例，发现其约占全部用户报告故障的 40%（MongoDB 因 2014 年起加 production assertion 比例最低）、68% 案例违反的语义自首个大版本就存在（如 ZooKeeper ephemeral node 语义自 2008 年沿用却十四年后仍被反复违反）、73% 案例有测试覆盖但缺触发要素，并区分 short-lived 与 long-lived 语义（67% 失败违反后者）。（YouTube EP3IxMR8NYe9s，[15.0-464.1]，L1）

- 〔FAST（推测）〕三大教训：被动加热、集群级磨损均衡与管理层根因。提出 passive heating——空闲 SSD 长时间受热邻居（同节点热 SSD 或同机架热节点）影响导致 RBER 累积并转化为 media error，DC4 因两种服务混部同机架使某 SSD 媒体错误率翻倍，实验显示持续加热后整盘读 RBER 达 57%，而每 4 小时主机级周期扫描可降至约 1%，进一步建议把扫描下沉进 SSD 内部（FTL 已知温度、refresh 能力与 NAND 质量）；块存储一世代架构因用户 LBA 到三副本物理 SSD 的静态映射与就地更新导致集群级磨损不均（CoV 25%），二代日志结构设计降至约 5%；另发现 faulty cable 比换 SSD 更常见（auto DMA CRC 错误与其强相关），约 20% 故障源于人为插错槽位，提出一接口一用途（M.2 系统盘、SATA 数据盘）。（YouTube EP3tZbxf22glM，[400.3-1067.6]，L1）
- 〔EuroSys（推测）〕NROS：用节点复制（NR）黑盒化解决多核内核的同步复杂性。犹他大学博士生 Ankit 介绍（与犹他、UBC、VMware Research 及 EPFL 合作者）内核因手工内存管理、类型不安全与异步事件处理而难写对，粗粒度大锁在 4 路 96 核帧插入基准下吞吐比单核低近百倍，而 Barrelfish 式 multikernel 放弃共享内存又把复杂性转移到用户态；NROS 在每个 NUMA 节点维护一份内核副本（虚拟内存、调度、内存文件系统），以共享操作日志同步副本并保证可线性化，使所有内核状态访问 NUMA 本地化、避免跨节点 QPI 流量。（YouTube EPBNlsYHxcahQ，[8.8-329.3]，L1）
- 〔EuroSys（推测）〕NR 实现细节与 CNR 可交换扩展的性能评估。NR 以 B 树元数据加 radix tree 页表、优化读写锁加 combiner 线程批处理实现黑盒并发：Memcached 在 NROS 上比 Linux 快 31%、页表遍历省 36% 周期，帧插入基准在大核数下吞吐稳定、比 Linux 高近百倍但仍不及 Barrelfish（10x）与 SV6（约 100x）；扩展为利用可交换性的 CNR——多日志加开发者提供的 log mapper（按 PML4 条目划分页表，每 512 GB 区域独立日志/combiner）后 CNR VMM 超过 Barrelfish 且首 socket 与 SV6 相当，论文另讨论副本内存耗尽、MMU 读取未应用日志、TLB shootdown 与延迟等挑战，项目网站 nrkernel.systems。（YouTube EPBNlsYHxcahQ，[329.3-883.7]，L1）
- 〔USENIX Security〕空指针解引用（NPD）修复需要上下文检查（ConQ）。George Mason 大学的 Yun Dongxing 介绍其 USENIX Security 2024 研究综述：NPD 被利用可导致 DDoS、资源泄漏、任意代码执行与系统崩溃，SOTA 方案 VFix 等采用 generate-and-validate 流程并按预定义 if-check 模式修补，却忽视宝贵上下文信息而产生错误补丁；三类示例分别为过程内 volatile 资源（已分配内存、持有的锁）未释放导致资源被永久占用、需重置的函数参数未重置引发调用方逻辑混乱、以及 void 函数直接返回使漏洞向调用方传播；ConQ 据此在补丁生成中考虑过程内状态回退、函数参数重置与 caller 评估。（YouTube EPEf3a00Cn4g0，[7.8-265.0]，L1）
- 〔USENIX Security〕ConQ 四步流水线与真实 CVE 评估。流程为 NPD 上下文图构建（过程内 CFG 加一跳 callee，以分离逻辑定位 null/error 位置并简化 CFG）、路径敏感修复位置选择（一节点一错误、多节点一错误等四类）、初始补丁生成（null/异常值/非空检查构造、基于从 CVE 记录与开源仓库收集的函数对数据集做内存与锁释放配对、按函数类型构造返回语句）、跨过程状态传播生成最终补丁（重置全局变量与函数参数加 caller 评估）；在 80 个真实 NPD 漏洞与 Defects4J 的 18 个 NPD 错误上对比 VFix、NPD-Fix、SimFix，分别生成 68/16 个正确补丁、优于 SOTA 超 26%，错误补丁均源于需专家知识的语义错误与上下文外的宏。（YouTube EPEf3a00Cn4g0，[265.0-667.1]，L1）
- 〔会议不详〕存储工作负载画像与缺失率曲线（MRC）基础。Coho Data 讲者（与 Coho 同事合作）指出存储层级日益深入多样（PCIe flash、PCM、shingled disk 层层叠加）使配置与在线数据放置决策困难，而理解工作负载的关键特征是重用距离：理想策略是 1966 年提出的按最短前向距离优先的最优替换策略，实践中退化为 LRU 按重用距离优先；MRC 即给定工作负载与替换策略下缺失率随缓存大小变化的曲线，对 LRU 而言 MRC 就是重用距离分布，MSR Cambridge 轨迹显示 MRC 随工作负载（硬件监控、Web 代理、SQL 服务器）与时间（首小时、12 小时、一周）剧烈变化，因此要在线决策就必须在线计算 MRC。（YouTube EPIBJ-vbat9MY，[9.8-590.0]，L1）
- 〔会议不详〕Counter Stack：次线性内存近似计算 MRC。Mattson 单遍算法时间复杂度已降到 O(n log m) 但内存 O(m) 不实用——MSR Cambridge 约 2.7 TB 唯一数据需 92 GB RAM；讲者提出 counter stack 数据结构测量时间上的唯一性（以 HyperLogLog 概率计数器为每个请求维护基数计数），相邻计数器的差分矩阵 delta X/delta Y 非零即重复引用、对应计数器值即重用距离；配合降采样（每 k 个请求）、剪枝（收敛计数器去重）与近似计数三种有损压缩，把同一 MRC 的内存从 92 GB 降到 80 MB，counter stack 流仅占 1–11 MB 磁盘，可在秒级查询离群点、相位变化并探索粗粒度调度（如挪动凌晨备份任务时间），已在 Coho 生产环境用于在线放置决策与扩容收益预测，低/高保真曲线均紧贴 Mattson 基准。（YouTube EPIBJ-vbat9MY，[585.4-1191.1]，L1）
