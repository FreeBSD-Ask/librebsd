# 321.4.82 〔会议不详〕透明超级页superpage管理的设计空间描述方案与系统洞见主讲人W

- 〔会议不详〕透明超级页（superpage）管理的设计空间描述方案与系统洞见。主讲人 Wei Shi 与莱斯大学 Alan Cox、Scott Rixner 教授合作，针对大内存应用的高地址转换开销，提出解耦超级页生命周期的五个事件（物理页分配、准备、映射创建、映射销毁、释放）的描述方案，并分析 Linux、FreeBSD、Ingens 与 Hawkeye 四个系统：Linux 在缺页中同步耦合分配/准备/映射、失败时主动压缩内存（激进而贪婪），Ingens 仅异步做三事件且阈值保守（利用率超 90%）、用轮转策略保证多进程公平，Hawkeye 采用与 Linux 相同的激进阈值并按 TLB 开销优先级排序，FreeBSD 用预留（reservation）系统追踪已分配物理超级页、缺页中增量准备并在最后一页完成时做 in-place 提升、尽量延迟释放。（YouTube EPDthSBUml3uY，[10-591]，L1）
- 〔会议不详〕Quicksilver 的设计与 FreeBSD 上的评估。洞见包括：三事件耦合仅在刚启动机器上最快、易造内存膨胀且增长堆的分配会失败；异步 out-of-place 提升可缓解延迟尖刺但页迁移干扰应用、延迟映射创建，性能反不如 FreeBSD 的 in-place 提升方案；预留系统支持推测性分配、多页尺寸与 in-place 提升，延迟部分释放可抗内存碎片，批量清零（bulk zeroing）可加速 2MB 页清零；Quicksilver 基于 FreeBSD 预留系统在首次缺页时推测分配，采用先增量后异步全量准备的混合策略并以 bulk zeroing 加速，用后台守护进程回收不活跃超级页；评估显示 Sync1/Sync64 变体在新机与重度碎片场景下匹配或超越 Linux（page rank 任务快两倍以上），Redis 服务端工作负载在 frag0 到 frag100 碎片度下吞吐与尾延迟几乎不变，Sync64 更适合长时运行服务器以避免数十万低利用率超级页。（YouTube EPDthSBUml3uY，[591-1182]，L1）
- 〔FAST（推测）〕去重存储系统的内存高效批量清洗（bulk sanitization）。主讲人与 Data Domain 合作工程师共同完成，目标是把存储系统恢复到“机密信息事故从未发生”的状态：清洗需符合 NIST/DoD 指南的 clearing（至少覆写一次）与 purging（消磁或销毁）两级要求，而加密清洗（每文件一把密钥、销毁密钥）在块共享与快照场景下密钥管理困难、牺牲读写性能且不被指南接受；既有威胁模型复用 casual 攻击（经 NFS/CIFS 普通接口）、robust 攻击（读取未分配/直接块）与 laboratory 攻击（专用硬件探测磁盘磁化状态）；去重存储以 fingerprint-chunk-container 的日志结构组织，大规模系统有数千亿 chunk，全内存存引用每块需 160 bits，Bloom filter（误报率百万分之一约需 28.76 bits/chunk）因误报可能遗漏而不可用，作者选用完美哈希（perfect hash）把内存降至约 2.54 bits/chunk，将索引分桶并按平均 16K fingerprints 组成 perfect hash bucket 逐桶构建完美哈希向量。（YouTube EPDwmhUjKdTEM，[10-730]，L1）
- 〔FAST（推测）〕五步 mark-and-sweep 清洗流程与读写模式支持及评估。流程为：merge 阶段确定 key space、取一致性点 CP0 并冻结镜像；analysis 阶段并行构建完美哈希向量（线性构建、常数时间访问）；mark 阶段枚举全部文件标记存活引用；sweep/copy 阶段对含死引用的 container 复制前进，最后清零空闲块及 swap 等受影响区域；支持写入需处理复活（resurrection）问题——去重引擎逐 fingerprint 通知清洗进程、按 container ID 是否落在哈希结构覆盖区间决定翻转位，并取第二个一致性点后分两步枚举（CP0-CP1 差异文件的小集合承受随机索引 I/O，CP0 无需索引查找）；在 16 核、可用容量约 130TB 的机器上以内部备份负载工具评估，无去重清洗吞吐约 7031 MB/s，去重因子 7.38x 时达 5.06 GB/s（加速约 7.1 倍、随去重因子近线性扩展），与数据摄取并发时二者各保持 45-70% 峰值吞吐（清洗偏 I/O 密集而摄取偏 CPU 密集）；结论称该功能是合规销售的关键，也可视为去重系统的垃圾回收器，问答中 Seagate 的 Dave Anderson 指出最新版指南已明确认可加密清洗。（YouTube EPDwmhUjKdTEM，[730-1751]，L1）
- 〔会议不详〕HAS：面向分布式 LSM 树键值存储的整体自动化任务调度。主讲人为高校教师，代因签证未能与会的第一作者学生报告，针对基于 Cassandra 的分布式键值存储指出延迟波动的两大根因：分布层负载均衡不高效、存储层前台读与后台压缩（compaction）任务相互干扰；在 10 节点同构三副本玩具集群上即便启用 Cassandra 的 dynamic snitching，最大/最小延迟比仍达 4.24 倍，单节点 30 分钟开关压缩实验中吞吐从 26.3 kops 跌至 7.3 kops，说明不能简单重实现压缩而应与读任务协同调度。（YouTube EPE00yL847NSk，[0-467]，L1）
- 〔会议不详〕HAS 的三项技术与评估。coarse-grained re-task assignment 扩展 Cassandra gossip 协议共享延迟信息并用 Raft 保证调度节点容错（100 节点三副本通信开销仅 15.2%），fine-grained re-task coordination 用类似 dynamic snitching 的 score 计算重路由读请求，compaction task scheduling 在 replica decoupling 后按读负载比例分配压缩率；基于 Cassandra 5.0、用 YCSB 与建模的 Facebook 生产负载评估，HAS 对比最先进的分布式 LSM 树存储可将 99 分位延迟分别降低 58.6% 与 59.9%，同时提升吞吐并压缩误差棒，代码已开源。（YouTube EPE00yL847NSk，[467-924]，L1）
- 〔会议不详〕名称碰撞（name collision）：跨大小写敏感文件系统的陷阱与安全后果。主讲人为最后一年的博士生（未给姓名），研究方向为系统、文件系统与内核安全，把大小写混用引发的攻击归入 name confusion attacks 谱系（别名导致符号链接遍历、时序竞争导致文件 squatting）；从大小写敏感卷把 foo/Foo 迁入大小写不敏感文件系统时二者只能存其一或发生内容覆盖；背景涵盖 Linux 内核 5.2 为 ext4 引入目录级大小写不敏感（casefold）、Linux 上的 FAT/JFS/ZFS 与大小写不敏感 tmpfs 补丁、跨大小写边界的 WSL，以及 Git 2021 年符号链接与目录名碰撞导致任意脚本执行、2014 年 .git 目录经大小写变体写入版本历史的 CVE。（YouTube EPE2zznSP2nl4，[0-454]，L1）
- 〔会议不详〕碰撞检测、评估与防御。用系统调用轨迹中的 create-use 对（inode 相同而名称大小写不同）刻画碰撞，并基于 auditd 日志（路径遍历、inode 与设备号、PID、可执行文件）实现自动化提取，生成目录、文件与符号链接的各种组合驱动 cp、tar、rsync；结果显示合并目录时静默丢失文件、不同权限时错误元数据被覆盖、cp 在特定场景符号链接遍历写出目标目录、rsync 在父目录与子目录双重碰撞时把机密文件写到目标之外；防御上指出单靠程序不可靠、纯系统侧会误报，主张由程序向文件系统传达意图，如 openat2 族增加碰撞即失败的标志、canonicalize 系统调用返回归一化路径、以及查询两个名称是否等价的系统调用。（YouTube EPE2zznSP2nl4，[454-897]，L1）
- 〔USENIX ATC（推测）〕Electra：用 eBPF 加速分布式共识协议。哈佛、北大与康奈尔大学的联合工作，主讲人致谢 Ellen 的开场介绍；云应用（Apache Kafka、Hadoop、Kubernetes 依赖 ZooKeeper/etcd）所用的 Multi-Paxos 在内核网络栈上开销高，leader 每请求调用网络 API 14 次，CPU 剖析显示约 19% 花在用户态-内核态切换、25% 在内核协议栈遍历、合计约 44%；DPDK 等内核旁路存在安全与隔离风险、busy polling 不利于云内 CPU 共享且维护成本高，故主张第三条路——不修改内核代码、不重启地用 eBPF 运行时安全定制内核（SPIN、Exokernel、XRP 为先例），按“性能关键且简单的操作入内核、复杂操作留用户态”分工。（YouTube EPE6qcR2Lb1xE，[0-484]，L1）
- 〔USENIX ATC（推测）〕Electra 的三项 eBPF 定制与评估。在 TC 钩子用内置的包克隆 API 实现消息广播（一次 send、一次上下文切换），在 XDP 用驱动层环形缓冲实现快速确认，并在 XDP 维护以 bitset 实现的 quorum 信息、只放行达到法定人数的 ACK 以过滤多余接收；针对 eBPF 与用户态无共享内存的状态同步难题，用 detach 与 eBPF map 开关规避竞争；在 CloudLab 裸金属（Mellanox 网卡、不改 Linux、不用 IP 多播）上 Multi-Paxos 吞吐提升 2 倍、尾延迟降低 20%，上下文切换与栈遍历从 14 次降到 5 次，7 副本改进更多，性能约为 DPDK 方案一半，体现内核原生路线的取舍。（YouTube EPE6qcR2Lb1xE，[484-969]，L1）
- 〔会议不详〕InfiniDedup：可扩展且高性价比的云分层去重。主讲人来自位于波兰华沙、专长存储与分布式系统的研发公司（转写为 Nihilize Data），工作与其 HydraStore 一脉相承；现有云分层去重方案把全部元数据处理压在本地层，云层规模受限、多个本地系统之间无法去重，而云侧有存储分级与 spot 实例（约比常规实例便宜 10 倍）等降本手段；InfiniDedup 把去重做成云端批处理：只把文件配方（file recipe，即构成文件的块指纹列表）等元数据传到云端，与云端指纹索引比对后仅上传去重后的块，恢复可回到本地层（不重复下载本地已有数据）或独立位置，删除数据则在云端垃圾回收无引用块。（YouTube EPE72C3hkYW28，[0-413]，L1）
- 〔会议不详〕InfiniDedup 的批处理、云端结构与成本优化。批处理为分布式计算，按需拉起云实例并可用 spot 实例，数 PB 数据集几美元即可处理；把集群与数据规模同时翻倍后计算时间仍约 2 小时，呈线性扩展；云端把数据块放进容器（约 1000 块一个）以减少 put/get 请求，元数据分指纹索引与文件配方两类；垃圾回收按备份策略把到期日传播到单个块，只在重写容器有利润时执行，并据此在热/冷存储间混放（冷存储最短存储期 90 天、延迟同为毫秒级），由管理员预估恢复频率并加启发式预测未来引用，中间读写场景混放收益最大。（YouTube EPE72C3hkYW28，[413-827]，L1）
- 〔Black Hat（推测）〕跨容器攻击：云端被“迷惑”的 eBPF。主讲人来自乔治梅森大学（转写为 Yun Dongxing），论文由清华大学与乔治梅森大学合作；eBPF 已被云广泛用于网络管理、性能剖析与安全监控，但 bpf_probe_write_user 等攻击性特性可改写其他进程内存与系统调用（Defcon 与 Black Hat 已有 eBPF rootkit 演示），据此归纳三类 eBPF 跨容器攻击：本地容器逃逸、Kubernetes 集群攻击与云安全中心绕过，并发现一个新 CVE；容器内用户可借 eBPF 追踪特性探测其他容器与宿主，用 raw tracepoint 监控特权 bash 的 read 系统调用并注入恶意命令，还能取 libc 基址、离线组装 ROP 链推入受害进程栈，实现不依赖其他漏洞、在任何容器环境稳定的本地提权（LPE）。（YouTube EPE7E8Y20q9ZU，[0-337]，L1）
- 〔Black Hat（推测）〕现实影响调研与 CapBit 缓解。Kubernetes 场景中攻击者可滥用过度授权的 service account 分发 eBPF 恶意软件实施跨节点攻击、窃取其他 pod 的令牌，并阻止防御工具在用户态与内核态收集日志、经网络层拦截控制包构建隐蔽 C2 信道；调研发现 6 个真实在线服务启用 eBPF 且均可被攻击、Docker Hub 上超过 2.5% 的容器具备 eBPF 权限、四家头部云厂商的 Kubernetes 服务均可创建可被逃逸的 eBPF 容器，其中只有阿里云安全中心给出告警，Datadog 等知名工具也使用攻击性特性、存在供应链攻击风险；根源是 eBPF 只有一级权限且易随其他能力被无意启用，提出 CapBit 为每个进程增加属性位实现细粒度 eBPF 访问控制，开销接近 Linux 原生 capability 检查，而 LSM 方案开销超过 15%。（YouTube EPE7E8Y20q9ZU，[337-675]，L1）
- 〔会议不详〕SPHT：可扩展的持久硬件事务。主讲人 Daniel Castro，与 Alexandre Baldassin、Paulo Romano、João Barreto 合作；持久事务内存（PTM）需结合硬件事务内存（HTM）与字节寻址持久内存（PM），难点在于 HTM 事务内刷新 CPU 缓存会确定性中止，现有方案多以影子内存加日志重放解决（NVHTM、CCHTM、VHTM，Crafty 用非破坏性 undo log）；SPHT 采用影子内存路线并遵循数据库式的立即持久化（immediate durability）准则——事务返回应用时其自身及其依赖的前序事务必须已持久化；针对现有工作全局逻辑时钟引起伪中止、扩展 HTM 逻辑边界易冲突、关键路径串行化与串行日志重放浪费现代硬件资源等局限，主张不牺牲持久性的可扩展性。（YouTube EPE8J10_bZ1Hs，[0-371]，L1）
- 〔会议不详〕SPHT 的组提交与并行日志重放。NVHDM 为满足立即持久化让高物理时钟事务等待低时钟事务刷新 commit marker，并发越高等待越长；SPHT 的关键洞察是让最高时钟事务（如 T3）经 CAS 更新持久全局 commit marker，代表自 T0 至 T3 的整组事务，其余事务检测后把更新委托给它并安全免等；日志重放采用并行、NUMA 感知、写回与缓存失效指令以及链式日志（linked log，复用提交逻辑以低成本提示前/后继事务）；在 HTM CPU 加 512GB（仿真）PM 上用 STAMP 的 vacation 与 genome 基准评估，SPHT 可扩展到 64 线程、吞吐比 NVHTM 高 2.6 倍，其他方案在约 150 万事务/秒处遇到瓶颈，链式日志使日志重放在 16 线程取得 2.1 倍收益（vacation 为 1.3 倍）。（YouTube EPE8J10_bZ1Hs，[371-742]，L1）
- 〔会议不详〕面向移动文件系统 F2FS 的增量压缩（delta compression）。主讲人 Liping 来自台湾阳明交通大学（NYCU）；移动应用愈发 AI 密集、写入频繁，而闪存 P/E 周期有限，厂商向高密度 TLC/QLC 迁移后 QLC 限值仅约 1000 次，透明的写入减负可让应用继续写密集、厂商放心转向更便宜更大的高密度闪存；基于 F2FS（日志结构文件系统）的观察是 inode 的 inline area 占比大却常被闲置，负载分析显示约 90% 文件未用完 inline area 指针、约 80% 写为更新且增量极小，SQLite 与临时文件是小增量主要来源，inode 在页缓存中缓存良好、落盘前可累积多个小增量；现有 inline files 方案适用文件少，常规压缩的压缩比依赖数据模式并增加设计与读写开销。（YouTube EPE9Ci0X38jWY，[0-541]，L1）
- 〔会议不详〕DCI/DCM 设计与评估。DCI 在块写时判断是否更新及增量大小，用 XOR 比较原数据与新数据得到含大量零的差量，经游程编码或 LZO 轻量编码后嵌入 inode inline area，并限制基块最多挂一个增量以控制读放大；inline area 溢出时按 FIFO 或“长期 I/O 效率更好才替换”的原则做增量替换，被逐出的增量交给 DCM 存入常规块（meta page、meta block、compact block），且只服务经聚类识别的读写热文件；一致性靠“基块先于增量块、再先于 inode 落盘”的写序避免悬挂增量；实测平均削减超过 50% 写流量、换算寿命延长超过 100%，写 I/O 延迟降约 30%，读延迟也因调度队列争用缓解而改善。（YouTube EPE9Ci0X38jWY，[541-1082]，L1）
