- 〔HotCloud〕空间与时间变异性实测、在线学习权重、保证转换与放置评测。动手前先去收数据：从 HP 云服务顶架交换机上的 sFlow 数据里，为每个应用每小时得到一份流量矩阵，每个元素是两台虚拟机之间发送的字节数，整场报告都以一小时为周期展开〔06:00〕。空间变异性的量化很直观：设 F_ij 为从虚拟机 i 到 j 的租户流量占比，当所有 F 值相等时变异系数为零，当只有两个不同取值时是一，取值很多时大于一，他们用的度量就是这组 F 值的标准差除以均值〔07:13〕。结论是应用展现出高空间变异性——绝大多数取值大于一，部分高达一百；用类似方法量化的时间变异性同样偏高〔08:01〕。她判断今天的客户不会自己去建模这么大的变异性，这足以支撑不做结构假设、做更通用预测这条路线。预测器本身很简单：预测是过去若干个矩阵的线性组合，每个历史矩阵带一个权重，权重越高影响力越大；关键设计是不预设权重而是在线学习，于是每次做出预测后都能根据误差调整权重函数——取上一轮的权重乘以一个损失函数来纠正误差，再归一化，权重本质上是时间的函数〔08:37〕。她同时声明自己并不是在证明这是史上最好的流量预测算法。第一个评估看预测精度，对比对象是一个受 SIGCOMM 那类刚性应用模型启发、需要客户自己输入参数的系统，她为公平起见用了 oracle 方法挑最优参数并允许其随时间变化，同时看 L2 范数误差与相对误差——相对误差能区分过高与过低预测（她最在意的是低预测，那会直接拖垮客户性能），但它可能让高估与低估相互抵消，所以还要看 L2〔10:13〕。结果是 Cicada 明显更好，而且完全不要求客户输入；缺点是会偶尔低预测，他们希望能把这条左尾再压下去，而对比系统在 oracle 参数下从不高估，代价是客户必须填参数；另一个优势是几乎不需要历史，通常只有几个小时的数据就能做出准确预测，虽然历史越多总体越好〔11:07〕。把预测变成保证时采用 pipe model——“these are going to be what are known as pipe model guarantees”〔12:15〕——即每个源目的对一份保证、数值就等于预测值，但有四点注意事项：网络资源必须真的可用，否则提供商不会做承诺；客户可以自己再加一层缓冲；提供商可以选择性地增补 Cicada 不太自信的那些预测——小应用尤其不自信，只有两三台虚拟机或流量很小的应用基本不适合这个系统；最后 Cicada 能通过观察丢包发现某个保证给低了并立即给出新保证，因为它持续收集测量、任何时刻都能生成预测，坏保证不必等满一小时才被纠正〔12:09〕。第二个评估看网络利用率与浪费的带宽，而提供商并不平等对待所有带宽——机架间带宽通常便宜、机架内带宽更贵，所以要最小化的是机架间浪费的带宽〔13:46〕；Cicada 自带一个贪心放置启发式——“a greedy heuristic, we just place the pairs of VMs that need the highest guarantee on the fastest paths”〔14:39〕——把需要最高保证的虚拟机对放到最快的路径上。结论是云应用展现出既有模型不能总捕捉到的变异性，Cicada 的预测能捕捉它，并且能给出快速且准确的保证——单次预测通常只要几毫秒——所需历史很少，还能提高网络利用率〔15:55〕；这段工作是她博士论文的主要部分，正文有 135 页单倍行距。问答中有人追问虚拟机是否真能把链路打满，她承认自己只有虚拟化层的抽样数据、没有链路利用率数据；被问到是否与拿上一小时当下一小时预测的朴素预测器相比，她说 Cicada 更好，而且从学到的权重看最近一小时的矩阵权重最大，同时过去约五个小时的矩阵仍占相当显著的权重〔17:06〕。（YouTube EPXOpaxxF0uqk，[720-1432]，L1）
- 〔OSDI〕我们真的必须与数据竞争共存吗？Determinator 用检查-检出式工作副本模型在操作系统层给出答案。讲者指出业界已经从做更快的 CPU 转向做更宽、更并行的 CPU，这带来全新的软件难题，而在这届 OSDI 上大家已经看过大量证据〔00:04〕。并行让编程更难，因为它引入了非确定性与数据竞争，进而产生 Heisenbug。竞争无处不在且存在于多个抽象层：内存访问层有对同一变量的两次写竞争、读与写的竞争，读到非确定性的版本；共享文件系统中不但有并发读写同一文件的竞争，连 open 与 rename 的竞争都会制造检查点到使用点漏洞，既是安全问题也是编程 bug〔00:26〕；同步层还有所谓高级数据竞争——一个变量的所有使用都完美加了锁，但因为锁的获取顺序可以是任意的，语义上依然存在内部非确定性；系统 API 也在细枝末节处引入非确定性，比如两个线程并发分配内存会竞争到某一块特定内存、拿回非确定性的不同指针，并发文件打开亦然。当然我们也可以与竞争共存：要么不写出有 bug 的程序，要么靠日志回放、竞争检测器与确定性调度器帮忙，但根本上竞争仍然是程序所写编程模型的一部分〔02:24〕。所以他的问题是：我们一定要忍受竞争吗？理想是一个竞争压根不会出现的编程模型。这样的模型确实存在——纯函数式语言、确定性消息传递语言，或者用类型系统强制分离并行活动的确定性并行 Java——但代价是必须重写全部串行代码，而不能在既有语言里就地并行化〔03:00〕。Determinator 就是这个目标下推出的新实验操作系统，尝试在整个系统 API 内贯彻一个天然无竞争的并行编程模型；因为它工作在内核层，所以与既有语言兼容，同时能在内存、文件系统、同步等多个抽象层避开竞争；原型采取白纸重写的设计思路，以便保有完全的选型自由，同时明确当前只聚焦计算受限类应用、是一个限制很多的早期原型〔04:03〕。（YouTube EPXPlxS_phXX8，[4-1078]，L1）
- 〔OSDI〕工作副本模型如何消除读-写竞争、冲突怎样被检测，以及微内核实现与评测。核心思想他称为 check-in/check-out 或工作副本模型：在常规 Linux pthreads 下父线程 fork 出子线程后，两者立刻开始访问同一变量、同一内存，并在任意时刻互相干扰；而在 Determinator 的模型里，父线程 fork 子线程时子线程拿到整个状态一份完全独立的工作副本，两个线程各在自己的工作副本上工作，直到下一个由程序定义的同步点，在此之前从不交互，只在那个 join 点上由系统把两者的改动合并回父线程〔05:44〕。他强调这不是全新想法，很早的并行 Fortran 系统就在并行 do 循环里做过类似的事，只是语言特定且局限于某个构造，人们手工写软件时其实一直在用。他举两个示意例子说明效果。第一个是共享内存的模拟程序：维护一个 actor 数组表示虚拟世界状态，每个时间步为每个 actor fork 一个线程，线程读取数组里任意元素、决定它负责的 actor 下一步动作、再更新该 actor；同一段代码在 Linux pthreads 上显然有 bug——某个线程跑得比别的快、已经开始更新，而另一个线程还在读，读到新旧混杂的值，整个状态一团乱，当然可以按常规办法多加同步来修。在 Determinator 里主线程 fork 出子线程后，每个子线程拿到 actors 数组的完整独立副本，各线程只读到自己所做的改动，到 join 点时 Determinator 把每个线程对自己负责那个数组元素的改动合并，形成下一个时间步的起始数组〔07:11〕。第二个例子是文件系统层的进程级并行：一个简单的 makefile 分别编译 foo.in 与 bar.in 再合并，串行 make 下每个子进程各自创建再删除临时文件，完全正常；一旦加上 -j 并行编译就变成 Heisenbug——两个看似独立的编译任务共用同一个临时文件，谁都可能拿到本该属于对方的临时文件〔09:50〕。在 check-in/check-out 模型下，make fork 出两个文件系统时各自拿到完整独立副本，各自读写与删除自己的临时文件都发生在本地工作副本上，等到重新合并时 Determinator 把两边的文件系统合并，只剩下 foo.out 与 bar.out 这些真正结果，再合成最终产物〔10:58〕。由此带来语义结论：常规系统里的数据竞争分写-写与读-写两类，而读-写竞争的整个类别在这个语义下消失了，因为写只通过同步点传播——某个线程的读永远只会看到因果上在先的那次写，绝不会看到另一个线程并发那次写；写-写竞争有时也会消失，就像刚才那个例子里两个子线程都在重新合并前删掉了自己可能冲突的临时文件，但一般不会自动收敛的写-写竞争会变成冲突，就像去中心化复制文件系统里的冲突；竞争与冲突的区别在于，竞争可能被某一线程非确定性地赢、或在确定性调度器下按一个仍不可预测的时刻被确定性地赢，而冲突一定在 join 或合并点被检测到，Determinator 目前把它当作编程错误处理，就像除零〔11:58〕。实现上 Determinator 是一个微内核，内核监督一棵严格的进程实体层次，每个实体称为 space，每个 space 都是纯单线程、只有一套寄存器状态、地址空间不能与其他 space 共享的受限 Unix 进程类似物；与 Unix 进程可任意互相通信不同，只有根 space 能直接做外部 I/O，其余 space 只能与直接父辈和子辈通信，于是微内核制造出一种由单核虚拟机组成的无共享分布式系统的假象〔13:45〕。每个 space 除私有地址空间外还有一份叫 snapshot 的第二份备份地址空间；微内核 API 极简单，只有 put、get、ret 三个系统调用，不提供进程、线程、文件这类高层抽象，那些由用户态运行时即 C 库提供——包括 Unix 风格的进程管理、标准 C 文件系统 API，以及既支持这种天然确定性模型、也通过确定性调度支持 pthreads API 以保持向后兼容的共享内存多线程；所有这些都在库里，因此可选、可由应用定制〔15:14〕。具体机制是 fork 转换为一个 put 系统调用，把父 space 的全部内容复制到指定子 space，而且复制两份：一份进主工作副本、一份进 snapshot 位置，随后父线程可以一次 fork 出任意多个子线程，每个子线程都拿到父地址空间的两份虚拟副本〔16:30〕。要重新同步时父线程发起 get 系统调用，用子线程最新的工作副本对比 fork 时刻保存的 snapshot，以 snapshot 为参考副本做三路 diff 与 merge，把改动合并回父线程，对第二个子线程同样处理；如果程序员正确地避开了冲突，这些改动会落到不同内存区域〔17:09〕。显然这些复制若不加优化会非常慢，于是用标准虚拟内存写时复制，并把写时复制扩展成粒度很细的机会性 diff 与 merge——因为很多时候只有父或只有子改动了某个页，检测到时直接取用相应的新页、避免任何页级工作，只有两个线程并发写同一个页时才做字节级 diff 与 merge〔18:13〕。文件系统方面它提供文件系统 API 但目前没有持久文件系统，更像临时文件系统，在每个进程的地址空间里保留文件系统完整副本；由于进程之间不共享内存，它们实质上构成一个弱一致性的分布式复制文件系统，fork 时对文件系统与其余内容做完整虚拟副本，wait 时把子进程的改动以文件而不是字节为粒度合并回父进程的副本，冲突按文件粒度检测、一般形成硬冲突并以信号错误上报；唯一特例是当两个进程对同一文件都是追加写时，允许它们无冲突地发生，因为追加内容会被合并，从而让日志文件或控制台输出按确定性顺序收集全部追加〔19:11〕。内核还能强制执行确定性，并提供通过进程迁移实现的简单分布式计算支持，以及为向后兼容而可选的确定性调度〔20:58〕。评测部分用简单计算型基准在对数刻度的加速图上验证：有些基准扩展性相当好，另一些实在不行，尤其是并行粒度更细的那些；把绝对执行时间与 Linux 对比（对数刻度、最多 12 个 CPU）可以看到粗粒度基准上性能大体相当甚至偶尔更好——可能源于缓存效应与两个系统之间的其他差异——但更细粒度的应用会付出严重性能代价〔21:50〕；他拿并行快速排序改变数组规模来调整粒度，小数组伴随频繁同步会出现明显减速，等到粒度足够时性能又能与 Linux 相当〔23:27〕。他明确说这只是早期概念验证、有很多限制；结论是理论上似乎确实可能造出一个自然且无处不在地确定性的并行编程模型，它从源头避免竞争而不是与之共存，至少对一部分工作负载效率还算可以〔24:16〕。问答中 Marcus Aguilera
