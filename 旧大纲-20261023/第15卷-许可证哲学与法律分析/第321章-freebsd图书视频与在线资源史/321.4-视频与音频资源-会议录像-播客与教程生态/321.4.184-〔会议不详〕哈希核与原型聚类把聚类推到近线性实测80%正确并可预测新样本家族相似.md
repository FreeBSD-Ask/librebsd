# 321.4.184 〔会议不详〕哈希核与原型聚类把聚类推到近线性实测80%正确并可预测新样本家族相似

- 〔会议不详〕哈希核与原型聚类把聚类推到近线性，实测 80% 正确并可预测新样本家族。相似度比较是聚类瓶颈，经典 k-means 与层次聚类为 O(n²) 难以扩展，Mutanex 用两招提速：一是机器学习社区提出的哈希核方法，把高维特征向量映射到低维以同时省存储与计算且精度损失很小——直接用 n-gram 的哈希值作低维向量下标，冲突时把原计数累加到新计数上，只要哈希函数均匀，维度下降的损失仅随输入数量对数增长；二是基于原型的聚类，属非结构化、无模型方法但在真实数据上经验表现良好：先选一组原型使每个数据点到最近原型的距离都小于阈值 p_max（原型即一组相似点的代表，选择复杂度 O(N·K)，N 为样本数、K 为原型数），再把原型本身聚类，递归合并邻近原型直到任意两簇间距离大于阈值 min_d，最后把与各原型关联的数据点归入其原型所在簇；由于原型数量通常与恶意家族数量同阶、远小于样本数，整体复杂度对样本数近似线性。评测用两个数据集：约 5000 样本的参考集（标签由杀软厂商安全专家给出，用于调参与评估）与在线恶意样本库的 13 万余样本（用杀软扫描打标，用于可扩展性）。调好参数下 Mutanex 约 20 秒即可正确聚类参考集的 80%，其中 p_max 对运行时间影响更大（越小则每原型覆盖区域越小、需更多原型、原型选择与聚类都更慢），min_d 对精度影响更大（越小则更早停止合并、避免不相干簇被并大，但会把一个大家族切碎），实测 p_max 取 0.4、min_d 取 0.3 平衡最佳；相对层次聚类与 k-means 通常只需约一半甚至三分之一时间而精度相当。哈希位宽方面精度随位宽升高，超过 12 位（4096 桶）冲突概率可忽略、精度与不哈希基线几乎一致，但位宽越小越省时间与时延峰值内存，取 12 位可把内存占用与运行时间减少 80% 而精度几乎不变，且样本越多哈希越重要，否则内存占用会迅速高到不可接受；在 13 万余样本上以 12 位哈希与上述参数，全流程两小时内完成且精度尚可。时序实验用 PE 映像头时间戳取样本创建月份，以 2008 年各月划分训练与测试并预测新到达样本家族：只固定前六个月训练时精度从 7 月的 0.7 以上跌到 12 月的 0.4 以下（情报过期），保留全部历史则维持 0.7–0.8，只用最近六个月仅略低于全历史，说明样本间强时间相关性与用 Mutanex 预测标签的实用价值。答疑补充：论文除基础的一般解壳算法外还写了应对多层与增量加壳的启发式，仍会被"先解到磁盘再启动新进程"这类壳绕过；标签真值依赖安全专家，专家自身也存在把差异很大的变体归为同一家族的问题；只取 opcode 而未考虑系统调用属动态分析范畴，两者互补，当前工作正在整合。（YouTube EPUXUU3owyFJA，[919.8-1827.8]，L1）
- 〔会议不详〕CoFS：专为加速容器冷启动而设计的文件系统。报告人 Haoze Wu，工作来自金山软件（Kingsoft）的 Li Wang 博士及其团队。动机是容器虽提供弹性与可移植性，冷启动却是公认瓶颈：它是一条顺序流水线——下载镜像、解包并配置、然后启动，而 FAST 2016 的一项标志性研究（作者引述为 Harter）显示拉取镜像占容器启动总时间的 76%，但启动过程实际只读取其中 6.4% 的数据，为用不到数据下载付出的时间会形成严重启动延迟，可能在 serverless 计算中违反响应性 SLO，或在为突发请求自动扩容时出问题。既有按需拉取方案各有代价：Nydus 与 stargz 属 FUSE 文件系统层方案，继承 FUSE 两项开销——首次元数据查找需与用户态守护进程一来一回并多次在用户态与内核态间上下文切换，以及即使数据已下载、读请求仍要经用户态处理；改用内核 EROFS 配合 FS-Cache 的方案则把下载同步写盘并通知 FS-Cache 驱动后才可供内核服务、且缓存淘汰难控制导致性能波动；overlaybd 工作在块层，因而无法跨容器共享镜像数据的页缓存。作者认为 FUSE 对按需拉取是最自然的框架，于是选择保留 FUSE 并缓解开销。FUSE 的两个瓶颈是：读文件前内核自上而下逐组件遍历路径（如 /user/local/bin/app 需 4 次独立查找，每次都要从 Linux VFS 经内核 FUSE 驱动切到用户态守护进程再反向回传，即每个路径组件都伴随多次上下文切换与请求拷贝），以及已落在本地主机文件系统的已下载数据仍要把读请求转发用户态、连缓存数据也支付切换与拷贝。CoFS 的关键洞察是容器镜像只构建一次且层只读不可变：文件名全集在构建期即已知，可用完美哈希函数预计算所有条目的哈希，从而在运行时以 O(1) 完成查找且无需目录遍历。具体使用最小完美哈希函数 M_PHF——把 m 个键无冲突映射到 0..m-1：以父 inode 号与文件名拼接为输入键，经子哈希 f1、f2 得下标 a、b，在预构建数组 G 中取 G[a] 与 G[b] 相加对 m 取模得唯一索引 h_k，据此查元数据；其吸引点是无冲突、O(m) 空间最优、O(1) 查找，且构建为线性时间。元数据布局基于 stargz 镜像格式并新增二进制元数据文件 CoFS.ino（替换原 JSON 元数据）：先是含魔数与 M_PHF 参数的 12 字节定长头，随后是 M_PHF 使用的三个数组 T1、T2、G，再后是真正的元数据数组——每 inode 条目约 112–120 字节，文件名不超过 16 字节时内联存放、更长的放入末尾额外元数据段，总空间复杂度 O(m)，百万文件约 9.5 MB。（YouTube EPUYOJe_ISIlo，[18.9-402.5]，L1）
- 〔会议不详〕内核态查找与快路径读：CoFS 架构、数据路径与评测。CoFS 由两部分组成：用户态 CoFS snapshotter 基于 stargz snapshotter 实现，负责拉取元数据文件、建立缓存镜像目录并作为 FUSE 守护进程按需从远端镜像仓库下载数据；内核态 CoFS 驱动是扩展的 FUSE 驱动，直接用 M_PHF 处理查找请求，并把读请求当网关——若数据已下载（本地主机文件系统上存在镜像文件）走快路径直接从内部文件系统读，未下载才回退慢路径，像普通 FUSE 那样先联系用户态 snapshotter 从镜像仓库取元数据与数据再返回驱动与应用；snapshotter 同时异步把取回数据写进主机文件系统的镜像文件供下次快路径使用。查找流程：以父 inode 号与文件名为键算 M_PHF 值得元数据数组下标并读出条目，再校验父 inode 与文件名长度，inode 不匹配或文件不存在则失败，都匹配则从条目构造内存 inode——整个过程最多一次 I/O，若对应磁盘块已在页缓存则完全无 I/O，而 ext4 等传统文件系统无缓存时的 inode 查找 I/O 次数取决于目录大小与深度。针对路径解析，作者构建第二个以完整路径为键的 M_PHF（两个哈希对同一文件给出相同值）：当 open 解析到深度超过三级的路径时把它派发到内核工作队列线程，由工作线程自底向上从叶子逐个计算完整路径 M_PHF 构造 inode，一旦碰到已驻留内存的 inode 就停下（某 inode 被缓存则其所有祖先必然已缓存），与 VFS 自上而下解析并发进行并在中途相遇，从而切断串行查找链。数据路径上，未缓存读时驱动检查 inode 镜像文件指针为空则查镜像目录，首次访问无镜像文件（或稀疏文件对应区间为洞）就转发 snapshotter 从远端取数返回应用，随后 snapshotter 若镜像文件不存在则创建空稀疏文件并异步写入对应区间；快路径读则直接经主机文件系统读镜像文件——镜像文件指针有效且所需数据完全落在无洞区间时即可，此时不触碰 snapshotter、也不联系镜像仓库，读完全在内核态完成、无上下文切换。评测为模拟远端共享镜像仓库带宽受限的部署，覆盖 MariaDB、Redis、Tomcat、Elasticsearch 四类常用镜像（幻灯片展示其中三类），CoFS 在每个被测容器上都胜过其他系统。两点意外发现：多数系统启动后在后台继续下载剩余镜像反而会拖累性能（图中以 -P 结尾的列），因为整个镜像远大于启动期实际访问的数据、后台下载与本地网络带宽和 I/O 竞争；Nydus EROFS 在某些场景比原生 Nydus FUSE 更差，推测源于其继承的漫长 FS-Cache 调用链。按启动期 FUSE lookup 函数执行时间衡量，CoFS 的查找平均时延相比简单 FUSE 查找提升 73%–86%，并行路径解析对目录更深的镜像再贡献约 28% 额外提升；缓存读带宽与时延上所有内核态方案（含 CoFS）几乎一致，而 Nydus FUSE 与 stargz 等用户态方案因缓存读仍要经用户态 FUSE 守护进程而更差；M_PHF 构建时间随文件数线性增长，而大规模构建镜像本身至少需数分钟，故该开销可忽略。三项贡献可归纳为：构建期预计算的 M_PHF 让查找在内核态 O(1) 完成且最多一次 I/O、彻底避免用户态往返；主机文件系统上的稀疏文件增量缓存已下载数据、缓存读完全走内核态无 FUSE 开销；以完整路径为键的第二个 M_PHF 让内核工作线程自底向上解析与 VFS 自上向下遍历并发进行，从而使 CoFS 胜过所有最先进的按需拉取系统、查找相比 FUSE 提升 73%–86%。（YouTube EPUYOJe_ISIlo，[403.9-994.4]，L1）
- 〔会议不详〕SwiftPaxos：只对冲突命令排序的强一致状态机复制协议。主讲人来自以色列 Technion 计算机科学系，与（音作 AMD Software 的）Federico Abinini、Alexey Gutman 合作。背景是多地点数据被不同客户端使用，各复制点靠复制协议保持同步以保证透明高效、且部分地点失效后系统仍可用；保证此类性质的黄金标准是状态机复制：每个副本维护日志、访问数据的命令按日志顺序执行，协议运行一个共识实例决定日志下一条目的位置——如三副本 R1、R2、R3 与三命令 A、B、C 的顺序为 B、A、C，R1 已执行 B 与 A、即将执行 C，ZooKeeper、Spanner、Apache Cassandra 等系统都走这条路。SwiftPaxos 另辟蹊径：只排序相互冲突的命令，冲突指在应用层访问同一变量。示例中 A 把 X 设为 42、B 把 Y 设为 7、C 把 X 与 Y 之和存入 Z：A 与 B 访问不同变量故可任意顺序执行、互不产生依赖（示例中 R2 已执行 A 而 R3 已执行 B），而 C 同时依赖 A 与 B。协议为每条命令计算依赖集（必须先于它执行的命令）并按依赖执行，以三不变式保证活性与安全：各副本上依赖必须无环（保证活性，客户端发出的每条命令最终都返回）、各副本对同一命令算出的依赖必须一致、冲突命令必须互相可见（若 x 与 y 冲突则 x 在 y 的依赖中或反之，该性质保证系统线性化）。性能上 SwiftPaxos 至少保持 Paxos 速度：无争用（命令不冲突、或在各副本以相同顺序到达完成）时以最优的单次往返执行命令，否则只需一次半往返；其关键新点是支持双重投票——共识过程中副本可以投两次票，先投自己提出的提案、再为 leader 的提案投第二次。（YouTube EPU_gurNydiow，[15.8-486.4]，L1）
- 〔会议不详〕快速路径、双重投票与乐观执行，及 AWS 上七协议对比。作者以五副本演示：R5 提交命令 B、R3 收到后把自己的提案作为 B 的依赖回送并提出让 B 排第一，若达到 quorum 且各方同时回送相同依赖即可执行；此处 quorum 中 R3、R4、R5 都自发提议让它最先执行，命令直接走快速路径，位于 R5 的客户端只需两次消息延迟，达到最优。再看 A、B 以 B 先 A 后到达 R3：若两者访问不同变量即满足交换律、无需排序，R3 便告知 R1 "A 之前无依赖"，尽管 B 已先到达，因为没必要创建依赖，命令同样走快速路径——协议由此利用应用层交换律；若第三条命令 C（把 X 翻倍）以相同顺序到达 R1–R3，各方也自发提议保持该顺序，C 在单次往返内经快速路径完成，即直接复用网络的自发到达顺序。双重投票示例：命令 B 把 y 置 7、D 返回 x 与 y 之和，另有副本 R4 负责解决分歧；若 R3 先收到 D 后收到 B 而 R4 先收到 B，副本间对 B 的排序出现分歧，SwiftPaxos 允许 leader 副本广播其提案，收到与自己不同提案的副本便纠正并投第二次票（本例 R3 改为投 B 优先），这之所以可行是因为在给定选票中该选票的 leader 是其所有 quorum 的成员，满足该假设即可做这种批量纠正，从而最坏情况只需三次消息延迟、即 Paxos 速度。对非同址客户端，常见做法是把命令发给一个 quorum、待某副本执行后才能取结果（如命令 D 在 R5 执行返回 0），SwiftPaxos 的乐观执行机制则在 leader 副本执行并把结果连同依赖直接回给客户端，一旦 quorum 的依赖与 leader 一致，客户端即知这是持久化的最终结果，从而快速应答非同址客户端。评测在 AWS 上进行：13 个站点（5 个副本站点、10 个客户端站点），no-op 服务、命令负载 1 KB，对比七个竞争协议；左图按冲突率变化看相对 Paxos（1× 基线）的时延，右图在 2% 冲突率（实践常见值）下看全部站点的时延 CDF。N²Paxos 把 B2 消息全部发给所有副本作为提交消息，相对 Paxos 仅约 5% 时延改善；源自应用层交换律的协议随冲突率升高性能快速下滑；最佳竞争者是 NSDI 2019 的 Skarp，平均比 Paxos 快约 18%，而 SwiftPaxos 最多快 40%，其 CDF 上没有任何 Paxos 点位于其左侧。两个应用评测：一是在对象版本变更与指针切换间流水线化下发命令的场景把窗口从 1 变到 10000，SwiftPaxos 最多比 Skarp 快 49%，原因正是 Skarp 无法利用网络自发排序；二是 YCSB 键值基准，SwiftPaxos 快于 Skarp 与 EPaxos，而论文提出的变体允许在任意副本执行读且保持线性化、同样更优。结论是 SwiftPaxos 作为 leader 驱动的 SMR 协议在无争用时单次往返、否则一次半往返，实践中时延比 Paxos 好 16%–29%、吞吐最高达替代方案三倍；元数据使用上也值得注意：出现冲突时不会改选票（不同于 Fast Paxos 与 Generalized Paxos），只要 leader 可用选票保持不变；实现已开源在作者 GitHub 仓库。（YouTube EPU_gurNydiow，[486.5-957.0]，L1）
