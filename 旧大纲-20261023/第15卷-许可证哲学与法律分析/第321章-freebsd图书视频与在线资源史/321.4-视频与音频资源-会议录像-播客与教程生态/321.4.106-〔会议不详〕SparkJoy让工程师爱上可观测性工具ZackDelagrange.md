- 〔NSDI（推测）〕NetChain：基于可编程交换机的亚 RTT 网络内协调系统。主讲人指出协调服务（Chubby、ZooKeeper、etcd）以 Paxos 类共识在多服务器上复制键值存储，时延瓶颈在服务器软件栈处理而非网络，而协调负载是通信密集而非计算密集，故提出用 PISA 可编程交换机在数据平面线速处理读写、请求时延仅半个 RTT。系统采用链复制（chain replication）：存储节点映射到交换机数据平面、辅助主节点（auxiliary master）映射到网络控制器处理重配置；键值存储用交换机 ASIC 中的寄存器数组（SRAM）存取、一致性哈希加虚拟节点跨交换机分片（单交换机设计源自 SOSP 2017 的 NetChain），多链路由借鉴分段路由：客户端在包头插入链上交换机 IP 列表，逐跳更新目的 IP 与剩余跳数（hop count），读请求直达 tail。（YouTube EPGjIJkdL9J4o，[10-848]，L1）
- 〔NSDI（推测）〕NetChain 的容错、性能与问答。针对尽力而为网络中的乱序投递，给键值项引入头部插入的单调递增序列号，后续交换机丢弃低序号读请求以保强一致性（正确性不变式附 TLA+ 规约）；交换机故障分两步：快速故障转移只更新邻居交换机即可恢复处理，故障恢复用两阶段原子切换并把数据分成 100 个虚拟组逐组迁移以降低扰动。4 台 Barefoot Tofino（6.5 Tbps，P4 实现，支持 10 万条、128 位值）加 4 台 Intel DPDK 服务器的原型上，8200 万 qps 仍打不满系统（预估可达数十亿 qps），时延仅 9.7 微秒，对比 ZooKeeper 读 170 微秒、写 2350 微秒；问答中 Dan Ports（Microsoft Research）、Murat Demirbas（SUNY Buffalo）等确认每交换机约 10MB 存储、辅助主节点在服务器上用 Paxos 复制、选链复制是因其请求处理简单到可全部下放交换机数据平面。（YouTube EPGjIJkdL9J4o，[850-1689]，L1）
- 〔USENIX ATC（推测）〕Mangosteen：面向持久内存的快速透明持久化。University of Surrey 与 Royal Holloway University of London 的合作工作指出：NVM 字节可寻址且接近 DRAM 速度（新一代 3D XPoint 设备即将到来），但其表现为弱内存，开发崩溃一致程序需手工插 flush 与 fence，过多或过强会降性能、过少则无法恢复。以公共 API 请求为失败原子粒度的透明方案（Pronto 用快照、Persimmon 用影子执行）仍有硬伤：不支持非确定请求与全局变量，日志处理与快照开销在大工作集、高更新率下严重。Mangosteen 提供快速透明持久化：通用（仅需实现 6 个开发者回调即可移植既有易失应用），前端在 DRAM、后端在 NVM，NVM 感知并发控制拦截读写请求的写指令，去重压缩后仅写"压缩的原子写指令批次"进 redo 日志，因此可支持非确定请求。（YouTube EPGkCSRk0SxOY，[16-584]，L1）
- 〔USENIX ATC（推测）〕Mangosteen 的并发控制与实验。核心是将并发控制与持久化协同设计：每核一线程处理只读请求（共享锁、无限制并发），读写请求用 flat combining——线程在 advertisement 表中登记请求，赢得独占锁的 combiner 在动态二进制插桩下串行执行并产出写指令流；把 DRAM 逻辑划为 32 字节区域、哈希表去重后顺序写入持久环形缓冲 redo 日志，每批关键路径仅 2 次 fence。在 128GB DRAM + 1TB Intel Optane 的 Ubuntu 服务器上用 YCSB（Redis 版）与 LevelDB 基准评测：在全部更新率区间优于原生 Redis 与 Persimmon——低更新率靠读写并发（Redis 本身串行），高更新率靠持久化协同设计实现吞吐平滑退化；去重在 Zipf 与均匀键分布下均有效（后者得益于相邻写合并）。（YouTube EPGkCSRk0SxOY，[606-1297]，L1）
- 〔ACSAC（推测）〕PICO SDN：面向 SDN 攻击的溯源驱动因果分析。主讲人 Ben Ujcich（转写作 Ben Usage）先解释 SDN 把控制平面从数据平面解耦、控制器像网络操作系统一样经南北向 API 编排流规则，已见恶意应用投毒其他应用视图使其沦为 confused deputy、恶意主机借跨平面信息流影响决策等攻击。从防守者视角需要端到端看清攻击，而数据溯源（principals、processes、data objects 构成的有向无环图）可沿边高效回溯根因、反向沿边前向追踪影响并忽略无关历史；SDN 场景的难点是依赖爆炸、跨平面因果缺失以及主机可伪造信息（如 ARP 欺骗）导致的错误归因。（YouTube EPGkjHsCPHUCg，[9-255]，L1）
- 〔ACSAC（推测）〕PICO SDN 的设计与评测。设计要点：把对象与进程按事件监听器循环等控制平面重复模式分区以缓解"每包都依赖长驻进程"的依赖爆炸；联合控制与数据平面信息补齐经泛洪（flooding）到控制器再被其他应用看见的间接因果链；对默认流规则（default flow rule）按端口而非主机指派责任以防学习交换机场景的高扇出；给主机标识变化加非因果边以快速定位 ARP 式伪装（主流 SDN 控制器均不阻止此类欺骗）；并提供定位共同根因、看各阶段影响、总结活动、发现欺骗的查询工具。系统实现在 ONOS SDN 控制器上（包装事件、挂钩 API、序列化溯源后离线建图），评测显示在精心构造的跨平面攻击绕过防火墙 ACL 的场景中，可借数据平面模型回溯真实根因在 switch 1 port 1，而非被误导的 switch 2。（YouTube EPGkjHsCPHUCg，[269-693]，L1）
- 〔USENIX ATC（推测）〕Secured Routines：Go 语言级可信执行环境支持。EPFL 博士生 Antoine Ghosn（转写作 Adrian，与导师 James Larus、Edouard Bugnion 合作）指出 SGX 这类 TEE 的痛点：enclave 进出（crossings）昂贵、往里塞太多代码会引发昂贵页驱逐并扩大攻击面、系统调用还需与不可信代码协作，任何疏漏都可能泄漏机密。方案是语言级抽象 secured routines：在 Go 中新增 go secure 关键字（用法与 go 完全一致），编译器扩展 GoTE 在编译期据此把代码与依赖装入 enclave（ELF 中新增 .enclave 节），运行期用跨域类型化 Go 通道（自动深拷贝，基于域内类型反射并附安全检查）替代 crossings，既实现独立垃圾回收器与增强内存隔离，也让可信代码不再持有不可信内存指针、从机制上防误泄机密。（YouTube EPGl7ml_xTk94，[10-413]，L1）
- 〔USENIX ATC（推测）〕Secured Routines 的运行时协作与评测。跨域同步经中间 trusted ready 队列由可信调度器解除 secured routine 的阻塞实现；系统调用也走通道，且暂只暴露运行时所需的窄 API。对比 Intel SGX SDK 的 crossings：getuid 系统调用时延改进 2.7 倍、go secure 同步调用 2.3 倍、吞吐 5.2 倍（线程不阻塞、由 routine 阻塞）。案例：把 SSH 服务器整体包进一个函数 go secure 即可运行、应用代码零改动；Go 标准 TLS 包私钥入 enclave 仅改 9 行（握手吞吐达原生 88%）；go-ethereum keystore 用一天 500 行（多为简化后的 keystore 逻辑）把主密钥守护进 TEE。TCB 方面含完整嵌入 SSH 服务器的 keystore 应用约 4MB 可入 enclave，Hello World 仅 13 行、go build 一条命令即可构建（对比 SGX SDK 复杂的代码与 makefile）。（YouTube EPGl7ml_xTk94，[414-913]，L1）
- 〔USENIX ATC（推测）〕MuCache：微服务调用图中的自动缓存框架。主讲人 Haoran（与 Konstantinos、Spiros 及 Rajiv、Sebastian、Vincent 等教授合作）指出微服务相比单体应用的主要开销在高代价调用，生产系统靠缓存缓解——Alibaba 发现 40% 的微服务调用图深度不超过 3 正是因为命中缓存，Meta 报告缓存命中率超 80%——但缓存一致性需要在每次数据库更新后跨缓存协调，现状是开发者手工配置从秒到小时不等的 TTL，调错既影响正确性也影响性能。MuCache 自动在微服务应用中添加并管理缓存，开发者只需声明哪些服务端点只读（不写数据库、无副作用）；目标是支持真实应用的动态调用图与多语言部署、不修改应用与数据库、可证明正确，且不在请求处理关键路径上加开销。（YouTube EPGllwVXlidW4，[16-461]，L1）
- 〔USENIX ATC（推测）〕MuCache 的宽松正确性、设计与评测。关键洞察借鉴顺序一致性：客户端并不关心跨客户端请求的先后（且这类重排在原应用中本就因网络乱序与延迟而可能发生），把正确条件放宽为"存在某种跨客户端重排后，缓存启用应用的执行集合仍是原应用执行集合的子集"（论文给出完整证明），由此可把全部缓存管理移出关键路径、服务间零同步。系统三组件：sidecar 中的 wrapper（先查缓存、命中即返回，并向 cache manager 供应请求参数、时间戳与读写键）、与应用并置的 cache manager（维护执行时间线，请求结束后无同键写则通知上游 save、有覆盖则发 invalidate）、任意缓存服务（Redis、Memcached），基于 Dapr 实现。在四个开源微服务（酒店预订、影评、社交媒体、Google Cloud 演示的 online boutique）上评测：中位尾延迟与吞吐优于仅后端缓存（BC）基线，接近永不失效的 TTL 无限上限（中位延迟最多高 20%、吞吐低 5%）；自身平均引入约 13% CPU 但缓存命中为应用省下更多，垃圾回收把 cache manager 元数据压到缓存大小 3% 以下，总网络用量降 27%。（YouTube EPGllwVXlidW4，[486-804]，L1）
- 〔SREcon（推测）〕错误预算下的 SRE 风险管理：风险的定义与误区。Matt（Google Customer Reliability Engineering 团队 tech lead，来自新西兰，本报告系其 3 月 SREcon Americas 报告的重讲）介绍 CRE 如何把 Google SRE 经验跨客户边界应用，其中可靠性评审（reliability review）沉淀出一张风险清单。在 SRE 语境下他把风险定义为"消耗错误预算的情形"（four nines 的月度错误预算约合 4.32 分钟停机）。他强调风险形式多样且高度个人化（以自己对蜂蜇过敏为例：事实层面后果更重，感知层面还有恐惧与不成比例的反应）、人在风险上并不总是理性，但风险也是前进的代价（教儿子骑自行车终要拆辅助轮）；既不能忽视风险——Google SRE 之父 Ben Treynor 常说"Hope is not a strategy"，也不能因惧怕变更而筑墙自守：变更常是故障首要诱因，但 SRE 的本职是在守住 SLO 的前提下让变更以最高速度上线，变更冻结后的下一次发布往往翻倍、排障也加倍，熵总是赢。（YouTube EPGny_-gWBwa4，[5-860]，L1）
- 〔SREcon（推测）〕用预期成本给风险排序。直觉排序不可靠：以色列假释委员会研究发现时段与情绪显著影响专业法官裁决，新近事件与"电影式威胁"也会放大感知，承认偏差之后还需要一套强制流程。CRE 先用 3×3 的可能性（frequent/common/rare）×影响（catastrophic/damaging/minimal）矩阵沟通——矩阵利于沟通却难以 stack rank——继而引入风险管理学界的 expected cost（金融、制造、油气行业日常在用）：量化可能性（MTBF，实践中用 ETBF 估计值）与影响（MTTR，拆成检测时长 ETTD 与恢复时长，并加受影响用户比例等因子）相乘。配套的 risk register 电子表格输出"坏分钟/年"并与错误预算目标对比：单一风险消耗超过错误预算四分之一即不可接受（红色）；four nines（年约 53 分钟）与 three nines（525 分钟）档位下可交互式选择接受（橙色转绿）或处置，把风险讨论从主观争论变成客观量化，也把"你需要 100% 可靠"的对话拉回数据基础。（YouTube EPGny_-gWBwa4，[862-2179]，L1）
- 〔OOPSLA（推测）〕JITServer：云上 JVM 的 JIT 编译解聚。多伦多大学（Alexey Karabrov、Eyal De Lara）与 IBM Canada（Vijay Sundaresan 等）的合作工作指出 JVM 的 JIT 编译在启动与爬坡期造成 CPU 尖峰（DayTrader 应用稳态半核、瞬时高达 350%）与内存尖峰（稳态约 370MB 仍突发 OOM 风险），迫使过度供给、增加成本且尖峰幅度因 Java 的非确定性难以预估。方案是把 JIT 与 JVM 解聚：编译器独立成进程、容器化为云服务，可多客户端共享（已在 Eclipse OpenJ9 实现，代号 JIT server technology），保留本地编译作可靠性兜底。收益：内存尖峰因各应用峰值在服务端错峰而摊平、容器内存限额更小，CPU 不再被编译抢占（启动、爬坡与 QoS 改善），编译资源可独立伸缩（微服务思想下沉到 JVM 层），供给只需考虑应用自身。代价是网络开销把 CPU 成本搬上集群总量、且一次编译实际含多轮类/剖析信息往返查询而非一个来回。（YouTube EPGolfCy3INvM，[13-497]，L1）
- 〔OOPSLA（推测）〕JITServer 的编译产物缓存与序列化。利用云上水平自动扩缩产生的同应用多实例，把远程 JIT 编译产物在服务端缓存复用，把编译成本摊到多个 JVM 并跳过多轮消息往返。实现难点靠 serialized 格式解决：重定位记录修正指针在新 JVM 的加载地址、验证记录校验投机优化（如去虚化 guard：比较对象类型命中内联体否则走慢路径）在新环境仍成立，并以全限定名 + ROM 类（OpenJ9 中 java class 的只读预处理表示）SHA-256 沿继承链（含接口）逐级比对确认跨 JVM 类等价，类加载器以首个加载类名启发式标识（失效仅损性能不损正确性）；仅缓存爬坡级优化编译（可重定位代码慢约 10%，更热方法再本地重编译），实测缓存命中率约 70%-95%。Acme Air、DayTrader、Spring PetClinic 评测：启动最多缩短 15%（容器越大收益越小），爬坡最多缩短 87%，64 个短生命周期 JVM 场景下总 CPU 成本最多省 77%，内存收益单靠远程 JIT 已足够，缓存后可容忍约 6 毫秒网络时延（无缓存约 3 毫秒）。（YouTube EPGolfCy3INvM，[497-1413]，L1）
