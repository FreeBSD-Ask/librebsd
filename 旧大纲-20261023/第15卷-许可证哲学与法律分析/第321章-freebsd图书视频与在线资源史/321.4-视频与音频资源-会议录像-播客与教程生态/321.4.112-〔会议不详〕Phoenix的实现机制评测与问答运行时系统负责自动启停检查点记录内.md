- 〔会议不详〕Phoenix 的实现机制、评测与问答。运行时系统负责自动启停检查点、记录内部与外部状态、检测外设访问成败并执行三步恢复；SRAM 划分为标准 Python 堆与较小的恢复堆，恢复堆含日志（journal，借助 MPU 保护使每次写堆生成条目以回滚）、每个外设一个重物化队列和驱动 redo 模式的控制流队列，并按外设确认滚动释放；编译器遍历 AST 在参数首次加载处插入启用检查点的字节码并跟踪未决外设访问，面向恢复的中断处理器在失败时抛异常交还 Python 解释器。开发者只需在四个 Python 超类中定义外设并实现 recover/save_state（示例中各仅一行）以及含依赖信息的配置文件。在 Stellaris LM3S9B92（96KB SRAM，划出 64KB 堆）上评测：检查点数据仅占 4-6KB，恢复耗时 12-143ms，软件日志带来每次写 6.2 微秒开销（论文提出的简单硬件机制可再降两个数量级），三个应用中两个无可察觉减速；问答讨论了 C 语言重实现的潜在收益，以及回滚到故障前状态是否适配任务关键系统（发言人认为此类语义应由应用层处理）。（YouTube EPHdbOPlOMFWw，[440-1345]，L1）
- 〔USENIX Security〕Android 可信应用回滚防范的实证研究。EPFL HexHive 实验室的 Marcel（与 Philipp、Matthias 合作）研究基于 Arm TrustZone 的可信执行环境（TEE）中可信应用（TA）的回滚攻击：厂商修复漏洞后出现新旧两个版本的签名 TA，无人阻止攻击者把过期带漏洞的旧版加载回 TEE，典型缓解是 TA 头部版本字段加回滚计数器、加载器只接受最后所见版本。团队构建了覆盖 5 家 OEM（占全球 65% 市场份额）近四年固件的数据集，逆向 4 种 TEE 实现上共 35,500 个可信应用，解析出 190 次回滚计数器变更事件并汇总约 2,500 个含公开漏洞的 TA。结论是尽管公开漏洞通告与 PoC 博客存在，回滚计数器远未被广泛使用；51 台设备的数据显示 29 台可被已知漏洞利用实现可回滚地进入 TEE，数据集中唯一较系统使用计数器的厂商是 Samsung。（YouTube EPHdgg7LqjXBo，[8-360]，L1）
- 〔USENIX Security〕跨产品与跨 OEM 泄漏及结论。大公司产品化开发分散，不同团队独立打补丁时一方忘记递增回滚计数器，仅凭计数器对比即可泄漏关键漏洞与回滚攻击可行性信息，实例是 Widevine TA 在 Samsung A10 上收到计数器更新而 Galaxy S10 没有；跨公司边界购买或自行维护第三方 TA 也会造成同样泄漏，Oppo、vivo、小米基于联发科芯片的机型共享 14 个 TA（部分有漏洞），只因回滚计数器未被使用或所用 TEE 缺少该功能而未观察到实际泄漏。总体结论是回滚防范在整个行业层面基本失效：一些 TEE 根本没有回滚能力、公司内部计数器使用不协调、且对外部而言极不透明；作者呼吁厂商把漏洞生命周期延伸到所有设备完成补丁且处理回滚防范为止，论文、工具与聚合数据集已开源于 GitHub 并获得全部三项 artifact evaluation 徽章。（YouTube EPHdgg7LqjXBo，[360-642]，L1）
- 〔USENIX ATC（推测）〕F2FS：面向闪存存储的新文件系统。三星电子（Samsung Electronics）发言人介绍 F2FS（转写误作 FTLFS/FTFS/FDFS）——工作在块接口 NAND 闪存设备上的新文件系统：随机写导致自由空间碎片化，迫使 FTL 做高代价垃圾回收，造成持续随机写性能退化与寿命缩短；而顺序写友好的 LFS 又需要在文件系统层做清理。五大设计特性为闪存友好盘上布局（超块置于设备前部以利用局部性）、高效清理基础设施、多头日志按温度分离节点与数据（节点比数据更新更频繁，直接节点比间接节点更热，目录项块为热数据，可用文件扩展名识别极冷数据）、自适应日志，以及加速 fsync 的前滚恢复。与 LFS 的大单日志不同，F2FS 用节点地址转换表（NAT）扩展 LFS 的 imap 来索引直接/间接节点，更新文件数据时只需更新直接节点与 NAT、避免更新传播；盘上组织为 4KB 块、2MB 段（segment）、多段组成 section、若干 section 聚成 zone（转写中的 John 为 zone 误写），当前配置 6 条日志。（YouTube EPHgCvcMQnJQ0，[10-418]，L1）
- 〔USENIX ATC（推测）〕F2FS 的多日志分离、清理、自适应日志与恢复。zone 盲分配会让不同温度的节点/数据日志混入 FTL 同一擦除块，因此把各日志分配到不同 zone；对页映射 FTL 还可用 multi-stream 接口把各节点/数据日志映射到不同流以进一步分离。垃圾回收以 section 为单元并与 FTL 的 GC 单元对齐：选定牺牲 section 后检查有效块、迁移数据并更新交叉引用、标记为 pre-free，待下一次检查点后释放。针对高利用率与碎片化下清理耗时问题，自适应日志在文件系统空闲 section 低于 5% 时切换为线程式日志（threaded logging，写入脏段中的无效块），接受一定随机写以换取比其他文件系统更优的性能，并通过该策略把写放大系数尽量保持在低位。恢复采用检查点与回滚机制，检查点区保存 NAT/SIT 日志化的双影子副本；评测在移动与服务器基准上与 Linux 先前文件系统对比。（YouTube EPHgCvcMQnJQ0，[418-784]，L1）

- 〔会议不详〕RevDecode：用相关性解码改进二进制函数匹配。发言人（转写为 Tong Wei）指出函数匹配在逆向工程中用于识别嵌入式固件中的库、隔离漏洞函数与理解代码复用，但受编译选项、优化级别与版本差异影响而困难。现有方法依赖相似度得分，存在不足：度量关注结构相似而逆向工程师更关心匹配是否有洞察价值（示例中语料库内 libssl 3.0.2 的旧版本比结构最相似的 libbfd 2.30 更相关）；穷尽式语料库不现实；相似函数难以区分导致匹配歧义。提出的 RevDecode（转写多种变体均为其误写）利用函数前后代码段等上下文信息做相关性解码，不是新的匹配技术而是增强任何底层匹配器的框架；三个阶段：把匹配器输出转成有向分层图（每列按二进制中的函数顺序对应一个未知函数），以相似度、置信度、库得分与邻接得分为边权构图，再用 Viterbi 启发的前向遍历高效计算所有位于最大权重路径上的节点。（YouTube EPHgt0_b9VUDo，[12-417]，L1）
- 〔会议不详〕RevDecode 评测与并行图遍历。在 binutils、busybox、openssl 跨版本编译的通用数据集（110 亿函数匹配）与模拟真实固件关键结构的 frankenbinaries 数据集（58 亿匹配）上，用 tie-aware NDCG 评测 BSim、Discovery、SAFE、Gemini 四个匹配器：通用二进制 56.3%-97.3% 的排名得到改进，frankenbinaries 上为 72.3%-98.8%，BSim 上近 40% 排名达到 1.0 的理想 NDCG。改进来自两类：借助邻域强匹配的上下文恢复因版本或编译差异而结构不相似的匹配（如把 libzip Ubuntu 20.04 的 uncompress 从第 148 位提至首位）、消解缺乏区分特征的函数歧义（通用数据集上约 35% 的改进属此类）；组件消融显示不确定节点（uncertain node）可减少 7% 的上下文引入排名错误。为扩展到大图提出三种并行图遍历算法（朴素、细粒度、基于分段的估算），细粒度与分段估算远快于朴素遍历与 CPU 基线，分段估算只损失 0.003 的 NDCG 即获得更大加速。（YouTube EPHgt0_b9VUDo，[417-811]，L1）
- 〔会议不详〕云应用管理平面（operator）的可靠性研究与失败模式。UIUC 的 Tyler 报告论文 Who Watches the Watchers?，开篇以真实 Postgres operator 故障为例：operator 观察到主节点崩溃后做故障转移，却忽略仍处 booting 状态的备节点并将其提升，导致整个应用不可用。与一次性脚本或人工操作不同，软件 operator 是处理应用全生命周期的常驻服务，在 Kubernetes 上已成事实管理范式，bug 因自动化与广泛复用而被放大；operator 需与四类外部实体交互：被管理应用（如查询 get cluster 端点、post 到 failover 端点）、云平台（pods/卷/config maps）、共置的其他 operator、以及用户的声明式接口。对 13 个成熟 Kubernetes operator（MySQL、Postgres、Kafka、ZooKeeper、Knative 等）的 412 个真实失败研究表明，多数失败源于与外部实体的交互而非内部逻辑 bug，其中应用交互占交互失败的 42% 且此前无人研究或理解；应用交互失败有四种模式，最普遍的语义违规占 64%，其余为可观测性问题、版本不兼容与错误处理。（YouTube EPHhgLw8K6iyA，[18-467]，L1）
- 〔会议不详〕语义违规深挖与 OAT 测试工具。同一 Postgres operator 对同一 failover 操作接连出现三个 bug（提升 booting 备节点、忽略 WAL 滞后造成静默数据丢失、同步复制模式下提升异步备节点），每次修复都暴露开发者先前未知的前置条件；其他模式示例包括 MinIO 扩容时成员列表更新不一致致节点无法入簇、MongoDB 在备份配置未完全更新前启动备份、pg_data 目录权限过宽违反 Postgres 要求。深层根因是云应用缺乏良定义的管理接口，需求散落在手册、源码甚至 FAQ 中，开发者常靠生产故障逆向工程得到。作者构建 OAT——针对应用交互的全自动按钮式测试工具（针对未修改的 Kubernetes operator，属 Acto 项目，沿用 Acto 在 SOSP'23 提出的状态中心测试方法），从 operator 仓库挖掘样例或查询大语言模型合成应用特定的状态声明，执行测试活动时注入容器崩溃、网络分区等应用故障，并用自动 oracle 标记 bug。在 6 个成熟 operator 上发现 86 个新 bug 且零误报；结论主张可管理性应成为一等设计原则，且当 AI 代理取代基于规则的 operator 时，形式化管理接口将成为代理安全护栏的关键。（YouTube EPHhgLw8K6iyA，[467-952]，L1）
- 〔SREcon〕Linux 软件网络接口的构建块深潜。NativeWave（云原生托管服务与咨询公司）的 Matt Turner 因调试一个出问题的 Kubernetes 部署而花一周弄清 Linux 网络机制，本讲（明确区别于 SDN）讲解支撑虚拟机与容器联网的接口类型。先快速补齐网络基础：以太网与 MAC 地址、ARP（以太网的 DNS）、IEEE 802.1Q VLAN 与 trunk 端口、iptables/netfilter 钩子与 NAT、路由与 NAT 的差别及 conntrack 端口映射回查、路由表、A/B/C 类网络到 CIDR 的演进、单播/广播/组播/任播与 DHCP。随后给出核心心智模型：主机接口是悬空的软件插头（箭头），可分配地址并用 connect/bind 系统调用使用；由此展开真实物理接口、tun/tap 设备（用约一页 C 写出响应 ping 的 packetd，说明 VPN 的封装原理）、用 NAT 或 IP 转发把外部流量引入隧道接口、以及 Linux bridge 作为软件交换机（广播域扩展）等构建块。（YouTube EPHiktxCMF03A，[6-1710]，L1）
- 〔SREcon〕从虚拟机到容器再到 MACVLAN/IPVLAN。QEMU/KVM 通过 tap 接口联网并对外伪装 e1000 网卡，其反直觉之处在于把内存中的帧再还原为假线事务，故有 virtio-net 半虚拟化（共享环形缓冲，快得多）；bridge 自带宿主端口 br0（与桥名同空间，brctl 与 ifconfig 看到的是两个不同的 br0），另有 Open vSwitch 及 netmap、VPP、DPDK 等内核旁路加速路径。容器是 cgroups（硬件隔离与限速）加 namespaces（软件隔离）的组合，网络命名空间隔离接口、iptables 与路由表，把 veth pair 一端移入命名空间（Docker 将其改名为 eth0）即可接入网络；VLAN 子接口带 VLAN ID 42 标记上行并可整体移入容器。为摆脱慢且难管理的 bridge，MACVLAN 让同一物理口上的多个上层接口各有独立 MAC，可置于 bridge 模式（无需 MAC 学习与生成树，最小可行的最快桥）或 hairpin 模式（交给上游交换机处理，但可能触发防伪造机制），MacVTap 免去接桥即可供 VM 使用；等交换设备进化后 IPVLAN 层二模式可共用 MAC，层三模式进一步去掉 MAC，但要求子网划分与路由，需用 BGP（如 Bird）通告路由——这正是 Calico 的做法。结论是最新的未必最优，IPVLAN L3 是个带大量开销的怪异局部最优。（YouTube EPHiktxCMF03A，[1710-3415]，L1）
