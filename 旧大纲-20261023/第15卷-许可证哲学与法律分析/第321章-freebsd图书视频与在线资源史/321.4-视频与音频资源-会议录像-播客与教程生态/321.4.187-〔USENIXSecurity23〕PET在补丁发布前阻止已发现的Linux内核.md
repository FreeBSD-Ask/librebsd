- 〔USENIX Security '23〕PET：在补丁发布前阻止已发现的 Linux 内核错误被触发。南京大学 Zicheng Wang（合著者 Yueqi Chen 来自科罗拉多大学博尔德分校、Qing Gai Zeng 同属南京大学）指出，漏洞从引入、发现到修补、合入、部署之间存在平均至少 66 天的时间窗，期内内核处于无法自我保护的状态；PET 以 sanitizer 报告为输入，定位错误点与触发条件并生成 eBPF 程序，借助 eBPF 的 verifier、JIT 引擎、helper 函数以及基于 kprobe 的挂点，在不重编译、不重启内核的前提下于每次执行到错误点之前检查当前上下文是否满足触发条件，命中则跳过错误行跳向函数返回并向恶意进程发送 SIGKILL。以 slab 越界为例，args 数组长度由入参 size 决定、合法最大下标应为 size-1，代码却误写下标 size 造成一字节约界，生成的 eBPF 程序将执行从第 645 行跳转至第 693 行返回错误码，使内核沿调用栈走错误处理路径恢复正常。系统采用分层架构，底层是错误无关机制，上层是针对各漏洞类型的错误相关防御策略，并内置 BPF 程序模板支持自动扩展。（YouTube EPUkEIfzJ3mYE，[8-438]，L1）
- 〔USENIX Security '23〕PET 的机制边界与评估结果。底层机制中，报告处理器用正则从执行 PoC 得到的报告中提取信息；sanitizer 到原生的映射用 addr2line 与变量到寄存器两条翻译流交叉校验（二者均可从 DWARF 调试信息获得），把误报降到每例零；检查点-恢复在函数入口记录寄存器上下文，条件命中时跳至函数出口并把错误码写入 RAX，使调用栈中的 raise 函数把它当作失败处理。但该方案只是权宜之计，因为存在约五百对难以回滚的操作（文件读写、设备操作、锁、内存分配、全局内存修改等），当前仅处理锁与内存分配两类，并用数周日常任务负载验证稳健性。评估以自收集的 sanitizer 报告与 CVE 为准：平均性能开销低于 3%，同时运行二十余个 eBPF 程序时最坏开销低于 8%（NAPI 网络接口在高并发 Web 请求下的高频热路径除外），释放后使用扫描器在 60 GB 内存机器上的最优参数为 256 MB 范围、每 4 秒一次；现场演示在虚拟机上用两个终端分别拦截整数溢出、越界、释放后使用与未初始化访问，并杀死恶意进程而内核继续运行。（YouTube EPUkEIfzJ3mYE，[438-776]，L1）
- 〔USENIX Security '21〕针对可搜索对称加密的高精度查询恢复攻击。Marc Damie（合著者 Florian Han、Andreas Peter）先用高层方式解释可搜索对称加密：用户持有密钥与陷门函数，可把任意关键词转换成查询令牌（本文称 trapdoor 陷门）；服务器侧是加密索引，即查询令牌到标识符列表的映射，用户把陷门发给服务器后取回加密文档。被动查询恢复攻击先据访问模式与搜索模式的泄露构造陷门共现矩阵，再与攻击者据已知文档得到的关键词共现矩阵比对，既有路线要么建模成优化问题用经典数学方法求解，要么迭代过滤候选；作者指出已知的已知数据假设（掌握已索引文档的约三成）过强且不太现实，而“相似数据”场景尚无有效准确的攻击。其贡献是提出可解释的打分式攻击方法、把准确率推到九成，并对文档集相似性这一概念做了正式化，同时给出对最强攻击的性质与局限的充分分析。（YouTube EPUnt3Kbd9SCE，[8-417]，L1）
- 〔USENIX Security '21〕打分攻击、精炼版本与防御结论。攻击者知道的是与索引文档相似但并非索引本身的文档集，从中提取词汇与关键词共现矩阵，同时观测部分查询并知道其中少量查询的真实关键词，据此得到陷门协方差矩阵。打分攻击把这些基础知识向量化，使陷门与关键词可直接比较，匹配分数取两者距离的对数变换，分数越高越可能是关键词-陷门对；算法对每个陷门-关键词组合打分并返回最高分者，几秒即可完成、结果确定（不同于非凸优化未必可复现），且分数可用于设计改进策略。实验中在真正互不相交的相似数据设定下平均可达约八成准确率，优于既有工作，但代价是需要大量已知查询、且随可查询词表增大而急剧上升。为此提出精炼打分攻击：每轮先移除已知查询，用基线分类器为未知查询找候选并以分数衡量确定性，取前 k 个最确定者并入已知查询集合，直至剩余未知查询不超过 k 则返回结果，准确率可达九成以上。作者另提出相似度度量 ε 并观察到文档越不相似准确率越低、低到一定程度攻击完全失效；最后用填充与混淆两类极简单对策即可成功缓解该攻击，结论是即便攻击非常准确，简单对策也能生效，代价是若干性能开销。（YouTube EPUnt3Kbd9SCE，[417-716]，L1）
- 〔NSDI '14〕FaRM：面向现代数据中心硬件的快速远端内存平台。主讲人自称 Alexander（对应 FaRM 论文作者 Alexander Ilnytskyi，加州大学伯克利分校）说明，FaRM 不只是一个键值存储，而是面向现代数据中心硬件的分布式计算平台，受两大硬件趋势驱动：内存成本下降使数十台机器的小集群即可拥有数十到数百 TB DRAM，足以在内存中容纳多数应用的全部数据集；数据中心正在引入当年高性能计算用的网络，吞吐高、时延低并暴露 RDMA 原语，使一台机器无需打断对端 CPU 就能直接读取远端内存（A 机 CPU 发起请求，B 机网卡直接建立 DMA 搬运数据，不经过中断）。在 20 台机器、40 Gb/s RoCE RDMA 网络上的随机读微基准中，把 RPC 消息面换成 RDMA 即可带来近一个数量级的吞吐提升，直接用 RDMA 读远端内存再提升约一倍，最低时延同样改善一个数量级；据此 FaRM 采用对称模型（存数据与跑计算落在同一批机器上，因为本地访存比 RDMA 远端访问快约二十倍，且服务方 CPU 大量闲置），把全集群内存组织为共享地址空间（做 RDMA 需要知道起始地址与长度），提供严格可串行化的 ACID 事务、可用单次 RDMA 读实现的无锁读，以及把相关对象放到同一台机器、把计算搬到数据所在机器、优化单服务器事务等本地性手段。（YouTube EPUoL3FGcDsE4，[10-756]，L1）
- 〔NSDI '14〕FaRM 的事务与无锁读实现及评估。事务由单台协调服务器执行、乐观并发控制：提交时先向写集合所在机器发消息加锁并取回应答，再由协调者用单边 RDMA 读校验读集合（确认执行期间读到的内容未变），校验通过则以单向消息更新并解锁对象——因为网络提供按序可靠传输；数据还复制到副本机器写入 SSD 日志以获得容错，思路类似 RamCloud。无锁读方面，单机做法是在对象头放版本号，写者加锁改数据后解锁并递增版本，读者读版本-读数据-再读版本两次相同才可用，但这需要三次网络访问、会抵消使用 RDMA 的收益；FaRM 利用网卡缓存一致的同一缓存行内写入顺序保证，把版本号放进每个缓存行，一次 RDMA 读取回整个对象后校验各行版本是否一致，并把 64 位头版本截成 16 位缓存行版本以把空间开销从 12.5% 降下来，再辅以时间界限（约 14 纳秒的最小更新周期推算出约 2 毫秒容限、留 0.2 的时钟漂移因子）防止缓存行版本溢出，实验中从未真正触发超时。评估中 FaRM 哈希表可达每秒约 1.45 亿次操作、约为 TCP 键值存储的十五倍，峰值吞吐下时延改善约两个数量级（35 微秒对约 10 毫秒）；仿照 Facebook TAO 实现的图存储吞吐提升约十倍、时延改善四十到五十倍。问答中主讲人解释了 TCP 瓶颈主要在内核态（与 UDP 相比差距不大但都远逊于 RDMA）、与 RamCloud 的差异在于后者为快速故障恢复而设计、系统已在 78 台机器的较旧集群上验证可扩展、数据本地性仍由应用自行决定。（YouTube EPUoL3FGcDsE4，[756-1477]，L1）
- 〔SREcon18 Asia/Australia〕用 OpenCensus 把可观测性做进应用。主讲人自报名为 Samil（自述前职 SRE，现为 OpenCensus 开发者）从微服务谈起：多支团队各写一部分并共享 Kubernetes 等基础设施，随着缓存、负载均衡等组件加入，一个请求要在多层软件间扇出再汇聚、部分可并行部分必须串行，难以在脑中维持整体图景；于是要为进入系统的每个请求分配 trace ID、为子操作生成 span ID，两者构成 trace 上下文，随 HTTP 头或 gRPC metadata 在微服务间传播，各服务把 span 上报后端拼装成整棵树（整棵树称 trace、单个操作称 span），从而看清拓扑、阻塞关系与关键路径。可观测性的另一半是指标：GKE 之类默认的黑盒系统级指标（CPU、磁盘 IO、内存）反映不了用户真正关心的错误率与延迟，应用级指标无法直接从虚拟机或容器提取、必须靠插桩。OpenCensus 是开源项目，每种语言一套风格化但命名与概念一致的库、当前支持七种语言，提供追踪与指标的清晰 API，自动集成流行 Web 与 RPC 框架并自动传播上下文、度量延迟与错误，配有 Zipkin、Prometheus 等导出器与用于实时查看 Trace Z、Stats Z 的 Z pages；此外新增打标机制，任一组件设置的键值标签会自动传播到子 RPC，只需在一处代码插入即可为指标引入任意自定义维度，Go 库还支持 pprof。（YouTube EPUpDDJXb7jys，[5-532]，L1）
- 〔SREcon18 Asia/Australia〕OpenCensus 双语言演示与后续路线。现场运行 OpenCensus 附带的 gRPC 示例：Java 服务端、Go 客户端，指标导出到笔记本上的 Prometheus，追踪发送到 Stackdriver。演示依次展示 Trace Z 与 Stats Z 在空载与有流量时的形态、measure 与 view（如服务端延迟的聚合视图）、Prometheus 抓取的文本型指标端点，用累计延迟求导后除以计数得到每个 RPC 的平均时延（约 35，与 20 毫秒加 30 毫秒随机的设定相符）、按不同 RPC 自动分列，并可继续用标签拆出更多维度；随后在 Span Z 与 Stackdriver 中查看 span 的 trace ID、span ID、父子关系与注解——注解相当于每个 span 的日志行，主讲人强调在数据库返回之间出现未解释的长间隔时，注解能直接指出下一步该查哪里。总结之后给出路线图：支持更多语言、更多开箱即用的框架、为 Redis 与 libmysql 等客户端库补齐产出领域相关 span 与指标的插桩、标准化 Trace Context 的 HTTP 头格式、跟进 Prometheus 社区主导的 OpenMetrics、把 trace ID 写入日志做关联、日志 API 仍在实验阶段，以及实验在操作后期按缓慢或报错自适应采样而非只做随机采样——出错或有慢的追踪对排障更有价值。（YouTube EPUpDDJXb7jys，[532-1199]，L1）
- 〔LISA18〕抛开容器重新理解隔离。Fastly 的 CTO Tyler McMullen 开场即声明这场报告与容器无关，只讨论多租户场景下的隔离：他非正式地把隔离定义为“让某段代码运行而不会以意外方式影响其他正在运行的代码”，涵盖资源隔离、进程隔离、故障隔离与软件故障隔离，进程、容器、虚拟机都是同一问题的不同解法且开销与强度各异；他借用控制工程中的 FDIR（故障检测、隔离、恢复）把三阶段拆开——检测是知道故障何时发生，隔离是证明故障发生爆炸半径受控，恢复是保证执行可重启且系统对其发生无感知。由此他把隔离问题归结为控制流完整性与内存安全两件事，并引入故障域（fault domain）的概念，即回答“这个程序炸了之后到底坏掉哪些东西”，目标是把可能的故障缩小到可知、可恢复的范围。Fastly 的需求极为苛刻：要隔离的是单个请求的内部执行，全球数千节点每秒处理数万个请求，请求生命周期常在 1 毫秒以内、最多 5 到 10 毫秒，因此进程、容器与虚拟机都太重。回顾进程模型可见其故障域其实就是地址空间——虚拟内存由硬件 MMU 与内核 VMA 提供，代码与数据共处同一空间，于是可以完全忽略控制流问题；这也解释了为何 Spectre 让所有人不安，因为虚拟内存屏障是进程之间唯一的隔离；系统调用则扩展了故障域，使不同进程的故障域开始重叠，而容器只是在同样的基础上再叠加 PID、命名空间与系统调用过滤。（YouTube EPUpgUrJiz-_M，[11-753]，L1）
- 〔LISA18〕用 WebAssembly 在进程内实现轻量隔离。McMullen 认为 Wasm 的真正价值在于它是社区首次真正达成一致的第一门快速、多语言、可重定向、安全的中间表示，已是多种语言的一等后端：内存与代码分离声明、函数带类型、函数必须显式导入（无法调用没有导入的函数），而代码与内存分离意味着故障只影响内存、代码仍可安全重用，与进程模型截然不同（进程一旦出错就必须重新加载代码）。实现上团队自研编译器与运行时：Clang、Go、Rust 都能产出 Wasm，编译器再转成本机目标对象码，通过 dlopen 加载共享对象，并用微调过的 SysV 调用约定让 RDI 指向 VM 上下文（指针上方是实例元数据与全局变量，下方是线性内存），取内存只需在该指针上做偏移。边界检查通常会让程序慢 2 到 10 倍，而 Wasm 线性内存向上增长且无空洞，所以只需检查上界；引入 4 KB 保护页后可只检查基址并把开销摊到多次访问上，把保护区扩到 4 GB 后 32 位 Wasm 地址根本不可能越界、彻底免除检查。为防编译器自身出错又引入陷阱表（trap table）：编译器为每个函数输出可预期异常的指令偏移，运行时若遇到表中没有的陷阱就认定编译器有 bug 并整体终止。实现基于 Mozilla 的 Cranelift（Firefox 的 JIT，可视为用 Rust 写的小型 LLVM）。问答中他坦承现有方案尚不足以直接承载不可信多租户代码，Spectre 等问题需要超出内存安全与陷阱表的额外工作，并说明移植遗留代码需借助内部的 IDL 式机制处理 32 位与 64 位指针的转换。（YouTube EPUpgUrJiz-_M，[753-1724]，L1）
