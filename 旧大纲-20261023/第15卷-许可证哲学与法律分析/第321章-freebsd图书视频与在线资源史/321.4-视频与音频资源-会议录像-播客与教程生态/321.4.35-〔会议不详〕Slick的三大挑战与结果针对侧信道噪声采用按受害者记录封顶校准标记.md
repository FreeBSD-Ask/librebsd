# 321.4.35 〔会议不详〕Slick的三大挑战与结果针对侧信道噪声采用按受害者记录封顶校准标记

- 〔会议不详〕Slick 的三大挑战与结果。针对侧信道噪声采用按受害者记录封顶校准标记记录，攻击者与受害者步速差异用绝对值动态时间规整（absolute value DTW）对齐，尚不存在的未来蜂窝网络则以 Wi-Fi 网络仿真；在两栋多层楼宇 46 条室内路径片段合成 100-300 条路径的大规模实验中，Slick 对 200-250 米路径识别准确率达 94%，更长路径升至 98.4%，LTE 小规模实验验证了可行性；对策包括加密激活位图（需改标准）、位图加噪（可立即部署但仅部分有效）与更频繁更换临时标识 TMSI（4G 困难、5G 改善），漏洞已报告 GSMA 并获确认。（YouTube EP4gmlNAl_hUU，[310.2-649.6]，L1）
- 〔会议不详〕文件系统去重侧信道。VU Amsterdam 与 ETH Zurich 合作研究（主讲人 Andrei Bacht）展示攻击者可利用文件系统内联去重在远程以字节粒度泄露数据：以往内存去重侧信道已见诸研究，而文件系统去重因粒度大、行为异步被视作安全；ZFS 约每 5 秒一个事务刷盘且事务内含去重检查，重复数据的事务时长（时间域峰值宽度）更短，构成定时侧信道；攻击以 128KB 去重记录为约束，通过缓存整形（cache massaging）、对齐探测（alignment probing）逐字节独立探测并降低熵，配合 timed write 原语测量事务时间。（YouTube EP4gtzaspkmn0，[8.7-435.8]，L1）
- 〔会议不详〕远程 OAuth 令牌泄露与对策。远程场景含四个角色（受害者浏览器、SSO 服务器、运行 Nginx 的 SSO 客户端、攻击者网站），目标是 OAuth 2.0 隐式授权写入 ZFS 去重日志文件的长效 access token：受害者经隐藏 iframe 携带 token 发出 GET 请求落入日志并溢出一字节到下一去重块，攻击者独立发起 GET 探测并以 0.5 秒阈值实时判峰；secret spraying 把候选值喷洒到多个去重记录以放大远程信号，在 FreeBSD+ZFS 默认配置（128KB dedup 块、Nginx 1.14）上 LAN（1 跳）400 次探测/字节耗时 42 分钟成功率 92%，WAN（12 跳）成功率 94%、每小时一字节，整个 22 字节 base64 token 约 21 小时；缓解为覆盖写重复数据的伪恒时（pseudo constant-time）策略，无需重设计文件系统即可消除远程信号。（YouTube EP4gtzaspkmn0，[436.1-882.9]，L1）
- 〔USENIX ATC（推测）〕R2P2：数据中心 RPC 传输协议。EPFL 的 Marius 与 George、Adrian、Jonas 及导师 Ed Bugnion 提出 UDP 上的无连接请求-响应对协议：请求由源 IP/端口加客户端请求 ID 标识，无协议强制排序、无 fate sharing，回应可来自与请求目标不同的服务器，从而化解 TCP 复用 RPC 的队头阻塞并让网络对 RPC 感知（RPC 成为一等公民）；中间盒只参与策略决策与首个数据包转发，多包请求与回应流绕过中间盒直连服务器，形成线速在网策略执行且不构成 I/O 瓶颈；实验显示 Nginx 反向代理（join shortest queue）在 25 微秒指数服务时间下因 I/O 瓶颈无法超过约 22 万 req/s，而 DPDK 软件中间盒仅加 5 微秒时延、双核打满 10G 链路，Tofino（Barefoot）ASIC 硬件中间盒仅加 1 微秒。（YouTube EP4k8MUERtQwM，[10.1-492.6]，L1）
- 〔USENIX ATC（推测）〕JBSQ 调度、策略字段与 Redis 实验。针对分布式队列尾延迟差、单中心队列不扩展的矛盾，提出联合有界最短队列（JBSQ）分列队列策略：中央无界队列加每服务器有界队列、尽量推迟调度决策，软件方案 5 个 outstanding 请求、硬件方案 3 个即达排队论预测的最大吞吐且尾延迟接近理论最优；R2P2 头部策略字段支持 route any/route fixed 并可扩展 sticky、hashing 等策略，在 Redis 主从复制中让 set 定向 master、get 均衡到 3 个 slave，Facebook 负载下比 TCP 原生 Redis 吞吐提升 5.3 倍，写比例从 0.2% 升至 2% 时调度收益更显著；问答确认 outstanding 请求量取决于服务时间及其波动，中间盒只维护每队列 outstanding 计数即可扩展。（YouTube EP4k8MUERtQwM，[493.4-1261.1]，L1）
- 〔会议不详〕静态分析与模糊测试工具的可用性用户研究。Fraunhofer FKIE 的 Stefan Pflueger 介绍对 Clang 静态分析器与 libFuzzer 的定性可用性评估：静态分析早已是业界找 bug 核心手段，fuzzing 则是近年学界热点且被 Google（仅 Chrome 即发现两万余 bug）、Microsoft、Cisco 等大公司有效使用，但在中小企业采纳远不及静态分析，研究旨在检验可用性问题是否构成采纳障碍；研究采用被试内设计，含 32 名计算机硕士生与 6 名本地 CTF 选手两组，选用 Clang 静态分析器与 AFL/libFuzzer 中的 libFuzzer，并强调两工具各擅其长、评估不应视作对等比较。（YouTube EP4o9RyavWkkU，[16.2-156.0]，L1）
- 〔会议不详〕结果与改进建议。学生组简单静态任务几乎人人找到 bug、难静态任务无人完成且半数放弃；26 名开始模糊测试任务的学生中仅 3 人能实际把 fuzzer 跑起来，而 CTF 选手虽未能触发目标 bug 但多数能认真 fuzz 目标程序，无一人退出；Clang 静态分析器因易用性好受好评但真实场景（难任务）中误报与重复报告多，fuzzing 全流程——选择 fuzz 函数、编写与优化 fuzz target、插桩编译（被形容为痛苦）以及输出解读——均成痛点；建议包括协助用户选择 fuzz 目标函数、帮助创建与改进 fuzz target、自动化插桩构建链接流程并改进代码覆盖率。（YouTube EP4o9RyavWkkU，[156.2-287.5]，L1）
- 〔会议不详〕CAPA：把 Android 强制访问控制扩展到第三方应用。主讲人 Matthew（第二部分交由 Dayu）介绍对 Android 开源项目的一组修改：应用内所有组件同处一个沙箱，用户授权精确定位后同一应用内的第三方广告框架即可读取 GPS 追踪用户；CAPA 旨在实现应用内部分舱（compartmentalization），思路是把组件拆分到不同进程并按进程调节权限（引入 SELinux 域）——进程拆分可复用 manifest 的 process 标签，权限调节由开发者在 APK 内提供 policy 模块四件套（file_context 路径-类型映射、map_permissions.xml 权限映射、进程-域映射的 seapp context（转写为 syscall context）与 policy.cil），选用 CIL（Common Intermediate Language）子集，以 block 语句把每个 policy 模块包进按包名命名的唯一命名空间来表达“来源（origin）”约束，禁止修改系统策略、防止权限越界传播，allow 语句按来源分四类处理，system 对 local 类型授权一律拒绝并以不可编辑的宏提供安全替代。（YouTube EP4p-33raoIlk，[8.0-432.2]，L1）
- 〔会议不详〕安装期/运行时支持与开销测量。安装时由 package manager 服务抽取并校验 policy 模块、与设备上其他策略片段合并后用 sepolicy 编译二进制策略并由 init 重载；运行时修改 Zygote 在进程孵化前按 local seapp context 设置域（缺失时回退系统 context），新增 restorecon 系统服务（转写为 Restorcon）配合与 java.io.File 同接口的 android.os.file API 处理文件标签，并修改 Treble 二阶段 init 仅挂载 data 分区后即构建重载策略，保证模块在任何应用启动前加载、不可绕过；对 Google Play 150 个热门应用分 basic/ordinary/huge 三档合成策略测量，进程创建开销可忽略、文件创建约 370 微秒，仅声明 100 个类型的 huge 边缘配置有显著安装开销；代码与 artifact 评估材料已开源于 GitHub。（YouTube EP4p-33raoIlk，[433.6-684.2]，L1）
- 〔会议不详〕Balboa：面向数据中心 SmartNIC 的开源 RoCE v2 FPGA 网络栈。ETH Systems Group 的 Max 与同事构建 FPGA 开源基础设施，其中 Balboa（转写音写为 Rocky Balboa，报告称已提交今年的 OSCI）是开源 RoCE v2 网络栈：商用 RDMA 网卡（Nvidia BlueField、AMD Pensando）把 RoCE v2 传输栈硬化固化在硬件中，研究者无从修改协议；Balboa 立足四个支柱——保持 100G 吞吐、遵循 RoCE v2 协议以与现有交换机/网卡互操作、资源高效可共置其他在网计算、开放可扩展；其设计在 FPGA shell Coyote v2（去年发表于 ASPLOS，被称为 FPGA 的“操作系统”）内运行于 Alveo U55C（250MHz 时钟），并支撑把数据库算子卸载到网卡的 Celaris 项目；栈内分核栈（IP/UDP/InfiniBand 分层封装的包处理管线加流控/拥塞控制/重传等控制块）与扩展块（on-path、平行路径协议增强及按流多路复用的应用卸载）。（YouTube EP4p8Xa41WZnM，[18.4-425.8]，L1）

- 〔USENIX ATC（推测）〕ext4 Fast Commits：高效的文件系统日志。主讲人 Harshad（Google 软件工程师，合作者 Sourabh 与 ext4 维护者 Ted Ts'o）剖析 JBD2 物理日志的代价：fsync 触发的日志提交需写提交描述块、全部变更元数据块、cache flush 再写提交标记，串行两条 I/O 请求；fsync 越频繁写入日志的数据呈指数增长（应用吞吐下降、journal 干扰加剧），NFS 每次元数据更新都隐式 fsync，邮件服务器负载中 journal 带宽达用户数据 4 倍，云上按 IOPS/带宽计费时直接变成美元成本；提出的 Fast Commits 是混合方案——fsync 时做逻辑日志、周期性物理提交，邮件服务器负载磁盘带宽降低 44%、完成时间缩短 33%，相关工作中 iJournaling 首创混合日志但未优化资源效率且改变 fsync 一致性语义，CJFS 是 JBD2 的扩展性优化。（YouTube EP4pm8JpCZrhY，[16.4-619.6]，L1）
- 〔USENIX ATC（推测）〕Fast Commits 设计与评估。设计上周期性 slow commit 提交自上次 slow commit 以来的全部差异并使其前的 fast commit 失效，从而大幅简化恢复；不支持的操作回退到 slow commit，该回退路径也便于增量合入上游（90% 代码已进入主线）；三项核心技术：compact logging 把元数据更新紧凑打包进单个 4KB 块（同一场景 196 字节对 JBD2 的 24KB，可用 FUA 单次 I/O 提交）、inline journaling 省去专用 jbd2 内核线程以减少调度延迟、selective flushing 仅在 fsync 路径写过数据时才需 cache flush（80% 的 fsync 重负载无需 flush），合计 fsync 延迟约降 57%；在 GCE local SSD 上以 ext4/CJFS/XFS 对 Varmail、FsMark、FileServer、Postmark 评估，写入字节最多减 56%、I/O 数最少，NFS 场景受网络延迟限制而在 InfiniBand 等高速网络下预期更好。（YouTube EP4pm8JpCZrhY，[619.8-1227.2]，L1）
