# 321.4.212 〔学术会议演讲场合未明示〕上海交大的Xinda报告DST面向分布式事务多版本的标

- 〔学术会议演讲（场合未明示）〕上海交大的 Xinda 报告 DST：面向分布式事务多版本的标量时间戳。MVCC 的意义是更新数据不覆盖原内容、而是另存一个新版本，从而改善读写之间的并发：读方可读过去的自洽版本，写方同时更新最新版本〔00:16〕。版本分配有两个硬要求：版本必须与事务顺序一致——若事务 1 读了 A 的 v0、事务 2 改写 A 生成 v1，则 "V zero must be smaller than V one"〔00:55〕；且赋值要高效、对事务影响最小。候选方案各有短板：物理时钟好用但 "it is hard or challenged to synchronize physical clocks so that they are not guaranteed to be consistent"〔01:17〕；全局时间戳预言机能保证一致性，代价是 "global logical clock has non-trivial cost to the transactions"——每笔事务都要与时间戳服务器通信〔01:40〕，而 "using a single timestamp server" 处理所有请求 "may become a scalability bottleneck"〔02:08〕；向量化全局时间戳让取号时 "each worker only need to query its local clock entry"〔02:41〕，但更新时钟项仍要与全局服务器交互，只是缓解而非根治，且 "the size of the timestamp grows linearly with the number of machines in a cluster"〔02:53〕。关键观察是：事务本身已被某种并发控制协议（如两阶段锁）排序，所以 "we can leverage the concurrency control protocol in read-write transactions to make the efficient but unordered physical timestamps to be ordered in a lightweight fashion"〔03:05〕。DST 由此提出：一个 MVCC 的标量时间戳，形似物理时钟，但靠与读写事务的并发控制协议联动保持自洽，从而给出 "zero-responsible snapshot reads"（转写如此，应为零依赖快照读），读路径可绕过并发控制〔03:34〕。作者坦承 DST "not a particularly new idea"，建立在多个去中心化时间戳前期工作之上，但声称是首个面向分布式事务场景、适用于 MVCC 的通用时间戳〔05:07〕。规则取自事务的冲突访问模式：只有冲突事务之间才需要协调时间戳，故规则应像并发控制一样按冲突类型挂载，先讲写写冲突规则。（YouTube EPXRTsgW7g6CQ，[16-340]，L1）
- 〔学术会议演讲（场合未明示）〕后半段展开规则与实测。写写规则的依据很朴素："if transaction two has a write-write conflict with transaction one, which means that it overwrites the data previously written by transaction one, the timestamp of transaction two must be larger than transaction one"〔06:01〕；执行手段是 "we can store the last writer's timestamp with the data"〔06:15〕，使后来的事务能拿本地时间戳与库里现版本比对。以记录 A 为例：T1 首写，把 A 的版本设为 T1 的时间戳；T2 覆盖之，则按规则把自己时间戳抬到 T1 之上，写写规则即在两者间成立。两阶段锁下的落地扩展有三步：事务开始时额外取本地时钟作为时间戳；锁请求被服务端处理时，服务端 "additionally send back the database's current version to the transaction"〔07:29〕，事务据此把时间戳调到大于 A 当前版本；解锁时 "only needs to additionally write its timestamp to A to publish its timestamp"〔07:48〕。读路径的难点在于：若不把读也挂上并发控制，"the reader's physical clock may be inconsistent with the writer's timestamp"〔08:40〕，因此读方在真正读版本前先把自己的时间戳 "leave its timestamp to A"〔08:56〕，让后续写方知道存在进行中的读——这个修复 "only incurs additional CPU" 而 "no additional network requests"〔09:26〕。评估上 DST 规则通用、不绑定具体并发控制，在两阶段锁、乐观并发控制与 Lococo 三种协议、以及传统网络与 RDMA 等高速网络上评测〔09:30〕，其中两阶段锁以 MySQL Cluster 扩展、乐观并发的基线在转写中音写为 Doctrine Plus R。结论：两阶段锁场景下 DST "can provide similar performance as RC, the read committed isolation level"〔10:07〕并因跳过锁阶段而优于两阶段锁；乐观并发场景同样接近 RC 且优于 OCC，因为 OCC "will frequently retries reads due to the contended workloads"〔10:22〕；与全局时间戳服务器 GTS、向量化全局时间戳 VTS 相比，"even in the fast network" 两者仍因额外网络请求而有可观成本〔11:05〕。最终归纳为：DST 是让多种并发控制协议下 MVCC 高效且可扩展的通用时间戳方案〔11:05〕。（YouTube EPXRTsgW7g6CQ，[340-675]，L1）
- 〔SREcon（推测）〕Google Maps 的 SRE 负责人 Joe Abrams 与 Micah Lerner 报告 "product reliability for Google Maps"〔00:18〕。团队是横跨旧金山与悉尼的二十名 SRE〔01:00〕；Micah 曾任职 Mapbox 与 Strava 的基础设施与可靠性团队，Joe 此前在 Pandora、AWS 与 Sony Crackle 处理故障。Google Maps 已近二十年、月活超十亿，能力涵盖地图、路线、地点与商户搜索，挑战在于 "running global services at a huge scale" 同时保持高可用与低时延〔01:47〕。转折点是复盘：全局冗余与优雅故障处理这类服务端可靠性投入已见效、SLO 违约显著下降、经典的服务端雪崩越来越罕见；但分析 postmortem 时发现 "a majority of incidents were manually detected"〔03:21〕，且 "These issues were more subtle where servers were running well but the user experience was not what users were expecting"——多数事故在既有服务器监控里根本看不到。三个案例：其一，用户从旧金山十六街与密申的 BART 站路线到 Embarcadero，App 给出一条不合理路线，事故由数据更新引起且 "completely invisible in our server SLOs"〔04:40〕；其二，iPhone 客户端为 Immersive View 功能的一次更新与特定系统版本交互出错，用户 "would click open and it wouldn't even open"〔05:22〕，幸好已有面向用户的埋点得以快速缓解〔05:49〕；其三，在旧金山搜 coffee 返回 "Google Maps can't find coffee"，想加一条空结果告警却很难，因为 "there were many cases where having no results is actually expected in a valid response from our servers"〔06:12〕，另一次搜知名运营商无结果则源于代码推送〔06:40〕。归纳出两个缺口：生产告警 "didn't capture the full user experience"，以及自动告警时 "we weren't always informing our code management systems"〔07:23〕；由此形成两条判断——把重心转向 "shifting our focus towards user centricity"，并把用户体验指标接入交付反馈回路〔07:54〕。策略三支柱：与核心体验的所有者对齐功能关键性与事故严重度；构建可直接度量用户体验的信号，能借用伙伴团队已有成果就借用；最后把信号接入既能预防又能检测事故的系统，他们称之为 "defense in depth"〔09:01〕。三类度量是可用性、时延与数据质量，其中时延回归虽未必严重，但 "even milliseconds of delay on critical features like search impact how people use the product"〔11:08〕。（YouTube EPXSsrafnpvxU，[16-725]，L1）
- 〔SREcon（推测）〕后半段讲工程实现与经验教训。可用性走两条路：界面元素序列，"When a user clicks the button, does it take them to the expected destination?"，把 if-this-then-that 断言喂给自动变更监督与生产告警〔12:08〕；以及崩溃率等系统健康指标〔13:03〕。时延一侧用 trace，"The image visualizes execution of code in Google Maps using an open-source tool called Perfetto that is built into Android"〔13:40〕，由原始信号算出用户感知时延告警；trace 的附带好处是 "debuggability"——可深挖是渲染变慢、有逻辑误跑在主线程、还是网络栈新增调用〔14:02〕。数据质量是第三类：微服务依赖下团队用 "graceful degradation"〔15:00〕——不整体失败而返回可返回的部分信息，如次优搜索建议或地点详情缺项；数据质量回归不像功能坏掉那样显眼，而是 "lead to a slow boil of less useful features, ultimately impacting business metrics like user engagement, adoption, and retention"〔15:26〕。三类信号同时进入变更监督与近实时告警。受监督的三类变更向量是服务器滚动发布、应用二进制发布与特性放量〔15:48〕，其中应用发布最难，因为 "We can't roll back a released app"〔16:13〕如同不能回滚云上服务器；但 "change vector supervision is not enough"——超出团队控制的外部变更也要靠同样指标在近实时告警中发现〔16:34〕。案例的转折值得单记：过去难以把可靠性工作与业务优先级直接挂钩，因为服务端大量错误可能因 "client retries, graceful feature degradation, and multiple levels of caching" 被抵消〔18:00〕；现在可以直接表述为 "those errors led to a significant increase in user perceived latency"〔18:22〕。搜索空结果改造后，原本每年复发的大事故被他们称作 "shifting left" 的工作挡在逃逸之前〔18:55〕，生产告警作为最后防线使值班响应自动告警而非用户投诉，检测与修复的平均时间大幅下降〔19:24〕。教训有四：加强监控初期会让人 "perception of more outages"〔19:50〕；新类事故调试成本高，要 "drill very deep into the stack"〔20:23〕，于是发起 code yellow 这类跨组织临时集结的内部行动并把投资转向变更监督工具〔20:37〕；"The focus on integrating into the delivery loop was a major aha moment for our exec sponsors"〔21:13〕，把诉求包装成 "let's apply the same protections we use in the code yellow, but for this new feature that you're building" 在开发伙伴那里反响很好〔21:26〕；产品所有者买账需要如实讲清前期成本与误报开销，并用范围可控的特性做试点、"don't try to boil the ocean"〔23:08〕。未来工作指向已发布到应用商店的代码更难定位与缓解，需自动按维度与人群分解用户体验指标并直接推到值班手上〔23:23〕，以及自动发现接入深度防御框架的指标 "have either gone stale or are experiencing another kind of anomaly"，以维持高信噪比、防止 pager fatigue〔24:21〕。（YouTube EPXSsrafnpvxU，[725-1490]，L1）
- 〔会议不详〕DirectKV：把 KV 缓存下沉到 CPU 内存、注意力留在 GPU 的长上下文推理卸载系统。弗吉尼亚大学 Shu Tian Luo 报告 DirectKV，与导师 Huanrui Shen（转写作 Haiyun Shen）合作〔00:21〕。动机是 KV 缓存随上下文线性增长，上下文达数十万乃至百万 token 时单请求就需数百 GB 甚至数 TB 缓存〔01:16〕，于是“GPU provisioning becomes driven by memory capacity rather than computation”〔01:32〕，长上下文服务因此昂贵。现有单级卸载系统把 CPU 内存当备份层：计算前把所需 KV 块换入 HBM 暂存缓冲区再由注意力内核读取，重复换入换出压满 PCIe，暂存区又占用与卸载初衷相冲突的 HBM 容量〔03:16〕；被选 KV 块随请求与解码步动态变化，“This can disrupt CUDA graph replay and introduce launch overhead”〔03:45〕。NVIDIA GS200 与 GB200 以 NVLink C2C 集成 Grace CPU 与 Blackwell GPU、提供约七倍 CPU-GPU 带宽，GPU 内核可经高带宽路径直读 CPU 内存，CPU 内存由备份层变成 GPU 存储层级的自然延伸，从而有真正零拷贝 KV 缓存的可能〔03:55〕〔04:34〕。但矩阵乘案例显示 NVLink C2C 仍比本地 HBM 慢约四倍，B 在 CPU 内存时延迟虽降约一个数量级，与数据全在 HBM 的理想情形仍有约两倍差距，故剩余差距须靠围绕非对称存储层次重设计 GPU 内核弥合〔05:09〕〔05:24〕。第一条观察是瓦片划分应反映数据驻留位置：默认遍历顺序为本地 HBM 设计，会让同一 B 瓦片反复穿越 C2C，改为 CPU 内存感知划分后 B 瓦片取入共享内存即驻留、跨多个 A 与 C 瓦片复用〔06:55〕〔07:06〕。第二条观察是把 HBM 访问与计算重叠：生产者 warp 预取下一瓦片、消费者 warp 计算当前瓦片，矩阵乘案例有效吞吐提升 4.3 倍〔07:48〕〔08:33〕。（YouTube EPXT7soOM_YuM，[0-514]，L1）
- 〔会议不详〕第三条观察是内核融合：常规流水中投影内核把新生成的 K/V 写到 CPU 内存、注意力内核随即又读回来，在较慢的 CPU 内存上构成不必要的写读往返，融合投影与注意力后新 K/V 留在片上内存被注意力直接消费、仅落 CPU 内存一次〔08:44〕〔08:58〕。DirectKV 含四个组件：离线内核生成器构建 CUDA 内核、内核适配器在运行期挑选预编译内核、注意力融合引擎组合投影与注意力、KV 管理器在 CPU 内存分配 KV 块并暴露给 GPU 做零拷贝访问〔09:49〕〔10:10〕。预填充阶段多个查询 token 关注同一批 KV，用二维瓦片让每个 KV 瓦片跨多个查询瓦片复用；解码阶段只有一个新查询 token，改为一维遍历 KV 缓存、每个 KV 瓦片只取一次，目标一致——让每个瓦片穿越 C2C 的次数最少〔10:34〕〔10:51〕。为保住 CUDA 图重放，融合注意力内核只接收两个输入：指向 KV 池的固定基址指针与保存静态块索引的动态缓冲区，内核不再按实际内存地址编译，因此图拓扑跨解码步不变、每步只更新索引缓冲区，解码阶段接近零内核启动开销〔12:23〕〔13:19〕。评测在 96 GB HBM 的 GB200 上进行，三个模型、上下文 1k 到 32k、到达率最高每秒 30 请求，代码在 GitHub 与 Docker Hub 开源〔13:26〕〔13:51〕。结果 DirectKV 平均快 1.2 倍、高负载下快至 2.4 倍，且在所有基于 HBM 的基线耗尽显存后仍能继续服务更长上下文〔14:00〕〔14:08〕；分量结果印证各优化分别消除不同瓶颈，三个模型上延迟均下降、吞吐最高提升 3.5 倍、延迟降低约 50%〔14:25〕〔14:57〕。作者总结：长上下文推理使 GPU 采购越来越由 HBM 容量而非算力决定，NVLink C2C 提供了足以让 CPU 内存充当实际 GPU 工作层的带宽〔15:05〕〔15:14〕。（YouTube EPXT7soOM_YuM，[514-955]，L1）
