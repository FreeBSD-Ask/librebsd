# 321.4.197 〔SREcon推测〕从事故案例看指标为什么会骗人主讲人是BingCortana方

- 〔SREcon（推测）〕从事故案例看指标为什么会骗人。主讲人是 Bing / Cortana 方向的 SRE，从 Matt 处接着往下讲。他的切入点是：对 SRE 而言，指标与度量是日常工作中最重要的事情之一，不了解系统运行状况就很难为用户与客户保持好的质量，因此他以一系列成功与失败的例子说明可以学到什么。先从航空航天事故讲起：NASA 发射火星探测器最终失联，他们其实把该有的指标与监测都准备好了，问题出在探测器厂商洛克希德·马丁与 NASA 对指标单位理解不一致——一方用 SI 单位、另一方不用，结果探测器飞得比预期更远从而丢失。教训是必须对指标（SLO/SLI）有共同理解：不只是有定义，还要明确大家说的是指一天的可用性还是一个月，是每秒查询还是每秒请求。第二个例子来自八十年代的加拿大航空：一架从渥太华飞往曼尼托巴的长航线航班，航空公司为避免多带燃料而不自行把油箱加满；飞行员照例去看燃油表，读数为某个数字并被理解为一百公斤，判断足够后起飞，结果航程过半双引擎熄火，飞机彻底没油。真实原因是该读数其实是磅，约为真正所需燃油量的一半。有意思的是机组最终安全降落，69 名乘客无死亡、两人轻伤——一名飞行员持有滑翔执照、另一名有加拿大空军经历，他们靠滑翔超过一小时再俯冲落地救了所有人。他由此强调，我们不希望依靠临场英雄救场，因为那不可重复；但也要看到多样性背景带来的额外价值。核心结论是：统一指标定义、让所有人理解指标含义，以及保证监控本身可靠，极其重要。接着他谈可用性：用几个 9 说话很容易忽视真实停机时间，四个 9 换算下来全年可停机 52 分钟仍然算四九，团队于是改为一律用停机时间沟通，让工程师真正警觉起来；可用性也没有标准答案，只取决于产品与用户对它的预期（停车计时器用一九他都不介意，做激光手术的器械则想要尽可能高），对 Bing 这样的在线服务，99.95% 左右基于经验比较合适。可用性公式很简单——用总请求数减去失败数再除以总数——却有很多出错方式，团队对官方指标坚持全保真度请求、剔除机器人与噪声以保证数据清洁。以披萨店只考核准时送达、于是送来空盒也算达标为例，他指出只看单一指标并不可靠：Bing 自身一次事故中可用性曲线几乎是一条平线，因为度量从用户视角取值——页面渲染成功返回 200、有内容、还有人点击，于是全部计为成功，可事实上用户看到的只有广告、没有任何网络搜索结果，而那一小时由于没别的可点、点击全落在广告上，团队反而赚了一大笔钱；事后把这一点纳入拨号音指标之后帮助很大。他还强调要有相互制衡的指标：纯按变现优化会得出"只放广告"这个史上最成功的变现实验，但 session success rate 会显示用户点击广告后大量不满、不得不反复重新查询。（YouTube EPVe5Q7tobXNU，[5-758]，L1）
- 〔SREcon（推测）〕指标被钻空子与历史寓言对指标设计的启示。他给出第二个 Bing 事故：图表上可用性正常、请求量与失败率都在，可请求量中间出现了一个明显的缺口——那段时间系统收不到任何请求，而失败量本就极小，于是指标以为产品一切正常，实际上用户受到了影响（根因是 CDN 侧发生黑洞，团队当时信任的这个指标没有捕获它）；他由此建议引入异常检测（对比通常此时应有的流量）与外部探测（outside-in monitoring），并重视样本量。第三个更令人难堪的例子：2014 年前后知名搜索博客作者 Danny Sullivan 在 Twitter 上说 Bing 很慢、Google 更快、他要弃用 Bing，而当时 p75 与 p99 的 PLT 都很好，问题只出在极高分位数上、且仅限通过特定运营商的少数用户——这说明任何分布都可能带偏，平均值会掩盖问题、百分位也会掩盖问题，最终团队为监控增加了更多维度。性能度量同样会被钻空子：某功能团队因图片太多导致 PLT 严重回退，于是把图片改成延迟加载让 PLT 指标变得好看从而顺利发布，但用户在延迟加载发生前看到的是不完整页面；应对办法是把延迟加载情形也计入指标，并且认识到真正重要的是首屏（above the fold）可见内容而不是整页。他还用两个历史故事说明指标会带来非预期后果：1902 年法属印度支那推行灭鼠按条付酬，最终市民繁殖老鼠、只割下尾巴交差领取赏金，老鼠数量从未下降，城市里到处是没有尾巴的老鼠；十八世纪苏格兰与英格兰按窗户数量征税，人们开始木板封窗、挂上遮帘，后来才拆掉。结语是：任何指标都需要正确性、完备性与清洁度；指标会被刷分，必须持续更新；随着不断新增指标要避免指标过载，要回头审视已存在的指标是否仍必要，也要持续改进以免指标悄然回退。（YouTube EPVe5Q7tobXNU，[759-1353]，L1）
- 〔安全会议（推测）〕X509 DoS：用构造的 X.509 证书在密码学库中引发拒绝服务。主讲人 Bing Shi。既有密码学漏洞研究多聚焦机密性与完整性，对可用性的关注有限，团队因此专门研究了会因 CPU 耗尽、内存耗尽或崩溃而拒绝服务的密码学库实现，发现许多这类实现直接或间接与 X.509 证书相关，于是围绕构造证书这一攻击向量展开探索，包括发现相关漏洞、发展证书导向的访问策略以及在真实场景中做实验，并把这类攻击命名为 X509 DoS。背景方面，X.509 是公钥基础设施的广泛使用标准，定义了数字证书格式，最常见的应用是 HTTPS 所用的 TLS 协议；以 USENIX Security 官网为例，证书链由根证书、中间证书与叶证书（即末端实体证书）组成，叶证书的 subject 字段中 common name 就是 unix.org，对应网站域名。证书里承载身份信息的字段通常归在一个更大的字段（TBS certificate）之下，由发行方私钥用特定签名算法签名，签名结果放在证书末尾；证书验证时用上一级证书的公钥逐级校验签名，直到根证书。这一流程几乎所有库都实现了，但把它安全地实现下来绝非易事，即使是小疏漏也会引入风险。团队把风险归为三类——数学运算、ASN.1 解析与 X.509 路径验证，并在其中细致分析了 10 种不同拒绝服务风险，每种都由特定行为与对应的实现流程界定。关键在于这些风险发生在证书解析或路径验证阶段，而这早于签名验证，因此攻击者无需 CA 的私钥去重新签名就能修改证书发起拒绝服务，这是可以任意构造证书而无须担心其有效性的根本原因。由于嵌套的 ASN.1 序列结构复杂，手工构造与改动证书相当困难，人工把构造好的证书提交给各种 API 并监测资源消耗也极为繁琐，团队因此开发了一个自动化工具来生成、修改构造证书，并检测密码学库中的这些漏洞；在若干主流密码学库上测试后最终发现 18 个以上漏洞，已负责任地披露给各厂商或维护者，其中多数已被分配序列号（CVE）。（YouTube EPVeO-3Pjnvpo，[10-390]，L1）
- 〔安全会议（推测）〕两种真实威胁模型：mTLS 握手 DoS 与 macOS 零点击持久化攻击。为展示 X509 DoS 的真实世界威胁，作者选取了两个漏洞，一个来自 Botan 库，另一个来自苹果生态，并据此建立两种威胁模型。第一种与 TLS 握手有关，特别是双向（mutual）TLS 握手：不仅是网站服务器向客户端出示证书，客户端也有机会把自己的证书回传给服务器；攻击者于是扮演恶意客户端，在握手过程中发送构造的证书，由于服务器侧证书解析实现存在 DoS 漏洞，处理该证书可使服务器 CPU 使用率达到 100%，重复上述过程即可耗尽服务器上所有 CPU 核心，此后任何用户访问该网站都会发现它无响应，即针对远程服务器的拒绝服务已成功。第二种威胁模型是应用签名验证：为保证应用来自可信发布者且发布后未被修改，操作系统通常依赖证书验证机制来强制这一信任。以 macOS 为例，应用的签名与相关证书存放在一个由名为 LC_CODE_SIGNATURE 的加载命令所引用的数据块中，验证由名为 trustd 的守护进程处理；当用户尝试打开应用时，另一个守护进程 launchd 会向 trustd 发送 XPC 请求请求校验应用证书，验证结果再经 XPC 响应返回给 launchd，并在决定该应用是否被允许启动时发挥重要作用。如果攻击者构造恶意证书链，而 trustd 的证书验证实现存在 DoS 漏洞，处理该链会使 trustd 失去响应，此时用户打开任何应用都会卡住，随着系统资源被持续消耗，最终整个 macOS 都可能无响应。剩余的问题是如何在目标设备上触发这类证书链的验证：诱使用户手动安装证书并非理想方案，更强的方式是让攻击变成一个远程零点击漏洞——攻击者把包含恶意证书链的 S/MIME 邮件发给目标用户，邮件一到达，收件人邮箱（Apple Mail）就会触发对发件人证书的验证，使 trustd 达到 100% CPU 使用率；同时 Apple Mail 还会把这些证书加入收件人的钥匙串，两件事都是自动且静默发生的，即便用户从未读过这封邮件也是如此。若用户在系统异常时重启设备，由于邮件仍在收件箱，无论邮件客户端是被系统自动恢复还是被用户手动重新打开，内嵌证书的验证都会被再次触发，使 trustd 再次失去响应；此外这些证书已进入钥匙串，如果设备上存在 MDM 客户端之类的进程，用户重启后登录时会立即触发钥匙串中证书的验证，同样会让 trustd 失去响应。合起来这就构成一个针对 macOS 的远程零点击持久化攻击，同一攻击也适用于 iOS 以及苹果生态中的其他操作系统。作者最后表示，细节与演示视频可查阅论文与团队网站。（YouTube EPVeO-3Pjnvpo，[391-742]，L1）
- 〔系统会议（推测）〕Underbridge：用 PKU 做内核间隔离，调和微内核性能与隔离的矛盾。主讲人 Jingyu 来自上海交通大学，是与同事及导师的联合工作。单片内核把所有子系统跑在内核态，代码量极大——如今的 Linux 已超过两千万行，且子系统之间没有隔离，任何一处漏洞或运行故障都可能波及整个系统。微内核则把文件系统、网络协议栈、设备驱动等大多数组件搬进相互隔离的用户进程（作者称之 system servers），因而有更好的安全性与更强的故障隔离，既在 QNX 这类车规安全关键场景大获成功，也在通用领域重新受到关注，Google 的 Zircon 便是典型例子。但代价是性能普遍不如单片内核，根源是进程间通信（IPC）开销：单片内核一次系统调用只需一次用户态与内核态往返，子系统之间以函数调用交互；微内核中应用与各服务器之间、服务器彼此之间都依赖 IPC，整个流程昂贵得多。用 SQLite 搭配 xv6 风格的系统服务与一个简单 RAM 盘做实验，在 IPC 密集负载下，即便底层是有大量 IPC 优化的 seL4，也只有约 60% 的时间用于真正的工作；换到未做这些优化的 Zircon，IPC 成本更高。IPC 不仅有权限切换、进程切换等直接代价，还会污染 CPU 流水线、缓存与 TLB。近期 Intel CPU 新增的 PKU（Memory Protection Keys）特性允许在单一地址空间内建立隔离内存域：页表项中有 4 位 pkey，单个地址空间可被划成 16 个内存域，线程通过改写每 CPU 寄存器 PKRU 即可修改各域的读写权限而无需改页表，切换仅需约 28 个周期；Aerie 与 Holo 等先前工作已用 inter-PKU 实现高效的进程内隔离。作者的关键新观察是：PKU 看似只在用户态生效，但只要页表项的 U 位为真，CPU 就会在 ring 0 与 ring 3 都对内存访问透明地执行权限检查——这为内核间隔离打开了轻量化的机会。（YouTube EPViAmRLbIqNc，[7-540]，L1）
- 〔系统会议（推测）〕Underbridge 的执行域、服务器迁移、安全约束与性能增益。作者先排除了两种初步设计：把不同系统服务放进同一用户进程会显著降低服务间通信成本，但应用若只需调用单个服务就得不到收益；把服务直接映射进各应用地址空间则代价高昂（更新服务映射要改所有应用的页表）、建立 IPC 连接的页表修改开销不可忽视，还会限制应用使用完整地址空间与 PKU 硬件的能力。最终方案 Underbridge 基于前述 U 位观察，利用 PKU 在内核态建立执行域，把原本跑在用户态的系统服务下沉到内核空间，同时保留它们定义良好的 IPC 接口：应用调用一项系统功能只需一次用户态与内核态往返，服务之间也不再需要地址空间切换。隔离方面，每个执行域拥有一个私有内存域，系统服务把自己的数据、栈、堆都放在私有域中，其他服务默认无法访问，内核通过配置 PKRU 限定可访问的内存域并禁止执行域改写该寄存器；服务与服务之间共享内存通过让它们共同访问某个空闲内存域实现，而微内核可直接访问所有内存，因此与微内核共享内存不额外占用空闲域。IPC 门位于内存域 0，只有微内核能读写，对服务来说它是只执行的：调用时保存调用者状态、改写 PKRU 切换被调用方的执行域、恢复被调用方状态，微内核与服务之间同样设有 IPC 门，内部服务通过专用 IPC 门发起系统调用而非使用系统调用指令。由于 PKU 只提供 16 个内存域（含为微内核保留的一个），并发服务超过 15 个就无法满足，时间复用又会限制并发并带来可观切换开销，于是 Underbridge 引入服务器迁移：利用为不同系统服务对齐的互不重叠的虚拟内存区域，让服务无论跑在哪个执行域还是用户进程中都使用相同虚拟地址，再依在线或离线剖析把高频或性能关键的服务放在内核态、其余保留在用户进程。安全上，环 3 的服务被抬到环 0 后需防止其执行特权指令，否则一个被攻破的服务可能用 ROP 在不齐整指令边界上找到并执行特权指令而威胁整个系统；CFI 插桩运行时开销明显，二进制扫描重写又不可行（halt 指令仅一个字节，几乎无法消除），Underbridge 因此把硬件虚拟化与二进制重写结合：微内核运行在非 root 模式，root 模式部署一个小型安全监视器，对非关键路径的特权指令配置为触发 VM exit 并在监视器中做权限检查，对处于关键路径的（如写 CR3）用扫描重写专门处理。性能上，跨服务空函数调用的 IPC 往返约 109 个周期，主要由两条 PKRU 写指令决定，比依赖大量 VMFUNC 指令的微内核 IPC 优化方案 Skybridge 更快；移植到三个流行微内核后，以 SQLite 加 YCSB 这一 IPC 密集工作负载衡量，在最有效的 seL4 上吞吐最高提升 105%，相对 Skybridge 也可提升 35%。此外作者指出，除了高效的内核间隔离机制，Underbridge 也可用于加固单片内核的隔离。（YouTube EPViAmRLbIqNc，[541-1219]，L1）
