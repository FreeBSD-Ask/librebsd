- 〔会议不详〕应用 compaction 结果的一致性修复与端到端评测。secondary 不能直接应用 primary 的 compaction 结果：两端内部状态（尤其 memtable）不同，直接套用会丢失数据且与主节点不一致。示例中两线程分别收键 B 与 C，因线程调度顺序不同两端 memtable 内容交错不同，primary 的 memtable 触发 compaction 后共享并删除输入时，secondary 删除同号 memtable 会把键 C 丢掉。根因是跨服务器线程调度的非确定性，强制统一调度太贵，RoboDB 改为按目标 memtable ID 为写请求建立偏序：写入后给请求打上目标 memtable 的 ID 标签，secondary 发现标签与当前 memtable 不符即视为乱序请求放入单独缓冲，正确 memtable 切换后执行，新建 memtable 时轮询缓冲区执行就绪请求，保证两端 memtable 一致、既不丢数据也不冗余存储。评测在 CloudLab 服务器（r6525）上基于 Facebook 的 RocksDB 构建，用 YCSB 负载与 Twitter trace 对比逐实例 compaction 的复制版 RocksDB：write-only 负载 1.9 倍加速、Twitter cluster15 trace 1.7 倍（写越多节省越多），YCSB C 与 Twitter Class 2 等只读负载无提升（无 compaction），混合负载最高 1.4 倍；99% 尾延迟较基线最多降低 92% 与 93%（绝对延迟高因批大小为 1000），低压力下有一个数据点因请求缓冲出现 40% 延迟退化，高压力下收益抵消该开销。定量权衡（YCSB 100% insert、DB 30GB、副本因子 3）：三副本下节省 66% compaction CPU 与 144GB 读 I/O（secondary 无需读被删输入文件），代价是 SST 文件共享使网络 I/O 增至约 11GB，在高带宽数据中心网络可接受；NVMe-oF 是学界研究很少的协议，RoboDB 已在 GitHub 开源。（YouTube EP1Sjf79QyvrM，[669-1338]，L1）
- 〔USENIX Security〕Stitching the Gadgets：粗粒度 CFI 方案的系统性安全分析。报告人 Luca Davi（与学生 Daniel Lehmann、导师 Ahmad-Reza Sadeghi 及合作者 Fabian Monrose）围绕开放问题——是否存在实用且安全、能打破 ROP（return-oriented programming）图灵完备性的代码复用攻击防御——展开分析。近年微软 BlueHat 奖与 Microsoft EMET 工具推动了众多粗粒度 CFI（control flow integrity）方案，但报告带来坏消息：它们全部可被绕过。原始 CFI（Microsoft Research 2005）为控制流图各基本块打唯一标签并改写出口指令插入 CFI 检查，可提供细粒度保护，但有性能开销、依赖调试符号等难得信息，且依赖未公开的黑盒静态分析框架 Vulcan，精度无从得知；粗粒度 CFI 以减少标签数、简化检查换取实用性，但引入应用从未意图的新控制流路径。报告人评析近期方案：K-Bouncer 与 ROPecker 利用 Intel LBR（Last Branch Record）获取分支信息，RobGuard 与 Microsoft EMET 钩入 Win API 并检查栈上的 gadget 返回地址，CFI for code binaries 与 CCFIR 走二进制插桩路线；归纳出两条主要策略——返回只能指向 call 前置（call-preceded）指令序列、基于两条间接分支间序列长度的行为启发式（阈值 N）——并取各工具最严格设置构造 Uber CFI（同时启用两条策略且随时触发校验，任何单一工具都未强制），证明即便在此强对抗模型下攻击依然图灵完备。（YouTube EP1T3YZqW9uoY，[10-535]，L1）
- 〔USENIX Security〕仅凭 kernel32.dll 的图灵完备 gadget 集与三条根本教训。团队将 gadget 搜索限制在约 800KB、几乎被所有 Windows 应用链接的标准库 kernel32.dll，编写过滤器程序按寄存器、指令与操作数筛选指令序列，识别出覆盖通用寄存器装载、内存读写、算术逻辑运算及条件/无条件分支的图灵完备 gadget 集，并讨论仅允许 call 前置序列时的副作用补偿问题。所有 gadget 用 call 前置序列绕过策略一，但策略二的序列长度启发式会拦截短序列链，因此构造了通用长 NOP gadget：选择在小数据内存区执行大量受控静态值内存写的长序列，工作流为先执行真正的 ROP gadget、把将受影响的寄存器（如 ESI、EDI、EBP）暂存到栈上指定区域、初始化 ESI 与 EDI 指向小数据区，长 NOP 序列执行静态受控写并作为副作用顺便恢复暂存寄存器，随后可继续调用下一个 gadget 直到攻击完成。该 gadget 补偿副作用、对阈值变化足够鲁棒且可置于 gadget 链任意位置；团队据此改造了两个被 CFI 与 Microsoft EMET 检测的真实漏洞利用并成功利用。三条教训：一是 call 前置序列过多，即便极小代码库也足以支撑图灵完备 ROP，应回归原始 CFI 的 shadow stack 限制返回到原始调用者；二是启发式只是补丁式防御，长 NOP gadget 证明其无效，且大规模基准实验表明 K-Bouncer 与 ROPecker 现有阈值连续启用时已导致大量误报；三是间接跳转与调用目标仍过多，解析是难题，可借编译器支持补充信息（次日 USENIX 报告的 CFI 工作已解决 vtable 指针问题）。进行中的工作包括与 Intel 合作硬件软件协同设计实现细粒度 CFI、与微软合作改进 EMET 的 ROP 引擎；Q&A 中 UC Berkeley 的 Chao Zhang 询问 gadget 副作用判定，主讲人说明 PoC 利用采用栈溢出、JIT ROP 等相关工作也用过堆溢出。（YouTube EP1T3YZqW9uoY，[528-1070]，L1）
- 〔会议不详〕MaxTune 的问题剖析：多任务 PEFT 微调的性能瓶颈与现有方案局限。上海交通大学的 Chunyu 与新加坡国立大学合作提出 MaxTune，系统化审视数据中心多任务微调：OpenAI、Google Gemini 等服务商微调 API 的背后，集群调度器通常为每个任务启动独占实例（一组 GPU 与加载骨干参数的对象），PEFT 场景冻结骨干参数仅训练小尺寸适配器（LoRA 即 Low Rank Adaptation，与骨干并行维护适配器跟踪权重更新；PEFT 算法分加性、选择性与重参数化三类）。PEFT 负载面临两个严重性能问题：模型算子利用率（MFU）比全量预训练低 1.47 倍——源于 PEFT 算法引入的小规模算子（如秩为 8 的低秩投影利用率低但延迟不可忽视）及较短序列长度与较小批尺寸；多 GPU 下更糟：流水线并行无法用零气泡技术（冻结骨干无权重梯度计算、不能把反向拆成输入与权重梯度细粒度调度，直用会比标准 1F1B 流水线低 1.16 倍吞吐），张量并行因输入小、按 tile 拆分计算重叠通信反而进一步降低算子利用率（通信虽省、端到端延迟反增 1.17 倍）。现有方案各有关键局限：NVIDIA MPS 或多 CUDA 流粗粒度空间复用硬件受显存瓶颈制约（骨干占绝大部分显存、无法扩展到大模型或多并发任务）；复用冻结骨干的多 LoRA 服务式合批本质不同于训练场景，合批收益递减、放大流水线气泡、跨数据源合批引入大量 padding 浪费算力与显存；仅共享单一骨干并调度计算以重叠设备停顿的思路又忽视了算子级利用率提升。MaxTune 据此提出时空（spatial-temporal）复用共享骨干，并将复杂的多维耦合优化空间分层解为任务级（时间复用减少设备停顿、空间复用提升利用率，需代价模型与高效搜索算法）、算子级（stage 内与 stage 间并行调度）与数据级（消除跨任务无效 token）三层。（YouTube EP1eax8OQtXGk，[18-433]，L1）
- 〔会议不详〕MaxTune 的系统设计与评测：时空复用共享骨干。MaxTune 将现有 PEFT 算法抽象为四个子模块——骨干算子（Base OP）、适配器（PEFT 算子）、准备多任务输入的 dispatch 与合并输出张量的 aggregate——现有多任务实现将适配器硬编码进骨干层，增删单个任务需重新初始化整个模型、开销很高；MaxTune 解耦适配器，用 PyTorch hook 机制动态注册任务并挂接适配器，并保证运行时错误与前后向计算的任务隔离，确保不影响每个任务的微调收敛。在时空融合权衡上：时间复用交错所有任务微批次以重叠设备停顿，空间复用将其合批，前者在算子利用率高时更优、后者相反；MaxTune 提出 hybrid task 抽象（hybrid task 内合批、hybrid task 间交错调度），用代价模型估计各 hybrid task 的端到端延迟并以动态规划算法最小化整体流水线延迟。算子编排将任务进一步分桶：桶内子图按拓扑深度赋予优先级以优先队列调度（弹出零入度且延迟最长者），计算与通信在不同 CUDA 流自然重叠；流水线调度发现代价高昂的逐迭代排序不可取（计算同质性影响场景包括微批次形状跨迭代一致与同 stage 前反向延迟相等），改用静态流水线模板（按延迟排序批次、同桶微批次连续、尽早启动尽可能多）并证明了该模板的最优性（通过消解最后 stage 的内部气泡）。数据层对齐采用基于 chunk 的方案：先把各任务序列打包为统一长度长序列再均分为等大小 chunk，关键在于调整 chunk 内任务比例以平衡序列长度差且不浪费注意力（每 chunk 只含单条部分序列），实测权衡后块大小取 64。评测覆盖不同输入尺寸、模型类型与硬件：较其他基线取得 1.05–2.3 倍吞吐提升（设备越好提升越大），显存占用最高降低 5.29 倍，并做了加速比分解、编排效率与 chunk 对齐有效性等消融研究。（YouTube EP1eax8OQtXGk，[433-866]，L1）
- 〔会议不详〕GList 的动机：把图学习搬进 SSD。中国科学院大学的 Cangyuan Li 介绍图学习（图上的机器学习）：不同于 PageRank 等只挖掘纯图结构信息的传统图分析，图学习从带丰富属性数据（顶点与边上附属性向量）的属性图中挖掘高层模式，可做用户分类与未知关系预测，本文聚焦高效、可扩展且在业界渐受欢迎的图神经网络（GNN）方法。以社交网络关系预测为例，图学习分两阶段：为 Rick 与 Alice 获得嵌入向量、再以嵌入向量为输入预测关系概率；GNN 嵌入含三步——从大图中为两用户采样小子图、用聚合函数让样本用户特征沿边流向目标用户、合并阶段经神经网络得到嵌入向量，多层 GNN 会多次执行该流程（示例预测 Rick 认识 Alex 的概率为 70%，推荐系统据此互荐并可在原图新增边）。随着大规模图学习（如商用推荐系统）流行，其成本开销须被关注：执行时间分解为 host 内存到 GPU 显存加载、SSD 加载与 GPU 计算三段，SSD I/O 占总执行时间超过 50% 成为瓶颈，基准数据图规模超过 100GB 使 GPU 显存受限，另需面对高性能计算与数据局部性利用两大挑战。GList 是存储内图学习系统：主机侧用户库提供图更新、图注册、模型注册与图分析四类 API，调用经请求路径或数据路径转成 NVMe 命令经 PCIe 发往设备侧（基于含 FPGA、嵌入式处理器、闪存阵列与 DRAM 的硬件平台）；用户库还做空间局部性感知的图重组数据布局优化——闪存只能按 16KB 页操作而单条属性向量远小于 16KB，故把更可能同时访问的向量放入同一闪页以消除闪存带宽浪费。（YouTube EP1nVPY3nF87w，[9-557]，L1）
- 〔会议不详〕GList 运行时、存储内加速器与评测。GList 运行时运行在硬件平台的嵌入式处理器上，以局部性感知方式调度用户请求以最大化时间局部性：无优化时顺序服务会浪费闪存带宽（请求一与请求三访问同一闪页），重排请求二与请求三即可消除冗余访问。存储内图学习加速器实现于 FPGA，解决资源受限 SSD 中执行图学习负载的挑战：sample 算子由采样器单元处理，aggregate 与 combine 算子由 PE（处理单元）处理。原型基于 Cosmos OpenSSD 平台构建，以 CPU 与 GPU 两种图学习方案为基线，在节点级（如节点分类）、边级（如链路预测）与图级（如图分类）三类任务上各选两种常用算法与三到四个数据集评测：原型平均分别比 CPU 与 GPU 方案快 13 倍与 10 倍，归因于充分挖掘的数据局部性与高性能加速器；平均能耗分别较 CPU 与 GPU 方案降低 98.7% 与 98%。消融显示随特征维度增大，启用图重组与请求调度的吞吐始终高于另两个基线（特征维度达 60384 时提升变小，但常用数据集鲜有如此长的特征向量），调整请求局部性程度后请求调度策略能充分挖掘请求间的时间局部性。结论：GList 通过图重组与请求调度两种策略利用两类关键数据局部性，为节能图学习提供保障。（YouTube EP1nVPY3nF87w，[401-802]，L1）
