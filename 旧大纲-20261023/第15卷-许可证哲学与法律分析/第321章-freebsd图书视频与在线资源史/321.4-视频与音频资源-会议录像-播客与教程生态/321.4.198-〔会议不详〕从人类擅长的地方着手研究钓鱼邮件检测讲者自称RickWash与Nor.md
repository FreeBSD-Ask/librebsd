- 〔会议不详〕从人类擅长的地方着手研究钓鱼邮件检测。讲者自称 Rick Wash，与 Norbert、Tala 和 Emily Rader 一起做这项研究。他们采取的路径与多数钓鱼研究相反：现有研究大多先找出人们的弱点，再做培训去修补这些弱点；他们则关注人们本就擅长做什么，并设法让这些优势发挥得更好——与其要求用户去做他们不擅长的事，不如先弄清他们已经做得好的地方，再帮他们做得更好。本研究的取样方式是问卷，对象是约 300 名非专家邮件用户：问卷的好处是响应量大，还能让样本人口结构与如美国人口这样的总体相匹配，代价是只能问事先想到的问题。他们请受访者回忆一次自己成功识破的具体钓鱼邮件实例，并回答关于自己当时如何判断、采取了什么行动的问题；问题设计依据的是讲者去年发表的、研究 IT 专家如何识别钓鱼邮件的论文，那篇论文归纳出专家使用的六个步骤，本问卷据此为六个类别分别编写了自定义问题。先看知识：72% 的受访者觉得之前收到过类似的邮件，也就是这封钓鱼邮件让他们觉得眼熟；同时 95% 的受访者报告这封邮件出乎他们意料——他们平时收到的邮件大多是意料之中的，唯独这一封不是。正是对以往类似邮件的熟悉与这封邮件的意外性叠加，让他们心里有一幅这类邮件通常长什么样、通常包含什么的图景；86% 的受访者因此注意到这封钓鱼邮件不正常，缺少那些通常应有的元素。这种基于以往经验的知识是技术过滤器无法自动获得的，而人类做起来是自动的。除知识之外还有能力：94% 的受访者能记得邮件要求他们去做的那个动作，而这个动作让 76% 的受访者觉得不寻常——邮件常常要求用户采取行动，但只有用户本人能判断这个动作是否合乎自己的情境，而受访者似乎不假思索就在做；此外 73% 会故意延迟回复以便进一步调查，延迟有时很短（比如把光标悬停在邮箱地址上），也有不少情况人们会等一等再去问别人求助。（YouTube EPVinz9JW8C_Y，[15-242]，L1）
- 〔会议不详〕瑞士奶酪模型带来的系统设计结论。讲者把钓鱼检测类比为 James Reason 的瑞士奶酪事故预防模型：每一片奶酪是一层过滤器，能挡住许多钓鱼消息，但每片奶酪上都有孔；如果所有检测器都用同样的信息与能力，奶酪上的孔就会对齐，给恶意消息留出一条通路——比如要求人们去解析 URL 这类做法，就是在让孔对齐。而研究发现人们在识破钓鱼邮件时天然使用的知识与能力与计算机很不一样，意味着他们的孔处在与技术过滤器不同的位置。很多建议专注于让消息根本不要到达终端用户手中，但他的发现提示：把技术过滤与终端用户检测都纳入整个系统，能比仅靠技术过滤获得更宽的钓鱼检测范围；这一发现也说明可以通过培训用户更好地利用自身独特的知识与能力，来提升终端用户的钓鱼检测水平。（YouTube EPVinz9JW8C_Y，[243-319]，L1）
- 〔USENIX Security〕AMD SEV 的密文侧信道与常量时间密码破解。主讲人 Meng Yuanli 来自俄亥俄州立大学（Ohio State University），与导师 Yin Chen Zhang（南方科技大学）以及百度安全、蔚来安全研究的同事合作。报告先回顾 SEV 及其 SEV-ES、SEV-SNP 三代：SEV 建立在传统虚拟化与硬件内存加密之上，按对齐的 128 位块以 AES 加物理地址 tweak 的 XTS 模式在写入内存时自动加密、读回缓存时自动解密；SEV-ES 把 VM exit 时原本明文保存在 VMCB 中的寄存器状态改为加密存入 VM save area（VMSA）；SEV-SNP 再用反向映射表 RMP 维护地址转换与页面归属，防止嵌套页表与密文被篡改。团队指出 VMSA 中的寄存器密文攻击者只能读不能写，由此提出密文侧信道——攻击者强制产生 VM exit 并持续记录 VMSA 中的密文序列，即可从包含 CR0 与 CR3 的 60 字节块发生变化推断发生了上下文切换，并因 CR0 几乎不变而把该块密文当作不同进程的标识，还能进一步推断 RIP 与 IX 等寄存器的变化。（YouTube EPVmxpdPEFV0Y，[9-386]，L1）
- 〔USENIX Security〕密文-明文词典、端到端密钥窃取与硬件修复方向。团队利用必须向 hypervisor 暴露寄存器状态的 NAE 事件构建词典：执行 CPUID 指令会触发由硬件产生的 VMCALL 异常，客户机中的 VC handler 把所需寄存器状态复制到未加密的 guest-host 通信块 GHCB，随后触发 VM exit 交由 hypervisor 模拟 CPUID，此时攻击者可在 GHCB 中读到 RAX 与 RCX 的明文，再在与该明文对应的时刻记录 IX 的密文，从而在启动期覆盖明文 0 至 127 的全部取值。基于该词典，攻击者先用执行状态推断定位 OpenSSL 常量时间实现中的 BN_mod_exp_ct 与 bn_get_bits5，再按顺序撤销两者的 present 位、在拦截嵌套页错误时捕获恰为 bn_get_bits5 返回时刻的 IX 密文；2048 位 RSA 私钥需 410 轮，最终可 100% 精度还原整条私钥。类似地，借助 bn_is_bit_set 可窃取 ECDSA 随机数 k，因 IX 只存放 0 或 1、熵仅 1 bit，同样可达 100% 精度。结论强调这是 AMD 处理器上首个公开的新侧信道、也是已知首个针对 SEV-SNP 的攻击，AMD 将发布安全公告并为相关泄漏分配 CVE；硬件层面的两条修复路线分别是借 IOMMU 表限制软件对 VM 内存与 VM I/O 的读取，以及在寄存器写入 VMSA 时加入随机化。（YouTube EPVmxpdPEFV0Y，[386-739]，L1）
- 〔USENIX Security〕ICSFuzz：为工控控制应用带来插桩模糊测试。主讲人 Dimitris Nikolas 与 Hadjer Ben Braida、Michalis Maniatakos 合作。报告指出工业物联网与工业 4.0 推动了运营技术与信息技术融合，如今 PLC 上常见第三方 SoC 与 Linux 等通用操作系统，而控制逻辑被编译成既非 ELF 也非 PE 的私有汇编格式，无法直接丢给 AFL 之类的模糊器；这些应用由梯形图、结构化文本、功能块图等待机语言编写，可引入 memcpy 等低层内存管理库，并由运行时进程承载——作者选取 CODESYS 平台，其在 Linux 上表现为单二进制、多线程的运行时，各线程分别负责 Modbus 通信、OPC UA 服务或控制逻辑本身。研究据此把模糊测试拆解为输入投递、执行控制与执行反馈三要素：PLC 的扫描周期天然提供持续的执行控制；输入侧沿传感器—PLC 的 I/O 模块—GPIO 内存—K-bus 内存的路径追溯，锁定 K-bus 内存作为最可控的注入点，用内核模块覆写其中的传感器值，并借助运行时派生的 K-bus cycle task 发出的自定义 ioctl 异步信号与扫描周期同步，找准覆盖写时机。（YouTube EPVqRQ5h80YCI，[7-379]，L1）
- 〔USENIX Security〕NOP 复用插桩、执行反馈与实测收益。反馈侧通过改造运行时初始化脚本这一可塑的前身进程，用 wait 等系统调用跟踪从运行时派生出的控制应用线程的退出，从而获得崩溃反馈；插桩则利用控制应用二进制中随机插入的空操作（NOP）——它们本用于消除执行冒险——将其替换为记录当前程序计数器（PC）的存储指令，据此近似估计覆盖率。实测发现 GitHub 等在线仓库中的真实 PLC 二进制过于简单，不足以隐藏漏洞；只要把开源的反序列化流程复杂度稍作提升即触发崩溃，确认可达拒止服务。进一步在二进制中引入数组、字符串以及 memcpy、memmove 等函数后，崩溃大量涌现，根因是缓冲区溢出与越界读写，由此可注入 shellcode 经 TCP 反弹 shell，或通过系统调用写入内核模块、向被劫持进程植入伪装正常功能的 rootkit。运行时本身也会整体崩溃，故采用分而治之：逆向动态加载库引入的函数及其执行上下文，在桩里实例化并编译成新的 ELF，用 AFL 等模糊器测试，其中也复现了 2017 年报告的 sys_sock_recv 相关已知 CVE。结论认为 PLC 语言的高层性使二进制本身较健壮，但控制应用正沿上世纪八九十年代软件的演化路径变复杂、漏洞随之可被利用，而运行时与普通 C/C++ 软件一样脆弱，可波及整个工控计算栈。（YouTube EPVqRQ5h80YCI，[379-765]，L1）
- 〔USENIX ATC〕货架现成系统中的存内计算案例研究。主讲人 Joel Nider 来自加拿大温哥华的英属哥伦比亚大学（UBC），与 Alexandra Fedorova 团队及法国初创公司 UpMem 合作。报告从内存墙切入：计算机体系结构为 CPU 提供了超标量、多线程、乱序与推测执行等大量技巧，而 DRAM 几乎没有相应进展，内存子系统改进赶不上 CPU，PIM（存内计算）正是为此提出，借助内存巨大的内部带宽解决问题。作者按计算单元与内存的距离、硬件通用性、以及落到现有硬件上所需改造复杂度三个维度，把 PIM 归为三类：计算在内存之外（有效带宽低、依赖缓存、算力通用但搬数能耗高）、计算在内存阵列内（带宽极大而算力受限）、以及 UpMem 采用的折中路线（不在阵列内但仍紧邻内存，用牺牲部分带宽与容量换取通用处理器）。作者强调硬件实测不可替代——仿真模型只包含设计者认为最重要的特性、复杂度上升又拖慢仿真，遗漏之处往往要等硬件真的造出来才暴露；他们点名仿真常漏掉的特性包括 DPU 之间无通信、无虚拟内存支持、芯片交叉未建模、DPU 必须分组调度，以及存在未被建模的数据拷贝开销。（YouTube EPVrZSD45iRRE，[8-340]，L1）
- 〔USENIX ATC〕UpMem 的交叉与调度约束及其负载实测。UpMem 的芯片内含 8 个 DPU，每个 DPU 直连私有 64 MiB DRAM，DRAM 也可由主机经 DDR4 访问但与 DPU 访问互斥；无缓存，只有软件管理的 scratchpad 在 DPU 与 DRAM 之间做缓冲，配合隔离与专用 DMA 通道可获得可预测性能。由于芯片交叉在 1 字节粒度上把主机内存条带化到各芯片，DPU 读到的是每第 8 个字节的错位混合，UpMem SDK 因此须在每次进出 PIM 内存时做矩阵转置，把每 DDR 通道的有效带宽从约 16 GB/s 降到约 13 GB/s；更关键的瓶颈是数据进出被迫走 SDK，反而引入了 PIM 本欲消除的搬数开销。此外 DPU 之间根本不存在通信（共享 die、共享 chip、共享 DIMM、整机层面共四级延迟），且为最大化 DDR 总线效率必须按 rank（64 个 DPU）粒度做集群调度、批内任一 DPU 处理时主机无法访问该 rank 其余 DPU 的内存，只能分批处理。好的一面是扩展性：随 PIM 容量增加带宽与算力线性增长。作者挑选了与之契合的尴尬并行负载——Google 的 Snappy 压缩（随数据量超线性加速，但需微调文件格式以获得更好并行度）、超维计算（数据集不足 4 MiB 仍显著优于主机 CPU）与 AES 加密等；结论是加密这类计算密集型负载打不过 AES-NI 专用指令，PIM 适合内存受限负载、对计算受限负载偏弱，而 UpMem 在带宽与可编程性之间选了一个不错的折中点。（YouTube EPVrZSD45iRRE，[340-740]，L1）
- 〔USENIX FAST〕AegonKV：KV 分离 LSM 存储的 GC 瓶颈与卸载动机。主讲人 Bing Tian 来自华中科技大学，代缺席作者介绍该工作。KV 分离把值范围与 LSM 结构解耦，SSTable 只保存键及其在 blob 字段中的地址引用，地址范围显著缩小从而缓解读写放大；但值范围会累积过期数据，系统须做垃圾回收（GC）扫描整个 blob 并查询 LSM 决定过滤还是重写，带来额外 I/O 与计算开销。作者对比了两条既有路线：以 Titan、PKA 为代表的直接 GC 按块挑选高垃圾比例区域，但仍要查询 LSM；以 DiffKV、BlobDB 为代表的压缩触发式 GC 把单层 blob 改为多层，compaction 时直接迁移有效值，以压缩开销换取 LSM 带宽节省。写压测显示 BlobDB 与 DiffKV 相对 RocksDB 吞吐高 17% 以上、尾延迟低 50% 以上，但空间放大严重——同样的实验数据 RocksDB 只需 9 GB，BlobDB 与 DiffKV 分别占 135 GB 与 53 GB，而 Titan 仅多 2 GB、压缩 I/O 与读放大最优，却比 RocksDB 吞吐低 18%；关掉 GC 后 Titan 吞吐提升 67%，说明 GC 仍是瓶颈，而瓶颈来自 LSM 中间数据的读写争抢计算与带宽。方案依托三星 SmartSSD Z——业界首个可定制可编程的计算存储设备，片内 FPGA 可经内部总线传数、绕过复杂的 I/O 栈与系统总线。（YouTube EPVrbtfVkzPqY，[15-347]，L1）
- 〔USENIX FAST〕AegonKV 的 GC 管理器、无校验插入与实测收益。设计由 GC manager、GC scheduler 与 SSD 上的 GC 计算单元组成：为每个 blob view 建立位图形式的 valid map 标记各键值对有效性，由 compaction 结果更新并按垃圾比例生成任务；调度器把 CU 调度上移到软件层，控制使用的 CU 数量与各自的 FPGA DRAM 分配，并加入缓冲队列把多线程写请求合并为统一通道，避免写接口并发竞争。为消除元数据校验造成的带宽争用，作者采用无校验插入——原方案虽按批处理元数据，仍须逐个查找以避免旧数据条目覆盖 GC 写入的最新版本；AegonKV 直接把校验推迟到 get 与 compaction：读到 GC 合并数据时继续向后查询更旧版本并比较元数据中保存的原始地址以确定最新值，compaction 中同样回溯下一版本，并在 compaction 时把元数据提升为普通数据以降低推迟校验频率。硬件流程分为导入解码 blob 字段与 valid map、按 valid map 离散遍历由特征模块决定重写或忽略、以及输出编码三个阶段，全程无需主机介入。实测在三星一代 SmartSSD 上用 YCSB 与 Facebook 社交图、Twitter 集群负载评测：吞吐提升 1.1 至 4.6 倍并接近无 GC 场景，尾延迟降低 14% 至 85%，空间开销仅多 7% 至 75%，CPU 占用节省约 20%，能效提升 15% 至 17%；在社交图与集群负载上吞吐高 1.1 至 2.2 倍、尾延迟低 31% 至 55%，且优势不受 GC 线程数、批大小与负载比例等参数影响。（YouTube EPVrbtfVkzPqY，[347-930]，L1）
