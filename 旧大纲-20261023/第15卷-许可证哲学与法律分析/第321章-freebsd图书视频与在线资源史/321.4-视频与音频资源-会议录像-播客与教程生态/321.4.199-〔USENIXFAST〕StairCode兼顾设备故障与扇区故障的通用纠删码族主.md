# 321.4.199 〔USENIXFAST〕StairCode兼顾设备故障与扇区故障的通用纠删码族主

- 〔USENIX FAST〕StairCode：兼顾设备故障与扇区故障的通用纠删码族。主讲人 Patrick Lee 介绍其与博士后 Mingcheng Li 的合作工作，后者贡献了全部构思与评测。报告以现场测量立论：年磁盘故障率可达 1% 至 10%，扇区级的潜伏错误比整盘故障更常见，且扇区错误常以小突发形式出现（突发长度多数为 1 至 2、偶尔超过 5），故须同时容忍设备与扇区两类故障。作者先对比三类方案：传统 RAID 或纠删码只提供设备级容忍，即便只为一个扇区也要独占一整块校验设备；设备内冗余为每个设备附加校验扇区以抵御突发扇区错误，但只保护单个设备、不感知其它设备状态，存储开销同样高；Vijay Prakash 的 SD Code 用 M、N 与 S 三个参数兼顾设备与扇区，但现有构造限于 s 不超过 3。以 m=1、m′=2、两个部分故障盘分别有 1 个与 3 个扇区错误的混合场景（映射到 n=8 设备的阵列）为例，SD Code 需要 4 个扇区级校验而当前构造尚不可用，因此 StairCode 的目标是给出一个通用且空间高效的族——不限制阵列规模、可容忍设备故障数 m 与扇区错误数，校验量恰等于要保护的扇区错误数。其构件包括失败覆盖向量、由两阶段 MDS 编码构成的码结构，以及可复用已算校验结果、彼此互补的 upstairs 与 downstairs 两种编码方法。（YouTube EPVrgBHfk-Wro，[9-558]，L1）
- 〔USENIX FAST〕失败覆盖向量、全局校验与三项实测。失败覆盖向量 E=(E0,E1,…,Em′-1) 以模式取代 SD Code 的单一参数 s：先界定部分故障设备数 m′，再分别界定各设备的扇区错误上限，如 E=(1,3) 表示除整盘丢失外还可容忍一台盘至多 3 个扇区错误、另一台至多 1 个，各元素之和即每条带的扇区错误总数；当扇区错误分散而非突发时，把 E 取成 1,1,1,1 这类平坦向量即可。编码分两阶段：先用 Cauchy Reed-Solomon 沿行方向生成用于抵御设备故障的校验设备与中间校验，再用列方向 MDS 生成全局校验——它经中间校验间接依赖全部数据扇区，故称全局，用于抵御扇区错误。为把全局校验内嵌进条带，作者把它们当作 0 值、把 4 个数据扇区视为丢失后重建，从而不必额外落盘，并借助论文中的规范条带（canonical stripe）及其增广行完成恢复；upstairs 与 downstairs 两种方式结果相同、性能互补（m′ 较大用 upstairs、较小用 downstairs）。实现在 GFComplete 库之上并配多核 SSE 支持，对比传统 Reed-Solomon 与 SD Code 看三项指标：相对传统纠删码节省的设备数随条带扇区数 r 增大而趋近 m′，因为扇区级容忍只靠单个校验即完成；编码速度显著快于 SD Code（得益于校验复用），而更新代价与 SD Code 接近、略高；作者同时开源了 StairCode 代码，并在问答中承认随机 I/O 下恢复单个扇区需重读整条带。（YouTube EPVrgBHfk-Wro，[558-1628]，L1）
- 〔USENIX WOOT〕内核漏洞发现与利用生成自动化的知识系统化。主讲人 Andrea Vandin Bratti 来自 IBM Research，代表 IBM 的 Anil、Alessandro 与 Armisys 的 Vincent、Damian、Bernard 介绍这篇 SoK。报告先梳理脉络：2009 年 Sean Heelan 的硕士论文首次尝试自动化攻击，聚焦控制流劫持；2011 年 Avgerinos 等人提出今天所称的自动利用生成（automatic exploit generation），把链路延伸到最终提权，但都针对普通程序而非内核；2016 年 DARPA Cyber Grand Challenge 让多个团队在攻防 CTF 中研发攻防系统，大幅推动静态与动态技术走向成熟，可惜该赛事使用简化操作系统、只有 7 个系统调用，且只关注小规模本地程序的二进制代码、把控制指令指针就算作成果而非完整利用。作者把目光投向最终目标内核：一旦攻陷即可接管系统、攻击面庞大，而 Linux 近 4000 万行代码。威胁模型除本地与远程攻击者外，还包括容器、用户态沙箱（如 eBPF）、内核沙箱（攻击者身处 eBPF 程序内欲逃逸）以及 lockdown 模式下 root 访问受限的场景；新的分类学把参与完整利用的漏洞归为三类——precursor（单独几乎无危害，须与越界写等搭配，如整数溢出）、helper（危害大但不能直接达成目标，如绕过 KASLR 所需的信息泄漏）与 base（可直接达成目标）。（YouTube EPVsJlIOgMOpM，[10-472]，L1）
- 〔USENIX WOOT〕真实漏洞案例、五阶段流水线与五类开放问题。作者以 Google Project Zero 博客中 Yan Horn 的一则 UNIX 套接字域垃圾回收漏洞演示分类学：攻击者初始化带文件描述符与引用计数的 skb 对象，垃圾回收线程检查自己是否持有最终引用后释放对象，而攻击线程在取得文件描述符与递增计数之间只有约 12 条指令的窗口，使回收方误以为独占引用——该竞态属 precursor，叠加 use-after-free 构成可提权的 base 漏洞；利用 Linux 定时器精确同步两条线程的三种技巧属针对竞态的 helper，此外还需绕过 KASLR 与混淆内存的 helper 才能完成提权。利用流水线被归纳为五个阶段：定位漏洞、找到触发它的输入（模糊测试可一步兼得）、刻画漏洞能力（能越界写多少字节、是否任意值）、组合多漏洞制定利用策略、组装可复现的 PoC。作者据此从 2013 至 2023 年顶会及其引用文献中筛出 41 篇论文：22 篇聚焦第一阶段（14 篇静态分析、8 篇内核模糊测试），9 篇覆盖第三至第五阶段，10 篇把新技术引入内核。开放问题包括：多数工作威胁模型无关或默认本地攻击者，且只重提权与信息泄漏而忽视内核 DoS（近两三年已有严重 CVE）；仅 41 篇中 2 篇会枚举漏洞的全部可达路径以完整评估可利用性；S2E 这类符号执行引擎依赖庞大、可用内核版本受限，导致移植成本高；每篇自定内核版本与漏洞集使结果难以横向比较；基础工具被反复重新实现、缺少 API 且新功能不回馈主分支，加上不少论文不公开代码，令领域进展被拖慢。（YouTube EPVsJlIOgMOpM，[472-1362]，L1）
- 〔USENIX Security Enigma Track〕为软件包仓库提供签名与构建溯源。主讲人任职于 GitHub（参与运营 npm），这项工作由约 50 人通过 OpenSSF 的 Securing Software Repositories 工作组完成，已部署到 npm、Homebrew、PyPI、Maven Central 与 RubyGems。报告从上一讲留下的问题切入：如何让开源代码与最终运行的产物对应起来。包仓库每天承载数十亿次下载，链路是开源源码、构建系统（GitHub Actions、GitLab Pipelines 或开发者本机）、命名与版本号入注册表，再到 CLI 安装；攻击者可以只把恶意代码放进非主干分支或 fork、向审计较少的构建指令里插代码、在传输途中攻陷 CDN 与恶意缓存代理，甚至直接攻击通常由志愿者运营的注册表——这正是 OpenSSF 技术倡议 SLSA 所描述的软件供应链问题的中段。方案由软件签名与 SLSA 构建溯源两部分组成，后者提供回指确切源码、构建指令与构建日志的不可伪造链接，使下载的包可做更全面的审计。之所以不用 GPG：PyPI 十年前曾支持 GPG 签名的存储与分发，两年前的审计发现使用率极低、已上传签名多不可验证，根因是私钥长期保管与公钥可发现可验证这两个密钥问题，PyPI 遂于两年前移除 GPG 支持。新流程由构建平台的签名工作负载身份驱动：构建向平台申领包含源码、构建指令、仓库、组织等信息的 OIDC token（该 token 有二十多个字段），因由平台签名而无法被篡改；接着生成临时密钥对，用私钥签名后立刻丢弃私钥，以省去密钥生命周期管理与保管负担。（YouTube EPVti6Av5NPuU，[9-497]，L1）
- 〔USENIX Security Enigma Track〕签名包、可信发布、PyPI 完整性 API 与 Ultralytics 事件复盘。OIDC token 与公钥被送往公共善项目 Sigstore 的 Fulcio，由其验证 token 签名并返回把这些属性烧进扩展字段的 X.509 证书；签名同时上传到公共透明日志，验证时必须有该日志条目，用户因此可审计自己的身份何时被用于签名。签名、证书与日志条目构成签名包一并上传注册表；同一枚 OIDC token 还用于可信发布——与注册表建立信任关系，声明来自特定平台、仓库与构建指令的构建即可代为发布，从而把 API 密钥从流水线中彻底移除。作者强调把职责拆分到构建平台、Sigstore 与注册表三方是刻意设计：单点被攻陷不足以发布伪造内容，须跨系统协同。落地成本极低：GitHub Actions 里只需两处改动——授予工作流申领 OIDC token 的权限，并告诉 Python 打包工作组维护的 Action 需要证明。消费侧 PyPI 提供完整性 API，用 jq 取出证书、base64 解码并交给 OpenSSL，即可看到某个特定版本的 urllib3 在哪个平台构建、构建时的仓库哈希与源码位置。作者同时提醒：有构建溯源不等于安全，任何人都能在 GitHub 注册账号、向 PyPI 发布；溯源提供的是可审计的不可伪造链接，用于更有根据的风险判断。2024 年 PyPI 于年中部署该能力，同年 12 月 Ultralytics 遭攻击：其 GitHub Actions 用法允许通过 PR 分支名注入代码，攻击者借此获得仓库完全权限，发布两个恶意版本并窃取流水线中存放的 PyPI API 密钥，在 GitHub 权限被收回后又凭该密钥再发两个恶意版本。溯源让社区从恶意源码与构建日志中看到分支名提权与后续恶意步骤的完整链条，而后续版本缺失溯源这一巨大红旗又加速了处置；改用可信发布后，吊销 GitHub 访问权限即可保护该包。目前 npm 于 2023 年上线、随后 Homebrew 与 PyPI、RubyGems 跟进、今年 Maven Central 支持验证 Sigstore 签名，Kaggle 与 NVIDIA NGC 也用 Sigstore 签名模型；作者建议先做可信发布（更易实施、也让用户熟悉 OIDC token）再补构建溯源，目前已支持五六种构建系统，并正在探索 SLSA 源码溯源与 in-toto 的一系列证明类型。（YouTube EPVti6Av5NPuU，[499-1141]，L1）
- 〔USENIX NSDI〕Beamer：以链式转发实现无状态数据中心负载均衡。主讲人 Vlad 与 Alexandra Agache、Dave、Costin Raiciu 合作。报告给出数据中心负载均衡的现状：服务扩容后需要多副本以统一入口（服务虚拟 IP，VIP）对外，管理员在机群中部署多台 mux（负载均衡器），mux 用 BGP 向边界路由器通告 VIP 距自己一跳可达；包抵达边界路由器后被转给某个 mux，mux 封装后送往服务器的直接 IP（DIP），服务器则绕过 mux 直接回包——这一点对下行流量远大于上行的数据中心极为有利。同一条连接的包必须始终命中同一服务器（连接亲和），若按包做朴素哈希，新增服务器就会重置既有连接；业界因此普遍维护逐流状态，但状态化并不真正保证连接亲和：新增第二台 mux 会重哈希其上的既有连接并打断其中一条，而 SYN 洪泛会耗尽 mux 的流状态内存、使其退回朴素哈希。作者由此主张彻底无状态——mux 不保留逐流状态、独立地为每个包做负载均衡，被改派到无状态服务器的迷失包再由服务器依据已存状态重定向，该机制称为 daisy chaining；维护场景下先把手停机器的流量改派给另一台，由后者把存量连接回传给原有状态的服务器、只本地服务新连接，等待链式连接自然消亡。为同时追求低扰动、负载均衡均匀与尽量少的数据面规则（ECMP 均衡好但池子稍变就重定向大量流量、一致性哈希扰动小但分布差、Google 的 Maglev 二者兼得却规则数明显更多），Beamer 引入一层间接：桶数严格大于预期最大服务器数，每桶分配给一台服务器，所有 mux 共享由集中控制器维护的映射，包按桶数取模哈希，控制器可自由实现任何哈希方案。（YouTube EPVvvOUyzMpO0，[10-546]，L1）
- 〔USENIX NSDI〕实现、评测、控制平面与工程取舍。每个 mux 除知道某桶当前负责的服务器外，还知道上一次负责该桶的服务器及改派时间戳，这两项信息连同时间戳被放进每个封装包，于是服务器可据此把迷失包转回原服务器。设计因此极简：内存占用低于有状态对端、运行期缓存抖动小、所有 mux 处理完全一致因而彼此可互换，并对 SYN 洪泛免疫，代价是每封装包多出 16 字节；作者在 P4 上做了硬件实现。软件实现基于 Netmap；由于所有有状态负载均衡器都闭源，作者另实现了一个同架构的有状态版本作对照。单 mux 单核可达 600 万包每秒、包长大于 256 字节即可线速，加第二核后所有包长均线速，而有状态版本不足 300 万包每秒、约为其一半。回放真实流量时上行可达 36 Gbps，考虑下行约为上行 15 倍即约 540 Gbps；按每台服务器 1 至 10 Gbps 估计，一台 mux 可支撑 50 至 500 台服务器。10 Gbps 测试床（以 IBM RX 交换机作边界路由器，多数为软件 mux 并配一台基于 P4 参考实现的 mux 验证互操作性）显示：起始仅一台基于 P4 参考实现的 mux 只有 55 Mbps，60 秒时加入新 mux 后吞吐升至 10 Gbps，随后每隔 60 秒再加，流量随 mux 数量自然增长；模拟 mux 故障时吞吐下降但期间没有任何连接被中断；从单台服务器逐步增至多台、每 30 秒加一台时负载分布依然均匀；在 700 条存量连接、8 台服务器、后台 100 万包每秒 SYN 洪泛下，有状态方案丢失的连接数与所排水服务器数大致成比例，而 Beamer 一条未丢。控制面由容错控制器借助 ZooKeeper 集群存储与分发桶到 DIP 的映射，允许 mux 出现短暂陈旧状态，因为链式转发可容忍这种不一致；在 AWS EC2 上部署 100 台 mux 与 3 节点 ZooKeeper、模拟 6.4 万服务器与 640 万桶（每服务器 100 桶）时，增删 3.2 万服务器需 1 至 10 秒更新 ZooKeeper，各 mux 再花 0.5 至 6 秒下载新数据面，期间产生约 1 GB 控制流量（每 mux 约 10 MB）。作者另说明论文未展开的内容：MPTCP 支持（限 6.4 万服务器以内）、把 mux 规则从每桶一条压缩到每服务器一条，以及链式转发无法防止连接被重置的若干边角情形；问答中还说明实现仅面向 IPv4，每包需额外 12 字节携带上一服务器与改派时间戳并存放于非标准 IP 选项中，而二层封装只是便于在内核处理的取舍、并非不可或缺。（YouTube EPVvvOUyzMpO0，[546-1248]，L1）
