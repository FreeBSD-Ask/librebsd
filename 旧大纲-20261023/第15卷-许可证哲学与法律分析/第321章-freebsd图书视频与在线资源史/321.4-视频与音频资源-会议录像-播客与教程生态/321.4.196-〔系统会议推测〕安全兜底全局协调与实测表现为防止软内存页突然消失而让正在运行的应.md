- 〔系统会议（推测）〕安全兜底、全局协调与实测表现。为防止软内存页突然消失而让正在运行的应用崩溃，Midas 让软指针隐藏原始引用、只返回副本，应用因此永远不会直接触碰底层软内存页从而免于故障，运行时则捕获 segmentation fault 信号并安全恢复。多应用并发时由内核中的全局协调器负责分配：它周期性探测各应用对软内存大小的性能敏感度，把最不敏感应用手中的一小段内存转给从中获益最大的应用，逐步改善整体性能。团队在 Linux 上实现并移植了四个真实应用——SocialNet（基于微服务的论坛，用 Memcached 缓存时间线到帖子等各类用户内容）、MongoDB 使用的 WiredTiger（缓存 B+ 树节点）、HDSearch（图像搜索引擎，用页缓存降低磁盘 I/O），靠灵活的抽象往往只需改几行代码。把四应用共置于单机并供给 20GB 空闲内存、运行 35 分钟：静态分配只能达到理想吞吐的 49%，Midas 通过动态协调把整体吞吐提升 1.5 倍；相较过度配置方案，Midas 在保持接近理想性能的同时减少 71% 的内存占用。为验证能否应对内存压力，他们对 WiredTiger 施加内存攻击（第 5、10 分钟各以每秒 7GB 的速度、每次 5GB 分配），Midas 能迅速缩小软内存用量把使用量压回可用范围内，负载始终没有触发 OOM 被杀，仅短暂掉速并在数秒内靠重建软状态恢复正常。作者归纳其三项关键设计为软内存抽象、管理并驱逐软状态对象的运行时、以及紧急情况下可快速 unmap 的内核支持，Midas 已开源。（YouTube EPV_cEoA5wF_E，[596-1057]，L1）
- 〔应用密码学会议（推测）〕认证加密中的密钥承诺（key commitment）问题。作者列出 Anshul Battiti、Tai Tong、Shai Goron、Otto Lucks 与 Sophie Schmick 等合作者。认证加密是互联网上加密大量流量所用的基础原语：输入明文与密钥，输出密文与认证标签，任何一位翻转都会被检测为无效且不泄露明文。作者不改动密文，而是改动密钥，指出标准安全定义（如 IND-CCA2）并不覆盖这一情形；直觉上错误密钥解密应当报错，但并不总是如此。论文研究真实场景中这会引发什么问题、有哪些实际利用方式、以及如何简单高效地修补既有认证加密方案，并配套开发了可自动化攻击与生成实例的工具。第一个实例是各云厂商普遍推荐的信封加密：生成随机对称密钥加密数据，再为每个接收者分别把该密钥包裹在其公钥下附加到密文上；发送方并没有义务对每个接收者包裹同一个密钥，若对不同接收者包裹了不同密钥，由于各自密钥被加密在自己名下、彼此无法相互比对，双方却看到完全相同的二进制密文并误以为会解出相同内容。AWS Encryption SDK 2.0 之前的版本就因此存在该问题，现已修补。（YouTube EPVazqgsBwzOY，[8-599]，L1）
- 〔应用密码学会议（推测）〕把攻击落成有意义文件，以及如何补回密钥承诺。除信封加密外，近年冒出许多实际例子：密钥轮换后历史密文可能解出不同内容；Subscribe with Google 中被发现的案例；早期一个漂亮的实践案例出现在 Facebook 的消息排序（滥用举报）流程中；去年 USENIX 上的 partitioning oracle 攻击表明基于密码的认证密钥交换也会因缺少密钥承诺而受影响；ETH 的一个学生项目则发现 age 这一类似 PGP 的文件加密工具同样不是 key committing。作者指出 AES-GCM、ChaCha20-Poly1305 都不具备该性质，连看起来更稳健的 AES-GCM-SIV 与概念上不同的 OCB 也缺少它。利用时同时受限于密码学约束（需要随机块去校正认证标签、需要填充）与文件格式约束（魔数、固定头部、长度字段等），论文提供支持 40 多种文件格式、270 种组合的全自动工具，可把两份文件合并为一个密文：用不同密钥分别得到 PDF 与可执行文件；下载作者的 e-print 论文后加密，换一把密钥解密即可在浏览论文的同时得到一个 PDF 阅读器。以 HTML 为例，用注释把前后缀的随机字节注释掉：一把密钥得到 hello world 页面，另一把密钥得到指向 evil.com 的链接，浏览器照样渲染，用户若不作细看难以察觉。修补方面，可直接选用文献中已知的 key committing 方案，或用 AES counter 加 HMAC 这种看起来难以破坏的组合；论文则聚焦修补现有方案，针对 AES-GCM 给出两种修补选项，另有刚发表于 Eurocrypt 的论文从更一般的角度讨论对认证加密输入做承诺并给出高效构造。作者的最后提醒是：缺少密钥承诺在实践中确实构成问题，协议设计者应把这一属性纳入考虑；发表新认证加密方案时也不应忽视它——CCA 竞赛中的许多方案至今没有人知道是否具备密钥承诺。（YouTube EPVazqgsBwzOY，[600-736]，L1）
- 〔安全会议（推测）〕Viper：为数据仅攻击（data-only attack）挖掘 SysGuard 变量。主讲人 Hengkai Ye 来自 Penn State。几十年来控制流劫持是利用内存漏洞的主流手段：先取得任意读写之类的内存访问原语，再破坏返回地址或函数指针等控制数据从而偏离控制流；代码指针完整性、控制流完整性（CFI）等防御让如今劫持控制流已相当困难，但数据仅攻击仍然可行且威力不减——它只破坏非控制数据却能达成相近的恶意目的。因此关键问题是能否自动识别那些至关重要的非控制数据，即 critical data；控制数据有低层共性（特定类型、特定内存位置），而 critical data 建立在高层语义之上，通用分析在大程序上并不实际。已有工作要么靠人工审查代码、费力且不可扩展，要么只能识别具有显式源或明确汇（如系统调用参数）的变量，Clari 更是只能识别 Linux 内核中与 I/O 调用相关的密码学数据。作者以 OpenSSH 认证代码为例：循环中核对用户名密码、正确才把布尔量 authenticated 置 1 并登录，攻击者可借 packet read 中的漏洞把 authenticated 置 1 从而用错误密码登录，这个变量就是 critical data。对既有 17 个数据仅攻击的系统研究得出两点观察：多数攻击依赖与安全相关的系统调用（如 execve），而这些系统调用通常被形如条件判断的安全检查所守卫；这类分支即 SysGuard 分支，其中的变量即 SysGuard 变量。在上述案例中 11 个变量是此前 FlowStitch 之类工作能识别的，其余全部属于 SysGuard 变量，而它们难以识别有两个难点：符号执行只能给出通往系统调用的完整路径，说明不了哪些变量更关键；静态分析在处理间接调用与跨过程分析时受限。为此作者设计 BranchForce：用给定输入先跑一遍程序，记录访问过的分支与触发的系统调用，然后对路径上每条分支逐条强制翻转再运行，并挂钩系统调用，一旦出现新的安全相关系统调用，被翻转的分支即为 SysGuard 分支。（YouTube EPVb-cZd4B5NM，[8-352]，L1）
- 〔安全会议（推测）〕可利用性评估、Viper 流水线与 V8 端到端攻击。BranchForce 只能得到候选变量，未必都能被内存漏洞破坏，因此要做能力评估：对每个候选变量做后向数据流分析，并用两个指标估计被破坏的概率——内存位置（全局变量比堆上或栈上的变量更容易被破坏）与变量生命周期内的内存写指令数量（假设每条写指令被滥用的概率相同，写指令越多越危险）。Viper 流水线据此运行：先跑一遍程序收集系统调用与分支，再只翻转唯一分支、并用 fork server 复用来加速重执行，随后在 LLVM IR 层记录执行轨迹并基于轨迹做模拟与后向数据流分析，最终输出高概率的 SysGuard 变量。评估在 20 个程序上进行（9 个有已知数据仅攻击、7 个来自 FuzzBench、4 个其他常用程序），语料来自源码仓库、在线获取或以 AFL++ 模糊生成，最终从 14 个程序识别出 36 个 SysGuard 变量，其中 15 个与 unlink 或 rename 相关（可删除或覆盖文件）、10 个与 execve 相关（可执行任意代码）；在可利用性方面，16 个变量被确认在其生命周期内存在可提供内存写原语的 CVE，作者还在两个程序上构造了 4 个新攻击。多数程序的分析耗时在 5 分钟内即可完成，与用于自动生成数据仅攻击的 FlowStitch 处于同一量级，两者可以串联使用。最有代表性的端到端攻击针对拥有超过三百万行代码、被广泛使用的 JavaScript 引擎 V8：Viper 确认了一个高概率的全局变量 enable_ossystem——只有该值非零时才允许调用库函数 system，作者用一个旧 CVE 绕过 ASLR 并将其置 1，于是无需任何额外配置就能在默认设置下让脚本执行 system 命令跑起 shell。作者总结说 Viper 可自动定位数据仅攻击所需的 SysGuard 变量，工具与漏洞利用均已开源。（YouTube EPVb-cZd4B5NM，[353-658]，L1）
- 〔会议不详〕Elixir：考虑流量突发性的软硬件混合转发流程表管理。主讲人 Yanshu Wang 来自清华大学，与清华大学的 Professor Dan Li、Professor Jianping Wu、腾讯的 Yuan Weiliu 博士以及同事 Huashao、Yutian Wang 合作完成。随着越来越多的报头字段进入转发规则，匹配字段从单一目的 IP 扩展到多字段，网络设备上的流程表规模迅速膨胀；硬件转发快但片上内存装不下大流程表，软件又有能力上限，于是许多设备采用软硬件混合方式管理流程表：硬件先从报头提取字段做匹配，命中即按条目动作转发，未命中则上送 CPU 与软件流程表匹配。因此关键问题是如何把流程表在硬件与软件之间切分，而切分方式不仅影响转发性能，还决定了为软件转发预留的 CPU 资源。已有工作普遍借助流量天际线（traffic skyline），认为把最大的 10% 流量卸载到硬件就能省下最多 90% 的 CPU 资源，作者反问这是否真的成立。团队用峰值速率与平均速率之比衡量突发程度，结果显示突发型流量在真实流量中同样普遍；进一步在软件转发器 CPU 消耗固定的前提下比较成本，发现突发流量会带来更大的队列规模与更高时延，为避免丢包软件必须为它们预留更多资源。结论是仅考虑大流量的既有方法在纳入流量突发性后仍有改进空间。（YouTube EPVca9QIwnMgo，[12-460]，L1）
- 〔会议不详〕Elixir 的双路径设计与吞吐、CPU、时延表现。突发流量的普遍存在带来两项挑战。其一是精确测量：硬件流程绕过软件，纯软件测不准，而虽可在硬件上为每条流设置计数器，计数器又非常消耗资源，因此必须设计既精确又低成本的测量方法。其二是替换时机：商用方案采用周期性替换，窗口太小会导致流程表被频繁替换从而降低转发速度，窗口太大又可能让平均速率低于稳定流量的突发流留在软件侧，进而被迫为它们预留更多 CPU。Elixir 分而治之：因为大流通常包含大量报文，少量采样即可获得准确信息，故以低采样率把硬件流量采样到软件侧用于大流识别，而对突发流则为每条分配硬件计数器、由软件读取以获得精确速率；在替换策略上，把大流的替换与突发流的替换分开——大流排名会随时间变化，用一个较大的周期性窗口处理以降低替换频率，而突发流出现不规则，改用事件驱动流程，一旦硬件上处理器超过预设阈值就触发软件去比对硬件与软件的计数器并尽快把突发流卸载到硬件。硬件流程表因此被划分为大流区与突发流区，软件流程表则被共享。与 TFO（用滑动窗口识别并替换大流）、LFP（用学习方法预测并替换大流）以及纯软件转发 PSF 三个基线相比，评估覆盖软件侧流量速率、CPU 消耗、转发能力、时延与丢包率：Elixir 能把软件侧转发流量长期稳定地压在低位，而其他方法会出现多次软件流量突发；在相同流量与相同丢包条件下，Elixir 较 PSF 节省 81% 的 CPU 资源、较 TFO 与 LFP 节省约 50%；在无丢包条件下 Elixir 的最大转发速率几乎是 TFO 与 LFP 的两倍，说明感知突发的卸载让硬件转发能力被更充分地利用；尾时延较 TFO 与 LFP 低约 97%，丢包率也更低。作者总结 Elixir 是首个考虑流量突发性的软硬件混合流程表管理系统。（YouTube EPVca9QIwnMgo，[461-873]，L1）
