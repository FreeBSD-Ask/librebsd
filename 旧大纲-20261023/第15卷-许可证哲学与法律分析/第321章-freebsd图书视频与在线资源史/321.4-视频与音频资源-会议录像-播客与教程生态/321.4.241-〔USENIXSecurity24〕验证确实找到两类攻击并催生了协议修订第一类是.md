- 〔USENIX Security '24〕验证确实找到两类攻击，并催生了协议修订。第一类是理论性的 key confusion：初版规范中 Alex 无法区分被签名的椭圆曲线预密钥与后量子 KEM 密钥，攻击者可互换两者迫使不安全计算；实践中密钥编码里有 key type 字节因而无法成真，但此类细节必须写进规范。第二类更实质：作者发现"assuming only chosen ciphertext attack indistinguishability"〔10:00〕对 KEM 而言无法证明协议安全，ProVerif 直接给出反例——简化版中 Alex 与 Robbie 诚实建联后，Robbie 把刚得到的共享秘密重新封装到 Blake 的 PQ 公钥下再发过去，两段本应独立的会话于是共享短期材料，session independence 丢失；更完整的版本表明，泄露单个 KEM 密钥即可破坏该方此后全部未泄露 KEM 密钥上的先采后破保护。快速修正是把 KEM 公钥放进 AEAD 关联数据；由此进入新一轮修订，细化原语密码假设、关键标识符用法、编码取值范围并明确关联数据，随后在符号与计算两种模型下证明 PQXDH 达到其经典与后量子安全目标。此外作者提出半诚实合谋抵抗 semi-honest collusion resistance，并强调这"not saying that this is a property that scheme designers should target"〔12:40〕，而是证明 PQXDH 安全所确需的性质；据此可证 Kyber 第三轮满足，并与 X3DH 论文的密文冲突抵抗（逻辑独立）及 Keeping up with the KEMs 的一组密钥绑定性质（其中一个可平凡推出该性质）作对比。结论是"designing P Q protocols is about a lot more than just dropping in P Q crypto"〔13:35〕，形式化验证是找出并规避这些陷阱的有力而实用手段，而 Signal 最大的体会是协议设计者与证明工程师紧密协作才能快速产出有效的协议与实现修订；ratchet 的后量子化等后续工作正在进行。（YouTube EPZg9WJlQnXoc，[436-865]，L1）
- 〔USENIX ATC '24〕华为加拿大网络与协议团队提出 Panorama，把软件定义网络下沉到每一位终端用户，对实时应用的端到端路由做联合优化。讲者 Geng Li 指出实时交互应用用户数指数增长——"The video conferencing product have increased like thirty or forty times since COVID nineteen"〔00:48〕——在线游戏、VR/AR 与直播进一步抬高了时延、吞吐与丢包要求，而"transparent latency over three hundred millisecond would become unacceptable for video streaming"〔01:21〕；但互联网自设计之初即尽力而为，"The Internet is connected by BGP and the route basically is selected by the commercial relationship instead of performance"〔01:57〕，路径对这类应用并不最优。为此业界自建 overlay 网络：由分布式 service edge 作为中继，连通性可混合私网链路与公网链路，其部署即为混合形态——私网链路按圈星拓扑连关键 overlay，公网链路在 SE 间全连接，转发设备上装两块不同网卡即可承载二者共存，公网被证明不仅是低成本过渡手段而可能是趋势。传统做法是 nearby access 加 backbone optimization：每用户就近接入时延最小的 SE，再在骨干网用周期采集时延加最短路算法选路，AWS 与 Google 等加速网络即依赖"骨干质量远优于公网"这一前提。混合部署下暴露四类问题：接入与骨干各自优化导致端到端次优——阿根廷到葡萄牙用户各就近接入巴西与迪拜时总时延约 260 ms，而让阿根廷用户改接巴西可达 140 ms；低时延路径可能伴随大抖动——UAE 到香港时迪拜到印度链路抖动很高，第二低时延路径抖动很低；时延与成本间缺少权衡——阿根廷到泰国最低时延需五跳而两跳路径时延相近；以及 SE 间负载不均。作者据此提出"Panorama, a scalable system for providing desired user experience to real-time applications over the overlay network"〔09:22〕，需应对紧密 SLA、全球端到端联合优化与百万级日活三大挑战。（YouTube EPZhFfR3Olbc0，[17-620]，L1）
- 〔USENIX ATC '24〕讲者随后展开 Panorama 的系统设计与实测收益。系统含一个逻辑集中的控制平面为所有通信会话计算并管理 overlay 路由，多个 route server 卸载百万用户的路由查询并把服务推近用户，另有 SDK 让开发者以两种方式接入——客户端覆盖移动端与桌面，后端覆盖 web server、CDN、SFU 与 HTTP server；API 分初始化与发送数据两组，应用只需创建本地 socket FD 即可发包，工作流为向 route server 取路、按返回路径以源路由加封装转发。可伸缩性是处理百万用户的主要挑战，因此引入用户与会话分组：最小粒度为用户组（IP 前缀约 /22 至 /24），把全部 SE 按时延升序排列后合并"top-2 SE 相同"的 /24 块，于是"from seven hundred fifty k active IP blocks. We will only need three K user group"〔13:31〕、约三十个 SE。路由与流量工程分三阶段：先在拓扑与真实测量基础上算 top-K 最短路，采用"one big switch"抽象复用骨干网 KSP，用户组只能选 SE 作入出口再叠加接入段时延比较端到端总时延，并借助强化学习优化搜索，百万级会话组一分钟内可算完；再依"the S L A requirement is defined as three upper bound thresholds of latency, jitter and loss"〔16:03〕按服务类别过滤不可达路径并留出代价分级；最后把剩余路径集建模为简化多商品流问题，以平衡负载、最小化代价加权最大链路利用率为目标求各路径权重，控制器默认每五分钟运行一次。评估使用真实部署中"eighty one million session instances"〔17:19〕，覆盖三十余个地域与六十六个国家：相对就近接入法在 p50、p90、p99 上分别改善约 10%、17%、23%，对百毫秒内短距会话虽有负收益但用户不可感知；其真正价值如作者所言"the main benefit of Panaro is not to turn a good quality session into a great quality session, but to change a bad quality session into good quality ones"〔18:42〕——超过三百毫秒的会话相对就近法减少约 97%、相对直连减少 99%，约 96% 会话时延可压到 200 毫秒以下。（YouTube EPZhFfR3Olbc0，[620-1223]，L1）
- 〔USENIX Security '14〕讲者论证 K-bouncer 与 ROPecker 一类"基于有限执行历史的 ROP 检测"防御可被系统性绕过，因此并不真正抬高攻击门槛。先补背景：十五年前利用内存破坏漏洞靠代码注入——把新指令写进进程、覆盖函数指针或返回地址后等其被调用；DEP 规定页只能可写或可执行而不能兼有，使栈与堆不可执行，彻底阻断注入，但留下了 ROP——"every attack is a return oriented programming attack because DEP is so widely deployed"〔01:16〕。ROP 的原理是把现存指令重新串接成新计算：挑选若干指令，其中最后一个以 return 结尾即可跳到攻击者控制的下一处，如此反复拼接，一段短指令序列被称为 gadget。防御方面 ASLR 普及最广但 ROP 攻击第一件事就是绕过它，CFI 另有他人工作讨论，本文聚焦较新的 K-bouncer 与 ROPecker。K-bouncer 的思路是在系统调用处检查近期执行历史，靠 Intel CPU 上的 last branch record 硬件寄存器"look at the last sixteen indirect branches which have executed"〔03:29〕，据此判断当前行为像 ROP 还是正常执行，正常则放行、攻击则杀进程；它做两项判定：其一，"rop attacks tend to issue returns to non-call preceded locations"〔04:10〕——正常程序中 return 必回到 call 之后的位置，故只允许 return 目标为 call-preceded 地址；其二，"define a gadget as a sequence of twenty or fewer instructions ending in a return"〔05:35〕，并禁止连续八个及以上短 gadget 组成的长链，因为正常程序通常是"大段计算 + return"交替。作者承认该防御吸引力很大——"K-Bouncer has basically no overhead"〔06:31〕，可在现有硬件透明部署——但随即断言"I'm going to argue that it does not"抬高门槛〔06:49〕。第一个攻击是 history flushing：全部攻击目标只是发出一次系统调用，为此构造 large no-op gadget，它同时是 call-preceded、长度超过二十条指令以越过防御阈值、且"an effective no-op"〔07:25〕，这类 gadget 在几乎所有程序中都易得；于是在发出系统调用前反复插入它，LBR 会被这些 no-op 填满，K-bouncer 能看到的历史里已无 ROP 痕迹。（YouTube EPZiffYSALxiQ，[10-517]，L1）
- 〔USENIX Security '14〕攻击收尾并推广到"无限历史"变体，随后讨论对防御设计的普遍含义。作者明确"this breaks K Bouncer"〔08:42〕，更彻底地说"it really breaks any limited history defense"〔08:44〕——任何只依赖有限历史且只在末尾检查的防御都可被同一手法击穿。显而易见的补救是把 LBR 做到无限长，等价于让 K-bouncer 常驻于每一时刻；这一 improved K-bouncer 确实能挡住 history flushing，因为它会在 ROP 刚出现时就杀进程，攻击者根本来不及发出系统调用。但作者给出新攻击：call-preceded 检测本身不充分，"we managed to show that call proceeded attacks are possible"〔10:19〕，作者在十个约两万条指令的 user bin 二进制中均找到足以构造完整 call-preceded ROP 的 gadget，规模与 user bin diff 相当，因此更大的程序里 gadget 更充裕。改进做法是复用前述 long no-op gadget：把 call-preceded 的 exploit 切成若干小块，每块之间插入这个长 no-op，于是 K-bouncer 在任意时刻看到的都是"若干短 gadget 加一个超过二十条指令因而不被归类为 gadget 的长片段"，其长度低于攻击检测阈值；作者由此断言"even with unlimited history, ROP attacks are still possible"〔11:47〕。ROPecker 即 NDSS 上公布的与 improved K-bouncer 基本等价的防御，其差异反而让攻击更有力。实验上 K-bouncer 原论文宣称可防六个真实漏洞，作者取其中四个改为更隐蔽版本使其在 K-bouncer 存在下仍然有效，另外两个因无法运行而无法验证，而"it took us about an afternoon"〔12:43〕——对真正的 exploit 开发者算不上障碍。对防御设计的三条含义是：不能依赖有限历史；call-preceded ROP 可行且极易，CFI 需要回到带 shadow stack 的完整实现，CFI-light 方案均被击穿；以及 K-bouncer 式"二十条以内为 gadget、以外为正常代码"的二分极难成立甚至可能根本不可行——防御应聚焦正常执行与 ROP 攻击之间的本质差异。问答确认两种字长均适用，四个被改造的 exploit 两个 32 位、两个 64 位，仅原始 exploit 复杂度不同。（YouTube EPZiffYSALxiQ，[517-1024]，L1）
- 〔USENIX Security '24〕来自 KTH 的研究者 Eric 提出 GHunter，把原型污染自动升级为运行时级的"通用 gadget"发现流水线。先讲背景：JavaScript 的继承本质基于原型，既有对象被复用充当父类——对象 A 通过 __proto__ 指向根 Object.prototype 从而获得 toString 等能力，对象 B 的 __proto__ 指向 A 则传递性继承自根原型。问题在于"there is no certification"〔00:56〕：本应存在的"反射式访问父类"与"常规编程构造"之间的分层在 JS 中并不存在，因为"dunder proto is just a regular string that anyone can access"〔01:26〕。演示用一个把用户键值对存于内存的 web server：正常用户传入数字 ID 只会在自己对象里写键值；恶意用户把 user ID 声称成 __proto__，服务器照办，把攻击者指定的键值写入根对象原型，于是运行时里所有对象都继承了这一对——这就是 prototype pollution，即"the lack of stratification leads to pollution"〔02:06〕。进一步引入 gadget 概念："a gadget is a piece of code that's otherwise benign, but inadvertently reads from such a polluted property and then performs some security sensitive operation"〔02:18〕。同一 server 中执行固定命令字符串的 exec 看似安全，但其 API 内部会取一个 options 对象并在缺省时实例化默认对象，随后询问 options 是否有 shell 属性——攻击者污染的 shell 恰好被读到、存入局部变量并用于真正执行命令，于是攻击者控制的 calc 被起进程，"will have a remote command execution"〔03:28〕。目标进一步收窄为 universal gadget：它"are gadgets that are present in the JavaScript runtime themselves"〔03:42〕，因而影响运行在其上几乎所有的程序；研究问题即"can we find such universal gadgets automatically and efficiently"〔03:56〕，威胁模型取 Node.js 与 Deno 上的服务端 JavaScript/TypeScript 应用，假定应用本身可被污染，攻击面覆盖任意代码执行与 SSRF 等类别。（YouTube EPZjTJNiyS9Yg，[8-335]，L1）
- 〔USENIX Security '24〕讲者给出 GHunter 的三阶段半自动流水线与发现结果。方法核心是以运行时自带测试套件为驱动：Node.js 套件约四千个测试、Deno 约五千五百个，两者均取得超过百分之九十的函数覆盖。第一步运行测试以发现 undefined property read——作者改造 V8 引擎（约八个文件、两百行改动），在缺失属性读取发生时将其记录以便后续引用；由于 V8 为 Node.js 与 Deno 共用，这一处改动同时惠及两个运行时。第二步以检测到的属性作为输入再次运行测试，寻找从 source 到 sink 的数据流：sink 定义为一切流入原生代码的路径，既包括 Node.js 与 Deno 为交互系统提供的 binding code，也包括 eval 等动态代码执行 API；于是每个测试对每个属性各跑一次，用固定魔数污染该属性，一旦命中 shell 这类真实被读取的属性，污染值便顺着局部变量与模板字面量流入 spawn sink，检测手段是检查 sink 调用的全部参数中是否出现该魔数，即"a form of very lightweight state tracking"〔08:00〕。第三步再以同一批属性跑一次并关注 segfault 等非预期终止，且刻意在完全未改动的引擎上进行，以排除自身改动造成的假阳性；随后合并前两步结果、去重并输出 SARIF 候选，人工复核并在可能的地方构造 PoC。最终"we found fifty six such gadgets in node js and sixty seven in deno"〔09:09〕，覆盖多类攻击：Node.js 中污染 source 属性可使相对导入不导入文件而直接执行脚本，构成任意代码执行；Deno 中污染四个属性即可接管 fetch 的 URL、method、body 与 headers，把请求改写成另一个完全不同的请求，构成 SSRF；两个运行时合计"one hundred twenty three exploitable gadgets"〔10:14〕，全部收录于独立仓库并与既有 gadget 一并发布。论文还对照提出 universal gadget 概念的 Silent Spring 一文，梳理并系统化既有缓解措施，并在实测中发现 Kibana 上"one new high severity exploit in Kibana due to an incorrectly fixed gadget"〔10:43〕。（YouTube EPZjTJNiyS9Yg，[335-662]，L1）
