- 〔LISA〕Red Hat IT 的开源身份管理基础设施全景。Red Hat IT 身份与访问管理团队（Brian Atkinson，自述第六次到会 LISA、首次演讲）介绍其支撑 redhat.com、access.redhat.com 等生产系统的技术栈：基础设施以 RHEL、RHEV 虚拟化（约 200 台 hypervisor）、Cisco UCS、NetApp、Gluster 为基础，配置管理自 2008 年从 CFEngine 全面转向 Puppet（每模块一个 Git 仓库、43 台 puppet master、提交钩子强制语法检查与分支父子关系）；用户数据以 Red Hat Directory Server/389DS 为权威（约 36 节点、13 万对象），除 POSIX 账号外还存邮件路由（8 万别名）、应用角色与 GPG/SSH 公钥，并通过 PAM pass-through 插件避免在 LDAP 中存密码、将密码留在 Kerberos。（YouTube EP2GWyAodwMwk，[9.8-2029.0]，L1）
- 〔LISA〕Kerberos、OTP、SAML 与 PKI 的统一 SSO 实践及 FreeIPA 展望。Kerberos realm 与公司同龄、单主结构是明年待修的单点故障，配合 SSSD 实现笔记本离线认证；两步认证在 RSA 泄密事件后改用 LinOTP，软硬令牌（FreeOTP、Gemalto、YubiKey）经 RADIUS 与 LDAP 插件接入；自建 SAML IdP 基于 JBoss PicketLink，为社区贡献了 GSSAPI 支持、OTP 会话复制并修补 mod_auth_mellon（随 RHEL 6.6 收录），约 20 个服务提供方接入后 GSSAPI 集成带来两倍流量增长；PKI 采用 Red Hat Certificate System/Dogtag 的多层离线 CA 与 HSM 设计；最后展望将 Kerberos、LDAP、PKI 融合的 FreeIPA/IDM 与 Ipsilon 项目，计划下一年度内部落地。（YouTube EP2GWyAodwMwk，[2032.8-4670.6]，L1）
- 〔SOSP〕云存储需要能自动重配置的配置服务。主讲人（与刚博士毕业于巴黎大学、即将加入普渡大学的 Masoud Sayedahmadi 合作）在去年 SOSP 发表的 Pileus 系统之上构建配置服务：配置由主副本集合及其所在数据中心、次级副本位置与同步频率构成，服务依据各客户端的一致性 SLA、聚合读写速率与到各数据中心的往返时延，以按读操作数加权的平均效用为目标，结合基于 Azure 定价的成本模型，在副本数量、数据地域与成本约束下选出每美元期望效用最大的配置。（YouTube EP2IzmIAgxJy8，[9.8-711.4]，L1）
- 〔SOSP〕不中断客户端的自动迁移与客户端快慢模式。迁移通过 RIP 标志加 delta 秒等待、利用 Pileus 多主复制先让新主接收新写、再由旧主向新主后台同步补齐旧数据，两阶段完成主副本搬迁且全程不静默系统；客户端经共享 Azure Blob 与配置服务通信（无直接网络连接），获得带租约的配置缓存并分快慢两模式，慢模式下强一致读需复核所读副本仍为主、写需对配置加锁；在亚/欧/美三数据中心、最快每 4 小时重配置的 YCSB 评估中，强一致读占比从 33% 提升到 49%，并显著降低效用波动。（YouTube EP2IzmIAgxJy8，[713.2-1489.1]，L1）
- 〔OSDI〕串行性能优化的三条原则与八大方法论。佐治亚理工的 Susan 报告一项系统化知识（SoK）工作：人工审阅 OSDI 与 SOSP 十年间的 477 篇论文（其中 206 篇聚焦性能优化），将所有串行优化归结为删除（remove）、替换（replace）与重排（reorder）三条原则，并从真实系统中归纳出批处理、缓存、预计算、延迟执行、上下文化等八种反复出现的方法论，构成统一分析框架，指出并行化受 Amdahl 定律限制后串行部分仍是瓶颈。（YouTube EP2VVhijxfkk4，[17.5-435.3]，L1）
- 〔OSDI〕框架应用：从 OSDI'22 的 Sync 锁分析出发发现被忽视的优化机会。作者详解批处理（合并高开销重复调用、丢弃过期任务、提升时空局部性）、延迟执行（移出关键路径、依赖投机）与上下文化（收集内存压力、请求模式等运行时上下文改进后续决策）三种方法论，并将 Sync 锁的线程队列重排映射到框架；据此提出原论文未采用的两个优化——在线程缓存行存元数据（缓存，吞吐提升 23% 以上）与直接运行已验证策略代码去除间接层（layering，再提升 14%），同时发布了网页版性能手册与基于八大方法论给出优化建议的 SysGPT。（YouTube EP2VVhijxfkk4，[415.8-864.0]，L1）
- 〔会议不详〕覆盖引导内核模糊测试难以触发的内存缺陷需要动作制导补充。加州大学圣巴巴拉分校博士生 Marius（与明尼苏达大学、EPFL 合作）指出 Google Syzkaller 全天候运行仍漏掉潜伏 15 年的 Linux 内核漏洞；use-after-free、越界等内存缺陷需同时满足空间（同一缓冲区）与时间（调用顺序）约束，而以未预期顺序调用系统调用会走浅层错误路径、覆盖率低而被覆盖引导 fuzzer 判为无趣放弃；为此提出 darts（dart）概念——系统调用、内核动作与调用栈的三元组，通过动作挖掘按共享内存关系分组，再以模板或 DSL 驱动程序合成生成潜在致错序列。（YouTube EP2WEAVyoy3Bw，[8.1-321.2]，L1）
- 〔会议不详〕原型 Actor 的实现与评测：十日在四个 Linux 内核版本发现 41 个新漏洞。分组先按地址、再跨程序按类型与调用栈合并为操作同一逻辑缓冲区的组；程序合成按 use-after-free 等七类漏洞模板排列动作顺序以解决时间约束。原型 Actor 基于成熟覆盖引导 fuzzer 构建，在开发内核上动作重触发率超过 50%，跨模板生成致错程序能力均优于 Syzkaller（use-after-free、越界等复杂模板优势更明显）；在长期支持与稳定版内核上运行十天发现 41 个新漏洞，24 个可稳定复现并上报，13 个确认、9 个已修复，其中 26 个为内存破坏。（YouTube EP2WEAVyoy3Bw，[312.8-634.3]，L1）
- 〔会议不详〕Kubernetes 控制平面成为 Serverless 突发负载的瓶颈。北京大学的 Zhang 指出 FaaS 平台普遍构建在 Kubernetes 之上，但其状态中心、控制器链式协作的设计在 FaaS 每分钟上万实例创建的突发下被放大——一次扩容调用展开为跨多个控制器的状态转换链，经 API server 与 etcd 逐级持久化并可能被限流，数百实例置备需数十秒；而 Azure Functions 轨迹显示函数平均仅约 800 毫秒、沙箱启动已优化至毫秒级，控制面延迟主导函数服务关键路径与尾延迟；相比干净重造（如 Dirigent）牺牲兼容性，KubeDirector 选择性能与生态兼容兼得。（YouTube EP2gU8QUAgl-s，[18.3-451.7]，L1）
- 〔会议不详〕绕过 API server 的直接 P2P 消息传递与层级写回缓存。核心洞察是控制器链具有顺序写（每级单一权威写者）与回滚容忍（半置备实例无外部副作用、无需持久化）两个性质，可在窄腰处绕过 API server 与 etcd；针对快速转发可能在 kubelet 驱逐后复活 Pod 的异常，将下游真相回喂上游作为缓存失效信号（断连/崩溃用硬失效同步握手、连接存活期用软失效异步增量反馈），终止语义不可回滚则用墓碑（tombstone）对象按链复制方式惰性回收；每控制器仅改约 150 行代码，80 节点集群上相对 Kubernetes 扩容总延迟改善 3.7 到 16.9 倍，Azure Functions 轨迹回放下调度的每函数延迟降低 26.7 倍、性能与 Dirigent 相当，且仍兼容 Prometheus、Istio 等扩展。（YouTube EP2gU8QUAgl-s，[356.4-926.7]，L1）
- 〔FAST（推测）〕阿里云弹性块存储三代演进的前两代。阿里巴巴集团的魏东（Wei Dong Zhang，阿里集团）回顾 EBS 十二年演进：2012 年发布的 EBS1 将虚拟盘 LBA 切分为固定大小块、两层架构三副本写在 ext4 文件上，就地更新与 N:1 映射简单但热盘易拖垮块服务器、且因对齐问题难以叠加压缩与纠删码；2015 年的 EBS2 引入追加式分布式文件系统 Pangu 与日志结构块设备核心 LSBD，以 128GB 段组/32GB 段的磁盘分段改善负载均衡，借垃圾收集时机做纠删码与压缩，空间成本从 3 降至 0.69，扩展到 500 余集群 200 万虚拟盘，平均写延迟 100 微秒、最高百万 IOPS。（YouTube EP37X8vCuLDRg，[15.8-540.2]，L1）
- 〔FAST（推测）〕EBS3 的 Fabricated 快速路径与弹性四要素。SSD 降价后瓶颈从空间转向流量，EBS3（2019 年发布，部署超 100 个存储集群、50 万虚拟盘）用 FPGA 混合压缩多用户写请求生成 journal 文件、以段缓存聚积读请求做大块纠删码，把写流量放大从 4.69 降到 1.59 且性能不降；弹性方面延迟由架构决定，EBS X 以持久内存（PMEM）跳过第二跳网络服务延迟敏感场景，5-9 尾延迟主要来自块服务器非 I/O 处理而非硬件故障，吞吐/IOPS 上限由客户端决定并支持按需自动性能等级（auto PL）与 base+burst 策略，分段设计支持 1GB 到 64TB 在线扩容、Pangu 硬链接使 1 分钟内可创建 1 万块虚拟盘。（YouTube EP37X8vCuLDRg，[541.2-1064.2]，L1）
- 〔SREcon（推测）〕复杂系统为何必然失败：Netflix 的 Systemantics 视角。主讲人（Netflix 工程师、现任 Chaos Monkey 实现作者）从一次冷启动测试注解遗漏导致单元测试提前运行、抛出 ClassNotFound 异常并造成流媒体故障讲起，引用儿科医生 John Gall 的《Systemantics》：复杂系统表现出不可预测的反常行为（antics）；错误处理引入新故障模式（超时重试引发 retry storm）、支持系统会拖垮生产（A/B 测试服务故障日志经 Kafka 发送线程与共享锁竞争饿死应用线程）、人为缓解操作也会引发事故（AWS S3 计费调试中的误操作）——这些可用性机制在提升可靠性的同时带来更复杂怪异的新失效模式。（YouTube EP3IdGjhETIVA，[10.2-661.2]，L1）
- 〔SREcon（推测）〕漂移失效理论与混沌工程实践。借安全研究者 Sidney Dekker《Drift into Failure》的四个方面解释失效：软件是无法建模的失控技术（容错不可组合，校验过 shim 层反而集中了几乎所有缺陷）、时间稀缺下的效率-周全权衡（Hollnagel 的 ETTO 原则）、以小步缓变滑向不安全（金丝雀分析标准逐次放宽的偏差常态化，Diane Vaughan）、对初始条件的敏感依赖（EV Cache 客户端把错误当缓存未命中的默认配置源于历史上的合理选择）；对策是混沌工程——Chaos Monkey 以随机终止实例为激励倒逼韧性设计，混沌自动化平台 ChAP 克隆集群、路由真实生产流量、注入 RPC 延迟并用自动金丝雀分析验证韧性，以 SPS（每秒流启动数）为 KPI、最小化爆炸半径。（YouTube EP3IdGjhETIVA，[717.2-2006.8]，L1）
- 〔SREcon〕排队论对系统性能的真实含义。Vivint Smart Home 软件与运营团队总监 Jeff Poole（自嘲向 SRECon 提案时不够资格、登台前补课）讲解排队论基础：服务器、队列、到达率 λ、利用率 ρ、平均服务时间 S、等待时间 W、驻留时间 R 与 Little 定律；自写动画模拟显示利用率 80% 时只要到达或服务时间服从指数分布就会出现排队（平均等待 2-3 倍服务时间、95 分位 6-8 倍），利用率越高延迟非线性恶化——50% 时平均驻留 2 倍服务时间、75% 时 4 倍、90% 时 10 倍，经验法则是闲置时间每减半预期驻留时间翻倍。（YouTube EP3at6ijBU2ug，[16.6-1198.6]，L1）
- 〔SREcon〕多服务器单队列、实用容量规划与可扩展性定律。95 分位延迟在 90% 利用率下可达 30 倍服务时间；单队列供多服务器取活（近似 Erlang C）显著优于每服务器独立队列，但分布式场景受网络取活延迟限制常需预取折中；以 uWSGI 与 Python 进程布局为例说明单实例低延迟与故障爆炸半径、扩缩粒度之间的权衡，并给出 80% CPU（延迟敏感 50%）的实用阈值；用 MongoDB 导出器的普通 Prometheus 数据验证驻留时间曲线约拟合 6-7 台服务器的有效并行度，最后介绍 Neil Gunther 的 PDQ 排队建模工具与通用可扩展性定律（Amdahl 定律加协调开销二次项）。（YouTube EP3at6ijBU2ug，[1198.6-2376.2]，L1）
- 〔会议不详〕FlexMig：面向分层内存的自适应页面画像与迁移（与 SK Hynix 合作）。主讲人介绍论文动机：DRAM 访问延迟约 95 纳秒但容量小（如 128 GB），慢内存延迟约 345 纳秒、容量 768 GB，持久内存约 250 纳秒、可达 TB 级；分层内存系统由内存访问画像器（把页面分类为冷/温/热页）、提升（promotion）与降级（demotion）三个组件构成。作者通过对 TPP（页错误画像）与 Memtis（PEBS 画像）等方案的实验得出三点观察：不同应用偏好不同画像方法、没有永久赢家；TPP 平均约 83% 页提升失败、缺降级机制的 AutoNUMA 几乎 100% 失败（多因快内存空间不足）；Silo 等内存数据库中 96% 的 bin-1 页在两个采样周期内迁入更高频 bin，单一 bin 无法有效刻画温页、误分类会造成不必要的页面迁移。（YouTube EP3h25uHL1z2g，[16-520]，L1）
- 〔会议不详〕FlexMig 的三项自适应设计与评估。针对画像，FlexMig 结合 PEBS 与页错误两种画像器、禁用各自的独立提升函数，仅保留一个 promotion agent 从两者中挑选合适候选以取长避短；针对提升失败，降级不再用恒定水位，而是依据快内存冷页数与上一周期提升失败数在运行时动态决定降级率并移动水位；针对温页，按相邻 bin 间页面迁移比例动态更新温页集。在 Intel Xeon（DRAM 限制到 30 GB、768 GB 持久内存）上的评估显示 FlexMig 在全部基准上最优，较 Tiering-0.8、TPP、Memtis 平均分别提升 32%、23%、27%，Silo 案例研究证明其识别更多温页、减少对温页的不必要降级。（YouTube EP3h25uHL1z2g，[522-1033]，L1）
- 〔会议不详〕Peregrine：与西门子合作开发的数值时序数据库。TUM 高级研究员 Alexander Vishnivskiy 介绍项目动机源于工业数据分析的两大用例（大跨度数据上的缩放浏览，以及按复杂条件搜索异常时间区间），目标是在 Amazon S3 等廉价远端对象存储上存放十年级、TB 级数据并高速执行搜索与抽取；核心思想是不惜一切代价减少与后端存储的通信。为此采用三级数据索引：时序按等长时间戳切成块区间，块元数据仅含元素数、编码长度与压缩标志三个字段，索引块合并为固定时间长度的索引段（含唯一标识即段文件名、段起始时间与版本号），段再合并为索引；序列编码把时间戳与值合并存储（时间增量用 32 位无符号整数、仅 4 字节，值按二进制表示求差以获得更长的零填充位序列），再以 Zstandard 压缩，从而一次请求即可读取数据。（YouTube EP3tXYm7IdYPM，[7-540]，L1）
