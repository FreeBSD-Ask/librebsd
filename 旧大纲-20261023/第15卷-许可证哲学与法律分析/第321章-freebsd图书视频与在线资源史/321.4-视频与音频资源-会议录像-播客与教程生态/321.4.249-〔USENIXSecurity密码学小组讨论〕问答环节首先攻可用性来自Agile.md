# 321.4.249 〔USENIXSecurity密码学小组讨论〕问答环节首先攻可用性来自Agile

- 〔USENIX Security 密码学小组讨论〕问答环节首先攻可用性：来自 Agile Bits 的 Jeffrey Goldberg 区分“给用户的可用性”与“给开发者的可用性”，指出认证口令与加密口令之别、信任某人身份与信任其作介绍人之别这类概念若要用户自行理解，再多好界面也无济于事〔16:30〕；有与会者随即给出隐形密码学的胜利案例：美国蜂窝网络空中接口“渐近地 100% 加密”，非国家行为者的空中窃听“作为问题已不复存在”〔18:37〕，可话锋一转——尽管自己懂认证与机密性之别，他“仍然不知道怎么给 Dan 发一封加密邮件”〔19:31〕。被问“标准遭篡改指控之后社区还能依靠什么”，全场先是“dead silence”〔21:59〕。Bernstein 转入简单性布道：OpenSSL 是庞然大物，其曲线清单含四五十条椭圆曲线、各自独立代码路径，其中一条无人听说过的 ANSI 曲线与 NIST P-224 实为同一条、只是 seed 元数据不同的重复实现〔24:02〕；与其在弱算法 A、B、C、D 间留后路，“直接实现强算法 Z 然后收工”〔25:29〕；MD5、RC4 这些 1990 年前后的老古董早该退役，Flame 恰是借 MD5 组合微软终端服务打进去的；极简的极端案例是 TweetNaCl——同接口的完整密码库，100 条推文、一张 A4 纸就印得下〔26:55〕。（YouTube EPKRcVB-Ruzew，[965-1660]，L1）
- 〔USENIX LISA10 大会演讲·系统性能可视化〕讲者先拆穿 IOPS 陷阱：从应用出发，IO 在抵达磁盘前的每一层都可能被改变——NFS 客户端库会预读，UFS 与 ZFS 有 prefetch/read-ahead 机制，文件系统元数据与 RAID 条带会放大 IOPS〔18:43〕；反向的“缩水”同样常见：读命中 DRAM 缓存直接弹回；应用反复覆写同一内存地址、文件系统异步刷盘时写入会被取消，压根到不了盘；ZFS 还会在 vdev 层把大量顺序 IO 聚合成更大的请求，加上“Don't mind the gap”特性，纵有空洞也宁可发一个 128KB 的大 IO〔20:39〕。为证明“IOPS 不生而平等”，他摆出 iostat 实例：一块盘 86 IOPS、99% busy，另一块 21,000 IOPS、99% busy，“听起来我该把第一块全扔了换第二块”——“当然，这两块是同一块盘”：前者是 8KB 随机负载，7200 RPM 盘本就只有约 110 IOPS 的上限；后者是 512B 顺序读，径直从磁盘的 DRAM 缓存弹射出来〔22:01〕。“用 IOPS 当主指标很难理解性能问题，我更愿意伸手去拿延迟”〔23:07〕：100 IOPS 是不是每盘故障？“很难说”；100 毫秒的 IO 是不是问题？“多半是”；同步延迟直接对应应用在等待，“延迟越高越糟”这一性能领域少见的简明法则让它成为首选主指标〔25:13〕。资源监控则是另一门学问，靠利用率预测问题：“我知道磁盘一旦到达饱和点就会出现大量排队”〔29:19〕；两块盘 %b 都到 99%，问“要不要加轴”，答案就是“要，因为盘快 100% 忙了，你即将撞墙、即将排队”——而此刻延迟尚未膨胀〔29:29〕。（YouTube EPml-t-9g6Mjc，[1104-1877]，L1）
- 〔USENIX LISA10 大会演讲·系统性能可视化〕可视化部分从“每秒平均”的局限切入：讲者坦承按秒汇总几乎总是够用，唯一一次失效是中断问题——多块盘同以 100 多毫秒完成 IO 且完成时刻完全一致，逐条翻看原始元组才发现中断未被拾取〔33:35〕；更要命的是平均会吞掉离群值：“一万次 1 毫秒的快 IO 加一次 500 毫秒的慢 IO，平均值只有 1.05 毫秒”〔35:13〕，磁盘出事时甚至会吐出数秒级的 IO，因此要看完整分布：DTrace 的磁盘延迟脚本显示绝大多数 IO 落在 64 微秒到 4.8 毫秒之间，而 65-131 毫秒那一桶里的 2 次 IO 恰是性能工程师最想要的离群值〔36:55〕。给分布加上时间这第三维就是热图：X 轴时间、Y 轴延迟、色饱和度表示落在该时间-延迟格子里的 IO 数；他展示自己在 Sun 开发的 ZFS L2ARC（以闪存 SSD 作二级缓存）启用前后的热图：启用后闪存在约 1 毫秒档填平了原先的空白带，右侧磁盘云随之变淡〔40:37〕。接着是著名的“冰湖”：单客户端、单线程对 22 盘条带池做 8KB 同步顺序写，热图竟铺满斜线；把单盘热图与 NFS 热图并排，靠肉眼图案匹配即可把 NFS 延迟关联到磁盘延迟，省得写两百行 DTrace 程序〔48:02〕；顶部那条 9.29 毫秒的线后来经读者来信与博客确认为磁道切换寻道延迟〔50:20〕。压轴的“彩虹翼龙”来自 48 盘两柜、顺序 128KB 读、每两秒加一块盘压饱和的实验：底部每盘吞吐曲线出现膝点，顶部延迟热图像一只翼龙〔53:10〕；数月后换了硬件、固件与软件版本重做，翼龙仍在——“躯干是 PCIe 一代总线争用，因为我顶到了吞吐上限”〔56:27〕；这些热图“让我充满恐惧，因为很多东西我还解释不了”，但它带来了前所未见的新数据。（YouTube EPml-t-9g6Mjc，[1877-3395]，L1）
- 〔SREcon 大会技术课程·分布式系统基础构件〕选主最土的办法是“IP 最小者为主”，简单到人人认同、多数时候也确实管用，可你即便认得出谁是最小 IP 的主，也“不知道它是否还在正常工作”〔08:14〕，于是需要锁服务器：每个候选协调者都去争抢一条代表主的记录，抢到者把自己的 DNS 名、IP 或 IP 加端口写进去，其余协调者读锁失败却能看到内容，转而跟随真正的 leader〔08:34〕。常见语义是持锁者须周期性续锁，20 秒一档很实用——一旦协调者倒下不再续锁，锁服务器就通知等待者：“你之前想拿这把锁，当前持锁者已 20 秒没联系我，我要拆锁了，要不要重新抢？”获胜者宣布接管、通报全组；用外部锁服务器就不必自己实现这套选主逻辑〔09:27〕。但这又制造了新的单点，而“你可能做的最糟的事，就是这个叫 failover 的东西——它是当年为了卖双份数据库许可证而发明的”〔10:43〕：两个可能的主都健康却彼此网络不通时谁接管？两者心跳断了（串口线坏了）算谁挂？备端认定主端失职、抢着接管，却带着旧版或坏掉的软件，把原本健康的生产环境弄垮；他亲历的惨案是：先升级线上主库、打算隔一两天再升备库，failover 恰在升级进行中触发，落得“半升级的备库加坏掉的主库”的不一致状态〔11:49〕。还有论文证明过：只有两套系统时，数学上就不可能做到可靠〔12:21〕。另一个血泪教训：千分片作业中某台机器本地磁盘失联，编排系统把该分片改派他机，原分片却浑然不觉地继续读盘、删盘、写盘，此后他们要求所有作业在后台跑一个线程、每 30 秒做一次自己分片号的 DNS 查询，向锁服务器确认“我还是合法分片吗”〔15:18〕。（YouTube EPMzDOCb82e5s，[494-1162]，L1）
- 〔SREcon 大会技术课程·分布式系统基础构件〕接着盘点锁服务器选型：ZooKeeper 或是最老牌的开源锁服务器，复杂但全面；他在 Facebook 的同侪却认为用 MySQL 锁一行就够——“一千个账号大概没问题，一百万个账号就真不行了”〔20:10〕；npm 自带一个锁服务器，集群化 Redis 带有为锁而设计的原语，etcd 与 Consul 也都胜任、只是块头不小。多台锁服务器又引出“锁服务器里的主是谁”的递归难题，于是进入共识：共识就是让一群服务器就“谁是老大”这一唯一真相达成一致；虽然编排器可以自己实现共识，但“就像加密——别去发明加密，让专家发明、你用他们的库，锁与共识同理，现实世界很复杂、一定会有 bug”〔21:36〕。共识的理论要求：所有非故障进程最终对单一取值作出决定，多数进程决定同一取值，且决定必须有效（由某个进程提议过）；难点是某台锁服务器不应答时“慢与坏只能视作同一回事”，一切决定都要有时间界，而“单个故障进程下分布式共识的不可能性”有篇极好的论文〔23:24〕——所以别假设“跟上一次一样”，没人保证每个节点都记得上一次。Raft 以 leader 加 followers 实现，所有变更走 leader，心跳一断即改选；节点数取奇数很关键：3 好决策、4 易僵持、5 好决策，故常见 3/5/7〔26:27〕。讲者回忆多年前照看 Google 锁服务器的经历：三副本时“每周大约被呼四次，因为某处锁服务器挂了”，换到五副本后“大约半年才被呼一次，所以我坚定地喜欢五”〔27:43〕。Paxos 复杂得多，但微软那篇《Paxos Made Simple》只有三页、半小时可读完；两者大区别在 Paxos 里所有服务器都能提议并接受变更、每笔变更都被投票，而 Raft 只在选主时投票〔28:03〕。凡正确实现共识者基本就是带日志与检查点的复制状态机，队列与锁服务器同属此类——“一旦意识到每个有用的有状态分布式系统都是复制状态机，一切都会容易得多”〔31:44〕。（YouTube EPMzDOCb82e5s，[1162-1917]，L1）
- 〔LISA 2013 主题演讲〕Joyent 首席性能工程师 Brendan Gregg 在 LISA 2013 主题演讲讲述火焰图的诞生与原理：开场自嘲 5 年前“对着 jbod 磁盘吼”的延迟热图视频在 YouTube 已有 90 余万次播放〔01:07〕；真正的起点是客户生产环境一台重度吃 CPU 的 MySQL 数据库，他以 997 Hz 采样 60 秒，分析器输出被压成 50 多万行、2.7 万条唯一栈的“灰色方块”，而最频繁的 show status 栈只占不到 2% 样本，完全无法定位〔04:42〕〔06:51〕；情急之下他用 Perl 画出把全部样本一次呈现、X 轴按字母排序、宽度正比样本数的交互式 SVG，鼠标悬停即读百分比，一眼看清 CPU 真正去向，“这就带来了 40% 的性能收益”〔09:54〕。随后他讲解栈帧与调用栈：自上而下读是祖先链、自下而上是代码路径〔11:48〕；并安抚非程序员——MySQL 约 1.5 万个函数、50 万行代码，但读懂一条栈通常只需约 20 个关键函数，火焰图恰好给出“值得浏览的 0.13% 代码”命中清单〔13:29〕。火焰图的本质是放弃时间轴、X 轴按字母序合并相邻同名框以最大化折叠：X 轴是样本总体、Y 轴是栈深、颜色随机〔18:33〕；看图先看顶边（直接在 CPU 上的函数），顺祖先找根源，比较宽度即可直观判断“file sort 约 40%、select 约 60%”〔24:04〕。实战案例连环上演：客户告警软件 cron 每 5 分钟互相踩踏，火焰图直指 utf8 编码转换函数——平台升级后 LANG 被设为 en_US.UTF8，改回去性能提升 2000 倍〔28:12〕〔29:04〕；云盘基准测试内核 24% CPU 耗在 TSC 读取，顺祖先发现 62% 在 ZFS zio_throttle——新平台实现了多租户磁盘限速，而他自己也完全忘了这回事，“卷完火焰图问题就解决了”〔31:40〕〔31:53〕〔33:26〕。（YouTube EPnZfNehCzGdw，[37-2699]，L1）
- 〔LISA 2013 主题演讲〕下半场进入“高级火焰图”：内存有分配器函数、brk、mmap、缺页四类视图——malloc 火焰图按字节展示 bash 的 command_word_complete 一次分配 20 KB；有开发者用 SystemTap 关联 malloc/free 地址做出 nginx 内存泄漏火焰图，能直接指给开发者“这几条路径在漏”〔56:33〕〔59:50〕〔61:12〕；brk 追踪开销近零，专治 top 里 RSS 只涨不缩的“堆扩张之谜”〔62:30〕；缺页火焰图则揭示真正开始使用内存的路径〔64:42〕。I/O 上他强调逻辑 I/O 与块设备层物理 I/O 可能“膨胀、缩水、互不相关”，iostat 里吓人的异步回写不必惊慌，应在文件系统顶部测延迟〔66:26〕；ZFS 文件系统延迟火焰图显示 gzip 写等待 224 毫秒、读 108 毫秒，MySQL 列里 join 与 select 的分叉一目了然〔69:00〕；但他自认 I/O 路径太少、文本就够，真正的杀手锏是 off-CPU 分析——记录线程每次离开 CPU 的时长与栈，渲染成 off-CPU 火焰图，连完全空闲的 MySQL 也能借底部分叉认出各线程与阻塞原因〔71:32〕〔73:34〕〔75:00〕。on-CPU 与 off-CPU 合成的 hot-cold 图“实际效果并不好”，瓶颈是条件变量——栈只说你“在等别人”〔78:24〕；于是他做唤醒追踪：内核知道谁唤醒了你，把同一条件变量的阻塞方与唤醒方关联，SSH 的延迟被追到每秒一次的 vmstat 输出〔79:36〕；更在当天凌晨 4 点半做出“链图”（chain graph）：沿唤醒链逆向堆栈、宽度仍表相对时长，把“线程 A 唤醒线程 B、B 唤醒 C、C 最终唤醒条件变量”整条链画进同一坐标〔82:26〕。结尾巡礼生态：Dave Pacheco 为 node.js 加探针让 JS 函数现身栈中，Sam Saffron 做出 Ruby 火焰图（栈太深只好隐去函数名），Bruce Dawson 接上 Windows Xperf；Google Chrome 受启发推出按时间排布的“flame charts”，他当场喊话希望加个开关〔85:04〕〔86:09〕；Q&A 里他解释采样用 99 或 997 Hz 而非整百整千，是避免与目标锁步——他实测发现如今内核定时器太准，真的会撞上并歪曲画像〔89:44〕。（YouTube EPnZfNehCzGdw，[2699-5414]，L1）
- 〔USENIX Security 测时奖圆桌〕圆桌致敬获测时奖的 2001 年论文《Inferring Internet Denial-of-Service Activity》。亲历者 Tom Anderson 回忆论文源于偶然：为做日志分析而搭建的回流流量测量系统上线后，突然看到大量指向本网从未存在主机的 SYN-ACK 报文——"they had tripped over the fact that there was these spoofed amplification attacks"〔11:56〕，即伪造源地址的反射放大攻击被网络望远镜无意捕获。这种"背景辐射"很快长成一整套指示与预警方法：晚近甚至有论文用"某网络背景辐射消失"判断其在线与否，或据此得知一个国家何时关停了互联网〔13:20〕；CodeRed 爆发时恰逢背散射纵向测量在线，感染机的随机探测蜂拥而至，蠕虫监测就此意外成立〔14:28〕。Bill Cheswick 补充 1989 年的故事：贝尔实验室闲置一年的 A 类网 net 12 被他通告进路由并导入 tcpdump，看到的是"internet background radiation——the death screams of machines"，仅凭这个报文望远镜就能知道全球哪些机器正遭受攻击〔16:35〕，其中不乏把回程地址设为"awful AT&T"的攻击。讨论转入近三年放大攻击的"hockey stick"式增长〔17:51〕：DNS ANY 响应放大逾 20 倍即成靶子，NTP monlist 曾催生约 400 Gbps 的攻击〔20:04〕，SSDP 又借通用即插即用设备接棒；主持人质问 BCP 38 自 2000 年就存在、开放解析器数以十万百万计，为何出口过滤仍不落实〔23:23〕。（YouTube EPO0TQTzcJU48，[596-1505]，L1）
