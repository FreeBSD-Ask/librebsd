# 328.2.9 文档规范与治理边界：man-pages 的观众、FHS 的目录、util-linux 的 BSD 构建目标与 Rust for Linux 的许可证追问（2005–2025）

GPL 与 BSD 的法律分野在 299.2.2 里已经呈现为代码与许可证字段的双向流动，但两派规范争夺的真正战场并不止在头文件与许可模板，也散布在 man-pages 的受众定位、GNU Coding Standards 的适用范围、FHS 目录规范的取舍、工具链构建目标的维护清单、以及新一代项目 Rust for Linux 的许可证默认设置——这些都是“谁来为读者、格式、目录、工具、跨平台复用定规范”的具体治理争议

早于上述代码流动的是文档治理之争：Kerrisk 与 Rob Landley 围绕 man-pages 的受众定位展开讨论，Landley 说自己在为打算支持 Dragonfly BSD 的平台写可移植程序时“会告诉你”，并指出“Posix 可移植”还涵盖 Windows NT 与奇怪的 IBM 大型机；Kerrisk 回应“man-pages 面向一般读者，其中许多人确实关心可移植性”，但强调“只要这个一般读者不包括那些把 Linux 视为自有平台的人即可”；当 Landley 表示自己在未翻页的情况下漏读了 notes 段，Kerrisk 顺势讨论了如何让读者注意到细则；同一脉络下 Kerrisk 亦在 pid_namespaces(7) 讨论中称 `_GNU_SOURCE` 是暴露 Linux 专属功能的标准方式，Landley 反问“哪个标准？Linux 没有编码规范”，把 `_GNU_SOURCE` 与 GNU Coding Standards 之间的鸿沟摆到台面上

文档治理的另一条线是 GNU 手册页并入 Linux man-pages：Colomar 回复称 GNU Coding Standards 对 `--help` 的要求可通过 `bug-standards@gnu.org` 争取修改，但他个人“don't intend to change that”；关于格式体系，Collin Funk 问“mdoc is the format mandoc uses for the different BSD man pages, correct?”，Colomar 答“Yes, the BSDs use mdoc(7) instead of man(7)”，并补充 Linux 上 nginx 等项目也使用 mdoc，“but they're minoritary”——mdoc 与 man(7) 的分野被同时保留为 BSD 文档传统与 Linux 边缘实践

目录规范的治理权则在 FHS 与 BSD 惯例之间显形：2013 年 Ingo Schwarze 批评某草案“dismissing decade-old *BSD standards like the use of /usr/ for the base system and /usr/local/ for packages as a standard violation”，并称“/opt/ which is firmly a Linux-only invention”；G. Branden Robinson 援引 Solaris 2.3/2.4 与 Oracle 文档确认 `/opt/` 早于 Linux 已存在；Schwarze 回忆曾试图说服 FHS 维护者将 *BSD 惯例纳入标准，但 FHS 社区“very firmly entrenched as "Linux only"”，拒绝将 `/usr/` 用于基本系统、`/usr/local/` 用于软件包等数十年 BSD 惯例，转而推广他视为“firmly a Linux-only invention”的 `/opt/`；Schwarze 因此退出并称其他 OpenBSD 开发者嘲笑他“Why do you even care about that Linux-only crap?”；Colomar 致谢，并引用 Branden 考证 `/opt/` 并非 Linux 专属

规范边界也落在工具链构建目标上：2014 年 util-linux 2.25.2 发布公告的变更清单多处跟踪 BSD 家族构建目标，包括为 BSD 改用 `-lutil` 链接、修补 ipcrm 在 BSD 上的构建失败，并标注 ipcs 仍有 kFreeBSD 构建残留，另有 blkdev 修正 GNU/kFreeBSD 下报告的磁盘容量，显示该用户态工具链长期维护对 FreeBSD 与 kFreeBSD 的兼容，原文“remaining kFreeBSD hackery for building”——BSD 构建目标不是可丢弃的兼容补丁，而是发布公告级别的项目承诺

规范边界也延伸到信号语义的取舍：Pavel Machek 与 Arseny Maslennikov 在为 SIGINFO 争取依据时援引“GNU make on BSD does support SIGINFO (Not a standard tool, but obviously an established one)”——GNU make 在各 BSD 家族系统上的支持被直接作为 Linux 内核信号扩展的先例论据，BSD 家族信号语义因此成为内核用户态接口取舍的参照

规范边界的最新一处显形落在新一代项目 Rust for Linux 的许可证选择上：2024 至 2025 年间一位 Rust for Linux 邮件列表新成员对许可证策略提出一问，注意到现有 Rust for Linux 代码似乎统一采用 GPL-2.0，询问这究竟是明确的集体决定，还是仅仅沿用默认设置；作者援引既有事实作为对照，Linux 的 DRM 核心以及 i915、radeon、amdgpu 等主要驱动均采用 GPL 与 MIT 双许可，正因为如此，OpenBSD 可以直接使用这部分代码；作者表示希望苹果芯片驱动也采取同样做法，目标是让驱动对其他内核同样有用，因此询问 Rust 核心中的一部分，尤其是进程宏和用 Rust 编写的通用代码，是否可以采用更宽松的许可，以便其他项目在自己复用它所支撑的驱动时能够直接引入这些公共代码——这一问把 GNU 内核中已有的双许可先例与 BSD 系统跨内核复用需求直接连起来，把许可证选择显形为跨平台复用能力而非单纯法律条款

从 Kerrisk 与 Landley 对 man-pages 观众的定位、到 Colomar 对 GNU Coding Standards 与 mdoc/man(7) 分野的回应、到 Ingo Schwarze 试图说服 FHS 维护者、到 util-linux 为 BSD 与 kFreeBSD 保留构建目标、到 SIGINFO 在 Linux 内核的扩展论据、再到 Rust for Linux 的许可证默认设置追问——这场博弈的落脚点不在某个具体的许可证条款，而在读者、格式、目录、工具、跨平台复用谁有权定规范；GPL 的强制回馈与 BSD 的宽松复用在这条规范边界上互相碰撞，最终以邮件列表的反复论战、草案的批评与致谢、发布公告的构建目标清单、补丁说明中的跨平台复用承诺落地
