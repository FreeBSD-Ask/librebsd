# 081.2.6 软件RAID在OpenBSD的被忽视现状树内仅有两个驱动自NetBSD继承的RA

- 软件 RAID 在 OpenBSD 的被忽视现状：树内仅有两个驱动——自 NetBSD 继承的 RAIDframe 极为庞大、亟须裁剪（NetBSD 在该领域投入远多），以及仅做镜像与条带化的极轻量 CCD、缺乏对付硬件故障族的智能；受访者坦言若有空闲愿意投入，制约因素纯粹是时间。（BSDTalk EP46，[382.36-434.80]，L1）
- 入门路径：1996 或 1997 年首装 Linux，得到提示符后不知所措而退回 Windows；入大学后因功课与共享网络需要 Unix，发现 OpenBSD 文档远比 Linux 的 howto 与贫乏文档可读而选择后者，自认当时不知为何没有选 FreeBSD；其对 OpenBSD 的第一项贡献是引入 USB 支持，经持续提交修复后获自行提交权限；此后遍历各 BSD 与多个 Linux，并在工作中照看 Solaris 机器。（BSDTalk EP46，[447.76-526.80]，L1）
- 桌面与服务器推荐的分野：其桌面定义仅为能 ssh、有浏览器、能放 MP3，此标准下 OpenBSD 完全胜任；但音频编辑、矢量图形等场景他不讳言会推荐 Mac OS 或 Windows，并自知此论会令社区不快；服务器端则除日历与 Exchange 支持外，OpenBSD 作任何他所工作过的网络的后端都能直接运转。（BSDTalk EP46，[675.60-717.52]，L1）
- 开发环境与社区对照：日常为 vi 加 make 加 screen 加当值语言，screen 被其称作有史以来第二重要的软件；他对 OpenBSD 开发社区的评价是极为支持与鼓励——报告 bug 会被认真对待、他人愿与你一同追踪直至修复，而其对比的图景是某些上游维护者一句我这儿正常便终结报告，令他困惑于对方无意改进软件；两种社区对待缺陷的方式构成鲜明差异。（BSDTalk EP46，[727.72-790.52]，L1）
- OpenCVS 的重写突破：hackathon 前两周他因受够 GNU CVS 的代码而与项目同侪商讨重写，获得实现思路后决定部分重写；会前已完成大量代码，抵达 hackathon 后集中提交、进展迅速——commit、update、checkout、status 等常规仓库操作命令在三周内全部可用，按其说法这三周做完的工作量超过 OpenCVS 此前两年的积累。（BSDTalk EP50，[143.12-200.74]，L1）
- OpenRCS 的先行策略：OpenCVS 开发一度停滞，遂与 Theo 商定先做 OpenRCS——既可将更多 BSD 许可程序收进 base 树，又能复用 OpenCVS 已有的 RCS parser；OpenRCS 反而先于 OpenCVS 完成，已成为 GNU RCS 套件的近乎全面替代（尚缺向分支提交的能力）；其后因共用 parser 并非长久之计而彻底分叉，如今两者的共性仅存于 RCS parser 本身。（BSDTalk EP50，[202.82-297.70]，L1）
- 对 pserver 的拒绝是明确的安全决策：其认证协议与口令加密算法属公开已知、加密口令极易被提取，支持如此不安全的机制在他看来非常愚蠢；OpenCVS 依赖 OpenSSH——以 SSH 连接远程 shell、执行 CVS 服务端命令、经标准输入输出通信；未来或许会有自带用户认证与真实 ACL 的 CVS 守护进程以解决匿名读与扩展访问控制，但他对此并不确定。（BSDTalk EP50，[428.54-503.50]，L1）
- GNU CVS 缺失而 OpenCVS 拟增的工程特性：目录与分支级的访问控制列表——如 portable 与 stable 分支并存的大项目中只允许特定人选向 stable 分支提交安全修复；离线 diff——在火车或飞机上无服务器连接时对先前的 head 修订查看自身改动；revert——按指定提交自动将所涉文件回滚至先前 head 修订、相当于反向合并；原子提交——保证提交要么完整发生要么完全不发生，而非五个文件只改了两个。（BSDTalk EP50，[518.02-652.38]，L1）
- 仓库接管的责任与容错空间：OpenCVS 尚未用于管理 OpenBSD 官方仓库——若他此时向 OpenBSD 仓库提交会被立即制止——但他已用其管理个人本地仓库； eventual 切换意味着巨大责任，RCS 文件一旦损坏则满盘皆乱；所幸 OpenCVS 沿用 RCS 纯文本格式——管理段与全部 delta 皆为明文、修订即相互施加的文本补丁，尚存恢复希望；二进制 delta 的支持刚在 OpenRCS 侧取得进展，OpenCVS 仍付阙如。（BSDTalk EP50，[311.50-426.54]，L1）
- 项目参与的动机：他为自己的小项目长期使用 CVS，却总遇到不应发生之事——最著名的莫过于运行简单的 cvs update 时抱怨既有文件挡路、要求挪开的无稽行为；阅读 GNU CVS 源码的经历令他深感可怖，认定读之只会陷入痛苦；其后经聊天渠道得知有人为 OpenBSD 发起 OpenCVS 项目，因自己常用 OpenBSD 便决定加入出力。（BSDTalk EP50，[656.30-716.70]，L1）
- 入坑 OpenBSD 的机缘是一块声卡：家中旧机的声卡在 Windows 与 Linux 下皆无法发声，而他极重音乐，遍寻替代时将 NetBSD 与 FreeBSD 都试过而无效，转试 OpenBSD 后声音竟然直接正常；此后他持续惊叹于 OpenBSD 中一切基本都能正常运作，并敬佩驱动作者的才智；以 OpenBSD 听音乐、聊天，对他而言已是完美的多媒体系统。（BSDTalk EP50，[722.86-803.54]，L1）
- SpamD 是一个小型邮件延迟守护进程：对 SMTP 连接或以 450/451 应答令对方稍后重试，或经调整 PF 表放行；兼具 tarpitting 与灰名单两类用途。其设计目标之一是与 Theo 商定确保在一台 SPARCstation IPC 上过滤一个大网络——守护进程不 fork，而是一个读大量套接字、跟踪全部连接状态并与 PF 通话的状态机；对邮件内容不做任何判断（不做正文统计词频分析），只依据 SMTP 连接本身的性质——是否符合标准、是否有规避反垃圾措施的迹象——作判断，故可跑在内存极小的机器上。在阿尔伯塔大学约八万个账户的中央邮件环境里，受访者把 SpamD 放在 Exchange 服务器之前，配合较激进的灰名单，五封 SMTP 消息约四封被挡下、仅一封进入实际处理，显著减轻主邮件处理器负载。（BSDTalk EP68，[77.8-496.0]，L1）
- 运行观察驱动默认行为：SpamD 初期对每个连接前 10 秒以极低速应答后恢复正常，受访者观察日志发现大量连接在三秒即断——垃圾邮件软件以此探测 tarpitting——遂把 10 秒初始延迟设为默认且不设旋钮；对发件方还可启用把 TCP 窗口压到极小、令其分片重传的“残忍”选项以考验对方 TCP 栈（代价是带宽，默认关闭）；对 SMTP auth 场景建议不用 25 端口提交，而以 465 的 SMTPS 与 587 的 mail submission 端口加 SSL 认证解决，必要时可用 PF 重定向规则整网豁免；对早期灰名单担心的出站邮件服务器地址池问题，其经验是一般不构成障碍——可预置 graylisting.org 公布的大站白名单，小池子重试终会通过，出入站共用地址会因 SpamD 观察外发而逐步白名单化，大型站点约两个月才需一次人工干预；相较之下 Sendmail Milter 负载高且按发件人-收件人-IP 三元组粒度过激，不适合大学站点，SpamD 以整 IP 白名单加进出双向观察更为合用。（BSDTalk EP68，[252.24-496.0]，L1）
- greytrapping 机制与轶事：把站点内已公开且弃用的邮件地址设为陷阱，凡向陷阱地址发信的机器即被阻塞 24 小时并遭低速应答，纵使一次投递百封也全数不通；受访者的陷阱名单甚至包括其历年写进软件文档的示例假地址。其举的 bigbutts@obtuse.com 一例成为蠕虫式扩散的活教材：文章发表前先布入陷阱，数日内即有垃圾邮件命中；数月后统计脚本发现命中暴涨，用 Google 一查，某 BSD 期刊的 OpenBSD 文章被色情站点爬虫抓取并在隐藏标签中复制全文，垃圾邮件发送者再爬色情站点把地址再次拾取——清理者与滥用者的食物链在陷阱地址上叠印。（BSDTalk EP68，[673.06-895.48]，L1）
- 社区体验与多重贡献：受访者形容 OpenBSD 社区是一群高强度但自得其乐的人——hackathon 通宵、技术讨论时大喊大叫上蹿下跳，留下来是因为“有趣且对我们有用”；其本人自认什么 都碰：重写过 SpamD（不满意即推倒重来）、近期在拆解 SCSI 层——多数 BSD 的磁带机与磁带库 changer 支持基本残废，遂对 SCSI 层、磁带驱动与 changer 驱动作内核级修整；参与各处的修复、测试与发布验证，运营 orders 网站（藏在其公司机器与自家地下室）；自嘲“样样通样样松”，并强调自己不是 OpenBSD 狂热者而只是一个 UNIX 用户——用其所善、避其所短。（BSDTalk EP68，[897.92-1020.56]，L1）
- 缘起故事：约 1995 年，受访者与合伙人写防火墙软件并在咨询业务中营销，以把它移植到一切平台为乐（含内核修改）；当时无线买不起联网可用机，弄到一台 SPARCstation 后发现 NetBSD 的 SPARC 移植完全不可用，而 OpenBSD 正在起步——安全正对其胃口，也不管社区恩怨只问“能不能用”；下载 SPARC 发行版果然能跑且修掉了一批旧 bug；当年网站还是 Theo 的个人页，写着“喜欢就打这个电话”——竟是卡尔加里一家比萨店的号码，身在三小时车程外埃德蒙顿的他打电话订比萨遭拒后转而向 Theo 抱怨，两人在汉堡店见面，他买下一张 CD，从此入伙。（BSDTalk EP68，[1020.56-1118.98]，L1）
- 桌面、家庭与文化参与：受访者笔记本、桌面与孩子的机器都跑 OpenBSD（孩子双启 Windows 只为游戏）；其桌面是极简的 fvwm，但承认近年 ports 收集安装体验进步惊人，孩子用全套 KDE 加 Linux 兼容层跑 OpenOffice 与教育、游戏软件，女儿用 MSN 客户端、儿子玩 Blender，全家充当 ports 的发布测试“小白鼠”；家中防火墙以 PF 的操作系统指纹特性只放行 Windows 走 80 端口以隔绝病毒。发行文化方面：4.0 已分支并开放预购，预购者常在 FTP 放开前拿到 CD；本次除 CD 套装外首推收录 3.0 至 4.0 全部发行歌曲加彩蛋曲目的音频 CD；受访者为 3.5 的“鱼执照”歌曲写过歌词（自认 Monty Python 粉丝玩过火）；制作水准主要来自卡尔加里的 Ty Semaka 与 Jonathan Lewis（乐队 Plaid Tongued Devils），他自己也在一曲中与 Theo、Peter Valchev 及儿子 Calvin 合唱“酒吧合唱”；收尾呼吁买 CD、T 恤、捐款——强调 OpenBSD 反哺众多项目、直接间接被广泛使用，募款并非乞讨。（BSDTalk EP68，[1159.18-1535.58]，L1）
