# 395.11.5 Linux社区翻译者质疑exec3为何用frontend而非wrapper描述e

- 【Linux社区】翻译者质疑 exec(3) 为何用 frontend 而非 wrapper 描述 exec 家族与 execve(2) 的关系。Kerrisk 回复该措辞已沿用数十年，因为整页取自 BSD，且含义清楚；不过他也承认这并非首选措辞，已改为 are layered on top of。 <!-- ROW_MINE: linux-man.messages.735305 -->`
- 【Linux社区】Branden 考证 Unix 手册页交叉引用的字体惯例来源：man(7) 宏包首见于 Unix V7（1979），由 Bell Labs 的 Doug McIlroy 编辑收录该版全部手册页的《Programmer's Manual Seventh Edition》。V7 正文中交叉引用用斜体标主题名、正体标括号与章节号，可靠性约 99.49%；他统计 V7 中 .IR 用三百五十七次、.BR 为零次。而 SEE ALSO 一节系统性采用全正体排版，McIlroy 不记得这是刻意决定。此后 AT&T System III 与 BSD Unix 均沿袭该惯例。 `<!-- ROW_MINE: linux-man.messages.735440 -->`
- 【Linux社区】Zack Weinberg 认为 <sys/queue.h> 原本是 BSD 内核的实现细节，本不打算供其他场合使用；外部软件照用不误，一度有足够的用户态软件假定其存在，glibc 才因此提供一份兼容实现。他主张不应鼓励新软件使用，甚至不确定它是否还该写进文档；Colomar 则认为该页需要大改。 <!-- ROW_MINE: linux-man.messages.735479 -->`
- 【Linux社区】Branden 反驳 Ingo Schwarze 关于手册页应永远用 \ 而非 \~ 的主张：后者虽为 GNU 扩展，但已有三十余年历史，Heirloom Doctools troff 支持它十七年、neatroff 约六年、mandoc 三年；Documenter's Workbench 与 plan9port troff 不支持，但前者已三十余年无人维护、后者活动量低。他悲观假定多数或全部专有 Unix 的 troff 分自 V7 Unix troff 或早期 device-independent troff。关键论断是 groff 有收录于 BSD Unix 的悠久传统——尽管 mdocml/mandoc 项目努力在 BSD 后裔社区取代 groff，该事实不变，因此弃用 \~ 在某种意义上是一次回退，且耗时很久才被补回。 <!-- ROW_MINE: linux-man.messages.735575 -->`
- 【Linux社区】Christoph Hellwig 说明为何不更新 glibc 的 queue.h：他当年导入时与 glibc 版本一致，尝试更新被 Ulrich Drepper 拒绝；理由是至少五年前各家仍在维护的 BSD 对 queue.h 的增补已相当不同，很难挑选取舍。Mike Frysinger 认为留着一个过时的版本同样糟糕，Kerrisk 则询问上游页面是否有具体需修正之处。 <!-- ROW_MINE: linux-man.messages.735599 -->`
- 【Linux社区】Theodore Y. Ts'o 讨论移除 blocking_pool 的后果：使 /dev/random 与不带 flag 的 getrandom 行为一致，等于放弃 /dev/random 是某种 TRNG 的主张；他认为这不荒唐——BSD 诸系统一直就是这么做的。但他警告：一旦 /dev/random 取得初始化后即不再阻塞的语义，未来若改成提取 256 位密钥后读取便阻塞、直至重新填充而可能耗时数秒数分钟数小时，就会被视为回退而无法实施。 <!-- ROW_MINE: linux-man.messages.736006 -->`
- 【Linux社区】回应 Ingo Schwarze 所称对通用 Linux 发行版而言 Linux man-pages 项目举足轻重、且该项目完全不认为 man(7) 语言过时之语，Colomar 表示这确有影响，Branden 与他正在把 man(7) 补齐到与 mdoc(7) 相当的水平，且已在构建系统加入 mdoc(7) 支持，新的 mdoc(7) 页将获得与他审查现有 man(7) 页相同的 lint 级别。他欢迎任何人用 mdoc(7) 撰写新页，并打算改写 intro.1（他记得该页原本即用 mdoc(7) 写成），还计划支持 mm(7) 页，前提是 POSIX 愿意提供源码。他还强调已降低 fork 门槛——自己在职场就用这套 lint 能力审查 mdoc(7) 页。 <!-- ROW_MINE: linux-man.messages.736108 -->`
- 【Linux社区】Colomar 展示用 dspinellis 的 unix-history-repo 仓库（含全部历史 Unix 系统）查证 BSD 源码的方法，并以 4.3BSD（1986）的 qsort 实现为例：比较函数写成 K&R 风格的 int (*compar)()，无 const 限定语。他据此回答 const 在 C++、C89 与 POSIX.1-1988 中的历史争议。 `<!-- ROW_MINE: linux-man.messages.736275 -->`
- 【Linux社区】Branden 谈 Unix 标识符发音的文化门槛：Unix 文化不记录其术语发音，于是命令与函数名的读法成了区分自学用户与正宗（authentic）Unix 专家的社会标记——后者可经师承链上溯至 Bell Labs CSRC 或 UC Berkeley CSRG 的某位名人，即名字须像 Ritchie 或 Joy 那样被低声提及的人物。他接着说 Unix 与 Linux 内核都是 levelling technologies，但每当拉平发生，总有人急于恢复 guild、caste 之类的等级秩序。 <!-- ROW_MINE: linux-man.messages.736386 -->`
- 【Linux社区】Branden 汇报 groff 1.23.0 rc2 进展，其中一项工作是他已拖延五年之久的学 mdoc(7)——为了解决 groff man(7) 与 mdoc(7) 排版不一致的问题。他自评 groff 1.22.4 的 mdoc(7) 用了过多 Courier 与过多粗体，并顺带修复了若干 mdoc(7) 实现缺陷，包括一个在 4.3BSD-Reno 中即有记载的缺陷。 <!-- ROW_MINE: linux-man.messages.736523 -->`

- 【Linux社区】Colomar 提交四十五个补丁为各页新增 LIBRARY 段，系列主题为 Add LIBRARY section（附注 based on FreeBSD manual pages）；他最初写作 Linux kernel - GNU C library，意在说明不止 glibc 事，后经 Eugene Syromyatnikov 提醒第二章（section 2）本意是系统调用、用户态与内核的接口而非其 libc 包装层，简化为 Standard C library（与 FreeBSD 一致）。Syromyatnikov 指出 FreeBSD 的做法不同：libc 与内核同属操作系统整体、彼此紧密相连，不存在多 libc 实现的前提，故不经 libc 直接调用系统调用远不如在 Linux 常见——Linux 上有时甚至必须如此，如 x32 上的非常规用法，libc 及其 syscall() 实现反而碍事。 <!-- ROW_MINE: linux-man.messages.736604 -->`
- 【Linux社区】Guillem Jover 说明 libbsd 手册页长期放在 3bsd 子段，排序早于 3type，故会与 3type 页争位；他因此不愿新增类型相关的 3bsd 页。Colomar 回应 projects shouldn't use their own subsection，应统一用 3type 并以 LIBRARY 段标注所需库。两人还查明 libbsd 提供 TIMEVAL_TO_TIMESPEC 与 TIMESPEC_TO_TIMEVAL 是为非 glibc 系统（对应 freedesktop bug 94320），而 glibc 现也已提供这两个宏。 <!-- ROW_MINE: linux-man.messages.736612 -->`
- 【Linux社区】Kerrisk 谈为新类型建页时的命名冲突：他并不太担心，libbsd 与 man-pages 之间本已存在许多冲突。Colomar 提出支持 man timespec 形式的结构体页，理由是 libbsd 即用这种形式，用户跨系统输入同一命令即可工作；他真正的担心是某结构体标签可能与同名函数冲突。Kerrisk 认为多数类型名带 _t 后缀故无冲突，并举 sigaction 为例说明现状已可容纳——man sigaction 本就同时指向函数与结构体。 <!-- ROW_MINE: linux-man.messages.736714 -->`
