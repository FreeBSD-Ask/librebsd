# 395.11.6 Linux社区aligned_alloc3的HISTORY段梳理C11两处UBs

- 【Linux社区】aligned_alloc(3) 的 HISTORY 段梳理 C11 两处 UB（size 非 alignment 倍数、alignment 非 2 的幂）如何经 DR460（2014）转为失败、再由 N2072（2016）删除前者，C17 首次同时收录。Colomar 据此比对 BSD 实现：OpenBSD conforms to C11+DR460, but not C17，而 FreeBSD seems to conform to C17, but it claims to conform to C11；并注 FreeBSD/jemalloc 文档声称保留该限制而实现实际正确。 <!-- ROW_MINE: linux-man.messages.738159 -->`
- 【Linux社区】就导入 queue(3) 手册页，Hellwig 说明导入时 queue.h 与当时 glibc 一致，他同期尝试更新 glibc 的 queue.h 却被 Uli 拒绝；反对把手册页写成追随某发行版分支的内容，理由是 “at least five year ago all the maintained BSDs actually had quite different additions to queue.h, so which one to pick would be rather hard”，故部分理解 Uli 的拒绝。 <!-- ROW_MINE: linux-man.messages.738397 -->`
- 【Linux社区】Colomar 发起 LIBRARY 节 RFC，明言 “I liked the style of FreeBSD for specifying where a function comes from”，并以 FreeBSD 的 open(2) 与 gamma(3) 页面为例；首批四页覆盖需 syscall(2) 者、由 glibc 之外的库包装者、由 glibc 包装者，以及数学函数四种情形。 <!-- ROW_MINE: linux-man.messages.738398 -->`
- 【Linux社区】就 man-pages(7) 中 “生成最佳字形须用 \-” 一条存疑，Branden 记录另一种立场：“There are people who would argue (I've heard mostly from BSD people) that man pages should DWIM”——任何语境下 “-” 都只作 ASCII 45 连字符，并顺带取消 `,`、`'`、`^`、`~` 的非 ASCII 字形映射。他反对该立场，认为违背自 1970 年代初期起 troff 对这些字符的语义，并指 groff 前维护者 Werner Lemberg 与其同见。 <!-- ROW_MINE: linux-man.messages.738465 -->`
- 【Linux社区】就 setgroups(2) 允许非特权进程丢弃附加组，Ts'o 强调 setgroups/getgroups ABI 虽非 POSIX/SuSv3 内容、故不破坏兼容性，但更大问题在于 “it's very different from how BSD 4.x has handled things, which means there is two decades of history”；并举 Digital 曾规定 setuid 对大于 32k 的值返回 EINVAL、Ultrix 实现成十进制 32000，致 MIT Athena 新生被分配 >32000 的 uid 时 /bin/login 未预期失败的安全事故。 <!-- ROW_MINE: linux-man.messages.738469 -->`
- 【Linux社区】Robert Elz（kre）就 <memory.h> 一手回忆：应 Paul Eggert 之问查阅 CSRG SCCS 文件后称 “apparently I did create these files for BSD in early Aug 1985 - probably based upon some kind of description of what was in System V”；而 4.4BSD 实际分发的代码 “would have been Chris Torek's ANSI C rewrite though, perhaps 4.3 as well”。 <!-- ROW_MINE: linux-man.messages.738756 -->`
- 【Linux社区】realpath() 的来历由 Brouwer 定论，引 Guy Harris 1992-01-17 原话：“realpath() is not present in BSD, as of 4.3-reno; I think it first showed up in SunOS 4.0, and was then picked up by other systems, such as System V Release 4”，即 SunOS 4.0 → SVr4 → Solaris 2.0。手册页演进则层层叠注：旧注称有时返回相对路径，后来版本前置新段称恒返回绝对路径，最晚版本才删去相对路径说法（Apple 将其注释掉）。 <!-- ROW_MINE: linux-man.messages.738819 -->`
- 【Linux社区】Colomar 改造 Unix socket 代码时发现 Linux、OpenBSD 与 POSIX 的 bind(2) 页面均未说明 socklen_t 的实际作用：内核不会越过该值读取，但用户可传 4 使 sun_path 有效长度为 2 字节，“No matter what the real size of the structure was”。他称此仅在 Linux unix(7) 一段中被轻微提及，遂请 Ingo 先在 OpenBSD 手册页中说明，以便自己再用于 Linux。 <!-- ROW_MINE: linux-man.messages.738941 -->`
- 【Linux社区】就 memmem(3) 的移植清单，Colomar 反对在页面上加入 macOS 与 Android/Bionic：“macOS is not free software. I refuse to reference nonfree software on this project”，且 Android 不是可编程的真实 Unix 系统。Guillem Jover 反驳：macOS 底层按 FSF/OSI 标准属自由软件——内核 Darwin、实现 memmem 的 libc 见 opensource.apple.com；Solaris 与 Illumos 亦类似但采 CDDL/MIT/BSD。Colomar 部分接受后仍须就 bionic 与 newlib 定策。 <!-- ROW_MINE: linux-man.messages.739020 -->`
- 【Linux社区】Colomar 原称 “Most C libraries, including the BSDs, glibc, and musl, provide <memory.h>” 而 Illumos 不提供；Mark Harris 更正 Illumos 在 usr/src/head/memory.h 确实提供，但仅声明历史上原有的 5 个函数（memccpy/memchr/memcmp/memcpy/memset）。Harris 补史：SVR4 为兼容标准 C 将 mem 系列声明复制进 string.h 而 memory.h 未加 memmove；4.3 BSD 于 1986 年为兼容 System V 增设 memory.h 时亦仅声明原有 5 个 mem 系列函数。现代 BSD 已将其作 <string.h> 同义。 <!-- ROW_MINE: linux-man.messages.739109 -->`
- 【Linux社区】Schwarze 就 <memory.h> 溯源给出 4.3BSD include/memory.h 原文：版权头为 1985 年加州大学董事会、注明 “Definitions of the Sys5 compat memory manipulation routines”，仅声明 memccpy/memchr/memcmp/memcpy/memset。他自评该版权头 “feels bogus”——按 SCCS 记录最初提交者是 Robert Elz，几乎不可能由 UCB 员工撰写这些原型；且函数原型通常不可受版权保护，即便原则上可，此处几无可保护文本，“the notice simply means nothing”。 <!-- ROW_MINE: linux-man.messages.739249 -->`
- 【Linux社区】Hunt 指出 strchr(3) 与 memchr(3) 未说明检索字符为 '\0' 时的行为（终止符被视为串的一部分，故返回终止符地址），并引 FreeBSD 手册页为已成文之先例；同时观察到 “the FreeBSD man pages are based upon the POSIX specification document which is similarly vague”，故 FreeBSD 的 memchr.3 亦同样遗漏该说明。 <!-- ROW_MINE: linux-man.messages.739275 -->`
- 【Linux社区】就内核文档是否迁入 man9，Colomar 界定 man9 官方名为 “Kernel Developer's Manual”，收内核内部 API 与仅供内核开发者之内容，并引 NetBSD、OpenBSD、FreeBSD 的 intro(9) 为范围判据，另提 Debian 曾有项目把 Linux 内核内部文档写入 man9 但已废弃。他反对把生成式文档与 man2 放进内核树：man-pages 仅 bpf-helpers(7) 一例生成文档、不宜效仿，且 man-pages 的构建系统强于内核，改为适配内核 Makefile 将是重要倒退。 <!-- ROW_MINE: linux-man.messages.739300 -->`
- 【Linux社区】就 setitimer(2)/alarm(2) 的 si_code，наб给出实现对照表：alarm 与 setitimer 在 Linux 与 NetBSD 均为 SI_TIMER，FreeBSD 与 illumos 皆无，OpenBSD 无 POSIX 定时器故不可比。他主张不宜称其为 “Linux extension”——实现自由选择 si_code 值，“The Linux behaviour matches NetBSD”；建议 NOTES 只写 POSIX 仅对 timer_create(2) 保证 SI_TIMER，实现可为其他定时器提供，Linux 行为与 NetBSD 一致。 <!-- ROW_MINE: linux-man.messages.739436 -->`
