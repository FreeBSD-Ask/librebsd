# 395.10.69 Linux社区MatthewGarrett以具体下游生态反驳Linus对Busy

- 【Linux社区】Matthew Garrett：以具体下游生态反驳 Linus 对 BusyBox 诉讼的“只剩争吵”定性——**“它让大量人拿到了他们本应有权获得的源码。它是 OpenWRT 这类项目成功的巨大组成部分，而 OpenWRT 又构成了大量（合规的）商业 Linux 产品的基础。它说服了多家 Android 厂商发布源码，使人们能在厂商放弃手机后继续更新它们。我们有一整批公司，其存在纯粹是因为它们得以在被胁迫下发布的代码之上继续构建。声称‘它只导致了一大堆争吵’是不实之词，你应该知道不该这么说”**；对“我们做得很好”的判断则指出 **“不，我们并不。我的意思是，当然，如果你在意的是企业支持，我们做得不错。但如果你在意的是拿到基于 Linux 的设备的人能否看到代码并弄清它们如何工作，那是一场该死的灾难”**；其举证是 **“当然，如果你买个无线路由器，大概会拿到 GPL 声明——但那只是因为几乎每一家重要的无线路由器厂商都被威胁过或输过官司。电视也是一样。但如果你看那些从没有过诉讼的产品线，你会发现几乎无处不在的 Linux 以及同样无处不在的源码缺失”**；最后强调 **“许多人是抱着不同的标准参与其中的，所以别假装这里的‘我们’指的是所有 Linux 贡献者”** `<!-- ROW_MINE: ksummit-discuss.messages.347106 -->`
- 【Linux社区】Linus Torvalds：明确 GPLv2 的立法目的与“友好条款优于强制执行”的论证——**“我在意的是把代码贡献收回来。那差不多就是 GPLv2 的全部要点。不是那些法律术语。是通过让人参与项目来壮大代码库”**；并指出对方论证的自相矛盾 **“你试图用‘如果你在意的是企业支持’来贬低它，暗示那在某种程度上是狭隘的。但企业支持恰恰是你另一方面声称要用执法行动去强制得到的东西”**；其经验判断是 **“确实有大量非常好的理由相信，我们靠与企业的友好条款收回的自愿代码贡献，比任何强制行动与刁难都要多。事实证明，公司大部分情况下其实想合规。至少只要它们把你当朋友而不是敌人。而诉讼往往把朋友变成敌人”**；并以 BusyBox 维护者的自述为证（**lwn.net/Articles/478361/**），援引 **“一个相当著名的疯狂定义是‘一遍又一遍做同样的事却期待不同的结果’……FSF 已经试过对抗模式，那正是人们开始改用‘开源’一词的原因。我们之所以非常成功，恰恰是因为我们没有那种疯狂的对抗”** `<!-- ROW_MINE: ksummit-discuss.messages.347107 -->`
- 【Linux社区】Matthew Garrett：区分“贡献”与“可获得性”两种价值，并以亲身经历给出量化证据——**“那是你在意的。那不是你的用户在意的。他们在意的是代码可获得性，不是贡献。他们不在乎他们的厂商是否向上游参与。他们只在意当厂商不再发布更新时，自己能修那台烂硬件”**；其反证是 **“但……并没有。真的没有。在过去一年我买的运行 Linux 的东西里，大概 25% 能提供源码，而且其中一次还得我去打电话、告诉他们我是版权持有人、威胁要起诉，然后还得告诉他们我在他们产品里发现了几个安全漏洞。而这还是一家名牌厂商！”**；其机理是 **“它们永远不会直接与上游合作，因为它们产品周期不长、从中得不到什么，但拿到它们源码的用户获益巨大”**；对 BusyBox 案则指出 **“Rob 一直没抓住这里的要点。当然，BusyBox 那些案子没有让更多代码进入上游 BusyBox。但它们确实让若干厂商发布了源码，也让同领域的其他厂商因害怕遭遇同样的事而照做。用户拿走那些代码，修好它，做出了更好的东西，并把它分享给别人……这些人里有些是孩子，他们会成为下一代到这里来给你发补丁的人；另一些是露宿街头的人，他们因为能拿到更新的操作系统而不必买新手机、也就不会遭前任伴侣入侵手机；还有一些人在构建 Freedom Box 这类项目，它之所以存在，仅仅是因为 AP 厂商对诉讼足够害怕、释放了足够多的源码让别人在其上构建新东西”**；最后批评 **“别再假装从中毫无益处了。那显然不实……用户从代码可获得性中获益，即使它没有贡献到上游”** `<!-- ROW_MINE: ksummit-discuss.messages.347108 -->`
- 【Linux社区】Linus Torvalds：以“长期唯有上游贡献才重要”回应可获得性论，并划定终局判断——**“你失去了阅读能力。我一直在谈的是坏处。诉讼（以及仅仅诉讼威胁）绝对巨大的坏处。那些你无视了全部证据而加以贬低的东西”**；对“用户从代码可获得性获益”回应 **“问题在于，长期来看真正重要的是最终的上游贡献。不贡献的非贡献型公司在定义上就没有把自己的 DNA 传播出去。它们长期并不重要。真正重要的是那些实际开发并贡献代码、让未来发生的人——和公司。那才是让项目真正活着的东西”**；其对“懒且坏的公司”的定性是 **“是的，它们是水蛭。那又怎样？这不漂亮。在理想情况下，你可以试着迷惑它们、引诱它们出来，希望它们成为有生产力的社会成员。但当你开始用法律枪支四处扫射时，连好人都会撤退。他们不想靠近战区”**；最后强调 **“我们绝对不需要那些把真实贡献者（个人与公司）几十年来所做全部代码、努力与社区一笔抹杀的律师。那些律师就该走开。因为他们比水蛭还糟”** `<!-- ROW_MINE: ksummit-discuss.messages.347109 -->`
- 【Linux社区】Matthew Garrett：以“要什么样的贡献者”反问收束，指向下一代黑客的养成条件——**“当然。那么你是想要再多几个企业级集群文件系统，还是在某个特定数据库负载下为 3% 性能提升把页分配器整个重写一遍，还是想要一群因为这是驱动他们拥有的每一台设备的系统而成长起来折腾这些东西的青少年？因为说实话，我认为正是后者帮你走到了今天，而如果对你最重要的变成了确保大公司不感到受威胁、而不是确保下一个宿舍里的 19 岁年轻人能真正折腾他们手机上的代码并因此造出更好的东西，那么他们就不会在那儿了。这最初也是把我带到这里来的原因，而且我远不是唯一一个”** `<!-- ROW_MINE: ksummit-discuss.messages.347110 -->`

- 【Linux社区】Julia Lawall：披露其与新加坡管理大学合作的机器学习识别 bug 修复补丁研究及其数据标注瓶颈——**“几年前我做过一些自动识别 bug 修复补丁的工作，基于把日志消息与代码的信息结合起来。比如一个问题是代码改动量，因为一个大改动即便是 bug 修复，对 stable 来说也可能过于复杂。工作里用到了机器学习”**；其致命弱点是 **“显而易见的弱点是，我们只有我一个人给数据打标，而不是一位真正的 stable 维护者”**；并给出合作方与时间窗 **“我在这个工作上的合作者是新加坡管理大学的 David Lo。我将在九月的第一周去拜访他，可以与他进一步讨论。如果你碰巧想到机器学习还可能在别处与内核开发相关，我也可以提出来。他对把机器学习应用到软件开发问题无所不知，但对 Linux 内核乃至 C 代码一无所知”** `<!-- ROW_MINE: ksummit-discuss.messages.347116 -->`
- 【Linux社区】Julia Lawall：把该机器学习研究的评估方法讲清楚，并指出其证明标准——**“基本思路是，我们可以把发往 stable 的补丁和没发往 stable 的补丁作为训练集，然后机器学习得出某个算法并产生一些结果。需要有专家来评估这些结果。也就是说，对一千个（随机选定的）补丁，如果算法说它是 bug 修复补丁，它到底是不是，反之亦然”**；其方法学难点是 **“当然，我们也可以在之前发过和没发过 stable 的补丁上评估，但那里有个问题，因为我们的目标是要让发往 stable 的补丁比现在更多，所以我们需要证明该算法能捕捉到人类遗漏的东西”** `<!-- ROW_MINE: ksummit-discuss.messages.347117 -->`
