# 395.10.64 Linux社区DanCarpenter以Smatch维护者身份系统说明返回值跟踪

- 【Linux社区】Dan Carpenter：以 Smatch 维护者身份系统说明返回值跟踪的实践与边界——**反对“显式限定返回值可能取值”的提案：“我认为那是个坏主意。我们应当传播我们所调用函数的错误，它应当能在不破坏兼容的前提下改变”**；给出 Smatch 的实际能力 **“Smatch 在跟踪返回值上做得相当好，尤其是如果你像我一样每天重建数据库”**，并披露其手工修补数据库的通道**“格式是 函数、空格、旧值、空格、新值”，文件为 smatch_data/db/kernel.return_fixes**；列出两处结构性难点 **“递归会让 Smatch 出问题：第一次调用时我们不知道函数返回什么，于是记录它可能返回任何值；第二次我们就‘知道’它能返回任何值，未知由此递归传播”** 以及 **“从另一个线程或工作队列复制返回值时也会出问题”**；给出典型误报场景 **“函数做 if (ret) return ret; 而调用者做 if (ret < 0) return ret; 就产生不匹配”**，以及上界记录需求 **“我们想记录 scnprintf() 的返回值小于 size 参数……这些上界是防止整数溢出与缓冲区溢出告警所必需的”**；并抱怨未记录的正返回值 **“例如 ocfs2_plock() 返回负数、零或 FILE_LOCK_DEFERRED。也许这是个 bug，我怎么会知道？另外 em_sti_clock_event_next() 应当返回零或 -ETIME，但它返回零或一，所以我认为它是有 bug 的”**；最后提出一条规范建议 **“有时候无法分辨我们是无意还是有意返回零……这是缺失错误码 bug 的 75%、有意为之的 25%。我觉得这种地方总是该有注释，就像我们在 switch 语句里总是写 /* fall through */ 来标注缺失的 break 一样”** `<!-- ROW_MINE: ksummit-discuss.messages.347018 -->`
- 【Linux社区】NeilBrown：以 btrfs 到 NFSv4 的真实事故反驳“错误码应当一律透明传播”——**“最近我遇到一个 bug，源于 btrfs（拟议中）的一处改动向 ->fh_to_dentry() 函数返回了不同的错误码。它被一路传播到 nfsd，并在线路上出现在 NFSv4 协议里。只有那个新错误码对协议是无效的，客户端（正确地）把它报告给用户空间而不是在内部处理”**；其成因与处置是 **“这件事发生是因为对哪些错误码有意义没有给予足够的思考/文档。我把 exportfs_decode_fh() 改成任何非 ENOMEM 的错误都变成 ESTALE，因为那是 nfsd 能合理处理的全部”**；结论是 **“我确信有许多（很多！）路径的错误码应当透明传播，但我不认为我们应当假定这总是成立”**；并反问 Carpenter **“在数据库里保留一份合法返回值清单是可以的，但把它作为文档保留在代码里、并在程序员做出改动时提醒他们以便声明（甚至记录）这是否是有意的改动，就不可以了？也许我只是误解了你的观点”** `<!-- ROW_MINE: ksummit-discuss.messages.347019 -->`

- 【Linux社区】Michael S. Tsirkin：澄清其主张是标注索引类型而非指针空间，并给出完整示例——**“当然，大家都在用这些（__user）。但我的意思是标注索引类型：int data[256]; int foo(u32 __user *ptr) { u32 i; if (get_user(i, ptr)) return -EFAULT; data[i] = 0; ^^^ security vulnerability }”**；**“上面 i 来自用户空间，所以在被用作索引前必须始终做范围检查”**；其方案是 **“也许我们可以让 get_user 返回一个带标记的结果：__from_user int，并让上面的代码告警，因为 __from_user 不能赋给普通 int”**，并给出配套改写 **“int force_range(__unsafe u32 value, unsigned idx) { return ((__force int)value) % idx; } … ichecked = force_range(i, sizeof data); data[ichecked] = 0; ^^^ ok now”** `<!-- ROW_MINE: ksummit-discuss.messages.347027 -->`
- 【Linux社区】Michael S. Tsirkin：就 IS_ERR/CHECKED 组合的可行性作技术回应——**“我们或许可以这样做：errno_t rv; rv = f(); if (IS_ERR(rv)) return rv; int r = CHECKED(rv);”**；并提出工具侧建议 **“工具或许可以验证所有通向 CHECKED 的路径实际上都经过了 IS_ERR 检查”** `<!-- ROW_MINE: ksummit-discuss.messages.347028 -->`
- 【Linux社区】Matthew Wilcox：就 errno_t 家族的命名与可扩展性作深入辨析——**“我同意 errno_t 很完美，但它并不真正属于一个漂亮的家族——count_t、long_count_t 和 ulong_count_t 都相当糟糕。它们没有像我期望的那样大喊‘我可能含有一个 errno，最好检查我！’。count_might_be_errno_t 并不悦耳。err_count_t，也许？”**；并给出一个超出“计数”范畴的实例 **“当然它可能不是一个计数……至少某个时点 NVMe 驱动有变量要么含 [-4095 到 -1]（Linux errno，通常是 -ENOMEM）、要么 0（成功）、要么 1-65535（表示某种设备故障的 NVMe 状态码）。我认为那些变量现在都没了，但那并非不合理的需求，而把那个东西叫做 ushort_count_t 就不真实了”**；其处置建议是 **“对那类东西，驱动应当创建自己的类型（或者如果我们在 SCSI 里做类似的事，子系统会创建一个基本私有的 scsi_status_t）”** `<!-- ROW_MINE: ksummit-discuss.messages.347029 -->`
