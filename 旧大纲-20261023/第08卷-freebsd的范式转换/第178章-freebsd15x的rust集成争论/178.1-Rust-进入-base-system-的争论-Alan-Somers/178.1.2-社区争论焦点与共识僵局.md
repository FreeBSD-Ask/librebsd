# 178.1.2 社区争论焦点与共识僵局

**要点**：Somers 提案引发的社区争论持续超过两年（2024.1-2026.7），核心争议点包括：① 构建时间与资源——反对者（如 Warner Losh（沃纳·洛什） imp@、Baptiste Daroussin（巴蒂斯特·达鲁桑） bapt@ 等）指出 Rust 工具链本身体积庞大（数百 MB）、编译速度慢，将显著增加 base 系统构建时间与 CI 资源消耗，对资源有限的 Tier 2 平台（如 riscv64、armv7）尤其不利；② 编译器复杂性——Rust 编译器（rustc）使用 LLVM 后端（与 FreeBSD 默认 Clang 一致）但本身是用 Rust 编写的，这意味着构建 Rust 工具链需要先有一个可用的 Rust 二进制（“自举问题”），这与 C 编译器可通过系统 C 编译器从源码构建的传统不同；③ 许可证——Rust 本身采用 MIT/Apache 2.0 双许可，与 FreeBSD 许可证兼容，这一点争议不大；④ 维护负担——引入新语言意味着需要一批懂 Rust 的开发者维护相关代码，而 FreeBSD 核心开发者群体中 Rust 专业知识分布不均；⑤ 安全收益是否值得——支持者（如 Colin Percival cperciva@ 等）认为内存安全漏洞占比数据（70%）说明问题严重，Rust 是可行解决方案；反对者认为改进 C 代码（静态分析、形式化验证、Capsicum 沙箱）也能提高安全性

  **Rust 入 base 五大争议焦点**：

  | 序号 | 争议点 | 反对者立场 | 支持者立场 |
  |---|---|---|---|
  | ① | 构建时间与资源 | Rust 工具链体积大、编译慢，对 Tier 2 平台不利 | 安全收益值得构建成本 |
  | ② | 编译器复杂性 | rustc 自举问题（需先有 Rust 二进制才能构建） | 与 LLVM 后端一致，可逐步解决 |
  | ③ | 许可证 | - | MIT/Apache 2.0 双许可，与 FreeBSD 兼容 |
  | ④ | 维护负担 | 需懂 Rust 的开发者，专业知识分布不均 | 可逐步培养 Rust 人才 |
  | ⑤ | 安全收益是否值得 | 改进 C 代码（静态分析、形式化验证、Capsicum）也可 | 70% 内存安全漏洞数据说明问题严重 |

**史料**：freebsd-hackers@ 邮件列表 Rust 讨论多轮线程（2024-2026）；BSDCan 2024/2025 相关 BOF 讨论记录；Poul-Henning Kamp（波尔-亨宁·坎普） phk@、Warner Losh imp@ 等资深开发者的公开立场 ［A］

**史观**：专题语（不设条号）——哲学思潮：Rust 争论反映了 BSD 社区中 “保守演进” 与 “革新进步” 两种哲学的张力——FreeBSD 历史上对新技术的引入一贯持审慎态度（如 ZFS 移植经历多年实验才正式进入 base、WireGuard 经重写后随 13.0（2021-04）进入 base）；Rust 作为可能改变 base 系统语言构成的重大变更，自然需要更长时间的讨论与验证（原“总纲第 14 条”标号与基线第 14 条“苦难不值得被提倡”不符，按 R2140 先例改不设条号专题语——批次 C275 问题 1）

**辨析**：“Rust 进入 FreeBSD base” 与 “Linux 内核 Rust for Linux” 需区别看待——Linux Rust 支持主要限于内核驱动（特别是新驱动可选使用 Rust），FreeBSD 提案起步是用户态工具而非内核；截至 2026.7，OpenBSD 明确拒绝 Rust（Ted Unangst 等公开反对），NetBSD 未正式讨论 Rust 入 base，DragonFly BSD 亦无 Rust 入 base 计划——FreeBSD 是三大 BSD 中唯一认真讨论 Rust 入 base 可能性的项目，但距离实际引入仍有相当距离
