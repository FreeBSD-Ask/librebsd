# 018.1.2 FreeBSD 社区对 Rust 的接纳与讨论

**要点**：FreeBSD 邮件列表自 2010 年代起多次讨论 Rust 在基本系统中的潜在应用，争议焦点为构建依赖、引导编译与许可证兼容性；**最重要的一次公开讨论发生于 2024 年 1 月 20 日**——FreeBSD committer Alan Somers（<asomers@FreeBSD.org>）在 freebsd-hackers 邮件列表发起主题为 "The Case for Rust (in the base system)“ 的讨论线程（UTC 16:51:25，归档编号 002823），该帖首先回顾此前在 src-committers 邮件列表的讨论，明确指出 “the cost is that it would double our build times”（成本为构建时间加倍），并提及 Warner Losh（沃纳·洛什）（imp）建议在 buildworld 之后增加一个额外步骤以容纳需外部工具链的组件，进而将 Rust 项目分为四类：(1) “Stuff that could only be written in Rust if it were in base”——包括 ctl-exporter（CTL 统计 API 不稳定，无法在 ports 中维护，最终用 C 实现）、fusefs 测试（“Absolutely impossible to do in C”，因与 **fusefs(5)** 耦合过紧无法在树外维护，最终选择 C++ 以便入 base）、devd（当前为 C++，imp 建议重写）、zfsd（当前为 C++，Somers 长期考虑用 Rust 重写以提高可测试性）、nscd（当前为 C，无测试覆盖）、802.11ac 与 Lightning 协议栈用户态部分（scottl 建议）、freebsd-kpi-r14-0；(2) “Stuff that can live in ports, but would be nicer in base”——包括 gstat-rs、geom-exporter、nfs-exporter、virtiofsd-rs、jail-exporter、jail managers、musikid 的 pjdfstest 重写、pf-rs、benchpmc；(3) “FreeBSD-related applications that are just fine in ports”——包括 fsx-rs、ztop、iocage-provision、rsblk、xfuse；(4) “Other FreeBSD-related libraries in Rust”——指向 crates.io/keywords/freebsd；该帖共收到 8 封公开回复（Gleb Popov 002824、Antranig Vartanian 002826、Warner Losh 002830、Rozhuk Ivan 002880、Alexander Leidinger 002898、void 002908、Wojciech Puchar 002924、Shawn Webb 2024-07 003433），其中 Warner Losh（imp）的回复（2024-01-20 18:37:25 UTC）最具影响力；至 2026 年 Rust 仍主要在 Ports 层，未进入 FreeBSD 基本系统

**史料**：freebsd-hackers 邮件列表 2024-01-20 Alan Somers "The Case for Rust (in the base system)"（lists.freebsd.org/archives/freebsd-hackers/2024-January/002823.html，2026-07-28 WebFetch 核实）；freebsd-hackers 邮件列表 2024-01-20 Warner Losh 回复（lists.freebsd.org/archives/freebsd-hackers/2024-January/002830.html，2026-07-28 WebFetch 核实）；src-committers 邮件列表前置讨论（Alan Somers 在 002823 号邮件中引用）；freebsd-hackers、freebsd-arch 邮件列表存档 ［A］

**史观**：总纲第 23 条与第 24 条——社区治理与许可证：FreeBSD 社区对 Rust 的保守接纳体现 “动手者创造历史” 与 “分离聚合” 的双重张力——Alan Somers 作为动手者提出具体方案，Warner Losh 作为资深 committer 以工程实用主义回应，二者皆非教条立场；项目史观总纲第 25 章载 “分离聚合是永恒规律”——Rust 在 FreeBSD 与 Linux 社区的接纳路径分化即分离聚合的具体呈现

**辨析**：社区讨论未形成明确决议——freebsd-hackers 邮件列表 2024-01-20 Alan Somers 发起的讨论线程（非 freebsd-arch，原叙事误记为 freebsd-arch）经 8 封回复后无结论收束，Core Team Minutes 2015-2025 年公开记录中无 Rust 入内核议题；FreeBSD 治理结构要求 Core Team 决议方可改变基本系统语言策略，社区讨论无约束力；**Warner Losh 在 002830 号回复中的核心立场**——(a) "Rust is interesting but without experience in the FreeBSD context we won't know if it materially improves things. The why of Rust is currently somewhere between hype and reality"；(b) 指出 Rust 工具链的工程难点——"the rust toolchain is difficult and different; it can do things automatically with crates that are insecure and unrepeatable"；(c) 提出渐进路径——“What is needed to convince people it's not just a fad is to bring some things into the tree that aren't critical to the tree"，建议从测试入手（“I suggested we start with better tests in rust"）；(d) 明确否决全面替换——“So no, we aren't going to rush headlong into fullscale rust replacement of all the things. However I'll note Linux hasn't done that either. They are taking a one step at a time approach."；(e) 提出前置条件——“Step one is build integration with an external toolchain, imho. Until we have that, 0 Rust will be in the system."；Losh 的立场体现 FreeBSD committer 群体共识文化——以工程实用主义而非教条立场评估新语言；**OpenBSD 的情况**——Rust 在 OpenBSD ports 树中作为 devel/rust 存在，但至 2026 年未发现公开的 tech@ 或 misc@ 邮件列表讨论线程关于将 Rust 引入 OpenBSD 基本系统，Theo de Raadt（西奥·德·若特） 与 OpenBSD 核心团队未公开表态，OpenBSD 对基本系统语言策略的保守程度较 FreeBSD 更甚（OpenBSD 基本系统至 2026 年仍为纯 C，连 C++ 组件亦不存在）；经两库检索，freebsd 邮件库以"The Case for Rust"精确主题检索 2024 年无命中，以"Rust"检索 2024 年仅见 `cu` 列表无关帖（如 Warner Losh `5A74E928-…`"Re: noatime on ufs2"），2024-01-20 freebsd-hackers"The Case for Rust (in the base system)"讨论线程未见于本地邮件库索引，按 0 信任原则标注两库无法验证（覆盖范围：FreeBSD 邮件库 1994- 起，该线程或在本库采集范围之外）
