# 249.1.6 反批评层——DragonFly 阵营的工程实用主义回应（2014-2017）

**要点**：DragonFly 阵营（以 Matt Dillon 与 François Tigeot 的工程实践为代表）对 BSD 阵营的三类批评提出三层回应。其一，“硬件支持现实”回应——dragonfly.duckdb 显示 2014-2015 年间 i915 关键词 commit 146 条、radeon 关键词 44 条，反映 DragonFly 在 FreeBSD DRM 框架下已无法跟上 Intel 与 AMD 的 GPU 硬件迭代速度，Linux DRM 作为上游拥有远超 FreeBSD DRM 的硬件支持覆盖率，DragonFly 选择 Linux DRM 移植是“让用户能用到现代 GPU”的工程现实选择。其二，“维护资源约束”回应——dragonfly.duckdb 显示 DragonFly 2014-2018 年间年均 commit 量仅 1888-2340 条，约为 FreeBSD 同期的 11.4%-13.5%，DragonFly 无力维护独立的 GPU 驱动栈，Linux DRM 移植的维护成本（Tigeot 一人 9 年 1346 条 commit）远低于独立维护 FreeBSD DRM 适配层的预期成本。其三，“BSD 哲学的多元展开”回应——BSD 许可证的核心精神在于“允许不同路线”而非“强制共享代码”，DragonFly 选择 Linux DRM 移植与 FreeBSD 选择独立适配层，是 BSD 哲学在 GPU 驱动领域的多元展开，二者在本体论上平等，无优劣之分

**史观**：总纲第 8 条——本体论上各方平等：dragonfly.duckdb 数据显示 FreeBSD DRM 与 Linux DRM 在 DragonFly 的工程实践中是两条平等的技术路线，二者在本体论上无优劣之分——FreeBSD DRM 的“独立适配”与 Linux DRM 的“直接移植”各有其工程合理性与代价；总纲第 5 条——没有必然性，只有偶然性：DragonFly 选择 Linux DRM 移植并非历史必然，而是 Tigeot 个人能力（对 Linux DRM 的熟悉）与 DragonFly 资源约束（无力维护独立栈）的偶然交汇
