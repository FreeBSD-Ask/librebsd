# 242.1.5 批评层——对 HAMMER 文件系统设计的三重质疑（2008-2010）

**要点**：DragonFly 2.0（**2008-07-21**）发布 HAMMER 1.0 文件系统后，其设计面临三类外部批评。其一，“与 ZFS 对比功能不足” 批评——ZFS 由 Sun Microsystems 企业团队开发（OpenSolaris 2005 年开源 ZFS、FreeBSD 7.0 引入 ZFS、8.x 完善 ZFS 集成），支持 `send`/`receive` 增量流式传输、`pool` 存储池管理、ARC 自适应替换缓存、数据去重、RAID-Z 等企业级特性；HAMMER 1.0 虽支持快照、历史记录、增量备份、多卷镜像，但功能集较小，缺少上述部分特性，难以满足企业级存储需求。其二，“社区规模过小难以维护复杂文件系统” 批评——dragonfly.duckdb dragonfly-src 仓库 contributors 表显示 2008 年 36 位贡献者（top10 占 91.56%）、2009 年 36 位贡献者（top10 占 86.93%）；复杂文件系统（如 ZFS）需企业级团队持续投入，DragonFly 社区规模难以支撑复杂文件系统的长期维护。其三，“Matt Dillon 单人开发风险” 批评——dragonfly.duckdb 显示 HAMMER 设计主要由 Dillon 个人完成（HAMMER 首引 commit `8750964d1997` 由 Dillon 于 2007-10-10 提交），巴士因子极低，Dillon 个人风险即项目风险，与 FreeBSD UFS 由 McKusick 及多位 committer 共同维护、OpenBSD FFS 由 de Raadt 与多位开发者审计的多元维护形成对照

**史料**：DragonFly 2.0 release notes（HAMMER 1.0 功能集）；FreeBSD 7.0/8.0 release notes（ZFS 集成与功能集）；OpenSolaris ZFS 设计文档（Bonwick 2005 年 ZFS 论文）；dragonfly.duckdb dragonfly-src 仓库 contributors 表（2008 年 36 位贡献者 top10 占 91.56%、2009 年 36 位贡献者 top10 占 86.93%）；dragonfly.duckdb dragonfly-src 仓库 commits 表（HAMMER 首引 commit `8750964d1997` 由 Dillon 提交）；20260724_dillon-governance-model.md（Dillon 合并 10666 条 commit）；20260724_external-critics-dragonfly.md（外部批评考据） ［A］

**史观**：总纲第 8 条——本体论上各方平等：HAMMER、ZFS、UFS 三种文件系统在本体论上地位相等，“功能集” 与 “社区规模” 的差异是经验事实而非本体论等级；专题语（不设总纲条号）——工程组织的演进（原挂总纲第 17 条系伪名目，删条号）：HAMMER 1.0 作为 “轻量级写时复制” 哲学的工程实现，其设计选择背后是 DragonFly 社区的工程约束

**辨析**：考据过程留痕——【查证来源】HAMMER 1.0 功能集经 DragonFly 2.0 release notes 一手核验，ZFS 功能集经 FreeBSD 7.0/8.0 release notes 与 OpenSolaris ZFS 设计文档核验；dragonfly.duckdb dragonfly-src 仓库 contributors 表的 bus factor 数据（2008 年 top10 占 91.56%）以 author_email 字段按年去重统计，author_email 字段可由提交者任意填写，须与 committer 字段交叉验证；【交叉验证方法】HAMMER 与 ZFS 的功能对比以各项目官方文档为依据，但 “功能不足” 的判断须结合具体使用场景——HAMMER 的快照与历史记录功能在轻量级场景下足够，ZFS 的 `send`/`receive` 与 `pool` 管理在企业级场景下必要，二者目标场景不同；【0 信任原则·Dillon 自述考据】Dillon 在 HAMMER 设计文档中关于 “轻量级写时复制” 的表述属当事人自辩，HAMMER 的实际内存消耗与稳定性须以独立第三方 benchmark 交叉验证；【存疑判定依据】HAMMER 1.0 在 2.x 周期的实际部署规模无权威统计，dragonfly.duckdb 显示 2.x 周期 HAMMER 相关 commit 以功能完善为主而非安全修复，但部署规模有限可能导致漏洞未充分暴露 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］
