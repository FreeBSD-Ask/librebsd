# 218.3.6 pledge/unveil 设计争议的反批评——OpenBSD 阵营的回应（反批评层）

**要点**：OpenBSD 阵营对 pledge/unveil 设计批评的回应集中于四点——其一，pledge 的粗粒度类别是有意的工程选择而非缺陷，seccomp-bpf 的细粒度虽灵活但配置复杂、易出错，过滤器编写错误导致的“假安全”比粗粒度类别更危险，de Raadt 在公开声明中多次强调“正确性优先于灵活性”——一个能被正确使用的简单机制优于一个能被错误使用的复杂机制；其二，pledge 的“fail-closed”语义（一旦调用即不可放宽）使自愿模型在调用后即成为强制约束，攻击者注入的代码无法通过再次调用 `pledge()` 放宽限制，故“自愿即无防护”批评混淆了“调用前无防护”与“调用后可绕过”两个不同语义层面；其三，pledge/unveil 的可移植性缺陷是 OpenBSD 工程哲学的必然结果——pledge 依赖 OpenBSD 内核的 `kern_pledge` 实现，移植至 Linux/FreeBSD 须重新实现内核侧支持，OpenBSD 不应为迁就其他系统而稀释自身设计，seccomp 的跨发行版可用性是 Linux 内核维护者的工程选择而非技术必然；其四，unveil 的“锁定即不可逆”设计是安全机制的应有之义——可逆的路径限制会引入 TOCTOU（time-of-check to time-of-use）竞态，攻击者可在解锁窗口期内绕过限制，landlock 的动态调整设计虽灵活但增加了竞态面的攻击复杂度

**史料**：de Raadt 在 misc@ 与 tech@ 关于 pledge 设计哲学的发言（<https://marc.info/?laccopenbsd-misc>、<https://marc.info/?laccopenbsd-tech）；OpenBSD> **pledge(2)** 手册页 DESCRIPTION 与 HISTORY 段（<https://man.openbsd.org/pledge.2>）；Bob Beck 关于 pledge/unveil 设计的公开声明；openbsd.duckdb openbsd-src 仓库 sys/kern/kern_pledge.c 与 sys/kern/kern_unveil.c 路径下的 commit（记录“fail-closed”语义的实现） ［A］

**史观**：总纲第 17 条——软件工程：pledge/unveil 的设计是 OpenBSD“正确性优先于灵活性”工程哲学的实践；总纲第 8 条——本体论上各方平等：pledge/unveil 与 seccomp、Capsicum 在本体论上地位相等，差异仅是工程哲学的不同而非本体等级的高下；总纲第 7 条——技术选择即政治选择：OpenBSD 选择 pledge 而非 seccomp 式的细粒度过滤是以“可采用性优先”为预设的政治选择

**辨析**：反批评的合理性在不同叙事中评估不一——部分视为有效辩护，部分视为合理化；需对照 OpenBSD 官方声明与 pledge/unveil 实际工程产出核实；【0 信任原则·官方声明不等于事实】de Raadt 与 Beck 关于“正确性优先于灵活性”的声明须与 pledge 实际工程产出（如基本系统工具的 pledge 覆盖率、pledge 相关 CVE 频率）交叉验证；【0 信任原则·fail-closed 语义的边界】“fail-closed 使自愿模型在调用后成为强制约束”论证须对照 pledge 的“execpromises”机制——pledge 在 **execve(2)** 后可重置为子进程的 promises，故“不可放宽”仅在同一进程内成立，跨 **execve(2)** 边界存在放宽可能；【0 信任原则·可移植性缺陷的合理化】“pledge 不可移植是工程哲学必然”论证须对照 Capsicum 的可移植性经验——Capsicum 虽源于 FreeBSD 但其设计文档明确讨论过移植至其他系统的可能性，可移植性与工程哲学并非互斥；【0 信任原则·TOCTOU 论证的有效性】“可逆限制引入 TOCTOU 竞态”论证须对照 landlock 的实际安全记录——landlock 自 Linux 5.13（2021）引入后未见因可逆性导致的 TOCTOU CVE，TOCTOU 风险可能为理论推断而非实际缺陷
