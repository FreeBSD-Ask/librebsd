# 212.2.1 代码审计的方法论与流程

**要点**：OpenBSD 代码审计方法论由 de Raadt 主导，包括逐行审查基本系统源码、关注缓冲区溢出与格式化字符串漏洞、关注信任边界与权限提升；审计流程为发现问题 → 修复 →commit log 详细记录 →security advisory；审计成果通过 Release Notes 与 **security(8)** 手册页公开；统计结论印证——openbsd.duckdb openbsd-src 仓库变点检测（统计结论 C-14）显示 Pettitt 检验变点位于 2001-01（BUISHAND 检验变点位于 2017-09），2001-01 变点恰位于 2.x 时期末端与 3.x 时期起点交界，反映代码审计文化从 2.x 时期 “逐行审计建立” 阶段向 3.x 时期 “加密集成深化” 阶段的工程节奏转换

**史料**：OpenBSD Security Advisories 1996-2000；OpenBSD CVS commit log 中 audit 相关 tag；OpenBSD 手册页 **security(8)** 与 **afterboot(8)**；openbsd.duckdb 查询 L1.1.1（经 L1.1.2 交叉验证）显示 openbsd-src 仓库 1996-2000 年 commit 量稳定运行，与代码审计周期并行，但 commit 量本身无法区分审计 commit 与功能 commit；openbsd.duckdb openbsd-src 仓库变点检测（统计结论 C-14：Pettitt 检验变点 2001-01 / BUISHAND 检验变点 2017-09，Python Pettitt 自实现 + BUISHAND R 自实现，查询日期 2026-07-27） ［A］

**史观**：总纲第 15 条——文化即形式主义：代码审计作为社区文化资产，是 OpenBSD 区别于其他 BSD 的核心；统计结论印证——C-14 Pettitt 变点 2001-01 反映 “分离聚合是永恒规律”（总纲第 4 条）的工程节奏显现：2.x 时期的审计文化建立阶段（1996-2000）与 3.x 时期的加密集成深化阶段（2001-2005）在 2001-01 时点形成工程节奏转换，审计文化的 “建立” 与 “深化” 两个阶段在 commit 量层面呈现可检测的变点

**辨析**：审计方法论在不同叙事中存在差异——部分资料强调 “逐行审查”，部分强调 “分类审查”，需对照 commit log 核验；审计的具体范围（基本系统 vs ports）需考据；openbsd.duckdb 查询 L3.1.1.audit 在数据报告中无独立查询条目——深层信息挖掘.md §L3.1.1 仅含 MFC/Fix/Add/Refactor/Document/Linux/Import/Update 关键词分析（跨 22 仓库汇总，非 openbsd-src 专属），无法直接获取 openbsd-src 中 audit/fix/security 关键词 commit 频率，此为数据缺口 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］；**统计局限性标注**——C-14 变点检测的 Pettitt 与 BUISHAND 两检验变点时点不一致（2001-01 vs 2017-09），反映变点检测方法的方法学敏感性——Pettitt 检验对中段变点敏感，BUISHAND 检验对全样本变点敏感，两检验变点不一致不等于 “变点不存在” 而反映 “不同检验对变点位置的统计推断差异”；统计显著 ≠ 实际显著，Pettitt 2001-01 变点须与 OpenBSD 3.0（2001-12-01）发布、IPFilter 许可证争议（2001-05）、pf fork（2001）等工程事件交叉验证后方可归因；多重比较风险——C-14 与 C-12（freebsd-src 变点 1999-08）、C-13（netbsd-src 变点 2011/2012）、C-15（dragonfly-src 变点 2016/2017）跨项目对比时须按 Bonferroni 校正；0 信任原则适用——变点检测基于月度 commit 量序列，commit 量本身无法区分审计 commit 与功能 commit，变点的工程归因须以 commit message 与 release event 交叉验证
