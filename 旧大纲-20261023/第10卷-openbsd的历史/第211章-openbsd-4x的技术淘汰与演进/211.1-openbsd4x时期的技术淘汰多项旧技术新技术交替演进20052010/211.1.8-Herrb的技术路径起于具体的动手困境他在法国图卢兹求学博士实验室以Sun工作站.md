# 211.1.8 Herrb的技术路径起于具体的动手困境他在法国图卢兹求学博士实验室以Sun工作站

- Herrb 的技术路径起于具体的动手困境：他在法国图卢兹求学，博士实验室以 Sun 工作站等接触 UNIX；约 1993 年免费 UNIX 可在家用 PC 运行时，他的图形卡不为 X386 支持便动手修改以驱动自己的硬件，从此未辍；先做 NetBSD 的 X 移植，后转入 OpenBSD。（BSDTalk EP106，[81.36-134.56]，L1）
- Xorg 7 的架构变革是构建体系的换代：弃用 X 专属的 imake 而改用新构建工具并走向模块化，库、客户端、X server 与每个驱动各自成包，合计三百余个包须按正确顺序分别构建；OpenBSD 希望直接在 base system 中构建 X，管理这批包的需求催生了 Xenocara——其核心只是 BSD make 文件加一套通用规则，技术亦可移植到其他 BSD（向 NetBSD 的初步尝试因 make 宏差异而复杂但可解）。（BSDTalk EP106，[269.6-351.96]，L1）
- 他澄清 OpenBSD 的 X 并非 Xorg 分叉，仅含少量本地补丁与配置微调且多不为用户所见；用户感知的差异在于 OpenBSD 默认不装 GNOME/KDE 而以 fvwm 为窗口管理器；目标是 OpenBSD 4.2 时全部架构改用 Xenocara，唯最慢架构与 SH4/Landisk 因尚无共享库而与新构建体系的假设冲突待解；旧 X386 3.x 时代因 setup 程序依赖 Tk 而需另装 Tcl/Tk 的负担随之消失。 [存疑脚注] SH4 与 Landisk 细节经转写受损重建，须以 Xenocara 架构支持文档核对（BSDTalk EP106，[208.6-445.84]，L1）
- Herrb 兼任 X.org 安全官，管理流向 X.org 的全部安全类缺陷报告，长期计划是更主动地修复 X.org 代码库；他期待模块化降低参与门槛、吸引更多开发者关注 X 的局部如 3D 硬件加速，而 OpenBSD 此方向正缺志愿者。（BSDTalk EP106，[521.44-594.4]，L1）
- 他发出 Linux 中心化的当事人警示：X 是覆盖操作系统最广的开源项目之一（各 UNIX 变体、Windows、Mac OS X 等），但 X.org 的主导者似乎日益漠视非 Linux 系统；并非全世界都是 Linux，任何操作系统都不应以独占世界为目标；非 Linux 用户因自认小众而不报缺陷，使缺陷数量不反映各系统的重要性，他呼吁其他系统用户向上游提交报告以纠正这一错误计算。（BSDTalk EP106，[663.34-775.8]，L1）
- 访谈于 OpenCon 2007 之后在威尼斯 Bar Piccolo Martini 进行，对象为 Peter Hansteen；其著作 The Book of PF（No Starch Press，OpenBSD 防火墙实务指南）定于 2007 年 12 月 15 日出版，OpenCon 上私印样书已拍卖，亚马逊与出版社渠道可预订，会上已有人洽谈多语种翻译；作者称读者仅需基础 TCP/IP 知识，内容从规则集求值逐步进阶。（BSDTalk EP136，[220.79-901.72]，L1）
- 其转向 PF 的经历：为小公司管理网络时平台先以 Linux 为主、渐转 FreeBSD，但防火墙始终在 Linux 上，iptables 维护渐成苦役；旧防火墙硬件烧毁后改用 OpenBSD 加 pf，“再未回头”。（BSDTalk EP136，[253.15-296.63]，L1）
- PF 的可读性哲学：向 iptables 用户展示配置时对方常难以相信规则能如此简单——“这不是 shell 脚本”；装好系统的机器上五到十行 pf.conf 置于网络与世界之间即可工作。宏以符号名为服务列表（ssh、domain、www、https 等）提供可读简称；表是专为 IP 地址与网段设计的高效数据结构，支持 CIDR 与取反、可自命令行操纵，配合锚点使外部程序与规则集交互；“PF 不能动态改规则”的质疑至多部分成立。（BSDTalk EP136，[296.63-457.8]，L1） [订正：原 296.63-446.16，2026-09-29 SenseAudio 重转核对]
- CARP（Common Address Redundancy Protocol）的诞生部分是对一个故障切换协议在 IETF 冲向标准途中被发现牵涉三四项专利的回应，OpenBSD 团队遂自行撰写替代；CARP 作为虚拟网络接口让一组机器共享对外 IP，一主多备，主机故障时备份近乎透明地接管——凌晨三点主防火墙宕机无需短信叫醒管理员，半年一次的 OpenBSD 升级可挪至工作时间完成，主机恢复后备机再行交还。（BSDTalk EP136，[458.44-546.15]，L1） [订正：原“约三百余项”，2026-09-29 SenseAudio 重转核对]
- hoststated 由 Reyk Floeter 与 Pierre-Yves Ritschard（转写作 Rick Fleeter 与 Pierre Verchaire，拼写存疑）写成，经 PF 表与规则集集成：对外发布单一 IP 与主机名并以轮询重定向到后端机器表，守护进程检测后端存活、将死机移出地址池，从而令服务更可靠；至 OpenBSD 4.2，hoststated 已能较好处理 SSL 连接。（BSDTalk EP136，[546.15-621.95]，L1） [订正：原“另一开发者（转写姓氏不可辨）”，2026-09-29 SenseAudio 重转核对]
- 抗 DDoS 的状态追踪选项源自一次拒绝服务受害者的通用化追问，于 OpenBSD 3.7 前后加入：规则中可限定单主机最大并发连接数与时间窗内连接速率，超限者落入专门表；处置方式从直接封锁（配合 flush global）到借 ALTQ 队列给超限者极小带宽任其排队。（BSDTalk EP136，[626.33-689.28]，L1）
- spamd 与灰名单：spamd 约于 OpenBSD 3.5 引入，最初对黑名单来源的 SMTP 连接以每字节一次的应答拖延至对方放弃；同期出现的灰名单基于对 SMTP 规范“临时错误须在合理时间内重试”的较真解读——垃圾邮件多出自被劫持 Windows 机器上的简易软件、从不检查返回码亦不重试，真实邮件服务器则会在约半小时内回来；五年后灰名单仍能当场消灭约 95% 的垃圾邮件；spamd 消除的是低垂果实，最精明的发件者或借开放中继者仍可能通过；spamd 亦伪装成开放中继诱捕不校验投递的中继检查器，其灰名单中可见上万封从未投递的转发尝试。（BSDTalk EP136，[695.52-840.75]，L1）
- 结语立场：支持 OpenBSD 请购买 OpenBSD 用品，支持作者请购买其书；并以略带激烈的方式断言——不运行 OpenBSD 或未在其他 BSD 上运行 PF 的管理员“错失良多，把事情做得比必要的更难”。（BSDTalk EP136，[903.76-928.32]，L1）
- 主播两周年回顾：BSDTalk 首期发布于 2005 年 12 月 20 日；两年间 NetBSD 自 3.0（2005 年 12 月 23 日发布）演进至 4.0，PC-BSD 从未及 1.0 到今日，FreeBSD 7.0 正筹备候选版本；主播感谢社区与听众在时间、金钱、主机与精力上的捐助。（BSDTalk EP136，[119.63-183.73]，L2）
- Brauer 回顾 match 规则的起源与根本性：他自 2003 年起就想要 pass 与 block 之外的中性动作而始终无法说服同侪；NAT 改造使其成为刚需——否则每条 pass 规则都得附带 nat to。实现之后他才意识到这是 PF 的根本变化：旧模型由最后匹配规则决定一切，状态只需保存指回该规则的指针；新模型下一个包可被多个 match 规则依次作用（队列、日志、标签、scrub 等），状态上须维护命中的 match 规则链表。（BSDTalk EP192，[199.30-325.90]，L1）[订正：原 [207.12-330.88]，2026-09-30 SenseAudio 重转核对]
- 4.6 的 scrub 重写源于 scrub 混杂了本不应混杂的职责：碎片重组、规范化与 MSS 钳制、TOS 改写等，且作为独立规则集须对每个进入的包遍历，代价高昂。拆分后规范化成为可选的常规规则，碎片重组简化为单一的开关并改为默认开启；此前用户忘记书写 scrub 行时，未经重组的碎片会被静默丢弃，而几乎没有人的规则集按碎片情形写过。（BSDTalk EP192，[424.76-586.58]，L1）
- 碎片重组原有三种方法，实际上无人使用替代方案，归一为全量重组有两条环境性理由：互联网因 path MTU discovery 基本生效而碎片大为稀少；OpenBSD 内核内存管理从 3.4 时代启动时静态池分配（PF 内存耗尽即 panic）转向动态分配，压力不再。4.7 的 NAT 重写则带来约三成的实测提速，从 4.4 直接跃升可叠加 scrub 与翻译规则集消除的双重收益达约六成且体感明显；NAT 重写净删近千行，整个过程共去除约一千三百至一千五百行，当事人自陈因改进过于显然而未再做大量基准测试。（BSDTalk EP192，[491.96-729.28]，L1）
- NAT 与 RDR 成为常规规则上的动作（nat-to、rdr-to）后改变了规则书写范式：地址自用户视角即时改写，先 match in nat to 某地址、后继 pass in from 同一地址即可命中；需要时也可写多条带不同 NAT 设置的 pass 规则。管理员的规则集得以按逻辑分组——以一组 match 规则完成队列挂接等魔法，再把放行或阻止的裁决推迟到别处。（BSDTalk EP192，[871.60-939.90]，L1）[订正：原 [871.08-929.16]，2026-09-30 SenseAudio 重转核对]
- Xenocara 的起源：因 X 窗口系统上游实现项目变更许可证条款、且旧名称已成商标，OpenBSD 一度考虑自行 fork 并另起新名；开发者 Matthieu Herrb 借清洁鱼缸玻璃的小鱼学名造出 Xenocara 一词（以 X 开头，呼应 OpenBSD 以鱼类命名的传统）。最终项目决定不 fork 而跟随 X.org，Xenocara 遂成为既有做法的正式名称——为把 X 作为 OpenBSD base 系统的一部分而设的构建系统（X 不经 ports 与包系统分发）。 [存疑脚注] 转写将许可证变更写作 X386 许可证与 David Davis，通行记载为 XFree86 许可证争议，人名与项目名待核。（BSDTalk EP221，[80.04-161.60]，L1）
- Xenocara 的实质是构建封装而非分叉：它按依赖顺序对超过 250 个 X.org 模块调用 configure、make、make install；因 X 属于 base 系统，构建不得依赖外部工具——Mesa 构建系统过深依赖 GNU make 与 Python，OpenBSD 遂将预生成文件作为源文件提交进 CVS 树，免除全体开发者构建时的 Python 与 GNU make 依赖；另有支持 Vax、Sparc 等旧平台的本地改动未上游化。（BSDTalk EP221，[161.60-213.88]，L1）
- X server 特权分离代码由 Herrb 于约十年前（2002-2003）实现，至今仍在 OpenBSD 正常工作，但因在 Linux、Solaris 等 X.org 支持平台上移植该代码缺乏足够兴趣——他本人无意独力承担，其他项目亦无人接手——始终以一组 diffs 形式存于 Xenocara 树内，未提交上游。（BSDTalk EP221，[214.12-251.72]，L1）
- KMS（内核模式设置）困境是当时 OpenBSD 图形栈的核心问题：X.org 驱动整体转向 KMS，而 OpenBSD 内核尚无 KMS 支持，使项目要么困于旧版驱动，要么另辟蹊径——开发者将源自 Linux KMS 驱动的模式设置代码回植用户态，为 Sandy Bridge 与 Ivy Bridge 芯片组维护自定义 Intel 驱动，以传统用户态 X 驱动方式运行，保住 3D 加速与 X 视频加速能力；受访者视向内核移植 KMS 为 X 的未来，也是去除 X 服务器额外特权（系统主要安全隐患之一）的前提。 [存疑脚注] 转写将两位开发者名记作 Owen Haysworth 与 Jonathan Gray，人名拼写待与源码提交记录核对。（BSDTalk EP221，[262.44-372.14]，L1）
- 对 Wayland 的评估：该项目由 Kristian Høgsberg 等人自零开始、面向 Linux 设计，深度依赖 Linux 特有内核接口（输入子系统尤甚）；模式设置部分因 BSD 拟采用类似 KMS 的内核接口而在理论上可移植，但 Wayland 开发者明确不愿构建操作系统无关抽象层，故移植到 BSD 近乎按其合成 API 思想重写，工作量巨大且尚无人启动；其理念（削减 X 开销、提升本地图形性能、经合成管理器以另一方式实现远程显示）是否根本正确、能否满足真实应用需求，受访者直言尚无把握，而 X 目前工作良好、使用无处不在。 [存疑脚注] Wayland 发起人名依转写为 Christian Huxberg，通行记载为 Kristian Høgsberg，待核。（BSDTalk EP221，[456.46-572.66]，L1）
- 构建系统的可移植性与线程议题：Xenocara 构建系统因刻意保持简单（仅是 autotools 流程的封装）而具备合理可移植性，已被 DPB（OpenBSD 分布式包构建器）用于在 ports 集群上并行构建 Xenocara 且无需改动其本身；X 内部多线程场景不多，但新版 Mesa 的 LLVMpipe 软件渲染驱动使用线程，rthreads 真线程将使其受益，前提是解决 LLVMpipe 对 LLVM 与 Clang 的依赖——像 FreeBSD 那样以 LLVM/Clang 构建 base 并非易事，因 LLVM 构建系统存在大量 base 系统所无的外部依赖。 [存疑脚注] 转写记作 Mark SP 的演讲者疑为 DPB 作者 Marc Espié，待核。（BSDTalk EP221，[374.68-448.84]，L1）
- 工作范围与个人部署：Marco Peereboom 在 OpenBSD 主要从事存储与 SCSI 中间层工作；3.9 周期中被岔去实现 IPMI（智能平台管理接口）——新型与高端服务器内置的传感器协议，跟踪风扇、温度、电压等状态并把信息呈现给用户空间，可配合 sensors 命令监控告警；i386 与 AMD64 平台均适用。其个人机器多台运行 OpenBSD：一台旧的工作站（转写含混，疑为 Alpha 或旧 SPARC64）、一台 i386 web 服务器（朋友网站亦托管其上）、一台 HPPA 防火墙（将升级 3.9 并使用 PF 新特性）。（BSDTalk EP27，[90.24-208.04]，L1）
- 资金困境与 hackathon 机制：项目已亏损运行一段时间；开销主要在基础设施——网络费用昂贵、电费极高，因为项目坚持所有平台全部本地原生构建（Zaurus 快照即在 Zaurus 上构建），地下室机器全天候运转；已收捐赠获致谢，同时呼吁企业级赞助——盼有公司愿意为 hackathon 买单。年度 hackathon 为开发者大聚会：多数人飞赴 Calgary 写代码、规划战略，邮件往返缓慢的事项在面谈中大大加速；其副作用是总能发现需要多人不同技能协作才能定位的重大 bug，产出大量好代码与想法进入下个发布；面对面建立信任，而这种开发模式极依赖信任。另有定向 hackathon：如前一年威尼斯的 ports hackathon，约 10 名专家使 ports 系统大幅进步；ports 与包工具近期升级体验显著改善且质量可直接测得。（BSDTalk EP27，[218.08-430.34]，L1）
- 开发哲学与安全记录：OpenBSD 开发模式不讲废话——永远做对的事，不适合操作系统的特性就不会发生，因此对社区有时显得生硬；对许可证绝不妥协并引以为豪，纵然承受社区与其他方面的压力，流程中保持理性，不合格的代码不会进入发布、甚至直接移出树——想在此协作就得守此规则。对保持默认安装无远程漏洞的纪录表示自信——正是这一点当初吸引他入坑（厌倦了隔三差五担心被入侵的日子），但他不能替全世界打包票。（BSDTalk EP27，[436.30-552.92]，L1）
- 升级流程与包工具评价：当事人认为 OpenBSD 的升级过程比 apt-get 更透明——他试装 Ubuntu 后觉得 apt-get 要求用户预先懂得太多；承认 OpenBSD 安装器对新用户略显生畏，但这只是习惯问题：图形安装器问的是同样的问题，打字与点击之别而已；升级复用与安装相同的安装器、识别现有系统、连按回车即开始，最难的一步是敲出二进制路径；ports 侧的工具已做到完全透明——一条命令即可升级全部 ports 并解析依赖；ports 升级与替换功能为 3.8 与 3.9 之间引入、随 3.9 发布；他本人不做 ports，靠定时任务自动升级。（BSDTalk EP27，[552.92-700.92]，L1）
