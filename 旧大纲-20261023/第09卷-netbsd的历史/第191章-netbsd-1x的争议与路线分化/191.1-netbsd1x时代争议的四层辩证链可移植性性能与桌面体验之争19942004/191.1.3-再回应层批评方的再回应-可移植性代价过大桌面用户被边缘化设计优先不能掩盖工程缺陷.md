# 191.1.3 再回应层：批评方的再回应——可移植性代价过大、桌面用户被边缘化、设计优先不能掩盖工程缺陷

**要点**：批评方对 NetBSD 阵营反批评的再回应以三条论纲展开。其一，“可移植性代价过大”——NetBSD 1.x 时代维持 31 至 52 种平台支持导致 MI/MD 分层抽象成本累积，部分驱动因需兼容多平台而无法进行平台特定微优化，netbsd.duckdb 显示 netbsd-src 1999-2002 年 commit 量持续在 4 万至 5.8 万区间高位运行，但相当比例 commit 用于跨平台同步与移植维护而非 i386 性能改进；NetBSD 1.6 虽引入 UBC 与 Round-robin page colouring，但同期 FreeBSD 4.x 已有 UFS_DIRPREF、Soft Updates、SMPng 等更深入的 i386 性能优化，NetBSD 1.x 时代的性能改进仍落后于 FreeBSD 4.x。其二，“桌面用户被边缘化”——NetBSD 1.x 时代 sysinst 安装器、X11 配置工具、PCMCIA/CardBus 支持、笔记本电脑电源管理的用户体验长期滞后于 FreeBSD 4.x，pkgsrc 软件包数量在 1999-2001 年虽 commit 量超越 FreeBSD Ports 但实际可用软件包数量仍少于 FreeBSD Ports，桌面终端用户在 NetBSD 社区中长期处于边缘地位。其三，“设计优先不能掩盖工程缺陷”——NetBSD system.html 所述"we prefer getting a design right to tweaking a poor implementation"作为工程哲学原则上成立，但具体到 NetBSD 1.x 时代的 i386 性能差距、SMP 锁粒度不足（直至 1.6 仍为粗粒度锁）、UVM 性能落后于 FreeBSD VM 等工程缺陷，不能以“设计优先”一概豁免——设计优先不等于设计正确，1.x 时代的若干设计（如 UVM 早期版本、SMP 粗粒度锁）在后续 2.x/3.x 时代被重写或大幅修订，反向证明 1.x 时代部分设计并非“right”

The NetBSD system [EB/OL].** <https://www.netbsd.org/about/system.html**>（"we prefer getting a design right to tweaking a poor implementation"）；netbsd.duckdb netbsd-src 仓库 commits 表 §L1.1.1（1999-2002 年 commit 量 4 万至 5.8 万区间）；netbsd.duckdb netbsd-pkgsrc 仓库 commits 表 §L1.1.3（1997-2002 年 commit 量比例上升，但 commit 量比例不等于软件包数量或桌面可用性）；NetBSD 2.0（2004.12.9）Release Announcement（**<https://www.netbsd.org/releases/formal-2.0/NetBSD-2.0.html>**）引入 SMP 细粒度锁（SMPng 风格），反向证明 1.x 时代 SMP 锁粒度不足；NetBSD 5.0（2009.4.29）引入新 SMP 与线程调度，反向证明 1.x/2.x 时代 SMP 设计需要重写 ［A］

**史观**：技术选择的代价：可移植性广度的代价是单一平台深度不足，NetBSD 1.x 时代 i386 性能差距与桌面体验滞后是这一代价的具象呈现；总纲第 22 条——知识注定过时：NetBSD 1.x 时代的 UVM、SMP 粗粒度锁等设计在 2.x/3.x/5.x 时代被重写或大幅修订，证明“设计优先”的具体设计本身亦会过时；总纲第 25 条——0 信任原则：NetBSD 官方“design over microoptimization”陈述需考据，不得因当事人自述即豁免具体工程缺陷的考据

**辨析**：考据过程留痕——【查证来源】NetBSD 1.6 公告经官方一手核验，公告未明确提及 SMP 细粒度锁改进，与 NetBSD 2.0（2004.12.9）公告明确引入 SMP 细粒度锁形成对照，可作 1.x 时代 SMP 锁粒度不足的间接证据；NetBSD 2.0 公告与 NetBSD 5.0 公告的 SMP 改进条目经官方原文核验；【交叉验证方法】netbsd.duckdb netbsd-src 1999-2002 年 commit 量高位运行与 NetBSD 1.6 公告的 UBC 等性能改进互证，但 commit 量比例不等于性能改进比例——相当比例 commit 用于跨平台同步、移植维护、安全补丁（参见 §70.12 安全修复 commit），非全部用于 i386 性能改进；【存疑判定依据】“NetBSD 1.x 时代 i386 性能落后于 FreeBSD 4.x”的具体量化数据（如 SPECint、LMbench、UnixBench 评分对比）须对照 1999-2002 年间 BSD 评测报告核验，本次考据未取得完整一手评测数据，多靠邮件列表讨论与用户印象间接推断；“pkgsrc 软件包数量在 1999-2001 年少于 FreeBSD Ports”的具体数字对比须对照 1999-2001 年间 pkgsrc 与 FreeBSD Ports 的实际软件包数量统计核验，netbsd.duckdb commit 量比例不能直接等同于软件包数量比例；0 信任原则提示：批评方再回应亦存在自利偏差风险——批评方多为 FreeBSD 用户或同时期 Linux 用户，其“性能落后”“桌面体验滞后”的批评可能带有路线偏好，须与 NetBSD 用户视角的反批评对称呈现；“1.x 时代部分设计需要重写”的判断须警惕事后诸葛亮式偏见——2.x/5.x 时代的重写可能源于硬件演进（多核普及、64 位化）而非 1.x 时代设计本身错误，史家须回到 1.x 时代语境评估设计决策，不得以 5.x 时代标准苛责 1.x 时代设计
