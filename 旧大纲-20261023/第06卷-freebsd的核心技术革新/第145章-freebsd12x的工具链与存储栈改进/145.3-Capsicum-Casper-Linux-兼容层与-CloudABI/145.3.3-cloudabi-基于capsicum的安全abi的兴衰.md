# 145.3.3 CloudABI——基于 Capsicum 的安全 ABI 的兴衰

**要点**：CloudABI 是由 Ed Schouten（ed@，FreeBSD 前 committer）创办的 Capabilities Limited 公司开发的“纯能力导向”应用 ABI，基于 Capsicum 设计理念，目标是提供 POSIX 兼容但默认安全的应用二进制接口——CloudABI 程序在启动时即处于能力模式，只能访问显式传入的文件描述符，无全局文件系统命名空间访问。CloudABI 在 FreeBSD 11.x-12.x 时期存在于 ports（devel/cloudabi、devel/cloudabi-toolchain）中并提供内核模块支持，但最终未获得主流采用，CloudABI 项目在 2010 年代末 -2020 年代初逐渐停止活跃开发。其理念影响了后续 WebAssembly（WASI，WebAssembly System Interface）的设计——WASI 同样采用基于能力的安全模型。

**史料**：CloudABI 官方文档（Nuxi 存档）、Ed Schouten CloudABI 演讲（FOSDEM/BSDCan）、freebsd-cloudabi 邮件列表、ports/devel/cloudabi、WASI 规范与 CloudABI 的历史关联文档。 ［A］

**史观**：总纲第 5 条——没有必然性，只有偶然性〔CloudABI 生态冷启动的偶然性，按报告建议，待主理人审定〕：CloudABI 是一次“重新设计安全 POSIX”的雄心勃勃的尝试，但失败原因在于：① 生态冷启动问题——为 CloudABI 编译的程序无法访问常规文件系统路径，难以移植现有软件；②Capsicum 本身在 FreeBSD 外的 adoption 有限；③ 容器化（Docker/Kubernetes）与 WebAssembly 提供了替代性的沙箱方案。但 CloudABI 的核心思想——“默认拒绝、显式授权”——是安全设计的正确方向，在 WASI 中得到了延续。

**辨析**：CloudABI 从未进入 FreeBSD base 系统——始终存在于 ports 与第三方内核模块中；12.0-RELEASE Release Notes 未将 CloudABI 列为核心特性。CloudABI 的失败不是技术缺陷而是生态问题——其安全模型在理论上优雅，但缺乏商业驱动力和社区采用。Ed Schouten 在离开 FreeBSD committer 岗位后创立了 Capabilities Limited 推动 CloudABI，公司最终转向其他方向。

**文献**：Schouten E. CloudABI: Secure by Default [C]//FOSDEM/BSDCan, 2015-2018；Nuxi CloudABI Documentation Archive [EB/OL]；WASI Preview 1 Specification [S]. W3C/WASI SG.

- 2015 年 5 月末，FreeBSD 的 Linux 兼容层（Linuxulator）64 位支持由开发者长期维护的用户分支以约 200 个提交合并进 head，64 位 Linux base ports 的提交预期赶在 BSDCan 2015 完成，64 位兼容端口不能与 32 位并存但自带 32 位兼容层；社区同时讨论 pkg 未来直接对接 yum 仓库以摆脱逐 RPM 手工解包的现状，而 Steam 在 FreeBSD 上仍因缺失 futex 相关系统调用无法运行，移植以增量补齐系统调用的方式推进。（BSD Now EP91，[344.84-569.38]，L2）
- PC-BSD 10.1.2 发布热修复版，修正 RAIDZ 安装中 cache 与 log 设备名解析及 TrueOS 文本安装器在 UEFI 模式下的分区问题；同期 Lumina 桌面 0.8.4 随该版本发布，以 Qt5 从零编写、不依赖 DBus、PolicyKit、ConsoleKit、SystemD、HAL 等桌面框架，文件管理器内建 ZFS 快照与目录回滚概念，项目计划以自研窗口管理器替代 Fluxbox，动机包括 4K 显示器下的界面与字体缩放及全局键盘快捷键统一，且已可移植至多种 Linux 发行版等非 FreeBSD 平台。（BSD Now EP91，[2702.44-2925.40]，L2）

**史料**：

- Linux Fest Northwest 2015 街访构成一组当事人一手口述：任职于 Microsoft 的 Debian 开发者自述 FreeBSD 已成为 Hyper-V 与 Azure 的一等访客，并称 Colin Percival 完成 AWS、Steve Wills 完成 Google Compute Engine 的同类移植，还主张 PostgreSQL 最初主要开发于 BSD、在该环境下表现最佳——节目内另一受访者对此仅谨慎回应“可能最初是”；MinnowBoard 从业者自述 FreeBSD 的 UEFI 支持居三大 BSD 之最，该板以 Coreboot 方案兜底后三者皆可引导，并展示带机载摄像头视觉避撞的四轴飞行器；另有受访者介绍 GBDE 的口令确认式销毁设计（受迫交出口令亦获确认而数据已毁）与一次性交换分区加密。（BSD Now EP91，[1131.20-1764.60]，L1）
- GitHub 上的 UNIX 历史仓库将 1972 年以来 44 年的 UNIX 演进整理为可克隆代码库，导入 AT&T 研究版第 1、3、4、5、6、7 版快照、Unix/32V、历次 BSD 发行版、CSRG 的 SCCS 版本管理档案、386BSD 两次发行以及 FreeBSD 自 1.0 经 2.0 至当代仓库的初始导入；配套论文统计出 850 位可识别贡献者、约 2600 万行代码与 65.9 万次提交，其谱系图量化了 FreeBSD 9 中承自 4.3 BSD、Net/2 与历代 FreeBSD 的代码占比，并附文件名长度、注释密度、goto 与 register 关键字使用率等演化曲线。（BSD Now EP91，[2371.54-2596.36]，L2）
- 邮件列表话题 Death by Chocolate 讨论为 OpenSSH 生成并验证 Diffie-Hellman moduli 素数的方法：OpenSSH 以 k 个随机基做强伪素数检验，被提及的取值为 k=100，使所生成的数误为合数的概率压至以“被巧克力噎死”作比的量级；同期 FreeBSD 安全官员自 OpenBSD 导入新的 OpenSSH moduli 文件，理由是无证据表明旧文件有缺陷、定期更换被视为良好卫生。 [存疑脚注] 邮件标题转写为 Week Diffie Hellman Primes，疑为 weak 之误；转写仅称回复者为 Darren，推断为 OpenSSH moduli 维护者 Darren Tucker；两处均须对 openssh-unix-dev 邮件列表 2015 年 5 月原文核实。（BSD Now EP91，[4131.80-4241.08]，L2）

**史观**：

- 总纲1 一切真历史都是古代史：UNIX 历史仓库的谱系图显示，FreeBSD 9 约三分之一代码直接承自 FreeBSD 8、三分之一为新写，其更深地层中仍有成块代码原封未动地来自 4.3 BSD 与 Net/2；ping 等基础工具的大量行仍出自 20 世纪 70 年代的最初发行版，甚至有开发者因 macOS 手册页缺失作者署名而将线索追溯回 FreeBSD 补录。当代系统并非取代历史，而是历史代码的层积现场，BSD 史必须以代码考古方式从现役仓库内部读出。（BSD Now EP91，[2463.60-2535.52]，L2）
- 总纲3 不存在进步，只有权力再分配：LLVM 落地 OpenMP 支持，使 clang 用户得以利用多核与向量单元并获得与 GCC、Intel 编译器的 ABI 兼容，支持范围覆盖 ARM、PowerPC 与 32/64 位 x86；主持人预期此举为 BSD 打开高性能计算之门，而该领域此前被视为 Linux 的独占领地。技术能力的补齐在此并不构成线性的进步叙事，真正进入史册的是算力版图上各平台位置的重新分配——一方的补强即是权力在系统生态间的流转。（BSD Now EP91，[792.66-836.54]，L2）

**辨析**：

- HardenedBSD 公开考虑整体移除 Linux 兼容层，理由是该层意味着额外的大宗审计负担且其安全性历来存有疑问；节目主持人则从实用立场反对，认为 Linuxulator 便利性显著且 NetBSD、OpenBSD 亦有同类机制可参照。同一兼容层在两个衍生项目中被分别视为增长点与负资产，折射出安全最小化与兼容性实用两种工程取向在 2015 年的分岔。 [存疑脚注] HardenedBSD 移除意向系主持人转述，仅此单一来源，须对 HardenedBSD 当时的官方投票或公告页面核实。（BSD Now EP91，[571.25-605.90]，L4）
