# 134.4.2 UFS2 TRIM 支持与 SSD 优化

**要点**：9.0-RELEASE 中 UFS2 同时新增 TRIM 命令支持，在释放数据块时向底层 SSD 设备发送 delete 通知；通过 **newfs(8)** `-t` 标志或 **tunefs(8)** `-t` 启用；TRIM 基于 ATA8-ACS2 标准的 Data Set Management Command，对 SSD 写入寿命与长期性能优化至关重要；ZFS 的 TRIM 支持则晚至 9.2（有限支持）和 10.0（完整支持）

**史料**：svn r216796（UFS TRIM 实现）、FreeBSD 9.0 Release Notes、ATA8-ACS2 规范文档 ［A］

**史观**：技术路线分化：UFS 对 SSD 特性的支持体现了 FreeBSD 对硬件演进的快速响应，但 ZFS 的 TRIM 延迟暴露了复杂文件系统适应新硬件的难度；Linux ext4 在 2010 年前后即支持 TRIM，FreeBSD UFS 同期支持，但 ZFS 因 Sun/Oracle 遗产与跨平台复杂性延迟

**辨析**：UFS TRIM 并非默认启用——需要显式打开 `-t` 标志，因为在某些 SSD（尤其是早期消费级盘）与 RAID 控制器上 TRIM 可能导致性能下降或数据风险；默认禁用体现了 FreeBSD 的安全保守原则

**文献**：svn commit r216796；FreeBSD 9.0-RELEASE Release Notes（File Systems 章节）；**newfs(8)**、**tunefs(8)** man pages ［A］

**要点**：

- McKusick 亲述 BSD 名称起源：Bill Joy 为磁带分发而命名为 Berkeley Software Distribution，早期无版本号，后以 2BSD 起开始编号，至 3BSD 才统一源码与 make 构建。（BSD Now EP5，[1151.64-1265.94]，L1）
- McKusick 亲述 UFS 设计：文件系统被分为策略与实现两层，实现层写于 1982 年、此后未改一行，日志、布局与更新策略的演进均落在策略层。（BSD Now EP5，[1883.32-1986.24]，L1）
- BSD 曾拟从 Sun 引入其重构的虚拟内存系统以支持 mmap，因法律顾虑被律师否决，转而引入 CMU Mach 的 VM，后由 FreeBSD 开发者精简其外部 pager 等机制。（BSD Now EP5，[1338.02-1537.26]，L1）
- FreeBSD 9.2 正式发布，带来 ZFS TRIM 与 LZ4、virtio 驱动、DTrace 更新及 OpenSSH 更新等；同期基本系统以 Unbound 与 LDNS 取代 BIND。（BSD Now EP5，[70.76-89.24]，L2）
- gjournal 是块级日志而非文件系统日志：它运行于文件系统层之下，仅需文件系统极少量特化代码即可提供日志能力，且不区分数据与元数据而两者皆记录；因此即便启用 gjournal，FreeBSD 在严格意义上仍属无日志文件系统的主流操作系统，引用时不应将 gjournal 记作 UFS 自身的日志功能。（BSDTalk EP52，[117.82-190.9]，L1）
- 作者说明同时记录数据与元数据的设计动机：仅记元数据存在已知竞态，两者皆记使日志设计更干净，并带来崩溃后镜像设备保持一致、无需重新同步等附带收益；gjournal 还可用于绕开 GBDE 的非可靠性问题。（BSDTalk EP52，[168.42-230.5]，L1）
- 在 soft updates 之下唯一已知的不一致是资源泄漏，后台 fsck 的作用即回收丢失资源；gjournal 使后台 fsck 不再必要。对删除但仍被进程打开的文件，inode 无文件名引用却仍占盘，原方案将其移入 .deleted 目录以便挂载时整体清除，发布补丁后收到反对意见，作者正改写为依赖更快速 fsck 仅回收泄漏 inode 与块的方案。（BSDTalk EP52，[239.98-405.54]，L1）
- GELI 是 GEOM 上的磁盘加密层，与 GBDE 同层但实现路径不同；作者刚提交的数据认证代码使其能够校验数据本身，据其所知此前没有磁盘加密框架认证数据，这对断电场景下防止新数据与旧哈希错配、保证崩溃一致性至关重要。（BSDTalk EP52，[517.02-648.12]，L1）

**史料**：

- 当事人 Marshall Kirk McKusick 自述 1970 年代入读加州大学伯克利分校，与 Bill Joy 同室，师从 Susan Graham 从事程序设计语言研究，是本期 BSD 起源叙述的一手来源。（BSD Now EP5，[960.48-1006.58]，L1）
- 当事人提及 David Greenman、Doug Rabson 精简 VM、Rick Macklem 长期维护 NFS、Jeff Roberson 完成 SUJ 主体，均为其亲述的同行贡献。（BSD Now EP5，[1638.30-1764.70]，L1）
- 当事人自述正与 George Neville-Neil、Robert Watson 撰写《The Design and Implementation of the FreeBSD Operating System》第四版，目标当年底完成初稿。（BSD Now EP5，[2038.08-2064.36]，L1）
- 该期为 gjournal 与 GELI 作者的一手口述：补丁面向 FreeBSD CURRENT 与 FreeBSD 6-STABLE 发布、全部测试基于 UFS2（预计兼容 UFS1）、计划先行提交 CURRENT 并拟在 6.2 之前合入 6-STABLE；同时载明 2006 年 FreeBSD 版本控制实况——项目在受访者加入前已选定 Perforce，当时存在 CVS 转 Subversion 的失败尝试，因而 Perforce 是唯一可行选择，如今大多数开发工作在 Perforce、其提交量远超主 CVS 仓库。（BSDTalk EP52，[277.58-848.3]，L1）

**史观**：

- 总纲9 经验优先：McKusick 自述 UFS 实现层自 1982 年起未改一行，并坦言其设计事后证明是好的，稳定性的根据是长期经验而非事先的完备规划。（BSD Now EP5，[1883.32-1986.24]，L1）
- 总纲5 没有必然性，只有偶然性：Sun 因法律顾虑拒绝回授 VM，迫使 BSD 转而采用 CMU Mach，这一关键技术路线由偶然的法律与组织因素塑造，而非必然的技术演进。（BSD Now EP5，[1338.02-1537.26]，L1）
- 总纲10 动手者创造历史：访谈记录 Bill Joy、Jeff Roberson、Rick Macklem 等具体动手者在磁带分发、文件系统与 NFS 上的具体工作，而非以机构或领袖为中心。（BSD Now EP5，[1638.30-1764.70]，L1）
- 总纲4 分离聚合是永恒规律：作者断言 gjournal 远比 soft updates 代码简单，关键在于它是完全独立于 UFS 的代码块而非内核集成实现，而 soft updates 最受诟病之处恰是代码复杂；外置分离构造与内核集成构造之争呈现了存储技术中分离与聚合两条路线的往复。（BSDTalk EP52，[405.54-448.5]，L1）
- 总纲5 没有必然性，只有偶然性：作者自述工具选择并无理性最优可言：Perforce 是项目在其实质参与前的既成事实，Subversion 转换失败这一偶然事件将其封闭在既有路径中；技术基础设施的形态常由偶然决策与失败尝试的叠加所规定。（BSDTalk EP52，[801.74-830.34]，L1）

**辨析**：

- UFS 实现层自 1982 年起未改一行为当事人的记忆性自述，未在本期给出逐行源码证据。 [存疑脚注] UFS 实现层长期未改动的说法属当事人记忆性陈述，宜与仓库历史核对。（BSD Now EP5，[1948.48-2024.26]，L4）
- 转写存在段序错乱与局部讹误：如“write-free configurations”“geom roll”“multi-puffing”等处疑为音频识别错误，后者涉及作者在 Perforce 分支上一个约两年的多路径 GEOM 类的名称，引用该类名称前须回听录音核对；UFS1 兼容性亦仅属作者推测而非测试结论。 [存疑脚注] 多路径 GEOM 类名称与镜像一致性收益的适用配置在转写中均有讹误嫌疑，UFS1 兼容性为作者未经测试的推断。（BSDTalk EP52，[592.4-613.24]，L5）
