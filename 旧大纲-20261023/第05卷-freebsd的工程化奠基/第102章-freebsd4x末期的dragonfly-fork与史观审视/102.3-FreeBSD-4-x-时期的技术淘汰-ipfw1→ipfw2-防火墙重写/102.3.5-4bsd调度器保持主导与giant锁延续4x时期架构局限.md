# 102.3.5 4BSD 调度器保持主导与 Giant 锁延续（4.x 时期架构局限）

  **要点**：FreeBSD 4.x 时期内核调度器沿用 4.3BSD 调度器（4BSD scheduler），基于 estcpu（CPU 使用估计）与 nice 值计算优先级，使用全局运行队列；4BSD 调度器算法 O(n)（n 为系统进程数），在数千进程系统中性能下降，无 CPU 亲和性、无 SMT 支持；4.x 时期 SMP 支持仍使用 Giant lock（单一内核大锁）模型，任何时刻仅一个 CPU 可在内核态运行，多核扩展性受限；SMPng（SMP Next Generation）项目 2001 年启动，但 5.0-RELEASE（2003.1.16）才引入初步 SMPng 架构，4.x 时期仍为 Giant-locked 内核；Giant 锁与 4BSD 调度器是 4.x 时期的技术债务，但带来稳定性收益——4.x 因 “Giant 锁保护下简单” 而成为 ISP 与 Web 托管提供商的 “黄金时代”
  
**史料**：FreeBSD 4.x Release Notes；Robert Watson “FreeBSD SMPng Project SMP Network Stack”（2005 演讲）；freebsd-smp 邮件列表 2001-2003 年 SMPng 讨论；Jeff Roberson “ULE: A Modern Scheduler For FreeBSD”（BSDCon 2003）；freebsd.duckdb freebsd-src 仓库 commits 表 ULE 调度器首次 commit 为 2003-01-26 Jeff Roberson（5.0-RELEASE 2003.1.16 之后），印证 4.x 时期 ULE 尚未合入，4.x 全程沿用 4BSD 调度器 ［A］
  
**史观**：专题语（不设总纲条号）——技术选择的代价（原挂总纲第 6 条系伪名目，删条号）：Giant 锁选择付出多核扩展性代价，但获得稳定性收益；专题语（不设总纲条号）——技术选择即政治选择（原挂总纲第 7 条系伪名目，删条号）：4.x 时期 FreeBSD 选择 “Giant 锁 + 4BSD 调度器” 反映 “稳定性优先” 的技术政治选择
  
**辨析**：经 **freebsd.duckdb** commits 表验证〔原 bsd_commits.duckdb 系拆分前旧库名〕，ULE 调度器首次 commit 为 2003-01-26（5.0-RELEASE 之后），印证 4.x 时期 4BSD 调度器主导地位确凿，存疑已解决；Giant 锁在 4.x 时期的具体性能影响仍需对照基准测试核验（4 CPU 瓶颈 vs 2 CPU 瓶颈），bsd_commits.duckdb 无对应性能数据，仅能确认架构事实；SMPng 项目在 4.x 时期的具体进展需考据（2001 年启动但未在 4.x 时期合入）；4BSD 调度器与 4.x 时期 Linux O(1) 调度器（Ingo Molnar，2002）的对比需对照源码核验

**要点**：

- DragonFly BSD 4.0 与其热修复版 4.0.1 于本播出周相继发布：新增 Haswell GPU 支持，SMP 能力提升至 256 处理器并在 PF 中改进多核扩展，同时放弃 i386 平台加入纯 64 位行列；高频系统调用 git、pid、setproctitle、clock_gettime 调用超过十次时改为内存直读以降低开销，随机数发生器引入 ChaCha 算法，并随附 GCC 4.7.4 与取自 FreeBSD 的 libfetch SSL 支持。主持人将其定位为面向集群与大规模部署、追赶 FreeBSD（后者正向 1024 处理器推进）的发行版更新。（BSD Now EP65，[3279.25-3484.30]，L2）
- Brendan Gregg 以当事人身份自述其职业轨迹：长期从事 Solaris 家族与 DTrace、ZFS 工作并著有 DTrace 专著，转入 Netflix 后面对的架构为大规模 EC2 Linux 云加 FreeBSD 物理设备组成的 OpenConnect CDN；用户点击播放后流媒体即由 FreeBSD 传输，其自述夜间超过三分之一的美国互联网流量来自这些 FreeBSD 设备，且 FreeBSD 上的 DTrace 与 pmcstat 使其性能工程方法得以延续。（BSD Now EP65，[1299.01-1391.42]，L1）
- Gregg 提出两条经验性论断：其一，人（对）基准数字没有直觉，报出“800 万 mogofoo-ops”这类数字无从判断正误，工具是否可靠亦属未知，故“基准测试几乎百分之百是错的”[1399.34-1404.74]；其二为基准悖论——评估是否切换操作系统须在多项基准上全面获胜，若每项胜负近于掷硬币，三项全胜概率仅约百分之十二，故准确的基准测试对 FreeBSD 的被选型是关键门槛。其对策为主动基准测试：在基准长时间稳态运行期间，同步以 top、pmcstat、DTrace、iostat、gstat、systat 等工具核验行为与测试意图一致，并要求每个结果附注疑似瓶颈因子。（BSD Now EP65，[1422.05-1783.95]，L1）
- 访谈以实证案例支撑论断：某专业基准公司用脚本解析 FIO 输出时丢弃 K 量级后缀并删除十进制小数点（1.6 变 16），报告偏差达三个数量级；又如测试套件 makefile 为 Linux 配置高优化等级而为其他系统配置 -O0、在 Solaris 上编 32 位而 Linux 上编 64 位，实际测得的是框架而非被测系统。Gregg 进一步指出反驳一个基准所需工程时间多于制造它、小公司缺乏反驳人力、发布坏基准无任何法律后果，互联网基准生态因而近于“狂野西部”[2138.91-2142.19]。（BSD Now EP65，[1801.00-2161.04]，L1）
