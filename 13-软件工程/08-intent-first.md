# 08 知难行易：意图确证先于手段

> **项目侧增补**（2026-10-29，依 ykla 指令）：本文件不是 WHCode 上游正文，只在本项目生效；上游采纳前按 `NOTICE.md` 版本化回流。适用**一切任务**，不限工程类批次。

本文件只回答一件事：任务开工之前必须先确证什么，以及为什么手段不能先于目标。

## 1. 命题与来源

“知难行易”在本文件中的工程含义是：任务的困难不在执行，而在“为什么要做、做到什么算完成、什么不做”的共识；共识不立，执行必然反复。

来源定位：`02-sacred源材料/sacred_sources.duckdb`，`files.id=45`（前言），`blocks.id=1848`（`block_index=50`）。原文（节引，逐字保真；该块全文另见数据库 `blocks.id=1848`，本文件只引与命题直接相关的一段）：

> 开放 rsync 同步只是几分钟的事情。但让他理解其必要性是困难的。知难行易，故而“行”也变得困难。破山中贼易，破心中贼难（王守仁. 与杨仕德薛尚谦书[C]//王守仁. 王阳明集. 王晓昕，赵平略，点校. 北京：中华书局，2016：卷四文录一.）你可以用数据和安全手段向他说明好处和项目优先级。但问题不在这里。

旁证两条：

- **总纲 21（革命与改革）**：见 `00a-yike-source.md` §2，原文“革命与改革是历史方法论的分歧。Linux 靠革命，BSD 靠改革。改革的困难远高于革命。破山中贼易，破心中贼难。”——同一命题在总纲层的表述，与 `blocks.id=1848` 同源。
- **史学释读**：见 `00-编纂规则与格式规范/02-操作手册/03-史观原则/第3.7节.md` §3.7.26，将“知难行易”释为 BSD 改革路径的认识论基础——“难”在事前之“知”，“行”在“知”立之后。

**转引层级**：正文引文取自数据库 `blocks.block_content` 原文，属一手；总纲 21 为同一源文档的总纲层表述，属同源旁证；§3.7.26 是项目史学释读，**仅作旁证，不得替代原文**，也不得据以回改引文。

## 2. 工程翻译

三条，逐条给“原文依据→工程推论”。

| 序 | 条目 | 原文依据 | 工程推论 |
| -- | ---- | -------- | -------- |
| 1 | 知难 | “但让他理解其必要性是困难的。” | 目标、方向、必要性共识是任务里最贵的一段；说不清就开工，等于把成本转移给返工与中途转向 |
| 2 | 行易 | “开放 rsync 同步只是几分钟的事情。” | 手段、实现、工具链是分钟到天量级的事，可替换、可重做；不得把手段当成目标的等价物 |
| 3 | 知不立则行不顺 | “知难行易，故而‘行’也变得困难。” | 目标缺失时，执行不会因为手段先进而变顺，只会以更高的返工率偿还 |

结论：**手段是次要的，目标是首要的**。任务开工的次序是“先确证意图，再选手段”，不是“先定手段，再为手段找目标”。

## 3. 意图确证单

按任务选档。档 A 为全量，档 B 为轻量；档 B 出现升档信号（见 §5）即补齐为档 A。

### 3.1 档 A：全量六字段

| 字段 | 判定要点 |
| ---- | -------- |
| 用户原话 | 逐字摘录发起人的原话或原指令，不改写、不概括；转述与原话并存时以原话为准，转述只作注 |
| 目标 | 一句话写清“做完之后哪个问题被解决、谁受益”，可被第三方复核；不写“优化”“完善”一类不可判定词 |
| 非目标 | 逐条列出本批明确**不做**的事，防止范围外扩；与既有规则边界冲突者单列 |
| 验收判据 | 二值可判：满足什么即算成功（脚本退出码、门禁 PASS、文件存在、数值等于某值）；不含主观评语 |
| 手段自由度 | 写明哪些手段可自选、哪些被锁定及其锁定理由；未写即视为可替换 |
| 未知／`[待验证]` | 列出尚不确定的前提与待验项，逐条标注 `[待验证]`；不得以“先做起来再看”替代 |

六字段缺一不得开工。字段之间不得互相替代：目标不等于验收判据，非目标不等于手段自由度。

### 3.2 档 B：轻量三要素

| 字段 | 判定要点 |
| ---- | -------- |
| 用户原话 | 同档 A，一句话即可，须可定位 |
| 目标 | 一句话说清要达成什么 |
| 完成判据 | 一句话说清“怎样算做完”，可二值判断 |

档 B 不单列“非目标”字段，但第三问“不做什么”仍须在会话内答出并留一句结论；未特别声明时沿用现有规则边界，手段自选。

### 3.3 触发档位

- **档 A**：工程类批次、长线批次、跨会话续跑、高风险或不可逆操作（写库、删除、凭据、平台承诺、规则实质判据）、派发子代理。
- **档 B**：单次只读查询、单文件小改、格式化。

落点与门禁接线不在本文件：全局判据见 `流程规则/01-复核与验证.md` 的意图确证节，工程类批次细目见 `工程实践规则.md` §0.6。

## 4. 三问 STOP

| 问 | 要答出的东西 | 答不出的处置 |
| -- | ------------ | ------------ |
| 谁在痛（不做会怎样） | 具体的受损方与代价，可指认到人或产物 | 停手澄清 |
| 做完算成功吗（二值判据） | 一个可二值判断的验收结论 | 停手澄清 |
| 不做什么（非目标） | 明确的范围外清单 | 停手澄清 |

任一问答不出即停手澄清，**禁止先做后问**。澄清成本远低于返工成本：一次澄清是一个问题，一次返工是一条链——改代码、改文档、改台账、改门禁，逐层重来。

## 5. 手段次位条款

- 不得以既有工具、技术栈、脚本、既有设施反向裁剪目标；手段是达成目标的备选项，不是目标的定义者。
- 换手段须保持验收判据不变，并记录换用理由；判据随手段而变，说明目标已被手段改写，须回到档 A 重写。
- 出现“先试工具”“先跑脚本”“先改架构”的念头，即为升档信号：先把目标与非目标写成档 A，再动手段。
- 手段选择的争论若无法落到验收判据，即不是技术问题，而是意图分歧，应回 §4 三问。

## 6. 反模式、自反与失效

### 6.1 反模式

| 反模式 | 表现 | 纠正 |
| ------ | ---- | ---- |
| 以忙碌替代方向确认 | 开工即写脚本、即调工具，进度以行数与批次计 | 先写意图确证单，再开工 |
| 只讨论怎么做，不问为什么做 | 会议与对话集中在工具选型、目录结构、命令写法 | 先答 §4 三问 |
| 把手段选择当重要决策，把目标当琐事 | 为工具与写法反复权衡，对“要解决什么”一句带过 | 目标是首要决策，手段可替换 |
| 用技术争论掩盖意图分歧 | 争论以“哪种做法更专业”收场，实际分歧在目标 | 停止争论，写出双方的验收判据对比 |

### 6.2 自反

本文件也是形式主义：它只有改变决策与产物才成立。若意图确证单写了却不改变任何决定、批批照抄同一份模板、验收判据不参与收口判定，则本文件只是仪式，应按 `00-philosophy.md` §9 降级或删除。

### 6.3 “知”的有限性

“知”不可能完备。意图确证收敛于**最小可判定契约**——够判定“做没做对”，不够解释“为什么世界如此”。禁止以“把意图彻底搞清楚”为名无限调研：调研本身也是手段，须有终止条件（答出三问即止）。

### 6.4 失效条件与复审触发

- **失效条件**：意图确证连续两季零改变决策（写了不改变任何批次的开工判定与收口结论）；或全部任务均由单一发起人即时口头确认且不存在跨会话续跑（此时以会话内口头确认为准，本文件退为备查）。
- **复审触发**：2027-01-29 定期复审；`audit_engineering_practice.py` E8 连续误报；`流程规则/01-复核与验证.md` 的规则实质判据再变更。
