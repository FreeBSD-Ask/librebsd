# 工程实践规则

- **版本**：1.0｜**生效日期**：2026-10-22｜**复审日期**：2027-01-22
- **适用**：工程类批次（脚本、门禁、模板、规则流程、数据库迁移与回写、目录页、`.trae/specs/` 工程批次）

本文件是《给我自由——一部 BSD 的历史》编纂项目的工程实践专门规则，承载 `13-engineering-doctrine/` 中现有规则尚未覆盖的需求基线、ADR、技术债、专项裁剪与复审要求。G0–G5 阶段定义、十类变更裁剪表与既有门禁阶段归属在 `流程规则.md` 的“工程实践生命周期与阶段门禁”节；本文件只引用，不复制。

## 单一来源与适用范围

- **流程边界**：批次阶段、裁剪与门禁选择以 `流程规则.md` 为准。
- **工程实践专门要求**：需求基线、ADR、技术债、04／05／06 专项与复审以本文件为准。
- **域规则优先**：考据、写作、主题、释读、功能对比与回库、镜像站与 OCR、ROW_MINE、大纲层级与目录、长线任务归档，在其域内仍为最高权威。
- **方法来源**：`13-engineering-doctrine/` 只提供方法与证据层级，不直接作为项目判据；引用时写明条款与失效条件。
- **适用对象**：固定脚本、门禁脚本、模板、规则流程、数据库迁移与写回、目录页装配与前端、`.trae/specs/` 工程批次。
- **不适用**：史料考据、正文撰写、大纲内容增删；这些由既有域规则主导，本文件只补范围、非目标、验收判据与证据位置。

本规则不重复以下内容：UTF-8 无 BOM／LF、引号、代码块不可篡改、脚本执行安全、Git 暂存、数据库写入门禁、文档格式门禁、页面资产与无障碍门禁。上述事项直接引用对应规则文件。

## 0. 任务强制审计、复核与轮替（2026-10-22 立）

> **生效**：2026-10-22 00:00（Asia/Shanghai）。**不追溯**：生效前启动、已交付或已闭口的任务不补审、不补复核、不回填、不重开；在推线只对下一批及以后适用。已闭口线只在状态说明中保留“已闭口／不追溯”。

### 0.1 四道强制闸门

1. **准入审计**：开工前在 `01-项目管理/02-工程决策与技术债/任务审计台账.md` 增一行，填任务 ID、任务名、类型、风险级别、起算日、准入结论、准入证据、复核轮次、理论适用性、承担者与复审触发；未 PASS 不得开工。**以已启动为界**（`ADR-0013`）：触发点是任务的“启动”而非“立项草案存在”；已启动＝`tasks.md` 已有 `- [x]`、或该 slug 已在审计台账、或该 slug 已在复核台账（三者任一）；未启动 spec 免准入并计入 SKIP，L2 只对已启动者要求准入行。
2. **独立复核**：普通任务至少两轮（修改前、修改后）；高风险任务至少三轮（初稿、独立复核、修复后复验）。复核者与作者角色分离，作者不得自批；复核者须复跑命令或回读产物，不得只采信自报。复核明细写入 `任务复核台账.md`。**以收口为界**（`ADR-0014`）：轮次义务在收口时结算，已收口行不足即门禁 FAIL，在途（未收口）行不足记 WARN、不阻断；声明轮次低于最小值仍对全部行 FAIL。
3. **收口审计**：标完成前回填复核轮次、最新复核 ID、收口结论、收口证据、changelog、Git 取证（`git=`；历史行 `prebak=` 仍认）、已知限制与轮替状态；未 PASS 不得标“已完成”。
4. **台账轮替**：审计台账与复核台账按 `任务轮替与归档规则.md` §三之六 轮替；主表超过 100 行、200 KB 或跨季度，三者先到者触发；只迁已收口任务，主表只留指针与统计行，禁止双源。

### 0.2 准入审计字段

| 字段 | 要求 |
| ---- | ---- |
| 任务 ID | 与 `.trae/specs/<slug>/` 或线级 spec 一致，批内唯一 |
| 任务名 | 一句话，不得只写“杂项” |
| 类型 | 十类变更之一 |
| 风险级别 | 普通／高风险；高风险＝P0、写库、删除、凭据、平台承诺或规则实质判据 |
| 起算日 | 不早于 2026-10-22 |
| 准入结论 | PASS／FAIL；FAIL 不得开工 |
| 准入证据 | spec／tasks／checklist、任务书或审计编号的可定位路径 |
| 复核轮次 | 普通 ≥2，高风险 ≥3 |
| 理论适用性 | “适用”或 `TG-NNN` 列表；引用须在缺口登记中存在 |
| 承担者 | 具体角色，不得写“项目组”“以后” |
| 复审触发 | 日期或事件，二者先到者为准 |

### 0.3 独立复核

- **角色**：作者、复核子代理、独立复核、主理人；作者不得自批；高风险任务须有主理人签收。
- **轮次**：普通任务修改前、修改后各一轮；高风险任务初稿、独立复核、修复后复验各一轮。
- **证据**：输入版本（spec 版本、提交号或 SHA-256）、判据、结论、发现项、处置、证据路径；不得只写“已复核”。
- **证据复核（TG-004）**：复核者不得只看 diff 或作者自述；须复跑门禁命令、回读库或产物、抽样或全量复算，并在复核行写明命令、退出码与回读路径。
- **抽样**：每季度或每完成一个试点批次，随机抽查不少于两条任务，核对记录与实际产物；结论写入 `工程实践复审台账.md`。

### 0.4 收口审计字段

门禁命令与退出码、未通过项与处理、复核结论与最新复核 ID、证据路径、changelog id、Git 取证（`git=<commit>`；历史行 `prebak=` 仍认）、已知限制与未验证项、轮替状态、规格归档指针。缺任一项不得标“已完成”。

### 0.5 台账、门禁与违规

- **门禁**：`audit_task_lifecycle.py`（第三十二件），L1–L12 判据；只读，`--selftest` 负向夹具；登记在 `audit_gate_registry.py` 的 `REGISTRY` 与 `STAGE_MAP`（`G1,G4,G5`）。其中 **L2 以已启动为界**（`ADR-0013`）：只对 `tasks.md` 已有 `- [x]`、或已在审计台账、或已在复核台账的 spec 要求准入行；未启动 spec 免准入并计入 SKIP，门禁详情须打印 SKIP 数量与 slug 列表（截断前 10 个）。L3 不受影响，已收口任务仍须收口行。**L7 以收口为界**（`ADR-0014`）：实有轮次 ≥ 声明 ≥ 最低、轮次编号连续与高风险主理人签收只对收口结论 ∈ {PASS, 不适用} 的行判 FAIL，在途行不足记 WARN 单列、不影响退出码；声明轮次低于最低、轮次非整数、作者自批、轮次编号重复对全部行判 FAIL。
- **违规**：未准入即开工、未复核即收口、未收口即标完成、记录失真、轮替双源、拒绝抽查，均视为流程违规；违规任务不得进入 changelog 的“已完成”记录，不得归档，不得作为后续任务的证据引用。
- **理论缺口**：遇到 G0–G5、ADR、复核、轮替与测试理论未覆盖的情形，先登记 `TG-NNN` 并给出增补或修订建议；可普适者按 `13-engineering-doctrine/NOTICE.md` 回流，不直接改教义正文。

## 1. 需求基线

每个工程类批次必须具备 `spec.md`、`tasks.md`、`checklist.md`。规格至少包含：

| 字段 | 要求 |
| ---- | ---- |
| 编号 | `FR-XXX`／`NFR-XXX`，批内唯一 |
| 标题 | 一句话说明行为或质量属性 |
| 优先级 | P0／P1／P2 |
| 来源 | 用户原话、Issue、审计编号、门禁输出或故障记录 |
| 描述 | 系统在什么条件下必须做什么 |
| 输入／前置 | 数据、权限、环境、依赖 |
| 输出／后置 | 产物、状态变化、可观察结果 |
| 失败路径 | 失败返回什么、是否可重试、状态如何标记 |
| 验收判据 | 二值可判的 Given／When／Then 或命令＋期望输出 |
| 证据位置 | 测试、产物、日志、门禁输出的路径 |
| 归属 | 批次／里程碑 |
| 证伪条件 | 什么结果会证明这条需求判断错误 |

追溯链：`来源 → FR／NFR → 任务 → 验收 Check → 测试或证据`。抽查发现断链时，修链条本身，不得只补文档说明。

内容编纂批次可使用轻量基线：范围、非目标、验收判据、证据位置四段；不强制 FR/NFR 编号。

**滚动基线（TG-002）**：长线战役或范围会随探索变化的任务，允许按批修订范围与验收判据，但每批须在 `tasks.md` 或批次记录写明变更理由、影响面、受影响任务与复审触发；FR／NFR 可为 batch-scoped，不得用“范围未定”替代基线。

## 2. 设计与 ADR

### 2.1 何时必须写 ADR

出现下列任一情形，先落 ADR 再实现：

- 新增模块、固定脚本、门禁、模板或目录；
- 跨层调用、依赖方向变化、数据所有权变化；
- 权限边界、平台承诺、外部服务、不可逆数据格式变化；
- 修改既有规则的实质判据、合并或删除条款；
- 引入新的并发、性能、安全或 UI 专项。

### 2.2 ADR 必填字段

使用 `02-操作手册/14-工程实践模板/模板G-架构决策记录.md`，十二项字段缺一不可：

形式、矛盾、正面、负面、承担者、过去依据、现在依据、将来失效条件、0 信任校验、自由影响、安全和解、复审触发。

答不出“不做会怎样”者不得进入实现。ADR 存放在 `01-项目管理/02-工程决策与技术债/ADR/`，编号四位递增，索引登记在 `index.md`。

**轻量 ADR（TG-005）**：不涉及写库、删除、凭据、平台承诺、不可逆数据格式或规则实质判据的小任务，可使用五字段轻量 ADR：形式、矛盾、选择、代价、失效条件；仍须编号、索引与复审触发。高风险任务必须使用十二字段完整 ADR。

### 2.3 设计检查

1. 是否破坏既有目录边界或单一来源？
2. 是否暴露了“可能变化的决策”，还是把临时方案固化为规则？
3. 是否为未来需求提前抽象？
4. 失败路径是否显式，重试语义是否正确？
5. 是否有测量、测试或门禁证据？
6. 负面成本由谁承担，何时复审？
7. 过去／现在／将来依据是否同时给出？

## 3. 实现与验证

- 编码前先确认脚本放置：临时脚本进 `script/`，固定脚本进 `01-规则/脚本与命令/`；固定脚本须被规则或索引引用。
- 脚本改动按 `流程规则.md` 的脚本执行安全规程执行：复核、`script/_staging/` 演示、再复核、正式执行。
- 新增行为须有正向与失败路径测试；无法自动化者须有可复现命令与人工核对记录。
- **验证单元（读写一体，`ADR-0009`）**：凡有写入面的批次，按 L0–L5 执行一次完整循环（读入→写入→回读→还原）：L0 生产零改动、L1 读入真实、L2 写入真实、L3 逐条内容回读、L4 内容级幂等＋还原、L5 失败环 stdout 可见。只读审计、dry-run、selftest 只能标“前置已核”，不得标“通过”；纯阅读型批次须书面声明“无写入面”方可只做 L1／L0。全局生效以 TD-015 条件满足为准。
- 静态检查、文档格式、引号、加粗空格、不可见字符、CRLF／BOM 门禁按触发面运行。
- 未取得证据的项写“阻塞／未取得”，不得勾选通过；`[待验证]` 不得以推断关闭。
- 批量写库前跑 `claimdb_guard.py --db <库名>`；register 写库另走 `register_waterlock.py`；写前不落任何副本，改为打印库文件 SHA-256，并在 `12-数据库备份/<db>/` 追加一份专项正式备份（2026-10-23 令）。
- 目录页改动走既有九件门禁、三套浏览器回归、无障碍与页面资产门禁，不以“样式微调”豁免。

**证据型验证（TG-003）**：外部站点、OCR、ASR、人工判读等非确定性环节，不强制单元测试；须至少有负向夹具、独立复算、双跑或回放、抽样人工判读中的两类证据，并写明失败路径与重试语义。无法自动化者须有可复现命令与人工核对记录。

**学术证据质量（TG-011）**：史料与正文质量按 `考据规则.md` 的来源层级、0 信任、三次复查、证据等级与逐字保真判定；本节只补工程证据，不复制考据规则正文。

## 5. 专项裁剪

### 5.1 04 并发与性能

触发面：多进程 OCR、批量并发、DuckDB 写并发、锁与水位、共享缓存、性能优化。

要求：

- 写共享状态、不变量、锁与水位数、失败模式、回退方案、验证计划；
- 多进程写库须串行化或分区，禁止无锁并发写同一表；
- 性能改动须有同夹具前后对比，报告 p50／p95／p99 或等价分布，不以单次样本结项；
- 不以“跑了几小时没崩”作为正确性结论；
- 复用 `claimdb_guard.py`、`register_waterlock.py`、`rotate_guard_state.py`、`镜像站挖掘与OCR流水线规则.md` 的既有经验，不另造平行设施。

### 5.2 05 安全、自由与主体性

触发面：网络抓取、令牌与账号、外部 API、下载执行、权限边界、日志脱敏。

要求：

- 写威胁模型：资产、对手、攻击面、信任边界、现有控制、残余风险、证据、代价、失效条件；
- 凭据只存本地受控位置，不入库、不进日志、不进夹具、不进提交；
- 外部命令与下载执行默认隔离，不直接在主进程执行不可信内容；
- 读者可见界面保留退出、导出、离线能力；不引入强制账户、强制联网、暗黑模式、排行榜或成瘾机制；
- 安全结论不得用“最佳实践／合规”替代威胁分析与可复现验证。

**本地凭据与外部服务（TG-010）**：key 池、Cookie、账号与令牌须有单一受控位置、权限限制、隔离区与轮换清单；发现泄露迹象立即轮换并重开技术债；凭据扫描报告须区分高／中／低风险，误报要留依据；不得把“本地文件”视为天然安全边界。

### 5.3 06 极简 UI 与资源

触发面：目录页 `重构2026/index.html` 或其装配源、任何读者可见界面。

要求：

- 复用既有页面资产、无障碍、服务器契约、三套浏览器回归门禁；
- 单文件自包含页面是当前和解，不直接套用教义 50 KB JS／20 KB CSS／2000 节点预算；须记录项目自己的实测值与失效条件；
- 最小化或不可见时停止绘制、动画与轮询；不以装饰性图片、视频、自动播放增加常驻资源；
- 主题、对比度、键盘可达、错误信息可读性按既有无障碍门禁判定。

## 6. 角色与批准

| 角色 | 职责 | 不得做的事 |
| ---- | ---- | ---------- |
| 主理人 | 范围、优先级、验收、发布批准；安全与平台承诺签收 | 以口头意见替代变更记录 |
| 主代理 | 执行、汇总、落账、提交；组织复核 | 自批门禁；把未验证能力写进结论 |
| 复核子代理 | 只读复核、反例优先、独立复现 | 作为唯一安全／平台／性能批准依据 |
| 发布／归档 | changelog、归档、标签或“未发布”声明 | 改写已发布记录或删除历史证据 |

单人＋AI 的补偿控制：作者与批准者帽子显式声明；能用脚本／测试判定的不用文字评审代替；评审结论落到路径、行号、命令输出或哈希；AI 结论可核验但不作独立审计；安全与平台承诺由主理人签收。

**AI 代理可靠性（TG-008）**：子代理或 AI 助手的自报不得作为证据；须以磁盘回读、独立进程复算或门禁输出为准。多会话共享工作树时，写库前须确认无并发写者，register 走 `register_waterlock.py`，写前打印库文件 SHA-256 并在 `12-数据库备份/<db>/` 落专项正式备份（不落工作区副本），写后断言仅本批意图段变更；上下文交接须留断点文件与真值源指针，不得依赖会话记忆。

## 7. 既有规则治理

对既有规则或流程的修订、增补、重构、合并、降级、删除，按下列程序：

1. **审计条目**：在基线审计或专项审计中给出文件、小节、问题、证据、处置、优先级、承担者；
2. **影响分析**：列出受影响的规则、脚本、门禁、模板、AGENTS 索引与 changelog；
3. **前后对照**：保留改动前原文要点与改动后行为；删除或合并须给迁移指针；
4. **备份**：删除或大段改写前，按 `流程规则.md` 的过时内容处理规则备份；
5. **执行与复核**：按脚本执行安全规程执行，逐处复核；
6. **门禁**：跑对应门禁与全量文档门禁；`audit_gate_registry.py` R1–R8 全 PASS；
7. **记录**：changelog 逐条记录审计编号、改动位置、理由与证据；
8. **复审**：在复审台账登记失效条件与下次复审日期。

无审计编号的“顺手改写”不得提交；不得以“重构”为名整篇重写未审计的文件；不得删除现行有效条款而不留替代或迁移说明。

## 8. 复审与回流

- **周期**：每季度或每完成一个工程类试点批次，以先到者为准；不创建自动化或定时任务。
- **内容**：规则是否仍改变决策、模板是否仍被使用、门禁是否仍有效、技术债是否到期、教义条款是否需项目化修订。
- **记录**：使用 `02-操作手册/14-工程实践模板/模板J-工程实践复审.md`，写入 `01-项目管理/02-工程决策与技术债/工程实践复审台账.md`。
- **空壳条款**：不能改变任何决策或产物的条款，删除或降级，并在台账记录原因。
- **上游回流**：可普适的教训按 `13-engineering-doctrine/NOTICE.md` 的变更记录版本化回流；项目侧不复制教义正文。

## 10. 不变量度量（TG-009）

本项目不采用 velocity／burndown；进度与质量以可复算的不变量为度量：

| 度量 | 口径 | 证据 |
| ---- | ---- | ---- |
| 台账＝源 | 登记表、审计台账、长线台账的数字必须由权威源派生，不另立数字 | 各线探针 `--check` |
| 六层对齐 | 包／产物／台账／库／大纲／宿主逐层计数闭合 | 线级对账脚本输出 |
| 门禁命中率 | 门禁发现的真实缺陷数／运行次数；连续空转须复审降级 | 门禁输出、复审台账 |
| 缺陷逃逸率 | 收口后由复核或抽查发现的缺陷数／本批缺陷总数 | 复核台账、抽查记录 |
| 复核产出率 | 复核发现项中改变结论或产物的比例；零产出须说明 | 复核台账 |

度量只用于判断“是否仍能改变决策”，不得作为绩效或排名；数据不完整时标“未取得”，不得估算。
