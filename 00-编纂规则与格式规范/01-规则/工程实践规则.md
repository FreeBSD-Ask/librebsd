# 工程实践规则

- **版本**：1.0｜**生效日期**：2026-10-22｜**复审日期**：2027-01-22
- **适用**：工程类批次（脚本、门禁、模板、规则流程、数据库迁移与回写、目录页、`.trae/specs/` 工程批次）

本文件是《给我自由—一部 BSD 史》编纂项目的工程实践专门规则，承载 `13-engineering-doctrine/` 中现有规则尚未覆盖的需求基线、ADR、技术债、专项裁剪与复审要求。G0–G5 阶段定义、六类变更裁剪表与既有门禁阶段归属在 `流程规则.md` 的“工程实践生命周期与阶段门禁”节；本文件只引用，不复制。

## 单一来源与适用范围

- **流程边界**：批次阶段、裁剪与门禁选择以 `流程规则.md` 为准。
- **工程实践专门要求**：需求基线、ADR、技术债、04／05／06 专项与复审以本文件为准。
- **域规则优先**：考据、写作、主题、释读、功能对比与回库、镜像站与 OCR、ROW_MINE、大纲层级与目录、长线任务归档，在其域内仍为最高权威。
- **方法来源**：`13-engineering-doctrine/` 只提供方法与证据层级，不直接作为项目判据；引用时写明条款与失效条件。
- **适用对象**：固定脚本、门禁脚本、模板、规则流程、数据库迁移与写回、目录页装配与前端、`.trae/specs/` 工程批次。
- **不适用**：史料考据、正文撰写、大纲内容增删；这些由既有域规则主导，本文件只补范围、非目标、验收判据与证据位置。

本规则不重复以下内容：UTF-8 无 BOM／LF、引号、代码块不可篡改、脚本执行安全、Git 暂存、数据库写入门禁、文档格式门禁、页面资产与无障碍门禁。上述事项直接引用对应规则文件。

## 采用级别

采用“完整（按需触发）”：

| 教义范围 | 项目适用 |
| -------- | -------- |
| 00–03、07 | 所有工程类批次的方法基线 |
| 04 并发与性能 | 多进程、多线程、锁、共享缓存、写库并发、性能优化时启用 |
| 05 安全、自由与主体性 | 网络访问、凭据、外部命令、权限边界、日志脱敏时启用 |

裁剪不等于跳过证据；每批在 `tasks.md` 写明适用专项或不适用理由。

## 1. 需求基线

每个工程类批次必须具备 `spec.md`、`tasks.md`、`checklist.md`。规格至少包含：

| 字段 | 要求 |
| ---- | ---- |
| 编号 | `FR-XXX`／`NFR-XXX`，批内唯一 |
| 标题 | 一句话说明行为或质量属性 |
| 优先级 | P0／P1／P2 |
| 来源 | 用户原话、Issue、审计编号、门禁输出或故障记录 |
| 描述 | 系统在什么条件下必须做什么 |
| 输入／前置 | 数据、权限、环境、依赖 |
| 输出／后置 | 产物、状态变化、可观察结果 |
| 失败路径 | 失败返回什么、是否可重试、状态如何标记 |
| 验收判据 | 二值可判的 Given／When／Then 或命令＋期望输出 |
| 证据位置 | 测试、产物、日志、门禁输出的路径 |
| 归属 | 批次／里程碑 |
| 证伪条件 | 什么结果会证明这条需求判断错误 |

追溯链：`来源 → FR／NFR → 任务 → 验收 Check → 测试或证据`。抽查发现断链时，修链条本身，不得只补文档说明。

内容编纂批次可使用轻量基线：范围、非目标、验收判据、证据位置四段；不强制 FR/NFR 编号。

## 2. 设计与 ADR

### 2.1 何时必须写 ADR

出现下列任一情形，先落 ADR 再实现：

- 新增模块、固定脚本、门禁、模板或目录；
- 跨层调用、依赖方向变化、数据所有权变化；
- 权限边界、平台承诺、外部服务、不可逆数据格式变化；
- 修改既有规则的实质判据、合并或删除条款；
- 引入新的并发、性能、安全或 UI 专项。

### 2.2 ADR 必填字段

使用 `02-操作手册/14-工程实践模板/模板G-架构决策记录.md`，十二项字段缺一不可：

形式、矛盾、正面、负面、承担者、过去依据、现在依据、将来失效条件、0 信任校验、自由影响、安全和解、复审触发。

答不出“不做会怎样”者不得进入实现。ADR 存放在 `01-项目管理/02-工程决策与技术债/ADR/`，编号四位递增，索引登记在 `index.md`。

### 2.3 设计检查

1. 是否破坏既有目录边界或单一来源？
2. 是否暴露了“可能变化的决策”，还是把临时方案固化为规则？
3. 是否为未来需求提前抽象？
4. 失败路径是否显式，重试语义是否正确？
5. 是否有测量、测试或门禁证据？
6. 负面成本由谁承担，何时复审？
7. 过去／现在／将来依据是否同时给出？

## 3. 实现与验证

- 编码前先确认脚本放置：临时脚本进 `script/`，固定脚本进 `01-规则/脚本与命令/`；固定脚本须被规则或索引引用。
- 脚本改动按 `流程规则.md` 的脚本执行安全规程执行：复核、`script/_staging/` 演示、再复核、正式执行。
- 新增行为须有正向与失败路径测试；无法自动化者须有可复现命令与人工核对记录。
- 静态检查、文档格式、引号、加粗空格、不可见字符、CRLF／BOM 门禁按触发面运行。
- 未取得证据的项写“阻塞／未取得”，不得勾选通过；`[待验证]` 不得以推断关闭。
- 批量写库前跑 `claimdb_guard.py --db <库名>`；register 写库另走 `register_waterlock.py`；写前 prebak。
- 目录页改动走既有九件门禁、三套浏览器回归、无障碍与页面资产门禁，不以“样式微调”豁免。

## 4. 技术债

使用 `02-操作手册/14-工程实践模板/模板H-技术债登记.md`，主表在 `01-项目管理/02-工程决策与技术债/技术债登记.md`。

每条必须含：ID、描述、来源、影响、承担者、偿还条件、复审日期或触发、状态。禁止“后续补”“已知问题”等无承担者条目。已偿还须附证据；条件失效须写失效依据。技术债不因批次结束而消失，只在复审中判“已偿还／仍存在／条件失效”。

## 5. 专项裁剪

### 5.1 04 并发与性能

触发面：多进程 OCR、批量并发、DuckDB 写并发、锁与水位、共享缓存、性能优化。

要求：

- 写共享状态、不变量、锁与水位数、失败模式、回退方案、验证计划；
- 多进程写库须串行化或分区，禁止无锁并发写同一表；
- 性能改动须有同夹具前后对比，报告 p50／p95／p99 或等价分布，不以单次样本结项；
- 不以“跑了几小时没崩”作为正确性结论；
- 复用 `claimdb_guard.py`、`register_waterlock.py`、`rotate_guard_state.py`、`镜像站挖掘与OCR流水线规则.md` 的既有经验，不另造平行设施。

### 5.2 05 安全、自由与主体性

触发面：网络抓取、令牌与账号、外部 API、下载执行、权限边界、日志脱敏。

要求：

- 写威胁模型：资产、对手、攻击面、信任边界、现有控制、残余风险、证据、代价、失效条件；
- 凭据只存本地受控位置，不入库、不进日志、不进夹具、不进提交；
- 外部命令与下载执行默认隔离，不直接在主进程执行不可信内容；
- 读者可见界面保留退出、导出、离线能力；不引入强制账户、强制联网、暗黑模式、排行榜或成瘾机制；
- 安全结论不得用“最佳实践／合规”替代威胁分析与可复现验证。

### 5.3 06 极简 UI 与资源

触发面：目录页 `重构2026/index.html` 或其装配源、任何读者可见界面。

要求：

- 复用既有页面资产、无障碍、服务器契约、三套浏览器回归门禁；
- 单文件自包含页面是当前和解，不直接套用教义 50 KB JS／20 KB CSS／2000 节点预算；须记录项目自己的实测值与失效条件；
- 最小化或不可见时停止绘制、动画与轮询；不以装饰性图片、视频、自动播放增加常驻资源；
- 主题、对比度、键盘可达、错误信息可读性按既有无障碍门禁判定。

## 6. 角色与批准

| 角色 | 职责 | 不得做的事 |
| ---- | ---- | ---------- |
| 主理人 | 范围、优先级、验收、发布批准；安全与平台承诺签收 | 以口头意见替代变更记录 |
| 主代理 | 执行、汇总、落账、提交；组织复核 | 自批门禁；把未验证能力写进结论 |
| 复核子代理 | 只读复核、反例优先、独立复现 | 作为唯一安全／平台／性能批准依据 |
| 发布／归档 | changelog、归档、标签或“未发布”声明 | 改写已发布记录或删除历史证据 |

单人＋AI 的补偿控制：作者与批准者帽子显式声明；能用脚本／测试判定的不用文字评审代替；评审结论落到路径、行号、命令输出或哈希；AI 结论可核验但不作独立审计；安全与平台承诺由主理人签收。

## 7. 既有规则治理

对既有规则或流程的修订、增补、重构、合并、降级、删除，按下列程序：

1. **审计条目**：在基线审计或专项审计中给出文件、小节、问题、证据、处置、优先级、承担者；
2. **影响分析**：列出受影响的规则、脚本、门禁、模板、AGENTS 索引与 changelog；
3. **前后对照**：保留改动前原文要点与改动后行为；删除或合并须给迁移指针；
4. **备份**：删除或大段改写前，按 `流程规则.md` 的过时内容处理规则备份；
5. **执行与复核**：按脚本执行安全规程执行，逐处复核；
6. **门禁**：跑对应门禁与全量文档门禁；`audit_gate_registry.py` R1–R8 全 PASS；
7. **记录**：changelog 逐条记录审计编号、改动位置、理由与证据；
8. **复审**：在复审台账登记失效条件与下次复审日期。

无审计编号的“顺手改写”不得提交；不得以“重构”为名整篇重写未审计的文件；不得删除现行有效条款而不留替代或迁移说明。

## 8. 复审与回流

- **周期**：每季度或每完成一个工程类试点批次，以先到者为准；不创建自动化或定时任务。
- **内容**：规则是否仍改变决策、模板是否仍被使用、门禁是否仍有效、技术债是否到期、教义条款是否需项目化修订。
- **记录**：使用 `02-操作手册/14-工程实践模板/模板J-工程实践复审.md`，写入 `01-项目管理/02-工程决策与技术债/工程实践复审台账.md`。
- **空壳条款**：不能改变任何决策或产物的条款，删除或降级，并在台账记录原因。
- **上游回流**：可普适的教训按 `13-engineering-doctrine/NOTICE.md` 的变更记录版本化回流；项目侧不复制教义正文。
