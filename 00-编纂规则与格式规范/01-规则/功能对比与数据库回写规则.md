# 功能对比与数据库回写规则

本文件汇总《给我自由——一部 BSD 的历史》编纂项目中“现代操作系统功能实现对比（4 大 BSD 与 Linux）”与“分析结果回写既有数据库（02-10）”的规范。涉及跨系统功能比较、技术演进时间线、分析结果入库的操作须逐条对照本文件执行，不得跳过。

## 功能对比分析规范

涉及操作系统功能实现比较（实现时间、差异、思想、替代品、平台支持、淘汰）的分析须遵循 0 信任原则，首现年等关键事实须以既有代码仓库数据库的提交记录为准，不得仅凭通识或单一来源采信。

具体执行要求：

- **数据源约束**：功能首现年、峰值年、末现年与提及提交数须来自各代码仓库数据库（`03-原始史料库/01-代码仓库史料/02-10`）的提交消息扫描结果，不得使用百科类来源（维基百科、百度百科等）作为时间依据。
- **0 信任原则适用**：首现年=该技术在提交消息中最早出现的年份，可能早于正式并入；提及≠实现；词典匹配含误报可能，所有结论须以相对趋势为准，并与卷章叙事互证后方可采信。
- **词典校验**：技术词典正则匹配须经过误报校验（如 `bpf` 命中 Berkeley Packet Filter、`kvm` 命中 kvm(3) 系统调用、`rust` 命中人名、`cgroup` 命中 UFS 分区术语、`DTRACE` 命中编译宏），对易冲突关键词改用组合词或函数调用形式，并接受残留边缘噪声且以注记声明。
- **首现年合理性审核**：每个功能的首现年须与该技术真实诞生年对照，明显偏早者须诊断误报源头并修正词典，禁止直接采用明显异常的年份。
- **五维对比字段**：功能对比须覆盖五个维度——实现时间（各仓库首现年）、差异（各系统实现区别）、思想（设计哲学）、替代品/演化（被取代或被借鉴的方向）、平台支持与淘汰。
- **史料价值区分**：同名概念的早期出现（如 FreeBSD 1995 的 SSH 1.2、1999 的神经网络模拟器）是真实历史事实，须保留并标注其与后期正式功能的区别，不得误删。

## 分析结果回写数据库规范

此前提取的提交分析信息（技术演进、功能对比、企业贡献、协作网络）须回写至既有代码仓库数据库（`03-原始史料库/01-代码仓库史料/02-10`），遵循去重与幂等原则。

具体执行要求：

- **目标数据库**：FreeBSD（02-FreeBSD/db/duckdb/freebsd.duckdb）、NetBSD（03-NetBSD/db/duckdb/netbsd.duckdb）、OpenBSD（04-OpenBSD/db/duckdb/openbsd.duckdb）、DragonFly（05-DragonFlyBSD/db/duckdb/dragonfly.duckdb）、Linux kernel（10-LinuxKernel/db/duckdb/linux-kernel.duckdb）。
- **新表结构**：回写内容存入以下新表（各库统一 schema）：
  - **tech_features**：功能对比，主键 `(repo, feature)`，字段含类别、各年（首现/峰值/末现）、提及提交数、思想、替代品、平台、差异注记。
  - **tech_roadmap**：技术演进路线图，主键 `(repo, tech)`，字段含类别、首现/峰值/末现年、提及提交数。
  - **org_contributions**：企业/组织贡献，主键 `(repo, org)`，字段含提交数、新增/删除行数。数据源为各库的 `*_sponsor_summary.json`、`*_submitted_summary.json`、`linux_kernel_sob_summary.json`。
  - **codev_network**：开发者合著网络，主键 `(repo, dev_a, dev_b)`，字段含合著提交数。数据源为各库的 `*_codev_network.csv`。
- **去重原则**：所有写入使用 `INSERT OR REPLACE`，以唯一键（主键）去重——重复写入时覆盖更新，不产生重复行；跨库不合并，每库存本库对应项目的数据。
  > **DuckDB 适配（2026-08-26 复核）**：目标库已升格 DuckDB 主存储层，且转换后的表**无主键/唯一约束**（实测 freebsd.duckdb 的 commits/repos/org_contributions/codev_network 等表 `table_constraints` 为空）。`INSERT OR REPLACE` 在无约束表上等同普通 `INSERT`，**不会去重**。回写脚本须二选一：①按各表逻辑主键（如 `codev_network(repo,dev_a,dev_b)`、`org_contributions(repo,org)`）先建唯一索引再 `INSERT OR REPLACE`；②采用“先 `DELETE` 同键旧行再 `INSERT`”幂等策略（可参照 `脚本与命令/bsdnow_igpu_transcribe.py` 的显式取号＋事务写入做法）。此为本规则在 DuckDB 层的未落地适配项。
- **字段名兼容**：组织数据源的 top 字段名可能为 `top`/`top_sponsors`/`top_authors`/`commits_with_org`，加载时须兼容，避免取到空值。
- **文件名兼容**：不同仓库的 summary 文件名前缀不同（linux-kernel 用下划线 `linux_kernel_`，FreeBSD 有历史 `fbsd_`），加载时须按仓库映射文件名。
- **元数据留痕**：每次回写须在 `db_meta` 表写入 `tech_features_written` 键记录各表行数，便于追溯。
- **幂等可重跑**：建表使用 `CREATE TABLE IF NOT EXISTS`，脚本可重复执行；重复执行仅更新既有行，不报错、不重复插入。
- **验证留痕**：回写后须执行验证查询（新表存在、关键功能首现年正确、组织贡献非空），记录验证结果。

## 分析结果写入大纲规范

全部分析结果（功能对比、技术演进、企业贡献、协作网络、跨项目对比等）须回写至对应大纲章节（`05-卷册大纲/`），确保大纲可索引到全部统计结论。

具体执行要求：

- **卷册总览嵌入**：每个卷册的卷总览章目录（`第N章-卷总览/`，N＝卷内章号）须含“统计分析报告引用（第九层 B-18 展开）”块，列出该卷相关的分析报告（报告名 + 一句话关键发现 + 报告路径）。
- **重点章节嵌入**：与技术演进/功能对比直接相关的章节（如 ZFS/DTrace/bhyve/pf/pledge/HAMMER 等技术史章节）的章级综合（`NNN.0-章级综合/`）须含“技术演进与功能对比结论引用”块，写明该章涉及功能的首现年与跨系统对比要点。
- **B 系列结论**：B-01~B-18 结论引用块按既定映射嵌入各卷总览与重点章节。
- **幂等自更新**：嵌入脚本须按报告名/章节名/结论编号去重，变更则替换旧行，缺失则追加；重跑不得产生重复内容。
- **路径规范**：大纲内引用的分析报告路径统一为 `03-原始史料库/01-代码仓库史料/01-数据库本体/统计分析/<报告名>.md`。
- **可复现脚本**：嵌入操作通过脚本执行（`embed_b_to_outlines.py`、`embed_reports_to_outlines.py`、`embed_tech_to_chapters.py`，均为历史一次性脚本，未在 `script/` 或 `脚本与命令/` 留存；见 `脚本与命令/README.md` 历史登记），禁止手工编辑大纲插入结论。

## 禁止事项

- **禁止使用不可信时间来源**：功能首现年不得使用百科类来源，须以数据库提交记录为准。
- **禁止直接采用异常年份**：未经误报诊断的首现年不得直接写入。
- **禁止篡改原始提交**：回写仅新增分析表，不修改 `commits`/`commit_files` 等原始表。
- **禁止批量无验证替换**：词典修正与写入须逐个验证，禁止无校验的批量替换。
- **禁止跨库混写**：每库只写本库对应项目的数据，禁止将 Linux 数据写入 BSD 库。
