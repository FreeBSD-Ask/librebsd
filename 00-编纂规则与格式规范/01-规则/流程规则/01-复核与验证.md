## 意图确证（知难行易；全任务适用；2026-10-29 立）

本节是**意图确证的判据正文**。理论依据见 `13-软件工程/08-intent-first.md`；其余文件（`AGENTS.md`、`工程实践规则.md`、`01-规则/README.md`、模板与门禁脚本）只引用本节，不复制本节正文。判据来源与原文定位：`02-sacred源材料/sacred_sources.duckdb` 的 `files.id=45`（前言）／`blocks.id=1848`（`block_index=50`）。

节引原文（逐字保真，仅引至本句；全文见 `13-软件工程/08-intent-first.md` §1）：

> 开放 rsync 同步只是几分钟的事情。但让他理解其必要性是困难的。知难行易，故而“行”也变得困难。

工程翻译：难在“知”（任务方向、目标与必要性的共识），不在“行”（具体手段）；“知”不立则“行”不顺（“故而‘行’也变得困难”）。故应把意图固化为可判定契约，把手段降为可替换的次要项，并适用于一切任务。

**适用范围（全任务，不限工程类批次）**：内容编纂、考据、数据库、大纲、目录页、归档、一次性小任务、长线续跑、派发子代理，一律适用。工程类批次与非工程任务的差别只在档位选择，不在是否需要确证。

**档 A（全量六字段）**：适用工程类批次、长线批次、跨会话续跑、高风险或不可逆操作（写库、删除、凭据、平台承诺、规则实质判据）、派发子代理。六字段逐项书面写出：①**用户原话**（逐字摘录，不应改写）；②**目标**（可判定的终态）；③**非目标**（明确排除项）；④**验收判据**（可测、可核）；⑤**手段自由度**（允许与不应更换的工具、设施、技术栈）；⑥**未知／`[待验证]`**（含验证路径）。

**档 B（轻量三要素）**：其余任务（单次只读查询、单文件小改、格式化等）适用。三要素：①**用户原话**；②**目标**；③**完成判据**（二值可判，即达成／未达成）。写于会话首条或任务书一行，应可定位（文件＋小节／行号，或会话消息位置）。**不应以“档 B”名义跳过三问 STOP。**

**升级条款**：一旦出现“手段先于目标”迹象（先试工具、先跑脚本、先改架构、先选技术栈、先沿用既有设施再补说目的），当批即升为档 A；已在执行的写入步骤应停手，补齐意图确证后方可继续。

**三问 STOP**：①**谁在痛**——不做这件事会怎样，代价由谁承担；②**做完算成功吗**——二值判据是什么；③**不做什么**——非目标清单是什么。任一问答不出即停手澄清，**不应先做后问**；取舍时一律选澄清，澄清成本远低于返工成本。

**手段次位**：不应以既有工具、技术栈、脚本或设施反向裁剪目标。更换手段应同时满足：验收判据不变；理由留痕（批次记录或 ADR）。目标是首要的，手段是次要且可替换的。

**落点**：档 A 写于 `spec.md` 首节、`tasks.md` 批首或长线任务书；档 B 写于任务书或会话记录一行。任务审计台账的准入证据应写明定位路径（文件名＋小节名或行号），不应只写“已确认”。

**子代理**：派发提示应含目标、非目标、验收判据三项；子代理不应自行改写目标，可在验收判据不变的前提下自选手段；子代理自报完成不构成意图确证证据，应由派发方按验收判据复核。

**长线续跑**：以该线任务书与 `01-项目管理/01-编纂规划与报告归档/长线任务总登记表.md` 的“权威源／续跑入口”字段中的既有目标与范围为意图基线；基线变更应记录（任务书或 changelog），不重做已完成批次，不追溯已收口行。

**变更回流与门禁**：意图变更（目标、非目标或验收判据的实质变动）回 G0 重写意图确证单、回 G1 重列需求与验收；工程类批次的接线由 `audit_engineering_practice.py` E8 校验，任务准入由 `audit_task_lifecycle.py` L2 校验；无机器判据的档 B 由复核抽查留痕（`任务复核台账.md`）。

**自反**：“知”不可能完备，确证收敛于最小可判定契约；不应以“再调研一轮”代替判断，不应无限调研。本节若不能改变决策或产物，按 `13-软件工程/00-philosophy.md` §9 删除或降级，不应留作空转条文。

## 修改前后复核规则

修改前后各复核一次，确认修改正确无误；允许使用脚本、批量工具等编程手段执行修改，但脚本输出与批量结果应逐项复核，不应默认接受。

具体执行要求：

- **修改前复核**：每次修改前应对原文进行一次复核，确认修改点与上下文一致。
- **修改后复核**：每次修改后应对修改结果进行一次复核，确认修改正确无误。
- **脚本与批量工具**：允许使用脚本（含 Python、sed、awk 等）与批量替换工具执行修改；脚本应放置 `script/` 目录下，文件名应见名知义；脚本运行前后各复核一次。
- **逐行核对**：复核时应逐行核对，不应跳行或简化检查；批量修改后应抽样或全量核对修改结果。
- **机械修改的上下文判断**：脚本规则应结合上下文设计（如正则应避免误匹配标题内实质括号），不应无差别替换；无法修改的内容可以保留原状。
- **阶段裁剪**：复核范围与强度按下文“工程实践生命周期与阶段门禁”的六类变更裁剪表执行；纯文档、缺陷修复、紧急修复不应跳过对应“不可裁剪”项。

## 三轮完整执行规则

上述流程应完整执行三轮，然后严格、完整的复查一轮，如果还有问题继续执行三轮，依次递归直至无问题。

具体执行要求：

- **三轮完整执行**：上述“修改前后复核 + AutoCorrect 调用 + 逐个核对”流程应完整执行三轮。
- **复查一轮**：三轮执行完毕后，应严格、完整地复查一轮，确保整体一致。
- **递归执行**：若复查后仍有问题，继续执行三轮，再复查一轮，依次递归直至无问题。
- **留痕**：每轮执行结果应记录，便于追溯。

## 校对规程（《图书校对工作基本规程》对接；2026-11-14 立）

**依据**：中国出版工作者协会《图书校对工作基本规程》（2004-10-12）§2—§7；《图书质量管理规定》（2005-03-01 实施）第五条及附件《图书编校质量差错率计算方法》；GB/T 14706-1993《校对符号及其用法》。位阶与裁剪见 `13-软件工程/10-standards-first.md` §5，标准著录见 `01-项目管理/02-工程决策与技术债/标准基线与文档治理差距-20261114.md`。

**适用**：一切读者可见交付物（号文、规则、模板、报告、目录页文本）与内容层落盘（大纲题名、注文、书目述评）。正文编纂仍按绝对红线不应，本规程不构成开禁。

### 一、校次与既有流程的映射

本规程不另立平行流程：既有“三轮完整执行规则”与“复查一轮”即三校一读的项目形态。

| 校次 | 规程表述 | 项目形态 | 主体 | 校什么 |
| ---- | -------- | -------- | ---- | ------ |
| 一校 | 初校 | 第一轮完整执行 | 机器为主 | 编码、引号、不可见字符、加粗空格、Markdown 结构、锚点、口径（校异同于机器判据） |
| 二校 | 二校 | 第二轮完整执行 | 人为主 | 逐行 diff、引文与来源比对、数字与单位、标点（校异同） |
| 三校 | 终校 | 第三轮完整执行 | 人 | 语义、事实、逻辑、知识、政治性（校是非） |
| 一读 | 通读检查 | 复查一轮 | 责任人 | 整篇连贯、读者视角、跨节一致、引用完整 |

**机校顶一个校次**（规程 §5.1）：全门禁通过可折抵一校，但不应折抵三校与通读；三校应由人完成。

### 二、校异同与校是非的分工（规程 §2）

- **校异同**：以原稿、来源、上游产物为基准逐字比对，发现并改正转换、录入、批处理造成的差异。项目落点：diff 复核、引文回源、装配 `--check`、哈希断言。
- **校是非**：判断原稿自身的内在矛盾。硬伤（错别字、多漏字、异体字、专名错、标点／数字／量和单位不合国标、版式不合规）直接改；语法、逻辑、事实性、知识性、政治性错误只质疑，不擅改，不润色（规程 §5.4）。

### 三、十类差错与判据（规程 §6）

| 类 | 差错 | 项目判据 | 处置层 |
| -- | ---- | -------- | ------ |
| 1 | 文字 | 错别字、多漏字、错简错繁、异体旧字形 | 人改／质疑 |
| 2 | 词语 | 错用、褒贬、异形词、生造、成语 | 人改／质疑 |

## 任务台账口径与不变量（2026-10-22 立）

**背景**：各任务线以 JSON 台账（`script/` 下的 `*_ledger.json` 等，gitignored）记录已判读进度。台账是**派生视图**，与权威源冲突时以权威源为准；但读数口径一旦错，进度与对账会同步失真。

**三条不变量（每条均应全库清零才可判“一致”）**：

| 不变量 | 含义 |
| ------ | ---- |
| `judged == sum(records 区间)` | 已判读量等于各区间长度之和 |
| `spec == judged` | 规格数等于已判读量 |
| `eff == messages → completed` | 有效量等于消息数时才可置 completed |

**口径硬约束**：

- **`read_judged`＝已判读封数**（＝`records` 区间之和），**不是候选条数、也不是入纲块数**。三者混用会得出互相矛盾的进度。
- **批次数应数 tag**，不许按文件数或估算。
- **note 里写百分数应写 `%%`**（否则格式化会吃掉），数字应可独立反查——记账文案不应照抄模板（历史上有把模板占位数字原样落账的先例）。
- **台账行数与 `\n` 计数差 1**：记账以 `git diff --numstat` 为准，核验器断言值应单独换算，两者不可混用。
- **含在途数据的台账整文件排除**，不入库。
- **台账文件可能被并发会话改写**——引用前必查 `mtime`；多处并发写时以“行在账”为准，勿重试补写造成真重复。

**判据非空**：三条不变量可对任一线的台账直接计算验证；`read_judged` 口径可由 `records` 区间和与新判读件数双向核对。
