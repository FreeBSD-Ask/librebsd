# 流程规则

本文件汇总 FreeBSD 历史书编纂项目中所有与工作流程、修改规范、复核流程、文件编码相关的规则。所有修改、复核、清理操作须逐条对照本文件执行，不得跳过。

**强制参照规则**：复核任何章节时，必须同时参照 `02-sacred源材料/shigang.md` 和 `02-sacred源材料/lishidagang.md`。复核流程按 lishidagang.md §3.3（评估）和 §2.6（监控与复核）执行，哲学符合度检验对照 shigang.md 编纂方法论执行。

## 修改前后复核规则

修改前后各复核一次，确认修改正确无误；允许使用脚本、批量工具等编程手段执行修改，但脚本输出与批量结果须逐项复核，不得默认接受。

具体执行要求：

- **修改前复核**：每次修改前须对原文进行一次复核，确认修改点与上下文一致。
- **修改后复核**：每次修改后须对修改结果进行一次复核，确认修改正确无误。
- **脚本与批量工具**：允许使用脚本（含 Python、sed、awk 等）与批量替换工具执行修改；脚本须放置 `script/` 目录下，文件名须见名知义；脚本运行前后各复核一次。
- **逐行核对**：复核时须逐行核对，不得跳行或简化检查；批量修改后须抽样或全量核对修改结果。
- **机械修改的上下文判断**：脚本规则须结合上下文设计（如正则须避免误匹配标题内实质括号），不得无差别替换；无法修改的内容可以保留原状。

## 脚本执行安全规程

执行任何脚本必须经过**四步**，缺一不可：

1. **复核脚本**：执行前审查脚本逻辑——输入源、输出目标、副作用、幂等性、安全边界；确认脚本不会在未授权情况下写正式库/改正式文件。
2. **单独文件夹演示**：在 `script/_staging/<脚本名>/` 下试运行。演示输入必须是真实数据的**只读副本或最小样本**（数据库脚本用 COPY 的临时库；文件脚本用临时目录；输出重定向至 staging 目录）。演示不得触碰正式数据。
3. **再复核演示结果**：比对演示输出与预期（计数、内容、副作用清单），确认行为正确、无越界。
4. **成功才能正式执行**：演示通过后，方可对正式数据执行；执行后仍须按“修改前后复核规则”复核正式结果。

具体执行要求：

- **分类执行**：
  - **只读类脚本**（扫描/统计/报告，无写操作）：第 1 步复核确认“纯只读”后可免演示，直接执行；但输出须抽样复核。
  - **写库/改名/删除/批量修改类脚本**：必须完整四步。演示须以临时副本验证破坏性操作的效果，确认无误再对正式数据执行。
- **演示隔离**：演示输入一律用副本/样本，演示输出一律在 `script/_staging/` 下，不得污染正式目录与正式库。
- **路径参数**：脚本设计时优先支持输出路径/输入路径参数（argv），以便演示时重定向至 staging；无参数的硬编码脚本，演示时使用复制到 staging 的临时版。
- **幂等性**：正式执行前确认脚本幂等（重跑不产生重复/累积效应）；破坏性脚本遵守“备份后一次性更新”原则（防链式污染）。
- **记录**：演示与正式执行的差异、复核结论登记 changelog。

## 批量过滤与删除型修复的安全规则

> **来源**：播客核心观点提取与大纲回写（spec `podcast-bibliographic-reference-integration-2026-08-27`）子节级回写中，为消除复核发现的错位项，错误地引入“整段黑名单”逐段剔除，导致数百条相关片段被连带删除。本节将此教训固化为强制规则。

核心原则：**修误命中用正向收紧，不用反向黑名单；删除型修复必须先评估影响面；复核与验证必须双向对称。**

具体执行要求：

- **正向收紧优先**：修复“误命中/错位”时，首选提高相关性门槛（强实体匹配、语义打分、关联度阈值），而非“命中某词即整段删除”。黑名单仅限用于明确无歧义的广告/垃圾短语，且不得以单个高频普通词（如 `intern`、`malloc`、`puppet`、`daemon`）作为黑名单词——这些词常是相关内容的正常组成部分。
- **删除前影响面评估**：任何“删除型”修复（黑名单、整段剔除、批量删除）在应用前，必须先统计该规则会命中多少条记录、其中多少是正例、多少是误杀（先跑 `count` 与抽样，再决定是否执行）。评估脚本与结果留痕于 `script/`。
- **双向复核**：复核“修复效果”时，必须同时查两向——**false positive**（该删没删的错位项，检查“是否已清除”）与 **false negative**（该留没留的正例，检查“是否被误杀”）。只查单向会导致删除型错误静默漏检。
- **对称验证脚本**：验证脚本不得只断言“错位项已清除”，必须对称地断言“正例仍保留”。正例清单取自复核前的已确认相关内容。
- **删除型操作不可静默**：删除不会报错、不产生错误日志，因此删除型修复比新增/改写更易漏检，须以显式计数与抽样复核弥补其不可见性。
- **禁止追加式黑名单膨胀**：不得在修复过程中反复追加黑名单词以“逐个消除”复核发现项；每追加一次即须重新执行“影响面评估 + 双向复核”，确认无连带误杀后方可保留。
- **回退与还原**：删除型修复一经发现误杀，立即停止追加，回退到误杀前的版本；不得在错误方向上继续修补。

## 序号调整例外

**说明**：本小节是“编号重排类操作”的专项规范，明确编号重排场景下脚本化修改的执行约束。编程方式修改文件内容须遵循上文“修改前后复核规则”与下文“脚本执行安全规程”。

**允许范围**：

- 子节编号重排（如 116.X → 120.X 的批量编号修正）
- 章节序号连续性修复
- 文件名与编号同步调整

**约束**：

- 脚本须放置 `script/` 目录下
- 脚本文件名须见名知义（如 `renumber_subsections_120.py`）
- 脚本输出须逐个手动复核，不得默认接受
- 脚本不替代最终人工核对
- 修改前后各复核一次

**示例**：

- `script/renumber_subsections_120.py` —— 第120章子节编号从 116.X 重排为 120.X
- `script/renumber_subsections_vol5.py` —— 第五卷子节编号重排
- `script/rename_volume_dirs_20260726.py` —— 12 个卷文件夹从“第N卷/”重命名为“第NN卷-中文slug/”格式，与章文件夹“第XX章-slug/”格式统一
- `script/fix_remaining_volume_refs_20260726.py` —— 修复原脚本负向回顾断言遗漏的 4 处“：”后路径引用

**适用边界**：

- 内容撰写、史料考据、文字润色等场景按“修改前后复核规则”执行（允许编程、须复核）
- 编号重排应保持编号本身的机械一致性，涉及内容语义的修改须结合上下文判断

## Frontmatter 元数据一致性规则

**说明**：本节规定 `概述.md` 的 YAML 前置元数据（`chapter`、`id`、`volume` 字段）须与 SUMMARY.md 的当前章号、卷号保持一致，不得遗留重排/重组前的旧编号。

### 字段对应关系

具体执行要求：

- **`chapter` 字段**：须与 SUMMARY.md 中该章的当前章号完全一致（如 SUMMARY 中为“第 21 章”，则 frontmatter 须为 `chapter: 第 21 章`，不得遗留旧编号如“第 161 章”）
- **`id` 字段**：须与当前章号一致（如 SUMMARY 章号为 21，则 frontmatter `id` 前缀须为 `CH21`，不得遗留旧前缀如 `CH161`）
- **`volume` 字段**：须与该章实际所在卷号一致（如章 345 在第十八卷，则 `volume: 第十八卷`，不得遗留旧卷号如“第十二卷”）
- **`cross_ref_ids` 字段**：跨引用中引用的章号须与当前编号体系一致；若涉及跨章引用，须复核被引用章的实际当前编号

### 触发条件

以下情形须触发 frontmatter 一致性检查：

- **章号重编号**：全书或局部章号重排后（如 2026-08-03 历史 1-348 重排）
- **卷重组**：章在卷之间迁移后
- **章拆分/合并**：章拆分或合并后
- **新增补遗章**：新增补遗章时，其 frontmatter 须以当前编号体系为准，不得引用旧编号体系

### 检测与修复流程

- **检测方式**：人工比对全部 `概述.md` 的 frontmatter（`chapter`/`id`/`volume`/`cross_ref_ids` 字段）与 SUMMARY.md 当前章号、卷号——逐章读取 frontmatter 原文，逐项比对
- **修复方式**：对检测到的不一致字段，逐个手动修改：先读取 `概述.md` frontmatter 原文 → 修改 `chapter`/`id`/`volume` 为当前值 → 确认 H1 标题已与 SUMMARY 一致 → 记录修改
- **修复后验证**：重新人工核查全部 `概述.md` frontmatter，确认不一致数为 0

### 例外

无例外。所有 `概述.md` 的 frontmatter 须与当前 SUMMARY 章号/卷号一致，不得保留旧编号。

1. `https://annas-archive.gl`
2. `https://annas-archive.pk`
3. `https://annas-archive.gd`

**故障转移机制**：若主镜像（`.gl`）请求失败（HTTP 5xx、超时、连接拒绝），自动切换至次镜像（`.pk`），再至第三镜像（`.gd`）；每个镜像最多重试 3 次，重试间隔指数退避（1s、2s、4s）。

### 搜索策略与结果筛选

**搜索优先级**（按精确度）：

1. ISBN 搜索：`<mirror>/search?q=<isbn>&ext=pdf&lang=<target_lang>`
2. DOI 搜索：`<mirror>/search?q=<doi>&ext=pdf`
3. 标题+作者搜索：`<mirror>/search?q=<title>+<author>&ext=pdf&lang=<target_lang>`
4. 仅标题搜索（兜底）：`<mirror>/search?q=<title>&ext=pdf`

**结果筛选规则**（按优先级）：

1. 语言匹配 `language_target` 字段（精确匹配优先；若无精确匹配，英文书籍可接受 `en-us`/`en-gb` 等变体）
2. 格式：PDF 优先，EPUB 次之（用户要求“便于识别的格式”，PDF 更通用）
3. 年份：与 `year` 字段一致优先；否则取最新版本
4. 文件大小：书籍 ≥ 1MB，论文 ≥ 50KB（避免下载到错误的小文件）
5. 来源：优先 `Library Genesis`、`Sci-Hub`、`Internet Archive` 标记的条目（这些通常质量较好）

### 文件完整性验证

下载完成后须验证文件完整性：

- **PDF 文件**：须以 `%PDF-` 开头
- **EPUB 文件**：须以 `PK`（ZIP）开头
- **文件大小阈值**：书籍 ≥ 1MB，论文 ≥ 50KB

验证通过后方可移动至目标目录并更新 manifest；验证失败时按“Anna's Archive 镜像优先级与故障转移”小节规则重试下一镜像。

### OCR 后处理

**PDF OCR**：使用 Tesseract 命令 `tesseract <input.pdf> <output_basename> -l eng+chi_sim+fra+deu --psm 1`，输出 Markdown 至对应 `ocr/` 目录，文件名同原 PDF 但扩展名 `.md`。

**文本层优先**：OCR 前须先检测 PDF 文本层（pymupdf `get_text()` 全页提取 >100 字符），**有文本层的矢量 PDF 直接用文本层入库（`pymupdf_textlayer`，ocr_status=verified），不 OCR**；仅纯扫描件才 OCR。

**RapidOCR 替代**：Tesseract 无法安装（winget/choco 权限受限）时改用 **RapidOCR**（`rapidocr_onnxruntime`，纯 Python + onnxruntime，清华镜像安装），流程：pymupdf 渲染 200-250dpi → RapidOCR 识别 → 输出 `ocr/*.md`；8 进程并行 + 每文件独立子进程。完整规范见 [镜像站挖掘与OCR流水线规则.md](镜像站挖掘与OCR流水线规则.md)。

**EPUB 转换**：使用 pandoc 命令 `pandoc <input.epub> -t markdown_strict -o <output.md>`，输出至对应 `ocr/` 目录。

**OCR 校对规则**：按 0 信任原则，OCR 文本须与原 PDF 抽样核对（每 100 页抽 5 页比对），警惕技术术语、版本号、人名错讹；在 manifest `ocr_status` 字段标注：错讹率 < 5% 标 `verified`，≥ 5% 标 `needs_review`。

**OCR 失败处理**：若 Tesseract/pandoc 未安装或失败，标记 `ocr_status=failed`，记录错误，不阻塞下载流程；扫描质量差到无法识别的（如 1 页模糊照片）检索其他转载格式代替（官方重印本/二手文献转录），不强行入库。

### 并行下载与限速

- **并行执行**：使用 `concurrent.futures.ThreadPoolExecutor` 并行下载
- **默认并行度**：`max_workers=3`，可通过 `--workers` 命令行参数调整，最大 5
- **限速**：每镜像每秒最多 2 个请求（`time.sleep(0.5)`）
- **原子性**：manifest 更新使用 `threading.Lock` 保证原子性，无并发写入冲突

### 失败处理与断点续传

- **失败标记**：三镜像全部失败时标记 `download_status=failed`
- **错误记录**：`errors` 数组含每次尝试的镜像、HTTP 状态、错误信息、时间戳
- **不阻塞**：失败不阻塞，继续下一条
- **断点续传**：支持 `--resume` 参数跳过 `download_status=success` 条目
- **重试失败**：支持 `--retry-failed` 参数仅处理 `download_status=failed` 条目（清空 `errors` 后重试）

### 文件名格式规则

**文件名模板**：`<year>_<author_lastname_or_surname>_<title_slug>_<lang>.<ext>`

**示例**：

- 英文书籍：`2012_Kuhn_The-Structure-of-Scientific-Revolutions_en.pdf`
- 中文书籍：`2012_库恩_科学革命的结构_zh.pdf`

- 法语原版书籍：`1969_Braudel_Ecrits-sur-l-Histoire_fr.pdf`

**slug 规则**：

- 英文：lowercase，空格→`-`，去除非字母数字字符（保留 `-`），最大 60 字符（超出截断且不在词中间断开）
- 中文：保留中文字符，标点（顿号/逗号/句号/冒号/书名号）→`-`，空格→`-`，最大 40 字符
- 其他外文：保留原文字符，空格/标点→`-`，最大 60 字符

**作者姓氏规则**：

- 英文：取 lastname（如 Kuhn、Bijker、McKusick、Prown）
- 中文：取姓氏（如 库恩、麦克西奇、潘诺夫斯基）
- 多作者（≥3）：第一作者姓氏 + `et-al`
- 法/德/意等：取作者姓氏（如 Braudel、Ginzburg、Latour）
- 日本：取姓氏罗马字（如 村上 Murakami）

**年份规则**：使用所下载版本的出版年（非首版年）。如下载 2012 年 50 周年纪念版则用 2012，下载 1962 首版则用 1962。

**扩展名规则**：`.pdf`、`.epub`。OCR 输出文件同名但扩展名为 `.md`。

**重名冲突处理**：若两书生成相同文件名，附加 `_v2`、`_v3` 后缀；并在 manifest `notes` 字段记录冲突。

## changelog 去重规则

每次向 changelog 数据库（`01-项目管理/00-变更记录/changelog.duckdb`）追加新条目时均须触发去重检查，按本节判定标准与操作规范执行，禁止跳过。

### 去重检查触发时机

每次向 changelog 数据库追加新条目时均须触发去重检查。检查范围为全部条目。

具体执行要求：

- **触发条件**：任何向 changelog 数据库 INSERT 新条目的操作均须触发去重检查。
- **检查范围**：全部条目（数据库支持跨日期全文搜索，无需限制范围）。
- **不跳过**：不得以“条目显然独特”为由跳过去重检查。

### “无效内容”判定标准

判定为无效内容的条目须按下述标准识别：

- **测试性条目**：开发或调试期间记录的“测试”前缀条目、占位符条目。
- **调试性条目**：仅记录调试过程无最终结论的条目。
- **空内容条目**：仅有标题无正文的条目，或正文为“无变更”“无修改”等无信息量内容。
- **已被后续条目明确撤销的条目**：后续条目明确写明“前述 XX 条目作废”“撤销 YY 变更”等。

### “重复内容”判定标准

判定为重复内容的条目须按下述标准识别：

- **同一变更被多条目记录**：同一变更内容（如同一文件的同一类型修改）在不同日期被多次记录，仅保留信息最完整且日期最早者。
- **同一信息在多条目中重复**：变更概述、影响范围等元信息在多条目中重复，仅保留首次完整说明者。
- **被新条目完全覆盖的旧条目**：新条目已包含旧条目全部信息且更详细，删除旧条目。

### 去重操作规范（SQL 查询辅助）

使用 SQL 查询辅助去重，但最终判定仍须逐个核对：

```sql
-- 查找疑似重复条目（相同日期、摘要前 60 字符相同）
SELECT a.id, b.id, a.date, a.summary
FROM entries a JOIN entries b ON a.date = b.date AND a.id < b.id
WHERE SUBSTR(a.summary, 1, 60) = SUBSTR(b.summary, 1, 60);
```

- **合并条目**：合并时保留信息最完整者，DELETE 冗余条目，不留占位符。
- **删除无效条目**：直接 DELETE，不留占位符，不留“已删除”标记。
- **保留历史性记录**：即使变更已被撤销，若撤销本身具历史意义（如用户明确撤销某决策的记录），保留原条目与撤销条目。
- **删除复核**：允许使用脚本或工具批量删除，但删除前须生成待删清单逐一核对，删除后复核剩余条目。

### 去重后验证要求

- **时间顺序复核**：须复核 changelog 时间顺序仍正确（`SELECT date, COUNT(*) FROM entries GROUP BY date ORDER BY date`）。
- **交叉引用复核**：须复核交叉引用仍有效（其他文件对 changelog 的引用未因删除条目而失效）。
- **条目数一致性复核**：`SELECT COUNT(*) FROM entries` 确认条目数正确。

具体执行要求：

- **SHA-256 精确去重**：每个待入库文件须计算 SHA-256，与 `references` 表 `sha256` 字段比对；相同哈希的文件跳过入库，写入 `reference_duplicates` 表（`dup_type='sha256'`）

- **重复文件处理**：重复文件不删除原文件，仅在数据库标记跳过；日志记录 `status='skipped'` 与 `error` 字段说明重复类型
- **禁跳过去重**：不得以“文件显然独特”为由跳过去重检查

### 元数据验证标准

具体执行要求：

- **三级回退采集**：元数据采集须按 YAML frontmatter → 文件名模式 → PDF metadata 三级回退，前一级采集成功则不降级
- **必填字段**：`title`、`author`、`year`、`format`、`file_path`、`filename`、`sha256`、`file_size` 八字段必填；无法采集的字段填“未知”（title）/“不详”（author、year）
- **年份规整**：年份须为四位整数；非四位整数的年份字段填“不详”
- **文件完整性验证**：PDF 须以 `%PDF-` 开头，EPUB 须以 `PK` 开头，文件大小须 ≥ 50KB；验证失败的文件不入库，日志标记 `status='failed'`
- **入库前核验**：文件大小、可读性、标题一致性三项核验须全部通过；不通过的文件立即删除后继续流程（详见 `project_memory.md` 硬约束）

### 章节匹配置信度阈值

具体执行要求：

- **高置信度匹配**：关键词重合 ≥ 2 项，`match_confidence ≥ 0.7`，自动入库并写入 `chapter_matches` 表
- **中置信度匹配**：关键词重合 1 项，`0.5 ≤ match_confidence < 0.7`，自动入库但日志标记“需人工复核”
- **低置信度匹配**：关键词重合 < 1 项，`match_confidence < 0.5`，写入 `chapter_matches` 表但 `primary_chapter=0`，日志标记 `status='manual'`，须人工确认
- **匹配依据留痕**：`chapter_matches.match_reason` 字段须记录匹配命中的关键词清单

具体执行要求：

- **著录格式**：`作者. 题名[M/J/D/R/C/EB/OL]. 出版地: 出版者, 年份: 页码.`
- **著录脚注**：著录条目末尾附“自动入库于 `<date>`”脚注
- **兜底分类**：未匹配到子目录类别的文件统一著录到 `bsd学术论文与学位论文.md`

### 参考文献总目与数据库同步回填（ref_id 机制）

**说明**：`04-现代研究文献/01-参考文献总目/` 各分类 `.md` 的著录条目以 `- [ref_id] 著录文本` 格式存在，其中 `[ref_id]` 即 `references_fulltext.duckdb` 中 `references.id`（总目由 `script/_gen_catalog_30_categories.py` 从数据库导出时生成，含此前缀）。该前缀构成“总目 ↔ 数据库”按 id 精确同步的机制基础。

具体执行要求：

- **同步方向**：数据库 → 总目（`_gen_catalog_30_categories.py` 导出）；总目 → 数据库（回填增强，**单向、只补缺失字段，不覆盖数据库已有值**）。
- **回填范围**：`references` 表中缺失的 `author` / `year` / `publisher` / `isbn_doi` 四个字段，从总目著录文本解析补录。
- **触发时机**：新增文献入库、总目著录被人工增补/修订后，运行 `script/_fix_from_catalog.py` 同步回填；回填结果须复核（dry-run 预览 → 正式执行）。
- **解析规则（0 信任原则）**：
  - `author`：取著录首段作者；**排除**纯大写缩写/文档编号（如 `AA-BG`、`SMM`）、文件名串（含下划线或过长）、期刊期号（如 `JulyAug`）、月份词、工具名/数据库名（Adobe、CNKI 等）；机构作者（FreeBSD Foundation、NASA 等）可保留，无法判定时宁缺勿滥。
  - `year`：仅取独立 4 位年份（1950–2030，前后非数字，排除 8 位日期与 ISBN 串）；优先出版年/会议年/期刊年，规避书名内年份范围（如《ACM图灵奖:1966-2006》取 2008）。**禁止使用 PDF CreationDate 作出版年**（其为文件创建/扫描时间）。
  - `publisher`：`[M]. 出版地: 出版者, 年份` 格式解析。
  - `isbn_doi`：`ISBN:` / `DOI:` 正则提取（如 `10.1145/989.990`、`978-0-201-54777-1`）。
- **留痕**：每次回填须写 `reference_update_log`（`updated_by='catalog_sync'`，记录字段变更与来源）。
- **一致性维护**：总目条目若指向已删除的 `references.id`（孤儿 id），不创建回填记录，标记待人工确认是否恢复文献或清除总目条目。

### 日志核验协议

具体执行要求：

- **日志文件位置**：`script/_auto_ingest_logs/ingest_log.jsonl`，每行一条 JSON 记录
- **必填字段**：`timestamp`、`file_path`、`status`（success/skipped/manual/failed/dry-run）、`reference_id`、`chapter_matched`、`error`
- **看板文件**：`script/_auto_ingest_logs/dashboard.md`，含六项统计（待入库文件数、成功入库数、跳过重复数、失败数、需人工确认数、本次检测时间）
- **入库后核验**：入库完成后须核验日志中 `status='failed'` 与 `status='manual'` 条目，逐条排查原因
- **数据库一致性核验**：核验 `references` 表新条目数 = 日志 `status='success'` 条目数；`chapter_matches` 表新条目数 = 日志 `status='success'` 条目数
- **CSV 一致性核验**：核验 CSV 新增行数 = 日志 `status='success'` 条目数
- **0 信任叠加**：本章节的自动入库不替代既有 0 信任原则与三次复查流程；自动匹配结果须人工抽样复核（每 10 条抽 1 条核对匹配准确性）

### 自动入库与人工复核关系

具体执行要求：

- **自动入库为辅助**：自动入库管线仅为辅助工具，不替代人工判断
- **人工复核保留**：低置信度匹配（`match_confidence < 0.5`）须人工确认章节归属；高置信度匹配须人工抽样复核
- **失败条目处理**：`status='failed'` 条目须逐条排查原因，修复后重跑 `--file` 模式入库
- **数据库修订**：人工确认后须手动更新 `chapter_matches.primary_chapter`、`match_confidence`、`match_reason` 字段
- **综述修订**：人工确认章节后须手动在 `chapter_reviews.revised_review_text` 中追加引用段落，并更新 `revised_word_count`、`revised_at`、`revised_by`（`revised_by='manual'`）

除 PDF/EPUB/CAJ 外，**所有落盘文件均须入库**——含网页参考、网页快照、考据整理文档、文本/字幕、纯文本等，提取正文后写入 references_fulltext.duckdb。auto_ingest 仅覆盖 01-pdf/02-epub/04-caj，本规则覆盖其余目录。

具体执行要求：

- **入库范围**：`07-网页参考/`、`06-html-snapshots/`（网页快照）、`01-判决书案例/`（案件整理 md）、`03-ocr/`、`07-audio-archive/`（srt/txt 字幕）、`05-书籍/06-论文` 等目录下所有未入库文件，以及任何新落盘文件。

- **脚本**：`script/_full_ingest_all.py`（全量，幂等可重跑）、`script/_fill_fulltext_final.py`（补 fulltext，子进程+超时防卡死）。

## 重复与错误文档清理规则

本章节为重复与错误文档清理的规则来源。当自动入库管线识别出重复文件或错误文件时，须按本章节规则执行清理流程。本章节是对“新增文献自动检测规则”中“重复文件不删除原文件”条款的修订：对于确认为重复或错误的文档，须实际删除文件系统中的副本，仅保留主副本。

### 重复文档判定标准

具体执行要求：

- **SHA-256 精确重复**：两个文件 SHA-256 哈希完全相同，判定为精确重复
- **标题+作者+年份模糊重复**：归一化标题（去除空格、标点、大小写）+ 第一作者姓氏 + 年份三元组全同，判定为模糊重复
- **主副本优先级**：当出现重复时，保留 `references` 表中 `id` 最小（最早入库）的记录对应文件为主副本，删除其余副本
- **路径优先级**：若两条记录 `id` 相同（理论上不会出现），保留路径较短者（靠近根目录者）
- **数据库标记**：重复关系须记录在 `reference_duplicates` 表（`duplicate_type='exact'` 或 `'fuzzy'`），`primary_reference_id` 为保留的主副本 id，`duplicate_reference_id` 为被删除的副本 id

### 错误文档判定标准

具体执行要求：

- **文件损坏**：PDF 文件不以 `%PDF-` 开头，或 EPUB 文件不以 `PK` 开头，判定为文件损坏
- **无法读取**：文件无法被 PDF 阅读器（PyMuPDF、pdfplumber）打开，或打开后页数为 0，判定为无法读取
- **文件过小**：文件大小 < 50KB（论文）或 < 1MB（书籍），且非合法的短篇文献，判定为文件过小
- **内容与标题不符**：文件名标识的主题与实际内容明显不符（如文件名为 BSD 论文但内容为 Windows 手册），判定为内容不符
- **OCR 解密失败**：CAJ/KDH 文件解密后无 `%%EOF` 标记或 PDF 对象解析异常，判定为解密失败
- **数据库标记**：错误文件须在 `references` 表中标记 `status='rejected'`，并在 `reference_duplicates` 表记录 `duplicate_type='corrupted'` 或 `'invalid'`

### 清理流程

具体执行要求：

- **第一步：识别**：运行清理脚本 `python script/cleanup_duplicates_and_errors.py`，扫描 `references` 表与 `reference_duplicates` 表，识别重复文件与错误文件
- **第二步：生成清单**：生成待删除文件清单 `script/_cleanup_logs/pending_deletion.jsonl`，每行含 `file_path`、`reason`（exact_duplicate/fuzzy_duplicate/corrupted/unreadable/too_small/content_mismatch/decrypt_failed）、`primary_reference_id`（重复文件的主副本 id）、`reference_id`（被删除文件的 id）
- **第三步：人工抽样复核**：对清单进行人工抽样复核（每 10 条抽 1 条核对），确认判定准确
- **第四步：执行删除**：复核通过后执行删除，删除文件系统中的副本文件，保留主副本
- **第五步：数据库更新**：将 `references` 表中被删除文件的 `status` 更新为 `'deleted'`，`file_path` 字段保留但追加 `[DELETED YYYY-MM-DD]` 前缀
- **第六步：日志记录**：删除操作须记录到 `script/_cleanup_logs/deletion_log.jsonl`，每行含 `timestamp`、`file_path`、`reason`、`reference_id`、`primary_reference_id`、`operator`
- **第七步：看板更新**：更新 `script/_cleanup_logs/dashboard.md`，含待删除数、已删除数、保留主副本数、本次清理时间

### 删除前核验

具体执行要求：

- **主副本存在性核验**：删除副本前须核验主副本文件仍存在于文件系统中；若主副本已丢失，须保留副本中的一个作为新主副本
- **数据库引用核验**：删除前须核验该文件未被 `chapter_reviews.revised_review_text` 引用；若已被引用，须先更新综述引用指向主副本
- **CSV 映射核验**：删除前须核验 `_匹配映射表.csv` 中的引用；若存在引用，须更新 CSV 指向主副本
- **参考文献总目核验**：删除前须核验 `04-现代研究文献/01-参考文献总目/` 中的著录条目；若存在重复著录，须删除多余条目
- **0 信任叠加**：本章节的清理不替代既有 0 信任原则；删除判定须基于数据库实际记录与文件系统实际状态，严禁基于模型记忆臆造删除清单

### 删除后验证

具体执行要求：

- **文件系统核验**：核验被删除文件已从文件系统中移除（`Path.exists()` 返回 `False`）
- **数据库一致性核验**：核验 `references` 表中 `status='deleted'` 的记录数 = 删除日志条目数
- **主副本完整性核验**：核验所有保留的主副本文件仍可被 PDF 阅读器打开
- **引用一致性核验**：核验 `chapter_reviews`、`_匹配映射表.csv`、参考文献总目中无指向已删除文件的悬空引用
- **磁盘空间核验**：记录清理前后 `04-现代研究文献/03-文献下载/` 目录占用空间变化

### 清理与自动入库的关系

具体执行要求：

- **清理先于入库**：每次运行 `auto_ingest_new_pdfs.py` 前须先运行 `cleanup_duplicates_and_errors.py`，确保数据库中无重复记录
- **清理不阻塞入库**：清理失败不阻塞入库流程；清理日志中的 `status='failed'` 条目须逐条排查
- **reference_duplicates 去重**：清理脚本须使用 `INSERT OR IGNORE` 写入 `reference_duplicates` 表，避免唯一约束冲突
- **定期清理**：建议每周运行一次清理脚本，或在每次大批量新增文献后运行

## 过时内容处理规则

本小节规定项目自产 Markdown 文件中过时内容（工作日志式日期标注、已废止规则小节、整体过时文件）的统一处理方式：**直接删除，不保留“某月某日干了什么”的痕迹，删除事项记入 changelog**。规则变更的历史轨迹由 `01-项目管理/00-变更记录/changelog.duckdb` 统一承载，文件正文只呈现现行时态的规则与内容。

### 工作日志式日期标注删除

具体执行要求：

- **判定标准**：项目自产 md 文件中叙述编纂行为本身的日期元标注，含括注式（如“（YYYY-MM-DD 新增）”“（YYYY-MM-DD 用户决策）”“（YYYY-MM-DD 蒸馏）”“（YYYY-MM-DD 自动挖掘）”）与整段式（如“卷章调整记录（YYYY-MM-DD）”“执行状态（YYYY-MM-DD 更新）”“停用说明（YYYY-MM-DD）”“废止说明（YYYY-MM-DD）”引语块），一律删除。
- **删除方式**：仅括注删括注（保留被修饰的实质内容，标题中的括注删后保留标题主体）；整段属工作日志（除日期与动作叙述外无实质规则/史实内容）删整段；混合段落剥离日志句、保留实质句。
- **现行时态改写**：删除标注后句子若残留“已自某日起”“已于某日废止”等过去完成叙述，改写为现行时态陈述（如“已整体移除”→“整体移除，正文不再编纂”）或直接删除该叙述。
- **留痕去向**：每处删除（尤其涉及整段/小节/文件移除的）登记 changelog.duckdb；文件内不留任何“何时改过”痕迹。
- **修改手段**：修改须逐处人工审阅上下文后进行，禁止无差别批量正则替换；无法安全剥离的内容保留原状并在 changelog 登记豁免理由。

### 废止规则小节与过时文件处置

具体执行要求：

- **废止小节**：规则文件中已声明废止的小节不保留“废止说明”存档正文——先复核小节内是否含未被他处覆盖的有效规则（有则按“材料合并强制要求”并入相邻小节），随后备份、删除小节，并修正 `01-规则/README.md`、`CLAUDE.md` 等处对它的索引与摘要行。
- **过时文件**：自标“弃用/历史参考/旧版/不再维护”或口径整体失效的文件——先复核其中是否含现行文件未覆盖的唯一实质内容（有则合并入现行文件），随后备份、删除，修正全部指向它的引用（历史快照报告内的提及除外），登记 changelog。
- **删除前备份**：任何小节/文件删除前，先将删除对象复制至 `script/_backup_YYYYMMDD_过时清理/`（保持相对路径结构），并逐条登记于该目录 `MANIFEST.md`（源路径、备份路径、处置方式、changelog 条目号）。
- **删除后复核**：核验删除对象已不存在、引用已全部修正、未误删相邻内容；备份与清单齐备方可继续下一项。

### 豁免清单

以下内容中的日期不属于工作日志式标注，不删除、不改写：

- **史料原文**：`03-原始史料库/`、`02-sacred源材料/` 源文本中的日期，及大纲“史料”字段中引用的一手/二手史料日期（含提交时间跨度、邮件日期、抓取时间戳等数据基线）
- **历史快照报告**：`08-核查报告与多轮复核/`（含 `重构2026/`）中带日期的审计报告、复核报告、映射数据基线——沿用“重构大纲目录口径同步规则”的历史快照豁免原则，整体不改写；其文件名与正文标题中的日期属快照标识
- **文献著录**：GB/T 7714-2015 著录条目中的出版年、访问日期、更新日期
- **机器可读元数据**：frontmatter、JSON、CSV 中的 date、verified_date、updated_at、created_at 等字段值
- **考据规范标注**：`[考据完成：YYYY-MM-DD <结论简述>]` 一类由 [考据规则.md](考据规则.md) “存疑数据库位置与使用规范”释疑流程明文规定的登记格式，其日期为该格式的必备字段，不属工作日志式标注
- **自动生成数据块溯源行**：脚本生成块头部的 `**生成时间**：… ｜ **复现**：…` 之类同时给出复现脚本的溯源行，属数据基线标识
- **文件名与路径**：文件名中的日期前缀（如 `20260810_schema审计报告.md`）、备份目录名中的日期
- **历史事实日期**：BSD/UNIX/计算机史本身的日期（1977 年、1993-06-12 等）
- **归档与临时区**：`en/`、`script/`、`.trae/`、`node_modules/`、`12-数据库备份/`

## 规则引用脚本与命令独立存储规则

### 完整性复核与重复源文件清理

本子小节是“源文件不可变性”子小节的例外出口，仅适用于 SHA-256 完全相同的精确重复副记录源文件删除场景；其他场景（模糊重复、git 仓库、二进制文件）维持不可删除。须在用户授权“允许编程解决，加快执行速度和复核力度”的例外条件下执行。

#### 适用场景

- 数据库构建与库内去重完成后，需系统复核 7 个数据库 `files` 表与磁盘文件的一致性
- 库内去重标记的精确重复副记录源文件（`duplicate_type='exact'`）需删除以释放磁盘冗余
- 0 字节空文件的副记录也按精确重复流程处理（SHA-256 固定值 `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`）

#### 复核脚本用法

- **脚本**：`script/audit_folder_db_integrity.py`
- **全量复核**：`python script/audit_folder_db_integrity.py --all`
- **单库复核**：`python script/audit_folder_db_integrity.py --db <db_name>`
- **dry-run**：`--dry-run` 选项仅输出报告不修改任何文件（本脚本默认不修改文件）
- **三维度审计**：① dangling_db_records（数据库登记但磁盘不存在）；② unindexed_disk_files（磁盘存在但数据库未登记，跳过 `.db`/git 仓库/二进制）；③ sha256_mismatch（重新计算磁盘 SHA-256 与 `files.sha256` 比对）
- **报告输出**：`script/_folder_db_logs/integrity_audit_report.md`（含汇总表 + 3 个详情小节 + 建议动作小节）

#### 清理脚本用法

- **脚本**：`script/cleanup_duplicate_sources.py`
- **全量清理**：`python script/cleanup_duplicate_sources.py --all`
- **单库清理**：`python script/cleanup_duplicate_sources.py --db <db_name>`
- **dry-run**：`python script/cleanup_duplicate_sources.py --all --dry-run`（仅输出报告不删除文件、不修改数据库）
- **报告输出**：`script/_folder_db_logs/cleanup_report.md`（含汇总表 + 5 个详情小节 + empty_files 小节 + next_actions 小节）

#### 双重校验原则

- **校验 1**：副记录 `file_path` 磁盘文件存在，且重新计算 SHA-256 与 `files.sha256` 一致
- **校验 2**：主记录 `file_path` 磁盘文件存在，且重新计算 SHA-256 与主记录 `files.sha256` 一致
- **校验 3**：副记录 SHA-256 与主记录 SHA-256 完全相同
- 三项校验全部通过才允许删除副记录源文件；任一校验失败，记录到 `cleanup_report.md` 的“skipped”小节，不删除

#### 删除范围

- **精确重复副记录**：`duplicate_type='exact'` 且 `duplicate_of_id IS NOT NULL`
- **0 字节空文件**：作为精确重复的副记录一并删除，主记录 0 字节空文件保留
- **保留主记录**：不删除主记录源文件、不删除副记录父目录（即使变空）

#### 例外清单

- **sacred 源材料**：`02-sacred源材料/` 源文件已清理入库，无源文件可删除
- **git 仓库**：`03-原始史料库/01-代码仓库史料/` 与 `02-man源与posix仓库/` 跳过删除
- **二进制文件**：PDF/EPUB/CAJ/PNG/JPG 等不入库，不构成数据库重复
- **模糊重复**：`duplicate_type='fuzzy'` 仅汇总数量，不删除源文件
- **主记录**：保留以便后续决定是否补写内容
- **未登记文件**：`unindexed_disk_files` 不在删除范围，建议 `--add-file` 入库
- **SHA-256 不一致**：`sha256_mismatch` 不在删除范围，建议 `--update-file` 刷新
- **跨库副记录源文件**：跨库去重仅标记 `status='merged'`，不删除源文件

### 跨库全局去重

本子小节规定 7 个文件夹级数据库的跨库三级全局去重流程，遵循“先比对后标记，副记录可逆标记”原则。

#### Schema 升级 1.2

- **新增字段**：`files` 表新增 `duplicate_of_db` TEXT（跨库主库名）与 `duplicate_of_global_file_id` INTEGER（跨库主记录 file_id）
- **幂等升级**：`ALTER TABLE files ADD COLUMN` 捕获 `duplicate column name` 异常，可重复执行
- **registry 更新**：`folder_db_registry.csv` 中 7 行的 `schema_version` 字段升级为 `1.2`
- **SQL 文件同步**：`00-编纂规则与格式规范/01-规则/脚本与命令/folder_db_common_schema.sql` 升级至 1.2 版本
- **升级日志**：`script/_folder_db_logs/schema_upgrade_log.md`

#### 三级去重流程

- **第一级 跨库 SHA-256 精确去重**（`global_exact`）：按 SHA-256 分组，找出跨库 SHA-256 完全相同的记录组，按数据库优先级（sacred>original>research>fact>review>cross>metadata）确定主记录
- **第二级 跨库 content_hash 内容级去重**（`global_content`）：对剩余 active 记录按 `content_hash` 分组
- **第三级 跨库标题+首段模糊去重**（`fuzzy_global`）：Levenshtein 比例 ≥0.85，使用 `difflib.SequenceMatcher`，按文件扩展名分组预筛选避免 O(n²) 爆炸
- **脚本**：`script/dedup_databases_global.py`

#### 数据库格式统一规则

本子小节规定 7 个文件夹级数据库的格式统一规范，对应 Schema v1.4 与 `optimize_folder_databases.py --reindex` 模式。所有数据库修改任务须遵循“清理前复核 → 执行清理 → 清理后复核 → before/after 对比确认”的完整流程，详见下方“删除安全规范”与“清理前后复核流程”。

**适用场景**：7 个文件夹级数据库的索引命名、schema_meta 键集合、table_count 统计、扩展表合并、引用查询加速索引、模块化分层设计、冗余文件清理、删除安全流程

**1. 索引命名规范**：

- `cross_references` 表索引一律使用 `idx_cross_references_*` 前缀，禁止与 `idx_xref_*` 旧命名并存
- `cross_references` 表保留 5 个索引：`idx_cross_references_source_file_id`、`idx_cross_references_target_path`、`idx_cross_references_resolution_status`、`idx_cross_references_reference_type`、`idx_cross_references_source_block_id`
- `files` 表索引集合统一为：`idx_files_status`、`idx_files_sha256`、`idx_files_content_hash`、`idx_files_duplicate_of_id`、`idx_files_duplicate_of_db`（不含 `idx_files_duplicate_type`，与 `idx_files_duplicate_of_id` 功能重复）
- 冗余索引清理：`python script/optimize_folder_databases.py --reindex`

**2. schema_meta 键集合规范**：

- 7 个数据库的 schema_meta 表须含且仅含 9 个标准键：`active_files`、`deleted_files`、`ghost_blocks_cleaned`、`journal_mode`、`last_optimize_at`、`last_vacuum_at`、`pragma_optimized_at`、`schema_version`、`table_count`
- 历史性键（如 `restored_from_git`）须迁移至 `update_log`（operation='migrate', field_changed='schema_meta_key'），不得保留在 schema_meta
- 新增非标准键前须先在本规则登记并升级 Schema 版本

**3. table_count 统计口径**：

- 统计口径：主要业务表数量 = 总表数 − FTS5 影子表（5 张：`blocks_fts_config`、`blocks_fts_content`、`blocks_fts_data`、`blocks_fts_docsize`、`blocks_fts_idx`）

  - research_notes: 7（无专属表）
  - fact_checks: 7（fact_check_records 已按需删除）

  - cross_indexes: 11（+person_records +terminology_index +concept_history +person_bio_research；person_bio_research 为人物五维度研究库）
  - metadata_interfaces: 10（+chapter_metadata +timeline_records +build_citation_records）

**4. 扩展表合并规范**：

- 低使用率扩展表须合并以减少表数量、简化查询，合并表须含 `record_type` 字段区分来源

- 数据库文件夹内禁止残留空文件夹（保留含 `index.md` 或其他有效内容的文件夹）
- 冗余文件清理须遵循“删除安全规范”流程
- **`.git` 内部目录豁免**：Git 仓库内部目录（`.git/refs/tags`、`.git/objects/info`、`.git/refs/heads` 等）是 Git 正常结构的一部分，不视为冗余空文件夹，核验脚本与人工清理均须排除。核验脚本判定“无冗余空文件夹残留”时，须在遍历中跳过任何路径分量含 `.git` 的子目录。

**8. 删除安全规范（预览→备份→确认→执行→复核）**：

所有删除操作（冗余备份文件清理、空文件夹清理等）须执行以下 5 步安全流程，禁止跳过预览与备份直接删除：

1. **删除前预览**：生成预览报告，列出待删除文件/文件夹的完整路径、大小、SHA-256（文件）、内容清单（文件夹），保存到 `script/_folder_db_logs/deletion_preview_<timestamp>.md`
2. **预览确认**：二次核验预览报告，确认清单均为预期删除对象（git 恢复流程产生的冗余备份、非活动数据库等）
3. **删除前备份**：将待删除文件打包备份到 `script/_folder_db_logs/deletion_backup_<timestamp>/` 目录（或 `.zip` 压缩包）
4. **备份完整性验证**：验证备份文件数、总大小、SHA-256 校验通过；备份完成前不执行任何删除操作
5. **执行删除**：预览确认无误 + 备份完整性验证通过后，逐个执行删除，每个文件/文件夹删除后立即核验删除结果
6. **删除后复核**：核验待删除对象已全部删除；核验未误删其他文件/文件夹；核验活动数据库（research_notes.duckdb 等）仍可正常打开与查询；删除清单与备份清单记录到 changelog

**清理前后复核流程**：

每个数据库修改任务（索引清理、schema_meta 统一、table_count 修正、扩展表合并、引用查询索引优化）均须执行以下完整流程：

- **清理前复核**：查询并记录当前状态（before snapshot），包括索引清单、schema_meta 键集合、table_count 值、扩展表行数，保存到 `script/_folder_db_logs/`
- **执行清理**：按规范执行修改操作
- **清理后复核**：查询并记录当前状态（after snapshot）
- **before/after 对比**：对比 before/after snapshot，确认只发生预期变更；如发现非预期变更，立即停止并回滚或修复
- **总复核**：所有修改任务完成后生成 before/after 对比报告，确认所有变更均为预期变更，无非预期数据丢失或结构损坏

**Schema 版本与 SQL 一致性**：

- 当前 Schema 版本：1.4（详见 [00-编纂规则与格式规范/01-规则/脚本与命令/folder_db_common_schema.sql](脚本与命令/folder_db_common_schema.sql)）
- `folder_db_common_schema.sql` 的索引定义须与实际数据库索引一致，禁止 SQL 定义中存在 `idx_xref_*` 命名
- Schema 升级时须同步更新 `folder_db_common_schema.sql` 头部注释（版本号、变更摘要、修订日期）与 `optimize_folder_databases.py` 的 `SCHEMA_VERSION_NEW` 常量
- Schema 版本同步登记到 `folder_db_registry.csv` 的 `schema_version` 字段与各数据库的 `schema_meta.schema_version` 键
- **核验脚本检查规则**：核验脚本判定“无 `idx_xref_*` 定义”时，只匹配 `CREATE INDEX` 语句中的 `idx_xref_*`，注释行（`-- ...`）中的历史变更说明（如 `idx_xref_* → idx_cross_references_*`）不计为定义。核验脚本的字符串包含检查（`in`）须替换为正则匹配（`re.compile(r"^\s*CREATE\s+INDEX[^;]*\bidx_xref_", re.IGNORECASE | re.MULTILINE)`），避免误判注释。

## 数据库备份保留规则

本节为数据库常设备份层的强制规则（起因：kaoju_records 误删事故——详见 `03-原始史料库/06-考据记录/20260818_kaoju_records误删事故.md`）。任何写库操作须在本节备份层保护下进行。

**强制触发**：对下列范围内任一数据库执行任何写操作（INSERT/UPDATE/DELETE/ALTER/VACUUM/REPLACE/重建/导入）之前，必须先执行一次备份（写库脚本内置调用或先手动执行 `backup_databases.py`）；无当日有效备份的写库操作视为违规。

**保留策略（每库独立轮换，5 槽）**：

- **当次**：最新一份备份（无论何时产生）；
- **1 日**：备份时刻距今 ≥ 1 日中的最新一份；
- **2 日**：距今 ≥ 2 日中的最新一份；
- **3 日**：距今 ≥ 3 日中的最新一份；
- **7 日**：距今 ≥ 7 日中的最新一份；
- 不落入上述任一槽位的备份在轮换时清理（`--prune`，删除前按“删除安全规范”生成预览清单落盘）；同一文件命中多槽位只保留一份。

**备份范围（0 库）**：全部 16 个非邮件正式库（changelog、sacred_sources 等）已转为 DuckDB 主存储层，SQLite 原库以 ARCHIVE_FINAL 永久归档于各自 `12-数据库备份/<db_name>/` 子目录（prune 永不触碰）。当前工作区无 SQLite 库需常设备份。**豁免**：261 个 freebsd/netbsd 邮件拆分子库（已转 DuckDB，逐库 `.duckdb` 于 `11-邮件列表史料/01-freebsd/db/`、`02-netbsd/db/` 下）。

**备份方法与轮替压缩**：统一使用 SQLite 在线备份 API（`Connection.backup()`，自动处理 WAL 活动事务），禁止对活动库直接文件复制；备份完成后对副本执行 `PRAGMA integrity_check`（须 ok）、计算解压内容 SHA-256，随即压缩为 `.db.gz`（gzip level 6）并完整回读校验 CRC 后删除明文 `.db`——即“轮替压缩”：所有槽位备份一律压缩存储（实测 20 库 3.63 GB → 1.31 GB，压缩率约 36%）。**恢复流程**：`gunzip` 解压 → 比对清单 sha256 → `PRAGMA integrity_check` → 方可覆盖/回插。清单与日志追加至 `12-数据库备份/backup_log.jsonl`。

**执行脚本**：`00-编纂规则与格式规范/01-规则/脚本与命令/backup_databases.py`（固定脚本）——`--all` 全量备份+压缩+轮换、`--db <db_name>` 单库、`--prune-only` 仅轮换清理、`--list` 查看各库备份现状（兼容 `.db` 与 `.db.gz` 两种存量形态）。

**与其他规则的关系**：“删除安全规范”的删除前备份（deletion_backup_*）与“脚本执行安全规程”的演示备份仍按各自流程执行，本节为叠加的常设轮换层，不替代；`12-数据库备份/` 为根目录一级正式文件夹，不属 `script/` 临时区，删除本目录任何内容须用户明示。

**更新与写入流程（27 库）**：

**播客库收尾流程（触发条件：转录进程退出）**：

1. **触发判定**：确认 `script/_bsdnow_igpu_transcribe.py` 转录进程（含 `--both` 模式）已退出，`bsdnow_podcast.db` 与 `bsd_podcasts_external.db` 不再被写入（mtime 稳定）；
2. **增量同步**：以 SQLite 源为基准，将两库 `.duckdb` 重建至最新状态（逐表转换 + 行数校验，方法同 `sqlite12_to_duckdb_20260825.py`，跳过 FTS5 虚拟表及影子表）；
3. **行数校验**：逐表比对 SQLite 源与 DuckDB 行数，全部一致方可进入下一步；

**校验**：`sqlite2duckdb.py --verify` 对在档库做源-镜像行数比对，对已归档库按 `duckdb/<name>.manifest.json` 的逐表行数校验（manifest 由 `--optimize` 刷新）；`--list` 显示在档/过期/已归档状态。

## Git 克隆目录与更新规则

本节为 git 仓库克隆的存放位置、更新流程与去重约束（因增量更新时在 `script/` 下重复克隆既有仓库而确立）。

**克隆存放位置**：所有 git 仓库克隆统一存放于 `03-原始史料库/01-代码仓库史料/<项目目录>/` 下，与对应 SQLite 数据库同目录层级（如 `09-Darwin/xnu/`、`02-FreeBSD/freebsd-src/`）。克隆目录名须与 `repos` 表的 `repo_name` 字段一致，以便脚本自动定位。

**强制使用 tree:0 过滤器（仅提交信息）**：所有 git 克隆操作**必须**使用 `--filter=tree:0`（仅获取 commit 对象，不传输 tree/blob 对象）。`git log` 元数据（作者、日期、消息、父提交）完整可用，但 `--numstat`/`--name-status` 不可用——即 commit_files 表无法从此克隆填充，只有 commits 表可更新。此规则适用于全部仓库，无论大小，永不例外。理由：① 全量克隆（如 linux-kernel ~8.2GB）在代理环境下持续 TLS 截断；② 提交信息是史料考据的核心需求，文件变更细节可从数据库已有存量 + 未来专项补抽获取；③ 磁盘占用与传输耗时最小化。

**已有克隆清单**：截至 2026-08-25，全部 66 仓库已通过 tree:0 方式克隆至对应项目目录下。Darwin 项目下 42 个 apple-oss-distributions 仓库为既有工作克隆（含 `.git` 子目录），其余 24 仓库为 bare tree:0 克隆（`<repo>.git` 目录）。

**禁止重复克隆**：`script/` 目录禁止存放任何 git 克隆（属临时文件区，非长期留存位置）；任何 git 克隆操作优先检查 `03-原始史料库/01-代码仓库史料/` 下是否已有同名克隆，已存在则直接复用，不得在 `script/` 或其他目录重复克隆。

**增量更新完整 8 步流程**（执行脚本 `script/git_update_duckdb_20260818.py`，写入目标为 DuckDB 主库 `duckdb/<db_name>.duckdb`）：

1. **克隆（tree:0）**：`git clone --bare --single-branch --filter=tree:0 <url> <目标目录>`——仅传输 commit 对象（约全量 5%），磁盘占用极小（linux-kernel 2.5GB→~200MB，netbsd-src 74MB）。如已有克隆则跳过此步直接复用。**Darwin 例外**：42 个既有工作克隆不含 tree:0 过滤，直接 `git fetch --tags` 拉取增量。

2. **门禁（哈希可达性）**：`git cat-file -e <库内最新已知 commit_hash>^{commit}`——验证库内最新哈希在新克隆中。通过 → 进入步骤 3；失败 → 进入锚点降级。

3. **锚点降级**（门禁失败时）：从 DuckDB 查询 `SELECT commit_hash, committer_date FROM commits WHERE repo_name=? ORDER BY committer_date DESC LIMIT 300`，逐条 `git cat-file -e` 探测，找到第一个可达哈希作为增量边界。典型场景：上游镜像分支重写导致最新哈希不在克隆中（如 hardenedbsd-src 降级至 2026-04-20）。若 300 条均不可达且仓库不在白名单（`REINGEST_ALLOW`），则报错退出。

4. **全量重灌**（白名单仓库锚点全不可达时）：情况 A——克隆 ≤2000 提交且 ≥ 存量一半（Apple 小库重写/清理引用，如 darwin 42 仓库）；情况 B——白名单仓库（上游镜像整体重建，如 trueos-src、netbsd-src）。执行 `DELETE FROM commits WHERE repo_name=?` 清空该 repo 存量后，按 `--all` 全量重灌。

5. **增量候选计算**：`git rev-list --all --since=<boundary-7天>` 获取候选哈希集合，减去 DuckDB 已有哈希（`SELECT commit_hash FROM commits WHERE repo_name=?`）得到真正新增。

6. **解析提交元数据**：`git -c core.quotepath=false log --all --since=<boundary> --date=iso-strict --pretty=format:<分隔符模板>` 一次遍历提取 12 字段：commit_hash、author_name/email/date、committer_name/email/date、message_subject、message_body、parent_hashes、signed_off_by（多签以 `,` 加空格连接）。分隔符：`\x01` 切 block，`\x02` 切字段。

7. **去重写入 DuckDB**：`rows = [r for r in rows if r[0] not in existing]`（用步骤 5 的已有哈希集合过滤），`BEGIN TRANSACTION` → `INSERT INTO commits (...) VALUES (...)` → `COMMIT`。由于 DuckDB 1.5.5 不支持 `ALTER TABLE ADD UNIQUE` 和 `INSERT OR IGNORE`，去重走应用层反连接。最后 `UPDATE repos SET commit_count=?, latest_commit_date=? WHERE repo_name=?`。

8. **优化**：该库全部仓库更新完成后，执行 `sqlite2duckdb.py --optimize --db <name>`（刷新 ART 索引 + CHECKPOINT + ANALYZE + manifest），确保后续查询走索引加速。

**状态与断点续跑**：`script/_git_update_duckdb_state.jsonl` 记录每条 (db, repo) 的执行状态（ok/uptodate/error/skip），脚本重启时自动跳过已完成项，仅重试 error 项。

**镜像重建白名单**（`REINGEST_ALLOW`，需人工研判后添加）：`trueos-src`（上游镜像整体重建，0/100 抽样不可达）、`netbsd-src`（GitHub 镜像 2025 年重建，316k vs 774k 提交）、`openssh-apple/openssh`（Apple 清理历史引用，13,860 vs 35 提交）。

**数据库更新后清理**：增量更新直接写入 DuckDB，不经过 SQLite 中转。`--optimize` 已包含 manifest 刷新与索引重建，无需额外步骤。

## 重构大纲目录四层解耦与装配规则（2026-09-18 立）

**核心原则**：`08-核查报告与多轮复核/重构2026/index.html` 是**装配产物**，其一切修改必须经由装配器 `assemble_index.py`；直接手改产物会在下次装配时被覆盖。

**四层源 → 单文件交付物**：

| 层 | 源文件 | 说明 |
| -- | ------ | ---- |
| 内容层 | `重构2026/data/outline.txt` | **纯文本行式**，零 HTML 标记；卷／章／节题与溯源注的唯一编辑入口 |
| 格式层 | `重构2026/assets/doc.css` | 原 `<style id="format-layer">` 正文 |
| 现代化层 | `重构2026/assets/modern.css` | 原 `<style id="modern-layer">` 正文 |
| 行为层 | `重构2026/assets/theme-preset.js`、`assets/doc.js` | 主题预设（head 内早执行）＋ 目录引擎 |
| 数据层 | `重构2026/data/catalog.json`、`data/schema.jsonld` | 运行时数据（persons/refs/revs）＋ 结构化元数据 |
| 页壳 | `重构2026/assets/page.template.html` | head／页框／main 骨架／tail ＋ 占位符 |

**内容源语法**（`data/outline.txt`）：

- `# 卷题` → `<h2>`（「第N卷」与题名间 **2 个半角空格**）
- `> 卷导言` → `<p class="vol-overview">`（可选）；`! 卷分工注` → `<p class="vol-note">`（可选）
- `## 章题` → `<h3 class="chapter">`（含「第 M 章 」前缀）
- `- 节号 节题` → `<li>`（节号与题文间 **1 个半角空格**）
- `- 节号 @@溯源注@@ 节题` → 溯源注**前置**（紧跟节号）；`- 节号 节题@@溯源注` → 溯源注**后置**（行尾）
- 内容源存**解码文本**（如 `AT&T`），HTML 转义由装配器负责（`&`→`&amp;`）

**标准形（canonical）**：一元素一行、LF、UTF-8 无 BOM；卷题后空一行；`<h3>` 与 `<ul class="sections">` 紧邻；节 `<li>` 之间无空行；`</ul>` 紧邻下一 `<h3>` 或 `</section>`；卷块之间空一行。

**口径派生**：doc-metrics／og:description／meta description／footer／JSON-LD 五处口径数字**一律由内容源派生**（`{{N_VOL}}`／`{{N_CH}}`／`{{N_SEC}}`／`{{N_CH_MAIN}}`／`{{N_CH_BIBLIO}}`／`{{TRIPLE}}` 占位符），不手工维护——口径与内容结构性同源，不可能漂移。

**装配与门禁**：

- `python assemble_index.py` —— 装配（幂等：同一组源两次装配产物位相同）
- `python assemble_index.py --check` —— 漂移检测（**第八件门禁**；不一致即退出码 1）
- 修改任一源后须跑：装配 → 九件门禁 → 三套浏览器回归
- `embed.py` 保留为**数据层序列化模块 ＋ 门禁**（`--check` 三项），装配器复用其 `encode_blob`／`integrity_of`／`serialize_content`

**禁止事项**：①不得直接手改 `index.html`（产物）；②不得在内容源中写入 HTML 标记；③不得在模板或内容源中硬编码口径数字（须用占位符）。

## 重构大纲目录页面资产层完整性门禁（2026-09-18 立）

**核心原则**：既有八件门禁皆以「产物 `index.html`」或「大纲 `.md`」为审计对象，**页面级附加件本身无护栏**。本门禁（第九件）以 `重构2026/` 树内**非装配产物**的页面资产为对象，覆盖四类此前无自动化判据的不变量。
