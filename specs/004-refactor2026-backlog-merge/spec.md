## 缘起与范围界定

主理人令：**在“重构2026/index.html”语境下，找出有关**建议书**与**待执行**的**最近的 spec**，并把**待办任务合并**为单一可执行清单。**

本 spec 在 0 信任实读后界定如下（详见 `research.md`）：

- **“最近的 spec”＝ `.trae/specs/converge-all-remaining-tasks/`（2026-10-09，《全量剩余任务合并总账（毕其功于一役）》）**。它是 2026-10-09 由主理人令“合并既有所有待办任务为新的任务书与 spec”产生的**唯一任务书**，其 Task 0（总账核定）与 Task 1（阶段 C 内容层收编 C-1～C-12）已闭环，**Task 2–7 未勾**。
- **次级来源＝ `.trae/specs/finalize-refactor2026/`**（重构2026 收官总案 spec），其剩余 Task 5／6／8／10 已依主理人令并入上者（本 spec 不重复开工，只作交叉核验源）。
- **建议书族＝ `08-核查报告与多轮复核/重构2026/` 之 00–125 号文**（120 余份）；其中最新两份为 **124 收官阶段建议书**与 **125 收官总案**，两者之未闭环项已被上述总账 spec 吸收。
- **唯一对账入口＝ `92-目录内容调整建议书-综合释疑库与未实施建议.md` §十一 施工进度对账表**；**总账文书＝ `review_logs/毕其功于一役-总任务账-20261009.md`**。
- **内容层唯一源＝ `重构2026/data/outline.txt`**；`重构2026/index.html` 是**装配产物**，唯一写者为 `assemble_index.py`——一切改动只改内容源，**禁手改产物**。

**本 spec 的定位**：把上述分散于“总账 spec＋号文族＋`review_logs/`＋长线登记表”的**待执行待办任务**，合并为一份**去重、定档、定序、可逐条验收**的清单（spec ↔ tasks ↔ checklist 三者可互相追溯）。依项目宪法 §VII，**spec 为需求／口径层**；`.trae/specs/converge-all-remaining-tasks/tasks.md` 仍是施工台账的**唯一真身**，本 spec 与之**逐条映射、不另立并行台账**（防双重台账）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 定位“最近的 spec”与建议书待执行面（0 信任核定）(Priority: P1)

编纂者以 **0 信任实读**为唯一方法，在“重构2026/index.html”语境下**定位**有关建议书与待执行的**最近的 spec**，并**逐源盘点**其未闭环项：①最近的 spec（`converge-all-remaining-tasks`）之 Task 2–7；②次级 spec（`finalize-refactor2026`）之剩余；③建议书族（124／125 等）之未闭环项；④`review_logs/` 总账与备核清单；⑤长线任务总登记表 17 线。判“未闭环”**以现跑内容源与各载体实测为据，不采信文书自述**。

**Why this priority**: 定位与核定是合并的前提；若“最近的 spec”认错（例如误取 `specs/003` 或旧号文），后续合并整体错位。主理人令的“找出”即指此步。

**Independent Test**: 交付一份“来源清单＋定位证据”：每个被认定为“最近的 spec”的目录给出绝对路径与判定理由（mtime／内容／`change-id`）；每个待办项给出其**现文实测证据**（文件路径＋行号／库名＋主键）。

**Acceptance Scenarios**:

1. **Given** 仓库同时存在 `specs/`（001–003）与 `.trae/specs/`（180+ 件）两套 spec 落点，**When** 定位“最近的 spec”，**Then** 产出唯一认定＝`.trae/specs/converge-all-remaining-tasks/`，并给出判据（2026-10-09 创建、`change-id`、主理人令原文、Task 0/1 已勾／Task 2–7 未勾），且**排除** `specs/003-login-claim-outline`（主题＝login 库判定入 claim，与本令无关）。
2. **Given** 任一被列为“待执行”的待办项，**When** 复核其证据，**Then** 该项具备**可定位的现文实测证据**（如 `重构2026/data/outline.txt` 行号、`review_logs/<件名>`、库名＋主键），不得仅以某文书自述为据。
3. **Given** 一份被并入的次级 spec（如 `finalize-refactor2026`），**When** 核对合并关系，**Then** 明确其剩余项的**唯一去向**（并入本总账 / 销号 / 另案维持），无静默丢失。

### User Story 2 - 合并为单一可执行任务清单（去重·定档·定序）(Priority: P2)

把 US1 核定的全部待执行项，**合并**为单一可执行清单：同一事项只列一次（取范围最大者）、标注来源、定档（卷级／章级／节级／注级／零节变／非内容层）、定序与前置、并逐项给出**可判定验收**。合并结果落于本 feature 的 `tasks.md`，并与 `.trae/specs/converge-all-remaining-tasks/tasks.md` **逐条映射**。

**Why this priority**: 主理人令的“合并执行待办任务”直接落在此步；合并质量决定“毕其功于一役”是否可能。

**Independent Test**: 任取一条原分散待办项，能在合并清单中定位到**唯一一行**，且该行含：来源、档位、序位、前置、验收判据；反向任取合并清单一行，能回溯到来源。

**Acceptance Scenarios**:

1. **Given** 同一事项同时出现在两份来源（如“★22 残留终校”既在 `finalize-refactor2026` Task 8 又在总账 Task 6），**When** 合并，**Then** 清单中**只出现一次**，并注明“另源已并入”。
2. **Given** 合并清单的任一条目，**When** 检查其验收措辞，**Then** 为**二值可判定事实**（含具体条件／数量／顺序／路径），**无**“功能正常”“质量良好”类不可判定措辞。
3. **Given** 合并清单，**When** 与 `.trae/specs/converge-all-remaining-tasks/tasks.md` 对账，**Then** 本 spec 之 tasks 条目与该总账 Task/SubTask **一一映射、无新增施工面、无口径冲突**。
4. **Given** 另案项（磁盘层／载体层／史料库层），**When** 合并，**Then** 明确标注“本 spec 是否施工／归属哪条线／前置为何”，不静默丢失、不擅自扩张施工面。

---

### User Story 3 - 按序分批执行待办任务（铁律收束）(Priority: P3)

按合并清单的序位**分批执行**：每批**只改内容源**，随后走收束铁律——改 `data/outline.txt` → 装配（`assemble_index.py`）→ 字体子集重建（视新字，`font_subset_rebuild.py`）→ **再装配** → 门禁全量 → 三套浏览器回归 → 落账（`changelog.duckdb`／92 号文 §十一／98 号文 §十一）→ 页面版本递增 → 提交。执行全程持守：0 信任、两说并陈、未获一手登记不静默、UTF-8 无 BOM／LF、禁直角引号与“谱系”词、同一内容源不可并行编辑。

**Why this priority**: 这是“执行”的实际落地；但须在 US1／US2 完成后进行，且逐批受主理人批准与既有批次纪律约束。

**Independent Test**: 任取一批：其内容源改动有 prebak 备份、装配链可复现、门禁与三套回归 FAILED=0、changelog 与 92 号文 §十一 有对应落账行、页面版本已递增。

**Acceptance Scenarios**:

1. **Given** 任一施工批，**When** 收束完成，**Then** 门禁全量与三套浏览器回归 **FAILED=0**，且 `changelog.duckdb` 与 92 号文 §十一 均有本批落账行，页面版本号递增。
2. **Given** 内容源改动，**When** 核查改动载体，**Then** 改动只落在 `重构2026/data/outline.txt`（及其派生的三表／夹具／字体子集），`index.html` 由装配器重新生成，**无手改产物**。
3. **Given** 某断言未获一手来源，**When** 施工至该处，**Then** **不落卷／不采纳**，并在 `review_logs/` 或库内登记留痕，保持可追溯。
4. **Given** 结构冻结前置未满足，**When** 有人试图改卷级结构，**Then** 施工停止——冻结须待内容层收编与终校完成（承总账 Task 7 前置）。

---

### User Story 4 - 双重台账防线与收官勾销 (Priority: P3)

全程守住“**唯一任务书**”边界：本 spec 为需求／口径层，施工台账唯一真身为 `.trae/specs/converge-all-remaining-tasks/tasks.md`；被并入的各 spec（`finalize-refactor2026`／`execute-login-title-fix-and-figures-ocr`／`write-doubt-marker-taskbook-2026-09-30`／`mail2d-*`／`podcast-*`／`digest-linux-mining-legacy-phase3` 等）在对应组完成后**统一勾销或标注并入**，**MUST NOT 双重台账并行施工**。收官时落冻结声明（卷骨架完成，禁再动结构）。

**Why this priority**: 项目已有“防双写”“不双重台账”铁律与多次被裹挟事故；不做此防线则合并本身即制造新风险。

**Independent Test**: 任取一份被并入 spec：其 tasks 未勾项已在总账中有一条唯一对应行，且自身状态已标注“并入”；全库无“同一事项在两份台账同时处于在途”的情形。

**Acceptance Scenarios**:

1. **Given** 本 spec 与被并入 spec 并存，**When** 抽查任一项，**Then** 该事项**仅在一处**处于“在途”，另一处为“并入／勾销”标注。
2. **Given** 收官完成，**When** 核查冻结声明，**Then** 声明已落盘且长线任务总登记表机读块已刷新。
3. **Given** 本 spec 自身，**When** 收束，**Then** 落账覆盖 `changelog`＋92 号文 §十一＋98 号文 §十一＋`review_logs/` 收官记录。

---

### Edge Cases

- **两套 spec 落点并存**（`specs/` 与 `.trae/specs/`）：须显式声明本 spec 属 `specs/`（spec-kit 原生），并说明与 `.trae/specs/` 的关系；不得因落点不同而重复开工同一施工面。
- **口径数字漂移**：文书中的卷／章／节／注数与现跑不一致时，**一律以现跑权威源为准**（`index.html` doc-metrics ＋ `sync_refactor2026_baseline.py --check`），文书数字只作历史时点记录，**不得据以施工**。
- **另案项被误升格**：磁盘层／载体层／史料库层中，主理人**未批准**者（如“磁盘 156 章疑似未迁移”原为搁置）不得擅自开工；如本令视为立项，须**显式标注并请批注**。
- **源缺失线**：H3／aline／bline／tri／podcast 等长线登记“权威源不存在”者，**不可执行**，保持登记，源重建后恢复。
- **历史弧 spec 批量销号争议**：约 87 件 2026-07～08 旧结构世界 spec 已按组销号；如主理人指认某件未被吸收，**批注恢复**为本 spec 新子项（不静默）。
- **门禁自身衰减**：新增／修改判据时须确认负向自检“拦下原因正是本组判据”，并跑第十二件负向夹具；判据有效性须被自证。
- **上下文预算与并发**：同改 `outline.txt` 的子项**须串行**；不同载体的线（如磁盘层／史料库层）可并行，但不得并行编辑同一内容源。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 以 0 信任实读**定位**“重构2026/index.html 语境下有关建议书与待执行的**最近的 spec**”，并给出唯一认定与判定证据（路径／mtime／`change-id`／已勾与未勾状态）；MUST 显式排除主题不相关者（如 `specs/003-login-claim-outline`）。
- **FR-002**: 系统 MUST **逐源盘点**待执行面并留痕：①最近的 spec 之未勾 Task；②次级 spec（`finalize-refactor2026`）剩余；③建议书族（124／125 及 00–125 号文）未闭环项；④`review_logs/` 总账与备核清单；⑤长线任务总登记表 17 线。每源给出绝对路径。
- **FR-003**: 判“未闭环”MUST 以**现跑实测**为据（`重构2026/data/outline.txt` 行号／各载体实测／库名＋主键），**MUST NOT** 采信文书自述或子代理回报。
- **FR-004**: 系统 MUST 将全部待执行项**合并为单一可执行清单**：同一事项只列一次（取范围最大者）、标注来源、定档、定序、前置与可判定验收；合并结果 MUST 与 `.trae/specs/converge-all-remaining-tasks/tasks.md` **逐条一一映射**。
- **FR-005**: 合并清单的每条验收措辞 MUST 为**二值可判定事实**（含具体条件／数量／顺序／路径）；MUST NOT 使用“功能正常”“质量良好”“性能可接受”等不可判定措辞。
- **FR-006**: 系统 MUST 保证**双向可追溯**：spec 需求 ↔ tasks 条目 ↔ checklist 项三者编号可互相定位；无“任务完整但需求未覆盖”的验收缺口。
- **FR-007**: 执行 MUST 恪守**收束铁律**：改内容源 → 装配（`assemble_index.py`）→ 字体子集（视新字）→ 再装配 → 门禁全量 → 三套浏览器回归 → 落账（changelog／92 §十一／98 §十一）→ 版本递增 → 提交；每批 prebak 备份先行。
- **FR-008**: 一切改动 MUST 只落**内容源与派生件**；`重构2026/index.html` MUST 由装配器生成，**禁手改产物**；口径数字 MUST 以 `index.html` doc-metrics 为唯一权威，由装配器派生，**不手工维护**。
- **FR-009**: 执行 MUST 遵守**批次纪律**：同一内容源不可并行编辑（同改 `outline.txt` 者串行）；涉及校验载体失败时先恢复再继续；不 commit 他人改动、不 rebase、不 `--force`；提交须路径限定。
- **FR-010**: 全程 MUST 持守**文本纪律**：UTF-8 无 BOM／LF；禁直角引号（U+300C／U+300D）与制表符；全库禁用“谱系”词（标题与注文一并清理，判据已固化）。
- **FR-011**: 凡断言**未获一手来源**者 MUST **不落卷／不采纳**，并在 `review_logs/` 或库内登记；涉在世人物者须主代理亲撰、两说并陈。
- **FR-012**: 系统 MUST 守住**唯一任务书**边界：本 spec 为需求／口径层，施工台账唯一真身为 `.trae/specs/converge-all-remaining-tasks/tasks.md`；被并入 spec 于对应组完成后统一勾销／标注并入，**MUST NOT 双重台账并行施工**。
- **FR-013**: 结构冻结 MUST 待内容层收编与终校完成后执行；**冻结后禁再动结构**；收官 MUST 落冻结声明并刷新长线任务总登记表机读块。
- **FR-014**: 另案项 MUST 明确标注“本 spec 是否施工／归属哪条线／前置为何”；主理人未批准者不得擅自开工；源缺失线保持登记、不可执行。

## Success Criteria *(mandatory)*

### Measurable Outcomes
