## 二、分析派生库的滞后性

`mapping.duckdb` 是 `mapping.tsv` 的只读派生快照，`schema_meta` 自述“本库未被单独写入”。实测其状态分布仍为落盘前形态（无 `CONFIRMED`），落后于现行 TSV。**凡判真值读 TSV；库只作分析，引用须注明快照时间。** 同类派生库还有 `chapter_keywords.json`／`theme_index.json`（由 `build_theme_index.py` 再生），以及各主题索引库。

## 三、存储版本与运行时

- 运行时锁定 `duckdb==2.0.0`、Python 3.14.2，唯一声明源是 `脚本与命令/duckdb-version-baseline.txt`；三脚本启动比对不吃版本即退出码 2。
- 存储版本只能用 `SELECT tags FROM duckdb_databases()` 的 `storage_version` 键读取；**禁读文件头偏移 12**（2.0.0 起该字段固定为弃用哨兵 999）。
- 25 个正式库已迁至 v2.0.0 存储格式；`changelog.duckdb` 暂缓。1.5.5 无法读已迁库，回退只能靠备份归档重灌（`ADR-0017`）。

## 四、写库门禁

任何批量写库（受控修库、register、批量导入）前：

1. `claimdb_guard.py --db <库名>` 必须 PASS，FAIL 即停；
2. register 另走 `register_waterlock.py probe → acquire → register → release`；
3. 写前写后各落一次 `rotate_guard_state.py` 一槽；
4. 重大施工前向 `12-数据库备份/<db>/` 追加专项正式备份，并落同名 `.json` 清单。

写前不落任何工作区副本（`ADR-0016`）。

## 五、备份与恢复

- **常规备份自动化**：三计划任务（`librebsd-dball-backup-30min`、`-hc-backup-30min`、`-outline-backup-30min`）以 `pythonw` 后台运行，频次每 5 小时；日志 `12-数据库备份/backup_log.jsonl`。**项目禁止新建自动化**——这三个任务是既有例外，不得新增同类。
- **归档形态**：`EXPORT DATABASE (FORMAT PARQUET)` → tar → gzip，档内含 34 个 parquet ＋ `schema.sql` ＋ `load.sql`。
- **恢复入口**：以 `IMPORT DATABASE '<解包目录>'` 重灌。**档内 `load.sql` 含导出机绝对路径**，单独执行必然失败，不得以它作恢复入口（`ADR-0017` 实测）。单文件拷贝恢复同样无效。
- **完整性**：`verify_archive()` 三段校验；判据不是“前 6 字节等于 DUCK 魔数”。
- **保留策略**：功能/史料库 24 小时密槽（30 分钟粒度）＋1/2/3/4/7/15 日槽；代码仓库 12 库为轻槽（无密槽，≤7 份）；播客、邮件列表、新闻组库不备份；`references_fulltext` 保留。
- **删除**：`12-数据库备份/` 任何内容删除须用户明示（红线 9）。

## 六、易错点

| 现象 | 原因 | 处置 |
| ---- | ---- | ---- |
| 库读不了、报版本错误 | 已迁 v2.0.0，运行时仍是 1.5.5 | 校验 `duckdb-version-baseline.txt` 与 `duckdb.__version__` |
| 状态分布与 TSV 不一致 | `mapping.duckdb` 是旧快照 | 以 TSV 为准；需要时重灌派生库 |
| 恢复后表缺失 | 用了单文件拷贝或直接跑 `load.sql` | 用 `IMPORT DATABASE` |
| 备份连续缺失 | 计划任务失败且无人看 | 查 `backup_log.jsonl`，连续两次缺失即阻断后续写库 |
| 写库被拒 | `claimdb_guard.py` FAIL 或水位锁未获取 | 先修库健康，再按序获取锁 |
