## 3. 判定口径

静态规则把“写文件”“f-string SQL”“argv 入参”一律记为高危，若不回到输入来源就会把全部本机工具判成漏洞。本批对每条命中问三件事，据此落五档判定。

1. **输入来源**：路径／SQL 片段／URL 是否来自网络、第三方语料或不可信文件？还是常量、库内目录、自测夹具、操作者参数？
2. **权限边界**：脚本是本机单用户手工运行，还是对外服务、CI 发布面、供他人执行？
3. **是否发布**：文件在 `git ls-files` 内（随仓库分发），还是 `script/`、`03-原始史料库/`、冻结归档等不入库区？

五档：`FIXED`（已改代码并有验证）、`FP`（误报，附具体误判机理）、`ACCEPTED`（真实模式但无权限边界或按设计如此，附理由）、`LOCAL-UNTRACKED`（本机未入库脚本，不发布；升级为固定脚本前须重新判定）、`OUT-OF-SCOPE`（第三方快照／冻结归档，按规则不得修改）。

## 5. 已修复（5 条）

### 5.1 `verify_tuhs_wiki.py:270`（ssrf）

问题：`NetClient.fetch()` 直接 `urlopen` 外部页面给出的 URL。V4／V6／V11 的抓取目标来自 Wiki 正文与外链，属不可信输入；本项目“抓取不受 robots 限制”的既定口径不构成访问本机、内网、链路本地或云元数据地址的授权。

改法：新增 `ssrf_rejection(url)`，只放行 `http`／`https`；拒绝 URL 内嵌凭据；`getaddrinfo` 解析后逐地址要求 `is_global`（回环、私网、链路本地、保留、组播、未指定地址一律拒绝）；畸形端口按拒绝处理。`fetch()` 在重试前先过防线，拒绝时返回 `ssrf_blocked:<原因>` 并计入失败。解析与请求之间的 DNS 重绑定残差以函数注释披露（本机非对抗环境接受）。

验证：`--selftest` 新增 4 例字面量断言（`file://`、`127.0.0.1`、`169.254.169.254`、URL 内嵌凭据），全套 15 项 0 失败。

### 5.2 `verify_tuhs_wiki_sql.py:219`（ssrf）

问题：`IndexClient.get_text()` 抓取 `?do=index` 索引页，目标同样来自外部内容。

改法：按该文件“不 import 主验证器、不复用其任何判据代码”的独立性要求，独立实现同名 `ssrf_rejection()`（同判据，不复用实现），在 `get_text()` 入口拦截并抛 `RuntimeError`，与既有请求失败路径一致。

验证：`--selftest` 新增同 4 例，全套 19 项 0 失败。

### 5.3 `analyze_all_databases.py:120`（sql-injection）

问题：`information_schema.columns WHERE table_name='{tbl}'` 把库名以字符串字面量拼进 SQL，库名含单引号时查询结构被改写。

改法：值改用参数绑定 `execute(sql, [tbl])`；同函数内 `"{tbl}"` 标识符插值保留并另行判定（见 7.1）。

验证：`py_compile` 通过；`?` 绑定在 DuckDB 2.0.0 实测可用（`information_schema.columns` 与 `pragma_table_info(?)` 双测）。

### 5.4 `mail_dedup_verify.py:15`（sql-injection）

问题：`PRAGMA table_info({t})` 未加引号，表名直接进入 PRAGMA 参数位。

改法：改用表值函数 `SELECT * FROM pragma_table_info(?)` 绑定表名（SQLite 3.16+／DuckDB 同形）。

验证：SQLite 与 DuckDB 双引擎实测返回同形状行列；`py_compile` 通过。

### 5.5 `dedup_databases_global.py:96`（sql-injection）

问题与改法同 5.4（`column_exists()`）；该文件只用 `sqlite3`，表值函数通道成立。

验证：同上。

### 5.7 PR 复核追补（Sourcery #1，2026-11-28 同日）

PR #1 的 Sourcery 复核提了 9 条，其中 5 条指向同一处残余：§5.1／§5.2 的防线只在请求前校验一次。本批把两个验证器的网络层改为逐跳在线校验，两文件各自独立实现同一判据集（SQL 复核器仍不 import 主验证器）：

- **重定向**：关闭 urllib 自动重定向（`redirect_request` 返回 None），3xx 交回 `http_get_checked()`，目标 URL 重新过字面量校验与解析校验；跳数上限 5，超限报 `too_many_redirects`。
- **代理**：显式装配 `ProxyHandler({})`，`HTTP_PROXY` 等环境变量不参与，代理无法把已校验的公网主机改投内网。
- **DNS 重绑定**：解析出的全局地址用于钉定连接（只替换 `_create_connection`，标准库 `connect()` 的 `sys.audit` 与 TCP_NODELAY 原样保留），URL 主机名只用于 Host 头与 TLS SNI，解析与连接之间不再有第二次解析。
- **DNS 超时与重试**：`getaddrinfo` 放进守护线程按 `DNS_TIMEOUT`（10 秒）等待，且解析移入重试环内——临时 `gaierror` 按原重试次数重来，慢解析不越过超时预算。
- **畸形 URL**：`urlsplit` 的 `ValueError`（如未配对的 IPv6 方括号）转成 `malformed_url:<原因>`，按一次抓取失败记录，不再中断整项判据。

另两条非安全问题：`analyze_all_databases.py` 的列查询补 `table_schema='main'` 与 `table_catalog = current_database()`（非 main schema 的同名表不再串列）；`deliverables/index.md` 的任务书版本、manifest 哈希、引号样式与复跑入口同步。

验证：两文件 `--selftest` 各新增 3 例（IPv6 回环、畸形方括号、非法端口），主验证器 18 项／SQL 复核器 22 项，失败 0；本地服务器 harness 24 项全过（钉定与 Host 保留、重定向到非全局地址被拒、跳数上限、环境代理被忽略、DNS 超时与重试恢复）；活网抽查 `https://wiki.tuhs.org/` 经钉定 TLS 取回 13 948 字节。

## 9. 覆盖缺口与残余风险

1. **`completeness=partial`**：扫描器自报 threatModel 与 findingDiscovery 两阶段部分覆盖，validation 阶段 `investigated=0`——全部命中均为静态模式匹配，未经动态复现。本报告的 FIXED 判定以代码审读与 selftest 为准，其余判定是“静态证据下的处置”，不等于“已证明不存在漏洞”。
2. **DNS 重绑定**：已在 §5.7 的复核追补中关闭——解析一次、钉定连接，重定向逐跳校验。新残余是环境代理一律禁用（依赖代理出网的环境会如实失败），以及解析超时靠守护线程等待（线程无法强杀，极端情况下遗留一个不阻塞退出的解析线程）。
3. **忽略区不修**：1 768 条 LOCAL-UNTRACKED 与 220 条 OUT-OF-SCOPE 保持原样。理由不是“看不见”，而是这些文件不随仓库分发、或按项目规则禁止修改；台账保留了逐条位置，升格或解冻时可直接复查。
4. **语料层不在静态代码面**：65 550 件 `.md` 与 `*.duckdb` 不由本扫描覆盖；语料与库的门禁由项目既有 48 件体系承担，本报告不重复声明其结论。
5. **单次快照**：扫描针对 2026-11-28 工作树。工作树在扫描后仍有他线在途改动（`_longline_status.py`、两本台账、`build_tool_registry.py` 等），本报告不代他线判定。
