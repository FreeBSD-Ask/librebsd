## 三、需要如实披露的两点

1. **迁移不一定缩小体积**。多数库缩小（`doubts_standalone` −91.2%、`openzfs` −64.1%、`historical_claims` −34.1%），
   但 `linux-kernel` **+22.8%**（2,038 → 2,504 MB）、`dragonfly` +6.8%、`metadata_interfaces` +10.0%。
   故“迁移可省空间”不能作为通用理由；总账为 −13.30%，主要由少数库贡献。
2. **等价判据不含物理布局**。核对口径为逻辑等价（表／列／约束／索引／行数／抽样行内容哈希／`schema_meta`），
   不比较页级布局与压缩编码——这正是体积变化的原因，不是数据差异。

## 六、存储版本号的更正（2026-10-24 复核）

本台账初版以“文件头字节 12–15 的 uint32”判定存储版本，记 2.0.0 新库为 **999**。经查 DuckDB 2.0.0 源码
`src/include/duckdb/storage/storage_info.hpp`：`MainHeader.version_number` **已弃用**，固定写
`StorageVersion::DEPRECATED = 999`；真实版本存于 `DatabaseHeader.storage_compatibility`，
枚举表为 `V1_0_0…V1_1_x = 64`、`V1_2_0 = 65`、`V1_3_0 = 66`、`V1_4_0 = 67`、`V1_5_x = 68`、`V2_0_0 = 69`。

改以官方接口 `SELECT tags FROM duckdb_databases()` 复核（`+` 表示该版本及以后可读）：

| 库 | `tags.storage_version` |
| -- | ---------------------- |
| 本轮迁移的 25 库 | `v2.0.0+` |
| `changelog`（未迁） | `v1.0.0+` |

即：迁移结果与官方 69／64 完全吻合，此前“999 待核”**撤回**。判据已写入 `流程规则.md`
“存储版本的读取口径”，后续禁止以文件头偏移 12 判定。
