# ADR-0001：采用 13-软件工程 为工程实践基线

- **状态**：已接受
- **日期**：2026-10-22
- **裁决人**：ykla
- **执行者**：主代理
- **复审日期**：2027-01-22
- **替代关系**：无；本 ADR 是工程实践台账的首件，后续 ADR 可修订或替代本件
- **2026-10-29 变更（不改决策）**：目录名由 `13-engineering-doctrine/` 改为 `13-软件工程/`，以对齐项目“数字序号-中文名称”命名规范；采纳范围、边界与复审日期不变。本 ADR 件名同步改为 `ADR-0001-采用13-软件工程为工程实践基线.md`

## 1. 形式

本决策的形式是“规则 + 台账 + 可执行门禁”的组合：

- `流程规则.md` 新增 G0–G5 生命周期、六类变更裁剪表与既有门禁阶段归属；
- `工程实践规则.md` 承载需求基线、ADR、技术债、04／05／06 专项与复审；
- `01-项目管理/02-工程决策与技术债/` 承载 ADR、技术债、复审与审计记录；
- `audit_engineering_practice.py` 检查 ADR、技术债、模板、规则登记与复审日期；
- `audit_gate_registry.py` 以 `STAGE_MAP` 与 R8 把既有门禁映射到 G0–G5。

边界：只覆盖工程类批次（脚本、门禁、模板、数据库迁移、目录页、规则流程）；内容编纂批次仍由考据、写作、主题规则主导。

## 2. 矛盾

不做的后果：

- 工程决策继续散落在任务书、会话记忆与临时脚本中，跨会话不可追溯；
- 同一个门禁或流程要求在多处重复，出现“文档写了、脚本没做、门禁没拦”的失效模式；
- 新批次无法判断应走哪些阶段与门禁，容易以“改动很小”跳过验证；
- 技术债没有承担者与复审日期，缺口长期静默存在；
- 教义入库后只剩口号，无法改变决策或产物。

受影响者：ykla（验收与风险承担）、主代理（执行与复核）、后续接手的会话与协作者。

## 3. 正面

- 每个工程批次有统一的阶段、裁剪与证据要求，减少漏跑门禁；
- ADR 让架构、门禁、目录与不可逆数据格式变更先设计后实现；
- 技术债有承担者、偿还条件与复审日期，缺口不再静默；
- 既有 28 件门禁获得 G0–G5 阶段归属，可回答“本批该跑哪几件”；
- 复审与上游回流让规则可被证伪、降级与删除，避免形式主义；
- 新增文件与既有规则改动均进入 changelog，可追溯。

验证方式：`audit_engineering_practice.py --selftest` 与正负样本；`audit_gate_registry.py` R1–R8；本批全量文档门禁；下一工程批次试点。

## 4. 负面

- **维护成本**：新增规则、模板、台账与门禁需要持续维护，承担者是主代理与 ykla；
- **批次节奏**：G1／G2 对工具批次增加前置工作，可能拖慢小改动；承担者是执行者；
- **门禁误报**：字段检查与阶段映射可能误报，导致额外排查；承担者是执行者；
- **规则漂移**：既有规则改动面大，可能与既有条款冲突；承担者是主代理与后续复审者；
- **形式主义风险**：模板与台账可能变成填表；承担者是所有使用者。

边界：若某条款连续两个复审周期不能改变决策或产物，按复审台账删除或降级；若门禁误报率高于实际拦截收益，按 ADR 修订判据。

## 5. 承担者

| 负面 | 承担者 | 承担时点 |

- 2026-10-17 全库直角引号清零、2026-10-21 加粗空格门禁表明：编码卫生必须由门禁固化，不能靠自觉。

- 这些历史条件说明：项目已有强门禁传统，但缺统一阶段模型、ADR 与技术债，导致经验难以复用。

## 7. 现在依据

- 2026-10-22 基线审计：`13-软件工程/00`–`07` 逐条对照，确认 G0–G5、ADR、技术债、复审为缺口；详见 `基线审计-20261022.md`。
- 实测：`audit_gate_registry.py` 现有 28 件编号门禁，无阶段字段；`流程规则.md` 243 901 B，无 G0–G5 二级标题；`01-规则/README.md` 仍写“十类规则”“76 个 .py”。
- 实测：目录页 `index.html` 2 852 715 B，`doc.css` 701 359 B，`doc.js` 116 601 B；单文件自包含页面，教义 06 的 Web 预算不能直接套用，需项目化裁剪。
- 实测：固定脚本层仅 `audit_server_contract.py` 使用线程；写库并发已有 `claimdb_guard.py`、`register_waterlock.py`、`rotate_guard_state.py`。
- ykla 2026-10-22 明确允许修订、增补、重构、改进既有规则和流程。

## 8. 将来失效条件

出现下列任一条件时，本 ADR 应被修订或替代：

1. `流程规则.md` 被拆分或重构，G0–G5 节不再存在；
2. 门禁体系改为外部 CI／平台执行，`STAGE_MAP` 不再是唯一阶段真值；
3. 技术债台账连续两个复审周期为空或全部“已偿还”，说明登记机制不再需要；
4. 新门禁误报导致批次频繁停摆，且修订判据后仍不能恢复；
5. 项目转为多人协作并引入 PR／代码评审平台，角色与批准规则需重写；
6. `13-软件工程/` 上游版本发生不兼容变更。

- 规则改动须有审计编号与前后对照，提交前跑 `audit_gate_registry.py`、`audit_engineering_practice.py` 与全量文档门禁。

## 11. 安全和解

- 资产：规则文本、门禁脚本、台账、changelog、数据库；
- 对手：误操作、脚本错误、跨会话并发写、外部下载执行；
- 攻击面：脚本写盘、数据库写库、Git 暂存、外部网络抓取；
- 信任边界：ykla 批准范围与发布；主代理执行；子代理只读或限定工作面；
- 现有控制：`claimdb_guard.py`、`register_waterlock.py`、`rotate_guard_state.py`、`git_commit_gate.py`、prebak、changelog、0 信任与三次复查；
- 残余风险：新门禁自身可能误报或空转；模板可能被填表化；规则改动可能引入冲突；
- 证据：`--selftest` 负向夹具、正负样本、全量门禁输出；
- 代价：维护成本与批次前置工作，由主代理与 ykla 承担；
- 失效条件：门禁依赖的解释器／库缺失、规则目录被整体替换、外部 CI 接管。
