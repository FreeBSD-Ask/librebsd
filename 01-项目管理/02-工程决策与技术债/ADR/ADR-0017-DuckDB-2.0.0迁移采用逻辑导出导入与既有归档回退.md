# ADR-0017：DuckDB 2.0.0 迁移采用逻辑导出导入与既有归档回退

- **状态**：已接受
- **日期**：2026-10-24
- **裁决人**：用户（ykla）
- **执行者**：主代理
- **复审日期**：2027-01-23
- **替代关系**：无（新增）；与 `ADR-0016` §1“正式备份槽”的关系是本 ADR 依存储预算约束**豁免本次迁移**的专项正式备份，改为复用 `12-数据库备份/` 既有归档；`ADR-0016` 其余条款（禁止旁路副本、Git 唯一留痕）继续有效

## 1. 形式

- **决策**：DuckDB 由 1.5.5 迁移至 2.0.0 采用**逻辑导出 → 导入**：旧版 `EXPORT DATABASE (FORMAT PARQUET)` → 新版 `IMPORT DATABASE` 重灌（实测档内 `load.sql` 含导出机绝对路径，单独运行必失败，故不以 `load.sql` 为恢复入口）。**“原地写入即升级”的原判据已被实测推翻**（2026-10-24：2.0.0 对 v64 副本做 `CREATE`／`INSERT`／`DROP`＋两次 `CHECKPOINT` 后，文件头存储版本仍为 **64**）；据此本条禁令的理由改述为：原地写入**不产生新格式、达不到迁移目的**，且不留可校验中间态，故仍禁止以原地写入充当迁移，违反者流程中止并报 `INPLACE_WRITE_FORBIDDEN`。
- **版本单一声明源**：`00-编纂规则与格式规范/01-规则/脚本与命令/duckdb-version-baseline.txt` 持有锁定版本（**2026-10-24 18:55 起为 `duckdb==2.0.0`**、Python 3.14.2）；`claimdb_guard.py`／`audit_databases.py`／`analyze_all_databases.py` 启动即比对 `duckdb.__version__`，不一致退出码 2 并指向基线文件；`--skip-version-check` 为显式逃生参数；基线变更须经 ADR。
- **范围（2026-10-24 修订）**：本轮迁移 **25** 个正式库（26 库扣除 `changelog.duckdb`）；`changelog` 因大纲落地批每批写入而**暂缓**，保持 v64。对大纲线**只读**的 `historical_claims.duckdb` 纳入本轮，以原子替换收尾。临时库、沙箱库、外部克隆不迁移。
- **回退通道**：以 `12-数据库备份/` **已有**归档为唯一回退体，`verify_archive()` 三段校验通过方可使用；本迁移**不新建任何备份**（存储预算，ykla 2026-10-24 明示）。
- **施工形态**：单库串行，峰值增量 ≤ 当前处理库体积 × 2；导出体在下一库开始前删除；无可用归档的库登记 `NO_ARCHIVE` 并跳过，不自动补建。
- 边界：不产生 `.bak`／`prebak*` 等旁路副本（红线 12）；不触内容层；与大纲落地批的**写库动作**（`changelog`）不交叉，只读库的替换须在无活跃句柄时执行。

## 2. 矛盾

- **背景（不做会怎样）**：DuckDB 2.0.0 LTS（2026-10-21）新建库使用 **storage version 69**，v1.0–v1.5 为 **64**；官方仅保证**向后兼容读取**——2.0.0 写入的库在 1.5.5 下**不可读**。本项目当前 duckdb **1.5.5**、**无版本 pin**、实测 **424 个 `.duckdb`／122.28 GiB**（其中正式库 26 个／9.83 GiB，`12-数据库备份/` 内 78 个快照件 37.72 GiB，其余为非 SCOPE 内容库与临时件）、三个备份计划任务以 `pythonw` 常驻。若任一次 `pip install -U` 或依赖解析隐式升级，则出现“库已变 v69、任务仍按 1.5.5 预期”的静默混版本：备份连续失败可无人察觉，且库已被改写、无中间态可退。
- **受影响者**：用户（122.28 GiB 数据的可读性）、主代理（每批写库与门禁判据）、三个计划任务（`librebsd-dball-backup-30min`／`-hc-backup-30min`／`-outline-backup-30min`）、大纲落地线（数据库层是其唯一真值载体）。

## 3. 正面

- **能力**：不可逆的存储格式变更被压缩为“新库写入”这一步，旧库在其被替换前始终是 v64 可读体；回退不依赖新建备份，而是既有逻辑归档；版本漂移由基线文件＋启动探测显式暴露，而不是靠人记得。
- **受益者**：用户、接手会话、门禁体系、三个计划任务、大纲落地线。
- **验证方式**：Task 1 三脚本在 1.5.5 下实跑且原判据不变（`claimdb_guard.py --db changelog` 退出码 0 PASS、`audit_databases.py`、`analyze_all_databases.py`）；双版本只读验证按 spec“双版本只读验证”以 SHA-256 前后相等与存储版本 64 判定；回退体以 `verify_archive()` 三段校验；收口以全部相关门禁全绿判定。

## 4. 负面

- **不可逆**：迁移完成后新库为 **v2.0.0 存储格式（编号 69）**，1.5.5 无法读取；同一台机器上任何仍以 1.5.5 打开的路径都会失败。
- **全线版本一致要求**：三个计划任务、全部固定脚本、venv 与门禁须同步切换；任一环节滞后即混版本。
- **成本**：26 库串行迁移与逐库等价校验（表清单、每表行数、`schema_meta`、抽样行校验和）；写死 1.5.5 假设的工具链须改造（TD-028，Task 8 偿还）。
- **时间窗口**：迁移期间数据库读写面须静默，不得与大纲落地批（Task 5／8）并行。
- **风险（本 ADR 风险段，技术债不重复登记）**：
  1. **迁移窗口与大纲落地冲突**：数据库层是大纲落地唯一真值载体，落地批施工中换地基不可接受；两条线须由《长线任务总登记表》串行排队，迁移窗口未开则整个迁移不启动。
  2. **计划任务混版本静默失败**：`pythonw` 任务若沿用旧解释器而库已 v69，备份会连续失败而不报警；以脚本启动版本探测告警＋`12-数据库备份/backup_log.jsonl` 连续两次缺失即触发升级阻断，禁止以“任务没报错”判为正常。
- **边界**：不新建备份、不删归档、不触内容层、不改大纲结构。

## 6. 过去依据

- **历史条件**：2026-08 起以 DuckDB 为主存储层（SQLite 原库转 `ARCHIVE_FINAL_*.db.gz`）；2026-10-14 起三计划任务系统化，常规备份不再人工；2026-10-23 `ADR-0016` 立“全库禁止旁路副本、Git 唯一留痕”，同日 `ADR-0015` 定大纲落地以目录真值派生、数据库为真值载体。
- **此前形式为何失效**：环境长期是“装最新、不 pin”，版本漂移无人核；备份脚本、校验脚本与门禁各自隐含 1.5.5 语义（如 `sqlite2duckdb.py` 注释“DuckDB 1.5.5 无 OPTIMIZE 语句”）；迁移路径从未定义——只要 `pip install -U` 成功，不可逆边界就被无声跨过。

## 7. 现在依据

- **官方与规格**：DuckDB 2.0.0 LTS 于 2026-10-21 发布；新库 storage version 69（v1.0–1.5 为 64）；仅保证向后兼容读取。来源：`.trae/specs/upgrade-duckdb-to-2-0-0-20261024/spec.md`（已批准的 Why／Constraints／Requirement）。
- **本机实测**：2026-10-24 于 `d:\librebsd`，`C:/Python314/python.exe` 实测 `duckdb.__version__ == 1.5.5`、Python 3.14.2；基线文件已落盘；三脚本实跑通过。
- **证据路径**：`00-编纂规则与格式规范/01-规则/脚本与命令/duckdb-version-baseline.txt`；`claimdb_guard.py`／`audit_databases.py`／`analyze_all_databases.py` 的 `require_duckdb_version()` 与实跑输出；`12-数据库备份/backup_databases.py` 的 `SCOPE`（26 库）与 `verify_archive()`；`12-数据库备份/backup_log.jsonl`。
- **证据等级说明**：版本与 storage version 结论本 ADR 取官方发布与已批准 spec 为一证；第二证（独立 venv 装 2.0.0 只读打开 1.5.5 库、前后 SHA-256 相等、存储版本仍 64）按 spec“双版本只读验证”在 Task 3 补齐，未完成前不得宣称兼容性已实测。

## 8. 将来失效条件

1. 上游出现可直接读写 v64 且支持原地降级的版本，逻辑导出导入不再是回退的唯一前提；
2. ykla 裁定长期停留 1.5.5 并接受失去 LTS 与上游安全修复；
3. `12-数据库备份/` 既有归档不可用，且存储预算约束解除、允许迁移前另立专项备份；
4. 数据库层不再是任何线的真值载体（届时串行窗口约束自然消失）。

## 9. 0 信任校验

- **独立复现方式**：基线解析只认 `版本锁定：duckdb==<版本>` 一行，避免多源；实际版本由 `duckdb.__version__` 直取；迁移后以“归档体用 1.5.5 打开、导入体用 2.0.0 打开”双向独立验证；等价性以表清单、每表行数、`schema_meta` 与抽样行校验和逐库比对，差异登记 `MIGRATION_DRIFT`，不以“新格式优化了存储”解释行数差异。
- **交叉验证工具**：三脚本启动探测（不一致退出码 2）；`backup_databases.py verify_archive()` 三段校验（34 parquet ＋ `schema.sql` ＋ `load.sql`，判据不用“前 6 字节 == DUCK 魔数”）；`_longline_status.py --check`。
- **原始证据位置**：上述 spec、基线文件、三脚本实跑输出、`backup_log.jsonl`、逐库迁移记录台账（迁移批落盘）。

## 10. 自由影响

- **退出**：不影响读者可见界面与目录页离线打开。
- **导出**：既有逻辑导出体保持可读；迁移后新导出一律走同一逻辑导出口径，不引入私有二进制快照。
- **离线**：全部本机执行，无外部服务依赖；无自动化与定时任务新增。
- **默认值可撤销性**：本 ADR 可被后续 ADR 替代；基线版本数字可经 ADR 变更；但已迁移库的存储格式**不可退回 v64**，唯一回退是既有归档重灌。

## 11. 安全和解

- **资产**：26 个正式库（9.83 GiB）＋非 SCOPE 内容库（不迁移）、`12-数据库备份/` 既有归档、三个计划任务、版本基线文件。
- **对手**：隐式升级、原地写入、混版本任务、磁盘耗尽、旁路副本、误删归档。
- **攻击面**：`pip install -U` 与依赖解析；`duckdb.connect(path)` 默认读写连接；`pythonw` 任务的解释器路径；导出体与中间产物残留。
- **信任边界**：ykla 裁定迁移窗口与存储预算；主代理执行串行迁移并逐库留证；基线文件持有版本声明。
- **现有控制**：基线＋启动探测（不一致退出码 2）＋`--skip-version-check` 显式逃生；逻辑导出导入；`INPLACE_WRITE_FORBIDDEN`；单库串行与磁盘预算（`DISK_BUDGET_EXCEEDED`）；`NO_ARCHIVE` 不自动补建；红线 12 与 `ADR-0016`；收口门禁全绿方可收口。
- **残余风险**：§4 两条（迁移窗口与大纲落地冲突、计划任务混版本静默失败）；TD-028 所述工具链写死 1.5.5 的假设在 Task 8 前仍存在。
- **证据**：见 §7。
- **代价**：迁移期大纲落地批须让行；每库多一轮等价校验；计划任务切换需同批完成并核对日志。
- **失效条件**：见 §8。

## 15. 存储版本号的口径更正（2026-10-24）

**先前错误**：本批前期报告（`duckdb-2.0-readonly-verification.md`、`duckdb-2.0-claims-and-swap-rehearsal.md`、`duckdb-2.0-migration-ledger.md`）据“文件头字节 12–15 的 uint32”判定存储版本，读到 2.0.0 新建库为 **999**，并把“999 与官方文档 69 不符”挂为待核。

**根因（源码实证）**：DuckDB 2.0.0 的 `src/include/duckdb/storage/storage_info.hpp` 中
`MainHeader.version_number` 已标注 “The main header storage version is now deprecated”，
写入值固定为 `StorageVersion::DEPRECATED = 999`；真实存储版本改存 `DatabaseHeader.storage_compatibility`。
同一枚举表载明：`V1_0_0…V1_1_x = 64`、`V1_2_0 = 65`、`V1_3_0 = 66`、`V1_4_0 = 67`、`V1_5_x = 68`、`V2_0_0 = 69`，
`DEFAULT_STORAGE_VERSION_INFO = V2_0_0`。故 1.5.5 报“can only read versions between 64 and 68”与源码上限 68 完全一致。

**更正后的判定方法与实测**：唯一合法读法为 `SELECT tags FROM duckdb_databases()`，
取 `storage_version` 键（带 `+` 后缀表示“该版本及以后可读”）。2026-10-24 复核 26 个正式库：
25 个返回 **`v2.0.0+`**，`changelog` 返回 **`v1.0.0+`**——与官方 69／64 完全吻合，**无任何异常**。

**结论**：迁移结果不变（25 库确为 v2.0.0 格式），此前“999 待核”一项**撤回**；
