## 零之一、为什么不是“写先于读”

顺序论看似补救，实则保留了我原来的错误二分：它仍把读、写当成两个可分别结项的阶段，只是换了先后。

**读写互为前提，不可拆开验证**：

- 读的判据要靠**写入后的回读**才能证明（读到的块是否真的落盘、读回的库行是否就是写入的那条）；
- 写的正确性要靠**读回**才能证明（块数、行数、内容、锚点是否与写入意图一致）；
- 因此单独任一侧“通过”都不构成验证；真正的验证单元是**一次完整读写循环**：`读入 → 写入 → 回读 → 还原`。

**本项目的真问题是半环验证，不是顺序**：260 单位读侧全绿时，写侧一行未验；若改称“写先于读”而不做回读，仍会得到“写过了，所以对”的假结论。

## 一、核心原则（P0，强制）

**任何链路的验证单元是一次完整读写循环：`读入 → 写入 → 回读 → 还原`。任一侧单独通过不构成验证；dry-run、selftest、只读审计都只是循环的前置检查。**

循环的每一环都必须有**可机器判定的证据**，且证据必须来自**磁盘或库的回读**，不得来自脚本自报或子代理回报。

## 二、三条推论

- **C1 判据双向落地**：每条读侧判据必须有对应的写侧后果与回读断言；每条写侧断言必须有读回证据。不能落地的判据，降级为 INFO 或删除。
- **C2 半环不算验证**：只读审计、dry-run、selftest 的结论只能标“前置已核”，不得标“通过”；未走完循环的链路一律标 `未验证`。
- **C3 沉默失败是首要对手**：显式 FAIL 会被修，静默跳过不会。写入、跳过、放弃、零结果必须在 **stdout** 与回读中同时可见；只写 stderr 视为未披露。

## 三、循环完成的最小可判定集

| # | 断言 | 判定方式 |
| - | ---- | -------- |
| L0 | **生产零改动**（前置） | 生产路径的逐文件或聚合 SHA-256 在循环前后一致，留档 |
| L1 | **读入真实** | 真实读取 N 个单位，输出可复点的清单与计数 |
| L2 | **写入真实** | 对生产等价副本真实写入 M 条（库／宿主／台账），有新增计数 |
| L3 | **回读一致** | 从磁盘／库读回，逐条比对内容与计数；**只比计数不算通过** |
| L4 | **幂等＋还原** | 同输入二跑新增 0；回滚后副本哈希复原；幂等判据须为**内容级**（块级锚点／主键），文件级判据不算 |
| L5 | **失败环可见** | 注入坏件（坏 key／空正文／越界 pk），断言停摆、**stdout 可见计数**、零写入 |

**禁止条款**：不得以“selftest 全绿”替代循环；不得以“dry-run 输出一致”替代写入；不得以“子代理回报”替代磁盘回读；不得以“计数相等”替代内容回读。
