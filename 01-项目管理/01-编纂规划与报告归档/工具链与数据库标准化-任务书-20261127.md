### 2.6 已识别的结构性问题（问题陈述，不是结论）

1. **工具入口碎片化**：121 个 Python 脚本按任务命名，规则以裸文件名引用；同一功能存在多代脚本与退役件，缺机器可读的工具总表与生命周期。
2. **路径与配置硬编码**：部分脚本写死 `D:/librebsd` 或 `C:/`，跨机／跨盘不可复现；未统一 `--root`／`Path(__file__)` 派生。
3. **数据库元数据不齐**：`schema_meta` 未全覆盖，`built_at` 缺失，schema 版本混杂，登记表与磁盘可能漂移；缺统一的数据字典与质量记分卡。
4. **并发与锁**：DuckDB 单写多读、Python GIL、批处理与子代理并发共存；已有 waterlock 与 guard，但缺统一的并发模型、背压、检查点与失败回退规范。
5. **Rust 化无判据**：没有“哪些工具值得改写”的评估矩阵，也没有语言标准与工程基线；容易陷入“为改写而改写”。
6. **公理化缺位**：没有对标准、工具、数据、规则之间的实体—关系—不变量做形式化；一致性、充分性、完备性无定义、无证明、无机器检查。
7. **缓存与垃圾无统一生命周期**：`script/`、`_tmp/`、`review_logs/`、`node_modules/`、`__pycache__`、构建产物并存；已有清理工具但缺分类、TTL、隔离与复扫的闭环。
8. **OCR／音频线各自为战**：Tesseract 命令、OCR 流水线规则、SenseAudio 四份任务书、播客转写脚本并存；缺统一的任务书模板、质量指标与绑定。
9. **specs 入库已裁定**：`specs/` 不排除、进行跟踪（2026-11-27 ykla 令）；剩余问题是 `.trae/specs/` 历史 260 目录仍为工作区，以及 spec 包体量与门禁接线。绑定仍保留 sha256 清单，作为跨会话比对与漂移检测。
10. **标准版本滞后**：GB/T 25000.10-2016 采 ISO/IEC 25010:2011，而 ISO 现行 2023 版；GB/T 36073-2018 已废止、2025 版现行；ISO 15489-1:2016 处于修订状态；SPDX 的 ISO 版本（2.2.1）落后于 3.0.1；ISO/IEC/IEEE 12207:2017 已被 2026 版替代。引用时必须区分“现行有效”与“最新版本”。

### 5.6 版本冲突与滞后（S01 必须逐条处置）

1. **ISO/IEC 25010:2023 vs GB/T 25000.10-2016**：后者采 2011 版（8 特性），前者 2023 版为 9 特性（新增 Safety；Usability→Interaction Capability；Portability→Flexibility；使用质量模型移至 ISO/IEC 25019）。项目 NFR 分类应以 ISO 2023 为方法基线，同时注明 GB/T 现行文本的差异；截至检索日未见替代国标。
2. **ISO/IEC/IEEE 12207:2017 已被替代**：官方状态 Withdrawn（95.99），由 ISO/IEC/IEEE 12207:2026（Ed.2，2026-04 出版）替代。凡按 2017 版写的过程条款一律改引 2026 版。
3. **ISO 15489-1:2016**：状态为“to be revised”（90.92），AWI Ed.3 已立项；引用时写“现行但修订中”，并跟踪新版。GB/T 26162-2021 采其 2016 版，存在二次滞后。
4. **GB/T 26162**：现行为 2021 版，不是 2024；检索时须回国家档案局标准库核对。
5. **GB/T 36073 已换版**：GB/T 36073-2018 已废止；GB/T 36073-2025（DCMM 2.0）2025-12-31 发布、2026-07-01 实施。旧引用须整批换版。
6. **GB/T 7408 已换版**：GB/T 7408-2005 已废止；GB/T 7408.1-2023（等同采用 ISO 8601-1:2019）2023-12-28 发布、2024-04-01 实施。日期格式引用整体迁移。
7. **ISO 8601-1:2019**：现行但“to be revised”（90.92），已有 Amd 1:2022；引用写“ISO 8601-1:2019/Amd 1:2022”。
8. **ISO/IEC/IEEE 15289:2019 与 29148:2018 均在修订**：15289 为 90.92（Ed.5 DIS 注册）；29148 的 Ed.3 处于 DIS 投票。引用须锁版次年号。
9. **ISO/IEC 11179-3:2023 已有修正案**：Amd 1:2026 已发布；引用须注明“含 Amd 1:2026”。
10. **GB/T 25000.12-2017 与 ISO/IEC 25012:2008**：ISO 侧 2025-01 复核仍现行，不构成版本滞后；但国标为修改采用（MOD），条款号不可回标 ISO。
11. **两套数据质量术语体系并存**：ISO 8000（TC 184）与 ISO/IEC 25012/25024（JTC 1/SC 7）各有术语；GB/T 36344 又给六类指标。项目须指定分工：质量模型用 25012、指标分类用 36344、交换原则用 8000。
12. **SPDX**：ISO/IEC 5962:2021 对应 SPDX 2.2.1；SPDX 3.0.1（2024-12）为当前稳定规范，ISO 3.0 版（Ed.2）出版中。项目 SBOM 采用 3.0.x 时须注明“非 ISO 认证版本”。
13. **ISO/IEC 11179-1**：2023 版现行，2015 版已撤；不得再引 2015。
14. **Rust**：2024 Edition 自 1.85.0 稳定；MSRV 与当前 stable 须在执行时实测，不得写死。
15. **PDF/A**：PDF/A-4（ISO 19005-4:2020）基于 PDF 2.0，状态 90.92 拟修订（ISO/DIS 19005-4.2 在投票）；与 PDF/A-1／2／3 的适用差异须在 OCR 流水线中明确。
16. **WebVTT**：现行文本为 Candidate Recommendation Draft（2026-05-20），不是 W3C Recommendation；TTML2 第1版 2018 为 Recommendation，2e 仍为 CR。引用不得写错状态。
17. **OAIS**：ISO 14721:2025（第3版）已替代 2012 版；ISO 16363:2025 替代 2012 版。长期保存引用须换版。
18. **DuckDB**：项目锁定 `duckdb==2.0.0`；官方 2.0.1 LTS 已于 2026-11-20 发布，升级须走 ADR，不得顺手升。

## 六、数据库归一化与质量框架（S02／S06 的设计约束）

### 6.1 唯一真值与路径

- 每个逻辑库只有一个物理真值路径；同名空壳零容忍（`流程规则/07-数据库与数据层.md`）。
- `historical_claims.duckdb` 唯一物理路径为 `04-现代研究文献/historical_claims.duckdb`；其它引用一律逻辑名。

- 运行时版本锁定 `duckdb==2.0.0`；存储版本只从 `duckdb_databases().tags` 读，禁读文件头偏移 12。

### 6.2 Schema 元数据标准（建议，执行时经 ADR）

每个正式库应含 `schema_meta`（或等价表），至少字段：

| 字段 | 类型 | 含义 | 约束 |
| ---- | ---- | ---- | ---- |
| `schema_name` | VARCHAR | 逻辑库名 | 非空、唯一 |
| `schema_version` | VARCHAR | 语义化版本 | SemVer 2.0.0 |
| `built_at` | TIMESTAMP WITH TIME ZONE | 构建时间 | ISO 8601 扩展格式 |
| `source_snapshot` | VARCHAR | 源快照标识／commit | 可追溯 |
| `generator` | VARCHAR | 生成脚本与版本 | 可定位 |
| `git_commit` | VARCHAR | 生成时仓库提交 | 可复现 |
| `row_count` | BIGINT | 构建时行数 | 与实测对账 |
| `checksum` | VARCHAR | 内容摘要（规范化后） | 可复算 |
| `quality_profile` | VARCHAR | 质量记分卡版本／路径 | 可追溯 |
| `notes` | VARCHAR | 例外与豁免 | 非空时可读 |

### 6.3 规范化判据

- 以关系模型与函数依赖为基础：1NF→2NF→3NF→BCNF；对分析型宽表，允许有理由的反规范化，但须在数据字典登记函数依赖与冗余理由。
- 函数依赖推理采用 Armstrong 公理（自反、增广、传递）及其导出规则；闭包与候选键用脚本复算。
- 规范化不是目的：以查询性能、可追溯性、更新异常三者权衡；每次反规范化须有 ADR 或设计注记。
- 跨库关系（claim／outline／reference）以稳定 ID＋显式映射表表达，不用隐式字符串拼接。

### 6.4 数据质量维度与指标

以 ISO/IEC 25012 的 15 特性为骨架，结合 GB/T 36344 与 DCMM：

| 维度 | 可操作指标（示例） | 机判 |
| ---- | ------------------ | ---- |
| 完整性 | 必填列空值率、表行数与源清单差、缺失年份／期号 | 是 |
| 准确性 | 抽样逐字比对、与一手源对账、校验和 | 部分 |
| 一致性 | 跨表孤儿、重复键、枚举越界、同一事实多值 | 是 |
| 唯一性 | 主键／候选键重复率、近似重复组 | 是 |
| 有效性 | 类型／格式／范围／正则、日期合法 | 是 |
| 时效性 | `built_at`、源快照日期、过期标记 | 是 |
| 可追溯性 | provenance 覆盖率、source_id 可回指率 | 是 |
| 可理解性 | 数据字典覆盖率、列注释率、命名合规率 | 是 |
| 可用性 | 打开成功率、查询超时率、锁冲突率 | 是 |
| 可恢复性 | 备份槽覆盖、恢复演练记录 | 部分 |
| 合规性 | 许可证字段、敏感数据标记 | 部分 |
| 保密性 | 凭据／个人信息扫描 | 是 |
| 效率 | 查询 p50／p95、全表扫描耗时 | 是 |
| 精度 | 数值小数位、单位一致性 | 是 |
| 可信性 | 证据等级分布、存疑标记率 | 部分 |

### 6.5 评估方法与记分卡

- **全量剖析，不抽样替代**：表级行数、列级空值／基数／分布、键与依赖、跨表对账；抽样只用于人工逐字复核。
- **只读**：`duckdb.connect(read_only=True)`；不建临时表；不在生产库上跑重查询；必要时复制到临时目录再剖析（复制件须按临时件管理）。
- **记分卡**：每库一行，含 15 维分数、加权总分、风险级别、主要问题、建议动作、证据路径。
- **独立复算**：关键数字由第二脚本或第二进程复算；差异 >0 即挂账。
- **不计成本**：全库、全表、全列剖析；关键库做跨库对账与抽样逐字复核；允许多轮复核与专家（ykla）抽审。但不等于无优先级：按风险×影响排序，先修高风险。

## 七、工具链归一化与并发（S03 的设计约束）

### 7.1 工具分类与生命周期

| 类别 | 判据 | 生命周期 | 落点 |
| ---- | ---- | -------- | ---- |
| 稳定工具 | 入库、被规则引用、有 `--selftest`、有门禁或定期自查 | `stable` | `01-规则/脚本与命令/` |
| 实验工具 | 入库、未被规则引用、有明确试验目标 | `experimental`（TTL 90 天） | `01-规则/脚本与命令/` 或 `script/` |
| 一次性工具 | 未入库、只服务单批 | `one-shot`（TTL 30 天） | `script/` |
| 退役工具 | 被替代、无调用 | `deprecated`（保留 1 季度） | 归档或删除（另批） |
| 外部工具 | 第三方二进制／服务 | 按上游 | 工具表登记版本与许可 |

### 7.2 CLI 契约（所有稳定工具）

- 必须支持 `--help`、`--root`、`--dry-run`；写操作必须支持 `--apply` 与 `--verify`；门禁类必须支持 `--selftest` 与 `--check`。
- 退出码：`0` 成功；`1` 判据失败；`2` 用法／环境／版本错误。禁止用 `0` 表示“有警告但继续”。
- 输出：人读摘要＋机器可读 JSONL／TSV；关键判据须打印原始计数与证据路径。
- 路径：从 `Path(__file__)` 或 `--root` 派生；禁止硬编码盘符；跨盘用参数。
- 配置：CLI 参数优先，环境变量次之，配置文件最后；不得读取用户主目录的隐式状态。
- 日志：UTF-8、LF、无 BOM；时间戳 ISO 8601；不得写入不可见字符。

### 7.3 并发模型

- **DuckDB**：单写多读；官方 2.0 文档明确多进程只读、写入串行化到单进程；项目锁 `2.0.0`，升级 2.0.1 LTS 须另走 ADR。写批必须走 `claimdb_guard.py`＋`register_waterlock.py`；同一库同一时刻只允许一个写者；读连接可并行，但避免长事务阻塞。
- **Python**：CPU 密集用 `ProcessPoolExecutor`；I/O 密集用 `ThreadPoolExecutor` 或 `asyncio`；禁止跨进程共享连接；大对象用 Arrow／Parquet 传递，减少 pickle。
- **GIL**：若本机 Python 3.15 为 free-threaded 构建，须实测 `sys._is_gil_enabled()`；未实测前按有 GIL 设计。
- **Rust**：CPU 密集用 Rayon；I/O 与网络用 Tokio；FFI 边界用 PyO3 时须固定 `Send`／`Sync` 约束，禁止在 Python 与 Rust 之间共享可变引用。
- **背压**：队列有界；批量大小可配；失败重试指数退避；限速按站点／API 配额。
- **检查点**：长任务每批落 checkpoint（JSON／TSV），记录输入哈希、完成项、失败项、下一站；重启幂等。
- **锁**：文件锁／数据库锁／水位锁三层分清；锁超时与死锁检测；禁止用删除锁文件代替释放。

### 7.4 性能与容量

- 基准：启动延迟、单件吞吐、批吞吐、峰值内存、磁盘 I/O、数据库查询 p50／p95。
- 目标：稳定工具在目标数据集上可重复跑完；不以“更快”为唯一目标，优先正确性与可复现性。
- 容量：单批数据量、临时盘占用、备份体积；超过阈值须分片。

### 7.5 供应链与许可

- 每个外部依赖登记：名称、版本、许可、来源 URL、用途、替代方案。
- 优先使用许可证兼容的依赖；GPL／AGPL 依赖须法务级评估（项目已有许可证考据规则）。
- SBOM：采用 SPDX 3.0 或 CycloneDX；注明 ISO 版本差异。
- 构建可复现：锁定版本、记录哈希、记录工具链版本。

## 九、公理化体系（S05 的设计约束）

### 9.1 形式系统定义

建议定义四元组 `S = (Σ, A, D, R)`：

- `Σ`：签名（排序与函数／关系符号）。排序至少含 `Tool`、`Artifact`、`Database`、`Dataset`、`Standard`、`Rule`、`Record`、`Metric`、`Actor`、`Time`。
- `A`：公理集（见 §9.2）。
- `D`：定义集（派生概念，如“合规”“可追溯”“稳定工具”）。
- `R`：推理规则（一阶逻辑＋等价替换＋传递闭包）。

### 9.2 公理草案（A01—A12）

| 编号 | 公理 | 含义 |
| ---- | ---- | ---- |
| A01 | 每个 `Artifact` 恰有一个 `canonical_path` | 单一真值 |
| A02 | 每个 `Database` 恰有一个 `schema_version`，且版本有序 | 版本唯一 |
| A03 | `derives(x,y) ∧ derives(y,z) → derives(x,z)` | 派生传递 |
| A04 | `conformsTo(x,s) ∧ supersedes(s2,s) → conformsTo(x,s2)` 仅当显式迁移 | 标准换版不自动继承 |
| A05 | 每个 `Record` 至少有一个 `provenance` 链到 `Source` | 可追溯 |
| A06 | `ownedBy(x,a) ∧ ownedBy(x,b) → a=b` | 单一责任者 |
| A07 | `checks(t,x) ∧ passes(t,x) → verified(x)` | 验证成立 |
| A08 | `verified(x) → ¬deprecated(x)`（同一时点） | 状态不矛盾 |
| A09 | `lifecycle` 状态迁移单调：`stable → deprecated → archived`，不可逆 | 生命周期 |
| A10 | `binding(spec,taskbook) → hash(spec)=hash(manifest)` | 绑定完整性 |
| A11 | 每个 `Goal` 至少被一个 `Spec` 覆盖 | 目标充分性 |
| A12 | 每个 `Spec` 至少覆盖一个 `Goal` | 无孤儿 spec |

### 9.3 一致性、充分性、完备性

- **一致性**：公理集有模型；不存在 `φ ∧ ¬φ` 的定理。用 Alloy 找反例、TLA+ 检查状态机、Lean／Coq 证明核心引理；工程上再加“实际仓库快照满足不变量”的模型检查。
- **充分性**：对声明的目标集 `G`，每个 `g∈G` 都有至少一个 `Spec` 覆盖，且该 spec 的 FR 可判定。用覆盖矩阵证明（有限集，可穷举）。
- **完备性**：对声明的域 `D`，每个对象都被分类（工具、库、标准、缓存、spec），且每条规则都有落点。相对完备性可证；绝对完备性不可证（需求会演化）。
- **诚实边界**：Gödel 不完备性适用于足够强的形式算术，不直接适用于工程规格；但“需求完备性”本质是经验问题，不能声称数学证明。故本任务书只主张“相对于声明范围的一致／充分／完备”，并明确范围与失效条件。

### 9.4 证明方法与工具

| 目标 | 工具 | 产物 |
| ---- | ---- | ---- |
| 公理一致性（找反例） | Alloy 6 | `axioms.als`＋反例／无模型报告 |
| 状态机与并发不变量 | TLA+／PlusCal | `Axioms.tla`＋TLC 模型检查 |
| 核心代数引理 | Lean 4 或 Coq | `Proofs.lean`／`Proofs.v` |
| 规格可读性 | Z 记号（ISO/IEC 13568） | `Spec.tex`／`Spec.md` |
| 数据库函数依赖 | Armstrong 公理＋闭包算法 | `fd_closure.py`＋证明表 |
| 绑定完整性 | sha256＋清单校验器 | `BINDING.tsv`＋`audit_task_spec_binding.py` |

### 9.5 交付物

- `公理化体系.md`：排序、符号、公理、定义、定理、证明、模型与反例。
- `axioms.als`／`Axioms.tla`／`Proofs.lean`：可机检文件。
- `traceability.tsv`：目标→公理→定理→证据。

## 十二、缓存与垃圾识别清理（S11 的设计约束）

### 12.1 分类

| 类别 | 示例 | 可再生产 | 默认动作 |
| ---- | ---- | -------- | -------- |
| 可再生缓存 | `__pycache__`、`.pytest_cache`、`.mypy_cache`、`.ruff_cache`、`node_modules`、`target/`、`dist/`、`build/` | 是 | 清理候选 |
| 临时件 | `script/` 一次性脚本、`_tmp/`、`review_logs/` 中间件 | 部分 | 按 TTL／引用 |
| 旁路备份 | `.bak`、`.prebak`、`.orig`、`.rej`、`~` | 否 | 禁止；已存在者另批清理 |
| 孤儿 staging | 无主批目录、过期 checkpoint、空目录 | 否 | 隔离后清理 |
| 过期快照 | 陈旧 DB 快照、旧版报告 | 否 | 保留策略判定 |
| 大文件 | >50 MB 非入库件 | 否 | 单独评估 |
| 错名目录 | 含 `…`、零宽字符、`[MASKED]`、前导 `._` | 否 | 隔离后清理 |

### 12.2 判据

- **路径**：命中已知缓存／临时模式。
- **年龄**：mtime 超过 TTL（缓存 7／30 天；一次性 30 天；隔离 30 天）。
- **引用**：basename 在规则、报告、任务书、脚本中被引用 → `keep` 或 `archive`。
- **所有权**：有活跃批／进程／锁 → 不动。
- **哈希**：与源件重复 → 去重候选。
- **入库状态**：`git ls-files` 命中 → 不删；仅未跟踪件可进入清理候选。
- **保护清单**：`05-卷册大纲/`、`旧大纲-20261023/`、`12-数据库备份/`、数据库、changelog、规则与文档、历史报告。

### 12.3 流程

`scan → classify → reference-check → manifest（path/type/size/mtime/sha256/category/in_scope/referenced/action）→ plan → apply → verify → ledger`

- 每步可独立运行；`apply` 只删 `action=delete` 且在 allowlist 内；歧义项移入隔离区。
- 不做定时自动化；全仓清理须 ykla 明示。
- 删除前有清单与 sha256；删除后 `--verify` 零残留；台账入 changelog。

### 13.2 归一化流水线（建议）

**OCR**：`输入 PDF／图片 → 文本层探测（有则优先）→ 预处理（去噪／纠偏／分辨率）→ OCR（Tesseract；可选 PaddleOCR）→ ALTO／hOCR＋纯文本 → 质量门（置信度／抽样 CER）→ Markdown → 入库（references_fulltext）→ provenance`

**音频**：`输入音频／视频 → 抽取音轨 → 响度分析与归一（BS.1770-5／R128）→ 转写（Whisper／SenseAudio）→ 时间戳与字幕（WebVTT／SRT）→ 质量门（WER／CER、时间戳误差）→ 入库（播客库）→ provenance`

### 13.3 质量指标

- OCR：字符准确率／CER、词准确率／WER、版面阅读顺序、置信度分布、语言覆盖、抽样人工复核比例、失败分级（verified／needs_review／failed）。
- 音频：WER／CER、时间戳对齐误差、响度（LUFS／dBTP）、采样率／位深／编码、字幕格式合规、转写置信度、人工复核比例。
- 每条指标注明标准或方法依据；无标准者标 `[方法依据]`（如 NIST SCTK、WER 论文），不冒充 ISO 标准。
