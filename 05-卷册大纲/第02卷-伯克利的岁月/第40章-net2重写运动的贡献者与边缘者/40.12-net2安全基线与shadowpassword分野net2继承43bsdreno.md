# 40.12 Net/2 安全基线与 shadow password 分野——Net/2 继承 4.3BSD-Reno 安全机制为后续 FreeBSD/NetBSD 提供安全代码基础，BSD 与 System V 在密码存储上的安全哲学分野延续至 FreeBSD 4.x 才弥合（1991）

## 40.12.1 Net/2 安全基线继承 4.3BSD-Reno 安全机制与对后续 FreeBSD/NetBSD 的安全代码基础

**要点**：Net/2（**1991.6**）作为 BSD 首个完全自由完整代码发布，其安全基线继承自 4.3BSD-Reno（**1990.6**）与 CSRG 后期安全机制——含 4.2BSD 起定型的 `/etc/passwd` 七字段文件格式（用户名、密码散列、UID、GID、GECOS、家目录、shell）与 **crypt(3)** DES 25 轮迭代散列、4.2BSD 网络栈引入的 **sendmail(8)**/**fingerd(8)**/**rlogind(8)**/**rshd(8)** 等网络服务及其 `~/.rhosts` 信任链、4.3BSD-Reno 引入的 MIT Kerberos v4 客户端库与 `klogind`/`krshd`/`kftpd` 服务（作为可选组件）、文件权限 rwx 与 setuid/setgid 检查机制、**chroot(2)** 系统调用（自 4BSD 起存在，原始动机为测试安装环境而非安全沙箱，事后被赋予安全意义的史实辨析保留［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］）；Net/2 通过完全自由发布使这些安全机制代码可被后续 FreeBSD 1.0（**1993.12**）、NetBSD 0.8（**1993.4**）直接继承而无需 AT&T 源代码许可证，386BSD（**1992**）作为 FreeBSD 与 NetBSD 的共同前身以 Net/2 为代码基础补全 6 个争议内核文件形成可运行系统；

蠕虫遗留漏洞面：Net/2 安全基线中 Morris 蠕虫（**1988.11**）暴露的 **sendmail(8)** DEBUG 命令、**fingerd(8)** 缓冲区溢出、`~/.rhosts` 信任链三类远程漏洞在 Net/2 发布时仍未根本修复——CSRG 在 4.3BSD-Tahoe（**1988.6**）与 4.3BSD-Reno（**1990.6**）期间发布过补丁（如 **sendmail(8)** DEBUG 命令默认禁用、**fingerd(8)** 缓冲区溢出修复），但网络服务信任模型未根本重构，使后续 FreeBSD/NetBSD 早期版本仍需面对蠕虫时代的遗留漏洞面

**史观**：第 4 条分离聚合是永恒规律——Net/2 将 BSD 安全机制代码从 AT&T 混合版权聚合体中分离出来，分离是为了聚合到完全自由 BSD 生态，安全代码的自由化是 BSD 完全自由路径的组成部分；第 13 条法律与道德是利益分配——BSD 许可证允许 Net/2 安全代码自由再分发，使后续 FreeBSD/NetBSD 无需 AT&T 许可证即可继承 BSD 安全机制，许可证条款的利益分配安排决定安全代码的继承路径

**辨析**：Net/2“安全基线”指安全机制代码的继承基础，而非 Net/2 引入新的安全机制——Net/2 的安全机制本身仍是 4.3BSD-Reno 的继承，Net/2 的历史意义在于“完全自由”使安全代码可被自由继承，须区分“安全机制创新”与“安全代码自由化”；Net/2 安全基线中 Morris 蠕虫暴露的远程漏洞在 Net/2 发布时仍未根本修复的判断需核对——CSRG 在 4.3BSD-Tahoe 与 4.3BSD-Reno 期间发布过补丁，但网络服务信任模型（`~/.rhosts`）未根本重构，须区分“补丁修复”与“信任模型重构”；**chroot(2)** 原始动机争议（Bill Joy 自述为测试安装环境设计，非安全沙箱）保留 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］，事后被赋予安全意义是史实重构而非原始设计意图

## 40.12.2 shadow password 在 BSD 与 System V 的分野——BSD 直至 4.4BSD-Lite 仍坚持 `/etc/passwd` 单文件格式，与 System V R3.2 的 `/etc/shadow` 形成对照，分野延续至 FreeBSD 4.x 才弥合

**要点**：shadow password（密码散列分离存储）在 BSD 与 System V 的分野源于 **1980 年代** 两者的安全哲学差异——System V **R3.2**（**1987 年**）引入 `/etc/shadow` 文件将密码散列从 `/etc/passwd` 移至仅 root 可读的 `/etc/shadow`，降低字典攻击风险，反映 System V 优先考虑商用客户的密码安全；BSD 则直至 **4.4BSD-Lite**（**1994.6**）仍坚持 `/etc/passwd` 单文件格式（密码散列留在所有用户可读的 `/etc/passwd` 中，虽经 **crypt(3)** DES 25 轮迭代散列但仍可被字典攻击破解），反映 BSD 优先考虑兼容性与简洁性；**Net/2**（**1991.6**）作为 BSD 完全自由完整代码发布继承此分野——Net/2 仍使用 `/etc/passwd` 单文件格式，未引入 shadow password，与同期 System V R3.2/R4 的 `/etc/shadow` 形成对照；此分野延续至 **FreeBSD 1.0-3.x**（**1993-2000**）与 NetBSD 早期版本均继承 BSD 单文件格式，直至 **FreeBSD 4.x**（**2000 年** 起）才引入 **master.passwd** 与 **spwd.db** 实现密码散列分离，弥合与 System V 的 shadow password 分野；BSD 选择单文件格式的工程原因是 NIS（Network Information Service，原黄页 Yellow Pages，因英国电信商标争议改名）分布式账户管理依赖 `/etc/passwd` 的可读性——NIS 客户端需读取 `/etc/passwd` 构造用户映射表，shadow password 会破坏 NIS 兼容性，此约束在 **1980-1990 年代** BSD 站点广泛部署 NIS 的语境下使 shadow password 不具备工程可行性

| 维度 | BSD（4.2BSD-4.4BSD-Lite） | System V（R3.2/R4） |
| -- | ----------------------- | ----------------- |
| 文件格式 | `/etc/passwd` 单文件 | `/etc/passwd` + `/etc/shadow` 双文件 |
| 密码散列位置 | `/etc/passwd`（所有用户可读） | `/etc/shadow`（仅 root 可读） |
| 安全模型 | **crypt(3)** DES 25 轮迭代散列 | shadow 密码分离，降低字典攻击风险 |
| 引入时间 | 4.2BSD 起至 **4.4BSD-Lite**（**1994.6**） | **R3.2**（**1987 年**）引入，**R4**（**1988 年**）标准化 |
| 兼容性考虑 | NIS 分布式账户管理依赖 `/etc/passwd` 可读性 | 不依赖 NIS，shadow 不影响 NIS |
| 弥合时间 | **FreeBSD 4.0**（**2000.3**）引入 **master.passwd** + **spwd.db** | — |

**史料**：**4.2BSD** `/etc/passwd` 文件格式规范（七字段，**crypt(3)** DES 25 轮迭代）；System V **R3.2** `/etc/shadow` 文件规范（**1987 年**）；**4.4BSD-Lite** Release Notes (**1994.6**) 确认仍使用 `/etc/passwd` 单文件格式；**FreeBSD 4.0** Release Notes (**2000.3**) 确认引入 **master.passwd** 与 **spwd.db**；NIS/Yellow Pages 设计文档；《4xbsd-security-1980-1991》内部史料（史实三）〔存疑：所引材料在本库无对应路径，原位待考〕 ［A］

**史观**：第 2 条历史是形式主义化的非存在——System V 的 shadow password 是“密码安全”形式逻辑的扩张（密码散列须分离存储），BSD 的单文件格式是“兼容性与简洁性”形式逻辑的坚守，两种形式主义对立驱动 shadow password 分野；第 9 条经验优先——BSD 选择单文件格式基于 NIS 分布式账户管理的工程实践需求，而非安全理论先行，工程实践约束决定了安全机制选择

**辨析**：shadow password 分野的“安全哲学差异”叙述需避免简化为“BSD 不重视安全”——BSD 选择单文件格式是基于 NIS 工程约束的实践判断，而非忽视密码安全，须区分“安全哲学差异”与“安全意识差异”；BSD 直至 **4.4BSD-Lite** 仍坚持 `/etc/passwd` 单文件格式的判断需核对——4.4BSD-Lite Release Notes 与 4.4BSD 系统管理员手册确认仍使用单文件格式，但 CSRG 内部可能讨论过 shadow password 引入，须区分“发布版本格式”与“内部讨论”；**FreeBSD 4.x** 引入 **master.passwd** 与 **spwd.db** 弥合 shadow password 分野的精确版本需核对——**FreeBSD 4.0**（**2000.3**）已引入 **master.passwd** 机制，须区分“FreeBSD 4.0 引入”与“FreeBSD 4.x 逐步完善”；System V **R3.2** 引入 `/etc/shadow` 的精确年份存在 **1987 年**（R3.2 引入）与 **1988 年**（R4 标准化）两种记载，须区分“R3.2 引入”与“R4 标准化”。〔存疑：System V R3.2 引入 /etc/shadow 的精确年份待多源交叉验证〕

**观点**：1991 年 8 月 1 日 Perry Metzger 在 bugs.4bsd 发文批评流行的 shadow 密码方案本质是“隐蔽即安全”：只要攻击者获得文件系统的短暂访问权，shadow 文件就失去全部意义；他主张更直接的做法是延长密码长度（16 至 32 字符）或干脆用密码学散列替代 crypt(3) 支持任意长度密码，并公开向网络征集比 crypt(3) 更好的替代方案，承诺“你会成为英雄”。
**邮件来源**：Perry Metzger，bugs.4bsd，1991-08-01，Message-ID: `1991Aug1.183556.25214@watson.ibm.com`
**史学意义**：Net/2 发布当月 BSD 阵营内部正在激烈辩论密码安全路径——BSD 坚守 /etc/passwd 单文件并非忽视安全，而是当时“隐蔽存储派”与“更长密码/更强散列派”之争中后者对前者的主动批判，Net/2 的安全基线是这场辩论的快照而非教条。
