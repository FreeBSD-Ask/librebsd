# 29.8 vi/csh 的长期影响——现代编辑器与 shell 中的延续

## 29.8.1 vi 谱系的现代延续：vim、neovim 与 vi 克隆

**要点**：vi 的模态设计自 1978 年 2BSD 发布以来持续影响现代编辑器生态，形成 “vi 谱系” 的漫长演化链——**vim**（Bram Moolenaar 1988 年在 Amiga 上开始开发，**1991 年 11 月** 首次公开发布 Vim 1.14 于 Fred Fish Disk #591，最初名为 “Vi IMitation”，**1992 年** Vim 1.22 移植到 UNIX/MS-DOS 后更名为 “Vi IMproved”）、**elvis**（Steve Kirkendall **1990 年** 开发，**1992 年** 被引入 BSD 用作 AT&T vi 代码移除后的临时替代）、**nvi**（Keith Bostic（基思·博斯蒂克） **1994 年** 为 4.4BSD-Lite 基于 elvis 1.8 重写）、**Neovim**（Thiago de Arruda **2014 年** 发起，fork Vim 代码库以 “aggressively refactor” 为目标，首版 v0.1.0 于 **2015 年 11 月 1 日** 由 justinmk 在 GitHub 打标签发布，仓库 <https://github.com/neovim/neovim>）；Neovim 的 fork 缘起于 Moolenaar 拒绝 De Arruda 提交的大型多线程补丁，De Arruda 遂 fork Vim 代码库另立项目，旨在简化维护、分割开发工作、启用基于 coprocess 的新插件架构、移除遗留平台支持与 Vi 兼容模式（`nocompatible` 成为 no-op）；Neovim 保留 Vimscript 兼容性但引入 Lua 作为首选扩展语言，内置 tree-sitter 解析器、LSP 客户端与现代 GUI 解耦架构

**史料**：Neovim GitHub 仓库（<https://github.com/neovim/neovim>，访问日期 2026-07-28，v0.1.0 标签日期 2015-11-01T21:16:53Z，标签者 justinmk，commit c4826c3）；Neovim 官方 Introduction Wiki（<https://github.com/neovim/neovim/wiki/Introduction>，访问日期 2026-07-28，引文 "Neovim is a project that seeks to aggressively refactor Vim source code“、”this is not a project to rewrite Vim fromscratch“、”Vi emulation will also be removed (setting nocompatible will be a no-op)"）；Neovim 官方 vim_diff 文档（<https://neovim.io/doc/user/vim_diff.html>，访问日期 2026-07-28）；Moolenaar, B. **史观**：第 4 条分离与聚合——vi 谱系在演化中既分离（vim、elvis、nvi、Neovim 各自独立发展）又聚合（均保留 vi 模态编辑核心）；第 2 条实践先于理论——Neovim 的 fork 缘起于具体的补丁拒绝事件而非理论分歧，体现实践冲突驱动技术演化；第 1 条偶然性——Moolenaar 拒绝 De Arruda 的补丁是偶然事件，但此偶然事件催生了 Neovim 这一持续影响现代编辑器生态的项目，“Vi IMitation” 更名为 “Vi IMproved” 亦体现命名的偶然性

## 29.8.2 vi 模式在现代编辑器中的扩散：emacs、VS Code 与 IDE 生态

**要点**：vi 的模态设计不仅延续于 vi 谱系编辑器，更扩散至其他编辑器家族——**GNU Emacs** 内置 **viper-mode**（VI PERilous，为 GNU Emacs 默认附带的 vi 仿真次模式，支持 vi 的命令模式、插入模式与可视模式，由 Michael Kifer 开发，随 GNU Emacs 发行版发布，GNU Emacs 手册专设 “Viper” 一章），emacs 社区另发展出 **evil-mode**（Extensible vi Layer for Emacs，由 Frank Fischer **2011 年 11 月** 在 GitHub 发起开发，仓库 <https://github.com/emacs-evil/evil>，最早 commits 可追溯至 2011 年 11 月 10 日，现为 emacs 社区最流行的 vi 仿真层，当前维护者 Tom Dalziel），evil-mode 采用状态机模型实现 vi 模态，被 Spacemacs、Doom Emacs 等流行 emacs 发行版默认集成；**Visual Studio Code** 通过扩展市场提供 Vim 扩展（vscodevim.vim，由 GitHub 用户 vscodevim 团队维护），在 IDE 环境中复现 vi 模态编辑；JetBrains 系列 IDE（IntelliJ IDEA、PyCharm、CLion 等）内置 IdeaVim 插件提供 vi 模态仿真；vi 模态的跨编辑器家族扩散证明 vi 设计的持久生命力，从 1978 年 2BSD 的 300 波特调制解调器约束演化为 2020 年代 IDE 生态的标配功能

**史料**：GNU Emacs 手册 “Viper” 章节（<https://www.gnu.org/software/emacs/manual/html_node/viper/>，访问日期 2026-07-28，访问时超时未获取完整内容，依据 GNU Emacs 官方文档目录确认 Viper 章节存在）；evil-mode GitHub 仓库（<https://github.com/emacs-evil/evil>，访问日期 2026-07-28，最早 commits 可追溯至 2011 年 11 月 10 日，作者 Frank Fischer，当前维护者 Tom Dalziel，仓库 Keywords: [emulation] [vim]）；VS Code Vim 扩展（vscodevim.vim，VS Code Marketplace）；JetBrains IdeaVim 插件（JetBrains Marketplace） ［A］

**史观**：第 4 条分离与聚合——vi 模态设计从 vi 谱系分离出去，被 emacs、VS Code、JetBrains 等不同家族的编辑器聚合吸收；第 6 条技术路线分化——vi 模态与 emacs 无模态的技术路线分化并未消除，而是通过 vi 仿真层在 emacs 内部并存，形成 “模态 vs 无模态” 的持续张力；第 14 章边缘者——viper-mode 作者 Michael Kifer 与 evil-mode 作者 Frank Fischer 在 vi 叙事中常被忽略，但其工作使 vi 模态得以跨编辑器家族传播，是 vi 影响力的关键放大者

## 29.8.3 csh 谱系的现代延续：tcsh、bash vi-mode、zsh vi-mode

**要点**：csh 的交互式创新（历史替换、作业控制、别名、文件名补全）被后续 shell 广泛吸收——**tcsh**（Ken Greer **1981 年 12 月** 在 HP Labs 将 TENEX 风格文件名补全合并入 csh，形成 csh 谱系的直接延续，Arch Linux man **tcsh(1)** 原文 “Ken Greer, HP Labs, 1981. File name completion.”）；**bash**（Brian Fox **1989 年** GNU 项目，吸收 csh 交互功能但以 Bourne shell 语法为基础，通过 readline 库提供 **vi-mode**——用户执行 `set -o vi` 启用 vi 风格命令行编辑，readline 库默认为 emacs-mode，vi-mode 提供命令模式与插入模式切换，支持 h/j/k/l 移动、dd 删除行、cc 修改行、w/b 词移动等 vi 命令）；**zsh**（Paul Falstad **1990 年** 在普林斯顿大学发布于 comp.sources.misc 新闻组，通过 `bindkey -v` 启用 vi-mode，支持 vi 风格命令行编辑，zsh 的 vi-mode 较 bash 更完整，支持 vi-style 文件名补全与命令历史导航）；tcsh 在 csh 基础上增加 TENEX 补全与命令行编辑，成为 BSD 系统（FreeBSD、NetBSD、OpenBSD）的默认 root shell 选项之一；bash 与 zsh 虽非 csh 直接后裔，但 csh 开创的交互式功能（历史替换、别名、作业控制、文件名补全）被二者以不同语法形式吸收，体现 “功能延续、语法分化” 的演化特征

**史料**：Arch Linux man **tcsh(1)** “AUTHORS” 节（HP Labs 1981 标注）；GNU Bash Reference Manual（readline vi-mode 章节，<https://www.gnu.org/software/bash/manual/>，访问日期 2026-07-28）；readline man page（`editing-mode` 配置项）；Fox, B. (1989) “Bash Reference Manual”；Falstad, P. (1990) zsh 0.1 发布公告（comp.sources.misc 新闻组，zsh.sourceforge.io 项目历史存档）；zsh Manual（vi-mode 章节，`bindkey -v`） ［A］

**史观**：第 4 条分离与聚合——csh 的交互功能被后续 shell 分别吸收与聚合，tcsh 直接延续 csh 谱系，bash 与 zsh 以不同语法形式聚合 csh 功能；第 6 条技术路线分化——交互式 shell（csh/tcsh）与脚本式 shell（sh/bash）的技术路线分化持续至今，bash 通过兼容 Bourne shell 语法统一了脚本与交互，但 vi-mode 作为交互功能仍独立于脚本语法；第 24 条许可证——csh 作为 BSD 创新未进入 AT&T 默认发行版，但其交互功能通过 bash（GNU）与 zsh（开源）在自由软件生态中得到延续

**辨析**：bash vi-mode 与 zsh vi-mode 的 “兼容性范围” 需区分两个层面——(1) 命令行编辑层面的 vi 模态（bash 与 zsh 均支持，通过 readline 与 zle 实现），(2) 脚本语法层面的 vi 兼容（不存在，bash 与 zsh 均为 Bourne shell 谱系而非 csh 谱系）；bash 的 vi-mode 通过 readline 库实现，readline 的 `editing-mode` 配置项可设为 `vi` 或 `emacs`（默认），`set -o vi` 为临时启用，`~/.inputrc` 中 `set editing-mode vi` 为永久配置；zsh 的 vi-mode 通过 Zsh Line Editor（zle）实现，`bindkey -v` 为启用命令，zsh 的 vi-mode 较 bash 更完整，支持 `vicmd`（命令模式）与 `viins`（插入模式）两套键绑定；tcsh 在 FreeBSD、NetBSD、OpenBSD 中作为可选 shell 提供，但非默认交互 shell（FreeBSD 14 默认为 sh，OpenBSD 默认为 ksh，NetBSD 默认为 sh）；［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］ bash、zsh、tcsh 的 “用户规模” 与 “市场份额” 难以获得可靠的一手统计数据——不同发行版的默认 shell 配置不同，且用户可自行更改，按 0 信任原则不引用具体百分比数字；Ken Greer 1981 年合并 tcsh 工作的所属机构在不同来源中存在分歧（Arch Linux man tcsh 标注 HP Labs，部分来源标注 CMU），按 0 信任原则以一手 man tcsh 为准；[2026-08-14 两库核查：tcsh（Ken Greer 1981）、bash（Brian Fox 1989）、zsh（Paul Falstad 1990）的具体发布时间在参考文献库（tech “tcsh” 0 命中）与邮件库 usenet 中均无直接条目，两库无法验证]

## 29.8.4 vi/csh 影响力的跨时代评估

**要点**：vi 与 csh 自 1978 年 2BSD 发布以来已延续 **47 年**（截至 2026 年），其影响力体现于三个层面——(1) 直接谱系延续：vi 谱系经 vim（1991）、elvis（1990）、nvi（1994）、Neovim（2015）持续演化，csh 谱系经 tcsh（1981）延续；(2) 功能扩散：vi 模态被 emacs（viper-mode/evil-mode）、VS Code（Vim 扩展）、JetBrains（IdeaVim）等跨家族编辑器吸收，csh 交互功能被 bash、zsh 以不同语法形式吸收；(3) 文化影响：vi 与 emacs 的 “编辑器圣战” 从 1980 年代延续至今，vi 模态设计从低速终端的物理约束演化为程序员群体的文化标识，“vi 难学但高效” 的认知在开发者社区中固化；vi/csh 的长期影响证明，源于具体硬件约束（300 波特调制解调器、PDP-11 16 位地址空间）的实践设计可以超越原始约束的消失而持续生效——现代终端与 IDE 的硬件性能已远超 1978 年的 PDP-11，但 vi 模态因其 “减少手指移动” 的人体工程学价值与 “模式分离” 的认知效率价值而被保留

**史料**：本节综合 11.8.1、11.8.2、11.8.3 各小节史料 ［A］

**史观**：第 2 条实践先于理论——vi/csh 的长期影响并非先验设计理论的胜利，而是实践设计在持续使用中被证明有效的结果；第 7 条硬件与软件辩证——vi 模态源于 300 波特调制解调器的硬件约束，但其价值在硬件约束消失后仍被保留，体现软件设计对硬件约束的 “超越性辩证”——硬件催生的设计可能因自身内在价值而独立于硬件存在；第 5 章 5.3 节记忆与必然化——“vi 难学但高效” 的认知在后世被必然化为 vi 设计的 “固有优越性”，但回到 1978 年的语境，vi 模态只是 Joy 在低速终端约束下的妥协方案，其 “高效” 是事后被赋予的必然化叙事，须警惕此类事后合理化

**辨析**：[自反性声明] 本小节的 “跨时代评估” 本身即是一种事后建构——将 vi/csh 的持续使用追溯为 “实践设计的胜利” 是史家的叙事框架，而非历史参与者（Joy、Moolenaar、De Arruda 等）的自觉意图；按项目史观总纲第 5 章 5.3 节 “记忆将许多偶然性认识为一种必然性”，“vi 模态的持久生命力” 这一判断可能将偶然的路径依赖（vim 取代 vi 成为事实标准、VS Code 扩展市场推广 Vim 扩展等）合理化为必然的设计优越性；［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］ vi/csh 的 “文化影响” 难以量化评估——“编辑器圣战” 的持续时间、vi 模态在开发者社区中的 “文化标识” 地位等判断缺乏可靠的一手统计数据，按 0 信任原则仅作定性描述不引用具体数字；本小节综合 11.8.1-11.8.3 各小节史料，未引入新的一手来源
