# 38.6 Kerberos v4 集成争议与 BSD 认证体系分歧——4.3BSD-Reno 首次引入第三方网络认证的争议焦点与长期边缘化（1990）

## 37.6.1 4.3BSD-Reno Kerberos v4 集成与 BSD 首次引入第三方网络认证
- 要点：4.3BSD-Reno（**1990 年 6 月** 磁带制作，Keith Bostic（基思·博斯蒂克） **1990 年 7 月 6 日** comp.archives 公告）集成 MIT Kerberos v4 客户端库与 `klogind`、`krshd`、`kftpd` 等基于 Kerberos 票据认证的网络服务（除 NFS 外大部分系统），是 BSD 首次引入第三方网络认证机制；MIT Kerberos v4 由 MIT Project Athena 于 **1988 年** 发布（Steiner, Neuman, Schiller 1988 年论文《Kerberos: An Authentication Service for Open Network Systems》），引入 KDC（Key Distribution Center）与票据（ticket）机制，使网络服务可基于第三方认证而非 `~/.rhosts` 信任链；Reno 的 Kerberos 集成使 BSD 网络服务（rlogin、rsh、ftp 等）可选用 Kerberos 票据认证替代传统的 `~/.rhosts` 信任链，理论上可消除 Morris 蠕虫（**1988 年 11 月**）所利用的 rshd 信任传递漏洞；但 Reno 作为 test release（Bostic 公告原文"NOT intended to be used on production systems"），Kerberos 集成仅为测试性预览而非生产就绪
- 史料：Keith Bostic 1990.7.6 comp.archives"V1.90 (4.3BSD-Reno)"公告原文（gunkies.org/wiki/4.3_BSD_Reno，记载 Kerberos v4 集成特性）；4.3BSD-Reno 源代码中 Kerberos 客户端库与 `klogind`/`krshd`/`kftpd` 实现；Steiner J G, Neuman C, Schiller J I. "Kerberos: An Authentication Service for Open Network Systems"[C]. MIT Project Athena, 1988；CSRG 贡献者名单（netbsd.org/people/CSRG-contrib.html，列出"Kerberos: MIT Project Athena"）；`unix-wizards` 与 `comp.unix.bsd` 邮件列表存档中关于 Reno Kerberos 集成的讨论（须查互联网档案馆） ［A］
- 史观：第 2 条形式主义——Kerberos v4 的“第三方票据认证”形式逻辑旨在替代 `~/.rhosts` 信任链，但形式逻辑的部署复杂性使其在 BSD 社区未能广泛采纳，形式主义膨胀遭遇工程实践阻力；第 9 条经验优先——Reno 作为 test release 集成 Kerberos 是实践驱动的测试而非理论先行的标准化，体现 CSRG"release early, get feedback"的工程哲学
- 辨析：Reno 的 Kerberos 集成“除 NFS 外大部分系统”须核对——Bostic 1990.7.6 公告原文记载 Kerberos 集成范围，NFS 因 Rick Macklem（加拿大圭尔夫大学）的独立实现而未集成 Kerberos，须区分“NFS 未集成”与“全部系统集成”；MIT Kerberos v4 发布时间为 1988 年（MIT Project Athena），Reno 集成时间为 1990 年 6 月，须区分“Kerberos v4 发布”与“BSD 集成”；Reno 作为 test release 的 Kerberos 集成“仅为测试性预览”须区分“测试预览”与“生产就绪”——Reno 公告明确"NOT intended to be used on production systems"，Kerberos 集成在 4.4BSD（1994）中才逐步成熟

## 37.6.2 Kerberos 集成争议的三个焦点——KDC 部署复杂性、US Export Control DES 限制、与 ~/.rhosts 兼容性
- 要点：BSD 社区对 4.3BSD-Reno Kerberos v4 集成的争议集中在三个焦点：（1）KDC 部署复杂性与小型站点运维负担——Kerberos v4 要求部署 KDC（Key Distribution Center）作为集中式密钥分发服务器，KDC 需专用硬件、安全物理环境与专职管理员，小型学术站点与个人工作站用户缺乏 KDC 运维资源，使 Kerberos 在小型站点中实际不可部署；（2）US Export Control 对 DES 加密算法的出口限制——Kerberos v4 使用 DES（Data Encryption Standard）加密算法，1980 年代末至 1990 年代初 US Export Control 将 DES 列为军需品出口管制对象（ITAR），BSD 源代码的国际分发因含 Kerberos DES 代码面临法律风险，CSRG 需维护含 Kerberos 与不含 Kerberos 两个版本以应对出口管制；（3）Kerberos 与现有 `~/.rhosts` 信任链的兼容性问题——Reno 集成 Kerberos 后网络服务（rlogin、rsh、ftp）同时支持 Kerberos 票据认证与 `~/.rhosts` 信任链两种模式，用户与管理员需选择认证模式，混合部署导致认证策略不一致，且 `~/.rhosts` 信任链仍可作为回退路径绕过 Kerberos 认证，削弱 Kerberos 的安全增益；三个争议焦点使 Kerberos 在 BSD 社区未能获得广泛采纳
- 史料：`unix-wizards` 与 `comp.unix.bsd` 邮件列表存档中关于 Reno Kerberos 集成争议的讨论（1989-1991，须查互联网档案馆）；4.3BSD-Reno Release Notes 中 Kerberos 集成说明；MIT Kerberos v4 文档中 KDC 部署要求；US Export Control ITAR（International Traffic in Arms Regulations）对 DES 加密算法的出口管制条款（1980 年代末至 1990 年代）；Salus, P. (1994) "A Quarter Century of UNIX"（含 Kerberos 集成争议的二手叙述）；McKusick et al. 1996《4.4BSD 操作系统设计与实现》中关于 4.3BSD-Reno 至 4.4BSD 安全机制演化的叙述 ［A］
- 史观：第 2 条形式主义——Kerberos v4 的“集中式 KDC 票据认证”形式逻辑在小型站点运维现实与 US Export Control 法律限制下遭遇工程实践阻力，形式主义膨胀被实践约束修正；第 24 条许可证——US Export Control 对 DES 的出口管制是许可证与法律约束对 BSD 代码分发的直接干预，使 BSD 须维护含 Kerberos 与不含 Kerberos 两个版本
- 辨析：KDC 部署复杂性“使 Kerberos 在小型站点实际不可部署”须区分“完全不可部署”与“运维负担过重”——小型站点技术上可部署 KDC 但运维成本高，须避免将“运维负担重”夸大为“完全不可部署”；US Export Control 对 DES 的出口管制须区分“BSD 源代码国际分发受限”与“BSD 源代码美国国内分发受限”——ITAR 主要限制国际出口，美国国内分发不受影响，CSRG 需维护两个版本以应对国际分发限制；Kerberos 与 `~/.rhosts` 的“兼容性问题”须区分“同时支持两种模式”与“认证策略不一致”——Reno 网络服务同时支持两种模式是兼容性设计，但混合部署导致的认证策略不一致是运维问题而非设计缺陷；三个争议焦点的相对权重在不同史料中描述详略不一，须核对 `unix-wizards` 邮件列表存档确认社区讨论的实际焦点

## 37.6.3 Kerberos 在 BSD 中的长期边缘化与 ssh(1) 的替代路径
- 要点：三个争议焦点使 Kerberos v4 在 BSD 中长期作为可选组件而非默认启用——4.4BSD（**1994**）与 4.4BSD-Lite（**1994**）保留 Kerberos v4 作为可选组件，FreeBSD 1.0-3.x（**1993-2000**）与 NetBSD 早期版本继承 BSD 单文件 `/etc/passwd` 格式与 `~/.rhosts` 信任链作为默认远程认证机制，Kerberos 仅作为可选组件存在；BSD 实际的远程认证主流是 **1995 年** Tatu Ylönen 发布的 **ssh(1)**（SSH 1.0），**ssh(1)** 基于公钥加密与对称加密混合体制，无须 KDC 集中式基础设施，部署门槛远低于 Kerberos，且不受 US Export Control 对 DES 的出口管制（SSH 1.0 使用 RSA 与 IDEA 等算法，后续 OpenSSH 使用 Blowfish、AES 等），快速取代 `~/.rhosts` 信任链成为 BSD 与 Linux 的远程认证主流；MIT Kerberos v5 与 RFC 1510（**1993 年 9 月** 由 Kohl & Neuman 发布的"The Kerberos Network Authentication Service (V5)"）标准化后，Kerberos v5 逐步解决 v4 的部分争议（如 KDC 部署简化、加密算法可插拔），但 BSD 社区已选择 **ssh(1)** 作为远程认证主流，Kerberos 直至 FreeBSD 5.x（**2003 年**）才作为默认可选组件；Kerberos 在 BSD 中的长期边缘化反映了 BSD 社区对认证基础设施的审慎态度——优先选择部署门槛低的 **ssh(1)** 而非安全性理论更强但部署复杂的 Kerberos

| 认证机制 | 引入年份 | 部署门槛 | BSD 中的地位 | 主要优势 |
| --- | --- | --- | --- | --- |
| `~/.rhosts` 信任链 | 4.1BSD（1981） | 极低（无 KDC） | 1995 年前的默认机制 | 部署简单 |
| Kerberos v4 | 1988（MIT）/ 1990（Reno 集成） | 高（需 KDC） | 4.4BSD 起可选组件 | 集中式票据认证，安全性理论强 |
| Kerberos v5（RFC 1510） | 1993.9 | 中（简化部署） | FreeBSD 5.x（2003）起默认可选 | 部分解决 v4 争议 |
| **ssh(1)**（SSH 1.0） | 1995 | 低（无 KDC） | 1990 年代末取代 `~/.rhosts` | 公钥加密，部署门槛远低于 Kerberos |
| OpenSSH | 1999 起 | 低 | OpenBSD 主导，BSD/Linux 主流 | 无 DES 出口管制问题（Blowfish/AES 等） |

(1995) SSH 1.0 发布记录与 RFC 系列文档；Kohl, J. & Neuman, C. (1993.9) RFC 1510"The Kerberos Network Authentication Service (V5)"；OpenSSH 发布记录（1999 年起，OpenBSD 项目主导）；FreeBSD 5.x Release Notes (2003) 中 Kerberos v5 默认可选组件说明 ［A］
- 史观：第 9 条经验优先——BSD 社区选择 **ssh(1)** 而非 Kerberos 是实践驱动而非理论先行，**ssh(1)** 的部署门槛优势在工程实践中压倒 Kerberos 的安全理论优势；第 2 条形式主义——Kerberos 的“集中式 KDC 票据认证”形式逻辑在 **ssh(1)** 的“分布式公钥认证”形式逻辑竞争下边缘化，两种形式主义的竞争以部署门槛为裁决标准
- 辨析：Kerberos 在 BSD 中“长期边缘化”须区分“完全弃用”与“作为可选组件保留”——Kerberos 在 BSD 中持续作为可选组件保留至现代（FreeBSD 当代版本仍支持 Kerberos v5），但从未成为默认远程认证机制，须区分“可选保留”与“主流采纳”；**ssh(1)** 取代 `~/.rhosts` 信任链的时间须区分“SSH 1.0 发布（1995）”与“SSH 广泛采纳（1990 年代末至 2000 年代初）”——SSH 1.0 发布后仍需数年才广泛取代 `~/.rhosts`，须避免将“发布”等同于“取代”；FreeBSD 5.x（2003）将 Kerberos v5 作为默认可选组件须区分“默认可选”与“默认启用”——FreeBSD 5.x 提供 Kerberos v5 作为安装时可选组件但非默认启用，须区分“可选组件”与“默认启用”；Kerberos v5 与 RFC 1510“解决 v4 部分争议”须谨慎判断——v5 确实简化了 KDC 部署与加密算法可插拔，但 KDC 集中式基础设施的根本复杂性仍存在，须区分“部分解决”与“完全解决”
