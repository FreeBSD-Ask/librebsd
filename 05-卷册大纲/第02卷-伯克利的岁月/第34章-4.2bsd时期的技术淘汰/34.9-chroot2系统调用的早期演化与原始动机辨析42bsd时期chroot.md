## 34.9.2 4.2BSD 网络栈引入后的远程漏洞面扩大

**要点**：4.2BSD（1983 年 8 月）引入完整的 TCP/IP 网络栈（4.2BSD sockets API、**sendmail(8)**、**fingerd(8)**、**rlogind(8)**、**rshd(8)** 等网络服务），使 BSD UNIX 从本地分时系统转型为网络化多用户系统，远程漏洞面随之扩大；4.2BSD 网络栈引入后的远程漏洞面集中在三类：(1) **sendmail(8)** DEBUG 命令——用于调试邮件传递，但允许远程执行任意命令；(2) **fingerd(8)** 使用 `gets` 函数读取输入——无边界检查，存在缓冲区溢出；(3) `~/.rhosts` 信任链——允许用户在可信主机上无需密码登录，但 DNS 欺骗与 IP 伪造可绕过信任链；这三类漏洞为 Morris 蠕虫（1988 年 11 月）得以快速扩散的史源背景，反映了 1980 年代 BSD 社区对网络化威胁的低估与漏洞响应机制的缺失

**史料**：4.2BSD Release Notes (1983.8)；4.2BSD 网络源代码（含 **sendmail(8)**、**fingerd(8)**、**rlogind(8)**、**rshd(8)** 实现）；Spafford E H. The Internet Worm Program: An Analysis [R]. Purdue University CSD-TR-823, 1988；CERT/CC CA-1988:01 公告；Bellovin S M. The Internet Worm and the FTP Security Workshop [R]. AT&T Bell Laboratories, 1989 ［A］

**史观**：第 2 条形式主义——**sendmail(8)** DEBUG 命令是形式主义便利（开发期调试）吞并安全实质，形式便利膨胀为安全灾难；第 17 条软件工程——网络栈引入后的远程漏洞面扩大反映了软件工程中“功能引入优先于安全审计”的普遍问题

**辨析**：4.2BSD 网络栈引入后的远程漏洞面在 Morris 蠕虫爆发前已为 BSD 社区知晓但未系统化修补，须区分“已知漏洞”与“系统化修补”——漏洞已知但修补机制缺失是 1980 年代 BSD 社区安全文化的真实状态；**sendmail(8)** DEBUG 命令、**fingerd(8)** 缓冲区溢出、`~/.rhosts` 信任链均为 Morris 蠕虫爆发前 BSD 与 Research UNIX 中长期存在的已知缺陷，非 Morris 蠕虫后才发现；4.2BSD 时期的远程漏洞面是 BSD 安全史从“本地多用户安全”扩展到“网络化远程安全”的关键转折，须区分“本地安全模型”（root + rwx + setuid）与“网络安全模型”（缺失）

## 34.9.3 4.2BSD TCP/IP 实现与 RFC 791/793 标准的具体偏差及 RFC 1122（1989）修正条款

**要点**：4.2BSD（1983.8）作为 TCP/IP 协议的事实参考实现，其代码在 RFC 791（IP，1981.9）与 RFC 793（TCP，1981.9）发布后仅两年即发布，部分实现细节与 RFC 标准文本存在偏差；IETF 于 1989 年 10 月发布 **RFC 1122**《Requirements for Internet Hosts -- Communication Layers》（Editor: R. Braden，URL: <https://www.rfc-editor.org/rfc/rfc1122.txt>，Status: Internet Standard STD 3，Updates: RFC 793，Updated by: RFC 1349、RFC 4379、RFC 5884、RFC 6093、RFC 6298、RFC 6633、RFC 6864、RFC 8029、RFC 9293）系统性修正并补充了主机协议实现要求，其中 TCP 部分的修正条款直接对应 4.2BSD 时期实现的具体偏差；4.2BSD TCP/IP 实现与 RFC 791/793 标准的具体偏差及 RFC 1122 对应修正条款可归纳为以下五项

- **偏差 1：紧急指针计算口径（RFC 1122 §4.2.2.4）**——RFC 793 §3.1 原文"the urgent pointer points to the sequence number of the octet following the urgent data"规定紧急指针指向紧急数据后的下一个字节，即紧急数据最后一字节序号 = SEQ + Urgent Pointer − 1；4.2BSD 实现沿用了 RFC 793 这一原始定义（即“LAST+1”口径），将紧急指针解释为指向紧急数据后下一字节；**RFC 1122 §4.2.2.4** 显式修正了 RFC 793 的错误，原文"The second sentence is in error: the urgent pointer points to the sequence number of the LAST octet (not LAST+1) in a sequence of urgent data"，即规定紧急数据最后一字节序号 = SEQ + Urgent Pointer（无 −1 修正）；BSD 历史实现因此与 RFC 1122 修正条款冲突，导致带外数据（Out-of-Band Data）在 BSD 与非 BSD 实现间存在互操作问题；后续 RFC 6093（2011）“On the Implementation of the TCP Urgent Mechanism”进一步澄清了该问题，Linux 通过 **TCP_URGENT_POINTER_TYPE** 套接字选项（参见 Linux `man 7 tcp`）允许在 RFC 793 与 RFC 1122 两种解释间切换，BSD 派生系统（含 macOS）默认保留 RFC 793 原始口径，长期未修正
- **偏差 2：MSL 与 TIME_WAIT 超时（RFC 1122 §4.2.2.13）**——RFC 793 §3.8 规定 MSL（Maximum Segment Lifetime）为 2 分钟，TIME_WAIT 状态持续 2×MSL = 4 分钟；4.2BSD 实现将 MSL 硬编码为 30 秒（定义于 `netinet/tcp_timer.h` 的 `TCPTV_MSL` 宏），TIME_WAIT 状态因此仅持续 60 秒，是 RFC 793 建议值的 1/4；**RFC 1122 §4.2.2.13** 重申 MSL 应为 2 分钟的建议，但承认实现可配置（原文"the values for MSL and 2*MSL are fixed by the protocol specification; an implementation may choose to use smaller values, but must be prepared to deal with the consequences"），即 BSD 的 30 秒 MSL 虽偏离建议值但不违反协议规范；该偏差延续至现代 BSD 派生系统（FreeBSD `net.inet.tcp.msl` 默认 30000 ms、macOS `net.inet.tcp.msl` 默认 30000 ms），Linux 早期亦采用 30 秒，后通过 `net.ipv4.tcp_fin_timeout` 可配置
- **偏差 3：TCP Keep-Alive 机制（RFC 1122 §4.2.3.6）**——RFC 793 未定义 Keep-Alive 机制，Keep-Alive 不是 TCP 协议规范的组成部分；4.2BSD 实现了 TCP Keep-Alive 作为工程扩展（通过 `SO_KEEPALIVE` 套接字选项启用），用于检测对端崩溃或网络中断导致的半开连接；**RFC 1122 §4.2.3.6** 将 Keep-Alive 列为“可选”功能（MAY 级别），原文“a TCP MAY implement keep-alive”，并规定若实现必须满足三项条件：(1) 默认关闭，(2) 仅在连接已空闲一段时间后发送，(3) 探测段必须允许 RST 响应；4.2BSD Keep-Alive 实现符合 RFC 1122 §4.2.3.6 的三项条件，但 BSD 后续版本（4.3BSD Reno、4.4BSD）默认参数（间隔 2 小时、重试 9 次）与 RFC 1122 建议值存在差异
- **偏差 4：零窗口探测机制（RFC 1122 §4.2.2.17）**——RFC 793 §3.7 提及零窗口情况但未规定探测机制的具体实现要求；4.2BSD 实现了零窗口探测（Zero Window Probing），即当对端通告零窗口后定期发送 1 字节探测段以触发对端窗口更新；**RFC 1122 §4.2.2.17** 规范化了该机制，要求“MUST implement zero-window probing”并规定探测间隔应使用指数退避（exponential backoff），4.2BSD 实现符合该要求但早于 RFC 1122 六年发布，其探测间隔参数（初始 1 秒、最大 60 秒）与 RFC 1122 建议范围一致
- **偏差 5：重传超时计算（RFC 1122 §4.2.3.1）**——RFC 793 §3.7 规定重传超时（RTO）应基于往返时间（RTT）测量动态计算但未给出具体算法；4.2BSD 实现采用 Phil Karn 与 Van Jacobson（范·雅各布森） 提出的 RTT 估算算法（Karn-Jacobson 算法），即通过加权移动平均计算平滑 RTT（SRTT）与 RTT 方差（RTTVAR），RTO = SRTT + 4×RTTVAR；**RFC 1122 §4.2.3.1** 采纳了该算法作为建议标准，原文"the following simple algorithm was described in [Jacobson88a] and is recommended for use“；后续 **RFC 6298**（2011）”Computing TCP's Retransmission Timer"对该算法进一步标准化，4.2BSD 的原始实现因此成为 IETF 标准算法的史源基础

**史观**：第 9 条经验优先——4.2BSD TCP/IP 实现作为工程先于标准的典型案例，反映了 BSD 工程实践“先实现后标准化”的传统，5 项偏差中有 4 项（Keep-Alive、零窗口探测、Karn-Jacobson 算法、紧急指针口径）后被 RFC 1122 采纳或修正，证明 BSD 实现是 IETF 标准的史源基础；第 6 条技术路线分化——BSD 的“工程优先”路径与 ISO/CCITT 的“标准优先”路径形成对比，BSD 路线最终通过 IETF 主导了互联网协议标准化
