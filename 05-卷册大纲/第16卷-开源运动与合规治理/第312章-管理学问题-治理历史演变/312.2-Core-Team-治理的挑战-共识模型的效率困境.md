# 312.2 Core Team 治理的挑战——共识模型的效率困境

## 312.2.1 共识决策模型与社区规模扩张的张力

**要点**：FreeBSD Core Team 采用共识决策模型，9 名成员（2020 年代）须就重大决策达成共识；共识模型在社区规模小（1990 年代 committer 约 50 人）时高效，但随 committer 数量增长至 400+ 人后决策效率下降；5.x 系列发布延迟（FreeBSD 5.0 延迟至 2003 年 1 月 19 日发布）是共识模型效率困境的典型案例；2022 年 Core Team 选举制度改革引入 “先投票选出 2 名候选人再由 Core Team 内部补选” 的流程，部分回应效率批评

**史料**：freebsd-core 邮件列表存档、Core Team 选举记录、FreeBSD 5.0 release engineering 讨论存档、2022 年 Core Team 选举改革公告 ［A］

**史观**：总纲第 22 条——社区治理，共识模型的效率困境是社区规模扩张与治理结构滞后之间的张力

**辨析**：5.x 延迟的具体原因需区分技术因素（SMPng 重构）与管理因素（共识决策）；Core Team 人数变化需考据；2022 年选举改革的具体内容与效果需跟踪

**文献**：FreeBSD Core Team. (2020-2025). *Core Team Reports*. lists.freebsd.org; Glass, R. L. (2002). *Facts and Fallacies of Software Engineering*. Addison-Wesley; O'Mahony, S. (2007). *The Governance of Open Source Projects: Does It Influence Innovation?* Journal of Management and Governance, 11(2), 123-146. ［A］

**要点**：

- 五位 core 团队成员（Warner Losh、George Neville-Neil、Hiroki Sato、Robert Watson、Brooks Davis）在 BSDCan 2007 集体口述治理制度：core 由拥有源码提交权的开发者选举产生，九人，其历史形态曾是项目关键中央开发者的自我遴选集合，约六年前改为选举制，受访时为第四届选举 core；Watson 与 Losh 自首届选举 core 起连任，Sato 主责文档与 ports 工程并担任日本与亚洲联络。core 的实际职能包括冲突解决、新 committer 的批准投票、开发者峰会与 BSD 会议的组织、新成员导师制，以及面向用户与厂商的对外代表职能。　[存疑脚注] 转写作“Werner Walsch”“I am a product of Tokyo Quantum member”，应为 Warner Losh 与 Hiroki Sato（东京）（BSDTalk EP114，[69.95-118.3, 147.37-181.67, 386.27-455.37]，L1）　[订正：原转写作“Werner Losh”“Hiroki Satolom Tokyo”，2026-09-29 SenseAudio 重转核对]
- 关于决策风格，当事人给出明确的共识制辩护：批准新 committer 时的投票绝非最高法院式五比四——到达表决环节时人选早已通过提交补丁、邮件列表讨论等显于社区，core 在此意义上近乎橡皮图章；core 内部从无超过八比一或七比一的分裂，因为成员会先花时间达成最能代表项目需求的共识，其前提是成员把项目利益置于个人议程之上。技术取舍则尽量下放：ZFS 是否进入 FreeBSD 7 由 release engineering 团队裁量，core 仅在法律、许可证或代码所有权争议出现时介入，原则是“间接力用尽、直接力最少”。（BSDTalk EP114，[414.53-499.65, 1025.66-1123.45]，L1）
- 透明度制度有具体机制支撑：core 以约月度频率发布 core report，约九成议题（含表决与结果）公开，唯受保密协议约束的公司往来与法律事项除外；首任 core secretary 确立“抵制清除冲动”（resist the urge to purge）原则——默认公开、私有为例外，即使内容令个别人或项目难堪亦予公开，因为社区需要好坏兼备的平衡图景；项目几乎无私有邮件列表（仅 core 与 release engineering 保留），且主动劝阻私有化，将争议引回 arch、net 等公开列表；“人们讨厌意外甚于讨厌坏消息”是贯穿的原则表述。项目另设非选举的 secretary 一职，记录全部议题并催办搁置事项，被喻为“core 的记忆”乃至 core 的驱动者。（BSDTalk EP114，[593.25-760.17, 345.05-385.91]，L1）
- 法律结构方面，当事人澄清：core team 与 FreeBSD 项目本身均无法律实体，唯 FreeBSD Foundation 作为独立组织承担签约与法律职能——如 Java 再分发协议、接受 Cisco 与 Coverity 等公司捐赠、代购硬件；开发者始终以个人身份获得提交权而非其雇主，公司通常与硬件厂商签署保密协议后出资雇人开发驱动、再由开发者个人提交入树，Intel 等公司雇员亦以此路径获得提交权；Watson 本人兼具 Foundation 董事与 core 成员两顶“帽子”。项目治理自 core 向下授权给一系列具章程的团队（release engineering、security、ports 管理），core 的角色被自嘲为“赶猫”——确保方向大致正确、发现被忽视的工作、保障成员互不知情的意外最少化。（BSDTalk EP114，[1218.0-1378.21, 1146.4-1173.09, 1173.88-1216.61]，L1）
- 技术路线口述要点：FreeBSD 7 计划于 2007 年夏发布，核心亮点为万兆网络性能、ZFS 与 SCTP，并明确“不存在秘密特性”——那不符合开源的公开流程；特性回移呈双向流动：先在 6.x 开发、送入 CURRENT 成熟、再回移 6.x，ZFS 因依赖新内核接口而不回移，SMP 扩展性工作因需底层根本性改动、对生产分支风险过大而不回移，内核 ABI 跨主分支保持兼容；5.x、6.x、7.x/CURRENT 三支并行的发布谱系分别服务安全维护、生产部署与前瞻开发——ISP 偏好久经考验的旧分支（数千台机器无法一夜升级），设备厂商则基于最新分支开发以期半年一年后上市；新架构方面正在引入 MIPS 并扩展 PowerPC 与 ARM 的片上系统支持，策略是与芯片厂商建立发布前的信息管道以求领先而非追赶。（BSDTalk EP114，[1768.5-1894.33, 1861.0-1880.31, 1921.85-1988.67, 2025.17-2058.95]，L1）

**史料**：

- 该期附带保存数条治理史细节：core 九人来自五个国家、分布跨约十四个时区，日常以邮件与 IRC 协作、会议凑法定人数，全员同地聚会可上溯至 2000 年蒙特雷 BSDCon；core 建制前存在“drive-by commit”（突袭式提交）问题，core 介入要求先公开讨论后已显著改善；围绕 FreeBSD 的开发者已有约三百人并继续增长。（BSDTalk EP114，[763.43-849.47, 219.44-234.91, 1430.64-1435.44]，L1）

**史观**：

- 总纲13 法律与道德是利益分配：关于章程设计，当事人披露一种自觉的反法律文书化立场：FreeBSD bylaws 公开发布，但刻意不写成可供钻营的法律文件——详列细则只会诱使成员组合条款自证其利，而宽泛的原则性表述促使人们思考“什么对项目最好”；治理模型本身系参照美国政府宪法与欧洲政制自行拼合，并以极低摩擦为第一原则，因为全员志愿者经不起程序性内耗。规则在此被理解为利益分配框架，其形态设计直接决定共同体内部斗争的形态。（BSDTalk EP114，[290.85-332.17, 852.39-913.95]，L1）

**辨析**：

- 关于可扩展性，当事人给出三层论证：其一，提交权限已从早期的全员同权分化为源码、文档、ports 专项，以控制成员的信息负荷与信噪比，且这种责任分离并未形成层级——一切“全关乎尊重”，源码作者并不高于文档作者；其二，项目周边已自然生长出 PC-BSD、FreeNAS、DesktopBSD 等衍生项目，构成项目组织之外的增长路径；其三，防止巴尔干化的机制是成员普遍脚踏多个领域，形成交联社区。当事人并直指电子邮件是极糟糕的沟通载体、多语种成员以英语沟通加剧误解，而让独立思考者协作本身即为开源治理的核心难题；其引 Kirk McKusick 的名言概括志愿劳动的结构性约束——工作、吃饭、睡觉之后项目总排在最后。（BSDTalk EP114，[966.29-1009.97, 1535.61-1662.19, 1716.79-1746.19, 332.79-344.01]，L1）
