- 关于决策风格，当事人给出明确的共识制辩护：批准新 committer 时的投票绝非最高法院式五比四——到达表决环节时人选早已通过提交补丁、邮件列表讨论等显于社区，core 在此意义上近乎橡皮图章；core 内部从无超过八比一或七比一的分裂，因为成员会先花时间达成最能代表项目需求的共识，其前提是成员把项目利益置于个人议程之上。技术取舍则尽量下放：ZFS 是否进入 FreeBSD 7 由 release engineering 团队裁量，core 仅在法律、许可证或代码所有权争议出现时介入，原则是“间接力用尽、直接力最少”。（BSDTalk EP114，[414.53-499.65, 1025.66-1123.45]，L1）
- 透明度制度有具体机制支撑：core 以约月度频率发布 core report，约九成议题（含表决与结果）公开，唯受保密协议约束的公司往来与法律事项除外；首任 core secretary 确立“抵制清除冲动”（resist the urge to purge）原则——默认公开、私有为例外，即使内容令个别人或项目难堪亦予公开，因为社区需要好坏兼备的平衡图景；项目几乎无私有邮件列表（仅 core 与 release engineering 保留），且主动劝阻私有化，将争议引回 arch、net 等公开列表；“人们讨厌意外甚于讨厌坏消息”是贯穿的原则表述。项目另设非选举的 secretary 一职，记录全部议题并催办搁置事项，被喻为“core 的记忆”乃至 core 的驱动者。（BSDTalk EP114，[593.25-760.17, 345.05-385.91]，L1）
- 法律结构方面，当事人澄清：core team 与 FreeBSD 项目本身均无法律实体，唯 FreeBSD Foundation 作为独立组织承担签约与法律职能——如 Java 再分发协议、接受 Cisco 与 Coverity 等公司捐赠、代购硬件；开发者始终以个人身份获得提交权而非其雇主，公司通常与硬件厂商签署保密协议后出资雇人开发驱动、再由开发者个人提交入树，Intel 等公司雇员亦以此路径获得提交权；Watson 本人兼具 Foundation 董事与 core 成员两顶“帽子”。项目治理自 core 向下授权给一系列具章程的团队（release engineering、security、ports 管理），core 的角色被自嘲为“赶猫”——确保方向大致正确、发现被忽视的工作、保障成员互不知情的意外最少化。（BSDTalk EP114，[1218.0-1378.21, 1146.4-1173.09, 1173.88-1216.61]，L1）
- 技术路线口述要点：FreeBSD 7 计划于 2007 年夏发布，核心亮点为万兆网络性能、ZFS 与 SCTP，并明确“不存在秘密特性”——那不符合开源的公开流程；特性回移呈双向流动：先在 6.x 开发、送入 CURRENT 成熟、再回移 6.x，ZFS 因依赖新内核接口而不回移，SMP 扩展性工作因需底层根本性改动、对生产分支风险过大而不回移，内核 ABI 跨主分支保持兼容；5.x、6.x、7.x/CURRENT 三支并行的发布谱系分别服务安全维护、生产部署与前瞻开发——ISP 偏好久经考验的旧分支（数千台机器无法一夜升级），设备厂商则基于最新分支开发以期半年一年后上市；新架构方面正在引入 MIPS 并扩展 PowerPC 与 ARM 的片上系统支持，策略是与芯片厂商建立发布前的信息管道以求领先而非追赶。（BSDTalk EP114，[1768.5-1894.33, 1861.0-1880.31, 1921.85-1988.67, 2025.17-2058.95]，L1）
