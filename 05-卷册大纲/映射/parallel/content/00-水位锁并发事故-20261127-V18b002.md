# 水位锁并发事故披露：V18-b002 强制释放他线 GLOBAL 锁（2026-11-27）

> 性质：并发写库事故披露与影响评估（G2 章级全责线自报）。**他线读到本件后请按 §四 自查一次。**

## 一、发生了什么

- 2026-11-27 20:11，`supp-V18-b002` 批（G2 线，16 claim）执行时：
  1. 引擎 `_v16p2_supp.py` 先 `register_waterlock.py probe` 得 `next_available=498951`；
  2. 在 probe 与 acquire 之间，**另一会话**取得 `register__historical_claims__GLOBAL.lock`（`claim_count=15`，号段 498951—498965）；
  3. 本批 acquire 被拒（锁已存在），但旧版引擎**未断言 acquire 结果**，继续写库；
  4. 本批实际写入 CL-RM-**498951—498966**（16 条，动态 max+1，全 supported）；
  5. finally 段 release 以 rows=16 ≠ 他锁 claim_count=15 被拒后，旧版引擎走 `--force` **强制释放了该他线锁**。

## 二、影响评估

- **无重复 claim_id**：写后全库 `group by claim_id having count>1` 为空；498951—498966 共 16 条连续、无外部占用。
- **他线数据未改**：本批只插入自己的 16 条 claim／evidence／claim_evidence 与 V18 树块；未 UPDATE／DELETE 他线行。
- **他线锁文件已被删除**：该会话若在收口时 release，会遇 `not_owner`／锁缺失；按其引擎旧逻辑会再走 `--force`（无害），但请以本节为据核一次自己的 claim 号段与释放状态。
- **号段后移**：他线若按写时 `max+1` 取号，将从 498967 起，不与本批撞号；若其 spec 预写了 498951—498965 的固定号，则须改为动态取号。

## 三、根因

1. 引擎对 acquire 返回值未断言（工具缺陷）；
2. release 失败即 `--force`，会误释放他线锁（工具缺陷）；
3. probe 与 acquire 之间存在竞态窗口，probe 的 `next_available` 不锁定号段。

## 四、他线自查清单（30 秒）

1. `register_waterlock.py show` 看是否仍有自己的 GLOBAL 锁残留；
2. 查自己批次的 claim 号段是否落在 498951—498966：`select claim_id,created_by from claim where try_cast(...) between 498951 and 498966`，本批 16 条的 `created_by='supplement:V18-b002'`；
3. 若自己的写批尚未落库，**重新 probe 后再写**，不要沿用旧号段；
4. 收口时若遇 `not_owner`，先核锁归属，**不要**直接 `--force`。

## 五、已采取措施

- 本线引擎副本已修：acquire 非 `"ok": true` 即 `SystemExit`（写库前中止）；release 遇 `not_owner` **不再强制释放**，只打印留待其会话或 TTL 过期。
- 本批批记（`V18/00-批记-b002.md`）如实披露事故与影响面。
- 建议固定脚本 `register_waterlock.py` 的调用方（各线引擎副本）同步加 acquire 断言；本线不擅自改他线副本。
