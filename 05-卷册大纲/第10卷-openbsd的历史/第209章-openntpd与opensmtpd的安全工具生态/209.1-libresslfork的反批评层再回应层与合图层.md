# 209.1 LibreSSL fork 的反批评层、再回应层与合图层

**要点**：本节补足 LibreSSL fork 的四层辩证链，呈现 LibreSSL 阵营对 OpenSSL 阵营批评的反批评、OpenSSL 阵营对反批评的再回应，以及二者长期演进的合图层；反批评层——LibreSSL 主导者 Ted Unangst（<tedu@openbsd.org>）于 EuroBSDCon 2014 演讲“LibreSSL: More Than 30 Days Later”中系统反驳 OpenSSL 阵营的批评，可归纳为四条线索；第一，Unangst 明确“LibreSSL is not the result of ‘the worst bug ever’”，LibreSSL fork 并非因单一 Heartbleed 漏洞，而是因“tragic comedy of other errors”（一连串错误的悲喜剧）——heartbeats 功能仅对 DTLS over UDP 有用却被默认编入 TLS over TCP、缓冲区分配器与 freelists 与漏洞利用缓解措施冲突、持续挖掘后“we keep on not liking what we're seeing”，fork 决策是代码质量与治理结构双重问题的累积结果而非对单一漏洞的过激反应；第二，Unangst 以 `FIONBIO` 与 `socklen_t` 两例证实 OpenSSL 代码质量问题的具体性——`FIONBIO` 例展示 OpenSSL 在 POSIX 系统上仍因头文件包含遗漏而意外回退到“crappy workaround”，`socklen_t` 例展示 OpenSSL 不直接声明 socklen_t 变量而是"create a union of a couple different ints, call accept(), then inspect the different union members to determine which ones were overwritten by the kernel"（创建一个包含几种 int 的联合体，调用 accept()，然后检查哪些联合体成员被内核覆写），并需检查大小端，此类代码并非“兼容性必要”而是工程缺陷；第三，Unangst 以 SRP（Secure Remote Password）时间线证实 OpenSSL 发布流程的问题——2014-05-05 LibreSSL 移除 libssl SRP 代码，2014-07-02 OpenSSL 收到 libssl SRP 崩溃漏洞报告（非公开），2014-07-28 LibreSSL 移除 libcrypto SRP 代码并在 commit message 中提示“hey there's a bug in here, but the details are secret”，2014-07-31 研究者在 libcrypto SRP 代码中发现远程可利用缓冲区溢出，2014-08-06 OpenSSL 1.0.1i 发布含约 12800 行 diff 的 jumbo 安全补丁，2014-08-08 用户报告升级后 SRP 失效——补丁本身被破坏且无人测试，Unangst 据此论证“don't drop jumbo security patches on users”（不要向用户倾倒巨型安全补丁），LibreSSL 通过分批发布避免此类回归；第四，Unangst 明确 LibreSSL 的演化路线——"The first 30 days were all about revolution. Now we've switched into evolution mode“（前 30 天是革命，现已转入演化模式），LibreSSL 不是冻结而是”apply the brakes"（踩刹车）以呈现更小攻击面，同时新建 ressl（Reimagined SSL）API 替代 OpenSSL API，ressl 不暴露 OpenSSL 类型与函数、不暴露 X.509 与 ASN.1 实现细节、默认启用 hostname 验证，旨在“break the monoculture”（打破单一文化）；再回应层——OpenSSL 阵营对 LibreSSL 反批评的再回应可归纳为四条线索；第一，OpenSSL 2014-07 路线图坚持改革路线，承认缺乏代码审查、不一致编码风格、糟糕文档、无平台战略、无定期发布周期五个问题但批评外界认为 OpenSSL“发展非常缓慢并且孤立”的观点，这是对 LibreSSL 阵营“代码质量系统性问题”叙事的再回应——承认问题但拒绝 fork 路线；第二，Linux Foundation 联合 Red Hat、Google、Microsoft、Facebook、IBM、Intel、Cisco、AWS 等公司于 2014-04 发起 Core Infrastructure Initiative（CII），每年向 OpenSSL 等关键开源项目提供数百万美元资助，CII 选择资助 OpenSSL 而非 LibreSSL，反映资金方对“改革原项目”路线的偏好——市场事实本身构成对 LibreSSL 革命路线的再回应；第三，安全研究员 Andrew Ayer 于 2014-10 前后发现 LibreSSL portable 在 Linux 上的伪随机数生成器（PRNG）实现存在“灾难性失败”——16 位 PID 在多进程间重复导致 PRNG 状态可预测，OpenSSL 阵营据此质疑 LibreSSL 在非 OpenBSD 平台的可靠性，这是对 LibreSSL 阵营“OpenBSD 上使用 arc4random 不受影响”辩护的再回应——portable 版本的问题证明 LibreSSL 的“简洁优先”路线在 OpenBSD 之外的平台上存在具体可靠性代价；第四，Google 于 2014 年发起 BoringSSL 作为 OpenSSL 的 fork，Google 选择自行 fork OpenSSL 而非采用 LibreSSL，反映 LibreSSL 的 API 兼容性局限与 OpenSSL 生态的路径依赖——即使认同 OpenSSL 代码质量问题的主体也未必选择 LibreSSL 路线，BoringSSL 的存在本身即是对 LibreSSL“打破单一文化”叙事的再回应；合图层——LibreSSL fork 与 OpenSSL 改革在 2014-2024 年间各自呈现，并非零和博弈；LibreSSL 在 OpenBSD 生态内成功（自 5.6 起默认）但 portable 版本采用率低，OpenSSL 经 CII 资助后代码质量显著改善（1.1.0 重构、1.1.1 LTS、3.0 重构）但保留原代码库与 API 兼容；LibreSSL 推动的 arc4random 一致化、libtls API、hostname 验证默认化等理念部分被 OpenSSL 与 BoringSSL 吸收，OpenSSL 改革成果亦被 LibreSSL 部分采纳（如 TLS 1.3 支持）；二者在长期演进中达成“各主体呈现与和解”的格局，争议的不可调和性体现在 LibreSSL portable 在 Linux 上的采用率长期低于 1% 且未逆转，但和解路径体现在二者共享 TLS 协议规范与部分加密原语实现

**史观**：总纲第 21 条——革命与改革是历史方法论的分歧：LibreSSL fork 是革命路线（彻底删除 70,000 行代码、移除 SSLeay 兼容层、新建 libtls/ressl API），OpenSSL CII 资助 + 路线图重构是改革路线（保留代码库、渐进改善代码审查与发布周期），Unangst 演讲中“revolution”到“evolution mode”的表述自认革命路线，OpenSSL 路线图承认问题但拒绝 fork 路线即自认改革路线，二者构成历史方法论分歧——革命路线破山中贼易（一次性删除代码）但破心中贼难（让 Linux 发行版接受 LibreSSL），改革路线破山中贼难（在原代码库上渐进改善）但破心中贼易（保留与下游的兼容性）；总纲第 19 条——解释学循环是历史认识的根本条件：Unangst 以“审计文化 + 简洁优先”为前理解（“we gutted the junk”、“apply the brakes”即为先前理解的显现），OpenSSL 阵营以“功能完整性 + 生态稳定”为前理解（路线图承认问题但拒绝 fork 即为先前理解的显现），两类前理解不可通约使分歧不可避免，权力与知识在历史书写中共谋——LibreSSL 演讲由 OpenBSD 开发者作，OpenSSL 路线图由 OpenSSL 项目书写，CII 资金分配由 Linux Foundation 与大型科技公司决定，各方叙事均倾向自身立场；总纲第 13 条——法律与道德是利益分配：CII 选择资助 OpenSSL 而非 LibreSSL 反映利益分配——fork 后 OpenSSL Software Foundation 的资金来源与影响力将受威胁，CII 资金的分配依赖 OpenSSL 项目的持续存在，“资助原项目”的改革路线偏好本身就是利益分配的形式主义化
