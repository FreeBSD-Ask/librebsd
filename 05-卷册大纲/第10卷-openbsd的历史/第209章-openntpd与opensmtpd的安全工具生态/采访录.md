### OpenBSD 安全工具生态建设者（2004-2026 时期当事人）

#### 采访 1：Bob Beck

**字段 1 采访元数据**

- 受访者：Bob Beck，时任 OpenBSD 核心开发者，LibreSSL 项目发起人
- 采访者：无（BSDCan 学术会议演讲）
- 采访时间：2014-05（BSDCan 2014）
- 采访形式：学术会议演讲（一手会议产出）
- 原始来源：Beck B. LibreSSL - The first 30 days and the Future [C]//BSDCan 2014. Ottawa: BSDCan, 2014 [2026-07-23]. **<https://www.openbsd.org/papers/bsdcan14-libressl>**
- 存档信息：原始 URL 经联网核实可访问（访问日期 2026-07-23），未失效

**字段 2 采访摘要**

Beck 在 BSDCan 2014 发表 LibreSSL fork 自 OpenSSL 后首月工作综述与未来路线图演讲，源于 2014 年 4 月 OpenSSL Heartbleed（CVE-2014-0160）漏洞后的紧急响应。LibreSSL fork 初期工程决策包括首周删除约 9 万行代码、全面应用 OpenBSD 安全审计流程、移除遗留的旧平台兼容代码。Beck 亦介绍 LibreSSL 的未来路线图：先在 OpenBSD 上稳定运行，再考虑多平台支持。

**字段 3 考据脚注**

本则会议演讲经 OpenBSD 官方 events 页面核实，slides 真实可访问（访问日期 2026-07-23）。Beck 关于 LibreSSL fork 初期工程决策的陈述属当事人一手自述，已作自利偏差审查。Heartbleed CVE-2014-0160 须经 CVE 数据库与 OpenSSL 官方公告交叉验证。openbsd.duckdb openbsd-src 仓库 LibreSSL fork commit b6553af36068 经数据库验证。完整考据过程见 [20260724_bob-beck-openbsd-security-response.md](../../../原材料/研究/考据记录/20260724_bob-beck-openbsd-security-response.md)。

**字段 4 与本章节内容的关联**

- 为子节 93.1（LibreSSL 的 fork 背景）提供 Heartbleed 漏洞作为 fork 触发事件的当事人陈述
- 为子节 93.2（LibreSSL 的工程决策）提供首周删除 9 万行代码的工程实践
- 为子节 93.3（LibreSSL 的路线图）提供“先稳定后移植”的路线图阐述

**字段 5 史观映射**

- 总纲 5“没有必然性，只有偶然性”——据第 5 章 5.1 节“世界上没有必然性，只有偶然性”，Heartbleed 漏洞（CVE-2014-0160）作为偶然爆发的安全事件，直接催生 LibreSSL fork。Heartbleed 的爆发时点与影响范围皆具偶然性，LibreSSL 的出现是偶然情势下的具体回应。若以“OpenSSL 迟早会被 fork”解释，即落入 5.2 节批评的“张三不上李四也会上”谬误——该谬误在 18.4 节被进一步批驳为“替代品的幻觉”。
- 总纲 21“革命与改革”——据第 21 章 21.1 节“Linux 的发展依靠不断的革命与彻底否定（或在其基础上再发展），而 BSD 这里只是不断的改革”，LibreSSL fork 自 OpenSSL 并首周删除约 9 万行代码，是革命而非改革：彻底推翻 OpenSSL 旧代码建立新代码库。但须区分：革命与改革在历史实践中辩证转化——LibreSSL 的革命性 fork 仍需通过“先稳定后移植”的改革路径落地。
- 总纲 4“分离聚合是永恒规律”——据第 4 章 4.1 节“分离聚合是世界发展的规律。分久必合，合久必分”，LibreSSL 从 OpenSSL 代码库中分离，移除遗留的旧平台兼容代码，是分离聚合规律在安全工具治理中的具体呈现。但须区分：fork 本身蕴含新的聚合可能——LibreSSL 与 OpenSSL 的代码分离并非永久性撕裂，未来可能通过安全审计共享实现聚合。

#### 采访 2：Theo de Raadt（西奥·德·若特）

**字段 1 采访元数据**

- 受访者：Theo de Raadt，时任 OpenBSD 项目创始人，OpenNTPD 与 OpenSMTPD 项目发起人
- 采访者：无（OpenBSD 官方文档与邮件列表自述）
- 采访时间：2004-2015（OpenNTPD 与 OpenSMTPD 开发时期）
- 采访形式：官方文档与邮件列表公开陈述
- 原始来源：OpenBSD Project. OpenNTPD Manual Page **openntpd(8)** [EB/OL]. [2026-07-23]. **<https://man.openbsd.org/openntpd>**；OpenSMTPD 项目页面 ** <https://www.opensmtpd.org/>**
- 存档信息：原始 URL 经联网核实可访问，未失效

**字段 2 采访摘要**

de Raadt 主导 OpenNTPD（2003 年引入，提供简单安全的 NTP 时间同步服务）与 OpenSMTPD（2008 年开始开发，提供安全合规的 SMTP 邮件服务）的创建，延续 OpenBSD“重新实现而非修补”的安全工具生态建设哲学。OpenNTPD 以代码简洁与默认安全配置为设计目标，取代 ISC NTP 的复杂配置。OpenSMTPD 采用 privilege separation 架构，将网络监听、队列管理与邮件投递分离为不同权限的进程。

**字段 3 考据脚注**

本则自述经 OpenBSD 官方文档与 OpenSMTPD 项目页面核实，真实可访问（访问日期 2026-07-23）。OpenNTPD 与 OpenSMTPD 的引入版本须经 OpenBSD Release Notes 与 **openntpd(8)**、**smtpd(8)** 手册页交叉验证。de Raadt 对“重新实现”哲学的阐述属 OpenBSD 阵营单方陈述，已作自利偏差审查：OpenNTPD/OpenSMTPD 与 ISC NTP/Postfix 的安全记录比较须经独立安全审计验证。完整考据过程见 [20260724_theo-deraadt-openbsd-security-culture.md](../../../原材料/研究/考据记录/20260724_theo-deraadt-openbsd-security-culture.md)。

**字段 4 与本章节内容的关联**

- 为子节 93.4（OpenNTPD 的创建）提供“重新实现”哲学在 NTP 领域的应用
- 为子节 93.5（OpenSMTPD 的创建）提供 privilege separation 架构在 SMTP 服务中的应用
- 为子节 93.6（OpenBSD 安全工具生态的整体设计）提供“安全工具生态”概念的官方阐述

**字段 5 史观映射**

- 总纲 21“革命与改革”——据第 21 章 21.1 节“Linux 的发展依靠不断的革命与彻底否定（或在其基础上再发展），而 BSD 这里只是不断的改革”，OpenBSD 选择“重新实现而非修补”ISC NTP/Postfix，是革命而非改革：彻底推翻旧工具建立新工具。但须区分：OpenNTPD/OpenSMTPD 的重新实现虽具革命性，但其 privilege separation 架构仍需通过持续改革落地。21.2 节所谓“破山中贼易，破心中贼难”——真正的阻力不在技术论证，而在观念和结构。
- 总纲 4“分离聚合是永恒规律”——据第 4 章 4.1 节“分离聚合是世界发展的规律。分久必合，合久必分”，OpenSMTPD 采用 privilege separation 架构，将网络监听、队列管理与邮件投递分离为不同权限的进程，是分离聚合规律在安全架构中的具体呈现。但须区分：分离本身蕴含新的聚合可能——各权限进程通过受控通道实现聚合，而非永久性隔离。
- 总纲 22“知识注定过时”——据第 22 章 22.1 节“如今翻开当年的甲种本、乙种本，甚至在你正学习的那一刻，知识便已过时”，OpenBSD 对已有工具（ISC NTP/Postfix/OpenSSL）的持续重新实现，回应了安全知识的累积性过时。22.2 节指出“技术债务是历史设计的代价”——ISC NTP/Postfix 的复杂配置与遗留代码即是历史设计代价，OpenBSD 的重新实现是对这一代价的回应。

**要点**：

- Jacek Masiulaniec 的路径：约十年前以游戏为目的接触计算机，经 Usenet 闻知 Linux，五年间试遍各发行版仍不满足；任小型 ISP 管理员时为解决流量整形问题，因 PF 队列系统在 OpenBSD 上远比 FreeBSD 易于配置，于 OpenBSD 3.8/3.9 前后转向，试过 FreeBSD 与 OpenBSD（未试 NetBSD）后留在后者。（BSDTalk EP179，[63.8-154.0]，L1）
- 他以源码可读性为标准选择学习材料：GNU 的 ls、ps 等小程序的风格令他无法卒读，OpenBSD 源码在他所见系统中最简单、最小、最紧凑；读完 Richard Stevens 的 Unix API 专著后寻找练手项目，恰逢 OpenSMTPD 导入源码树，从 imsg 框架与 buffer 例程读到 SMTP 服务器端，提交的修复数量多到因此获得开发者账号。（BSDTalk EP179，[188.5-287.6]，L1）
- OpenSMTPD 的定位与架构：他个人的目标是小型、紧凑、精干的 Sendmail 替代，但不排除高级特性，插件基础设施自始规划（对标 Sendmail 的 Milter 体系）；实现为典型 OpenBSD daemon 风格——特权分离与特权降级，与 BGPd、PF 等知名路由类 daemon 共享大量代码与思想，与 OpenSSH 共享思想，imsg 与 buffer API 通用于各 OpenBSD 服务器组件。（BSDTalk EP179，[298.6-443.9]，L1）
- 配置哲学：配置文件格式与 PF 高度相似，将邮件系统视为过滤器——消息本地投递抑或经远程网关中继取决于 SMTP 会话中匹配的规则；aliases 文件仅为 Sendmail 用户的兼容层而非必需；maps 层允许规则以别名参数指向 flat file、hashed file 或 SQL 数据库后端完成地址重写。（BSDTalk EP179，[359.4-637.9]，L1）
- 功能与成熟度：开箱支持 Mailbox 与 Maildir，并可经管道投递至任意外部程序；支持服务器与客户端两侧的 STARTTLS（暂缺客户端证书认证，计划实现）；虚拟主机为 sendmail 风格的定义文件且计划支持任意后端；随 OpenBSD 4.6 发布，但作者明确不推荐生产使用——current 中已有大量修复，建议自 CVS 获取最新源码。（BSDTalk EP179，[482.9-666.6]，L1）
- 可移植性评估：认证相关的 SMTP 扩展最暴露操作系统差异、部分代码不可移植；整体应可移植，已有 FreeBSD 与 NetBSD 的移植，尚无 Linux 或其他系统。（BSDTalk EP179，[445.9-482.9]，L1）
- Epitome（Marco Peereboom 的项目，Jacek 少量参与）：Unix 上的去重应用引擎，将文件切分为块、以 SHA-1 哈希存于可选后端（裸磁盘、Unix 目录或 SQL 数据库），后续备份仅存变化的块且块级压缩；对比 rsync 加硬链接的传统方案——小改动即复制整文件且无法压缩——并可随机提取存档中部文件而无需顺序读取。（BSDTalk EP179，[674.2-818.5]，L1）

**史料**：

- 该期提及的一手线索包括：OpenSMTPD 导入 OpenBSD 源码树并随 4.6 发布；CVS current 中 smtpd 的修复流；Marco Peereboom 的 Epitome 去重项目；Richard Stevens 的 Unix API 专著；GNU coreutils 与 OpenBSD 源码风格的对照样本；受访者在小型 ISP 的 PF 队列配置实践。（BSDTalk EP179，[242.2-287.6]，L1）

**史观**：
