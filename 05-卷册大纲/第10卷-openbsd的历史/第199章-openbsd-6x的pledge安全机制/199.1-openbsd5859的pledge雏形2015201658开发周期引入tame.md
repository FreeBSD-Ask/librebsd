# 199.1 OpenBSD 5.8-5.9 的 pledge 雏形（2015-2016）——5.8 开发周期引入 tame(2) 子系统，2015-10-09 重命名为 pledge(2)，5.8 中禁用，5.9 正式启用

## 199.1.1 **pledge(2)** 的设计与实现

**要点**：**pledge(2)** 的前身是 tame(2) 子系统，由 de Raadt 于 2015-07-19 commit `586b470f3a48` 引入（"tame(2) is a subsystem which restricts programs into a ‘reduced feature operating model’"）；2015-10-09 de Raadt commit `350b464c5787` 将 tame() 重命名为 pledge()（"Rename tame() to pledge(). This fairly interface has evolved to be more strict than anticipated"）；pledge 在 OpenBSD 5.8（2015-10-29 发布）中存在但被禁用——2015-10-12 schwarze commit `cfe38e1d85ad` 明确记载“pledge wasn't called pledge in 5.8, and it was disabled”；pledge 在 OpenBSD 5.9（2016-03-29 发布）中正式启用；pledge 让进程自愿放弃特定权限（如网络、文件系统访问），进程在程序启动时调用 `pledge("stdio rpath", NULL)` 即可限制权限

  **pledge/tame 演进关键 commit 时间线**：

  | 日期 | commit hash | 作者 | 说明 |
  | --- | --- | --- | --- |
  | 2015-07-19 | `586b470f3a48` | deraadt | tame(2) 引入——restricts programs into a ‘reduced feature operating model’ |
  | 2015-10-09 | `350b464c5787` | deraadt | 将 tame() 重命名为 pledge() |
  | 2015-10-12 | `cfe38e1d85ad` | schwarze | 明确 pledge 在 5.8 中被禁用 |
  | 2016-03-29 | — | OpenBSD | 5.9 正式启用 pledge(2) |

**史料**：openbsd.duckdb openbsd-src 仓库 commit `586b470f3a48`（2015-07-19 deraadt “tame(2) is a subsystem...”）、commit `350b464c5787`（2015-10-09 deraadt “Rename tame() to pledge()”）、commit `cfe38e1d85ad`（2015-10-12 schwarze“pledge wasn't called pledge in 5.8, and it was disabled”）；OpenBSD 5.9 Release Notes pledge 部分；**pledge(2)** 手册页（<https://man.openbsd.org/pledge.2>）〔L1 代码/构建产物/L3 官方文档与公告〕

**史观**：总纲第 17 条——软件工程：pledge 是“最小权限”原则的系统调用化实现——进程自愿声明所需权限子集，内核据此拒绝越权系统调用，这一设计将安全约束从外部沙箱转移至程序自身声明，是软件工程中“白名单优先于黑名单”原则在操作系统接口层的实践

**辨析**：[2026-08-15 邮件列表库验证通过]：2015-10 openbsd-tech/openbsd-bugs 多条邮件确认 pledge 在 2015 年 10 月已进入广泛测试阶段（2015-10-30 “syscall 96 in top(1) on renice”、2015-10-31 “pledge(2) and pselect(2)”、2015-10-09 Kevin Reay 提及“new pledge syscall”），与 5.8 开发周期时间线一致；pledge 的引入版本在不同叙事中存在分歧——部分资料称 5.9 正式引入，部分称 5.8 已有雏形；经 openbsd.duckdb 核查，tame() 于 2015-07-19 引入（5.8 开发周期），2015-10-09 重命名为 pledge()，但在 5.8 中被禁用（schwarze commit cfe38e1d85ad 明确记载），5.9 正式启用；原大纲称“5.4 引入 pledge 雏形”系误记——5.4（2014）时 tame/pledge 均不存在，tame 的最早 commit 为 2015-07-19

## 199.1.2 pledge 的工程哲学

**要点**：pledge 的设计哲学是“让程序员轻松做正确的事”——程序自愿声明权限而非被动接受沙箱，声明接口简洁（`pledge("stdio rpath", NULL)` 一行即可），避免 Linux seccomp 的复杂 BPF 过滤器；de Raadt 在 tech@ 邮件列表中主张 pledge 应简化至程序员愿意主动使用的程度；pledge 最初用于 OpenBSD 自带的用户态工具（如 **tcpdump(1)**、**nc(1)**），后续扩展至更多基本系统程序

**史料**：de Raadt 在 tech@ 关于 pledge 哲学的发言（<https://marc.info/?laccopenbsd-tech>）；OpenBSD pledge 设计文档；**pledge(2)** 手册页 DESIGN 部分（<https://man.openbsd.org/pledge.2>）；openbsd.duckdb openbsd-src 仓库 pledge 相关 commit（2015-10-09 起 deraadt、semarie、benno 等的 commit）〔L1 代码/构建产物/L2 即时通讯记录/L3 官方文档与公告〕

**史观**：总纲第 17 条——软件工程：pledge 的设计哲学是 OpenBSD 对软件工程的独特理解——安全机制的可采用性取决于接口简洁度，复杂的沙箱接口（如 seccomp BPF）因使用门槛高而采用率低，pledge 以“一行声明”降低采用门槛，使安全约束成为程序员的主动选择而非被动负担

**辨析**：pledge 与 seccomp 的工程哲学比较——两者设计目标不同，seccomp 以 BPF 过滤器提供细粒度系统调用控制但配置复杂，pledge 以预定义权限类别提供粗粒度控制但配置简洁；pledge 的“自愿”特性是否导致使用率不足——OpenBSD 基本系统中 pledge 覆盖率以 Release Notes 与 commit log 中 pledge 相关 commit 计数为准，基本系统主要用户态工具已普遍采用 pledge

**文献**：de Raadt 邮件列表发言 [EB/OL]. <https://marc.info/?laccopenbsd-tech>；OpenBSD **pledge(2)** 手册页 [EB/OL]. <https://man.openbsd.org/pledge.2>；Linux seccomp 文档 [EB/OL]. <https://www.kernel.org/doc/html/latest/userspace-api/seccomp_filter.html> ［A］

## 199.1.3 与 Linux seccomp/Capsicum 的比较

**要点**：Linux seccomp 使用 BPF 过滤器限制系统调用，灵活但复杂；FreeBSD Capsicum 提供能力模式与沙箱，设计精巧但采用率低；OpenBSD pledge 简洁但功能受限——三者设计哲学各自合理，pledge 以极简声明降低采用门槛，seccomp 以 BPF 灵活覆盖细粒度场景，Capsicum 以能力句柄提供细粒度资源控制

  **pledge/seccomp/Capsicum 三大沙箱机制对比**：

  | 机制 | 项目 | 接口形式 | 粒度 | 采用门槛 | 运行时开销 |
  | --- | --- | --- | --- | --- | --- |
  | pledge | OpenBSD | 声明式（`pledge("stdio rpath", NULL)`） | 粗粒度（系统调用类别） | 最低（一行声明） | 最低（系统调用入口检查） |
  | seccomp | Linux | BPF 过滤器 | 细粒度（单系统调用 + 参数） | 最高（BPF 配置） | 中（BPF 过滤器执行） |
  | Capsicum | FreeBSD | 能力句柄（`cap_rights_init()`） | 细粒度（资源 fd） | 中（多步调用） | 最高（能力句柄管理） |

**史料**：Linux seccomp 文档（<https://www.kernel.org/doc/html/latest/userspace-api/seccomp_filter.html>）；FreeBSD Capsicum 设计文档（<https://www.freebsd.org/cgi/man.cgi?query=capsicum>）；OpenBSD **pledge(2)** 手册页（<https://man.openbsd.org/pledge.2>）〔L3 官方文档与公告〕

**史观**：总纲第 7 条——技术选择即政治选择：三个项目选择不同的权限限制机制是各自对“安全与易用性权衡”的不同政治回应——OpenBSD 以“可采用性优先”为预设选择 pledge，Linux 以“灵活性优先”为预设选择 seccomp，FreeBSD 以“细粒度控制优先”为预设选择 Capsicum

**辨析**：三者的性能对比以同硬件同负载的 Phoronix 等基准测试为准——pledge 的运行时开销最低（仅系统调用入口检查），seccomp 次之（BPF 过滤器执行），Capsicum 最高（能力句柄管理）；Capsicum 在 FreeBSD 中的实际采用率以 FreeBSD 源码树中 cap_enter() 与 cap_rights_init() 的调用计数为准——Capsicum 主要被用于 FreeBSD 基本系统的少数服务（如 dhclient、casperd），采用率低于 pledge 在 OpenBSD 中的覆盖

**文献**：Linux seccomp 文档 [EB/OL]. <https://www.kernel.org/doc/html/latest/userspace-api/seccomp_filter.html>；FreeBSD Capsicum 文档 [EB/OL]. <https://www.freebsd.org/cgi/man.cgi?query=capsicum>；OpenBSD **pledge(2)** 手册页 [EB/OL]. <https://man.openbsd.org/pledge.2> ［A］

## 199.1.4 pledge commit 记录与文档考据

- 总纲21 革命与改革是历史方法论的分歧：Cantrill 断言“Linux 不是被设计的，它是演化的”，任何形似整体设计之物都会激起社区的免疫反应，而 ZFS、DTrace、容器与安全这类复杂构造无法靠演化抵达，必须有人重新思考整体并获准整合大型成果；FreeBSD 与 illumos 的价值恰在于允许这种整体性设计着陆，优秀想法还能在共享价值观的系统间交叉授粉。他将自由软件内部的路线之争表述为革命性整体设计与渐进演化两种历史方法论的分歧，并归因于 Linux 缺乏承担架构方向的责任结构、无人为设定架构方向负责。（BSD Now EP117，[4133.02-4236.92]，L1）
- 总纲15 文化即形式主义：Cantrill 力陈命名即软件的基石而非琐碎细节：名字将被未来世代用于理解、扩展既有设计并判断其做法是否恰当，命名失当如同基石被掀翻在街心，是系统沦为贫民窟、无法起造摩天楼的根源。他举 DNF 包管理器连作者本人都拒答缩写含义、systemd 与 libsystemd 以库之名封装守护进程且边界无限扩张、KVM 之名与机房键盘视频鼠标切换器相冲撞为例，指出命名混乱会迫使真正理解系统的善意聪明人自我怀疑；命名之争的僵局往往暗示存在尚未被想到的第三方案。（BSD Now EP117，[2781.72-2809.82]，L1）
- 总纲9 经验优先：allocation throttle 反转了跨设备均分分配的理论预设，以客户环境与内部系统的实际观测为准：池碎片化后各设备分配速度分化，索性“why not give more work to devices that are actually responding faster”（2193.18-2199.20），按响应能力倾斜工作负载使快设备保持满载。这一设计出自运维经验而非抽象公平原则，印证经验观测优先于理论均分的工程认识论。（BSD Now EP116，[2145.16-2202.86]，L1）
