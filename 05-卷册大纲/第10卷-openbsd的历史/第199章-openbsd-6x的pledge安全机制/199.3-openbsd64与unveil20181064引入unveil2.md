# 199.3 OpenBSD 6.4 与 unveil（2018.10）——6.4 引入 unveil(2) 系统调用，实现文件系统访问的路径级限制，与 pledge 配合形成双重沙箱

## 199.3.2 pledge 与 unveil 的配合

**要点**：pledge 限制系统调用类别（如“stdio”、“rpath”、“wpath”、“inet”等），unveil 限制文件系统访问路径——两者配合形成完整的权限沙箱；OpenBSD 自带工具（如 **tcpdump(1)**、**nc(1)**、**ftp(1)**）普遍使用 pledge+unveil；这种双重沙箱模式在 BSD/Linux 世界中独特——seccomp 仅限制系统调用，namespaces 仅隔离资源，二者均未提供 pledge+unveil 的“声明式双重限制”模式

**史料**：OpenBSD 用户态工具的 pledge+unveil 使用情况（以 openbsd.duckdb openbsd-src 仓库 usr.bin/ 路径下含 pledge/unveil 调用的 commit 为准）；**pledge(2)** 与 **unveil(2)** 手册页 EXAMPLES 部分（<https://man.openbsd.org/pledge.2>、<https://man.openbsd.org/unveil.2）；tech@> 邮件列表 pledge+unveil 讨论（<https://marc.info/?laccopenbsd-tech>）

**史观**：总纲第 17 条——软件工程：pledge+unveil 的配合是“最小权限”原则的完整实现——pledge 从系统调用维度限制权限，unveil 从文件路径维度限制权限，二者正交组合覆盖了进程权限的主要攻击面

**辨析**：pledge+unveil 的实际防护效果以安全研究论文与漏洞披露记录为准——pledge+unveil 在 OpenBSD Security Advisories 中多次被记录为限制漏洞影响范围的关键机制；OpenBSD 自带工具的 pledge+unveil 覆盖率以 openbsd.duckdb openbsd-src 仓库 usr.bin/ 路径下含 pledge() 或 unveil() 调用的源文件计数为准——基本系统主要用户态工具已普遍采用

## 199.3.3 与 Linux namespaces/Solaris zones 的比较

**要点**：Linux namespaces 提供进程隔离（mount、PID、network 等），Solaris zones 提供系统级容器隔离；OpenBSD pledge+unveil 是进程级权限限制，不提供完整隔离；三者设计目标不同——namespaces/zones 是容器化（隔离整个运行环境），pledge/unveil 是权限沙箱（限制单个进程的权限），二者非互斥但解决不同层面的问题

**史料**：Linux namespaces 文档（<https://man7.org/linux/man-pages/man7/namespaces.7.html>）；Solaris zones 设计文档；OpenBSD pledge/unveil 文档（<https://man.openbsd.org/pledge.2>、<https://man.openbsd.org/unveil.2）〔L3> 官方文档与公告〕

**史观**：总纲第 7 条——技术选择即政治选择：三项目选择不同的隔离机制是各自对“安全与隔离粒度权衡”的不同政治回应——Linux 以“资源隔离优先”为预设选择 namespaces，Solaris 以“系统级隔离优先”为预设选择 zones，OpenBSD 以“进程级权限限制优先”为预设选择 pledge/unveil

**辨析**：三者的隔离强度对比——设计目标不同难以直接比较，namespaces/zones 提供容器级隔离（适用于多租户场景），pledge/unveil 提供进程级权限限制（适用于单进程硬化）；Solaris zones 的实际部署规模以 Oracle Solaris 官方数据为准 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

**文献**：Linux namespaces 文档 [EB/OL]. <https://man7.org/linux/man-pages/man7/namespaces.7.html>；OpenBSD pledge/unveil 文档 [EB/OL]. <https://man.openbsd.org/pledge.2> ［A］

## 199.3.5 pledge/unveil 设计争议的批评——可移植性缺陷与细粒度局限（批评层）

**要点**：对 pledge/unveil 机制设计局限的批评集中于四点——其一，pledge 与 unveil 仅限 OpenBSD，无法移植至 Linux 或 FreeBSD，跨平台应用若欲使用须为 OpenBSD 单独维护一份代码分支，采用门槛过高，与 seccomp 自 Linux 2.6.12（2005）后普遍可用、Capsicum 自 FreeBSD 9.0（2012）后随系统发布的跨发行版可达性形成对照；其二，pledge 采用粗粒度类别（如 `stdio`、`rpath`、`wpath`、`inet`），无法对单一系统调用进行过滤，更无法基于系统调用参数过滤，而 seccomp-bpf 可针对单系统调用及其参数进行细粒度过滤，Capsicum 可对单个文件描述符授予细粒度能力，pledge 在过滤精度上明显落后；其三，pledge 与 unveil 均为自愿模型（voluntary model），须由程序员显式调用 `pledge()` 或 `unveil()` 方能生效，对未调用这两个接口的代码无任何防护作用，攻击者注入的代码可径直绕过 pledge 限制，而 seccomp 可由系统管理员通过 `PR_SET_SECCOMP` 全局强制启用，不受应用自愿与否约束；其四，unveil 一旦调用 `unveil(path, NULL)` 即锁定后续 unveil 调用为无效，这一“锁定即不可逆”设计在需要动态揭示路径的场景下缺乏灵活性，与 Linux landlock 可动态调整路径限制的设计形成对照

**史料**：Linux seccomp 文档（<https://www.kernel.org/doc/html/latest/userspace-api/seccomp_filter.html>）；FreeBSD Capsicum 文档（<https://www.freebsd.org/cgi/man.cgi?query=capsicum>）；OpenBSD **pledge(2)** 手册页（<https://man.openbsd.org/pledge.2>）与 **unveil(2)** 手册页（<https://man.openbsd.org/unveil.2>）；Linux landlock 文档（<https://docs.kernel.org/userspace-api/landlock.html>）；pledge 可移植性批评的公开讨论（<https://marc.info/?laccopenbsd-misc>） ［A］

**史观**：总纲第 14 条——商业与社区的张力：pledge/unveil 的可移植性缺陷使该机制的实际受益者局限于 OpenBSD 用户，外部性（跨平台应用的额外适配成本）由整个生态承担而非 OpenBSD 独自承担；总纲第 19 条——解释学循环：pledge/unveil 评估受前理解差异制约——OpenBSD 阵营以“简洁即正确”为前理解，批评者以“细粒度即安全”为前理解，二者难以通约

**辨析**：批评的合理性在不同叙事中评估不一——部分视为有效工程批评，部分视为对 OpenBSD 简洁哲学的误读；需对照 pledge/unveil 手册页与 seccomp-bpf、Capsicum 设计文档三方核实；【0 信任原则·可移植性的量化】“跨平台应用须单独维护一份代码分支”论证须提供具体案例（如哪个开源项目在 OpenBSD 上单独维护 pledge 调用分支），否则易沦为总体性指控；【0 信任原则·细粒度局限的解读】pledge 的粗粒度类别可能是有意设计而非缺陷——粗粒度减少了配置错误的概率，seccomp-bpf 的细粒度本身带来过滤器编写复杂度高、易出错的副作用，二者须对照区分；【0 信任原则·自愿模型的辨析】“自愿模型无防护”批评须对照 pledge 的“fail-closed”语义——pledge 一旦调用即不可放宽，攻击者注入的代码无法通过再次调用 `pledge()` 放宽限制，故“自愿”仅指调用前无防护而非调用后可绕过；【多源交叉验证不可靠性规则】多个 Linux 阵营对 pledge 的批评在多处一致，但这一一致性可能源于 Linux 社区对 seccomp 的共同立场而非独立验证

## 199.3.6 pledge/unveil 设计争议的反批评——OpenBSD 阵营的回应（反批评层）

**要点**：OpenBSD 阵营对 pledge/unveil 设计批评的回应集中于四点——其一，pledge 的粗粒度类别是有意的工程选择而非缺陷，seccomp-bpf 的细粒度虽灵活但配置复杂、易出错，过滤器编写错误导致的“假安全”比粗粒度类别更危险，de Raadt 在公开声明中多次强调“正确性优先于灵活性”——一个能被正确使用的简单机制优于一个能被错误使用的复杂机制；其二，pledge 的“fail-closed”语义（一旦调用即不可放宽）使自愿模型在调用后即成为强制约束，攻击者注入的代码无法通过再次调用 `pledge()` 放宽限制，故“自愿即无防护”批评混淆了“调用前无防护”与“调用后可绕过”两个不同语义层面；其三，pledge/unveil 的可移植性缺陷是 OpenBSD 工程哲学的必然结果——pledge 依赖 OpenBSD 内核的 `kern_pledge` 实现，移植至 Linux/FreeBSD 须重新实现内核侧支持，OpenBSD 不应为迁就其他系统而稀释自身设计，seccomp 的跨发行版可用性是 Linux 内核维护者的工程选择而非技术必然；其四，unveil 的“锁定即不可逆”设计是安全机制的应有之义——可逆的路径限制会引入 TOCTOU（time-of-check to time-of-use）竞态，攻击者可在解锁窗口期内绕过限制，landlock 的动态调整设计虽灵活但增加了竞态面的攻击复杂度

**史料**：de Raadt 在 misc@ 与 tech@ 关于 pledge 设计哲学的发言（<https://marc.info/?laccopenbsd-misc>、<https://marc.info/?laccopenbsd-tech）；OpenBSD> **pledge(2)** 手册页 DESCRIPTION 与 HISTORY 段（<https://man.openbsd.org/pledge.2>）；Bob Beck 关于 pledge/unveil 设计的公开声明；openbsd.duckdb openbsd-src 仓库 sys/kern/kern_pledge.c 与 sys/kern/kern_unveil.c 路径下的 commit（记录“fail-closed”语义的实现） ［A］

**史观**：总纲第 17 条——软件工程：pledge/unveil 的设计是 OpenBSD“正确性优先于灵活性”工程哲学的实践；总纲第 8 条——本体论上各方平等：pledge/unveil 与 seccomp、Capsicum 在本体论上地位相等，差异仅是工程哲学的不同而非本体等级的高下；总纲第 7 条——技术选择即政治选择：OpenBSD 选择 pledge 而非 seccomp 式的细粒度过滤是以“可采用性优先”为预设的政治选择

**辨析**：反批评的合理性在不同叙事中评估不一——部分视为有效辩护，部分视为合理化；需对照 OpenBSD 官方声明与 pledge/unveil 实际工程产出核实；【0 信任原则·官方声明不等于事实】de Raadt 与 Beck 关于“正确性优先于灵活性”的声明须与 pledge 实际工程产出（如基本系统工具的 pledge 覆盖率、pledge 相关 CVE 频率）交叉验证；【0 信任原则·fail-closed 语义的边界】“fail-closed 使自愿模型在调用后成为强制约束”论证须对照 pledge 的“execpromises”机制——pledge 在 **execve(2)** 后可重置为子进程的 promises，故“不可放宽”仅在同一进程内成立，跨 **execve(2)** 边界存在放宽可能；【0 信任原则·可移植性缺陷的合理化】“pledge 不可移植是工程哲学必然”论证须对照 Capsicum 的可移植性经验——Capsicum 虽源于 FreeBSD 但其设计文档明确讨论过移植至其他系统的可能性，可移植性与工程哲学并非互斥；【0 信任原则·TOCTOU 论证的有效性】“可逆限制引入 TOCTOU 竞态”论证须对照 landlock 的实际安全记录——landlock 自 Linux 5.13（2021）引入后未见因可逆性导致的 TOCTOU CVE，TOCTOU 风险可能为理论推断而非实际缺陷

## 199.3.7 pledge/unveil 设计争议的再批评——对反批评的再回应（再回应层）

**要点**：对 OpenBSD 阵营反批评的再回应集中于四点——其一，“粗粒度优于细粒度”论证忽视了复杂应用的真实需求——浏览器、虚拟机监控器等复杂应用须对单个系统调用进行差异化过滤（如允许 **openat(2)** 但禁止 **openat(2)** 的某些参数组合），pledge 的粗粒度类别无法满足这一需求，导致复杂应用要么放弃 pledge（如 Chromium 在 OpenBSD 上以 `pledge("stdio rpath wpath cpath inet dns", NULL)` 调用覆盖大部分操作，实际防护效果有限）要么人为拆分进程（如 Chromium 的沙箱模型），二者均非理想方案；其二，“fail-closed 语义使自愿模型在调用后成为强制约束”论证在跨 **execve(2)** 场景下失效——pledge 的 execpromises 机制允许子进程重置 promises，攻击者若能注入 **execve(2)** 调用即可绕过原进程的 pledge 限制，这一攻击路径在 seccomp-bpf 的全局过滤器下不存在（seccomp 过滤器在 **execve(2)** 后默认保留）；其三，“pledge 不可移植是工程哲学必然”论证忽视了 OpenBSD 自身在可移植性上的双重标准——OpenBSD 的 `libutil`、`libcrypto` 等库在其他 BSD 上有对应实现，OpenBSD 并非一律拒绝可移植性，pledge 的不可移植更可能源于内核侧实现成本而非哲学原则；其四，“可逆限制引入 TOCTOU 竞态”论证以理论风险否定实际工程方案——landlock 的可逆设计通过原子操作与路径解析锁定避免 TOCTOU，pledge/unveil 的不可逆设计虽消除 TOCTOU 但也消除了动态调整的灵活性，二者是工程权衡的不同选择而非一方正确一方错误

**史料**：Chromium 在 OpenBSD 上的 pledge 使用情况（OpenBSD ports 树 www/chromium 路径下 pledge 相关 patch）；seccomp-bpf 在 **execve(2)** 后的过滤器保留语义（Linux seccomp 文档 SECCOMP_FILTER_FLAG_TSYNC 部分）；landlock 的原子操作与路径解析锁定设计（Linux landlock 文档）；OpenBSD `libutil`、`libcrypto` 在其他 BSD 上的对应实现（FreeBSD libutil、LibreSSL） ［A］

**史观**：总纲第 19 条——解释学循环：pledge/unveil 评估受前理解差异制约——OpenBSD 阵营以“正确性优先”为前理解，批评者以“灵活性优先”为前理解，二者难以通约；总纲第 14 条——商业与社区的张力：pledge/unveil 的细粒度局限使复杂应用（浏览器、虚拟机监控器）的实际防护效果打折，这一成本由 OpenBSD 上的复杂应用用户承担而非 OpenBSD 项目独自承担

**辨析**：再批评的具体论据在不同叙事中差异较大——需对照 OpenBSD 实际部署与 seccomp/landlock 实际记录交叉验证；【0 信任原则·复杂应用案例的可证伪性】“Chromium 在 OpenBSD 上 pledge 防护效果有限”论证须提供具体证据——如 Chromium 的实际 pledge 调用语句、OpenBSD Security Advisories 中 pledge 限制 Chromium 漏洞影响的具体案例，否则易沦为总体性指控；【0 信任原则·execve 绕过的实际可行性】“execve 调用可绕过 pledge”论证须对照 OpenBSD 的 execpromises 实际配置——若 Chromium 等应用显式设置 execpromises，则 execve 绕过路径被阻断，须以具体应用配置而非抽象语义判断；【0 信任原则·可移植性双重标准的辨析】“OpenBSD 在 libutil/libcrypto 上有可移植性，在 pledge 上无”论证须对照两类组件的本质差异——库是用户态组件（移植成本低），pledge 是内核系统调用（移植成本高），二者不可直接类推；【0 信任原则·landlock TOCTOU 记录的有效性】“landlock 未见 TOCTOU CVE”论证须对照 landlock 的部署规模与审计强度——landlock 自 2021 年引入，部署规模与审计强度远低于 seccomp，无 CVE 不等于无漏洞

## 199.3.8 pledge/unveil 设计争议的辩证合图（合图层）

**要点**：pledge/unveil 设计争议的辩证合图——pledge/unveil 既是 OpenBSD 对 seccomp-bpf 与 Capsicum 复杂性的工程回应（反批评层）也是其细粒度局限与可移植性缺陷的具体显现（批评层与再回应层），二者并非非此即彼；pledge/unveil 在 OpenBSD 生态内具有工程合理性（粗粒度类别降低配置错误率、fail-closed 语义提供调用后强制约束、与 unveil 配合形成双重沙箱），但在跨平台生态内具有外部性（复杂应用须人为拆分进程、跨平台应用须单独维护 OpenBSD 分支、与 seccomp/landlock 的过滤精度差距）；合图不寻求“折中”而寻求揭示 pledge/unveil 的结构性张力——它既是 OpenBSD 安全哲学的工程实践也是其生态孤立的具体显现，“简洁自主”与“细粒度不足”是同一决策的共生效应，不可分割；本体论上，pledge/unveil 与 seccomp、Capsicum、landlock 在本体论上地位相等，差异仅是工程哲学的不同而非本体等级的高下——pledge 的“粗粒度正确性”与 seccomp 的“细粒度灵活性”各自在其生态内具有合理性，史家的任务不是判定优劣而是呈现张力；pledge/unveil 的历史意义不在于“取代 seccomp”（这一目标从未实现，亦非 OpenBSD 所求）而在于“证明粗粒度声明式沙箱是可行的安全范式”——pledge/unveil 的存在本身对 Linux landlock（2021 引入的声明式路径限制）与 FreeBSD Capsicum 的工程方向形成对照压力，促使各项目重新审视“简洁性”与“灵活性”的权衡

**史料**：pledge/unveil 与 seccomp/Capsicum/landlock 综合对比研究、BSD/Linux 沙箱机制演进史、OpenBSD Security Advisories 中 pledge/unveil 限制漏洞影响范围的具体案例、Linux landlock 与 pledge/unveil 的设计对照文档〔L3 官方文档与公告/L5 二手研究〕

**史观**：总纲第 8 条——本体论上各方平等：pledge/unveil 与 seccomp、Capsicum、landlock 在本体论上地位相等；总纲第 19 条——解释学循环：pledge/unveil 评估受前理解差异制约，合图不寻求消除差异而寻求呈现差异；总纲第 6 条——和解优于斗争：合图不寻求消除张力而寻求呈现张力，pledge/unveil 与 seccomp/Capsicum/landlock 的共存本身是安全机制生态的多元呈现

**辨析**：合图不寻求消除张力而寻求呈现张力——pledge/unveil 的“简洁自主”与“细粒度不足”是同一决策的共生效应，不可分割；【0 信任原则·合图的非终结性】合图并非辩证链的终结而是阶段性综合，随 pledge/unveil 与 seccomp/landlock 演进（如 landlock 的功能扩展与 pledge 的 promises 类别增加）须重新展开；【0 信任原则·合图的非折中主义】合图不是“pledge 在 OpenBSD 内合理、在跨平台外不合理”的简单分类，而是揭示“简洁自主”与“细粒度责任”的张力——OpenBSD 以跨平台兼容性成本换取工程自主是结构性选择而非道德缺陷，但这一选择的外部性须被自觉呈现；【0 信任原则·历史意义的辨析】“pledge/unveil 促使 landlock 引入”论证须对照时序——landlock 自 Linux 5.13（2021-06）引入，pledge 自 OpenBSD 5.9（2015-10）引入，unveil 自 OpenBSD 6.4（2018-10）引入，时序关联存在但因果关系须谨慎评估，landlock 的设计可能源于 Linux 自身的容器安全需求而非 pledge/unveil 的对照压力

**文献**：pledge/unveil 与 seccomp/Capsicum/landlock 综合对比研究；BSD/Linux 沙箱机制演进史；OpenBSD Security Advisories；Linux landlock 设计文档 [EB/OL]. <https://docs.kernel.org/userspace-api/landlock.html> ［A］

## 199.3.9 pledge/unveil 设计争议的项目统摄史观审视——总纲第 13、19、21 条映射（哲学审视子节）

**要点**：pledge/unveil 设计争议的项目统摄史观审视须从总纲三条切入——其一，总纲第 13 条“法律与道德是利益分配”映射：pledge/unveil 的“简洁正确性”叙事不仅是技术论证也是 OpenBSD 项目身份建构的政治产物，社区对 pledge 的辩护中混合了技术判断（粗粒度降低配置错误）与道德判断（“正确使用简单机制优于错误使用复杂机制”），后者本质是将 OpenBSD 工程哲学包装为道德优越，这一包装在社区治理中转化为对批评者的边缘化（misc@ 邮件列表中 pledge 批评者常被斥为“未理解 OpenBSD 哲学”），印证“社区治理亦是形式主义的政治产物”；其二，总纲第 19 条“解释学循环是历史认识的根本条件”映射：pledge/unveil 与 seccomp 的优劣评估受前理解差异制约——OpenBSD 阵营以“简洁即正确”为前理解，Linux 阵营以“细粒度即安全”为前理解，二者难以通约；同时，权力与知识在历史书写中共谋——pledge/unveil 的设计被 OpenBSD 官方文档与 de Raadt 公开声明塑造为“安全机制的正确方向”，而 seccomp-bpf 的复杂性被叙述为“Linux 的工程包袱”，这一叙述本身是 OpenBSD 阵营的权力行使，什么被记录为“正确设计”、什么被记录为“复杂包袱”，本身就是权力与知识的共谋；其三，总纲第 21 条“革命与改革是历史方法论的分歧”映射：pledge 是改革式路径——基于现有系统调用接口新增 `pledge()` 与 `unveil()` 两个调用，不改变内核架构，渐进式扩展覆盖范围（自 5.9 起逐 release 增加 base system 工具的 pledge 覆盖），seccomp-bpf 是革命式路径——引入 BPF 虚拟机作为内核内过滤器，改变了系统调用入口的执行模型，landlock 是另一改革式路径——基于现有路径解析机制新增安全模块；OpenBSD 选择 pledge 这一改革式路径与其在 LibreSSL、vmm 等子系统上的改革式选择一致，印证“BSD 靠改革”的方法论连续性，但改革的困难远高于革命——pledge 须逐个工具适配，覆盖范围扩展缓慢，而 seccomp-bpf 一经引入即可全局适用，“破山中贼易，破心中贼难”在 pledge 语境下体现为：技术机制（山中贼）易建，但让所有应用自觉采用（心中贼）难

**史料**：项目史观总纲第 13、19、21 条原文（原材料/哲学/项目统摄史观/第 25 章.md）；de Raadt 在 misc@ 关于 pledge 设计哲学与对批评者回应的发言（<https://marc.info/?laccopenbsd-misc>）；OpenBSD **pledge(2)** 手册页 HISTORY 段（记录 pledge 自 5.9 起的覆盖扩展）；Linux seccomp-bpf 设计文档与 landlock 设计文档；openbsd.duckdb openbsd-src 仓库 pledge 覆盖扩展 commit（usr.bin/ 路径下逐工具增加 `pledge()` 调用的 commit） ［A］

**史观**：总纲第 13 条——法律与道德是利益分配：pledge/unveil 的“简洁正确性”叙事是 OpenBSD 项目身份建构的政治产物，社区对批评者的边缘化是社区治理的政治行使；总纲第 19 条——解释学循环：pledge/unveil 与 seccomp 的优劣评估受前理解差异制约，权力与知识在“何为正确安全设计”的历史书写中共谋；总纲第 21 条——革命与改革是历史方法论的分歧：pledge 是改革式路径（新增系统调用、渐进扩展覆盖），seccomp-bpf 是革命式路径（引入 BPF 虚拟机改变执行模型），OpenBSD 选择改革式路径与其在 LibreSSL、vmm 等子系统上的选择一致，印证“BSD 靠改革”的方法论连续性

**辨析**：哲学审视的合理性须以三个层面交叉验证——【0 信任原则·道德包装论证的辨析】“pledge 辩护混合技术判断与道德判断”论证须对照 misc@ 邮件列表原文核实——若辩护文本仅含技术论证（如“粗粒度降低配置错误率”），不得人为添加道德判断成分，须以具体文本为据；【0 信任原则·权力-知识共谋的可证伪性】“pledge 被塑造为正确方向、seccomp 被叙述为包袱”论证须对照 OpenBSD 官方文档与第三方独立评估的差异——若第三方独立评估同样肯定 pledge 的工程价值，则“权力共谋”论证须重新审视；【0 信任原则·改革与革命路径的辨析】“pledge 是改革、seccomp 是革命”分类须对照二者的实际工程变更——pledge 新增了 `pledge()` 与 `unveil()` 两个系统调用并引入 `kern_pledge` 与 `kern_unveil` 内核子系统，这一变更幅度并非纯粹“改革”（亦包含新子系统的引入），seccomp-bpf 引入 BPF 虚机但 BPF 自 Linux 2.6.25（2008）已存在，seccomp-bpf 是对既有 BPF 的复用而非全新引入，故“革命 vs 改革”的二分须谨慎；【多源交叉验证不可靠性规则】多个 OpenBSD 阵营对 pledge 哲学优越性的论证在多处一致，但这一一致性可能源于社区共同立场而非独立验证，须以第三方独立安全研究交叉验证
