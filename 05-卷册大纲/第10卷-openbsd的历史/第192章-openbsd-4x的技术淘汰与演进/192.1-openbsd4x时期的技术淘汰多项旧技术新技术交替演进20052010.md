## 191.1.1 XFree86 → X.org 转换（OpenBSD 4.1-4.2，2007）

**要点**：XFree86 项目因 2004 年 1 月 XFree86 4.4.0 许可证变更（加入类似 “广告条款” 的限制性条款）引发社区分裂，X.Org 基金会 fork 形成 X.org 服务器；bsd_commits.db 显示 OpenBSD 在 4.x 时期完成从 XFree86 到 X.org 的转换——2005-05-04 jaredy commit 8462c87f5bf9 "change XFree86 -> X.Org" 标识手册页转换，2007-03-26 matthieu commit fcb4a8a3b89b "Switch X build instructions to xenocara. ok deraadt@ jmc@ mbalmer@" 标识 xenocara 构建框架首次引入（4.1 周期）；xenocara 是 OpenBSD 对 X.org 的定制构建框架，整合 X server、驱动、字体等组件；原大纲称 “为后续 xenocara 重组（6.0）奠定基础” 系误记——xenocara 于 4.1（2007.5）引入，非 6.0（2015.10）

**史料**：bsd_commits.db openbsd-src 仓库 commit 8462c87f5bf9（2005-05-04 jaredy "change XFree86 -> X.Org"）、commit fcb4a8a3b89b（2007-03-26 matthieu "Switch X build instructions to xenocara"）；XFree86 4.4.0 LICENSE 文件变更；X.Org 基金会成立公告；OpenBSD 4.1 Release Notes X11 部分 ［A］

**史观**：总纲第 24 条——许可证：XFree86 4.4.0 许可证变更（加入广告条款）催生 X.org fork，OpenBSD 通过 xenocara 聚合 X.org 完成替代——这一路径是 OpenBSD 许可证纯洁性哲学的实践，OpenBSD 拒绝接受含广告条款的 XFree86 4.4.0，选择 fork 后的 X.org

**辨析**：OpenBSD 从 XFree86 切换到 X.org 的具体版本以 commit log 与 Release Notes 交叉确认——2005-05-04 jaredy commit 标识手册页转换，2007-03-26 matthieu commit 标识 xenocara 构建框架引入，二者间隔约 2 年，反映 X.org 切换是渐进过程；XFree86 4.4.0 许可证变更的具体条款以原始 LICENSE 文件为准——新增条款要求所有文档与广告材料中提及 XFree86 项目

**文献**：bsd_commits.db openbsd-src 仓库 commit 8462c87f5bf9、fcb4a8a3b89b；XFree86 4.4.0 LICENSE 文件；X.Org 基金会公告；OpenBSD 4.1 Release Notes [EB/OL]. <https://www.openbsd.org/41.html> ［A］

## 191.1.2 gcc → pcc 尝试与 clang/LLVM 转向前期（2010 起）

**要点**：OpenBSD 4.x 时期（2005-2010）仍以 gcc 4.x 为默认编译器；2007 年起 de Raadt 对 gcc GPLv3 许可证与代码质量不满，开始探索替代方案；OpenBSD 团队曾尝试集成 pcc（Portable C Compiler）作为 gcc 替代，但因 pcc 功能不足（不支持 C99 完整特性、缺乏优化）放弃——bsd_commits.db openbsd-src 仓库中无 pcc（Portable C Compiler）实际集成 commit，pcc 探索主要在邮件列表讨论；至 4.x 末期（2010-2011）OpenBSD 开始评估 clang/LLVM 作为最终替代，为 5.7（2014.5）完全切换至 clang/LLVM 奠定基础

**史料**：de Raadt 关于 gcc GPLv3 的邮件列表发言（<https://marc.info/?laccopenbsd-tech>）；pcc 项目文档（<http://pcc.ludd.ltu.se/>）；OpenBSD tech@ 邮件列表关于 pcc/clang 的讨论；bsd_commits.db openbsd-src 仓库 pcc 相关 commit（数据库中 "pcc" 关键字搜索结果均为 pccons/pccom 误匹配，无 Portable C Compiler 实际集成记录） ［A］

**史观**：总纲第 24 条——许可证：gcc GPLv3 许可证争议是 OpenBSD 探索编译器替代的根本动因——OpenBSD 的 ISC 许可证偏好与 gcc GPLv3 的 copyleft 要求存在张力，这一张力推动 OpenBSD 评估 pcc（失败）与 clang/LLVM（成功）作为替代

**辨析**：OpenBSD 尝试 pcc 的具体时间以 tech@ 邮件列表讨论存档为准——pcc 探索主要在 2007-2008 年的邮件列表讨论中进行，未进入 openbsd-src 主干；pcc 放弃的具体原因以 de Raadt 与其他开发者的邮件列表发言为准——pcc 不支持 C99 完整特性、缺乏现代优化器；gcc 到 clang/LLVM 的切换动机以 OpenBSD 5.7 Release Notes 与 de Raadt 的公告为准——GPLv3 担忧与技术优势（更好的诊断信息、模块化设计）均为动机

**文献**：pcc 项目文档 [EB/OL]. <http://pcc.ludd.ltu.se/>；OpenBSD tech@ 邮件列表档案 [EB/OL]. <https://marc.info/?laccopenbsd-tech>；de Raadt 关于 gcc 的发言；clang/LLVM 项目文档 ［A］

## 191.1.3 yplib/ypcat → ypldap 替换（NIS → LDAP）

**要点**：NIS（Network Information Service，原 Yellow Pages）是 Sun Microsystems 1980 年代设计的网络目录服务，OpenBSD 早期通过 **yplib(3)**、**ypcat(1)**、**ypmatch(1)** 等工具支持；NIS 因安全设计缺陷（无认证、明文传输）逐步被 LDAP 取代；bsd_commits.db 显示 ypldap 首次 commit 为 2008-06-26 pyr commit f624240892b9 "ypldap -- Intended to be a drop-in replacement for ypserv, gluing in a LDAP directory a..."（4.4 周期，2008.11 release），2008-10-14 deraadt commit 33b8cba20fd2 "enable ypldap. serious development needs it to be enabled." 在 4.5 周期正式启用——原大纲称 “5.x 时期成熟” 系误记，ypldap 在 4.4-4.5 周期（2008-2009）已引入并启用；ypldap 作为 NIS 与 LDAP 的桥接，让 NIS 客户端可查询 LDAP 目录

**史料**：bsd_commits.db openbsd-src 仓库 commit f624240892b9（2008-06-26 pyr "ypldap -- Intended to be a drop-in replacement for ypserv"）、commit 33b8cba20fd2（2008-10-14 deraadt "enable ypldap"）；Sun NIS 文档；OpenBSD **ypldap(8)** 手册页（<https://man.openbsd.org/ypldap.8>） ［A］

**史观**：总纲第 19 条——信息技术：NIS 作为 1980 年代的网络目录信息技术被 LDAP 聚合替代——ypldap 的引入是 OpenBSD 对网络目录服务从 NIS 向 LDAP 迁移趋势的响应，但 OpenBSD 选择桥接（ypldap）而非直接取代（删除 ypserv）的渐进路径

**辨析**：ypldap 在 OpenBSD 中的引入版本以 bsd_commits.db commit log 为准——2008-06-26 pyr@ 首次引入（4.4 周期），2008-10-14 deraadt@ 启用（4.5 周期），原大纲称 “4.5 或更早” 与 “5.x 时期成熟” 均不准确；ypldap 与传统 ypserv 的关系以 **ypldap(8)** 手册页为准——ypldap 模拟 ypserv 协议让 NIS 客户端透明查询 LDAP，二者并存而非替代；NIS 在 OpenBSD 中的实际部署规模无权威统计 [考据完成：2026-07-28 NIS 在 OpenBSD 部署中的占比无公开调研]

**文献**：bsd_commits.db openbsd-src 仓库 commit f624240892b9、33b8cba20fd2；Sun NIS 文档；OpenBSD **ypldap(8)** 手册页 [EB/OL]. <https://man.openbsd.org/ypldap.8> ［A］

## 191.1.4 OpenSSL 集成与磁盘加密演进（softraid 加密等）

**要点**：OpenBSD 3.0（2001.12）引入 vnd 块设备的加密模式 svnd，使用 Blowfish 算法；OpenBSD 4.x 时期持续改进加密栈——softraid 加密于 2007-11-27 tedu commit f18dcc9c26b1 首次引入（4.2 周期），2008-06-14 hshoexer commit 79cdc9424edb 完整启用（4.4 周期），支持 AES-XTS，取代 svnd 成为推荐的磁盘加密方案；4.x 时期的 OpenSSL 集成为后续 LibreSSL fork（2014 年 4 月 Heartbleed 后）积累了 OpenSSL 工程实践——但 LibreSSL fork 发生在 5.6 周期（2014.11），与 4.x 时期（2005-2010）相隔约 4 年，二者不构成直接的 “前期演进” 关系

**史料**：bsd_commits.db openbsd-src 仓库 commit f18dcc9c26b1（2007-11-27 tedu "split crypto functions"）、commit 79cdc9424edb（2008-06-14 hshoexer "enable softraid crypto"）；OpenBSD 3.0 Release Notes vnd 部分；OpenBSD 4.2/4.4 Release Notes softraid 部分；OpenBSD **softraid(4)**、**bioctl(8)** 手册页 ［A］

**史观**：总纲第 21 条——密码学：加密栈从 svnd（Blowfish）到 softraid（AES-XTS）的演进是 OpenBSD 对密码学最佳实践变化的响应——AES-XTS 作为 NIST SP 800-38E 推荐的磁盘加密模式取代 Blowfish，这一路径是密码学标准演进对操作系统实现的具体塑造

**辨析**：svnd 与 softraid 的关系以 bsd_commits.db commit log 为准——softraid 首次 commit 为 2007-03-19 dlg commit 98855ba5cdbc "attach softraid to the root of the device tree"，是新的 RAID 框架，加密是其子功能；AES-XTS 支持的具体引入版本以 **softraid(4)** 手册页与 commit log 为准——softraid 加密自 2008 年启用即支持 AES-XTS；4.x 时期 OpenSSL 集成的具体版本以 OpenBSD Release Notes 为准

### 史观映射

OpenBSD 4.x 时期是项目统摄史观中 “形式主义化” 与 “修道度人” 在网络安全领域的双重实践。6 个月发布周期作为形式主义化结构（总纲第 17 条——软件工程），将时间固化为不可动摇的规则——krw@ 与 espie@ 的 release engineering 工作严格遵循 5 月与 11 月的节奏，这一形式化结构带来稳定性与可预测性，但也限制了单周期内的重大架构重构。pf 的持续演进是 “修道度人” 的工程实践（总纲第 17 条——软件工程）——claudio@ 与 henning@ 在 2005-2010 年间持续改进 pf，让 pf 守护着无数网络的边界，但 pf 的作者们很少在公众视野中出现。CARP 冗余协议的开发是对法律结构障碍的重新设计（总纲第 12 条——法律结构）——当 VRRP 协议的 Cisco 专利 US 5,473,599 成为障碍时，OpenBSD 选择重新设计协议（CARP）而非寻求专利授权，这一选择是法律结构对技术实现的直接塑造。malloc 替代（tedu@ 2006-10-24 commit 66e23c51）是 “边缘者承担安全关键基础设施” 的具体显现（总纲第 10 条——边缘者贡献）——OpenBSD 的 malloc 安全替代由单一开发者响应安全研究社区的漏洞披露而实现，非由大厂商团队推动。softraid 加密的引入（tedu@ 2007-11-27 commit f18dcc9c26b1 至 hshoexer@ 2008-06-14 commit 79cdc9424edb）是密码学标准演进对操作系统实现的具体塑造（总纲第 21 条——密码学）——AES-XTS 作为 NIST SP 800-38E 推荐模式取代 Blowfish。de Raadt 的个人主导模式是 “动手者” 存在主义的体现——一个人在不被理解中坚持自己的工程哲学，BDFL 治理（总纲第 23 条——社区治理）使 OpenBSD 在 4.x 时期保持技术方向一致性。

- 资金困境与 hackathon 机制：项目已亏损运行一段时间；开销主要在基础设施——网络费用昂贵、电费极高，因为项目坚持所有平台全部本地原生构建（Zaurus 快照即在 Zaurus 上构建），地下室机器全天候运转；已收捐赠获致谢，同时呼吁企业级赞助——盼有公司愿意为 hackathon 买单。年度 hackathon 为开发者大聚会：多数人飞赴 Calgary 写代码、规划战略，邮件往返缓慢的事项在面谈中大大加速；其副作用是总能发现需要多人不同技能协作才能定位的重大 bug，产出大量好代码与想法进入下个发布；面对面建立信任，而这种开发模式极依赖信任。另有定向 hackathon：如前一年威尼斯的 ports hackathon，约 10 名专家使 ports 系统大幅进步；ports 与包工具近期升级体验显著改善且质量可直接测得。（BSDTalk EP27，[218.08-430.34]，L1）
- 开发哲学与安全记录：OpenBSD 开发模式不讲废话——永远做对的事，不适合操作系统的特性就不会发生，因此对社区有时显得生硬；对许可证绝不妥协并引以为豪，纵然承受社区与其他方面的压力，流程中保持理性，不合格的代码不会进入发布、甚至直接移出树——想在此协作就得守此规则。对保持默认安装无远程漏洞的纪录表示自信——正是这一点当初吸引他入坑（厌倦了隔三差五担心被入侵的日子），但他不能替全世界打包票。（BSDTalk EP27，[436.30-552.92]，L1）
- 升级流程与包工具评价：当事人认为 OpenBSD 的升级过程比 apt-get 更透明——他试装 Ubuntu 后觉得 apt-get 要求用户预先懂得太多；承认 OpenBSD 安装器对新用户略显生畏，但这只是习惯问题：图形安装器问的是同样的问题，打字与点击之别而已；升级复用与安装相同的安装器、识别现有系统、连按回车即开始，最难的一步是敲出二进制路径；ports 侧的工具已做到完全透明——一条命令即可升级全部 ports 并解析依赖；ports 升级与替换功能为 3.8 与 3.9 之间引入、随 3.9 发布；他本人不做 ports，靠定时任务自动升级。（BSDTalk EP27，[552.92-700.92]，L1）
- 在研项目：正与 Jordan Hargrave 合作重写 ACPI——工程巨大、代码要写要调、BIOS 环境充满敌意、进展缓慢；另在升级磁盘控制器驱动以支持即将到来的 SAS 技术；并循 Theo de Raadt 的指引为 bioctl 增加更多 RAID 控制器支持——bioctl 为 3.8 引入的通用 RAID 管理工具，理念是各家 RAID 控制器虽差异巨大、基本视角下功能相同，bioctl 以简单方式确保 RAID 栈完好，提供换盘与重建工具且全程无需重启——磁盘故障后不重启即可恢复；此工具面向硬件 RAID 而非软件 RAID，二者将来或合并但为时尚远。桌面方面用 Ion 或 Ratpoison 平铺窗口管理器，在高分辨率宽屏上并排三个全尺寸窗口，重度使用 screen 切换文本终端，编辑器只用 vi——唯一确定永远在场的编辑器。（BSDTalk EP27，[700.92-925.88]，L1）
- sensors 框架的状态自述：该框架自 OpenBSD 3.4 或 3.5 经由 NetBSD 继承而来，近六至八个月才被真正发力推进，整体仍属粗糙、用户态部分亟待重写；其固有难点是低端主板上的廉价监控芯片只报出挂接数量，软件只能枚举 fan1 至 fan4 而不知物理对应，高端 SCSI 领域则可经 enclosure services、ESM 或 IPMI 查询到 Baseboard Fan1、Power Supply 2 一类的设备名；驱动集中于 i386 与 AMD64，框架本身在全部架构启用且至少五个架构有专属驱动，SCSI 设备的温度报告亦接入。（BSDTalk EP46，[162.92-308.44]，L1）
- bio 框架的动机是让 RAID 状态首次可被软件感知：此前树内 RAID 控制器一律伪装为 SCSI 驱动，管理员只见逻辑盘，盘阵降级无从得知，只能进机房看闪灯或听蜂鸣——有管理员甚至一日两次派初级员工巡视机房；bio 的目标是经软件检测 RAID 降级并以邮件告警、进而支持软件修复盘阵；该框架完全自产、于最近一次 hackathon 才问世却已惊人可用，暂只支持 MegaRAID 控制器且限于 i386 与 AMD64，向其他架构扩展容易只是缺硬件。（BSDTalk EP46，[326.64-380.88]，L1）
- 软件 RAID 在 OpenBSD 的被忽视现状：树内仅有两个驱动——自 NetBSD 继承的 RAIDframe 极为庞大、亟须裁剪（NetBSD 在该领域投入远多），以及仅做镜像与条带化的极轻量 CCD、缺乏对付硬件故障族的智能；受访者坦言若有空闲愿意投入，制约因素纯粹是时间。（BSDTalk EP46，[382.36-434.80]，L1）
- 入门路径：1996 或 1997 年首装 Linux，得到提示符后不知所措而退回 Windows；入大学后因功课与共享网络需要 Unix，发现 OpenBSD 文档远比 Linux 的 howto 与贫乏文档可读而选择后者，自认当时不知为何没有选 FreeBSD；其对 OpenBSD 的第一项贡献是引入 USB 支持，经持续提交修复后获自行提交权限；此后遍历各 BSD 与多个 Linux，并在工作中照看 Solaris 机器。（BSDTalk EP46，[447.76-526.80]，L1）
- 桌面与服务器推荐的分野：其桌面定义仅为能 ssh、有浏览器、能放 MP3，此标准下 OpenBSD 完全胜任；但音频编辑、矢量图形等场景他不讳言会推荐 Mac OS 或 Windows，并自知此论会令社区不快；服务器端则除日历与 Exchange 支持外，OpenBSD 作任何他所工作过的网络的后端都能直接运转。（BSDTalk EP46，[675.60-717.52]，L1）
- 开发环境与社区对照：日常为 vi 加 make 加 screen 加当值语言，screen 被其称作有史以来第二重要的软件；他对 OpenBSD 开发社区的评价是极为支持与鼓励——报告 bug 会被认真对待、他人愿与你一同追踪直至修复，而其对比的图景是某些上游维护者一句我这儿正常便终结报告，令他困惑于对方无意改进软件；两种社区对待缺陷的方式构成鲜明差异。（BSDTalk EP46，[727.72-790.52]，L1）
- OpenCVS 的重写突破：hackathon 前两周他因受够 GNU CVS 的代码而与项目同侪商讨重写，获得实现思路后决定部分重写；会前已完成大量代码，抵达 hackathon 后集中提交、进展迅速——commit、update、checkout、status 等常规仓库操作命令在三周内全部可用，按其说法这三周做完的工作量超过 OpenCVS 此前两年的积累。（BSDTalk EP50，[143.12-200.74]，L1）
- OpenRCS 的先行策略：OpenCVS 开发一度停滞，遂与 Theo 商定先做 OpenRCS——既可将更多 BSD 许可程序收进 base 树，又能复用 OpenCVS 已有的 RCS parser；OpenRCS 反而先于 OpenCVS 完成，已成为 GNU RCS 套件的近乎全面替代（尚缺向分支提交的能力）；其后因共用 parser 并非长久之计而彻底分叉，如今两者的共性仅存于 RCS parser 本身。（BSDTalk EP50，[202.82-297.70]，L1）
- 对 pserver 的拒绝是明确的安全决策：其认证协议与口令加密算法属公开已知、加密口令极易被提取，支持如此不安全的机制在他看来非常愚蠢；OpenCVS 依赖 OpenSSH——以 SSH 连接远程 shell、执行 CVS 服务端命令、经标准输入输出通信；未来或许会有自带用户认证与真实 ACL 的 CVS 守护进程以解决匿名读与扩展访问控制，但他对此并不确定。（BSDTalk EP50，[428.54-503.50]，L1）
- GNU CVS 缺失而 OpenCVS 拟增的工程特性：目录与分支级的访问控制列表——如 portable 与 stable 分支并存的大项目中只允许特定人选向 stable 分支提交安全修复；离线 diff——在火车或飞机上无服务器连接时对先前的 head 修订查看自身改动；revert——按指定提交自动将所涉文件回滚至先前 head 修订、相当于反向合并；原子提交——保证提交要么完整发生要么完全不发生，而非五个文件只改了两个。（BSDTalk EP50，[518.02-652.38]，L1）
- 仓库接管的责任与容错空间：OpenCVS 尚未用于管理 OpenBSD 官方仓库——若他此时向 OpenBSD 仓库提交会被立即制止——但他已用其管理个人本地仓库； eventual 切换意味着巨大责任，RCS 文件一旦损坏则满盘皆乱；所幸 OpenCVS 沿用 RCS 纯文本格式——管理段与全部 delta 皆为明文、修订即相互施加的文本补丁，尚存恢复希望；二进制 delta 的支持刚在 OpenRCS 侧取得进展，OpenCVS 仍付阙如。（BSDTalk EP50，[311.50-426.54]，L1）
- 项目参与的动机：他为自己的小项目长期使用 CVS，却总遇到不应发生之事——最著名的莫过于运行简单的 cvs update 时抱怨既有文件挡路、要求挪开的无稽行为；阅读 GNU CVS 源码的经历令他深感可怖，认定读之只会陷入痛苦；其后经聊天渠道得知有人为 OpenBSD 发起 OpenCVS 项目，因自己常用 OpenBSD 便决定加入出力。（BSDTalk EP50，[656.30-716.70]，L1）
- 入坑 OpenBSD 的机缘是一块声卡：家中旧机的声卡在 Windows 与 Linux 下皆无法发声，而他极重音乐，遍寻替代时将 NetBSD 与 FreeBSD 都试过而无效，转试 OpenBSD 后声音竟然直接正常；此后他持续惊叹于 OpenBSD 中一切基本都能正常运作，并敬佩驱动作者的才智；以 OpenBSD 听音乐、聊天，对他而言已是完美的多媒体系统。（BSDTalk EP50，[722.86-803.54]，L1）
- 哑终端的本质是显示器、键盘与一条连回中央计算机的长电缆，终端本身不承担实际处理任务，内部仅有少量电路且无运动部件；其存在意义在于让多个用户在文本模式下同时使用同一台计算机。（BSDTalk EP51，[50.36-74.32]，L1）
- 主播完整演示将 Wyse WY-50 哑终端经串口与 null adapter 以 9600 波特接入 OpenBSD 3.9 的流程：在 /etc/ttys 为 tty00 配置 /usr/libexec/getty，在 /usr/share/misc/termcap 检索 Wyse 50 对应的 WY50 类型，状态列设为 on 并加 secure 选项；他对 secure 的取舍依据是终端位于家中而非共享网络之上，体现了以物理边界界定信任域的经验性安全判断。（BSDTalk EP51，[86.94-246.46]，L1）
- 将默认控制台设为串口是调试与无头服务器（不装显卡）运维的常见做法；但 i386 架构的 BIOS 不向 COM 口输出，导致无头启动受限，而 alpha 与 Sun 等架构可全程经串口完成。（BSDTalk EP51，[257.66-286.34]，L1）
- 主播观察到 2006 年哑终端几乎随处可得、人们正将其当作垃圾丢弃甚至已不认识这种设备，同时串行端口正从个人计算机上消失，使此类配置愈发困难；他以此期录制作为对旧硬件的怀旧实践。（BSDTalk EP51，[291.32-310.42]，L1）

**史观**：

- 总纲13 法律与道德是利益分配：OpenSSH 悖论呈现了价值创造与利益分配的错位：OpenSSH 内置于 Cisco 交换机、AIX、OS X 等无处不在的平台，使用者以百万计，却无一分收入回流项目，连自身运转账单都难以支付；企业把公共品内化为基础设施而不承担其维护成本，公共品的存续被迫仰赖个人捐赠与偶发的企业善举——技术上的巨大成功与经济上的悬空并存。（BSDTalk EP27，[945.60-998.24]，L1）
- 总纲9 经验优先：代码质量教育的反思：大学课程教会 C、进阶 C 与 C++ 的语法基础，却没有教良好的编程实践，构成糟糕的代码质量根基；他自言是接触 OpenBSD 之后才相信自己能写出好代码；对新手的建议是去解决真正烦扰自己的问题并阅读他人优秀源码——项目之外坏代码被大量阅读并衍生更多坏代码，而好范例明明更多，决定代码能力的不是教材而是接触好代码的经验。（BSDTalk EP46，[533.12-622.68]，L1）
- 总纲10 动手者创造历史：主播以一线动手者身份记录保持旧硬件可用性的完整日常操作，表明技术史的延续不仅存在于版本发布与会议叙事中，也存在于普通实践者让被淘汰设备继续运转的动手环节里。（BSDTalk EP51，[0.0-328.02]，L1）
- 总纲3 不存在进步，只有权力再分配：哑终端“运行良好”却仍被丢弃、串口仍在消失的同期观察显示，旧技术的退场并非源于功能丧失，而是硬件产业取向转移的结果，技术更替并非线性进步叙事。（BSDTalk EP51，[291.32-310.42]，L1）
