### pf 演进与网络栈维护者的口述（2006-2011 时期当事人）

#### 采访 1：Reyk Flöter

**字段 1 采访元数据**

- 受访者：Reyk Flöter，时任 OpenBSD pf 维护者
- 采访者：无（BSDCan 学术会议演讲，无单一采访者）
- 采访时间：2008（BSDCan 2008）
- 采访形式：学术会议演讲（一手会议产出）
- 原始来源：Flöter R. PF: Past, Present and Future [C]//BSDCan 2008. Ottawa: BSDCan, 2008 [2026-07-23]. slides 位于 **<https://www.openbsd.org/papers/bsdcan08-pf/**。OpenBSD> 官方 events 页面 ** <https://www.openbsd.org/events.html>** 收录
- 存档信息：原始 URL 经联网核实可访问（访问日期 2026-07-23），未失效；OpenBSD 官方 events 页面直接收录 slides

**字段 2 采访摘要**

Flöter 在 BSDCan 2008 发表 pf 防火墙的过去、现在与未来综述演讲，回顾 pf 自 2001 年诞生至 4.x 时期的演进路径。演讲涵盖 pf 的状态跟踪优化、anchors 嵌套规则集机制、interface groups 匹配、tables 高速查找表等 4.x 时期关键特性，以及 pf 在 OpenBSD 4.4-4.9 期间的性能调优与 IPv6 支持完善。Flöter 亦讨论 pf 移植至 FreeBSD（通过 pfSense 项目）与 NetBSD 的跨平台影响。

**字段 3 考据脚注**

本则会议演讲经 OpenBSD 官方 events 页面核实，slides 真实可访问（访问日期 2026-07-23）。Flöter 关于 pf 4.x 时期特性的陈述，经 OpenBSD 4.x Release Notes（**<https://www.openbsd.org/40.html>** 至 **<https://www.openbsd.org/49.html>**）与 ** pf.conf(5)** 手册页历次版本交叉验证。pf 在 OpenBSD 4.1 引入 interface groups 匹配、4.2 扩展 anchors 与 tables 语法等版本归属须以各版本手册页与 Release Notes 交叉为准。当事人自述部分（Flöter 对 pf 性能优势的描述）已作自利偏差审查：pf 与 IPFilter、ipfw 的性能比较须经独立第三方基准测试验证。完整考据过程见 [20260724_reyk-floeter-pf-evolution.md](../../../原材料/研究/考据记录/20260724_reyk-floeter-pf-evolution.md)。

- 为子节 86.2（pf 4.x 时期的技术演进）提供 anchors、tables、interface groups 等关键特性的开发者一手陈述

- 为子节 86.4（IPv6 支持的完善）提供 pf 在 4.x 时期 IPv6 支持的演进细节

**字段 5 史观映射**

- 总纲 4“分离聚合是永恒规律”——据第 4 章 4.1 节“BSD 又分裂出 FreeBSD、NetBSD、OpenBSD、DragonFly BSD，此乃分离；而各分支间的代码共享、ports 互通、社区人员的流动，此乃聚合”，pf 从 OpenBSD 移植至 FreeBSD（通过 pfSense 项目）与 NetBSD，是 4.1 节意义上的聚合。但须注意：4.1 节描述的是分离聚合的循环结构，不是进步史观意义上的“扩散”——pf 的跨平台移植并非“OpenBSD 输出先进技术”，而是各 BSD 在不同形式主义选择下的再聚合，FreeBSD/NetBSD 的移植版本与 OpenBSD 基线版本已发生形式主义分化。
- 总纲 8“本体论上各方平等”——据第 25 章总纲 8“FreeBSD、OpenBSD、NetBSD、DragonFly BSD 在本体论上地位相等，差异仅是一刻状态的不同”，pf 在 OpenBSD、FreeBSD、NetBSD 上的不同实现形态，是各 BSD 本体论平等前提下的形式主义分化。Flöter 演讲中对 pf 跨平台影响的评估，不应被叙述为“OpenBSD 优越性的证明”，而应被呈现为 8 条意义上的本体平等状态差异。
- 总纲 9“经验优先”——据第 25 章总纲 9“优先呈现质朴的事实与当事人的直接经验”，Flöter 演讲从 pf 4.x 时期具体特性的工程经验切入（anchors、tables、interface groups），而非从防火墙设计的抽象理论框架推导。这种经验优先的认识论模式，使 pf 能够在 4.x 时期持续吸收生产环境的反馈而非停留在设计文档层面。
- 总纲 10“动手者创造历史”——据第 14 章 14.2 节“真正的问题不在于技术发展的程度，而在于是否动手”，Flöter 作为 pf 4.x 时期的核心维护者，其演讲展现了 14.2 节意义上的“在已有架构上持续动手”而非“推翻重来”。但须注意：14.1 节“没有多余形式主义的人就是老实人”批评的是形式主义的累积，pf 在 4.x 时期的特性叠加（anchors 嵌套规则集、tables 高速查找表、interface group 匹配）既是动手者的工程创造，亦可能成为 14.1 节意义上的“多余形式主义”——这一张力须被呈现，不可单边叙述。
- 总纲 22“知识注定过时”——据第 22 章 22.2 节“技术债务是历史设计的代价”，pf 从简单状态防火墙演进为支持 anchors、tables、interface groups 的复杂系统，每一代特性都在前一代基础上叠加，形成 22.2 节意义上的技术债务遗产。Flöter 演讲中对 pf 演进路径的回顾，应被理解为 22.1 节“史家有此自觉”在工程层面的对应——pf 维护者对技术债务的累积有此自觉。

**字段 5 史观映射**

- 总纲 9“经验优先”——据第 25 章总纲 9 与第 2 章 2.11 节“你观察到的永远只是事物呈现给你的样子”，Brauer 对网络栈代码的逐行审计从工程经验切入，而非从网络协议规范的理论推导出发。性能优化（中断处理、规则集编译器、多核适配）的决策基于生产环境的经验数据，这种经验优先的认识论使 Brauer 能够发现规范未明示的瓶颈。
- 总纲 10“动手者创造历史”——据第 14 章 14.2 节“真正推动 BSD 的是‘Get your hands dirty’（动手去做）的人”，Brauer 的 commit log 展现了 14.2 节意义上的“持续动手”而非“一次性设计”。但须注意：14.2 节批评“社区中大多数人连系统都没有装过就开始讨论一些看起来复杂的东西”，Brauer 的工作是反例——其 commit log 是动手的物证，而非旁观评论。须区分：14.1 节“没有多余形式主义的人就是老实人”中的“老实人”不可等同于“一线代码工人”的阶级范畴，Brauer 作为核心维护者的地位不来自阶级属性，而来自 14.2 节意义上的动手实践。
- 总纲 2“历史是形式主义化的非存在”——据第 2 章 2.2 节“历史从来都没有存在过，或者说，存在过，但是只有一种古代史”，Brauer 对网络栈代码的逐行审计不是揭示“真实代码”，而是重构可被信任的形式主义。OpenBSD“逐行审计”文化的产物亦是形式主义化的非存在——这一坦承本身，即是对形式主义最大的诚实，不可被叙述为“审计揭示真相”。
- 总纲 22“知识注定过时”——据第 22 章 22.2 节“技术债务是历史设计的代价”，Brauer 对网络栈的持续优化（中断处理、多核适配）回应了硬件演进带来的知识过时。但 22.2 节提醒：技术债务是历史遗产，既有正面价值也有技术债务——Brauer 的优化既累积新价值，亦产生新债务，不可被叙述为单向进步。
- 总纲 14“苦难不值得被提倡”——据第 12 章 12.1 节“一切苦难都不值得被提倡，那只是一种类似宗教救赎的神话叙事结构”，不应将 Brauer 长期维护网络栈的工作美化为“苦难造就伟大”。12.1 节明确“凡是强调苦难的意义和推崇苦难本身者都有其潜在的龌龊目的”，本条释读拒绝将长期维护叙事转化为道德资本。

**要点**：

- Herrb 的技术路径起于具体的动手困境：他在法国图卢兹求学，博士实验室以 Sun 工作站等接触 UNIX；约 1993 年免费 UNIX 可在家用 PC 运行时，他的图形卡不为 X386 支持便动手修改以驱动自己的硬件，从此未辍；先做 NetBSD 的 X 移植，后转入 OpenBSD。（BSDTalk EP106，[81.36-134.56]，L1）
- Xorg 7 的架构变革是构建体系的换代：弃用 X 专属的 imake 而改用新构建工具并走向模块化，库、客户端、X server 与每个驱动各自成包，合计三百余个包须按正确顺序分别构建；OpenBSD 希望直接在 base system 中构建 X，管理这批包的需求催生了 Xenocara——其核心只是 BSD make 文件加一套通用规则，技术亦可移植到其他 BSD（向 NetBSD 的初步尝试因 make 宏差异而复杂但可解）。（BSDTalk EP106，[269.6-351.96]，L1）
- 他澄清 OpenBSD 的 X 并非 Xorg 分叉，仅含少量本地补丁与配置微调且多不为用户所见；用户感知的差异在于 OpenBSD 默认不装 GNOME/KDE 而以 fvwm 为窗口管理器；目标是 OpenBSD 4.2 时全部架构改用 Xenocara，唯最慢架构与 SH4/Landisk 因尚无共享库而与新构建体系的假设冲突待解；旧 X386 3.x 时代因 setup 程序依赖 Tk 而需另装 Tcl/Tk 的负担随之消失。　[存疑脚注] SH4 与 Landisk 细节经转写受损重建，须以 Xenocara 架构支持文档核对（BSDTalk EP106，[208.6-445.84]，L1）
- Herrb 兼任 X.org 安全官，管理流向 X.org 的全部安全类缺陷报告，长期计划是更主动地修复 X.org 代码库；他期待模块化降低参与门槛、吸引更多开发者关注 X 的局部如 3D 硬件加速，而 OpenBSD 此方向正缺志愿者。（BSDTalk EP106，[521.44-594.4]，L1）
- 他发出 Linux 中心化的当事人警示：X 是覆盖操作系统最广的开源项目之一（各 UNIX 变体、Windows、Mac OS X 等），但 X.org 的主导者似乎日益漠视非 Linux 系统；并非全世界都是 Linux，任何操作系统都不应以独占世界为目标；非 Linux 用户因自认小众而不报缺陷，使缺陷数量不反映各系统的重要性，他呼吁其他系统用户向上游提交报告以纠正这一错误计算。（BSDTalk EP106，[663.34-775.8]，L1）
- Jacek Masiulaniec 的路径：约十年前以游戏为目的接触计算机，经 Usenet 闻知 Linux，五年间试遍各发行版仍不满足；任小型 ISP 管理员时为解决流量整形问题，因 PF 队列系统在 OpenBSD 上远比 FreeBSD 易于配置，于 OpenBSD 3.8/3.9 前后转向，试过 FreeBSD 与 OpenBSD（未试 NetBSD）后留在后者。（BSDTalk EP179，[63.8-154.0]，L1）
- 他以源码可读性为标准选择学习材料：GNU 的 ls、ps 等小程序的风格令他无法卒读，OpenBSD 源码在他所见系统中最简单、最小、最紧凑；读完 Richard Stevens 的 Unix API 专著后寻找练手项目，恰逢 OpenSMTPD 导入源码树，从 imsg 框架与 buffer 例程读到 SMTP 服务器端，提交的修复数量多到因此获得开发者账号。（BSDTalk EP179，[188.5-287.6]，L1）
- OpenSMTPD 的定位与架构：他个人的目标是小型、紧凑、精干的 Sendmail 替代，但不排除高级特性，插件基础设施自始规划（对标 Sendmail 的 Milter 体系）；实现为典型 OpenBSD daemon 风格——特权分离与特权降级，与 BGPd、PF 等知名路由类 daemon 共享大量代码与思想，与 OpenSSH 共享思想，imsg 与 buffer API 通用于各 OpenBSD 服务器组件。（BSDTalk EP179，[298.6-443.9]，L1）
- 配置哲学：配置文件格式与 PF 高度相似，将邮件系统视为过滤器——消息本地投递抑或经远程网关中继取决于 SMTP 会话中匹配的规则；aliases 文件仅为 Sendmail 用户的兼容层而非必需；maps 层允许规则以别名参数指向 flat file、hashed file 或 SQL 数据库后端完成地址重写。（BSDTalk EP179，[359.4-637.9]，L1）
- 功能与成熟度：开箱支持 Mailbox 与 Maildir，并可经管道投递至任意外部程序；支持服务器与客户端两侧的 STARTTLS（暂缺客户端证书认证，计划实现）；虚拟主机为 sendmail 风格的定义文件且计划支持任意后端；随 OpenBSD 4.6 发布，但作者明确不推荐生产使用——current 中已有大量修复，建议自 CVS 获取最新源码。（BSDTalk EP179，[482.9-666.6]，L1）
- 可移植性评估：认证相关的 SMTP 扩展最暴露操作系统差异、部分代码不可移植；整体应可移植，已有 FreeBSD 与 NetBSD 的移植，尚无 Linux 或其他系统。（BSDTalk EP179，[445.9-482.9]，L1）
- Epitome（Marco Peereboom 的项目，Jacek 少量参与）：Unix 上的去重应用引擎，将文件切分为块、以 SHA-1 哈希存于可选后端（裸磁盘、Unix 目录或 SQL 数据库），后续备份仅存变化的块且块级压缩；对比 rsync 加硬链接的传统方案——小改动即复制整文件且无法压缩——并可随机提取存档中部文件而无需顺序读取。（BSDTalk EP179，[674.2-818.5]，L1）
- sensors 框架的状态自述：该框架自 OpenBSD 3.4 或 3.5 经由 NetBSD 继承而来，近六至八个月才被真正发力推进，整体仍属粗糙、用户态部分亟待重写；其固有难点是低端主板上的廉价监控芯片只报出挂接数量，软件只能枚举 fan1 至 fan4 而不知物理对应，高端 SCSI 领域则可经 enclosure services、ESM 或 IPMI 查询到 Baseboard Fan1、Power Supply 2 一类的设备名；驱动集中于 i386 与 AMD64，框架本身在全部架构启用且至少五个架构有专属驱动，SCSI 设备的温度报告亦接入。（BSDTalk EP46，[162.92-308.44]，L1）
- bio 框架的动机是让 RAID 状态首次可被软件感知：此前树内 RAID 控制器一律伪装为 SCSI 驱动，管理员只见逻辑盘，盘阵降级无从得知，只能进机房看闪灯或听蜂鸣——有管理员甚至一日两次派初级员工巡视机房；bio 的目标是经软件检测 RAID 降级并以邮件告警、进而支持软件修复盘阵；该框架完全自产、于最近一次 hackathon 才问世却已惊人可用，暂只支持 MegaRAID 控制器且限于 i386 与 AMD64，向其他架构扩展容易只是缺硬件。（BSDTalk EP46，[326.64-380.88]，L1）
- 软件 RAID 在 OpenBSD 的被忽视现状：树内仅有两个驱动——自 NetBSD 继承的 RAIDframe 极为庞大、亟须裁剪（NetBSD 在该领域投入远多），以及仅做镜像与条带化的极轻量 CCD、缺乏对付硬件故障族的智能；受访者坦言若有空闲愿意投入，制约因素纯粹是时间。（BSDTalk EP46，[382.36-434.80]，L1）
- 入门路径：1996 或 1997 年首装 Linux，得到提示符后不知所措而退回 Windows；入大学后因功课与共享网络需要 Unix，发现 OpenBSD 文档远比 Linux 的 howto 与贫乏文档可读而选择后者，自认当时不知为何没有选 FreeBSD；其对 OpenBSD 的第一项贡献是引入 USB 支持，经持续提交修复后获自行提交权限；此后遍历各 BSD 与多个 Linux，并在工作中照看 Solaris 机器。（BSDTalk EP46，[447.76-526.80]，L1）
- 桌面与服务器推荐的分野：其桌面定义仅为能 ssh、有浏览器、能放 MP3，此标准下 OpenBSD 完全胜任；但音频编辑、矢量图形等场景他不讳言会推荐 Mac OS 或 Windows，并自知此论会令社区不快；服务器端则除日历与 Exchange 支持外，OpenBSD 作任何他所工作过的网络的后端都能直接运转。（BSDTalk EP46，[675.60-717.52]，L1）
- 开发环境与社区对照：日常为 vi 加 make 加 screen 加当值语言，screen 被其称作有史以来第二重要的软件；他对 OpenBSD 开发社区的评价是极为支持与鼓励——报告 bug 会被认真对待、他人愿与你一同追踪直至修复，而其对比的图景是某些上游维护者一句我这儿正常便终结报告，令他困惑于对方无意改进软件；两种社区对待缺陷的方式构成鲜明差异。（BSDTalk EP46，[727.72-790.52]，L1）

**史观**：

- 总纲8 本体论上各方平等：Herrb 明言没有任何操作系统应当以成为世界唯一系统为目标，X 的价值恰在于跨系统的广泛可移植；他反对以 Linux 为唯一中心的生态趋向，主张各操作系统在 X 生态中保持平等地位，是多方平等立场在图形基础设施层的直接表达。（BSDTalk EP106，[663.34-732.56]，L1）
- 总纲10 动手者创造历史：从为自己不被支持的显卡修改 X386 驱动，到主导 Xenocara 重构 OpenBSD 的 X 构建体系，Herrb 的轨迹显示基础设施变革往往源于个体动手者解决自身具体困境的行动，而非自上而下的规划。（BSDTalk EP106，[119.36-134.56]，L1）
- 总纲9 经验优先：其转向与扎根的每个决策均由亲历问题驱动：ISP 流量整形的配置难度决定平台选择，源码可读性决定学习材料，练手需求决定项目进入——工具与阵营的取舍以第一手操作经验为准。（BSDTalk EP179，[133.5-232.5]，L1）
- 总纲10 动手者创造历史：从阅读基础设施代码、提交修复到获得账号的叙述表明，OpenBSD 的开发者晋升由实际提交的修复推动，日常动手与代码劳作本身即是进入项目史的通道。（BSDTalk EP179，[262.4-287.6]，L1）
- 总纲9 经验优先：代码质量教育的反思：大学课程教会 C、进阶 C 与 C++ 的语法基础，却没有教良好的编程实践，构成糟糕的代码质量根基；他自言是接触 OpenBSD 之后才相信自己能写出好代码；对新手的建议是去解决真正烦扰自己的问题并阅读他人优秀源码——项目之外坏代码被大量阅读并衍生更多坏代码，而好范例明明更多，决定代码能力的不是教材而是接触好代码的经验。（BSDTalk EP46，[533.12-622.68]，L1）
