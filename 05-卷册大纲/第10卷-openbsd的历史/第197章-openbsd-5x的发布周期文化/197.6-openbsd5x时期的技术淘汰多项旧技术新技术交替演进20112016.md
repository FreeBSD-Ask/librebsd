## 197.6.1 固定地址加载 → 全系统 ASLR（5.2-5.6，2012-2014）

**要点**：OpenBSD 的地址空间随机化基础设施由 matthew 于 2012-08-20 commit 5f7066906156ece39fb432bab1cea4415d608bfc 引入——"Add support for .openbsd.randomdata sections and PT_OPENBSD_RANDOMIZE segments to the kernel, ld (2.15), and ld.so"，测试覆盖 alpha、amd64、i386、macppc、sparc64；2013-12-28 deraadt commit 2afebeae30e91331fb9f4496daf6b629e95d4d93 引入从 /etc/random.seed 加载熵数据的机制，将熵插入内核 ELF .openbsd.randomdata 段；ASLR 完成“固定地址加载 → 随机化加载”的替代，成为 OpenBSD 对抗代码重用攻击的根本性防御

**史料**：openbsd.duckdb openbsd-src 仓库 commit 5f7066906156ece39fb432bab1cea4415d608bfc（2012-08-20 matthew"Add support for .openbsd.randomdata sections and PT_OPENBSD_RANDOMIZE segments"）、commit 2afebeae30e91331fb9f4496daf6b629e95d4d93（2013-12-28 deraadt“Try to load entropy data from disk:/etc/random.seed”）、commit 9bb65f61fd5c3769b8ef4152583f06b78297c945（2013-12-27 deraadt"do not need to create the stack cookie using a constructor anymore, since the kernel supplies a .openbsd.randomdata segment"）；OpenBSD 5.2 Release Notes（<https://www.openbsd.org/52.html>）［A］

**史观**：软件工程：ASLR 作为形式主义化安全机制改变程序加载形式——.openbsd.randomdata 段与 PT_OPENBSD_RANDOMIZE 程序头将熵注入从运行时构造函数转移至加载时内核填充，这一设计是“安全约束从用户态显式调用转移至内核隐式保障”的工程实践，对应总纲第 17 条“形式与内容”的内在逻辑

**辨析**：原大纲称“OpenBSD 5.0（2011.11）由 Mike Belopuhov（迈克·别洛普霍夫） 等引入 KARL”——经 openbsd.duckdb 核查，此 attribution 有误：①bsd_commits.duckdb openbsd-src 仓库中无任何 Belopuhov 的 commit 记录（搜索模式‘%Belopuhov%’、‘%belopuhov%’均返回 0 条结果）；②.openbsd.randomdata/PT_OPENBSD_RANDOMIZE 基础设施的首次 commit 为 2012-08-20 by matthew，对应 OpenBSD 5.2 开发周期（5.1 于 2012-05 发布，5.2 于 2012-11 发布），而非 5.0（2011.11）；③ 从 /etc/random.seed 加载熵的机制首次 commit 为 2013-12-28 by deraadt，对应 5.5 开发周期；KARL（Kernel Address Space Layout Randomization）的完整启用版本以 OpenBSD Release Notes 为准 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

## 197.6.2 OpenSSL → LibreSSL fork（5.6，2014）

**要点**：2014 年 4 月 Heartbleed 漏洞（CVE-2014-0160）暴露 OpenSSL TLS heartbeat 扩展的缓冲区越界读取缺陷；OpenBSD 团队当即响应——2014-04-07 djm commit af0b15b8442f"cherrypick fix for CVE-2014-0160‘heartbleed’vulnerability from OpenSSL git"，2014-04-13 miod commit 9eac5592c816 导入 OpenSSL 1.0.1g，2014-04-14 beck 开始移除 OpenSSL 中的 Atalla/AEP 引擎，jsing 开始对 OpenSSL 代码应用 KNF 格式化；LibreSSL 作为独立库的首次 commit 为 2014-07-12 jsing commit b6553af36068"Initial version of libressl - a library that provides a clean, simple, consistent and secure-by-default API"；LibreSSL 作为 OpenBSD 5.6（2014.11）默认 TLS 库发布

**史料**：openbsd.duckdb openbsd-src 仓库 commit af0b15b8442f（2014-04-07 djm Heartbleed fix）、commit 9eac5592c816（2014-04-13 miod 导入 OpenSSL 1.0.1g）、commit b6553af36068（2014-07-12 jsing“Initial version of libressl”）；CVE-2014-0160 详情（<https://cve.mitre.org/cgi-bin/cvename.cgi?name=CVE-2014-0160>）；Heartbleed 官网（<http://heartbleed.com/>）；LibreSSL 官方公告（<https://www.libressl.org/>）；OpenBSD 5.6 Release Notes（<https://www.openbsd.org/56.html>）［A］

**史观**：密码学：Heartbleed 暴露密码学库的工程质量问题——OpenSSL 作为全球 HTTPS 基础设施的核心组件，其代码质量（dead code、维护混乱）与安全关键性不匹配，这一矛盾催生 LibreSSL fork；法律结构：LibreSSL fork 是 OpenBSD 对 OpenSSL 工程失败的回应，选择 fork 而非合作是 OpenBSD 许可证纯洁性哲学的实践

**辨析**：LibreSSL fork 的具体时间线——Heartbleed 于 2014-04-07 披露，OpenBSD 当即开始 OpenSSL 代码清理（2014-04-13 导入 1.0.1g，2014-04-14 beck 移除引擎、jsing 应用 KNF），LibreSSL 作为独立库的首次 commit 为 2014-07-12（jsing），LibreSSL 随 OpenBSD 5.6（2014-11）作为默认 TLS 库发布；Beck 是 fork 的主要协调者，jsing 是 libressl 库初始代码的提交者，二者角色不同——Beck 负责对外沟通与 dead code 清理，jsing 负责库架构设计与初始实现；Heartbleed 的责任归属——部分归咎 OpenSSL 项目（代码质量差、维护流程不透明），部分归咎使用方未及时更新；漏洞的实际影响范围无权威统计 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

## 197.6.3 gcc → clang/LLVM 替代（5.6-5.7，2014-2015）

**要点**：OpenBSD 的 gcc→clang/LLVM 切换是渐进过程——openbsd.duckdb 显示 2014-10-23 brad commit 6ad07a3f66f922604b423b6f0c03f220ffafd886 提及“Now that gcc2 is gone”，表明 gcc2 在 5.6 开发周期（2014 年下半年）已移除；2015-01-04 daniel commit 84938a7b9c572efc85c2b06e24f6122d8cc98702“remove code for ancient gcc”，2015-02-15 miod commit 1c93e2863e3b9f1c0c7e436e2db3db4debd0d628“Remove ancient gcc workaround on mips”，表明 5.7 开发周期（2015 年上半年）继续清理 gcc 残留代码；切换动机包括 gcc GPLv3 许可证与 OpenBSD ISC 许可证传统的冲突、clang/LLVM 的模块化设计与更好诊断信息

**史料**：openbsd.duckdb openbsd-src 仓库 commit 6ad07a3f66f922604b423b6f0c03f220ffafd886（2014-10-23 brad“Now that gcc2 is gone”）、commit 84938a7b9c572efc85c2b06e24f6122d8cc98702（2015-01-04 daniel“remove code for ancient gcc”）、commit 1c93e2863e3b9f1c0c7e436e2db3db4debd0d628（2015-02-15 miod“Remove ancient gcc workaround on mips”）；OpenBSD 5.7 Release Notes（<https://www.openbsd.org/57.html>）；Marc Espie 在 tech@ 关于 clang 切换的讨论（<https://marc.info/?laccopenbsd-tech>）［A］

**史观**：总纲第 24 条——法律结构：gcc GPLv3 与 OpenBSD ISC 许可证哲学的张力催生 clang/LLVM 替代——OpenBSD 以“许可证纯洁性优先”为预设，宁可承受编译器切换的工程代价也不接受 GPLv3 对基本系统的“污染”；技术选择的代价：切换的代价是部分架构的编译器稳定性需重新验证

**辨析**：gcc 到 clang/LLVM 的切换是渐进过程而非单一版本切换——gcc2 在 5.6 开发周期（2014 年下半年）已移除（brad 2014-10-23 commit 明确记载“Now that gcc2 is gone”），5.7 开发周期（2015 年上半年）继续清理 gcc 残留代码（daniel 2015-01-04、miod 2015-02-15）；切换动机以 de Raadt 与 Espie 在 tech@ 邮件列表的发言为准——许可证因素（GPLv3 与 ISC 不兼容）与技术因素（clang 的更好诊断信息）均为动机，前者在 de Raadt 的发言中权重更高；clang/LLVM 在不同架构上的成熟时间以 Release Notes 为准——amd64、i386 先行，arm64、sparc64 后续跟进

**文献**：openbsd.duckdb openbsd-src 仓库 commit 6ad07a3f66f922604b423b6f0c03f220ffafd886、84938a7b9c572efc85c2b06e24f6122d8cc98702、1c93e2863e3b9f1c0c7e436e2db3db4debd0d628；OpenBSD 5.7 Release Notes [EB/OL]. <https://www.openbsd.org/57.html>；OpenBSD tech@ 邮件列表档案 [EB/OL]. <https://marc.info/?laccopenbsd-tech> ［A］

## 197.6.4 朴素权限模型 → pledge 系统调用引入（5.9，2016.3.29）

**要点**：**pledge(2)** 的前身是 tame(2) 子系统，由 de Raadt 于 2015-07-19 commit 586b470f3a48 引入（"tame(2) is a subsystem which restricts programs into a‘reduced feature operating model’“）；2015-07-29 de Raadt commit c75cc85e06c9”Neuter tame(2) with ENOSYS for upcoming release cycle"在 5.8 release 前禁用 tame；2015-08-20 de Raadt commit b5edfc0c1710“reactivate tame()”重新激活；2015-10-09 de Raadt commit 350b464c5787 将 tame() 重命名为 pledge()（"Rename tame() to pledge(). This fairly interface has evolved to be more strict than anticipated"）；pledge 在 OpenBSD 5.9（2016-03-29 发布）中正式启用；pledge 让进程自愿放弃特定权限（如网络、文件系统访问），进程在程序启动时调用 `pledge("stdio rpath", NULL)` 即可限制权限

**史料**：openbsd.duckdb openbsd-src 仓库 commit 586b470f3a48（2015-07-19 deraadt“tame(2) is a subsystem...”）、commit c75cc85e06c9（2015-07-29 deraadt“Neuter tame(2) with ENOSYS for upcoming release cycle”）、commit b5edfc0c1710（2015-08-20 deraadt“reactivate tame()”）、commit 350b464c5787（2015-10-09 deraadt“Rename tame() to pledge()”）；OpenBSD 5.9 Release Notes（<https://www.openbsd.org/59.html>）；**pledge(2)** 手册页（<https://man.openbsd.org/pledge.2>）［A］

**史观**：总纲第 17 条——软件工程：pledge 是“最小权限”原则的系统调用化实现——进程自愿声明所需权限子集，内核据此拒绝越权系统调用，这一设计将安全约束从外部沙箱转移至程序自身声明，是软件工程中“白名单优先于黑名单”原则在操作系统接口层的实践

**辨析**：pledge 的引入版本——经 openbsd.duckdb 核查，tame() 于 2015-07-19 引入（5.8 开发周期），2015-07-29 在 5.8 release 前禁用（c75cc85e06c9“Neuter tame(2) with ENOSYS for upcoming release cycle”），2015-08-20 重新激活，2015-10-09 重命名为 pledge()，5.9（2016-03-29）正式启用；原大纲称“5.4 已有雏形”系误记——5.4（2013.11）时 tame/pledge 均不存在，tame 的最早 commit 为 2015-07-19；pledge 与 Linux seccomp 的工程哲学比较——seccomp 以 BPF 过滤器提供细粒度系统调用控制但配置复杂，pledge 以预定义权限类别提供粗粒度控制但配置简洁，二者设计目标不同

**文献**：openbsd.duckdb openbsd-src 仓库 commit 586b470f3a48、c75cc85e06c9、b5edfc0c1710、350b464c5787；OpenBSD 5.9 Release Notes [EB/OL]. <https://www.openbsd.org/59.html>；**pledge(2)** 手册页 [EB/OL]. <https://man.openbsd.org/pledge.2> ［A］

**要点**：

- John-Mark Gurney 自述 1994 年经同学影响接触 A/UX 与 Unixware 后，在 Slackware（目录硬性布局）、NetBSD（当年安装文档难懂）与 FreeBSD 之间选择后者，以 230KB 引导块完成 1.1.5.1 安装；高中时期提交 fsck 指定文件系统参数的约五六十行补丁并持续撰写工具与 SCSI man page，1997 年初获 commit bit。 [存疑脚注] 转写记为 AUX、fisk、MS-TOS，分别应为 A/UX、fsck 及待核的 DOS 变体；引其入 commit bit 的 George 具体所指待核。（BSD Now EP61，[900.66-1115.64]，L1）
- IPsec 现代化项目由 Netgate（pfSense 开发商）的 Jim Thompson 发起、经 FreeBSD Foundation 资助 Gurney 执行：FreeBSD opencrypto 框架长期缺失 AES-CTR 与 AES-GCM 模式，未利用 AES-NI 与 PCLMULQDQ 指令，项目目标是在廉价商用硬件上经 pfSense 实现约 10Gb/s 加密转发，而彼时软件加密仅数百 MB/s。（BSD Now EP61，[1117.88-1264.12]，L1）
- 当事人给出密码学工程论证：CBC 加密因块间数据依赖无法流水线化（解密方向可反向并行），CTR 以加密计数器异或明文消除依赖；GCM 作为 AEAD 将加密与认证合一提升吞吐；ChaCha20-Poly1305 尚处草案但其软件性能适合无 AES 指令的设备；Gurney 自写的新 GCM 软件实现性能优于 OpenBSD 版并计划反馈；他主张密码学实现应从五个收敛为两三个以便修错与复核，并指出 OpenBSD 版本缺少 FreeBSD 的 SMP 锁但差异仅数行。（BSD Now EP61，[1355.10-1662.62]，L1）
- 主持人转述 OpenBSD 5.6（2014 年 11 月 1 日发布）要点：作为六个学期准时发布周期的延续，5.6 是首个正式搭载 LibreSSL 的版本，新增休眠至全加密文件系统的能力；移除 AltQ 插件式流量整形框架（研究使命完成，HFSC 直用并简化配置），并处于服务栈过渡期——Apache 已由 Nginx 替代、下版再由 httpd 接替，Sendmail、BIND 分别让位 OpenSMTPD 与 Unbound，Kerberos、Bluetooth、TCP wrappers 同时移除；发行歌与 CD 套装销售为 OpenBSD Foundation 主要收入。 [存疑脚注] 转写将 httpd 记为 HDBD、OpenSMTPD 记为 open SMTBD，须以 5.6 官方 changelog 复核。（BSD Now EP61，[479.30-754.10]，L2）
- Theo de Raadt 亲述 OpenBSD 起源：386BSD 停滞、NetBSD 成立后他作为首批四人之一加入；随后因与 NetBSD 的冲突失去仓库访问权，最终另立仓库，OpenBSD 由此诞生。（BSD Now EP6，[508.09-609.45]，L1）
- CSRG 遭入侵事件使其重新转向安全，此后 OpenBSD 建立全代码审计传统；审计后又认识到审计还不够，继而引入 ProPolice 等防护机制。（BSD Now EP6，[594.81-721.24]，L1）
- OpenBSD 几乎不设正式政策，开发者各自在领域内推进，de Raadt 自称最后的协调者；项目不维护分支，开发者与用户同处一条前进的代码路径，并鼓励用户运行快照。（BSD Now EP6，[845.54-908.82]，L1）
- de Raadt 主题演讲论述 64 位 time_t 的必要性：32 位与 16 位嵌入式系统仍将长期存在，SCADA 等关键基础设施升级周期缓慢，须尽早跨越 Y2038 时间曲线。（BSD Now EP6，[1131.78-1233.30]，L1）
- FreeBSD 发行工程团队在代码冻结后审批所有针对该分支的变更，目标是在已知良好状态上修复既有问题而非引入新特性，以降低升级回归风险。（BSD Now EP2，[2347.62-2437.94]，L1）
- Glen Barber 加入 FreeBSD 基金会后获得专职时间协调发布流程，并兼管集群管理团队与项目资源维护，使发布节奏不再完全依赖志愿者的时间。（BSD Now EP2，[4398.47-4558.76]，L1）
- FreeBSD 10-CURRENT 自 2013 年 9 月起不再默认构建 GCC，基本系统改以 Clang 为默认编译器；需要 GCC 的场景改由 ports 提供现代版本。（BSD Now EP2，[543.86-622.62]，L2）
- LDNS 与 Unbound 正被移植入 FreeBSD 基本系统，计划在 10.0 前移除 BIND；主持人预期此举可减少约三分之一的安全公告负担。（BSD Now EP2，[4075.30-4225.94]，L1）
- Poudriere 以 jail 隔离并发构建二进制包，可在一台机器上按 FreeBSD 版本与架构分 jail 编译，并以增量重建与摘要签名支撑自有 pkg 仓库分发。（BSD Now EP2，[865.40-904.68]，L2）
- 该期头条报道 OpenBSD 已实现 64 位 time_t，以避免 2038 年 32 位时间戳溢出；该改动使 32 位平台也能跨越 Y2038 时间曲线。（BSD Now EP2，[71.70-150.60]，L2）
- Henning Brauer 自述正在重写 PF 的队列子系统以取代旧 ALTQ：旧实现约九千行代码、带有 32 位上限且使用方式过于困难，新实现按 PF 原生方式重建队列功能；计划保留旧 ALTQ 一至两个发布周期供用户过渡，届时重命名若干冲突关键词，迁移成本基本只是一次配置调整。（BSDTalk EP214，[90.0-179.32]，L1）
- rthreads 是 OpenBSD 5.1 发布后 current 中最重大的变化：一对一的线程实现使用户态每个线程对应一个内核线程，取代此前内核只见单一进程的用户态模拟线程；旧实现要求全部文件描述符置为非阻塞并手工模拟阻塞语义，既无法利用多核又不可能百分之百正确。作者据当事人口述约在 2004 或 2006 年提交首批代码，启用后经过一个完整六个月开发周期除错，主要遗留问题是 CPU 时间统计与文件描述符表锁定。 [存疑脚注] 受访者本人对 rthreads 首批提交年份不确定（2004 或 2006），转写将提交者名转写为 TATU，通常应指 tedu（Ted Unangst），须以仓库提交记录核证（BSDTalk EP214，[2214.26-2427.73]，L1）
- BGPD 是第一个采用 PF 风格配置语言与内部消息传递框架的守护进程，其后 OpenNTPD、OpenSMTPD 等新写守护进程均沿用该框架，重复代码后来收拢为库；设计目标是使仅懂英语者读配置文件即可了解守护进程行为，与 sendmail 需要八百页专著的复杂性形成对照。OpenSMTPD 沿用 OpenBSD 特权分离模型，受访者判断 BSD 许可的邮件服务器在此之前长期缺位。（BSDTalk EP214，[2769.76-2909.16]，L1）
- OpenBSD 存储栈早期即决定不在硬件 RAID 控制器之上另建逻辑盘接口，而是在控制器之上加 SCSI 模拟层；此后业界反向跟进，硬件 RAID 控制器如今直接在逻辑盘上呈现 SCSI 接口，SCSI 由一种存储接口演化为通用协议。SATA 设备经 SAS ATA 翻译层归入同一路径，与 Linux 与 Solaris 的做法一致，仅旧式 PCI IDE 设备尚未迁移；项目目标是使一切硬件存储最终呈现为 SCSI 盘，SD 卡与 U 盘均已达成，遗留的只有老式并行 ATA 与个别旧架构直连盘驱动。（BSDTalk EP219，[423.04-551.28]，L1）
- SCSI 协议的长寿源于其结构简单与后向兼容：协议本质是命令帧加可选数据载荷，每版协议虽为新读写命令各立条目，但新版本包含对旧版的兼容支持，需要新特性时只是增设新消息。闪存以薄置备 SCSI 盘形式通告逻辑块与物理块无关，配合四千字节物理块对五百一十二字节逻辑块的通告，协议已足以支撑上层软件对存储特性的利用，其灵活性正是普遍性的原因。（BSDTalk EP219，[570.16-700.64]，L1）
- 存储性能的瓶颈已从设备数转向命令槽资源调度：二十年前的 SCSI 总线挂七台设备、每台一至两个命令槽，如今 SAS 与 RAID 控制器可管理一二八至五一二台设备、每台可有上千命令槽，而适配器自身槽位有限，如何调度这些槽位成为核心问题。受访者刻意淡化大内核锁问题的优先级，理由是处理器增速远超磁盘与适配器，宁可在锁上自旋也不可浪费命令槽；SCSI 中层细粒度锁虽已预先布置，其正确性须待整个内核脱离大锁才能验证。（BSDTalk EP219，[727.06-846.5]，L1）
- MCLGETI 的设计动因是巨型帧描述符环的内存压力：九千字节帧乘以五百一十二项描述符环会侵占内核本已有限的内存，在部分架构上内核仅能使用主机内存中的六七十兆；该机制默认仅为环填入两个槽位，按每个中断的实际用量渐进扩大分配，其后 Theo de Raadt 将其推广为背压机制，在系统耗尽处理器时间时限制递交给网卡的包量以归还算力。受访者自述其生产系统已放大其他拥塞限制，仅依赖 MCLGETI 承担过载保护。（BSDTalk EP219，[1002.74-1234.8]，L1）
- Brauer 自述其在柏林 hackathon 收尾的校验和处理重写：新模型假定每条输出路径都具备校验和硬件卸载能力，栈上层不再预计算与就地修补校验和，仅需在数据包上置标记声明需要何种协议校验和，全部计算集中到输出路径末端的单一位置，仅在确知该路径无卸载能力时才回退软件实现。（BSDTalk EP234，[305.23-320.29]，L1）
- 旧实现的缺陷根源在于部分网卡（以 Intel 与 Broadcom 千兆芯片为代表，约占服务器市场九成）要求保留伪头校验和，而另一些网卡做全量卸载，PF 无法判别数据包携带的是部分校验和还是完整校验和，就地更新便可能出错；重写后栈上层彻底不管校验和，桥接路径也被修正；ICMP 错误报文中被引用原始包的校验和因多数被截断而无法验证，选择忽略，并以手工构造异常报文的专用工具对 PF 行为做验证。（BSDTalk EP234，[822.90-1029.94]，L1）
- 新排队子系统分两层：优先级排队极为简单，把 ifnet 结构的单一输出队列头改为八个队列的数组并按序处理，默认优先 CARP 公告与生成树报文以防主备双主故障，且常开不可关闭；带宽整形部分则取代约一万二千行的 AltQ——后者原是 Kenjiro Cho 十余年前的论文研究项目，2003 年 Cho 与 Brauer 将其并入 PF 使 PF 充当分类器，次年加入的 HFSC 因语法难懂而少有人用，用户多用较简单的 CBQ——新版保留可完全表达 CBQ 的 HFSC、重写胶水层并删除可插拔调度器框架，全系统缩至约三千五百行，随 OpenBSD 5.5 提交。（BSDTalk EP234，[374.70-624.38]，L1）
- 关于 PF 的可移植性，Brauer 区分了两类情形：OpenSSH 是用户态、大体以 POSIX 为边界的守护进程集合，故能维持 portable 版本；PF 是内核的内嵌成分，依赖各操作系统的内存管理，可移植难度更高，但 Apple 与 QNX 均已集成 PF，FreeBSD 的移植虽面对不同的内存管理也无需重写一半，各系统挂接网络栈的方式差异有限。（BSDTalk EP234，[1449.18-1525.40]，L1）
