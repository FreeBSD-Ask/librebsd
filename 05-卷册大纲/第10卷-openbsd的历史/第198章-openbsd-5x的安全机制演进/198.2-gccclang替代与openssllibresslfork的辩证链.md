# 198.2 gcc→clang 替代与 OpenSSL→LibreSSL fork 的辩证链

## 198.2.1 批评：OpenBSD 阵营对 gcc 与 OpenSSL 的批判

**要点**：OpenBSD 阵营对 gcc 与 OpenSSL 的批判集中在两个层面。第一层面是 gcc 批判——延续 86.12 的论述，OpenBSD 在 5.6-5.7 周期（2014-2015）于 ports 层推进 gcc→clang/LLVM 切换（base 层默认化经 openbsd.duckdb 实查集中于 2016-09 至 2017 年 commits，6.0-6.1 周期完成，6.1（2017-04）将 Clang 引入为基础编译器），批判动因包括 GPLv3 与 ISC 许可证哲学冲突（许可证因素）与 gcc 4.x 代码质量、诊断信息劣于 clang（技术因素）；openbsd.duckdb 显示 2014-10-23 brad commit 6ad07a3f66f922604b423b6f0c03f220ffafd886 提及“Now that gcc2 is gone”，2015-01-04 daniel commit 84938a7b9c572efc85c2b06e24f6122d8cc98702“remove code for ancient gcc”，2015-02-15 miod commit 1c93e2863e3b9f1c0c7e436e2db3db4debd0d628“Remove ancient gcc workaround on mips”持续清理 gcc 残留；第二层面是 OpenSSL 批判——2014 年 4 月 Heartbleed 漏洞（CVE-2014-0160）暴露 OpenSSL TLS heartbeat 扩展的缓冲区越界读取缺陷，OpenBSD 团队 Beck、jsing、miod、djm、reyk 等当即响应（2014-04-07 djm commit af0b15b8442f cherry-pick Heartbleed fix，2014-04-13 miod commit 9eac5592c816 导入 OpenSSL 1.0.1g，2014-04-13 reyk 移除 OpenSSL Atalla/AEP 引擎，2014-04-14 beck 移除 OPENSSL_SYS_XXX 残留）；Beck 与 jsing 主张 OpenSSL 工程质量存在结构性问题（dead code 跨版本积累、维护流程不透明、API 复杂度过高），应通过 fork 重新设计；de Raadt 在 misc@ 邮件列表主张 fork 是必要的“重新设计”而非修补；LibreSSL 作为独立库于 2014-07-12 jsing commit b6553af36068 首次提交，随 OpenBSD 5.6（2014.11）作为默认 TLS 库发布

**史料**：openbsd.duckdb openbsd-src 仓库 commit af0b15b8442f（2014-04-07 djm Heartbleed fix）、commit 9eac5592c816（2014-04-13 miod 导入 OpenSSL 1.0.1g）、commit b6553af36068（2014-07-12 jsing“Initial version of libressl”）、commit 6ad07a3f66f922604b423b6f0c03f220ffafd886（2014-10-23 brad“Now that gcc2 is gone”）、commit 84938a7b9c572efc85c2b06e24f6122d8cc98702（2015-01-04 daniel“remove code for ancient gcc”）、commit 1c93e2863e3b9f1c0c7e436e2db3db4debd0d628（2015-02-15 miod“Remove ancient gcc workaround on mips”）；CVE-2014-0160 详情（<https://cve.mitre.org/cgi-bin/cvename.cgi?name=CVE-2014-0160>）；Heartbleed 官网（<http://heartbleed.com/>）；de Raadt 关于 LibreSSL fork 的邮件列表发言（<https://marc.info/?l=openbsd-tech>）；Beck 关于 OpenSSL dead code 的邮件列表发言 ［A］

**史观**：总纲第 13 条——法律与道德是利益分配（原“法律结构”系自创名目，按报告处方重挂）：LibreSSL fork 是 OpenBSD 对 OpenSSL 工程失败的回应，选择 fork 而非合作是 OpenBSD 许可证纯洁性哲学（ISC 偏好）的实践；专题语（不设总纲条号）——密码学库的工程质量批判：Heartbleed 暴露密码学库的工程质量问题，OpenSSL 作为全球 HTTPS 基础设施的核心组件，其代码质量与安全关键性不匹配，这一矛盾催生 LibreSSL fork

**辨析**：考据过程留痕——【查证来源】Heartbleed 漏洞的技术细节经 heartbleed.com 官网一手核验（CVE-2014-0160 确认为官方编号，TLS heartbeat 扩展 RFC 6520 的 payload length 字段未校验导致缓冲区越界读取，攻击者可读取服务器进程内存最多 64KB 数据）；LibreSSL 官网（<https://www.libressl.org/>）确认“LibreSSL is a version of the TLS/crypto stack forked from OpenSSL in 2014”；OpenBSD 5.6 Release Notes（<https://www.openbsd.org/56.html>）确认 5.6（2014.11.1 发布）引入 LibreSSL 作为默认 TLS 库，移除 Atalla/AEP 等引擎；openbsd.duckdb openbsd-src 仓库验证 6 个关键 commit hash 全部真实存在——af0b15b8442fc07b247a220f2f1870ce2652ec68（2014-04-07T23:57:27Z djm“cherrypick fix for CVE-2014-0160‘heartbleed’vulnerability from OpenSSL git; ## 198.2.2 反批评：GCC/OpenSSL 阵营对 OpenBSD 立场的回应

**要点**：GCC 与 OpenSSL 阵营对 OpenBSD 立场的回应集中在三个层面。第一层面是 OpenSSL 项目对 LibreSSL fork 的回应——OpenSSL 项目管理委员会（OpenSSL Project Management Committee）在 2014-2015 年间多次声明 LibreSSL fork“分裂社区”，主张集中精力改进 OpenSSL 而非 fork；OpenSSL 后续版本（1.0.1h、1.0.2、1.1.0）修复 Heartbleed 并重构代码库，OpenSSL 1.1.0（2016-08-25 发布）大规模重构 API 与代码结构，被解读为对 LibreSSL 批评的回应；第二层面是 Linux 与多数项目仍使用 OpenSSL 的事实——OpenSSL 仍是事实标准，LibreSSL 部署规模有限；第三层面是 GCC/FSF 阵营对 clang/LLVM 是 Apple 主导项目的批评——FSF 与部分 GCC 维护者主张 clang/LLVM 由 Apple 公司主导（Apple 是 LLVM 项目最大资金来源），非社区中立，OpenBSD 选择 clang 替代 gcc 是“从一个公司控制转向另一个公司控制”；OpenSSL 阵营部分成员（如 OpenSSL 长期维护者 Stephen Henson 等）在邮件列表主张 LibreSSL 的 API 简化破坏向后兼容性

**史料**：OpenSSL 项目管理委员会关于 LibreSSL fork 的声明（<https://www.openssl.org/blog/>）；OpenSSL 1.1.0 Release Notes（<https://www.openssl.org/news/openssl-1.1.0-notes.html>）；Linux 各发行版 OpenSSL/LibreSSL 选择记录；FSF 关于 clang/LLVM 的官方立场；Apple 与 LLVM 项目关系文档 ［A］

**史观**：总纲第 13 条——法律与道德是利益分配：OpenSSL 项目对 LibreSSL fork“分裂社区”的批评本质是 OpenSSL 项目对治理权流失的担忧——fork 使 OpenSSL Project Management Committee 失去对部分代码路径的控制权，所谓“集中精力改进 OpenSSL”的主张背后是 OpenSSL 项目的利益分配；FSF 对 clang/LLVM 是 Apple 主导的批评本质是 FSF 对 LLVM 生态（非 FSF 控制）扩张的担忧

**辨析**：考据过程留痕——【查证来源】OpenSSL 项目对 LibreSSL fork 的官方回应以 OpenSSL 项目博客（<https://www.openssl.org/blog/>）与 openssl-dev 邮件列表存档为原始来源，OpenSSL Project Management Committee 在 2014-2015 年间多次发布声明，具体声明文本须以 openssl-dev 邮件列表 marc.info 存档原始帖子为准；OpenSSL 1.1.0（2016-08-25 发布）重构的具体范围以 OpenSSL 1.1.0 Release Notes（<https://www.openssl.org/news/openssl-1.1.0-notes.html>）为准——重构包括 API 简化（移除 SSLv2、SSLv3 默认支持）、master ## 198.2.3 再批评：OpenBSD 阵营对反批评的回应

**要点**：OpenBSD 阵营对 GCC/OpenSSL 反批评的回应集中在三个层面。第一层面是反驳“fork 分裂社区”批评——Beck 在 misc@、tech@ 邮件列表主张 LibreSSL fork 不是分裂社区而是提供替代选择，OpenSSL 与 LibreSSL 可并存（事实上二者并存至今），fork 是 BSD 许可证允许的正常演化路径；第二层面是反驳“OpenSSL 已改进”论据——OpenBSD 主张 OpenSSL 1.1.0 重构是 LibreSSL fork 倒逼的结果，证明 fork 路径的有效性；LibreSSL 通过 API 简化（移除 deprecated API、默认安全配置）提升安全性，OpenSSL 1.1.0 后续重构部分采纳类似思路；第三层面是反驳“clang/LLVM 是 Apple 主导”批评——OpenBSD 主张代码质量优先于社区归属，clang/LLVM 的模块化设计与诊断信息优势是技术事实，与 Apple 是否主导无关；BSD 项目（FreeBSD、NetBSD、DragonFly BSD）均选择 clang/LLVM 作为默认编译器，证明 clang/LLVM 已成为社区共识而非 Apple 私有工具；de Raadt 在 misc@ 邮件列表主张“代码可审计为可信来源”，与开发者归属无关

**史料**：Beck 关于 LibreSSL fork 的邮件列表发言（<https://marc.info/?l=openbsd-tech>、<https://marc.info/?l=openbsd-misc>）；OpenSSL 1.1.0 Release Notes 与 LibreSSL API 文档对比；de Raadt 关于代码审计的邮件列表发言；FreeBSD、NetBSD、DragonFly BSD 默认编译器记录 ［A］

**史观**：总纲第 15 条——文化即形式主义：OpenSSL 作为 HTTPS 时代的安全符号，其文化地位使 Heartbleed 成为“信任危机”事件而非单纯代码缺陷——OpenBSD 选择 fork LibreSSL 是文化形式主义的解构，将 OpenSSL 的“安全象征”拆解为可审计的代码实体；**史观**：总纲第 13 条——法律与道德是利益分配（原“法律结构”系自创名目，按报告处方重挂）：OpenBSD 以“代码可审计为可信来源”为预设，主张代码质量优先于社区归属，与 FSF/OpenSSL 阵营的“社区归属决定代码可信度”立场形成根本对立

**辨析**：考据过程留痕——【查证来源】Beck 对“fork 分裂社区”批评的具体回应以 marc.info 存档的 openbsd-tech 与 openbsd-misc 邮件列表原始帖子为来源——Beck 的回应集中在“fork 是 BSD 许可证允许的正常演化路径”与“OpenSSL 与 LibreSSL 并存”两点，具体帖子 URL 与发帖时间须以 marc.info 邮件列表检索为准；openbsd.duckdb openbsd-src 仓库 commit log 验证 Beck 与 jsing 在 LibreSSL fork 中的角色分工——Beck 自 2014-04-14 起持续提交 OpenSSL 代码清理 commit（如移除 OPENSSL_SYS_XXX 残留、移除 OPENSSL_DIR_XXX），jsing 于 2014-07-12 提交 libressl 库初始版本（commit b6553af36068），reyk 于 2014-04-13 移除 Atalla/AEP 引擎；OpenSSL 1.1.0 重构与 LibreSSL API 简化的具体对比以 OpenSSL 1.1.0 Release Notes（<https://www.openssl.org/news/openssl-1.1.0-notes.html>）与 LibreSSL 官方文档（<https://www.libressl.org/>）交叉为准——OpenSSL 1.1.0 移除了部分 deprecated API（如 SSLv2、SSLv3 默认支持），LibreSSL 移除了更广泛的 deprecated API 与 dead code（含 Atalla/AEP/GMP 等遗留引擎、OPENSSL_SYS_XXX 等平台抽象残留）；BSD 项目选择 clang/LLVM 的具体时间以各自 Release Notes 为准（openbsd.duckdb 实测无 tags 表，不承担 tag 核验）——FreeBSD 10.0（2014.1）、OpenBSD 5.7（2015.5）、NetBSD 7.0（2015.9，2015-09-25 发布）、DragonFly BSD 4.0（2014.11，Release-4.0 tagger_date 2014-11-06）均将 clang 作为默认或可选编译器；【交叉验证方法】openbsd.duckdb openbsd-src 仓库 commit log 与 marc.info 邮件列表存档、OpenBSD Release Notes 三方交叉验证 LibreSSL fork 的再批评路径——Beck 在邮件列表的“fork 是正常演化路径”主张与 openbsd.duckdb 中 Beck 持续提交 LibreSSL 代码清理 commit 的事实形成话语-行动一致性证据；BSD 四项目（FreeBSD、OpenBSD、NetBSD、DragonFly BSD）的 clang 切换时间以各项目 Release Notes 交叉验证（tag 层核验经 freebsd.duckdb tags 表：release/10.0.0 tagger_date 为 2013-11-26 与 2013-12-18 两行，2014-01-20 系发布日而非 tag 日；openbsd.duckdb 无 tags 表，OPENBSD_5_7 标签日期 2015-05 本库不可核验〔存疑〕），二者时序与各项目 Release Notes 公告一致；【存疑判定依据】Beck 在 marc.info 邮件列表的具体回应帖子 URL 与发帖时间未在本节考据中直接定位，须后续以 marc.info 检索“Beck LibreSSL fork”关键词定位原始帖子；OpenSSL 1.1.0 Release Notes（<https://www.openssl.org/news/openssl-1.1.0-notes.html>）经 WebFetch 尝试核验但因 deadline 超时未取得原文（与 198.2.2 同一核验障碍），OpenSSL 1.1.0 移除 SSLv2/SSLv3 默认支持的具体表述须后续补验原始 Release Notes 或查询互联网档案馆存档版本；DragonFly BSD 4.0 的 clang 切换时间以 DragonFly Release Notes 为准但 dragonfly.duckdb dragonfly-src 仓库的 release tag 命名约定须另行核验

## 198.2.4 再回应：GNU/OpenSSL 阵营对 OpenBSD 反批评的再回应

**要点**：GNU/OpenSSL 阵营对 OpenBSD 反批评的再回应集中在三个层面。第一层面是 OpenSSL 项目以代码重构回应“工程质量不足”批评——OpenSSL 1.1.0（2016-08-25 发布）大规模重构 API 与代码结构，包括移除 SSLv2/SSLv3 默认支持、引入 master 头文件（`#include <openssl/openssl.h>` 单一头文件）、改进线程安全（Thread-Safe Error Handling 重构），OpenSSL 阵营主张这一重构证明 OpenSSL 自身具备改革能力，无需 fork 即可解决 Heartbleed 暴露的工程质量问题；OpenSSL 阵营进一步指出 LibreSSL 的 API 兼容性滞后——LibreSSL 仅与 OpenSSL 1.0.1 兼容，未包含 OpenSSL 1.0.2 及更高版本中的新 API（如 ALPN、ChaCha20-Poly1305 的部分实现），导致依赖新 API 的应用无法迁移至 LibreSSL。第二层面是 OpenSSL 阵营与独立安全研究者对 LibreSSL 自身质量问题的揭露——安全研究者 Andrew Ayer（Opsmate 创始人）于 2014 年发现 LibreSSL 伪随机数生成器存在缺陷，Andrew Ayer 将其称为“伪随机数生成器的致命缺陷”，该缺陷使父进程与子进程可能共享可预测的随机数状态，OpenSSL 阵营据此主张 LibreSSL 的激进删除策略并非安全银弹，fork 后的新代码同样可能引入新缺陷；OpenSSL 阵营进一步指出 LibreSSL portable 版本（libressl-portable）的跨平台支持范围有限，主要面向 BSD 系统与 POSIX 平台，Windows 支持滞后，而 OpenSSL 作为事实标准拥有更广泛的平台覆盖与下游测试。第三层面是 GCC/FSF 阵营对“clang/LLVM 已成为 BSD 共识”论据的再回应——FSF 与 GCC 维护者主张 GCC 仍是 Linux 主流发行版（Debian、Fedora、Ubuntu、RHEL）的默认编译器，clang/LLVM 在 Linux 生态中的份额有限，BSD 四项目选择 clang 不能代表整个自由软件社区的共识；GNU 阵营进一步为 GPL copyleft 哲学辩护，主张 copyleft 是保护软件自由的必要机制——GPLv3 的 copyleft 条款确保衍生作品必须保持自由，而 ISC 许可证过于宽松，允许厂商将代码闭源，从长远看削弱软件自由；FSF 主张所谓“许可证纯洁性”实为对 copyleft 保护机制的放弃，OpenBSD 选择 clang 替代 gcc 是以“许可证纯洁”为名行“放弃 copyleft 保护”之实

## 198.2.5 合图：gcc→clang 与 OpenSSL→LibreSSL fork 的历史定位

**要点**：gcc→clang 替代与 OpenSSL→LibreSSL fork 的合图层论点包含三个历史定位。第一是 LibreSSL 与 OpenSSL 并存至今的历史结果——OpenSSL 在 Heartbleed 后启动 LibreSSL 之外的改革（OpenSSL 1.1.0 重构），LibreSSL 推动 OpenSSL 改进但未完全替代，证明 fork 是双轨而非替代；第二是 gcc 与 clang/LLVM 在 Linux 与 BSD 间分化——Linux 仍坚持 gcc 作为默认编译器，BSD 项目（FreeBSD、NetBSD、OpenBSD、DragonFly BSD）均切换至 clang/LLVM，证明两者各有适配；第三是 OpenBSD 的“改革路径”在两案例中的一致性——gcc 替代（pcc 探索失败后转向 clang/LLVM）与 OpenSSL fork（Heartbleed 后 fork LibreSSL）均体现 OpenBSD“渐进改革优于革命性重写”的方法论，但 LibreSSL fork 因 Heartbleed 紧急性具有“被动革命”特征，与 gcc 替代的“主动改革”形成对比

**史料**：OpenSSL 与 LibreSSL 各版本 Release Notes（<https://www.openssl.org/news/>、<https://www.libressl.org/>）；Linux 各发行版与 BSD 各项目默认编译器记录；openbsd.duckdb openbsd-src 仓库 LibreSSL 与 clang 相关 commit ［A］

**史观**：总纲第 4 条——分离聚合是永恒规律：LibreSSL 与 OpenSSL、clang 与 gcc 的并存是“分合循环”的具体显现——fork 不必然导致一方消亡，二者并存是 BSD 史中“分离聚合”的常态；总纲第 21 条——革命与改革是历史方法论的分歧：OpenSSL 选择改革（渐进改进），OpenBSD 选择革命（fork 重写），但 LibreSSL fork 后的演进是渐进的（移除 dead code、API 简化），证明革命与改革并非二分而是交织——LibreSSL 的“革命性 fork”后是“渐进性改革”，OpenSSL 的“渐进性改革”中包含“革命性重构”（1.1.0）

**要点**：

- OpenBSD 6.1 于 2017 年发布，是该项目第 42 个版本；该版本引入 Clang 作为基础编译器，动因是既有 GCC 的 GPLv2 版本无法支持 ARM64 平台。（BSD Now EP487，[72.92-129.86]，L2）
- 主持人逐段解读 Ritchie《The Evolution of the Unix Time-sharing System》，指出该论文回顾 UNIX 自 1969 年诞生、经 PDP-7 至 PDP-11 移植的早期史，依次讲述文件系统、进程控制、I/O 重定向与管道发明。（BSD Now EP487，[1048.88-1308.52]，L2）
- Ping 程序由 Mike Muuss 于 1983 年在 4.2a BSD 上编写，直接动因是同年 7 月 Dave Mills 在 DARPA 会议上关于以定时 ICMP 回显请求测量路径延迟的评论；Muuss 为此补全了内核的 raw ICMP socket 支持。（BSD Now EP487，[4653.46-4790.7]，L2）
- FreeBSD 将 ZFS 压缩发送接收功能导入 vendor branch，该功能依赖此前的 compressed ARC，使 ZFS send 可跨网络直接传输压缩数据，避免先解压再压缩的低效路径。（BSD Now EP487，[3892.42-4264.2]，L2）
- FreeBSD MAC 强制访问控制框架源自 DARPA 资助的 TrustedBSD 项目，允许以细粒度策略替代传统 root 特权；以 portacl 为例，可让非 root 用户绑定 1024 以下的特权端口。（BSD Now EP487，[4264.2-4648.22]，L2）
- David Chisnall 当事人自述 UNIX 初遇与转向 FreeBSD 的技术动因：在 Swansea 大学就读时，因 Linux 内核 TCP/IP 栈启动致谢中的校名（Swansea 曾参与实现）与 UNIX 结缘，该校因此吸引了大量计算机科学报考者；室友在路由器上安装 OpenBSD 引其关注，但 OpenBSD 安装器“按 yes 可能毁掉硬盘全部内容”的警告吓退了他，FreeBSD 安装器行为相同却不打印警告，遂选用 FreeBSD。2002-2003 年间 Linux 声音栈碎片化——/dev/dsp 的 OSS 模拟无软件混音、ALSA 依赖硬件混音、KDE 与 GNOME 各持一个声音守护进程、XMMS 直写 /dev/dsp——使其四个应用（BZFlag、XMMS、即时消息、邮件客户端）无法同时发声，而 FreeBSD 4.x 可显式配置多个 /dev/dsp 设备逐一指派应用解决此困局；FreeBSD 5 beta 在其满载 Nvidia 二进制驱动的机群上仍显稳定，4.x 服务器一直运行到 4.10/4.11。（BSD Now EP36，[1147.94-1391.16]，L1）
- Chisnall 自述从编译器贡献者到 FreeBSD 核心圈层的路径：为让 Objective-C 代码在 FreeBSD 上编译而投入 Clang 开发，发现从编译器视角 FreeBSD“既像 OS X 又像 Linux，但与两者都不完全相同”，而当时拥有 LLVM 提交权的开发者中少有人使用 FreeBSD；经 Roman 建议将工作上游化并加入 Clang on FreeBSD 项目，随后 FreeBSD 基金会资助其完成 libc++ 向 FreeBSD 的移植，继而又自嘲“看起来很傻”地当选 core team 成员。（BSD Now EP36，[1413.28-1476.48]，L1）
- Chisnall 对 core team 职责的当事人界定：职责难以严格定义，核心是“确保该对话的人彼此对话”，与“放牧猫群”的说法相当贴切；它不是公司式管理，没有解雇权——宣布对方工作糟糕并将其解雇只会让人庆幸重获自由时间；实际工作包括撮合有共同兴趣者、有问题者与有技能者（例如企业希望基于 FreeBSD 构建产品但缺少某项功能，项目方可牵线愿意以开发换取报酬者），以及调解线上沟通引发的冲突：时区错位与清晨未喝咖啡时发出的邮件在公共邮件列表上层层升级，需要有人坐下来告知双方“你们并不真的恨对方”，因为多数交流只发生在线上而线下见面往往发现彼此并无恶意。（BSD Now EP36，[1476.48-1627.42]，L1）
- head 测试文化与持续集成愿景：Netflix 在 10.0 发布前约六个月即运行开发分支，30 Gbps 流量使 IPv6 协议栈引用计数器缺陷在周末即暴露（普通用户需运行数月方可见），对照 Windows NT4 因计数器 47 天溢出、据称需两年部署才有机暴露的旧事；项目由此推动由 FreeBSD 基金会资助的持续集成——长期目标是每个更改编译并测试全部架构、拉起 QEMU 实例、对各类开发板网络启动，并运行回归与性能测试，以缩短变更从 head 到用户测试之间的时滞。　[存疑脚注] 转写记 Windows NT4 计数器溢出阈值为 47 天，通行记载为 49.7 天（约 2^32 秒），疑转写失真；NT4 一节系 Chisnall 口述转引，非一手材料（BSD Now EP36，[1781.32-1957.46]，L1）
- 网络栈的多方负载协调（Chisnall 当事人综述）：Verisign 运营多个 DNS 根域，流量为极短生命周期的微小 UDP/TCP 连接，净载荷可能仅占连接包数的一半；Netflix 处于另一极端，以约 1 MB 为有效“包”从磁盘读出写入 socket 经 TCP 下发、对方仅回 ACK；WhatsApp 居中，长连接上承载极小的即时消息心跳包且每服务器并发约 400 万安全连接。三方对网络栈的需求近乎对立，项目须防止任何一方把栈推向只利自身的方向，同时让各方改进惠及全体；多数时候各方自然协调，偶有冲突才需 core team 介入调解。（BSD Now EP36，[1996.70-2142.74]，L1）
- 无 GPL 基本系统路线图与 ARM 方向：多家不愿具名的企业向 Chisnall 提出对全 BSD 许可栈（编译器、操作系统、libc、C++ 实现开箱即用）的嵌入式需求；FreeBSD 已接近该目标，剩余缺口包括默认仍随附 GNU grep、troff 尚待切换至 mdoc、工具链中链接器为最后一大块——在研 BSD 许可链接器有 BOLD、MediaTek 驱动的 MC Linker 与 Sony 驱动的 LLD 三项，预期次年 FreeBSD 用户将有三选；规划 FreeBSD 11 可构建无 GPL 但可用的镜像，FreeBSD 12 默认无 GPL。同期他推动 ARM 支持与电源管理：树莓派硬件虽弱但廉价且销量巨大，被 FreeBSD 树内 ARMv6 架构分支选作参考平台，以缓解 ARM 开发板“一移植即过时废弃”的碎片化困境，并期望借此提供可烧录 SD 卡即启的稳定参考镜像。（BSD Now EP36，[2552.32-2845.64]，L1）
