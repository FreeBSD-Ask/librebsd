# 195.5 pf 防火墙移植“代码掠夺”批评与安全审计文化排他性批评的四层辩证链——FreeBSD 移植 pf 后未充分回移上游的伦理批评、OpenBSD 安全审计文化的排他性指控

## 195.5.1 批评层——“代码掠夺”批评与安全审计文化排他性批评

**要点**：批评层对 pf 移植与安全审计文化的批评集中于三点——其一，“代码掠夺”批评：批评者（部分 OpenBSD 阵营内外观察者）认为 FreeBSD 移植 pf 后大量修改未回移上游，构成对 OpenBSD 工程成果的单向汲取——FreeBSD 在 2003 年后由 Max Laier、Cyrille Bergeron 等维护 pf 移植版，引入 FreeBSD 特定的 `ifconfig` 集成、anchor 机制扩展、`pfsync` 与 `carp` 集成等修改，部分修改未回移至 OpenBSD 上游，OpenBSD 上游与 FreeBSD 下游的 pf 代码逐步分化，批评者认为这种“取走代码但不回馈上游”的模式是对 OpenBSD 工程投入的单向汲取；其二，“安全审计文化排他性”批评：批评者（Linux 社区与部分 FreeBSD 阵营成员）认为 OpenBSD 的“全代码审计”安全文化具有排他性——de Raadt 在 <misc@openbsd.org> 与公开演讲中多次将 OpenBSD 安全记录与其他 BSD/Linux 项目对比，批评者认为这种对比隐含“仅 OpenBSD 的安全审计是合法安全实践”的排他性预设，忽视了 FreeBSD TrustedBSD、Linux SELinux 等其他安全模型的存在与价值；其三，“代码掠夺”与“排他性”两批评的交织：批评者认为两批评共同构成对 OpenBSD 阵营“双重标准”的指控——一方面指责 FreeBSD“掠夺”pf 代码（维护 OpenBSD 上游权威），另一方面以“安全审计”排他性否定其他项目的安全实践（拒绝下游与同侪的安全合法性），两批评共同指向 OpenBSD 阵营的“中心化”倾向

**史料**：FreeBSD CVS/Git commit log（`sys/netpfil/pf/` 目录，2003-2010 年间 Max Laier、Cyrille Bergeron 等 commit）；OpenBSD 邮件列表 de Raadt 关于 pf 移植的发言（<misc@openbsd.org> 存档，marc.info 第三方归档）；OpenBSD security.html 官方页面（“We have been auditing since the summer of 1996”陈述）；de Raadt Slashdot 访谈与 BSDCan 演讲存档；FreeBSD TrustedBSD 项目文档（Robert Watson 主导）；Linux SELinux 项目文档（NSA 主导）；原材料/哲学/项目统摄史观/第 25 章.md（总纲第 8 条与第 19 条原文）；freebsd.duckdb freebsd-src 仓库 `sys/netpfil/pf/` 目录 commit 历史 ［A］

**史观**：总纲第 8 条——本体论上各方平等：OpenBSD 阵营与 FreeBSD pf 移植维护者、OpenBSD 安全审计文化与 FreeBSD TrustedBSD/Linux SELinux 安全模型在本体论上地位平等，无任何一方构成对其他方的本体论优越或劣等；总纲第 19 条——解释学循环与权力知识共谋：“代码掠夺”与“排他性”两批评的叙事建构受各方前理解差异决定，须以多元叙事审视而非单一立场裁决

**辨析**：【0 信任原则·“代码掠夺”批评的实证基础】FreeBSD pf 移植维护者对 pf 的具体修改清单须以 freebsd.duckdb freebsd-src 仓库 `sys/netpfil/pf/` 目录 commit 历史核验，“未回移上游”的具体清单须以 OpenBSD 上游与 FreeBSD 下游的代码 diff 量化，不得仅凭单方面声明；【“排他性”批评的代表性与边界】de Raadt 的具体发言措辞须对照 <misc@openbsd.org> 邮件列表原始帖核验，“排他性”的判断须区分“OpenBSD 对自身安全文化的强调”与“OpenBSD 否定其他项目安全实践的合法性”两类不同陈述；【“双重标准”批评的方法论】“双重标准”的判断须以 OpenBSD 阵营的具体发言为依据，不得以推断替代实证；【多源交叉验证不可靠性规则】多个 FreeBSD 阵营批评者在“代码掠夺”上的一致可能源于 FreeBSD 阵营的共同立场而非独立验证，多个 Linux 阵营批评者在“排他性”上的一致可能源于 Linux 阵营的共同立场

## 195.5.2 反批评层——OpenBSD 阵营的回应

**要点**：OpenBSD 阵营对“代码掠夺”与“排他性”批评的回应集中于四点——其一，“代码掠夺”批评误读 BSD 许可证哲学——OpenBSD 选择 ISC/BSD 许可证即允许下游自由修改与再分发，FreeBSD 对 pf 的修改是许可证自由的具体显现，“回移上游”是工程选择而非许可证义务，OpenBSD 不试图垄断 pf 代码主导权，亦不要求下游强制回移；其二，OpenBSD 上游与 FreeBSD 下游的 pf 代码分化是工程必然而非“掠夺”——两项目的内核架构（OpenBSD 的 `sellock` 与 FreeBSD 的 `mutex` 同步原语差异）、网络栈结构（OpenBSD 与 FreeBSD 的 `mbuf` 实现差异）不同，部分修改无法直接回移上游是技术架构差异而非工程恶意；其三，“安全审计文化排他性”批评误读 OpenBSD 的安全陈述——OpenBSD 的“全代码审计”是对自身工程实践的描述，de Raadt 对其他项目的批评是基于具体技术事实（如默认配置的漏洞数、远程漏洞响应时间）而非排他性预设；其四，OpenBSD 的安全陈述是对“默认安装安全”的工程承诺，与 FreeBSD TrustedBSD（强制访问控制）、Linux SELinux（标签强制访问控制）是不同维度的安全实践，不存在“排他性”——OpenBSD 关注默认安装的“无远程漏洞”，TrustedBSD/SELinux 关注访问控制的“权限最小化”，两者互补而非排斥

**史料**：OpenBSD 邮件列表 de Raadt 关于 pf 移植与安全文化的发言（<misc@openbsd.org> 与 <tech@openbsd.org> 存档，marc.info 第三方归档）；OpenBSD security.html 官方页面（“We have been auditing since the summer of 1996”陈述）；OpenBSD 3.0-3.6 Release Notes（安全特性引入时间与 6 个月发布周期）；FreeBSD TrustedBSD 项目文档（Robert Watson 主导，强制访问控制框架）；Linux SELinux 项目文档（NSA 主导，类型强制模型）；原材料/哲学/项目统摄史观/第 25 章.md（总纲第 8 条与第 24 条原文） ［A］

**史观**：总纲第 17 条——软件工程：OpenBSD 上游与 FreeBSD 下游的 pf 代码分化反映两项目内核架构与工程哲学的差异，是工程必然而非“掠夺”；总纲第 24 条——法律结构：BSD/ISC 许可证的自由允许下游修改与再分发，“回移上游”是工程选择而非许可证义务；总纲第 8 条——本体论上各方平等：OpenBSD 的“全代码审计”与 FreeBSD TrustedBSD、Linux SELinux 是不同维度的安全实践，本体论上地位平等，不存在“排他性”

**辨析**：【0 信任原则·BSD 许可证哲学的引用边界】BSD/ISC 许可证允许下游修改但不等于 OpenBSD 不在意下游修改方向——OpenBSD 在 pf 上游与 FreeBSD 下游的代码分化中仍维护“OpenBSD 上游权威”，但该权威是技术信誉而非法律强制；【代码分化的技术实证】OpenBSD 与 FreeBSD 内核架构的具体差异（同步原语、`mbuf` 实现）须以两项目源码核验，不得仅凭推测；【“排他性”批评的实证】de Raadt 对其他项目的具体批评措辞须对照原始发言核验，须区分“基于具体技术事实的批评”与“排他性预设的批评”；【安全实践维度的辨析】OpenBSD 的“默认安装安全”与 TrustedBSD/SELinux 的“访问控制”是不同维度的安全实践，但两者在实际部署中可能重叠（如 OpenBSD 亦有 `systrace` 与 `pledge` 等访问控制机制），须以具体机制核验避免简化

## 195.5.3 再回应层——批评方的再回应

**要点**：对 OpenBSD 阵营反批评的再回应集中于三点——其一，“BSD 许可证哲学允许下游修改”不否定“代码掠夺”的伦理批评——BSD 许可证的法律自由与工程伦理的回馈义务是不同维度，许可证允许不等于伦理鼓励，批评者认为 FreeBSD pf 移植维护者在享受 OpenBSD 工程投入的同时未充分回馈上游，构成工程伦理层面的“单向汲取”而非法律层面的“侵权”；其二，“代码分化是工程必然”的反批评者指出，部分 FreeBSD pf 修改（如 `pfsync` 与 `carp` 集成、`ifconfig` 集成）并非纯粹的架构差异驱动——OpenBSD 上游在 4.x 时期亦引入类似机制（如 OpenBSD 的 `pfsync` 与 `carp` 实现），但两项目的实现独立演化，未形成代码共享，“工程必然”的判断须以具体修改清单核验而非笼统断言；其三，“安全审计文化不排他”的反批评者指出，de Raadt 在公开演讲与邮件列表中多次将 OpenBSD 安全记录与其他 BSD/Linux 项目对比时使用“only OpenBSD”等措辞，隐含“仅 OpenBSD 的安全实践是合法”的预设——de Raadt 的具体发言措辞须对照 <misc@openbsd.org> 邮件列表与 BSDCan 演讲原始记录核验，“排他性”的判断须以原始发言为依据而非推断

**史料**：OpenBSD 邮件列表 de Raadt 关于其他项目安全实践的发言（<misc@openbsd.org> 存档，marc.info 第三方归档）；FreeBSD CVS/Git commit log（pf 相关 commit，2003-2010 年间，`sys/netpfil/pf/` 目录）；OpenBSD 4.x Release Notes（`pfsync` 与 `carp` 引入时间）；de Raadt BSDCan 演讲存档；原材料/哲学/项目统摄史观/第 25 章.md（总纲第 8 条与第 13 条原文） ［A］

**史观**：总纲第 8 条——本体论上各方平等：OpenBSD 阵营与反批评者在“代码掠夺”与“排他性”争议上地位平等，反批评不构成对 OpenBSD 阵营反批评的否定，而是辩证链中的再回应环节；总纲第 13 条——法律与道德是利益分配：“代码掠夺”的伦理批评实质是 OpenBSD 与 FreeBSD pf 移植维护者在工程投入与回馈义务利益分配上的冲突，“法律自由”与“伦理义务”的判断服务于不同的利益分配诉求

**辨析**：【法律自由 vs 伦理义务的维度区分】BSD 许可证的法律自由与工程伦理的回馈义务是不同维度，须分别评估——法律自由不否定伦理义务的批评，伦理义务的批评亦不否定法律自由的存在；【代码分化具体清单的实证】FreeBSD pf 移植维护者的具体修改清单中可回移上游但未回移的部分须以 freebsd.duckdb freebsd-src 仓库 `sys/netpfil/pf/` 目录 commit 历史与 OpenBSD 上游 commit 历史对照核验，不得仅凭推测；【“排他性”发言的原始措辞考据】de Raadt 使用“only OpenBSD”等措辞的具体发言须以 <misc@openbsd.org> 邮件列表原始帖与 BSDCan 演讲记录核验，“排他性”的判断须以原始发言为依据而非推断；【多源交叉验证不可靠性规则】多个 FreeBSD 阵营批评者在“代码掠夺”上的一致可能源于 FreeBSD 阵营的共同立场而非独立验证

## 195.5.4 合图层——从项目统摄史观审视“代码掠夺”与“排他性”争议

**要点**：以项目史观总纲第 8 条（本体论上各方平等）与第 13 条（法律与道德是利益分配）审视“代码掠夺”与“排他性”争议——FreeBSD pf 移植维护者与 OpenBSD 上游、“全代码审计”与 TrustedBSD/SELinux 安全模型在本体论上地位平等，争议本身是 BSD 阵营内部对工程投入回馈义务、安全实践合法性等多元议题的多元判断的具体显现，无须以“对错”二元裁决；以“法律与道德是利益分配”的史观审视，“代码掠夺”的伦理批评实质是 OpenBSD 与 FreeBSD pf 移植维护者在工程投入与回馈义务利益分配上的冲突——OpenBSD 维护“上游权威”的工程信誉利益，FreeBSD 维护“下游自主”的工程演进利益，二者的利益分配无法通过许可证条款（法律形式）完全调和，须以工程协商（如上游-下游同步机制）补充；“排他性”批评实质是 OpenBSD 安全审计文化与其他 BSD/Linux 安全模型在“安全合法性”利益分配上的冲突——OpenBSD 维护“全代码审计”的安全叙事主导权，其他项目维护各自安全模型的合法性，二者的利益分配无法通过“默认安装安全”等量化指标完全调和；以多元史观综合审视，“代码掠夺”与“排他性”争议的历史意义在于——它是 BSD 阵营内部对许可证哲学、工程伦理、安全实践合法性等多元议题的多元回应之一，无须以单一史观裁决其正当性，争议本身的不可调和性反映 BSD 阵营内部工程哲学的多元性，和解史观要求承认多元立场的并存而非强制统一

**史料**：原材料/哲学/项目统摄史观/第 25 章.md（总纲第 8 条与第 13 条原文）；OpenBSD 邮件列表存档（de Raadt 与 FreeBSD pf 移植维护者的发言，<misc@openbsd.org> 存档，marc.info 第三方归档）；FreeBSD CVS/Git 仓库（pf 相关 commit 历史，`sys/netpfil/pf/` 目录）；OpenBSD security.html 官方页面；FreeBSD TrustedBSD 项目文档；Linux SELinux 项目文档 ［A］

**史观**：总纲第 8 条——本体论上各方平等：FreeBSD pf 移植维护者与 OpenBSD 上游、OpenBSD 安全审计文化与 FreeBSD TrustedBSD/Linux SELinux 在本体论上地位平等，争议是平等主体间的分歧；总纲第 13 条——法律与道德是利益分配：“代码掠夺”与“排他性”批评均以“工程利益”或“安全利益”为名，但“工程利益”与“安全利益”的界定本身即利益分配的争议焦点，须以多元利益框架审视

**辨析**：【和解史观的边界】“和解优于斗争”不等于“争议无意义”——“代码掠夺”与“排他性”争议在 BSD 阵营内部工程哲学的多元性显现上具有历史意义，和解史观要求承认多元立场的合理性但亦要求承认争议本身的历史意义，不得以“和解”为名取消对争议的考据与分析；【本体论平等的引用边界】“本体论上各方平等”不等于“各方立场无差异”——OpenBSD 的“全代码审计”与 FreeBSD TrustedBSD、Linux SELinux 在安全实践维度上有差异，本体论平等不否定安全实践差异；【法律与道德是利益分配的引用边界】总纲第 13 条“法律与道德是利益分配”不等于“法律与道德无客观性”，须对照原文核验——该条强调法律与道德的形式服务于利益分配，但不否定利益分配本身的合理性判断；【争议不可调和性的辨析】“代码掠夺”与“排他性”争议的不可调和性是 BSD 阵营内部工程哲学多元性的显现，不可调和性不等于“无须和解”——和解史观要求承认不可调和性的事实，但同时要求各方在不可调和性中寻找工程协商的可能路径（如上游-下游同步机制、跨项目安全对话机制）

**要点**：

- PF 的诞生是一桩许可事件：OpenBSD 3.0 之前使用 Darren Reed 的 IPFilter，Reed 变更许可、限制开放与自由分发，OpenBSD 遂在一个发布周期内由 Daniel Hartmeier 从零写出全新包过滤器并吸收既有过滤器技术，随 OpenBSD 3.0 发布；此后 PF 逐步成为各 BSD 通用的防火墙组件。（BSDTalk EP105，[149.96-202.68]，L1）
- Dixon 以咨询者视角评点规则语言：Linux NetFilter/iptables 是难以上手的句法式过滤语言，IPFilter 则出自开发者视角而忽视可用性——开源开发者惯于为开发者写软件；PF 走语言化路线，类 Cisco 风格、可读性高，man page 详尽而清晰，只要具备 TCP/IP 基础即易掌握，这是 PF 区别于前两者的特质。（BSDTalk EP105，[202.68-295.78]，L1）
- 他梳理了有状态过滤的概念史：stateful 一词因 CheckPoint 而流行，早期防火墙只是按源目地址与端口过滤的包过滤器，其后发展到由包头推断连接状态、放行属于可信会话的后续包；PF 的 scrub（normalization）重组分片成完整包再行过滤，并剔除不可能的 TCP 标志组合以防接收端漏洞利用，synproxy 则在防火墙上代答 TCP 三次握手以抵御 SYN flood。（BSDTalk EP105，[423.94-631.08]，L1）
- 防火墙冗余设计上，CARP（Common Address Redundancy Protocol）为替代 Cisco 持有专利的 VRRP 而生，以虚拟 IP 与心跳实现多台防火墙的无缝故障切换，pfsync 经多播在防火墙间持续同步状态表；Dixon 常在 LinuxWorld 与 OSCON 上演示边播流媒体边砍断主防火墙线缆而业务不断，甚至有风险投资人观后主动递名片。（BSDTalk EP105，[745.86-850.14]，L1）
- spamd 体现以资源扼制攻击者的反垃圾哲学：命中黑名单的源地址被 tarpit——服务器以每秒一字符的速度回送响应，最终以 SMTP 临时错误迫使对方重新排队，对以量取胜的群发者极具消耗性；灰名单机制对未识别的源与发件人组合返回临时错误，若其在配置时限内重试则记入白名单表；二者皆依托 PF tables 的高效 IP 查询。（BSDTalk EP105，[1310.3-1430.02]，L1）
- PF 的生态扩散与使用文化：pfSense 作为 monowall 的分支沿用其 Web 界面引擎，但以 PF 而非 IPFilter/IPFW 为核心并运行于 FreeBSD，成为 PF 可移植性的活例证；Dixon 本人坚持命令行管理，认为 GUI（Firewall Builder、PFW 等）只适合主机级简单场景，唯有手写规则才能真正理解所配技术。（BSDTalk EP105，[976.86-1069.14]，L1）
