# 195.1 OpenBSD 3.0 与 pf 防火墙（2001.12）——3.0 引入 pf（Packet Filter）防火墙替代 IPFilter，因 IPFilter 许可证变更引发的 fork

## 195.1.1 IPFilter 许可证变更与 pf fork

**要点**：IPFilter（IPF）作者 Darren Reed（达伦·里德） 2001.5.30 在 IPFilter 3.4.31 中修改许可证，加入“不得修改或重新分发”等限制性条款；OpenBSD 因违反其 BSD 许可证传统无法继续使用 IPF；de Raadt 决定由 Daniel Hartmeier（丹尼尔·哈特迈尔） 主导开发 pf 替代 IPF，pf 1.0 随 OpenBSD 3.0（2001.12）发布

**史料**：IPFilter 3.4.31 LICENSE 文件变更；Darren Reed 与 de Raadt 邮件列表争论；OpenBSD 3.0 Release Notes pf 部分 ［A］

**史观**：法律结构：IPFilter 许可证变更作为法律结构变化直接催生 pf fork

**辨析**：IPFilter 许可证变更的具体条款在不同叙事中存在差异——部分资料称“不得用于商业用途”，部分称“不得修改”，需对照原始 LICENSE 文件核验；Darren Reed 的动机（商业 vs 个人）需考据

**文献**：IPFilter LICENSE 文件；Darren Reed 与 de Raadt 邮件；OpenBSD 3.0 Release Notes［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

## 195.1.2 pf 的设计与实现

**要点**：pf 由 Daniel Hartmeier 设计，采用 BPF 字节码与状态跟踪机制；pf 设计强调简洁性与可扩展性，与 IPFilter 复杂配置形成对比；pf 引入 anchors 与 macros 等灵活配置机制；pf 迅速成为 OpenBSD 默认防火墙并被 FreeBSD/NetBSD 移植

**史料**：pf 设计文档；Daniel Hartmeier 个人 pf 历史文章；OpenBSD CVS commit log ［A］

**史观**：总纲第 4 条——分离聚合是永恒规律：pf 作为独立防火墙框架与 OpenBSD 内核聚合，与 IPFilter 在概念上分离

**辨析**：pf 与 IPFilter 的“性能对比”在不同来源中差异较大——需对照同硬件测试核验；pf 在 FreeBSD/NetBSD 的移植时间需考据；openbsd.duckdb 查询 L2.3.1.pf 在中观模式挖掘报告中不存在（报告仅含 L2.3.1.ZFS、L2.3.1.Capsicum、L2.3.1.bhyve、L2.3.1.Clang、L2.3.1.ARM64、L2.3.1.RISC-V 等 FreeBSD 特性查询，未覆盖 OpenBSD pf 子系统），pf 相关子系统级 commit 数据须以 openbsd.duckdb 直接查询 file_path 维度（如 sys/net/pf*.c、sbin/pfctl/）补全

**文献**：pf 设计文档；Hartmeier 个人 pf 历史；OpenBSD pf(4) 手册页；netbsd.duckdb 查询 L2.3.1.pf（来源：原材料/研究/bsd 仓库分析/数据分析/中观模式挖掘.md §L2.3.1，数据缺口） ［A］

## 195.1.3 与 FreeBSD IPFW 与 Linux iptables 的比较

**要点**：FreeBSD IPFW 是 FreeBSD 原生防火墙，由 FreeBSD 团队维护；Linux iptables 是 Linux 标准防火墙，由 Rusty Russell 等设计；pf 与 IPFW/iptables 在设计哲学上差异——pf 强调状态跟踪与简洁语法，IPFW 强调性能，iptables 强调灵活性

- Pascal Stumpf 在专访中自述 OpenBSD 静态 PIE 的实现：PIE 使可执行文件可映射到随机内存偏移，是 ASLR 全景（栈随机化、随机 mmap、库位置随机化）中“完整随机地址空间的最后一块”（1291.18-1303.74）；在“严格 W 异或 X 策略——任何内存不可同时可写与可执行”（1315.10-1327.10）之下，攻击者无法跳入被覆盖缓冲区执行 shellcode，只能复用可执行文件与 libc 中以 ret 结尾的 gadget，PIE 随机化令 gadget 地址不可预测；静态二进制没有 `ld.so` 的运行时重定位，重定位须在链接进每个可执行文件的 C 启动代码中完成；实现归功于 Theo de Raadt、Kurt Miller 与 Mark Kettenis，Kettenis 写大部分代码、Stumpf 承担推动，向其他架构的移植在数日至一周内完成。　[存疑脚注] 转写将 Mark Kettenis 记作 Mark Katanis，依 OpenBSD 开发者名录与 PIE 工作语境校正为 Mark Kettenis；另 1535.68-1537.68 处活动名转写作 Azure PSDCon，疑为 vBSDcon，未能确证。（BSD Now EP85，[1182.5-1531.9]，L1）
- Solaris 与 PF 的新闻浓缩了许可证重塑防火墙格局的因果链：Oracle 因一封提交给 OpenBSD 的 bug 报告“意外泄露”Solaris 12 将以 PF 为自带防火墙（78.80-84.32），11.3 中 PF 先以可选防火墙身份出现，而 IP filter 被判入“death row”（126.08-131.84）；主持人回顾 PF“实际是因许可证问题在 OpenBSD 上作为 IP filter 的替代品而生”，且 Solaris 正是 IPF 的原始开发平台，故此番采纳“算是兜了一圈回到主场地盘”（133.80-150.40），并称 PF“正在到处扩散”（182.16-184.40）；FreeBSD 树中残留的 IP filter 则被认为“可能需要死在那里”。（BSD Now EP85，[70.4-170.9]，L2）
- PackageNG 1.50 发布被主持人视为包管理变革的关键节点：provides/requires 框架进入正式版，使依赖协商可按能力而非具体包名进行（以 Perl 版本替换为例）；升级比较忽略大小写、支持以 `pkg -r` 安装至指定根目录、求解器会明确解释重装、移除或升级每个包的理由，并开始支持 OS X 等平台；路线图上的 cherry-picking 升级、MariaDB 与 MySQL 的互替声明、直接管理 CentOS 仓库 RPM 的 Linux 包后端、同仓库多版本共存、下载断点续传与文件 immutable 标志，被明确与 base 系统打包的推进相勾连。　[存疑脚注] 转写作 Edge BSD 的平台名可辨性弱，疑指 pkgng 的 EdgeBSD 支持条目，暂不确证。（BSD Now EP85，[2288.3-2653.2]，L2）　[订正：原 范围 [2288.3-2619.5]，2026-09-30 SenseAudio 重转核对——转写中下载断点续传（2619.40-2642.20）与文件 immutable 标志（2642.50-2653.20）位于原终点之后]
- OpenBSD 3.0 引入 PF 后，Henning Brauer 将运行 IPF 的防火墙机器迁移至 PF，并与 Daniel Hartmeier 共同调试初期崩溃问题；修复后同一批机器以约 10% 的 CPU 负载处理原先满载的流量。（BSD Now EP9，[1015.4-1088.7]，L1）
- Henning Brauer 因向 misc@openbsd 报告 PF 迁移效果而收到 Theo de Raadt 的 hackathon 邀请，2002 年参加后获得提交权限，此后约十一年主要工作在 PF 与网络栈。（BSD Now EP9，[1090.3-1119.2]，L1）
- 他回顾早期 PF 黑客倾向在 PF 内解决一切问题，后转向以整个网络栈为对象的处理方式；并先后参与 bgpd、ntpd 与校验和处理，新排队系统计划替代 ALTQ。（BSD Now EP9，[1138.7-1640.5]，L1）
- PF 的诞生是一桩许可事件：OpenBSD 3.0 之前使用 Darren Reed 的 IPFilter，Reed 变更许可、限制开放与自由分发，OpenBSD 遂在一个发布周期内由 Daniel Hartmeier 从零写出全新包过滤器并吸收既有过滤器技术，随 OpenBSD 3.0 发布；此后 PF 逐步成为各 BSD 通用的防火墙组件。（BSDTalk EP105，[149.96-202.68]，L1）
- Dixon 以咨询者视角评点规则语言：Linux NetFilter/iptables 是难以上手的句法式过滤语言，IPFilter 则出自开发者视角而忽视可用性——开源开发者惯于为开发者写软件；PF 走语言化路线，类 Cisco 风格、可读性高，man page 详尽而清晰，只要具备 TCP/IP 基础即易掌握，这是 PF 区别于前两者的特质。（BSDTalk EP105，[202.68-295.78]，L1）
- 他梳理了有状态过滤的概念史：stateful 一词因 CheckPoint 而流行，早期防火墙只是按源目地址与端口过滤的包过滤器，其后发展到由包头推断连接状态、放行属于可信会话的后续包；PF 的 scrub（normalization）重组分片成完整包再行过滤，并剔除不可能的 TCP 标志组合以防接收端漏洞利用，synproxy 则在防火墙上代答 TCP 三次握手以抵御 SYN flood。（BSDTalk EP105，[423.94-631.08]，L1）
- 防火墙冗余设计上，CARP（Common Address Redundancy Protocol）为替代 Cisco 持有专利的 VRRP 而生，以虚拟 IP 与心跳实现多台防火墙的无缝故障切换，pfsync 经多播在防火墙间持续同步状态表；Dixon 常在 LinuxWorld 与 OSCON 上演示边播流媒体边砍断主防火墙线缆而业务不断，甚至有风险投资人观后主动递名片。（BSDTalk EP105，[745.86-850.14]，L1）
- spamd 体现以资源扼制攻击者的反垃圾哲学：命中黑名单的源地址被 tarpit——服务器以每秒一字符的速度回送响应，最终以 SMTP 临时错误迫使对方重新排队，对以量取胜的群发者极具消耗性；灰名单机制对未识别的源与发件人组合返回临时错误，若其在配置时限内重试则记入白名单表；二者皆依托 PF tables 的高效 IP 查询。（BSDTalk EP105，[1310.3-1430.02]，L1）
- PF 的生态扩散与使用文化：pfSense 作为 monowall 的分支沿用其 Web 界面引擎，但以 PF 而非 IPFilter/IPFW 为核心并运行于 FreeBSD，成为 PF 可移植性的活例证；Dixon 本人坚持命令行管理，认为 GUI（Firewall Builder、PFW 等）只适合主机级简单场景，唯有手写规则才能真正理解所配技术。（BSDTalk EP105，[976.86-1069.14]，L1）
- 访谈于 OpenCon 2007 之后在威尼斯 Bar Piccolo Martini 进行，对象为 Peter Hansteen；其著作 The Book of PF（No Starch Press，OpenBSD 防火墙实务指南）定于 2007 年 12 月 15 日出版，OpenCon 上私印样书已拍卖，亚马逊与出版社渠道可预订，会上已有人洽谈多语种翻译；作者称读者仅需基础 TCP/IP 知识，内容从规则集求值逐步进阶。（BSDTalk EP136，[220.79-901.72]，L1）
- 其转向 PF 的经历：为小公司管理网络时平台先以 Linux 为主、渐转 FreeBSD，但防火墙始终在 Linux 上，iptables 维护渐成苦役；旧防火墙硬件烧毁后改用 OpenBSD 加 pf，“再未回头”。（BSDTalk EP136，[253.15-296.63]，L1）
- PF 的可读性哲学：向 iptables 用户展示配置时对方常难以相信规则能如此简单——“这不是 shell 脚本”；装好系统的机器上五到十行 pf.conf 置于网络与世界之间即可工作。宏以符号名为服务列表（ssh、domain、www、https 等）提供可读简称；表是专为 IP 地址与网段设计的高效数据结构，支持 CIDR 与取反、可自命令行操纵，配合锚点使外部程序与规则集交互；“PF 不能动态改规则”的质疑至多部分成立。（BSDTalk EP136，[296.63-446.16]，L1）
- CARP（Common Address Redundancy Protocol）的诞生部分是对一个故障切换协议在 IETF 冲向标准途中被发现牵涉约三百余项专利的回应，OpenBSD 团队遂自行撰写替代；CARP 作为虚拟网络接口让一组机器共享对外 IP，一主多备，主机故障时备份近乎透明地接管——凌晨三点主防火墙宕机无需短信叫醒管理员，半年一次的 OpenBSD 升级可挪至工作时间完成，主机恢复后备机再行交还。（BSDTalk EP136，[458.44-546.15]，L1）
- hoststated 由 Reyk Floeter 与另一开发者（转写姓氏不可辨）写成，经 PF 表与规则集集成：对外发布单一 IP 与主机名并以轮询重定向到后端机器表，守护进程检测后端存活、将死机移出地址池，从而令服务更可靠；至 OpenBSD 4.2，hoststated 已能较好处理 SSL 连接。（BSDTalk EP136，[546.15-621.95]，L1）
- 抗 DDoS 的状态追踪选项源自一次拒绝服务受害者的通用化追问，于 OpenBSD 3.7 前后加入：规则中可限定单主机最大并发连接数与时间窗内连接速率，超限者落入专门表；处置方式从直接封锁（配合 flush global）到借 ALTQ 队列给超限者极小带宽任其排队。（BSDTalk EP136，[626.33-689.28]，L1）
- spamd 与灰名单：spamd 约于 OpenBSD 3.5 引入，最初对黑名单来源的 SMTP 连接以每字节一次的应答拖延至对方放弃；同期出现的灰名单基于对 SMTP 规范“临时错误须在合理时间内重试”的较真解读——垃圾邮件多出自被劫持 Windows 机器上的简易软件、从不检查返回码亦不重试，真实邮件服务器则会在约半小时内回来；五年后灰名单仍能当场消灭约 95% 的垃圾邮件；spamd 消除的是低垂果实，最精明的发件者或借开放中继者仍可能通过；spamd 亦伪装成开放中继诱捕不校验投递的中继检查器，其灰名单中可见上万封从未投递的转发尝试。（BSDTalk EP136，[695.52-840.75]，L1）
- 结语立场：支持 OpenBSD 请购买 OpenBSD 用品，支持作者请购买其书；并以略带激烈的方式断言——不运行 OpenBSD 或未在其他 BSD 上运行 PF 的管理员“错失良多，把事情做得比必要的更难”。（BSDTalk EP136，[903.76-928.32]，L1）
- 主播两周年回顾：BSDTalk 首期发布于 2005 年 12 月 20 日；两年间 NetBSD 自 3.0（2005 年 12 月 23 日发布）演进至 4.0，PC-BSD 从未及 1.0 到今日，FreeBSD 7.0 正筹备候选版本；主播感谢社区与听众在时间、金钱、主机与精力上的捐助。（BSDTalk EP136，[119.63-183.73]，L2）
- OpenBGPD 的缘起：BGP 即边界网关协议，依 RFC 定义，用于 ISP 之间互宣网络可达性——各 ISP 向对端宣告自有网络与客户网络，形成巨型对等 mesh，互联网路由表由此建立。当事人此前用当时人人使用的 Zebra，其 KAME 系代码有趣但问题多：事件模型错误、忙时会丢弃 BGP 会话、越忙越糟直至离线；他到处修改以提高可靠性，勉强可用但从未满意。某天重读 RFC 觉得并不复杂，受够之后坐下动手实现会话处理，九天后即有自认为完整可用的会话引擎（后来发现若干 bug 但基础正确）；2004 年末致信 Claudio Jeker 等相关者；此后项目稳步成长，如今已有相当多站点使用，通常比其他实现更快更可靠。（BSDTalk EP23，[333.28-490.80]，L1）
- BGP 会话保护：BGP 会话一旦丢失即告离线，会话是天然攻击面，保护至关重要而多数运维者毫无作为；TCP MD5 签名对任务而言可用但不优秀、聊胜于无；其他实现从不支持，因为问题的另一半在内核、只在应用层处理便失去意义。OpenBSD 很早实现了健壮的 TCP MD5，另提供他处不易获得的 IPsec，并自称是唯一以 isakmpd 做动态密钥 IPsec 的实现——其场景下零配置：拷贝密钥、启动 isakmpd，bgpd 自行完成其余协商。（BSDTalk EP23，[501.80-561.84]，L1）
- 随机化哲学：对 TCP、IP 及其上层协议，寻找 RFC 要求插入时间戳等半静态信息之处并验证能否以完全随机值替代——如完全随机的临时源端口（OpenBSD 随机选取，据其所知其他系统均为单调递增）；当年即知是好主意却无法证明，七八年后 Paul Watson 于 2004 年发表针对长生命周期 TCP 会话的注入攻击研究，随机源端口使此类攻击难得多，七年后才终于明白当初为何那样做。进程 ID、IP ID、初始序列号、DNS 查询 ID 皆正确随机化。所有需要随机数的子系统调用 arc4random 从内核熵池取数，众多来源使取数时机本身不可预测，即便熵池被单调计数器稀释仍能保持良好随机性。安全始终在开发者的头脑中：寻找可随机化之处、三思暴露什么——例如默认 Apache 1.3 暴露版本指纹，他们不删除该信息而以随机值替代。（BSDTalk EP23，[572.24-816.16]，L1）
- blob 批评（3.9 发布主题）：blob 即二进制大对象——硬件厂商隐瞒硬件 API 实属愚蠢，以太网芯片数十种、技术早已无秘密；厂商不给文档只给链接进内核的目标文件（NVIDIA 在此恶名昭著）。后果有三：内容不可知、可能藏有恶意；绑死厂商愿支持的架构，x86 目标文件无法用于 AMD64、SPARC64 或 alpha；厂商对系统影响力过大，且在内核空间运行不可信代码使安全问题遍地。这与二十年前伯克利清除 AT&T 专有代码是同一本质问题——依赖大公司，而公司利益很少与自由社会一致；为 OpenBSD 维护 blob 不可接受，直接给出文档即可；此前争取无线芯片组文档的成功是可行先例。（BSDTalk EP23，[913.68-1058.02]，L1）
- PF 取代 IPF 的始末：IPF 作者以所谓澄清为名修改许可证（当事人认为原措辞本就意在让人误读），最终明确禁止发布修改版——荒谬之处在于 IPF 问题不断、OpenBSD 修复过其中一些，许可证却禁止发布修复；意识到后一天之内 IPF 即被移出树。许可证只是压垮骆驼的最后一根稻草，此前对 IPF 早已不满；Daniel Hartmeier 随之起手编写 PF，3.0 首个随带 PF 的发布虽功能不及 IPF 全、大规模部署有问题，但已相当可用；长期看，其他曾用 IPF 的系统纷纷导入 PF，大量 IPF 用户在其他操作系统上也转向 PF，如今 PF 强大得多、其他系统基本皆已改用 PF。（BSDTalk EP23，[1059.82-1167.26]，L1）

**史观**：
