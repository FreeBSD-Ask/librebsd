# 201.2 OpenBSD 6.x 周期漏洞与安全响应综览——pledge 普及、unveil 引入与 CPU 漏洞爆发下的加固重构循环

## 201.2.1 6.x 周期安全态势总览——errata 存档完整性与 commit 数据的对照

**要点**：OpenBSD 6.x 周期（commit 数据覆盖 **2016 年 9 月 1 日** 至 **2019 年 10 月 1 日**，对应 6.0 发布至 6.6 发布；6.0-6.9 实际版本跨度 **2016 年 9 月** 至 **2021 年 5 月**）openbsd-src 仓库共出现 **20 条 CVE 相关 commit** 与 **5 条无 CVE 编号的安全修复 commit**，对应 **31 个去重 CVE**；CVSS v3.x 评分分布为 0 个 Critical、0 个 High、1 个 Medium（CVE-2019-1125，5.6）、30 个无评分——无评分比例高达 96.8%，反映 OpenBSD commit message 较少显式引用 CVE 编号的工程习惯，这一比例与 7.x 周期的 95.5% 接近，印证 OpenBSD commit 风格的跨周期一致性；**关键考据发现**：本地 errata 存档 `〔存疑：原引 原材料/研究/bsd漏洞史/官方公告/openbsd-errata.md 全库无档，实经 WebFetch 外部核验〕` 中 6.0-6.9 全部 10 个版本仅有索引条目（URL 引用）而无详细 errata 列表，经 WebFetch 核验 `https://www.openbsd.org/errata60.html`、`errata64.html`、`errata69.html` 三个代表版本，6.0 共 45 个 patch、6.4 共 26 个 patch、6.9 共 36 个 patch——errata 页面内容完整，本地存档缺失的是详情抓取而非页面本身；这一发现修正了“6.x errata 存档缺失”的初步判断，6.x 周期 errata 发布机制运转正常，与 7.x 周期本地存档显示“0 条目”的情况本质不同

  **OpenBSD 6.x 周期 CVE 与 errata 统计**：

  | 维度 | 6.x 周期 | 7.x 周期（对照） |
  | --- | --- | --- |
  | commit 数据时间范围 | 2016-09-01 至 2019-10-01 | 2021-10-14 至 2026-07-22 |
  | CVE 相关 commit | 20 条 | 60 条 |
  | 无 CVE 编号安全修复 | 5 条 | — |
  | 去重 CVE 数 | 31 个 | — |
  | 无评分比例 | 96.8% | 95.5% |
  | 代表版本 errata patch 数 | 6.0: 45、6.4: 26、6.9: 36 | — |

**史料**：**openbsd.duckdb** `commits` 表 openbsd-src 仓库 6.x 周期 CVE commit 查询：

  ```sql

  WHERE repo_name='openbsd-src'
    AND author_date>=‘2016-09-01’
    AND author_date<‘2019-10-01’

  ```

  结果 20 条；`〔存疑：原引 原材料/研究/bsd漏洞史/版本周期/openbsd-6.x.md 全库无档〕` 版本周期归档（2026-07-22 整理）；`〔存疑：原引 原材料/研究/bsd漏洞史/官方公告/openbsd-errata.md 全库无档，实经 WebFetch 外部核验〕` 本地 errata 存档 6.0-6.9 索引条目；OpenBSD 官方 errata 页面 `https://www.openbsd.org/errata60.html`、`errata64.html`、`errata69.html`（经 WebFetch 核验三个代表版本） ［A］

**史观**：总纲第 19 条——解释学循环是历史认识的根本条件（原“0 信任原则”系伪标签族，按考据认识论旨改挂）：6.x 周期 errata 存档的考据是 0 信任原则在数据驱动考据中的实践——本地存档显示“仅有索引”不等于“errata 不存在”，WebFetch 核验证明 6.0/6.4/6.9 三个版本的 errata 页面内容完整；这与 7.x 周期 errata 条目数为 0 的情况形成对照——7.x 的“0 条目”可能是抓取工作流失效，6.x 的“仅有索引”是本地存档未抓取详情；两种情况的辨析须以官方页面原始 HTML 为准，单一数据源不足以判断安全态势

**辨析**：**须严格区分** 6.x 周期 commit 数据的时间范围与版本发布时间范围：① commit 数据覆盖 2016-09-01 至 2019-10-01（对应 6.0 发布至 6.6 发布），6.7-6.9 的 commit 未纳入版本周期归档；② 6.0-6.9 的 errata 实际时间跨度为 2016-08 至 2022-04（6.9 最后一个 errata 为 2022-04-11 的 036_rpki.patch）；③ commit 数据与 errata 数据的覆盖范围不一致——commit 数据以开发时间索引，errata 以发布后修补时间索引，二者不可混为一谈；**与 7.x 周期对比**：7.x 周期 commit 数据覆盖 2021-10-14 至 2026-07-22（60 条 CVE commit），6.x 周期 commit 数据覆盖 2016-09-01 至 2019-10-01（20 条 CVE commit）——6.x 周期 commit 密度较低不意味着漏洞更少，而是 OpenBSD commit message 在 6.x 周期更少显式引用 CVE 编号；**errata 数量对比**：6.0 的 45 个 errata patch 远超 6.4 的 26 个与 6.9 的 36 个，反映 6.0 作为 6.x 系列首个版本积累了较多未修复问题

## 201.2.2 pledge 从部分应用到全面普及——6.0-6.9 的渐进部署与 errata 中的 pledge 身影

**要点**：6.x 周期是 **pledge(2)** 从“5.9 正式启用后的部分应用”走向“基本系统全面覆盖”的过渡期——6.0（**2016 年 9 月 1 日** 发布）时 pledge 已启用但覆盖率有限，主要集中于 **tcpdump(1)**、**nc(1)** 等网络工具；6.1-6.3 持续扩展 pledge 覆盖至更多用户态工具；6.4-6.9 进一步将 pledge 与新引入的 **unveil(2)** 配合，形成双重沙箱；**openbsd.duckdb** 显示 6.x 周期内 pledge 相关 commit 持续出现，deraadt、semarie、benno、millert 等 committer 反复扩展 pledge 覆盖范围；pledge 在 6.x errata 中亦留下身影——6.0 errata 013_ssh_kexinit.patch 修复 **sshd(8)** 协议解析 bug 导致的未认证内存与 CPU 消耗，pledge 限制了此类漏洞的可利用范围；pledge 的渐进部署模式是 OpenBSD“主动审计—快速修复—加固重构”循环中“加固重构”环节在 6.x 周期的具体显现——发现漏洞后不仅修补 bug，还通过扩展 pledge 限制范围来缓解同类漏洞的潜在影响

**史料**：**openbsd.duckdb** `commits` 表 openbsd-src 仓库 6.x 周期 pledge 相关 commit 查询：`SELECT commit_hash, author_date, author_name, message_subject FROM commits WHERE repo_name='openbsd-src' AND author_date>='2016-09-01' AND author_date<'2019-10-01' AND message_subject LIKE '%pledge%' ORDER BY author_date ASC`；OpenBSD 6.0-6.9 Release Notes pledge 部分（`https://www.openbsd.org/60.html` 至 `https://www.openbsd.org/69.html`）；**pledge(2)** 手册页（`https://man.openbsd.org/pledge.2`）；6.0 errata 013_ssh_kexinit.patch（**sshd(8)** 协议解析 bug 修复） ［A］

**史观**：专题语（不设总纲条号）——安全工程的演进（原挂总纲第 17 条系伪名目，删条号）：pledge 在 6.x 周期的渐进部署是“可采用性优先”工程哲学的实践——pledge 接口简洁（`pledge("stdio rpath", NULL)` 一行即可），但覆盖范围扩展是一个持续工程过程，从 5.9 启用至 6.x 全面普及历时约 3 年；这一渐进路径与 FreeBSD Capsicum 的低采用率形成对比——Capsicum 因接口复杂（需 cap_rights_init() 等多步调用）在 FreeBSD base 中覆盖率长期低于 pledge 在 OpenBSD 中的覆盖；pledge 的“渐进部署”模式体现 OpenBSD 对安全机制“宁可慢速部署也要保证可采用性”的工程纪律

**辨析**：**须精确说明 pledge 在 6.x 周期的覆盖范围**：pledge 覆盖率以 openbsd.duckdb openbsd-src 仓库 usr.bin/ 路径下含 `pledge()` 调用的源文件计数为准——6.x 周期末期基本系统主要用户态工具已普遍采用 pledge，但精确覆盖率无单一权威统计 ；**pledge 与 errata 的关系**：pledge 不是 errata 修复的对象而是 errata 修复的辅助——errata 修补具体 bug，pledge 限制 bug 可利用范围，二者在 6.x 周期形成“修复 + 加固”双轨；**与 7.x 周期的对比**：7.x 周期 pledge 进入“成熟部署与漏洞响应工具”阶段，6.x 周期是“从部分应用到全面普及”的过渡阶段，两个阶段的工程节奏不同

## 201.2.3 **unveil(2)** 引入与 **syspatch(8)** 机制——6.4 双重安全革新

**要点**：OpenBSD 6.4（**2018-10-18** 发布〔原“10 月 25 日”与行 133 复查段自斥，统一为官方发布日〕）在安全响应机制上实现双重革新——其一，引入 **unveil(2)** 系统调用（openbsd.duckdb 显示首次 commit 为 2018-07-13 beck `8b23add8c74b`），实现文件系统访问的路径级限制，与 pledge 配合形成双重沙箱；其二，**syspatch(8)** 二进制补丁机制首次在 6.4 errata 页面中被提及——6.4 errata 页面明确记载"Alternatively, the syspatch(8) utility can be used to apply binary updates on the following architectures: amd64, i386, arm64"，而 6.0 errata 页面仅提及 **signify(1)** 签名的源码 patch，无 **syspatch(8)** ；**syspatch(8)** 的引入是 OpenBSD 安全响应机制从“源码补丁手动编译”到“二进制补丁一键更新”的范式转变，大幅降低管理员补丁负担；**unveil(2) 自身的安全修复**：6.4 errata 013_unveil.patch（**2019 年 1 月 27 日**）修复了 **unveil(2)** 系统调用的内存泄漏——这是 unveil 引入仅 4 个月后即发现并修复的自身漏洞，体现 OpenBSD“新机制引入后持续审计”的工程纪律

**史料**：**openbsd.duckdb** `commits` 表 openbsd-src 仓库 unveil 相关 commit 查询：`SELECT commit_hash, author_date, author_name, message_subject FROM commits WHERE repo_name='openbsd-src' AND author_date>='2018-07-01' AND author_date<'2019-10-01' AND message_subject LIKE '%unveil%' ORDER BY author_date ASC`；OpenBSD 6.4 errata 页面（`https://www.openbsd.org/errata64.html`）中 **syspatch(8)** 与 013_unveil.patch 条目；OpenBSD 6.0 errata 页面（`https://www.openbsd.org/errata60.html`）中 **signify(1)** 条目（无 **syspatch(8)**）；**unveil(2)** 手册页（`https://man.openbsd.org/unveil.2`）；**syspatch(8)** 手册页（`https://man.openbsd.org/syspatch.8`） ［A］

**史观**：专题语（不设总纲条号）——安全工程的演进（原挂总纲第 17 条系伪名目，删条号）：6.4 的双重安全革新体现 OpenBSD“安全机制演进与补丁分发现代化并行”的工程哲学——**unveil(2)** 是“最小权限”原则在文件系统访问中的实现，**syspatch(8)** 是“补丁可采用性优先”原则在分发机制中的实现；二者同期引入并非偶然，而是 OpenBSD 对“安全机制再好，若管理员不打补丁也无效”这一工程现实的回应；**syspatch(8)** 将补丁应用从“下载源码 patch→ signify 验证 → 编译 → 安装”简化为“syspatch 一键更新”，降低补丁部署门槛是安全治理成熟化的标志

**辨析**：**须严格区分** **syspatch(8)** 引入前后的补丁分发机制差异：① 6.0-6.3 周期（syspatch 引入前）：补丁以 **signify(1)** 签名的源码 unified diff 形式发布，管理员须手动下载、验证、编译、安装——这一流程对技术能力要求高，补丁部署延迟较大；② 6.4 起（syspatch 引入后）：补丁同时以源码 diff 与二进制 syspatch 形式发布，amd64/i386/arm64 架构管理员可通过 `syspatch` 命令一键更新——二进制补丁大幅降低部署门槛；**unveil(2) 自身漏洞的辨析**：6.4 errata 013_unveil.patch 修复 **unveil(2)** 内存泄漏，这是“安全机制自身亦有漏洞”的典型样本——任何安全机制都是代码，代码就有漏洞，**unveil(2)** 的内存泄漏不影响其作为文件系统访问限制机制的整体有效性，但提醒安全机制须经持续审计；**与 FreeBSD freebsd-update(8) 对比**：FreeBSD **freebsd-update(8)** 早在 6.x 周期前已提供二进制补丁（FreeBSD 6.2 起），OpenBSD **syspatch(8)** 在 6.4 引入是“后发但设计更简洁”——syspatch 仅支持 errata 补丁，freebsd-update 支持大版本升级与 errata 补丁

## 201.2.4 LibreSSL 独立维护路径的巩固——与 OpenSSL 路线分离的早期成果

**要点**：6.x 周期是 LibreSSL fork 后（2014 年 4 月 Heartbleed 后启动）独立维护路径的巩固期——openbsd-src 仓库 6.x 周期 LibreSSL 相关 CVE commit 至少 4 条：CVE-2016-0702（**2016 年 9 月 3 日** bcook `28f6a8c2f092`、`2eb27d8a6f67`，OpenSSL MOD_EXP_CTIME_COPY_FROM_PREBUF 常数时间修复）、CVE-2016-7055（**2017 年 1 月 31 日** inoguchi `6ebeafd8beed`，Broadwell Montgomery 乘法进位 bug）、CVE-2018-0735（**2018 年 11 月 15 日** tb `a67a257033ac`，OpenSSL ECDSA 签名时序侧信道缓解）、CVE-2019-1547（**2019 年 9 月 29 日** tb `baf7262a6abf`，EC_GROUP_set_generator NULL 余因子处理）；4 条 commit 涉及 4 个 CVE，年均约 1 个——这一频率远低于 OpenSSL 同期 CVE 数量，印证 LibreSSL“减少代码复杂度即减少攻击面”的工程哲学；LibreSSL 在 6.x 周期持续以 ISC 许可证独立维护，不跟随 OpenSSL 1.1.0/1.1.1 的 API 变更，与 FreeBSD 14.x 周期跟随 OpenSSL 3.0 的路径根本不同

  **LibreSSL 6.x 周期 CVE 修复 commit 列表**：

  | 日期 | commit hash | 作者 | CVE 编号 | 说明 |
  | --- | --- | --- | --- | --- |
  | 2016-09-03 | `28f6a8c2f092`、`2eb27d8a6f67` | bcook | CVE-2016-0702 | MOD_EXP_CTIME_COPY_FROM_PREBUF 常数时间修复 |
  | 2017-01-31 | `6ebeafd8beed` | inoguchi | CVE-2016-7055 | Broadwell Montgomery 乘法进位 bug |
  | 2018-11-15 | `a67a257033ac` | tb | CVE-2018-0735 | ECDSA 签名时序侧信道缓解 |
  | 2019-09-29 | `baf7262a6abf` | tb | CVE-2019-1547 | EC_GROUP_set_generator NULL 余因子处理 |

**史料**：**openbsd.duckdb** `commits` 表 openbsd-src 仓库 LibreSSL 相关 CVE commit 查询：

  ```sql
  SELECT commit_hash, author_date, author_name, message_subject
  FROM commits
  WHERE repo_name='openbsd-src'
    AND author_date>=‘2016-09-01’
    AND author_date<‘2019-10-01’
    AND (message_subject LIKE ‘%SSL%’ OR message_subject LIKE ‘%libcrypto%’
         OR message_subject LIKE ‘%LibreSSL%’)
    AND (message_body LIKE '%CVE-%' OR message_subject LIKE '%CVE-%')
  ORDER BY author_date ASC
  ```

  ；bcook 的 CVE-2016-0702 修复 commit `28f6a8c2f092`、`2eb27d8a6f67`；inoguchi 的 CVE-2016-7055 修复 commit `6ebeafd8beed`；tb 的 CVE-2018-0735 修复 commit `a67a257033ac`；tb 的 CVE-2019-1547 修复 commit `baf7262a6abf`；LibreSSL 项目文档（`https://www.libressl.org/`） ［A］

**史观**：总纲第 13 条——法律与道德是利益分配（原“法律结构”系伪名目，按许可证利益论旨改挂）：LibreSSL 独立维护路径是 OpenBSD“许可证纯洁性”哲学在加密栈的具体实践——OpenSSL 的 Apache 许可证与 OpenBSD 的 ISC 许可证偏好存在张力，fork 后 LibreSSL 以 ISC 许可证发布；6.x 周期 LibreSSL 年均约 1 个 CVE 的低频率印证“代码精简即安全增益”的工程逻辑——LibreSSL 删除了 OpenSSL 中的大量 dead code 与旧 API，攻击面随之缩减；但独立维护的代价是 LibreSSL 不获得 OpenSSL 1.1.0/1.1.1 的新特性（如 TLS 1.3 支持），这是“安全自主”与“功能跟随”的权衡

**辨析**：**须精确说明 LibreSSL CVE 的来源**：CVE-2016-0702 与 CVE-2016-7055 是 OpenSSL 上游漏洞（LibreSSL 因 fork 自 OpenSSL 继承了相关代码），LibreSSL 通过自行修复跟进；CVE-2018-0735 同样是 OpenSSL 上游漏洞，tb 将 OpenSSL commit `99540ec79491` 移植至 LibreSSL；CVE-2019-1547 是 OpenSSL 上游漏洞，tb 自行编写修复；4 个 CVE 均为 OpenSSL 上游漏洞的 LibreSSL 跟进修复，非 LibreSSL 独有漏洞——这一事实既说明 LibreSSL 继承了 OpenSSL 的历史代码债务，也说明 LibreSSL 维护者持续跟进上游安全修复；**与 OpenSSL 路径的对比**：OpenSSL 在 6.x 同期（2016-2019）发布了 1.1.0（2016.8）与 1.1.1（2018.9）两个大版本，引入 TLS 1.3 等新特性但伴随新 CVE；LibreSSL 选择不跟随 1.1.0/1.1.1 的 API 变更，以“代码稳定优先”避免新特性引入的新攻击面；**与 7.x 周期 LibreSSL 的对比**：7.x 周期 LibreSSL CVE 修复由 tb 主导（每年 2-3 个），6.x 周期 LibreSSL CVE 修复由 bcook、inoguchi、tb 多人参与，反映 LibreSSL 维护团队在 6.x 周期尚未集中至 tb 一人

## 201.2.7 6.x 周期 OpenBSD 安全响应文化评估——“主动审计—快速修复—加固重构”循环的形成期

**要点**：6.x 周期是 OpenBSD“主动审计—快速修复—加固重构”循环的形成期——**主动审计** 体现于 6.0 errata 中 8 月 3 日单日发布 029-039 共 11 个 patch（含 8 个 SECURITY FIX〔原作 9 个与辨析 8 SECURITY+3 RELIABILITY 明细自斥，按 errata 页面原始分类统一〕），反映一次系统性的内核安全审计；**快速修复** 体现于 Spectre v2 披露后 14 天内提交修复 commit（kettenis `d855ec95cfe6`，2018-01-17）；**加固重构** 体现于 6.4 引入 **unveil(2)** 与 RETGUARD 两项加固机制——unveil 是文件系统访问限制，RETGUARD 是返回地址保护，二者均是“发现漏洞后通过新机制缩小同类漏洞攻击面”的加固实践；6.x 周期 errata 发布机制经历从“源码 patch+**signify(1)** 签名”（6.0-6.3）到“源码 patch+**syspatch(8)** 二进制补丁”（6.4 起）的转变，这一转变大幅降低管理员补丁负担；**与 FreeBSD 安全文化对比**：FreeBSD 以集中式 Security Advisory（SA）发布安全修复，6.x 周期 FreeBSD 11.x/12.x 发布约 30 个 SA，OpenBSD 6.0-6.9 共 10 个版本的 errata patch 总数远超 30（仅 6.0/6.4/6.9 三个版本即达 107 个）——但 errata 数量多不意味着 OpenBSD 代码质量更差，而是 OpenBSD errata 包含 RELIABILITY FIX（可靠性修复）与 SECURITY FIX（安全修复）两类，FreeBSD SA 仅发布安全修复；**与 Linux 安全文化对比**：Linux 内核安全修复直接合并至主线 stable 分支，无集中式 errata 或 SA 发布机制——用户须自行跟踪 stable 分支 commit，补丁部署门槛高于 OpenBSD **syspatch(8)** 与 FreeBSD **freebsd-update(8)**

**史料**：**openbsd.duckdb** `commits` 表 openbsd-src 仓库 6.x 周期安全相关 commit 综合查询；OpenBSD 6.0 errata 页面（`https://www.openbsd.org/errata60.html`）中 2017-08-03 单日 11 个 patch 条目；OpenBSD 6.4 errata 页面（`https://www.openbsd.org/errata64.html`）中 **syspatch(8)** 条目；**pledge(2)**、**unveil(2)**、**signify(1)**、**syspatch(8)** 手册页；FreeBSD Security Advisories 官方存档（`https://www.freebsd.org/security/advisories/`）11.x/12.x 周期 SA 数量统计 ［A］

**史观**：总纲第 8 条——本体论上各方平等（原“社区治理”系伪名目，按族例改挂）：6.x 周期是 OpenBSD 安全响应文化从“源码补丁时代”向“二进制补丁时代”的过渡期，**syspatch(8)** 的引入是这一过渡的标志——补丁分发机制的现代化是安全治理成熟化的关键环节，再好的安全机制若管理员不打补丁也无效；OpenBSD errata 同时包含 RELIABILITY FIX 与 SECURITY FIX 的传统，反映 OpenBSD 将“可靠性”与“安全性”视为连续谱而非截然二分——一个可能导致 panic 的 bug 虽非直接安全漏洞，但可能被利用为 DoS 攻击向量，故须同步修复；这一传统与 FreeBSD SA 仅发布安全修复的传统不同，体现两个项目对“安全修复范围”的不同界定

**辨析**：**须精确说明 6.0 errata 8 月 3 日单日 11 个 patch 的性质**：029_sigio（RELIABILITY）、030_sendsyslog（RELIABILITY）、031_fuse（SECURITY）、032_recv（SECURITY）、033_tcp_usrreq（SECURITY）、034_sockaddr（SECURITY）、035_ptrace（SECURITY）、036_fcntl（SECURITY）、037_wsdisplay（RELIABILITY）、038_sosplice（SECURITY）、039_ieee80211（SECURITY）——11 个 patch 中 8 个为 SECURITY FIX、3 个为 RELIABILITY FIX，集中发布于同一日反映一次系统性的内核安全审计；**errata 数量对比的辨析**：OpenBSD errata 包含 RELIABILITY FIX 与 SECURITY FIX 两类，FreeBSD SA 仅发布安全修复——直接对比数量不公平，须区分 errata 中 SECURITY FIX 的数量；**syspatch(8) 引入的意义**：**syspatch(8)** 将补丁应用从“下载源码 patch→signify 验证 → 编译 → 安装”简化为“`syspatch` 一键更新”，降低补丁部署门槛是安全治理成熟化的标志，但 **syspatch(8)** 仅支持 amd64/i386/arm64 三架构，其他架构（如 macppc、sparc64）仍须源码 patch ；**与 7.x 周期的对比**：7.x 周期 pledge/unveil 进入“成熟部署与漏洞响应工具”阶段，6.x 周期是“形成期”——6.x 周期的“主动审计—快速修复—加固重构”循环在 7.x 周期成熟为稳定的工程节奏
