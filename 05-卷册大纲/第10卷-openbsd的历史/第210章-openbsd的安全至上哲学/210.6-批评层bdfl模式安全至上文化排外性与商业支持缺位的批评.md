## 210.6.1 BDFL 模式的权力集中风险与继承危机

**要点**：对 OpenBSD BDFL 模式的批评集中于权力集中与继承风险两个维度——其一，权力集中风险：de Raadt 个人掌握 committer 准入批准权、权限撤销权与所有重大架构决策的最终裁定权，OpenBSD 项目未如 FreeBSD Core Team 那样建立制度化的选举与制衡机制（9 人核心团队，2000 年起直选制），亦未如 NetBSD Foundation 那样建立正式的董事会议事规则，单一领导者的偏好直接决定 committer 阵容与技术路线；openbsd.duckdb openbsd-src 仓库 contributors 表显示 <deraadt@openbsd.org> 累计 27181 commits（1995-10-18 至 2026-07-16），占 openbsd-src 总 245857 commits 约 11%——这一占比在 31 年时间尺度上反映 de Raadt 个人对项目代码库的持续主导；其二，继承危机：de Raadt 1968 年生于南非比勒陀利亚，至 2026 年已年过五旬，OpenBSD 项目未建立公开的 BDFL 继任机制（对比 Linux Torvalds 公开提及的“副手梯队”或 Python PEP 13 治理委员会），de Raadt 退出后 OpenBSD 的治理结构能否维持是未知数；FreeBSD Core Team 选举制与 NetBSD Foundation 董事会选举制均建立了制度化的继任机制，BDFL 模式在继任问题上的脆弱性是结构性而非偶发性问题

**史料**：openbsd.duckdb openbsd-src 仓库 contributors 表（<deraadt@openbsd.org> 27181 commits 1995-10-18 至 2026-07-16）；OpenBSD 项目治理文档（<https://www.openbsd.org/goals.html>，经 WebFetch 核验未发现正式 committer 政策文档）；FreeBSD Core Team bylaws（<https://www.freebsd.org/internal/core-team/>）；NetBSD Foundation bylaws（<https://www.netbsd.org/foundation/>）；de Raadt 在 <misc@openbsd.org> 关于权限管理的发言（<https://marc.info/?laccopenbsd-misc>）；OpenBSD Foundation 年报（<https://www.openbsdfoundation.org/>，经 WebFetch 核验为加拿大非营利公司，支持 OpenBSD 及 OpenSSH、OpenBGPD、OpenNTPD、OpenSMTPD、LibreSSL、mandoc、rpki-client 等相关项目）［ 查证来源：openbsd.duckdb openbsd-src 仓库 contributors 表 <deraadt@openbsd.org> 记录；OpenBSD 官方 goals.html 页面经 WebFetch 核验未含正式 committer 政策文档；FreeBSD Core Team bylaws 与 NetBSD Foundation bylaws 经官网核验含选举条款；交叉验证方法：对照 OpenBSD 官方治理文档与 FreeBSD/NetBSD 治理文档的继任机制条款，对照 openbsd.duckdb deraadt 个人 commit 占比与项目总 commit 占比；存疑判定依据：OpenBSD 官方未公开发布 BDFL 继任机制文档，亦未公开讨论继任议题，项目可能存在内部讨论但未公开，须以邮件列表存档与 Foundation 文档交叉验证后方可确证 ］

**史观**：总纲第 5 条——没有必然性，只有偶然性：de Raadt 个人偏好与历史经验（1994 年被 NetBSD Core Team 疏远）直接塑造 OpenBSD BDFL 治理形态，单一领导者的人格与判断偶然地决定了项目的治理结构，而非制度化的集体决策机制；总纲第 13 条——法律与道德是利益分配：committer 权限的授予与撤销本质上是一种利益分配机制，谁获得 commit 权、谁被剥夺 commit 权，反映 OpenBSD 项目内部权力运作的具体形式

**辨析**：批评的合理性在不同叙事中评估不一——OpenBSD 阵营将 BDFL 模式视为“治理效率与一致性保障”，批评者将 BDFL 模式视为“权力集中与继承风险”，二者难以通约；【0 信任原则·权力集中风险的量化】“权力集中风险”论证须提供具体案例——若 OpenBSD 在 7.x 周期未发生实际的权限滥用事件或大规模 committer 退出潮，则“风险”可能是理论推演而非实践问题；【0 信任原则·继承危机的辨析】de Raadt 年龄增长是事实，但年龄不等于能力衰退——openbsd.duckdb 显示 de Raadt 2026-07-16 仍有 commit，其持续活跃度须以年度 commit 统计核验而非以年龄推演；【多源交叉验证不可靠性规则】多个 OpenBSD 外部观察者对 BDFL 模式的批评在多个独立来源中一致，但这一一致性可能源于对 BDFL 模式的共同前理解而非独立验证，须对照 OpenBSD 实际治理产出（如 31 年 release 节奏、committer 加入退出记录）综合评估

- 20.6.2“安全至上”文化的工程代价与生态影响

**要点**：对 OpenBSD“安全至上”文化的批评集中于工程代价与生态影响两个维度——其一，工程代价：OpenBSD 拒绝 binary blob 与 NDA 的哲学（OpenBSD goals.html 经 WebFetch 核验载明“NDAs are never acceptable”）让硬件支持进度受限，新 GPU、新无线网卡、新 ARM 单板支持通常滞后 Linux 1-2 年；OpenBSD 6.x-7.x 仍保留 big-lock 模型，多核扩展性不及 FreeBSD 与 Linux，在数据库等高并发场景落后；OpenBSD 未提供 Docker 运行时支持，jails 机制不完善，通过 vmm/vmd 提供轻量级虚拟化作为替代——这些工程代价是“安全至上”哲学的直接后果；其二，生态影响：OpenBSD“安全至上”文化在 BSD 阵营内部形成独特定位，但这一定位的代价是 OpenBSD 在云服务器、容器化、高性能计算等主流市场边缘化；Linux 选择 cgroups+namespaces 容器化路线、FreeBSD 选择 Jails+Capsicum 路线、OpenBSD 选择 pledge/unveil 路线——三者各自合理但市场结果不同，OpenBSD 的“安全细分市场”虽不可替代但规模有限；de Raadt 在 misc@ 邮件列表中多次以“Linux 接受 binary blob 牺牲了自由”反击硬件支持滞后的批评，但这一反击不改变 OpenBSD 硬件支持滞后的事实；统计结论印证——openbsd.duckdb 资料数据库 references 表总条目数 16,867（统计结论 C-41），其中可提取年份的条目 7,493 条，年份提取率 44.42%（统计结论 C-42），反映本书编纂过程中累积的 OpenBSD 相关学术文献总量；dblp 学术数据库收录的 BSD 主题论文共 122 篇（外部基准 E-19，去重前），其中 OpenBSD 主题论文 20 篇，OpenBSD 学术产出在 BSD 4 项目中居第二位（FreeBSD 74 篇、OpenBSD 20 篇、NetBSD 15 篇、BSD UNIX 13 篇），与 Linux 对照 dblp 论文 2,802 篇约为 OpenBSD 的 140 倍——学术产出规模差距反映 OpenBSD“安全至上”文化在学术界的影响范围相对有限

**辨析**：工程代价的合理性在不同叙事中评估不一——OpenBSD 阵营将硬件支持滞后视为“自由哲学的必要代价”，批评者将其视为“工程保守主义的局限”；【0 信任原则·binary blob 哲学的辨析】OpenBSD 拒绝 binary blob 的哲学在许可证纯洁性维度具有合理性，但在硬件支持维度产生代价——二者是同一选择的不同命名，不可分割；【0 信任原则·性能差距的量化】OpenBSD 在数据库与编译场景下通常落后 FreeBSD/Linux 20-50% 的判断须以同硬件同负载的基准测试为准，不同基准测试结果差异较大，不得以单一基准测试概括；【0 信任原则·容器支持不足的辨析】OpenBSD 缺乏容器支持是主动选择（pledge/unveil 路线）而非资源限制，但主动选择不等于无代价——容器生态的边缘化是这一选择的直接后果；**统计局限性标注**——C-41 references 表总条目 16,867 是本书编纂过程中累积的文献总量，非 OpenBSD 学术产出的全量统计，受本书编纂范围与收录标准影响，不得作为 OpenBSD 学术影响的权威评估；C-42 年份提取率 44.42% 受 references 表条目来源多样性影响（部分网页、邮件列表等来源未明确标注年份），不得仅凭年份提取率推断文献时间分布的完整性；E-19 dblp OpenBSD 论文 20 篇基于 dblp 收录标准（仅收录 CS 正式发表），受 dblp 收录偏差影响（会议论文优先于期刊论文、英文文献优先于其他语种），实际 OpenBSD 学术产出可能高于 20 篇；0 信任原则适用：统计显著 ≠ 实际显著，dblp 论文数量仅反映学术数据库收录情况，不等于 OpenBSD 学术影响的实际强度——OpenSSH、LibreSSL 等 OpenBSD 衍生项目被全球 SSH 与 TLS 部署采纳，其实际影响远超 dblp 收录的 20 篇 OpenBSD 主题论文

## 210.6.3 排外性文化与邮件列表氛围的系统性效应

**要点**：对 OpenBSD 排外性文化的批评集中于邮件列表氛围与贡献者融入两个维度——其一，邮件列表氛围：de Raadt 的批评风格以直接、尖锐著称是事实，<misc@openbsd.org> 邮件列表中存在“RTFM 文化”与“公开斥责”传统——新用户提问若未充分阅读手册页或 FAQ，可能遭遇生硬回应；de Raadt 本人在 misc@ 的多次发言以讽刺、斥责风格著称，这一风格在 OpenBSD 核心圈被视为“工程严谨”的体现，但在外部观察者眼中形成“排外”印象；其二，贡献者融入的系统性效应：邮件列表氛围可能系统性排斥特定类型的贡献者——如初学者、非英语母语者、风格温和的贡献者，这些贡献者可能在首次互动后即放弃贡献；openbsd.duckdb openbsd-src 仓库 contributors 表显示活跃 committer 阵容相对稳定但新加入者数量缓慢，对比 FreeBSD freebsd-src 仓库 contributors 表规模数倍于 OpenBSD——社区规模差异部分源于融入效率差异；被疏远贡献者的退出叙事须对称呈现——OpenBSD 历史上存在多位因与 de Raadt 风格冲突而退出的贡献者，但权限撤销的具体细节在 misc@ 中有时公开有时不公开，被撤销者的公开回应存档有限

## 210.6.4 商业支持缺位与资金困境的生态代价

**要点**：对 OpenBSD 商业支持缺位的批评集中于资金规模与生态影响两个维度——其一，资金规模：OpenBSD Foundation 2023 年度收入约 30 万 USD，对比 FreeBSD Foundation 2023 年度收入约 500 万 + USD（16.7 倍）、Linux Foundation 2023 年资产超 1 亿 USD（333 倍）——OpenBSD 资金规模约为 FreeBSD 的 6%、Linux Foundation 的 0.3%；OpenBSD Foundation 无全职员工，所有开发均靠志愿者业余推进，这使 OpenBSD 在与有企业支持的 Linux 内核、有 Foundation 全职员工的 FreeBSD 的功能开发竞赛中处于劣势；其二，生态影响：资金紧缺使 OpenBSD 无法雇佣全职开发者，2014 年 1 月因卡尔加里电费危机（约 20,000 USD/月）发出募捐公告——这一危机反映 OpenBSD 项目运营资金的结构性脆弱；商业支持的缺乏亦使 OpenBSD 在企业采纳维度受限——对比 FreeBSD 被 Netflix、Juniper 等企业大规模采纳，OpenBSD 的企业采纳案例较少（仅少数公司如 Kernel Networks 等提供支持［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］）；OpenBSD 以不到 30 万 USD 年预算维持的项目却产出 OpenSSH（全球事实标准）、LibreSSL、pf 等被广泛采纳的成果——这是“低投入 + 高影响”模式，但这一模式的可持续性依赖 de Raadt 与核心贡献者的持续志愿投入

**要点**：

- Asterisk 的架构由当事人澄清为两个分离的包：Asterisk 本体是呼叫控制与脚本系统，在 BSD 上运行良好——他在访谈中即经由两个 OpenBSD 系统通话；而 Zaptel（后更名为 DAHDI）电话卡内核驱动更为挑剔，旧版仅有 FreeBSD 与 OpenBSD 移植（由 handle 为 Gonzo 的贡献者等人完成），FreeBSD 的 package 版本偏旧。Digium 与开源开发者近月正推动把单体化的 Zaptel 组件拆分以降低耦合，目标使 Solaris 与 BSD 的移植更容易；BSD 社区对开发列表上报的兼容性问题通常能在 24 至 48 小时内修复。（BSDTalk EP166，[205.56-360.16]，L1）
- Digium 的商业模式建立在 GPL with exception 授权之上：代码以 GPL 发布，但回馈补丁的编码者须声明权利并允许 Digium 在极有限情形下于 GPL 之外商业授权，这一例外授权收入是 Digium 生存并持续向开源项目投入的基础。此外 Zaptel 驱动的计时功能长期支撑会议桥、呼叫等待音乐与 IAX2 中继等特性，纯 IP 部署则完全无需内核模块。（BSDTalk EP166，[437.92-464.70]，L1）
- Digium 不为 Linux 之外的系统提供官方支持，当事人坦承这并非技术问题而是专业人力与市场结构问题：BSD 社区虽然根基深厚，但其用户多为清楚自身需求的资深系统管理员，问题习惯在社区内部解决，商业支持需求远少于 Linux；辅以 BSD 系统管理员难觅且价格偏高的劳动力市场现实，企业自然倾向 Linux。Digium 设有专门的 asterisk-bsd 邮件列表（lists.digium.com）维持问答。（BSDTalk EP166，[681.96-946.40]，L1）
- 当事人自述其平台选择史：远自查旧 SunOS 时代学习 Unix，经历 Sun 与 NeXT 的迁移，90 年代中期接触 OpenBSD 预发布版本；虽认为 FreeBSD 与 NetBSD 特性推进更快，仍选择 OpenBSD 作为全部生产系统的默认平台，理由是其默认安全使部署后无需熬夜担忧；其个人网络几乎全为 OpenBSD（4.2 与 4.4 并行渐进升级），Mac 仅作前端，Linux 只用于测试经由 AMI、AGI 接口触达 Asterisk 的无 BSD 移植的第三方组件。（BSDTalk EP166，[743.68-826.16]，L1）
