# 194.10 OpenBSD 2.x 时期用户实测与硬件兼容实录（1998-2001）

**本节定位**：本小节承载 OpenBSD 2.x 时期（2.1—2.9，1997-06 至 2001-03）来自邮件列表的**用户实测类**史料——外围设备兼容报告、安装与启动排障、内核与显示配置调优、版本迁移阵痛、第三方应用部署实录。此类史料的共同特征是：陈述者即当事人（用户在 `<install@>`／`<users@>` 自述复现步骤，开发者在 `<tech@>`／`<ports@>` 直接回应），属**过程性证据**而非结论性断言。

**设立缘由**：2.x 时期恰是 OpenBSD 从「少数开发者的工程实验」走向「大量用户的生产与日常部署」的过渡期，用户实测报告由此成为该时代最稠密的一手史料来源。在 194.x 既有分工下——`194.1` 收多元群体贡献、`194.2` 收技术淘汰、`194.3` 收同期系统对照、`194.4` 收漏洞与 errata 响应、`194.6` 收 release 公告、`194.7`—`194.9` 收 4.4BSD-Lite2 继承的技术谱系——**用户实测类此前无第二个归宿**，只能倒进 `194.1`（多元群体贡献），造成该节的体量与语义双重错位。本小节自 2026-10-12 起作为该类史料的默认归宿；后续批次（`ob_b016` 起）的用户实测类候选一律路由至此，不再回流 `194.1`。

**证据等级纪律**：本节史料一律以 **L3**（转述／里程碑／当事人陈述）或 **L4**（发件人即当事人自述实测）标注。按考据纪律，L3／L4 属过程性证据，**具体事实与量化结论仍须交叉复核，不得单独引为定论**。

## 194.10.1 外围设备与总线兼容实测（1998-2001）

**要点**：2.x 时期 OpenBSD 的硬件支持是**用户驱动**的——内核设备枚举代码（PCI 配置空间扫描、ISA 探测、`umass` 等 USB 质量存储驱动、PCMCIA 卡功能配置）的实际覆盖范围，主要由用户在邮件列表中报告「装不上／认不出／起不来」后由开发者逐条补洞形成。典型形态包括：用户报告某型号磁盘控制器或 RAID 卡在启动或挂载时陷入内核态 panic；用户报告某 USB 调制解调器无法识别，转而追问其在设备表中缺的厂商 ID（vendor id）；用户询问某 PCMCIA 以太网卡是否为 `ne2k` 兼容，转引他人 `dmesg` 显示 `pcmcia0 function 0` 未配置；用户报告某数码相机经 `umass` 挂载时报 `Illegal Request` 一类协议层拒绝。这一时期的「兼容性」不是产品规格表，而是**一份由用户报告持续扩充的例外清单**——每份报告都是一次内核分支的边界探测。

**史料**：OpenBSD 邮件列表存档 `<tech@openbsd.org>`／`<ports@openbsd.org>`／`<install@openbsd.org>`（marc.info 收录，1998-2001）；marc.info 归档镜像；2.x 各版本 Release Notes 中的已知硬件问题章节；设备表与驱动提交日志。［考据注：具体型号与内核版本的对应关系以本小节末尾逐条 ROW_MINE 块的来源字段为准；本要点为类别性归纳，不作单条史料的替代］

**史观**：兼容清单的边界即项目权力边界的边界（去条号留论旨）：内核支持什么，取决于谁报告、谁被听见；用户实测报告因此不只是技术档案，而是贡献者网络的实际拓扑图

**辨析**：用户报告的**型号识别**环节错误率最高——用户在邮件中填写的型号、品牌名、总线类型常与厂商官方命名不一致，转述与转引链中型号漂移频繁；内核版本的判定亦易错（2.x 各版本间隔短，用户常以「最新版」而非版本号表述）。引用时须回到 `dmesg` 原文与其对应的内核版本，不得以型号名倒推支持状态；「已支持」不等于「稳定」——多数报告只证明该设备在某一内核版本上完成过一次挂载

**文献**：OpenBSD 邮件列表存档（marc.info）；2.x 各版本 Release Notes；`<tech@openbsd.org>` 设备提交线程

## 194.10.2 安装、启动与调试实录（1998-2001）

**要点**：安装与启动链路是本时期实测报告的第二密集区，且**报告质量两极分化**：一端是用户自述安装失败却拿不出完整复现步骤的模糊报告，另一端是完整贴出 `dmesg`／串口输出的高质量报告。后者构成了本时期安装流程与调试接口演进的真实需求来源。典型形态包括：用户报告 `ifconfig` 配置某接口时系统挂起；用户通过 `minicom` 经串口（`com1`／`ttyC` 类设备）接入 boot monitor 定位挂起位置；用户与开发者就 TTY 分配展开讨论——某串口被让给 X server（`xdm` 运行时占用），开发者给出 `init` 中 `getty` 不应占用该口的配置指引并指向 `/var/X11/xdm`。此外，控制台行为本身（Caps Lock 指示灯、`PCVT` 层的 LED 更新开关）亦成为实测对象，暴露出用户在无图形界面环境下对内核控制台驱动的可见性依赖。

**史料**：OpenBSD 邮件列表存档 `<install@openbsd.org>`／`<bug@openbsd.org>`／`<tech@openbsd.org>`（marc.info 收录，1998-2001）；marc.info 归档镜像；`init`／`getty`／`pcvt` 相关手册页与提交日志。［考据注：TTY 分配规则、串口占用归属的具体表述以末尾逐条 ROW_MINE 块的来源字段为准］

**史观**：可调试性是一种被低估的公共产品（去条号留论旨）：能否给出可复现的串口输出，直接决定了一份报告能否进入内核讨论——报告质量的差异，实质是调试接口可用性的差异

**辨析**：本类报告的**环境复原成本最高**——安装阶段的失败常无法复现（分区表、BIOS 设置、磁盘几何量均影响结果），且报告者常不记录 BIOS 与固件版本；「串口看不到输出」一类报告的诊断价值极低，须与「串口输出停在某一内核符号」明确区分。引用时只取可定位（含符号名／断点／`dmesg` 片段）的报告

**文献**：OpenBSD 邮件列表存档（marc.info）；`init(8)`／`getty(8)`／`pcvt(4)` 手册页；`<install@openbsd.org>` 安装流程讨论线程

## 194.10.3 内核与系统配置调优实录（1998-2001）

**要点**：进入桌面与网络日常部署后，配置层面的实测报告成为主体，且开发者回应往往给出**替代方案而非补丁**——这是 OpenBSD 简约哲学在配置支持上最直接的体现。典型形态包括：用户在 PIII 上装完 2.6 后配置 X 失败，改用 `xfree` 二进制并运行 `xf86setup`，分辨率卡在 680×400，手动改 `XF86Config` 与 `/var/backup` 至 1024×768 均无效，尽管显卡支持 24 位色深——此类报告集中暴露了该时期 X 配置文档与实际驱动行为之间的缺口；用户询问防火墙用途的点传协议配置，开发者建议改用用户态 `ppp` 而非 `pppd` 并指向 `man ppp`，其中 `-background` 选项可用于常驻后台运行；用户与开发者就网卡接口（如 `fxp0` 与 `fxp2`）能否接入同网段展开讨论；`cron` 的 `MAILTO` 配置亦成为高频实测点。此外，文件系统替代品的可靠性亦进入实测视野：开发者明确表态 `union` 文件系统除最简单用途外问题很多，`nullfs` 亦不完全可靠——即用户态可用方案与项目认可度之间存在落差。

**史料**：OpenBSD 邮件列表存档 `<users@openbsd.org>`／`<porting@openbsd.org>`／`<tech@openbsd.org>`（marc.info 收录，1998-2001）；marc.info 归档镜像；`XF86Config` 与 `xfree` 相关手册页；`ppp` 手册页与提交日志。［考据注：`union`／`nullfs` 可靠性表态的具体归属人以其 ROW_MINE 块来源字段为准］

**史观**：「以替代方案代替补丁」是一种刻意的技术政治（去条号留论旨）：它把适配成本转移给用户，换取内核面的稳定；配置类实测报告因此同时是满意度数据与不满数据

**辨析**：本类报告**时效性衰减最快**——配置文档与驱动行为在数版本内即漂移，1998 年的 `XF86Config` 排障方法对 2001 年已部分失效；引用时须以报告日期所对应的版本为准，不得跨版本合并结论；分辨率、色深一类数值在不同报告间口径不一（用户常以「跑不满」表述），须回原文核定

**文献**：OpenBSD 邮件列表存档（marc.info）；`ppp(8)`／`XF86Config` 手册页；`<users@openbsd.org>` 配置讨论线程

## 194.10.4 版本迁移与用户态兼容阵痛（1998-2001）

**要点**：2.x 时期用户态的兼容性成本集中体现为**运行时告警与标准合规落差**，且报告者多为被告警打断的普通用户，而非开发者。典型形态包括：用户在升级后遭遇 `libc` 运行时版本不匹配（如 `libc.so.19.0` 类版本符号）引发的动态链接器告警；用户报告 `makewhatis` 一类索引工具 SIGSEGV；用户报告 Alpha 架构（`sx164` 类平台）在版本差异中的移植问题。更结构性的一类是**标准合规落差**：开发者明确表态 OpenBSD 头文件距离 `_XOPEN_SOURCE` 等标准合规「还很远」，用户据此反馈既有的 STREAMS 类软件无法编译，而项目给出的指引是改用套接字接口（或需 FreeBSD 的 `netgraph`），并明确 OpenBSD 无 STREAMS——即**不兼容即不补**。此外，文档一致性亦成为实测对象：用户核验 `kinit(1)` 手册 SEE ALSO 段列出的 `kerberos(1)`、`kdestroy(1)`、`klist(1)`、`toehold(1)` 时，用 `man toehold` 与 `locate toehold` 检索均查不到该条目，判定文档引用有误。

**史料**：OpenBSD 邮件列表存档 `<tech@openbsd.org>`／`<porting@openbsd.org>`（marc.info 收录，1998-2001）；marc.info 归档镜像；相关版本 Release Notes 的运行时库变更段；手册页提交日志。［考据注：「`_XOPEN_SOURCE` 合规距离」与「无 STREAMS」两处表态的具体归属人以其 ROW_MINE 块来源字段为准］

**史观**：不兼容即不补，是项目对下游适配成本的显式定价（去条号留论旨）：标准合规落差不是缺陷而是约束条件，用户的迁移阵痛是被计入工程预算的成本项

**辨析**：本类报告的**版本号口径最需核验**——用户常以模糊表述（「最新版」）代替版本号，而 2.x 各版本间隔短，运行时库版本符号的对应关系须回 `dmesg` 与 Release Notes 核定；SIGSEGV 一类报告若不附 `ulimit -a` 与二进制来源，则无法判断是工具缺陷还是环境异常；标准合规表态属**开发者意见**而非规范结论，引用时须标明其为陈述而非判定

**文献**：OpenBSD 邮件列表存档（marc.info）；2.x 各版本 Release Notes；`kinit(1)` 等手册页修订日志

## 194.10.5 第三方与应用层兼容实录（1998-2001）

**要点**：应用层兼容报告标志着用户群从「跑系统」进入「跑业务」，报告对象从内核设备转向第三方组件的部署条件。典型形态包括：用户在部署特定应用（如 Zope 2.3.0 一类的第三方 Web 应用）时报告其安装与运行条件依赖，由开发者给出适配建议；应用对运行时库版本、头文件标准合规（见 194.10.4）的依赖在此集中暴露。此类报告与 194.10.1—194.10.4 的区别在于：问题根因往往不在 OpenBSD 自身，而在第三方软件的工程假设与 OpenBSD 工程假设之间的错配，解决方案因此多落在应用侧配置或编译开关，而非内核补丁。

**史料**：OpenBSD 邮件列表存档 `<ports@openbsd.org>`／`<users@openbsd.org>`（marc.info 收录，1998-2001）；marc.info 归档镜像；第三方应用自身的历史文档。［考据注：具体应用名称与版本号以末尾逐条 ROW_MINE 块的来源字段为准］

**史观**：应用层兼容问题是「谁承担适配成本」的一次公开表决（去条号留论旨）：当解决方案落在应用侧，项目即宣布自身工程假设不可谈判

**辨析**：本类报告的**第三方组件版本极易漂移**——第三方软件版本更新快于操作系统，同一问题在不同应用版本上的表现可能完全不同；引用时须同时固定操作系统版本与第三方组件版本，二者缺一则结论不可迁移；「已解决」的多数案例是应用侧改配置而非项目改代码，不得据此推断项目侧支持状态

**文献**：OpenBSD 邮件列表存档（marc.info）；`<ports@openbsd.org>` 部署讨论线程；第三方应用历史文档

### 史观映射

> 用户实测类史料的价值在于其**过程性**而非**结论性**：2.x 时期内核覆盖范围、安装调试接口的可用性、配置文档与驱动行为的落差、标准合规的战略选择、应用侧适配成本的分配——这五项工程决策都不在 Release Notes 里，而只存在于用户报告与开发者回应的往返之中。把它们从 `194.1`（多元群体贡献）分流至此，不是给史料换一个住处，而是承认：**用户实测报告是一个独立的史料层，其证据等级（L3／L4，过程性证据）与叙事功能（记录决策过程而非宣告结论）都与开发者自述（`194.1`）不同**。本小节末尾逐条 ROW_MINE 块按 pk 升序排列，时间序为 1998-06 至 2001-03；引用时须以各块的来源字段（`CL-RM-*` 与日期）为唯一权威定位，本小节的类别性要点仅作导读，不作单条史料的替代。
