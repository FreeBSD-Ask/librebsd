# 202.6 OpenBSD 7.x 时期的技术淘汰——多项旧技术 → 新技术交替演进（2020-2026）

**OpenBSD 7.x 技术淘汰时间线总览**：

| 旧技术 | 新技术 | 引入版本 | 发布日期 | 演进方向 |
| --- | --- | --- | --- | --- |
| 旧 ARM64 支持（Tier-2） | Tier-1 arm64 平台 | 7.0 | 2021-10-14 | 实验性 → 主流架构 |
| 旧 ARM 单板支持 | RK3588/Raspberry Pi 5 支持 | 7.4-7.5 | 2023-10/2024-05 | 旧 ARM 单板 → 新 ARM 单板 |
| 单音频设备子系统 | 多音频设备并发与切换 | 7.4 | 2023-10 | 单设备 → 多设备并发 |
| 早期安全机制 | pledge/unveil/RETGUARD 持续硬化 | 7.0-7.7 | 2021-2025 | 早期机制 → 持续硬化 |

## 202.6.1 旧 ARM64 支持 → Tier-1 arm64 平台（7.0，2021.10）

**要点**：OpenBSD 7.0（2021-10）将 arm64 提升为 Tier-1 平台，与 amd64 同级；先前 arm64 在 6.x 时期已有支持但为 Tier-2；7.0 的 Tier-1 提升意味着 arm64 获得完整安装介质、二进制快照、长期维护承诺；后续 7.2-7.4 持续改进 ARM64 支持——包括树莓派 4/5、Apple Silicon（M1/M2）的实验性支持；可视为 “实验性 arm64→Tier-1 主流架构” 的演进

**史料**：OpenBSD 7.0 Release Notes arm64 部分（<https://www.openbsd.org/70.html>）；OpenBSD 7.2-7.4 Release Notes arm64 改进；arm64 移植邮件列表；CVS commit log；openbsd.duckdb openbsd-src 仓库 commit 2021-10-15 “openbsd 7.0 release shipped with...” ［A］

**史观**：总纲第 7 条——技术选择即政治选择：OpenBSD 将 arm64 提升为 Tier-1 是 ARM64 硬件市场普及背景下的政治选择——以 “主流架构必须完整支持” 为预设，将工程资源从 Tier-2/Tier-3 平台转移至 arm64，与 NetBSD “支持一切硬件” 的路线不同

**辨析**：arm64 Tier-1 的具体定义以 OpenBSD 平台支持政策文档为准——Tier-1 平台获得完整安装介质、二进制快照、长期维护承诺；Apple Silicon 支持的具体进度以 Release Notes 与 commit log 为准——M1 实验性支持始于 7.2，M2 支持在 7.4 后逐步完善；经 openbsd.duckdb openbsd-src commits 表验证，OpenBSD 7.0 release 相关 commit 为 2021-10-15（“openbsd 7.0 release shipped with...”），与 7.0（2021.10）发布时间一致

**文献**：OpenBSD Release Notes [EB/OL]. <https://www.openbsd.org/70.html>；arm64 移植文档 [EB/OL]. <https://www.openbsd.org/arm64.html>；OpenBSD 平台支持政策文档；邮件列表档案 [EB/OL]. <https://marc.info/?laccopenbsd-misc>；openbsd.duckdb openbsd-src 仓库 commit 2021-10-15 “openbsd 7.0 release shipped with...” ［A］

## 202.6.2 旧单板计算机 → RK3588/Raspberry Pi 5 支持（7.2-7.4）

**要点**：OpenBSD 7.2-7.4 持续改进对新一代 ARM 单板计算机的支持——包括 Rockchip RK3588（7.4）、Raspberry Pi 5（7.5）；这些支持基于 OpenBSD 拒绝 binary blob 的开源驱动哲学，代码质量高但支持进度滞后 Linux；OpenBSD 在单板计算机市场的存在感让其成为嵌入式与教育场景的可选 BSD 系统；可视为 “旧 ARM 单板 → 新 ARM 单板” 的硬件支持替代

**史料**：OpenBSD 7.2-7.5 Release Notes 单板计算机支持部分；**rkgrf(4)**、**rkgpio(4)** 等驱动手册页；CVS commit log；arm64 移植邮件列表 ［A］

**史观**：总纲第 24 条——法律结构：OpenBSD 拒绝 binary blob 的许可证哲学影响新单板支持进度——以 “代码必须可审计为可信来源” 为预设，宁可支持滞后也不接受厂商闭源固件

**辨析**：RK3588 与 Raspberry Pi 5 的具体支持版本以 OpenBSD Release Notes 与手册页为准——RK3588 支持始于 7.4，Raspberry Pi 5 支持始于 7.5 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］；OpenBSD 与 Linux 在单板支持上的差距以各自手册页与内核文档的驱动引入时间对比为准

**文献**：OpenBSD Release Notes [EB/OL]. <https://www.openbsd.org/plus.html>；手册页 [EB/OL]. <https://man.openbsd.org/>；arm64 移植文档 [EB/OL]. <https://www.openbsd.org/arm64.html>；OpenBSD 邮件列表档案 [EB/OL]. <https://marc.info/?laccopenbsd-misc> ［A］

## 202.6.3 旧音频子系统 → 多音频设备改进（7.4）

**要点**：OpenBSD 7.4（2023-10）改进音频子系统，支持多音频设备并发与切换；先前 OpenBSD 音频子系统（基于 **audio(4)** 与 **mixerctl(8)**）对多设备场景支持有限；7.4 引入新的音频设备管理机制，让用户可在多个输出设备间动态切换；改进让 OpenBSD 在桌面用户场景获得更好体验；可视为 “单音频设备 → 多音频设备并发” 的演进

**史料**：OpenBSD 7.4 Release Notes 音频部分（<https://www.openbsd.org/74.html>）；**audio(4)**手册页（<https://man.openbsd.org/audio.4>）；**mixerctl(8)** 手册页（<https://man.openbsd.org/mixerctl.8>）；**sndioctl(1)** 手册页（<https://man.openbsd.org/sndioctl.1>）；tech@ 邮件列表音频讨论；CVS commit log ［A］

**史观**：总纲第 7 条——技术选择即政治选择：OpenBSD 投入工程资源改进音频子系统是针对桌面用户需求的政治选择——以 “安全系统亦须可用作日常桌面” 为预设，将资源分配给音频子系统而非仅专注于服务器场景

**辨析**：多音频设备改进的具体版本以 OpenBSD 7.4 Release Notes 与 **audio(4)** 手册页修订历史为准——7.4 引入多设备并发与动态切换机制；**sndioctl(1)** 的引入版本以手册页为准 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］；OpenBSD 音频子系统与 Linux PulseAudio/PipeWire 的对比以各自架构文档为准——OpenBSD 音频子系统设计简洁但功能较少，Linux PulseAudio/PipeWire 功能丰富但架构复杂

**文献**：OpenBSD 7.4 Release Notes [EB/OL]. <https://www.openbsd.org/74.html>；**audio(4)**手册页 [EB/OL]. <https://man.openbsd.org/audio.4>；**mixerctl(8)** 手册页 [EB/OL]. <https://man.openbsd.org/mixerctl.8>；OpenBSD 邮件列表档案 [EB/OL]. <https://marc.info/?laccopenbsd-tech> ［A］

## 202.6.4 持续安全硬化 → 7.x 标志性安全改进（7.0-7.7）

**要点**：OpenBSD 7.x 时期（2020-2026）持续进行安全硬化改进——包括 pledge/unveil 覆盖率扩展、RETGUARD 架构扩展（arm64 等）、KARL 改进、malloc 强化持续；7.x 时期还引入对新型 CPU 漏洞（如 Spectre/Meltdown 后续变种）的缓解；这些改进延续 OpenBSD “默认安全” 工程哲学，让 7.x 在安全机制领域保持领先；可视为 “早期安全机制 → 持续硬化安全机制” 的演进

**史料**：OpenBSD 7.0-7.7 Release Notes 安全部分（<https://www.openbsd.org/plus.html>）；**pledge(2)**手册页（<https://man.openbsd.org/pledge.2>）、**unveil(2)** 手册页（<https://man.openbsd.org/unveil.2>）；OpenBSD 安全机制设计文档；tech@ 邮件列表安全讨论；CVS commit log ［A］

**史观**：总纲第 25 条——0 信任原则：7.x 时期安全硬化是 0 信任原则在工程实践中的持续显现——pledge/unveil 覆盖率扩展意味着更多基本系统程序接受权限限制，RETGUARD 架构扩展意味着更多平台获得控制流完整性保护，KARL 改进意味着内核地址随机化更难预测

**辨析**：7.x 时期安全改进的具体里程碑以 Release Notes 安全部分为准——每个版本的安全改进在 Release Notes 中有独立条目；pledge/unveil 覆盖率的具体数字无权威统计 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］；与 Linux KASLR/CFG、Microsoft CFG 的对比以各自设计文档为准——三者设计目标与覆盖范围不同（pledge 是进程级权限限制，KASLR/CFG 是内核级防护）

**文献**：OpenBSD 7.0-7.7 Release Notes [EB/OL]. <https://www.openbsd.org/plus.html>；**pledge(2)**手册页 [EB/OL]. <https://man.openbsd.org/pledge.2>；**unveil(2)** 手册页 [EB/OL]. <https://man.openbsd.org/unveil.2>；OpenBSD 安全机制文档；tech@ 邮件列表档案 [EB/OL]. <https://marc.info/?laccopenbsd-tech> ［A］
