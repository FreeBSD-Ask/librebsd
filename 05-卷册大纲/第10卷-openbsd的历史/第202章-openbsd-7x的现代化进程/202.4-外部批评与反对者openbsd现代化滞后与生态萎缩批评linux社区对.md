# 202.4 外部批评与反对者：OpenBSD 现代化滞后与生态萎缩批评——Linux 社区对 OpenBSD “硬件支持滞后” 的批评、FreeBSD 社区对 OpenBSD “SMP 性能不足” 的质疑、用户对 OpenBSD “Docker/容器支持不足” 的抱怨

## 202.4.1 硬件支持滞后的批评

**要点**：2013-2026 年间 Linux 社区对 OpenBSD “硬件支持滞后” 的批评持续——新 GPU、新无线网卡、新 ARM 单板支持往往明显滞后于 Linux；OpenBSD 拒绝 binary blob 与 NDA 的哲学让支持进度受限；de Raadt 反击称 Linux 接受 binary blob 牺牲了自由

**史料**：Linux 邮件列表与论坛对 OpenBSD 硬件支持的批评；de Raadt 在 misc@ 的反击发言（<https://marc.info/?l=openbsd-misc>）；OpenBSD 硬件支持文档（<https://www.openbsd.org/faq/faq3.html>） [A]

**史观**：总纲第 13 条——法律与道德是利益分配：OpenBSD 拒绝 binary blob 的许可证哲学直接导致硬件支持滞后——以 “代码必须可审计为可信来源” 为预设，宁可支持滞后也不接受厂商闭源固件，这一选择是许可证层面的利益分配对硬件支持范围的直接塑造

**辨析**：硬件支持滞后的具体时间差在不同硬件类别中差异较大——GPU 与 ARM 单板支持的滞后常以年计，无线网卡支持的滞后则多以月计；具体滞后时间以 OpenBSD 手册页与 Linux 内核文档的驱动引入时间对比为准

**文献**：OpenBSD 硬件支持文档 [EB/OL]. <https://www.openbsd.org/faq/faq3.html>；Linux 社区批评档案；de Raadt 邮件列表发言 [EB/OL]. <https://marc.info/?l=openbsd-misc> [A]

## 202.4.2 SMP 性能不足的质疑

**要点**：FreeBSD 社区对 OpenBSD “SMP 性能不足” 的质疑持续——OpenBSD 6.x-7.x 仍保留 big-lock 模型，多核扩展性不及 FreeBSD 与 Linux；OpenBSD 在数据库等高并发场景落后；de Raadt 辩称安全优先于性能

**史料**：OpenBSD SMP 设计文档；基准测试对比报告；misc@ 邮件列表中关于 SMP 性能的讨论（<https://marc.info/?l=openbsd-misc>） [A]

**史观**：总纲第 3 条——不存在进步，只有权力再分配：OpenBSD 选择安全优先的 SMP 路线（big-lock 模型简化了内核并发控制，降低了安全漏洞风险）是以 “安全性优先于性能” 为预设的选择——SMP 扩展性的差距并非技术进步程度的差距，而是安全与性能两种价值取向之间的权力再分配——宁可牺牲多核扩展性也不引入细粒度锁带来的并发复杂性

**辨析**：SMP 性能差距的具体数字在不同基准测试中差异较大——以同硬件同负载的 Phoronix 等基准测试为准，OpenBSD 在数据库（PostgreSQL/MySQL）与编译（`make -jN`）场景下通常落后于 FreeBSD/Linux，差距幅度因负载与版本而异；6.x-7.x 时期的 SMP 改进以 Release Notes 中 kernel 部分为准

**文献**：OpenBSD SMP 文档；BSD 基准测试对比；misc@ 邮件列表档案 [EB/OL]. <https://marc.info/?l=openbsd-misc> [A]

## 202.4.3 容器支持不足的抱怨

**要点**：用户对 OpenBSD “Docker/容器支持不足” 的抱怨持续——OpenBSD 未提供 Docker 运行时支持，亦无 FreeBSD 式 jails 机制；OpenBSD 通过 vmm/vmd 提供轻量级虚拟化作为替代；容器支持不足让 OpenBSD 在云服务器市场边缘化

**史料**：misc@ 邮件列表中关于容器支持的抱怨（<https://marc.info/?l=openbsd-misc>）；OpenBSD vmm/vmd 文档（<https://man.openbsd.org/vmm.4>、<https://man.openbsd.org/vmd.8>）；Docker on OpenBSD 讨论 [A]

**史观**：总纲第 3 条——不存在进步，只有权力再分配：OpenBSD 选择 pledge/unveil 路线（进程级沙箱）而非 Docker 路线（容器级隔离）是以 “最小权限优先于容器化” 为预设的选择——沙箱与容器并非技术进步程度的差距，而是两种隔离哲学之间的权力再分配——pledge/unveil 提供进程级权限限制，vmm/vmd 提供轻量级虚拟化，二者组合替代容器但不与 Docker 生态兼容

**辨析**：OpenBSD 缺乏容器支持的具体原因是技术选择——OpenBSD 选择 pledge/unveil + vmm/vmd 路线而非 cgroups + namespaces 路线，是主动选择而非资源限制；用户对容器需求的实际规模无权威统计 [考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准]

**文献**：OpenBSD vmm 文档 [EB/OL]. <https://man.openbsd.org/vmm.4>；misc@ 邮件列表档案 [EB/OL]. <https://marc.info/?l=openbsd-misc>；Docker 相关讨论 [A]
