# 191.2 pf 防火墙的持续演进（2005-2012）——pf 从 4.0 到 5.2 持续改进，引入 synproxy、state tracking、ALTQ（队列调度）、CARP（冗余协议）等特性

## 191.2.1 synproxy 与 state tracking 的设计

**要点**：pf 引入 synproxy 状态以防御 SYN flood 攻击，代理 TCP 三次握手——synproxy 让 pf 在客户端与服务器之间插入代理，仅当三次握手完成才向服务器转发连接请求；state tracking 机制跟踪连接状态，自动关闭空闲连接；synproxy 与 Linux SYN cookies 设计思路不同——SYN cookies 在服务器端无状态地编码连接状态至 SYN-ACK 序列号，synproxy 在防火墙端有状态地代理握手，前者节省服务器资源但牺牲 TCP 语义完整性，后者保留 TCP 语义但需防火墙维护状态

**史料**：OpenBSD **pf.conf(5)** 手册页 synproxy state 部分（<https://man.openbsd.org/pf.conf.5>）；OpenBSD CVS commit log 中 synproxy 相关 commit；Linux SYN cookies 文档（<https://www.kernel.org/doc/html/latest/networking/syncookies.html>） ［A］

**史观**：总纲第 17 条——软件工程：synproxy 作为状态机代理改变 pf 的 DoS 防御能力——synproxy 将防火墙从 “无状态包过滤” 升级为 “有状态握手代理”，这一设计将 DoS 防御从服务器端（SYN cookies）转移至网络边界（pf synproxy），是软件工程中 “职责分离” 在网络安全层的实践

**辨析**：synproxy 与 Linux SYN cookies 的具体差异以 **pf.conf(5)** 手册页与 Linux 文档对比为准——synproxy 是 pf 的可选状态模式（`set state defaults synproxy`），SYN cookies 是 Linux 内核的 sysctl 开关（`net.ipv4.tcp_syncookies`）；state tracking 的状态机以 **pf.conf(5)** 手册页 “Stateful Filtering” 部分为准——pf 维护 TCP/UDP/ICMP 的连接状态表，默认空闲超时由协议决定

**文献**：OpenBSD **pf.conf(5)** 手册页 [EB/OL]. <https://man.openbsd.org/pf.conf.5>；Linux SYN cookies 文档 [EB/OL]. <https://www.kernel.org/doc/html/latest/networking/syncookies.html> ［A］

## 191.2.2 ALTQ 队列调度的工程效应

**要点**：ALTQ（Alternate Queuing）是 OpenBSD 集成至 pf 的流量整形框架，由 Kenjiro Cho（kjc@）等在 1990 年代末设计；ALTQ 支持 CBQ、HFSC、PRIQ 等队列调度算法；openbsd.duckdb 显示 kjc@ 在 openbsd-src 仓库 2002-05-31 commit 0b32f0e6892eb “define ALTQ_NOPCC if i386 and ! I586_CPU and ! I686_CPU” 反映 ALTQ 在 4.x 周期前的早期维护；ALTQ 让 pf 在企业网络流量管理领域获得部署

**史料**：openbsd.duckdb openbsd-src 仓库 commit 0b32f0e6892eb（2002-05-31 kjc “define ALTQ_NOPCC”）；ALTQ 项目文档（<http://altq.sourceforge.net/>）；Kenjiro Cho 论文（Kenjiro Cho, "A Framework for Alternate Queueing: Towards Traffic Management Beyond PFIFO", 1999, INQIE）；OpenBSD 4.x Release Notes ALTQ 部分 ［B］

**史观**：总纲第 10 条——边缘者贡献：Cho 作为日本裔研究者在 1990 年代末设计的 ALTQ 框架，后续被 OpenBSD 集成为 pf 的流量整形子系统——这一路径是 “学术研究 → 开源集成” 的典型，ALTQ 从研究原型（Cho 在东京大学的博士工作）演变为生产系统组件

**辨析**：ALTQ 与 Linux tc（traffic control）的设计差异——ALTQ 集成于 pf 规则语言，配置与防火墙规则统一；Linux tc 独立于 netfilter，配置需单独的 tc 命令，二者抽象层次不同；ALTQ 在企业部署的实际规模无权威统计 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

**文献**：ALTQ 项目文档 [EB/OL]. <http://altq.sourceforge.net/>；Kenjiro Cho. A Framework for Alternate Queueing [R]. 1999；openbsd.duckdb openbsd-src 仓库 commit 0b32f0e6892eb ［B］

## 191.2.3 CARP 冗余协议的开发

**要点**：CARP（Common Address Redundancy Protocol）由 OpenBSD 开发作为 VRRP（Virtual Router Redundancy Protocol，RFC 3768）的替代，因 VRRP 涉及 Cisco 持有的美国专利 US 5,473,599（1995 年申请，2005 年到期）；CARP 由 Reyk Flöter（reyk@）等设计，openbsd.duckdb 显示 reyk@ 在 openbsd-src 仓库 2005-01-03 至 2010-12-22 共 1004 条 commit；CARP 随 OpenBSD 3.5（2004.5）发布——openbsd.duckdb 中 2004-03-28 millert commit `2897e1ed6a948` “Revise for OpenBSD 3.5” 提及 3.5 release 上下文；CARP 让 OpenBSD 在高可用性网络部署中获得存在感

  **CARP 与 VRRP 对照**：

  | 维度 | VRRP | CARP |
  | --- | --- | --- |
  | 协议规范 | RFC 3768 | OpenBSD 自研 |
  | 专利状态 | Cisco US 5,473,599（1995 申请，2005 到期） | 无专利负担 |
  | OpenBSD 引入版本 | 未引入（专利期内） | 3.5（2004.5） |
  | 兼容性 | — | 不兼容 VRRP（协议头不同） |
  | 功能等价 | 是 | 是 |

**史料**：openbsd.duckdb openbsd-src 仓库 reyk@ 2005-2010 commit 统计（1004 条）；commit 2897e1ed6a948（2004-03-28 millert “Revise for OpenBSD 3.5”）；CARP 设计文档（<https://www.openbsd.org/faq/pf/carp.html>）；VRRP 专利 US 5,473,599（USPTO）；RFC 3768 VRRP ［A］

**史观**：总纲第 12 条——法律结构：VRRP 专利作为法律结构障碍催生 CARP fork——Cisco 持有的 US 5,473,599 专利使 OpenBSD 无法自由实现 VRRP，OpenBSD 选择重新设计协议（CARP）而非寻求专利授权，这一选择是法律结构（专利制度）对技术实现（协议设计）的直接塑造

**辨析**：VRRP 专利 US 5,473,599 的具体范围以 USPTO 专利文本为准——该专利于 1995 年 6 月申请，2005 年 6 月到期，覆盖 “虚拟路由器冗余协议” 的核心机制；CARP 与 VRRP 的兼容性以协议规范对比为准——CARP 不兼容 VRRP（协议头不同），但功能等价；Cisco 在专利到期后（2005 年后）未公开追究 CARP 实现

**文献**：CARP 设计文档 [EB/OL]. <https://www.openbsd.org/faq/pf/carp.html>；USPTO 专利 US 5,473,599；RFC 3768 VRRP；openbsd.duckdb openbsd-src 仓库 reyk@ commit ［A］

**要点**：

- Brauer 回顾 match 规则的起源与根本性：他自 2003 年起就想要 pass 与 block 之外的中性动作而始终无法说服同侪；NAT 改造使其成为刚需——否则每条 pass 规则都得附带 nat to。实现之后他才意识到这是 PF 的根本变化：旧模型由最后匹配规则决定一切，状态只需保存指回该规则的指针；新模型下一个包可被多个 match 规则依次作用（队列、日志、标签、scrub 等），状态上须维护命中的 match 规则链表。（BSDTalk EP192，[207.12-330.88]，L1）
- 4.6 的 scrub 重写源于 scrub 混杂了本不应混杂的职责：碎片重组、规范化与 MSS 钳制、TOS 改写等，且作为独立规则集须对每个进入的包遍历，代价高昂。拆分后规范化成为可选的常规规则，碎片重组简化为单一的开关并改为默认开启；此前用户忘记书写 scrub 行时，未经重组的碎片会被静默丢弃，而几乎没有人的规则集按碎片情形写过。（BSDTalk EP192，[424.76-586.58]，L1）
- 碎片重组原有三种方法，实际上无人使用替代方案，归一为全量重组有两条环境性理由：互联网因 path MTU discovery 基本生效而碎片大为稀少；OpenBSD 内核内存管理从 3.4 时代启动时静态池分配（PF 内存耗尽即 panic）转向动态分配，压力不再。4.7 的 NAT 重写则带来约三成的实测提速，从 4.4 直接跃升可叠加 scrub 与翻译规则集消除的双重收益达约六成且体感明显；NAT 重写净删近千行，整个过程共去除约一千三百至一千五百行，当事人自陈因改进过于显然而未再做大量基准测试。（BSDTalk EP192，[491.96-729.28]，L1）
- NAT 与 RDR 成为常规规则上的动作（nat-to、rdr-to）后改变了规则书写范式：地址自用户视角即时改写，先 match in nat to 某地址、后继 pass in from 同一地址即可命中；需要时也可写多条带不同 NAT 设置的 pass 规则。管理员的规则集得以按逻辑分组——以一组 match 规则完成队列挂接等魔法，再把放行或阻止的裁决推迟到别处。（BSDTalk EP192，[871.08-929.16]，L1）
- Henning Brauer 自述正在重写 PF 的队列子系统以取代旧 ALTQ：旧实现约九千行代码、带有 32 位上限且使用方式过于困难，新实现按 PF 原生方式重建队列功能；计划保留旧 ALTQ 一至两个发布周期供用户过渡，届时重命名若干冲突关键词，迁移成本基本只是一次配置调整。（BSDTalk EP214，[90.0-179.32]，L1）
- rthreads 是 OpenBSD 5.1 发布后 current 中最重大的变化：一对一的线程实现使用户态每个线程对应一个内核线程，取代此前内核只见单一进程的用户态模拟线程；旧实现要求全部文件描述符置为非阻塞并手工模拟阻塞语义，既无法利用多核又不可能百分之百正确。作者据当事人口述约在 2004 或 2006 年提交首批代码，启用后经过一个完整六个月开发周期除错，主要遗留问题是 CPU 时间统计与文件描述符表锁定。　[存疑脚注] 受访者本人对 rthreads 首批提交年份不确定（2004 或 2006），转写将提交者名转写为 TATU，通常应指 tedu（Ted Unangst），须以仓库提交记录核证（BSDTalk EP214，[2214.26-2427.73]，L1）
- BGPD 是第一个采用 PF 风格配置语言与内部消息传递框架的守护进程，其后 OpenNTPD、OpenSMTPD 等新写守护进程均沿用该框架，重复代码后来收拢为库；设计目标是使仅懂英语者读配置文件即可了解守护进程行为，与 sendmail 需要八百页专著的复杂性形成对照。OpenSMTPD 沿用 OpenBSD 特权分离模型，受访者判断 BSD 许可的邮件服务器在此之前长期缺位。（BSDTalk EP214，[2769.76-2909.16]，L1）
- OpenBSD 存储栈早期即决定不在硬件 RAID 控制器之上另建逻辑盘接口，而是在控制器之上加 SCSI 模拟层；此后业界反向跟进，硬件 RAID 控制器如今直接在逻辑盘上呈现 SCSI 接口，SCSI 由一种存储接口演化为通用协议。SATA 设备经 SAS ATA 翻译层归入同一路径，与 Linux 与 Solaris 的做法一致，仅旧式 PCI IDE 设备尚未迁移；项目目标是使一切硬件存储最终呈现为 SCSI 盘，SD 卡与 U 盘均已达成，遗留的只有老式并行 ATA 与个别旧架构直连盘驱动。（BSDTalk EP219，[423.04-551.28]，L1）
- SCSI 协议的长寿源于其结构简单与后向兼容：协议本质是命令帧加可选数据载荷，每版协议虽为新读写命令各立条目，但新版本包含对旧版的兼容支持，需要新特性时只是增设新消息。闪存以薄置备 SCSI 盘形式通告逻辑块与物理块无关，配合四千字节物理块对五百一十二字节逻辑块的通告，协议已足以支撑上层软件对存储特性的利用，其灵活性正是普遍性的原因。（BSDTalk EP219，[570.16-700.64]，L1）
- 存储性能的瓶颈已从设备数转向命令槽资源调度：二十年前的 SCSI 总线挂七台设备、每台一至两个命令槽，如今 SAS 与 RAID 控制器可管理一二八至五一二台设备、每台可有上千命令槽，而适配器自身槽位有限，如何调度这些槽位成为核心问题。受访者刻意淡化大内核锁问题的优先级，理由是处理器增速远超磁盘与适配器，宁可在锁上自旋也不可浪费命令槽；SCSI 中层细粒度锁虽已预先布置，其正确性须待整个内核脱离大锁才能验证。（BSDTalk EP219，[727.06-846.5]，L1）
- MCLGETI 的设计动因是巨型帧描述符环的内存压力：九千字节帧乘以五百一十二项描述符环会侵占内核本已有限的内存，在部分架构上内核仅能使用主机内存中的六七十兆；该机制默认仅为环填入两个槽位，按每个中断的实际用量渐进扩大分配，其后 Theo de Raadt 将其推广为背压机制，在系统耗尽处理器时间时限制递交给网卡的包量以归还算力。受访者自述其生产系统已放大其他拥塞限制，仅依赖 MCLGETI 承担过载保护。（BSDTalk EP219，[1002.74-1234.8]，L1）

**史料**：

- Hansteen 自述文档一侧的处境：新版《The Book of PF》因 FreeBSD 与 NetBSD 移植 4.7 等价代码的时间无从预料，索性完整收录新旧两套示例；现役版本中古老的 FTP proxy 示例被整体移除，而 FTP proxy 是一项“长期的挣扎”，已第三次从头实现；三大 BSD 的 PF 已严重分叉，FreeBSD 基线约为 4.1 加补丁。（BSDTalk EP192，[1077.74-1185.94]，L1）
- 作者本人完整口述 CARP 协议定名史：因 VRRP 受专利阻碍，OpenBSD 向 IANA 申请多播地址被拒，遂复用 VRRP 的多播地址与报头格式，使 CARP 报文自称为 VRRP 版本 3，从而永久占据该版本号；PFSYNC 申请协议号同样被 IANA 拒绝，该号码现被列为保留。此口述为研究 CARP 协议诞生时标准组织与专利环境作用的一手材料。（BSDTalk EP214，[1037.12-1131.48]，L1）
- 受访者自述 BGPD 过滤器引擎最初仅是线性匹配的工作原型而非最终设计，无法扩展至十万条路由级别：阿姆斯特丹 AMS-IX 互联网交换点实际在用，而法兰克福 DE-CIX 因约十万条路由的复杂过滤需求无法使用；重写过滤器引擎与过滤语言的计划因缺乏人力长期搁置。该自述同时记录了 BGP 会话 TCP MD5 保护在 OpenBSD 借由 IPsec 框架实现及 FreeBSD 侧跟进的线索。（BSDTalk EP214，[2925.0-3086.08]，L1）
- 受访者供职昆士兰大学工程建筑与信息技术学院并管理全院技术栈，构成大规模 PF 生产部署的一手数据：十三四栋楼各设员工、实验室与受管设备三类网络，连同隔离区合计约六十个网络；中央防火墙对仅三个物理接口，其上叠加六十个 VLAN 与 CARP 地址接口，接口总数过百，上游经 OSPF 取缺省路由，客户端侧以 CARP 通告缺省网关。接手时继承六台 FreeBSD IPF 防火墙、各载两千至一万六千条规则合计约四万条，整合至一对 OpenBSD 防火墙后借 PF 语言特性先降至四千五百条、再降至约两千三百行，规则文件以 vi 编辑并纳入 Subversion 版本控制。（BSDTalk EP219，[1317.78-1547.34]，L1）
- TFTPD 重写的一手缘由：学院实验室镜像原以单播方式逐台分发且镜像日益庞大，管理者须在学期初数周人工排队调度镜像服务器；改用 BitTorrent 后启动环境连带更换，TFTP 在此场景暴露可扩展性问题，促成 5.2 全新 TFTPD 与 5.3 TFTP 代理替换。受访者另证实 Debian 缺省收录 OpenBSD 的小型网络守护进程，其本人在 Debian 系统上也使用 OpenBSD 的 TFTP 守护进程，为 OpenBSD 用户态工具跨发行版扩散提供当事人证词。（BSDTalk EP219，[1657.2-1731.44]，L1）

**史观**：

- 总纲5 没有必然性，只有偶然性：match 规则今日被视为 PF 的根基，其诞生却是偶然的聚合：一个 2003 年起的个人执念多年无人附议，恰逢 NAT 改造的工程需要才获得实现契机，连实现者本人也未曾预料其根本性——数年前社区 consensus 还将其斥为无用的东西。技术共识的方向并不由先验论证决定。（BSDTalk EP192，[214.34-251.26]，L1）
- 总纲22 知识注定过时：文档作者随 4.7 双轨重写全部示例、FTP proxy 第三次从头再来、man page 因黏着性语义反复改写，共同印证围绕活跃系统的技术知识注定过时：写作者的劳动不是记录恒定之理，而是追赶形式不断重铸的表述。（BSDTalk EP192，[1136.42-1157.26]，L1）
- 总纲9 经验优先：PFSYNC 主主负载分担在技术上不可能真正高效：同步状态表使每条连接的工作量翻倍，防御手段唯有延迟并批量打包同步报文，而这又引入级联延迟；据此作者依据真实运维经验主张生产环境采用平淡的主备两节点配置，认为多节点增加的复杂性本身就在提高失败概率。可靠性来自尽量简单的工程判断，是对炫目特性优先的价值观反驳。（BSDTalk EP214，[1203.64-1429.22]，L1）
- 总纲4 分离聚合是永恒规律：三大 BSD 自 1995 年最后一次分叉后已各自独立开发逾十五年，但当事人观察认为 OpenBSD 与 FreeBSD 在用户视角下的差异小于共享同一代码基础的若干 Linux 发行版之间的差异；BSD 项目间的技术互取被视为理所当然而不必每两周重造轮子。分叉后的再聚合以技术共享而非代码合并的形式延续，呈现分离与聚合的循环结构。（BSDTalk EP214，[3225.86-3283.85]，L1）
- 总纲4 分离聚合是永恒规律：受访者以年龄与经验变化解释其向软件 RAID 的转移：设备与磁盘之间的抽象越少，栈的上层越容易做聪明的事；随着 Dynamo 论文及 Riak、Voldemort、Cassandra 等实现在应用层接管数据存活与冗余，磁盘层高可用降为次要关切。数据冗余职责由硬件 RAID 层向应用层转移，存储栈呈现逐层分离再聚合的演进结构。（BSDTalk EP219，[309.26-399.72]，L1）

**辨析**：

- 语义陷阱与保守策略并存：match 与 pass 在动作黏着性上不同，旧 PF 实现中许多动作不黏着本属设计缺陷，却不可更改——旧规则集仍会被加载，静默改变行为过于危险，man page 为此打磨良久；NAT 只能出向、RDR 只能入向的旧限制源于返回流量路由查找使用未改回的地址，4.7 以 pfctl 的简单检查阻止反向用法，Brauer 倾向未来移除检查并以文档说明后果，4.8 或许放开。（BSDTalk EP192，[805.32-1049.02]，L1）
- Apple 在 OS X 中维护自己的 PF 分支，受访者称 Apple 是 FreeBSD 代码的主要消费者之一，且 OS X 上存在相当数量手写 PF 配置的用户；Peter Hansteen 愿意为移植提供协助，而 Henning Brauer 对是否关心 Apple 分支态度冷淡。FreeBSD 是否会跟进新版 PF 在访谈中仅为推测与期望，未见任何一方的正式承诺，须以 FreeBSD 源码树与提交记录核证。　[存疑脚注] FreeBSD 跟进新版 PF 与 Apple PF 分支的维护细节均为访谈中口头推测，非正式路线陈述（BSDTalk EP214，[439.96-491.92]，L4）
- bioctl 统一管理硬件与软件 RAID 的设想在访谈中仍停留在意图层面：受访者坦言各厂商在术语、布局与物理盘到逻辑盘的抽象上差异过大，找出让接口易用的统一抽象尚无成案，只确立硬件 RAID 无非带磁盘的磁盘、应如 ifconfig 一般寻址的方向。该统一接口理想当时未兑现，考据 bioctl 能力边界时应以其后手册页与源码为准。　[存疑脚注] bioctl 统一抽象的实现进度在访谈时点为未完成设想，后续进展须以源码树核证（BSDTalk EP219，[235.76-309.26]，L1）
