# 191.4 OpenBSD 的 6 个月发布周期文化——OpenBSD 坚持 6 个月固定发布周期，是 BSD 世界中最严格的发布节奏，确保稳定性与可预测性

## 190.4.1 6 个月周期的工程实践

**要点**：OpenBSD 自 2.5（1999.5）起确立 6 个月固定发布周期（5 月与 11 月）——这一节奏从未改变；6 个月周期由 release manager 协调，包含开发期、特征冻结、hackathons、beta、release 流程；bsd_commits.db 显示 4.x 时期 release engineering 工作主要由 krw@（Kenneth R. Westerback，2005-2010 共 1202 条 commit，涵盖 install/disklabel/MAKEDEV 等 release 安装介质相关组件）与 espie@（Marc Espie（马克·埃斯皮），2005-2010 共 1984 条 commit，涵盖 ports infrastructure 与 release 打包）承担——原大纲称 “release engineering 团队包括 Steven Mestdagger、Marc Espie 等”，"Steven Mestdagger" 系误记，bsd_commits.db openbsd-src 仓库 245857 条 commit 中无任何匹配 "Mestdagger" 的作者记录 [考据完成：2026-07-28 Mestdagger 可能在 CVS 时期以不同用户名提交，但 bsd_commits.db 中无匹配记录；实际 4.x 时期 release engineering 工作以 krw@ 与 espie@ 为主]

  **OpenBSD 4.x 时期 release engineering 贡献者统计（2005-2010）**：

  | 贡献者 | commit 数 | 主要负责组件 |
  | --- | --- | --- |
  | espie@（Marc Espie） | 1984 | ports infrastructure、release 打包 |
  | krw@（Kenneth R. Westerback） | 1202 | install、disklabel、MAKEDEV |

**史料**：bsd_commits.db openbsd-src 仓库 krw@ 2005-2010 commit 统计（1202 条，含 install/disklabel/MAKEDEV）；espie@ 2005-2010 commit 统计（1984 条，含 ports/release）；OpenBSD Release Notes 与 release engineering 文档（<https://www.openbsd.org/faq/faq5.html>）；misc@、tech@ 邮件列表关于发布流程的讨论（<https://marc.info/?l=openbsd-misc>） ［A］

**史观**：总纲第 17 条——软件工程：6 个月发布周期作为形式化结构塑造了开发节奏与功能选择——时间规则（5 月与 11 月 release）作为不可变约束，使 OpenBSD 开发者须在 6 个月内完成特性开发与稳定化，未完成的特性推迟至下个周期，这一形式化结构使 release 日期可预测但限制了单周期内的重大架构重构

**辨析**：6 个月周期的具体起始时间以 OpenBSD 2.5（1999.5）与 2.6（1999.11）的 release 日期为锚点——二者间隔 6 个月，此后延续至今；release manager 的更替历史以 OpenBSD hackathons 记录与邮件列表公告为准——krw@ 与 espie@ 在 4.x 时期承担 release engineering 主要工作，deraadt@ 作为项目创始人保留最终决策权

**文献**：bsd_commits.db openbsd-src 仓库 krw@、espie@ commit；OpenBSD Release Notes [EB/OL]. <https://www.openbsd.org/plus.html>；OpenBSD release engineering FAQ [EB/OL]. <https://www.openbsd.org/faq/faq5.html> ［A］

## 190.4.2 与 FreeBSD/NetBSD 发布周期的比较

**要点**：FreeBSD 在 4.x 之前采用 “准备好就发布” 模式，5.x/6.x 时期改为大约 18 个月周期（4.11 至 5.0 间隔 31 个月，5.5 至 6.0 间隔 19 个月），后逐步缩短至约 2 年；NetBSD 周期更长且不规律——1.0 至 2.0 间隔 8 年（1994-2001）；OpenBSD 的 6 个月周期在 BSD 世界中独一无二——可预测性成为 OpenBSD 的标志性特征

**史料**：FreeBSD Release Notes 各版本间隔时间（<https://www.freebsd.org/releases/>）；NetBSD Release Notes 各版本间隔时间（<https://www.netbsd.org/releases/>）；OpenBSD Release Notes（<https://www.openbsd.org/plus.html>）；bsd_commits.db tags 表 freebsd-src release/4.11.0、release/5.0.0、release/6.0.0 tagger_date ［A］

**史观**：总纲第 5 条——组织结构塑造技术路径：发布周期作为组织结构塑造了不同 BSD 项目的开发节奏——FreeBSD 的 18 个月周期适配其大规模贡献者群体与复杂特性集成，NetDB 的不规律周期反映其资源限制，OpenBSD 的 6 个月周期适配其小团队与稳定性优先导向

**辨析**：FreeBSD/NetBSD 的发布周期以各自 Release Notes 与 bsd_commits.db tags 表的 tagger_date 交叉确认——bsd_commits.db tags 表含 freebsd-src 仓库的 release tag（如 release/9.0.0 tagger_date = 2012-01-02T18:59:55Z），可精确核查 FreeBSD release 日期；FreeBSD 周期缩短的具体时间点以 FreeBSD 9.0（2012.1）后的 release 间隔为准——9.0 至 10.0 间隔 25 个月，10.0 至 11.0 间隔 35 个月，未显著缩短

**文献**：FreeBSD Release Notes [EB/OL]. <https://www.freebsd.org/releases/>；NetBSD Release Notes [EB/OL]. <https://www.netbsd.org/releases/>；bsd_commits.db tags 表 freebsd-src release tag ［A］

## 190.4.3 6 个月周期对社区的效应

**要点**：6 个月固定周期让 OpenBSD 社区形成稳定的开发节奏——hackathons、特征冻结、beta 测试、release 派对都按节奏进行；可预测的发布日期让企业用户能规划升级周期；该周期也带来压力，开发者必须在 6 个月内完成所有合并，未完成的特性须推迟到下个周期

**史料**：OpenBSD hackathons 历史记录（<https://www.openbsd.org/hackathons.html>）；misc@、tech@ 邮件列表关于发布节奏的讨论（<https://marc.info/?l=openbsd-misc>）；OpenBSD release parties 记录 ［A］

**史观**：总纲第 23 条——社区治理：6 个月周期作为社区治理的核心规则塑造了 OpenBSD 开发者文化与协作节奏——这一规则使开发者形成 “6 个月冲刺” 的周期性工作模式，与 Linux 的持续集成模式形成差异

**辨析**：6 个月周期对开发者流失的影响以邮件列表与 hackathons 记录为准——部分前 committer 在邮件列表提及 burnout（如 brad@ 在 2008 年后活跃度下降，bsd_commits.db 显示 brad@ 2005-01-01 至 2008-12-15 共 2728 条 commit 后停止），但无系统性研究证实 6 个月周期是 burnout 的主因；企业用户对周期的实际依赖程度无权威统计 [考据完成：2026-07-28 OpenBSD 企业用户对 6 个月周期的依赖程度无公开调研]

**文献**：OpenBSD hackathons 记录 [EB/OL]. <https://www.openbsd.org/hackathons.html>；de Raadt 邮件列表发言 [EB/OL]. <https://marc.info/?l=openbsd-misc>；OpenBSD FAQ [EB/OL]. <https://www.openbsd.org/faq/> ［A］

## 190.4.4 发布记录与里程碑考据

**要点**：OpenBSD 4.x-5.x 时期 Release Notes 与 CVS commit log 是研究 6 个月周期工程实践的核心史料；release tags、release engineering 邮件、hackathons 报告共同构成考据链；OpenBSD 4.0 release 周期起点以 2006-09-17 steven commit e8d7e8373d3b "4.0-current" 为标识

**史料**：bsd_commits.db openbsd-src 仓库 commit e8d7e8373d3b（2006-09-17 steven "4.0-current"）；OpenBSD 4.x-5.x Release Notes（<https://www.openbsd.org/plus.html>）；CVS release tags；release engineering 邮件列表 ［A］

**史观**：总纲第 25 条——0 信任原则：Release Notes 的完整性须以 commit log 补充——plus.html 页面仅记录 “重要的和用户可见的变更”，部分内部代码重构（如 tedu@ 的 malloc 分配器拆分）在 Release Notes 中可能简化描述

**辨析**：Release Notes 的完整性以 plus.html 页面为准——该页面仅记录用户可见变更；release tags 与实际发布日期的差异以 OpenBSD 官方公告为准——OpenBSD 仓库无 git release tag，release 日期以 openbsd.org 公告为准
