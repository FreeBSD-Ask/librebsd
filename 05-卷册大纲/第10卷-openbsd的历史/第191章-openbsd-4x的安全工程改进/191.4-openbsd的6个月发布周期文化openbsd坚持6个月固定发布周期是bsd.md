# 191.4 OpenBSD 的 6 个月发布周期文化——OpenBSD 坚持 6 个月固定发布周期，是 BSD 世界中最严格的发布节奏，确保稳定性与可预测性

## 191.4.1 6 个月周期的工程实践

**要点**：OpenBSD 自 2.5（1999.5）起确立 6 个月固定发布周期（5 月与 11 月）——这一节奏从未改变；6 个月周期由 release manager 协调，包含开发期、特征冻结、hackathons、beta、release 流程；openbsd.duckdb 显示 4.x 时期 release engineering 工作主要由 krw@（Kenneth R. Westerback，2005-2010 共 1202 条 commit，涵盖 install/disklabel/MAKEDEV 等 release 安装介质相关组件）与 espie@（Marc Espie（马克·埃斯皮），2005-2010 共 1984 条 commit，涵盖 ports infrastructure 与 release 打包）承担——原大纲称 “release engineering 团队包括 Steven Mestdagger、Marc Espie 等”，“Steven Mestdagger” 系误记，openbsd.duckdb openbsd-src 仓库 245857 条 commit 中无任何匹配 “Mestdagger” 的作者记录 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

**史观**：总纲第 17 条——软件工程：6 个月发布周期作为形式化结构塑造了开发节奏与功能选择——时间规则（5 月与 11 月 release）作为不可变约束，使 OpenBSD 开发者须在 6 个月内完成特性开发与稳定化，未完成的特性推迟至下个周期，这一形式化结构使 release 日期可预测但限制了单周期内的重大架构重构

**辨析**：6 个月周期的具体起始时间以 OpenBSD 2.5（1999.5）与 2.6（1999.11）的 release 日期为锚点——二者间隔 6 个月，此后延续至今；release manager 的更替历史以 OpenBSD hackathons 记录与邮件列表公告为准——krw@ 与 espie@ 在 4.x 时期承担 release engineering 主要工作，deraadt@ 作为项目创始人保留最终决策权

## 191.4.2 与 FreeBSD/NetBSD 发布周期的比较

**要点**：FreeBSD 在 4.x 之前采用 “准备好就发布” 模式，5.x/6.x 时期改为大约 18 个月周期（4.11 至 5.0 间隔 31 个月，5.5 至 6.0 间隔 19 个月），后逐步缩短至约 2 年；NetBSD 周期更长且不规律——1.0 至 2.0 间隔 8 年（1994-2001）；OpenBSD 的 6 个月周期在 BSD 世界中独一无二——可预测性成为 OpenBSD 的标志性特征

**史料**：FreeBSD Release Notes 各版本间隔时间（<https://www.freebsd.org/releases/>）；NetBSD Release Notes 各版本间隔时间（<https://www.netbsd.org/releases/>）；OpenBSD Release Notes（<https://www.openbsd.org/plus.html>）；freebsd.duckdb tags 表 freebsd-src release/4.11.0、release/5.0.0、release/6.0.0 tagger_date ［A］

**史观**：总纲第 5 条——组织结构塑造技术路径：发布周期作为组织结构塑造了不同 BSD 项目的开发节奏——FreeBSD 的 18 个月周期适配其大规模贡献者群体与复杂特性集成，NetDB 的不规律周期反映其资源限制，OpenBSD 的 6 个月周期适配其小团队与稳定性优先导向

**辨析**：FreeBSD/NetBSD 的发布周期以各自 Release Notes 与 freebsd.duckdb tags 表的 tagger_date 交叉确认——freebsd.duckdb tags 表含 freebsd-src 仓库的 release tag（如 release/9.0.0 tagger_date = 2012-01-02T18:59:55Z），可精确核查 FreeBSD release 日期；FreeBSD 周期缩短的具体时间点以 FreeBSD 9.0（2012.1）后的 release 间隔为准——9.0 至 10.0 间隔 25 个月，10.0 至 11.0 间隔 35 个月，未显著缩短

**文献**：FreeBSD Release Notes [EB/OL]. <https://www.freebsd.org/releases/>；NetBSD Release Notes [EB/OL]. <https://www.netbsd.org/releases/>；freebsd.duckdb tags 表 freebsd-src release tag ［A］

## 191.4.3 6 个月周期对社区的效应

**要点**：6 个月固定周期让 OpenBSD 社区形成稳定的开发节奏——hackathons、特征冻结、beta 测试、release 派对都按节奏进行；可预测的发布日期让企业用户能规划升级周期；该周期也带来压力，开发者必须在 6 个月内完成所有合并，未完成的特性须推迟到下个周期

**史料**：OpenBSD hackathons 历史记录（<https://www.openbsd.org/hackathons.html>）；misc@、tech@ 邮件列表关于发布节奏的讨论（<https://marc.info/?laccopenbsd-misc>）；OpenBSD release parties 记录 ［A］

**史观**：总纲第 23 条——社区治理：6 个月周期作为社区治理的核心规则塑造了 OpenBSD 开发者文化与协作节奏——这一规则使开发者形成 “6 个月冲刺” 的周期性工作模式，与 Linux 的持续集成模式形成差异

**辨析**：6 个月周期对开发者流失的影响以邮件列表与 hackathons 记录为准——部分前 committer 在邮件列表提及 burnout（如 brad@ 在 2008 年后活跃度下降，openbsd.duckdb 显示 brad@ 2005-01-01 至 2008-12-15 共 2728 条 commit 后停止），但无系统性研究证实 6 个月周期是 burnout 的主因；企业用户对周期的实际依赖程度无权威统计 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

**文献**：OpenBSD hackathons 记录 [EB/OL]. <https://www.openbsd.org/hackathons.html>；de Raadt 邮件列表发言 [EB/OL]. <https://marc.info/?laccopenbsd-misc>；OpenBSD FAQ [EB/OL]. <https://www.openbsd.org/faq/> ［A］

- Balmer 在 OpenCon 之外的工作是组织 OpenBSD 开发者会议（hackathon）：属非公开、仅受邀的内部活动，且趋势是越办越小规模，如上年葡萄牙的 hackathon；此类活动公开可见度低。（BSDTalk EP133，[315.13-344.45]，L1）
- 规模与国际化：注册开放的首个周末已有来自 11 个国家的 28 人报名；上年参会者超过 130 人，甚至有来自黎巴嫩者；Balmer 感叹 BSD 社区已成长到足以支撑专门的国际会议。（BSDTalk EP133，[357.94-384.05]，L1）
- 受访者以约 40 人软件公司 IT 经理的身份口述其 OpenBSD 环境：约 12 台 OpenBSD 服务器分别承担防火墙、VPN 网关、DNS 与 DHCP、面向 Windows 与 Mac 用户的文件服务、Web 服务以及执行反垃圾与反病毒扫描的 MTA 等角色；他自 3.7 版入场，此后每个新版本发布后不久即升级，访谈时已全面运行 OpenBSD 4.0。（BSDTalk EP90，[79.08-172.24]，L1）
- 替换史：受访者入职时公司几乎全为 Linux；他选择熟悉的 OpenBSD 并获“只要能工作可装任何系统”的授权，替换过程对终端用户完全透明——升级在下班时间完成、用户所用应用毫无变化，Linux 上能用的在 OpenBSD 上同样可用且多出新功能（如此前不存在的反垃圾与反病毒能力）。服务层的运维选择与用户桌面层解耦，是其得以透明换血的结构前提。（BSDTalk EP90，[107.68-157.04]，L1）
- 受访者讲解冗余与网络架构：两台约 1GHz、512MB 内存的普通机器以 CARP 互为防火墙冗余——既有廉价硬件加 CARP 的组合胜过购置内置冗余的高价设备；总部网络划为 LAN（用户与内部服务器）、DMZ（Web 服务器与演示机）与开发网络（快速装机服务器）三区，防火墙决定区间流量。另有两台 sparc64 专作 MTA 并以 CARP 做故障转移，曾在一次机器故障中即插即换、无缝接管。（BSDTalk EP90，[181.56-235.5]，L1）
- 邮件栈：以 Sendmail 为 MTA、利用其 libmilter 功能自研过滤口，接入 ClamAV 与 SpamAssassin，再将邮件投递给内网 Exchange——Exchange 因此不直接暴露于互联网，垃圾与病毒在入口即被滤除；另有 spamd 以黑名单模式屏蔽特定来源。灰名单因新客户首次邮件会被延迟半小时的顾虑暂未获公司批准，他设想以已知客户白名单等变通方式证明其价值。（BSDTalk EP90，[245.48-320.0]，L1）
- 升级实践：每个 release 用 OpenBSD 安装介质的 upgrade 选项进行，以 mergemaster 合并 /etc 变更；版本之间则采用 Gerardo Santana 的二进制补丁系统——编译补丁、比对受影响的二进制与文件、打包升级。他自陈许多开发者不赞成此类方案，但从运维角度合理：同一服务器上多个服务共存时，httpd 获补丁后无需停摆其他服务、只须重启受影响者。jail 的取舍遵循同样权衡——静态 HTML 站点因须把 Perl 等依赖复制进沙箱反而不再使用 jail。（BSDTalk EP90，[711.7-770.18]，L1）

**史观**：

- 总纲20 历史地理塑造思想土壤：OpenCon 的地理组织——威尼斯会场、11 国乃至黎巴嫩的参会者流动——显示欧洲城市节点与会议空间如何承载并塑造 BSD 社区的交流形态，社区思想的生长与其地理聚点不可分。（BSDTalk EP133，[59.18-72.61]，L1）
- 总纲10 动手者创造历史：工程生产的核心场域在非公开的 hackathon 而非公开舞台：仅受邀、趋小规模、低公开可见度的开发者会议承载实际工作，而公开会议拒绝录像、强调亲临现场——可见的庆典之下，动手者的协作空间另有其处。（BSDTalk EP133，[304.13-344.45]，L1）
- 总纲10 动手者创造历史：这家公司的 BSD 基础设施由一两名动手运维者以退役硬件与免费软件建成：软件支出归零、硬件靠开发测试淘汰下来的机器，企业与 OpenBSD 项目的联结系于运维者个人的经验与信心。中小企业的开源采纳在微观层面由这类个体的劳动与判断推动，而非组织性的采购决策。（BSDTalk EP90，[410.74-435.5]，L1）
