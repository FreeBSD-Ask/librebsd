# 191.6 多元群体贡献：OpenBSD 4.x 时期的贡献者多样性——核心团队、基金会与全球志愿者

## 191.6.1 核心开发者与基金会治理的多元化

**要点**：OpenBSD 4.x 时期（2005-2010）延续小而精核心模式——Theo de Raadt（创始人，加拿大卡尔加里）主导方向（openbsd.duckdb 显示 deraadt@ 2005-2010 共 5416 条 commit），otto@（Otto Moerbeek（奥托·穆尔贝克），malloc 子系统维护，1020 条 commit）、henning@（Henning Brauer（亨宁·布劳尔），pf 与 ospfd 维护，1017 条 commit）、reyk@（Reyk Flöter，网络服务与 iked，1004 条 commit）等资深开发者负责关键子系统；2007 年 OpenBSD Foundation 在加拿大注册为非营利组织（详见 86.5），引入企业赞助与法律/资金支撑，使贡献者群体从 “纯志愿者” 扩展到 “基金会 + 企业 + 志愿者” 三元结构

**史料**：openbsd.duckdb openbsd-src 仓库 2005-2010 贡献者统计（deraadt 5416、jmc 3921、miod 3760、brad 2728、kettenis 2271、espie 1984、otto 1020、henning 1017、reyk 1004）；OpenBSD 4.x Release Notes；OpenBSD Foundation 2007 注册公告 ［A］

**史观**：专题——基金会治理与贡献者政治构成（不设总纲条号）：基金会的企业赞助结构改变了 OpenBSD 的贡献者政治构成——4.x 时期前 OpenBSD 资金主要来自个人捐赠与 hackathons 赞助，Foundation 成立后企业赞助（如 Google 编程之夏、Microsoft 等）的引入使贡献者群体从纯志愿者扩展至包含企业赞助参与者

**辨析**：Moerbeek、Brauer、Flöter 等核心开发者的具体隶属/国别以邮件列表自述与 hackathons 记录为准——本章仅确认其在 OpenBSD 提交中的主导角色，不推断国别或族裔；Foundation 赞助者名单的具体构成随年份变动，以 Foundation 年报为准

**文献**：openbsd.duckdb openbsd-src 仓库 2005-2010 贡献者统计；OpenBSD 4.x Release Notes [EB/OL]. <https://www.openbsd.org/plus.html>；OpenBSD Foundation 公告 [EB/OL]. <https://www.openbsdfoundation.org/> ［A］

**要点**：与 2.x 时期相同，4.x 时期的提交统一经 @openbsd.org 账号，openbsd.duckdb openbsd-src 仓库 contributors 数据无法直接以邮箱域识别国别/机构；openbsd.duckdb 显示 openbsd-src 仓库 2005-2010 年间活跃贡献者约 100 人以上，邮件列表与发布注记显示贡献者横跨欧洲、北美及其他地区

## 191.6.3 企业赞助与产业协作的多元贡献

**要点**：OpenBSD Foundation 引入企业赞助后，OpenBSD 的 “贡献者” 概念扩展到资金与法律层面；4.x 时期 OpenBSD 成果（pf 被 FreeBSD 移植、OpenSSH 被产业广泛采用）形成跨项目贡献闭环——openbsd.duckdb 显示 FreeBSD 于 2004-02-26 由 Max Laier commit 5c45a928b954 "Vendor import of OpenBSD's packet filter (pf) as of OpenBSD 3.4" 首次移植 pf；CARP、synproxy 等特性亦受益于网络运营商与安全公司的实际需求反馈；注意：LibreSSL 在 4.x 时期（2005-2010）尚未 fork（LibreSSL fork 于 2014 年 4 月 Heartbleed 后），4.x 时期的 TLS 库仍是 OpenSSL 集成

**史料**：freebsd.duckdb freebsd-src 仓库 commit 5c45a928b954（2004-02-26 Max Laier "Vendor import of OpenBSD's packet filter (pf) as of OpenBSD 3.4"）；openbsd.duckdb openbsd-src 仓库 LibreSSL 相关 commit 统计（2014 年前 0 条，验证 4.x 时期无 LibreSSL）；OpenBSD Foundation 赞助者名单（<https://www.openbsdfoundation.org/>） ［A］

**史观**：总纲第 13 条——法律与道德是利益分配：BSD 许可证使 OpenBSD 成果被产业自由采纳，放大多元群体贡献——pf 被 FreeBSD 移植、OpenSSH 被产业广泛采用，是 BSD 许可证 “允许 fork 不强制回馈” 特性的具体显现

**辨析**：“企业回馈” 的具体程度以 openbsd.duckdb commit 记录为准——部分赞助为资金而非代码，对代码库的直接贡献以 commit author_name 与 committer_email 维度核查；FreeBSD pf 移植始于 2004-02-26（5.3 周期），后续 pf 3.5（2004-06-16）、pf 3.7（2005-05-03）持续同步

**文献**：freebsd.duckdb freebsd-src 仓库 commit 5c45a928b954；OpenBSD Foundation 年报 [EB/OL]. <https://www.openbsdfoundation.org/>；cross-BSD 协调邮件列表 ［A］

**要点**：

- ACPI 的本质与 AML 机制：它是现代 PC 的大规模配置与电源接口，源自旧式即插即用规范的演进——厂商把以 AML 语言写就的代码编译成字节码置入内存，操作系统须在电源键按下、合盖、热区过热等事件发生时执行相应片段；早期实现集中于挂起恢复，如今扩展到热管理、PCI 自动配置、设备枚举、嵌入式控制器、背光与时钟，规范随每个版本增厚数百页、已逾七百页。（BSDTalk EP195，[241.76-326.76]，L1）
- AML 解析器呈三足格局：其余 BSD 采用 Intel 参考实现，另一家是微软，第三家即 OpenBSD 自研解析器（由 Marco Peereboom、Jordan Hargrave 等人写成）；OpenBSD 实现仅数个文件、极为轻量，立场是不依附厂商实现——Intel 实现并无具体缺陷，只是庞大且会迫使项目跟随其取舍。　[存疑脚注] 转写将 Jordan Hargrave 仅呈为 Jordan，i386、amd64 分别误作 I-286、AIMB64，均依语境辨正，建议核对原始音频。（BSDTalk EP195，[371.64-433.34]，L1）
- 挂起恢复的工程结构：合盖动作的策略代码被故意禁用，唤醒须以睡眠键或 zzz 命令并运行 APMD；2009 年 Edmonton 与其后 Coimbra 两次 hackathon 先行铺设胶水层，使各设备驱动的作者得以编写自己的挂起恢复钩子——没有驱动层的关断与重编程，宣称支持挂起恢复只是空话；工作优先磁盘、网络与屏幕，Intel 与 ATI 视频芯片表现尚可，Nvidia 则因开发者少有该硬件而无人修复。　[存疑脚注] 转写将 ATI 误作 EKI，依语境辨正，建议核对原始音频。（BSDTalk EP195，[593.42-735.22]，L1）
- 测试报告文化：邮件列表用户两分——认真测试者与只喊坏了帮我修者；有效报告须附 ACPI dump（机器 AML 的快照，曾据此修复数台机器）、dmesg 与硬件信息，缺乏信息的报告会被忽略，PCI 与 USB 转储亦有价值；部分机器仅凭 AML 无法推演，必须实物上手，社区遂以捐款购置 HP 笔记本专供热区与 AML 方法调试。（BSDTalk EP195，[825.76-930.00]，L1）[订正：原 [825.76-939.04]，2026-09-30 SenseAudio 重转核对]
- 下一步是 ACPI S4：睡眠级别中 S0 为全功率运行，S1、S2 为低功耗模式，S3 关闭 CPU 而保持内存，S4 为挂起到盘即休眠；S4 更复杂，需在初始引导环境中从磁盘读回内存页并要求更多设备支持，但方案已有腹稿；这将使 OpenBSD 拥有其他 BSD 尚不具备的能力，当事人期待实现会传播到其他 BSD 阵营。（BSDTalk EP195，[945.04-1012.76]，L1）
- 受访者自述 hoststated（Host State Demon）源于一个快速的临时实现：OpenBSD 当时没有任何监控主机状态并把存活主机放入 PF 表的工具，他写了一个执行 TCP 连接检查、将存活主机置于 PF 表中、使重定向规则永不指向宕机主机的程序。与 round-robin DNS 相比，DNS 负载均衡无从得知主机死活、依赖客户端自行切换到下一主机（多数浏览器会如此、并非全部）；hoststated 则借 PF 的三层目的地址重写对客户端完全透明。典型部署为服务器池置于负载均衡器之后，DNS 将连接指向均衡器，PF 以 RDR 规则把连接分发到池内机器。（BSDTalk EP97，[62.86-198.28]，L1）
- hoststated 实为围绕 PF 的包装器，以非阻塞方式检查主机响应是否足够快；他仿照 OSPFD 实现了配套的 hoststated ctl，管理员可借此查看在线主机、并在维护或升级时禁用某台。检查方法包括 ICMP（对 IPv6 主机用 ping6）、TCP 连接检查、HTTP 检查（校验指定 URL 的返回码与页面内容的 SHA1 摘要），以及通用的 send/expect 方法——向连接发送一段数据并期待特定回应（如 SMTP banner 可只期待不发送），初以正则实现后改用 fnmatch；SSL 代码可用，所有 TCP 类检查方法均可包裹于 SSL。（BSDTalk EP97，[198.28-365.8]，L1）
- 关于演进方向：按服务器负载加权的均衡是计划中的目标——但加权所需的代码在内核中与 PF 绑定，须在 PF 侧实现方可让某些主机被查询得更少；团队的长期目标是功能完整的负载均衡器。初始可用版本的目标已然达成，他希望 hoststated 能赶在 4.1 之前链入 build（否则将于 4.1 打标签后的早期 snapshot 提供）。测试环境为笔记本电脑加上家与单位各一组负载均衡测试机器，另有一台由他自管、带真实均衡器与专用主机的准生产部署用于大改动验证，并尽量实现每种场景以测试回归。（BSDTalk EP97，[365.8-498.68]，L1）
- 受访者澄清负载均衡的一个常见误解：PF 式的基本负载均衡只重写目的地址、不重写源地址，因此 Web 服务器日志中记录的是真实的客户端信息，站点统计仍然准确；只有当均衡器与 Web 主机不在同一网段时才须同时重写源地址——此场景下若无七层负载均衡介入则丢失客户端信息（服务器只见来自均衡器的连接），做七层时通常附加 X-Forwarded 头。多数部署不采用该场景，源地址得以保留。（BSDTalk EP97，[517.96-600.4]，L1）
- 与 CARP 冗余防火墙的配合及可移植性：两台防火墙各自运行 hoststated、分别维护 PF 表，CARP 切换时备份机上的表处于良好状态；代价是须在 CARP 设备与底层接口上共预留三个 IP、双机都要运行，略显过度。hoststated ctl 暂只支持本地连接。依赖方面只要操作系统支持 PF 与 C 库即可——有人尝试在 FreeBSD 上编译且据称顺利（需要 3.5 之后版本的 PF ioctl 及 strlcpy 等函数），虽此后未再收到回音，据他所见可以运行。（BSDTalk EP97，[600.4-716.24]，L1）
