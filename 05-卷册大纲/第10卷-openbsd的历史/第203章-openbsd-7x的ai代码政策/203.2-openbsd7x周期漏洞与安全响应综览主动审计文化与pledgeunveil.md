# 203.2 OpenBSD 7.x 周期漏洞与安全响应综览——主动审计文化与 pledge/unveil 加固机制的成熟

## 203.2.1 7.x 周期安全态势总览——errata 存档缺失与 commit 数据的反差

**要点**：OpenBSD 7.x 周期（**2021 年 10 月 14 日** 7.0 发布至 **2026 年 7 月 22 日**）openbsd-src 仓库共出现 **60 条 CVE 相关 commit** 与 **10 条无 CVE 编号的安全修复 commit**，对应 **88 个去重 CVE**；CVSS v3.x 评分分布为 0 个 Critical、3 个 High（CVE-2024-1931、CVE-2024-7594、CVE-2024-8176，均为 7.5）、1 个 Medium（CVE-2024-8508，5.3）、84 个无评分——无评分比例高达 95.5%，远超 FreeBSD 14.x 周期的 91.6%，反映 OpenBSD commit message 较少显式引用 CVE 编号的工程习惯；**关键考据发现**：本地 errata 存档 `原材料/研究/bsd漏洞史/官方公告/openbsd-errata.md` 中 OpenBSD 7.0-7.9 全部 10 个版本均显示 “errata 条目数：0”，与 60 条 CVE commit 数据形成强烈反差——这一反差不代表 7.x 周期无漏洞修复，而是反映本地 errata 抓取工作流在 7.x 系列失效 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］；OpenBSD 不发布 FreeBSD 式的 Security Advisory（SA），而通过 errata patches 与 CVS commit 直接发布修复，这是 OpenBSD 与 FreeBSD 安全发布机制的根本差异
  **OpenBSD 7.x 周期 CVE 与 errata 统计**：

**史观**：总纲第 25 条——0 信任原则：7.x 周期 errata 存档缺失是 0 信任原则在数据驱动考据中的典型样本——本地 errata 存档显示 “0 条目” 不等于 “OpenBSD 7.x 无漏洞修复”，commit 数据已证明 60 条 CVE commit 的存在；任何单一数据源（无论是 errata 存档、commit 数据库还是 cvelistV5）都不能单独作为安全态势的判据，须多源交叉验证；OpenBSD 在 cvelistV5 中元数据较少（84 个 CVE 无 CVSS 评分），更须以本地 commit 存档为主、数据库为辅，这与 FreeBSD 14.x 周期以 SA 公告为主、数据库为辅的考据路径形成对照

**辨析**：**须严格区分** 三种数据源的可信度层级：① openbsd-src 仓库 commit 是最可信的一手史料（代码变更的直接记录）；② OpenBSD 官方 errata 页面是二一手史料（经发布的修复公告），但本地抓取存档可能失效；③ cvelistV5 元数据是三手史料（CVE 编号分配机构的记录），OpenBSD commit 不引用 CVE 编号时 cvelistV5 与 commit 的对应关系须人工建立；**与 FreeBSD 14.x 周期对比**：FreeBSD 14.x 周期发布 80 个 SA，OpenBSD 7.x 周期无 SA 仅有 errata patches 与 commit——这一差异不意味着 OpenBSD 安全态势更好或更差，而是两个项目安全发布机制的根本不同（FreeBSD 集中式 SA 披露 vs OpenBSD 分散式 errata + commit）；**CVSS 评分缺失的辨析**：84 个 CVE 无 CVSS 评分不代表这些漏洞不严重，而是 OpenBSD 修复时未同步上游 CVSS 评估，libexpat 系列 CVE 多数在上游有评分但本地未录入

## 203.2.2 libexpat 批量同步与第三方库治理——“跟随上游—批量回溯” 工作流

**辨析**：**须精确说明 libexpat 在 OpenBSD base 中的角色**：libexpat 是 XML 解析库，被 OpenBSD base 中多个组件（如 **httpd(8)**、pkg_add 等）依赖，但 libexpat 本身是上游独立项目（由 Google 维护）；OpenBSD 不 fork libexpat（与 LibreSSL 不同），而是直接 vendor import 上游版本；**2026 年 6 月 27 日一次修复 13 个 CVE** 的 commit `82efd71b9bc2`（libexpat 2.8.2）是 7.x 周期单次 commit 修复 CVE 数量最多的一次，涉及 CVE-2026-50219、CVE-2026-56131、CVE-2026-56132、CVE-2026-56403 至 CVE-2026-56412 等——这些 CVE 编号在 cvelistV5 中多数无 CVSS 评分，但 libexpat 上游已确认修复；**与 LibreSSL 路径的对比**：libexpat 是 “跟随上游”（vendor import），LibreSSL 是 “独立 fork”（自主维护），两者代表 OpenBSD 对第三方库的两种不同治理策略

## 203.2.3 unbound、smtpd 与 OpenSSH 漏洞——OpenBSD 网络服务攻击面演进

**要点**：7.x 周期 OpenBSD 网络服务相关 CVE 集中于三个组件——unbound DNS resolver（CVE-2024-1931 CVSS 7.5 High、CVE-2024-8508 CVSS 5.3 Medium、CVE-2025-11411）、**smtpd(8)** 邮件服务（CVE-2025-62875）、OpenSSH（CVE-2024-7594 CVSS 7.5 High）；unbound 漏洞由 sthen 与 florian 通过同步上游补丁修复，CVE-2025-11411 的修复过程呈现 “不完整缓解 → 后续完整修复” 的迭代——**2025 年 10 月 22 日** sthen 提交 `a37023f05c72` 应用上游 commit 缓解，**2025 年 11 月 27 日** sthen 再提交 `b89c80c7e695` 补完不完整的缓解，反映 OpenBSD 对漏洞修复的后续验证机制；**smtpd(8)** CVE-2025-62875 由 gilles 于 **2025 年 10 月 30 日** 修复（commit `2b660d1f723c`），漏洞机制为 malformed imsg 导致 **smtpd(8)** 进程 die——这是 OpenBSD 自研邮件服务的安全债务显现；**OpenSSH CVE-2024-7594**（Vault SSH secrets engine valid_principals 问题）由 djm 于 **2025 年 12 月 22 日** 修复（commit `f0c5ff0ccd2e`），CVE 编号年份（2024）与修复年份（2025）的差异反映 CVE 分配与修复的时序脱节 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

**史观**：总纲第 17 条——软件工程：unbound/smtpd/OpenSSH 三个网络服务的漏洞分布反映 OpenBSD 网络服务攻击面的结构——OpenSSH 与 unbound 是 OpenBSD 对外暴露的核心服务（**sshd(8)** 默认监听 22 端口、unbound 作为 caching resolver 常部署于网关），其漏洞直接影响系统边界安全；**smtpd(8)** 是 OpenBSD 自研的邮件服务（区别于历史上的 sendmail/postfix），其漏洞体现 “自研服务的安全维护负担”——自研减少了第三方代码依赖但增加了自行维护的安全责任；CVE-2025-11411 的 “不完整缓解 → 补完” 迭代体现 OpenBSD 的 “快速修复—后续验证—加固重构” 循环——修复不是一次性事件而是持续验证过程

**辨析**：**须严格区分** unbound 的两种修复路径：① 同步上游补丁（如 CVE-2024-1931 的 `apply https://nlnetlabs.nl/downloads/unbound/patch_CVE-2024-1931.diff`）；② OpenBSD 自行编写修复（如 CVE-2025-11411 的 `add upstream's commit to fix` 后继以 `Sync to unbound`）；前者是被动跟随上游，后者是 OpenBSD 主动同步未正式发布的上游修复；**regreSSHion（CVE-2024-6387）的考据**：CVE-2024-6387 是 OpenSSH 上游的预认证 RCE 漏洞（FreeBSD 14.x 周期通过 SA-24:04.openssh 修复），但 openbsd-src 仓库 7.x 周期 commit 中未发现显式引用 CVE-2024-6387 的修复 commit ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］；**smtpd(8)** 的安全史：**smtpd(8)** 是 OpenBSD 5.x 周期引入的自研邮件服务（替代 sendmail），其历史 CVE 较少但 7.x 周期出现的 CVE-2025-62875（malformed imsg 导致 die）表明自研服务并非免疫漏洞

## 203.2.5 pledge/unveil 在漏洞响应中的扩展——“主动审计—快速修复—加固重构” 循环

**要点**：7.x 周期 pledge/unveil 机制从 “新特性引入” 阶段进入 “成熟部署与漏洞响应工具” 阶段——7.1（**2022 年 4 月**）将 unveil 设为默认、引入 **malloc.c** 随机化，7.3（**2023 年 4 月**）引入 malloc 自检与 unveil 改进，7.6（**2024 年 10 月**）引入 unveil 路径规范化；这些改进不仅是功能增强，更是 OpenBSD “主动审计—快速修复—加固重构” 循环中 “加固重构” 环节的具体体现——发现漏洞后不仅修复单个 bug，还通过扩展 pledge/unveil 限制范围来缓解同类漏洞的潜在影响；7.x 周期 base 系统中 pledge/unveil 覆盖率持续扩展，新漏洞往往通过扩展 pledge/unveil 限制范围来缓解而非仅修补 bug；这一模式与 FreeBSD 14.x 周期以 SA 修补 bug 为主的模式形成根本对比——OpenBSD 倾向 “修复 + 加固” 双轨，FreeBSD 倾向 “修复” 单轨
