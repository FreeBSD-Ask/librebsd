# 213.3 安全审计文化考据与专业批评——Ballista 合作、代码审计方法论与学术界安全评估

**要点**：OpenBSD 的安全审计文化起源于项目创建后不久——de Raadt 被一家名为 Secure Networks, Inc.（SNI）的本地安全软件公司联系。SNI 正在开发名为“Ballista”的网络安全审计工具（后更名为 Cybercop Scanner，因 SNI 被 Network Associates 收购）。这一合作关系对 OpenBSD 早期安全审计起到了催化作用——SNI 使用 Ballista 对 OpenBSD 进行漏洞扫描与渗透测试，发现的漏洞反馈给 OpenBSD 开发者修补；OpenBSD 开发者则通过“做正确、恰当、安全的事”来回应 SNI 的发现。这种“攻击-修复”循环在 OpenBSD 2.3 发布前达到高峰（约 1997-1998 年），奠定了项目“安全优先”的工程文化。
随着 OpenBSD 的安全性提高，SNI 发现“漏洞越来越难找到和利用，以至于不再具有成本效益”，双方的合作逐渐终止。但审计文化的惯性已经形成——OpenBSD 开发者 Marc Espie（马克·埃斯皮） 将代码审计描述为“从未完成……更像是一个持续的过程而非针对特定 bug 的狩猎”。他列举了发现 bug 后的典型步骤：检查整个源代码树中的相同和类似问题、判断文档是否需要修订、调查“是否可能增强编译器以警告此特定问题”。
2017-2019 年学术界的安全评估为该文化提供了最有分量的外部检验：（1）2017 年 IOActive 的 Ilja van Sprundel 在 DEF CON 与 34C3 发表的“Are all BSDs created equally?”指出“尽管 OpenBSD 在安全性方面明显赢过其他 BSD，但‘在内核中找到 bug 仍然很容易’”——这意味着安全审计文化虽优于同级系统，但离“无 bug”的理想仍有差距；（2）2019 年匿名研究者“Stein”在 36C3 的演讲“A systematic evaluation of OpenBSD's mitigations”指出 OpenBSD 的缓解措施“基于纯粹的运气和迷信”并呼吁更理性的设计方法——这是对 OpenBSD 安全叙事最直接的外部学术挑战。

**史观**：总纲第 9 条“经验优先”与总纲第 11 条“自反性”——OpenBSD 的安全审计方法论是“经验优先”的极致实践：通过逐行审计每一行代码、使用安全 API 替换不安全的函数、部署 W^X 内存保护、引入 pledge/unveil 沙箱——每一步都是工程经验的产物而非安全理论的推演。但“Stein”的 2019 年批评恰是总纲第 11 条“自反性”所要求的：OpenBSD 的安全成就须被承认，但其安全叙事的“神圣化”（“世界上最安全的操作系统”）同样须被检验——安全不是绝对状态而是持续实践，任何缓解措施的安全效果都须接受实证检验而非基于信仰。

①概念与早期实践（1980s）：1984 年 GNU 计划启动；1985 年《GNU 宣言》定反专有化原则，FSF 成立；GNU 组件先以程序专属 copyleft 许可发布。②GPL v1（1989）：与律师 Jerry Cohen 把各许可整合为统一 GNU GPL，禁止只发二进制、禁止附加限制条款，实现强 copyleft。③GPL v2（1991-06）：新增第 7 节应对软件专利；同年发布 LGPL 弱 copyleft；1991 年 Linux 内核以 GPL 发布，促成 GNU/Linux。④GPL v3（2007-06-29）：经历两年公开讨论，回应 tivo 化、DRM、微软—Novell 专利协议。与 BSD 对比：BSD 系为 permissive 许可，仅要求保留版权声明与免责声明，不要求衍生作品同许可，可并入专有软件；copyleft 则要求衍生作品以相同条款再分发。
