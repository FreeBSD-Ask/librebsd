# 140.5 5.x 网络栈性能倒退——SMPng 过渡期间网络子系统的锁竞争导致网络性能显著下降，直到 6.0 才开始重大网络栈性能增强

## 140.5.1 SMPng 过渡期间网络子系统锁竞争的技术分析

**要点**：SMPng（SMP Next Generation）项目于 2000-2002 年间设计与实现（本文件所引 SMPng 论文即 2001 年），FreeBSD 5.0（2003 年 1 月）为首个搭载该架构的版本，目标是将 FreeBSD 内核从传统的单 Giant 锁模型迁移到细粒度锁 SMP 架构；Giant 锁是一个全局内核互斥锁，早期 FreeBSD SMP 支持中所有内核操作都持有 Giant，导致多 CPU 时性能严重下降；网络子系统 SMP 化的核心挑战在于：① **mbuf(9)** 分配器需要 per-CPU 缓存；② 协议控制块（inpcb）需要独立锁而非全局锁；③ 网络接口输入/输出路径需要减少锁竞争；FreeBSD 5.x 采用了 “先粗粒度拆分，后逐步优化” 的策略——5.0-5.5 期间网络栈虽然引入了部分细粒度锁，但关键路径仍依赖 Giant 或存在严重锁竞争，导致在多 CPU 系统上网络性能相比 FreeBSD 4.x 出现显著倒退（部分测试显示倒退 30-50% 甚至更多）

**史料**：FreeBSD SMPng 项目文档（freebsd.org/smp）；McKusick, Neville-Neil, Watson 2014 第 4 章 SMP 架构章节；FreeBSD 5.x Release Notes SMP 章节；Andre Oppermann 网络栈锁优化的邮件列表帖子（2004-2006）；FreeBSD 内核锁定文档（locking(9) 手册页） ［A］
    FreeBSD 社区论文：[FP-2013-004] How SMPng Works and Why It Doesn't Work The Way You Think（John Baldwin（约翰·鲍德温），2013）<https://papers.freebsd.org/2013/baldwin-nycbug_smpng/>

**史观**：专题语（不设总纲条号）：SMPng 期间的性能倒退是 “架构迁移成本” 的教科书案例——从单 Giant 锁到细粒度锁不可能一步完成，必须经历一个 “锁拆分但优化尚未到位” 的中间状态，这个状态的性能必然不如旧架构；FreeBSD 核心团队选择在 5.x 系列承受性能倒退以换取架构现代化，这是一个有争议但有远见的工程决策

**辨析**：“FreeBSD 5.x 完全不能用” 是夸张说法——FreeBSD 5.x 在单 CPU 系统上性能与 4.x 接近，倒退主要发生在多 CPU 系统和高网络负载场景；锁竞争的主要来源：① 路由表锁（radix 锁）竞争；②inpcb（协议控制块）全局锁竞争；③ 网络接口 TX/RX 路径锁；Andre Oppermann 在 FreeBSD 6 周期的优化主要针对这些热点；部分网络文章称 “FreeBSD 5 网络慢得 unusable”，这是相对于 FreeBSD 4 和 Linux 2.6 的比较级说法，不是绝对不可用

(2014). *The Design and Implementation of the FreeBSD Operating System* (2nd ed.), Chapter 4; Oppermann, A. (2004-2006). *Network Stack Locking and Performance Posts*. freebsd-net@; FreeBSD Project. (2003-01). *FreeBSD 5.0 Release Notes* (SMPng section). ［A］

## 140.5.2 性能倒退对用户与部署的效应

**要点**：FreeBSD 5.x 网络性能倒退对用户群体产生了显著影响：① 许多 FreeBSD 4.x 生产用户拒绝升级到 5.x，继续停留在 4.x 系列直到 6.x 发布；② 防火墙/路由器用户（高度依赖网络性能）受影响最大，pfSense 等防火墙项目在 FreeBSD 5 时代曾面临是否升级的困境；③ 社区对 FreeBSD 项目产生了质疑——部分用户和开发者认为 5.x 在网络性能未就绪时不应标记为 STABLE；④ 这一事件直接导致 FreeBSD 发布工程团队调整发布策略——FreeBSD 6 开始更强调性能回归测试，且引入了 “one release for features, next for stabilization” 的模式

**史料**：FreeBSD 邮件列表 2003-2005 年关于 5.x 性能的讨论；BSD Magazine 和 Daemon News 当时的文章；pfSense 项目历史（FreeBSD 版本选择）；FreeBSD Core Team 关于 5.x 状态的声明 ［A］

**史观**：总纲第 8 条——本体论上各方平等：SMPng 性能倒退事件是 FreeBSD 社区治理的一次压力测试——核心团队必须在 “推动架构现代化” 和 “满足生产用户期望” 之间找到平衡；社区通过公开邮件列表辩论、Release Notes 诚实说明、后续版本快速修复等方式化解了危机，体现了开源社区的自我纠错能力

**辨析**：FreeBSD 5.x 是否应该被标记为 STABLE——FreeBSD 的 STABLE 分支含义是 “API/ABI 稳定，适合开发者跟进” 而非 “生产环境推荐”，但许多用户误解 STABLE 为 “生产稳定”；这一误解在 5.x 时代加剧了用户不满；生产环境实际推荐版本在 5.x 时代是 4.x，直到 6.0/6.1 发布才推荐 6.x；“FreeBSD 因此流失了大量用户给 Linux”——这一说法难以量化，但确实有部分用户从 FreeBSD 转向 Linux 2.6，2003-2006 年也是 Linux 在服务器市场快速增长的时期

**文献**：FreeBSD Stable Mailing List. (2003-2005). *FreeBSD 5.x Performance Discussion Threads*. freebsd.org; Lucas, M. W. (2007). *Absolute FreeBSD* (2nd ed.) (5.x transition chapter). No Starch Press; pfSense Project. (2004-2006). *Version History*. pfsense.org; FreeBSD Core Team. (2005). *FreeBSD 5.x Status Statement*. freebsd.org. ［A］

## 140.5.3 6.0 网络栈性能增强的修复路径

**要点**：FreeBSD 6.0（2005 年 11 月）引入了 Andre Oppermann 领导的重大网络栈重写和性能优化，核心改进包括：① 重写 TCP/IP 协议输入路径，减少锁竞争；② 引入 per-CPU 路由缓存，缓解 radix 锁竞争；③ 优化 mbuf 分配器，引入 UMA（Universal Memory Allocator）mbuf zone；④ 改进网络接口发送/接收路径的锁模型；⑤ 引入 TCP syncache 重写，提升 SYN flood 抵抗能力和性能；FreeBSD 6.x 系列（6.0、6.1、6.2、6.3）持续优化网络栈，到 FreeBSD 7.0（2008 年）时网络栈不仅恢复了 4.x 水平，而且在多 CPU 系统上实现了真正的 SMP 性能扩展；FreeBSD 7.0 还引入了 libpcap/bsd 改进的零拷贝 BPF（Berkeley Packet Filter）和 SCTP 支持

**史料**：FreeBSD 6.0/7.0 Release Notes 网络性能章节；Oppermann, A. 2005 年网络栈重写 commit；FreeBSD 网络性能测试对比（2005-2008）；McKusick 第二版书籍网络章节 ［A］

**史观**：总纲第 9 条——经验优先：6.0 的性能修复不是基于理论推导，而是基于生产环境测量——Oppermann 和其他开发者使用性能计数器与 KTR 内核跟踪等当时可用的测量手段分析锁竞争热点，逐个修复（DTrace 移植至 FreeBSD 系 2006-2007 年的 6.2/7.0 时期，晚于 6.0 的主要优化工作）；这是 “测量优先、优化有据” 的工程范例

**辨析**：FreeBSD 6.0 是否完全解决了性能问题——6.0 显著改善了性能但仍有优化空间，6.1/6.2/6.3 和 7.0 持续改进；到 FreeBSD 7.0 多 CPU 网络性能才真正超越 4.x；Oppermann 是否是 “唯一的功臣”——不，网络栈 SMP 化是多人贡献，包括 罗伯特·N. M. 沃森（Robert Watson）、Jonathan Lemon、Gleb Smirnoff 等人，Oppermann 是 6.x 周期网络优化的核心协调者；syncache 重写解决了什么问题——旧的 SYN 缓存实现有锁竞争和 DoS 漏洞，新 syncache 是 per-CPU 设计，性能和安全性都大幅提升

**文献**：FreeBSD Project. (2005-11). *FreeBSD 6.0 Release Notes* (Network Performance section). freebsd.org; Oppermann, A. (2005). *TCP/IP Stack Rewrite Commits*. svn.freebsd.org; FreeBSD Project. (2008-02). *FreeBSD 7.0 Release Notes* (Networking section). freebsd.org; Lemon, J. (2001-2006). *Per-CPU Network Optimizations*. freebsd-net. ［A］

## 140.5.4 性能倒退事件的史料辨析

**要点**：SMPng 性能倒退事件的一手史料包括：FreeBSD SMPng 项目页面（2000-2006）、freebsd-current/freebsd-net/freebsd-stable 邮件列表档案、各版本 Release Notes、内核源码的锁定注释、Andre Oppermann 等人的 commit 日志；二手史料包括 Michael Lucas 的《Absolute FreeBSD》对 5.x 时代的描述、BSDCan 演讲；一个重要的历史背景：FreeBSD 5.x 不仅网络栈在 SMP 化，调度器、文件系统、VM 子系统都在经历 Giant 锁拆分——网络栈的性能倒退是整个内核 SMP 化阵痛的一部分，不是网络子系统的孤立问题。SMPng 网络栈性能倒退与恢复的关键节点汇总见下表。

| 时间 | FreeBSD 版本 | 关键事件 | 性能影响 |
| --- | --- | --- | --- |
| 2003.01 | FreeBSD 5.0-RELEASE | 5.x 系列首次搭载 SMPng（项目 2000-2002 年间启动），网络栈开始细粒度锁化 | 单 CPU 接近 4.x；多 CPU 高网络负载下倒退 30-50% 或更多 |
| 2003-2005 | FreeBSD 5.1-5.5 | 部分细粒度锁引入，但关键路径仍依赖 Giant 或存在严重锁竞争 | 多 CPU 网络性能持续倒退；许多 4.x 生产用户拒绝升级 |

**史料**：FreeBSD SMPng 项目文档（web.archive.org 存档）；FreeBSD 邮件列表 2002-2006 完整档案；Oppermann 网络优化 commit 历史；Lucas 2007《Absolute FreeBSD》 ［A］

**史观**：总纲第 2 条——历史是形式主义化的非存在：SMPng 阵痛是 “形式化过程必须经历不完美” 的体现——从单锁到细粒度锁是架构形式化的必然步骤，但这个步骤本身会暂时降低系统性能；历史书写必须避免 “后见之明”，不能因为最终成功就否定阵痛时期的困难

**辨析**：性能倒退百分比的准确数字——不同硬件配置、不同工作负载下倒退幅度差异巨大，单 CPU 几乎无倒退，4 路 SMP 高网络负载下可能倒退 50% 以上，网上常说的 “50% 倒退” 是特定测试场景数字，不是普遍情况；“FreeBSD 5.0 是失败的版本”——从工程角度看 5.0 是技术预览版，向 SMP 架构迁移的必要步骤，但项目在版本命名和用户预期管理上存在不足；FreeBSD 5.x 持续了约 3 年（2003-2006），5.5 是 5.x 系列最后也是最稳定的版本

- turnstile 被称为整套锁机制得以运转的枢纽数据结构：由于一个线程同一时刻只能阻塞在一处，系统按线程而非按锁分配 turnstile（锁数量远多于线程数，每个进程表项自带数把互斥），阻塞线程把自身 turnstile 交给内核挂入等待链，锁释放时以回收的 turnstile 转交新持有者，从而以最小内存代价支撑优先级传播。（YouTube EPUfiTV9QWhM4，[1318.03-1456.32]，L1）
- 优先级反转的解法是递归优先级传播：高优先级线程发现持锁者未在运行时让出处理器并把自身优先级授予对方，直至其释放锁后优先级“逐层冒泡”归还；演讲以柏林开往华沙的特快列车令沿线十四列普通客车停驶待行为喻。与之相对，睡眠队列类锁不做优先级传播，因为唤醒等待磁盘 IO 的进程并不能让 IO 更快完成。（YouTube EPUfiTV9QWhM4，[1042.559-1148.08]，L1）
