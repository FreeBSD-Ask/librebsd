# 149.6 OpenZFS 合并与 13.x ZFS 演进——OpenZFS 2.0/2.1 统一代码库

## 149.6.1 FreeBSD ZFS 与 OpenZFS 上游合并

**要点**：FreeBSD 13.0 时期完成了 FreeBSD ZFS 代码库与 OpenZFS 上游的统一——在此之前 FreeBSD 维护着自己的 ZFS 分支（从 illumos 移植后独立演化），与 ZoL（ZFS on Linux）、illumos ZFS 存在代码分叉；OpenZFS 2.0（2020 年 11 月发布）正式统一了 FreeBSD、Linux、illumos、macOS 的 ZFS 代码库，所有平台共享同一代码基线；FreeBSD 13.0 采用 OpenZFS，13.1 升级到 OpenZFS 2.1.4（2022-05），13.2 升级到 OpenZFS 2.1.9（2023-04），13.3 升级到 OpenZFS 2.1.14（2024-03）；这一合并意味着 FreeBSD 能够更快获得 ZFS 新功能、bug 修复和性能改进，同时 FreeBSD 开发者也向上游 OpenZFS 贡献代码

**史料**：OpenZFS 2.0/2.1 Release Notes（github.com/openzfs/zfs/releases）；FreeBSD 13.x Release Notes ZFS 章节；Matt Ahrens、Brian Behlendorf（布莱恩·贝伦多夫） 关于 OpenZFS 统一的演讲［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］ 〔L1 代码；L3 官方文档；L4 事后叙述〕

**史观**：总纲第 4 条——分离与聚合：ZFS 从 illumos/FreeBSD/Linux 三端分叉（分离）到 OpenZFS 统一代码库（聚合），是开源项目“分久必合”的典型案例——分叉让各平台快速适配，统一后共享维护成本

**辨析**：OpenZFS 2.0 统一发生在 13.0 发布前（2020-11），13.0 是首个包含统一 OpenZFS 的 FreeBSD 大版本；13.0 之前 FreeBSD ZFS 维护独立分支，与 ZoL（ZFS on Linux）、illumos ZFS 存在代码分叉，这一分叉状态持续了约 13 年（2007-2020）；ZFS 文件系统本身的历史详见相关章节，本节仅讨论 13.x 时期（2021-2024）的 OpenZFS 代码库合并与版本演进，不重复 ZFS 起源叙事

## 149.6.2 OpenZFS 2.1 核心特性：zstd 压缩、Persistent L2ARC、Sequential Resilver、dRAID

**要点**：13.x 期间的 OpenZFS 2.1 系列带来多项重要特性：(1) **zstd 压缩**：支持 Zstandard 压缩算法，在压缩比和性能之间提供良好平衡，比 gzip 更快、比 lz4 压缩比更高；(2) **Persistent L2ARC**：L2ARC（二级缓存）在重启后保留缓存内容，避免重启后的缓存预热期；(3) **Sequential Resilver**：顺序重建（resilver），在替换故障磁盘时按顺序而非随机 IO 重建数据，大幅缩短大容量磁盘重建时间；(4) **dRAID（Distributed RAID）**：分布式 RAID，为热备盘场景优化，支持更快的重建速度；(5) **加密改进**：原生加密的性能和兼容性改进；(6) **trim/discard 支持改进**；(7) 大量性能优化和 bug 修复

**史料**：OpenZFS 2.1 Release Notes；**zfs(8)** 手册页新特性说明；Allan Jude（艾伦·裘德） 在 BSDCan/Vendor 演讲中关于 OpenZFS 新特性的介绍 ［A］

**史观**：总纲第 2 条——实践先于理论：这些新特性均来自生产环境需求——Persistent L2ARC 解决数据库等场景重启后缓存冷启动问题；Sequential Resilver 和 dRAID 解决大容量（10TB+）磁盘重建时间过长的实际运维痛点

**辨析**：dRAID 在 13.x 时期是可用功能但需要仔细评估其适用性，并非所有场景都推荐 dRAID 替代传统 RAID-Z/镜像；Persistent L2ARC 需要在创建池时启用或设置属性，不是默认启用

**文献**：OpenZFS Project. (2021-07). *OpenZFS 2.1.0 Release Notes*. github.com/openzfs/zfs/releases; Jude, A. (2021). *OpenZFS 2.1 New Features*. BSDCan 2021.［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

## 149.6.3 UFS/UFS2 64-bit inode 与其他文件系统改进

**要点**：FreeBSD 13.0 对 UFS/UFS2 文件系统进行了长期以来最重要的改进之一：**64 位 inode 编号支持**——UFS2 之前使用 32 位 inode 编号，限制单个文件系统最多约 2^32（约 42 亿）个 inode，在大容量存储上可能成为瓶颈；64 位 inode 将此限制扩展到 2^64，支持超过 80 亿文件且未来几乎不会耗尽；13.2 新增功能：使用日志软更新（journaled soft updates）时支持 UFS 快照；**makefs(8)** 工具新增 ZFS 支持，可直接创建 ZFS 文件系统镜像而无需 root 权限或挂载；**fusefs(4)**（FUSE，用户态文件系统）在 13.x 期间持续完善，性能和兼容性显著提升

**史料**：FreeBSD 13.0/13.2 Release Notes“File Systems”章节；**ffs(4)**（UFS/UFS2）手册页关于 64-bit inode 的说明；**makefs(8)** 手册页 ZFS 支持部分；麦库西克（Marshall Kirk McKusick）关于 UFS 64-bit inode 的邮件列表帖子和演讲 ［A］

**史观**：总纲第 7 条——BSD 与 UNIX 谱系的连续性：UFS 是 BSD 最古老、最稳定的文件系统，源自 1980 年代的 Berkeley Fast File System（FFS）；64 位 inode 改进延续了 McKusick 等原 BSD 开发者对 UFS 的持续维护，体现了 BSD 对传统技术负责、不轻易抛弃的精神

**辨析**：64 位 inode 是向后兼容的——现有 32 位 inode 的 UFS2 文件系统可以正常读写，但新创建的文件系统默认使用 64 位 inode；13.0 的 bsdgrep 默认化属于用户态工具改进而非文件系统改进

**文献**：FreeBSD Project. **ffs(4)**, **makefs(8)**, **fusefs(4)** Manual Pages; McKusick, M. K. (2020). *UFS 64-bit Inodes*. EuroBSDCon 2020. ［B］

## 149.6.4 13.x 时期文件系统史料辨析

**要点**：13.x 时期文件系统改进的一手史料包括：(1) OpenZFS GitHub 仓库 release 页面和 commit 历史；(2) FreeBSD src 仓库 sys/fs/ 目录（UFS、fusefs 等）和 sys/contrib/openzfs/ 目录 commit；(3) 麦库西克、Allan Jude、Matt Ahrens 等开发者的邮件列表帖子和会议演讲；(4) **zfs(8)**/**ffs(4)**/**makefs(8)** 等手册页更新记录；ZFS 在 13.x 时期仍是推荐的默认文件系统（对于新安装），UFS 继续得到全面维护和改进，两者并存是 FreeBSD 文件系统格局的特点

**史料**：git.freebsd.org src/ 目录 sys/fs/ 和 sys/contrib/openzfs/ commit 历史；OpenZFS GitHub releases；BSDCan/EuroBSDCon 文件系统相关演讲 ［A］

**史观**：总纲第 5 条——技术债务与代码考古：UFS 64-bit inode 改进是对一项 40 年历史技术的持续还债——32 位 inode 在 1980 年代设计时看似足够，但磁盘容量增长最终突破了这一限制；持续维护和演进旧代码是 FreeBSD 区别于“重写一切”文化的重要特征

**辨析**：**makefs(8)** ZFS 支持主要用于安装镜像构建和嵌入式系统镜像制作，不是普通用户日常创建 ZFS 池的工具；普通用户仍应使用 **zpool create** 和 **zfs create**

**文献**：McKusick, M. K., Joy, W. N., Leffler, S. J., & Fabry, R. S. (1984). *A Fast File System for UNIX*. ACM TOCS; FreeBSD Manual Pages. ［B］
