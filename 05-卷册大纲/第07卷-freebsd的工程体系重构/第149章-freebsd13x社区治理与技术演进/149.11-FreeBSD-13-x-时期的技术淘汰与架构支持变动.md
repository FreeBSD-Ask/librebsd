# 149.11 FreeBSD 13.x 时期的技术淘汰与架构支持变动

## 149.11.1 MIPS 架构降级与退役路径

**要点**：FreeBSD 13.0-RELEASE 将 MIPS 架构（包括 mips、mipsel、mips64、mips64el、mipsn32、mipselhf、mipshf、mips64elhf、mips64hf 等多种变种）从 Tier-2 降级，标志着 FreeBSD 对 MIPS 架构支持的终结过程开始；MIPS 自 FreeBSD 8.0（2009-11）起由 Oleksandr Tymoshenko、Jung-uk Kim 等开发者移植，主要用于嵌入式路由器（Atheros/Qualcomm Wi-Fi 路由器、Lantiq DSL 调制解调器）、SGI 工作站、龙芯（Loongson）处理器；MIPS 退役原因：(1) 市场份额被 ARM 大幅取代——路由器厂商逐步转向 ARM 架构；(2) 龙芯自 2020 年代起转向自主指令集 LoongArch，不再使用 MIPS；(3) Clang/LLVM 对 MIPS 后端支持长期滞后于 GCC；(4) 活跃维护者持续减少；(5) MIPS 存在多种 ABI（o32/n32/n64）和字节序变种，维护复杂度极高；FreeBSD 13.x 期间 MIPS 支持持续降级，13.4 是最后一个包含 MIPS 支持的稳定分支之一

**史料**：FreeBSD 13.0 Release Notes“Architectures”章节；freebsd-mips@ 邮件列表 Oleksandr Tymoshenko 等关于 MIPS 退役的帖子；Oleksandr Tymoshenko、Jung-uk Kim 的 MIPS 相关 commit 历史 ［A］

**史观**：总纲第 7 条——BSD 与 UNIX 谱系的连续性：MIPS 是 RISC 处理器的先驱，SGI IRIX 是重要的商业 UNIX 平台；FreeBSD 对 MIPS 的支持延续了 BSD 在非 x86 架构上的传统，但市场和技术的变化使其退役成为必然

**辨析**：13.0 是 MIPS 降级而非完全移除——MIPS 代码在 13.x 源码树中仍存在但不再作为正式支持架构；MIPS 完全移除发生在 FreeBSD 14.0；与 sparc64、PC98、armv6 等退役架构类似，MIPS 退役是架构生态演化的自然结果

**文献**：FreeBSD Project. (2021). *13.0 Release Notes* (Architectures section); Tymoshenko, O. (2020-2021). freebsd-mips mailing list posts on MIPS support status. ［A］

## 149.11.2 riscv64sf（软浮点 RISC-V）退役与 riscv64 演进

**要点**：FreeBSD 13.0 移除了 riscv64sf（64 位 RISC-V 软浮点变体）架构支持，仅保留 riscv64（hard-float）作为 Tier-2 支持；riscv64 与 riscv64sf 最初由 Ruslan Bukin、Mitchell Horne（米切尔·霍恩） 等于 FreeBSD 12.0 时期移植；riscv64sf 退役原因：(1) RISC-V 规范明确 hard-float 为标准配置，软浮点仅用于早期 FPGA 原型和模拟器；(2) 主流 RISC-V 硬件（SiFive U74、Allwinner D1、StarFive JH7110 等）均使用 hard-float；(3) 维护两个 ABI 变体成本高于收益；(4) riscv64sf 实际用户基数极小；riscv64 在 13.x 期间持续改进，但仍保持 Tier-2 地位，13.x 发布 RISC-V 虚拟机镜像但不提供 RELEASE 级别的阻塞保证

**史料**：FreeBSD 13.0 Release Notes；RISC-V ISA 规范；freebsd-riscv@ 邮件列表 Ruslan Bukin、Mitchell Horne 等的帖子 ［A］

**史观**：总纲第 7 条——BSD 与 UNIX 谱系的连续性：RISC-V 是开放指令集架构的新希望，FreeBSD 是较早支持 RISC-V 的通用操作系统之一；riscv64sf 的退役不是对 RISC-V 的放弃，而是聚焦资源支持标准硬件配置

**辨析**：RISC-V 在 13.x 时期仍为 Tier-2，不应被宣传为“全面支持”——riscv64 在 13.x 适合开发者和早期采用者，生产环境使用需谨慎；riscv64 升 Tier-1 是长期目标但未在 13.x 实现

**文献**：FreeBSD Project. (2021). *13.0 Release Notes*; RISC-V International. *RISC-V ISA Specifications*. riscv.org; Bukin, R., Horne, M. (2018-2024). freebsd-riscv mailing list. ［A］

## 149.11.3 OpenSSL 1.0.2 移除与 1.1.1 时代

**要点**：FreeBSD 13.0 移除了旧版本 OpenSSL 1.0.2，base 系统仅保留 OpenSSL 1.1.1；OpenSSL 1.0.2 于 2019 年 12 月 31 日 EOL（End of Life），FreeBSD 12.x 期间为兼容性保留了 1.0.2，13.0 彻底移除；OpenSSL 1.1.1 是 TLS 1.3 支持的首个 LTS 版本，引入 ChaCha20-Poly1305、X25519 等现代密码学算法；FreeBSD 13.x 全程保持 OpenSSL 1.1.1 系列，未升级到 OpenSSL 3.0——OpenSSL 3.0 升级在 FreeBSD 14.0（2023-11）才进行；同期 LibreSSL（OpenBSD fork）和 BoringSSL（Google fork）作为替代加密库存在，但 FreeBSD base 系统继续使用 OpenSSL

**史料**：FreeBSD 13.0 Release Notes；OpenSSL 1.0.2 EOL 公告（2019-12-31）；OpenSSL 1.1.1 Release Notes；freebsd-security@ 邮件列表关于 OpenSSL 升级的讨论 ［A］

**史观**：总纲第 5 条——技术债务与代码考古：OpenSSL 1.0.2 在 EOL 后继续保留在 FreeBSD 12.x 中是典型的技术债务——兼容性要求推迟了不可避免的升级；13.0 偿清了这笔债务

**辨析**：OpenSSL 3.0 未在 13.x 引入是保守工程决策——OpenSSL 3.0 引入了新的 API 和许可证变更（Apache 2.0），且发布初期有较多兼容性问题，在稳定分支中引入风险过大；稳定分支（stable/13）通常不引入 OpenSSL 大版本升级

**文献**：OpenSSL Project. (2019-12-31). *OpenSSL 1.0.2 EOL Announcement*. openssl.org; OpenSSL Project. *OpenSSL 1.1.1 Release Notes*; FreeBSD Project. (2021). 13.0 Release Notes (OpenSSL section).［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

## 149.11.4 bsdgrep 默认化与 GNU grep 移除

**要点**：FreeBSD 13.0 将 BSD 许可证的 **bsdgrep(1)** 设为默认 **grep(1)** 实现，移除了长期在 base 中的 GNU grep；bsdgrep 源自 OpenBSD 的 grep 实现，由 Gabor Kovesdan 等移植到 FreeBSD，最初在 ports 中（textproc/bsdgrep），后合入 base；bsdgrep 成为默认前经历了多年性能优化；与 GNU grep 相比，bsdgrep 是 BSD 许可证、代码更简洁、与 BSD 工具链更一致，但某些 GNU 扩展选项不支持；同期 OpenBSD 早已在 5.0（2011）将 grep 替换为 BSD 许可证实现；这一变化是 FreeBSD 持续去 GNU 化工程的一部分

**史料**：FreeBSD 13.0 Release Notes；**grep(1)** 手册页；freebsd-current@ 2010 年关于 bsdgrep vs GNU grep 的讨论（历史背景）；Gabor Kovesdan bsdgrep 相关 commit ［A］

**史观**：总纲第 12 条——法律结构：GNU grep 是 GPLv3 许可证，将其保留在 base 中存在许可证兼容性考量，替换为 BSD 许可证实现可消除 GPL 组件在 base 系统中的占比；这与 GCC 替换为 Clang/LLVM 的逻辑一致

**辨析**：bsdgrep 在 13.0 成为默认，但用户若需要 GNU grep 语法/扩展可通过 ports 安装 textproc/gnugrep；bsdgrep 不是“从零写的新 grep”，而是基于 OpenBSD grep 移植并优化

**文献**：FreeBSD Project. (2021). 13.0 Release Notes (Userland section); **grep(1)** Manual Page; OpenBSD Project. **grep(1)** history.［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

- 62.11.4-辩证 bsdgrep 默认化与 GNU grep 移除的辩证链——四层对称呈现

**要点**：bsdgrep 默认化是 FreeBSD 许可证纯洁化工程在用户态工具层面的标志性事件，其辩证过程可拆解为四层：(1) **批评层（FreeBSD 阵营对 GNU grep 的批评）**——GNU grep 自 2007 年起随核心工具转为 GPLv3 许可证，与 FreeBSD base 系统“以 BSD 许可证代码为核心”的工程目标冲突；FreeBSD 长期维护一份冻结在 GPLv2 时代的 GNU grep 旧版本（约 2.5.1），既无法升级到上游现代版本（受 GPLv3 约束），又承担安全修复与功能滞后双重技术债务；Gabor Kovesdan 等开发者在 2010 年前后于 freebsd-current@ 邮件列表发起 bsdgrep 替代讨论，论证 BSD 许可证 grep 实现的可行性。(2) **反批评层（GNU 阵营与用户群体对 bsdgrep 替代的质疑）**——GNU grep 是 UNIX 生态事实标准，性能经数十年优化（如 **grep(1)** 的 `--mmap`、DFA 引擎等），广泛存在于脚本、构建系统、CI 流水线中；bsdgrep 早期在处理大文件、复杂正则表达式（尤其 PCRE `-P` 选项）时性能与兼容性不及 GNU grep；部分用户质疑“许可证纯洁化不应以功能降级为代价”，认为强制切换默认 grep 会破坏既有脚本兼容性。(3) **再回应层（FreeBSD 阵营的再回应）**——FreeBSD 并未“禁止”GNU grep，而是通过 ports 中的 `textproc/gnugrep` 保留 GNU grep 的完整可用性，用户可通过 `pkg install gnugrep` 或修改 PATH 优先级恢复 GNU grep 体验；bsdgrep 覆盖 POSIX grep 规范与绝大多数常用扩展选项（`-r`、`-i`、`-n`、`-v`、`-E` 等），对普通用户与系统脚本足够；base 系统的工具选择应服务于操作系统核心许可证目标，而非追求单一工具的功能极致；bsdgrep 源自 OpenBSD grep，经过 OpenBSD 社区多年代码审计，安全性与代码简洁性优于 GNU grep 的庞大代码库。(4) **合图层（辩证综合）**——bsdgrep 默认化不是“GNU grep 被驱逐出 FreeBSD”，而是“base 与 ports 的分工重构”：base 系统承担操作系统核心职责，以 BSD 许可证代码为底座；ports 生态承担“提供用户选择”的职责，GNU grep、GNU sed、GNU coreutils 等 GPL 工具在 ports 中继续得到良好维护；这一二元结构既实现了许可证纯洁化的工程目标，又保留了用户对 GNU 工具的完整访问权，是 BSD 哲学中“自由即选择”的体现

**史料**：FreeBSD 13.0-RELEASE Release Notes“Userland”章节（bsdgrep 默认化条目）；**grep(1)** 手册页（FreeBSD 13.0 版本，标注 BSD 许可证）；freebsd-current@ 邮件列表 2010 年 bsdgrep 讨论线索（lists.freebsd.org/pipermail/freebsd-current/，Gabor Kovesdan 等参与）；Gabor Kovesdan bsdgrep 移植 commit 历史（svnweb.freebsd.org 时代记录，后迁移至 cgit.freebsd.org）；OpenBSD 5.0（2011）Release Notes grep 替换条目；GNU grep 2.5.1 与 3.x 许可证对比（GPLv2 → GPLv3）；FreeBSD ports `textproc/gnugrep` FreshPorts 条目；**freebsd.duckdb 代码级证据**（`原材料/研究/bsd仓库分析/freebsd.duckdb`，2026-07-23 经 `script/query_if_wg_commits.py` 查询验证，freebsd-src 仓库 Kyle Evans bsdgrep/grep 相关 commit 共 30 条）：(1) **bsdgrep 成为 /usr/bin/grep 的关键 commit**——`b82a9ec5f53e`（2020-12-08T14:05:25Z Kyle Evans，“src.opts.mk: switch to bsdgrep as /usr/bin/grep”），此 commit 标志 bsdgrep 正式取代 GNU grep 成为 base 系统默认 grep；(2) **GNU_GREP 默认关闭 commit**——`32420de98684`（2020-12-11T03:59:41Z Kyle Evans，“Flip the GNU_GREP default to OFF”），距上一 commit 仅约 3 天，体现“默认化 → 关闭旧选项”的工程节奏；(3) **gnugrep 与 libgnuregex 完全移除 commit**——`47d1ad2413da`（2020-12-22T15:38:09-06:00 Kyle Evans，“gnu: remove gnugrep and libgnuregex”）与 `8aff76fb37b5`（2020-12-22T15:36:40-06:00 Kyle Evans，“build: remove the option to build gnugrep”），二者相隔仅约 1 分 30 秒，体现“移除 gnugrep 源码 + 移除构建选项”的配套清理；(4) **bsdgrep 早期移植与优化 commit**——`cab7d341dcd9`/`cadd3b8fcb41`（2020-08-04 Kyle Evans，“bsdgrep: switch to libregex for GNU_GREP_COMPAT”）、`97741df0a0c8`（2019-11-11 Kyle Evans MFC 一批 bsdgrep 修复）、`38325e2ab8f0`（2019-09-25 Kyle Evans，"bsdgrep(1): various fixes of empty pattern/exit code/-c behavior"）、`aef64c62c2a6`（2019-09-03 Kyle Evans，"bsdgrep(1): add some basic tests for some GNU Extension support"）等，反映 bsdgrep 默认化前约两年时间的渐进式优化路径，印证 62.11.4-辩证“改革式路径”的合图判断 ［A/B］

**史观**：总纲第 13 条——法律与道德是利益分配：bsdgrep 默认化表面上是“许可证纯洁化”，实质上是 FreeBSD 项目对“base 系统应由何种许可证代码构成”这一利益分配问题的形式化决策——GPLv3 阵营主张“代码应强制开源延续”，BSD 阵营主张“代码应允许自由使用包括闭源再分发”，bsdgrep 默认化是后一种利益分配主张在 grep 工具上的落实；总纲第 15 条——文化即形式主义：grep 作为 UNIX 文化的基础工具，其实现选择本身就是一种文化形式主义——选择 bsdgrep 还是 GNU grep 不仅是技术选择，更是对“BSD 文化”或“GNU 文化”的形式化认同

**要点**：62.11.4-辩证 已呈现四层辩证链（批评层 → 反批评层 → 再回应层 → 合图层），本节补足第五层——GNU 阵营与 GPL 生态支持者对 FreeBSD 阵营再回应（第三层）的再回应，并深化合图层。FreeBSD 阵营在第三层提出三项辩护：(a) GNU grep 仍可通过 ports `textproc/gnugrep` 安装，(b) bsdgrep 覆盖 POSIX 规范与绝大多数常用扩展选项，(c) base 系统应服务于核心许可证目标而非单一工具功能极致。GNU 阵营的再回应针对这三项辩护分别反驳：(1) **对“ports 保留 gnugrep”辩护的反驳**——“用户不应被迫安装 ports 才能获得完整的 grep 功能”：base 系统的默认工具选择具有强烈的路径依赖效应，绝大多数用户与脚本不会主动安装 gnugrep 而是直接使用 `/usr/bin/grep`，因此“ports 可用”在实践中无法真正保障用户对 GNU grep 功能的访问权；CI/CD 流水线、容器镜像、嵌入式系统等场景中，base 系统的 grep 是唯一可用的 grep，切换为 bsdgrep 后这些场景中的脚本兼容性问题无法通过“安装 ports”解决；这一反驳揭示了“base 与 ports 分工”辩护的结构性局限——分工在理论上保障了选择权，但在实践中 base 的默认选择具有事实上的强制性。(2) **对“bsdgrep 覆盖 POSIX”辩护的反驳**——“POSIX 规范是最低标准而非工程目标”：POSIX grep 规范定义的是跨平台兼容性的最低要求，将其作为 base 系统默认 grep 的功能上限是以“最低标准”替代“最佳实践”；GNU grep 的 DFA 引擎、`--mmap`、`-P`（PCRE）等扩展功能是数十年工程优化的成果，并非可有可无的装饰；以“覆盖 POSIX”为 bsdgrep 辩护，实质上是将“功能降级”重新定义为“标准合规”，这是许可证意识形态对工程实践的绑架。(3) **对“base 服务于许可证目标”辩护的反驳**——“许可证纯洁化不应以功能降级为代价”：base 系统的首要服务对象是用户而非许可证意识形态；BSD 许可证的核心价值在于“允许自由使用包括闭源再分发”，这一价值不应反向转化为“排斥 GPL 代码出 base”的纯洁化要求；GNU grep 作为 GPLv3 代码存在于 base 中，并不妨碍 FreeBSD 用户行使 BSD 许可证赋予的权利，“许可证纯洁化”叙事将 BSD 许可证的“允许”重新定义为“排斥”，是对 BSD 哲学的扭曲；这一反驳触及了 FreeBSD 许可证纯洁化工程的根本张力——“自由的操作系统”是否应当允许用户在 base 中选择 GPL 工具，还是应当以“纯洁化”名义替用户做出选择。(4) **合图层深化**：bsdgrep 默认化的辩证链在第五层后呈现更为复杂的图景——62.11.4-辩证 的合图层将“base 与 ports 分工”视为双赢方案，但 GNU 阵营的再回应揭示了这一分工的权力不对称性：base 系统的默认选择是 FreeBSD 项目对用户的事实性强制，“ports 可用”的承诺在实践中受限于用户的安装意愿与场景约束；合图层因此须承认——bsdgrep 默认化不是无代价的“双赢”，而是 FreeBSD 项目以“许可证纯洁化”为名、以“base 默认选择权”为权力杠杆、以“ports 可用”为安抚性让步的利益分配决策；GNU 阵营的再回应与 FreeBSD 阵营的再回应之间的分歧是不可调和的——前者认为“用户选择权”高于“许可证纯洁化”，后者认为“许可证纯洁化”是 base 系统的工程目标；这一不可调和性印证总纲第 19 条“前理解的差异使分歧不可避免”，合图层只能呈现分歧的结构本身，无法裁判哪一方“正确”；最终的工程和解路径（bsdgrep 默认 + gnugrep 保留 ports + 持续优化 bsdgrep 性能）是各方在承认分歧不可调和后的务实妥协，而非价值共识的达成

## 149.11.5 13.x 技术淘汰史辨析

**要点**：13.x 时期的技术淘汰（MIPS 降级、riscv64sf 退役、GCC 4.2.1 移除、OpenSSL 1.0.2 移除、GNU grep 移除、Beastie ASCII 菜单移除、**syscons(4)** 从 GENERIC 移除）共同构成 FreeBSD 持续现代化的过程；这一进程与 10.x（GCC 引入、BIND 替换、pkg 替代 pkg_*）、11.x（IA-64 退役）、12.x（PC98/sparc64/armeb/arm 退役）形成连续线；技术淘汰是操作系统保持健康的必要过程——移除不再维护的旧代码减少了维护负担、降低了安全风险，但需要平衡兼容性影响

**史观**：总纲第 9 条——简洁与复杂的辩证：移除代码是“做减法”的工程，看似简单但涉及兼容性判断、用户迁移、文档更新等复杂工作；一个健康的项目不仅要会添加新功能，也要会移除不再需要的旧功能

**辨析**：13.x 没有移除大量架构（主要仅 MIPS 降级和 riscv64sf 移除），相比 12.x 移除 sparc64/PC98 等大动作，13.x 更聚焦于工具链和用户态组件的现代化；架构退役主要阶段在 12.x 已完成
