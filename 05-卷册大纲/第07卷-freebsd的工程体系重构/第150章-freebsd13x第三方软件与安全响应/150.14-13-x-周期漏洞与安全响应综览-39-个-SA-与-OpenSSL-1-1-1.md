# 150.14 13.x 周期漏洞与安全响应综览——39 个 SA 与 OpenSSL 1.1.1 LTS 的守护岁月

## 150.14.1 13.x 周期安全态势总览——39 个 SA 的分布与节奏

**要点**：13.x 周期（**2021-04-01** 至 **2023-11-01**，按版本周期文件边界）共发布 **39 个 FreeBSD-SA**——其中 2021 年 10 个（SA-21:08 至 SA-21:17）、2022 年 15 个（SA-22:01 至 SA-22:15）、2023 年 14 个（SA-23:01 至 SA-23:14）；对应 **freebsd.duckdb** `commits` 表 freebsd-src 仓库 **226 条 CVE 相关 commit** 与 **68 个去重 CVE**；NVD 元数据中 13.x 周期 68 个 CVE 全部无 CVSS v3 评分——这一数据分布反映 13.x 周期 FreeBSD base 系统未出现 CVSS 9.0 以上 Critical 漏洞，但“无评分”不等于“不严重”，CVE-2021-29631（vm_fault COW 页映射多重映射）与 CVE-2021-29630（**ggatec(8)** 远程代码执行）从描述看潜在严重性较高；2023 年 8-9 月（SA-23:06 至 SA-23:12）是 13.x 周期单月 SA 发布密度的峰值，6 周内发布 7 个 SA，反映 bhyve、pf、pam_krb5、wifi、msdosfs 等子系统的集中维护

**史料**：**freebsd.duckdb** `commits` 表 freebsd-src 仓库 13.x 周期 CVE commit 查询：`SELECT count(*) FROM commits WHERE repo_name='freebsd-src' AND author_date>='2021-04-01' AND author_date<'2023-11-01' AND (message_subject LIKE '%CVE-%' OR message_body LIKE '%CVE-%')` 结果 226 条；FreeBSD Security Advisories 官方存档 2021-04-01 至 2023-11-01 共 39 条；本地 cvelistV5 仓库 13.x 周期 68 个去重 CVE 元数据，全部无 CVSS v3 评分 ［A］

**史观**：总纲第 17 条——软件工程：13.x 周期 SA 节奏相对平缓反映 Security Team 工作模式仍处于“被动响应外界报告”阶段——Security Officer Team 在 Gordon Tetlow（戈登·泰特洛）（Security Officer）、Ed Maste（埃德·马斯特）（Deputy）主导下保持稳定延续，但未开展 14.x 周期那样的系统性主动审计；这种被动响应模式既是工程稳态的体现（base 系统架构成熟、攻击面相对稳定），也是审计资源不足的反映；与 14.x 周期 80 个 SA（不足 3 年）相比，13.x 周期 2.5 年内仅 39 个 SA，节奏明显更慢

**辨析**：39 个 SA 的统计口径需精确说明：以 SA 公告发布日期在 **2021-04-01** 至 **2023-11-01** 之间为准；SA-23:15 至 SA-23:19（2023-11-08 至 2023-12-19）虽属 13.3-RELEASE 修复范围但发布日期超出周期边界，未计入 39 个；SA-21:07.openssl（2021-03-25）发布于 13.0-RELEASE 前 19 天，属 12.x 周期尾声的修复，但影响 13.0-RELEASE 镜像，统计上归入 12.x 周期；13.x 周期 68 个 CVE 全部无 CVSS v3 评分不等于“漏洞不严重”，而是 NVD cvelistV5 镜像中未提取到评分数据——CVE-2021-29631 与 CVE-2021-29630 从 commit subject 描述看潜在严重性较高，但 FreeBSD 官方公告未公布 CVSS 评分

## 150.14.2 OpenSSL 1.1.1 LTS 守护期——加密栈稳定性与 13.4 升级代价

**要点**：13.x 周期是 FreeBSD base 系统使用 OpenSSL 1.1.1 系列的完整生命周期——13.0（2021-04）使用 `1.1.1l`、13.1（2022-05）使用 `1.1.1o`、13.2（2023-04）使用 `1.1.1t`、13.3（2024-03）使用 `1.1.1w`（1.1.1 系列最终版本，**2023-09-11** EOL）；13.x 周期内 OpenSSL 1.1.1 系列共发现并修复至少 9 个 CVE：CVE-2021-23839（RSA_SSLV23_PADDING 类型）、CVE-2021-23840（**X509_verify_cert** NULL 解引用）、CVE-2021-23841（**X509_check_ca** 内部 NULL 解引用）、CVE-2021-3711（SM2 解密缓冲区溢出，潜在严重）、CVE-2021-3712（ASN.1 字符串读取越界）、CVE-2022-0778（**BN_mod_sqrt** 无限循环 DoS，commit `7895cf4ce4f7cb3bdf4f84388e97035cf256f97c` 等 7 个分支同步）、CVE-2022-4304（RSA 解密时序侧信道）、CVE-2022-4450（**PEM_read_bio_ex** 空指针解引用）、CVE-2023-0286（X.400 地址类型混淆）；13.x 周期共发布 5 个 OpenSSL 相关 SA（SA-21:07、SA-21:16、SA-21:17、SA-22:03、SA-23:03），均通过 vendor import 同步上游 1.1.1 系列修复；**13.4-RELEASE（2024-09-17）** 才在 stable/13 分支中升级到 OpenSSL 3.0.16+，是 13.x 系列末期的一次性代际迁移

**史料**：**freebsd.duckdb** `commits` 表 freebsd-src 仓库 OpenSSL CVE commit 查询：`SELECT commit_hash, author_date, author_name, message_subject FROM commits WHERE repo_name='freebsd-src' AND author_date>='2021-04-01' AND author_date<'2023-11-01' AND message_subject LIKE '%OpenSSL%' AND (message_body LIKE '%CVE-%' OR message_subject LIKE '%CVE-%') ORDER BY author_date ASC`；FreeBSD-SA-21:07/21:16/21:17/22:03/23:03.openssl PGP 签名公告；Gordon Tetlow 的 OpenSSL 修复 commit `aef815e7873b006bd040ac1690425709635e32e7`（2021-08-24，一次修复 CVE-2021-3711 与 CVE-2021-3712）与 `e237b128e080f98e91c43c7050409a817d007672`（2023-02-16，一次修复 CVE-2022-4304、CVE-2022-4450、CVE-2023-0215、CVE-2023-0286 共 4 个 CVE）；OpenSSL 1.1.1 系列发布时间表（1.1.1l 至 1.1.1w） ［A］

**史观**：软件工程：OpenSSL 1.1.1 是 LTS（长期支持）版本，FreeBSD 选择在 stable/13 全周期保持 1.1.1 系列而不升级到 3.0，体现了“稳定分支不引入大版本升级”的保守工程原则；这种保守性带来双重效应：一方面避免了 OpenSSL 3.0 引入的新 CVE 与 API 兼容性问题，另一方面使 13.x 周期内的 OpenSSL CVE 都是 1.1.1 系列自身的问题，而非 3.0 迁移引入的新债务；与 14.x 周期 OpenSSL 3.0 迁移带来约 16 个 CVE 相比，13.x 周期 OpenSSL 1.1.1 系列仅 9 个 CVE，反映 LTS 版本成熟度优势

**辨析**：**需严格区分**：① 13.x 版本周期文件（2021-04 至 2023-11）查询结果中出现的 OpenSSL 3.0 commits（如 2023-08-10 `aa7957345732816fb0ba8308798d2f79f45597f9` “OpenSSL: update to 3.0.10”、2023-09-22 `315108b81694de474bbc273c0050b195047f5eed` “openssl: Vendor import of OpenSSL 3.0.11”、2023-10-24 `825caf7e12445fa4818413cc37c8b45bebb6c3a9` “OpenSSL: Vendor import of OpenSSL 3.0.12”）实际是 main 分支（stable/14）的工作，并未 MFC 到 stable/13——13.3-RELEASE（2024-03-05）仍使用 OpenSSL 1.1.1w；② 13.4-RELEASE（2024-09-17）才正式在 stable/13 中升级到 OpenSSL 3.0.16+，这超出了 13.x 版本周期文件边界；③ CVE-2021-3711（SM2 解密缓冲区溢出）从描述看潜在严重性较高，但 FreeBSD 官方公告与 NVD cvelistV5 镜像均未给出 CVSS v3 评分，无法精确量化其严重性；④ OpenSSL 1.1.1 系列在 13.0-13.3 的“全程守护”不是工程失败而是工程胜利——LTS 版本的稳定性是 FreeBSD 选择保守升级路径的核心动机

## 150.14.3 bhyve/jail/netmap 虚拟化边界漏洞群——攻击面首次系统审视

**要点**：13.x 周期内 FreeBSD 虚拟化与隔离子系统共发布 7 个 SA——bhyve 3 个（**SA-21:13.bhyve**、**SA-22:05.bhyve**、**SA-23:07.bhyve**）、jail 3 个（**SA-21:04.jail_remove**、**SA-21:05.jail_chdir**、**SA-21:10.jail_mount**）、netmap 1 个（**SA-22:04.netmap**，含 CVE-2022-23084 TOCTOU 与 CVE-2022-23085 整数溢出）；bhyve 3 个 SA 涉及不同子系统：**SA-21:13.bhyve**（CVE-2021-29631，virtqueue 处理错误，由 Gordon Tetlow 与 Mark Johnston（马克·约翰斯顿） 修复，commit `20f96f215562c7533053e01b186066ad935d11d0`、`71fbc6faed62e8eb5864f7c40839740f5e9f5558`、`398bfe63e6f7d265c6bae2f56da29d37f6fc7a01`、`eb01dfe6c01c700418a872ae520187a1292ea7da` 等多分支同步）涉及多设备模型的 `vq_getchain()` 错误处理；**SA-22:05.bhyve**（CVE-2022-23087，e82545 网卡校验和字段验证，commit `9c55c1cf567c598b0bbb2e996d09ca0b44ba88f5`、`b85c68857da3fdd833c4c146e2f5f49f4c16b0d7`）由 Mark Johnston 修复；**SA-23:07.bhyve**（CVE-2023-3494，fwctl 状态机重置，commit `2bae613e0da39531422b20910366195373ffa794`、`9fe302d78109b12867bd933bb68cd900c9940b7d`、`87702e38a4b4fe990b06f39b5cf267fb564c367e`、`bed3ae1d7863ac1e0b1e82ae7bf952937e921efe`）由 John Baldwin（约翰·鲍德温） 修复；3 个 bhyve SA 跨越 2021-08 至 2023-08，反映 bhyve 攻击面审计的渐进性而非集中爆发

**史料**：**freebsd.duckdb** `commits` 表 freebsd-src 仓库 bhyve/jail/netmap CVE commit 查询：`SELECT commit_hash, author_date, author_name, message_subject FROM commits WHERE repo_name='freebsd-src' AND author_date>='2021-04-01' AND author_date<'2023-11-01' AND (message_subject LIKE '%bhyve%' OR message_subject LIKE '%jail%' OR message_subject LIKE '%netmap%') AND message_subject LIKE '%CVE-%' ORDER BY author_date ASC`；FreeBSD-SA-21:13/22:05/23:07.bhyve、SA-21:04/05/10.jail_*、SA-22:04.netmap PGP 签名公告；Mark Johnston bhyve * *vq_getchain()** 修复 commit `20f96f215562c7533053e01b186066ad935d11d0`；Vincenzo Maffione netmap 修复 commit `7c55c52696d2aec39441802d687badc8b012432e`（CVE-2022-23084）、`9df8dd3ea36c8b3abe8fc182647472ca9cd83efd`（CVE-2022-23085） ［A］**

**史观**：总纲第 7 条——硬件与软件辩证：bhyve 3 个 SA 跨度两年反映 13.x 周期虚拟化边界审计处于“零星发现”阶段——外界报告或代码审查发现问题后逐个修复，未开展系统性审计；jail 3 个 SA 集中于 2021-02-24 与 2021-04-06 两个发布批次，均涉及 jail 配置与权限边界，是 **jail(2)** 系统调用与 `jail_remove`、`jail_mount`、`jail_chdir` 操作的隔离性问题；**jail vs bhyve 的边界**：jail 是操作系统级容器（共享内核），bhyve 是 Type-2 hypervisor（独立内核），两者安全模型不同——jail 漏洞通常是配置/权限边界问题，bhyve 漏洞通常是设备模拟内存错误；netmap 1 个 SA 涉及 **nmreq_copyin** 函数的 TOCTOU（time-of-check to time-of-use）与整数溢出，是 netmap 用户态-内核态数据拷贝路径的固有问题

**辨析**：**需精确说明**：① **SA-21:13.bhyve** 涉及 virtqueue 处理（**vq_getchain()** 函数）的多个设备模型错误，影响 bhyve 运行时设备模拟，攻击向量是恶意 guest 操作触发 host 内核漏洞；② **SA-22:05.bhyve** 涉及 e82545 网卡模拟器的校验和偏移字段验证，是单个设备模型的特定漏洞；③ **SA-23:07.bhyve** 涉及 fwctl 状态机重置，是 bhyve 内部 fwctl 子系统漏洞，John Baldwin 修复方案是“在 guest 请求重置时完全重置状态机”；3 个 SA 攻击向量均为恶意 guest 操作触发 host 内核漏洞——但实际利用需要 guest 已有 root 权限或能控制 guest 内核，攻击门槛较高；**netmap SA 的特殊性**：SA-22:04.netmap 是 13.x 周期少数同时包含 TOCTOU 与整数溢出两种不同类别漏洞的 SA，反映 netmap API 设计中用户态指针处理的复杂性

## 150.14.5 **mitigations(7)** 与 13.x 安全文档化——Ed Maste 的工程伦理贡献

**要点**：**2023 年 9 月 8 日** Ed Maste 提交 `8977587e89cbf221b1819d0a873fe53311de2fbd`、`272bc4597d0b41eebdfa7c108778070665acb431`、`b6a61ac2d475fba9c45f7f407549a522f60dea18` 共 3 个 commit，新增 **mitigations(7)** 手册页描述 FreeBSD base 系统的漏洞缓解机制——这是 13.x 周期最重要的安全文档化贡献；**mitigations(7)** 系统化整理了 FreeBSD 内核与用户态已实现的漏洞缓解措施，包括 ASLR（13.2 起对 64 位可执行文件默认启用）、W^X（写异或执行保护）、stack protector、PIE（位置无关可执行文件）、RELRO（只读重定位）、stack gap（栈间隙）、BTI（分支目标标识，arm64）、IBRS/STIBP（Spectre v2 缓解）、KPTI（内核页表隔离）等；**mitigations(7)** 的引入标志着 FreeBSD 安全文档从“散落于各手册页”向“系统化集中描述”的转变；Ed Maste 当时担任 Security Officer Deputy，其主导的文档化工作体现了“工程伦理 = 透明披露已实现的保护机制”的理念；这一文档化工作发生在 13.x 周期末期（13.3-RELEASE 前 7 个月），是 Security Team 对 13.x 周期安全工程经验的总结

**史观**：总纲第 22 条——开源运动：**mitigations(7)** 的引入是开源运动“透明性即安全性”理念的体现——闭源操作系统通常不详细披露其漏洞缓解机制（视为“安全通过 obscurity”），而 FreeBSD 通过手册页公开所有缓解机制的设计与状态，使安全研究者、系统管理员、下游项目（如 HardenedBSD）能够基于完整信息进行安全评估；这种透明性也使漏洞赏金计划与第三方安全审计成为可能——审计者知道哪些缓解已启用，可以聚焦于未覆盖的攻击面；**与 OpenBSD 的对比**：OpenBSD 长期通过 release notes 与多个手册页（如 **pledge(2)**、**unveil(2)**、**malloc.conf(3)**）分散披露其缓解机制，FreeBSD **mitigations(7)** 选择了集中化文档化路径，两者各有所长

**辨析**：需区分 **mitigations(7)** 与 HardenedBSD 项目：HardenedBSD 是 FreeBSD 的 fork，专注于更激进的漏洞缓解（如更严格的 ASLR、KARL 地址随机化、禁用 Intel SGX 等）；**mitigations(7)** 描述的是 FreeBSD base 系统自身的缓解机制，不直接涉及 HardenedBSD 的扩展；**13.x 周期 ASLR 默认启用**：13.2-RELEASE（2023-04-11）起对 64 位可执行文件默认启用 ASLR，但 32 位程序因地址空间限制未默认启用——这与 **mitigations(7)** 文档化时间（2023-09-08）接近，反映 13.x 周期安全加固与文档化的同步推进；**mitigations(7) 的工程意义**：手册页是一种“工程契约”——一旦文档化，缓解机制的存在与默认状态即成为公开承诺，未来移除或更改需要经过正式的 deprecation 流程；这与 sendmail→ **dma(8)** 迁移（14.0 才发生）的“减法”型架构现代化不同，**mitigations(7)** 是“加法”型文档现代化

## 150.14.6 sendmail 最后时代与 13.x 周期安全响应文化评估——被动响应期与工程稳态

**要点**：13.x 周期 FreeBSD Security Team 的 39 个 SA 在节奏上呈现“季度发布”特征——2021 年 4 个发布批次（4-8 月，10 个 SA）、2022 年 4 个发布批次（1-11 月，15 个 SA）、2023 年 5 个发布批次（2-10 月，14 个 SA），每批次 3-6 个 SA，反映“积累-集中披露”的工作节奏；**sendmail 在 13.x 全周期仍是默认 MTA**（13.0-13.4 均使用 sendmail 8.16.1/8.18.1），但 13.x 版本周期文件中未出现 sendmail 相关 CVE commit——sendmail 已进入“维护模式”，上游开发停滞，新 CVE 较少；sendmail 的安全风险更多是“配置错误”而非“代码漏洞”，这是 sendmail→ **dma(8)** 迁移发生在 14.0 而非 13.x 的工程考量之一；**与 14.x 周期对比**：13.x 周期 2.5 年内 39 个 SA，14.x 周期不足 3 年内 80 个 SA——14.x 周期 SA 密度约为 13.x 的 1.7 倍；剔除 14.x 周期 2026 年上半年的 49 个 SA（主动审计主题）后，13.x 与 14.x 周期 SA 密度接近，反映 13.x 周期是 Security Team 工作模式演进的“前主动审计期”

**史料**：**freebsd.duckdb** `tags` 表 freebsd-src 仓库 13.x 与 14.x 系列 SA 数量统计——基于本地 SA 存档目录 `原材料/研究/bsd漏洞史/官方公告/freebsd-sa.md` Grep 统计；FreeBSD Security Officer Team 历史成员名单（Gordon Tetlow、Ed Maste、Mark Johnston、Philip Paeps）；13.x 版本周期文件 `原材料/研究/bsd漏洞史/版本周期/freebsd-13.x.md` sendmail 相关 commit 查询：`SELECT count(*) FROM commits WHERE repo_name='freebsd-src' AND author_date>='2021-04-01' AND author_date<'2023-11-01' AND message_subject LIKE '%sendmail%' AND message_subject LIKE '%CVE-%'` 结果 0 条 ［A］

**史观**：总纲第 23 条——社区治理：13.x 周期 FreeBSD 安全响应文化呈现两个特征：① **“被动响应-季度披露”模式**——Security Team 主要响应外界报告与上游 CVE 通告，按季度集中发布 SA，未开展系统性主动审计；② **“贡献组件跟随上游”模式**——OpenSSL 1.1.1、OpenSSH、Heimdal、unbound、sqlite3、libarchive 等贡献组件的 CVE 修复主要通过 vendor import 同步上游，而非 FreeBSD 自行发现；这两个特征反映 13.x 周期 Security Team 资源相对有限，工作聚焦于“及时响应”而非“主动挖掘”；**sendmail 时代的尾声**：sendmail 在 13.x 全周期作为默认 MTA 未发生重大 CVE，但这不代表 sendmail 安全——sendmail 的复杂配置历史与 root 权限运行特性使其在 14.0 切换至 **dma(8)** 是合理工程决策；**13.x 周期作为“被动响应期”的工程意义**：13.x 周期是 Security Team 从“被动响应”向 14.x 周期“主动审计”过渡的中间阶段，**mitigations(7)** 文档化与 Heimdal 集中清理是这一过渡期的标志性事件

**辨析**：**数量对比的辨析**：13.x 周期 39 个 SA 与 14.x 周期 80 个 SA 的对比需考虑两个因素：其一，14.x 周期 base 系统引入了更多新子系统（bhyve 成熟、Capsicum 扩展、ktls、libcasper 等），新代码意味着新攻击面；其二，14.x 周期 Security Team 投入更多资源进行主动审计——SA 数量增长中相当部分来自主动审计而非外界报告，这是工程伦理的进步而非代码质量下降；**与 OpenBSD 对比**：OpenBSD errata 仍是逐版本（每年 2 个版本）发布，13.x 周期对应 OpenBSD 6.9-7.4 共 6 个版本，FreeBSD 13.x 单一 stable 分支 4 个 RELEASE 的 SA 数量已超过 OpenBSD 同时段 errata 数量——但这不意味着 FreeBSD 代码质量更差，而是 FreeBSD base 中包含更多第三方贡献组件（OpenBSD base 严格最小化）；**sendmail 安全史的辨析**：sendmail 在 13.x 周期未出现 CVE commit 不等于“sendmail 是安全的”——sendmail 历史上曾出现多个严重 CVE（如 CVE-2003-0694、CVE-2014-3951 等），13.x 周期“无 CVE”反映 sendmail 上游开发停滞而非代码质量提升；**dma(8) 在 13.x 中的修复**：2022-01-28 Ed Maste 提交 `647d3bf17cd907ded624dccf4fe4567924c4f399`、`eb32eb2b453d21534efaea4cfa17043a634e6199`、`1c91aedf25bce879a8aced6439200e46601eb8a4` 修复 CVE-2021-4034（**dma(8)** 中的 argc 校验问题），这是 **dma(8)** 在 13.x 周期作为可选 MTA 的安全修复，为 14.0 切换默认 MTA 做了铺垫
