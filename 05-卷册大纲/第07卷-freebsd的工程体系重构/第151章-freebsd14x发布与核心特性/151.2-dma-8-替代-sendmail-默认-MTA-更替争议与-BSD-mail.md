# 151.2 dma(8) 替代 sendmail——默认 MTA 更替争议与 BSD mail 系统演进

## 151.2.1 **dma(8)** 取代 sendmail 默认地位的工程决策

**要点**：FreeBSD 14.0 采用 **dma(8)**（DragonFly Mail Agent）作为默认 MTA，取代自 FreeBSD 1.0（甚至可追溯至 4.2BSD）以来持续近四十年的 sendmail 默认地位；**dma(8)** 是 DragonFly BSD 项目开发的轻量级 MTA，设计目标不是替代完整功能的 sendmail/postfix/exim，而是满足桌面/简单服务器场景的本地邮件投递与上游 SMTP 转发需求——即 “接受本地 MUA 提交的邮件并递送到本地或远程智能主机（smarthost）”；sendmail 并未从 base system 中移除，仍可通过 **mailer.conf(5)** 配置切换回 sendmail 作为默认；这一决策最早由 Baptiste Daroussin（巴蒂斯特·达鲁桑）（bapt@）在 freebsd-current 邮件列表提出讨论（约 2022-2023 年），理由包括：sendmail 配置复杂度远超普通用户需求、绝大多数 FreeBSD 安装不运行公开邮件服务器、OpenBSD 早已使用 smtpd、NetBSD 使用 postfix、DragonFly 使用 dma——FreeBSD 是最后一个仍以 sendmail 为默认的主流 BSD；**dma(8)** 代码量约为 sendmail 的十分之一，攻击面显著减小

**史料**：FreeBSD 14.0 Release Notes Userland 部分；Baptiste Daroussin dma(8) 导入 commit（cgit.freebsd.org/src/）；DragonFly BSD dma(8) 项目主页；freebsd-current@ 邮件列表 2022-2023 年 sendmail 替换讨论线程；mailer.conf(5) 手册页 ［A］

**史观**：总纲第 10 条——动手者创造历史：**dma(8)** 来自 DragonFly BSD——一个核心开发者长期仅个位数的 “边缘 BSD 分支”，却为整个 BSD 生态贡献了一个解决实际问题的工具；这印证了 BSD 生态中 “小项目解决大问题” 的传统：pf 来自 OpenBSD、HAMMER/HAMMER2 来自 DragonFly、pkg 来自 FreeBSD 自身但最初为独立项目——每个 BSD 分支的动手者都可能做出被整个生态采纳的创新

**辨析**：需澄清 “sendmail 被移除” 的误解——sendmail 在 14.0 中仍完整保留在 base system 中（包括 sendmail.cf 配置、makemap 等工具），只是默认 mailer.conf 指向 dma；这与 telnetd 在 14.0 中被完全移除（见 85.13）性质不同；**dma(8)** 不适合作为公开互联网邮件服务器的 MTA（缺乏完整 SMTP 中继、反垃圾邮件、邮件列表管理等功能），运行邮件服务器的用户仍需安装 postfix/exim 或切换回 sendmail——这一设计是有意的，dma 定位为 “默认满足 80% 场景，专业场景自行选择完整 MTA”

## 151.2.2 sendmail 默认地位的历史意义与社区反应

**要点**：sendmail 由 Eric Allman（埃里克·奥尔曼） 于 1979-1981 年在 BSD 上编写（最初为 delivermail，随 4.0BSD 1980 发布；sendmail 随 4.1cBSD 1983 发布），是互联网邮件系统的基石之一；FreeBSD 自项目创立即继承 sendmail 作为默认 MTA，这一传统延续了整整 30 年（1993-2023）；社区对 dma 替换的反应呈现两极分化：传统系统管理员群体中有人批评这是 “简化过度”、“抛弃 BSD 传统”，认为即使大多数用户不需要完整 MTA，sendmail 的存在本身是 BSD 作为服务器操作系统的标志；桌面与轻量级用户则普遍欢迎，认为 sendmail 配置是新用户的主要障碍之一；freebsd-current 讨论线程中最具说服力的论点来自 Colin Percival 与 Baptiste Daroussin：安全审计显示 sendmail 历史上有大量 CVE（仅 FreeBSD Security Advisory 中就有十余个 sendmail 相关 SA），代码复杂度高且默认配置的攻击面对大多数用户而言完全不必要

**史料**：Eric Allman sendmail 历史记述（sendmail.org 文档）；freebsd-current@ 2022-2023 年 dma 替换讨论线程（lists.freebsd.org/pipermail/freebsd-current/）；FreeBSD Security Advisories 中 sendmail 相关条目（FreeBSD-SA-xx: sendmail.* 系列）；Allman E. sendmail: An Internetwork Mail Router [C]. USENIX Conference Proceedings, 1983.

**史观**：总纲第 22 条——知识注定过时：sendmail 的退场不是技术优劣的简单判断，而是互联网使用模式变迁的结果——1980-1990 年代几乎每台 UNIX 主机都是邮件服务器，sendmail 的复杂性是必需的；2020 年代绝大多数 UNIX 主机不运行公开 SMTP 服务，本地邮件投递只需要一个简单的 MDA/MSA 而非完整 MTA；这一变迁反映了互联网架构从 “端到端对等” 到 “客户端-服务器集中化” 的宏观转变——sendmail 默认地位这一曾经的工程常识随实践变迁而过时，技术债务终成历史遗产

**辨析**：“1980 年代 80% 邮件服务器运行 sendmail” 是行业常用统计数字，但精确比例随年代变化很大（1990 年代中期可能达到 70-80%，2000 年代随 postfix/exim/qmail 兴起而下降）；Eric Allman 本人对 dma 替换未公开发表评论，他在 2010 年代后已基本退出 sendmail 活跃开发（Sendmail Inc. 被 Proofpoint 收购，2013 年）；需要注意：sendmail 的 m4 配置宏系统（sendmail.cf/mc 文件）被公认为 UNIX 系统管理中最复杂的配置系统之一，这也是推动替换的重要工程原因

**文献**：Allman E. Sendmail: An Internetwork Mail Router [C]. Proceedings of the USENIX Conference, 1983; Vixie P, Allman E, et al. sendmail: Theory and Practice [M]. Digital Press, 2000. ISBN 978-1-55558-210-9; FreeBSD Security Team. FreeBSD Security Advisories — sendmail [EB/OL]. [2026-07-19]. <https://www.freebsd.org/security/advisories/>.

## 151.2.3 其他 BSD 与 OS 默认 MTA 策略比较

**要点**：各 BSD 与开源 OS 的默认 MTA 策略演进：OpenBSD 于 4.6（2009 年）引入 OpenSMTPD（smtpd）并于此后逐步替换 sendmail 为默认；NetBSD 默认使用 postfix；DragonFly BSD 是 **dma(8)** 的发源地，默认使用 dma；Linux 各发行版差异较大——Debian 默认 exim4、Ubuntu 默认 postfix、RHEL/CentOS 默认 postfix、Arch Linux 无默认 MTA 需用户自选；macOS 以 postfix 为默认（但默认禁用 SMTP 监听）；Windows Server 无内置传统 MTA；FreeBSD 14.0 选择 dma 而非 postfix/OpenSMTPD 的考量包括：dma 代码量最小（约 3,000 行 C 代码 vs postfix 约 100,000 行）、与 BSD 许可证兼容、来自 DragonFly BSD 已有十余年生产使用历史、配置简单到无需配置文件即可工作

**史料**：各 BSD 项目 Release Notes MTA 部分；OpenSMTPD 项目历史（opensmtpd.org）；postfix 官方文档（postfix.org Wietse Venema 编写，最初为 IBM  secure mailer 项目 1998 年发布）；各 Linux 发行版 Release Notes 默认 MTA 记录 ［B］

**史观**：总纲第 8 条——本体论上各方平等：MTA 选择反映了各系统的设计哲学——OpenBSD 选择自己重写 smtpd 体现 “自己编写安全关键代码” 的 OpenBSD 哲学；NetBSD 选择 postfix 体现 “选择成熟第三方方案” 的实用主义；FreeBSD 选择 dma 体现 “base 只包含最小必要功能” 的小 base 哲学（专业用户通过 pkg 安装 postfix/exim）；这种分化不是 “谁更先进” 的竞争，而是不同工程哲学在同一问题域的多元呈现

**辨析**：OpenSMTPD 最初名为 OpenBSD smtpd，曾被多个 Linux 发行版采用，但 2015 年和 2020 年出现严重安全漏洞（包括 CVE-2020-7247 远程代码执行），导致部分发行版转而使用 postfix——这一事件是 FreeBSD 未选择 OpenSMTPD 的历史背景之一；**dma(8)** 因为设计上根本不支持公开 SMTP 中继功能（仅支持本地投递与 smarthost 转发），攻击面天然极小，安全风险显著低于完整 MTA

**文献**：OpenBSD Project. OpenSMTPD Documentation [EB/OL]. [2026-07-19]. <https://www.opensmtpd.org/>; Venema W. postfix Architecture Overview [EB/OL]. [2026-07-19]. <http://www.postfix.org/>; CVE-2020-7247: OpenSMTPD Remote Code Execution Vulnerability [EB/OL]. ## 151.2.4 MTA 更替史料辨析

**要点**：**dma(8)** 导入 FreeBSD base 的工程过程可追溯至：2022 年 Baptiste Daroussin 开始在 freebsd-current 测试 dma，2023 年初正式导入 ports（mail/dma）作为测试，2023 年中在 14.0-CURRENT 中导入 base 并设置为默认，经过 BETA/RC 阶段的测试与 bug 修复后于 2023.11 随 14.0-RELEASE 正式发布；导入 base 的 commit 由 Baptiste Daroussin 提交，Simon J. Gerraty（sjg@）、Ed Maste（埃德·马斯特）（emaste@）等参与代码评审；DragonFly BSD 的 **dma(8)** 最初由 Matthias Schmidt（<matthias@dragonflybsd.org>）于 2010 年前后开发，作为 DragonFly 替换 sendmail 计划的一部分，至 2023 年已有十余年稳定运行历史；**dma(8)** 在 FreeBSD 中的版本持续跟进 DragonFly 上游，但也有 FreeBSD 特定的修改（如 mailer.conf 集成、与 FreeBSD sendmail 路径兼容等）

**史料**：cgit.freebsd.org/src/ dma import commit（2023 年）；DragonFly BSD Git 仓库 dma 目录历史；Baptiste Daroussin 邮件列表 dma 状态更新 ［A］

**史观**：总纲第 13 条——法律与道德是利益分配：dma 采用 BSD 3-Clause 许可证，与 FreeBSD 完全兼容；这是 dma 能够被直接导入 base 而无许可证障碍的关键——如果 dma 是 GPL 许可，即使技术上更优也无法进入 FreeBSD base；许可证兼容性是 BSD base system 组件选择的硬性约束——许可证选择本质是法律框架下的利益分配结构，base 准入规则即该结构的直接体现

**辨析**：**dma(8)** 在 FreeBSD 14.0 中的具体版本号对应 DragonFly BSD 哪个版本未在 Release Notes 中明确记载，需通过源码树 vcs 历史追溯；邮件列表讨论中有用户提出 “dma 是否会与 port 版本冲突”——答案是 base_dma 与 mail/dma 设计为不冲突，base 版本安装在 /usr/libexec/dma 与 /usr/sbin/dma，port 版本通常安装在 /usr/local，通过 mailer.conf 切换
