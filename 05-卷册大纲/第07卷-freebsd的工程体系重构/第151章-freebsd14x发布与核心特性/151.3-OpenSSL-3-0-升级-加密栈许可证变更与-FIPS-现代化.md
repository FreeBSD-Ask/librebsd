# 151.3 OpenSSL 3.0 升级——加密栈许可证变更与 FIPS 现代化

## 151.3.1 OpenSSL 3.0 的技术与许可证变迁

**要点**：FreeBSD 14.0 将 base 系统中的 OpenSSL 从 1.1.1t 升级至 **3.0.12**，这是自 OpenSSL 1.1.0（2016 年）以来最重大的版本升级；OpenSSL 3.0.0 于 2021 年 9 月 7 日正式发布，最重要的变更是 **许可证从 OpenSSL 许可证（双重许可 OpenSSL/SSLeay，与 GPL 不兼容）变更为 Apache License 2.0**，彻底解决了困扰开源社区二十余年的 OpenSSL 许可证兼容性问题；3.0 系列引入了全新的 **provider 架构**——将加密算法实现从 libcrypto 核心中分离为可加载模块，包括 default provider（默认加密算法）、fips provider（FIPS 140 认证算法模块）、legacy provider（遗留算法如 MD2、RC4 等）；OpenSSL 1.1.1 系列于 2023 年 9 月 11 日正式 EOL（End of Life），14.0 及时跟进至 3.0 确保安全支持延续；14.0 还包含了 KTLS（内核 TLS）对 TLS 1.3 接收端卸载的支持（由 Netflix 赞助，John Baldwin（约翰·鲍德温） 与 John Baldwin 团队实现）

**史料**：OpenSSL 3.0 Release Notes（2021.9.7）；OpenSSL 3.0 License Change Announcement；FreeBSD 14.0 Release Notes “OpenSSL 3.0” 章节；OpenSSL Security Support Schedule（1.1.1 EOL 2023.9.11）；KTLS TLS 1.3 commit 05a1d0f5d7ac（Netflix 赞助标记） ［A］

**史观**：许可证：OpenSSL 许可证问题是 BSD 与 GPL 生态长达二十年的法律灰区——旧 OpenSSL 许可证（原 SSLeay 许可证 + OpenSSL 许可证的 “advertising clause”）与 GPL 不兼容，导致所有链接 OpenSSL 的 GPL 程序都需要特殊例外条款；Apache 2.0 许可证的采用彻底解决了这一问题，这一变化对整个开源生态的影响深远——包括 FreeBSD base 与 ports 中大量软件的版权声明简化

**辨析**：OpenSSL 3.0 的 FIPS provider 并非默认启用——FIPS 模式需要显式配置与安全策略激活，FreeBSD base 系统本身不持有 FIPS 140-2/140-3 认证，认证由各商业发行版（如 TrueNAS、pfSense 等基于 FreeBSD 的产品）自行申请；“FreeBSD 不持有 FIPS 认证” 是一个必须明确区分的事实——FreeBSD 作为社区项目不进行形式认证，但基于 FreeBSD 的商业产品可以使用 OpenSSL FIPS provider 配合自身的认证流程

[2026-07-19]. <https://www.openssl.org/blog/blog/2017/11/04/apache/>; NIST. Cryptographic Module Validation Program (CMVP)[EB/OL]. ## 151.3.2 KTLS TLS 1.3 与内核 TLS 卸载演进

**要点**：KTLS（Kernel TLS）最早由 Netflix 在 FreeBSD 10.x/11.x 时期引入并贡献，允许 TLS 记录层的对称加密/解密在内核中完成（通过直接在 socket 层处理加密，避免用户态-内核态数据拷贝），显著提升 TLS 吞吐量——Netflix 利用 KTLS 支撑其 CDN 每秒数 TB 级别的视频流量加密；14.0 之前 KTLS 已支持 TLS 1.0-1.2 的发送端（send）卸载，14.0 新增 **TLS 1.3 接收端（receive）卸载支持**（commit 05a1d0f5d7ac），意味着 KTLS 现在支持 TLS 1.0-1.3 的双向（发送 + 接收）加密卸载；KTLS 1.3 RX 卸载支持 AES-GCM 与 ChaCha20-Poly1305 套件，需要支持 AES-NI/ARM CE 等 CPU 加密指令以获得最佳性能；FreeBSD 是最早在内核中完整支持 TLS 1.3 卸载的通用操作系统之一（Linux 的 kTLS 在 4.13 引入，TLS 1.3 RX 支持在 Linux 5.x 跟进）

**史料**：Netflix KTLS 技术博客与 FreeBSD 提交记录（John Baldwin、Netflix 团队）；FreeBSD 14.0 Release Notes Kernel 部分；Baldwin J. KTLS Improvements in FreeBSD [C]. BSDCan 2023 演讲；ktls(4) 手册页

**史观**：边缘者贡献：KTLS 的故事是企业大规模用户反哺开源项目的典范——Netflix 作为全球最大的 FreeBSD 商业用户之一（其 CDN 服务器全部运行 FreeBSD），没有选择 fork 私有版本，而是持续将 KTLS 改进贡献回 FreeBSD 主线；这种 “自用即贡献” 模式与 GNU/Linux 生态中 Red Hat、Intel、Google 等大公司的内核贡献模式一致，但在 BSD 生态中 Netflix 是规模最大的持续企业贡献者

**辨析**：KTLS 与是否 “默认启用” 无关——KTLS 需要应用程序显式启用（通过 setsockopt 设置 TLS_TX/TLS_RX 选项），不会自动加密所有连接；OpenSSH 与大多数用户态 TLS 程序（如 curl、nginx 经由 port 安装）仍使用用户态 OpenSSL，除非专门配置使用 KTLS；Netflix 的 CDN 服务器使用自定义的 TLS 栈与 KTLS 集成

**文献**：Baldwin J. Kernel TLS in FreeBSD [C]. BSDCan 2018/2023 Presentations; Netflix Technology Blog. TLS in the FreeBSD Kernel [EB/OL]. (2018-2023)[2026-07-19]. <https://netflixtechblog.com/>; FreeBSD Project. ktls(4) Manual Page [EB/OL]. [2026-07-19]. <https://man.freebsd.org/ktls/4>.

## 151.3.3 OpenSSH 与系统安全工具链更新

**要点**：14.0 同时将 OpenSSH 更新至 **9.5p1**，重要变更包括：默认禁用 ssh-rsa SHA-1 公钥算法（SHA-1 密码学已不安全）、FIDO/U2F 硬件密钥支持（ecdsa-sk、ed25519-sk）、sshd_config 包含改进、sftp 服务器性能与安全增强；14.0 还包含多个安全加固：64 位平台默认 PIE+ASLR、Intel Alder Lake/Raptor Lake 混合架构页失效硬件 bug 修复（cde70e312c3f，FreeBSD Foundation 赞助）、libc stdio 缓冲区溢出修复（SA-23:15）、cap_net 权限修复（SA-23:16）；LLVM AddressSanitizer 可用于 amd64 内核（**kasan(9)**）

**史料**：FreeBSD 14.0 Release Notes Security Advisories 部分；OpenSSH 9.5 Release Notes；Intel Alder Lake page invalidation erratum 相关 commit；kasan(9) 手册页 ［A］

**史观**：开源运动：OpenSSH 版本的快速跟进（14.0: 9.5p1、14.1: 9.7p1、14.3: 9.9p2、14.4: 10.0p2 含后量子算法 mlkem768x25519-sha256 默认启用）反映了安全工具链在现代 OS 中的特殊地位——加密协议、SSH 版本、TLS 版本的跟进速度直接决定系统面对密码学攻击的防御能力，2020 年代后量子密码学（PQC）的快速标准化（NIST 2024 年发布首批后量子标准）推动各 OS 紧急跟进；14.4 默认启用混合后量子密钥交换是 FreeBSD 历史上首次在 SSH 中默认启用抗量子计算算法

**辨析**：OpenSSH 9.5 默认禁用 ssh-rsa 可能导致与老版本 SSH 客户端/服务器的连接问题——Release Notes 与 UPDATING 文件中有详细的兼容处理说明，用户仍可通过 HostKeyAlgorithms 配置手动启用 ssh-rsa 但不推荐；FIDO/U2F 支持需要 USB HID 设备与相应库，在 GENERIC 内核中已包含必要驱动但某些硬件可能需要额外固件

**文献**：OpenSSH Project. OpenSSH 9.5 Release Notes [EB/OL]. (2023-09)[2026-07-19]. <https://www.openssh.com/releasenotes.html>; NIST. Post-Quantum Cryptography Standards [EB/OL]. [2026-07-19]. <https://csrc.nist.gov/pqc-standardization>; FreeBSD Project. FreeBSD-SA-23:15.stdio [EB/OL]. ## 151.3.4 加密栈更新史料辨析

**要点**：OpenSSL 3.0 升级工作由 Ed Maste（埃德·马斯特）、Bryan Drewery（布莱恩·德鲁里）、Bernard Spil 等多位开发者协作完成，涉及 base 系统中所有链接 libcrypto 的库与工具的重新编译与测试；由于 OpenSSL 3.0 的 API 相对于 1.1 有若干废弃函数与变更，Ports 中大量软件需要补丁才能与 OpenSSL 3.0 兼容——这是 14.0 发布前 ports 冻结期较长的原因之一；OpenSSL 1.1.1 作为 FreeBSD 12.x/13.x 的默认版本，在 13.x 周期内通过 backport 安全补丁持续维护至 13.x EOL；OpenSSL 3.0 的长期支持（LTS）版本，官方支持至 2026 年 9 月（但会扩展，类似 1.1.1 延长支持）

**史料**：FreeBSD base OpenSSL 3.0 迁移 commit 系列；Ports Collection OpenSSL 3.0 跟踪 PR；OpenSSL Release Schedule（openssl.org/policies/releasestrat.html） ［A］

**史观**：软件工程：OpenSSL 大版本升级是 base system 维护中风险最高的变更之一——libcrypto 被几乎所有涉及网络的基础程序链接（ssh、telnet、fetch、pkg、证书工具、KTLS 等），任何 API 不兼容都可能导致系统级故障；FreeBSD 采用 “大版本边界升级” 策略（14.0 升级 3.0，13.x 保持 1.1.1）而非 “滚动升级”，是为了避免在 STABLE 分支中引入此类高风险变更

**辨析**：vendor import OpenSSL 到 FreeBSD base 的过程采用了与 OpenZFS 类似的 vendor branch 策略（在 crypto/openssl 目录下维护与上游对齐的代码，本地修改通过 svn2git/vendor 分支管理）；OpenSSL 3.0 在 FreeBSD 14.0 发布时的精确版本为 3.0.12，14.1 跟进至 3.0.x 更新版本（随 14.1 OpenSSH 9.7p1 同步）
