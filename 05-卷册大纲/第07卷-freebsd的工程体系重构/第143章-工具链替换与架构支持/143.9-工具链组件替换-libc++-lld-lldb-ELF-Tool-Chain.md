# 143.9 工具链组件替换：libc++、lld、lldb、ELF Tool Chain

## 143.9.1 libc++ 与 libcxxrt：C++ 标准库的 BSD 化

**要点**：GCC 4.2.1 携带的 libstdc++ 版本过老，完全不支持 C++11 标准（2011 年发布），这是 Clang 迁移必须解决的 C++ 标准库问题。David Chisnall（戴维·奇斯纳尔）（theraven@）主导了 BSD 许可的 C++ 标准栈在 FreeBSD 中的引入：libc++（LLVM 项目的 C++ 标准库实现，MIT/UIUC 双许可）与 libcxxrt（BSD 许可的 C++ 运行时 ABI 层，由 PathScale 开发后被 FreeBSD 采纳）组合提供完整的 BSD 许可 C++ 支持。FreeBSD 9.1（2012.12.30）将 libc+++libcxxrt 作为可选 C++11 栈引入（Q1 2012 状态报告记录了 David Chisnall 的工作），FreeBSD 10.0（2014.1.20）正式将其设为默认 C++ 标准库。libc++ 提供完整的 C++11/14/17/20 标准支持，解决了 GCC 4.2.1/libstdc++ 冻结导致的 C++ 生态停滞问题。xlocale 实现（libc++ 依赖的本地化扩展）由 Chisnall 同步完成。

**史料**：FreeBSD 9.1/10.0 Release Notes、FreeBSD Quarterly Status Report 2012 Q1（GNU-Free C++11 Stack 条目，联系人 David Chisnall）、libc++ 官方文档（libcxx.llvm.org）、libcxxrt 项目页面。 ［B］

**史观**：总纲第 17 条——软件工程：C++ 标准库替换比编译器替换风险更高——C++ 库 ABI 兼容性问题可能导致所有 C++ 程序需要重新编译，因此 FreeBSD 采取了 “可选 → 默认” 的两阶段策略（9.1 可选，10.0 默认），为 ports 生态预留了约两年适配期。David Chisnall 的工作是 Clang 迁移不可或缺的组成部分——仅有编译器没有配套的 BSD 许可 C++ 库，迁移无法完成。

**辨析**：libc++ 与 libstdc++ 的 ABI 不兼容是迁移中最大的技术挑战之一——使用 libstdc++ 编译的 C++ 程序无法直接链接使用 libc++ 编译的库，反之亦然。FreeBSD 10.0 之后的混合过渡期中，ports 中部分 C++ 库仍依赖 libstdc++，通过 ports 中的 gcc 编译器和 libstdc++ 兼容包解决。

**文献**：FreeBSD 9.1/10.0 Release Notes [Z]；Chisnall D. GNU-Free C++11 Stack entry in FreeBSD Quarterly Status Report [R]. 2012 Q1；LLVM Project. libc++ C++ Standard Library [EB/OL]. libcxx.llvm.org.［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

## 143.9.2 lld 链接器替换 GNU ld

**要点**：LLVM 项目的 lld 链接器是 Clang/LLVM 工具链替换 GNU ld（GNU binutils 一部分，GPLv3 许可）的关键组件。lld 设计目标是高速、兼容 GNU ld 命令行选项、原生支持 LTO（Link-Time Optimization）。FreeBSD 12.0（2018.12）将 lld 设为 amd64、i386、armv7 架构的默认 bootstrap linker（提交 r334391、r336901、r337057），后续版本将 lld 扩展到所有支持架构。lld 的链接速度相比 GNU ld 有数量级提升（尤其在大型项目 LTO 构建时），这对 FreeBSD 本身的构建速度（buildworld/buildkernel）和 ports 中大型软件（如 Chromium、LLVM 自身）的编译速度有显著改善。

**史料**：FreeBSD 12.0 Release Notes（Userland Application Changes: "The default bootstrap linker has been changed to ld.lld(1) for amd64/i386/armv7"，r334391/r336901/r337057 引用）、lld 官方文档（lld.llvm.org）、Rafael Espíndola（lld 主要作者）等关于 lld 设计的演讲。 ［B］

**史观**：软件工程：链接器是工具链中最保守的组件（因为其 bug 可能导致所有程序失效），lld 从实验到默认用了更长时间（比 Clang 编译器晚约四年）。FreeBSD 作为最早大规模采用 lld 作为系统链接器的主流操作系统之一，为 lld 的成熟提供了重要的真实世界测试。

**辨析**：lld 在 FreeBSD 12.0 中是 “bootstrap linker”（构建世界/内核时使用的链接器），GNU ld 在 base 中仍保留一段时间以支持旧架构和特殊需求；完全移除 GNU ld 的过程持续到后续版本。

**文献**：FreeBSD 12.0-RELEASE Release Notes [Z]. 2018-12；LLVM Project. The LLVM Linker (lld)[EB/OL]. lld.llvm.org；SVN commits r334391, r336901, r337057 [Z]. svn.freebsd.org. ［A］

## 143.9.3 lldb 调试器替换 GDB

**要点**：GDB（GNU Project Debugger）是 GPLv3 许可的调试器，是许可证纯洁化工程需要替换的另一个核心工具。LLDB 是 LLVM 项目的调试器，与 Clang/LLVM 紧密集成，支持 Clang AST 解析表达式、与 Clang 编译器共享代码生成基础设施。FreeBSD 12.0（2018.12）对 GDB 做出重大调整：传统 base 系统中的 **gdb(1)** 被移至 `/usr/libexec/gdb`，仅供 **crashinfo(8)** 内核崩溃调试使用，不再作为默认交互式调试器安装；gdbserver 和 gdbtui 不再安装。官方推荐用户使用 **lldb(1)** 进行交互式调试，或从 ports/devel/gdb 安装现代版本 GDB。这一调整标志着 FreeBSD base 系统调试器从 GDB 向 LLDB 的战略转移。

**史料**：FreeBSD 12.0 Release Notes（Userland Application Changes: "The legacy gdb(1) utility included in the base system is now installed to /usr/libexec for use with crashinfo(8). The gdbserver and gdbtui utilities are no longer installed."，r317416 引用）、LLDB 官方文档（lldb.llvm.org）。 ［B］
    FreeBSD 社区论文：[FP-2024-001] LLDB FreeBSD Kernel Module Improvement（Sheng-Yi Hong，2024）<https://papers.freebsd.org/2024/asiabsdcon/hong-lldb-freebsd-kernel-module-improvement/>

**史观**：软件工程：调试器切换比编译器切换面临更多用户习惯阻力——GDB 的命令集和脚本生态已积累数十年，LLDB 虽然提供了 GDB 命令兼容模式但老用户迁移存在学习成本。FreeBSD 采取 “移除非交互使用、保留 crashinfo 用途” 的渐进策略降低冲击。

**辨析**：FreeBSD 12 时 LLDB 的 C++ 调试体验（尤其是模板、多线程、STL 容器漂亮打印）相比现代 GDB 仍有差距，这也是为什么 base 保留 gdb（虽然移到 libexec）且 ports/devel/gdb 持续维护的原因。

**文献**：FreeBSD 12.0-RELEASE Release Notes [Z]. 2018-12；LLVM Project. The LLDB Debugger [EB/OL]. lldb.llvm.org；SVN commit r317416 [Z]. svn.freebsd.org. ［A］
    FreeBSD 社区论文与演讲 [316]，[316] Sheng-Yi Hong. LLDB FreeBSD Kernel Module Improvement [C]//AsiaBSDCon 2024. [S.l.]: [s.n.], 2024. 获取路径：<https://papers.freebsd.org/2024/asiabsdcon/hong-lldb-freebsd-kernel-module-improvement/> [访问日期 2026-07-26].

## 143.9.4 ELF Tool Chain 项目与 binutils 替换

**要点**：GNU binutils 是一组二进制工具集（**ar(1)**、**as(1)**、**ld(1)**、**objdump(1)**、**ranlib(1)**、**nm(1)**、**readelf(1)**、**size(1)**、**strings(1)**、**strip(1)** 等），均为 GPLv3 许可。FreeBSD 许可证纯洁化工程使用 ELF Tool Chain 项目（BSD 许可）和 LLVM 工具链共同替代 GNU binutils。ELF Tool Chain 项目起源于 Elfutils 替代需求，提供 **ar(1)**、**ranlib(1)**、**readelf(1)**、**objdump(1)**、**nm(1)**、**size(1)**、**strings(1)**、**strip(1)** 等 BSD 许可实现；**as(1)**（汇编器）则主要由 LLVM 的集成汇编器（LLVM integrated assembler，Clang 直接输出目标文件无需外部汇编器）和 LLVM **llvm-mc(1)** 替代。FreeBSD 12.0 将 ELF Tool Chain 更新至 r3614（r333063）。binutils 替换是一个渐进过程——部分工具（如 gas 的某些旧架构特性）在非 Tier 1 架构上仍需要外部 binutils 支持。

**史料**：FreeBSD 12.0 Release Notes（Contributed Software: “The ELF Tool Chain has been updated to version r3614”，r333063 引用）、ELF Tool Chain 项目官方站点（elftoolchain.sourceforge.io）、LLVM 集成汇编器文档。［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］ 〔L3 官方文档〕

**史观**：总纲第 17 条——软件工程：二进制工具（特别是汇编器）是工具链中最底层、最依赖架构的部分，替换难度大。Clang 的 “集成汇编器” 设计（编译器直接输出目标文件，不依赖外部 `as`）是解决汇编器替换的聪明方案——不需要编写完整的多架构汇编器，因为 Clang 直接从 AST 生成机器码。

**辨析**：ELF Tool Chain 项目并非 FreeBSD 专属，它是一个独立的 BSD 许可 ELF 工具项目，FreeBSD 是其主要用户和贡献者之一。某些特殊工具（如 **addr2line(1)**、**objcopy(1)**）的 BSD 替代时间线需逐工具核实，部分工具在较晚版本才完成替换。

**文献**：FreeBSD 12.0-RELEASE Release Notes [Z]. 2018-12；ELF Tool Chain Project [EB/OL]. elftoolchain.sourceforge.io；SVN commit r333063 [Z]. svn.freebsd.org. ［A］

- 此前的主要障碍符号版本支持与链接脚本表达式求值已接近完成，BSDCan 上 LLD 已能编译并启动 FreeBSD 内核。（BSD Now EP156，[3380.74-3510.98]，L2）
- DigitalOcean 教程以 MFSBSD 制作 tarball 覆盖运行系统，实现从 UFS droplet 到 ZFS 的全新安装。（BSD Now EP156，[3525.66-3660.0]，L2）
- Piotr Kubaj 在 LibreBoot 邮件列表报告其 Lenovo X200 成功启动 FreeBSD 11.0 RC1 与 OpenBSD 安装器。（BSD Now EP156，[3803.62-3945.0]，L2）
- TeachBSD 源于 gnn（George Neville-Neil）与 Robert Watson 数年前的共识：操作系统教材应以开源方式发布，教师拿到现成材料便更可能采用；其目标一是让 BSD 回到大学以补充新开发者，二是以 FreeBSD 的实际创新辅助教学，已形成剑桥研究生课与面向从业者的两天实践课两套材料，托管于 GitHub 的 teachbsd 组织并接受补丁。　[存疑脚注] 转写将受访者名录为“George Temple Neal”，当为 George Neville-Neil（gnn），本卡按后者著录。（BSD Now EP136，[1831.20-1974.90]，L1）
- gnn 批判三种操作系统教学路径：把数百万行真实代码直接交给本科生的“火线试炼”（trial by fire）、缺失异步与真实负载的玩具系统、以及只读论文写综述的研讨式；他与 Watson 的替代方案是利用 DTrace 的安全性与全景可见性，让学生在真实内核上运行实验，避免新手在无内存保护的单地址空间内核中因一次修改即崩溃而无所适从。（BSD Now EP136，[2035.50-2216.20]，L1）
- WhatsApp 于 2016 年 4 月为约十亿用户全量启用基于 Signal 协议（Open Whisper Systems）的端到端加密，其服务器运行 FreeBSD，据称仅约 50 名工程师支撑全部服务，约 15 人团队完成跨 iOS、Android、Windows Phone 乃至旧款诺基亚与黑莓的平台覆盖；身份核验沿用类 GPG 密钥签名聚会的 QR 码与数字串当面比对，加密之外还须解决“对方是谁”的证明问题。　[存疑脚注] 转写将协议作者名录为“Moxie Merlin Spike”，当为 Moxie Marlinspike。（BSD Now EP136，[1288.74-1424.48]，L2）
- Ed Maste 在致 LLVM 邮件列表的报告中自述“现在能用 LLD 作为 buildworld 的链接器构建出可运行的 FreeBSD 系统”，仅需少量绕行补丁，产出系统可登录并通过基本健全性测试，内核仍以 LD.BFD 链接；符号版本化、内核链接脚本与 -N 等旗标仍是缺口，LLVM 侧视 FreeBSD 为有望首个以 LLD 完整构建的操作系统——这是替换 GNU 链接器进程在 2016 年的端到端里程碑。　[存疑脚注] 转写作“Ed Mast”，当为 FreeBSD 开发者 Ed Maste。（BSD Now EP136，[978.62-995.12]，L1）
- 两位当事人界定 Clang 与 LLVM 的分工：LLVM 是编译器后端，可承载自有语言与即时编译，Apple 即用它把 OpenGL 表达式现场编译为 SSE2、SSE3 指令以提升性能；Clang 则是 C、C++ 与 Objective-C 的前端解析器，借助 LLVM 生成最终二进制。（BSDTalk EP191，[149.68-210.42]，L1）
- 迁移进行时的实测状态：clangbsd 分支在 amd64 上已可完成 make buildworld 且结果可用，内核构建已稳定运作逾一年，Ed Schouten 自述已有约九个月不用 GCC 构建内核；代码质量约与老旧的 GCC 4.2 相当而尚不及 GCC 4.4、4.5，i386 的残余问题正在会议现场修复，开发者峰会已决议约两周内导入 head。（BSDTalk EP191，[211.42-293.38]，L1）
- 选择 Clang 的理由被概括为：速度快、对用户友好、生成代码质量可与 GCC 比肩、开发活跃，且不受 GCC 所携带的许可证问题困扰；开发者峰会决定其将以 Intel 架构随 FreeBSD 9 默认发布。（BSDTalk EP191，[106.60-135.68]，L1）
- 导入并非终点而是负担的起点：目前仅有五到十人测试 clangbsd 分支，进入 head 后全员测试将带来 bug 报告潮——Clang 产生的警告远多于现有 GCC，代码库并不干净；同时必须紧贴上游，重要修复即便一周两次也要导入，长期滞留同一版本会让 LLVM 开发者无从判断某 bug 是否已在现行代码中修复。（BSDTalk EP191，[584.98-692.94]，L1）
- 关于治理机制，当事人评价开发峰会不解决技术问题，却切实推动政治与决策：clang 导入的决定若非此前专门讨论工具链的峰会便不会发生；同类先例是 vimage 代码在 perforce 中搁置多年，峰会上一旦拍板即整组进入 SVN，表明集体决策场合能把长期僵持的工程变成现实。（BSDTalk EP191，[477.06-565.30]，L1）
- FreeBSD 对 Clang 的采用始于 2009 年 2 月 Roman 与 Pavel 的构建实验，当时距 GPLv2 版 GCC 最后一次发布已近两年；实验迅速达到可编译内核并引导的程度，随即在 LLVM Bugzilla 开设元缺陷 PR2696 追踪全部阻塞项。2010 年 1 月 Clang 实现自举，距 2006 年 C 解析器入库约三年半，且依赖 Apple 与 Google 的全职投入；同年 9 月可构建全部基础系统，2011 年 5 月元缺陷关闭、x86-64 上以标准优化级别完成全量编译。此后 9.0 将 Clang 列为可选编译器，10-CURRENT 使其成为 tier-1 架构默认编译器并以 libc++ 与 libcxxrt 取代 GNU C++ 栈。（BSDTalk EP233，[706.77-841.00]，L1）
- 编译器切换的收尾长尾集中在调试端：Clang 默认输出 Dwarf 4，而基础系统 GDB 仅支持 Dwarf 2，ports 中的 GDB 虽支持 Dwarf 4 却属 GPLv3，以旧 GDB 调试 Clang 代码时行号时有时无、断点失效、变量列表错乱乃至解析器崩溃。Ed 移植源自 Apple 的 LLDB，彼时支持 AMD64 单线程活调试、多线程近于完成、核心转储可用，32 位与 MIPS 尚未支持，内核调试器集成被排在最后；FreeBSD Foundation 另拟资助以 Capsicum 将调试器沙箱化，以应对被调试程序元数据损坏或恶意输入对调试器本身的攻击面。（BSDTalk EP233，[3591.80-3765.87]，L1）
- 受访者介绍 libelf 为 SVR4 ELF API（GABI）的实现（转写中该标准名称有失真）：一个支持跨平台、跨架构读写 ELF 文件的低层库，处理大小端字节交换与面向目标架构的 ELF 布局。其直接动因是为 FreeBSD 的 PMC 性能工具项目实现跨架构剖析——在一台机器上分析另一架构收集的性能数据必须解析可执行文件；他不欲再添一个临时实现，转而寻找标准 API，未发现 BSD 许可的现成库，遂自行实现该 API。树中其他工具可借之清理代码，DTrace 移植工作亦从中受益，属计划外的收获。　[存疑脚注] 转写将所实现的 API 名称记作 System 5.0.3 与 GL3，疑为 System V Release 4/GABI 之失真，待核。（BSDTalk EP87，[93.02-312.78]，L1）
- 受访者解释 ELF（Extensible Linking Format）取代 a.out 的缘由：ELF 是目标文件格式，编译产物为含有链接器组装可执行文件所需附加信息的可重定位对象；相比旧格式，ELF 更好地支持动态链接等现代操作系统特性，因此各主要 UNIX 以及所有使用 GNU 工具链的开源系统均已或终将迁移至 ELF。（BSDTalk EP87，[127.1-206.62]，L1）
- 关于与 GNU 工具链的关系：libelf 定位于 binutils 中最底层的 libbfd（binary file descriptor）库的某种替代。受访者判断 nm、strip 等二进制操作工具当日即可改用 libelf 编写，而 ld 的困难不在 ELF 格式本身而在其功能复杂度；他暂无立即替换 GNU 工具链其他部分的计划，但该方向保持开放。（BSDTalk EP87，[206.62-231.86]，L1）
- 受访者陈述完成度与实现差异问题：大部分 API 已实现并自评功能完备但仍可能有 bug，测试随代码同步编写；API 本身在 Sun 的手册页中文档化良好，但存在实现层面的特殊行为与未指定行为，从 Solaris 移植代码（如 John 所做的 DTrace 工作）时会逐一暴露并增量修复；测试覆盖 i386、AMD64 与 sparc 等其拥有硬件的架构，项目基本可用。（BSDTalk EP87，[328.14-390.62]，L1）

**史观**：

- 总纲9 经验优先：工具链组件以“能链接未修改内核”为切换门槛，经验验证先于宣告。（BSD Now EP156，[3438.72-3510.98]，L2）
- 总纲22 知识注定过时：链接器的替换逐项清除障碍，工具链持续更替，旧知识随架构演进而过时。（BSD Now EP156，[3380.74-3510.98]，L2）
- 总纲10 动手者创造历史：在研究生课第三部分，学生用 DTrace 追踪 TCP 状态、亲手推导 TCP 状态机图并撰写实验报告；gnn 强调学生操作的是与 Netflix、NetApp、Juniper 及 PlayStation 4 生产环境同源的真实系统工件，动手实验使学习者从课堂听众转变为与生产实践同构的操作者。　[存疑脚注] 转写将生产环境首例名录为“Iceland”，结合语境当为 Netflix。（BSD Now EP136，[2242.70-2287.94]，L1）
- 总纲5 没有必然性，只有偶然性：WhatsApp 全量加密的最终促成契机，据当期转述并非路线图排期，而是一位不在 WhatsApp 工作的亲缘者的一次家庭团聚；重大工程节点的落定常系于此类偶发人际事件，技术史叙述宜为偶然性保留位置，而非将其化约为组织意图的必然产物。（BSD Now EP136，[1496.50-1513.16]，L2）
- 总纲3 不存在进步，只有权力再分配：从 GCC 到 Clang 的迁移并不构成编译器技术线性进步的叙事——当事人承认 Clang 尚不及新版本 GCC——其真正驱动力是许可证权力结构的再分配：摆脱 GCC 附带的许可证问题，才是工具链权力易手的枢纽。（BSDTalk EP191，[135.68-142.68]，L1）
- 总纲5 没有必然性，只有偶然性：两位当事人进入 FreeBSD 的路径纯属偶然：Roman Divácký 做了半年 Linux 用户后由高中同学递来一张安装 CD 从此停留；Ed Schouten 则因 Eindhoven 大学全楼唯一有无线网的地方是 Unix 用户组而入会，再被周围同城的 FreeBSD 开发者劝动转用并开始提交补丁。宏大的工具链迁移正是由这类偶然个人轨迹汇聚而成。（BSDTalk EP191，[856.42-936.88]，L1）
- 总纲13 法律与道德是利益分配：许可证决策在叙述中呈现为利益与风险的分配而非技术优劣的裁决：FreeBSD 阵营对 GPLv2 予以容忍、却以‘never’级别的决心拒绝 GPLv3 进入基础系统，理由不在代码质量而在法律边界与依赖失控的担忧；Chisnall 又以自己参与 GNU 项目时 LGPLv2 升级 v3 遭遇唯一开源 PDF 渲染库为 GPLv2-only 的冲突、被迫回退的亲历，说明许可证版本切换实为生态利益格局的重新切割；宽松许可的价值则被表述为让律师替你思考法律问题、从而解放开发者专注于代码。（BSDTalk EP233，[303.27-390.49]，L1）
- 总纲5 没有必然性，只有偶然性：跨平台移植中暴露的调用约定差异被当事人解读为无对错可言的历史承袭：i386 结构返回惯例上 Linux 沿 DOS 时代的做法经指针间接传递，FreeBSD 则承袭 VAX 的寄存器返回路径，且当事人明言双方都并非出于正确理由；FreeBSD、Linux 与 OS X 对向量参数的传递方式亦各不相同。系统接口差异的成因是偶然的路径依赖，而非任何一方的必然优越。（BSDTalk EP233，[1042.59-1082.11]，L1）
- 总纲19 解释学循环是历史认识的根本条件：C++ 两阶段名字查找的兼容性案例显示规范文本与实现之间的解释学循环：GCC 依其理解先行实现而与后来澄清的语义相悖，微软编译器以另一种方式同样做错，致跨两家编译器的模板代码无从适配；Clang 因晚出生约十年得以从各方错误中反推规范本意而实现正确，C++ 标准委员会又经 C++03 澄清与后续技术报告反复改口。标准是经实现碰撞而被反复重读的形式约定，而非一次写定的真理。（BSDTalk EP233，[1712.33-1771.59]，L1）
- 总纲5 没有必然性，只有偶然性：受访者的社区轨迹系于一次偶然的正反馈：1996 年那枚以太网驱动补丁被 David Greenman 提交入库后，他自述从此入迷，持续投递补丁直至获得 commit bit。长期贡献的起点并非规划，而是一枚补丁被承认的偶然事件。（BSDTalk EP87，[437.58-448.22]，L1）

**辨析**：

- [存疑脚注] LLD 里程碑与切换计划为节目转述 Ed Maste 博客，具体落地时间须以 FreeBSD 12 开发记录为准。　[存疑脚注] 计划性披露，须与开发记录核验。（BSD Now EP156，[3427.38-3510.98]，L4）
- 微软收购 FreeBSD 愚人节假新闻的笑点恰在于暴露真实误解：FreeBSD 基金会并不拥有源码仓库，仓库由 FreeBSD 项目自身维护，基金会仅作为持有商标、签署合同所需的单一法律实体，而项目是约千名贡献者的松散集合；OpenBSD 与 NetBSD 亦绝非 FreeBSD 的“子品牌”，三者法律与谱系上各自独立。（BSD Now EP136，[4058.62-4115.20]，L2）
- GCC 兼容有其内在限度：Clang 力求兼容 GCC 语言扩展以服务 Apple 等大客户，但 C89 与 C99 的 inline 关键字语义冲突无法弥合，多维变长数组因语义不明而不实现，嵌套函数亦不支持的破坏已在 ports 中显现；反过来，port manager 跑动的 ports 构建与两万余个软件包构成扩展实际使用情况的证据库，可反哺 Clang 团队决定实现哪些扩展。　[存疑脚注] 转写将 port manager 人名呈为 Aaron Lansing，依语境辨正为 Erwin Lansing，建议核对原始音频。（BSDTalk EP191，[707.74-856.42]，L1）
- 演讲对 PCC 与 GCC 的评价带论战色彩，需与其他来源交叉验证：PCC 网页曾宣称 C++ 支持易于实现，而当事人指出 C++ 解析在一般情形下是不可计算问题、Clang 自举即耗时三年半并依赖 Apple 与 Google 的全职人力，故该宣称不足为凭；对 GCC 4.2.1 代码质量的贬抑亦系个人观感，其自陈因许可证原因从未阅读 GPLv3 代码，所评实为旧版。　[考据脚注] 对 PCC 与 GCC 的评价为当事人单方论战性叙述，PCC 网页宣称的具体时间与措辞、GCC 4.2.1 代码质量判断均需与两项目社区自身文献交叉核验。（BSDTalk EP233，[501.97-530.29]，L1）
- 以 Phoronix 基准中 FreeBSD 唯一显著落后一项为例，当事人将其归因于 Clang 当时缺失 OpenMP 支持而 GCC 内置 GNU OpenMP 库，并引 Intel 向 LLVM 捐赠 OpenMP 运行时为解决路径，预计 10.1 至 10.2 具备支持；该解释属单一来源对第三方基准的归因，且 HPC 用户通常不使用系统编译器，基准对公众认知的影响大于对实际工程的影响。　[存疑脚注] FreeBSD 在该基准中落后约 8 倍的归因仅为当事人解释，需对照 Phoronix 原始测试数据与当时 Clang/GCC 的 OpenMP 支持状态独立验证。（BSDTalk EP233，[3329.75-3394.84]，L4）
- 许可证在此不是偏好而是工程约束：受访者明言希望工具进入 base system，而纳入 base 必须采用 BSD 许可，且愈彻底愈好。他进一步提出结构性主张——若要构建 BSD 许可的工具链，须以跨 BSD 的协作项目方式完成方能惠及所有项目，并欢迎 libelf 成熟后移植到其他 BSD。个体工程动机与跨项目公共品供给在其陈述中合为一体。（BSDTalk EP87，[312.78-324.7]，L1）
