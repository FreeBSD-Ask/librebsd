# 143.10 各架构 Clang 支持与 arm64/AArch64 到来

## 143.10.1 i386/amd64：首批完成 Clang 迁移的架构

**要点**：i386 和 amd64（x86）是 Clang/LLVM 最早支持且最成熟的架构，也是 FreeBSD 首批完成 Clang 迁移的架构。Roman Divacky 于 2009 年 2 月宣布 Clang 可编译可启动的 i386/amd64 内核；FreeBSD 9.0（2012）中 i386/amd64 world 和 GENERIC 内核已可完整使用 Clang 构建；2012 年 11 月 Brooks Davis 在 -CURRENT 中切换 Clang 为 x86 默认编译器；FreeBSD 10.0（2014.1.20）正式在 RELEASE 版本中将 Clang 设为 i386/amd64 默认且不再默认安装 GCC。x86 架构的 Clang 支持成熟得益于 Apple 的长期投入——macOS/iOS 均运行在 x86（及后续 Apple Silicon）上，Clang x86 后端是优化最好、测试最充分的后端之一。

## 143.10.2 arm64/AArch64：Andrew Turner 与原生 Clang 支持

**要点**：arm64（AArch64）架构在 FreeBSD 中的支持是 Clang/LLVM 迁移的重要副产品——GCC 4.2.1 完全不支持 AArch64（ARM 64 位架构在 2011 年才发布，远晚于 GCC 4.2.1 的 2007 年），因此没有 Clang 就不可能有 FreeBSD/arm64。Andrew Turner（andrew@）是 FreeBSD/arm64 移植的主要开发者，在 FreeBSD Foundation 和商业赞助商支持下完成了 arm64 支持。FreeBSD 11.0（2016.10.10）首次将 arm64 作为支持架构发布（但非 Tier 1）；FreeBSD 13.0（2021.4.13）正式将 arm64/AArch64 提升为 Tier 1 架构，与 amd64 并列获得发布镜像、二进制包、安全更新的全面支持。Clang/LLVM 对 AArch64 的原生支持（AArch64 后端由 ARM 公司和 Apple 工程师联合开发，质量极高）使 FreeBSD/arm64 从一开始就有高质量编译器支持——这与 mips/powerpc/sparc64 等旧架构在 Clang 迁移中挣扎形成鲜明对比。arm64 升为 Tier 1 标志着 FreeBSD 正式进入 64 位 ARM 服务器、云原生和嵌入式市场。

**史料**：FreeBSD 11.0/13.0 Release Notes 和 Announcement、Andrew Turner arm64 移植邮件列表公告和提交记录、FreeBSD Quarterly Status Reports arm64 章节、FreeBSD 架构支持级别页面。 ［A］

**史观**：总纲第 5 条——没有必然性，只有偶然性：Clang 原生支持 AArch64 的事实使 FreeBSD 在 ARM64 时代获得了相对于旧 GCC 生态的架构优势——新架构不必等待旧编译器（GCC 4.2.1）的移植，因为 Clang/LLVM 本身就原生支持 AArch64。这是许可证纯洁化工程的意外正面红利：摆脱了古老 GCC 的束缚后，FreeBSD 得以更快拥抱新硬件架构。

**辨析**：FreeBSD/arm（32 位 ARMv6/v7）的 Clang 支持早于 arm64，但 32 位 ARM 生态碎片化（大量不同 SoC）使其从未升为 Tier 1；arm64 因 ARM 服务器标准化（SBSA/SBBR 规范）和 Apple Silicon Mac 的推动而快速成熟。FreeBSD 13 arm64 Tier 1 后，Amazon EC2 Graviton、Ampere Altra 等 ARM 云实例正式支持 FreeBSD。

**文献**：FreeBSD 11.0-RELEASE Announcement [Z]. 2016-10-10；FreeBSD 13.0-RELEASE Announcement [Z]. 2021-04-13；Turner A. FreeBSD/arm64 status reports and commits [Z]. 2014-2021. ［A］

## 143.10.3 其他架构：powerpc/mips/sparc64/arm 的 Clang 支持

**要点**：powerpc、mips、sparc64 等旧架构的 Clang 支持远落后于 x86 和 arm64，是 GCC 4.2.1 在 FreeBSD base 中保留多年的主要原因。powerpc（32 位和 64 位 powerpc64）的 Clang 支持在 FreeBSD 11/12 时期逐步完善，但在某些 powerpc 变体上仍有问题；mips 架构因 MIPS 公司转向 RISC-V 和 MIPS 设计本身的复杂性（多种 ABI、尾码、原子操作模型），Clang 支持长期不完善；sparc64（Sun/Oracle SPARC 64 位）的 Clang 支持进展最慢，且 SPARC 硬件市场在 Oracle 收购 Sun 后急剧萎缩。这些架构的支持路径分三种：①Clang 支持逐步完善后切换（如 powerpc64 在较晚版本完成）；② 架构本身因市场萎缩而被降级或废弃（sparc64 在 FreeBSD 13 降级为 Tier 2，mips 在 FreeBSD 13 后也逐步降级）；③ 社区通过外部 GCC 工具链（ports/devel/gcc 或外部 binutils）继续支持非 Tier 1 架构。RISC-V 作为新架构从一开始就依赖 Clang/LLVM 支持（GCC 4.2.1 不可能支持 RISC-V），FreeBSD/riscv 从开发初期即使用 Clang。各架构 Clang 支持与迁移状态汇总见下表。

**史观**：总纲第 4 条——分离聚合是永恒规律：GCC 4.2.1 从 base 移除的标志不是 “所有架构都用 Clang”，而是 “所有 Tier 1 架构都用 Clang，Tier 2/Tier 3 架构可依赖 ports GCC”。这标志着 FreeBSD 工具链策略从 “base 支持所有架构” 转向 “base 保证 Tier 1 质量，其他架构由 ports/社区支持” 的分层模式。

**辨析**：架构的 Tier 级别是动态调整的——sparc64 从 FreeBSD 13 起不再是 Tier 1，mips 支持也大幅缩水，但这不完全归因于 Clang 迁移；SPARC 和 MIPS 硬件市场在 2010 年代的整体衰退（Oracle 终止 SPARC 服务器开发、MIPS 公司转向 RISC-V）是更深层原因。

**文献**：FreeBSD Project. Supported Architectures [EB/OL]. freebsd.org/platforms/；FreeBSD 12.0/13.0 Release Notes [Z]；Losh W. GCC 4.2.1 retirement email [EB/OL]. freebsd-arch, 2018. ［A］

## 143.10.4 架构支持对迁移时间线的效应

**要点**：非 x86 架构的 Clang 支持进度是 GCC 从 FreeBSD base 完全移除的主要阻塞因素。迁移的关键时间节点如下：①2009.2——i386/amd64 内核可启动（Divacky）；②2012.1——FreeBSD 9.0 发布，Clang 导入 base 但 GCC 默认；③2012.11——x86 -CURRENT 默认 Clang；④2014.1——FreeBSD 10.0 发布，i386/amd64 默认 Clang，GCC 仍为其他架构保留；⑤2016.10——FreeBSD 11.0 发布，arm64 首次作为支持架构；⑥2018.12——FreeBSD 12.0 发布，lld 为 x86/armv7 默认 linker，gdb 移至 libexec，LLVM 6.0.1，ELF Tool Chain r3614；⑦2018——Warner Losh 宣布 GCC 4.2.1 退休（所有受支持架构已使用 Clang 或外部工具链）；⑧2021.4——FreeBSD 13.0 发布，arm64 升为 Tier 1，LLVM Clang 11，移除过时 GNU 工具（含 GCC 和 grep）；⑨2024.7——FreeBSD 16-CURRENT 移除 dialog（最后一个 GPL 组件）。〔考据注：dialog/cdialog 替换工程真实存在，本收束节点表述尚须以 releng 公告三次复查补验〕

**史料**：各版本 Release Notes/Announcement、Warner Losh 2018 邮件、2024 dialog 移除新闻。 ［C］

**史观**：总纲第 22 条——知识注定过时：从 2009 年 i386/amd64 内核可启动到 2024 年最后一个 GPL 组件移除，Clang/LLVM 迁移与许可证纯洁化工程历时 15 年，是 FreeBSD 历史上持续时间最长、影响最深远的基础设施工程。这一工程彻底改变了 FreeBSD 的工具链、架构支持和许可证身份。

**辨析**：FreeBSD 13.0（2021）“移除 GCC” 指从 base 安装集移除 GCC 4.2.1 二进制文件（在 Clang 可完整支持所有 Tier 1 架构后），但 ports/devel/gcc 仍提供现代 GCC 版本供需要的 ports 使用；GCC 在 ports 中的存在是永久性的，因为大量 C++/Fortran/Ada 等软件仍依赖 GCC 扩展或更好的优化。
