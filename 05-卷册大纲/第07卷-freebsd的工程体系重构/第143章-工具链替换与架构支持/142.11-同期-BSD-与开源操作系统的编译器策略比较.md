# 142.11 同期 BSD 与开源操作系统的编译器策略比较

## 142.11.1 OpenBSD：分多年逐架构 Clang 迁移
  - 要点：OpenBSD 在 FreeBSD 之后也进行了 Clang 迁移，但时间更晚、策略更分阶段。OpenBSD 长期使用 GCC 3.x（GPLv2 版本）作为默认编译器以回避 GPLv3 问题；当 GCC 3.x 过老无法支持新硬件和 C++ 标准时，OpenBSD 开始评估 Clang。OpenBSD 的 Clang 迁移分架构逐批完成：amd64/i386 于 2017 年 7 月 26 日（OpenBSD 6.2 开发周期）切换默认编译器（Robert Nagy 提交）；armv7 于 2018 年 1 月 19 日切换（Mark Kettenis 提交）；octeon（Cavium OCTEON MIPS64）于 2019 年 7 月切换；powerpc 于 2020 年 4 月切换；loongson（MIPS64 Loongson）于 2020 年 12 月切换。OpenBSD 的许可证纯洁化更广泛：mandoc（Ingo Schwarze 开发，OpenBSD 项目）替代 groff、LibreSSL（2014 年 Heartbleed 后 Theo de Raadt 领导 fork）替代 OpenSSL，但需注意 LibreSSL 仅在 OpenBSD base 中为默认，FreeBSD base 仍使用 OpenSSL。
  - 史料：OpenBSD CVS 提交记录（Robert Nagy 2017.7.26、Mark Kettenis 2018.1.19、Visa Hankala 2019-2020 各架构切换）、OpenBSD 6.2 Release Notes、mandoc 项目历史（Ingo Schwarze）、LibreSSL 项目公告（2014.7）。[考据完成：2026-07-28 经穷尽联网考据，上述史料清单为已知公开来源汇总，部分原始档案未公开数字化或须档案馆藏地现场核验，属史料缺口，须待原始档案公开后方可补充确证]
    FreeBSD 社区论文：[FP-2019-014] LLVM and the state of sanitizers on BSD（David Carlier，2019）<https://papers.freebsd.org/2019/asiabsdcon/carlier-llvm_and_the_state_of_sanitizers_on_bsd/>
  - 史观：总纲第 6 条——技术路线分化：OpenBSD 比 FreeBSD 晚约三年半切换 amd64/i386 默认 Clang（FreeBSD 2014.1 vs OpenBSD 2017.7），这反映了两个项目不同的工程优先级——FreeBSD 因 C++11 支持需求和 Apple 投入更迫切需要迁移，OpenBSD 因长期停留在 GCC 3（GPLv2）而推迟了切换压力。
  - 辨析：原文件误称 “OpenBSD 5.5 默认 Clang” 或 “2014 年”——经 OpenBSD CVS commit log 交叉验证，amd64/i386 实际切换时间为 2017 年 7 月 26 日（commit 时间戳精确到日），5.5 是 2014 年 5 月发布，此错误已修正。Theo de Raadt 在许可证问题上的立场比 FreeBSD 更为激进（他对 GPL 和 NDA 均持强烈批评态度），这也是 OpenBSD mandoc/LibreSSL/Clang 全面替换的动力之一。

## 142.11.2 NetBSD：多编译器支持策略
  - 要点：NetBSD 对 Clang/LLVM 的态度比 FreeBSD 和 OpenBSD 更为多元和渐进。Jörg Sonnenberger 在 2012 年 1 月即发表 “Status of NetBSD and LLVM” 报告评估 Clang 移植状态，但 NetBSD 采取了更为保守的 “多编译器并行” 策略——长期同时支持 GCC 和 Clang，不同架构、不同版本使用不同默认编译器。NetBSD 的 GCC 策略也与 FreeBSD 不同：NetBSD 基于 GPLv2 的 GCC 4.x 版本长期维护（不升级到 GPLv3 的 GCC 4.8+），而不是像 FreeBSD 那样停留在 GCC 4.2.1。这使 NetBSD 在没有 Clang 迁移紧迫性的情况下获得了更好的 C++ 支持，但也意味着其 base 系统长期包含 GPLv2 代码。
  - 史料：Jörg Sonnenberger 2012.1.19 “Status of NetBSD and LLVM” 报告、NetBSD 各版本 Release Notes、NetBSD Wiki LLVM 页面。 ［B］
  - 史观：总纲第 6 条——技术路线分化：NetBSD 的多编译器策略反映了其 “高度可移植” 项目哲学——支持最多架构、最大灵活性是首要目标，而非 base 系统许可证纯洁性。三个 BSD 项目在 Clang 迁移上的速度差异（FreeBSD 最快，OpenBSD 分架构慢但彻底，NetBSD 最保守）准确反映了各自的项目优先级。
  - 辨析：NetBSD 是否在特定版本将 Clang 设为特定架构默认需逐版本核实——公开资料显示 NetBSD 在 2014-2020 年间逐步增加 Clang 支持，但未像 FreeBSD 10.0 那样宣布 “架构 X 默认 Clang” 的鲜明切换点。
  - 文献：Sonnenberger J. Status of NetBSD and LLVM [EB/OL]. sonnenberger.org, 2012-01-19；NetBSD Project. NetBSD Release Notes and Wiki [Z]. netbsd.org. ［B］
## 142.11.3 Apple Xcode、Android/Chromium 与商业生态
  - 要点：Clang/LLVM 的最大商业驱动力是 Apple——Apple 自 2005 年雇佣 Chris Lattner 后持续重金投入 LLVM/Clang 开发，Xcode 4.2（2011 年）将 Clang 设为 macOS/iOS 默认编译器，完全替换了 Xcode 中的 GCC。Google 是 LLVM/Clang 的第二大贡献者：Android NDK 从 r13（2016 年）起逐步切换 Clang，r18（2018 年）移除 GCC；Chromium/Chrome 浏览器从 2018 年 3 月起全平台使用 Clang 构建（包括 Windows 版本）。Sony 使用基于 Clang 的编译器作为 PlayStation 4/5 SDK 工具链（PS4 Orbis OS 本身基于 FreeBSD 9.0）。Microsoft 从 2020 年代开始在 Visual Studio 中集成 Clang/LLVM 工具链（clang-cl）。这些商业巨头的投入使 LLVM/Clang 成为一个由竞争对手共同资助的共享基础设施项目——Apple、Google、Microsoft、Sony、ARM、Intel、AMD 互为市场对手，但在 LLVM 项目中协作开发编译器核心。
  - 史料：Apple Xcode 4.2 Release Notes（2011）、Android NDK Revision History（r13 2016 Clang 默认、r18 2018 移除 GCC）、Google “Clang is now used to build Chrome for Windows” 博客（2018.3）、Sony PS4 SDK 工具链文档、Microsoft Visual Studio Clang 支持公告。 ［C］
  - 史观：总纲第 22 条——开源运动：LLVM/Clang 生态开创了一种 “商业竞争驱动开源协作” 的新模式——互为死敌的公司在宽容许可证框架下共同投资共享基础设施，各自保留专有后端和产品差异化。这与 GCC 由 FSF/Red Hat 主导的 “社区驱动” 模式形成鲜明对比，两种模式均成功但代表不同的开源治理范式。
  - 辨析：FreeBSD 作为 LLVM 早期采用者和重要测试平台，间接从这些商业投入中获益——Apple/Google/Microsoft 修复的 Clang bug 和优化直接惠及 FreeBSD，但 FreeBSD 对 LLVM 上游的代码贡献相比这些大公司仍然较小。

NDK Revision History [EB/OL]. developer.android.com/ndk.[考据完成：2026-07-28 经穷尽联网考据，上述文献清单为已知公开来源汇总，部分原始档案未公开数字化或须付费访问，属史料缺口，须待原始档案公开后方可补充确证]
## 142.11.4 Linux 生态：GCC 为主，Clang 为可选
  - 要点：Linux 生态对 Clang 的态度与 BSD 世界形成有趣对比。Linux 内核长期以 GCC 为唯一支持编译器，使用了大量 GCC 扩展和特定 GCC 行为。LLVMLinux 项目（2010 年代初启动）致力于使 Clang 可编译 Linux 内核；2020 年代 Linux 内核正式支持 Clang 编译（但仍以 GCC 为主要编译器和默认配置）。Android 内核和 ChromeOS 内核强制使用 Clang（因 Google 全栈 Clang 策略），但主线 Linux 发行版（Ubuntu、Debian、Fedora、RHEL 等）仍以 GCC 为默认编译器。Linux 内核持续使用 GCC 的主要原因：① 历史——2007 年 GPLv3 发布时 林纳斯·托瓦兹（Linus Torvalds）决定 Linux 内核保持 GPLv2 only 不升级到 GPLv3，因此 GCC 4.3+（GPLv3）作为编译器其许可证不传染输出（GCC Runtime Library Exception 明确），不构成法律问题；② 生态——20 余年积累的 GCC 扩展和内核代码深度依赖 GCC；③ 性能——GCC 在某些内核配置和架构上的优化仍优于 Clang；④ 治理——Linux 内核社区对 GCC 有更大影响力（GCC 社区更愿意接受 Linux 相关补丁）。各开源操作系统编译器策略比较汇总见下表。

| 操作系统 | 默认编译器 | Clang 默认切换时间 | 法律动机 | 工程动机 | 切换策略 |
| --- | --- | --- | --- | --- | --- |
| FreeBSD | Clang/LLVM | FreeBSD 10.0（2014.1.20，i386/amd64） | GPLv3 §6/§7/§11 法律风险，base 系统须保持 BSD 纯洁 | GCC 4.2.1 无法编译 C++11（2011） | 五阶段渐进：探索 → 导入 → 可选 → 默认 → 移除（2009-2024） |
| OpenBSD | Clang/LLVM | 2017.7.26（amd64/i386，OpenBSD 6.2 周期） | Theo de Raadt 对 GPL/NDA 的强烈批评 | GCC 3.x 过老无法支持新硬件 | 分架构逐批切换（2017-2020，amd64→armv7→octeon→powerpc→loongson） |
| NetBSD | GCC（多编译器并行） | 未宣布鲜明切换点 | 项目哲学优先可移植性而非 base 许可证纯洁 | 长期基于 GPLv2 GCC 4.x 维护 | 多编译器并行支持，不同架构不同默认 |
| DragonFly BSD | 双编译器支持 | 2009 年起实验，长期双支持 | 比 FreeBSD 更宽容 | 早期实验性采用 | 长期保持双编译器兼容 |

| Apple macOS/iOS | Clang/LLVM | Xcode 4.2（2011） | GCC 无法满足 IDE 集成、Objective-C 支持、许可证控制 | Apple 投入 LLVM 最早最重（2005 雇佣 Lattner） | 完全替换 GCC（无回退） |

| Sony PS4/5 | 基于 Clang 的工具链 | PS4 SDK（基于 FreeBSD 9.0） | 商业 SDK 工具链选择 | Orbis OS 基于 FreeBSD | 商业专有 SDK |

- 史观：总纲第 6 条——技术路线分化：Linux 无需迁移 Clang 的法律基础是 Torvalds 在 2006-2007 年拒绝将 Linux 内核升级到 GPLv3——GCC 4.3+ 的 GPLv3 许可证适用于编译器本身，但编译输出（内核）的许可证由内核作者决定而非编译器许可证决定（FSF 明确确认），因此 GCC GPLv3 对 Linux 内核不构成许可证危机。这一法律解释的差异是 Linux 与 FreeBSD 工具链分道扬镳的根源。
- 辨析：“GCC GPL 传染编译产物” 是常见误解——FSF 明确表示 GCC 的 GPL 许可证不适用于 GCC 编译输出的程序（只要不是基于 GCC 运行时库的 GPL 代码片段衍生），GCC Runtime Library Exception 进一步明确了这一点。因此 Linux 使用 GCC 4.3+（GPLv3）不涉及许可证问题，但 FreeBSD base 系统中包含 GCC 二进制和库文件本身就是 GPL 代码分发，因此升级到 GPLv3 GCC 意味着 base 系统包含 GPLv3 代码。
