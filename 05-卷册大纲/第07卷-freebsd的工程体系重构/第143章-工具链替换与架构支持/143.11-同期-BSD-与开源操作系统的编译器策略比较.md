# 143.11 同期 BSD 与开源操作系统的编译器策略比较

## 143.11.1 OpenBSD：分多年逐架构 Clang 迁移

**要点**：OpenBSD 在 FreeBSD 之后也进行了 Clang 迁移，但时间更晚、策略更分阶段。OpenBSD 长期使用 GCC 3.x（GPLv2 版本）作为默认编译器以回避 GPLv3 问题；当 GCC 3.x 过老无法支持新硬件和 C++ 标准时，OpenBSD 开始评估 Clang。OpenBSD 的 Clang 迁移分架构逐批完成：amd64/i386 于 2017 年 7 月 26 日（OpenBSD 6.2 开发周期）切换默认编译器（Robert Nagy 提交）；armv7 于 2018 年 1 月 19 日切换（Mark Kettenis（马克·凯特尼斯） 提交）；octeon（Cavium OCTEON MIPS64）于 2019 年 7 月切换；powerpc 于 2020 年 4 月切换；loongson（MIPS64 Loongson）于 2020 年 12 月切换。OpenBSD 的许可证纯洁化更广泛：mandoc（Ingo Schwarze（英戈·施瓦茨） 开发，OpenBSD 项目）替代 groff、LibreSSL（2014 年 Heartbleed 后 Theo de Raadt（西奥·德·若特） 领导 fork）替代 OpenSSL，但需注意 LibreSSL 仅在 OpenBSD base 中为默认，FreeBSD base 仍使用 OpenSSL。

**史料**：OpenBSD CVS 提交记录（Robert Nagy 2017.7.26、Mark Kettenis 2018.1.19、Visa Hankala 2019-2020 各架构切换）、OpenBSD 6.2 Release Notes、mandoc 项目历史（Ingo Schwarze）、LibreSSL 项目公告（2014.7）。［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］ 〔L1 代码；L3 官方文档〕
    FreeBSD 社区论文：[FP-2019-014] LLVM and the state of sanitizers on BSD（David Carlier，2019）<https://papers.freebsd.org/2019/asiabsdcon/carlier-llvm_and_the_state_of_sanitizers_on_bsd/>

**史观**：总纲第 6 条——技术路线分化：OpenBSD 比 FreeBSD 晚约三年半切换 amd64/i386 默认 Clang（FreeBSD 2014.1 vs OpenBSD 2017.7），这反映了两个项目不同的工程优先级——FreeBSD 因 C++11 支持需求和 Apple 投入更迫切需要迁移，OpenBSD 因长期停留在 GCC 3（GPLv2）而推迟了切换压力。

**辨析**：原文件误称 “OpenBSD 5.5 默认 Clang” 或 “2014 年”——经 OpenBSD CVS commit log 交叉验证，amd64/i386 实际切换时间为 2017 年 7 月 26 日（commit 时间戳精确到日），5.5 是 2014 年 5 月发布，此错误已修正。Theo de Raadt 在许可证问题上的立场比 FreeBSD 更为激进（他对 GPL 和 NDA 均持强烈批评态度），这也是 OpenBSD mandoc/LibreSSL/Clang 全面替换的动力之一。

**文献**：OpenBSD Project. OpenBSD 6.2 Release Notes [Z]. 2017-10-09；Nagy R. switch the default compiler on amd64 and i386 to clang [EB/OL]. openbsd-cvs, 2017-07-26；Schwarze I. mandoc history [EB/OL]. mandoc.bsd.lv；OpenBSD Project. LibreSSL [EB/OL]. libressl.org, 2014. ［A］

## 143.11.2 NetBSD：多编译器支持策略

**要点**：NetBSD 对 Clang/LLVM 的态度比 FreeBSD 和 OpenBSD 更为多元和渐进。Jörg Sonnenberger 在 2012 年 1 月即发表 “Status of NetBSD and LLVM” 报告评估 Clang 移植状态，但 NetBSD 采取了更为保守的 “多编译器并行” 策略——长期同时支持 GCC 和 Clang，不同架构、不同版本使用不同默认编译器。NetBSD 的 GCC 策略也与 FreeBSD 不同：NetBSD 基于 GPLv2 的 GCC 4.x 版本长期维护（不升级到 GPLv3 的 GCC 4.8+），而不是像 FreeBSD 那样停留在 GCC 4.2.1。这使 NetBSD 在没有 Clang 迁移紧迫性的情况下获得了更好的 C++ 支持，但也意味着其 base 系统长期包含 GPLv2 代码。

**史料**：Jörg Sonnenberger 2012.1.19 “Status of NetBSD and LLVM” 报告、NetBSD 各版本 Release Notes、NetBSD Wiki LLVM 页面。 ［B］

**史观**：总纲第 6 条——技术路线分化：NetBSD 的多编译器策略反映了其 “高度可移植” 项目哲学——支持最多架构、最大灵活性是首要目标，而非 base 系统许可证纯洁性。三个 BSD 项目在 Clang 迁移上的速度差异（FreeBSD 最快，OpenBSD 分架构慢但彻底，NetBSD 最保守）准确反映了各自的项目优先级。

**辨析**：NetBSD 是否在特定版本将 Clang 设为特定架构默认需逐版本核实——公开资料显示 NetBSD 在 2014-2020 年间逐步增加 Clang 支持，但未像 FreeBSD 10.0 那样宣布 “架构 X 默认 Clang” 的鲜明切换点。

**文献**：Sonnenberger J. Status of NetBSD and LLVM [EB/OL]. sonnenberger.org, 2012-01-19；NetBSD Project. NetBSD Release Notes and Wiki [Z]. netbsd.org. ［B］

## 143.11.3 Apple Xcode、Android/Chromium 与商业生态

**要点**：Clang/LLVM 的最大商业驱动力是 Apple——Apple 自 2005 年雇佣 Chris Lattner 后持续重金投入 LLVM/Clang 开发，Xcode 4.2（2011 年）将 Clang 设为 macOS/iOS 默认编译器，完全替换了 Xcode 中的 GCC。Google 是 LLVM/Clang 的第二大贡献者：Android NDK 从 r13（2016 年）起逐步切换 Clang，r18（2018 年）移除 GCC；Chromium/Chrome 浏览器从 2018 年 3 月起全平台使用 Clang 构建（包括 Windows 版本）。Sony 使用基于 Clang 的编译器作为 PlayStation 4/5 SDK 工具链（PS4 Orbis OS 本身基于 FreeBSD 9.0）。Microsoft 从 2020 年代开始在 Visual Studio 中集成 Clang/LLVM 工具链（clang-cl）。这些商业巨头的投入使 LLVM/Clang 成为一个由竞争对手共同资助的共享基础设施项目——Apple、Google、Microsoft、Sony、ARM、Intel、AMD 互为市场对手，但在 LLVM 项目中协作开发编译器核心。

**史料**：Apple Xcode 4.2 Release Notes（2011）、Android NDK Revision History（r13 2016 Clang 默认、r18 2018 移除 GCC）、Google “Clang is now used to build Chrome for Windows” 博客（2018.3）、Sony PS4 SDK 工具链文档、Microsoft Visual Studio Clang 支持公告。 ［C］

**史观**：总纲第 22 条——开源运动：LLVM/Clang 生态开创了一种 “商业竞争驱动开源协作” 的新模式——互为死敌的公司在宽容许可证框架下共同投资共享基础设施，各自保留专有后端和产品差异化。这与 GCC 由 FSF/Red Hat 主导的 “社区驱动” 模式形成鲜明对比，两种模式均成功但代表不同的开源治理范式。

**辨析**：FreeBSD 作为 LLVM 早期采用者和重要测试平台，间接从这些商业投入中获益——Apple/Google/Microsoft 修复的 Clang bug 和优化直接惠及 FreeBSD，但 FreeBSD 对 LLVM 上游的代码贡献相比这些大公司仍然较小。

**文献**：Apple Inc. Xcode 4.2 Release Notes [Z]. 2011；Google. Clang is now used to build Chrome for Windows [EB/OL]. LLVM Project Blog, 2018-03-05；Android Developer. NDK Revision History [EB/OL]. developer.android.com/ndk.［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

## 143.11.4 Linux 生态：GCC 为主，Clang 为可选

**要点**：Linux 生态对 Clang 的态度与 BSD 世界形成有趣对比。Linux 内核长期以 GCC 为唯一支持编译器，使用了大量 GCC 扩展和特定 GCC 行为。LLVMLinux 项目（2010 年代初启动）致力于使 Clang 可编译 Linux 内核；2020 年代 Linux 内核正式支持 Clang 编译（但仍以 GCC 为主要编译器和默认配置）。Android 内核和 ChromeOS 内核强制使用 Clang（因 Google 全栈 Clang 策略），但主线 Linux 发行版（Ubuntu、Debian、Fedora、RHEL 等）仍以 GCC 为默认编译器。Linux 内核持续使用 GCC 的主要原因：① 历史——2007 年 GPLv3 发布时 林纳斯·托瓦兹（Linus Torvalds）决定 Linux 内核保持 GPLv2 only 不升级到 GPLv3，因此 GCC 4.3+（GPLv3）作为编译器其许可证不传染输出（GCC Runtime Library Exception 明确），不构成法律问题；② 生态——20 余年积累的 GCC 扩展和内核代码深度依赖 GCC；③ 性能——GCC 在某些内核配置和架构上的优化仍优于 Clang；④ 治理——Linux 内核社区对 GCC 有更大影响力（GCC 社区更愿意接受 Linux 相关补丁）。各开源操作系统编译器策略比较汇总见下表。

| 操作系统 | 默认编译器 | Clang 默认切换时间 | 法律动机 | 工程动机 | 切换策略 |
| --- | --- | --- | --- | --- | --- |
| FreeBSD | Clang/LLVM | FreeBSD 10.0（2014.1.20，i386/amd64） | GPLv3 §6/§7/§11 法律风险，base 系统须保持 BSD 纯洁 | GCC 4.2.1 无法编译 C++11（2011） | 五阶段渐进：探索 → 导入 → 可选 → 默认 → 移除（2009-2024） |
| OpenBSD | Clang/LLVM | 2017.7.26（amd64/i386，OpenBSD 6.2 周期） | Theo de Raadt 对 GPL/NDA 的强烈批评 | GCC 3.x 过老无法支持新硬件 | 分架构逐批切换（2017-2020，amd64→armv7→octeon→powerpc→loongson） |

**史观**：总纲第 6 条——技术路线分化：Linux 无需迁移 Clang 的法律基础是 Torvalds 在 2006-2007 年拒绝将 Linux 内核升级到 GPLv3——GCC 4.3+ 的 GPLv3 许可证适用于编译器本身，但编译输出（内核）的许可证由内核作者决定而非编译器许可证决定（FSF 明确确认），因此 GCC GPLv3 对 Linux 内核不构成许可证危机。这一法律解释的差异是 Linux 与 FreeBSD 工具链分道扬镳的根源。

**辨析**：“GCC GPL 传染编译产物” 是常见误解——FSF 明确表示 GCC 的 GPL 许可证不适用于 GCC 编译输出的程序（只要不是基于 GCC 运行时库的 GPL 代码片段衍生），GCC Runtime Library Exception 进一步明确了这一点。因此 Linux 使用 GCC 4.3+（GPLv3）不涉及许可证问题，但 FreeBSD base 系统中包含 GCC 二进制和库文件本身就是 GPL 代码分发，因此升级到 GPLv3 GCC 意味着 base 系统包含 GPLv3 代码。

- Marino 给出三代构建工具的机制分野：portmaster/portupgrade 在宿主系统就地构建并安装构建依赖、更新非原子且串行，中断即可能使系统进退两难；poudriere 以 FreeBSD Jail 构成近乎不可穿透的隔离层，面向不容失败的集群调度；Synth 则以 chroot 加 nullfs 与 tmpfs 挂载换取速度并深度接管 pkg 的本地升级，作者自陈这是速度与健壮性之间的取舍，并称二者能力相近、目标人群不同。（BSD Now EP129，[1824.10-2200.16]，L1）
- Marino 回顾其约十三个年头的 BSD 历程：2002-2003 年在慕尼黑依雇主要求试用的多款 Linux 发行版接连崩溃，转投 FreeBSD 4.8 后一切顺畅；其后在八台 Sun 服务器上以 FreeBSD 6 承载网络业务多年不停机；由向 DragonFly 提交补丁获邀成为 committer，经 pkgsrc 贡献在图卢兹完成 PGP 签名取得 NetBSD commit bit，再将 FreeBSD ports 引入 DragonFly 的 DPorts 实验大获成功，pkg 亦先于 NetBSD 在 DragonFly 投入生产。（BSD Now EP129，[1301.78-1590.30]，L1）
- OpenBSD 基金会公布 2016 年度募款目标 25 万美元，2015 年实际成绩已超既定目标；基金会强调企业捐助与社区个人捐助的构成均衡，是向潜在企业赞助者证明社区真实健康度的关键；其推算若每份 OpenBSD 安装计 10 美元、每次 OpenSSH 源码直接下载计 2 美元即已达标，且未计入随各操作系统与手机分发的部分——如 iOS 内置 PF——显示其技术渗透远超装机数字。（BSD Now EP129，[574.76-676.04]，L2）
- 入行经过：大学时新笔记本需要可用的无线局域网，FreeBSD 5 当时未就绪、NetBSD 与 OpenBSD 在该机器上亦不理想，恰逢 Matt Dillon 宣布 DragonFly 项目且缺少 CardBus（32 位 PCMCIA 扩展）支持，其首个贡献即把 FreeBSD 5 的 CardBus 支持回移到 DragonFly。（BSDTalk EP135，[101.77-137.10]，L1）

- NetBSD 电源管理工作：Jared McNeill 早先着手改进 ACPI 挂起/恢复（部分机器可用、许多笔记本失效、AMD64 完全不可用）；另一方向是让未使用设备自动断电（未启用的网络接口、声卡等）；有专门邮件列表推动电源管理进入更多驱动；其本人因笔记本需要而投入，并视电源管理为当前比 jail 更紧迫的工作。（BSDTalk EP135，[253.27-312.47]，L1）
- Google Summer of Code 的 pkgsrc 项目分两部分：一是重做批量构建框架——旧系统无法处理多 chroot 或分布式构建集群，新系统以轻松利用多机、动态加入与退出为设计目标；二是 pkgsrc 交叉编译，重点是 modular Xorg（沿 XFree86 老路则工作量巨大且与 DragonFly 需求重复维护），核心是让 pkgsrc 复用 NetBSD 基础系统的交叉编译工具链，使 Amiga、VAX 等慢架构免于本地构建大包；适用前提为单平台且目标基础设施相似（ELF），跨操作系统交叉编译仅为未测试设想。（BSDTalk EP135，[365.44-505.83]，L1）
- GPLv3 的两大问题（EuroBSDCon 2007 项目状态讨论议题）：基础系统层面，需定期更新的 GPL 组件是 groff 与 GCC，要害不在 GCC 本身而在 libgcc 与 libstdc++——二者长期带有允许链接的例外条款，GPLv3 未将例外延及反 tivoization 条款，使高度定制且不允许篡改的系统能否用 GCC 构建成疑；对策包括 OpenBSD 导入 PCC、为 groff（BSD 源码树中唯一主要 C++ 组件）寻求替代。包管理层面，pkgsrc 已有非开源许可标签框架（mk.conf 的 acceptable_licenses 变量控制构建），计划扩展至全部许可类别尤其是 GPLv3，令用户知情并自决；批量构建基础设施问题待解决，目前仅对升级到 GPLv3 的包加注释。（BSDTalk EP135，[509.55-721.07]，L1）
- DragonFly jail 与 FreeBSD jail 的分化：DragonFly 源自 FreeBSD 4 的 jail 代码，FreeBSD 5/6 期间核心未大改（主要是适配 Robert Watson 的新凭证框架）；DragonFly 近期提交关键补丁，支持每 jail 多 IP 地址乃至 jail 内 IPv6，jail 的一大主要问题基本消除；FreeBSD 尚缺此能力，其替代路径是重量级虚拟化而非修补 jail 代码。（BSDTalk EP135，[734.95-791.94]，L1）
- NetBSD 的 kauth 式 jail 设想：kauth 已把大部分安全决策抽象到单一位置、便于修改；在 NetBSD 实现 jail 需给进程结构与凭证增加字段，使 root 权限决策可依是否处于 jail 而调整；剩余难题是 localhost 地址翻译的复杂代码；虚拟化路径的优点是避免在 jail 代码中特判。应用兼容性问题：Samba 因 localhost 特殊处理需要本地补丁，syslog 等守护进程绑定全部地址的对外行为需如 FreeBSD 团队那样专门修改。（BSDTalk EP135，[797.41-886.94]，L1）
- 开发者自我定位与环境：自称对所工作的 BSD 大体持不可知态度，现用 NetBSD 只因在其笔记本上优于 DragonFly，欣赏 DragonFly 的许多想法，不排斥 OpenBSD 且可能提交补丁；开发环境以控制台与多个 xterm 为主，使用 ion 平铺窗口管理器、midnight commander 与 vi。（BSDTalk EP135，[320.47-353.67]，L1）
- BSD Fund 仿照 Linux Fund 模式运作，定位为 501(c)(3) 型非营利机构，通过奖励型信用卡与直接捐赠两条渠道，为 BSD 活动、软件开发与硬件运输筹款；其首个软件资助对象是 PCC 编译器项目。（BSDTalk EP175，[217.5-323.6]，L1）
- PCC 资助以单条社区新闻帖启动，约两三天内募集约 5000 美元；捐赠者的疑问在帖内自行得到解答，社区呈现自我协调状态，未出现常见的小额零散捐赠噪音，Dexter 以此为社区自组织能力的例证。（BSDTalk EP175，[379.5-431.5]，L1）
- PCC 当时即将发布 AMD64 支持；据 Dexter 转述，Anders Magnusson 与 Linus Torvalds 曾讨论以 PCC 作为 Linux 内核专用编译器以替代日益庞大的 GCC，谈判受阻于缺少 AMD64 支持。　[存疑脚注] 此事系 Dexter 转述当事人通信，本期无独立旁证，需以邮件列表或 PCC 仓库记录交叉验证。（BSDTalk EP175，[432.5-497.4]，L2）
- Dexter 提出 PCC 之外尚需更广泛的非 GPL 工具链（链接器、汇编器及配套实用程序），并论证宽松 BSD 许可证允许专有与非专有使用，使编译器可同时惠及开放与专有的嵌入式项目。（BSDTalk EP175，[622.1-698.2]，L1）
- BSD Fund 的成本结构为直接捐赠约 99% 直达项目、仅预留支付处理费，间接费用由 Linux Fund 承担；硬件运输基金已实际运作，将 FreeGeek Portland 捐赠的服务器运交欧洲开发者，另正与荷兰税务当局接洽注册外国非营利组织以便欧洲捐赠者抵税。（BSDTalk EP175，[720.0-794.0]，L1）
- Dexter 提出虚拟硬件实验室设想：开发者发布可烧录至闪存的系统镜像，硬件持有者引导该介质使其回连，开发者即可远程验证 ACPI 等硬件支持，以解决捐赠硬件物流不畅与现代笔记本缺少串口的困难。（BSDTalk EP175，[1211.0-1298.5]，L1）

**史观**：

- 总纲4 分离聚合是永恒规律：Marino 以 locales/collation 修复为例呈现项目间循环：DragonFly 因用户少、仅维护一个旧版本而得以先行整改，FreeBSD 侧开发者不愿落后而引入同一实现，FreeBSD 的庞大用户随即暴露缺陷，反馈又流向代码原出处 Illumos——边缘先行试验、中心收编检验、再回流源流，构成三向的分离聚合运动，而非单向取代或线性进步。（BSD Now EP129，[3354.48-3413.32]，L1）
- 总纲8 本体论上各方平等：跨项目开发者以可用性与问题驱动选择工作对象而非效忠单一分支：从 DragonFly 回移、到 pkgsrc 提交、再到 NetBSD 电源管理与可能的 OpenBSD 补丁，四大 BSD 在其实践中是可互换的工程场域。（BSDTalk EP135，[320.47-353.67]，L1）
- 总纲4 分离聚合是永恒规律：jail 代码从 FreeBSD 4 分离至 DragonFly 后独立演化出多 IP 与 IPv6 支持，而包管理层反向聚合于跨项目的 pkgsrc 平台——分离与聚合在代码谱系的不同层面同时进行，构成循环而非单向演进。（BSDTalk EP135，[142.22-791.94]，L1）
- 总纲13 法律与道德是利益分配：pkgsrc 的许可标签框架把许可证选择转译为用户可见的构建配置（acceptable_licenses），GPLv3 包的处置方案是让用户在知情前提下自决——许可证的利益分配通过包管理基础设施落到用户决定。（BSDTalk EP135，[649.76-705.47]，L1）
- 总纲10 动手者创造历史：Dexter 强调 BSD 开发多为志愿劳动、同时在公司内又具职业性质，资助机制的意义在于补足预算、期限与优先项目识别的正式化灰色地带，使实际动手的开发者获得资源而非只资助机构本身。（BSDTalk EP175，[517.6-555.2]，L1）
- 总纲4 分离聚合是永恒规律：Dexter 主张一切 BSD 皆可上溯至伯克利代码发布，各项目历经分化之后仍存在可独立维护的共同代码空间，PCC 即可同时服务各 BSD 项目乃至 Linux，体现分化后重新聚合的资金与代码双向流通观。（BSDTalk EP175，[665.7-698.2]，L1）

**辨析**：

- 对 BSD 不受 CVE-2015-7547 影响的结论须分层限定：FreeBSD libc 与 glibc 解析器同源，但缺陷源于 glibc 重写后并行发出 A/AAAA 查询时的缓冲区管理失误，BSD 系仍串行查询故不涉险；可一旦经 Linux 仿真层安装 linux_base-c6 之类依赖，易感 glibc 即随之进入系统；再叠加 Red Hat 指明的 nss_dns 模块条件与 musl 等其他 libc 的差异，风险归属取决于 libc 具体实现与安装路径，而非操作系统阵营标签。（BSD Now EP129，[259.76-311.34]，L3）
- 关于把 Ada 前端移植到 LLVM 的可行性：受访者认为 GNAT 前端技术上可嫁接，但中端须重写，且即便完成也无法摆脱源自 GPL 的许可约束，故工作量与收益严重不成比例；这一判断与 DragonFly 计划以 clang 3.8 取代旧 GCC 的路线互为表里，凸显许可证与维护成本共同塑造编译器版图。　[存疑脚注] 移植可行性与许可约束判断仅为受访者单一来源推断，未经实现验证或第三方评审。（BSD Now EP129，[2894.30-2947.78]，L4）
- 转写讹误密集：Jörg Zonenberger 应为 Jörg Sonnenberger，Cartos 应为 CardBus，3BSD5 应为 FreeBSD 5，Package Source 应为 pkgsrc，KOF 应为 kauth，Nuoff 与 NUROV 疑为 groff 之讹（后者被称 BSD 源码树唯一主要 C++ 组件），OpenUSD 应为 OpenBSD，modular XORC 应为 modular Xorg，X386 应为 XFree86，电源管理邮件列表名与 Todd 之姓氏不可辨识。　[存疑脚注] 专名经上下文推断校正，邮件列表名与人名部分无法辨识，须以 pkgsrc/NetBSD 邮件列表存档核证（BSDTalk EP135，[89.22-721.07]，L4）
- “为 groff 寻得替代后仍可构建系统或构建稍慢”一句语义含混，无法确定所指为构建路径、性能或兼容层，原意须回听音频或比对后续 groff 替代工作（如 heirdom/mdocml 系）核证。　[存疑脚注] 表述含混，无法确证（BSDTalk EP135，[621.35-630.03]，L4）
- Malt 项目在 DCBSDCon 获良好反响，据称 Henning Brauer 曾对 jail 拥护者回应称其更优；但此后无人接手协助，开发者 Kristaps 因另一项目的政治纠葛受挫，其所在学校拟将 Malt 申报欧盟资助，Malt 能否成为 BSD Fund 项目取决于社区技术与资金双重兴趣。　[存疑脚注] Malt 的技术性质仅凭本期转写无法确证；受访者口中的 Henning Brower 拼写存疑，通行拼写为 Henning Brauer。（BSDTalk EP175，[1059.2-1113.7]，L2）
