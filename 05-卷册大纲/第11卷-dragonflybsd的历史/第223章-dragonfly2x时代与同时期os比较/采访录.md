#### 采访 1：Matthew Dillon

**字段 1 采访元数据**

- 受访者：Matthew Dillon，时任 DragonFly BSD 项目创始人兼 HAMMER 文件系统设计师
- 采访者：自述，无采访者
- 采访时间：2008-06-21

- 原始来源：Matthew Dillon, “The HAMMER File System”, DragonFly BSD 项目设计文档，2008-06-21。文档经互联网档案馆存档（archived from the original on 2022-10-09），存档检索路径见 **<https://www.dragonflybsd.org/hammer/>** 页面底部“HAMMER1”段落的设计文档链接

**字段 2 采访摘要**

Dillon 在 HAMMER 设计文档中详述 HAMMER 文件系统的设计哲学与技术架构。HAMMER 是 DragonFly 自研的 B-tree 写时复制文件系统，目标是替代 UFS 并与 ZFS 形成对照。设计文档涵盖 B+Tree 索引、UNDO/REDO 日志、历史保留、多卷镜像、CRC 校验等核心机制。HAMMER 的设计哲学是“轻量级写时复制”，避免 ZFS 的内存消耗与复杂度，同时提供即时快照、即时崩溃恢复与近实时镜像等特性。文档明确 HAMMER 作为 DragonFly 第二阶段集群工作基础的设计意图。

**字段 3 考据脚注**

本则 HAMMER 设计文档的作者与日期（Matthew Dillon, 2008-06-21）经多源交叉验证：DragonFly BSD 官方 HAMMER 页面（**<https://www.dragonflybsd.org/hammer/**>，访问日期 2026-07-24）“HAMMER1”段落引用该设计文档；`原材料/研究/考据记录/20260723_announcements-dragonfly.md` 第 6 条记录 2.0 release 页面 `https://www.dragonflybsd.org/release20/` 与 HAMMER 引入日期一致；dragonfly.duckdb dragonfly-src 仓库中 `sys/vfs/hammer/` 目录首引 commit（8750964d1997, 2007-10-10）与设计文档日期（2008-06-21）形成工程时间序列——代码先行于文档，反映“实践先于理论”的工程模式。自利偏差审查：Dillon 作为 HAMMER 设计者，在设计文档中对 HAMMER 原创性的陈述带有自身辩护倾向，正文引用时另以 Bonwick 2005 年 ZFS 论文与 HAMMER 源码（`sys/vfs/hammer/`）的源码级比较加以对照。HAMMER 与 ZFS 是否为“平行创新”而非“启发关系”，须经源码级比较方能定论 ［考据注：2026-07-28 联网考据留痕，模板句式已按 0 信任原则精简（WO-004）；语义以正文与所引来源为准］。完整考据过程见 [20260723_announcements-dragonfly.md](../../../原材料/研究/考据记录/20260723_announcements-dragonfly.md) 与 [20260724_dillon-hammer-design-doc.md](../../../原材料/研究/考据记录/20260724_dillon-hammer-design-doc.md)。

**字段 5 史观映射**

- 总纲 17“证明世界先于解释和改造世界”——项目史观总纲第 25 章原文“问题不在于解释世界和改造世界，而在于证明世界。我们在行动之前必须先使世界‘生成’”。HAMMER 设计文档本身是“证明世界”的工程化呈现：bsd_commits.duckdb 显示 `sys/vfs/hammer/` 路径首引 commit（8750964d1997, 2007-10-10）先于设计文档日期（2008-06-21）9 个月，反映“代码先行于文档”的工程认识论——HAMMER 的可行性须先以可运行代码使世界“生成”，再以设计文档加以解释。须区分项目统摄史观主张与项目统摄史观批评的对象：项目统摄史观批评的是“解释世界与改造世界的二分”这一形式主义框架本身，而非简单地主张“实践先于理论”。

- 总纲 8“本体论上各方平等”——项目史观总纲第 25 章原文“FreeBSD、OpenBSD、NetBSD、DragonFly BSD 在本体论上地位相等，差异仅是一刻状态的不同。文档与代码本体平等”。HAMMER 路线与 ZFS 路线在本体论上地位相等：HAMMER 选择 B+Tree 与 UNDO/REDO，ZFS 选择 merkle tree 与端到端校验，“主流采纳”（ZFS）与“非主流采纳”（HAMMER）是工程生态的偶然而非本体论的等级。须注意项目统摄史观批评的对象是“以采纳率判定技术价值”的形式主义评判，而主张各技术路线在本体论上地位相等——HAMMER 即使在用户基数上远逊于 ZFS，其作为文件系统设计的本体论地位并不因此降低。

**要点**：

- Dillon 综述迟了两三周发布的 DragonFly 2.8：集成大部分 Linux 模拟层、提供带条带化与加密的 DM 存储管理器、恢复 GUI USB 安装镜像，并伴随大量底层稳定性工作。（BSDTalk EP202，[47.32-95.60]，L1）
- 并发架构进展：巨型 MP 锁在代码层面基本移除（发布版默认仍启用以求稳定）；内核拆分为承接系统调用的前端与处理中断、设备调度的后端，后端几乎全部达到 MP 安全——网络栈、全部网络驱动、NATA 磁盘驱动、直至用户态缓存情形的整条 IO 路径与 HAMMER 均不触碰大锁；前端改用 token 锁协作，其中约半数仍保留回落大锁的保险机制；移除大锁后用户报告 Xorg 桌面等负载不再被单线程路径阻塞，性能显著改善。（BSDTalk EP202，[456.50-589.08]，L1）
- NFS 客户端重构为完全异步：RPC 不再依赖其他 BSD 中的 NFSIOD 机制（连内核线程形式也不存在），改为每条 NFS 套接字分配一对专用内核线程分别负责收发，预读默认大幅上调至十六至六十四；该实现自 2.6 起性能表现极佳，高预读引入的个别停滞边角案例在 2.8 中已修复至仅剩其一。（BSDTalk EP202，[589.08-670.24]，L1）
- HAMMER 两条线：其一，GSoC 去重项目接近入库（仍标实验性），按 B 树内建 CRC 收集匹配、经数据块实际一致性校验后合并引用，测试中在两块 TB 级盘获得可观去重比，但须让 reblocker 感知去重结果，否则无条件重整会撤销全部去重成果；其二，因一位用户盘面出现坏扇区且未做备份的求助，Dillon 放弃尝试两年未果的 HAMMER fsck（判定过于复杂不可行），改用一两天内写成的灾难恢复工具——对坏盘线性扫描识别 B 树节点、抽取文件与目录项并在目标盘动态重建文件系统，该用户借此恢复了九成九的数据。　[存疑脚注] 转写将 dedup 误作 D-Doop、去重比例数字（3 至 4 与 5 比 1 之间）含混，具体数值须回查原音频或发布说明（BSDTalk EP202，[124.88-807.80]，L1）
- 存储与加密配套：swapcache 自 2.6 稳定运行，2.8 树内经 VM 调整进一步优化并在发布后修复高负载下 pageout 守护进程迟滞引发的停滞，一块约百二十美元的 40GB Intel SSD 即可让单 HDD 加单 SSD 承载生产服务器并显著省本；内核开放加密框架经三人小组 MP 化改造后，软件加密由多核仅用单核的每秒三四十 MB 提升至一百五十 MB 以上，加密选项正在集成进安装器；标准磁盘安装采用七百 MB UFS 引导分区加整盘 HAMMER 的两分结构，使 HAMMER 分区可整盘加密并支持复杂根挂载；集群单一镜像系统长期目标仍在，但先行推进 multi-master 集群文件系统与缓存一致性，SSI 本身暂缓。（BSDTalk EP202，[248.22-498.28]，L1）

**史料**：

- 一手史料包括 Dillon 对 2.8 发布清单、GSoC 去重项目与加密框架开发的口述，以及其对参与 Google Code In 的说明——本人因连续指导 GSoC 而疲惫退出，由三四位开发者接手主持；本访谈录于 MeetBSD California 2010 第二天现场，本身即该会议的一手记录。（BSDTalk EP202，[851.16-884.52]，L1）

**史观**：

- 总纲5 没有必然性，只有偶然性：HAMMER 灾难恢复工具并非按计划演进的产物，而是由一位用户坏盘且无备份的偶然求助直接触发——Dillon 在规划两年的 fsck 处处碰壁后，反而用一两天写成临时方案并成为发布特性，显示工程演进中偶然事件对技术路线的实际塑造力。（BSDTalk EP202，[747.92-807.80]，L1）
