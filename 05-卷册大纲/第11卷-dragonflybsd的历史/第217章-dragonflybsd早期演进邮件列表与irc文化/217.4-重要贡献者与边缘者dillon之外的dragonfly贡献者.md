# 217.4 重要贡献者与边缘者：Dillon 之外的 DragonFly 贡献者——Jeffrey Hsu（核心开发者）、Sascha Wildner（长期 release engineer）、Francois Tigeot（HAMMER 文件系统协作者）等被忽视的 DragonFly 贡献者群体

**史料**：dragonfly.duckdb dragonfly-src 仓库 contributors 表（Hsu 280 条 2003-07-24 至 2007-11-06、Wildner 合并 10846 条 2004-12-17 至 2026-05-21）；dragonfly.duckdb dragonfly-src 仓库 commits 表（Hsu 与 Wildner 各自 commit message 主题分布）；DragonFly BSD 邮件列表存档（Hsu 与 Wildner 发言记录）

## 217.4.2 边缘贡献者的融入困境与流失

**要点**：dragonfly.duckdb dragonfly-src 仓库 contributors 表显示 7173 条贡献者记录中绝大多数仅有 1-10 条 commit 即停止贡献——典型早期边缘贡献者如 Max Okumoto（603 条，2004-12-08 至 2005-09-24，活跃期不足 1 年）、Jeroen Ruigrok/asmodai（547 条，2003-08-05 至 2005-09-25，活跃期 2 年）、Hiten Pandya（503 条，2003-07-26 至 2007-08-06，活跃期 4 年）。边缘贡献者的流失直接加剧巴士因子问题——早期贡献者淡出后无新贡献者补位

**史料**：dragonfly.duckdb dragonfly-src 仓库 contributors 表（7173 条记录，按 commit_count 与 first_commit_date/last_commit_date 间隔统计活跃期）；dragonfly.duckdb dragonfly-src 仓库 commits 表（按 author_email 与 author_date 交叉统计显示贡献者淡出时点）；DragonFly BSD 邮件列表存档（新贡献者出现与消失记录）

**史观**：第 14 章边缘者贡献：边缘者流失对项目的影响——dragonfly.duckdb 显示 DragonFly 早期（2003-2007）边缘贡献者活跃度较高（Okumoto/Ruigrok/Pandya/Hsu 合计约 1933 条 commit），2008 年后该批边缘贡献者集体淡出，同期项目 commit 频率从 2005 年峰值 4194 条/年逐步下降——边缘者流失与项目整体活跃度下降存在时间相关性

**辨析**：贡献者流失的原因多样——bsd_commits.duckdb 显示 Okumoto/Ruigrok/Pandya 均在 2005-2007 年间停止贡献，时点接近但不完全同步，可能因个人职业变动、项目方向分歧、社区氛围变化等多重因素；不得单凭 commit 停止时点即归因于“社区文化不友好”；Hsu 2007 年停止后由 Sepherosa Ziehau 2005-2021 年间接续，反映核心子系统维护存在交接但边缘贡献者无交接机制

**要点**：

- DragonFly BSD Digest 的起源由当事人自述：2003 年 Matt Dillon 自 FreeBSD 4 分叉出 DragonFly 时他注意到项目启动，想贡献却不愿以写 C 为业，而 BSD 项目几乎所有互动都在邮件列表上进行，遂决定做一份摘编网站替人筛选要闻；他先默默试运行约一周确认能坚持，再公开宣布，至访谈时已持续约五年。（BSDTalk EP169，[91.60-158.72]，L1）
- Digest 之外的社区建设包括：将 FreeBSD Handbook 转换为 DragonFly 版并自 SGML 体系迁移至今日的 wiki、搭建 DragonFly 网站的邮件列表存档、推动 wiki 与主站整合；计划次年为 DragonFly 设立非营利法人，以摆脱互联网散兵游勇状态——法人实体便于美国捐赠者移交硬件、也能提供章程焦点。他盛赞 FreeBSD Foundation 的示范：送开发者赴会、推动项目完成，年度 30 万美元募款目标接近达成。关于社区健康度，他坦承 DragonFly 仍然很小，愿意做操作系统的人数增长远不及互联网，热点在 Twitter、WordPress 式应用开发；DragonFly 的吸引力恰在人少而无既有结构，可以说事情可以这样办、没有必须沿袭的包袱，代价是谁发声谁干活。（BSDTalk EP169，[158.72-402.22]，L1）
- 他长期以 DragonFly 自用：Digest 网站本身运行于 DragonFly 机器多年；系统应用以 pkgsrc 安装，pkgsrc 对频繁升级不友好但可忍受；他在 packagebox.dragonflybsd.org 上对 pkgsrc 季度发布做约 8000 个包的 bulk build，实测这是给文件系统施压的极好方式，该机器当前即运行 HAMMER 文件系统，尽管他个人并未在其他场合使用 HAMMER。（BSDTalk EP169，[402.22-476.42]，L1）
- 他对 BSD 哲学的被吸引点做了非宗教式表述：1998 至 1999 年在旧东家因同事偶语而装上 FreeBSD 4 尝试，相较 Linux，吸引他的不是许可证立场，而是一种以质量为本的做事方式——写代码因为它是该做的对事、是高质量的做法，而非软件必须自由的信仰宣示；他认为这种 quality-based 的取向让工作本身更有趣。（BSDTalk EP169，[493.30-573.38]，L1）
- Digest 的编辑理念被他上升为氧气论：一个操作系统需要其周围的气氛，胜过其他一切。主流科技博客以轻快语调追逐硬件与游戏，不追问计算机史从何而来、BSD 为何重要；而每个计算机系三年级学生都能写一个操作系统，写完却会发现无事可做，因为操作系统真正需要的是周边生态与身份氛围。他引述某个他记不清归属者的说法，认为 FreeBSD Diary、BSD Talk 与 Digest 的工作正是定义“说自己是 BSD 用户意味着什么”，这也是 advocacy 的实质。（BSDTalk EP169，[573.38-789.40]，L1）
- 关于志愿项目的维持机制，他将 BSD 项目与其他全志愿非营利事业（教育、食物、住所）视为同构：发不出工资，奖赏只能是公开庆祝成就——提交日志无人翻检，必须有人明说这块硬件能用了多亏某人，哪怕回报只是日后会议上一杯致谢的酒。会议被他视为提交活动的催化剂：会议数量增长是生态健康迹象，每次会议后都有活动爆发，第 25 届混沌通信大会收官当天 Simon Schubert 即因与会交流而向 DragonFly 集中提交；面对面接触带来的即时反馈远胜邮件。（BSDTalk EP169，[794.44-1008.94]，L1）
- Justin Sherrill 的主要项目工作是维护 DragonFly BSD Digest，每日从邮件列表中选摘要点；HAMMER 是 Matt Dillon 打造的历史保留、即时检查、可无限快照的文件系统，用户可按磁盘空间余量随时回溯历史版本文件，受访者称其为救命文件；HAMMER 1 采用 master-slave 复制，可在同一机器或跨机乃至跨互联网指定从盘并按带宽同步，主盘损毁时可将从盘提升为主，单主多从且各从盘可保留不同时长的历史，例如用大慢盘存放长期历史。（BSDTalk EP212，[54.16-349.12]，L1）
- HAMMER 1 已功能完备并经数年使用与修复锤炼；Sherrill 本人在重要数据上启用全部特性，开启去重后回收了约 20% 的磁盘空间；去重提供实时与隔夜两种模式，他使用隔夜模式即可满足需求，实时去重被比作快速复制——在大量数据复制过程中即时去重；HAMMER 内存要求很低，256MB 内存即可运行（需关闭吃内存的隔夜 reblocking），与作为对比基准的 ZFS 形成鲜明反差。（BSDTalk EP212，[447.16-638.52]，L1）
- HAMMER 与 ZFS 的主要差距在工具集成而非核心能力：ZFS 将磁盘管理与 RAID 等工具内建、具有所想即所得的便利，HAMMER 则采用主从复制而非 RAID，期望软件 RAID 的用户应转向硬件 RAID 卡；因此更好的硬件 RAID 卡驱动支持被视为 DragonFly 成败的关键因素，Sascha Wildner 近期引入 Areca 卡支持且该公司亲自测试了驱动，被受访者视为项目获得业界承认的时刻。（BSDTalk EP212，[641.47-760.04]，L1）
- HAMMER 2 在访谈前数日刚进入代码树，处于极早期，Matt Dillon 称六个月内无可玩内容、年底方能完成；其 multi-master 设计是 DragonFly 早期集群目标的当代回归——最初目标是整个操作系统的集群，而多核处理器的普及使单机多核已能满足算力需求，集群理想遂转向存储层；HAMMER 2 将继承 HAMMER 1 全部特性，新增更精细的去重（可只对部分文件系统执行）与配额支持，并已有技术性 release notes 发布。（BSDTalk EP212，[207.66-447.16]，L1）
- 架构与产品想象方面，DragonFly 支持 i386 与 x86_64；Sherrill 口头上一直鼓吹 ARM（尤其即将到来的 ARMv8）但自认缺乏执行技能、项目内亦无人推动，且新架构移植本身极为困难；他设想基于 ARM 的小型 NAS 设备运行 HAMMER、在亲属家放置第二台作受信备份并经 SSH 同步文件系统，认为这是一个亟待出现的 FreeNAS 的 HAMMER 等价物——相较每月三十美元电费的台式机，小 ARM 盒更容易被家庭接受。（BSDTalk EP212，[830.22-927.22]，L1）
- 社区观察：DragonFly 开发者总数保持静态，有人离开也会回归；受访者担忧编写操作系统已不像十年前那样吸引人，潜在贡献者转向 Android、iOS 应用开发；非 Windows 系统的开发日益由公司赞助，他即兴估计 Linux 内核约八成贡献来自公司付费开发者；开源从业余者人人贡献转向受益公司付费贡献，他不以此为大恶——认为水涨众船高——但怀旧 2002 年前后一个 tarball 即可开搞的朴素网页与个人痴迷式文档传统，对比如今要么商业抛光、要么近乎不存在的生态，并自承此判断并不科学。（BSDTalk EP212，[1018.30-1251.22]，L1）
- 治理与基础设施实态：DragonFly 完全由志愿者运作且没有法人实体，Sherrill 长期想创建 DragonFly 非营利组织以获得可签约、可持有版权的法律实体；代码版权栏写 DragonFly BSD Project 但技术上并不存在该实体，受访者自承非律师、不知此问题多严重；基础设施是一堆地下室——主站是 Matt Dillon 家中的数台机器，pkgsrc 批量构建依赖志愿者捐赠的机器空间，无商业实体托管；版本控制已由 CVS 转 Git 且相当成功，pkgsrc 的 CVS 到 Git 转换正在进行；Sherrill 自愿出任 3.0 发布经理，尚余七个阻塞 bug，nightly build 与候选版已可下载；项目连续四年参与 Google Summer of Code 并拟再次参加。（BSDTalk EP212，[1251.22-1595.34]，L1）

**史观**：

- 总纲10 动手者创造历史：Digest 的五年自身即是历史由默默动手者写就的例证：一个不愿以写 C 为业、白天在墨盒制造厂维护老旧 Debian 系统的普通人，以每日筛读邮件列表、转换手册、搭建存档的琐碎劳动，为一个分叉项目保住了公共记忆与氧气。操作系统的存续不只在提交日志里，也在这些无名整理者的持续劳作中。（BSDTalk EP169，[91.60-158.72]，L1）
- 总纲4 分离聚合是永恒规律：DragonFly 最初以整个操作系统的集群为目标，多核硬件的普及使单机算力已足，集群理想遂在 HAMMER 2 的 multi-master 存储设计中重新聚合，呈现目标随技术条件变迁而分离再聚合的轨迹。（BSDTalk EP212，[373.04-397.04]，L1）
- 总纲3 不存在进步，只有权力再分配：开源贡献结构从业余志愿者的普遍参与转向受益公司付费开发者（以 Linux 约八成贡献来自付费开发者的观察为代表），在受访者看来并非简单的进步或堕落，而是贡献权力在爱好者与资本方之间的再分配。（BSDTalk EP212，[1088.30-1111.56]，L1）
- 总纲10 动手者创造历史：DragonFly 的日常运转依赖地下室服务器、自愿发布经理、长期日更的 digest 等无名动手者的劳作维系，项目史的真实支撑并非治理宣言而是这些具体劳动。（BSDTalk EP212，[1322.12-1365.98]，L1）
