# 222.3 DragonFly BSD 2.x 时期的技术淘汰——UFS→HAMMER 1.0 默认、FreeBSD Ports→pkgsrc、传统内核调试 →vkernel 稳定（2008-2010）

## 222.3.1 UFS 默认文件系统 → HAMMER 1.0 默认（DragonFly 2.0，**2008.7.20**）

**要点**：DragonFly 2.0（**2008.7.20** 发布）将默认文件系统从 FreeBSD 4.x 继承的 UFS 切换为 Dillon 自研的 HAMMER 1.0，发行说明明确称 HAMMER 为默认文件系统，安装器在 `newfs` 阶段默认调用 `newfs_hammer` 而非 `newfs`；HAMMER 1.0 采用 B-tree 写时复制设计，支持历史快照、增量备份、多卷镜像，但默认 undo 空间与历史保留策略对内存有一定需求；UFS 仍保留在 base system 中作为可选文件系统，与 HAMMER 并行存在；这一切换让 DragonFly 成为 BSD 阵营中首个以自研写时复制文件系统为默认的项目，与 FreeBSD UFS、OpenBSD FFS、NetBSD FFS 形成对照

**史料**：DragonFly 2.0 release notes（**2008.7.20**）；Dillon HAMMER 设计文档 v1（2007 年首次发布）；DragonFly 源码 `sys/vfs/hammer/`；kernel@ 邮件列表 HAMMER 默认切换讨论 ［A］

**史观**：总纲第 17 条——软件工程：HAMMER 1.0 默认切换体现“先设计 → 实验引入 → 默认切换”的工程节奏；总纲第 6 条——技术路线分化：DragonFly 与 FreeBSD/OpenBSD/NetBSD 在文件系统默认选择上分化

**辨析**：UFS 切换为 HAMMER 默认的具体版本需考据——DragonFly 1.2（2006.2）仅引入 HAMMER 雏形，2.0（2008.7.20）才正式切换默认；HAMMER 1.0 与 ZFS 的功能对比需结合具体场景，避免笼统优劣判断；UFS 在 base system 中保留的时间长度需结合 commit log 核验

**文献**：DragonFly 2.0 release notes；HAMMER 设计文档；DragonFly 源码 sys/vfs/hammer/；kernel@ 邮件列表档案 ［A］

## 222.3.2 FreeBSD Ports → pkgsrc 采纳与 DPorts 雏形（2005-2011）

**要点**：DragonFly fork 自 FreeBSD 4.x 初期仍共享 FreeBSD Ports tree，但随代码差异扩大，ports tree 同步成本上升；2005 年 DragonFly 决定采纳 NetBSD 的 pkgsrc 作为补充软件包管理路径，与 FreeBSD ports 并行存在；pkgsrc 提供跨 BSD 通用软件包管理，但与 FreeBSD ports 不完全兼容，导致 DragonFly 用户面临双软件包管理系统的复杂性；2.10（2011）引入 DPorts 雏形——基于 pkgsrc 与 FreeBSD ports 的混合方案，为后续 DPorts 完整化奠定基础；这一时期的软件包管理演化“淘汰”了 DragonFly 对 FreeBSD ports 直接同步的依赖

**史料**：DragonFly 2005 年 pkgsrc 采纳公告；DragonFly 2.10 release notes DPorts 部分；DragonFly 邮件列表 pkgsrc/DPorts 讨论 ［A］

**史观**：总纲第 4 条——分离与聚合：DragonFly 软件包管理从 FreeBSD ports 转向 pkgsrc/DPorts 是分离聚合律的体现——技术分离推动软件包管理系统独立；总纲第 17 条——软件工程：软件包管理演化反映“先共享 → 后独立”的工程路径

**辨析**：pkgsrc 采纳的精确日期需考据——2005 年是 DragonFly 官方文档记载，但实际 commit 可能更早；DPorts 雏形与正式版的边界需考据——2.10 仅是雏形，正式 DPorts 在后续版本完善；pkgsrc 与 FreeBSD ports 在 DragonFly 中的并行持续时间需结合 commit log 核验

**文献**：DragonFly pkgsrc 采纳公告；DragonFly 2.10 release notes；DragonFly 邮件列表档案 ［A］

## 222.3.3 传统内核调试 → vkernel 用户态虚拟化稳定（DragonFly 1.8 → 2.x 持续改进）

**要点**：vkernel 由 Matt Dillon 开发，2006 年 9 月首次在 DragonFly 1.7 开发版中披露，**2007 年 1 月 30 日** 随 DragonFly 1.8 首次稳定发布，定位为 “虚拟内核架构”——kernel 代码编译为用户态进程运行，便于内核调试与一般虚拟化；vkernel 让 DragonFly 开发者可在用户态运行内核镜像进行调试，“淘汰” 了传统内核调试需要双机或串口连接的繁琐方式；2.x 时期 vkernel 持续改进，包括对多 vkernel 实例的支持、网络栈改进、内存管理优化；vkernel 与 Linux user-mode Linux、NetBSD rump kernel 形成跨项目对照。vkernel 与同期虚拟化技术对照如下：

    | 项目 | 路径 | 首次稳定 | 典型场景 |
    |---|---|---|---|
    | DragonFly vkernel | 用户态运行内核 | 2007.1.30（DragonFly 1.8） | 内核调试、轻量虚拟化 |
    | Linux user-mode Linux | 用户态运行内核 | 2001 | 内核调试 |
    | NetBSD rump kernel | 用户态运行内核子系统 | 2009 | 子系统调试、服务化 |
    | Xen（全系统虚拟化） | hypervisor | 2003 | 服务器虚拟化 |
    | KVM（全系统虚拟化） | 内核模块 + QEMU | 2007 | 服务器虚拟化 |
**史料**：DragonFly 1.8 release notes（**2007.1.30**）；**vkernel(7)** 手册页；Dillon 在 kernel@ 关于 vkernel 的设计发言；DragonFly 源码 `sys/platform/vkernel/` ［A］

**史观**：总纲第 17 条——软件工程：vkernel 是软件工程中“用户态虚拟化”哲学的具体实现；总纲第 22 条——BSD 反向影响线：vkernel 作为 DragonFly 的创新，与 Linux user-mode Linux、NetBSD rump kernel 形成跨项目影响

**辨析**：vkernel 稳定版本需考据——1.7 开发版首次披露，1.8 正式稳定发布；vkernel 的实际性能与限制需结合具体使用场景辨析；vkernel 与后续 6.0（2021.5.10）移除的关系需在叙事中标注

**文献**：DragonFly 1.8 release notes；vkernel(7) 手册页；DragonFly 源码 sys/platform/vkernel/；kernel@ 邮件列表档案 ［A］

## 222.3.4 与 FreeBSD/NetBSD/OpenBSD 同期文件系统/软件包管理演化的对照（2008-2010）

**要点**：2008-2010 年间 FreeBSD 8.x 引入 ZFS 默认文件系统选项、改进 pkg_install 与 pkgng 雏形；OpenBSD 4.4-4.8 改进 FFS 与 ports 系统；NetBSD 5.x 维护 pkgsrc 作为主软件包管理系统；DragonFly 2.x 同期完成 UFS→HAMMER 默认切换、pkgsrc 采纳、vkernel 稳定——四 BSD 在文件系统与软件包管理上演化路径分化明显，对照如下：

    | 项目 | 默认文件系统 | 软件包管理 | 同期关键演化 |
    |---|---|---|---|
    | FreeBSD 8.x | UFS（ZFS 可选） | pkg_install + pkgng 雏形 | ZFS 集成、DTrace、ULE 调度器改进 |
    | OpenBSD 4.4-4.8 | FFS | ports 系统 | 安全审计、pledge 前身工作 |
    | NetBSD 5.x | FFS | pkgsrc | 跨平台支持完善 |
    | DragonFly 2.x | HAMMER 1.0（默认） | pkgsrc + FreeBSD ports 并行 | UFS→HAMMER 默认、vkernel 稳定 |
    FreeBSD 追求 ZFS 与 pkgng 现代化、OpenBSD 坚守 FFS 与 ports 传统、NetBSD 维护 pkgsrc 跨平台、DragonFly 自研 HAMMER 与 vkernel

**辨析**：跨项目比较需结合具体场景——FreeBSD ZFS 适合大规模存储，OpenBSD FFS 适合安全审计，NetBSD pkgsrc 适合跨平台，DragonFly HAMMER 适合轻量级写时复制；性能对比缺乏权威基准，需对照同硬件同负载核验

## 222.3.5 批评层——对 UFS→HAMMER 1.0 默认切换的质疑（2008-2010）

**要点**：DragonFly 2.0（**2008.7.20**）将默认文件系统从 UFS 切换为 HAMMER 1.0 的决策面临三类批评。其一，“成熟度不足”批评——HAMMER 1.0 仅经 1 年密集开发（2007-2008 年 1,213 条 commit），dragonfly.duckdb dragonfly-src 仓库 `sys/vfs/hammer*` 路径 2007 年 commit 仅 181 条（设计阶段），2008 年激增至 1,213 条（工程爆发），但相比 UFS 数十年部署历史（源自 4.2BSD Fast File System 经 CSRG/McKusick 持续维护）与 ZFS 企业级团队开发（Sun Microsystems），HAMMER 1.0 的成熟度不足以承担默认文件系统职责。其二，“巴士因子风险”批评——dragonfly.duckdb dragonfly-src 仓库 contributors 表显示 HAMMER 设计主要由 Dillon 个人完成（2008 年 Dillon 个人占比仍居主导），HAMMER 作为默认文件系统后 Dillon 个人风险即项目风险，与 FreeBSD UFS 由 McKusick 及多位 committer 共同维护、OpenBSD FFS 由 de Raadt 与多位开发者审计的多元维护形成对照。其三，“用户迁移成本”批评——UFS 用户需迁移至 HAMMER 1.0，而 HAMMER 1.0 的功能集较小（无 ZFS 的 send/receive、无 ZFS 的 pool 管理），迁移后的功能损失需用户承担；FreeBSD 8.x 同期采取保守策略——UFS 仍为默认，ZFS 作为可选，让用户按需选择，避免强制迁移

**史料**：DragonFly 2.0 release notes（**2008.7.20** HAMMER 默认切换）；dragonfly.duckdb dragonfly-src 仓库 `sys/vfs/hammer*` 路径 commit 演化（2007 年 181 条、2008 年 1,213 条、2009 年 282 条）；dragonfly.duckdb dragonfly-src 仓库 contributors 表（2008 年 bus factor：top10 占 91.56%、Dillon 个人占比）；FreeBSD 8.0 release notes（UFS 默认、ZFS 可选）；HAMMER 设计文档 v1 ［A］

**史观**：总纲第 8 条——本体论上各方平等：UFS、HAMMER、ZFS 三种文件系统在本体论上地位相等，“成熟度”与“功能集”的差异是经验事实而非本体论等级；总纲第 17 条——软件工程：HAMMER 1.0 默认切换体现“先设计 → 实验引入 → 默认切换”的工程节奏，但批评者质疑该节奏过快

**辨析**：考据过程留痕——【查证来源】HAMMER 1.0 默认切换经 DragonFly 2.0 release notes 一手核验，dragonfly.duckdb dragonfly-src 仓库 tags 表无 v2.0 系列 tag，2.0 发布日期 **2008.7.20** 须与 Dillon 在 kernel@ 邮件列表的 2.0 RELEASED 公告交叉验证；HAMMER 路径 commit 统计以 `sys/vfs/hammer*` 路径匹配，可能遗漏散落在其他路径的相关 commit（如文档、测试、工具）；【交叉验证方法】HAMMER 1.0 与 UFS/ZFS 的成熟度对比以 dragonfly.duckdb commit 量与部署历史为依据，但 commit 量不等于质量——2008 年 HAMMER 路径 1,213 条 commit 含大量基础工作，并非全部用于核心功能完善；UFS 的“数十年部署历史”以 4.2BSD FFS（1983）为起点，须经 McKusick 相关论文与 FreeBSD release notes 交叉验证；【0 信任原则·Dillon 自述考据】Dillon 在 HAMMER 设计文档中关于“轻量级写时复制”优于 ZFS 的表述属当事人自辩，须以独立第三方 benchmark 交叉验证，不得仅凭 Dillon 单方面陈述采信；【存疑判定依据】HAMMER 1.0 在 2.x 周期的实际部署规模无权威统计，dragonfly.duckdb 显示 2.x 周期 HAMMER 相关 commit 以功能完善为主而非安全修复，但部署规模有限可能导致漏洞未充分暴露 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

## 222.3.6 反批评层——Dillon 与 DragonFly 阵营对 HAMMER 默认切换的辩护（2008-2010）

**要点**：Dillon 与 DragonFly 阵营对 HAMMER 默认切换的辩护以工程哲学与架构一致性为核心。第一层是 HAMMER 设计的前置周期——dragonfly.duckdb dragonfly-src 仓库 `sys/vfs/hammer*` 路径显示 HAMMER 雏形在 1.2（2006.2）即披露，2007 年 181 条 commit 为设计阶段，2008 年 1,213 条 commit 为工程爆发，实际开发周期为 2 年（2006-2008），并非仓促切换。第二层是 UFS 的历史包袱——UFS 作为 FreeBSD 4.x 继承的文件系统，其设计源于 4.2BSD FFS（1983），DragonFly fork 后继续以 UFS 为默认即继续承担 4.x 的技术债务，与 LWKT 消息传递的轻量级内核哲学不匹配。第三层是 HAMMER 的架构一致性——HAMMER 的 B-tree 写时复制设计与 LWKT 的消息传递、token 机制在哲学上一致（皆追求轻量级与避免复杂锁），HAMMER 作为默认文件系统是 DragonFly 架构哲学的完整呈现。第四层是 UFS 的保留——dragonfly.duckdb dragonfly-src 仓库显示 UFS 仍保留在 base system 中作为可选文件系统（与 HAMMER 并行存在），用户可按需选择，并非强制迁移。第五层是 HAMMER 的功能优势——HAMMER 1.0 支持快照、历史记录、增量备份、多卷镜像，这些功能 UFS 不支持（需 `mksnap_ffs` 等外部工具），HAMMER 默认切换让 DragonFly 用户获得现代文件系统功能

**史料**：DragonFly 2.0 release notes（HAMMER 默认、UFS 保留为可选）；dragonfly.duckdb dragonfly-src 仓库 `sys/vfs/hammer*` 路径 commit 演化（2006 年雏形、2007 年设计、2008 年工程爆发）；Dillon HAMMER 设计文档 v1；DragonFly 源码 `sys/vfs/hammer/` 与 `sys/vfs/ufs/`；kernel@ 邮件列表 HAMMER 默认切换讨论 ［A］

**史观**：总纲第 17 条——软件工程：HAMMER 默认切换是“先设计 → 实验引入 → 默认切换”工程节奏的完成，体现软件工程中“架构一致性”优先于“成熟度继承”的哲学；总纲第 6 条——技术路线分化：DragonFly 以 HAMMER 默认切换完成与 FreeBSD UFS/OpenBSD FFS/NetBSD FFS 的文件系统路线分化

**辨析**：考据过程留痕——【查证来源】HAMMER 雏形在 1.2（2006.2）披露经 DragonFly 1.2 release notes 核验，dragonfly.duckdb dragonfly-src 仓库 `sys/vfs/hammer*` 路径 2006 年 commit 须单独查询核验（现有数据报告显示 2007 年才出现 HAMMER commit，2006 年雏形可能以设计文档与头文件形式存在，散落在 `sys/vfs/` 与其他路径）；UFS 保留为可选经 DragonFly 2.0 release notes 核验，dragonfly.duckdb dragonfly-src 仓库 `sys/vfs/ufs/` 路径 commit 在 2.x 时代仍持续，反映 UFS 维护未停止；【交叉验证方法】HAMMER 与 LWKT/token 的架构一致性以 Dillon 设计文档为依据，但“架构一致性”是工程哲学判断，无量化标准，须以 HAMMER 的 B-tree 写时复制设计与 LWKT 的消息传递设计的哲学比较核验；【0 信任原则·Dillon 自述考据】Dillon 关于 HAMMER“轻量级写时复制”优于 ZFS 的表述属当事人自辩，HAMMER 的实际内存消耗与稳定性须以独立第三方测试核验；【存疑判定依据】HAMMER 1.0 的功能优势（快照、历史记录、增量备份）的实际性能与稳定性须以部署案例核验，dragonfly.duckdb 显示 2.x 周期 HAMMER 相关 commit 以功能完善为主，功能集的实际完整性须结合 commit message 主题词单独查询 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

## 222.3.7 再批评层与合图层——对 HAMMER 默认切换的再审视与项目史观总纲第 6 条、第 8 条的综合（2008-2010）

**要点**：对 HAMMER 默认切换反批评的再审视可见 2.x 时代 fork 路线在文件系统层的双重面相——一方面，dragonfly.duckdb dragonfly-src 仓库显示 HAMMER 1.0 在 2.x 周期持续维护（2009 年 282 条 commit、29 个文件），2.x 周期 dragonfly.duckdb 未见直接归因于 HAMMER 文件系统的 CVE，证明 HAMMER 1.0 作为默认文件系统在 2.x 周期基本稳定；另一方面，dragonfly.duckdb 显示 HAMMER 部署规模有限（2.x 周期 DragonFly 社区规模远小于 FreeBSD），2.x 周期无 HAMMER CVE 可能因部署规模而非设计优越性，HAMMER 漏洞史须以 3.x/4.x 周期的实际 CVE 数据验证。以项目史观总纲第 6 条（和解优于斗争）审视，HAMMER 默认切换是 fork 后技术分离的完成——dragonfly.duckdb 显示 2007 年 HAMMER 首引（commit `8750964d1997`）后 DragonFly 从 FreeBSD 回移代码基本停止，2008 年 HAMMER 默认切换使 DragonFly 在文件系统层彻底脱离 FreeBSD 4.x UFS 血缘，和解在代码层面的“短暂接纳”（2003-2007）至 2.x 时代彻底结束，HAMMER 默认切换是和解失败的最终标志。以第 8 条（本体论上各方平等）审视，UFS 路线与 HAMMER 路线在本体论上地位相等——二者皆是各主体性呈现的技术路径，差异仅是一刻状态的不同；UFS 的“数十年成熟”与 HAMMER 的“轻量级创新”在本体论上无高下之分

**史料**：项目史观总纲第 6 条、第 8 条；dragonfly.duckdb dragonfly-src 仓库 `sys/vfs/hammer*` 路径 commit 演化（2009 年 282 条 commit、29 个文件）；dragonfly.duckdb dragonfly-src 仓库 commits 表（2007 年 HAMMER 首引 commit `8750964d1997` 后回移停止）；dragonfly.duckdb dragonfly-src 仓库 2.x 周期 HAMMER 相关 CVE 查询（无直接归因于 HAMMER 的 CVE） ［A］

## 222.3.8 批评层——对 pkgsrc 采纳与 DPorts 雏形的质疑（2005-2011）

**要点**：DragonFly 2.x 时期软件包管理从 FreeBSD Ports 转向 pkgsrc/DPorts 的路径面临三类批评。其一，“双系统复杂性”批评——2005 年 DragonFly 采纳 NetBSD 的 pkgsrc 后，pkgsrc 与 FreeBSD ports 在 DragonFly 中并行存在，用户面临双软件包管理系统的复杂性，pkgsrc 与 FreeBSD ports 不完全兼容，导致软件可用性与依赖管理混乱。其二，“软件可用性不足”批评——pkgsrc 的软件包数量少于 FreeBSD ports（FreeBSD ports 在 2005-2011 年间维持数万 ports），DragonFly 用户通过 pkgsrc 获得的软件范围受限，与 FreeBSD 用户的软件体验形成落差。其三，“DPorts 雏形不完整”批评——2.10（2011）引入的 DPorts 雏形基于 pkgsrc 与 FreeBSD ports 的混合方案，但雏形与正式版边界模糊，DPorts 在 2.x 时代末期仍未完整化，DragonFly 软件包管理处于过渡期的不确定状态。对比 FreeBSD 8.x 同期推进 pkgng 雏形（更现代的二进制包管理）、OpenBSD ports 系统（与 base system 紧密集成）、NetBSD pkgsrc（作为原生软件包管理），DragonFly 的 pkgsrc+DPorts 路径在成熟度与一致性上均落后

**史观**：总纲第 8 条——本体论上各方平等：FreeBSD ports、NetBSD pkgsrc、OpenBSD ports、DragonFly pkgsrc/DPorts 四种软件包管理系统在本体论上地位相等，“成熟度”与“一致性”的差异是经验事实而非本体论等级；总纲第 4 条——分离与聚合：DragonFly 软件包管理从 FreeBSD ports 转向 pkgsrc/DPorts 是分离聚合律的体现，但批评者质疑该分离聚合的代价过高

## 222.3.9 反批评层——DragonFly 阵营对 pkgsrc/DPorts 批评的回应（2005-2011）

**要点**：DragonFly 阵营对 pkgsrc/DPorts 批评的回应以分离必要性与跨 BSD 协作为核心。第一层是 FreeBSD ports 同步成本上升——DragonFly fork 自 FreeBSD 4.x 后，随着 LWKT、token、HAMMER 等自有创新的引入，与 FreeBSD 4.x 的代码差异逐渐扩大，FreeBSD ports tree 的同步成本随之上升，继续依赖 FreeBSD ports 即继续承担同步债务。第二层是 pkgsrc 的跨 BSD 通用性——pkgsrc 作为 NetBSD 的原生软件包管理系统，设计上支持跨 BSD 通用，DragonFly 采纳 pkgsrc 即接入 NetBSD 的跨平台软件包生态，与 NetBSD 社区建立协作关系，是 BSD 阵营内部的跨项目聚合。第三层是 DPorts 雏形的前瞻性——2.10（2011）引入的 DPorts 雏形虽未完整化，但为后续 DPorts 完整化奠定基础，DPorts 后续成为 DragonFly 的主软件包管理路径，证明 2.x 时代的雏形投入具有前瞻性。第四层是软件包管理的独立性——pkgsrc/DPorts 路径让 DragonFly 在软件包层面建立独立于 FreeBSD 的能力，与 HAMMER 默认切换（文件系统独立）、LWKT（内核独立）共同构成 DragonFly 的完整技术身份

**史观**：总纲第 4 条——分离与聚合：DragonFly 软件包管理从 FreeBSD ports 转向 pkgsrc/DPorts 是分离聚合律的体现——技术分离推动软件包管理系统独立，同时聚合至 NetBSD pkgsrc 生态；总纲第 17 条——软件工程：软件包管理演化反映“先共享 → 后独立”的工程路径，DPorts 雏形是该路径的中间状态
