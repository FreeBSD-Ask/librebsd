# 220.2 DragonFly 1.x 周期漏洞与安全响应——FreeBSD SA 跟进、OpenSSH/OpenSSL 漏洞群与 LWKT MP-safe 子系统的并发安全考量（2003-2007）

## 220.2.1 CVE 编号稀疏性与 FreeBSD SA 跟进机制的建立（2003-2006）

**要点**：DragonFly 1.x 版本周期（2003-07-01 至 2007-02-01）dragonfly.duckdb dragonfly-src 仓库仅收录 5 条去重 CVE 与 12 条无 CVE 编号的 Security fix commit，但 17 条早期漏洞补遗显示实际漏洞响应数量远超数据库收录——DragonFly fork 自 FreeBSD 4.x 后早期安全响应主要通过跟进 FreeBSD SA 公告实现，2003-09-25 Dillon commit `8fd3e627ee2c3d0dbe7136c313bc7150b59a320d` 标注 "Apply FreeBSD Security Advisory FreeBSD-SA-03:14.arp. Fix DOS crash due to arp starvation."，2004-11-18 asmodai commit `9eb5b2ab3854c519dbaaa634d22ee557bc445b88` 标注 “Merge FreeBSD SA 04:16 security fix.”，二者均以 FreeBSD SA 编号引用而非 CVE 编号——DragonFly 1.x 时期 commit message 引用 FreeBSD SA 编号的频率高于 CVE 编号，反映 fork 初期对上游 FreeBSD 安全公告体系的依赖

**史料**：dragonfly.duckdb dragonfly-src 仓库 commit `8fd3e627ee2c3d0dbe7136c313bc7150b59a320d`（2003-09-25 Dillon “Apply FreeBSD Security Advisory FreeBSD-SA-03:14.arp”）、commit `9eb5b2ab3854c519dbaaa634d22ee557bc445b88`（2004-11-18 asmodai “Merge FreeBSD SA 04:16 security fix.”）、commit `10a4d47e52c899a6f589f523a04e0dc9f2e3007a`（2003-09-16 Dillon “update version to match FreeBSD after buffer security fix.”）；原材料/研究/bsd 漏洞史/版本周期/dragonflybsd-1.x.md 早期漏洞补遗 17 条 ［A］

**史观**：总纲第 4 条——分离聚合是永恒规律：DragonFly fork 自 FreeBSD 4.x 是分离聚合律的体现，但 fork 后安全响应仍聚合至 FreeBSD SA 体系——这种 “代码分离、安全响应聚合” 的张力是 fork 项目初期的典型特征，反映 DragonFly 在建立独立安全响应能力前对上游的路径依赖

**辨析**：DragonFly 1.x 时期 CVE 编号引用稀疏的原因有二——其一，2003-2006 年 CVE 编号体系尚未全面普及，部分漏洞以 FreeBSD SA 编号或 CERT VU 编号引用；其二，DragonFly fork 后部分 commit message 沿用 FreeBSD 习惯引用 SA 编号而非 CVE 编号；dragonfly.duckdb 收录的 5 条去重 CVE 均集中于 2006 年，2003-2005 年的漏洞响应主要以 FreeBSD SA 编号或无编号 Security fix commit 形式存在

**文献**：dragonfly.duckdb dragonfly-src 仓库；原材料/研究/bsd 漏洞史/版本周期/dragonflybsd-1.x.md；FreeBSD-SA-03:14.arp 公告；FreeBSD-SA-04:16 公告 ［A］

## 220.2.2 OpenSSH/OpenSSL 漏洞群——CVE-2006-0225/CVE-2006-4339/CVE-2006-4924/CVE-2006-5051（2006）

**要点**：DragonFly 1.x 周期数据库收录的 5 条去重 CVE 中 4 条集中于 OpenSSH 与 OpenSSL 组件，详见下表：

| CVE 编号 | 组件 | 技术机制 | 修复者 | 修复日期 | commit hash |
|---|---|---|---|---|---|

| CVE-2006-4339 | OpenSSL | RSA 签名伪造 | Simon Schubert | 2006-09-06 | `7a1c30b32857247c5a0da44330ecf45ff0c135c7` |
| CVE-2006-4924 | OpenSSH | 拒绝服务 | Victor Balada Diaz | 2006-10-01 | `b96fff2ab5ed2a4f48ae6c59e5ec09640645c091` |
| CVE-2006-5051 | OpenSSH | 释放后使用 | Victor Balada Diaz | 2006-10-01 | `b96fff2ab5ed2a4f48ae6c59e5ec09640645c091`（同上） |

4 条 CVE 均无 CVSS v3 评分，NVD 未为其提取 v3 评分；CVE-2006-0225 与 CVE-2006-5051 涉及 OpenSSH 4.2p1 的 **scp(1)** 与信号处理路径，反映 DragonFly 1.x 时期 OpenSSH 版本跟进的紧迫性。Schubert 修复 CVE-2006-4339 的 commit message 原文为：

    > Fix OpenSSL RSA Signature Forgery (CVE-2006-4339)
**史料**：dragonfly.duckdb dragonfly-src 仓库 commit `c2e4f831d184302b23589c73e8e691dc87c026a0`（2006-02-13 Simon Schubert “Fix a possible local privilege escalation bug in scp.”）、commit `7a1c30b32857247c5a0da44330ecf45ff0c135c7`（2006-09-06 Simon Schubert “Fix OpenSSL RSA Signature Forgery (CVE-2006-4339)”）、commit `b96fff2ab5ed2a4f48ae6c59e5ec09640645c091`（2006-10-01 Victor Balada Diaz “Fix security issues CVE-2006-4924 and CVE-2006-5051.”）；NVD CVE-2006-0225/CVE-2006-4339/CVE-2006-4924/CVE-2006-5051 条目 ［A］

**史观**：总纲第 10 条——动手者创造历史：Simon Schubert 与 Victor Balada Diaz 作为 DragonFly 核心开发者承担了 1.x 时期 OpenSSH/OpenSSL 漏洞响应的主要工作——Schubert 在 2006 年 2 月至 9 月间独立修复 3 条 CVE，Balada Diaz 在 2006 年 10 月修复 2 条 CVE，二者的密集贡献是 small-team 项目中 “边缘者承担安全关键基础设施” 的典型显现

**辨析**：CVE-2006-0225 的 CVSS v2 评分在 NVD 中未提取，技术机制为 **scp(1)** 文件名含 shell 元字符或空格时被二次扩展，攻击者可借构造的文件名执行任意命令实现本地提权——此漏洞影响 OpenSSH 4.2p1 及更早版本，DragonFly 1.x 时期 OpenSSH 版本须以 commit log 中 OpenSSH 版本号变更确认；CVE-2006-4924 与 CVE-2006-5051 由同一 commit 修复，前者为拒绝服务后者为释放后使用，二者影响 OpenSSH 信号处理路径；4 条 CVE 均无 CVSS v3 评分，写作中不臆造评分

**文献**：dragonfly.duckdb dragonfly-src 仓库 commit `c2e4f831d184302b23589c73e8e691dc87c026a0`、`7a1c30b32857247c5a0da44330ecf45ff0c135c7`、`b96fff2ab5ed2a4f48ae6c59e5ec09640645c091`；NVD CVE-2006-0225、CVE-2006-4339、CVE-2006-4924、CVE-2006-5051 ［A］

**辨析**：CVE-2006-4304 影响内核 PPP 代码（**ippp(4)** 与 **pppoe(4)** 共享的 `net/if_spppsubr.c`），技术机制为对 peer 呈现的选项检查不足导致缓冲区溢出——此漏洞由 NetBSD 先发现并修复（NetBSD rev 1.96），DragonFly 跟进合并；栈内存泄露漏洞由 Xin Li 报告，影响所有将内核栈内存复制到用户态的系统调用——Hsu 的修复在函数返回前将栈内存清零；CERT VU#697164 的具体技术细节须查 CERT 原始公告核实

## 220.2.4 LWKT MP-safe 子系统与 HAMMER 雏形期的并发安全考量（2003-2007）

**要点**：DragonFly 1.x 时期 LWKT（Light Weight Kernel Threading）子系统的 MP-safe 设计对漏洞响应产生双重影响——其一，LWKT 的消息传递模型与 token 机制替代传统 mutex，减少了部分竞态条件漏洞的风险（token 不持有时不阻塞其他 CPU，降低了锁竞争导致的死锁类漏洞）；其二，LWKT 引入新的并发复杂性——每 CPU 线程模型与 IPI（Inter-Processor Interrupt）消息传递的调试困难让并发相关漏洞的定位与修复成本高于传统锁模型；dragonfly.duckdb dragonfly-src 仓库 1.x 周期未见直接归因于 LWKT 并发缺陷的 CVE，但栈内存泄露漏洞（Hsu 2006-04-21 commit `60d8d1d3fb1751a713308fc989a1d97ad5ea256c`）的修复路径涉及内核入口点的并发路径——须在多 CPU 同时进入系统调用时确保栈内存清零；HAMMER 文件系统在 1.x 时期仍为雏形（1.2 引入设计讨论），1.x 周期数据库未见 HAMMER 相关 CVE，HAMMER 漏洞史主要集中于 2.x 周期（HAMMER 1.0 发布后）

**史料**：dragonfly.duckdb dragonfly-src 仓库 1.x 周期 LWKT/token 相关 commit；commit `60d8d1d3fb1751a713308fc989a1d97ad5ea256c`（2006-04-21 Jeffrey Hsu 栈内存清零）；DragonFly 1.0 Release Notes LWKT 部分；Matt Dillon LWKT 设计文档 ［A］

**史观**：专题语：LWKT 的 MP-safe 设计作为 “形式主义化” 的工程实践——将 “轻量级内核” 的哲学固化为 token 与消息传递的代码结构，这一形式选择直接塑造了 DragonFly 的漏洞响应模式：并发相关漏洞的修复须遵循 LWKT 的消息传递语义而非传统锁语义，是 “形式改变内容能力” 在安全响应层的体现

**辨析**：LWKT 消息传递模型对竞态条件漏洞的防御效果无同行评审研究证实——token 机制理论上减少了持锁等待导致的死锁，但 IPI 消息传递的异步性可能引入新的时序漏洞；1.x 周期未见直接归因于 LWKT 并发缺陷的 CVE，可能因 DragonFly 1.x 时期 SMP 部署规模有限，并发漏洞未充分暴露；HAMMER 雏形期（1.2-1.8）的安全考量须以 HAMMER 设计文档与 2.x 周期 HAMMER 1.0 发布后的漏洞史反推

**文献**：dragonfly.duckdb dragonfly-src 仓库；DragonFly 1.0 Release Notes；Matt Dillon LWKT 设计文档 ［A］
