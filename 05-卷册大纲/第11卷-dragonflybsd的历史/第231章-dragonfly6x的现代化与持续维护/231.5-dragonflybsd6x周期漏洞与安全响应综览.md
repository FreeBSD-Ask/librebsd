# 231.5 DragonFly BSD 6.x 周期漏洞与安全响应综览——16 个 CVE commit 背后的工程伦理

## 231.5.1 DragonFly 6.x 周期安全态势总览——16 个 CVE commit 的数据切片

**要点**：DragonFly BSD 6.x 周期（**2020 年 6 月 1 日** 至 **2026 年 7 月 22 日**，覆盖 v6.0.0 于 **2021 年 5 月 7 日** 发布至 v6.4.2 于 **2025 年 5 月 9 日** 发布）数据库共记录 **16 条 CVE 相关 commit**，对应 **32 个去重 CVE**；NVD 元数据中仅 1 个 CVE 有 CVSS v3.x 评分——CVE-2024-6387（regreSSHion，CVSS 8.1 High），其余 31 个 CVE 在本地 cvelistV5 镜像中无 CVSS v3 评分；这一数据分布与 FreeBSD 14.x 周期（648 条 CVE commit、189 个去重 CVE、80 个 FreeBSD-SA）形成鲜明对比——DragonFly 6.x 周期 CVE commit 量仅为 FreeBSD 14.x 同期的 2.47%，且无任何正式 Security Advisory。6.x 周期漏洞来源分布如下：

    | 来源类别 | commit 数 | 占比 | 具体组件/CVE |
    |---|---|---|---|
    | 贡献组件 vendor import | 12 条 | 75% | expat/libarchive/libressl/zlib/libpcap/less/openssh |
    | FreeBSD 安全补丁 MFC 回溯 | 2 条 | 12.5% | CVE-2023-3107、CVE-2008-2476 |
    | DragonFly base 本地修复 | 2 条 | 12.5% | **ftpd(8)** CVE-2020-7468（两条 commit 对应同一 CVE 的不同分支回溯） |
    base 系统原创漏洞极少，与 DragonFly base 代码量小、社区审计投入低的客观条件吻合
**史料**：**dragonfly.duckdb** `commits` 表 dragonfly-src 仓库 CVE commit 查询：`SELECT count(*) FROM commits WHERE repo_name='dragonfly-src' AND author_date>='2020-06-01' AND author_date<'2026-07-22' AND (message_subject LIKE '%CVE-%' OR message_body LIKE '%CVE-%')` 结果 16 条；**原材料/研究/bsd 漏洞史/版本周期/dragonfly-6.x.md** 版本周期归档（2026-07-22 整理）；dragonfly.duckdb dragonfly-src 仓库 tags 表 v6.0.0 = 2021-05-07、v6.4.2 = 2025-05-09 ［A］

**史观**：软件工程：16 条 CVE commit 的稀疏分布反映 DragonFly 6.x 周期安全态势的两个特征——其一，base 系统代码量小且架构稳定（LWKT/HAMMER2 等核心子系统已过初始 CVE 高发期）；其二，社区规模有限导致主动安全审计投入不足（2024 年 commit 谷值 277 条仅为 FreeBSD 同期 1.9%）；这与 FreeBSD 14.x 周期“主动审计—批量披露”模式形成对照——DragonFly 的安全响应是被动的、依赖上游 CVE 披露后跟进，而非主动审计发现漏洞

**辨析**：16 条 commit 数量少不等于安全态势好——可能反映 DragonFly base 系统未进入第三方安全研究者的审计视野，HAMMER2 等独有子系统不在通用 CVE 扫描工具覆盖范围；与 OpenBSD errata 同期约数百条对比，DragonFly 的 CVE commit 稀疏更可能是“审计盲区”而非“代码质量优”；cvelistV5 中 31 个 CVE 无 CVSS v3 评分反映这些 CVE 多为老旧 CVE（CVE-2008-2476、CVE-2012-0876 等），NVD 未重新评估其严重性，而非 DragonFly 特有现象

## 231.5.2 HAMMER2 文件系统漏洞史——与 HAMMER1 的对照

**要点**：DragonFly 6.x 周期数据库中 **无任何 HAMMER/HAMMER2 相关 CVE commit**——16 条 CVE commit 中无一涉及文件系统；dragonfly.duckdb 显示 HAMMER2 关键词 commit 在 6.x 时期持续（2022 年 87 条、2023 年 117 条、2024 年 16 条、2025 年 27 条、2026 年 11 条），HAMMER1 关键词 commit 在 2022-2024 年降至 0 条后 2025/2026 年各 1 条——文件系统持续改进但未触发 CVE 编号；HAMMER2 自 **2019 年 v5.6.0**（tagger_date = 2019-06-16）起成为默认文件系统，6.0（**2021 年 5 月 7 日**）发布时 HAMMER2 已是默认选项，6.x 周期是 HAMMER2 作为默认文件系统的第二个完整版本周期（5.x 后期至 6.x）；与 HAMMER1 历史（2007 年首引、2008 年 v1.12 集成、v2.0.1 默认）对比，HAMMER2 在 6.x 周期未公开任何 CVE，但这不意味着代码无 bug——dragonfly.duckdb 显示 HAMMER2 commit 多为 bug 修复与性能改进。6.x 时期 HAMMER1 与 HAMMER2 关键词 commit 对照如下：

**史观**：总纲第 17 条——软件工程：HAMMER2 在 6.x 周期“无 CVE”现象的解释须与 5.x 周期根本不同——5.x 周期 HAMMER2 处于 EXPERIMENTAL 状态，用户基数极小，“无 CVE”可归因于“未进入审计视野”；6.x 周期 HAMMER2 已是默认文件系统达 4 年（自 2019 年 v5.6.0），用户基数相对扩大，但 6.x 周期数据库中仍无 HAMMER/HAMMER2 相关 CVE commit——这一连续性反映“无 CVE”的成因不仅是审计盲区，还涉及 DragonFly 项目对本地 bug 的 CVE 申请缺位（DragonFly 不主动为本地 bug 申请 CVE 编号，与 FreeBSD 对 OpenZFS 集成漏洞的 CVE 申请惯例不同）；HAMMER1 在 6.x 周期进入 0 commit 维护状态（2022-2024 年），反映 DragonFly 文件系统代际更替的工程节奏——HAMMER1 退役后 HAMMER2 承担全部文件系统负载，但 HAMMER2 仍未触发 CVE 反映审计覆盖盲区与 CVE 申请缺位双重因素

## 231.5.3 regreSSHion（CVE-2024-6387）与 OpenSSH 快速跟进——Dillon 的 3 天响应

**要点**：CVE-2024-6387（regreSSHion）是 DragonFly 6.x 周期唯一有 CVSS v3 评分且达 High 级别的漏洞——CVSS 8.1，OpenSSH **sshd(8)** 预认证远程代码执行；Qualys TRU 于 **2024 年 7 月 1 日** 公开披露，DragonFly 于 **2024 年 7 月 4 日** 由 Matthew Dillon（马修·狄龙） 本人提交 commit `ba1276acd1c8c22d225b1bcf370a14c878644f44` “IMPORT openssh-9.8p1”——距公开披露仅 3 天；这是 6.x 周期 16 条 CVE commit 中唯一由 Dillon 亲自提交的 commit，反映 Dillon 对高严重性漏洞的快速响应；与 FreeBSD **SA-24:04.openssh**（**2024 年 7 月 1 日** 同步发布 PGP 签名公告）对比，DragonFly 无正式 SA，仅通过 commit message 通知用户——用户需自行监控 dragonfly-src 仓库 commit log 或 kernel@ 邮件列表才能获知漏洞修复；regreSSHion 是 CVE-2006-5051 的 18 年回归，DragonFly 因持续跟进 OpenSSH 上游版本而受影响。regreSSHion 响应时序对照如下：

    | 时间 | 事件 | 主体 |
    |---|---|---|
    | 2024-07-01 | Qualys TRU 公开披露 regreSSHion | Qualys |
    | 2024-07-01 | FreeBSD **SA-24:04.openssh** PGP 签名公告同步发布 | FreeBSD Security Team |
    | 2024-07-04 | commit `ba1276acd1c8c22d225b1bcf370a14c878644f44` “IMPORT openssh-9.8p1” | Matthew Dillon |

    > IMPORT openssh-9.8p1 — DragonFly commit `ba1276acd1c8c22d225b1bcf370a14c878644f44`（2024-07-04，作者 Matthew Dillon）
**史料**：**dragonfly.duckdb** `commits` 表 dragonfly-src 仓库 CVE-2024-6387 commit：commit hash `ba1276acd1c8c22d225b1bcf370a14c878644f44`，作者 Matthew Dillon，author_date = 2024-07-04，message_subject =“IMPORT openssh-9.8p1”；Qualys TRU. regreSSHion: Remote Unauthenticated Code Execution Vulnerability in OpenSSH server [EB/OL]. 2024-07-01；FreeBSD-SA-24:04.openssh PGP 签名公告（2024-07-01） ［A］

**史观**：软件工程：regreSSHion 案例显示 DragonFly 无 SA 系统不等于响应慢——Dillon 3 天内完成 OpenSSH 9.8p1 vendor import，速度快于多数 Linux 发行版；但“快速响应”与“用户可知”是两个维度——FreeBSD SA 系统确保用户通过 PGP 签名公告获知漏洞，DragonFly 仅通过 commit message 通知，用户须主动监控仓库；这一差异反映两种安全响应文化的权衡：DragonFly 牺牲形式化流程换取响应速度，FreeBSD 以流程化确保用户可知性；Dillon 本人亲自提交此 commit 反映 6.x 时期 Dillon 虽代码贡献量下降（2024-2026 年共 79 条 commit）但仍保留对高严重性漏洞的最终响应权

**辨析**：**需严格区分**：① CVE-2024-6387 是 OpenSSH 上游漏洞（Qualys 报告，所有使用 OpenSSH 8.5p1 及之后的系统受影响），DragonFly 通过 vendor import 修复，与 FreeBSD 修复方式相同；② FreeBSD 另有 CVE-2024-7589（SA-24:08.openssh）是 FreeBSD 特有的 blacklistd 集成引入的同类问题，DragonFly 不使用 blacklistd 故不受此 CVE 影响；**响应速度的辨析**：Dillon 3 天响应 vs FreeBSD 7 月 1 日同步发布，表面看 DragonFly 慢 3 天，但 FreeBSD Security Team 在 Qualys 公开披露前已获预通知（embargo 期内修复），故“3 天”实为公开披露后的响应速度，与 FreeBSD 同步发布不可直接比较；DragonFly 是否在 embargo 期内获通知 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］ 须以 kernel@ 邮件列表核验

## 231.5.4 FreeBSD 安全补丁单向回溯——CVE-2023-3107 与 CVE-2008-2476 的 MFC 路径

**要点**：DragonFly 6.x 周期 16 条 CVE commit 中有 2 条明确标注“MFC freebsd”——CVE-2023-3107（IPv6 integer overflow，commit `fe18a0e48ab846d5ba575fe3d92bb31881a932aa`，**2023 年 8 月 1 日**，作者 Matthew Dillon）与 CVE-2008-2476（IPv6 NDP，commit `d256b4905e56e3bfe5d624625e422640dd1c0043`，**2024 年 7 月 2 日**，作者 Roy Marples）；这两条 commit 反映 DragonFly 作为 FreeBSD 4.x fork 持续单向回溯 FreeBSD 安全补丁的工程实践——DragonFly 2003 年从 FreeBSD 4.x 分叉后，网络栈（netinet6/NDP）等子系统仍与 FreeBSD 共享代码基因，FreeBSD 后续安全修复需手动 backport 至 DragonFly；CVE-2008-2476 是 **2008 年** 漏洞，在 **2024 年** 才回溯至 DragonFly——16 年滞后反映 DragonFly 在 IPv6 NDP 子系统的维护滞后，dragonfly.duckdb 显示 commit message 为"inet6: Set net.inet6.icmp6.nd6_onlink_ns_rfc4861 to 0 by default."是 Roy Marples 从 FreeBSD 回溯的修复；CVE-2023-3107 是较及时的回溯（FreeBSD 修复后数月内），commit message 明确标注“MFC freebsd ff3d1a3f9d71e706f320f51bae258e4e1a51b388”

**史料**：**dragonfly.duckdb** `commits` 表 dragonfly-src 仓库 MFC commit 查询：`SELECT commit_hash, author_date, author_name, message_subject FROM commits WHERE repo_name='dragonfly-src' AND author_date>='2020-06-01' AND author_date<'2026-07-22' AND message_subject LIKE '%MFC%freebsd%'` 结果含 fe18a0e48ab846d5ba575fe3d92bb31881a932aa 与 d256b4905e56e3bfe5d624625e422640dd1c0043；commit `fe18a0e48ab846d5ba575fe3d92bb31881a932aa` message_subject ="netinet6 - MFC freebsd ff3d1a3f9d71e706f320f51bae258e4e1a51b388"；commit `d256b4905e56e3bfe5d624625e422640dd1c0043` message_subject ="inet6: Set net.inet6.icmp6.nd6_onlink_ns_rfc4861 to 0 by default."；CVE-2008-2476 MITRE 记录 ［A］

**史观**：总纲第 22 条——BSD 反向影响线：DragonFly 从 FreeBSD 单向回溯安全补丁是 BSD 家族“基因延续”的典型——DragonFly 虽 2003 年分叉但网络栈代码仍与 FreeBSD 4.x 同源，FreeBSD 后续安全修复对 DragonFly 仍有“溢出效应”；但这一回溯是单向的——FreeBSD 不从 DragonFly 回溯任何代码，反映 DragonFly 创新子系统（LWKT/HAMMER2）未获 FreeBSD 采纳；CVE-2008-2476 的 16 年滞后反映 DragonFly 维护资源有限——BSD 社区规模差异直接体现为安全补丁回溯时延，FreeBSD Security Team 修复后 DragonFly 社区需自行跟踪并手动 backport

**辨析**：**MFC（Merge From Current）的语义辨析**：DragonFly 的“MFC freebsd”与 FreeBSD 内部的 MFC（从 main 分支合并至 stable/分支）语义不同——DragonFly 的 MFC 是跨项目回溯（从 FreeBSD 回溯至 DragonFly），FreeBSD 的 MFC 是项目内分支合并；**CVE-2008-2476 时延的辨析**：16 年滞后可能反映两个原因——其一，DragonFly IPv6 NDP 代码与 FreeBSD 4.x 同源但与 FreeBSD 后续重构差异大，backport 困难；其二，DragonFly 社区未跟踪 CVE-2008-2476 的修复需求，直到 2024 年才由 Roy Marples 主动处理；**单向回溯的边界**：DragonFly 仅回溯网络栈等共享基因子系统的安全补丁，LWKT/HAMMER2 等 DragonFly 独有子系统无回溯需求

## 231.5.5 贡献组件漏洞集中清算——expat/libarchive/libressl 升级链

**要点**：DragonFly 6.x 周期 16 条 CVE commit 中 12 条（75%）为贡献组件 vendor import 升级——expat（commit `0c65ac1dc98bdeacfd970251eb73ccf33a29b90b`，**2022 年 11 月 12 日**，Antonio Huete Jimenez（安东尼奥·韦特·希门尼斯），一次升级从 2.1.0 至 2.5.0 处理 18 个 CVE）、libarchive（2 次升级，Daniel Fojt 与 Huete Jimenez）、libressl（4 次升级，Daniel Fojt）、zlib（commit `f4d4bc82ad279b10124935460f1478e541a32da0`，**2023 年 3 月 16 日**，Aaron LI）、libpcap（commit `ed775ee718148819f0ec9481195b31f346fbe774`，**2022 年 11 月 20 日**，Huete Jimenez）、less（commit `320d7c8af5f0ab744bd93909d165334864d1d53b`，**2024 年 3 月 11 日**，Aaron LI）、openssh（commit `ba1276acd1c8c22d225b1bcf370a14c878644f44`，**2024 年 7 月 4 日**，Dillon）；其中 expat 升级一次性处理 18 个 CVE（CVE-2012-0876、CVE-2012-6702、CVE-2013-0340、CVE-2015-1283、CVE-2016-0718 等）是 6.x 周期规模最大的单次 CVE 清算——expat 在 DragonFly base 中滞留 2.1.0 版本长达约 10 年（2012-2022），积压的 CVE 由一次 vendor import 集中清理；这一模式与 FreeBSD 14.x 周期 Heimdal 集中清理（2024 年 2 月 14-15 日两天处理 6 个积压 CVE）类似，但 DragonFly 的积压周期更长。6.x 周期贡献组件 vendor import 升级链如下：

## 231.5.6 MP-safe 子系统与安全演化——MPSAFE-TTY 时代的并发安全

**要点**：DragonFly 6.0（**2021 年 5 月 7 日** 发布）引入 MPSAFE-TTY，是 6.x 周期 MP-safe 子系统演化的关键节点——dragonfly.duckdb 显示 6.0 系列期间 message_subject 含“MPSAFE”的 commit 集中于 TTY 子系统的锁细化，反映 TTY 是 DragonFly 最后完成 MP-safe 化的子系统之一；6.0 之后 MPSAFE 关键词 commit 量显著减少，反映 LWKT 路线在 6.x 周期已进入“维持阶段”而非“扩展阶段”；6.x 周期数据库中无 MP-safe 相关 CVE commit，反映 MP-safe 重构在 6.x 之前已基本完成（5.x 时期是 MP-safe 重构高峰）；但 MP-safe 子系统的复杂性可能引入新的并发 bug 类——这类 bug（如 race condition、deadlock）难以通过 CVE 系统捕获，多通过普通 bug 报告处理

**史料**：**dragonfly.duckdb** `commits` 表 dragonfly-src 仓库 MPSAFE 关键词查询：`SELECT commit_hash, author_date, author_name, message_subject FROM commits WHERE repo_name='dragonfly-src' AND author_date>='2021-01-01' AND author_date<'2022-06-01' AND message_subject LIKE '%MPSAFE%'` 结果含 6.0 系列 MPSAFE-TTY commit；DragonFly 6.0 release notes MPSAFE-TTY 说明；DragonFly LWKT 设计文档 ［A］

**史观**：总纲第 7 条——硬件与软件辩证：6.x 周期 MPSAFE-TTY 的引入标志着 DragonFly MP-safe 路线进入“收尾阶段”——与 5.x 周期“持续演化的关键阶段”不同，6.x 周期 TTY 子系统作为最后持有 Giant Lock 的子系统之一完成 MP-safe 化，反映 DragonFly LWKT 路线在 6.x 时期已基本覆盖全部主要内核子系统；6.x 周期 LWKT 路线的工程问题从“扩展 MP-safe 覆盖”转为“维持 MP-safe 稳定性”——dragonfly.duckdb 显示 6.x 周期 MPSAFE 关键词 commit 量较 5.x 时期减少（主要集中于 6.0 系列的 TTY 锁细化），反映 MP-safe 重构已完成主要工作量；但 MP-safe 子系统的复杂性带来的并发 bug 隐患在 6.x 周期持续存在，这类 bug 通常不申请 CVE 编号——这与 FreeBSD 14.x 周期 ZFS 协调锁漏洞偶发 CVE 形成对照

**辨析**：**MP-safe 完成 vs CVE 关系的辨析**：6.x 周期 MPSAFE-TTY 完成后 DragonFly 主要内核子系统均已 MP-safe 化，但 MP-safe 完成不等于并发安全无虞——MP-safe 重构引入的 bug（如 race condition、deadlock、use-after-free）在 6.x 周期仍以普通 bug fix commit 处理，不申请 CVE 编号；与 5.x 周期“扩展 MP-safe 覆盖”阶段不同，6.x 周期进入“维持 MP-safe 稳定性”阶段后，并发 bug 的出现频率应较 5.x 周期降低（但 dragonfly.duckdb 中无统计佐证）［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］；**MPSAFE-TTY 的安全意义**：MPSAFE-TTY 使 TTY 子系统在多核环境下无需 Giant Lock，提升了多核场景下的 TTY 操作并发性，但其安全影响是间接的——主要体现为性能提升而非安全加固；与 FreeBSD 14.x 周期 TTY 子系统早已 MP-safe 化的对照，DragonFly 6.0 才完成 TTY MP-safe 化反映 DragonFly MP-safe 路线的完成时间晚于 FreeBSD 约 15 年（FreeBSD Giant Lock 退役始于 5.x 时期约 2006 年）

## 231.5.7 无 SA 系统的安全响应文化——Dillon 个人主导模式的可持续性辨析

**要点**：DragonFly BSD 无正式 Security Advisory（SA）系统，安全修复通过 commit message 与 kernel@ 邮件列表通知用户——这与 FreeBSD SA（14.x 周期 80 个 PGP 签名 SA）、OpenBSD errata（逐版本发布 errata patches）形成鲜明对比；6.x 周期 16 条 CVE commit 中，仅 CVE-2024-6387（regreSSHion）commit message 隐含漏洞严重性（通过 OpenSSH 9.8p1 vendor import 间接体现），其余 15 条 commit 仅以“vendor/xxx: upgrade from X to Y”或“fix CVE-XXXX-YYYY”形式记录；dragonfly.duckdb 显示 6.x 周期 DragonFly 年均 commit 量（2024 = 277、2025 = 561、2026 截至 7 月 = 906）远低于 FreeBSD（14541/15598/9041）与 OpenBSD（6512/5330/3205），安全审计投入必然受限；无 SA 系统的好处是响应快（regreSSHion 3 天响应），坏处是用户难以系统跟踪安全修复——DragonFly 用户须自行监控 dragonfly-src 仓库 commit log 或订阅 commits@ 邮件列表

**史料**：**dragonfly.duckdb** `commits` 表四仓库 2024-2026 年对照（dragonfly-src/freebsd-src/openbsd-src/netbsd-src 按年 commit 量）；dragonflybsd.org 官方无 SA 页面（无类似 <https://www.freebsd.org/security/advisories/> 的页面）；lists.dragonflybsd.org 邮件列表归档（kernel@/commits@/users@/bugs@）；FreeBSD Security Advisories 官方存档；OpenBSD errata patches 存档 ［A］

**史观**：总纲第 23 条——社区治理：6.x 周期 DragonFly 无 SA 系统的问题从“是否可行”转为“可持续性如何”——5.x 周期 Dillon 仍是主导代码贡献者（年均约 385 条 commit）个人能力覆盖内核、HAMMER2、安全响应多个维度，无 SA 系统在其个人主导下尚可运转；6.x 周期 Dillon 代码贡献量持续下降（2024-2026 年共 79 条 commit，仅 1 条 CVE commit 即 regreSSHion 应急响应），其他 committer（Daniel Fojt、Aaron LI、Antonio Huete Jimenez）已承担主要贡献组件维护职责——但安全响应仍依赖 Dillon 个人决策，这一“代际更替未完成”的状态使无 SA 系统的可持续性面临新风险；与 5.x 周期“个人主导可行”的判断不同，6.x 周期须考虑 Dillon 退出后是否有人具备 embargo 期接入与漏洞响应协调能力——这是 6.x 周期 DragonFly 安全治理的核心不确定性

**辨析**：**无 SA 系统可持续性的辨析（vs 5.x 周期）**：5.x 周期无 SA 系统在 Dillon 主导代码贡献的背景下可行（Dillon 4 条 CVE commit 中 2 条为 embargo 期内修复），6.x 周期无 SA 系统面临 Dillon 淡出的可持续性挑战——dragonfly.duckdb 显示 6.x 周期 Dillon 仅 1 条 CVE commit，其余 15 条由其他 committer 提交，反映 Dillon 在安全响应一线已淡出但未完全退出；**可持续性风险**：当前 Aaron LI、Huete Jimenez、Daniel Fojt 等其他 committer 是否接入 distros 邮件列表的 embargo 期预通知机制 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］ 须以 kernel@ 邮件列表中安全相关讨论核验，若未接入则 DragonFly 在 Dillon 退出后将无法在 embargo 期内修复高严重性漏洞——这一风险在 5.x 周期不存在；**与 OpenBSD errata 的对比**：OpenBSD errata 虽形式简单（errata patches 文档）但仍有正式编号与影响说明，DragonFly 连 errata 级文档都未维护——这一差异在 5.x 周期可归因于“Dillon 个人能力替代形式化流程”，6.x 周期则须重新评估，因 Dillon 淡出后无形式化流程意味着无接续机制
