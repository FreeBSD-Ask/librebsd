## 216.3.2 共享代码从渐行渐远到几乎独立

**要点**：dragonfly.duckdb dragonfly-src 仓库首 commit `984263bcb83a`（2003-06-17）标题“Initial import from FreeBSD RELENG_4”——DragonFly 1.x 与 FreeBSD 4.x 在 fork 初期 userland 与内核共享大量代码。2003-06-17 至 2003-06-18 期间 Dillon 提交的 commit `1de703daf673`/`6e2852121810`/`bec037ae07f0`/`efe09d8ced7c` 显示其立即开始"Add the DragonFly cvs id and perform general cleanups on cvs/rcs/sccs ids“与”Remove UUCP support"等差异化操作。至 2010 年代（v2.10-v2.13 系列）DragonFly 内核与 FreeBSD 内核已几乎完全独立，userland 工具亦逐步分化

**史料**：dragonfly.duckdb dragonfly-src 仓库 commits 表（2003-06-17 至 2003-06-18 期间 commit 序列显示差异化操作启动）；dragonfly.duckdb dragonfly-src 仓库 commit_files 表（sys/dev/、sys/kern/、sys/vfs/ 目录文件在 2003-2010 年间的 freebsd-src 对照）；DragonFly 与 FreeBSD 源码 diff（git diff 历史）〔L1 代码/构建产物〕

**史观**：分离与聚合：fork 后代码从“Initial import from FreeBSD RELENG_4”的完全共享状态，经 2003-2010 年间逐步差异化操作（移除 UUCP、添加 DragonFly cvs id、LWKT 重构、HAMMER 引入等），演变为内核与 userland 几乎完全独立——分离过程历时约 7 年，符合“分离非瞬时事件而是长期演化”的史观

**辨析**：代码共享减少的原因包括技术分歧（LWKT 消息传递 vs SMPng、HAMMER vs ZFS、vkernel vs bhyve）与人际因素（Dillon 与 Core Team 交恶），二者难以完全区分——dragonfly.duckdb 显示 2003-2005 年间仍存在回移 commit，反映技术分歧尚未完全阻断代码共享；2007 年 HAMMER 首引后回移停止，反映技术分歧积累至临界点后代码共享终止

**要点**：OpenBSD 1996 年从 NetBSD fork 后两者关系长期紧张，但 2007 年 NetBSD Foundation 与 OpenBSD Foundation 均注册成立后关系逐步缓和，至 2015 年后两项目在 LibreSSL/portable 代码共享等议题上出现协作。DragonFly-FreeBSD 关系至 2026 年仍未出现类似缓和迹象——dragonfly.duckdb 显示 2010 年后 DragonFly 与 FreeBSD 内核代码共享停止，userland 共享亦逐步减少

## 216.3.6 反批评层——Dillon 与 DragonFly 阵营的回应

**要点**：Dillon 与 DragonFly 阵营对 FreeBSD committer 负面话语的回应集中于四个层面——其一，fork 公告本身已预先回应 BSD 频繁分裂的批评，Dillon 在 2003-07-16 公告（**lists.freebsd.org/pipermail/freebsd-current/2003-July/006889.html**）中明确将 DragonFly 定位为“the logical continuation of the FreeBSD 4.x series”，以“4.x 路线延续”而非“另立门户”的话语策略回应“too many BSD's”的批评；其二，Dillon 在 ONLamp 2004 年采访（“DragonFly BSD: A Fork in the FreeBSD Road”）中以技术论证回应——选择 4.x 基线而非 5.x 是基于“it is simply too heavily mutexed”的工程判断，而非个人偏好；其三，dragonfly.kernel 邮件列表 2003-2006 年间 Dillon 持续发言，以 LWKT、HAMMER、vkernel 等技术产出证明 fork 的工程价值，dragonfly.duckdb 显示 Dillon 在 dragonfly-src 仓库共 4222 条 commit（截至 2008-11-13T02:23:53Z），以代码层回应证明 fork 的实质性；其四，dragonflybsd.org 官方 history 页面后期将 fork 公告中“logical continuation”描述标注为“has long since become obsolete”，反映 DragonFly 阵营从“对抗性否定”转向“独立性宣告”的话语策略演变

**史料**：Dillon 2003.7.16 fork 公告原文（**lists.freebsd.org/pipermail/freebsd-current/2003-July/006889.html**）；ONLamp 2004“DragonFly BSD: A Fork in the FreeBSD Road”采访原文（经 archive.org 核验，web.archive.org/web/2004*/onlamp.com）；dragonfly.kernel 邮件列表 2003-2006 年 Dillon 发言存档（lists.dragonflybsd.org）；dragonfly.duckdb dragonfly-src 仓库 contributors 表 Matt Dillon（<dillon@dragonflybsd.org>）first_commit_date = 2003-06-17T02:57:24Z、last_commit_date = 2008-11-13T02:23:53Z、commit_count = 4222；DragonFly BSD 官方 history 页面（dragonflybsd.org/history/，“has long since become obsolete”段）

**史观**：哲学思潮：话语策略的演变反映社区自我定位的变化——Dillon 从 fork 公告中的“4.x 延续”话语，经 ONLamp 采访的“工程判断”话语，至 dragonflybsd.org 后期“obsolete”修订，话语策略从“对抗性否定”转向“独立性宣告”，这一演变本身即社区自我定位从“FreeBSD 的分支”转向“独立 BSD 项目”的具体显现；终结与延续：fork 公告中“logical continuation”话语被后期标注为“obsolete”反映话语的终结，但 fork 后的代码延续（4222 条 commit）证明 fork 的实质性——话语终结不等于实践终结

**辨析**：【0 信任原则·Dillon 回应的完整性】Dillon 的回应须区分“技术论证”与“话语策略”两层——ONLamp 采访中的“too heavily mutexed”是技术论证，fork 公告中的“logical continuation”是话语策略，二者性质不同须分别评估；【代码层回应的代表性】dragonfly.duckdb 显示 Dillon 4222 条 commit 是 fork 后工程价值的客观证据，但 commit 量不等于代码质量，须结合 commit 规模（additions/deletions）与 message 质量综合判断——DragonFly 早期 commit 多为 LWKT 子系统从零构建的大型 commit，单条 commit 影响力高于 FreeBSD 同期维护性 commit；【“obsolete”标注的时点考据】dragonflybsd.org/history 页面将“logical continuation”描述标注为“obsolete”的具体修订时点 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］，须以 web.archive.org 历史快照追溯核验；【间接回应的界定】Dillon 在 dragonfly.kernel 邮件列表的持续发言是否构成对 FreeBSD committer 负面话语的“回应”须谨慎界定——直接回应（针对 Stacey/Kennaway 跟帖）与间接回应（持续技术产出）性质不同

## 216.3.7 再批评层与合图——对反批评的再回应与项目统摄史观审视

**要点**：对 Dillon 与 DragonFly 阵营反批评的再回应集中于三点——其一，“4.x 延续”话语策略的批评者指出，将 DragonFly 定位为“FreeBSD 4.x 的逻辑延续”实质上否定 FreeBSD 5.x 路线的合法性，这一话语策略在 fork 后逐步失效（dragonflybsd.org 后期标注为“obsolete”）反映其策略性而非事实性；其二，“too heavily mutexed”技术论证的批评者指出，SMPng 在 2003 年仍处于演进期，FreeBSD 5.3（2004-11-06 release）后 SMPng 性能显著改善，Dillon 2003 年的判断可能过早——dragonfly.duckdb 显示 FreeBSD 5.x 系列持续演进至 5.5（2006-05-25 release），证明 Core Team 对 SMPng 路线的坚持并非“错误”；其三，代码层回应（4222 条 commit）的批评者指出，DragonFly 三大核心创新（LWKT/HAMMER/vkernel）均未被业界主流采纳，fork 后 23 年间（2003-2026）DragonFly 未建立明确细分市场——dragonfly.duckdb 显示 DragonFly 2024 年 commit 量仅 277 条（vs OpenBSD 同期 5097 条［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］），社区规模差距反映 fork 后工程产出的实际影响力有限；合图层以项目史观总纲第 6 条（和解优于斗争）与第 8 条（本体论上各方平等）审视争议——Stacey/Kennaway 的负面话语、Core Team 的沉默、Dillon 的反批评、再批评的质疑，各方在本体论上地位平等，争议本身是 BSD 阵营内部对 fork 必要性的多元判断的具体显现，无须以“对错”二元裁决，而应以“和解优于斗争”的史观审视争议的历史意义

**史料**：freebsd-current 邮件列表 2003-July 归档（Stacey/Kennaway/Sobolev/Drosihn 跟帖，邮件 ID 同 3.3.5）；freebsd.duckdb freebsd-src 仓库 tags 表（FreeBSD 5.0-5.5 release 序列：5.0 = 2003-01-19、5.1 = 2003-06-09、5.2 = 2004-01-09、5.3 = 2004-11-06、5.4 = 2005-05-25、5.5 = 2006-05-25）；dragonfly.duckdb dragonfly-src 仓库 commits 表（按年统计 2024 = 277）；openbsd.duckdb openbsd-src 仓库 commits 表（2024 = 5097［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］）；dragonflybsd.org/history 页面“obsolete”标注；原材料/哲学/项目统摄史观/第 25 章.md（25 条总纲原文，第 6 条与第 8 条）

**史观**：总纲第 6 条——和解优于斗争：fork 事件中的争议无须以“对错”二元裁决——Stacey/Kennaway 的负面话语、Core Team 的沉默、Dillon 的反批评、再批评的质疑，各方立场均有其历史语境与合理性，和解的史观要求承认多元立场的并存而非强制统一；总纲第 8 条——本体论上各方平等：Dillon 与 FreeBSD Core Team、DragonFly 阵营与 FreeBSD 阵营在本体论上地位平等，fork 事件的争议是平等主体间的分歧，不构成任何一方的本体论优越或劣等

**辨析**：【0 信任原则·SMPng 性能判断的时点性】Dillon 2003 年“too heavily mutexed”的判断须以 2003 年硬件语境评估，不得以 2004-2006 年 SMPng 改善后的事后视角否定 2003 年判断的合理性——dragonfly.duckdb 显示 FreeBSD 5.0（2003-01）至 5.3（2004-11）期间 SMPng 仍处于性能调优期，Dillon 的判断在 2003 年时点具有工程依据；【代码层回应的“未被采纳”标准】“未被业界主流采纳”是否构成对 fork 必要性的有效批评须以多元标准评估——dragonfly.duckdb 显示 DragonFly 23 年持续维护与 HAMMER2 生产可用本身即 fork 的内在价值，“业界采纳”标准反映业界主流的实用主义视角，不构成对 fork 必要性的唯一有效评判；【合图层的史观边界】合图层以“和解优于斗争”审视争议不等于取消争议——和解史观要求承认各方立场的合理性，但亦要求承认争议本身的历史意义，不得以“和解”为名取消对争议的考据与分析；【项目史观总纲第 6 条与第 8 条的引用边界】总纲第 6 条与第 8 条的引用须对照原材料/哲学/项目统摄史观/第 25 章.md 原文核验，避免断章取义——第 6 条“和解优于斗争”不等于“无斗争”，第 8 条“本体论上各方平等”不等于“各方立场无差异”

**要点**：

- Scott Long 完整描述 FreeBSD 发布工程的制度细节：开发以 CVS 为中心，head 分支即 7-current 收纳一切新特性与实验改动，约每两三年从中切出发布分支，2005 年 6 月切出 RELENG_6 并发布 6.0，分支内只进 bug 修复与少量驱动、基调保守；五人发布团队不足以完成充分测试，靠向社区推送候选版本与快照构建征集反馈；发布判据是一份公开的 to-do 清单，收录高需求缺陷报告、功能请求与可能构成发布阻碍的去稳定缺陷，6.0 因此宁可推迟数月也修完缺陷再发；日程表只用于驱动参与者保持节奏，最终以修到满意为准；同时他承认过去 4.x 与 5.x 双发布周期并行使没有分支的 ports 树每次都要停摆配合，故自 2005 年起拉开发布间隔、终结双周期，6.1 与 5.5 成为 5 系列的最后发布，后续年内出 6.2、次年出 6.3、2007 年中切出 7 分支。（BSDTalk EP17，[186.94-728.46]，L1）
- 关于 5 系列谢幕的理由与善后：FreeBSD 6 在稳定性、功能与性能上已明显领先，继续投入 5 系列意义不大，而 5 到 6 的升级极少意外、基本系统几乎无变化；安全团队按既定政策对 5 系列再支持两年，照顾无法承担升级成本的用户；主持人以 Red Hat 放弃 Professional 转向 Fedora 后 Red Hat 9 仅获六个月支持的骤停作对照，Long 表示以善待过时版本为荣，因为用户依赖持续的安全修复。（BSDTalk EP17，[520.15-613.67]，L1）
- PowerPC 移植负责人 Peter Graham 的定位被 Long 转述为一手澄清：在 Apple 硬件上运行 FreeBSD 只是便于获取设备、便于用户参与的手段，真正目标是嵌入式 PowerPC，包括 IBM 440 系列嵌入式芯片与 Cell 芯片；Apple 转向 Intel 对该计划并非重创，PPC 版 Mac 仍将长期可得，同时社区已在 Apple 新 Intel iMac 上推进移植并预期其很快成为可行目标。（BSDTalk EP17，[736.44-814.47]，L1）
- 对 BSD 间代码流动的 2006 年时点判断：NetBSD 与 FreeBSD 分道已十三年，传统三项目间核心功能持续分化，共享退守至 USB 驱动等外围领域；DragonFly BSD 基于 FreeBSD 4，共享机会可观，数名开发者同时持有两个项目的提交权限，代码双向回流，DragonFly 开发的 BSD 安装器已在 FreeBSD 完整部署并可能很快进入 FreeBSD 7，其多处理器与可扩展性工作对 FreeBSD 直接有益。（BSDTalk EP17，[836.72-923.71]，L1）
- 存储方向的两项个人工作自述：其一为 SCSI 子系统加锁与 SMP 化，将大幅提升 SCSI 性能，虽并行 SCSI 本身在退场，SAS 与 Fibre Channel 等后续技术将直接受益；其二为 UFS 日志，与 soft updates 的可靠性之争多年互有胜负、基准基本打平，但 soft updates 即便保证崩溃一致性、恢复时仍须全盘检查，在数百 GB 至数百 TB 的企业文件服务器上是不可行的阻碍，而日志方案可在数秒内恢复一致性——这是 soft updates 结构上无法提供的优势。（BSDTalk EP17，[927.27-1047.06]，L1）

**史料**：

- 本期限定一手传记与时间锚点：受访者 1992 至 1993 年在密歇根大学初识 BSD，当时除 386BSD 外尚无 NetBSD 等后继；此后海军服役六年离开 Unix 一线；2000 年秋因 Adaptec 驱动工作获得 FreeBSD 提交权限，继而扩展至文件系统与核心部件；2002 年受邀加入发布工程团队，从协调沟通的秘书角色成长为近两年担任的负责人角色。（BSDTalk EP17，[80.91-170.33]，L1）

**史观**：

- 总纲21 革命与改革是历史方法论的分歧：BSD 以进化而非革命著称的发布声誉，在 Long 的叙述中呈现为一套被制度化的渐进方法论：新特性必须先在 head 分支经受时间沉淀，再经分支切出、候选迭代与缺陷清零才能抵达用户，日程让位于质量判断；这与同期依赖激进重写换取跃进的路线构成发布方法论上的结构性分歧。（BSDTalk EP17，[173.41-358.07]，L1）
- 总纲4 分离聚合是永恒规律：BSD 各分支十三年的走向呈现出分离聚合的轨迹：核心功能随各自目标持续分离，共享面收缩到外围驱动；而 DragonFly 自 FreeBSD 4 分出后，又以双向提交权限、安装器回流与多处理器成果共享形成局部的再聚合——分离不是单向的撕裂，聚合也从未彻底中断。（BSDTalk EP17，[836.72-923.71]，L1）

**辨析**：

- 本段转写专名失真密集，引用须全面校核：早期系统被记作 3.6 BSD 与 3.0 BSD，应为 386BSD；雇主被记作 AdaptTech 与 adaptive products，应为 Adaptec；FreeBSD 在全文中大量变形为 FreeBee、FreeBC、EVC、PreviousD 等噪音；Farber Channel 应为 Fibre Channel；Centrano 应为 Centrino；SCSI S&P 应为 SCSI SMP。 [存疑脚注] 专名以 FreeBSD 社区公开记录与当事人履历复核：386BSD、Adaptec、Fibre Channel、Centrino、SCSI SMP。（BSDTalk EP17，[80.91-96.62]，L1）
