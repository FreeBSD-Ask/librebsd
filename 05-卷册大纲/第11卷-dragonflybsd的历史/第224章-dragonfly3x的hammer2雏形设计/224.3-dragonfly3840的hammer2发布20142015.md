## 224.3.3 HAMMER 2 与 OpenZFS/btrfs 的比较

**要点**：

- blacklistd 缘起于 Zoulas 的运维实感：互联网可达主机上 SSH 等服务持续遭暴力破解、日志逐年膨胀，他不愿以改端口、改习惯的方式回避攻击，而期望机器在检测到入侵尝试时“自动停止应答来自该攻击者的请求”（1597.72-1598.72），把防御自动化内建于系统而非依赖管理员临时处置。（BSD Now EP87，[1562.52-1598.72]，L1）
- blacklistd 的核心设计是以结构化上报替代日志解析：Zoulas 指出 fail2ban 类工具依赖各守护进程格式不一、可被伪造且缺少接口信息的日志，解析日志“并非精确的科学”（1635.12-1639.08），故改为由守护进程在原 syslog 调用处追加数行直接通告攻击，并向 blacklistd 传递连接的文件描述符，以 getsockname/getpeername 核验调用者确为套接字属主，使封禁决策建立在内核可验证的连接信息之上。（BSD Now EP87，[1683.88-1775.22]，L1）
- 新闻段落转述 OpenBSD 重写 file(1)：因近年出现安全漏洞而引入特权分离，规则求值进程以非特权用户 _file 运行并受 systrace 沙箱约束；重写由 tmux 作者 Nicholas Marriott 主导，原作者 Ian Darwin 在提交后留下简短公开回应，主持人并讨论以 Capsicum 与之互补、以及非官方便携版可能经 ports 树回流其他系统的前景。（BSD Now EP87，[858.30-916.34]，L2）
- Ian Sutton 在 GSoC 期间为 OpenBSD 编写 systemd 四个非 init 组件的兼容包装器：GNOME 3 对 hostnamed、localed、timedated、logind 存在硬依赖，包装器经由 D-Bus 提供与 systemd 相同的接口使其透明可用；项目按操作系统无关设计，FreeBSD 提交者 Baptiste Daroussin 已着手移植，logind 因涉及 PAM 与 3D 加速设备权限传递而最为复杂，其余三个组件已基本成形。（BSD Now EP71，[879.16-934.98]，L1）
- 在 ISC NTPD 连串安全补丁与 NTP 反射攻击的背景下，长期无人维护的 portable OpenNTPD 由曾参与 LibreSSL 相关工作的 Brent Cook 等志愿者接手复活，产出 16 个补丁并重新发布至 GitHub 与 FreeBSD 包仓库，修复过程中还反哺了 OpenBSD 原生版代码。（BSD Now EP71，[602.16-686.20]，L2）
- pkg（pkgng）新增对 OS X 的支持并连发新版本，MacPorts 因 FreeBSD ports 树日益依赖 pkg 而考虑移植其完整功能，未来或为 Mac 引入二进制包；pkg 由此从 BSD 生态扩展为跨平台包管理方案，同期亦出现 Linux 移植迹象。（BSD Now EP71，[1842.70-1950.34]，L2）
- Dillon 说明 DragonFlyBSD 4.0 的定名缘由：HAMMER2 未就绪，项目不再走 3.10 式小步版本而直接称 4.0；新版同时移除 32 位 x86 支持、转向仅 64 位内核，master 分支并开始清除 IPv6 早期遗留的 IPv4 over IPv6 隧道与通配套接字等临时方案。（BSDTalk EP248，[57.04-99.40、2002.14-2030.92]，L1）
- 网络栈方面，Dillon 称其已与其他 BSD 实质分叉为自研实现：数据包尽可能固定于单一 CPU 走完生命周期，TCB 结构因此免锁；新实现提供并发 listen-accept 队列与按 CPU 分立的监听队列，使多核服务接受连接不再有瓶颈；UDP 栈此前锁定 CPU 0 的问题也已解除。（BSDTalk EP248，[702.30-748.44、476.10-502.42、187.84-192.88]，L1）
- 关于 HAMMER1 与 HAMMER2 的关系，Dillon 陈述：HAMMER1 稳固但只理解单一块设备、无冗余，其设计受制于 buffer BIO 机制而无法加入聚类，已是设计死胡同；HAMMER2 旨在修正这些问题，核心文件系统虽已工作，但多主聚类、广域网部署与快照仍需将每个聚类节点的 IO 隔离至独立线程，以便在块设备失联时前端可剥离故障节点而不中断运行，这是剩余最难的部分。（BSDTalk EP248，[760.40-794.48、802.64-927.28、1445.20-1492.58]，L1）
- 包管理方面，Dillon 介绍 DragonFly 采用源自 FreeBSD 的 pkgng 并运行良好：全量构建约两万个包，由两台加强 blade 约需 24 至 30 小时完成；构建峰值每秒可达约 6000 次 fork 加 exec，成为遍历全系统代码路径的压力测试，而 exec、fork、exit 路径的细粒度锁使并发构建不再有瓶颈。（BSDTalk EP248，[1503.48-1616.54、1635.62-1671.38、394.28-417.68]，L1）
- 图形支持方面，Dillon 说明项目从 Linux 3.8.13 重新移植 Radeon 与 Intel 的 GPU 驱动，引入 GEM 与 TTM 虚拟内存子系统及内核模式设置，OpenGL 加速已经可用；Radeon 代码剩余缺陷是 4.0 RC3 延迟发布的唯一原因。项目还自行编写触摸板与触摸屏驱动，使系统可运行于 Acer C720 系列Chromebook，虽无挂起恢复，但依托 Haswell 后 HALT 指令的自动降功耗，空闲功耗约 5 瓦、续航 6 至 7 小时。（BSDTalk EP248，[102.06-152.70、1818.04-1933.20、353.26-369.74]，L1）
- 关于社区与定位，Dillon 自述偏好小型项目，称 DragonFly 为研究型操作系统：两年间核心开发者净增两三位，分别深耕网络、SMP 与 DRM/DRI 图形接口；资金不是问题，时间才是；历届谷歌编程之夏约半数项目代码质量足以集成。编译器方面已能以 Clang 构建 world，项目保持 GCC 与 Clang 双编译器并存，下一发行版起可用环境变量选择。（BSDTalk EP248，[1031.76-1174.26、1196.08-1232.06、1671.38-1734.06]，L1）
- Dillon 对 systemd 争议表态：其二进制格式日志对他而言不可接受，但面向 Linux 的约两万个包迫使各 BSD 构建兼容基础设施；DragonFly 开发 reaper 机制，孤儿进程改为重新挂靠父链中的回收者而非 init，便于服务追踪并达成所需分区化约四分之一的目标。他坦言操作系统 API 层面在某种程度上受 Linux 导向的应用生态支配，BSD 若过快落后于应用需求，用户终将流向 Linux，并期望各 BSD 在正交工作之外逐步协调 API。（BSDTalk EP248，[2129.32-2300.54、2381.30-2406.92、2500.72-2518.16]，L1）

- 本期为 Matthew Dillon 的当事人一手口述（BSDTalk 第 248 期，2014 年 11 月 19 日），涉及 DragonFly master 分支与 4.0 RC3 发布候选状态、HAMMER2 在树代码的聚类线程化 IO 设计、自 Linux 3.8.13 移植的 DRM/GEM/TTM 图形栈、pkgng 全量构建数据（约两万包、24 至 30 小时）与 Acer C720 驱动等一手工程事实。（BSDTalk EP248，[0.00-2584.82]，L1）

**史观**：

- 总纲10 动手者创造历史：Zoulas 自述其 NetBSD 安全官身份并非任命所得，“人人都去做他们认为能帮上忙的事”（1438.96-1447.12）；blacklistd 亦非立项规划的产物，而是他面对自身服务器日志膨胀时的动手自救。项目角色与工具产出均生长于具体动手者在偶然遭遇中的自发行动，这一时期的 BSD 史应当由这些动手者的实践而非职位与蓝图来解释。（BSD Now EP87，[1438.96-1447.12]，L1）
- 总纲8 本体论上各方平等：主持人在访谈中主动检讨对 NetBSD 的覆盖不足，承诺“像对待其他 BSD 一样给他们公允的机会”（2249.26-2252.42），Zoulas 回应称包括自己在内的 NetBSD 社区成员“一直不太愿意接受访谈”（2275.50-2281.82）；同一期节目也为 MidnightBSD 这类小型衍生分支留出版面。各分支在本体论层面的平等呈现，在此是社区媒体的自觉实践而非修辞。（BSD Now EP87，[2246.30-2269.50]，L2）
- 总纲9 经验优先：全期叙事以当事人一手经验为骨架——Ian 自述因 Arch Linux 升级 systemd 时的目录冲突而转向 OpenBSD，CodeRot 作者自述删除死代码的体会，主持人强调开发者日常自用能在使用而非审查中发现问题；经验先于抽象论证的认识次序贯穿整期节目。（BSD Now EP71，[371.44-428.30]，L1）
- 总纲4 分离聚合是永恒规律：本期呈现的工具史并非线性进步，而是分离聚合的流转：pkg 从 FreeBSD 生态分离出去向 OS X 与 Linux 扩散又反向吸纳外部需求，portable OpenNTPD 先脱离 OpenBSD 独立维护、失修后再由志愿者重新聚合；各分支在分合中重构边界，而非简单的优胜劣汰。（BSD Now EP71，[1867.32-1931.22]，L2）
- 总纲9 经验优先：Dillon 强调系统宣称的能力必须落到实物验证：核心数上限从 63 提到 256 后，因项目并无超过 48 核的真实硬件而未能实测，仅靠 QEMU 模拟会因自旋锁失真而不可信，宁可承认未测也不夸口。这一以亲手实测为准的态度，是经验优先原则的工程化身。（BSDTalk EP248，[595.82-651.38]，L1）
- 总纲8 本体论上各方平等：Dillon 自述 DragonFly 平等地从各项目借鉴，包括 Linux（DRM 即移植而来）与 FreeBSD（pkgng），并在许可证上以务实为先：自研代码取 BSD 许可，contrib 下接受 GPL，比部分 BSD 宽松纯属必要。各分支在本体论上并无高下，可用性而非纯粹性决定取舍。（BSDTalk EP248，[2370.88-2483.46]，L1）
- 总纲3 不存在进步，只有权力再分配：Dillon 指出操作系统在 API 层面是应用空间的从属者：两万个以 Linux 为目标的包决定了 BSD 必须做的让步，不跟进则用户漂移向 Linux。操作系统间的消长并非单纯技术进步，而是应用生态权力的再分配，兼容性工作即是对这一权力的回应。（BSDTalk EP248，[2381.30-2406.92、2497.44-2518.16]，L1）
- 总纲5 没有必然性，只有偶然性：HAMMER2 的滞后并非路线图的必然结果：Dillon 承认开发已两三年，进度不及预期源于本人被诸多事务分心等偶然条件；HAMMER1 走入设计死胡同、只能以 HAMMER2 重起炉灶，同样是当初设计取舍的偶然累积，而非注定如此。（BSDTalk EP248，[1313.76-1339.58、1470.14-1492.58]，L1）

**辨析**：

- 关于 file(1) 重写，Zoulas 给出当事人权衡：魔法规则集已支持递归引用，JPEG 等格式无固定偏移可循，多年累积使解析器能力与攻击面同步增长，“问题在于你想理解多少文件定义，与想要多安全之间如何取舍”（2424.66-2431.78）；他并提醒 file 程序与 libmagic 库早已分离，PHP、Apache 等软件直接复用该库，仅修固命令前端并不等于修复生态中的库本体。（BSD Now EP87，[2424.66-2457.66]，L1）
