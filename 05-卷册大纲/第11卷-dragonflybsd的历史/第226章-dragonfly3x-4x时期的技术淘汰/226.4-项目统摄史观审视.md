## 226.4.2 本体论平等视角下的路线分化——以总纲第 8 条审视

**要点**：DragonFly 与 FreeBSD 在 v3.x-v4.x 时期（2011-2015）的技术路线分化以总纲第 8 条“本体论上各方平等”审视——DragonFly 的 LWKT（轻量级内核线程）/HAMMER2（自研 CoW 文件系统）/vkernel（虚拟化）路线与 FreeBSD 的 SMPng（Giant Lock 拆分）/ZFS（OpenZFS 集成）/bhyve（虚拟化）路线在本体论上地位相等，二者皆是 BSD 谱系的一刻状态——差异是工程哲学的不同而非本体等级的高下；openzfs.duckdb 提供的客观数据（DragonFly 2011-2015 年间 MFC commit 量 6/34/37/34/18、活跃 committer 数 33/35/33/33/28、Dillon commit 量 467/567/377/323/335）反映 DragonFly 的独立演进出工程实质而非仅是形式存在——HAMMER2 文件系统在 v4.0.0（2014-11-23）正式发布并在 v5.6.0（2019）成为默认文件系统，LWKT 路线在 v3.x-v4.x 时期持续演进（多核调度改进与 LWKT 改进），vkernel 在 v3.x 系列继续维护；DragonFly 的路线分化不是“偏离 FreeBSD 主流”而是“BSD 谱系内多元演化的具体显现”——DragonFly 与 FreeBSD 在 fork 后各自独立演进，技术路线分歧累积使代码共享的基础逐步削弱，代码共享减少是 fork 关系的预期结果而非异常现象；DragonFly 的生态孤立（dports vs FreeBSD Ports、软件包数量与更新及时性不及 FreeBSD）是路线分化的代价而非本体等级的劣等——DragonFly 以生态孤立换取自研路线独立性（HAMMER2/LWKT/vkernel 的自主演进）、技术路线自主性（不受 FreeBSD SMPng/ZFS 路线约束）、工程哲学纯粹性（LWKT 轻量级内核线程路线的持续演进）是结构性选择而非道德缺陷

**史观**：总纲第 8 条——本体论上各方平等：DragonFly 的 LWKT/HAMMER2/vkernel 路线与 FreeBSD 的 SMPng/ZFS/bhyve 路线在本体论上地位相等，二者皆是 BSD 谱系的一刻状态——差异是工程哲学的不同而非本体等级的高下；代码共享减少不等于 DragonFly 本体论地位低于 FreeBSD——DragonFly 的独立演进（持续维护与 HAMMER2 生产可用）证明其本体论地位的实质性

## 226.4.3 解释学循环与权力知识共谋——以总纲第 19 条审视代码共享叙事

**要点**：代码共享减少事件的叙事建构以总纲第 19 条“解释学循环与权力知识共谋”审视——DragonFly 与 FreeBSD 代码共享减少的叙事在不同立场中呈现显著差异：FreeBSD 阵营叙事强调“DragonFly 自研路线导致代码共享趋近于零是 fork 关系的自然结果”，DragonFly 阵营叙事强调“代码共享减少是 DragonFly 独立演进的工程合理性体现”，Linux/illumos 外部叙事强调“BSD 阵营频繁分裂导致各项目代码共享减少”；三种叙事的前理解（vorverständnis）差异决定其叙事建构的差异——FreeBSD 阵营的前理解是“集体治理与代码共享优于个人主导与独立演进”，DragonFly 阵营的前理解是“技术路线自主性与工程哲学纯粹性优于代码共享与生态协同”，Linux/illumos 阵营的前理解是“统一聚合优于分裂演化”；illumos-gate.duckdb 提供的客观数据（MFC commit 量按年 6/34/37/34/18、活跃 committer 数 33/35/33/33/28、Dillon commit 量 467/567/377/323/335）可部分校正叙事偏差，但数据本身亦非中立——MFC commit 量反映代码共享的频率但不反映代码共享的质量（驱动程序移植 vs 核心子系统移植），活跃 committer 数反映社区规模但不反映社区健康度（活跃 committer 数下降不等于社区衰退，可能是维护效率提升）；权力与知识的共谋体现于叙事建构——FreeBSD 通过 Release Notes、Foundation 年报、Core Team 决议记录建构“集体治理合法性”叙事，DragonFly 通过 commit message、fork 公告、dragonflybsd.org/history 页面建构“技术路线合法性”叙事，两种叙事均以“项目利益”为名但服务于不同的权力诉求；本节（98.4.5-98.4.7、13.5）的辩证链补足与项目统摄史观审视即是试图打破单一叙事的权力垄断，使 FreeBSD 阵营与 DragonFly 阵营的论点对称呈现——解释学循环亦适用于本审视自身——项目统摄史观审视嵌入项目统摄史观的前理解，须自觉呈现这一前理解而非伪装中立，合图（98.4.7）不是辩证链的终结而是阶段性综合，随 DragonFly 与 FreeBSD 代码共享的进一步演化（如 DragonFly 是否在 v5.x-v6.x 时期进一步减少或增加 MFC commit）须重新展开

## 226.4.4 革命与改革——以总纲第 21 条审视 DragonFly 的 fork 路线选择

**要点**：DragonFly 2003 年 fork 后的代码共享减少演化以总纲第 21 条“革命与改革是历史方法论的分歧”审视——Dillon 2003 年选择 fork（革命）而非在 Core Team 框架内继续协商（改革），反映 DragonFly 阵营的“革命”方法论与 FreeBSD Core Team 的“改革”方法论的方法论分歧——Dillon 认为 FreeBSD 5.x 的 SMPng 路线“too heavily mutexed”（ONLamp 2004 年采访），通过 fork 重建个人主导的技术路径（LWKT/HAMMER/HAMMER2/vkernel）是革命性变革而非渐进性改革；dragonfly.duckdb 显示 DragonFly fork 后 8-12 年间（至 2011-2015 年 v3.x-v4.x 时期）的代码共享减少（MFC commit 量从 6 条到 18 条）反映革命的代价——革命后的代码共享减少使 DragonFly 无法有效利用 FreeBSD 社区的维护力量，DragonFly 须独立维护全部子系统；但革命亦有收益——DragonFly 通过 fork 实现了 HAMMER2 文件系统的自研（无 CDDL 许可争议）、LWKT 路线的持续演进（不受 FreeBSD SMPng 路线约束）、vkernel 的自主开发（不受 FreeBSD bhyve 路线约束）；FreeBSD Core Team 的“改革”方法论（在 Core Team 框架内协商解决技术路线分歧）的收益是代码共享与生态协同（FreeBSD 可利用社区力量维护全部子系统），代价是技术路线协商成本（Core Team 须协调不同派系的资深开发者异议，如 Dillon fork 前的协调失败）；“革命”与“改革”的优劣无客观裁决标准——DragonFly 以代码共享减少、社区规模萎缩、生态孤立换取自研路线独立性、技术路线自主性、工程哲学纯粹性是结构性选择而非道德缺陷，FreeBSD 以技术路线协商成本、集体决策效率限制换取代码共享与生态协同亦是其结构性选择——二者皆有其历史语境与合理性，须以多元利益框架审视
