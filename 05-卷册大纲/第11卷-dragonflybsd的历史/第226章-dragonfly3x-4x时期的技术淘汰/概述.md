## 本章概述（五字段，2026-09-11 整改补写）

- 要点：本章叙述 DragonFly 3.x-4.x 时期（约 2011-2015）的技术淘汰三线——其一，sendmail 从 base 移除与 DMA 默认 MTA 切换（2007 年 3 月 corecode 首发 DMA，2015 年 3 月 DMA 成为默认 MTA）；其二，与同时期操作系统（FreeBSD、Linux、OpenBSD）的文件系统与内核技术对照；其三，3.x 周期漏洞与安全响应（dragonfly.duckdb 载 3.x 周期 CVE 相关 commit 18 条、Security fix commit 1 条，OpenSSL 多次版本导入）
- 史料：dragonfly.duckdb dragonfly-src 仓库 commits 表（CVE/Security fix commit 序列、MFC/From FreeBSD 关键词按年统计、Dillon 2011-2015 年按年 commit 量）；corecode 2007.3 kernel@ DMA 首发公告与 Matthias Schmidt 2008.2.1 “round two” 邮件；DragonFly BSD Digest 2015.3.9 报道；FreshPorts mail/dma 元数据；DragonFly 官方 release 页面（v3.2.0/v3.4.0/v3.6.0）；下方 MAIL_INSIGHT 两条 Dillon 2023 年邮件（VLAN 基础设施过时自述、驱动移植困难自述）
- 史观：总纲第 17 条（证明世界先于解释和改造世界）——DMA“先发布核心、再渐进增强”的工程节奏；总纲第 22 条（知识注定过时）——sendmail 在 BSD 阵营的退场节奏差异（NetBSD 渐进替换、OpenBSD 安全优先、DragonFly 自研替代、FreeBSD 保守保留）；总纲第 5 条（没有必然性，只有偶然性）——技术淘汰的具体路径由偶然事件与主体选择构成；总纲第 19 条（解释学循环）——fork 初期技术路线在二十年后以“API 分歧导致驱动无法移植”的形式回归为结构性约束；多方平等与经验优先——以邮件列表原始帖与 commit 原文为优先依据
- 辨析：DMA 首发日期 2007.3 与 2008.2 两说须区分“首发”与“功能完整化”两个节点；OpenBSD sendmail 移除时点（5.6 仍含、5.7 确认移除）与二手转述“2014 下半年”须交叉验证；驱动移植困难的因果链（fork 路线选择→API 分歧→结构性技术债务）须避免目的论化
- 文献：详见 226.1-226.4 各节文献字段；DragonFly BSD Digest 2015.3.9 报道；FreshPorts mail/dma 页面；GitHub corecode/dma 上游仓库；dragonfly.duckdb dragonfly-src 仓库 commits 表
