# 219.3 DragonFly 1.2-1.8 的持续改进（2005-2006）——1.2 引入 HAMMER 文件系统雏形、1.4 改进 SMP 性能、1.6 引入新的网络栈、1.8 改进 VFS 层

## 219.3.1 HAMMER 雏形的设计

**要点**：DragonFly 1.2（2005-04-08）发布，但 HAMMER 文件系统雏形并非于 1.2 引入（其实验性支持始于 1.12/2008-02-26、生产可用随 2.0/2008-07-20）[存疑脚注：经 DragonFly 官方 release 页核验]——Dillon 设计的 B-tree 写时复制文件系统，目标是替代 UFS 与 ZFS；HAMMER 雏形仅支持基本功能，完整版在 2.0（2008.7）发布；HAMMER 设计哲学是 “轻量级写时复制”，避免 ZFS 的内存消耗与复杂度

**史料**：DragonFly 1.2 Release Notes HAMMER 部分；Dillon 的 HAMMER 设计文档；DragonFly 邮件列表 HAMMER 讨论；dragonfly.duckdb 查询 L1.1.1 显示：dragonfly-src 2005 年 commit 量 4,194 条（1.x 时代峰值），2006 年 commit 量 1,874 条（显著回落），反映 1.2 发布前后开发强度变化；dragonfly.duckdb 专门查询 dragonfly-src 中 sys/vfs/hammer* 路径 commit 演化显示：HAMMER 文件系统 commit 在 2007 年才出现（181 条 commit、21 个文件），2008 年激增至 1,213 条 commit（32 个文件，对应 HAMMER 1.0 随 DragonFly 2.0-RELEASE 发布），反映 HAMMER 雏形在 1.2（2005-04-08）时期仍处于设计阶段，大规模工程实现集中在 2007-2008 年；dragonfly.duckdb 查询 dragonfly-src bus factor 显示：2005 年 top10 贡献者占 90.34%（22 位贡献者中前 10 位占九成），2006 年 top10 占 94.88%，反映 1.x 时代开发高度集中于少数核心开发者 ［A］

**史观**：总纲第 17 条——软件工程：HAMMER 雏形体现 “轻量级写时复制” 的工程哲学——以减法对抗 ZFS 的加法

**辨析**：HAMMER 雏形与正式版的功能差异需考据；HAMMER 与 ZFS 的设计哲学比较在不同叙事中存在简化；【0 信任原则·commit 量不等于质量】2005 年 commit 量峰值 4,194 条可能含大量 LWKT/token 基础设施重构 commit，并非全部用于 HAMMER 雏形；2006 年回落至 1,874 条可能与 HAMMER 雏形进入稳定期或 Dillon 个人精力分配变化有关，须结合 commit message 主题词核验；【0 信任原则·文件路径匹配局限】sys/vfs/hammer* 路径匹配可能遗漏 HAMMER 相关的头文件与文档 commit，2006 年 HAMMER 雏形的设计文档与头文件 commit 可能散落在 sys/vfs/与其他路径

**要点**：

- DragonFly BSD 1.4 于 2006 年 1 月 7 日发布；主持人补记此前遗漏，并说明该项目由一群围绕 FreeBSD 5 系内核希望作出重大改动的人分叉而来，旨在验证其在多处理性能上的理论，若理论成立则成果可惠及全部 BSD。（BSDTalk EP7，[20.38-79.16]，L2）
- GPL 正酝酿第三版：Richard Stallman 主导的修订拟纳入争议性反 DRM 条款，即 GPLv3 软件不得被改造用于对不自愿用户强制数字版权管理（如 TiVo 式设备限制用户复制与媒介转移的合理使用）。因 BSD 生态大量依赖 GNU 工具、尤其 GCC 编译器（Apple 亦曾长期为 PowerPC 改进 GCC），主持人推演其后果：并非所有软件都会升级到 v3，若 GCC 随 v3 发布可能出现以 v2 末版为基的分叉编译器，商业公司转向 Intel 平台后也可能改用 Intel 编译器；而 BSD 许可证仅有数行、几乎无限制（只要求署名与免于诉讼），GPLv3 的争议或促使商业公司重新审视 BSD 许可证与 BSD 系统，成为 BSD 的转折点。（BSDTalk EP7，[84.90-361.82]，L2）
- 主持人选取五款 BSD live CD 实测：FreeSBIE（FreeBSD 基）、Anonymous（OpenBSD 基）、DragonFly 安装盘（自述兼作 live CD 但极简）、NetBSD 官方 live CD（定位救援盘兼 KDE 桌面）、Newbee（NetBSD 基，主打全功能图形桌面）；测试硬件为 233 MHz/128 MB 旧笔记本、自制 AMD 2600 台式机、仅 USB 外设的 Dell GX280 与新款 Centrino 笔记本 Dell Latitude D610。（BSDTalk EP7，[376.02-517.04]，L1）
- 实测结果：除 Dell GX280 上 NetBSD live CD 不识别 USB 键盘致无法继续外，其余组合均可启动联网；DragonFly 盘仅文本模式、实用价值低但足以验证硬件支持；NetBSD 盘因缺 libqt 而无法启动 KDE，但 X 与轻量窗口管理器可用；Newbee 启动 Fluxbox 或 Blackbox 并预装浏览器邮件聊天工具；FreeSBIE 允许启动时选择轻量或重量级图形界面，基于 FreeBSD 5.3（2004 年 12 月发布），虽技术偏旧仍被主持人评为最佳 BSD live CD 桌面。横向对照：BSD live CD 资源占用普遍不高，但与 Linux 系 live CD 参照物（转写作 Canopix）相比浏览器启动明显偏慢，当事人将差距归因于后者更成熟、优化投入更多。（BSDTalk EP7，[549.84-843.56]，L1）
- 分叉缘由与时机：DragonFly 自 FreeBSD 4.8 或 4.9 分叉，时机极佳——恰在 FreeBSD 为 5.x 及以后进行重大改造之前取得极稳定基座；分叉主因是 FreeBSD 为从单处理器架构迈向真 SMP 采取了他不认同的重型机制，特别是以 mutex 锁定内核各部分以摆脱 giant lock 的方式，未必错误但他认为过重，这促使他考虑分叉建树。（BSDTalk EP22，[244.72-298.60]，L1）
- 透明集群愿景：终极目标是内核级透明的集群架构——进程可在机器间迁移，机群运作如单一系统映像；愿景是把互联网广域环境的算力联合起来，从 SETI@home 式原始形态进阶到将家庭机器的 CPU、存储与网络资源安全地分配给互联网上的集群，供望远镜项目、公钥猎获、天气预报等需超算或本地大集群的任务使用。维护场景要求双机集群中把一台机的全部进程迁出后可安全关机换件，这不是冗余（冗余更难）。前提是数据一致性：把文件当数据库用的复杂程序需要与 SMP 模型相当的缓存一致性，这是进程迁移的门槛；此构想不同于任何现有操作系统，但概念不新——今日以 NFS 导出文件系统是粗糙等价物。安全约束：广域多贡献者集群存在安全问题，最适用途是结果可被更安全机器独立验证的批处理。架构取舍：仅支持 Intel/AMD 32 位，64 位虽为其所好但暂缓——开发者与时间有限必须排定优先级，跨架构移植会把内核核心焊死、妨碍大改，须先把核心朝目标做扎实。（BSDTalk EP22，[111.52-628.28]，L1）
- 版本与稳定性：刚发布 1.4（实际第三个主要发布），采用类 Linux 的偶数稳定、奇数开发版本号，1.5 约在六七月转为 1.6；迄今工作多为内核内部大手术、用户可见变化刚开始浮现；1.4 是迄今最稳定的系统，堪比以稳定著称的 4.x。团队规模：约 12 人做显著内核贡献、另四五人做文档，外围贡献者在 DragonFly 与 NetBSD、OpenBSD、FreeBSD 各树之间双向搬运 bug 修复。透明集群目标预计还需约两年，年底开始出现用户可见部件——内部重构已足以着手多机环境所需的缓存架构。（BSDTalk EP22，[301.40-431.56]，L1）
- 采纳 pkgsrc 的决策链：项目初创时 Jordan Hubbard 建议第一要务是包系统，但包系统整合极难——包往往面向特定系统、大量面向 Linux，即便命令集同源仍有可移植性问题，上千包的规模更放大难度。最初在 ports 上加 shim 与 overlay 打小补丁，但从无长期维护之意。选 pkgsrc 的理由：它是同期起步、已趋成熟的多平台努力；FreeBSD ports 若有可移植尝试，本质上仍是 FreeBSD 专用系统、并非为 DragonFly 设计，长期必成维护负担；更关键的是数名 DragonFly 开发者同时是 pkgsrc committers 并在做积极开发——不能指望无人开发、无人修 bug、无人深知它的包系统能长期维持，人的因素是决定性考量。（BSDTalk EP22，[628.28-801.04]，L1）
- 对开源生态的结构判断：须区分内核中心项目（Linux、FreeBSD、NetBSD、OpenBSD 内核）与应用集——后者由编写应用的人代表而非打包系统，GIMP、KDE、OpenOffice 等可轻松移植到几乎任何类 Unix 环境，不少新包虽面向 Linux 编写仍可移植；Linux 从 Unix 继承了大量应用集。开源在公众眼中的增长实际是应用集的增长，与内核与核心工作几乎无关，且将长期如此；因此媒体所谓 Linux 正在碎片化、内核太多的报道不实——内核可以很多，KDE 只有一个。（BSDTalk EP22，[1182.76-1295.62]，L1）
- 1.6 定位以修复为主，修复清单长达两三百条且以文件系统代码居多；基础设施层面完成缓冲缓存的 buffer 与 BIO 拆分（与 FreeBSD 约一年前的做法类似）、彻底废除块编号改用 64 位字节偏移，并将大内核锁显著推进，使多数文件描述符例程已可 MP safe 运行；另含新随机数生成器与 soft updates、NFS、浮点子系统、线程等大量修复。（BSDTalk EP53，[164.24-249.12]，L1）
- Dillon 列出三大目标：userland VFS（允许文件系统作为用户进程运行的 API）、ZFS 移植（依赖 userland VFS，直接移植进内核相当困难）与集群（他称之为最大的一盘棋）；并坦言创立 DragonFly 时未料到集群之前需完成如此大量的内核基础设施工作。（BSDTalk EP53，[293.5-348.74]，L1）
- 集群的正确含义远超 NFS：跨机共享打开文件须做到百分之百缓存一致性，因为单一线程化程序的线程可能分属两台物理机；为此需要类似 SMP 硬件缓存一致性协议的软件机制，把 BSD 传统上对写操作独占整个 v-node 的锁改为按文件的范围锁，由此牵出整条基础设施改造链。（BSDTalk EP53，[354.34-454.78]，L1）
- 部分机制已获实现验证：并行路由表工作正常，线程化网络栈运转良好（性能测试暂不理想，因 MP 锁尚未完全移除）；线程切换时间低于一微秒，进程间消息低于一微秒且可批处理——批模式下首条约一微秒、后续每条仅 10-15 纳秒；这些量化证明使内核能以更模块化、更可调试的方式编写。（BSDTalk EP53，[836.86-894.9]，L1）
- Dillon 自述内核设计立场：既不属于微内核阵营也不属于单整体阵营，支持模块化但承认大型基础设施必须单整体才能获得真实性能，稳定性也要求代码集成于一处——他以 Windows 由五万个厂商提供驱动、兼容性碰运气作反例，自认处于中间地带。（BSDTalk EP53，[895.9-962.0]，L1）
- Dillon 开场自我定位为 DragonFly 项目创始人，自述过去两年一直在谈理论，本场是他首次就 DragonFly 已实现的 SMP 机制给出实测硬数字；测试平台为 AMD Athlon 3800+ 低成本双核（约 300 美元、2 GHz）装于 Shuttle 机箱，因机载 Nvidia 千兆网卡不工作而改插 Intel em 的 PCI 网卡，并明言测试目的是算法性能而非吞吐量，故无法测吞吐。（YouTube EPEfNZ4jMQic4，[36.7-59.9, 59.9-95.9, 195.4-230.6, 230.8-259.8]，L1）[订正：原 594.5-643.8（乒乓测试与 TSC 漂移段，与本条内容无关）→61.6-93.4（“过去两年只谈理论、首次给出 SMP 实测硬数字”段），内容复核]
- 测量前他先量化测量工具本身：KTR 内核追踪日志机制经其确认原创于 BSDi，设计极简且 MP 安全，无参数记录一次约 40 纳秒，该开销从全部结果中扣除。critical section 为 CPU 本地原语，承袭 FreeBSD 4 SPL“置内存标记、中断仅记录即返回”的思想而不复用 cli/sti，纯标准指令高度可缓存，进出合计实测 9.5 纳秒，设计意图是让内核代码随处进入临界区而不必顾虑性能代价。（YouTube EPEfNZ4jMQic4，[260.1-321.0, 295.3-315.5, 422.8-495.9, 438.0-465.7]，L1）[订正：原 [262.2-299.1] 未覆盖“无参数约 40 纳秒”数值段→扩至 [262.2-320.1] 并含 306.0-320.1（40 纳秒与扣除说明），内容复核]
- IPIQ 是 DragonFly 的低层异步跨 CPU 消息机制，底层为各 CPU 间完全无锁的软件 FIFO（独立读写索引追赶式推进），连续多条消息只触发一次实际 IPI 中断；端到端乒乓测试给出约 1 微秒的单次往返（含全部中断与 APIC 开销，两 CPU 各摊约 500 纳秒），流水线预热后单条消息开销降至 40 纳秒以下，据此他向缺乏 SMP 经验的开发者澄清：跨 CPU 发消息远没有直觉中昂贵，除非达到每秒百万级消息量。（YouTube EPEfNZ4jMQic4，[501.7-593.1, 599.2-748.3, 642.7-705.0, 705.9-748.3]，L1）[订正：原 [503.3-592.4] 截断“连续多条消息只触发一次实际 IPI 中断”结论（590.2-598.8）→扩至 [503.3-598.8]，内容复核]
- 唤醒与内存释放路径呈现同一无锁化逻辑：单 CPU 上 tsleep 唤醒端到端约 1.2-1.3 微秒，跨 CPU 时发起侧仅 75 纳秒（异步排队即返回），目标侧延迟约 1.7 微秒，wakeup 实现完全无锁，仅存一个 CPU 的总线锁周期且他仍在设法消除；slab 分配器按 CPU 拥有内存，跨 CPU 释放以 IPI 归还属主，使分配器仅需临界区即可本地运作；passive IPI 更把释放请求滞留于 FIFO、由时钟中断顺带冲刷，实现目标 CPU 上的“保证聚合”，多次释放可摊薄单次 IPI 成本。（YouTube EPEfNZ4jMQic4，[774.2-902.4, 904.4-949.3, 1082.3-1157.7, 1127.5-1157.7]，L1）〔订正：新转写为“one bus lock cycle for a CPU”，原“CPU 掩码”无据，据新转写订正〕
- 测量中的异常本身成为方法论注脚：跨 CPU 释放在目标侧最初测得 745 纳秒的怪值，他排查缓存效应无果后归因于 malloc/free 路径携带参数的 KTR 日志干扰，精简日志后降至 359 纳秒。网络栈方面每 CPU 各设一个 TCP 线程，输入包按地址与端口解复用，特定连接的报文恒由同一线程处理其 TCB，故重负载下完全无需自旋锁，但 giant lock 尚未彻底去除；em 中断单包开销 2.5 微秒，部分源于发送前为消息头而 malloc，预分配嵌入 mbuf 预计可省两三百纳秒；全场最大结论是缓存效应巨大——一次缓存失效相当于 10-30 条可缓存指令，这促使他更坚定地推进工作聚合。（YouTube EPEfNZ4jMQic4，[960.2-1046.2, 1272.7-1314.4, 1168.4-1229.9, 1251.0-1269.8]，L1）
