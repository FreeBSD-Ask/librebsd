# 219.7 DragonFly BSD 1.x 时期的技术淘汰——FreeBSD 4.x→DragonFly fork、SMPng 细粒度锁 →LWKT 消息传递、传统 mutex/BGL→token、FreeBSD 4.x VM→DragonFly 早期 VM 改造（2003-2008）

## 219.7.1 FreeBSD 4.x → DragonFly BSD fork（**2003.7.16**，Matt Dillon）

**要点**：2003 年 6 月 Matt Dillon 开始基于 FreeBSD 4.8（2003.4 发布）的 fork 工作，**2003 年 7 月 16 日** 在 freebsd-current@ 邮件列表发布 DragonFly BSD 公告，原文要点如下：
    > Annoucning DragonFly BSD!（原文拼写如此）
    > DragonFly is the logical continuation of the FreeBSD 4.x series.
    > giving the BSD base an opportunity to grow in entirely new direction from the one taken in the FreeBSD-5 series.
    这一 fork 行为 “淘汰” 了 FreeBSD 4.x 作为 DragonFly 直接上游的地位，也 “淘汰” 了 FreeBSD 5.x SMPng 细粒度锁路径在 DragonFly 中的可能性；Dillon 先前在 FreeBSD 项目内部推动消息传递架构但与 Core Team 冲突，commit bit 最终被撤销，fork 成为唯一出路；“the logical continuation of the FreeBSD 4.x series” 的定位后期被 Dillon 自己放弃，DragonFly 官方 history 页面改称：
    > this description has long since become obsolete
**史料**：Dillon 2003.7.16 freebsd-current@ 公告（**lists.freebsd.org/pipermail/freebsd-current/2003-July/006889.html**）；OSNews 2003.7.17 报道 “FreeBSD 4.x Forked Into DragonFly”（osnews.com/story/4058/）；DragonFly 官方 history 页面（dragonflybsd.com/history/）记载 “DragonFly BSD was forked from FreeBSD 4.8 in June of 2003, by Matthew Dillon（马修·狄龙）” ［A］

**史观**：总纲第 4 条——分离与聚合：DragonFly fork 是 BSD 阵营分离聚合律的又一次重演，技术路线分歧导致组织分离；总纲第 22 条——BSD 反向影响线：DragonFly 作为 FreeBSD 的反向影响者，通过 fork 验证了 FreeBSD 5.x SMPng 路径并非唯一选择

**辨析**：fork 公告的精确日期在不同来源中存在差异——butthurtfork.com 与部分二手百科来源均确认为 2003.7.16，OSNews 报道日期为 2003.7.17；Dillon 开始 fork 工作的日期（2003 年 6 月）与公告日期（7 月 16 日）有约 1 个月间隔，需在叙事中区分 “开始工作” 与 “公开公告” 两个节点；“logical continuation of the FreeBSD 4.x series” 的定位后期被 Dillon 自己放弃，DragonFly 官方 history 页面称 “this description has long since become obsolete”

**文献**：Dillon fork 公告；OSNews 2003.7.17 报道；DragonFly 官方 history 页面 ［C］

## 219.7.2 FreeBSD 5.x SMPng 细粒度锁路径 → DragonFly 1.0 LWKT 消息传递（2003-2004）

**要点**：FreeBSD 5.x（5.0 于 2003.1 发布）选择 SMPng（SMP Next Generation）细粒度锁路径改造内核，让多核并行进入内核；Dillon 认为 SMPng 的锁路径 “过于复杂、脆弱、维护困难”，主张以消息传递与轻量级内核线程替代；**DragonFly 1.0**（**2004.7.12** 发布）即包含 LWKT（Light Weight Kernel Threading）子系统、IPI（Inter-Processor Interrupt）消息传递机制、每 CPU 独立线程队列；1.0 发布公告明确称：
    > replaced nearly all of the core threading, process, interrupt, and network infrastructure
    并将 “开始移除 BGL（Big Giant Lock）” 列为下一阶段目标；同期 FreeBSD 5.x 继续推进 SMPng 路径，二者在 SMP 设计上根本分化。DragonFly 1.x 版本发布时间线如下：
    | 版本 | 发布日期 | 关键特性 |
    |---|---|---|
    | 1.0 | **2004.7.12** | LWKT、token 雏形、FreeBSD 4.x 兼容性 |
    | 1.0A | **2004.7.14** | 快速修正版 |
    | 1.2 | 2005-04-08 | 基础发布（HAMMER 雏形实为 1.12/2008-02-26 实验性引入） |
    | 1.4 | 2006.8 | SMP 性能改进、LWKT 调度器优化 |
    | 1.6 | 2007.2 | 基于 LWKT 的每 CPU 网络栈线程 |
    | 1.8 | 2007.11 | 基于 LWKT 的 VFS 操作消息传递 |
    | 1.10 | **2007.8.6** | token 机制替代 mutex |
    | 1.12 | 2008.4 | token 优化、多核性能改进 |
**史料**：DragonFly 1.0 RELEASED 公告（**lists.dragonflybsd.org/pipermail/kernel/2004-July/212809.html**，Dillon 2004.7.12）；DragonFly 1.0A 公告（**lists.dragonflybsd.org/pipermail/kernel/2004-July/212852.html**，2004.7.14，快速修正版）；DragonFly 1.0 release notes；SMPng 设计文档；LWKT 设计文档（dragonflybsd.org/goals/threads.cgi）［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］〔L3 官方文档与公告〕

**史观**：总纲第 6 条——技术路线分化：SMPng 与 LWKT 的根本分歧反映 FreeBSD 与 DragonFly 的技术路线分化，是 BSD 阵营技术路线分化的典型；总纲第 17 条——软件工程：LWKT 是软件工程中 “消息传递 vs 锁” 哲学分歧的具体实现

**辨析**：DragonFly 1.0 的精确发布日期在不同来源中存在差异——本卷 50.1.2 节原稿沿用 ~~2005.3~~ 说法，经 WebFetch `https://www.dragonflybsd.org/releases/` 一手核证与 Dillon 2004.7.12 kernel@ 邮件公告交叉验证，已修正为 **2004.7.12**（1.0A 为 **2004.7.14**）；~~2005.3~~ 系部分二手来源的误传；1.0 公告中 “replaced nearly all” 的表述为 Dillon 自我陈述，需对照 commit log 核验实际替换范围；1.0 仍依赖 FreeBSD ports tree 与 4.x pthreads 模型，并非完全替换

## 219.7.3 传统 mutex 与 BGL（Big Giant Lock）→ DragonFly token 机制（2005-2007）

**要点**：FreeBSD 4.x 继承自传统 BSD 的 BGL（Big Giant Lock，亦称 MP lock）在 DragonFly fork 初期仍大量保留，1.0 公告将 “移除 BGL” 列为下一阶段目标；DragonFly 1.10（**2007.8.6** 发布）引入 token 机制——LWKT 框架下的轻量级同步原语，让线程在持有时可被抢占，避免 mutex 的死锁与优先级反转问题；token 由 Dillon 设计，是 DragonFly 区别于其他 BSD 的关键同步机制，1.10 之后 BGL 在 DragonFly 中逐步被 token 替代；同期 FreeBSD 5.x/6.x 继续推进 SMPng 细粒度锁，与 DragonFly token 路径根本分化；DragonFly 官方 history 页面记载：
    > the token, lends itself directly to ease of maintenance and understandability of the kernel
    token 与 mutex 的关键差异对照如下：
    | 维度 | FreeBSD mutex | DragonFly token |
    |---|---|---|
    | 持有时可抢占 | 否 | 是 |
    | 同步原语类型 | 自旋锁/睡眠锁 | LWKT 框架下轻量级同步原语 |
    | 死锁风险 | 较高 | 较低（持有时可被抢占） |
    | 优先级反转风险 | 较高 | 较低 |
    | 多核扩展性 | 适配现有代码 | 适配重新设计 |
    | 学习曲线 | 较平缓 | 较陡 |
**史料**：DragonFly 1.10 release notes；Dillon 的 token 设计文档；DragonFly 源码 `sys/sys/lwkt_token.h`；DragonFly 官方 history 页面 ［A］

**史观**：总纲第 17 条——软件工程：token 机制是软件工程中 “避免锁竞争” 哲学的极致实现，体现 DragonFly 形式主义化的工程路径；总纲第 3 条——形式主义膨胀：token 是 Dillon 将 “轻量级同步” 哲学固化为代码结构的形式主义化实践

**辨析**：1.10 的精确发布日期在不同来源中存在差异——日文 wdic 记载 **2007.8.6**，本卷 50.4.1 节沿用 ~~2007.11~~ 的说法，需以 DragonFly 官方 release notes 为准；token 与 mutex 的性能对比缺乏权威基准——需对照同硬件同负载核验；BGL 的移除是渐进过程而非 1.10 一次性完成，需对照 commit log 考据具体移除时间

**文献**：DragonFly 1.10 release notes；DragonFly token 设计文档；DragonFly 源码 lwkt_token.h ［A］

## 219.7.4 与 FreeBSD/NetBSD/OpenBSD/Linux 同期 SMP 技术路线选择的对照与辨析（2003-2008）

**要点**：2003-2008 年间 BSD/Linux 阵营在 SMP 同步机制上呈现四条路径——FreeBSD 5.x/6.x/7.x 选择 SMPng 细粒度锁、DragonFly 1.x 选择 LWKT 消息传递与 token、OpenBSD 3.4-4.3 选择 “Big Lock 简化” 保守路径、Linux 2.6 选择 BKL 渐进移除与 BKL→mutex 替换；NetBSD 同期选择细粒度锁定路径但进度保守；DragonFly 的 token 路径在 BSD 阵营中独树一帜，与 FreeBSD SMPng、OpenBSD 保守路径均不同；这一时期各项目的 SMP 路径选择塑造了后续十年的技术演化基础。同期 BSD/Linux SMP 路径分化对照如下：

    | 项目 | 同步机制 | 路径选择 | 典型版本 |
    |---|---|---|---|
    | FreeBSD 5.x/6.x/7.x | SMPng 细粒度锁 | 锁路径 | 5.0（2003.1）至 7.x |
    | DragonFly 1.x | LWKT 消息传递 + token | 消息传递路径 | 1.0（2004.7.12）至 1.12 |
    | OpenBSD 3.4-4.3 | Big Lock 简化 | 保守路径 | 3.4（2003）至 4.3（2008） |
    | Linux 2.6 | BKL 渐进移除 | 锁路径 | 2.6.0（2003.12）至 2.6.39（2011） |
    | NetBSD 2.x/3.x | 细粒度锁定（保守） | 锁路径（保守） | 2.0（2004）至 3.0（2005） |
**史料**：FreeBSD 5.x/6.x/7.x release notes 与 SMPng 设计文档；DragonFly 1.x release notes；OpenBSD 3.4-4.3 release notes；Linux 2.6 release notes 与 BKL 移除记录［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］〔L3 官方文档与公告/L5 二手研究〕

**史观**：总纲第 6 条——技术路线分化：BSD/Linux 四个项目的 SMP 路径分化是技术路线分化的极致体现，每种路径都有其项目目标驱动；总纲第 22 条——BSD 反向影响线：DragonFly 的 token 路径虽未成为主流，但为 BSD 阵营提供了 “避免锁竞争” 的另一种可能性

**辨析**：四条路径的优劣无绝对标准——FreeBSD SMPng 在大规模商业部署中更成熟，DragonFly token 在小规模高并发场景有局部优势，OpenBSD 保守路径在安全审计中更可控，Linux BKL 移除在生态规模上更成功；性能比较需结合具体负载与硬件配置，避免笼统优劣判断；Linux 2.6 BKL 移除工作的具体进度需考据——2003-2008 年间 Linux 仍保留大量 BGL 用法，完全移除延续至 2011 年后的 2.6.39 与 3.x 系列

**文献**：各 BSD/Linux 项目 release notes 与设计文档；SMP 同步机制比较研究文献［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

## 219.7.5 DragonFly fork 详述辩证链——批评、反批评、再批评与项目统摄史观合图（2003-2010）

### 219.7.5.1 批评层——社区对 fork 必要性的质疑（2003.7-2003.12）

**要点**：2003 年 7 月 16 日 Dillon 在 **lists.freebsd.org/pipermail/freebsd-current/2003-July/006889.html** 发布 fork 公告后，批评方史料主要来自三个层面。其一，FreeBSD committer 群体在 freebsd-current 邮件列表的跟帖质疑——Julian Stacey（<jhs@berklix.org>）在 2003.7.17 跟帖直言“There’s too many BSD’s already”，质疑再次分裂 BSD 开发者力量的必要性；Kris Kennaway（<kris@obsecurity.org>）同日以讽刺口吻回应，称"a Markov chain script could do a fairly passable impersonation of the latter"；Maxim Sobolev（<sobomax@portaone.com>）确认 Dillon 身份真实但未表态支持；Garance A Drosihn（<drosih@rpi.edu>）态度友善中性。其二，技术媒体的匿名评论——OSNews 2003.7.17 报道下 51 条评论中，评论 21 原文"yet another BSD fork based on the ego of a single hacker who couldn’t get along with the rest of the team“、评论 28 原文”EXACTLY my way or no way isn’t an ego thing?! ### 219.7.5.2 反批评层——Dillon 与 DragonFly 阵营的回应（2003.7-2004.7）

**要点**：Dillon 对 fork 必要性的论证以工程判断为核心而非情绪性辩护，回应分言论与代码两个层面。言论层面，fork 公告原文明确表述三项工程理由：其一，FreeBSD 5.x“too heavily mutexed”（锁机制过重），其二，"it was actually faster to start with 4.x and move forward rather then to start with 5.x and move backwards“（从 4.x 向前推进比从 5.x 向后退更快），其三，LWKT 子系统已在”proving work“中验证了无 mutex 的轻量级内核线程可行性；DragonFly 官方 history 页面将 fork 定位为”the logical continuation of the FreeBSD 4.x series“；ONLamp 2004 采访”DragonFly BSD: A Fork in the FreeBSD Road"中 Dillon 进一步阐述 LWKT 消息传递架构优于 SMPng 细粒度锁的设计理念；dragonfly.kernel 邮件列表 2003-2006 年间 Dillon 多次提及 FreeBSD 5.x 路线的“过度复杂化”。代码层面，dragonfly.duckdb 显示 Dillon 在 dragonfly-src 仓库 2003-2008 年间 4222 条 commit（<dillon@dragonflybsd.org> 邮箱），LWKT 在 fork 后 2 天 19 小时即实现（`984263bcb83a` → `8ad65e080342`），token 机制在 1.10（2007.8.6）引入，HAMMER 雏形在 1.2（2006.2）披露——以代码成果证明 fork 路线的可行性。社区支持者从四个维度为 fork 辩护：不同的工程目标不可调和、不同项目需以不同方式探索、软件开发存在最优参与人数而非越多越好、BSD 历史上 fork 常带来正向回报（如 OpenSSH 源自 OpenBSD fork）；dragonfly.duckdb 显示 Jeffrey Hsu 在 dragonfly-src 首 commit 为 `2003-07-24T05:21:48Z`（距 fork 公告仅 8 天），反映 fork 公告前已与 Dillon 达成合作意向，Hsu 的转向是对 fork 必要性质疑的间接回应

**史料**：Dillon 2003.7.16 fork 公告原文（**lists.freebsd.org/pipermail/freebsd-current/2003-July/006889.html**，标题原文“Annoucning DragonFly BSD!”拼写如此），公告核心表述“take over development of the 4.x tree”“too heavily mutexed”“faster to start with 4.x and move forward”；ONLamp 2004“DragonFly BSD: A Fork in the FreeBSD Road”采访（经 archive.org 核验）；dragonfly.kernel 邮件列表 2003-2006 年 Dillon 发言（lists.dragonflybsd.org 完整归档）；DragonFly 官方 history 页面（**dragonflybsd.org/history/**），“the logical continuation of the FreeBSD 4.x series”表述与“this description has long since become obsolete”自否弃声明并存；OSNews 评论 27 原文"Matt Dillon talked about forking 4.x way back when 5.x was in planning stages...I don’t think it’s purely an ego thing“、评论 18 从五个维度论证 fork 合理性、评论 24 论证 BSD 历史 fork 的正向回报”FreeBSD has benefited from both OpenBSD and NetBSD"；DragonFly 1.0 RELEASED 公告（**lists.dragonflybsd.org/pipermail/kernel/2004-July/212809.html**，Dillon 2004.7.12），1.0 的发布本身即是对 fork 必要性质疑的工程性回应；dragonfly.duckdb dragonfly-src 首 commit `984263bcb83a`（`2003-06-17T02:57:24Z`，message“Initial import from FreeBSD RELENG_4”），反映 fork 工程工作在公告前约 1 个月即已启动；dragonfly.duckdb dragonfly-src 仓库 contributors 表 Matt Dillon（<dillon@dragonflybsd.org> 邮箱 commit_count = 4222，first_commit_date = 2003-06-17T02:57:24Z，last_commit_date = 2008-11-13T02:23:53Z）；dragonfly.duckdb dragonfly-src 仓库 contributors 表 Jeffrey Hsu（first_commit_date = `2003-07-24T05:21:48Z`）；dragonfly.duckdb dragonfly-src 仓库 commits 表 LWKT 首引 commit `8ad65e080342`（2003-06-20T02:09:59Z） ［A］

**史观**：总纲第 10 条——动手者创造历史：Dillon 以 fork 公告与 LWKT 工程实现作为对质疑的回应，体现“动手者”以行动而非言论创造历史；总纲第 4 条——分离与聚合：Dillon 的工程论证将 fork 定位为技术路线分歧的必然分离而非个人冲突

**辨析**：考据过程留痕——【查证来源】fork 公告原文经 **lists.freebsd.org/pipermail/freebsd-current/2003-July/006889.html** 一手核验，逐句读取，“too heavily mutexed”与“faster to start with 4.x”表述确为 Dillon 原文；【关键考据发现·“logical continuation”表述溯源】DragonFly 官方 history 页面声称“the logical continuation of the FreeBSD 4.x series”出自 fork 公告（原文“as quoted in the announcement”），但经公告原文逐句核验，公告中并无此句——公告原文的表述是“take over development of the 4.x tree”。“logical continuation”这一表述可能源自 DragonFly 网站早期 Goals 页面或 OSNews 2003.7.17 报道的转述（OSNews 报道原文"designed to be the logical continuation of the FreeBSD-4.x OS series"），后被官方 history 页面误记为出自公告本身。这一考据发现是 0 信任原则的典型应用——即使是项目官方 history 页面对自身公告的引用，亦须经公告原文核验，不得因“官方自述”即直接采信；【0 信任原则·Dillon 自述的工程判断】“too heavily mutexed”是 Dillon 的主观工程判断，FreeBSD Core Team 与 SMPng 开发者可能持有不同判断，史家不得因 Dillon 一方陈述即采信 5.x“锁过重”的判定；【再回应的层次区分】Dillon 的再回应分言论层（fork 公告、ONLamp 采访、dragonfly.kernel 发言）与代码层（4222 条 commit），代码层再回应较言论层更具实质——dragonfly.duckdb 显示 LWKT 在 fork 后 2 天 19 小时即实现，反映 Dillon 以代码速度回应质疑；【“logical continuation”定位的放弃】Dillon 后期放弃“logical continuation of the FreeBSD 4.x series”的定位，DragonFly 官方 history 页面标注“this description has long since become obsolete”，反映 fork 后 DragonFly 逐渐建立独立技术身份，不再以 FreeBSD 4.x 延续者自居；【Hsu 转向的因果归属】Hsu 在 fork 公告后 8 天即首 commit，反映 fork 公告前已与 Dillon 达成合作意向，但 Hsu 转向的具体原因（技术分歧 vs 个人因素）dragonfly.duckdb 与公开邮件列表无直接证据；【社区支持者史料范围】OSNews 评论中支持 fork 的评论（18、24、27 等）多为匿名，支持者身份与专业背景无法确证，“fork 带来正向回报”的历史论证须以具体案例（如 OpenSSH）逐一考据而非笼统采信

### 219.7.5.3 再批评层——对反批评的再回应（2004-2010）

**要点**：批评方对 Dillon 反批评的再回应聚焦三个维度。其一，“logical continuation”表述的自我否定——Dillon 本人在 DragonFly 官方 history 页面承认“this description has long since become obsolete”，印证批评方对 fork 定位模糊性的质疑。其二，LWKT 路径的工程可行性——LWKT 与 token 机制学习曲线陡峭，业界未见主流采纳，DragonFly 在多核基准测试中未能持续保持对 FreeBSD 的性能优势；dragonfly.duckdb 显示 DragonFly 1.x 时代持续发布 8 个版本（1.0 至 1.12，2004-2008），LWKT、token、HAMMER 雏形、vkernel 等核心子系统均由 Dillon 一人首引并落地，证明 fork 路线在技术上可行，但 bus factor 极低（2003 年 top10 占 100.00%、2008 年 top10 占 91.56%），Dillon 个人占比从 53.13%（2003）降至 21.84%（2008）但仍居主导。其三，小社区可持续性——dragonfly.duckdb 显示 DragonFly 2024 年 commit 量仅 277 条，社区规模从 2005 年峰值 22 位贡献者至 2008 年 36 位贡献者，相对 FreeBSD 数百 committer 群体属少数派，与 OpenBSD fork 后建立安全细分市场形成对照。再批评并非全盘否定，而是承认 fork 的工程探索价值的同时指出其未能兑现 2003 年的工程承诺

**史料**：DragonFly 官方 history 页面“this description has long since become obsolete”自否弃声明（**dragonflybsd.org/history/**）；dragonfly.duckdb dragonfly-src 仓库 2024 年 commit 量 277 条；dragonfly.duckdb dragonfly-src bus factor 查询显示 2003 年 top10 占 100.00%（10 位贡献者）、2008 年 top10 占 91.56%（36 位贡献者），Dillon 个人占比 2003 年 53.13%、2008 年 21.84%；dragonfly.duckdb dragonfly-src 历史全时段 top10 贡献者统计显示 Dillon 两邮箱合计约 10,620 条 commit 为全时段第一；dragonfly.duckdb dragonfly-src 仓库 tags 表（1.0 至 1.12 版本序列）；DragonFly 1.0 公告"replaced nearly all of the core threading, process, interrupt, and network infrastructure"表述（**lists.dragonflybsd.org/pipermail/kernel/2004-July/212809.html**），1.0 仍依赖 FreeBSD ports tree 与 4.x pthreads 模型，“replaced nearly all”的自我陈述需对照 commit log 核验实际替换范围；DragonFly 官方 history 页面后期表述"From a performance perspective DragonFly’s only real competitor these days is Linux"反映定位从“4.x 延续”向“与 Linux 竞争”的漂移 ［A］

**史观**：总纲第 5 条——没有必然性，只有偶然性：再批评须警惕“fork 必然失败”的目的论叙事——DragonFly 社区规模萎缩是多种偶然因素（细分市场未建立、LWKT 未获主流采纳、Dillon 个人精力分配）的叠加，而非 fork 决策本身的必然结果；总纲第 8 条——本体论上各方平等：再批评不等于否定，LWKT 路径与 SMPng 路径在本体论上地位相等，前者未获主流采纳不等于后者“正确”

**辨析**：考据过程留痕——【查证来源】“this description has long since become obsolete”经 **dragonflybsd.org/history/** 一手核验，确为官方页面自述，但 0 信任原则提示：history 页面是动态的，可能存在事后修订，2003-2004 年原始页面内容须以互联网档案馆存档交叉验证；【“logical continuation”自否弃的时间点存疑】官方 history 页面未注明 Dillon 何时放弃“logical continuation”表述，dragonfly.duckdb commit message 亦未见明确的放弃声明 commit，自否弃的具体时间点无法确证 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］；【LWKT 性能对比的史料局限】LWKT 与 SMPng 的性能对比缺乏权威第三方基准，“DragonFly 未能持续保持性能优势”的判断须以同硬件同负载基准测试核验，本节不臆造具体性能数字；【1.x 时代双重面相的平衡】fork 路线的可行性（LWKT/token/HAMMER 落地）与可持续性风险（bus factor 极低、社区规模小）须并陈，不得偏废一方；【社区可持续性判断的界限】2024 年 commit 量 277 条反映开发活跃度下降，但不等于项目“失败”——DragonFly 至今仍持续发布版本，可持续性挑战与项目失败是两个不同判断，史家不得以 commit 量下降即推论“fork 失败”；【与 OpenBSD 比较的史观界限】OpenBSD 建立安全细分市场与 DragonFly 未建立明确细分市场的比较须严格区分——两者 fork 动机不同（人际冲突 vs 技术分歧），细分市场的建立与 fork 动机无直接因果，不得以 OpenBSD 的成功反推 DragonFly 的失败；【技术批评的时点局限】1.x 时代 LWKT/token 路径“过于实验性”的批评以 2003-2008 年部署规模为准，后续 DragonFly 持续维护 23 年证明路径可行但未成主流

### 219.7.5.4 合图层——项目史观总纲第 6 条与第 8 条审视

**要点**：辩证链的合图不是和解的实现，而是争议不可调和性的承认。项目史观总纲第 6 条“和解优于斗争”在此不是要求双方握手言和，而是提示史家：Dillon 与 FreeBSD Core Team 以分离取代对话，争议在分离中凝固为 BSD 阵营的永久结构性事实，这一凝固本身是和解的失败而非和解的达成；但分离后 2003-2007 年间 DragonFly 仍从 FreeBSD 回移代码，是“短暂的接纳”，至 2007 年 HAMMER 首引（commit `8750964d1997`）后回移停止，和解彻底断裂。总纲第 8 条“本体论上各方平等”在此要求：SMPng 路线与 LWKT 路线在本体论上地位相等，FreeBSD Core Team 的决议权与 Dillon 的项目创建权各自成立，差异仅是一刻状态的不同——SMPng 获得主流采纳不等于“正确”，LWKT 未获主流采纳不等于“错误”，二者皆是 BSD 哲学的不同一刻呈现。合图之下，争议的不可调和性源于工程判断的可通约性未能转化为实践妥协——SMPng 与 LWKT 在理论上可通约（二者皆追求 SMP 扩展性），但在工程实践中未能妥协（Dillon 选择 fork 而非在 FreeBSD 内部推进 LWKT）

**史料**：Dillon 2003.7.16 fork 公告（**lists.freebsd.org/pipermail/freebsd-current/2003-July/006889.html**）；DragonFly 官方 history 页面（**dragonflybsd.org/history/**）；freebsd.duckdb commits 表（Dillon freebsd-src 末次 commit `2003-01-28T18:44:40Z`、dragonfly-src 首 commit `2003-06-17T02:57:24Z`，间隔 140 天；2003-2007 年代码回移记录，2007 年 HAMMER 首引 commit `8750964d1997` 后回移停止）；项目史观总纲第 6 条“和解优于斗争。历史的动力不是对抗，而是各主体性的呈现与和解。和解是事物真正完整的一刻。”、第 8 条“本体论上各方平等。FreeBSD、OpenBSD、NetBSD、DragonFly BSD 在本体论上地位相等，差异仅是一刻状态的不同。” ［A］

**史观**：总纲第 6 条——和解优于斗争：本事件的合图是和解的失败——Dillon 与 Core Team 以分离取代对话，史家须诚实呈现这一失败，不得以“分离即和解”的叙事美化不可调和性；但分离后的代码回移是短暂的接纳，至 2007 年 HAMMER 首引后回移停止，和解彻底断裂；总纲第 8 条——本体论上各方平等：SMPng 路线与 LWKT 路线在本体论上地位相等，“主流采纳”与“非主流”是工程生态的偶然而非本体论的等级；总纲第 4 条——分离与聚合：DragonFly fork 是分离聚合律的具象——分离之初仍保留 FreeBSD 4.x 共享代码，聚合的惯性使二者无法立即完全独立，随时间推移共享代码减少，分离律最终主导

**辨析**：考据过程留痕——【合图的史观界限】本节合图承认争议的不可调和性，但不可调和性不等于“无对错”——工程判断的可通约性意味着双方在理论上有妥协空间，但实践中的 fork 选择使妥协未能发生，史家须如实区分“不可调和”与“未能调和”；【与 OpenBSD fork 合图的比较】OpenBSD fork 的不可调和性源于前理解差异（不可通约），DragonFly fork 的不可调和性源于工程判断分歧（可通约但未妥协）——前者是解释学循环的必然，后者是实践选择的偶然，史家不得将二者等同；【“短暂的接纳”的考据】2003-2007 年间 DragonFly 从 FreeBSD 回移代码的记录须以 dragonfly.duckdb dragonfly-src 仓库 merge commit 比例核验 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］，现有数据报告中 L7.1.1 系列未覆盖 dragonfly-src 仓库，故回移停止时间节点的精确判定须以 commits 表 parent_hashes 字段单独查询核验；【0 信任原则·合图的开放性】合图基于现有公开史料，若未来 FreeBSD Core Team 内部决议记录或 Dillon 未公开声明披露，可能改变合图的判定——合图不等于定论；【道德判断的警惕】合图层须警惕两种叙事陷阱——其一为“Dillon 正确、Core Team 保守”的个人英雄叙事，其二为“Core Team 正当、Dillon 分裂”的组织中心叙事，两种叙事均以道德判断取代史观审视；【史观应用的界限】项目史观总纲第 6、8 条是史观审视框架，非史实判定标准——“和解优于斗争”不意味着 fork 是“错误”，“本体论上各方平等”不意味着 SMPng 与 LWKT 路线“同样成功”（dragonfly.duckdb 显示 DragonFly 2024 年 commit 量仅 277 条，远低于 FreeBSD 主线，市场选择的结果差异是经验事实而非本体论判断）

> DragonFly 1.x 时代是“分离聚合律”的又一次重演——Dillon 从 FreeBSD 4.x 分裂出去，带着 LWKT 的设计走上一条独立的道路；LWKT 与 token 机制是 Dillon 对 FreeBSD 5.x SMPng“过度复杂化”的回应——他选择重新设计一个“轻量级”的形式主义结构，而非沿用 FreeBSD 的细粒度锁；然而 DragonFly 社区规模的持续萎缩让“轻量级内核”的理想成为一种会者定离的修行——Dillon 在不被理解中坚持自己的架构哲学；50.7 **网络栈 MPSAFE 演进（每 CPU 线程模型、IPI 消息传递）**——每 CPU 线程模型的设计：每个 CPU 拥有独立的网络栈线程；IPI（Inter-Processor Interrupt）消息传递替代传统锁的工程实现；与 FreeBSD 细粒度锁路径的对比：消息传递 vs 细粒度锁的哲学分歧；MPSAFE 网络栈对 DragonFly 多核扩展的影响：线性扩展性；消息传递模型的局限性：延迟、复杂度、调试困难；Dillon 为何选择消息传递而非锁：对 FreeBSD 5.x SMPng 的反思 ｜ **子-子节**：50.7.1 每 CPU 线程模型的设计与网络栈并行化；50.7.2 IPI 消息传递替代锁的工程实现；50.7.3 与 FreeBSD 细粒度锁路径的对比及哲学分歧；50.7.4 MPSAFE 网络栈对多核扩展的影响及消息传递模型的局限性；50.8 **DragonFly SMP 性能 benchmark 与 FreeBSD 对比**——DragonFly 声称 SMP 性能优于 FreeBSD 的 benchmark（2.x-3.x 时代）；benchmark 方法的争议：测试场景选择、硬件配置、测量指标；独立第三方测试结果：部分支持、部分质疑 DragonFly 的声称；SMP 性能叙事对 DragonFly 社区信心的影响：技术优越感的建立；后续 benchmark 的反转：FreeBSD 8.x/9.x 性能超越 DragonFly；性能叙事的演变：从“超越 FreeBSD”到“小而美”｜ **子-子节**：50.8.1 DragonFly 声称 SMP 性能优于 FreeBSD 的 benchmark；50.8.2 benchmark 方法的争议与独立第三方测试结果；50.8.3 SMP 性能叙事对 DragonFly 社区信心的影响；50.8.4 后续 benchmark 的反转及性能叙事的演变 | DragonFly 1.x 时代体现了项目统摄史观中“分离聚合律”与“形式主义化”的双重运作：从 FreeBSD 4.x 分离是分离聚合律的又一次重演，LWKT 与 token 的设计是形式主义化的工程实践——将“轻量级内核”的哲学固化为代码结构；Dillon 的个人主导模式则是“动手者”存在主义的体现
