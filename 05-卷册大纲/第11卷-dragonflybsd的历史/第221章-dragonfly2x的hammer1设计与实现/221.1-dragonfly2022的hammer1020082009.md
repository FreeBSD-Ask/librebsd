## 221.1.2 HAMMER 与 ZFS/UFS 的技术比较

**要点**：HAMMER 1.0 与 ZFS 均为写时复制文件系统，但设计哲学不同——HAMMER 轻量级、ZFS 功能丰富；HAMMER 与 UFS 均为 BSD 文件系统，但 HAMMER 支持快照与历史记录；HAMMER 在内存消耗与稳定性上优于 ZFS，但功能集较小。三者关键特性对照如下：

    | 维度 | HAMMER 1.0 | ZFS | UFS |
    |---|---|---|---|
    | 设计哲学 | 轻量级写时复制 | 功能丰富的企业级文件系统 | 传统 BSD 文件系统 |
    | 写时复制（CoW） | 是 | 是 | 否 |
    | 快照 | 是 | 是 | 否（需 mksnap_ffs 等外部工具） |
    | 历史记录 | 是 | 否（快照替代） | 否 |
    | 增量备份 | 是 | 是（send/receive） | 否 |
    | 多卷镜像 | 是 | 是（pool） | 否 |
    | 内存消耗 | 较低 | 较高（ARC 缓存） | 低 |
    | 稳定性 | 优（小规模） | 优（大规模） | 优（成熟） |
    | 功能集 | 较小 | 丰富 | 基础 |
    | 主导设计者 | Matt Dillon（个人） | Sun Microsystems（企业团队） | CSRG/McKusick 等 |
**史料**：HAMMER 设计文档（Dillon 2008 完整设计 PDF **<https://www.dragonflybsd.org/hammer/hammer.pdf**，B+Tree> 索引与 UNDO/REDO 日志设计）；ZFS 设计文档（Bonwick 2005 USENIX FAST 论文）；UFS 设计文档（McKusick UFS 设计文献）；三者功能对比基准测试；dragonfly.duckdb dragonfly-src 仓库 commits 表与 commit_files 表（路径 `d:\librebsd\03-原始史料库\01-代码仓库史料\01-数据库本体\`，含 HAMMER 首引 commit `8750964d1997` 2007-10-10、sys/vfs/hammer* 路径 2008 年 1,213 条 commit）；HAMMER2 设计文档（**<https://gitweb.dragonflybsd.org/dragonfly.git/blob/HEAD:/sys/vfs/hammer2/DESIGN**）；DragonFly> BSD 邮件列表存档（**<https://www.dragonflybsd.org/mailinglists/**）；DragonFly> BSD Release Notes（**<https://www.dragonflybsd.org/releases/**，2.0> HAMMER 默认切换）；Dillon fork 公告（**<https://lists.freebsd.org/pipermail/freebsd-current/2003-July/006889.html**）[三角验证：dragonfly.duckdb> + 邮件列表 + Release Notes] ［A］

**史观**：总纲第 4 条——分离聚合是永恒规律（原“技术路线分化”系伪名目，按论旨改挂）：HAMMER、ZFS、UFS 三种文件系统反映不同技术路线分化

**辨析**：三者性能对比缺乏权威基准——需对照同硬件同负载核验；HAMMER 的实际稳定性需考据

## 221.1.5 批评层——对 HAMMER 文件系统设计的三重质疑（2008-2010）

**要点**：DragonFly 2.0（**2008-07-21**）发布 HAMMER 1.0 文件系统后，其设计面临三类外部批评。其一，“与 ZFS 对比功能不足” 批评——ZFS 由 Sun Microsystems 企业团队开发（OpenSolaris 2005 年开源 ZFS、FreeBSD 7.0 引入 ZFS、8.x 完善 ZFS 集成），支持 `send`/`receive` 增量流式传输、`pool` 存储池管理、ARC 自适应替换缓存、数据去重、RAID-Z 等企业级特性；HAMMER 1.0 虽支持快照、历史记录、增量备份、多卷镜像，但功能集较小，缺少上述部分特性，难以满足企业级存储需求。其二，“社区规模过小难以维护复杂文件系统” 批评——dragonfly.duckdb dragonfly-src 仓库 contributors 表显示 2008 年 36 位贡献者（top10 占 91.56%）、2009 年 36 位贡献者（top10 占 86.93%）；复杂文件系统（如 ZFS）需企业级团队持续投入，DragonFly 社区规模难以支撑复杂文件系统的长期维护。其三，“Matt Dillon 单人开发风险” 批评——dragonfly.duckdb 显示 HAMMER 设计主要由 Dillon 个人完成（HAMMER 首引 commit `8750964d1997` 由 Dillon 于 2007-10-10 提交），巴士因子极低，Dillon 个人风险即项目风险，与 FreeBSD UFS 由 McKusick 及多位 committer 共同维护、OpenBSD FFS 由 de Raadt 与多位开发者审计的多元维护形成对照

**史料**：DragonFly 2.0 release notes（HAMMER 1.0 功能集）；FreeBSD 7.0/8.0 release notes（ZFS 集成与功能集）；OpenSolaris ZFS 设计文档（Bonwick 2005 年 ZFS 论文）；dragonfly.duckdb dragonfly-src 仓库 contributors 表（2008 年 36 位贡献者 top10 占 91.56%、2009 年 36 位贡献者 top10 占 86.93%）；dragonfly.duckdb dragonfly-src 仓库 commits 表（HAMMER 首引 commit `8750964d1997` 由 Dillon 提交）；20260724_dillon-governance-model.md（Dillon 合并 10666 条 commit）；20260724_external-critics-dragonfly.md（外部批评考据） ［A］

**史观**：总纲第 8 条——本体论上各方平等：HAMMER、ZFS、UFS 三种文件系统在本体论上地位相等，“功能集” 与 “社区规模” 的差异是经验事实而非本体论等级；专题语（不设总纲条号）——工程组织的演进（原挂总纲第 17 条系伪名目，删条号）：HAMMER 1.0 作为 “轻量级写时复制” 哲学的工程实现，其设计选择背后是 DragonFly 社区的工程约束

**辨析**：考据过程留痕——【查证来源】HAMMER 1.0 功能集经 DragonFly 2.0 release notes 一手核验，ZFS 功能集经 FreeBSD 7.0/8.0 release notes 与 OpenSolaris ZFS 设计文档核验；dragonfly.duckdb dragonfly-src 仓库 contributors 表的 bus factor 数据（2008 年 top10 占 91.56%）以 author_email 字段按年去重统计，author_email 字段可由提交者任意填写，须与 committer 字段交叉验证；【交叉验证方法】HAMMER 与 ZFS 的功能对比以各项目官方文档为依据，但 “功能不足” 的判断须结合具体使用场景——HAMMER 的快照与历史记录功能在轻量级场景下足够，ZFS 的 `send`/`receive` 与 `pool` 管理在企业级场景下必要，二者目标场景不同；【0 信任原则·Dillon 自述考据】Dillon 在 HAMMER 设计文档中关于 “轻量级写时复制” 的表述属当事人自辩，HAMMER 的实际内存消耗与稳定性须以独立第三方 benchmark 交叉验证；【存疑判定依据】HAMMER 1.0 在 2.x 周期的实际部署规模无权威统计，dragonfly.duckdb 显示 2.x 周期 HAMMER 相关 commit 以功能完善为主而非安全修复，但部署规模有限可能导致漏洞未充分暴露 ［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

## 221.1.6 反批评层——Dillon 与 DragonFly 阵营对 HAMMER 设计批评的反批评（2008-2010）

**要点**：Dillon 与 DragonFly 阵营对 HAMMER 设计批评的反批评以工程哲学与架构一致性为核心。第一层是 HAMMER 设计简洁优于 ZFS 复杂性——Dillon HAMMER 设计文档 v1（**2008-06-21**）阐述 “轻量级写时复制” 哲学，HAMMER 的 B-tree 写时复制设计避免了 ZFS 的 ARC 自适应替换缓存的高内存消耗（ZFS 推荐至少 1GB 内存用于 ARC），HAMMER 在内存消耗上优于 ZFS；DragonFly 官方 history 页面称 HAMMER “designed to solve numerous issues and to add many new capabilities to DragonFly, such as fine-grained history retention (snapshots), instant crash recovery, and near real-time mirroring”。第二层是小社区有敏捷优势——dragonfly.duckdb 显示 DragonFly 决策链短，Dillon 可直接推进 HAMMER 设计迭代，2.0（**2008-07-21**）发布 HAMMER 1.0 后至 2.2（**2009-04-26**）release notes 称 “HAMMER is now considered production-capable”，9 个月即达生产级；对比 ZFS 从 2001 年 Sun 内部开发至 2005 年 OpenSolaris 开源历经 4 年。第三层是 Dillon 的工程能力足以支撑——dragonfly.duckdb 显示 Dillon 合并 10666 条 commit（据 20260724_dillon-governance-model.md），主导 LWKT（首引 commit `8ad65e080342`）、token 机制、HAMMER（首引 commit `8750964d1997`）、HAMMER2（首引 commit `703720e4d599`）、vkernel（早期铺垫 commit `39619464950a`〔系机器架构目录重组，非 vkernel 字样首引，原“首引”依据不足已改称〕）等核心创新，其个人工程能力与长期投入是 DragonFly 持续运行的根本

## 221.1.8 合图层——项目史观总纲第 6 条与第 8 条审视（2008-2010）

## 221.1.9 项目统摄史观审视——总纲第 13、19、21 条切入（2008-2010）

**要点**：以项目史观总纲第 13 条 “法律与道德是利益分配”、第 19 条 “解释学循环是历史认识的根本条件”、第 21 条 “革命与改革是历史方法论的分歧” 审视 HAMMER 文件系统设计争议，可见争议的更深维度。**总纲第 13 条审视**：HAMMER 与 ZFS 的设计争议背后是许可证哲学与利益分配的差异——HAMMER 采用 BSD 许可证（与 DragonFly 整体许可证一致），ZFS 采用 CDDL（Common Development and Distribution License，Sun Microsystems 制定的 Mozilla Public License 衍生许可证），二者许可证哲学不同：BSD 许可证允许闭源衍生与商业整合，CDDL 要求衍生作品以 CDDL 开源；FreeBSD 8.x 集成 ZFS 须处理 CDDL 与 BSD 许可证的兼容性（CDDL 与 GPL 不兼容，但与 BSD 许可证在文件级可共存），DragonFly 自研 HAMMER 避免了许可证兼容性问题——HAMMER 的 BSD 许可证让 DragonFly 在文件系统层保持许可证纯洁性，这一选择背后是 DragonFly 社区对 “许可证纯洁性” 利益的分配。**总纲第 19 条审视**：HAMMER 与 ZFS 的比较不可避免地带有前理解的差异——ZFS 使用者以 “功能丰富” 为前理解审视 HAMMER，自然得出 “功能不足” 的判断；HAMMER 使用者以 “轻量级” 为前理解审视 ZFS，自然得出 “过度复杂” 的判断，前理解的差异使分歧不可避免；权力与知识在 HAMMER 设计争议的书写中共谋——主流技术媒体（Phoronix、OSNews 等）对 ZFS 的报道远多于 HAMMER，ZFS 作为 “主流文件系统设计” 被记录，HAMMER 作为 “非主流” 被边缘化，什么被记录、什么被遗忘，本身就是权力行使。**总纲第 21 条审视**：HAMMER 与 ZFS 的设计路径是 “革命与改革” 方法论分歧的体现——ZFS 是 Sun Microsystems 的 “革命” 路径，重写文件系统设计（从传统 inode 到对象存储模型、从 fsck 到 self-healing、从固定块到 variable-sized blocks），破除传统文件系统的设计约束；HAMMER 是 Dillon 的 “改革” 路径，在 BSD 文件系统传统（UFS/FFS 血缘）内推进写时复制与 B-tree 设计，保留传统文件系统的概念框架同时引入新特性；项目史观总纲第 21 条言 “Linux 靠革命，BSD 靠改革。改革的困难远高于革命。破山中贼易，破心中贼难。”——HAMMER 作为改革路径，须在传统框架内推进创新，困难高于 ZFS 的革命路径；但革命路径亦有其代价——ZFS 的复杂性（ARC 缓存、pool 管理、CDDL 许可证）是革命路径的代价，HAMMER 的功能集较小是改革路径的代价

**要点**：

- 节目介绍在 DragonFly BSD 上以 LUKS 兼容加密层对磁盘加密后搭建 HAMMER 主从文件系统，展示 HAMMER 作为可跨多台机器的分布式文件系统的特性，并提示 LUKS 提供的安全性与同步复制取舍。（BSD Now EP251，[66.84-354.00]，L2）
- Intel FPU 推测执行漏洞被确认：OpenBSD 的 Philip Guenther 于 7 月 5 日提交从惰性切换到主动切换的变更，Colin Percival 根据 Theo de Raadt 演讲披露的信息约五小时写出概念验证并通知 Intel，促使 Intel 提前公布；FreeBSD 2015 年 3 月的邮件列表曾有人建议为性能做同样变更。（BSD Now EP251，[3176.16-3380.00]，L1）
- BSDCan 2018 复盘记录 Ben O'Rice 的 systemd 悲剧主题演讲，他主张不应仅因批评就否定 systemd 的合理意图，BSD 社区可吸收其优点而不必照搬；并记录 Kirk McKusick 的 FreeBSD 治理演进演讲，回顾核心团队每两年改选、从 Jordan 时代到 Watson 时代再到当代的交替。（BSD Now EP251，[831.08-2315.32]，L1）
- 节目考据多个 Unix 命令名词源：awk 取自 Aho、Weinberger、Kernighan 姓氏首字母；grep 源自 ed 的 g/re/p（全局正则表达式打印）；cat 是 concatenate 的缩写；GECOS 字段源自 Honeywell 的 General Electric Comprehensive Operating Supervisor；rc 可追溯至 1965 年 MIT CTSS 的 runcom。（BSD Now EP251，[3944.18-4195.44]，L2）
- 发布轨迹与设计动机：DragonFly 2.0 原定 2007 年末至 2008 年 1 月发布，因 HAMMER 远未就绪而再滚 1.12 版并推迟至 7 月中旬；Dillon 认为 UFS 十五至二十年间叠 additions（如前端目录缓存）皆属权宜修补，未触及根本缺陷——重启需 fsck、inode 数量受 fsck 内存需求限制；HAMMER 据此以近即时挂载与无 fsck 为第一目标。（BSDTalk EP154，[92.04-295.34]，L1）
- 在线历史保留重构备份与审计：文件系统每 30 秒同步落盘即留存完整历史，经目录的 as-of 事务 ID 扩展即可访问任意时点的整文件系统快照，快照稳定（同一快照多日后 tar 加 MD5 校验一致）可作审计依据；相比硬链接复制式每日增量备份在两千万 inode 规模下的空间浪费，HAMMER 以快照软链接加 prune 清理即可在本地或异地备份机上管理任意久远的备份，且保留最近快照至当前的 30 秒粒度。（BSDTalk EP154，[295.34-574.70]，L1）
- 架构与镜像能力：HAMMER 以单一 B-tree 索引 inode、目录项与文件块，extent 型设计单元素可达 2GB，首版以 16K 与 64K 固定块实现，在廉价 RAID 上已近盘速，inode 全动态分配无上限；镜像采用非队列设计——将事务 ID 传播至 B-tree 根，镜像代码仅扫描已变节点即可序列化变更流，与前端操作解耦，可指向互联网目标、不可靠连接、流式或批量、多目标不同进度， Dillon 明确拒绝 Oracle 式队列复制在文件系统层的做法；配套 reblocker 可在线重分配全部媒体结构以弥补首版分配器不局部化数据的缺陷。（BSDTalk EP154，[574.70-854.50]，L1）
- 寻址与结构演化策略：一切基于 64 位偏移（字节粒度），后端最多 256 卷，64 位空间以 4 位元数据类型与 8 位卷号划分后单文件系统可寻址约 1 EB；发布前完成硬改动（如为每个 8 MB large block 设独立追加索引）以支持发布后的局部化分配演进，宁可要求用户重新格式化也不留待发布后，目标是跨大版本保持向后兼容。（BSDTalk EP154，[765.07-1058.22]，L1）
- 完整性哲学与集群愿景：HAMMER 对一切结构做非递归 CRC（节点校验和存于自身以保性能），采用 32 位 CRC 只负责报告损坏，Dillon 不认为校验和可像 ZFS 的 128 位哈希那样用于恢复；B-tree 键中的 32 位 localization 字段高 16 位作伪文件系统选择器，单棵全局 B-tree 支持至多 65536 个伪文件系统，各自独立 reblock 且拥有独立 inode 编号空间，镜像时可连同 inode 号得到精确副本，为未来多主集群预留。（BSDTalk EP154，[1068.04-1257.26]，L1）
- 信任建立与运维图景：面对 UFS 的历史信任，HAMMER 的策略是让管理员可运行程序断言文件系统未损坏——从事务 ID 零做全盘序列化镜像流扫描，无 CRC 错误即近乎保证干净，这是其赢得社区尊重、积累可靠性历史的路径；可增长与收缩依赖 free map 稀疏映射配合 reblocker 搬迁数据，首版未开放但媒体结构已预留；首版不可启动，newfs 预留线性空间供引导程序取内核；作者实测最大约 2 TB，大卷格式化仅需数秒；RAID 不入文件系统，由下层软件或硬件层承担。（BSDTalk EP154，[1437.00-1560.92]，L1）
- DragonFly BSD Digest 的起源由当事人自述：2003 年 Matt Dillon 自 FreeBSD 4 分叉出 DragonFly 时他注意到项目启动，想贡献却不愿以写 C 为业，而 BSD 项目几乎所有互动都在邮件列表上进行，遂决定做一份摘编网站替人筛选要闻；他先默默试运行约一周确认能坚持，再公开宣布，至访谈时已持续约五年。（BSDTalk EP169，[91.60-158.72]，L1）
