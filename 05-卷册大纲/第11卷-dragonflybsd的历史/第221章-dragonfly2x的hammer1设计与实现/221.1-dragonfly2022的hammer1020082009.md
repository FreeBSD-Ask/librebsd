## 220.1.2 HAMMER 与 ZFS/UFS 的技术比较
  - 要点：HAMMER 1.0 与 ZFS 均为写时复制文件系统，但设计哲学不同——HAMMER 轻量级、ZFS 功能丰富；HAMMER 与 UFS 均为 BSD 文件系统，但 HAMMER 支持快照与历史记录；HAMMER 在内存消耗与稳定性上优于 ZFS，但功能集较小。三者关键特性对照如下：

    | 维度 | HAMMER 1.0 | ZFS | UFS |
    |---|---|---|---|
    | 设计哲学 | 轻量级写时复制 | 功能丰富的企业级文件系统 | 传统 BSD 文件系统 |
    | 写时复制（CoW） | 是 | 是 | 否 |
    | 快照 | 是 | 是 | 否（需 mksnap_ffs 等外部工具） |
    | 历史记录 | 是 | 否（快照替代） | 否 |
    | 增量备份 | 是 | 是（send/receive） | 否 |
    | 多卷镜像 | 是 | 是（pool） | 否 |
    | 内存消耗 | 较低 | 较高（ARC 缓存） | 低 |
    | 稳定性 | 优（小规模） | 优（大规模） | 优（成熟） |
    | 功能集 | 较小 | 丰富 | 基础 |
    | 主导设计者 | Matt Dillon（个人） | Sun Microsystems（企业团队） | CSRG/McKusick 等 |

  - 史料：HAMMER 设计文档（Dillon 2008 完整设计 PDF **https://www.dragonflybsd.org/hammer/hammer.pdf**，B+Tree 索引与 UNDO/REDO 日志设计）；ZFS 设计文档（Bonwick 2005 USENIX FAST 论文）；UFS 设计文档（McKusick UFS 设计文献）；三者功能对比基准测试；bsd_commits.db dragonfly-src 仓库 commits 表与 commit_files 表（路径 `d:\librebsd\03-原始史料库\01-代码仓库史料\01-数据库本体\`，含 HAMMER 首引 commit `8750964d1997` 2007-10-10、sys/vfs/hammer* 路径 2008 年 1,213 条 commit）；HAMMER2 设计文档（**https://gitweb.dragonflybsd.org/dragonfly.git/blob/HEAD:/sys/vfs/hammer2/DESIGN**）；DragonFly BSD 邮件列表存档（**https://www.dragonflybsd.org/mailinglists/**）；DragonFly BSD Release Notes（**https://www.dragonflybsd.org/releases/**，2.0 HAMMER 默认切换）；Dillon fork 公告（**https://lists.freebsd.org/pipermail/freebsd-current/2003-July/006889.html**）[三角验证：bsd_commits.db + 邮件列表 + Release Notes] ［A］
  - 史观：总纲第 6 条——技术路线分化：HAMMER、ZFS、UFS 三种文件系统反映不同技术路线分化
  - 辨析：三者性能对比缺乏权威基准——需对照同硬件同负载核验；HAMMER 的实际稳定性需考据

## 220.1.5 批评层——对 HAMMER 文件系统设计的三重质疑（2008-2010）
  - 要点：DragonFly 2.0（**2008-07-21**）发布 HAMMER 1.0 文件系统后，其设计面临三类外部批评。其一，“与 ZFS 对比功能不足” 批评——ZFS 由 Sun Microsystems 企业团队开发（OpenSolaris 2005 年开源 ZFS、FreeBSD 7.0 引入 ZFS、8.x 完善 ZFS 集成），支持 `send`/`receive` 增量流式传输、`pool` 存储池管理、ARC 自适应替换缓存、数据去重、RAID-Z 等企业级特性；HAMMER 1.0 虽支持快照、历史记录、增量备份、多卷镜像，但功能集较小，缺少上述部分特性，难以满足企业级存储需求。其二，“社区规模过小难以维护复杂文件系统” 批评——bsd_commits.db dragonfly-src 仓库 contributors 表显示 2008 年 36 位贡献者（top10 占 91.56%）、2009 年 36 位贡献者（top10 占 86.93%）；复杂文件系统（如 ZFS）需企业级团队持续投入，DragonFly 社区规模难以支撑复杂文件系统的长期维护。其三，“Matt Dillon 单人开发风险” 批评——bsd_commits.db 显示 HAMMER 设计主要由 Dillon 个人完成（HAMMER 首引 commit `8750964d1997` 由 Dillon 于 2007-10-10 提交），巴士因子极低，Dillon 个人风险即项目风险，与 FreeBSD UFS 由 McKusick 及多位 committer 共同维护、OpenBSD FFS 由 de Raadt 与多位开发者审计的多元维护形成对照
  - 史料：DragonFly 2.0 release notes（HAMMER 1.0 功能集）；FreeBSD 7.0/8.0 release notes（ZFS 集成与功能集）；OpenSolaris ZFS 设计文档（Bonwick 2005 年 ZFS 论文）；bsd_commits.db dragonfly-src 仓库 contributors 表（2008 年 36 位贡献者 top10 占 91.56%、2009 年 36 位贡献者 top10 占 86.93%）；bsd_commits.db dragonfly-src 仓库 commits 表（HAMMER 首引 commit `8750964d1997` 由 Dillon 提交）；20260724_dillon-governance-model.md（Dillon 合并 10666 条 commit）；20260724_external-critics-dragonfly.md（外部批评考据） ［A］
  - 史观：总纲第 8 条——本体论上各方平等：HAMMER、ZFS、UFS 三种文件系统在本体论上地位相等，“功能集” 与 “社区规模” 的差异是经验事实而非本体论等级；总纲第 17 条——软件工程：HAMMER 1.0 作为 “轻量级写时复制” 哲学的工程实现，其设计选择背后是 DragonFly 社区的工程约束
  - 辨析：考据过程留痕——【查证来源】HAMMER 1.0 功能集经 DragonFly 2.0 release notes 一手核验，ZFS 功能集经 FreeBSD 7.0/8.0 release notes 与 OpenSolaris ZFS 设计文档核验；dragonfly.db dragonfly-src 仓库 contributors 表的 bus factor 数据（2008 年 top10 占 91.56%）以 author_email 字段按年去重统计，author_email 字段可由提交者任意填写，须与 committer 字段交叉验证；【交叉验证方法】HAMMER 与 ZFS 的功能对比以各项目官方文档为依据，但 “功能不足” 的判断须结合具体使用场景——HAMMER 的快照与历史记录功能在轻量级场景下足够，ZFS 的 `send`/`receive` 与 `pool` 管理在企业级场景下必要，二者目标场景不同；【0 信任原则·Dillon 自述考据】Dillon 在 HAMMER 设计文档中关于 “轻量级写时复制” 的表述属当事人自辩，HAMMER 的实际内存消耗与稳定性须以独立第三方 benchmark 交叉验证；【存疑判定依据】HAMMER 1.0 在 2.x 周期的实际部署规模无权威统计，dragonfly.db 显示 2.x 周期 HAMMER 相关 commit 以功能完善为主而非安全修复，但部署规模有限可能导致漏洞未充分暴露 [考据完成：2026-07-28 HAMMER 1.0 在 2.x 周期无 CVE 可能因部署规模而非设计优越性]

## 220.1.6 反批评层——Dillon 与 DragonFly 阵营对 HAMMER 设计批评的反批评（2008-2010）
  - 要点：Dillon 与 DragonFly 阵营对 HAMMER 设计批评的反批评以工程哲学与架构一致性为核心。第一层是 HAMMER 设计简洁优于 ZFS 复杂性——Dillon HAMMER 设计文档 v1（**2008-06-21**）阐述 “轻量级写时复制” 哲学，HAMMER 的 B-tree 写时复制设计避免了 ZFS 的 ARC 自适应替换缓存的高内存消耗（ZFS 推荐至少 1GB 内存用于 ARC），HAMMER 在内存消耗上优于 ZFS；DragonFly 官方 history 页面称 HAMMER “designed to solve numerous issues and to add many new capabilities to DragonFly, such as fine-grained history retention (snapshots), instant crash recovery, and near real-time mirroring”。第二层是小社区有敏捷优势——bsd_commits.db 显示 DragonFly 决策链短，Dillon 可直接推进 HAMMER 设计迭代，2.0（**2008-07-21**）发布 HAMMER 1.0 后至 2.2（**2009-04-26**）release notes 称 “HAMMER is now considered production-capable”，9 个月即达生产级；对比 ZFS 从 2001 年 Sun 内部开发至 2005 年 OpenSolaris 开源历经 4 年。第三层是 Dillon 的工程能力足以支撑——bsd_commits.db 显示 Dillon 合并 10666 条 commit（据 20260724_dillon-governance-model.md），主导 LWKT（首引 commit `8ad65e080342`）、token 机制、HAMMER（首引 commit `8750964d1997`）、HAMMER2（首引 commit `703720e4d599`）、vkernel（首引 commit `39619464950a`）等核心创新，其个人工程能力与长期投入是 DragonFly 持续运行的根本

## 220.1.8 合图层——项目史观总纲第 6 条与第 8 条审视（2008-2010）
  - 要点：HAMMER 文件系统设计争议的合图不是和解的实现，而是争议不可调和性的承认与各主体性的并存。项目史观总纲第 6 条 “和解优于斗争” 在此审视：HAMMER 设计争议的不可调和性源于工程判断的可通约性未能转化为实践妥协——HAMMER 的 “轻量级写时复制” 与 ZFS 的 “功能丰富企业级” 在理论上可通约（二者皆追求文件系统稳定性与数据完整性），但在工程实践中二者的目标场景不同（HAMMER 适合轻量级场景、ZFS 适合企业级场景），妥协不可能在单一文件系统设计中同时满足二者；bsd_commits.db 显示 HAMMER 路径 commit 在 2008 年激增至 1,213 条（工程爆发）、2009 年回落至 282 条（维护期），这一非线性分布反映 HAMMER 设计的工程投入集中在发布前一年，争议的不可调和性在工程节奏中显现——HAMMER 既未能如 ZFS 般持续获得企业级团队投入，亦未能如 UFS 般借助数十年部署历史积累成熟度。总纲第 8 条 “本体论上各方平等” 在此要求：HAMMER、ZFS、UFS 三种文件系统在本体论上地位相等，差异仅是一刻状态的不同——HAMMER 的 “轻量级创新” 与 ZFS 的 “企业级丰富” 在本体论上无高下之分，“主流采纳” 与 “非主流” 是工程生态的偶然而非本体论的等级；Dillon 的 “轻量级设计” 与 Sun 团队的 “企业级设计” 在本体论上亦平等，二者皆是主体性的表达方式

## 220.1.9 项目统摄史观审视——总纲第 13、19、21 条切入（2008-2010）
  - 要点：以项目史观总纲第 13 条 “法律与道德是利益分配”、第 19 条 “解释学循环是历史认识的根本条件”、第 21 条 “革命与改革是历史方法论的分歧” 审视 HAMMER 文件系统设计争议，可见争议的更深维度。**总纲第 13 条审视**：HAMMER 与 ZFS 的设计争议背后是许可证哲学与利益分配的差异——HAMMER 采用 BSD 许可证（与 DragonFly 整体许可证一致），ZFS 采用 CDDL（Common Development and Distribution License，Sun Microsystems 制定的 Mozilla Public License 衍生许可证），二者许可证哲学不同：BSD 许可证允许闭源衍生与商业整合，CDDL 要求衍生作品以 CDDL 开源；FreeBSD 8.x 集成 ZFS 须处理 CDDL 与 BSD 许可证的兼容性（CDDL 与 GPL 不兼容，但与 BSD 许可证在文件级可共存），DragonFly 自研 HAMMER 避免了许可证兼容性问题——HAMMER 的 BSD 许可证让 DragonFly 在文件系统层保持许可证纯洁性，这一选择背后是 DragonFly 社区对 “许可证纯洁性” 利益的分配。**总纲第 19 条审视**：HAMMER 与 ZFS 的比较不可避免地带有前理解的差异——ZFS 使用者以 “功能丰富” 为前理解审视 HAMMER，自然得出 “功能不足” 的判断；HAMMER 使用者以 “轻量级” 为前理解审视 ZFS，自然得出 “过度复杂” 的判断，前理解的差异使分歧不可避免；权力与知识在 HAMMER 设计争议的书写中共谋——主流技术媒体（Phoronix、OSNews 等）对 ZFS 的报道远多于 HAMMER，ZFS 作为 “主流文件系统设计” 被记录，HAMMER 作为 “非主流” 被边缘化，什么被记录、什么被遗忘，本身就是权力行使。**总纲第 21 条审视**：HAMMER 与 ZFS 的设计路径是 “革命与改革” 方法论分歧的体现——ZFS 是 Sun Microsystems 的 “革命” 路径，重写文件系统设计（从传统 inode 到对象存储模型、从 fsck 到 self-healing、从固定块到 variable-sized blocks），破除传统文件系统的设计约束；HAMMER 是 Dillon 的 “改革” 路径，在 BSD 文件系统传统（UFS/FFS 血缘）内推进写时复制与 B-tree 设计，保留传统文件系统的概念框架同时引入新特性；项目史观总纲第 21 条言 “Linux 靠革命，BSD 靠改革。改革的困难远高于革命。破山中贼易，破心中贼难。”——HAMMER 作为改革路径，须在传统框架内推进创新，困难高于 ZFS 的革命路径；但革命路径亦有其代价——ZFS 的复杂性（ARC 缓存、pool 管理、CDDL 许可证）是革命路径的代价，HAMMER 的功能集较小是改革路径的代价
