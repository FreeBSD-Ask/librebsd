# 215.3 HAMMER 文件系统——DragonFly 自研的 B-tree 写时复制文件系统，与 ZFS 形成对照

## 214.3.1 HAMMER 的 B-tree 写时复制设计

**要点**：HAMMER 文件系统采用 B-tree 结构与写时复制（COW）设计，支持快照、历史记录与数据完整性。bsd_commits.db 显示 HAMMER 首引 commit 为 `8750964d1997`（author_date = 2007-10-10T19:37:25Z，Dillon 提交），位于 sys/vfs/hammer/ 目录。其设计目标是在简洁性与功能性之间取得平衡，对比 ZFS 的池化设计与 256MB ARC 最小内存要求，HAMMER 仅需 64MB 内存即可运行

**史料**：Dillon HAMMER 设计文档（dragonflybsd.org/docs/hammer/）；DragonFly 源码 sys/vfs/hammer/ 目录（bsd_commits.db commit_files 表 status ='A' 首引 commit = 8750964d1997，2007-10-10）；DragonFly mailing list 讨论（lists.dragonflybsd.org，2007-2008 年 HAMMER 开发期）〔L1 代码/构建产物/L2 即时通讯记录/L3 官方文档与公告〕

**史观**：总纲第 17 条——软件工程：HAMMER 的 B-tree + COW 设计在工程上选择 “简洁优先”——64MB 内存最低要求 vs ZFS 256MB ARC，单节点设计 vs ZFS 池化设计，反映 DragonFly 在资源受限场景下的工程取舍；bsd_commits.db 显示 HAMMER 由 Dillon 一人首引（commit 8750964d1997），符合 DragonFly “个人主导核心子系统” 的工程文化

**辨析**：HAMMER 与 ZFS 的优劣比较须基于具体工作负载——HAMMER 在单节点、低内存场景下优于 ZFS；ZFS 在多盘池化、高内存场景下优于 HAMMER。bsd_commits.db 显示 HAMMER 首引（2007-10-10）晚于 ZFS 在 FreeBSD 的引入（FreeBSD 7.0-RELEASE，2008-02-27），但 HAMMER 设计独立于 ZFS，并非对 ZFS 的简化复制

**文献**：Dillon M. HAMMER File System Design [EB/OL]. 2007. dragonflybsd.org/docs/hammer/；Bonwick J. ZFS: The Last Word in File Systems [C]. USENIX FAST, 2005；bsd_commits.db dragonfly-src 仓库 commit_files 表（HAMMER 首引 commit 8750964d1997, 2007-10-10） ［B］

## 214.3.3 HAMMER 与 ZFS 及 UFS 的技术比较

**要点**：HAMMER 在功能上介于 UFS 与 ZFS 之间——提供快照与历史记录（B-tree + COW）但无 ZFS 的池化与去重；单节点设计 vs ZFS 池化设计，更适合 DragonFly 的小规模部署。bsd_commits.db 显示 HAMMER 首引（2007-10-10）早于 OpenZFS 移植至 FreeBSD（FreeBSD 13.0-RELEASE 默认 OpenZFS，2021-04-13），反映两项目文件系统路线分化

**史料**：freebsd.db dragonfly-src 仓库 commits 表 HAMMER 首引 = 2007-10-10；freebsd.db freebsd-src 仓库 commits 表 OpenZFS 移植 commit（FreeBSD 13.0-RELEASE 2021-04-13）；HAMMER 与 ZFS 技术对比文档（DragonFly wiki）；DragonFly 与 FreeBSD 性能测试报告（Phoronix 2008-2015 年基准测试）〔L1 代码/构建产物/L3 官方文档与公告/L5 二手研究〕

**史观**：总纲第 6 条——技术路线分化：HAMMER 与 ZFS 代表不同的文件系统路线——HAMMER 选择 “单节点 + B-tree + COW + 低内存” 路线，ZFS 选择 “池化 + ARC + 高内存” 路线，两条路线在 2007-2026 年间并行发展，bsd_commits.db 显示 HAMMER 由 Dillon 一人主导（首引 commit 8750964d1997），ZFS 由 Sun/Oracle 团队主导后经 OpenZFS 社区维护

**辨析**：性能比较结果因测试方法不同而差异显著——Phoronix 2008-2015 年基准测试显示 HAMMER 在单盘随机读场景下性能优于 ZFS（低内存优势），在多盘 RAID-Z 场景下 ZFS 优于 HAMMER（池化优势）；正式撰写时须引用具体测试配置（CPU、内存、磁盘、文件系统版本）

**文献**：Bonwick J. ZFS: The Last Word in File Systems [C]. USENIX FAST, 2005；Dillon M. HAMMER File System Design [EB/OL]. 2007. dragonflybsd.org/docs/hammer/；Phoronix. DragonFly BSD HAMMER Performance Benchmarks [EB/OL]. 2008-2015 ［B］

**要点**：

- 1.6 定位以修复为主，修复清单长达两三百条且以文件系统代码居多；基础设施层面完成缓冲缓存的 buffer 与 BIO 拆分（与 FreeBSD 约一年前的做法类似）、彻底废除块编号改用 64 位字节偏移，并将大内核锁显著推进，使多数文件描述符例程已可 MP safe 运行；另含新随机数生成器与 soft updates、NFS、浮点子系统、线程等大量修复。（BSDTalk EP53，[164.24-249.12]，L1）
- Dillon 列出三大目标：userland VFS（允许文件系统作为用户进程运行的 API）、ZFS 移植（依赖 userland VFS，直接移植进内核相当困难）与集群（他称之为最大的一盘棋）；并坦言创立 DragonFly 时未料到集群之前需完成如此大量的内核基础设施工作。（BSDTalk EP53，[293.5-348.74]，L1）
- 集群的正确含义远超 NFS：跨机共享打开文件须做到百分之百缓存一致性，因为单一线程化程序的线程可能分属两台物理机；为此需要类似 SMP 硬件缓存一致性协议的软件机制，把 BSD 传统上对写操作独占整个 v-node 的锁改为按文件的范围锁，由此牵出整条基础设施改造链。（BSDTalk EP53，[354.34-454.78]，L1）
- 部分机制已获实现验证：并行路由表工作正常，线程化网络栈运转良好（性能测试暂不理想，因 MP 锁尚未完全移除）；线程切换时间低于一微秒，进程间消息低于一微秒且可批处理——批模式下首条约一微秒、后续每条仅 10-15 纳秒；这些量化证明使内核能以更模块化、更可调试的方式编写。（BSDTalk EP53，[836.86-894.9]，L1）
- Dillon 自述内核设计立场：既不属于微内核阵营也不属于单整体阵营，支持模块化但承认大型基础设施必须单整体才能获得真实性能，稳定性也要求代码集成于一处——他以 Windows 由五万个厂商提供驱动、兼容性碰运气作反例，自认处于中间地带。（BSDTalk EP53，[895.9-962.0]，L1）
