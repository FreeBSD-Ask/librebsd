## 227.1.3 与 FreeBSD 11.x 技术进展的比较

**要点**：freebsd.duckdb 显示 2016-2018 年间两仓库 commit 量对照——2016 年 freebsd-src = 17362、dragonfly-src = 2340；2017 年 freebsd-src = 16157、dragonfly-src = 1888；2018 年 freebsd-src = 14985、dragonfly-src = 1709。FreeBSD 11.0（2016-10-10 发布）引入 arm64 支持、改进 bhyve、改进无线网络栈；DragonFly v4.2.0/v4.4.0（2015）在 GPU 与网络栈改进上有局部进展，但 dragonfly.duckdb 显示其 commit 量仅为 FreeBSD 同期 13.5%（2016）、11.7%（2017）、11.4%（2018），整体生态与硬件支持仍落后

**史料**：dragonfly.duckdb 查询 L1.1.1 显示：dragonfly-src 2015 年 commit 量 3,111 条（author_date 口径），2016 年 2,340 条，2017 年 1,888 条，2018 年 1,709 条（4.x 时代持续下降趋势）；FreeBSD 11.0 release notes；DragonFly 4.2/4.4 release notes

**史观**：总纲第 4 条——分离聚合是永恒规律〔存疑：伪标签“技术路线分化”按族例重映射暂挂，待总纲原文复核〕：dragonfly.duckdb 数据显示 FreeBSD 与 DragonFly 在硬件支持广度上的分化持续加深——FreeBSD 11.x 时期 arm64 支持、bhyve 改进均属 “扩展技术广度” 的投入，DragonFly 4.x 时期 GPU 与网络栈改进属 “深化既有特性” 的投入；commit 量差距（FreeBSD 是 DragonFly 的 7.4-8.8 倍）反映两个项目的工程动员能力差距

**辨析**：技术比较易被社区情感影响——DragonFly 支持者强调 LWKT 与 HAMMER 哲学优越性，FreeBSD 支持者强调生态与硬件支持，须结合 dragonfly.duckdb 客观数据辨析；FreeBSD 11.0 的 arm64 支持为 Tier-2（非 Tier-1），Tier-1 在 13.0 才引入；DragonFly 4.x 同期未进入 ARM 市场；【0 信任原则·commit 量不等于质量】dragonfly-src 2015-2018 年 commit 量持续下降（3111→2340→1888→1709）反映开发活跃度递减，但 HAMMER2 等核心子系统仍在持续改进，须结合 commit message 主题词辨析 [存疑脚注：FreeBSD 11.0 arm64 Tier-2 与 13.0 Tier-1 的分级须以 FreeBSD 官方平台文档核验，本轮考据未联网核验]。（校验前提：author 字段可伪造、tagger_date 偏差、关键词匹配局限等留考据记录备查，正文仅保留结论性辨析）

**要点**：

- Yahoo 起源故事的叙事链条由当事人书面自述构成：Stanford 时期的 SunOS 机器无法承受不断膨胀的 HTTP 请求，团队先后测试 IRIX、Linux 与 BSDi 均因性能与稳定性不佳而放弃，最终从网站下载软盘启动镜像安装 FreeBSD，数日内即有可用系统并加入 web 服务器集群，当事人自述“几周的实验之后，我们被说服了”（956.14-958.82），此后 FreeBSD 成为 Yahoo 生产与开发环境的专属平台。（BSD Now EP118，[787.20-998.66]，L2）
- Mark Heily 在访谈中自述 relaunchd 的动机与路线：受 Jordan Hubbard 等人 NextBSD 计划将 launchd 引入开源世界的消息触动，但认为 launchd 深度依赖 Mach IPC、移植性差且外围依赖链复杂，遂决定从零实现可移植版本，配置由 XML 转为 JSON，主张“init 系统应当非常简单、易于理解”（1911.12-1918.10）；原型先用 Ruby 数日完成验证，因社区反馈不愿以 Ruby 进程充当 PID 1 而改写为 C，并把原型阶段视为理解 launchd 各部件如何协作的教学过程。（BSD Now EP118，[1799.46-2040.72]，L1）

**史料**：

- 该期提及的一手史料包括：Yahoo 联合创始人刊于 FreeBSD News 的起源自述（原站已失效、仅存第三方网络缓存，由主持人代读引介，787.20-801.52）；Mark Heily 关于 relaunchd 设计与个人 BSD 经历的现场访谈自述（1518.34-3131.02）；Mike Larkin 将 VMM 初始代码推入 OpenBSD base 的提交信息与 man 页指引（611.74-674.10）；Matthew Dillon 关于 HAMMER2 硬链接修复的提交说明（3384.00-3450.56）；以及 Syncthing 项目公开的操作系统构成 metrics 统计页（3792.10-3842.42）。（BSD Now EP118，[787.20-3842.42]，L1）

**史观**：

- 总纲9 经验优先：Yahoo 采纳 FreeBSD 的决策过程是经验优先的典型样本：价格固然诱人，但当事人明言决定性因素是稳定性、性能与源代码可得性；关键判据不是基准测试而是日常运维事实——核心 Perl 脚本在 Linux 上反复崩溃而在 FreeBSD 上持续运行（1149.90-1170.77），动手运维者以自身经验完成裁决，任何理论性的操作系统优劣论证在此都退居其次。（BSD Now EP118，[962.62-1170.77]，L2）
- 总纲5 没有必然性，只有偶然性：Yahoo 与 FreeBSD 的结缘并无技术必然性可言：当事人自述当时公司无人了解 FreeBSD，只是“看到相关引用后决定一试”（849.54-858.54），一次偶然尝试叠加 Perl 崩溃差异的偶然事实，偶然地奠定了门户时代最大站点之一的生产基座；此后多次迁移计划均未完成，Yahoo.com 首页至 2015 年仍由 FreeBSD 服务，历史路径由偶然而非规律写成。（BSD Now EP118，[849.54-998.66]，L2）

**辨析**：

- 主持人补充的后续线索称 Yahoo 内部长期运行拼装混合的私有分支，掺杂 4.x、7.x 与 11.x 的代码片段，并流传 FreeBSD 4 二进制源码遗失、只能靠旧快照二进制维持运转的轶事（1197.18-1256.62）；该线索指向大公司私有分支与上游社区脱节的典型现象，但细节全凭转述与道听途说，不能作为直接史实引用。　[存疑脚注] YahooBSD 混合版本构成与 FreeBSD 4 二进制源码遗失轶事仅来自主持人转述 Hacker News 讨论及个人见闻，具体版本号与 Peter Wemm 快照故事细节均无一手文献佐证，本卡仅作线索存档（BSD Now EP118，[1197.18-1256.62]，L4）
- 访谈现场即时暴露了 relaunchd 的工程张力：主持人 Alan 当场指出以 system 拼接用户输入调用 rm 的命令注入风险与用 asprintf 拼出 shell 命令建目录的做法（2113.96-2124.72），Heily 承认初期 C 代码存在粗糙之处并明确警告不宜用于生产（2097.08-2104.40）；jail 内 socket 继承以免除 NAT 的设计被追问与 Capsicum 先初始化后锁定的权限模型存在冲突（2483.76-2527.08），说明把沙箱语义编入 init 配置在 2015 年仍是未经实践检验的新概念。（BSD Now EP118，[2061.88-2527.08]，L2）
