**要点**：

- Justin Sherrill 的主要项目工作是维护 DragonFly BSD Digest，每日从邮件列表中选摘要点；HAMMER 是 Matt Dillon 打造的历史保留、即时检查、可无限快照的文件系统，用户可按磁盘空间余量随时回溯历史版本文件，受访者称其为救命文件；HAMMER 1 采用 master-slave 复制，可在同一机器或跨机乃至跨互联网指定从盘并按带宽同步，主盘损毁时可将从盘提升为主，单主多从且各从盘可保留不同时长的历史，例如用大慢盘存放长期历史。（BSDTalk EP212，[54.16-349.12]，L1）
- HAMMER 1 已功能完备并经数年使用与修复锤炼；Sherrill 本人在重要数据上启用全部特性，开启去重后回收了约 20% 的磁盘空间；去重提供实时与隔夜两种模式，他使用隔夜模式即可满足需求，实时去重被比作快速复制——在大量数据复制过程中即时去重；HAMMER 内存要求很低，256MB 内存即可运行（需关闭吃内存的隔夜 reblocking），与作为对比基准的 ZFS 形成鲜明反差。（BSDTalk EP212，[447.16-638.52]，L1）
- HAMMER 与 ZFS 的主要差距在工具集成而非核心能力：ZFS 将磁盘管理与 RAID 等工具内建、具有所想即所得的便利，HAMMER 则采用主从复制而非 RAID，期望软件 RAID 的用户应转向硬件 RAID 卡；因此更好的硬件 RAID 卡驱动支持被视为 DragonFly 成败的关键因素，Sascha Wildner 近期引入 Areca 卡支持且该公司亲自测试了驱动，被受访者视为项目获得业界承认的时刻。（BSDTalk EP212，[641.47-760.04]，L1）
- HAMMER 2 在访谈前数日刚进入代码树，处于极早期，Matt Dillon 称六个月内无可玩内容、年底方能完成；其 multi-master 设计是 DragonFly 早期集群目标的当代回归——最初目标是整个操作系统的集群，而多核处理器的普及使单机多核已能满足算力需求，集群理想遂转向存储层；HAMMER 2 将继承 HAMMER 1 全部特性，新增更精细的去重（可只对部分文件系统执行）与配额支持，并已有技术性 release notes 发布。（BSDTalk EP212，[207.66-447.16]，L1）
- 架构与产品想象方面，DragonFly 支持 i386 与 x86_64；Sherrill 口头上一直鼓吹 ARM（尤其即将到来的 ARMv8）但自认缺乏执行技能、项目内亦无人推动，且新架构移植本身极为困难；他设想基于 ARM 的小型 NAS 设备运行 HAMMER、在亲属家放置第二台作受信备份并经 SSH 同步文件系统，认为这是一个亟待出现的 FreeNAS 的 HAMMER 等价物——相较每月三十美元电费的台式机，小 ARM 盒更容易被家庭接受。（BSDTalk EP212，[830.22-927.22]，L1）
- 社区观察：DragonFly 开发者总数保持静态，有人离开也会回归；受访者担忧编写操作系统已不像十年前那样吸引人，潜在贡献者转向 Android、iOS 应用开发；非 Windows 系统的开发日益由公司赞助，他即兴估计 Linux 内核约八成贡献来自公司付费开发者；开源从业余者人人贡献转向受益公司付费贡献，他不以此为大恶——认为水涨众船高——但怀旧 2002 年前后一个 tarball 即可开搞的朴素网页与个人痴迷式文档传统，对比如今要么商业抛光、要么近乎不存在的生态，并自承此判断并不科学。（BSDTalk EP212，[1018.30-1251.22]，L1）
- 治理与基础设施实态：DragonFly 完全由志愿者运作且没有法人实体，Sherrill 长期想创建 DragonFly 非营利组织以获得可签约、可持有版权的法律实体；代码版权栏写 DragonFly BSD Project 但技术上并不存在该实体，受访者自承非律师、不知此问题多严重；基础设施是一堆地下室——主站是 Matt Dillon 家中的数台机器，pkgsrc 批量构建依赖志愿者捐赠的机器空间，无商业实体托管；版本控制已由 CVS 转 Git 且相当成功，pkgsrc 的 CVS 到 Git 转换正在进行；Sherrill 自愿出任 3.0 发布经理，尚余七个阻塞 bug，nightly build 与候选版已可下载；项目连续四年参与 Google Summer of Code 并拟再次参加。（BSDTalk EP212，[1251.22-1595.34]，L1）

**史观**：

- 总纲4 分离聚合是永恒规律：DragonFly 最初以整个操作系统的集群为目标，多核硬件的普及使单机算力已足，集群理想遂在 HAMMER 2 的 multi-master 存储设计中重新聚合，呈现目标随技术条件变迁而分离再聚合的轨迹。（BSDTalk EP212，[373.04-397.04]，L1）
- 总纲3 不存在进步，只有权力再分配：开源贡献结构从业余志愿者的普遍参与转向受益公司付费开发者（以 Linux 约八成贡献来自付费开发者的观察为代表），在受访者看来并非简单的进步或堕落，而是贡献权力在爱好者与资本方之间的再分配。（BSDTalk EP212，[1088.30-1111.56]，L1）
