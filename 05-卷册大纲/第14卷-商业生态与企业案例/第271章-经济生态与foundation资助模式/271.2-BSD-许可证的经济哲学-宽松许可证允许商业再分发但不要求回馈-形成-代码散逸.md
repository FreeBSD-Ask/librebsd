# 271.2 BSD 许可证的经济哲学——宽松许可证允许商业再分发但不要求回馈，形成“代码散逸”的经济后果，Apple Darwin/BSD 用户空间、Sony PS 系列固件、Netflix CDN 等商业使用未形成对等回馈，与 GPLv2 的强制回馈机制形成经济哲学对照

## 271.2.1 BSDL 允许商业再分发的设计

**要点**：BSD 许可证（BSDL）的原始设计允许商业再分发且不要求回馈源代码：许可证仅要求保留版权声明与免责声明；这一设计源自 1980 年代 CSRG 与 BSD Inc. 的经济考量——鼓励厂商采用 BSD 代码以扩大 UNIX 影响；与 GPLv2 的 copyleft 强制回馈形成根本对照

**史料**：BSD 许可证原文（1989、1990 修订版）、GPLv2 文本（1989）、FSF 对 BSD 许可证的评论［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］〔L3 官方文档与公告〕

**史观**：总纲第 4 条——分离聚合是永恒规律：BSDL 设计延续 CSRG 的宽松传播传统，代码经商业再分发散逸至众多专有产品

**辨析**：宽松设计是否源于“被采纳优于被回馈”的策略——此策略在 bsd_commits.duckdb 中无直接 commit 证据，须依赖 McKusick 等 CSRG 时期开发者自述与 BSD 许可证起草历史文档交叉验证

## 271.2.2 代码散逸的经济后果

**要点**：代码散逸（code drift）的经济后果：Apple Darwin/BSD 用户空间、Sony PS3/PS4/PS5 Orbis OS、Netflix Open Connect CDN、Juniper Junos、NetApp ONTAP、Sun/Oracle Solaris 部分组件、iOS/macOS 网络栈等大量商业产品基于 FreeBSD 代码但未对等回馈；估计数十亿美元商业价值流出自 FreeBSD 社区

**史料**：Apple Darwin 源代码发布页、Sony PS4 系统文档、Netflix Tech Blog、Juniper Junos 文档 ［A］

**史观**：总纲第 13 条——法律与道德是利益分配，BSD 社区作为“被沉默的元老”承担代码散逸成本

**辨析**：散逸规模在 darwin.duckdb 中不可得（商业产品内部代码不反映在 FreeBSD commit 中），“数十亿美元”估算须依赖 Apple/Sony/Netflix 等企业商业报告与市场份额数据交叉验证；散逸的“经济损失”是否被“影响力收益”抵消是价值判断而非事实判断——BSD 社区以散逸换取影响力（Apple Darwin、Sony PS、Netflix CDN 均基于 FreeBSD）这一事实成立，但“抵消”与否取决于评估标准

**文献**：McKusick 关于 BSD 商业使用的访谈 ［B］

**要点**：

- 嵌入与安装有三重本质差异：嵌入以母镜像批量部署到多台设备而安装逐机定制并依赖发布工程或第三方项目产出镜像；嵌入要求一个跨版本可以精确重建的系统子集；嵌入面对的设备驱动需求不同，典型设备低功耗、无移动部件、全闪存运行并周期休眠，但亦有需风扇散热的路由器与文件服务器等接近普通 PC 的大型嵌入场景。（BSDTalk EP122，[82.04-181.52]，L1）
- 其十年嵌入式实践集中在两类平台：其一为 Intel 单板计算机从 Compact Flash 运行，需与大量自定义设备通信取状态与测量，构建时将闪存当普通盘但严格限制写入并深度子集化系统，产品镜像从约 14MB 到 96MB 不等；其二为基于 Atmel AT91RM9200 片上系统的低成本 ARM 平台，以 I2C 标记部件身份、SPI 承载引导 ROM、SD 卡存放系统，内存足迹更小且须更谨慎对待文件系统写入。（BSDTalk EP122，[184.52-288.32]，L1）
- 构建方法上从 FreeBSD 源码树取发布前后的快照，树本身几乎不加修改，配以自研软件、若干 ports 与 chroot 环境中的构建胶水，使镜像跨构建机器可再现且具有相同 MD5 签名；除特定自定义硬件外，全部平台支持都直接集成进 FreeBSD 树并进入受支持设备与处理器列表，所修缺陷与 ports 问题一律回馈原作者并滚动进后续版本。（BSDTalk EP122，[288.32-433.36]，L1）
- 闪存工程经验表明 SD 卡与 Compact Flash 的耐磨性已足够，只需多数系统只读挂载、不更新访问时间、日志先写入内存文件系统再刷回永久存储等简单预防，即可在除需与 MS-DOS 格式 U 盘互操作外的全部场景沿用 FFS；实时需求则完全下沉到硬件层，由操作系统定时调度、硬件执行测量后排队回传，产品无需任何实时增强。（BSDTalk EP122，[436.04-512.36]，L1）
- 当时嵌入式生态图景：x86 上已有 pfSense、m0n0wall 与 FreeNAS 等可下载镜像即装即得防火墙或网络存储；Linksys NSLU2（XScale ARM）与 WRT 系列路由器（MIPS）上均有移植努力，后者代码存于 Perforce 仓库但受 Linksys 持续削减闪存与 RAM 的成本策略阻碍；大量 MIPS 代码等待合入主树并期望赶上 7.0，ARM 与 PowerPC 的现成镜像仍然薄弱。　[存疑脚注] MIPS 移植赶在 7.0 之前合入属受访者当时的预期且自认存在后勤变数，实际合入时点须与发布工程记录核实。（BSDTalk EP122，[512.36-683.88]，L1）
- 他认为 FreeBSD 作为嵌入式系统的竞争力来自三点：多年专注服务器积累的强大网络与并行能力正日益成为嵌入设备的关键；集成源码树使构建与交叉构建所需一切都在仓库内，无须自行卷制发行版；BSD 许可证允许公司自由利用软件，随着其他开源许可证新限制出现，商业方正在重新审视 BSD 许可软件的价值。（BSDTalk EP122，[683.88-913.4]，L1）
- Bruce Momjian 回顾 Postgres 起点：1996 年代码离开伯克利时是一堆能力出色、前途可期但缺陷众多、学术导向的代码，他是启动基于互联网的协作开发的人之一，前四年以志愿者身份工作，此后受雇于从事 Postgres 业务的公司；近十年间项目从利基爱好成长为获得 Sun 及日美大型企业采用的主流数据库，.org 顶级域的 DNS 数据即由 Postgres 承载，美国国家气象局、大型金融公司与 Ameritrade 亦在使用；截至访谈时 8.1.2 为当前版本，8.2 开发重点转向数据仓库与高可扩展场景。（BSDTalk EP15，[356.75-628.76]，L1）
- Momjian 提出 BSD 许可证的企业友好论证：BSD 许可证没有任何附加条件或被认为没有附加条件，省去企业对开源许可证的律师审查恐惧，向内部推销极为容易；其结果是培育出一批以 Postgres 为业务的公司，出售商业版本、附加组件与支持服务；他把社区与企业的分工讲得直白——社区擅长开发与发版，但没有销售员、没有技术支持电话、没有上门做性能调优的人，而这些恰是许多组织需要的，BSD 许可证使大量公司得以全力支撑 Postgres 用户。（BSDTalk EP15，[467.44-570.88]，L1）
- Windows 原生 port 曾在 Postgres 社区内部引发真实斗争：是否要 Windows port、同一代码库同时容纳 Windows 与 Unix 的代价有多大；Momjian 花约两年与社区成员完成移植，结果是代码经模块化反而比开工前更干净；面对为何推广专有平台的质疑，他的回答是必须先在对方平台上展示开源的能力才能促成向开放操作系统的迁移，而 Windows 市场的实际定位是销售演示与开发者笔记本测试，并非大型服务器。（BSDTalk EP15，[806.95-901.72]，L1）
- 跨大版本就地升级是 Postgres 的结构性困境：子事务、两阶段提交等特性不断改变磁盘格式，一旦格式改变就必须读入并重写数据库的每一页，成本几乎等同转储重灌；Momjian 称这是项目前进太快带来的诅咒——技术上能写就地升级脚本，但每次核对跨版本变化后都显得不切实际；社区现行推荐是 Slony 复制方案，让新旧两版数据库并行运行，切换服务器即完成升级，停机仅一次重启，项目仍在零停机与转储重灌两类用户需求之间权衡是否值得再造第三条升级路径。（BSDTalk EP15，[923.85-1089.19]，L1）
- Covalent 的商业模式：八年来支持 Apache 软件基金会技术（Apache Web Server、Tomcat、Axis 网络服务框架，并新近支持 Geronimo），将免费获取的软件引入内部 QA 与测试实验室制成认证构建与安装器，向企业出售支持计划——技术支持、可检索知识库、保证缺陷修复的服务等级协议，以及传统开源世界不提供的产品赔偿（针对专利与版权侵权的 indemnification）；其可行的关键在于所支持的每个项目内部均有本公司代码提交者。（BSDTalk EP34，[114.82-244.0]，L1）
- Covalent 的工程实践：全部代码直接取自 ASF 分支、不维护自有版本控制分支；工程师对所支持项目拥有直接提交权，白天工作与夜间激情合一，此前在 Sun 或 IBM 时开源只是副业；发布纪律上宁等稳定——当前分发 Tomcat 5.5.9 而 ASF 最新为 5.5.16，因其判定后者尚不稳定、一级缺陷未清；选择支持对象的诀窍是选企业必需、正在使用且稳健成熟的技术，过早介入不成熟项目会令支持生意亏本。（BSDTalk EP34，[927.58-1136.54]，L1）
- 应用服务器格局与开源 Java：JBoss 极为成功且 Covalent 与之保持伙伴关系；Apache Geronimo 于 2006 年 1 月获 J2EE 认证，为可增删模块的轻量容器，与 JBoss 的分野核心在许可证——对 ISV 与惧怕改动 JBoss 代码的企业而言 Apache 许可几乎是不二之选；IBM、BEA、Oracle、Novell 均已嵌入 Apache 技术，若这些技术采用 GPL 它们将转而自行重写；Java 运行时许可须向 Sun、HP、IBM 分别获取，ASF 内孵化中的 Harmony 项目（以 Apache 类许可发布全套 JDK 与运行时）一旦认证完成，Geronimo 与 JBoss 都可能采纳。（BSDTalk EP34，[639.34-927.58]，L1）
- BSD 企业需求下滑的供给侧证词：Covalent 曾支持 BSD 平台，如今发布仅覆盖 Windows、IBM AIX、Solaris、HP-UX 与各发行版 Linux 六类平台（32 与 64 位），BSD 因需求下降而退出产品线，仅剩个别客户由其代为构建；当事人推测主因是 Linux 在财富千强级别大型商业企业中迅速崛起，而这恰是 Covalent 客户基所在；若有大客户重新采用，公司有能力随时恢复 BSD 支持。　[存疑脚注] 当事人对 BSD 需求下滑原因仅为推测性归因（Linux 在其客户群崛起），非系统市场研究结论（BSDTalk EP34，[1232.76-1300.72]，L1）

**史观**：

- 总纲13 法律与道德是利益分配：许可证在本期叙述中呈现为一种利益分配的制度形式：BSD 许可证的宽松条款使企业得以将 FreeBSD 转化为商业产品并愿意投入，而其他开源许可证新增的限制则改变企业侧的利益计算，驱使其重新分配对 BSD 的注意力；技术采用格局随许可证条款这一利益边界的变化而移动。（BSDTalk EP122，[713.92-913.4]，L1）
- 总纲5 没有必然性，只有偶然性：Momjian 自述约 1991 年起接触开源，并把参与 Postgres 归于纯粹的好运——是运气让他撞上这个特定项目；一个此后影响大量企业与机构的基础设施项目，其核心贡献者的加入并无必然路径，只系于个人轨迹中的偶然相遇。（BSDTalk EP15，[405.10-413.29]，L1）
- 总纲6 和解优于斗争：Windows port 之争的化解方式不是阵营间决出胜负，而是把改造成本内部化：移植过程中对代码库大规模模块化，使 Windows 与 Unix 在同一代码基中共存且质量反而提升，同时以先在对方平台证明开源价值的说服逻辑替代对专有系统的拒斥，构成一次以和解与互相渗透收场的路线分歧。（BSDTalk EP15，[820.31-901.72]，L1）
- 总纲3 不存在进步，只有权力再分配：当事人观察开源商业价值的迁移：过去客户选择开源主要为价格（Web 服务器还有经证明的稳定性与安全性），而近两年驱动因素转为创新——开源项目产出专有厂商尚未提供的尖端技术，企业对开源的期待已超越商品化的旧技术，并愿意为创新付费获取支持；ASF 自身从两三年前仅三四个主力项目扩张到约三十个可用项目加三四十个孵化项目，Covalent 参与其中四个孵化项目，开源生态正从成本替代品转为创新来源地。（BSDTalk EP34，[1145.26-1368.28]，L1）

**辨析**：

- 转写存在系统性专名失真：Bruce Momjian 被误记作 Momgen 与 Mumgen；复制方案 Slony 被误记作 Sloanie 与 Sloane；受访者所称曾用商业 BSD 被转写为 BFDI，应为 BSDi；所谓 the Douglas and Douglas book 的作者姓名须另行核考。引用本段史料时一律以正字为准。　[存疑脚注] 人名与专名以 PostgreSQL 社区公开记录复核：Momjian、Slony-I、BSDi；Douglas 书作者待考。（BSDTalk EP15，[342.19-350.55]，L1）
- 宽松许可证的回馈压力自述：Apache 与 BSD 系许可允许对软件做任何改动并以商业许可再授权，这既是其慷慨之美，也带来双重诱惑——外部软件商将 Apache 项目加值写成专有附加组件转售，公司内部亦有“加一点专有功能即可多收支持费”的声音；Covalent 约在访谈前两年半做出有意识决定，早期曾以 Apache 相关专有附加组件盈利，此后一切构建全部回馈相应项目；当事人承认 BSD 或 Apache 许可并不确保增强回到社区。（BSDTalk EP34，[368.54-458.8]，L1）
- 当事人对 GPL 的两面评价：先替 GPL 辩护——GPL 与 LGPL 确保项目不分叉、防止公司拿软件改动牟利而不回馈社区，这正是其原则；随后指出其负面——SAP、Oracle 等 ISV 因修改须交回社区且无法以商业许可授权自建产品而回避嵌入任何 GPL 代码（只保证产品与 Linux、JBoss 等并存运行），财富千强中非软件企业则担心工程师改动源码后在现行 GPL 下是否构成衍生作品并不清晰，GPLv3 有望对此作出更清楚的界定。（BSDTalk EP34，[480.28-636.34]，L1）
