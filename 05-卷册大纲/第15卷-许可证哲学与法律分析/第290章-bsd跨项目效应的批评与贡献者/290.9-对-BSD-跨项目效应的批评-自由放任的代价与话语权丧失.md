# 290.9 对 BSD 跨项目效应的批评：自由放任的代价与话语权丧失

## 290.9.1 BSD 许可证导致回馈不足的批评

**要点**：BSD 跨项目影响的最大批评是“回馈不足”——Apple、Sony、NetApp、Juniper 等大量采用 BSD 代码但回馈有限（参见商业生态章）；OpenSSH 被 Linux 发行版、Windows、macOS 广泛采用，但 OpenBSD 项目长期资金紧张——2014 年 1 月 Theo de Raadt（西奥·德·若特） 公开呼吁支付电费账单（约 2 万加元），Bob Beck 称“如果我们没有资金维持运转，OpenBSD 将关闭”，后获 Mircea Popescu 约 2 万美元比特币捐赠解困；LibreSSL fork 后未能吸引足够贡献者，开发长期依赖 OpenBSD 项目内部资源；Linus Torvalds 在 1998 年 LinuxFocus 访谈中表示“GPL 与 BSD 许可证相比并无本质优越性，但 GPL 是我想要使用的编程许可证，因为不同于 BSD 许可证，它保证任何未来参与项目的人也会将其修改回馈给社区”——此立场隐含地批评了 BSD 许可证的回馈缺位；批评者认为 BSD 许可证的设计导致无法形成可持续回馈循环

**史料**：de Raadt 2014 年 1 月 openbsd-misc 邮件“Request for Funding our Electricity”（marc.info/?l=openbsd-misc&m=138730448307723）、Bob Beck 后续呼吁邮件（“OpenBSD will shut down if we do not have the funding to keep the lights on”）、Mircea Popescu 比特币捐赠报道（The Register 2014-01-20）、Torvalds 1998 年 LinuxFocus 访谈（linuxdoc.org/linuxfocus/English/March1998/article27.html）、FreeBSD commit 记录中 @apple.com/@sony.com/@netapp.com 统计 ［A］；freebsd.duckdb 查询 L3.2.1 显示：BSD 全谱系 22 仓库中商业实体（Netflix/Juniper/NetApp/EMC/Google/Apple/Microsoft/Sony/iXsystems 等 12 类邮箱域名）commit 占比随时间变化——2005 年 153 commercial_commits / 267,087 total（commercial_pct 低于 0.1%），2010 年 597 / 265,065，2015 年 3,391 / 381,897，2020 年 3,820 / 303,425，反映商业实体 commit 绝对值自 2010 年后增长但占比长期低于 1.3%，与 Torvalds 1998 年批评中“BSD 许可证不保证回馈”的论断在数据层面相互印证；freebsd.duckdb 查询 L7.2.1 显示：衍生项目贡献者在 freebsd-src 的回馈 commit 前 10 位中，iXsystems（<ryan@iXsystems.com> 329 次）、LLNL（<behlendorf1@llnl.gov> 2,603 次 + <hutter2@llnl.gov> 342 次，共 2,945 次）、Delphix（<mahrens@delphix.com> 229 次）等商业实体员工是重要回馈来源，说明部分商业实体确有回馈但回馈集中度高

**史观**：总纲第 13 条——法律与道德是利益分配（原“许可证”系伪名目，按 dagang.md 13 条分析指令改挂）：BSD 许可证的设计决定了回馈不足的结构性；总纲第 13 条——法律与道德是利益分配（原“商业与社区的张力”系伪名目，按族例改挂，存疑）：商业采用与社区回馈的不对称

**辨析**：回馈“不足”的量化标准须明确——是 commit 数、代码行数还是资金量；OpenBSD 资金紧张的具体数据须查基金会年报；Torvalds 批评的语境须查原访谈；0 信任原则局限标注：L3.2.1 查询基于 12 类商业邮箱域名（@netflix.com/@juniper.net/@netapp.com/@ixsystems.com 等）匹配，企业员工若用个人邮箱（@gmail.com）或 @users.noreply.github.com 提交则不计入 commercial_commits，可能低估实际商业贡献；查询覆盖 22 个仓库包括 BSD 4 大 src 与衍生项目，但 Apple/Sony 等公司在 macOS/PS 内部 fork 中的贡献未公开，无法纳入统计；L7.2.1 的“衍生项目贡献者”定义仅覆盖 7 个衍生仓库（trueos-src/ghostbsd-src/hardenedbsd-src/midnightbsd-src/truenas-middleware/opnsense-core/pfsense-src），OpenZFS/OpenSSH 等独立项目贡献者未被纳入，<behlendorf1@llnl.gov> 的 2,603 次回馈 commit 仅反映其在 freebsd-src 中的贡献，不含其在 openzfs-zfs 中的核心贡献；commercial_pct 字段四舍五入可能导致占比显示偏低，须结合绝对值综合判断；author 字段可由提交者任意填写，author_email 与实际雇主关系须结合 LinkedIn/公司公开员工列表等独立来源交叉验证

**文献**：de Raadt 资金呼吁；Torvalds 评论；基金会年报 ［B］；bsd_commits.duckdb L3.2.1 查询报告（深层信息挖掘.md §L3.2.1）；bsd_commits.duckdb L7.2.1 查询报告（衍生项目与跨项目对比分析.md §L7.2.1）

## 290.9.2 BSD 效应力被 Linux 阵营抢占话语权的批评

**要点**：BSD 跨项目影响虽广但话语权长期被 Linux 阵营抢占——Jails 早于 Docker 13 年但 Docker 流行化后被广泛称为“容器革命”，Jails 的开创性贡献被忽视；socket API 进入 POSIX 后被普遍称为“POSIX socket”而非“BSD socket”；OpenSSH 被广泛采用但 OpenBSD 项目未获相应声誉；批评者认为 BSD 阵营缺乏 Linux 阵营的市场推广能力（如 Linux 基金会、Canonical、Red Hat 等商业推广）

**史观**：总纲第 13 条——法律与道德是利益分配（原“商业与社区的张力”系伪名目，按族例改挂，存疑）：BSD 阵营市场推广能力不足导致话语权丧失；总纲第 9 条——经验优先（原“0 信任原则”系伪标签族，按族例改挂）：话语权“丧失”的判断须独立考据

**辨析**：“话语权丧失”的量化困难——须具体到案例（如 Jails vs Docker）而非泛化；BSD 阵营是否真“缺乏市场推广能力”须对比 FreeBSD 基金会 与 Linux 基金会预算

## 290.9.3 BSD 项目资源分散导致衍生项目失控的批评

**要点**：BSD 跨项目影响的另一批评是“资源分散”——OpenBSD 项目同时孵化 OpenSSH、LibreSSL、mandoc、pf、httpd 等多个项目，资源分散导致每个项目维护压力巨大；LibreSSL fork 后未能吸引足够贡献者，长期依赖 OpenBSD 内部团队；OpenSSH portable 分支独立于 OpenBSD 基础系统，治理分散；批评者认为 BSD 项目应集中资源于核心项目而非广泛孵化

**史料**：OpenBSD 项目历年开发者统计、LibreSSL commit 频度统计、OpenSSH portable 治理结构文档、de Raadt 关于资源分散的公开声明 ［A］

**史观**：专题语（不设总纲条号）——技术选择的代价（原挂总纲第 6 条系伪名目，删条号）：广泛孵化带来资源分散的代价；专题语（不设总纲条号）——组织结构塑造技术路径（原挂总纲第 5 条系伪名目，删条号）：OpenBSD“自给自足”文化的代价

**辨析**：资源“分散”的判断须对比 OpenBSD 与 Linux 内核开发者数量；LibreSSL 维护压力须查 commit 频度；“集中资源”的建议须辨析——集中可能降低孵化能力

**文献**：OpenBSD 开发者统计；LibreSSL commit 历史 ［A］

## 290.9.4 批评的形式主义分析

**要点**：对 BSD 跨项目影响的批评存在形式主义倾向——单纯以“回馈不足”“话语权丧失”“资源分散”否定 BSD 阵营的跨项目贡献是形式主义误读；BSD 跨项目影响的实质在于“基础设施性”——OpenSSH、socket API、Jails 等构成全球软件基础设施，其价值不在于直接回馈而在于生态支撑；形式主义分析忽视 BSD 跨项目影响的“非存在性”特征——影响通过不存在的方式（许可证宽松、设计传承、协议标准化）实现，难以量化

**史料**：BSD 跨项目影响历年研究、形式主义批评方法论文献、开源生态量化研究 ［B］

**史观**：专题语（不设总纲条号）——技术选择即政治选择（原挂总纲第 7 条系伪名目，删条号）：形式主义分析忽视技术选择背后的实际效果；总纲第 9 条——经验优先（原“0 信任原则”系伪标签族，按族例改挂）：形式主义批评须独立考据

**辨析**：形式主义批评与实质批评的边界存在争议——“回馈不足”的实质影响须具体到项目可持续性而非仅 commit 数；“基础设施性”价值的量化须避免空洞口号

**文献**：BSD 跨项目影响研究；形式主义批评方法论文献 ［B］

### 290.9.5 反批评层：BSD 阵营对“回馈不足”“话语权丧失”“资源分散”批评的反批评

- **要点**：对 BSD 跨项目效应的“回馈不足”“话语权丧失”“资源分散”三项批评，BSD 阵营的反批评聚焦于四点：第一为 **“回馈不足是 BSD 许可证的设计意图而非失败”**——Linus Torvalds 在 1998 年 LinuxFocus 访谈中表示“GPL 与 BSD 许可证相比并无本质优越性，但 GPL 保证任何未来参与项目的人也会将其修改回馈给社区”——此立场隐含地承认 BSD 许可证的“无强制回馈”是设计选择而非缺陷。BSD 阵营若要求强制回馈则与 BSD 许可证的“消极自由”原则矛盾。bsd_commits.duckdb 查询 L3.2.1 显示商业实体 commit 占比长期低于 1.3% 但绝对值自 2010 年后增长（2015 年 3,391 commits、2020 年 3,820 commits），反映“回馈虽有限但非完全缺失，且呈增长趋势”。第二为 **“话语权丧失是标准化的必然结果而非 BSD 阵营的失败”**——BSD socket API 进入 POSIX 后被称为“POSIX socket”是标准化的目的（消除特定来源标签）；Jails 早于 Docker 13 年但 Docker 流行化后被广泛称为“容器革命”是市场推广能力的差异而非技术原创性的丧失；OpenSSH 被广泛采用但 OpenBSD 项目未获相应声誉是“基础设施性”的必然代价（影响越基础越容易被忽视）。第三为 **“资源分散是 BSD 阵营‘广泛孵化’文化的代价而非治理失败”**——OpenBSD 项目同时孵化 OpenSSH、LibreSSL、mandoc、pf、httpd 等多个项目，资源分散导致每个项目维护压力巨大，但此“广泛孵化”是 OpenBSD“自给自足”文化的体现——OpenBSD 不依赖外部项目而自建所需工具链，此文化有代价（资源分散）但也有价值（独立性与安全审计的全面性）。第四为 **“形式主义分析的局限性——‘基础设施性’价值须以非量化方式评估”**——BSD 跨项目影响的实质在于“基础设施性”——OpenSSH、socket API、Jails 等构成全球软件基础设施，其价值不在于直接回馈（commit 数、资金量）而在于生态支撑（全球软件依赖 BSD 代码运行）；形式主义分析（以量化指标否定 BSD 跨项目贡献）忽视了“非存在性”特征——影响通过不存在的方式（许可证宽松、设计传承、协议标准化）实现，难以量化。
- **史料**：OpenBSD Copyright Policy 官方文档（openbsd.org/policy.html，BSD/ISC 许可证“无回馈”设计意图直接表述，经 2026-07-30 一手核验）；McKusick “Twenty Years of Berkeley Unix: From AT&T-Owned to Freely Redistributable”（载 O'Reilly Open Sources 1999，mckusick.com/history/，BSD“自由可再分发”设计意图直接表述，经 2026-07-30 一手核验）；Torvalds 1998 年 LinuxFocus 访谈（linuxdoc.org/linuxfocus/English/March1998/article27.html，明确表示“GPL 保证回馈”但“GPL 与 BSD 无本质优越性”）；openbsd.duckdb 查询 L3.2.1（商业实体 commit 占比长期低于 1.3% 但 2015 年 3,391 commits、2020 年 3,820 commits）；openbsd.duckdb 查询 L7.2.1（衍生项目贡献者回馈前 10 位，<behlendorf1@llnl.gov> 2,603 次、iXsystems 329 次、Delphix 229 次，反映部分商业实体确有回馈但集中度高）；OpenBSD 基金会 2014 年 1 月资金呼吁（de Raadt 公开呼吁支付电费账单约 2 万加元，后获 Mircea Popescu 约 2 万美元比特币捐赠解困）；Docker 市场推广文献与 Jails 文献中“BSD 容器”被忽视的案例；socket API 在教科书中“POSIX socket”的称呼。
- **史观**：专题语——道与术的辩证（原挂总纲第 5 条系伪名目，删条号）与总纲第 13 条——法律与道德是利益分配（原“许可证哲学”系伪名目，改挂）。BSD 阵营的反批评实质上是将“回馈不足”“话语权丧失”“资源分散”的批评置于“许可证设计意图”“标准化必然结果”“广泛孵化文化代价”的框架下重新审视——此三者非“失败”而是“设计代价”。项目史观总纲第五章“道与术的辩证”在此显现：BSD 许可证作为“道”（哲学原则）允许“术”（具体采用）的无回馈，此“无回馈”非“道”的失败而是“道”的工程化显现。

### 290.9.6 再回应层：批评方对 BSD 阵营反批评的再回应

- **要点**：对 BSD 阵营反批评的四点（设计意图、标准化必然、广泛孵化代价、形式主义局限性），批评方的再回应聚焦于四点：第一为 **“设计意图不能豁免实际后果”**——BSD 阵营以“许可证设计意图即允许无回馈”自辩，但设计意图与实际后果不可等同。OpenBSD 2014 年 1 月资金危机（de Raadt 公开呼吁支付约 2 万加元电费账单，Bob Beck 称“如果我们没有资金维持运转，OpenBSD 将关闭”）是“设计代价”的极端显现——若非 Mircea Popescu 约 2 万美元比特币捐赠解困，OpenBSD 项目可能关闭，此后果非“设计意图”所能豁免。**bsd_commits.db** 查询 L3.2.1 显示商业实体 commit 占比长期低于 1.3%，2015 年 3,391 commits / 381,897 total、2020 年 3,820 commits / 303,425 total，绝对值虽增长但占比仍极低，“增长趋势”的基数过低不足以证明回馈可持续。“设计意图”论证存在循环推理风险——以“BSD 许可证设计为允许无回馈”证成“无回馈是合理的”，但此论证以设计本身证成设计的后果，未提供独立证成。第二为 **“标准化不必然消除归属”**——BSD 阵营以“BSD socket API 进入 POSIX 后被称为 POSIX socket 是标准化目的”自辩，但标准化消除特定来源标签并非必然。TCP/IP 协议进入 RFC 标准后仍保留“TCP/IP”名称（源于 DARPA 项目但未被标准化消除归属），对比可见“POSIX socket”的命名是特定选择而非标准化必然。Jails 早于 Docker 13 年（FreeBSD 4.0 release notes 2000.3 vs Docker 2013）被 Docker 流行化掩盖，不仅是市场推广能力差异，更是 BSD 阵营在文档建设、生态运营、开发者教育方面的系统性不足——Docker 提供全面文档、Docker Hub 生态、开发者大会，Jails 缺乏对应生态建设。第三为 **“广泛孵化文化的代价由社区与用户承担而非仅由项目承担”**——BSD 阵营以“资源分散是广泛孵化文化的代价”自辩，但此代价的承担者不仅是 OpenBSD 项目本身，还包括依赖 OpenSSH、LibreSSL 等项目的全球用户与发行版。LibreSSL fork 后未能吸引足够贡献者，长期依赖 OpenBSD 内部团队，反映“广泛孵化”模式在吸引外部贡献方面存在结构性局限——此局限非“代价”二字所能涵盖，而是治理模式的可持续性问题。OpenSSH portable 分支独立于 OpenBSD 基础系统，治理分散导致安全更新协调成本增加，此为采用者与发行版承担的隐性代价。第四为 **“‘基础设施性’论证本身是形式主义”**——BSD 阵营以“基础设施性价值须以非量化方式评估”反驳形式主义分析，但“基础设施性”论证本身是一种形式主义抽象——它将具体的回馈不足、话语权丧失、资源分散等问题抽象为“基础设施性贡献”的整体叙事，以此回避具体问题的量化评估。若完全拒绝量化，BSD 阵营无法评估自身影响力的实际分布，也无法识别哪些项目（如 OpenSSH）需要紧急资源支持——“非量化评估方法”在实践中难以操作化，可能成为回避问责的盾牌。

### 290.9.7 合图层：BSD 跨项目效应的“基础设施性”与“许可证代价”的辩证统一

- **要点**：综合批评-反批评-再回应三层辩证，BSD 跨项目效应的核心矛盾可总结为“基础设施性与许可证代价的辩证统一”——即 BSD 许可证的“消极自由”使 BSD 代码（OpenSSH、socket API、Jails、libarchive、jemalloc 等）构成全球软件基础设施的一部分，但同一“消极自由”使采用者无强制回馈义务，导致 OpenBSD 2014 年资金危机、Jails 被 Docker 流行化掩盖、socket API 被称为“POSIX socket”而非“BSD socket”等现象。此矛盾不可“调和”——因 BSD 许可证的设计意图即允许无回馈采用，若要求强制回馈则与许可证哲学矛盾——但可“分离聚合”——因“基础设施性”（全球软件依赖 BSD 代码）与“许可证代价”（回馈有限、话语权丧失、资源分散）是同一 BSD 许可证的两面。合图层的核心判断为：BSD 跨项目效应是“基础设施性贡献”而非“回馈失败”——OpenSSH 的全球采用（Linux 发行版、Windows、macOS）、socket API 的 POSIX 标准化、Jails 的容器设计先驱、libarchive 的 macOS/Debian/Homebrew 采用、jemalloc 的 Meta/Rust 采用，均证明 BSD 代码构成全球软件基础设施的一部分；而“回馈不足”“话语权丧失”“资源分散”是此“基础设施性”的许可证代价，非“失败”而是“设计代价”。此判断对应项目史观总纲第六章“主体性与和解”——BSD 阵营以“基础设施性贡献”为主体性呈现，采用者以“无回馈采用”为自身主体性呈现，二者的辩证即“分离聚合”的循环。形式主义分析（第 136.9.4 节）的局限性在此显现——单纯以量化指标（commit 数、资金量、话语权）否定 BSD 跨项目贡献忽视了“非存在性”特征，而“基础设施性”价值须以非量化方式评估。

### 290.9.8 项目统摄史观审视：许可证哲学、解释学循环与革命改革方法论

- **要点**：BSD 跨项目投入与回报不对称争议的四层辩证链（批评-反批评-再回应-合图）可从项目史观总纲第 13 条、第 19 条、第 21 条三个维度审视。**从总纲第 13 条（法律与道德是利益分配）审视**：BSD 许可证争议本质上是利益分配问题而非道德问题或法律哲学问题。“回馈不足”的道德批评与“设计意图”的反批评，皆是将利益分配问题转化为道德话语（“应为”“不应为”）或法律话语（“设计意图”“许可证条款”）的形式主义操作。BSD 许可证作为法律文本，是形式主义的政治产物——它规定了 BSD 阵营与采用者（Apple、Meta、Linux 发行版等）之间的利益分配规则，此规则的非强制性（无 copyleft 条款）使利益分配偏向采用者一方。但此“偏向”非“失败”亦非“设计意图”，而是利益分配的一种形式主义呈现。项目史观总纲第十三章“史学含义”提示：BSD 史不应写成一部技术英雄的颂歌，BSD 史中真正值得书写的是那些“不在场的观众”——无数安装使用却从未出现在 commit log 中的用户。跨项目效应的“基础设施性”价值，恰恰在于这些“不在场的观众”的集体性存在，而非 BSD 阵营的“贡献”叙事。**从总纲第 19 条（解释学循环与权力知识共谋）审视**：话语权争议本质上是权力与知识的共谋。什么被记录（Docker 作为“容器革命”载入技术史）、什么被遗忘（Jails 作为容器设计先驱被忽视），本身就是权力行使。“POSIX socket”的命名是权力运作的显例——BSD socket API 的实质贡献被标准化吸收，而 BSD 的标签被标准化消除，此为“权力与知识在历史书写中共谋”的典型案例。批评方与反批评方的前理解差异使分歧不可避免——批评方预设“回馈是应尽的义务”，反批评方预设“无回馈是设计意图”，再回应方预设“设计意图不能豁免后果”，合图层预设“基础设施性与许可证代价是辩证统一”。此四者的前理解差异非可通过“更多事实”消解，而是解释学循环的根本条件。项目史观总纲第十九章“历史参考的同一性问题”在此显现：当我们讨论“BSD”时，我们指的是 4.4BSD-Lite、FreeBSD 14.0、还是 OpenBSD 7.4？跨项目效应的“BSD”是一个形式主义化的非存在——它通过不存在的方式（许可证宽松、设计传承、协议标准化）实现影响，此“非存在性”使“BSD 跨项目效应”成为一个难以对象化的历史对象。**从总纲第 21 条（革命与改革）审视**：Linux 的“革命”（GPL 强制回馈、Docker 流行化、市场推广）与 BSD 的“改革”（许可证宽松、广泛孵化、基础设施性贡献）是历史方法论的分歧。改革的困难远高于革命——BSD 的“改革”路径在话语权上处于劣势（Jails 被 Docker 流行化掩盖、socket API 被称为“POSIX socket”），但保留了独立性与基础设施性（OpenSSH 全球采用、libarchive 进入 macOS 基础系统）。“破山中贼易，破心中贼难”——BSD 阵营面临的根本困境不在于技术论证（**bsd_commits.db** 量化数据可证商业实体 commit 占比低于 1.3%），而在于观念和结构的改变。一旦想改变“无回馈采用”的结构，BSD 阵营本身已是此结构的一部分（BSD 许可证的设计即允许无回馈），改变已不可能——此为改革者面临的根本困境。项目史观总纲第二十一章“原型先行与否定之否定”在此显现：BSD 的“改革”路径形成了一种否定之否定的局面——不敢也不能否定主体自身（BSD 许可证的设计），此“不敢否定”非“保守”而是“忒修斯之船式的否定”——主体在保留中迭代，而非在否定中重建。
