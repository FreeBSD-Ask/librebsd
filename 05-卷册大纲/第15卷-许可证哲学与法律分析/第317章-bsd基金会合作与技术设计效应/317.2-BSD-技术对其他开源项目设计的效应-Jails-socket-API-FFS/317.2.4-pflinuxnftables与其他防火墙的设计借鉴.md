# 317.2.4 pf → Linux nftables 与其他防火墙的设计借鉴

**要点**：OpenBSD pf（详见 136.1.3）的设计理念——状态检测、ALTQ 集成、可读语法——在防火墙领域产生了广泛影响；Linux 早期 ipchains（1998 年）→ iptables（2001 年，Linux 2.4）→ nftables（2014 年，Linux 3.13）；经核查 nftables 官方 wiki，nftables 语法设计受 tcpdump 启发（“a compact syntax inspired by tcpdump”），并非直接借鉴 pf；nftables 与 pf 在 table/chain 抽象层面存在结构相似性，但此为防火墙设计的通用模式而非直接继承；pf 还被 FreeBSD（5.3 起）、NetBSD、macOS（底层自 10.6 Snow Leopard 起以 pf 替换 ipfw；10.5 Leopard 引入的应用层防火墙 ALF 为独立组件、与 pf 异层，Apple 采用 pf 的具体时点细节存疑待考）、QNX 等采用；pf 的设计影响是 OpenBSD 塑造开源网络基础设施的典型案例

**史料**：OpenBSD 3.0 release、Linux 2.4 iptables 文档、Linux 3.13 nftables 文档、FreeBSD 5.3 release、nftables 设计文档（netfilter.org）［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］〔L3 官方文档与公告〕

**史观**：总纲第 4 条——分离聚合是永恒规律：pf 设计跨 BSD 与 Linux 扩散；总纲第 3 条——不存在进步，只有权力再分配：pf 跨平台移植存在性能与功能差异

**辨析**：经核查 nftables 官方 wiki，nftables 语法设计受 tcpdump 启发（“a compact syntax inspired by tcpdump”），非直接借鉴 pf；pf 与 nftables 在 table/chain 结构层面的相似性为防火墙设计的通用模式，不宜表述为 “pf 影响 nftables”；pf 在 macOS 中的应用层防火墙关系须查 Apple 开发者文档——macOS 10.5 Leopard 引入 Application Firewall（独立组件），10.6 Snow Leopard 起底层改用 pf 替换 ipfw，二者为不同层次；iptables 与 pf 的性能对比须查独立基准测试

**要点**：

- SmallWall 的诞生系于一次突然的项目终结：2015 年 2 月 monoWall 作者 Manuel Kasper 以一封邮件宣布项目停止开发，长期依赖该精简防火墙的咨询者与用户在震惊中几乎同时注册域名、搭建基础设施，Lee Sharp 以连续的 beta 发布承接社区，并因 Slashdot 报道获得爆发性下载，项目由此复活。 [存疑脚注] 转写将发件人误作 a manual，依 monoWall 项目史推断为作者 Manuel Kasper（BSD Now EP97，[1031.14-1112.33]，L1）
- SmallWall 的产品立场是刻意求小：Lee Sharp 明言遵循 “do one thing and do it well”（1149.05-1153.09）的旧 Unix 哲学，拒绝大而全防火墙，专注低功耗嵌入式与虚拟化场景（早期即加入 VirtIO 驱动以适配 KVM 等开源虚拟机）；管理面以 Web 界面防呆、把多网段等危险操作刻意变难，配置为可任意编辑的扁平 XML 文件（1514.23-1539.05），固件更新经 RAM disk 中转以保护 CF 卡与 U 盘的写入寿命。（BSD Now EP97，[1144.38-1194.77]，L1）
- Docker 登陆 FreeBSD ports tree 由当期主持人亲自提交 port（其自述移植主体另有其人、自己只补 port 打包），实测 FreeBSD 容器原生运行于 Jail 子系统与 ZFS 之上、近全部子命令可用，在 -CURRENT 的 64 位 Linuxulator 上亦可尝试运行 Linux 容器；遗留缺口包括 resolv.conf 未自动复制与依赖 PF 做 NAT 转发的临时胶水，期望日后由 port 内部接管。（BSD Now EP97，[3383.60-3518.65]，L1）[订正：原 [3375.71-3518.65]，2026-09-30 SenseAudio 重转核对]
- 2015 年的两个外部靠拢信号由主持人转述：微软因决定在 Windows 中集成 OpenSSH 而向 OpenBSD 基金会捐赠、成为金牌赞助商，并在 OpenSSH 邮件列表发出合同工作邀约、承诺变更酌情上游回馈；同期 Oracle 的 Solaris 计划以原生 OpenSSH 取代 Sun SSH 分叉，并自 OpenBSD 借入 getentropy、将 arc4random 并入 libc（2545.47-2576.31）。（BSD Now EP97，[3630.00-3658.04]，L2）[订正：原 [3615.63-3658.04]，2026-09-30 SenseAudio 重转核对]

**史观**：

- 总纲第 10 条 动手者创造历史：SmallWall 的谱系由动手者而非明星人物书写：Lee Sharp 自述当年受教于 monoWall 周边的实践者——Chris 后执掌 pfSense 与 BSD Perimeter，写文档者独立门户，做网络架构者遍及全球——如今他刻意降低开发门槛、把工具与文档摆出来，请有想法的人跳进来，以日常劳动的传递续写项目，而非依赖英雄叙事。 [存疑脚注] 转写将相关人名误作 Michael Adema、Escozia、Jonathan DeGraves 等，准确拼写待核（BSD Now EP97，[1986.33-2023.69]，L1）
- 总纲第 5 条 没有必然性，只有偶然性：项目的存在本身即偶然性的产物：没有那份宣布停更的邮件便没有 SmallWall，Lee Sharp 强调少数人 “had the same idea at the same time”（1078.33-1083.33），复活不是历史必然，而是几个用户在同一周内的应急反应；其早期声势亦系于 Slashdot 曝光这类无法规划的事件。（BSD Now EP97，[1031.14-1090.33]，L1）

**辨析**：

- 旧基线之辩是本期最有张力的技术判断：SmallWall 坚守 FreeBSD 8.4，主张 “Old is good”（1380.53-1383.13）——基线更久经测试，因 Shellshock 与 Heartbleed 均未波及（无 shell、无受影响特性），但 8.4 安全支持数月内终止，向 FreeBSD 10 迁移牵动大量代码；且历史上 monoWall 曾因 FreeBSD 6 网络性能不济而自 4 直接跳 8——稳定与前沿的取舍并非单向进步，而是按自身负载场景的权衡。（BSD Now EP97，[1374.01-1478.79]，L1）
