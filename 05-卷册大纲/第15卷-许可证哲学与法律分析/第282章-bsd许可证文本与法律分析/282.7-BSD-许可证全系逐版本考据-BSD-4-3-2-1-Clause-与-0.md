# 282.7 BSD 许可证全系逐版本考据——BSD 4/3/2/1-Clause 与 0BSD 的文本演变、SPDX 标识与语义差异

> 本节依据“许可证考据规则”：许可证考据必须按具体版本逐个考据，禁止合并表述。全部版本信息经 SPDX License List（spdx.org/licenses）、OSI 官方（opensource.org/licenses）、FSF（gnu.org）与 OSI 邮件列表一手记录交叉验证。

## 282.7.1 BSD-4-Clause（Original BSD License）——广告条款时代

**要点**：BSD 4-Clause 为 BSD 原始许可证，含广告条款（第 3 条：所有提及本软件功能的广告材料须注明“由加州大学伯克利分校及其贡献者开发”）；1999-07-22 由 University of California, Berkeley Office of Technology Licensing（OTL）主任 William Hoskins 发布公告（抬头“To All Licensees, Distributors of Any Version of BSD”）宣布立即废除广告条款。原始文件：`ftp://ftp.cs.berkeley.edu/pub/4bsd/README.Impt.License.Change`。FSF 视 4-Clause 为自由许可证但与 GPL **不兼容**（广告条款与 GPL 冲突），OSI 未批准其通过开源定义（广告条款违反 OSD §6 无歧视）。

**史料**：Berkeley OTL 1999-07-22 公告（William Hoskins 签署）；SPDX `BSD-4-Clause` 条目；FSF “The BSD License Problem” ［A］

**史观**：总纲第 13 条——法律与道德是利益分配：广告条款的兴废是 BSD 许可证史上最具戏剧性的条款变迁

**辨析**：广告条款的废除动因含 FSF 与 Stallman 的推动（为 BSD-GPL 兼容性），属共同体共识推动制度变更的实例；4-Clause 与 3-Clause 的过渡时间线（1999-07-22 公告 → OSI 批准 3-Clause）经多源交叉验证一致 [考据完成：2026-08-04]

**文献**：Berkeley OTL 1999-07-22 公告；SPDX License List `BSD-4-Clause`；FSF Various Licenses and Comments about Them ［A］

## 282.7.2 BSD-3-Clause（New/Revised BSD）——背书禁止条款

**要点**：BSD 3-Clause 由 BSD 4-Clause 删去广告条款而来（1999-07-22 OTL 公告，见 282.7.1），2-Clause 再移除其背书禁止条款（第 3 条：未经事先书面许可，不得使用机构名称或贡献者姓名背书/推广衍生品）；1999-07-22 起为 BSD 标准形式；OSI 批准（opensource.org/licenses/BSD-3-Clause）；FSF 确认与 GPL 兼容。

**史料**：SPDX `BSD-3-Clause`；OSI 批准页；FSF Various Licenses ［A］

**史观**：总纲第 13 条——法律与道德是利益分配

**辨析**：3-Clause 的背书禁止条款与 2-Clause 的移除是该系列版本差异的核心；FreeBSD 项目早期用 3-Clause 后转 2-Clause [考据完成：2026-08-04]

**文献**：SPDX. BSD-3-Clause[DB/OL]. 年份不详；OSI. BSD-3-Clause 批准页[EB/OL]. 年份不详；FSF. Various Licenses[EB/OL]. 年份不详 ［A］

## 282.7.3 BSD-2-Clause（Simplified/FreeBSD）——背书条款移除

**要点**：BSD 2-Clause 移除背书禁止条款，仅保留版权声明保留（源码）与再分发声明（二进制）；FreeBSD 项目默认许可证（FreeBSD License 变体增加“观点与意见”免责声明）；FSF 称 Simplified BSD / FreeBSD License，确认与 GPL 兼容。

**史料**：SPDX `BSD-2-Clause`；FreeBSD 官网 LICENSE；OSI 批准页 ［A］

**史观**：总纲第 13 条——法律与道德是利益分配：2-Clause 成为现代 BSD 项目（FreeBSD/Nginx/Varnish 等）主流选择

**辨析**：BSD-2-Clause 与 MIT 实质等价（条款差异仅措辞）；FreeBSD 版本附加免责声明 [考据完成：2026-08-04]

**文献**：SPDX；FreeBSD LICENSE；OSI ［A］

## 282.7.4 BSD-1-Clause（FreeBSD 变体）——极简单条款

**要点**：BSD 1-Clause 仅保留“源码再分发须保留版权声明”一条；1990 年代 Berkeley Software Design（BSDi）使用（版权行“Copyright (c) 1995, 1999 Berkeley Software Design, Inc.”，出处挂靠：FreeBSD svnweb ifaddrs.h，见本节史料）；2019-12-10 Pedro Giffuni 在 FreeBSD 代码树 ifaddrs.h 中发现并向 OSI 提交；**2020-03-13 OSI 董事会批准**（Pamela Chestek 确认）。

**史料**：OSI License-review 邮件列表（2020-04 提交记录，Pamela Chestek 批准确认）；SPDX `BSD-1-Clause`；FreeBSD svnweb ifaddrs.h ［A］

**史观**：总纲第 13 条——法律与道德是利益分配：1-Clause 是 BSD 简化方向的极致化

**辨析**：1-Clause 与 0BSD 的区别——1-Clause 仍要求保留版权声明，0BSD 完全不要求 [考据完成：2026-08-04]

**文献**：OSI License-review 邮件列表；SPDX；FreeBSD 源码 ［A］

## 282.7.5 0BSD（Zero-Clause BSD）——零条款与公共领域等价

**要点**：0BSD 零条款（仅保留许可证名称与免责声明）；2011 年 Rob Landley 将 Toybox 自 GPLv2 转 OpenBSD 模板许可（ISC 衍生），2013 年简化为公共领域等价许可，2013-10 获 Kirk McKusick 许可命名 “Zero Clause BSD”（Ohio LinuxFest 45 周年 UNIX 庆典）；2014-12 并入 Android 6.0 Marshmallow；2015 年 SPDX 授予 0BSD 标识，OSI 批准。

**史料**：Rob Landley OSI 邮件列表一手时间线（2021-04/2024-01）；landley.net/toybox/license.html；SPDX `0BSD`；LWN 2015 Android 合并报道 ［A］

**史观**：总纲第 13 条——法律与道德是利益分配：0BSD 是 BSD 哲学的极致化（零义务），也是嵌入式 BSD 工具替代（Toybox vs BusyBox）的许可证标志

**辨析**：0BSD 双归属——语义上近 permissive（BSD 家族、SPDX 归 BSD 系）但严格说是“零义务”公共领域等价，建议作双归属说明；Rob Landley 明确 0BSD 源自 ISC 而非 BSD 4-Clause（获 McKusick 许可才归 BSD 家族） [考据完成：2026-08-04]

**文献**：Rob Landley OSI 邮件列表；SPDX `0BSD`；Toybox 官网 ［A］

## 282.7.6 BSD 机构变体（BSD-4-Clause-UC、BSD-3-Clause-LBNL 等）

**要点**：SPDX License List 收录多个 BSD 机构变体——BSD-4-Clause-UC（加州大学原始变体）、BSD-3-Clause-LBNL（劳伦斯伯克利国家实验室变体，含核设施免责条款）等；各变体在标准条款基础上定制免责声明或附加条款。

**史料**：SPDX License List 各变体条目 ［A］

**辨析**：机构变体的多样性反映 BSD 许可证作为“家族”而非单一文本的性质 [考据完成：2026-08-04]

## 282.7.7 当事人素材与叙述章——BSD 许可证文本在 Linux 内核中的逐版考据（1994–2025）

广告条款时代（BSD-4-Clause）在 Linux 内核中留存的最后一处痕迹由 Paul Mackerras 于 2004 年前后启动的清理工作揭出——`the license on include/linux/if_ppp.h is the old BSD-style license with advertising clause`，补丁将代码移至新文件并转移版权，是内核清理 4-Clause BSD 遗留的直接记录；而 William Hoskins 于 1999-07-22 代表 UC Berkeley Office of Technology Licensing 发布公告、立即废除广告条款的第 3 条，是 BSD 与 GPL 生态利益兼容的关键转折点——公告抬头 `To All Licensees, Distributors of Any Version of BSD`，签署人为 Director of OTL，公告即刻生效，是 BSD 许可证史上最具戏剧性的条款变迁之一

Tony Finch 更早以 unix.bsd.misc 邮件指出 BSD 许可之广告条款为 GPL 所不容、二者之码不得相并，是 BSD 4-Clause 时代与 GPL 阵营互斥的一手现场记录；altq HFSC 移植许可协商（2004-01-26，DSLXC-14842/16802）构成广告条款废除后 BSD-3-Clause 与 GPL 相容性的一次实证——Patrick McHardy 将 NetBSD altq HFSC 移植入 Linux 时提出许可问题，Jamal Hadi Salim 回复称这可能是 `the most contentious issue`，`given the SCO situation` 并要求 `written consent from the original authors`，而原作者方回复 `they removed the advertising clause, but they did not want to release the code under the GPL`；altq 版本最终以 `a BSD-style License without advertising clause` 形态入树，因内含少量 GPL 代码故定为纯 GPL 而非双许可，David S. Miller 亲自主持处理 BSD 授权代码的转换，要求取得原作者书面同意以转为纯 GPL，是 BSD 风格授权进入内核前的许可治理实例

2010 年前后 Linux 网络栈的 PMTU 与 tcp_sequence 代码中仍可见 BSD-4.2 兼容负担——David Miller 直接引用已被删除的内核 guard `BSD 4.2 derived systems incorrectly adjust` `tot_len by the IP header length, and report`，并拒绝为这类主机妥协；同一人亦报告 `there are still some Windows 2000 machines out there emitting` `BSD 4.2 style keepalives (one garbage byte instead of an empty out-of-window probe frame)`，一个 1990 年代的 BSD 行为在 2010 年仍约束 Linux tcp_sequence()——这是 BSD-4-Clause 时代在协议栈层的隐性延续

2015-07-31 Christoph Lameter 在 ksummit 上报告近期 Linux 内核中出现的许可变更——`a couple of license changes recently from GPL to a GPL-or-BSD choice in the infiniband stack`，并追问 `What exactly qualifies to be a copyright holder?`——这是 BSD-3-Clause 作为 GPL 的可选项在 Linux 中被制度化的早期证据；同期 Jiri Slaby 在 ath5k 移植中说明 base.c 进入公有领域后以 `dual-licensed under 3-clause-BSD and GPL` 形态发布，是 BSD 无线驱动谱系在 Linux 内核中双许可化的又一直接记录

libbpf 双重许可（2019-2020，DSLXC-16073/16948）是 BSD-2-Clause 进入 Linux 用户态库的标志性事件——Alexei Starovoitov 提出 `relicense libbpf as dual license LGPL-2.1 or BSD-2-Clause, since BSD-2 is compatible with Apache2`，Daniel Borkmann `Applied` 收尾，Greg KH 表态 `I've already ACKed this, and is fine with (LGPL-2.1 OR BSD-2-Clause)`，目的是让 bcc、bpftrace、gobpf、Cilium 等 Apache2 项目可合法依赖 libbpf——Andrii Nakryiko 在 bpf_helpers.h 与 bpf_endian.h 上延续 `we need them to be dual-licensed as LGPL-2.1 OR BSD-2-Clause` 的做法，把 BPF 公共 API 头文件从 selftests 树释放到 libbpf 内；同期 stmmac IEEE 802.1Qbv 补丁声明 `This file is targeted for dual licensing which is GPL-2.0 OR BSD-3-Clause`，Andrew Lunn 反问双许可是否真需要封装并追问理由，是 BSD-3-Clause 在内核驱动层落地成本的现场讨论

SGX 加密计算补丁审查（2020-10，DSLXC-15087/15160）暴露 BSD-3-Clause 与 GPL-only 头文件混合许可的现场争议——Greg Kroah-Hartman 与 Christoph Hellwig 对同一文件提出几乎相同的问题：`you use gpl-only header files in this file, so how in the world can it be bsd-3 licensed?`，Greg KH 要求作者先由法务部门确认混合 GPLv2-only 代码的做法，Hellwig 仅要求把 SPDX 之外的斜杠注释去掉而未就许可冲突本身展开论证——这是 BSD-3-Clause 作为 GPL-2.0 双重许可进入 Linux 内核主线的现场许可审查

设备树绑定双许可制度确立（2020-04-07，DSLXC-15412/14888）——Lubomir Rintel 提交 checkpatch 补丁要求 DT 绑定文档 `licensed (GPL-2.0-only OR BSD-2-Clause)`，Andrew Morton 补充 checkpatch.pl 新增 BSD-2-Clause 的 SPDX 正则匹配与 WARN，Laurent Pinchart 认为 preferable 措辞过弱应改为 shall；BSD-2-Clause 由此明文写入内核官方文档许可治理，成为 DT 绑定层的标准双许可模式——2021 年前后 Renesas rzn1-a5psw、Ti bluetooth、X-Powers AC200 MFD、Marvell Armada 7K/8K pinctrl 等 YAML 绑定文件相继写入 `SPDX-License-Identifier: (GPL-2.0-only OR BSD-2-Clause)`，Conor Dooley 更在 TI dp8386x 讨论中反问 `What's wrong with BSD-2-Clause, the standard dual license for bindings, why not use that?`，Rob Herring 附和——BSD-2-Clause 在绑定文档层的制度化由此完成

libbpf 与 bpftool 内部则延续 `LGPL-2.1 OR BSD-2-Clause` 的宽松许可策略，Cloudflare 亦把生产级 L4 负载均衡代码以 `dual GPL-2.0 or BSD 3-clause terms` 开放；Greg Kroah-Hartman 在 sysfs 测试驱动上坚持 `one of the compatible GPL variants and alternatively under a permissive license like BSD, MIT etc.` 是 Documentation/process/license-rules.rst 允许的第二许可形式；Thomas Gleixner 在 selftests 争议中反驳 Greg KH 的排他主张，指出 `we have enough code in the kernel which is licensed MIT/BSD` 且能正常调用 GPL-v2-only API，Greg KH 在 ethsw 系列上则以 `Remember, BSD is not the license you want` 明确劝退暴露用户空间的 GPL 头文件采用 BSD

UDF SPDX 转换（2023-05-22/30，Bagas Sanjaya，DSLXC-16864/16865/17086/17092）暴露 BSD 家族内部非标准变体的分类困难——`fs/udf/ecma_167.h` 使用了一种无法用 SPDX 标识符表达的 BSD 变体：`The latter file apparently looks like 2-clause BSD Source-Code license, yet the second clause is from third clause of 3-Clause BSD`；该文件被排除在转换之外，是 BSD 许可证文本在 Linux 内核树中的遗留与分类实例；同期 selftests/exec 目录中 SPDX 标识符判读争议亦把 OpenBSD 许可与 ISC 许可严格区分，作者比对 Linux 树内 LICENSES 目录后询问正确的 SPDX 标识符，确认 `The license is OpenBSD, not ISC`——BSD 家族内部各机构变体（OpenBSD、ISC、BSD-2/3-Clause 及其混合）在 SPDX 治理下的边界争议由此暴露

zerocopy crate 引入 Rust for Linux（Miguel Ojeda，DSLXC-11846）把 BSD-2-Clause 作为 Apache-2.0 与 MIT 之外的第三重许可选项带入 Linux 内核的 Rust 子系统——Miguel 向 Linus Torvalds 提交 Rust for Linux v7.2 合并请求，`zerocopy 以 BSD-2-Clause 或 Apache-2.0 或 MIT 三重许可授权，导入时基本保持原样仅需增删数行适配`，展示了 Rust 内核子系统引入非 GPL 许可 crate 的许可决策与依赖管理实践；Sparc Linux 邮件列表中 James Bottomley 更进一步讨论 `GPL with additional rights` 表达 BSD 模块的可行性，指出与内核结合的派生作品总是 GPLv2、BSD 模块需用 `GPL with additional rights` 表示以防许可滥用——BSD 与 GPL 组合在模块层与内核层的许可归属由此得到细化

综上，BSD 许可证家族从广告条款时代的 BSD-4-Clause 经 Hoskins 公告后的 BSD-3-Clause、BSD-2-Clause、BSD-1-Clause 乃至 0BSD 逐版简化，每一版差异本质都是利益分配机制的调整；进入 SPDX 时代后 BSD-2-Clause 与 BSD-3-Clause 在 Linux 内核内部分化出清晰分工——前者主要作为 DT 绑定的标准双许可选项，后者广泛用于 NXP SJA1105、WireGuard netlink、QED/qede 等 BSD-3 家族硬件与工具代码；BSD-1-Clause 由 Pedro Giffuni 2019-12-10 在 FreeBSD 代码树 ifaddrs.h 中发现并送 OSI，2020-03-13 OSI 董事会批准；0BSD 由 Rob Landley 2013 年由 Toybox 简化而来、2013-10 得 Kirk McKusick 命名许可、2014-12 并入 Android 6.0 Marshmallow、2015 年 SPDX 授予标识；而 BSD 家族内部的非标准混合变体（如 UDF ecma_167.h 混合 2-Clause 与 3-Clause 第三条）仍暴露出 BSD 许可证文本在 Linux 内核中残留的分类与合规缺口

## 282.7.8 SPDX 时代 BSD 许可证的分类与合规缺口（续 282.7.7，2020–2025）

进入 SPDX 时代后，BSD 许可证家族在 Linux 内核中的具体版本并非静态文本，而是逐条被重新判定与清理。2020-04 的 libbpf 事件是 BSD-2-Clause 进入内核用户态库的一次标志性谈判——Alexei Starovoitov 以 `relicense libbpf as dual license LGPL-2.1 or BSD-2-Clause, since BSD-2 is compatible with Apache2` 提出重许可方案，Daniel Borkmann 以 `Applied` 合入，Greg KH 表态 `I've already ACKed this, and is fine with (LGPL-2.1 OR BSD-2-Clause)`；其动机是允许 bcc、bpftrace、gobpf、Cilium 等 Apache-2.0 项目合法依赖 libbpf，Andrii Nakryiko 更把 `bpf_helpers.h` 与 `bpf_endian.h` 一并改成 `LGPL-2.1 OR BSD-2-Clause` 以便随 libbpf 分发——BSD-2-Clause 由纯 FreeBSD 内部许可证转成 Linux 与 Apache 阵营之间的许可桥梁，是 BSD 系列版本在 SPDX 时代最典型的语义漂移

同期 SGX 驱动审查则暴露 BSD-3-Clause 与 GPL-only 头文件混合的合规红线——Greg Kroah-Hartman 在 Intel SGX 加密计算补丁上直接质问 Christoph Hellwig 的 SPDX 声明：`You use gpl-only header files in this file, so how in the world can it be bsd-3 licensed?`，要求作者先由法务确认混合 GPLv2-only 代码的做法；这是 BSD-3-Clause 作为双许可在 Linux 主线入库时受拷问的一次现场记录，与 282.7.1 时代广告条款被废除的"许可简化"叙事形成鲜明对照——SPDX 化时代的问题不再是删除条款，而是判定条款组合是否被 SPDX 正则接受

2020-04-07 的 checkpatch 补丁把 BSD-2-Clause 写入内核官方文档治理——Lubomir Rintel 提交 `check proper licensing of Devicetree bindings`，Andrew Morton 合入并补充 `checkpatch.pl` 中 BSD-2-Clause 的 SPDX 正则匹配与 WARN，Laurent Pinchart 认为 `preferable` 措辞过弱应改为 `shall`；此后 Renesas `rzn1-a5psw.yaml`、Ti bluetooth、X-Powers `ac200`、Marvell Armada 7K/8K pinctrl、Renesas `ethertsn.yaml` 等 YAML 绑定文件相继以 `SPDX-License-Identifier: (GPL-2.0-only OR BSD-2-Clause)` 落地，Conor Dooley 在 TI dp8386x PHY 头文件争议中反问 `What's wrong with BSD-2-Clause, the standard dual license for bindings, why not use that?`，Rob Herring 附和——BSD-2-Clause 在设备树绑定层的"标准双许可"身份由此制度化，但 Stephen Hemminger 的 iproute2 全库 SPDX 清理又给出反面证据：`tc: replace GPL-BSD boilerplate in codel and fq` 表明 BSD-3-Clause 与 GPL 双许可在内核用户态工具中同样存在，且需要 `There is no change in licensing here, and none is planned` 的显式声明才能被接受，是 BSD 系列条款在内核工具链与内核树之间的双向扩散

真正暴露 BSD 家族内部非标准混合变体的是 2023-05 的 UDF SPDX 转换——Bagas Sanjaya 在 `fs/udf/ecma_167.h` 上直接判定：`The latter file apparently looks like 2-clause BSD Source-Code license, yet the second clause is from third clause of 3-Clause BSD`，因此该文件被排除在转换范围外；这一判定意味着 BSD-2-Clause 与 BSD-3-Clause 之间的"版本差异"在 Linux 树中曾以物理混合形态存在，无法被 SPDX 单一标识符表达；同期 selftests/exec 目录里的 SPDX 判读争议进一步区分子类——作者比对 Linux 树内 LICENSES 目录后确认 `The license is OpenBSD, not ISC`，说明 OpenBSD、ISC、BSD-2/3-Clause 虽在概念上同源，但在 SPDX 标识符层面必须严格分立；man-pages 项目内的 VERBATIM 许可证谱系（1994 年 9 月首次出现于 man-pages-1.4，作者 Rik Faith）与 Colomar 的 `string_copying(7)` 页面采用 `BSD-3-Clause for the string_copying(7) page` 并存于同一仓库，构成 BSD-3-Clause 作为通用宽松许可进入非内核 Linux 文档生态的旁证

综合 SPDX 时代十余年邮件列表史料，BSD 系列版本在 Linux 内核中的实际地位呈现三层分化：BSD-2-Clause 主要承担与 Apache-2.0 兼容的用户态桥梁（libbpf、bpftool）与设备树绑定标准双许可，BSD-3-Clause 承担硬件厂商代码与网络工具的宽松侧（NXP SJA1105、WireGuard netlink、QED/qede、codel/fq），而非标准混合变体（UDF ecma_167.h）与 BSD-1-Clause 变体则持续暴露分类缺口——这与 282.7.1–282.7.6 的"逐版简化"文本史互为映射：广告条款被删之后，条款的"数量"简化了，但条款的"分布"在 Linux 生态内反而复杂化，是 BSD 许可证家族从"单文本"演化为"版本群"在工程化治理中的最终形态



## 282.7.9 时间序列总叙述——从 2004 年 altq HFSC 到 2026 年 SPDX 标识的 BSD 逐版实证链

本叙述章按 186 条 ROW_MINE 锚点提取的邮件日期对 BSD 全系版本的当事人证据作一次时间串联，把散落于 netdev、linux-fsdevel、linux-mm、linux-man、linux-arch、linux-scsi、linux-api、rust-for-linux、sparclinux、ksummit 十个列表的一手表态编织成一条从 2004 到 2026 的连贯实证链——

链条起点落在 2004 年 1 月 26 日，Patrick McHardy 把 NetBSD altq 的层次化流调度器移植入 Linux 2.6 时，在提交说明中专门处理许可证问题，自述 `The altq version is released under a BSD-style License without advertising clause (the original authors kindly agreed to remove it)`，并因代码含少量 GPL 代码而定为 GPL 而非 Dual BSD/GPL；Jamal Hadi Salim 当即称这可能是 `the most contentious issue`、`given the SCO situation` 并索取 `written consent from the original authors`，David S. Miller 亲自主持要求取得原作者书面同意以转为纯 GPL——广告条款废除五年后，BSD-3-Clause 血统代码入树仍须版权人书面授权，是 BSD 谱系进入 Linux 的第一道治理闸门；同期 ath5k 移植中 Jiri Slaby 说明 base.c 进入公有领域后以 `dual-licensed under 3-clause-BSD and GPL` 发布，Miklos Szeredi 合入 UFS 补丁系列时其前置补丁名为 `add-in-sunos-41x-compatible-mode-for-ufs.patch`，SunOS 4.1.x 的 BSD-4.1 血统由此与 UFS 驱动对齐；2007 年 10 月 shadow directories 讨论中 David Newall 援引 FreeBSD 手册 `See link(2) for 2.10BSD` 论证目录硬链接，Al Viro 转述 `The claim is wrong` 的驳斥被 Jan Engelhardt 以 `But hell will break lose if you allow hardlinking directories` 终结——BSD 权威文档在此作为 VFS 设计取舍的论据被直接援引，是 BSD 血统在文件系统层以语义对齐而非许可冲突形态延续的现场记录——

2010 年 David Miller 报告 `there are still some Windows 2000 machines out there emitting` `BSD 4.2 style keepalives (one garbage byte instead of an empty out-of-window probe frame)`，一个 1990 年代的 BSD 行为仍约束 Linux tcp_sequence()；2012 年 3 月 Paul Mackerras 清理 `the license on include/linux/if_ppp.h is the old BSD-style license with advertising clause`，把代码移入新文件并转移自己的版权，David Miller 合入，是内核清理 BSD-4-Clause 遗留的直接记录；2015 年 7 月 31 日 Christoph Lameter 在 ksummit 报告 `a couple of license changes recently from GPL to a GPL-or-BSD choice in the infiniband stack` 并追问 `What exactly qualifies to be a copyright holder?`——BSD-3-Clause 作为 GPL 可选项在内核中被制度化的早期证据由此落地——

2017 至 2020 年是 BSD-2-Clause 进入内核治理层的分水岭；2017 年 11 月 Cyril Hrubis 借 unix-history-repo 考据 mmap，指出首个 mmap 出现在 `BSD-4_2-Snapshot` 且当时并无 MAP_FIXED，首个支持 MAP_FIXED 的实现是 BSD-4.3_Reno 快照，早期 BSD 代码库还留有兼容 HPUX 的 HPUXMAP_FIXED 与 HPUXMAP_REPLACE；Philippe Ombredanne 反对 nds32 移植逐行 GNU GPL 法律声明，要求 `Have you considered using the new SPDX ids instead of this fine legalese`；2018 年 9 月 Jakub Kicinski 提议 `Could we possibly make it dual licensed LGPL + BSD?`，随后 Alexei Starovoitov 正式提出 `relicense libbpf as dual license LGPL-2.1 or BSD-2-Clause, since BSD-2 is compatible with Apache2`，Daniel Borkmann 以 `Applied` 合入，Greg KH 表态 `I've already ACKed this, and is fine with (LGPL-2.1 OR BSD-2-Clause)`，Andrii Nakryiko 更把 bpf_helpers.h 与 bpf_endian.h 改成 `we need them to be dual-licensed as LGPL-2.1 OR BSD-2-Clause` 以便随 libbpf 分发——BSD-2-Clause 由 FreeBSD 内部许可证转为 Linux 与 Apache 阵营之间的许可桥梁；2019 年 2 月 Boaz Harrosh 就 ZUF 文件系统主张共享 API 头以 BSD-3-Clause 授权以便在 macOS 与 Windows 上编译 ZUS 用户态服务端，Greg KH 反问 `You are asking legal questions to a technical person?` 并改用 SPDX 表述；2019 年 11 月 Thomas Gleixner 就 LRNG 补丁要求移除冗余 BSD 免责声明以避免许可证扫描误报，标识定为 `GPL-2.0 OR BSD-2-Clause`；2020 年 4 月 7 日 Lubomir Rintel 的 checkpatch 补丁把 `DT binding documents should be licensed (GPL-2.0-only OR BSD-2-Clause)` 写入内核官方文档许可治理，Andrew Morton 补充 checkpatch.pl 中 BSD-2-Clause 的 SPDX 正则匹配与 WARN，Laurent Pinchart 认为 `preferrably` 措辞过弱应改为 `shall`；同期 Greg Kroah-Hartman 与 Christoph Hellwig 就 Intel SGX 飞地驱动提出几乎相同的质问 `You use gpl-only header files in this file, so how in the world can it be bsd-3 licensed?`，要求作者先由法务部门确认混合 GPLv2-only 代码的做法——SPDX 时代的问题不再是删除条款，而是判定条款组合是否被正则接受——

2020 至 2023 年暴露 BSD 家族内部的分类缺口；Peter Zijlstra 引入 moodycamel lock-free freelist 时以 `GPL-2.0-only OR BSD-2-Clause` 双许可，Cameron 回答 `both GPLv2 and BSD-2 (my personal favourite) are fine`；2023 年 5 月 Bagas Sanjaya 的 UDF SPDX 转换跳过 `fs/udf/ecma_167.h`，因其 `apparently looks like 2-clause BSD Source-Code license, yet the second clause is from third clause of 3-Clause BSD`，该自定义许可无法用 SPDX 标识符表达；同期 selftests/exec 目录确认 `The license is OpenBSD, not ISC`，说明 OpenBSD、ISC、BSD-2/3-Clause 虽在概念上同源却在 SPDX 标识符层面必须严格分立；Linux 网络栈侧 Alexander Lobakin 为 QLogic qed/qede 修正错误 SPDX 标签并声明 `QLogic QED drivers source code is dual licensed under GPL-2.0/BSD-3-Clause`，Cloudflare 把生产级 L4 负载均衡代码以 `dual GPL-2.0 or BSD 3-clause terms` 开放；man-pages 的 SPDX 复核把 VERBATIM 谱系一并摆上台面——Andries E. Brouwer 追溯出该文本由 Rik Faith 于 1994 年 9 月 man-pages-1.4 首次发布，VERBATIM_TWO_PARA 首现于 2008 年 3.07 的 move_pages.2 却挂着 `Copyright (C) 2006 Silicon Graphics, Inc. Christoph Lameter` 被 Fedora 判为非自由，Lameter 反驳 `The licensing was GPL and not a proprietary one`；Alejandro Colomar 为 string_copying(7) 选择 `BSD-3-Clause` 并说明 `I'd like it to be as widespread as possible`——BSD-3-Clause 作为通用宽松许可进入非内核 Linux 文档生态——

2022 至 2026 年 BSD 双许可在设备树绑定与 Rust for Linux 层全面扩散；Miguel Ojeda 引入 zerocopy crate 时其以 BSD-2-Clause 或 Apache-2.0 或 MIT 三重许可授权，导入时基本保持原样仅需增删数行适配；Asahi Lina 反驳双许可在内核中棘手的说法，称大量驱动与 DRM 核心本身双许可、全树约十分之一文件采用双许可，且 FreeBSD 已在宽松许可下直接使用了一大块 Linux DRM 代码；James Bottomley 更进一步提出 BSD 模块需用 `GPL with additional rights` 表示，因与内核结合的派生作品总是 GPLv2；Renesas RZ/N1、R-Car UFS、X-Powers AC200、qcom ppe、ethertsn、hyperv vmbus 等 YAML 绑定相继以 `(GPL-2.0-only OR BSD-2-Clause)` 落地，Krzysztof Kozlowski 就 AT91 重许可提醒 `You need all contributors to ack this...`；2024 年 5 月 dp8386x PHY 头文件之争中 Conor Dooley 反问 `What's wrong with BSD-2-Clause, the standard dual license for bindings, why not use that?`，Rob Herring 附和并指出该许可利于 Zephyr 与 FreeBSD 生态复用；同期 Greg KH 对 TIPC 全库 `GPL-2.0 OR BSD-3-Clause` 补标回问 `The original license of TIPC is GPL-2.0. Why do you think it should be dual licensing now`，Thomas Gleixner 则在 selftests 争议中反驳 Greg KH 的排他主张，指出 `we have enough code in the kernel which is licensed MIT/BSD` 且能正常调用 GPL-v2-only API；2023 年 ynl netlink 生成代码统一为 `GPL-2.0 OR BSD-3-Clause`，作者自述原本 `I was intending to make all the Netlink Spec code BSD-3-Clause to ease the adoption` 却因内核普遍预期 GPL 而改为双许可；2025 至 2026 年 wireguard netlink 生成代码采用 `((GPL-2.0 WITH Linux-syscall-note) OR BSD-3-Clause)`，tcp_bbr 自引入以来笼统的 `Dual BSD/GPL` 模块字符串被修正为标准 `GPL-2.0 OR BSD-3-Clause`，util-linux v2.39.3 公告中混入 `add DragonFlyBSD GPT partition types` 标志用户态工具正式吸收 BSD 生态分区标识——

贯穿二十二年的四条主线由此清晰可辨：一是 BSD-4-Clause 的广告条款在 1999 年 Hoskins 公告后被彻底清除，但其语义影响以 BSD 4.2、2.10BSD、BSD-4.3_Reno 的考据形态延续至 2017 年；二是 BSD-2-Clause 完成从 FreeBSD 内部许可证到 Linux 与 Apache 阵营许可桥梁的语义漂移，并在设备树绑定层获得标准双许可身份；三是 BSD-3-Clause 承担硬件厂商代码、网络工具与 netlink 生成代码的宽松侧，但与 GPL-only 头文件混合的红线须由法务签字而非工程判断划定；四是 BSD 家族内部的机构变体——OpenBSD、ISC、VERBATIM_TWO_PARA、UDF ecma_167.h 的 2-Clause 与 3-Clause 混合体——在 SPDX 单一标识符体系下持续暴露分类缺口——BSD 版本的迭代并不是条款的线性简化，而是许可证文本在 Linux 生态分层治理压力下的分布式响应——

**要点**：

- PCC 几乎就是原初的 UNIX C 编译器，主要由 Stephen Johnson 写作，是 1970 年代中后期首个真正可重定目标的编译器；其可移植性设计是当年 UNIX 取得巨大成功的原因之一。该编译器原为 AT&T 授权，直到 2001-2002 年 Caldera 以 BSD 许可证发布后才为公众可得。（BSDTalk EP131，[50.43-92.48]，L1）
- Ragge 复兴 PCC 的偶然路径：他出于对奇异计算机架构的兴趣写过 NetBSD 的 VAX 移植，后受托把 GCC 移植到 PDP-10，却发现 GCC 充满 bug、难以驾驭且远不能为该架构生成合理代码；适逢 Caldera 开放旧 PCC，他判断 1970 年代为奇异架构所写的编译器更易移植，遂将 PCC 移植到 PDP-10 并用它编译 NetBSD 的 PDP-10 版，自 2002 年起作为业余项目持续约五年。（BSDTalk EP131，[102.23-172.27]，L1）
- 工程目标是将这个三十年老编译器改造成小型、可理解、C99 兼容的编译器；已重写寄存器分配器（他自评属当今最佳实现之列），编译器可自举，但开发期间用 GCC 编译 PCC 以免落入自己造成的 bug；当前版本内置大量内部一致性检查以验证生成代码的正确性。（BSDTalk EP131，[174.79-333.31]，L1）
- 性能画像：编译速度约为 GCC 的 10 至 15 倍（同一台机器编译 NetBSD 全源码 GCC 约十小时而 PCC 略超两小时）；生成代码执行速度目前比 GCC 慢 10-20%，但在长整型需双寄存器的 Intel 场景其寄存器分配优于 GCC 3。（BSDTalk EP131，[247.43-362.83]，L1）
- 架构与语言扩展：已有 i386、MIPS、PDP-10 支持（i386 移植仅两天，两小时打出 hello world），PDP-11 与 VAX 旧移植约一天可复活，HPPA 进行中、ARM32 有人启动；PCC 天生前后端分离——语言相关前端经良定义中间格式对接目标相关后端，从旧 BSD 源码复原的 Fortran 77 前端已可直接复用其后端与优化，C++ 前端因日常工作无暇，RISC 所需的延迟加载类交错指令处理尚待补齐。（BSDTalk EP131，[264.59-414.28]，L1）
- 采纳过程：一封宣告邮件引发远超预期的兴趣，OpenBSD 人在数小时内决定将其引入基础系统，NetBSD 导入主源码树，DragonFly BSD 与 MirOS BSD 有人跟进移植；Red Hat 为 Fedora 制作软件包但因许可证条款不能进入主分发版；项目基础设施（网页、wiki、源码树、邮件列表）依托吕勒奥理工大学机房一台旧机器搭建。（BSDTalk EP131，[410.59-631.76]，L1）
- 许可证细节：Caldera 以四条款 BSD 许可证（含广告条款）发布 PCC——随其他产品分发该编译器须在全部广告材料中标注 Caldera 版权；广告条款在 1980 年代即构成使用旧 BSD 代码的实际障碍，现代 BSD 已改用三条款或更少；Red Hat 因无法在主分发版履行广告义务而将 PCC 挪入收录此类许可证软件的独立源码仓库。（BSDTalk EP131，[481.72-550.73]，L1）
- 动机演变与版本策略：Ragge 自承最初并不特别在意许可证（本人即 BSD 用户），只是想让真正的 BSD C 编译器复活；但随着 GPLv3 即将问世且许多人对之不满，BSD 许可证对大量潜在使用者变得极重要；其发布策略为先冻结新开发、打磨 1.0 稳定基线供人编译真实软件，之后再加优化与清理。（BSDTalk EP131，[631.76-767.15]，L1）

**史料**：
