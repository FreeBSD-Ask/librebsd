**要点**：

- TiddlyWiki 的独特设计：传统 wiki 是架设于 web 服务器的网站、内容分页、点链接跳转新页；TiddlyWiki 则把信息块（作者自嘲起名不当的 tiddlers）呈现在单个页面内、随阅读动态开合，相当于微型 wiki。其整体存在于单个 HTML 文件之中，可如 Word 文档般拷入 U 盘、邮件传送、双击即在浏览器中打开并就地编辑、保存后写回磁盘；发布只需把文件拷上任意 web 服务器（如 Google Pages 账号即可），无需 PHP 或 Perl 扩展、也无需数据库后端。（BSDTalk EP24，[328.50-455.74]，L1）
- 游击 wiki 场景：基础设施需求薄如纸，使其可部署于无法架设真正 wiki 的场合——压制性政权之下，或大型跨国公司之内（IT 部门忙于安装本周的安全补丁，无暇为你建站）；任何人下载即可在本机运行，并在工作小组内分享，全程无需 IT 部门参与。（BSDTalk EP24，[459.54-512.06]，L1）
- 实现与规模：其行为层为 JavaScript——在浏览器中查看源码，开头三四千行 JavaScript 看上去与常规 C 代码相仿，内容打包于文件末尾的一小块 HTML；跨浏览器兼容是作者的祸根，浏览器间差异细小而难查，Internet Explorer 与其他所有浏览器做法不同，Firefox 与 Safari 则可互通。可扩展性出人意料：许多用户的单文件已达 1.5 MB 左右（约 200 KB 为 JavaScript 代码、其余 1.2 MB 为用户内容，相当于几本书），而性能上限来自浏览器——浏览器 JavaScript 原为图片翻转之类小把戏而设计，此项目是在掰弯浏览器。（BSDTalk EP24，[512.06-657.50]，L1）
- 许可证演变：初版仅作实验发布、未细想许可证，恰逢 Creative Commons 刚上线且当时受关注的作品多用 CC，遂采用允许共享但为自己保留商业权利的 CC 版本（心底想着或许能商业开发）；收到的普遍反馈是 CC 是内容许可证而非代码许可证（当事人不认为必然如此，但反馈之多促使复核）；两三封论证有力的来信指出非商业条款的麻烦——排除商业使用几乎等于排除一切有意思的再利用。作者的目标是让人尽可能多地使用、谈论与思考它，不愿设任何门槛；粗查发现 BSD 许可证短到能读懂、足够开放；且 TiddlyWiki 是开源更是暴露源——查看源码即见全部、不过一个文本文件、无从保护，索性把限制化为优点，选一个能找到的最友好开放的许可证。（BSDTalk EP24，[662.22-815.66]，L1）
- Wiki 词源与理念背景（当事人转述）：WikiWiki 为夏威夷语之快，夏威夷公交车上即写有 wiki wiki；Ward Cunningham 发明 wiki-wiki web 时寻找形容其编辑之快的词，其核心洞见是协作场景中最难的是促使人贡献，故把编辑门槛降到最低——任何人可编辑任何页并保存；直觉上似在纵容破坏，但在重要的社区场景中社区能自我调节保持内容切题有用，Wikipedia 为经典例；wiki 使链接如标点般轻易，camel case 规则令大写开头的复合词自动成为链接。（BSDTalk EP24，[155.00-323.74]，L2）
- YUI 库源于约一年半前 Yahoo 内部的平台化倡议：将分散的前端开发整合为平台工程，集中代码库以鼓励复用与一致性、在各产品组间标准化；作为发布激励，Yahoo 公开原始源码与完整 API 文档，并分享应对各浏览器开发怪癖的经验，供撞过同样墙壁的开发者复用。（BSDTalk EP33，[69.44-147.94]，L1）
- YUI 的结构分两组：utilities 为低层行为（拖放、浏览器事件、DOM 操作），已做跨浏览器差异均一化封装；widgets 为低层行为的复杂 UI 实现（组合框、日历控件、滑块、树视图等），旨在让 Web 应用超越 HTML 基本的文本框、下拉列表与单选钮，行为趋近桌面应用；其生产部署实例是改版后的 My Yahoo 首页，支持拖拽重排内容模块。（BSDTalk EP33，[182.66-347.46]，L1）
- 当事人阐述选择 BSD 许可证的动机：Yahoo 意图采取中立立场，以最易鼓励采纳、尽可能降低进入门槛为原则，希望开发者把代码用于任何自认为合适的应用与环境，BSD 许可证提供了其认定的最大使用灵活性；此为 2006 年大型互联网公司主动选用 BSD 许可证的直接决策陈述。（BSDTalk EP33，[363.46-406.06]，L1）
- Yahoo 的浏览器支持哲学是“体验连续体”：A 级浏览器为经测试可完整支持 YUI 的现代浏览器（IE6/7、Firefox 1.0.x 及以上、Safari 1.3+、Opera 8.5+，覆盖约 95% 入站流量），C 级为不具备能力的过时浏览器，X 级为未经主动测试的新兴或边缘浏览器；富组件须可降级——JavaScript 被禁用或 DOM 方法缺失时回退为 HTML 基本形态（富日历退化为表格日历加点击刷新模式），用户体验与设计组为此提供基线体验准则。（BSDTalk EP33，[418.98-616.52]，L1）
- 社区与开放路线：YUI 发布于 Yahoo Developer Network，已成为其 JavaScript 论坛（逾 1100 名成员）的主要流量来源；Yahoo 借此外部社区收集使用反馈、缺陷报告、修复建议与功能增强，并承诺将外部反馈纳入开发计划；下一步计划以某种匿名 CVS 形式托管代码以便更及时地响应补丁，并在适当时机开放外部贡献，5 月底前将依用户反馈新增组件。（BSDTalk EP33，[624.36-880.26]，L1）
- Enlightenment 的项目形态：E17 被作者定位为桌面 shell——窗口管理器承担管理 X 会话、启动与切换应用等传统职能并叠加部分桌面环境职能，但不捆绑全套应用；开发无资金与工时保障、全凭业余推进，故拒绝发布日期承诺，采用待办清单加里程碑的方法，版本号按序递进不跳级。（BSDTalk EP44，[65.00-135.36]，L1）
- 面向应用开发者的设施：项目提供 EWL 与 ETK 两个由成员独立开发的 widget 集（彼时尚属实验）；底层渲染工具包取结构性保留模式而非即时模式——创建对象、修改属性、对状态求值后自动完成重绘，widget 集因此远小于 GTK 或 QT；另有事件循环、配置与数据结构持久化、网络通信、IPC 包装、内存管理包装等配套库；Edje 主题引擎把高层 GUI 概念抽象进数据文件，让设计者深度主导界面形态，被比作 Flash、HTML、CSS 与 JavaScript 的混合体而专用于界面图形元素。（BSDTalk EP44，[223.80-378.64]，L1）
- 设计哲学的两面：其一为几乎一切可见元素皆可调校且无须改源码的极致灵活性；其二为反对把界面砍至最低公分母的笨化路线，信奉选项愈多愈好、难在呈现得当——新手不致迷惑而高级用户可图形化直达全部高级选项；工程上高度优化且库可按需拆用，E17 能运行于 Sharp Zaurus 掌上设备，相对特性量的内存与 CPU 足迹极低，惠及不愿为桌面环境付出数百兆内存的用户。（BSDTalk EP44，[383.02-508.50]，L1）
- 对 XGL 与 AIGLX 的技术辨析：XGL 是以 OpenGL 实现 X 驱动，AIGLX 则是让间接 GL 加速（经 X server 代理 3D 硬件），两者皆靠窗口像素图映射为 3D 纹理再由合成管理器出特效；Enlightenment 与二者无涉且视其为实验品——它们依赖高端 3D 卡与闭源驱动，在 BSD、Solaris 等系统上根本不可得，等于限制受众并限制自由；E 项目反其道而行，以纯软件客户端管线全速呈现柔和阴影等特效多年，可回溯兼容 1988 年以来的 X server，虽有 OpenGL 与 Xrender 后端，但前者欠稳定、后者驱动实现低效且慢于自家软件引擎，最终能在 200 或 100 MHz ARM 的无加速帧缓冲上以合理速度跑出同等效果。（BSDTalk EP44，[518.30-847.66]，L1）
- 网络行为特征：客户端渲染导致带宽占用偏高，但架构刻意避免往返请求——往返延迟才是 X 性能的真正杀手，故局域网表现良好；窄带接入（DSL 或调制解调器）则不适用，此类场景应改用 VNC 或 NX 等高压缩远程桌面方案。（BSDTalk EP44，[847.66-927.18]，L1）
- 作者的技术形成史：八岁始于学校 Commodore VIC-20 的彩色屏幕与随机 BASIC 手册，继于 C64 以 6502 机器码编写小型冒险游戏，Amiga 时代凭硬件手册以 68k 汇编直写芯片组寄存器构造游戏、图形与声音引擎；入大学后经 X 终端初遇 UNIX，因 MWM 之丑而学会配置窗口管理器并体认 Unix 极端可配置的哲学——用户改造系统以适己而非屈己适系统；为使用 Xlib 而自学 C，先改造 RXVT 得到可绘背景的 rxvt-xpm（后演化为 Eterm），再改 Fvwm 求渐变与纹理，终觉修补不能扩展而自零重写窗口管理器，Enlightenment 由此发端。（BSDTalk EP44，[1080.88-1376.84]，L1）
- AsiaBSDCon 定位为面向全 BSD 家族的技术会议，向 NetBSD、OpenBSD、FreeBSD、DragonFly 及 Mac OS X 等 BSD 系平台的使用者与建设者征集论文，2007 年 3 月 10 日至 13 日在东京举行为期四天；Hiroki Sato 任大会主席、George Neville-Neil 任程序委员会主席；主会期之外安排 BOF 与 FreeBSD Dev Summit，并计划全体晚宴；CFP 已发布，官网页面正由日本本地成员重新设计，会后即向各邮件列表广发通知。（BSDTalk EP74，[132.52-207.10]，L1）
- 办会模式与准入政策：AsiaBSDCon 各届由不同地区的团队接手、组织方式各异，上届于两年前在台湾举行并收取少量名义费用；本届延续低价原则，以让全亚洲各地参与者负担得起为约束，会场设在东京大学；是否固化为双年会尚未决定，取决于志愿者供给；会期附近无重叠的同类会议。（BSDTalk EP74，[239.14-333.34]，L1）
- 亚洲 BSD 生态的强度与成因：George Neville-Neil 与日本众多 BSD 开发者互动的总体印象是 Linux 与 BSD 在日本大致处于均势——商业领域 Linux 更流行，而开发者偏爱 BSD；日本 BSD 开发者众多的结构性原因在于嵌入式采用：打印机、电话机、小型便携 DVD 播放器等设备以 BSD 为底，直接把开发者基数做大；亚洲其他地区的 BSD 部署亦相当广泛。（BSDTalk EP74，[338.14-416.70]，L1）
- 许可证被点名为嵌入式采用的决定变量：设备制造商不愿公开源代码，而 GPL 强制公开，BSD 许可证因此在这类应用中通常胜出——操作系统在嵌入式商业场景的胜负手不是纯技术指标，而是源码披露义务所对应的利益结构。（BSDTalk EP74，[416.70-439.08]，L1）
- 文档本地化的双重困境：组织层面，翻译工作对普通开发者吸引力低，专职翻译团队覆盖约八种语言却并不活跃，成员多为用户而非开发者，招译者困难；德语与法语翻译最活跃，中文近期活跃但人手极少。技术层面，用户文档翻译尚可，而消息目录、内核消息与命令行消息的翻译构成硬障碍——翻译需要多种编码，但消息文本通常写死在源代码中，多编码方案无法进入源码。（BSDTalk EP74，[444.56-601.12]，L1）
- 两位当事人的个人使用图景：George Neville-Neil 纯 FreeBSD 阵营——网络与安全研究用的多台服务器、跑 6.1-stable 的生产邮件与 web 服务（6.2 即将发布）、跟踪 head 的实验机、内含大量 BSD 的 Mac 笔记本，此前供职于服务器普遍采用 FreeBSD 的大型互联网公司；Hiroki Sato 在大学维护实验室网络，以 OpenBSD 作为终端与科研仿真环境并为研究领域开发设备驱动，兼用 FreeBSD、NetBSD 及其他多种 Unix，收藏老式系统（含老 Linux 与 SunOS 4）是其爱好。（BSDTalk EP74，[620.00-745.52]，L1）

- turnstile 被称为整套锁机制得以运转的枢纽数据结构：由于一个线程同一时刻只能阻塞在一处，系统按线程而非按锁分配 turnstile（锁数量远多于线程数，每个进程表项自带数把互斥），阻塞线程把自身 turnstile 交给内核挂入等待链，锁释放时以回收的 turnstile 转交新持有者，从而以最小内存代价支撑优先级传播。（YouTube EPUfiTV9QWhM4，[1318.03-1513.5]，L1）[订正：原 [1318.03-1456.32]→[1318.03-1513.5]，"整套锁机制得以运转的枢纽数据结构"（Crux）实际口述于 [1504.9-1513.5] 段，内容复核]
- 优先级反转的解法是递归优先级传播：高优先级线程发现持锁者未在运行时让出处理器并把自身优先级授予对方，直至其释放锁后优先级“逐层冒泡”归还；演讲以柏林开往华沙的特快列车令沿线十四列普通客车停驶待行为喻。与之相对，睡眠队列类锁不做优先级传播，因为唤醒等待磁盘 IO 的进程并不能让 IO 更快完成。（YouTube EPUfiTV9QWhM4，[1042.559-1546.7]，L1）[订正：原 [1042.559-1148.08]→[1042.559-1546.7]，递归传播/逐层冒泡与睡眠队列不做优先级传播（磁盘 IO 理由）实际口述于 [1471.7-1546.7] 段，内容复核]
- 自适应阻塞互斥在释放时唤醒全部等待者而非逐个传递锁，理由是无竞争锁的释放只需一次赋值而遍历 turnstile 链代价更高；由于自适应自旋的存在，被唤醒者中只有持锁者真正在跑时才会竞争，故惊群代价可控。McKusick 同时警告该策略隐含互斥粒度足够细的前提——数百线程排队于一把互斥说明数据结构设计本身需要反思。（YouTube EPUfiTV9QWhM4，[2140.52-2233.32]，L1）
- 死锁避免采用锁类偏序：全部锁划入有序类别，线程在每类至多持有一把、只能向更高编号类申请；旧时代该规则仅靠源码注释人工维护，多线程化后锁数量爆炸，遂引入 witness 代码在启动阶段观察锁的实际获取顺序自动推断类别，程序员仅在推断错误时以少量显式定义纠正；残余的锁序反转（LOR）则提交专门的邮件列表集体会诊，网络栈因上下行双向数据流成为最难处理的领域。（YouTube EPUfiTV9QWhM4，[2958.4-3452.2]，L1）[订正：原 [2958.4-3416.52]→[2958.4-3452.2]，网络栈上下行双向数据流表述实际口述于 [3414.6-3452.2] 段，内容复核]
