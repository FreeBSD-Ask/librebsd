# 282.11 其余许可证逐个考据——MIT、Apache、MPL、EPL、CDDL、ISC、Artistic、zlib、BSL、SSPL、Unlicense、OpenSSL

> 本子节为 2026-08-04 许可证系统性考据工程新增。铁律：以下许可证须逐版本逐个考据（按 SPDX 标识），禁止合并表述、禁止以“宽松类”“copyleft 类”笼统带过。

## 281.11.1 MIT License 与 ISC License——极简宽松双雄

**要点**：**MIT**（SPDX：MIT）1980 年代起，仅版权声明+免责声明，与 BSD-2-Clause 实质等价；**ISC**（SPDX：ISC，Internet Systems Consortium License）2006 年前确立，极简许可，OpenBSD 默认采用；二者均为 permissive 的极简代表。

**史料**：OSI MIT/ISC 条目；SPDX License List `MIT`/`ISC`；OpenBSD 项目 COPYING 文件 ［A］

**史观**：总纲第 14 条——许可证约束：MIT/ISC 的极简与 BSD-2-Clause 一起构成 permissive 光谱的“最小义务”端。

**辨析**：MIT 与 BSD-2-Clause“实质等价”须逐条比对（条款语义近似但措辞不同，法律适用上可能因文本差异产生细微差别），不得预设完全等价；ISC 与 MIT/BSD-2 的文本差异（ISC 措辞更简）须辨析。

**文献**：OSI. MIT License [EB/OL]. <https://opensource.org/license/mit/；OSI>. ISC License [EB/OL]. <https://opensource.org/license/isc/；SPDX>. SPDX License List [EB/OL]. <https://spdx.org/licenses/> ［A］

## 281.11.2 Apache License 1.0/1.1/2.0——permissive 中“最重”

**要点**：**Apache-1.0**（1995）与 **Apache-1.1**（2000）为简单宽松许可；**Apache-2.0**（2004-01）为 permissive 中“最重”——§3 明示专利授权（明确专利许可，permissive 中罕见）、§4 保留版权/专利/商标声明、§7 终止条款；Apache 2.0 与 GPLv3 兼容。

**史料**：Apache Software Foundation 官方许可证文本（apache.org/licenses/）；OSI Apache-2.0 条目 ［A］

**史观**：总纲第 14 条——许可证约束：Apache-2.0 的专利授权条款是宽松许可证对专利时代的制度回应，与 BSD 2/3-Clause 的“零专利条款”形成对照。

**辨析**：Apache-1.1 与 2.0 的差异（专利授权、终止条款、声明保留）须逐条对照；Apache-2.0 与 GPLv3 兼容但非 GPLv2 兼容（因 GPLv2 无专利授权对应条款）须辨析。

**文献**：Apache Software Foundation. Licenses [EB/OL]. <https://www.apache.org/licenses/；OSI>. Apache License 2.0 [EB/OL]. <https://opensource.org/license/apache-2-0/> ［A］

## 281.11.3 MPL、EPL、CDDL——文件级弱 copyleft 三杰

**要点**：**MPL-1.0/1.1/2.0**（Mozilla Public License，1998/1999/2012）文件级 copyleft（弱 copyleft），MPL-2.0 与 Apache-2.0/GPL 兼容；**EPL-1.0/2.0**（Eclipse Public License，2004/2017）弱 copyleft，Eclipse 基金会采用；**CDDL-1.0**（Common Development and Distribution License，2004-12）Sun/OpenSolaris 采用，MPL-1.1 衍生，Oracle 收购 Sun 后 Solaris 闭源事件使其成为 BSD 史对照样本。

**史料**：Mozilla 官方 MPL 文本（mozilla.org/MPL/）；Eclipse Foundation EPL 文本（eclipse.org/legal/）；OSI CDDL 条目 ［A］

**史观**：总纲第 14 条——许可证约束：文件级 copyleft 是“传染边界”的制度折中——比 permissive 强、比 GPL 弱，传染范围限定于被修改文件。

**辨析**：MPL/EPL/CDDL 的“文件级 vs 整体级”传染边界差异须辨析（MPL 传染限被改文件，CDDL 同 MPL-1.1 模式但文本差异）；CDDL 与 GPL 不兼容导致 OpenSolaris 代码难以并入 GPL 生态，是 Solaris 闭源后社区续命的许可证障碍（详见 296 章 illumos）。

**文献**：Mozilla. Mozilla Public License [EB/OL]. <https://www.mozilla.org/MPL/；Eclipse> Foundation. Eclipse Public License [EB/OL]. <https://www.eclipse.org/legal/epl-2.0/；OSI>. CDDL-1.0 [EB/OL]. <https://opensource.org/license/cddl-1-0/> ［A］

## 281.11.4 Artistic License 1.0/2.0 与 zlib License

**要点**：**Artistic-1.0/2.0**（1987/2000）Perl 双许可的组成部分；**Jacobsen v. Katzer** 案涉 **Artistic-1.0**——联邦巡回上诉法院认定 Artistic License 条款创设版权条件（conditions），违反即构成版权侵权（535 F.3d 1373）；**zlib License**（1995）极简许可，zlib 压缩库采用。

**史料**：OSI Artistic-1.0/2.0 条目；zlib 官方 LICENSE；Jacobsen v. Katzer 判决书（535 F.3d 1373, Fed. Cir. 2008） ［A］

**史观**：总纲第 14 条——许可证约束：Artistic 的“灰色地位”（FSF 视 Artistic-2.0 为自由许可、OSI 认可，但其条款允许变通）使其成为弱 copyleft 灰区样本；Jacobsen 案是“许可条件=版权条件”的先例来源。

**辨析**：Artistic-1.0 与 2.0 差异须对照；Artistic 的“改个名就不开源”变通条款（Artistic 1.0 允许改名后非开源再分发）与 FSF/OSI 态度的张力须辨析。

**文献**：OSI. Artistic License 2.0 [EB/OL]. <https://opensource.org/license/artistic-2-0/；zlib>. zlib License [EB/OL]. <https://zlib.net/zlib_license.html；Jacobsen> v. Katzer, 535 F.3d 1373 (Fed. Cir. 2008) ［A］

## 281.11.5 BSL-1.1 与 SSPL-1.0——Source-available（源码可得）反例

**要点**：**BSL-1.1**（Business Source License）2023-08-10 HashiCorp 将 Terraform/Vault 从 MPL-2.0 改为 BSL-1.1 → 2023-08-16 OpenTofu fork，非 OSI 开源；**SSPL-1.0**（Server Side Public License）2018-10-16 MongoDB 发布，§13 要求“为他人提供服务”须公开完整源码，FSF 明确 SSPL 非自由许可证；二者均属 **Source-available**（源码可得）——源码可见但使用/商业/修改受限，非 OSI 开源、非 FSF 自由。

**史料**：HashiCorp 官方公告（2023-08-10）；OpenTofu 官方公告（2023-08-16）；MongoDB SSPL 文本（mongodb.com/licensing/）；FSF 对 SSPL 的官方表态 ［A］

**史观**：总纲第 14 条——许可证约束：BSL/SSPL 是后 BSD 时代的反例与张力——“开放源代码”与“开源许可证”的边界在云时代的重新博弈。

**辨析**：SSPL 与 GPL 有血缘（§13 是 copyleft 逻辑向服务领域的极端延伸），但 FSF/OSI 均不认可——归 Source-available 类比归 copyleft 更准确，须说明这一争议归属；BSL-1.1 的"Change License/Change Date"机制（到期转回开源许可）须辨析。

**文献**：HashiCorp. BUSL 公告 [EB/OL]. 2023-08-10. <https://www.hashicorp.com/blog/hashicorp-adopts-business-source-license；MongoDB>. SSPL [Z/OL]. 2018-10-16. <https://www.mongodb.com/licensing/server-side-public-license；OpenTofu>. 公告 [EB/OL]. 2023-08-16 ［A］

## 281.11.6 Unlicense、OpenSSL License 与公共领域边界

**要点**：**Unlicense**（2010）公共领域奉献+免责，与 CC0 并列；**OpenSSL License**（1998-2003）OpenSSL+SSLeay 双许可，**与 GPL 不兼容**——促成 OpenBSD LibreSSL fork（BSD 史上重要因果链：OpenSSL 双许可的 GPL 不兼容 + Heartbleed 漏洞双重动因）。

**史料**：Unlicense 官方文本（unlicense.org）；OpenSSL 官方 LICENSE；OpenBSD LibreSSL 项目历史 ［A］

**史观**：总纲第 14 条——许可证约束：OpenSSL 的 GPL 不兼容是“许可证兼容性”塑造技术路线（LibreSSL fork）的直接案例。

**辨析**：Unlicense 与 CC0 的公共领域奉献机制差异（Unlicense 无“不得反悔”条款）须辨析；OpenSSL 双许可（OpenSSL License + SSLeay License + 附加条款）的具体兼容性矩阵须逐条核验。

**文献**：Unlicense. The Unlicense [EB/OL]. <https://unlicense.org/；OpenSSL>. LICENSE [EB/OL]. <https://www.openssl.org/source/license.html；OpenBSD>. LibreSSL [EB/OL]. <https://www.libressl.org/> ［A］

史学含义：BSD 史中不乏准宗教性的现象——对 UNIX 哲学的信仰、对开源精神的信奉、对特定人物的崇拜、对"稳定性"的坚守。这些不完全是理性选择或技术决策，而有深刻的信仰属性。信仰是人民为了活着而强加于自己的形式，BSD 社区的维系同样靠的是信仰而非利益。BSD 许可证之争本质上是不同信仰体系的冲突——BSD 承认人类的有限性，GPL 则用形式限制自由实则起了反作用。史家应识别技术决策背后的信仰结构，而非将其伪装为纯技术选择。道风的缺乏即是道风的道——BSD 社区的沉默与萎缩，本身也是一种道。

史学含义：BSD 社区的治理结构——Core Team、committer 权限、Ports 维护者制度——皆是形式主义的政治产物。Core Team 的权威不来自技术优越，而来自形式主义的权力分配。社区中的边缘化现象、贡献者的话语权不均，皆是利益分配问题的体现。BSD 许可证选择承认人类的有限性，而非以强制形式限制自由。史家应揭示社区治理结构背后的权力逻辑，而非将其伪装为纯技术决策。
