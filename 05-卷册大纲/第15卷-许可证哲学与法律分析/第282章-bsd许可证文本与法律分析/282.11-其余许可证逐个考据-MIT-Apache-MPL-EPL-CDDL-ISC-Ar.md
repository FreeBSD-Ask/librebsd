# 282.11 其余许可证逐个考据——MIT、Apache、MPL、EPL、CDDL、ISC、Artistic、zlib、BSL、SSPL、Unlicense、OpenSSL

> 本子节为 2026-08-04 许可证系统性考据工程新增。铁律：以下许可证须逐版本逐个考据（按 SPDX 标识），禁止合并表述、禁止以“宽松类”“copyleft 类”笼统带过。

## 282.11.1 MIT License 与 ISC License——极简宽松双雄

**要点**：**MIT**（SPDX：MIT）1980 年代起，仅版权声明+免责声明，与 BSD-2-Clause 实质等价；**ISC**（SPDX：ISC，Internet Systems Consortium License）2006 年前确立，极简许可，OpenBSD 默认采用；二者均为 permissive 的极简代表。

**史料**：OSI MIT/ISC 条目；SPDX License List `MIT`/`ISC`；OpenBSD 项目 COPYING 文件 ［A］

**史观**：总纲第 13 条——法律与道德是利益分配：MIT/ISC 的极简与 BSD-2-Clause 一起构成 permissive 光谱的“最小义务”端。（原“总纲第 14 条——许可证约束”标号与基线第 14 条“苦难不值得被提倡”不符，本节七处统一按权威表改挂第 13 条“法律与道德是利益分配”——批次 C344 问题 1）

**辨析**：MIT 与 BSD-2-Clause“实质等价”须逐条比对（条款语义近似但措辞不同，法律适用上可能因文本差异产生细微差别），不得预设完全等价；ISC 与 MIT/BSD-2 的文本差异（ISC 措辞更简）须辨析。

**文献**：OSI. MIT License [EB/OL]. <https://opensource.org/license/mit/>；OSI. ISC License [EB/OL]. <https://opensource.org/license/isc/>；SPDX. SPDX License List [EB/OL]. <https://spdx.org/licenses/> ［A］

## 282.11.2 Apache License 1.0/1.1/2.0——permissive 中“最重”

**要点**：**Apache-1.0**（1995）与 **Apache-1.1**（2000）为简单宽松许可；**Apache-2.0**（2004-01）为 permissive 中“最重”——§3 明示专利授权（明确专利许可，permissive 中罕见）、§4 保留版权/专利/商标声明、§7 终止条款；Apache 2.0 与 GPLv3 兼容。

**史料**：Apache Software Foundation 官方许可证文本（apache.org/licenses/）；OSI Apache-2.0 条目 ［A］

**史观**：总纲第 14 条——许可证约束：Apache-2.0 的专利授权条款是宽松许可证对专利时代的制度回应，与 BSD 2/3-Clause 的“零专利条款”形成对照。

**辨析**：Apache-1.1 与 2.0 的差异（专利授权、终止条款、声明保留）须逐条对照；Apache-2.0 与 GPLv3 兼容但非 GPLv2 兼容（因 GPLv2 无专利授权对应条款）须辨析。

**文献**：Apache Software Foundation. Licenses [EB/OL]. <https://www.apache.org/licenses/>；OSI. Apache License 2.0 [EB/OL]. <https://opensource.org/license/apache-2-0/> ［A］

## 282.11.3 MPL、EPL、CDDL——文件级弱 copyleft 三杰

**要点**：**MPL-1.0/1.1/2.0**（Mozilla Public License，1998/1999/2012）文件级 copyleft（弱 copyleft），MPL-2.0 与 Apache-2.0/GPL 兼容；**EPL-1.0/2.0**（Eclipse Public License，2004/2017）弱 copyleft，Eclipse 基金会采用；**CDDL-1.0**（Common Development and Distribution License，2004-12）Sun/OpenSolaris 采用，MPL-1.1 衍生，Oracle 收购 Sun 后 Solaris 闭源事件使其成为 BSD 史对照样本。

**史料**：Mozilla 官方 MPL 文本（mozilla.org/MPL/）；Eclipse Foundation EPL 文本（eclipse.org/legal/）；OSI CDDL 条目 ［A］

**史观**：总纲第 14 条——许可证约束：文件级 copyleft 是“传染边界”的制度折中——比 permissive 强、比 GPL 弱，传染范围限定于被修改文件。

**辨析**：MPL/EPL/CDDL 的“文件级 vs 整体级”传染边界差异须辨析（MPL 传染限被改文件，CDDL 同 MPL-1.1 模式但文本差异）；CDDL 与 GPL 不兼容导致 OpenSolaris 代码难以并入 GPL 生态，是 Solaris 闭源后社区续命的许可证障碍（详见 296 章 illumos）。

**文献**：Mozilla. Mozilla Public License [EB/OL]. <https://www.mozilla.org/MPL/>；Eclipse Foundation. Eclipse Public License [EB/OL]. <https://www.eclipse.org/legal/epl-2.0/>；OSI. CDDL-1.0 [EB/OL]. <https://opensource.org/license/cddl-1-0/> ［A］

## 282.11.4 Artistic License 1.0/2.0 与 zlib License

**要点**：**Artistic-1.0/2.0**（1991/2006）Perl 双许可的组成部分；**Jacobsen v. Katzer** 案涉 **Artistic-1.0**——联邦巡回上诉法院认定 Artistic License 条款创设版权条件（conditions），违反即构成版权侵权（535 F.3d 1373）；**zlib License**（1995）极简许可，zlib 压缩库采用。（原记 1987/2000 系年代讹误，按 SPDX/OSI 通行记载订正为 1991/2006——批次 C344 问题 2）

**史料**：OSI Artistic-1.0/2.0 条目；zlib 官方 LICENSE；Jacobsen v. Katzer 判决书（535 F.3d 1373, Fed. Cir. 2008） ［A］

**史观**：总纲第 14 条——许可证约束：Artistic 的“灰色地位”（FSF 视 Artistic-2.0 为自由许可、OSI 认可，但其条款允许变通）使其成为弱 copyleft 灰区样本；Jacobsen 案是“许可条件=版权条件”的先例来源。

**辨析**：Artistic-1.0 与 2.0 差异须对照；Artistic 的“改个名就不开源”变通条款（Artistic 1.0 允许改名后非开源再分发）与 FSF/OSI 态度的张力须辨析。

**文献**：OSI. Artistic License 2.0 [EB/OL]. <https://opensource.org/license/artistic-2-0/>；zlib. zlib License [EB/OL]. <https://zlib.net/zlib_license.html>；Jacobsen v. Katzer, 535 F.3d 1373 (Fed. Cir. 2008) ［A］

## 282.11.5 BSL-1.1 与 SSPL-1.0——Source-available（源码可得）反例

**要点**：**BSL-1.1**（Business Source License）2023-08-10 HashiCorp 将 Terraform/Vault 从 MPL-2.0 改为 BSL-1.1 → 2023-08-16 OpenTofu fork，非 OSI 开源；**SSPL-1.0**（Server Side Public License）2018-10-16 MongoDB 发布，§13 要求“为他人提供服务”须公开完整源码，FSF 明确 SSPL 非自由许可证；二者均属 **Source-available**（源码可得）——源码可见但使用/商业/修改受限，非 OSI 开源、非 FSF 自由。

**史料**：HashiCorp 官方公告（2023-08-10）；OpenTofu 官方公告（2023-08-16）；MongoDB SSPL 文本（mongodb.com/licensing/）；FSF 对 SSPL 的官方表态 ［A］

**史观**：总纲第 14 条——许可证约束：BSL/SSPL 是后 BSD 时代的反例与张力——“开放源代码”与“开源许可证”的边界在云时代的重新博弈。

**辨析**：SSPL 与 GPL 有血缘（§13 是 copyleft 逻辑向服务领域的极端延伸），但 FSF/OSI 均不认可——归 Source-available 类比归 copyleft 更准确，须说明这一争议归属；BSL-1.1 的“Change License/Change Date”机制（到期转回开源许可）须辨析。

**文献**：HashiCorp. BUSL 公告 [EB/OL]. 2023-08-10. <https://www.hashicorp.com/blog/hashicorp-adopts-business-source-license>；MongoDB. SSPL [Z/OL]. 2018-10-16. <https://www.mongodb.com/licensing/server-side-public-license>；OpenTofu. 公告 [EB/OL]. 2023-08-16 ［A］

## 282.11.6 Unlicense、OpenSSL License 与公共领域边界

**要点**：**Unlicense**（2010）公共领域奉献+免责，与 CC0 并列；**OpenSSL License**（1998-2003）OpenSSL+SSLeay 双许可，**与 GPL 不兼容**——促成 OpenBSD LibreSSL fork（BSD 史上重要因果链：OpenSSL 双许可的 GPL 不兼容 + Heartbleed 漏洞双重动因）。

**史料**：Unlicense 官方文本（unlicense.org）；OpenSSL 官方 LICENSE；OpenBSD LibreSSL 项目历史 ［A］

**史观**：总纲第 14 条——许可证约束：OpenSSL 的 GPL 不兼容是“许可证兼容性”塑造技术路线（LibreSSL fork）的直接案例。

**辨析**：Unlicense 与 CC0 的公共领域奉献机制差异（Unlicense 无“不得反悔”条款）须辨析；OpenSSL 双许可（OpenSSL License + SSLeay License + 附加条款）的具体兼容性矩阵须逐条核验。

**文献**：Unlicense. The Unlicense [EB/OL]. <https://unlicense.org/>；OpenSSL. LICENSE [EB/OL]. <https://www.openssl.org/source/license.html>；OpenBSD. LibreSSL [EB/OL]. <https://www.libressl.org/> ［A］

**要点**：

- sysjail 2.0 是对其基于 systrace 的轻量级虚拟化系统的完全重写，面向 OpenBSD 与 NetBSD，原生支持 Compat Linux 与 Compat FreeBSD；借助二进制接口兼容而非在 Xen 实例中启动整个内核，可在 SSH 登录下把 BSD 主机呈现为完整的 Fedora 式 Linux 环境，并遵循 FreeBSD jail 的约定。（BSDTalk EP128，[123.83-159.75]，L1）
- Robert Watson 的论文与演讲揭示系统调用包装器这一整类技术（systrace、ptrace 及一切拦截系统调用的机制）的潜在漏洞：UNIX 模型中子进程可修改父进程内存，恶意进程可在受检前 fork 并保存进程信息副本，再由子进程以原始信息重装父进程，绕过已被 systrace 设备放行的检查；后果轻则拒绝服务，重则任意系统调用得逞。Watson 早在 2006 年米兰 EuroBSDCon 即当面警告过其理论性。（BSDTalk EP128，[173.15-496.88]，L2）
- 短期修复方案由 systrace 原作者建议的 look-aside buffer 构成：将进程信息保存进 systrace 设备或内核空间，fork 发生时弃用保存副本而保留经设备核准的原始信息；Kristaps 与 Dexter 希望在当周 EuroBSDCon 前做出原型，并需为此剥离 systrace 诸多未暴露于前端的冷门功能。（BSDTalk EP128，[499.83-576.39]，L1）
- 长期方向为重写内核上半部并自始为多重性设计：取消 root 与全局网络实例概念，使对系统的访问总是表现为另一个实例，而非在一个全局实例下伪造众多实例；该提案获里加大学与 KTH 斯德哥尔摩的积极回应，尚处规划阶段、未选定工作内核，Dexter 希望保持与源内核下半部的同步而不倾向 fork。（BSDTalk EP128，[778.64-884.08]，L1）
- Dexter 断言几乎一切虚拟化系统（FreeBSD jail、sysjail、Xen、VMware、Parallels、自建 chroot jail、Linux vServer）都是 hack，是让单机呈现多系统外观的笨拙手段；多重性难题随硬件廉价化循环重演——多用户、多磁盘与 RAID、多显示器、SMP 依次成为挑战，DragonFly 项目即为解决 SMP 问题而分叉，且极少有议题被彻底解决。（BSDTalk EP128，[605.27-733.79]，L1）[订正：原 Solaris Zones，2026-09-29 SenseAudio 重转核对]
- ISC 为美国 501(c)(3) 非营利公益组织，维护 BIND、DHCP 及遗留产品 INN，约 40 名员工且半数远程办公，收入主要来自支持合同；Losher 任高级运维架构师，自嘲职责是“让所有人能在家里工作”。F 根服务器实际运行基本是现货软件：99.9% 情况下跑官方 FTP 站的 stock BIND，系统以 FreeBSD 为主、杂有少量 Linux 与 Windows，防火墙以 dummynet 应对 DDoS。（BSDTalk EP206，[45.36-400.88]，L1）
- 根服务器负载史：早期 F 根托管 com、net、org 及军方 mil 等大型区域，须用 DEC Alpha 5U 大机并装载 8GB 内存才能容纳 zone；Verisign 将 com/net 迁往 gTLD 服务器、arpa 区域外移后，根服务器专注于根区域本身。如今 F 根分布式部署逾 50 个节点、以 1U 商品机 4GB 内存即为过剩（签名后的根 zone 不足 300K），十三家根运营者之间刻意保持操作系统、硬件与名字服务器软件的多样性。（BSDTalk EP206，[527.92-682.16]，L1）
- DNSSEC 与 IPv6：根区域签名于此前一年夏天完成，从根运营者视角切换“无可挑剔”，曾担忧的“响应增大三至四倍、穿透不过防火墙”并未成真；ISC 自有区域已签名五年，com/net/org 与主要 ccTLD 已陆续签名，下一步目标是把 DNSSEC 验证能力推进到基础操作系统层而非仅浏览器。ISC 自 2003 年起内部双栈运行 IPv4/IPv6，参与 World IPv6 Day 并向项目提供 IPv6 隧道。（BSDTalk EP206，[682.16-856.78]，L1）
- 商业化与公益的边界：因根服务基础设施属公益免费资源，ISC 长期拒绝企业“帮忙做 secondary”的请求；此后另建由多家 tier-1 提供商组成的全球网络（ISC 运营设备而非自有网络）推出商业 secondary DNS 服务，把 F 根多年运维经验变现。F 根部署扩展则面向发展中世界（斐济、内罗毕、达卡等），并正将平台缩减得更经济、便于运输。（BSDTalk EP206，[856.78-948.80]，L1）

- Robert Watson 2007 年关于系统调用包装器漏洞的论文及其演讲幻灯片（第 17 页含以 sysjail 为例的漏洞图示），发表前曾允许 Kristaps 评审；其理论警告早在 2006 年米兰 EuroBSDCon 即已当面提出。（BSDTalk EP128，[173.15-236.51]，L1）
- Kristaps 在里加大学（University of Latvia）举办的系列讲座，为 sysjail 发布风波后双方反思并酝酿长期提案的直接契机；sysjail 软件发布于 sysjail.org 与 sysjail.bsd.lv。（BSDTalk EP128，[757.23-978.88]，L1）
- 节目开头新闻条目：2007 年 EuroBSDCon 于当周在哥本哈根举行，OpenBSD 4.2 开放预订；Dexter 另提及 AMD 当日发布四核处理器。（BSDTalk EP128，[35.07-50.68]，L2）
- 本访谈为根服务器运维史与 ISC 组织史的一手口述，可提取的事实包括：BIND 9 研发阶段由 Sun、HP、IBM 等大厂资助并以其展示多处理器多线程能力、F 根节点分布于斐济/内罗毕/达卡等地、早期 Alpha 服务器 8GB 内存需求、签名根区小于 300K、BIND 用户仍大量滞留 9.3/9.4 旧版等，均为当事人自述。（BSDTalk EP206，[259.68-447.82]，L1）

**史观**：

- 总纲4 分离聚合是永恒规律：多重性议题（多用户、多磁盘、多显示器、多核 SMP、多实例）随硬件成本下降而循环重演且从未被彻底解决，虚拟化即让单一系统分离出多系统外观再聚合为多实例的技术形态，印证分离聚合的循环结构而非线性进步。（BSDTalk EP128，[654.15-733.79]，L1）
- 总纲13 法律与道德是利益分配：许可证是利益分配的形式化装置而非人性改造工具：Dexter 以“许可证不改变人性”“路由器厂商被要求也不会交出 GPL 代码”而 BSD 用户无强制条款仍自愿回馈为据，主张简明协议优于复杂法律构造，法律设计的正当性在于可理解与可辩护而非道德强制。（BSDTalk EP128，[1209.31-1244.14]，L1）
- 总纲21 革命与改革是历史方法论的分歧：GPL 的 copyleft 强制路径与 BSD 的自愿回馈路径构成许可证方法论的根本分歧；Dexter 预言 GPLv3 的专利条款与复杂性将引发诉讼乱局，反而反衬 BSD 式简明协议的优势，这是以对手的激进改革为参照系确认自身演化路线的历史判断。　[存疑脚注] GPLv3 将成为 BSD 二十年来最好的事系 Dexter 个人预言，属单一来源推断，2007 年时点无法验证（BSDTalk EP128，[1100.96-1191.35]，L4）
- 总纲8 本体论上各方平等：长期提案取消 root 与全局网络实例，让一切系统访问都以平权实例的形态存在，而非全局特权之下伪造的从属实例——这在本体论层面消解了全局与局部实例的等级差序。（BSDTalk EP128，[813.39-833.27]，L1）
- 总纲8 本体论上各方平等：总纲8 本体论上各方平等：Losher 明言十三家根运营者间须维持操作系统、硬件与名字服务器软件的多样性——没有人主张 FreeBSD 或 BIND 是唯一正确选择，ISC 亦同时杂用 Linux 与 Windows；多样性被制度化为互联网基础设施的抗脆弱策略，而非某一方的正统性叙事。（BSDTalk EP206，[458.54-505.52]，L1）
- 总纲13 法律与道德是利益分配：总纲13 法律与道德是利益分配：Losher 解释 ISC 许可证的价值在于给商业组织以确定性——集成后不强制开放修改源码，回馈与否“留给最终用户决定，不是自上而下强制”；许可证在此并非道德宣言而是利益分配装置，它决定了 Sun、HP、IBM 等厂商是否愿意资助 BIND 9。（BSDTalk EP206，[301.24-341.92]，L1）
