- 〔USENIX Security（推测）〕验证上，他们用 FFMalloc 替换 glibc 等默认分配器，针对一系列已知易受 UAF 影响的二进制做测试：先确认概念验证攻击在默认分配器下可行，再用 FFMalloc 重跑攻击，所有情况下攻击都失败〔06:33〕〔06:46〕。其中若干测试对象是内存安全语言的运行时，理论上这些语言应对 UAF 免疫，但因为运行时本身是 C 应用，仍然易受影响；即便是默认使用自有分配器而非 glibc 的 PHP，也易受 UAF 漏洞影响〔07:01〕〔07:19〕。FFmalloc 有意不处理堆溢出等其他内存安全错误，以便聚焦验证一次性分配的可行性，但其设计也能顺带检测无效 free 与双重 free 并终止应用，与 glibc 惯例一致〔07:29〕。性能方面，在 SPEC CPU 基准套件上，相较 glibc 几何平均增加的开销不到 2.5%（以下结果均以 8 页作为归还操作系统的阈值）〔07:50〕〔08:08〕；但在多线程的 Parsec 基准上开销更显著，跨所有测试基准与线程组合几何平均达 22%，一部分原因是当前设计中有少量锁，更主要的是每次内存映射系统调用都要争抢 Linux 内核里的全局 mmap 锁，未来内核若把这个锁做得更细粒度，FFmalloc 有望获得可观的性能提升〔08:17〕〔08:35〕。内存开销方面，即便经过仔细设计，FFmalloc 仍有中等开销，处于其他反 UAF 方案的中间位置：SPEC 上 61%、Parsec 上 51%，部分源于内存碎片、部分源于按批释放页面；可以通过更频繁归还页面以降低内存开销，但代价是更多 CPU 消耗〔08:51〕〔09:17〕。真实应用方面，他们用 Nginx 做负载测试，在各种并发连接数与 worker 线程组合下吞吐与其他分配器相当；内存开销则不太亮眼，超过 glibc 的 5 倍，但这与面向性能的 free_guard 相当，且明显优于以 UAF 为目标的 marcus〔09:27〕〔09:44〕。他对比概率式方案：它们靠随机性降低攻击者控制被错误复用内存区域的可能性，但若漏洞可从网络触达，攻击者可能反复触发重分配从而强制复用目标块，而且这类方案的整体安全影响难以推理；极端情形下，非确定性分配还可能让缓冲区溢出等其他漏洞变糟——它可能周期性地把攻击者可控内存放到本来在确定性分配下不会相邻的其他块旁边〔09:57〕。其他提供硬 UAF 保证的系统大体以复杂度为代价，体现在运行时开销上；其中一些基于编译器改造，因而无法追溯修复已部署的代码，且必须等所有链接库都被重新编译后才能提供完整保护；相比之下 FFMalloc 是 glibc malloc 的即插即换替代品，无需重编译，提供一个容易推理的硬安全保证，且常常对执行速度影响很小〔10:41〕。最后他总结：C 这类不安全语言写下的海量代码仍是现代计算的关键，UAF 这类内存安全错误依然是重大安全威胁；一次性分配是显然且直接的解法，却长期被当成不切实际而遭摒弃，他认为 FFMalloc 的工作表明该重新把它视为可行的反 UAF 技术，代码已发布于 GitHub〔11:20〕。（YouTube EPYmvSM31HtqU，[357-720]，L1）
- 〔OSDI（推测）〕Azure 的 Abhishek 报告 Protean：Azure 的虚拟机分配服务，属 Azure 与微软研究院的联合工作；单实例 Protean 管理整个可用区的全部分配，而一个可用区如今可承载超过十万台机器〔00:09〕〔00:36〕。他先谈规模、多样与不可预测：Azure 的足迹覆盖 61 个区域与数百个边缘站点，一天之内在超过 200 万台服务器上创建超过 500 万台新虚拟机〔01:41〕。层级结构上，最顶层是区域，由若干数据中心组成、最多含三个可用区；可用区有独立的供电、冷却与网络设施，可承载逾十万台机器；区域与可用区直接暴露给客户，可用区再细分为许多集群，与可用区不同，集群内机器是同构的、具有相同配置与能力，这一事实被用来优化分配服务性能；二三十年间已用过八代硬件，一个可用区同时容纳四到五代硬件完全可能，除通用硬件外还有大内存机器、带高性能互连的加速器等专用计算基板，这些差异使放置算法高度依赖底层硬件，从而大幅增加复杂度〔01:55〕〔02:21〕〔02:41〕。应用也高度多样：Azure 从单台虚拟机到带自动缩容的大规模虚拟机集合，再到数据库与机器学习服务，最终都通过虚拟机消耗硬件资源，所以内部把资源请求表示为虚拟机分组，称为 tenant，一个 tenant 可以只有一台也可以是上千台虚拟机，且 tenant 内虚拟机可表达故障域之类的相互关系；虚拟机最终是资源分配单元，其资源需求由虚拟机类型（size）定义，如今已有 700 多种类型且还在增长，从左侧红色规格的一核两吉到右侧“monster”的 224 核 12 太，不仅绝对需求量差异大，核内存比也不尽相同；新类型有时并不在旧代硬件上受支持，此外还有优先级、故障域等数十种影响放置决策的特性〔03:19〕〔03:45〕〔04:21〕。分布上，他在两个可用区展示按类型分布的已分配虚拟机：每个区域有大量类型，但少数几种明显更受欢迎；按已分配核数看，多数虚拟机只用 1 到 4 核，但也有大到占满整台机器的虚拟机，这种类型与分布的差异让把这些虚拟机打包得很整齐变得非常困难〔05:21〕。需求方面，较忙的一个可用区按小时看有昼夜规律，但放大到每秒就能看到大量尖峰，而且这些尖峰很大又难以预测，理想情况下 Protean 应能在不降级服务的前提下扛住尖峰〔05:56〕〔06:10〕。目标上，首要且根本的是正确地把虚拟机分配到机器、遵守每一个客户约束；此外还有一批很重要的内部目标，例如卓越的客户体验——Protean 偏好能更快启动虚拟机的机器、考虑未来硬件维护事件可能带来的潜在中断、并尽量最小化对低优先级虚拟机的驱逐〔06:32〕〔07:00〕。几乎同等重要的是低碎片：在 Azure 的规模下，碎片率降低 1 个百分点就能带来每年约一亿美元的成本节省〔07:15〕；好的打包还会留空更多机器，而空机器对寻找难以放置的大虚拟机的位置很重要〔07:27〕。还有一组关于 Protean 本身的目标：可扩展与可适应——应能容易且安全地加入新行为，或调整既有行为；以及可解释性，因为“我的分配为什么失败”是一个必须反复回答的常见问题，所以要为分配失败提供详细原因〔07:39〕〔07:51〕。他随后转向 Protean 如何做到这些。（YouTube EPYns52ci_MVw，[9-506]，L1）
- 〔OSDI（推测）〕Protean 的核心做法是把复杂分配逻辑表达为一组规则：分配一台虚拟机本质上是从库存里所有机器中为该虚拟机选出最好的节点，分两步完成——先过滤，把不能用于该虚拟机的节点全部拒绝，这一步通过一系列 validator 规则强制执行全部硬约束；然后对剩余节点按一系列 preference 规则排序，表达软约束〔08:26〕〔08:39〕〔08:45〕〔08:57〕。他强调排序是严格分层的：任何规则只能为被上一层规则视为相等的节点打破平局；生产环境中这样的规则已有一百多条〔09:04〕〔09:15〕。validator 规则实现 isValid 方法以判断某节点或集群对该虚拟机请求是否有效，例如 NodeResourcesValid 检查节点是否有足够资源容纳一台虚拟机；preference 规则实现 compare 方法以比较两个节点、判断哪个更适合放置新虚拟机，例如 PreferNonEmptyMachines 会把半满节点排在完全空节点之前，因为空节点本身是有价值的〔09:25〕〔09:47〕〔10:06〕。他也指出多偏好规则带来的张力：由于排序严格分层，若某条规则把单一节点排到其余所有节点之前，下面所有更弱规则就都失效了，因此他们对避免规则过于严苛花了很多功夫，通常通过量化（quantization）来平滑；best fit 规则是典型例子，它用多维 best-fit 算法改善打包，给每台机器一个 0 到 1 之间的归一化分数，再把这个分数量化成若干桶来平滑规则〔10:22〕〔10:46〕。他展示不同桶数下的效果：随着桶数上升，打包密度改善但收益递减，桶数超过三之后尤甚，同时落入最高桶的节点比例不断降低——这一比例越低，规则就越严苛〔11:11〕〔11:27〕〔11:42〕。规则化带来的额外好处是新增行为容易、且诊断分配失败相当直接〔12:13〕。为降低虚拟机分配耗时，他们的第一招是用一个廉价的过滤与排序步骤预选出合格且高质量的集群——在集群层面推理远比在机器层面便宜得多，因为集群数量比机器数量少得多；随后机器选择只针对所选集群内的节点进行，这才是真正的瓶颈步骤〔13:12〕。瓶颈靠多层缓存框架加速，动机来自两个观察：请求具有时间局部性，即便考虑它们可能携带的各种特性，请求之间仍然相似；而库存变化缓慢——一个可用区可能有逾十万台机器，但两次分配之间状态发生变化的机器数量少得多〔13:48〕。核心思想是：评估一个虚拟机请求时会得到一份已排序的有效节点列表，保存并复用这份列表；下一个请求到来时，只需重新评估在此期间发生变化的节点的位置，这就是他们想要做的全部计算〔14:07〕〔14:17〕。以 NodeResourcesValid 规则的朴素实现为例，其 isValid 方法在每个虚拟机请求中对每个节点都会被调用，且可能包含大量计算，因此他们改用以虚拟机类型与节点为键的查表，使 isValid 变成常数时间操作，并把单一规则对象在所有请求间复用〔14:39〕。为此每条规则实现一个 update 方法，在规则对象被使用之前立即调用，参数是自上次调用以来被修改过的机器列表，于是重计算只发生在 update 内部、只针对被修改的节点〔15:06〕。更进一步的优化是：单个规则对象存储所有虚拟机类型的状态，导致 update 里出现嵌套循环，因此把这个对象拆成每类虚拟机类型一个对象，每个对象只计算并存储单一类型状态，消除嵌套循环；请求到来时先更新对应类型对象再用于评估，从而吃到前面提到的请求局部性〔15:41〕。他们还可以存储并复用整个评估结果——已排序的机器列表——保存在 rule evaluation 对象里，同时还要保存用来计算该结果的规则，以及这些规则所依赖的全部特性取值，特性取值共同唯一标识这些评估对象〔16:30〕〔16:56〕。他举例说明依赖树结构：设特性 X 可取值 x1、x2，特性 Y 可取 y1、y2，规则 R1 同时依赖 X 与 Y、R2 只依赖 X，则有四种唯一的特性组合、对应四个不同的 rule evaluation 对象与四个 R1 对象，而 R2 只需两个对象、被两个评估对象共享，于是每个评估对象成为一棵依赖树的根〔17:14〕。如此便形成一棵棵依赖对象树，被缓存在大小恒定的 LRU 池里；生产上的效果是，能命中缓存结果时分配耗时改善约一个数量级，而维护这些缓存对象的内存开销随库存规模亚线性增长，在当前可用区规模下并不是问题〔18:00〕〔18:12〕。他还提到论文随附生产轨迹，可用于探索不同的打包算法，并致谢该服务的整个团队〔18:40〕。（YouTube EPYns52ci_MVw，[506-1137]，L1）
