- 〔USENIX LISA '14〕让“绿灯即推”成为现实。主讲人（自述讲的是自己在 Google 的做法，转写中未自报姓名）以“让 push on green 成为现实”为题，强调自己讲的不是如何造出 push on green，而是到达它之前必须先备好的东西，并称这是一段演进过程。他把 push on green 定义为：由人、或构建系统加测试套件、或人加某种实时监控系统判断“看起来没问题，可以发布了”，随后就要把它真正上线；但现实总会入侵你的系统——数据依赖、网络依赖、会变的 API 与新 flag 无处不在，数百名工程师同时改动时意外就成了常态，因此需要覆盖开发、测试、监控以及更新与回滚方式的“跨文化”控制心态。以 Google 的做法为例（他明确说这不是因为规模大才有效，单机或多机同样适用）：所有代码改动必须同行评审，不只审正确性还审测试与可读性；不仅测预期情形也测异常情形是否优雅失败——他以 OpenSSL 只有约五个测试、成百上千小模块无人测试而酿成 Heartbleed 为反例；测试组合应包含单元、模块、端到端、冒烟与探针以及最重要的回归测试；监控必须记录量、延迟与吞吐、可绘图可回溯，据此建立告警，而告警又依赖 SLA、SLA 依赖 SLO、SLO 依赖 SLI。更新与回滚则要求静态构建（避免共享库升级同时拖垮所有依赖者）、人类可读的带日期版本号、只“标记”哪个版本为 live 而非到处推送版本号、把发布与监控图关联以便定位拐点、发布必须自动化且幂等，以及金丝雀（canary）作业：给它一部分流量、与正常作业做归一化对比看趋势，出问题就调回负载均衡器，用户只会看到极小规模的故障。（YouTube EPRYbzzlIJYfg，[18-1111]，L1）
- 〔USENIX LISA '14〕金丝雀浸泡、flag 分步引入与安全文化。作者给出数据变更的安全上线流程：先静音“版本不一致”一类告警，更新金丝雀后立即跑冒烟测试，通过则让金丝雀浸泡（soak）一段时间——例如某类请求只占 1%，需要跑到六小时才够样本量，再推送剩余作业、重新跑冒烟测试，最后恢复告警；他同时澄清“回滚”只是把版本往前推到更早的版本，涉及数据库 schema 变更时要格外小心地管理。软件变更部分以“允许用比特币支付”的 flag 为例给出完整分步：先在源码里定义 flag 且默认 false（相当于推送一个 no-op 二进制）→ 改配置文件显式写出该隐式值 → 只让金丝雀启用 → 全部启用 → 最后才把源码默认值改成 true 并移除守卫，且守卫与定义要分两步删除，避免一次改动同时牵动多个相互依赖的 flag、保证任何时刻都只回滚一件小事。回报是：他 2013 年接手该项目时每周约 12 次发布，后来升到每周 70 余次且全部为人工把关的发布，自动化还额外释放了一名全职工程师。后续改进包括每日（工作日，周五下午除外）自动周期性发布、发布间互锁、发布时刻表与一键回滚；未来方向是回滚可行性评估、走向持续交付、引入发布配额，以及“green on green”式上线——但他坚持仍需人在环路中，因为若出了问题就自动推新版本只会更糟。文化上的落点是：坏事每天都会发生，重要的是找到原因并写事后复盘（postmortem），惩罚肇事者唯一的方式就是让他写复盘，同时改掉流程使其不可能再次发生——“我们修复流程而不是指责人”；他最后强调即便非 Google 规模甚至单人团队也能照做，可以用 Cacti、MRTG 这类工具甚至 sendmail 队列统计做监控，没有银弹，只能靠 baby steps 一步步走。（YouTube EPRYbzzlIJYfg，[1111-2244]，L1）
- 〔SREcon16 Europe〕网络运维的过去、现在与未来。David Barroso（自报全名，Fastly 网络系统工程师）在 SREcon Europe 2016 第三天以近乎 rant 的口吻回顾网络运维的过去、现在与未来。他先用历史开场：今天用于监控与备份网络的工具大多诞生于二三十年前，NETCONF 作为“最新”的运维进展也要到 2006 年才出现，也就是说从 2006 到 2015 年，从运维角度看网络什么都没发生；而系统侧同期从 2001 年的虚拟化、2005 年的 Puppet、Linux 容器、DevOps 运动、ELK、Docker、chat ops 直到 Kubernetes 一路狂奔，两个世界的运维演化出现巨大断层。他解释原因：网络本身就是复杂分布式系统（“我们用 BGP 用了三十年”）；开发者硬编码 IP 这类蠢事在网络上留下无法自动化的唯一性 hack，几个月后就会炸掉东西；网络人过去精力都花在出新协议、做互操作与提升设备带宽上；高成本认证的工程师会把学到的奇怪旋钮全用一遍，制造出一堆一次性特例；厂商只想卖东西，什么都想靠再加一个地址族或封装机制解决，网络变慢就发明 VXLAN 之类的东西绕过去而不是修根因，甚至有大运营商手握海量工程师却认为规模化运维就是 Notepad++ 加并行 SSH。（YouTube EPRaGQ3e5LMQU，[6-472]，L1）
- 〔SREcon16 Europe〕NAPALM、OpenConfig 与 Fastly 的实战。2015 年出现的一线希望是 NAPALM 与 OpenConfig：前者抽象掉设备差异，让运维只声明“我要做什么”而不必关心如何在 Juniper 或 Cisco 上做到；后者自带的流式遥测（streaming telemetry）终于在二十五年后取代 SNMP——从持续轮询“给我你的接口计数器”改成订阅服务、计数器一变就推过来。他也指出有人终于意识到给设备 Linux 开放 root 权限（乃至通过 SDK 或 netlink 触及 ASIC）是竞争优势而非麻烦，可以自建小控制面而不必苦等半年某个特性；2016 年的网络人开始把 DevOps 当朋友而不是敌人。接着他展示 Fastly 的实践：后端保存网络完整模型（设备、链路、对等关系、接口），随时可据此重建网络；用 Ansible 把数据翻译成配置并推到设备；把部署 pop、drain pop、装软件、检查 pop 是否正常等操作抽象成极简任务，再通过 API 暴露出来与 CI 流水线联动（末尾跑检查，失败就回滚），用 chat ops（Slack）让所有人都能看到发生了什么；他们还在网络上跑服务、把交换机直接变成硬件负载均衡器，并强调对待网络上跑代码应像对待前后端一样走 CI 与集成测试。更棘手的是流量工程：全球有大量 pop，一旦决定把拥堵区域流量改道，就要靠路由服务器（如今被称为基于 BGP 的 SDN 控制器）下发改动并全网传播，一个错别字就可能让全网掉线，因此他们把路由服务器配置放在 GitHub，改动推分支、上 staging 测试、再开 PR 走审批，和对待软件完全一致。总结时他说网络迟到了但正在追赶，呼吁 SRE 去理解网络为何如此、别重复造轮子、复用 DevOps 与 SRE 社区的现成知识（“你不需要 Gradle 专用工具，Travis、CircleCI 都行”），并停止听厂商的（“厂商都有议程；如果他们不给你设备 root 权限，他们可能在撒谎”）——DevOps for networking 的目的不是抢网络工程师的饭碗，而是让这份工作更有意思。（YouTube EPRaGQ3e5LMQU，[472-996]，L1）
- 〔SREcon19 Americas〕Finagle 中的非合作式客户端负载均衡。Ruben（Twitter 工程师，负责 Finagle）介绍 Finagle 客户端内置的负载均衡算法，称其承接此前讲者关于七层负载均衡的话题。他强调在数百上千实例的微服务场景下要安全利用聚合容量必须前面放负载均衡器，而所有请求都过一遍负载均衡器也正是绕开实例故障的理想位置；他们的负载均衡器是“非合作式”的（多个负载均衡器各自独立决策，从而不必为昂贵的协同付出代价）与“客户端侧”的（内嵌于客户端，基础设施层数更少），且同时平衡会话与请求，但以请求分布作为衡量负载均衡器优劣的主要指标，因为它更能代表资源利用情况。基础策略叫 P2C，源自 Michael Mitzenmacher 的 The Power of Two Choices：每个请求随机选两个实例比较负载，把请求发给更空闲的那个；其性质是负载分布比纯随机指数级更优（同质副本时表现均匀）、无需同步昂贵数据结构、可常数时间完成，更重要的是它把“选择”与“比较”解耦——第一步随机且对负载一无所知，第二步才比较负载。会话层当时并未做文章（就是全网格），代价是每个实例都被建连、每条会话都要健康检查，且非合作式意味着一个实例坏掉时每个负载均衡器都得各自独立发现、没有隔离；另外客户端并发不足时负载指标保真度低，反而要提高每会话并发。（YouTube EPRb0TtkBZ4_s，[11-761]，L1）
- 〔SREcon19 Americas〕从随机 aperture 的混沌到确定性环形坐标。第一版方案叫 random aperture：负载均衡器维护一个窗口，用反馈控制器把它动态扩缩到“恰好覆盖一条活跃请求”的最小规模，并随机挑选会话落入窗口；结果是服务 B 上出现严重冷热不均——线上部署后每服务器 RPS 曲线“几乎是纯粹的混乱”，分布极宽，让容量规划与过载判断都很困难，也把大量资源留在桌上。他们能证明把会话分配建模为二项分布后，扩大窗口可减轻（但不能消除）这种条带效应，于是建了内部 wiki 指导服务方用二项分布配置窗口；这被他称为“真的馊主意”，因为它把配置负担推给服务负责人，配置会腐化并收敛成一堆烂配置。改进灵感是改用环形拓扑：把服务实例按服务发现提供的实例 ID 与总数映射到离散坐标环上（形似一致性哈希但不使用哈希），再让两条共享同一值域的环可被组合，使服务 A 的每个实例都能沿环顺时针导出对服务 B 的唯一顺序，并把 aperture 展开在这个顺序上；多环组合会带来 off-by-one 式的视觉拥挤与新的冷热点，进一步引入连续坐标后，每个实例占值域上的一片区间，P2C 只需在自己的区间内随机取两个坐标、映射到服务 B 的离散坐标（计算两环交集得到 A、B），并把负载按其权重做反向归一化，避免偏向本已负载更轻的实例。该连续坐标模型能跨互不相识的服务环公平分布请求，仅需服务发现里带出的实例 ID 与数量等轻量元数据，同时保持更少会话；aperture 可设最小值以增强韧性（通过让环绕整数圈实现），并继承一致性哈希的最小扰动特性，另加入确定性洗牌以避免 thundering herd（防止多环同步绕开同一批节点造成类似协同式 DNS 攻击的连带效应）、合并服务发现更新、以及用 peer size 启发式对抗滚动重启带来的会话抖动。生产结果：某服务从随机 aperture 切到环形模型后，请求速率的相对标准差下降 78%，聚合连接数下降 91%（从 280k 降到 25k），该服务失败数减少 75%，CPU 用量下降 20%–25%，GC 总时间减半；约 95% 的实现已开源在 Finagle 项目中。（YouTube EPRb0TtkBZ4_s，[764-1358]，L1）
- 〔USENIX NSDI '18〕NEAt：给网络加上自动纠错。Wenxuan（仅自报名字，与 Jason Croft、Bingzhe Liu、Elaine Ong 及 Matthew Caesar 教授合作）介绍论文《Automatically Correcting Networks with NEAt》。他们指出今天的网络极其复杂，难以确认它确实在做对的事：从运维者视角看，网络应当满足一组正确性条件——从简单的环路避免、阻止不可信流量进入安全区，到复杂的合规要求；这些条件往往要靠运维者编写相当复杂的配置或控制软件并下发到成千上万台不同厂商的设备上实现，再加上持续加速的变更，企业网络中多站点、WAN、云网络与数据中心内多层多协议叠加，其结果是新闻里不断出现数据泄露与中断事故，几乎十之九的运维者并不完全确信自己的变更不会引入新问题。现有工作主要有两支：一支是网络行为验证技术，输入策略与某种网络抽象（配置文件、控制面、数据面或控制软件）并找出违规，但止步于此、不帮运维者修复出错的运行状态；另一支是从零合成符合策略的正确网络状态，但像编译器一样离线运行、策略一变就得重来。（YouTube EPRbKVZf85qXA，[10-394]，L1）
