# 321.4.231 〔OSDI20〕本演讲介绍一种基于地址空间代际addressspacegener

- 〔OSDI '20〕本演讲介绍一种基于地址空间代际（address space generations）的 wait-free 代码补丁技术：用户态多线程进程在运行时打补丁，业界惯用的全局静止（global quiescence）会令响应速率归零、尾延迟飙升甚至死锁，本方案把全局静止降格为线程级局部静止，从而在打补丁期间维持服务质量〔00:08〕。运行时打补丁即动态软件更新——可能无法关机重启，例如高可用系统必须保证服务质量、或重启代价昂贵；操作系统内核是典型例子、Linux 已有数套活跃的 live patching 方案，但如今不仅内核启动缓慢、动辄有成千客户端的大型数据库等用户态程序同样如此，而该领域研究不少、用户态运行时打补丁在实践中却很少使用〔00:17〕。典型服务器应用如 OpenLDAP：一个监听线程接受大量客户端连接、再由一组工作线程处理；工作线程的代码大致是等待监听线程送来新的工作包、然后在 do_work 函数里做实际处理。若要补丁化某个可能被 do_work 调用的函数，则补丁施加时该函数不得正被任何线程执行、也不得出现在任何线程的调用栈上——即它必须不活跃〔01:19〕。单线程情形下静止会在 do_work 返回之后自然到达；若有补丁待施、工作线程就在屏障处等待其余线程抵达同一点，全体线程都停在屏障上即称全局静止，随后由专门的补丁线程施加补丁并恢复各工作线程——屏障法就是多线程用户态进程打补丁的业界现状〔02:25〕。在 OpenLDAP 上实测很差：响应速率在补丁请求后很快掉到零、补丁完成后积压才得到处理、在接近两秒处形成尖峰；最大延迟先出现一段完全没有延迟（速率已归零）、随后冒出约一百五十毫秒的尖峰〔03:17〕。原因是长计算阻止线程抵达屏障、以及可能无界的 I/O；另一问题是线程间依赖可能引发彻底死锁——OpenLDAP 中没观察到、但 MariaDB 因事务中持锁而会出现〔04:02〕。这固然能解、却需大量应用知识且很容易做错，三条问题合起来让全局静止既伤性能又难做对〔04:37〕。内核方案的做法不同：一类反复探测静止而非阻塞等待屏障——在内核里可行（大部分时间本就在用户态）、但用户态中静止可能永远达不到、补丁永远打不上；另一类更进阶的方案（转写作 K-Craft）把补丁版函数与旧版并行安装、逐线程决定用哪一版，从而把全局静止降为线程局部静止〔04:49〕，但它被限制于函数重定向式补丁方法（新旧两版必须并存）、依赖调试断点与核间中断保证原子性、还因函数调用间接带来性能惩罚〔05:35〕。作者的目标是保留各线程独立打补丁即局部静止的思路、却不受内核补丁特有约束，于是给出地址空间代际方案并在 Linux 内核上实现〔05:59〕。实测上 wait-free 方式在补丁期间响应速率毫无变化、最大延迟也无显著变化，且因线程永不阻塞于静止屏障、线程间依赖导致的死锁不复存在〔06:47〕（YouTube EPZ14ykUbWnjY，[8-425]，L1）
- 〔OSDI '20〕机制上每个进程初始只有一个地址空间、其中文本段有一处待补丁。内核扩展提供新系统调用 wait_free_create：像 fork 那样克隆整个地址空间、但克隆留在当前进程内部、内存区域在克隆之间共享而无 copy-on-write；另一关键差异是映射变更会被同步——新建、删除映射或修改访问权限都会同时作用于所有克隆，因此逻辑上它们仍像同一个地址空间。补丁需要例外：借助 write-through pin 标记某些映射不参与代际间共享、退回普通 copy-on-write，且须在首次 wait_free_create 之前完成，之后即可只在新的一代里修补问题区域〔07:24〕。再由新系统调用 wait_free_migrate 把各线程迁入新一代；线程仍在同一进程内、经共享映射通信，代亦可删除。显性限制是只能补丁代码、不能补丁数据结构或数据解释方式——数据在全部代间共享、处于不同补丁状态的线程同时访问同一数据必然冲突〔08:41〕。回到 OpenLDAP：把全局静止转为局部静止时，补丁器只需创建新代、迁入并打补丁、完全不牵动工作线程；工作线程各自到达局部静止点后再迁移；任何全局静止点自动可作局部静止点、而局部静止点更多、往往更易到达〔09:33〕。Linux 实现上地址空间以内核中的 memory map 结构表示。wait_free_create 像 fork 一样复制 memory map，被 pin 的页例外；wait_free_migrate 只是改掉线程的 memory map 指针并做一次上下文切换。难点在映射变更：改变地址空间拓扑的操作必须同时作用于所有兄弟代，故所有做映射变更的系统调用与内核函数都要改造；扩展匿名映射（如堆）时页由缺页惰性分配、同样需同步，而立即复制到所有代会成瓶颈，于是也惰性处理——把最初的 memory map 特殊化为主 memory map、分页先在它上面执行，其他代缺页时先查主 map 并复制其已有页表项。代价是主 memory map 不可删除、贯穿进程整个生命周期并兼作所有代的锁代理；扩展约两千行代码、基于 Linux 5.1、在 AMD64 上测试〔10:27〕。评测选了 OpenLDAP、Apache、Memcached、Samba、MariaDB 与 Node.js 六个服务器应用；补丁取自 Debian 10 及其维护者的全部补丁（括号内数字为关联 CVE 的关键补丁），因只支持纯代码补丁、改数据结构的被丢弃但仍剩百分之八十七〔13:10〕。二进制补丁由改造版 kpatch 生成、另写一个小用户态库，既可走本扩展的局部静止、也可走标准屏障法的全局静止〔13:38〕。对比方法是在高负载下测请求延迟、反复用屏障法建立全局静止或改用 wait-free、每基准重复一千次〔14:38〕。OpenLDAP 延迟通常在零到四十毫秒、全局静止下会出现约一百四十毫秒长尾而局部静止没有；MariaDB 更极端：全局静止延迟均匀分布且超过一秒、wait-free 的九十九点五分位低于八毫秒〔15:00〕。开销上新建地址空间代从 Memcached 的八十八微秒到 Node.js 的约两毫秒、代际迁移仅五到八微秒；常驻的主 memory map 带来永久内存开销、但只影响调用过 wait_free_create 的进程、最高约一千八百千字节〔15:58〕。作者还设想该机制可用于 JIT 并发重编译而无需改代码指针、在内核态做路径相关优化、支持动态能力管理、在线程间隔离关键数据，并主张内核中应进一步解耦进程与地址空间两个概念〔16:48〕（YouTube EPZ14ykUbWnjY，[425-1128]，L1）
- 〔PEPR '23〕本演讲讨论差分隐私在有限精度计算机上的真实漏洞：连续数学定义的 Laplace 机制一旦用浮点朴素实现、分布之间就会留下浮点数永远到不了的洞，使攻击者能仅凭输出反推真实输入；修复关键不在噪声生成器、而在于把整个加噪声步骤替换为直接采样并以严格证明对齐实现与理论〔00:09〕。差分隐私的立意很简单：给统计量加统计噪声、使一个人的影响不可被检测。示例问题是数据库里有多少条记录——若真实为一百或一百零一、你都不该能分辨；Laplace 机制可证明地做到，因为两场景的分布形状彼此至多相差两倍、一种场景下的回答在另一种场景下也能以相近概率出现〔00:16〕。问题在于论文里的机制用连续数学定义、要完美实现就得返回无限精度的数、而计算机没有无限精度〔01:36〕。若朴素实现这一步噪声加法并把两条曲线放大看，得到的浮点数分布已不像直线：红刻度代表浮点数、箭头指示每个分布实际能达到的值。坏消息是分布并不能覆盖所有可能取值——有些值只能由一个分布达到而另一个到不了〔02:07〕。例如取到 3.75 时便可断定真实答案是 101、因为另一条线到不了那里；而这恰恰是差分隐私本想避免的事〔02:36〕。朴素实现是：先生成两个随机量——一个符号决定加正还是负噪声、另一个是零到一的均匀随机数，再代入数学式得到噪声值、最后返回真值加噪声〔03:07〕。十年前差分隐私研究者 Ilya Mironov 就指出：向 Python、Java、C++、Go 等标准库索要零到一的均匀随机数时、库并不会给出所有可能值、通常只生成五十二位——即某个很大的整数除以二的五十二次方，因极接近零、需要极高精度的那些值永远取不到；把它送进公式就制造出那些洞〔03:45〕。这件事发生在二〇一二年、距今逾十年〔04:10〕。做浮点原语时他们本以为问题早已解决、直接取现成方案即可，结果发现各家做法不一，只有两种尝试：一是改变噪声生成方式以避开洞、二是合并多个噪声采样以最大化随机性让人难以反推洞的位置；关键在于这两条来自不同平台的路子都没有附带安全性证明〔04:28〕。于是换个角度追问：即便噪声生成完美无缺、把它加回真值那一刻会发生什么〔05:31〕。观察浮点轴上以二幂为界的区间可知、数越小其周围区间越短——一二之间的数都是二的负五十二次方的倍数。对精度为二的负五十二次方的 1.25 加噪声分两种情况：噪声小（绝对值小于零点五）时和不会偏离原值太远、精度至多下降一层、故和总被舍入为二的负五十三次方的倍数；噪声大时噪声自身精度也是二的负五十三次方及以上、两个这样的倍数相加仍是它的倍数〔06:08〕。一般化即：向某精度的区间中的数相加、结果总落在下一级精度的倍数上〔07:41〕（YouTube EPZ2OugolaoVA，[9-466]，L1）
- 〔PEPR '23〕把这个结论用到 1.25 上就很致命：把加噪声后 1.25 的可能输出、与对 0 加噪声（无上述精度问题）的输出相比，若某个和的精度小得过分、就能断定它必然来自真值为 0 的分布——否则不可能在与原值相加时落到这么小的精度上。也就是说十年之后我们只是回到起点：仅凭输出就能猜出选的是哪个数〔07:51〕。修复思路由 Sam 接手：既然和本身也敏感、就必须一次性修好整个例程——单独把噪声生成做安全不够。总思路是不先生成噪声再加回真值、而是直接以真值为中心生成想要的整个分布：先给出以一百为中心的 Laplace 累积分布函数，再用逆变换采样——取零到一之间的数、经累积分布函数的逆变换为样本、最后舍入到最近浮点数返回〔08:47〕。可惜浮点使这一切无法精确完成，于是改为模拟：不从 y 轴采样一个值、而是采样一个区间。第一步把零到一区间对半分并选一半、再用累积分布函数的逆变换为 x 轴上的区间，这一步叫区间细化；此后每步采一个比特、把区间一分为二、再做变换。区间端点用任意精度浮点表示、可细化到任意小与任意准〔09:42〕。何时停止？放大到曲线已像直线、x 轴上可见连续浮点值时、看区间两端四舍五入到最近浮点会分别落到哪：若落在两个不同值上、因不知那个假想实数落在区间何处、也就不知它会舍入到哪个值、必须继续细化；一旦两端舍入到同一值即可终止并返回——无论实数落在何处都会舍入到同一个值。因此整个流程恰好模拟了采样一个实数并舍入到最近浮点〔11:00〕。还有个细节：累积分布函数的逆算不出精确值（其中含对数），于是对 y 轴每个端点算出 x 轴上一个包含真值的区间、再用左区间左端点与右区间右端点构造最终区间——最终区间略大、其余步骤不变〔12:19〕。作者认为有三点漂亮之处：借假想实数这条论证、算法与采样实数后舍入到最近浮点等价、因而易于给出满足所愿隐私保证的证明；演示虽用 Laplace、换成其他噪声机制同样适用；理论与实践上都收敛很快、一个实用优化是每次迭代采多个比特（如五十位而非一位）、此时算法几乎总在一两次迭代内终止〔13:11〕。三点收获：差分隐私确实会有漏洞；发现漏洞时不该想着如何让这一个漏洞消失而做权宜之计、而应给出实现与理论一致的证明；好消息是常常能找到有原则的做法、在保持简洁高效的同时根除这类漏洞。防住它需要什么？什么都不用做、只要用带已证明修复的库。开源盘点是：仍有两个库有漏洞、其中一个已无人维护；OpenDP 起初有此漏洞、后用分布的离散版本修复（与 Google 做法类似、但略损隐私保证），本方案不需任何离散化参数、适用更广泛分布。最后致谢：这一切若没有开源代码根本无法做到〔14:19〕（YouTube EPZ2OugolaoVA，[466-937]，L1）
