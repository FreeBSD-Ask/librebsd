- 〔会议不详〕不可变的几种实现模式、Digital Rebar 演示与问答。讲者先厘清 SRE 视角：这种“要一个状态、给一台机器”的黑盒背后有大量隐藏操作（重置、初始化、配置、测试、加入集群），不可变要求操作透明、不隐藏操作，且 create-destroy 必须可靠；若云商不返回实例或返回坏机器，团队会被逼回“机器能用就别动它”的旧习惯。模式一是 baseline 加 reset：照旧跑完配置脚本，但要打补丁时改为重置机器、清盘再复用，卫生度高却慢、仍需解析依赖图，是很好的第一步；模式二是内存 live boot（不必用 CoreOS，多数操作系统都支持），刷新只需重启一次，攻击者留下的改动一次断电即被抹除，但引导基础设施就此成为关键路径——真正的 HA DHCP 极少见，电力闪断后全机同时上线压力极大。模式三是 image deploy：在流水线里（常仍用配置管理工具）构建纯净镜像并直接写盘引导，配置量与配置时间大幅下降，但仍需初始化阶段（仅让 chef/puppet agent phone home 不够，因为机器身份没有重置），也不必一机一镜像；实测比常规 netboot 快约 5 倍——演示中在笔记本上用三分钟完成整机重启、镜像落盘、CentOS 启动可用，而传统 netboot 装 CentOS 约九分钟，若再装 Kubernetes 要十五到二十分钟并依赖会场网络；镜像并非魔法产物，仍需在某处配置一次再全舰队复用，存储上只保留已知良好的快照用于回滚即可。Demo 基于 Digital Rebar 的 UX 与 CLI：机器首现后内存 boot（基于 CentOS）进入等待态，再由工作流部署镜像、cloud init、标记完成，Windows 因需多次重启不能把首次重启当作完成。问答环节：约 10% 听众已在用类似流程、约 20% 在考虑、约半数能可靠零接触拉起服务器；依赖图每天都在变，两个月前的构建可重现概率很快趋近于零；对状态化裸金属建议把数据盘与系统盘分离、依赖复制冗余，先做无状态再推进状态化。（YouTube EPSomEsVvolz8，[1130-2260]，L1）
- 〔会议不详〕Yuan Kang 报告自动检测错误处理缺陷的工作。错误处理不当是主要安全缺陷来源，OWASP 把它列入十大问题，并催生过许多足以单独获得 CVE 的漏洞；在 C 中尤为突出，因为没有内建异常处理机制，错误约定全靠自己——有的函数出错返回 0，有的返回空指针，遵循所有约定既繁琐又容易出错。报告举了一个真实 CVE：在某流行 TLS 库（GNU TLS）里，程序调用一个检查证书是否属于证书颁发机构的函数，而 CA 可以签发任意证书，因此该校验出错意味着攻击者只需签一张证书就能冒充任意身份。程序检查返回值是否为 0，看起来合理；但该函数在出错时让 result 小于 0 并直接跳到末尾返回该值，而调用方不检查负值，把 result 置为 1，于是攻击者用一张畸形证书即可冒充任何人。这类问题难以被发现：错误很少在正常执行中出现，导致传统测试以及静态、动态分析都很难碰到；即便出现，也通常不是显眼的崩溃，只是产生错误结果。因此需要一个错误 oracle 判断错误是否被正确处理，手工为每个函数写规则既枯燥又不可扩展；还有缺陷定位难题——这类静默缺陷的出现点往往远离成因点。工具 EPIX（转写多处音写为 Apex、Apic、Epic、ePAX）名字取自 error path exploration：由于路径很多，它对可能失败的被测函数只在其调用方内做欠约束符号执行，并在这些较短路径里只关注错误路径（即被测函数可能返回错误码的路径，依据是说明每个函数出错时可能返回哪些值的错误规格）。判断是否为缺陷时检查三种通用错误处理方式：仅记录日志、通过返回值等方式向上游传递、或以错误码终止程序；三者皆无即判为错误未处理并报告缺陷。（YouTube EPSotmydHlcyA，[11-685]，L1）
- 〔会议不详〕EPIX 的完整流程、规模评估与误报分析。向上游传递不必完全逐字传递：错误码可被调用方转换，因此错误规格里还包含错误协议，只要调用方返回落在约定范围内的值即视为错误已被传播处理。聚焦调用方还带来定位便利——缺陷被定位在调用方首次停止处理错误的位置，因为此后不再有可靠信息可用于判断。局限是：错误规格写错会把非错误路径误判为错误路径，路径探索不完整会暴露不可行的有缺陷路径，二者都产生误报；缓解办法是跨同一被测函数的各调用点比较，找出错误处理的不一致处并据此优先报告，例如某函数的失败在所有调用点都被忽略则不予报告。用 GNU TLS 例子走一遍：在被测函数内部若 result 非负则置 0 返回，按错误规格 0 不是错误码，该路径非错误路径并停止探索；若 result 小于 0 则返回同一负值，构成错误路径，而调用方返回 1——按 GNU TLS 的错误协议 1 恰恰不是错误值，又无 exit 或日志调用，因此判定错误未处理、确为缺陷。错误规格并不难写：多数函数只遵循少数错误码，通常返回宏或枚举；二百五十六个函数的错误规格只有三十八种唯一规格，且库函数的规格可跨应用复用，另有自动生成错误规格的工作将在次月的 ASE 会议报告。实现上以 KLEE 的静态分析引擎对 C 代码做欠约束符号执行并挂自定义 Clang checker（六百一十七行 C++），最后是二百二十七行 Python 过滤脚本；它在编译期挂钩构建环境完成检查，不依赖测试覆盖。规模评估：九个流行开源项目、八十六万七千行 C 代码（四个 SSL/TLS 库与五个使用 OpenSSL 的应用），EPIX 报告一百三十二个缺陷，其中一百零二个为真、二十八个为误报，精确率百分之七十八；因为只看错误路径，它比 Clang 自带的除零 checker 略快，但远慢于无检查的编译，仍适合集成到夜间构建。真实缺陷包括：返回值根本没被读取，导致后续读到损坏数据；随机数函数出错返回 0 或 -1 而调用方只检查负值，使初始化向量可能不随机、加密更易破解；指数运算失败时返回已分配但未初始化的变量（按错误协议，返回指针的函数应返回空指针），导致生成的密钥偏弱或失效；GNU TLS 的 OCSP（在线证书状态协议，负责证书吊销）出错时只把时间值置为负值而返回值表示成功，调用方只检查返回值，最终用无效的时间值做比较。误报多源于 KLEE 一次只看一个源文件、跨文件调用的符号执行信息丢失；这并非 EPIX 的根本缺陷，它与具体符号执行引擎解耦，引擎改进后误报会减少。工具代码已在 GitHub 开源。（YouTube EPSotmydHlcyA，[685-1370]，L1）
- 〔USENIX ATC（推测）〕新加坡国立大学的 Bing Gao 报告论文《Scalable and Effective Page Table and TLB Management on NUMA Systems》，为与 Horizon Quantum Computing、伦敦玛丽女王大学合作的工作。NUMA 是后摩尔时代扩展系统性能的手段：每个 CPU 直连一片内存模块构成 NUMA 节点，节点之间靠 inter-CPU 连接通信；在 NUMA 系统上，本地与远端内存访问在延迟、带宽与能耗上差距巨大，在八 socket 机器上量到的内存访问延迟相差达 10 倍。现有 NUMA 研究多聚焦于确保数据本地访问（把数据放到线程附近，或把线程调度到数据附近），却很大程度上忽视了关键的操作系统数据结构，尤其是页表，因此本工作专注页表在 NUMA 上的放置。第一类问题是页表读：地址翻译时在 TLB miss 期间读取页表，但当前操作系统的页表放置不感知 NUMA，频繁的远端访问代价很高——即使数据是本地的，页表不本地就不最优。第二类问题是页表更新：内存分配与释放、或应用调用系统调用修改页表读位（例如 unprotect）时会发生更新，随后所有运行该进程的核都要执行 TLB shootdown，开销很大。背景上，页表通常用 radix tree 组织，从主存读一条页表要四到五次内存访问来遍历，非常昂贵；TLB 靠近 CPU 核缓存翻译结果可省去走表开销，但引入 TLB 一致性问题——某核要把虚拟地址 VA1 从 PA5 重映射到 PA8，需向运行同进程的所有其他核发 shootdown 信号，等它们刷新条目并回送确认后才能继续运行，极其昂贵，在 NUMA 上因信号需穿越 inter-NUMA 连接而更贵。他做的 mprotect 基准（仅一个线程修改页表并访问数据，其余线程空转不碰任何数据，实际只有那一个线程用到 TLB）显示，随空转线程数增加运行时间持续变差、性能劣化可达 40 倍，根源是 TLB shootdown 数量增加；双 socket 受控实验还表明，大数据应用的执行由页表读主导，即使数据本地，页表不本地也会显著影响性能。既有最先进方案（转写音写为 Mid-Noise、Mid-Oils）在每个 socket 上复制页表以解决页表读问题，却解决不了页表更新与 TLB shootdown 问题。（YouTube EPSpS0VrDa8nc，[16-490]，L1）
- 〔USENIX ATC（推测）〕Hydra 机制与评估。Hydra 是一种惰性、部分、选择性的页表复制方案：自动在 NUMA 节点之间复制页表项，按需让线程本地访问页表，既保证页表读为本地访问，又主要通过减少无副本节点上的 TLB shootdown 来让页表更新变便宜。关键在于 Hydra 额外记录哪些节点持有哪部分页表副本：若某节点没有副本，则该节点的线程从不访问页表，其 TLB 中也不会缓存页表条目，因此发起 shootdown 前先查副本信息，跳过没有副本的节点。例如四节点上只有节点 0、1 持有页表副本、节点 2、3 无副本，线程 3 需要访问节点 0 上的数据时，Hydra 惰性地把对应页表复制到节点 3，此后即可本地访问。评估亮点：在 mmap/munmap 类实验中，基线每次映射或取消映射都要向其他 socket 发 TLB shootdown 从而变慢，Hydra 优化后取得 15 倍加速，原因是减少了 TLB shootdown 数量；在通用数据分析负载的页表读场景下，Hydra 的加速与既有最佳方案相当，而且由于既有方案要在每个 socket 上创建完整页表、创建耗时更长，Hydra 初始只需创建部分副本，开销更小；内存足迹方面，既有方案为页表维护约 8 倍空间（Linux 基线约 0.2 倍），Hydra 只在各节点保留最小必要副本，占用更少。结论是 Hydra 消除了页表读与更新上的 NUMA 效应、保证本地地址翻译、避免不必要的 TLB shootdown 从而优化页表一致性性能，并让页表更新操作能在 NUMA 系统上扩展，同时保证页表副本的最小内存足迹，使页表读与更新可扩展到大规模 NUMA 系统。（YouTube EPSpS0VrDa8nc，[490-984]，L1）
- 〔USENIX Security（推测）〕报告介绍网络侧信道如何威胁互联网应用隐私，以及首个基于差分隐私给出精确数学保证的缓解系统 NetShaper（与不列颠哥伦比亚大学 CIST 实验室同事合作，转写音写为 Cistopia Lab）。在加密的客户端-服务端通信中，攻击从不攻破加密：公共互联网由交换机、路由器等构成，ISP 或国家级对手能观察链路上的传输大小与传输时机，即流量形状，因为加密并不隐藏这些信息；已有工作表明这足以推断客户端访问的是哪个网页或视频（会前一场报告刚展示过它如何泄漏 ChatGPT 对话）。已有缓解手段各有短板：流量切分把数据走多条链路，带宽开销低但网络运维成本高，且无法对付能监视所有路径的 ISP 或国家级对手；流量整形改写包的大小与时机使其与秘密无关，其中恒定速率整形（等大小包、等间隔发送）能隐藏流量形状透露的信息，但不自适应流量状况，代价是高带宽占用、高延迟或两者兼有；变速率整形策略则以一定隐私损失换开销，却普遍没有形式化隐私保证，也不一定能挡住已知与未来的攻击。为此 NetShaper 提供基于差分隐私的形式化隐私保证，并让用户可配置隐私与开销的取舍。差分隐私源自数据库领域：两个只差一条记录的数据库上做 sum 等聚合查询，可从输出判断查询跑在 D 还是 D' 上；做法是给查询加噪，噪声由 epsilon 等 DP 参数决定，使概率比有界于 e 的 epsilon 次方，epsilon 即用户愿意牺牲的隐私量，论文实际采用 (epsilon, delta) 差分隐私；DP 还有组合性，可量化多次查询累积的隐私损失。网络流是动态的，直接套用并不容易，NetShaper 的做法是：以固定间隔 T 发送数据，用缓冲队列在每个 T 内缓存应用未整形的字节流，队列大小即原始查询；对该查询加噪（噪声可为负）后，若噪声为正则补 padding 入队到指定字节数，若为负则只入队指定数量，再加密使数据与 padding 在网络上不可区分后发出，于是包大小在时间单位 T 上满足 (epsilon_t, delta_t) 差分隐私；把长度为 w 的流看作固定数量 T 间隔 burst 组成的“数据库”，即可用组合性计算整条流的隐私损失。（YouTube EPSqzdH4rBjZc，[8-360]，L1）
- 〔USENIX Security（推测）〕NetShaper 的中间盒设计与评估。系统里用户按整条长度为 w 的流配置 epsilon 与 delta：epsilon 越大隐私损失越大，但带宽开销越低，用户可按应用需要自由取舍；每个方向独立整形，双向的总隐私损失同样用组合性计算。落地时以网络隧道抽象来施加整形策略，隧道端点须覆盖对手可观察的网络路径，并设三条安全设计目标：隧道必须正确实现 DP 机制、保证隧道内所有流量都是差分隐私的；网络上所有字节无论数据还是 padding，在底层网络协议层面都必须不可区分；端点应用不得影响隧道内的整形。端点被设计成模块化、可移植的网络中间盒，通过常规 socket 接口与客户端或服务端通信、可充当代理，无需修改端主机；实现底层用 QUIC，但原则上任何可靠网络协议都可替换；整个程序位于用户态，不需要修改内核；多条流共享同一隧道时可摊薄开销。评估覆盖安全性与性能：用跨洲两台虚拟机采集带真实网络噪声的基线流量，对两种先进分类器（BDT 与 burst attack）及自研的 TCN 分类器测试；在五分钟视频流上，不做整形时分类器识别准确率极高，而 NetShaper 故意使用实验室同型号机器（无网络噪声、对手最强情形），epsilon 低于 200 时分类器基本无法准确工作，即便 epsilon 大到 1000（意味着低带宽开销）攻击也无效，说明其隐私保证远超抵御当前攻击所需，而理论保证还能覆盖未来攻击。开销方面：增大 DP 间隔 T 会减少测量队列的次数、同等隐私下需加更少噪声，因此带宽开销下降，多流共隧道可进一步摊薄；客户端响应延迟随 DP 间隔线性增长且主要取决于该间隔，总体上隐私、延迟与带宽开销是三者权衡，系统提供配置框架。结论：NetShaper 是首个模块化、可移植的差分隐私网络侧信道缓解系统，提供可量化的理论保证，并已开源。（YouTube EPSqzdH4rBjZc，[360-723]，L1）
