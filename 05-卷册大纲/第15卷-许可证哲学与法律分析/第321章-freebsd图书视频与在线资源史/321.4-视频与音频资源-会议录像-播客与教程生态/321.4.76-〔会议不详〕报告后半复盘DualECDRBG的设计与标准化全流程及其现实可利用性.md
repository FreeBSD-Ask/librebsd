- 〔会议不详〕报告后半复盘 Dual EC DRBG 的设计与标准化全流程及其现实可利用性。G 输出为椭圆曲线点 x 坐标且分布有偏，需恰好舍弃 16-17 位——丢多了陷门失效、丢少了偏置明显；标准化绕开可能说 no 的 NIST，先走 ANSI X9F1 工具委员会的私有流程，其间 Dan Brown 与 Scott Vanstone 以利用 P/Q 关系做密钥托管的专利向委员会施压，NSA 通报 RSA 已用现有标准参数实现 Dual EC，迫使标准只新增可选的自选参数机制而保留原 P/Q 为默认值，随后进入 NIST SP 800-90，NSA 又接管 ISO 标准编辑并恰恰删去了自选参数机制，Microsoft、Cisco、BlackBerry 乃至 OpenSSH 相继实现。针对 NSA 的 Dickie George 在视频中现实难以利用、论文数学不实际的说法，讲者介绍周四主会论文：TLS 只给 28 字节 server random（时间戳占 4 字节，需猜 2^32 个值）、部分实现的最多 32 字节随机 session ID 则有帮助；据此提出 kleptographic friendly implementation 概念（默认使用该 RNG、缓存输出使各字段来自同一 G 块、避免 NIST additional input、支持 512 位曲线、带指纹检测机制）；RSA BSafe 产品中发现了 NSA 的 Eric Rescorla 与 Margaret Salter 撰写、未采纳的 Extended Random RFC 扩展，可将 server random 扩到 2^16-1 字节，配合 BSafe 的缓存每会话可得 31-60 字节连续随机数，攻击仅需约 2^16 计算量，而其他实现仅 28 字节需 2^32；OpenSSL 用 NIST additional input 投熵的缓解也可被击破，代价约 2^k×83 分钟——给定一条 TLS 会话的 pcap，持陷门者至多数百分钟甚至不到一分钟即可完全解密会话。结尾讨论 Intel RDRand（若 AES DRBG 更新密钥被替换则可类似利用）作为 kleptographic 实现的未来形态，并回应微代码更新后门与黑天鹅式问题。（YouTube EPCQGkhCPN_KM，[925.0-1850.1]，L1）
- 〔USENIX SREcon〕SREcon 21 上 RackN 的 Rob Hirschfeld 带来构建优秀基础设施管线的九个问题，是其基础设施代码自动化系列第三章（一年前的第一章谈裸金属自动化，LISA 21 的第二章谈基础设施即代码与物理基础设施的挑战）。核心症结是复杂性：环境复杂且孤岛化，工具只在自己的层或应用集内有效，叠加多层并用不同工具使跨层顺畅自动化更难，因此要建设类似 CI/CD 但面向基础设施的自动化管线。第一组问题辨析概念：CI/CD 管线沿单向流动物件，而基础设施是资源模型，资源状态、环境约束、生命周期与配置漂移是理解系统的关键，物理资源尤其持久，不是单向不可变过程；管线与编排不同——管线以目的地为导向、结果可预测，编排则充满分支与 if-then。他强调把意图（outcome）作为抽象边界：用户只声明要一台 Kubernetes 就绪的机器，不关心管线内部，管线天然是集成点而非手动旋钮。他还区分系统内配置（Ansible/Chef/Puppet 的加固与装应用）与系统外置备（PXE 启动、网络安装、Terraform），并指出监控与集群协调是另外两种上下文，管线需在这些自动化类型间切换而非堆叠；状态共享是命门——Terraform state、Ansible inventory 各自垄断真相、不对外分享，把工具限制在其强项内使用、标准化状态与需求的传递才让管线强于各部分之和。（YouTube EPCQgC6mHFgkQ，[12.7-750.3]，L1）

- 〔会议不详〕讲者 Anubhav（与 TU Munich 及东京理科大学同事合作）报告 MicroShell——基于微内核的 FPGA shell 架构，并感谢工件评估委员会授予杰出工件奖。FPGA 因高性能、高能效与可重编程已被主流云厂商广泛部署；当前模型把 FPGA 分为 shell（静态区，像 OS 一样把 FPGA 管理为一组 vFPGA 并提供共享服务）与动态区（可重配置区域），应用经综合为单一比特流后经 shell 部署，一个应用占一个 vFPGA，即单体（monolithic）模型。这与真实云应用模块化、可组合的本性不匹配：视觉应用（decode+DNN+encode 流水线）中把 DNN 换成 DNN+ 需重建重部署整个应用（灵活性差），第二个应用即使共享 DNN+ 也要单独比特流重复部署（资源低效）。现有 shell 缺三样东西：vFPGA 之间没有访问控制的隔离、数据通路静态或不安全的模型组合、以及没有模型共享策略导致重复部署与资源闲置的调度。MicroShell 的关键思路是把微内核原则用于 FPGA shell：capabilities 做 vFPGA 间隔离、IPC 做动态模块组合、调度支持模块共享，三原则对应三挑战；硬件上由能力执行单元 CU（memory gateway 与收发 gateway 两类校验检查点，配合经 IPC 机制的路由信号）验证每一次访问请求，OS 上的 capability manager 以树形空间管理对象能力与内存能力，由于能力是不可伪造令牌，实现软件管理、硬件强制的细粒度隔离。（YouTube EPCRy27xXDIHI，[18.6-422.6]，L1）
- 〔会议不详〕后半讲安全 IPC、组件感知调度与评估结果。数据互连（data interconnect）动态路由数据流以实现 MicroShell 的安全 IPC，覆盖 vFPGA 到内存（互连把 vFPGA 接到 DMA 引擎）与跨 vFPGA（经路由信号在 vFPGA 间设直连路径）两种情形，补上既有设计一直缺失的组合；组件感知调度围绕三策略：高优先级应用优先部署到 vFPGA、高优先级放不下时以低优先级应用回填（limited priority inversion）提升资源效率，以及关键的组件重叠——应用复用已部署共享模型、提升部署顺位并只部署新模块。评估在 AMD 服务器（跑 MicroShell OS）+ Alveo U280 FPGA（跑 shell）上进行，以最先进的单体式 shell Coyote v2 为基线、五个真实应用为基准：拆分应用跨 vFPGA 后吞吐仅因数据互连与 CU 的固定开销略降，几乎保持一致；部署时间上 Coyote 因无法共享模型需 58 毫秒全量重配置，而 MicroShell 复用模型使部署成本降低数个数量级；应用数从 8 增到 16 时，Coyote 重配置次数线性增长，MicroShell 因复用而保持低位恒定，重配置最多减少 79%、deadline 违约最多减少 69%。工件已公开在 GitHub。（YouTube EPCRy27xXDIHI，[441.5-866.7]，L1）
