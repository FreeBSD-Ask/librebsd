# 321.4.90 〔会议不详〕BFS枚举增量轨迹检查与评估应对并发用BFS枚举所有可能的in消息顺

- 〔会议不详〕BFS 枚举、增量轨迹检查与评估。应对并发用 BFS 枚举所有可能的 in 消息顺序以覆盖全部执行可能，并通过"推断"（从 out 消息反推当前 term、日志位置、本节点是否 leader 等）高效判断某状态是否允许发送该消息，同时剪枝探索；应对轨迹增长用增量检查——每遇到一条 out 消息就找出能到达它的路径，把终点状态作为下一轮起点并移除已用消息。工具用 Go 实现，在 etcd、ZooKeeper、Redis Raft 三个开源 DBMS 上共复现并检出 10 个 bug；生产部署开销极低（仅占 2 核、无需网络资源，处理轨迹的吞吐至少为被测系统生成轨迹吞吐的 2 倍），结论称 RPRC 提供无需协调通信的本地运行时正确性检查。（YouTube EP-dQB2VN1kLc，[475.7-941.1]，L1）
- 〔FAST（推测）〕OPIMQ：面向多队列块设备的保序 I/O 栈。主讲人来自 KAIST OS Lab（转写作 Jian Kim，论文报告），指出多队列 I/O 栈天然无序：请求分散到各请求队列与 NVMe/UFS 命令队列后可被存储控制器或 FTL 重排，应用须用昂贵机制保证存储顺序（数据库日志与文件系统日志的崩溃一致性），这限制并行并增加延迟。2005 年随 eMMC 引入的 cache barrier 命令可保证按序持久化，但 barrier 式 I/O 栈只适用于单队列设备，Lazy barrier 限于 UFS、OPT-R 只支持单写流，其余方案（转写 Horey/CCM/VME/RIO）依赖专用硬件或低效排序。他们定义 stream（单线程发出的 I/O 请求集）与 epoch（由 cache barrier 界定、内部可重排但须按创建序持久化的写请求组），核心难题是跨队列的 inter-queue storage order：工作窃取导致核迁移会造成 epoch split，跨线程写则需跨队列保序。（YouTube EP-lLA9M3wU44，[16.0-438.1]，L1）
- 〔FAST（推测）〕OPIMQ 设计与评估。OPIMQ 由主机与存储协作保序：主机侧保序文件系统决定 cache barrier 位置、为每个 I/O 分配 (stream ID, epoch ID)，用 epoch pinning 防止核迁移导致 epoch split（新请求只写入迁移后队列），用 dual-stream write 让一个写请求同时携带两组 ID 承载跨流顺序；存储侧 OP-FTL 允许数据乱序刷写以吃满内部并行、映射表严格按 epoch 序更新（sibling-aware delayed mapping）。在 40 核服务器加 Samsung 980 Pro 上实现于 Linux 内核（EXT4 改造为 OP-EXT4）：fsync 延迟降至 legacy EXT4 的三分之一，Varmail/Dbench/SysBench 相比原生 Linux I/O 栈提升约 2.8-2.9 倍，epoch pinning 与 OP-FTL（Cosmos+ Open SSD 板卡）开销可忽略；OPIMQ 已开源。（YouTube EP-lLA9M3wU44，[438.1-887.0]，L1）
- 〔会议不详〕理解云系统中的 fail-slow 硬件故障。主讲人 Geng Dong 来自华中科技大学（与普渡大学合作，论文报告），把硬件状态分为健康、fail-stop 与新兴的 fail-slow（功能正常但性能低于预期）三类：Google 网卡曾骤降至 1kbit/s，阿里云发现 fail-slow NVMe SSD 可退化到 SATA SSD/HDD 水平，fail-slow 故障与 fail-stop 同样常见（年发生率 1-2%）。他们定义 fail-slow 硬件造成的软件层症状（FSH 值），以 ZooKeeper 因 fail-slow 网卡把序列化线程卡死、进而卡住持有锁的请求处理线程导致客户端报错为例；随后研究 5 个大型云系统（协调服务、文件系统、数据分析框架、数据库）中的 48 个 fail-slow 案例，发现过半导致节点服务不可用、约 20% 属静默（需系统规约才能检测），三大根因是无限阻塞、有 bug 的内部检查器与数据竞争，本质是 synchronized 与超时机制在慢硬件下的坏实践。（YouTube EP-peBeCYEyfY，[18.4-406.7]，L1）
- 〔会议不详〕故障注入测试框架的设计与评估。现有生产检测器（Panorama、Perseus 等）只能在故障已造成损害后发现，故障注入工具（FIT、Kronos 等）又忽视 fail-slow 特征、注入粒度粗，作者提出面向云系统的 fail-slow 注入测试框架（转写作 Save/sieve）：静态 fault point 分析器先识别由 synchronized 与超时保护的故障点（把 Java 代码翻译为字节码后找正确的 entry/exit 点、按超时机制配对起止时间），再自动插桩 hook 实现实现级的细粒度 fail-slow 模拟，配合注入控制器、故障值检查器与工作负载驱动完成测试。在 ZooKeeper、HDFS、Kafka 三个核心系统上检出 6 个新 bug（2 个已确认），案例研究与框架均已在 GitHub 开源。（YouTube EP-peBeCYEyfY，[406.7-808.7]，L1）
- 〔会议不详〕Breakwater：微秒级 RPC 的过载控制。主讲人是 MIT 三年级博士生（转写作 Inojou，论文报告），指出网络与存储变快、内存操作普及后大量 RPC 只需微秒级处理，但扇出流量下服务器会因负载不均、突发流量、故障重定向而过载：吞吐因 CPU 被包处理和请求解析侵占而下降，连 p50 都飙升，几乎所有请求违反 SLO。理想过载控制应保持服务器请求队列短而不空、把多余请求排在客户端，但服务器端 AQM 在微秒尺度下丢弃请求代价过高（包处理+解析成本与执行时间相当），客户端限速又需频繁探测服务状态。Breakwater 以请求排队延迟为拥塞信号，组合三个机制：基于信用的准入控制（credit pool 在未过载时每 RTT 加性增、过载时乘性减，客户端凭信用发请求）、需求投机（需求信息搭在请求上、对用尽信用的客户端投机发放信用以消除需求消息）与基于延迟的 AQM（排队延迟超过阈值才丢请求并立即回 reject 消息，作为罕见的安全网）。（YouTube EP-sXsEfnn5vA，[9.1-867.7]，L1）
- 〔会议不详〕Breakwater 评估。在 CloudLab 测试床上基于 TCP 传输实现 RPC 库，与 Dagger（微信微服务采用的优先级过载控制）和 SEDA（SEDA 架构的自适应过载控制）对比，指标为 goodput（延迟低于 SLO 的响应速率）。1000 客户端需求突然超出容量 40% 时 Breakwater 在 20ms 内收敛，而 Dagger、SEDA 分别需 0.5s、1.6s 才从拥塞崩溃中恢复，收敛后稳态吞吐仍高约 6%/5%；拒绝消息能在违反 SLO 前送达客户端（Dagger 崩溃期拒绝延迟达数百毫秒，SEDA 则从不丢弃请求），1 万客户端时吞吐退化最小、比另两者高 10%。结论称 Breakwater 是迈向多层级微服务过载控制的重要一步。（YouTube EP-sXsEfnn5vA，[867.7-1194.0]，L1）
- 〔会议不详〕Illumos 的历史：从 SunOS 到 Solaris 10。主讲人从内容可辨认为 DTrace 联合作者、时任 Joyent 的 Bryan Cantrill，从 Unix 战争后的年代讲起：SunOS 4.x 到 Solaris 2.x 是 BSD 内核与 SVR4 内核融合的痛苦过渡（Solaris 2.1 根本不可用），Larry McVoy 的 NSC Lite（后演变为 Teamware→BitKeeper→Git）才让开发得以进行；Solaris 2.5 由 Roger Faulkner、Jeff Bonwick、Tim Marsland、Joe Kowalski 等工程师接管发布决策并立 Bonwick 为 gatekeeper（早期 BDFL 模式），质量才真正过关。1997 年微软 Scalability Day 的假演示被华尔街日报识破成为 Unix 反攻的转折点，Sun 坚持全 Unix 战略吸引来被称为 Bonwick Youth 的一代人才，2001 年起 Bonwick 从零启动 ZFS、他与 Mike Shapiro、Adam Leventhal 做 DTrace、zones 由项目 Kevlar 更名而来，加上 SMF、FireEngine、Casper/最小权限等汇成 Solaris 10；他强调这些技术全部来自工程师个人而非管理层或市场需求文档。（YouTube EP-zRN7XLCRhc，[9.8-1099.3]，L1）
- 〔会议不详〕开源化、Oracle 关闭与 illumos 的诞生。Sun 系统深度专有的残留（libc 国际化代码、少量工具与驱动）使开源化举步维艰，2005 年 1 月首先开源 DTrace、6 月 OpenSolaris 发布，许可证选择文件级 copyleft 的 CDDL（在 Mozilla Public License 基础上清理，允许 EMC/Veritas 等专有驱动）。2007 年秋 Sun 把新发行版命名为 OpenSolaris 引发他所谓"开源导弹危机"、社区被压制，2009 年 Sun 被 Oracle 收购，2010 年 8 月 13 日的内部备忘录悄然停止源码发布（他称之为开源史上最可耻的时刻之一，社区贡献被变为专有）。同年 Garrett D'Amore（Nexenta）与 Rich Lowe、Jason King 等从重写被关闭的代码起步创立 illumos（2010 年 8 月 3 日以代码与演示发布），Oracle 核心团队出走 illumos 后陆续产出 ZFS feature flags、ref ratio、ZFS send/receive 进度、zone I/O throttling、STMF unmap、DTrace 的 CTF 感知 print 等创新，并把 Linux KVM 移植到 illumos 在 Joyent 生产运行（KVM 跑在 zone 内）； illumos 价值观是自由 fork、代码高于讨论、创新高于民主（引 David Clark"拒绝国王、总统与投票，相信粗略共识与可运行代码"），治理采用仁慈寡头制。（YouTube EP-zRN7XLCRhc，[1099.3-3840.8]，L1）
- 〔LISA（推测）〕窃听的风险：技术与法律。主讲人从内容可辨认为密码学家/安全政策学者 Susan Landau（与 Whitfield Diffie 合著窃听论文，其新书当年出版），这是一场面向系统管理员大会的政策演讲：中心化通信（固话经五级交换、手机经归属位置寄存器、Facebook/Gmail 等云端汇聚）易于依法搭线，而 P2P VoIP（Alice/Bob 在各 ISP 与 VoIP 提供商会合交换 IP 后直连）使窃听复杂化。她梳理美国窃听法制史：James Otis 反对通用搜捕状（writs of assistance）催生第四修正案（须特别描述搜查对象与场所）、Olmstead(1928)/Nardone(1937-1939)/Katz(1967) 判例、Title III(1968) 与 FISA(1978)，再到 CALEA(1994) 要求运营商在数字交换机中内置窃听能力、Patriot Act 把 FISA 窃听的"主要目的"改为"重要目的"并简化 pen register/trap and trace、FCC 裁决 CALEA 适用 VoIP，以及 2005-2008 年无证窃听曝光（Mark Klein 揭露 AT&T 旧金山机房把光缆分流进秘密过滤房间、USA Today 揭露成批通话详单）与 Protect America Act、FISA 修正案。（YouTube EP0AuzNzEX4Nw，[4.8-1862.8]，L1）
- 〔LISA（推测）〕窃听的实效、风险与原则。她用政府年度 wiretap 报告等数据说明拟议方案实效有限（绑架案年均仅约 6 起用 Title III 窃听对比 450 起；十年窃听报告中只有 1 次解密费力），而交易性信息（谁与谁通信）极有价值：Khalid Sheikh Mohammed 靠手机定位落网、Najibullah Zazi 酒店熬制过氧化氢炸药案靠三次急促通话发现、美国法警追逃从平均 42 天缩到 2 天。把窃听能力内建于基础设施带来真实风险：希腊 Vodafone/Ericsson 交换机被入侵窃听百余政府高官 10 个月（发现于 SMS 异常）、意大利 Telecom Italia 十年间非法窃听约 6000 人（约万分之一意大利人）、Cisco 开放架构的 recommendations（非强制）被 IBM 的 Tom Cross 指出可被 spoof、FBI exigent letters 无书面授权跟踪 7 名记者 7 个月；威胁谱系中内部人（Kim Philby、Bradley Manning）历史上最危险，Titan Rain、GhostNet 与 APT 代表国家级网络利用。她的结论：通信安全须为宪法序言"确保自由之福泽"设计、任何通信隐私的暂停必须短暂、应像 NSA 那样用 clever solution 与终端漏洞而非在基础设施筑后门；Q&A 涉及端到端加密、瑞典跨境监听法、印度/阿联酋要求 BlackBerry 设接入点，以及 carrier-grade NAT 下 CALEA 会话归属日志（每 8000 订户约 1TB/天、须存 7 年）的荒谬成本。（YouTube EP0AuzNzEX4Nw，[1862.8-4588.6]，L1）
- 〔会议不详〕Linux 内核释放后使用（UAF）漏洞利用自动化的挑战与 FUSE 的设计动机。主讲人来自中国科学院大学与宾州州立大学的合作团队，指出利用开发面临三重挑战：分析内核 panic 需大量人工、选择堆喷射对象与系统调用需深入内核专业知识、构造利用还需安全专家经验，既有工作如 heap spray、heap feng shui 与自动利用生成（如 Cyber Grand Challenge 开源的 AEG）未能覆盖真正的隐藏挑战。通过真实 POC 案例说明：悬挂指针的不同解引用途径能产生不同原语，POC 中只得到可控数据写可控地址的弱原语，而在 close 后插入带合适参数的 sendmsg 即可解引用漏洞对象并可能直接劫持指令指针。（YouTube EP0a69zKj1bQc，[10-586]，L1）
- 〔会议不详〕FUSE 三步流程与 15 个真实 UAF 漏洞的利用生成评估。FUSE 先结合 ftrace 与 KASAN 日志做日志分析提取关键信息（悬挂指针产生与解引用点、堆喷射时间窗口），再在正确时间窗口内用 Syzkaller 在悬挂指针产生后尝试各种系统调用以发现不同解引用方式，最后用符号执行检查预定义利用原语（最常见为指令指针符号化的 unconstrained state），配合自定义 concretization 策略与限制路径长度应对状态爆炸。可约束指令指针到 stack pivot gadget 以在用户空间执行 ROP payload 绕过 SMEP，或用函数 gadget 覆写寄存器以禁用 SMAP；对 15 个真实 UAF 漏洞，FUSE 辅助生成的利用多于公开利用，可对更多漏洞绕过 SMEP 并为两个无公开利用的漏洞生成绕过 SMAP 的利用，且通过不同系统调用多样化利用以绕过基于系统调用模式的杀软检测，失败案例包括 CVE-2015-3636 与 CVE-2017-7374。Q&A 中主讲人说明稳定 slab cache 上成功率可达 90% 以上，竞态漏洞因堆布局不稳仅约 15%，思路适用于浏览器但需应对堆隔离与延迟复用。（YouTube EP0a69zKj1bQc，[590-1247]，L1）
- 〔会议不详〕内核敏感对象识别的动机与敏感对象特征分析。主讲人对比三类防御路线：漏洞修补无法应对未知 zero-day，CFI 等软件与系统加固可缓解未知漏洞但不论系统是否漏洞都引入性能代价，而对象级保护通过校验敏感对象完整性在安全与性能间取得平衡，其前提是识别需保护的对象。识别途径有三：分析公开利用找到被滥用对象（无法发现尚未被滥用者）、按开发者意图与程序语义分类脆弱对象（结果可能偏离攻击者视角）、以及按特定攻击知识分析目标代码（如既有工作均聚焦特定利用类型、非通用解）。通过分析利用过程发现利用分为能力升级与能力拼接两部分：漏洞触发得到的溢出或覆写等弱能力需借助敏感对象升级为任意读写或 IP 劫持，示例中利用 MSG 与 TTV 抽象对象完成地址链接与函数指针调用实现 IP 劫持。（YouTube EP0ehaHbrW_Uc，[8-340]，L1）
- 〔会议不详〕Alpha EXP：知识图谱驱动的攻击路径生成与敏感对象分类。系统包含知识图谱构建、攻击测试生成与敏感对象分类三个单元：用知识图谱表达对象结构（成员）、内存读写操作及与用户态操作的关系，以静态与动态分析从内核提取知识；攻击路径生成框架通过状态池选取状态与用户态操作进行推理，推理成功则提升状态被选概率并标记相应对象为敏感。推理引擎采用基于规则的 Datalog 实现规则化推理；分类则从应用条件（kmem cache 能力、漏洞类型）与达成效果（写、执行、读能力）两个视角对敏感性分级。实验识别出 50 个写、81 个读、112 个执行对象，多于按开发者意图标记的数量，并划分为 12 个敏感级别；知识提取静态过程耗时 19 分钟、动态过程耗时 72 小时，启发式可提升攻击路径生成效率。（YouTube EP0ehaHbrW_Uc，[335-638]，L1）
