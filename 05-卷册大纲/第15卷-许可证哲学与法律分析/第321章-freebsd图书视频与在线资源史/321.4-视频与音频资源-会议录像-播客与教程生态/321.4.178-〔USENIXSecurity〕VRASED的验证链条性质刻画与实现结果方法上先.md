# 321.4.178 〔USENIXSecurity〕VRASED的验证链条性质刻画与实现结果方法上先

- 〔USENIX Security〕VRASED 的验证链条、性质刻画与实现结果。方法上先定义端到端目标“远程证明的 soundness 与安全性”，再形式化微控制器模型以推理新实现与既有行为的交互：软件侧复用已验证的 HMAC 实现（HACL 库、以 F*/Low* 子集编写，已验证功能正确性、内存安全与 secret-independence，因 Low* 不能自动翻译成 C 需可翻译后才能跑在 MCU 上），硬件侧自行设计，从 CPU 引出程序计数器、数据读写地址等约七个信号并据此陈述所有可能的“坏事”（例如执行期间越权读取密钥就立即发出复位命令），规范用线性时序逻辑（LTL，在命题逻辑上扩展时序量词，可表达“本状态发生 A 则下一状态必须发生 B”“A 永不发生”“A 直到 B 发生”），硬件设计成一组有限状态机并用 Verilog 描述，经自动转换工具转成验证语言 SMV、由模型检查器 NuSMV 证明组合体满足全部 LTL 规范，最后用 LTL 定理证明器结合密码归约证明组合结果蕴含目标。性质分两类：密钥保护（HMAC 所用对称密钥绝不能被非特权软件看到或访问）与安全执行（不能窥探或篡改证明例程本身，含原子性即必须一次性执行完毕、受控调用即必须从第一条指令执行到最后一条，并以受控调用给出两条 LTL 与对应状态机示例：当前执行地址在 HMAC 区间而下一时钟周期不在，则必须是最后一条指令否则复位），架构上把已验证 HMAC 放在只读存储器以获得功能正确性与不可篡改性（软件可被恶意程序改代码，故不可变性不可或缺）、其余靠硬件保证始终从首指令开始末指令结束且不被非特权软件中断、并通过访问控制与独立栈保证 malware 无法学到密钥；实现基于开源 OpenMSP430 Verilog 设计，硬件额外开销约 6%、能在半秒内完成对整个程序存储器的证明，并在商用 Basys3 FPGA 上完成综合，全部硬件设计、软件与证明均在 GitHub 开源可复现（还可借 Xilinx 捐赠计划免费获取 FPGA），问答补充这类设备有的根本没有 DMA、有的有（OpenMSP430 的 T430 变体支持 DMA）并可通过 DMA-enable 与 DMA 地址信号检查 DMA 触发的越权，作者还提出可构建在证明之上的服务——软件更新证明、擦除证明、复位证明与软件执行证明，把现场传感器的输出与其实际执行的代码绑定，即使软件被完全攻陷传感器也无法“撒谎”。（YouTube EPT4XpkIPAKas，[402-1151]，L1）
- 〔OSDI〕用大数据方法把关键路径分析扩展到 Facebook 这类大规模异构服务。报告人（未自报姓名，Facebook 工程师）以单次 Facebook 请求的水滴图说明问题：一张图同时暴露 Facebook 的巨大规模与异构性（PHP 执行、JavaScript 执行、网络字节传输各有颜色），但仅凭瀑布图无法推导出该请求的关键路径，缺的是段与段之间的因果关系或依赖；方法分四步：先识别请求中必须执行的段——请求由多个 task 组成，task 内的事件在整条请求生命周期中唯一且恰好映射到组件日志里的一条消息，两个唯一事件之间的时间区间即一个 segment，再凭这套最小 schema 聚合出端到端 trace，随后用大量 trace 推断整个系统的因果模型，最后把模型应用到单条与大量 trace 上做瓶颈与关键路径分析并汇总成系统级统计。之所以不用全系统插桩（工作量巨大，要为每个调度器与所有组件间通信插桩）也不靠召集工程师口述模型（不随系统演进扩展），是因为可以复用两项既有事实：Facebook 各组件已有大量日志只是格式各异、若能把它们聚合并会获得单次请求执行的巨量细节，同时请求量极大、即使低采样率也能获得海量经验观测连罕见行为都能观察到，实测仅用一个多月的时间就把这些异构日志统一成详细端到端 trace；因果模型假设所有可能的关系并逐条 trace 迭代反驳，三类关系为 happens-before（B 必须等 A 结束）、互斥（两段争锁）与流水线（段间必须按任务 FIFO 顺序），它们要么成立要么不成立、出现单一反例即被否决，在 6 组件示例中演示如何从“假设所有两两 happens-before”起步用每条 trace 的反例逐步剔除（如 S2 在 S1 之后执行则删去 S2→S1、N1 与 N2 并发则删去 N1→N2）。（YouTube EPT5IgnEqErRY，[10-660]，L1）
- 〔OSDI〕因果模型收敛成本、关键路径归因与 slack/what-if 分析。规模上，对一个月内约 130 万条 trace 与数十万候选关系，在 Hadoop 集群上约 2 小时即可收敛、因此可每晚作为批处理任务产出新的因果模型，并用传递归约简化呈现，关键路径则通过把模型中的依赖注入单条 trace 后跑标准最长路径算法求得；与“直接累加各组件时延并归入五类”的朴素做法相比，关键路径视角下服务器部分占的时延实际上是朴素法的两倍、而网络与 JavaScript 被高估，说明并发环境下必须依赖因果模型才能正确理解时延归因，更值得注意的是构成随请求剧烈变化——服务器对关键路径的贡献在最慢 20% 的请求里仅约 10%、在最快 20% 的请求里达 50% 以上，网络与客户端同理，网络或客户端快的用户受服务器生成速度限制、仍在拨号的用户被网络排队限制、老电脑用户被客户端 JavaScript 渲染限制，因此服务器、网络、客户端在任何时点都可能主导时延。由此引出调度优化设想：把用户分为有 slack 的慢用户（服务器生成更慢也不改变其端到端时延）与无 slack 的快用户（服务器更快可缩短其时延），核心思想是“按需交付而非越快越好”，slack 定义为组件可被延迟而不进入关键路径的时间，what-if 分析则用大数据集里的自然波动模拟更慢或更快的服务器；实证显示 slack 越大越能说明服务器生成时间影响端到端时延（快用户点贴近 y=x、慢用户呈一团无清晰规律），由于 slack 只能在请求结束后计算而无法用于调度前预测，最终发现过去 slack 是最好的预测特征（浏览器类型、操作系统都不如它），用 0.5 秒阈值把 slack 大于 0.5 秒判为慢用户，简单分类器准确率为 83%（其中 8% 误判为有 slack、9% 错过优化机会），问答中针对跨机时钟漂移说明做法是取同一客户端-服务器重复通信的最小 RTT 估算偏差（服务间对每次 RPC 估计）、同机内则假设时钟一致，并借 Magpie（OSDI'04）、WebFifteen（WWW'07）、Rake、XTrace（OSDI）等既有工作强调本作的价值在于复用既有日志快速落地同等分析。（YouTube EPT5IgnEqErRY，[673-1477]，L1）
- 〔USENIX Security〕µFUZZ：用微服务架构重构并行模糊测试。报告人先给出并行模糊的动机：现代 CPU 有多核、要充分利用资源就得跑多个实例，且要在更短时间内找到更多 bug 以跟上快节奏的开发周期，AFL/AFL++ 支持并行模糊、Google 的 OSS-Fuzz 每天为单个项目投入数十万 CPU 小时、ClusterFuzz Lite 也支持 CI 场景（如 GitHub Actions）中的并行模糊。当前最先进架构只是把多个基座模糊器实例并行运行、各实例内部仍串行且独立执行，并靠周期性同步语料来共享进度，其局限的根因在于底层模糊器并非为并行设计（AFL 是从语料中取用例、变异、执行、收集反馈的串行循环、每步按序发生），由此产生两大挑战：一是 CPU 周期被阻塞 I/O 浪费（循环中任一步被阻塞都会浪费 CPU 时间，例如 fuzz tcpdump 时 CPU 利用率只有约 70%），二是同步要么不及时要么昂贵（频率过低会让实例在废弃状态上做重复工作，频率过高则因依赖文件系统而引入大量阻塞 I/O），实验佐证是用 10 个 AFL++ 实例模糊被测程序 1 小时、同步频率过高或过低性能都大幅下跌、即便取合适频率仍远差于单实例跑 10 小时。为解决“既不浪费 CPU 又及时而廉价地更新状态”，作者从微服务架构中找到了契合点：该架构把应用组织为松耦合的细粒度服务集合并以轻量协议通信，天然并发（服务彼此独立运行）、可并行（每个服务可多实例运行），并通过服务间状态分区（数据分片）减少同步，µFUZZ 由此把处理循环拆成四个服务——语料管理、用例生成、用例执行与反馈收集，每个服务并发运行且各有多个 worker 以获得并行度，模糊状态在服务和 worker 间分区。（YouTube EPTDlr3ibxCP4，[9-300]，L1）
- 〔USENIX Security〕µFUZZ 的服务化拆分、两级状态分区与评测。模糊状态在服务间分区（corpus 由语料管理服务持有、覆盖率映射由反馈收集服务持有）从而松耦合并留出改进空间；为支持并发在每个服务输出端加缓存队列，输出先入队列而非直连消费者、消费者就绪时再从队列取输入，使生产者与消费者并发运行、任一服务因任何原因卡住其余仍可推进，为支持并行则在每个服务内加输入分发器做负载均衡，维护空闲 worker 的 FIFO 队列、服务收到输入后从队列弹出 worker 派发，遇到大输入先按空闲 worker 数切分再派发以避免一个 worker 独占巨大输入而其余闲置；状态分区分两级——服务级把整体模糊状态按服务划分、worker 级再把服务状态在其 worker 间划分（例如语料管理服务中 10 个 worker 各持语料子集），每个分区自洽使 worker 之间无需互相同步即可完成工作（服务要取 10 个用例时只需每个 worker 各取 1 个再汇总，发现新的有趣用例则随机只分发给其中一个 worker），由于每个分区只有一个 worker 访问、状态更新既快又及时、worker 始终基于最新状态工作并避免重复劳动。评测中 µFUZZ 在覆盖率与 bug 发现两方面与三个最先进并行方案 AFL++、AFLTeam、AFLEdge 对比，40 核并行 24 小时平均多约 24% 代码覆盖率与多约 33% 的 bug，消融显示状态分区贡献约 20% 性能、并发贡献不到 10%，另在 Lua、FFmpeg、PHP 等知名项目上发现 11 个新 bug，项目已发布在 GitHub；局限是分布式场景下服务间数据通信量高于既有方案（可改为每台机器跑一个实例、只同步语料管理这类有状态服务）、状态分区未必适用于所有现有模糊算法且重设计困难（可 best-effort，最坏退化为不分区、回落到周期性同步），并提出开放问题：并行模糊能否实现线性加速（n 个实例跑 1 小时是否等价于单实例跑 n 小时）。（YouTube EPTDlr3ibxCP4，[300-660]，L1）
- 〔USENIX FAST〕面向温存储（Warm Blob Storage）的网络编码重新审视。华中科技大学的 Ping Chen 代表论文作者作报告（工作由俞春艳、冯丹两位教授指导），论文观察指出块存储被广泛部署用于存放海量非结构化数据（照片、文档等），实践上会用不同性能的存储层做成本-性能权衡——Facebook 会把新数据先放进热存储以保证高访问性能、数据变冷后迁移到温存储，而温数据占存储比例超过 80% 且 blob 普遍很小（几乎全部照片与约 60% 的视频小于 1 MB）。为对抗故障的可靠性需求块存储广泛部署纠删码：把关键数据切成 N 个码块组成一条带、任取其中 K 块即可恢复，但单块修复需取回两个块、修复代价高，因此有再生码一类技术把大块拆成更小的子块以降低传输量（子块数即子包化级别），其中 MSR 是最能最小化存储冗余的一类，分非系统化 MSR（只存校验块）与系统化 MSR（同时存数据块与校验块、可直读原数据、读性能更好因而更流行）。论文指出系统化 MSR 虽在读原数据时表现好却在修复操作上表现差——修复一个块需要在多个节点各取多个子块、产生大量非连续 I/O，实验确认在不同 n、k 与不同 blob 尺寸下修复性能随 blob 变小而急剧下降、小 blob 的修复性能被明显限制；现有对策（连续布局）把小块合并成等大的大块以改善访问与 I/O 效率，却带来不必要的取数与读放大，实测降级读性能随合并尺寸增大而显著下降并随块尺寸减小而急剧下降。（YouTube EPTDnlprDSyoE，[16-310]，L1）
- 〔USENIX FAST〕NC Blob：混合编码设计、局部性优化与实测评测。论文发现非系统化 MSR 对读取小数据反而更优（子块更少、I/O 更少）——修复丢失块只需取回 3 个子块、而系统化 MSR 需要 6 个，于是设计 NC Blob 结合两类 MSR 的优点：小数据采用非系统化 MSR、大数据保留系统化方案，并围绕三项关键挑战给出方案，其一，非系统化 MSR 修复性能好但在读原数据时产生读放大（读一个块需从 K 个节点解码 K 个块，而系统化 MSR 可直接读出原数据），其主目标是降低读放大，思路是利用 blob 的两种访问局部性把数据按组编码：blob 内局部性（同批照片常一起被访问、读到任意字节就应预取其余）与 blob 间局部性（如同一用户 ID 的多个 blob 常被一起访问），据此提出 split-merge-encode 针对 blob 内局部性、merge-split-encode 针对 blob 间局部性——示例是 D1 与 D2 有局部性时读两个块所需解码从 4 块降到 2 块、且读到 D1 时 D2 很可能紧接着被读。其二，非系统化 MSR 对大 blob 仍困难、而观察到 Clay 码对大 blob 表现好，故提出混合编码架构：小 blob 用非系统化 MSR、大 blob 用 Clay（系统化 MSR），阈值取“磁盘寻道时间开始主导”的那个数据尺寸（图中红线），右侧域为小 blob、左侧为大 blob；其三，既有非系统化 MSR 只支持最多两块故障，因此设计子块纠删轮换以支持更多故障场景。实现为 Linux 上的 C++ 系统，含管理访问局部性 blob 的 locality manager 模块，编码与分布模块基于 Ceph、并行修复基于并行 RPC；阿里云实验显示与最先进系统化 MSR 相比读吞吐相当，而单块修复时间最多降低 45%、整节点修复时间最多降低 38%，代码已开源供研究者使用。（YouTube EPTDnlprDSyoE，[310-583]，L1）
