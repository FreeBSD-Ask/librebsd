- 〔USENIX ATC（推测）〕主讲人 Konstantin Tarasov 指出 Java 应用收发一个对象（如 person 类实例）要先分配发送缓冲、经序列化库把对象转成字节流，接收端再分配接收缓冲、读入字节流并反序列化重建对象，步骤繁多；网络越快序列化越是瓶颈——在 1Gb 互连上发送 100 万对象时序列化、网络、反序列化各占约三分之一，网络提速后 99% 的时间耗在序列化与反序列化上。根因是 Java 作为托管语言不暴露内存布局：对象不连续（person 对象之外还有对应的 char 数组对象）、堆内还有仅本地 JVM 可理解的类描述符等元数据，序列化库正是提取有效信息并转成可移植字节流（Java 序列化格式含类名，Kryo 等可用类型注册优化）。为此实现免序列化网络库 Naos：对象以发送端内存中的原样格式、不加变换地从本地堆直写（RDMA write）到远端堆，无需中间缓冲，连接可为 TCP 或封装 InfiniBand verbs 的 RDMA 连接。（YouTube EPKwQHhMYrwVQ，[8.6-448.4]，L1）
- 〔USENIX ATC（推测）〕核心挑战在于原样发送会带上对端无效的字段（如指向 char 数组的裸指针）、GC 可能并发触碰和移动对象、RDMA 网卡还会绕过 CPU 并发访问内存。Naos 的算法在发送端与接收端都以 DFS 序遍历对象图并生成发送列表与修复用元数据，把指针分为首次出现的平凡指针与指向已访问对象的 back 指针，只传 back 指针元数据（多数数据结构与工作负载中为 0），接收端一次线性扫描即可完成指针修复（论文还说明类指针恢复与内存安全保护）；网络流程上发送端静默把堆内存写入接收端预分配区域、再写完成元数据并等确认，接收端调用 readObject 完成指针修复并物化对象。评估显示 RDMA 下发送 float 数组延迟仅 8 微秒、全面击败现有序列化库；把阻塞通信改为异步后吞吐从 25 万请求/秒（约为 Java Kryo 的三分之一）提升到 15 亿请求/秒，源码已开源可供试用。（YouTube EPKwQHhMYrwVQ，[449.1-891.7]，L1）
- 〔USENIX Security（推测）〕宾州州立大学的 Tianrui Xia 介绍间接调用目标识别问题：间接调用广泛用于 Firefox、Chrome、LibreOffice、Apache HTTP server 等 C/C++ 程序，数据流分析（如用 SVF 分析 Linux 内核需数小时到数天）精确但太慢，基于函数签名的类型分析快但大程序中大量函数共享签名、误报率高。MLTA（多层类型分析）利用复合数据结构的额外类型信息改进类型分析，但两类信息流会破坏多层类型匹配：类型变换（赋值与类型强转引起的函数地址传播）与参数传递（形参与实参多层类型不同），处理不当会使间接调用与函数的多层类型不匹配、造成漏报（unsoundness）；MLTA 以拆分多层类型并求交集来应对，却因拆分削弱多层类型约束而引入误报。团队提出强多层类型分析 SMLTA：以 type-func map 记录完整多层类型与函数的映射、保留多层类型的强约束，使间接调用的解析结果恰为其唯一真实目标。（YouTube EPKwgw5-vSTcA，[18.1-416.5]，L1）
