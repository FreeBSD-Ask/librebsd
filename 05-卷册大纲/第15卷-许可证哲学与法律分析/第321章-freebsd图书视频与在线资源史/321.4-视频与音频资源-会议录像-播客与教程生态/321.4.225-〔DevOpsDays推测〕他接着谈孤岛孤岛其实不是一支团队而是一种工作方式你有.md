- 〔DevOps Days（推测）〕他接着谈孤岛。孤岛其实不是一支团队，而是一种工作方式：你有自己的上下文、单一待办清单与统一工具，但企业里没有任何东西孤立存在，工作总要在孤岛之间传递，而坏交接、等待与误解几乎都发生在这些上下文断裂处〔22:38〕。识别孤岛最好的信号是工单驱动的请求队列：凡需要给别人提工单、进队列等专家处理的地方，就存在上下文断裂、优先级不一致与工具不同——你排在第 67 位只能去催，于是有人空降进来毫无上下文，做出一锤子买卖再退回去，来回乒乓〔23:23〕。孤岛里的人会为自己的孤岛优化：如果我是“密西西比河以西最会改防火墙规则的人”，那我每周四会把防火墙改得比史上任何人都好，但如果你没赶上周三下午三点的窗口，就得等下一个周四〔24:20〕。工单系统不只是孤岛制造机，还是雪flake制造机：空降的专家做出技术正确、下次却略有不同的独一份，这些微小差异让自动化变难、事后出错变易〔25:17〕。流行的解药是用跨职能团队替代孤岛，但在大型企业不成立：DBA、数据中心、网络与安全都人不够分，没法给每个交付团队配一套，于是又回到集中式 NOC 或 SRE 与工单循环〔25:47〕。他给出的答案是 operations as a service 设计模式：建一个公共平台，让造东西的人按统一词汇（start、stop、restart、reconfigure、清缓存、健康检查等）定义照料自己东西的过程；运维可以审查并加上自己的经验，同时始终掌管策略——谁能跑什么；然后运维与被授权方都能按需执行，不必再提工单干等〔26:57〕。他把自动化过程拆成三件：定义、执行与治理（安全、监督、合规、谁可跑什么）。传统运维孤岛把三者都握在运维手里；刚性自助只是给他们一个不能改的按钮，能卸载的很有限；自助运维是定义与执行都交出去而治理仍由运维掌握；更高绩效的组织连治理也下推，运维只搭“能做什么、不能做什么”的壳，让业务在自己的世界里管谁跑什么〔29:20〕。落地路径分三步：先建安全中枢，把健康与当前配置信息及所有标准操作流程拉进来，若当初那些 L2 有这些过程本可自己动手，而密钥、身份、访问策略与审计仍由运维与安全共管；再把过程变成代码，把 runbook 与 SOP 放进源码管理走 code review，由开发写、运维与安全审，从而拿到高速交接；再往外扩，挂上工单系统与制品库让更多信息进入同一看板，这也让合规满意——过程从哪来、谁审过、谁跑的、何时何地跑的都有审批轨迹，因此可以论证这样反而更安全，所谓“going faster and being able to lock things down at the same time”〔31:28〕。最后一个转变是鼓励开发者以 operable first 思考：可部署性、可配置性、可监控性都是像业务特性一样的一等公民，因为代码跑不起来就没收入，运维特性需求应与业务特性同等重要〔34:40〕。案例是 Ticketmaster：主网业务事故的平均 MTTR 曾有 47 分钟，新来的 CTO Jody Mulkey 与运维负责人 Justin Dean 在 Mark Mau 打好的基础上启动 support at the edge 项目，约 18 个月后 MTTR 从 47 分钟降到平均 3.8 分钟（约九成降幅），升级次数降了五成，支持成本几乎腰斩〔36:04〕。做法是一套新支持升级模型并借用医疗隐喻：NOC 是 EMT（15 分钟 SLA）、SRE 是急诊（30 分钟）、production engineering 是创伤外科（1 小时），再往外是数据服务、平台工程、全球网络等专科外科；关键在于不是升级得更快，而是把行动能力推到最靠近问题的地方——过去只负责看红灯找人打的 NOC 重新变成有按钮可推的操作者，SRE 则拿到各专业团队写好的全部过程〔37:42〕，同时长期投资 operability（部署、配置、监控、runbook），让交付团队写并审这些自动化过程、运维保有全部策略权〔39:37〕。如今大约 94% 的事故由产品支持团队或 NOC 自己解决；他的总结是：用精益思想把事件响应当流程分析、度量对的东西、把控制与决策左移、拆掉孤岛、建立 operations as a service，并让开发者以 operable first 思考〔40:22〕。Q&A 里，对于如何说服高层，他的答案是把它换算成钱：用交付侧那套精益手法把常见事故映射出来并当成供应链问题看，浪费与抖动一眼可见；除非把成本显性化，否则无从论证〔42:47〕。（YouTube EPYd74Qa5OUpw，[1341-2673]，L1）
- 〔NSDI（推测）〕说话人代 Google 数据网络团队报告统一超低延迟数据中⼼⽹络 Aquila。先交代背景：数据中心由集群构成，集群是 10 到 50k 台机器，通过多阶段 Clos 网络与商品以太交换机互联〔00:21〕；但两类趋势在挑战这一架构。一是资源解耦，要求极低延迟以匹配延迟在 10 微秒以下的设备；二是越来越多负载进入数据中心，如高性能计算与机器学习，它们需要紧凑且可预测的延迟以让昂贵的加速器持续满载，而当前做法是为它们单独建专用网络，既昂贵又增加可管理性开销〔00:48〕〔01:05〕。于是提出 Cliks 的愿景：把计算与加速器组成一个可作为调度域的功能单元，簇内带宽极高、延迟相对数据中心其余部分极低，并通过数据中心互联接到其余网络〔01:32〕。Aquila 是朝此目标的第一次尝试，思路是用一种新的基于分组的二层协议，把交换机与网卡 ASIC 整合，即 GenNet：为超低延迟与传统 IP 流量提供统一的⽹络，并提供超低延迟的 fabric，在负载下 RTT 为 40 微秒、OneRMA 低于 10 微秒，对共同设计的应用意味着延迟降低 300%〔02:26〕。他给出四个设计目标并说明达成方式：低成本拓扑，从 HPC 社区选了 Dragonfly 这类直连拓扑；超低延迟，采用他们自研的浅缓冲分组式二层协议；统一 fabric，在网卡里原生集成多个协议引擎；以及共存，即通过以太网与其余 fabric 相连〔03:14〕。拓扑上，Dragonfly 是 HPC 社区的直连拓扑，所谓直连是指主机直连交换机〔04:01〕；把若干主机全连接构成第一维，称为 pod，再把 pod 组成第二层全连接网格，即二维 Dragonfly〔04:23〕；这种拓扑能通过减少长距离光链来压低成本，Aquila 中有 48 个 pod、每个 pod 约 12 个 TENS、共约 1000 台机器〔04:34〕，对均匀随机流量的 bisection bandwidth 超过每秒百太比特，对最坏流量模式也超过 50 太比特〔04:49〕。延迟方面，他概括 GenNet 三条设计要点：一是分组化，浅缓冲分组带来的交换延迟仅 15 纳秒，并支持 IP 与低延迟流量共享带宽而无队头阻塞，还配虚拟通道做 QoS 隔离〔05:09〕〔05:31〕；二是在分组层面近无丢失，链路上用基于 credit 的流控，而在以太网边缘用深缓冲允许丢包〔05:47〕；三是需要在硬件中做自适应路由，以便在 Dragonfly 网络里走非最短路径，从而在最坏流量模式下获得高带宽并绕开瞬时拥塞〔06:02〕。最后他说明 Aquila 如何与 Jupiter 共存：在每个 TENS 上增加以太网链路，使 Aquila 簇内的机器可以用以太网与数据中心其余部分通信〔06:23〕。（YouTube EPYiRDNNjVVrA，[13-442]，L1）
- 〔NSDI（推测）〕Aquila 的具体实现围绕在 NIC 内部原生放置多个协议引擎展开。他说明在网卡内加入 GenNet 交换芯片，并配 18 条内部链路连到协议引擎，其中一个是 IP 协议引擎，另一个是 OneRMA 引擎；这样做使得 GenNet 既可作为承载 IP 流量的统一 fabric，也能为 OneRMA 原生流量提供服务，并且 OneRMA 引擎还额外加了一条 PCIe 链路接到 PCIe 交换机上〔07:39〕。IP 在 GenNet 上运行依赖端到端准入控制，做法类似 EDQDS：为每个报文发送 RTS 与 CTS，只有当接收端有足够的带宽与缓冲时才发出 CTS，而 RTS 到达的先后顺序决定了报文放行到主机的顺序〔08:16〕；由此带来排序保证，并在入口缓冲报文从而提供 incast 保护〔08:26〕。他接着用报文生命周期说明：报文到达源端后立即向目的端发 RTS，一旦目的端具备足够带宽与缓冲便回 CTS〔08:44〕，随后立即发送可在 Aquila 簇内自适应路由的分组，因为这些分组可能乱序到达，所以需要组包与重排后才把报文释放给主机〔08:55〕。OneRMA 引擎为簇内提供读、写与原子原语〔09:09〕，它不是叠加在 GenNet 之上，而是与 GenNet 共同设计，所以 OneRMA 的读请求与响应本身就是第一等公民的 GenNet 分组；读请求的作用类似 CTS，充当准入控制信号，因此能容忍乱序投递、无需重排即可直接落地到内存〔09:29〕，同时还与 PCIe 共同设计，使 PCIe 响应可直接在 GenNet 上发送，并借助虚拟通道与 IP 流量隔离〔09:52〕。评估使用 Aquila 簇内的 500 台机器，负载包括用 Pony Express 产生的背景 IP 流量与使用 RDMA 的生产级键值存储 ClickMap〔10:06〕；测量指标是硬件时间戳得到的 fabric RTT 与由硬件导出的 OneRMA 总执行延迟，后者包含 PCIe 响应处理，因此高估了 fabric 缓冲开销〔10:33〕。先看两者分开运行的情况：OneRMA 在高负载下尾延迟低于 10 微秒，而 IP 为 40 微秒〔11:06〕。隔离实验中，把 ClickMap 放在比批量 IP 流量更高的优先级虚拟通道上时，几乎看不到批量流量的影响〔11:32〕；改为共享虚拟通道则能观察到批量流量对尾延迟的影响；作为对照，在以太网上让 ClickMap 用更高优先级 QoS 类而批量流量走低优先级，虽然也能实现所需隔离，但总体延迟仍高于 Aquila〔12:00〕。在应用层面，他们测了 ClickMap 的端到端查找延迟，基于 OneRMA 的 ClickMap 明显优于基于 Pony Express 的版本，延迟降低超过 300%〔12:42〕。回顾部分他坦承三点不足：直连拓扑虽省钱，但需要一次性落地整个 Dragonfly，不利于增量部署，还受光链路长度限制，若继续这条路可能仍要回到 Clos〔13:07〕〔13:32〕；分组交换对延迟友好但会增加带宽开销，调试也因缺乏 traceroute 等标准工具而更难，不得不自建工具〔13:37〕；此外应用性能收益主要来自共同设计的应用，对传统应用由于操作系统与主机栈的影响收益不大〔13:51〕。他总结道，Aquila 是构建紧耦合计算与存储基础设施的第一次尝试，提供低于 10 微秒的延迟，并希望激发后续研究〔14:09〕。（YouTube EPYiRDNNjVVrA，[442-872]，L1）
- 〔USENIX Security（推测）〕清华大学的 Qwen Zhou 介绍 RustSan：为 Rust 改造地址消毒器。先交代背景：Rust 正作为 C/C++ 这类传统系统编程语言的安全替代出现，其借用检查器与所有权体系带来了内存与类型安全保证〔00:09〕；热度可见于被纳入 Linux 内核与 GitHub 语言提交趋势〔00:36〕。但他强调这种安全并非免费——Rust 迫使程序员参与严格的语言语义，有时相当繁琐，因此程序员有时会转向“dark side”，即 unsafe Rust，以逃避编译器规则〔00:50〕；实践中 unsafe 对系统底层交互确有必要，但常被当作“trades safety for convenience”的捷径，风险随之回来，Rust 程序的内存安全 CVE 被持续报告，unsafe 是其中最主要的来源〔01:06〕〔01:14〕。Rust 社区也吸收了传统手段：Rust 工具链已内置 Address Sanitizer（ASan）构建选项，许多源于内存错误的 Rust CVE 也是通过消毒器辅助的模糊测试发现的〔01:54〕。他的动机由此而来：他的观察是，即便存在 unsafe，大多数 Rust 程序仍保留安全保证，因此问题变成能否准确识别这些安全部分、让它们免于昂贵的消毒器检查〔02:22〕。他把安全代码分两类：一类从不被 unsafe 影响、保持安全；另一类可能被 unsafe 影响而一并变不安全，后者称为 fallback code〔02:43〕。他用代码示例说明 unsafe 站点如何产生：第 3 行有一个 unsafe 块，但只是指针运算与类型转换，块本身不产生非法内存访问；真正危险的是返回的不一致指针在后续被引用，而解引用点位于安全代码中，其指针值却受 unsafe 影响，可能实施非法内存访问，这是 false safe 的一个例子；解引用本身又是危险的，于是 load 返回不一致值，污染可能传播多远难以判定〔03:07〕〔03:36〕〔03:50〕。他总结术语：不属于 unsafe 块且与 unsafe 块无数据流关联的内存访问点是 safe；unsafe 块内的访问点称 unsafe site，块内被修改的对象称 unsafe object；与 unsafe object 交互的访问点称 false safe 点，这类点可能实施非法内存操作；另有一类 overlapping object，即在全部安全点的指向集中与 unsafe object 重叠的一小批安全对象，由于检查是上下文不敏感的，允许所有安全点访问这一小集合〔04:04〕。RustSan 的思路是改造地址消毒器，以定位潜在不安全的内存访问，同时把昂贵的 ASan 检查从其余位置剥离，做法有两点：一是在 LLVM 与 Rust MIR 两级上做静态分析（称为 cross-IR analysis）以识别全部 unsafe 与 false safe 点；二是扩展 ASan 的影子内存模型，为安全点与不安全点施加不同策略〔05:08〕〔05:30〕。（YouTube EPYldjPs9Y1eM，[8-355]，L1）
