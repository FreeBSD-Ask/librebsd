- 〔USENIX NSDI（推测）〕报告 Batfish——从网络配置中查找错误的新工具，合作方包括 UCLA、USC 与微软研究院。网络误配置普遍且昂贵（如 Time Warner 配置错误导致全客户数小时中断），根因是配置包含大量底层指令，需映射高层意图并正确处理 BGP、IS-IS、OSPF、MPLS 等多协议交互。以 multipath consistency 违例为例演示埋在数千行配置深处的真实 bug；对比既有两条研究路线——数据平面分析（Anteater、Header Space Analysis，只能对运行网络做被动反应）与静态分析（RCC 等，不产出数据平面、无法直接检查转发性质），提出第三条路线：从配置出发计算数据平面再做数据平面分析，核心贡献是配置到数据平面状态的链接，以高保真声明式控制平面模型实现为四阶段流水线，工具见于 www.batfish.org。（YouTube EPONKu5u-MFIs，[10.0-682.9]，L1）
- 〔USENIX NSDI（推测）〕后半场介绍三个新转发不变量：multipath consistency（同一报文多路径既可达又被丢弃即违例）、failure consistency（容错）与 destination consistency（任意网络条件下给定目的地址只应送往一个客户）；实现支持 IOS、NX-OS、Juniper、Arista、Quanta 等语言，经统一厂商中立中间表示过滤特性使分析可扩展。在两所大学大型网络（21 路由器联邦式、17 路由器集中式）上评估，发现大量真实 bug，如运动学院流量可劫持全校、宿舍与图书馆共用前缀互相窃流，多数被运营方确认或修复。Q&A 讨论厂商实现差异（Cisco 与 Juniper 的 BGP 选路算法不同、默认值有异）及在图灵完备声明式语言中建模正则表达式的开销。（YouTube EPONKu5u-MFIs，[685.8-1421.8]，L1）
- 〔会议不详〕报告基于同态加密的常重量码字（constant-weight codeword）等值比较算子。同态加密中乘法比加法慢可达 20 倍，且乘法深度决定系统参数与性能，故应尽量减少乘法次数并降低电路乘法深度；传统按位表示的等值算子对 L 位长度需约 2L 次乘法、乘法深度为 log L + 1，可扩展性受限。改为常重量码字（1 比特个数恰为 k 的二进制串）后，明文混合情形比 folklore 等值算子快约 10 倍，得益于更少乘法与更小乘法深度；密文算术情形加速有限但乘法深度仅取决于重量 k，可用更小参数。代价是常重量表示更占内存，需在运行时与内存占用间权衡。（YouTube EPOSMpwmVlZBs，[7.8-373.6]，L1）
- 〔会议不详〕后半场先说明算术情形操作可高度并行，并行化后相对 folklore 提速约 10 倍（folklore 至多 2 倍）；继而用该等值算子构造单服务器关键字 PIR：用户加密查询关键词，服务器用快速等值算子将查询与库中实际关键词逐个比较生成 0/1 选择向量，与数据做内积后在密文下返回记录，单轮完成且无既有方案降级为 index PIR 的额外通信轮次与失败概率。操作次数只取决于数据库实际元素数而非关键词域大小，数据库越稀疏优势越大；相同乘法深度下常重量表示更小，返回约 250KB 以上大响应时协议主体可一次前置完成、每份密文仅边际成本。代码已发布于 GitHub。（YouTube EPOSMpwmVlZBs，[374.0-780.0]，L1）
- 〔会议不详〕Xiao Kang Hu（上海交通大学，与 Intel 合作）报告 QAT 加速压缩文件系统 QZFS（转写中作 QDFS，QAD Accelerated Compression File System）。HPC 存储子系统成本高昂（如德国气候研究 HPC 系统约占总拥有成本 20%），压缩可省空间并减少 I/O；压缩可集成于应用层（Nginx、Hadoop）、文件系统层（ZFS、Btrfs）或块层。QZFS 在 ZFS 中集成 Intel Quick Assist（QAT）ASIC 并卸载 gzip，新增压缩服务引擎与 QAT 卸载模块两个模块：支持 4KB-1MB 的选择性卸载（小数据收益被卸载开销抵消、大数据需大块预分配缓冲）、压缩率依赖卸载（空间节省低于 10% 阈值则返回原始数据），并以 vector I/O（scatter-gather 列表）与页帧划分实现零拷贝数据重构、按内核内存区域区分地址翻译。（YouTube EPOVBQVEEIFVE，[10.3-639.7]，L1）
- 〔会议不详〕后半场评估与讨论：FIO 微基准中软件 gzip 的 CPU 利用率高达 95% 导致吞吐极低，卸载到 QAT 后成本效率（压缩比与 CPU 利用率之比）大幅提升，压缩后写吞吐甚至高于不压缩；与 LZ4 等快速算法相比 QAT 加速 gzip 成本效率最高。基因组数据后处理中执行时间减少 63%、成本效率 6 倍，QZFS 总开销甚至小于应用层 gzip 的纯转换流程，且仅需改一处文件系统即可惠及所有应用。瓶颈分析指出 ZFS 工作线程数受 QAT 实例数限制且同步模式交互阻塞后续请求，异步卸载需全栈异步支持（暂停恢复可用状态标志、fiber 或协程，可参考 2019 年发表的 QTLS 异步 SSL/TLS I/O 框架）。Q&A 讨论块粒度时延与 DMA 拷贝开销：块大于 64KB 时 QAT 加速仍快于 CPU。（YouTube EPOVBQVEEIFVE，[654.0-1284.1]，L1）
- 〔SREcon（推测）〕Grafana Labs 工程师介绍将 Grafana Cloud Logs 的 Memcached 集群扩容到 50TB 的历程：对象存储请求减少 65%、服务可靠性大幅改善并意外带来 2% TCO 下降。先铺陈 Grafana Loki 内部机制（不索引日志内容、以 label 标识来源、stream 压缩为带内容寻址 ID 的 chunk 存入对象存储、LogQL 靠 label 选择器收敛集合），多租户服务部署于三个公有云 20 个区域，needle-in-haystack 型查询给对象存储带来压力遭限速，吞吐下降、SLO 预算告警频发，甚至因客户压测被云厂商误判为 DDoS 而切断 bucket 24 小时；在少查数据与多缓存之间选择后者。关键发现是 prod-three 实例无近期数据偏斜、命中率日均 70%-90% 虚高而掩盖问题——未取回即被逐出（unfetched eviction）一度接近每分钟整缓存轮换一次，估算需要约 50TB 容量与 0.5 Tbps 网络吞吐的缓存。（YouTube EPOVL3fgFq_9g，[16.0-783.4]，L1）
- 〔SREcon（推测）〕后半场给出方案与权衡：Memcached 冷存储特性 extstore（转写中作 XDCR/X-Store）把 LRU 尾部溢出到 SSD 而非逐出，配合云上本地 SSD（Google local SSD 每块 375GB 每月 30 美元、AWS instance storage，排除 NFS 与多租户噪声），不动应用代码、两周完成落地。新架构 33 实例各配 4 块 SSD 共 50TB、每节点 16Gbps 共 0.5Tbps，缓存每 GB 每月成本从 4.43 美元降至 0.08 美元（降 98%），反而比原架构便宜。上线后限速趋稳、SLO 持续达标、日平均命中率约 95%、churn 大幅下降，缓存取回数据量比对象存储高近一个量级且查询性能不受影响（瓶颈已不在数据访问层）。代价是 P50 时延从个位数毫秒升至最高约 50ms（仍优于对象存储且可批量请求）、SSD 并不持久（单节点丢失仅约 3%-4% 缓存、被动重建），磁盘故障靠驱逐节点、回收重换解决。（YouTube EPOVL3fgFq_9g，[793.1-1495.6]，L1）
- 〔会议不详〕内核文件系统开发者介绍面向长期稳定档案库（HSM）的 POSIX 归档文件系统 ScadaFS（转写中作 ScataFS/ScalityFS）。面对十亿级文件量，按命名空间遍历的搜索式工作流（如归档代理找新文件、磁带被飓风损毁后找全部相关文件）不再可行，且归档后文件内容被截断、POSIX 文件系统成为仅含元数据的命名空间与文件位置的权威数据库。方案采用对称节点加共享存储的经典架构提供 POSIX 语义：用离线扩展（offline extents，读取时阻塞并触发软件代理取回归档层副本）与 magic ioctl 支撑，更关键的是提供 inode 索引（当前按最近修改时间，实为提交事务号到 inode 的索引），维护与其余元数据相同的原子键值存储中并随索引字段变更在同一原子事务中更新；索引以 LSM 组织，manifest 存于预分配环上的 B-tree、写只推进尾指针，旧版本树配合逻辑锁实现高并发。（YouTube EPOVREshQGkLI，[10.6-605.0]，L1）
- 〔会议不详〕后半场与 Q&A 深入并发与 compaction 机制：各节点对 inode 持独占锁、对将变更的索引项持共享锁，将索引项并行写入 level 0 的 LSM 日志片段，从而无需全局锁 B-tree 即可并发更新全局索引；因命名空间巨大，节点间索引项相交概率极小。Q&A 释疑归档工作负载（HPC checkpoint 大量并行读加随后的 set xattr 元数据更新全局索引，若不能并发更新将被全局串行化）、compaction 细节（段写后不可变、输出写自由空间、原子更新 manifest，陈旧块由序列号检测后取新 B-tree 根重试）、以及 LSM 以 IOPS 换带宽的根本取舍——1MB 流式写足以胜过受 IOPS 约束的 4KB 粒度树系统。（YouTube EPOVREshQGkLI，[587.5-1198.5]，L1）
- 〔OpenZFS Developer Summit（推测）〕Shailendra Tripathi（文件系统开发负责人，Delphix，转写音作 Tizil）介绍 iRAID：并非新 RAID，而是对 ZFS RAIDZ2 分配层的虚拟化改造，面向 4K/8K 小块生产负载。现有动态条带 RAIDZ 的优势是读改写免读、free 为直通操作，但问题严重：小块 I/O 膨胀（512B 扇区下 4K 逻辑读被拆成 8-10 个小 I/O，10 万逻辑 I/O 放大为 60 万叶级 I/O），改用 4K 扇区又致空间膨胀（4K I/O 写成 D+P+Q 共 12K，RAIDZ2 下可达 3 倍逻辑大小），且 resilver 随机 I/O 化极度耗时（百 TB 系统三个月未完成）。iRAID 虚拟化分配层、解耦逻辑 I/O 与设备 I/O：以 1MB 大块 chunk 聚合写入、经 chunk map header 间接寻址（DVA 内嵌 chunk 位），子块入队完全无锁、按事件驱动刷写，空间图等少数元对象有意不分块，free 依赖 L1/L2 日志与垃圾回收。（YouTube EPOaZmkq5jgfk，[2.6-1386.6]，L1）
- 〔OpenZFS Developer Summit（推测）〕后半场介绍回收、resilver 与评估：recompaction 借鉴 LSM 思想，free 进入逻辑 L1 日志再经后台 chunk 变换合并为按物理偏移、每 slab 一份的 L2 位图日志；策略上默认不必要不回收，设 90% 可释放阈值与 40%/80% zpool 填充门限、带宽与 CPU 限额，达到均衡即停止，必要时反压节流入速。resilver 顶层机制不变，先并行顺序扫描 1MB chunk map header 并用 block pointer 的 chunk 位跳过已分块数据。附带收益包括内置碎片整理（迁移未用块并 compaction 释放旧位）、任务队列同步事件数降低约两个数量级与空间图加载耗时消失。VDBench/FIO 评估显示空间占用接近理想 RAIDZ2 数学（仅约 0.78% chunk map header 开销），mirror 与多盘 RAID 配置的随机覆盖写显著提升；三校验 RAID、7TB 盘、63% 填充的 resilver 逻辑速率约 8.4 GB/s，将原需三个月的任务缩至约 4.76 小时。Q&A 说明读路径约 12% 额外开销、源码暂未开放，以及用 Intel CRC 的子块影子校验页保证 recompaction 与 resilver 期间数据完整性。（YouTube EPOaZmkq5jgfk，[1390.8-2917.0]，L1）
- 〔会议不详〕Pei Qi Yin（香港中文大学）报告面向大规模向量检索（近似最近邻搜索 ANNS）的计算-内存分解系统。RAG、推荐与异常检测等应用依赖向量检索，最先进方法为基于图的方法（在向量数据集上建图、从锚点做 BFS 式遍历并逐点计算距离）；十亿级节点、1024 维时全内存存放开销过大，于是出现两阶段 ANN 索引（内存存 PQ 压缩向量、磁盘存精确向量与图数据），代表系统 DiskANN 与 Starling。但存在三大挑战：压缩向量常驻内存（约占数据集 10%，且高压缩比会降低近似距离精度、增加图遍历节点访问数）、每次图遍历迭代需一次磁盘读且磁盘访问时间主导查询时延，以及单机全耦合难以横向扩展（扩容需全量复制压缩向量与图数据）。（YouTube EPObqi9SYXVHc，[17.8-514.9]，L1）
- 〔会议不详〕后半场提出分解式设计 DistVS（转写中亦作 DiskVS）：依据精确向量仅用于最终重排、图数据在搜索中需求更高，以及低精度 PQ 仍可为图搜索提供引导两个观察，设计三精度搜索算法（转写中作 press 算法）——低精度 PQ 扩展邻居、高精度 PQ 选下一轮候选、精确向量做最终重排——并将三者分别部署于计算服务器、内存服务器与存储服务器，经 RDMA 通信。系统优化包括基于迭代的异步执行（协程与流水线并行避免 CPU 空等远端响应）与连续 RDMA I/O 批量合并（避免小消息使 RDMA 通道成为瓶颈）。在 DiskANN、Starling 与 PAGN（转写音）及五个数据集（1 亿至 10 亿节点、96 至 768 维）上评估，吞吐相对 DiskANN 最高提升 114%、相对另一基线提升 70%，时延相当且内存占用更低。（YouTube EPObqi9SYXVHc，[515.4-1021.6]，L1）
- 〔会议不详〕Lu（University of California, San Diego，人名依转写）报告容错持久内存编程库 Pangolin，在提供崩溃一致性的同时处理持久内存错误，包括硬件不可纠正与不可检测错误。PM 字节可寻址且缓存一致，DAX 直通绕过页缓存与文件系统，是用户态到持久存储的最快路径；按硬件 ECC 可检测/可纠正将错误分三类：可检测可纠正无需软件介入，可检测不可纠正触发 SIGBUS（许多应用未准备好而崩溃丢数据），不可检测错误则直接交付损坏数据。文件系统保护仅覆盖 read/write 接口、mmap 直通会绕过文件系统（如 Nova），故需用户态库。Pangolin 仅复制元数据（分配位图与事务日志）并以奇偶校验保护任意大小随机分布的对象数据，1GB 对象存储仅约 1% 空间开销，全量校验和检测不可检测错误；对象修改先复制到 DRAM 级 macro buffer，事务提交时以失败原子方式刷新校验和与相应奇偶范围。（YouTube EPOhH3fzRvyjE，[10.2-547.2]，L1）
- 〔会议不详〕后半场介绍奇偶更新与事务机制：数据区按等大行（row，为 16GB 数据区的 1% 即 160MB）划分，每区保留一行作对象奇偶，按列异或计算、可承受整行丢失；提交时用 macro buffer 与 PM 中未改范围的 XOR 差量（parity patch）直接更新奇偶行而无需读其他数据行，掉电导致的奇偶部分更新在重启时经 redo 日志重放并重读全部数据行重算受影响奇偶范围。多线程共享奇偶段时采用混合方案：小于 8KB 的更新以原子 XOR 指令加共享锁无锁并发，更大更新取页范围独占锁用向量化 XOR，阈值依实测而异。在 libpmemobj 之上实现并于 Intel Optane DC PM 平台评估：单对象覆盖写时延比带复制的 libpmemobj 低 11%，多对象映射数据结构达带复制版本 90% 性能而空间开销小得多。Q&A 说明 macro buffer 默认线程本地、Intel TSX 工作在缓存层不保证崩溃一致性，奇偶区磨损依赖硬件磨损均衡。（YouTube EPOhH3fzRvyjE，[564.2-1113.6]，L1）
