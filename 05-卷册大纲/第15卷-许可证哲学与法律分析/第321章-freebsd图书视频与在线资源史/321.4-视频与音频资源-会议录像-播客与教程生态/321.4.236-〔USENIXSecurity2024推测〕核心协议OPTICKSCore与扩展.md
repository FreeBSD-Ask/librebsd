# 321.4.236 〔USENIXSecurity2024推测〕核心协议OPTICKSCore与扩展

- 〔USENIX Security 2024（推测）〕核心协议 OPTICKS Core 与扩展、实现与评测。服务方维护包含每位用户各版本密钥的目录（如 Alice 在纪元 T1 的版本一、Bob 在 T1 的版本一；Alice 之后换钥加入 PK_A′），并在每个纪元发布该目录的 ADC 承诺〔07:49〕。查询示例：Bob 当前密钥版本为二，Alice 查 Bob 时服务方返回 Bob 当前密钥外加证明——即针对该承诺、版本一与版本二的成员性证明，加上下一个版本的非成员性证明；用户自查密钥历史时检查方式类似，但会连同真实密钥一并返回〔08:16〕。为何成立：Bob 做密钥历史时拿到版本一、二的成员性证明与版本三的非成员性证明；若服务方给 Alice 返回过期密钥（版本一），就必须对版本二出示非成员性证明，与 Alice 密钥历史证明中的成员性证明直接冲突——对同一用户名与版本、在同一承诺下不可能同时有成员性与非成员性证明；反之若服务方虚构一个并不存在的版本三，则 Alice 见到成员性、而 Bob 见到该版本的非成员性，同样矛盾〔08:46〕。OPTICKS 扩展：核心协议需要检查到最新版本为止的全部历史版本，若客户端能缓存并记住某用户上次看到的密钥，就只需看更新的密钥〔10:06〕；针对只追加结构带来的存储无限增长，引入“时间段”这一固定系统参数——从一个时段到下一时段目录会被压缩、旧密钥全部丢弃（如 Alice 的版本一、二只把版本二提升到新目录），代价是用户必须在一个时间段内上线以确认其密钥被正确提升〔10:35〕。实现采用与前作不同的分体架构：服务方本质上只是路由器，把查询与更新转发到逻辑与物理上都独立的查询服务与更新服务；查询服务连存目录的数据库并应答查询，更新服务是个极简 REST API 把更新请求入队，再由周期性触发的更新任务取出排队更新、生成目录更新与新承诺写回〔11:35〕。好处是可以为查询服务与更新任务采用不同内存表示（查询服务可用哈希表式缓存只存部分目录、更新任务必须全量常驻），实测端到端查询吞吐在百万级密钥数据集约 4400 QPS，规模增大后曲线下降、瓶颈转为通信量〔12:41〕；更新一律按 1000 条批量（单条更新无意义），可达每秒数百次，即便目录很大，单纪元（插入这 1000 条更新）耗时大致一秒钟到平均不到四秒；性能瓶颈主要在数据库操作、尤其是数据库写入，若换更懂数据库的人优化还有不少空间〔13:11〕。对比：与 Parakeet 做了完整系统级对比（该实现较为复杂、细节见论文），与 Merkle Square 则更合理地对比核心 ADC 原语，量级上明显更优、但安全模型稍弱〔14:11〕。（YouTube EPZN8uA0P_IT0，[451-898]，L1）
- 〔USENIX Security 2022（推测）〕密歇根大学 Diwen Xue 报告与 UMich、Merit Networks、ASU 合作、关于 OpenVPN 可被指纹识别的研究，〔00:07〕"My name is Diwen from the University of Michigan"。商业 VPN 需求近十年稳步增长，部分源于每日可见的网络流量被监控或篡改的报道；VPN 协议在网络上创建加密隧道，起先是企业安全工具，如今已进入普通用户手中以抵御监控、地理封锁与审查〔00:20〕。既往研究多聚焦隧道完整性（隧道渗透攻击可注入伪造数据）或保密性（DNS 或 IPv6 泄漏），而威胁行为者越来越以阻断或限速来攻击隧道可用性；这并非假想威胁——ISP 与政府为维持可见性与控制而针对 VPN 流量，加之廉价的商用 DPI 让针对用户流量变得前所未有容易〔01:12〕。因此“能不被标记地在隧道上通信”越来越重要，供应商也推出了所谓混淆 VPN 服务〔01:44〕。研究问题是：在实践中，ISP 能否以近实时、大规模且无重大附带损害的方式针对 VPN 流量〔02:02〕"in practice, how feasible it is for ISPs to target VPN traffic in near real time, at scale and without significant collateral damage"。对象选 OpenVPN——商用 VPN 最流行的协议，且几乎所有混淆 VPN 服务都构建在 OpenVPN 核心协议之上；OpenVPN 还带 HMAC 保护等阻碍指纹识别的机制、比别的协议更难指纹化〔02:18〕。既往工作用机器学习分类器与连接时长、包间延迟等流级统计，其实际可部署性令人存疑；有效调查不仅要指出脆弱性，还要在 ISP 与审查者的真实运作约束下展示可行利用〔02:48〕。方法上研究者扮演恶意网络运营商并与真实 ISP Merit 合作，使用 Merit 内部商用级 API 模拟国家级审查部署的已知能力，并遵循本机构列出的伦理流程以降低隐私风险〔03:15〕。框架两阶段：先用多台 DPI 对原始报文应用过滤规则，DPI 观察骨干路由器的镜像流量、该路由器承载约两成 ISP 总流量，输出是可疑服务器 IP 与端口的集合；第二阶段主动探测，向这些端点发送定制探针以诱发目标协议应有的服务器响应——这正是现实审查者检测并阻断 Tor、Shadowsocks 等工具的做法〔03:43〕。指纹有二：一是 opcode 字段，其取值对应 OpenVPN 会话各通信阶段，握手期间取值以独特顺序演化、可用于指纹化，且过滤不需字节级精确匹配以抵抗某些混淆策略〔04:50〕；二是 add 报文的重复模式——OpenVPN 以 TLS 风格握手自举、需显式的 add 与重传模型以支持 UDP，进入的自举报文由特殊 add 报文确认，这些被封装在 TCP 载荷中的 IP 报文在同一会话内是均匀的（勿与 TCP ACK 标志混淆），过滤以阈值式规则并行捕获该重复〔05:16〕。两者都足够快且灵活，既能对付原版 OpenVPN、也能对付野外发现的主要混淆变体。（YouTube EPZNVff1rH-vA，[7-368]，L1）
- 〔USENIX Security 2022（推测）〕规模化检测结果、主动探针设计与结论。以 Merit 上的一天快照为例：两百多万条持久连接中标出 1.5 万条可疑，误报率上限约 1%，与前代机器学习分类器的检出率相当，〔06:08〕"Out of two million uh persistent flows, we flagged uh fifteen thousand as suspicious"；但这一量级的潜在误报会造成显著附带损害，因此必须叠加主动探测、把准确率提到现实审查者可接受的水平〔06:23〕。对 OpenVPN 设计主动探测并不简单，因为多数 OpenVPN 服务器使用的防御机制反而顺带让它们对盲打探测保持沉默；但精心设计的探针即使服务器对所有探测都沉默也能高准确率识别〔06:37〕。每个探针利用 OpenVPN 必须具备的特征：TCP 流的分包方式、以网络 MTU 为函数的合法报文长度定义，以及可预期的网络层行为，例如服务器断开连接前经过的时间〔07:06〕。举例：OpenVPN 服务器要等当前报文全部片段从 TCP 流中重组完毕才会去解析加密错误，故第一个探针因 HMAC 签名无效被立即丢弃，第二个会在重组缓冲区里多留一会儿直到超时，从而观察到不同的连接关闭时间；而绝大多数非 OpenVPN 服务器对这两个探针的响应高度一致〔07:29〕。把过滤与探测组合成框架去测试真实世界的 VPN 实现，效果显著：不仅检出原版 OpenVPN，还出乎意料地识别出三分之二以上的混淆 VPN 连接，主因是这些混淆服务以 OpenVPN 为骨干却未能有效掩盖指纹〔08:14〕。进一步考察排名靠前的混淆服务采用哪些策略：最流行的是某补丁（转写音写为 "ads or patch"），它用若干异或操作打乱载荷，但输出字节总是与密钥的同一字节、同一位置比特异或、因而总映射到同一密文；尽管 OpenVPN 官方不建议使用，前五名中四家供应商都直接开箱使用它〔08:54〕。这些供应商同时对外宣称不可观测性、给用户虚假的安全或匿名感，若用户在禁用 VPN 的地区依赖这种不可观测性则更糟〔09:17〕。附带损害方面：框架在镜像流量上连续运行一周，标出约 3600 条 OpenVPN 连接，误报率上限比机器学习分类器低三个数量级〔10:04〕；由于是真实 ISP 流量、没有严格真值，遂人工核查，90% 的被标连接找到旁证，例如共享端口上的 OpenVPN Web 界面，具体包括 common name 或 whois 记录〔10:24〕。结论是：OpenVPN 是否易被 ISP 指纹化？是的，而且出人意料的容易，即便配合野外大多缓解补丁——普通用户可能面临限速或阻断，高风险用户则可能招致针对隧道本身的后续攻击〔10:28〕。作者已向相关供应商披露并提供如“服务器该如何响应失败握手”之类的短期建议〔10:52〕；积极面是主流供应商如今普遍提供某种混淆服务、说明不可检测已进入其威胁模型，但研究界在抗指纹混淆上的进展与供应商实际部署之间存在巨大鸿沟，本文意在缩小该差距，后续将弄清是什么拖慢了有效混淆的落地——是运维成本、性能权衡还是其他〔11:13〕。（YouTube EPZNVff1rH-vA，[368-731]，L1）
- 〔AWS 存储架构主题演讲（会议不详）〕主讲人称这次与他的前一场演讲非常不同，讲存储在 AWS 的工作与教训：CAP 定理所类理论边界带来的取舍、可用性与“爆炸半径”如何塑造设计，以及为满足某块特定需求而建的系统 Phaethon 的架构〔00:10〕。先把云块存储简化到极限：一个客户端驱动 I/O、一个主副本与一个副本、类链式复制协议——搬数据好用但不等价于共识，所以重配置需要外力〔01:09〕。若网络分区形成（两端网络都活着却过不了那条线）而仍想继续 I/O，因复制协议不是完整共识、无法安全继续，只能求助“更高权威”：主说它原本就是主、数据全、最新、缓存是热的、还想当主，副本说听不到那个主所以要接管；两者找权威、权威必须一致裁决，需要的性质是线性一致性，即线性的 compare-and-swap／compare-and-set 操作〔02:22〕。矛盾由此而来：这份一致性与全部想要的可用性无法兼得〔02:38〕。一种退化情形：分区后主能到权威、而权威必须是网络中唯一一点（因其一致性无法同时存在分区两侧），副本却能到客户端、客户端只能被动不可用——对云架构基础件而言很糟；更常见的是配置服务自身被分区或故障打挂、一侧或两侧都够不着。真实数据中心的分区也不是一刀切、而是一段混乱期，之后能互通的东西零散、协议不同、端口不同；因此躲不掉的决定是共识多数必须放在分区的上侧或下侧、二者不能兼得〔04:25〕。若想要极高可用，办法是缩小半径——画尽可能小的圆、把客户端、主、副本与配置服务都放进去，只要足够小、无论数据中心被怎么切那条线都极不可能穿过你〔04:43〕。云上架构靠冗余换可用性（两份副本、RAID、主备、故障转移），但总有个星号：只有故障互不相关时冗余才提升可用性——一箱 RAID10 遇上失火、全网络副本遇上全网故障，冗余毫无帮助〔06:27〕。故可用性有三件事：宕机稀少、修复短暂（云厂商在此持续重投）、影响面小；小即不相关，任何问题应影响尽可能少的资源，客户才能用冗余获得优于任一单组件的可用性、消掉那个星号〔07:40〕。多年来 AWS 越来越重视“小”，内部有爆炸半径之说：压低任何一次故障触及的客户数、资源数与事物数〔08:39〕。这带来架构大转向：云计算早期崇尚造最大、最坚不可摧、铺最广的系统以换经济性，但这类大铁块其实并不坚不可摧，需要一点谦卑——故障发生时能弄得多小〔09:26〕。灵感来自僧帽水母 Physalia physalis：它不是一个个体、而是许多各自擅长某一角色的小个体合演一只漂浮水母，由此想到用大量小部件构建有机体〔09:33〕。回到半径：把客户端、主、副本尽量放在一起，紧邻再建一个小共识系统——图示五个节点、生产版七个——作为更高权威即这个配置存储、好在出问题时恢复复制协议，每组这样的小共识组称为一个 Fazelia cell（转写在 five alias cell／Fasalia／Fazelia 间摇摆）〔10:20〕。（YouTube EPZO9AxJTlgsU，[4-620]，L1）
