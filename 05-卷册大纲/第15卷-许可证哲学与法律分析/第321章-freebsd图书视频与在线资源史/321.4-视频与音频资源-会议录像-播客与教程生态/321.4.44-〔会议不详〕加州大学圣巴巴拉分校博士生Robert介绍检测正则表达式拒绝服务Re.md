# 321.4.44 〔会议不详〕加州大学圣巴巴拉分校博士生Robert介绍检测正则表达式拒绝服务Re

- 〔会议不详〕加州大学圣巴巴拉分校博士生 Robert 介绍检测正则表达式拒绝服务（ReDoS）漏洞的动态分析系统 Regulator。ReDoS 的本质是攻击者以极小代价实现攻击放大的不对称性，正则表达式恰是这种"难以识别却易被利用"的隐藏复杂度载体：一个周下载两千六百万的 npm 包中看似无害的正则即被确认为最坏情况多项式时间运行的漏洞。作者指出以往工具基于 NFA 歧义性建模，但现代回溯式正则引擎（如 Firefox/Chrome/Node.js 使用的 Irregexp，ASR 转写为 eregex）实为嵌入现代语言的完整软件系统——词法、解析、编译为字节码后在轻量解释器上运行（即 Spencer 回溯算法），且既有工具对引擎新特性支持有限、误报漏报率高。（YouTube EP76RSI-53A4k，[8.4-353.7]，L1）
- 〔会议不详〕Regulator 拥抱"正则即软件"的理念：先用改进的 slowdown fuzzer 在 Irregexp 解释器上以 AFL 式 perf map 收集字节码分支覆盖、寻找最慢输入（含记录分支处应替换字符的 suggestion 变异及对陈旧输入降优先级），再取最慢 witness 串启发式扫描推导"攻击前缀-泵串-后缀"公式，经采样与模型拟合判断复杂度曲线是线性、多项式还是指数，最后动态验证：最长（一百万字符内）攻击串若造成十秒延迟即标记为 ReDoS 漏洞并二分搜索最慢串。评测使用三个标准正则语料并抓取 npm 四万条正则：真阳性率比既有工具高 2-7 倍、漏报率低，报告漏洞获分配 6 个 CVE，检测出依赖 flags、高复杂度及 backreferences/lookarounds 等高级特性的难测漏洞；并建议将输入长度限制在 1000-10000 字符即可缓解绝大多数 ReDoS。（YouTube EP76RSI-53A4k，[399.7-824.1]，L1）
- 〔SYSTOR 2014（推测）〕犹他大学 Xing Lin（与 EMC 多位合作者）介绍 Migratory Compression：通过粗粒度数据重组将相似块分组以提升可压缩性，可作为任意标准压缩器的通用预处理阶段。传统压缩器受窗口大小限制——gzip 窗口小、压缩差但快，7z 窗口最大也仅 1GB、压缩最好但最慢，bzip2 居中；Zlib 先做文件内去重再用 bzip2 压缩余量，达到接近 7z 的压缩比且更快。工作有两个动机与用例：Mzip 压缩单个大文件（先重组使相似块相邻再用标准压缩器），以及去重存储系统从备份层向归档层迁移数据时将散落在不同压缩区域的相似块压入同一压缩区域。相似块检测采用 Broder 十多年前提出的相似特征技术（强哈希查重、弱哈希特征提示相似），曾用于 block-level 冗余消除等项目；数据重组提出 multi-pass 多趟顺序扫描优化，把随机 I/O 转化为若干次顺序扫描。（YouTube EP77cGm3RSEL0，[9.8-623.7]，L1）
- 〔SYSTOR 2014（推测）〕评测覆盖 workstation 备份、Exchange 邮件备份与虚拟机磁盘镜像数据集：workstation 一号上 gzip 约 20MB/s、2x 压缩比，叠加 Migratory Compression 后压缩比与吞吐同时提升（去重与数据重组是两大来源）；对去重率极低的 Exchange 备份压缩比仍升但吞吐略降、预处理开销显现。即便 7z 以最大参数运行（压缩比 6x），叠加该技术仍能同时改善两项指标。数据迁移实验将相似块按簇大小排序分三阶段迁移，压缩比提升 44% 至超过 150%（workstation），降低归档层磁盘占用；代价是迁移耗时近三倍、读回更慢（仅重组 top 簇时运行时仅增 24%）。Q&A 中 IBM Almaden 研究员问及解压需整体重组并提到 Google Bigtable 曾用 Bentley-McElroy 相似方法，UC Santa Cruz 的 Ethan Miller 质疑"挤干冗余影响可靠性"，Microsoft Research 的 Jay Lorch 询问改造压缩器本身使其重组感知的可能性。（YouTube EP77cGm3RSEL0，[625.1-1601.8]，L1）
- 〔会议不详〕主讲人 Matthias（ASR 转写为 Matthias Kotschack）讨论 AVX2/AVX512 等功耗密集指令下的公平调度问题。现代 CPU 受功耗与 dark silicon 限制，AVX2/AVX512 代码必须在降档频率执行，且降频会波及完全不用这些指令的其他任务，相关工作中 AVX512 负载测得超过 15% 的不公平。两种典型场景：上下文切换后 CPU 因不知道下一任务是否再用 AVX 而实施频率变化限速，使新任务以远低于应有的频率执行（任务 A 拖慢任务 B）；超线程两线程共享一个核频，一个线程跑 AVX512 会拖慢另一个。这破坏了"等 CPU 时间即等相对性能"的性能隔离假设，因此需要重新思考公平调度：提出恢复"所有任务获得相同相对 CPU 性能"的直观公平定义（给受降频影响的时间片稍多 CPU 时间），并论证以能量为一等调度资源需要当前 CPU 上不可能构建的精细能耗模型，故改为修改现有基于时间的公平调度——从时间片中减去降频损失的时间。（YouTube EP77cM6m-KXAI，[7.7-469.4]，L1）
- 〔会议不详〕实现上以"理想频率与实际频率之比"度量不必要的降频，用性能计数器统计时间片内高/低频档时间占比（难点包括 AVX512 之外的 AVX2 档与 Turbo Boost 依赖活跃核数的众多频率档，OS 并不知道上一时间片平均活跃核数），并在上下文切换时禁用 256/512 位向量寄存器、以首次 AVX 指令触发的异常记录任务是否用过 AVX，仅对未使用且降频不必要的时间片做补偿。原型发现修改时间记账后不同核上"时间流速"不一，需要迁移任务实现全局公平，遂改用外部多队列调度器（ASR 转写为 external multiqueue cplist，应为 MuQSS 类 deadline 调度器）并移植 CFS 公平算法。在 Intel Xeon Gold 6130 上以 PARSEC、Nginx、内核构建等负载与 x265 视频编码器并行实测：平均将 AVX512 导致的不公平降低四倍，大多数基准无统计显著的额外开销，仅串行段长的基准收益有限。（YouTube EP77cM6m-KXAI，[470.7-906.9]，L1）
- 〔会议不详〕主讲人 Zory（ASR 转写）介绍 HyperTurtle：通过把 L1 客户机 hypervisor 的代码安全地卸载到 L0 宿主机、改写为在 L0 运行的 eBPF 程序，通用加速嵌套虚拟化。动因是虚拟化容器（如 Kata Containers）部署在虚拟化基础设施上时承受嵌套虚拟化开销：EPT fault/VM exit 处理比非嵌套慢五倍、启动 Kata 容器慢两倍、profiler 采样器慢近十一倍。慢的根源在于 L1 以非 root 运行、其虚拟化操作被 L0 陷入模拟，L2 嵌套 guest 的 VM exit 全部透传 L0，引发大量 world switch；既有工作（EuroSys'19、ASPLOS'20、SOSP 等）作用域有限、缺乏通用方案。HyperTurtle 的设计目标是通用基础设施、非侵入（L0 仅数百行代码、隔离于 KVM 与 eBPF 模块、便于上游化）、保持 L1 控制权与高性能；借鉴 ATC 2018 的 hyper upcalls（guest 向 host 导出 eBPF 作通信通道），把四次 world switch 化为 L0 上由 eBPF 程序处理的一次，并给出共享信息（eBPF maps、helper 函数）、定义 hook、编写程序的三步加速配方，且必须保持 L1 之间的隔离。（YouTube EP78g1bG3BOFs，[18.3-465.7]，L1）
- 〔会议不详〕以嵌套虚拟内存管理为例：L0 影子化 L1 的 EPT 生成 combined EPT，这一影子化使 EPT fault 慢五倍且占容器启动时间 46%（非嵌套 7 微秒、嵌套 35 微秒，5x 减速、3x world switch 增加）；按配方共享 VMM 页表根地址与帧池、在 L0 页表遍历发现缺失项后调用 eBPF 程序修复 combined EPT（失败则回退注入 L1），恢复到接近原生的 7 微秒。端到端评测：容器启动时间（Alpine、Java、预载 1GB 快照的 Redis）降低 27%（Redis 14 秒启动降 35%，应用用内存越多收益越大）；网络方面以 L1 中 eBPF 防火墙策略对比 nested virtio 与 direct virtual assignment，在 500 微秒 SLA 下 memcached 吞吐提升 72%（约 9% 减速，策略越轻减速越小）；嵌套 guest profiling 采样延迟从近 60 微秒降至接近非嵌套的 7 微秒（7x 降低），对 Memcached 等时延敏感应用约 20% 改善；论文与代码均已开源。（YouTube EP78g1bG3BOFs，[465.9-941.7]，L1）
- 〔会议不详〕主讲人（与 Microsoft Research、UIUC 及清华大学合作者）介绍 X-Kernel：为 Linux 内核中成千上万个编译期冻结的关键性能常数（perf-cants，含阈值、间隔、批量大小、缩放因子）提供原则化可调性。开篇以 block layer 决定批量合并请求数的宏为例：HDD 顺序读将默认值调大（如 128，ASR 转写为 one to eight）吞吐提升近 50 倍，而 NVMe 上随机写负载的 RocksDB 将其设为 1 可降 29% 延迟；云端混合负载下 NVMe 随机 I/O 与 HDD 顺序 I/O 共享一台服务器，一个全局值无法兼得，而 commit message 显示该默认值当年是随意选定的。理想的可调性是：运行时调参、启发式与策略可编程且可变粒度（如仅对特定设备生效）、更新快速；sysctl 方案需重编译重启且难以上游，Linux KLP（内核热补丁）无需重启但同样无细粒度策略与副作用保护，且每次改值都要重新编译、极其缓慢。（YouTube EP79P4FauqUj0，[19.4-388.0]，L1）
- 〔会议不详〕X-Kernel 基于 scoped indirect execution（SIE）：对源码与二进制随机改值做一次性重编译，经 binary diff 得到 seed instructions 定位常数分布；再用符号执行与线性回归建立源级值与寄存器（如 iv=2v，写 eax）的对应，并沿前向/后向追踪把 seed 指令扩展为 critical span——常数影响运行时状态之处；安全上以依赖分析把基本块扩展为 safety span，获得比语句级（源级）与函数级（热补丁）更强的版本原子性保证，仅当无线程程序计数器落在 span 内时切换，避免线程内/线程间不一致导致系统崩溃。系统完全构建于内核原生机制（kprobe 挂载处理器、eBPF 编写策略并经 BPF helper 读取设备名等应用提示），无需修改内核即可部署于开箱 Linux。案例包括 TCP cubic 缩放因子按 RTT>80ms 条件置 1 使高 RTT 流的流完成时间显著改善而低 RTT 流几乎不变、软中断最大执行时间（降低最坏情况时延换 CPU 占用）与内存回收批大小（减小批大小增加数据重用、改善内存访问时延）的新权衡。（YouTube EP79P4FauqUj0，[389.7-939.5]，L1）
- 〔NSDI（推测）〕Metron：以底层硬件真实速度运行的 NFV 服务链平台。主讲人 Yorgos（Georgios P. Katsikas，与 Tom Barbette、Diane Kostich 等合作）指出 2009-2017 年数据中心链路速率增长五十倍而 CPU 晶体管增长跟不上，NFV 服务链依赖通用 CPU 已成瓶颈；在百吉比特测试床上，E2 线性扩展到约 12 核后性能退化，OpenBox 虽优于 E2 仍达不到硬件上限，而 Metron 通过将路由表卸载至 Mellanox 网卡、在硬件中先行流量分类与打标再映射到正确 CPU 核，实现服务链组件间零核间通信，匹配 76 Gbit/s 硬件吞吐上限，效率较最先进方案提升 6.5 倍。（YouTube EP6-U5AOjbhjo，[10.5-703.9]，L1）
- 〔NSDI（推测）〕Metron 的评估与结论：从 40G 到 100G 部署及动态负载均衡。在 40 Gbit/s 防火墙+DPI 服务链中，Metron 将防火墙卸载到 OpenFlow 交换机、每核支撑 4 Gbit/s 并驱动至约 38 Gbit/s 的硬件上限，延迟较现有系统降低 35%-97%；在 100 Gbit/s 部署中通过逐一关闭硬件卸载与准确 CPU 分发量化各贡献的收益；在 10 Gbit/s 可变速率负载下，控制器检测到核心过载后拆分流量类别并重新打标实现动态 CPU 核分配，开源组件包括 ONOS 控制器驱动与 FastClick 扩展。（YouTube EP6-U5AOjbhjo，[705.4-1153.5]，L1）
- 〔SREcon（推测）〕Twitter 的多路复用 RPC 之路：Thrift 与 TCP 的痛。主讲人 Burke（Twitter SRE，转向前端流量管理）回顾 Twitter 自 2007-2008 年选用 Thrift 作为 RPC 协议，指出其类似 HTTP/1.1 的请求-等待模式带来队头阻塞；由于大规模分布式架构扇出巨大，逐次建立 TCP 连接的三次握手、慢启动与子毫秒级延迟累积，使端到端 50ms 的目标难以达成，而 TCP keepalive 间隔不短于两小时且由内核而非应用控制，无法支撑存活性检测、请求取消与可用性通告。（YouTube EP60hVn7kMfqY，[9.7-1771.9]，L1）
- 〔SREcon（推测）〕Mux 的设计与生产实践：NACK、租约与目的地分发。Burke 介绍开源的 Mux（Finagle 的一部分，已开源一年多并大规模用于生产）：作为会话层协议复用任意七层协议，通过显式队列管理提供 NACK、背压信号与租约机制（协议以纳秒通信，租约可选）；Finagle 可预测年轻代 GC 并提前只发 10ms 短租约、回收租约以优雅排水，实现毫秒级背压逐层向上传播直至前端返回 retry-after 头。目的地分发让 Mux router 承载逻辑路由、灰度切流与透明转发到 staging 集群，RPC 认证在会话层一次性解决，RPC Tab（类似 awk 的分布式系统故障注入调试工具）为 hack week 产物。（YouTube EP60hVn7kMfqY，[1772.1-3543.8]，L1）
- 〔NSDI（推测）〕SafeBricks：用 SGX 与语言级隔离解决云中网络函数的安全三难。主讲人 Rushabh（与 Chang Lan 等合作）指出 NFV 外包到云后需同时保证：流量不泄露给云提供商、NF 不来自恶意独立软件商外泄流量、NF 代码与规则集对客户和云保密，而端到端 TLS 无法在密文上计算、BlindBox 等专用加密方案又功能受限；SafeBricks 结合 Intel SGX 硬件 enclave 与基于 NetBricks/Rust 语言隔离的 NF 框架，网关截获 TLS 连接经 IPsec 隧道送入 enclave 内解密处理，报文头与载荷在云端始终加密、仅在 enclave 内解密。（YouTube EP64cLVRZ_WOE，[10.2-697.4]，L1）

- 〔CoNEXT（推测）〕Green：用服务器间横向直连链路替代昂贵的多归属。主讲人 Alex（与 Zvone、Costin Raiciu 合作，来自罗马尼亚布加勒斯特理工大学 UPB）观察到数据中心网络过度供给而端主机只用单网卡，多归属（双 ToR 交换机）虽能翻倍可用容量但购置与运维昂贵；Green 直接用交换机多余端口在服务器间连横向二级链路，配合 Multipath TCP 把一条连接拆分为多个子流，理想情况下获得多归属性能而无需第二台交换机。分析表明 HN 多跳横向路由并不比只用直接邻居更能找到空闲容量，故采用 H1 路由并设计 Green 编址方案：地址由服务器标识符加 Green 标识符组成，主地址以 1 结尾、二级地址复制邻居服务器标识符。（YouTube EP67Td-i0pSnk，[10.2-659.7]，L1）
