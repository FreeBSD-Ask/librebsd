- 〔会议不详〕阿里云的 Jinke 介绍 C-Star Gateway（转写中亦作 C-SAR/Cesar Gateway），为公有云上异构网络功能虚拟化（NFV）补齐基础设施短板。阿里云 NFV 以 VNIC 作为租户流量端点、多个 NFV 虚拟机组经 ECMP 分担流量，这种对既有云基础设施的完全复用带来根本张力：基础设施为租户 VM 优化，而作为中间转发节点的 NFV VM 资源消耗模式根本不同。生产数据识别出四类关键资源错配：VNIC 耗尽（NFV VM 三个可用区平均消耗 97 个以上 VNIC、租户 VM 仅约 2 个；SmartNIC 存储资源有限，每服务器只能支持约 4000 个 VNIC，属经济性设计约束而非硬件瓶颈）；会话耗尽（负载均衡类 NFV VM 面临高达每秒 100 万的并发短流突发，填满 vswitch 会话表后新流被丢，而 CPU/内存/I/O 仍有大量余量）；中央转发闲置 CPU（中转路由器近乎峰值 I/O 时 CPU 仅约 6%，Tbps 规模下按 I/O 扩容而闲置 CPU 在经济上不可持续）；以及 RSS 下大象流钉死单核造成的丢包风险。对此提出在租户 VM 与 NFV VM 之间引入最小侵入的内核态无状态网关方案，且无需改动 vswitch 本身。（YouTube EPOElpdlC1v1A，[17.2-480.8]，L1）
- 〔会议不详〕C-Star Gateway 的三个核心设计组件与上线评估。一是 VNIC 聚合：网关引入伪唯一 ID 替换原 vswitch 的 VNI/服务 IP 到物理 VNIC 的映射，包封装进 Geneve 隧道（外层再套 VXLAN）传输，NFV VM 侧解封装后据此查租户配置并执行访问控制，每 NFV VM 只需一个基础 VNIC，彻底消除 VNIC 耗尽；二是会话聚合：多条租户流聚进单个 Geneve 隧道，vswitch 只见外层五元组，多条分布式流只占一个会话条目，并按流在受限端口范围内随机化 UDP 源端口保证 ECMP 散列多样性；三是对 I/O 密集与大象流由 NFV VM 监测每流包/字节计数器，检测到后经控制平面通知网关重定向到专用 FPGA 集群并迁移会话条目实现无缝切换（其余仍由 NFV VM 处理以保弹性），同时把 ECMP 一致性哈希从数百台分布式交换机收敛到集中网关。上线后三个可用区 NFV VM 的 CPU/I/O 利用率从不足 10% 提升至少 5 倍，内存占用平均仅增 4.3%，NFV VM 数量分别减少 80%、94% 与 91%，扣除网关自身成本仍有显著节省。（YouTube EPOElpdlC1v1A，[559.9-988.7]，L1）

- 〔会议不详〕来自 UC Berkeley 与威斯康星大学麦迪逊分校合作的 Romil 介绍通用性能感知资源分配框架 Cilantro。等分资源（100 个 CPU 平分给 Alice 与 Bob）公平但低效，而 Kubernetes、Slurm 等现代调度器让用户自报资源需求，用户却往往不知道达到 SLO 所需的资源、只能给估计值，导致低效分配。Cilantro 主张性能感知调度：用户只提交 SLO 与反馈，由事先未知的资源-性能曲线（如 SQLite 上跑 TPC-DS 的吞吐-CPU 曲线）把 SLO 映射为资源需求，且当资源不足以满足所有 SLO 时由集群管理员声明性能或公平类目标。框架用在线学习持续收集作业反馈（延迟、SLO、当前负载）更新资源性能模型，并把分配策略与学习机制解耦，使模型成为任何策略都可用的中间层；针对搜索空间大而昂贵、模型估计带置信区间的不确定性两大挑战，先以“单调不减且在 SLO 处截断”的约束效用模型压缩搜索空间。（YouTube EPOFjlUqHbrMQ，[16.5-440.3]，L1）
- 〔会议不详〕Cilantro 的目标表达、不确定性感知策略与微服务评估。约束效用模型支撑起经典框架无法表达的多样目标：最大化跨作业平均效用的社会福利、最大化最小效用的平均主义福利（防饥饿）、面向微服务集合的端到端延迟最小化，以及类似 maximin 的 NJC（无正当抱怨）公平；策略采用“不确定性面前保持乐观”（OFU）原则，用模型置信上界平衡探索与利用（按最高上置信界选动作、按实际回报校正模型）。评估在 DeathStarBench 的 Hotel Reservation 基准（19 个微服务）上进行：Cilantro 只观测端到端查询延迟、对微服务结构与个体性能无先验可见性，即可自动定位瓶颈微服务并分配资源；与均分资源、epsilon-greedy 和进化算法三个基线相比，其先保守探索、随估计变准而快速收敛，将 p99 延迟压到次优基线的 43%。（YouTube EPOFjlUqHbrMQ，[462.7-916.9]，L1）
- 〔会议不详〕Google 研究者（与在场的 Dan、Chandra 紧密合作，系统由大型工程团队构建）讲述在 Gmail 等生产系统上做有意义的性能实验所需的负载认知。QPS 并非平滑昼夜曲线而是极端尖峰与陡降，且以平均响应大小衡量的请求混合一周内可变化 2 倍。原因在于系统同时服务用户可见请求与非用户可见请求（如大规模数据不变性检查）：后者优先级低、被前者节流，形成此消彼长；即便只看用户可见请求，白天笔记本/桌面访问与夜间手机同步仍使混合变化 20% 以上；非用户可见请求更不可预测，会并入一次性事件——如比利时数据中心遭四次雷击宕机后，系统自动在数日内重建丢失的数据副本、非用户可见请求激增。因此只能做同时刻对比的 test/control 实验：同一代码同配置各 10 万活跃用户时 p95 延迟差异仍可达 50%，而每组 1000 万以上用户才能检出 1% 的性能变化。（YouTube EPOGW2JS3Q5rk，[97.1-610.6]，L1）
- 〔会议不详〕性能回归调试所需的运营上下文与时间上下文：垂直上下文注入与协同突发采样。跨层传 token 的传统追踪方式难以覆盖不受控的库代码、也不敢进内核；Google 改用垂直上下文注入——用 ftrace 等现成机制收集内核级轨迹，各层通过风格化的系统调用（如给 getpid 传参标记高层操作起止）把信息注入内核轨迹，从而给内核事件着色归属到高层操作（含 RPC、锁争用）；曾借此定位到服务用户请求时对用户属性的大量细碎读取形成的惊群导致 CPU 突发与限流。时间上下文用协同突发采样：对当前毫秒时间戳应用低位 d 位为 0、高位 P-d 位为 1 的位掩码（如掩码 11100 即每 32ms 采 4ms 突发），借机器时钟跨进程对齐突发，再与跨机 RPC 追踪系统 Dapper 结合。结论：须在生产环境做千万级用户的长期受控 A/B 实验（test/control 同数据中心、各千万用户、约一周以覆盖周周期），生产数据采集必须高效克制。（YouTube EPOGW2JS3Q5rk，[805.6-1239.5]，L1）
