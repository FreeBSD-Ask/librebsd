- 〔USENIX Security（推测）〕Z-Lane 系统设计与部署评估。Z-Lane 由路由器调度机制与部署在源网络边缘的网关组成：路由器用单个优先级队列加每网络令牌桶实现带宽隔离（每令牌桶仅 20-60 字节内存、合规检查只需几十纳秒；内存优化的令牌桶降到 8 字节，并借助 SCION 的 ISD 按网络组配置速率，10 万网络也仅需 5.3 KB），低于保证速率的流量确保转发、超出部分仅尽力而为；网关把网络级保证速率分发到终端主机并隔离同网主机，超用流量按策略拒绝授权或丢弃。与传统反应式方案不同，Z-Lane 主动即时提供转发保证且与攻击者流量模式无关：未认证攻击流量因低优先级不影响认证流量，认证攻击流量也无法耗尽带宽保证。团队在 SCIONLab（ASR 误写作 Zyan Lab）全球研究试验床上部署三个月未见问题并验证了网络级与路由器级增量部署，DPDK 高速版路由器与网关在商用硬件上演示 60 Gbit/s 转发、性能随核数线性扩展；结论是 Z-Lane 可与带宽预留系统共存（后者保护视频会议等长时流量），为高可用 DNS 等新应用奠基。（YouTube EPlV1y8TSrslo，[313.0-624.6]，L1）
- 〔OSDI（推测）〕This talk is about providing tenants or users in shared data centers absolute triple guarantees。主讲人 Chris（ASR 未给出全名，Q&A 中被称 Chris）指出云数据中心共享设备（key-value store、load balancer 等 appliance）上“激进”租户会挤占他人资源，实测租户在设备与网络资源上的吞吐可相差达 5 倍，且网络语义与设备语义各自隔离都不足保证端到端（读请求在网络上仅约 80 字节的头部，却可与写请求同样昂贵，单独在设备上隔离又因读请求占比畸高而失效）。他提出虚拟数据中心（VDC）抽象来承载端到端保证：VM 经虚拟网络连接虚拟设备，每条链路与设备都关联固定或最低的虚拟容量，兼顾要可预测性与要弹性的租户；度量上用绝对但以 token 计的虚拟请求代价（virtual request cost），由提供方公布代价函数把请求类型、大小等特征映射为 token，避免按最贵请求保守供给，也免去分别量化 bits/s 与 IOPS；系统 Pulsar 以 hypervisor 中的 rate enforcer 模块实现限速（不改 appliance、客户 OS 或应用），由集中控制器按租户与提供方两类策略协调各 enforcer。（YouTube EPnV8wUjdfnzQ，[9.8-769.9]，L1）
- 〔OSDI（推测）〕容量估计、实现与评估。由于设备容量随负载变化，Pulsar 借鉴拥塞控制隐式估计容量的思想，由控制器维护估计窗口并用二分搜索按拥塞信号（如设备吞吐远低于估计值说明估计过高）收敛到“满足所有保证时”的最大设备容量，负载显著变化时重启估计，通常 10 秒（10 个控制间隔）内收敛。实现上 rate enforcer 位于 Hyper-V 并用新研多资源令牌桶执行分配，控制器复用 DRF、HDRF 等多资源分配机制实现富策略；在 40 Gbit/s 网络、10 台计算服务器、113 个 VM、4 个共享资源租户（Hotmail trace 驱动负载）的测试床中，关闭 Pulsar 时激进租户夺走大部分吞吐、保守租户保证亏空 64% 与 32%，开启后所有租户保证均满足且空闲资源按保证比例分配（总吞吐约低 7-10%，因工作负载性质被改变），enforcer 软件开销多数请求约 2%（512 字节小请求约 15%，源于 40 Gbit/s 下的数据结构锁），富策略下可支撑约 2.4 万 VM 与 200 台 appliance；问答（UBC 的 Nodir、George Washington University 的 Tim Wood、Stanford 的 Henry 等提问）确认代价函数固定、暂不提供延迟保证，并建议用 Cicada、Bazaar 等工作从高层需求推导 token 保证。（YouTube EPnV8wUjdfnzQ，[769.9-1531.9]，L1）
- 〔会议不详〕OxFS：跨用户态、内核与设备层的协同式文件系统。主讲人 Jonghyun（UIC 与 KAIST 的合作工作）指出设备层随 PCIe 世代演进最快，内核开销使文件系统无法充分利用高速设备；用户级文件系统（如 UFS）虽吞吐高但 CPU 消耗达 ext4 的三倍以上、文件系统栈差距达 15 倍，设备侧文件系统又受 PCIe 传输延迟与弱设备 CPU 限制。其协同式架构把用户库（OxLib，经 hook 系统调用免改应用接入）、主机服务器、内核组件（不改内核代码的新内核文件系统）与设备服务器整合进单一文件系统，各组件各展所长。（YouTube EP20DSQXffRyk，[18.6-411.6]，L1）
- 〔会议不详〕OxFS 关键设计与评估：非对称 I/O 路径、元数据共享所有权与拆分日志。读写系统调用被转为对内存映射文件的内存操作，读经内核 page cache 并按 read-ahead 预取，写绕过内核用用户级线程吃满设备性能；元数据读入共享内存由三个主机侧组件免拷贝共享，inode 每个属性只有单一属主，卸载任务只操作块地址以减少主机与设备间通信。设计 split journaling 把 fsync 与周期性后台提交拆成两条独立持久化路径以消除崩溃一致性串行化依赖，在 BlueField DPU 加 Samsung SSD 模拟计算型存储的测试床上，OxFS 吞吐较 UFS 最高提升 86%，并取得最高 CPU 效率。（YouTube EP20DSQXffRyk，[441.0-1058.5]，L1）
- 〔会议不详〕热恢复（Hot Restore）：面向虚拟机集群的快速恢复系统。主讲人李智（Li Zhi，Beihang University/北航）指出大规模云大量使用商品硬件，其年故障率可达 20%-60%，而当前快照/恢复机制恢复单个虚拟机需取回多达数十 GB 的内存状态、耗时长，且各虚拟机恢复延迟差异会引发 TCP backoff 等网络中断问题。用 distcc 编译 Linux 内核的 12 虚拟机实验显示恢复延迟超过 60 秒，且 VM 之间延迟差约 20 秒。（YouTube EP2_A4GGK4y0A，[9.8-216.6]，L1）
- 〔会议不详〕解决方案与结果：弹性工作集与恢复线（restore line）。一是以 post-copy 式快照在 checkpoint 期间追踪被触碰页构成弹性工作集，只按需加载数十 MB 即实现约 94% 缩减；二是从时序执行构建恢复依赖图（A 发包给 B 则 B 先启动、环内节点同时启动），再结合工作集大小次序用线性规划求出一致的最终工作集尺寸。在 QEMU 平台实现并在 Elasticsearch/distcc 负载下验证，backoff 时长降至毫秒级、虚拟机可在数秒内恢复；提问环节确认依赖模型基于快照期间记录的数据包。（YouTube EP2_A4GGK4y0A，[218.1-745.6]，L1）
