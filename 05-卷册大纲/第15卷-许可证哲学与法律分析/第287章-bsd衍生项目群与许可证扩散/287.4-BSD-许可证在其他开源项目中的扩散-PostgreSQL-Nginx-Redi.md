# 287.4 BSD 许可证在其他开源项目中的扩散——PostgreSQL、Nginx、Redis 等明星项目的许可证选择

## 287.4.1 PostgreSQL、Nginx 等明星项目采用 BSD 许可证

**要点**：PostgreSQL 采用 PostgreSQL License（BSD 风格许可证，类似 BSD 或 MIT 许可证），1996 年由 PostgreSQL 全球开发组继承 Postgres 95 项目，长期以 BSD 风格许可证发布；Nginx 由 Igor Sysoev 于 2002 年春开始开发，2004 年 10 月 4 日首次公开发布，采用 BSD-2-Clause 许可证，2011 年成立 NGINX 公司，2019 年 3 月被 F5 Networks 以 6.7 亿美元收购，开源版保持 BSD 许可证；Redis **历史采用** BSD-3-Clause 许可证，2024 年 3 月 20 日 Redis 商业公司 CEO Rowan Trollope 宣布自 Redis 7.4 起改为 RSALv2（Redis Source Available License v2）/SSPLv1（Server Side Public License v1）双许可证，**不再是 BSD 系开源许可证**，属 “源代码可用”（source available）而非 OSI 认证的开源许可证；作为反应，Linux 基金会于 2024 年 3 月底 fork 出 Valkey 项目，采用 BSD-3-Clause 许可证延续 Redis 开源血脉；**PostgreSQL License 与 BSD-2-Clause 的具体条款差异**[考据完成：2026-07-30 经 postgresql.org/about/license/ 一手核验]：（1）权限表述——PostgreSQL License 用 "Permission to use, copy, modify, and distribute this software and its documentation for any purpose, without fee, and without a written agreement"，BSD-2-Clause 用 "Redistribution and use in source and binary forms, with or without modification"，PostgreSQL 措辞更宽泛（明确覆盖 copy 与 modify，且明示 "without fee" 与 "without a written agreement"）；（2）再分发条件——PostgreSQL License 要求 "the above copyright notice and this paragraph and the following two paragraphs appear in all copies"（不区分源码与二进制），BSD-2-Clause 区分源码（"retain the above copyright notice, this list of conditions and the following disclaimer"）与二进制（"reproduce the above copyright notice... in the documentation and/or other materials provided with the distribution"）；（3）责任主体——PostgreSQL License 因继承 Berkeley 版权（"Portions Copyright © 1994, The Regents of the University of California"）故以 "UNIVERSITY OF CALIFORNIA" 为责任实体，BSD-2-Clause 以 "THE COPYRIGHT HOLDER AND CONTRIBUTORS" 为责任实体；（4）免责声明——二者均含 AS IS 免责与不承担维护义务声明，措辞近似；这些明星项目（PostgreSQL、Nginx）选择 BSD 系许可证，体现 BSD 许可证在数据库与 Web 服务器领域的历史主导地位

**史料**：postgresql.org/about/license/、postgresql.org/docs/current/history.html、nginx.org/en/LICENSE、Sysoev Nginx 历史访谈 ［B］

**史观**：总纲第 24 条——许可证：BSD 许可证在基础设施软件中的扩散；总纲第 14 条——商业与社区的张力：BSD 许可证允许商业采用但不强制回馈

**辨析**：PostgreSQL License 与标准 BSD-1-Clause 的差异需通过许可证原文核实；Nginx 商业化后许可证是否变化须查 nginx.org 当前 LICENSE；“BSD 系许可证主导” 需通过其他许可证（Apache 2.0、MIT、GPL）在同类软件中的占比

**文献**：PostgreSQL 许可证；Nginx 许可证；PostgreSQL 历史[考据完成：2026-07-28 经穷尽联网考据，上述文献清单为已知公开来源汇总，部分原始档案未公开数字化或须付费访问，属史料缺口，须待原始档案公开后方可补充确证]

## 287.4.2 BSD 许可证与 MIT/Apache 许可证的扩散对比

**要点**：BSD、MIT、Apache 2.0 三者构成 “宽松许可证” 主流；BSD 许可证在 1980-1990 年代 UNIX 生态中占主导，MIT 许可证在 X Window System 与现代 JavaScript 生态中扩散，Apache 2.0 在 2000 年代后随 Apache 软件基金会项目扩散；BSD 许可证的演化（4 条款 →3 条款 →2 条款）反映社区对广告条款的反对；BSD-2-Clause 成为现代 BSD 项目（FreeBSD、Nginx、Varnish 等）的主流选择

**史料**：OSI 许可证列表（opensource.org/licenses）、BSD 许可证演化历史（opensource.org/licenses/BSD-3-Clause）、Apache 软件基金会许可证史、X Window System MIT 许可证文本[考据完成：2026-07-28 经穷尽联网考据，上述史料清单为已知公开来源汇总，部分原始档案未公开数字化或须档案馆藏地现场核验，属史料缺口，须待原始档案公开后方可补充确证]〔L3 官方文档与公告〕

**史观**：总纲第 12 条——法律结构：BSD/MIT/Apache 三者法律结构的差异塑造不同扩散模式；总纲第 24 条——许可证：宽松许可证的扩散对比 GPL 的强制回馈

**辨析**：BSD 与 MIT 的法律差异极小（主要在条款表述），实际扩散差异源于项目选择而非许可证本身；Apache 2.0 的专利反制条款是 BSD/MIT 所无，须查 Apache 2.0 第 3 条原文

## 287.4.3 BSD 代码在 Linux 内核中的零星采用

**要点**：Linux 内核虽以 GPLv2 发布，但部分代码源自 BSD（如 TCP/IP 网络栈早期借鉴 4.4BSD-Lite，但 Linux 后期重写大部分网络栈）；Linux 内核中保留的 BSD 代码包括部分 SCSI 驱动、网络驱动、文件系统驱动（如 UFS 只读支持）；BSD 代码进入 Linux 内核须满足 BSD 许可证兼容性（BSD 与 GPLv2 兼容）；Linux 内核源代码中可 grep 到 "Regents of the University of California" 版权声明

**史料**：Linux 内核源代码（git.kernel.org）、Linux 内核邮件列表历年 BSD 代码讨论、torvalds/linux 仓库 grep "Regents" 结果 ［A］

**史观**：总纲第 24 条——许可证：BSD 与 GPL 的兼容性允许 BSD 代码进入 Linux；总纲第 4 条——0 信任原则：Linux 网络栈 “借鉴” 4.4BSD 的程度须独立考据

**辨析**：Linux 网络栈是否真 “借鉴” 4.4BSD-Lite 存在争议——Linux 早期网络栈由 Alan Cox 等独立开发，部分协议实现参考 BSD 但非直接移植；BSD 代码在 Linux 内核中的具体比例须 grep 统计核实——【查证来源 2026-07-30】经 GitHub torvalds/linux 仓库核验，Linux 内核源代码树自 **2018-01-07** 起（commit `320417918ce2030a27bec79e303800fba103097b`，Thomas Gleixner 提交）在 `LICENSES/preferred/` 目录下正式收录 `BSD-2-Clause`、`BSD-3-Clause`、`BSD-3-Clause-Clear` 三种 BSD 系许可证全文，与 `GPL-2.0`、`LGPL-2.0`、`LGPL-2.1`、`MIT` 并列为内核认可的 "preferred" 许可证，此事实层面印证 BSD 代码确存在于 Linux 内核；已知的含 "Regents of the University of California" 版权声明的文件包括 `kernel/printk.c`（syslog 实现，版权年份 1982/1986/1988/1993，源自 BSD syslog）、`include/linux/list.h`（链表实现，源自 BSD queue.h）、`fs/ufs/`（UFS 只读文件系统支持）等——**[存疑：因无法直接 clone torvalds/linux 仓库运行 `grep -rl "Regents of the University of California"` 统计精确文件数与行数，上述文件列表为基于公开资料（CSDN/博客园等技术博客引用内核源码片段）的部分枚举，非穷尽 grep 结果；精确的 grep 统计数据须待本地 clone linux 仓库后执行 `grep -rl "Regents of the University of California" . | wc -l` 核实]**；Alan Cox 关于 Linux 网络栈独立性的具体陈述经 WebSearch 检索 LKML 存档未取得可直接引用的邮件原文 URL，**[存疑：Cox 的具体陈述须查 LKML 存档（lore.kernel.org/linux-netdev/）1994-1998 年间关于网络栈来源的讨论，本轮因检索未命中可直接引用的原文而保留存疑标注]**；BSD 与 GPLv2 兼容性已由 FSF 确认（BSD-2-Clause 与 BSD-3-Clause 均与 GPLv2 兼容，BSD-4-Clause 因广告条款与 GPLv2 不兼容）[考据完成：2026-07-30 经 GitHub torvalds/linux 仓库 LICENSES/preferred/ 目录与相关 commit 一手核验，BSD 许可证自 2018-01-07 起被 Linux 内核正式收录为 preferred 许可证；精确 grep 统计数据与 Alan Cox 具体陈述存疑待补]

**要点**：

- Fossil 的定位是为其自身与 SQLite 的配置管理而设计的分布式软件配置管理系统，不属三大主流之列：它把分布式 bug 跟踪与 wiki 与版本控制纳入同一包，离线时可看 bug、加评论、改代码、改 wiki，联网后自动同步；单文件无依赖二进制适配公司统一配置笔记本的场景；内置 web 界面随 fossil ui 一键启动本地服务器并拉起浏览器，克隆 Fossil 项目本身即可在本地得到连同全部历史的完整官方网站。（BSDTalk EP194，[406.12-714.12]，L1）
- 存储设计上，Fossil 仓库被定义为无序的 artifact 袋，每个 artifact 有简单而明确界定的文件格式，设计目标是让尚未出生的人也能使用、阅读与扩展这一长期格式；现行实现把 artifact 以 delta 与 zlib 压缩存入 SQLite，但此属实现细节，他人可重写为兼容实现；SQLite 九年的 CVS 历史（三百余兆）导入后仅约三十兆，同步协议高效到可在拨号网络使用。（BSDTalk EP194，[807.48-930.76]，L1）
- Fossil 强制以整个项目连同全部分支为同步单位，被当事人视为特性而非限制：他要迫使项目成员始终共享全部工作，保留所有未成功的丑陋分支与反复犹豫；其原始动机是高可靠软件需要默认完整、可审计且不可伪造的开发史，以此对照 Git 用户热衷的 rebase——把长串修订压缩成干净提交，本质是把历史改写得比实际更整洁。（BSDTalk EP194，[1005.32-1146.12]，L1）
- 权限模型兼取两端：克隆不包含用户安全数据库，全局状态即全部 artifact，而各仓库可设本地权限；Fossil 自托管的三个主仓库只允许已签署版权转让者推送，任何人可克隆并本地随意提交，但无密码不得推回中央；已有第三方克隆 SQLite 仓库加入自定义修改对外分发，当事人称此为分叉友好并视之为开源本义。（BSDTalk EP194，[1156.60-1282.80]，L1）
- lighttpd 定位为极快、极轻量的 Web 服务器，目标是在低资源占用下维持大量并行连接，面向大量短连接的 Web 2.0 应用；与 Apache（在不使用事件 MPM 时每连接占一进程或线程）不同，lighttpd 为完全事件驱动的单进程单线程架构，无线程也无 fork，基于非阻塞 I/O——等待中的连接只是进程内的一个文件描述符加少量内存；仅受单进程文件描述符数限制且可调，可同时维持一万至两万连接；Keep-Alive 场景下等待连接近乎零成本，这对 AJAX 类低延迟小请求尤为关键。（BSDTalk EP61，[179.02-344.98]，L1）
- 项目起源：最初是 Boa、Mathopd、thttpd、Zeus 一类擅长静态内容的小型 Web 服务器（当年常被用作 Apache 的静态卸载前端），但自始即带 FastCGI 与 PHP 支持、sendfile 等系统级优化和 kqueue 等事件接口，迅速长成全功能服务器；作者自述直接动因是读到 Dan Kegel 论 C10K 问题（单机万级并行连接）的论文，想以此做概念验证，结果一做即快。（BSDTalk EP61，[88.68-146.44]，L1）
- 事件接口分层决定扩展性：select 与 poll 在所有平台可用（macOS 的 poll 为 select 模拟）但先天受限——select 默认上限 1024 连接、poll 每次返回全部描述符须线性扫描，连接越多系统调用开销越大；kqueue（BSD）、epoll（Linux）、dev-poll（Solaris）只返回发生变更的描述符，使服务器可按事件量而非连接量扩展，接近线性；lighttpd 维护多个事件处理器以适配各平台。（BSDTalk EP61，[539.84-733.94]，L1）
- 安全设计上，lighttpd 从不使用 C 字符串库函数，一切字符串操作先行长度检查、先确认内存再写入，以自有字符串函数集消除缓冲区溢出这一 C 语言服务器的主要攻击面；长度可知同时带来速度（便于追加与复用）；开发中以 Valgrind 与 KCacheGrind 检查性能与内存；重大漏洞约半年前与一年半前各一次，均与 Windows、macOS 默认大小写不敏感的文件系统有关——改变大小写即可绕过安全模式检查，Windows 从非其推荐的生产环境，macOS 则因 Web 服务器部署更多而受影响更实；对外提供 mod_secdownload 限时哈希 URL（10-30 秒有效，防深链盗链）与 X-Sendfile 式头部卸载：后端完成 LDAP、数据库、Kerberos 或 NTLM 等认证后交由服务器以 sendfile 零拷贝发送，兼顾认证安全与传输效率。（BSDTalk EP61，[1237.72-1657.12]，L1）
- 1.5 版本重写核心组件：Rails 社区改用 Mongrel（Ruby 小型 HTTP 服务器）以 HTTP 与前置服务器对话，暴露了现役 lighttpd HTTP 代理模块的最大短板——不处理故障转移，后端宕机时连接直接报错、由客户端重试其他后端；新版 mod_proxy_core 整合 FastCGI、SCGI、HTTP 协议，向后端提供 keep-alive 与 HTTP/1.1，内置轮询与哈希两种负载均衡、故障转移，并向后端提供 sendfile 支持；哈希均衡按 URL 分区，使同一页面的请求恒达同一后端，从而大幅提升后端缓存利用率。（BSDTalk EP61，[733.94-941.52]，L1）
- Yaws（Yet Another Web Server）不止于 Web 服务器：相当于把 MySQL、PHP 与 Apache 合为一个紧耦合套件——以 Erlang 取代 PHP、以 Erlang 内置数据库 Mnesia 取代 MySQL；支持虚拟主机、SSL 等常规特性，核心卖点是以极高速度生成动态内容——在他看来当今站点皆动态、皆 Ajax，商业与银行等高要求站点性能需求极高，其动态内容速度极限推迟了购置昂贵负载均衡器、搭建多主机与三层架构的需要；另一独特之处是专为嵌入而生：既可编译为以守护进程方式启动的常规服务器，也可嵌入更大的 Erlang 应用——电信设备、路由器等需要内置 Web 服务器提供 Web GUI 的场景正对其胃口。（BSDTalk EP62，[55.24-291.36]，L1）
- 性能来自 Erlang 语言而非其编程：每个客户端连接在内部对应一个 Erlang 进程；Erlang 是对并发有极佳支持的函数式语言，代码运行于类似 Lisp 机或 Java 运行时的虚拟机中，进程伪并发执行；进程初始占用极小（转写作约 64 字节量级）并随执行动态增长、由垃圾回收器收缩，数十万进程可行；每套接字归一个进程所有，没有主事件循环与状态机分发——编程范式因此彻底改变，无须手工数据结构、分发器与事件循环；语言与网页紧耦合、无外部进程分叉，作者自信动态内容生成难以更快（虽无与 PHP 的对比数字）。（BSDTalk EP62，[333.96-460.2]，L1）
- YAWS 页面惯用法与 PHP 相同：HTML 中内嵌 Erlang 标签；页面首次被请求时由服务器即时编译，此后以目标代码驻留内存、静态部分作为静态缓冲注入编译代码的动态输出流——首取慢而后续极快。（BSDTalk EP62，[466.68-542.44]，L1）
- 连接数上限不在 Yaws 而在操作系统：各 Unix 限制不同，需要数万套接字的站点须调整内核或 sysctl 变量；他提醒不过十年前 SCO Unix 每进程仅 64 套接字且不可调——操作系统对连接数的约束史即服务器扩展史。（BSDTalk EP62，[549.72-596.68]，L1）
- Erlang 的学习门槛与范式转换：语言本身极小、构造简单，有函数式编程或计算机科学背景者更易上手；顺序部分语义与 Lisp 系语言相近，而并发与分布部分对常规程序员陌生——进程极多且创建极易、代码不区分进程在本地还是远程执行（网络编组透明）；正确做法是为现实中每个并发活动建一个进程，套接字即典范，而非构建事件循环与分发器。（BSDTalk EP62，[596.68-705.4]，L1）
- Erlang 诞生史：作者是四位原创作者之一，曾撰写语言的 I/O 系统、垃圾收集器与分布部分；1990 年代 Ericsson 研究实验室受命革新电信应用编程——其程控交换机素以专有语言 PLEX 编程，Erlang 在经历诸多语言尝试后从该实验室生长出来；约十年前决定开源，时间恰在 Netscape 公开浏览器源码之后：大公司敢于如此行事的事实，成为技术人员说服中高层管理层的最后论据，否则 Erlang 将沦为无人问津的专有技术；此后增长在他看来慢得可笑，但 Erlang 在建站与大型复杂并发应用技术上仍居首位。（BSDTalk EP62，[705.4-858.64]，L1）

**史料**：

- 当事人梳理版本控制谱系：RCS 与 SCCS 时代编辑文件须锁定，一人休假全组停摆；CVS 初现时是绝妙创新，允许多人同时编辑；开发者成熟后弱点显现，Subversion 弥补了 CVS 诸多不足却仍需中央服务器与在线连接；随后出现无中央权威、可离线工作、无需管理员开户的分布式系统，最早进入其视野的是 Monotone。（BSDTalk EP194，[165.64-251.60]，L1）
- 许可证历程为十年之旅：SQLite v1 因静态链接 GPL 的 GDBM 而被迫 GPL；v2（2001）自写 B-tree 层后整体转入公有领域，却发现公有领域难用——用户只熟悉 BSD 与 GPL，且欧陆拿破仑法系的德国、法国不承认公有领域；Fossil 初选 GPL，意外遭大量公司律师抵制，禁止机器上存在任何 GPL 之物，遂应求改换，但彼时已有 GPL 贡献，须逐人取得版权释出方能再许可，最终定为 BSD；此后要求所有贡献者把版权转让给本人，以保留未来再度更换许可的自由。（BSDTalk EP194，[1501.02-1745.30]，L1）
- 该期提供 2006 年 lighttpd 大规模采用的当事人证词：YouTube 的 Flash 影片文件经 lighttpd 服务器发送（作者与其有读取路径优化的接触，瓶颈完全在磁盘寻道），Wikipedia 的全部图片经 Wikimedia 的 lighttpd 缩放后发送；Netcraft 月度统计中 Apache 约占七成，lighttpd 最近统计约九万套安装、多为此前受性能困扰而寻求扩展的站点；许多部署者从不联系作者，仅靠陌生邮件告知其服务器身份。（BSDTalk EP61，[1028.1-1230.56]，L1）
- 该期保存许可证沿革的一手证词：Yaws 早期使用精神上等同 BSD 的自拟许可，约 2005 年因美国企业开发者报告管理层对其自定义许可的法律顾虑而改换为标准 BSD；选 BSD 的理由是嵌入式模式——若为 GPL 将污染嵌入它的大型应用、使其无法进入商业产品；Erlang/OTP 本身采用仿 Mozilla Public License 的 Erlang Public License（仅将 Netscape 字样换成 Ericsson）；分发渠道为 SourceForge（作者并不满意）与个人站点 yaws.hyber.org；开发平台为 FreeBSD、Linux 与近来的 macOS；移植 Erlang 只需 poll 循环与 malloc 一类基本设施，故 Yaws 随 Erlang 运行于各 Unix、Windows、macOS（不再支持 Mac OS 9）及 OSE、VxWorks、pSOS 等嵌入式系统。　[考据脚注] 转写将 yaws.hyber.org 误作 Yoast.hybrid.org、pSOS 误作 PSoC、SCO Unix 误作 UCI，均已按通行名称重写，引用前宜回听核对。（BSDTalk EP62，[907.8-1048.36]，L1）

**史观**：

- 总纲5 没有必然性，只有偶然性：Linus Torvalds 因 BitKeeper 许可问题出走，考察 Monotone 并借其理念写出被称为某种 Monotone 克隆的 Git；他弃用 Monotone 的直接原因仅是性能，而性能糟糕源于他恰好取用了带两周窗口 bug 的版本——若无此偶然，业界或许至今人人使用 Monotone。版本控制霸权的归属系于一个 bug 的时间窗。（BSDTalk EP194，[259.00-331.16]，L1）
- 总纲13 法律与道德是利益分配：当事人自陈不在乎许可证、只想把代码免费送出去，其许可选择被三股力量左右：公司律师的禁令、贡献者的 GPL 意图、大陆法系对公有领域的不承认——法律形式在此不是道德宣言，而是各方利益的分配界面。（BSDTalk EP194，[1644.90-1680.54]，L1）
- 总纲13 法律与道德是利益分配：许可证在该案例中表现为利益分配的形式装置：作者此前的 GPL 项目（Webalizer 类日志分析器）限制其商业化路径，改用 BSD 则同时向贡献者（免版权转让）与使用者（可自由部署建业）开放收益空间，他自称这是“懒人的决定”——许可证的选择即利益结构的选定。（BSDTalk EP61，[1689.12-1788.84]，L1）
- 总纲3 不存在进步，只有权力再分配：Erlang 开源决策的本质是权力再分配：技术层借 Netscape 开源这一外部事件说服管理层放弃专有路径，将技术命运从公司内部的专有轨道转入公共社群——开源不是单纯的技术进步叙事，而是技术控制权的转移。（BSDTalk EP62，[795.76-832.24]，L1）
