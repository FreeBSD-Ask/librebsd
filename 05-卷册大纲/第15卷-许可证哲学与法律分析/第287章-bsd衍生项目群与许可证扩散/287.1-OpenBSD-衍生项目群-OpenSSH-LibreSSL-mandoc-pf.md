# 287.1 OpenBSD 衍生项目群——OpenSSH、LibreSSL、mandoc、pf 等独立开源项目的孵化与全球扩散

## 287.1.1 OpenSSH 的诞生与全球采用

**要点**：OpenSSH 由 OpenBSD 项目于 1999 年 9 月 26 日从 Björn Grönvall 的 OSSH（其本身 fork 自 Tatu Ylönen 的 SSH 1.2.12 最后自由版本）import 入 OpenBSD 源代码树，1999 年 12 月 1 日随 OpenBSD 2.6 正式发布；创始团队为 Theo de Raadt（西奥·德·若特）、Niels Provos（尼尔斯·普罗沃斯）、Markus Friedl（马库斯·弗里德尔）、Bob Beck、Aaron Campbell、Dug Song；许可证为 BSD、ISC 与公共领域的混合；OpenSSH 此后被 Linux 发行版、macOS、Windows 10（1803 起 OpenSSH 客户端内置）、Solaris、AIX 等几乎所有现代操作系统采用，成为 SSH 协议事实标准实现；portable 版本由 Damien Miller（达米安·米勒） 等维护，独立于 OpenBSD 基础系统但同步演化

## 287.1.2 LibreSSL 从 OpenSSL fork 的工程史

**要点**：LibreSSL 由 OpenBSD 项目于 2014 年 4 月 Heartbleed 漏洞（CVE-2014-0160，2014 年 4 月 7 日公开）公开后启动 fork，由 Bob Beck 与 Theo de Raadt 主导；首个 portable 版本于 2014 年 7 月 11 日发布，2014 年 11 月 1 日随 OpenBSD 5.6 首次进入基础系统；Beck 自述 fork 真正诱因并非 Heartbleed 而是 OpenSSL 的 LIFO 内存分配器破坏了 Coverity 与 Valgrind 的可用性；fork 后首周内删除约 9 万行 C 代码，发现大量 20 年未维护的 FIPS 认证遗留代码（“abandonware”）；LibreSSL 后被 FreeBSD ports（2014 年 7 月 12 日加入 security/libressl）、Linux 发行版（Gentoo 等）、macOS 等采用

**史料**：threatpost.com/libressl-sticks-a-fork-in-openssl/105653（2014.4.23 Beck 访谈）、threatpost.com/first-version-of-libressl-debuts（2014.7.14）、openbsd.org/56.html（OpenBSD 5.6 release）、FreshPorts security/libressl 条目（Port Added: 2014-07-12）、libressl.org 官网、OpenBSD 源代码 src/lib/libssl、Beck 在 BSDCan 2014 演讲幻灯片 ［A］

**史观**：总纲第 4 条——0 信任原则：Beck 自述 fork 诱因须独立考据，不能仅因官方叙事即采信；总纲第 25 条——0 信任原则：FIPS 遗留代码问题需通过 OpenSSL 仓库核实

**辨析**：LibreSSL 的实际采用率远低于预期——OpenSSL 仍占主流，LibreSSL 主要在 OpenBSD 基础系统与少数 Linux 发行版中；fork 后 API 兼容性维护策略（Beck 称 “preserve API compatibility”）是否真实现需通过下游应用编译记录核实；“9 万行删除” 数字据 Beck 自述为 fork 首周内删除，需通过 OpenBSD CVS commit 历史核实具体时间分布；[考据完成：2026-07-30 三次联网核查补入 Beck 2014.4.23 Threatpost 访谈具体引文——访谈作者 Michael Mimoso，发布日期 2014-04-23 12:57 pm，URL `https://threatpost.com/libressl-sticks-a-fork-in-openssl/105653/`，原文引文如下：(1) "Bob Beck, an OpenBSD developer, told Threatpost via email that 90,000 lines of C code have already been deleted as the code has been converted slowly to modern C programming practices, including modern memory allocation practices and integer overflow avoidance, just to name two.“（90,000 行 C 代码已删除，转换为现代 C 编程实践）；(2) ”I‘d say we’ve probably already ‘improved’ it. For the time being we want to make sure that other than anything we find that is intrinsically dangerous, we want to preserve API compatibility so we don't break all the software out there that uses this.“（API 兼容性维护策略原话）；(3) ”Forking isn't something we take lightly, we know darn good and well it's a lot of work, however it had become painfully obvious in the past while that we would not be getting useful fixes from upstream“（fork 决策原话）；(4) ”For myself, and for Theo, I know it's been in the works seriously since we saw that allocator.“（fork 真正诱因为 LIFO 内存分配器，非 Heartbleed）；(5) ”The LibreSSL developers have found 20-year-old chunks of unmaintained code in OpenSSL, ‘abandonware,’ as Beck put it, code that was added for FIPS certification and never attended to again."（20 年未维护的 FIPS 认证遗留代码）；(6) “Important bugs sat in OpenSSL's tracker for four years—until we found them and fixed them in our tree.”（OpenSSL bug tracker 中重要 bug 滞留四年）；(7) "Most of the code doesn't use anything approaching best practices for modern C code. Lots of it will make your eyes bleed and roll backwards into your skull as your brain tries desperately not to see it."（OpenSSL 代码质量问题原话）；[存疑脚注] OpenBSD CVS commit 历史中“9 万行删除”的具体 commit hash 与时间三次复查未得——OpenBSD CVS 仓库 `https://cvsweb.openbsd.org/src/lib/libssl/` 可访问，但具体删除 90,000 行代码的 commit 序列须通过 CVS commit log 逐条核验，三次 WebFetch 抓取 cvsweb.openbsd.org 超时未能获取具体 commit hash，标注为存疑待后续 CVS 日志本地核验后补充确证]

## 287.1.3 pf 防火墙的跨项目移植

**要点**：pf（packet filter）由 Daniel Hartmeier（丹尼尔·哈特迈尔） 原创开发并由 OpenBSD 项目维护，首次出现在 OpenBSD 3.0（2001 年 12 月 1 日），作为 IPFilter（IPF）许可证争议后的替代品——IPF 作者 Darren Reed（达伦·里德） 的许可证条款引发 OpenBSD 法律审查后，OpenBSD 决定自研 pf，Hartmeier 提交初版并被 OpenBSD 纳入基础系统；pf 后被 FreeBSD（FreeBSD 5.3 起，2004 年 11 月 6 日）、NetBSD、Mac OS X（自 10.6 Snow Leopard 起 Apple 在 pf 基础上构建应用层防火墙）、QNX 等采用；pf 的状态检测、ALTQ 集成、语法设计［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］ **[存疑：经 2026-07-30 复核 McHardy 2009-03-18 nftables 首次发布公告与 nftables 官方 wiki，均未提及 pf 为设计来源，“pf 影响 nftables 设计” 叙事无 primary source 支持，应视为存疑推断，详见辨析字段]** 影响了 Linux nftables 的设计

**史料**：OpenBSD 3.0 release notes（openbsd.org/30.html）、Hartmeier 个人主页（benzedrine.ch/pf.html）、FreeBSD 5.3 release notes（2004-11-06）、Apple Mac OS X 10.6 Snow Leopard release notes、Reed-OpenBSD 许可证争议邮件列表存档、man.openbsd.org/pf.4 ［A］

**史观**：总纲第 12 条——法律结构：IPF 许可证争议直接催生 pf，是法律结构塑造技术路径的典型案例；总纲第 7 条——BSD 与 UNIX 谱系的连续性：pf 跨 BSD 项目与商业 OS 扩散

**辨析**：pf 是否真 “影响” 了 nftables 经 2026-07-30 联网考据确认为存疑——【查证来源】Patrick McHardy 2009-03-18 在 netfilter-devel 邮件列表发布的 nftables 首次发布公告（lore.kernel.org/all/49C078B6.4020603@trash.net/）全文未提及 pf、OpenBSD 或 BSD 防火墙为设计来源，公告明确称 nftables “written from scratch” 且 “intended to become a successor to iptables”，设计依据为 iptables 的局限性（代码重复、协议特定扩展、语法不一致等）而非 pf 的特性；nftables 官方 wiki “What is nftables?” 页（wiki.nftables.org）描述设计动机时同样未提 pf，仅称语法 “inspired by tcpdump” 而非 pf；nftables 最初于 2008 年第 6 届 Netfilter Workshop（巴黎）向 Netfilter 社区展示，该 Workshop 议程未公开提及 pf 影响；【交叉验证方法】McHardy 2009 首次发布公告（一手）与 nftables 官方 wiki 设计动机页（一手）双向印证 “nftables 设计来源为 iptables 局限性而非 pf” 的事实层面成立；Pablo Neira Ayuso 作为 netfilter 核心开发者的公开声明中未检索到承认 pf 为设计来源的表述；【存疑判定依据】“pf 影响 nftables 设计” 的叙事在 primary source 层面无证据支持——nftables 的 set lookup/dictionary/虚拟机等核心设计在 pf 中无对应物（pf 采用状态检测+规则链模型，nftables 采用通用数据表示+分类语言解释器模型，二者架构差异显著），故采信 “nftables 设计未受 pf 实质性影响，本节先前 'pf 语法设计影响了 Linux nftables 的设计’ 的叙事为过度推断，应标注为存疑并降低论证强度” 的判断；Apple 应用层防火墙（Application Firewall，10.5 Leopard 起独立组件）与底层 pf（10.6 Snow Leopard 起替换 ipfw）的关系须查 Apple 开发者文档区分；Hartmeier 在 pf 中的 “原创” 角色需通过 OpenBSD CVS commit 历史核实[考据完成：2026-07-30 经 lore.kernel.org 邮件列表存档与 wiki.nftables.org 一手核验，nftables 首次发布公告与官方 wiki 均未提及 pf 为设计来源，“pf 影响 nftables 设计” 叙事存疑]

- 总纲10 动手者创造历史：主持人转述的 2000 年 Salon 文章给出与英雄史观相反的判断：对 Bill Joy 的过度聚焦是一种圣徒传式叙事，遮蔽了更大的图景——“伯克利最重要的贡献不是软件本身，而是创造软件的方式”（1076.64-1104.68）——一个任何时刻不超过四人的核心小组，把不断扩张的远方志愿程序员网络协调成渐进发布、稳步改进的流水线。技术史的真正主角是协作结构的发明，而非站在台前的个人。（BSD Now EP142，[1045.86-1104.68]，L2）
- 总纲5 没有必然性，只有偶然性：Perlstein 走向 FreeBSD 开发者的每一步都系于偶然：恰好在 MS-DOS 时代自学汇编，恰好被同学讥讽而另寻出路，恰好学校采用 FreeBSD 作教学平台，恰好邮件列表给出令他折服的长篇答复。没有哪一环是历史必然，一个行动者的转向由一连串具体偶然事件串联而成。（BSD Now EP142，[1561.38-1617.20]，L1）

- 总纲5 没有必然性：DSA 的困境展示了技术标准如何被偶然条件锁死：SSH2 标准化时 RSA 尚在专利期，标准只能指定 DSA 为唯一强制签名算法并绑定 SHA-1 与 1024 位密钥，二十年后该强制项仅相当于 80 至 112 位对称安全、逼近国家级资源主动攻击的可行域，而大量只实现规范最低要求的小型路由器设备使迁移摩擦集中爆发于用户侧——签名算法的路径由专利到期时机这类偶然事件塑造，而非由技术优越性决定。（BSD Now EP104，[1314.46-1419.06]，L1）
- 总纲22 知识注定过时：Miller 以“墙上的字写着”形容 MD5 的命运：HMAC 构造因有密钥参与而使 MD5 在其中仍属强健，但先于加密库的演化主动弃用，是为将来不被库的变更倒逼；配合 ChaCha20 取代 AES 默认地位、以单元测试与 AFL 模糊测试应对自称“遗留噩梦”的代码基，可见安全工程的时间观——任何默认配置都是暂时的知识快照，维护者的职责在于为过时预留退路，而非宣称某一配置的永恒正确。（BSD Now EP104，[1863.12-1939.96]，L1）
- 总纲10 动手者创造历史：Spil 反复自陈自己不是程序员、只是在 ports 树里修修补补（1700.57-1713.22），既无 commit 权也靠四十余个 PR 等待合并；然而整个 FreeBSD 生态向 LibreSSL 的迁移正是由这类运维者与修补者的具体劳动累积推进，而非出自架构师的宏大设计——动手者的琐碎修补构成生态级变革的真实载体。（BSD Now EP82，[1700.57-1713.22]，L1）

- 总纲14 苦难不值得被提倡：Poul-Henning Kamp（转写作 Paul Henningkamp）2004 年众筹时因收款无上限而陷入每周八十小时、自感亏欠出资人的过劳，2010 年改为发票限流的 Varnish Moral License 模式；主持人补充 FreeBSD 基金会资助的正是 UEFI 引导代码等无人愿做却必需的无名工作。两例共同显示：维护者的自我消耗不被浪漫化，可持续的维护史由把劳动制度化的安排而非苦行支撑。（BSD Now EP43，[773.82-824.68]，L2）

- 总纲3 不存在进步，只有权力再分配：文档格式语言的历史并非线性进步史：五十年来许多人试图发明优于 mdoc 的语言而大多失败，重型替代方案屡屡被证明难以为继，最终承担手册格式化的反倒是尊重既有语义传统的轻量实现；groff 到 mandoc 的更替是格式化实现权与维护权的转移，而非语言本身的淘汰更迭。（BSDTalk EP243，[468.58-524.04]，L1）
- 总纲9 经验优先：mandoc 的功能取舍由真实手册语料驱动而非语言理论：只要现实中的手册用了某个 groff 特性，格式化器就必须处理它，哪怕该特性与手册无关；这种以既有文本经验为准绳、而非按理想模型裁剪输入的工程立场，是 BSD 文档工具数十年延续的底层方法。（BSDTalk EP243，[617.94-684.34]，L1）

**辨析**：

- Perlstein 对 FreeBSD 上手体验提出一组可检验的批评：pkg install Django 直接报无包，而真实包名是 py27-django 这类带版本前缀的命名；学会 Subversion 与 Phabricator 的技能难以外溢到 Git/GitHub 主流生态；仓库过大令新手克隆即卡壳。他主张举办“反向安装马拉松”——不给新手帮助，只记录他们在何处卡住——甚至公开抛出为项目改名的争议建议（3051.12-3136.92），理由是连大会讲者与他的母亲都念错 FreeBSD。这些均为当事人单一来源立场，尚待社区实践检验。（BSD Now EP142，[2686.14-2922.74]，L1）
- NetBSD 引入 NVMe 支持取 OpenBSD 代码而非 FreeBSD 实现，后者系 Intel 直接贡献；主持人归因于 OpenBSD 本为 NetBSD 的 fork、设备模型与内核更接近故移植 diff 更小，并以同一 NVMe 设备在传统盘模拟接口下五六百兆与 NVMe 模式读 3800 兆、写 1700 兆每秒的性能差，及协议允许 65536 并发而当前设备 63 并发的队列细节佐证技术跃迁。　[存疑脚注]移植路径归因为主持人单源推断（原话以 I imagine 引导），未见 NetBSD 移植者自述佐证；性能数字为主持人借测试集群设备的一手自述（BSD Now EP141，[3607.47-3631.34]，L4）
- Tarsnap 1.0.36 修复 libarchive 一字节堆溢出（字符串 null 终止符计数错误）后，Colin Percival 的悬赏对象不是找新漏洞而是利用已知漏洞——2015 年底前第一位可信演示严重利用者获 1000 美元，Starfighter 创始人随即加倍至 2000 美元；这种把 bounty 从发现转向利用路径确认的做法，将“可利用性尚不确证”公开化并以经济激励求解，显示加密备份服务商对数据安全的自我施压式治理，与常规漏洞悬赏形成方法论差异。　[存疑脚注] 转写将 Thomas Ptacek 记为 Thomas Patak，demonology.net 与 Starfighter 拼写语义可辨但待核；悬赏金额与截止年份据主持人转述，未见原文直接核验（BSD Now EP104，[3999.24-4129.92]，L2）
- FreeBSD 10.2 的变更组合指向发行策略转向：新装系统默认采用季度二进制包集，以放弃滚动更新换取主版本稳定与纯安全补丁；Linux 兼容层基座由 Fedora Core 换为 CentOS 6（64 位支持未及赶上）；growfs 随 first boot 脚本默认化，使 SD 卡与虚拟机镜像首启自动扩容。讲解者兼具 PC-BSD 相关项目当事人身份，将其解读为面向 Linux 背景迁移者与服务器用户的可用性经营，而非单纯的技术升级。（BSD Now EP104，[452.92-560.22]，L2）
- iXsystems 数年试水官方 PC-BSD/FreeBSD 笔记本失败的结构性原因由当事人自述：厂商不承诺特定型号的生产一致性，除非万台起订；压货仓储成本高企而笔记本约五个月即过时；零部件随机替换（如 Wi-Fi 芯片）即足以摧毁兼容性认证。实测兼容良好的 Lenovo 老款（X230/T430/T530）只是无承诺的经验值，Broadwell 世代的 X1 Carbon 仍有障碍，尚在众筹的开放硬件笔记本被视作可能的替代路径，“官方笔记本”因此悬置于市场结构之外。（BSD Now EP104，[4550.56-4735.40]，L1）
- LibreSSL 与 OpenSSL 的安全对比数字存在口径风险：Spil 自报其个人汇总的公告计数为 OpenSSL 三十五项对 LibreSSL 十九项（2676.30-2680.38）并已载入 Wikipedia（2654.60-2661.94）；其将 LibreSSL 随机数问题评 medium 遭 Bob Beck 异议，Spil 亦自陈为免显得偏袒 LibreSSL 而将 OpenSSL 同类问题同降为 low（2714.42-2741.42）——评级带有人为对称校准，两组数字只宜作叙事线索而非两库安全性的计量结论。　[存疑脚注] 计数（35/19）与涉事版本号均出自转写且系当事人单方汇总，转写处 210 or 211、212 0 0 等存在明显语音失真，须以官方公告与 bug 追踪原件复核后方可引用（BSD Now EP82，[2676.30-2744.68]，L1）
- Pipecut 与 UNIX 哲学的紧张在演讲现场即被点破：Maxwell 转述 Jordan Hubbard 评议“你在构建一个把 Unix 里所有事都做了的工具”（2024.86-2030.24），并承认若要理解全部命令则项目永无完工之日；其折中是 black box 机制——单引号包裹的命令以 exec 原样执行，工具只对其输出作弱假设。对“每程序只做一件事并做好”的偏离与守成，构成对该哲学一次具体的当代检讨。（BSD Now EP73，[2015.46-2043.30]，L2）
- LibreSSL 替代 FreeBSD base 系统 OpenSSL 在 2015 年初仍是未竟之问：base 更新受制于测试与发布流程而滞后于 ports，committers 已开始记录以 make.conf 变量改用 ports OpenSSL 并试验 LibreSSL portable 的过程，OPNsense 团队亦透露考虑在 ports 与 base 双线切换；主持人提醒“不愿看到他们在未权衡全部影响前就切换”（1084.02-1088.02），且部分 Python ports 的不兼容标记属陈年遗留而非实际依赖。（BSD Now EP73，[943.92-1090.34]，L2）
- 主持人转述 Tor 中继平台分布统计（Linux 近 6000、Windows 约 1600、FreeBSD 173、OpenBSD 44、NetBSD 7、DragonFly BSD 仅 1），并以 Verisign 按 Linux、FreeBSD、Solaris 三分部署、OpenSSL 单点缺陷波及全网、Linux 伪随机数缺陷致 Tor 部分节点失效为例，主张平台多元是对冲系统性风险的工程策略；该论证与本期 LibreSSL 背景互为呼应　[存疑脚注] 节点统计数字仅经主持人转述且未附原始出处，属单一来源线索，待 tor-relays 邮件列表原始数据核验（BSD Now EP63，[928.52-1024.56]，L4）
- 三处专名与归属在转写中失真而须核验：其一，Espie 转述原包工具作者自评“周末写成的好用的垃圾”时自称记不清是否为 PHK，作者归属与措辞均待 pkg_install 历史与邮件列表原文印证；其二，构建机所在“Fios basement”疑为人名误听（OpenBSD 包构建长期由 Landry Breuil 维护）；其三，影响 Java 的“PCI DS”应为 PCID（Process Context Identifier），具体 errata 编号待查 FreeBSD 公告档。　[存疑脚注] PHK 归属、Fios basement 人名、PCID errata 编号三处均系转写失真或记忆性转述，须以邮件列表原文与 FreeBSD Errata Notices 核验后方可引用（BSD Now EP43，[1955.80-1988.06]，L4）
- LibreSSL 分叉初期的技术辨析：OpenSSL 被评述为兼具最好与最糟的 SSL/TLS 库——加密原语尚可用而外围实现与协议处理腐烂；LibreSSL 以可直接替换 OpenSSL 为目标而被迫继承恶劣 API；向 Linux 与 FreeBSD 的早期移植尝试被指存在把 explicit_bzero 简单别名到常规清零函数、致使密钥清零被编译器优化掉的隐患，移植须区分“能跑起来”与“正确地工作”（4158.20-4162.08），该讨论呼应 Bob Beck 关于 LibreSSL 头三十天的演讲（BSD Now EP38，[4086.40-4199.42]，L2）
- Schwarze 转述其与 Eric Raymond 交谈、Raymond 又与 Richard Stallman 交谈的结果，称两人同意弃用 GNU info 并以其他方案替代，而 Stallman 与 Raymond 属意的 AsciiDoc/DocBook 路线被 Schwarze 评为工具链沉重、未必更易用；此说经过两级转述，RMS 的真实立场须以 FSF 原始文献核证，且许多替代尝试皆已失败的判断亦属其个人评断。　[存疑脚注] GNU info 弃用共识系经 Raymond 转述的二手信息，未经 Stallman 本人文本证实（BSDTalk EP243，[447.54-518.64]，L2）
