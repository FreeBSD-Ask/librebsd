# 1.5.22 Spectre/Meltdown 与 MDS 硬件安全响应——6.x 周期 CPU 漏洞爆发期

**要点**：6.x 周期是 CPU 侧信道漏洞集中爆发期，OpenBSD 的响应体现“预防性禁用—快速跟进—自主实现缓解”三阶段工程态度——**预防性禁用（原说已证伪）**：6.0 Release Notes 检索无默认禁用超线程表述，SMT 默认禁用（`hw.smt`）实为 6.4 引入、系 Spectre/Meltdown 披露后响应〔本文件行 133 复查段已证伪“6.0 早于披露 16 个月”旧说，此处为回写订正；de Raadt 的批评言论史实另计〕；**快速跟进**：CVE-2017-5715（Spectre v2）由 kettenis 于 **2018 年 1 月 17 日** 提交 `d855ec95cfe6` 修复（分支预测器目标注入刷新），CVE-2018-3639（Spectre v4）由 kettenis 于 **2018 年 5 月 23 日** 提交 `2d5eadd64df9` 简化 CVE-2017-5715 workaround 代码时一并处理；**自主实现缓解**：MDS（Microarchitectural Data Sampling）由 guenther 于 **2019 年 5 月 17 日** 提交 `a0dcb1783e6f` 修复（使用 VERW 指令），6.4 errata 018_mds.patch（**2019 年 5 月 29 日**）与 021_swapgs.patch（**2019 年 8 月 9 日**，SWAPGS 漏洞）同步发布；此外 mlarkin 于 **2018 年 1 月 7 日** 提交 `ca88a4fb6ab1` 移除 Intel CPU 的 PG_G 全局页映射，guenther 于 **2018 年 7 月 12 日** 提交 `1fc8fad1ef00` 重组 Meltdown 入口与出口蹦床——5 条无 CVE 编号的安全修复 commit 中有 4 条与 CPU 漏洞相关，反映 6.x 周期硬件安全响应的密集程度

**史料**：**openbsd.duckdb** `commits` 表 openbsd-src 仓库 6.x 周期 CPU 安全相关 commit 查询：

  ```sql
  SELECT commit_hash, author_date, author_name, message_subject
  FROM commits
  WHERE repo_name='openbsd-src'
    AND author_date>=‘2016-09-01’
    AND author_date<‘2019-10-01’
    AND (message_subject LIKE ‘%spectre%’ OR message_subject LIKE ‘%meltdown%’
         OR message_subject LIKE ‘%MDS%’ OR message_subject LIKE ‘%VERW%’
         OR message_subject LIKE ‘%PG_G%’ OR message_subject LIKE ‘%branch predictor%’
         OR message_subject LIKE ‘%cr3%’)
  ORDER BY author_date ASC
  ```

**史观**：专题语（不设总纲条号）——硬件与软件辩证（原挂总纲第 7 条系自创名目，删条号）：6.x 周期 CPU 漏洞爆发是“硬件设计缺陷由软件承担责任”工程哲学的集中显现——Spectre/Meltdown/MDS 本质是 Intel CPU 微架构设计缺陷，但操作系统须通过软件缓解（分支预测器刷新、VERW 指令、TLB 双次失效、内核页表隔离）承担防护责任；OpenBSD 6.0 预防性禁用超线程早于 Spectre 披露 16 个月，这一“先知性”决策源于 OpenBSD 对 CPU 微架构共享资源侧信道风险的长期认知——de Raadt 在 2016 年即认为超线程共享执行资源是不安全的；OpenBSD 对 CPU 漏洞的“自主实现缓解”态度（不等待 Linux 内核 commit，自行编写缓解代码）与其拒绝 binary blob 的许可证哲学一致——以“硬件支持须自主可控为可信来源”为预设

**辨析**：**须精确说明 6.0 禁用超线程与 Spectre 的关系**：6.0 禁用超线程（2016-09）早于 Spectre/Meltdown 披露（2018-01），但超线程共享资源的侧信道风险在 2016 年已被 OpenBSD 团队认知——禁用决策是预防性的而非响应性的；Spectre/Meltdown 披露后 OpenBSD 的响应（2018-01 起）是针对分支预测器与推测执行的特定缓解，与超线程禁用是不同层面的防护；**CVE-2017-5715 修复的时序**：kettenis 的 `d855ec95cfe6`（2018-01-17）是 Spectre v2 披露（2018-01-03）后 14 天的快速跟进，反映 OpenBSD 安全响应的敏捷性；jsg 于 **2019 年 2 月 21 日** 提交 `218a2c1fee50` 确认 Cortex A76 不受 Spectre v2 影响——这一后续 commit 体现 OpenBSD 对缓解范围的精确评估，避免过度缓解影响性能；**与 FreeBSD/Linux 对比**：Linux 内核对 Spectre/Meltdown 的缓解涉及 IBRS/IBPB/STIBP 等多种微码依赖机制，复杂度高且性能开销大；OpenBSD 选择更简洁的分支预测器刷新路径，性能开销较低但覆盖范围可能不如 Linux 全面 ；**【2026-07-30 三次复查·SMT 默认禁用版本与 BSDCan 2018 演讲考据·7z 条目】** 经 WebFetch OpenBSD 6.4 Release Notes（**<https://www.openbsd.org/64.html>**）§“What's New” 一手核验，原文 "Because Simultaneous MultiThreading (SMT) uses core resources in a shared and unsafe manner, it is now disabled by default. It can be enabled with the new `hw.smt` **sysctl(2)** variable."——SMT 默认禁用实为 OpenBSD 6.4（2018-10-18 发布），由 `hw.smt` **sysctl(2)** 控制，6.4 同期引入 Retpoline（Spectre v2 缓解）、SpectreRSB 缓解、Meltdown i386 缓解三项硬件安全机制；经 WebFetch OpenBSD 6.0 Release Notes（**<https://www.openbsd.org/60.html>**）全文 334 行 grep “SMT|hyper|Spectre|Meltdown|speculation|threading” 检索，6.0 Release Notes 完全未提及 SMT/超线程/Spectre/Meltdown/speculation——证实 6.0（2016-09-01）未引入 SMT 默认禁用；〔存疑：原引“第88B章 88.10.1”全库无对应，交叉引用悬空〕“OpenBSD 6.0（2016-09-01 发布）默认禁用 Intel CPU 的超线程（Hyper-Threading）”与“这一决策早于 2018 年 Spectre/Meltdown 漏洞披露”两句表述错误，SMT 默认禁用实为 6.4（2018-10-18）且恰是 Spectre/Meltdown 披露（2018-01-03）后的响应措施，并非“早于”披露，须予更正；**de Raadt 2018 BSDCan 演讲考据**：经 WebFetch OpenBSD Events and Papers 页面（**<https://www.openbsd.org/events.html>**）§“Past events → 2018 → BSDCan 2018” 一手核验，BSDCan 2018（2018-06-06 至 06-09，Ottawa, Canada）Theo de Raadt（西奥·德·若特） 演讲 “Speculation about Intel Speculation”，slides PDF 链接 **<https://www.openbsd.org/papers/speculation2018.pdf>**；经 WebFetch 该 slides PDF 一手核验内容，slides 文本含 "Past embargos / Invitation to Embargo?
