## 74.9.5 被疏远贡献者的反批评——OpenBSD 阵营的回应（反批评层）

  **要点**：OpenBSD 阵营对 “被疏远贡献者” 叙事的回应集中于三点——其一，部分被疏远贡献者的离开是个人选择而非被驱逐，OpenBSD 不强制贡献者留存，离开是开源社区的常态流动；其二，部分被拒绝的补丁确实存在质量问题，OpenBSD 的代码审计标准高于 BSD/Linux 主流项目，被拒绝不等于被排斥；其三，被疏远贡献者叙事常被外部观察者放大，忽视了 OpenBSD 内部贡献者流动的正常性——OpenBSD 在 1995-2026 年间累计 403 名贡献者（openbsd.duckdb openbsd-src contributors 表），贡献者流动是项目演进的正常组成
  
**史料**：de Raadt 关于被疏远贡献者的公开声明、OpenBSD 核心开发者关于贡献者流动的访谈录、OpenBSD 邮件列表中被拒绝补丁的具体案例；openbsd.duckdb 数据库证据——openbsd-src contributors 表共 403 名贡献者，邮箱域 100% 为 `openbsd.org` ［A］
  
**史观**：本体论上各方平等：被疏远贡献者与核心开发者在叙事中地位相等，需对称呈现；0 信任原则：被疏远贡献者叙事须考据验证，不得因单一来源即采信
  
**辨析**：反批评的合理性在不同叙事中评估不一——部分视为有效辩护，部分视为合理化；需对照 OpenBSD 官方声明与被疏远贡献者自述交叉验证；【0 信任原则·“个人选择” 叙事的辨析】“个人选择离开” 与 “被环境排斥而离开” 的边界难以厘清——贡献者在持续被拒绝后 “选择” 离开实为被结构性排斥，须对照邮件列表时序与贡献者自述核实；【0 信任原则·贡献者基数的解读】403 名贡献者反映 OpenBSD 项目的开放性，但贡献者基数不等于核心决策圈规模——核心决策圈（hackathon 邀请名单、commit bit 持有者）远小于 403 人，须区分 “贡献者” 与 “决策者”
  
**文献**：de Raadt 公开声明；OpenBSD 核心开发者访谈录；OpenBSD 邮件列表存档；openbsd.duckdb openbsd-src contributors 表 ［A］

## 74.9.6 被疏远贡献者的再批评——对反批评的再回应（再回应层）

  **要点**：对 OpenBSD 阵营反批评的再回应集中于三点——其一，“个人选择” 叙事忽视了结构性压力，贡献者在持续被拒绝或被 de Raadt 公开羞辱（如 “this is stupid” 式回复）后 “选择” 离开，实为被结构性排斥而非自由选择；其二，“补丁质量问题” 论证忽视了质量标准的主观性——de Raadt 的审美偏好（如 KNF 代码风格、API 简洁性要求）常以 “质量” 名义行使，部分被拒绝补丁在技术正确性上无缺陷但不符合 de Raadt 的设计哲学；其三，被疏远贡献者叙事的 “放大” 指控本身可能是 OpenBSD 阵营对批评的回避——“外部观察者放大” 的指控忽视了被疏远贡献者本人自述的存在，将批评者定性为 “外部” 本身就是排斥性话语
  
**史料**：被疏远贡献者关于结构性压力的自述、OpenBSD 邮件列表中补丁被拒绝的具体案例与时序（含 de Raadt 的回复原文）、社区治理研究中关于结构性排斥的文献、OpenBSD KNF 代码风格文档
  
**史观**：解释学循环：被疏远贡献者叙事的评估受前理解差异制约——OpenBSD 阵营以 “个人选择” 为前理解，批评者以 “结构性排斥” 为前理解，二者难以通约；文化即形式主义：de Raadt 的言辞文化（“this is stupid” 等）在形式主义化过程中被固化为排斥机制
  
**辨析**：考据过程留痕——【查证来源】被疏远贡献者结构性排斥论证的关键证据基于 OpenBSD misc@、tech@ 邮件列表原始存档（marc.info 与 OpenBSD 官方邮件列表归档）中补丁被拒绝的具体时序与 de Raadt 的回复原文；OpenBSD KNF 代码风格文档（style.styles(9) 手册页）为质量标准主观性论证的对照基础；openbsd.duckdb openbsd-src 仓库 contributors 表（403 名贡献者）为贡献者基数证据；OpenBSD security.html 经 <https://www.openbsd.org/security.html> 一手核验，页面明确记载 "Our security auditing team typically has between six and twelve members"，确认代码审计团队规模为 6-12 人，远小于 403 名贡献者基数——核心决策圈与贡献者基数的差距是结构性排斥的量化证据；【交叉验证方法】被疏远贡献者自述（当事人叙事）与邮件列表原始记录（技术记录）与 commit message 中 “ok” 行（审核者署名）三方互证，区分 “补丁被拒绝” 与 “补丁被推迟” 两种情形——前者是结构性排斥的强证据，后者可能仅反映审核流程延迟；“结构性排斥” 论证须提供可证伪的证据（如补丁被拒绝的具体时序、de Raadt 的具体回复原文、贡献者离开的时序与拒绝时序的关联），否则易沦为不可证伪的总体性指控；“质量标准主观性” 论证须列举具体被拒绝补丁案例（如补丁内容、拒绝理由、技术评估），不得以 “可能存在” 模糊表述；【存疑判定依据】将批评者定性为 “外部观察者” 本身是排斥性话语，须辨析批评者是否为前 OpenBSD 贡献者——若是前贡献者，则 “外部” 定性不成立，OpenBSD 阵营的 “外部放大” 指控本身可能是回避批评的形式主义话语；0 信任原则提示：被疏远贡献者自述存在自利偏差与记忆偏差风险，当事人可能在离开后重构 “被排斥” 叙事以合理化个人选择；多源交叉验证不可靠性规则提示：多个被疏远贡献者在 “排斥感” 叙述上的一致性可能源于共同立场而非独立验证，史家须辨析其是否为对同一文化氛围的独立观察；OpenBSD KNF 代码风格本身是工程标准而非纯审美偏好——C 代码格式化、命名约定、错误处理风格等 KNF 规范有客观工程基础，“质量主观性” 论证须区分 “审美偏好” 与 “工程标准” 两类拒绝理由，不得将所有 KNF 相关拒绝归为审美偏好
  
**文献**：被疏远贡献者自述；OpenBSD 邮件列表存档（misc@、tech@ 中补丁被拒绝案例）；OpenBSD KNF 代码风格文档；社区治理研究文献 ［A］

## 74.9.7 被疏远贡献者的辩证合图（合图层）

  **要点**：被疏远贡献者的辩证合图——被疏远贡献者既有真实的质量不达标案例（反批评层）也有结构性排斥的受害者（批评层与再批评层），二者并非非此即彼；OpenBSD 的精英主义在特定规模（核心开发者约数十人）与特定目标（安全至上代码审计）下具有工程质量保障功能，但这一功能以部分贡献者的疏远为代价——精英主义的 “筛选” 与 “排斥” 是同一机制的不同命名；合图不寻求 “折中” 而寻求揭示精英主义的双重效应——它既是 OpenBSD 安全文化的工程基础（保证代码审计的高标准一致性）也是其人才流失的结构性根源（排斥潜在贡献者与多样性视角）；本体论上，被疏远贡献者与核心开发者在 OpenBSD 安全文化中的贡献地位相等——被疏远贡献者的边缘贡献（如被拒绝但技术正确的补丁、离开后的反思）亦是 OpenBSD 历史的组成部分，不应被排除在叙事之外
  
**史料**：被疏远贡献者案例综合研究、OpenBSD 贡献者流动统计（bsd_commits.duckdb contributors 表）、BSD 三项目（OpenBSD/FreeBSD/NetBSD）贡献者保留率对比、被疏远贡献者与核心开发者的对照访谈录 〔L1 代码/L4 事后叙述/L5 二手研究〕
  
**史观**：本体论上各方平等：被疏远贡献者与核心开发者在 OpenBSD 安全文化中的贡献在本体论上地位相等；动手者创造历史：被疏远贡献者的边缘贡献亦是 OpenBSD 历史的组成部分；解释学循环：被疏远贡献者叙事的评估受前理解差异制约，合图不寻求消除差异而寻求呈现差异
  
**辨析**：考据过程留痕——【查证来源】合图层的关键证据基于 OpenBSD security.html（<https://www.openbsd.org/security.html>，"Our security auditing team typically has between six and twelve members " 经一手核验）的代码审计团队规模、openbsd.duckdb openbsd-src contributors 表（403 名贡献者，deraadt 累计 27,181 commits）的量化证据、OpenBSD goals.html（“ Focus on being developer-oriented in all senses ”）的精英主义定位、OpenBSD KNF 代码风格文档（style.styles(9) 手册页）的质量标准定义；【交叉验证方法】精英主义的“ 质量保障 ”效应与“ 人才排斥 ”效应须以同一组 commit 历史证据同时呈现——openbsd.duckdb openbsd-src contributors 表中核心开发者（deraadt、Brauer、Beck、Friedl 等）的 commit 占比与边缘贡献者的 commit 占比对照，可量化呈现“ 核心圈 ”与“ 边缘圈 ”的工程贡献差距；被疏远贡献者案例与 OpenBSD 官方 errata 历年记录交叉验证，确认被拒绝补丁中是否存在后来被官方 errata 修复的同类问题——若存在，则“ 质量不达标 ”论证不成立；BSD 三项目（OpenBSD/FreeBSD/NetBSD）贡献者保留率对比须以三项目 contributors 表对照核验，OpenBSD 的精英主义是否导致更低的贡献者保留率须以量化数据而非主观印象判断；【存疑判定依据】合图并非辩证链的终结，随新被疏远贡献者自述的出现须重新展开；合图不寻求“ 折中 ”而寻求揭示精英主义的双重效应——“ 质量保障 ”与“ 人才排斥 ”是同一机制的共生效应，不可分割；“ 各打五十大板 ”的折中主义将精英主义的双重效应割裂为可分别评估的独立维度，违反结构性双重效应的本体；“ 质量 ”标准本身的结构性权力——谁定义质量（de Raadt 与核心开发者）、谁执行质量（代码审计团队 6-12 人）、谁被质量排斥（被疏远贡献者），本身就是权力行使；0 信任原则提示：合图层的史观审视本身嵌入项目统摄史观的前理解（总纲第 8 条本体论平等与第 19 条解释学循环），史家须自觉呈现这一前理解而非伪装中立；被疏远贡献者的边缘贡献（如被拒绝但技术正确的补丁、离开后的反思）在本体论上与核心开发者的贡献地位相等，但本体论平等不豁免考据义务——被拒绝补丁的“ 技术正确性 ” 仍须以源码 diff 与 errata 历史交叉验证，不得以本体论平等预先判定

**要点**：

- Suleen Rapin 从早期 Linux 与 PC-BSD 起步，工作中以 FreeBSD 替换 Linux 服务器，后转向 OpenBSD，因提交 ports 更新补丁而被邀请加入团队。（BSD Now EP435，[138.4-317.56]，L1）
- 她发起 OpenBSD Webzine，意图以面向非技术读者的月刊形式传播 OpenBSD 新闻、技巧与开发者访谈。（BSD Now EP435，[1434.94-1549.12]，L1）
- 其“旧电脑挑战”以 PowerPC 苹果笔记本运行 OpenBSD，并借助 Charlene Wendling 对 PowerPC 软件包的长期维护，展示 OpenBSD 对旧硬件的兼容。（BSD Now EP435，[530.8-929.72]，L1）
- SpamD 是一个小型邮件延迟守护进程：对 SMTP 连接或以 450/451 应答令对方稍后重试，或经调整 PF 表放行；兼具 tarpitting 与灰名单两类用途。其设计目标之一是与 Theo 商定确保在一台 SPARCstation IPC 上过滤一个大网络——守护进程不 fork，而是一个读大量套接字、跟踪全部连接状态并与 PF 通话的状态机；对邮件内容不做任何判断（不做正文统计词频分析），只依据 SMTP 连接本身的性质——是否符合标准、是否有规避反垃圾措施的迹象——作判断，故可跑在内存极小的机器上。在阿尔伯塔大学约八万个账户的中央邮件环境里，受访者把 SpamD 放在 Exchange 服务器之前，配合较激进的灰名单，五封 SMTP 消息约四封被挡下、仅一封进入实际处理，显著减轻主邮件处理器负载。（BSDTalk EP68，[77.8-496.0]，L1）
- 运行观察驱动默认行为：SpamD 初期对每个连接前 10 秒以极低速应答后恢复正常，受访者观察日志发现大量连接在三秒即断——垃圾邮件软件以此探测 tarpitting——遂把 10 秒初始延迟设为默认且不设旋钮；对发件方还可启用把 TCP 窗口压到极小、令其分片重传的“残忍”选项以考验对方 TCP 栈（代价是带宽，默认关闭）；对 SMTP auth 场景建议不用 25 端口提交，而以 465 的 SMTPS 与 587 的 mail submission 端口加 SSL 认证解决，必要时可用 PF 重定向规则整网豁免；对早期灰名单担心的出站邮件服务器地址池问题，其经验是一般不构成障碍——可预置 graylisting.org 公布的大站白名单，小池子重试终会通过，出入站共用地址会因 SpamD 观察外发而逐步白名单化，大型站点约两个月才需一次人工干预；相较之下 Sendmail Milter 负载高且按发件人-收件人-IP 三元组粒度过激，不适合大学站点，SpamD 以整 IP 白名单加进出双向观察更为合用。（BSDTalk EP68，[252.24-496.0]，L1）
- greytrapping 机制与轶事：把站点内已公开且弃用的邮件地址设为陷阱，凡向陷阱地址发信的机器即被阻塞 24 小时并遭低速应答，纵使一次投递百封也全数不通；受访者的陷阱名单甚至包括其历年写进软件文档的示例假地址。其举的 bigbutts@obtuse.com 一例成为蠕虫式扩散的活教材：文章发表前先布入陷阱，数日内即有垃圾邮件命中；数月后统计脚本发现命中暴涨，用 Google 一查，某 BSD 期刊的 OpenBSD 文章被色情站点爬虫抓取并在隐藏标签中复制全文，垃圾邮件发送者再爬色情站点把地址再次拾取——清理者与滥用者的食物链在陷阱地址上叠印。（BSDTalk EP68，[673.06-895.48]，L1）
- 社区体验与多重贡献：受访者形容 OpenBSD 社区是一群高强度但自得其乐的人——hackathon 通宵、技术讨论时大喊大叫上蹿下跳，留下来是因为“有趣且对我们有用”；其本人自认什么 都碰：重写过 SpamD（不满意即推倒重来）、近期在拆解 SCSI 层——多数 BSD 的磁带机与磁带库 changer 支持基本残废，遂对 SCSI 层、磁带驱动与 changer 驱动作内核级修整；参与各处的修复、测试与发布验证，运营 orders 网站（藏在其公司机器与自家地下室）；自嘲“样样通样样松”，并强调自己不是 OpenBSD 狂热者而只是一个 UNIX 用户——用其所善、避其所短。（BSDTalk EP68，[897.92-1020.56]，L1）
- 缘起故事：约 1995 年，受访者与合伙人写防火墙软件并在咨询业务中营销，以把它移植到一切平台为乐（含内核修改）；当时无线买不起联网可用机，弄到一台 SPARCstation 后发现 NetBSD 的 SPARC 移植完全不可用，而 OpenBSD 正在起步——安全正对其胃口，也不管社区恩怨只问“能不能用”；下载 SPARC 发行版果然能跑且修掉了一批旧 bug；当年网站还是 Theo 的个人页，写着“喜欢就打这个电话”——竟是卡尔加里一家比萨店的号码，身在三小时车程外埃德蒙顿的他打电话订比萨遭拒后转而向 Theo 抱怨，两人在汉堡店见面，他买下一张 CD，从此入伙。（BSDTalk EP68，[1020.56-1118.98]，L1）
- 桌面、家庭与文化参与：受访者笔记本、桌面与孩子的机器都跑 OpenBSD（孩子双启 Windows 只为游戏）；其桌面是极简的 fvwm，但承认近年 ports 收集安装体验进步惊人，孩子用全套 KDE 加 Linux 兼容层跑 OpenOffice 与教育、游戏软件，女儿用 MSN 客户端、儿子玩 Blender，全家充当 ports 的发布测试“小白鼠”；家中防火墙以 PF 的操作系统指纹特性只放行 Windows 走 80 端口以隔绝病毒。发行文化方面：4.0 已分支并开放预购，预购者常在 FTP 放开前拿到 CD；本次除 CD 套装外首推收录 3.0 至 4.0 全部发行歌曲加彩蛋曲目的音频 CD；受访者为 3.5 的“鱼执照”歌曲写过歌词（自认 Monty Python 粉丝玩过火）；制作水准主要来自卡尔加里的 Ty Semaka 与 Jonathan Lewis（乐队 Plaid Tongued Devils），他自己也在一曲中与 Theo、Peter Valchev 及儿子 Calvin 合唱“酒吧合唱”；收尾呼吁买 CD、T 恤、捐款——强调 OpenBSD 反哺众多项目、直接间接被广泛使用，募款并非乞讨。（BSDTalk EP68，[1159.18-1535.58]，L1）
- 移植工程缘起：Christoph Egger 经一家以 OpenBSD 为基础出售安全产品的慕尼黑公司 Gainware 接触 OpenBSD，寻找学位论文题目时由公司选定“把 OpenBSD 移植到 Xen”；其于 2005 年 12 月从 Xen 2 起步，2006 年 XenSource 经由 Google Summer of Code 把“OpenBSD 移植到 Xen3”立项，因其已有 OpenBSD 跑在 Xen 2 上的基础而顺势承接，至受访时已在 Xen 3 上完整可用——身份是 Xen 客户机（Xen guest）而非宿主。（BSDTalk EP69，[83.32-248.96]，L1）
- Xen 技术原理：Xen 是 XenSource 开发的 hypervisor，把大型机虚拟化技术带到 PC，使多个操作系统同时高速并行；所有系统都运行在 Xen 之上，Xen 掌管硬件与 CPU，其中特权最高的 domain zero（xenhost）负责管理其余客户机。Xen 不模拟整机（那是 VMware 的全虚拟化，客户机看到的是伪造的通用硬件），而采用半虚拟化——客户机操作系统自知运行于虚拟环境并直视真实硬件，开销约 2%-3%；借助 AMD Pacifica 与 Intel VT 硬件虚拟化还可运行未经修改的客户机。版本演进上，Xen 2 仅支持 i386 且要求 i686 级 CPU，Xen 3 已扩展至 IA64、Itanium、AMD64 并在开发 PowerPC 支持，加入 ACPI 电源管理与客户机 SMP；迁移分停机迁移与动态迁移（后者 TCP 网络连接不中断），并支持运行时增删 CPU 与增减内存——前提是客户机操作系统支持相应热插拔，否则结果未定义。（BSDTalk EP69，[159.36-505.38]，L1）
- OpenBSD 客户机功能与回馈主线：其移植提供网络、块设备 I/O（磁盘与 CD-ROM）、时钟、FPU、控制台五类基础驱动，使其普通可用；自加的特别功能是网络与块设备在运行时动态挂载与卸载。工作自 OpenBSD current（彼时即 4.0）起步并持续跟进 current；移植过程暴露的缺陷已修复并被接受——其一在 TCP 栈、其一在 UVM 内存管理，均已进入 OpenBSD 3.9，后续补丁将进入 current；此举也被视为 OpenBSD 社区借 Xen 移植清理内核缺陷的集体努力，目标是进入 OpenBSD current 并希望 4.1 收录 OpenBSD/Xen；现时代码经其 GSoC 导师与其他 OpenBSD 开发者试用，进展在专门邮件列表上讨论；使用状态为家中自用与部分开发者测试，尚无生产环境用户。（BSDTalk EP69，[505.38-897.16]，L1）
- 跨项目关系与许可证立场：受访者先找 NetBSD 后经公司转入 OpenBSD，评价两者代码干净、文档优良、运行稳定且极为相似——既已互移植彼此的缺陷修复，本可更紧密合作；许可证方面，其认为 BSD 许可证不强制公司开源，是优点还是缺点取决于立场，个人对 GPL 与 BSD 均接受、认为差别不大，只有在公司语境讨论是否开放源码时才真正相关；其时已供职 AMD，公司重心在市占更大的 Linux，但研究部门仍用 BSD 以求更宽的观察面，且多位同事使用并定期阅读 BSD 动态；桌面并跑 OpenBSD、NetBSD（SPARC 与 i386）与 Solaris、Mac OS X，除 Mac 外几乎全命令行，编辑器用 VI。（BSDTalk EP69，[624.8-815.22]，L1）
