# 079.2.4 全代码审计安全响应模型与版本周期架构关联——从被动 errata 到主动审计的工程路径

  **要点**：OpenBSD 2.0/2.1/2.2 时期（1996-1997）的漏洞响应模型呈现 “全代码审计主动识别 + errata 补丁被动发布” 的双层结构——全代码审计（1996 年夏天起）系统性识别 4.4BSD-Lite 遗留漏洞面（BIND/cron/IP 源路由/NFS/Kerberos V/procfs/rfork/vacation/lpd/tgetent/xterm），errata 机制以补丁形式向已发布版本回溯修复；该模型与同期 FreeBSD 2.1/2.2（以 Security Advisory 被动响应为主，无系统全代码审计）与 NetBSD 1.1/1.2（以 pullup 模型回溯修复为主，无系统全代码审计）形成鲜明对照；securelevel 经 4.4BSD-Lite → NetBSD 1.0 → OpenBSD 1.0 路径继承，在 OpenBSD 2.0 时期作为内核安全等级机制为漏洞响应提供纵深防御——level 1 安全模式禁止 `/dev/mem` 访问与原始磁盘写入，level 2 高安全模式进一步限制系统时间修改，securelevel 一旦提升至非零级即不可降级须重启方能恢复至 level 0；r-commands（**rsh(1)**/**rlogin(1)**/**rcp(1)**）在 OpenBSD 2.0 时期逐步退役，减少基于 `~/.rhosts` 信任链的远程攻击面，与全代码审计形成协同——审计识别 r-commands 信任链缺陷，退役消除缺陷根源
  
**史料**：OpenBSD security.html（“We have been auditing since the summer of 1996”）、OpenBSD 2.0/2.1/2.2 errata 页面、4.4BSD SMM: 16《On the Security of UNIX》securelevel 描述、OpenBSD **securelevel(7)** 手册页历史版本、OpenBSD 早期 r-commands 退役 commit 序列；openbsd.duckdb 数据库证据——openbsd-src 1996 年 5,240 commits、1997 年 6,888 commits，反映全代码审计期开发活跃度持续增长 ［A］
  
**史观**：全代码审计安全响应模型是 OpenBSD 从被动 errata 到主动审计的工程路径转折；de Raadt 个人主导的审计方法论决定 OpenBSD 2.0/2.1/2.2 的安全架构演化
  
**辨析**：全代码审计与 errata 补丁的双层结构须严格区分——审计是主动识别（针对源码树），errata 是被动回溯（针对已发布版本），二者在时间维度与工程目标上不同；securelevel 在 OpenBSD 2.0 时期的实际默认启用状态须对照源码与 release notes 核实，概念雏形与默认启用为不同维度；r-commands 退役的精确版本与默认配置变更须对照 OpenBSD 2.0/2.1/2.2 release notes 核实；【0 信任原则·commit 量不等于审计质量】1996-1997 年 openbsd-src commit 量（5,240→6,888）反映开发活跃度但不等于审计覆盖度，全代码审计的覆盖深度须结合 errata 条目数量与 commit message 主题词综合判断；【0 信任原则·与 FreeBSD/NetBSD 对照的公平性】将 OpenBSD 全代码审计与 FreeBSD/NetBSD 被动响应对照时须注意——FreeBSD 2.1/2.2 与 NetBSD 1.1/1.2 时期的安全工程目标以功能完善与平台扩展为优先，全代码审计尚未成为独立工程目标，史家不得以 OpenBSD 的审计标准回溯评判同期 FreeBSD/NetBSD 的安全实践
  
**文献**：OpenBSD security.html；OpenBSD 2.0/2.1/2.2 errata 页面；4.4BSD SMM: 16《On the Security of UNIX》；OpenBSD **securelevel(7)** 手册页；OpenBSD 早期 r-commands 退役 commit 序列；本项目。原材料/研究/bsd 漏洞史/版本周期/openbsd-2.x.md；本项目。bsd_commits.duckdb 数据分析报告：宏观趋势统计 [R/OL]. 2026. ［A］
