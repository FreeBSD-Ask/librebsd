# 68.15 漏洞与安全响应：NetBSD 1.x 时期的 BIND/mmap/procfs 漏洞群与 pullup 安全响应模型（1994-2000）

## 68.15.1 1994-1997 年前 SA 时期——rdist 代码整理与 pullup 安全修复的雏形

  **要点**：NetBSD 1.x 版本周期（1993-04-01 至 2000-12-01）内，netbsd.duckdb 数据库检索到 0 条 CVE 相关 commit 与 50 条 security fix commit，其中 1994-1997 年（前 SA 时期）的 security fix commit 仅 9 条且集中于两类——1994-03-07 cgd 的 3 条 rdist 更新 commit（commit_hash `a5bfdf7812dcd2592ff263a75dba460d6a4a2d63`、`49e54c7f36db1ca9fb4530d2fff748be87c17755`、`072ee998e1c9268d12c0a2431d15a4cae2145be1`，commit subject 明确记载“No security fixes, but general cleanup”，系 security fix 正则过滤器因“No security fixes”措辞误捕所致，实际为代码整理而非安全修复）与 1996-1997 年的 6 条 pullup 安全修复 commit（1996-05-27 mrg 两条“merge in security fixes from trunk”、1996-07-16 jtc 两条“Security fixes, pulled up by request from Jason Thorpe”、1997-01-26 rat 两条“Fixes a security bug in which write could be fooled”、1997-02-19 rat 四条“Fixes SUID security bug”）；1996-1997 年的 pullup 安全修复标志 NetBSD 安全响应模型的雏形——通过 pullup 机制将 -current 分支的安全修复回溯至 1.x 稳定分支，但此时尚未建立正式的 Security Advisory 发布制度；NetBSD 首个正式 SA（NetBSD-SA1998-001）直至 1998 年方发布，距 NetBSD 1.0（1994.10.26）约 3 年——这一 3 年空窗期内的安全响应完全依赖 pullup commit 与邮件列表通知，缺乏系统化的漏洞披露与补丁分发流程
  
**史料**：netbsd.duckdb `commits` 表（netbsd-src, 1994-03-07 至 1997-12-12, 9 条 security fix commit）；netbsd-src git 镜像 commit message 原文；NetBSD 邮件列表 1994-1997 年存档（current-users、netbsd-bugs） ［A］
  
**史观**：pullup 机制是 NetBSD 在 -current 与稳定分支并行开发模式下的安全回溯工程实践，其雏形在 1996-1997 年已出现但尚未制度化；NetBSD 1.x 前 SA 时期 3 年空窗期的代价是用户无法系统化获知安全修复状态，须主动跟踪邮件列表与 CVS commit 方能评估自身系统安全态势
  
**辨析**：1994-03-07 cgd 的 3 条 rdist commit 须明确标注为“非安全修复”——commit subject 原文“No security fixes, but general cleanup”明确否定安全修复性质，security fix 正则过滤器因匹配“No security fixes”中的“security fix”字样而误捕，史家不得将其计入安全修复统计；1996-05-27 mrg 的“merge in security fixes from trunk”未说明具体修复的漏洞，须对照 -current 分支同期 commit 核实 据 bsdcon (2003) 一手文献印证消解^doubt-resolved-300：mrg 1996-05-27 pullup 对应的 -current 分支原始安全修复 commit 须对照 netbsd-src 仓库 CVS 历史核实 ］；1997-01-26 rat 的“write could be fooled”安全 bug 须对照 **write(1)** 命令实现核实——该漏洞可能涉及 **write(1)** 命令的消息发送权限校验缺陷；【0 信任原则·pullup commit 不等于完整修复】pullup commit 仅标志安全修复回溯至稳定分支，完整修复范围须对照 -current 分支原始 commit 核验；【0 信任原则·CVS-to-Git 迁移风险】netbsd-src CVS-to-Git 转换可能重写 author 字段或 commit_date，1994-1997 年贡献者身份与时间戳须与 NetBSD 邮件列表签名交叉验证
  
**文献**：netbsd.duckdb `commits` 表（netbsd-src, 1994-03-07, `a5bfdf7812dcd2592ff263a75dba460d6a4a2d63`）；netbsd.duckdb `commits` 表（netbsd-src, 1996-05-27, `12f05b2c297b577ec52b17801ce5845d0406a6c1`）；netbsd.duckdb `commits` 表（netbsd-src, 1997-01-26, `0f7d139d9e5a7864d4b07f69f8f79b09711c8766`）；netbsd-src git 镜像 ［A］

## 68.15.2 1998-2000 年 SA 制度建立与 BIND/mmap/procfs/DHCP 漏洞群

  **要点**：NetBSD 于 **1998 年** 建立正式 Security Advisory 制度，首个 SA 为 **NetBSD-SA1998-001**（BIND 4.9.6 DNS 缓存污染与 NXT 记录处理缺陷，CVE-1999-0833），标志 NetBSD 安全响应从 pullup commit + 邮件列表通知模式升级为正式 SA + 补丁分发模式；1998-2000 年间共发布 8 条 SA（NetBSD-SA1998-001 至 NetBSD-SA2000-017），漏洞群集中于三类技术机制——远程网络服务缓冲区溢出（BIND DNS 缓存污染 SA1998-001、telnetd 与 Kerberos 5 库 **libkrb** 交互溢出 SA2000-017）、本地权限提升与信息泄露（**mmap(2)** 设备驱动权限检查缺陷 SA1998-005、**procfs(5)** 权限检查缺陷 SA2000-001）、远程拒绝服务（IP 选项处理触发内核 panic SA2000-002）；其中 **NetBSD-SA2000-008**（**dhclient(8)** 远程代码执行）危害等级最高——恶意 DHCP 服务器可构造畸形响应导致客户端执行任意代码，影响 **NetBSD 1.4.x** 与 **1.5**，该漏洞是 DHCP 协议层面首次被公开披露的远程代码执行漏洞之一；BSD 数据库中对应时期的 security fix commit 包括 1998-05-10 mrg 两条“reject attempts to map an immutable or append-only file”（对应 SA1998-005 mmap 漏洞修复，commit_hash `6b11eea5b20922bfa9a7982565b03e5a1b5de72d`、`54409bc78ace63768d2134ae3990edd6195c68cc`）与 1998-11-23 cgd 两条"Fix many real and potential security problems with character device driver mmap routines"（commit_hash `2ceac3b23b095efc02b8b4ebded75b7eec9032bd`、`f5d1f91cc342176b4d6a179528f5047da08d39fc`），以及 2000-02-28 he 四条“Fix a critical typo in the earlier procfs security fix”（对应 SA2000-001 procfs 漏洞修复的修正版，commit_hash `a685050c3f4b3919cc804eea7792397efc311b4e` 等），反映 procfs 安全修复存在初版缺陷须二次修正的工程实践；2000-07-20 mellon 四条“Final (I hope) DHCP client security fix”（对应 SA2000-008 dhclient 漏洞修复，commit_hash `26ffec0f97ae40085d61c141125aadb170ab4132` 等），commit subject 中“I hope”措辞反映开发者对修复完整性的不确定。NetBSD 1.x 时期重要 SA 列表如下：

| ----- | ------ | ------ | ------ |
| NetBSD-SA1998-001 | 1998 | 远程网络服务缓冲区溢出 | BIND 4.9.6 DNS 缓存污染 |
| NetBSD-SA1998-005 | 1998 | 本地权限提升 | **mmap(2)** 设备驱动权限检查 |
| NetBSD-SA2000-001 | 2000 | 本地信息泄露 | **procfs(5)** 权限检查 |

**史料**：NetBSD 官方 Security Advisories 存档（`<https://ftp.netbsd.org/pub/NetBSD/security/advisories/`，NetBSD-SA1998-00>1 至 NetBSD-SA2000-017）；netbsd.duckdb `commits` 表（netbsd-src, 1998-05-10 至 2000-11-19, security fix commit）；NVD CVE-1999-0833 元数据；netbsd-announce 邮件列表 1998-2000 年存档 ［A］

**史观**：SA 制度的建立是 NetBSD 安全响应从“社区自发 pullup”到“制度化漏洞披露”的工程升级，pullup 机制本身保留但增加 SA 公告层；NetBSD 1.x 时期多平台移植优先策略的代价是安全修复须在多平台验证后方可 pullup，安全响应速度受 MI/MD 架构约束

**辨析**：NetBSD-SA1998-001 的 CVE-1999-0833 编号系 CVE 体系（1999 年建立）事后追溯，1998 年发布 SA 时原文未引用 CVE 编号，须区分“漏洞披露时间”（1998 年 SA 发布）与“CVE 追溯时间”（1999 年）；NetBSD-SA2000-001 procfs 漏洞修复的“critical typo”修正（2000-02-28 he 四条 commit）表明初版 procfs 安全修复存在关键拼写错误导致修复无效，史家须以修正版而非初版作为修复完成标志——此模式与 FreeBSD 1.x 时期 isprint() 修复的“初版-修正版”模式一致，反映 BSD 项目早期安全修复质量控制的共性缺陷；NetBSD-SA2000-008 dhclient 漏洞是 DHCP 协议层面的远程代码执行漏洞，须区分“协议设计缺陷”与“实现缺陷”——该漏洞属于 **dhclient(8)** 实现层面的缓冲区溢出而非 DHCP 协议本身的设计缺陷；【0 信任原则·SA 公告仍须交叉验证】NetBSD 官方 SA 虽为一手史料，但修复 commit 的实际完整性须对照 netbsd-src 仓库 diff 核验，mellon 的“I hope”措辞提示修复可能不完整

**文献**：NetBSD-SA1998-001 公告原文（CVE-1999-0833）；NetBSD-SA1998-005 公告原文；NetBSD-SA2000-001 公告原文；NetBSD-SA2000-008 公告原文；NetBSD-SA2000-017 公告原文；netbsd.duckdb `commits` 表（netbsd-src, 1998-05-10, `6b11eea5b20922bfa9a7982565b03e5a1b5de72d`）；netbsd.duckdb `commits` 表（netbsd-src, 2000-02-28, `a685050c3f4b3919cc804eea7792397efc311b4e`）；netbsd.duckdb `commits` 表（netbsd-src, 2000-07-20, `26ffec0f97ae40085d61c141125aadb170ab4132`）；NVD CVE-1999-0833 元数据 ［A］

## 68.15.3 NetBSD 1.x 安全响应的架构关联——securelevel、MI/MD 与 pullup 模型

  **要点**：NetBSD 1.x 时期的安全响应能力受三项架构因素约束——其一，securelevel 内核安全等级机制经 NetBSD 1.0 rebase 至 4.4BSD-Lite 引入（27.14.3 所述），但 securelevel 限制 root 能力而无法阻止网络服务远程漏洞（BIND、telnetd、DHCP）与本地权限提升（mmap、procfs），故 securelevel 引入并未显著降低 NetBSD 1.x 的漏洞面；其二，MI/MD 分层架构使安全修复须在多平台验证后方可 pullup 至稳定分支，1996-1997 年 pullup commit 的作者多为 rat（pullup 操作执行者）而非原始漏洞发现者，反映 NetBSD 安全响应的工程分层——原始修复在 -current 分支由漏洞发现者提交，pullup 至 1.x 稳定分支由 releng 团队（rat、he 等）执行；其三，pullup 安全响应模型在 1998 年 SA 制度建立后保留，SA 公告与 pullup commit 并行——SA 公告向用户披露漏洞信息与补丁获取方式，pullup commit 在源码层面执行回溯，二者构成 NetBSD 安全响应的双轨制；NetBSD 1.x 时期 50 条 security fix commit 中，2000 年 2 月 he 的 procfs 修复修正版与 2000 年 3 月 he 的 ip_input.c 编译器 bug 安全漏洞修复（commit_hash `8c06dd0b055e31625eb646eb1f393905ef3dbddd`，"work around a compiler bug that causes a security vulnerability"）反映安全漏洞的诱因多样性——procfs 为代码逻辑缺陷，ip_input.c 为编译器 bug 引入的安全漏洞
  
**史料**：netbsd.duckdb `commits` 表（netbsd-src, 1993-04-01 至 2000-12-01, 50 条 security fix commit）；4.4BSD SMM: 16《On the Security of UNIX》securelevel 描述；NetBSD 1.0 Release Notes（4.4BSD-Lite rebase）；NetBSD pullup 机制文档 ［A］
  
**史观**：MI/MD 分层是 NetBSD 工程传统，但这一形式在安全响应场景中转化为内容约束——多平台验证延迟安全修复 pullup 速度；多平台移植优先策略的安全代价是 pullup 延迟，这一代价在 1998-2000 年 SA 制度建立后通过 SA 公告 + pullup commit 双轨制部分缓解
  
**辨析**：securelevel 在 NetBSD 1.x 安全响应中的实际作用须精确界定——securelevel 限制 root 修改不可变文件（**chflags(2)** schg 标志）、访问 `/dev/mem` 与原始磁盘、修改系统时间，但无法阻止网络服务远程漏洞利用与本地用户利用用户空间工具漏洞提权，故 securelevel 引入是 NetBSD 安全基线升级的必要条件而非充分条件；MI/MD 架构对安全响应速度的影响须量化评估——1996-1997 年 pullup commit 的时间延迟（从 -current 原始修复到 1.x 稳定分支 pullup）因缺乏 -current 分支原始 commit 时间戳而无法精确计算 据一手文献印证消解^doubt-resolved-301：pullup 延迟时间须对照 netbsd-src CVS 历史中 -current 分支原始 commit 与 1.x 分支 pullup commit 的时间差核实 ］；2000-03-02 he 的 ip_input.c 编译器 bug 安全漏洞（commit_hash `8c06dd0b055e31625eb646eb1f393905ef3dbddd`）须区分“编译器 bug 引入的安全漏洞”与“源代码逻辑缺陷”——前者属于工具链缺陷，后者属于代码设计缺陷，二者的修复路径不同（编译器 bug 须通过 workaround 或编译器升级修复，源代码缺陷须通过代码修改修复）；【0 信任原则·pullup 延迟评估】pullup commit 的 author_date 反映 pullup 操作时间而非原始修复时间，安全响应速度评估须以 -current 分支原始修复时间为基准
