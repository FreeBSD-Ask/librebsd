- 【Linux社区】2000-05-24 linux-mm 讨论 2.3/4 版 VM 队列重构 RFC 时，Matthew Dillon（FreeBSD 与 DragonFly 主要开发者）以 FreeBSD 自身经验支持多队列方案，并详述 FreeBSD 4.x 的两遍 pageout 扫描算法与 PV entry 物理页老化机制，指出该老化设计移植到 Linux 是最难的部分。原文引语：“The multi-queue approach is the right way to go (for the same reason FBsd took that approach)”。这是 BSD VM 子系统的实现经验直接进入 Linux 内存管理设计讨论的典型谱系证据。`<!-- ROW_MINE: linux-mm.messages.1080746 -->`

Howlett 回应 Theo de Raadt 对 mmap 与 mseal 交互的质疑，邮件转引 Theo 的 OpenBSD 立场：“OpenBSD won't be doing this”。Theo 指出他曾在草案中做过 PROT_IMMUTABLE，但研究后发现“基本上没有任何情境”需要用户态在 mmap 时直接创建不可变映射，反而形成“危险的反模式”，因此 OpenBSD 最终未采纳；Liam 本人则指出 mseal 检查需在 mmap_lock 下遍历 VMA 树，代价为正的非零数。`<!-- ROW_MINE: linux-mm.messages.1137525 -->`
- 【Linux社区】Pedro Falcato 回应 Jann Horn 关于 fork 时 CoW 造成子进程内存不一致的问题，指出写保护路径也无法避免部分地址空间不一致，必须挂起多线程才能修复。原文引语：“This would only be fixable if e.g we suspended every thread on a multi-threaded fork”。他另指出此类写保护路径自 1980 年代的 BSD 以来在概念上保持稳定，fork 内存快照一致性实际无法达成；该讨论触及 POSIX 与 Linux 语义差异，属跨内核 API 语义对照范畴。`<!-- ROW_MINE: linux-mm.messages.1138252 -->`
- 【Linux社区】Jeff Xu引Theo de Raadt的OpenBSD视角说明mseal与sigaltstack的交互风险，引语：“In OpenBSD, sigaltstack() forces MAP_STACK onto the specified (pre-allocated) region”。Theo称OpenBSD在syscall入口强制sp指向MAP_STACK区域，能严重破坏ROP跳转方法，而Linux尚无MAP_STACK强制机制，建议Linux检查sigaltstack是否构成mseal的绕过路径。`<!-- ROW_MINE: linux-mm.messages.1139187 -->`
- 【Linux社区】Waiman Long提议将MAP_STACK映射为VM_STACK以防止栈VMA与非栈匿名VMA合并。引语：“One of the flags of mmap(2) is MAP_STACK to request a memory segment suitable for a process or thread stack”。他指出glibc用MAP_STACK映射线程栈，而Linux内核完全忽略该标志，致使栈VMA可与相邻匿名VMA合并，触发SELinux禁止可执行栈的检查失败并造成随机SEGV。`<!-- ROW_MINE: linux-mm.messages.1141674 -->`
