# 5.8.22 【Linux社区】其他技术承袭

- 【Linux社区】1999 年 1 月 Matthew Dillon 自 freebsd-hackers@FreeBSD.ORG 发出“Review and report of linux kernel VM”经 Craig Schlenter 转发至 LKML，以 FreeBSD 内核视角系统比较两套 VM：“the linux kernel uses persistent hardware-level page tables... the function of the persistent page tables is roughly equivalent to the function of FreeBSD's vm_object's”，并断言“linux's VM system is much cleaner then FreeBSD's... but at the cost of eating some extra memory”，是 BSD 内核作者对 Linux VM 架构的公开技术审视 <!-- ROW_MINE: lkml.messages.1901629 -->`
- 【Linux社区】klibc 开发帖中 Matti Aarnio 就 HPA 称赞 NetBSD“新增系统调用一处即全平台可用”的模型评论：解读为 NetBSD 新增架构将即刻继承全部历史系统调用（含 obsolete 的 oldumount 等，部分旧调用虽被撤销但并非全部），只要旧调用仍受支持，内核就必须处理 10 年前的服务；对比 glibc 为兼容 2.0 内核至今做怪异模拟的极端痛苦，而 klibc 可紧贴内核演进不背历史包袱。NetBSD 系统调用治理作为 Linux 对照参照。 <!-- ROW_MINE: lkml.messages.2138036 -->`
- 【Linux社区】Ted Ts'o (tytso@mit.edu) 就 suspend block api 补丁线程回帖，回忆早年指出主线 PCMCIA 代码弹出时 10% 概率崩溃，NetBSD 自豪宣称代码 iron-clad 任何时候弹出都正确处理，但 NetBSD PCMCIA 比 Linux 晚 3 年可用，Ts'o 感慨“我们曾是技术务实派，Linus 至今仍是务实派，而其他人则是极端完美主义”，并称“近来 NetBSD 态度已开始感染 LKML 而这是不幸的”，以 Linus 曾以“merge or kill”决定结束过长讨论作结。BSD/Linux 文化态度冲突的直接表达。 <!-- ROW_MINE: lkml.messages.5376129 -->`
- 【Linux社区】2001 年 10 月 Matthias Andree 在 Rik van Riel“2.4.10 vs. 2.4.10-ac2 与 qsort”线程中，就 Rik 建议改试 merge sort 时直接给出“Just rip it off NetBSD and there you go”，并对比 FreeBSD 与 NetBSD 的 merge.c 实现差异——“FreeBSD's breaks on machines like SPARC, NetBSD's does not”，附 de.freebsd.org 上的 NetBSD libc/stdlib/merge.c rev1.10 源码链接。这是 BSD libc merge sort 被 LKML 明确点名引入 Linux 内核 VM 讨论的早期证据。 <!-- ROW_MINE: lkml.messages.2002317 -->`
- 【Linux社区】2001 年 Guenter Millahn 追问 David S. Miller 关于 sun4c 平台 Linux 性能落后的问题：转引 NetBSD/Sparc FAQ 称 sun4c 的 MMU 硬件未被 Linux 良好处理、NetBSD 在此硬件上快得多，davem 回复确认属实，称追求顶级性能请在 sun4c 上使用 BSD 系统，并自陈知道如何修复但已无意再开发该平台；Millahn 询问 OpenBSD 是否与 NetBSD 相同，并请求 davem 公开修复思路以便他人产出补丁，是 Linux 早期 SPARC sun4c 移植受限于 MMU 而 BSD 表现更优的一手证据 <!-- ROW_MINE: lkml.messages.1904977 -->`
- 【Linux社区】2014年12月Rickard Strandqvist提交的ps3_repository_write_highmem_info()移除补丁被Geoff Levand NAK，FreeBSD PS3端口负责人Nathan Whitehorn（nwhitehorn@freebsd.org）论证该函数不可删：“we really need this for FreeBSD since that port uses the repository directly instead of FDT. We could adapt FreeBSD to use FDT (this is the only non-device-tree PowerPC port) but there hasn't been any reason”；Linux arch/powerpc/ps3子系统代码被FreeBSD otheros++端口反向依赖，形成不可删除契约。 <!-- ROW_MINE: lkml.messages.5822881 -->`
- 【Linux社区】2004年Bill Huey（hui，bhuey@lnxw.com）在Linux BKL撤除串中论及FreeBSD-current自适应锁（adaptive mutex）与Solaris MUTEX设计，评价“the FreeBSD community has ignored a lot of the really hard work of pushing down locks in favor of 'getting fancier locks', which only abuses thread priorities and the scheduler”，并援引Bill Irwin闲谈提供的数据，将Linux手雕per-CPU感知的SMP路线与FreeBSD/Solaris复杂SMP基础架构作对照，认为Linux路线当下明显更正确，是SMP锁策略跨内核比较的一手存档。 <!-- ROW_MINE: lkml.messages.1822653 -->`
- 【Linux社区】2004年Keith Whitwell（Tungsten Graphics，DRM开发者）在“DRM and 2.4”串中回应Arjan van de Ven“the DRM codebase proves that it's incapable of even doing BSD support properly(eg without the right abstractions but instead fouling up the entire codebase to the point of unreadability)”的批评，澄清“Most of the abstractions that you're complaining about existed prior to the addition of freebsd support”、宏滥用与BSD支持的因果关系存在混淆，并指出Dave Airlie正将代码回归到“something less obscure”，是DRM维护者就BSD支持对Linux DRM代码库抽象层影响公开澄清的一手存档。 <!-- ROW_MINE: lkml.messages.2098352 -->`
