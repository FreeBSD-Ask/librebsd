- 【Linux社区】本邮件是作者刚加入 Rust for Linux 邮件列表后针对许可证策略提出的一问。作者注意到现有 Rust for Linux 代码似乎统一采用 GPL-2.0，询问这究竟是明确的集体决定，还是仅仅沿用默认设置。作者援引既有事实作为对照：Linux 的 DRM 核心以及 i915、radeon、amdgpu 等主要驱动均采用 GPL 与 MIT 双许可，正因为如此，OpenBSD 可以直接使用这部分代码。作者表示希望苹果芯片驱动也采取同样做法，目标是让驱动对其他内核同样有用，因此询问 Rust 核心中的一部分，尤其是进程宏和用 Rust 编写的通用代码，是否可以采用更宽松的许可，以便其他项目在自己复用它所支撑的驱动时能够直接引入这些公共代码。这段讨论把 GNU 内核中已有的双许可先例与 BSD 系统跨内核复用需求直接联系起来。 `

<!-- ROW_MINE: rust-for-linux.messages.9298084 -->`
- 【Linux社区】本邮件在 Linux 内核 Rust 支持提案的讨论中提出许可证隐患，作者开头声明自己并非法律专业人士。作者引用一次访谈中的观点作为论据：大量以 BSD 或 MIT 等宽松许可发布的开源项目，一旦具有商业价值往往走向分裂，公司随后把各自部分转为专有；而 GPLv2 大致是最佳平衡点，既让所有人遵守同一规则，又通过相互回馈义务形成回报机制，允许分叉同时保留重新合并的权利。作者据此推断 Rust 编译器许可存在风险：它不要求回馈社区，某家公司可以自行添加专有扩展并开发驱动，即便驱动代码按 GPL 发布，除该公司外其他人也无法构建。作者还说明 LLVM 这一单一实现混合使用了 MIT、Apache、BSD 兼容等多种许可，与构建内核所需工具普遍采用的强互惠许可形成反差。作者建议等到存在功能完备的 GPL Rust 实现之前暂缓合入内核 Rust 代码，并建议把内核必须可由自由软件构建这一要求明确写入政策。 `
