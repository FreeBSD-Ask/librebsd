# 5.7.3 BSD 谱系：Rust for Linux 的许可采纳与套接字抽象

- 【Linux社区】Miguel Ojeda 向 Linus Torvalds 提交 Rust for Linux v7.2 合并请求，核心是引入 zerocopy 库以替换大量处理字节序列与类型间转换的不安全代码。zerocopy 以 BSD-2-Clause 或 Apache-2.0 或 MIT 三重许可授权，导入时基本保持原样仅需增删数行适配。该条目展示了 Rust 内核子系统引入非 GPL 许可 crate 的许可决策与依赖管理实践，涉及宽松许可与内核 GPL 许可的交叉地带。 `<!-- ROW_MINE: rust-for-linux.messages.9268951 -->`
- 【Linux社区】Andrew Lunn 审阅 Rust Socket 抽象补丁，质疑其 API 设计的合理性。他指出用户空间应用通常通过 BSD sockets 与内核及协议通信，因此需要明确 Rust socket 抽象层与现有 BSD socket API 的层次关系。他质疑为何低时延网络协议需要穿越两次 socket 层，以及如何在将 socket 底层连回顶层时避免死锁。该讨论触及 BSD socket 接口在 Rust 内核抽象中的定位与兼容性问题。 `<!-- ROW_MINE: rust-for-linux.messages.9270985 -->`
- 【Linux社区】Andrew Lunn 继续讨论 Rust Socket 抽象补丁，指出当前实现使用 procfs 或共享内存映射的字符设备缓冲区而非 BSD sockets。他强调内核已有 Eric 等人实现的 socket 零拷贝支持以及 netlink 控制平面机制，质疑为何要在 socket 之上再建一层 API。他还建议服务可改用 eBPF 从用户空间加载，避免每次修改都需经过合并流程。该讨论涉及 BSD socket 接口在低时延分布式系统中的适用性边界。 `<!-- ROW_MINE: rust-for-linux.messages.9271703 -->`
- 【Linux社区】Davide Rovelli 回应 Andrew Lunn 关于 Rust Socket 抽象补丁的质疑，解释当前实现使用 procfs 或共享内存映射字符设备缓冲区而非 BSD sockets。他指出该 API 提供分布式服务如故障检测器与共识机制，通过 SDN 协议优先化流量。他解释系统设计将用户空间应用与内核空间服务分离，以实现端到端低时延通信与处理，从而实现高效的分布式服务。该讨论涉及 BSD socket 接口在低时延分布式系统中的定位。 `<!-- ROW_MINE: rust-for-linux.messages.9275252 -->`
- 【Linux社区】Miguel Ojeda 回复 Asahi Lina 关于以 Rust 编写 Apple AGX GPU 驱动的讨论，涉及 Rust 绑定的维护权与许可策略。他提到 DRM 子系统与 OpenBSD 和 FreeBSD 活跃共享代码，建议将 DRM 绑定、驱动及进程宏设为双许可，以便各 BSD 系统能够使用。他还讨论了核心子系统抽象的维护归属问题，提出即使子系统当前不愿维护抽象，只要有责任人即可先行提交，最终由高层维护者决定。该条目涉及 BSD 系统与 Linux 内核在 DRM 子系统的代码共享与许可交叉。 `<!-- ROW_MINE: rust-for-linux.messages.9277169 -->`
- 【Linux社区】Enrico Weigelt 在 Rust V4L2 支持讨论中明确划定 BSD 代码在内核邮件列表的范围边界。针对 Hans Petter Selasky 展示的 webcamd 项目即 BSD 许可的用户空间驱动示例，Enrico 明确表示 BSD 代码不属于 LKML 讨论范围，并指出将内核代码复制到用户空间后需自行维护，内核 API 从不存在稳定固定版本。他还反驳了 V4L2 驱动应移至用户空间的观点，认为这与内核开发无关。该条目触及 BSD 许可代码与 Linux 内核开发边界的治理问题。 `<!-- ROW_MINE: rust-for-linux.messages.9279512 -->`
- 【Linux社区】本邮件是苹果芯片 Rust 图形驱动讨论帖中的一段，作者回应 Rust for Linux 负责人关于许可证的说明。被引部分指出，Rust for Linux 团队自启动之初便约定全部代码使用 GPL-2.0，此前还讨论过复用一份用于 GRUB 模块的 Rust 文件。作者随即说明，DRM 子系统与 OpenBSD 和 FreeBSD 之间存在活跃的代码共享关系，因此希望社区就 DRM 绑定层、驱动本身以及配套进程宏能否双许可作出表态，同时承认 BSD 系统是否愿意引入 Rust 仍是开放问题。作者另指出，若绑定代码被 GPL 覆盖，DRM 维护者将来需重写宏与辅助代码才能支持非 GPL 使用者，这会构成负担。文末作者特别区分了支持双许可与支持专有 Rust 内核模块两种情形，表示个人并不看好专有模块对生态的影响。整段讨论把 GPL-2.0 统一许可策略与 BSD 家族代码复用需求之间的张力摆到台面。 `<!-- ROW_MINE: rust-for-linux.messages.9285777 -->`
- 【Linux社区】本邮件是作者刚加入 Rust for Linux 邮件列表后针对许可证策略提出的一问。作者注意到现有 Rust for Linux 代码似乎统一采用 GPL-2.0，询问这究竟是明确的集体决定，还是仅仅沿用默认设置。作者援引既有事实作为对照：Linux 的 DRM 核心以及 i915、radeon、amdgpu 等主要驱动均采用 GPL 与 MIT 双许可，正因为如此，OpenBSD 可以直接使用这部分代码。作者表示希望苹果芯片驱动也采取同样做法，目标是让驱动对其他内核同样有用，因此询问 Rust 核心中的一部分，尤其是进程宏和用 Rust 编写的通用代码，是否可以采用更宽松的许可，以便其他项目在自己复用它所支撑的驱动时能够直接引入这些公共代码。这段讨论把 GNU 内核中已有的双许可先例与 BSD 系统跨内核复用需求直接联系起来。 `<!-- ROW_MINE: rust-for-linux.messages.9286518 -->`
- 【Linux社区】本邮件是引入群晖嵌入式微控制器驱动的补丁系列说明，主体内容属于设备支持与代码组织的技术描述。群晖在 NAS 设备中使用通过串口连接的小型微控制器，用于控制指示灯、风扇转速、蜂鸣器，并处理正常关机重启、按键与风扇故障；补丁依赖此前已提出的 Rust 指示灯抽象与 Rust 串口设备抽象，当前版本仅实现指示灯控制，其余功能还需补齐监控、输入以及关机与硬件保护关机相关的 Rust 抽象。本条入选是因为版本变更记录中有一条许可相关的明确表述：把设备树绑定文件的许可定为 GPL-2.0-only 或 BSD-2-Clause 二选一的双许可形式。这表明 Linux 内核文档层面已出现 BSD 二条许可条款与 GNU 许可并行的具体应用。除这一条记录外，全文不含 BSD 谱系、许可证论证或治理讨论。 `<!-- ROW_MINE: rust-for-linux.messages.9286619 -->`
- 【Linux社区】本邮件是围绕 Rust 内核网络抽象文件命名的一次简短讨论。提交者原先把网络抽象集中放在单一文件中，因完整网络接口过于庞大，审阅者建议按实际覆盖的小范围命名，提交者于是提议改用 socket 相关的文件路径。回复者认为新命名更好，同时提示应由核心维护者对此给出意见。回复者说明自己刻意在名称中加入内核字样，目的是明确区分这一点：该模块封装的不是 BSD 套接字内核接口，而是 Linux 内核内部的套接字接口，而作者本人也说不清这一区分在实践中有多重要。虽然内容属于命名层面的技术细节，但这段讨论明确引入了 BSD 套接字接口作为对照参照，触及两个体系在同名接口上的界限划分。 `<!-- ROW_MINE: rust-for-linux.messages.9291777 -->`
- 【Linux社区】本邮件是群晖嵌入式微控制器驱动补丁系列的一个早期版本说明，正文主体同样是设备功能描述与迭代变更清单，涵盖串口连接微控制器对指示灯、风扇、蜂鸣器与关机流程的控制，以及所需 Rust 抽象的补齐计划。入选依据来自变更记录中重复出现的一条许可表述：把设备树绑定文件的许可设定为 GPL-2.0-only 或 BSD-2-Clause 的双许可组合。这与后续版本中的同类记录相互印证，说明该驱动系列在提交之初就把 BSD 二条许可条款与 GNU 许可并列写入内核文档许可标识中。邮件其余部分不涉及 BSD 派系、许可证论证或项目治理议题，属于以纯技术实现为主的补丁提交，BSD 相关性仅限于这条许可记录。 `<!-- ROW_MINE: rust-for-linux.messages.9292380 -->`
- 【Linux社区】本邮件针对内核中双许可是否棘手这一说法展开反驳。被引用的 Rust 负责人称，双许可在内核中会迅速变得复杂，是否可行取决于接收补丁的树是否接受双许可，以及被抽象的对象是否仅限 GPL。作者认为这一说法奇怪，表示从未听说双许可在内核中构成障碍：大量驱动本身就是双许可，DRM 核心亦然；作者粗略检索 SPDX 许可行后发现，整个内核约十分之一的文件采用某种双许可形式。作者说明 Asahi Linux 项目主动鼓励双许可，以便其他操作系统也能使用相关代码，且尚未听说因此产生异议。作者进一步解释，只要其中一个许可是 GPL 或兼容 GPL，驱动即可任意选择许可组合。作者指出苹果芯片图形驱动是最可能被其他系统直接移植的驱动之一，DRM 早已接受双许可驱动，因此相关抽象层也应保持双许可，否则仅因改用 Rust 就让许可条件比原来更严格，逻辑上说不通，并以 FreeBSD 在宽松许可下直接使用了一大块 Linux DRM 代码为例证。 `<!-- ROW_MINE: rust-for-linux.messages.9293027 -->`
- 【Linux社区】本邮件是作者对在内核媒体子系统引入 Rust 支持的回应。作者主张 V4L2 应用单一语言实现，认为对摄像头、DVB 接收等媒体驱动而言，Rust 并无实际收益，因为其前提假设是所有代码都在内核中运行，而作者认为 media 目录下多数驱动应当运行在用户空间。作者援引 FreeBSD 的 Capsicum 能力框架作为对照：驱动位于用户空间时，设备摘除会终止驱动进程并回收内存，同时可借助能力机制锁死所有接口与文件句柄，即使代码被利用也不会造成系统级损害。作者以自己维护的 webcamd 守护进程为例，说明该实现已在 FreeBSD 的 amd64 平台接近六 MB 并支持约五百个驱动，且直接构建自 Linus Torvalds 维护的源码树。作者由此认为，与其推动内核驱动改用 Rust，不如推动厂商就设备协议的二进制格式达成共识，Linux 驱动开发的目标应当是减少而非增加驱动数量。 `<!-- ROW_MINE: rust-for-linux.messages.9298084 -->`
- 【Linux社区】本邮件在 Linux 内核 Rust 支持提案的讨论中提出许可证隐患，作者开头声明自己并非法律专业人士。作者引用一次访谈中的观点作为论据：大量以 BSD 或 MIT 等宽松许可发布的开源项目，一旦具有商业价值往往走向分裂，公司随后把各自部分转为专有；而 GPLv2 大致是最佳平衡点，既让所有人遵守同一规则，又通过相互回馈义务形成回报机制，允许分叉同时保留重新合并的权利。作者据此推断 Rust 编译器许可存在风险：它不要求回馈社区，某家公司可以自行添加专有扩展并开发驱动，即便驱动代码按 GPL 发布，除该公司外其他人也无法构建。作者还说明 LLVM 这一单一实现混合使用了 MIT、Apache、BSD 兼容等多种许可，与构建内核所需工具普遍采用的强互惠许可形成反差。作者建议等到存在功能完备的 GPL Rust 实现之前暂缓合入内核 Rust 代码，并建议把内核必须可由自由软件构建这一要求明确写入政策。 `<!-- ROW_MINE: rust-for-linux.messages.9298389 -->`
