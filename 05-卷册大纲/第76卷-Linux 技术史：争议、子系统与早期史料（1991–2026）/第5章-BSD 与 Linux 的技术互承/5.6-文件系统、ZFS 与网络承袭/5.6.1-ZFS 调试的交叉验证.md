- 【Linux社区】Davide Rovelli 回应 Andrew Lunn 关于 Rust Socket 抽象补丁的质疑，解释当前实现使用 procfs 或共享内存映射字符设备缓冲区而非 BSD sockets。他指出该 API 提供分布式服务如故障检测器与共识机制，通过 SDN 协议优先化流量。他解释系统设计将用户空间应用与内核空间服务分离，以实现端到端低时延通信与处理，从而实现高效的分布式服务。该讨论涉及 BSD socket 接口在低时延分布式系统中的定位。 `

- 【Linux社区】2003 年 7 月 David Schwartz 在 LKML epoll 补丁讨论中转述对话者以 IRC 服务器实践为其论点辩护：对话者称同批 IRC 服务器用 poll() 时数千客户端即占满 CPU，改用 FreeBSD 的 kqueue()/kevent() API 后 CPU 占用远低于 10%，并称规模最大的五个 IRC 网络中有四个的服务器软件在 FreeBSD 上偏好 kqueue()、其所在网络也期待 Linux 的 epoll()；Schwartz 回应称对方并未驳倒其论点，自己讨论的是可扩展性而非绝对性能，并承认 epoll 在各配置下都比 poll 更省 CPU，是 BSD kqueue 与 Linux epoll 性能对比进入内核社区讨论的一手材料 

<!-- ROW_MINE: lkml.messages.1932268 -->`
- 【Linux社区】kevent RFC 讨论中 Evgeniy Polyakov 以自制 HTTP 服务器 benchmark 直接对比 FreeBSD kqueue、Linux epoll、Linux kevent 与 kevent_poll 四者，httperf 客户端 30k 连接、3k burst、1 秒 burst 间隔：kevent >2600 rps，epoll 与 kevent_poll 1600-1800 rps，FreeBSD 6 默认参数下 kqueue 出现大量连接重置仅 62% 成功（疑配置不当）；kevent 首页附详细数据。Linux 事件通知机制与 FreeBSD kqueue 的量化对照。 

<!-- ROW_MINE: lkml.messages.5863808 -->`
- 【Linux社区】Florian Weimer 就 VM_DROPPABLE 补丁转引 Linus 对用户态 RNG 顾虑的驳斥，披露 glibc 在 Jason Donenfeld 反对用户态缓冲后改用 getrandom() 实现 arc4random，chrony 改链 glibc 版 arc4random 后 NTP 服务器每秒最大请求数实测下降约 25%（强调并非 arc4random 慢 25%，而是服务器整体性能影响）；指出 arc4random 的逆构缩写 A Replacement Call For random 本意是可放心使用而无性能之忧，并称 glibc 借 MADV_WIPEONFORK 获得进程 fork 保护（OpenBSD 的对应机制略有不同）。glibc 采用 OpenBSD arc4random 的量化代价证据。

- 【Linux社区】Mark Fortescue 在排查 sun4c 平台 SCSI 主机控制器无法识别设备的故障时，向 James Bottomley 说明他判断该问题不是硬件故障，理由是系统固件与 SunOS 4.1.1 在同一 ESP 控制器的同一磁盘上都能正常发现并访问设备，而在 Linux 2.6.21 之前的版本中也未观察到该问题，Linux 2.6.22 之后才变为必然复现。他还提到 V1 版 ESP SCSI 驱动在能启动到该阶段的内核上从未失败过，但对 V2 版驱动测试较少，因为 2.6.21 之后的内存问题需要先修复才能跑起来。该条目直接记录了在同一 sparc 硬件上以固件与 SunOS 作为对照组来判定 Linux 回归来源的排查方法。 `
