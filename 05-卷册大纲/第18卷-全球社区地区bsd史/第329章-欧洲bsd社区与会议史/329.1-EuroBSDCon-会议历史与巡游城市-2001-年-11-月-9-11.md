**要点**：

- Allan Jude 的 FreeBSD 网络排查文章经同行对谈展开：以 ping 建立时延基线、以 iPerf3 做带宽测量（JSON 输出便于进入自动化流水线）、以 netstat 的计数器定位丢包与错误并验证单测行为、以 systat -ifstat 补足无进度条的传输观察；卫星等高时延链路需放大缓冲，且测量工具自身也可能出错——Linux 与 FreeBSD 的 iPerf3 统计口径版本错位曾造成假性性能差距。（BSD Now EP396，[314.6-821.57]，L1）
- The Register 专访 John Baldwin 与 Ed Maste 综述 FreeBSD 13：历时约十年、经多届开发者峰会推动的 GCC 至 Clang/LLVM 工具链迁移至此完成（MIPS 等 tier-2 架构的 GCC 移出主干树），FreeBSD 对 LLVM 的集成改动同时回流上游；版本要点还包括 Foundation 资助的 bridge 提速、ISP 资助的 PF 改进、面向 Netflix 场景的内核 TLS 与切换至 OpenZFS 上游树；Baldwin 强调 BSD 许可证使 FreeBSD 成为厂商构建 appliance 的工具箱，且从未导入任何 GPLv3 工具链。（BSD Now EP396，[912.85-1358.06]，L2）
- Florian Obser 将 dhcpleased（IPv4 DHCP 客户端守护进程）与 dhcpleasectl 导入 OpenBSD：沿用项目特权分离设计，解析不可信数据的 engine 进程被 pledge 限制至标准 IO、无法访问文件系统与外界，配合 ifconfig autoconf4 与 hostname.if 常驻运行，与 SLAACD 共同构成统一的地址获取模型，被认为显著缩小了主机的攻击面。（BSD Now EP396，[1416.9-1571.22]，L2）
- Adrian de Groot 记录在 bhyve 中运行 Calamares 等 Linux 发行版安装器的完整链路：UEFI 固件经 Rebecca Cran 修复后恢复速度，图形依赖 VNC（需注意客户端与服务端兼容，TigerVNC 表现最佳），组网依赖 tap 接口入 bridge 并设置 net.link.tap.up_on_open，盘后端可用 ZFS 数据集；作者测试了 19 个 VNC 客户端中的 6 个并给出兼容性对照表。（BSD Now EP396，[1575.4-1958.42]，L2）
- Colin Percival 为 FreeBSD/EC2 补充两项特性：EFS 自动挂载（依托 automounter 与 Rick Macklem 此前打通的 NFS over EFS，仅需 auto_master 配置即可透明挂载）与 EBS NVMe ID（新增 /dev/aws/disk 树，把 EC2 API 指定的设备名映射到实际 NVMe 设备）；他说明这项多年业余维护依赖 Patreon 资助才能持续。（BSD Now EP396，[1988.66-2245.84]，L1）
- NYC*BUG 公布的早期 USENIX 会议照片引发社区影像史料保存讨论：照片既是口述史的辅助材料，也暴露了链接失效、人物无法辨识等数字化保存问题；主持人提醒当下 BSD 会议影像若无标注，十年后同样无人可识。（BSD Now EP396，[2250.38-2457.84]，L2）
- JT 自述进入 BSD 的路径：他本是 Linux 用户，因家庭朋友为免当技术支持而故意安装自己不懂的 Slackware 而留在 Linux 阵营，后在 Southeast Linux Fest 结识 Ken Moore 并协助把 Lumina 桌面移植到 Linux，又因 Linux 与 BSD 之间 Qt 版本差异导致双方 bug 无法互现，遂改用与 Ken 相同的 PC-BSD 做 bug 测试，随后经历 PC-BSD 更名 TrueOS，最终在开发者峰会上被 iXsystems 聘用开发后来成为 TrueCommand 的产品。（BSD Now EP382，[509.42-667.44]，L1）
- 被问及能否在 OpenBSD/FreeBSD 硬件上制作整期节目时，主持人坦言当时并非如此：Benedikt 用 Mac、JT 用 Windows 游戏机；合成可用 OBS 替代、录音用 Audacity，但 JT 的编辑工具 DaVinci Resolve 依赖硬件 dongle 许可、未必能在 BSD 上运行；如今节目改为纯音频、不再发布视频，改用 FreeBSD 已更可行，只是维持“打开即录、录完即关”的低摩擦流程是节目连续播出七年的关键。（BSD Now EP382，[676.38-884.42]，L1）

- Benedikt 回忆其文档贡献与相识路径：2012 年首次 BSDCan 几乎未结识他人，次年受邀加入 doc working group，在前往 BSDCan 的四小时火车上写出替换旧 ZFS 章节的初稿并自学 DocBook，2014 年由 Benedikt 授予 commit bit；BSD Now 于 2013 年夏开播，首件大事是 EuroBSDCon Malta 的现场采访，其中包括与 Poul-Henning Kamp 及 Matt Ahrens 的访谈，后者因麦克风 USB 线约两分钟即松脱而未录下任何内容。（BSD Now EP382，[1028.54-1344.16]，L1）

- 硬件收藏与旧企业设备的再循环：JT 收藏大量二手服务器（HP blade center、三台 HPC 7000、Sun 280R、Dell 与 IBM 1U），地下室总计过半 PB 存储却不足 200 核；他想拿 2011 年的八路 HP DL980（80 核 160 线程、空载 1kW、满载 2.7kW）与 64 核 Threadripper 做十年能效对照，展示社区对淘汰企业硬件的持续消化。（BSD Now EP382，[3532.84-3728.76]，L1）

- Xenocara 的起源：因 X 窗口系统上游实现项目变更许可证条款、且旧名称已成商标，OpenBSD 一度考虑自行 fork 并另起新名；开发者 Matthieu Herrb 借清洁鱼缸玻璃的小鱼学名造出 Xenocara 一词（以 X 开头，呼应 OpenBSD 以鱼类命名的传统）。最终项目决定不 fork 而跟随 X.org，Xenocara 遂成为既有做法的正式名称——为把 X 作为 OpenBSD base 系统的一部分而设的构建系统（X 不经 ports 与包系统分发）。　[存疑脚注] 转写将许可证变更写作 X386 许可证与 David Davis，通行记载为 XFree86 许可证争议，人名与项目名待核。（BSDTalk EP221，[80.04-161.60]，L1）
- Xenocara 的实质是构建封装而非分叉：它按依赖顺序对超过 250 个 X.org 模块调用 configure、make、make install；因 X 属于 base 系统，构建不得依赖外部工具——Mesa 构建系统过深依赖 GNU make 与 Python，OpenBSD 遂将预生成文件作为源文件提交进 CVS 树，免除全体开发者构建时的 Python 与 GNU make 依赖；另有支持 Vax、Sparc 等旧平台的本地改动未上游化。（BSDTalk EP221，[161.60-213.88]，L1）
- X server 特权分离代码由 Herrb 于约十年前（2002-2003）实现，至今仍在 OpenBSD 正常工作，但因在 Linux、Solaris 等 X.org 支持平台上移植该代码缺乏足够兴趣——他本人无意独力承担，其他项目亦无人接手——始终以一组 diffs 形式存于 Xenocara 树内，未提交上游。（BSDTalk EP221，[214.12-251.72]，L1）
- KMS（内核模式设置）困境是当时 OpenBSD 图形栈的核心问题：X.org 驱动整体转向 KMS，而 OpenBSD 内核尚无 KMS 支持，使项目要么困于旧版驱动，要么另辟蹊径——开发者将源自 Linux KMS 驱动的模式设置代码回植用户态，为 Sandy Bridge 与 Ivy Bridge 芯片组维护自定义 Intel 驱动，以传统用户态 X 驱动方式运行，保住 3D 加速与 X 视频加速能力；受访者视向内核移植 KMS 为 X 的未来，也是去除 X 服务器额外特权（系统主要安全隐患之一）的前提。　[存疑脚注] 转写将两位开发者名记作 Owen Haysworth 与 Jonathan Gray，人名拼写待与源码提交记录核对。（BSDTalk EP221，[262.44-372.14]，L1）
- 对 Wayland 的评估：该项目由 Kristian Høgsberg 等人自零开始、面向 Linux 设计，深度依赖 Linux 特有内核接口（输入子系统尤甚）；模式设置部分因 BSD 拟采用类似 KMS 的内核接口而在理论上可移植，但 Wayland 开发者明确不愿构建操作系统无关抽象层，故移植到 BSD 近乎按其合成 API 思想重写，工作量巨大且尚无人启动；其理念（削减 X 开销、提升本地图形性能、经合成管理器以另一方式实现远程显示）是否根本正确、能否满足真实应用需求，受访者直言尚无把握，而 X 目前工作良好、使用无处不在。　[存疑脚注] Wayland 发起人名依转写为 Christian Huxberg，通行记载为 Kristian Høgsberg，待核。（BSDTalk EP221，[456.46-572.66]，L1）
- 构建系统的可移植性与线程议题：Xenocara 构建系统因刻意保持简单（仅是 autotools 流程的封装）而具备合理可移植性，已被 DPB（OpenBSD 分布式包构建器）用于在 ports 集群上并行构建 Xenocara 且无需改动其本身；X 内部多线程场景不多，但新版 Mesa 的 LLVMpipe 软件渲染驱动使用线程，rthreads 真线程将使其受益，前提是解决 LLVMpipe 对 LLVM 与 Clang 的依赖——像 FreeBSD 那样以 LLVM/Clang 构建 base 并非易事，因 LLVM 构建系统存在大量 base 系统所无的外部依赖。　[存疑脚注] 转写记作 Mark SP 的演讲者疑为 DPB 作者 Marc Espié，待核。（BSDTalk EP221，[374.68-448.84]，L1）
