## 第一章 引用回溯系统（Phase 34）

### 1.1 设计目标与思想层挂钩

引用回溯系统的目标是让全书每一句正文都可被机器与人工沿链追溯至原始史料实体：**Sentence（正文语句）→ Claim（历史主张）→ Evidence（证据条目）→ Source（来源描述）→ Original Document（原始史料实体）**。

思想层依据：

- lishidagang.md §3.2.1 使用规范："每条事实性陈述标注史料来源：来源类型（一手/二手）+ 获取方式（数据库/网址/文件路径）+ 时间戳。"——三元组标注是本系统的最低要求，五层链是其结构化升级。
- dagang.md 总纲 2 推论：关于历史的形式主义记录"构成了形式主义重构的'硬边界'"。Original Document 层即硬边界的机器可读形态：任何 Claim 的合法性最终由其能否挂接到 Original Document 决定（P5、P12）。
- dagang.md §4.1 映射表"非存在 → 史料透明 → 标注每条事实的史料来源与可信度"：回溯链是"史料透明"操作原则的完整制度化（P37）。
- lishidagang.md §2.5.2c 矛盾仲裁规则（层级优先 → 时间优先 → 并置 → 同步修正）直接落为链内冲突处理状态机（见 1.3.3）。
- lishidagang.md 标准 1（史实准确）与 P53（三次复查）：断链检测规则是标准 1 的可执行核查器。

### 1.2 五层对象的精确定义与粒度边界

#### 1.2.1 层级定义表

| 层 | 定义 | 粒度边界 | 示例 |
| -- | ---- | -------- | ---- |
| L1 Sentence | 正式书稿（或大纲字段文本）中承载陈述的最小语句单位 | 一个陈述句（或语义完整的句群）；**不是**语法句子——用分号连接的两个并列史实应拆为两个 Sentence；一个含因果连接的复句若含两个可独立证伪的陈述，亦拆为两个 | "1994 年 6 月，CSRG 发布 4.4BSD-Lite，其中删除或重写了所有受 USL 版权主张约束的代码。" |
| L2 Claim | 可独立证伪的历史主张，是回溯链的**枢纽层** | 一个主张 = 一个可被证据支持或推翻的命题；**不是**观点、修辞或过渡句——"由此可见""值得注意的是"类语句不产生 Claim；一个 Sentence 可含 0-N 个 Claim（0 个的 Sentence 属叙事连接组织，登记但豁免建链，见 1.3.4） | "4.4BSD-Lite 发布于 1994 年 6 月"（事实主张）；"USL 诉讼压力是 4.4BSD-Lite 发布的直接动因"（因果主张） |
| L3 Evidence | 支撑或反驳某一 Claim 的一条具体证据内容 | 一条证据 = 一段可引用的原始内容摘录 + 其出处指向；**不是**来源本身——同一来源的不同段落是不同 Evidence；证据必须附原文摘录（quote）而非仅指针 | "4.4BSD-Lite 发布公告写道：'This release contains no AT&T code…'"（摘录自发布公告原文） |
| L4 Source | 对证据出处的书目性/档案性描述 | 一个 Source = 一份可被多次引用的出版物/档案集合/邮件列表/仓库；**不是**物理文件——同一 Source 可对应多个 Original Document 实体 | "CSRG 4.4BSD-Lite Release Notes（1994）"；"FreeBSD 邮件列表归档 freebsd-announce" |
| L5 Original Document | 史料实体：实际留存的记录物 | 一个实体 = 一封邮件、一次 commit、一份 tarball 中的一份文件、一篇论文 PDF、一段采访录音的转写稿；粒度以"独立的、带时间戳的留存单位"为准 | "`03-原始史料库/13-44doc文档史料/` 中 4.4BSD-Lite 发布公告文件"；"1993-06-XX McKusick 在 freebsd-announce 的公告邮件（message_id: …）" |

#### 1.2.2 粒度裁决规则（边界争议的判定顺序）

1. **证伪单元规则**：若两段内容可以一真一假，它们必须分属不同 Claim。
2. **摘录完整规则**：Evidence 的 quote 必须长到可脱离上下文理解（不少于原文相关完整段落或完整邮件引段），禁止摘半句。
3. **实体独立规则**：Original Document 以"独立时间戳 + 独立作者/产生机制"为判准；一次 git commit 是一个实体，一个仓库不是一个实体（仓库是 Source）。
4. **层级不可跳挂规则**：Sentence 不得直接挂 Evidence（必须经 Claim）；Evidence 不得直接挂 Original Document 而跳过 Source（必须经 Source）——这是保证书目层可独立审计的关键。

#### 1.2.3 标识符方案（ID 命名规则）

| 层 | 前缀 | 格式 | 示例 |
| -- | ---- | ---- | ---- |
| Sentence | `S` | `S-V{卷3位}C{章3位}.{节}-{句序号3位}` | `S-V002C042.3-017` |
| Claim | `C` | `C-{6位流水}` + 可选语义助记 `C-000123[usl-settle-date]` | `C-000123` |
| Evidence | `E` | `E-{7位流水}` | `E-0004567` |
| Source | `SRC` | `SRC-{类型码}-{4位流水}`，类型码：`ARC`（档案/史料库文件）`ML`（邮件列表）`GIT`（代码仓库）`PUB`（出版物）`WEB`（可溯源网页，需白名单） | `SRC-PUB-0089` |
| Original Document | `OD` | `OD-{来源库码}-{原库主键}`，来源库码：`OSDB`（original_sources.db）`MLDB`（6 个邮件列表库）`GITDB`（11 个代码仓库库）`RFT`（references_fulltext.db）`RN`（research_notes.db）`FS`（未入库的文件系统实体） | `OD-MLDB-freebsd-announce-199406-0023` |

规则：

- 全链 ID 一经分配不得复用；对象被废弃时置 `status='retired'` 并记入 update_log，ID 永久保留。
- OD-ID 优先复用既有数据库主键（02-数据库盘点确认各库均以 files/blocks 主键 + sha256 定位），避免平行编号漂移。
- 跨库 OD 一律带来源库码前缀，解决 cross_db_references.csv 悬空引用的历史教训（02-数据库盘点 1.1 节：全仓 13 条跨库引用中 7 条指向不存在的 `bsd_commits` 库）。

#### 1.3.2 五层对象表 DDL

```sql
-- L1 正文语句
CREATE TABLE sentences (
  id              TEXT PRIMARY KEY,               -- S-V002C042.3-017
  volume          INTEGER NOT NULL,               -- 卷号 1-12
  chapter         INTEGER NOT NULL,               -- 跨卷连续章号 1-181
  section         TEXT NOT NULL,                  -- 节号 N.N 或概述/卷首
  sentence_index  INTEGER NOT NULL,               -- 节内序号（自 1）
  text            TEXT NOT NULL,                  -- 语句全文
  sentence_role   TEXT NOT NULL DEFAULT 'claim_bearer'
                  CHECK(sentence_role IN ('claim_bearer','narrative_tissue',
                       'quote_display','heading','transition')),
  text_sha256     TEXT NOT NULL,                  -- 语句指纹，改句必留痕
  status          TEXT NOT NULL DEFAULT 'draft'
                  CHECK(status IN ('draft','frozen','retired')),
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL,
  created_by TEXT NOT NULL,
  UNIQUE(volume, chapter, section, sentence_index)
);

-- L2 历史主张（枢纽层）
CREATE TABLE claims (
  id              TEXT PRIMARY KEY,               -- C-000123
  claim_text      TEXT NOT NULL,                  -- 命题陈述（规范句式，见下）
  claim_type      TEXT NOT NULL CHECK(claim_type IN (
                    'factual',        -- 事实主张（时间/人物/版本号/事件）
                    'causal',         -- 因果主张
                    'interpretive',   -- 解释/定性主张
                    'evaluative',     -- 评价主张（受禁用叙事约束最严）
                    'counterfactual', -- 反事实主张（五段式第 6 段）
                    'priority',       -- 首次/最早类主张
                    'motive')),       -- 动机归因
  claim_status    TEXT NOT NULL DEFAULT 'open' CHECK(claim_status IN (
                    'open','supported','contested','suspended','refuted','retired')),
  requires_rebuttal INTEGER NOT NULL DEFAULT 0,   -- 触发强制反驳=1（见第三章）
  rebuttal_id     TEXT,                           -- 指向 objections 表
  principle_refs  TEXT,                           -- 所依据的编纂原则，如 'P15,P48'
  chapter_scope   TEXT,                           -- 主要所属章，如 'V02C42'
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL, created_by TEXT NOT NULL
);

-- L3 证据条目
CREATE TABLE evidence (
  id              TEXT PRIMARY KEY,               -- E-0004567
  claim_id        TEXT NOT NULL REFERENCES claims(id),
  evidence_role   TEXT NOT NULL CHECK(evidence_role IN ('support','refute','context')),
  quote           TEXT NOT NULL,                  -- 原文摘录（禁摘半句，见 1.2.2）
  quote_lang      TEXT NOT NULL DEFAULT 'en',
  paraphrase      TEXT,                           -- 中文转述（可选，须与 quote 一致）
  source_id       TEXT NOT NULL REFERENCES sources(id),
  locator         TEXT,                           -- 实体内定位：页码/段落/message_id/commit hash/文件路径
  tier            INTEGER NOT NULL CHECK(tier BETWEEN 1 AND 5),  -- 史料五层级
  evidence_grade  TEXT,                           -- 证据等级，Phase 28 接口（见 1.4）
  grade_source    TEXT NOT NULL DEFAULT 'reserved-phase28',
  extraction_note TEXT,                           -- 摘录方式说明（OCR/原文/转写）
  created_at TEXT NOT NULL, created_by TEXT NOT NULL
);
CREATE INDEX idx_evidence_claim ON evidence(claim_id);
CREATE INDEX idx_evidence_source ON evidence(source_id);

-- L4 来源描述
CREATE TABLE sources (
  id              TEXT PRIMARY KEY,               -- SRC-PUB-0089
  source_type     TEXT NOT NULL CHECK(source_type IN (
                    'archive','mailing_list','repo','publication','web_sanctioned')),
  title           TEXT NOT NULL,
  creator         TEXT,                           -- 作者/产生机构
  date_text       TEXT,                           -- 原始日期文本（'1994-06'）
  date_iso        TEXT,                           -- 规范化 ISO（'1994-06'）
  location        TEXT,                           -- 本地路径或 URL
  location_kind   TEXT NOT NULL CHECK(location_kind IN (
                    'local_db','local_file','url','mixed')),
  db_name         TEXT,                           -- 所在 SQLite 库名（若有）
  gbt7714         TEXT,                           -- GB/T 7714-2015 著录全文
  reliability_note TEXT,
  created_at TEXT NOT NULL, created_by TEXT NOT NULL
);

-- L5 原始史料实体
CREATE TABLE original_documents (
  id              TEXT PRIMARY KEY,               -- OD-MLDB-freebsd-announce-199406-0023
  source_id       TEXT NOT NULL REFERENCES sources(id),
  doc_kind        TEXT NOT NULL CHECK(doc_kind IN (
                    'email','commit','tarball_file','doc_file','paper','transcript',
                    'meeting_minutes','photo','binary_artifact','other')),
  title           TEXT NOT NULL,
  producer        TEXT,                           -- 作者/提交人
  created_date    TEXT,                           -- 实体产生时间（ISO，可粗粒度）
  archive_path    TEXT,                           -- 本地归档路径
  archive_db      TEXT,                           -- 所在库名（与 OD 前缀一致）
  archive_key     TEXT,                           -- 原库主键（files.id / messages.id / commits.id）
  sha256          TEXT,                           -- 实体内容指纹（如有数字载体）
  retrieved_at    TEXT,                           -- 获取时间（P52 三元组之时间戳）
  tier            INTEGER NOT NULL CHECK(tier BETWEEN 1 AND 5),
  status          TEXT NOT NULL DEFAULT 'active' CHECK(status IN ('active','lost','retired')),
  note            TEXT,
  created_at TEXT NOT NULL, created_by TEXT NOT NULL
);
CREATE INDEX idx_od_source ON original_documents(source_id);
```

Claim 规范句式要求：`claim_text` 必须写成可独立检验的命题（主语+谓语+可核验谓项），禁止含"大概""显然"等副词；因果主张必须显式写出原因项与结果项（与 Phase 9-11 因果链系统的因果三元组接口对齐，见第五章）。

#### 1.3.3 层间关系表与冲突处理 DDL

```sql
-- Sentence-Claim 多对多（一句话可支撑多个 Claim）
CREATE TABLE sentence_claims (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  sentence_id TEXT NOT NULL REFERENCES sentences(id),
  claim_id   TEXT NOT NULL REFERENCES claims(id),
  support_mode TEXT NOT NULL CHECK(support_mode IN (
                 'assert','cite','concede','contrast')),  -- 断言/转述他人/让步/对照陈述
  UNIQUE(sentence_id, claim_id)
);

-- Claim-Evidence 已由 evidence.claim_id 承载（一证据单挂一主张）；
-- 同一原文支撑多主张时，登记多条 evidence（quote 可相同，claim 不同），
-- 由 (quote, source_id, locator) 上的查重视图提示录入者复用而非重复抄写。

-- 证据冲突登记
CREATE TABLE evidence_conflicts (
  id            TEXT PRIMARY KEY,                 -- CF-00012
  claim_id      TEXT NOT NULL REFERENCES claims(id),
  evidence_a_id TEXT NOT NULL REFERENCES evidence(id),
  evidence_b_id TEXT NOT NULL REFERENCES evidence(id),
  conflict_kind TEXT NOT NULL CHECK(conflict_kind IN (
                  'contradiction',   -- 直接矛盾（X vs 非X）
                  'date_discrepancy',-- 日期分歧
                  'attribution_discrepancy')), -- 归属/署名分歧
  state         TEXT NOT NULL DEFAULT 'suspended' CHECK(state IN (
                  'suspended','adjudicated','coexist')),
  adjudication  TEXT CHECK(adjudication IN ('prefer_a','prefer_b','coexist')),
  reason        TEXT,                             -- 裁决理由（引仲裁顺位）
  decided_by    TEXT,
  decided_at    TEXT,
  CHECK (evidence_a_id <> evidence_b_id)
);
CREATE INDEX idx_conflict_claim ON evidence_conflicts(claim_id);
```

#### 1.3.4 链完整性规则与断链检测

**建链完整性规则**（写入流程强制，见 1.5）：

| 编号 | 规则 | 例外 |
| ---- | ---- | ---- |
| R-C1 | 每个 `claim_bearer` 型 Sentence 至少挂 1 个 Claim | `narrative_tissue`（过渡、场景描写）豁免，但须登记 sentence_role 供叙事审查（第四章）抽查 |
| R-C2 | 每个 Claim 至少挂 1 条 `support` 型 Evidence | 无——无证据的主张禁止入稿 |
| R-C3 | 每条 Evidence 必须挂 1 个 Source，且该 Source 至少挂 1 个 Original Document | 纯背景解释性转述不产生 Evidence |
| R-C4 | Evidence.tier、Original Document.tier、Source 类型三者一致性校验（邮件列表实体不得标为第一层级） | 无 |
| R-C5 | `support_mode='assert'` 的 Claim 不得只挂第四、五层级史料而无第一至三层佐证 | 存疑标注 `[存疑脚注]` 后允许（P53："不得默认为确证"——此时 claim_status='suspended'） |
| R-C6 | `priority`/`motive` 型 Claim 一律 `requires_rebuttal=1`（第三章触发器） | 无 |

**断链检测**：SQL 审计脚本（固定脚本位置：`00-编纂规则与格式规范/01-规则/脚本与命令/trace_chain_audit.py`，遵循 CLAUDE.md 脚本规则）每章交付时运行，检测并报告：

1. 断链类型 A：`claim_bearer` 句无 Claim（违 R-C1）；
2. 断链类型 B：Claim 无 support 证据（违 R-C2）；
3. 断链类型 C：Evidence 无 Source，或 Source 无 Original Document（违 R-C3，即"证据悬空"）；
4. 断链类型 D：层级不一致（违 R-C4）；
5. 断链类型 E：OD 指针悬空（archive_key 在目标库查无，对应 02-数据库盘点的悬空跨库引用病灶）；
6. 断链类型 F：冲突未决（evidence_conflicts.state='suspended' 超过本章冻结日）。

**报告格式**（归档至 `08-核查报告与多轮复核/链审计报告/YYYYMMDD_断链审计_V{卷}C{章}.md`）：

```markdown
# 断链审计报告 V02C42（2026-08-12）
- 本章 Sentence 总数：N；Claim 总数：N；完整链占比：X%
- A 类断链：N 条（清单：S-…, S-…）
- B 类断链：N 条（清单：C-…, C-…）
- C/E 类断链：N 条（清单含缺失层）
- 未决冲突：N 项（清单：CF-…）
- 结论：【可进入审稿 / 阻断——须修复后重审】
- 豁免登记：narrative_tissue 句 N 句（占比 Y%，超 15% 触发叙事审查复核）
```

阻断阈值：A+B 类断链为 0 方可进入审稿；C/E 类存量 ≤ 2% 且全部有修复工单；豁免句占比 ≤ 15%。

#### 1.3.5 冲突处理状态机（挂钩 lishidagang.md §2.5.2c 矛盾仲裁）

冲突三状态及其转换：

```
        发现矛盾
          │
          ▼
      [suspended]（挂起：两证据并录，Claim 标 contested，正文暂缓采信任一方）
          │
          ├─ 仲裁可行？按 §2.5.2c 四步顺位：
          │    1. 以低形式主义程度史料为准（tier 小者胜）
          │    2. 层级相同以更早史料为准（created_date 早者胜）
          │    3. 仍无法判定 → 转 [coexist]
          │    4. 裁决成立 → [adjudicated]，reason 字段记录顺位依据，
          │       并触发"所有涉及卷章同步修正"义务（写入 update_log + 生成修正工单）
          ▼
      [coexist]（双说并存：正文取层级最高版本为主要叙述，
                 其余版本入脚注/"辨析"字段，不给定论——lishidagang.md §3.2.4；
                 Claim 保持 contested，永久保留两链）
```

**与既有存疑体系的分工**：事实登记层（本表 + 项目参数卡）执行仲裁制，叙事呈现层执行并置制——本机制即 01-编纂原则清单 T8 张力的操作化落点（T8 处理建议："参数卡/事实层=仲裁制；正文辨析层=并置制"）。仲裁后仍无法判定的，按 P53 标注 `[存疑脚注]`，同步在 `04-现代研究文献/06-存疑数据库/doubts_standalone.db` 登记存疑条目（接口见第五章）。

### 1.4 与史料五层级模型的挂钩

每条 Evidence 与每个 Original Document 强制标注两个维度：

**(a) 史料层级 `tier`**（lishidagang.md §1.2.1，P41）：

| tier | 类型 | doc_kind 对应 | 使用原则 |
| ---- | ---- | ------------- | -------- |
| 1 | 代码与构建产物 | commit / tarball_file / binary_artifact | 最高可信度，优先使用 |
| 2 | 即时通讯记录 | email / meeting_minutes（即时记录型） | 核心史料，邮件须追踪讨论串全程（P42） |
| 3 | 官方文档与公告 | doc_file（Release Notes/安全公告/手册页） | 经编辑筛选，中等 |
| 4 | 事后叙述 | transcript / paper（演讲、采访、回忆录） | 引用须带保留语气 |
| 5 | 二手研究 | paper / publication | 不得作唯一来源（P41 使用原则） |

**(b) 证据等级 `evidence_grade`**：Phase 28（证据等级系统）另行设计评级标准。本系统预留接口：`evidence.evidence_grade TEXT` + `evidence.grade_source TEXT`，Phase 28 交付后以 UPDATE 批量回填，并以 schema_meta 记录评级标准版本号；回填前一律为 `'reserved-phase28'`。禁止本阶段擅自发明等级词表——避免与 Phase 28 重复设计后被迫迁移。

**层级与断链规则联动**：R-C5 规定纯四五层级证据链的 Claim 自动进入 suspended；矛盾仲裁顺位（1.3.5）直接以 tier 为第一判据。这两条使五层级模型从"写作建议"变为数据库层的硬约束。

#### 1.5.1 规模估算

以 350-400 万字、12 卷 181 章（冻结基准）为基数：

| 层 | 估算依据 | 量级 |
| -- | -------- | ---- |
| Sentence | 中文陈述句均长约 35-45 字，350 万字 ≈ 85-100 万句；其中 claim_bearer 约 55-60%（余为 narrative_tissue/引文/标题） | **约 50-60 万** |
| Claim | 平均每 claim_bearer 句 1.1-1.3 个主张 | **约 55-75 万** |
| Evidence | 每 Claim 平均 2-3 条（含 support/refute/context） | **约 130-200 万** |
| Source | 每 Evidence 平均 1.5-2 条来源（一源多证） | **约 20-30 万** |
| Original Document | **关键控制点**，见下 | **目标 ≤ 8 万** |

**OD 层不爆炸的设计**：3.16M 封邮件库（CLAUDE.md）若逐封建 OD 将产生数百万条实体。控制规则：OD 只登记**实际被引用**的实体；未被任何 Evidence 引用的邮件不建 OD，仅在 Evidence.locator 中以 `(db_name, message_id)` 外部指针形式挂接 MLDB，待首次被引用时转正为 OD。按每章平均引用 150-250 个实体、181 章估算，OD 总量约 3-5 万，SQLite 单库可承受（02-数据库盘点实测 references_fulltext.db 已达 1.19GB 仍完整可用）。

SQLite 容量预估：全链约 300-380 万行、行均 0.6-1.2KB，traceability.db 预计 3-6GB——与 references_fulltext.db 同量级，按"数据库操作加速规则"（CLAUDE.md）建索引、关闭 WAL 长事务即可。

| 批次 | 范围 | 目的 |
| ---- | ---- | ---- |

#### 1.5.3 最小可行单元与正文强制同步建链流程

最小可行单元 = **一章的完整闭环**：正文（或大纲字段文本）→ 全句登记 → 全链建成 → 断链审计通过 → 交付审稿。先在第 42 章上跑通，产出验收演示（1.6 节）。

**强制同步建链流程**（正文撰写任务的标准作业程序，SOP）：

1. **领取**：撰写 agent 领取章节任务时，同时领取本章的 Sentence ID 段（预分配）与本章参数卡（P61）。
2. **写一句，挂一链**：正文撰写时以"语句块"为单位提交——每个语句块写入 sentences 表的同时提交其 Claim 清单；禁止"先写完全章再补链"（补链模式下 Evidence 易被反向裁剪以迁就正文，违反 P5 硬边界原则）。
3. **Evidence 当场摘录**：Claim 的 Evidence 必须在撰写当场完成原文摘录（quote），摘录动作即考据第一轮（P53）；第二轮交叉验证与第三轮判定在章级复核时完成。
4. **章末自检**：撰写 agent 运行 `trace_chain_audit.py`，A/B 类断链清零后方可提交；C/E 类带工单提交。
5. **复核 gate**：章级审稿（第四章）以断链审计报告为前置文件；无报告或 A/B 类断链非零的章节直接退回，不进入内容审查。

E-0004567  claim_id=C-000123  evidence_role=support

SRC-PUB-0089  source_type=publication

  location_kind=url（须入 web_sanctioned 白名单）

```

**L5 Original Document**

```
OD-FS-44doc-lite-announce-0001
  source_id=SRC-ARC-0031  doc_kind=doc_file

#### 示例链二：诉讼与分叉的因果链（含反对方证据）

**L1 Sentence**

```
id: S-V004C061.2-004
text: "USL 对 BSDi 的诉讼及其引发的法律不确定性，是 FreeBSD 项目在 1993 年从 386BSD 社区中分离出来的直接触发条件之一。"
sentence_role: claim_bearer
```

**L2 Claim**

```
C-000201  claim_type=causal
  claim_text="USL v. BSDi 诉讼造成的法律不确定性是 FreeBSD 于 1993 年自 386BSD 社区分离的直接触发条件之一"
  claim_status=supported  requires_rebuttal=1（因果主张，第三章触发器）
  principle_refs="P14,P15"（分离聚合循环；偶然性优先——注意"之一"措辞，拒绝单一原因，lishidagang.md §2.3.1 分析段）
```

**L3 Evidence**（正反俱录）

```
E-0005101  claim_id=C-000201  evidence_role=support  tier=2
  quote:（FreeBSD 项目早期公告邮件中关于分叉背景的陈述，实施时摘录）
  source_id=SRC-ML-0003（freebsd-announce 列表归档）
E-0005102  claim_id=C-000201  evidence_role=support  tier=1
  quote:（早期 FreeBSD 仓库中引用 386BSD patchkit 与法律免责声明的首批 commit，实施时摘录）
  source_id=SRC-GIT-0001（FreeBSD 代码仓库史料库）
E-0005103  claim_id=C-000201  evidence_role=refute  tier=4
  quote:（事后叙述中将分叉动机归于技术分歧而非法律压力的说法，实施时摘录）
  source_id=SRC-PUB-0102
```

**冲突处理演示**：E-0005102（tier 1）与 E-0005103（tier 4）构成 attribution_discrepancy；按仲裁顺位 1（低形式主义程度者优先），裁决 prefer 支持链，但 E-0005103 不删除——按 §3.2.4 在正文"辨析"字段并置呈现（"另有事后叙述将动机归于技术分歧，见……"），Claim 保持 supported 且残余风险入第三章反驳记录。

**L4/L5**：

```
SRC-ML-0003 → OD-MLDB-freebsd-announce-1993-XXXX（邮件实体，tier=2）
SRC-GIT-0001 → OD-GITDB-freebsd-commit-XXXXXX（commit 实体，tier=1）
SRC-PUB-0102 → OD-RFT-XXXX（事后叙述文献实体，tier=4）
```

两链演示了系统的两个关键能力：**一句多 Claim 的证伪粒度控制**（链一）与**因果主张的正反证据并录加层级仲裁**（链二）。

## 第二章 AI 角色分离系统（Phase 35）

### 2.1 设计目标与思想层挂钩

任务书要求：至少使用四种角色（Researcher / Historian / Skeptic / Editor），**禁止同一个生成任务同时承担四种角色**。**新版编纂总纲 §6 铁律**："禁止 资料→AI→正文。四个角色必须分离执行。"——本系统的十步链与四角色分离流程即为该铁律的制度化落地方案。

思想层依据：

- dagang.md §1.2.3 三重形式主义化模型（P43）：认识经事件、记录、重构三重加工，任何单一视角都宣称自己走完了全程即"客观"幻觉；角色分离是把三重加工拆给不同主体执行，使每一重的形式主义性质可见。
- dagang.md 总纲 8 多方平等（P18）：Skeptic 与 Historian 在本体论上地位均等——攻击角色不是"辅助"角色，其产物与起草产物同等进入回溯链。
- dagang.md §3.2 "反对得好就不是形式主义"：Skeptic 的攻击只有真实执行（有证据、有产物、有权退回）才不是形式主义。
- 同源互证准则（P3）：指导思想源材料（教材前言哲学段落）不得作为史料——角色分离在流程上落实这一隔离：Researcher 的证据清单中禁止出现 sacred_sources.db 条目，由交接清单的禁入项强制检查。
- lishidagang.md §4.4 六项编纂技能：角色分离与技能分工同构——Researcher 承担史料辨识与考据留痕（技能 a/b），Historian 承担叙事建构与分析论证（技能 c/d/e），Skeptic 承担自反性思维（技能 f），Editor 承担可读性（标准 10）。

### 2.3 任务隔离机制

"同一生成任务不兼任四角"的四重保证：

**(a) 会话隔离**：四角色由四个独立会话/独立 agent 实例执行，会话上下文互不共享。技术上即本项目现行多 agent 结构（每角色一个 agent 进程）；若同一模型底座承担多角色，角色间不得复用会话记忆——角色 A 的上下文窗口内容不得作为角色 B 的输入，只允许经交接文件传递。

**(b) 提示词模板隔离**：四套模板（2.4 节）各自完整、互不引用对方的角色设定；每个 agent 启动时仅装载其一。模板中内置"角色越界自检问句"（见各模板尾部），模型在每次输出前自问是否越界。

**(c) 产物隔离**：每角色写各自的中间文件，路径与命名强制区分：

```
08-核查报告与多轮复核/角色产物/V{卷}C{章}/
├── R-{章号}-证据清单-{日期}.md          # Researcher 产物
├── R-{章号}-存疑清单-{日期}.md
├── H-{章号}-草稿-{日期}.md              # Historian 产物
├── K-{章号}-反驳清单-{日期}.md          # Skeptic 产物（K 取怀疑义，避免与 S=Researcher 源文件混淆）
├── E-{章号}-编辑意见-{日期}.md          # Editor 产物
└── handoff/                             # 交接清单（2.5 节格式）
```

**(d) 交接清单 gate**：角色间只经 handoff 文件传递信息，交接清单含"越界检查"项——接收方核验上游产物是否含越界内容（如证据清单中出现叙事句即退回 Researcher），不合格交接不启动。

### 2.6 与既有团队结构的映射

本项目当前即为多 agent 协作（ykla + topic-refiner / data-engineer / causal-analyst / lit-reviewer / robustness-auditor / academic-writer 等）。四角色是**叠加在既有结构上的工作流角色，不是新建的常设岗位**——同一 teammate 在不同任务阶段装载不同角色模板，但任一生成任务内只装载一个角色：

| 既有 teammate | 承担角色 | 说明 |
| ------------- | -------- | ---- |
| lit-reviewer | Researcher（主） | 其现行 Phase 18-19 反偏差审查中的检索职能即 Researcher 职能；Anti-Bias 产出（外部叙事对照矩阵）作为 Skeptic 的输入 |
| academic-writer | Historian（主） | 其现行 Phase 22/24-26 大纲生成与章节产出即 Historian 产出；受"禁止自行检索"约束 |
| robustness-auditor | Skeptic（主） | 其现行 Phase 4-5 审计与七维覆盖检查即 Skeptic 攻击职能的章级前移；断链审计（1.3.4）由其执行 |
| topic-refiner | Skeptic（原则维度）+ Historian（大纲阶段） | 原则清单维护者，负责 Skeptic 的"疑似违反原则清单"维度；大纲阶段兼任 Historian（大纲即叙事骨架） |
| causal-analyst | Skeptic（因果维度专职） | 所有 claim_type=causal 的反驳由 causal-analyst 以 Skeptic 模板执行；与 Phase 9-11 因果链系统对接 |
| data-engineer | 系统支撑（不装四角色） | traceability.db 建库、断链审计脚本、OD 指针核验 |
| team-lead（ykla） | 调度与裁决 | 掌握唯一跨级退回权；冲突仲裁的最终裁决（1.3.5）；不直接承担四角色任何之一 |

**不冲突论证**：既有结构按"职能分工"组建，四角色按"生成任务的工序分工"组建，两者正交——一个 teammate 先后承担不同角色不违反隔离（隔离的对象是"同一个生成任务"，不是"同一个 agent"）；隔离的硬判据是会话上下文与产物文件（2.3 a/c），而非人员身份。唯一需要 ykla 注意的风险：同一 teammate 连续承担 R 与 K（如 lit-reviewer）时，K 阶段的会话必须全新启动，不得携带 R 阶段上下文——否则 Skeptic 会不自觉地为自己收集的证据辩护。

### 3.1 设计目标与思想层挂钩

任务书要求：每个重要判断必须回答"如果错了，最强反驳是什么"。

思想层依据：

- dagang.md §3.1（P9）："自反性是区分'活的理论'与'死的理论'的标准。"强制反驳是书稿层面的自反性执行装置——不是事后免责声明，而是嵌入生产过程的"持续自觉"（lishidagang.md §4.4f，P58）。
- dagang.md 总纲 5（P15）：一切必然性表述都是事后建构——强制反驳的首要攻击对象就是草稿中的事后建构。
- lishidagang.md 标准 2"不回避争议——若存在学界/社区争议，须在'辨析'中呈现正反双方论点"：强制反驳产出的采纳部分直接进入"辨析"字段（P47）。
- 本方案 R-C6 规则（第一章）：priority/motive 型 Claim 自动 requires_rebuttal=1，本章给出其余触发类型与完整格式。

### 3.2 "重要判断"的判定标准（触发清单）

一个 Claim 满足下列任一条件即标记 `requires_rebuttal=1`，必须附强制反驳记录：

| 编号 | 触发类型 | 判定标准 | 对应 claims.claim_type | 典型示例 |
| ---- | -------- | -------- | ---------------------- | -------- |
| TR-1 | 因果主张 | 主张 A 导致/促成/触发 B（含"直接原因之一"弱化式） | causal | "USL 诉讼触发了 FreeBSD 分叉" |
| TR-2 | 转折点定性 | 把某事件定性为转折/分水岭/起点/终点 | interpretive | "4.4BSD-Lite 发布标志着 CSRG 时代的终结" |
| TR-3 | 人物动机归因 | 对历史行动者的动机、意图作归因 | motive | "Jolitz 夫妇开发 386BSD 出于个人兴趣而非商业规划" |
| TR-4 | 首次/最早类断言 | "第一个/最早/首次/首创"类优先权主张 | priority | "4.2BSD 是第一个原生集成 TCP/IP 的 UNIX 版本" |
| TR-5 | 评价性定性 | 对分支、人物、决策作优劣成败定性（受 P18/P11 约束最严的类型） | evaluative | "NetBSD 的跨平台策略在当时是可行的选择" |
| TR-6 | 反事实主张 | 五段式第 6 段"假如不"陈述 | counterfactual | "若 USL 不起诉，386BSD 可能不会失去开发者信任" |
| TR-7 | 结构性模式抽象 | 从多个事件抽象出模式（允许抽象，但不得叙述为历史规律，P58 技能 d） | interpretive | "每次版本控制工具更替都伴随话语权转移" |
| TR-8 | 沉默推断 | 对"未留下记录者"的立场作推断 | interpretive | "未参与讨论的 committer 默认接受了该决定" |

**豁免类型**：纯事实主张（factual）经三次复查确证且无冲突登记时豁免强制反驳（但其硬事实仍须两次独立核验，标准 1）。豁免判定记入 claims.rebuttal_id='EXEMPT-factual-verified'。

**防漏机制**：触发判定不依赖撰写者自觉——Historian 草稿提交时由断链审计脚本（1.3.4）对 claim_type 字段做机检，凡属 TR-1 至 TR-8 而 requires_rebuttal=0 的一律阻断并回退。关键词预扫描（"导致/使得/标志着/首次/天才/注定"）作为辅助手段提示撰写者正确标注 claim_type。

### 3.3 反对意见的结构化格式

每条强制反驳记录存入 traceability.db 的 `objections` 表：

```sql
CREATE TABLE objections (
  id              TEXT PRIMARY KEY,               -- OBJ-00045
  claim_id        TEXT NOT NULL REFERENCES claims(id),
  rebuttal_text   TEXT NOT NULL,                  -- 最强反驳陈述（完整、不缩写）
  strength        TEXT NOT NULL CHECK(strength IN ('S','A','B')),
                                          -- S=可独立推翻原主张；A=动摇但不足推翻；B=边缘质疑
  basis_kind      TEXT NOT NULL CHECK(basis_kind IN (
                    'evidence','interpretive','search_lead')),
                                          -- 有证据/纯解释性/仅为检索线索
  disposition     TEXT NOT NULL DEFAULT 'pending' CHECK(disposition IN (
                    'pending','accepted','partial','rejected')),
  disposition_reason TEXT,                        -- 采纳/部分采纳/驳回的理由
  residual_risk   TEXT,                           -- 驳回时的残余风险声明（驳回必填）
  text_placement  TEXT CHECK(text_placement IN ('main','footnote','analysis','omitted')),
                                          -- 反驳内容进入正文的位置
  decided_by      TEXT, decided_at TEXT,
  created_at TEXT NOT NULL, created_by TEXT NOT NULL  -- created_by 必为 Skeptic 角色
);
CREATE INDEX idx_objection_claim ON objections(claim_id);
```

**单条记录填充样式**（续第一章示例链二 C-000201）：

```
OBJ-00045
  claim_id: C-000201（"USL 诉讼是 FreeBSD 分离的直接触发条件之一"）
  rebuttal_text: "FreeBSD 核心发起者在分叉前后的邮件中反复讨论的是 386BSD 的
    开发流程问题（patchkit 管理、单一维护者瓶颈），而非法律风险；将分叉归因于
    诉讼是以今日对 USL 案重要性的认知倒灌当时当事人的关切（时间位置倒灌，
    原则清单问题 7-10）。"
  strength: A
  basis_kind: evidence（挂 E-0005103 及另外两条邮件串证据 E-ID）
  disposition: partial
  disposition_reason: "采纳'诉讼非唯一动因'部分——正文已将主张措辞限定为
    '触发条件之一'并增列技术流程动因；不采纳'诉讼无关紧要'部分——仲裁顺位
    以第一、二层证据（E-0005101/E-0005102）支持法律不确定性至少是必要条件。"
  residual_risk: "若日后发现 1993 年夏季核心邮件串中法律议题完全缺席的新证据，
    本主张应降级为背景条件；该邮件串现存档不全（P42 幸存者偏差），此缺口
    无法在现有史料内闭合。"
  text_placement: analysis（进入"分析"段多因素并陈 + "辨析"字段呈现反驳全文）
```

**处置规则**：

- `accepted`：反驳推翻或实质修正原主张——Historian 必须改写 Claim 措辞，claims 表记 update_log，正文同步；
- `partial`：部分采纳——正文保留原主张但限定措辞/增列其他因素，反驳全文入"辨析"字段；
- `rejected`：驳回——**必填 residual_risk**（残余风险声明），且反驳仍须以脚注或"辨析"形式在正文留痕（不给定论的诚实要求，P55）；`text_placement='omitted'` 仅在反驳强度为 B 且 ykla 批准时允许。

### 3.4 与引用回溯系统的挂钩：反驳也是 Claim

**反稻草人规则**：反对意见本身也是历史主张，必须受同一套证据纪律约束——

1. `basis_kind='evidence'` 的反驳：反驳所依据的材料必须作为 Evidence 登记（evidence_role='refute'，挂被攻击的 claim_id），进入完整五层链。Skeptic 不得引用未登记的"常识"作证据性反驳。
2. `basis_kind='interpretive'` 的反驳（纯解释性质疑，如"这个因果归因忽略了共因可能"）：允许，但强度上限为 A，且 disposition_reason 中必须说明为何解释性质疑成立；若后续 Researcher 检得实证，升级为 evidence 型。
3. `basis_kind='search_lead'` 的反驳：Skeptic 提出"应当存在但未见"的史料线索（如"应查 NetBSD 侧同期邮件"），本身不评级，直接转为 Researcher 检索工单；工单结果回流后反驳重新定级。
4. **强度评级与证据层级联动**：反驳证据的最高 tier 不得高于原主张证据的最高 tier 才能评 S 级——防止用第五层二手研究"推翻"第一层代码证据的伪反驳（P41 层级采信原则在反驳方向的镜像适用）。

此规则堵住的漏洞：没有证据约束的"强制反驳"会退化为走过场的稻草人——Skeptic 构造一个无人持有的弱观点再轻易驳回，形式上完成了 TR 清单，实质上零信息量。这正是 dagang.md §3.2 所斥的"走了形式但目的不自反"的形式主义。

### 3.5 与 01-编纂原则清单的关联：最易被违反的原则与强制反驳检查

基于 64 条原则的结构分析与 BSD 史写作的实际风险，以下五条原则在实践中最易被违反（违反方式往往不是显式使用禁用句式，而是隐性的叙事倾斜）。为每条配套**强制反驳检查问句**——凡章节叙事涉及相应主题，Skeptic 必须逐问攻击：

| 原则 | 最易违反的方式 | 强制反驳检查问句（Skeptic 必问） |
| ---- | -------------- | -------------------------------- |
| **P15 偶然性优先**（总纲 5） | 隐性目的论：不用"必然"字样，但叙事组织方式让读者感到事件"顺理成章地"走向已知结局 | "把本章的结局从叙事中遮住，仅凭事件中呈现的史料，读者还能推出这个结局吗？若不能，叙事中是否偷偷动用了'已知结局'来筛选和组织材料？列出每一处。" |
| **P11 拒绝进步叙事**（总纲 1/3） | 功能对比替代进步定性：不写"更先进"，但通过只呈现新版本功能增量、不呈现废弃与代价，制造隐性阶梯 | "本章每个版本对比是否同时呈现了新增与废弃/代价？是否存在只选'改进项'的对比表？把对比表反转（以旧版本为基准）是否仍然成立？" |
| **P18 多方平等**（总纲 8，R2 裁决） | 篇幅倾斜伪装成史料丰度差异：FreeBSD 叙事详于其他分支，理由是"史料多"，但史料收集投入本身未在各分支间均衡分配 | "其他分支的史料少，是因为客观留存少，还是因为 Researcher 的检索投入少？列出每个分支的检索工单数与 OD 建设数对比。若投入均衡后仍少，是否已按标准 2 标注信息黑洞而非省略？" |
| **P16 和解史观/非斗争叙事**（总纲 6） | 战争隐喻残留："竞争""输给""战胜""失守"等词未出现，但章节组织按"攻防"结构展开 | "本章的事件选择是否预设了胜负框架？若把 BSD 与 Linux 全部替换为中性的'系统甲/系统乙'，叙事结构是否仍然成立？不成立则说明斗争框架已渗入选材层而非仅在措辞层。" |
| **P24 拒绝苦难叙事**（总纲 14） | 结构性描述中的隐性道德化：不写"无私奉献"，但通过渲染资源匮乏的细节（"仅 N 人""无商业支持"）激发读者道德感动 | "删除本章所有资源匮乏细节后，事实陈述是否完整？若完整，这些细节的功能就是情感动员而非信息传递——它们是苦难叙事的变体。" |

**执行方式**：五组问句固化进 Skeptic 提示词模板（模板 C 第 1 条的展开附件）；每组问句的回答作为反驳记录的 disposition_reason 附件存档。章级审稿（第四章 R1 史料学审查之外的专设步骤"原则符合度审查"）复核这五组问句是否全部执行。

## 第四章 学术审稿模式（Phase 37）

### 4.0 总体设计

任务书要求建立七项审查清单：**R1 史料学审查、R2 技术史审查、R3 组织史审查、R4 制度史审查、R5 叙事审查、R6 反 BSD 中心主义审查、R7 反 Linux 中心主义审查**。

**双向防御原则**（任务书明示）：R6 与 R7 必须成对执行、同一章节双审——既防 BSD 中心主义的自我美化，也防 Linux 中心主义的挪用叙事。依据 dagang.md 总纲 8（P18 多方平等）与总纲 6（P16 非斗争叙事）：两个方向的中心主义在本体论上都是"把一刻的不均等固化为本体论等级"，都不允许。

**审稿执行者**：七项审查由 Skeptic 角色（第二章）在章级与卷级执行，其中 R1/R2 需要 data-engineer 提供断链审计报告与代码史料核验支持；R6/R7 由两名不同 agent 分别执审（防止同一审查者的立场偏好同时污染两个方向）。

**审稿输出统一格式**（见 4.8）：逐条结论（通过/存疑/不通过）+ 证据指针 + 修改建议。

### 4.1 R1 史料学审查

**审查目标**：本章史料的层级标注、来源合法性、考据留痕、冲突处理是否符合 lishidagang.md §1.2.1 五层级模型与 §3.2.2 三次复查（P41/P52/P53）。

**典型病灶**（BSD 史写作中真实高发）：

| 病灶 | 说明 |
| ---- | ---- |
| 百科依赖 | 以维基百科/FreeBSD 官网 wiki 条目作为事件时间线依据，而非原始邮件或公告 |
| 记忆重构采信 | 以 2010 年代会议演讲中对 1993 年事件的回忆为唯一依据，不与同期邮件串交叉 |
| 幸存者偏差无自觉 | 以现存邮件列表为"社区全貌"，不标注早期列表缺失（如 386BSD 时期若干列表已失档） |
| 单一来源事实 | 硬事实（日期、版本号、人名）仅一处来源，未做第二次独立核验即入稿 |
| 教材/指导思想混入 | sacred_sources.db 内容被当作 BSD 史事实引用（违反 P3 同源互证） |

**检查问题清单**（12 问，逐条打勾）：

1. 本章每条事实性陈述是否都能沿回溯链走到 Original Document（断链审计 A/B/C 类为零）？
2. 本章 Evidence 的 tier 标注与 doc_kind 是否一致（R-C4 校验通过）？
3. 是否存在纯第四、五层级证据支撑而无低层级佐证的 Claim（R-C5 违例清单是否为空）？
4. 每个硬事实（生卒年/机构名/版本号/时间节点）是否至少两次独立核验（标准 1）？
5. 本章是否引用了任何百科类或不可溯源来源（P41 禁入清单）？
6. 本章是否误用 sacred_sources.db 条目或教材前言哲学段落作史料（P3）？
7. 邮件列表引用是否均含发件人+时间戳+message_id，并标注讨论串参与人数（P42）？
8. 本章是否依赖已失档的邮件列表而不自知（对照 11-邮件列表史料 实际覆盖范围核查）？
9. 证据冲突是否全部登记于 evidence_conflicts 且无超期 suspended（1.3.4 F 类）？
10. 考据留痕文件（三字段：查证来源/交叉验证方法/存疑判定依据）是否齐备（P53）？
11. 存疑条目是否全部标 `[存疑脚注]`，无一处"默认为确证"？
12. 第五层级史料是否均作补充参照而非唯一来源（P41）？

### 4.2 R2 技术史审查

**审查目标**：技术陈述的准确性、技术决策叙事的偶然性、"技术理性选择"神话的清除（lishidagang.md §3.1.1；P15/P22）。

**典型病灶**：

| 病灶 | 说明 |
| ---- | ---- |
| 功能进步叙事 | 把 4.3BSD→4.4BSD、或 FFS→ZFS 的引入写成"性能改善的必然选择"，不呈现当时的约束与代价 |
| 技术决定论 | "TCP/IP 使 BSD 成功"式单因归因，违反 §2.3.1"不提供单一原因" |
| 时代错置的技术评价 | 用今日标准评价当年决策（"当年没用 X 是失误"），违反事后不倒灌（问题 7） |
| 代码证据缺位 | 涉及内核/文件系统演进的章节不引 commit 或源码差异，只引事后技术博客 |
| 技术术语无解释 | 术语首次出现不标英文原文与必要解释（标准 10），或反之——对专业读者过度科普 |

**检查问题清单**（12 问）：

1. 本章每个技术决策陈述是否呈现了当时的约束、偏好、资源限制等偶然条件（§3.1.1）？
2. 是否存在"因为技术上更好所以被选择"的理性选择叙事？（改为"在 [约束] 下选择了 X"）
3. 涉及代码演进的 Claim 是否至少有一条第一层级证据（commit/源码/构建产物）？
4. 版本对比是否同时呈现新增功能与废弃/代价（与 3.5 进步叙事检查问句联动）？
5. 是否存在以今日技术标准倒评当年决策的语句？
6. 技术术语首次出现是否标注英文原文；人名是否首次出现标注全名与生卒年（标准 10）？
7. 本章技术陈述与代码仓库史料库（01-代码仓库史料 各分库）的实际内容是否可对照核验？
8. "X 技术使 Y 成功"类技术决定论句式是否已改为多因素并陈？
9. 技术争议的辨析是否呈现双方当时的实际论点（而非事后总结的论点）？
10. 对"简洁/优雅/先进"类技术美学评价词，是否已改为具体功能差异描述（标准 3："X 在 A 方面与 Y 不同"）？
11. 本章是否把 BSD 技术写成 UNIX 的附属演进（与 R6-2 联动核查）？
12. 技术史"遗产"段是否以实践方式的存续（代码审查、审计、ports 维护，P32）而非功能清单收束？

### 4.3 R3 组织史审查

**审查目标**：社区治理叙事是否避免"从混乱到有序"进步框架、是否呈现沉默的大多数、是否记录动手者（lishidagang.md §3.1.3；P20/P42）。

**典型病灶**：

| 病灶 | 说明 |
| ---- | ---- |
| 治理进化论 | "BSD 社区从无序走向规范化治理"——把 Core Team 制度的建立写成进步（§3.1.3 明禁） |
| 领袖中心 | 章节只写 McKusick/de Raadt 等台前人物，无普通贡献者记录（违反标准 12） |
| 共识虚构 | "社区一致认为"类无主语表述，把邮件列表中少数活跃者的讨论当作社区共识（P42 使用方法论 1） |
| 分裂归因单一化 | 把 OpenBSD 分离只归因于个人冲突，或只归因于理念分歧，不并陈多因素与权力重组（总纲 4 与总纲 3 联动） |
| 贡献者等级化 | 正文按 P0/P1/P2 分级排定人物书写优先级（标准 12 明禁：分级仅用于资源分配） |

**检查问题清单**（10 问）：

### 4.6 R6 反 BSD 中心主义审查

**审查目标**：清除 BSD 叙事中的自我美化、正统论、受害者悲情——防止本书自身滑向它所批判的中心主义。

**典型病灶**：

| 病灶 | 说明 |
| ---- | ---- |
| BSD 写成 UNIX 注脚 | 把 BSD 叙述为"UNIX 历史的一个分支章节"，否认 BSD 对 UNIX 传统的改造与延续的主体性（本书核心命题是"从 UNIX 到 BSD 再到 4 大 BSD 是连续不间断的整体"——连续不等于附属） |
| 正统继承论 | "FreeBSD 赓续 CSRG 未竟事业"被写成排他性正统主张，暗示其他分支不合法或不正统（"正统/旁支"为标准 5 明禁表述） |
| 受害者悲情 | 把 BSD 的市场位置写成"被 Linux 夺走本该属于它的地位"，混合斗争修辞与苦难叙事（P16/P24 双违反） |
| 自我美化的独特性 | "BSD 更优雅/更纯粹/更工程化"类无证据的群体自画像，违反 P18"成功指标是形式主义建构" |
| 贬抑性对照 | 通过贬低 Linux/GNU 来抬高 BSD（"Linux 只是拼凑"类表述） |

**检查问题清单**（10 问）：

1. 本章是否把 BSD 写成 UNIX 的注脚或附属分支，而非连续传统中具有自身主体性的一段？
2. "赓续 CSRG 事业"类表述是否被写成排他性正统主张？其他分支（NetBSD/OpenBSD/DragonFly）的同源继承地位是否被同等承认（P18）？
3. 是否存在"本该属于 BSD"类地位悲情表述？市场位置是否按结构性位置（总纲 20 边缘性）而非"被夺走"来叙述？
4. 是否出现"主流/支流""正统/旁支"表述（标准 5 零容忍）？
5. 对 BSD 各分支的比较是否避免了优劣定性，仅用"在 A 方面与 B 不同"句式（标准 3）？
6. 是否存在通过贬低 Linux/GNU/Windows 来抬高 BSD 的对照？
7. BSD 的技术/文化特质是否被写成"天然如此"而非其具体历史条件的产物（P25 文化自然化批判）？
8. 卷 4"大分裂"叙事是否把分叉写成 BSD 的损失/悲剧而非分离聚合循环的一个相位（总纲 4）？
9. 本章是否承认 BSD 社区自身的结构性特征（精英主义、排外性、性别失衡，§3.1.7）而非只写成就？
10. 书名意识检查："给我自由"的问题意识是否被写成 BSD 的道德优越性宣言，而非对自由之不对称分配的历史追问（原则清单问题 10）？

### 4.7 R7 反 Linux 中心主义审查

**审查目标**：清除以 Linux 为参照系、以 Linux 历史地位为默认坐标的叙事——这是本书"BSD 传统被 Linux 文化挪用所遮蔽"核心命题的直接审稿装置。

**典型病灶**：

| 病灶 | 说明 |
| ---- | ---- |
| 挪用叙事 | 把 Linux 的成功写成纯粹 GNU/FSF 自由软件理念的胜利，遮蔽 Linux 对 BSD 代码、工程实践、社区模式的继承（本书主题直接批判的对象） |
| Linux 为默认坐标 | 以"Linux 出现之前/之后""与 Linux 相比"作为时间线和价值参照，BSD 成为被比较项而非叙述主体 |
| 影响倒置 | 把 BSD 的技术成就写成"影响了 Linux"——以 Linux 的采纳作为 BSD 价值的证明，等于承认 Linux 是价值裁判（P8：不存在外部认识论位置，本书拒绝让中心给边缘发证书） |
| 单一原因归因 | 把 Linux 兴起归因于单一因素（GPL 的天才/Linus 的领导力/互联网时机），违反偶然性优先（P15）与多因素并陈要求 |
| 份额即历史 | 以市场占有率变化作为历史重要性标尺（总纲 8 明斥："用用户数量衡量操作系统的成功=用形式主义化的指标替代对事物本身的判断"） |

**检查问题清单**（10 问）：

1. 涉及 Linux 的段落中，Linux 是否作为平行传统的叙述对象，而非 BSD 叙事的参照坐标？
2. Linux 的兴起是否按多因素+偶然条件呈现（许可证选择、386 硬件普及、Minix 限制、网络时机等），无单一原因叙事？
3. 是否存在"Linux 的成功证明了……"句式——以 Linux 结果反推历史正当性？
4. BSD 的价值论证是否完全不依赖"被 Linux 采纳/继承"作为证据？（影响关系的呈现可以存在，但不得作为价值证明）
5. 涉及 GNU/Linux 关系的段落，是否同时呈现 GNU 侧（编译器/工具链/许可证框架）与 BSD 侧（完整操作系统先例/网络栈/许可证实践）的贡献，不偏废？
6. 市场份额数据是否仅作描述性引用并附"形式主义化指标"自觉标注，从未作为重要性论证？
7. "开源"话语的起源叙述是否呈现 BSD 传统与自由软件传统各自的贡献，而非把开源史写成 FSF/OSI 单线（P23 利益分配分析适用于开源话语本身）？
8. 涉及 macOS/Darwin 的章节，BSD 层（XNU 中的 BSD 成分）是否被当作独立研究对象而非 Apple 产品的附注？
9. 比较 BSD 与 Linux 时是否对称呈现双方立场与理由（标准 5）——包括对称呈现 Linux 社区的自身逻辑，而非将其漫画化？
10. 本章叙事在删除全部与 Linux 的比较段落后是否仍然完整——若删除后章节坍塌，说明本章是以 Linux 为组织轴的倒置叙事。

### 4.8 审稿输出格式

每次审稿形成一份结构化记录，归档至 `08-核查报告与多轮复核/审稿记录/REV-{审查码}-{卷章}-{日期}.md`，并同步登记入 review_reports.db（既有文件夹级库，schema_version 1.4）。格式：

```markdown
# 审稿记录 REV-R2-V02C42-20260812
- 审查项：R2 技术史审查
- 审稿人（角色）：Skeptic（robustness-auditor 装载）
- 对象：第 2 卷第 42 章草稿 H-42-草稿-20260810.md
- 前置文件：断链审计报告（通过）/ 反驳清单处置（完成）

## 逐条结论
| 问题号 | 结论 | 证据指针 | 说明 |
|---|---|---|---|
| R2-1 | 通过 | 全章 causal claim 均已多因素并陈（C-000201 等） | — |
| R2-3 | 不通过 | C-000312 无第一层级证据（断链审计 C 类清单 #7） | 涉及 4.4BSD 代码变更的陈述须补 commit 级证据 |
| R2-5 | 存疑 | S-V002C042.4-009 | "当年的选择在今天看仍有价值"——疑似时代错置评价，交 Historian 复核措辞 |
（全部问题逐条列出，不允许省略）

## 统计：通过 X / 存疑 Y / 不通过 Z
## 修改建议（按优先级）
1. 【阻断】R2-3：补第一层级证据或改写陈述（未修复不得进入下一流程）
2. 【建议】R2-5：措辞修订
## 结论：【通过 / 有条件通过（列条件）/ 不通过】
```

**三态判定规则**：

- 任何"不通过"项 → 整项审查结论为不通过，退回对应角色（事实类→Researcher+Historian；结构类→Historian；表述类→Editor），与第二章退回权一致；
- 仅"存疑"项 → 有条件通过，存疑项转为工单，修复后由原审稿角色复核销项；
- 全部通过 → 进入下一审查项；
- 修订次数沿用 P60：同一章同一审查项累计 2 轮修订仍未通过 → 强制通过但挂审核警告（lishidagang.md §5.2.2 模板），审稿记录如实登记残留。

## 附：待裁决张力登记

以下张力为本方案设计过程中发现的、与思想层文件存在真实紧张之处，依任务要求显式标注并给出处理建议；最终裁决权在 ykla。

**Z1：全量语句登记与"理论字数越多越不值钱"（总纲 7 延伸）的工程版张力**
回溯系统要求约 50-60 万句全量登记，是继 350-400 万字书稿之后的又一层大规模形式主义装置。处理建议：沿用 01b 裁决 R1 的逻辑——规模本身不是问题，问题在于单位信息量；回溯链的每一行都以"可追溯性"为信息内容，不属于理论膨胀。但应设自反条款：若试点（第 42 章）显示建链成本导致证据质量下降（录入者为凑链而降低摘录标准），则允许 ykla 裁减 Sentence 层登记粒度（如只对 claim_bearer 句建 ID，narrative_tissue 句仅计数不登记）。

**Z2：强制反驳的完备性与修订次数限制（P60）的冲突**
若 Skeptic 对每条重要判断的反驳都引发 Historian 重写，章级修订可能迅速耗尽"2 次修订"上限，大量章节带审核警告强制通过，使警告泛滥贬值。处理建议：反驳处置分级执行——strength=S 的反驳必须当轮处置；strength=A 的反驳可并入下一轮修订；strength=B 的反驳只登记不强制修文。此分级已在 3.3 隐含，提请 ykla 确认为正式规则。

**Z3：Editor"不得引入新事实"与可读性修订的灰色地带**
表述压缩（如把两句合并为一句）在技术上不引入新事实，但可能改变 Claim 的粒度（合并后一句承载两个 Claim，触发证伪单元规则）。处理建议：凡 Editor 修订触及 Sentence-Claim 挂接关系的，一律开退回工单由 Historian 确认，Editor 不得径行合并——已在模板 D 禁止行为中落实，提请 ykla 确认该严格度（代价是编辑效率）。

**Z4：R6/R7 双审与"和解优于斗争"（总纲 6）的分寸**
两项中心主义审查本质是对叙事的对抗性攻击，存在把 BSD-Linux 关系重新审成"斗争"的风险（审查者的对立框架渗入审稿意见）。处理建议：R6/R7 审稿记录的措辞约束——审查意见只允许指出"中心主义病灶"，不允许使用战争隐喻描述病灶本身（审稿意见同样受 P54 禁用表述扫描）。此为自律条款，提请 ykla 确认。

**Z5：试点章选择与 R5 裁决（索引漂移）的潜在牵连**
本方案以 CLAUDE.md 记载的"18 卷 348 章、第 42 章属 vol-2"为试点定位；而 01b 裁决 R5 记载 SUMMARY.md 实际为 19 卷 354 章，索引回写冻结后才统一执行。若最终章号重排，Sentence-ID 的卷章段（S-V002C042…）需批量改写。处理建议：ID 中的卷章段以当前 CLAUDE.md 记载为准，重排时由脚本批量迁移（ID 流水段不变，仅改卷章前缀），迁移记入 update_log。提请 ykla 在索引冻结时点同步触发迁移。
