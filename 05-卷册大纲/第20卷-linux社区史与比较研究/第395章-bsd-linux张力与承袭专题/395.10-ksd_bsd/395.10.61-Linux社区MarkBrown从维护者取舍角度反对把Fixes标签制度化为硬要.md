# 395.10.61 Linux社区MarkBrown从维护者取舍角度反对把Fixes标签制度化为硬要

- 【Linux社区】Mark Brown：从维护者取舍角度反对把 Fixes 标签制度化为硬要求——**“如果是在‘我接受一个 mainline bugfix’与‘我找人给我一个准确指出哪个提交引入了某改动的 commit ID’之间做选择，我大概不会做后者，尤其当许多这类东西更属于‘我们现在对硬件理解更好了’这一类型时”**；并给出其真实关注点 **“我真的很高兴有人参与上游。如果有人填写额外信息我很高兴，但老实说，比起拿到一个 Fixes 标签、或者去核对别人加的标签是否准确，我更关心一份清晰的变更日志”**；另披露其对小众硬件的评审取向 **“我曾告诉驱动作者：对于发行量有限的硬件的驱动，我主要看它对子系统与可维护性的影响——很大程度上如果没人能说清驱动在那儿是否能工作，我在意的程度就有限”** `<!-- ROW_MINE: ksummit-discuss.messages.346940 -->`
- 【Linux社区】Jiri Kosina：回应“许多 stable 补丁是 PCI ID 添加”的反例，直接质疑非修复类补丁进入 -stable 的正当性——**“如果它不是 bugfix，它之于 -stable 的适用性在我看来非常可疑”**；并给出可能例外 **“设备 ID 或许可以做成与 merge window 之后向 Linus 树添加 PCI ID 相同的例外。即便在那里，-rc1 之后一切都应当是 bugfix，但设备 ID 添加是被允许的”** `<!-- ROW_MINE: ksummit-discuss.messages.346941 -->`
- 【Linux社区】Mark Brown：把“部分驱动不支持 deferred probe”的实况收束为应修的 bug——**“当然，但此刻这些基本就只是 bug——它是我在 probe 例程里见到的最常见的错误模式之一；不过它往往伴随‘算了忽略这个错误吧，它不可能重要’这种糟糕做法，而那种做法本来就该被修掉”** `<!-- ROW_MINE: ksummit-discuss.messages.346942 -->`
- 【Linux社区】James Bottomley：为 Fixes 标签给出超越 stable 的存在理由与精确的回归定义——**“为什么不换个角度看：任何修正先前提交的 bug 修复实际上就是一个回归。我们区别对待回归（并真的有人去跟踪它们）的原因是它们正是用户痛恨的那类问题：意味着先前能工作（因而被依赖）的东西突然不工作了”**；并补上边界 **“注意并非每个带 fixes 标签的 bug 修复都是技术意义上的回归——如果 fixes 标签指向的实际上是首次引入该特性的提交，那它就不是回归，因为无 bug 的行为从未对最终用户可见过。不过跟踪回归的人有能力把这点分辨出来”**；结论是 **“我想指出的是 Fixes: 的用途远超 stable。这就是为什么我确实认为它是内核的好实践。它是我们本来就该在做的事，可以辅助 stable 流程，而不是专为此发明的”** `<!-- ROW_MINE: ksummit-discuss.messages.346943 -->`
- 【Linux社区】Steven Rostedt：反驳“清晰变更日志与 Fixes 标签二选一”的设定并给出经验观察——**“谁说过要在两者之间做选择？”**；**“清晰的变更日志与拥有 Fixes 标签是正交的。实际上，依我的经验，带 Fixes 标签的变更日志往往比不带的有更清晰的解释，因为为了得到那个 Fixes 标签，人已经做了一番研究弄清 bug 最初为何发生”**；并说明适用范围 **“对某些冷门驱动来说，清晰变更日志与 fixes 标签可能没那么重要，因为用户不多，而且谁知道将来我们想查这段代码历史时那个硬件是否还存在。我主要在内核核心工作，而内核中任何使用面大得多的部分都会从清晰的变更日志以及指向回归（甚至 bug 一直都在）的 Fixes 标签中大大受益。它除 stable 之外在许多方面都有帮助。正如 James 提到的，它有助于回归跟踪——那是人们一直想恢复的东西”**；另举亲历 **“我在用的一个旧内核版本里发现一个 bug，查上游时发现有 fixes 标签。我不仅轻易找到了正确的修复，还由此确认那段坏代码确实存在于我在玩的那个内核里”** `<!-- ROW_MINE: ksummit-discuss.messages.346944 -->`
- 【Linux社区】Takashi Iwai：厘清其反例的确切含义——**“是的，我不是指非修复。常见的添加 PCI ID 或添加设备专用 quirk 实际上确实是‘修复’，但不是能指向某个特定提交的回归修复。驱动代码本身在新硬件出现之前是好的，只是驱动代码之后才出现了一个新设备”**——为“修复”一词的语义边界提供精确定义 `<!-- ROW_MINE: ksummit-discuss.messages.346945 -->`
- 【Linux社区】Josh Triplett：附议 Lutomirski 的 user namespace 隔离方案并指出其安全前提的严苛程度——**“我们绝对应该这样做，它会产生很大差别。然而，‘除非有 bug’是个很大的前提；实践中，从 user 到 kernel 大概比从 user 到 root 更容易，因为前者任何能做系统调用的进程都可以尝试。而我们在修复系统调用漏洞方面还远远没有完成”**；对落地路径则给出乐观判断 **“systemd 让为一个服务配置这类命名空间隔离变得相当容易。比如你可以把不需要网络的服务放进一个只含 localhost 的网络命名空间。我猜会有远多于手动配置等效隔离方案的服务用上它”**（KS2014 档案） `<!-- ROW_MINE: ksummit-discuss.messages.346946 -->`
