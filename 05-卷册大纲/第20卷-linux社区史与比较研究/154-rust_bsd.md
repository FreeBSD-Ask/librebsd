## 154.1 许可证

- 【Linux社区】Miguel Ojeda 回应 Linus Torvalds 关于 Rust alloc crate 导入时许可证标注的意见。Linus 在审阅上游 alloc crate 导入补丁时要求明确说明许可证状态，而非依赖外部链接让阅读者自行查找。Miguel 承认应在拆分补丁时就标注许可证，因当前版本已无 SPDX 标识符，并承诺在后续补丁的 README 文件中添加明确说明。该条目记录了 Rust 内核子系统引入上游 crate 时对许可证声明规范的早期讨论，涉及许可证状态透明化的治理要求。 `<!-- ROW_MINE: rust-for-linux.messages.9267987 -->`
- 【Linux社区】自一九九一年参与 Linux 开发的 Dr. Greg 在社群影响力讨论中表达深层忧虑。他提到一九九五年在 Stallman 赞助的 MIT 自由软件会议上首次与 Linus Torvalds 见面，并回忆当时因 Linux 医疗流程优化而让北达科他癌症患者获得更多家庭时间。他批评当前内核开发流程中技术贡献被忽视，其耗时两年的四项安全建模补丁系列未获任何代码审阅。该条目涉及 Linux 内核治理模式的演变与早期自由软件社群记忆。 `<!-- ROW_MINE: rust-for-linux.messages.9270903 -->`
- 【Linux社区】Sami Tolvanen 回应 Greg Kroah-Hartman 关于 gendwarfksyms 工具许可证标记的质疑。Greg 追问是否真的意指 GPL-2.0-or-later，并指出 Google LLC 版权标记的许可类型存在问题。Sami 承认许可证是从系列中包含的 genksyms 代码继承而来，表示将与公司内部法务团队商议并在 v3 版本中调整其他部分的标记。该条目记录了 Linux 内核引入 Google 版权代码时对 GPL-2.0-or-later 许可适用性的审慎讨论。 `<!-- ROW_MINE: rust-for-linux.messages.9278159 -->`
- 【Linux社区】本邮件是对同线程中一条许可证论证的反驳。被引段落先援引 GPL 条款，要求任何分发或发布的衍生作品必须整体按该许可条款免费授予第三方，随后提出论断：使用非 GPL 工具会带来开发并分发 GPL 兼容但带专有成分的内核版本这一后果。作者以反问切入，认为该论证成立的前提是内核被牢牢锁定在完全没有非 GPL 等价物、并且某种程度受保护从而不会获得等价物的工具上，随后列举了可能实现这一锁定方式的具体手段，包括依赖工具未文档化且快速变化的特性、对接口主张版权、软件专利，并质疑描述这类安排所需的观念扭曲程度，认为把它称为自由并不合适，但同时说明幸运的是内核目前远未接近这种处境。作者最后明确表态自己不喜欢 Rust 这门语言、也怀疑它在内核中的价值，但要求不要把某编译器因为采用 GPL 而更好这类主张混入这场讨论，理由是不论 Rust 与否，内核显然并未在所有相关架构上被锁定于某一编译器。 `<!-- ROW_MINE: rust-for-linux.messages.9298170 -->`
- 【Linux社区】本邮件是一段关于补丁文件许可标识如何选择的简短协商，起因是某宏工具补丁涉及的代码来自上游项目、原作者持有版权。Greg 在来信中解释，作者作为版权持有人完全可以自行把代码用于其他用途或改以其他许可发布，并不需要双许可，前提是不带入他人以其他许可所做的改动；他提醒混用许可几乎没有必要，而长期维护多许可文件会带来显著负担。Miguel 在回复中表示赞同，并补充说明部分开发者确实有自身理由，例如希望各处使用同一标识，使读者在看到代码时能意识到它在别处是以更宽松的许可发布的，而这种双许可做法在 Rust 社区的项目中颇为常见。经过这一往返，作者决定遵从建议把该文件的许可统一替换为 GPL-2.0，理由是相关同事也认可这一选择。这段往来记录了内核 Rust 代码在继承上游宽松许可代码时的实际取舍，以及最终统一为 GPL 的结果。 `<!-- ROW_MINE: rust-for-linux.messages.9301763 -->`
- 【Linux社区】Greg KH 对 Sami Tolvanen 提交 gendwarfksyms 代码时使用的许可证标识提出质疑。Sami 在新文件头中标注 SPDX-License-Identifier: GPL-2.0-or-later，Greg 追问他是否真的打算在该系列所有文件中都使用 or later 标记。Greg 特别指出 Google LLC 作为版权持有方，对某些许可证标记的覆盖范围存在特定限制，暗示 or later 版本可能不适用于所有 Google 贡献代码的许可证策略。此讨论触及 GPL 许可证版本选择中 GPL-2.0-only 与 GPL-2.0-or-later 的治理分歧，以及大型企业对许可证标识选择的谨慎态度。 `<!-- ROW_MINE: rust-for-linux.messages.9304786 -->`
- 【Linux社区】Greg KH 在审阅 Danilo Krummrich 提交的 devres 抽象补丁时，注意到所有新 Rust 文件缺少版权声明。Greg 表示自己支持不加版权声明的做法，但指出与他共事的公司法务人员对没有版权行的文件持强烈反对态度，建议 Danilo 去确认公司要求，否则未来可能面临严厉谈话。这反映了 Rust for Linux 项目中关于是否需要版权声明的 GPL 实践争议，涉及版权归属与公司法律要求之间的张力，也体现了开源项目中个人偏好与企业法务需求的平衡问题。 `<!-- ROW_MINE: rust-for-linux.messages.9309410 -->`
- 【Linux社区】Mariusz Ceier 质疑非 GPL 工具能否促成 GPL 兼容但专有的内核版本发布。Al Viro 反驳称，除非内核被锁定在只能使用无 GPL 替代品的工具上，否则非 GPL 工具不构成威胁，并批评 gcc 更好因为 GPL 的论调无关紧要，因为我们显然并未在所有架构上锁定于 gcc。Mariusz 表示他更担忧功能完备的 Rust 编译器在封闭环境中开发，可能偏离 GPL 精神。讨论触及 GPL 许可证对编译工具链的约束力，以及 Rust 编译器开源状态对内核许可证合规性的潜在影响。 `<!-- ROW_MINE: rust-for-linux.messages.9309804 -->`
- 【Linux社区】Greg KH 警告 Miguel Ojeda 在 Rust paste proc macro 中使用双重许可证需谨慎，尤其不要在内核树中混用非 GPL 许可证。他指出 GPL-2.0 以外的许可证极易引发复杂问题，甚至需要律师签核。Miguel 解释这是 Rust 项目的通用做法，也用于 alloc 标准库的 vendor 引入，因为 proc macro 在用户空间也有用途，贡献者 Gary 可能想将其发布到 crates.io。Greg 认为版权所有者可自行选择许可证，无需双重许可，混合许可证是长期维护的沉重负担。 `<!-- ROW_MINE: rust-for-linux.messages.9309946 -->`

## 154.2 治理

- 【Linux社区】Hector Martin 参与关于社群影响力与基础设施去中心化的讨论。针对 Linus Torvalds 认为百分之八十五从 kernel.org 拉取并不意味着集中的观点，Hector 指出这实际上等同于完全集中，任何 kernel.org 宕机都会对社区造成等同影响。他强调应聚焦可恢复性与数据可用性而非单纯去中心化，并区分短期中断与永久丢失两种场景的不同应对策略。该讨论触及 Linux 内核基础设施治理与冗余策略的核心张力。 `<!-- ROW_MINE: rust-for-linux.messages.9268507 -->`
- 【Linux社区】Danilo Krummrich 在 Rust 内核策略讨论中澄清维护者否决权边界。Linus Torvalds 明确表示维护者无权以个人偏好控制 API 的使用者，并称若维护者认为可控制代码使用者则理解错误。Danilo 对此表示认同，并补充维护者对其维护的 API 在被滥用损害内核整体时确实拥有否决权，但该否决权不能基于个人偏好或特定项目排斥。该讨论触及 Linux 内核治理中维护者权限与 API 使用自由的核心张力。 `<!-- ROW_MINE: rust-for-linux.messages.9270159 -->`
- 【Linux社区】Jason Gunthorpe 就 Rust 内核构建策略与顶层维护者治理展开讨论。他指出维护者峰会已就 rc1 构建破坏问题达成共识但未提出改动方案，而 Linus Torvalds 接受 PR 的前提是维护者必须保证 CONFIG_RUST=y 构建通过。当 PR 被拒绝时，维护者面临紧急情况，因为他们对提交者的代码合并负有责任。他引用 Andrew 在上一周期被迫 rebase 并丢弃补丁的案例，强调维护者应提前进行 Rust 构建测试以避免紧急返工，并主张明确向维护者传达这是他们的职责。 `<!-- ROW_MINE: rust-for-linux.messages.9304171 -->`

## 154.3 BSD谱系

- 【Linux社区】Miguel Ojeda 向 Linus Torvalds 提交 Rust for Linux v7.2 合并请求，核心是引入 zerocopy 库以替换大量处理字节序列与类型间转换的不安全代码。zerocopy 以 BSD-2-Clause 或 Apache-2.0 或 MIT 三重许可授权，导入时基本保持原样仅需增删数行适配。该条目展示了 Rust 内核子系统引入非 GPL 许可 crate 的许可决策与依赖管理实践，涉及宽松许可与内核 GPL 许可的交叉地带。 `<!-- ROW_MINE: rust-for-linux.messages.9268951 -->`
- 【Linux社区】Andrew Lunn 审阅 Rust Socket 抽象补丁，质疑其 API 设计的合理性。他指出用户空间应用通常通过 BSD sockets 与内核及协议通信，因此需要明确 Rust socket 抽象层与现有 BSD socket API 的层次关系。他质疑为何低时延网络协议需要穿越两次 socket 层，以及如何在将 socket 底层连回顶层时避免死锁。该讨论触及 BSD socket 接口在 Rust 内核抽象中的定位与兼容性问题。 `<!-- ROW_MINE: rust-for-linux.messages.9270985 -->`
- 【Linux社区】Andrew Lunn 继续讨论 Rust Socket 抽象补丁，指出当前实现使用 procfs 或共享内存映射的字符设备缓冲区而非 BSD sockets。他强调内核已有 Eric 等人实现的 socket 零拷贝支持以及 netlink 控制平面机制，质疑为何要在 socket 之上再建一层 API。他还建议服务可改用 eBPF 从用户空间加载，避免每次修改都需经过合并流程。该讨论涉及 BSD socket 接口在低时延分布式系统中的适用性边界。 `<!-- ROW_MINE: rust-for-linux.messages.9271703 -->`
- 【Linux社区】Davide Rovelli 回应 Andrew Lunn 关于 Rust Socket 抽象补丁的质疑，解释当前实现使用 procfs 或共享内存映射字符设备缓冲区而非 BSD sockets。他指出该 API 提供分布式服务如故障检测器与共识机制，通过 SDN 协议优先化流量。他解释系统设计将用户空间应用与内核空间服务分离，以实现端到端低时延通信与处理，从而实现高效的分布式服务。该讨论涉及 BSD socket 接口在低时延分布式系统中的定位。 `<!-- ROW_MINE: rust-for-linux.messages.9275252 -->`
- 【Linux社区】Miguel Ojeda 回复 Asahi Lina 关于以 Rust 编写 Apple AGX GPU 驱动的讨论，涉及 Rust 绑定的维护权与许可策略。他提到 DRM 子系统与 OpenBSD 和 FreeBSD 活跃共享代码，建议将 DRM 绑定、驱动及进程宏设为双许可，以便各 BSD 系统能够使用。他还讨论了核心子系统抽象的维护归属问题，提出即使子系统当前不愿维护抽象，只要有责任人即可先行提交，最终由高层维护者决定。该条目涉及 BSD 系统与 Linux 内核在 DRM 子系统的代码共享与许可交叉。 `<!-- ROW_MINE: rust-for-linux.messages.9277169 -->`
- 【Linux社区】Enrico Weigelt 在 Rust V4L2 支持讨论中明确划定 BSD 代码在内核邮件列表的范围边界。针对 Hans Petter Selasky 展示的 webcamd 项目即 BSD 许可的用户空间驱动示例，Enrico 明确表示 BSD 代码不属于 LKML 讨论范围，并指出将内核代码复制到用户空间后需自行维护，内核 API 从不存在稳定固定版本。他还反驳了 V4L2 驱动应移至用户空间的观点，认为这与内核开发无关。该条目触及 BSD 许可代码与 Linux 内核开发边界的治理问题。 `<!-- ROW_MINE: rust-for-linux.messages.9279512 -->`
- 【Linux社区】本邮件是苹果芯片 Rust 图形驱动讨论帖中的一段，作者回应 Rust for Linux 负责人关于许可证的说明。被引部分指出，Rust for Linux 团队自启动之初便约定全部代码使用 GPL-2.0，此前还讨论过复用一份用于 GRUB 模块的 Rust 文件。作者随即说明，DRM 子系统与 OpenBSD 和 FreeBSD 之间存在活跃的代码共享关系，因此希望社区就 DRM 绑定层、驱动本身以及配套进程宏能否双许可作出表态，同时承认 BSD 系统是否愿意引入 Rust 仍是开放问题。作者另指出，若绑定代码被 GPL 覆盖，DRM 维护者将来需重写宏与辅助代码才能支持非 GPL 使用者，这会构成负担。文末作者特别区分了支持双许可与支持专有 Rust 内核模块两种情形，表示个人并不看好专有模块对生态的影响。整段讨论把 GPL-2.0 统一许可策略与 BSD 家族代码复用需求之间的张力摆到台面。 `<!-- ROW_MINE: rust-for-linux.messages.9285777 -->`
- 【Linux社区】本邮件是作者刚加入 Rust for Linux 邮件列表后针对许可证策略提出的一问。作者注意到现有 Rust for Linux 代码似乎统一采用 GPL-2.0，询问这究竟是明确的集体决定，还是仅仅沿用默认设置。作者援引既有事实作为对照：Linux 的 DRM 核心以及 i915、radeon、amdgpu 等主要驱动均采用 GPL 与 MIT 双许可，正因为如此，OpenBSD 可以直接使用这部分代码。作者表示希望苹果芯片驱动也采取同样做法，目标是让驱动对其他内核同样有用，因此询问 Rust 核心中的一部分，尤其是进程宏和用 Rust 编写的通用代码，是否可以采用更宽松的许可，以便其他项目在自己复用它所支撑的驱动时能够直接引入这些公共代码。这段讨论把 GNU 内核中已有的双许可先例与 BSD 系统跨内核复用需求直接联系起来。 `<!-- ROW_MINE: rust-for-linux.messages.9286518 -->`
- 【Linux社区】本邮件是引入群晖嵌入式微控制器驱动的补丁系列说明，主体内容属于设备支持与代码组织的技术描述。群晖在 NAS 设备中使用通过串口连接的小型微控制器，用于控制指示灯、风扇转速、蜂鸣器，并处理正常关机重启、按键与风扇故障；补丁依赖此前已提出的 Rust 指示灯抽象与 Rust 串口设备抽象，当前版本仅实现指示灯控制，其余功能还需补齐监控、输入以及关机与硬件保护关机相关的 Rust 抽象。本条入选是因为版本变更记录中有一条许可相关的明确表述：把设备树绑定文件的许可定为 GPL-2.0-only 或 BSD-2-Clause 二选一的双许可形式。这表明 Linux 内核文档层面已出现 BSD 二条许可条款与 GNU 许可并行的具体应用。除这一条记录外，全文不含 BSD 谱系、许可证论证或治理讨论。 `<!-- ROW_MINE: rust-for-linux.messages.9286619 -->`
