# 318.1 三大 BSD 类似团队批评：NetBSD、OpenBSD、DragonFly BSD

## 317.14.1 NetBSD 各团队的批评：Core Team 封闭、pkgsrc 管理僵化与安全响应迟缓

  **要点**：NetBSD 项目各团队面临的批评——Core Team 封闭性比 FreeBSD 更甚，Core Team 成员长期稳定，新人进入极难，决策几乎完全在内部达成，社区参与度低；pkgsrc 管理僵化，pkgsrc 核心团队对新包提交与现有包更新的审查严格且缓慢，贡献者常因格式问题而非技术问题被拒，打击积极性；安全团队响应迟缓，NetBSD 安全公告（NetBSD Security Advisories）数量少于 FreeBSD 与 OpenBSD，部分漏洞长期未修复，被批评为“安全优先级低”；文档团队人手不足，NetBSD 指南（NetBSD Guide）更新滞后，多语言翻译几乎停滞；基础设施团队资源有限，邮件列表、CVS/SVN 仓库、Bugzilla 等服务常出现中断，镜像站覆盖不足
  **史料**：NetBSD Core Team 历届成员名单；pkgsrc 提交记录与 PR 统计；NetBSD Security Advisories 存档；NetBSD Guide 版本历史；netbsd-tech-kern、netbsd-tech-user、pkgsrc-users 等邮件列表存档 ［A］
  **史观**：总纲第 14 条——社区与文明历史哲学，小规模社区更容易形成封闭性内圈；总纲第 8 条——经济历史哲学，NetBSD 基金会预算远小于 FreeBSD Foundation，资源约束更紧
  **辨析**：NetBSD Core Team 的“封闭”是治理模式选择还是人员老化须区分；pkgsrc 管理的“僵化”是质量保证还是官僚主义须辩证看待；安全响应迟缓与项目规模的关系——人手少导致响应慢是客观限制还是管理问题须厘清
  **文献**：NetBSD Core Team 页面；pkgsrc 统计数据；NetBSD Security Advisories Archive；NetBSD Guide 历史版本；邮件列表存档 ［A］

## 317.14.2 OpenBSD 各团队的批评：Theo 个人主导、开发团队排外与文档傲慢

  **要点**：OpenBSD 项目各团队面临的批评——Theo de Raadt（西奥·德·若特） 个人主导整个项目，技术决策、人事任免、资金分配均由 Theo 最终决定，缺乏制度化的集体决策机制，“仁慈的独裁者”模式比 Linux 的 Linus 模式更集中；开发团队排外，外部贡献者提交的补丁常被公开斥责，Theo 的批评风格以直接、尖锐著称，部分贡献者因无法忍受而离开，社区被批评为“有毒”；文档团队风格傲慢，OpenBSD 手册页（man pages）虽以质量高著称，但 FAQ 与新手文档对初学者不友好，常以“读手册”回应简单问题，RTFM 文化比 FreeBSD 更甚；安全团队的“安全至上”理念被批评为走极端，为了安全牺牲过多功能性与性能，导致 OpenBSD 适用场景受限；翻译团队几乎不存在，多语言支持极差，非英语用户难以参与
  **史料**：OpenBSD 邮件列表（tech@、misc@）存档；Theo de Raadt 公开声明与演讲；OpenBSD 补丁接受率统计；OpenBSD FAQ 与手册页；外部开发者对 OpenBSD 社区的公开评论 ［A］
  **史观**：总纲第 10 条——动手者创造历史，Theo 作为“动手者”塑造了 OpenBSD 的独特文化，但也带来个人主导的治理风险；总纲第 14 条——社区与文明历史哲学，排外文化既是质量保证也是自我封闭
  **辨析**：Theo 的“个人主导”是事实还是夸张——有多少决策实际由 Theo 个人决定须考据；“有毒”社区的判断须基于具体案例统计，避免以偏概全；安全与功能的平衡是价值判断，不同用户有不同偏好，不宜简单否定 OpenBSD 的选择
  **文献**：OpenBSD 邮件列表存档；Theo 公开声明；补丁统计；外部评论文章 ［A］

## 317.14.3 DragonFly BSD 各团队的批评：规模过小、核心团队单一与社区互动不足

  **要点**：DragonFly BSD 项目因规模远小于 FreeBSD、NetBSD、OpenBSD，面临独特的团队批评——核心团队规模极小，长期由 Matt Dillon 主导，核心开发者数量不足十人，公交因子（bus factor）极低，一旦核心成员离开项目可能难以为继；团队结构单一，缺乏正式的分工体系，Core Team、安全团队、文档团队等职能边界模糊，往往由同一批人身兼数职；社区互动不足，DragonFly BSD 用户与开发者基数小，邮件列表流量低，论坛与 IRC 活跃度不高，新用户难以获得及时帮助；文档团队力量薄弱，DragonFly BSD 手册与 Wiki 内容相对简略，新手指南不完善，上手难度高于 FreeBSD；Ports/DragonFly dports 团队人手不足，dports（DragonFly Ports）基于 FreeBSD Ports，但维护者少，更新滞后，软件包数量远少于 FreeBSD
  **史料**：DragonFly BSD 开发者名单与 commit 统计；dragonfly-kernel、dragonfly-users 邮件列表存档；dports 提交记录；DragonFly BSD Wiki 与手册页内容统计；用户对 DragonFly BSD 社区的反馈 ［A］
  **史观**：总纲第 14 条——社区与文明历史哲学，小规模社区的生存困境是 BSD 谱系内部分化的结果；总纲第 25 条——终结中的延续，DragonFly BSD 作为 BSD 谱系的“小众分支”，其存在本身就是“终结中的延续”的体现
  **辨析**：“规模过小”是 DragonFly BSD 的选择（坚持技术方向而非追求规模）还是无奈结果须区分；核心团队单一与 Matt Dillon 个人能力的关系——Dillon 作为主要设计者与实现者，其高度参与是项目优势还是风险须辩证看待；社区互动不足与用户基数小互为因果，不宜简单归因于团队态度
  **文献**：DragonFly BSD 开发者页面；邮件列表存档；dports 统计；Wiki 与手册；用户反馈 ［A］
