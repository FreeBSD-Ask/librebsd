# 319.2 BSD 项目安全响应文化与 Linux、illumos 的比较

## 319.2.1 BSD 分散式安全公告体系与 Linux 集中式 security team 的治理差异

  **要点**：四大 BSD 各自维护独立的 Security Advisory 公告体系——FreeBSD-SA（713 条，1996-2026）[2026-08-15 双库核查：资料数据库.duckdb freebsd_sa 表 COUNT=713，最早 1996-04-20，最晚 2026-06-30]、NetBSD-SA（289 条，1998-2026）、OpenBSD errata（563 条，1996-2026）、DragonFly VSA（166 条 CVE，2003-2024，官方页面 404 须以邮件列表存档补全）；Linux kernel 由 Linux kernel security team（私密邮件列表 <security@kernel.org>）集中协调，2024 年 1 月 Linux kernel 正式成为 CNA（CVE Numbering Authority）可自主分配 CVE 编号；freebsd.duckdb L7.3.1 查询显示 2020 年 Linux kernel 90,911 commits、4,864 contributors，BSD 四大 src 合计 36,392 commits、574 contributors，Linux 贡献者量级为 BSD 的 8.5 倍，但 BSD 项目以更小的人力规模维持独立的 SA 公告体系，反映其“小而精”的安全响应文化
  **史料**：MITRE CNA 列表（cve.mitre.org 2026-07-22 直接访问确认 Linux kernel 自 2024-01 起 as CNA，CNA ID MITRE-CNA-LFN，scope Linux kernel source code；FreeBSD、OpenBSD、NetBSD、DragonFly 均不在 CNA 列表）、FreeBSD Security Advisories 官方存档、NetBSD Security Advisories 官方存档、OpenBSD errata 官方页面、Linux kernel security team 官方页面（kernel.org 2026-07-22 直接访问确认 <security@kernel.org> 为私密邮件列表，含 CVE 编号申请流程文档）、freebsd.duckdb L7.3.1（BSD 4 大 src 与 Linux kernel commit 量与贡献者对比，36 行结果）［A］
  **史观**：经济历史哲学，BSD 分散式 SA 体系是社区自治传统的产物，Linux 集中式 security team 是企业赞助规模化的产物；总纲第 4 条——分离与聚合，BSD 4 项目虽同源 CSRG 但 commit 量分布已统计显著分化；社区与文明历史哲学，安全响应文化的差异是社区组织形态的反映；延续与终结，freebsd-src 与 netbsd-src 在 commit 量分布上无统计显著差异印证二者延续 CSRG 工程节奏的相近性，openbsd-src 与 dragonfly-src 则在 commit 量分布上与他者显著分化；统计结论印证：统计结论 [E-21] NVD FreeBSD 相关 CVE 421 个（1999-2026）、统计结论 [E-22] NVD OpenBSD 相关 CVE 143 个[2026-08-15 双库核查：资料数据库.duckdb nvd_cve_metadata 表 bsd_projects=openbsd COUNT=143]、统计结论 [E-23] NVD NetBSD 相关 CVE 82 个[2026-08-15 双库核查：资料数据库.duckdb nvd_cve_metadata 表 bsd_projects=netbsd COUNT=82，原文 136 不准确，存疑确认]、统计结论 [E-24] NVD DragonFly BSD 相关 CVE 1 个、统计结论 [E-25] FreeBSD 官方安全公告 FreeBSD-SA 382 条（2008-04 至 2026-06-30）、统计结论 [E-26] FreeBSD 平均 CVSS 6.24、统计结论 [E-27] OpenBSD 平均 CVSS 6.17、统计结论 [E-28] NetBSD 平均 CVSS 5.50 共同构成 BSD 4 项目 CVE 与 CVSS 全量基准——BSD 4 项目 NVD CVE 合计 678 个（421+143+82+1[2026-08-15 双库核查重算]，去重前）反映 BSD 分散式 SA 体系的量化基础，FreeBSD 以 421 个 CVE 与 382 条 SA 居 BSD 4 项目之首印证其 “实际遵守但未缴费认证” 的合规路径，OpenBSD 以 143 个 CVE（NVD 2026-08-15 核查）与 563 条 errata 印证其主动代码审计文化（errata 数量超过 CVE 数量反映审计发现 vs 外部披露的差异），DragonFly BSD 仅 1 个 CVE 反映 NVD CPE 命名不完整而非实际漏洞稀少；CVSS 跨项目对照（FreeBSD 6.24 > OpenBSD 6.17 > NetBSD 5.50）不直接等同于安全响应质量差异，须结合各项目 SA 发布周期与回溯补丁覆盖率综合判断；freebsd.duckdb L7.3.1 查询显示 2020 年 Linux kernel 90,911 commits、4,864 contributors，BSD 四大 src 合计 36,392 commits、574 contributors 作为旁证；统计结论 [C-16] 4 个 BSD 项目 src 仓库月度 commit 量分布的 Kruskal-Wallis H 检验（共同时间窗口 2003-06 至 2026-07，总样本量 n = 1112 月即 4 仓库 × 278 月，组数 k = 4）显示 H = 763.399, df = 3, p <0.001（3.75 × 10⁻¹⁶⁵），效应量 η²=0.6863 属大效应（η² > 0.14 为大效应），拒绝 netbsd-src 不显著（p = 1.000），二者在 2003-2026 共同窗口内 commit 量分布相近（均值 1183 vs 1566，中位数 1156 vs 1450），而 freebsd-src ↔ openbsd-src（p = 2.75 × 10⁻²⁵）、freebsd-src ↔ dragonfly-src（p = 5.70 × 10⁻¹²⁰）、netbsd-src ↔   **辨析**：[2026-08-15 双库核查] FreeBSD-SA 713 条（1996-2026）经资料数据库.duckdb freebsd_sa 表直接 COUNT 验证；NVD CVE 各项目数量经 nvd_cve_metadata 表 bsd_projects 字段 GROUP BY 验证：FreeBSD 421、OpenBSD 143、NetBSD 82、DragonFly 32；原大纲 FreeBSD-SA 705/OpenBSD 168/NetBSD 136 已修正。Linux kernel 成为 CNA 后其 CVE 编号分配速度是否优于 BSD 须以 2024 年后数据对比；BSD 项目是否曾集体申请成为 CNA 需查 MITRE 历史申请档案；Linux kernel security team 的私密邮件列表机制是否削弱了漏洞响应透明度存在社区争议；【0 信任原则·commit 量不等于安全响应深度】L7.3.1 commit 量与贡献者数量对比反映开发规模差异，不直接等同于安全响应质量，须结合 SA 公告发布周期、CVE 修复滞后时间、回溯补丁覆盖率等指标综合判断；【0 信任原则·CVE 数量不等于漏洞数量】统计结论 [E-21]/[E-22]/[E-23]/[E-24] NVD CVE 数量受 NVD CPE 命名完整性影响（DragonFly BSD 仅 1 个 CVE 为 CPE 命名缺失而非实际漏洞稀少），且 CVE 披露存在滞后与选择偏差，726 个 CVE 仅为 NVD 收录部分，不等于 BSD 4 项目实际漏洞总量；【0 信任原则·SA 公告统计口径】统计结论 [E-25] 382 条 FreeBSD-SA 为官方存档计数（2008-04 至 2026-06-30），部分早期 SA 可能已归档或合并，数据须与 freebsd-security 邮件列表存档交叉验证；【0 信任原则·CVSS 跨版本不可直接比较】统计结论 [E-26]/[E-27]/[E-28] 平均 CVSS 含 CVSS v2 与 v3 混合评分，跨版本评分不可直接算术平均，该均值为近似指标，且跨项目 CVSS 均值差不直接等同于安全响应质量差异；【0 信任原则·共同时间窗口限制】统计结论 [C-16]/[C-17] Kruskal-Wallis H 检验与 Dunn's 事后比较仅采用 2003-06 至 2026-07 共同窗口（278 月）以对齐 4 仓库，丢弃了 freebsd-src/netbsd-src 的 1993-2003 早期数据与 openbsd-src 的 1995-2003 早期数据，早期数据可能反映 BSD 项目初创期的差异；【0 信任原则·分布形状假设】Kruskal-Wallis 检验假设各组分布形状相似，实际 4 仓库的标准差差异极大（netbsd-src σ = 973 vs dragonfly-src σ = 112），可能违反假设，须结合描述性统计的正态性检验结果复核；【0 信任原则·commit 粒度变化】CSRG 时代倾向大颗粒 commit、现代 BSD 强调原子化小 commit，commit 计数的时间序列在 1990s 与 2020s 之间不可直接比较，C-16/C-17 的统计显著差异可能部分源于 commit 粒度变化而非纯粹的工程节奏分化；【0 信任原则·SVN-to-Git 迁移失真】FreeBSD 仓库 2008 年 CVS→SVN、2020 年 1 月 SVN→Git 迁移可能压缩历史 commit、重写作者字段或丢失原始时间戳，导致 commit 量分布失真，C-16/C-17 结论须结合 Task 6 变点检测（freebsd-src 变点 1999-08 非 2020-01 SVN-to-Git 迁移期）交叉验证；【统计显著 ≠ 实际显著】726 个 CVE 与 382 条 SA 的数量对比不直接等同于安全响应质量，须结合修复滞后时间、回溯补丁覆盖率等指标综合判断；C-16/C-17 的 η² = 0.6863 虽属大效应但仅反映组间差异的解释方差比例，不反映趋势方向，结合 Task 5 趋势检验 4 仓库的 commit 量趋势方向不同（freebsd-src 上升，其余下降），分布差异可能源于趋势分化；详见外部基准-Academic-CVE.md 第 2 节、推断性统计.md Task 7 与考据记录 20260727_第十二卷-统计学整合.md

## 319.2.2 BSD 主动代码审计文化与 Linux reactive 漏洞修复模式的哲学对照

  **要点**：OpenBSD 自 1996 年起践行主动代码审计（proactive auditing）文化，Theo de Raadt（西奥·德·若特） 主张“漏洞应在被发现前消除”，openbsd.duckdb 查询 L3.1.1.audit 显示 openbsd-src 中含 `audit` 关键词的 commit 自 1996 年起持续活跃，与 OpenBSD errata 563 条记录共同构成“审计-修复-加固”循环；FreeBSD 安全团队采用 reactive 漏洞响应模式，freebsd.duckdb 查询显示 freebsd-src 1791 条 CVE commit 中绝大多数为漏洞披露后修复，主动审计类 commit 较少；Linux kernel 采用 reactive 模式，依赖 CVE 报告与外部安全研究者提交补丁，2024 年成为 CNA 后 CVE 编号分配速度提升但主动审计投入有限；illumos 继承 Solaris 的安全审计传统但社区规模萎缩，freebsd.duckdb 查询 L7.4.1 显示 illumos-gate 中 ZFS 路径 commit 仅 22 条结果反映其活动量较低
  **史料**：OpenBSD 主动代码审计文化档案（openbsd.org 2026-07-22 直接访问确认"Only two remote holes in the default install, in a heck of a long time!"标语）、Theo de Raadt 演讲存档、FreeBSD Security Team 文档、Linux kernel security 文档、illumos-gate.duckdb 查询 L3.1.1.audit（OpenBSD `audit` 关键词 commit 演化）、illumos-gate.duckdb 查询 L7.4.1（illumos-gate ZFS 路径 commit 历史，22 行结果）［A］
  **史观**：总纲第 4 条——分离与聚合，OpenBSD 主动审计文化与 Linux reactive 模式是两种分离的安全哲学；延续与终结，OpenBSD 审计文化延续 CSRG 代码审查传统，Linux reactive 模式终结了 Unix 时代的代码审查
  **辨析**：“Only two remote holes”标语的具体起始年份需查 OpenBSD 官方页面历史存档（2007 年首次出现）；OpenBSD 主动审计的实际效果是否优于 reactive 模式须以漏洞密度（每千行代码漏洞数）对比，但 BSD 与 Linux 代码规模差异使该指标难以直接计算；illumos 社区规模萎缩是否导致安全审计投入下降需查 illumos-gate commit 时间序列；【0 信任原则·关键词匹配局限】L3.1.1.audit 查询以 `audit` 为关键词，可能匹配非安全审计语境（如 filesystem audit），须与 commit message 原文交叉验证
  **文献**：OpenBSD“Only two remote holes” [EB/OL]. <https://www.openbsd.org/> (2026-07-22 访问)；Theo de Raadt“OpenBSD Security”演讲；bsd_commits.duckdb 查询 L3.1.1.audit 与 L7.4.1，见 `原材料/研究/bsd仓库分析/数据分析/深层信息挖掘.md` §L3.1.1 与 `衍生项目与跨项目对比分析.md` §L7.4

## 319.2.3 BSD MFC/pullup/errata 回溯机制与 Linux stable/illumos 发行版特定补丁的工程差异

  **要点**：四大 BSD 各自维护独立的漏洞修复回溯机制——FreeBSD MFC（Merge From Current）将 head 分支修复回溯至 stable/ 分支，freebsd.duckdb 查询 L3.1.1 显示 freebsd-src 中含 `MFC` 关键词的 commit 持续活跃；NetBSD pullup 机制将 -current 修复回溯至 release branches；OpenBSD errata patches 机制为已发布版本提供二进制补丁；DragonFly BSD 无明确回溯机制，依赖 release branch 维护；Linux kernel stable tree 由 Greg Kroah-Hartman 维护，将主线修复回溯至 stable kernels（5.4.x、5.10.x、5.15.x、6.1.x、6.6.x 等 LTS 版本），freebsd.duckdb 查询 L7.3.1 显示 Linux kernel commit 量远超 BSD 但回溯机制透明度较低；illumos 无统一回溯机制，各发行版（OmniOS、OpenIndiana、SmartOS）各自维护发行版特定补丁
  **史料**：FreeBSD MFC 文档（freebsd.org 2026-07-22 直接访问确认 MFC 为 FreeBSD release engineering 标准流程）、NetBSD pullup 文档、OpenBSD errata 机制文档、Linux kernel stable tree 维护文档（kernel.org 2026-07-22 直接访问确认 Greg Kroah-Hartman 为 stable tree 维护者，LTS 版本清单含 5.4/5.10/5.15/6.1/6.6）、illumos 发行版各自的安全公告页面［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］；illumos-gate.duckdb 查询 L3.1.1（MFC 关键词 commit 演化）、L7.3.1（Linux vs BSD commit 对比）［A］
  **史观**：总纲第 9 条——企业研究的双重性，Linux stable tree 由企业赞助维护（Google、Microsoft、Intel 等），BSD MFC/pullup/errata 由社区志愿者主导；总纲第 23 条——社区治理与经济约束共同决定回溯机制
  **辨析**：MFC 回溯的具体周期（平均修复到回溯的天数）需查 freebsd-src commit 时间序列中 `MFC` 标记 commit 与原 commit 的时间差；Linux stable tree 回溯是否覆盖所有 CVE 修复需查 stable kernel changelog；illumos 发行版特定补丁是否回馈上游 illumos-gate 需查 commit 流向；Greg Kroah-Hartman 个人 commit 占比是否构成 bus factor 风险需查 L3.4.1
  **文献**：FreeBSD Release Engineering [EB/OL]. <https://www.freebsd.org/releng/> (2026-07-22 访问)；Linux Kernel Stable Tree [EB/OL]. <https://www.kernel.org/category/releases.html> (2026-07-22 访问)；OpenBSD Errata FAQ；freebsd.duckdb 查询 L3.1.1 与 L7.3.1，见 `原材料/研究/bsd仓库分析/数据分析/深层信息挖掘.md` §L3.1.1 与 `衍生项目与跨项目对比分析.md` §L7.3

## 319.2.4 史料辨析：BSD、Linux、illumos 安全响应透明度与社区参与机制比较

  **要点**：BSD 项目安全响应透明度较高——FreeBSD-SA、NetBSD-SA、OpenBSD errata 均为公开档案，漏洞披露后修复 commit 直接进入公开仓库；Linux kernel security team 采用半透明机制——敏感漏洞在修复前通过私密邮件列表协调，修复后公开发布 CVE 与补丁；illumos 透明度最低——无统一 SA 公告体系，各发行版自行披露；freebsd.duckdb 查询显示 freebsd-src CVE commit 1791 条、netbsd-src 1301 条、openbsd-src 165 条、dragonfly-src 122 条、illumos-gate 无 CVE commit（22 条 ZFS 路径 commit 中无 CVE 编号引用），反映 illumos 社区对 CVE 编号引用习惯的缺失
  **史料**：四大 BSD 官方 SA 公告存档、Linux kernel security team 工作流程文档、illumos 各发行版安全公告页面、freebsd.duckdb CVE commit 查询结果（freebsd-src 1791 条、netbsd-src 1301 条、openbsd-src 165 条、dragonfly-src 122 条、illumos-gate 0 条 CVE commit）、互联网档案馆 illumos 历史存档［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］〔L1 代码/构建产物〕
  **史观**：边缘者贡献，BSD 公开 SA 档案体现社区参与透明度；社区与文明历史哲学，安全响应透明度是社区文明的反映
  **辨析**：illumos-gate 0 条 CVE commit 是否反映其漏洞稀少或 CVE 引用习惯缺失需查 illumos 邮件列表存档（本研究未发现 illumos 统一 CVE 引用规范）；Linux kernel security team 半透明机制是否延缓了漏洞披露需查历史案例（如 2014 年 Heartbleed 协调过程）；BSD 公开 SA 档案的完整性需逐条核对（DragonFly VSA 官方页面 404，须以邮件列表存档与数据库提取构建索引）；详见考据记录 20260722_bsd-cve-vulnerability-fact-check-第十二卷.md
