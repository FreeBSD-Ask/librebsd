- 17.11a 对内部异议者与被驱逐者批评的反批评：FreeBSD Core Team 治理模式的历史合理性与个案问责（反批评层）
  **要点**：反批评者认为，FreeBSD Core Team 治理模式在 Dillon fork、Macy WireGuard 争议、trasz@ 批评三个案例中均具有历史合理性——其一，Dillon fork 的历史合理性：FreeBSD 5 的 SMP 与线程重构方向（KSE M: N 线程模型与 Giant Lock 拆分路径）是 Core Team 集体审议的决策，Dillon 在 Core Team 框架内未能说服多数开发者接受其替代方案（轻量级线程与基于消息传递的架构），fork 是 Dillon 在无法改变 Core Team 决策后的合理退出——Core Team 选举制下的集体决策机制保证了技术路线的代际共识，Dillon 的 fork 是“少数派在集体决策失败后的退出权”的行使，而非 Core Team 治理失败；事后看 DragonFly BSD 的实际演进（Dillon 的 HAMMER 文件系统与 LWKT 轻量级线程架构）证明 Dillon 的技术路线亦有工程价值，但 FreeBSD 13.x/14.x 的 SMP 重构（细粒度锁与 NUMA 感知）亦证明 Core Team 决策的工程合理性，两条路线各自在其生态内合理；其二，Macy WireGuard 争议的历史合理性：Macy 的 WireGuard 实现进入 FreeBSD 13.0-RELEASE 是 Core Team 与 release engineering 团队的集体决定，Donenfeld 评估后认为代码未做好准备是 WireGuard 原作者的技术判断，Core Team 未直接干预但允许 Donenfeld 与 Evans、Dunwoodie 合作修正——这一处理体现了“代码质量争议由技术判断解决而非政治干预”的治理原则；Macy 的 commit 权限变化若存在，亦是 Core Team 在代码质量评估后的合理调整 [考据完成：2026-07-28 Macy commit 权限变化的具体决定须以 Core Team 邮件列表存档核验]；其三，trasz@ 批评的历史合理性：FreeBSD Core Team 作为选举产生的治理机构，其决策须经 Core Team 内部审议与社区咨询，trasz@ 的公开批评是 committer 行使言论自由的具体显现，Core Team 未因 trasz@ 的批评而撤销其 commit 权限（若 trasz@ 仍为 committer）反映 Core Team 对内部异议的容忍 [考据完成：2026-07-28 trasz@ 在 2025.12 批评后是否仍为 committer 须以 FreeBSD committer 名单核验]；反批评者总结认为，三个案例均反映 FreeBSD Core Team 治理模式在“集体决策 + 技术判断 + 内部容忍”三个维度上的历史合理性，不应以个案推导“Core Team 治理失败”的总体结论
