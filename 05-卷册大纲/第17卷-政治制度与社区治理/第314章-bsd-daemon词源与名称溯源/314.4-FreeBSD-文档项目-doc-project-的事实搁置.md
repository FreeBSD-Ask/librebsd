# 314.4 FreeBSD 文档项目（doc project）的事实搁置

## 314.4.1 FreeBSD 文档项目的历史架构：Handbook/FAQ/Articles 的 CVS/SVN 仓库

  **要点**：FreeBSD 文档项目（Documentation Project，简称 doc project）独立于源码项目（src project）与 Ports 项目（ports project），拥有独立的 doc 仓库（最初 CVS，后迁 SVN，2020 年随主仓库迁 Git）；文档项目包括 FreeBSD Handbook（核心手册）、FAQ（常见问题）、Articles（专题文章）、Man Pages（手册页）、Web 站点内容（www 仓库）；doc committer 与 src committer 是不同权限类别，doc committer 仅能修改文档；文档项目在 1995-2005 年活跃，Handbook 多次重构（如 2003 年 DocBook 迁移、2014 年 Hugo 迁移）；2020 年迁 Git 后文档项目活跃度持续下降
  **史料**：FreeBSD doc 仓库 commit 历史；FreeBSD Handbook 版本档案；FreeBSD Documentation Project 章程；commit 邮件列表存档 ［A］
  **史观**：社区与文明历史哲学，文档是文明传承的物质载体，文档项目搁置即文明记忆的断层；总纲第 7 条——文化历史哲学，文档作为“形式主义化的非存在”在社区中常被低估
  **辨析**：doc/ports/src 三仓库的独立性与权限模型须准确描述；Handbook 重构的具体时间与决策过程须考据；2020 年 Git 迁移对文档项目的影响须有量化数据
  **文献**：FreeBSD doc 仓库；Handbook 历史；Documentation Project 章程；commit 邮件列表 ［A］

## 314.4.2 文档贡献者二等公民化与提交者制度对文档的轻视

  **要点**：FreeBSD committer 制度中 doc committer 与 src committer 在权限等级、决策参与、社区声望上存在结构性差异；src committer（源码提交者）被视为“真正的开发者”，doc committer（文档提交者）常被视为“二等公民”；此现象在邮件列表讨论、Core Team 选举、会议演讲邀请中均有体现；NetBSD 与 OpenBSD 亦存在类似差异（如 OpenBSD 的 FAQ 维护者与 src 开发者的关系）；DragonFly BSD 因项目规模小，文档与源码差异不显著；此二等公民化是 BSD 文化“代码中心主义”的体现，与开源运动“文档与代码本体平等”理念相悖
  **史料**：FreeBSD 邮件列表中 doc committer 与 src committer 关系讨论；Core Team 选举记录中 doc committer 的参与情况；BSDCan/AsiaBSDCon/EuroBSDCon 演讲邀请记录；用户文章关于 BSD 文档二等公民化的论述 ［A］
  **史观**：社区与文明历史哲学，文档与代码的等级化是社区权力结构的微观体现；总纲第 19 条——历史解释学与权力，“二等公民化”是话语权运作在贡献者等级中的呈现
  **辨析**：“二等公民”是贡献者主观感受还是结构性事实须分别考据；不同 BSD 项目（FreeBSD/NetBSD/OpenBSD/DragonFly BSD）的文档贡献者地位须分别考察，避免普世化；用户文章的论断须按 0 信任原则考据
  **文献**：FreeBSD 邮件列表档案；Core Team 选举档案；BSD 会议演讲记录；用户文章 ［A］

## 314.4.3 文档项目事实搁置的表现：Handbook 更新滞后、翻译项目停滞、doc committer 老龄化

  **要点**：FreeBSD Handbook 部分章节自 14.0-RELEASE（2023 年 11 月 20 日，www.freebsd.org/releases/14.0R/announce/ 官方公告与 freebsdfoundation.org 2024-06-04“FreeBSD 14.1: What's new”交叉印证）后更新滞后，新特性（如 OpenZFS 2.2、PECOFF 支持、wireguard 改进）文档化不及时；多语言翻译项目（中文、日文、俄文、德文、西班牙文等）多数停滞，仅保留少数维护者；doc committer 群体老龄化，新增 doc committer 速度远低于退休速度；2023-2025 年 FreeBSD Foundation 雇佣专职文档工程师（如 Glen Barber（格伦·巴伯）、Li-Wen Hsu（许立文））部分缓解但未根本扭转；doc 项目“事实搁置”非官方宣布而是事实状态——名义上仍活跃，实际上多数章节长期无更新
  **史料**：FreeBSD Handbook 各章节最后更新时间统计；多语言翻译项目状态档案；doc committer 活跃度统计；FreeBSD Foundation 员工档案 ［A］
  **史观**：总纲第 18 条——时间哲学与历史，“事实搁置”是时间性在文档项目中的呈现——非正式死亡而是缓慢失活；总纲第 25 条——终结中的延续，名义延续与实质停滞的张力是“终结中的延续”的典型
  **辨析**：“事实搁置”的判断须有量化数据支持（如各章节最后更新时间分布）；不同文档（Handbook/FAQ/Articles/Man Pages）的搁置程度须分别考察；专职文档工程师的雇佣是否实质改善须有数据
  **文献**：FreeBSD Handbook 章节更新统计；翻译项目档案；doc committer 统计；Foundation 员工档案 ［A］

## 314.4.4 史料辨析：doc project 活跃度统计与文档团队口述历史

  **要点**：doc project 活跃度统计须基于 git commit 频率、提交者数量、PR 解决速度、Handbook 章节更新频率等多维度量化；文档团队口述历史须收集现役与退休 doc committer 的访谈；FreeBSD Foundation 关于文档项目的公开声明须考据；用户文章关于 doc 项目搁置的论述须按 0 信任原则考据；须区分“事实搁置”与“项目死亡”——doc 项目仍有维护，只是活跃度大幅下降
  **史料**：doc 仓库 git 统计；doc committer 访谈；Foundation 声明；用户文章 ［A］
  **史观**：史学方法论，量化统计与口述历史的结合是史学方法的双轨；0 信任原则——口述历史须警惕记忆偏差与自利偏差
  **辨析**：git commit 频率统计的方法论（按 commit 数/按变更行数/按提交者）须明确；“事实搁置”与“项目死亡”的判断边界须明确；不同 BSD 项目的文档状态须分别考察
  **文献**：doc 仓库 git 历史；口述历史档案；Foundation 声明；用户文章 ［A］
