# 321.2 BSD 通用习俗特殊文化考据

## 321.2.1 BSD license 添加传统：源文件头部 BSD license 模板与 SPDX 现代化

  **要点**：BSD license 自 4.3BSD（1986 年）与 4.4BSD（1994 年）时代确立模板，CSRG 在源文件头部统一添加版权声明；FreeBSD、NetBSD、OpenBSD、DragonFly BSD 均继承此传统；FreeBSD Committer's Guide 第 10 节 “Preferred License for New Files” 规定新文件默认采用 BSD 2-clause license，第 11 节 “Keeping Track of Licenses Granted to the FreeBSD Project” 与第 12 节 “SPDX Tags in the tree” 规范 license 追踪与 SPDX 标签；FreeBSD 已引入 SPDX 标签（SPDX-License-Identifier: BSD-2-Clause）以现代化 license 管理，NetBSD、OpenBSD、DragonFly BSD 仍主要使用传统 BSD license 模板；OpenBSD Policy 页面明确 "ISC or Berkeley style licences are preferred, the GPL is not acceptable when adding new code“；BSD license 是 BSD 项目最深远的文化遗产，”permissive“（宽松）许可哲学与 GPL 的 ”copyleft" 形成对照
  **史料**：FreeBSD Committer's Guide 第 10 节 “Preferred License for New Files”（<https://docs.freebsd.org/en/articles/committers-guide/#pref-license>，访问 2026-07-27）；FreeBSD Committer's Guide 第 12 节 “SPDX Tags in the tree”（<https://docs.freebsd.org/en/articles/committers-guide/#spdx.tags>）；OpenBSD Policy 页面（<https://www.openbsd.org/policy.html>，访问 2026-07-27，原文 "ISC or Berkeley style licences are preferred, the GPL is not acceptable when adding new code"） ［A］
  **史观**：总纲第 13 条——法律与道德是利益分配，BSD license 作为法律工具是利益分配机制的具体显现，“谁有权使用代码” “谁有权闭源衍生品” 是利益分配的具体形式，与 GPL 的 copyleft 形成对照；总纲第 4 条——分离聚合是永恒规律，BSD license 自 CSRG 时代聚合至 FreeBSD、NetBSD、OpenBSD、DragonFly BSD 四大分支，是分离聚合律的具体显现；总纲第 5 条——没有必然性，只有偶然性，BSD license 模板的形式（二句版 vs 三句版）与 SPDX 现代化的引入皆是项目偶然选择的结果，而非许可演化的必然路径；总纲第 7 条——理论必须自反，本子节作为 BSD license 添加传统的考据叙事，自身亦嵌入 “permissive 即许可善” 的前理解，须自觉呈现这一前理解；总纲第 23 条——一切历史写作都是基于哲学设定的历史小说，“BSD license 是 BSD 项目最深远的文化遗产” 等文化意义叙事是史家基于当下史料的形式主义建构
  **辨析**：考据过程留痕——【查证来源】FreeBSD Committer's Guide 第 10 节经 docs.freebsd.org/en/articles/committers-guide/#pref-license 一手核验；第 12 节 “SPDX Tags in the tree” 经 docs.freebsd.org/en/articles/committers-guide/#spdx.tags 一手核验；OpenBSD Policy 页面经 openbsd.org/policy.html 一手核验，确认 "ISC or Berkeley style licences are preferred, the GPL is not acceptable when adding new code" 表述；【交叉验证方法】BSD license 模板的演化（4.3BSD 1986 至 4.4BSD 1994 至 SPDX 现代化）须以 CSRG 原始源码、各 BSD 项目源码、SPDX 规范三源互证；FreeBSD 与 NetBSD、OpenBSD、DragonFly BSD 的 license 模板差异须以各项目源码头部互证；【0 信任原则·“4.3BSD 1986 年确立模板”】“BSD license 自 4.3BSD（1986 年）与 4.4BSD（1994 年）时代确立模板” 的考据须以 CSRG 原始源码核验，本考据以既有学术文献（如 McKusick 与 Neville-Neil《The Design and Implementation of the FreeBSD Operating System》）为间接依据；【0 信任原则·“NetBSD、OpenBSD、DragonFly BSD 仍主要使用传统 BSD license 模板”】各 BSD 项目当前 license 模板使用情况须以各项目源码头部实际样本核验，本考据以定性观察为依据；【0 信任原则·SPDX 标签覆盖率】FreeBSD 已引入 SPDX 标签的具体覆盖率（全树 vs 部分子系统）须以 FreeBSD 源码实际统计核验，本考据以 Committer's Guide 第 12 节为间接依据；【与同类 UNIX/BSD 习俗对比】Linux 内核采用 GPL-2.0-only；BSD license 模板因其简洁与宽松被大量非 BSD 项目采用（如 NTP、SQLite 等）；illumos 采用 CDDL 与 BSD 双许可；【自反性声明】本子节作为 BSD license 添加传统的考据叙事，自身嵌入 “permissive 即许可善” 的前理解，实际 BSD license 对项目商业采用与社区贡献的双重效应（如 FreeBSD Foundation 筹资 vs Linux Foundation 商业生态）须以多源交叉验证逼近史实
  **文献**：FreeBSD Documentation Project. FreeBSD Committer's Guide §10-12 [EB/OL]. <https://docs.freebsd.org/en/articles/committers-guide/>；OpenBSD Project. OpenBSD Policy [EB/OL]. <https://www.openbsd.org/policy.html> ［A］

## 321.2.2 man page 写作传统：BSD 工程文档形式与 intellectually honest 缺陷承认

  **要点**：man page 系统由 Unix 第 1 版（1971 年，Doug McIlroy 主导）创立；BSD 自 3BSD（1979 年）起强化 man page 工程；HISTORY 段与 BUGS 段自 4.2BSD（1983 年）成为标准；BSD man page 遵循严格格式：NAME、SYNOPSIS、DESCRIPTION、RETURN VALUES、ENVIRONMENT、FILES、EXAMPLES、DIAGNOSTICS、ERRORS、SEE ALSO、STANDARDS、HISTORY、AUTHORS、CAVEATS、BUGS、SECURITY CONSIDERATIONS；FreeBSD man pages 在线（man.freebsd.org）覆盖 FreeBSD 2.2.8 至 16.0-CURRENT、4.4BSD Lite2、4.3BSD NET/2、4.3BSD Reno、2.11 BSD、2.10 BSD、2.9.1 BSD、2.8 BSD、386BSD 0.0/0.1 等历史版本；OpenBSD man pages 同步 7.9；NetBSD man pages 覆盖多版本；“每个程序必须有 man page” 是 BSD 工程纪律；HISTORY 段保留代码历史脉络；BUGS 段诚实承认缺陷，体现 BSD 的 intellectually honest 传统
  **史料**：FreeBSD man pages 在线（<https://man.freebsd.org/>，访问 2026-07-27，覆盖 FreeBSD 2.2.8 至 16.0-CURRENT、4.4BSD Lite2、4.3BSD NET/2、4.3BSD Reno、2.11 BSD、2.10 BSD、2.9.1 BSD、2.8 BSD、386BSD 0.0/0.1 等历史版本）；OpenBSD man pages（<https://man.openbsd.org/>，访问 2026-07-27，同步 7.9）；NetBSD man pages（<https://man.netbsd.org/>，访问 2026-07-27） ［A］
  **史观**：总纲第 9 条——经验优先，man page 是工程实践的具体沉淀，每段格式（NAME、SYNOPSIS、DESCRIPTION 等）皆源于实际工程文档需求而非预先设计的理论框架；总纲第 4 条——分离聚合是永恒规律，man page 系统从 Unix 第 1 版（1971 年）聚合至 BSD（3BSD 1979 年起）是分离聚合律的具体显现；总纲第 7 条——理论必须自反，本子节作为 man page 写作传统的考据叙事，自身亦嵌入 “文档即工程善” 与 “intellectually honest 即道德善” 的前理解，须自觉呈现这一前理解；总纲第 23 条——一切历史写作都是基于哲学设定的历史小说，“BUGS 段体现 BSD 的 intellectually honest 传统” 等文化意义叙事是史家基于当下史料的形式主义建构
  **辨析**：考据过程留痕——【查证来源】FreeBSD man pages 在线经 man.freebsd.org 一手核验，覆盖 FreeBSD 2.2.8 至 16.0-CURRENT 与 4.4BSD Lite2、4.3BSD NET/2、4.3BSD Reno、2.11 BSD、2.10 BSD、2.9.1 BSD、2.8 BSD、386BSD 0.0/0.1 等历史版本；OpenBSD man pages 经 man.openbsd.org 一手核验，同步 7.9；NetBSD man pages 经 man.netbsd.org 一手核验；【交叉验证方法】man page 各段格式的演化（4.2BSD 1983 年 HISTORY/BUGS 段标准化）须以 4.2BSD 原始 man page 与 4.4BSD man page 互证；FreeBSD、OpenBSD、NetBSD 三大 BSD man page 的段格式差异须以同命令（如 ls(1)、grep(1)）的 man page 互证；【0 信任原则·“3BSD 1979 年起强化 man page 工程”】“BSD 自 3BSD（1979 年）起强化 man page 工程” 的考据须以 3BSD 原始 man page 核验，本考据以既有学术文献为间接依据；【0 信任原则·“4.2BSD 1983 年 HISTORY/BUGS 段标准化”】“HISTORY 段与 BUGS 段自 4.2BSD（1983 年）成为标准” 的考据须以 4.2BSD 原始 man page 核验，本考据以既有学术文献为间接依据；【0 信任原则·“每个程序必须有 man page”】“每个程序必须有 man page” 是 BSD 工程纪律的表述须以各 BSD 项目 Committer's Guide 或文档规范核验，本考据以定性观察为依据；【与同类 UNIX/BSD 习俗对比】Linux man pages 项目（man7.org、kernel.org）同样延续 Unix 传统；GNU info 系统是 GNU 项目对 man 的替代尝试，但 BSD 始终坚守 man page；【自反性声明】本子节作为 man page 写作传统的考据叙事，自身嵌入 “文档即工程善” 与 “intellectually honest 即道德善” 的前理解，实际 man page 工程的执行情况（如 BUGS 段的实际填充率、HISTORY 段的准确性）须以多源交叉验证逼近史实

## 321.2.3 BSD make 与 GNU make 区别传统：bsd.*.mk 宏文件与 /usr/share/mk/ 共享工程

  **要点**：BSD make 宏文件传统自 4.4BSD（1994 年）确立，包括 bsd.prog.mk（程序构建）、bsd.lib.mk（库构建）、bsd.man.mk（man page 安装）、bsd.dep.mk（依赖关系）、bsd.subdir.mk（子目录递归）等；BSD make（pmake）与 GNU make（gmake）语法差异显著——BSD make 使用 ${VAR} 与 .include 指令，GNU make 使用 $(VAR) 与 include 指令；BSD make 依赖系统定义的宏文件（位于 /usr/share/mk/）简化 Makefile 编写；FreeBSD ports 框架基于 bsd.port.mk，是 BSD make 工程应用的巅峰；FreeBSD、NetBSD、OpenBSD、DragonFly BSD 均保留 /usr/share/mk/ 宏文件传统；pkgsrc 在非 NetBSD 平台使用 bmake 替代 make，NetBSD 官方文档明确 "use the bmake command instead of ‘make’ to run NetBSD make, which is required for correct pkgsrc operation"
  **史料**：NetBSD pkgsrc 文档（<https://www.netbsd.org/docs/software/packages.html>，访问 2026-07-27，原文 "Note that when using pkgsrc on a non-NetBSD system, use the bmake command instead of ‘make’ to run NetBSD make, which is required for correct pkgsrc operation"）；FreeBSD Porter's Handbook（<https://docs.freebsd.org/en/books/porters-handbook/>，访问 2026-07-27） ［A］
  **史观**：总纲第 9 条——经验优先，bsd.*.mk 宏文件是工程实践的具体沉淀，每个宏文件（bsd.prog.mk、bsd.lib.mk 等）皆源于实际构建需求而非预先设计的理论框架；总纲第 4 条——分离聚合是永恒规律，BSD make 从 GNU make 分离，形成 BSD 独有的宏文件聚合，是分离聚合律的具体显现；总纲第 7 条——理论必须自反，本子节作为 BSD make 与 GNU make 区别传统的考据叙事，自身亦嵌入 “简洁即工程善” 的前理解，须自觉呈现这一前理解；总纲第 23 条——一切历史写作都是基于哲学设定的历史小说，“bsd.*.mk 宏文件是 BSD 工程简洁性的体现” 等文化意义叙事是史家基于当下史料的形式主义建构
  **辨析**：考据过程留痕——【查证来源】NetBSD pkgsrc 文档经 netbsd.org/docs/software/packages.html 一手核验，确认 “use the bmake command instead of ‘make’ to run NetBSD make” 表述；FreeBSD Porter's Handbook 经 docs.freebsd.org/en/books/porters-handbook/ 一手核验；【交叉验证方法】bsd.*.mk 宏文件清单与演化须以 4.4BSD 源码、各 BSD 项目 /usr/share/mk/ 目录、FreeBSD Porter's Handbook 三源互证；BSD make 与 GNU make 语法差异须以同 Makefile 在 pmake 与 gmake 下的执行差异互证；【0 信任原则·“4.4BSD 1994 年确立宏文件传统”】“BSD make 宏文件传统自 4.4BSD（1994 年）确立” 的考据须以 4.4BSD 源码 /usr/share/mk/ 目录核验，本考据以既有学术文献为间接依据；【0 信任原则·宏文件清单完整性】“bsd.prog.mk、bsd.lib.mk、bsd.man.mk、bsd.dep.mk、bsd.subdir.mk” 的清单完整性须以各 BSD 项目 /usr/share/mk/ 目录实际样本核验，本考据以既有学术文献为依据；【与同类 UNIX/BSD 习俗对比】Linux 发行版主要使用 GNU make 与 autotools；BSD make 因简洁性被部分跨平台项目（如 pkgsrc）选用；illumos 与 Solaris 使用 Sun make，与 BSD make 与 GNU make 形成三方对照；【自反性声明】本子节作为 BSD make 与 GNU make 区别传统的考据叙事，自身嵌入 “简洁即工程善” 的前理解，实际 BSD make 宏文件的工程代价（如跨平台移植性、与现代构建系统如 CMake、Meson 的兼容性）须以多源交叉验证逼近史实

## 321.2.4 /usr/share/examples/ 传统：BSD 示例代码目录与可执行文档哲学

## 321.2.5 /usr/src/、/usr/obj/、/usr/local/、/usr/pkg/ 目录传统：BSD hier(7) 目录层次与工程纪律

  **要点**：/usr/src/ 自 4.2BSD（1983 年）起为源码目录；/usr/obj/ 为构建产物目录；/usr/local/ 为本地安装目录自 4.4BSD 标准化；/usr/pkg/ 为 NetBSD pkgsrc 默认安装前缀；BSD 目录层次（hier(7)）严格定义各目录用途——/usr/src/ 为系统源码（内核与基本系统）、/usr/obj/ 为构建 /usr/src/ 的中间产物（make obj 后产生）、/usr/local/ 为本地编译软件安装前缀（FreeBSD ports 默认前缀）、/usr/pkg/ 为 NetBSD pkgsrc 默认前缀（避免与 /usr/local 冲突）、/usr/ports/ 为 FreeBSD ports 树；所有 BSD 系统遵循 hier(7) 标准；DragonFly BSD 使用 /usr/local/（DPorts 基于 FreeBSD ports），NetBSD 使用 /usr/pkg/；清晰的目录层次是 BSD 工程纪律的体现，使系统构建可重复、可维护

## 321.2.7 securelevel 传统：BSD 内核安全级别与不可逆降级机制

  **要点**：securelevel 自 4.4BSD（1994 年）引入；BSD securelevel 是内核安全级别机制，分为多个级别——-1 永久不安全模式（permanently insecure）、0 不安全模式（insecure mode，默认启动状态）、1 安全模式（secure mode，无法清除文件 schg 标志、无法 /dev/mem、无法写已挂载文件系统的 raw 分区）、2 高度安全模式（highly secure mode，无法设置系统时间、无法写 /dev/mem 与 /dev/kmem）、3 网络安全模式（network secure mode，无法调整网络接口与 IP 防火墙规则）；FreeBSD、NetBSD、OpenBSD、DragonFly BSD 均保留 securelevel；NetBSD About 页面明确 "the traditional BSD securelevels further restrict operations that can be performed by even the superuser“；securelevel 是 BSD 安全设计的经典范例，将 ”even root cannot bypass" 制度化，与 chflags 结合实现纵深防御；高级别 securelevel 无法降级至低级别（除非重启）是 BSD 独有的不可逆安全机制
  **史料**：NetBSD About 页面（<https://www.netbsd.org/about/>，访问 2026-07-27，原文 "the traditional BSD securelevels further restrict operations that can be performed by even the superuser"）；NetBSD secmodel_securelevel man page（<https://man.netbsd.org/secmodel_securelevel>，访问 2026-07-27）；FreeBSD init(8) man page（<https://man.freebsd.org/cgi/man.cgi?query=init&sektion=8>，访问 2026-07-27，含 securelevel 描述） ［A］
