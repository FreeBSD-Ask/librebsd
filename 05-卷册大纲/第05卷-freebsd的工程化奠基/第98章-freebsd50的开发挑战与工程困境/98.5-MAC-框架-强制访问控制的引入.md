# 98.5 MAC 框架——强制访问控制的引入

## 98.5.1 强制访问控制的引入

  **要点**：MAC(Mandatory Access Control) 框架由 Robert Watson 等在 FreeBSD 5.0 引入，允许加载多个安全策略模块 (如 mac_biba/mac_mls/mac_none/mac_seeotheruids/mac_partition/mac_portacl)；目标是提供细粒度访问控制替代传统 UNIX 自主访问控制
  
**史料**：Watson BSDCon 2001 MAC 演讲、mac(4) 手册页、FreeBSD 5.0 Release Notes ［A］
  
**史观**：总纲第 6 条——形式主义膨胀与抽象克制，MAC 框架是抽象克制设计

## 98.5.5 再回应层（反批评层 + 再批评层）：Core Team 对 DragonFly fork 的回应与 Dillon 路线的后续验证

  **要点**：【反批评层】FreeBSD Core Team 对 Dillon 批评与 fork 决定的回应可从两个层面考察。其一，Core Team 在 fork 后的公开表态中未对 Dillon 个人进行进一步攻击，而是延续 5.x SMPng 路线，以实际工程进展回应 Dillon 对 5.x “too heavily mutexed” 的批评——5.3（2004-11-04）开始性能逐步改善，6.0（2005）回归稳定，7.1（2008-12-31）ULE 成为默认后 SMP 性能显著提升，证明细粒度锁路线在长期工程上是可行的。其二，Core Team 撤销 Dillon commit 权限的决议本身在公开档案中未检索到完整辩护文本，与 NetBSD Core Team 1994-12-23 撤销 de Raadt 权限时通过 Adam Glass（亚当·格拉斯） 邮件列表公开发布决议通知（参见第六卷第 1 章 1.3.5 节）形成对照——FreeBSD Core Team 选择以 “沉默回应” 而非 “公开辩护” 作为对撤权决定的反批评形式，这一沉默本身是史观素材。【再批评层】对 Core Team 反批评的再批评指出两层。其一，5.x 后续成熟不等于 5.x 路线 “必然正确”——5.0-5.2 时期的性能倒退是用户承受的真实代价，以 7.x 成熟反推 5.x 路线正确是回溯性建构；其二，DragonFly 的 LWKT 路线在后续也面临挑战——原定的内核级集群（single system image clustering）目标被放弃，DragonFly 官方历史页面承认 "This original design direction, although no longer the primary goal of the DragonFly project, has influenced many of the design decisions"；HAMMER 文件系统开发耗时远超预期（2008 年才随 2.0 发布）。再批评层指出，Dillon 2003 年对 5.x 的批评在短期内被 5.0-5.2 性能倒退所印证，但在长期被 FreeBSD 6.x/7.x 的成熟所修正；而 DragonFly 的无锁路线虽在 LWKT 子系统上取得工程成功，但其集群目标的放弃证明激进重构亦有代价

## 98.5.6 合图层：Dillon 冲突、撤权与 fork 的综合判断

  **要点**：综合 Dillon 与 Core Team 双方立场，5.x 时期的 Dillon 冲突、撤权与 DragonFly fork 事件并非单纯的 “个人性格冲突” 或 “路线对错”，而是 BSD 谱系在 SMP 现代化转型期 “分离聚合” 规律的必然呈现。Core Team 的 SMPng 细粒度锁路线与 Dillon 的 LWKT 无锁路线代表对多核未来的两种诚实判断——前者选择渐进改造但付出 5.x 早期性能倒退代价，后者选择激进重构但付出集群目标放弃代价；二者在 2003 年的技术语境下均非显然正确。撤权事件本身是组织权力对个人路线的终止，但 BSD 许可证使 fork 成为 “制度化的和解”——Dillon 携 4.x 代码另起 DragonFly，双方在代码层面保持法律上的和平。合图层不判定 “谁对谁错”，而呈现冲突作为 BSD 谱系演化张力的历史事实：FreeBSD 与 DragonFly 在本体论上地位相等，二者的分歧是 BSD 哲学多元探索的体现，而非零和博弈
