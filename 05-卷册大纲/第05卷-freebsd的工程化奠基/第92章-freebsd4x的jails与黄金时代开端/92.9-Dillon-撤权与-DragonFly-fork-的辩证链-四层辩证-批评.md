# 92.9 Dillon 撤权与 DragonFly fork 的辩证链——四层辩证（批评—反批评—再批评—合图）

## 91.9.1 批评层：Core Team 对 Dillon 协作风格与技术路线的批评

  **要点**：FreeBSD Core Team 对 Dillon 的批评集中于两点——协作风格与技术路线。协作风格层面，Core Team 认为 Dillon 技术风格强硬、坚持个人路线、难以与团队其他成员达成共识，在邮件列表中频繁与他人发生技术争执，导致团队协作成本高昂；技术路线层面，Core Team 主推 5.x SMPng（细粒度锁替代 Giant Lock）路线，而 Dillon 反对 5.x 的锁模型，主张从 4.x 以无锁的轻量级内核线程（LWKT）路线推进 SMP。Core Team 撤销 Dillon 提交权限（commit bit）的决定，正式理由为协作问题，但深层原因包含技术路线分歧。bsd_commits.db 数据显示，Dillon 在 freebsd-src 的最后一条 commit 为 2003-01-28T18:44:40Z（commit hash f959d237889c23cf709e1981c53a2ab62495a81a，message"Backout last commit by request."），距 5.0-RELEASE（2003-01-16）仅 12 天，此后 Dillon 在 FreeBSD 仓库的活动终止
  
**史料**：bsd_commits.db freebsd-src 仓库 commits 表 Dillon 最后 commit 记录（f959d237889c23cf709e1981c53a2ab62495a81a，2003-01-28T18:44:40Z）；freebsd-current 与 freebsd-hackers 邮件列表 2002-2003 年 Dillon 与 Core Team 成员的公开讨论；Dillon 2003-07-16 DragonFly BSD 公告（freebsd-current 邮件列表，lists.freebsd.org/pipermail/freebsd-current/2003-July/006889.html） ［A］
  
**史观**：总纲第 5 条——组织结构塑造技术路径，Core Team 的协作结构无法容纳 Dillon 的个人路线
  
**辨析**：考据过程留痕——【查证来源】Core Team 撤销 commit bit 的内部决策记录未完整公开，本节以 freebsd-current 邮件列表 2002-2003 年公开讨论与 Dillon 2003-07-16 DragonFly BSD 公告（<https://lists.freebsd.org/pipermail/freebsd-current/2003-July/006889.html>）为准；bsd_commits.db freebsd-src 仓库 commits 表 Dillon 末次 commit f959d237889c23cf709e1981c53a2ab62495a81a（2003-01-28T18:44:40Z，subject"Backout last commit by request."）经 SQL 查询一手核验，与 release/5.0.0 tag（2003-01-16T16:56:23Z）仅相隔 12 天；【交叉验证方法】Dillon 末次 commit 时间（代码级证据）与 Dillon 2003-07-16 公告中"the last few months"（最近几个月）的时间表述互证，确认撤权决议发生于 2003 年 1 月至 7 月之间；release/5.0.0 tagger_date（2003-01-16T16:56:23Z）与 Dillon 末次 commit（2003-01-28T18:44:40Z）的时序吻合，5.0-RELEASE 发布 12 天后 Dillon 即提交最后一条 commit；【0 信任原则·撤权理由的官方表述】Core Team 公开表述的“协作问题”理由可能掩盖技术路线分歧的深层原因，史家须区分“官方理由”与“实际原因”，不得因 Core Team 单方面表述即采信；"Backout last commit by request"这一最后 commit 主题是否暗示冲突已公开化，需对照邮件列表核实，不得仅凭 commit message 臆断；【存疑判定依据】Core Team 撤权决议的内部投票记录与各成员具体立场至今未完整公开，freebsd-core 私有列表存档未取得，决议程序是投票还是共识、各成员的具体立场均无法确证；本节以邮件列表公开讨论与 Dillon 公告为准，存疑保留待未来 Core Team 内部档案披露

## 91.9.2 反批评层：Dillon 的自我辩护与支持者的反驳

  **要点**：Dillon 对 Core Team 批评的反驳集中于技术判断的正确性。Dillon 在 2003-07-16 的 DragonFly BSD 公告中明确陈述其选择从 4.x fork 而非 5.x 的技术理由："I considered starting with a 5.x base but it is simply too heavily mutexed, it was actually faster to start with 4.x and move forward rather then to start with 5.x and move backwards."（我考虑过以 5.x 为基础，但它被互斥锁覆盖得太重了，从 4.x 开始向前推进比从 5.x 开始向后倒退实际上更快）。Dillon 的支持者进一步指出，5.0-5.2 性能倒退的事实印证了 SMPng 路线的代价——5.x 早期 SMP 性能反不如 4.x Giant Lock 模型，部分场景下因细粒度锁竞争导致 cacheline 抖动；DragonFly 的 LWKT（轻量级内核线程）子系统与 token 同步机制证明无锁 SMP 路线在工程上可行。Dillon 主张其技术路线并非“难以合作”，而是对 5.x 路线错误的诚实判断
  
**史料**：Dillon 2003-07-16 DragonFly BSD 公告原文（freebsd-current 邮件列表）；DragonFly BSD 官方历史页面（dragonflybsd.org/history/，明确记载"DragonFly BSD was forked from FreeBSD 4.8 in June of 2003, by Matthew Dillon"）；DragonFly BSD 仓库首条 commit（bsd_commits.db dragonfly-src 仓库，2003-06-17T02:57:24Z，commit hash 984263bcb83ad82313113c6ac840d99124d8f90c，message"Initial import from FreeBSD RELENG_4:"）；Phoronix 早期 FreeBSD 5.x 基准测试、freebsd-performance 邮件列表关于 5.x 性能倒退的讨论 ［A］
  
**史观**：总纲第 2 条——实践先于理论，5.x 性能倒退的实践印证了 Dillon 对锁模型的批评；总纲第 1 条——偶然性改写历史，Dillon 选择 4.x 而非 5.x 改变 BSD 谱系
  
**辨析**：考据过程留痕——【查证来源】Dillon 2003-07-16 DragonFly BSD 公告原文经 WebFetch 一手核验（<https://lists.freebsd.org/pipermail/freebsd-current/2003-July/006889.html>），发布时间为 Wed Jul 16 12:41:34 PDT 2003，标题拼写为"Annoucning DragonFly BSD!"（原文如此拼写），引文"I considered starting with a 5.x base but it is simply too heavily mutexed, it was actually faster to start with 4.x and move forward rather then to start with 5.x and move backwards."（注意原文"rather then"为 Dillon 原文拼写）经核验准确；DragonFly BSD 官方历史页面（<https://www.dragonflybsd.org/history/>）经 WebFetch 一手核验，明确记载"DragonFly BSD was forked from FreeBSD 4.8 in June of 2003, by Matthew Dillon"与"This original design direction, although no longer the primary goal of the DragonFly project, has influenced many of the design decisions"；bsd_commits.db dragonfly-src 仓库 commits 表首条 commit 984263bcb83ad82313113c6ac840d99124d8f90c（2003-06-17T02:57:24Z，subject"Initial import from FreeBSD RELENG_4:"）经 SQL 查询一手核验；【交叉验证方法】Dillon 公告（一手）、DragonFly 官方历史页面（二手但官方）、bsd_commits.db 首 commit 时间（代码级证据）三方互证——公告发布于 2003-07-16，首 commit 时间 2003-06-17，DragonFly 官方页面记载"June of 2003"与首 commit 时间吻合，差异为“代码 fork”与“公告发布”的时间差（约 29 天）；Dillon 公告中"the last few months"（最近几个月）的时间表述与首 commit 时间 2003-06-17 至公告日 2003-07-16 之间约 1 个月，与"few months"表述存在张力，可能 Dillon 将 2003 年 1 月末次 FreeBSD commit 后的筹备期（约 5 个月）一并计入；【0 信任原则·Dillon 自述的立场偏见】Dillon 公告属当事人自辩，其对 5.x"too heavily mutexed"的判断带有立场偏见，史家须结合 5.x 后续在 6.x/7.x 成熟的事实辩证看待，不得因 5.x 早期倒退即全盘否定 SMPng 路线；【存疑判定依据】5.0-5.2 性能倒退的具体基准测试数据未在 Dillon 公告中引用，Phoronix 早期 FreeBSD 5.x 基准测试与 freebsd-performance 邮件列表讨论为外部佐证，但具体测试场景与硬件配置需对照原始报告核验；"the logical continuation of the FreeBSD 4.x series"引文经 DragonFly 官方历史页面标注"as quoted in the announcement"，但 WebFetch 获取的公告原文中未直接出现这一表述，可能为公告后续邮件（006894.html 等下一条邮件）中的表述或 DragonFly 官方页面对公告的概括性引述，存疑保留待后续公告完整邮件线程核验

## 91.9.3 再批评层：对 Dillon 反驳的再批评

  **要点**：对 Dillon 反驳的再批评指出，DragonFly 的 LWKT 路线后续也面临重大挑战，Dillon 的“无锁”理想并非全然成功。其一，DragonFly 原定的内核级集群（single system image clustering）目标在 2007 年前后被放弃，官方历史页面承认"This original design direction, although no longer the primary goal of the DragonFly project, has influenced many of the design decisions"；其二，DragonFly 的 HAMMER 文件系统开发耗时远超预期（2008 年才随 2.0 发布），原定的集群基础设施未能实现；其三，FreeBSD 的 SMPng 路线虽在 5.x 付出性能倒退代价，但在 6.x/7.x 逐步成熟，7.1（2008-12-31）ULE 成为默认后 SMP 性能显著提升，证明细粒度锁路线在长期是可行的。再批评者认为，Dillon 对 5.x"too heavily mutexed"的批评在 2003 年有其道理，但 5.x 后续的演化证明 Core Team 的路线选择在长期是正确的
  
**史料**：DragonFly BSD 官方历史页面（dragonflybsd.org/history/，关于集群目标放弃的表述）；DragonFly BSD 2.0 Release Notes（2008，HAMMER 文件系统首次发布）；FreeBSD 7.1-RELEASE Release Notes（ULE 成为默认）；bsd_commits.db freebsd-src 仓库 tags 表 release/7.1.0 的 tagger_date = 2008-12-31T22:57:14Z ［A］
  
**史观**：总纲第 22 条——知识注定过时，Dillon 2003 年的判断在 2008 年后的 FreeBSD 演化中部分过时；总纲第 2 条——历史是形式主义化的非存在，“路线正确”本身是回溯性建构
  
**辨析**：考据过程留痕——【查证来源】DragonFly BSD 官方历史页面（<https://www.dragonflybsd.org/history/>）经 WebFetch 一手核验，明确记载"This original design direction, although no longer the primary goal of the DragonFly project, has influenced many of the design decisions"，原文以"no longer the primary goal"措辞承认集群目标已放弃，但未给出具体放弃年份；DragonFly BSD 2.0 Release Notes（2008）经核验记载 HAMMER 文件系统首次随 2.0 发布；FreeBSD 7.1-RELEASE Release Notes 与 bsd_commits.db freebsd-src 仓库 tags 表 release/7.1.0 的 tagger_date = 2008-12-31T22:57:14Z（tagger = cvs2svn，target_commit_hash 经 SQL 查询一手核验）互证，ULE 调度器在 7.1 成为默认；“2007 年前后”为概数，须对照 DragonFly 邮件列表（users@与 <kernel@dragonflybsd.org>）核实集群目标被明确放弃的决议时间；【交叉验证方法】DragonFly 官方历史页面（二手但官方）、DragonFly 2.0 Release Notes（一手发布文档）、FreeBSD 7.1-RELEASE Release Notes（一手发布文档）、bsd_commits.db freebsd-src tags 表 release/7.1.0 tagger_date（代码级证据）四方互证——HAMMER 2008 发布与 release/7.1.0 2008-12-31 tag 时序一致，二者在 2008 年时点同步验证 Core Team SMPng 路线“长期成熟”判断成立；【0 信任原则·“长期正确”的回溯性建构】称 Core Team 路线“长期正确”本身是一种回溯性建构，5.x 在 2003-2005 年的性能倒退是当时用户承受的真实代价，不得以 7.x 的成熟反推 5.x 路线“必然正确”——史家须区分“路线在长期被验证可行”与“路线从一开始即正确”两种判断，前者为事实陈述，后者为回溯性建构；DragonFly 的 HAMMER 文件系统虽开发耗时（2003 fork 至 2008 发布历时约 5 年）但最终成功，不得以其开发周期长即否定 LWKT 路线；【存疑判定依据】DragonFly 集群目标被明确放弃的具体年份未在官方历史页面给出，“2007 年前后”为概数，须对照 DragonFly 邮件列表存档核验；“5.x 性能倒退”在 Phoronix 与 freebsd-performance 邮件列表中的具体基准测试数据未在 Dillon 公告中引用，需后续补验具体测试场景与硬件配置；称“Core Team 路线长期正确”这一判断须以 5.x-7.x 完整 release cycle 的性能数据为据，当前仅以 7.1 ULE 默认为节点证据，存疑保留待 6.x-7.x 详细性能基准测试数据补验

## 91.9.4 合图层：fork 作为 BSD 谱系演化的必然张力

  **要点**：综合四方立场，Dillon 撤权与 DragonFly fork 事件并非单纯的“个人冲突”或“路线错误”，而是 BSD 谱系演化中“分离聚合”规律的必然呈现。Core Team 的 SMPng 路线与 Dillon 的 LWKT 路线代表对多核未来的两种诚实判断——前者选择细粒度锁的渐进改造，后者选择无锁线程化的激进重构；二者在 2003 年的技术语境下均非显然正确，5.x 的性能倒退与 DragonFly 的集群目标放弃分别证明了两条路线各自的代价。fork 的结果是 BSD 谱系增加了 DragonFly 这一独立探索分支，两条路线在后续十余年中分别演化——FreeBSD 的 SMPng 在 7.x 后成熟，DragonFly 的 HAMMER 文件系统与 LWKT 子系统亦成为 BSD 工程遗产的一部分。BSD 许可证使 fork 成为“和平分手”而非“战争”，这与 GPL 生态下的 fork 张力形成对照。合图层不判定“谁对谁错”，而呈现 fork 作为历史偶然中的必然张力
  
**史料**：上述 37.9.1-37.9.3 节综合史料；DragonFly BSD 官方历史页面；FreeBSD 5.x/6.x/7.x Release Notes ［A］
  
**史观**：总纲第 4 条——分离聚合是永恒规律，DragonFly 从 FreeBSD 分离是 BSD 谱系分合循环的一环；总纲第 25 条——终结与延续，fork 终结了 Dillon 在 FreeBSD 的贡献，延续了 BSD 哲学的多元探索
  
**辨析**：考据过程留痕——【查证来源】本节史料综合 37.9.1-37.9.3 节一手与二手史料：Dillon 2003-07-16 DragonFly BSD 公告（freebsd-current 邮件列表，<https://lists.freebsd.org/pipermail/freebsd-current/2003-July/006889.html>，经 WebFetch 一手核验）、DragonFly BSD 官方历史页面（<https://www.dragonflybsd.org/history/>，经 WebFetch 一手核验，明确记载"forked from FreeBSD 4.8 in June of 2003"）、bsd_commits.db freebsd-src 仓库 Dillon 末次 commit f959d237889c23cf709e1981c53a2ab62495a81a（2003-01-28T18:44:40Z，经 SQL 查询一手核验）、bsd_commits.db dragonfly-src 仓库首条 commit 984263bcb83ad82313113c6ac840d99124d8f90c（2003-06-17T02:57:24Z，经 SQL tagger_date（2003-01-16）时序吻合（5.0 发布 12 天后 Dillon 提交最后一条 commit），DragonFly 首 commit（2003-06-17）与 Dillon 公告（2003-07-16）时序吻合（fork 代码事实 29 天后公告），形成“撤权—fork—公告”完整时间链；BSD 许可证文本与 GPL 许可证文本对照核验“和平分手”表述的法律基础——BSD 许可证允许 fork 后双方独立演化无强制回馈条款，GPL 许可证要求 fork 后继续开源但亦不禁止 fork，二者在 fork 法律自由度上无本质差异，差异在 fork 后代码回流机制；【0 信任原则·合图层的立场中立】合图层须严格保持双方对称呈现，不得因 DragonFly 后续规模小于 FreeBSD 即判定其路线“失败”，亦不得因 FreeBSD SMPng 最终成熟即判定 Core Team“正确”——“成功”与“失败”的判定标准本身是回溯性建构，史家须以 2003 年时点的技术语境判断两条路线的合理性，而非以 2008 年或更晚的演化结果反推 2003 年的路线选择；“和平分手”的表述须以 BSD 许可证的实际法律框架为据，而非浪漫化 fork 事件——BSD 许可证使 fork 在法律上自由，但社区层面的张力并未因此消解（如 Dillon 公告中"too heavily mutexed"的判断仍带有对 FreeBSD 5.x 路线的否定）；fork 的“必然性”仅指 BSD 谱系的结构性张力（总纲第 4 条“分离聚合是永恒规律”），不指 Dillon 个人离开的必然——后者属偶然（总纲第 5 条“没有必然性，只有偶然性”），Dillon 个人在 2003 年 1 月末次 FreeBSD commit 后选择 fork 而非其他出路（如停止提交、转投其他 BSD 项目）属偶然性事件；【存疑判定依据】合图层“必然性”与“偶然性”的区分须以 BSD 谱系长期演化的多 fork 案例（如 OpenBSD fork 自 NetBSD 1996、DragonFly fork 自 FreeBSD 2003、LibreSSL fork 自 OpenSSL 2014）对照核验——若 BSD 谱系长期呈现 fork 频发现象，则 fork 的“结构性张力”判断成立；若仅为偶发，则“必然性”判断存疑，须对照其他 fork 案例核验；Dillon 个人离开 FreeBSD 的具体内部决策记录（如 Core Team 内部投票、各成员立场）至今未完整公开，本节以邮件列表公开讨论与 Dillon 公告为准，存疑保留待未来 Core Team 内部档案披露
