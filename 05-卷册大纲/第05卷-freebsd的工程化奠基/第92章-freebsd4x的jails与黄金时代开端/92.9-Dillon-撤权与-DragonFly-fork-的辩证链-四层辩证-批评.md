# 92.9 Dillon 撤权与 DragonFly fork 的辩证链——四层辩证（批评—反批评—再批评—合图）

## 92.9.1 批评层：Core Team 对 Dillon 协作风格与技术路线的批评

  **要点**：FreeBSD Core Team 对 Dillon 的批评集中于两点——协作风格与技术路线。协作风格层面，Core Team 认为 Dillon 技术风格强硬、坚持个人路线、难以与团队其他成员达成共识，在邮件列表中频繁与他人发生技术争执，导致团队协作成本高昂；技术路线层面，Core Team 主推 5.x SMPng（细粒度锁替代 Giant Lock）路线，而 Dillon 反对 5.x 的锁模型，主张从 4.x 以无锁的轻量级内核线程（LWKT）路线推进 SMP。Core Team 撤销 Dillon 提交权限（commit bit）的决定，正式理由为协作问题，但深层原因包含技术路线分歧。freebsd.duckdb 数据显示，Dillon 在 freebsd-src 的最后一条 commit 为 2003-01-28T18:44:40Z（commit hash f959d237889c23cf709e1981c53a2ab62495a81a，message“Backout last commit by request.”），距 5.0-RELEASE（2003-01-16）仅 12 天，此后 Dillon 在 FreeBSD 仓库的活动终止
  
**史料**：freebsd.duckdb freebsd-src 仓库 commits 表 Dillon 最后 commit 记录（f959d237889c23cf709e1981c53a2ab62495a81a，2003-01-28T18:44:40Z）；freebsd-current 与 freebsd-hackers 邮件列表 2002-2003 年 Dillon 与 Core Team 成员的公开讨论；Dillon 2003-07-16 DragonFly BSD 公告（freebsd-current 邮件列表，lists.freebsd.org/pipermail/freebsd-current/2003-July/006889.html） ［A］
  
**史观**：组织结构塑造技术路径（去条号留论旨）〔订正注：原挂“总纲第 5 条”系伪标签——权威第 5 条为“没有必然性，只有偶然性”；本条论旨（协作结构影响技术路线）不在权威 25 条目内，按处方去条号留论旨〕：Core Team 的协作结构无法容纳 Dillon 的个人路线
  
**辨析**：考据过程留痕——【查证来源】Core Team 撤销 commit bit 的内部决策记录未完整公开，本节以 freebsd-current 邮件列表 2002-2003 年公开讨论与 Dillon 2003-07-16 DragonFly BSD 公告（<https://lists.freebsd.org/pipermail/freebsd-current/2003-July/006889.html>）为准；freebsd.duckdb freebsd-src 仓库 commits 表 Dillon 末次 commit f959d237889c23cf709e1981c53a2ab62495a81a（2003-01-28T18:44:40Z，subject“Backout last commit by request.”）经 SQL 查询一手核验，与 release/5.0.0 tag（2003-01-16T16:56:23Z）仅相隔 12 天；【交叉验证方法】Dillon 末次 commit 时间（代码级证据）与 Dillon 2003-07-16 公告中“the last few months”（最近几个月）的时间表述互证，确认撤权决议发生于 2003 年 1 月至 7 月之间；release/5.0.0 tagger_date（2003-01-16T16:56:23Z）与 Dillon 末次 commit（2003-01-28T18:44:40Z）的时序吻合，5.0-RELEASE 发布 12 天后 Dillon 即提交最后一条 commit；【0 信任原则·撤权理由的官方表述】Core Team 公开表述的“协作问题”理由可能掩盖技术路线分歧的深层原因，史家须区分“官方理由”与“实际原因”，不得因 Core Team 单方面表述即采信；“Backout last commit by request”这一最后 commit 主题是否暗示冲突已公开化，需对照邮件列表核实，不得仅凭 commit message 臆断；【存疑判定依据】Core Team 撤权决议的内部投票记录与各成员具体立场至今未完整公开，freebsd-core 私有列表存档未取得，决议程序是投票还是共识、各成员的具体立场均无法确证；本节以邮件列表公开讨论与 Dillon 公告为准，存疑保留待未来 Core Team 内部档案披露

## 92.9.2 反批评层：Dillon 的自我辩护与支持者的反驳

  **要点**：Dillon 对 Core Team 批评的反驳集中于技术判断的正确性。Dillon 在 2003-07-16 的 DragonFly BSD 公告中明确陈述其选择从 4.x fork 而非 5.x 的技术理由：“I considered starting with a 5.x base but it is simply too heavily mutexed, it was actually faster to start with 4.x and move forward rather then to start with 5.x and move backwards.”（我考虑过以 5.x 为基础，但它被互斥锁覆盖得太重了，从 4.x 开始向前推进比从 5.x 开始向后倒退实际上更快）。Dillon 的支持者进一步指出，5.0-5.2 性能倒退的事实印证了 SMPng 路线的代价——5.x 早期 SMP 性能反不如 4.x Giant Lock 模型，部分场景下因细粒度锁竞争导致 cacheline 抖动；DragonFly 的 LWKT（轻量级内核线程）子系统与 token 同步机制证明无锁 SMP 路线在工程上可行。Dillon 主张其技术路线并非“难以合作”，而是对 5.x 路线错误的诚实判断
  
**史料**：Dillon 2003-07-16 DragonFly BSD 公告原文（freebsd-current 邮件列表）；DragonFly BSD 官方历史页面（dragonflybsd.org/history/，明确记载“DragonFly BSD was forked from FreeBSD 4.8 in June of 2003, by Matthew Dillon”）；DragonFly BSD 仓库首条 commit（dragonfly.duckdb dragonfly-src 仓库，2003-06-17T02:57:24Z，commit hash 984263bcb83ad82313113c6ac840d99124d8f90c，message“Initial import from FreeBSD RELENG_4:”）；Phoronix 早期 FreeBSD 5.x 基准测试、freebsd-performance 邮件列表关于 5.x 性能倒退的讨论 ［A］

## 92.9.3 再批评层：对 Dillon 反驳的再批评

  **要点**：对 Dillon 反驳的再批评指出，DragonFly 的 LWKT 路线后续也面临重大挑战，Dillon 的“无锁”理想并非全然成功。其一，DragonFly 原定的内核级集群（single system image clustering）目标在 2007 年前后被放弃，官方历史页面承认“This original design direction, although no longer the primary goal of the DragonFly project, has influenced many of the design decisions”；其二，DragonFly 的 HAMMER 文件系统开发耗时远超预期（2008 年才随 2.0 发布），原定的集群基础设施未能实现；其三，FreeBSD 的 SMPng 路线虽在 5.x 付出性能倒退代价，但在 6.x/7.x 逐步成熟，7.1（2008-12-31）ULE 成为默认后 SMP 性能显著提升，证明细粒度锁路线在长期是可行的。再批评者认为，Dillon 对 5.x“too heavily mutexed”的批评在 2003 年有其道理，但 5.x 后续的演化证明 Core Team 的路线选择在长期是正确的
  
**史料**：DragonFly BSD 官方历史页面（dragonflybsd.org/history/，关于集群目标放弃的表述）；DragonFly BSD 2.0 Release Notes（2008，HAMMER 文件系统首次发布）；FreeBSD 7.1-RELEASE Release Notes（ULE 成为默认）；freebsd.duckdb freebsd-src 仓库 tags 表 release/7.1.0 的 tagger_date = 2008-12-31T22:57:14Z〔存疑：经 duckdb 实测该时刻 tag 的 tagger 为 Ken Smith，cvs2svn 名下 release/7.1.0 为 2008-12-19T21:12:36Z，标记者与时间错配待回源核正〕［A］

## 92.9.4 合图层：fork 作为 BSD 谱系演化的必然张力

  **要点**：综合四方立场，Dillon 撤权与 DragonFly fork 事件并非单纯的“个人冲突”或“路线错误”，而是 BSD 谱系演化中“分离聚合”规律的必然呈现。Core Team 的 SMPng 路线与 Dillon 的 LWKT 路线代表对多核未来的两种诚实判断——前者选择细粒度锁的渐进改造，后者选择无锁线程化的激进重构；二者在 2003 年的技术语境下均非显然正确，5.x 的性能倒退与 DragonFly 的集群目标放弃分别证明了两条路线各自的代价。fork 的结果是 BSD 谱系增加了 DragonFly 这一独立探索分支，两条路线在后续十余年中分别演化——FreeBSD 的 SMPng 在 7.x 后成熟，DragonFly 的 HAMMER 文件系统与 LWKT 子系统亦成为 BSD 工程遗产的一部分。BSD 许可证使 fork 成为“和平分手”而非“战争”，这与 GPL 生态下的 fork 张力形成对照。合图层不判定“谁对谁错”，而呈现 fork 作为历史偶然中的必然张力
  
**史料**：上述 92.9.1-92.9.3 节综合史料；DragonFly BSD 官方历史页面；FreeBSD 5.x/6.x/7.x Release Notes ［A］
  
**史观**：总纲第 4 条——分离聚合是永恒规律，DragonFly 从 FreeBSD 分离是 BSD 谱系分合循环的一环；总纲第 3 条——不存在进步，只有权力再分配（存疑）〔订正注：原挂“总纲第 25 条——终结与延续”系伪标签（权威第 25 条为“逻辑是形式主义而非世界本身的结构”），按族例改挂第 3 条〕，fork 终结了 Dillon 在 FreeBSD 的贡献，延续了 BSD 哲学的多元探索

FreeBSD commit 后选择 fork 而非其他出路（如停止提交、转投其他 BSD 项目）属偶然性事件；【存疑判定依据】合图层“必然性”与“偶然性”的区分须以 BSD 谱系长期演化的多 fork 案例（如 OpenBSD fork 自 NetBSD 1996、DragonFly fork 自 FreeBSD 2003、LibreSSL fork 自 OpenSSL 2014）对照核验——若 BSD 谱系长期呈现 fork 频发现象，则 fork 的“结构性张力”判断成立；若仅为偶发，则“必然性”判断存疑，须对照其他 fork 案例核验；Dillon 个人离开 FreeBSD 的具体内部决策记录（如 Core Team 内部投票、各成员立场）至今未完整公开，本节以邮件列表公开讨论与 Dillon 公告为准，存疑保留待未来 Core Team 内部档案披露
