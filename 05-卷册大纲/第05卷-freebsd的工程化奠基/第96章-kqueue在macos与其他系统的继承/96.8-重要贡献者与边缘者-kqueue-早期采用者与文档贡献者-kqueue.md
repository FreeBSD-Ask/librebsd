## 96.8.5 跨项目采用实证：PostgreSQL 13 以 kqueue 替代 poll（2020）

  **要点**：Thomas Munro 在 BSDCan 2020 报告，PostgreSQL 13 以 **kqueue(2)** 替代 **poll(2)** 进行多路复用等待，大幅降低高核数、多活动连接系统的系统时间，类似于 Linux 上采用 **epoll(2)** 的改进（Munro, 2020）——补充 95.8.1 节“PostgreSQL 8.x 后端连接池”之后的新采用案例，显示 kqueue 在 2020 年代仍作为 FreeBSD 上主流数据库的事件通知接口持续生效
  
**史料**：Munro. PostgreSQL on FreeBSD [C]. BSDCan 2020. references_fulltext ref 717 ［A］
  
**史观**：总纲第 25 条——终结与延续，kqueue 从 FreeBSD 内核原语延续为跨项目采用的基础设施
  
**辨析**：Munro 同时为 PostgreSQL 与 FreeBSD 开发者（<tmunro@postgresql.org> 与 <tmunro@freebsd.org>），该采用属个人驱动还是社区共识须对照 PostgreSQL 13 release notes 核验；其报告中“大幅降低系统时间”为特定负载（hw.ncpu=88）下的观测，不得泛化为普遍结论
  
**文献**：Munro. PostgreSQL on FreeBSD: Some news, observations and speculation [C]//BSDCan 2020. Ottawa, 2020 ［A］

**要点**：

- 当事人概述 FreeBSD GNOME 团队的低层移植成果：网络与系统监控 applet 可监视无线状态、网络活动与文件系统统计，配合高层的 Evolution 与 Epiphany 构成完整桌面；其主张 GNOME 优于其他桌面之处在于开箱即用且高度模块化——普通用户得简单入门，老练用户可按需挑选 panel、Nautilus 等组件，不必整包安装。（BSDTalk EP32，[196.8-302.52]，L1）
- 当事人移植 D-BUS 的动因是 HAL（硬件抽象层）：HAL 有望把桌面与操作系统底层良好衔接，而其主依赖 D-BUS 当时使用者尚少；移植的唯一重大非 Linux 障碍是 socket 上的凭证传递，解决后移植即稳定可用，这构成 D-BUS 与桌面栈进入 FreeBSD 的早期技术节点。（BSDTalk EP32，[457.22-496.44]，L1）
- D-BUS 演化中渗入的 Linux 特性由 kqueue 对等化解：Linux 版以 inotify 监视新装应用带来的 D-BUS 服务、免重启系统总线，当事人用 FreeBSD 的 kqueue 内核接口实现同等能力，并以日常使用的 Rhythmbox 换曲弹窗（配合 libnotify）验证可用；他判断 D-BUS 将取代 GNOME 的 CORBA 与 libbonobo 消息基础设施，在 GNOME 2.14 中已被大量模块默认启用，而 freedesktop.org 正试图统一各桌面的底层设施以避免重复造轮子。（BSDTalk EP32，[498.96-696.06]，L1）
- FreeBSD GNOME 的两层发布模型：ports 树维护当前稳定版（2.14；因准备 FreeBSD 5.5 与 6.1 的 ports 冻结，树中一度仍为 2.12），开发版则在当事人自托管的 marcuscom.com CVS 树中推进；大量 FreeBSD 用户自愿测试不稳定代码，上游发布后数小时内即可宣布 FreeBSD 版本，并附截图、已知问题与新文档，用户因此获得经过生产桌面检验的版本。（BSDTalk EP32，[697.9-820.7]，L1）
- 当事人对 FreeBSD 桌面 KDE 偏好的观察与解释：DesktopBSD 等衍生项目与不少 FreeBSD 开发者偏向 KDE，或因 KDE 更早达到可用且令人安心的状态、外观更讨喜，而 GNOME 多年外观平淡（2.16 将有较大改变）； FreeBSD GNOME 组自认开创新技术——率先引入 D-BUS、维护 freetype、Mozilla 与 Firefox 等低层组件，且 GTK 桌面生态更为普及；他对各 fork 项目释放合作邀请。（BSDTalk EP32，[820.7-980.18]，L1）
- lighttpd 定位为极快、极轻量的 Web 服务器，目标是在低资源占用下维持大量并行连接，面向大量短连接的 Web 2.0 应用；与 Apache（在不使用事件 MPM 时每连接占一进程或线程）不同，lighttpd 为完全事件驱动的单进程单线程架构，无线程也无 fork，基于非阻塞 I/O——等待中的连接只是进程内的一个文件描述符加少量内存；仅受单进程文件描述符数限制且可调，可同时维持一万至两万连接；Keep-Alive 场景下等待连接近乎零成本，这对 AJAX 类低延迟小请求尤为关键。（BSDTalk EP61，[179.02-344.98]，L1）
- 项目起源：最初是 Boa、Mathopd、thttpd、Zeus 一类擅长静态内容的小型 Web 服务器（当年常被用作 Apache 的静态卸载前端），但自始即带 FastCGI 与 PHP 支持、sendfile 等系统级优化和 kqueue 等事件接口，迅速长成全功能服务器；作者自述直接动因是读到 Dan Kegel 论 C10K 问题（单机万级并行连接）的论文，想以此做概念验证，结果一做即快。（BSDTalk EP61，[88.68-146.44]，L1）
- 事件接口分层决定扩展性：select 与 poll 在所有平台可用（macOS 的 poll 为 select 模拟）但先天受限——select 默认上限 1024 连接、poll 每次返回全部描述符须线性扫描，连接越多系统调用开销越大；kqueue（BSD）、epoll（Linux）、dev-poll（Solaris）只返回发生变更的描述符，使服务器可按事件量而非连接量扩展，接近线性；lighttpd 维护多个事件处理器以适配各平台。（BSDTalk EP61，[539.84-733.94]，L1）
- 安全设计上，lighttpd 从不使用 C 字符串库函数，一切字符串操作先行长度检查、先确认内存再写入，以自有字符串函数集消除缓冲区溢出这一 C 语言服务器的主要攻击面；长度可知同时带来速度（便于追加与复用）；开发中以 Valgrind 与 KCacheGrind 检查性能与内存；重大漏洞约半年前与一年半前各一次，均与 Windows、macOS 默认大小写不敏感的文件系统有关——改变大小写即可绕过安全模式检查，Windows 从非其推荐的生产环境，macOS 则因 Web 服务器部署更多而受影响更实；对外提供 mod_secdownload 限时哈希 URL（10-30 秒有效，防深链盗链）与 X-Sendfile 式头部卸载：后端完成 LDAP、数据库、Kerberos 或 NTLM 等认证后交由服务器以 sendfile 零拷贝发送，兼顾认证安全与传输效率。（BSDTalk EP61，[1237.72-1657.12]，L1）
- 1.5 版本重写核心组件：Rails 社区改用 Mongrel（Ruby 小型 HTTP 服务器）以 HTTP 与前置服务器对话，暴露了现役 lighttpd HTTP 代理模块的最大短板——不处理故障转移，后端宕机时连接直接报错、由客户端重试其他后端；新版 mod_proxy_core 整合 FastCGI、SCGI、HTTP 协议，向后端提供 keep-alive 与 HTTP/1.1，内置轮询与哈希两种负载均衡、故障转移，并向后端提供 sendfile 支持；哈希均衡按 URL 分区，使同一页面的请求恒达同一后端，从而大幅提升后端缓存利用率。（BSDTalk EP61，[733.94-941.52]，L1）

**史料**：

- HAL 移植的节点性线索：当事人访谈前一日（约 2006 年 4 月 12 日）团队 Jean-Yves 宣布着手 HAL 移植，当事人手头亦有自写代码；HAL 若成功将大幅补足 FreeBSD 桌面特性但并非银弹；另有 amd64 构建服务器与 port 测试机项目维持多架构 GNOME 构建，ia64 无人桌面使用、sparc64 测试者长期失联。（BSDTalk EP32，[1228.06-1398.54]，L1）
- 该期提供 2006 年 lighttpd 大规模采用的当事人证词：YouTube 的 Flash 影片文件经 lighttpd 服务器发送（作者与其有读取路径优化的接触，瓶颈完全在磁盘寻道），Wikipedia 的全部图片经 Wikimedia 的 lighttpd 缩放后发送；Netcraft 月度统计中 Apache 约占七成，lighttpd 最近统计约九万套安装、多为此前受性能困扰而寻求扩展的站点；许多部署者从不联系作者，仅靠陌生邮件告知其服务器身份。（BSDTalk EP61，[1028.1-1230.56]，L1）

- 总纲13 法律与道德是利益分配：许可证在该案例中表现为利益分配的形式装置：作者此前的 GPL 项目（Webalizer 类日志分析器）限制其商业化路径，改用 BSD 则同时向贡献者（免版权转让）与使用者（可自由部署建业）开放收益空间，他自称这是“懒人的决定”——许可证的选择即利益结构的选定。（BSDTalk EP61，[1689.12-1788.84]，L1）
