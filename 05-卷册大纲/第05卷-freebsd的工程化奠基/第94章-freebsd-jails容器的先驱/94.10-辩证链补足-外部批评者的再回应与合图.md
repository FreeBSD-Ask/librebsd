# 94.10 辩证链补足：外部批评者的再回应与合图

## 94.10.1 VMware 阵营的再回应

  **要点**：针对 FreeBSD 阵营“批评基于旧版本”的反批评，VMware 阵营的再回应指出四点：其一，VMware 2018.2.27 博客“The Story of Containers”批评的是 Jails 设计层面的结构性限制——“a jail could only have one IPv4 address for communication and could only use UDP or TCP for communication (no raw sockets, no IPv6, etc.)”，这些限制在 Jails 设计之初即存在，并非“旧版本”问题；其二，VMware 博客明确指出 FreeBSD 后期放宽限制是“In response to the emergence of not so restricting container capabilities in other operating systems”，即在外部容器生态压力下的被动跟进，这一判断基于 Jails 改进时间线（VNET 于 8.0 引入、IPv6 支持更晚）与 Solaris Zones（2004）、LXC（2008）发展的对应关系，是结构性观察而非版本偏见；其三，“批评基于旧版本”的反批评本身可能是形式主义——以“版本更新”为标准否定批评的有效性，忽略了 Jails 在容器生态中的结构性位置（共享内核、缺乏镜像分发、缺乏编排层）并未因版本更新而根本改变；其四，外部批评与 jails 作者的自我评价在“虚拟化能力不足”这一判断上形成交叉印证——phk 本人在其个人网站 jails saga 中将文章标题直书为“Jails – High value but shitty Virtualization”，即“高价值但糟糕的虚拟化”，并明确承认 jails 不是优秀的虚拟化方案，这表明 VMware 阵营“severe restrictions”的批评并非外部偏见，而是与作者自我认知一致的工程判断，FreeBSD 阵营“批评基于旧版本”的反批评因此失去效力——作者本人未将“限制”视为待修正的缺陷，而是将其重新框定为“不完美虚拟化往往更可取”的有意设计

## 94.10.2 Rutgers 阵营的再回应

  **要点**：针对 FreeBSD 阵营“课程笔记非权威”或“批评未标注版本”的反批评，Rutgers 阵营的再回应指出三点：其一，Rutgers 课程笔记的批评“lacked fine-grained resource management”针对的是 Jails 的资源管理模型——Jails 早期缺乏 CPU、内存、进程数的细粒度配额，这是设计层面的工程事实，**mac_jail(4)** 与 **jail_set(2)** 后期的引入恰恰证明了这一不足的客观性；其二，课程笔记作为教学材料的权威性来自其系统性——Rutgers 操作系统课程基于标准教材（如 Silberschatz《Operating System Concepts》），其对 Jails 资源管理的批评反映了操作系统教学领域对资源管理的基本要求，这一要求是 Jails 早期未满足的；其三，“课程笔记非权威”的反批评可能忽略了批评的实质——即 Jails 在资源管理上的工程不足是客观存在的，**mac_jail(4)** 与 **jail_set(2)** 的后期引入本身就是对这一不足的承认
  
**史料**：Rutgers 大学操作系统课程笔记、Silberschatz《Operating System Concepts》资源管理章节、**mac_jail(4)** 手册页、**jail_set(2)** 手册页 ［A］

## 94.10.3 Solaris Zones 阵营的再回应

  **要点**：针对 FreeBSD 阵营“市场胜利非技术标准”的反批评，Solaris Zones 阵营的再回应指出四点：其一，Sun 的批评针对的是资源管理的工程完整性（CPU、共享内存、进程数的细粒度配额），并非以市场份额衡量技术价值；其二，Jails 的“轻量隔离优势”是事后追认的定位，phk 与 Robert Watson 合著的 SANE 2000 会议论文标题“Jails: Confining the Omnipotent Root”指向安全隔离而非轻量定位，2000 年的原始设计意图并非“轻量”，2004 年 ACM Queue 文章“Building Systems to be Shared Securely”亦将 jails 定位为“安全共享系统”方案；其三，Zones 的全局区域（global zone）管理模型提供了 Jails 缺乏的统一治理入口，这是工程架构差异而非形式主义偏见；其四，Sun 阵营“工程完整性”论存在自反性——phk 在 jails saga 中明确指出 Sun 在 Zones 推出前后就 jails 的“patently obvious aspects”（明显属于现有技术的方面）申请了十几项专利，其中部分专利覆盖的特性在 FreeBSD jails 实现中已存在，Sun 甚至在专利申请中引用 phk 与 Watson 的 SANE 文章作为参考，这表明 Sun 一边以 jails 为反面论证 Zones 的工程完整性，一边将 jails 已有的工程特性纳入自身专利范围，其“工程完整性”批评的客观性因此受到结构性削弱

## 94.10.4 Linux 容器阵营的再回应

  **要点**：Linux 容器阵营对 FreeBSD“先驱不被记住”叙事的再回应指出四点：其一，Docker 团队未公开否认容器技术有先驱，但其工程立场是“生态与标准化比时间先后更重要”；其二，Docker 的镜像分层、`Dockerfile` 声明式接口、Docker Hub 分发机制是 Jails 设计中不存在的工程层，并非简单“市场包装”；其三，“先驱”身份本身也是一种形式主义——以时间先后作为技术价值的评判标准，恰恰是 FreeBSD 阵营所批评的形式主义的镜像；其四，Docker 官方文档的叙事选择构成事实层面的“沉默抹除”——经查证 Docker 官方文档“Docker Overview”页面“The underlying technology”小节原文为“Docker is written in the Go programming language and takes advantage of several features of the Linux kernel to deliver its functionality. Docker uses a technology called namespaces to provide the isolated workspace called the container.”，该小节仅提及 Linux namespaces 与 Linux 内核特性，未提及 FreeBSD jails、Solaris Zones 等 BSD 谱系先驱，这一叙事选择既非明确否认亦非明确承认，而是通过“仅叙述 Linux 内核起源”的框架将 jails 排除在容器正史之外，其效果是让 Docker 用户在阅读官方文档时无从知晓 jails 的存在，这比明确否认更有效地实现了先驱的遗忘

## 94.10.5 合图层：商品形式主义与革命—改革方法论

  **要点**：合图层从项目史观总纲第 11 条与第 21 条审视整条辩证链。第 11 条“商品是形式主义”揭示：容器技术的市场选择不是自然选择，Docker 的胜利是资本、生态与营销的形式主义权力运作，而非技术优越性的自然显现；“劣币驱逐良币”的普遍规律在此表现为——Docker 以工程上较粗糙但生态上更激进的方案，驱逐了工程上更早更稳健但生态保守的 Jails。第 21 条“革命与改革”揭示：Linux 选择革命（Docker 彻底重建容器栈，引入镜像、声明式配置、编排层等全新抽象），BSD 选择改革（Jails 从 **chroot(2)** 增量演进而来，**jail_set(2)**、VNET 等改进均为渐进调适）；“改革的困难远高于革命”在此具象化——Jails 的渐进改进慢于 Docker 的革命性重建，不是因为 BSD 工程能力不足，而是改革方法论本身的结构性约束。综合四方再回应，辩证链收敛于一个判断：VMware 的“被动跟进”论、Rutgers 的“资源管理不足”论、Sun 的“工程完整性”论、Docker 的“生态优先”论，四者并非孤立批评，而是从不同维度共同揭示了 Jails 在容器生态中的结构性位置——Jails 是工程上的先驱，但不是生态上的革命者；这一位置不因 FreeBSD 阵营的反批评而改变，也不因外部批评的尖锐而否定 Jails 的历史价值。合图层须进一步承认争议的不可调和性：四方批评与 FreeBSD 阵营的反批评在“先驱是否应被记住”这一命题上无法达成一致——批评方以“生态完整性”与“工程完整性”为标准衡量 Jails，FreeBSD 阵营以“时间先后”与“安全隔离”为标准辩护 Jails，两套标准不可通约，任何一方说服对方都不可能，因为争议的根源不在事实层面（jails 早于 Docker 13 年这一事实各方均无异议），而在价值判断层面（时间先后是否构成技术价值、生态完整性是否构成评判标准），价值判断的分歧无法通过事实考据消解。和解路径唯一存在于 phk 本人提出的“不完美虚拟化”哲学——phk 在 jails saga 中陈述“we accidentally discovered that imperfect virtualization can and often is preferable to perfect virtualization, both as a matter of cost and as matter of security”，即“不完美的虚拟化往往比完美的虚拟化更可取，无论从成本还是安全角度”，这一陈述既承认了 jails 作为虚拟化方案的“不完美”（回应 VMware 与 Rutgers 的批评），又将其重新框定为有意的工程选择（回应 FreeBSD 阵营的辩护需要），从而在批评方与反批评方之间开辟了一条超越“先驱是否被记住”的第三条道路——jails 的历史价值不在于它是否是“好的容器”，而在于它发现了“不完美虚拟化”这一被后续容器生态遗忘的工程哲学
