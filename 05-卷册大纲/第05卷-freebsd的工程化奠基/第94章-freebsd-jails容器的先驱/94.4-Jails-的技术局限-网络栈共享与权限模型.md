# 94.4 Jails 的技术局限——网络栈共享与权限模型

## 93.4.1 网络栈共享的局限

  **要点**：早期 Jails 共享主机网络栈，每个 Jail 仅能绑定一个 IPv4 地址，不支持独立路由表、防火墙规则；VNET(8.0) 引入后才实现完全网络栈虚拟化
  
**史料**：jail(8) 手册页早期版本、VNET 设计文档、VMware 2018 容器史博客 ［A］
  
**史观**：总纲第 6 条——技术路线分化，Jails 网络共享与 VNET 完全虚拟化是两条路线
  
**辨析**：网络共享是否 “严重限制” 存在争议，VMware 2018 博客称 "severe restrictions"
  
**文献**：jail(8) 手册页；VNET 文档；VMware 2018 容器史博客 ［A］

## 93.4.2 特权分离机制不足

  **要点**：早期 Jails 的特权分离较粗，root in jail 仍能执行部分特权操作 (如绑定低端口)，后续通过 **mac_jail(4)** 与 **jail_set(2)** 参数细化；Rutgers 课程笔记批评 "lacked fine-grained resource management"
  
**史料**：mac_jail(4) 手册页、Rutgers 课程笔记、jail_set(2) 文档 ［A］
  
**史观**：总纲第 3 条——形式主义膨胀，早期 Jails 的粗粒度特权可能形式主义
  
**辨析**：批评是否 “客观” 需对照具体版本
  
**文献**：mac_jail(4) 手册页；Rutgers 课程笔记；jail_set(2) 文档 ［A］

## 93.4.3 局限性的效应分析

  **要点**：Jails 的局限性导致其在复杂容器场景被 Solaris Zones 与 Docker 超越，但在轻量隔离场景 (如共享主机、构建环境) 仍保持优势
  
**史料**：容器技术比较论文、Jails 部署案例、Zones/Docker 文档 ［B］
  
**史观**：总纲第 6 条——技术路线分化，不同场景适用不同技术
  
**辨析**：局限性的 “严重程度” 需结合场景评估
  
**文献**：容器技术比较；Jails 部署案例；Zones/Docker 文档[考据完成：2026-07-28 经穷尽联网考据，上述文献清单为已知公开来源汇总，部分原始档案未公开数字化或须付费访问，属史料缺口，须待原始档案公开后方可补充确证]

## 93.4.4 局限性史料辨析

## 93.4.5 Jails 论文所载 jailed root 限制清单（一手具体化）

  **要点**：Jails 论文（SANE 2000）列举 jailed root 的八项限制——禁止直接修改内核与加载内核模块、禁止修改网络配置（接口、地址、路由表）、禁止挂载/卸载文件系统、禁止创建设备节点、禁止访问 raw/divert/routing socket、禁止修改内核运行时参数（大部分 **sysctl(8)** 设置）、禁止修改 securelevel 相关文件标志、禁止访问与 jail 无关的网络资源（Kamp & Watson, 2000）——将 93.4.2 节“特权分离较粗”的批评具体化为一手限制清单，显示 jails 早期即对“全能 root”做了系统化裁剪
  
**史料**：Kamp & Watson. Jails: Confining the omnipotent root [C]. SANE 2000. references_fulltext ref 2689/499 ［A］
  
**史观**：总纲第 4 条——分离与聚合，八项限制以“禁止越出 jail 边界”为原则，是分离哲学的工程化清单
  
**辨析**：该清单为论文所述设计意图，实际实现（sys/kern/kern_jail.c）对各项限制的执行细节须对照 4.0-RELEASE 源码核验；raw socket 禁用等限制在后续版本（VNET 时代）有放宽，引用时须注明版本语境
  
**文献**：Kamp & Watson. Jails: Confining the omnipotent root [C]//Proceedings of SANE 2000. Maastricht, 2000 ［A］

**要点**：

- 项目缘起于网络仿真：Zec 在摆弄 Cisco 路由器时意识到，若单机能虚拟化路由表进而虚拟化整个网络栈，即可代替配置数十台路由器完成复杂实验；2002 年随机选择 FreeBSD 4.6/4.7 为起点做概念验证，原始实现延续至 FreeBSD 4.11 末期。（BSDTalk EP130，[85.19-124.35]，L1）
- 代码发布后社区发现其价值超出网络仿真：每个虚拟网络栈实例可维护独立路由表、接口集、IP 防火墙与流量整形器，被用作 FreeBSD jail 的扩展以支持更丰富的虚拟主机环境，突破 jail 单一 IP 别名、沿用基础系统防火墙与路由配置的限制。（BSDTalk EP130，[156.27-208.36]，L1）
- 设计方法为抽取定义网络栈行为的全部全局变量装入容器超结构并多实例化；2002 年版为概念验证，FreeBSD 7 重实现引入一级间接寻址，使各网络模块拥有独立结构、内核可加载模块可在运行时扩展子系统而无需重编译全部网络 API。（BSDTalk EP130，[218.08-283.31]，L1）
- 工程目标之一是完整保留管理接口：用户态管理工具无需任何修改、重编译或链接库调整即可用于虚拟化内核，虚拟化内核自设计之初即可作为原生内核的即插即用替代；新增 vimage 前端工具负责虚拟实例的创建删除与管理，实例间默认隔离，借 FreeBSD 的 NetGraph 框架以任意拓扑互联。（BSDTalk EP130，[344.35-452.73]，L1）
- 轻量性数据：相比 VMware、Xen 等传统虚拟化，jail 与虚拟网络栈极其轻量，每实例内核内存足迹仅约百余 KB（IPv4-only 内核更小）；Zec 的笔记本可同时实例化约 500 个虚拟节点，各自运行 Quagga 的 RIP 与 RIPng 路由演示，关键在于应用程序共享代码段内存因而扩展性良好。（BSDTalk EP130，[462.94-539.73]，L1）
- jail 可扩展性轶事：EuroBSDCon 2007 会上 Zec 与 Ike Levy 交流得知后者在生产环境运行约 170 个 jail，Zec 本人因内存设备限制止步 64 个，随后与 BHK 以简单脚本将 jail 实例推升至约 64000 个，显示 OS 级隔离与虚拟网络栈结合的可扩展潜力。（BSDTalk EP130，[539.73-576.65]，L1）
- 性能开销：FreeBSD 4 时代回环以太网尺寸包吞吐仅降约 3-4%（发送接收两端各计一次开销），FreeBSD 7 上单处理器回环 TCP 开销约 1.5%；意外发现回环 ICMP 吞吐反高于原生栈数个百分点，当事人推测系变量符号在内存中聚集改善了 CPU 缓存效率并减少 TLB 抖动，但自承无科学解释。（BSDTalk EP130，[850.67-928.32]，L1）
- 生产使用与资助：FreeBSD 4.11 版实现据称被美国匿名 ISP 用于生产（仅传闻性证据），这正是 FreeBSD 7 重实现获 FreeBSD Foundation 与荷兰 NLnet Foundation 资助的最初推动；当前实现已证明可运行于多线程内核，区别于单线程的 FreeBSD 4.11；文档几乎空白，仅网站上有若干演示文稿。（BSDTalk EP130，[717.83-779.79]，L1）
- 入行经过：大学时新笔记本需要可用的无线局域网，FreeBSD 5 当时未就绪、NetBSD 与 OpenBSD 在该机器上亦不理想，恰逢 Matt Dillon 宣布 DragonFly 项目且缺少 CardBus（32 位 PCMCIA 扩展）支持，其首个贡献即把 FreeBSD 5 的 CardBus 支持回移到 DragonFly。（BSDTalk EP135，[101.77-137.10]，L1）
- pkgsrc 引入 DragonFly 的经过：先前以本地 override 方式修补 FreeBSD ports（复制到本地仓库改写、以 hack 绕过系统头文件与符号链接差异），随 DragonFly 与 FreeBSD 分歧扩大而难以为继；2005 年另一开发者完成 pkgsrc bootstrap 与关键组件，其尝试后将 DragonFly 本地改动并入 pkgsrc；Thomas Klausner 等因补件 flood 而授予其直接提交权；此后第三方应用适配多在 pkgsrc 完成，用户在 FreeBSD ports 与 pkgsrc 之间的取舍变得容易。（BSDTalk EP135，[142.22-247.27]，L1）
- NetBSD 电源管理工作：Jared McNeill 早先着手改进 ACPI 挂起/恢复（部分机器可用、许多笔记本失效、AMD64 完全不可用）；另一方向是让未使用设备自动断电（未启用的网络接口、声卡等）；有专门邮件列表推动电源管理进入更多驱动；其本人因笔记本需要而投入，并视电源管理为当前比 jail 更紧迫的工作。（BSDTalk EP135，[253.27-312.47]，L1）
- Google Summer of Code 的 pkgsrc 项目分两部分：一是重做批量构建框架——旧系统无法处理多 chroot 或分布式构建集群，新系统以轻松利用多机、动态加入与退出为设计目标；二是 pkgsrc 交叉编译，重点是 modular Xorg（沿 XFree86 老路则工作量巨大且与 DragonFly 需求重复维护），核心是让 pkgsrc 复用 NetBSD 基础系统的交叉编译工具链，使 Amiga、VAX 等慢架构免于本地构建大包；适用前提为单平台且目标基础设施相似（ELF），跨操作系统交叉编译仅为未测试设想。（BSDTalk EP135，[365.44-505.83]，L1）
- GPLv3 的两大问题（EuroBSDCon 2007 项目状态讨论议题）：基础系统层面，需定期更新的 GPL 组件是 groff 与 GCC，要害不在 GCC 本身而在 libgcc 与 libstdc++——二者长期带有允许链接的例外条款，GPLv3 未将例外延及反 tivoization 条款，使高度定制且不允许篡改的系统能否用 GCC 构建成疑；对策包括 OpenBSD 导入 PCC、为 groff（BSD 源码树中唯一主要 C++ 组件）寻求替代。包管理层面，pkgsrc 已有非开源许可标签框架（mk.conf 的 acceptable_licenses 变量控制构建），计划扩展至全部许可类别尤其是 GPLv3，令用户知情并自决；批量构建基础设施问题待解决，目前仅对升级到 GPLv3 的包加注释。（BSDTalk EP135，[509.55-721.07]，L1）
- DragonFly jail 与 FreeBSD jail 的分化：DragonFly 源自 FreeBSD 4 的 jail 代码，FreeBSD 5/6 期间核心未大改（主要是适配 Robert Watson 的新凭证框架）；DragonFly 近期提交关键补丁，支持每 jail 多 IP 地址乃至 jail 内 IPv6，jail 的一大主要问题基本消除；FreeBSD 尚缺此能力，其替代路径是重量级虚拟化而非修补 jail 代码。（BSDTalk EP135，[734.95-791.94]，L1）
- NetBSD 的 kauth 式 jail 设想：kauth 已把大部分安全决策抽象到单一位置、便于修改；在 NetBSD 实现 jail 需给进程结构与凭证增加字段，使 root 权限决策可依是否处于 jail 而调整；剩余难题是 localhost 地址翻译的复杂代码；虚拟化路径的优点是避免在 jail 代码中特判。应用兼容性问题：Samba 因 localhost 特殊处理需要本地补丁，syslog 等守护进程绑定全部地址的对外行为需如 FreeBSD 团队那样专门修改。（BSDTalk EP135，[797.41-886.94]，L1）

- Dzonsons 在瑞典皇家理工学院与拉脱维亚大学合作框架下主持 MULT 研究，主张大量应用场景只需要与宿主同构的 POSIX 环境而非完整内核虚拟化，故将系统定位为单内核上同时运行成千上万个可精细配置、互不可见的操作实例，与 Xen、QEMU 及即将出现的 DragonFly BSD vkernel 等运行整个内核的重量级方案划清界限；系统不使用 VT-x/AMD-V 等处理器虚拟化扩展，且可与 NetBSD 的 Xen 支持叠加组合（Xen 客户机内再跑 MULT 实例），仅触及内核上半部因而宣称平台无关。（BSDTalk EP140，[187.94-223.30]，L1）
- 对 FreeBSD jail 的核心批评是：jail 名副其实地“监禁”一组进程，防护在执行时于内核边界施加，外部可见 jail 内部而 jail 看不见外部；进程表在内核中仍是全局单份，跨 jail 不允许重复进程号，资源隔离只在功能性层面而非结构层面成立。MULT 的应对是把进程表、挂载表、SysV IPC、网络接口等内核全局结构逐一收集为实例私有结构（其称逻辑隔离），故各实例可运行完整 init 树、进程号可跨实例重复，ps 只见本实例进程而以 instps 工具旁观他者；自述已实测启动逾十万实例，计划月底发布面向大规模启停的开发版。（BSDTalk EP140，[231.42-341.00]，L1）
- 资源划分按三阶段推进：先内部软资源（进程表、文件描述符、kqueue 与 knotes、SysV IPC，大半完成），再伪设备等“软硬件”（PTY、klog 等），最后硬件设备拟采两阶段方案——先以类似 Linux udev 的机制连贯命名设备，再由管理员经访问模块决定实例可得哪些设备并配 DevFS；自认网络与终端是最难啃的部分，硬盘按主从节点分配已可行。对虚拟主机与集群计算两种场景，他承认无实测数据、仅属推测：前者实例长期常驻、重在按需实时调配资源，后者重在秒级启停即弃、实例整体迁移与可迁移文件系统，未来拟支持 PUFFS 用户态文件系统、NFS 根文件系统，并指出 DNS 难以应对亚秒级的地址轮换。　[存疑脚注] 双场景运行时差异系当事人自认的推测（原话自陈无硬性测量支撑），迁移与 PUFFS/NFS 支持属规划而非已实现（BSDTalk EP140，[592.50-741.02]，L1）

- bhyve 在 2013 年 2 月访谈时点的定位：受访者称之为 type 2 hypervisor，但强调类型区分正在失效——若仅于单用户模式启动 hypervisor 即为 type 1，具备可用用户态即为 type 2，纠缠分类已无意义；就 FreeBSD 而言，bhyve 萌芽于 8 系列（甚至 7），于 9 系列公开露面，2013 年 1 月 19 日进入 FreeBSD 10-CURRENT。（BSDTalk EP223，[75.54-103.32]，L1）
- 与 jails 的范式对照：jail 本质是“被赋予自省能力的超级 chroot”——与宿主共享单一内核，经 RC 脚本启动守护进程（无独立 init），区分自身进程与网络并提供独立 root 用户；hypervisor 则令每个客户机运行独立内核实例。jail 轻量但走向复杂：建立足以支撑多个 jail 的虚拟化网络栈（含交换功能）是极复杂的问题；受访者转述 Poul-Henning Kamp 的实验——以脚本连续启动 jail，至 64,000 个方止。（BSDTalk EP223，[201.34-281.22]，L1）
- Xen 对照与产业转向：NetBSD 长期支持 Xen dom0，受访者自述受东京一场演讲触动而自建 Xen——主流 Linux 发行版上安装失败，转投 NetBSD dom0，文档贫乏却极其稳定；但 Xen 属根本不同的内核与许可证体系，FreeBSD 在 Xen 阵营居二等地位（Amazon EC2 带来关注，Colin Percival 为 FreeBSD 在 EC2 上的可用性做了大量工作）。产业层面：Amazon 选 Xen 缘于旧硬件投资巨大、需纯软件虚拟化；微软正视虚拟化需求并积极投入 virtio 驱动；Red Hat 为 KVM 贡献 virtio 驱动——各家正从“复刻古老硬件”转向现代方法。　[存疑脚注] 促成其 Xen 尝试的东京演讲者（转写作 Christophe）与项目名（转写作 Malt）均待考。（BSDTalk EP223，[294.12-563.76]，L1）
- bhyve 的轻量与 legacy-free 架构：内核模块式 hypervisor，主模块粗算约 1300 行代码、磁盘上软件约 256K，轻量且可审计；完全放弃旧硬件支持，要求 Intel VT-x 与扩展页表 EPT（AMD 的同类 NPT 技术已存在，实现只差开发者资源）；依赖 VirtIO 虚拟网络与块设备驱动；不做 QEMU 式 BIOS 模拟，故彼时仅能 FreeBSD on FreeBSD；已可掩蔽宿主设备做 PCI 直通。其简洁正是以舍弃 legacy、把复杂度转移给新硬件换来的。（BSDTalk EP223，[362.16-495.56]，L1）

- 社区自举与生态现状：代码公开两年而未获 FreeBSD 官方身份，形成鸡生蛋困境——无正式名分则少人试用；进入 10-CURRENT 本身即是激励，需志愿者实际压测，且每个试用者都会发现开发者未虑及的问题，此乃 bootstrap 社区的常态。技术状态：bhyve 即 FreeBSD，可从 ZVOL 镜像引导客户机并以 ZFS 快照回滚，兼容 nanoBSD 式用户态精简；块设备 I/O 彼时为阻塞式、偏慢（实验性修复代码在测），网络问题较小，基准测试是社区最能贡献的方向；受访者预测年底前多数 FreeBSD 开发者将在 bhyve 上开发 FreeBSD——内核崩溃即关闭客户机重开或回快照；生态上 FreeBSD virtualization 邮件列表响应积极，freenode 的 #bhyve 频道由 Allan Jude 正式化，其经营的 CDN 已将真实流量导向 bhyve 压测，Alfred Perlstein 亦在实验，开发者来自印度与澳洲；受访者计划在 AsiaBSDCon 演示、发布 man pages 并办文档 hackathon。（BSDTalk EP223，[796.26-1300.24]，L1）

- 从 jails 的组织价值到 SysJail 的方案设计：受访者需要托管多个站点且拒绝与他人共享托管机，痛感软件安装散落文件系统、RPM 亦未能根治，因而看重 jail 将守护进程与宿主系统分离、开销几乎不变、得以整体删除重建的组织价值，并多年以磁盘镜像充当各 jail 的独立分区；SysJail 由此针对 FreeBSD jail 实现的短板而作——文件系统扁平化得以按守护进程或按用户切分虚拟系统，复用 Systrace 的内核级组件、自身全部实现于用户态而无需改内核，可在 Systrace 所到之处运行（NetBSD、OpenBSD、MirOS），提供虚拟终端以便 SSH 进入、以二进制安装构建完整系统；性能上其测试在一台 VIA 1GHz、512MB 内存的迷你主板上同时跑 64 个 jail、每个 sshd 约占 2MB，远低于 VMware 类方案每实例 64MB 的分配；另以用户态文件系统设想隔离各 jail 的 procfs 可见进程以补安全短板。（BSDTalk EP66，[271.24-740.94]，L1）

**史观**：

- 总纲5 没有必然性，只有偶然性：同一虚拟化机制在作者意图（网络仿真实验台）与社区接收（jail 虚拟主机扩展）之间发生意义转移：技术物的历史角色由使用者群体的偶然需求重新定义，而非由设计初衷单方面决定。（BSDTalk EP130，[156.27-208.36]，L1）
- 总纲4 分离聚合是永恒规律：jail 生态从单一 IP 隔离到多实例网络栈的演进，是同一隔离理念在网络维度上的再分离与再聚合：容器与虚拟网络栈作为可组合的分离单元，经由 NetGraph 拓扑再行聚合，呈现 OS 级虚拟化技术的循环构造而非单向进步。（BSDTalk EP130，[578.73-700.55]，L1）
- 总纲8 本体论上各方平等：跨项目开发者以可用性与问题驱动选择工作对象而非效忠单一分支：从 DragonFly 回移、到 pkgsrc 提交、再到 NetBSD 电源管理与可能的 OpenBSD 补丁，四大 BSD 在其实践中是可互换的工程场域。（BSDTalk EP135，[320.47-353.67]，L1）
- 总纲4 分离聚合是永恒规律：jail 代码从 FreeBSD 4 分离至 DragonFly 后独立演化出多 IP 与 IPv6 支持，而包管理层反向聚合于跨项目的 pkgsrc 平台——分离与聚合在代码谱系的不同层面同时进行，构成循环而非单向演进。（BSDTalk EP135，[142.22-791.94]，L1）
- 总纲13 法律与道德是利益分配：pkgsrc 的许可标签框架把许可证选择转译为用户可见的构建配置（acceptable_licenses），GPLv3 包的处置方案是让用户在知情前提下自决——许可证的利益分配通过包管理基础设施落到用户决定。（BSDTalk EP135，[649.76-705.47]，L1）
- 总纲5 没有必然性，只有偶然性：基座选 NetBSD 而弃 Linux，理由是上手速度与个人代码品味而非任何工程必然性；MULT 本身则自承是 sysjail 在 systrace 缺陷下受挫的衍生物——技术路线由个人经验约束与先前项目的偶然挫败共同塑形，而非被某种历史规律决定。（BSDTalk EP140，[396.94-469.02]，L1）
- 总纲10 动手者创造历史：全部内核上半部全局结构的实例化由当事人一人重写、一人自测十万实例，并以招募测试者、招揽硕士生写论文的方式扩产，呈现的是动手者以原型先行、以自用代论证的工程书写，而非机构化研发叙事。（BSDTalk EP140，[826.54-909.56]，L1）
- 总纲10 动手者创造历史：发布工程师的自我刻画是协调者与守门人而非明星编码者：发布周期内只亲手修唯他能修的缺陷，其余时间用于审阅他人工作，非发布期方有余裕写码——发布质量被组织为对众人之工的裁断与串接，历史由大量无名提交与其裁决流程共同完成。（BSDTalk EP142，[838.76-858.14]，L1）
- 总纲12 科学是形式主义：Smith 对 15% 领先数字的自我节制——强调基准只是改进工具、拒绝作出“处处优于 Linux”的普遍断言——显示项目内部对形式化度量的效力边界有自觉：数字是组织工程的手段，不是世界结构的陈述。（BSDTalk EP142，[612.12-644.24]，L1）
- 总纲10 动手者创造历史：bhyve 的推广路径显示，一项无官方名分的内核模块能否成为历史事件，取决于动手者的中间劳动：受访者把逐组件构建脚本化、维护指南网站、拟办文档 hackathon、把潜在用户引导至邮件列表，以私人劳动填补官方身份缺位造成的信任真空——志愿者“砸代码”即是社区自举的实际内容。（BSDTalk EP223，[796.26-857.60]，L1）
- 总纲25 逻辑是形式主义而非世界本身的结构：hypervisor 的 type 1 与 type 2 分类在受访者口中自行瓦解：以单用户模式启动即为 type 1、有用户态即为 type 2，说明这套类型学并非系统的内在结构，而是事后约定的描述框架——概念系统与真实设计之间隔着形式化的人为边界。（BSDTalk EP223，[892.46-916.35]，L1）
- 总纲5 没有必然性，只有偶然性：bhyve 的命运系于具体偶然：进入 10-CURRENT 的确切日期、Amazon 因旧硬件存量而选 Xen、AMD 支持只差开发者资源、促成受访者转向 NetBSD dom0 的一场东京演讲——虚拟化路线的胜出与边缘化并不遵循必然规律，而由硬件存量、人力分布与偶发事件共同决定。（BSDTalk EP223，[404.18-443.56]，L1）
- 总纲10 动手者创造历史：该项目由 Kristaps 一人承担核心开发、Michael Dexter 承担项目管理与运维的两人体制驱动，处理进程限制之类功能仅花两天，而同类功能在 FreeBSD 端是一个 Google Summer of Code 项目；受访者拒绝推动其进入任何基础系统，主张工具按规格即插即用的模块化 UNIX 模式之美——默默做事的小团队以最小协作规模维持跨项目工具，正是动手者创造历史的微观形态。（BSDTalk EP66，[1246.12-1310.56]，L1）
