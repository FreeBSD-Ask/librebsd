**要点**：

- 2006 年 2 月中旬 FreeBSD 6.1 Beta 1 与 5.5 Beta 1 相继发布，发布说明称两者均为小幅更新且仅供测试；5.5 被定位为 5 系列的最终版本，为无法完成向 6 系列升级的用户维持维护线，但主持人观察到社区压力明显指向离开 5 系列、迁往 6 系列。（BSDTalk EP16，[63.07-95.13]，L2）
- 主持人把 vi 的双模式结构概括为新手最大困惑来源：命令模式与插入模式分离、启动默认进入命令模式，误以为自己在输入文本而实际处于命令态的用户会触发删除整行、段落或光标跳转等意外行为；入门命令集相应收缩为进入插入的 i、返回命令态的 Esc、不保存退出的 :q!、保存退出的 :wq 以及等效的 ZZ。（BSDTalk EP16，[195.30-341.32]，L2）
- 以 2006 年的使用者视角看，vi 的生态地位在于普遍可得：无论何种 Unix、Linux 或 BSD，唯一能确定存在的编辑器就是 vi，系统受损或身处陌生系统时它往往是唯一可依赖的工具；功能更多、体量更大的 Emacs 是另一极，两个社群之间存在自认非敌意的趣味性文化战斗。（BSDTalk EP16，[118.01-161.39]，L2）
- Scott Long 完整描述 FreeBSD 发布工程的制度细节：开发以 CVS 为中心，head 分支即 7-current 收纳一切新特性与实验改动，约每两三年从中切出发布分支，2005 年 6 月切出 RELENG_6 并发布 6.0，分支内只进 bug 修复与少量驱动、基调保守；五人发布团队不足以完成充分测试，靠向社区推送候选版本与快照构建征集反馈；发布判据是一份公开的 to-do 清单，收录高需求缺陷报告、功能请求与可能构成发布阻碍的去稳定缺陷，6.0 因此宁可推迟数月也修完缺陷再发；日程表只用于驱动参与者保持节奏，最终以修到满意为准；同时他承认过去 4.x 与 5.x 双发布周期并行使没有分支的 ports 树每次都要停摆配合，故自 2005 年起拉开发布间隔、终结双周期，6.1 与 5.5 成为 5 系列的最后发布，后续年内出 6.2、次年出 6.3、2007 年中切出 7 分支。（BSDTalk EP17，[186.94-728.46]，L1）
- 关于 5 系列谢幕的理由与善后：FreeBSD 6 在稳定性、功能与性能上已明显领先，继续投入 5 系列意义不大，而 5 到 6 的升级极少意外、基本系统几乎无变化；安全团队按既定政策对 5 系列再支持两年，照顾无法承担升级成本的用户；主持人以 Red Hat 放弃 Professional 转向 Fedora 后 Red Hat 9 仅获六个月支持的骤停作对照，Long 表示以善待过时版本为荣，因为用户依赖持续的安全修复。（BSDTalk EP17，[520.15-613.67]，L1）
- PowerPC 移植负责人 Peter Graham 的定位被 Long 转述为一手澄清：在 Apple 硬件上运行 FreeBSD 只是便于获取设备、便于用户参与的手段，真正目标是嵌入式 PowerPC，包括 IBM 440 系列嵌入式芯片与 Cell 芯片；Apple 转向 Intel 对该计划并非重创，PPC 版 Mac 仍将长期可得，同时社区已在 Apple 新 Intel iMac 上推进移植并预期其很快成为可行目标。（BSDTalk EP17，[736.44-814.47]，L1）
- 对 BSD 间代码流动的 2006 年时点判断：NetBSD 与 FreeBSD 分道已十三年，传统三项目间核心功能持续分化，共享退守至 USB 驱动等外围领域；DragonFly BSD 基于 FreeBSD 4，共享机会可观，数名开发者同时持有两个项目的提交权限，代码双向回流，DragonFly 开发的 BSD 安装器已在 FreeBSD 完整部署并可能很快进入 FreeBSD 7，其多处理器与可扩展性工作对 FreeBSD 直接有益。（BSDTalk EP17，[836.72-923.71]，L1）
- 存储方向的两项个人工作自述：其一为 SCSI 子系统加锁与 SMP 化，将大幅提升 SCSI 性能，虽并行 SCSI 本身在退场，SAS 与 Fibre Channel 等后续技术将直接受益；其二为 UFS 日志，与 soft updates 的可靠性之争多年互有胜负、基准基本打平，但 soft updates 即便保证崩溃一致性、恢复时仍须全盘检查，在数百 GB 至数百 TB 的企业文件服务器上是不可行的阻碍，而日志方案可在数秒内恢复一致性——这是 soft updates 结构上无法提供的优势。（BSDTalk EP17，[927.27-1047.06]，L1）
- 2006 年 2 月下旬 FreeBSD 发布 6.1 与 5.5 的第二个 beta 并公开征集测试者，同期 BSDCan 公布讲者与赞助者名单，主持人推荐关注其讲者阵容。（BSDTalk EP20，[33.73-63.27]，L2）
- NFS 由 Sun Microsystems 开发、为 Unix 及类 Unix 系统的原生文件共享协议，当时协议已至第四版而多数 BSD 仍支持到第三版，版本协商可自动完成；主持人以 OpenBSD 3.8 i386 演示：服务端在 rc.conf.local（而非直接改 rc.conf）启用 portmap、NFS 服务与加锁守护进程，NFS 依赖 RPC 且 RPC 守护进程须向 portmapper 注册；导出清单写在 etc exports，目录默认以读写导出但文件自身权限仍然生效；客户端挂载与传统软盘光盘挂载无异，仅在设备名前加服务器冒号前缀；调试靠 rpcinfo 查询 portmap 注册与 showmount 列出可用导出。（BSDTalk EP20，[139.19-498.16]，L2）
- NFS 的安全本质近乎只凭 IP 地址认证：exports 文件限定分享给某个地址或网段即到头；这套模型内嵌了协议诞生年代的组织假设——服务器与计算机极其昂贵、网内任何机器默认由公司统一管理、用户账户处处一致并依赖集中账户系统（原称 Yellow Pages，因电话簿公司商标之争改称 YP、后为 NIS）；UID 数字信任链是其要害：服务器只告知远端某文件属于 UID 1000，把哪个用户对应哪个号码完全交由客户端决定，任何可控的 Unix 笔记本自建 UID 1000 即可冒充他人；叠加不同系统基础账户起始编号不同（有从 1000 有从 500），混用各版 BSD 与 Linux 的归属关系必然错乱。（BSDTalk EP20，[498.16-699.51]，L2）
- 由此得出的家庭网络对策是假定全网与全部用户可信：导出一个目录并将其中所有文件设为全员可读写，反而防止把重要内容放进去，也免去了用户权限同步的全部复杂度——想在 NFS 上做真正的用户隔离并非不能，但需要成倍的额外功夫；主持人同时警告绝不要把可能带出门的笔记本身作 NFS 服务器，否则其导出清单会随机器流向外部网络；展望方面，NFSv4 承诺修补早期版本的缺陷，AFS 等分布式文件系统与模仿 Windows 共享模型的 Samba（有人主张将其确立为通用互联网文件系统标准）构成替代选项，主持人拒绝对后一争论表态。（BSDTalk EP20，[700.31-853.97]，L2）
- 受访者以发布工程师身份概括 FreeBSD 6.2 为“更好的 6.x”：包含大量 bug 修复，尤其是网络栈与文件系统在高负载条件下的稳定性修复，设备驱动更新与网络性能改进；用户可见的新特性包括二进制更新工具自 ports 进入 base system（使不愿重编译源码的用户可直接对运行中系统做二进制安全更新）、GNOME 2.16 与 KDE 桌面更新、Linux 模拟库刷新至 Fedora Core 4 的库。（BSDTalk EP84，[119.52-230.16]，L1）
- 受访者讲述了 GNOME 与 FreeBSD 发布周期错位的史实：此前数个版本中 GNOME 的新版发布恰好落在 FreeBSD 进入发布冻结之前，团队来不及充分测试最新代码，屡屡错过；直到 6.2 这一循环才被打破，得以随附新鲜版本的 GNOME。这是两个上游项目周期相互牵制的具体案例。（BSDTalk EP84，[177.8-217.96]，L1）
- 受访者界定发布工程的性质：照看 FreeBSD 的代码线，把开发者社区的全部工作打包成稳定可用的发布。当时 release engineering 团队由 7 名开发者组成、Ken Smith 领导，成员各有所长（受访者本人负责发布文档），并与 Port Manager 团队（ports 树与 CD/ISO 包构建）、Documentation Engineering 团队（handbook 与 FAQ）、安全团队（安全问题的记录、分析与修复）协作；临近发布时制作一系列 beta 与 release candidate 快照供社区测试。他还说明 6.2 最终发布时间预估为 12 月中旬且属移动目标，团队有意赶在冬季节日之前，因为既往经验显示假期会拖慢发布推进。（BSDTalk EP84，[272.36-419.8]，L1）
- 受访者回溯自己重整 release notes 的经历：自 FreeBSD 4.1 起，他发现版本间变更缺乏有组织的收集与发布流程，既有 release notes 无人真正负责流程、且只是朴素的文本文件；他的第一个 FreeBSD 项目即是重组、更新并持续维护 release notes，并推动转换为 DocBook SGML，从而以单一源文件产出 HTML、PDF、PostScript 与纯文本多格式（HTML 上网站、纯文本置于 ISO 映像）。记录范围限于对用户普遍有意义的内容：新功能、已处理的安全公告、重大 bug 修复与功能变更；Hiroki Sato 为协作成员，团队并鼓励各开发者撰写自己所做工作的 release notes 部分。（BSDTalk EP84，[758.28-852.48]，L1）

**史观**：

- 总纲9 经验优先：主持人指出 vi 诞生年代无法保证目标机器使用何种键盘，因而同一操作通常保留多条命令路径，hjkl 与方向键并存至今；他同时承认 vi 怪异、无法凭界面直觉掌握、只能靠教程与练习习得——vi 的界面形态是早期硬件约束的沉淀，其熟练度只能来自经验积累，这构成了一个仍在 2006 年被反复传递的经验优先传统。（BSDTalk EP16，[355.13-436.50]，L2）
- 总纲21 革命与改革是历史方法论的分歧：BSD 以进化而非革命著称的发布声誉，在 Long 的叙述中呈现为一套被制度化的渐进方法论：新特性必须先在 head 分支经受时间沉淀，再经分支切出、候选迭代与缺陷清零才能抵达用户，日程让位于质量判断；这与同期依赖激进重写换取跃进的路线构成发布方法论上的结构性分歧。（BSDTalk EP17，[173.41-358.07]，L1）
- 总纲4 分离聚合是永恒规律：BSD 各分支十三年的走向呈现出分离聚合的轨迹：核心功能随各自目标持续分离，共享面收缩到外围驱动；而 DragonFly 自 FreeBSD 4 分出后，又以双向提交权限、安装器回流与多处理器成果共享形成局部的再聚合——分离不是单向的撕裂，聚合也从未彻底中断。（BSDTalk EP17，[836.72-923.71]，L1）
- 总纲22 知识注定过时：NFS 的信任模型是一个被协议固化的时代切片：它把计算机属于公司、用户处处同一的组织假设直接编码为机器级信任机制，而当计算环境进入个人可以完全掌控一台 Unix 笔记本的时代，这些假设没有随之失效声明，而是悄悄变成了安全债务——协议本身提醒人们，任何技术约定都带着其诞生年代的前提，前提消散后约定仍在运转。（BSDTalk EP20，[537.50-666.67]，L2）
- 总纲10 动手者创造历史：release notes 的案例呈现了基础设施性劳动如何从无人认领到有人接手：版本差异信息长期缺乏有组织的生产流程，用户的信息需求悬置多年，最终由一位注意到此空缺的开发者以个人项目的方式填补，并经 DocBook 化演化为多格式文档工程。项目的可理解性正依赖这类不被归功的持续整理劳动，而非仅由标志性功能演进构成。（BSDTalk EP84，[758.28-852.48]，L1）
