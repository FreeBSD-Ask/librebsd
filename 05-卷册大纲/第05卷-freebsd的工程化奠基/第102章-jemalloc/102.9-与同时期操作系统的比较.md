# 102.9 与同时期操作系统的比较

## 102.9.1 Linux ptmalloc 与 Solaris libumem

**要点**：Linux ptmalloc（基于 Wolfram Gloger 的 ptmalloc2）与 Solaris libumem（主要实现者 Mike Shapiro，其 slab 与 vmem 机制思想源自 Jeff Bonwick（杰夫·邦威克））是同期主流分配器；ptmalloc 多线程扩展性弱，libumem 性能优秀但仅限 Solaris 平台。　[存疑脚注] libumem 的用户态实现主要由 Mike Shapiro 完成，Bonwick 系 slab 分配器（USENIX 1994）与 magazines/vmem 机制（USENIX 2001）的原创者，实现者与思想源头的归属以一手文献为准。

**史料**：glibc 源码树 malloc.c（ptmalloc2 实现与注释）；OpenSolaris usr/src/lib/libumem 源码与 man 3 libumem 手册页［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］ 〔L3 官方文档〕

**史观**：总纲第 8 条——本体论上各方平等：各操作系统的分配器路线互为参照系，不以单一生态的市场地位预设优劣

**辨析**：jemalloc 与二者优劣须以基准测试回答——据 Evans（BSDCan 2006），jemalloc 的多线程扩展性优于 ptmalloc 的 per-thread arena 设计，与 libumem 同属 slab 系但缺少同环境对照数据，架构推断不能替代实测。

**文献**：Gloger W. ptmalloc2: A Multi-Threaded malloc Implementation[Z]. 2006（glibc 源码树 malloc.c 附带说明）；Bonwick J, Adams J. Magazines and Vmem: Extending the Slab Allocator to Many CPUs and Arbitrary Resources[C]//USENIX ATC 2001；Bonwick J. The Slab Allocator: An Object-Caching Kernel Memory Allocator[C]//USENIX Summer 1994；Shapiro M. libumem 实现源码[Z]. OpenSolaris usr/src/lib/libumem ［B］

## 102.9.2 Windows LFH

**要点**：Windows LFH（Low Fragmentation Heap，Vista 引入 2006）是 Microsoft 对碎片问题的回应；与 jemalloc 路线不同（LFH 修改现有 heap，jemalloc 完全重写）。

**史料**：MSDN Low Fragmentation Heap 文档（Memory Management 一节）［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］ 〔L3 官方文档〕

**史观**：总纲第 4 条——分离聚合是永恒规律：LFH 改造现有堆与 jemalloc 另起炉灶，是同一碎片问题在不同谱系内分化出的两条路线

**辨析**：LFH 与 jemalloc 的优劣缺少同条件公开基准——LFH 以降低碎片为目标、jemalloc 以多核扩展为目标，设计目标不同使结论不可直接互换，须分场景测试。

**文献**：Microsoft Windows Low Fragmentation Heap (LFH) MSDN documentation；Russinovich, M. et al. Windows Internals, 7th ed. (Microsoft Press, 2017), Chapter 5［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

## 102.9.3 分配器路线的辨析

**要点**：分配器路线辨析：（1）per-thread arena（Linux）；（2）per-CPU arena（jemalloc）；（3）slab 分配器（Solaris libumem）；（4）LFH（Windows）。

**史料**：Evans BSDCan 2006 论文（arena 设计与性能数据）、Ghemawat TCMalloc 技术报告（Google, 2004）、Berger 等 Hoard 论文（ACM SIGPLAN Notices 35(11), 2000）［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］ 〔L3 官方文档〕

**史观**：总纲第 4 条——分离聚合是永恒规律：四条分配器路线由同一“分配器难题”分化而来，又各自在其生态内聚合成形

**辨析**：四条路线的优劣依负载而异——多线程服务器负载利好 per-CPU arena（jemalloc），低内存与单线程场景差距缩小；路线比较必须绑定负载类型，不存在普适优劣。

**文献**：Evans J. A Scalable Concurrent malloc(3) Implementation for FreeBSD[C]//BSDCan 2006；Ghemawat S. TCMalloc: Thread-Caching Malloc[Z]. Google, 2004；Berger E D, McKinley K S, Blumofe R D, et al. Hoard: A Scalable Memory Allocator for Multithreaded Applications[J]. ACM SIGPLAN Notices, 2000, 35(11)；Gloger W. ptmalloc2[Z]. 2006 ［B］

## 102.9.4 比较的史料辨析

**要点**：比较史料疑点：（1）测试环境是否一致；（2）比较时间点是否对齐；（3）比较维度是否公平。

**史料**：Phoronix 2008-2011 分配器基准存档、Evans jemalloc 性能数据（BSDCan 2006）［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］ 〔L3 官方文档〕

**史观**：总纲第 9 条——经验优先：分配器比较的结论以基准测试的实测数据为据，先于架构优劣的先验判断

**辨析**：测试环境的硬件、内核配置与负载生成器直接决定分配器基准的可比性；不同年代的公开基准（如 Phoronix 2008-2011）因内核版本差异也不宜纵向合并。

### 史观映射

> jemalloc 是 BSD 代码散逸的教科书案例——Jason Evans 写出的 arena 分配器被 Facebook 和 Mozilla 拿走，BSDL 允许他们这样做，也允许他们不回馈。但更深的散逸不在代码，在话语：Evans 曾表示 jemalloc 在 Linux 上相对 glibc ptmalloc 的优势“不足以构成替换理由”，Linux 社区评论中有代表性的一种意见认为“除非系统分配器真的糟透了，否则没理由换”——一个技术优秀的分配器，就这样被“够用就行”的保守态度挡在了 glibc 的墙外　[存疑脚注] 两处引语均未取得原帖出处，暂以本章 102.5、102.7 节与 Evans 的 BSDCan 2006 论文互证，待回源核验。
