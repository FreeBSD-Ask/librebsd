## 90.7.1 Port 维护者谱系

  **要点**：Port 维护者谱系从 Jordan Hubbard(创始人) 经 Will Andrews、Steve Price、Joe Marcus Clarke 至当前 portmgr 团队，历经 30 年代际更替，每个时期的核心维护者约 5-10 人，负责 bsd.port.mk 框架与全局策略
  
**史料**：portmgr 团队历史名单、freebsd-ports 邮件列表维护者变更公告、《Porter's Handbook》 各版本 ［A］
  
**史观**：总纲第 4 条——分离聚合是永恒规律〔订正：原作“总纲第 25 条——终结与延续”系伪标签名目，本句主旨近总纲 4，依核查报告重挂〕：Port 维护者谱系的代际更替是 BSD 社区延续性的体现
  
**辨析**：部分早期维护者已不可考，需查 SVN commit log 中的 MAINTAINER 字段
  
**文献**：portmgr 团队页面；《Porter's Handbook》；freebsd-ports 邮件列表 ［A］

## 90.7.2 被遗忘的提交者

  **要点**：Port 提交者中约 60% 在提交 10 次以下后 inactive，这些“被遗忘的提交者”贡献了数百个 port 的初始版本，但因未长期参与而未进入社区记忆
  
**史料**：SVN 仓库 ports/ commit 统计、freebsd-committers 邮件列表 inactive 记录 ［A］；freebsd.duckdb 查询 L4.3.1.freebsd-ports 显示：freebsd-ports 仓库活跃维护者数（每年有 commit 的独立维护者）——1994 年 17 人、1995 年 30 人、1996 年 35 人、1997 年 53 人、1998 年 76 人、1999 年 106 人、2000 年 142 人、2001 年 171 人、2002 年 188 人（峰值）、2003 年 184 人、2004 年 189 人、2005 年 210 人（峰值）、2006 年 189 人、2007 年 200 人、2008 年 189 人、2009 年 182 人、2010 年 191 人，活跃维护者数在 2002 年与 2005 年两次达到峰值后回落，印证“约 60% 提交 10 次以下后 inactive”的社区记忆
  
**史观**：总纲第 10 条——动手者创造历史〔订正：原作伪标签名目“边缘者贡献”，依核查报告改用权威名目，条号不变〕：被遗忘的提交者是 Port 增长的隐性基础设施
  
**辨析**：inactive 提交者的精确统计困难，因部分提交者改为非 commit 贡献；【0 信任原则·author 字段可伪造】L4.3.1 的活跃维护者数基于 author_email 字段聚合，author_email 可由提交者任意填写，部分维护者使用团队邮箱（如 <ports@FreeBSD.org>）导致单人被统计为多人或多人被合并为一人，须与 MAINTAINER 字段交叉验证
  
**文献**：Ports commit 统计；freebsd-committers 邮件列表 ［A］；freebsd.duckdb 查询 L4.3.1.freebsd-ports：每年活跃维护者数（1994-2010）[DB/OL]. 原材料/研究/bsd 仓库分析/数据分析/ports 生态分析.md〔存疑：该路径经全库检索不存在，引用落空，依核查报告注明〕

- FreeBSD 文档团队 Benedict Reuschling 自述进入路径与当下工作：原为 Debian 用户，实习时经 FreeSBIE live CD 发现 FreeBSD（虚拟终端切换明显更快、handbook 把文档集中一处），与 Debian 并行安装数周后完全转换；硕士论文写作的漫长枯燥期读到 FreeBSD 德语文档项目招募新血的博客，回复后成为唯一响应者，由奥地利的 Johann Kois 担任导师学会文档编辑与提交规范，数月后获得完整 docs commit bit；如今一边追赶德语树的翻译积压，一边与 Alan Jude 在独立分支重写 handbook 的 ZFS 章，并坦言文档 committer 人数稀少、积压是常态，他以 mentoring 回馈自己受指导的经历，把积极贡献者培养为文档提交者。（BSD Now EP41，[978.92-1261.60]，L1）
- Benedict 的大学场景实践：为母校计算机系建设教职员与学生按需开虚拟机的教学云，评估 OpenStack 与 OpenNebula 以替代免费版 ESXi，倾向以 ZFS 作后端（虚拟机备份在 ZFS 上远比数千欧元的存储或 VMware 付费快照组件容易）；接管一门内容停留在 Linux 2.4 时代的过时 Unix 课程，全面重做并加入 BSD、ZFS 专题讲座与 sed、grep、awk 脚本课；作业不限定操作系统，让学生凭充分信息自主选择，明确表示不推销特定系统，因为 FreeBSD 并非总能解决一切问题；系里因关键业务依赖 Linux 而对引入 BSD 存在阻力。（BSD Now EP41，[1270.92-1678.12]，L1）
- 对开源协作的人类学观察与会议速修轶事：做了近 15 年 BSD 用户，此前只见过 commit message 与邮件地址，见面才发现对年龄与性格的想象常全错；邮件列表与 IRC 的技术分歧常夹杂性格冲突，纯文本难以化解，面对面通常轻松解决并找到共同基础。例证：受访者在马耳他 BHyve 虚拟机内建 ZFS pool 触发断言崩溃，45 分钟后收到修复补丁；Olivier 想要的安装器特性一夜之间出现；OpenBSD 开发者与 BHyve 开发者被安排同处一室六小时，数日内 OpenBSD 得以在 BHyve 启动——平时分处不同时区、数周数月甚至不会发生的协作，在会场被压缩为当场解决。会议还为长期纯线上奉献者“给 BSD 电池充电”，缓解只身贡献的孤独感，有人甚至按会议日程安排假期。（BSD Now EP41，[1845.48-2173.20]，L1）
- 本期标题的由来（片头预告的特别惊喜）：Benedict 以半戏谑的“处理过度提交者案例”口吻宣布，文档团队与文档工程团队一致认定，对付 excessively 提交文档树改动的 Alan Jude 的最佳方式，就是授予其 documentation commit bit；由 Warren Block、Eitan Adler 与 Benedict 三人因时区差异共同担任导师，指导其补丁流程，数月内（或更快）成为 FreeBSD 完整文档提交者——commit bit 的授予过程在听众面前全程呈现。（BSD Now EP41，[2260.60-2332.20]，L1）
- 同期新闻要点：FreeBSD 官方缺陷跟踪自 GNATS 迁移至 Bugzilla（BSDCan 期间决定立即执行、随后数周末完成，PR 编号不变，bugs.freebsd.org 提供永久 URL，迁入后缺陷关闭数量随即大涨，主持人称 GNATS 的退役“已谈了约 17 年”）；DragonFly 3.8 发布并宣布为最后一个 32 位版本，3.8.1 快速点版本随即带 OpenSSL 修复，bin 与 sbin 动态链接以启用 PAM 与 NSS，USB4BSD 成为默认，自 FreeBSD 移植 i915 驱动至 HD 4000，并采用 FreeBSD 包系统（dports），其维护者常驻 FreeBSD ports 频道工作、改进反哺 ports 树并使其更 OS 无关；OpenZFS 欧洲会议 2014 的演讲视频与幻灯上线，开发者峰会定于 11 月旧金山并特意避开与其他会议撞期。（BSD Now EP41，[65.00-797.04]，L2）
- 受访者介绍 Mono 为基于公开 ECMA 规范的 .NET 平台自由开源实现：源码编译为 CIL 字节码后由 mono 运行时执行；与 Java 将开发者绑定于单一语言不同，.NET 平台容纳 C#、VB.net、ASP.net、Java 实现（IKVM）、IronPython 以及 Boo、Nemerle 等多种语言。Mono 出自 Novell 旗下 Ximian 一侧、由 GNOME 创始人之一 Miguel de Icaza 发起，起因是在 GNOME 上以 C 开发大型应用困难而寻求更易用的平台；Tomboy 已随 GNOME 2.16 进入标准模块，当时多数 Mono 应用基于 GTK# 构建。（BSDTalk EP85，[106.44-210.52]，L1）
- 受访者陈述 2006 年底 Mono 在 BSD 生态中的格局：FreeBSD 在各 BSD 中走得最远——ports 树停留在随 6.2 冻结的旧稳定版，BSD# 树已至 1.2.1，并将在 6.2 发布后的 ports slush 之后合并回 FreeBSD 树；他在发布冻结时宁选已知可工作的版本而非无法保证的上游最新版。NetBSD 当时在寻找 Mono 维护者，OpenBSD 旧维护者的树外快照已停止更新。微软早年曾以 shared source 许可发布 BSD 版 .NET 运行时，因并非真正的自由许可而未获社区响应。　[存疑脚注] 本期转写噪声较多，具体版本号（1.1.13.8.1 与 1.1.17.2）存在转写失真风险，仅作参考。（BSDTalk EP85，[202.52-372.5]，L1）
- 关于移植经验：受访者判断 Mono 应用跨操作系统移植通常不算困难，应用多为 C# 与 C 的混合，C# 部分不成问题，麻烦多出在 C 代码与运行时层面；Beagle 即因 FreeBSD 上反复暴露新问题（索引 RSS 时约三十秒即崩溃、近期又生成海量临时文件耗尽 inode）始终未能进入 ports 树。他的排查方法是在 Fedora Core 参考机上对比 Linux 行为，以判定问题属上游还是 FreeBSD 特有。（BSDTalk EP85，[398.22-493.34]，L1）
- 受访者披露 BSD# 的人力困境与交接安排：运行两年多后他决定交棒给协作者 Philip Newman；即使两人协作也已吃力，一人接手更难，项目实际需要全职专职的维护者——他类比为“想学 Java 并维护几个应用，却发现连 JDK 也得一起维护”。本人拟于 2007 年 2 月收缩 ports 工作后转向当时刚启动的 FreeBSD Python 等新项目，并表示更偏爱 Python 甚于 C#。（BSDTalk EP85，[641.52-754.64]，L1）
- 关于 Mono 的官方归属：受访者转述与 Mono 前项目经理解得到的解释——Novell 资助 Mono 的目的在于便捷地开发同时支持 Linux 与 Windows 的跨平台应用，FreeBSD 并不在其计划之内；OS X 侧的主力开发者亦非 Novell 雇员而是兴趣驱动的个人。他据此认为成为 Novell 的官方目标并不重要，只要 FreeBSD 社区持续投入并将成果向上游提交即可自立。（BSDTalk EP85，[788.44-861.26]，L1）

**史料**：

- 本期为 FreeBSD ports committer Tom McLaughlin 的口述访谈（bsdtalk085，2006-11-30），提供其履历的一手陈述：居于波士顿郊外，任职于向医院销售医疗信息系统的 Metatech 公司、岗位介乎帮助台与初级管理员之间；约 2003 年进入 FreeBSD 世界，因身为 GNOME 用户而通过邮件与 IRC 报告 bug，其后自行修复并创办 BSD# 项目维护 Mono，2005 年前后成为 ports committer；其工作环境因客户需求转向 CentOS/Linux，当时引入 FreeBSD 并不合适；家用 FreeBSD 笔记本，并以 tinderbox 与多个 jails 作为 ports 构建测试的干净参考系统。（BSDTalk EP85，[63.6-91.92]，L1）

**史观**：

- 总纲10 动手者创造历史：本期几乎是一部“动手者如何再生产动手者”的实录：Kois 指导 Reuschling 取得 commit bit，Reuschling 又以 mentoring 培养后来者，最终在节目现场为 Alan Jude 设三位导师启动同一路径；与之呼应的是 45 分钟送达的 BHyve 补丁与一夜长出的安装器特性——项目的延续不靠制度文本，而靠一双手把手地把下一双手带进树里。（BSD Now EP41，[1124.36-2332.20]，L1）
- 总纲6 和解优于斗争：受访者对邮件列表与 IRC 冲突的观察揭示了解释学处境：文本交流剥离语气与人格，技术分歧极易升级为性格对抗且难以收束；会议把对话还原为面对面的在场交流，冲突通常可当场化解并确立共同基础——OpenBSD 与 BHyve 开发者被置于同一房间数小时而非隔空争论，数日后即达成可行结果；开源社区的常态运转依赖这种周期性的和解机制。（BSD Now EP41，[1896.20-2091.16]，L1）
- 总纲10 动手者创造历史：受访者自我定位为“glorified user”而非开发者，认为称其开发者是对真正行家的冒犯；他自述从报告与拾取小 bug 起步，每修一批问题便学到更多、进而挑战更难的问题，逐步成长为 committer，并强调志愿者项目由“真正起身做事的人”推动、社区随时愿意给新来者分派工作。贡献在此由劳动行为而非身份资格定义，为动手者创造历史的微观机制提供了当事人样本。（BSDTalk EP85，[966.52-1050.96]，L1）

**辨析**：

- OpenBSD 磁盘性能悬案：自 Arch Linux（经 GRsecurity 与 PaX 长期加固）转向 OpenBSD 5.5 stable 的听众报告 SSD 上 iostat 峰值仅约 180MB/s，而 Linux 全盘 AES-256 加密可达 350MB/s；主持人指出 OpenBSD 出于安全考量以 Giant Lock 将多核操作强制于单锁之下、多核性能受限，同时提醒 Linux 数字可能包含不安全的写缓存，并强调 FFS/UFS 本身并不慢，建议核对 CPU 占用；该问题当期未获最终解释，留待 OpenBSD 社区反馈。　[存疑脚注] 性能差异成因仅为主持人基于 Giant Lock 架构的推断，当期无实测结论（BSD Now EP41，[3094.68-3315.54]，L2）

- 访谈发生于 Novell 与 Microsoft 专利协议引发开源社区激烈反应之后：受访者自述不认同软件专利，但也不参与阴谋论式论战，认为 Novell 方基于公开 ECMA 规范开发、且 ECMA 流程本身含有专利规则（他自认不掌握细节）；其个人动机是学习兴趣而非政治立场。这一自白呈现了一线维护者与意识形态论战之间的距离：社区层面的专利焦虑未必传导为个体贡献者的行为约束。（BSDTalk EP85，[861.26-962.12]，L1）
