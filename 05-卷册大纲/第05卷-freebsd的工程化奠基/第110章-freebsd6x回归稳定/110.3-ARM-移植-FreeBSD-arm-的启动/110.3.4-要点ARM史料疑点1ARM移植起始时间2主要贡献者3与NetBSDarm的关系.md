**要点**：

- 受访者以发布工程师身份概括 FreeBSD 6.2 为“更好的 6.x”：包含大量 bug 修复，尤其是网络栈与文件系统在高负载条件下的稳定性修复，设备驱动更新与网络性能改进；用户可见的新特性包括二进制更新工具自 ports 进入 base system（使不愿重编译源码的用户可直接对运行中系统做二进制安全更新）、GNOME 2.16 与 KDE 桌面更新、Linux 模拟库刷新至 Fedora Core 4 的库。（BSDTalk EP84，[119.52-230.16]，L1）
- 受访者讲述了 GNOME 与 FreeBSD 发布周期错位的史实：此前数个版本中 GNOME 的新版发布恰好落在 FreeBSD 进入发布冻结之前，团队来不及充分测试最新代码，屡屡错过；直到 6.2 这一循环才被打破，得以随附新鲜版本的 GNOME。这是两个上游项目周期相互牵制的具体案例。（BSDTalk EP84，[177.8-217.96]，L1）
- 受访者界定发布工程的性质：照看 FreeBSD 的代码线，把开发者社区的全部工作打包成稳定可用的发布。当时 release engineering 团队由 7 名开发者组成、Ken Smith 领导，成员各有所长（受访者本人负责发布文档），并与 Port Manager 团队（ports 树与 CD/ISO 包构建）、Documentation Engineering 团队（handbook 与 FAQ）、安全团队（安全问题的记录、分析与修复）协作；临近发布时制作一系列 beta 与 release candidate 快照供社区测试。他还说明 6.2 最终发布时间预估为 12 月中旬且属移动目标，团队有意赶在冬季节日之前，因为既往经验显示假期会拖慢发布推进。（BSDTalk EP84，[272.36-419.8]，L1）
- 受访者回溯自己重整 release notes 的经历：自 FreeBSD 4.1 起，他发现版本间变更缺乏有组织的收集与发布流程，既有 release notes 无人真正负责流程、且只是朴素的文本文件；他的第一个 FreeBSD 项目即是重组、更新并持续维护 release notes，并推动转换为 DocBook SGML，从而以单一源文件产出 HTML、PDF、PostScript 与纯文本多格式（HTML 上网站、纯文本置于 ISO 映像）。记录范围限于对用户普遍有意义的内容：新功能、已处理的安全公告、重大 bug 修复与功能变更；Hiroki Sato 为协作成员，团队并鼓励各开发者撰写自己所做工作的 release notes 部分。（BSDTalk EP84，[758.28-852.48]，L1）

**史料**：

- 本期为 FreeBSD 开发者、release engineering 团队成员 Bruce Mah 的口述访谈（bsdtalk084，2006-11-28），提供其个人履历的一手陈述：1987 年前后在 UC Berkeley 就读本科时开始使用 BSD，1995 年起使用 FreeBSD，2000 年成为 committer，2002 年加入 release engineering team；任职于 nCircle Network Security，以 FreeBSD 为组件构建网络安全设备；家中防火墙、邮件与 Web 服务器及一台桌面均运行 6.2 预发布版并跟踪 stable 分支。（BSDTalk EP84，[81.36-110.52]，L1）

**史观**：

- 总纲10 动手者创造历史：release notes 的案例呈现了基础设施性劳动如何从无人认领到有人接手：版本差异信息长期缺乏有组织的生产流程，用户的信息需求悬置多年，最终由一位注意到此空缺的开发者以个人项目的方式填补，并经 DocBook 化演化为多格式文档工程。项目的可理解性正依赖这类不被归功的持续整理劳动，而非仅由标志性功能演进构成。（BSDTalk EP84，[758.28-852.48]，L1）

**辨析**：

- 关于版本支持生命周期：受访者说明最后的 4.x 版本将于 2007 年 1 月由安全团队与 Port Manager 团队终止支持，标志 4.x 系列的落幕；同时他强调 6.2 的发布本身并不连带终止任何其他版本的支持——发布事件与支持策略是解耦的。这为 4.x 至 6.x 过渡期的支持终止节点提供了当事人时间锚点。（BSDTalk EP84，[243.96-272.36]，L1）
