# 100.17 第三方软件变更——PF 防火墙引入与 MTA 格局

## 100.17.1 PF 防火墙从 OpenBSD 引入

  **要点**：FreeBSD 5.3-RELEASE（2004 年 11 月，release/5.3.0 tag 为 2004-11-04，发布日区分见辨析段）正式从 OpenBSD 导入 PF（Packet Filter）防火墙，作为 IPFilter 的替代选择。PF 由 Daniel Hartmeier（丹尼尔·哈特迈尔） 为 OpenBSD 设计，随 OpenBSD 3.0（2001 年 12 月 1 日）首次发布，其设计动机源于 IPFilter 许可证争议——2000 年 Darren Reed（达伦·里德） 修改 IPFilter 许可证条款，导致 OpenBSD 将其从源码树移除，Hartmeier 从头编写 PF 作为替代。PF 支持状态检测（stateful inspection）、NAT/NAPT、ALTQ 流量整形、pfsync 状态同步、authpf 用户认证等特性，FreeBSD 移植由 Max Laier 主导完成，将 PF 从 OpenBSD 的 pf(4) 源码适配到 FreeBSD 内核（导入提交的哈希与时间戳移见史料与文献字段）。FreeBSD 5.3 同时保留 IPFilter 与 PF，用户可选其一作为防火墙；PF 在后续版本中性能和功能持续改进，逐步成为 FreeBSD 社区首选防火墙。IPFilter 最终在 FreeBSD 10.0（2014 年 1 月 20 日）从 base system 移除，PF 延续至今作为 FreeBSD 的三款内置防火墙之一（PF、IPFW、IPFilter 共存至 10.0）。
  
**史料**：FreeBSD 5.3-RELEASE Announcement（release/5.3.0 tagger_date = 2004-11-04T19:12:42Z，明确 PF 导入）、OpenBSD 3.0 Release Notes（2001.12.1，PF 首次发布）、Daniel Hartmeier BSDCon 2002 论文 “The Design and Implementation of the OpenBSD Packet Filter (PF)”、Max Laier PF 移植提交记录（freebsd.duckdb freebsd-src 仓库 commits 表 commit_hash = 32b30983561ed562aa495d8e124488ab94b332aa，committer_date = 2004-06-16T23:03:14Z，author = Max Laier，message_subject = “Import pf from OpenBSD 3.5 (OPENBSD_3_5_BASE)”）；freebsd.duckdb freebsd-src 仓库 tags 表 release/5.3.0 的 tagger_date = 2004-11-04T19:12:42Z（target_commit_hash = f8d4987d7271c1003cce92715022709505f995c7） ［A］
  
**史观**：总纲第 4 条——分离聚合是永恒规律：PF 从 OpenBSD 到 FreeBSD 的移植是 BSD 家族内部代码共享的典型案例——OpenBSD 因许可证问题移除 IPFilter 后编写 PF，FreeBSD 因 PF 的技术优势将其移植，两个 BSD 项目在防火墙领域的代码流动体现了 BSD 社区 “择优而用” 的务实传统；总纲第 13 条——法律与道德是利益分配：IPFilter 许可证争议是 PF 诞生的直接催化剂，也是 BSD 社区对许可证问题敏感的早期例证
  
**辨析**：经 freebsd.duckdb tags 表验证，5.3-RELEASE 的 tagger_date 为 2004-11-04T19:12:42Z（非旧叙事 2004.11.6，误差 2 天，可能为公告日期与 tag 日期差异）；经 freebsd.duckdb commits 表验证，PF 导入 commit 为 2004-06-16T23:03:14Z Max Laier “Import pf from OpenBSD 3.5 (OPENBSD_3_5_BASE)”（早于 5.3-RELEASE 约 4.5 个月，属 5.3-CURRENT 开发周期）；需区分 PF 的 “创建” 与 “引入 FreeBSD” 两个时间点——PF 创建于 OpenBSD（2001），FreeBSD 在 5.3（2004）引入，引入时已非 PF 首个版本；FreeBSD 的 PF 移植与 OpenBSD 主线的 PF 在后续发展中逐步分化——OpenBSD 持续改进 PF（如 4.1 引入 pfsync 改进、4.3 引入 address pool 等），FreeBSD 的 PF 在 5.3 后也经历了多 CPU 性能优化（10.x 细粒度锁定）、VIMAGE 支持等差异化改进，但 FreeBSD 的 PF 版本长期落后于 OpenBSD 最新版本；部分资料称 “FreeBSD 5.3 用 PF 取代 IPFilter”——经 Release Notes 核实，5.3 是同时提供 PF 和 IPFilter，而非替代，IPFilter 保留至 10.0 才移除

## 100.17.2 sendmail 作为默认 MTA 的延续

  **要点**：FreeBSD 5.x 全系列中 sendmail 仍为 base system 的默认 MTA（Mail Transfer Agent），版本为 sendmail 8.12.x-8.13.x。sendmail 自 4.1cBSD 起（〔存疑：纳入 4.1cBSD 的确切年份未经 TUHS 档案核验，姑系于 1982 年前后〕；Eric Allman（埃里克·奥尔曼） 在 UC Berkeley 开发）即为 BSD 系统的标准 MTA，在 FreeBSD 2.0-13.x 长达 30 年间持续作为默认。需特别注意：Postfix 从未进入 FreeBSD base system——Postfix 由 Wietse Venema 于 1997 年在 IBM T.J. Watson 研究中心开发，作为 sendmail 的安全替代品，但 FreeBSD 始终将其保留在 ports（mail/postfix）中供用户自行安装，从未纳入 base。关于 FreeBSD 默认 MTA 从 sendmail 替换为其他软件的实际发生时间，不是 5.x 时期（Postfix 从未进入 base），不是 10.x 时期（DMA 仅存在于 ports），而是 FreeBSD 14.0（2023 年 11 月 20 日）将 DMA（DragonFly Mail Agent）设为默认 MTA 替换 sendmail。5.x 时期用户对 sendmail 配置复杂、安全性历史方面虽有关切，但 FreeBSD 社区选择保留 sendmail 而非引入 Postfix 到 base，这一决策延续了 20 年。
  
**史料**：FreeBSD 5.0-5.4 Release Notes（sendmail 版本更新记录）、FreeBSD 14.0 Announcement（DMA 成为默认 MTA）、Venema W. Postfix 设计文档、Allman E. sendmail 历史［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］ 〔L3 官方文档〕
  
**史观**：总纲第 22 条——知识注定过时：sendmail 是 BSD 系统中旧知识长期存续、终被更替的典型代表——其 sendmail.cf 配置文件语法以晦涩难懂著称，安全性历史上多次出现严重漏洞（如 1988 年 Morris 蠕虫利用 sendmail 漏洞），但因其 “够用” 且替换成本高（所有系统邮件脚本、cron 输出、第三方软件依赖其行为），在 base 中保留了 30 年；总纲第 13 条——法律与道德是利益分配：Postfix 使用 IBM Public License（后改为 EPL），sendmail 使用 sendmail License（BSD 风格），许可证差异不是 Postfix 未进入 base 的原因（Postfix 许可证兼容），而是 FreeBSD 社区认为 “sendmail 虽不完美但足够” 的保守主义决策
  
**辨析**：关于 “sendmail vs Postfix” 的争论在 2000 年代初期（5.x 时期）的 FreeBSD 社区邮件列表讨论中持续存在，但 FreeBSD Core Team 从未正式讨论过将 Postfix 纳入 base 替换 sendmail 的提案；DMA 来自 DragonFly BSD 项目，由 Matthias Schmidt 开发，专为 “无需完整邮件服务器的桌面/客户端系统” 设计，仅负责本地邮件投递与通过外部 smarthost 转发，不能替代 sendmail 的完整 MTA 功能——当 14.0 将 DMA 设为默认时，意义在于 “默认情况下大部分 FreeBSD 系统不需要完整 MTA” 而非 “DMA 在功能上等价于 sendmail”
  
**文献**：FreeBSD 5.0-5.4 Release Notes [Z]. 2003-2005；FreeBSD 14.0-RELEASE Announcement [Z]. 2023-11-20；Allman E. Sendmail: An Internetwork Mail Router [C]//USENIX Summer Conference. 1983；Venema W. Postfix Architecture Overview [EB/OL]. postfix.org

## 100.17.3 第三方软件变更的史料辨析

  **要点**：5.x 时期第三方软件变更的核心特征是 “引入而非替换”——PF 引入是与 IPFilter 并存而非替代，sendmail 延续默认地位而非被替换。这种 “新旧并存” 的过渡模式是 FreeBSD 5.x 时期 “激进内核改造 + 保守用户空间” 策略的体现：内核层面（SMPng、GEOM、KSE、ULE）进行激进重写，但用户空间层面（sendmail、BIND、GCC 2.95/3.x）保持稳定，避免内核和用户空间同时变动给用户带来过大冲击。真正的大规模第三方软件替换发生在 10.x 时期（2014 年），届时 Clang 替换 GCC、Unbound 替换 BIND、bsdinstall 替换 sysinstall 等多项变更在一到两个版本内集中完成。
  
**史料**：FreeBSD 5.x Release Notes、FreeBSD 10.x Release Notes、freebsd-hackers 邮件列表 ［A］
  
**史观**：总纲第 4 条——分离聚合是永恒规律：5.x 时期的第三方软件策略揭示了一个规律——系统软件的 “替换” 往往不是在一个版本内完成的，而是经历 “引入共存 → 默认切换 → 旧者移除” 三个阶段，而 5.x 对 PF/IPFilter、sendmail 的策略处于第一阶段（引入共存），旧者移除（IPFilter 移除）发生在 10.x（2014 年），sendmail 替换发生在 14.0（2023 年，详见 100.17.2）
  
**辨析**：不能因为 5.x 时期没有发生大规模第三方软件替换就认为 5.x “保守”——5.x 在内核层面的激进改造（SMPng、KSE、GEOM、ULE、MAC）是整个 FreeBSD 历史上最剧烈的架构变更，用户空间保持稳定是明智的工程权衡；“引入而非替换” 的策略降低了 5.x 的升级风险——用户可以在 5.x 选择使用 PF 或继续使用 IPFilter，可以选择使用 UFS2 或继续使用 UFS1，无需被迫立即迁移
