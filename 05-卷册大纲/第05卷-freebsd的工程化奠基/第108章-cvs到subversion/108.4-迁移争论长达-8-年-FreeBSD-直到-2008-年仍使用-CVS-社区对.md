# 108.4 迁移争论长达 8 年——FreeBSD 直到 2008 年仍使用 CVS，社区对 BitKeeper、Git、Mercurial 等替代方案无法达成共识，最终由 Peter Wemm（彼得·韦姆） 强行推进 SVN 转换，反映核心团队决策机制的低效

## 108.4.1 迁移争论的社区过程

  **要点**：FreeBSD 社区讨论 CVS 替代方案的起始时间存在两种口径：主节口径自 2000 年起、争论持续 8 年；一手口述（BSDTalk EP164，Peter Wemm）则称替换 CVS 的讨论可追溯至 1997 年、历时约十一年，两口径并存待考（标题“8 年”取 2000 年起算口径）；核心争论是 SVN vs Git vs Mercurial，社区无法达成共识；BitKeeper 因许可证问题被排除
  
**史料**：freebsd-hackers 邮件（2000-2008） ［A］
  
**史观**：总纲第 21 条——革命与改革是历史方法论的分歧，8 年争论是否反映决策低效
  
**辨析**：8 年争论不是“必要”与否的问题而是社区共识机制的代价——FreeBSD Core Team 采用共识导向决策，任何重大变更须社区广泛同意，8 年争论反映社区对版本控制工具选择的慎重而非决策低效；但 8 年争论也使 FreeBSD 错失 Git 早期红利，这是共识机制的必然代价
  
**文献**：freebsd-hackers mailing list VCS migration discussions (2000-2008)；freebsd-arch mailing list 2008 SVN decision；LWN.net FreeBSD VCS migration (2008) ［A］

## 108.4.2 Peter Wemm 强行推进的决策

  **要点**：Peter Wemm 于 2008 年以行政决定推进 SVN 迁移（当事人 BSDTalk EP164 自述：因社区无法说服彼此，最终以行政决定选择 Subversion）；“强行推进是否构成决策低效”不在要点中断言、留待辨析双面呈现，其直接效果是终结了长期争论
  
**史料**：邮件、commit log ［A］
  
**史观**：总纲第 5 条——没有必然性，只有偶然性，Wemm 的个人决策偶然终结争论
  
**辨析**：强行推进在程序上破坏社区共识但在结果上终结了 8 年僵局——Wemm 作为仓库基础设施维护者具有事实上的技术权力，其“强行推进”是技术权力凌驾共识程序的具体案例；是否破坏社区共识须依赖 freebsd-arch 邮件列表 2008 年讨论交叉验证
  
**文献**：freebsd-hackers mailing list Wemm SVN push (2008)；freebsd-arch mailing list core team decision；Wemm, P. SVN migration status reports (2008) ［A］

## 108.4.3 争论辨析

  **要点**：争论辨析：(1) 8 年是否过长；(2) SVN 是否正确选择（vs Git）；(3) 核心团队决策机制是否低效
  
**史料**：邮件、博客 ［C］
  
**史观**：总纲第 9 条——经验优先
  
**辨析**：决策机制在事实上是低效的——8 年争论未能形成共识，最终由个人技术权力强行终结，反映共识导向决策在面对技术路线分歧时的局限性；但低效是相对的——Linux 内核由 Linus Torvalds 单一决策可快速迁移但牺牲社区共识，FreeBSD 的共识机制牺牲速度但保留社区凝聚力
  
**文献**：freebsd-hackers mailing list 8-year debate analysis (2008)；freebsd-arch mailing list VCS decision review；LWN.net FreeBSD SVN discussion (2008) ［A］

**要点**：

- Smith 以首席发布工程师身份描述流程全貌：决定发布后进入代码冻结，阻止开发者添入新功能而专注收尾，随后切出发布分支并做测试构建（自 beta 起），此间一切代码改动须经发布工程团队批准方可提交，由该队裁量何者为必须先行解决的拦路问题、何者留待未来版本；经候选版本测试合格方正式发布，同一团队同时操办 6.3 与 7.0 两个发布；版本号语义上，次版本号系列内竭力维持 ABI 与 API 不变，主版本号变更则一切约束解除，允许要求重编译的剧变与新子系统进场。（BSDTalk EP142，[106.80-241.68]，L1）
- 7.0 并无单一中心目标，主旋律是自 FreeBSD 5 起延续至今的 SMPNG 倡议进入性能阶段：内核已大体具备 SMP 能力，开发者转而剖析锁的落点与次序以求削减瓶颈；Kris Kennaway（转写误作 Chris Kenoway）的基准测试被用作定位与验证工具，部分基准较 Linux 领先约 15%，但 Smith 明确拒绝将其外推为全面优势，并举例基准互动的健康竞争——Kennaway 曾发现 Linux 侧异常行为、经提出后由对方修复。 [存疑脚注] 基准测试者人名系据上下文（基准与瓶颈分析）辨识为 Kris Kennaway，转写原文作 Chris Kenoway，待与其他史料核对（BSDTalk EP142，[414.06-664.64]，L1）
- 7.0 的两项悬置：ULE 调度器仅以毫厘之差未成默认，被喻为“稍晚了些的选择性手术”，7.1 大概率转正；DTrace 则因拟议中思科方面感兴趣的合同工作告吹而搁浅，未能进入 7.0，仍在与有意者接洽。支持矩阵上，ZFS 不向 6 系列回移而性能改进择要回移，开发者重心在 7；5 系列仅余安全团队短暂维护、不再出新版；Linux 兼容层默认仍对 2.4 内核，2.6 支持有进展但尚有缺陷与缺项、未达默认水准；7 的改进大体利于服务器，桌面用户须自行重编译内核换用 ULE 方得其利。（BSDTalk EP142，[467.00-721.20]，L1）
- FreeBSD 7.1 的特性包由当事人现场列明：ULE 调度器在 7.0 已随附但未设默认，7.1 起将开关翻转；John Baldwin 将 cpuset 自 8-CURRENT 回移以利计算密集应用；7.1 是首个包含 DTrace 支持的发行版；网络栈多处理器改造使 BIND 在高负载下并行性能大幅提升；Chelsio 万兆网卡的全 TCP offload 亦自 8 回移，使整个网络栈可下沉到网卡硬件运行。（BSDTalk EP164，[392.42-455.34]，L1）
- 当事人以升级体验刻画版本策略的效果：4 到 6 的迁移因 GCC 2 升 GCC 3 的 ABI 断裂与共享库版本号变更而极其痛苦，是大规模部署者的创伤记忆；6 到 7 虽同样更换编译器，但 ABI 相对稳定，配合符号版本化锁定内核与模块接口，成为平顺的增量升级。6.4 被定性为 6.x 系列近乎收官的一版，发布流程近乎自动导航；而 7.0 被评价为项目历史上最成功的点零版本之一，打破了点零发布必出问题的成见。（BSDTalk EP164，[962.70-1058.62]，L1）
- 虚拟化被确认为 8-CURRENT 的头号议题。2008 年夏在剑桥召开的开发者峰会是首次脱离大型会议独立举办的四天峰会，二十至三十名开发者集体通读数千行虚拟化代码。其中的网络栈虚拟化工作使每个 jail 拥有独立的防火墙、IPsec、路由、虚拟网络接口与限速， jail 内管理员可管理自己的栈实例，这是既有 jail 功能无法做到的。（BSDTalk EP164，[1098.78-1170.74]，L1）
- Peter Wemm 一手还原源代码控制迁移的决策史：替换 CVS 的讨论可追溯至 1997 年，历时约十一年；期间评估过 Bitkeeper、Perforce、PCVS、PRCS、Darcs、Mercurial 等候选，Perforce 曾长期承载项目分支，但其客户端状态集中于服务器导致数据库膨胀、维护纪律要求过高而不可持续；CVS 的致命缺陷是分支提交会永久丢失文件来源等元数据且不可恢复；由于无人能说服彼此，最终以行政决定选择 Subversion——作为 CVS 的逻辑后继保留既有工作流，并把分散于多个仓库的开发收拢回单一可见仓库。（BSDTalk EP164，[1500.56-1737.68]，L1）
- 迁移工程本身由 Peter Wemm 个人承担：花四至六个月修复历年积累的 RCS 文件微妙损坏，编写数千行脚本、配置与大量手写符号标签转换表，并依赖个人记忆与邮件列表存档找回仓库中已无记录的 5-STABLE 分支起点，迁移期间仓库停机数日。当事人定义的成功标准是全部开发者直接向 Subversion 提交 base 树、利用 merge info 追踪跨分支合并；同时明确过渡态：ports 与 doc 树仍留 CVS，用户继续经 CVSup 获取导出，6.x 与 7.x 发行周期在 CVS 内维护，8 是否直接自 Subversion 发行尚待决定，Perforce 项目分支预期逐步迁出收尾。（BSDTalk EP164，[1785.24-2030.32]，L1）
- gjournal 是块级日志而非文件系统日志：它运行于文件系统层之下，仅需文件系统极少量特化代码即可提供日志能力，且不区分数据与元数据而两者皆记录；因此即便启用 gjournal，FreeBSD 在严格意义上仍属无日志文件系统的主流操作系统，引用时不应将 gjournal 记作 UFS 自身的日志功能。（BSDTalk EP52，[117.82-190.9]，L1）
- 作者说明同时记录数据与元数据的设计动机：仅记元数据存在已知竞态，两者皆记使日志设计更干净，并带来崩溃后镜像设备保持一致、无需重新同步等附带收益；gjournal 还可用于绕开 GBDE 的非可靠性问题。（BSDTalk EP52，[168.42-230.5]，L1）
- 在 soft updates 之下唯一已知的不一致是资源泄漏，后台 fsck 的作用即回收丢失资源；gjournal 使后台 fsck 不再必要。对删除但仍被进程打开的文件，inode 无文件名引用却仍占盘，原方案将其移入 .deleted 目录以便挂载时整体清除，发布补丁后收到反对意见，作者正改写为依赖更快速 fsck 仅回收泄漏 inode 与块的方案。（BSDTalk EP52，[239.98-405.54]，L1）
- GELI 是 GEOM 上的磁盘加密层，与 GBDE 同层但实现路径不同；作者刚提交的数据认证代码使其能够校验数据本身，据其所知此前没有磁盘加密框架认证数据，这对断电场景下防止新数据与旧哈希错配、保证崩溃一致性至关重要。（BSDTalk EP52，[517.02-648.12]，L1）

**史料**：

- 一手运维场景自述：布法罗纽约州立大学计算机系以 FreeBSD 兼营生产与教学，有八处理器 64 位系统承担网页、FTP 与视频处理负载，系统管理员即 Smith 本人且执教高级内核课程；其跨大版本升级惯用源码树更新后整体重建安装，第三方软件以 portupgrade 从源码跟进，并期待以 ZFS 改造系内大容量存储服务器。（BSDTalk EP142，[262.20-364.80]，L1）
- 8-CURRENT 期的组织性一手节点：7.0 发布、API 冻结之后，开发者随即开启 FreeBSD 8 的自由议题，其中 jail 基础设施改进讨论已于受访前两周启动，jail 被评“立了大功但已见老”；与 PC-BSD、DesktopBSD 等衍生项目的发布团队则几乎不相往来，Smith 自承沟通是其短板并有意改善。（BSDTalk EP142，[737.68-798.68]，L1）
- 该期为 gjournal 与 GELI 作者的一手口述：补丁面向 FreeBSD CURRENT 与 FreeBSD 6-STABLE 发布、全部测试基于 UFS2（预计兼容 UFS1）、计划先行提交 CURRENT 并拟在 6.2 之前合入 6-STABLE；同时载明 2006 年 FreeBSD 版本控制实况——项目在受访者加入前已选定 Perforce，当时存在 CVS 转 Subversion 的失败尝试，因而 Perforce 是唯一可行选择，如今大多数开发工作在 Perforce、其提交量远超主 CVS 仓库。（BSDTalk EP52，[277.58-848.3]，L1）

**史观**：

- 总纲10 动手者创造历史：发布工程师的自我刻画是协调者与守门人而非明星编码者：发布周期内只亲手修唯他能修的缺陷，其余时间用于审阅他人工作，非发布期方有余裕写码——发布质量被组织为对众人之工的裁断与串接，历史由大量无名提交与其裁决流程共同完成。（BSDTalk EP142，[838.76-858.14]，L1）
- 总纲12 科学是形式主义：Smith 对 15% 领先数字的自我节制——强调基准只是改进工具、拒绝作出“处处优于 Linux”的普遍断言——显示项目内部对形式化度量的效力边界有自觉：数字是组织工程的手段，不是世界结构的陈述。（BSDTalk EP142，[612.12-644.24]，L1）
- 总纲10 动手者创造历史：被社区公认为“无法转换”的 FreeBSD 仓库最终得以后转，靠的不是制度安排而是一个人的数月劳动：Peter Wemm 自愿承担修复、记忆考订与停机转换的全部风险。这一转折点由一线动手者的个体劳动与个人记忆撬动，工程史的关键节点往往系于愿意“站出来把它做成”的具体个人。（BSDTalk EP164，[1888.04-1905.64]，L1）
- 总纲6 和解优于斗争：FreeBSD 被当事人自认为开源世界中少有的民选领导层项目：选举允许领导层渐进更替，人来人往而项目延续，避免过度依赖单一个人导致的倦怠与断档。2008 年选举中上届成员几乎全员连任、仅一人退出、两名新人加入，被在场者解读为开发者对项目现状的信任投票；权力以周期性同意而非斗争方式完成再分配。（BSDTalk EP164，[281.78-334.66]，L1）
- 总纲4 分离聚合是永恒规律：作者断言 gjournal 远比 soft updates 代码简单，关键在于它是完全独立于 UFS 的代码块而非内核集成实现，而 soft updates 最受诟病之处恰是代码复杂；外置分离构造与内核集成构造之争呈现了存储技术中分离与聚合两条路线的往复。（BSDTalk EP52，[405.54-448.5]，L1）
- 总纲5 没有必然性，只有偶然性：作者自述工具选择并无理性最优可言：Perforce 是项目在其实质参与前的既成事实，Subversion 转换失败这一偶然事件将其封闭在既有路径中；技术基础设施的形态常由偶然决策与失败尝试的叠加所规定。（BSDTalk EP52，[801.74-830.34]，L1）

**辨析**：

- Smith 转述老一辈开发者间流传的“奇数版本魔咒”：FreeBSD 3 与 5 两个主版本皆非项目佳话，故社区期望 7.0 破除趋势。此属把成败经验凝结为魔咒的社区俗信，主版本号本身并不构成失败原因，恰是典型的把偶然处境误作规律的叙事，版本评价须回到各版本具体工程事实。（BSDTalk EP142，[924.82-940.82]，L2）
- 转写存在系统性误植，须按上下文考订：Zen 应为 Xen（6.4 与 7.1 支持以客户操作系统身份运行于 Xen，补丁来自 Kip Macy，当时未全量入 base 树，8 已全部合入）、yearly scheduler 应为 ULE 调度器、de-trace 应为 DTrace、Macurial 应为 Mercurial、user offering system 应为 guest operating system。另转写将两条录音线交错排列且说话人归属时有错乱，“两名新成员是我和 Peter”一语与 Peter Wemm 自称首届选举即任 core team 相互矛盾，新成员身份细节须以会议纪要与邮件列表复核。[存疑脚注] 本期说话人归属及个别新成员身份无法自转写内证确证。 [存疑脚注] 转写交错排列致说话人归属存疑；Zen、ULE 等均为按上下文与同期 FreeBSD 开发史所作考订，待会议纪要交叉验证。（BSDTalk EP164，[301.66-324.66]，L4）
- 转写存在段序错乱与局部讹误：如“write-free configurations”“geom roll”“multi-puffing”等处疑为音频识别错误，后者涉及作者在 Perforce 分支上一个约两年的多路径 GEOM 类的名称，引用该类名称前须回听录音核对；UFS1 兼容性亦仅属作者推测而非测试结论。 [存疑脚注] 多路径 GEOM 类名称与镜像一致性收益的适用配置在转写中均有讹误嫌疑，UFS1 兼容性为作者未经测试的推断。（BSDTalk EP52，[592.4-613.24]，L5）
