# 108.3 社区开发模式变化——CVS 时代的补丁文化与 SVN 时代的中央仓库文化

## 108.3.1 CVS 时代的补丁文化

  **要点**：CVS 时代 FreeBSD 社区采用补丁文化：开发者通过 diff/patch 提交补丁，由 committer 审核提交；补丁文化强调社区参与，边缘者可通过补丁贡献
  
**史料**：freebsd-hackers 邮件、补丁提交记录 ［A］
  
**史观**：总纲第 13 条——边缘者的作用，补丁文化允许边缘者参与
  
**辨析**：补丁文化与中央仓库文化无绝对优劣但有不同后果——补丁文化降低参与门槛但增加 committer 审核负担，中央仓库文化提升提交效率但提高边缘者参与门槛；freebsd.duckdb contributors 表显示 freebsd-src 仓库 commit 数量在 2008 年前后未发生突变（月度 commit 数 644-1430 区间波动），说明模式变化对总提交量的影响有限，但对贡献者结构的影响须依赖邮件列表讨论交叉验证
  
**文献**：freebsd-hackers mailing list patch culture (2000-2008)；freebsd-committers mailing list commit statistics；McKusick, M. K. FreeBSD committer model in Open Sources (O'Reilly, 1999) ［A］

## 108.3.2 SVN 时代的中央仓库文化

  **要点**：SVN 时代 FreeBSD 社区转向中央仓库文化：committer 直接提交，分支管理更规范；但边缘者参与门槛提高，补丁提交减少
  
**史料**：commit log、邮件 ［A］
  
**史观**：总纲第 14 条——话语权与边缘者，中央仓库文化可能削弱边缘者参与
  
**辨析**：文化变化影响在 freebsd.duckdb 中可通过 contributors 表首末活动时间间接验证——2008 年后新进入 committer 的首条 commit 时间分布须依赖 contributors 表逐人核查，但 “边缘者参与门槛提高” 的主观感受在 commit 中不可见，须依赖 freebsd-hackers 邮件列表与 freebsd-advocacy 讨论交叉验证
  
**文献**：freebsd-hackers mailing list SVN commit culture (2008-2010)；freebsd-committers mailing list；FreeBSD Committer's Guide (freebsd.org) ［A］

## 108.3.3 开发模式变化辨析

  **要点**：开发模式变化辨析：(1) 补丁文化是否更民主；(2) 中央仓库是否更高效；(3) 边缘者参与是否减少
  
**史料**：邮件、commit log ［A］
  
**史观**：总纲第 4 条——0 信任原则
  
**辨析**：模式无绝对优劣但有后果——补丁文化强调社区参与但效率受限于 committer 审核带宽，中央仓库文化强调提交效率但边缘者参与门槛提高；freebsd.duckdb 数据显示 freebsd-src 仓库月度 commit 数在 2008 年前后未发生突变，说明模式变化对总提交量影响有限
  
**文献**：freebsd-hackers mailing list patch vs commit culture (2008-2010)；freebsd-arch mailing list development model (2009)；FreeBSD Committer's Guide ［A］

## 108.3.4 模式变化史料辨析

  **要点**：模式变化史料疑点：(1) 变化的时间线；(2) 关键推动者；(3) 是否有社区讨论影响变化
  
**史料**：邮件、commit log ［A］
  
**史观**：总纲第 4 条——0 信任原则
  
**辨析**：变化原因在 bsd_commits.duckdb 中无直接 commit 证据——SVN 迁移作为模式变化的触发器是技术驱动的，但文化变化的深层原因（committer 群体代际更替、企业受薪开发者比重上升）须依赖邮件列表讨论与 Foundation 年度报告交叉验证
  
**文献**：freebsd-hackers mailing list 2000-2008 VCS migration discussions；freebsd-arch mailing list VCS selection threads；FreeBSD Committer's Guide ［A］

**要点**：

- FreeBSD 的开发组织呈一条代码成熟度连续谱：未经打磨的“生代码”先进入 current，约每六个月自 current 切出 stable 分支，经完整 QA 后发布 release，此后 errata 与安全修复以更严的审视回灌；理论上每 18 至 24 个月一个版本、分支活跃约两年，且因项目资源有限，同时只维护一个 stable 与一个 current，以把资源战略性地投给用户最需要的质量。（YouTube EP66enuplpZxw，[302.31-462.24]，L1）
- 现实与理论偏差显著：分支寿命差异极大，4.x 分支长年活跃获得大量关注，紧随其后的 5.x 分支却迅速失宠；5.x 试图同时完成 SMP 相关改造而“贪多嚼不烂”，分支久拖不决，6.x 的快速推出部分源于用户急于逃离 5.x，6 到 7、7 到 8 之间则间隔合理、产品质量良好；代码冻结造成需求积压，分支点之后提交量骤然上升；讲者并自认 current 在 5.x 时期非常不稳定，这正是项目另起 Perforce 侧线的由来。（YouTube EP66enuplpZxw，[612.37-654.85]，L1）
- 针对“曲线趋平即 FreeBSD 正在死亡”的流行解读，讲者以数据完整性反驳：仅统计 CVS 提交确见趋平，但大量开发发生在 Perforce 侧线上、其曲线仍近指数增长；迁移 Subversion 后开发者可用 svk、git-svn 或 Mercurial 网关进行与主仓库脱钩的私有工作，这部分数据无法采集，故“死亡论”是统计口径缺陷造成的误导。（YouTube EP66enuplpZxw，[654.85-726.53]，L1）
- 商业使用 FreeBSD 的核心风险集中在升级：第一个版本怎么做都不难，唯有第一次升级时才暴露当初的取舍对错；企业需要向前移植本地修改，并区分偶发性修改（如对 libc 例程的缺陷修复）与核心性修改（如为自家应用定制的调度器）；讲者强调缺陷修复一般不构成竞争优势——修补串口例程对以转发数据包为业的设备毫无商业价值，而携带本地补丁的成本随时间累积，把每一行改动都视作竞争资产是短视管理决策的根源。（YouTube EP66enuplpZxw，[837.21-1089.17]，L1）
- 讲者归纳四种跟踪策略的谱系与代价：抓取即用最简单且无需社区互动，但升级痛苦、串口设备命名等 API 变更屡屡踩坑、新特性与新硬件支持进不来；跟踪 stable 分支可在分支生命周期内演进多年、借社区 QA 力量、分支早期向上游推送补丁容易，但多分支维护开销大且跨 major 移植在所难免；镜像 FreeBSD 开发流程把痛苦摊成持续小额而非跳版巨痛并可与社区互哺，却重复了 release engineering 的工作、内部切点的分支难以获得社区帮助，IronPort 曾做成此法最终亦在 7 时代放弃；三年不跟踪再做大移植则被明确指为最差实践。（YouTube EP66enuplpZxw，[1100.87-1913.21]，L1）
