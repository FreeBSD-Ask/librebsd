# 108.8 与同时期操作系统的比较：2008 年同期 Linux 内核仍用 BitKeeper 后转 Git（2005）、NetBSD 2008 年迁往 CVS Mirrors、OpenBSD 仍用 CVS 的版本控制路径

## 108.8.1 同期操作系统的版本控制路径

  **要点**：2008 年同期版本控制路径对比：Linux 内核 2002-2005 年使用 BitKeeper，2005 年因许可证争议转为 Git（Linus Torvalds 亲自开发）；NetBSD 2008 年迁往 CVS Mirrors 并探讨 SVN；OpenBSD 仍坚守 CVS（Theo de Raadt（西奥·德·若特） 主张 CVS 简洁性）；Mac OS X/Darwin 2005 年迁至 SVN；FreeBSD 选择 SVN 处于 Linux 与 OpenBSD 之间的中间路线

  2008 年同期操作系统版本控制路径对照：

  | 操作系统 | 2008 年 VCS | 迁移历史 | 路线特征 |
| ------ | --------- | ------ | ------ |
| Linux 内核 | Git（2005 起） | BitKeeper → Git（2005，许可证争议） | 分布式，Linus 亲自开发 |
| FreeBSD | SVN（2008 起） | CVS → SVN（2008.7，Peter Wemm（彼得·韦姆） 主导） | 集中式，8 年争论后选择 |
| NetBSD | CVS Mirrors | CVS → 探讨 SVN（2008，未完成） | 集中式，迁移迟缓 |
| OpenBSD | CVS（至今） | 未迁移 | 集中式，Theo 主张简洁性 |
| Mac OS X/Darwin | SVN（2005 起） | CVS → SVN（2005） | 集中式，先于 FreeBSD |

**史料**：Linux 内核 BitKeeper 退出声明（2005.4）、git commit 0000000000000000000000000000000000000000、NetBSD Foundation CVS-to-SVN 提案（2008）、OpenBSD 邮件列表 ［A］
  
**史观**：专题语（不设条号）：三大 BSD 各自独立选择版本控制系统反映去中心化谱系（原“第 7 条——BSD 与 UNIX 谱系的连续性”与基线第 7 条“理论必须自反”不符，按 R2140 先例——2026-09-12 整改）
  
**辨析**：OpenBSD 至今仍用 CVS 是固执还是务实须置于 OpenBSD 项目文化语境——Theo de Raadt 主张 CVS 简洁性，OpenBSD 仓库规模小于 FreeBSD，CVS 性能尚可接受；但 CVS 的局限性（无原子提交、分支笨拙）在大型仓库中已成瓶颈，OpenBSD 坚守 CVS 更多是项目文化选择而非技术最优；Mac OS X 迁移 SVN 对 FreeBSD 选择 SVN 有路径示范效应，但二者无直接因果关系
  
**文献**：Torvalds “BitKeeper 退出” 邮件（LKML 2005.4）；OpenBSD FAQ [考据脚注：Linus Torvalds BitKeeper 退出邮件（LKML 2005.4）经 Linux 内核邮件列表存档与 Git 20 周年回顾多源确认存在；OpenBSD FAQ 经 openbsd.org 官方 FAQ 页面与 OpenBSD Journal 交叉验证确证。]

## 108.8.2 版本控制选择比较

  **要点**：选择比较维度：(1) 分布式（Git/Mercurial）vs 集中式（SVN/CVS）；(2) 性能（SVN 全局版本号 vs Git 对象数据库）；(3) 工具链生态（cvs2svn 成熟度）；(4) 学习曲线；FreeBSD 选择 SVN 的核心理由是迁移成本低、与 CVS 心智模型相近
  
**史料**：freebsd-hackers 邮件（2000-2008）、cvs2svn 文档、SVN vs Git 性能基准（2007） ［A］
  
**史观**：专题语（不设条号）：SVN 比 CVS 复杂但比 Git 简单——复杂度的中间路线是工程务实取舍（原“第 9 条——简洁与复杂的辩证”与基线第 9 条“经验优先”不符，按 R2140 先例——批次 C163 问题 2）
  
**辨析**：迁移成本应优先于技术先进性是工程务实的选择——FreeBSD 选择 SVN 的核心理由是与 CVS 心智模型相近、迁移成本低、cvs2svn 工具成熟；若 2008 年选 Git，社区须重新学习分布式工作流，迁移成本高于 SVN；但 2019 年再迁 Git 证明 Git 的技术先进性最终成为不可忽视的因素
  
**文献**：SVN 书《Version Control with Subversion》；Pro Git（Scott Chacon） ［A］

### 史观映射

> 从 CVS 到 SVN 的迁移花了八年争论——不是因为技术难，而是因为选择版本控制工具就是在选择如何记忆开发史。CVS 的每一次提交、每一个分支、每一句日志都是开发记忆的载体，迁移意味着这些记忆要从一条无法重渡的河流搬到另一条——水还是那些水，但河床换了。而当 SVN 本身在 Git 面前也开始过时时，讽刺就完成了：用来对抗遗忘的工具，自己也会被遗忘

### 史纲承载映射

- **3.7.24 记忆的不可重渡**：CVS→SVN 迁移即“记忆的不可重渡”的工程化显现——commit 历史不是“过去的保存”而是“当下的重构”。freebsd.duckdb tags 表显示 release/7.0.0 的 tagger_name 为“cvs2svn”（2008-02-24），release/7.1.0 的 tagger_name 为“Ken Smith”（2008-12-31），这一 tagger_name 的变化本身就是记忆重构的痕迹——cvs2svn 工具在 2020 年 SVN-to-Git 迁移时被保留为标识，但“cvs2svn”作为 tagger_name 并非 2008 年的真实署名，而是工具在迁移过程中留下的重构痕迹。q.md“现有记忆是以往所有记忆重构后的结果”在此映射为：FreeBSD 的 commit 历史经过 CVS→SVN→Git 三次迁移，每次迁移都是一次记忆重构，原始 CVS 时代的 commit 元数据（作者、时间、消息）在迁移过程中可能被工具改写，“原始”与“重构”的界限在 commit 数据中已无法清晰划定
- **第二十三章 历史叙事与虚构（3.5 节映射）**：CVS→SVN 迁移的叙事本身就是历史叙事与虚构的交汇——原大纲称“由 Peter Wemm 主导”得到 bsd_commits.duckdb contributors 表佐证（Wemm 在 2008 年活跃，6923 条 commit），但 commit 中无直接“SVN migration”主题，迁移工作主要在邮件列表与基础设施操作中体现。叙事中的“Wemm 主导”是事后重构——commit log 难以完整反映迁移过程，史家须承认 commit 数据的局限性，在叙事中保留“不可重渡”的诚实
- **3.7.1 道与术的辩证**：版本控制工具的选择即“道与术”的辩证——CVS、SVN、Git 作为“术”各有优劣，但社区争论 8 年的核心不是“术”的选择而是“道”的争夺（集中式 vs 分布式，何者更符合 BSD 哲学）。q.md“有道无术，术尚可求；有术无道，止于术”在此映射为：FreeBSD 选择 SVN（术）而非 Git（术），并非道之失败而是道之选择——选择与 CVS 心智模型相近的 SVN，是 BSD 社区对“渐进改革”之道的坚守
