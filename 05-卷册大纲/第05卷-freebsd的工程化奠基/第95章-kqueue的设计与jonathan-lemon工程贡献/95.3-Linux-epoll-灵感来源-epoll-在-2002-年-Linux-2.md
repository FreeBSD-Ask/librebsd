# 95.3 Linux epoll 灵感来源——epoll 在 2002 年 Linux 2.5.44 引入

## 95.3.1 epoll 的设计灵感

  **要点**：Linux epoll 由 Davide Libenzi 设计，2002.10.22 在 Linux 2.5.44 引入 sys_epoll 系统调用，灵感来源存在争议：(1) Libenzi 自述参考 /dev/poll；(2) Linux 内核邮件列表提及 kqueue；(3) epoll 选择了 composable 设计而非 kqueue 的 filter 中心化
  
**史料**：Libenzi “Improving (network) I/O performance”(xmailserver.org/linux-patches/nio-improve.html, 2001-07-01 初稿，2002-10-30 更新为 epoll 合入内核版本)、Linux kernel 2.5.44 changelog、LKML 2002.3 epoll 讨论［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］ 〔L1 代码；L2 即时通讯〕
  
**史观**：总纲第 5 条——没有必然性，只有偶然性，Libenzi 选择 composable 而非 filter 路线导致后续 Linux 生态与 BSD 生态分野（原挂第 1 条系伪标签，按偶然性论旨改挂第 5 条）
  
**辨析**：Libenzi 与 Lemon 的设计是否独立演化，需对比二者 2002 前的邮件往来

## 95.3.2 kqueue 对 epoll 的效应

  **要点**：kqueue 对 epoll 的具体影响体现在：(1) stateful 设计思想一致；(2) 内核维护就绪列表；(3) 但 epoll 拒绝 filter 抽象，改为 “任意 fd 即可挂载” 的 composable 模型，每新增一种资源不需改内核
  
**史料**：Libenzi “Improving (network) I/O performance” 论文（xmailserver.org, 2002.10.30 更新版本，论文未设独立的 kqueue 对比节，绪论考察的五种方法 poll、/dev/poll、RT 信号、RT signals with one-sig-per-fd patch、/dev/epoll 未将 kqueue 列入考察范围）、Linux **epoll(7)** 手册页 ［A］
  
**史观**：专题语（不设总纲条号）——epoll 的 composable 简洁在扩展性上胜过 kqueue filter（原挂第 9 条“简洁与复杂的辩证”系自撰名目，与权威“经验优先”不符，去条号）

### 95.3.5.2 composable 设计的独立性主张

  **要点**：Libenzi 的 epoll 采用 composable 设计（任意 fd 即可挂载，无需专用 filter），与 kqueue 的 filter 中心化设计（EVFILT_READ/EVFILT_WRITE 等七类 filter）形成根本分野；这一设计差异被 Libenzi 阵营主张为 epoll 独立于 kqueue 的核心证据——若 epoll 衍生自 kqueue，应当继承 filter 抽象而非抛弃之。但反对者指出，composable 与 filter 之争是设计哲学选择而非独立发明的证据，“参考后选择不同路线”与“完全独立发明”在考据上难以区分［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］
  
**史料**：Linux **epoll(7)** 手册页（epoll 使用 EPOLLIN/EPOLLOUT/EPOLLERR/EPOLLET 等事件掩码，无 filter 概念）；Lemon BSDCon 2000 论文第 4.1 节 kqueue filters（EVFILT_READ/EVFILT_WRITE/EVFILT_AIO/EVFILT_VNODE/EVFILT_PROC/EVFILT_SIGNAL/EVFILT_TIMER）［A］
  
**史观**：专题语（不设总纲条号）——composable 简洁与 filter 中心化是设计空间中的两种权衡，二者并非衍生关系而是平行选择（原挂第 9 条“简洁与复杂的辩证”系自撰名目，与权威“经验优先”不符，去条号）
  
**辨析**：composable 设计的独立性主张存在逻辑漏洞——“选择不同设计”不能反证“未受影响”，设计者可能在参考后主动选择差异化路线；这一辨析点须结合 0 信任原则审慎对待，避免单方面采信 Libenzi 阵营的独立性主张
  
**文献**：Linux **epoll(7)** 手册页；Lemon BSDCon 2000 论文 ［A］

### 95.3.6.2 filter 中心化设计的辩护

  **要点**：FreeBSD 阵营对 Libenzi composable 设计独立性主张的再回应，集中于 filter 中心化设计的工程优越性——filter 抽象允许内核为每种事件源提供定制化的就绪判定逻辑（如 EVFILT_VNODE 的文件系统变更语义、EVFILT_PROC 的进程退出语义），而 epoll 的 composable 设计只能处理“fd 可读/可写”这一通用语义，对非 socket 事件源（如文件系统变更、进程退出）的支持需通过额外机制（如 inotify、netlink）补足。这一辩护主张 filter 中心化并非技术债务，而是语义丰富性的体现

#### 95.3.7 合图层：偶然性与形式主义的辩证审视

### 95.3.7.1 偶然性视角下的 epoll/kqueue 分野

  **要点**：从项目史观总纲第 5 条“没有必然性，只有偶然性”审视，epoll 与 kqueue 的设计分野是多重偶然性的叠加——Lemon 在 2000 年选择 filter 中心化路线是偶然，Libenzi 在 2001 年选择 composable 路线是偶然，二者的设计差异并非技术必然性的展开，而是两个独立主体在各自工程语境中的偶然决策。若 Lemon 未在 2000 年提交 kqueue，或 Libenzi 未在 2001 年提出 /dev/epoll，事件通知领域的历史将完全不同。“epoll 衍生自 kqueue”的指控与“epoll 独立发明”的辩护，本质上都是在事后用必然性叙事重构偶然性事件——项目史观总纲第 5.3 节指出“记忆将许多偶然性认识为一种必然性，同时否定了这种偶然性的发生”
  
**史料**：项目史观总纲第 5 章第 5.1-5.3 节；**freebsd.duckdb** kqueue 首次 commit 2000-04-16；Libenzi /dev/epoll 2001.7 ［A］
  
**史观**：总纲第 5 条——没有必然性，只有偶然性；每一个关键人物、每一次 fork、每一个技术决定，都是不可替代的偶然
  
**辨析**：偶然性视角不否定技术影响的客观存在——kqueue 先于 epoll 是事实，但“先发”与“被借鉴”是两个不同的命题，偶然性审视要求区分二者；衍生指控与独立辩护都是形式主义的叙事建构，真相可能介于二者之间

### 95.3.7.3 合图层的辩证综合

  **要点**：合图层将偶然性视角与形式主义视角综合——epoll 与 kqueue 的关系是偶然性事件在形式主义化叙事中的重构。偶然性视角揭示二者都是不可替代的独立技术决策，形式主义视角揭示衍生争议本身是权力-知识的共谋场域。综合二者，epoll 与 kqueue 的关系既非纯粹的衍生（Libenzi 的 composable 设计确实不同于 Lemon 的 filter 中心化，且 Libenzi 论文 References 节列 10 条文献完全未引用 kqueue，构成独立性主张的形式主义证据），也非纯粹的独立发明（时间线优先性——kqueue 2000.4 早于 /dev/epoll 2001.7 约 15 个月——与术语沿用——level-triggered/edge-triggered 由 Lemon BSDCon 2000 首创——确证了某种程度的影响传播），真相在衍生与独立之间，而这一“之间”的状态正是形式主义化叙事所试图抹除的——形式主义要求非此即彼的归属判断，而偶然性的真相是模糊的传播与转化。Libenzi 论文 References 节缺失 kqueue 引用这一事实，在合图层中呈现其双重性质——作为独立性主张的形式主义证据，它支持 Libenzi 阵营；作为权力-知识共谋的形式主义标记，它支持 FreeBSD 阵营的淡化指控；而真相可能既非“刻意回避”亦非“完全无意识”，而是文献检索盲区与形式主义权力行使的模糊叠加
  
**史料**：项目史观总纲第 5 章、第 15 章；Linux **epoll(7)** 手册页；Lemon BSDCon 2000 论文；Libenzi D. Improving (network) I/O performance. xmailserver.org/linux-patches/nio-improve.html. 2001-07-01 初稿，2002-10-30 更新 ［A］
  
**史观**：总纲第 5 条与第 15 条的综合——偶然性在形式主义化中被重构为必然性的归属判断
  
**辨析**：合图层的辩证综合是否构成“各打五十大板”的折衷主义，须审慎对待——综合不等于无立场，本节的立场是：衍生指控与独立辩护都是形式主义叙事，真相是模糊的传播与转化，这一立场本身亦须接受 0 信任原则的审视

### 95.3.7.4 LKML 2003.3.14 辩论的合图层补足——争议的不可调和性

  **要点**：LKML 2003.3.14 的 Lemon-Libenzi 直接对辩为合图层提供了更为充实的辩证素材。从偶然性视角审视，Libenzi 在辩论中提出的 “API are a matter of personal taste”（API 是个人品味问题）看似是相对主义的让步，实则是以个人品味为名拒绝承认 kqueue 对 epoll 的潜在影响——若 API 纯属个人品味，则不存在 “衍生” 或 “借鉴” 的问题，所有设计选择都是平行的个人偏好。但 Lemon 的回应揭示了这一立场的逻辑漏洞——个人品味无法解释术语沿用（level-triggered/edge-triggered 由 Lemon BSDCon 2000 首创）与时间线优先性（kqueue 2000.4 早于 /dev/epoll 2001.7 约 15 个月），这些客观事实超越了个人品味的范畴。从形式主义视角审视，LKML 辩论本身即是形式主义化的典型场域——双方都将实质的设计思想传播问题重构为可形式化判断的表层指标：Libenzi 用 “24590 flags”（夸张修辞）与 “99% of its users will use only 1%”（未经实证的统计声称）将 kqueue 的 filter 中心化定性为 “过度膨胀”，Lemon 用 “6 user-settable flags”（核心代码标志位数）与 “event framework”（事件框架定性）将 kqueue 定性为 “语义丰富”。二者的争论不是关于设计思想传播的实质辨析，而是关于如何形式化定性 kqueue 的修辞争夺。从权力-知识共谋视角审视，LKML 作为 Linux 内核的官方邮件列表，其话语场域本身即具有权力不对称性——Libenzi 作为 epoll 作者在 LKML 上是 “主场作战”，而 Lemon 作为 kqueue 作者在 LKML 上是 “客场发言”，这一权力不对称在 Libenzi 的 "quite a few kqueue users currently running on your favourite OS, are moving to Linux+epoll"（相当多的 kqueue 用户正在从你最喜欢的操作系统迁移到 Linux+epoll）这一市场选择论证中达到顶峰——市场份额本身被建构为设计优越性的证据，而 kqueue 的先发地位被市场选择所遮蔽。合图层须承认这一争议的不可调和性——Libenzi 的 composable 路线与 Lemon 的 filter 中心化路线在设计哲学上根本对立，二者不可通过技术辩论达成共识，因为分歧的根源不是技术事实而是设计价值观（简洁 vs 语义丰富、用户空间 vs 内核空间、composable vs filter）。和解路径不在于技术层面的胜负判定，而在于承认二者作为各自主体性呈现的不可替代性——epoll 的简洁与 kqueue 的语义丰富都是事件通知设计空间中的合法选择，而非非此即彼的零和博弈。项目史观总纲第 6 条 “和解优于斗争” 在此显现：历史的动力不是对抗，而是各主体性的呈现与和解；Libenzi 与 Lemon 的 LKML 对辩不应被书写为 Linux 与 BSD 的零和博弈，而应被理解为两个独立技术主体在事件通知这一共同问题域中的各自呈现
  
**史料**：项目史观总纲第 5 章第 5.1-5.3 节、第 15 章第 15.1-15.5 节、第 19 章第 19.3-19.5 节、总纲第 6 条；LKML 2003.3.14 Lemon-Libenzi 对辩邮件（marc.info 邮件 ID m = 104766084321908、m = 104767975212974、m = 104768094314029、m = 104768520518018、m = 104768636918775）；Libenzi “API are a matter of personal taste” 原文；Libenzi “24590 flags” “99% of its users will use only 1%” 原文；Lemon “6 user-settable flags” “event framework” "epoll is designed to only solve a limited subset of problems that kqueue does“ 原文；Libenzi ”quite a few kqueue users...are moving to Linux+epoll" 市场选择论证原文 ［A］
