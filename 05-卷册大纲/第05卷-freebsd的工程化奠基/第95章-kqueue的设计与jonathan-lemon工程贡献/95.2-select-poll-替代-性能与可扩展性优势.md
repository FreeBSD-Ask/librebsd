# 94.2 select/poll 替代——性能与可扩展性优势

## 94.2.1 select/poll 的性能瓶颈
  - 要点：**select(2)** 受 FD_SETSIZE 限制默认 1024，**poll(2)** 虽无此限但每次调用需遍历全部 fd 集合，O(N) 复杂度在 10K+ 并发连接下成为瓶颈，且内核需重复扫描用户态传入的 fd 数组
  - 史料：select(2)/poll(2) 手册页、Banga 1998 论文测量数据、Lemon BSDCon 2000 论文性能对比图 ［A］
  - 史观：总纲第 5 条——技术债务与代码考古，select/poll 的 1980s 设计在 2000 年代 Web 服务器场景下成为债务
  - 辨析：FD_SETSIZE 限制是否可通过内核 sysctl 调整，不同来源说法不一，需查 sys/select.h 与内核实现
  - 文献：Stevens《UNIX Network Programming》第 6 章；Banga USENIX 1998 ［B］
## 94.2.2 kqueue 的 O(1) 优势
  - 要点：kqueue 在内核维护就绪事件列表，**kevent(2)** 调用仅返回已就绪事件，复杂度从 O(N) 降至 O(1)，且支持水平触发 (LT) 与边沿触发 (ET) 两种模式，stateful 设计避免每次重新注册
  - 史料：kqueue(2) 手册页 EV_CLEAR 标志说明、Lemon BSDCon 2000 论文第 4 节性能数据 ［A］
  - 史观：总纲第 2 条——实践先于理论，stateful 设计源于实际服务器场景需求
  - 辨析：kqueue 是否真正 O(1) 在某些 filter(EVFILT_PROC) 下存在争议，需区分 hot path 与 cold path
  - 文献：Lemon BSDCon 2000；kqueue(2) 手册页 ［A］
## 94.2.3 可扩展性分析
  - 要点：kqueue 的可扩展性体现在三方面：(1) 横向可扩展到万级 fd；(2) filter 机制支持新增事件源 (VNODE/PROC/TIMER) 无需新系统调用；(3) 与 AIO 集成支持异步 IO 通知，为 nginx/lighttpd 等事件驱动服务器奠定基础
  - 史料：nginx 早期 commit 使用 kqueue、lighttpd 1.4.0 changelog、FreeBSD AIO 实现 ［A］
  - 史观：总纲第 9 条——简洁与复杂的辩证，filter 抽象简洁但扩展时需改内核
  - 辨析：nginx 作者 Igor Sysoev 选择 kqueue 而非 epoll 的初始动机，需查 nginx 早期邮件列表
  - 文献：Sysoev nginx 邮件列表归档；lighttpd 1.4.0 release notes ［A］
## 94.2.4 性能优势史料辨析
  - 要点：性能优势史料的争议点：(1) Lemon 论文的基准测试环境与对比对象是否公平；(2) Banga 1998 的 /dev/poll 数据是否被 Lemon 引用；(3) 不同操作系统在不同负载下的相对表现
  - 史料：Lemon BSDCon 2000 基准测试脚本 (已遗失，需查 BSDCon 存档)、Banga 1998 测试环境记录 ［A］
  - 史观：总纲第 4 条——0 信任原则，对作者自行设计的基准测试需独立复现验证
  - 辨析：Lemon 论文未公开测试脚本，性能数据的可复现性存疑，后续 Provos 2002 论文部分验证
