# 103.4.7 资源划分按三阶段推进先内部软资源进程表文件描述符kqueue与knotesSys

- 资源划分按三阶段推进：先内部软资源（进程表、文件描述符、kqueue 与 knotes、SysV IPC，大半完成），再伪设备等“软硬件”（PTY、klog 等），最后硬件设备拟采两阶段方案——先以类似 Linux udev 的机制连贯命名设备，再由管理员经访问模块决定实例可得哪些设备并配 DevFS；自认网络与终端是最难啃的部分，硬盘按主从节点分配已可行。对虚拟主机与集群计算两种场景，他承认无实测数据、仅属推测：前者实例长期常驻、重在按需实时调配资源，后者重在秒级启停即弃、实例整体迁移与可迁移文件系统，未来拟支持 PUFFS 用户态文件系统、NFS 根文件系统，并指出 DNS 难以应对亚秒级的地址轮换。 [存疑脚注] 双场景运行时差异系当事人自认的推测（原话自陈无硬性测量支撑），迁移与 PUFFS/NFS 支持属规划而非已实现（BSDTalk EP140，[592.50-741.02]，L1）
- Smith 以首席发布工程师身份描述流程全貌：决定发布后进入代码冻结，阻止开发者添入新功能而专注收尾，随后切出发布分支并做测试构建（自 beta 起），此间一切代码改动须经发布工程团队批准方可提交，由该队裁量何者为必须先行解决的拦路问题、何者留待未来版本；经候选版本测试合格方正式发布，同一团队同时操办 6.3 与 7.0 两个发布；版本号语义上，次版本号系列内竭力维持 ABI 与 API 不变，主版本号变更则一切约束解除，允许要求重编译的剧变与新子系统进场。（BSDTalk EP142，[106.80-241.68]，L1）
- 7.0 并无单一中心目标，主旋律是自 FreeBSD 5 起延续至今的 SMPNG 倡议进入性能阶段：内核已大体具备 SMP 能力，开发者转而剖析锁的落点与次序以求削减瓶颈；Kris Kennaway（转写误作 Chris Kenoway）的基准测试被用作定位与验证工具，部分基准较 Linux 领先约 15%，但 Smith 明确拒绝将其外推为全面优势，并举例基准互动的健康竞争——Kennaway 曾发现 Linux 侧异常行为、经提出后由对方修复。 [存疑脚注] 基准测试者人名系据上下文（基准与瓶颈分析）辨识为 Kris Kennaway，转写原文作 Chris Kenoway，待与其他史料核对（BSDTalk EP142，[414.06-664.64]，L1）
- 7.0 的两项悬置：ULE 调度器仅以毫厘之差未成默认，被喻为“稍晚了些的选择性手术”，7.1 大概率转正；DTrace 则因拟议中思科方面感兴趣的合同工作告吹而搁浅，未能进入 7.0，仍在与有意者接洽。支持矩阵上，ZFS 不向 6 系列回移而性能改进择要回移，开发者重心在 7；5 系列仅余安全团队短暂维护、不再出新版；Linux 兼容层默认仍对 2.4 内核，2.6 支持有进展但尚有缺陷与缺项、未达默认水准；7 的改进大体利于服务器，桌面用户须自行重编译内核换用 ULE 方得其利。（BSDTalk EP142，[467.00-721.20]，L1）
- bhyve 在 2013 年 2 月访谈时点的定位：受访者称之为 type 2 hypervisor，但强调类型区分正在失效——若仅于单用户模式启动 hypervisor 即为 type 1，具备可用用户态即为 type 2，纠缠分类已无意义；就 FreeBSD 而言，bhyve 萌芽于 8 系列（甚至 7），于 9 系列公开露面，2013 年 1 月 19 日进入 FreeBSD 10-CURRENT。（BSDTalk EP223，[75.54-103.32]，L1）
- 与 jails 的范式对照：jail 本质是“被赋予自省能力的超级 chroot”——与宿主共享单一内核，经 RC 脚本启动守护进程（无独立 init），区分自身进程与网络并提供独立 root 用户；hypervisor 则令每个客户机运行独立内核实例。jail 轻量但走向复杂：建立足以支撑多个 jail 的虚拟化网络栈（含交换功能）是极复杂的问题；受访者转述 Poul-Henning Kamp 的实验——以脚本连续启动 jail，至 64,000 个方止。（BSDTalk EP223，[201.34-281.22]，L1）
- Xen 对照与产业转向：NetBSD 长期支持 Xen dom0，受访者自述受东京一场演讲触动而自建 Xen——主流 Linux 发行版上安装失败，转投 NetBSD dom0，文档贫乏却极其稳定；但 Xen 属根本不同的内核与许可证体系，FreeBSD 在 Xen 阵营居二等地位（Amazon EC2 带来关注，Colin Percival 为 FreeBSD 在 EC2 上的可用性做了大量工作）。产业层面：Amazon 选 Xen 缘于旧硬件投资巨大、需纯软件虚拟化；微软正视虚拟化需求并积极投入 virtio 驱动；Red Hat 为 KVM 贡献 virtio 驱动——各家正从“复刻古老硬件”转向现代方法。 [存疑脚注] 促成其 Xen 尝试的东京演讲者（转写作 Christophe）与项目名（转写作 Malt）均待考。（BSDTalk EP223，[294.12-563.76]，L1）
- bhyve 的轻量与 legacy-free 架构：内核模块式 hypervisor，主模块粗算约 1300 行代码、磁盘上软件约 256K，轻量且可审计；完全放弃旧硬件支持，要求 Intel VT-x 与扩展页表 EPT（AMD 的同类 NPT 技术已存在，实现只差开发者资源）；依赖 VirtIO 虚拟网络与块设备驱动；不做 QEMU 式 BIOS 模拟，故彼时仅能 FreeBSD on FreeBSD；已可掩蔽宿主设备做 PCI 直通。其简洁正是以舍弃 legacy、把复杂度转移给新硬件换来的。（BSDTalk EP223，[362.16-495.56]，L1）
- 硬件门槛与入门路径：需 Nehalem 至 Ivy Bridge 的 Intel 处理器（Core i3/i5/i7 及 Pentium、Celeron、Xeon 变体），ark.intel.com 已补上 EPT 支持查询，亦可查 dmesg 中的 POPCNT 指令（恒与 EPT 同现）；三百美元级办公笔记本即可胜任（或缺 suspend/resume 等 FreeBSD 特性支持）；2013 年 1 月 20 日起的 FreeBSD 10-CURRENT snapshot 已含全部组件，镜像在 mirrors 的 snapshots 目录，配 Neel 的说明页与脚本——自动创建 8GB 磁盘镜像并引导进入标准 FreeBSD 安装流程；受访者本人早前的路线是把全部组件逐个经 ports 构建打包（在 9 可行、10 不行），以脚本贯穿建镜像、格式化 iSCSI target、装入所选发行版全程，文档化于其维护的 bhyve.org。 [存疑脚注] 转写将说明页与脚本作者记作 Neonat2、NeoScript，据上下文应为 bhyve 开发者 Neel Natu 及其脚本，待与 FreeBSD virtualization 邮件列表核对。（BSDTalk EP223，[572.36-776.62]，L1）
- 社区自举与生态现状：代码公开两年而未获 FreeBSD 官方身份，形成鸡生蛋困境——无正式名分则少人试用；进入 10-CURRENT 本身即是激励，需志愿者实际压测，且每个试用者都会发现开发者未虑及的问题，此乃 bootstrap 社区的常态。技术状态：bhyve 即 FreeBSD，可从 ZVOL 镜像引导客户机并以 ZFS 快照回滚，兼容 nanoBSD 式用户态精简；块设备 I/O 彼时为阻塞式、偏慢（实验性修复代码在测），网络问题较小，基准测试是社区最能贡献的方向；受访者预测年底前多数 FreeBSD 开发者将在 bhyve 上开发 FreeBSD——内核崩溃即关闭客户机重开或回快照；生态上 FreeBSD virtualization 邮件列表响应积极，freenode 的 #bhyve 频道由 Allan Jude 正式化，其经营的 CDN 已将真实流量导向 bhyve 压测，Alfred Perlstein 亦在实验，开发者来自印度与澳洲；受访者计划在 AsiaBSDCon 演示、发布 man pages 并办文档 hackathon。（BSDTalk EP223，[796.26-1300.24]，L1）
- Michael Dexter 的技术路径：1991 年读计算机科学时以 SunOS 与 Ultrix 入门真实系统；在密歇根州卡拉马祖求学拉丁语期间偶遇捐赠设立的 NeXT 实验室而接触 NextStep；1998 年前后在俄勒冈州波特兰身处 Red Hat 环境中使用 BSD 相关系统，经历 Red Hat 5.2 的 RPM、Red Hat 6 与 GNOME 测试版时代；2001 年任职 MandrakeSoft 内部 IS 团队，公司失利后迁居拉脱维亚；2002 年前后确立 BSD 主攻方向，恰逢 FreeBSD 5 带来 jls、jexec 等 jail 特性。（BSDTalk EP66，[56.68-254.04]，L1）
- 从 jails 的组织价值到 SysJail 的方案设计：受访者需要托管多个站点且拒绝与他人共享托管机，痛感软件安装散落文件系统、RPM 亦未能根治，因而看重 jail 将守护进程与宿主系统分离、开销几乎不变、得以整体删除重建的组织价值，并多年以磁盘镜像充当各 jail 的独立分区；SysJail 由此针对 FreeBSD jail 实现的短板而作——文件系统扁平化得以按守护进程或按用户切分虚拟系统，复用 Systrace 的内核级组件、自身全部实现于用户态而无需改内核，可在 Systrace 所到之处运行（NetBSD、OpenBSD、MirOS），提供虚拟终端以便 SSH 进入、以二进制安装构建完整系统；性能上其测试在一台 VIA 1GHz、512MB 内存的迷你主板上同时跑 64 个 jail、每个 sshd 约占 2MB，远低于 VMware 类方案每实例 64MB 的分配；另以用户态文件系统设想隔离各 jail 的 procfs 可见进程以补安全短板。（BSDTalk EP66，[271.24-740.94]，L1）
- 转向 OpenBSD 的动机与挫折：受访者认为 FreeBSD 5 系列不如其前的 4 系稳定，故障无 core dump、无征兆、存活时长不定，令其放弃；其眼中 OpenBSD 是血统上最纯正、守旧而创新的 BSD，却始终没有 jail——邮件列表的答复是其实现复杂、资源应集中于 OpenSSH 与整体安全，且标准答案常是“用 Systrace”；而 ports 中 Systrace profile 屈指可数，社区并未把 Systrace 的行为约束能力制度化为基线配置，SysJail 即以此引入基线 profile 并追加 Systrace 不具备的系统调用拦截。（BSDTalk EP66，[429.72-540.54]，L1）
- 拉脱维亚生态与延伸项目：受访者四年前抵拉脱维亚时当地并无开源产业、其技能被归入 Windows 管理员，遂活跃于本地社区，曾邀 MySQL 的 David Axmark 到里加；XFSscale 项目为 nnpfs（旧名 XFS）的文档工程，定位类似 FUSE 的用户态文件系统，设想跨平台 SSHFS 并充当 jail 专用 procfs；Kristaps 与大学合作波罗的海超算网格 Baltic Grid，并排定在米兰 EuroBSDCon 讲 XFSscale、在纽约市 BSD 大会讲 SysJail；BSD.LV 计划转向纯开源合同业务的商业面向，指欧洲 EU 资金只要懂申请便可得，而 DARPA 之类资金已对 OpenBSD 枯竭；又鼓动为拉脱维亚制造的 RouterBoard（现跑 Debian 的无线路由整机）移植 OpenBSD 这类真正的路由操作系统。（BSDTalk EP66，[1474.28-1743.16]，L1）
- 个人使用与 2006 年社区观察：受访者桌面用 Mac OS X（iBook），服务器用 OpenBSD；曾期待苹果以 FreeBSD 用户态与 Jordan Hubbard 的加入带来服务器与桌面同构的统一环境，但该愿景未至，且 Emmanuel Dreyfus 的 compat Darwin 等项目亟需维护；收尾时其判断苹果的开放程度恰以满足自身需要为限、Linux 渐趋平台期、BSD 阵营正经历震荡——尤其点出近日引起广泛关注的 Future of NetBSD 消息，为该事件的同时期社区感知留下口述记录。（BSDTalk EP66，[1743.16-2052.2]，L1）
- Bastille 作者以 FreeBSD Salt Stack 十年维护者与 Hubble 监控系统架构师（该系统监控全球数十万系统并服务于安全合规）的双重背景，将 Salt 的自动化原则与 Hubble 的安全概念合并为安全的轻量容器管理器；其自述“不知道如何在人人可见的开放环境之外构建软件”，模板文件改进、ZFS 支持与克隆功能等大量代码出自社区贡献而非其一人之手；项目现居犹他州的作者以观鸟与改装露营车旅行著称，讲座中并以 Raspberry Pi 4 实机演示。（YouTube EPIOUr7Is5FSU，[100.56-149.6]，L1）[订正：原引文“在人人可见的开放环境之外我不会构建软件”→“不知道如何在人人可见的开放环境之外构建软件”（转写为 I don't know how to build software not out in the open）；原“实机演示全部功能”→“实机演示”（转写仅示 update 与模板等数项演示）；原“零依赖的轻量容器管理器”→“安全的轻量容器管理器”（转写为 merge them into a lightweight secure container manager，零依赖系后文 package 段所言，见设计哲学条目）] [订正：引文与社区贡献之述出自结尾致谢段 [3316.1-3348.6]、Raspberry Pi 4 实机演示出自 [1582.3-1591.0]，均不在所引区间内，内容复核]
- 演讲者列举 Linux vserver、Solaris Zones、OpenVZ、LXC、systemd-nspawn、Docker 以至 Kubernetes 的容器谱系，强调 FreeBSD 早在 2000 年即交付 jails（距演讲时约 21 年），做容器的时间早于各竞争者；在其个人判断中 jails 是 FreeBSD 的杀手级特性——轻量级系统虚拟化在其他平台无可匹敌——这正是他选择以 jails 为基座构建 Bastille 的原因。（YouTube EPIOUr7Is5FSU，[296.24-391.3]，L1）[订正：原 [296.24-330.08]→[296.24-391.3]，容器谱系至 Kubernetes、“早于所有人”与“杀手级特性”诸段（342.0-391.3）原不在区间内，内容复核]
- 演讲以一手演示呈现 jails 的技术边界：jail 如单向镜子，容器外可见其内而容器内不见外部；容器只是宿主上多跑的几组进程（默认仅 syslogd 与 cron）；uname 从宿主内核读取数据因而无法用于判断容器内版本，须改用 freebsd-version；宿主 root 即容器 root，免密 console 建立在此之上；Bastille 默认削减攻击面——禁用 syslog 网络套接字、关闭 sendmail、为 cron 加入 60 秒抖动以免容器同时执行任务；网络方面提供克隆回环接口（适配云端单 IP 场景）、IP 别名与 VNET 桥接（近两年无需重编内核）三种方案。（YouTube EPIOUr7Is5FSU，[396.7-1991.2]，L1）[订正：原 [1642.16-1678.4]→[396.7-1991.2]，单向镜子（396.7-409.0）、网络三方案（748.9-942.1）、默认削减攻击面（1905.3-1928.2）与宿主 root／免密 console（1970.5-1991.2）诸段原不在区间内，内容复核]
