# 103.4.6 ports树在录制约一周前移除了为93101102等已生命周期终结版本准备的向后

- ports 树在录制约一周前移除了为 9.3、10.1、10.2 等已生命周期终结版本准备的向后兼容垫片，使此前被旧版本锁死的新 Xorg 与 Wayland 支持得以合入；配套 FreeBSD 11 新发布节奏：11.x 总支持期仍为五年，但 11.1 发布后 11.0 仅余三个月，敦促用户尽快升级；此前移植者的验证矩阵覆盖 9.3、10.1、10.2、10.3 与 11 共五个版本，如今仅需测试 10.3 与 11；包构建基线相应由最老支持版本 10.1 上移至 10.3，包得以使用 openat、linkat 等 *at 函数（open 已成 openat 的 POSIX 包装并为 Capsicum 所依赖），旧系统安装将因未定义符号立即报错，package.static 至多救回 pkg 命令本身，已装程序仍将损坏。（BSD Now EP178，[70.24-417.92]，L2）
- TrueOS 迁移 OpenRC：OpenRC 为依赖式 init 系统，出自 NetBSD 开发者 Roy Marples，被 Gentoo 与 Alpine Linux 采用，其可移植性与双条款 BSD 许可使其整合进 TrueOS 成为容易的决策；TrueOS 以 init.d 取代 rc.d、每服务可配 conf.d、引入 runlevel 与 rc update 命令并集成图形化服务管理器；核心收益是桌面与笔记本场景的快速启动（15 秒内到登录，此前约一分钟）与服务监控、崩溃标记；基本系统服务约九成已迁移，ports 中约一千个 RC.d 脚本计划年内完成转换，多数只需将 shebang 改为 openrc-run 并微调变量，OpenVPN、VirtualBox、nginx、Apache、PostgreSQL、MySQL 等高频服务已先行完成。（BSD Now EP178，[525.96-863.72]，L2）
- 沉默法则（Silence is Golden）：程序在没有令人惊讶、有趣或有用的信息时应当缄默，把用户的注意力当作珍贵资源；Unix 哲学被概括为小、简、透明、模块化、可移植与可扩展，沉默法则约束输出的经济性以保全管道组合——前一程序的输出即后一程序的输入；主持人的辩证补充是错误信息必须清晰且能从噪音中被挑出，ZFS 混合 vdev 的含混报错曾诱使用户盲目追加 -F 铸成大错，模态对话框则被比作索要注意力的小孩。（BSD Now EP178，[1464.44-1768.94]，L2）
- FreeBSD 评审将 traceroute 迁入 Capsicum 沙箱：进入沙箱后无法外发连接做 DNS 解析，引入 Casper 轻量服务框架，在入沙箱前创建会话、由其 system.dns 服务以受限方式代为解析主机名；实际补丁约五十行，DNS 路径仅三行改动（cap_gethostbyname 取代 gethostbyname）；主持人展望 Casper 文件系统服务可预注册文件清单并按批发放描述符，以解决 gzip 等批量文件工具难以沙箱化的困境。（BSD Now EP178，[3528.92-3735.26]，L2）

- 设计方法为抽取定义网络栈行为的全部全局变量装入容器超结构并多实例化；2002 年版为概念验证，FreeBSD 7 重实现引入一级间接寻址，使各网络模块拥有独立结构、内核可加载模块可在运行时扩展子系统而无需重编译全部网络 API。（BSDTalk EP130，[218.08-283.31]，L1）
- 工程目标之一是完整保留管理接口：用户态管理工具无需任何修改、重编译或链接库调整即可用于虚拟化内核，虚拟化内核自设计之初即可作为原生内核的即插即用替代；新增 vimage 前端工具负责虚拟实例的创建删除与管理，实例间默认隔离，借 FreeBSD 的 NetGraph 框架以任意拓扑互联。（BSDTalk EP130，[344.35-452.73]，L1）
- 轻量性数据：相比 VMware 等传统虚拟化，jail 与虚拟网络栈极其轻量，每实例内核内存足迹仅约百余 KB（IPv4-only 内核更小）；Zec 的笔记本可同时实例化约 500 个虚拟节点，各自运行 Quagga 的 RIP 与 RIPng 路由演示，关键在于应用程序共享代码段内存因而扩展性良好。（BSDTalk EP130，[462.94-539.73]，L1）[订正：原 相比 VMware、Xen 等传统虚拟化，2026-09-29 SenseAudio 重转核对]

- 性能开销：FreeBSD 4 时代回环以太网尺寸包吞吐仅降约 3-4%（发送接收两端各计一次开销），FreeBSD 7 上单处理器回环 TCP 开销约 1.5%；意外发现回环 ICMP 吞吐反高于原生栈数个百分点，当事人推测系变量符号在内存中聚集改善了 CPU 缓存效率并减少 TLB 抖动，但自承无科学解释。（BSDTalk EP130，[850.67-928.32]，L1）
- 生产使用与资助：FreeBSD 4.11 版实现据称被美国匿名 ISP 用于生产（仅传闻性证据），这正是 FreeBSD 7 重实现获 FreeBSD Foundation 与荷兰 NLnet Foundation 资助的最初推动；当前实现已证明可运行于多线程内核，区别于单线程的 FreeBSD 4.11；文档几乎空白，仅网站上有若干演示文稿。（BSDTalk EP130，[717.83-779.79]，L1）
- 入行经过：大学时新笔记本需要可用的无线局域网，FreeBSD 5 当时未就绪、NetBSD 与 OpenBSD 在该机器上亦不理想，恰逢 Matt Dillon 宣布 DragonFly 项目且缺少 CardBus（32 位 PCMCIA 扩展）支持，其首个贡献即把 FreeBSD 5 的 CardBus 支持回移到 DragonFly。（BSDTalk EP135，[101.77-137.10]，L1）
- pkgsrc 引入 DragonFly 的经过：先前以本地 override 方式修补 FreeBSD ports（复制到本地仓库改写、以 hack 绕过系统头文件与符号链接差异），随 DragonFly 与 FreeBSD 分歧扩大而难以为继；2005 年另一开发者完成 pkgsrc bootstrap 与关键组件，其尝试后将 DragonFly 本地改动并入 pkgsrc；Thomas Klausner 等因补件 flood 而授予其直接提交权；此后第三方应用适配多在 pkgsrc 完成，用户在 FreeBSD ports 与 pkgsrc 之间的取舍变得容易。（BSDTalk EP135，[142.22-247.27]，L1）
- NetBSD 电源管理工作：Jared McNeill 早先着手改进 ACPI 挂起/恢复（部分机器可用、许多笔记本失效、AMD64 完全不可用）；另一方向是让未使用设备自动断电（未启用的网络接口、声卡等）；NetBSD 设有专门分支（转写作 jmcnally-pm）以把电源管理支持推进更多驱动；其本人因笔记本需要而投入，并视电源管理为当前比 jail 更紧迫的工作。（BSDTalk EP135，[253.27-312.47]，L1） [订正：原“有专门邮件列表推动电源管理进入更多驱动”，2026-09-29 SenseAudio 重转核对]
- Google Summer of Code 的 pkgsrc 项目分两部分：一是重做批量构建框架——旧系统无法处理多 chroot 或分布式构建集群，新系统以轻松利用多机、动态加入与退出为设计目标；二是 pkgsrc 交叉编译，重点是 modular Xorg（沿 XFree86 老路则工作量巨大且与 DragonFly 需求重复维护），核心是让 pkgsrc 复用 NetBSD 基本系统的交叉编译工具链，使 Amiga、VAX 等慢架构免于本地构建大包；适用前提为单平台且目标基础设施相似（ELF），跨操作系统交叉编译仅为未测试设想。（BSDTalk EP135，[365.44-505.83]，L1）
- GPLv3 的两大问题（EuroBSDCon 2007 项目状态讨论议题）：基本系统层面，需定期更新的 GPL 组件是 groff 与 GCC，要害不在 GCC 本身而在 libgcc 与 libstdc++——二者长期带有允许链接的例外条款，GPLv3 未将例外延及反 tivoization 条款，使高度定制且不允许篡改的系统能否用 GCC 构建成疑；对策包括 OpenBSD 导入 PCC、为 groff（BSD 源码树中唯一主要 C++ 组件）寻求替代。包管理层面，pkgsrc 已有非开源许可标签框架（mk.conf 的 acceptable_licenses 变量控制构建），计划扩展至全部许可类别尤其是 GPLv3，令用户知情并自决；批量构建基础设施问题待解决，目前仅对升级到 GPLv3 的包加注释。（BSDTalk EP135，[509.55-721.07]，L1）
- DragonFly jail 与 FreeBSD jail 的分化：DragonFly 源自 FreeBSD 4 的 jail 代码，FreeBSD 5/6 期间核心未大改（主要是适配 Robert Watson 的新凭证框架）；DragonFly 近期提交关键补丁，支持每 jail 多 IP 地址乃至 jail 内 IPv6，jail 的一大主要问题基本消除；FreeBSD 尚缺此能力，其替代路径是重量级虚拟化而非修补 jail 代码。（BSDTalk EP135，[734.95-791.94]，L1）
- NetBSD 的 kauth 式 jail 设想：kauth 已把大部分安全决策抽象到单一位置、便于修改；在 NetBSD 实现 jail 需给进程结构与凭证增加字段，使 root 权限决策可依是否处于 jail 而调整；剩余难题是 localhost 地址翻译的复杂代码；虚拟化路径的优点是避免在 jail 代码中特判。应用兼容性问题：Samba 因 localhost 特殊处理需要本地补丁，syslog 等守护进程绑定全部地址的对外行为需如 FreeBSD 团队那样专门修改。（BSDTalk EP135，[797.41-886.94]，L1）
- 开发者自我定位与环境：自称对所工作的 BSD 大体持不可知态度，现用 NetBSD 只因在其笔记本上优于 DragonFly，欣赏 DragonFly 的许多想法，不排斥 OpenBSD 且可能提交补丁；开发环境以控制台与多个 xterm 为主，使用 ion 平铺窗口管理器、midnight commander 与 vi。（BSDTalk EP135，[320.47-353.67]，L1）
- Dzonsons 在瑞典皇家理工学院与拉脱维亚大学合作框架下主持 MULT 研究，主张大量应用场景只需要与宿主同构的 POSIX 环境而非完整内核虚拟化，故将系统定位为单内核上同时运行成千上万个可精细配置、互不可见的操作实例，与 Xen、QEMU 及即将出现的 DragonFly BSD vkernel 等运行整个内核的重量级方案划清界限；系统不使用 VT-x/AMD-V 等处理器虚拟化扩展，且可与 NetBSD 的 Xen 支持叠加组合（Xen 客户机内再跑 MULT 实例），仅触及内核上半部因而宣称平台无关。（BSDTalk EP140，[187.94-223.30]，L1）
- 对 FreeBSD jail 的核心批评是：jail 名副其实地“监禁”一组进程，防护在执行时于内核边界施加，外部可见 jail 内部而 jail 看不见外部；进程表在内核中仍是全局单份，跨 jail 不允许重复进程号，资源隔离只在功能性层面而非结构层面成立。MULT 的应对是把进程表、挂载表、SysV IPC、网络接口等内核全局结构逐一收集为实例私有结构（其称逻辑隔离），故各实例可运行完整 init 树、进程号可跨实例重复，ps 只见本实例进程而以 instps 工具旁观他者；自述已实测启动逾十万实例，计划月底发布面向大规模启停的开发版。（BSDTalk EP140，[231.42-341.00]，L1）
