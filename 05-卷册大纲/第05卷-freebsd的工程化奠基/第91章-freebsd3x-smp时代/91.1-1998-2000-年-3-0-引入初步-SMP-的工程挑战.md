# 90.1 1998-2000 年 3.0 引入初步 SMP 的工程挑战

## 90.1.1 SMP 引入的工程语境
  - 要点：1996-1998 年多 CPU 服务器在 ISP 与企业普及，FreeBSD 2.x 的 Giant Lock 在 4 CPU 以上扩展性极差，迫使 3.0 引入初步 SMP；同期 Linux 2.0(1996) 已有粗粒度 SMP，Solaris 2.6(1997) 已有细粒度锁
  - 史料：freebsd-smp 邮件列表 1996-1998 年讨论、3.0 SMP 设计文档、BSDCon 1998 SMP 演讲 ［A］；freebsd.db 查询 L1.1.1 显示：freebsd-src 仓库年度 commit 量 1996 年 7,948 条（占 23 仓库总量 27.18%）、1997 年 11,046 条（24.49%）、1998 年 10,035 条（25.02%）、1999 年 13,083 条（22.45%）、2000 年 15,347 条（20.06%），3.x 时期（1998-2000）commit 量持续增长反映 SMP 引入带来的工程活跃度上升
  - 史观：总纲第 7 条——硬件与软件辩证，多 CPU 硬件普及倒逼 FreeBSD 引入 SMP
  - 辨析：3.0 SMP 的引入是被动响应还是主动规划存在争议，需查 Core Team 1996 年路线图；经邮件列表库验证通过（fact-check 2026-08-14），1998-10-25 Brett Glass《Re: Where's the 3.0 press release?》（freebsd-advocacy，Message-ID `<4.1.19981025025521.066b7ec0@127.0.0.1>`）佐证 FreeBSD 3.0 已于 1998 年 10 月发布（与官方 1998-10-16 一致），freebsd-announce 1998 年归档未直接命中 3.0 公告原文（归档不完整）；【0 信任原则·commit 量不等于质量】L1.1.1 的 commit 量增长可能包含 SVN-to-Git 迁移引入的日期偏差与 cvs2svn 转换噪声，且 commit 量上升不必然等同于 SMP 工程质量提升，须结合 commit message 主题词与文件路径交叉验证

## 90.1.2 3.0 的 SMP 实现
  - 要点：FreeBSD 3.0(1998.10) 引入初步 SMP，采用单一 Giant Lock 但允许中断在任意 CPU 处理，IPI(处理器间中断) 机制用于 CPU 间通信；SMP 支持通过 SMP 内核选项启用，默认 UP 内核仍可用
  - 史料：SVN 仓库 sys/i386/i386/ 模块 SMP commit、3.0 SMP 配置文档、freebsd-smp 邮件列表；freebsd.db freebsd-src 仓库 tags 表 release/3.0.0 的 tagger_date = 1999-01-21T00:55:32Z（target_commit_hash = 76b5366091f76c9bc73570149ef5055648fc2c39），与官方公告的 1998.10.16 发布日期存在时差，按 0 信任原则推断 tagger_date 反映 2020 年 SVN-to-Git 迁移期 tag 重打时间而非原始 release tag 时间，采信官方公告 1998.10.16 ［A］
  - 史观：总纲第 2 条——实践先于理论，3.0 SMP 是渐进式实践而非理论最优设计
  - 辨析：3.0 SMP 是否 “真正” 支持多 CPU 存在争议，Giant Lock 下同时刻仅一 CPU 在内核态；bsd_commits.db 中 3.0 tagger_date(1999-01-21) 与 4.0 tagger_date(2000-03-20)、5.0 tagger_date(2003-01-16) 间隔模式不符合同一迁移规则下应有的 “约 1 年/3 年间隔” 规律，进一步印证 3.0 tag 在迁移期被重打；【0 信任原则·SVN-to-Git 迁移】L2.2.1.sys_kern 数据基于 2020 年 SVN-to-Git 迁移后的仓库，迁移过程中转换脚本可能引入日期偏差或作者归属错误，sys/kern 路径匹配 sys/kern% 可能漏掉重命名后的文件，须与 SVN 时代邮件列表存档交叉验证；bsd_commits.db 查询 L2.3.1.smp（SMP 特性引入周期）在已读取的中观模式挖掘报告中未找到对应数据段落，SMP 特性的 commit 级引入时间线存疑，待后续直接查询数据库补充

## 90.1.3 初步 SMP 的局限
  - 要点：3.0 SMP 的 Giant Lock 导致内核态串行化，4 CPU 性能仅比 1 CPU 提升约 1.5-2 倍，远低于线性扩展；用户态多线程可受益但内核密集型工作负载 (如网络栈) 扩展性差
  - 史料：3.0 SMP 性能基准测试、freebsd-smp 邮件列表性能报告、BSDCon 1999 SMP 性能分析 ［A］
  - 史观：总纲第 6 条——技术路线分化，Giant Lock 路线与 Solaris 细粒度锁路线分化
  - 辨析：3.0 SMP 性能数据在不同负载下差异巨大，需对照具体基准测试
  - 文献：3.0 SMP 性能报告；BSDCon 1999 论文；Solaris SMP 性能白皮书 ［B］
## 90.1.4 工程挑战的史料辨析
  - 要点：3.0 SMP 的工程挑战史料保存于 freebsd-smp 邮件列表与 SVN commit log，但 Giant Lock 拆分的具体决策过程缺乏系统性文档
  - 史料：freebsd-smp 邮件列表 1996-1998 年归档、SVN commit log、Core Team 会议纪要 ［A］；freebsd.db 数据库交叉印证——统计结论 C-03 freebsd-src 仓库总 commit 数 444,203 条作为 3.x SMP 时期（1998-2000）的累计背景；统计结论 C-29 freebsd-src ARIMA(5,0,5) 模型 AIC = 107.39（`statsmodels.tsa.arima.model.ARIMA` 自回归阶数 p = 5、差分阶数 d = 0、移动平均阶数 q = 5），反映 freebsd-src 月度 commit 时序存在显著自回归与移动平均结构，即历史 commit 量对当期 commit 量有可量化的预测能力；统计结论 C-33 freebsd-src 预测精度 MAPE = 24.56% RMSE = 456.55 coverage = 94.74%，MAPE < 30% 属可接受预测精度区间，coverage 94.74% 接近 95% 名义覆盖率反映模型校准良好；Python 脚本 `script/phase3_timeseries.py` Task 14（ARIMA 拟合）与 Task 15（MAPE/RMSE 自实现），查询日期 2026-07-27 ［B］
  - 史观：总纲第 17 条——软件工程，SMP 工程挑战的史料保存依赖邮件列表归档；统计结论印证——C-29 ARIMA(5,0,5) 与 C-33 MAPE = 24.56% 反映 freebsd-src commit 时序的可预测性，与项目史观总纲第 5 条 “没有必然性，只有偶然性” 形成张力：ARIMA 模型的统计可预测性不等于工程演进的必然性，SMP 引入的具体决策仍属偶然性事件，统计模型仅刻画 commit 量的时序结构而非工程因果
  - 辨析：部分 SMP 设计决策的归属存在争议，需查 commit log 与邮件交叉验证；**统计局限性标注**——统计显著 ≠ 实际显著，C-29 ARIMA(5,0,5) AIC = 107.39 仅反映模型对历史数据的拟合优度，不等于模型对未来 commit 量的预测能力；AIC 为相对指标，须与其他 ARIMA(p, d, q) 参数组合的 AIC 比较解读，单一 AIC 数值无绝对意义；C-33 MAPE = 24.56% 基于 freebsd-src 全周期（1993-2026）月度数据计算，非 3.x SMP 时期（1998-2000）单段精度，跨时期引用时须注意；RMSE = 456.55 与 commit 量纲相关，不可直接与其他仓库 RMSE 横比；coverage = 94.74% 接近 95% 名义覆盖率但存在抽样波动；0 信任原则适用——ARIMA 模型假设时序平稳性或可差分平稳化，freebsd-src commit 时序存在变点（C-12 1999-08）可能违反模型假设，模型参数解释须谨慎；多重比较风险——本卷 16 章跨章引用 C-03、C-29、C-33 时存在多重比较风险
