# 103.2 ipfw vs IPF vs PF 之争——三者的设计哲学差异

## 103.2.1 三者的设计哲学差异

**要点**：ipfw（FreeBSD 原生，1994，Ugen J.S. Antsilevich 设计〔设计者归属待一手 commit 核〕）采用规则序号 + 状态表设计；IPFilter（Darren Reed（达伦·里德），1995）采用 NAT + 状态保持设计；PF（OpenBSD，2001）采用规则集优化（skip steps）+ALTQ 集成设计；三者哲学各异，ipfw 重简洁、IPF 重跨平台、PF 重规则优化

  ipfw、IPFilter 与 PF 设计哲学对照：

  | 特性 | ipfw | IPFilter | PF |
| -- | -- | ------ |--|
| 引入年份 | 1994 | 1995 | 2001 |
| 设计者 | Ugen J.S. Antsilevich | Darren Reed | Daniel Hartmeier（丹尼尔·哈特迈尔） |
| 起源项目 | FreeBSD | 跨平台 | OpenBSD |
| 规则模型 | 规则序号 + 状态表 | NAT + 状态保持 | 规则集优化（skip steps） |
| 流量整形 | dummynet | —— | ALTQ 集成 |
| 许可证 | BSD | 争议（2001 年致 OpenBSD 移除，Darren Reed 后重授权双许可） | ISC/BSD |
| FreeBSD 状态 | 保留（原生） | 保留至今（5.3 引入 PF；IPFilter 移除系 OpenBSD 2001 年事件） | 5.3 引入 |

**史料**：**ipfw(8)**、**ipf(5)**、**pf.conf(5)** 手册页 ［A］

**史观**：总纲第 25 条——逻辑是形式主义而非世界本身的结构：三者设计哲学反映对防火墙这一形式的不同建构取舍

**辨析**：三者优劣，需查基准测试；设计哲学差异是否决定性能差异

**文献**：作者不详. ipfw(8)/ipf(5)/pf.conf(5) 手册页[Z]. 年份不详 ［A］

- pf 的跨平台扩散由演讲者概述：pf 为 BSD 许可的状态化包过滤器，由 OpenBSD 开发，FreeBSD 自 5.3 版起引入，此后亦移植到 NetBSD、现代 macOS、DragonFly BSD 与 QNX 等系统；现代 macOS 机器默认即带 pf 防火墙。（YouTube EPN-7xZB0afyA，[957.68-990.32]，L2）

- ipfw 的声明式配置体系与审计实操由演讲者完整演示：rc.conf 变量（firewall_enable、firewall_script、firewall_type、firewall_trusted 等）驱动 open、closed、client、workstation 等预设规则集，workstation 模式可声明式放行服务端口并限定信任网段；自定义脚本经 chmod 加 sysrc 注册后以 service ipfw restart 重载；ipfw show 可显示每条规则的命中计数，ipfw0 伪设备配合 tcpdump 用于排错，并对启用默认规则集可能锁死远程管理给出警告。审计侧以 praudit 与 auditreduce 处理 /var/audit 下的二进制日志，类别（认证授权、登录登出、文件写入、程序执行等）映射到系统调用，audit_pipe 伪设备提供实时事件流且可输出 XML，auditd 按定义应更好地支持 jails 但实际支持不足，惟可透视 jail 内部活动。（YouTube EPN-7xZB0afyA，[285.64-357.28]，L1）

**辨析**：

- 三防火墙应否裁并之争中，Adrian Chadd 给出与“合并即专注”主流论相反的证词：多防火墙并存迫使内核维持 netpfil 抽象层，“让这些家伙保持诚实”（2174.62-2178.62），用户态 IPFW 正是借该抽象与 netmap 得以实现；且合并以集中人力为前提的条件并不成立——项目本无足够活跃的防火墙开发者，VIMAGE 等并发需求亦使单一路线未必更低成本。此证词可与 PF 移植史的文献记载互校。（BSD Now EP101，[2153.58-2335.46]，L1）
- 图形栈跨项目移植呈现两条互不兼容的路线：DragonFly 引入 Linux 兼容层承接 DRI 代码从而快速跟进新硬件，FreeBSD 则将 DRI 代码 BSD 化以深度融入内核；前者更新因此难以回流后者，Adrian Chadd 明言 FreeBSD 追平新图形硬件的前提是先建成更完整的 Linux 兼容层（OFED 更新正在进行中）——路线分歧成为后续演化路径依赖的直接来源。（BSD Now EP101，[2864.64-2910.02]，L1）
