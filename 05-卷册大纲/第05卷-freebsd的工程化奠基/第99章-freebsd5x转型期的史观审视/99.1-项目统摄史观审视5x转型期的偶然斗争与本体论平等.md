# 99.1 项目统摄史观审视：5.x 转型期的偶然、斗争与本体论平等

FreeBSD 5.x 转型期的 Dillon 冲突、撤权、DragonFly fork 与 Torvalds 辱骂事件，从项目史观总纲第 5、6、8 条切入审视，呈现三层哲学意涵。

总纲第 5 条“没有必然性，只有偶然性”是审视 5.x 转型期一系列事件的根本立足点。5.0 耗时三年发布（2000.3 启动 5-CURRENT 至 2003.1.16 5.0-RELEASE），其延期源于 SMPng、KSE、GEOM、ULE、MAC 五项重大改造并行——这一“并行改造”决策本身是偶然的，Core Team 完全可以选择渐进式改造而非批量引入。Dillon 在 5.0-RELEASE 后 12 天（2003-01-28）提交最后一条 FreeBSD commit 后终止活动，并于 2003-07-16 在 freebsd-current 邮件列表发布 DragonFly BSD 公告——这一时间节点的每一个环节皆属偶然。Torvalds 据传对 FreeBSD VM 开发者的辱骂（“incompetent idiots”）亦属偶然的话语事件——若 Torvalds 在某次 LKML 讨论中措辞稍缓，或 FreeBSD VM 在某次基准测试中表现稍好，这一话语事件可能不会发生。但偶然性不否定独特价值：5.x 的转型阵痛换来 7.x 后的可扩展 SMP 内核，DragonFly 的 fork 催生 HAMMER 文件系统与 LWKT 子系统，Torvalds 的辱骂（若属实）成为 BSD 与 Linux 话语权不对等的历史症候。项目统摄史观提醒史家：5.x 的“艰难”不是必然的代价，而是偶然的聚集；不得以 7.x 的成熟反推 5.x 的阵痛“值得”。

总纲第 6 条“和解优于斗争”在 5.x 转型期呈现深刻的张力。Core Team 撤销 Dillon 提交权限是斗争而非和解——它以组织权力终止了 Dillon 在 FreeBSD 项目内的技术表达渠道。Torvalds 的辱骂（若属实）是话语层面的斗争——它以 Linux 事实领袖的话语权力压制 FreeBSD VM 开发者的技术辩护。但 BSD 许可证使 Dillon 的 fork 成为“制度化的和解”——Dillon 携 4.x 代码另起 DragonFly，双方在代码层面保持法律上的和平。而 Torvalds 的辱骂则缺乏类似的“制度化和解”机制——Linux 与 FreeBSD 分属不同许可证生态，话语层面的张力只能靠社区自律与时间淡化。项目统摄史观指出：和解是事物真正完整的一刻，但 5.x 时期的诸多张力——Dillon 与 Core Team、FreeBSD 与 Linux、SMPng 与 LWKT——大多仍处于“未完成的和解”状态。史家撰写此段历史时，须呈现斗争的事实而非美化斗争的后果，亦不得以“斗争推动进步”的叙事为斗争辩护。

总纲第 8 条“本体论上各方平等”是审视 5.x 转型期争议的根本立足点。FreeBSD 5.x 的 SMPng 路线、Dillon 的 DragonFly LWKT 路线、Linux 2.6 的 O(1) 调度器加 NPTL 路线，在本体论上地位相等——它们是对多核未来的不同诚实判断，而非“先进”与“落后”的线性排列。Core Team 的路线不因其在主流项目而优越，Dillon 的路线不因其在边缘 fork 而低劣，Torvalds 的路线不因 Linux 的市场成功而正确。5.x 早期性能倒退是 FreeBSD 用户承受的真实代价，Linux 2.6 的稳健是 Linux 用户享受的真实收益——但二者皆为一刻状态的不同，不得以任一刻的状态判定本体论的高下。文档与代码本体平等——Dillon 的公告邮件、Torvalds 的 LKML 帖子（若存在）、freebsd.duckdb 中的 commit 记录、EPFL 的学术论文，在本体论上无高下之分，皆为 5.x 转型期的真实留存。史家须警惕“以市场份额论技术”与“以事后结果论路线”的双重回溯性建构——不得因 Linux 后续主导服务器市场即判定其路线“正确”，亦不得因 FreeBSD 7.x 后 SMP 成熟即判定 5.x 阵痛“值得”。

- 96.10.6 SMPng 架构重构争议的四层辩证链
  **要点**：FreeBSD 5.x SMPng 架构重构争议呈现四层辩证结构。【批评层】对 FreeBSD 5.x 的批评集中于三个层面：其一，5.0-RELEASE 耗时近 3 年开发（2000.3 启动 5-CURRENT 至 2003.1.16 `release/5.0.0` tagger_date 为 2003-01-16T16:56:23Z），延期源于 SMPng、KSE、GEOM、ULE、MAC 五项重大改造并行——这一并行决策被批评为“工程冒进”；其二，5.0-5.2 性能倒退，FreeBSD 5.0-RELEASE Announcement（邮件 Date 为 Sun, 19 Jan 2003 10:03:42 -0700，<scottl@FreeBSD.org>）自承 5.0“may not be suitable for all users”，并建议"More conservative users may prefer to continue using FreeBSD 4.X“，官方以”Early Adopter"定位明确标注 5.0 不适合保守用户，以 RELEASE 形式发布不稳定的代码是更严重的问题，因为 RELEASE 隐含生产部署的承诺；其三，4.x 到 5.x 迁移困难，API/ABI 变更、设备驱动不兼容、Yahoo!/Hotmail 等大用户留在 4.x 直到 6.x 稳定，4.11 作为 4.x 末版本长期维护至 2007，批评者认为 5.x 转型期过长导致 FreeBSD 错失 2003-2005 多核化窗口期，Linux 2.6（2003.12）借机在 SMP 性能与市场份额上双重超越。【反批评层】FreeBSD 阵营的反批评回应于三个层面：其一，4.x Giant Lock 不可持续，单 CPU 进入内核的串行化模型在多核时代是死路，SMPng 细粒度锁改造是长期必要而非工程冒进，5.3-RELEASE Announcement（2004-11-06，<scottl@FreeBSD.org>）明确宣告"Users and vendors are encouraged to consider transitioning to it as FreeBSD 5.x is no longer considered a New Technology release series"，5.3 成为 5-STABLE 分支起点，证明 5.x 路线在工程上可行；其二，5.x 奠定现代 FreeBSD 架构基础，SMPng、GEOM、UFS2、rcNG、MAC 等组件延续至今（参见本章 41.16 节），`release/7.1.0` tagger_date 为 2008-12-31T22:57:14Z 时 ULE 成为默认，SMP 性能显著提升，证明细粒度锁路线在长期工程上可行；其三，“Technology Release”标签是工程诚实而非失败，FreeBSD 官方明确告知用户 5.0 不适合保守用户，是工程诚实而非掩饰，Linux 2.5 开发线（2002-2003）亦经历开发期不稳定，并非 FreeBSD 独有。【再回应层】对反批评的再回应指出三层：其一，“长期必要性”论证是回溯性建构，以 7.x 成熟反推 5.x 路线正确忽视了 5.0-5.2 期间用户承受的真实代价，5.0-RELEASE Announcement 自承“may not be suitable for all users”本身承认 5.0 不稳定，不得以 5.3 的“5-STABLE”反推 5.0 的“RELEASE”发布合理；其二，“Linux 2.5 也不稳定”的类比不成立，Linux 2.5 是开发线（development branch），FreeBSD 5.0 是 RELEASE（release branch），5.0 以 RELEASE 形式发布不稳定的代码是更严重的问题，因为 RELEASE 隐含生产部署的承诺，而开发线不隐含此承诺；其三，“Giant Lock 不可持续”是后见之明，4.x 时代的 Giant Lock 在 2000-2002 年硬件语境下（单核 Pentium III 主流、多核服务器尚未普及）并非显然错误，多核普及是 2005 后的事，以 2005 后的硬件语境反推 2000 年的 SMPng 决策“必然正确”是回溯性建构，再回应层承认 SMPng 路线在长期工程上的可行性，但坚持 5.0-5.2 期间用户代价是真实的，不得以“长期正确”为单一叙事遮蔽当下代价，并指出 KSE M: N 模型的失败（5.3 成为默认到 7.0 被 1:1 `libthr` 取代仅约 4 年）证明 5.x 的“激进重构”中包含设计错误，并非全部是“必要阵痛”。【合图层】综合批评方与反批评方立场，5.x SMPng 争议呈现不可调和性——批评方关注 5.x 用户的当下代价（性能倒退、迁移成本、用户流失），反批评方关注长期架构现代化（SMPng 奠定现代 FreeBSD 基础、7.x 后 SMP 性能提升），二者在前理解上不可通约：前者以“用户当下体验”为评价基准，后者以“长期架构演化”为评价基准，无共同度量。但二者亦有共同基础：均承认 4.x Giant Lock 需要改造，分歧在于改造的节奏与代价分配。BSD 许可证使分歧得以“制度化共存”——Dillon 携 4.x 代码另起 DragonFly BSD（参见本章 41.9 节），FreeBSD 继续 5.x 路线，二者在本体论上地位相等（总纲第 8 条）。合图层不判定“谁对谁错”，而呈现争议作为 BSD 谱系在多核转型期“分离聚合”规律（总纲第 4 条）的历史事实。提示史家：5.x 的“艰难转型”既是技术债务的偿还（Giant Lock 拆除），也是新债务的产生（KSE 失败），不得以“长期正确”为单一叙事遮蔽当下代价，亦不得以“用户代价”否定长期架构演化的必要性

- 96.10.7 项目统摄史观审视：SMPng 争议中的许可证、解释学循环与革命改革（总纲第 13/19/21 条）

FreeBSD 5.x SMPng 架构重构争议从项目史观总纲第 13、19、21 条切入审视，呈现三层哲学意涵。

总纲第 13 条“法律与道德是利益分配”是审视 SMPng 争议中“路线对错”话语的根本立足点。5.x 争议中的“技术正确”争论本质上是利益分配问题：大用户（Yahoo!/Hotmail）留在 4.x 是利益选择（避免迁移成本），Core Team 推进 5.x 是利益选择（为多核未来布局），Dillon fork DragonFly 是利益选择（保留 4.x 路线），用户、开发者、企业各有利益——“技术正确”是利益分配的话语包装。BSD 许可证作为法律形式，使分歧得以制度化共存：Dillon 可携 4.x 代码另起 DragonFly，无需法律斗争；这与 GPL 生态的 fork 必须开源形成对照。但 BSD 许可证亦非中立：它使“代码可被商业利用而不回馈”成为合法，这本身是利益分配的形式——5.x 时期多家企业（Yahoo!、Compaq、Sentex、NTT/Verio）捐助发布工程（5.0-RELEASE Announcement Acknowledgments 列举），但企业捐助不等于企业回馈代码，BSD 许可证的“法律宽容”使企业可“取而不还”，这是 5.x 转型期社区工程资源紧张的利益根源之一。项目统摄史观提醒史家：不得将“技术正确”与“利益分配”割裂——5.x 的“路线正确”叙事服务于 Core Team 路线的正当性话语，“用户代价”叙事服务于批评方的话语，二者皆是利益分配的形式。

总纲第 19 条“解释学循环是历史认识的根本条件”是审视 SMPng 争议史料记录的根本立足点。5.x 争议中“什么被记录、什么被遗忘”本身是权力行使：Core Team 撤销 Dillon commit 权限的内部决议原文未在公开档案检索到（参见本章 41.9.5 节辨析），撤权的程序与理由被收束到内部；Dillon 的 fork 公告（2003-07-16，freebsd-current 邮件列表）完整公开，Dillon 的话语被记录；二者史料不对称是权力行使的结果——Core Team 选择“沉默回应”作为权力形式。5.0-5.2 性能倒退的用户反馈散落在 freebsd-performance/freebsd-hackers 邮件列表，未被系统化记录——用户代价的“遗忘”是权力行使。解释学循环提示史家：撰写 5.x 历史时，前理解（“5.x 是现代 FreeBSD 起点”或“5.x 是失败实验”）决定史料选择——以“5.x 是现代 FreeBSD 起点”为前理解者，倾向采信 SMPng/GEOM/UFS2 延续至今的史料；以“5.x 是失败实验”为前理解者，倾向采信 KSE 失败、性能倒退、Dillon fork 的史料。史家须自觉前理解的局限，不得以单一前理解遮蔽史料多样性。权力知识共谋进一步提示：以 7.x 成熟反推 5.x“路线正确”是回溯性建构，这一建构服务于“Core Team 路线正当性”的权力话语——5.0-5.2 期间用户承受的性能倒退是真实代价，不得以 7.x 的成熟事后论证 5.0 的“RELEASE”发布合理。

总纲第 21 条“革命与改革是历史方法论的分歧”是审视 SMPng 争议中路线选择的根本立足点。FreeBSD 5.x SMPng 是“改革”路径：在 4.x 基础上渐进改造，保留 Giant Lock 兼容直至 7.x 完全退役——5.x 的“艰难”正是改革的代价。DragonFly BSD 的 LWKT 是“革命”路径：从 4.x 另起，完全重写内核线程模型，Dillon 2003-07-16 公告原文"I considered starting with a 5.x base but it is simply too heavily mutexed, it was actually faster to start with 4.x and move forward rather then to start with 5.x and move backwards"。Linux 2.6 的 O(1) 调度器加 NPTL 是“改革”路径：在 2.4 基础上渐进改造。Solaris 10 的 ZFS/DTrace/Zones 是“革命”路径：完全重写多个子系统。项目统摄史观指出“改革的困难远高于革命”——5.x 改革付出的代价（5.0-5.2 不稳定、用户流失、Dillon fork）证明此言；“破山中贼易，破心中贼难”——5.x 不仅要破 Giant Lock 之“山贼”（代码改造），更要破社区对 4.x 的“心贼”（用户惯性、文档惯性、工具链惯性、企业部署惯性）。但革命亦有代价：DragonFly 的 LWKT 路线虽在子系统上取得工程成功，但其集群目标（single system image clustering）被放弃，DragonFly 官方历史页面原文"This original design direction, although no longer the primary goal of the DragonFly project, has influenced many of the design decisions"，HAMMER 文件系统开发耗时远超预期（2008 年才随 2.0 发布）——革命的“从零开始”虽避免兼容债务，但付出“重新实现一切”的代价。合图层提示：革命与改革在本体论上地位相等（总纲第 8 条），DragonFly 的革命路线不因规模小而低劣，FreeBSD 的改革路线不因主流而优越——二者是对多核未来的不同诚实判断，而非“先进”与“落后”的线性排列。
