# 115.9 外部批评与反对者——LWN 编辑 Jonathan Corbet 2007 年“On DTrace envy”勾勒 Linux 社区话语框架

## 115.9.1 Corbet 的“DTrace envy”话语框架

**要点**：LWN.net 编辑 Jonathan Corbet 于 2007 年 8 月 7 日发表《On DTrace envy》（lwn.net/Articles/244536/），勾勒了 Linux 社区面对 DTrace 时的复杂话语框架：“DTrace 支持者常说 SystemTap 不过是 DTrace 的劣质仿制品，SystemTap 支持者则反驳它是独立开发、自有其价值”；Corbet 分析了 Linux 追踪领域的现状——kprobes、SystemTap 等工具在可用性和安全性上与 DTrace 存在差距，但 CDDL 许可证使 DTrace 无法进入 Linux 主线；该文奠定了此后十年 Linux 社区讨论 DTrace 时的“羡慕但不愿承认”的话语基调

**史料**：Jonathan Corbet 2007-08-07《On DTrace envy》原文（lwn.net/Articles/244536/）；LWN.net DTrace/SystemTap/eBPF 相关报道时间线（2005-2020 年） ［C］

**史观**：总纲第 23 条——社区治理：Corbet 的文章是技术新闻话语塑造社区认知的经典案例——“DTrace envy”这一短语精准捕捉了 Linux 社区面对 DTrace 时的复杂情感（羡慕技术优势 + 排斥因许可证 + 维护 NIH 自尊），这一框架影响了此后多年对 DTrace/Linux 追踪问题的讨论方式

**辨析**：Corbet 作为 LWN 编辑，其立场相对平衡——他既承认 DTrace 的技术优势，也理解 Linux 社区的许可证立场和发展独立工具的必要性；“envy”一词在文中不是贬义，而是对社区心理的准确描述；该文发表于 eBPF 诞生之前（2007 年 vs 2014 年），彼时 SystemTap 是 Linux 追踪的主要希望

**文献**：Corbet, J. (2007-08-07). On DTrace envy. LWN.net. lwn.net/Articles/244536/; LWN.net. Tracing coverage archive. lwn.net［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

## 115.9.2 SystemTap 与 CDDL 批评

**要点**：SystemTap 由 Red Hat 于 2005 年发起，源自 IBM dprobes 技术，目标是为 Linux 提供类似 DTrace 的动态追踪能力；SystemTap 的设计与 DTrace 不同：它通过将脚本编译为内核模块并加载来实现追踪，而非使用内核内置虚拟机；SystemTap 在早期版本中存在稳定性问题——编写不当的 SystemTap 脚本可能导致内核崩溃，这与 DTrace 的安全模型形成鲜明对比；SystemTap 社区和 Linux 内核开发者常以“GPL 兼容性”和“我们自己能做得更好”为由解释为何不移植 DTrace；SystemTap 从未获得 DTrace 那样的行业广泛采用，但在 Red Hat Enterprise Linux 生态中有一定使用

**史料**：SystemTap 项目文档（sourceware.org/systemtap/）；LWN.net 2005-2010 年 SystemTap 报道；Corbet 2007 文章中关于 SystemTap 的讨论；Red Hat SystemTap 官方文档 ［B］

**史观**：总纲第 22 条——开源运动：SystemTap 的故事是开源生态中“NIH 综合征”（Not Invented Here）与许可证政治交织的案例——Linux 社区选择独立开发 SystemTap 而非移植 DTrace，既是因为 CDDL-GPL 不兼容的法律约束，也因为社区对控制核心技术的自主追求；最终 eBPF 的成功证明了独立路线也能达到世界级水平，但 SystemTap 本身未能成为最终答案

**辨析**：将 SystemTap 简单描述为“DTrace 的劣质仿制品”是不公平的——SystemTap 有自己的设计哲学和技术特色（如更丰富的用户态分析能力），且其开发早于 DTrace 在 Linux 上有可行移植方案的时间；但 SystemTap 早期版本的稳定性问题确实严重，这也是 Gregg 等 DTrace 支持者对其持批评态度的原因

**文献**：SystemTap Project. sourceware.org/systemtap/; LWN.net SystemTap coverage (2005-2015); Corbet, J. (2007). On DTrace envy［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

## 115.9.3 Oracle 向 eBPF 靠拢的工程意义

**要点**：Oracle 在 2017-2019 年间的两个重要决策标志着 DTrace 技术路线的相对退潮：(1) 2017 年 8 月 Oracle 将 DTrace Linux 内核代码以 GPLv2+ 许可发布——这实质上是承认了 CDDL 路线在 Linux 上的失败，通过重新许可能够让 DTrace 代码更自由地进入 Linux 生态；(2) Oracle Linux 同时支持 DTrace 和 eBPF——Oracle UEK 内核持续集成 eBPF 功能；Cantrill 于 2010 年离开 Oracle，他是 DTrace 在 Sun 内部最强有力的支持者；Oracle 收购 Sun 后战略重心转向数据库、云服务和 Linux，Solaris 和 DTrace 不再是核心战略

**史料**：Mark J. Wielaard 2018-02-14 博客关于 Oracle GPL 许可 DTrace 的报道；Oracle Linux 博客 DTrace 和 eBPF 相关公告；Cantrill 2010-07-25《Good-bye, Sun》博客；Oracle UEK 内核发布说明 ［C］

**史观**：总纲第 25 条——终结与延续：Oracle 作为 DTrace 的“母公司”向 eBPF 靠拢，在工程话语权上标志着 DTrace 不再是可观测性领域的唯一或主导路线；但 DTrace 的技术遗产通过 eBPF 得到了延续——eBPF 验证器、探针模型、聚合思想都有 DTrace 的影子

**辨析**：Oracle 将 DTrace 代码以 GPLv2+ 发布并未使 DTrace 大规模进入 Linux 主线——因为此时 eBPF 已经成熟（2017-2018 年 eBPF 已广泛用于生产环境），DTrace Linux 移植的窗口期已过；这一时间点很重要——Oracle 可以更早（2010-2014 年间）选择 GPL 许可，但 Oracle 在 Sun 收购后忙于整合，战略方向摇摆，错过了可能改变 Linux 追踪生态的时间窗口

**文献**：Wielaard, M. J. (2018-02-14). dtrace for linux; Oracle does the right thing; Cantrill, B. (2010-07-25). Good-bye, Sun. dtrace.org/blogs/bmc/; Oracle. Unbreakable Enterprise Kernel Release Notes ［C］

**要点**：围绕 DTrace 的外部批评一手史料主要包括：Corbet 2007 LWN 文章（“DTrace envy”话语框架）；LKML 上关于 Linux 追踪方案的讨论（包括反对直接移植 DTrace 的论点）；SystemTap 开发者对 DTrace 批评的回应；Oracle 2017 年 GPL 许可决策的相关讨论；eBPF 兴起后社区对 DTrace 的回顾性评价（多为“先驱”定位）；Brendan Gregg 作为同时使用 DTrace 和 eBPF 的专家，其著作和博客提供了相对平衡的技术评估

**史料**：LWN.net 完整存档（lwn.net，含所有 DTrace/SystemTap/eBPF 报道）；LKML 存档（lkml.org）；Brendan Gregg 博客和书籍；SystemTap 项目邮件列表存档；Oracle 技术博客 ［A］
