# 125.20 项目统摄史观审视——BSD patch 替代 GNU patch 争议的方法论反思

## 125.20.1 总纲第 13 条审视——法律与道德是利益分配

**要点**：总纲第 13 条断言 “法律与道德是利益分配。任何道德问题本质上是利益问题，社区治理亦是形式主义的政治产物”。以此审视 BSD patch 替代 GNU patch 争议，可见双方道德话语（FSF 的 “保护自由” 与 BSD 阵营的 “真正的自由”）实质是不同利益群体的政治表达。FSF 的 copyleft 保护用户免于工具被专有锁定（用户利益），BSD 宽容许可保护商业开发者任意处置代码与免受 GPLv3 法律义务约束（开发者与商业参与者利益），两者均非道德绝对而系利益取向。**patch(1)** 作为基础工具，其许可证争议的结构与 GCC→Clang 迁移（详见第 58 章 58.4.7）同构——选择性地将 “避免 GPLv3 法律风险” 工程化，却接受同样含专利报复条款的 Apache 2.0（LLVM 现用许可证），这一选择性揭示 “纯洁化” 话语并非中立的工程评估，而是特定利益群体（免受 GPLv3 约束的商业参与者）风险偏好的形式主义包装。但 BSD patch 争议的特殊性在于：**patch(1)** 是小工具，其许可证纯洁化的工程收益极小（不像 GCC→Clang 有 C++11 支持的工程必要性），故利益分配的底色更清晰——BSD patch 替换几乎纯系许可证驱动，工程必要性遮蔽论在此更为有力。道德话语的层叠遮蔽了利益分配的底层结构，史家的任务不是裁决哪方 “更道德”，而是还原道德话语背后的利益地理。

## 125.20.2 总纲第 15 条审视——文化即形式主义

**要点**：总纲第 15 条断言 “文化即形式主义。传统在形式主义化过程中被遮蔽与重构。知音难觅同样适用于技术社区”。以此审视 BSD patch 替代争议，可见 **patch(1)** 作为 UNIX 传统工具，其 “传统” 在许可证纯洁化过程中被重构与遮蔽。Larry Wall 1985 年原始 patchkit 是 UNIX 工具传统的组成部分，FSF 在其基础上增强为 GNU patch 是传统的形式主义化（纳入 copyleft 框架），OpenBSD 替换 GPL 文件为 PD/无限制许可证是传统的再次形式主义化（纳入 BSD 许可框架），DragonFly 增强、NetBSD 采纳、FreeBSD 反向移植是传统的第三次形式主义化（跨项目重构）。每一次 “恢复” 传统都是一次新的建构——BSD patch 并非 “回归 Larry Wall 原始传统”，而是以 BSD 许可证框架重新建构的 “传统”。BSD 阵营叙事将 BSD patch 包装为 “回归 UNIX 原始工具传统”（脱离 GPL 约束），GPL 阵营叙事将 GNU patch 包装为 “UNIX 工具的 GNU 增强”（copyleft 保护下的传统延续），两种叙事都是形式主义化的非存在——真正的 Larry Wall 原始 patch(1) 已在多次形式主义化中被遮蔽。项目史观总纲第 7 章 7.2 节 “传统的断裂与重构” 指出 “传统在形式主义化过程中被遮蔽，离开了内容，形式还能是形式吗？年复一年的重复，人们必须记住些什么，去做些什么，可那些真正值得我们纪念的，早已经不再了”——BSD patch 争议中，**patch(1)** 的 “传统” 已不再是 Larry Wall 的原始实现，而是各阵营许可证框架的形式主义建构。总纲第 15 条续言 “知音难觅同样适用于技术社区”——BSD patch 跨项目谱系（OpenBSD→DragonFly→NetBSD→FreeBSD）的协作本身就是 “知音” 在技术社区的体现，但这种知音仅限于 BSD 阵营内部，GPL 阵营与 BSD 阵营之间的 “知音” 已不可得，这正是许可证文化结构不可通约的体现。

**史料**：总纲第 15 条原文（02-sacred源材料/shigang.md 第 19 行）、项目史观总纲第 7 章 “文化历史哲学”（7.1 文化即形式主义、7.2 传统的断裂与重构、7.4 文化记忆的虚妄）、57.15.1（现行对应节号待核定） BSD patch 跨项目谱系考据。 ［A］

## 125.20.3 总纲第 21 条审视——革命与改革是历史方法论分歧

**要点**：总纲第 21 条断言 “革命与改革是历史方法论的分歧。Linux 靠革命，BSD 靠改革。改革的困难远高于革命。破山中贼易，破心中贼难”。以此审视 BSD patch 替换工程，可见其方法论本质是典型的 “改革” 而非 “革命”——FreeBSD 采取 “导入 → 可选 → 默认 → 保留兼容” 四阶段渐进策略（r246074 2013.1.29 导入为可选 WITH_BSD_PATCH→r253689 2013.7.26 成为默认 →GNU patch 改名 `gnupatch` 保留而非立即删除），而非一次性断裂式切换。这种改革的困难远高于革命：革命可以一夜之间宣布 “从今用 BSD patch”，但 FreeBSD 须维持双 patch 兼容期（`bsdpatch` 与 `gnupatch` 并存）、逐步验证功能等价性（pfg 邮件呼吁 “please test extensively”）、为 ports 与用户脚本预留充足适配期。项目史观总纲第 21 章 21.2 节 “破山中贼易，破心中贼难” 指出 “真正的阻力不在于技术论证，而在于观念和结构。一旦想改变一种结构，你本身已是这种结构的一部分，改变已不可能。与这种结构对话是不可能的，它已经内部自洽”——BSD patch 替换中，GPL 阵营与 BSD 阵营都无法说服对方，正因为真正的阻力不在技术论证（`-I`/`-S` 选项是否过时、GPLv3 §11 专利条款的法律风险均可被精确陈述），而在观念与结构：一旦想改变一种许可证文化结构，你本身已是这种结构的一部分。FreeBSD 的改革智慧在于不试图说服 GPL 阵营，而是以渐进工程事实（r246074→r253689 的近 6 个月代码级验证期，再至 pfg 2014.9.19 在 PR 99173 关闭评论的约 1 年 8 个月社区稳定期）让 BSD patch 成为既成默认。这一改革方法论既是 BSD 的传统（4.4BSD-Lite 的渐进释放亦然），也是 BSD patch 作为许可证纯洁化工程序幕的方法论奠基——后续 GCC→Clang、GNU ld→LLD、GNU grep→bsdgrep 等替换均沿用 “导入 → 可选 → 默认 → 移除” 四阶段改革范式。总纲第 21 条续言 “改革的困难远高于革命”——从 r246074 到 r253689 的代码级迁移耗时约 6 个月（2013.1.29-2013.7.26），若加上 pfg PR 99173 关闭评论的 2014.9.19 则历时约 1 年 8 个月方告一段落，而若采取革命式切换可能仅需一个 commit，但革命式切换的代价是 ports 兼容性断裂与用户脚本失效，BSD 改革方法论选择了时间成本而非兼容性成本。
