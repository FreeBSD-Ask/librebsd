# 113.13 与同时期操作系统的比较：2005-2026 年同期 Linux Btrfs（Chris Mason 2007 年发布，Oracle 资助，受 R Reiser4 启发，但 Btrfs 长期未达 ZFS 的稳定性声誉）、Linux ext4（Theodore Ts'o 2008 年稳定）、Linux XFS（SGI IRIX 移植，Red Hat 主导维护）、Solaris ZFS 原版（Oracle 闭源后社区被剥夺）、OpenZFS on Linux/illumos/macOS、Windows ReFS（Microsoft 2012 年发布但限制于 Server 版）、Apple APFS（2017 年发布，Docker 与 Time Machine 整合）——FreeBSD ZFS 的稳定性与法律确定性独树一帜

## 113.13.1 Btrfs 与 ZFS 的技术路线差异

**要点**：Btrfs（B-tree file system，常读作“Butter FS”或“B-tree FS”）由 Chris Mason 于 2007 年在 Oracle 工作期间启动开发，设计目标是打造 Linux 原生的下一代 CoW 文件系统，提供与 ZFS 类似的功能（快照、校验、池化、RAID）；Btrfs 于 Linux 2.6.29（2009 年）合入主线内核，标记为 experimental；Btrfs 与 ZFS 的核心技术差异：（1）许可：Btrfs 采用 GPLv2（与 Linux 内核一致），可以直接进入 upstream；（2）设计：Btrfs 基于 B-tree 结构，ZFS 基于 Merkle 树 + 块指针；（3）成熟度：Btrfs 的 RAID 5/6 实现长期被标记为不稳定（存在 write hole 问题），直到 2020 年代仍有许多生产环境警告；（4）功能覆盖：Btrfs 缺少 ZFS 的一些企业级功能（如 send/recv 增量流虽然支持但不完整、无 ZIL/SLOG 分离等）；Red Hat 在 RHEL 中从 RHEL 6/7 开始将 Btrfs 列为 technology preview，但在 RHEL 8（2019 年）中移除了 Btrfs 支持，转而支持 Stratis（基于 XFS+LVM）

**史观**：总纲第 24 条——许可证：Btrfs 的诞生很大程度上是为了在 Linux 内核中“绕过”ZFS 的 CDDL 许可问题——Oracle 作为 ZFS 版权持有者，选择重新开发一个 GPL 许可的 CoW 文件系统，这本身就是 CDDL-GPL 不兼容如何塑造技术生态的最好例证

**辨析**：Btrfs 稳定性的争议：Btrfs 在单盘场景下已经相当稳定（被 openSUSE/SUSE 作为默认文件系统多年），但其多盘 RAID 功能的稳定性长期被质疑；这与 ZFS 在所有模式下（包括 RAID-Z）都以生产稳定著称形成对比；Btrfs 的 write hole 问题（RAID 5/6 模式下的原子性问题）直到 2023 年前后才通过新的日志机制部分解决

## 113.13.2 同期文件系统的工程演进比较

**要点**：2005-2026 年间同期主要文件系统时间线：ext4 由 Theodore Ts‘o（Ted Ts’o）开发，基于 ext3 扩展，Linux 2.6.28（2008 年 12 月）标记为稳定，是 RHEL 6/7/8/9 和多数 Linux 发行版的默认文件系统，采用日志而非 CoW 设计；XFS 最初由 SGI 为 IRIX 开发（1994 年），2001 年移植到 Linux，由 Red Hat 主导维护，是高性能 64 位日志文件系统，RHEL 7+ 默认文件系统；ReiserFS 由 Hans Reiser 开发（2001 年合入 Linux），但 Reiser 谋杀案后维护停滞，Reiser4 从未进入主线；Btrfs（2007 年启动，前述）；HAMMER（2008 年，DragonFly BSD）；HAMMER2（2018 年默认，DragonFly BSD）；ReFS（Resilient File System）由 Microsoft 于 Windows Server 2012 引入，是 Windows 的 CoW 文件系统，借鉴了 ZFS/Btrfs 的许多概念但仅限 Windows Server，不支持引导；APFS（Apple File System）由 Apple 于 2017 年发布（macOS 10.13/iOS 10.3），取代 HFS+，是 CoW 文件系统，支持快照、加密、空间共享，但不提供 ZFS 级别的池化/RAID；OpenZFS 成为跨平台统一代码库（2020 年 OpenZFS 2.0）

**史料**：各文件系统官方文档；Linux 内核文件系统历史；ext4、XFS、ReFS、APFS 各项目官方文档与 Release Notes；各操作系统 Release Notes ［D］

**史观**：总纲第 6 条——技术路线分化：2000 年代末 -2010 年代的文件系统演进呈现明显的“CoW vs 日志”路线分化——ZFS 引领了 CoW 潮流，Btrfs、HAMMER/HAMMER2、ReFS、APFS 纷纷跟进，但传统日志文件系统（ext4、XFS）在 Linux 企业市场仍占主导；许可问题是造成这一分化的关键因素之一

**辨析**：时间线交叉验证：ext4 稳定化时间——Linux 2.6.28 于 2008 年 12 月 25 日发布，ext4 在该版本中标记为 stable；XFS Linux 移植——最初由 Silicon Graphics 于 2001 年贡献到 Linux 2.5 主线；APFS 发布——macOS 10.13 High Sierra 于 2017 年 9 月 25 日发布，APFS 在该版本中默认启用（SSD）；ReFS——Windows Server 2012 于 2012 年 9 月 4 日发布，ReFS 随该版本首次亮相

## 113.13.3 FreeBSD ZFS 法律确定性比较

**要点**：FreeBSD ZFS 的法律确定性是其在所有平台中独有的优势：（1）BSD 许可与 CDDL 许可明确兼容——CDDL §3.5 允许与其他许可证的代码聚合，FreeBSD Foundation 和核心团队从未质疑 ZFS 在 FreeBSD base system 中的法律地位；（2）FreeBSD 将 ZFS 纳入 base system（2007 年起），不是作为可选模块或 DKMS 包，由 FreeBSD committer 直接维护，与内核同步更新；（3）FreeBSD 项目有统一的治理结构，核心团队明确支持 ZFS，没有 Linux 世界中“创始人 vs 发行版 vs 用户”的分裂；（4）相比之下：Linux 上 ZFS 始终是 out-of-tree 模块，受内核 API 变更影响，许可问题从未获得司法裁决，发行版支持差异大（Ubuntu 支持、Red Hat 不支持、Debian 在 main/contrib 之间反复）；macOS 上 ZFS（OpenZFS on OS X/macOS）是第三方移植，非 Apple 官方支持；Windows 上 OpenZFS 端口（2020 年代）同样是社区项目，非 Microsoft 支持；FreeBSD 成为 ZFS 法律和工程确定性最强的生产级平台
