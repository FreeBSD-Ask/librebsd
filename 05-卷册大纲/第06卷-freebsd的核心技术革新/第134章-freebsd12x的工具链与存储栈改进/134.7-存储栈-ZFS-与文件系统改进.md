# 134.7 存储栈、ZFS 与文件系统改进

## 133.7.1 UFS/FFS TRIM 整合与文件系统完整性
  - 要点：FreeBSD 12.0 中 UFS/FFS 文件系统更新了 TRIM/BIO_DELETE 命令整合逻辑（UFS/FFS filesystem has been updated to consolidate TRIM/BIO_DELETE commands, reducing read/write requests due to fewer TRIM messages being sent simultaneously），减少 SSD 上同时发送的 TRIM 命令数量以降低读写请求拥塞，由 麦库西克（Marshall Kirk McKusick）（mckusick@）等开发者实现。SUJ（Soft Updates Journaling）在 12.x 持续修复稳定性问题。**bectl(8)** ZFS 引导环境管理是 12.0 最重要的存储工具新组件。ZFS 在 12.x 时期持续从 OpenZFS 上游同步特性改进，但 ZFS 原生加密（native encryption）在 OpenZFS 2.0（对应 FreeBSD 13.0）才正式引入，12.x 加密仍依赖 **geli(8)**。**geli(8)** 12.0 支持多 provider 同密码初始化（r336659）。
  - 史料：FreeBSD 12.0-RELEASE Announcement（"The UFS/FFS filesystem has been updated to consolidate TRIM/BIO_DELETE commands"）、12.0 Release Notes Storage/ZFS 章节、commit r336659（geli 多 provider）、麦库西克 FFS 相关提交。 ［A］
  - 史观：总纲第 5 条——技术债务与代码考古：UFS/FFS 作为 FreeBSD 原生文件系统已延续四十余年（源自 1980 年代的 BSD FFS），至今仍在持续优化。TRIM 整合是 SSD 时代对传统文件系统的适配——机械硬盘时代不需要 TRIM，SSD 普及后文件系统需要主动通知存储设备哪些块已不再使用。
  - 辨析：ZFS 原生加密（ZFS native encryption）在 12.x 不存在——加密仍通过 GELI(8) 块级加密层实现；OpenZFS 原生加密在 2020 年 OpenZFS 2.0 发布后随 FreeBSD 13.0 引入。ZFS 书签重命名在 11.4 引入而非 12.0。
  - 文献：FreeBSD 12.0-RELEASE Announcement/Release Notes Storage sections [Z]. 2018；McKusick M K, et al. The Design and Implementation of the FreeBSD Operating System (2nd ed.)[M]. Addison-Wesley, 2014. ［B］
## 133.7.2 NFSv4.1 服务端与 pNFS 支持
  - 要点：FreeBSD 12.0 的 NFSv4.1 服务器实现更新，包含 pNFS（Parallel NFS）服务器支持（"The NFS version 4.1 server has been updated to include pNFS server support"）。pNFS 允许 NFSv4.1 服务器向客户端提供数据服务器（data server）集群布局，客户端可并行访问多个数据服务器进行 I/O，显著提高大规模存储环境的吞吐量。NFSv4.1/pNFS 服务端主要由 Rick Macklem（rmacklem@）长期开发与维护。NFS 客户端方面，12.x 持续改进 NFSv4 兼容性、支持 Amazon EFS（Elastic File System）等云 NFS 服务。
  - 史料：FreeBSD 12.0-RELEASE Announcement（NFSv4.1 pNFS 服务器）、**nfsd(8)**/**nfsv4(4)** 手册页、Rick Macklem NFS 相关提交与邮件列表讨论。 ［A］
  - 史观：总纲第 19 条——信息技术：NFSv4.1/pNFS 是企业级存储协议的重要演进，FreeBSD 对其支持使其在 NAS（网络附加存储）领域保持竞争力。相比 Linux NFS 实现，FreeBSD NFS 服务器以代码简洁、稳定性高著称，被部分商业 NAS 厂商（如 iXsystems TrueNAS）采用。
  - 辨析：pNFS 在 12.0 为初始支持状态，实际部署需要精心配置元数据服务器（MDS）与数据服务器（DS），在 12.x 时期主要用于特定企业场景；大多数 FreeBSD NFS 部署仍使用 NFSv3 或 NFSv4.0。
  - 文献：FreeBSD **nfsd(8)** Manual Page [Z]；FreeBSD 12.0-RELEASE Announcement Storage/Network sections [Z]. 2018；Shepler S, et al. RFC 5661: NFSv4.1 [S]. IETF, 2010.[考据完成：2026-07-28 经穷尽联网考据，上述文献清单为已知公开来源汇总，部分原始档案未公开数字化或须付费访问，属史料缺口，须待原始档案公开后方可补充确证]
## 133.7.3 UEFI+GELI 安装选项与引导改进
  - 要点：FreeBSD 12.0 的 **bsdinstall(8)** 安装器新增 UEFI+GELI 作为官方安装选项（r338282，Klara Systems 赞助），允许在 UEFI 引导模式下使用 GELI 加密根文件系统。先前 UEFI+GELI 需要手动配置，12.0 起安装器原生支持此配置。Lua **loader(8)**（基于 Lua 的引导加载器）在 12.0 获得多项改进（"Various Lua **loader(8)** improvements"），是 FreeBSD 11.x 引入 Lua loader 替代 Forth loader 后的持续完善。12.x 时期 **loader.conf(5)** 配置、UEFI Secure Boot 支持、**zfsbootcfg(8)** 等引导工具持续改进。**vt(4)** 控制台在 12.0 获得性能优化，文本绘制速度提升 2-6 倍。
  - 史料：FreeBSD 12.0-RELEASE Announcement（UEFI+GELI、Lua loader 改进、vt 性能提升）、**bsdinstall(8)**/**loader(8)**/**vt(4)** 手册页、commit r338282。 ［A］
  - 史观：总纲第 17 条——软件工程：UEFI+GELI 安装选项的加入是“加密即默认”理念在安装流程中的体现——全盘加密在笔记本电脑与移动设备场景下已成为最佳实践，安装器原生支持可避免用户手动配置出错。Lua loader 替代 Forth loader 则是用户可编程基础设施的现代化——Lua 比 Forth 更广为人知，降低了引导加载器脚本开发的门槛。
  - 辨析：UEFI+GELI 在 12.0 为安装器支持新选项，但 GELI 加密本身自 FreeBSD 6.x 即已存在；BIOS 模式下 GELI 加密引导支持更早版本即已存在。GELI 加密启动引导代码（gptgeliboot 与 gptzfsboot 的 GELI 支持）由 Allan Jude（艾伦·裘德） 主导开发（Jude, 2016）：开发中 gptldr 引导代码的 16 位汇编 64KB 复制限制曾使加入 AES/SHA 实现的加密 ZFS 引导代码（超 90KB）无法装入，最终由 Colin Percival 在 EuroBSDCon 2015 开发者峰会后以可扩展的可变 32KB 块复制方案解决（Jude, 2016）。Lua loader 在 11.x 已引入，12.0 是改进而非首次引入。
  - 文献：FreeBSD **bsdinstall(8)**/**loader(8)**/**geli(8)** Manual Pages [Z]；FreeBSD 12.0-RELEASE Announcement [Z]. 2018；commit r338282 [Z]. svn.freebsd.org；Jude A. Booting from Encrypted Disks on FreeBSD [C]//AsiaBSDCon 2016. Tokyo, 2016. ［A］
