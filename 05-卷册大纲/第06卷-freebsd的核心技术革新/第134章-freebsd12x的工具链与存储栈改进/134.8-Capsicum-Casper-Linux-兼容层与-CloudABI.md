# 133.8 Capsicum/Casper、Linux 兼容层与 CloudABI

## 133.8.1 Capsicum 能力模式完善与 Casper 守护进程
  - 要点：FreeBSD 12.0 中 Capsicum 能力沙箱继续完善：**sshd(8)** 新增 Capsicum 支持（r339216）；armv6/armv7 默认启用 Capsicum 支持（先前仅 amd64/arm64 默认启用）；更多 base 系统工具进入 capability mode。Capsicum 由 罗伯特·N. M. 沃森（Robert Watson）（rwatson@）领导的 Cambridge 团队开发，采用能力模式（capability mode）与文件描述符权限模型，与 Linux 的 SELinux/AppArmor MAC 模型路径不同。Casper——Capsicum 特权守护进程集合，在 12.x 时期继续完善——为沙箱内程序提供受限的系统服务访问（如 DNS 解析、文件打开、随机数获取），避免程序在 capability mode 下因无法执行某些特权操作而功能受限。
  - 史料：FreeBSD 12.0-RELEASE Announcement（"Additional **capsicum(4)** support has been added to **sshd(8)**"、"Support for **capsicum(4)** has been enabled on armv6 and armv7 by default"）、**capsicum(4)**/**casper(3)** 手册页、罗伯特·N. M. 沃森 Capsicum 论文与演讲、commit r339216。 ［A］
  - 史观：总纲第 4 条——分离与聚合：Capsicum 代表了“操作系统原生安全原语”的设计哲学——不引入复杂的安全策略标签系统（如 MAC），而是通过进程能力限制来缩小攻击面。Capsicum 的核心洞察是：大多数程序不需要完整的系统调用访问权限，限制文件描述符的能力即可有效遏制漏洞利用。但 Capsicum 需要程序源代码主动适配才能进入沙箱，这限制了其 adoption 速度。
  - 辨析：sshd Capsicum 支持在 12.0 是新增但并非完整沙箱——sshd 是特权网络服务，完全沙箱化面临挑战；12.x 中 sshd 的 Capsicum 支持主要限制了某些子进程而非主进程。Casper 在 12.x 提供的服务包括：system.dns（DNS 解析）、system.grp（组数据库访问）、system.pwd（密码数据库访问）、system.random（随机数）、system.sysctl（sysctl 只读访问）等。
  - 文献：Watson R N M, et al. Capsicum: Practical Capabilities for UNIX [C]//USENIX Security 2010；FreeBSD **capsicum(4)**/**casper(3)** Manual Pages [Z]；FreeBSD 12.0-RELEASE Announcement [Z]. 2018.
## 133.8.2 Linux 兼容层——CentOS 7 与 Ubuntu 用户态
  - 要点：FreeBSD 12.x 时期 Linux 二进制兼容层（Linuxulator）持续改进：①CentOS 7 用户态兼容层 ports（emulators/linux-c7）在 12.x 成熟，提供 Linux  glibc、libstdc++ 等核心库，可运行大量 Linux 二进制；②12.2-RELEASE（2020.10）起支持在 **jail(8)** 中运行 Linux 二进制；③Ubuntu 用户态兼容层（emulators/linux-ubuntu）在 12.x 后期开始引入但未达生产就绪；④Linuxulator 在 12.x 实现了更多 Linux 系统调用，包括 **epoll(7)** 子集、timerfd、eventfd 等；**linux(4)** 默认使用 64 位 Linux 系统调用向量；但 Docker、systemd 等依赖 Linux 特有内核特性（cgroups v2、完整 namespaces、netlink 等）的软件仍无法直接运行。Linuxulator 主要由 Konstantin Belousov（康斯坦丁·别洛乌索夫）（kib@）等人维护。
  - 史料：FreeBSD 12.2-RELEASE Announcement（jail+Linux 支持）、**linux(4)** 手册页、Konstantin Belousov Linuxulator 提交记录、freebsd-emulation 邮件列表、emulators/linux-c7 ports 目录。 ［A］
  - 史观：总纲第 22 条——开源运动：Linuxulator 是 FreeBSD 实用主义精神的体现——FreeBSD 不排斥 Linux 生态，而是通过系统调用翻译层在 FreeBSD 内核上直接运行 Linux 二进制，性能损失远低于全虚拟化。Linuxulator 的存在使 FreeBSD 服务器可直接运行大量闭源 Linux 商业软件（如 Oracle Database、Matlab 等），增强了 FreeBSD 在企业场景的可用性。
  - 辨析：Linuxulator 在 12.x 不能运行 Docker——Docker 依赖大量 Linux 特有内核特性（cgroups v2、完整 namespaces、netlink 套接字、overlayfs 等），Linuxulator 实现的系统调用子集不足以支持 Docker 守护进程；Docker on FreeBSD 在 12.x 需通过 bhyve 运行 Linux 虚拟机间接实现。Wine（Windows 二进制兼容）是独立于 Linuxulator 的子系统，通过 ports 提供。Linux 内核版本模拟在 12.x 为 3.2.x/4.x 级别，部分较新 Linux 二进制可能不兼容。
  - 文献：FreeBSD **linux(4)** Manual Page [Z]；FreeBSD 12.2-RELEASE Announcement [Z]. 2020；Belousov K. Linuxulator Improvements [C]//BSDCan various years.
## 133.8.3 CloudABI——基于 Capsicum 的安全 ABI 的兴衰
  - 要点：CloudABI 是由 Ed Schouten（ed@，FreeBSD 前 committer）创办的 Capabilities Limited 公司开发的“纯能力导向”应用 ABI，基于 Capsicum 设计理念，目标是提供 POSIX 兼容但默认安全的应用二进制接口——CloudABI 程序在启动时即处于能力模式，只能访问显式传入的文件描述符，无全局文件系统命名空间访问。CloudABI 在 FreeBSD 11.x-12.x 时期存在于 ports（devel/cloudabi、devel/cloudabi-toolchain）中并提供内核模块支持，但最终未获得主流采用，CloudABI 项目在 2010 年代末 -2020 年代初逐渐停止活跃开发。其理念影响了后续 WebAssembly（WASI，WebAssembly System Interface）的设计——WASI 同样采用基于能力的安全模型。
  - 史料：CloudABI 官方文档（Nuxi 存档）、Ed Schouten CloudABI 演讲（FOSDEM/BSDCan）、freebsd-cloudabi 邮件列表、ports/devel/cloudabi、WASI 规范与 CloudABI 的历史关联文档。 ［A］
  - 史观：总纲第 6 条——技术路线分化：CloudABI 是一次“重新设计安全 POSIX”的雄心勃勃的尝试，但失败原因在于：① 生态冷启动问题——为 CloudABI 编译的程序无法访问常规文件系统路径，难以移植现有软件；②Capsicum 本身在 FreeBSD 外的 adoption 有限；③ 容器化（Docker/Kubernetes）与 WebAssembly 提供了替代性的沙箱方案。但 CloudABI 的核心思想——“默认拒绝、显式授权”——是安全设计的正确方向，在 WASI 中得到了延续。
  - 辨析：CloudABI 从未进入 FreeBSD base 系统——始终存在于 ports 与第三方内核模块中；12.0-RELEASE Release Notes 未将 CloudABI 列为核心特性。CloudABI 的失败不是技术缺陷而是生态问题——其安全模型在理论上优雅，但缺乏商业驱动力和社区采用。Ed Schouten 在离开 FreeBSD committer 岗位后创立了 Capabilities Limited 推动 CloudABI，公司最终转向其他方向。
  - 文献：Schouten E. CloudABI: Secure by Default [C]//FOSDEM/BSDCan, 2015-2018；Nuxi CloudABI Documentation Archive [EB/OL]；WASI Preview 1 Specification [S]. W3C/WASI SG.
