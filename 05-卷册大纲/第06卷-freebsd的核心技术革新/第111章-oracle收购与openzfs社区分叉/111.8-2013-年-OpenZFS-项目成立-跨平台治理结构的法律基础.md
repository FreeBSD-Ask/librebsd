# 111.8 2013 年 OpenZFS 项目成立——跨平台治理结构的法律基础（**OpenZFS Bylaws**）与商标持有

## 110.8.1 OpenZFS Bylaws 与商标的法律结构

**要点**：OpenZFS 项目于 2013 年正式成立，首届 OpenZFS Developer Summit 于 2013 年 11 月 18-19 日在旧金山举行；OpenZFS 由 Matt Ahrens（Delphix）发起，联合各平台 ZFS 开发者共同建立跨平台治理结构；OpenZFS Bylaws 规定了项目治理结构：选举产生的指导委员会（Governing Board）、各平台代表席位（FreeBSD、Linux、illumos、macOS/Windows 等）、代码贡献流程、发布流程；OpenZFS 商标最初由 Matt Ahrens 个人持有，后转让至 OpenZFS 组织；OpenZFS 的核心目标是建立跨平台的共享 ZFS 代码库，减少各平台移植之间的代码分叉

**史料**：OpenZFS Bylaws（openzfs.org/wiki/Bylaws，2013 年发布）；第一届 OpenZFS Developer Summit 日程（2013-11-18）；Matt Ahrens LinuxCon 2013 "OpenZFS" 主题演讲；OpenZFS 商标注册信息；netbsd.db 查询 L6.1.1 显示：openzfs/zfs 仓库共 161 个 release tag，最早为 `zfs-0.4.1`（tagger_date = 2009-01-21T12:25:52-08:00，tagger_name = Brian Behlendorf（布莱恩·贝伦多夫），target_commit_hash = a66e5effd5c81f504fca32b7097cba83c625bebc），早于 OpenZFS 组织 2013 年成立，系 ZoL 时代标签继承；2013 年 OpenZFS 成立后 tag 进入 zfs-0.6.x 系列（如 `zfs-0.6.1` tagger_date = 2013-03-26），至 2020 年 `zfs-2.0.0` 实现跨平台代码统一；netbsd.db 查询 L6.3.1 显示：openzfs/zfs 仓库共 967 位贡献者，FreeBSD src 中 OpenZFS 相关贡献者（@openzfs/@delphix/@klarasystems/@ixsystems 邮箱域）68 位，二者重叠 65 位，重叠率 95.6%（65/68），表明 FreeBSD OpenZFS 维护者与上游 OpenZFS 核心团队高度重合 ［A］

**辨析**：OpenZFS 成立的精确时间：第一届 OpenZFS Developer Summit 于 2013 年 11 月举行，但 OpenZFS 作为协作项目的筹备始于 2012-2013 年，Matt Ahrens 等人在多个会议上提出了跨平台 ZFS 统一的构想；OpenZFS 不是从零创建 ZFS 的 fork，而是一个协调已有 ZFS 实现（illumos ZFS、ZoL、FreeBSD ZFS）的 umbrella 组织；netbsd.db L6.1.1 数据提示：openzfs/zfs 仓库 161 个 release tag 中 2009-2013 年的 zfs-0.4.x/0.5.x/0.6.0-rc 系列均由 Brian Behlendorf 单一 tagger 标注，反映 ZoL 时代的个人项目特征；2013 年后 tagger 字段开始出现多人，与 OpenZFS 组织化治理吻合；0 信任原则提示：openzfs/zfs 仓库 2019-11-07 前历史继承自 openzfs/openzfs，可能丢失早期 commit，L6.1.1 中 2009 年的 tag 须与 illumos-gate 交叉验证

## 110.8.2 跨平台治理的工程协调过程

**要点**：OpenZFS 成立前，各平台 ZFS 实现存在严重分叉：illumos ZFS 是 Solaris ZFS 的直接后代（维护最完整）；ZoL（ZFS on Linux）由 Brian Behlendorf 在 LLNL 启动，为适配 Linux 内核 API 做了大量修改；FreeBSD ZFS 通过 compat 层运行，定期从 illumos 同步新功能；macOS 的 ZFS 移植（MacZFS/O3X）独立维护；OpenZFS 的核心工程目标是建立共享代码库，通过 platform-specific 抽象层（zfs_config.h、platform/*目录）分离平台相关代码和核心 ZFS 逻辑；feature flags 机制（pool version 28 之后引入，约 2012 年）是跨平台协调的关键技术——每个新功能对应一个 feature flag，各平台可以独立选择启用哪些 feature，避免池版本号必须全局同步的问题

**史料**：OpenZFS developer summit 年度演讲记录（2013-2024）；feature flags 设计文档（Matt Ahrens，2012）；OpenZFS 代码库 github.com/openzfs/zfs 的提交历史；各平台 ZFS porting 层代码比较 ［A］

**史观**：总纲第 10 条——边缘者贡献：OpenZFS 跨平台协调的成功离不开非 Sun/Oracle 开发者的关键贡献——Brian Behlendorf（ZoL）、Matt Ahrens（Delphix/illumos）、Pawel Dawidek（FreeBSD）、各平台移植维护者，这些 “边缘者” 共同构建了 ZFS 的跨平台未来

**辨析**：OpenZFS 代码库统一的里程碑是 2020 年 11 月 30 日发布的 OpenZFS 2.0.0——在此之前 FreeBSD ZFS 和 ZoL 是独立代码库，定期从 illumos 同步 patch；OpenZFS 2.0 以 ZoL 代码为基础，将 FreeBSD 支持直接合入共享代码库，实现了真正的跨平台统一开发；OpenZFS 2.0.0 发布日（2020-11-30）两库无法验证（参考文献库无 OpenZFS 发布公告原文；邮件列表库命中 openzfs-2.1-freebsd 兼容性讨论始于 2021-12，未含 2.0 发布公告）

## 110.8.3 OpenZFS 与 illumos 的关系辨析

**要点**：illumos 是 2010 年由 Garrett D'Amore（加勒特·达莫尔） 发起的 OpenSolaris 社区 fork，包含完整的 Solaris 内核（ZFS、DTrace、Zones、Crossbow、SMF 等）；OpenZFS 是 2013 年成立的跨平台 ZFS 协作组织，专注于 ZFS 文件系统本身而非完整操作系统；2013-2020 年间，illumos ZFS 是 OpenZFS 社区的 "upstream"——大多数新 ZFS 功能先在 illumos 中开发，然后移植到 FreeBSD 和 ZoL；2020 年 OpenZFS 2.0 发布后，openzfs/zfs GitHub 仓库成为跨平台 ZFS 开发的核心，illumos 也开始从 OpenZFS 同步新功能，upstream/downstream 关系发生了逆转

**史料**：illumos 项目文档（illumos.org/docs）；OpenZFS 和 illumos 关系说明（openzfs.org/wiki/History）；Matt Ahrens 2013-2020 年 DevSummit 演讲；OpenZFS 2.0 Release Notes ［B］

**史观**：总纲第 3 条——形式主义膨胀：upstream/downstream 关系的逆转是开源生态演化的典型案例——一个项目（illumos）最初是整个生态的中心，但随着其他平台（尤其是 Linux）的开发者数量和活跃度超过 illumos 本身，开发重心自然迁移到更活跃的社区；这不是任何正式决策的结果，而是贡献者数量和代码活跃度的自然结果

**辨析**：需纠正一个常见误解：OpenZFS 不是 illumos 的 fork——OpenZFS 最初是一个协调组织，2020 年前没有独立代码库；OpenZFS 2.0 代码库以 ZoL 代码为基础而非 illumos 代码，因为 ZoL 在 2013-2020 年间发展出了更活跃的开发者社区和更多平台适配代码

**文献**：OpenZFS Project. *History of OpenZFS*. openzfs.org/wiki/History; illumos Project. *illumos Documentation*. illumos.org/docs; Ahrens, M. (2020). *OpenZFS 2.0*. OpenZFS Developer Summit 2020. ［B］

- Ahrens 口述 ZFS 起源：Jeff Bonwick 早于项目一年多即受命为 Solaris 打造下一代文件系统，配有十余名多为 UFS 出身的人手却因迟迟无设计而难以推进，遂向管理层承认原路不通；2001 年他与刚毕业的 Ahrens 以两人小组在雷达之下重启 ZFS，白板推演设计。分工上 Bonwick 深谙 Solaris 内核与大公司政治，负责在需要低调时维持项目隐匿、在有所成果时对外推广，Ahrens 则以新人之姿不设设计成见，二人自认缺一不可。　[存疑脚注] 转写将 Jeff Bonwick 记作 Jeff Bondwick、将 skunkworks 记作 SoundQuirks，均按语境校正。（BSDTalk EP227，[121.88-315.90]，L1）
- 早期时间线：2001 年夏提出基本设计，并以 Ahrens 在校期间所写的文件系统 interposer 层实现用户态原型，约五六个月后的 2001 年万圣节前后跑通，万圣节自此成为 ZFS 的标志性节点；随后引入有 UFS 经验的 Mark Maybee 等人负责 ZPL 层，即实现属主、文件大小、权限、目录与符号链接等真实文件系统语义的部分，约一年后的 2002 年万圣节前后得到可随 Solaris 运行常规工具的内核级完整文件系统。　[存疑脚注] 转写作 Mark Mabee 与 Marcus Schellenbaum，按语境疑为 Sun 的 UFS/ZFS 工程师 Mark Maybee 与 Mark Shellenbaum，须以原始音频与 Sun 时期人员记录复核。（BSDTalk EP227，[392.72-502.08]，L1）
- 开源与信任曲线：2005 年万圣节前后 ZFS 源码随 OpenSolaris 发布，彼时团队约十余名工程师、累计投入近 100 工程年；发布虽引起热望，但用户对把数据托付给新文件系统持保留态度，历经新品亮相、进入 Solaris 10 成受支持产品、客户测试数月乃至一年后进入生产的缓慢爬坡；近两三年 ZFS 经 OpenZFS 运动可用于 FreeBSD、Linux 与 macOS，用户与以其为业的企业数量激增。（BSDTalk EP227，[518.66-610.58]，L1）
- 可移植性源于设计阶段的模块化分层而非移植意图——ZFS 当年深嵌 Solaris：最上层的 ZPL/POSIX 层因须对接各平台 VFS 而差异最大，中部大块代码高度可移植，最底层的磁盘接口既小又易于移植，这种清晰分层同时解释了 ZFS 后来的跨平台扩散能力。（BSDTalk EP227，[724.44-794.26]，L1）
- OpenZFS 伞状项目在 2013 年访谈时点刚刚起步、尚无正式管理结构，目标是把 Illumos/Solaris 衍生、FreeBSD 与 Linux 各平台实现收拢一伞，让各平台的创新彼此可得、避免在每处重复修同一 bug。现状是 Illumos 为上游仓库、改动流向 Linux 与 FreeBSD，但 FreeBSD 开发者向 Illumos 回馈改动因对方社区更小、缺乏便捷的开发测试环境而困难；第一步即降低向 Illumos 集成改动的门槛，Ahrens 正与 FreeBSD 社区的 ZFS 负责人协作推进。　[存疑脚注] 转写将 FreeBSD 侧协作人记作 Powell，按语境疑为曾主持 ZFS 移植 FreeBSD 的 Pawel Dawidek，待原音频复核。（BSDTalk EP227，[858.58-998.08]，L1）
- 对重写问题的回应：ZFS 基础扎实、极易修改与增强，去重即开发晚期干净加入且代码集中于单层，故无需推倒重来，并以 UFS 约三十年的寿命为期许。但若今日重新设计，将面向未来十年以 Flash 为主的硬件：Flash 随机读能力强，或使常开去重变得可行——去重如今依赖巨型哈希表在每次写块时查询，磁盘介质上代价高昂，SSD 化后可望大幅缓解。（BSDTalk EP227，[1115.24-1409.52]，L1）

**史观**：

- 总纲21 革命与改革是历史方法论的分歧：pkg base 以改革姿态出现：不改写 base 与第三方的结构边界，仅替换升级工具链，用最小的本体论让步换取运维层面的变革；对照听众的 Linux 化疑虑可见，工程社区靠明确区分这是换工具而非换结构来消解变革阻力。（BSD Now EP84，[3919.82-3985.84]，L2）
- 总纲10 动手者创造历史：Matt Ahrens 粗算 ZFS 蕴含逾百工程年的积累，据此判定任何新实现从零追赶在可见期限内不可行；pkg 作者亦以近五年持续打磨工程细节回应路线图之问。技术史的走向由长时段的默默积累决定，而非发布节点上的宏大宣言。（BSD Now EP84，[1278.02-1332.40]，L2）
- 总纲3 不存在进步，只有权力再分配：缓存技术的存废由消费者需求而非技术逻辑再分配：persistent L2ARC 代码去年夏天检查时已接近完成，却因 Delphix 产品不用 L2ARC 而停在等待有人接手“最后冲刺”的状态；compressed ARC 则因客户内存可换来两到三倍等效缓存、成为好卖的卖点而被排进下一个发布周期——同一代码库内，功能的命运取决于商业方愿为谁的资源买单（当事人自述，ts 1923.98-2059.10）。（BSD Now EP77，[1923.98-2059.10]，L1）
- 总纲4 分离聚合是永恒规律：m0n0wall 在 2015 年宣布停止开发，但它的形式并未随项目一起死去：主持人指出 pfSense fork 自 m0n0wall，“甚至 FreeNAS 最初也是从 m0n0wall fork 的，因为它已经具备 appliance 胶水与构建脚本”（ts 809.29-815.56），OPNsense 再自 pfSense 衍生，BSD Router Project 亦在此谱系中——项目解体而特性扩散，分离聚合延续了这条防火墙发行品的生命（主持人转述，ts 773.14-842.24）。（BSD Now EP77，[773.14-842.24]，L2）
- 总纲4 分离聚合是永恒规律：OpenZFS 的成立以跨平台合作为目标，体现 ZFS 在封闭之后于多平台社区间重新聚合。（BSD Now EP14，[1078.7-1191.8]，L1）
- 总纲10 动手者创造历史：George Wilson 以恢复他人存储池为业余实践，将工程验证落实于具体动手。（BSD Now EP14，[684.2-707.1]，L1）
- 总纲9 经验优先：OpenSMTPD 源于 Gilles Chehade 在实际维护邮件系统时遭遇 sendmail 无法修补的具体困境，是经验先行、因需而作的工程起点。（BSD Now EP3，[653.72-703.80]，L1）
- 总纲4 分离聚合是永恒规律：Oracle 关闭 OpenSolaris 源码后，各平台分散的 ZFS 实现以 OpenZFS 重新聚合为统一治理结构，是分离与聚合的具体呈现。（BSD Now EP3，[2935.46-3032.28]，L2）
- 总纲8 本体论上各方平等：OpenSMTPD 通过可移植层与回注队列的接口兼容第三方工具，使不同平台与不同邮件软件处于平等可接入的位置。（BSD Now EP3，[804.20-890.16]，L1）
- 总纲22 知识注定过时：Ahrens 自述年少无知反而是设计自由之源：不识既有成规便可一一追问其存在理由并予以抛弃，这种天真使人敢于设想更大的改动；若今日有人提议彻底重构 ZFS，他反会顾虑代价。既有知识既是积累也是边界，年轻而不知难，才有时机与人力把激进设计做成现实。（BSDTalk EP227，[315.90-381.66]，L1）
- 总纲8 本体论上各方平等：Ahrens 阐明 OpenZFS 的长期目标是不专属任何平台、各平台地位平等：ZFS 不是 Illumos 的技术，更不只是 Oracle 的技术，而是跨平台技术；不应偏袒任何一方，要在维持质量红线的同时不让其他平台多付额外代价。（BSDTalk EP227，[998.08-1034.98]，L1）
- 总纲13 法律与道德是利益分配：CDDL 与 GPL 的不兼容无法通过改授权解决：既有代码版权分散在包括 Oracle 在内的众多公司与个人手中，且他们不会以 GPL 重授权。Linux 侧的实践者遂以可加载内核模块的方式实现 ZFS，按许可允许的状态假定推进，寄望主流发行版分装；当下各主流发行版已有可安装的包。许可与版权结构直接塑造了 ZFS 在 Linux 的存在形态。（BSDTalk EP227，[1036.12-1103.10]，L1）

**辨析**：

- 是否 Linux 化的分歧被摆上台面：听众来信以 base 与附加软件的清晰区隔正是 FreeBSD 区别于任意包集合式 Linux 发行版之处为由质疑打包化方向；主持人与访谈者反复申明 base 与第三方以 usr/local 为界的结构不变、world 与 kernel 仍一体化开发，pkg 只是升级与分发载体。争议实际落在工具链变更与本体论边界的混淆上。（BSD Now EP84，[3885.96-3985.84]，L2）
- 企业存在与治理文化的双重辨析：主持人断言 Juniper 设备几乎皆基于 FreeBSD、多数 Cisco 防火墙亦然，PF 已内置于 OS X 与 iOS，以此论证 BSD 技能的职场价值；另以 OpenBSD 提交日志末尾的 OK 署名对照 FreeBSD 的 Reviewed by 与 Approved by 机制，展示两项目代码评审治理的同构与差异。　[存疑脚注] 多数 Cisco 防火墙基于 FreeBSD 的说法为主持人单方断言，本期未给出处，未经交叉验证；Juniper 基于 FreeBSD 属可查事实但同样未当期举证。（BSD Now EP84，[4197.66-4389.78]，L2）
