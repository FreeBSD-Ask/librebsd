# 111.9 OpenZFS 在 Linux 上的法律灰区——ZFS On Linux 项目由 Brian Behlendorf（布莱恩·贝伦多夫） 维护，依靠 CDDL 允许内核模块以独立版权形式加载，但 林纳斯·托瓦兹（Linus Torvalds）明确表态 “我不能把 ZFS 合入内核，因为我不是律师”（I'm not a lawyer），Greg Kroah-Hartman 进一步声明 “我们认为 ZFS 不属于 Linux 内核”——此即 FreeBSD 在 ZFS 部署上相对 Linux 的法律壁垒优势

## 111.9.1 ZFS On Linux 的 CDDL 模块加载机制

**要点**：ZFS On Linux（ZoL）最初由 Lawrence Livermore National Laboratory（LLNL）的 Brian Behlendorf 于 2008 年发起，作为 HPC（高性能计算）场景下 ZFS 的 Linux 移植；ZoL 将 ZFS 实现为可加载内核模块（LKM），通过 SPL（Solaris Porting Layer，solaris.ko 和 spl.ko 模块）提供 Solaris 内核 API 兼容层；ZoL 代码完全以 CDDL 许可发布，不包含任何 GPL 代码，因此主张 ZFS 模块是独立作品而非 Linux 内核的衍生作品；Linux 内核的 MODULE_LICENSE(“CDDL”) 宏标记 ZFS 为非 GPL 模块，这意味着 ZFS 无法使用 Linux 内核中仅导出给 GPL 模块的符号（GPL-only symbols），但可使用所有 EXPORT_SYMBOL() 导出的通用符号

**史料**：Behlendorf 2008 年 ZoL 项目公告（zfsonlinux.org）；SPL（Solaris Porting Layer）GitHub 仓库（github.com/openzfs/spl）；ZoL 代码库 MODULE_LICENSE 声明；Linux 内核 COPYING 文件关于模块的例外条款说明；netbsd.duckdb 查询 L6.4.1.Linux 显示：openzfs/zfs 仓库 commit message 含 “Linux” 关键词的年度统计——2008 年 6249/8883（70.4%）、2009 年 8927/10914（81.8%）、2010 年 3989/5656（70.5%），2011 年骤降至 140/459（30.5%）反映 ZoL 代码库从 LLNL 内部仓库迁移至 GitHub 后 commit 量大幅下降；2019 年 146/1090（13.4%）至 2025 年 266/1552（17.1%），Linux 关键词占比稳定在 13%-25%，反映 OpenZFS 2.0 统一代码库后 Linux 不再是唯一主导平台；netbsd.duckdb 查询 L6.4.1.FreeBSD 显示：FreeBSD 关键词 commit 从 2011 年 2/459（0.4%）上升至 2024 年 621/1352（45.9%）、2025 年 640/1552（41.2%），与 OpenZFS 2.0 后 FreeBSD 集成深度提升一致 ［A］

**史观**：专题语（不设总纲条号）——技术路线分化（原挂总纲第 6 条系伪名目）：ZoL 的模块加载策略是法律约束下的工程妥协——ZFS 无法进入主线内核，因此通过 DKMS/LKM 方式在主线外分发；这种 “核外生存” 模式虽然有性能和维护成本，但在法律灰区中开辟了一条可行路径

**辨析**：需澄清：Linux 内核的 GPL 许可范围问题——Linux 内核 COPYING 文件明确指出 “kernel modules are considered derivative works”，但内核社区实际上长期容忍非 GPL 模块（NVIDIA、VMware 等闭源驱动，以及 OpenAFS 等 CDDL 模块），这形成了事实上的 “模块例外” 实践；ZoL 的法律地位在理论上有争议，但在实践中已被大多数 Linux 发行版（Ubuntu、Debian、Fedora、SUSE 等）通过各种方式接受；netbsd.duckdb L6.4.1 数据提示：2008-2010 年 Linux 关键词占比高达 70%-82%，因 ZoL 早期 commit message 普遍含 “Linux” 适配说明；2011 年后占比下降并非 Linux 适配工作减少，而是 OpenZFS 代码库统一后 commit message 不再强调平台特定性；0 信任原则提示：关键词匹配大小写不敏感（LIKE 默认），“Linux” 可能匹配非平台语境（如人名、路径名），须结合 commit message 全文交叉验证

## 111.9.2 Torvalds 与 Kroah-Hartman 的表态

**要点**：林纳斯·托瓦兹关于 ZFS 的最著名表态发表于 2020 年 1 月 6 日，是在 RealWorldTech 论坛一个关于 Linux 内核调度器的帖子（由 David Kanter 发起）的评论回复中，原文为 "Don‘t use ZFS. It’s that simple. It was always more of a buzzword than anything else, I feel, and the licensing issues just make it a non-starter for me"；该回复被广泛解读为 “Linus 禁止 ZFS 进入 Linux”，但实际上 Torvalds 的表态更多是个人立场而非正式的内核政策声明——他强调自己不是律师，不会在内核中合入存在许可证争议的代码；Greg Kroah-Hartman（Linux 内核稳定分支维护者）的表态更为正式，他在 2020 年 1 月的 Linux 内核邮件列表中表示 ZFS 不属于 Linux 内核，且 Linux 内核社区不会为 ZFS 提供稳定的内核 API/ABI，这使得 ZFS 作为外核模块必须持续跟进内核 API 变化；Torvalds 同时指出，如果 Oracle 以 GPL 兼容许可证重新授权 ZFS，或有人提供明确的法律意见认为 ZFS LKM 在 GPL 下合法，立场可能改变

**史料**：林纳斯·托瓦兹 2020-01-06 RealWorldTech 论坛评论（realworldtech.com/forum，互联网档案馆存档）；Greg Kroah-Hartman 2020-01 LKML 帖子；LWN.net 2020-01-10 报道 “Linus on ZFS”；Phoronix 2020 年 1 月相关报道 ［A］

**史观**：专题语（不设总纲条号）——开源社区的法律策略（原挂总纲第 22 条系伪名目）：Torvalds 和 Kroah-Hartman 的表态体现了 Linux 内核社区的核心治理原则——“无法律风险优先于技术卓越”；即使 ZFS 在技术上优于 Linux 原生文件系统，许可证风险足以阻止其进入主线；这与 BSD 社区的实用主义形成鲜明对比

**辨析**：原文称 Linus 说 “我不能把 ZFS 合入内核，因为我不是律师”——经核实原话是 "The Linux kernel cannot merge ZFS, because we cannot merge code that isn‘t GPLv2 compatible... ## 111.9.3 FreeBSD 与 Linux ZFS 法律地位比较

**要点**：FreeBSD 与 Linux 在 ZFS 法律地位上的根本差异：FreeBSD 内核采用 BSD-2-Clause 许可证（permissive），CDDL 文件可以直接放入内核源码树分发，不存在 copyleft 冲突；Linux 内核采用 GPLv2（strong copyleft），CDDL 文件无法合入主线，只能通过 DKMS/LKM 方式单独分发；这一差异导致的实际后果：FreeBSD 从 7.0（2008 年）起即在内核中包含 ZFS，FreeBSD 13.0（2021 年 4 月）将 OpenZFS 2.0 作为默认文件系统；Linux 上 ZFS 始终是外核模块，发行版支持情况不一（Ubuntu 20.04+ 可选安装、Debian contrib 源、Fedora 不官方支持、NixOS 原生支持）；FreeBSD 可以通过 pkg 升级 ZFS 版本，也可在启动时选择不同 ZFS 版本；Linux ZFS 升级通常需要重新编译内核模块（DKMS 自动处理）

## 111.9.4 法律灰区争议的史料辨析

**要点**：CDDL-GPL 兼容性争议的法律意见分为三派：FSF/GPL 阵营认为 CDDL 与 GPL 不兼容（FSF 许可证列表分类、Eben Moglen 多次讲话）；SFLC（Software Freedom Law Center）2016 年意见认为通过 DKMS 分离分发 ZFS 在 GPL 下可能合法（mere aggregation 解释）；Canonical/Ubuntu 法务团队认为在 Ubuntu 中分发 ZFS DKMS 包是合法的；Linux 内核社区主流立场（Torvalds、Kroah-Hartman）认为 ZFS 不能合入主线，但不阻止他人作为外核模块分发；截至 2025 年，没有任何法院就 CDDL-GPL 兼容性或 ZFS LKM 合法性做出判决，所有讨论均为法律意见；Ubuntu 2016 年决定在 16.04 中包含 ZFS 是发行版中的标志性事件，SFLC 为其出具了法律支持意见

**史料**：FSF 许可证列表 CDDL 条目（gnu.org）；SFLC 2016 年法律意见书（softwarefreedom.org）；Ubuntu Technical Board 2016-02 决议；Torvalds/Kroah-Hartman 2020 年公开声明；LWN.net 2016-2020 年 ZFS 法律报道系列 ［C］

**史观**：专题语（不设总纲条号）——形式与内容的张力（原挂总纲第 3 条系伪名目）：长达 20 年的 CDDL-GPL 争议没有法律结论，这本身就是开源法律生态的一个重要特征——开源许可证的执行主要靠社区规范和商业审慎，而非司法判决；这种 “灰区共存” 模式使得技术可以在法律不确定的情况下继续发展

**辨析**：FSF 关于 CDDL 不兼容的精确日期和文档：原文称 “FSF 2005 年 12 月声明”，经 gnu.org 许可证列表互联网档案馆存档查证，FSF 在 2006 年初已在许可证列表中标注 CDDL 为 “GPL-incompatible free software license”，但未发布专门的 “声明” 文档；FSF 对 CDDL 的立场是通过持续更新的许可证列表表达的，而非一次性声明，因此精确日期标注为 ［ 存疑脚注：此处事实待多源交叉验证 ］

- 将 1989/1990 年的模糊测试研究与 2016 年的讨论并置可见一条方法论延续线：当年以随机字符流击溃约四分之一实用工具、甚至在 Sequent 上令 refer 拖垮整个操作系统的发现，至 2016 年仍由 afl 这类以源码覆盖率引导输入生成的模糊器持续产出修复，主持人并追问其中多少缺陷历经二十余年未愈——可靠性工程并未随系统演化线性改善，而是同一测试哲学在不同工具形态中的循环再现（BSD Now EP131，[4690.52-4740.40]，L2）

- Ahrens 口述 ZFS 起源：Jeff Bonwick 早于项目一年多即受命为 Solaris 打造下一代文件系统，配有十余名多为 UFS 出身的人手却因迟迟无设计而难以推进，遂向管理层承认原路不通；2001 年他与刚毕业的 Ahrens 以两人小组在雷达之下重启 ZFS，白板推演设计。分工上 Bonwick 深谙 Solaris 内核与大公司政治，负责在需要低调时维持项目隐匿、在有所成果时对外推广，Ahrens 则以新人之姿不设设计成见，二人自认缺一不可。　[存疑脚注] 转写将 Jeff Bonwick 记作 Jeff Bondwick、将 skunkworks 记作 SoundQuirks，均按语境校正。（BSDTalk EP227，[121.88-315.90]，L1）
- 早期时间线：2001 年夏提出基本设计，并以 Ahrens 在校期间所写的文件系统 interposer 层实现用户态原型，约五六个月后的 2001 年万圣节前后跑通，万圣节自此成为 ZFS 的标志性节点；随后引入有 UFS 经验的 Mark Maybee 等人负责 ZPL 层，即实现属主、文件大小、权限、目录与符号链接等真实文件系统语义的部分，约一年后的 2002 年万圣节前后得到可随 Solaris 运行常规工具的内核级完整文件系统。　[存疑脚注] 转写作 Mark Mabee 与 Marcus Schellenbaum，按语境疑为 Sun 的 UFS/ZFS 工程师 Mark Maybee 与 Mark Shellenbaum，须以原始音频与 Sun 时期人员记录复核。（BSDTalk EP227，[392.72-502.08]，L1）
- 开源与信任曲线：2005 年万圣节前后 ZFS 源码随 OpenSolaris 发布，彼时团队约十余名工程师、累计投入近 100 工程年；发布虽引起热望，但用户对把数据托付给新文件系统持保留态度，历经新品亮相、进入 Solaris 10 成受支持产品、客户测试数月乃至一年后进入生产的缓慢爬坡；近两三年 ZFS 经 OpenZFS 运动可用于 FreeBSD、Linux 与 macOS，用户与以其为业的企业数量激增。（BSDTalk EP227，[518.66-610.58]，L1）
- 可移植性源于设计阶段的模块化分层而非移植意图——ZFS 当年深嵌 Solaris：最上层的 ZPL/POSIX 层因须对接各平台 VFS 而差异最大，中部大块代码高度可移植，最底层的磁盘接口既小又易于移植，这种清晰分层同时解释了 ZFS 后来的跨平台扩散能力。（BSDTalk EP227，[724.44-794.26]，L1）
- OpenZFS 伞状项目在 2013 年访谈时点刚刚起步、尚无正式管理结构，目标是把 Illumos/Solaris 衍生、FreeBSD 与 Linux 各平台实现收拢一伞，让各平台的创新彼此可得、避免在每处重复修同一 bug。现状是 Illumos 为上游仓库、改动流向 Linux 与 FreeBSD，但 FreeBSD 开发者向 Illumos 回馈改动因对方社区更小、缺乏便捷的开发测试环境而困难；第一步即降低向 Illumos 集成改动的门槛，Ahrens 正与 FreeBSD 社区的 ZFS 负责人协作推进。　[存疑脚注] 转写将 FreeBSD 侧协作人记作 Powell，按语境疑为曾主持 ZFS 移植 FreeBSD 的 Pawel Dawidek，待原音频复核。（BSDTalk EP227，[858.58-998.08]，L1）
- 对重写问题的回应：ZFS 基础扎实、极易修改与增强，去重即开发晚期干净加入且代码集中于单层，故无需推倒重来，并以 UFS 约三十年的寿命为期许。但若今日重新设计，将面向未来十年以 Flash 为主的硬件：Flash 随机读能力强，或使常开去重变得可行——去重如今依赖巨型哈希表在每次写块时查询，磁盘介质上代价高昂，SSD 化后可望大幅缓解。（BSDTalk EP227，[1115.24-1409.52]，L1）
