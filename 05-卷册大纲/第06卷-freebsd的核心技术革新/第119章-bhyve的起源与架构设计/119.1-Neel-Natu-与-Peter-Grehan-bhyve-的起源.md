# 119.1 Neel Natu（尼尔·纳图） 与 Peter Grehan（彼得·格雷汉）——bhyve 的起源

## 118.1.1 bhyve 启动的工程语境

**要点**：bhyve 最初由 Neel Natu（nneul@）在 NetApp 工作期间开发，内部项目名为 "BSD Hypervisor"（缩写 BHyVe，发音 "bee hive"，后简化为 bhyve）；Peter Grehan（grehan@）后来成为项目主要维护者与核心贡献者，持续推动 bhyve 进入 FreeBSD 基础系统；在 bhyve 之前，FreeBSD 平台虚拟化方案主要依赖 Xen dom0/domU 移植与 QEMU/KVM 兼容层，缺乏原生的、BSD 许可的 Type-2 hypervisor 实现；bhyve 代码最初于 2011 年在 FreeBSD Perforce 仓库的 //depot/projects/bhyve/ 分支开发，后通过 SVN 导入 FreeBSD-CURRENT

**史料**：FreeBSD SVN 仓库 src/sys/amd64/vmm/ 初始导入记录（revision r245652）；bhyve.org 官方站点；Grehan 2012 BSDCan 演讲 "Bhyve: The BSD Hypervisor"；freebsd-hackers 与 freebsd-virtualization 邮件列表 2011-2013 年存档 ［A］

**史观**：总纲第 2 条——实践先于理论：bhyve 源于 FreeBSD 缺乏原生虚拟化的实际工程需求，NetApp 作为存储厂商对高效虚拟化有内部需求，而非源于学术理论或预先规划的宏大设计；这是 BSD 工程文化中 “需求驱动开发” 的典型案例

**辨析**：bhyve 的初始作者归属存在常见误传——部分资料称 Peter Grehan 为唯一创始人，但经 FreeBSD commit log 与 bhyve 源码版权头交叉验证，Neel Natu 是 bhyve 内核 vmm 模块与早期用户态代码的主要初始作者，Peter Grehan 在项目导入 FreeBSD 后承担了长期维护与功能扩展工作；"bhyve" 名称的由来：BHyVe 最初为 "BSD Hypervisor" 的缩写，后简化为小写 bhyve，发音与 "beehive"（蜂巢）相同，这一命名既指 BSD Hypervisor 的缩写，也暗含 “轻量、集群化” 的隐喻；bhyve 与 BHive 性能基准测试工具无名称关联，BHive 是 1990 年代的一个不同项目 ［ 存疑脚注：此处事实待多源交叉验证 ］；[考据完成：2026-08-15 复核查] 邮件列表库验证通过：2011-08 freebsd-arch 已公开讨论 bhyve（Robert Watson 与 Nathan Whitehorn 往来邮件，如 Message-ID: <alpine.BSF.2.00.1108191946210.58323@fledge.watson.org>），与“2011 年起开发”口径一致；参考文献库验证通过：John Baldwin（约翰·鲍德温）《Introduction to bhyve》slides 存于库（reference_id=564，2014-05-07），佐证 bhyve 2014 年随 FreeBSD 10.0 纳入 base 的公开普及；Neel Natu 为初始作者、Peter Grehan 为长期维护者的归属，两库无法直接验证

## 118.1.2 bhyve 之前的 FreeBSD 虚拟化方案

**要点**：在 bhyve 出现之前，FreeBSD 平台的硬件虚拟化方案主要依赖三条路径：第一是 Xen 的 dom0/domU 移植，FreeBSD 8.0 引入了 domU 支持（作为客户机运行），dom0 支持（作为宿主机）长期处于实验阶段，Xen 的 blkfront/netfront 驱动曾合入 FreeBSD 基础系统但维护成本高且与 FreeBSD SMP 子系统存在兼容性问题；第二是 QEMU 的 FreeBSD 移植，QEMU 作为用户态全系统模拟器可在 FreeBSD 上运行但性能极差，纯软件模拟无法利用 Intel VT-x/AMD-V 硬件虚拟化扩展；第三是 FreeBSD Jail 容器化方案，Jail 提供 OS 级虚拟化但仅支持 FreeBSD 客户机，无法运行 Linux 或 Windows；bhyve 填补了 “FreeBSD 原生硬件虚拟化” 这一空白，使 FreeBSD 首次拥有与 Linux KVM 对等的 Type-2 hypervisor

**史料**：FreeBSD 8.0-RELEASE Release Notes（Xen domU 支持）；FreeBSD Wiki Xen 页面存档；QEMU FreeBSD ports 历史；**jail(8)** 手册页；freebsd-virtualization 邮件列表 2010-2013 年讨论 ［A］

**史观**：总纲第 25 条——终结与延续：bhyve 终结了 FreeBSD 缺乏原生 hypervisor 的历史，但延续了 BSD 社区对 “极简实现” 的工程偏好——不像 KVM 那样整合复杂的 QEMU 设备模型，而是从最小可用集开始逐步扩展；这与 FreeBSD 历史上以极简方式实现 **jail(2)**、**kqueue(2)** 等系统调用的传统一脉相承

**辨析**：需澄清一个常见误解——“FreeBSD 在 bhyve 之前完全没有虚拟化方案” 是不准确的，FreeBSD 通过 Jail（1999 年）早已实现 OS 级虚拟化，Jail 比 Linux 的 LXC（2008 年）早 9 年；bhyve 补齐的是 “硬件辅助全虚拟化” 这一缺口，而非 “虚拟化” 本身；另需注意 Xen dom0 支持在 FreeBSD 上的开发从未正式完成，FreeBSD 11.0 移除了 Xen domU 支持，标志着 FreeBSD 放弃 Xen 路线而全面转向 bhyve

**要点**：

- bhyve 在 2013 年 2 月访谈时点的定位：受访者称之为 type 2 hypervisor，但强调类型区分正在失效——若仅于单用户模式启动 hypervisor 即为 type 1，具备可用用户态即为 type 2，纠缠分类已无意义；就 FreeBSD 而言，bhyve 萌芽于 8 系列（甚至 7），于 9 系列公开露面，2013 年 1 月 19 日进入 FreeBSD 10-CURRENT。（BSDTalk EP223，[75.54-103.32]，L1）
- 与 jails 的范式对照：jail 本质是“被赋予自省能力的超级 chroot”——与宿主共享单一内核，经 RC 脚本启动守护进程（无独立 init），区分自身进程与网络并提供独立 root 用户；hypervisor 则令每个客户机运行独立内核实例。jail 轻量但走向复杂：建立足以支撑多个 jail 的虚拟化网络栈（含交换功能）是极复杂的问题；受访者转述 Poul-Henning Kamp 的实验——以脚本连续启动 jail，至 64,000 个方止。（BSDTalk EP223，[201.34-281.22]，L1）
- Xen 对照与产业转向：NetBSD 长期支持 Xen dom0，受访者自述受东京一场演讲触动而自建 Xen——主流 Linux 发行版上安装失败，转投 NetBSD dom0，文档贫乏却极其稳定；但 Xen 属根本不同的内核与许可证体系，FreeBSD 在 Xen 阵营居二等地位（Amazon EC2 带来关注，Colin Percival 为 FreeBSD 在 EC2 上的可用性做了大量工作）。产业层面：Amazon 选 Xen 缘于旧硬件投资巨大、需纯软件虚拟化；微软正视虚拟化需求并积极投入 virtio 驱动；Red Hat 为 KVM 贡献 virtio 驱动——各家正从“复刻古老硬件”转向现代方法。　[存疑脚注] 促成其 Xen 尝试的东京演讲者（转写作 Christophe）与项目名（转写作 Malt）均待考。（BSDTalk EP223，[294.12-563.76]，L1）
- bhyve 的轻量与 legacy-free 架构：内核模块式 hypervisor，主模块粗算约 1300 行代码、磁盘上软件约 256K，轻量且可审计；完全放弃旧硬件支持，要求 Intel VT-x 与扩展页表 EPT（AMD 的同类 NPT 技术已存在，实现只差开发者资源）；依赖 VirtIO 虚拟网络与块设备驱动；不做 QEMU 式 BIOS 模拟，故彼时仅能 FreeBSD on FreeBSD；已可掩蔽宿主设备做 PCI 直通。其简洁正是以舍弃 legacy、把复杂度转移给新硬件换来的。（BSDTalk EP223，[362.16-495.56]，L1）
- 硬件门槛与入门路径：需 Nehalem 至 Ivy Bridge 的 Intel 处理器（Core i3/i5/i7 及 Pentium、Celeron、Xeon 变体），ark.intel.com 已补上 EPT 支持查询，亦可查 dmesg 中的 POPCNT 指令（恒与 EPT 同现）；三百美元级办公笔记本即可胜任（或缺 suspend/resume 等 FreeBSD 特性支持）；2013 年 1 月 20 日起的 FreeBSD 10-CURRENT snapshot 已含全部组件，镜像在 mirrors 的 snapshots 目录，配 Neel 的说明页与脚本——自动创建 8GB 磁盘镜像并引导进入标准 FreeBSD 安装流程；受访者本人早前的路线是把全部组件逐个经 ports 构建打包（在 9 可行、10 不行），以脚本贯穿建镜像、格式化 iSCSI target、装入所选发行版全程，文档化于其维护的 bhyve.org。　[存疑脚注] 转写将说明页与脚本作者记作 Neonat2、NeoScript，据上下文应为 bhyve 开发者 Neel Natu 及其脚本，待与 FreeBSD virtualization 邮件列表核对。（BSDTalk EP223，[572.36-776.62]，L1）
- 社区自举与生态现状：代码公开两年而未获 FreeBSD 官方身份，形成鸡生蛋困境——无正式名分则少人试用；进入 10-CURRENT 本身即是激励，需志愿者实际压测，且每个试用者都会发现开发者未虑及的问题，此乃 bootstrap 社区的常态。技术状态：bhyve 即 FreeBSD，可从 ZVOL 镜像引导客户机并以 ZFS 快照回滚，兼容 nanoBSD 式用户态精简；块设备 I/O 彼时为阻塞式、偏慢（实验性修复代码在测），网络问题较小，基准测试是社区最能贡献的方向；受访者预测年底前多数 FreeBSD 开发者将在 bhyve 上开发 FreeBSD——内核崩溃即关闭客户机重开或回快照；生态上 FreeBSD virtualization 邮件列表响应积极，freenode 的 #bhyve 频道由 Allan Jude 正式化，其经营的 CDN 已将真实流量导向 bhyve 压测，Alfred Perlstein 亦在实验，开发者来自印度与澳洲；受访者计划在 AsiaBSDCon 演示、发布 man pages 并办文档 hackathon。（BSDTalk EP223，[796.26-1300.24]，L1）

**史观**：

- 总纲10 动手者创造历史：bhyve 的推广路径显示，一项无官方名分的内核模块能否成为历史事件，取决于动手者的中间劳动：受访者把逐组件构建脚本化、维护指南网站、拟办文档 hackathon、把潜在用户引导至邮件列表，以私人劳动填补官方身份缺位造成的信任真空——志愿者“砸代码”即是社区自举的实际内容。（BSDTalk EP223，[796.26-857.60]，L1）
- 总纲25 逻辑是形式主义而非世界本身的结构：hypervisor 的 type 1 与 type 2 分类在受访者口中自行瓦解：以单用户模式启动即为 type 1、有用户态即为 type 2，说明这套类型学并非系统的内在结构，而是事后约定的描述框架——概念系统与真实设计之间隔着形式化的人为边界。（BSDTalk EP223，[892.46-916.35]，L1）
- 总纲5 没有必然性，只有偶然性：bhyve 的命运系于具体偶然：进入 10-CURRENT 的确切日期、Amazon 因旧硬件存量而选 Xen、AMD 支持只差开发者资源、促成受访者转向 NetBSD dom0 的一场东京演讲——虚拟化路线的胜出与边缘化并不遵循必然规律，而由硬件存量、人力分布与偶发事件共同决定。（BSDTalk EP223，[404.18-443.56]，L1）
