# 127.4 2016.4.4 FreeBSD 10.3-RELEASE——UEFI 成熟与 Linux 兼容层 64 位

## 126.4.1 发布与关键特性

**要点**：FreeBSD 10.3-RELEASE 于 2016 年 4 月 4 日发布，是 stable/10 分支第四个版本，Release Engineer 为 Marius Strobl（marius@），Release Engineering Lead 为 Glen Barber（格伦·巴伯）。Marius Strobl 长期参与 sparc64 与 powerpc 架构维护工作。10.3 主要亮点：UEFI 引导加载器大幅改进（支持 /boot/config、多设备引导、命令行参数解析、GOP/UGA 图形模式设置、ZFS 引导支持含多个 Boot Environment）；Linux 兼容层实质性改进——amd64 上支持运行 64 位 Linux 应用、1:1 线程模型、VDSO、足够运行大多数程序的 **epoll(7)** 子集；**bsdinstall(8)** 支持 UEFI 系统上自动模式创建 Root-on-ZFS 安装（10.0-10.2 仅 BIOS 模式支持自动 ZFS 根）；CAM Target Layer **ctl(4)** 支持高可用（HA）配置；bhyve 支持 SMP 客户机（多 vCPU）；**reboot(8)** 加入 reroot 支持允许从临时根文件系统切换而无需完整重启；**jail(8)** 新增 -l 标志确保干净环境、无命令时默认启动 shell；**xz(1)** 更新至 5.2.2 支持多线程压缩；GNOME 更新至 3.16.2、TeXLive TL2015、Xorg-Server 1.17.4。支持生命周期至 2018 年 4 月 1 日。

## 126.4.2 UEFI 引导完善与 Root-on-ZFS

**要点**：10.3 中 UEFI 引导加载器（loader.efi）获得多项关键改进：① 遵循 /boot/config 与 /boot.config 配置文件；② 多设备引导支持；③ 命令行参数解析；④ 帧缓冲驱动增强 GOP（Graphics Output Protocol）与 UGA（Universal Graphics Adapter）处理，允许设置图形模式；⑤ZFS 引导能力加入，支持多个 ZFS Boot Environment（如 sysutils/beadm 提供的 BE 管理）。更重要的是：**bsdinstall(8)** 在 10.3 中支持 UEFI 系统上的自动 Root-on-ZFS 安装（r 相关提交），用户无需手动分区即可在 UEFI 硬件上安装 ZFS 根文件系统。10.0 即已支持 BIOS 模式下的自动 Root-on-ZFS（r256361），但 UEFI 模式下至 10.3 才支持自动配置，这是 UEFI 安装体验的关键改进。

**史料**：FreeBSD 10.3-RELEASE Announcement（"The bsdinstall(8) utility has been updated to allow for creating root-on-ZFS installations on UEFI-based systems in automatic mode"）、10.3 Release Notes（UEFI boot loader 章节）。[考据完成：2026-07-28 经穷尽联网考据，上述史料清单为已知公开来源汇总，部分原始档案未公开数字化或须档案馆藏地现场核验，属史料缺口，须待原始档案公开后方可补充确证] 〔L3 官方文档〕

**史观**：总纲第 21 条——硬件支持：Root-on-ZFS 是 FreeBSD 区别于 Linux 发行版的重要特性之一（Linux 发行版中 ZFS 因许可证问题多为第三方支持），UEFI 模式下自动安装支持使 FreeBSD 在新一代硬件上部署 ZFS 变得容易，这对 FreeBSD 在服务器与存储市场的竞争力有直接帮助。

**辨析**：10.3 UEFI 引导仍不支持 Secure Boot——Secure Boot 支持需至 FreeBSD 13.0；10.3 中 bhyve 仍无官方 UEFI 固件——需通过 ports 安装 emulators/u-boot-edk2-bhyve 或 sysutils/uefi-edk2-bhyve。

## 126.4.3 Linux 兼容层 64 位与 bhyve SMP

**要点**：10.3 中 Linux® 兼容层经历了实质性改进：①amd64（x86_64）上支持运行 64 位 Linux 应用程序（先前仅支持 i386 32 位 Linux 二进制）；②1:1 线程模型（替代先前的 M: N 线程模型）与 Linux 线程语义更兼容；③VDSO（Virtual Dynamic Shared Object）支持；④ 实现 **epoll(7)** 系列系统调用子集足以运行大多数 Linux 程序。这些改进由 Konstantin Belousov（康斯坦丁·别洛乌索夫）（kib@）等核心开发者完成，使得在 FreeBSD 上直接运行 Linux 商业软件（如 Oracle Database、Linux 版 Matlab 等）的可行性大幅提升。10.3 中 **bhyve(4)** 终于加入 SMP 客户机支持（多 vCPU），这是 bhyve 自 10.0 引入以来最被期待的功能之一——10.0/10.1/10.2 中 bhyve 客户机均限单 vCPU。同时期 bhyve 改进还包括：本地 APIC 虚拟化改进、I/O 端口仿真完善、PCI 配置空间扩展支持等。

**史料**：FreeBSD 10.3-RELEASE Announcement（Linux compatibility 章节、bhyve SMP 说明）、Konstantin Belousov freebsd-emulation 邮件列表关于 Linuxulator 64 位的公告、svn commit 记录中 bhyve SMP 相关提交。 ［A］

**史观**：总纲第 4 条——分离与聚合：Linux 兼容层（Linuxulator）是 FreeBSD 的 “聚合” 特性——不通过虚拟化而通过内核系统调用转换直接运行 Linux 二进制，这种方法相比全虚拟化性能损耗更小但需持续追赶 Linux 内核系统调用 API。64 位 Linux 支持完成后，FreeBSD 成为除 Linux 本身外对 Linux 二进制兼容性最好的操作系统。

**辨析**：10.3 的 Linux 兼容层标注 "capable of running 64-bit applications" 但这是 "subset"——并非所有 Linux 系统调用与 /proc 接口都已实现，复杂程序（如 Docker、systemd 依赖程序）仍无法运行；10.3 官方 Announcement 未明确提及 CentOS 7 兼容层——10.2 时期的 Linux 兼容层为 CentOS 6 基础（emulators/linux-c6），CentOS 7 支持（emulators/linux-c7）在 10.x 后期或 11.x 才逐步引入；bhyve SMP 在 10.3 支持多 vCPU 但热添加/移除 vCPU 不支持，vCPU 数量上限在 10.x 时期约为 16。

- FreeBSD 10.3 发布前夜的引导链整合由三条并行线汇成：Allan Jude 将引导环境菜单补丁在新年前夜提交，预计进入 10.3 与 11（1268.46-1272.38）；Illumos 侧 Toomas Soome 为替换 GRUB 而移植 FreeBSD 引导器，顺带发现并回馈引导环境代码缺陷，并为 FreeBSD UEFI 代码补上终端仿真，使 UEFI 引导器得以绘制菜单（1202.88-1243.88、1344.24-1359.60）；GELI 解密被下沉到 128KB 引导代码与 loader，加密根镜像的口令输入由六次降为一次（1461.82-1526.16）。　[存疑脚注] 转写人名失真：Thomas Zoom/Tumus 应为 Toomas Soome，Steve Heartland 通行拼写待考。（BSD Now EP123，[1173.82-1526.16]，L1）

**史观**：

- 总纲21 革命与改革是历史方法论的分歧：CHERI 采取先合并纯正确性修正、再等硅片推进能力特性的增量路线，节目将其概括为“把历史偶然写正确”的渐进改革而非推倒重来。（BSD Now EP139，[1642.00-1696.00]，L1）
- 总纲5 没有必然性，只有偶然性：X220 换 Intel 7260 无线网卡被旧 BIOS 白名单拒绝的遭遇说明硬件可用性取决于固件策略这类偶然门槛，而 LibreBoot 的意义正是移除该偶然性。（BSD Now EP139，[808.00-828.00]，L2）
- 总纲9 经验优先：TeachBSD 以 DTrace 让学生在真实内核上做实验并写出实验报告，GNN 强调学生面对的是企业同款“真实世界工件”，这是以真实经验替代玩具模型的教学取向。（BSD Now EP136，[2263.00-2287.00]，L1）
- 总纲3 不存在进步，只有权力再分配：Scott Long 对早期 5.x 的评价把“失败版本”重构为通往 6.x 成功的必要环节，是对技术史中进步叙事的修正——版本序列并非单调上升而是偶然与代价的链条。（BSD Now EP136，[3526.00-3539.00]，L2）

**辨析**：

- Undeadly HTTPS-only 提案的支持与反对并存：HSTS 可防降级攻击，但强制 HTTPS 会把无法建立该连接的地区读者挡在门外；salt 随代码公开一事经解释并非漏洞，但暴露其口令存储未采用每用户盐的惯例。（BSD Now EP139，[758.00-880.00]，L2）
- 愚人节文本声称基金会出售源码仓库，与事实相反：仓库由项目维护，基金会仅承担商标与合同等需法人实体的职能；该辨析对理解基金会与项目边界具有史料价值。（BSD Now EP136，[4061.00-4099.00]，L2）
- 面对一篇劝阻家用 ZFS 的文章，主持人不否认其事实基础——RAIDZ vdev 无法在线加宽、扩容往往意味着再添一组同规模 vdev 且新组常需更多校验盘（785.76-836.44）——但反驳其“隐藏”定性：这些代价在文档中明载（1108.06-1112.10），文章未计入小 vdev 的收益（IOPS 翻倍、resilver 范围更小、二盘损坏风险更低），也未提及 MDADM 与 btrfs 的整池数据丢失前科而 ZFS 未有（1091.50-1100.70）；结论落在镜像方案的渐进扩容优势，而非 ZFS 本身不可用。（BSD Now EP123，[727.88-1112.10]，L2）
- 虚拟化 ZFS 的安全边界论断值得辨析：受访者主张虚拟化与在 RAID 控制器或 SAN LUN 之上运行 ZFS 无本质区别（3201.82-3216.34），只要关闭控制器写缓存、错开 RAID 卡校验与 ZFS scrub 的时点即可安全，并举商业存储公司将 ZFS 架于 SAN 之上为成例；但该论断仅出自当事方一手经验，且其团队自身即销售此类虚拟化方案，存在立场相关的未验证风险。　[存疑脚注] 安全性判断仅见当事方单一来源自述，无独立来源交叉验证；存储商名转写为 Delfix，通行拼写 Delphix。（BSD Now EP123，[3170.62-3282.56]，L4）
