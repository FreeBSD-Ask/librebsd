# 118.9 CheriBSD——Watson 团队维护的 CHERI 扩展 FreeBSD 分支，作为 CHERI 硬件的主要参考操作系统持续演进

## 118.9.1 CheriBSD 的技术架构与 CheriABI 纯能力 ABI

**要点**：CheriBSD 是 SRI International 与剑桥大学维护的 FreeBSD 分支，专门支持 CHERI 硬件能力架构；CheriBSD 在 FreeBSD 基础上添加了 CHERI 能力感知的内核内存管理、进程装载、信号处理、系统调用接口和用户态库支持；CheriBSD 最重要的软件创新是 CheriABI（Capability Hardware Enhanced RISC Instructions ABI）——由 Brooks Davis 等人设计，发表于 ASPLOS 2019 会议的论文"CheriABI: Enforcing Valid Pointer Provenance and Minimizing Pointer Privilege in the POSIX C Run-time Environment"；CheriABI 是纯能力 POSIX ABI，所有指针均用 CHERI 能力表示，编译器（扩展版 LLVM/Clang）自动生成能力感知代码，用户态程序经重新编译后可获得确定性空间内存安全（防止缓冲区溢出）和指针 provenance 保护，无需修改源代码逻辑；CheriBSD 同时支持传统 ABI 进程（非能力、无安全收益）和 CheriABI 进程（纯能力、内存安全）混合运行

## 118.9.2 CheriBSD 与 FreeBSD 主线的关系及上游化努力

**要点**：CheriBSD 是 FreeBSD 的一个 fork（分支）而非 FreeBSD 基础系统的一部分——截至 2025 年，FreeBSD 主线（main 分支）不包含 CHERI 硬件支持；CheriBSD 与 FreeBSD 主线保持定期同步（通常基于 FreeBSD -CURRENT 或 -STABLE 分支进行开发），CheriBSD 团队持续将与 CHERI 无关的通用改进向上游 FreeBSD 提交；CheriBSD 维护者（包括 Brooks Davis、Edward Tomasz Napierala、John Baldwin（约翰·鲍德温）、Jessica Clarke 等 FreeBSD committers）本身就是 FreeBSD 社区的活跃贡献者，许多 CheriBSD 中的通用改进（如 RISC-V 架构支持完善、链接器改进、bhyve 增强等）已进入 FreeBSD 主线；但 CHERI 硬件支持本身（能力感知的内核、CheriABI 等）因需要相应硬件才能测试且涉及大量 ABI 变更，短期内不太可能合入 FreeBSD 主线

**史料**：CheriBSD 源码仓库与 FreeBSD 主线的 Git 历史对比（github.com/CTSRD-CHERI/cheribsd vs github.com/freebsd/freebsd-src）；FreeBSD 邮件列表中 Brooks Davis/Edward Napierala 等人关于 CHERI 上游化的讨论；CheriBSD 项目声明其与 FreeBSD 的关系；CHERI 团队在 BSDCan/EuroBSDCon 的演讲 ［A］

**史观**：总纲第 10 条——边缘者贡献：CheriBSD 作为 FreeBSD 研究分支的模式类似于 BSD 历史上的诸多研究分支（如 BSD/OS、BSD/386 是商业化分支）——研究分支承担高风险新特性的早期探索，成熟后部分成果反馈主线；这一模式与 FreeBSD 本身从 386BSD 分支发展而来的历史形成呼应，体现了 BSD 生态中分支实验与主线稳定的动态平衡

## 118.9.3 CheriBSD/CheriABI 与 Capsicum 的协同

**要点**：CheriBSD 同时支持 Capsicum（OS 级软件沙箱）和 CHERI（硬件级内存安全），两者形成深度协同：(1) Capsicum 的能力模式提供 OS 级隔离（切断 ambient authority，沙箱进程仅能访问授权的文件描述符），CHERI 提供硬件级内存安全（防止指针伪造和越界访问）——两者组合提供纵深防御；(2) 在 CHERI 硬件上，Capsicum 能力文件描述符可获得硬件级保护——进程无法伪造指向文件描述符的能力指针，从硬件层面防止沙箱逃逸中常见的指针伪造攻击；(3) casperd 在 CheriBSD 上同样运行，为 CheriABI 沙箱进程提供服务代理；(4) CheriBSD 的 bhyve 虚拟化支持（CHERI-enabled bhyve）允许在 CHERI 硬件上运行 CheriBSD guest 并保持能力隔离，实现多层安全栈

**史料**：CheriBSD 文档中 Capsicum 相关章节；CHERI/Capsicum 论文（Watson 等人在多篇论文中讨论 Capsicum 在 CHERI 上的协同增强）；CheriBSD bhyve 特性文档；Watson et al. 2024 IEEE S&P 论文 ［B］
    FreeBSD 社区论文：[FP-2010-005] Capsicum: practical capabilities for UNIX（Robert N. M. Watson，2010）<https://papers.freebsd.org/2010/rwatson-capsicum/>

**史观**：技术路线分化：Capsicum（软件）与 CHERI（硬件）分别独立设计但最终互补的事实说明：安全是多层防御问题，不存在单一银弹；软件沙箱与硬件强制保护各有优势，二者结合比任一单独使用提供更强的安全保证；这也印证了盐泽-施罗德原则中的“纵深防御（Defense in Depth）”原则

**辨析**：需明确：Capsicum 不需要 CHERI 即可运行——Capsicum 在标准 FreeBSD/x86 上完全可用，纯软件实现；CHERI 也不需要 Capsicum 即可提供内存安全——CheriABI 单独即可防止空间内存安全漏洞；二者是互补关系而非依赖关系；CloudABI/WASI 的纯能力模型与 CHERI 硬件能力在思想上同源，但 WASI 运行在 WebAssembly 虚拟机而非裸机上

**要点**：

- Brooks Davis 自述 CHERI 是剑桥大学与 SRI International 开发的能力硬件扩展，以不可伪造的 capability 替代裸指针，为分配空间附加边界与标签，从而在架构层阻断缓冲区溢出，并抑制大部分时序内存安全漏洞。（BSD Now EP486，[419.69-546.33]，L1）
- Morello 是由 UKRI“Digital Security by Design”计划与 ARM 共同出资的全尺寸原型芯片，在 ARM N1（Amazon Graviton 所用核型）上加入 CHERI，从架构到 tape out 仅用一年，制造成本逾一亿英镑；其目标之一是打破软件界不愿面向不存在硬件编程、硬件界不愿制造无人使用硬件的僵局。（BSD Now EP486，[583.47-774.5]，L1）
- Brooks Davis 称 CheriBSD 是首个在 Morello 上开发的操作系统；团队十年前从 64 位 MIPS 起步将 FreeBSD 移植为 CheriBSD，此后并行开展 RISC-V 与 ARM 端口，并自动化了 FreeBSD 兼容层创建，使新增系统调用时只需正确标注即可判断是否需要兼容函数。（BSD Now EP486，[821.15-999.65]，L1）
- Olivier Cochard-Labbé 自述 2005 年为搭建家用 NAS 修补 m0n0wall 防火墙时偶然发现其底层并非 Linux 而是 FreeBSD，遂将防火墙配置替换为 Samba 配置，由此创建 FreeNAS；FreeNAS 最初只是面向家庭文件共享的 PHP Web 界面加 gvinum RAID 方案。（BSD Now EP486，[1225.45-1346.59]，L1）
- Olivier 自述 FreeNAS 迅速被社区广泛采用，甚至被巴西城市用于存储监控视频，超出其业余维护能力，最终将项目交给 iXsystems；此后他创立强调命令行接口、贴近原生 FreeBSD 的 BSD Router Project，并在约四年前进入 Netflix 从事网络性能基准工作。（BSD Now EP486，[1606.01-1909.91]，L1）
- Brooks Davis 在亚洲 BSDCon 受访时自述，CHERI 项目为支持自研研究处理器而维护 FreeBSD 的分支（转写误作 CherryBSD），在 MIPS64 指令集基础上增加 ISA 扩展以实现空间内存安全，并辅以时间内存安全框架；在改动最深的纯能力模式下缓冲区溢出被消解，越界将触发硬件异常而非任意行为，编译后的 SSH 理论上不应再有缓冲区溢出；项目由 DARPA 资助、至受访时已进行约五年，因既有 MIPS32 FPGA 设计而选择 MIPS64，并向 RISC-V 与标记内存方向延展。（BSD Now EP139，[1444.10-1541.46]，L1）
- Davis 阐明 CHERI 的工程路线：目标是将成果合回 FreeBSD 主线，当前已先行合并纯正确性修复，如以 uintptr_t 替代以 long 操纵指针的历史习惯写法，待流片后将更激进地合并；移植 Linux 内核的难点恰在其内核大量以 long 操纵指针；改造成本高度依赖代码结构，将 TCP 分组缓冲区能力化因编码风格而成为最坏情形，涉及约五千行改动，而具有良好 typedef 抽象的代码仅需更改类型即可完成。（BSD Now EP139，[1642.10-1798.42]，L1）
- Allan Jude 在 BSDCan 2026 报告 OpenZFS 的 anyRAID 方案：vdev 空间被划分为 16 GiB 的 tile，经一块置于 vdev 前端固定偏移、保留四份冗余的 tile map 完成逻辑到物理的间接寻址，无需导入存储池即可读取，从而把 RAID Z 固定条带宽度改造为可随盘数动态伸缩的条带，支持镜像与 RAID Z1/2/3 混合、vdev 扩容与收缩、以及以重平衡替代整盘搬迁，并兼容快照、DDT、块克隆与收发等既有 ZFS 特性，定位于以最低每 TB 成本换取最大容量与灵活性；其约束亦被明确：tile map 容量决定单 vdev 上限 256 盘与 65000 tile，未来新盘不得超过初始最小盘的 1024 倍，收缩下限为 RAID Z 条带宽度。（YouTube EPmZ-dhntnkCQ，[1044.959-1120.639]，L1）

- Kirk McKusick 报告 FreeBSD 内核的扩展错误消息框架，并以设计史还原开篇：Unix 的纯整数错误码根源于 PDP-11 的 16 位地址空间——64K 文本段约合一万行 C，字符串是稀缺资源，内核以数字返回、用户态再展开为可读串曾是工程必然；在 64 位地址空间下该约束失效，新框架允许系统调用返回带至多两个参数的格式化错误串，逐文件注册错误类别、可经编译选项剥离以兼顾嵌入式场景，由 C 运行时与线程库按线程预置缓冲、成功调用零开销，错误沿 BIO 与内核线程上下文逐层回传至发起进程，并可用 ktrace/kdump 检视。（YouTube EPmZ-dhntnkCQ，[13264.96-14136.88]，L1）
- Brooks Davis 阐述 CHERI 能力架构的 FreeBSD 集成路线：团队目标在 FreeBSD 16 至少交付空间安全支持、时间安全视进度而定；上游选择覆盖 RISC-V Y 标准（目标 tier 2）与 Morello 两类硬件，后者被视为终将被蒸馏的超集架构；策略上内核支持先行、纯能力模式起步并明确拒绝混合模式，再依次推进用户态库、运行时链接器与基于链接器的隔离仓， heap 时间安全列为更高风险的后续阶段；机内相关改动量级与一次 RISC-V 移植相当，而 CheriBSD 的先行积累被其视为 FreeBSD 及其他 BSD 相对 Linux 的先发优势。（YouTube EPmZ-dhntnkCQ，[18933.2-19045.52]，L1）
