## 133.1.2 VIMAGE/VNET 默认启用与网络虚拟化成熟

**要点**：VIMAGE（VNET 虚拟网络栈）在 FreeBSD 12.0 GENERIC 内核中正式默认启用，结束了自 FreeBSD 8.0（2009）引入以来长达近十年的实验性状态。VIMAGE 允许每个 **jail(8)** 拥有独立的网络栈实例——包括独立的路由表、接口集合、防火墙规则、套接字缓冲区等网络状态，是云环境与容器化部署的关键基础设施。VIMAGE/VNET 的主要开发者包括 Bjoern Zeeb（bz@）、Marko Zec 等人，FreeBSD Foundation 赞助了部分稳定性工作。VNET 默认启用后，与 **pf(4)** 可在 **jail(8)** 中使用（12.0 另一个新特性）配合，使每个 jail 可拥有独立的 pf 防火墙规则集。同期 NUMA（Non-Uniform Memory Access）支持也在 amd64 GENERIC 与 MINIMAL 内核配置中默认启用，优化多路 CPU 系统的内存访问性能。

**史料**：FreeBSD 12.0-RELEASE Announcement（“The VIMAGE kernel configuration option has been enabled by default”、“The NUMA option has been enabled by default in the amd64 GENERIC and MINIMAL kernel configurations”）、**VNET(9)** 手册页、Bjoern Zeeb 关于 VNET 的技术演讲与邮件列表提交、FreeBSD Quarterly Status Reports 网络章节、GENERIC 内核配置文件中 `options VIMAGE` 的默认启用提交。 ［A］

**史观**：总纲第 9 条——经验优先：VIMAGE/VNET 是一个典型的“复杂内核功能经过长期实践检验最终进入默认配置”案例。网络虚拟化本质上是给内核网络子系统引入了一整套“实例化”机制——每个网络状态都需要从全局变量变为 per-instance 变量，这涉及数千行代码的重构。VIMAGE 从实验性选项到默认启用耗时近十年，体现了 FreeBSD 以运行经验与稳定性验证为准绳、“不到成熟不默认”的工程哲学。

**辨析**：部分资料称“VNET 在 11.x 已稳定可用”——11.x 时期 VIMAGE 确实可通过自定义内核启用，但 GENERIC 内核默认不带 `options VIMAGE`，用户需重编译内核；12.0 是 GENERIC 首次默认包含此选项。VNET 默认启用不等于网络栈完全虚拟化无缺陷——12.x 与 13.x 时期仍有 VNET 相关的稳定性修复，特别是模块加载/卸载时的资源泄漏问题。**pf(4)** 在 jail 中的支持在 12.0 为初始状态，部分高级功能（如 ALTQ 队列规则）在 jail 环境中仍有限制。

**文献**：FreeBSD **VNET(9)**/**jail(8)**/**pf(4)** Manual Pages [Z]；FreeBSD 12.0-RELEASE Announcement [Z]. 2018；Zeeb B. VIMAGE: Virtualized Network Stacks [C]//BSDCan/EuroBSDCon various years.

## 133.1.3 工具链现代化——lld 默认链接器与 x86 架构 GCC 移除

**要点**：FreeBSD 12.0 在工具链领域完成三项重要变更：①lld（LLVM 链接器）成为 amd64、i386、armv7 架构的默认引导链接器（bootstrap linker，r334391 for amd64, r336901 for i386, r337057 for armv7，均由 FreeBSD Foundation 赞助），取代了使用数十年的 GNU ld（GPL 许可）；②GCC 4.2.1 从 x86 架构的基础系统构建中移除（commit r338562，Warner Losh 于 2018 年 9 月提交），amd64/i386 全面使用 Clang/LLVM 工具链编译，但 sparc64、powerpc、powerpcspe、mips 等非 x86 架构在 12.x 仍使用 GCC 4.2.1；③WITH_REPRODUCIBLE_BUILD 选项默认启用（r338642，FreeBSD Foundation 赞助），使构建输出具有确定性，相同源码应产生相同二进制文件；④ 新增 WITH_RETPOLINE 选项（r340773，FreeBSD Foundation 赞助）以启用 Spectre v2 漏洞的 retpoline 编译器缓解。此外，legacy **gdb(1)** 被移至 /usr/libexec 仅用于 **crashinfo(8)** 内核崩溃分析，交互式调试推荐使用 **lldb(1)** 或 ports 中的现代 gdb。

**史料**：FreeBSD 12.0-RELEASE Release Notes（Userland Application Changes、Userland Configuration Changes 章节）、commit r334391/r336901/r337057（lld 默认链接器）、r338562（GCC 从 x86 移除）、r338642（可重现构建默认）、r340773（RETPOLINE 选项）、r317416（gdb 移至 libexec）。 ［A］

**史观**：总纲第 13 条——法律与道德是利益分配：工具链从 GPL 组件向 BSD/MIT 许可组件的迁移是许可证利益结构驱动工程决策的典型案例。GCC 4.2.1 是 2007 年发布的 GPLv2 版本，而 GCC 4.4+ 采用 GPLv3 许可证，FreeBSD 因 GPLv3 的 copyleft 约束无法升级新版 GCC；Clang/LLVM 采用 BSD-style 许可证，无 copyleft 限制，成为 FreeBSD 工具链的自然选择。这一迁移从 FreeBSD 10.0（2014）x86 默认使用 Clang 开始，至 12.0（2018）x86 完全移除 GCC 4.2.1 基本完成。

**辨析**：“GCC 完全移除”的说法在 12.0 时期不准确——如前所述，非 x86 架构仍依赖 GCC 4.2.1；GCC 从整个源码树完全移除（包括所有架构）发生在 FreeBSD 13.0。lld 作为默认引导链接器不等于系统所有地方都使用 lld——12.0 中 lld 主要用于 world/kernel 的构建过程（bootstrap 和 build 阶段），最终链接仍可能在某些场景下使用 BFD ld；lld 成为全系统默认链接器在后续版本进一步完善。可重现构建（reproducible builds）在 12.0 为默认启用但并非所有软件包都已实现完全确定性输出，这是一个持续多年的项目。

**文献**：FreeBSD 12.0-RELEASE Release Notes Toolchain/Userland sections [Z]. 2018；commit r334391, r336901, r337057, r338562, r338642, r340773 [Z]. svn.freebsd.org. ［A］

## 133.1.4 OpenSSL 1.1.1a 与 TLS 1.3 时代

**要点**：FreeBSD 12.0 将 OpenSSL 升级至 1.1.1a 版本（r340711），这是 OpenSSL 项目于 2018 年 9 月发布的 LTS（长期支持）版本，首次正式支持 TLS 1.3 协议（RFC 8446）。TLS 1.3 相比 TLS 1.2 具有显著改进：握手延迟从 2-RTT 减少至 1-RTT（0-RTT 可选）、移除了大量老旧不安全的密码套件（如 RSA 密钥交换、SHA-1、MD5、3DES、RC4 等）、强制使用前向保密（Forward Secrecy）。Unbound DNS 解析器更新至 1.8.1 并默认启用 DANE-TA（DNS-Based Authentication of Named Entities, Trust Anchor）支持（r339278/r339303）。OpenSSH 更新至 7.8p1（r338561），**sshd(8)** 新增 Capsicum 能力模式沙箱支持（r339216）。新增 **getrandom(2)** 系统调用与 **getentropy(3)** 库函数（r331279），兼容 Linux 与 OpenBSD 实现，为用户态程序提供安全的随机数来源，避免直接访问 /dev/random 的复杂性。WPA 工具更新至 2.6。

**史料**：FreeBSD 12.0-RELEASE Release Notes（Contributed Software 章节）、commit r340711（OpenSSL 1.1.1a）、r339278/r339303（Unbound/DANE-TA）、r338561（OpenSSH 7.8p1）、r339216（sshd Capsicum）、r331279（getrandom/getentropy）、OpenSSL 1.1.1 Release Notes（openssl.org）、RFC 8446（TLS 1.3 协议规范）。 ［A］

**史观**：总纲第 22 条——知识注定过时：TLS 1.3 的部署标志着互联网加密协议进入“现代密码学”时代，TLS 1.2 时代的密码学知识随老旧不安全套件的移除而批量过时。FreeBSD 作为 Netflix、Yahoo! 等大型互联网公司的服务器操作系统，其基础系统的 TLS 栈升级直接影响全球互联网流量的安全性。OpenSSL 1.1.x 系列相对于 1.0.x 系列进行了大规模 API 重构（许多数据结构变为不透明、初始化函数变化），旧有接口知识随之失效，FreeBSD ports 中大量软件需要适配才能与 OpenSSL 1.1.1 配合使用，这是 ports 集合在 12.0 周期的主要适配工作之一。

**辨析**：OpenSSL 1.1.1a 中的“a”后缀表示这是 1.1.1 系列的首个补丁版本（修复了 1.1.1 初始发布后的问题），不是预发布版本。TLS 1.3 在 12.0 发布时已获 IETF 批准（RFC 8446 于 2018 年 8 月发布），但浏览器与服务器生态系统的完全迁移花费了数年时间。FreeBSD 12.0 中 Kernel TLS（kTLS，TLS 加密/解密在内核中进行以降低 CPU 开销）为初步支持状态——Netflix 主导的 kTLS 发送端卸载（TLS transmit offload）在 12.x 时期逐步完善，接收端卸载（receive offload）在后续版本成熟。

**文献**：FreeBSD 12.0-RELEASE Release Notes Security/Contributed Software sections [Z]. 2018；Rescorla E. RFC 8446: The Transport Layer Security (TLS) Protocol Version 1.3 [S]. IETF, 2018；OpenSSL Project. OpenSSL 1.1.1 Release Notes [EB/OL]. openssl.org, 2018；commit r340711, r331279 [Z]. svn.freebsd.org. ［A］
