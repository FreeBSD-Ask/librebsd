# 133.5 架构支持变化——RISC-V 引入、sparc64 退役与 ARM64 成熟

## 133.5.1 RISC-V（riscv64）架构引入

**要点**：FreeBSD/riscv64（64 位 RISC-V）移植工作主要由 Ruslan Bukin（br@）主导，在 FreeBSD 11.x 时期开始于 -CURRENT 分支，12.x 时期持续开发但未提供正式发布镜像直至 12.4-RELEASE（2022.12.5）。RISC-V 是 2010 年代兴起的开源指令集架构（ISA），由 UC Berkeley 发起、RISC-V International 标准化，以许可证自由（免授权费）、模块化扩展设计为特征，被视为 x86/ARM 之外的第三极。FreeBSD/riscv64 在 12.x 时期支持 SMP 多核、UART 控制台、virtio 设备（在 QEMU 中运行）、UEFI 引导等核心功能，但驱动支持有限，主要在 QEMU 虚拟机与少数开发板（如 SiFive HiFive Unmatched）上运行。RISC-V 在 FreeBSD 12.x 为 Tier 3 状态（实验性支持），FreeBSD Foundation 在 2020 年代持续资助 RISC-V 移植工作。

**史料**：FreeBSD 12.4-RELEASE Announcement（riscv64 加入发布架构列表）、Ruslan Bukin RISC-V 移植 commit log、FreeBSD Wiki RISC-V 页面（wiki.freebsd.org/riscv）、FreeBSD Foundation 年度报告（RISC-V 赞助记录）、FreeBSD Quarterly Status Reports RISC-V 章节。 ［A］

**史观**：总纲第 4 条——分离聚合是永恒规律：RISC-V 是计算架构领域的重要新变量，但在 12.x 时期（2018-2022）仍处于非常早期阶段。FreeBSD 对 RISC-V 的支持体现了操作系统项目对新兴架构的前瞻布局——等到 RISC-V 硬件生态成熟再移植将错失时机，但过早投入则维护成本高且用户基数小。与 Linux 相比，FreeBSD 的 RISC-V 支持起步时间相近但人力投入更少，成熟度落后 Linux RISC-V 约 1-2 年。

**辨析**：RISC-V 在 12.0-12.3 中完全没有发布镜像，仅存在于 -CURRENT 与源码树中；12.4 首次提供 riscv64 发布镜像，官方将其列入发布架构，但其 tier 归属尚处过渡状态〔存疑：旧文“标记为 Tier 3”与“提供发布镜像通常对应 Tier 2”两种口径冲突，难以确证〕；riscv64 升为 Tier 2 在 FreeBSD 13.x/14.x。RISC-V 32 位（riscv32）在 FreeBSD 中不支持。RISC-V 的“Free”（自由）与 FreeBSD 的“Free”（自由）在词源与理念上的呼应常被社区讨论，但 FreeBSD 支持 RISC-V 的主要动机是架构多元化而非意识形态。

**文献**：FreeBSD 12.4-RELEASE Announcement [Z]. 2022；Waterman A, Asanović K. The RISC-V Instruction Set Manual [R]. RISC-V International, 2019；FreeBSD Foundation Annual Reports 2019-2022 [R]（RISC-V sponsorship）.［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

## 133.5.2 sparc64 架构退役

**要点**：sparc64（Sun UltraSPARC 64 位）架构在 FreeBSD 12.4-RELEASE 中正式从发布架构列表移除，结束了自 FreeBSD 5.0-RELEASE（2003.1）以来长达 19 年的正式支持。sparc64 由 Jake Burkholder、Kris Kennaway、Marius Strobl（marius@）等人移植与维护，支持 Sun UltraSPARC 工作站/服务器（Sun Blade、Sun Fire 系列）与 Oracle SPARC T 系列服务器。退役原因：①Oracle 于 2017 年停止 SPARC 处理器路线图开发（SPARC M8 于 2017 年发布后无后继型号），硬件生态终结；②Clang/LLVM 对 sparc64 后端支持长期滞后，sparc64 在 12.x 仍依赖 GCC 4.2.1 构建；③ 主要维护者 Marius Strobl 在 2018 年后逐步减少活动，12.4 Release Team 已无其名；④sparc64 用户基数极小（主要是怀旧 Sun 工作站爱好者），工程资源投入产出比不合理。sparc64 从 12.4 移除时 FreeBSD 13.0（2021.4）也已不再支持 sparc64。FreeBSD 12.3-RELEASE（2021.12.7）是最后一个正式支持 sparc64 的版本，sparc64 代码在源码树中的移除并非一次完成，而是贯穿 13.x 周期渐进收尾（13.0 之后仍有清理残留引用的提交）。

**史料**：FreeBSD 12.3/12.4-RELEASE Announcements（架构列表对比确认 sparc64 在 12.3 存在、12.4 移除）、Marius Strobl commit log 活动变化、Oracle SPARC 路线图终止公告、FreeBSD Platforms 页面各版本存档。 ［A］

**史观**：总纲第 4 条——分离聚合是永恒规律：sparc64 的退役不仅是一个架构的淘汰，更标志着 Sun Microsystems 硬件时代的彻底终结。Sun 是 BSD 的发源地之一（比尔·乔伊（Bill Joy）是 Sun 联合创始人，SunOS 基于 4.2BSD/4.3BSD），UltraSPARC 工作站曾是 1990 年代 BSD 黑客的标志平台。FreeBSD 对 sparc64 长达 19 年的支持，是对 Sun/SPARC UNIX 谱系最后的守灵。

**辨析**：旧稿曾以“ch第 83 章”的残缺交叉引用称“12.4-RELEASE（2023.12）为最后支持 sparc64 的版本”（现行第 83 章为 UNIX 版权归属争议与 Novell 卖 SCO，该引用已断链〔存疑：所称文件无法定位〕）——经 12.3 与 12.4 Announcement 交叉验证，此说法有误：12.3 最后包含 sparc64，12.4 已移除 sparc64 并新增 riscv64/powerpc64le；12.4 发布日期为 2022 年 12 月 5 日而非 2023 年 12 月。现有文件称“GCC 4.2.1 从 base 完全移除”——如前所述，12.x 时期 GCC 仍用于 sparc64/powerpc 等架构。NetBSD 与 OpenBSD 仍保留对 sparc64 的支持，反映了不同 BSD 项目在架构支持策略上的差异。

**文献**：FreeBSD 12.3/12.4-RELEASE Announcements [Z]. 2021/2022；Oracle SPARC End-of-Life announcements [Z]. 2017.［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

## 133.5.3 arm64/aarch64 持续成熟（Tier 2）

**要点**：FreeBSD/arm64（AArch64）在 12.x 时期继续以 Tier 2 架构状态成熟发展：12.0 起提供正式发布镜像（延续 11.0 的支持），支持 AWS Graviton/Graviton2 等 ARM 服务器、Raspberry Pi 3/4（12.x 后期完善 RPi 4 支持）、SoftIron Overdrive、Pine64 等平台；12.1 起 AWS 正式提供 arm64 AMI 镜像；PCIe、USB、SATA、网络驱动持续完善；**bhyve(8)** 对 arm64 的支持在 12.x 开始引入但处于实验状态；arm64 在 12.x 仍为 Tier 2（best-effort 支持），升级为 Tier 1 发生在 FreeBSD 13.0-RELEASE（2021.4.13）。Andrew Turner（andrew@）是 arm64 移植的主要维护者，FreeBSD Foundation 持续赞助。与同期 Linux 相比，FreeBSD/arm64 在服务器平台（AWS Graviton、Ampere Altra）可用性较好，但在桌面/笔记本 ARM 设备（Apple M 系列、Qualcomm Snapdragon）支持方面落后。

**史料**：FreeBSD 12.x 各版本 Announcement（Availability 章节列出 aarch64 为发布架构、AWS arm64 AMI 从 12.1 起提供）、Andrew Turner BSDCan/various 演讲、FreeBSD Foundation 年度报告（arm64 赞助记录）、FreeBSD Platforms 页面 Tier 定义。 ［B］

**史观**：总纲第 13 条——法律与道德是利益分配〔存疑：原挂“硬件支持”不在 25 条总纲权威表，按云厂商商业利益驱动架构成熟语义暂挂〕：arm64 在 12.x 时期从“新兴架构”逐渐成长为“主流架构候选”，这与 AWS Graviton 系列（2018 年 Graviton 1、2020 年 Graviton 2）的商业成功密切相关。云厂商主动提供 ARM 实例并向 FreeBSD 贡献驱动支持，是 FreeBSD/arm64 成熟的重要推动力。Apple M1/M2 系列（2020-2022）虽在桌面市场掀起 ARM 浪潮，但 FreeBSD 对 Apple Silicon 的支持在 12.x 基本为零（Asahi Linux 项目在 13.x/14.x 时期才有相关 FreeBSD 移植尝试）。

**辨析**：arm64 升为 Tier 1 不在 12.x 时期——FreeBSD 13.0-RELEASE（2021.4.13）才将 aarch64 升为 Tier 1。Raspberry Pi 4 于 2019 年 6 月发布，其 FreeBSD 支持在 12.x 后期逐步完善，但 12.0-12.2 时期 RPi 4 支持不完整。12.4 提供的 arm64 虚拟机镜像在 QCOW2/VHD/VMDK/raw 格式中可用。

**文献**：FreeBSD 12.x RELEASE Announcements [Z]. 2018-2022；FreeBSD Platforms page [EB/OL]. freebsd.org/platforms/；Turner A. FreeBSD on ARM64 updates [C]//BSDCan various years.

## 133.5.4 PC98 与 armeb 架构在 12.0 正式退役

**要点**：FreeBSD 12.0-RELEASE 正式移除 PC98（NEC PC-9801/9821）与 armeb（32 位 big-endian ARM）架构支持。PC98 由 John Baldwin（约翰·鲍德温） 在 commit r312910（2017.2.1）从 -CURRENT 中移除，12.0 生效，结束了自 FreeBSD 2.2-RELEASE（1997）起约 21 年的支持。PC98 是为兼容日本 NEC PC-9801 系列（1982 年发布，1990 年代日本市场占有率超 60%）而衍生的 i386 变体，长期仅有 NAKAJIMA Hiroyuki〔存疑：原文“NAKaccepI”系人名讹变，一说为 NAKAJIMA，以一手来源核验为准〕等少数维护者。armeb 移除原因与 PC98 类似：32 位 big-endian ARM 设备市场趋近零（ARMv6/v7/AArch64 均为 little-endian），Clang/LLVM armeb 后端支持不完整，用户基数极小。11.4-RELEASE（2020.6）为最后支持 PC98 与 armeb 的版本。移除的还有 xlint（传统 lint 工具）、**asf(8)**（被 kgdb 内置功能取代）、**ctm(1)**（标记为将在 13.0 移除）。

**史料**：commit r312910（PC98 移除）、FreeBSD 12.0-RELEASE Release Notes（Obsolete Files/Removed Features 章节）、freebsd-pc98/freebsd-arm 邮件列表归档。 ［A］

**史观**：专题语（不设总纲条号；原挂“第 5 条——技术债务与代码考古”系伪标签，权威表第 5 条为“没有必然性，只有偶然性”）：PC98 与 armeb 的移除是“代码大扫除”的一部分——保留无法测试、无人维护的代码是对工程资源的浪费，每次架构移除都简化了代码树、降低了新开发者的认知负担。但移除也意味着历史文化信息的流失——PC98 曾是 FreeBSD 全球化努力的见证，标志着 BSD 在日本市场的历史存在。

**辨析**：PC98 退役 commit r312910 时间为 2017.2.1，生效于 2018.12.11（12.0 发布），间隔近两年因 12.0 多次延期。armeb 移除的具体 commit 号未在 Release Notes 中显式标注，但源码树中相关代码与 PC98 同期清理。

**文献**：commit r312910 [Z]. svn.freebsd.org, 2017；FreeBSD 12.0-RELEASE Release Notes Removed Features section [Z]. 2018. ［A］
