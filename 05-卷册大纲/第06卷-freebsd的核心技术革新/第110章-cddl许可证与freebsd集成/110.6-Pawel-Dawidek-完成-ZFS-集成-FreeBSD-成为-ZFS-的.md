# 110.6 Pawel Dawidek 完成 ZFS 集成——FreeBSD 成为 ZFS 的 “一等公民” 操作系统，根因在于 BSD 许可证与 CDDL 兼容（CDDL §3.5 明确允许与 BSD 许可证代码混合分发）

## 110.6.1 Dawidek 移植 ZFS 的技术路线

**要点**：Paweł Jakub Dawidek（波兰开发者，FreeBSD src committer，当时负责 GEOM 存储框架）于 2006 年启动 ZFS 到 FreeBSD 的移植工作，移植的核心工程挑战是 ZFS 深度依赖 Solaris 内核 API——包括 vnode 操作、kmem 内存分配器、taskq 任务队列、vfs 层接口、condvar 条件变量、mutex/sx/rwlock 锁原语、cyclic 时钟等；Dawidek 的解决方案是在 src/sys/cddl/compat/opensolaris/目录下实现一个 Solaris 内核 API 兼容层（solaris.ko 内核模块），将 Solaris 特定 API 映射到 FreeBSD 原生 API；ZFS 代码本身作为独立内核模块（zfs.ko 和 opensolaris.ko）存放在 src/sys/cddl/contrib/opensolaris/uts/common/fs/zfs/目录，以 vendor branch 方式维护，尽量减少对 ZFS 上游代码的改动以利于后续同步

**史观**：总纲第 6 条——技术路线分化：Dawidek 的兼容层移植策略是一个关键工程决策——通过在 BSD 内核中模拟 Solaris API 而非修改 ZFS 代码适配 BSD，FreeBSD 得以在后续 15 年里持续从上游（illumos/OpenZFS）合并新功能，而无需承担巨大的代码分叉维护成本；这一决策也体现了 BSD 内核工程文化中的 “最小侵入” 原则

**辨析**：Dawidek 移植的精确 commit 时间线经 freebsd.duckdb L2.3.1.zfs 查询与 `commits` 表、`commit_files` 表交叉验证〔原标注 netbsd.duckdb 系挂库讹误，相关哈希仅存于 freebsd.duckdb〕——ZFS 特性引入周期的首条相关 commit 为 `7ee07175afcf33fd06dc817dd28ec220b40a3a16`，author = Pawel Jakub Dawidek（<pjd@FreeBSD.org>），author_date = 2006-11-16，标记 ZFS 移植工作的实际启动时间早于主干导入近 5 个月；ZFS 主干导入 commit 为 `f0a75d274af375d15b97b830966b99a02b7db911`，作者 Pawel Jakub Dawidek（<pjd@FreeBSD.org>），author_date = committer_date = 2007-04-06T01:09:06Z，message_subject 为 “Please welcome ZFS - The last word in file systems.”；该 commit 同时引入 `sys/cddl/contrib/opensolaris/` 目录下 ZFS 源文件（acl_common.c 等）以及 `sys/cddl/compat/opensolaris/` 兼容层代码；原大纲据早期邮件列表存档引用 svn revision r171309，但该 r 编号在 2020 年 FreeBSD SVN-to-Git 迁移后已不再作为主引用，Git commit hash 为当前权威追溯依据；FreeBSD 7.0-RELEASE（release/7.0.0 tag 实测两枚：2008-01-15T02:29:14Z、2008-02-24T03:11:57Z；2008-02-27 系发布日而非 tagger_date）正式发布包含 ZFS；FreeBSD 7.0 中 ZFS 版本为 ZFS version 6，随 FreeBSD 版本更新逐步跟进 ZFS pool version 和 feature flags 演进；0 信任原则提示：commit_hash 经 SVN-to-Git 迁移重算，但 author/committer 字段一致（<pjd@FreeBSD.org>）且与 BSDCan 2007 演讲时间吻合，采信度高；另经邮件列表库验证通过（freebsd-advocacy，Robert Watson 2007-04-06 转发 “ZFS committed to the FreeBSD base. ## 110.6.2 BSD 与 CDDL 兼容的法律基础

**要点**：BSD 与 CDDL 兼容性的法律基础建立在两个关键点上：第一，CDDL §3.5 明确规定 "Covered Software may be distributed with other software under different licenses"，即 CDDL 代码可以与其他许可证代码聚合分发；第二，BSD 许可证（2-Clause 和 3-Clause）是 permissive 许可证，不对被许可人施加 “衍生作品必须以相同许可证发布” 的 copyleft 义务；两者互不冲突，因为 CDDL 的文件级 copyleft 仅约束 CDDL 文件本身，BSD 许可的 FreeBSD 内核文件不受 CDDL 影响；FreeBSD Core Team 和 FreeBSD 基金会在引入 ZFS 前进行了法律审查，确认 CDDL/BSD 兼容性不存在问题；罗伯特·N. M. 沃森（Robert Watson）（FreeBSD Core Team 成员、安全官员）是这一法律评估的主要推动者之一

**史料**：CDDL §3.5 原文（opensource.org/licenses/CDDL-1.0）；BSD 2-Clause/3-Clause 许可证文本；FreeBSD Core Team 2006-2007 年关于 ZFS 许可的邮件列表讨论（<freebsd-arch@freebsd.org> 存档）；FreeBSD 基金会 2007 年 ZFS 法律评估 ［A］

**史观**：总纲第 22 条——开源运动：BSD 与 CDDL 的兼容性从根本上说是 “permissive + weak copyleft” 组合的自然结果——permissive 许可证（BSD/MIT/ISC）不对下游施加 copyleft 限制，因此可以与任何其他开源许可证（包括 GPL、CDDL、MPL）的代码在同一作品中共存；这与 GPL（strong copyleft）形成鲜明对比

**辨析**：常被忽略的一点是：macOS（Darwin 内核）同样集成了 ZFS 的早期移植版本——Apple 于 2007-2009 年间曾在 Mac OS X 10.5 Leopard 中包含 ZFS 只读支持（该特性系 Mac OS X Server 10.5 所载，客户端版本仅 beta），但在 Mac OS X 10.6 Snow Leopard 中移除了 ZFS 支持，原因推测与 CDDL 许可争议及 Apple 转向 APFS 有关；FreeBSD 和 macOS 同为 BSD 血统操作系统，都能集成 ZFS，印证了 BSD 许可证的灵活性

**文献**：FreeBSD Core Team. (2007). *ZFS Integration License Review*. freebsd.org; Open Source Initiative. *BSD 2-Clause License*; Open Source Initiative. *CDDL 1.0*; Robert Watson's FreeBSD mailing list posts on ZFS (2007). ［A］

- 技术路径上，受访者归纳移植可行的三重条件：ZFS 代码整洁且多数可在用户态编译，Sun 侧为可移植性投入充分；FreeBSD 与 Solaris 内核 API 相近程度远超 FreeBSD 与 Linux；他自建的 Solaris 兼容层虽自嘲“不甚体面”（692.05-701.13），却将本方改动与上游差异压至最小，得以跟上 Sun 时期 ZFS 的高速迭代。最大障碍在 VFS 层集成——他称其为内核中最复杂、充满“隐秘知识”的部分（744.45-747.29），并以亲身体验解释此前多次文件系统移植失败之因；FreeBSD VFS 代劳缓冲等事务的设计，对 ZFS 这类自带缓冲策略与文件区间锁的复杂文件系统反而构成掣肘。（BSD Now EP62，[650.77-853.73]，L1）

- Dan Langille 把 ZFS 概括为合并了文件系统与卷管理器功能的文件系统：zpool 是基本构件，由若干 vdev（虚拟设备，可为单盘、两盘以上镜像或 RAID Z）聚合而成；文件系统经 zfs create 在池内分层创建、自父级继承属性，并可挂载到与 ZFS 名无关的任意路径；他反复强调池的冗余与恢复能力位于 vdev 层而非池层——损失一个 vdev 即失去整个池，设计存储池时须时刻记住这一约束；相较 UFS 按分区划拨空间、/usr 满后以符号链接搬迁的旧习，池把全部空间统一调度。（YouTube EPpN7OLChclH8，[357.12-585.839]，L1）
- 关于 RAID Z 的语义，讲者辨正流传误解：RAID Z 不是 RAID 5 或 RAID 6，也没有专用校验盘——RAID Z n 的含义是阵列中任意 n 块盘可失效而无数据丢失；原版文档把这些盘涂色标作“校验盘”，曾令用户误以为只能丢那几块指定的盘；RAID Z 的真正意义是为你赢得更换故障盘的时间，越早更换越好；镜像则只要剩一块盘仍能工作。（YouTube EPpN7OLChclH8，[373.28-434.639]，L1）
- 讲者把数据完整性列为 ZFS 的头号卖点：其元数据自上而下逐层校验，读盘结果与校验和不符即报告数据损坏，而无校验的文件系统无从得知；在镜像或 RAID Z 的冗余之内，ZFS 能从别处取得正确数据自动修复错误，系统照常运行而不为人所觉；scrub 读取全量数据核对校验和，属预防性手段，他每周运行并建议启用，可在磁盘隐患扩大成灾之前发现；另须监控池容量，尽量勿超八成、绝勿满盘。（YouTube EPpN7OLChclH8，[1342.72-1462.799]，L1）
- 讲者给出一整套运维准则：换盘先以 gpart 把序列号作卷标识别故障盘，旧盘若仅降级尚能工作应留在池内直至 zpool replace 完成，以免移除后另一块盘再失效而全池俱毁；勿用 RAID 卡——RAID 卡自行“修复”后向系统报告驱动器已死，剥夺 ZFS 自愈的机会，应使用 HBA（部分 RAID 卡可刷写成 IT 模式，FreeBSD 项目维护有兼容清单）；bectl 与 beadm 管理的引导环境把内核与系统装在独立 ZFS 文件系统中，升级或试新内核前先保存旧环境，故障时经引导装载器回切，被他称作“终会救你一命的安全网”，nextboot 则可只指定下一次启动所用内核；配额把后代数据集与快照一并计入，宜设在路径末端；可将 SSD 池挂载到 /var/db/postgres 一类路径实现挂载中嵌套挂载，对系统全然透明；快照只读且不可变，同一主机上的快照不是备份，发送到别处才成为备份，亦可用于取证；以“静止数据库快照加可写克隆”快速搭建开发测试库，用毕即弃；mkdir 之际不妨考虑 zfs create，让照片、项目各成文件系统以便快照、发送与配额。（YouTube EPpN7OLChclH8，[1060.16-2066.8]，L1）
