# 116.1 罗伯特·N. M. 沃森（Robert Watson）团队设计 Capsicum——论文“Capsicum: Practical Capabilities for UNIX”（USENIX Security 2010，Watson、Anderson、Laurie、Kennaway）的核心贡献

## 116.1.1 Capsicum 论文的核心技术贡献

**要点**：Capsicum 由剑桥大学计算机实验室 罗伯特·N. M. 沃森 团队与 Google 合作设计，核心论文“Capsicum: Practical Capabilities for UNIX”于 2010 年 8 月在第 19 届 USENIX Security Symposium（华盛顿特区）发表；作者为 罗伯特·N. M. 沃森（剑桥）、Jonathan Anderson（剑桥）、Ben Laurie（Google）、Kris Kennaway（Google/FreeBSD committer）；论文提出三大核心 OS 原语：能力文件描述符（capabilities，带细粒度权限位的文件描述符）、能力模式（capability mode，通过 **cap_enter(2)** 系统调用进入的单向沙箱态，进程丧失对全局命名空间的访问权）、进程描述符（process descriptors，以文件描述符替代 PID 的能力中心进程管理）；论文原型基于 FreeBSD 8.x 开发，同步完成了 tcpdump、dhclient、gzip、OpenSSH 以及 Chromium 浏览器的沙箱改造演示

## 116.1.2 Watson 团队的设计过程

**要点**：Capsicum 设计始于 2008 年前后，Watson 在 FreeBSD TrustedBSD MAC 框架的多年工作经验使他认识到：基于强制访问控制（MAC）标签的安全模型配置复杂、容易出错，且与 POSIX API 的全局命名空间访问模式存在根本冲突；设计团队（剑桥的 Watson、Anderson 与 Google 的 Laurie、Kennaway）确定了“混合能力模型（hybrid capability system）”路线——不推翻传统 UNIX 权限模型，而是允许进程在需要时自愿进入能力模式（capability mode），在该模式下丧失所有 ambient authority（环境权限），仅能通过已持有的能力文件描述符访问资源；Pawel Jakub Dawidek 在 FreeBSD 基金会与 Google 开源计划办公室联合资助下承担了 Capsicum 从研究原型到产品级代码的后续工程化工作

**史料**：剑桥大学 Capsicum 项目 people 页面 cl.cam.ac.uk/research/security/capsicum/people.html；FreeBSD 基金会 2013 年公告“FreeBSD Foundation Announces Capsicum Framework Project”（freebsdfoundation.org/blog/）；LWN.net 2013-04-18 文章“FreeBSD Foundation, Google fund Capsicum framework work”；Watson 博士论文 UCAM-CL-TR-818 第 4-6 章详细记录设计决策过程 ［B］

**史观**：终结与延续〔订正注：原"总纲第 25 条"伪标签去条号，权威总纲 25 为"逻辑是形式主义"〕：Capsicum 的设计过程体现了安全研究从“外围加固”到“内核重构”的转向——MAC 框架（TrustedBSD/SELinux）是在 UNIX 权限模型之外附加安全策略层，而 Capsicum 选择在进程自愿前提下替换权限模型核心；这一设计决策既是 TrustedBSD 项目经验的延续（Watson 是 TrustedBSD MAC 框架的作者），也是对该框架局限性的反思

**辨析**：Capsicum 与 Google 的合作关系需精确描述——Google 是 Capsicum 研究的资助方（Ben Laurie 为 Google 员工，参与设计），Chromium 浏览器是 Capsicum 最早的目标应用之一；但 Google 从未将 Capsicum 作为 Chrome 沙箱的主方案——Chrome 在 Linux 上最终选择 seccomp-bpf（参见 74.6 节），在 FreeBSD 上的 Chromium Capsicum 沙箱长期维护状态不稳定；“剑桥大学独立设计”的说法也不准确——Capsicum 从一开始就是学术界（Cambridge）与工业界（Google）的合作产物

## 116.1.3 与 POSIX 能力模型的范式比较

**要点**：Capsicum 与 POSIX capabilities（Linux capabilities）属于完全不同的能力范式：POSIX capabilities 是对 UNIX root 权限的分割——将 root 的全能特权拆分为 CAP_NET_ADMIN、CAP_SYS_ADMIN 等约 40 个细粒度特权位，仍以“进程持有哪些特权”为中心，保留全局命名空间访问能力；Capsicum 是对象能力模型（object-capability model）——以文件描述符为唯一能力载体，进程进入能力模式后完全丧失全局命名空间访问权（无法以路径名 open 文件、无法访问 PID 命名空间的任意进程、无法动态加载内核模块），仅能通过启动时传入或通过 Unix domain socket 接收的能力文件描述符执行操作；POSIX capabilities 解决的是“root 权限过大”问题（root 被攻破则系统全部沦陷），Capsicum 解决的是“任何进程被攻破都可能造成大规模损害”问题（沙箱内进程被攻破只能损害该沙箱持有的能力范围内的资源）

**史料**：Watson et al. 2010 USENIX Security 论文第 2-3 节（与 POSIX/Linux capabilities 的区分）；LWN.net 2012-02-22 Edge 文章开篇对比"Capsicum takes a very different approach from other capabilities systems (like Linux capabilities or POSIX capabilities)"；**capsicum(4)** FreeBSD 手册页（capability mode 限制列表）；**cap_enter(2)** 手册页；Linux **capabilities(7)** 手册页 ［A］
    FreeBSD 社区论文：[FP-2019-082] CheriABI: Enforcing Valid Pointer Provenance and Minimizing Pointer Privilege in the POSIX C Run-time Environment（Brooks Davis，2019）<https://papers.freebsd.org/2019/davis-asplos-cheriabi/>

**史观**：技术路线分化〔订正注：原"总纲第 6 条"伪标签去条号，权威总纲 6 为"和解优于斗争"〕：Capsicum vs POSIX capabilities 的范式分化是安全架构设计中“身份中心 vs 对象中心”这一根本哲学分歧的体现——POSIX/Linux capabilities 仍以“进程身份（UID/特权位）”为授权基础，Capsicum 则以“对象引用（文件描述符/能力）”为授权基础；这一分化可追溯至 1970 年代 PSOS、Hydra 等系统的能力研究，但在 UNIX 世界中长期处于边缘位置，Capsicum 是首个在主流 BSD 系统中产品化的对象能力实现

**辨析**：LWN Jake Edge 在 2012 年文章开篇说 Capsicum 采取“very different approach”并定性为非主流异类，但通读全文可知 Edge 并非批评 Capsicum——LWN 的标题“Capsicum: practical capabilities for UNIX”是正面的技术介绍，评论区也主要是 Linux 用户询问移植可能性；将该句解读为“将 Capsicum 与 Linux 既有能力体系对立”属于过度诠释，Edge 的对比性描述是技术新闻写作中常用的定位手法；真正的范式差异在于：POSIX capabilities 是对 setuid-root 模型的修补，Capsicum 是对 ambient authority 模型的替换
