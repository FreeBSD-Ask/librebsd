# 116.2 能力（capability）与沙箱（sandbox）的设计哲学——以进程级 capability 替代全局 UID/GID 权限模型，每个进程只能访问其被授予的能力句柄

## 116.2.1 capability 替代 UID/GID 的技术论证

**要点**：传统 UNIX 权限模型以 UID/GID 为核心——root 用户（UID 0）绕过所有内核权限检查，非 root 用户受 DAC（自主访问控制）约束；这一模型存在根本缺陷：(1) Ambient Authority（环境权限）问题——进程继承其运行用户的全部权限，而非仅获得完成任务所需的最小权限；(2) setuid-root 程序被攻破即授予攻击者完整 root 权限；(3) 即使非 root 进程也通常持有远超其需要的文件系统和系统调用访问权；Capsicum 能力模式（capability mode）通过 **cap_enter(2)** 系统调用进入后，进程丧失对全局命名空间的所有访问权——禁止的系统调用类别包括：以路径名为参数的 **open(2)**（必须使用 **openat(2)** 且传入目录能力文件描述符）、**shm_open(2)** 仅允许匿名共享内存、**sysctl(2)** 仅允许约 30 个安全 sysctl 节点（总计约 3000 个中）、**kldload(2)** 禁止加载内核模块、setuid/setgid 二进制执行被禁止；进程只能操作进入能力模式时已持有的文件描述符（通过 **cap_new(3)** 预先包装权限）或后续通过 Unix domain socket 使用 **sendmsg(2)**/**recvmsg(2)** 接收的能力文件描述符

**史观**：哲学思潮：Capsicum 对 ambient authority 的拒绝是最小权限原则（Principle of Least Privilege, PoLP）在 UNIX API 层的彻底工程化实现——Saltzer 与 Schroeder 1975 年经典论文《The Protection of Information in Computer Systems》即已提出最小权限原则，但 UNIX 此后 35 年未在 OS 原语层面真正落实该原则（POSIX capabilities 仅分割 root 权限而非消除 ambient authority）；Capsicum 的“自愿进入沙箱”设计也与 FreeBSD jail 强制隔离模型形成哲学对照——jail 是管理员从外部施加的隔离，Capsicum 是程序自行声明的权限收缩

**辨析**：Capsicum 并非“替代”UID/GID 模型——Capsicum 是混合模型（hybrid capability system），非纯能力系统（pure capability system）：未进入能力模式的进程仍完全运行在传统 UNIX 权限模型下，Capsicum 能力模式是进程可选择进入的附加约束态；这一设计选择降低了应用迁移成本，但也意味着 Capsicum 无法防护不选择进入能力模式的进程；纯能力操作系统（如 KeyKOS/EROS、seL4）从根本上消除 ambient authority，但应用兼容性代价巨大，Capsicum 的混合设计是工程可行性与安全保证之间的权衡

## 116.2.2 进程级能力模型的工程实现

**要点**：Capsicum 在 FreeBSD 内核中的工程实现包括以下核心组件：(1) **capsicum(4)** 内核框架——在 GENERIC 内核中默认编译（options CAPABILITIES 和 options CAPABILITY_MODE，FreeBSD 9.0 即已加入）；(2) **cap_enter(2)** 系统调用——设置进程的 P_CAPMODE 标志，该标志一旦设置不可清除（单向门），子进程自动继承；(3) 能力文件描述符——在普通文件描述符上附加 cap_rights 权限集合（如 CAP_READ、CAP_WRITE、CAP_SEEK、CAP_MMAP、CAP_IOCTL 等），通过 **cap_rights_limit(2)**、**cap_ioctls_limit(2)**、**cap_fcntls_limit(2)** 系统调用逐步收缩权限；(4) **libcapsicum(3)** 用户态库——提供高层 API 简化沙箱创建（**cap_init(3)**、**cap_service_open(3)**、**cap_wrap(3)** 等），封装 fork+fd passing+cap_enter 的标准流程；(5) **cap_new(3)**——将普通文件描述符包装为能力文件描述符并设置初始权限；(6) casperd 守护进程（**casper(3)**/**casperd(8)**）——为沙箱内进程提供受限系统服务（DNS 解析、随机数、文件打开对话框等），避免进程因需要系统服务而持有过多全局权限

**史料**：FreeBSD 9.0-RELEASE Release Notes（CAPABILITIES/CAPABILITY_MODE 选项记录，commit r219129）；FreeBSD 源码 src/sys/kern/kern_cap.c、src/sys/kern/descrip.c（Capsicum 内核实现）；FreeBSD 源码 src/lib/libcapsicum/（libcapsicum 库）；FreeBSD 源码 src/libexec/casper/（casperd 守护进程）；**capsicum(4)**、**cap_enter(2)**、**cap_rights_limit(2)**、**cap_ioctls_limit(2)**、**libcapsicum(3)**、**casper(3)** 手册页 ［A］

**史观**：总纲第 22 条——开源运动：Capsicum 的工程实现采用了“默认编译但不默认启用应用沙箱”的集成策略——FreeBSD 9.0 将 Capsicum 框架加入 GENERIC 内核但不附带任何 Capsicum 化的应用程序（LWN 2012 报道明确记载"9.0 release only contains the kernel changes required for Capsicum but doesn't ship any applications that use the facility"），从 9.1/10.x 开始逐步将基础系统工具 capsicum 化（tcpdump、dhclient、kdump、killall、hostctl 等）；这一渐进策略是 FreeBSD 工程文化的典型特征

**辨析**：casperd 的引入版本经 **freebsd.duckdb** `commits` 表与 `commit_files` 表交叉验证已确认：casperd 首次合入 FreeBSD-CURRENT 的 commit 为 `42a859525652decb08bba47ffaceb769d394175e`（Pawel Jakub Dawidek，2013-12-02T08:21:28Z，subject: "Please welcome casperd daemon. It (and its services) will be responsible for giving access to functionality that is not available in capability mode sandbox. The functionality can be precisely restricted."）；该 commit 引入了 `libexec/casper/` 目录及 dns、grp、pwd、random、sysctl 等服务模块；同日 Dawidek 补加 `lib/libcasper/` 目录（commit `05af64096c3cad1331108f5be2f4662555653de3`，2013-12-02T10:18:25Z，subject: “Forgot to ‘svn add’ lib/libcasper/ directory.”）；由于此合入发生在 FreeBSD 10.0-RELEASE（2014-01-20）发布前约 7 周，casperd 作为独立守护进程随 FreeBSD 10.0 首次正式发布；2013-12-19 commit `f01f7446472b47340fbaddd4d582fa4006df3842`（Dawidek，subject: "Make the world a bit more secure place (hopefully) and turn the casperd on by default."）将 casperd 默认启用；2016-02-25 commit `c501d73c7e2d5c843583084b84bd3e6f68a0047e`（Mariusz Zaborski）将 casperd 从独立守护进程架构重构为 libcasper 库架构（cap_init(3) 时 Casper 从原进程 fork 而非连接外部 daemon），同时移除 libcapsicum 库——因此 “casperd 作为独立守护进程” 的存在时期为 FreeBSD 10.0（2014-01）至 11.0（2016-10）之间；FreeBSD 基础系统中 capsicum 化工具的完整清单随版本演进变化，**tcpdump(1)** 是最常被引用的案例——仅需约两行代码即可在 BPF 设置完成后进入能力模式，但 DNS 解析需要 casper 的 DNS 服务支持；最初 tcpdump Capsicum 改造因 glibc/libc 解析器需要访问 **/etc/resolv.conf** 和网络命名空间导致功能受限，后通过 casper 的 libcasper_dns 服务解决

## 116.2.3 与沙箱模型的设计哲学比较

**要点**：Capsicum 与其他沙箱/隔离模型的哲学差异显著：(1) Capsicum vs chroot/jail——**chroot(2)** 仅改变文件系统根目录，不限制系统调用访问；**jail(8)** 是管理员级强制虚拟化隔离，提供独立 IP、主机名、文件系统视图，但 jail 内 root 仍持有 jail 内的全部环境权限；Capsicum 是进程级自施加沙箱，在进入能力模式后连 jail 内的全局权限都被剥夺；(2) Capsicum vs seccomp-bpf——seccomp-bpf（Linux 3.5+，2012 年）通过 BPF 过滤器限制可使用的系统调用号集合，是系统调用级白名单；Capsicum 不仅限制系统调用，还通过能力文件描述符限制每个文件描述符可执行的操作类型，并彻底切断全局命名空间访问；(3) Capsicum vs OpenBSD pledge/unveil——**pledge(2)**（OpenBSD 5.9，2016 年 5 月）采用系统调用族承诺（promises）模型，进程声明自己将使用哪些类别的系统调用；**unveil(2)**（OpenBSD 6.4，2018 年 10 月）限制文件系统可见路径；Capsicum 通过能力文件描述符提供更细粒度的对象级权限控制，pledge 通过系统调用白名单提供更简单的最小接口暴露

**史料**：FreeBSD **jail(8)** 手册页；Linux **seccomp(2)** 手册页（seccomp mode 2/SECCOMP_FILTER）；OpenBSD **pledge(2)**、**unveil(2)** 手册页；LWN.net 2012-02-22 Edge 文章；Chromium 沙箱设计文档（chromium.googlesource.com/chromium/src/+/HEAD/docs/design/sandbox.md） ［A］

**史观**：技术路线分化：Capsicum、seccomp-bpf、pledge/unveil 三者代表了 2010-2016 年操作系统沙箱技术的三条路线分化：Capsicum 追求对象能力模型的完备性（以文件描述符能力为核心），seccomp-bpf 追求系统调用过滤的通用性（BPF 虚拟机驱动），pledge/unveil 追求 API 极简性（少量系统调用实现大幅攻击面缩减）；这三条路线并非互斥，但反映了不同社区的工程哲学差异：FreeBSD 借鉴学术研究成果（剑桥能力模型理论）、Linux 依赖虚拟机抽象（BPF）、OpenBSD 追求最小化与代码审计可控性

**辨析**：原大纲称 OpenBSD pledge 由“Theo de Raadt（西奥·德·若特） 设计于 2015 年”有两处事实错误：**pledge(2)** 主要设计者是 Ted Unangst（tedu@），Theo de Raadt 是项目领导者但非主设计师；pledge 首次出现在 OpenBSD 5.9 发布于 2016 年 5 月 1 日（非 2015 年）；**unveil(2)** 更晚，出现在 OpenBSD 6.4（2018 年 10 月）；macOS Sandbox（原 Seatbelt）最初基于 FreeBSD TrustedBSD MAC 框架（罗伯特·N. M. 沃森（Robert Watson）本人参与了 Apple 的早期 MAC 框架移植），与 Capsicum 属于不同技术世代

## 116.2.4 能力模型设计史料的文本考据

**要点**：Capsicum 能力模型的理论溯源可至 1970 年代的能力系统研究：剑桥大学 CAP computer（1970s，世界首个能力计算机）、PSOS（Provably Secure Operating System，SRI International，Peter G. Neumann 参与）、Hydra（CMU）、KeyKOS（Key Logic，1980s）、EROS（Extremely Reliable Operating System，Jonathan S. Shapiro，1990s）、Coyotos（EROS 后继）；E 语言（E Rights，Mark Miller 等，1990s）与 Tahoe-LAFS（Least Authority File System，Zooko Wilcox-O'Hearn 等，2007+）是对象能力模型在分布式系统与文件系统中的重要实践；Watson 等人在 Capsicum 论文 related work 节明确引用了这些前驱；Capsicum 的关键创新不在于“发明能力模型”，而在于在保持 POSIX 兼容性的前提下将对象能力模型实用化地嵌入 UNIX——这是先前所有能力系统（均为新设计的非 UNIX 系统）未能做到的

**史料**：Henry Levy 1984 年著作《Capability-Based Computer Systems》（能力系统历史的权威综述，archive.org 可获取完整扫描版）；Watson et al. 2010 USENIX Security 论文 Section 7“Related Work”；Mark Miller et al. 2003 年“Capability Myths Demolished”技术报告；E 语言网站 erights.org；Tahoe-LAFS 项目文档 tahoe-lafs.org ［B］

**史观**：形式主义膨胀：能力模型研究从 1970 年代的 CAP computer、PSOS 到 2010 年的 Capsicum 跨越了四十年，期间经历了形式化验证（PSOS）、商业失败（Intel iAPX 432）、开源实践（EROS/Coyotos）的多次起伏；Capsicum 选择“混合模型”而非“纯能力系统”是对四十年能力系统研究经验的工程化回应——纯能力系统在安全保证上更彻底，但应用兼容性代价使其无法在主流操作系统中落地；形式主义的完备性在此让位于工程实用性

**辨析**：原大纲文献列表多次错误列入“Lucas 2018 'FreeBSD Mastery: Storage Essentials’”——Storage Essentials 是存储主题书籍，与 Capsicum/CHERI 无关，属于模板复制时未清理的无关文献，已全部删除并替换为 Capsicum/CHERI 相关权威文献；原大纲还列入"Skorstengaard, Devriese, Birkedal 2018 'Reasoning about a Machine with Local Capabilities’"——该论文是关于能力机器的形式化推理，属于 CHERI 理论文献但非 Capsicum 核心文献，保留在相关理论章节；原大纲列入"Jolitz & Jolitz 1990s Dr. Dobb's Journal ‘Porting UNIX to the 386’"与 Capsicum 完全无关，系模板错误，已删除

- Capsicum 被界定为面向应用沙箱化的能力框架：既有安全机制或以用户彼此隔离为模型，或依赖顶层密级策略，均不适配应用内部组件失效的场景；Capsicum 令进程进入 capability mode 后无法访问文件系统、System V 共享内存等全局命名空间，并以文件描述符承载类似 object capability 的不可伪造引用，实现细粒度权限传递，从而把进程受损后的可破坏范围压缩到最小。（BSD Now EP39，[1017.09-1141.35]，L1）
- 访谈以 tcpdump 为标杆案例说明沙箱收益：该工具须以 root 运行、携带大量不以安全为设计目标的协议解析器、又常在疑似受攻击时启用，构成特权、脆弱性与攻击窗口的三重叠加；Capsicum 化后其先完成特权初始化再入沙箱，即便被攻破，注入代码也仅能破坏指定输出文件，而无法打开任意文件、改动口令、启用其他网络接口或执行改变网卡行为的 ioctl。（BSD Now EP39，[1157.11-1258.40]，L1）
- Casper 守护进程（命名取自动画角色“Casper the Friendly Ghost”，亦即本期标题“友好沙箱”的出处）作为能力服务提供者，代沙箱内进程完成 DNS 解析等依赖全局命名空间的操作：应用经由初始套接字向 Casper 请求 DNS 服务句柄，取得所需服务后即可切断与 Casper 的连接，再进入不可信数据处理阶段，使沙箱内代码保留查询能力而丧失滥用解析设施的权限。（BSD Now EP39，[1259.67-1389.83]，L1）
- 集成态势方面，Capsicum 内核 API 自 FreeBSD 10 起默认启用；OpenSSH 上游接受改动，使任何支持 Capsicum 的平台上的 OpenSSH 均可受益；FreeBSD 基本系统中 Chromium、dhclient、gzip 等已采用，gzipped 手册页查看即在沙箱中运行；Google 力推移植 Linux，DragonFly BSD 与 OpenBSD 亦有关注；但 API 推广面临“无平台则无应用、无应用则无平台”的双向冷启动困境，团队同时在平台与应用两端推进。（BSD Now EP39，[1264.64-1568.2]，L1）[订正：原 [1264.64-1586.33]，2026-09-30 SenseAudio 重转核对]
- 进行中的后续工作包括改进运行时链接器，使更大更复杂的应用能在沙箱内定位库文件，最终目标是构建通用能力 shell，令未感知沙箱的应用经命令行参数推断所需权限后即可在沙箱中不加修改地运行，作为对 jails 等重型机制的基础性补充。（BSD Now EP39，[1462.46-1508.18]，L1）
- 不可变与只可追加文件标志可上溯至 1980 年代 CSRG 的真实安全困境：当时具有登录权限的协作者凭证外流、木马代码险些混入代码库，促使开发组将 setuid-root 二进制标记为不可变、将日志文件标记为只可追加；据 McKusick 回忆，攻入者既无法替换关键程序，也无法抹去记录其操作与来源的日志，多数人就此放弃并不再返回，他还追述了循线索追踪一名荷兰入侵者至其住所、由荷兰合作者上门探访后入侵骤然停止的轶事。（YouTube EPE04LxKiu79I，[786.67-941.12]，L1）
- jails 为一组进程提供带独立根环境与独立 IP 的受限执行世界：本质上是不可逃逸的 chroot，每个 jail 获得自己的虚拟网络栈与成对虚拟接口，从内部视角自认为独占整机；jail 内 root 可管理本 jail 的进程、文件与端口绑定，却无法看见或向 jail 外进程发信号、无法变更内核变量、无法挂卸文件系统、无法关闭物理网卡或重启系统；随着 ZFS 委派与虚拟网络栈的引入，jail 可行事项持续扩充，其资源占用远低于完整虚拟机，单台服务器可承载数以百计乃至千计的实例。（YouTube EPE04LxKiu79I，[1259.79-1550.19]，L1）
- 随机数体系由 Mark Murray 在 FreeBSD 5.3（2004 年）引入的 /dev/random 奠定：因中断时序、键盘节奏等熵源采集缓慢且总量稀少，系统以真实熵为种子驱动 Yarrow 密码学伪随机数发生器持续输出，并在新熵到达时重置密钥；Yarrow 由熵采集框架、熵累加器、重置密钥机制与生成机制四部分组成，刻意复用经公开文献充分检验的密码学原语而非自行设计；硬件熵源历经 VIA 专用芯片直通输出（早期嵌入式 CPU 跑 Yarrow 需占约两成算力）、Intel RdRand 直通（FreeBSD 9.2 起）到维基解密与斯诺登事件后改为与其它熵源一并经 Yarrow 混合（FreeBSD 11 引入并回移植至 10.0 及以后）且可被管理员关闭的演进；McKusick 并指出 Fortuna 将以自动化的熵源估计取代 Yarrow 的固定算法，而开机与装机时最需要强随机数却熵源最少的矛盾在其看来仍无良解。　[存疑脚注] Intel RdRand 是否实际被掺假设施并无公开确证，演讲所述属防御性信任决策；Fortuna 替换在演讲时点仍是讨论中的方案而非树内现实。（YouTube EPE04LxKiu79I，[1554.43-2381.76]，L1）
- 访问控制列表的标准史在当事人口中是一部标准政治史：POSIX 1003.1e 草案完成约九成时，委员会内反对者刻意拖延六个月令其越过十八个月的制定期限而死亡，各厂商只得自行补齐剩余一成，造成互不兼容的 ACL 实现，Windows 更另立一套；ACL 早在 1990 年代前中期即已存在，却因各系统实现各异而长期无人使用；此后厂商群体补完 POSIX 草案，另一路与 Windows 兼容的语义进入 NFSv4 规范；FreeBSD 在 UFS 上以挂载选项择一启用，两种语义共用同一套 getfacl 与 setfacl 工具，McKusick 建议新部署采用可跨 UFS、ZFS 与 NFS 且与 Windows 互通的 NFSv4 语义。（YouTube EPE04LxKiu79I，[2677.83-2905.76]，L1）
- 审计以问责与入侵检测为目标，围绕 OpenBSM 建立记录体系，须能回答谁在何时对谁做了什么；McKusick 以美国零售商 Target 数据泄露后数周乃至数月才被发觉、四千万客户信息外流六周的事故说明无人查看的审计日志形同虚设，而 FreeBSD 每夜对全系统 setuid 程序清单做差分、只报告二十四小时内新增或变动条目的做法，被视为让报告短到有人真会去看的实践范例；auditd 守护进程负责筛收与分发审计记录，可应对以填满磁盘来压制审计的攻击手法，记录详尽程度被比作强化版 ktrace，数据亦可外送异地保存；他并透露 FreeBSD 基础设施在约一年半前遭入侵后全面重建，二十年未更新的组件被替换。（YouTube EPE04LxKiu79I，[3413.23-3868.19]，L1）
- capsicum 被演讲者称为 FreeBSD 最新加入的安全机制，由 Robert Watson 与剑桥大学计算机实验室团队设计，大量实现工作出自此前将 ZFS 移植入 FreeBSD 的开发者 pav（Pawel Jakub Dawidek）；其思路是把不受信任的大型库从特权程序中拆出、置于能力模式的子进程中运行，仅凭主进程授予的文件描述符与能力行事——cap_enter 之后的进程如入不可逆的 chroot，无法打开绝对路径、无法访问全局名字空间、无法外联网络或落盘藏匿数据，描述符权利可细分至读、写、定位、监听等单项；名字服务器与 tcpdump 等组件已被沙箱化或在推进中，将大库整体置入能力模块只需付出边界穿越的小代价，即可对未经审计的第三方代码获得实质信心；答问中 McKusick 强调 capsicum 能力与 root 特权列表虽形似而目标迥异：前者隔离不可信组件，后者把 root 权限更精细地授予可信主体。（YouTube EPE04LxKiu79I，[3871.39-4365.60]，L1）
