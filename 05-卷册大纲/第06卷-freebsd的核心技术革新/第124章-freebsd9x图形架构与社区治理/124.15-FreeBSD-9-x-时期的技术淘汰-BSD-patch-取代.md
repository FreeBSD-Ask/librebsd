# 124.15 FreeBSD 9.x 时期的技术淘汰——BSD patch 取代 GNU patch 与许可证纯洁化序幕

## 124.15.1 BSD patch 移植的源头与跨项目谱系

**要点**：**patch(1)** 工具由 Larry Wall 开发原始实现，FSF 在此基础上增强为 GNU patch；FreeBSD 长期使用 GNU patch 2.1 早期版本（其中两个文件受 GPL 约束）；OpenBSD 从 patch 2.0 早期版本分叉并以 PD 或无限制许可证替换 GPL 文件，DragonFly BSD 在 OpenBSD 版本基础上进一步增强，NetBSD 采纳 DragonFly 版本；FreeBSD 由 Pedro F. Giffuni（pfg@）从 DragonFly 反向移植并回填 FreeBSD 原有增强；原始 **patch(1)** 由 Larry Wall 开发，FSF 在其基础上增强为 GNU patch，这是 BSD patch 跨项目谱系的完整脉络

**史料**：Pedro Giffuni 2013.1.29 18:42 freebsd-current 邮件列表 [CFT] WITH_BSD_PATCH 原文（含完整谱系叙述）、Andreas Kohn 2006.6.19 PR 99173 原始 bug 报告、pfg 2014.9.19 PR 99173 关闭评论 ［A］

**史观**：总纲第 22 条——开源运动：BSD patch 的跨项目谱系是 BSD 阵营内部 “代码共享-反向移植” 协作模式的典型样本——OpenBSD 起源 →DragonFly 增强 →NetBSD 采纳 →FreeBSD 反向移植，形成四项目循环的代码流，与 GPL 阵营 “中央仓库-下游分发” 模式形成对照

**辨析**：谱系叙述中须区分两个层次——技术源头是 Larry Wall 原始 **patch(1)**，许可证源头是 OpenBSD 替换 GPL 文件为 PD/无限制版本；DragonFly 的 “进一步增强” 具体内容须对照 DragonFly commit log 核实；pfg “反向移植 FreeBSD 原有增强” 表明 FreeBSD 版本与 DragonFly 版本并非简单复制关系，而是双向融合；Andreas Kohn 2006.6.19 提交的原始 PR 在 7 年后才由 pfg 完成，体现 BSD 工程的长期积累特性

**文献**：Pedro Giffuni 2013.1.29 [CFT] WITH_BSD_PATCH（freebsd-current 邮件列表 archives/2013-January/039367.html）；FreeBSD Bugzilla PR 99173（bugs.freebsd.org/bugzilla/show_bug.cgi?id = 99173）；Kohn A. 2006.6.19 lwpatch 提案附件 ［A］

## 124.15.3 功能差异与社区测试过程

**要点**：BSD patch 与 GNU patch 的功能差异：BSD patch 缺失 `-I` 与 `-S` 两个选项（pfg 在邮件中说明 "Both options seem to be obsolete and don't seem to be used in ports"），同时 GNU 与 BSD patch 已使用 `-I` 表示忽略空白字符；pfg 在邮件中呼吁 "please test extensively, report bugs, and submit patches. We would love to use the new patch by default in 10.0 but only testing will let us know when it's ready."；特别鸣谢 Christoph Mallon 移植 perforce diff 支持与 Gabor Kovesdan 完成导入；r253689 是真正使 BSD patch 成为默认的 commit

**史料**：pfg 2013.1.29 18:42 邮件原文（功能差异说明、测试呼吁、特别鸣谢）、FreeBSD 10.0 release notes、freebsd-current 邮件列表 2013.1-2014.9 BSD patch 测试反馈线程、PR 99173 评论历史（pfg 2014.9.19 关闭评论 "This was done in r253689 and preceding commits. BSD-licensed patch is shipping since FreeBSD 10."） ［A］

**史观**：总纲第 17 条——软件工程：BSD patch 引入作为可选构建选项而非立即默认，体现 FreeBSD 项目 “工程优先于意识形态” 的实用主义——即便有许可证纯洁化的法律动机，仍须通过社区测试验证功能等价性方可切换默认

**辨析**：`-I` 与 `-S` 选项的 “obsolete” 判断须对照 ports 集合实际使用情况核实——pfg 的判断基于 “don't seem to be used in ports” 的初步调查，但 “seem” 一词表明该判断存在不确定性；r253689 是真正使 BSD patch 成为默认的 commit，经 freebsd.duckdb freebsd-src 仓库 commits 表与 GitHub freebsd/freebsd-src 仓库一手核验，其提交日期为 **2013-07-26T21:25:18Z**（commit hash `21244d522787c25ce4187cbd9b523e266b6ca8c6`，作者 Pedro F. ## 124.15.4 9.x 时期淘汰史辨析与许可证纯洁化序幕定位

**要点**：FreeBSD 9.x 时期 BSD patch 取代 GNU patch 在 FreeBSD 许可证纯洁化整体进程中具有开端地位——从 2006.6.19 Andreas Kohn 原始提案到 2013.1.29 r246074 首次导入再到 2013.7.26 r253689 完成迁移（BSD patch 成为默认 `patch`，GNU patch 退为 `gnupatch`），整个迁移过程历时 7 年（提案到完成）与 7 个月（首次导入到默认化），BSD patch 是 FreeBSD 历史上第一个为许可证纯洁化目的而替换的 GNU 工具，标志着后续 GCC→Clang、gdb→lldb、GNU grep→bsdgrep、binutils→LLVM、GNU diff3→OpenBSD diff3、dialog→bsddialog 等系列替换工程的序幕

**史料**：Andreas Kohn 2006.6.19 PR 99173 原始提案、pfg 2012.10.24 freebsd-hackers 邮件 "we do need to port and test **patch(1)** from NetBSD or DragonFly to replace GNU patch"、r246074（2013.1.29 gabor 提交首次导入，commit hash `2dd076b84bb1129d0a62b886a4e736a9344b3376`）、r253689（2013.7.26 pfg 提交，commit hash `21244d522787c25ce4187cbd9b523e266b6ca8c6`，commit_subject “Make the BSD-licensed patch the default.”）、pfg 2014.9.19 PR 99173 关闭评论、FreeBSD 10.0-RELEASE Release Notes ［A］

**史观**：总纲第 25 条——终结与延续：BSD patch 的引入既是 GNU patch 在 FreeBSD 基础系统中 “终结” 的开始，也是许可证纯洁化工程 “延续” 的起点——该工程历经 14 年（2012-2026）方在 16.0-CURRENT 完成 base system GPL 清零；9.x 时期 BSD patch 的引入是这一长期工程的第一个具体节点

**辨析**：BSD patch 替换的许可证动机须明确——FreeBSD 长期使用 GNU patch 2.1 早期版本（GPLv2 时代），因 GPLv3 发布后 FreeBSD 项目认为其条款 “对基础组件不可接受” 而无法升级到 GPLv3 版本的 GNU patch，故选择替换为 BSD 许可的替代实现；这一动机与后续 GCC→Clang（GCC 4.2 是最后一个 GPLv2 版本）、GNU grep→bsdgrep 等替换同源；Andreas Kohn 2006.6.19 原始提案与 pfg 2012.10.24 邮件倡议之间的 6 年间隔须还原——Kohn 的提案因当时社区优先级与工程资源限制而长期搁置，pfg 在 2012.10 Google Code-In 任务讨论中重新激活该议题；2013.1.29 距 pfg 2012.10.24 邮件仅 3 个月，表明一旦优先级确认工程进展迅速

**文献**：altusintel.com 2026.7.15 “FreeBSD-CURRENT Base Now GPL-Free”；FreeBSD Bugzilla PR 99173 完整历史；FreeBSD 10.0-RELEASE Release Notes ［A］

## 124.15.5 GNU 阵营对 BSD patch 替代 GNU patch 的批评层

**要点**：BSD patch 替代 GNU patch 的争议虽规模小于 GCC→Clang 迁移，但在 GPL/Linux 阵营仍引发批评，可归纳为四层。第一层为 “功能等价性质疑”：BSD patch 缺失 GNU patch 的 `-I` 与 `-S` 两个选项（pfg 在 2013.1.29 邮件中说明 "Both options seem to be obsolete and don't seem to be used in ports“），但 ”seem" 一词表明该判断存在不确定性，ports 集合之外的脚本或工作流可能依赖这两个选项，以 “似乎过时” 为由删除功能是工程判断而非事实确证。第二层为 “工程必要性质疑”：**patch(1)** 是基础工具而非编译器，替换 GNU patch 的技术收益远小于替换 GCC，且 GNU patch 2.1 早期版本在 FreeBSD base 中已稳定运行多年，不存在 GCC 4.2.1 无法编译 C++11 的工程瓶颈，故替换动机纯系许可证而非工程。第三层为 “意识形态驱动” 批评：BSD patch 替换是 FreeBSD 许可证纯洁化工程的序幕（57.15.4 已定位），与 GCC→Clang 同属 “为许可证纯洁而牺牲功能兼容性” 的教条主义，十余年工具替换消耗本可用于新功能开发的开发者资源。第四层为 “工具链碎片化” 批评：OpenBSD 从 patch 2.0 早期版本分叉、DragonFly 在 OpenBSD 版本基础上增强、NetBSD 采纳 DragonFly 版本、FreeBSD 再从 DragonFly 反向移植——这一跨项目谱系虽体现 BSD 协作，但也加剧了 UNIX 工具的碎片化，同一 **patch(1)** 在不同 BSD 项目中行为可能不一致，与 POSIX 工具一致性原则存在张力。需注意：上述批评系从 GPL/Linux 阵营立场与 FSF 哲学立场综合重构，无单一 FSF 官方文件专门点名批评 BSD patch 替换（BSD patch 替换的知名度远低于 GCC→Clang 迁移），属考据重构而非直接引用。

**史料**：Pedro Giffuni 2013.1.29 18:42 freebsd-current 邮件 [CFT] WITH_BSD_PATCH 原文（`-I`/`-S` 选项说明）、FSF 官方许可证列表（gnu.org/licenses/license-list.html，将 Modified BSD 与 FreeBSD license 列为 “兼容 GNU GPL”）、Stallman《Free Software, Free Society》关于宽容许可证与 copyleft 的哲学论述、freebsd-current 邮件列表 2013.1-2014.9 BSD patch 测试反馈线程。 ［A］

**史观**：总纲第 13 条——法律与道德是利益分配：GPL 阵营的批评反映 copyleft 主义内部的逻辑自洽——若 “自由” 定义为 “用户免于被锁定的自由”，则宽容许可证确为 “较弱的保护”，BSD 阵营替换 GPL 工具实为削弱对用户自由的保护。但该批评同样遮蔽了 BSD 阵营对 “自由” 的不同定义（开发者任意处置代码的自由），双方在各自哲学框架内均自洽，争议的实质是 “自由” 定义权之争而非道德高下之分。

## 124.15.6 FreeBSD 阵营的反批评层——工程必要性与跨项目协作模式

**要点**：FreeBSD 阵营对 GPL 阵营批评的反驳集中于五点。其一，“工程必要性” 反驳：GNU patch 2.1 早期版本中受 GPL 约束的两个文件（57.15.1 已考据）因 GPLv3 发布而升级路径被切断——FreeBSD 项目因 GPLv3 法律条款不可接受（详见第 58 章 58.4.6 关于 GPLv3 §5/§6/§11 的法律分析）而无法升级到 GPLv3 版本的 GNU patch，长期冻结在 2.1 早期版本意味着无法获得 GNU patch 后续的功能改进与 bug 修复，虽 **patch(1)** 不像 GCC 那样面临 C++11 标准支持瓶颈，但冻结本身就是技术债务。其二，“功能等价性” 反驳：pfg 已声明缺失的 `-I`/`-S` 选项 “seem to be obsolete and don't seem to be used in ports”，且 Christoph Mallon 移植了 perforce diff 支持（57.15.3 已记录），功能缺失范围有限且已部分补足。其三，“跨项目协作” 反驳：BSD patch 是 OpenBSD→DragonFly→NetBSD→FreeBSD 的跨项目协作产物（57.15.1 已考据谱系），非 FreeBSD 独立重写或 “挪用”——OpenBSD 先于 FreeBSD 用 PD/无限制许可证替换 GPL 文件，DragonFly 在此基础上增强，FreeBSD 从 DragonFly 反向移植并回填 FreeBSD 原有增强，这是 BSD 阵营内部 “代码共享-反向移植” 协作模式的典型样本，与 GPL 阵营 “中央仓库-下游分发” 模式形成对照。其四，“渐进式工程范式” 反驳：WITH_BSD_PATCH 作为可选构建选项引入（r246074，2013.1.29），r253689 才成为默认，GNU patch 改名 `gnupatch` 而非立即删除——这一 “导入 → 可选 → 默认 → 保留兼容” 的四阶段策略（57.15.2 已考据）体现了 “先验证后切换” 的工程谨慎，非教条主义的断裂式切换。其五，“许可证纯洁化非教条” 反驳：BSD patch 替换与 GCC→Clang 同源，是 GPLv3 法律风险评估的工程必然，且 **patch(1)** 作为基础工具纳入 base 系统须受 base 整体许可证约束，若 base 系统作为单一作品整体分发，纳入 GPLv3 代码将触发 GPLv3 §5 整体 copyleft 义务（详见第 58 章 58.4.6 法律机制分析）。

## 124.15.7 GPL 阵营的再回应与合图——利益分配视角的审视

**要点**：GPL 阵营对 FreeBSD 反批评的再回应集中于两点。其一，“宽容许可锁定论”：**patch(1)** 原始实现由 Larry Wall 开发，FSF 在其基础上增强为 GNU patch；OpenBSD 替换的 GPL 文件中，底层算法可能源自 Larry Wall 的原始实现（原始许可证待考据［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］），BSD 阵营以 PD/无限制许可证替换 GPL 文件并重新分发，恰恰印证了 FSF “宽容许可证允许专有锁定” 的论点——Larry Wall 的原始代码可被任何许可证（包括 BSD）重新包装，FSF 通过 copyleft 防止这种 “锁定”，BSD 阵营通过替换 GPL 文件消除了 copyleft 保护，使后续修改可被专有锁定。其二，“工程必要性遮蔽论”：FreeBSD 反批评中 “GNU patch 2.1 早期版本成技术债务” 的论证，只证明 patch 升级必要，不证明必须驱逐 GNU patch——FreeBSD 完全可以接受 GNU patch 2.1 早期版本继续在 base 中存在（如同 OpenSSL 许可证兼容 BSD 仍保留在 base），替换纯系许可证纯洁化的意识形态延伸。合图层须承认：两阵营在各自 “自由” 定义下均逻辑自洽，争议无法通过纯逻辑裁决。从总纲第 13 条审视，BSD patch 替换争议的实质非道德高下而是利益分配——FSF 代表用户免于锁定的利益，BSD 阵营代表商业开发者任意处置代码的利益（含免受 GPLv3 法律义务约束的利益），社区治理中的 “许可证纯洁” 话语本身是形式主义的政治产物。BSD patch 跨项目谱系（OpenBSD→DragonFly→NetBSD→FreeBSD）本身证明了宽容许可的代码流动能力，但 FreeBSD 选择 BSD 许可版本而拒绝 GPLv3 增强版本，反映了两阵营在 “自由” 定义上的不可调和——这一不可调和性不因 **patch(1)** 是小工具而减弱，反而在小工具层面更清晰地暴露了争议的结构性本质。

**史料**：**patch(1)** 原始实现 Larry Wall 1985 年 patchkit 历史考据［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］、FSF 官方许可证列表关于宽容许可证与 copyleft 的哲学立场、Stallman《Free Software, Free Society》关于 “宽容许可证允许专有锁定” 的论述、57.15.1 BSD patch 跨项目谱系考据、GPLv3 §5 官方文本。 ［A］

**史观**：总纲第 13 条——法律与道德是利益分配：BSD patch 替换争议的道德话语（“保护自由” 对 “真正的自由”）实质是利益分配的政治表达。FSF 的 copyleft 保护用户免于锁定（用户利益），BSD 宽容许可保护商业开发者任意处置代码（开发者利益），两者均非道德绝对而系利益取向。社区治理中将 “许可证纯洁” 塑造为工程原则，本身是形式主义的政治产物——选择性地将 “避免 GPLv3 法律风险” 工程化，却接受同样含专利报复条款的 Apache 2.0（LLVM），揭示 “纯洁化” 话语的利益选择性（详见第 58 章 58.4.7 合图层）。
