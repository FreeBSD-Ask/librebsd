# 117.6 Google Chromium 对 Capsicum 的早期评估与最终放弃——Chrome 团队选择自行开发 seccomp-bpf 沙箱，capsicum-linux 项目长期维护但未成为主线方案

## 117.6.1 Chromium 评估 Capsicum 的技术过程

**要点**：Google Chrome/Chromium 是 Capsicum 最早的目标应用之一——在 Watson 团队的 Cambridge-Google 合作中，Ben Laurie（Google 安全工程师、Capsicum 论文共同作者）推动了 Chromium 浏览器的 Capsicum 适配；Capsicum 论文记载，Chromium 在 FreeBSD 上的 Capsicum 沙箱改造仅需约 100 行新代码，因为 Chromium 已设计有跨平台特权分离架构（sandbox process、renderer process、zygote process 等），Capsicum 作为额外沙箱层适配简单；LWN 2012-02-22 报道明确提到"One of the main applications of interest is the Chromium web browser""Roughly 100 new lines of code were all that was required to use Capsicum in Chromium on FreeBSD"；但 Chromium 的 Capsicum 适配始终主要停留在 FreeBSD 平台支持层面，未成为 Chrome 安全沙箱的核心技术路线

**史观**：总纲第 10 条——动手者创造历史：Chromium 对 Capsicum 的采用模式是“平台特定优化”而非“核心架构依赖”——在 FreeBSD 上 Capsicum 可用时用它增强沙箱，但 Chrome 的跨平台安全模型必须支持 Linux（seccomp-bpf）、Windows（Win32k lockdown/AppContainer）、macOS（Sandbox/Seatbelt）、Android（SELinux/isolatedProcess）等多个平台；Capsicum 作为仅在 FreeBSD 上原生可用的沙箱机制，无法成为 Chrome 的主方案，这是平台市场份额差异导致的必然结果

**辨析**：原大纲标题暗示“Chrome 团队因 Linux 内核排斥 capability 模型而放弃 Capsicum”——这一说法过度简化且带有阴谋论倾向；实际原因包括：(1) 平台优先级——Chrome 用户主要在 Windows/macOS/Linux/Android，FreeBSD 桌面市场份额极小；(2) 时间线不匹配——Capsicum 在 Linux 上的移植（capsicum-linux）在 2012-2014 年才逐步可用，Chrome 的沙箱在 2010-2012 年已确定 seccomp-bpf 路线；(3) seccomp-bpf 是 Linux 内核原生机制（从 3.5 开始），无需第三方补丁；(4) Capsicum 的对象能力模型需要应用更深度的架构改造（fd passing、权限管理），seccomp-bpf 的系统调用过滤更易在现有代码基础上增量部署

## 117.6.2 seccomp-bpf 替代路线的工程选择

**要点**：Linux seccomp-bpf（secure computing mode with BPF）是 Chrome 团队在 Linux 上的主要沙箱技术：seccomp mode 1（严格模式）自 Linux 2.6.12（2005）存在，仅允许 read/write/_exit/sigreturn 四个系统调用；seccomp mode 2（SECCOMP_FILTER，即 seccomp-bpf）于 Linux 3.5（2012 年 7 月）合入主线，由 Will Drewry（Chrome 团队）等人贡献，允许通过 BPF（Berkeley Packet Filter）程序灵活过滤系统调用号及其参数；Chrome 团队从 2009-2010 年开始基于 seccomp 严格模式开发沙箱（Chrome 6 起开始集成），2011-2012 年转向 seccomp-bpf（Chrome 20+ 后逐步成熟），成为 Chrome Linux 沙箱的核心技术；seccomp-bpf 的设计哲学是系统调用级白名单/过滤，而非 Capsicum 的对象能力模型——seccomp-bpf 不切断全局命名空间访问，不改造文件描述符权限模型，仅在系统调用入口处检查进程是否有权进行特定调用

**史料**：Linux 内核 seccomp(2) 手册页（SECCOMP_FILTER_FLAG_TSYNC 等描述）；Will Drewry 等人 2012 年 Linux 内核 SECCOMP_FILTER 补丁（LKML 提交记录）；Chrome 沙箱设计文档 chromium.googlesource.com/chromium/src/+/HEAD/docs/design/sandbox.md；LWN.net 2012-01-11 Jonathan Corbet 文章“Secure computing with filters”；Linux 3.5 Release Notes（2012 年 7 月 21 日发布） ［A］

**史观**：总纲第 4 条——分离聚合是永恒规律：Chrome 选择 seccomp-bpf 而非推动 Capsicum 进入 Linux 主线，代表了工业界在“采纳现有主流内核功能”与“引入新安全范式”之间的务实选择——seccomp-bpf 基于已存在的 BPF 虚拟机（自 1992 年起在 BSD/UNIX 中用于包过滤），Linux 内核社区对 BPF 扩展接受度高，且 seccomp-bpf 补丁由 Chrome 团队直接提交 LKML 并获合入；这一路径证明：Google 并非“排斥能力模型”，而是更倾向于直接控制其目标平台（Linux）上游的安全机制演进

**辨析**：原大纲称“seccomp-bpf（2012 年 Linux 3.5 引入，Google Chrome 团队主导）”基本准确，但需精确化：seccomp mode 2/SECCOMP_FILTER 由 Will Drewry（Google Chrome 安全团队）设计并贡献，Linux 3.5（2012 年 7 月）正式合入；seccomp-bpf 与 Capsicum 的核心设计差异在于：seccomp-bpf 限制“哪些系统调用可以调用”，Capsicum 限制“对每个对象可以做什么操作”——前者是粗粒度的系统调用白名单，后者是细粒度的对象权限控制；seccomp-bpf 在落地简单性上有优势，Capsicum 在安全保证完备性上有优势

## 117.6.3 Capsicum 与 seccomp-bpf 的范式比较

**要点**：Capsicum 与 seccomp-bpf 的范式差异可从多个维度对比：(1) 安全模型——Capsicum 是对象能力模型（object-capability），以文件描述符为能力载体，在能力模式中彻底消除 ambient authority；seccomp-bpf 是系统调用过滤模型（syscall filtering），以 BPF 程序决定允许哪些系统调用，不修改进程对已有文件描述符或全局命名空间的访问权；(2) 改造深度——Capsicum 要求应用在进入能力模式前预先设置好所有能力并传递给沙箱，涉及架构重构；seccomp-bpf 可在进程启动后应用 BPF 过滤器，相对增量式；(3) 权限粒度——Capsicum 可对每个文件描述符设置不同权限（CAP_READ 但无 CAP_WRITE，特定 ioctl 命令白名单等）；seccomp-bpf 仅能基于系统调用号和参数值做二进制允许/拒绝决定；(4) 与现有 UNIX API 关系——Capsicum 引入新系统调用（**cap_enter(2)**、**cap_rights_limit(2)** 等）并限制现有语义（openat 等）；seccomp-bpf 不修改 POSIX API 语义，仅通过 prctl(PR_SET_SECCOMP) 添加过滤层；(5) 沙箱代理需求——Capsicum 需要 casperd 等代理访问系统服务；seccomp-bpf 也需要 broker 进程（Chrome 中即使用 broker process 代理受限系统调用）

**史料**：Watson et al. 2010 USENIX Security 论文；Chrome sandbox 设计文档（说明 broker process 与 seccomp-bpf 配合）；FreeBSD **capsicum(4)** 手册页；Linux **seccomp(2)** 手册页；Edge 2012 LWN 文章对两种方案的比较 ［A］

**史观**：总纲第 13 条——法律与道德是利益分配〔存疑：原挂“第 14 条——哲学思潮”系伪标签，权威表第 14 条为“苦难不值得被提倡”，待主理人审定〕：Capsicum 与 seccomp-bpf 的范式之争本质上是“深度防御（defense in depth through principled redesign）”vs“增量加固（incremental hardening）”两种安全工程哲学的对立；Capsicum 试图从根本上修复 UNIX 权限模型的缺陷（ambient authority），seccomp-bpf 试图在不改变 POSIX API 的前提下用过滤层减少攻击面；从部署结果看，seccomp-bpf 在 Linux/Chrome/Android/Firefox/Docker/Flatpak 等生态中获得广泛应用，Capsicum 主要影响 FreeBSD 和学术/研究社区；但这一结果更多反映生态惯性而非技术优劣——eBPF（seccomp-bpf 的 BPF 虚拟机后继者）最终发展为通用内核可编程平台，其影响力远超沙箱领域

**辨析**：capsicum-linux 项目状态需精确核实：Google 确实开发了 Linux 内核的 Capsicum 移植（github.com/google/capsicum-linux），LWN 2012 年评论区即有该仓库链接，2014 年评论补充了 GitHub 地址；但该项目长期为实验性维护状态，从未提交 LKML 试图合入 Linux 主线，Chrome 也从未在 Linux 上使用 Capsicum 作为沙箱机制（Chrome Linux 使用 seccomp-bpf）；capsicum-linux 与 Linux capabilities（POSIX capabilities）是完全不同的东西——不应混淆

## 117.6.4 Capsicum-Linux 与 CloudABI/WASI 的后续效应

**要点**：Capsicum 对 Linux 生态的直接影响有限，但其思想通过 CloudABI 和 WASI 产生了间接影响：CloudABI 由荷兰开发者 Ed Schouten（Nuxi 公司）于 2015 年前后开发，是基于 Capsicum 能力模型的跨平台 POSIX 派生 ABI——CloudABI 提供“POSIX 减去全局命名空间”的精简接口，程序编译为 CloudABI 二进制后可在 FreeBSD（natively 支持）、Linux、macOS 上运行，天然具有沙箱属性；CloudABI 于 2020 年 3 月正式宣布弃用（deprecated），原因是社区兴趣不足，开发者 Ed Schouten 转而支持 WebAssembly System Interface（WASI）；WASI（WebAssembly System Interface）是 W3C 社区组标准，为 WebAssembly 提供系统接口抽象，其能力模型设计（以 capabilities/handles 为核心，无全局命名空间访问）继承自 CloudABI/Capsicum 思想；这一演进路径为：Capsicum（FreeBSD OS 原语）→ CloudABI（跨平台纯能力 ABI）→ WASI（WebAssembly 标准化能力系统接口）

**史料**：CloudABI 官方项目 github.com/NuxiNL/cloudabi（README 中 2020-03-30 标记 deprecated 并指向 WASI）；LWN.net 2016-02-10 Neil Brown 文章“CloudABI”（lwn.net/Articles/674770/）；WASI 官方文档 wasi.dev；Ed Schouten 关于 CloudABI→WASI 过渡的说明 ［D］

**史观**：总纲第 4 条——分离聚合是永恒规律〔存疑：原挂“第 25 条——终结与延续”系伪标签，权威表第 25 条为“逻辑是形式主义而非世界本身的结构”，待主理人审定〕：CloudABI 的弃用和 WASI 的兴起标志着能力安全模型从内核级机制向通用运行时抽象的迁移——Capsicum 证明了对象能力模型可以在 UNIX 中产品化，但 OS 级能力模型面临应用改造门槛高、跨平台支持难的问题；WASI 将能力模型提升到语言/运行时层面（WebAssembly 作为平台无关的执行环境），避免了内核改造的门槛，且天然契合 Web 浏览器沙箱需求；Capsicum 的直接部署规模有限，但其设计思想通过 WASI 进入了更广阔的生态系统

**辨析**：原大纲本节标题为“Google 放弃 Capsicum-Linux 与 ANU 质疑”——ANU（Australian National University）的 CHERI/Capsicum 相关“质疑”经检索未找到明确的一手文献对应［据 standalone (2019) 一手文献印证消解 doubt-resolved-640：此处事实待多源交叉验证］；如果指的是 CHERI 硬件能力绕过攻击的学术论文，那属于 CHERI 范畴（74.11 节），与 Capsicum 软件能力模型无直接关系；将“ANU 质疑”作为 Chromium/Capsicum 关系的要点缺乏可靠来源支持，本节改写为“Capsicum-Linux 与 CloudABI/WASI 的后续影响”以反映真实技术演进脉络
