# 117.4 FreeBSD 9.0（2012.1）将 Capsicum 作为可选特性引入——框架加入 GENERIC 内核但不附带 Capsicum 化应用程序，10.x/11.x 时代逐步成熟与 casperd 完善

## 117.4.1 FreeBSD 9.0 可选特性的集成路径

**要点**：Capsicum 首次随 FreeBSD 正式发布是在 FreeBSD 9.0-RELEASE（2012 年 1 月 12 日），而非原大纲所称的 FreeBSD 10.0；FreeBSD 9.0 中的 Capsicum 标记为 experimental（实验性）——Release Notes 明确说明这是 “sandboxing support” 的框架，且 LWN 2012-02-22 报道明确记载 "9.0 release only contains the kernel changes required for Capsicum but doesn't ship any applications that use the facility"；FreeBSD 9.0 中的 Capsicum 仅提供内核框架和系统调用，**libcapsicum(3)** 用户态库、**casperd(8)** 守护进程以及大量基本系统工具的 Capsicum 改造均在后续版本中完成；关于 GENERIC 内核配置——经 **freebsd.duckdb** `commits` 表验证，将 `options CAPABILITY_MODE` 与 `options CAPABILITIES` 加入 GENERIC 内核配置的 commit 为 `009d2032af44e1f71bd17cda89ace46a4df2d2cc`（罗伯特·N. M. 沃森（Robert Watson），2011-12-29T22:48:36Z，subject 明确记载 "Add ‘options CAPABILITY_MODE’ and ‘options CAPABILITIES’ to GENERIC kernel configurations for various architectures in FreeBSD 10.x."，即该 commit 是为 FreeBSD 10.x CURRENT 添加 GENERIC 配置，对应 SVN r219129）；因此 FreeBSD 9.0 中 Capsicum 框架存在但需手动添加 options，FreeBSD 10.0（2014-01-20）才将 Capsicum 框架纳入 GENERIC 默认编译

**史料**：FreeBSD 9.0-RELEASE Release Notes（2012-01-12，Release Highlights 第一条即记载 Capsicum）；FreeBSD `commits` 表 commit `009d2032af44e1f71bd17cda89ace46a4df2d2cc`（对应 SVN r219129，CAPABILITIES/CAPABILITY_MODE 加入 GENERIC，但 commit message 明确说明是 10.x 而非 9.0）；LWN.net 2012-02-22 Jake Edge 文章 “9.0 release only contains the kernel changes”；FreeBSD **capsicum(4)** 手册页 HISTORY 节（记录 “Capsicum first appeared in FreeBSD 9.0”）；**freebsd.duckdb** L2.2.1.sys_security 查询（sys/security 子系统 commit 演化）——该查询在 `中观模式挖掘.md` §L2.2 报告段落中计划但未单独执行，freebsd.duckdb 的 L2.2.1 系列查询目前仅覆盖 sys/kern、sys/net、sys/geom、sys/cam、sys/dev、sys/vm、sys/fs、sys/contrib 八个子系统，尚未包含 sys/security 子系统；Capsicum 代码主要位于 `sys/kern/`（sys_capability.c、capability.c 等）和 `sys/security/` 目录下，sys_security 查询数据缺失意味着无法通过 commit 量统计直接量化 Capsicum 代码在 sys/security 子系统中的占比；替代数据来源：可通过 freebsd-src 仓库的 `sys/security/capabilities/` 路径直接查询 commit 历史获取 Capsicum 相关代码演化数据；0 信任原则局限提示：sys/security 子系统不仅包含 Capsicum，还包含 TrustedBSD MAC 框架、Jail、audit 等其他安全组件，commit 量统计须结合 commit message 关键词过滤才能区分 Capsicum 与其他安全特性 ［A］

## 117.4.2 casperd 与 libcapsicum 的工程演进

**要点**：Pawel Jakub Dawidek 在 FreeBSD 基金会与 Google 开源计划办公室联合资助下（2013 年 4 月公告），持续推进 Capsicum 的产品化工作；casperd（**casperd(8)**，Capsicum Service Daemon）是其核心成果——该守护进程以特权进程运行，为能力模式下的沙箱进程提供受限系统服务代理；casperd 通过 **libcasper(3)** 库向沙箱进程提供服务，包括：DNS 解析（libcasper_dns，替代沙箱内无法访问的 **/etc/resolv.conf** 和网络命名空间）、随机数获取（libcasper_random，通过 **getrandom(2)** 等安全方式）、文件打开对话框（libcasper_fileargs，用户授权的文件访问代理）、sysctl 受限访问（libcasper_sysctl）等；**libcapsicum(3)** 高层库提供更便捷的沙箱 API，避免应用开发者直接处理 fd passing 和 cap_enter 的底层细节；casperd 最早在 FreeBSD 10.x 系列进入基本系统，FreeBSD 11.x 进一步完善，FreeBSD 12/13/14 中成为稳定的 Capsicum 服务基础设施

## 117.4.3 从实验框架到基本系统组件的策略转变

**要点**：Capsicum 在 FreeBSD 中的成熟过程可分为三个阶段，覆盖从 FreeBSD 9.0 内核框架引入到 FreeBSD 14.x 稳定基础组件的完整路径，各阶段关键特征与首批 Capsicum 化程序见下表。

| 阶段 | FreeBSD 版本 | 时间 | 关键特征 | 首批 Capsicum 化程序 |
| --- | --- | --- | --- | --- |
| 1 | 9.0 | 2012.1 | 内核框架加入 GENERIC，experimental 标记，无任何应用默认使用 | 无 |
| 2 | 10.x | 2014-2016 | libcapsicum 和 casperd 开发完善，基本系统中逐步加入首批 Capsicum 化工具，从 experimental 逐步转为 supported | **tcpdump(1)**、**dhclient(8)**、**kdump(1)**、**killall(1)**、**hostctl(8)** |
| 3 | 11.x-14.x | 2016-2024 | casperd 服务集扩展，更多基本系统程序 capsicum 化，FreeBSD 14（2023 年 11 月）中 Capsicum 成为基本系统安全加固的默认组件 | **bhyve(8)** 虚拟化组件、**wait(1)** 等 |

- capsicum 化程序在 FreeBSD 基本系统中的精确数量随版本增加，但相较基本系统总计约 1000+ 个程序，Capsicum 化比例仍较低。

**史料**：FreeBSD 各版本 Release Notes（9.0-14.x）Kernel Changes 与 Userland Changes 章节中 Capsicum 相关条目；FreeBSD src 树中 cap_enter() 调用 grep 统计（可通过 codesearch 或源码分析获取各版本 capsicum 化程序清单）；FreeBSD Wiki Capsicum 页面 wiki.freebsd.org/Capsicum [据一手文献印证消解^doubt-resolved-635，页面需经互联网档案馆访问] ［A］

**史观**：开源运动：Capsicum 在 FreeBSD 基本系统中的渐进推广模式反映了 BSD 社区在安全机制部署上的工程保守主义——不在一个版本中大规模改造所有程序，而是逐程序、逐版本进行 sandboxing 改造，每次改造都经过充分测试和代码审计；这与 Linux 生态中 systemd、eBPF 等新机制迅速扩散的模式形成对比

**辨析**：FreeBSD 10.0-RELEASE 发布日期为 2014 年 1 月 20 日，11.0-RELEASE 为 2016 年 10 月 10 日——原大纲写“11.0（2014.1）”是将 10.0（2014.1）与 11.0（2016.10）混淆，已修正；关于“FreeBSD 11.0 默认编译启用”的说法：Capsicum 内核框架从 9.0 起已默认编译，11.0 的意义在于 casperd 默认启用和更多用户态程序默认使用 Capsicum 沙箱；具体哪些程序从哪个版本开始默认使用 Capsicum，需逐程序检查 release notes 和源码，tcpdump 是最常被引用的早期案例

**要点**：

- 嘉宾（结合 ZFS 移植、GELI、casper、auditdistd 等工作可辨认为 FreeBSD 提交者 Pawel Jakub Dawidek，转写讹作 Dodek）自述移植缘起：少年时自 Amiga 直接转用 FreeBSD，后经在波兰电信业任职的朋友偶然谈及 Sun 正在开发、具备多数据集、端到端校验、压缩与集成卷管理的新文件系统，遂起意亲手移植；彼时 FreeBSD 除 UFS 外，HFS、ReiserFS、XFS 等移植皆未竟或只读，UFS2 仅属有限改良。他自述“十天十夜几乎不停编码”即得可读写原型（587.77-595.77），其后又历时数月方达可提交状态。（BSD Now EP62，[483.69-624.77]，L1）
- 技术路径上，受访者归纳移植可行的三重条件：ZFS 代码整洁且多数可在用户态编译，Sun 侧为可移植性投入充分；FreeBSD 与 Solaris 内核 API 相近程度远超 FreeBSD 与 Linux；他自建的 Solaris 兼容层虽自嘲“不甚体面”（692.05-701.13），却将本方改动与上游差异压至最小，得以跟上 Sun 时期 ZFS 的高速迭代。最大障碍在 VFS 层集成——他称其为内核中最复杂、充满“隐秘知识”的部分（744.45-747.29），并以亲身体验解释此前多次文件系统移植失败之因；FreeBSD VFS 代劳缓冲等事务的设计，对 ZFS 这类自带缓冲策略与文件区间锁的复杂文件系统反而构成掣肘。（BSD Now EP62，[650.77-853.73]，L1）
- GELI 一节系其一手叙述：因早期 ZFS 加密不合需求，他另写位于文件系统之下的磁盘加密 GEOM 类，特色包括软件内数据认证（以存储空间为代价校验数据完整性）、自始集成 OpenCrypto 框架以利用硬件加速与 AES-NI，以及多密钥解锁——口令、U 盘密钥文件等可并用；他举例企业场景中安全官另持主密钥，雇员遗失密钥亦不致数据不可恢复。同类方案他点名 TrueCrypt 与 Linux 自有实现。　[存疑脚注] 受访者提及 macOS 已出现同类块级加密方案处转写残损（Mac OS 10 502），具体所指待核。（BSD Now EP62，[1015.53-1152.29]，L1）
- Capsicum 部分他自述：内核部分已趋可用，重心转向 casper 守护进程，用以在无全局命名空间访问权的沙盒内以能力方式提供域名解析等受控服务；架构上曾试验 casper 作为独立进程，因资源限制、CPU 集与路由表等上下文无法经 UNIX 域套接字安全转发而判定不可取，转向由主进程派生并继承全部限制的方案。生态上他提及 Google 赞助 Linux 移植、OpenBSD 亦在考察相近设计。　[存疑脚注] OpenBSD 相关设计的转写含混（does live design），所指方案待核。（BSD Now EP62，[1282.25-1490.00]，L1）

**史料**：

- 本期一手史料以 EuroBSDCon 会场走廊即兴访谈本身为核心：受访者以亲历者身份口述 ZFS 移植代码实践（含 Solaris 兼容层与上游版本跟进）、GELI、casper、auditdistd 及其公司 Wheel Systems（转写讹作 rule systems）的 Fudo（转写讹作 food）远程会话审计产品；另涉其组织于波兰的一届 EuroBSDCon（亲历），以及 MeetBSD 大会由 iXsystems 每两年于硅谷主办、Intel 与 Western Digital 赞助等讯息（系主持人转述）。（BSD Now EP62，[283.13-1797.05]，L1）

**史观**：

- 总纲10 动手者创造历史：该期堪称动手者史的范本：移植的成败不系于宣言或路线图，而系于个体连续十昼夜的编码、其后数月的打磨与多年近乎独自的维护——他自陈 FreeBSD 侧移植数年间几乎由其一人支撑、尽管 ZFS 本身绝非一人项目，并长期“等待他人加入”（1174.94-1193.82）；企业采用亦由工程师在生产环境中逐案促成。技术史在此呈现为具体劳动的累积，而非抽象进程的展开。（BSD Now EP62，[587.77-1193.82]，L1）

**辨析**：

- 受访者对 Oracle 版 ZFS 加密的批评——数据集级密钥与去重不兼容、面向多用户共享的假设错配单用户笔记本与服务器断电取钥场景、元数据无法纳入加密——及其按 vdev 层乃至裸扇区加密的替代设想，属个人技术论断而非 Oracle 内部证词，采信须谨慎。　[存疑脚注] 该段为单一来源推断，未与其他来源交叉验证；转写中 ZIPL 疑为 ZIL 之讹误。（BSD Now EP62，[857.82-997.41]，L4）
- 关于生态流动的叙述多经主持人转述或当事人口耳相传：Voxer 因 ZFS、DTrace 与 TRIM 支持转向 FreeBSD，Solaris 用户因 Oracle 收购迁离，另有企业为获取 ZFS 自 Linux 迁入；受访者并称 FreeBSD ZFS 的 SSD TRIM 支持系其为一家英国公司（转写 multiplayer，或即 Multiplay，待核）所做，且“据我所知”为他家所无（1232.21-1244.02）。　[存疑脚注] TRIM 唯一性与企业迁移归因均为单源口述，需以提交记录与企业公开资料交叉验证。（BSD Now EP62，[1216.09-1275.37]，L2）
