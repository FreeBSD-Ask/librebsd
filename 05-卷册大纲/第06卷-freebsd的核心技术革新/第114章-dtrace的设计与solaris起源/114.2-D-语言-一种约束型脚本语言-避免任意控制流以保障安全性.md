# 114.2 D 语言——一种约束型脚本语言，避免任意控制流以保障安全性

## 114.2.1 D 语言语法约束与安全模型

**要点**：DTrace 的 D 编程语言（非 Walter Bright 的 D 编程语言，二者同名但完全无关）是受 C 语言语法启发的专用脚本语言，结构上类似 awk 程序：由一组 probe 描述和对应 action 组成，格式为 `probes /predicate/ { actions }`；核心安全约束包括：禁止循环（loop）和递归——所有 D 程序的执行时间静态可确定；禁止无条件跳转（无 goto、无 longjmp）；禁止写入内核内存——D 程序只能读取内核状态和聚合数据，不能修改；指针解引用有边界检查；执行时间有上限——探针触发后在有限指令内必须完成；D 支持线程局部变量（thread-local variables，`self->`）、聚合函数（`count()`、`sum()`、`avg()`、`min()`、`max()`、`quantize()`、`lquantize()`）、关联数组；D 编译器在加载 D 程序时做全面静态检查，不安全的程序在编译阶段即被拒绝，不会在内核中执行

**史料**：Cantrill et al. 2004 USENIX 论文第 3 节（D Program Language 完整描述）；Solaris Dynamic Tracing Guide 第 2 章 D Programming Language；FreeBSD **dtrace(1)** 手册页 D Language 章节；Brendan Gregg DTrace 书第 2 章 D Language Fundamentals ［A］

**史观**：总纲第 24 条——许可证：D 语言的受限设计是安全与表达力之间工程权衡的经典案例——通过牺牲通用语言的任意控制流能力（图灵不完备），换取在生产环境内核中安全执行的保证；这种“故意设计成非图灵完备”的安全语言思想，与后来 eBPF 验证器的设计哲学一脉相承，是安全内核扩展的重要范式

**辨析**：D 语言与 Walter Bright 的 D 编程语言（通用编程语言，2001 年发布）同名，二者常被混淆——DTrace D 语言是 2003-2004 年间由 Cantrill 团队专为追踪设计的受限语言，非通用语言；DTrace 官方文档明确区分这两种语言；D 语言“类似 awk”指其程序结构（predicate-action 对），而非语法细节——语法层面更接近 C；D 语言的安全模型在 USENIX 论文中有详细形式化描述，验证器（validator）是 DTrace 安全性的核心，而非简单的“沙箱”

**文献**：Cantrill, B. M. et al. (2004). Dynamic Instrumentation of Production Systems. USENIX ATC '04 (Section 3: The D Programming Language); Oracle Corporation. Solaris Dynamic Tracing Guide, Chapter 2; FreeBSD Project. **dtrace(1)** Manual Page (D Language section); Gregg, B., & Mauro, J. (2011). DTrace (Chapter 2: D Language Fundamentals) ［B］

## 114.2.2 约束型脚本语言的工程实现

**要点**：D 语言编译器和执行环境在 FreeBSD 中作为内核模块 **dtrace.ko** 实现，用户态工具为 **dtrace(1)** 命令行工具；D 程序的编译过程：用户提交 D 脚本 →libdtrace 将其编译为 DIF（DTrace Intermediate Format）字节码 →DIF 验证器在加载前检查所有安全约束 → 验证通过的 DIF 在探针触发时由 DIF 虚拟机在内核上下文中执行；聚合数据（aggregations）使用 per-CPU 缓冲区存储，通过 **libdtrace** 在用户态读取和合并，避免内核锁竞争；DIF 虚拟机设计为可移植实现，FreeBSD、macOS、illumos、Oracle Linux 均复用核心 DIF 逻辑

**史料**：FreeBSD src/sys/cddl/contrib/opensolaris/uts/common/dtrace/ 目录（D 语言核心实现：dtrace.c、dt_dof.c、dt_provider.c 等）；FreeBSD src/cddl/contrib/opensolaris/lib/libdtrace/ 目录（用户态 D 编译器库）；FreeBSD **dtrace(1)** 和 **dtrace(4)** 手册页；Cantrill et al. 2004 论文第 4 节（Implementation） ［A］

**史观**：信息技术：DIF 字节码 + 验证器的架构是可验证安全执行的经典工程实现——它证明了可以在操作系统内核中安全执行用户提供的代码，只要对代码形式进行足够严格的约束；这一思想直接影响了 Linux eBPF 的设计——eBPF 同样采用字节码 + 内核验证器的架构

**辨析**：D 语言在 FreeBSD 中的实现最早由 John Birrell 发起，George V. Neville-Neil（乔治·V·内维尔-尼尔） 等人后续完善；DIF（DTrace Intermediate Format）与 DOF（DTrace Object Format）是不同概念——DIF 是内核中执行的字节码，DOF 是用户态编译器输出的目标文件格式（类似 ELF），原文未区分二者；D 语言并非“解释执行”——DIF 虚拟机在早期 Solaris 版本中是解释器，后续版本包括 FreeBSD 增加了 DIF 到 native code 的 JIT 编译以提升性能

**文献**：FreeBSD Source Repository. src/sys/cddl/contrib/opensolaris/uts/common/dtrace/; FreeBSD Project. **dtrace(1)**, **dtrace(4)** Manual Pages; Cantrill, B. M. et al. (2004). Dynamic Instrumentation of Production Systems. USENIX ATC '04 (Section 4: Implementation) ［B］

## 114.2.3 D 语言与 awk/C/BPF 程序比较

**要点**：D 语言在语法层面大量借鉴 C：变量声明、类型系统、运算符（算术、逻辑、位运算）、结构体/指针操作、`->` 成员访问等均遵循 C 语义；在程序结构层面借鉴 awk：probe/predicate/action 三元组对应 awk 的 pattern/action 模式；D 与 Linux eBPF 的比较：D 语言专为追踪设计，内置聚合、speculative tracing（推测追踪）、栈跟踪等高级原语；eBPF 是通用内核虚拟机，程序用 C 编写并编译为 eBPF 字节码，功能更通用（网络、安全、追踪）但追踪专用原语需通过 helper 函数实现；D 语言的局限性：不支持用户自定义函数（D 程序只有内联 action，无函数调用抽象）、无循环（只能用条件截断）、无浮点运算（内核中避免浮点状态切换）

**史料**：Cantrill 2004 论文 D Language 节；Gregg 2014-2016 年关于 DTrace vs eBPF 的博客文章；Alexei Starovoitov eBPF 设计文档（Linux 内核源码 Documentation/bpf/ 目录）；Brendan Gregg《BPF Performance Tools》（2019，Addison-Wesley）第 1-2 章（eBPF 与 DTrace 比较） ［A］

**史观**：技术路线分化：D 语言与 eBPF 的设计差异体现了专用语言与通用虚拟机的技术路线分化——D 是追踪专用语言，为追踪场景做了深度优化（聚合、推测追踪、消费者-生产者模型）；eBPF 是通用执行引擎，通过 helper 函数扩展到网络、安全、追踪等多场景；这一分化决定了二者的应用边界

**辨析**：Brendan Gregg 对 eBPF 的评价需精确引用——他在 2014 年《DTrace to eBPF》演讲中梳理了 DTrace 对 eBPF 的技术启发路径，但并非简单称 bpftrace 为“DTrace 2.0”；Gregg 后续积极参与 eBPF 生态开发并著《BPF Performance Tools》，但他多次强调 DTrace 在生产环境追踪方面仍有优势（如任意内核位置的动态追踪）；bpftrace 是 Alastair Robertson 于 2018 年前后开发的基于 eBPF 的追踪工具，语法受 D 语言启发，但 Gregg 称其为“DTrace 2.0”更多是一种定位叙事而非严格技术判断

**文献**：Gregg, B. (2014). DTrace to eBPF. USENIX LISA 2014 Presentation; Starovoitov, A. (2014). eBPF Design Document. Linux kernel Documentation/bpf/verifier.rst; Gregg, B. (2019). BPF Performance Tools: Linux System and Application Observability. Addison-Wesley. ISBN 978-0136554820; Robertson, A. bpftrace Project. github.com/iovisor/bpftrace ［B］

## 114.2.4 D 语言设计文档考证

**要点**：D 语言最权威的设计文档是 Cantrill 等人 2004 年 USENIX 论文的第 3 节，该节完整描述了 D 语言的类型系统、变量种类（全局、线程局部、子句局部、聚合）、安全约束、执行模型；Solaris Dynamic Tracing Guide（Sun/illumos 出版）是最完整的参考手册，含 D 语言所有特性的逐章说明；FreeBSD 手册页 **dtrace(1)** 的 D Language 节是 FreeBSD 系统最直接的参考，但内容比 Solaris 指南简略；D 语言没有独立的语言规范文档（如 ISO 标准），其规范以 Sun/Oracle/illumos 的实现和官方指南为准

**史料**：Cantrill et al. 2004 USENIX 论文（D 语言设计的原始来源）；Solaris Dynamic Tracing Guide（illumos 版本 illumos.org/books/dtrace/ 为可访问的权威版本）；FreeBSD **dtrace(1)** 手册页；dtrace.org 博客中关于 D 语言设计的文章（Cantrill 和 Leventhal 均有相关文章） ［A］

**史观**：形式主义膨胀：D 语言无独立语言规范这一事实体现了工业界语言与学术界语言的设计路径差异——D 语言是先有实现后有文档（论文 + 指南），而非先有规范后有实现；这种“代码即规范”的模式在开源项目中常见，但增加了跨平台移植时的语义模糊风险

**辨析**：原文称“D 语言与 BPF 程序比较”但引用 Jolitz DDJ 文章系无关文献错误已修正；D 语言不支持浮点运算是一个常被忽视的限制——DTrace 在内核态执行时默认不使用浮点寄存器以避免保存/恢复浮点上下文的开销，D 程序中不能使用 float/double 类型；D 语言的数组大小有静态上限（DTRACEOPT_MAXSIZE 等可调参数），这些限制都是安全模型的一部分

**文献**：Cantrill, B. M. et al. (2004). Dynamic Instrumentation of Production Systems. USENIX ATC '04; illumos Project. Solaris Dynamic Tracing Guide. illumos.org/books/dtrace/; FreeBSD Project. **dtrace(1)** Manual Page (D Language Reference) ［B］

- DTrace 起源于 2000 年代初的 Solaris，2003 年随 Solaris 10 发布；讲者指出其思想前身至少可追至 1999 年论文“Fine Grain Dynamic Instrumentation of Commodity Operating System Kernels”，该工作已在 Solaris 与 SPARC 平台解决向内核任意位置注入机器码并保证不致崩溃的大部分难题。移植史方面，John Birrell 于 2000 年代中期将其移植到 FreeBSD，是 Solaris 之外移植的第一人，2009 年去世，生前还参与了 FreeBSD 若干基础组件的开发；macOS 亦集成 DTrace 但多为工具底层间接使用；illumos 社区维护的 dtrace.org 指南是最全面的参考资料。　[存疑脚注] 转写噪声致个别数字失真：Birrell 最活跃时期被转写为“2006 至 2018”，与其 2009 年去世矛盾，应为 2006-2008 年前后；“2012 年起默认启用”一句同样受损，年份与版本细节待与 FreeBSD 发布记录核对（YouTube EPE06GVdH-LX0，[508.2-626.8, 536.3-600.8, 631.0-711.9, 515.0-535.8, 4774.9-4783.5]，L1）[订正：原 [631.0-662.3]→[631.0-711.9]，补“Solaris 之外首移植”“参与 FreeBSD 基础组件开发”及存疑脚注所指“2012 年启用”受损句锚点，内容复核]

**史观**：

- 总纲9 经验优先：讲者对自身方法的自述呈现出鲜明的经验优先取向：他不以 DTrace“直接解决问题”，而是把它当作向系统提问的工具——先粗采大量数据，再迭代收窄问题域，使对问题的认识逐步澄清；相对于静态工具只能回答罐装问题，动态追踪让开发者直接向运行中的内核求证，以一手观测取代猜测。（YouTube EPE06GVdH-LX0，[2585.8-2626.9, 364.2-384.2, 3139.9-3151.2]，L1）
- 总纲22 知识注定过时：DTrace 的当下处境本身构成一条技术史命题：它曾是动态可观测性范式的开创者，而十余年后创新重心已移向 Linux eBPF，讲者直言其大量新能力在 DTrace 中并无对应物，进而呼吁社区思考“DTrace 2.0”以直面自身缺陷——开创性工具所承载的知识终将被后来者超越，工具史亦无恒定的进步主角。（YouTube EPE06GVdH-LX0，[4856.1-4913.8, 4917.7-4943.1]，L1）
- 总纲4 分离聚合是永恒规律：DTrace 的生命周期呈现典型的分合循环节律：诞生于 Solaris，经 illumos 开源承接而与母体分离，再扩散至 FreeBSD 与 Mac OS 各自演化，如今以 OpenDTrace 谋求跨系统的单一上游再聚合；聚合并非回到 Sun 时代的集中式母体，而是以正式规格与 RFC 流程为基础的新形态协作，说明分离聚合不是回到原点，而是以新形式重构协作结构。（YouTube EPj_TVpq8S2Io，[126.1-184.9, 2165.2-2342.7]，L1）

**辨析**：

- 讲者坦承 DTrace 的三类缺陷：一是可发现性差，当开发者尚不知道该问什么时难以构造查询，这是其最大困扰，dwatch 等高层封装只是部分缓解；二是缺乏端到端追踪，无法沿用户程序到协议栈再到驱动的完整路径连续观测同一 I/O；三是 fbt 仅支持函数入口与出口，无法在巨型函数中段插桩。用户态 DTrace 则被指文档稀缺且需侵入构建系统嵌入探针后处理步骤，Python 探针补丁未获上游接受，仅在 Isilon 内部集成。（YouTube EPE06GVdH-LX0，[4917.7-4943.1, 4953.9-5033.8, 5037.2-5057.7, 2634.4-2708.9]，L1）
- 转写存疑三处：其一，移植者姓名新转写作 John Brezoi（旧转写作 John Burrell），与 FreeBSD DTrace 移植史公认人物 John Birrell 高度疑似同一人之语音识别误差；其二，演讲人称 FreeBSD audit 子系统“自 2004 年起可选”——新转写逐字为“It's been optional in FreeBSD since 2004”，口述内容已证实，与通行记载不符处属演讲人自述与外部记载之出入；其三，净室重实现动因一句在新转写中已可辨识：演讲人称曾有重实现 CTF 工具之尝试，“due to a license allergy, people wish to not use the CDD [CDDL] code, they want to have a clean room reimplementation”，可确认系因 CDDL 许可证过敏而拒绝使用该代码并诉求净室重实现，旧转写所谓 cincy apfel's 等不可还原之词经新转写已消解。另 schedgraph 新转写已作 sched graph（旧转写作 skin-graft）；eBPF 处新转写逐字为“eBPF now has feature parity with P-Trace”（旧转写作 feature pirate in two pieces），故旧注“eBPF 特性分化为两个部分”系据旧转写之误辨，应订正为“eBPF 现已具备 feature parity”。[订正：移植者姓名新转写作 John Brezoi 而非 John Burrell；audit 年份新转写为 2004 而非 2000；净室重实现动因句在新转写中已可完整辨识，不再属严重失真；eBPF 处实为 feature parity 而非“分化为两个部分”；schedgraph 已可辨识]　[存疑脚注] 移植者姓名（John Birrell）之语音辨识与净室重实现所述 CTF 工具重实现尝试的具体所指，仍需核对原视频。（YouTube EPj_TVpq8S2Io，[126.1-2682.5]，L4）
