# 122.5 磁盘标签、分区与 I/O 调度

## 122.5.1 BSD disklabel、MBR 与 GPT：从传统到现代分区

**要点**：传统 BSD 磁盘标签（**disklabel(8)**，又称 BSD disklabel）是 BSD 独有的分区方案，可在一个 MBR 分区内再划分最多 8 个 BSD 分区（传统命名 a-h，a 为根、b 为交换、c 为整个磁盘/分片）；随着 EFI 和 GPT（GUID Partition Table）普及，FreeBSD 7.x 引入 **gpart(8)** GEOM 类作为统一分区工具，支持 MBR、GPT、APM（Apple Partition Map）、VTOC8（Sun VTOC）、BSD disklabel 等多种分区表；**gpart(8)** 替代了旧的 **fdisk(8)**（MBR 分区）和 **disklabel(8)**/**bsdlabel(8)** 工具，现代 FreeBSD（9.0+）推荐使用 **gpart(8)** 和 GPT 分区方案；GPT 支持最多 128 个分区（默认）、64 位 LBA、CRC32 校验、分区类型 GUID、分区名称，解决了 MBR 只能有 4 个主分区、2TB 磁盘上限等问题；**glabel(8)** 提供文件系统标签功能，可通过 UFS ID、文件系统标签、GPT 分区标签等方式引用设备，避免因设备名变化（如磁盘插拔顺序变化）导致引导失败

**史料**：**gpart(8)**, **disklabel(8)**, **fdisk(8)**, **glabel(8)** 手册页；FreeBSD Handbook “Adding Disks” 章节；FreeBSD 7.0/8.0 Release Notes gpart 章节；FreeBSD src/sys/geom/part/ 源码 ［A］

**史观**：总纲第 15 条——文化即形式主义：**gpart(8)** 对多种分区方案的统一是 GEOM 架构优势的体现——传统分区工具（fdisk、bsdlabel）直接读写磁盘，而 gpart 是一个 GEOM class，分区作为 GEOM provider 存在，可以被其他 GEOM 模块堆叠、支持自动拓扑发现、支持运行时分区调整；这种架构统一使得添加新分区方案（如 GPT）只需写一个新的 GEOM part 模块，无需重写整个工具链

**辨析**：工具替换时间线需准确：**fdisk(8)** 和 **bsdlabel(8)** 在 FreeBSD 10.x/11.x 中仍存在但不推荐用于新系统，**gpart(8)** 是官方推荐工具；GPT 分区的 FreeBSD 引导支持：FreeBSD 8.0 开始支持 GPT 分区引导（gptboot 引导代码），FreeBSD 9.0+ 全面支持 GPT 作为默认分区方案；BSD disklabel 中 c 分区代表整个磁盘/整个 MBR 分片——这是历史遗留，新手常犯的错误是将 c 分区当作普通分区使用导致覆盖整个磁盘；GPT 分区在 FreeBSD 中命名为 /dev/gpt/*，也可通过 /dev/ada0p1 这样的 gpart 分区设备名引用

(2018). *FreeBSD Mastery: Storage Essentials*. Chapter 8-9.［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

## 122.5.2 geom_sched：未完成的 I/O 调度器

**要点**：**geom_sched(8)** 是一个实验性的 GEOM class，旨在实现块设备 I/O 调度算法，如类似 Linux CFQ（完全公平队列）、deadline、anticipatory 等调度器；geom_sched 由 Fabio Checconi 等人在 2008-2009 年开发，随 FreeBSD 8.x 作为实验功能引入，但从未达到生产就绪状态；FreeBSD 传统上没有独立的块层 I/O 调度器，CAM 层的标签队列和磁盘自身固件负责 I/O 排序；geom_sched 存在的问题包括：与 CAM TCQ/NCQ 功能重叠、在 SSD/NVMe 上 I/O 调度收益甚微甚至降低性能、代码维护不足、GEOM 架构下 I/O 调度位置不理想（调度应在块层最底层而非 GEOM 中间层）；截至 FreeBSD 14，geom_sched 仍标记为实验性，默认不启用，社区也没有投入资源完善它的计划

**史料**：**gsched(8)** 手册页；Checconi 2008-2009 年 geom_sched 提交记录；FreeBSD 8.x Release Notes geom_sched 说明；FreeBSD 邮件列表中关于 I/O 调度器必要性的讨论 ［A］

**史观**：总纲第 3 条——不存在进步，只有权力再分配：geom_sched 的 “未完成” 状态是技术演进的自然结果——当它在 2008 年开始开发时，针对机械硬盘的 I/O 调度仍有意义；但 SSD 在 2010 年代快速普及、NVMe 在 2015 年后成为主流，I/O 调度从 “性能必需” 变成了 “有害无益”，因为 SSD 随机访问性能高、内部有更优的调度算法，额外的内核 I/O 排序只会增加延迟；Linux 也从 CFQ 转向 none/mq-deadline 默认调度，正是同样的行业趋势

**辨析**：一个常见误解是 “FreeBSD 没有 I/O 调度器所以性能差”——实际上对于现代 SSD/NVMe 设备，操作系统层面的 I/O 调度通常是不必要的，因为：1）SSD 无机械寻道时间，不存在 “排序减少寻道” 的收益；2）设备自身支持多队列（NVMe 最高 65535 队列），固件做调度比内核更合适；3）GEOM/CAM 已实现基本的请求合并和排序；对于机械硬盘，CAM 标签队列和磁盘 TCQ/NCQ 已提供一定程度的 I/O 排序；geom_sched 未能完成不是 FreeBSD 开发能力不足，而是硬件演进使其失去了必要性

**文献**：FreeBSD Project. **gsched(8)** Manual Page; Checconi, F. (2008-2009). *geom_sched Commits*. svn.freebsd.org; FreeBSD Project. *FreeBSD 8.x Release Notes*. ［A］

## 122.5.3 磁盘分区与 I/O 调度的史料辨析

**要点**：FreeBSD 磁盘命名演进历史：早期 MFM/RLL 磁盘为 wd?（Winchester Disk），SCSI 磁盘为 sd?；FreeBSD 3.x CAM 引入后 SCSI 磁盘改为 da?（Direct Access）；FreeBSD 5.x 时期 ATA 磁盘为 ad?（ATA Direct Access）；FreeBSD 9.0 ATA 接入 CAM 后改为 ada?（ATA Direct Access in CAM）；NVMe 为 nvd? 或 nda?；各种虚拟设备包括 md?（内存盘）、mirror/?（gmirror）、eli/?（geli）、label/?（glabel）、gpt/?（GPT 分区标签）等；设备命名稳定问题：传统设备名（ada0, da0 等）由磁盘探测顺序决定，插拔磁盘可能导致设备名变化，这是引入 glabel、GPT 标签的根本原因——通过标签或文件系统 UUID 引用设备可避免引导失败

**史料**：**ada(4)**, **da(4)**, **nda(4)** 手册页；FreeBSD 各版本 Release Notes 设备命名变化记录；Lucas 2018 书磁盘命名章节 ［A］；Tuffli C. Frankenstein’s Disk Drive [C]//BSDCan 2019. Ottawa, 2019（作者为 FreeBSD NVMe 驱动开发者，提出以 bhyve 模拟的虚拟 NVMe 设备 pci_nvme.c 加定制固件替代“错误模式注入”与 mock，测试 NVMe 驱动错误处理）

**史观**：总纲第 15 条——文化即形式主义：从 wd→sd→ad→da→ada→nvd/nda 的设备名变化，反映了存储技术演进和架构统一的过程，但这种名称变化给用户带来了迁移成本，也使得早期文档和教程过时；gpart + glabel 通过标签抽象解决了这个问题，这是形式化抽象在工程实践中降低历史耦合的案例

**辨析**：“FreeBSD 设备名混乱” 是一个常见批评——与 Linux sda/sdb 看似稳定的命名对比，FreeBSD 设备名确实随着架构整合变化过多次；但 Linux 从 hd?（IDE）到 sd?（libata 统一）也经历过类似变化，而且 Linux 的 sd? 命名同样依赖探测顺序，实际生产中也使用 UUID/LVM 标签引用设备而非 sd? 名称；两者只是走了不同的演进路径，最终都收敛到 “通过标签而非物理位置/顺序引用设备”

**要点**：

- Michael W. Lucas 自述 FreeBSD Mastery: Storage Essentials 的成书动机：自 Absolute FreeBSD 之后，FreeBSD 存储栈经历了 CAM 层接管设备命名、默认分区方案转向 GPT 等重大变化，需要一次自底向上的连贯文档更新；该书从 CAM 与 GEOM 的 provider/consumer 堆叠讲起，对 UFS/FFS 做深度剖析，并论证 UFS 在许多场景仍是恰当工具，而体量庞大的 ZFS 留待单独成书。（BSD Now EP68，[1803.65-1936.66]，L1）
- 本期新闻聚合呈现 2014 年末 BSD 生态的多线动态：OpenSMTPD 自 OpenBSD 5.6 起成为默认邮件传输代理，sendmail 将于 5.7 完全移除，并发布邮件过滤 API 草案；OpenBSD 自研 httpd 于 5.6 首秀，以特权分离、默认 chroot 与近乎自然语言的配置语法获得早期用户好评；FreeBSD 的 opencrypto 框架在 FreeBSD Foundation 与 Netgate 赞助下加入 AES-ICM/GCM 模式与 AES-NI 支持，修复了一处可伪造消息的时序信息泄露，部分代码借自 OpenBSD 与 NetBSD。（BSD Now EP68，[3695.95-4047.35]，L2）
- 主持人梳理 BSD 磁盘术语的历史分层：BSD 自 1970 年代后期沿用至今，在 PC 语境中把容纳操作系统的磁盘段称 slice，其内再以 disklabel 划分 a（根）、b（交换）、c（整盘或整 slice）等 BSD partition，与 Windows、Linux 的 partition 概念形成名实错位；BSD 安装器以文本界面而非图形完成该过程，体现其文本配置传统。（BSDTalk EP3，[173.68-390.25]，L2）
- 主持人概述文件系统版图：UFS 与 FFS 常互称但非严格等同（他自承不明其差异并求教社区），作为稳定可信、长期存在、崩溃后通常可恢复的传统选择，Linux 与 Mac 系统亦可读取；FreeBSD 推出的 UFS2 在理论上突破 2TB 限制但仍有 disklabel 等额外障碍，并带来 ACL 与文件系统快照；NetBSD 已导入 UFS2 代码，OpenBSD 则因开发者无暇未移植，他公开呼召文件系统开发者贡献力量。（BSDTalk EP3，[434.04-602.74]，L2）
- 主持人以崩溃一致性为主线对比写盘策略：ext2 默认缓冲写盘换取速度而崩溃后可能难以恢复，FFS 以有序写出元数据再写数据换取安全，日志文件系统以盘上日志记录意图实现回滚，BSD 的 soft updates 则不以日志而以特定顺序排布元数据写入，崩溃后文件系统可能比预想新三十秒至一分钟但状态一致；他自述一直启用并视 soft updates 为三 BSD 通用推荐，同时承认存在边缘场景异议。（BSDTalk EP3，[749.22-888.76]，L1）
- 主持人补记 2005 年末的移植动向：FreeBSD 与 NetBSD 据其所知正移植 Silicon Graphics 的高性能日志文件系统 XFS；快照能力使后台文件系统检查成为可能，RAID 为三 BSD 共同支持，留待后续节目。（BSDTalk EP3，[853.36-954.50]，L2）

**史料**：

- 主持人以在场者身份回忆 OpenSMTPD 默认化的宣布现场：Henning Brauer 在 AsiaBSDCon 旅馆大堂的饮酒聚会上宣布这一消息，sendmail 作者 Eric Allman 亦在场并以“你是说你们还在用它？你们之前不是已经杀掉它了吗？”（3730.06-3733.06）打趣，构成 sendmail 时代落幕的一则第一手轶事，也旁证 BSD 会议非正式社交场合的史料价值。（BSD Now EP68，[3716.02-3733.06]，L1）
- Lucas 以作者身份详述 GBDE 的设计意图与一手考据：GBDE 借鉴 PGP 在战乱地区救援者场景中的教训——加密保护的不是被攻击者本人而是其联系人名单——故提供可销毁盘上密钥的机制，被胁迫时错误消息显示“密码正确，但盘上的密钥已被销毁”（2382.83-2388.76）；他并自述写作中发现 GBDE 缺陷，由技术评审 Poul-Henning Kamp 在付印前修复，属作者与原作者直接交互的罕见记录。（BSD Now EP68，[2301.87-2597.47]，L1）
- 该期构成 2005 年末三 BSD 文件系统能力实态的一手口述证词：UFS2 在 FreeBSD 已可用、NetBSD 刚导入、OpenBSD 未移植的梯度分布，soft updates 作为跨 BSD 推荐挂载选项的地位，以及 XFS 移植进行中的社区动向，均可作为该时点文件系统生态的口述史料。（BSDTalk EP3，[510.02-878.10]，L1）

**史观**：

- 总纲5 没有必然性，只有偶然性：Lucas 对磁盘子系统史的叙述揭示技术形态的偶然塑形：x86 移植时 BSD 需要五至二十个分区而 MBR 只支持四个，这一硬件偶然约束迫使开发者把 disklabel 塞入 MBR，造就分区中的分区即 slice 的术语错位与遍布内核的丑陋代码；他调侃“如果不得不写真正丑陋的代码，就让它遍布各处”（2806.19-2808.52），恰说明当下的结构并非必然演进的产物，而是偶然条件下的权宜沉淀。（BSD Now EP68，[2624.89-2819.89]，L1）
- 总纲4 分离聚合是永恒规律：反馈段转述的 ZFS 设备移除支持流向——先提交至 Delphix 树，随其发布上游至 Illumos，再进入 FreeBSD——呈现了 Oracle 之外 ZFS 代码在多个项目间的分叉与回流；代码在分离与聚合的循环中流转而非单向进步，上游路径本身即成为跨项目治理结构的记录。（BSD Now EP68，[4440.04-4535.39]，L2）
