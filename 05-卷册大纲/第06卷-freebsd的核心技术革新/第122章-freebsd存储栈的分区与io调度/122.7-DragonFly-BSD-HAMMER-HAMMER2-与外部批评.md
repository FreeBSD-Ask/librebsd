# 122.7 DragonFly BSD HAMMER/HAMMER2 与外部批评

## 122.7.1 DragonFly BSD 存储架构与 HAMMER/HAMMER2 对比

**要点**：DragonFly BSD 作为 2003 年从 FreeBSD 4.x 分叉的操作系统，选择了完全不同的存储栈路线：Matthew Dillon（马修·狄龙）设计的 HAMMER（2008 年 DragonFly 2.0 引入）和 HAMMER2（2017 年 DragonFly 5.0 引入）文件系统，内建卷管理、快照、复制、校验、压缩、去重等功能，设计理念与 ZFS 类似但完全独立实现；DragonFly 没有引入 GEOM 框架，其存储栈更简洁：设备层 → 磁盘调度器（`dsched`） → HAMMER/HAMMER2 文件系统；HAMMER2 使用 B+ 树、写时复制、端到端校验，支持集群镜像；DragonFly 也没有引入 CAM，而是继续维护传统的 SCSI/ATA 驱动栈；这种架构差异源于 Dillon 对 FreeBSD 5.0 时期 SMPng 和 GEOM 等大规模重构方向的不认同

**史料**：DragonFly BSD HAMMER/HAMMER2 文档；Matthew Dillon 2003 年 DragonFly 分叉声明；Dillon HAMMER 设计文档；DragonFly 5.0 Release Notes HAMMER2 章节［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］ 〔L3 官方文档〕

**史观**：总纲第 4 条——分离聚合是永恒规律：DragonFly 与 FreeBSD 的存储栈分化是 BSD 生态“分叉后独立发展”的典型——Dillon 不认同 FreeBSD 5.0 时代的架构方向（他认为 GEOM、SMPng 过度复杂化），选择分叉出去走自己的路；两种路线没有绝对的对错：FreeBSD 的 GEOM/CAM 提供了更好的模块化和扩展性，DragonFly 的一体化设计更简洁、HAMMER2 某些设计比 ZFS 更现代

**辨析**：一个常见误解是“HAMMER 是 ZFS 的克隆”——HAMMER 和 HAMMER2 是独立设计的文件系统，虽然功能集与 ZFS 有重叠（快照、校验、写时复制），但磁盘格式和实现完全独立；DragonFly 不使用 GEOM/CAM 不代表其存储栈“落后”——它只是做了不同的权衡：用更少的抽象层获得更好的性能和可维护性，但失去了模块化堆叠的灵活性；截至 2025 年，HAMMER2 仅在 DragonFly BSD 上可用，没有移植到 FreeBSD/Linux

**文献**：Dillon, M. (2008). *HAMMER File System Design*. dragonflybsd.org; DragonFly Project. *HAMMER2 Documentation*. dragonflybsd.org; DragonFly Project. *DragonFly BSD 2.0, 5.0 Release Notes*.［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

## 122.7.2 Valerie Aurora 对 Soft Updates 的批评与社区回应

**要点**：Valerie Aurora（当时名 Valerie Henson，ext4 文件系统开发者）于 2009 年 7 月 1 日在 LWN.net 发表文章“Soft updates, hard problems”（lwn.net/Articles/339337/），从 Linux 文件系统开发者视角对 Soft Updates 提出系统性批评，核心论点包括：Soft Updates 实现极端复杂、只有极少数开发者（基本只有 McKusick 本人）能完整理解和修改、崩溃后仍需 fsck 后台遍历（SUJ 当时尚未发布）、与日志相比没有本质性能优势、文件系统研究社区已基本放弃 Soft Updates 路线转向日志/写时复制；McKusick 和 FreeBSD 社区对这一批评未做正式回应，但 2012 年 SUJ 的引入事实上回应了“崩溃恢复慢”的批评；Harvard/CMU 等学术团队（Seltzer et al. 2000 USENIX 论文）对日志与 Soft Updates 的性能比较显示两者各有优劣，并非日志全面胜出

**史料**：Aurora 2009 LWN 文章原文；Seltzer et al. 2000 USENIX“Journaling Versus Soft Updates”论文；McKusick & Roberson 2010 SUJ 白皮书；LWN 文章讨论区 FreeBSD 开发者回应 ［B］

**史观**：总纲第 10 条——动手者创造历史：Aurora 的批评是 Linux 主流社区对 BSD 技术路线的典型审视——站在日志文件系统的视角，Soft Updates 确实“过于复杂”；但 Soft Updates 代表了一种不同的工程哲学：“通过精细的依赖分析和动态回滚保证一致性，而不是通过写日志增加额外开销”；这种哲学在 BSD 社区有吸引力，在 Linux 社区则难以被接受

**辨析**：需要准确引用 Aurora 的原话：“soft updates are, simply put, too hard to understand, implement, and maintain to be part of the mainstream of file system development”——这句话有具体语境：Aurora 讨论的是为什么 Soft Updates 没有成为文件系统主流，不是说 Soft Updates 技术上“错误”或“性能差”；一个重要背景：Aurora 是 ZFS-on-Linux 的支持者之一，她的批评也是为 ext4 和 ZFS 做辩护；NetBSD 6.0（2012）和 OpenBSD 7.4（2023）先后移除 Soft Updates，一定程度上印证了 Aurora 的维护复杂度批评

**文献**：Aurora, V. (2009-07-01). *Soft updates, hard problems*. LWN.net, lwn.net/Articles/339337/; Seltzer, M. I. et al. (2000). *Journaling Versus Soft Updates: Asynchronous Meta-data Protection in File Systems*. USENIX ATC '00; McKusick, M. K., & Roberson, J. (2010). *Journaled Soft-updates*. mckusick.com/softdep/suj.pdf. ［B］
