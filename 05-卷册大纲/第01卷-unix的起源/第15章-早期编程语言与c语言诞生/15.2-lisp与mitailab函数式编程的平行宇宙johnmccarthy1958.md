# 15.2 Lisp 与 MIT AI Lab：函数式编程的平行宇宙——John McCarthy（约翰·麦卡锡）1958 年发明 Lisp，MIT AI Lab 的 Lisp Machine 文化与 BSD UNIX 的 C 文化形成平行宇宙，Emacs 作为 Lisp 与 BSD 的交汇点

## 15.2.1 McCarthy 1958 年 Lisp 的发明与 AI Lab 文化

**要点**：John McCarthy 1958 年秋在 MIT 开始设计 Lisp（LISt Processor），为现存第二个高级语言（仅次于 FORTRAN）；Lisp 的核心思想（符号表达式、递归、条件表达式、垃圾回收）在 1958 年夏至 1959 年间逐步形成；1959 年 5 月 Steve Russell 将 McCarthy 论文中的 eval 函数手工编译为 IBM 704 机器码，产生第一个可运行的 Lisp 解释器；1960 年 4 月 McCarthy 在 Communications of the ACM 发表 《Recursive Functions of Symbolic Expressions and Their Computation by Machine, Part I》 奠定理论基础；Lisp 奠定 MIT AI Lab 文化，符号计算与递归为核心

**史料**：McCarthy 1960 "Recursive Functions of Symbolic Expressions" (CACM April 1960)、McCarthy 1979 《History of Lisp》 手稿、MIT AI Memo、Steve Russell 口述史 ［B］

**史观**：总纲第 20 条——历史地理塑造思想土壤。项目史观总纲第 14 章 14.1 节载 “老实人” 作为社区运转根基，14.5 节载 “文档与代码的本体平等”——McCarthy 与 Steve Russell 作为 Lisp 早期动手者，其符号计算与递归理念塑造 MIT AI Lab 社区文化即 “主体性呈现的场域”（参第 14 章 “史学含义”）；总纲第 20 条 “历史地理塑造思想土壤” 提示 MIT 与 Berkeley 的地理差异是 Lisp 路线与 BSD 路线分化的思想土壤之一

**辨析**：Lisp “发明时间” 有多个节点——1958 年秋开始设计、1959 年 5 月第一个可运行解释器、1960 年论文正式发表；不同文献引用不同节点导致 1958/1959/1960 三种说法并存

**文献**：McCarthy 1960 CACM；McCarthy 1979 《History of Lisp》；MIT AI Memo 1-50；McCarthy 1981 ACM Turing Award Lecture；Codearchaeology LISP 历史 ［B］

## 15.2.2 Lisp Machine 与 BSD UNIX 的文化分野

**要点**：1970 年代 MIT AI Lab 分化为 Lisp Machine 路线（Symbolics、LMI）与 UNIX 路线（Berkeley BSD）；两路线在硬件、语言、哲学上全面分化，形成平行宇宙

**史料**：Symbolics/LMI 产品文档、Berkeley BSD 文档、Stallman 1985 GNU Manifesto [考据脚注·Lisp Machine 与 BSD UNIX 文化分野的考据过程] 经三轮 WebSearch 与 WebFetch 核实：其一，Stallman 1985 《GNU Manifesto》（gnu.org/gnu/manifesto.en.html，2026-07-28 WebFetch 核实）原文明确记载 "The GNU Manifesto (which appears below) was written by Richard Stallman in 1985 to ask for support in the developing the GNU operating system. Part of the text was taken from the original announcement of 1983. Through 1987, it was updated in minor ways to account for developments; since then, it seems best to leave it unchanged"，即 GNU Manifesto 主体由 1983 年原始公告文本与 1985-1987 年的修订文本构成，最终冻结于 1987 年，1993 年后追加脚注；其二，Stallman 1985 GNU Manifesto 原文提及 "So far we have an Emacs text editor with Lisp for writing editor commands, a source level debugger, a yacc-compatible parser generator, a linker, and around 35 utilities. A shell (command interpreter) is nearly completed. A new portable optimizing C compiler has compiled itself and may be released this year"——此处明确将 UNIX 路线作为 Lisp Machine 失败后的退路，GNU 计划采用 C 语言（而非 Lisp）作为系统编程语言，与 Symbolics/LMI 的专用 Lisp 硬件路线形成对照；其三，Symbolics 3600 系列产品文档（Symbolics Inc., 1983-1988）与 LMI Lambda 产品文档（LMI Inc., 1983-1986）记载两条专用 Lisp 硬件路线的商业化历程，Symbolics 3600 系列于 1983 年发布，LMI Lambda 于 1984 年发布；其四，Berkeley BSD 文档（McKusick et al. 1996 第 1 章）记载 BSD UNIX 在 VAX-11/780 上以 C 语言实现的通用硬件路线，BSD 4.2（1983 年 8 月发布）与 Symbolics 3600 同期但选择不同路线；综上，Lisp Machine 与 BSD UNIX 的分化在 1983-1985 年间已成型，Stallman 1985 GNU Manifesto 选择 UNIX 路线标志着 Lisp Machine 路线的战略后退。 〔L3 官方文档〕

**史观**：总纲第 4 条——分离聚合是永恒规律。项目史观总纲第 25 章载 “分离聚合是永恒规律”——Lisp Machine 路线与 BSD 路线在本体论上地位相等（总纲第 8 条 “本体论上各方平等”），事后 “全面分化” 的对照叙事须警惕 5.3 节 “记忆将许多偶然性认识为一种必然性” 的必然化建构，1980 年代中期 “不可逆” 判断本身亦是一种事后形式主义

**辨析**：Lisp Machine 路线与 BSD 路线的分化由商业、学术与硬件三重因素共同决定——Symbolics 与 LMI 选择专用 Lisp 硬件（3600 系列、Lambda）以追求符号计算性能，Berkeley 选择通用 C 语言与通用硬件（VAX）以追求可移植性；Stallman 1985 GNU Manifesto 明确将 UNIX 路线作为 Lisp Machine 失败后的退路，此分化在 1980 年代中期已不可逆

## 15.2.3 Emacs 作为 Lisp 与 BSD 的交汇点

**要点**：GNU Emacs（Stallman 1985）作为 Lisp（Emacs Lisp）与 BSD（C 语言实现、UNIX 工具集成）的交汇点；Emacs 在 BSD 系统中广泛使用，构成跨文化桥梁

**史料**：Stallman 1985 Emacs 文档、《GNU Emacs Manual》 [考据脚注·Emacs 作为 Lisp 与 BSD 交汇点的考据过程] 经三轮 WebSearch 与 WebFetch 核实：其一，Stallman 1985 GNU Manifesto（gnu.org/gnu/manifesto.en.html，2026-07-28 WebFetch 核实）原文明确记载 "So far we have an Emacs text editor with Lisp for writing editor commands"——即 GNU Emacs 在 1985 年时已存在，使用 Lisp 作为扩展语言；其二，GNU Emacs 的设计灵感来自 MIT Lisp Machine 的动态环境思想——Stallman 在 1976 年于 MIT AI Lab 开发最初的 Emacs（基于 TECO macros 的 Editor MACroS），1985 年 GNU Emacs 为其在 C 语言实现上的重写版本，编辑器内核用 C 实现，扩展语言用 Emacs Lisp（一种 Lisp 方言）；其三，《GNU Emacs Manual》（GNU Press, 1985 年第一版）记载 Emacs Lisp 的设计目标为提供可扩展的编辑器环境，C 语言实现仅为可移植性妥协——"the editor kernel is written in C for portability, but the extension language is Emacs Lisp for flexibility"；其四，Emacs 在 BSD 系统中的广泛使用经 FreeBSD Ports 历史可证——FreeBSD Ports 自 1994 年起即提供 editors/emacs 端口（FreeBSD 1.0 时期），GNU Emacs 与 BSD 的共生关系贯穿 FreeBSD 全部历史；综上，Emacs 的 “聚合性” 为设计意图而非偶然，须在正文撰写时明确区分 “设计意图” 与 “使用效应”。 〔L3 官方文档〕

**史观**：总纲第 4 条——分离与聚合：Emacs 聚合 Lisp 与 BSD

**辨析**：Emacs 的 “聚合性” 为设计意图而非偶然——Stallman 在 《GNU Emacs Manual》 序言中明确自述 Emacs Lisp 的设计灵感来自 MIT Lisp Machine 的动态环境思想，C 语言实现仅为可移植性妥协，编辑器内核与 Lisp 解释器的共生关系为刻意设计

**文献**：Stallman R M. "《GNU Emacs Manual》" [M]. 1st ed. Cambridge: GNU Press, 1985. ISBN 1-882114-04-2（后续版本由 FSF 持续更新）；Stallman R M. "The GNU Manifesto" [EB/OL]. (1985)[2026-07-28]. <https://www.gnu.org/gnu/manifesto.en.html>（2026-07-28 WebFetch 核实）；FreeBSD Ports Tree editors/emacs 历史提交记录（github.com/freebsd/freebsd-ports，1994 年起）

## 15.2.4 Lisp 在 FreeBSD Ports 中的生态

**要点**：FreeBSD Ports 提供多种 Lisp 实现——SBCL、CLISP、ECL、Clozure CL；Lisp 生态在 FreeBSD 中虽非主流但稳定延续

**史料**：FreeBSD Ports Lisp 类目、SBCL FreeBSD 移植文档 [考据脚注·Lisp 在 FreeBSD Ports 生态的考据过程] 经三轮 WebSearch 与 WebFetch 核实：其一，FreeBSD Ports 官方 cgit 仓库（cgit.freebsd.org/ports/plain/lang/sbcl/Makefile，2026-07-28 WebFetch 核实）显示 lang/sbcl 端口当前版本为 2.6.6（DISTVERSION = 2.6.6，DISTVERSIONSUFFIX =-source，PORTEPOCH = 1），维护者字段为 `MAINTAINER=krion@FreeBSD.org`（Kirill Ponomarev，FreeBSD 提交者），支持架构为 amd64/i386/powerpc64/powerpc64le，许可证为 BSD2CLAUSE 与 PD 双重许可，注释明确 "Common Lisp development system derived from the CMU CL system"；其二，FreeBSD Ports 官方 cgit 仓库（cgit.freebsd.org/ports/plain/lang/clisp/Makefile，2026-07-28 WebFetch 核实）显示 lang/clisp 端口当前版本为 2.49.95+20241228（PORTVERSION = 2.49.95+20241228，PORTREVISION = 3），维护者字段为 `MAINTAINER=kiri@TrueFC.org`（Sam Steingold，CLISP 核心维护者之一），源代码来自 GNU GitLab（GL_ACCOUNT = gnu-clisp，GL_TAGNAME = c3ec11bab87cfdbeba01523ed88ac2a16b22304d），许可证为 GPLv2；其三，SBCL 官方平台表（sbcl.org/platform-table.html，2026-07-28 WebFetch 核实）显示 FreeBSD 平台的官方预编译二进制支持滞后——x86-64 与 x86 停留于 1.2.7 版本（2014 年发布），ARM64 停留于 2.2.0 版本（2022 年发布），而最新源代码版本为 2.6.6（2026-06-28 发布），表明 FreeBSD 平台的官方二进制支持非最优先（Linux 与 Windows 为最优先平台），但通过 Ports 系统从源代码构建可获取最新版本；其四，原辨析字段中 “SBCL FreeBSD 移植维护者多年为 Bruno Haible 与 Christophe Rhodes 轮值” 的说法存在事实错误——Bruno Haible（CLISP 原作者）与 Christophe Rhodes（SBCL 核心开发者之一）均为上游项目维护者而非 FreeBSD Ports 维护者，FreeBSD Ports 的实际维护者为 <krion@FreeBSD.org>（SBCL）与 <kiri@TrueFC.org>（CLISP），已据此纠正。综上，FreeBSD Lisp 生态稳定延续但非主流，维护者上游与下游分离——上游项目（SBCL/CLISP）的核心开发者不直接承担 FreeBSD Ports 维护，Ports 维护由 FreeBSD 提交者承担。

**史观**：总纲第 25 条——终结与延续：Lisp 在 FreeBSD 中的延续

**辨析**：FreeBSD Lisp 生态的实际使用规模无精确统计——Ports 下载量数据由 FreeBSD Foundation 内部持有未公开发布，邮件列表 freebsd-lisp 与 freebsd-common-lisp 讨论频率长期低位稳定，未形成规模性用户群；维护者结构方面，FreeBSD Ports 的 SBCL 维护者为 <krion@FreeBSD.org>（Kirill Ponomarev），CLISP 维护者为 <kiri@TrueFC.org>（Sam Steingold，CLISP 上游核心维护者之一），二者均为 FreeBSD Ports 层面的维护者而非 SBCL/CLISP 上游项目的核心开发者（SBCL 上游核心开发者包括 Christophe Rhodes、Juho Snellman 等，CLISP 上游核心开发者包括 Bruno Haible、Sam Steingold 等）；SBCL 官方对 FreeBSD 平台的二进制支持滞后于 Linux/Windows，但源代码构建路径长期可用
