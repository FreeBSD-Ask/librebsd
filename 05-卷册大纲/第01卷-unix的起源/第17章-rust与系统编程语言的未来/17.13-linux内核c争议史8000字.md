# 17.13 Linux 内核 C++ 争议史（约 8,000 字题注，实际篇幅以正文为准）

## 17.13.1 Linus Torvalds 对 C++ 的公开发难：1992 年尝试、2004 年 LKML 邮件与 2007 年 Git 选择 C 的理由

**要点**：Linus Torvalds 对 C++ 的批评贯穿 Linux 内核项目三十余年，形成三条主线：(1) 1992 年 Linux 内核早期曾尝试使用 C++ 编写内核代码，Torvalds 在 2004 年 LKML 邮件中回溯此次经验为"It sucks. Trust me - writing kernel code in C++ is a BLOODY STUPID IDEA."，称 1992 年的尝试为其 C++ 立场的直接经验来源；(2) 2004 年 1 月 19 日（PST），Torvalds 在 LKML 回复 Robin Rosenberg 关于 C++ 内核模块编译的讨论时（邮件主题"Re: Compiling C++ kernel module + Makefile"，由 Click Modular Router 自 2.4 至 2.6 内核移植问题引发），系统阐述了反对 C++ 的三大理由：异常处理机制在内核中"fundamentally broken"、编译器在背后隐藏内存分配不可接受、C 语言本身足以写出面向对象代码（如文件系统 VFS 层）；(3) 2007 年 9 月 6 日（BST，对应 UTC 9 月 6 日 17:50），Torvalds 在 Git 邮件列表（gmane.comp.version-control.git）与 Microsoft 工程师 Dmitry Kakurin 争论 Git 为何用 C 而非 C++ 时，发表了最为激烈也最为著名的批评："C++ is a horrible language... even if the choice of C were to do *nothing* but keep the C++ programmers out, that in itself would be a huge reason to use C."，并进一步批评 STL 和 Boost 导致"infinite amounts of pain"和"inefficient abstracted programming models"；这三条主线共同构成 Torvalds 从 C++ 支持者（大学时期使用 C++）到 C++ 反对者的完整转变叙事，其立场在 2022 年 Linux 6.1 接纳 Rust 为内核第二语言时被反复引用作为对比参照

**史料**：Torvalds 2004-01-19 LKML 邮件（Date: Mon, 19 Jan 2004 22:46:23 -0800 (PST)，回复 Robin Rosenberg，主题"Re: Compiling C++ kernel module + Makefile"，KernelTrap node/2067 存档）、Torvalds 2007-09-06 Git 邮件列表（gmane.comp.version-control.git，Date: Thu, 6 Sep 2007 18:50:28 +0100 (BST)，Message-ID: <alpine.LFD.0.999.0709061839510.5626@evo.linux-foundation.org>，LWN.net Article 249460 一手存档）、Torvalds 1992 C++ 尝试的二次引述（2004 邮件中提及）、Torvalds 1991 comp.os.minix 首次 Linux 公告 ［A］

**史观**：总纲第 4 条与第 17 条——分离聚合与证明世界先于解释和改造世界。项目史观总纲第 25 章载 “分离聚合是永恒规律”——内核语言选择是工程权衡与个人经验共同作用的结果，C 与 C++ 的路线分化即分离聚合的具体呈现

**辨析**：Torvalds 的 C++ 批评是否应被理解为技术真理还是个人偏好——需区分技术论证（异常处理、内存管理、ABI 稳定性）与修辞策略（"horrible language""BLOODY STUPID IDEA"）；Torvalds 2004 年邮件中"we did try C++ once already, back in 1992"的具体细节缺乏一手文档（1992 年 Linux 内核尚在 0.1x 版本，邮件列表存档不完整），仅能从 Torvalds 后续回忆中推断；2007 年 Git 邮件中 Torvalds 以 Monotone（C++ 编写的 VCS）为例说明 C++ 项目"horrible and unmaintainable"，但此批评的适用性因 Monotone 与 Git 的设计目标差异而存疑；Torvalds 本人 2022 年接纳 Rust 入内核时态度缓和，称“Rust 不是 C++”，暗示其反对的是 C++ 而非“非 C 语言”本身；[考据脚注] 2007 Git 邮件时区经 LWN.net Article 249460 一手档案邮件 Date 头 "Thu, 6 Sep 2007 18:50:28 +0100 (BST)" 复核——BST 为英国夏令时（UTC+1），对应 UTC 9 月 6 日 17:50:28，早期修正稿曾误标为 “9 月 5 日（PST）/ 9 月 6 日（UTC）”，实际即便换算为 PST（UTC-8）亦为 9 月 6 日 09:50:28，“9 月 5 日（PST）” 表述错误，已修正

**文献**：Torvalds 2004-01-19 LKML 邮件（KernelTrap node/2067 存档）；Torvalds 2007-09-06 Git 邮件列表（LWN.net Article 249460 全文存档，lore.kernel.org/all/alpine.LFD.0.999.0709061839510.5626@evo.linux-foundation.org/）；Torvalds 1991-08-25 comp.os.minix 首次 Linux 公告；Stroustrup B. ## 17.13.2 Linux 内核中 C++ 的实际使用尝试：GCC C++ 化迁移的冲击与内核模块 C++ 的实验

**要点**：尽管 Linux 内核主线从未正式接纳 C++，C++ 在 Linux 内核生态中的实际影响通过三条路径渗透：(1) GCC 编译器自身的 C++ 化迁移——2012 年 8 月 GCC 指导委员会批准 GCC 从 C 迁移至 C++ 实现（GCC 4.8 开始允许 C++ 子集，GCC 15.1 于 2025 年 4 月 25 日正式发布并完成全面 C++ 迁移，经 GCC 官方 releases.html 一手确认），这一迁移对 Linux 内核编译产生间接影响：内核构建系统需要确保主机编译器支持 C++ 以编译 GCC 本身，但内核代码本身仍需 C 编译器编译，形成“编译器用 C++ 写但内核用 C 编译”的微妙依赖关系；(2) 内核模块中 C++ 的社区实验——Click Modular Router（MIT 开发的可编程路由器框架）在 2000 年代初期尝试以 C++ 编写 Linux 内核模块（2.4 内核时代），正是该项目向 2.6 内核的移植困难触发了 2004 年 Robin Rosenberg 的 LKML 提问与 Torvalds 的著名回复；此后仍有零星 C++ 内核模块实验（如 2017 年 CppCon 上 Billy Baker 展示的"Almost Unlimited Modern C++ in Kernel-Mode Applications"），但均未进入主线；(3) Linux 内核中 C++ 风格的设计模式——内核大量使用函数指针表（如 file_operations、address_space_operations）、container_of 宏、虚拟文件系统（VFS）等 C 语言实现的面向对象模式，实质上是“用 C 写 C++”，Torvalds 2004 年邮件中明确承认"you can write object-oriented code (useful for filesystems etc) in C, *without* the crap that is C++"

**史料**：GCC 指导委员会 2012 年 C++ 迁移决定（gcc.gnu.org/wiki/CppConventions）、GCC 15.1 发布公告（2025-04-25，经 gcc.gnu.org/releases.html 一手确认）、Click Modular Router 文档（pdos.csail.mit.edu/click/）、Baker 2017 CppCon"Almost Unlimited Modern C++ in Kernel-Mode Applications"、Linux 内核 VFS 与驱动模型源码 ［A］

**史观**：总纲第 17 条与第 2 条——软件工程与实践先于理论：C++ 对内核的影响通过间接路径而非直接采纳

**辨析**：GCC 的 C++ 迁移是否意味着内核最终也会迁移——GCC 从 C 到 C++ 的迁移（2012-2025 历时 13 年）与 Linux 内核从 C 到 Rust 的迁移（2022-2026 历时 4 年）是两个独立过程，不应混淆；内核“用 C 写 C++”的设计模式是否应被视为 C++ 语言的隐性胜利——此论调忽略 C 语言面向对象编程的独立传统（如 X Toolkit Intrinsics、GObject 等），将面向对象等同于 C++ 是一种范畴错误；Click Modular Router 的 C++ 内核模块实验在 2.4 内核时代部分可用，但 2.6 内核引入的抢占式内核（preemptible kernel）与新的内核同步模型使 C++ 模块的异常处理和 RTTI 支持变得更为困难，此技术障碍非 Torvalds 个人偏好可完全解释

**文献**：GCC Wiki"C++ Conversion"（gcc.gnu.org/wiki/CppConventions）；GCC 15.1 Release Notes（2025-04-25，gcc.gnu.org/releases.html）；Click Modular Router（pdos.csail.mit.edu/click/）；Baker 2017 CppCon 演讲；Linux 内核 Documentation/ 目录下 VFS、driver-model 文档；Love 2010"Linux Kernel Development"第 3 版 ［B］

## 17.13.3 Linux 与 BSD 内核语言策略的对比分析

**要点**：Linux 与三大 BSD 在 1990 年代至 2020 年代遵循相似的内核语言策略——以 C 为唯一系统编程语言，但四者在执行严格性与演进路径上存在显著差异：(1) Linux 内核在 1992 年短暂尝试 C++ 后彻底放弃，Torvalds 以个人权威维持 C 单一语言政策直至 2022 年 Rust 入核，其决策模式为“仁慈独裁者”（BDFL）模式，个人偏好权重极大；(2) FreeBSD 内核从未有任何 C++ 实验记录，其语言策略由 Core Team 集体决策与 committer 社区共识驱动，决策模式为“精英治理”（meritocracy），工程论证（ABI 稳定性、构建依赖、可移植性）权重高于个人偏好；(3) NetBSD 内核以 C 为主，但在工具链层（如 makefs、crunchgen）中使用多种语言，其"of course it runs NetBSD"的可移植性哲学要求内核语言必须能在所有 57 种以上架构上编译，C++ 编译器的跨架构可用性不足构成技术障碍；(4) OpenBSD 内核在 Theo de Raadt（西奥·德·若特） 领导下执行最严格的语言政策——不仅禁止 C++，连 C 代码本身也需通过严格的安全审计，其语言保守主义与安全至上哲学直接关联，de Raadt 曾多次公开表示“复杂性是安全的敌人”，C++ 的语言复杂性在此视角下是安全威胁而非工程资产；四者共同构成 UNIX 内核语言保守主义的完整谱系——从 Linux 的“独裁者说 C”到 OpenBSD 的“安全要求 C”，保守主义的外在表现一致但内在逻辑各异

**史料**：Linux 内核文档 Documentation/process/coding-style.rst、FreeBSD 内核源码树与 committer 指南、NetBSD 内核源码树与 port 列表（wiki.netbsd.org/ports/）、OpenBSD 技术邮件列表与 de Raadt 公开演讲、freebsd-arch 与 freebsd-hackers 邮件列表存档 ［A］

**史观**：总纲第 5 条、第 6 条与第 23 条——组织结构塑造技术路径、技术路线分化与社区治理：四种内核语言策略的差异源于四种治理结构的差异

**辨析**：四种 BSD/Linux 内核语言策略的差异是否实质大于形式——所有四者均以 C 为内核语言，差异仅在边缘政策与演进路径上，此相似性可能反映的是 C 语言在操作系统内核领域的客观技术优势而非治理结构的差异；OpenBSD 的“安全要求 C”是否经得起实证检验——OpenBSD 内核虽为纯 C 但仍有安全漏洞，Rust 的内存安全保证在理论上可减少特定类别的漏洞，但 OpenBSD 社区认为 Rust 引入的构建复杂度与信任链扩展（需信任 rustc 编译器与 LLVM 后端）可能引入新的攻击面，此权衡尚无定论

**文献**：Linux 内核 coding-style.rst；FreeBSD committer's guide（docs.freebsd.org/en/articles/committers-guide/）；NetBSD 项目文档（netbsd.org/docs/）；OpenBSD 项目文档（openbsd.org/）；McKusick et al. 1996"The Design and Implementation of the 4.4BSD Operating System"；de Raadt 公开演讲与 OpenBSD 邮件列表存档 ［A］
