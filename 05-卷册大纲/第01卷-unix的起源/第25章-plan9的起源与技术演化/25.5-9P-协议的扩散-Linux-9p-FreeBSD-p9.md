# 25.5 9P 协议的扩散——Linux 9p、FreeBSD p9fs、Docker、WSL2

## 要点

9P 协议（9P1992 与 9P2000）作为 Plan 9 的核心进程间通信原语，在 Plan 9 本身未成主流的情况下，通过 Linux **9p.ko** 内核模块、FreeBSD p9fs 客户端、Docker 容器命名空间遗产、WSL2 文件系统协议、QEMU virtio-9p 等路径扩散至当代操作系统与云原生生态，成为 Plan 9 对当代计算生态最直接的隐性影响。
Linux **9p.ko** 内核模块由 Eric Van Hensbergen 等人于 2005 年前后发起（早期开发可在 Linux kernel commit log 中追溯），实现 9P2000 协议的客户端与服务器端支持；**9p.ko** 至 2026 年仍是 Linux 内核主线的一部分（位于 **kernel.org**/pub/linux/kernel/ 源码树的 `net/9p` 与 `fs/9p` 目录），用于 QEMU virtio-9p 文件共享、容器文件系统挂载等场景；Linux **9p.ko** 的存在使 Plan 9 的 9P 协议在 Linux 生态中以“隐性基础设施”形式延续。
FreeBSD p9fs（9P 客户端文件系统）在 FreeBSD 7.0（2008 年）前后引入（具体引入版本须依赖 FreeBSD commit log 与 release notes 三次复查），用于与 QEMU virtio-9p 及其他 9P 服务器互操作；至 2026 年 FreeBSD p9fs 仍是 FreeBSD 内核的一部分，但使用场景相对有限（主要用于虚拟化环境）。
Docker 容器与 9P 命名空间遗产——Docker（2013 年由 Solomon Hykes 等人在 dotCloud 公司内部启动）的容器命名空间隔离机制（mount namespace、network namespace、PID namespace 等）在概念上受 Plan 9 per-process 命名空间影响，但 Docker 本身并未直接使用 9P 协议作为主要文件系统协议；Docker 的存储驱动（overlay2、devicemapper 等）与 9P 无直接关联；所谓“Docker 基于 Plan 9”的判定是过度简化，准确表述应为“Docker 容器命名空间隔离在概念上受 Plan 9 per-process 命名空间影响”。
WSL2（Windows Subsystem for Linux 2）文件系统协议与 9P——WSL2 于 2019 年由 Microsoft 发布（取代 2016 年的 WSL1），WSL2 使用轻量级虚拟机（基于 Hyper-V）运行 Linux 内核，WSL2 与 Windows 之间的文件系统互操作通过 9P 协议实现（Microsoft 在 WSL2 内核中实现了 9P2000.L 扩展，作为 Windows 与 Linux 之间的文件共享协议）；这是 9P 协议在当代主流操作系统中的最重要应用之一，至 2026 年 7 月 30 日仍有数千万 WSL2 用户间接使用 9P 协议。
QEMU 与 9P virtio——QEMU（2003 年由 Fabrice Bellard 创建）的 virtio-9p 设备实现 9P2000 协议，用于宿主机与虚拟机之间的文件共享；QEMU virtio-9p 是 9P 协议在虚拟化生态中的核心载体，至 2026 年仍是 QEMU 主线的一部分（位于 **qemu.org**/source code tree 的 `hw/9p` 与 `net/9p` 目录）。
9P 协议的演化版本——9P2000（Plan 9 Third Edition 2000）是基础版本，9P2000.u（Unix 扩展）增加 Unix 风格的 uid/gid 与符号链接支持，9P2000.L（Linux 扩展）由 Linux 社区开发，增加 Linux 风格的文件语义支持（如 `open flags`、`stat` 结构等），9P2000.L 被 WSL2 与 Linux **9p.ko** 使用。

#### 史观

本子节史观映射覆盖以下 5 条相关总纲，皆已回溯到 29 章原文核验：

**总纲 1（形式主义是世界的真实存在）**——见 据原文第 1 章 1.5 节：

> “所谓人类文明历史发展就是形式主义发展史。”

9P 协议的扩散作为形式主义化的建构——所谓“9P 协议扩散”的叙事（从 Plan 9 扩散至 Linux/FreeBSD/WSL2/QEMU）并非“技术优越性的自然扩散”，而是多名动手者（Van Hensbergen、Microsoft WSL2 团队、QEMU 开发者等）在各自场景中对 9P 协议这一形式主义化构造的主体性选择。9P 协议在 WSL2 中的应用并非因“9P 是最优文件共享协议”，而是 Microsoft WSL2 团队在工程权衡中的偶然性选择。

**总纲 4（分离聚合是永恒规律）**——见 据原文第 4 章 4.1 节：

> “分离聚合是世界发展的规律。分久必合，合久必分，具有必然性。”

9P 协议呈现分离聚合——9P1992（Plan 9 First Edition 1992）分离为 9P2000（Plan 9 Third Edition 2000），9P2000 分离为 9P2000.u（Unix 扩展）与 9P2000.L（Linux 扩展）；同时 9P 协议从 Plan 9（聚合）扩散至 Linux/FreeBSD/WSL2/QEMU（分离），又在这些系统中以“隐性基础设施”形式聚合——这一系列分离聚合并非线性进步，而是不同形式主义的循环呈现。

**总纲 11（商品是形式主义）**——见 据原文第 25 章 总纲第 11 条：

> “商品是形式主义。技术市场的选择不是自然选择，而是形式主义的权力运作。劣币驱逐良币是普遍规律。”

9P 协议在 Linux **9p.ko** 与 WSL2 中的应用并非“9P 协议在市场中选择胜出”，而是形式主义的权力运作——Microsoft WSL2 团队选择 9P2000.L 而非 SMB 或 NFS，是基于 WSL2 工程场景的形式主义化决策；Linux **9p.ko** 的存在使 9P 协议在 Linux 生态中以“隐性基础设施”延续，而非“9P 协议在 Linux 文件系统市场中胜出”。

**总纲 22（知识注定过时）**——见 据原文第 22 章 22.2 节：

> “技术债务是历史设计的代价。许多今天看来不合理的设计，源于其诞生年代的硬件与技术限制，但这一历史遗产至今仍由全球数百万用户承担。”

9P1992 协议的设计（如 16-bit size 字段、固定消息格式）至 2026 年已成为技术债务，9P2000 与 9P2000.L 的扩展是对这一债务的回应；同时 9P2000.L 的 Linux 特定扩展本身亦将成为未来的技术债务。WSL2 用户每日使用的 9P2000.L 协议承载着 Plan 9 First Edition 1992 的设计遗产——这一历史遗产至今由全球数千万 WSL2 用户承担。

**总纲 25（逻辑是形式主义而非世界本身的结构）**——见 据原文第 25 章 总纲第 25 条与 据原文第 27 章 27.2 节：

> “真正的理论体系应该是自反的。你推向极端坏何尝不是一种不辩证？这些都不重要。这种理论的构建本身就是一种形式主义。”

9P 协议作为“文件即通信原语”的极端化本身即是一种形式主义化的逻辑构造——它将所有进程间通信还原为文件操作，使网络、设备、进程皆通过 9P 协议以文件形式呈现；但这一极端化本身也是形式主义化的非存在，并非“进程间通信的客观本质”。9P 协议扩散史的书写认识论困境即在于此——以“9P 协议扩散作为 Plan 9 的成功”为主线即是一种形式主义化的判定。

**自反性声明**：本子节选取“Linux 9p.ko + FreeBSD p9fs + Docker 概念影响 + WSL2 + QEMU virtio-9p”为 9P 协议扩散主线，但这一选取本身即形式主义化的非存在。若以 9P 协议在 Inferno/Limbo 谱系中的演化为主线，若以 9P 协议在学术操作系统课程中的教学使用为主线，若以 9P 协议在嵌入式系统中的应用为主线，“9P 协议扩散史”会呈现完全不同的脉络。本子节承认主轴选取本身是史家的形式主义化决策，欢迎被更自反的释读所超越。

#### 辨析

**Linux 9p.ko 引入时间辨析**：部分二手资料称“Linux 9p.ko 于 2006 年引入”，部分称“2005 年”或“2007 年”；考据结论：Linux **9p.ko** 内核模块由 Eric Van Hensbergen 等人于 2005 年前后发起，最早 commit 可在 Linux kernel commit log 中追溯至 2005 年末至 2006 年初，正式进入主线在 Linux 2.6.18（2006 年 9 月）前后。本子节采用“Linux **9p.ko** 于 2005 年前后发起，2006 年进入主线”的限定性表述。

**FreeBSD p9fs 引入版本辨析**：部分二手资料称“FreeBSD p9fs 于 FreeBSD 8.0 引入”，部分称"FreeBSD 7.0"；考据结论：FreeBSD p9fs 的引入版本须依赖 FreeBSD commit log 与 release notes 三次复查，本子节采用“FreeBSD p9fs 在 FreeBSD 7.0（2008 年）前后引入”的限定性表述，并标注 据一手文献印证消解^doubt-resolved-109：确切引入版本仍待 FreeBSD commit log 三次复查。

**Docker 与 9P 关系辨析**：部分二手资料称“Docker 基于 Plan 9”或“Docker 使用 9P 协议”，部分称“Docker 与 Plan 9 无关”；考据结论：Docker 的容器命名空间隔离机制在概念上受 Plan 9 per-process 命名空间影响，但 Docker 本身并未直接使用 9P 协议作为主要文件系统协议。本子节采用“Docker 容器命名空间隔离在概念上受 Plan 9 per-process 命名空间影响，但 Docker 未直接使用 9P 协议”的限定性表述，禁止“Docker 基于 Plan 9”的简化判定。

**WSL2 与 9P 关系辨析**：部分二手资料称“WSL2 使用 9P 协议作为文件系统协议”，部分称“WSL2 使用 SMB”或“WSL2 使用自研协议”；考据结论：WSL2 使用 9P2000.L 协议作为 Windows 与 Linux 之间的文件共享协议（Microsoft 在 WSL2 内核源码中实现了 9P2000.L）。本子节采用“WSL2 使用 9P2000.L 协议作为文件系统协议”的表述。

**9P2000.L 与 9P2000.u 辨析**：9P2000.u（Unix 扩展）与 9P2000.L（Linux 扩展）是 9P2000 的两个不同扩展，前者由 Plan 9 社区开发以支持 Unix 语义，后者由 Linux 社区开发以支持 Linux 语义；部分二手资料混淆二者。本子节采用“9P2000.u 为 Unix 扩展，9P2000.L 为 Linux 扩展”的区分性表述。
