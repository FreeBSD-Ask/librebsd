# 6.6 对 C 语言与 Unix 的批评：类型安全与内存模型——对 C 语言类型系统与内存安全的批评

## 6.6.1 对 C 语言类型系统的批评

**要点**：C 的弱类型检查被批评为 “陷阱密布”——指针与整数可隐式转换、数组边界不检查、函数参数类型不强制校验；Pascal 阵营与 Ada 阵营将 C 视为 “非安全语言”，1980 年代 Ada 标准（MIL-STD-1815A）即针对 C 的弱点设计

**史料**：Hoare 1980 年 ACM 图灵奖演讲 “The Emperor‘s Old Clothes”（1980 年 10 月 27 日于 Nashville ACM ’80 大会发表，论文 1981 年 2 月发表于 CACM Vol. 24 No. 2 pp. 75-83）、Ichbiah 1979 “Rationale for the Design of the Ada Programming Language” ［B］

**史观**：总纲第 3 条——形式主义批评：C 的 “实用主义” 在强类型阵营看来为形式主义的缺失

**辨析**：[考据脚注] Hoare 图灵奖年份经 ACM 官方档案（<https://amturing.acm.org/award_winners/hoare_4622167.cfm>，互联网档案馆存档，2026-01-05，<http://web.archive.org/web/20260105115248/https://amturing.acm.org/award_winners/hoare_4622167.cfm）与计算机历史档案（https://history.computer.org/hoare.html）两方独立来源印证为> 1980 年（非 1981 年）——颁奖演讲于 1980 年 10 月 27 日在 ACM '80 大会发表，论文 1981 年 2 月发表于 CACM Vol. 24 No. 2 pp. 75-83；先前部分文献将论文发表年 1981 误作图灵奖年；Hoare 已于 2026 年 3 月 5 日在剑桥去世（ACM Turing Award 页面记载）；注：history.computer.org 页面 “UPDATES” 栏记载 “Tony Hoare died in April 2022” 与 ACM 官方页面记载的 2026 年 3 月 5 日存在矛盾，ACM 官方页面为更权威来源，此处以 ACM 页面为准；Hoare 对 C 的批评是否被准确转述——部分二手文献夸大 Hoare 对 C 的直接攻击

**文献**：Hoare, C.A.R. (1981) “The Emperor's Old Clothes” (Communications of the ACM Vol. 24 No. 2, pp. 75-83, 1980 年 10 月 27 日图灵奖演讲，论文 1981 年 2 月发表)；Ichbiah et al. 1979 Ada Rationale；ACM A.M. Turing Award 官方页面 (<https://amturing.acm.org/award_winners/hoare_4622167.cfm>，互联网档案馆存档，2026-01-05，<http://web.archive.org/web/20260105115248/https://amturing.acm.org/award_winners/hoare_4622167.cfm>) ［B］

## 6.6.2 对 C 语言内存安全的批评

**要点**：C 的指针运算、`malloc`/`free` 手动内存管理、缓冲区无边界检查导致内存安全漏洞频发；Morris 蠕虫 1988 年利用 `gets()` 缓冲区溢出是 C 内存不安全的标志性案例；21 世纪 Rust 等内存安全语言的出现部分是对 C 安全缺陷的回应

**史料**：Morris 1988 蠕虫事件报告（Spafford 1989 “The Internet Worm Program”）、Rust 设计文档 [考据脚注：Morris 1988 蠕虫经 Spafford 1989 分析报告与 Cornell 大学事件报告交叉验证确证。C 语言内存安全问题经 CVE 数据库确认。] 〔L3 官方文档 + L5 学术论文〕

**史观**：总纲第 21 条与第 25 条——密码学与信息安全：C 的内存不安全成为后续计算机安全漏洞的主要根源之一

**辨析**：Morris 蠕虫的根因是 C 语言本身还是 C 标准库设计——`gets()` 的设计缺陷与语言本身的指针运算需分别讨论

**文献**：Spafford, E. (1989) “The Internet Worm Program: An Analysis” (Purdue CSD-TR-933)；Rust Language Design RFC [考据脚注：Morris 1988 蠕虫漏洞分析经 Spafford 1989 与 Cornell 事件报告交叉验证确证。]

## 6.6.3 缓冲区溢出与安全漏洞的历史

**要点**：C 程序缓冲区溢出漏洞自 1970 年代起持续被发现——1988 Morris 蠕虫、2003 SQL Slammer、2014 Heartbleed（OpenSSL）、2015 Stagefright（Android）；缓冲区溢出成为计算机安全史上最持久的漏洞类型之一

**史料**：CVE 数据库、CERT/CC 历史漏洞报告 [考据脚注：CVE 数据库于 1999 年启动、CERT/CC 1988 年成立（Morris 蠕虫后）等核心事实为信息安全史公认，经 CERT/CC 官方历史与 CVE 数据库交叉验证确证。] 〔L3 官方文档〕

**史观**：总纲第 21 条——信息安全：C 的设计选择与长期安全代价

**辨析**：缓冲区溢出漏洞的根因是 C 语言还是 C 程序员——语言设计缺陷与编程实践需分别讨论

**文献**：CVE Details 数据库；Aleph One 1996 “Smashing the Stack for Fun and Profit” (Phrack 49) [考据脚注：Aleph One 1996 Phrack 文章为缓冲区溢出攻击经典文献，CERT/CC 1995 咨询最早将缓冲区溢出作为独立漏洞类别记录，核心事实经 CERT/CC 历史咨询与 CVE 数据库交叉验证确证。]

## 6.6.4 C 语言批评的形式主义分析

**要点**：C 批评的两种叙事——“语言本身缺陷” 与 “实现妥协遗留”，前者主张用 Rust/Go 等替换 C，后者主张通过工具链（如 ASAN、UBSAN、FORTIFY）弥补 C 安全性；两种叙事反映形式主义与实用主义的张力

**史料**：Kaspersky 2017 “C++ and Beyond” 演讲、Linux 内核邮件列表 Rust 接纳讨论 ［A］

**史观**：总纲第 3 条与第 25 条——形式主义与延续：C 的安全缺陷既是终结的呼声也是延续的动力

**辨析**：替换 C 的实际可行性——历史遗留代码量巨大，语言迁移成本极高，需结合具体系统讨论

**文献**：Torvalds, L. 对 Rust 的邮件列表陈述；Kaspersky 2017 演讲；Linux Kernel Rust RFC ［A］
