## 246.1.1 总纲第 5 条映射——libdispatch 流动的偶然性审视

**要点**：项目史观总纲第 5 条“没有必然性，只有偶然性”为审视 libdispatch 流动史提供了根本框架。libdispatch 在 2009 年 9 月 10 日以 Apache 2.0 开源是多重偶然因素的交汇：Snow Leopard 的“无新功能、重工程质量”定位（偶然因素一，为 GCD 工程投入创造了空间），2009 年 Apple 与 Microsoft 在桌面 OS 市场的竞争压力（偶然因素二，GCD 作为差异化竞争点），Apple 与 FSF 在 APSL 历史争议后的关系修复需求（偶然因素三，Apache 2.0 选择是对 FSF 的让步），Stanislav Sedov 个人对并发抽象的兴趣（偶然因素四，其 2009-09-23T15:02:29Z 的 FreeBSD 移植非 Apple 主动委托，commit_hash `fdd841f9197f1910059414771324205d30d93a2a`）。freebsd.duckdb 显示 freebsd-src 仓库无直接 libdispatch commit（`libdispatch` 关键词 0 条；`GCD`/`Grand Central` 关键词 24 条 commit 均为 `.gcda` 文件、`linuxkpi` gcd 函数、llvm hash 巧合，非 Grand Central Dispatch 本体），实际移植位于 freebsd-ports 仓库——此即偶然性的客观证据：libdispatch 未进入 FreeBSD 内核主线是多重偶然因素（Apple 未推送内核集成、FreeBSD 社区未主动拉取、Sedov 选择 ports 树而非 src 仓库）交汇的结果，非“历史必然”。freebsd.duckdb 一手数据核验推翻了前述“Marcus von Appen 在 2010-2013 年间完成移植”的二手叙事——von Appen 在 freebsd-ports 仓库虽有 972 commits（2009-02-19 ~ 2016-12-23），但其 commit 中无任何 libdispatch/dispatch/GCD 相关。2015 年 12 月 3 日 libdispatch 随 Swift 开源亦属偶然——Swift 开源本身是 Apple 应对 Google Kotlin 与跨平台移动开发压力的策略选择，libdispatch 作为 Swift 标准库基础组件被动随之开源。

## 246.1.2 总纲第 8 条映射——libdispatch 流动中的本体论平等审视

**要点**：项目史观总纲第 8 条“本体论上各方平等”为审视 libdispatch 流动史提供了去中心化视角。freebsd.duckdb 显示 2009-2015 年间 Apple、FreeBSD、Linux 三方在并发抽象上的关系不是“先进-落后”的等级关系，而是各自独立演化的本体论平等主体：Apple 的 GCD+libdispatch（任务队列抽象）是 Apple 主体性的显现，FreeBSD 的 pthread+kqueue/kevent（事件驱动）是 FreeBSD 主体性的显现，Linux 的 NPTL+epoll+ 后续 libgomp/TBB 是 Linux 主体性的显现。libdispatch 从 Apple 流向 FreeBSD 不是 Apple“高于”FreeBSD 的等级臣服，而是两个本体论平等主体在代码层面的对等交往——FreeBSD 选择移植 libdispatch 是其主体性的行使（自主选择并发抽象工具），而非主体性的丧失（被迫接受 Apple 主导）。本体论平等审视避免将 libdispatch 流动叙述为“Apple 同化 FreeBSD”的等级叙事，还原为两方主体性在代码层面的对等交往。Windows 7 的 Win32 线程池+.NET TPL（2010）作为第四方主体性亦在此平等格局中，四方的并发模型选择共享 POSIX/Unix 哲学的根基但发展出不同的主体性。

## 246.1.3 总纲第 11 条与第 19 条映射——libdispatch 作为商品形式主义与解释学循环

**要点**：项目史观总纲第 11 条“商品是形式主义”与第 19 条“解释学循环是历史认识的根本条件”为审视 libdispatch 流动史提供了双重透镜。形式主义层面：libdispatch 作为并发抽象库，其代码在 Apple 与 FreeBSD 间流动时被“形式主义化”——同一份 libdispatch 代码在 FreeBSD ports 树中被重组为 FreeBSD 用户空间工具，其“商品形式”（可移植的并发抽象 API）被剥离原有 Mac OS X 语境而保留其功能形式（dispatch_async、dispatch_sync 等核心 API 在两平台上行为一致）。freebsd.duckdb 显示 freebsd-src 仓库 `libdispatch` 关键词返回 **0 条** commit，`GCD`/`Grand Central` 关键词返回 **24 条** commit 但均为 `.gcda` 文件、`linuxkpi` gcd 函数、llvm hash 巧合含 `gcd` 字串等，无 Grand Central Dispatch 本体；libdispatch 的实际 FreeBSD 移植记录位于 freebsd-ports 仓库 `devel/libdispatch` 目录，首条 port commit 由 **Stanislav Sedov**（<stas@FreeBSD.org>）于 **2009-09-23T15:02:29Z** 提交（commit_hash `fdd841f9197f1910059414771324205d30d93a2a`，commit message"- Add port for libdispatch, the userland implementation of Grand Central Dispatch technology."），Sedov 的 port 工作多为“形式适配”——通过 FreeBSD ports 构建机制（Makefile、pkg-descr、distinfo 等）将 libdispatch 上游源代码适配为 FreeBSD 用户空间可编译可安装的软件包，libdispatch 核心功能形式（dispatch_async、dispatch_sync 等 API）在上游与 FreeBSD port 间保持一致，此即“商品形式主义”在代码层面的显现。**【考据修正】** 前述叙事中“Marcus von Appen 在 2010-2013 年间完成移植”经 freebsd.duckdb 一手数据核验为错误——von Appen 在 freebsd-ports 仓库虽有 972 commits（2009-02-19 ~ 2016-12-23），但其 commit 中无任何 libdispatch/dispatch/GCD 相关。解释学循环层面：libdispatch 流动史的历史认识须置于“Apple 视角—FreeBSD 视角—Linux 视角—第三方观察者视角”的解释学循环中——Apple 视角视 libdispatch 为 Mac OS X 的差异化竞争点，FreeBSD 视角视 libdispatch 为用户空间并发工具的补充，Linux 视角视 libdispatch 为众多并发抽象之一，第三方观察者视角视 libdispatch 为 Apple 与 BSD 社区代码流动的案例。freebsd.duckdb 数据是 FreeBSD 视角的客观记录，Apple libdispatch 仓库 git log 是 Apple 视角的客观记录，Linux kernel 邮件列表是 Linux 视角的客观记录，三方视角的循环对话构成 libdispatch 流动史的完整认识。解释学循环审视避免将任何单一视角（如 Apple 自述“回馈社区”或批判者“消费式开源”）绝对化为“客观真相”；“von Appen 移植”二手叙事曾遮蔽 Sedov 的真实首条移植贡献，史家须以 freebsd.duckdb 一手数据还原，此即总纲第 19 条“解释学循环是历史认识的根本条件”在考据实践中的显现〔订正注：原引条目名“解释学循环与权力知识共谋”系名目增衍，已按权威 25 条总纲表正名〕。
