# 171.9 与同时期操作系统的比较——init 系统的多元路径

#### 要点

init 系统谱系呈现多元路径：大一统路径（systemd / macOS launchd / Solaris SMF）vs 极简路径（runit / s6）vs 演化路径（BSD rc.d / OpenRC）。macOS launchd 是 Apple 统一服务管理框架，同时管理 Launch Daemons（系统级）与 Launch Agents（用户会话级），取代传统的 cron、inetd、init、StartupItems 机制，引入时间 Mac OS X 10.4 Tiger（2005）**［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］**（Apple 文档未在 fetched 页面明确标注，建议进一步核查）。Solaris SMF（Service Management Facility）引入于 Solaris 10（2005）**［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］**（Oracle 文档站点重定向至 Cloud 登录页，建议通过互联网档案馆核查），与 launchd 同年引入，两者均为现代 init 系统的早期探索。**[重要更正]** OpenRC 由 Daniel Robbins 于 2001 年为 Gentoo Linux 1.0_rc6 独立开发，与 BSD rc.d **无派生关系**，仅在依赖式启动理念上有共鸣。runit 由 Gerrit Pape 开发，跨平台（GNU/Linux、*BSD、MacOSX、Solaris），三阶段启动，进程 1 极简，文档 `https://smarden.org/runit/`。s6 由 Laurent Bercot 开发，承袭 daemontools/runit，模块化工具箱，文档 `https://skarnet.org/software/s6/`。macOS launchd 早于 systemd 但较少争议，原因在于 Apple 闭源生态封闭性使社区无法争议。

**init 系统谱系分类与代表项目**：

| 路径类别 | 代表项目 | 共同特征 | 主要发行版 / 操作系统 |
|---|---|---|---|
| 大一统路径 | systemd（2010）、launchd（2005）、SMF（2005） | PID 1 整合多功能（服务管理、依赖、日志、网络等），代码规模大，单一组织主导 | Linux 主流、macOS、Solaris |
| 极简路径 | runit（Gerrit Pape）、s6（Laurent Bercot）、daemontools（D. J. Bernstein） | 进程 1 极简，强调服务监督，模块化工具箱，避免功能整合 | Void Linux（runit）、其他可选 |
| 演化路径 | BSD rc.d（NetBSD 1.5 / FreeBSD 5.0 / OpenBSD 4.9 / DragonFly BSD）、OpenRC（Gentoo 2001） | shell 脚本基础，依赖排序，文本配置，演化而非革命 | FreeBSD/NetBSD/OpenBSD/DragonFly BSD、Gentoo/Alpine（OpenRC） |

**[重要更正]** 任务描述中“OpenRC 受 BSD rc.d 影响”的陈述需修正——OpenRC **并非派生自 BSD rc.d**，而是由 Daniel Robbins 于 2001 年为 Gentoo Linux 1.0_rc6 独立开发的依赖式 init 脚本系统。OpenRC 采用 2-clause BSD 许可证，且"designed to be used in other Linux distributions and BSD systems"（Gentoo Wiki），但其设计起源是 Gentoo baselayout，而非 BSD rc.d。OpenRC 与 BSD rc.d 的相似点是“依赖式启动”，但两者独立发展。本节修正为“OpenRC 由 Daniel Robbins 于 2001 年为 Gentoo 独立开发，与 BSD rc.d 在依赖式启动理念上有共鸣，但无派生关系”。

runit 一手来源：smarden.org 官方文档（作者 Gerrit Pape）`https://smarden.org/runit/`。关键内容：runit 是跨平台 Unix init 方案，带服务监督（service supervision），替代 sysvinit 与其他 init 方案，运行于 GNU/Linux、*BSD、MacOSX、Solaris。设计原则：“The amount of code in process no 1 should be minimal”（进程 1 的代码量应最小化）。三阶段启动：Stage 1（`/etc/runit/1` 一次性初始化）、Stage 2（`/etc/runit/2` 持续运行 `runsvdir`）、Stage 3（`/etc/runit/3` 关机）。服务依赖自动解析。与 systemd/rc.d 的关系：runit 与 daemontools 同属“服务监督”流派，强调进程 1 极简；与 systemd 的“庞大进程 1”哲学相反；Void Linux 以 runit 为默认 init。

s6 一手来源：skarnet.org 官方文档（作者 Laurent Bercot）`https://skarnet.org/software/s6/`。关键内容：s6 是小型 UNIX 进程监督（service supervision）工具套件，承袭 daemontools 与 runit 的设计思路，定位为“toolbox for low-level process and service administration”。提供"Reliable service readiness notification, which is the basis for service dependency management“。提供”useful parts of socket activation ... without having to switch to any specific init system"。与 systemd/rc.d 的关系：s6 属于“极简服务监督”流派，与 runit、daemontools 同源；强调模块化、可组合，反对 systemd 的“一体化”设计；s6 与 runit 均可作为非默认 init 在现有系统上运行。

init 系统谱系分类：

- 大一统路径：systemd（Linux，2010）、launchd（macOS，2005）、SMF（Solaris，2005）——共同特征：PID 1 整合多功能（服务管理、依赖解析、日志、网络等），代码规模大，单一组织主导。
- 极简路径：runit（跨平台，Gerrit Pape）、s6（跨平台，Laurent Bercot）、daemontools（D. J. Bernstein）——共同特征：进程 1 极简，强调服务监督，模块化工具箱，避免功能整合。
- 演化路径：BSD rc.d（NetBSD 1.5 / FreeBSD 5.0 / OpenBSD 4.9 / DragonFly BSD）、OpenRC（Gentoo 2001）——共同特征：shell 脚本基础，依赖排序，文本配置，演化而非革命。

#### 史观

项目史观总纲第 8 条“本体论上各方平等”在本节叙事中具体体现为：init 系统多元路径各有其工程合理性——大一统路径（systemd/launchd/SMF）适合需要整合多种系统级服务的场景（如容器化、云原生）；极简路径（runit/s6）适合追求进程 1 极简与服务监督的场景；演化路径（rc.d/OpenRC）适合延续 shell 脚本传统与文本配置的场景。三者在本体论上地位相等，无“先进 vs 落后”之分，亦无“正确 vs 错误”之分。

项目史观总纲第 5 条“没有必然性只有偶然性”在本节叙事中具体体现为：systemd 在 Linux 阵营“胜出”是偶然的——若 Debian CTTE 2014-02-09 投票结果不同（4:4 平局后 Bdale Garbee 投 sysvinit 或 Upstart），systemd 在 Linux 阵营的扩散路径将完全不同；OpenRC、runit、s6 等替代方案在技术上同样可行，Void Linux 以 runit 为默认 init 多年稳定运行即是例证。systemd“胜出”非技术必然，而是 CTTE 主席一票之差的偶然结果 + Red Hat/IBM 商业资本推动 + 各发行版跟进的多重偶然性叠加。

macOS launchd 早于 systemd 但较少争议的判断须有具体证据：launchd 于 Mac OS X 10.4 Tiger（2005）引入，比 systemd（2010）早 5 年；但 launchd 较少引发社区争议，原因在于 Apple 闭源生态封闭性——macOS 是 Apple 闭源操作系统，launchd 由 Apple 内部开发，社区无法 fork 或替换，争议无意义。systemd 在 Linux 阵营引发争议，是因为 Linux 是开源生态，社区可以 fork（如 Devuan）、可以替代（如 OpenRC/runit/s6）、可以批评（如 LKML、邮件列表、博客）——开源生态的可争议性本身是开源精神的体现。

macOS launchd 较少争议的原因须有具体证据——Apple 闭源生态封闭性使社区无法 fork 或替换：macOS 是 Apple 闭源操作系统，launchd 由 Apple 内部开发，社区无法 fork 或替换（macOS 不支持更换 init 系统），争议无意义。这与 Linux 开源生态形成对比——Linux 是开源操作系统，社区可以 fork（如 Devuan）、可以替代（如 OpenRC/runit/s6）、可以批评（如 LKML、邮件列表、博客）。systemd 在 Linux 阵营引发争议，部分源于开源生态的可争议性。

init 系统谱系分类须谨慎——“大一统 / 极简 / 演化”三分法是史家选择的分类框架，物理存在的 init 系统本身并不自我宣称为某一类。某些 init 系统可能跨越分类（如 OpenRC 既有演化路径的 shell 脚本基础，又有极简路径的进程 1 设计；systemd 既有大一统路径的功能整合，又有演化路径的版本迭代）。本节采信三分法作为分析框架，但承认其形式主义性质。

**史观**：

- 总纲9 经验优先：Yahoo 采纳 FreeBSD 的决策过程是经验优先的典型样本：价格固然诱人，但当事人明言决定性因素是稳定性、性能与源代码可得性；关键判据不是基准测试而是日常运维事实——核心 Perl 脚本在 Linux 上反复崩溃而在 FreeBSD 上持续运行（1149.90-1170.77），动手运维者以自身经验完成裁决，任何理论性的操作系统优劣论证在此都退居其次。（BSD Now EP118，[962.62-1170.77]，L2）
- 总纲5 没有必然性，只有偶然性：Yahoo 与 FreeBSD 的结缘并无技术必然性可言：当事人自述当时公司无人了解 FreeBSD，只是“看到相关引用后决定一试”（849.54-858.54），一次偶然尝试叠加 Perl 崩溃差异的偶然事实，偶然地奠定了门户时代最大站点之一的生产基座；此后多次迁移计划均未完成，Yahoo.com 首页至 2015 年仍由 FreeBSD 服务，历史路径由偶然而非规律写成。（BSD Now EP118，[849.54-998.66]，L2）
- 总纲10 动手者创造历史：全期的叙事重心置于不显眼的劳作之上：主持人称赞 LibreSSL 移除 SSLv3 与 Tarsnap 安全赏金这类“吃力不讨好的工作”（2442.82-2445.26），指出删除特性并承受其连锁反应是不被看见的贡献，正因如此才要感谢源码树后的清理者；节目又在两周年之际向幕后编者 TJ 致敬，将其每周整理的 show notes 与选题组织确认为节目得以存在的隐形基底——书写对象由此从发布会与版本号转向维持系统运转的动手者。（BSD Now EP105，[2442.82-2464.44]，L2）
- 总纲8 本体论上各方平等：各 BSD 分支在同一时段的多线并进构成本体论平等的经验呈现：DragonFly BSD 合入 Linux 3.17 的 Intel 显卡栈更新并辅以 3.19 的稳定性修复，其图形进度反令 FreeBSD 侧主持人自嘲羡慕；OpenBSD 独立推进 tame() 沙箱、UEFI 启动与 SSLv3 清除；FreeBSD 侧则以 bhyve、多路径 TCP 补丁集与 11 CURRENT 应对——没有任何单一分支被叙述为普遍进步的主线，呈现的只是不同努力在各自曲线上的流转。（BSD Now EP105，[740.84-749.74]，L2）
- 总纲10 动手者创造历史：BSD 图书的生产方式本身即是动手者共同体的实践：作者多为 committer 或教程实践者，评审者为项目核心开发者，审定权部分落在项目基础机构（如 OpenBSD Foundation 审读背书）——出版不是外在于社区的产业链，而是动手者彼此校验、共同署名的延伸。（BSDTalk EP145，[210.72-228.88]，L1）
- 总纲21 革命与改革是历史方法论的分歧：Will 的对照呈现两种系统演化方法的分岔：Linux 侧以 upstart 一类新范式整体替换运行级传统，能力跃进而教学连续性断裂；BSD 侧守成 rc.conf 的声明式简明，牺牲部分自动化想象而保住一致性与可授性——革命与改革之别在服务管理的日常教学中显影。（BSDTalk EP145，[111.12-148.92]，L1）

**辨析**：

- 主持人补充的后续线索称 Yahoo 内部长期运行拼装混合的私有分支，掺杂 4.x、7.x 与 11.x 的代码片段，并流传 FreeBSD 4 二进制源码遗失、只能靠旧快照二进制维持运转的轶事（1197.18-1256.62）；该线索指向大公司私有分支与上游社区脱节的典型现象，但细节全凭转述与道听途说，不能作为直接史实引用。　[存疑脚注] YahooBSD 混合版本构成与 FreeBSD 4 二进制源码遗失轶事仅来自主持人转述 Hacker News 讨论及个人见闻，具体版本号与 Peter Wemm 快照故事细节均无一手文献佐证，本卡仅作线索存档（BSD Now EP118，[1197.18-1256.62]，L4）
- 访谈现场即时暴露了 relaunchd 的工程张力：主持人 Alan 当场指出以 system 拼接用户输入调用 rm 的命令注入风险与用 asprintf 拼出 shell 命令建目录的做法（2113.96-2124.72），Heily 承认初期 C 代码存在粗糙之处并明确警告不宜用于生产（2097.08-2104.40）；jail 内 socket 继承以免除 NAT 的设计被追问与 Capsicum 先初始化后锁定的权限模型存在冲突（2483.76-2527.08），说明把沙箱语义编入 init 配置在 2015 年仍是未经实践检验的新概念。（BSD Now EP118，[2061.88-2527.08]，L2）
- Syncthing 事件呈现边缘社区在数据时代的可见性困境：匿名使用统计默认关闭，而 OpenBSD 用户的隐私文化使其更倾向拒绝上报，项目方据“只有三名 OpenBSD 用户”的统计关闭了 /proc 路径错误的跨平台 bug 报告并让用户自行提交补丁（3737.82-3743.26）；博客作者随后开启自有全部机器的上报使 OpenBSD 用户数即时翻倍（3842.42-3847.54），计数基础设施的统计失真与社区“以可见性对抗不可见性”的抗争策略在同一事件中并置。（BSD Now EP118，[3686.46-3847.54]，L2）
- 本期最具考据价值的片段是当事人自纠：听众 Mason 来信指认主持人在上期约 1 小时 56 分钟处声称 X 进入基本系统的最大障碍是许可证不利于 BSD，并指出 X 许可证与 BSD 许可证几乎无异、NetBSD 与 OpenBSD 携带 X 已近二十年；Allan Jude 随即更正，澄清真正的障碍并非许可证，而是 FreeBSD 项目不愿为跨 FreeBSD 10 的五年生命周期维持 ABI 稳定而在基本系统内维护 X 的分支，X 的定位始终是 port；他同时透露 FreeBSD 正延续将组件移出基本系统的路线——Perl 自 FreeBSD 4 起已移除，OpenSSL 拟改为仅内部私用、用户态依赖自 ports 获取以加快补丁节奏。（BSD Now EP105，[3272.78-3362.70]，L1）
- 围绕 NextBSD 移植 LaunchD 的争议呈现流言与澄清的典型结构：一篇评论文章主张 FreeBSD 不应采用 LaunchD，Reddit 上正反意见交锋并引来大量社区邮件；Allan Jude 澄清所谓 XML 配置的恐惧源自过去某设备厂商对 launchd2 的 FreeBSD 移植，而 NextBSD 实际使用的版本改用 JSON 且更为精简，提醒听众核对正确版本再作评判；工程层面，Kip Macy 正在修复安装器以便发布可试用的 NextBSD ISO，Jordan Hubbard 与 Kip Macy 均已同意接受访谈但需待 EuroBSDCon 之后，PC-BSD 下一版将基于 FreeBSD 11 CURRENT 与 NextBSD 构建并集成 launchd，且计划按月发布镜像、或与 HardenedBSD 合流。（BSD Now EP105，[589.64-628.86]，L2）
