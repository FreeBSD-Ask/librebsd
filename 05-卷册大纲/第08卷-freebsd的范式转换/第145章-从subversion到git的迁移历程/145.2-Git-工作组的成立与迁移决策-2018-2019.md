# 168.2 Git 工作组的成立与迁移决策（2018-2019）

## 168.2.1 Git 工作组的成立语境与核心成员
  - 要点：经过多年讨论和初步试验，FreeBSD Core Team 于 **2019 年 Q2** 正式任命 Git 工作组（Git Working Group）负责规划和执行从 SVN 到 Git 的迁移；FreeBSD 基金会提供专项资金资助迁移工作，这是基金会首次为单一基础设施项目提供专项资助；Git 工作组核心成员经多源交叉验证包括：主席 **Ed Maste（emaste@）**（FreeBSD 基金会技术总监，整体协调与对外沟通）、**Ulrich Spörlein（uqs@）**（SVN→Git 转换工具与历史完整性）、**Li-Wen Hsu（lwhsu@）**（基础设施、CI/CD 与镜像运维）、**Warner Losh（imp@）**（文档、committer 培训与迁移指南）、**Glen Barber（gjb@）**（发布工程适配与 releng 分支迁移）、**Baptiste Daroussin（bapt@）**（ports 仓库迁移）；工作组采用公开透明的工作方式，所有讨论在 freebsd-git@ 邮件列表公开进行

  - 史观：总纲第 23 条——社区治理：Git 工作组的成立标志着 FreeBSD 基础设施决策从“松散讨论”走向“有组织的工程实施”，基金会资助与专门工作组的模式为此后的大型基础设施项目（如 WiFi 驱动改进、aarch64 优化等）树立了先例
  - 辨析：Git 工作组成员名单在不同来源中略有差异——核心成员（Ed Maste、Ulrich Spörlein、Li-Wen Hsu、Warner Losh）在所有官方公告中一致，其他成员（如 Glen Barber、Baptiste Daroussin）因负责特定仓库迁移而深度参与，但不总是出现在正式名单中；这是典型的开源项目“核心团队 + 领域专家”协作模式

## 168.2.2 迁移决策中的关键争论与妥协
  - 要点：Git 迁移决策过程中社区讨论的核心争议点包括：(1) **主仓库位置**：是使用自主托管的 **git.freebsd.org** 还是以 GitHub 为主仓库——最终决定主仓库自主托管，GitHub/GitLab 仅作为只读镜像；(2) **工作流选择**：是采用 Linux 式的“分布式维护者分层模型”还是延续 FreeBSD 传统的“单一主干 + committer 直接推送”模型——最终选择后者作为基础，同时引入可选的代码审查流程；(3) **历史转换完整性**：是否完整保留从 CVS 到 SVN 的全部 27 年提交历史——决定完整转换，包括作者映射、提交时间、提交信息等元数据；(4) **分阶段迁移顺序**：doc、src、ports 三大仓库的迁移顺序——最终确定 doc 先行（规模最小、风险最低）、随后 src（核心代码）、最后 ports（规模最大、最复杂）；(5) **代码审查工具**：继续使用 Phabricator 还是迁移到 Gerrit 或 GitHub PR——决定继续使用 Phabricator（reviews.freebsd.org），后于 2023 年迁移到 GitLab
  - 史料：freebsd-hackers 与 freebsd-git 邮件列表迁移方案讨论（2018-2019）；Git 工作组会议纪要；Core Team 迁移方案投票记录；Warner Losh“FreeBSD Subversion to Git Migration: Why?”博客文章 ［A］
  - 史观：总纲第 6 条——技术路线分化：每一个争议点的决策都是 FreeBSD 工程哲学的体现——自主托管体现技术自主原则、保守工作流延续体现“不破坏开发者体验”原则、完整历史转换体现对项目遗产的尊重
  - 辨析：社区内对 Git 的反对声音被部分外部评论夸大——实际不存在“有组织的反 Git 阵营”，讨论主要集中在具体方案细节而非“是否迁移”的方向问题；大部分 committer 认可 Git 是必然趋势，担忧主要在于迁移过程的风险和学习成本
  - 文献：Losh, W. (2020-09). *FreeBSD Subversion to Git Migration: Why?* bsdimp.blogspot.com; FreeBSD Git Working Group. (2019-2020). *Migration Proposal and Discussion Threads*. freebsd-git mailing list; FreeBSD Wiki. *GitTransition FAQ*. ［A］
## 168.2.3 分阶段迁移策略的工程设计
  - 要点：Git 工作组设计了精密的三阶段渐进迁移策略，以最小化对开发和发布流程的干扰：**第一阶段：doc 仓库（2020 年 12 月初）**——文档仓库规模最小、提交频率较低，作为试点验证迁移流程和工具链；**第二阶段：src 仓库（2020 年 12 月中下旬）**——核心代码仓库，风险最高，选择在 13.0 发布前的代码冻结窗口期迁移；**第三阶段：ports 仓库（2021 年 3-4 月）**——规模最大（超过 4 万个 port）、提交最频繁，留待最后且在 src 迁移经验基础上进行；每个仓库迁移都遵循相似流程：预先公告 → 提交冻结 → 最终转换 → 只读验证 → 开启写权限 → 镜像同步 → 事后复盘；迁移期间为 committer 提供了多轮培训、文档更新和实时支持

  **SVN→Git 三阶段迁移策略**：

  | 阶段 | 仓库 | 时间 | 特点 |
  |---|---|---|---|
  | 第一阶段 | doc | 2020.12 初 | 规模最小、风险最低，试点验证 |
  | 第二阶段 | src | 2020.12 中下旬 | 核心代码，13.0 代码冻结窗口期 |
  | 第三阶段 | ports | 2021.3-4 | 规模最大（4 万 + port），最后迁移 |

  - 史料：Git Transition Wiki 三仓库详细时间表（精确到小时）；freebsd-announce 迁移公告邮件；Ed Maste EuroBSDCon 2020“FreeBSD Git Migration”演讲；Git 工作组迁移后复盘报告 ［A］
  - 史观：总纲第 17 条——软件工程：三阶段渐进迁移是大型基础设施变更的典范实践——从低风险到高风险、从试点到全面推广、每一步都有验证和回退预案，这体现了 FreeBSD 发布工程团队的专业素养
  - 辨析：“渐进式迁移”并不意味着“拖延”——从 2019 年工作组成立到 2021 年 4 月全面完成历时约两年，这期间进行了大量工具开发、测试转换、committer 培训工作；ports 仓库因规模巨大（30 万 + 提交历史）确实遇到了未预见的技术挑战，导致比原计划略有推迟
  - 文献：FreeBSD Wiki. *GitTransition* (detailed hourly schedule); Maste, E. (2020). *FreeBSD Git Migration*. EuroBSDCon 2020; FreeBSD Git Working Group. (2021-04). *Git Migration Complete: Post-Mortem Report*. ［A］
## 168.2.4 Git 工作组决策史料辨析
  - 要点：Git 工作组决策过程的一手史料主要包括：(1) freebsd-git@ 邮件列表的公开讨论存档（最完整、最权威）；(2) Git Transition Wiki 页面的历史版本（记录了方案演变）；(3) Ed Maste、Warner Losh 等人的会议演讲和博客文章；(4) Core Team 的公开状态报告；Core Team 内部讨论和投票细节未完全公开，部分决策理由只能从公开信息推断；工作组决策总体遵循 Rough Consensus and Running Code 原则，没有进行正式的全社区投票
  - 史料：<freebsd-git@lists.freebsd.org> 完整存档（2019-2021）；wiki.freebsd.org/GitTransition 页面编辑历史；BSDCan/EuroBSDCon/MeetBSD 会议演讲资料；FreeBSD Foundation 季度/年度报告 ［A］
  - 史观：总纲第 3 条——形式主义膨胀：Git 迁移的决策过程体现了开源社区“公开讨论 + 核心团队决策”的形式化治理模式——公开讨论确保社区声音被听到，核心团队最终决策避免无限期讨论
  - 辨析：部分评论称“Git 迁移是基金会强行推动的”——这一说法不准确：基金会提供了资金支持，但技术决策由 Git 工作组（由资深 committer 组成）做出，Core Team 保留最终批准权；基金会资助使迁移工作能够更快推进，但并未改变社区决策流程
  - 文献：FreeBSD Project. *freebsd-git Mailing List Archives*. lists.freebsd.org; FreeBSD Wiki. *GitTransition* (page history); FreeBSD Foundation. (2019-2021). *Quarterly Status Reports*. ［A］
