# 168.4 基础设施与开发模式变革

## 168.4.1 git.freebsd.org 主仓库架构与镜像策略
  - 要点：FreeBSD 选择自主托管主仓库 **git.freebsd.org** 而非依赖 GitHub/GitLab，这一决策延续了从 CVS/SVN 时代开始的“基础设施自主”传统；git.freebsd.org 采用 GeoDNS 分布式架构，全球多个镜像站点就近服务开发者，主仓库位于 FreeBSD 集群基础设施；Web 界面使用 **cgit**（cgit.freebsd.org）提供轻量级代码浏览；访问方式支持 SSH（提交用）和 HTTPS（只读用）；GitHub（github.com/freebsd/）、GitLab（gitlab.com/FreeBSD/）等平台的仓库配置为 **只读镜像**，双向同步但不接受直接提交；提交权限管理延续 committer 分级制度——src committer、ports committer、doc committer 分别拥有对应仓库的推送权限
  - 史料：FreeBSD Committer's Guide Git 章节；FreeBSD Handbook 镜像章节；git.freebsd.org 架构说明（集群管理员文档）；cgit 配置文档 ［A］
  - 史观：总纲第 23 条——社区治理：自主托管主仓库是 FreeBSD 技术自主原则的体现——项目不将核心基础设施托付给任何第三方商业平台，避免平台锁定、服务条款变更或服务中断带来的风险；同时通过只读镜像利用 GitHub/GitLab 的生态便利性
  - 辨析：git.freebsd.org 与 cgit.freebsd.org 的关系需明确：git.freebsd.org 是 Git 协议/SSH/HTTPS 访问的主仓库域名，cgit.freebsd.org 是 Web 浏览界面；GitHub/GitLab 上的 freebsd 组织仓库是 **只读镜像**，不是主仓库——这是外部开发者最常见的误解之一；2023 年 FreeBSD 推出 GitLab 实例（gitlab.FreeBSD.org）用于代码审查和 CI，但主仓库仍保持在 git.freebsd.org
  - 文献：FreeBSD Project. *Committer's Guide: Git Primer*. docs.freebsd.org/en/articles/committers-guide/#git-primer; FreeBSD Project. *Handbook: Git Mirrors*. docs.freebsd.org/en/books/handbook/mirrors/#git; FreeBSD Cluster Administration Team. *Git Infrastructure Architecture*. wiki.freebsd.org. ［A］
## 168.4.2 代码审查演变：从 Phabricator 到 GitLab
  - 要点：FreeBSD 的代码审查系统在 Git 迁移前后经历了演变：(1) **SVN 时代早期（-2012）**：没有强制代码审查，committer 可以直接提交到主干，重要变更通过邮件列表讨论；(2) **Phabricator 时代（2012-2023）**：**Phabricator**（reviews.freebsd.org）于 2012 年引入，提供 Differential 代码审查工具，但审查是可选而非强制的，新 committer 或高风险变更建议审查；Phabricator 在 Git 迁移后继续使用了约两年；(3) **GitLab 时代（2023-）**：2023 年 FreeBSD 将代码审查从 Phabricator 迁移到自建 **GitLab** 实例（gitlab.FreeBSD.org），与 Git 工作流深度集成，CI/CD 管道也基于 GitLab CI 构建；值得注意的是，FreeBSD 始终未采用 GitHub Pull Request 作为官方审查渠道——GitHub 镜像保持只读，PR 不被官方处理

  **FreeBSD 代码审查系统演变**：

  | 时代 | 时间 | 工具 | 审查性质 |
  |---|---|---|---|
  | SVN 时代早期 | -2012 | 邮件列表讨论 | 无强制审查，committer 直接提交主干 |
  | Phabricator 时代 | 2012-2023 | Phabricator（reviews.freebsd.org） | 可选审查，新 committer 或高风险变更建议审查 |
  | GitLab 时代 | 2023- | GitLab（gitlab.FreeBSD.org） | 与 Git 工作流深度集成，CI/CD 基于 GitLab CI |

  - 史料：FreeBSD Phabricator 上线公告（2012）；reviews.freebsd.org 文档；FreeBSD GitLab 上线公告（2023）；Committer's Guide 代码审查章节 ［A］
  - 史观：总纲第 17 条——软件工程：代码审查从无到有、从可选到与 CI/CD 集成的演变，反映了 FreeBSD 项目规模扩大后对质量控制的制度化需求；200 人规模的项目可以靠个人能力和同行评审，1000 人规模的项目必须有制度化的审查流程
  - 辨析：常见误解称“Git 迁移后 FreeBSD 开始强制代码审查”——实际上代码审查并非 Git 迁移带来的突变，Phabricator 在 SVN 时代的 2012 年就已引入；Git 迁移确实使审查流程与版本控制集成更顺畅，但审查制度本身早于 Git 迁移
  - 文献：FreeBSD Project. (2012). *Phabricator Code Review Launch Announcement*. freebsd-hackers; FreeBSD Project. *Committer's Guide: Code Review*. docs.freebsd.org; FreeBSD Project. (2023). *GitLab Instance Launch Announcement*. freebsd-announce. ［A］
## 168.4.3 工作流变化：分支策略、提交规范与 MFC 延续性
  - 要点：Git 迁移后 FreeBSD 的核心开发工作流保持了高度延续性，并未发生革命性变化：(1) **分支模型**：main（原 head）、stable/N、releng/N.N 三层分支模型完全延续 SVN 时代，stable/13、stable/14 等命名保持不变；(2) **直接推送权限**：committer 仍拥有直接推送到 main 和稳定分支的权限（有权限分级），并非所有变更都必须通过 PR/审查；(3) **MFC 流程**：Merge From Current（将 main 分支的变更合并到稳定分支）的传统在 Git 下通过 git merge 或 git cherry-pick 继续执行，MFC-after 标签在提交信息中继续使用；(4) **提交信息规范**：提交信息格式要求延续，包括提交说明、PR/Reviewed-by/Tested-by/MFC-after 等标签；Git 带来的主要增量变化：(1) 本地分支功能使 feature branch 开发更便捷；(2) 离线提交成为可能；(3) git format-patch 替代 svn diff 生成补丁；(4) 轻量级标签和分支使实验性开发更容易
  - 史料：FreeBSD Committer's Guide Git 工作流章节；Committer's Guide SVN 时代历史版本对比；src/UPDATING 中 Git 相关说明；freebsd-current 工作流讨论 ［A］
  - 史观：总纲第 6 条——技术路线分化：FreeBSD 选择“保守演进”而非“革命式重构”工作流——在发挥 Git 分布式优势的同时最大限度保持开发者熟悉的工作模式，这与 Linux 内核的多层级维护者模型形成鲜明对比，体现了不同的社区文化和项目规模适配
  - 辨析：外部评论常误以为“Git 迁移意味着 FreeBSD 采用了 GitHub 式的 PR 工作流”——实际上 FreeBSD 保持了传统的 committer 直接推送模型，GitHub PR 从未成为官方贡献渠道；这一选择是有意为之：FreeBSD 认为 committer 制度经过 30 年验证是有效的，没必要为了“看起来更现代”而放弃自身传统
  - 文献：FreeBSD Project. *Committer's Guide: Git Workflow*. docs.freebsd.org/en/articles/committers-guide/#git-workflow; FreeBSD Project. src/UPDATING (Git migration notes, 2020-12); Losh, W. (2020-10). *FreeBSD Git Primer for Users*. bsdimp.blogspot.com. ［A］
## 168.4.4 CI/CD 与外部贡献生态变化
  - 要点：Git 迁移为 FreeBSD 带来的最显著长期变化是 CI/CD（持续集成/持续交付）能力的提升和外部贡献门槛的降低：(1) **CI/CD**：基于 GitLab CI 和 Cirrus CI 的自动化构建和测试管道在 Git 迁移后逐步建立，每次提交都会触发多架构构建和测试，这在 SVN 时代难以实现；(2) **外部贡献**：虽然 GitHub 不接受直接 PR，但开发者可以更容易地在 GitHub 上 fork 仓库、创建分支、生成补丁，然后通过 Phabricator/GitLab 或邮件列表提交；(3) **贡献门槛降低**：Git 的普及意味着熟悉 Git 的年轻开发者无需学习 SVN 即可参与 FreeBSD；(4) **代码托管生态**：与 GitHub/GitLab 的集成使得 FreeBSD 对外部开发者更可见，star 数、fork 数等指标提升了项目曝光度；Git 迁移后 FreeBSD 在 GitHub 上的外部贡献确实有所增加，但核心开发仍由已授权的 committer 团队完成
  - 史料：FreeBSD CI/CD 文档；Cirrus CI FreeBSD 配置；GitHub freebsd 组织统计数据；FreeBSD Foundation 年度报告中关于贡献者增长的数据 ［B］
  - 史观：总纲第 22 条——开源运动：Git 迁移使 FreeBSD 与当代开源生态基础设施接轨，降低了新开发者的进入门槛，这对于项目的长期可持续性至关重要——开源项目的生命力在于持续吸纳新贡献者
  - 辨析：“Git 迁移使 FreeBSD 开发速度大幅提升”这一说法需辩证看待——单个提交的合入速度不一定更快（因为审查流程可能更规范），但整体开发吞吐量确实因更好的工具链、更多外部贡献和 CI 自动化而提升；开发质量也因自动化测试而提高
  - 文献：FreeBSD Project. *CI/CD Documentation*. ci.freebsd.org; FreeBSD Foundation. (2021-2024). *Annual Reports* (contributor growth statistics); Cirrus CI. *FreeBSD CI Configuration*. github.com/freebsd/freebsd-src/tree/main/.cirrus.yml. ［A］
