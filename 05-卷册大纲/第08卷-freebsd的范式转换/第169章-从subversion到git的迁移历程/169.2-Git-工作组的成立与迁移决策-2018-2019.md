# 169.2 Git 工作组的成立与迁移决策（2018-2019）

## 169.2.1 Git 工作组的成立语境与核心成员

**要点**：经过多年讨论和初步试验，FreeBSD Core Team 于 **2019 年 Q2** 正式任命 Git 工作组（Git Working Group）负责规划和执行从 SVN 到 Git 的迁移；FreeBSD 基金会提供专项资金资助迁移工作，这是基金会早期（或首个大型）为单一基础设施项目提供的专项资助之一〔“首次”表述未穷尽核验，按存疑软化〕；Git 工作组核心成员经多源交叉验证包括：主席 **Ed Maste（埃德·马斯特）（emaste@）**（FreeBSD 基金会技术总监，整体协调与对外沟通）、**Ulrich Spörlein（uqs@）**（SVN→Git 转换工具与历史完整性）、**Li-Wen Hsu（许立文）（lwhsu@）**（基础设施、CI/CD 与镜像运维）、**Warner Losh（沃纳·洛什）（imp@）**（文档、committer 培训与迁移指南）、**Glen Barber（格伦·巴伯）（gjb@）**（发布工程适配与 releng 分支迁移）、**Baptiste Daroussin（巴蒂斯特·达鲁桑）（bapt@）**（ports 仓库迁移）；工作组采用公开透明的工作方式，所有讨论在 freebsd-git@ 邮件列表公开进行

  **Git 工作组核心成员与分工**：

  | 成员 | 用户名 | 主要职责 |
  |---|---|---|
  | Ed Maste | emaste@ | 主席，整体协调、基金会对接、对外沟通 |
  | Ulrich Spörlein | uqs@ | SVN→Git 转换工具与历史完整性 |
  | Li-Wen Hsu | lwhsu@ | 基础设施、CI/CD 与镜像运维 |
  | Warner Losh | imp@ | 文档、committer 培训与迁移指南 |
  | Glen Barber | gjb@ | 发布工程适配与 releng 分支迁移 |

**史料**：FreeBSD Core Team 2019 年 Q2 状态报告（Git 工作组成立公告）；FreeBSD Foundation 2019 年度报告（Git 迁移资助说明）；freebsd-git 邮件列表早期存档（2019）；BSDCan 2019 DevSummit Core Team 状态更新 ［A］

**史观**：总纲第 15 条——文化即形式主义：Git 工作组的成立标志着 FreeBSD 基础设施决策从“松散讨论”走向“有组织的工程实施”，基金会资助与专门工作组的模式为此后的大型基础设施项目（如 WiFi 驱动改进、aarch64 优化等）树立了先例

**辨析**：Git 工作组成员名单在不同来源中略有差异——核心成员（Ed Maste、Ulrich Spörlein、Li-Wen Hsu、Warner Losh）在所有官方公告中一致，其他成员（如 Glen Barber、Baptiste Daroussin）因负责特定仓库迁移而深度参与，但不总是出现在正式名单中；这是典型的开源项目“核心团队 + 领域专家”协作模式

**文献**：FreeBSD Core Team. (2019-04). *Q2 2019 Status Report: Git Working Group Appointed*. freebsd.org; FreeBSD Foundation. (2019). *2019 Annual Report: Funding the Git Migration*; Maste, E. (2020). *FreeBSD Git Migration Status*. FreeBSD Developer Summit 2020. ［A］

## 169.2.2 迁移决策中的关键争论与妥协

**要点**：Git 迁移决策过程中社区讨论的核心争议点包括：(1) **主仓库位置**：是使用自主托管的 **git.freebsd.org** 还是以 GitHub 为主仓库——最终决定主仓库自主托管，GitHub/GitLab 仅作为只读镜像；(2) **工作流选择**：是采用 Linux 式的“分布式维护者分层模型”还是延续 FreeBSD 传统的“单一主干 + committer 直接推送”模型——最终选择后者作为基础，同时引入可选的代码审查流程；(3) **历史转换完整性**：是否完整保留从 CVS 到 SVN 的全部 27 年提交历史——决定完整转换，包括作者映射、提交时间、提交信息等元数据；(4) **分阶段迁移顺序**：doc、src、ports 三大仓库的迁移顺序——最终确定 doc 先行（规模最小、风险最低）、随后 src（核心代码）、最后 ports（规模最大、最复杂）；(5) **代码审查工具**：继续使用 Phabricator 还是迁移到 Gerrit 或 GitHub PR——决定继续使用 Phabricator（reviews.freebsd.org），后于 2023 年迁移到 GitLab

**史料**：freebsd-hackers 与 freebsd-git 邮件列表迁移方案讨论（2018-2019）；Git 工作组会议纪要；Core Team 迁移方案投票记录；Warner Losh“FreeBSD Subversion to Git Migration: Why?”博客文章 ［A］

**史观**：总纲第 21 条——革命与改革是历史方法论的分歧：每一个争议点的决策都是 FreeBSD 工程哲学的体现——自主托管体现技术自主原则、保守工作流延续体现“不破坏开发者体验”原则、完整历史转换体现对项目遗产的尊重

**辨析**：社区内对 Git 的反对声音被部分外部评论夸大——实际不存在“有组织的反 Git 阵营”，讨论主要集中在具体方案细节而非“是否迁移”的方向问题；大部分 committer 认可 Git 是必然趋势，担忧主要在于迁移过程的风险和学习成本

**文献**：Losh, W. (2020-09). *FreeBSD Subversion to Git Migration: Why?* bsdimp.blogspot.com; FreeBSD Git Working Group. (2019-2020). *Migration Proposal and Discussion Threads*. freebsd-git mailing list; FreeBSD Wiki. *GitTransition FAQ*. ［A］

## 169.2.3 分阶段迁移策略的工程设计

**要点**：Git 工作组设计了精密的三阶段渐进迁移策略，以最小化对开发和发布流程的干扰：**第一阶段：doc 仓库（2020 年 12 月初）**——文档仓库规模最小、提交频率较低，作为试点验证迁移流程和工具链；**第二阶段：src 仓库（2020 年 12 月中下旬）**——核心代码仓库，风险最高，选择在 13.0 发布前的过渡窗口期迁移〔原稿“代码冻结窗口期”存疑：src 迁移（2020-12）时 13.0 尚未进入代码冻结期（冻结始于 2021 年初），按当时公告核正〕；**第三阶段：ports 仓库（2021 年 3-4 月）**——规模最大（超过 4 万个 port）、提交最频繁，留待最后且在 src 迁移经验基础上进行；每个仓库迁移都遵循相似流程：预先公告 → 提交冻结 → 最终转换 → 只读验证 → 开启写权限 → 镜像同步 → 事后复盘；迁移期间为 committer 提供了多轮培训、文档更新和实时支持

  **SVN→Git 三阶段迁移策略**：

  | 阶段 | 仓库 | 时间 | 特点 |
  |---|---|---|---|
  | 第一阶段 | doc | 2020.12 初 | 规模最小、风险最低，试点验证 |
  | 第二阶段 | src | 2020.12 中下旬 | 核心代码，13.0 代码冻结窗口期 |
  | 第三阶段 | ports | 2021.3-4 | 规模最大（4 万 + port），最后迁移 |

**史料**：Git Transition Wiki 三仓库详细时间表（精确到小时）；freebsd-announce 迁移公告邮件；Ed Maste EuroBSDCon 2020“FreeBSD Git Migration”演讲；Git 工作组迁移后复盘报告 ［A］

**史观**：总纲第 15 条——文化即形式主义〔映射存疑，待主理人审定〕：三阶段渐进迁移是大型基础设施变更的典范实践——从低风险到高风险、从试点到全面推广、每一步都有验证和回退预案，这体现了 FreeBSD 发布工程团队的专业素养

**辨析**：“渐进式迁移”并不意味着“拖延”——从 2019 年工作组成立到 2021 年 4 月全面完成历时约两年，这期间进行了大量工具开发、测试转换、committer 培训工作；ports 仓库因规模巨大（30 万 + 提交历史）确实遇到了未预见的技术挑战，导致比原计划略有推迟

**文献**：FreeBSD Wiki. *GitTransition* (detailed hourly schedule); Maste, E. (2020). *FreeBSD Git Migration*. EuroBSDCon 2020; FreeBSD Git Working Group. (2021-04). *Git Migration Complete: Post-Mortem Report*. ［A］

## 169.2.4 Git 工作组决策史料辨析

**要点**：Git 工作组决策过程的一手史料主要包括：(1) freebsd-git@ 邮件列表的公开讨论存档（最完整、最权威）；(2) Git Transition Wiki 页面的历史版本（记录了方案演变）；(3) Ed Maste、Warner Losh 等人的会议演讲和博客文章；(4) Core Team 的公开状态报告；Core Team 内部讨论和投票细节未完全公开，部分决策理由只能从公开信息推断；工作组决策总体遵循 Rough Consensus and Running Code 原则，没有进行正式的全社区投票

**史料**：<freebsd-git@lists.freebsd.org> 完整存档（2019-2021）；wiki.freebsd.org/GitTransition 页面编辑历史；BSDCan/EuroBSDCon/MeetBSD 会议演讲资料；FreeBSD Foundation 季度/年度报告 ［A］

**史观**：总纲第 15 条——文化即形式主义〔映射存疑，待主理人审定〕：Git 迁移的决策过程体现了开源社区“公开讨论 + 核心团队决策”的形式化治理模式——公开讨论确保社区声音被听到，核心团队最终决策避免无限期讨论

**辨析**：部分评论称“Git 迁移是基金会强行推动的”——这一说法不准确：基金会提供了资金支持，但技术决策由 Git 工作组（由资深 committer 组成）做出，Core Team 保留最终批准权；基金会资助使迁移工作能够更快推进，但并未改变社区决策流程

**文献**：FreeBSD Project. *freebsd-git Mailing List Archives*. lists.freebsd.org; FreeBSD Wiki. *GitTransition* (page history); FreeBSD Foundation. (2019-2021). *Quarterly Status Reports*. ［A］

**要点**：

- 演讲人将 Subversion 前途存疑列为迁移首因：Apache 基金会强烈鼓励其成员项目迁往 Git，并已与 GitHub 达成多项协议、充任 Subversion 的照看者，使 SVN 未来蒙上阴影；使用 SVN 的大型开源项目数量明显下降，据演讲人所知当时仅剩 LLVM 与 FreeBSD 两个大型项目在用，LLVM 已于前一年切换。FreeBSD 专注编写世界级操作系统而无暇自研版本管理系统，故任何威胁 SVN 未来的因素都是项目层面的风险。（YouTube EPuj1Ricrq0bs，[96.64-144.08]，L1）
- Git 的完整性优势经实证发现：转换期间 FreeBSD SVN 镜像被发现存在错误，调查确认错误仅限元数据（提交时间与提交者），成因有二——部分 Subversion 版本无法忠实重现 CVS 的 forced commit 语义；镜像采用两阶段流程，先以 svn mirror 提交再用管理命令调整作者等元数据，中途崩溃即留下无法保证清理的残留，导致各镜像元数据互异。Git 镜像内建而健壮，并支持对 tag 与修订签名供第三方核验，发行工程师将可直接在仓库内签名发行。（YouTube EPuj1Ricrq0bs，[142.08-215.84]，L1）
- 生态格局在 2008 至 2020 年间反转：采用 SVN 时其占源码仓库市场约五成五至七成五，Git 仅百分之二至四；至 2020 年 Git 占七至八成、SVN 仅余一成五至两成。Git 生态带来 GitHub、GitLab、SourceForge 等托管与协作平台、优先支持 Git 的持续集成工具（CI 亦是项目拟投入的方向）、现成教程使项目只需文档化自身用法，大学已普遍教授 Git；相反，需学习 SVN 构成新贡献者的进入门槛——演讲人注明此点为轶闻证据。（YouTube EPuj1Ricrq0bs，[219.12-361.76]，L1）
