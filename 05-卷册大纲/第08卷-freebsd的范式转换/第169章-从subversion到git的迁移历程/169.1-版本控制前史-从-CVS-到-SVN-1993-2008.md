# 169.1 版本控制前史：从 CVS 到 SVN（1993-2008）

## 169.1.1 FreeBSD CVS 时代（1993-2008）：从 CSRG 遗产到集中式版本控制

**要点**：FreeBSD 自 1993 年项目创立起即使用 CVS（Concurrent Versions System）作为版本控制系统，这一选择继承自 CSRG（Computer Systems Research Group）的 BSD 开发传统；CVS 在 FreeBSD 早期发展中发挥了关键作用，支撑了从 1.0 到 7.x 的 15 年开发历程；CVS 采用客户端-服务器架构，支持多人协作开发，但存在原子提交缺失、分支/标签操作昂贵、文件名移动支持差等固有缺陷；FreeBSD CVS 仓库最初运行于 freefall.FreeBSD.org，由 Core Team 成员维护，cvsup 成为开发者同步源码树的标准工具；到 2000 年代中期，CVS 的技术局限性日益明显，尤其在处理大规模分支合并和 vendor 分支管理方面

**史料**：FreeBSD CVSup 使用文档（2000 年代版）；freebsd-hackers 邮件列表 CVS 相关讨论（1990s-2000s）；FreeBSD 1.0-7.0 Release Notes；The FreeBSD Handbook（CVS 章节历史版本，Wayback Machine 存档） ［A］

**史观**：总纲第 25 条——终结与延续：CVS 作为 FreeBSD 第一代版本控制系统，承载了项目从创立到成熟的完整早期历史，从 CSRG 继承的 CVS 使用传统本身就是 BSD 技术谱系连续性的体现

**辨析**：FreeBSD 并非“一开始就选择 CVS”——CSRG 在 1980 年代使用 SCCS（Source Code Control System），CVS 是 1990 年代初才逐渐成为主流的开源版本控制方案；FreeBSD 项目创立时 CVS 已成为开源社区事实标准，这一选择更多是时代背景下的自然延续而非主动决策

**文献**：FreeBSD Project. (1993-2008). *CVS Repository History*. cvsweb.FreeBSD.org; FreeBSD Project. *FreeBSD Handbook: Using CVS* (historical editions, Wayback Machine archives); Berliner, B. (1990). *CVS II: Parallelizing Software Development*. USENIX Winter Conference 1990. ［B］

## 169.1.2 2008 年 CVS→SVN 迁移：Peter Wemm（彼得·韦姆） 推动的八年争论终局

**要点**：FreeBSD 从 CVS 迁移到 Subversion（SVN）的讨论持续约八年，最终由 Peter Wemm（peter@）主导推进，于 **2008 年** 完成迁移；迁移并非无争议——社区内部分开发者担忧 SVN 的复杂性、性能问题以及学习成本，但 CVS 的技术缺陷已成为项目发展的瓶颈；SVN 相比 CVS 的核心改进包括：原子提交保证、目录/文件重命名的一等支持、更高效的分支/标签实现、改进的二进制文件处理；SVN 迁移采用了类似后来 Git 迁移的渐进策略，先转换历史再逐步切换各仓库；SVN 时代 FreeBSD 保持了单一中央仓库模型，提交权限管理延续 CVS 时代的 committer 分级制度

**史料**：Peter Wemm 2008 年 CVS→SVN 迁移公告（freebsd-hackers）；SVN 转换工具与脚本（svn2svn 等）；FreeBSD 8.0 Release Notes（首个在 SVN 下完整开发的版本）；freebsd-hackers 邮件列表 SVN 迁移讨论线程（2000-2008） ［A］

**史观**：总纲第 6 条——技术路线分化：CVS→SVN 迁移是 FreeBSD 工程文化中“渐进式改进”传统的体现——历经八年讨论而非激进切换，这与后来 Git 迁移的漫长决策过程一脉相承

**辨析**：**关键事实修正**：CVS→SVN 迁移的主要推动者是 **Peter Wemm**，而非 Poul-Henning Kamp（波尔-亨宁·坎普）——Poul-Henning Kamp 是 FreeBSD 资深开发者和 Varnish 作者，但版本控制迁移并非由他主导；“经过八年争论”的时间跨度（约 2000-2008）反映了 FreeBSD 社区对基础设施变更的审慎态度

**文献**：Wemm, P. (2008). *FreeBSD Subversion Migration Announcement*. freebsd-hackers mailing list; FreeBSD Project. (2008). *Subversion Repository Conversion Notes*. wiki.freebsd.org; FreeBSD Release Engineering Team. (2009). *FreeBSD 8.0-RELEASE Announcement*. ［A］

## 169.1.3 SVN 时代的开发模式与局限（2008-2020）

**要点**：SVN 时代（2008-2020）是 FreeBSD 工程化快速成熟的十二年——这一时期发布了 8.x、9.x、10.x、11.x、12.x 五个大版本系列，完成了 Clang/LLVM 引入、bhyve 虚拟化、ZFS 生产级支持、pkg 软件包管理器重构等重大工程；SVN 的集中式模型与 FreeBSD 的“单一主干 + stable/N 分支”开发模式高度契合，svn merge 流程支撑了 MFC（Merge From Current）稳定分支合并机制；但 SVN 的局限性也在 2010 年代日益凸显：(1) 分支和合并在大规模代码库上性能较差；(2) 无离线提交能力，开发者必须联网才能工作；(3) 与新兴的分布式开发生态（GitHub、GitLab）脱节；(4) 第三方贡献者参与门槛高，必须生成 svn diff 补丁通过邮件发送

**史料**：FreeBSD Committer's Guide（SVN 时代版本）；FreeBSD 8.0-12.x Release Notes；svn.freebsd.org 仓库统计；Warner Losh（沃纳·洛什）“The Long Road to Git”博客文章 ［A］

**史观**：总纲第 17 条——软件工程：SVN 的十二年是 FreeBSD 从“黑客项目”向“工程化操作系统”转型的关键时期，集中式版本控制的严格性为这一转型提供了基础设施保障

**辨析**：SVN 并非“失败的过渡”——它在 FreeBSD 历史上发挥了承前启后的作用，解决了 CVS 的大部分紧迫问题，为后来的 Git 迁移积累了大规模版本控制迁移的经验；将 SVN 时代描述为“浪费的十二年”是后见之明的误读

**文献**：FreeBSD Project. (2008-2020). *Committer's Guide: Subversion Workflow*. docs.freebsd.org (historical editions); Losh, W. (2020). *The Long Road to Git*. bsdimp.blogspot.com; FreeBSD Foundation. (2020). *12 Years of Subversion: A Retrospective*. ［A］

## 169.1.4 Git 早期讨论与其他 VCS 评估（2010-2018）

**要点**：FreeBSD 社区关于迁移到分布式版本控制系统的讨论始于 **2010 年代初期**，几乎与 Git 在 Linux 内核成功后开始流行同步；社区评估了多种分布式 VCS 选项，包括 Git、Mercurial（hg）、Bazaar（bzr）等；Git 之所以最终胜出而非 Mercurial 等其他 DVCS，原因包括：(1) Linux 内核采用 Git 产生的网络效应；(2) GitHub 平台的快速崛起提供了良好的外部协作生态；(3) Git 在性能和大型仓库处理上的优势；(4) 2010 年代中期以后 Git 已成为开源界事实标准；同期其他 BSD 项目的 VCS 选择形成对照：DragonFly BSD 从创立起（2004 年）即使用 Git，NetBSD 长期讨论后于 2020 年代完成 CVS→Git 迁移，OpenBSD 则坚持使用 CVS 至今（2026 年）

**史料**：freebsd-hackers 邮件列表 Git/Mercurial/Bazaar 讨论线程（2010-2018）；Ed Maste（埃德·马斯特） MeetBSD 2018“Git for FreeBSD”演讲；BSD Now Episode 316: git commit FreeBSD（2019）；NetBSD、OpenBSD VCS 相关文档 ［A］

**史观**：总纲第 22 条——开源运动：VCS 选择不是纯粹的技术决策，而是社区生态与网络效应共同作用的结果——Git 的胜利很大程度上是开源生态整体迁移的结果，而非单一技术优势

**辨析**：经邮件列表库验证通过（来源：freebsd-git 列表，Message-ID <CAPyFy2CKdHW_KkOOQozPW04jBDz8ZaNWSJLqFWAdzKcaDfSzcA@mail.gmail.com>，2017-02-21，Ed Maste 发起“Reconsider switching from svn to git?”，Warner Losh 回复）；经邮件列表库验证通过——2014-11-16 Bartłomiej Rutkowski 发起“First step towards GitHub integration”（Message-ID <9A004225-B20E-4795-971A-B363F02B78BC@FreeBSD.org>），Alfred Perlstein、Craig Rodrigues、Kubilay Kocak 参与；2017-02-21 Ed Maste 发起“Reconsider switching from svn to git?”（Message-ID <CAPyFy2CKdHW_KkOOQozPW04jBDz8ZaNWSJLqFWAdzKcaDfSzcA@mail.gmail.com>），Warner Losh、Ulrich Spörlein、Grzegorz Junka 等多方参与讨论。常见误解称“FreeBSD 因为不喜欢 林纳斯·托瓦兹（Linus Torvalds）而迟迟不迁移 Git”——这是没有证据的猜测，社区讨论主要聚焦于技术适配性、工作流连续性、迁移成本等实际问题，而非个人好恶；林纳斯·托瓦兹（Linus Torvalds）的个人风格与 FreeBSD 社区文化确有差异，但这从未成为正式讨论中的因素

**文献**：Maste, E. (2018). *Git for FreeBSD*. MeetBSD 2018 presentation; BSD Now. (2019-09-18). *Episode 316: git commit FreeBSD*; OpenBSD Project. *Why OpenBSD Developers Use CVS*. openbsd.org/anoncvs.html; Torvalds, L. (2005). *Git initial release announcement*. Linux Kernel Mailing List. ［A］

**要点**：

- Bryan Cantrill 指出 POSIX 将 madv_dontneed 定义为“近期不再使用此内存”的建议，FreeBSD 与 illumos 将其实现为纯粹的页面置换优先级建议并保留映射，Linux 却将其实现为立即撕毁映射并保证再次访问读到全零，语义与所有其他 Unix 截然不同；Joyent 团队严格按建议语义实现该调用后，依赖 Linux 破坏性语义的 jemalloc（随 Facebook 代码引入）在生产环境于调用栈深处离奇崩溃，且因无帧指针而难以取得栈回溯，排查极为艰难。他还以 mmap 为例说明“撕毁映射要击落 TLB、改写页表”的真实开销，批评依赖未经度量的直觉判断系统性能。（BSD Now EP117，[3446.14-3786.44]，L1）
- Cantrill 阐明 BSD、illumos 与 Linux 对“操作系统”边界的定义分歧：前二者视操作系统为内核、用户态与系统工具的整体，ls 亦属操作系统；Linux 则只是内核，GNU 栈与 glibc 皆属发行版层面，这也解释了 GNU 与 Linux 之争的根源。正因 Linux 将 ABI 僵化地锚定在系统调用层且极不情愿破坏任何应用，SmartOS 得以在 LX 品牌化区域中完整实现 Linux 系统调用表使 Linux 二进制直接运行；该机制原为 Sun 所创、因当年 Linux 演进过快而封存，2014 年由社区成员在区域内跑通 Linux 版 Skype 而意外复活，此后经 2014 至 2015 年推向完成。（BSD Now EP117，[2111.92-2333.50]，L1）
- Cantrill 以航空安全作类比主张事后调试是可靠软件的基石：软件失败时必须留存状态快照，如同驾驶舱语音记录器与飞行数据记录器之于法航 AF447 事故——直到找到记录器才确认空速管结冰与人为失误；拒绝取证如同在被连环杀手肆虐的城市里宣布关闭太平间。他进而批评 Linus Torvalds 约 2001 年表达过的“使系统可调试会让开发者变软”的立场，认为技术者负有尽最大努力构造可靠系统的社会责任，拒绝为此提供机制的态度在伦理上不可接受。（BSD Now EP117，[5215.96-5305.30]，L1）
- 斋藤博纪自述入道经历：入大学前使用 PC-98（日本特有规格的 IBM 兼容机）加 MS-DOS，经电话线拨号与他人通信；进大学后接触 Sun 工作站与 IBM AIX，深受震撼，遂想在自家机器上运行 UNIX。因 PC-98 规格特殊需要移植版 PC UNIX，当时 Linux 与 FreeBSD 均有移植而只有 FreeBSD 能在其机器上运行；版本约 2.2.5，机器仅 8MB 内存与 180MB 硬盘，编译 X 花了两天。直接动机是在原生 UNIX 环境使用正宗 TeX 实现撰写论文——MS-DOS 上须借 DOS 扩展器才能用扩展内存——此后学习网络配置接入互联网。（BSD Now EP59，[1743.93-2004.19]，L1）
- 日本 BSD 生态的转折点（当事人一手叙述）：1994—1995 年日本 FreeBSD 用户众多；NetBSD 引入 newconfig 配置框架后，日本许多能读内核代码的高手认为应基于 config 实用工具另建配置框架并写出自有代码，但美方多数人不知该代码存在；这些日本开发者相信自己代码技术上更优，却不参与英文邮件列表讨论，仅投递超长行数的补丁且不说明理由，补丁因难读难懂而被忽略。结果是多数日本 FreeBSD 开发者转投 NetBSD，部分人随后创立公司；IIJ 作为主要 ISP 因熟悉内核而在服务与产品中大量采用 NetBSD。日本 FreeBSD 拥趸的这次集体转向，塑造了此后亚洲 BSD 大会浓厚的 NetBSD 色彩，而日本其他开源会议多面向爱好者而非开发者。（BSD Now EP59，[2227.32-2511.23]，L1）
- 当代工作与组织改革设想：斋藤近期积极改进 FreeBSD 的 IPv6 栈——KAME 项目结束后该栈实际无人维护，而 IETF 与 RFC 持续发布新规范需跟进实现。作为 core team 成员，他拟提交 Quality Assurance 团队提案：汇集分散的测试基础设施努力，以统一 web 界面保存各分支的质量评估并供开发者共享，纠正对个人努力的依赖（此前的性能分析者离开后工作即中断），并为 core team 的方向决策提供咨询。作为 Foundation 董事，他运营 AsiaBSDCon、走访企业与洽谈镜像站点；另设立本地非营利组织作为与企业谈判的凭据，因其直言日本人只信任有机构背景者而非热情个人：NEC 的 UNIX 服务器软件销量居日本之首、大量客户想用 FreeBSD 却不知如何获得支持，他已向 NEC 提供信息并获积极回应；Sony 则因保密文化几无信息可获——曾谈成的开发者采访在 Sony 要求预审问题清单后杳无音信，且公司内部必须经经理层许可，开发者本人无对外联络的决策权。（BSD Now EP59，[2011.63-2783.80]，L1）
- IPFW 十余年来最大更新的要点：表可命名（至多 65000 个表、每个名称 63 字符）、表感知规则集可实现原子切换、批量增删、新增 flow 表类型与按 CIDR 哈希/接口/数字/流等多种查找算法、表值可承载多数据字段；主锁改为 RM lock，规则计数器与规则本体分离并按 CPU 分配以降低锁争用；旧命令行工具对新内核接口保持 ABI 兼容但无法识别表名、一律显示为表 65535。BSD Router Project 维护者 Olivier 的基准测试（4 核 Xeon 2.13GHz 配 Intel X540 双口万兆网卡、2000 条状态）显示改动前后吞吐提升约每秒 10 万包，其本人表示期待出现 pfsync 的 IPFW 等价物。（BSD Now EP59，[1391.89-1594.26]，L2）
- Fossil 的定位是为其自身与 SQLite 的配置管理而设计的分布式软件配置管理系统，不属三大主流之列：它把分布式 bug 跟踪与 wiki 与版本控制纳入同一包，离线时可看 bug、加评论、改代码、改 wiki，联网后自动同步；单文件无依赖二进制适配公司统一配置笔记本的场景；内置 web 界面随 fossil ui 一键启动本地服务器并拉起浏览器，克隆 Fossil 项目本身即可在本地得到连同全部历史的完整官方网站。（BSDTalk EP194，[406.12-714.12]，L1）
- 存储设计上，Fossil 仓库被定义为无序的 artifact 袋，每个 artifact 有简单而明确界定的文件格式，设计目标是让尚未出生的人也能使用、阅读与扩展这一长期格式；现行实现把 artifact 以 delta 与 zlib 压缩存入 SQLite，但此属实现细节，他人可重写为兼容实现；SQLite 九年的 CVS 历史（三百余兆）导入后仅约三十兆，同步协议高效到可在拨号网络使用。（BSDTalk EP194，[807.48-930.76]，L1）
- Fossil 强制以整个项目连同全部分支为同步单位，被当事人视为特性而非限制：他要迫使项目成员始终共享全部工作，保留所有未成功的丑陋分支与反复犹豫；其原始动机是高可靠软件需要默认完整、可审计且不可伪造的开发史，以此对照 Git 用户热衷的 rebase——把长串修订压缩成干净提交，本质是把历史改写得比实际更整洁。（BSDTalk EP194，[1005.32-1146.12]，L1）
- 权限模型兼取两端：克隆不包含用户安全数据库，全局状态即全部 artifact，而各仓库可设本地权限；Fossil 自托管的三个主仓库只允许已签署版权转让者推送，任何人可克隆并本地随意提交，但无密码不得推回中央；已有第三方克隆 SQLite 仓库加入自定义修改对外分发，当事人称此为分叉友好并视之为开源本义。（BSDTalk EP194，[1156.60-1282.80]，L1）

- FreeBSD 2014 年第三季度状态报告（7—9 月）所载一手进展：core team 报告含 git.freebsd.org 提升为官方服务、与 Foundation 协商取得 ZenForo 论坛软件许可、与 Oracle 谈成 Java 7/8 官方支持（开放 OpenJDK 代码双向流动并提供 TCK 测试框架签署认证）、在贡献者与 committer 之间居中调解；UEFI 状态报告确认 10.1 采用常规镜像加单独 UEFI 镜像、11 快照为混合镜像、boot1.efi 的 ZFS 驱动列为待实现、作者笔记本在 Optimus 独显模式下 UEFI 无法定位显卡的调试案例；VT 控制台驱动补齐 vidcontrol 特性、CJK 字体进行中并在 11 默认启用；John-Mark Gurney 向 OpenCrypto 框架加入 AES-GCM 与 AES-CTR 模式；Chelsio T4/T5 网卡的 iSCSI offload 以硬件无关方式同时支持 target 与 initiator，并实现 VMware VAAI 与 Hyper-V ODX 加速（write same、extended copy、unmap 空间回收，相当于 Zvol 的 trim 支持）；Debian/kFreeBSD 状态报告称其工作过程发现了两个月前安全公告中的内核 bug；PXE 自动化安装为 GSoC 项目，bsdinstall 增加按 MAC 地址取配置的脚本化能力；另有 ARM 板卡与 ARM64 的 LLDB 调试器移植。（BSD Now EP59，[580.29-1284.73]，L2）

**史观**：

- 总纲10 动手者创造历史：Cantrill 叙述其通过删除代码完成的罕见系统改进：SmartOS 低内存时的 kmem 迁移逻辑会在持有锁的状态下“狩猎”magazine 层数以百万计的缓冲区，使系统陷入无法观测的停顿，统计工具本身亦被锁死；他判定该逻辑与低内存场景自相矛盾而整体删除，diff 全为减号、未新增一条指令，并主张内核函数名中永远不应出现 hunt 之类动词，还要为此补写注释说明为何不再如此。系统史由动手者以手术刀式的删除书写，而非仅由宏大的架构图书写。（BSD Now EP117，[1823.68-1876.66]，L1）
- 总纲21 革命与改革是历史方法论的分歧：Cantrill 断言“Linux 不是被设计的，它是演化的”，任何形似整体设计之物都会激起社区的免疫反应，而 ZFS、DTrace、容器与安全这类复杂构造无法靠演化抵达，必须有人重新思考整体并获准整合大型成果；FreeBSD 与 illumos 的价值恰在于允许这种整体性设计着陆，优秀想法还能在共享价值观的系统间交叉授粉。他将自由软件内部的路线之争表述为革命性整体设计与渐进演化两种历史方法论的分歧，并归因于 Linux 缺乏承担架构方向的责任结构、无人为设定架构方向负责。（BSD Now EP117，[4133.02-4236.92]，L1）
- 总纲15 文化即形式主义：Cantrill 力陈命名即软件的基石而非琐碎细节：名字将被未来世代用于理解、扩展既有设计并判断其做法是否恰当，命名失当如同基石被掀翻在街心，是系统沦为贫民窟、无法起造摩天楼的根源。他举 DNF 包管理器连作者本人都拒答缩写含义、systemd 与 libsystemd 以库之名封装守护进程且边界无限扩张、KVM 之名与机房键盘视频鼠标切换器相冲撞为例，指出命名混乱会迫使真正理解系统的善意聪明人自我怀疑；命名之争的僵局往往暗示存在尚未被想到的第三方案。（BSD Now EP117，[2781.72-2809.82]，L1）
- 总纲20 历史地理塑造思想土壤：日本 BSD 社区轨迹的地域性：PC-98 这一日本特有硬件生态决定了斋藤只能在 FreeBSD 与 Linux 的本地移植中择路；语言与文化边界使技术上占优的日本补丁因拒绝进入英文邮件列表的讨论形式而被系统性忽略，进而引发整个开发者群体向 NetBSD 的迁移。硬件土壤与沟通文化共同塑造了日本 BSD 版图从 FreeBSD 倾向转为 NetBSD 倾向的历史路径，而非任何技术必然性。（BSD Now EP59，[2227.32-2483.87]，L1）
- 总纲5 没有必然性，只有偶然性：Linus Torvalds 因 BitKeeper 许可问题出走，考察 Monotone 并借其理念写出被称为某种 Monotone 克隆的 Git；他弃用 Monotone 的直接原因仅是性能，而性能糟糕源于他恰好取用了带两周窗口 bug 的版本——若无此偶然，业界或许至今人人使用 Monotone。版本控制霸权的归属系于一个 bug 的时间窗。（BSDTalk EP194，[259.00-331.16]，L1）
- 总纲13 法律与道德是利益分配：当事人自陈不在乎许可证、只想把代码免费送出去，其许可选择被三股力量左右：公司律师的禁令、贡献者的 GPL 意图、大陆法系对公有领域的不承认——法律形式在此不是道德宣言，而是各方利益的分配界面。（BSDTalk EP194，[1644.90-1680.54]，L1）
