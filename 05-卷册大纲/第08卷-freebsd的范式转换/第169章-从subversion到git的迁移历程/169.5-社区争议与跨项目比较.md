# 169.5 社区争议与跨项目比较

## 168.5.1 社区内部对 Git 迁移的不同声音

**要点**：Git 迁移过程中社区内部确实存在不同声音和担忧，经邮件列表存档交叉验证主要包括：(1) **学习曲线担忧**：部分资深 committer 使用 SVN/CVS 十多年，对 Git 的索引（stage）、变基（rebase）、分离头指针（detached HEAD）等概念感到困惑，担心学习成本影响生产力；(2) **分布式复杂性担忧**：部分开发者认为分布式 VCS 的灵活性会带来混乱，偏好 SVN 集中式模型的简单性；(3) **历史转换风险担忧**：有 committer 担心 SVN→Git 历史转换会丢失信息或引入错误；(4) **平台依赖担忧**：部分开发者对 GitHub/GitLab 等商业平台的依赖表示担忧，支持完全自主托管；(5) **工具性能担忧**：ports 仓库规模巨大，部分开发者担心 Git 处理 30 万 + 提交历史的性能；这些担忧大部分通过充分的文档、培训、试点验证和工具优化得到缓解，但确实有极少数 committer 因不适应 Git 而减少了贡献或退役

**史料**：freebsd-git 和 freebsd-hackers 邮件列表讨论线程（2019-2021）；Git 工作组 FAQ（专门回应常见担忧）；BSD Now 等社区播客中的讨论 ［A］

**史观**：总纲第 23 条——社区治理：健康的开源社区应当允许不同声音的表达——担忧和反对意见不是“阻碍进步”，而是帮助发现风险、优化方案的重要反馈；Git 迁移的顺利完成在很大程度上要感谢那些提出尖锐问题的开发者

**辨析**：需区分“对迁移方案的建设性批评”和“反对迁移本身”——前者大量存在且被工作组认真吸纳，后者几乎不存在；没有 committer 公开反对“FreeBSD 应该迁移到 Git”这一大方向，争论全部集中在“如何迁移”“何时迁移”“迁移后采用什么工作流”等具体问题上

**文献**：FreeBSD Wiki. *GitTransition - FAQ* (addressing common concerns); freebsd-git mailing list discussion threads (2019-2021); BSD Now. (2020-12). *Episode 379: Git Migration Special*. ［A］

## 168.5.2 GitHub 依赖与技术自主的辩证

**要点**：Git 迁移过程中关于 GitHub 依赖的讨论反映了开源社区长期存在的一个张力：**技术自主** vs **生态便利性**；支持“以 GitHub 为主仓库”的论点：(1) GitHub 是全球最大的开源社区，能提升 FreeBSD 曝光度；(2) Pull Request 工作流对新贡献者更友好；(3) 无需自主运维基础设施，节省资源；支持“自主托管主仓库”的论点：(1) 避免平台锁定——GitHub 服务条款变更、服务中断、被收购等风险都可能影响项目；(2) 保持项目独立性——FreeBSD 不应该将核心基础设施托付给商业公司（微软于 2018 年收购 GitHub）；(3) 延续自主传统——从 CVS 到 SVN，FreeBSD 始终自主托管版本控制仓库；最终决策是务实的折中：主仓库自主托管在 git.freebsd.org，同时在 GitHub/GitLab 维护只读镜像享受生态便利

**史料**：freebsd-hackers 邮件列表 GitHub 策略讨论；FreeBSD Foundation 关于基础设施自主的声明；其他开源项目（如 GNOME、KDE）的 GitHub 使用策略作为参照 ［A］

**史观**：总纲第 22 条——开源运动：平台依赖是 2020 年代开源运动面临的核心挑战之一——大型科技公司通过代码托管平台、CI 服务、软件包仓库等基础设施 exert 对开源生态的影响力；FreeBSD 的折中策略是中小开源项目在现实约束下保持自主性的典型方案

**辨析**：“FreeBSD 不信任 GitHub/微软”是过度简化——FreeBSD 充分利用 GitHub 作为镜像平台的价值，只是不将主仓库放在那里；这是风险管理而非意识形态排斥；其他项目（如 Linux 内核也不使用 GitHub PR）也有类似考量

**文献**：FreeBSD Foundation. (2021). *Why We Host Our Own Git Repository*. freebsdfoundation.org; freebsd-hackers mailing list GitHub strategy threads (2019-2020); Raymond, E. S. (1997). *The Cathedral and the Bazaar*. O'Reilly. ［A］

## 168.5.3 与其他操作系统 VCS 迁移路径比较

**要点**：FreeBSD 的 Git 迁移放在同期操作系统 VCS 变迁的大背景下更能凸显其特点：(1) **Linux 内核**：2002-2005 使用 BitKeeper，2005 年 林纳斯·托瓦兹 亲自创建 Git 后即切换，Linux 从未使用 CVS/SVN；(2) **NetBSD**：长期使用 CVS，src 仓库 2020 年完成 Git 转换，但 pkgsrc 等仍在 CVS，2025 年 1 月 Taylor R Campbell 宣布转向 **Mercurial+Git 双轨方案**（以 Mercurial 为主仓库，Git 通过 git-cinnabar 双向同步），迁移路径曲折；(3) **OpenBSD**：Theo de Raadt（西奥·德·若特） 和核心团队坚持使用 CVS 至今（2026 年），认为 CVS 足够简单、可靠、符合 OpenBSD 开发模型，明确拒绝迁移到更复杂的 VCS；(4) **DragonFly BSD**：2004 年从 FreeBSD 分叉时即选择 Git，从未使用 SVN；(5) **illumos**：从 OpenSolaris 继承 Mercurial，2015 年迁移到 Git；FreeBSD 是主要 BSD 项目中迁移准备最充分、过程最平稳的一个

  **主要操作系统 VCS 迁移路径对比**：

  | 项目 | 早期 VCS | 当前 VCS（截至 2026.7） | 迁移路径特点 |
  |---|---|---|---|
  | Linux 内核 | BitKeeper（2002-2005） | Git | 2005 年 林纳斯·托瓦兹 创建 Git 后即切换，从未使用 CVS/SVN |
  | FreeBSD | CVS（1993-2008）→ SVN（2008-2020） | Git | 2020.12-2021.4 三阶段渐进迁移，过程最平稳 |
  | NetBSD | CVS（长期） | Mercurial+Git 双轨（2025.1 宣布） | src 仓库 2020 年转 Git，pkgsrc 仍用 CVS，2025 年转向双轨方案 |
  | OpenBSD | CVS | CVS | 坚持使用 CVS 至今，明确拒绝迁移 |
  | DragonFly BSD | Git（2004 创立即用） | Git | 从未使用 CVS/SVN |
  | illumos | Mercurial（继承自 OpenSolaris） | Git | 2015 年迁移到 Git |

**史料**：OpenBSD anoncvs 官方说明；NetBSD 2020-2025 迁移讨论邮件列表；Taylor R Campbell 2025 年 1 月 4 日 tech-repository 邮件；Linux 内核 Git 历史；illumos 2015 Git 迁移公告 ［A］

**史观**：总纲第 6 条——技术路线分化：VCS 选择没有放之四海而皆准的“正确答案”——Linux 创建 Git 是因为需要、OpenBSD 坚持 CVS 是因为够用、FreeBSD 花两年精心迁移是因为重视稳定性、NetBSD 选择 Mercurial 双轨是因为社区未达成共识，这些差异反映了各项目社区文化、规模、治理结构的根本不同

**辨析**：**关键事实修正**：原大纲/部分网络资料称“NetBSD 2015 年迁移到 Git”——经 NetBSD 官方邮件列表和 Wiki 交叉验证，这是 **错误** 的：NetBSD src 仓库 2020 年才完成 Git 转换，pkgsrc 至今（2026 年）仍使用 CVS，且 2025 年 1 月宣布转向 Mercurial+Git 双轨而非单一 Git；“NetBSD 2015 迁移”是长期流传的网络谣言

**文献**：OpenBSD Project. *Anonymous CVS*. openbsd.org/anoncvs.html; Campbell, T. R. (2025-01-04). *Core statement on version control systems*. <tech-repository@NetBSD.org> mailing list; NetBSD Wiki. *Source (multi) repository conversion*. wiki.netbsd.org; Torvalds, L. (2005). *Git initial announcement*. LKML; illumos Foundation. (2015). *illumos moves to Git*. ［A］

## 168.5.4 迁移争议史料辨析

**要点**：Git 迁移争议相关一手史料的可靠性需分级评估：(1) **最高可信度**：官方 Wiki 时间表、freebsd-git 邮件列表原始帖子、版本控制系统中的 commit 记录——这些是当时形成的一手文档，可信度最高；(2) **高可信度**：Ed Maste（埃德·马斯特）、Warner Losh（沃纳·洛什） 等核心成员的会议演讲和博客文章——作者是亲历者，但事后回忆可能存在细节偏差；(3) **中等可信度**：FreeBSD Foundation 报告、BSD Now 等社区媒体报道——信息基本准确但可能有简化；(4) **低可信度**：第三方技术博客、论坛讨论、社交媒体评论——常有事实错误，需交叉验证；常见误解汇总：(1) “NetBSD 2015 年迁移 Git”（错误，2020 年 src 转换，2025 双轨方案）；(2) “OpenBSD 不用 Git 是因为保守”（错误，OpenBSD 有明确技术理由）；(3) “FreeBSD 以 GitHub 为主仓库”（错误，主仓库在 git.freebsd.org）；(4) “CVS→SVN 是 Poul-Henning Kamp（波尔-亨宁·坎普） 推动的”（错误，是 Peter Wemm）

**史料**：各等级一手/二手史料清单；常见事实错误对照；Git 工作组事后复盘 ［A］

**史观**：总纲第 3 条——形式主义膨胀：历史书写中的事实考据是形式主义的基础工作——每一个日期、人名、事件都必须有可靠来源支撑，不能以“大概是”“众所周知”作为依据；0 信任原则要求我们对所有来源都保持审慎，包括“一手”材料

**辨析**：部分争议点可能永远没有完全清晰的答案——例如 Core Team 内部讨论的细节、某些决策的真实考量、个别 committer 退役的真实原因等；史笔至此须存疑，不可为了叙事完整性而编造或推断

**文献**：FreeBSD Project. *freebsd-git and freebsd-hackers mailing list archives*. lists.freebsd.org; Wayback Machine. *FreeBSD Wiki historical snapshots*. web.archive.org; FreeBSD Foundation. (2021). *Git Migration Retrospective*. ［A］

- Alfred Perlstein 回顾入圈路径：少年时写 MS-DOS 汇编，1998 年前后在大学接触 FreeBSD 并被邮件列表的长篇技术回答留住；Des 手把手带其完成首批内核补丁，此后约二十年持续贡献。（BSD Now EP142，[1536.00-1705.00]，L1）
- Perlstein 列举其贡献：早期 SMP 项目中的 select/poll 锁定、leaf 区域、SIGIO 与 System V 资源锁；收编 USB2 大型代码库；接受 Paul Saab 引导把 Yahoo 的 accept filters 送入树，单颗 Pentium 400 达成每秒一千五百连接，并称 kqueue 是该时代创新使项目成为可能。（BSD Now EP142，[1706.00-1986.00]，L1）
- 其职业经历构成 FreeBSD 生产力的旁证：曾在 Apple 内核团队处理 NFS 断连不挂死、在 Juniper 将修改版 FreeBSD 铺上高速线卡、任 OKCupid CTO 时全部跑 FreeBSD，后因无人掌握编译器升级而整体迁往 Linux——他认为 base 打包化本可避免该迁移。（BSD Now EP142，[1994.00-2103.00]，L1）
