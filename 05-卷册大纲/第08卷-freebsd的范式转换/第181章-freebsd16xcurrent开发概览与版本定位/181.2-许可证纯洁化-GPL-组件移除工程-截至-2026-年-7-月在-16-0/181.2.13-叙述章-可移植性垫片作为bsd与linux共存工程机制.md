# 181.2.13 叙述章——可移植性垫片作为 BSD 与 Linux 共存工程机制

GPL 移除的另一面是可移植性承诺——当 FreeBSD 从 base system 中剔除 GPL 组件时，Linux 内核同时在做相反方向的工程：把 BSD 接口保留为可移植性垫片，使 BSD 用户态工具能在 Linux 上无缝编译运行，两条工程路径在同一个历史时段内互为镜像

网络层是最典型的保留区。2017 年 5 月 Sowmini Varadhan 在 netdev 关于 struct ip 冗余的争论中直接定性："struct ip is a BSD-ism, intended to be used if you were porting some BSD app"，Linux 内核中的 struct ip 并非原生实现，而是为可移植性保留的垫片；2012 年 9 月 Eric Dumazet 在 BPF 模运算提议中反问"what about the other OS - eg all the BSDs?"，并补一句"Or is BSD so hard to update these days"，把 BPF 指令集冻结问题与 BSD 兼容性挂钩；David Laight 在同线程进一步提出"I had a vague idea that BPF was supposed to be reasonable portable"，BPF 作为 BSD 与 Linux 共享的过滤器语言被明确当作跨平台接口处理

文件系统层同样保留了 BSD 血统。David Howells 在讨论 st_gen 字段时指出该字段沿用 BSD 命名，Maciej W. Rozycki 补充"Note the Alpha port has had an st_gen member reserved in its struct stat for many years now"，并称该字段"as it is called that way on BSD"——BSD 的 stat 结构体成员名被 Linux 内核保留多年，构成 stat(2) 系统调用跨平台接口的一部分，属于接口契约式的历史继承而非代码抄录

FUSE UAPI 整数类型改造把 BSD 用户态工具作为可移植性验证的正式目标。Carlos Llamas 2022 年 3 月为 __u32 类型提出 BSD 兼容垫片，援引 DRM 先例 commit 1a95916f5465，称"the best way to accommodate this while still conforming with the __u32 types"；Arnd Bergmann 与 Bernd Schubert 2026 年 1 月进一步主张"not defining __linux__ makes it use the stdint types after all"，所以"I would expect the patch to not have changed anything for BSD"——BSD 用户态工具成为 Linux FUSE 接口设计的显式兼容目标

驱动层的双向移植同样构成工程证据。Joe Perches 在 ath10k 争论中指出"porting easier between bsd and linux"，把 mbuf 与 skb 数据访问器的差异作为跨系统移植成本的量化指标；Dave Chinner 关于 hfsplus 维护困境讨论中援引"We used to have one that was ported from the open source Darwin code drops"，把 hfsplus 工具链追溯至 Darwin/BSD 血统；John W. Linville 在 wireless-next 拉取请求中声明"addition of the ar5523 driver, ported from an original FreeBSD driver"；Fred L Templin 的 IPv6 RFC4214 补丁说明"entail a port of the FreeBSD rtsold daemon"

反向的移植提案则体现两个方向的对偶。Eric Dumazet 在 Johannes Lundberg 提议为 epoll 增加 EPOLLEMPTY 时反驳"similar functionality was previously added to FreeBSD as the kqueue event EVFILT_EMPTY"，转而提出"Our timestamping infrastructure should be ported to FreeBSD instead"；Luis Rodriguez 在 alx 讨论中直言"BSD folks can simply use the external unified tree now to port the driver to BSD"，但承认受"license divergence"限制——BSD 派生代码在 Linux 内核中的流动并非无成本

AF_PACKET 的可移植性争论则展示了这一承诺的边界。Tom Herbert 直接反驳担忧："it already has Linux specific stuff for checksum offload. The portability to BSD for AF_PACKET is a non-issue"——当 Linux 侧新增特性已经 Linux-specific 时，BSD 可移植性被显式判定为非阻碍，portability shim 只在接口已冻结的场景下才有约束力

从工程机制看，FreeBSD 的 GPL 移除与 Linux 内核的 BSD 接口保留构成同一历史过程的两面：前者以深原则回避传染性 GPL 为工程目标，后者以 portability shim 为工程手段；portability shim 把 BSD 接口从源代码血缘提升为接口契约，使 BSD 与 GNU 的技术合作得以绕过法律层面的传染性争议

**辨析**：考据留痕——【与既有小节的差异】本节刻意回避 181.2.11 的时间轴框架与 166.2.12 的镜像叙事框架，改以可移植性垫片这一工程机制为组织原则，把 12 条 claim 聚类为网络、文件、UAPI、驱动、反向移植、边界六域，以便观察 BSD 与 Linux 的共存机制如何在许可证纯化工程的另一侧同步演化；【存疑判定】(1) portability shim 是本文作者对 struct ip 与 st_gen 与 FUSE UAPI 三类证据的机制性归纳，非当事人自述，本节采信 Varadhan 的 BSD-ism intended to be used if you were porting some BSD app 作为最接近当事人表述的引用；(2) Eric Dumazet 的 timestamping 反向移植提案出自具体补丁讨论，本节仅采信为过程性证据而非制度化趋势；(3) Tom Herbert 关于 AF_PACKET 的 BSD 可移植性非阻碍判定是 2010 年前后的当事人观点，2026 年 AF_PACKET 接口现状须以 kernel.org 最新文档复核；(4) 本节所述 portability shim 与 GPL 传染性争议的关系为工程机制层面的合理归纳，GPL 与 BSD 在法律层面的兼容性仍须以 FSF 官方许可证评论页面为准 ［A］
