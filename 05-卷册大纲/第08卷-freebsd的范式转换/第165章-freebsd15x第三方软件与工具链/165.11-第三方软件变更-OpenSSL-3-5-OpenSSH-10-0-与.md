# 165.11 第三方软件变更——OpenSSL 3.5、OpenSSH 10.0 与 Clang 工具链

## 165.11.1 OpenSSL 3.5 与 OpenSSH 10.0 引入

**要点**：FreeBSD 15.0-RELEASE（2025 年 12 月 2 日）搭载 OpenSSL 3.5.4 和 OpenSSH 10.0p2，两项均为该版本引入的重大加密组件升级。OpenSSL 3.5 系列在 3.0 基础上引入更多后量子加密（PQC）算法支持、改进的 Provider 架构、FIPS 140-3 模块更新，是 OpenSSL 3.x 系列中功能最完整的版本。OpenSSH 10.0 是 OpenSSH 项目的里程碑版本，默认启用混合后量子密钥交换算法——OpenSSH 上游默认为 <sntrup761x25519-sha512@openssh.com>（自 OpenSSH 9.0 起即为默认），FreeBSD 15.0 的配置将默认算法设为 `mlkem768x25519-sha256`（基于 NIST FIPS 203 标准化的 ML-KEM 后量子密钥封装机制，与 FreeBSD 14.4 配置一致），这是 OpenSSH 对后量子密码学标准化的积极响应。15.0 继续搭载 Clang 20/LLVM 20 作为系统编译器。

  **FreeBSD 15.0 加密组件版本**：

  | 组件 | 15.0 搭载版本 | 关键特性 |
  |---|---|---|
  | OpenSSL | 3.5.4 | PQC 算法支持、Provider 架构改进、FIPS 140-3 模块更新 |
  | OpenSSH | 10.0p2 | 默认混合后量子密钥交换（FreeBSD 配置 `mlkem768x25519-sha256`） |
  | Clang/LLVM | 20 | 系统编译器，支持 C23、C++23 |

  > OpenSSH 上游默认为 `sntrup761x25519-sha512@openssh.com`，FreeBSD 配置默认为 `mlkem768x25519-sha256`（基于 NIST FIPS 203 标准化的 ML-KEM）。

**史观**：软件工程：OpenSSH 10.0 默认启用后量子密钥交换是 FreeBSD 对后量子密码学威胁的主动响应——尽管量子计算机尚未达到破解现有公钥密码的规模，但 “先存储、后解密”（Store Now, Decrypt Later）的威胁模型要求尽早部署后量子算法，FreeBSD 15.0 的 OpenSSH 默认配置是这一安全策略的体现

**辨析**：OpenSSH 10.0 的混合后量子密钥交换是 “混合” 方案——同时使用经典算法（x25519）与后量子算法（sntrup761 或 mlkem768），确保即使后量子算法被破解，经典算法仍提供安全保证；须区分 OpenSSH 上游默认（<sntrup761x25519-sha512@openssh.com>）与 FreeBSD 配置默认（mlkem768x25519-sha256）——FreeBSD 选择 mlkem768 是因为 NIST 已于 2024.8.13 将 ML-KEM 标准化为 FIPS 203，而 sntrup761 尚未被 NIST 标准化；OpenSSH 10.0 的版本号从 9.x 跳跃至 10.x 是因为 OpenSSH 项目在 10.0 中引入了多项重大变更（包括后量子密钥交换默认启用、DSA 签名算法废弃、scp 默认使用 SFTP 协议等），而非版本号策略变更

## 165.11.2 Clang/LLVM 工具链持续升级

**要点**：FreeBSD 15.0-RELEASE 搭载 Clang 20/LLVM 20 作为系统编译器，15.1 搭载 Clang 21/LLVM 21。自 10.0（2014）Clang 成为默认编译器以来，FreeBSD 已连续 11 年使用 LLVM 工具链，Clang 版本从 3.3（10.0）升级至 20（15.0），跨越 17 个主版本。15.x 时期 Clang 已完全成熟——支持 C23、C++23 标准，LLVM 20 的编译器优化质量与 GCC 最新版本持平，LTO/PGO（Profile-Guided Optimization）支持完善。LLD 作为全架构默认链接器、LLDB 作为唯一调试器、libc++/libc++abi 作为 C++ 标准库，LLVM 工具链在 15.x 中已全面接管 FreeBSD base 的构建、调试、链接、C++ 运行时。

  **FreeBSD 15.x Clang/LLVM 工具链版本**：

  | 版本 | Clang/LLVM | 说明 |
  |---|---|---|
  | 15.0 | Clang 20/LLVM 20 | 支持 C23、C++23，LTO/PGO 完善 |
  | 15.1 | Clang 21/LLVM 21 | 持续升级 |

  **LLVM 工具链在 FreeBSD base 中的角色**：

  | 组件 | 角色 |
  |---|---|
  | Clang | 系统编译器 |
  | LLD | 全架构默认链接器 |
  | LLDB | 唯一调试器 |
  | libc++/libc++abi | C++ 标准库 |

**史料**：FreeBSD 15.0-15.1 Release Notes（Clang/LLVM 版本号）、LLVM Project Release Notes［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］〔L3 官方文档与公告〕

**史观**：总纲第 25 条——终结与延续：Clang 20 的部署是 LLVM 工具链在 FreeBSD 中 “延续” 的第 11 年——从 10.0 的 “GCC 替代品” 到 15.0 的 “唯一编译器”，Clang 已从 “迁移工具” 成为 “正统工具”，新一代 FreeBSD 开发者可能从未在 base 中使用过 GCC

**辨析**：FreeBSD 15.x 的 Clang 版本号跳跃（20→21）是 LLVM 项目每半年递增主版本号的结果，不反映重大功能变更；ports 中的 GCC 仍持续提供（lang/gcc14-gcc15 等），用户可自由选择编译工具链

## 165.11.3 第三方软件变更的史料辨析

**要点**：15.0 的第三方软件变更以 “加密组件现代化” 与 “工具链持续升级” 为主题——OpenSSL 3.5/OpenSSH 10.0 的后量子加密支持是安全层面的前瞻性升级，Clang 20 是工具链层面的持续改进。15.0 的变更与 10.0/14.0 的模式不同——10.0 是 “集中引入新组件”，14.0 是 “集中退役旧组件”，15.0 是 “持续升级 + 架构收缩”——新组件升级（OpenSSL 3.5、OpenSSH 10.0、Clang 20）是持续改进，无类似 10.0 的 “集中换代” 事件；架构收缩（i386 降级、32 位架构退役）是资源聚焦而非技术创新。

  **FreeBSD 10.0/14.0/15.0 第三方软件变更模式对照**：

  | 版本 | 变更模式 | 主要变更 |
  |---|---|---|
  | 10.0（2014） | 集中引入新组件 | compiler/debugger/DNS/installer/MTA 等多项替换 |
  | 14.0（2023） | 集中退役旧组件 | sendmail→DMA、telnetd 移除、root shell 切换等 |
  | 15.0（2025） | 持续升级 + 架构收缩 | OpenSSL 3.5/OpenSSH 10.0/Clang 20 升级、i386 降级、32 位架构退役 |

**史料**：FreeBSD 10.0/14.0/15.0 Release Notes 对比［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］〔L3 官方文档与公告〕

**史观**：总纲第 25 条——终结与延续：15.0 的 i386 降级是 “终结”，OpenSSL 3.5/OpenSSH 10.0 的后量子加密支持是 “延续”——FreeBSD 在收缩硬件支持范围的同时，在加密安全领域持续前瞻性投入，这是资源有限的开源项目必须做出的权衡

**辨析**：15.0 的第三方软件变更 “规模” 小于 10.0 和 14.0——10.0 有 compiler/debugger/DNS/installer/MTA 等多项替换，14.0 有 sendmail→DMA/telnetd 移除/root shell 切换等多项变更，15.0 的变更集中在加密组件升级和架构降级，这反映了 FreeBSD 在 30 周年后 “稳定优于变革” 的工程哲学——大规模组件替换已完成，后续版本集中于持续改进和架构优化
