# 161.2 SMPng 的开发困境——大内核锁的移除挑战

**要点**：SMPng（SMP next generation）项目于 2000 年前后启动，目标是将 FreeBSD 从“Giant Lock 大内核锁”模式改造为细粒度多处理器支持——Giant 锁作为过渡方案长期覆盖 VFS 与网络栈大部，逐子系统移除是贯穿 5.x 至 7.x 的长程工程；基础设施层由 John Baldwin 等人建成（mutex/sx/turnstile/优先级传播与 witness 锁序监控），Greg Lehey 任 SMPng 项目负责人并执笔设计文档（ref 501/1168），Scott Perlstein 等当事人完成 select/poll、SIGIO、System V 资源锁等叶区锁定（BSD Now EP142 口述）；大内核锁的移除暴露了锁序反转（LOR）治理、优先级传播与锁粒度设计等系统性难题（参见下文 PODCAST_REVIEW 块 McKusick 锁体系分层演讲）

**史料**：[DB:code_repos:freebsd.duckdb] freebsd 仓库 SMPng 时期 commit 记录（2000-2007 时段切片）；ref 501 Lehey G（grog）等 SMPng 论文（2001）；ref 1168 SMPng 设计文档（2002）；ref 562 Baldwin J. SMPng 演讲幻灯片（NYCBUG，2013）；BSD Now EP142（2016-05-18）Perlstein SMP 叶区锁定当事人口述；McKusick《An Overview of Locking in the FreeBSD Kernel》（EuroBSDcon 2012）演讲及转写

**史观**：总纲第 5 条——没有必然性，只有偶然性：SMPng 的推进节奏取决于 Giant 锁过渡策略的取舍、各子系统改造人手的分布与 LOR 案例的偶然暴露，不存在“细粒度化的必然时刻”；总纲第 10 条——动手者创造历史：大内核锁的移除不是设计图的自上而下落地，而是 Baldwin、Lehey、Perlstein 等动手者在逐叶区锁定、锁序会诊与 LOR 邮件列表辩论中的实践产物

**辨析**：SMPng“完成”无单一时间节点——Giant 锁移除是逐子系统渐进过程，“5.x 完成 SMPng”的常见叙事须以具体子系统的锁化 commit 与 release notes 逐项核验；数据库统计受 CVS-to-Git 迁移、镜像滞后等因素影响存在系统性偏差，须结合一手史料交叉验证；IBM 读多写少锁专利的专利号与规避算法细节缺证（仅当事人单源陈述，见 PODCAST_REVIEW 块辨析），引用须另行交叉验证

**要点**：

- 主持人细读 NSA 面向通用操作系统的 W^X（write XOR execute）安全功能要求：内存页要么可执行、要么可写、决不可兼得，以防攻击者把写入的数据当作程序执行（288.04-330.38）；并对照 Intel 的 NX 位与 DEP 机制、即时编译等例外情形（344.10-362.82），以及 SPARC 与 ARM 处理器在这类 RISC 平台上的原生支持差异（362.82-369.38），与本期标题的 RISC 主题相呼应。（BSD Now EP142，[288.04-369.38]，L2）
- Perlstein 回顾入坑史：少年时代在 MS-DOS 上写汇编自学编程，进大学被计算机系同学讥笑“MS-Dog”，恰逢学校以 FreeBSD 为教学平台，其多任务与内存管理令他感到这是一个真正完整的操作环境；1998 至 1999 年间他在邮件列表提问文件系统问题，收到详尽而易懂的长篇技术答复，自此被社区吸引而留下。（BSD Now EP142，[1536.28-1617.20]，L1）
- Perlstein 自述其 FreeBSD 内核工程履历：2000 年前后参与 SMP 项目，完成 select 与 poll 的初始 SMP 锁定、SIGIO 锁定与 System V 资源锁等叶区锁；USB2 大型代码库合入时充当“牧羊人”，协调在真空中工作的外部开发者与社区的磨合；又改造大于 3GB 内存机器的默认参数，使 4GB 以上内存机器插电即得足够 mbuf 支撑万兆网卡，承认短期引入破坏但认为长期值得。（BSD Now EP142，[1706.00-1839.22]，L1）[订正：原 大于 4GB 内存机器的默认参数，2026-09-30 SenseAudio 重转核对]
- FreeBSD 成为 Perlstein 的立身之本：1999 年经 Paul Saab 引导将 Yahoo 的 accept filters 推入系统，配合当时新出现的 kqueue，在单颗 Pentium 400 上实现每秒 1500 连接的 web 追踪服务；受雇 Apple 内核团队解决 NFS 断连导致系统挂起的问题；在 Juniper 把 Junos（FreeBSD 改版）部署到高速线卡并做粗粒度线程化；任 OkCupid CTO 期间全栈运行 FreeBSD；后来还赞助 libuinet 用户态网络栈用于安全设备并期望其合回主线。（BSD Now EP142，[1923.76-2127.04]，L1）
- McKusick 将 2012 年时点的 FreeBSD 内核锁体系描述为自底向上的完整分层：最底层依赖硬件提供的原子读改写指令（传统教科书式 test-and-set，实际使用 compare-and-swap 配合 mutex unowned 哨兵值判定锁归属），其上依次构建临界区、自旋互斥、自适应阻塞互斥、池化互斥、读写锁与读多写少锁，再经睡眠队列接口向上提供共享独占锁、条件变量与功能最全的锁管理器，顶端由 witness 代码监控整个锁序不被违反。（YouTube EPUfiTV9QWhM4，[354.16-911.44]，L1）
- turnstile 被称为整套锁机制得以运转的枢纽数据结构：由于一个线程同一时刻只能阻塞在一处，系统按线程而非按锁分配 turnstile（锁数量远多于线程数，每个进程表项自带数把互斥），阻塞线程把自身 turnstile 交给内核挂入等待链，锁释放时以回收的 turnstile 转交新持有者，从而以最小内存代价支撑优先级传播。（YouTube EPUfiTV9QWhM4，[1318.03-1456.32]，L1）
- 优先级反转的解法是递归优先级传播：高优先级线程发现持锁者未在运行时让出处理器并把自身优先级授予对方，直至其释放锁后优先级“逐层冒泡”归还；演讲以柏林开往华沙的特快列车令沿线十四列普通客车停驶待行为喻。与之相对，睡眠队列类锁不做优先级传播，因为唤醒等待磁盘 IO 的进程并不能让 IO 更快完成。（YouTube EPUfiTV9QWhM4，[1042.559-1148.08]，L1）
- 自适应阻塞互斥在释放时唤醒全部等待者而非逐个传递锁，理由是无竞争锁的释放只需一次赋值而遍历 turnstile 链代价更高；由于自适应自旋的存在，被唤醒者中只有持锁者真正在跑时才会竞争，故惊群代价可控。McKusick 同时警告该策略隐含互斥粒度足够细的前提——数百线程排队于一把互斥说明数据结构设计本身需要反思。（YouTube EPUfiTV9QWhM4，[2140.52-2233.32]，L1）
- 死锁避免采用锁类偏序：全部锁划入有序类别，线程在每类至多持有一把、只能向更高编号类申请；旧时代该规则仅靠源码注释人工维护，多线程化后锁数量爆炸，遂引入 witness 代码在启动阶段观察锁的实际获取顺序自动推断类别，程序员仅在推断错误时以少量显式定义纠正；残余的锁序反转（LOR）则提交专门的邮件列表集体会诊，网络栈因上下行双向数据流成为最难处理的领域。（YouTube EPUfiTV9QWhM4，[2958.4-3416.52]，L1）
