# 163.7 后量子密码学时代——OpenSSH 10 默认 PQC、OpenSSL 3.5 PQC 与 Y2Q 准备

## 163.7.1 NIST 后量子密码标准与 OpenSSL 3.5 集成

**要点**：2024 年 8 月 13 日，NIST 正式发布三项后量子密码学（Post-Quantum Cryptography, PQC）标准：FIPS 203（ML-KEM，基于 CRYSTALS-Kyber 格密码密钥封装）、FIPS 204（ML-DSA，基于 CRYSTALS-Dilithium 格密码数字签名）、FIPS 205（SLH-DSA，基于 SPHINCS+ 哈希签名）；这是密码学历史上的里程碑事件——这些算法设计用于抵抗量子计算机的 Shor 算法攻击（Shor 算法可在多项式时间内破解 RSA、ECC 等基于整数分解/离散对数的经典公钥密码）；FreeBSD 15.0 搭载的 **OpenSSL 3.5.4 LTS** 已包含对 ML-KEM、ML-DSA、SLH-DSA 的支持，并支持 QUIC 协议；OpenSSL 3.5 于 2025 年 4 月 8 日正式发布，是首个完整支持 NIST PQC 标准的 LTS 版本

  **NIST 三项后量子密码学标准**：

  | 标准编号 | 算法名称 | 基于 | 用途 |
  |---|---|---|---|
  | FIPS 203 | ML-KEM | CRYSTALS-Kyber 格密码 | 密钥封装 |
  | FIPS 204 | ML-DSA | CRYSTALS-Dilithium 格密码 | 数字签名 |
  | FIPS 205 | SLH-DSA | SPHINCS+ 哈希签名 | 数字签名 |

  > 这些算法设计用于抵抗量子计算机的 Shor 算法攻击（Shor 算法可在多项式时间内破解 RSA、ECC 等基于整数分解/离散对数的经典公钥密码）。

**史料**：NIST FIPS 203/204/205 标准文本（2024.8.13，Federal Register 2024.8.14）；OpenSSL 3.5 Release Notes（2025.4.8）；FreeBSD 15.0 Release Notes OpenSSL 部分［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］〔L3 官方文档与公告〕

**史观**：总纲第 19 条——信息技术：Y2Q（Year to Quantum，量子计算机破解现有密码的 “那一天”）问题与 Y2K（千年虫）问题有相似之处——都是需要提前多年准备的技术迁移问题，但 Y2Q 的时间线更不确定（量子计算何时能破解 RSA-2048 专家估计从 10 年到 30 年不等），且迁移成本更高（需要更换所有公钥证书、密钥交换协议、签名算法）；FreeBSD 15.0 在 OpenSSL/OpenSSH 中默认支持 PQC，是主流 OS 中较早为 Y2Q 做准备的系统之一

**辨析**：“支持 PQC” 不等于 “默认使用 PQC 替换所有经典密码”——15.0 中 ML-KEM/ML-DSA/SLH-DSA 可通过 API 调用，但 TLS 1.3 与 SSH 默认是否使用混合密钥交换需区分：OpenSSH 10.0p2（15.0 搭载）**默认启用混合后量子密钥交换**（<sntrup761x25519-sha512@openssh.com>，结合 X25519 ECDH 与 ML-KEM 近似版本 NTRU-HRSS/sntrup761）；OpenSSL 3.5 中 PQC 算法可用但 TLS 中是否默认启用取决于应用配置；当前 PQC 采用 “混合模式”（经典算法+PQC 算法同时使用）以确保即使 PQC 算法被发现缺陷也不会降低安全性

## 163.7.2 OpenSSH 10.0 默认后量子密钥交换

**要点**：FreeBSD 15.0 搭载的 **OpenSSH 10.0p2** 标志着后量子密码学在 SSH 中的实际部署里程碑——自 2022 年 OpenSSH 9.0 引入 <sntrup761x25519-sha512@openssh.com> 混合密钥交换以来，经过约两年测试，OpenSSH 10.0 将其设为 **默认密钥交换算法**；这意味着默认配置下，FreeBSD 15.0 的 SSH 连接已可抵抗量子计算机对密钥交换的窃听攻击（“harvest now, decrypt later” 攻击——攻击者现在记录加密流量，待量子计算机可用后解密历史流量）；OpenSSH 10.0 还包含多项其他安全改进

**史料**：OpenSSH 10.0 Release Notes（2025）；Damien Miller（达米安·米勒）（djm@OpenBSD）sntrup761x25519 设计文档与邮件列表说明；FreeBSD 15.0 Release Notes OpenSSH 部分 ［A］

**史观**：总纲第 22 条——开源运动：OpenSSH 默认启用 PQC 是密码学迁移的 “低垂果实”——SSH 是交互式远程管理协议，密钥交换在连接建立时进行，对延迟不敏感，混合密钥交换的性能开销可接受；TLS（HTTPS）的 PQC 迁移更复杂（需要 CA 证书、浏览器、服务器全部支持），但 SSH 作为系统管理员最常用的工具率先完成默认 PQC 化具有重要示范意义

**辨析**：sntrup761x25519 与 NIST ML-KEM 的关系需澄清——sntrup761（NTRU-HRSS 的变体）不是 NIST 标准化的 ML-KEM，而是 Streamlined NTRU Prime（Daniel J. Bernstein 等设计），它在 NIST PQC 进程中进入第四轮备选但未被选为首选标准；OpenSSH 选择 sntrup761 而非 Kyber/ML-KEM 的原因包括：sntrup761 代码更简洁、专利风险更低（NTRU 相关专利有更复杂的历史）、更早可用；ML-KEM-512（原名 Kyber-512）集成预计在 OpenSSH 未来版本跟进

**文献**：OpenSSH Project. OpenSSH 10.0 Release Notes [EB/OL]. (2025)[2026-07-19]. <https://www.openssh.com/releasenotes.html>; Bernstein D J, et al. Streamlined NTRU Prime [EB/OL]. [2026-07-19]. <https://ntruprime.cr.yp.to/>.［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］

## 163.7.3 KTLS 与内核 TLS 演进

**要点**：15.0 中 KTLS（Kernel TLS）持续完善，包括 TLS 1.3 发送/接收双向卸载支持的成熟化；KTLS 允许 TLS 记录层对称加密在内核中完成（通过直接在 socket 层处理），避免用户态-内核态数据拷贝，显著提升高带宽 TLS 连接吞吐量——Netflix 是 KTLS 的主要赞助者与使用者，其 CDN 服务器利用 KTLS 支撑每秒数 TB 级别的视频流量加密；15.0 中 KTLS 与 OpenSSL 3.5 PQC 算法的协作、与 **sendfile(2)** 零拷贝的集成持续优化

**史料**：Netflix KTLS 技术博客；FreeBSD 15.0 Release Notes Kernel Networking 部分；ktls(4) 手册页；John Baldwin（约翰·鲍德温） KTLS 演讲（BSDCan 2023-2025） ［A］

**史观**：总纲第 10 条——边缘者贡献：KTLS 的故事再次证明企业大规模用户反哺开源的模式——Netflix 没有为自己的 CDN 维护一个 FreeBSD 私有分支，而是持续将所有 KTLS 改进贡献回主线；这种 “自用即贡献” 模式使 FreeBSD 在高带宽 TLS 性能上保持领先地位

**辨析**：KTLS 不加密所有连接——应用程序需要显式通过 setsockopt 启用 KTLS（TLS_TX/TLS_RX 选项），OpenSSH、curl、nginx 等用户态程序默认使用用户态 TLS 栈（OpenSSL），除非专门配置使用 KTLS；Netflix 的 CDN 使用自定义 TLS 栈与 KTLS 深度集成

**文献**：FreeBSD Project. ktls(4) Manual Page [EB/OL]. [2026-07-19]. <https://man.freebsd.org/ktls/4>; Baldwin J. Kernel TLS Improvements [C]. BSDCan 2025.

## 163.7.4 后量子迁移的长期性与 FreeBSD 定位

**要点**：后量子密码学迁移是一个长达 10-20 年的过程，涉及互联网几乎所有加密协议（TLS、SSH、IPsec、DNSSEC、PGP、信号协议等）；FreeBSD 作为服务器与网络设备 OS，在 PQC 迁移中扮演基础设施角色——需要为上层应用（Web 服务器、VPN、SSH、证书管理）提供稳定的 PQC 算法实现；15.0/15.1 在 OpenSSL 3.5 与 OpenSSH 10.0 中集成 PQC 是这一长期迁移的第一步；16.0 及以后版本预计将持续跟进 PQC 标准化进展与性能优化

  **Y2Q 与 Y2K 迁移对照**：

  | 维度 | Y2K（千年虫） | Y2Q（量子破解） |
  |---|---|---|
  | 截止日期 | 固定（2000.1.1） | 不确定（10-30 年或更久） |
  | 威胁性质 | 日期处理错误 | 加密流量被解密 |
  | 迁移成本 | 修改日期字段 | 更换所有公钥证书、密钥交换协议、签名算法 |
  | 攻击模式 | 即时故障 | “harvest now, decrypt later”（先记录后解密） |
  | FreeBSD 准备 | 历史上已解决 | 15.0 在 OpenSSL/OpenSSH 中默认支持 PQC |

**史料**：NIST PQC 标准化时间表；IETF PQC 协议集成草案；FreeBSD Security Team 密码学相关 SA/EN［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］〔L3 官方文档与公告〕

**史观**：总纲第 19 条——信息技术：Y2Q 迁移与 Y2K 迁移的历史对比——Y2K 问题因修复日期固定（2000.1.1）而有明确截止日期，Y2Q 时间线不确定但威胁更根本（一旦实用量子计算机出现，所有历史加密流量都可能被解密）；“harvest now, decrypt later” 攻击模式意味着即使量子计算机 20 年后才出现，今天记录的敏感流量也可能在未来被解密——这使 PQC 迁移具有紧迫性

**辨析**：不应夸大量子计算对密码学的威胁——实用密码学相关量子计算机的时间表高度不确定（乐观估计 10-15 年，悲观估计 30+ 年，部分专家认为永远不会实现）；当前 PQC 算法仍处于早期阶段，未来可能发现数学弱点，因此 “混合模式”（经典+PQC）是当前最安全的选择；FreeBSD 跟进 PQC 是前瞻性准备而非紧急需求
