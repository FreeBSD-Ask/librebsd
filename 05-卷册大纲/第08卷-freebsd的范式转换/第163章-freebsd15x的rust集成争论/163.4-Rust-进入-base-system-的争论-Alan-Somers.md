# 163.4 Rust 进入 base system 的争论——Alan Somers 提案与社区共识僵局（2024-2026）

## 163.4.1 Alan Somers 的 Rust 集成方案（2024.1.20）

**要点**：2024 年 1 月 20 日，开发者 Alan Somers（asomers@，Google 工程师、FreeBSD 文件系统与存储子系统长期贡献者）在 freebsd-hackers@ 邮件列表发布 “The Case for Rust (in the base system)” 一文，正式提出将 Rust 编程语言引入 FreeBSD 基础系统的方案；Somers 指出：Rust 的内存安全特性可以消除 C/C++ 代码中大量的内存安全漏洞（据 Google/MSRC 统计约 70% 的安全漏洞源于内存安全问题）；FreeBSD 已在 Ports 中支持 Rust，但 base system 中引入 Rust 工具链允许用 Rust 重写/新写安全关键组件（如用户态工具、新驱动、文件系统工具等）；Somers 承认主要缺点是构建时间将加倍（Rust 编译器编译较慢），但认为安全收益超过成本

  **Somers Rust 集成方案优缺点对照**：

  | 维度 | 优势 | 劣势 |
  |---|---|---|
  | 内存安全 | 消除 C/C++ 约 70% 安全漏洞（Google/MSRC 统计） | - |
  | 构建时间 | - | Rust 编译器编译较慢，构建时间将加倍 |
  | 工具链 | - | Rust 工具链体积庞大（数百 MB） |
  | 渐进范围 | 先引入工具链，再允许 Rust 编写新用户态工具 | 内核 Rust 支持是远期可能性 |

**史料**：Alan Somers 2024.1.20 邮件原文 “The Case for Rust (in the base system)”（<https://lists.freebsd.org/archives/freebsd-hackers/2024-January/002823.html>）；LWN 2024.8.19 报道 “FreeBSD considers Rust in the base system”（<https://lwn.net/Articles/985210/>）；Rust 编程语言官方文档；Google/MSRC 内存安全漏洞统计报告 ［A］

**史观**：专题语（不设条号）——软件工程：Rust 进入 base 的争论本质上是 “工程安全性” 与 “工程简洁性” 的权衡——C 语言是 FreeBSD 30 多年来的基石，C 编译器与工具链相对简单、构建快速、跨平台支持好；Rust 带来内存安全但增加工具链复杂度与构建时间；Linux 内核自 6.1（2022.12）开始接受 Rust 代码但标记为实验性，为 BSD 社区提供了参考案例（原“总纲第 17 条”标号与基线第 17 条“证明世界先于解释和改造世界”不符，按 R2140 先例改不设条号专题语——批次 C275 问题 1）

**辨析**：Somers 提案并非要求 “用 Rust 重写整个 FreeBSD” 或 “内核立即接受 Rust 代码”——提案范围非常渐进：首先引入 Rust 工具链到 base（作为 ports 之外的基础系统组件），然后允许用 Rust 编写新的用户态工具（如 nfsd、bhyve userspace 组件等），内核 Rust 支持是更遥远的可能性；截至 2026.7，**Rust 尚未进入 FreeBSD base system**——提案仍处于讨论阶段，未形成 Core Team 决议。经邮件列表库验证通过（来源：freebsd-hackers 列表，Message-ID <CAOtMX2hAUiWdGPtpaCJLPZB+j2yzNw5DSjUmkwTi++myemehCA@mail.gmail.com>，2024-01-20，发件人 Alan Somers <asomers@freebsd.org>，主题“The Case for Rust (in the base system)”，同线程含 Gleb Popov、Dimitry Andric、Antranig Vartanian、George Mitchell 等多方回复）

**文献**：Somers A. The Case for Rust (in the base system)[EB/OL]. (2024-01-20)[2026-07-19]. <https://lists.freebsd.org/archives/freebsd-hackers/2024-January/002823.html>; LWN.net. FreeBSD considers Rust in the base system [EB/OL]. (2024-08-19)[2026-07-19]. <https://lwn.net/Articles/985210/>. ［A］

## 163.4.2 社区争论焦点与共识僵局

**要点**：Somers 提案引发的社区争论持续超过两年（2024.1-2026.7），核心争议点包括：① 构建时间与资源——反对者（如 Warner Losh（沃纳·洛什） imp@、Baptiste Daroussin（巴蒂斯特·达鲁桑） bapt@ 等）指出 Rust 工具链本身体积庞大（数百 MB）、编译速度慢，将显著增加 base 系统构建时间与 CI 资源消耗，对资源有限的 Tier 2 平台（如 riscv64、armv7）尤其不利；② 编译器复杂性——Rust 编译器（rustc）使用 LLVM 后端（与 FreeBSD 默认 Clang 一致）但本身是用 Rust 编写的，这意味着构建 Rust 工具链需要先有一个可用的 Rust 二进制（“自举问题”），这与 C 编译器可通过系统 C 编译器从源码构建的传统不同；③ 许可证——Rust 本身采用 MIT/Apache 2.0 双许可，与 FreeBSD 许可证兼容，这一点争议不大；④ 维护负担——引入新语言意味着需要一批懂 Rust 的开发者维护相关代码，而 FreeBSD 核心开发者群体中 Rust 专业知识分布不均；⑤ 安全收益是否值得——支持者（如 Colin Percival cperciva@ 等）认为内存安全漏洞占比数据（70%）说明问题严重，Rust 是可行解决方案；反对者认为改进 C 代码（静态分析、形式化验证、Capsicum 沙箱）也能提高安全性

  **Rust 入 base 五大争议焦点**：

  | 序号 | 争议点 | 反对者立场 | 支持者立场 |
  |---|---|---|---|
  | ① | 构建时间与资源 | Rust 工具链体积大、编译慢，对 Tier 2 平台不利 | 安全收益值得构建成本 |
  | ② | 编译器复杂性 | rustc 自举问题（需先有 Rust 二进制才能构建） | 与 LLVM 后端一致，可逐步解决 |
  | ③ | 许可证 | - | MIT/Apache 2.0 双许可，与 FreeBSD 兼容 |
  | ④ | 维护负担 | 需懂 Rust 的开发者，专业知识分布不均 | 可逐步培养 Rust 人才 |
  | ⑤ | 安全收益是否值得 | 改进 C 代码（静态分析、形式化验证、Capsicum）也可 | 70% 内存安全漏洞数据说明问题严重 |

**史料**：freebsd-hackers@ 邮件列表 Rust 讨论多轮线程（2024-2026）；BSDCan 2024/2025 相关 BOF 讨论记录；Poul-Henning Kamp（波尔-亨宁·坎普） phk@、Warner Losh imp@ 等资深开发者的公开立场 ［A］

**史观**：专题语（不设条号）——哲学思潮：Rust 争论反映了 BSD 社区中 “保守演进” 与 “革新进步” 两种哲学的张力——FreeBSD 历史上对新技术的引入一贯持审慎态度（如 ZFS 移植经历多年实验才正式进入 base、WireGuard 经重写后随 13.0（2021-04）进入 base）；Rust 作为可能改变 base 系统语言构成的重大变更，自然需要更长时间的讨论与验证（原“总纲第 14 条”标号与基线第 14 条“苦难不值得被提倡”不符，按 R2140 先例改不设条号专题语——批次 C275 问题 1）

**辨析**：“Rust 进入 FreeBSD base” 与 “Linux 内核 Rust for Linux” 需区别看待——Linux Rust 支持主要限于内核驱动（特别是新驱动可选使用 Rust），FreeBSD 提案起步是用户态工具而非内核；截至 2026.7，OpenBSD 明确拒绝 Rust（Ted Unangst 等公开反对），NetBSD 未正式讨论 Rust 入 base，DragonFly BSD 亦无 Rust 入 base 计划——FreeBSD 是三大 BSD 中唯一认真讨论 Rust 入 base 可能性的项目，但距离实际引入仍有相当距离

## 163.4.3 Rust 与 C/C++ 在 FreeBSD 生态中的共存展望

**要点**：截至 2026.7，Rust 在 FreeBSD 生态中的实际状态是：Ports 中已有成熟的 Rust 工具链与大量 Rust 编写的第三方软件（如 ripgrep、exa、fd-find、rustc 本身、Firefox 部分组件等）；FreeBSD 内核中 **没有** Rust 代码；base system 中 **没有** Rust 组件；但社区讨论中逐渐形成一种可能的渐进路径：① 先在 ports 中持续维护 Rust 工具链的高质量支持；② 允许用 Rust 编写一些可选的用户态工具（如新的管理工具、测试工具）作为 ports 存在；③ 考虑引入 Rust 标准库到 base 以支持 Rust 编写的 base 组件（如果/当共识形成）；④ 内核 Rust 支持是非常远期的可能性（即使在 Linux 中也仍处于实验阶段）；16.0（预计 2027-2028）周期内是否会有 Rust 组件进入 base 仍是未知数

  **Rust 进入 FreeBSD 生态的渐进路径**：

  | 阶段 | 内容 | 状态（截至 2026.7） |
  |---|---|---|
  | ① | ports 中持续维护 Rust 工具链高质量支持 | 已实现 |
  | ② | 允许 Rust 编写可选用户态工具作为 ports 存在 | 部分实现 |
  | ③ | 引入 Rust 标准库到 base 以支持 Rust 编写的 base 组件 | 讨论中 |
  | ④ | 内核 Rust 支持 | 非常远期（Linux 中仍实验阶段） |

**史料**：FreeBSD Ports Collection lang/rust 目录与相关 Rust 应用 port 历史；freebsd-arch@ 邮件列表 Rust 架构讨论 ［A］

**史观**：专题语（不设条号）——技术路线分化：C 语言与 Rust 在操作系统开发中的争论是 2020 年代最重大的编程语言路线分化——Linux 选择 “实验性支持 Rust 驱动” 路径，OpenBSD 选择 “明确拒绝 Rust” 路径，FreeBSD 选择 “长期讨论、渐进探索” 路径，三种路径各有其哲学基础与工程逻辑；这种分化不是 “谁对谁错” 的问题，而是不同社区在同一技术变革面前基于自身历史与价值观做出的不同选择（原“总纲第 6 条”标号与基线第 6 条“和解优于斗争”不符，按 R2140 先例改不设条号专题语——批次 C275 问题 1）

**辨析**：需警惕两种极端叙事——一种是 “Rust 会立刻取代 C 成为 FreeBSD 主要语言”（不现实，30 多年 C 代码不可能重写），另一种是 “Rust 永远不会进入 FreeBSD base”（过于绝对，技术演进往往超出预期）；合理预期是：未来数年内 Rust 可能以有限方式进入 FreeBSD 生态（如某些可选工具、测试基础设施），但 C 语言仍将是 FreeBSD 内核与 base 系统的主导语言

**文献**：FreeBSD Ports Collection. lang/rust [EB/OL]. [2026-07-19]. <https://cgit.freebsd.org/ports/tree/lang/rust>; Evans S, et al. Is It Time to Rewrite the Operating System in Rust?[C]. USENIX HotOS 2021.
