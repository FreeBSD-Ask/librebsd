## 166.2.2 gnu/ 目录退役与 GNU 构建基础设施清理

**要点**：截至 2026 年 7 月，在 dialog 移除同期，FreeBSD 16.0-CURRENT 分支中专用的 gnu/目录已被整体退役，同步删除剩余 GNU 专用构建文件、测试、许可文件及相关基础设施；这是 FreeBSD 历史上首次将整个 gnu/子目录从源码树中移除，标志着自 4.4BSD-Lite2（1993 年）以来继承的 GNU 工具集成范式在 base system 层面的终结；该清理工作通过代码审查流程（类似 D55425 等审查票）进行

**史料**：FreeBSD src repository cgit 提交记录（gnu/目录移除提交，截至 2026 年 7 月）、Phoronix 2026 年 7 月 15 日相关报道（标题提及 FreeBSD 16 Goes GPL-Free，注意该报道发布时 16.0 尚未发布，应指 16-CURRENT）、OpenNET 2026 年 7 月 15 日俄文报道"Базовая система FreeBSD-CURRENT избавлена от компонентов под лицензией GPL"、FreeBSD 4.4BSD-Lite2 源码树 gnu/目录历史记录 ［A］

**史观**：许可证〔订正注：原误挂总纲第 24 条，权威 24=美是消解性的体验，许可证论旨非总纲条目，去号〕：gnu/目录作为 FreeBSD 源码树中 GNU 软件的物理容器，其整体退役不仅是法律意义上的许可清理，更是 BSD 项目对自身身份认同的形式化重构——从此 FreeBSD 源码树不再为 GNU 软件保留专属空间

**辨析**：gnu/目录退役不等于 FreeBSD 与 GNU 生态完全割裂——GCC、GDB、Emacs、Bash、coreutils 等 GNU 工具仍通过 Ports 和 pkg 提供，且将继续得到良好支持；该清理仅针对 base system（内核、系统库、命令行工具、安装器、基础管理工具）；部分媒体报道将“16-CURRENT 移除 GPL”简化为“FreeBSD 16 已 GPL-free”，这种表述不够准确，须明确分支状态

## 166.2.3 dpv 三件套 Ports 化延续与 bsdpv 重写

**要点**：在 base system 移除 dialog/dpv/libdpv/libfigpar 之前，相关组件已预先在 Ports 集合中创建以延续功能：devel/libfigpar、devel/libdpv、sysutils/dpv 三个新 ports 于 2026 年 6 月 29-30 日创建，devel/libfigpar 与 devel/libdpv 维护者为 Devin Teske（<dteske@FreeBSD.org>），sysutils/dpv 维护者为 Dag-Erling Smørgrav（<des@FreeBSD.org>）〔订正注：原误作三件套维护者均为 Devin Teske，与 166.2.6 辨析修正同步〕，许可证为 BSD-2-Clause；同时存在在 bsddialog 之上重写 dpv 为 bsdpv 的工程（审查票类似 D58133），将公共 API 从 dpv_*重命名为 bsdpv_* 以标记与 GNU dialog 依赖的彻底决裂，并修复原 dpv 的若干 bug；该“先 port 化延续、再 base 移除、再 BSD 许可重写”模式是 FreeBSD 渐进式淘汰工程哲学的体现

**史料**：FreeBSD FreshPorts 记录（devel/libfigpar、devel/libdpv、sysutils/dpv 三个 ports 添加时间 2026 年 6 月 30 日前后，维护者 dteske）、FreeBSD Phabricator/Reviews 相关审查票（ports 创建审查、bsdpv 重写审查）、类似 14.0 net/freebsd-telnetd、15.0 ftp/freebsd-ftpd 的“port 接续”模式历史记录 ［A］

**史观**：终结与延续〔订正注：原误挂总纲第 25 条，权威 25=逻辑是形式主义而非世界本身的结构，去号〕：FreeBSD 从未采用“一刀切”式淘汰策略，而是遵循“引入替代 → 验证成熟 →port 化延续 →base 移除 → 原生重写”的渐进路径；这一路径既保证了许可证纯洁化目标的实现，又最大限度减少了对现有用户的破坏

**辨析**：ports 创建时间（2026 年 6 月底）早于 base 移除时间（2026 年 7 月），表明该工程是事先规划而非临时补救；bsdpv 重写工程截至 2026 年 7 月可能处于审查或已提交但尚未完全稳定状态，是否最终合入 16.0-RELEASE 仍需以 RELEASE 时的源码状态为准；dpv 等工具属于较为边缘的系统工具，多数普通用户可能不会直接使用，但作为系统组件的延续体现了对兼容性的重视

**文献**：FreeBSD FreshPorts. devel/libfigpar, devel/libdpv, sysutils/dpv 条目（freshports.org）；FreeBSD Phabricator. 相关 ports 创建与 bsdpv 审查票（reviews.freebsd.org）；FreeBSD 14.0-RELEASE Release Notes（net/freebsd-telnetd port 化）；FreeBSD 15.0-RELEASE Release Notes（ftp/freebsd-ftpd port 化） ［A］

## 166.2.5 辩证链第一层（批评层）——GPL/GNU 阵营对 dialog 移除与 GPL 代码清零的批评

**要点**：GPL/GNU 阵营对 BSD 许可证纯洁化工程的批评可归纳为三点。**其一，法律必要性存疑**：GPLv2 允许与 BSD 许可证代码共存，dialog 作为 LGPL/GPL 组件在 FreeBSD base 中存在 20 余年未引发许可证冲突，移除 dialog 的法律必要性存疑——GPL 软件进入 base 不迫使 FreeBSD 改变自身许可证；FSF 官方许可证评论页面（gnu.org/licenses/license-list.html）将 FreeBSD 许可证归类为“松散的、纵容型、非 copyleft 的自由软件许可证，兼容 GNU GPL”，承认 BSD 与 GPL 在法律层面可共存，移除 GPL 组件并非许可证兼容性所必需。**其二，“重新发明轮子”的资源浪费批评**：bsddialog 作为 dialog 的 BSD 许可替代，需重复实现 dialog 已成熟的功能（如菜单、表单、进度条、文件选择器等 TUI 控件），开发者资源本可用于更有价值的工程任务，如驱动开发、性能优化、新硬件支持；FSF 在许可证评论中虽承认“修改版 BSD 许可证并不差”，但同时“更推荐 Apache 2.0 许可证”，这一立场隐含对 BSD 路径的保留态度——FSF 倾向 copyleft 路径，dialog 移除强化了非 copyleft 路径，与 FSF 推荐方向相反。**其三，兼容性风险**：bsddialog 虽力求 API 兼容，但 GNU dialog 的部分高级特性与 `.dialogrc` 配置支持可能存在差异，依赖这些特性的脚本可能受影响——dialog 的 `.dialogrc` 文件允许用户自定义颜色、属性、阴影等界面元素，bsddialog 的兼容程度需逐一验证。这些批评共同指向“过度纯洁化”质疑：FreeBSD 是否在追求许可证纯洁的工程中偏离了“实用主义”传统，将许可证标签置于功能完整性之上。

## 166.2.6 辩证链第二层（反批评层）——FreeBSD 阵营对批评的回应与许可证纯洁化工程必要性论证

**要点**：FreeBSD 阵营对 GPL/GNU 阵营批评的回应可归纳为三点。**其一，BSD 许可证纯洁化不是“法律必要性”问题而是“工程原则”问题**：FreeBSD Licensing Policy（docs.freebsd.org/en/articles/license-guide/）明确偏好 BSD-2-Clause 许可证——“The FreeBSD Project uses this text as the preferred license”——base system 作为操作系统核心应保持许可证一致性，这是项目身份认同的形式化表达；法律必要性论证局限于“是否被强制”，但工程原则论证扩展至“是否应当”，二者属不同论证层次，FreeBSD 选择后者。**其二，bsddialog 非“重新发明轮子”而是“基于 FreeBSD 基础库的重新实现”**：bsddialog 由 Alfonso S. ## 166.2.7 辩证链第三层（再回应层）——GPL/GNU 阵营对 FreeBSD 反批评的再回应

**要点**：GPL/GNU 阵营对 FreeBSD 反批评的再回应可归纳为两点。**其一，“工程原则”论证可能遮蔽实际利益结构**：BSD 许可证纯洁化的主要受益者是商业厂商（如 iXsystems、Netgate、Juniper、Apple 等），这些厂商可无义务地将 base system 用于专有产品——BSD 许可证允许商业再分发而不要求开源衍生作品，这一“无义务”特性使厂商可在 base system 之上构建闭源商业产品（如 Netgate pfSense、iXsystems TrueNAS）；GPL 移除的“原则”叙事服务于“商业友好”的实际利益，“工程原则”作为修辞策略将利益结构问题转化为技术哲学问题。**其二，bsddialog 的“充分验证”需经独立第三方审计确认**：3,123 次 commit 与 7 个 release 的数量指标不等于代码质量——commit 数量反映开发活跃度，但不直接证明代码的安全性与可维护性；dialog 作为 GNU 项目多年维护的成熟软件，其代码审计深度可能超过 bsddialog——dialog 经历了 Linux 发行版、GNU/Hurd、其他 BSD 项目多年的实战验证，而 bsddialog 的部署范围主要限于 FreeBSD 生态。这一再回应指向“原则 vs 利益”与“数量 vs 质量”两组元层面的诘难：FreeBSD 阵营的反批评在论证层次上回应了 GPL/GNU 阵营的批评，但 GPL/GNU 阵营的再回应将争议提升至元层面——“原则”叙事本身是否是利益结构的遮蔽，“充分验证”的判断标准如何确立。

**史料**：FreeBSD Foundation 2024 Annual Report（freebsdfoundation.org/our-donors/，企业赞助者名单含 iXsystems、Netgate、Juniper、Apple 等）；bsddialog 项目页面（gitlab.com/alfix/bsddialog，3,123 commits/7 releases/18 tags，但无独立第三方安全审计报告）；GNU dialog 项目维护历史（FSF GNU 项目档案，dialog 作为 GNU 项目多年维护的成熟软件）；FreeBSD 16.0-CURRENT base system 许可证扫描（须以 cgit.freebsd.org/src/ 实时源码与许可证扫描工具输出为准）；Linuxiac 2026-07-17 报道（确认 4 年迁移工程，但未涉及独立安全审计）；freshports.org misc/dialog port（GNU dialog 仍可通过 Ports 安装）〔L1 代码/构建产物/L3 官方文档与公告/L5 二手研究〕

## 166.2.8 辩证链合图层——dialog 移除与 GPL 代码清零的史观审视

**要点**：dialog 移除与 GPL 代码清零的合图不在“一方正确、一方错误”的二元判定中，而在 FreeBSD 选择的“base 纯洁化 + ports 多元化”双层架构中——base system 保持 BSD 许可证一致性满足工程原则与商业友好需求，Ports 集合保留 GPL 软件（含 GNU dialog）满足功能兼容与用户选择需求。这一双层架构使“BSD 纯洁化”与“GPL 软件可用”两个看似矛盾的诉求在分层架构中得到和解。Devin Teske 创建的 `devel/libfigpar`、`devel/libdpv`（维护者 <dteske@FreeBSD.org>）与 `sysutils/dpv`（维护者 <des@FreeBSD.org>，即 Dag-Erling Smørgrav）三个 Port（2026 年 6 月 29-30 日由 <des@FreeBSD.org> 提交）与 bsdpv 重写工程体现了“不抛弃旧用户”的兼容性承诺。这一合图印证总纲第 6 条“和解优于斗争”——和解不是 GPL 阵营放弃批评，也不是 BSD 阵营放弃纯洁化，而是双方在“base 与 ports 分层”的架构中找到各自位置。但合图不等于完美——bsddialog 与 GNU dialog 的功能差异仍可能影响部分用户，GPL 阵营的“资源浪费”批评仍成立（bsddialog 确实重复实现了 dialog 的功能），这印证总纲第 2 条“历史是形式主义化的非存在”——所谓“GPL 清零”只是当下主体对形式的重构，下一刻的争议（如 Rust 是否进入 base、AI 生成代码的许可证问题）正在形成。16.0-CURRENT 作为“可能性的集合”（参见 65.6 史观映射），其 GPL 清零不是 FreeBSD 历史的终点，而是新的形式主义化过程的起点。

**史料**：FreeBSD Ports 中 GNU 软件列表（misc/dialog port、lang/gcc port、misc/gnuls port 等，freshports.org 一手核验）；bsddialog 与 GNU dialog 功能差异（`.dialogrc` 配置支持等，须以 bsddialog 项目文档为准）；FreeBSD FreshPorts 三个 ports（devel/libfigpar、devel/libdpv、sysutils/dpv，2026-06-29/30）；FreeBSD 16.0-CURRENT 开发状态（截至 2026 年 7 月，main 分支处于 Open 状态）；FreeBSD Licensing Policy（docs.freebsd.org/en/articles/license-guide/，BSD-2-Clause 偏好条款）；Linuxiac 2026-07-17 报道与 IT 之家 2026-07-18 报道（dialog 移除事件三源交叉验证）

**史观**：总纲第 6 条——和解优于斗争〔订正注：原条号 6 下混写“分离聚合是永恒规律”（系第 4 条名目），拆分错配〕：dialog 移除的合图层印证“和解是事物真正完整的一刻”——危机不是历史的终点，`gnu/` 目录的移除看似“GNU 时代终结”，实则是 FreeBSD 与 GNU 生态在新架构（base/ports 分层）中的重新定位；总纲第 2 条——历史是形式主义化的非存在：合图不等于完美，下一刻的争议正在形成，史家须以自反姿态承认本书自身的形式主义性质；总纲第 8 条——本体论上各方平等：BSD 阵营的“工程原则”与 GPL 阵营的“资源浪费”批评在本体论上地位相等，二者皆是各主体性呈现的利益诉求表达，差异仅是一刻状态的不同，史家不得以“原则”或“利益”任一视角压制另一方

## 166.2.9 当事人素材与叙述章——BSD 许可证纯洁化的历史脉络（1987–2026）

2026 年 7 月 10 日，G. Branden Robinson 在 linux-man 邮件列表关于 man(7) 手册语言之争的回帖中做了一次跨度近半个世纪的复盘，把 BSD 许可证史与 GPL 回避原则连成了一条清晰的因果链——这份反思也是本节目前可直接引用的一手史料之一

Branden 的时间起点是 1979 年，他写道 man(7) 出自 "Bell Labs CSRC, 1979" 并被 "good enough" 也就是 "worse is better" 的原则保留至今，同时给出了文档语义化失败的判断：Markdown "can't do semantics"，DocBook-XML 有 "something like 400 elements" 过于臃肿，∴ "Goodbye, 'semantic Web'"

真正的转折发生在约 1987 至 1988 年。Branden 指出 mdoc(7) 的诞生并非出于美学偏好，而是一场直接的许可证规避："mdoc(7) was only created in the first place because AT&T were such jerks about the licensing of troff (and Unix generally). So the Berkeley CSRG's mandate, I infer, was to spec out a macro system that could eventually be ripped free of troff and set down on top of something else"——Berkeley CSRG 从立项的第一天就把"可剥离 GNU troff"写进了 mdoc 的设计目标

紧随其后，James Clark 的 groff 出现："That decision, taken in maybe 1987 or 1988, predated by only one year the advent of James Clark's 'groff', which BSD promptly shipped in Net/2 and later 4.4BSD"，但结局是被后辈再次移除："Later, its descendants ripped it out again, because GPL and C++ bad. BAD!"——这是 BSD 阵营对 GPL 组件主动切割最直白的一次史料记录

1995 年 5 月，4.4BSD Lite Release 2 发布，被 Branden 称为 "the 'last' Berkeley CSRG release"。此后 CSRG 的工作重心转向 BSDI："The 'real work' was by then happening as BSDI, where every developer was assured that their deeply principled avoidance of the viral GPL would result in billionaire status for them all. Winning!" 这句略带讽刺的话把 BSDI 时期"GPL 纯洁化"从技术选择提升到了近乎商业信条的地位

许可证纯洁性的实践并不限于 BSD 一侧。在另一封 2021 年 8 月 1 日的回复中，Colomar 引述 Branden 关于 groff 文档形态的经验："We'd had it documented in the groff Texinfo manual instead, which some distributors won't ship because it uses some obnoxious features of the GNU FDL that are not DFSG-free"——部分发行版因 GNU FDL 中"不 DFSG-free"的特性拒绝发行 groff 手册，团队因此改用 ms 宏包自我文档化，形成一份 22 页的 ms.ms 文档，由 Branden 亲自修订

Branden 在 2026 年 7 月那封长信里给这条脉络下了结论："Almost the only people writing mdoc(7) are strident BSD partisans"，并戏谑地指出 "You will then understand how *BSD is a refuge from the evangelicalism of GNU people"

而在 Linux man-pages 项目内部，Branden 明确主张不要试图追溯 BSD 特性的来源与时间线："researching such history is a poor use of Linux man-pages contributors' time"，理由是工作量 "too much work"、缺乏自动化工具，∴ "The juice is not worth the squeeze"。他给出的替代安慰是 "this project largely uses the GPL, and that they can't expect anything good to come from sick, evil copyleftists anyway"

至此，BSD 许可证纯洁化的历史轮廓可见一斑——从 1987/1988 年 Berkeley CSRG 为绕开 AT&T 对 troff 的严苛授权而设计 mdoc 的立项动因，到 *BSD 在 Net/2 与 4.4BSD 发行 groff 之后又因其 GPL 与 C++ 属性而再度剥离，再到 1995 年 BSDI 时代把"deeply principled avoidance of the viral GPL"当作近乎致富承诺的集体信条，这条线索构成了 FreeBSD 后续十余年持续迁移工程（从 GCC 到 Clang、从 GNU binutils 到 LLVM、从 GNU dialog 到 bsddialog）的历史前提与思想底色；Branden 在 2026 年 7 月的复盘正是这段历史在 Linux 文档社区内部获得公开、连贯表述的少数几处一手史料之一

## 166.2.10 当事人素材与叙述章——BSD 血统进入 Linux 内核与许可证纯洁化的镜像

2003 年 8 月，Douglas Gilbert 主持维护的 scsi_mid_low_api.txt 文档卷入一场许可证事件，维护者达成一致判定 GFDL 不适合作文档许可证，建议将文档重新许可为 GPL 兼容条款并折叠进 scsi_mid_low_api.txt，补丁将 GNU 自由文档许可证替换为 GNU 通用公共许可证 v2 或更高版本，维护者共识记录为 "we agreed that GFDL is"，这场小型事件在 GPLv3 争议正式发酵前已埋下 GPL 阵营对文档许可证形态的关注

到 2010 年代，BSD 血统代码大规模进入 Linux 内核——Jiri Slaby 指出 madwifi 走的是移植来的 BSD net80211 实现 "madwifi goes through ported bsd net80211"，Michael Wu 在 Linux 802.11x 支持差距讨论中转述 "Madwifi has a fairly complete 802.11 stack (ported from netbsd)"，Andriy Korud 在开放硬件无线卡讨论中重申 "madwifi Linux driver with MAC layer ported from xBSD"；IPsec 工具链的谱系同样清晰，Vegard Nossum 在 Kconfig 帮助文本中留证 "PF_KEYv2 socket family, compatible to KAME ones" 与 "IPsec tools ported from KAME"，KAME 源自 FreeBSD 与 NetBSD；文件系统工具的移植谱系更为古老，Dave Chinner 在 hfsplus 维护困境讨论中点明 "ported from the open source Darwin code drops"，而 Darwin 内核源自 4.x BSD；Andrew Morton 在 UFS 目录与页缓存改造讨论中回忆早年尝试移植 BSD ufsutils 失败 "I had a go at porting BSD ufsutils a few years ago and nearly died"，Jan Engelhardt 追问时留下"几年前移植 BSD ufsutils 几乎丧命"的相同表述，Al Viro 审阅 Linux UFS 端口时把 OpenBSD 6.1 的 Newfs 与 fsck 作为权威交叉核查基线 "pass fsck on OpenBSD"；内存管理领域，linuxsuperpages 项目讨论文本明确 "Superpages FreeBSD prototype that has been ported to the 2.6 Linux kernel"，把 Rice University 在 FreeBSD 上的原型移植到 2.6 内核覆盖 IA64、x86-64 与 x86-32

2016 年 7 月 15 日，Dexuan Cui 的 Hyper-V VM Sockets（AF_HYPERV）cover letter 把新传输层定位在 BSD socket 语义之上，理由是以相同 socket 调用保持应用可移植性，直录引语 "by the traditional BSD-style socket APIs"；同一时期 linux-fsdevel 线程中，Indan Zupancic 反对 Linux-only 的 sys_syncfs 添加，要求同时加入 BSD 版本 "at least ad it together with BSD so it's slightly portable"，而 Eric Dumazet 在 BPF 模运算讨论中反问 "What about the other OS - eg all the BSDs?"，David Laight 追问 BPF 是否"本应是合理可移植的"；netdev 线程中 Luis Rodriguez 明确 "BSD folks can simply use the external unified tree now to port the driver to BSD"，同时承认受 "license divergence" 限制

2018 年 util-linux v2.35 发布公告中，Carlos Santos 因 GPLv3 引入对嵌入式部署的影响直接提议改用 BSD 等更宽松许可证移植同类代码，原文 "An alternative approach would be porting a similar code using a more liberal license, e.g. BSD"，这是 BSD 许可证作为 GPL 替代方案最直接的正面主张；同期 util-linux 2.28-rc1 与 2.28-rc2 两次发布公告都把"移植到非 Linux 系统（BSD、XOs/OSX）"作为改进项公开留痕，英文原文 "portable to non-Linux systems (BSD, XOs)" 与 "The package build system and code have been improved to be more portable to non-Linux systems (BSD, OSX)"

2021-2022 年间，IPE 与 IMA 元数据格式能否进入 NFS 标准及 IETF 规范之争浮现了 GPL 与 BSD 许可证边界的实质冲突，James Bottomley 反驳 Chuck Lever 关于 GPL 束缚格式的说法，指出 GPL 是代码许可证而非数据或文档许可证，而 IETF 贡献采用与 GPL 不兼容的 BSD 风格许可证，原文 "IETF contributions occur under a BSD-style license incompatible with the GPL"，非 Linux 实现者依赖该流程规避许可索赔；同一时期 netdev 上 McHardy 在 ppp SC_MUST_COMPRESS 补丁里把 if_ppp.h 头文件注释整体替换为 CMU 来源的 BSD 许可证文本，立即引发对其 GPL 兼容性的追问 "Why do you change the license, especially to something GPL-incompatible?"

GPL 阵营对 BSD 迁移趋势的公开表态最早清晰见于 Linux Kernel Summit 场合——Greg KH 反对 Bradley Kuhn 把诉讼当作唯一出路，声称 "If you don't defend the GPL in courts, we need to give up on it"，并援引 BusyBox 诉讼催生 Toybox、LLVM 因规避 FSF 与 GPLv3 而生的案例，称无意开战；Guenter Roeck 在同一议题中援引其此前雇主经历，判断多数新项目改用 BSD 或 Apache 许可证以规避 GPL 隐患，原文 "most new projects ended up using BSD or Apache licenses to avoid the pitfalls of GPL"，构成 BSD 许可证对 GPL 形成迁移替代的实证陈述

2026 年 7 月 FreeBSD 完成 GPL 移除工程之时（dialog/dpv 移除与 `gnu/` 目录退役，Linuxiac 2026-07-17、IT 之家 2026-07-18、Phoronix 2026-07-15 三源印证），Linux 内核邮件列表内部关于 BSD 血统代码的持续追溯才第一次获得系统性呈现——BSD 血统代码在 Linux 内核中已分布至 madwifi、ar5523（John W. Linville 在 wireless-next 拉取请求中说明 "addition of the ar5523 driver, ported from an original FreeBSD driver"）、IPsec tools、KAME 移植、UFS 工具、Superpages 内存管理、BSD socket 语义、OpenBSD 网络随机化补丁（补丁主题即 "OpenBSD Networking-related randomization port"）、madwifi 完整 802.11 栈等多个子系统，且 BSD 许可证在 Linux 生态内被显式承认是规避 GPL 的主流替代路径——BSD 许可证的"纯洁化"（把 GPL 从 base 剔除）与 BSD 血统代码的"流动性"（Linux 内核持续吸收 BSD 派生实现）在同一历史过程中互为镜像，Linux 内核内部 BSD 派生代码的规模恰是 FreeBSD 侧许可证纯洁化工程的外部支撑条件

## 166.2.11 叙述章——GPL 移除与许可证纯洁化的编年时间线（2003–2026）

2003 年 8 月 25 日，Christoph Hellwig 在 linux-scsi 列表中记录了维护者的共识——GFDL 不适合作为文档许可证，Douglas Gilbert 的 SCSI 文档应重许可为 GPL 兼容条款并折叠进 scsi_mid_low_api.txt：「we agreed that GFDL is not suitable」，此事件在 GPLv3 争议发酵前已埋下 GPL 阵营对文档许可证形态的关注；一年之后许可证议题首次以技术实体身份进入 Linux 内核的合法性论证——2004 年 2 月 18 日 Paul E. McKenney 在 linux-mm 关于 invalidate_mmap_range 非 GPL 导出之争中做了一次全盘托出：「in the spirit of full disclosure, the wrapper is actually distributed under the bsd license」，同时澄清 GPFS 工程师口中的 gpl 实为 gpfs portability layer 缩写，导出争议靠一份 BSD 许可证声明化解

BSD 语义随后沿"移植"与"对齐"两条动词路径渗入内核的接口层。2004 年 6 月 2 日 Sam Leffler 在 netdev 表示「done a rough port of wpa_supplicant to the bsd world too」；同年 12 月 9 日 Ilya Pashkovsky 的补丁说明要求 Linux 的 SO_REUSEADDR「implement the behaviour of SO_REUSEPORT of BSD」，把 BSD 接口语义当作 Linux 应当追齐的规范而非可选项。2005 年 2 月 netdev 出现主题即声明来源的「[PATCH] OpenBSD Networking-related randomization port」；同年 5 月 9P2000 的使用说明把 Plan 9 用户态程序移植目标写作「ported to Linux/BSD/OSX/etc」；2005 年 8 月 14 日 Patrick McHardy 在 ppp SC_MUST_COMPRESS 补丁中把 if_ppp.h 注释整体替换为 CMU 来源的 BSD 许可证文本，立即招致追问「Why do you change the license, especially to something GPL-incompatible?」——BSD 许可证作为 GPL 替代物的争论从 SCSI 文档一路延伸到网络协议栈

文件系统侧的 BSD 血统在十年间以零散补丁的形式累积。2008 年 4 月 4 日 fstest 套件的起源被记录为「when Pawel Jakub Dawidek ported ZFS to FreeBSD」，随后由 NTFS-3G 团队移植至 Linux 验证权限与属主支持；2009 年 2 月 Corentin Chary 介绍 UFFS 时把可移植目标写作「portable (linux, windows, fuse (for MacOSX and *BSD))」；2006 年 5 月 Andrew Morton 在 UFS 补丁审阅中自嘲「I had a go at porting BSD ufsutils a few years ago and nearly died」，Jan Engelhardt 于同日重复同一句；2011 年 3 月 Indan Zupancic 反对 Linux-only 的 sys_syncfs 添加，要求同时加入 BSD 版本「at least ad it together with BSD so it's slightly portable」；2017 年 6 月 Al Viro 要求 UFS 移植测试镜像「pass fsck on OpenBSD」，以 OpenBSD 6.1 的 newfs 与 fsck 为跨查基线

协议可移植性成为 BPF、IPsec 与网络接口的隐性约束。2009 年 1 月 Timo Teras 以可移植性为 SADB_X_EXT_NAT_T_OA 辩护，断言该功能已在 BSD 家族与 Linux 跨平台可用「Works on Linux too」；2012 年 9 月 Eric Dumazet 在 BPF 模运算讨论中反问「What about the other OS - eg all the BSDs?」并补一句「Or is BSD so hard to update these days」；2014 年 2 月 Luigi Rizzo 在 netmap 公告中宣称「All the code below runs with equal features and performance on FreeBSD and Linux」；2007 年 5 月 Rick Jones 把 Linux 的 ip_local_port_range 小值区间归为「variations on the old BSD defaults theme」

BSD 作为可移植性测试台的地位在 2010 年代后半段被显式承认。2010 年 2 月 Karsten König 报告 ax88172 无法改 MAC 地址时贴出 openbsd misc 列表与 cvsweb 链接，Andrew Morton 转发时写道「porting that openbsd patch across, see if it fixes Karsten's hardware」；2012 年 11 月 John W. Linville 在 wireless-next 拉取请求中点名「addition of the ar5523 driver, ported from an original FreeBSD driver」；2013 年 7 月 Luis R. Rodriguez 重申「FreeBSD has many users」，并说明「BSD folks can simply use the external unified tree now to port the driver to BSD」，同时承认受「license divergence」限制；2017 年 5 月 Sowmini Varadhan 与 Oleg 以「struct ip is a BSD-ism, intended to be used if you were porting some BSD app」解释 Linux 内核中 struct ip 仅为可移植性垫片；2011 年 8 月 Adrian Chadd 自述「I'm porting the atheros 802.11n TX aggregation code to FreeBSD」

BSD 与 Linux 在事件通知模型上完成了一次互鉴与反向移植：2021 年 9 月 Johannes Lundberg 提议 epoll EPOLLEMPTY 时说明「similar functionality was previously added to FreeBSD as the kqueue event EVFILT_EMPTY」，Eric Dumazet 反驳后反向提出「Our timestamping infrastructure should be ported to FreeBSD instead」；性能修正亦向 BSD 侧回流——2020 年 3 月 Josh Triplett 把 ENA 管理命令轮询从 5 ms 砍至 10 us，c5.12xlarge 适配器初始化从 173.6 ms 降至 1.9 ms，并建议同一修正移植到 EFA 驱动与 FreeBSD 侧；2020 年 8 月 James Bottomley 与 Pavel Machek 在 IPE/IMA 元数据能否进入 IETF 标准之争中，以「IETF contributions occur under a BSD-style license incompatible with the GPL」界定贡献路径的法律边界；2022 年 3 月 Carlos Llamas 为 FUSE UAPI 整数类型提议 BSD 可移植垫片，援引 DRM 先例 commit 1a95916f5465；2026 年 1 月 Arnd Bergmann 与 Bernd Schubert 以 BSD 用户态为 FUSE UAPI 改动的可移植性测试台，Bernd Schubert 称「I would expect the patch to not have changed anything for BSD」

GPL 阵营对 BSD 迁移趋势的公开表态最早清晰见于 Linux Kernel Summit 场合——2016 年 8 月 27 日 Greg KH 反对 Bradley Kuhn 把诉讼当作唯一出路：「If you don't defend the GPL in courts, we need to give up on it」，并援引 BusyBox 诉讼催生 Toybox、LLVM 因规避 FSF 与 GPLv3 而生的案例；两天后 Guenter Roeck 援引前雇主经历给出实证回应：「most new projects ended up using BSD or Apache licenses to avoid the pitfalls of GPL」；同一时段 util-linux 维护者给出了 BSD 许可证作为替代方案的正面主张——2020 年 1 月 24 日 Carlos Santos 因 GPLv3 对嵌入式部署的影响提出「An alternative approach would be porting a similar code using a more liberal license, e.g. BSD」

叙述的尾声落在 linux-man——2021 年 8 月 1 日 Colomar 引述 groff 团队因 GNU FDL 中「obnoxious features of the GNU FDL that are not DFSG-free」而拒绝发行 Texinfo 手册、改用 22 页 ms 宏文档自我文档化；2026 年 7 月 10 日 G. Branden Robinson 复盘 mdoc(7) 的立项动因：「mdoc(7) was only created in the first place because AT&T were such jerks about the licensing of troff」，James Clark 的 groff 仅晚该决策约一年问世，*BSD 随即在 Net/2 与 4.4BSD 中发行它，其后续者又「because GPL and C++ bad. BAD!」将其移除，最终断言「*BSD is a refuge from the evangelicalism of GNU people」；其 2025 年 12 月 30 日的前一封信更早地把 BSDI 时期的 GPL 回避称作每位开发者被许诺的「billionaire status」，并主张追溯 2.11BSD 特性时间线「too much work」——「The juice is not worth the squeeze」

## 166.2.12 叙述章——BSD 血统代码流入 Linux 内核与 FreeBSD 侧 GPL 移除的双向镜像

2003 年 8 月，Christoph Hellwig 在 linux-scsi 列表讨论 scsi_mid_low_api.txt 文档许可证时留下维护者共识 we agreed that GFDL is not suitable，Douglas Gilbert 将其 SCSI 文档从 GNU 自由文档许可证改为 GPL 兼容条款；这一事件在 GPLv3 争议发酵前已埋下 GPL 阵营对文档许可证形态的关注。2004 年 2 月，Paul E. Linville 在 wireless-next 拉取请求中点名 addition of the ar5523 driver, ported from an original FreeBSD driver，2016 年 7 月 Dexuan Cui 的 Hyper-V VM Sockets AF_HYPERV cover letter 明确 by the traditional BSD-style socket APIs，新传输层被定位为 BSD socket 语义之上以保持应用可移植性

## 166.2.13 叙述章——可移植性垫片作为 BSD 与 Linux 共存工程机制

GPL 移除的另一面是可移植性承诺——当 FreeBSD 从 base system 中剔除 GPL 组件时，Linux 内核同时在做相反方向的工程：把 BSD 接口保留为可移植性垫片，使 BSD 用户态工具能在 Linux 上无缝编译运行，两条工程路径在同一个历史时段内互为镜像

网络层是最典型的保留区。2017 年 5 月 Sowmini Varadhan 在 netdev 关于 struct ip 冗余的争论中直接定性："struct ip is a BSD-ism, intended to be used if you were porting some BSD app"，Linux 内核中的 struct ip 并非原生实现，而是为可移植性保留的垫片；2012 年 9 月 Eric Dumazet 在 BPF 模运算提议中反问"what about the other OS - eg all the BSDs?"，并补一句"Or is BSD so hard to update these days"，把 BPF 指令集冻结问题与 BSD 兼容性挂钩；David Laight 在同线程进一步提出"I had a vague idea that BPF was supposed to be reasonable portable"，BPF 作为 BSD 与 Linux 共享的过滤器语言被明确当作跨平台接口处理

文件系统层同样保留了 BSD 血统。David Howells 在讨论 st_gen 字段时指出该字段沿用 BSD 命名，Maciej W. Rozycki 补充"Note the Alpha port has had an st_gen member reserved in its struct stat for many years now"，并称该字段"as it is called that way on BSD"——BSD 的 stat 结构体成员名被 Linux 内核保留多年，构成 stat(2) 系统调用跨平台接口的一部分，属于接口契约式的历史继承而非代码抄录

FUSE UAPI 整数类型改造把 BSD 用户态工具作为可移植性验证的正式目标。Carlos Llamas 2022 年 3 月为 __u32 类型提出 BSD 兼容垫片，援引 DRM 先例 commit 1a95916f5465，称"the best way to accommodate this while still conforming with the __u32 types"；Arnd Bergmann 与 Bernd Schubert 2026 年 1 月进一步主张"not defining __linux__ makes it use the stdint types after all"，所以"I would expect the patch to not have changed anything for BSD"——BSD 用户态工具成为 Linux FUSE 接口设计的显式兼容目标

驱动层的双向移植同样构成工程证据。Joe Perches 在 ath10k 争论中指出"porting easier between bsd and linux"，把 mbuf 与 skb 数据访问器的差异作为跨系统移植成本的量化指标；Dave Chinner 关于 hfsplus 维护困境讨论中援引"We used to have one that was ported from the open source Darwin code drops"，把 hfsplus 工具链追溯至 Darwin/BSD 血统；John W. Linville 在 wireless-next 拉取请求中声明"addition of the ar5523 driver, ported from an original FreeBSD driver"；Fred L Templin 的 IPv6 RFC4214 补丁说明"entail a port of the FreeBSD rtsold daemon"

反向的移植提案则体现两个方向的对偶。Eric Dumazet 在 Johannes Lundberg 提议为 epoll 增加 EPOLLEMPTY 时反驳"similar functionality was previously added to FreeBSD as the kqueue event EVFILT_EMPTY"，转而提出"Our timestamping infrastructure should be ported to FreeBSD instead"；Luis Rodriguez 在 alx 讨论中直言"BSD folks can simply use the external unified tree now to port the driver to BSD"，但承认受"license divergence"限制——BSD 派生代码在 Linux 内核中的流动并非无成本

AF_PACKET 的可移植性争论则展示了这一承诺的边界。Tom Herbert 直接反驳担忧："it already has Linux specific stuff for checksum offload. The portability to BSD for AF_PACKET is a non-issue"——当 Linux 侧新增特性已经 Linux-specific 时，BSD 可移植性被显式判定为非阻碍，portability shim 只在接口已冻结的场景下才有约束力

从工程机制看，FreeBSD 的 GPL 移除与 Linux 内核的 BSD 接口保留构成同一历史过程的两面：前者以深原则回避传染性 GPL 为工程目标，后者以 portability shim 为工程手段；portability shim 把 BSD 接口从源代码血缘提升为接口契约，使 BSD 与 GNU 的技术合作得以绕过法律层面的传染性争议

GPL 阵营内部的公开立场分化最清晰见于 2016 年 8 月 Linux Kernel Summit 的 ksummit 讨论——2016 年 8 月 27 日 Greg KH 反对 Bradley Kuhn 把诉讼当作唯一出路，留下著名判断 If you don't defend the GPL in courts, we need to give up on it，并援引 BusyBox 诉讼催生 Toybox、LLVM 因规避 FSF 与 GPLv3 而生的案例，称无意开战；两天后 8 月 29 日 Guenter Roeck 援引其此前雇主经历给出实证回应，指多数新项目改用 BSD 或 Apache 许可证以规避 GPL 隐患——most new projects ended up using BSD or Apache licenses to avoid the pitfalls of GPL——GPL 阵营的公开表态与 BSD 迁移的实证首次在同一场会议中被并列陈述

BSD 许可证作为 GPL 替代方案在 Linux 生态内的正面主张则更早在 2020 年 1 月 24 日 Carlos Santos 于 util-linux v2.35 发布公告回复中直接表达——因 GPLv3 对嵌入式部署的影响，他提出 An alternative approach would be porting a similar code using a more liberal license, e.g. BSD；随后 2020 年 8 月 11 日 James Bottomley 在 IPE 与 IMA 元数据格式能否进入 NFS 标准及 IETF 规范之争中反驳 Chuck Lever 关于 GPL 束缚格式的说法，界定 GPL 是代码许可证而非数据或文档许可证，而 IETF 贡献采用与 GPL 互斥的 BSD 风格许可——IETF contributions occur under a BSD-style license incompatible with the GPL；同年 8 月 1 日 Colomar 在 linux-man 邮件列表中引述 groff 团队因 GNU FDL 中"令人厌烦的、不符合 DFSG"的特性而拒绝发行 Texinfo 手册、改用 ms 宏包自我文档化的经验，形成 22 页的 ms.ms 文档——BSD 与 GNU 的许可证立场差异在 Linux 生态内已构成一条可识别的技术-法律边界

2026 年 6-7 月，FreeBSD 16.0-CURRENT 分支执行了这场许可证立场分化的最终工程——6 月 30 日 Dag-Erling Smørgrav 在 Ports 中创建 devel/libfigpar、devel/libdpv、sysutils/dpv 三个 ports 作为 base 移除的前置延续，随后 7 月 dialog、dpv、libdpv、libfigpar 从 base 中移除，专用 gnu/ 目录整体退役；Phoronix 7 月 15 日首发、Linuxiac 7 月 17 日深度报道、IT 之家 7 月 18 日中文转载三源交叉印证 FreeBSD Base System No Longer Contains Any GPL-Licensed Software
