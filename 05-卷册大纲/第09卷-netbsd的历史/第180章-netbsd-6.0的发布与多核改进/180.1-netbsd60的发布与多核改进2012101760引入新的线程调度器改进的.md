**要点**：NetBSD 6.0（**2012.10.17**）继续由 Andrew Doran（安德鲁·多兰） 改进的线程调度器，引入更细粒度的优先级继承与多核负载均衡；6.0 的 SMP 改进特别针对 8 核以上机器优化；调度器设计延续 5.0 渐进式路径，未引入革命性重构

## 180.1.2 NPF 防火墙的引入

  **NPF 首次导入 commit 原文**：

  > Import NPF - a packet filter. Some features: ...
  >
  > ——rmind (Mindaugas Rasiukevicius), netbsd-src 仓库，commit `2e6f2099c639`, 2010-08-22T18:56:18Z

**要点**：NetBSD 6.0 引入 NPF（NetBSD Packet Filter）作为新防火墙框架，由 Mindaugas Rasiukevicius 设计；NPF 提供 IPF（IPFilter）与 PF（OpenBSD 移植）的现代替代品，支持状态跟踪、NAT、流量整形；NPF 设计强调可扩展性与性能，使用 BPF 字节码

**史料**：NPF 设计文档与 man npf(7)；tech-net 邮件列表讨论；CVS commit log 中 npf 相关 commit；netbsd.duckdb netbsd-src 仓库 commits 表 NPF 首次引入 commit 验证：rmind（Mindaugas Rasiukevicius）2010-08-22T18:56:18Z“Import NPF - a packet filter. **史观**：总纲第 4 条——分离聚合是永恒规律：NPF 作为独立防火墙框架与 NetBSD 内核聚合，但与 IPF/PF 在概念上分离，体现工具独立哲学

**辨析**：NPF 与 OpenBSD PF 的关系存在叙事分歧——部分资料称 NPF 借鉴 PF 设计，部分称独立设计，需对照源码核验；NPF 的实际采用率（与 IPF/PF 共存情况）需考据。经 netbsd.duckdb netbsd-src 仓库 commits 表验证：NPF 首次导入 commit 2010-08-22T18:56:18Z 由 rmind（Mindaugas Rasiukevicius）提交，与“NPF 由 Mindaugas Rasiukevicius 设计”叙事作者归属吻合；NPF 首次导入时间（2010.8.22）早于 6.0 发布（2012.10.17）约 2 年 2 个月，反映 NPF 在 6.0 发布前已在主分支开发约 2 年，与“6.0 引入 NPF”叙事时序吻合（NPF 在 6.0 开发周期内启动，随 6.0 正式发布）；存疑已解决（NPF 作者归属与首次引入时间得到代码级确认）

## 180.1.3 与 FreeBSD 9.x/10.x 技术进展的比较

**要点**：FreeBSD 9.0（2012.1）引入 Capsicum 沙箱、softdep 改进、NFSv4；10.0（2014.1）切换至 Clang/LLVM 默认编译器、引入 bhyve 虚拟化；同期 NetBSD 6.0（2012.10）专注 SMP 与 NPF；FreeBSD 在虚拟化与编译器现代化领先，NetBSD 在跨平台与防火墙设计有特色

**史料**：FreeBSD 9.0/10.0 Release Notes；NetBSD 6.0 Release Notes；BSD 基准测试对比［考据注：2026-07-28 联网考据留痕，模板句式已按考据审慎原则精简（WO-004）；语义以正文与所引来源为准］〔L3 官方文档与公告/L5 二手研究〕

**要点**：

- NetBSD 6.0 的 LVM 支持源于 Google Summer of Code 项目：用户态基本直接导入 Linux 工具并加兼容层，使标准 Linux 卷管理命令可直接操作，而内核侧因许可证问题必须另行实现，与用户态接口完全不同；引入动机是既有 ccd、RAIDframe、vnd、VINUM 各有局限而用户长期需要逻辑卷管理，且熟悉的命令能降低 Linux 用户的迁移成本。　[存疑脚注] LVM 内核侧重写与用户态兼容层的具体边界为受访者转述 GSoC 成果，须对照 NetBSD 源码树中 dm 与 lvm2 组件核证（BSDTalk EP215，[412.54-583.56]，L2）
- 6.0 时期内核多处理能力由受资助的有偿工作推动：Andrew Doran 完成部分线程化内核与细粒度锁，使部分子系统脱离大内核锁，受访者明确承认 FreeBSD 在此领先而 NetBSD 正在追赶；Xen 的多处理器支持同样是有偿工作，发布前数月才进入代码树。此外 6.0 引入线程局部存储、可在用户空间运行多个 IP 栈，并以 64 位 time_t 提前规避 2038 年问题。（BSDTalk EP215，[1104.3-1216.26]，L1）
- NetBSD 发布历来以功能而非时间表驱动：主分支切出发布分支后开发者在树顶投入大特性，6.0 含四十五个以上新驱动与 MIPS64 支持；向后移植到稳定分支取决于用户需求与人手，受访者坦言多数用户只关心在稳定版上运行新硬件。6.0 首次以政策形式确立自动化测试：受访者为测试体系发起人，另一开发者推动新政策，自动系统每日从空白机器完成构建、安装并运行测试，配合短提交窗口使问题在引入后数小时内暴露。（BSDTalk EP215，[638.84-739.38]，L1）
- 多架构支持的实际收益超越罕见硬件本身：受访者论证为众多架构构建的纪律使代码整体更干净，仅用 i386 与 amd64 的用户同样受益；嵌入式企业选择 NetBSD 是因为对应 CPU 的编译器、总线、芯片组与驱动已现成可用，且 build.sh 单命令交叉构建可加快开发周期。Clang 与 PCC 被引入构建体系但仅覆盖其支持的架构子集，Clang 背后的商业与开源动力被预期持续推动其扩张。（BSDTalk EP215，[739.38-935.94]，L1）
