## 178.1.2 约 2 年发布周期的工程原因

  **NetBSD 3.x-5.x 版本发布时间线与分支维护期**：

  | 版本 | 官方公告发布日期 | 对应分支 | 分支末次更新时间 | 末次更新 commit | 分支维护期 |
  | --- | --- | --- | --- | --- | --- |
  | 3.0 | **2005.12.23** | `netbsd-3-0` | 2009-04-30T20:36:52Z | `99f7cbea021b` | 约 3 年 4 个月 |
  | 4.0 | **2007.12.19** | `netbsd-4-0` | 2012-11-14T20:26:54Z | `e8a6796c553c` | 约 4 年 11 个月 |
  | 5.0 | **2009.4.29** | `netbsd-5-0` | 2014-12-25T23:54:07Z | `f0717457fc3b` | 约 5 年 8 个月 |

**要点**：NetBSD 4.0（**2007.12.19**）距 3.0（**2005.12.23**）约 2 年发布周期的工程原因——细粒度锁改造工程量大、多平台测试复杂、Core Team 资源有限；2 年周期反映 NetBSD 多平台策略的代价

**史料**：NetBSD 4.0 Release Notes；Core Team 发布周期讨论邮件；NetBSD 官方发布历史页面（netbsd.org/releases/formal.html）；netbsd.duckdb netbsd-src 仓库 branches 表验证：origin/netbsd-3-0 branch commit_date = 2009-04-30T20:36:52Z（commit 99f7cbea021b，晚于 3.0 发布 2005.12.23 约 3 年 4 个月），origin/netbsd-4-0 branch commit_date = 2012-11-14T20:26:54Z（commit e8a6796c553c，晚于 4.0 发布 2007.12.19 约 4 年 11 个月），两 branch commit_date 均非发布时间，但 branch 创建时序与版本演进顺序一致；netbsd.duckdb 查询 L1.1.1 显示：netbsd-src 2005 年 commit_count = 30,344（3.0 发布年），2006 年 = 30,561，2007 年 = 28,670（4.0 发布年），3.0 至 4.0 期间（2006-2007）commit 量从 30,561 降至 28,670（降幅约 6.2%），与 “细粒度锁改造工程量大、多平台测试复杂导致发布周期延长至 2 年” 叙事在 commit 活跃度下降上得到间接印证；netbsd.duckdb 查询 L1.4.1 显示：netbsd-src 在标准 release tag 过滤条件下（tag_name LIKE ‘release/%’ OR ’%-RELEASE’ OR 'OPENBSD_%’）无匹配 tag，NetBSD 采用 CVS/HG tag 命名约定（如 `netbsd-4-0` 分支），与 FreeBSD `release/12.0.0` 命名约定不同，故 L1.4.1 查询不适用于 netbsd-src，发布间隔须以 branches 表与官方公告交叉验证 ［A］

**史观**：总纲第 6 条——技术选择的代价：多平台策略付出发布周期代价

**辨析**：先前叙事中称 ~~“3 年发布周期”~~ 系误传——3.0（**2005.12.23**）至 4.0（**2007.12.19**）实际间隔约 2 年；具体原因需考据——细粒度锁改造与多平台测试的具体影响需对照 commit 日志核实。经 netbsd.duckdb netbsd-src 仓库 branches 表验证：3.0 与 4.0 的 branch 最后更新时间（2009-04-30 与 2012-11-14）相隔约 3 年 7 个月，反映两版本分支的持续维护期重叠且 4.0 分支维护期更长，与 “4.0 引入细粒度锁改造导致发布周期延长至 2 年” 的叙事在分支维护期长度上得到间接印证；但发布日期间隔仍须以官方公告为准（3.0 为 **2005.12.23**，4.0 为 **2007.12.19**，间隔约 1 年 11 个月，与 “约 2 年” 叙事吻合）。L1.1.1 查询的 commit 量下降趋势（2006 年 30,561→2007 年 28,670）须注意 GitHub 镜像滞后风险——netbsd-src 为 GitHub 镜像，主仓 Mercurial **hg.NetBSD.org** 的实际 commit 量可能更高，降幅可能被镜像同步延迟放大；L1.4.1 查询的 “无匹配 tag” 不等于 “netbsd-src 无版本标签”，而是 tag 命名约定差异导致查询条件不匹配，须以 branches 表（`netbsd-3-0`、`netbsd-4-0` 等）替代分析

**要点**：NetBSD 4.0 SMP 与 FreeBSD 5.x（2003-2005）/6.x（2006-2008）SMP 进展的比较——FreeBSD 5.0 引入 SMPng，FreeBSD 6.0 进一步优化；NetBSD 4.0 的 SMP 进展落后 FreeBSD 约 2 年

**史料**：NetBSD 与 FreeBSD SMP 进展对比；两项目 Release Notes；freebsd.duckdb 查询 L1.1.1 显示：netbsd-src 2003 年 commit_count = 50,546，2004 年 = 37,918，2005 年 = 30,344（3.0 发布年），同期 freebsd-src 2003 年 = 15,654，2004 年 = 16,479，2005 年 = 17,689（数据来自 L1.1.2 查询），netbsd-src commit 量在 2003-2005 年间从 50,546 降至 30,344（降幅约 40%），而 freebsd-src 同期从 15,654 升至 17,689（增幅约 13%），反映两项目在 SMP 改造期的不同开发节奏——NetBSD 因细粒度锁改造投入大导致 commit 量下降，FreeBSD 因 SMPng 已在 5.0 完成而保持稳定增长；freebsd.duckdb 查询 L2.3.1.smp 显示：netbsd-src 2007 年 SMP 相关 commit = 38（4.0 发布年），而 freebsd-src 同期 SMP 相关 commit 数据须另行查询方可对比 ［A］

**史观**：总纲第 7 条——技术选择即政治选择：SMP 进展差异反映不同技术政治选择

**辨析**：比较需考虑项目目标——NetBSD 多平台，FreeBSD x86 性能；不得直接对比 “优劣”。L1.1.1/L1.1.2 查询的 commit 量对比须注意两点局限：其一，netbsd-src 与 freebsd-src 均存在版本控制迁移问题（netbsd-src 为 GitHub 镜像，freebsd-src 于 2020 年由 SVN 迁移至 Git），commit 量可能因迁移脚本差异而不可直接比较；其二，commit 量不等于技术影响力，FreeBSD SMPng 的架构性改造可能用较少 commit 完成，而 NetBSD 细粒度锁改造可能因多平台适配而用较多 commit，故 38 这个 SMP 相关 commit 数与 FreeBSD 同期数据的对比仅作为开发活跃度参考，不作为技术先进性判断依据

**要点**：

- 受访者概括 NetBSD 4.0 的内容：在常规 bug 修复之外，新特性包括 tmpfs 与自 OpenBSD 移植的 CARP；AGR 设备提供 802.3AD 以太网链路聚合（近似 Cisco EtherChannel，曾险些错过 NetBSD 3）；另有 iSCSI target、multi-boot 与 time counter 支持；从 FreeBSD 引入 NDIS、从 OpenBSD 引入 GPIO 与 OneWire 设备支持；并提供 Xen3 的 Domain Zero 支持。新硬件平台集中于嵌入式领域，如 EVBARM 诸平台、MIPS、SH3 及 NSLU2 等。同期 sendmail 与 UUCP 停止随附系统，默认编译器迁往 GCC4 后 GCC3 亦被移除。（BSDTalk EP89，[65.72-187.68]，L1）
- 受访者解释 NetBSD 的发布方法论：全部开发在 CVS trunk 进行；周期性从 trunk 分支并声明其为 major release 分支，经 pull up 机制将修复自 trunk 回灌至 release 分支，质量满意后发布；沿同一分支发生的 minor release（如刚发布的 3.1）仅拉入新设备支持与 bug 修复，绝不进行大规模重构；虚拟内存子系统之类的重大改动通常在分支后进入 trunk。选择何种修复进入发布并无硬性规则，而是方法论问题。（BSDTalk EP89，[192.56-286.42]，L1）
- 关于 4.0 的推迟与重新分支：项目原于 8 月分支、意在延续提高 major release 频率的势头（3.0 于上一年 12 月发布）；分支数周后的 beta 期间，开发者 Elad Efrat 组织 IRC hackathon 吸引用户参与集中修 bug 与关闭 problem reports，一个周末即关闭约 300 份报告，一个月后再办一场且热情不减；发布工程团队认为这些修复理应进入 4.0，但逐一回灌工作量巨大，遂决定放弃原分支、于 12 月初重新分支，宣布 8 月至 12 月之间的全部变更直接进入 4.0。当时处于 beta 阶段，期望 3 月发布，现实估计 3 月中旬。（BSDTalk EP89，[286.42-416.0]，L1）
- 受访者描述构建基础设施的运作：daily builds 全部依托成熟的交叉编译系统完成；当前为约 5 台机器的集群（另加半台兼做 pkgsrc 构建），混合运行 i386 与 AMD64，主控机分发构建任务；构建结束设 compare 阶段以去除跨架构重复的二进制（手册页等在各架构间相同，FTP 服务器只存一份）。单架构全平台完整构建约需一天，理想状态下每周产生一至两次新构建（近期因硬件故障不太顺畅）；用户可自 ftp.netbsd.org 的 daily 区下载 beta 快照参与测试。系统依赖各 port master 对各自平台的测试与验证，平台众多导致支持程度参差，被视为常态。（BSDTalk EP89，[445.32-647.74]，L1）
- 关于发布形态与支持周期：4.0 将面向全部 port 同时发布——对源码树统一打 tag 即可在所有架构间划出同一界线；发布后偶发的次要 port 问题经由 teeny release 修复；项目正走向官方的 port 分级体系，但无退役任何 port 的计划，新硬件获得更多关注而旧硬件仍由活跃开发者维护。支持策略为维护最近一个 major release：4.0 发布前同时为 2 与 3 的各子分支提供安全修复，4.0 发布后不久将退役 2 分支（如同 3.0 发布后退役 1.6），周期不设死限、通常约两年半至三年。（BSDTalk EP89，[647.74-763.1]，L1）

**史料**：

- 本期为 NetBSD 开发者、4.0 发布工程师 Jeff Rizzo 的口述访谈（bsdtalk089，2006-12-29），提供其履历一手陈述：自 NetBSD 0.9 时代（1994 年）起为其用户，当时为 Amiga 寻找系统，在不知名的 Linux port 与学校所用而令他感兴趣的 BSD 之间选择后者；安装异常顺利，内核消息滚过 Amiga 屏幕的兴奋记忆犹新；此后在 NetBSD 支持的大多数 CPU 平台上安装过，个人主力为 x86 与若干 MacPPC；过去 13 年的历份工作多以某种形式使用 NetBSD，尤其服务器与防火墙用途。（BSDTalk EP89，[766.86-848.42]，L1）

**史观**：

- 总纲5 没有必然性，只有偶然性：4.0 发布时间表被一场计划外的社群活动改变：Elad Efrat 出于集中修 bug 的意图组织的 IRC hackathon 意外地在一个周末关闭约 300 份 problem reports，其成果之大使发布工程团队放弃已确立的原分支、重新划分 4.0 的边界。发布工程的正式时间表在此被志愿者社群的自发热情临时改写，工程决策由偶然的集体热情而非预定计划塑造。（BSDTalk EP89，[317.42-397.08]，L1）

**辨析**：

- 受访者坦陈 problem report 处理机制的两极化现实：报告要么被立即处理、要么搁置数周，此为志愿者项目的本性——取决于恰好有人注意到与否；他建议提交者以礼貌的方式在邮件列表上催促以加速处理。这为理解志愿者项目中问题报告系统的实际运作（而非其名义流程）提供了当事人证词。（BSDTalk EP89，[507.44-544.92]，L1）
