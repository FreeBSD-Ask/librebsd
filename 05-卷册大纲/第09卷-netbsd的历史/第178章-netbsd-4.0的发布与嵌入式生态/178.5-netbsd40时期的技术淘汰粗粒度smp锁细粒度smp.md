# 177.5 NetBSD 4.0 时期的技术淘汰——粗粒度 SMP 锁 → 细粒度 SMP 锁、用户态线程 → 原生线程支持、约 2 年发布周期 → 后续节奏改进、GPIO 框架引入（2007-2009）

## 177.5.1 粗粒度 SMP 锁 → 细粒度 SMP 锁（2007.12.19）
  - 要点：NetBSD 3.x 及之前采用大内核锁（Big Kernel Lock, BKL）的粗粒度 SMP 实现，多核扩展性受限；NetBSD 4.0（2007.12.19）引入细粒度锁替换大内核锁，将全局锁拆分为子系统级锁与对象级锁；细粒度锁改造由 Andrew Doran（安德鲁·多兰） 等开发者推进，工程量巨大是 4.0 发布周期约 2 年（自 3.0 于 2005.12.23 发布起算）的重要原因；细粒度锁使 NetBSD 在 4 核至 16 核机器上获得显著性能提升
  - 史料：NetBSD 4.0 Release Notes；Andrew Doran 在 tech-kern 邮件列表的 SMP 锁设计帖；CVS commit log 中 SMP 锁相关 commit；netbsd.db netbsd-src 仓库 branches 表验证：origin/netbsd-4-0 branch commit_date = 2012-11-14T20:26:54Z（commit e8a6796c553c，远晚于 4.0 发布 2007.12.19 约 4 年 11 个月，属分支末次维护更新时间，非发布时间），origin/netbsd-3-0 branch commit_date = 2009-04-30T20:36:52Z（commit 99f7cbea021b，晚于 3.0 发布 2005.12.23 约 3 年 4 个月）；两 branch commit_date 印证 3.x 与 4.x 分支均持续维护至 2009/2012 年，4.x 分支维护期更长（约 5 年），与 “4.0 细粒度锁改造工程量大、维护周期长” 叙事间接吻合；netbsd.db 查询 L1.1.1 显示：netbsd-src 2007 年 commit_count = 28,670（4.0 发布年），2008 年 = 26,543，2009 年 = 26,690，2007-2009 年间 commit 量稳定在 26,000-29,000 区间，反映 4.0 发布后进入稳定维护期；netbsd.db 查询 L2.3.1.smp 显示：netbsd-src 2005 年 SMP 相关 commit = 15，2006 年 = 8，2007 年 = 38（4.0 发布年，显著峰值），2008 年 = 24，2009 年 = 24，2007 年 SMP commit 量为 2005-2009 年间最高，印证细粒度 SMP 锁改造集中在 4.0 发布年 ［A］
  - 史观：总纲第 6 条——技术选择的代价：细粒度锁付出复杂度与发布周期代价，但获得多核性能；总纲第 17 条——形式与内容：从大内核锁到细粒度锁是锁机制 “形式” 的演进
  - 辨析：4.0 细粒度锁的具体实现范围需考据——并非所有子系统完成细粒度化，部分仍保留粗粒度锁，需对照源码 diff 核验；4.0 与 5.0 在 SMP 锁改造上的分工需考据。经 netbsd.db netbsd-src 仓库 branches 表验证：origin/netbsd-4-0 与 origin/netbsd-3-0 的 commit_date 时序与版本演进顺序一致，但 commit_date 非发布时间，4.0 发布日期 2007.12.19 与 3.0 发布日期 2005.12.23 仍须以 NetBSD 官方公告为准。L1.1.1 查询的 commit 量数据存在 GitHub 镜像滞后风险——netbsd-src 为 GitHub 镜像（主仓为 Mercurial **hg.NetBSD.org**），2007-2009 年 commit 量可能不完整；L2.3.1.smp 查询基于 message_subject LIKE '%SMP%’ 匹配，38 这个数字是 SMP 相关 commit 的下限，实际涉及细粒度锁改造的 commit 可能更多（如 subject 中含 "lock" "mutex" "scheduler" 但未含 "SMP" 的 commit 未被统计）
  - 文献：NetBSD 4.0 Release Notes；Andrew Doran SMP 设计邮件；BSD 多核架构比较研究；origin/netbsd-4-0. netbsd-src 仓库 branch [DB/OL]. 2012-11-14T20:26:54Z. commit: e8a6796c553c；origin/netbsd-3-0. netbsd-src 仓库 branch [DB/OL]. 2009-04-30T20:36:52Z. commit: 99f7cbea021b；bsd_commits.db 数据分析·宏观趋势统计.md §L1.1.1（netbsd-src 2007-2009 年度 commit 量）、§L2.3.1.smp（netbsd-src SMP 相关 commit 2005-2009） ［A］
## 177.5.2 用户态线程 → 原生线程支持（2007.12）
  - 要点：NetBSD 3.x 及之前采用用户态线程（M: N 模型）实现，线程调度在用户空间，内核仅看到进程；NetBSD 4.0（2007.12）引入原生线程（1:1 模型）支持，每个用户线程对应一个内核线程；原生线程支持由 YAMAMOTO Takashi 等开发者推进；原生线程使 NetBSD 线程在多核机器上获得真正的并行能力；同期 FreeBSD 5.0（2003.1）已引入 KSE 与 1:1 线程，NetBSD 4.0 落后约 4 年
  - 史料：NetBSD 4.0 Release Notes；YAMAMOTO Takashi 在 tech-kern 邮件列表的线程设计帖；CVS commit log 中线程相关 commit ［A］
  - 史观：总纲第 6 条——技术选择的代价：原生线程付出复杂度代价，但获得多核并行能力；总纲第 1 条——偶然性改写历史：NetBSD 线程模型选择落后 FreeBSD 4 年是偶然性事件
  - 辨析：NetBSD 4.0 原生线程的具体实现需考据——是否完全替换 M: N 模型还是并存，需对照源码 diff 核验；与 FreeBSD KSE/ULE 线程的关系需考据
  - 文献：NetBSD 4.0 Release Notes；YAMAMOTO Takashi 线程设计邮件；BSD 线程模型比较研究[考据完成：2026-07-28 经穷尽联网考据，上述文献清单为已知公开来源汇总，部分原始档案未公开数字化或须付费访问，属史料缺口，须待原始档案公开后方可补充确证]

  - 要点：NetBSD 4.0（**2007.12.19**）距 3.0（**2005.12.23**）间隔约 2 年，5.0（**2009.4.29**）距 4.0 间隔约 1 年 4 个月；2 年发布周期源于细粒度锁改造工程量大、多平台测试复杂、Core Team 资源有限；4.0 至 5.0 周期相比 3.0 至 4.0 显著缩短，反映 Core Team 反思发布节奏后的改进；NetBSD 5.0 后 Core Team 继续引入特性分支与时间分支模型改进后续发布周期

  - 史观：总纲第 6 条——技术选择的代价：多平台策略付出发布周期代价；总纲第 5 条——组织结构塑造技术路径：Core Team 发布节奏决策塑造 NetBSD 技术演进路径
  - 辨析：先前叙事中称 ~~“5.0 距 4.0 间隔近 3 年”~~ 系误传——4.0（**2007.12.19**）至 5.0（**2009.4.29**）实际间隔约 1 年 4 个月；3.0 至 4.0 间隔约 2 年而非 3 年；5.0 后发布节奏改进的具体措施需对照 tech-releases 邮件列表核验。经 bsd_commits.db netbsd-src 仓库 branches 表验证：origin/netbsd-4-0 与 origin/netbsd-5-0 的 branch commit_date（2012-11-14 与 2014-12-25）时序与版本演进顺序一致，5.0 分支维护期（约 5 年 8 个月，从 **2009.4.29** 至 2014.12.25）长于 4.0 分支维护期（约 4 年 11 个月，从 **2007.12.19** 至 2012.11.14），与 “5.0 后 Core Team 引入特性分支与时间分支模型改进发布周期” 叙事在分支维护期长度上间接吻合；但发布日期间隔仍须以官方公告为准（4.0 为 **2007.12.19**，5.0 为 **2009.4.29**，间隔约 1 年 4 个月，“近 3 年” 叙事不正确）

## 177.5.4 各平台 GPIO 驱动各自实现 → 统一 GPIO 框架（2007.12）
  - 要点：NetBSD 3.x 及之前缺乏统一的 GPIO（General Purpose Input/Output）框架，各嵌入式平台 GPIO 驱动各自实现；NetBSD 4.0（2007.12）引入统一 GPIO 框架，提供 **gpio(4)** 设备接口与 **gpioctl(8)** 用户空间工具；GPIO 框架由 Marc Balmer 等开发者贡献；GPIO 框架使 NetBSD 在嵌入式设备（如 SoC 板卡）的 GPIO 控制标准化，简化嵌入式开发
  - 史料：NetBSD 4.0 Release Notes GPIO 章节；**gpio(4)** 与 **gpioctl(8)** 手册页；Marc Balmer GPIO 框架 commit log；bsd_commits.db netbsd-src 仓库 commits 表 GPIO 相关 commit 验证：christos 2007-01-06T00:58:04Z "PR/34682: Bucky Katz: Add support for the OMAP GPIO blocks."（commit faa54b03a6a3，OMAP GPIO 块支持，早于 4.0 发布 2007.12.19 约 11 个月），christos 2007-01-06T16:08:54Z "Update the gpio code to the latest. From Bucky Katz"（commit ee28c46912e3，GPIO 代码更新）；此两 commit 由 christos 提交但署名 Bucky Katz 贡献，与 “GPIO 框架由 Marc Balmer 贡献” 叙事存在作者归属差异 ［A］
  - 史观：总纲第 17 条——形式与内容：GPIO 框架作为 “形式” 统一了各平台 GPIO “内容”；总纲第 6 条——技术选择的代价：GPIO 框架付出抽象层代价，但获得嵌入式开发简化
  - 辨析：GPIO 框架的具体引入版本需考据——部分资料称 4.0，部分称 4.99.x（开发分支），需对照 Release Notes 与 commit log 核验；Marc Balmer 的具体贡献需对照 commit log 核验。经 bsd_commits.db netbsd-src 仓库 commits 表验证：2007-01-06 christos 提交的 GPIO 相关 commit（OMAP GPIO 块支持、GPIO 代码更新）早于 4.0 发布日期 2007.12.19 约 11 个月，可视为 4.0 开发周期内 GPIO 框架演进的代码级证据；但 commit 署名贡献者为 Bucky Katz 而非 Marc Balmer，“GPIO 框架由 Marc Balmer 贡献” 叙事的作者归属需对照更多 commit 与邮件列表最终核验，存疑已部分解决（GPIO 框架在 4.0 周期内引入得到代码级确认，但作者归属待最终核验）

## 177.5.5 NetBSD 4.0 引入 Iain Hibbert 的蓝牙栈（跨 BSD/UNIX/macOS 扩展）
  - 要点：NetBSD 4.0（**2007-12-19**）合入 Iain Hibbert 实现的蓝牙栈，含 **btconfig(8)** 命令与 **bluetooth(4)** 驱动框架——其核心机制是基于 Netgraph 风格的节点图（node graph）抽象，将 HCI、L2CAP、RFCOMM 等协议层作为可堆叠节点。man page 见 **man.netbsd.org/btconfig.8** 与 **man.netbsd.org/bluetooth.4**。NetBSD 蓝牙栈的合入时间（2007）晚于 Linux BlueZ（2001 年合入 2.4.6）但早于 DragonFly BSD（无蓝牙实现）。
  - 史料：NetBSD 4.0 Release Notes；**btconfig(8)** 与 **bluetooth(4)** man page；NetBSD src 仓库 **sys/netbt/** 目录源码；Hibbert, I. (2007). *NetBSD Bluetooth Stack*. tech-kern 邮件列表存档；Bray, J., & Sturman, C. F. (2001). *Bluetooth: Connect Without Cables* (2nd ed.). Prentice Hall.
  - 史观：总纲第 1 条——源头时刻：NetBSD 蓝牙栈是 Hibbert 面对嵌入式设备蓝牙需求的工程洞察；总纲第 2 条——分离与聚合：蓝牙栈在 NetBSD 4.0 中聚合入主线，是嵌入式生态需求的聚合时刻；总纲第 6 条——技术选择的代价：NetBSD 选择 Netgraph 风格节点图而非常规协议栈实现，付出抽象层复杂度代价，但获得协议层的灵活组合能力；总纲第 10 条——边缘者贡献：Hibbert 作为 NetBSD 蓝牙栈开发者，其姓名在嵌入式蓝牙叙事中常被遮蔽；总纲第 17 条——形式与内容：Netgraph 节点图作为“形式”统一了不同蓝牙协议层的“内容”；自反性声明：本释读不预设“NetBSD 中心论”——蓝牙栈在 Linux（BlueZ）、macOS（IOBluetooth）有独立演化路径，本节仅释读 NetBSD 一支。
  - 辨析：NetBSD 蓝牙栈与 FreeBSD Netgraph-based Bluetooth 在设计上类似（均采用节点图抽象）但代码独立；与 Linux BlueZ 的关键差异——BlueZ 采用传统协议栈实现，NetBSD 蓝牙栈采用 Netgraph 节点图；macOS IOBluetooth 是 Apple 私有框架，与 BSD/Linux 蓝牙栈无源码关系；OpenBSD 明确拒绝蓝牙支持（**openbsd.org/faq/faq7.html** 中的硬件策略声明）。
