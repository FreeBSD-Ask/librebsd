# 195.5.5 NetBSD 4.0 引入 Iain Hibbert 的蓝牙栈（跨 BSD/UNIX/macOS 扩展）

**要点**：NetBSD 4.0（**2007-12-19**）合入 Iain Hibbert 实现的蓝牙栈，含 **btconfig(8)** 命令与 **bluetooth(4)** 驱动框架——其核心机制是基于 Netgraph 风格的节点图（node graph）抽象，将 HCI、L2CAP、RFCOMM 等协议层作为可堆叠节点。man page 见 **man.netbsd.org/btconfig.8** 与 **man.netbsd.org/bluetooth.4**。NetBSD 蓝牙栈的合入时间（2007）晚于 Linux BlueZ（2001 年合入 2.4.6）但早于 DragonFly BSD（无蓝牙实现）。

**史料**：NetBSD 4.0 Release Notes；**btconfig(8)** 与 **bluetooth(4)** man page；NetBSD src 仓库 **sys/netbt/** 目录源码；Hibbert, I. (2007). *NetBSD Bluetooth Stack*. tech-kern 邮件列表存档；Bray, J., & Sturman, C. F. (2001). *Bluetooth: Connect Without Cables* (2nd ed.). Prentice Hall.

**史观**：源头时刻：NetBSD 蓝牙栈是 Hibbert 面对嵌入式设备蓝牙需求的工程洞察；总纲第 4 条——分离聚合是永恒规律：蓝牙栈在 NetBSD 4.0 中聚合入主线，是嵌入式生态需求的聚合时刻；技术选择的代价：NetBSD 选择 Netgraph 风格节点图而非常规协议栈实现，付出抽象层复杂度代价，但获得协议层的灵活组合能力；边缘者贡献：Hibbert 作为 NetBSD 蓝牙栈开发者，其姓名在嵌入式蓝牙叙事中常被遮蔽；总纲第 17 条——形式与内容：Netgraph 节点图作为“形式”统一了不同蓝牙协议层的“内容”；自反性声明：本释读不预设“NetBSD 中心论”——蓝牙栈在 Linux（BlueZ）、macOS（IOBluetooth）有独立演化路径，本节仅释读 NetBSD 一支。

**辨析**：NetBSD 蓝牙栈与 FreeBSD Netgraph-based Bluetooth 在设计上类似（均采用节点图抽象）但代码独立；与 Linux BlueZ 的关键差异——BlueZ 采用传统协议栈实现，NetBSD 蓝牙栈采用 Netgraph 节点图；macOS IOBluetooth 是 Apple 私有框架，与 BSD/Linux 蓝牙栈无源码关系；OpenBSD 明确拒绝蓝牙支持（**openbsd.org/faq/faq7.html** 中的硬件策略声明）。

**要点**：

- 受访者概括 NetBSD 4.0 的内容：在常规 bug 修复之外，新特性包括 tmpfs 与自 OpenBSD 移植的 CARP；AGR 设备提供 802.3AD 以太网链路聚合（近似 Cisco EtherChannel，曾险些错过 NetBSD 3）；另有 iSCSI target、multi-boot 与 time counter 支持；从 FreeBSD 引入 NDIS、从 OpenBSD 引入 GPIO 与 OneWire 设备支持；并提供 Xen3 的 Domain Zero 支持。新硬件平台集中于嵌入式领域，如 EVBARM 诸平台、MIPS、SH3 及 NSLU2 等。同期 sendmail 与 UUCP 停止随附系统，默认编译器迁往 GCC4 后 GCC3 亦被移除。（BSDTalk EP89，[65.72-187.68]，L1）
- 受访者解释 NetBSD 的发布方法论：全部开发在 CVS trunk 进行；周期性从 trunk 分支并声明其为 major release 分支，经 pull up 机制将修复自 trunk 回灌至 release 分支，质量满意后发布；沿同一分支发生的 minor release（如刚发布的 3.1）仅拉入新设备支持与 bug 修复，绝不进行大规模重构；虚拟内存子系统之类的重大改动通常在分支后进入 trunk。选择何种修复进入发布并无硬性规则，而是方法论问题。（BSDTalk EP89，[192.56-286.42]，L1）
- 关于 4.0 的推迟与重新分支：项目原于 8 月分支、意在延续提高 major release 频率的势头（3.0 于上一年 12 月发布）；分支数周后的 beta 期间，开发者 Elad Efrat 组织 IRC hackathon 吸引用户参与集中修 bug 与关闭 problem reports，一个周末即关闭约 300 份报告，一个月后再办一场且热情不减；发布工程团队认为这些修复理应进入 4.0，但逐一回灌工作量巨大，遂决定放弃原分支、于 12 月初重新分支，宣布 8 月至 12 月之间的全部变更直接进入 4.0。当时处于 beta 阶段，期望 3 月发布，现实估计 3 月中旬。（BSDTalk EP89，[286.42-416.0]，L1）
- 受访者描述构建基础设施的运作：daily builds 全部依托成熟的交叉编译系统完成；当前为约 5 台机器的集群（另加半台兼做 pkgsrc 构建），混合运行 i386 与 AMD64，主控机分发构建任务；构建结束设 compare 阶段以去除跨架构重复的二进制（手册页等在各架构间相同，FTP 服务器只存一份）。单架构全平台完整构建约需一天，理想状态下每周产生一至两次新构建（近期因硬件故障不太顺畅）；用户可自 ftp.netbsd.org 的 daily 区下载 beta 快照参与测试。系统依赖各 port master 对各自平台的测试与验证，平台众多导致支持程度参差，被视为常态。（BSDTalk EP89，[445.32-647.74]，L1）
- 关于发布形态与支持周期：4.0 将面向全部 port 同时发布——对源码树统一打 tag 即可在所有架构间划出同一界线；发布后偶发的次要 port 问题经由 teeny release 修复；项目正走向官方的 port 分级体系，但无退役任何 port 的计划，新硬件获得更多关注而旧硬件仍由活跃开发者维护。支持策略为维护最近一个 major release：4.0 发布前同时为 2 与 3 的各子分支提供安全修复，4.0 发布后不久将退役 2 分支（如同 3.0 发布后退役 1.6），周期不设死限、通常约两年半至三年。（BSDTalk EP89，[647.74-763.1]，L1）

- 本期为 NetBSD 开发者、4.0 发布工程师 Jeff Rizzo 的口述访谈（bsdtalk089，2006-12-29），提供其履历一手陈述：自 NetBSD 0.9 时代（1994 年）起为其用户，当时为 Amiga 寻找系统，在不知名的 Linux port 与学校所用而令他感兴趣的 BSD 之间选择后者；安装异常顺利，内核消息滚过 Amiga 屏幕的兴奋记忆犹新；此后在 NetBSD 支持的大多数 CPU 平台上安装过，个人主力为 x86 与若干 MacPPC；过去 13 年的历份工作多以某种形式使用 NetBSD，尤其服务器与防火墙用途。（BSDTalk EP89，[766.86-848.42]，L1）

**史观**：

- 总纲5 没有必然性，只有偶然性：4.0 发布时间表被一场计划外的社群活动改变：Elad Efrat 出于集中修 bug 的意图组织的 IRC hackathon 意外地在一个周末关闭约 300 份 problem reports，其成果之大使发布工程团队放弃已确立的原分支、重新划分 4.0 的边界。发布工程的正式时间表在此被志愿者社群的自发热情临时改写，工程决策由偶然的集体热情而非预定计划塑造。（BSDTalk EP89，[317.42-397.08]，L1）

- 受访者坦陈 problem report 处理机制的两极化现实：报告要么被立即处理、要么搁置数周，此为志愿者项目的本性——取决于恰好有人注意到与否；他建议提交者以礼貌的方式在邮件列表上催促以加速处理。这为理解志愿者项目中问题报告系统的实际运作（而非其名义流程）提供了当事人证词。（BSDTalk EP89，[507.44-544.92]，L1）
