  **netbsd.duckdb 安全修复 commit 查询示例**：

  ```sql
  -- 查询 netbsd-src 仓库 1993-2000 年间的 Security fix commit
  SELECT commit_hash, author, commit_date, message_subject
  FROM commits
  WHERE repo_name = ‘netbsd-src’
    AND commit_date BETWEEN ‘1993-01-01’ AND ‘2000-12-31’
    AND (message_subject LIKE ‘%security%’
      OR message_subject LIKE ‘%Security fix%’
      OR message_subject LIKE ‘%merge in security%’
      OR message_subject LIKE ‘%Pullup%Fixes a security bug%’)
  ORDER BY commit_date;
  ```

**要点**：NetBSD 1.x 时期是 NetBSD Security Officer 制度与 SA（Security Advisory）公告体系的奠基阶段；netbsd.duckdb netbsd-src 仓库查询显示 1993-2000 年间 0 条 CVE 编号 commit，但 50 条 Security fix commit 以“merge in security fixes”“Pullup...Fixes a security bug”等 subject 标识，反映此时期安全修复以 SA 公告驱动而非 CVE 编号驱动；28 条早期漏洞补遗覆盖 1998-2004 年，以 NetBSD-SA1998-001 至 NetBSD-SA2004-007 编号发布，公告托管于 **ftp.netbsd.org/pub/NetBSD/security/advisories/**；此时期 NetBSD 尚无 VERIEXEC、pkg_signatures、kauth、NPF、kernel ASLR 等后续安全机制，安全防线依赖传统权限模型与 SA 响应

**史观**：总纲第 8 条——社区文化即技术资产：NetBSD SA 公告体系的建立是社区安全文化的形式主义化——将“发现漏洞—发布公告—提供补丁”的流程固化为可追溯的工程制度；软件工程：SA 驱动而非 CVE 驱动的安全响应模式反映 1990 年代 BSD 项目的安全治理成熟度先于 CVE 编号体系的普及

**辨析**：netbsd.duckdb netbsd-src 仓库 0 条 CVE commit 不等于 0 个漏洞——CVE 编号体系在 1999 年才开始系统化分配，NetBSD 1.x 时期大量漏洞以 SA 公告编号记录而非 CVE 编号；50 条 Security fix commit 中部分为同源漏洞的多分支 pullup（如 `a5bfdf7812dcd2592ff263a75dba460d6a4a2d63` 与 `49e54c7f36db1ca9fb4530d2fff748be87c17755` 为同一 rdist 修复的多次提交），去重后实际独立修复约 25-30 项；【0 信任原则·GitHub 镜像滞后风险】netbsd-src 为 GitHub 镜像，1993-2000 年 commit 可能存在 CVS→Git 迁移期间的时间戳偏差，SA 公告日期须与 ftp.netbsd.org 原始公告交叉验证
