# 181.2 NetBSD 8.0 时期的技术淘汰——旧 ARM 多核→aarch64 改进、旧 SMP→改进 SMP、旧内核无 KASLR→KASLR 引入（2016-2018）

## 181.2.1 旧 ARM 多核 → 改进 ARM 多核与 aarch64 支持（2018）

**要点**：NetBSD 8.0（2018.7）引入 aarch64（ARM64）支持，由 Ryo Shimizu 等推动；开发历时 3 年（2015-2018），涉及内核 ABI、虚拟内存、中断控制器（GICv3）等；aarch64 是 NetBSD 在 ARM 服务器市场（如 Cavium ThunderX）的关键布局；旧 ARMv7 多核路径作为分离分支保留，体现“分离与聚合”

**史料**：NetBSD 8.0 Release Notes aarch64 部分；tech-port-arm 邮件列表；CVS commit log 中 aarch64 相关 commit；netbsd.duckdb netbsd-src 仓库 branches 表验证：origin/netbsd-8 branch commit_date = 2024-05-11T15:25:24Z（commit ab6a8c79a9ccf226543e67913f62460a7f63b848，远晚于 8.0 发布 2018.7 约 5 年 10 个月，属分支末次维护更新时间，非发布时间）；netbsd.duckdb netbsd-src 仓库 commits 表 aarch64 验证：joerg 2013-02-04 引入 LLVM/Clang AArch64 后端，matt 2013-10-29 添加 AARCH64 定义，ryo 2015 年提交 iMX6 ARM 相关工作（commit hash 详见 77.1.1 史料）；netbsd.duckdb 查询 L1.1.1 显示：netbsd-src 2016 年 commit_count = 16,600，2017 年 = 13,101（较 2016 年下降 21.1%），2018 年 = 10,983（8.0 发布年，较 2017 年下降 16.2%），2016-2018 年间 commit 量持续下降反映 8.0 开发周期内社区规模收缩或开发模式转型（如向 Mercurial 迁移的过渡期影响）；netbsd.duckdb 查询 L2.3.1.aarch64 显示：netbsd-src 2016 年 aarch64 相关 commit = 47，2017 年 = 13（开发低谷），2018 年 = 79（8.0 发布年峰值，较 2017 年增长 507.7%），2018 年 aarch64 commit 峰值反映 8.0 发布年 aarch64 移植的最终收尾与稳定化投入 ［A］

**史观**：总纲第 4 条（分离聚合是永恒规律）：aarch64 作为新技术与 NetBSD 内核聚合，但 ARMv7 作为分离路径延续；总纲第 5 条——偶然性：ARMv8 服务器市场的兴起是偶然事件，NetBSD 抓住机会投入 aarch64

**辨析**：NetBSD aarch64 支持与 Linux aarch64 支持的成熟度对比缺乏权威基准。经 netbsd.duckdb netbsd-src 仓库 commits 表验证：aarch64 开发起点应追溯至 2013.2.4（joerg 引入 LLVM/Clang AArch64 后端），而非原叙事所称 2015 年，实际开发周期约 5 年（2013-2018）；ryo（Ryo Shimizu）于 2015.1-2015.3 提交 iMX6 ARM 相关 commit，是 aarch64 时期活跃贡献者，但作者归属为“ryo”而非全名，须对照 NetBSD 官方贡献者列表核验；Cavium ThunderX 在 NetBSD 上的实际可用性需考据——netbsd.duckdb netbsd-src 仓库 commits 表查询未找到与 Cavium ThunderX（ARMv8 服务器 SoC）直接相关 commit，仅找到 Cavium Octeon（MIPS SoC）相关 commit，原叙事中“Cavium ThunderX 关键布局”声明暂未得到代码级确认，存疑待考据【考据完成：2026-08-02 经项目数据库（netbsd.duckdb/netbsd.duckdb netbsd-src 仓库 commits 表）精确查询核验，结果详见本子节史料/辨析字段；相关声明未获代码级确认，维持存疑，特性是否引入留待官方 Release Notes 复核】；aarch64 与 armv7 在 8.0 中的共存机制需对照源码核验；8.0 发布日期 2018.7 仍须以 NetBSD 官方公告为准。L1.1.1 与 L2.3.1.aarch64 查询的局限性（GitHub 镜像滞后风险、message_subject 匹配下限、commit 量峰值不等于技术成熟度峰值）详见 77.1.1 辨析

## 181.2.2 旧 SMP 实现 → 改进 SMP 支持（2018）

**要点**：NetBSD 8.0（2018.7）改进 SMP 实现，引入对多核扩展性与性能的优化；旧 SMP 实现存在锁竞争与缓存一致性问题，8.0 引入新的同步原语与调度优化；改进让 NetBSD 在 16 核以上机器上获得更好性能；旧 SMP 路径作为分离分支保留，体现“终结中的延续”（总纲第 4 条分离聚合的延续面）

**史料**：NetBSD 8.0 Release Notes SMP 部分；tech-kern 邮件列表讨论；CVS commit log 中 SMP 相关 commit；netbsd.duckdb 查询 L1.1.1 显示：netbsd-src 2016 年 commit_count = 16,600，2017 年 = 13,101（较 2016 年下降 21.1%），2018 年 = 10,983（8.0 发布年，较 2017 年下降 16.2%），2016-2018 年间 commit 量持续下降反映 8.0 开发周期内社区规模收缩或开发模式转型；netbsd.duckdb 查询 L2.3.1.smp 显示：netbsd-src 2016 年 SMP 相关 commit = 10，2017 年 = 5（开发低谷），2018 年 = 21（8.0 发布年峰值，较 2017 年增长 320%），2018 年 SMP commit 峰值反映 8.0 发布年 SMP 改进的集中投入，2017 年的低谷可能反映 SMP 开发在 8.0 开发周期中段进入平台期 ［A］

**史观**：专题语（不设总纲条号）：旧 SMP 实现的形式主义膨胀（锁粒度过粗）促使重构；SMP 作为信息技术的基础组件，其演进体现总纲第 4 条（分离聚合是永恒规律）的分合循环

**辨析**：8.0 SMP 改进的具体性能提升缺乏权威基准——需对照同硬件测试核验；与 FreeBSD SMP 的对比需考据；新同步原语的具体名称与设计需对照源码核验。L1.1.1 查询的 commit 量数据存在 GitHub 镜像滞后风险——netbsd-src 为 GitHub 镜像（主仓为 Mercurial **hg.NetBSD.org**），2016-2018 年 commit 量可能不完整，2016-2018 年持续下降趋势的归因需复核——NetBSD 主仓由 CVS 迁移至 Mercurial（**hg.NetBSD.org**）于 2020 年完成，晚于该时段，不能以迁移解释该下降，镜像滞后与匹配口径仍为主要局限；L2.3.1.smp 查询基于 message_subject LIKE‘%SMP%”匹配，10/5/21 这组数字是 SMP 相关 commit 的下限，实际涉及 SMP 改进的 commit 可能更多（如 subject 中含“scheduler”“lock”“mutex”“runqueue”“preemption”“work stealing”但未含“SMP”的 commit 未被统计）；2018 年 SMP commit 峰值（21）与 8.0 发布年时序吻合，但 commit 量峰值不等于技术成熟度峰值

**文献**：NetBSD 8.0 Release Notes；tech-kern 邮件列表；SMP 设计文档；netbsd.duckdb 数据分析·宏观趋势统计.md §L1.1.1（netbsd-src 2016-2018 年度 commit 量）、§L2.3.1.smp（netbsd-src SMP 相关 commit 2016-2018） ［A］

## 181.2.3 旧内核无 KASLR → KASLR 引入（2018）【~~retguard~~ 已剔除——属 OpenBSD 特性非 NetBSD】

**要点**：NetBSD 8.0（**2018.7**）引入 KASLR（Kernel Address Space Layout Randomization）内核安全特性；旧内核无 KASLR，存在固定地址空间布局的攻击面；KASLR 由 Maxime Villard 实现；此改进让 NetBSD 在内核安全上追赶 OpenBSD。~~原叙事中 “NetBSD 8.0 引入 retguard” 声明不正确~~——retguard 是 OpenBSD 独有的安全特性（由 mortimer/guenther 于 2018-06-06 在 openbsd-src 中引入），NetBSD 从未引入 retguard
