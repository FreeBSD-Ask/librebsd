**要点**：NetBSD 5.x 版本周期（2011-04-01 至 2012-10-01，系 5.0 发布后维护期）是 NetBSD 5.0 大规模架构重构后的稳定维护期——netbsd.duckdb netbsd-src 仓库查询显示此周期内 212 条 CVE commit、5 条 Security fix commit、35 条去重 CVE（全部无 CVSS v3 评分），CVE commit 量与 4.x 周期持平但 Security fix commit 量骤降（从 22 条降至 5 条），反映 NetBSD 5.x 时期安全响应从 “主动安全审计” 向 “被动 CVE 跟进” 的转型；NetBSD 5.0 引入的新 SMP 调度器、改进 VFS 层、jemalloc 内存分配器等架构变化在提升性能的同时引入新的潜在攻击面——新调度器的竞态条件、VFS 层的并发访问路径、jemalloc 的内存布局变化均可能成为漏洞载体；此时期 NetBSD 发布周期延长至约 3 年 6 个月（5.0 于 2009.4.29 发布，6.0 于 2012.10.17 发布），发布节奏放缓使漏洞修复的 pullup 工程压力增大

**史料**：netbsd.duckdb netbsd-src 仓库 commits 表（5.x 周期 212 条 CVE commit、5 条 Security fix commit、35 条去重 CVE）；NetBSD 5.0 Release Notes（2009.4.29）；早期漏洞补遗归档（原材料/研究/bsd 漏洞史/版本周期/netbsd-5.x.md） ［A］

**史观**：专题语（不设总纲条号）——软件工程：Security fix commit 量骤降反映 NetBSD 5.x 时期 “主动安全审计” 能力的衰退——社区资源紧张使开发者从 “主动寻找漏洞” 转向 “被动跟进上游 CVE”，此为开源项目资源约束下的常见困境；专题语（不设总纲条号）——社区安全文化：CVE commit 量持平但 Security fix commit 量骤降的 “剪刀差” 是社区安全文化衰退的早期信号（须先排除 CVE 分类漂移效应，见辨析）

**辨析**：Security fix commit 量骤降是否等同于 “主动安全审计衰退” 须考据——可能部分源于 CVE 编号体系普及使原本归类为 Security fix 的 commit 改为引用 CVE 编号，从而被计入 CVE commit 而非 Security fix commit；NetBSD 5.0 架构重构是否直接引入新漏洞须对照源码 diff 核验——架构变化与漏洞出现的时序关联不等于因果关系；【0 信任原则·CVSS 评分缺失】35 条去重 CVE 全部无 CVSS v3 评分系 NVD 回填滞后所致
