# 267.1 Netflix 的 FreeBSD 选型（2011-2015）

## 267.1.1 流媒体基础设施的 BSD 基础
  - 要点：Netflix 在扩展流媒体时选择 FreeBSD 构建 OCA 边缘设备，理由包括网络栈性能、ZFS 存储可靠性、`dtrace` 可观测性；Netflix 工程师在 BSDCan 等会议公开其 FreeBSD at scale 实践。Netflix 于 2011 年开始建设 Open Connect CDN，逐步从第三方 CDN（如 Akamai、Limelight）迁移至自建 OCA 边缘设备，以降低带宽成本并提升流媒体交付质量；Open Connect 的 OCA 设备部署于全球互联网交换中心（IXP）与互联网服务提供商（ISP）数据中心，通过 FreeBSD 的网络栈与 ZFS 存储组合实现高吞吐视频分发。Netflix 选择 FreeBSD 而非 Linux 的决策须置于 2011-2015 年的技术语境中理解——当时 FreeBSD 的网络栈（特别是 TSO、LRO、RSS 等卸载特性）在高吞吐场景下的表现被 Netflix 工程团队评估为优于 Linux，且 ZFS 的数据完整性保障与 `dtrace` 的生产环境可观测性是 Linux 当时难以匹配的能力组合；但这一选型决策的具体评估过程（是否进行过 Linux 与 FreeBSD 的基准测试对比）须以 Netflix 工程博客与 BSDCan 演讲存档交叉验证，不得仅凭结果推断动机。
  - **Netflix FreeBSD 选型技术理由表**：

| 技术维度 | FreeBSD 提供能力 |
| --- | --- |
| 网络栈性能 | 高吞吐低延迟 |
| ZFS 存储可靠性 | 数据完整性保障 |
| `dtrace` 可观测性 | 生产环境运行时分析 |

**要点**：

- Netflix 通过 sendfile 系统调用实现零拷贝内容分发，并进一步把 sendfile 改造成异步调用，以提升并发连接能力。（BSD Now EP159，[480.54-562.14]，L2）
- 为在 TLS 场景保留 sendfile 收益，Netflix 设计混合 TLS 方案：会话管理留在用户态（nginx 与 OpenSSL），批量加密在 sendfile 内核路径完成。（BSD Now EP159，[583.62-635.58]，L2）
- Netflix 对比 BoringSSL 与 Intel ISA-L 的 AES-GCM 实现，最终选用 ISA-L，在典型流量下较基线提升最高约 30% 吞吐。（BSD Now EP159，[646.28-712.6]，L2）
- OpenBSD 社区将系统移植到 HP Stream 7 平板（Intel Atom），绕开 Windows 10 周年更新对 32GB eMMC 设备的空间挤压。（BSD Now EP159，[779.96-1090.88]，L2）
- DragonFly BSD 开始创建仅供基础系统二进制链接的私有 LibreSSL 库，OpenSSL 仍为 dports 与第三方应用保留。（BSD Now EP159，[1113.14-1205.52]，L2）
- 内核模块自动加载的技术路线：Losh 观察到几乎所有设备驱动都在其表中携带即插即用信息（厂商 ID 等字段），先由同事 Hans Petter Selasky 以独立 ELF 节存表并生成 devfs 脚本作为原型，其方案则改为把即插即用信息与既有模块依赖信息一并以标准化形式编码进 KLD 文件，使引导器、内核与用户态工具均可读取，配合小型匹配脚本语言在总线无匹配事件时将设备与驱动配对，并以实验代码动态生成 devd.conf；最终目标是从 generic 内核大量移除驱动（树中已有名为 Minimal 的内核模块作为工作目标），时间表指向 FreeBSD 11 分支，并预期对嵌入式环境尤为有用。　[存疑脚注] 同事名转写为 Hans Peter，据 USB 栈开发背景推断应为 Hans Petter Selasky。（BSD Now EP109，[488.14-734.96]，L1）
- one-wire 温度传感器项目显示开发者以手边器物解决问题的取向：其稻草 Bale 高效住宅依靠夜间引入冷空气并日间缓释蓄冷，须以数据检验各房间冷暖与通风手段的实效，遂购入 Dallas Semiconductor 设计的单总线温度传感器——既有 eBay 整件，亦有以约十分之一价格购自中国厂商的散芯片——并复用住宅既有 RJ11 电话线布线组建 one-wire 网络，代码自行完成总线设备枚举、驱动匹配与周期测温，经 sysctl 发布数据供报表或控制环使用，并在 BSDCan 展出引发兴趣。（BSD Now EP109，[2081.48-2186.52]，L1）
- 受访者自述 2003 年其莫斯科家庭 ISP 的 Windows 服务器每日多次崩溃，遍试 Red Hat、SuSE、Gentoo、Slackware 均因文档不足以架设 PPPoE 而放弃，转而打印约 1300 至 1400 页的 FreeBSD Handbook，一夜读完约七成并称“看了文档大约十分钟就完全被说服”（481.96-486.94），48 小时内在原崩溃机器上架起稳定路由、PPPoE 服务器与 IPFW 实时流量统计；该叙述把 FreeBSD 的采纳动因归于文档完备与可复现的运维细节，而非性能对比。（BSD Now EP108，[446.4-583.58]，L1）
- 2010 年前后受访者出任莫斯科一家面向俄语世界的音乐流媒体初创 CTO，按其测算采用成品专有方案需 1000 万至 2000 万美元级前期资本开支，遂转向单一集成基础设施：每节点同时承担主数据、本地处理与对外流送，每盘独立 UFS、以内容哈希命名文件、以 Postgres 调度器统一管理哈希与冗余，经 Igor Sysoev 咨询在纯机械盘条件下实现单机 6 Gbit/s 饱和与数千并发流，18 个月内扩至约 2 PB 原始容量；Jails 的独立网络栈（当时仍属实验特性）为其内外网通信提供隔离边界。（BSD Now EP108，[1954.22-2250.28]，L1）
- 受访者称 Nginx 走向公司化后早期大客户即 Netflix，而当 Netflix 公开 OpenConnect 基础设施时，他发现“其中 90% 正是我们所做的——独立 UFS 盘、Nginx 与高速网络”（2928.86-2937.22），并将 Netflix 的采用视为其技术路线的“终极印证”（2965.14-2972.42）；此系 2015 年 9 月录制的当事人对照评价，可为 Netflix 选型 FreeBSD 的研究提供同期口述旁证，但相似度判断本身属其个人结论。（BSD Now EP108，[2913.56-2975.48]，L1）
- 内容摄取环节构成该期最生动的技术轶事：首批内容硬盘自中国运抵且全部为损坏的 ext4 盘，而当时 FreeBSD 仅原生支持 ext2，受访者启用此前 Google Summer of Code 学生开发的实验性 ext3 实现——因 ext3 可不挂日志读入 ext4——不仅恢复约 99% 数据，且较 Linux 读损坏盘即崩溃的表现更为稳健；其后从 FAT、NTFS 到 TrueCrypt 加密盘在 FreeBSD 下均可挂载读取，受访者据此强调 FreeBSD 文件系统层的互操作韧性。　[存疑脚注] 转写将 ext2/ext3/ext4 记作 Xt2/Xt3/X4，专名依通行拼写回写；受访者对 Linux 读盘崩溃行为的描述未附版本与复现细节。（BSD Now EP108，[3666.18-3804.16]，L1）
- 受访者以企业实践量化开源协作成本：定制开发本身已耗资不菲，而“以可上游的方式去做，代价至少是两到三倍”（3976.74-3985.32），但从次年升级上游版本时自有补丁仍可存活的角度看仍然值得；他批评 Yahoo、Google 等大公司把多机管理方案作为私有轮子自我保留，主张转而充实 FreeBSD 用户态工具集（如 sysrc、硬盘串号提取、fstype 识别），使“一次 FreeBSD 安装”可以横跨集群而非局限于单机。（BSD Now EP108，[3976.74-4012.2]，L1）
- DragonFly BSD 4.0 与其热修复版 4.0.1 于本播出周相继发布：新增 Haswell GPU 支持，SMP 能力提升至 256 处理器并在 PF 中改进多核扩展，同时放弃 i386 平台加入纯 64 位行列；高频系统调用 git、pid、setproctitle、clock_gettime 调用超过十次时改为内存直读以降低开销，随机数发生器引入 ChaCha 算法，并随附 GCC 4.7.4 与取自 FreeBSD 的 libfetch SSL 支持。主持人将其定位为面向集群与大规模部署、追赶 FreeBSD（后者正向 1024 处理器推进）的发行版更新。（BSD Now EP65，[3279.25-3484.30]，L2）
- Brendan Gregg 以当事人身份自述其职业轨迹：长期从事 Solaris 家族与 DTrace、ZFS 工作并著有 DTrace 专著，转入 Netflix 后面对的架构为大规模 EC2 Linux 云加 FreeBSD 物理设备组成的 OpenConnect CDN；用户点击播放后流媒体即由 FreeBSD 传输，其自述夜间超过三分之一的美国互联网流量来自这些 FreeBSD 设备，且 FreeBSD 上的 DTrace 与 pmcstat 使其性能工程方法得以延续。（BSD Now EP65，[1299.01-1391.42]，L1）
- Gregg 提出两条经验性论断：其一，人（对）基准数字没有直觉，报出“800 万 mogofoo-ops”这类数字无从判断正误，工具是否可靠亦属未知，故“基准测试几乎百分之百是错的”[1399.34-1404.74]；其二为基准悖论——评估是否切换操作系统须在多项基准上全面获胜，若每项胜负近于掷硬币，三项全胜概率仅约百分之十二，故准确的基准测试对 FreeBSD 的被选型是关键门槛。其对策为主动基准测试：在基准长时间稳态运行期间，同步以 top、pmcstat、DTrace、iostat、gstat、systat 等工具核验行为与测试意图一致，并要求每个结果附注疑似瓶颈因子。（BSD Now EP65，[1422.05-1783.95]，L1）
- 访谈以实证案例支撑论断：某专业基准公司用脚本解析 FIO 输出时丢弃 K 量级后缀并删除十进制小数点（1.6 变 16），报告偏差达三个数量级；又如测试套件 makefile 为 Linux 配置高优化等级而为其他系统配置 -O0、在 Solaris 上编 32 位而 Linux 上编 64 位，实际测得的是框架而非被测系统。Gregg 进一步指出反驳一个基准所需工程时间多于制造它、小公司缺乏反驳人力、发布坏基准无任何法律后果，互联网基准生态因而近于“狂野西部”[2138.91-2142.19]。（BSD Now EP65，[1801.00-2161.04]，L1）
- Open Connect 设备是装有大容量磁盘的 PC 架构服务器，用于缓存、存储并流式分发影片；Netflix 此前依赖 Level 3 与 Akamai 等第三方内容分发网络，此后将分发全部收回自营，以基于 FreeBSD 9 的 Open Connect 设备实现，受访时该设备已开发近两年并持续扩大部署。（BSDTalk EP226，[160.64-196.22]，L1）
- 选择 FreeBSD 的理由有三：工程师本身的偏好是约两年前启动 Open Connect 设备开发时的关键决策；良好的厂商支持是加分项；对商业友好的 BSD 许可条款更是重大优势。（BSDTalk EP226，[205.36-231.90]，L1）
- 受访时点引用 Sandvine 报告称 Netflix 占北美下行流量约 32-33%（峰值口径），第二名 YouTube 仅为其一半，且受访者称其中大部分流量此刻正由 FreeBSD 承载。　[存疑脚注] 流量份额与 FreeBSD 承载比例为受访者单方陈述，Sandvine 报告本身不含操作系统维度，须以报告原文与 Netflix 官方资料交叉验证。（BSDTalk EP226，[253.36-281.40]，L1）
- 设备具有相当的通用性：服务软件的改动几乎全部回馈社区，用市售 PC 组件即可复现同样性能；仅与云端控制面通信的部分属专有组件，负责影片放置与客户端调度统计。其架构定位是分布式源站而非代理缓存，在填充窗口推入内容、在峰值时段向外服务，操作系统与 web 服务器的性能增强均已交还社区。（BSDTalk EP226，[347.98-396.20]，L1）
- Netflix 期待 FreeBSD 10 的虚拟内存设计改进，使 VM 系统与缓存层更高效，并已着手把其中部分特性回移植到 FreeBSD 9 以提前验证；受访工程师强调公司工程师数量少、无力独自维护整个操作系统，与活跃社区共生是其使用 FreeBSD 的根基，并愿以自身实践为后来企业铺路。（BSDTalk EP226，[405.02-457.14]，L1）
- Netflix 正在把 FreeBSD 推向此前未至的工作区：目标为单机持续 40Gb 流量，且不是仅从内存缓存输出静态内容，而是从磁盘经 CPU 到网络层的全链路持续吞吐，为此对系统各子系统提出全面挑战。（BSDTalk EP226，[471.14-499.66]，L1）
- Scott Long 自述其参与 FreeBSD 约十五年，Netflix 的全部视频服务运行于 FreeBSD；据其展示的测量，当时互联网上约 34.2% 的服务流量出自 FreeBSD，但 Netflix 并不主动宣扬这一基底，演讲幻灯即以不要告诉别人我是 FreeBSD 为玩笑，是企业沉默使用 BSD 的直接口述证据。（BSDTalk EP249，[43.86-54.44、0.00-20.18、9.50-13.14]，L1）
- Long 剖析传统 Web 服务器路径的代价：磁盘数据先读入应用空间的工作线程、再写回内核网络栈，双重复制使内存带宽加倍消耗并冲刷各级 CPU 缓存。Netflix 以 NGINX 配合内核内数据路径规避：数据驻留内核、经总线直接内存访问搬运，由 sendfile 直接送入网络栈，全程不触碰 CPU 与应用空间，并进一步实现异步 sendfile 调用与可变预读、可变缓存策略，单服务器吞吐达 20 至 40 Gbps。（BSDTalk EP249，[172.34-266.38]，L1）
- 全量加密的性能冲击源自外部政治与技术环境：斯诺登事件与 NSA 监控曝光促使谷歌等企业认真对待全量 SSL 加密，Netflix 由 Silverlight 转向 HTML5 播放器后，HTML5 标准化进程禁止混合模式对象，控制通道加密即意味着数据通道也须加密；而 SSL 库位于应用空间，数据须重新读入、加密、写回，实测使 24 Gbps 的服务能力骤降至 8 Gbps，即使启用 AES-NI 硬件指令仍如此，纯软件 AES 将更糟。（BSDTalk EP249，[84.46-135.36、280.48-327.36]，L1）
- Netflix 的对策是把批量加密移入内核：用户态 SSL 库继续负责密钥交换与会话管理，经套接字选项向内核交换连接密钥，数据在 socket 层内联 AES 加密，或经 OpenCrypto 框架转交加密加速器、其他 CPU 等非对称卸载；该方案不召回存量机器加装加速卡，而以现有及未来低端硬件为目标。概念验证已服务基本 SSL 流量，数周内面向真实客户，数月后供社区评审；主要开发者为 Randall Stewart，与 John-Mark Gurney 等社区成员协作，并计划次年在 MeetBSD 与 BSDCan 发表论文、在邮件列表展开讨论。（BSDTalk EP249，[341.50-474.79]，L1）
- 答问环节补充若干技术边界：内核仅承担批量 AES，密钥交换与会话管理仍是历史攻击面向，留在用户态库照常更新，OpenSSL 侧仅需新增密码库挂钩、代码改动极小；TLS 重协商是真正的难点，团队考虑整体禁用，TLS 1.3 预期从协议层面消除该问题；Intel 即将推出芯片组内置加密加速，该架构预留驱动接入位；超线程对纯内核负载本属无用，但 AES 所用 SSE 指令易于在两个超线程核间流水化，开启后可望挽回约 20% 至 30% 的加密性能损失。（BSDTalk EP249，[487.06-524.12、524.12-573.48、586.34-663.28]，L1）

**史观**：

- 总纲9 经验优先：Netflix 把功能下沉到内核以减少数据拷贝，是工程经验驱动的性能优化。（BSD Now EP159，[624.54-635.58]，L2）
- 总纲4 分离聚合是永恒规律：混合 TLS 方案把会话管理与批量加密分离，再以内核 sendfile 聚合，呈现分离与聚合的分工。（BSD Now EP159，[583.62-618.12]，L2）
- 总纲10 动手者创造历史：在廉价设备上迁移到 OpenBSD，是对厂商更新强制与空间挤压的具体回应，由动手者完成。（BSD Now EP159，[813.22-996.28]，L2）
- 总纲4 分离聚合是永恒规律：镜像构建工具的碎片化与再聚合是基础设施层的分离聚合循环：NanoBSD 出自 Poul-Henning Kamp 之手后交由 Losh 维护，而 crochet、发行工程镜像、root-on-ZFS 方案各自将树莓派、BeagleBoard、uBoot 端口等板级知识硬编码于自身，致其无法复用且随硬件演进而失效；Losh 的更新策略并非就地修补 NanoBSD，而是先抽取通用工具层——为各 uBoot 端口提供生成镜像的脚本、以包装器统一 gpart 操作、沉淀入基系统——再令 NanoBSD 与其他方案复用，Netflix 亦以 NanoBSD 双分区镜像与自动回滚向数十万台设备每六周滚动固件；分散的工具形态并不构成线性进步，聚合出的公共层才是新一轮构造的起点。（BSD Now EP109，[2414.12-2653.10]，L1）

**辨析**：

- [存疑脚注] Netflix 最高 30% 性能提升为节目转述其博客，具体基准条件与 OCA 硬件型号须以原文为准。　[存疑脚注] 性能数字转述，须核验原文基准。（BSD Now EP159，[646.28-712.6]，L4）
- 主持人在访谈中提出的生态缺口：PC-BSD 使用 GRUB 引导，而 GRUB 无法自动加载模块依赖，只能在 grub.cfg 中预先逐一列全，且彼时缺乏可直接列出某模块依赖树的用户态工具——KLDXRef 虽可能有读取 linker.hints 的模式但状态不明；这一问答从使用者视角映照出自动加载工程尚未覆盖引导链的现实。（BSD Now EP109，[928.86-948.60]，L2）
- GEOM 在内存耗尽时的回退机制构成一个由改进放大旧缺陷的案例：既有实现以分配失败计数触发退避，将系统长期压制在每秒 10 次 IOPS；Alexander Motin 的 direct dispatch 改进使并发下发的 I/O 从个位数跃升至数千，失败分配随之放大，病态退避更易触发；Losh 的权宜修复是将病态行为上限抬至每秒 1000 次 IOPS 并改为以失败是否持续为节流条件，而根本方案是预分配 I/O 事务全栈所需内存（编译期静态数组或受限的 UMA 储备池），否则当换出页所需的内存本身无法分配时理论上可构成经典死锁——其 Netflix 服务器有 256 GB 内存故罕见触发。（BSD Now EP109，[1739.60-1993.68]，L1）
- 受访者转述油气行业用户“跑 Linux 时约百节点每周一故障，换 FreeBSD 后一年无故障”（1606.5-1626.8），并断言多数 Linux 发行版的质量平衡“过于靠近够用”（4068.02-4085.42）；两条比较均出自单一场合口述、无仓库数据或公告可独立复核，且受访者立场明显亲 FreeBSD，书稿引用时须与 Netflix 等大规模 Linux 生产环境案例相互制衡，避免以一己对比修辞直接立论。　[存疑脚注] 故障率对比系受访者转述的第三方经验，无法独立验证；对 Linux 发行版质量的评价属当事人立场性论断。（BSD Now EP108，[1606.5-1626.8]，L4）
