# 267.1 Netflix 的 FreeBSD 选型（2011-2015）

## 267.1.1 流媒体基础设施的 BSD 基础
  - 要点：Netflix 在扩展流媒体时选择 FreeBSD 构建 OCA 边缘设备，理由包括网络栈性能、ZFS 存储可靠性、`dtrace` 可观测性；Netflix 工程师在 BSDCan 等会议公开其 FreeBSD at scale 实践。Netflix 于 2011 年开始建设 Open Connect CDN，逐步从第三方 CDN（如 Akamai、Limelight）迁移至自建 OCA 边缘设备，以降低带宽成本并提升流媒体交付质量；Open Connect 的 OCA 设备部署于全球互联网交换中心（IXP）与互联网服务提供商（ISP）数据中心，通过 FreeBSD 的网络栈与 ZFS 存储组合实现高吞吐视频分发。Netflix 选择 FreeBSD 而非 Linux 的决策须置于 2011-2015 年的技术语境中理解——当时 FreeBSD 的网络栈（特别是 TSO、LRO、RSS 等卸载特性）在高吞吐场景下的表现被 Netflix 工程团队评估为优于 Linux，且 ZFS 的数据完整性保障与 `dtrace` 的生产环境可观测性是 Linux 当时难以匹配的能力组合；但这一选型决策的具体评估过程（是否进行过 Linux 与 FreeBSD 的基准测试对比）须以 Netflix 工程博客与 BSDCan 演讲存档交叉验证，不得仅凭结果推断动机。
  - **Netflix FreeBSD 选型技术理由表**：

| 技术维度 | FreeBSD 提供能力 |
| --- | --- |
| 网络栈性能 | 高吞吐低延迟 |
| ZFS 存储可靠性 | 数据完整性保障 |
| `dtrace` 可观测性 | 生产环境运行时分析 |

**要点**：

- Netflix 通过 sendfile 系统调用实现零拷贝内容分发，并进一步把 sendfile 改造成异步调用，以提升并发连接能力。（BSD Now EP159，[480.54-562.14]，L2）
- 为在 TLS 场景保留 sendfile 收益，Netflix 设计混合 TLS 方案：会话管理留在用户态（nginx 与 OpenSSL），批量加密在 sendfile 内核路径完成。（BSD Now EP159，[583.62-635.58]，L2）
- Netflix 对比 BoringSSL 与 Intel ISA-L 的 AES-GCM 实现，最终选用 ISA-L，在典型流量下较基线提升最高约 30% 吞吐。（BSD Now EP159，[646.28-712.6]，L2）
- OpenBSD 社区将系统移植到 HP Stream 7 平板（Intel Atom），绕开 Windows 10 周年更新对 32GB eMMC 设备的空间挤压。（BSD Now EP159，[779.96-1090.88]，L2）
- DragonFly BSD 开始创建仅供基础系统二进制链接的私有 LibreSSL 库，OpenSSL 仍为 dports 与第三方应用保留。（BSD Now EP159，[1113.14-1205.52]，L2）
- DragonFly BSD 4.0 与其热修复版 4.0.1 于本播出周相继发布：新增 Haswell GPU 支持，SMP 能力提升至 256 处理器并在 PF 中改进多核扩展，同时放弃 i386 平台加入纯 64 位行列；高频系统调用 git、pid、setproctitle、clock_gettime 调用超过十次时改为内存直读以降低开销，随机数发生器引入 ChaCha 算法，并随附 GCC 4.7.4 与取自 FreeBSD 的 libfetch SSL 支持。主持人将其定位为面向集群与大规模部署、追赶 FreeBSD（后者正向 1024 处理器推进）的发行版更新。（BSD Now EP65，[3279.25-3484.30]，L2）
- Brendan Gregg 以当事人身份自述其职业轨迹：长期从事 Solaris 家族与 DTrace、ZFS 工作并著有 DTrace 专著，转入 Netflix 后面对的架构为大规模 EC2 Linux 云加 FreeBSD 物理设备组成的 OpenConnect CDN；用户点击播放后流媒体即由 FreeBSD 传输，其自述夜间超过三分之一的美国互联网流量来自这些 FreeBSD 设备，且 FreeBSD 上的 DTrace 与 pmcstat 使其性能工程方法得以延续。（BSD Now EP65，[1299.01-1391.42]，L1）
- Gregg 提出两条经验性论断：其一，人（对）基准数字没有直觉，报出“800 万 mogofoo-ops”这类数字无从判断正误，工具是否可靠亦属未知，故“基准测试几乎百分之百是错的”[1399.34-1404.74]；其二为基准悖论——评估是否切换操作系统须在多项基准上全面获胜，若每项胜负近于掷硬币，三项全胜概率仅约百分之十二，故准确的基准测试对 FreeBSD 的被选型是关键门槛。其对策为主动基准测试：在基准长时间稳态运行期间，同步以 top、pmcstat、DTrace、iostat、gstat、systat 等工具核验行为与测试意图一致，并要求每个结果附注疑似瓶颈因子。（BSD Now EP65，[1422.05-1783.95]，L1）
- 访谈以实证案例支撑论断：某专业基准公司用脚本解析 FIO 输出时丢弃 K 量级后缀并删除十进制小数点（1.6 变 16），报告偏差达三个数量级；又如测试套件 makefile 为 Linux 配置高优化等级而为其他系统配置 -O0、在 Solaris 上编 32 位而 Linux 上编 64 位，实际测得的是框架而非被测系统。Gregg 进一步指出反驳一个基准所需工程时间多于制造它、小公司缺乏反驳人力、发布坏基准无任何法律后果，互联网基准生态因而近于“狂野西部”[2138.91-2142.19]。（BSD Now EP65，[1801.00-2161.04]，L1）
