# 261.1 pfSense 的 FreeBSD 根基（2004-2014）

## 261.1.1 从 m0n0wall 到 pfSense
  - 要点：pfSense 由 Chris Buechler 与 Scott Ullrich 于 2004 年 9 月自 Manuel Kasper 的 m0n0wall（FreeBSD 嵌入式防火墙）分叉而来，目标是克服 m0n0wall 作为嵌入式系统的可扩展性局限——m0n0wall 功能强大但受限于嵌入式形态，pfSense 旨在提供更完整的 FreeBSD 防火墙发行版；pfSense 沿用 FreeBSD 的 `pf`/`ipfw`、Packet Filter 与 Web 管理，并由 BSD Perimeter（后更名为 Netgate）提供商业支持，是 FreeBSD 在网络防火墙领域的主导产品。m0n0wall 项目于 2015 年 2 月 15 日由 Manuel Kasper 宣布永久终止，Manuel Kasper 在终止公告中鼓励 m0n0wall 用户迁移至 OPNsense，标志 BSD 防火墙谱系中 m0n0wall 时代的终结与 pfSense/OPNsense 双雄格局的最终形成。

- 主持人入手一台 Soekris 5501——无移动部件、以闪存盘作存储、带四个 10/100 以太口的 AMD 系小型机，常被用作防火墙；因学区已升级至可峰值千兆的 Internet 2 连接，此机无法胜任校内防火墙（254.58-284.18）；他点名 m0n0wall 及基于其派生的项目（286.62-295.82），并征询除此之外的非常规用途，自设选项包括 Asterisk 小型语音服务器、家用应答机与家用防火墙，同时认定防火墙仍是此类设备的典型应用（299.62-321.3）。（BSDTalk EP157，[254.58-321.3]，L1）
- 核心团队成员回顾 7.x 系列的市场反馈：SMP 扩展性改进兑现为大规模性能提升，用户得以在高速多核服务器上完成服务器整合，把原本需要多台机器的负载并入一机，同时降低空间与能耗开销；大量基于 6.x 的企业与设备厂商正加速向 7.x 迁移，实际升级远不如其担忧的那样痛苦；7.2 定位为 7.x 线的精炼版本。（BSDTalk EP173，[309.9-364.8]，L1）
- 对于 8.0，受访成员一致指认虚拟网络栈（VNET/vimage）为最大变更：每个 jail 获得独立网卡配置、独立路由与自己的网络栈实例，互不影响，使 web 托管与机器整合场景受益；jail 框架由此完成从纯文件系统级、到获得网络支持、再到真正网络栈支持的逻辑升级，并与整机虚拟化到轻量虚拟服务器的连续谱系相衔接，8.0 开箱即用。　[存疑脚注] 转写将 FreeBSD 7 与 FreeBSD 4 误转为 3BSD7 与 3BSD4，此处按上下文订正（BSDTalk EP173，[383.5-470.7]，L1）
- 关于 IPv6，受访者给出关键的历史定性：KAME 团队当年向多个操作系统交付 IPv6 参考实现，对 FreeBSD 而言属于外部贡献，项目此后逐步取得该代码的所有权，使其与自有网络栈收敛、消除残余的巨型锁，并确立“凡改动 IPv4 必须同步改动 IPv6 并说明”的开发准则；IPv6 多播（MLD 与选择源多播）重新实现而非沿袭 IPv4 的后补设计，服务 IPTV 类应用；部署上日本与亚洲、欧洲部分地区已可取得原生 IPv6 服务而北美多为隧道，美国国防部要求采购支持 IPv6，Apple 的 Mac OS X 亦使用 FreeBSD 派生代码完成部分设备的 IPv6 配置。　[存疑脚注] 转写将 KAME 误作 Kami、将 cvsup6 服务器名讹化为 cvsub 等表述，引用时以原始音频核对（BSDTalk EP173，[1934.8-2165.3]，L1）
- 核心团队描述与 PC-BSD 的协作关系：PC-BSD 团队连续数年参加 FreeBSD 开发者峰会并演示其新版集成 jail 的图形化创建与管理功能；团队与上游合作改进桌面硬件支持，其中长期阻碍 64 位平台 Nvidia 驱动所需的虚拟内存特性由 John Baldwin 补齐，预期 FreeBSD 8.0 与 7.3 将支持 64 位 Nvidia；PC-BSD 背后由 iXsystems 推动，核心团队正吸纳其成员深入社区、增进对发布过程的了解，并期待其最终实现与 FreeBSD 发布同步。　[存疑脚注] 转写将 PC-BSD 讹作 PCVSD、PCBSC 等，将 iXsystems 误转为 IAC systems，将 Kris Moore 仅记作 Chris，正名以通行拼法为准（BSDTalk EP173，[1311.4-1460.4]，L1）
- 关于 pfSense，核心团队将其定位为面向防火墙场景的嵌入式 FreeBSD 衍生发行版，配以 web 管理界面；该产品直接集成 8.x 的虚拟接入点支持，使单块无线网卡可承载多个 SSID 与属性各异的网络，并吸纳了在 FreeBSD 社区搁置已久的 NAT-T 补丁；其大规模部署为这些代码提供了额外的实战检验，反馈回流使代码回归 base 树时更成熟，pfSense 团队亦因此受邀参加开发者峰会，带来与既有 PR 渠道不同的用户需求清单。（BSDTalk EP173，[1460.4-1553.9]，L1）
- Buechler 自述 1.x 到 2.x 的演进规模：从 1.0 到 2.0 系统几乎每个部分都被改动，几乎每项功能都有显著增强，2.0 到 2.1 的最大工程量在 IPv6 支持；升级路径上，任何旧版本（含 2005 年前后的 0.7 alpha）都可直升最新稳定版 2.1.3，配置文件按起点版本自动逐级执行转换步骤，无需人工干预格式变迁。（BSDTalk EP242，[147.05-283.24]，L1）
- FreeBSD 基底策略的波折：2.1 系列因 FreeBSD 9.0 对其使用场景问题过多、来不及在合理时间内修复而滞留 8.3，且其 8.3 并非原版——backport 了 10 中的 Intel 千兆与万兆网卡驱动等多个驱动；开发中的 2.2 转向 10-STABLE，贴近上游以便更快吸收驱动与性能改进，并将补丁回馈给 FreeBSD 使所有 FreeBSD 用户受益。（BSDTalk EP242，[293.20-422.64]，L1）
- Heartbleed 的版本差异：运行 2.1 或 2.1.1 的系统因 Web 界面与 OpenVPN 使用的 OpenSSL 版本而受影响，Web 界面可被未认证攻击者窃取会话 cookie；OpenVPN 默认配置因启用 TLS 认证、攻击者须先持有 TLS 密钥方可利用而得到一定缓解；2.0 与 1.x 系列使用的 OpenSSL 版本较老反而不受 Heartbleed 影响，但已积压约两百个其他漏洞——他对此的通俗口径是“有九十九个问题，但 Heartbleed 不在其中”。（BSDTalk EP242，[439.88-530.54]，L1）
- 升级风险的实质归因：升级后用户报告的问题多数并非升级本身所致，而是长期数年不重启的机器在重启时暴露出硬盘消失、无法通过自检等硬件老化故障；真正的软件不兼容仅是约万分之一的特殊硬件组合，并可通过选用官方或合作方预先测试过的硬件（如 Netgate 机型）规避。（BSDTalk EP242，[560.34-646.70]，L1）
- 许可证与商标的再调整：pfSense 从 BSD 二条款许可证改为类似 OpenSSL 的新许可证，对普通用户无实质影响，主要约束的是不向项目回馈任何东西的商业产品构建者；同时项目开始清理并强化商标执行，由此在社区引发“终将闭源”的传言，Buechler 以当事人身份否认，称外界对公司的想象连其合伙人也未曾听闻。（BSDTalk EP242，[689.60-925.12]，L1）
- 商业模式的自我定位是在自由软件之上附加价值：软件全部免费开放，不存在付费专业版；收入来自支持服务、直销硬件、周边商品以及约半年前推出的 Gold 订阅，后者包含加密配置云备份 AutoConfigBackup、最新版书籍的访问权与每月一次、由订阅者投票选题的线上讲解会；他明确表示不打算阉割免费版或扣留关键功能。（BSDTalk EP242，[727.62-889.38]，L1）
- 受访者 Ken Worcester（缅因州 Glenburn 学区技术总监）自述约 2008 年 PFsense 1.2 版本时期即开始使用，先在家庭环境长期运行，2012 年前后起在学区生产环境部署约三年，用以替换原有商业网关与路由产品；选型动因是软件免费且功能足以胜任校园网络。（BSDTalk EP254，[156.88-191.48]，L1）
- FreeNAS 的使用形态随技术环境而迁移：学区在“前云计算时代”自建 FreeNAS 文件服务器，学校转为 Google Apps for Education 后存储需求转向 Google Drive，FreeNAS 转而承担虚拟化服务器的 iSCSI 存储与服务器本地加异地双重备份，体现小型机构存储架构从本地文件服务向云混合形态的过渡。（BSDTalk EP254，[195.54-231.46]，L1）
- 作为学校唯一的 IT 人员，受访者主动购买 PFsense Gold 订阅（含在线备份与官方手册）与 PFsense University 远程培训；会议现场另有至少两所学校在商业生产环境运行 PFsense、一所计划当年夏季上线。这一证据表明 BSD 衍生发行版在美国地方教育市场的实际渗透依赖“开源软件加付费商业支持”的混合模式，对单人 IT 部门尤具吸引力。（BSDTalk EP254，[343.46-381.54]，L1）
- 受访者因早年接触 Solaris 而了解 ZFS，将 FreeNAS 对 ZFS 的支持列为选型关键，并在面向同行的宣讲中论证 ZFS 相对传统硬件 RAID 的数据可靠性优势；其 FreeNAS 跨版本升级曾数次出问题但从未导致数据丢失、文件系统均可救回。（BSDTalk EP254，[415.60-473.64]，L1）
- pfSense 的定位与起源：全功能防火墙发行版，面向中大型企业，具备 m0n0wall 所缺的负载均衡、监控等功能——功能缺口正是当初 fork m0n0wall 代码的初始动因；据当事人所知是继 m0n0wall 之后第二个以 PHP 实现的 FreeBSD 系完整防火墙发行版；当事人认为足以替代多数市售商业防火墙，大量 ISP 在用，其本人已部署约 25 处，并有巴西一家医院在 155Mb 管道上跑到约七至七成五利用率、正准备以 CARP 增设负载均衡的实例。（BSDTalk EP39，[88.12-247.36]，L1）
- 名称渊源与技术取舍：pfSense 得名于所用的 OpenBSD 包过滤器 PF，同时采用 OpenBSD 的 CARP 与 pfsync，并计划很快集成 OpenBGPD 与 OpenOSPFD；但基底仍是 FreeBSD——当事人十年深度使用 FreeBSD 形成的熟练度是主要因素，技术上并非不能移植到 OpenBSD，只是部分组件依赖 FreeBSD 专属守护进程、移植工作量可观；团队正在等待 FreeBSD 6.1：多数所需特性 6.0 已备，唯无线支持欠佳，无线开发者 Sam 的系列提交令 6.1 的无线明显改善。（BSDTalk EP39，[125.12-202.68]，L1）
- 两种安装模式与 BSD installer 的设计哲学：完整安装走 BSD installer，嵌入式版面向 CompactFlash——用 DD 或 Windows 的 physdiskwrite 把镜像写入介质、重启即得完整 pfSense，嵌入式安装方式承自 m0n0wall；BSD installer 虽同用 curses 文本框架，却摒弃传统 FreeBSD 安装器令人晕头转向的无限循环菜单，改为顺序步骤、失败即回退上一步，九成情况下全选默认即可安装重启后直接可用。（BSDTalk EP39，[253.36-378.04]，L1）
- BSD installer 的通用化：它完全可用于一般 BSD 发行版，已有多人投入移植——当事人早期做过向 FreeBSD 的首次移植，近期又把 Lua 版 BSD installer 移植到 FreeBSD，并曾列为 Summer of Code 项目；团队拟在 BSDCan 的开发者峰会上推动 FreeBSD 更广泛地采用 BSD installer。（BSDTalk EP39，[347.32-378.04]，L1）
- VPN 互操作与包安装机制：据用户反馈 pfSense 的 IPsec 部分与 Cisco、Nortel 设备互操作良好，与 m0n0wall 天然互通（同用 racoon），OpenBSD 一侧的用户经 isakmpd 亦报告良好，OpenVPN 作为上升期的 SSL VPN 方案同样内置，而旧式 PPTP 虽被当事人视为希望消失的遗留协议、却因用户反对而保留；包安装器则叠在 FreeBSD packages 之上、以若干 XML 文件包装，可将 XML 在运行中动态变换为 PHP GUI，GUI 呈现乃至包数据保存全部自动完成，包作者几乎无须编写 PHP，只须挂接钩子、从配置文件取数据并生成配置文件，用户全程无须接触命令行。（BSDTalk EP39，[378.04-486.32]，L1）
