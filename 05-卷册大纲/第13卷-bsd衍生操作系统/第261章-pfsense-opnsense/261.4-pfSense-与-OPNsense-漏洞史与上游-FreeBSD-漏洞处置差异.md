# 261.4 pfSense 与 OPNsense 漏洞史与上游 FreeBSD 漏洞处置差异

## 261.4.1 pfsense-src 仓库的 CVE 继承与 pfSense 低频上游同步策略
  - 要点：freebsd.duckdb 查询显示 pfsense-src 仓库共 929 条 CVE 相关 commit、567 个去重 CVE，merge commit 比例在 2016 年为 2.3%（661/28,813）、2017 年 2.4%（629/26,654）、2022 年 1.3%（133/10,179），长期维持在 1-3% 水平，显著低于 hardenedbsd-src 同期 24.3% 的 merge 比例；此差异反映 pfSense 的上游同步策略——pfSense 以 Netgate 商业发布周期为导向选择性合并 FreeBSD 安全修复，而非像 HardenedBSD 那样频繁全量同步上游；pfsense-src 的 567 个去重 CVE 中绝大多数为继承自 FreeBSD 上游的修复 commit，pfSense 本地特有的安全 commit 须通过 parent_hashes 交叉验证识别
  - **pfsense-src 与 hardenedbsd-src 上游同步策略对照表**：

| 维度 | pfsense-src | hardenedbsd-src |
| --- | --- | --- |
| CVE 相关 commit | 929 条 | 1670 条 |
| 去重 CVE | 567 个 | 627 个 |
| 2016 年 merge 比例 | 2.3%（661/28,813） | 24.3%（10,726/44,207） |
| 2017 年 merge 比例 | 2.4%（629/26,654） | 23.6%（9,667/40,943） |
| 2022 年 merge 比例 | 1.3%（133/10,179） | —（缺数原因：hardenedbsd-src 2022 年度 merge 比例未在本次抽取范围内统计，非为零值） |
| 上游同步策略 | 选择性合并，以商业发布周期为导向 | 频繁全量同步上游 hardened 分支 |

- 史料：**bsd-derivatives.duckdb**（pfsense-src 切片）查询 CVE 相关 commit（929 条，567 个去重 CVE，抽取日期 2026-07-23；2026-09-12 整改：旧合并库名 bsd_commits.duckdb 改指具体项目库，查询编号保留；原引 `原材料/研究/bsd漏洞史/数据库提取/pfsense-src-cve-commits.md` 断链作废留痕——该提取文件经全库检索未落盘）；**bsd-derivatives.duckdb** 查询 L7.1.1.pfsense-src（merge commit 比例时间序列）；Netgate 安全公告档案〔L1 代码/构建产物/L3 官方文档与公告〕
- 史观：总纲第 13 条——法律与道德是利益分配：Netgate 作为商业防火墙厂商以发布周期为导向选择性同步上游安全修复——商业发布节奏与社区同步节奏之间的取舍即安全责任利益的分配（原挂「总纲第 9 条——企业研究投入的双重性」，基线第 9 条为“经验优先”，按权威表改挂——2026-09-12 整改）
- 辨析：pfsense-src 的 567 个去重 CVE 须区分 “继承自 FreeBSD 上游的修复” 与 “pfSense 本地特有 commit”——fork 仓库的 commit 历史包含上游继承部分，识别本地特有 commit 须通过 merge commit 与 parent_hashes 交叉验证，不可仅凭时间戳判定；merge commit 比例低不必然意味着安全修复滞后，须与 Netgate 官方安全公告、pfSense 发布记录交叉验证——Netgate 可能通过独立分支维护安全补丁而非直接 merge 上游 commit；pfsense-src commit 量从 2016 年 28,813 降至 2022 年 10,179 的下降趋势须与 Netgate 商业战略调整、pfSense Plus 商业版推出等事件交叉验证

## 261.4.2 CVE-2019-11816 OPNsense 权限提升漏洞与 Web 界面安全
  - 要点：2019 年 5 月 19 日，opnsense-core 仓库记录了 CVE-2019-11816 的修复 commit `03c75f71be88d4d2d930c217377b5ff23f0ecae7`（author Ad Schellevis，committer Franco Fichtner），subject 为 “system: address CVE-2019-11816 privlege escalation bugs”，报告者为 Arnaud Cordier；此漏洞为 OPNsense Web 界面的权限提升，攻击者可利用 Web 管理界面的输入验证缺陷获取更高权限；freebsd.duckdb 查询显示 opnsense-core 仓库共 8 条 CVE 相关 commit、4 个去重 CVE，数量远低于 pfsense-src（929 条），反映 OPNsense core 仓库仅承载 OPNsense 自身应用层代码，底层 FreeBSD 基底漏洞由 FreeBSD 上游跟踪

**要点**：

- Buechler 自述 1.x 到 2.x 的演进规模：从 1.0 到 2.0 系统几乎每个部分都被改动，几乎每项功能都有显著增强，2.0 到 2.1 的最大工程量在 IPv6 支持；升级路径上，任何旧版本（含 2005 年前后的 0.7 alpha）都可直升最新稳定版 2.1.3，配置文件按起点版本自动逐级执行转换步骤，无需人工干预格式变迁。（BSDTalk EP242，[147.05-283.24]，L1）
- FreeBSD 基底策略的波折：2.1 系列因 FreeBSD 9.0 对其使用场景问题过多、来不及在合理时间内修复而滞留 8.3，且其 8.3 并非原版——backport 了 10 中的 Intel 千兆与万兆网卡驱动等多个驱动；开发中的 2.2 转向 10-STABLE，贴近上游以便更快吸收驱动与性能改进，并将补丁回馈给 FreeBSD 使所有 FreeBSD 用户受益。（BSDTalk EP242，[293.20-422.64]，L1）
- Heartbleed 的版本差异：运行 2.1 或 2.1.1 的系统因 Web 界面与 OpenVPN 使用的 OpenSSL 版本而受影响，Web 界面可被未认证攻击者窃取会话 cookie；OpenVPN 默认配置因启用 TLS 认证、攻击者须先持有 TLS 密钥方可利用而得到一定缓解；2.0 与 1.x 系列使用的 OpenSSL 版本较老反而不受 Heartbleed 影响，但已积压约两百个其他漏洞——他对此的通俗口径是“有九十九个问题，但 Heartbleed 不在其中”。（BSDTalk EP242，[439.88-530.54]，L1）
- 升级风险的实质归因：升级后用户报告的问题多数并非升级本身所致，而是长期数年不重启的机器在重启时暴露出硬盘消失、无法通过自检等硬件老化故障；真正的软件不兼容仅是约万分之一的特殊硬件组合，并可通过选用官方或合作方预先测试过的硬件（如 Netgate 机型）规避。（BSDTalk EP242，[560.34-646.70]，L1）
- 许可证与商标的再调整：pfSense 从 BSD 二条款许可证改为类似 OpenSSL 的新许可证，对普通用户无实质影响，主要约束的是不向项目回馈任何东西的商业产品构建者；同时项目开始清理并强化商标执行，由此在社区引发“终将闭源”的传言，Buechler 以当事人身份否认，称外界对公司的想象连其合伙人也未曾听闻。（BSDTalk EP242，[689.60-925.12]，L1）
- 商业模式的自我定位是在自由软件之上附加价值：软件全部免费开放，不存在付费专业版；收入来自支持服务、直销硬件、周边商品以及约半年前推出的 Gold 订阅，后者包含加密配置云备份 AutoConfigBackup、最新版书籍的访问权与每月一次、由订阅者投票选题的线上讲解会；他明确表示不打算阉割免费版或扣留关键功能。（BSDTalk EP242，[727.62-889.38]，L1）

**史料**：

- 本期为 pfSense 项目核心开发者、商业合伙人 Chris Buechler 在 BSDCan 2014 现场的当事人口述，可作一手史料的内容包括：1.x 到 2.x 各版本功能演进与 IPv6 工程量、跨版本配置自动升级机制、8.3 基底与驱动 backport 清单、Heartbleed 影响版本与缓解措施、许可证变更动机、Gold 订阅与 AutoConfigBackup 服务的推出时间。（BSDTalk EP242，[56.14-991.28]，L1）

**辨析**：

- 社区以 Vyatta 限制 ARP 表条目数等厂商先例类推 pfSense 将走向功能阉割与闭源，这一担忧的依据是对其他项目轨迹的观察而非本项目的事实；Buechler 的否认属当事人立场陈述，不足以独立定谳——许可证收紧与商标执行同商业利益的张力，须与次年 pfSense 生态的分叉动向及后续许可证实践相互印证后方可评判。　[考据脚注] 闭源化担忧为社区推断、当事人否认，两者均为立场表达；pfSense 生态后续分叉须另行考据（BSDTalk EP242，[938.90-978.70]，L2）
