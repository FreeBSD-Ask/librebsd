# 8.2.7 许可证：crate 导入的 SPDX 标注、双许可与非 GPL 工具链之争

- 【Linux社区】Miguel Ojeda 回应 Linus Torvalds 关于 Rust alloc crate 导入时许可证标注的意见。Linus 在审阅上游 alloc crate 导入补丁时要求明确说明许可证状态，而非依赖外部链接让阅读者自行查找。Miguel 承认应在拆分补丁时就标注许可证，因当前版本已无 SPDX 标识符，并承诺在后续补丁的 README 文件中添加明确说明。该条目记录了 Rust 内核子系统引入上游 crate 时对许可证声明规范的早期讨论，涉及许可证状态透明化的治理要求。 `<!-- ROW_MINE: rust-for-linux.messages.9267987 -->`
- 【Linux社区】自一九九一年参与 Linux 开发的 Dr. Greg 在社群影响力讨论中表达深层忧虑。他提到一九九五年在 Stallman 赞助的 MIT 自由软件会议上首次与 Linus Torvalds 见面，并回忆当时因 Linux 医疗流程优化而让北达科他癌症患者获得更多家庭时间。他批评当前内核开发流程中技术贡献被忽视，其耗时两年的四项安全建模补丁系列未获任何代码审阅。该条目涉及 Linux 内核治理模式的演变与早期自由软件社群记忆。 `<!-- ROW_MINE: rust-for-linux.messages.9270903 -->`
- 【Linux社区】Sami Tolvanen 回应 Greg Kroah-Hartman 关于 gendwarfksyms 工具许可证标记的质疑。Greg 追问是否真的意指 GPL-2.0-or-later，并指出 Google LLC 版权标记的许可类型存在问题。Sami 承认许可证是从系列中包含的 genksyms 代码继承而来，表示将与公司内部法务团队商议并在 v3 版本中调整其他部分的标记。该条目记录了 Linux 内核引入 Google 版权代码时对 GPL-2.0-or-later 许可适用性的审慎讨论。 `<!-- ROW_MINE: rust-for-linux.messages.9278159 -->`
- 【Linux社区】本邮件是对同线程中一条许可证论证的反驳。被引段落先援引 GPL 条款，要求任何分发或发布的衍生作品必须整体按该许可条款免费授予第三方，随后提出论断：使用非 GPL 工具会带来开发并分发 GPL 兼容但带专有成分的内核版本这一后果。作者以反问切入，认为该论证成立的前提是内核被牢牢锁定在完全没有非 GPL 等价物、并且某种程度受保护从而不会获得等价物的工具上，随后列举了可能实现这一锁定方式的具体手段，包括依赖工具未文档化且快速变化的特性、对接口主张版权、软件专利，并质疑描述这类安排所需的观念扭曲程度，认为把它称为自由并不合适，但同时说明幸运的是内核目前远未接近这种处境。作者最后明确表态自己不喜欢 Rust 这门语言、也怀疑它在内核中的价值，但要求不要把某编译器因为采用 GPL 而更好这类主张混入这场讨论，理由是不论 Rust 与否，内核显然并未在所有相关架构上被锁定于某一编译器。 `<!-- ROW_MINE: rust-for-linux.messages.9298170 -->`
- 【Linux社区】本邮件是一段关于补丁文件许可标识如何选择的简短协商，起因是某宏工具补丁涉及的代码来自上游项目、原作者持有版权。Greg 在来信中解释，作者作为版权持有人完全可以自行把代码用于其他用途或改以其他许可发布，并不需要双许可，前提是不带入他人以其他许可所做的改动；他提醒混用许可几乎没有必要，而长期维护多许可文件会带来显著负担。Miguel 在回复中表示赞同，并补充说明部分开发者确实有自身理由，例如希望各处使用同一标识，使读者在看到代码时能意识到它在别处是以更宽松的许可发布的，而这种双许可做法在 Rust 社区的项目中颇为常见。经过这一往返，作者决定遵从建议把该文件的许可统一替换为 GPL-2.0，理由是相关同事也认可这一选择。这段往来记录了内核 Rust 代码在继承上游宽松许可代码时的实际取舍，以及最终统一为 GPL 的结果。 `<!-- ROW_MINE: rust-for-linux.messages.9301763 -->`
- 【Linux社区】Greg KH 对 Sami Tolvanen 提交 gendwarfksyms 代码时使用的许可证标识提出质疑。Sami 在新文件头中标注 SPDX-License-Identifier: GPL-2.0-or-later，Greg 追问他是否真的打算在该系列所有文件中都使用 or later 标记。Greg 特别指出 Google LLC 作为版权持有方，对某些许可证标记的覆盖范围存在特定限制，暗示 or later 版本可能不适用于所有 Google 贡献代码的许可证策略。此讨论触及 GPL 许可证版本选择中 GPL-2.0-only 与 GPL-2.0-or-later 的治理分歧，以及大型企业对许可证标识选择的谨慎态度。 `<!-- ROW_MINE: rust-for-linux.messages.9304786 -->`
- 【Linux社区】Greg KH 在审阅 Danilo Krummrich 提交的 devres 抽象补丁时，注意到所有新 Rust 文件缺少版权声明。Greg 表示自己支持不加版权声明的做法，但指出与他共事的公司法务人员对没有版权行的文件持强烈反对态度，建议 Danilo 去确认公司要求，否则未来可能面临严厉谈话。这反映了 Rust for Linux 项目中关于是否需要版权声明的 GPL 实践争议，涉及版权归属与公司法律要求之间的张力，也体现了开源项目中个人偏好与企业法务需求的平衡问题。 `<!-- ROW_MINE: rust-for-linux.messages.9309410 -->`
- 【Linux社区】Mariusz Ceier 质疑非 GPL 工具能否促成 GPL 兼容但专有的内核版本发布。Al Viro 反驳称，除非内核被锁定在只能使用无 GPL 替代品的工具上，否则非 GPL 工具不构成威胁，并批评 gcc 更好因为 GPL 的论调无关紧要，因为我们显然并未在所有架构上锁定于 gcc。Mariusz 表示他更担忧功能完备的 Rust 编译器在封闭环境中开发，可能偏离 GPL 精神。讨论触及 GPL 许可证对编译工具链的约束力，以及 Rust 编译器开源状态对内核许可证合规性的潜在影响。 `<!-- ROW_MINE: rust-for-linux.messages.9309804 -->`
- 【Linux社区】Greg KH 警告 Miguel Ojeda 在 Rust paste proc macro 中使用双重许可证需谨慎，尤其不要在内核树中混用非 GPL 许可证。他指出 GPL-2.0 以外的许可证极易引发复杂问题，甚至需要律师签核。Miguel 解释这是 Rust 项目的通用做法，也用于 alloc 标准库的 vendor 引入，因为 proc macro 在用户空间也有用途，贡献者 Gary 可能想将其发布到 crates.io。Greg 认为版权所有者可自行选择许可证，无需双重许可，混合许可证是长期维护的沉重负担。 `<!-- ROW_MINE: rust-for-linux.messages.9309946 -->`
