- 【Linux社区】Jeremy Allison：以“好警察/坏警察”分工解释 Bradley 为何名声不佳，并指出联盟存在本身即是对现状的抗议——**“有些开发者觉得有必要加入一个联盟来执行他们的版权权利，这一事实本身表明：他们认为围绕保护 Linux 的现有结构做得不够好。你可能该想想为什么会这样”**；**“为什么 Bradley 得到这么差的名声？就我个人而言、在与他共事足够久之后，我认为是因为当 Bradley 和 Conservancy 不得不介入某个局面时，那局面已经超出了社区参与与自治的正常方法”**；其比喻是 **“我对 Bradley 的看法是，他类似于《低俗小说》里的 Winston Wolf。你不到需要他的时候不会叫他，但当你‘在 818 区没有朋友、而有人需要从你的沙发缝里捡起那些碎成渣的违反 GPL 的代码’时，他就是那个你该记住号码的人 :-)”**；**“我们作为开发者通常能扮演好警察，去请求其他开发者做他们本来就想做的事。当他们因某种原因被阻止那样做时，你就确实需要一个坏警察去向控制那些开发者行动的人论证：合作从长远看对所有人都有好处”**；**“没有愿意做那件吃力不讨好的事的人——而它确实是吃力不讨好的，正如这个邮件列表线程如此贴切地证明了——所有好警察能做的就只剩下问你在决定是否做正确的事时需不需要再来点咖啡和甜甜圈。有些人永远不会靠自己走到那一步（参见我先前关于 Apple、EMC、Isilon 和 NetApp 的评论）”** `<!-- ROW_MINE: ksummit-discuss.messages.347206 -->`

- 【Linux社区】Bradley M. - 【Linux社区】David Woodhouse：以“无诉讼选项即无谈判地位”立论，并指出承诺永不起诉等于实质改为 BSD——**“正如我之前说的，它们必须是一个选项。因为否则你基本上就完全没有谈判地位了。GPL 提供了一个法律框架，据此一方被要求做某些事。你甚至无法向违规者指出这一事实，而不带某种隐含暗示：他们可能会被要求履行其法律义务”**；**“如果只需要‘这对你有好处、别人都在这么做’，那我们其实根本不需要 GPL 许可证；一个 BSD 许可证就够了。而如果我们往内核的 COPYING 文件里加一条，说‘法律上你必须发布源码……但我们保证如果你不发布我们永不起诉’，那基本上就把它变成了 BSD 许可证（就多数用途而言）”**；**“法律惩罚是最后最差的选项。绝对如此。但它们必须是一个选项”** `<!-- ROW_MINE: ksummit-discuss.messages.347209 -->`
- 【Linux社区】Greg KH：承认措辞不当并以四个具体案例论证企业贡献的不可替代性——**“好吧，是的，那措辞有点糟，但我们是开发者不是律师，显然没人在校对我们的邮件 :)”**；**“我们让 Linux 成为一个非常友好的合作场所，这一点帮助了企业来帮我们。几乎所有人为 Linux 做贡献都是出于自私的方式，正如我一直说的，也正如 Linus 刚才又说的”**；其四例为 **“巨大的 SMP 支持。是的，Alan 让 Linux 的基本 SMP 支持跑了起来，但为了扩展到大得多的规模我们不得不做不同的事。由于 SMP 硬件稀缺，需要拥有那种硬件的公司在内核里做工作让事情运转得更好。正因为如此我们得到了 RCU——没有它我们绝不可能像现在这样运作得好。看看 BSD 们作为对照，它们没有 RCU 的访问权，因此无法扩展”**；**“新硬件支持。没有规格访问权或测试硬件，让内核跑起来要很长时间。USB 2 和 USB 3 支持是由那些早早拿到规格、想卖硬件的公司赞助的。Linux 因此更好，因为我们先拿到了它。同样，BSD 们现在才拿到 USB 3 支持的基础，因为它不得不由人们用自己的时间来做”**；**“LSM 支持。我当时‘白天的工作’是为 Linux 做安全方面的事，当 LSM 这个话题在内核峰会上被提出时，我看到一个办法能让我的雇主‘赞助’那项工作。没有那个，我肯定不会去做它，因为说真的，除非非做不可，谁想碰那类东西？”**；**“‘企业级’特性。IBM 往 Linux 投了大量资金推进许多我们没有、但当时被认为其他操作系统有的功能。这些是我们自己绝不会做的事，因为我们不会在乎，也永远不可能接触到那么‘大’的硬件”**；其结论是 **“所以我强烈相信，没有公司对 Linux 贡献的帮助，我们就不会处在今天的位置。走到这里靠的是所有人，我们无法独自完成。所以让我们永远不要试图把自己与我们视为‘敌人’的人割裂开，而应把他们仅仅看作‘哦，他们还没完全明白’，并努力教育他们、把他们带进我们的社区”**；脚注补充 **“（Solaris 多年前发布代码时，我翻看它是如何解决我们基于‘Solaris 有所以我们也得有’而实现的那些问题的。结果发现 Solaris 其实从未真正实现很多他们漂亮营销手册里谈的东西……所以某种意义上，Solaris 的营销部门是 Linux 在那些市场如此成功的一个驱动力。）”**、**“（再看 Intel 作为这有多有效的例子。他们过去是滥用 GPL 的恶劣范例。现在再看微软对 Linux 的支持，也是我们友善待人所获得的回报。）”** `<!-- ROW_MINE: ksummit-discuss.messages.347210 -->`
- 【Linux社区】Wolfram Sang：以“竞争对手不愿出示代码”的情形反问“永不起诉”路线的自洽性——**“这里又是关于不合规后果的核心问题：如果竞争对手不想出示代码呢？你当时能向那家公司宣传一种‘不起诉’的做法吗？”** `<!-- ROW_MINE: ksummit-discuss.messages.347211 -->`
- 【Linux社区】Daniel Vetter：以一线开发体验说明 IOMMU fault 风暴是启用 IOMMU 的实际障碍——**“缺少这个机制对开发来说是大痛点，至少就我在 gpu 驱动上折腾的经验而言，iommu fault 风暴非常频繁地发生。而且负载常常重到即使重新加载驱动（那本应能恢复）也做不到。这在实践中意味着我的开发机都没有启用 iommu，因为那太常带来太多痛苦了。这意味着回归常常溜进 -rc 甚至正式发布的内核，又强化了发行版干脆默认不启用 iommu 的决定。所以我认为有一些 iommu 风暴处理机制（就像我们对中断以及许多其他东西所做的那样）会大大有助于‘到处都启用 iommu’这个目标”**（KS2014 档案） `<!-- ROW_MINE: ksummit-discuss.messages.347212 -->`
- 【Linux社区】Alexey Dobriyan：把 checkpatch 的问题归因于 Perl 正则堆叠的架构缺陷并逐项评估其警告——**“它是 Perl 毛病的一个教科书式例子。它不是像编译器那样解析 C 代码，而是把整个脚本堆成一坨正则。它大体能用（用 Perl 的话说叫‘在干它的活’），是因为人们大多遵守编码风格”**；其分类是 **“就单条警告而言：有些是好的（RETURN_VOID、DATE_TIME、USE_NEGATIVE_ERRNO），有些鉴于内核分配内存的风格是可以接受的但理由站不住脚（UNNECESSARY_CASTS，居然链接到 malloc() 返回 ‘int’ 的用户空间例子！）。然后还有 ALLOC_SIZEOF_STRUCT，它主张 ‘kmalloc(sizeof(*p))’”**；其结论是 **“问题在于 c-h.pl 在提交历史里制造噪声，并让 git-blame 变得不如它本可以的有用。就我而言，自它引入以来我基本上放弃它了”** `<!-- ROW_MINE: ksummit-discuss.messages.347213 -->`
- 【Linux社区】Greg KH：澄清其“核选项”立场并系统对比“代表登门”与“开发者登门”两种路径的后果——**“好，我不是在说‘永远不该采取法律行动’，但我在说的是与 Linus 相同的东西：‘只在最严峻的情形下’，核选项”**；**“所以是的，如果有人拿走我们全部的源码、贴上另一个许可证并改名，我会第一个打电话给我的律师让他们停止那样做。但那在这里从来不是情况”**；**“事实是，到目前为止我看到的是：与违规公司合作永远比带着律师或代表上门要好。回去再读一遍我对 Bradley 的回复，想想当有人敲开一家公司的门说‘我是内核版权持有人的代表，要你们发布你们所发布的所有代码’时，那家公司会经历什么。他们封舱备战、出于我已给出的所有理由奋力对抗”**；**“相比之下，一个开发者去同一家公司、找到写那段代码的工程师，问他们‘嘿，需要帮忙把你的代码合并到上游、让你下一个产品轻松点吗？’现在你就能与那家公司合作，让他们把代码一块块地往上游送，直到他们突然在这个社区里的投入远超从前，并看到合作的商业利益”**；**“这是完全不同的问题、不同的路径，而最终我们的路子行得通，SFC 的路子不行”**；其对 SFC 的批评是 **“我反对 SFC 那种‘让我们替你们处理那些烦人的版权问题’的立场（转述），因为当开发者那样做时，他们放弃了自己拥有的真正力量。SFC 是一招鲜（把代码给我们，全部，扔过墙来，否则我们起诉），而作为开发者，我有 101 招可用，能达成甚至更好的最终方案（公司成为社区的一部分，而不是被疏离）”**；**“开发者处在一个比他们意识到的更强大的位置，而我反对 SFC 夺走那份力量。事实上，SFC *需要开发者才能开业，如果没有开发者签他们的协议，他们就无事可做！”** `<!-- ROW_MINE: ksummit-discuss.messages.347214 -->`
