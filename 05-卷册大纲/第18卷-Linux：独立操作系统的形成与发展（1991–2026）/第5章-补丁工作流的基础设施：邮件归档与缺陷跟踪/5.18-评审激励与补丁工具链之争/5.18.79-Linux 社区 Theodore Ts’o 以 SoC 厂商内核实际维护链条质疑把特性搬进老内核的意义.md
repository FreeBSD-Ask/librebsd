# 5.18.79 Linux 社区 Theodore Ts’o 以 SoC 厂商内核实际维护链条质疑把特性搬进老内核的意义

- 【Linux社区】Theodore Ts'o：以 SoC 厂商内核的实际维护链条质疑“把特性搬进老内核”的意义——**“我真的不确定你想在这里解决什么问题”**；其现状描述是 **“据我所能判断，SoC 厂商提供的内核是某个 LTS 内核在某个时点的快照，之后他们就不再费心合并上游内核的任何 bug 修复或安全修复了。如果注意到某个问题（例如它被全国性媒体报道），他们可能会取个别补丁，但否则他们会卡在像 3.10.23 这样的胡闹版本上。然后产品厂商取走 SoC 内核、进一步魔改，一旦取了快照，据我所知他们也不再从 SoC 厂商那里接受滚动更新”**；**“我不确定这有多少是因为缺乏工程带宽、有多少是因为担心更新的 SoC 内核会引入回归，但无论哪种，他们会锁在一个老 SoC 内核上，并且显然只在注意到有问题时才取 bug 修复（而在多个案例中，我接到过 SoC 厂商求助电话，帮他们弄清一个问题，而答案往往是修复在最新 LTS 内核里，但那对他们没帮助）”**；其核心质问是 **“那么把特性搬进某个古老内核意义何在？谁会用它？肯定不是消费 SoC 内核的产品厂商。SoC 厂商？为什么不干脆鼓励他们把设备驱动弄进 staging、然后直接去用更新的 LTS 内核？因为我保证那会比取一堆随机特性、回溯进某个古老内核风险更小”**；**“或者就此而言，为什么不干脆去用最新主线内核……SoC 厂商或下游产品厂商可能得看 3 或 4 个补丁发布而不是一个。那真的那么难吗？”** `<!-- ROW_MINE: ksummit-discuss.messages.347346 -->`
- 【Linux社区】James Bottomley：以 2.4 企业内核的历史教训与“上游优先”政策的由来批评 LSK，并点出其恶性循环——**“它疯是因为它恰恰鼓励了错误的行为：厂商瞄准这棵树，而不是上游”**；**“历史在重演：这几乎就是发行版在它们的 2.4 企业内核里为所有树外补丁所用的那套精确理由。最终导致的灾难（补丁集比内核本身还大、无法全部上游化）正是直接导致它们转向‘上游优先’政策的原因”**；**“所有发行版更贴近地跟进上游，也意味着它被更好地测试：你离上游越远，遇到的问题就越多”**；**“那样的 diff 会无界增长……”**；**“你不会有的风险，如果你就直接遵循上游优先的话。你可以把这加到你因为不上游化补丁而制造出的问题清单里”**；其核心判断是 **“这种态度需要改变。如果企业界最终能意识到更贴近地跟进上游是个好策略——在主干上共享测试，为什么嵌入式不行？他们看到的那个‘上游内核的巨大风险’到底是什么？诚然，他们有一个恶性循环：因为瞄准了非上游内核，所以需要非上游的东西，这又导致他们不想上游化它，但打破这个循环难道不正是 Linaro 的职责吗？”** `<!-- ROW_MINE: ksummit-discuss.messages.347347 -->`

- 【Linux社区】Rik van Riel：以“已存在的协作树”收束争论——**“对一棵公共内核树上承载嵌入式特性的协作项目存在需求，这一事实表明他们已经在自己感受到痛了。缺失的是那个认识：我们已经有一棵这样的树，在那里所有人（不只是嵌入式那帮人）都在为特性协作。那就是上游内核。嵌入式公司可以选择花钱自己去重复大量上游内核的工作，或者参与一个更大的社区、减少重复劳动、让更多不在他们工资单上的开发者做更多工作”** `<!-- ROW_MINE: ksummit-discuss.messages.347350 -->`
- 【Linux社区】Timothy Bird（Sony）：以供应链实况与三个历史条件为嵌入式侧作系统辩护，并点出主线的具体缺口——**“我来试着回答这个（‘为什么嵌入式不行？’）问题。在很多情况下，当许多嵌入式 SoC 厂商最初开始用 Linux 时，有三件事的组合：1）内核不足以满足他们的需求（尤其在移动领域）；2）对上游化与社区缺乏经验；3）赶上市（总有赶上市）”**；**“Android 想出的方案——先发布、上游化以后再说或干脆不管——对他们极其奏效。它给整个供应链造成痛苦（我个人感受过），但它把事办成了。我的论证是，他们根本不可能遵循任何‘上游优先’策略，即便他们具备技能或意愿。举个例子：内核社区花了 3 年才接受他们在移动领域的电源管理策略”**；**“我们现在所处的位置是，其中一些 SoC 有数百万行树外代码。它在缓慢减少，但仍有一些重要领域主线内核就是没有发布产品所需的支持。我的心头刺是 USB 充电支持，Linaro 有一个补丁集被 USB 维护者搁置和/或忽视长达 2 年！！”**；**“这场讨论把推进某些东西上游化的难度给轻描淡写了。至少企业那帮人是在同一个芯片架构上工作。对某些 SoC 厂商而言，问题是他们在某些问题上采取完全不同的做法、已经在出货，而且与其他厂商的补丁之间几乎没有协同可言。那是嵌入式领域的分裂性问题，而企业发行版没有这个问题”**；**“再加上设备树造成的巨大变动，他们在过去几年能取得重大上游化进展简直是个奇迹。残酷的现实是，近期内主线在某些 SoC 上就是无法可行地用于出货产品。而没有哪个 SoC 厂商会停下来等它成熟再发布产品”**；**“现在——我并不认为 SoC 厂商无可指责。他们中许多人在做上游化工作时用了几乎最糟的方式，如果他们尝试过的话。我同情那种‘我们没能说服他们如何做对的事’的看法”** `<!-- ROW_MINE: ksummit-discuss.messages.347351 -->`
- 【Linux社区】Linus Torvalds：以“NO_IRQ 是坏的”直接裁定该 ABI 应彻底消失并给出两难论证——**“NO_IRQ 是坏的。我们很久以前就一致同意 0 就是‘无 irq’，而测试它的正确方式就是 if (!irq) …，那也是所有通用驱动用的方式。看看例如 git grep '(!.*irq)' 就知道那有多常见”**；**“（如果你 grep NO_IRQ，你会在尤其是 powerpc 的驱动与平台里找到很多，但那里 NO_IRQ 其实就被定义为 (0)，所以最终是同一回事）ARM 仍然有一个似乎被定义为 ((unsigned int)-1) 的 NO_IRQ，这只意味着有 bug 藏着：如果 ARM 真的用那个值表示‘无 IRQ’，那么所有通用驱动都会坏；如果 ARM 核心不用，那么那些仍用 NO_IRQ 的驱动就是坏的。两种情况下你都赢不了。所以请确保 NO_IRQ 完全消失（或者，如果你出于某些遗留理由坚持要那个令人困惑的 #define，就把它像 powerpc 那样设为 0，这样‘!irq’这种真正正确的测试方式也能工作）”**；对“我有值为 0 的真实 irq”的辩解则 **“有人说过‘但是但是但是我有值为 0 的真实 irq’，但那无关紧要——内核的 ‘irq’ 值不一定与中断控制器看到的那个值相同，因为中断控制器可以藏在各种其他嵌套控制器之后等等。所以一个架构可能需要把 ‘irq’ 翻译成实际的硬件中断控制器值”** `<!-- ROW_MINE: ksummit-discuss.messages.347352 -->`

- 【Linux社区】Linus Torvalds：把 powerpc 维护者拉进 NO_IRQ 清理并当场给出可执行的 sed 脚本方案——**“powerpc 显然是最大的情形，大约一半 NO_IRQ 实例在 arch/powerpc/ 之下（还有几处在 ppc 特定驱动里）……因为让它彻底消失、或至少稀少到没人会再把它当正确做法重新引入，那会真的很好”**；其脚本为**“git grep -wl NO_IRQ arch/powerpc/ | while read a; do sed 's/(\([a-z_]*irq\) != NO_IRQ)/(\1)/' < $a > $a.new; sed 's/(\([a-z_]*irq\) == NO_IRQ)/(!\1)/' < $a.new > $a; done——至少能修掉一部分。剩下的赋值和 ‘return NO_IRQ;’ 语句，再加几个 sed 脚本就能处理掉大部分。然后删掉 #define，做一次完整构建找出所有漏网的”** `<!-- ROW_MINE: ksummit-discuss.messages.347360 -->`
