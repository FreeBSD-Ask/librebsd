# 5.18.82 Linux社区OlofJohansson以ChromeOS的成功经验与rebas

- 【Linux社区】Olof Johansson：以 Chrome OS 的成功经验与“rebase 是甩包袱机会”的内行视角，拆解上游化的真实动力学——**“作为客户这很难——你离决策链好几步远，而且他们永远不会把产品失败归因于缺上游化”**；**“真正有杠杆的时点，是你为造部件的公司工作的时候。偏爱与已理顺上游故事的厂商合作，或者施压、帮助、指导其他厂商、或把他们对接到能帮忙的承包商，都是把合适的商业压力回传给厂商的好办法。Chrome OS 在这点上很成功（如果我可以自夸的话），让几家早先上游存在感很薄的厂商显著改善”**；其内行判断是 **“你谈‘让他们感受 rebase 之痛’，说得好像他们这些年没做过一样。事实是，他们已经很擅长了。简直是大师——擅长 rebase 对他们是竞争优势”**；**“rebase 也是他们能甩掉旧硬件支持的时刻。事实上，好几家盼着 rebase，因为那意味着能甩掉一大坨软件负担、（相对）轻装上阵”**；**“房间里另一头大象是：刚开始上游化、只有一部分代码进上游时，rebase 会极其痛苦，而且这段时间你常会从上游收到大量抵触。据我所见，避免这个的最好办法是换个名字/位置做上游化，这样可以保持并行实现直到准备切换。如果你踩到相同的文件/驱动名，等着你的就是大量冲突与痛苦”** `<!-- ROW_MINE: ksummit-discuss.messages.347404 -->`
- 【Linux社区】Al Viro：发起“tracepoint 与 ABI 稳定性保证”议题，指出 tracepoint 全体默认成为用户空间 ABI 的危险——**“现在没有任何机制可以说‘如果这个 tracepoint 坏了，不关我们的事’。它们全是用户空间 ABI 的一部分，可能把各种内核内部结构铸进石头。例如就在今天，一个往 kobject 原语加 tracepoint 的补丁系列发了出来；如果那成为稳定 ABI 的一部分，我们就把一切内嵌 kobject 之物的生存期规则暴露给了用户空间、且可能再也无法更改——只需要一个软件非平凡地使用它们”**；**“把内核内部暴露给调试脚本等是好的，但前提是我们承诺让那些脚本一直能跑。否则我们就是在承诺：一大坨我们根本看不见的代码、把手指深深插进内核内部，将被保持功能正常地穿过内核变更。这当然是彻底的疯狂”**；其结构性问题诊断是 **“tracepoint 是一坨无差别的大杂烩，用户空间没有任何办法区分它在用的是稳定的东西、还是某个人的等价于调试 printk 的无稳定承诺之物。而各位，外面确实有一些在各式用户空间项目上有提交权限的人，他们已把话说得非常清楚：他们找到的任何内核接口都是可以用的——原话是‘如果你不想它被用，你为什么把它放进内核？’。不管我多不喜欢那帮人的其他做派，我不能怪他们在那个政策上不够坦率。它已表达得非常清楚，我们最好认真对待这个警告”**；其提案为 **“我认为这需要在 KS 讨论；依我看我们至少需要某种方式，表达对单个 tracepoint 所作稳定承诺的程度，以及防止向全面稳定悄悄蠕变的机制——比如‘非稳定 tracepoint $FOO 被 $PROGRAM 使用，内核已 tainted’之类，至少先这样”** `<!-- ROW_MINE: ksummit-discuss.messages.347405 -->`
