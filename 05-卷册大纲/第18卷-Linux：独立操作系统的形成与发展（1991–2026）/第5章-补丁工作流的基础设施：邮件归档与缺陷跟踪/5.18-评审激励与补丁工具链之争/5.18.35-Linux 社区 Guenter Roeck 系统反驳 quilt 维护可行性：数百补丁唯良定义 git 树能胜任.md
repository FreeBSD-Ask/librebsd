# 5.18.35 Linux 社区 Guenter Roeck 系统反驳 quilt 维护可行性：数百补丁唯良定义 git 树能胜任

- 【Linux社区】Guenter Roeck：系统反驳 quilt 维护可行性——**其前雇主在 Yocto 用 patch series“很快放弃”改用 git；维护数百补丁时 git merge 轻松无痛、rebase 到新内核通常仅数小时、唯有良定义 git 树可做到；反问 QCOM 若用 quilt 树“那 250 万行 LOC 根本写不出来”**；披露 **chromeos-4.4 已在 4.4.14 上积累 4400+ 补丁（过半为 backport）**；断言 quilt 树仅适合不活跃修改内核的公司、活跃开发场景下不可行——数据密集 `<!-- ROW_MINE: ksummit-discuss.messages.346141 -->`
- 【Linux社区】Greg KH：以发行版团队为反例反驳 quilt 不可行论——**“It is possible, look at the Red Hat and SuSE kernel development teams”——新 release 期间全部工作以 quilt 进行、增删改补丁不停；SoC 场景下补丁几乎全是 driver/subsystem 专属、互不触碰、并不算难**；结尾抛出争议金句：**“It does take a better calibre of developer to do this type of thing, that might be a harder thing to deal with at some SoC vendors”（这需要更高水准的开发者、对某些 SoC 厂商恐怕才是难点）** `<!-- ROW_MINE: ksummit-discuss.messages.346142 -->`
- 【Linux社区】NeilBrown（SUSE）：澄清 quilt 用法真相——**“I do development upstream if git. Upstream first.”——开发全部在 upstream 用 git 完成、再用脚本把成果转成 quilt 需要的格式、使 quilt“是 pain 而非 nightmare”**；quilt 真正有用是 backport 补丁系列时可逐个解决冲突、在补丁列表中前后移动，而 git 缺少管理“待应用补丁分支”的机制（或可用 stgit）；总结 Greg 与 Guenter 实为一致：quilt 利于发布管理、不利开发 `<!-- ROW_MINE: ksummit-discuss.messages.346143 -->`
- 【Linux社区】Greg KH：确认与 Guenter 共识（quilt 利于发布管理、开发需 git 形态）并点出症结：**人们拿你发布的东西继续开发、故发布产物须是可开发的格式**；透露与 Geert 讨论后获得方案：**将 LTSI 树输出为可开发的 git 树——“Much like I've started to do now with the stable trees, and the -rc git tree of patches built from my quilt series”——stable 维护已采用“quilt 系列→-rc git 补丁树”的双轨输出**——stable 工作流形态演进的一手制度证据 `<!-- ROW_MINE: ksummit-discuss.messages.346144 -->`
- 【Linux社区】Steven Rostedt：提出 stable 信任层级论——**维护者自行 cherry-pick 进 for-stable 分支与 stable 团队从 Linus 树 cherry-pick 的差别在于信任级别：历史上不止一次有人发给 Greg 尚未进入 mainline 的补丁；改用 git pull request 会让核验更难**；提议自动化验证：**每个 commit 以特定方式指明其 backport 的上游 commit、工具与 Linus 树中对应 commit 比对、差异过大则拒收须人工放行**；剩余难点是判定改动属 bug fix 还是 feature、是否够格进 stable（KS2014 档案） `<!-- ROW_MINE: ksummit-discuss.messages.346145 -->`
- 【Linux社区】Jeff Layton：以 OFD file lock 重命名案例论证 API 评审缺口——**file-private 到 OFD 的补丁连载数月、“it wasn't until it was merged that people started speaking out over the name”（合并后才有反对声）、若早知 linux-api@ 并抄送或可提前解决**；欲将 OFD lock 推回 POSIX spec、主张建立与 POSIX 组织的明确互动渠道；追问评审边界：**新 syscall 显然需严审、但新 mount option 算不算 API/ABI 变更？** 同时警示流程不可过于形式化否则将痛苦难行（KS2014 档案） `<!-- ROW_MINE: ksummit-discuss.messages.346146 -->`

- 【Linux社区】James Bottomley：反驳 NeilBrown“git 无补丁分支管理”论——**基础 git 已具备等价能力：git cherry-pick 可接受补丁范围、一次选定一批补丁批量 backport；git cherry 可在两个 commit id 不同的分支间近似判定哪些补丁相同（approximation、因其采用 matching 机制）**；承认输出格式“对不熟者有点吓人”（a bit frightening）、stgit 用户体验或更好、但基本 git 即可完成 quilt 式操作 `<!-- ROW_MINE: ksummit-discuss.messages.346148 -->`
