# 5.18.72 Linux 社区 David Woodhouse 以三组专有替代品案例论证违规并非无受害者

- 【Linux社区】David Woodhouse：以三组专有替代品案例论证“违规并非无受害者”，并拆解“不起诉即无风险”对商业逻辑的釜底抽薪——**“Greg，这完全是毫无帮助的夸张。你所有的例子都在打一个巨大的稻草人。没人在把公司称为‘敌人’，也没人试图说它们没有对 Linux 的发展做出巨大贡献。我们当然想要企业参与。我们只是希望每个人都遵守许可证的条款”**；**“有一小撮不良行为者就是不做许可证要求他们做的事。而那并非无害。当存在一个闭源但‘够用’的方案时，它就大幅降低了去做一个真正开源方案的动力。没有 OpenAFS，我们会早得多地在内核里获得真正的 AFS 支持。没有 nVidia 驱动，我们在 nouveau 上会有快得多的进展。没有仅二进制的 Broadcom 无线驱动，我们会有一个好得多的平台供 OpenWRT 之类在其上开发”**；**“当然，有些 GPL 违规是‘无受害者的犯罪’，但许多不是。许多违规者实际上是在与那些为做正确的事而付出额外成本的诚实公司竞争，并通过走捷径来削价”**；**“James 说，为 GPL 代码做贡献的‘坚实商业理由’基于这一事实：‘你的竞争对手必须向你展示他们将用来与你竞争的那份代码。’当然，那是我对‘必须’这几个字的强调——因为在一个从没有人真正被要求遵守许可证条款、每个人都像对待 BSD 那样蒙混过关、只在自己乐意时才回馈的世界里，James 的‘坚实商业理由’底子就塌了”**；**“在 GPL 说你‘必须’回馈 GPL 代码时未能回馈是一种风险。你似乎在主张你想让以那种方式违法明确地不成为风险，而你似乎没有意识到我们需要它成为风险，因为那是我们希望永远足以解决每一桩违规的所有静默谈判的支撑”** `<!-- ROW_MINE: ksummit-discuss.messages.347215 -->`

- 【Linux社区】Joe Perches：给出其对 checkpatch 定位的核心判断并附实测命令与统计——**对 80 字符限制的争议回应“那个论证已经做过好几次了。它让 Linus 满意。我无所谓”**；**“我认为最大的问题是有些人把 checkpatch 的消息当成教条、而不是可忽略的哞叫”**；其改良建议是 **“我仍然认为 ERROR→defect、WARNING→unstylish、CHECK→nitpick 会是个好改动（lkml.org/lkml/2015/7/16/568）”**；对 git-blame 噪声则指出 **“git-blame 里几乎所有的杂乱都可以用 -w 避免”**；并给出其自己的实测命令与统计（**git log --pretty=oneline --author=torvalds --no-merges --since=1-year-ago 过滤后逐条跑 checkpatch，再以 grep -P “^(ERROR|WARNING)” | cut -f1,2 -d“:” | sort |uniq -c | sort -rn 汇总**），结果为 **46 WARNING:LONG_LINE_COMMENT / 45 WARNING:LEADING_SPACE / 37 WARNING:LONG_LINE / 16 ERROR:GIT_COMMIT_ID / 11 WARNING:COMMIT_LOG_LONG_LINE / 5 WARNING:BRACES / 2 WARNING:BAD_SIGN_OFF / 2 WARNING:AVOID_BUG / 2 ERROR:SPACING / 1 WARNING:SPLIT_STRING / 1 WARNING:FILE_PATH_CHANGES / 1 WARNING:ENOSYS / 1 ERROR:MISSING_SIGN_OFF**；对工具语言则 **“唉，我也不是 Perl 人。我认为它几乎全是正则，而大多数人并不擅长正则。所以它是 Perl 还是 Python 都无所谓。spatch 不是合适的工具。你会建议用什么替代？”** `<!-- ROW_MINE: ksummit-discuss.messages.347217 -->`
- 【Linux社区】Theodore Ts'o：明确支持存在“红色按钮”但主张决定权在 Linus 而非 SFC，并给出其评判 SFC 议程的证据链——**“就记录在案，我相信可以存在需要那个闪亮红按钮的情形。我只是希望是 Linus、而不是 SFC（或 SFC 自己承认的少数派开发者群体）来决定何时适合按下它”**；**“我说过，再说一遍。对我来说，这更多是项目治理问题。我们不让随便哪个恼火的军官决定何时发动第三次世界大战。同样，Linux 有既定的共识流程，会考虑所有利益相关方——是的，包括那些 Bradley 在会议演讲里如此热爱抨击的‘邪恶企业’”**；**“（Linus、Greg 和我都提到过 Bradley 的演讲，因为幸运的是它们在 YouTube 上可看。我们一直在看它们，然后把它们与 Bradley、Karen 和你自己所声称的 SFC 立场作比较。）”**；**“SFC 似乎愿意接受一小撮开发者，并且似乎宣称‘我们会按客户告诉我们的去做’。我们可能不能或无法阻止 SFC，正如我们能阻止 Patrick McHardy 的事也有限”**；**“但 Linus 已相当清楚地表明了他的偏好，而如果 SFC 将 100% 支持 Bradley 在他 linux.conf.au 演讲中所采取的立场——即‘我们必须在尽可能多的法律场合处理内核模块问题’以及‘由于公司因诉讼风险转向 Toybox 而耗尽了 BusyBox，Linux 是 GPL 的下一个伟大战场’——那么也许就能理解为什么许多内核开发者不会信任 SFC 的议程与动机”** `<!-- ROW_MINE: ksummit-discuss.messages.347218 -->`
